# 3416: Reconcile archives a live run when an earlier PR from the same branch name has merged

Surface: infra

**Related:** #3503, #3412, #3249, #2870, #2912, #2986, #3079, #3263, #3284, #3289, #3295, #3297, #3363, #3442, #3483, #3515

## Current State

- **Observed incident (2026-10-17, run `2026-10-17T144508-spec-3375-3380`).** A background reconcile pass from a sibling session archived this live run at 17:19:21Z, while it was mid-build and its own PR #3406 was OPEN. It moved the directory to `.claude-tweaks/pipelines/archive/` and wrote `run-state.json` `{status: 'clean', worktree: null}`. The run was archived again at 18:35:03Z, a minute after `console.json` was written. Both of the run's issue claims were also released twice (15:12Z and 18:18Z) with reason `merged: reconciled from PR #3391`. No archive commit landed, so the owning session restored the run by hand. Confirmed via `gh pr view`: #3391 (MERGED 2026-10-17T14:09:02Z) and #3406 share the head branch `worktree-record-3229`, because the worktree was reused for the next run.
- **Cause 1: the PR is identified by branch name, not by the run's own PR number.** In `plugin/bin/lib/reconcile/archive-merged.js`'s main loop (line 1853), the branch comes from the live worktree entry: `(wtEntry && wtEntry.branch) || fallbackBranch(...)`. `archiveMergedRun` (line 1620) then calls `resolvePrState(root, branch)`, which runs `gh pr list --head {branch}`. `pickGoverningPr` in `plugin/bin/lib/reconcile/pr-state.js` (line 64) returns any MERGED PR in that list ahead of an OPEN one. So a reused branch name returns the old merged PR, and `decideArchiveCore` (line 320) sees `MERGED`. The by-number probe, `resolvePrStateByNumber(root, state.pr.number)`, runs only in the `if (!branch)` fallback (lines 1854-1920). It never runs when a branch resolves.
- The clean-status sweep (the `iterCleanRunDirs` loop at line 1941) has the same flaw. It derives the branch via `fallbackBranch` (`plugin/bin/lib/hooks/run-integrity.js` line 172, from `state.pr.branch` or `decisions.md`) and goes through the same `archiveMergedRun` call.
- Claim release has the same flaw. `plugin/bin/lib/reconcile/release-merged.js` (line 429) builds the same branch join. It resolves by branch first via `resolvePrStateAsync(root, c.branch)` (line 467) and probes `pr.number` only for candidates whose branch did not resolve (line 485). #3412 (5cf9073d3, merged 2026-10-18, after the incident) narrowed the damage: `decideRelease` now releases on MERGED only when that PR actually closes the issue (`prClosesIssue`, line 53). But the wrong PR still governs. A reused-branch run gets `pr-merged-not-closing` or `issue-closed` evidence where it should get `pr-open` (line 99), whose own comment says "open PR means work may be landing — issue-closed evidence never overrides". With #3406 being the run's own open PR, the `pr-open` guard never fires.
- **Cause 2: the staged-items check reads only the top-level `staged/`.** With no `console.json`, `decideArchiveCore` archives once `hasStagedPending === false` (#3249). `hasStagedItems` (line 397) runs `readdirSync(path.join(runDir, 'staged'))` only. A multi-spec run keeps per-spec items under `spec-{N}/staged/` (`plugin/skills/flow/multispec-run-dir-layout.md`; `listSpecDirs`, line 462, already enumerates those subdirectories). In the incident, `spec-3375/staged/` held three items, and the run was archived with them pending. `hasStagedItems` has three callers: `classifyRunDir` (line 1494), `archiveMergedRun` (line 1626), and the main loop's by-number fallback (line 1894).
- With a console present, Cause 2 no longer applies, and Cause 1 alone archived the run the second time. A run whose branch name ever backed a merged PR cannot survive past its own console.
- `reap-merged.js` (line 209) also resolves PR state by worktree branch (`resolvePrState(root, wt.branch)`). It removes worktrees, not run dirs, and has no run-state join of its own, so it is out of scope here (see Gotchas).

## Deliverables

- In `archive-merged.js`, when a run's `run-state.json` carries `pr.number`, resolve PR state by that number (`resolvePrStateByNumber`) before any branch-name lookup. Do this in both the main loop and the clean-status sweep. Use the branch-name path only when no `pr.number` is stamped. In practice `archiveMergedRun` takes the run's state (or a pre-resolved PR state) so both callers share one resolution order. The existing `!branch` by-number fallback keeps its current behavior for runs with no derivable branch.
- In `release-merged.js`, a candidate whose run state carries `pr.number` resolves by number (`resolvePrStateByNumberAsync`) instead of by branch. Branch-joined resolution remains the path for candidates with no stamped number. A run's own OPEN PR then reaches `decideRelease` and yields `pr-open`.
- `hasStagedItems(runDir)` also counts non-dotfile entries under every `spec-*/staged/` directory (via `listSpecDirs`). Keep the existing fail-closed rule: any read error other than ENOENT counts as pending, at every level.
- Regression tests in `tests/bin-lib/reconcile/archive-merged.test.js` and `tests/bin-lib/reconcile/release-merged.test.js`. Each test fails against the current code and passes after the fix.

## Acceptance Criteria

1. A non-clean run dir whose `run-state.json` stamps `pr.number` of an OPEN PR, while its live worktree's branch also backs an older MERGED PR, is skipped with reason `pr-open` by `archiveMerged` and is not moved to `archive/`.
2. A clean-status run dir (`status: clean`) whose `pr.number` is OPEN is not archived by the clean-status sweep, even when its `state.pr.branch` also backs a MERGED PR.
3. In `releaseMerged`, a live claim whose run state stamps `pr.number` of an OPEN PR is skipped with reason `pr-open`. It is not released, and no tombstone is written, even when the run's branch backs a MERGED PR that closes the issue.
4. A run with no `pr.number` stamped keeps today's branch-name resolution in all three paths. Existing tests in both suites pass unchanged.
5. A multi-spec run dir whose only staged items sit under `spec-{N}/staged/`, with a MERGED PR and no `console.json`, is skipped with `console-never-rendered`. The same run dir with every `spec-*/staged/` empty or absent still archives (the #3249 fast path is preserved).
6. Each new test for criteria 1, 2, 3 and 5 is shown failing against the pre-fix code (by reverting the source change) before the fix is kept.

## Release Note

Fix the reconciler archiving a live run, and releasing its claims, when an earlier PR from a reused branch name had already merged, or when a multi-spec run still had staged items under its per-spec directories.

## Technical Approach

- **PR identity.** Treat `run-state.json`'s `pr.number` as the run's PR identity. It is stamped once at PR-early lifecycle time and never cleared. A branch name is a reusable label. Add one resolution helper in `archive-merged.js`, used by both archive loops: a stamped `pr.number` goes to `resolvePrStateByNumber`, otherwise the branch goes to `resolvePrState`. `archiveMergedRun` then takes the resolved PR state, or the run state, so the main loop and the clean-status sweep cannot drift apart. `resolvePrStateByNumber` already returns the same `{state, number, mergeCommit, ...}` shape (or `gh-absent` / `network-failure` / `invalid-arguments`), so `decideArchiveCore` and `localHasMerge` need no change. Map `invalid-arguments` to a skip rather than an archive.
- **Missing-PR fallback.** When a by-number probe returns `null` (no such PR), fall back to the branch-name path. Do not skip permanently: a stale or mistyped stamp should not strand the run.
- **Claim release.** In `release-merged.js`'s Phase 1.5, split candidates three ways. A candidate with `prNumber` goes to the by-number pool. One with a branch and no number goes to the branch pool. One with neither keeps its join-failure reason. The existing by-number block for join failures becomes the general by-number path. Keep the `runWithConcurrency` pooling.
- **Staged items.** `hasStagedItems(runDir)` checks the top-level `staged/`, then `listSpecDirs(runDir)` mapped to `path.join(runDir, name, 'staged')`, with the same dotfile filter and ENOENT-versus-other-error rule at each level. `listSpecDirs` swallows an unreadable run dir and returns `[]`. That is acceptable here because the top-level read already fails closed on a non-ENOENT error.
- **Tests.** Use the suites' existing gh interception, which puts a PATH-prepended `gh` wrapper script ahead of the real one. Dispatch on argv so `gh pr list --head {branch}` returns a MERGED PR, while `gh pr view {n} --json ...` (the by-number resolver's call, `pr-state.js` line 176) returns OPEN. Add an orthogonal case: a stamped `pr.number` that is MERGED while the branch's list returns OPEN still archives, which proves resolution is keyed on the number and not on a MERGED-wins pick.

### Key Files

- `plugin/bin/lib/reconcile/archive-merged.js` — resolve the run's PR by stamped `pr.number` first in the main loop and the clean-status sweep (shared helper, `archiveMergedRun` signature); `hasStagedItems` counts `spec-*/staged/`
- `plugin/bin/lib/reconcile/release-merged.js` — Phase 1.5 resolves by `pr.number` for every candidate that stamps one, before any branch join
- `plugin/bin/lib/reconcile/pr-state.js` — read-only reference: `pickGoverningPr`'s MERGED-wins tie-break and `resolvePrStateByNumber`'s return shape; no change expected
- `plugin/bin/lib/hooks/run-integrity.js` — read-only reference: `fallbackBranch`; no change expected
- `tests/bin-lib/reconcile/archive-merged.test.js` — regression tests for criteria 1, 2, 4 and 5
- `tests/bin-lib/reconcile/release-merged.test.js` — regression test for criterion 3 (and criterion 4's unchanged path)

## Gotchas

- #3503 (ready, `auto:build`) edits the same merged-PR archive paths in `archive-merged.js` (`decideArchiveCore` and the by-number fallback) to add a manifest-closure check. It is a different trigger with the same symptom. Building both concurrently will conflict, so sequence them, or rebase whichever lands second. Both should share the one PR-resolution helper rather than each adding its own.
- `pickGoverningPr`'s MERGED-wins tie-break is deliberate for branch-scoped callers (`archive-branches.js`, `prune-remote.js` opts into `preferOpen`). Do not change it in `pr-state.js`. The defect is using a branch-scoped answer for a run-scoped question, not the tie-break itself.
- `reap-merged.js` (line 209) has the same branch-name shape for worktree removal. A reused worktree whose branch backed a merged PR could be reaped while a new run is live in it. The `own-cwd` and `in-use` (locked) skips usually prevent this, which is why it is out of scope here. If the build finds an unlocked live worktree reachable this way, file a separate record rather than widening this one.
- The Review Console's reader, `plugin/bin/lib/console/resolve.js`'s `readSnapshot` (line 228), also reads only the top-level `staged/`. Widening `hasStagedItems` to `spec-*/staged/` deliberately diverges from it on directory scope, failing toward not archiving. Do not "align" the two by narrowing `hasStagedItems` back. Whether the console should also surface per-spec staged items is a separate question.
- The existing `installGhWrapper` in `archive-merged.test.js` returns one canned body for every `gh` call. The new fixtures need a wrapper that dispatches on argv: `pr list` versus `pr view` (`pr-state.js` line 176 calls `gh pr view {n} --json ...`). `installGhIssueStateWrapper` is the precedent.
- #3412 changed `release-merged.js` after the incident. Current code would not have released this run's claims via #3391, since #3391 does not close #3375 or #3380. Criterion 3 therefore uses a MERGED PR that *does* close the issue, the case where the wrong PR still causes a release today.
