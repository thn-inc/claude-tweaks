# 3137: dispatch MCP transport: list_issues silently truncates labels when `fields` is passed

Origin: dispatch next (scheduled Routine firing, 2026-10-14)

**Related:** #3098

## Current State

`skills/dispatch/mcp-transport.md` documents the `gh`-absent MCP transport path for
`queue-pull-script.md`'s queue pull (`mcp__github__list_issues`), but says nothing about label
fidelity. During a live `gh`-absent firing (GH_TOKEN/GITHUB_TOKEN were proxy placeholders, `gh
auth status` failed), calling `list_issues` with an explicit `fields` array that included
`"labels"` returned a **silently truncated** labels array for every one of 11 candidates checked
— e.g. issue #2807 actually carries `ready, risk:low, size:medium, type:task, auto:build,
bot:in-progress, priority:low` (7 labels, confirmed via `mcp__github__issue_read`'s `get_labels`
method), but the same issue came back from `list_issues` with only `["ready","risk:low",
"size:medium","type:task"]` — missing `auto:build`, `bot:in-progress`, and `priority:low`
entirely, with no error or truncation flag. Cross-checking all 11 candidates individually via
`issue_read` was the only reason this run caught it before trusting the result for an eligibility
decision.

Feeding a truncated labels array into `parseRecordFacets` (`bin/lib/issues/record.js`) can
misjudge `grants.build` / `bot.inProgress` / `bot.blocked` / `bot.parked` / `grants.merge` — e.g.
a record whose `bot:in-progress` label gets dropped by the truncation would look falsely
eligible to a headless dispatch firing, risking a double-claim of a record another session
already owns.

## Deliverables

Update `skills/dispatch/mcp-transport.md` (and `queue-pull-script.md`'s MCP-path note, if it also
needs it) to document this gotcha and require one of:
- Omit `fields` entirely on the primary `list_issues` queue-pull call, so the full, unprojected
  labels array is returned (verify this actually avoids the truncation first), or
- Require a per-candidate `issue_read`/`get_labels` cross-check of the labels actually used for
  facet parsing, before any eligibility or exclusion decision is made from an MCP-sourced queue
  pull — promoted from "a firing improvised this" to a standing documented step, the same way
  #2523's native blocked-by workaround was promoted in the same file.

## Acceptance Criteria

- `mcp-transport.md` names the `list_issues` `fields`-triggered label truncation explicitly, with
  the issue number/label counts above as evidence
- A standing, required mitigation is documented (fields omission confirmed safe, or a per-candidate
  verification step) so a future `gh`-absent dispatch firing doesn't need to independently
  rediscover this
- If the fields-omission fix is verified to avoid truncation, `queue-pull-script.md`'s MCP-path
  note is updated to recommend it as the default

## Release Note

No user-visible change: documents and mitigates a latent correctness gap in the `gh`-absent MCP
transport path that could cause a headless dispatch firing to misjudge an issue's labels.
