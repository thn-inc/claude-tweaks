# 6353: Finish `/claude-tweaks:design`: parts and estimate, approval, and filing the parts through decomposition as written

Surface: backend
Risk-flags: none
Blocked by #6352

## Overview

The design skill's last three steps turn a checked design into filed work: the parts are written and sized before approval, the maintainer approves the design with its parts and estimate, and the parts are filed as a parent issue with sub-issues exactly as written. Today `/claude-tweaks:specify` derives its own work units from a design doc, so what gets filed is not what was approved. This record adds the three steps and lets decomposition file a given parts list.

## Non-Goals

- A token estimate from per-station history. Until stations have history, the estimate is the number of parts by size times v6's measured use per size, and says so.
- New support for orders that span repositories. One parent per repository is filed by running the last step in each repository with the same design, with blockers in the `owner/name#N` form v6 already reads.
- Changing what decomposition does for a design doc with no parts section.

## Prerequisites

- The design skill through step 7 (the record this one is blocked by).
- Decided by the maintainer on 2026-11-27, after filing: this work is dispatched now, in parallel with its siblings, and its pull request merges by itself once every gate is green. An earlier line here said it was built by hand and was not for `auto:build`; that no longer holds.

## Current State

- `/claude-tweaks:specify`'s decomposition mode (`plugin/skills/specify/decomposition-mode.md`, Step 2) breaks a design doc into work units by its own sizing and boundary rules, then decides about a parent (Step 2.6).
- Its mechanical range (Steps 3 to 9, `decomposition-mode-closeout.md`) creates the records, links them, runs a red-team and deletes the consumed design doc.
- A cross-repository blocker is written `owner/name#N` and read on every blocker surface.

## Deliverables

- [ ] **Step 8, Parts and estimate.** The parts are written into `design.md` before approval, in a fixed table: each part's name, size, repository and what it waits for, with the part that makes the order visible to a user last. The token estimate follows from that list and states its basis.
- [ ] **Step 9, Approve.** The maintainer approves the design with its parts and estimate. The skill writes a status line into `design.md`, and from then on refuses to change the frame, the approach or the parts without a new approval.
- [ ] **Step 10, File the issues.** The parts become a parent issue with sub-issues and blockers through `/claude-tweaks:specify`'s decomposition, which is given the parts list and files it as written. The worth-it measure from the frame is copied onto the parent issue.
- [ ] Decomposition accepts a design whose parts section is present and approved: Step 2 takes those parts as its work units, in that order, with those blockers, and skips its own sizing and boundary heuristics. Overlap analysis against open records, the file-overlap check, the collapse decision and everything in Steps 3 to 9 run as today.
- [ ] A part naming another repository is not filed here: decomposition lists it in its summary as left for that repository's run.
- [ ] A design folder is kept after filing, since it holds the evidence and the notes: decomposition marks the parts as filed in `design.md` with their issue numbers and does not delete the folder.
- [ ] The skill graph, `/help` and `CLAUDE.md`'s pipeline lines say that an order enters through the design skill and that decomposition files an approved parts list as written.

## Acceptance Criteria

- [ ] Given an approved `design.md` with four parts for this repository, decomposition files exactly four sub-issues with those names and blockers under one parent, in that order. Verify: a fixture-driven test over the parts-table parser, and one real filing quoted in the pull request.
- [ ] An approved parts list of two or more parts fixes the parent decision: decomposition keeps a parent and does not collapse. Its red-team may flag and stage a finding on a part but never changes a part's name, size or blockers, and a gate that would change one stops and asks. (Settled at filing from a red-team finding.)
- [ ] Given the same file with no status line, decomposition refuses to use the parts list and says the design is not approved.
- [ ] Given a design doc with no parts section, decomposition behaves as today. Verify: the existing decomposition conformance suites pass unchanged.
- [ ] The parent issue carries the worth-it measure word for word.
- [ ] After approval, an edit to the parts table through the skill asks for a new approval first.
- [ ] The status line carries a digest of the frame, the approach and the parts table. The parts-table parser recomputes it and refuses a file whose digest does not match; the filed-issue marks are left out of the digest. Verify: a parser test that edits one cell after approval. (Settled at filing from a red-team finding.)
- [ ] `plugin/skills/specify/SKILL.md` stays under the 52,500-byte read limit.

## Release Note

`/claude-tweaks:design` now ends by listing the parts of an order with an estimate, taking approval, and filing the parts as written. `/claude-tweaks:specify` files an approved parts list without deriving its own.

## Technical Approach

Parse the parts table in code, in a small module under `plugin/bin/lib/`, so that both the skill and decomposition read one definition of the table and the status line. Decomposition's Step 2 gains one branch at its top: an approved parts list is the work-unit list. The keep-and-mark rule for the design folder is a new row in Step 7's table. Read every caller of decomposition's Step 2 output (the handoff template in `mechanical-handoff.md`, the planning entry in `planning.md`) before changing its shape.

## Gotchas

- `plugin/skills/specify/SKILL.md` is 43,737 bytes; the flag line is 47,250 and the limit 52,500. Put the new text in `decomposition-mode.md` (24,261 bytes), not in `SKILL.md`.
- Decomposition's conformance tests pin its prose; run the full suite before the pull request leaves draft.
- A part's size uses the labels this repository already has (`size:low`, `size:medium`, `size:high`).
- An approved design must not be re-derived on resume: decomposition's idempotency check matches a part to an already-filed issue by fingerprint.
- Define the parts table once, in the parser module header: header row, column order, `owner/name` for repository, a comma-separated blocker column, the `size:*` values, and the filed-issue column the parser ignores when it checks the approval. The status line's exact text and the heading holding the worth-it measure are defined there too.
- A part's unit slug is a slug of its name, stable across resume; renaming a filed part needs a new approval. A part blocked on a part left for another repository keeps its blocker as the symbolic part name until that repository's run writes the `owner/name#N` form.
- The estimate's per-size figures come from v6's per-size token use in the model-profile or timing data the builder cites; when none is found the estimate says so instead of inventing a number.
- `decomposition-mode.md` stays within its own read limit; add the check to the size conformance test if it has none.
