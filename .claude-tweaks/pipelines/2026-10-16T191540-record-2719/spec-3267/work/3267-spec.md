# 3267: closing-tally.js counts 0 for every line apply-refine-labels.js logs

**Related:** #2729, #1073, #844

Defer-reason: tangential

## Current State

`backlog/refine-closing-summary.md` requires the closing tally line to come from `bin/closing-tally.js --run`, never hand-composed (#2729). That CLI counts only lines matching its `PATTERNS` (`plugin/bin/lib/closing-tally/closing-tally.js:30-41`), all phrased as `Backlog refine: {verb} …` from the closing-summary templates. Its `unclassified` drift guard also only scans `Backlog refine:`-prefixed lines.

The lanes' documented apply path, `bin/apply-refine-labels.js` (#844, #1073), logs its own lines as `apply-refine-labels: #{n}: applied +{labels}` / `#{n}: comment posted` (`:82-99`). Those match no pattern and carry no `Backlog refine:` prefix, so they are counted as zero and never reported as unclassified.

Observed in run `2026-10-16T172830-backlog-standalone` (6.140.0): 2 grants, 1 priority and 1 needs-decision applied through `apply-refine-labels.js`, and the CLI rendered `0 priority set · … · 0 granted · … · 0 needs-decision · 0 skipped · 0 failed` with `unclassified: []`. A correct tally only came after hand-logging the template lines too. A refine run that follows the documented path reports a clean zero-write run with no caveat.

## Deliverables

- [ ] Make one of the two sides authoritative. Either `apply-refine-labels.js` emits the `refine-closing-summary.md` template line for each write (it knows the lane from its actions), or `closing-tally.js` classifies `apply-refine-labels:` lines into the existing fields. Pick one, and don't double-count when both forms exist in one `decisions.md`.

- [ ] Widen the `unclassified` guard so that any `/backlog`-section AUTO/FAILED line that is neither a counted pattern nor an `IGNORED_PATTERNS` entry is reported, not just `Backlog refine:`-prefixed ones.

### Key Files

- `plugin/skills/backlog/refine-closing-summary.md` — the template lines (only if wording changes)

## Acceptance Criteria

1. A test feeds `closing-tally` a `decisions.md` written only by `apply-refine-labels.js` (grant, priority, needs-decision, and a flag-back with its comment line), and the tally reports the true per-type counts.

2. A test with both the `apply-refine-labels` lines and the template lines for the same writes counts each write once.

3. A test with an unknown `/backlog` AUTO line that has no `Backlog refine:` prefix gets it listed in `unclassified`.

4. `npm test` passes.

## Build Notes

- **Authoritative side: `closing-tally.js`.** apply-refine-labels' actions JSON carries no lane field, so the classifier types each `applied {labels}` line by the labels it applied (`+auto:build`/`+auto:merge` → granted, `+priority:*` → priority, `+needs:decision` → needs-decision, `-ready` → flagged back). `apply-refine-labels.js` itself is unchanged.
- **Beneficial deviation (Common Step 4.5): the double-count rule is per source, not whole-file.** Per (field, record) the count is max(template count, apply count): a write logged both ways counts once, while distinct same-source writes on one record (a priority and a Related write that both failed) still count separately. The whole-branch review overturned the first whole-file dedup, which undercounted those cases.
- **Beneficial deviation: partial flag-back / needs-decision.** A record whose label edit landed but whose comment failed counts once, under `failed` only, as `refine-lanes.md`'s counting rule already required.
- apply-refine-labels lines count only under `## /backlog`, and both apply regexes anchor to the producer's exact `- {STATUS} {HH:MM:SS} — apply-refine-labels: #N: ` prefix.
