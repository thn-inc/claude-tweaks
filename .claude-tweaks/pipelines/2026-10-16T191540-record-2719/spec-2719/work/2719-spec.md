# 2719: backlog refine: two concurrent unattended-posture grant sweeps produced divergent auto:merge verdicts on the same records with no reconciliation signal

Surface: infra

Origin: by:feedback (self-referential session evaluation, /claude-tweaks:feedback bare invocation)

**Related:** #2718, #2720

## Current State

This project runs `autonomy: unattended`, so `/claude-tweaks:backlog refine`'s labeling-lane confirm gate resolves with zero clicks (`refineAutoApply`), and (per policy) the grant chain can also originate autonomously. In a session on 2026-09-20, a whole-queue grant-check pass computed `RECOMMEND_BUILD`/`RECOMMEND_MERGE` judgments for 40 ready records, in parallel with what turned out to be a concurrent actor running the same sweep. Comparing the two sets of judgments on records both actors evaluated showed real disagreement on the `RECOMMEND_MERGE` call for at least six records — one actor recommended `auto:merge`, the other did not, for the same content. Because `unattended` removes the human click from this decision, whichever actor's write landed first became the final, unreconciled state, with no visibility that a second, differently-reasoned judgment existed.

`refine-mode.md`'s existing pre-write reverify (Step 5) already catches the underlying race mechanically: "A grant row whose live labels lost `ready`... has had its premise invalidated by a concurrent write: drop it from this write, log an `AUTO … skipped …` line... and skip the `gh edit`/`writeRecord` calls." What it does not currently do is distinguish *why* the write was skipped — a concurrent grant that agreed with this run's own judgment logs identically to one that disagreed, so the audit trail cannot currently answer "did two independent judgments actually diverge, or did they just repeat the same conclusion?"

## Deliverables

- When a grant sub-stage's pre-write reverify (`refine-mode.md` Step 5) detects that a record it computed a fresh grant-check judgment for was already granted differently by a concurrent write (rather than merely "already granted the same way"), log the disagreement specifically — not just "skipped: premise changed" — naming both the discarded judgment's `RECOMMEND_MERGE` value and rationale, and the live state's actual grant, so a human reviewing `decisions.md` can see that two independent judgments diverged rather than assuming they agreed.
- Consider whether repeated divergence on the same class of record should feed the trust-signal machinery (`_shared/trust-table.md`) as a distinct low-confidence indicator, separate from the existing "insufficient evidence" state.

## Acceptance Criteria

- A pre-write reverify skip caused by a concurrent grant that disagrees with this run's own computed `RECOMMEND_MERGE` value is logged distinguishably from a skip caused by a concurrent grant that agrees.
- The `decisions.md` audit trail lets a human find every such disagreement from one sweep without re-deriving it by hand.

## Release Note

Flagged when two concurrent backlog refine runs grant auto-merge differently on the same record.

## Technical Approach

`refine-mode.md`'s Step 5 pre-write reverify (the "General rule" and grant-row paragraphs) already re-fetches the record's live labels immediately before writing and compares them against the row's Step 1-captured premise; on a mismatch it currently drops the write and logs a generic `AUTO … skipped …` line. Extend that comparison at the grant-row site only: when the mismatch is specifically "live state already carries a grant (`auto:build`/`auto:merge`) that differs from this run's own computed `RECOMMEND_BUILD`/`RECOMMEND_MERGE` verdict," emit a distinguishable log line naming both this run's discarded verdict (with its rationale) and the live grant that won the race, instead of the existing generic `{what changed}` skip text — reusing the same `AUTO … skipped …` template and `skipped` tally bucket (`refine-closing-summary.md`), just with richer `{what changed}` content for this one case. Leave the fetch-failure and non-grant reverify paths (priority/related rows, body reverify) untouched — this only adds detail to the grant-row mismatch branch.

### Key Files

- `plugin/skills/backlog/refine-mode.md` — Step 5's pre-write reverify, specifically the grant-row mismatch branch that currently logs a generic skip
- `plugin/skills/backlog/refine-closing-summary.md` — the `AUTO … skipped …` template and tally bucket this enhancement reuses rather than replaces
- `plugin/skills/_shared/trust-table.md` — candidate destination for the second (exploratory) deliverable, if repeated divergence is judged worth feeding into trust signals

## Gotchas

- The second deliverable ("consider whether repeated divergence should feed the trust-signal machinery") is deliberately exploratory, not a hard requirement — the Acceptance Criteria above cover only the first (logging) deliverable; a build should treat the trust-signal question as a judgment call to make and document, not a mandatory code change.
- This does not change what gets granted or merged — only what gets logged when two independent judgments disagree. The underlying race (last-writer-wins on GitHub's label API, no conditional-write primitive) is `refine-mode.md`'s own already-accepted residual risk, not something this record re-opens.
