# 4581: Review Console never settles an aggregate reproduction STAGED line naming several findings with shortened locations

Surface: infra

**Related:** #4632, #4038, #4620, #3822, #3835, #3977, #4359, #4472, #4621, #4636, #4663, #4672, #4679, #4826

## Current State

`plugin/skills/review/step3-lens-dispatch.md` (the "Findings present in only one agent's output" bullet, line 106 on `origin/main`) defines one STAGED line per unreproduced finding: `STAGED {HH:MM:SS} — Reproduction: lens "{lens}" finding {path}:{line} not reproduced. Staged to Review Console as low-confidence. …`. The Review Console (`plugin/bin/lib/console/resolve.js` `findingKey`/`lineKeys`) keys a STAGED line on its first `lens` and first `path.ext:line` (plus the second location of the documented two-finding coincidence line), and a later tiebreak verdict supersedes it only on that key.

Reviewers have improvised an aggregate line instead, in at least two runs:

- Run `2026-10-27T184830-spec-4481`, decisions.md line 52: `STAGED 04:38:49 — Step 3: Reproduction: lens "3a" 10 findings not reproduced (A: journey:89 medium, test:1921 low, git-command.js:2253 low, :2433 info, …; B: ledger:5 medium, policy-schema-coverage.md:30 medium, …)`
- A spec #1921 run: `STAGED 00:04:18 — spec #1921 — Reproduction: lens "3f Test quality" 4 findings not reproduced …`

Its findings use shortened locations, so its key (`3a|git-command.js:2253`) matches no tiebreak verdict (those carry full repo-relative paths); the line resolves keep-staged and its console residue needs a human `console-residue.js --ack`. Across local run logs, 5 decisions.md files carry an aggregate `N findings` reproduction line against 169 carrying the per-finding form.

Both observed lines carry `log-decision.js`'s own `--step`/`--spec` prefixes, so they went through the writer — `_shared/auto-decision-log.md` names `bin/log-decision.js` the sole append path for `decisions.md`. The writer validates flags and the step-prefix repeat (`repeatsStep`, exit 2) but never the text's shape, so nothing stops a reviewer from collapsing findings into one line.

**Decision (settled in brainstorming, 2026-11-01): fix the producer (option A), not the reader.** Teaching `resolve.js` to parse an aggregate line (option B) would mean fuzzy-matching shortened locations (`journey:89`, `:2433`) against full paths — guesswork that can settle the wrong finding. The residue already on disk (run 4481, archived) is cleared once by hand with `console-residue.js --ack`, not by reader code.

## Plan Review Clarifications

- Decided by the user at plan review: "names more than one finding" (Deliverable 1, AC3) is detected by grammar, not location count — a plural `findings` subject (a count such as `10 findings`, a lens noun phrase such as `lens "3f" findings a.js:1 and b.js:2`, or `findings` directly after the `reproduction:` marker) or two `lens … finding` clauses. A singular-`finding` line that cites further locations is accepted. Replaces: "a count of findings (`{N} findings`, N a number), or two or more `path.ext:line` locations" (Deliverable 1) and AC3's "naming two full `path.ext:line` locations without a count".
- Decided by the user at plan review: the reproduction-line marker (Deliverable 1, AC5) is a case-insensitive `reproduction:` with the lens quotes optional — matching the Console reader's `findingKey` and `_shared/multi-agent-coordination.md`'s `/review reproduction: lens …` form — so lens-less aggregates (`Reproduction: 26 unconfirmed single-agent findings …`) are refused too. Replaces AC5's "the guard keys on the `Reproduction: lens "` marker only"; a non-reproduction line is still never matched.

## Build Alignment (Beneficial deviations, /build Common Step 4.5)

- The reader changed too, not only its pattern's home: `resolve.js` `lineKeys` keys a quoted multi-word lens on its first token and matches the coincidence line case-insensitively, the same key `findingKey` yields, so every coincidence line the writer exempts is one the Console can settle.
