# 3351: flow multi-spec: Validation step 3 has no behavior for a failed preflight-records.js call

Surface: infra

## Current State

`plugin/skills/flow/multi-spec.md` Validation step 3 runs one `bin/preflight-records.js {targets} --merge-gate --integration-branch "$INTEGRATION_BRANCH"` call and documents only its exit codes (0 success, 1 any fetch failed, 2 malformed or a `--waves` cycle) — not what the run does on 1 or 2. On a non-zero exit `records`, `overlapGroups`, `workLinks` and `mergeGate` are all withheld, and step 4 (dependency-aware ordering) and step 5 (conflict detection) have neither a fallback nor a stop.

Two sibling files patch around the gap without closing it: `multispec-merge-gate.md` step 1 says a non-zero exit voids the whole collection and then proceeds unsplit with a `SKIP` (deferring "what Steps 4-5 do" to step 3, which says nothing); `multispec-parallel-waves.md`'s "No plan" re-runs the call without `--waves`, which only helps when `--waves` itself caused the failure.

What actually reaches a non-zero exit at step 3 (verified against `origin/main`, 2026-10-17):

- **A `gh`-absent sandbox — every time.** `preflight-records.js` fetches each record by shelling out to `gh issue view` and has no other input path, so in a cloud/Routine sandbox it exits 1 on every multi-spec run. `bin/materialize.js` already solved the same problem with `--record-json <path>` (#1459): the calling skill fetches over MCP `issue_read` and hands the JSON in. `preflight-records.js` never got the equivalent.
- **A transient `gh`/network failure, or the `work-links: native` GraphQL call failing** — exit 1. A genuinely missing record cannot reach step 3: step 1 (Parse, `materialize.md`'s Resolution) already hard-stops on any unresolvable record.
- **A malformed invocation, an unresolvable owner/repo under `native`, or a `--waves` dependency cycle** — exit 2: an invocation bug, or a cycle step 4 hard-fails anyway.

Native `blocked-by` links have no MCP equivalent at all — the GitHub MCP server exposes no GraphQL passthrough (`dispatch/mcp-transport.md`, #2523), and `/dispatch` already degrades to body-text dependency mentions on a `gh`-absent firing.

Decided with the maintainer, 2026-10-17: a real failure hard-stops; a `gh`-absent run gets real record data through a new input path instead of degrading; the one unrecoverable slice — native links without `gh` — degrades to body-text `blocked-by` with a logged `SKIP`, matching `/dispatch`.

## Deliverables

1. `bin/preflight-records.js` accepts `--records-json <path>`: a JSON array of already-fetched records, each in `gh issue view {n} --json number,title,body,labels,url`'s shape (`labels` as array-of-`{name}` or bare strings — the shape `parseRecordFacets` reads). When given, the CLI makes no `gh` call of any kind; every downstream computation (`buildRecords`, `buildOverlapGroups`, `--merge-gate`, `--waves`) runs on the file's records unchanged.
2. Under `--records-json` with `work-links` resolving `native`, `blockedBy` comes from `parseDependencies(body)`, the envelope reports `workLinks: "body-text"` plus `nativeLinksUnchecked: true`, and one stderr line names the degrade. The field appears only on that path.
3. A new sub-file, `plugin/skills/flow/multispec-preflight-failure.md`, holds the ruling, and `multi-spec.md` Validation step 3 gains one pointer sentence to it (`multi-spec.md` is 19,957 bytes against a 20,480-byte read budget, so the ruling cannot live inline). The ruling:
   - exit 0 → proceed;
   - exit 1 on the `gh` transport → re-run the identical call once; a second exit 1 → **STOP** before claiming, quoting stderr (which names every failing record on a fetch failure; a native GraphQL failure names none);
   - exit 2 → **STOP** before claiming, no retry, quoting stderr;
   - `gh` unavailable → fetch each target via MCP `issue_read` (reusing step 1's already-fetched records where present), write them to a session-scoped temp file, and call with `--records-json`;
   - `nativeLinksUnchecked: true` → proceed, and once the parent run directory exists write one `SKIP` naming the unchecked native links and that ordering, the merge-state gate and (under `parallel`) the wave plan ran on body-text dependencies.
4. Steps 4 and 5 state they run only on an exit-0 envelope — a stopped run never reaches them.
5. `multispec-merge-gate.md` step 1's non-zero-exit branch (currently "proceed unsplit … `SKIP`") is replaced by a pointer to step 3's ruling, and it notes that under `nativeLinksUnchecked` the gate evaluates on body-text `blocked-by` only, covered by step 3's `SKIP`.
6. `multispec-parallel-waves.md`'s "No plan" re-run without `--waves` counts as step 3's one retry on exit 1; exit 2 (malformed or a `--waves` cycle) is step 3's STOP with no re-run, and if the exit-1 re-run also exits non-zero, step 3's STOP applies — never a third call.
7. `docs/plugin-structure.md`'s `preflight-records.js` CLI line lists `--records-json` and the `nativeLinksUnchecked` envelope field.

## Technical Approach

Mirror `materialize.js`'s #1459 seam. In `preflight-records.js`, parse `--records-json` with the same trailing-value guard the other value flags use; read the file through a `deps.readFile` seam (as `materialize.js` does) so tests never touch the filesystem. Validate the array against the positional numbers (exactly once each) before building anything, and turn it into the same `issues` Map `fetchIssues` returns, so `buildRecords`/`buildOverlapGroups`/`planMergeGateSplit`/`planParallelWaves` are untouched. Skip `deps.remoteUrl()`/repo resolution entirely on this path — nothing downstream needs a repo without a `gh` call. When `work-links` resolves `native`, pass `dependencies: null` to `buildRecords` (its body-text branch) and set the envelope flag.

The prose changes are the ruling in `multispec-preflight-failure.md`, cited from step 3, plus pointers from steps 4/5, the merge gate and the waves fallback back to it — state the ruling once, in that sub-file, never restated in the siblings. The `SKIP` entry follows `multispec-merge-gate.md`'s existing `log-decision.js` form (`--section "/flow" --status SKIP --step "Step 1 native dependency links (skipped)" … --reversibility n/a`), written once the parent run directory exists.

## Gotchas

- Native-only `blocked-by` links are invisible on the `gh`-absent path — a deliberate, maintainer-approved degrade (2026-10-17), the same limit `dispatch/mcp-transport.md` documents (#2523). In a `native` repo, bodies rarely carry dependency mentions, so cross-record ordering is effectively unchecked in cloud runs; the `SKIP` entry must say so plainly, never read as "no dependencies."
- No silent fallback in either direction: `--records-json` must never shell out to `gh` when the file is bad, and the `gh` path must never quietly switch to body text when the native call fails — that is exit 1 and the retry/STOP ruling.
- The MCP `issue_read` response must be reshaped to `gh issue view`'s field names before it is written (`materialize.md`'s #1459 paragraph is the precedent); `labels` shape mismatches show up as empty facets, not errors.
- `SKIP` logging must wait for the parent run directory (after the Manifesto write) — step 3 runs before it exists, the same timing `multispec-merge-gate.md` already handles.
- A STOP inside a `/dispatch`-launched bundle surfaces as that bundle's failed run, which is intended — the retry absorbs a one-off `gh` hiccup, so a STOP means a persistent problem.
- `multi-spec.md` has a hard 20,480-byte read budget pinned by three tests; every addition there must be measured (`wc -c`) — #3360 already had to trim it once. Open PR #3348 also edits `multi-spec.md`, so expect a rebase conflict if it lands first.
- Out of scope: `flow/claim-targets.md`'s file-overlap warning also calls `preflight-records.js` with no non-zero-exit handling (a never-gate warning, so its answer differs); reported separately rather than folded in here.
