# 5228: Judgment workers: merge-check verdict and acceptance brief, read-only

Surface: backend

## Overview

This unit supplies the two judgments the driver's merge step (#5226) needs and cannot make itself: the merge-check content judgment (`plugin/skills/assess-agent-autonomy/merge-check.md`) and the authoring half of acceptance labeling (`plugin/skills/wrap-up/verification-brief.md`). Each becomes a read-only worker, launched the way Phase 1's launcher launches every role, under the worker rules that bind all of them: no `gh`, no label or comment write, no merge. A worker reads and returns a verdict or a text; the driver logs, confirms, posts and applies. `plugin/bin/lib/driver/judgments.js` wires both as the supplier that `merge.js` consumes, and is what turns driver merging on. Design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, section "Phase 2 — Merge".

The merge-check judge returns a verdict in the vocabulary of `assess-agent-autonomy merge-check` (`auto-merge` or `needs-human`); the driver logs it and confirms it by the same deterministic step dispatch uses, and anything but a confirmed `auto-merge` ends the run `pending-review`. The acceptance author returns the texts the procedure has a model write; the deterministic gates in that file (the parent gate and the oversight-floor gate) run as driver code, and so do gathering the packet's facts, rendering, posting and every label write.

Whether a worker's prompt is the existing skill file's text or a shorter one is the builder's choice, with the constraint that verdicts and labels match today's on the same inputs. That is shown on a fixture set of past records whose merge-check verdict is on record.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- Any change to `merge-check.md`, `verification-brief.md`, `plugin/skills/dispatch/settle-and-merge.md` or the prose express lane, and any test that reads them.
- Any merge, ready or label call by a worker, and any change to the merge steps themselves (#5226). The two units meet only at the supplier's return shape.
- A review worker or any review finding input on the driver lane. The lane runs no review, so the merge-check judge is told `review findings: none` (`_shared/express-lane.md` step 9). A reviewer is Phase 4.
- The visual-review safety net of `verification-brief.md` Step 2.5. The driver lane has no frontend surface, so an acceptance plan of kind `app-route` or `rendered-page` is not completed here, and the run ends `pending-review`.
- Re-running the worker after a failed render. The procedure's one re-render after a model fix is not ported: a render that exits 1 means acceptance is not completed.
- Using `merge-check`'s verdict anywhere but the merge step, and granting any label other than the acceptance label the gates call for.
- Pinning `docs/driver.md`'s text with any test.

## Release Note

Added read-only judgment workers to the pipeline driver, so a driven record with merge authority gets its merge-check verdict and its acceptance brief without any model holding merge rights.

## Technical Approach

- **Roles.** Two entries in `roles.js`: `merge-check` (inputs: the wrapped record, the diff, the blast-radius summary, the check state, and a `reviewFindings` input that is `none` in production, where the lane ran no review, and is filled by the evaluation harness from a fixture) returning `{ verdict, rationale }`; `acceptance` returning the authored texts. Both launch with the worker rules every role has; neither is given a tool that writes. The worker's working directory is the record's worktree, so Read, Grep and Glob can open the changed files for the refutation test.
- **Untrusted input.** The record body and the diff are untrusted; each is wrapped as `_shared/untrusted-record-content.md` prescribes and the worker's prompt says to judge it only for its purpose. The verdict is read only from the schema field of the worker's structured result, never from text inside the wrapped content.
- **Merge-check path.** (1) `blast-radius.js --integration-branch {ref}` as code: non-zero exit, or non-empty `sensitiveFilesTouched`, returns `needs-human` with no launch. (2) Otherwise launch the judge. (3) Validate the field strictly. (4) Log and confirm per acceptance criterion 3. The prose logs a `needs-human` too, so the log shows every verdict the gate saw. Only these two floors are code. The size guideline, the agent-instruction-file refutation test and the content weighing stay with the judge, as in `merge-check.md`, which treats `auto-merge-max-lines` and `auto-merge-max-files` as one input and not a cutoff; the model is therefore the only guard against a large behavior-changing diff on this lane, the same trust today's merge-check places in the judging model, and Phase 1's diff bounds (enforced by `express-lane.js check` before the push) limit the exposure.
- **Prompt source.** Either the existing skill file's judging text or a shorter one, the builder's choice. Reading `merge-check.md`'s Step 2 and Calibration sections from the plugin at run time and passing them as the instructions keeps one source of truth, at the cost of an extraction that depends on headings; if it cannot find them the supplier fails closed. A shorter prompt copies the rules and drifts silently when the skill file changes; whichever is chosen, the fixture evaluation is the check, and a later change to `merge-check.md`, `verification-brief.md`, the prompt or the judging model means re-running it; `docs/driver.md` says so and names the harness command.
- **Acceptance routes.** The routing is `verification-brief.md`'s, run as code; the model writes only the texts in the third column.

| Gate result | Driver code | Authored by the worker | Labels applied | `completed` is `true` when |
|---|---|---|---|---|
| `parent-gate.js` `state: incomplete`, `gated` or `resolved` | post the sub-issue's Try it block alone as the `try-it` PR run comment (`verification-brief.md`'s "Posting it alone") | the Try it block | none | that post succeeded |
| `due`, `exceeds: false` | the same Try it post; no parent write now (Step 4.0b closes the parent after the merge) | the Try it block | none | that post succeeded |
| `due`, `exceeds: true` | read the parent's comments for an already-posted brief (a trusted `## Verification Brief` with a `### Confirmed` section) and skip the comment when one exists; otherwise post the parent brief comment; bootstrap the acceptance labels and add `demo:pending` to the parent; then the Try it post | the parent brief text and the Try it block | `demo:pending` on the parent | every call succeeded |
| `no-parent`, oversight floor `exceeds: false` | gather, render, post with no `--label`; record the exemption with `set-verify-expectations.js --oversight-exempt {n}` | the Try it block, the observation plan, the narrative claims | none | gather, render, post and the exemption write all succeeded |
| `no-parent`, `exceeds: true` | bootstrap the acceptance labels, gather, render, post with `--label demo:pending` | the same three texts | `demo:pending` on the record | gather, render and post (label included) all succeeded |

The driver always takes the sub-issue-side entry of the Parent-Gate Procedure (it holds a record number): `parent-gate.js --sub-issue {n} --closing {n}`; the parent-side entry is `/claude-tweaks:tidy`'s. Exit 0 routes the verdict. Any non-zero exit is a failing call under that procedure's "Fail open on every gh call" paragraph, so the route falls back to the no-parent rows: a record that has a parent then gets a record-level packet instead of the parent's gate, which is that paragraph's stated behavior and not a driver choice. `post`'s exits: 0 is success, every other exit is not completed.

- **Gather and render** (`acceptance-packet.js gather --record {n} --out {FACTS} --run {run-dir} --spec {spec} --base origin/{ref} --head {head} --links {LINKS} --surface backend`, then `render` with the worker's narrative) take no `--ac-results` (the lane ran no review) and no `--report` unless the run's checkout is the cwd; the fixtures for these calls follow `verification-brief.md` Step 4's argument grammar rules for every pasted value.
- **Fixtures.** Every record with a verdict on record in the maintainer's archived run directories is extracted once into a committed JSON file at `tests/bin-lib/driver/fixtures/merge-check-verdicts.json`, so the evaluation is repeatable without the gitignored directories. Each entry holds: the record number; the recorded verdict (the latest one, read through `merge-verdict.js`'s `confirmPassingVerdicts`); the merge commit sha; the record body as it reads at extraction time (a later edit of the record since is a named divergence in the fixture file's header); the blast-radius summary computed once at extraction against the merge's first parent, with the policy values in force at extraction (`auto-merge-max-lines`, `auto-merge-max-files`, `merge-sensitive-paths`) recorded beside it; and `reviewFindings`, a list of `{ severity, text }` taken from the archived run's review output, empty when that run held none; plus (architecture alignment at build) the merged closing PR number `closingPr` and its `checks`, read at extraction with production's own `gh pr checks {pr} --json name,bucket` so the judge is replayed with the input production passes, check state as of extraction being a named divergence in the header. The diff is `git diff {mergeSha}^1 {mergeSha}`, read at evaluation time. The evaluation harness is `tools/driver-merge-check-eval.js` (new, maintainer-side, not shipped), run by hand. Public records, their merged diffs and the verdicts are all that goes in; no rationale text, no paths.
- **Supplier shape.** `createJudgments(deps)` returns `async (ctx) => ({ mergeCheck: { verdict }, acceptance: { completed } })`; `completed` is `true` only when the chosen route ran to its end with every call succeeding.

## Gotchas

- The judge must not be told it is auditing a past run. A fixture is judged with the inputs the original judgment had: the record body, the diff, the blast-radius summary and the review findings of that run (a recorded `needs-human` caused by a Medium review finding must not be re-judged with "review findings: none", which would be a different input and could read as a false `auto-merge`). A fixture whose archived run holds no readable review summary is excluded and counted, with the reason, in the closing comment.
- The confirmation proves the line is well formed, not that the judgment was sound: `confirmFromFile` reads back what the driver itself wrote. The independent control is that the verdict text in `decisions.md` is built by the driver from the validated enum, never from the worker's output, and `merge.js` re-reads it before any ready call (#5226).
- A passing line is anchored at its end (`PASS_ACTION_RE` in `merge-verdict.js`): a rationale, a trailing note or any extra text on the line makes it `unparsed`. Keep the rationale out of `decisions.md`; it goes to the event detail, bounded.
- `acceptance.completed` must never be `true` on a partial route. A packet posted but whose label add failed is not completed, because `_shared/pr-first-merge.md` Step 1 owes the labeling before the merge closes the record.
- The acceptance label is a function of the two gates, so the worker's output cannot change it. The design's phrase that the worker returns "the acceptance labels it calls for" is met by the gates: they call for the labels, and driver code applies them.
- Every record the driver lane can drive that came from a `/claude-tweaks:specify` decomposition has a parent, so the common route is the Parent-Gate Procedure, not the packet. Test the parent routes first.
- Only `risk` is aggregated at the parent gate; `size` is never evaluated there (`verification-brief-parent-gate.md`, "Oversight-floor check").
- The procedure's `Posting it alone` step posts a parent-linked sub-issue's Try it block as a `try-it` PR run comment (`_shared/pr-run-comments.md`); that is a forge write by driver code, from the worker's text after neutralization.
- The driver lane touches no frontend surface (eligibility refuses it), so a plan of kind `app-route` or `rendered-page` is a worker mistake, not a case to run a browser for.
