# 3358: Filter run-comment marker reads by the posting identity, not the marker alone

Surface: backend

**Related:** #3333, #2821

## Current State

Every reader that picks a GitHub comment out by a plugin marker or heading trusts the marker alone — no author check. Anyone who can comment on a PR or issue (on a public repo, anyone with a GitHub account) can therefore post a comment the plugin then treats as its own:

- `_shared/pr-run-comments.md`'s Find step selects with `select(.body | startswith("<!-- run-comment: {kind} -->"))`. Its MCP-transport branch finds the prior comment to name in `Supersedes {url}` the same way. On the `gh` transport a planted marker comment is then **updated in place** (`updateIssueComment` — an owner can edit anyone's comment), so the run's real verdict/brief/try-it ends up under the outsider's name.
- `/claude-tweaks:demo` (`demo/entry-paths.md`) renders the `try-it`/`brief` body it finds verbatim as "the same walkthrough the Pipeline Summary and the PR showed" — and a Try it block's Steps may carry runnable commands (`_shared/try-it.md`). The issue-side reads (last comment containing `## Verification Brief`, the `Verification Brief posted to PR #…` pointer that names which PR to read) have the same gap; #2821 carried it to PR comments.
- `bin/lib/wrap-up/engine-verify.js`'s acceptance-labeling check (`includes('## Verification Brief')`, `includes('Verification Brief posted to PR #')`, `includes('<!-- run-comment: brief -->')`) can be satisfied by a planted comment.
- `wrap-up/verification-brief-parent-gate.md`'s already-posted check skips the real brief post when **any** parent comment carries `## Verification Brief` + `### Confirmed`.
- `bin/lib/reconcile/console-execute.js` find-or-updates the `<!-- console-item: executed -->` reply by `startsWith` (the console comments themselves are found by the ids recorded in `console.json`, so they are not exposed).
- `needs-decision` readers: `bin/lib/release-note-repair/detect.js`'s `hasPendingTidyDecision` (a planted unresolved `<!-- needs-decision: tidy -->` comment drops a record from `/tidy`'s worklist), and `/specify`'s own resolution lookup (`specify/shaping-mode-stamping.md`), which prepends `**Resolved:**` to — i.e. edits — every unresolved marker comment it finds.

**Who actually posts these** (every comment on this repo since 2026-09-01, `gh api repos/{owner}/{repo}/issues/comments`): 4155 by `thomasholknielsen` via `gh` (`MEMBER`), 375 by `thomasholknielsen` `performed_via_github_app: claude` — the MCP transport (`MEMBER`), 1090 `github-actions[bot]` (`CONTRIBUTOR`), 3 `dispatch-hub-5098[bot]` (`CONTRIBUTOR`), 1 outside user (`NONE`). All 40 run-comments on the last 40 merged PRs are `thomasholknielsen`/`MEMBER`. The Claude GitHub app acts on behalf of the user, so both transports post as the same login. The original Open Question — gh's identity versus the MCP app's identity — does not come up in practice.

The trusted-association rule already exists once: `bin/materialize.js:103`'s `TRUSTED_AUTHOR_ASSOCIATIONS = new Set(['OWNER', 'MEMBER', 'COLLABORATOR'])`, which gates `Premise-check:` execution (`flow/materialize.md`'s Author-association gate). `gh pr view --json comments` / `gh issue view --json comments` return `authorAssociation` per comment (checked on PR #3359: keys `author, authorAssociation, body, …, viewerDidAuthor`); the REST/MCP shape is `author_association`.

## Deliverables

1. **One shared trust predicate.** Move `TRUSTED_AUTHOR_ASSOCIATIONS` out of `bin/materialize.js` into a new `plugin/bin/lib/issues/comment-trust.js`, exporting the set plus `isTrustedComment(comment)`. The predicate reads `authorAssociation` (gh `--json comments` shape) or `author_association` (REST/MCP shape) and returns false when neither is present (fail closed). `materialize.js` imports the set from there — behavior unchanged.

2. **Trust = GitHub's author association, not the viewer.** A marker or heading comment counts only when its author association is `OWNER`, `MEMBER`, or `COLLABORATOR`. No viewer lookup (`viewerDidAuthor`) and no per-transport identity. State this rule once, in `_shared/pr-run-comments.md` (a short "Trusted authors" section that every other reader cites), with the reason: anyone with write access can already push to the PR branch, so a narrower rule adds no protection, while a viewer match would reject legitimate comments read by a different maintainer or account.

3. **Apply it at every reader**:
   - `_shared/pr-run-comments.md` Find step: add the association test to the jq select (`--json comments` already returns the field). Apply the same test in the MCP branch's `Supersedes` lookup on `author_association`.
   - `bin/lib/wrap-up/engine-verify.js`: the issue-side full-brief, pointer, and PR `brief` checks.
   - `demo/entry-paths.md`: the issue-side `## Verification Brief` and pointer scans, and the PR run-comment lookup's step 2.
   - `wrap-up/verification-brief-parent-gate.md`: the already-posted brief check.
   - `bin/lib/reconcile/console-execute.js`: the `console-item: executed` reply find.
   - `bin/lib/release-note-repair/detect.js` `hasPendingTidyDecision`, and `specify/shaping-mode-stamping.md`'s unresolved-`needs-decision` lookup.
   - Any further reader turned up by a repo-wide grep of `plugin/` for comment selection by `<!-- ` markers or brief headings. Each one either gets the filter or is recorded in the PR body as exempt, with the reason.

4. **Skipped ≠ silent.** When a reader passes over a marker comment because its author is untrusted, it says so in one line naming the comment URL (or id), author login, and association. Skill readers put this line in their output. `engine-verify.js` puts it in the check's `detail`. `console-execute.js` and `detect.js` put it in their returned result. An untrusted planted comment then makes the reader take the same path as "no such comment" (create a fresh comment, fall back, or fail the check), never the trusted path.

## Technical Approach

The predicate goes in `bin/lib/issues/` next to `record.js`, which already references this trust tier in its comment at line 821. Code readers call `isTrustedComment` directly. Skill prose readers use the jq form, `select(.authorAssociation == "OWNER" or .authorAssociation == "MEMBER" or .authorAssociation == "COLLABORATOR")`, chained before the marker `startswith`, or `author_association` on MCP payloads. That way the three values live in one prose location (`_shared/pr-run-comments.md`'s Trusted authors section) and one code location (`comment-trust.js`). Add a prose conformance test that pins the two lists equal, per the `prose-code-twin-pin` skill.

For the skip notice, the jq read needs to return untrusted matches too, so the reader can name them. Either use two selects, or one pass emitting `{id, url, author, trusted}` that the reader partitions. Pick whichever keeps the Find step readable.

## Gotchas

- **#3333 touches the same readers.** It is `ready` with `auto:build`, and it makes `engine-verify.js` and demo's PR lookup read `brief:{n}` first, then fall back to plain `brief`. Whichever lands second rebases onto the other. The trust filter must cover both the qualified and the plain marker reads.
- **Check the MCP payload field before relying on it.** `issue_read`/`get_comments` is expected to return REST-shaped comments with `author_association`. Confirm it at build time. If the field is missing, MCP-path readers fail closed (every marker comment untrusted, with the skip line), which is visible but turns MCP-transport `Supersedes` naming off. In that case, say so in the PR rather than shipping a silent degrade.
- **Bots are excluded on purpose.** `github-actions[bot]` and other app bots show up as `CONTRIBUTOR`. If a future transport ever posts run comments as a bot identity, readers would ignore them, and the trust rule would need revisiting then.
- **Association is computed at read time.** Comments by someone who later leaves the org become untrusted. That is the correct direction for this check.
- **The run-comment and brief formats are byte-pinned by conformance tests.** Changing the Find-step jq will turn existing pins red. Run the full suite, not just targeted files.
- `materialize.js`'s Premise-check gate reads the *issue's* author association, not a comment's. Only the set moves into the shared module; that lookup stays as it is.

## Current State

`_shared/pr-run-comments.md`'s Find step selects PR comments by first-line marker alone (`select(.body | startswith("<!-- run-comment: {kind} -->"))`), with no author check. Since #2821, `/claude-tweaks:demo`'s PR run-comment lookup (`demo/entry-paths.md`) reuses that read and renders the `try-it`/`brief` body verbatim to the human as "the same walkthrough the Pipeline Summary and the PR showed". The Try it Steps field may carry runnable commands (`_shared/try-it.md`). Anyone who can comment on the PR can therefore plant a walkthrough that demo presents as the run's own.

The issue-side lookups (the `## Verification Brief` heading scan and the `Verification Brief posted to PR #…` pointer that names which PR to read) worked this way before #2821; #2821 carried the same lookup to PR comments. Found by #2821's review, lens 3b, both reproduction agents; refs #2821.

## Deliverables

1. Decide which identity counts as the run's own poster under each transport: the authenticated user under the gh transport (`viewerDidAuthor` / `author.login`), and the app or user the MCP server posts as under the MCP transport.

2. Apply that filter in every marker reader: the pr-run-comments.md Find step, `bin/lib/wrap-up/engine-verify.js`'s acceptance check, and demo's issue-side brief/pointer lookups and PR lookup.

3. When a reader skips a marker comment from another author, it says so in one line rather than silently ignoring it.

## Open Question
