# 4897: Background post-merge summary counts a failed-close run as ran

Surface: backend

**Related:** #4798, #4318, #3646, #4797, #4932, #4933, #3977, #4779

## Current State

`plugin/bin/hooks.js`'s `reconcile-background` summary (`plugin/bin/hooks.js:1882` and `:1886` on `2defc6d05`) counts a background post-merge pass's `ran` entries as `postMergeRan` whenever `step40Failed` is unset, and as `postMergeFailed` only when it is set or the check threw (`reason === 'error'`).

A `ran` entry whose Step 4.0 action word is not clean (`reopen-failed`, `close-failed`, `close-pending`) has no `step40Failed`, so the next SessionStart reports it as `post-merge steps ran for N merged run(s)`: a clean outcome. Those three words mean a record is left in the wrong state.

`classifyEntry` (`plugin/bin/lib/reconcile/post-merge.js:440`, added by #4692) already classifies those entries `verdict: 'failed'` for the single-run path, so the two paths judge one entry differently. A third site holds the same narrow rule: `plugin/bin/lib/reconcile/format-summary.js:54` and `:57`, the reconcile CLI's summary lines, which the record as filed did not name.

Three facts constrain the recovery wording:

- `plugin/bin/lib/hooks/session-start.js:350` says `tidy's parent-gate backstop recovers them` for every failed run. That covers parents only. The backstop selects on `parent-issue` once every sub-issue has closed, so it never closes or reopens the failed record itself, and a parent held by a `close-failed` record does not come due until that record is settled.
- A `ran` entry's marker is already written, so no later pass retries it (`classifyEntry` returns `next: 'none'`).
- `plugin/bin/closing-links.js` logs each failed close or reopen to `decisions.md` as a `Closing links (degraded)` SKIP line with its hand action. A summary line pointing only there would not tell the reader which records, so the SessionStart line names them and points there. (Corrected at build: this bullet first said no such line exists.)
- Build deviation, beneficial: the reconcile CLI's failed row also names the records (`post-merge steps failed: 2 merged runs (records #101, #102)`), since a failed run reached through the CLI writes its marker and SessionStart then never names its records.

Loop entries do not carry the record lists today: `processRun` adds `records` only under `includeRecords`, which only `postMergeOne` sets (`plugin/bin/lib/reconcile/post-merge.js:497`).

**Decision on the filed question (made while shaping; the user opted out of questions).** A non-clean word counts as failed, because that is the single-run path's verdict and the run did leave work undone. A `parentFailures`-only entry counts as failed too, through the same `classifyEntry` call. The line names the records that need a hand fix and keeps the backstop clause for parents.

**Boundary with #4798 (open, `ready`, `auto:build`).** #4798 owns emitting `parentFailures` on loop entries and naming the unclosed parent in SessionStart. This record owns the shared classification and the Step 4.0 half. The two are order-independent: once this lands, an entry carrying `parentFailures` already counts as failed, whichever record merges first.

## Release Note

SessionStart no longer reports a background post-merge run as clean when its closes failed, and it names the records that need a hand fix.

## Technical Approach

Call `classifyEntry` on `ran` entries only. On a `skipped` entry it returns `failed` for every reason, including `transient-failure`, which must stay out of these counts.

Suggested failed line, with the record clause only when `postMergeFailedRecords` is a non-empty array:

`post-merge steps failed for N merged run(s) (records #101, #102 need a hand reopen or close per _shared/pr-first-merge-post-merge.md Step 4.0, and no later pass retries them; tidy's parent-gate backstop recovers the parents)`

Render closed parents on their own line when `postMergeRan` is 0, in the style of the existing unmarked-closes line.
