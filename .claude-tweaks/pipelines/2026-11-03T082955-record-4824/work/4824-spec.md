# 4824: Pass --repo on the parent gate prose's gh issue comment and close writes

Origin: follow-up from #4603 (PR #4678) wrap-up

Defer-reason: genuinely-larger

## Current State

#4603 made the parent gate's reads and the reconciler's two writes (`plugin/bin/lib/issues/below-floor-parent-close.js`) target one repository, adding `--repo {owner}/{repo}` to each (SDD rulings 18 and 19), so a multi-remote checkout never splits one gate across remotes. The gate's prose still carries bare writes with no `--repo`: `plugin/skills/wrap-up/verification-brief-parent-gate.md` runs `gh issue comment $PARENT_NUM --body-file ...` (around lines 439 and 594) and `gh issue close $PARENT_NUM --reason completed` / `--reason "not planned"` (around lines 447 and 455). On a checkout whose `gh` base repo differs from `origin`, those writes land in a different repository than the gate's reads. The same bare-write shape exists across the rest of the prose class (`_shared/health-filing-mechanics.md`, `_shared/issue-claims.md`'s claim comment, and similar fences), so this needs a plugin-wide pass, not a one-file edit. It was deferred in #4603 because it needs a verdict field or a resolution step that supplies `{owner}/{repo}` to the prose, plus a sweep of the class.

Ledger row 20 of #4603's `docs/plans/2026-10-31-parent-gate-cli-ledger.md`.

## Plan Review Clarifications

Answer to the plan-review question, decided by the maintainer on 2026-11-02.

**Runnable inline-span `gh issue` writes are inventoried too.** Deliverable 2 and the third acceptance criterion cover fenced lines and runnable inline spans in instruction text. Each runnable write is classified as carrying `--repo`, intentionally cwd-scoped, or needing a fix. A span that only describes a command, such as a transport mapping table or a command a human runs, is recorded as descriptive. The inventory classifies; it does not fix the inline writes.

**The first acceptance criterion's grep also matches a mapping sentence.** `verification-brief-parent-gate.md` line 69 names `gh issue comment` and `gh issue close` in a transport mapping, so the grep matches five unfixed lines, not four. That line is not a command: the criterion applies to the runnable lines, and line 69 is either reworded or excluded from the check.

**Writes classified as needing a fix go to one follow-up record.** The "needing a fix" class covers fences as well as inline spans, and supersedes Deliverable 2's two-way "carries `--repo` or intentionally cwd-scoped". A fence or span in that class satisfies the third acceptance criterion, and this record files one named follow-up listing them all. This record adds `--repo` only to the Parent-Gate Procedure, and adds no slug-resolution step to any other procedure.

**A `--repo` value this record adds must not be empty.** `--repo "$VAR"` with an unset variable passes an empty flag, and `gh` then exits 0 and uses its default repository, which is the failure this record fixes. Every fence this record gives `--repo` stops before the write when the value is empty, and the conformance test pins that.

## Build Notes (architecture alignment)

Deviations found by `/build` Common Step 4.5, each classified Beneficial and kept as built:

- **The empty-value stop is a fail-closed placeholder plus a pinned stop rule, not a shell guard.** Each gh line passes `--repo "{parent-repo}"`, which the agent fills from the verdict's `repo` the way it fills `$PARENT_NUM`. A shell-variable guard (`--repo "${PARENT_REPO:?…}"`) can never bind here: every Bash call starts a fresh shell, a prefix assignment expands too late, and a separate assignment makes the call compound, which the worktree guard refuses. The `repo` bullet therefore carries one stop rule, scoped to the `gh` path, and `tests/parent-gate-repo-flag-conformance.test.js` pins it. An unfilled placeholder or a pasted `null` fails closed in `gh` itself (`expected the "[HOST/]OWNER/REPO" format`). This meets "stops before the write when the value is empty" with a mechanism that can actually run.
- **Apply's partial-state note now names the gh-default label bootstrap.** That bootstrap stays on `gh`'s default repository, so a missing `demo:pending` label is reported as partial state, not as an impossible transient.
- **Follow-up #5048 carries three sites beyond the 19 `needs-fix` rows.** These are `dispatch/queue-pull-script.md:608`'s staged close, `claim-targets.js`'s bare writes, and the label-bootstrap residual. All three show the same read/write split that the clarification routes to one follow-up.
