# 3134: simplify criteria: no rule against replacing a test's literal expected value with the production constant under test

Surface: backend

**Related:** #2994, #3004, #3052, #3053, #3060, #3079, #3099, #3115

## Current State

The simplification criteria live in `plugin/skills/_shared/criteria-simplification.md` and have two consumers:

- `/claude-tweaks:simplify` dispatches `code-simplifier:code-simplifier` with a scope block whose only rules are one `Constraints:` line (`plugin/skills/simplify/SKILL.md`, Step 2 dispatch template): "preserve all behavior; never expand scope beyond the listed files", plus git-mutation bans. The subagent cannot read the fragment, so that line is everything it is told about what not to do.
- `/claude-tweaks:code-health`'s simplification judgment lens has the fragment inlined into its subagent prompts via `plugin/bin/lib/code-health/criteria.js` (`fragment: 'criteria-simplification.md'`).

The fragment's `## Constraints (what NOT to flag)` section lists four rules: preserve all behavior, stay in scope, don't over-simplify at the cost of readability, and don't simplify generated files. None of them covers test expectations. A literal in a test assertion that repeats a production constant looks like duplication, and replacing it with the constant passes the "preserve all behavior" rule on its face. The test still runs and still passes. What is lost is its ability to fail: the assertion now reads its expected value from the code under test, so it holds for any value of that constant.

Observed (6.140.1, `/claude-tweaks:build` Common Step 3): the code-simplifier pass rewrote `abs(row - mean) <= 0.01 * scale` to `abs(row - mean) <= module.OFFSET_SCALE * scale`. That literal was the only place the spec's required offset size was pinned. A review test-quality lens caught the tautology later, and the cost was one review finding, one fix commit and one extra scoped re-verify.

## Deliverables

1. **A test-oracle constraint in `criteria-simplification.md`'s `## Constraints (what NOT to flag)` section.** Never replace a literal expected value in a test assertion with the production constant, or a call to the production function, that the test is checking. A test's expected value is an independent oracle, not duplication. Moving a repeated literal into a test-local constant is allowed. Reading the expected value from the module under test is not.
2. **The same rule in `/claude-tweaks:simplify`'s Step 2 dispatch `Constraints:` line**, stated in one clause so the `code-simplifier` subagent, which only sees the dispatch prompt, receives it.
3. **Pin both** by extending `tests/code-health-misc/criteria-fragments.test.js`'s "simplification fragment carries signature criteria" test with an assertion on the new constraint, and by adding an assertion that `simplify/SKILL.md`'s dispatch `Constraints:` line carries the test-oracle clause.

## Acceptance Criteria

- `criteria-simplification.md`'s Constraints section contains a bullet that forbids replacing a test assertion's literal expected value with the production constant or function under test, names the expected value as an independent oracle, and allows a test-local constant.
- `simplify/SKILL.md`'s Step 2 dispatch template's `Constraints:` line carries the same rule inside the fenced template the subagent receives, not only in surrounding prose.
- `tests/code-health-misc/criteria-fragments.test.js` asserts both additions. Deleting either addition turns its assertion red (shown by reverting before commit).
- `/claude-tweaks:code-health`'s simplification lens receives the new constraint with no code change, because `criteria.js` inlines the fragment. Confirm this by reading the composed fragment text the lens prompt uses.
- `npm test` passes in full.

## Release Note

Stop `/simplify` from rewriting a test's expected value to read the production constant it checks, which made the test unable to fail.

## Technical Approach

This is a prose change in two places plus a test extension, matching how the fragment already works. The fragment is the source of truth for code-health. The simplify dispatch line has to restate the rule because, under the subagent contract, the dispatched agent sees only its prompt and cannot read sibling files. Keep the dispatch clause short, since that line is the subagent's whole constraint set, and keep the fuller wording (oracle rationale, test-local constant carve-out) in the fragment.

### Key Files

- `plugin/skills/_shared/criteria-simplification.md` — new test-oracle bullet in `## Constraints (what NOT to flag)`
- `plugin/skills/simplify/SKILL.md` — Step 2 dispatch template's `Constraints:` line gains the test-oracle clause
- `tests/code-health-misc/criteria-fragments.test.js` — assertions pinning the fragment bullet and the dispatch clause
- `plugin/bin/lib/code-health/criteria.js` — read only, to confirm the fragment is inlined whole, so code-health picks the rule up with no change

## Gotchas

- The dispatch template in `simplify/SKILL.md` sits inside a fenced block that subagent-contract tests may pin (`tests/subagent-contract-clauses.test.js` and siblings). Run the full suite after editing the `Constraints:` line, because a byte-pinned template assertion would fail only there.
- The rule targets test expectations specifically. Production code that duplicates a constant stays fair game for simplification, so word the bullet so it can't be read as a general ban on replacing literals with constants.
- "Preserve all behavior" is not enough on its own, because the rewrite preserves runtime behavior. The new bullet should say that what it protects is the test's ability to fail.

## Original request

simplify criteria: no rule against replacing a test's literal expected value with the production constant under test

**Summary:** The simplification criteria have no rule against rewriting a test's literal expected value to read the production constant it is checking, which turns the assertion into a tautology.

**Kind:** Gap

**Affected component:** `_shared/criteria-simplification.md` (applied by `/claude-tweaks:simplify`'s code-simplifier dispatch)

**Use case:** During `/claude-tweaks:build` Common Step 3, the code-simplifier pass rewrote a test assertion. It had been `abs(row - mean) <= 0.01 * scale`, and the simplifier changed it to `abs(row - mean) <= module.OFFSET_SCALE * scale`, treating the literal `0.01` as a magic number duplicating a production constant. That assertion was the only place the spec's required offset size was pinned. After the rewrite, the tests stay green for any value of `OFFSET_SCALE`. A review test-quality lens caught it later, and the literal was restored.

The simplification criteria treat a literal that repeats a production value as duplication to remove, and don't distinguish production code from test expectations. In a test, stating the expected value independently of the code is the whole point: it is the oracle. Rewriting it to read the constant under test makes the assertion a tautology. The same rewrite will strip the independent oracle from any test whose expectation mirrors a module constant, such as a threshold, scale, limit or timeout.

**Proposed rule (sketch):** Add this to the constraints in `_shared/criteria-simplification.md` and to the constraint line in the dispatch prompt: never replace a literal expected value in a test assertion with the production constant or function it is testing. Literals in test expectations are intentional oracles, not duplication. Moving a repeated test literal into a test-local constant is fine. Importing the production value is not.

**Cost observed:** One review finding, one fix commit and one extra scoped re-verify.

**Definition:** Clear

**Plugin version:** 6.140.1
