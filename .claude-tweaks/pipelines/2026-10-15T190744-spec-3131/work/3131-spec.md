# 3131: Dispatch headless self-report: flow-step-2.8-claim-contest

**Related:** #2789, #3032, #3030, #2702, #2733, #2734, #2775, #2776, #2783, #2821, #2868, #2869, #2877, #2912, #2941, #2970, #3002, #3003, #3012, #3014, #3024, #3029, #3031, #3047, #3048, #3051, #3065, #3079, #3098, #3117, #3132, #3137

## Current State

The self-report records a headless `/claude-tweaks:dispatch` firing on 2026-10-13. It selected #1350, and `/flow` Step 2.8 stopped on a `'live'` claim held by run `2026-10-12T142210-record-1350` (cloud host `vm`, claim blob commit `ad229f771`). The self-report and its stop are the designed headless outcome of a contest (`plugin/skills/dispatch/settle-and-merge.md`, Claim-contest special case). What was not designed is dispatch selecting a held record in the first place.

Dispatch's queue pull excludes held records by label only: `bot:in-progress` is the pre-filter, and Step 2.8's claim read is the authoritative check. #1350's label-event history shows the projection was missing for the whole hold. `bot:in-progress` was unlabeled 2026-10-10T19:12 (a `/tidy` stale-claim sweep) and labeled again only 2026-10-14T12:33 (the next run's claim). No labeled event follows the 2026-10-12T14:29 claim, which wrote the blob and a mirror comment but never added the label, so the 2026-10-13 queue pull saw an unheld record.

Marker comments written from cloud (MCP-transport) runs are stored HTML-escaped. The comment body itself, read back via the REST API, begins `&lt;!-- ... --&gt;` rather than `<!-- ... -->`:

- #1350's 2026-10-12 claim mirror comment (`&lt;!-- agent-claim: {...} --&gt;`). Every other claim comment on #1350 carries the raw marker.
- The `run-comment: verdict` comments on PR #2819, PR #2879 and PR #3127 (`&lt;!-- run-comment: verdict --&gt;`).

An escaped marker renders as visible text and never matches a find-by-marker lookup. Verdict refresh (`_shared/pr-run-comments.md`'s post-or-update), self-report dedup, and the claim mirror's hidden-marker shape (`_shared/issue-claims.md`, "The mirror") all key on the raw `<!--` form.

On the `gh` transport, `bin/claim-targets.js` reports a failed label add in its `labelFailures` output. On the MCP path, `plugin/skills/flow/claim-targets.md` carries the claim as prose, with no read-back of the label add and no failure record. #2789 (merged, `d5a08a9b0`) made the MCP label add non-destructive: `issue_write`'s `labels` is full-replace, and `mergeLabelNames` in `plugin/bin/lib/issues/label-write.js` now computes the merged array. It added no check that the add landed.

The specific #1350 contest is superseded: #1350 closed via PR #3135 on 2026-10-15.

## Deliverables

1. **Read-back of the `bot:in-progress` add on the MCP claim path** (`plugin/skills/flow/claim-targets.md`'s MCP claim branch, and `_shared/issue-claims.md`'s "The bot:in-progress label" section). After a successful claim write, re-read the record's labels. When `bot:in-progress` is absent, retry the add once through `mergeLabelNames`'s read-then-merge write. When it is still absent, log a `STAGED` decision-log entry naming the record and stating that the dispatch label pre-filter will not see this hold. The claim itself is never aborted: the label stays best-effort, per the existing contract.
2. **Unescaped markers on every MCP-transport comment write.** First establish which write stores the escaped body. Candidates are the `add_issue_comment` mapping in `_shared/github-write-transport.md`'s CRUD table, or an agent posting a body it read back sanitized. Then fix that write path, at the shared mapping when the cause lives there, so a comment whose first line is a `<!-- ... -->` marker is stored with the literal marker. Add a read-back after each marker-comment post on the MCP path that logs a `STAGED` entry when the stored body begins `&lt;!--`.
3. **Contest self-report names the projection gap.** `dispatch/settle-and-merge.md`'s Claim-contest special case adds one line to the self-report body stating whether the contested record carried `bot:in-progress` at selection time (from the queue pull's own label snapshot). A missing projection is then diagnosable from the report alone, without a label-event history dig.

## Technical Approach

All three deliverables add observability on the existing best-effort contracts. None turns a label into a gate: the authoritative hold check stays the Step 2.8 claim read, as `dispatch/SKILL.md` Step 2 already states ("labels are projection, not truth"). Deliverable 1 reuses #2789's `mergeLabelNames` rather than adding a second label-write path.

For Deliverable 2, investigate before changing anything. `_shared/pr-early-run-lifecycle.md`'s "Root cause" section already documents that the MCP server sanitizes HTML comments on *read*, and `_shared/github-write-transport.md`'s PR-create exception says the PR write tools pass bodies through unsanitized. A body that is escaped *in storage* fits two explanations: an agent re-posting a sanitized read, or a comment write tool that escapes on write. The fix differs between them, so pick it from evidence.
