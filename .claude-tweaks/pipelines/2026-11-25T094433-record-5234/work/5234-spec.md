# 5234: verify.js: CI-sourced verdicts fall back to a local run when the only dirty path is bookkeeping-only

Surface: backend
Risk-flags: none

## Current State

`verify.js --scope` takes a CI-declared suite's verdict from the PR's CI job only on a tree that was clean when the run started. In `plugin/bin/verify.js`'s CI loop, any `startGit.dirty !== false` skips CI for every CI-declared suite with `dirty-tree` (or `tree-state-unreadable`), and the suite runs locally, or, under `localRuns: "on-request"`, the run exits 3 with no verdict. `startGit.dirty` comes from `git status --porcelain` being non-empty, so one untracked file is enough.

Plugin steps routinely leave inert files dirty right before a scoped verification:

- `hooks.js ledger-row` appends to the tracked `docs/plans/<feature>-ledger.md` during `/claude-tweaks:build` Common Step 4 and at wrap-up's reflect pass. Common Step 5's scoped verify then ran all three CI-declared suites locally with `dirty-tree`: about 8 minutes on a loaded machine, observed on 6.164.0 and again on 6.168.0. The consumer's `verify-scope.json` maps that path to `suites: [], static: false`.
- `/claude-tweaks:design-wrapper`'s review mode leaves its audit cache, `docs/plans/YYYY-MM-DD-{feature}-audit.json`, untracked. `/claude-tweaks:review`'s Step 6.7 re-verify then ran every CI-declared suite locally, about 20 minutes, with two load-timeout failures in untouched files (6.168.0). Moving that cache out of the tree is #4431's scope.

The runner already knows these paths are inert. After the ledger row was committed, the same run printed `Scope: none … still-verified: bookkeeping-only delta (docs/plans/<feature>-ledger.md)`. That comes from `plugin/bin/lib/verify/scope.js`'s `selectScope`, which takes each file's first matching rule, `decl.rules.findIndex(...)`. A precedent exists for the `generated` globs: `plugin/bin/lib/verify/declaration.js`'s `generatedExemption(dirtyPaths, generated)` already treats a tree dirty only in declared `generated` paths as clean, for the stamp (#2987, #3757). The CI-source precondition consults neither of them.

## Deliverables

1. A new pure helper `inertDirtyPaths(decl, paths)` in `plugin/bin/lib/verify/scope.js`, exported. It returns the sorted, de-duplicated `paths` when every path is inert, and `null` otherwise, including for an empty or `null` list. A path is inert when either:
   - it matches one of `decl.generated`'s globs, or
   - its **first** matching rule (the same `findIndex(globToRegExp(r.match).test(file))` order `selectScope` uses) has `suites` equal to an empty array, `static` false, and no `impact`.

   A path no rule matches is never inert: it fails closed, as in `selectScope`.
2. `verify.js`'s CI-source precondition: when `startGit.dirty === true` and `inertDirtyPaths(decl, dirtyFilePaths(undefined, scopeStatusRead))` is non-null, the tree counts as clean for CI sourcing, and each CI-declared suite goes to `fetchCiVerdict` as on a clean tree. `dirtyFilePaths` lists tracked, untracked and both sides of a rename. When that path list cannot be read (`null`), the precondition stays `dirty-tree`. `tree-state-unreadable` is unchanged.
3. Each CI attempt entry taken under the exemption carries `dirtyExempt: [paths]` (`null` otherwise), in `report.json`'s `ci` entries and the verify event's `ci` entries. stdout prints one line before the CI wait: `CI: tree dirty only in inert paths ({paths, comma-joined}) — taking CI verdicts on HEAD`.
4. The pass stamp is unchanged: it still records the tree's real `dirty` state. This record changes the CI-source precondition only.
5. `plugin/skills/test/ci-source.md`: the `dirty-tree` row (and the "on a clean tree" wording in the section that introduces the CI source) names the exemption: dirty paths that are all declared `generated` or bookkeeping-only (first matching rule `suites: []`, `static: false`) do not block CI sourcing. `plugin/skills/test/verification.md`'s CI source paragraph ("HEAD must be pushed and be the open PR's head, on a clean tree") gets the same qualifier.
6. Tests (see Acceptance Criteria).

## Acceptance Criteria

- `inertDirtyPaths` unit tests in `tests/bin-lib/verify/scope.test.js`:
  - a single path whose first matching rule is `{suites: [], static: false}` returns `[path]`;
  - a path matching a `generated` glob returns it;
  - a mix of one inert path and one path whose rule selects a suite returns `null`;
  - an unmatched path returns `null`;
  - a path whose first matching rule selects a suite, though a later rule would be inert, returns `null` (first match wins);
  - a rule with `static: true` and `suites: []` is not inert;
  - `[]` and `null` return `null`.
- `tests/bin-lib/verify/ci-cli.test.js`: a scoped run whose only dirty path is an uncommitted edit to a file mapped to `suites: [], static: false` consults the fake `gh`, takes the CI verdict (`used: true`, no local check spawned for that suite), and prints the `CI: tree dirty only in inert paths (…)` line. Its `report.json` CI entry carries `dirtyExempt` naming that path.
- The same run with the dirty path untracked instead of modified behaves the same.
- A scoped run with one inert dirty path and one dirty source file still records `fallback: 'dirty-tree'` and runs locally.
- A scoped run under `localRuns: "on-request"` with only inert dirty paths does not exit 3 for `dirty-tree`.
- `npm test -- --full` passes.

## Release Note

Take CI-sourced verification verdicts even when the only uncommitted files are bookkeeping or generated paths the scope declaration already marks as running no checks.

## Technical Approach

Add `inertDirtyPaths` beside `selectScope` in `scope.js`. It reuses the module's `globToRegExp` import and the same first-match lookup. Consider extracting a `firstRuleIndex(decl, file)` used by both, so the two cannot drift. In `verify.js`, compute `ciDirtyExempt` once, before the CI loop, and only when `startGit.dirty === true && decl && decl.ci`. Reuse `scopeStatusRead`, the porcelain text the scope read already holds (#5773), so no second `git status` runs. Change the `skipCi` guard to `startGit.dirty !== false && ciDirtyExempt === null`. Thread `ciDirtyExempt` into `verdict.ci.dirtyExempt` after each `fetchCiVerdict` call, and into `skipCi`'s entry shape as `null`, so every CI entry has the field. The stamp-write gate's own `generatedExemption` use is untouched.

### Key Files

- `plugin/bin/lib/verify/scope.js`: new exported `inertDirtyPaths` (and a shared first-match helper)
- `plugin/bin/verify.js`: CI-source precondition consults `inertDirtyPaths`; `dirtyExempt` on CI entries; one stdout line
- `plugin/skills/test/ci-source.md`: `dirty-tree` row and clean-tree wording name the exemption
- `plugin/skills/test/verification.md`: CI source paragraph's clean-tree qualifier
- `tests/bin-lib/verify/scope.test.js`: `inertDirtyPaths` unit cases
- `tests/bin-lib/verify/ci-cli.test.js`: inert-dirty CI-sourcing cases, tracked and untracked

## Gotchas

- Decided while shaping: the report's preferred fix (treat inert dirty paths as clean for the CI precondition) is the one built. The two alternatives (commit ledger rows before Common Step 5; warn from `ledger-row`) each cover one producer, and the second occurrence showed several producers in the chain.
- Decided while shaping: "inert" means the first matching rule is `suites: []` and `static: false`, plus declared `generated` globs. It is not "any path `selectScope` would put in a `none`-mode delta": an `impact` rule's path can select a subset, and a `static: true` rule runs lint or types on it, so neither is inert.
- Decided while shaping: the design-wrapper audit cache (second comment) is left to #4431, which moves it out of the tree. This record does not add `docs/plans/*-audit.json` to any declaration. A consumer whose scope file maps it to an inert rule gets the exemption automatically. An unmatched path stays fail-closed.
- Soundness: CI ran on HEAD, and the exempt paths are by declaration ones no check reads, so HEAD's CI verdict still describes everything the suites test. A misdeclared rule (a path that does affect tests, mapped to `suites: []`) would already be wrong for scope selection today. This change trusts the same declaration, never more.
- A parallel lane (`ct-verify-stamp`) is editing `verify.js`'s stamp and slot code, and #5800 edits the same CI loop two lines below this precondition. Keep the edit to the `skipCi` guard and the entry fields, and expect catch-up merges.

- #5484 (commit ledger rows from Common Steps 4.5 and 6.5 before Step 5) and #5673 (keep `/review`'s ledger writes from dirtying HEAD) are the per-producer alternative this record's report weighed. They stay useful on their own, for the pass stamp and for projects whose scope file has no inert rule for the ledger path. This record does not replace them, and they do not replace it.

## Original request

verify.js: CI-sourced verdicts fall back to a local run when the only dirty path is bookkeeping-only

**Summary:** `verify.js --scope` takes CI verdicts only on a clean tree, and it falls back to a local full run even when the only dirty path is one its own scope rules classify as bookkeeping-only.

**Kind:** Gap

**Affected component:** `bin/verify.js` (CI-sourced suite verdicts, `skills/test/ci-source.md`)

**Use case:**
- `/claude-tweaks:build` Common Step 5 runs `verify.js --scope .claude-tweaks/verify-scope.json` so the suite verdicts come from the PR's CI jobs.
- In one pipeline run, the only uncommitted change at that point was a row `hooks.js ledger-row` had just appended to `docs/plans/<feature>-ledger.md`. The project's `verify-scope.json` maps that path to `suites: [], static: false`.
- All three CI-declared suites reported `fallback: "dirty-tree"` and ran locally: about 8 minutes on a loaded machine, while the same suites were already queued in CI at 4–6 minutes.

After committing that one row and re-running, the same runner printed `Scope: none … still-verified: bookkeeping-only delta (docs/plans/<feature>-ledger.md)`. So its change-set logic already knows the path is inert, but the clean-tree precondition for CI sourcing doesn't consult that classification. The local pass also wasn't CI-sourced, so getting a CI-sourced verdict took an extra commit, push and re-run.

**Suggested behavior:**
- **Preferred:** treat a tree whose only dirty paths match a scope rule with `suites: []` and `static: false` (or a declared `generated` path, the same set `liveGeneratedExempt` already covers) as clean for the CI-source precondition.
- **Alternative:** have Common Step 5 commit pending ledger rows before invoking verification.
- **Alternative:** have `ledger-row` print a warning when it leaves the worktree dirty inside an active pipeline run.

**Definition:** Clear

**Plugin version:** 6.164.0
