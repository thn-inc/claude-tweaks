# 4492: policy resolution in worktrees: gitignored policy.yml is invisible, so pr-early-open targets the default branch

Surface: infra

**Related:** #4494, #4499, #3256, #3396, #3721, #3813, #3822, #3875, #3878, #3975, #3982, #3995, #4275, #4360, #4362, #4366, #4442, #4452

## Current State

Policy reads anchor `.claude-tweaks/policy.yml` to the current checkout's root. `resolvePolicyConfig` (`plugin/bin/lib/policy-schema.js:692-703`) takes `git rev-parse --show-toplevel` (cwd fallback) and joins the path onto it. `readPolicyFile(repoRoot)` (`plugin/bin/lib/policy.js:15`) and `auditPolicy(repoRoot)` (`policy-schema.js`) do the same with a caller-supplied root. 14 `plugin/bin` modules read policy through these, among them `pr-early-open.js`, `resolve-policy.js`, `hooks/pre-tool-use.js`, `flow/preflight.js`, `release-preflight/pack.js`, `wrap-up/pack.js` and `express/policy.js`.

When a project gitignores `.claude-tweaks/policy.yml` (or all of `.claude-tweaks/`), a fresh linked worktree has no copy. From a worktree cwd every key then reads as unset, silently. The run's `{runDir}/config.yml` overlay does not carry `integration-branch` either.

Three independent reports on 6.156.1 (this record, #4494, #4499) hit the same failure. The main checkout's policy set `integration-branch: develop`, GitHub's default branch was `main`, and `/claude-tweaks:flow #N` ran with the worktree strategy under `pr-first`. Flow's Step 2.5 divergence check, run from the main checkout, resolved `develop`. `/claude-tweaks:build` then ran `pr-early-open.js` from inside the worktree. There the key was unset, the integration-branch ladder (`_shared/integration-branch.md`) fell through to `defaultBranchRef`, and the draft PR opened against `main`. Each operator retargeted by hand with `gh pr edit --base develop`. One copied `policy.yml` into the worktree so later phases resolved `develop`. A run nobody watched would have built, reviewed and merge-gated against the production branch. The same blind spot applies to every worktree-side policy read (`worktree-always`, timeouts, `port-services`, …), not only `integration-branch`.

`.claude-tweaks/pipelines/` already solves this for the run directory: `_shared/pipeline-run-dir.md`'s Anchoring section resolves `$RUN_ROOT` to the main checkout through `git rev-parse --git-common-dir`.

## Deliverables

1. One policy-file locator used by `resolvePolicyConfig`, `readPolicyFile` and `auditPolicy`. If `<root>/.claude-tweaks/policy.yml` exists, read it, so a tracked, branch-local policy keeps today's behavior. If it is absent and `root` is a linked worktree, read the main checkout's `policy.yml` instead (the parent of `git rev-parse --git-common-dir`, resolved the same way as `$RUN_ROOT`).
2. Return which file was read (worktree or main checkout) from `resolvePolicyConfig`. `resolve-policy.js` emits a one-line stderr degrade note when the main-checkout fallback was used.
3. `pr-early-open.js` warns on stderr whenever it falls back to the GitHub default branch while running in a linked worktree, naming both the resolved base and the fact that no `integration-branch` was found.
4. The fix PR closes this record, #4494 and #4499 with closing keywords. All three report this one defect.

## Acceptance Criteria

- From a linked worktree whose project gitignores `.claude-tweaks/`, with `integration-branch: develop` in the main checkout's policy, `resolve-policy.js --values integration-branch` prints `develop` and `pr-early-open.js` resolves base `develop`.
- When the worktree has its own tracked `policy.yml`, that file wins: the main checkout's is not read.
- From the main checkout, behavior is byte-identical to today.
- `pr-early-open.js` run from a linked worktree with no `integration-branch` anywhere prints the fallback warning and still opens against the default branch.
- Unit tests cover the three locator cases (worktree file present, worktree absent with main present, both absent), using a fake `git` runner as `blast-radius-cli.js`'s tests already do. One end-to-end test runs `resolve-policy.js` in a real temporary linked worktree.

## Release Note

Pipelines running in a worktree now read the main checkout's `.claude-tweaks/policy.yml` when the project keeps that file out of git, so draft PRs target the configured integration branch instead of the GitHub default.

## Technical Approach

The reporters offered three fixes: fall back to the main checkout's policy, copy `integration-branch` into the run's `config.yml` at the Manifesto, or have `pr-early-open.js` refuse a base that differs from the manifest's. The fallback is chosen because it fixes every policy key and every reader at once, in the one place they share. The other two fix only `integration-branch`, and only for runs that went through the Manifesto. Reuse the existing `$RUN_ROOT` resolution (`_shared/pipeline-run-dir.md`, and the helper the hooks already use to find the main checkout) rather than writing a second `--git-common-dir` parser.

### Key Files

- `plugin/bin/lib/policy-schema.js` — `resolvePolicyConfig` and `auditPolicy` use the locator
- `plugin/bin/lib/policy.js` — `readPolicyFile` uses the locator
- `plugin/bin/resolve-policy.js` — degrade note when the fallback was used
- `plugin/bin/pr-early-open.js` — default-branch fallback warning in a worktree
- `plugin/skills/_shared/integration-branch.md` — rank 3 reads policy through the locator; note the worktree fallback
- `plugin/skills/_shared/pipeline-run-dir.md` — reference: the existing main-checkout anchoring

## Gotchas

- `hooks/pre-tool-use.js` reads policy on the hook hot path (the `worktree-always` gate). The fallback adds at most one `git rev-parse --git-common-dir` call and one file stat. Keep it lazy, only when the worktree file is absent, and check `perf/` budgets.
- A worktree cwd that is not inside any git repo must keep the current `process.cwd()` fallback, not throw.
- On Windows, `--git-common-dir` can return a relative or forward-slash path. Resolve it against the cwd before taking its parent.

## Original request

policy resolution in worktrees: gitignored policy.yml is invisible, so pr-early-open targets the default branch

**Summary:** A gitignored `.claude-tweaks/policy.yml` in the main checkout is invisible inside a `/flow` worktree, so `pr-early-open.js` opens the draft PR against the default branch instead of the configured `integration-branch`.

**Kind:** Defect

**Affected component:** policy resolution in linked worktrees (`bin/resolve-policy.js`, as consumed by `bin/pr-early-open.js` from `/claude-tweaks:build` Spec Step 1)

**Repro steps:**
1. In a repo whose default branch is `main` but whose PRs target `develop`, put `integration-branch: develop` in the gitignored `.claude-tweaks/policy.yml` of the main checkout.
2. Run `/claude-tweaks:flow #N` (default `worktree` strategy, `integration-model: pr-first`).
3. Flow's Step 2.5 divergence check, run from the main checkout, resolves `develop` correctly.
4. `/build` creates the worktree with `EnterWorktree` and runs `bin/pr-early-open.js` from inside it after the materialize commit.

**Expected vs. actual:**
Expected: the draft PR targets `develop`, the configured integration branch.
Actual: inside the worktree, `resolve-policy.js --values integration-branch` prints nothing. The worktree's own `.claude-tweaks/` holds only `pipelines/`, because the gitignored `policy.yml` is never copied into a new worktree. So `pr-early-open.js` opens the draft PR against `main`, the production branch. It was caught by eye and retargeted by hand (`gh pr edit --base develop`). One run therefore used two different integration branches: the main-checkout readers saw `develop`, and every worktree-side reader saw the default branch.

**Suggested fix:** resolve `.claude-tweaks/policy.yml` the same way the run directory is already anchored (`_shared/pipeline-run-dir.md`'s Anchoring section). From a linked worktree, fall back to the main checkout's `policy.yml` when the worktree has none (`git rev-parse --git-common-dir`, then its parent). Alternatively, have `pr-early-open.js` refuse to open the PR when the integration branch it resolved differs from the one the run's manifest recorded.

**Definition:** Clear
