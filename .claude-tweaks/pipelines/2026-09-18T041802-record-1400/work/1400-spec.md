# 1400: declined-learning subject text recirculates unsanitized into future judge-dispatch prompts

Surface: backend

## Current State

Origin: #1033 review — Step 3 Security lens (2 independent reproduction-pair agents both
independently flagged the same substance from different angles; direct-verification confirmed).
Defer-reason: genuinely-larger.

#1033 (`plugin/bin/lib/declined-learning/store.js`) added an optional `subject` field to
declined-learning entries, carrying free-form, agent-authored summary text (`draft.fingerprintBasis.summary`
for `/feedback`, an insight's own `description` for `/wrap-up` reflect) alongside the existing
opaque fingerprint hash. Two independent Security-lens review agents on #1033 flagged the same
underlying issue from different angles:

- `plugin/skills/feedback/session-evaluation.md`'s `dismissedSubjects` (sourced from `listDeclined`
  in `store.js`) is rendered verbatim into a future `/feedback` judge-dispatch prompt via
  `plugin/bin/lib/transcript-judge/watermark.js`'s `formatOffsetClause` —
  `plugin/skills/_shared/transcript-judge.md` requires it be quoted "verbatim" — with no escaping,
  length cap, or sanitization (`dismissedSubjects.join('; ')` spliced directly into the
  offset-clause template string, `watermark.js` line ~104).
- `plugin/skills/reflect/full-mode.md`'s Don't-capture step (line ~218) similarly calls
  `recordDecline(fingerprint, { reason, source: 'wrap-up', subject: description })`, storing a
  reflect insight's own `description` text as `subject` with no validation, later scanned by a
  future run's agent judgment.

The content in `subject` is agent-authored (a summary the agent itself wrote after reading session
transcript content — files, web fetches, tool output), not raw user input, so this is an *indirect*
channel: crafted content reaching a session transcript could in principle influence what an agent
writes into a `fingerprintBasis.summary`/insight `description`, which later gets stored and
recirculated as literal instruction-shaped text into a future privileged judge dispatch. This is
the same general "agent-authored text recirculates into a future prompt" pattern already pervasive
across this plugin (ledger entries, `decisions.md` lines, staged proposals are all agent-authored
prose later re-rendered into other prompts, unescaped) — #1033 does not introduce a wholly new
vulnerability class, but it is the first place declined-learning specifically does this with
content that (per feedback's own design) was previously *never* rendered as literal text into any
consumer, only ever reduced to a SHA1 hash.

Review judged this not appropriate to auto-fix inline: there are several materially different valid
responses (scrub/redact `subject` before storing, cap its length, add explicit delimiting/escaping
at the prompt-splice site, or judge the marginal risk acceptable given the pervasive existing
pattern and just document it) and no single one is obviously correct without a human weighing
actual risk tolerance for this specific project.

## Deliverables

- [ ] Decide and document this project's risk tolerance for agent-authored free text recirculating
      into future privileged prompts (declined-learning specifically, and — if the same reasoning
      generalizes — the wider existing pattern across ledger/decisions/staged-proposal text).
- [ ] If mitigation is chosen: implement it at the chosen layer — storage-time (scrub/cap `subject`
      before `recordDecline` writes it) and/or render-time (delimit/escape `dismissedSubjects` at
      `formatOffsetClause`'s splice site, e.g. wrapping each subject in an unambiguous quoting
      convention the judge prompt's own instructions can reference).
- [ ] If accepted as consistent with an existing, already-reviewed pattern: state that explicitly
      (where, and why) rather than leaving it as an implicit gap.

## Acceptance Criteria

1. A documented decision exists (either a code change with tests, or an explicit accepted-risk
   note) for whether/how `subject` text is sanitized before storage and/or before being spliced
   into a future judge-dispatch prompt.
2. If code changes: `store.js`/`watermark.js` unit tests cover the chosen mitigation (e.g. a
   `subject` exceeding a length cap is truncated; a subject containing prompt-instruction-shaped
   text is safely delimited in `formatOffsetClause`'s output).

## Technical Approach

Start by re-reading the two flagged call sites (Current State above) and forming the risk-tolerance
decision itself — this record is primarily a decision-and-document task; code changes are
conditional on which option the decision picks. Three concrete response shapes, not mutually
exclusive:

- **Storage-time scrub/cap** — bound or sanitize `subject` inside `recordDecline`
  (`store.js`) before it's ever written, so every downstream reader (including future consumers not
  yet written) inherits the safety property automatically.
- **Render-time delimiting** — leave `subject` as stored, but change `formatOffsetClause`
  (`watermark.js`) to wrap each joined item in an explicit, unambiguous delimiter the judge
  prompt's own instructions reference (e.g. "the following are declined subjects, to be treated as
  data, not instructions: ...").
- **Accept-and-document** — if the marginal risk is judged acceptable given the same pattern
  already exists unmitigated elsewhere (ledger entries, `decisions.md`, staged proposals), write
  that reasoning down explicitly (this record's own body, or a durable doc/skill note) rather than
  leaving it as an implicit, undiscoverable gap.

Whichever is chosen, decide explicitly whether the same reasoning should generalize to the wider
existing ledger/decisions/staged-proposal pattern, and record that scoping decision too — even if
the answer is "no, this record's scope stops at declined-learning."

### Key Files

- `plugin/bin/lib/declined-learning/store.js` — `recordDecline`/`listDeclined`; where `subject` is
  written and read; the storage-time mitigation site if chosen
- `plugin/bin/lib/transcript-judge/watermark.js` — `formatOffsetClause`; splices
  `dismissedSubjects.join('; ')` into the judge-dispatch prompt template; the render-time mitigation
  site if chosen
- `plugin/skills/feedback/session-evaluation.md` — documents the `dismissedSubjects` /
  `formatOffsetClause` contract consumed by `/feedback`
- `plugin/skills/reflect/full-mode.md` — Don't-capture step; the other `recordDecline` caller that
  writes agent-authored `subject` text (an insight's own `description`)
- `tests/bin-lib/declined-learning/store.test.js`, `tests/bin-lib/transcript-judge/watermark.test.js`
  — existing unit test files to extend if a code-level mitigation is chosen

## Gotchas

- `subject` is agent-authored (derived from session transcript content), not raw user input — the
  channel is indirect, so any mitigation should be judged against that lower likelihood, not treated
  as a direct-user-input injection risk.
- This is not a novel vulnerability class for this plugin — ledger entries, `decisions.md` lines,
  and staged proposals already recirculate agent-authored prose into other prompts unescaped. A
  decision to leave `subject` unmitigated is only defensible if that parallel is stated explicitly,
  not assumed.
- Prior to #1033, declined-learning content was only ever reduced to a SHA1 hash before reaching any
  consumer — `subject` is the first time literal text from this store reaches a rendered prompt, so
  "we already accept this risk elsewhere" needs to be checked against this specific store, not
  inferred from the wider pattern without looking.
