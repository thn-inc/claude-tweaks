# 2458: Tighten release-bootstrap's --release-type/--extra-file override validation seam

## Current State

Follow-up from #2324's whole-branch review. #2324 added `--release-type <type>`/`--extra-file <path>` to `plugin/bin/lib/init/release-bootstrap.js` and its CLI (`plugin/bin/release-bootstrap.js`), with tests in `tests/bin-lib/init/release-bootstrap.test.js` and `tests/bin-lib/init/release-bootstrap-cli.test.js`, and a stack-table prose pin in `tests/init-release-bootstrap-conformance.test.js`. Five small gaps surfaced during review, none blocking that merge:

1. `tests/bin-lib/init/release-bootstrap.test.js` has two tests asserting the identical throw on the identical branch ("override releaseType without extraFile throws" and "override with releaseType but no extraFile throws").
2. The CLI (`plugin/bin/release-bootstrap.js`) validates `--release-type`'s vocabulary before the both-together pairing check; the lib (`resolveReleaseType`) checks pairing first, vocabulary second. Both are usage errors (no functional bug), but the two layers disagree on order.
3. `resolveReleaseType`'s thrown errors ("--release-type and --extra-file must be given together", "invalid release-type override: ...") are phrased in CLI-flag language even though the function's own parameters are `releaseType`/`extraFile` — every other error in this file is parameter-shaped ("invalid branch name:", "root is not a directory:"). A direct lib caller bypassing the CLI gets a message naming flags it never passed.
4. `tests/init-release-bootstrap-conformance.test.js` pins the stack table row-for-row against its code twin, but nothing pins the new override paragraph's prose (e.g. that it correctly states the vocabulary is "this table's types plus simple").
5. During #2324's final-review fix wave, `bootstrapRelease`'s seed-version line changed from branching on the raw `extraFile` param to branching on `extraFiles.length` (to reuse one validated path for both the override case and the new `--extra-file` readability check). This incidentally changed the untested, no-override auto-detected-`simple` path too: previously that path always ignored an auto-found manifest's version (`readStackManifestVersion` has no `simple` case, falling back to a `v*` tag or `0.1.0`); it now reads the auto-found manifest's real version. Likely a correctness improvement, but unrequested scope with zero test coverage for that specific path.

## Deliverables

- Drop the duplicate test from item 1, keeping the one that's genuinely distinct (the `extraFile`-without-`releaseType` direction).
- Align validation order between the CLI and the lib (pick one order, apply it in both places).
- Reword `resolveReleaseType`'s two new thrown errors to be parameter-shaped rather than flag-shaped, matching the file's existing error style.
- Add one conformance assertion in `tests/init-release-bootstrap-conformance.test.js` pinning the override paragraph's key claims (flags named, vocabulary described).
- Add a `bootstrapRelease` test for the no-override, auto-detected-`simple`-with-a-found-manifest case, asserting the (now-changed) seeded version — or, if the pre-#2324 behavior was actually intentional, revert the `extraFiles.length`-based branch so the override and auto-detect paths use independent version sources again.

## Acceptance Criteria

- `node --test tests/bin-lib/init/release-bootstrap.test.js tests/bin-lib/init/release-bootstrap-cli.test.js tests/init-release-bootstrap-conformance.test.js` passes, with one fewer test than before item 1's fix and one more covering item 5.
- Only one test exercises the "must be given together" throw per direction, not two for the same direction.
- The CLI and lib both reject an invalid `--release-type` value the same way regardless of whether `--extra-file` is also missing (validation order no longer observably differs between the two layers).
