# 4578: policy-schema detectIntegrationModel: ignores gh-timeout-ms and silently falls back to local-merge

Surface: infra

## Current State

`integration-model` has no static schema default. When neither the run's `config.yml` pin nor `.claude-tweaks/policy.yml` sets it, `detectIntegrationModel` (`plugin/bin/lib/policy-schema.js:642-659`) computes it from the forge-detection ladder (`plugin/skills/_shared/forge-detection.md`, checks 1 and 3). Verified on `main` at `fed17360e`:

- Line 644 builds one `execOpts` with a hardcoded `timeout: 5000` for both the `git remote get-url origin` probe and the `gh repo view --json owner,name` probe. The project's `gh-timeout-ms` policy key (`policy-schema.js:134`, bounded 1000–60000, default 5000) and the `CLAUDE_TWEAKS_GH_TIMEOUT_MS` env override, which every other direct `gh` call honours through `plugin/bin/lib/shared-primitives.js`'s `GH_TIMEOUT_MS` ladder (env > policy > default), are never read here.
- Lines 652-656: any throw from the `gh` probe returns `'local-merge'`. A timeout (the child killed after 5 s) cannot be told apart from a definitive "not authenticated / not a GitHub repo" exit, and nothing records which one happened.
- The function is called in three places: `plugin/bin/lib/policy-derived-defaults.js:45` (behind `bin/resolve-policy.js`'s `integration-model` branch), `resolveIntegrationModel` (`policy-schema.js:670-676`, used by `bin/lib/reconcile/index.js`), and `plugin/bin/lib/hooks/pre-tool-use.js:1659` (`resolveRunPinnedIntegrationModel`, the PR-stamp gate's fallback for a run with no pin yet).

Observed effect (reported against plugin 6.156.3): on a GitHub Enterprise host where `gh` calls routinely take 4–14 s, two unpinned reads of `integration-model` during one `/claude-tweaks:flow #A,#B,#C` run returned `local-merge` and then `pr-first`, both `source: default`. `/build` logged a SKIP of the draft-PR bootstrap, and the bookkeeping-stamps gate then denied the next write (`bookkeeping-stamp-deny`, record-pr) until the run was corrected by hand. A contributing factor is that the first read ran without `--run`, so it bypassed the run-scoped pin (`plugin/skills/_shared/integration-model.md`, "Run-scoped stability"). That caller-side miss is a separate concern. This record covers the detection function: it fails on a slow forge and leaves no trace.

## Deliverables

1. `detectIntegrationModel` bounds its `gh repo view` probe with the resolved `gh` timeout for the repo it is detecting: `CLAUDE_TWEAKS_GH_TIMEOUT_MS` (when valid within the key's bounds) > `gh-timeout-ms` read from `{repoRoot}/.claude-tweaks/policy.yml` > the 5000 ms schema default. This is the same precedence as `shared-primitives.js`'s ladder, but anchored on `repoRoot` rather than `process.cwd()`. An explicit `opts.timeoutMs` passed by a caller wins over the ladder. The `git remote get-url origin` probe keeps a short local bound; it does not need the `gh` budget.
2. A `gh` probe that ends by timeout (`ETIMEDOUT` / killed by signal) is retried once with the same timeout before detection gives up. That matches `gh-timeout-ms`'s documented "killed and retried once" semantics. A definitive outcome is not retried: a non-zero exit, or `gh` absent (`ENOENT`).
3. Detection reports *why* it resolved `local-merge`. A timeout that survives the retry is a **degraded** detection, kept distinct from a detected `local-merge` (no remote, `gh` absent, or `gh repo view` exiting non-zero). Whatever form the signal takes, `detectIntegrationModel(repoRoot, opts)` keeps returning a bare enum string for every existing caller (additive only). Callers that want the reason get it through a new opt-in surface, for example an `opts.onDegrade` callback or a sibling export.
4. `bin/resolve-policy.js`'s `integration-model` resolution (through `policy-derived-defaults.js`) surfaces a degraded detection in two ways: a `degraded — integration-model: forge detection timed out after {ms} ms (x2); resolved local-merge — pin integration-model in .claude-tweaks/policy.yml or raise gh-timeout-ms` line on stderr, and an additive `degraded: "<reason>"` field on that key's JSON entry. `--values` output is unchanged (still the bare value on stdout).
5. `pre-tool-use.js`'s `resolveRunPinnedIntegrationModel` passes an explicit `opts.timeoutMs` chosen so that its worst case (probe plus one retry) stays within the hook's spawn budget (the "I5" budget its own comment cites). A comment at the call site explains why the hook does not inherit a 60 s `gh-timeout-ms`.
6. `plugin/skills/_shared/forge-detection.md`'s "Code twin" paragraph and `detectIntegrationModel`'s header comment (`policy-schema.js:623-641`, which currently says "Each check runs under a 5s timeout") describe the new timeout source, the retry-once rule, and the degraded-vs-detected distinction.
7. Tests in `tests/integration-model.test.js`, `tests/merge-verification.test.js` (which pins `computeDerivedDefaults` today), and `tests/resolve-policy-cli.test.js` cover the new behaviour. Each one must go red against the current code.

## Acceptance Criteria

- With `gh-timeout-ms: 20000` in a fixture repo's `policy.yml` and a fake `gh` on `PATH` that sleeps 8 s and then prints valid JSON, `detectIntegrationModel(fixture)` returns `pr-first`. Today it returns `local-merge` after 5 s.
- With `CLAUDE_TWEAKS_GH_TIMEOUT_MS=20000` and no policy key, the same fake resolves `pr-first`. With an explicit `opts.timeoutMs: 1000`, it resolves `local-merge` as a degraded detection.
- When the fake `gh` times out on its first call and succeeds on its second, the result is `pr-first`, and the fake records exactly two invocations.
- When the fake `gh` exits non-zero immediately (no timeout), the result is `local-merge`, the fake is invoked exactly once, and no degrade is reported.
- When `gh` is absent from `PATH` and a remote is present, the result is `local-merge` with no degrade, which is today's behaviour for the MCP-only environment. `mcpReachable: true` still short-circuits to `pr-first`.
- When the fake `gh` always times out, `node bin/resolve-policy.js integration-model` (JSON mode, no `--run`, no pin) prints `local-merge` with `source: "default"` and a `degraded` field, and prints exactly one `degraded — integration-model: …` line on stderr. `--values integration-model` prints only `local-merge` on stdout.
- With `integration-model: pr-first` pinned in `policy.yml`, or in `--run`'s `config.yml`, none of the above invokes `gh` at all: the pin still wins outright.
- `resolveRunPinnedIntegrationModel` passes an explicit `timeoutMs`, and a test (or a source-scan assertion) pins that value at or below the hook budget it cites.
- `forge-detection.md`'s Code-twin paragraph and the `detectIntegrationModel` header comment no longer state a fixed 5 s timeout.
- `npm test` passes.
- **Decision (plan review, 2026-10-31):** `session-start.js` passes a hook-bounded `timeoutMs` into `reconcile()`, which forwards it to `resolveIntegrationModel`/`detectIntegrationModel`, pinned by a test like Deliverable 5's pre-tool-use one. The SessionStart path gets the same bound as the pre-tool-use hook. (Plan-review Q1: Reading B.)
- **Decision (plan review, 2026-10-31):** The pre-tool-use hook keeps 5000 ms per gh attempt. With one retry plus the 5 s git probe its worst case is 15 s, and "the hook budget" in Deliverable 5 and the criterion above means that 15 s bound, not the I5 spawn-count fast path. (Q2: Reading B.)
- **Decision (plan review, 2026-10-31):** `resolveRunPinnedIntegrationModel` takes the timeout as a parameter. The hook passes its hook-bounded value; `plugin/bin/lib/pr-bookkeeping/precondition.js` (behind `check-pr-bookkeeping.js`) passes nothing and follows the `gh-timeout-ms` ladder. (Q3: Reading B.)
- **Decision (plan review, 2026-10-31):** Any failed retry after a first-attempt timeout (a second timeout or a non-zero exit) is a degraded detection. A test with a fake `gh` that times out and then exits non-zero asserts two invocations and one degrade. (Q4: Reading B.)

## Release Note

Forge detection for `integration-model` now honours `gh-timeout-ms`, retries once on a timeout, and reports a degraded detection instead of silently resolving `local-merge` on a slow GitHub host.

## Technical Approach

Keep `detectIntegrationModel`'s string return and add the reason through an opt-in surface, so no existing caller changes shape (expand-contract). Resolve the timeout inside `policy-schema.js` from `repoRoot`. `readFileSafe` and `resolveValue` already live in that module, so the policy read needs no new dependency. Do not top-level require `./policy`, which itself requires `./policy-schema`, or `./shared-primitives`, whose `GH_TIMEOUT_MS` getter reads `process.cwd()` rather than the repo being detected. Classify the `execFileSync` error: `err.code === 'ETIMEDOUT'` or a set `err.signal` means timeout and is eligible for one retry; `ENOENT` means `gh` is absent, a definitive result; anything else is a definitive non-zero exit. Thread the reason through `computeDerivedDefaults` into the result entry, and have `resolve-policy.js` print the stderr degrade line in the existing `degraded —` style (`bin/verify-run-bookends.js:205`). Tests reuse `tests/integration-model.test.js`'s `gitRepo()` / `ghAbsentPath()` fixtures. Add a fake-`gh` shim directory placed first on `PATH`, configurable for sleep duration, exit code and an invocation counter.

### Key Files

- `plugin/bin/lib/policy-schema.js` — `detectIntegrationModel`: resolved timeout, retry-once on timeout, degrade reason; header comment updated
- `plugin/bin/lib/policy-derived-defaults.js` — carry the degrade reason into the `integration-model` result entry
- `plugin/bin/resolve-policy.js` — emit the stderr `degraded —` line and the additive JSON `degraded` field
- `plugin/bin/lib/hooks/pre-tool-use.js` — `resolveRunPinnedIntegrationModel` passes an explicit hook-bounded `timeoutMs`
- `plugin/bin/lib/shared-primitives.js` — read-only reference for the env > policy > default ladder and bounds (`timeoutFromEnv`, `policyKeyBounds`); change only if a repoRoot-anchored helper is extracted here
- `plugin/skills/_shared/forge-detection.md` — Code-twin paragraph: timeout source, retry, degraded vs detected
- `tests/integration-model.test.js` — fake-`gh` timeout/retry/degrade cases
- `tests/merge-verification.test.js` — `computeDerivedDefaults` degrade-field propagation
- `tests/resolve-policy-cli.test.js` — stderr degrade line and JSON `degraded` field; `--values` unchanged

## Gotchas

- The reporter's `gh-timeout-ms: 90000` is above the key's schema max of 60000 (`policy-schema.js:134`). `resolveValue` silently turns an out-of-range value into the 5000 default, so even after this fix that exact setting still resolves to 5 s. The acceptance tests deliberately use in-range values. Whether an out-of-range timeout should warn is a separate concern and is not changed here.
- The fallback value stays `local-merge` on a degraded detection. `forge-detection.md` documents the ladder as fail-open, and `pr-first` with an unreachable `gh` would fail at the draft-PR bootstrap instead. Run-to-run stability inside a pipeline comes from the run-scoped pin (`_shared/integration-model.md`), which this record leaves untouched. This record makes a failed detection visible and less likely; it does not invent a cross-call cache.
- `pre-tool-use.js` runs inside a lifecycle hook. Inheriting a 60 s `gh-timeout-ms` plus one retry there could exceed the hook's own timeout and break the session-safety invariant in `docs/hooks.md`, so that call site must keep an explicit bound.
- Requiring `./policy` from `policy-schema.js` at module top level creates a require cycle (`policy.js` requires `policy-schema.js`). Read `policy.yml` with `readFileSafe` and `resolveValue` in place, or lazy-require inside the function.
- The live-repo test (`detectIntegrationModel: this repo … resolves a valid enum value`) asserts shape only, so it must not start depending on network latency. Keep every new case on the fake `gh`.

## Original request

policy-schema detectIntegrationModel: ignores gh-timeout-ms and silently falls back to local-merge

**Summary:** Forge detection for `integration-model` uses a hardcoded 5 s `gh repo view` timeout. It ignores the project's `gh-timeout-ms` and silently returns `local-merge` on any failure, so on a slow GitHub Enterprise host the resolved model flips from run to run.

**Kind:** Defect

**Affected component:** `bin/lib/policy-schema.js` (`detectIntegrationModel`), used by `resolve-policy.js integration-model`

**Repro steps:**
1. Use a project with no `integration-model:` key in `.claude-tweaks/policy.yml`. Set `gh-timeout-ms: 90000` because the forge is a GitHub Enterprise host where `gh` calls routinely take 4–14 s.
2. Run `/claude-tweaks:flow #A,#B,#C` (a multi-record run on the default worktree strategy).
3. Resolve `integration-model` once before the worktree catch-up and once again inside the worktree minutes later.

**Expected vs. actual:**
Expected: the same model on every resolution. Detection should honour `gh-timeout-ms`; if it can't decide, it should fall back to a stable value with a logged degrade, not silently switch models.
Actual: one read returned `local-merge` and a later read returned `pr-first`. Both came from detection (`source: default`), because the hardcoded `timeout: 5000` (`bin/lib/policy-schema.js:644,652-654`, still present on main at bcd27902c) sometimes fails and falls back to `local-merge` without a trace. `/build` logged a SKIP of the draft-PR bootstrap. The bookkeeping-stamps gate then denied the next write (`bookkeeping-stamp-deny`, record-pr), and a manual correction was needed before the draft PR opened. Contributing factor: the first read ran without `--run`, so it bypassed the Manifesto's run-scoped pin (`_shared/integration-model.md`, "Run-scoped stability").

**Suggested fix:** pass the resolved `gh-timeout-ms` to the detection `gh` call. When detection fails, keep the pinned or default model rather than silently returning `local-merge`, and log a degrade line so that "detected local-merge" can be told apart from "detection failed". Workaround: pin `integration-model:` explicitly in `.claude-tweaks/policy.yml`.

**Definition:** Clear
