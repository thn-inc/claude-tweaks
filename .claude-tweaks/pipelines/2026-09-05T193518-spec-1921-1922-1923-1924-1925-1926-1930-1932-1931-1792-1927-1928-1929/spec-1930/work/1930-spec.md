# 1930: wrap-up-pack.js: one deterministic fact pack for wrap-up Phases 3 and 4, read once instead of ten serial probes

Surface: backend
**Related:** #1869, #1236

## Overview

On record #1535's dispatched run, wrap-up took 15 minutes: residue sweep, unblocked-record search, merge-check inputs, oversight-floor comparison, merge-size probe, PR state refresh, release status, claim state, ledger count — ten deterministic probes, each its own model turn with a reasoning step between, every probe's raw output left in context for the rest of the call. Wrap-up plus reflect (27 min) exceeded every verification run on that record combined.

This unit applies the boundary `verify.js` (#892) and `build-review-context.js` already drew: the runner owns execution and bounding, the skill owns judgment. `bin/wrap-up-pack.js --run <dir>` runs the deterministic inputs wrap-up's Phase 3 and Phase 4 consume, concurrently, and emits one JSON document with a per-probe `{ok, value | error, durationMs}` envelope — a probe failure degrades that field, never the pack. `wrap-up/SKILL.md` Phases 3–4 read the pack once; the `assess-agent-autonomy merge-check` dispatch keeps its own LLM judgment but takes its inputs from the pack; every existing decision-log line is still written, from the pack's values. Named `wrap-up-pack.js` rather than the design's `wrap-up-facts.js` because `plugin/bin/lib/wrap-up/facts.js` already exists (curation-registry gate facts) and a same-basename CLI would collide with it.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Changing any wrap-up judgment, gate, or decision-log entry — identical entries from the pack's values.
- The second call's preflight pack (`flow-preflight.js`), reflect depth, console auto-resolution — Phases 7b/7c.
- Replacing `wrap-up-engine.js` (Phase 2's curation engine) or `wrap-up-state.js` (the State block) — the pack calls them, it does not fork them.
- Running the residue sweep's `remedy: auto` actions — the pack reads; the skill acts.

## Acceptance Criteria

1. `gatherPack` with fake deps where `residue` throws returns `pack.residue.ok === false` with the error message, every other probe `ok: true`, and `pack.inputs` naming `{record, pr, base, integrationBranch, worktree}` with sources.

3. `--run` pointing at a worktree-local shadow path exits 3 with a stderr message and writes nothing.
4. All probes run concurrently: with fake deps that each sleep 200 ms, the pack's `durationMs` is under 600 ms (not ~2 s).
5. `grep -c 'wrap-up-pack.js --run' plugin/skills/wrap-up/SKILL.md` is 1; `wrap-up/SKILL.md` is smaller than before this unit (byte count strictly lower); `residue-sweep.md`, `unblocked-records.md`, `review-console.md`, `auto-merge-short-circuit.md`, `summary-template.md`, `cleanup-procedures.md` each cite `wrap-up-pack.json` and state the absent-file fallback.
6. `merge-check.md` Step 1 documents the `--pack` input and still documents the CLI path when absent.
7. `npm test` passes with no new failures relative to `main`.

## Technical Approach

One process runs ten independent reads concurrently and returns one bounded JSON; the skill's ten sub-steps become ten field reads with the same downstream judgments. Envelope per probe, never per pack, so a failing `gh` call degrades one field and the rest of wrap-up proceeds exactly as today's per-probe failure handling already allows.

## Gotchas

- Red-team resolution: `pack.inputs` gains a `records: [N, ...]` array (the dispatched group's member record numbers, sourced from `run-state.json`'s group membership, or a single-element array for a non-grouped run); `recordLabels.value` is keyed by each of those numbers.
- Red-team resolution: the `release` probe calls only `shipped-record.js`'s read/status-check export — never a write path; this is a pure-read call, stated explicitly since the pack's read-only invariant otherwise enumerates only claims/archive/comments.
- Red-team resolution: distinguish two "no data" cases explicitly — (a) `wrap-up-pack.json` entirely absent (older run, never generated) → the sub-file's own probe runs exactly as it did before this unit; (b) the file is present but a specific key is missing (e.g. after `--only`) → treated identically to that field's `ok: false` (the sub-step's existing degraded-field handling), never a wholesale fallback to the old per-step probe.
- Red-team resolution: `--only` always still includes `inputs`, `generatedAt`, and `durationMs` in its output, regardless of which probe keys were requested.
- Red-team resolution: an `ok: false` `blastRadius` field (e.g. an unresolvable base, `[IL-131]`) routes `merge-check`'s Step 1 to its existing `could-not-gather` path — it never triggers a fresh call to `blast-radius.js`, since the pack's failure already represents the freshest attempt.
- Red-team resolution: under a `local-merge`/no-forge project, the `pr`/`recordLabels`/`release` probes report `ok: false, error: 'no-forge'` (a distinct reason string from `gh`-absent, though handled identically downstream by the sub-steps that read them).
- Red-team resolution: subprocess-vs-module boundary for the remaining five probes — `claim` calls `bin/lib/issues/claims` directly (a module read, no subprocess); `ledger` reads and parses `docs/plans/*-ledger.md` directly via `fs` (no subprocess); `unblocked` uses a native GraphQL call via `gh` (subprocess) under `work-links: native`, or a body-text `Blocked by #N` regex scan (no subprocess) otherwise; `recordLabels` and `pr` both shell to `gh` (`gh issue view`/`gh pr view`, subprocesses).
- Red-team resolution: the `unblocked` probe reads `work-links` from the project's resolved policy (`resolve-policy.js --values work-links`) — the same source `/specify`'s Step 4 linking pass already reads.
- Red-team resolution: `pack.inputs.sources` maps each field to its origin — `record` ← the materialized header; `pr` ← `run-state.json`'s `pr.number`; `base` ← the merge-base against the integration branch; `integrationBranch` ← `_shared/integration-model.md`'s resolution; `worktree` ← `run-state.json`'s `worktree`.
- Red-team resolution: the `residue` probe's invocation is `residue.js --base <sha> --scope blast-radius --json` in both places this record mentions it — the Deliverables bullet is aligned to include `--base <sha>`.
- Red-team resolution: concurrent real `git`/`gh` subprocess calls under `Promise.allSettled` are expected to be safe since each probe reads independently (no shared lockfile writes among the ten probes); a transient rate-limit or `index.lock` collision degrades that one probe's field to `ok: false` rather than failing the whole pack, consistent with CLAUDE.md's own machine-load caveat.
- Red-team resolution: when one of the three input sources (`run-state.json`, materialized header, `config.yml`) is missing, that specific `pack.inputs` field is marked with `source: 'unavailable'` and the rest of the pack still gathers using whatever inputs ARE available (e.g. `base`/`integrationBranch` can resolve without a PR number).

- `wrap-up/SKILL.md` is 40,708 bytes; this unit must make it smaller, not larger — replace each superseded invocation sentence with a field read, and keep every procedure detail in the sub-files.
- Name collision: `plugin/bin/lib/wrap-up/facts.js` exists (curation gate facts) — hence `pack.js`/`wrap-up-pack.js`; do not rename the existing module.
- `merge-check`'s dispatch is a subagent: the pack's `blastRadius` value must be inlined into its prompt, not referenced by path (`_shared/subagent-output-contract.md`).
- `blast-radius-cli.js` throws on an unresolvable base by design (`[IL-131]`); the pack records `ok: false` — never substitute an empty summary.
- `merge-size-probe.js` exits 1 with no stdout on a probe failure; as a module call, catch `MergeSizeProbeError` into the envelope.
- `gh` may be absent (MCP-transport sandboxes, `_shared/github-write-transport.md`); the `pr`/`recordLabels`/`unblocked` probes report `ok: false, error: 'gh-absent'` and the sub-steps take their existing MCP/no-forge paths.
- The pack is read-only: it never releases claims, archives, or posts comments. Anchoring via `resolveTarget` (`[IL-127]`).
- Every decision-log line that exists today must still be written with identical wording — grep `decisions.md` literals in the touched sub-files and keep them.
- `refs #N` in commits.

## Decision Rationale

See the Phase 1 sub-issue's Decision Rationale for the design-wide rationale. Specific to this unit: deterministic-first — where a step is reads followed by a judgment, the reads are one CLI and the judgment is one turn; the accepted trade is running probes the model might have skipped after an early finding (seconds of CLI time against minutes of turns); per-probe envelopes so a failure is reported as failed rather than silently absent.
