# 1925: Runner-owned flaky retry allowlist in verify.js: exact-path files, every-failing-file-listed-or-no-retry, hit-counter escalation

Surface: backend
**Related:** #1837

## Overview

A flaky test costs a full suite run today: `test/verification.md`'s "Flake adjudication" has the *agent* re-run the failed file in isolation, and because the pass stamp is written only for a full-set pass, an adjudicated flake cannot stamp, so the agent runs the whole suite again. #1904's Group B paid three full reruns (~18 min) for one intermittent file. This unit moves the retry into the runner: a project lists known-flaky test files (exact repo-relative paths) in `verify-scope.json`'s `flaky` section with a per-suite `retry` command template; on a `tests`-family failure the runner extracts the failing file paths from the log, and only when **every** failing file is allowlisted re-runs those files serially (log order), each up to `maxRetries` attempts, stopping at the file's first pass; a file that exhausts its attempts fails the run and short-circuits the rest. All pass → the check is `pass (flaky-retried: [...])`, the stamp and `report.json` record `flakyRetried`, and a `CAVEAT:` line renders under the table. Any unlisted failing file → ordinary failure, no retry. A per-file hit counter in the count-stamp file escalates the caveat at 5 hits so the allowlist cannot quietly become permanent.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Retrying `types`/`lint` (deterministic; never retried).
- Test-name or regex-based allowlisting — file paths only.
- Auto-adding a file to the allowlist — the agent may *propose* it as a staged patch after an isolated rerun passes, never add it silently.
- Fixing #1837 (vitest counts parse as `null` on ANSI-coloured output) — a separate bug; but the failing-file extraction added here must strip ANSI escapes so it does not inherit the same defect.

## Acceptance Criteria

1. `extractFailingFiles` returns `['tests/a.test.js']` for a node `--test` log whose only failing frame is `at TestContext.<anonymous> (tests/a.test.js:12:5)`, `['src/x.test.ts']` for a vitest `FAIL src/x.test.ts` line wrapped in `^[[31m…^[[0m`, and `[]` for a generic log.
2. `planRetry` returns `retry: true` only when every failing file is listed and a template exists; `unlisted: [...]` names every unlisted file; `no-parse` when `failingFiles` is empty.
3. CLI: with a declaration listing `tests/flaky.test.js` and a `retry.tests` template, a `tests` command that exits 1 printing a failing frame for that file, and a retry command that exits 0, the run exits 0, the table row contains `flaky-retried`, stdout contains `CAVEAT: flaky-retried: tests/flaky.test.js`, `report.json.checks.tests.flakyRetried` equals `['tests/flaky.test.js']`, and the stamp file exists with `flakyRetried` set.
4. Same setup with a failing frame for an unlisted `tests/real.test.js` → exit 1, no retry command spawned (assert via marker file), stamp not written.
5. With a pre-seeded count stamp `flakyHits: {"tests/flaky.test.js": 4}`, AC3's run prints `CAVEAT: flaky-allowlist: tests/flaky.test.js retried 5 times` and `report.json.flakyEscalation` has one entry.
6. `maxRetries: 2` performs at most two per-file attempts; `maxRetries: 3` fails `readDeclaration` (ceiling 2, Phase 2a's validator).
7. `types`/`lint` failures never trigger `planRetry` (assert no retry spawn for a failing `lint` check).
8. `npm test` passes with no new failures relative to `main`.

## Technical Approach

The runner already extracts a failing region per family; extracting failing *files* is the same sniff one level up. The retry is a normal `runOne` spawn with its own log, so the report's bounded-extraction contract is unchanged. The allowlist is exact-path, the runner enforces "every failing file listed or no retry", and the hit counter is the honesty mechanism.

### Data / API Surface

- Declaration (Phase 2a): `flaky: {files: [repo-relative paths], maxRetries: 1}`; `retry: {suiteName: "cmd -- {file}"}`.
- `report.json`: per-check `flakyRetried: [files]`, `retryFailed: [files]`; top-level `flakyEscalation: [{file, hits}]`.
- Stamp: `flakyRetried: [files]` (field reserved in Phase 1).
- Count stamp: `{tests, sha, recordedAt, flakyHits: {file: n}}`.
- stdout: `pass (flaky-retried: {files})` row; `CAVEAT: flaky-retried: …` and `CAVEAT: flaky-allowlist: …` lines.

## Gotchas

- Red-team resolution: Current State's `declaration.js`/`flaky`/`retry` API is described as Phase 2a designs it — if Phase 2a's merged implementation deviates from this shape, this unit's Deliverables adjust to match the merged interface (Prerequisites already marks Phase 2a `blocked-by`).
- Red-team resolution: the ANSI-strip regex in this record's Gotchas is corrected to `/\x1b\[[0-9;]*m/g` (ESC-anchored) — the previously stated `/^[\[[0-9;]*m/g` never matches the real ESC control byte that begins an ANSI sequence and must not be implemented literally.
- Red-team resolution: at `flakyHits >= 5`, BOTH caveat lines render in the same run (the ordinary `flaky-retried` line, then the escalation line) — they state independently true facts, not alternatives.
- Red-team resolution: retry log filenames are namespaced per file, not just per attempt — `{name}-retry-{file-slug}-{i}.log`, where `{file-slug}` is the retried file's path with `/` replaced by `-`, so two simultaneously-retried files never collide on the same log path.
- Red-team resolution: when a failing file is allowlisted but its suite has no `retry[suite]` template yet, the staged allowlist proposal also notes that a retry template must be added alongside the `flaky.files` entry — the proposal is incomplete without both.
- Red-team resolution: `flaky.files` is global (suite-agnostic) — a listed file is eligible for retry under whichever `tests`-family suite it fails in, using that suite's own `retry[suite]` template.
- Red-team resolution: `flakyHits` pruning happens inside `count-stamp.js`'s write path on every `verify.js` run — any key present in the stored `flakyHits` map but absent from the current `flaky.files` allowlist is dropped before the count stamp is rewritten.
- Red-team resolution: table-row format for multiple retried files in one check joins with `, ` — e.g. `pass (flaky-retried: a.test.js, b.test.js)`.
- Red-team resolution: the isolated-retry mechanism assumes a listed flake is file-intrinsic (its failure reproduces or clears independent of surrounding suite state) rather than suite-emergent (order- or shared-fixture-dependent) — this is an accepted, unvalidated assumption; a file whose flake is actually suite-emergent could pass its isolated retry while masking a real regression. The hit-counter escalation (5 retries) is the mitigation: a suite-emergent flake keeps re-triggering and eventually forces human attention rather than silently laundering forever.

- `wrap-up/SKILL.md` is 40,708 bytes today — already within ~250 bytes of the 40,960 ceiling. Do not add to it; add the row to `leftover-routing.md` and, if a citation is unavoidable, trim an equal number of bytes elsewhere in `SKILL.md` first (`[IL-140]`).
- Strip ANSI before every regex (`/^[\[[0-9;]*m/g`) — #1837 is the live example of a parser defeated by colour codes.
- Bounded retry, not unbounded best-of-N: each allowlisted failing file is re-run sequentially (serial, in the order the log listed them), up to `maxRetries` attempts, stopping at its first pass; a file that exhausts `maxRetries` without passing fails the run immediately (short-circuit — remaining files are not retried, and the report names the file that exhausted). `maxRetries` is a per-file attempt ceiling, never a per-run count of retried files.
- The retry spawns must go through `runOne` so log capture, spawn errors, and duration are recorded the same way; never `execSync` inline.
- The stamp after a retried pass is a legitimate full pass (every declared check passed on the final attempt) — write it; the design's guarantee is preserved because the retried file re-ran the same command family in isolation, which is what the old agent-side adjudication prescribed.
- Keep the constants (`maxRetries` ceiling 2, escalation at 5) as stated literals in code with a comment; no policy lever.
- `refs #N` in commits; `**Related:** #1837` on this record (file overlap on `extract.js`, different concern).

## Decision Rationale

See the Phase 1 sub-issue's Decision Rationale for the design-wide rationale. Specific to this unit: file-path allowlisting because every runner family prints paths and the isolation rerun already keys on them (a regex invites listing a whole suite); "every failing file listed or nothing" so a real regression can never hide behind a listed flake; the hit counter because an allowlist with no pressure to shrink becomes permanent.
