# 3372: /flow: treat a dispatch-bound run as auto regardless of auto-mode policy (backstop for #3335)

Surface: infra

**Related:** #3335, #3212, #3368, #3289

## Current State

#3335 (PR #3369, merged as 77ed997bf) made `/claude-tweaks:dispatch` pass `auto` explicitly on both Task-call `/claude-tweaks:flow` commands, so a project with `auto-mode: default-off` no longer resolves a dispatched, headless call to `interactive`. That guarantee lives only in prose. It holds only if the dispatched agent runs the command text verbatim, and #3212 documents first-call agents that paraphrase or skip parts of `/flow`.

Today `/claude-tweaks:flow` Step 1 (`plugin/skills/flow/SKILL.md:117-119`) resolves the mode in this order:

1. An explicit mode keyword.
2. The `auto-mode` policy, where `default-off` gives `interactive`.
3. The intrinsic `auto`.

Step 1 never consults the run's own dispatch binding, even though that binding is already on disk when Step 1 runs. `/claude-tweaks:dispatch` Step 5 runs `hooks.js record-worktree --run <dir> <wt> --dispatch` before call 1 (`dispatch/sibling-session-check.md`). That call stamps a permanent `dispatched: true` into `{run-dir}/run-state.json` and passes the same directory inline as `PIPELINE_RUN_DIR`.

Suppose a dispatched agent runs `/flow` but drops the `auto` token. Under `default-off`, the call resolves to `interactive`. `flow/manifesto.md:17` says interactive mode writes no `config.yml`. `checkDispatchConfigGate` (`plugin/bin/lib/hooks/pre-tool-use.js`) then denies every git write in the bound worktree, and its remedy tells the agent to run Step 3, which an `interactive` run never does.

The decision on the open question was made on 2026-10-17: yes. A dispatch-bound run resolves to `auto` regardless of the `auto-mode` policy, as a mechanical backstop beside the explicit token.

## Deliverables

1. In `plugin/skills/flow/SKILL.md` Step 1's mode-resolution list, add a new rung between "Explicit mode keyword" and "`auto-mode` policy". When `$PIPELINE_RUN_DIR` is set, resolves under `$RUN_ROOT` (`_shared/pipeline-run-dir.md`'s anchoring check), and its `run-state.json` parses with `dispatched: true`, the mode is `auto`. Any other outcome falls through to the `auto-mode` policy rung unchanged. That covers an unset variable, a directory outside `$RUN_ROOT`, a missing or unparseable `run-state.json`, and `dispatched` absent or not `true`.
2. Record the resolved mode's source so the run shows why it is `auto`. The Manifesto's Mode row (`flow/manifesto.md`, row 1) and its log line name the source as the dispatch binding, for example `auto (dispatched run)`. Do not write a `decisions.md` line at Step 1, for the reason given in Gotchas.
3. Update `plugin/skills/_shared/auto-mode-contract.md`:
   - The mode table's `interactive` row and the **Default note** must state that `auto-mode: default-off` does not lower a `/flow` run whose run dir is bound `dispatched: true`.
   - An explicit mode keyword still outranks that binding.
4. Update every other restatement of "`default-off` → `interactive`" that claims to describe `/flow` so it carries the dispatched-run exception. At minimum that includes `plugin/skills/_shared/policy-schema.md`'s `auto-mode` row. Grep the repo for further restatements, including in docs and journeys.
5. Add a new `node --test` prose-conformance pin. It must assert three things against the live `flow/SKILL.md`: the rung exists, it sits after the explicit-keyword rung, and it sits before the `auto-mode` policy rung. It must also assert the contract's dispatched-run sentence.

## Acceptance Criteria

- `flow/SKILL.md` Step 1 lists four mode-resolution rungs in this order: explicit keyword, then the dispatch binding (`run-state.json` `dispatched: true` → `auto`), then the `auto-mode` policy, then intrinsic `auto`.
- The dispatch-binding rung names its fall-through cases explicitly: unset `PIPELINE_RUN_DIR`, a run dir that fails the `$RUN_ROOT` anchoring check, a missing or unparseable `run-state.json`, and `dispatched` not `true`. Each falls through to the `auto-mode` policy rung, and none of them stops the run.
- An explicit `interactive`, `hybrid`, or `confirm` keyword on a dispatch-bound run still wins. The new rung sits below rung 1, never above it.
- On a dispatch-bound run that resolved through the new rung, the Manifesto's Mode row names the dispatch binding as the mode's source.
- `_shared/auto-mode-contract.md`'s `interactive` row and Default note both state the dispatched-run exception. `_shared/policy-schema.md`'s `auto-mode` row does too.
- The new test fails when the rung is removed from `flow/SKILL.md`, which can be shown by reverting the rung. It also fails when the rung is moved above the explicit-keyword rung.
- `npm test` passes.

## Technical Approach

Step 1 reads `$PIPELINE_RUN_DIR/run-state.json` directly and does not route through `resolve-policy.js`. The dispatch binding is run state, not policy, and `resolve-policy.js` walks only `config.yml` → `policy.yml` → the schema default. That walk cannot be the source here, because `config.yml` is exactly what the Manifesto has not written yet.

Use one plain `node -e` read that prints `dispatched` or nothing. It must be fail-open: any exception prints nothing, so the rung falls through. Anchor the path check with the same rule Step 3's adoption already applies (`_shared/pipeline-run-dir.md`), so a worktree-trapped `PIPELINE_RUN_DIR` is never trusted `[IL-127]`.

The test follows `tests/dispatch-flow-explicit-auto-mode.test.js`'s pattern: live-prose slicing of the `### Step 1: Validate Input` section, with an ordering assertion on the numbered rung list.

### Key Files

- `plugin/skills/flow/SKILL.md` — Step 1 mode resolution gains the dispatch-binding rung
- `plugin/skills/flow/manifesto.md` — Mode row (row 1) and its log line name the dispatch binding as source
- `plugin/skills/_shared/auto-mode-contract.md` — `interactive` row and Default note state the dispatched-run exception
- `plugin/skills/_shared/policy-schema.md` — `auto-mode` row carries the dispatched-run exception
- `tests/flow-dispatched-run-auto-mode.test.js` — new prose pin for the rung's presence, its order, and the contract sentence
