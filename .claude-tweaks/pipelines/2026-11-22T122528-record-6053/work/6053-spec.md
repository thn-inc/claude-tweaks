# 6053: Tell specify which records a plan-less lane will take

Surface: infra
Risk-flags: none

## Overview

Specify should not write a plan for a record that a lane with no plan will take: the pipeline driver, the express lane ("the lane composes no plan", `_shared/express-lane.md`) and build's micro-plan path. `drive.js --check` cannot answer this at specify time, because it also refuses on grants, open blockers, open PRs and `express-driver: split` parity, none of which is settled when a record is shaped. This record adds a predicate that answers only from the record's lane bounds.

**Complexity:** Low
**Estimated tasks:** 3-4

## Non-Goals

- Changing driver admission (#6018, #6019 do).
- Calling the predicate from specify (the specify record does).

## Current State

- `plugin/bin/lib/driver/admission.js` — `evaluateAdmission`, `reviewerGateReason`.
- `plugin/bin/lib/express/eligibility.js` — `isInsideLaneBounds`, `isBeyondExpressBounds`.
- `plugin/skills/build/micro-plan.md` — applicability gate: `ceremony: fast-lane` + `size: low` + at most one implementation Key File.
- Lane-bound policy keys in `plugin/bin/lib/policy-schema.js` (`express-driver`, `express-driver-max-size`, `express-driver-max-key-files`, protected paths).

## Deliverables

1. A pure function `needsNoPlan({labels, keyFiles, body, policy}) -> {lane: 'driver'|'express'|'micro-plan'|null, reason}` beside the admission code, reusing `isInsideLaneBounds` and the micro-plan gate's rule; it ignores grants, blockers, PRs and parity. `express-driver: off` means the driver lane never matches; `split` is read as `on` for the bounds, since parity is ignored.
   - Inputs: `size`, `ceremony` and `risk` come from the record's `size:*`, `ceremony:*` and `risk:*` labels (stamped before specify plans); `keyFiles` is parsed from the body's `### Key Files` section by the existing parser; risk flags from the `Risk-flags:` line by `parseRiskFlags`; `policy` is the resolved policy object from `resolve-policy`.
   - Bounds: the driver lane reads size, Key File count, ceremony, risk and protected paths through the same helpers admission uses, so #6018, #6019 and #6020 are followed. The express lane reads `eligibility.js`'s express bounds minus grants, blockers and PRs.
   - Precedence: driver, then express, then micro-plan.
   - Fail closed: a missing, unreadable or malformed input returns `lane: null` with a `reason` (the build then writes a plan). `reason` is a short stable code.
   - The verdict is advisory: it means eligible by bounds, not admitted. A record a lane later refuses is built by `/build`, which composes its own micro-plan or full plan.
2. A CLI verb (on an existing CLI or a new one, the builder's call) that prints the verdict for one record body plus labels.
3. Tests covering each lane, the null case, and `express-driver: off`.
4. The micro-plan gate's rule lives in code (a shared module the predicate and `micro-plan.md` both cite), with `micro-plan.md` citing it rather than restating the count, and a conformance test pins the prose's condition list to the code.
5. A parity test: with grants, blockers and PRs neutralised, the predicate's driver verdict equals the bounds portion of `evaluateAdmission` for the same record and policy.

## Acceptance Criteria

1. A record inside the driver's lane bounds with `express-driver: on` reads `lane: 'driver'` even with no `auto:build` and an open blocker.
2. A record passing the micro-plan gate reads `lane: 'micro-plan'`.
3. A record outside every lane reads `lane: null`.
4. The micro-plan rule is not restated: the function and `micro-plan.md` share one implementation or one cited source.
5. `npm test` passes.
6. A record matching more than one lane reads the first in precedence order (driver, express, micro-plan); `express-driver: split` reads like `on`; a record with a missing Key Files section or an unreadable bound reads `lane: null`.

## Build Alignment Notes

1. Beneficial: `needsNoPlan`'s `keyFiles` input is `extractKeyFileEntries(body)`'s result — `null` (no section) or `{entries: [{path, note}], unparsed}` — an extension of the existing `### Key Files` parser (`extractKeyFilesSection` is now a map over it, unchanged for its callers), so "missing", "unparseable" and "parsed to zero" stay distinguishable as the fail-closed rule needs.
2. Beneficial: the driver's lane-bound options (`laneBounds`, `eligibilityOptions`) moved from `driver/steps.js` into the leaf module `driver/lane-bounds.js` (`steps.js` imports both and re-exports `eligibilityOptions`), so the predicate reads the same helpers admission uses without loading the step table, and `express/cli.js` requires the predicate with no require cycle.
3. Beneficial: a template-placeholder `### Key Files` item (an unfilled spec-template line) counts as unparsed, so an unfilled template never reads as "zero implementation files".
4. Intended (ratified at the Review Console, build-deviation-1): a `### Key Files` note marks an entry read-only only through `read only` / `read-only`, or a `no change(s)` that ends the note or a clause (`READ_ONLY_NOTE_RE` in `micro-plan-gate.js`). `(modify — no change to callers)` and similar notes count as implementation files, so fewer records take /build's micro-plan path than under the old substring match, never more.
