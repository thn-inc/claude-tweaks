## Deliverables

1. **Lookback window.** New policy key `trust-evaluation-window-days` (integer, min 1, default 30). `trustRows` grades a cell only on closed records whose tracker `closedAt` falls inside the window. A closed record outside the window contributes to no cell, but is still scanned as a follow-up source the same way an open record is. All-time counts are not kept beside the windowed ones: the fetch limit already bounds "all-time".
2. **Rate threshold for follow-ups.** New policy key `trust-follow-up-rate-max-percent` (integer, min 0, max 100, default 30). Each row gains `followUpRecords` (distinct in-window records with at least one corrective follow-up) and `followUpRate` (`followUpRecords / total`). `clean` requires `followUpRate * 100 <= trust-follow-up-rate-max-percent` in place of `followUps === 0`. The `followUps` count stays on the row for display. Setting the key to `0` restores zero tolerance.
3. **Zero tolerance kept, now windowed, for `changesRequested` and `negativeEvidence`.** One human rejection, one discovered revert, or one correctness/ambiguous failure marker inside the window still pins the class below `clean`, and the pin lifts once the record ages out of the window.
4. **Verdict reasons.** Each row gains `mixedReasons`: an array of `'changes-requested' | 'follow-up-rate' | 'negative-evidence' | 'batch-only'`, empty unless `verdict === 'mixed'`. Gate 2's deny `reason` names the reasons together with the measured rate and the threshold.
5. **Every `trustRows` call site passes the new keys.** That covers `plugin/bin/backlog-grant-gate.js` (add both keys to its `resolvePolicyKeys` list) and `plugin/bin/lib/backlog-grant-gate/backlog-grant-gate.js`, plus the node snippets in `_shared/trust-table.md`, `backlog/trust-signal.md`, and `capture/SKILL.md`, along with the `resolve-policy.js --values` lines in `backlog/refine-mode.md` and `capture/SKILL.md` that feed them. trust.js exports one `TRUST_POLICY_KEYS` list naming all three trust keys, and each site resolves that list, so a user's override is never silently dropped at a site that passes only `trust-revert-window-days`.
6. **Docs describe the gate after the change.** `_shared/autonomy-ceiling.md` replaces "Not currently time-windowed" with the window and threshold rule, and says what `grant-origination-enabled` and `fleet-daily-grant-cap` still control: the opt-in still gates every machine grant, and the cap still bounds grants per day. `_shared/trust-table.md` replaces "Known limitation: no time window" with the rule, adds `Follow-up rate` to the render, and states the window, the threshold, and the oldest graded close's age in the render header. `_shared/policy-schema.md`'s Config Lever Index gains both keys.
7. **Removal condition recorded.** `_shared/autonomy-ceiling.md` states that the bridge is re-decided (retired or kept) when #4623 ships, and the build posts one comment on #4623 linking this record so the re-decision is visible on the record that triggers it.
8. **All-refused outcome in plain words.** `backlog/machine-grant-outlook.md`: when `eligible` is 0 and `refused` is non-empty, the `specified`-stage annotation reads `# machine grants: none possible — all {n} candidates refused ({failedKey}: {count}, ...)`. When `trust` is among the keys, it appends each refusing class with its verdict and `mixedReasons`, e.g. `producer:capture|elevated mixed (follow-up rate 33% > 30%, 2 negative)`. The existing `# machine-grant live ...` line stays for the eligible > 0 case.

## Technical Approach

All changes are in the pure trust engine and its readers. Gate order, gate 1, gate 3, gate 4, and gate 5 (`grant-gate.js`), the merge-lane breaker, and dispatch's Auto-merge gate stay as they are. Follow the `policy-key-addition` project skill for both keys (schema row, Config Lever Index row, coverage tests).

In `trustRows`: resolve the three keys through `resolveValue`. Filter `closed` by `now - closedAt <= windowDays * MS_PER_DAY` before building cells. Track distinct follow-up targets per cell in a `Set` alongside the existing `followUps` count. Compute `followUpRate`, `mixedReasons`, and the verdict from those. The `MIN_SAMPLES`/`MIN_VERDICTS` floors apply to the windowed counts unchanged.

Expected outcome, simulated 2026-11-13 against the live fetch with the defaults above: `producer:capture|low` reads `clean` (rate 25.4%, 0 negative). `producer:capture|elevated` stays `mixed` (33.3%, 2 negative). The docs-health, harness-health, and dispatch producer classes stay `insufficient-evidence` / no cell. 66 candidates would reach gate 4's grant-check, capped at 3 grants a day. The born-ready chain stays suppressed, because it reads `producer:capture|elevated`.

### Decisions

- **Window length 30 days (agent's call).** It must exceed `trust-revert-window-days` (14) or operational evidence can never land inside it. At roughly ten closed records per class per month, it is the shortest window that reaches `MIN_SAMPLES` (8). Today it changes no verdict, because the fetched history spans 23 days. It makes the window explicit instead of an accident of the fetch limit.
- **Rate on distinct records, threshold 30% (agent's call).** "Share of shipped records that drew corrective work" is the rate a human would read. Counting follow-ups instead lets one record count several times (`producer:capture|low` is 32% by count, 25.4% by record). 30% is calibrated against the 2026-11-13 measurement: it is the lowest round value that lets the low-risk capture class through while keeping `producer:capture|elevated` out. It is a policy key so the maintainer can tighten it.
- **`changesRequested` and `negativeEvidence` keep zero tolerance inside the window (agent's call).** These are known-bad outcomes (a human rejection, a revert, a correctness failure), not routine corrective filings. Keeping them at zero preserves `_shared/autonomy-ceiling.md`'s Revocation contract that one negative outcome auto-revokes a class, and the window makes that revocation recoverable. A rate for `negativeEvidence` was the alternative. It would weaken a documented safety property, and no class needs it: the class that clears has 0.
- **One verdict still drives both born-ready and born-authorized (agent's call).** A `clean` class under the new rule also earns `auto:merge-pending` eligibility through `permittedGrants`, exactly as `clean` did before. The safeguards behind it stay: grant-check, the oversight floor, merge-sensitive paths, the daily cap, the merge-lane breaker, and dispatch's Auto-merge gate. Splitting the verdict would add a mechanism that #4623 is expected to replace.
- **Retirement deferred to #4623 (agent's call).** The maintainer's answer covers "bridge now" only. This record records the removal condition (Deliverable 7) rather than deciding it.
