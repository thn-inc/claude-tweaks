# 6113: Rebuild a conflicting learned-skills PR on the integration tip during the drain

Surface: backend
Risk-flags: irreversible-side-effect

## Current State

- The learned-skills `drain` (sibling sub-issue) reports a `DIRTY` learned-skills PR as `conflicting` and leaves it open.
- The conflicts behind #6088 are two runs appending a bullet or numbered item at the same anchor of the same `.claude/skills/**` file. #6083 folded ten such PRs by hand with a 3-way merge that kept both sides where both only added lines, then fixed a duplicated numbered item and a numbering collision. #6097 and #6098 both edit `.claude/skills/skill-prose-conformance-tests/SKILL.md` today.
- #6088 dropped the human-review floor for the learned-skills PR, so a rebuild needs no reviewer.

## Deliverables

1. When `drain` meets a conflicting marker PR, it rebuilds the PR's branch: a 3-way merge of the PR's head onto the current integration tip, done through git plumbing on a temp index (never touching any worktree's own branch, index or files, as `land` does). The rebuild is one result commit whose parent is the integration tip; its message carries the union of the PR commits' run-id and entry-id trailers, in order, so no entry loses its trailer.
2. A conflict hunk where **both sides only add lines** at the same spot is resolved by keeping both: the integration side's lines first, then the PR's. The predicate: with `git merge-file --diff3`, a conflict block is a pure double-append only when its base section is empty and both its ours and theirs sections are non-empty; any other block, and any `merge-tree` conflict type other than a content conflict (modify/delete, rename), refuses. A line the PR adds that already appears verbatim among the integration side's added lines is dropped, so one lesson added twice stays once. Afterwards, within each resolved hunk, a numbered-list collision (two items with the same number, or numbering that no longer increases by one) is renumbered so the list stays consecutive. An item is a line matching `^\s*\d+[.)]\s`. Renumbering applies only when the resolved hunk ends its list (the next line is not an item at that indent); a mid-list hunk refuses with the `conflict needs a human` reason.
3. A conflict hunk where either side deletes or changes an existing line is not auto-resolved: the PR is left open and reported `leftOpen: {pr, reason: "conflict needs a human: {file}"}`, naming every conflicted file, comma-joined.
4. A successful rebuild is pushed with `git push --force-with-lease=refs/heads/learned-skills/{run-id}:{old-head}` to the PR's own branch only (never the integration branch, never a branch not named `learned-skills/*`), keeps every commit's run-id and entry-id trailers, and the PR then follows the drain's pending path (merged by a later drain once green, where green means checks on the rebuilt head SHA: a status that predates the head is pending). The push uses the session's own git credentials, not `GITHUB_TOKEN`, so CI runs on the new head. A rejected lease is `leftOpen` reason `lease-rejected` with no retry; a head ref outside `learned-skills/*` is never touched.
5. The drain's JSON gains `rebuilt:[…]`, and each rebuild or refusal is logged to `decisions.md` (`AUTO` for a rebuild, `SKIP` for a refusal) with the tag `[lever: learned-skills-auto-merge={value}]`.
6. Migration (#6088 Deliverable 3): after this ships and the installed plugin carries it (`claude plugin update`, not a stale cache), run `learned-skills-pr.js drain` on this repository, at most 3 passes each waiting out CI, until no learned-skills PR is left open except any reported `conflict needs a human`, which gets a PR comment naming the file. That drains the PRs the old never-armed path opened (five as of 2026-11-23: #6089, #6092, #6096, #6097, #6098; the last two edit the same file), so the old and new shapes do not coexist.

## Release Note

Wrap-up now repairs learned-skill update PRs that conflict because two runs added to the same spot, instead of leaving them for a person to fold by hand.

## Technical Approach

Use `git merge-tree --write-tree` against the integration tip to detect conflicts and produce the merged tree; for conflicted files, run `git merge-file` per file and post-process conflict blocks: a block whose base section is empty on both sides is a pure double-append and is unioned; any other block refuses. Build the result commit with `commit-tree` on a temp index, carrying the PR's commits' trailers in the message. Keep the algorithm in a pure function over three strings (base, ours, theirs) so it is unit-testable without git. The `git-ground-truth-test-env` project skill covers fixture git environments.

### Key Files

- `plugin/bin/lib/learned-skills/rebuild.js` — new: conflict classification, union, renumbering, plumbing commit, lease push
- `plugin/bin/lib/learned-skills/drain.js` — call the rebuild for a conflicting PR
- `plugin/bin/learned-skills-pr.js` — header contract names `rebuilt`
- `tests/bin-lib/learned-skills/rebuild.test.js` — new: pure union/renumber cases and fixture-repo cases

## Gotchas

- A union of two pure appends gives the same text the two PRs would have produced if merged one after the other without conflict, so it introduces nothing a sequential merge would not; a block with any deleted or changed line is exactly where a contradiction could hide, which is why it refuses.
- `merge-tree` needs git ≥ 2.38; on an older git the rebuild refuses with `leftOpen` reason `git-too-old` instead of falling back to a temp worktree (that would break the no-worktree rule). Confirm the CI and Windows runners' git versions at build time.
- Renumbering must stay inside the resolved hunk; never renumber a list the PR did not touch.
- Two appended bullets can still contradict each other; no step checks that. The accepted backstop is the green-CI gate, and a verbatim duplicate is the only semantic case the rebuild handles.

## Build Clarifications (architecture alignment, beneficial deviations)

- `conflicting` stays in the drain JSON for two cases the rebuild does not take: a conflict the `gh pr merge` call itself reports, and a PR that classifies conflicting again after this drain already rebuilt it once (at most one rebuild per PR per drain).
- "A mid-list hunk refuses" is applied when an item at the hunk's last run's indent follows the hunk (past blank lines and that item's deeper-indented continuation). A run closed inside the hunk by a heading, or by prose after a blank line, does not refuse when the next item restarts at `1.` (a new list); an item continuing the numbering still refuses.
- A rebuild that fails for any reason the spec does not name (a fetch, merge or plumbing error) is `leftOpen` reason `rebuild-failed` with the git error's first line as `detail`; a head that moved before the fetch is `head-changed`.
