# 5218: drive.js: a named record from admission to a green draft PR

Surface: backend

## Overview

This unit builds `drive.js`: given named records, it takes each one, one at a time and in order, from admission to a green draft PR, with a program owning every step that needs no judgment and a headless worker (the launcher from the sibling unit) used only to write the change. Design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, sections "How a record moves through it", "Eligibility", "Event lines" and "Phase 1".

The order, the escalation points and the outcome words (`pending-review`, `express-escalated`, `blocked`) are `plugin/skills/_shared/express-lane.md`'s, unchanged; the driver adds one word of its own, `refused`, for a record that never entered the lane (the lane has no word for that). Nothing merges in this unit: every successful run ends `pending-review` with the PR left in draft. Here `express-escalated` means the record left the lane before the push and an escalation is owed; this unit writes no escalation line, the settle unit does. The driver writes every log line, label and comment itself; the worker's transcript holds no harness CLI call, no `gh` call and no `git` write.

In this unit a failed step stops the run for that record, emits its event line, and leaves the claim, worktree and run directory as they are. The settle behavior for standalone runs is the next unit's.

**Complexity:** High
**Estimated tasks:** 8

## Non-Goals

- Settling a stop (escalation write, claim release, worktree removal, `bot:blocked`, comments): the settle unit. Here a stop is an event line and nothing else.
- Any merge, `gh pr ready`, or the content judgments of the merge path (Phase 2 of the design).
- Entry from `/claude-tweaks:dispatch` and queue selection (`--budget`) (Phases 3 and 5).
- Parallel records: one record at a time, in the order named.
- A prose contract for the driver under `plugin/skills/_shared/` and any test that reads skill prose. The code is the statement of record; a usage page comes with the settle unit.
- Retrying any step, other than the single transient retry `_shared/express-lane.md` step 7 allows for `gh pr create`. No step is fixed by the driver itself, and a red test run is never fixed on the lane.

## Acceptance Criteria

1. With `express-driver` resolving `off`, `drive.js #N` writes nothing (no claim, no run directory, no worktree, no file) and emits one event naming the refusal, whose final line carries outcome `refused`. A record that fails eligibility or admission does the same, and its event names every reason. A record whose fetch fails is refused the same way, with the fetch error named.
2. Over a fake runner, a happy-path record produces the calls listed in the second deliverable in exactly that order, with one record fetch (one `gh issue view` of the record, whose JSON is also the `--record-json` for `check`), and the push happens only when `git rev-parse HEAD` in the worktree equals `check`'s `head`. A different HEAD stops the record at the push step with a `stop` event and no push. A `check` envelope with no `head` or a `head` that is not a full commit sha, and a failing `git rev-parse HEAD`, also stop the record at the push step with no push: an unreadable or malformed value never passes the guard.
3. The commit is made by the driver, by explicit path, from the changed files git reports in the worktree, never from the worker's result. A worker that returns `ok` with no changed files stops the record at the commit step. A commit that fails (identity, a hook) is a `fail` at the commit step. The worker's title is normalized before it enters the message: first line only, whitespace collapsed, trailing period dropped, every `#N` reference and every closing keyword (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`, any case) removed, and an empty result stops the record at the commit step; the message is then `{title} — refs #{n}` (a test feeds a title that contains a closing keyword followed by an issue reference). The implementer's launch uses the `implementer` role, and the allow list the real `roles.js` produces for it contains no rule for `gh`, `git add`, `git commit`, `git push`, any `plugin/bin` harness CLI or any interpreter other than the test command (test over the real roles module).
4. The PR is opened as a draft (`gh pr create --draft`, with `--base` the integration branch and `--head` the record's branch) with a body composed by `compose-pr-body.js --express`, so `express-lane.js samples` counts it.
5. Every step emits one event line with the fields above to stdout. Events emitted before the run directory exists (policy read, fetch, eligibility, admission, claim) carry `run: null` and are held in memory; once the run directory is minted they are appended to `{run-dir}/driver-events.jsonl` ahead of the later ones, so from the claim step on the file holds every event of the record. A record refused before the claim writes no file, so its events reach stdout only. The final line carries the outcome word, total milliseconds with and without the CI wait, the PR number and `ci`. A test reads both sinks for a driven record and asserts they hold the same lines in the same order.
6. A red test run, a `check` verdict of `escalate`, a worker `timeout` or `fail`, and a failed claim each stop the record at that step with a `stop` or `fail` event naming it. `stop` means a gate said no (refusal, red tests, an `escalate` verdict, a HEAD mismatch, a refused scope file); `fail` means a call failed (a claim or CLI exit, a worker `fail` or `timeout`, a launch error, a commit failure). No step is retried except the single transient retry `_shared/express-lane.md` step 7 allows for `gh pr create`, and before that retry the driver looks for an open PR on the branch (`gh pr list --head {branch} --state open`) and uses it when one exists, so a call that actually succeeded never opens a second PR.
7. Outcome words on the final line, total over every stop: a refusal before the claim (policy `off`, ineligible, not admitted, unreadable record) is `refused`; a claim that is not obtained (any non-zero exit of `claim-targets.js`) or a run directory that cannot be minted is `blocked`, because no run directory exists to hold an escalation; any other stop or failure after the run directory exists and before the push is `express-escalated` (worktree creation or stamp, worker `fail` or `timeout`, no changed files, commit failure, red tests, a refused scope file, a `check` verdict of `escalate`, a HEAD mismatch, a failed push); a non-zero exit of `check`, a failed `gh pr create` (after its one retry), `hooks.js record-pr` or `set-config.js` is `blocked`, because the branch is pushed; a failed summary entry, and any CI state other than green, are `pending-review`, as are green CI. The final line's `ci` is the state word `bin/pr-checks.js` printed (`green`, `red`, `inherited-red`, `pending`, `stale`, `no-ci`, `read-failed`, `no-pr`, `gh-absent`) or `timeout` when the state was still `pending` at the wait's bound, and `null` when no PR exists. A table-driven test pins the mapping, one row per stop above.
8. No code path in this unit merges: over every test's fake runner, no recorded call contains `gh pr merge` or `gh pr ready`, and the steps module does not name them.
9. A second named record runs after the first finishes, whatever the first's outcome (fake runner: first record refused, second driven to `pending-review`, and the reverse). A record that already has leftover state from an earlier stopped run (a worktree, branch or run directory for it) is refused at the worktree step as a `fail`, outcome `express-escalated`, with the leftover named; the driver cleans up nothing in this unit, so the settle unit owns that case.
10. A malformed invocation (no record reference, a non-numeric reference) exits 2 with the usage text; `--help` exits 0 before any probe of `gh`, git or policy. Exit codes follow the Combined-2 vocabulary (`plugin/bin/link-records.js`): 0 when every named record reached a final event, whatever its outcome (outcomes are data); 1 when the policy cannot be read at all and no record was attempted; 2 for a malformed invocation or an absent `gh` or `git`. The header comment and the usage text state them.
11. `docs/plugin-structure.md` lists `drive.js`.
12. The scoped-or-full test choice follows `.claude-tweaks/verify-scope.json` in the worktree, read as a regular file only: present as a regular file runs the scoped invocation; absent runs the full invocation, and the test step's event `detail` says `full (no verify-scope.json)`; a symlink at that path, whether it resolves outside the checkout or dangles, is refused and never read, with a `stop` event naming the file and no test run. The check uses `plugin/bin/lib/path-guard`'s `lstatType`.
13. `STEPS`'s names, in order, equal the step-name constants `events.js` exports (a test pins both), and `run.js` names no step: adding a step is a table entry, never a change to the loop.
14. The two cross-spec promises #5215 assigns to this unit hold. F1: when `drive.js` is interrupted (`SIGINT`, `SIGTERM`) while a worker runs, it signals the worker through the launcher's handle before exiting, so a POSIX worker, which leads its own process group, does not outlive it (a fake-runner test), and a win32 caller passes `bin` explicitly. F2: every string the worker controls (the result's title and summary, `detail` when it carries the worker's text, each `denials[].tool_input`) is never placed in a command and is neutralized before it reaches a commit message, the PR body or an event line (a test feeds each field a closing keyword, an `@mention`, a backtick fence and a newline).

## Technical Approach

- **Order and gates are the express lane's.** Port `_shared/express-lane.md`'s steps 1 to 8 and 10 as code; step 9 (merge) is omitted by design. Escalation is possible only before the push, as there.
- **One fetch.** The record is fetched once with `gh issue view {n} --json number,title,body,labels,state`; that value feeds eligibility, admission, the worker's prompt and `check --record-json`. Blocker and open-PR facts that admission needs come from the shared helpers' own queries (`buildLinkedPRQuery`, the native `blockedBy` read) as reads in the eligibility step, not a second record fetch.
- **Policy read once per run** through `plugin/bin/lib/express/policy.js`'s seam: `express-driver`, the two ceilings, `merge-sensitive-paths`, `integration-model`, and the express diff-bound values that `check` itself reads.
- **Injected runner.** Every external call (`gh`, `git`, the `plugin/bin` CLIs, the worker) goes through `deps`; a fake runner records calls in order and serves canned results. Windows: paths and spawns follow `.claude/skills/windows-checkout-test-parity` (platform as a parameter; `windowsHide` on child processes).
- **The commit.** Changed files come from `git status --porcelain -z --untracked-files=all` in the worktree: modified, added, deleted and untracked entries, and both paths of a rename. They are staged by explicit path with `git add -- {paths}` (a deleted path is staged as a deletion), except anything under `.claude-tweaks/pipelines/`; files git ignores are never reported, so never committed. Out-of-bounds paths are not filtered here: they are committed and `express-lane.js check` rejects them, because the protected-path and Key File bounds are its job (including `.claude-tweaks/verify-scope.json`, a protected path at `plugin/bin/lib/express/eligibility.js:61`, so a worker that edits the scope file to narrow the test run is escalated by `check` before any push). The message is built per acceptance criterion 3. The commit lands before any test runs, so an escalation leaves a clean tree.
- **Worktree, branch and base.** The worktree is created with `git worktree add` (the raw-add fallback `_shared/worktree-setup.md` documents for a caller that cannot enter a worktree) on a new branch whose name contains the record number; names and location are the builder's. The integration ref used for `--integration-branch`, `--base` and `gh pr create --base` is resolved once per run per `_shared/integration-branch.md`. The post-creation catch-up that file describes runs before the worker starts.
- **The worker's result.** The driver consumes the launcher unit's envelope (`status`, `reason`, `result` with the title and summary, `usage`, `turns`, `denials`); `usage` and `turns` feed the worker step's event line, and the final line's report carries cost (from the usage block) and turns for the Phase 1 report.
- **Event line vocabulary.** `step` names are stable strings (one per step above); `status` is `ok`, `stop` or `fail`; `ms` is the step's own duration. `usage` and `denials` are present on the worker step. `model` is the worker's model name when the result reports it.
- **Run directory.** The existing run directory under the main checkout is used (`resolve-run-dir --create`, then `--run` on every CLI that takes it), anchored per `plugin/skills/_shared/pipeline-run-dir.md`. The driver is an ordinary process, so the worktree-isolation refusals a model meets writing across that boundary do not arise.
- **CI wait.** `bin/pr-checks.js --run {run-dir}` makes one read and prints one JSON line whose `state` is `red | inherited-red | pending | stale | green | no-ci | read-failed | no-pr | gh-absent` (exit 0 in every state, per its header). The driver polls it while the state is `pending` or `stale`, with a named constant bound and poll interval (the builder's values) and stops on any other state; the bound is excluded from the "without CI wait" total. The worker's wall-clock ceiling applies to the worker only. `pr-checks.js` logs its own `decisions.md` line under `--run`.
- **Coupling to the prose lane.** `plugin/bin/lib/driver/steps.js` carries a header comment naming `_shared/express-lane.md` steps 1 to 8 and 10 as the procedure it ports, and each step function names the step it ports. No test reads the prose, so an edit to the prose lane does not turn anything red; the comment is how a maintainer editing either side finds the other.
- **Exit codes.** Outcomes are data in the final event line; the codes are fixed by acceptance criterion 10.

### Data / API Surface

- `run(argv, deps)` in `plugin/bin/lib/driver/run.js`; `deps` carries the runner, `stdout`, `stderr`, clocks and the file seams.
- Event line: `{ ts, run, record, step, status, ms, model?, usage?, denials?, detail? }`; final line adds `outcome`, `msTotal`, `msWithoutCi`, `pr`, `ci`, and the Phase 1 report fields (worker cost, turns and denial count).
- Outcome words: `pending-review` | `express-escalated` | `blocked` | `refused`.
- The final event also carries the structured stop for the settle unit: `stop: { step, class, pushed, created, reason, detail, checkLogged }`, where `class` is `refused`, `claim` (the claim step or the run-directory mint failed), `pre-push`, `blocked` (every stop after the push, and a non-zero exit of `check`) or `none`; `pushed` is true from the moment the push succeeds; `created` is `{ worktree, branch }`, each true only when this run created it (so a leftover from an earlier run is never mistaken for this run's); and `checkLogged` is `check`'s `logged` value when `check` ran. A test pins the class for every row of acceptance criterion 7.

## Gotchas

- `express-lane.js check` reads the runner pass stamp and the diff bounds in the worktree, never the cwd of the process that calls it; every call that depends on the worktree passes it explicitly (`git -C`, the worktree path) and the driver's own cwd is never relied on.
- The push is conditional on HEAD equalling `check`'s `head`. The driver commits only once, before the tests, so a mismatch means something else moved the branch; treat it as a stop, not a re-run, because no step is retried.
- A tool failure after the push cannot escalate: `check` and `escalate` refuse once `run-state.json` records the PR (`_shared/express-lane.md`, Escalation). Record the PR with `hooks.js record-pr` immediately after `gh pr create` succeeds, before the later calls, so a failure after that point is correctly classified `blocked`.
- The driver adds the step 8 summary entry (`log-decision.js --status AUTO --section "/express-lane" --step "Express lane" --text-file …`, text `#{n} built on the express lane: {files}; tests {scoped|full}; PR #{pr}.`, written by the driver itself) because the design says the driver writes every log line. A non-zero exit is outcome `pending-review` with a `fail` event, as the express lane has it.
- This record's PR body uses `compose-pr-body.js --express` with the run id, summary file and record-number arguments exactly as `_shared/express-lane.md` step 7 states them; the summary is the worker's one-to-two-sentence summary, written to a file by the driver.
- The implementer receives the record body as untrusted input; the narrow rights and the diff-bounds check inside `check` are what contain it. The prompt carries the Key Files and the limits (the express diff bound, the test command) and says nothing that relies on the worker being trusted.
- A run started with no session id is the driver's normal case: `record-worktree` writes its owner block only with a session id (`plugin/bin/hooks.js:753`) and `claim-targets.js` defaults the owner to empty. Pin it with a test that runs the steps with `CLAUDE_CODE_SESSION_ID` unset in the fake environment.
- A new `plugin/bin/` CLI reading the filesystem uses `plugin/bin/lib/path-guard`'s `lstatType` for existence checks, and reads files directly with `ENOENT` caught instead of checking first (`.claude/skills/gh-api-module-pattern/cli-wrapper-contract.md`).
- ASSUMPTION — verify at build: `/claude-tweaks:tidy`'s orphan and reap rules treat a driver run with an empty owner block like any other run during the minutes a record is being driven — confirm by reading `plugin/skills/tidy/scan-procedures.md` for how it classifies a run directory and worktree with no owner block, and record the answer in the header of `run.js`.
- Named records are independent by design: nothing merges in this phase, so a later record's worktree is cut from an integration branch that lacks the earlier record's change. Two named records that touch the same Key File will conflict at merge time, which is outside this unit.
- A worker ceiling (wall-clock or spend) ends the worker before the commit step, so a ceiling stop is always a pre-push stop in this unit.
- Phase 1's done criterion is an operational check, not an acceptance criterion here: three real eligible records driven to draft PRs with green CI, each report showing cost, wall clock with and without CI wait, worker turns and denials, no harness CLI, `gh` or `git` write in any worker transcript, and `express-lane.js verify` exiting 0. It is carried by the parent record.

## Plan Review Clarifications

- Decided by the user at plan review (AC9, Reading A): AC9 stands as written. A stopped run "leaves the claim, worktree and run directory as they are", so re-driving a record whose earlier claim is still live ends `blocked` at the claim step (class `claim`; `claim-targets.js` exit 3, contested).
