# 5216: Driver lane admission: relaxed ceremony gate, grant and state checks, split rule, and the express-driver policy keys

Surface: backend

**Related:** #4591

## Overview

The pipeline driver (design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, sections "Eligibility", "Policy key" and "Ceilings") runs the express lane's gates as code, with one difference and two additions. This unit builds the admission side and nothing that runs a worker.

- **One difference in eligibility.** A record with no ceremony label is accepted by the driver lane; a record labelled `ceremony:standard` is still refused. This is an option on the existing express eligibility function. With the option absent the function's verdicts do not change, so the prose express lane is unaffected.
- **Admission, which the express gate does not do.** Dispatch's queue pull filters authorization and state before the express gate runs. A named record has no queue pull in front of it, so the driver applies those checks itself, on the record's live labels and state: it needs `auto:build`, must not be parked or blocked, must have no open blocker and no open PR. A new pure module returns `{ admitted, reasons }` and also applies the routing value.
- **Three policy keys.** `express-driver` (`off` | `split` | `on`, default `off`) plus a per-record wall-clock ceiling and a per-record spend ceiling. The ceilings are read by later units; this unit registers them.

## Acceptance Criteria

1. With the new option absent, every existing test in `tests/bin-lib/express/eligibility.test.js` passes unmodified.
2. With the option set, an otherwise-eligible record with no `ceremony:*` label is eligible. The same record labelled `ceremony:standard` is not eligible, and its reasons include `ceremony is not fast-lane`. A record with `risk:medium` and no ceremony label is not eligible with the option set (only the ceremony rule is relaxed). A record carrying a `ceremony:` label the parser does not recognise (`ceremony:fastlane`, `ceremony:Standard`) is not eligible with the option set, because `parseRecordFacets` returns `ceremony: null` for it, the same as for an absent label (probed on this checkout), so the rule must look at the raw labels to tell the two apart.
3. Admission refuses each of the following with its own reason, one reason string per case, exported as named constants in `ADMISSION_REASONS`, and each case has its own test that goes red when only that gate is removed: the record lacks `auto:build` (`record lacks auto:build`); the record is parked, by the `parked` stage label or `bot:parked` (`record is parked`); the record carries `bot:blocked` (`record is blocked`); the record has an open blocker (`record has an open blocker`); the record has an open PR (`record has an open PR`); the record's state is not open, meaning anything other than the exact value `OPEN` that `gh issue view --json state` returns (`record is not open`). A test pins the exported key set of `ADMISSION_REASONS`, so adding or removing a gate turns it red.
4. A record failing three gates yields all three reasons in one call, not the first. A record carrying both `bot:blocked` and an open blocker yields both reasons.
5. Unreadable or malformed facts fail closed, each with its own test: a `null`, `undefined` or non-array blocker list, a `null`, `undefined` or non-array open-PR list, and a missing or non-string state each yield `admitted: false` with the exported reason `blocker facts unreadable`, `open PR facts unreadable` or `record state unreadable`. An empty array of blockers or open PRs means none and does not refuse.
6. Routing: `off` refuses every record with the reason `express-driver is off`; `split` admits an even issue number and refuses an odd one with `express-driver split: issue number is odd`; `on` admits both. A routing value outside the three is refused with the template `express-driver value not recognised: {value}`, and an issue number that is missing or not an integer under `split` is refused with `express-driver split: issue number unreadable`. Tests match the constants exactly and the template by its prefix.

## Technical Approach

- **Eligibility option.** Add `allowAbsentCeremony` to the destructured `opts` in `evaluateRecordEligibility` and change only the ceremony line: with the option `true`, the rule fails unless the raw labels carry no `ceremony:*` label at all or `facets.ceremony` is `fast-lane`. Every other rule, and the reasons array's order, stay as they are. Why an absent label is acceptable here is the design's call (it relaxes the ceremony rule only; `risk:low`, `size:low`, a `type:*` label, Key Files and the shape gate still apply), not a claim that absence means assessed.
- **Admission is pure, and the helpers run in its caller.** `evaluateAdmission` takes the record's labels and state plus the verdicts the caller computed with the shared helpers (`openBlockerRefs` over the native, cross-repository and body-text blocker reads, and the open linked-PR query), and returns `{ admitted, reasons }`. The run loop (a sibling unit) does the fetching once and calls the helpers, so its blocker and state verdicts match dispatch's in both `work-links` modes; this unit's tests feed admission the helpers' real output for fixtures built in both modes, so a change to a helper's output shape turns them red. A parity test compares admission's blocker verdict with dispatch's partition helpers over the same fixture.
- **Closed rule.** The refusal list in acceptance criterion 3, plus the unreadable-fact and routing reasons in criteria 5 and 6, is the complete set of states admission knows; `admitted` is `true` only when `reasons` is empty. A state outside the list is not refused by implication. A plan review that finds another unlisted state applies this rule as a plan amendment adding that state's refusal line (adding a refusal is the only amendment it may make; removing or loosening a listed refusal is a contract change and needs its own record), not as a `needs-human` gap. A claimed record (`bot:in-progress`) is deliberately not an admission gate: the claim step that follows admission owns it and refuses a record another run holds.
- **Routing.** `off`: refuse all. `split`: admit when `number % 2 === 0`. `on`: admit all. A routing refusal is a refusal like any other, but its reasons carry the `express-driver` prefix so a caller can tell "not this half" from an ineligible record. The resolver's own fallback (an invalid value resolves to the default `off` with `invalid: true`) means a malformed policy value never reaches admission as something other than the three words, but admission still refuses a value it does not recognise. Parity of the issue number is a cheap split, not an unbiased one (numbers cluster by filing batch); the `express-driver` doc row says so.
- **Policy keys.** Follow `.claude/skills/policy-key-addition` site by site: the `POLICY_KEYS` rows, tier `advanced` (the core tier is capped at 12), the key-count pin, the doc rows in `_shared/policy-schema.md` stating what the resolver returns for unset, set and malformed input (from the code, not from intent), and the `policyOnly` decision.

### Data / API Surface

- `evaluateRecordEligibility(issue, { ..., allowAbsentCeremony })`: unchanged return shape `{ number, eligible, reasons, keyFiles }`.
- `evaluateAdmission({ number, state, labels, openBlockerRefs, openLinkedPRs, routing })` returns `{ admitted: boolean, reasons: string[] }`. `state` is the `gh` state string; `labels` is the label name list (or `gh`'s label objects, as `parseRecordFacets` accepts); `openBlockerRefs` is the string array `openBlockerRefs()` returns; `openLinkedPRs` is the array of open linked PR numbers; `routing` is the resolved `express-driver` string. `ADMISSION_REASONS` is the exported object of reason constants.
- Policy keys: `express-driver` is an `enum` with values `off`, `split`, `on`, default `off`; each ceiling is an `integer` with `min: 1`, a default at or above the design's targets and its unit (minutes, whole dollars) in its summary. The ceiling keys are named `express-driver-wall-clock-minutes` and `express-driver-spend-ceiling-dollars`. The names are pinned here, not left to the builder, because #5218 is built at the same time as this unit and reads both keys.

- All three keys are `policyOnly: true`, and each doc row says why: `.claude/skills/policy-key-addition` sets the flag for anything executed or anything that names who is trusted, the two ceilings bound autonomous spend, and `express-driver` routes records to autonomous machinery, so a run-config overlay must not raise a ceiling or switch the routing. Name all three in the `policyOnly` bullet of `_shared/policy-schema-coverage.md` (find it by that bullet's text; it is at `plugin/skills/_shared/policy-schema-coverage.md:101` today).
- Only the ceremony rule is relaxed. `risk:low`, `size:low`, a `type:*` label, one to three Key Files, no frontend surface, no protected or merge-sensitive path, spec-shaped and not `auto:merge-pending` all still apply to a record with no ceremony label.
- Do not reimplement blocker or open-PR detection. Parsing `Blocked by` lines or reading `blockedBy` here would disagree with dispatch in one of the two `work-links` modes, which is the drift `.claude/skills/blocker-surface-parity` exists to prevent.
- `split` is temporary by design: it is removed, in favour of `on` or `off`, once each arm has 20 merged records. The doc row for `express-driver` states that threshold. The two arms are the records the driver took and the records it accepted but left to the other paths because their issue number is odd. The Phase 4 parent record of this design ("Pipeline driver, Phase 4: one evidence-based reviewer and a wider lane") owns the removal: when both arms have 20 merged records it files the change that replaces `split` with `on` or `off`. Until then `split` stays; nothing in this repository needs to observe the scoreboard for that, because the count is of merged records and is read from the forge.- Over the 484 records open when the design was written, the prose gates accepted 14 and the driver gates accept 73, of which 23 carry `auto:build` (design, "Eligibility"). That is the expected effect of relaxing the ceremony rule and a figure to re-check, not to hard-code in a test.
