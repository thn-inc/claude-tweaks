# 5384: Resolve policy in-process in the shipped modules that spawn resolve-policy.js

Surface: backend
Risk-flags: none

## Overview

Four shipped modules resolve a policy value by starting `node resolve-policy.js` and parsing its stdout: the wrap-up fact pack, the phase-exit check, the dispatch prompt composer and the release tip check. Each call costs a node start (46 ms measured) in every pipeline run, and in the test suite they account for about 60 of the 79 `resolve-policy.js` processes that no test starts directly.

After #5374, `resolve-policy.js` exports a core that returns the resolved values as an object. This record moves the four modules onto it and converts the six remaining test files that spawn `resolve-policy.js` themselves.

**Complexity:** Medium
**Estimated tasks:** 7

- `plugin/bin/calibration-report.js` (#5382).
- Skill prose that runs `node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-policy.js"` from a bash fence.
- Any change to which value a key resolves to.

## Technical Approach

Each caller gets a `resolvePolicy` dep whose real value calls `require('../../resolve-policy').resolvePolicy(…)` (path adjusted per file) with `cwd: () => <the directory the caller passed as the child's cwd today>`. The caller reads `result[key].value` (or the `--values` rule: an `{error}` entry or a null value is the empty string).

The subprocess gave two things the in-process call does not: a kill timeout (`phase-exit.js` line 77, because `integration-model` can run forge detection through `gh`) and isolation from a crash. Forge detection has its own `gh-timeout-ms` bound inside `computeDerivedDefaults` (5000 ms by default, per `resolveForgeProbeTimeoutMs` in `plugin/bin/lib/policy-schema.js`). Confirm at build that the bound covers every blocking call on this path. Where it does not (a hung `git`, a slow `readFile`), `phase-exit.js`, the one caller that had the kill timeout, keeps its subprocess, and the other three accept that no bound exists outside forge detection. Say which in a comment at each call site, not only in the PR body. Wrap each call in the caller's existing `try/catch`.

Why `run(argv, deps)` and not a new `main`: see #5374's Decision Rationale.

The entry contract, set by #5374:

- The CLI exports `run(argv, deps)` and `realDeps`. `argv` is `process.argv.slice(2)`. `run` returns an integer exit code, or a Promise of one when the CLI is async.
- The script entry is the last statement of the file: `if (require.main === module) process.exitCode = run(process.argv.slice(2), realDeps);` (async: `run(…).then((code) => { process.exitCode = code; })`).
- The CLI reaches the outside world only through `deps`. Standard io keys, each present only when the CLI uses it: `stdout(text)`, `stderr(text)`, `cwd()` (returns a string), `env` (a plain object, read-only), `stdin()` (returns the whole input as a string), `homeDir()` (returns the user's home directory; real value `() => os.homedir()`). Other seams (`runner`, `now`, `mainRoot`, …) keep their names.
- Above the guarded entry, and in everything `run` calls: no `process.exitCode`, no `process.exit()`, no `process.chdir()`, no write to `process.env`.
- A relative path is resolved against `deps.cwd()`, never left to `path.resolve` or `fs`, which use the real working directory.
- Every child process is started with `cwd: deps.cwd()` and `env: deps.env`. A child started without them inherits the test runner's working directory and environment, so a `gh` or `git` stub on an injected `PATH` is skipped and the real tool runs.

## Gotchas

- The installed plugin build reads this repo's committed config with older code. The script entry of `resolve-policy.js` and its output do not change here, so an older installed caller that still spawns it keeps working.
- `facts.js` and `phase-exit.js` pass a specific directory as the child's `cwd` (the worktree, the facts root). The core must receive exactly that directory through `cwd`, or it resolves the wrong project's `policy.yml`.
- `resolve-policy.js`'s `--run` anchoring guard (`anchoredOrOutsideMessage`) refuses a worktree-local run directory. The core must apply the same guard, so a caller cannot bypass it by going in-process; `tests/resolve-policy-run-dir-anchoring.test.js` pins the refusal.
- `tests/integration-model.test.js` (12.9 s) and `tests/merge-verification.test.js` stub `gh` on `PATH`. In-process the forge-detection child must receive the injected `env`.
- `lib/policy-schema.js` keeps a forge-degrade memo with a 60 s TTL (`FORGE_DEGRADE_MEMO_TTL_MS`, line 775). Read how it is keyed before relying on a second in-process call seeing a fresh detection; pass `fresh: true` where a test needs one.
- A module that branches on the core's result imports any exit-code constant from `resolve-policy.js`; do not retype `1`.
- `policyReadTimeoutMs` (`plugin/bin/lib/phase-exit/phase-exit.js`, also used at `plugin/bin/dispatch-prompt.js:116`) exists only to size the child's kill timeout. Delete it, and its tests in `tests/bin-lib/phase-exit/phase-exit.test.js`, when its last spawn goes.
- The "today" counts come from one full-suite run on main @ 79cd5710d (2026-11-13) with a `NODE_OPTIONS=--require` preload that logs every node process. They are a floor: a test that spawns with a replaced `env` drops `NODE_OPTIONS`, so its children were not counted. Re-measure before starting.
- `node --test` runs each test file in its own process, so in-process state is shared only between the tests of one file.
- A CLI that relied on process exit to drop an open handle, timer or signal listener keeps the test file alive in-process. `run` closes what it opens.
- A test stays on a real process only when the process is its subject (a signal, a lock held across processes, a detached child, a closed stderr, `process.exit` timing). Use `spawnCli` for it and list it in the PR body.
- A test that fakes `gh` or `git` with a stub on `PATH`, or isolates the home directory with `HOME`, works in-process only when the CLI passes `deps.env` to every child it starts and reads the home directory through `deps.homeDir()`. Convert such a test by threading `env` to the child, or by injecting a fake `runner` through `deps`. If neither fits this record, leave the test on `spawnCli` and list it; never let it run with the stub silently skipped.
- Source-scan suites read `plugin/bin` files as text and pin their shape; `tests/bin-lib/exit-code-conformance.test.js` reads each file's last `require.main` block. Run the full suite before pushing, not only the converted files.
