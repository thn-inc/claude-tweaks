# 4701: Rank near-duplicate hits by shared-anchor depth so a differently titled duplicate is not buried

Origin: reflect full from wrap-up (shaping batch #4093,#4107,#4052,#4070,#4090,#4101,#4105,#4106,#4073)

Defer-reason: tangential

## Current State

`findNearDuplicates` (`plugin/bin/lib/issues/near-duplicate.js:152-199`) scores a candidate as the count of signal kinds that fired (1-3) and sorts by that score, then by issue number (:199). How many anchors a candidate shares (`sharedAnchors`) plays no part in the order. `/claude-tweaks:specify` shaping writes the hits, in that order, as a flat `**Related:**` line. `shapingRefusal` (:222-235) refuses only on title-similarity, so a duplicate with a differently worded title is never refused, and its rank is the only cue a shaper has.

Observed 2026-10-31: shaping #4093 surfaced ten hits. The true duplicate, #3508, shared six anchors (`acceptance-labeling`, `due`, `gated`, `parentGateState`, `resolved`, the `engine-verify.js` path), but it scored 1 (body-anchor-overlap only) and ranked fifth. It sat behind four score-2 hits sharing one anchor each (#4551, #4603, #4610, #4617). #4093 was shaped and stamped `ready`, and two minutes later the human closed it as a duplicate of #3508 and carried its evidence over by hand. `isStrongNearDuplicate` (:212-216) uses anchor count, but only as a ≥2 threshold, which all five of those hits clear. So it does not separate them either.

Probe: `git grep -n -F -e 'b.score - a.score || a.number - b.number' origin/main -- plugin/bin/lib/issues/near-duplicate.js` matched :199 (sort unchanged on the integration branch). An open-record search for near-duplicate ranking found no existing record.

## Deliverables

- [ ] Order `findNearDuplicates` results so that shared-anchor depth breaks score ties and outranks shallow overlap. For example, sort by `sharedAnchors.length` descending within a score, or fold the anchor count into the sort key. The `score` field stays the signal-kind count, because `shapingRefusal`'s `MIN_REFUSAL_SCORE` and `isStrongNearDuplicate` read it.
- [ ] In `/claude-tweaks:specify` shaping, call out a hit whose shared-anchor count is well above the rest (a deep-overlap candidate) in the shaping report, not only on the `**Related:**` line, so the shaper reads it before stamping `ready`.
- [ ] Add a test with the #4093/#3508 shape: one candidate with six shared anchors and one signal, and four with one anchor and two signals. Assert the six-anchor candidate ranks first, and assert it is named in the shaping report.

## Acceptance Criteria

- [ ] For a subject whose candidates are {6 anchors, score 1} and four {1 anchor, score 2}, `findNearDuplicates` returns the 6-anchor candidate first.
- [ ] The new ordering test fails with today's sort at `near-duplicate.js:199` restored.
- [ ] `shapingRefusal` and `isStrongNearDuplicate` return the same results as before for every existing test case, and `npm test` passes.

## Release Note

`/claude-tweaks:specify` now ranks likely duplicates by how much they actually overlap, so a duplicate with a differently worded title is no longer buried in the related-records list.

- Decided by the user at plan review: the call-out is surface-only ("so the shaper reads it before stamping `ready`"). Shaping proceeds and stamps `ready` as before; a deep-overlap candidate never refuses (#3141's "file and anchor overlap alone never refuse" stands).
- Decided by the user at plan review: "assert it is named in the shaping report" is met by asserting `deepOverlapHits` returns the six-anchor candidate for the #4093/#3508 fixture, plus a prose pin on the shaping-mode sentence that tells the shaper to name it. The report itself is model prose, so it has no code to assert against.
- The sort folds the anchor count into the key ("or fold the anchor count into the sort key"): `score + sharedAnchors.length`. As an intended consequence, a body-only hit with 2 anchors (key 3) outranks a title-plus-key-files hit with no anchors (key 2).
