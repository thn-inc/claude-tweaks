# 2566: reconcile: worktree reap fails with "Filename too long" on Windows and leaves the worktree prunable

Surface: infra

## Current State
After a merge, `bin/lib/reconcile/reap-merged.js` attempts to remove the run's worktree via `git worktree remove`. On Windows, a pnpm/Node monorepo worktree under `.claude/worktrees/{worktree}` with installed `node_modules` frequently has deep nested paths that exceed Windows's `MAX_PATH` limit, causing `git worktree remove` to fail with `Filename too long`. Git partially unregisters the worktree in this failure case, leaving it in a `prunable` state while the directory remains on disk. `reap-merged.js` reports this as `worktrees: [{ action: "skipped", reason: "removal-failed" }]` and leaves cleanup to a human — the observed workaround was a small ad-hoc Node script using the `\\?\` long-path prefix with `fs.rmSync`, followed by `git worktree prune` and `git branch -D`. Related: #1796 (escalate-residue's removal-failed escalation body), which currently handles this failure by escalating to a human rather than attempting the long-path fallback.

## Deliverables
1. In `bin/lib/reconcile/reap-merged.js`, when `git worktree remove` fails, add a fallback: `fs.rmSync('\\\\?\\' + path, { recursive: true, force: true, maxRetries })` (the `\\?\` long-path prefix bypasses Windows's `MAX_PATH` limit), followed by `git worktree prune`, then the branch delete step that would otherwise have run after a successful `git worktree remove`.
2. Confirm this fallback is a no-op / behaves correctly on non-Windows platforms (the `\\?\` prefix is Windows-specific; the fallback should only trigger after a genuine removal failure, and should not be reached at all on platforms where `git worktree remove` already succeeds for long paths).
3. Update #1796's removal-failed escalation body (or confirm no update needed) to reflect that a long-path fallback is now attempted before escalating to a human — the escalation should now only fire if the fallback itself also fails.

## Acceptance Criteria
- On Windows, a worktree removal that fails with `Filename too long` due to deep `node_modules` paths is retried via the `\\?\`-prefixed `fs.rmSync` fallback, and this fallback succeeds where the direct `git worktree remove` failed — verified with a reproduction fixture (a worktree containing a deeply nested path exceeding `MAX_PATH`) or, if a live Windows CI runner isn't available, a unit test that mocks `git worktree remove`'s failure and asserts the fallback's `fs.rmSync` call receives the correctly prefixed path.
- After the fallback succeeds, `git worktree prune` runs and the worktree no longer appears as `prunable` in `git worktree list`, and the branch delete step (that would run after a normal successful removal) also completes.
- `reap-merged.js`'s existing `removal-failed` escalation (per #1796) still fires when the fallback itself fails (e.g. permissions issue unrelated to path length), so a genuine unrecoverable failure is still surfaced to a human rather than silently swallowed.
- No behavior change on non-Windows platforms where `git worktree remove` already succeeds — verified by the existing `reap-merged.js` test suite continuing to pass unmodified for the success-path cases.

## Release Note

Fixed worktree cleanup failing on Windows when paths are too long.

## Technical Approach
Add the long-path fallback directly in `reap-merged.js`'s worktree-removal step, gated behind the `git worktree remove` failure branch (not gated behind `process.platform === 'win32'` alone, since the fallback should simply be attempted whenever the primary removal fails — the `\\?\` prefix is a no-op/harmless on paths that don't need it, though confirm this assumption or gate by platform if it isn't safe cross-platform). Reuse `maxRetries`/`recursive`/`force` options already established as conventions elsewhere in this codebase's filesystem-cleanup code, if any exist, rather than inventing new retry semantics.

### Key Files
- `plugin/bin/lib/reconcile/reap-merged.js` — add the long-path `fs.rmSync` fallback after a `git worktree remove` failure, followed by `git worktree prune` and the branch delete
- `plugin/bin/lib/reconcile/` (escalate-residue module, per #1796) — confirm/update the removal-failed escalation body to reflect the new fallback-before-escalate ordering

## Gotchas
- Confirm the `\\?\` long-path prefix is safe to prepend unconditionally (i.e., doesn't break `fs.rmSync` on macOS/Linux where the prefix has no meaning) before deciding whether to gate this fallback by `process.platform === 'win32'` or apply it universally.
- `git worktree prune` after a manual `fs.rmSync` removal must run correctly even though the directory was removed by Node rather than by git itself — verify prune correctly detects the now-missing directory and cleans up git's internal worktree registration.
- This is a defect specific to Windows long-path behavior; without Windows CI, verification may need to rely on a mocked/simulated failure path rather than a genuine reproduction — call this out explicitly in the PR/build notes if a live Windows repro isn't available.
