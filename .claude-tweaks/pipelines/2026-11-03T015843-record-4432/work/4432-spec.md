# 4432: dispatch: shipped-candidate exclusion treats an API-first half PR's non-closing "Refs #N" as shipping the whole record

Surface: infra

## Current State

`/claude-tweaks:dispatch`'s queue pull runs a shipped-candidate exclusion (#1984, `plugin/skills/dispatch/queue-pull-script.md:505-560`). `classifyShipped` (`plugin/bin/lib/issues/shipped-candidate.js:47`) rates a merged PR that mentions the record, merged after the record was created, as `weak`; with title-similarity or `### Key Files` coverage it becomes `strong`, and a `strong` record is dropped from `dispatch-groups.json` with a staged `staged/shipped-close-N.md` proposing `gh issue close N`. The #4314 fix skips mentions whose PR was opened before the record existed.

Observed on 6.155.0 (rule unchanged in 6.156.1): two records built API-first — PR A shipped the API half with `Refs #N` (a deliberate non-closing reference), the pipeline released the claim with a reason naming the remaining UI half, and the record stayed open with `auto:build`. The next `/claude-tweaks:dispatch #N` logged `#N excluded, shipped by merged PR #A (merged-pr-mention-after-created, title-similarity)` (the second record: `key-files-covered`), removed both records with no bypass, and staged close proposals. Approving them would close unfinished records; the only workaround was `/claude-tweaks:flow #N` directly.

What the detector sees: `fetchLinkedPRs` (`plugin/bin/lib/issues/linked-prs.js:69-72`) gives each mention only `{number, title, state, merged, mergedAt, createdAt}` — nothing about whether the reference closes the record, and nothing about the record's own claim history. A non-closing reference alone cannot be the signal: the instances the detector was built for (#1791/#1803, #1484/#1857) were merged PRs that shipped everything without a closing keyword. The distinguishing fact here is that a pipeline **released the record's claim after PR A merged** — `release-claim.js` writes an `agent-claim-release` marker comment and a `released: true` tombstone, both carrying `releasedAt` (`plugin/bin/lib/issues/claims.js:56-66`). A release after the merge means a run saw the merge and deliberately left the record open.

## Deliverables

1. Give `classifyShipped` the record's latest claim-release time (from the claims-registry tombstone `dispatch` already reads, or the latest `agent-claim-release` comment marker). A mention whose `mergedAt` is earlier than that release never rates `strong`; it rates `weak` at most, so the record stays dispatchable.
2. Feed that value from the queue pull's two `classifyShipped` call sites in `queue-pull-script.md`, via whichever read is cheapest at that point (a claim-reader read for the candidate records, or a `comments` field added to `buildLinkedPRQuery`'s batched GraphQL).
3. Log the downgrade so the exclusion decision stays auditable, e.g. `#N kept: merged PR #A predates claim release at {releasedAt} — remaining work declared`.

## Acceptance Criteria

- A record mentioned by a merged PR with title-similarity, whose claim was released after that PR's `mergedAt`, classifies `weak` (not excluded, no `shipped-close-N.md` staged).
- The same record with no release after the merge still classifies `strong`, so the #1791/#1803-style detection is unchanged.
- A release *before* the PR merged does not downgrade (it predates the PR's evidence).
- A missing or unreadable release time never downgrades and never upgrades (the prior behavior holds).
- `tests/bin-lib/issues/shipped-candidate.test.js` covers all four cases; `tests/dispatch-shipped-candidate-prose.test.js` still passes with the updated call sites.

## Release Note

Dispatch no longer treats a record as already shipped when a pipeline merged only part of it and released the record to finish the rest.

## Technical Approach

The reporter offered two signals: a non-closing reference (`Refs #N`) where a closing keyword was available, and a claim-release reason naming remaining work. The release *time* is chosen over both. The keyword alone cannot distinguish this case from the historical no-keyword ships the detector exists for. Parsing the reason text for "remaining work" is free-text judgment, while "released after the merge" is a timestamp comparison on data the plugin itself writes. Keep `classifyShipped` pure: the caller passes `opts.lastReleasedAt` (ISO or null) the same way it already passes `opts.prFiles`.

### Key Files

- `plugin/bin/lib/issues/shipped-candidate.js` — release-time downgrade rule
- `plugin/bin/lib/issues/linked-prs.js` — only if the release time is read via the batched GraphQL
- `plugin/bin/lib/issues/claims.js` — reference: release marker and tombstone shape
- `plugin/skills/dispatch/queue-pull-script.md` — pass the release time at both `classifyShipped` call sites; log the downgrade
- `tests/bin-lib/issues/shipped-candidate.test.js` — four-case coverage
- `tests/dispatch-shipped-candidate-prose.test.js` — prose pins for the call sites

## Gotchas

- Sweeps also release claims (`release-claim.js --reason ... ` from `/claude-tweaks:specify`'s drain and `/claude-tweaks:tidy`'s stale-claim backstop). A shaping-only release after a merge would also downgrade. That is the safe direction (the record stays dispatchable, and the build's own shipped-exit check, `tests/build-already-shipped-exit.test.js`, still catches a truly shipped record), but say so in the code comment.
- Compare instants, not strings: `mergedAt` and `releasedAt` are both ISO, but normalize through `Date` as the existing createdAt checks do.

## Original request

dispatch: shipped-candidate exclusion treats an API-first half PR's non-closing "Refs #N" as shipping the whole record

**Summary:** `bin/lib/issues/shipped-candidate.js`'s `classifyShipped` rated two open records `strong` (already shipped) because a merged PR mentioned each with a non-closing reference (`Refs #N` / `(refs #N)`) plus title-similarity or key-files-covered — but both PRs were the deliberate API-first half of a two-PR record whose UI half was still unbuilt.

**Kind:** Defect

**Affected component:** dispatch queue pull — shipped-candidate exclusion (#1984), `bin/lib/issues/shipped-candidate.js`, `skills/dispatch/queue-pull-script.md`

**Repro steps:**
1. A record whose Deliverables span an API route and a UI section is built API-first (the project ships the API half in one PR and the UI half in a later one): PR A implements the API half, its body states it references the record without closing it, its fixes block carries `Refs #N` (no closing keyword), and its title matches the record's title (or its changed files cover the record's `### Key Files`). PR A merges.
2. The pipeline releases the record's claim with a reason naming the remaining work, e.g. agent-claim-release `{"reason":"merged API half: PR A; UI half still to build"}`, and the record stays open with `auto:build` for the UI half.
3. Run `/claude-tweaks:dispatch #N` (or an explicit list containing it).

**Expected vs. actual:**
Expected: a merged PR that only references the record with a non-closing keyword, on a record whose own claim-release reason says work remains, is at most `weak` — the record stays dispatchable.
Actual: queue pull logs `#N excluded, shipped by merged PR #A (merged-pr-mention-after-created, title-similarity)` (second instance: `key-files-covered`), removes the record from `dispatch-groups.json` with no `#N` bypass, and stages `staged/shipped-close-N.md` proposing `gh issue close N --comment "Deliverables already shipped by #A"`. Approving that proposal would close an unfinished record. Two records hit this in one firing. The only workaround is to bypass dispatch and run `/claude-tweaks:flow #N` directly.

The #4314 fix (skip a mention whose PR was opened before the record was created) does not cover this: here the record predates the PR. Possible signals the detector could use: the mention is a non-closing reference while a closing keyword was available (`Refs`/`refs` vs `Fixes`/`Closes`), and/or the record's latest agent-claim-release reason names remaining work.

**Definition:** Clear

**Plugin version:** 6.156.1 (observed on 6.155.0; `classifyShipped`'s strong-tier rule is unchanged in 6.156.1)
