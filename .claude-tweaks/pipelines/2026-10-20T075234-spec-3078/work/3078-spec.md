# 3078: review/step3-lens-dispatch: medium+ lens dispatch has no rule for a reviewer running as a dispatched subagent, and the low-tier carve-out contradicts the dispatch prompt

**Related:** #3015, #3049, #3377, #3266, #2734, #3301, #3329, #3378, #3577, #3589, #3604, #3657, #3675

## Current State

A `/claude-tweaks:review` running inside a `/claude-tweaks:dispatch` second call (`review,polish,wrap-up`) at `review-effort: medium` had no rule for its 3a/3b/3c/3f reproduction pairs, applied the low-tier carve-out by analogy, and judged all four lenses itself — "the medium tier's two-reader correlated-misread protection was silently not provided."

This record's first decision (2026-10-15: "a FOREGROUND nested `Agent`/`Task` dispatch from a dispatched subagent is safe") was falsified by three build attempts' premise probes, so Deliverable 1 below replaces it:

- Attempts 1 and 2 (Claude Code 2.1.302; probe comments [6241606477](https://github.com/thn-inc/claude-tweaks/issues/3078#issuecomment-6241606477) and [6277950746](https://github.com/thn-inc/claude-tweaks/issues/3078#issuecomment-6277950746)): a dispatched subagent's `Agent` call always launches async. The tool result is launch metadata ("Async agent launched successfully", an `output_file`), never the child's reply, and the `Agent` tool exposes no foreground/background parameter. The child's result arrives as a `<task-notification>`: in-turn while the parent is still making tool calls (attempt 2, at both depths, during a bounded foreground poll), or as a later turn after the parent ended its turn (attempt 1, level 2).
- Attempt 3 (Claude Code 2.1.304, cloud routine sandbox; probe comment [6278773869](https://github.com/thn-inc/claude-tweaks/issues/3078#issuecomment-6278773869)): the dispatched subagent had no `Agent`/`Task` tool at all.
- Nested fan-out from a dispatched subagent does work today: the 2026-10-19 dispatch of #3377 ran its review with 12 lens agents (6 reproduction pairs) inside a dispatched second call and returned `DONE`.

Verified on origin/main (cf09383fe):

It never says how a dispatched agent keeps its turn alive while children run. `:237` ("No `Task`/Agent tool available", #2644) already says to run the step in-session as an adversarial self-review and log the fallback.
- `plugin/skills/dispatch/task-prompt.md:40-56` (item 7, Async-wait discipline) says "nothing wakes you … Never end your turn to 'wait for' a background-task or nested-agent notification", then its #2714 marker rule describes ending a turn while "a nested `Agent`-tool dispatch you launched is still pending, per each template's Foreground execution clause carve-out (#2533)". ## Deliverables

1. Decision (re-approved 2026-10-20, replacing the falsified 2026-10-15 decision): a nested `Agent` call from a dispatched subagent always launches async. A dispatched agent may fan out nested agents (lens pairs, low-tier single reads, curation judges) at every tier, but it keeps its own turn alive with bounded foreground work until every child's completion notification has arrived, and never ends its turn with a child outstanding. When no `Agent`/`Task` tool exists, or a child has not reported when the bounded wait expires, the agent judges that unit itself, logs the downgrade, and every finding from that unit enters `unconfirmed`. Rejected: extending the low-tier carve-out to every tier (drops a second reader that #3377's run shows works), and parking until a foreground form ships (leaves the contradiction live).
2. Keep-alive probe, run FIRST, before any contract text is written: from a dispatched subagent, launch one trivial child, then run the keep-alive primitive the rule will prescribe — one bounded foreground Bash call that waits for the child's completion (cap stated in the probe) without reading the child's transcript into context — and record whether the child's `<task-notification>` arrives before that call returns. Record `claude --version`, the primitive's exact command, and the raw outcome as a comment on this record, and quote it in the PR body. Stop and report BLOCKED when the build environment has no `Agent`/`Task` tool (the probe cannot validate a primitive there — build this record locally, not in a cloud routine), or when an `Agent` tool exists and the child's notification does not arrive within the bounded wait. ## Gotchas

- The keep-alive primitive is the weakest assumption. The child's reply never appears in the tool result, and the harness tells the agent not to read or tail the child's `output_file` (it is the full JSONL transcript). The probe must use a wait that does not pull that transcript into context — for example a bounded loop testing for a completion marker with `grep -q`, or a plain bounded wait — and the core section names whatever the probe proved.
- A child that reports after the bounded wait expires can still deliver its notification later, possibly after the parent's final `STATUS:` line (attempt 1 saw a later-turn delivery). The rule must say a late result is ignored once that unit was self-judged, so it never silently changes a reported verdict.
- Leave `plugin/bin/lib/hooks/subagent-stop.js` and `_shared/dispatch-waiting.md` unchanged. #3015's pending-dispatch exemption stays as the safety net for a turn that ends with a child outstanding anyway, and `dispatch-waiting.md` describes a top-level dispatcher.
- `_shared/subagent-dispatch-core.md` is composed into the review-dispatch bundle, so net growth counts against `CEILING_BYTES` in `tests/review-dispatch-composition.test.js`. Rewrite rather than append, and fold the `:237` paragraph rather than duplicating it.
- PR #3635 (#3377, open) edits `subagent-dispatch-core.md`'s Template A "Used by" line. The hunks do not overlap, but rebase onto it if it merges first.
- #3266 still carries `auto:build`. If `/claude-tweaks:dispatch` builds it before this record, its one-sentence edit lands in item 7 first — rebase and keep the sentence, then drop Deliverable 6's `Fixes #3266`.
- Cloud routine sandboxes may expose no `Agent` tool at all (attempt 3). At runtime, the fallback branch is the normal path there and the shipped rule must not treat it as an error. At build time it is a stop: the Deliverable 2 probe needs a real `Agent` tool, so build this record locally.

## Original request

review/step3-lens-dispatch: medium+ lens dispatch has no rule for a reviewer running as a dispatched subagent, and the low-tier carve-out contradicts the dispatch prompt

**Summary:** A reviewer running `/claude-tweaks:review` inside a `/claude-tweaks:dispatch` Task subagent gets contradictory guidance on whether it may dispatch reproduction-pair lens agents, and no guidance at all at `medium`+.

**Kind:** Gap

**Affected component:** skills/review/step3-lens-dispatch.md (Lens scope and dispatch), skills/dispatch task prompt (Foreground execution / Async-wait discipline)

**Use case:**
A `/claude-tweaks:dispatch` second call (`review,polish,wrap-up`) ran `/claude-tweaks:review` inside the dispatched Task subagent. The record's labels resolved `review-effort: medium`, so Step 3 called for 2-agent reproduction pairs for lenses 3b, 3c, 3a and 3f.

Two plugin texts give the dispatched reviewer opposite guidance:

- `skills/review/step3-lens-dispatch.md`'s Low-tier single-read rule says a reviewing agent that is itself a Task-tool subagent "cannot safely wait on this dispatch's own completion notification" (citing `dispatch/task-prompt.md`'s Async-wait discipline item) and must skip the Task dispatch and apply the Direct-verification override instead. That rule is scoped to `low` only; the `medium`+ reproduction-pair text has no equivalent clause.
- The dispatch task prompt itself says the stall risk "does not cover an in-turn `Agent`-tool dispatch (a lens-dispatch fan-out, a reproduction pair) whose completion notification the harness is expected to deliver back into this same ongoing turn sequence".

The reviewer had no tie-breaker. It applied the low-tier rule by analogy and judged all four lenses itself, so the medium tier's two-reader correlated-misread protection was silently not provided. The same choice recurs for wrap-up's curation-engine fan-out (3+ open rows → parallel Capable judges) and for feedback's Step 6 scrub singleton when they run inside a dispatched call.

Expected: one consistent rule for a reviewer (or wrap-up controller) running as a dispatched subagent, stated at every tier that dispatches. Either nested in-turn dispatches are safe (then drop the low-tier carve-out's premise), or they are not (then extend the carve-out to `medium`+ and say what replaces the second reader, e.g. a logged downgrade to single-read with every finding entering as `unconfirmed`).

**Definition:** Needed — two viable directions (nested in-turn dispatch is safe vs. extend the carve-out to every tier) and no stated preference.

**Cost this session:** low — resolved in one step, but no second reader confirmed the medium-tier findings.

**Plugin version:** 6.137.0
