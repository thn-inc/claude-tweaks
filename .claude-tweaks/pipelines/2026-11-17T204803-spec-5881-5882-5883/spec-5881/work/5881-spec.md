# 5881: Run the full suite on GitHub's macOS runner and add a sha-dispatchable macOS release check

Surface: infra
Risk-flags: none

## Current State

`/claude-tweaks:release` Step 3 runs `/claude-tweaks:test full` on the developer machine. It is the only macOS run before a tag (#5370), and it waits for the machine-wide suite slot (~55 min with 8 sessions queued). No CI workflow runs the suite on macOS.

A throwaway spike, draft PR #5860 (run 44134197962, closed), ran `npm test -- --full` on a standard `macos-latest` runner (Apple M1 virtual, macOS 26.7.2):

| Node | Runner wait | Suite time | Tests | Failures |
|---|---|---|---|---|
| 20 | 1 min 23 s | 608 s | 32,572 | 3 |
| 22 | 8 min 8 s | 870 s | 32,582 | 2 |

Failures:
- `tests/bin-lib/hooks/guard-rewrite.test.js` fails "every positive case is argv-identical under bash and zsh" and "drop-git-C-cwd must-decline cases: the naive drop prints a different directory under bash and zsh" on both Node versions. The bash child ran `Node.js v24.22.2`, the runner image's own Node, instead of the test's stub.
- `tests/risk-flags-cli.test.js` fails on Node 20 only, with `uncaughtException: Unable to deserialize cloned data due to invalid or unsupported version`. That is the test runner's error when a child test process runs a different Node major than its parent.

Hypothesis, not yet reproduced: on the macOS runner, a child process resolves `node` from `PATH` to the image's Node 24 rather than the setup-node binary.

This is the first piece of the release-as-promotion design (parent #5838). The release gate will dispatch a macOS check on the exact commit it ships, instead of running the suite locally.

**Related:** #5652, #5198

## Deliverables

1. Find the root cause of the three macOS-runner failures and fix each failure that reproduces on the runner, so the suite passes on a standard `macos-latest` runner under Node 20 and Node 22 without weakening any assertion. Fix the cause, for example by making a child process run the parent's own Node binary (`process.execPath`), not the symptom. The three failures may have different causes (guard-rewrite: a bash child resolving the image's Node 24; risk-flags-cli: a Node-20-only parent/child major mismatch). Reproduce first and record the diagnosed cause per test file in the PR description; if the cause is not `PATH` resolution, re-scope the fix before changing code. A failure that does not reproduce is recorded with its evidence and routed to a backlog record (#5900). For each reproduced cause, add a regression assertion that the child process runs the parent's Node, so a later `PATH` reorder fails loudly.
2. Add `.github/workflows/macos-release-check.yml`:
   - **Triggers:** `workflow_dispatch` with a required `sha` input, validated as 40 hex characters before checkout. The input reaches the job through `env:` and is validated in a first step, never interpolated into a `run:` script. On `pull_request` the job checks out the PR head and runs a Node 20 and Node 22 matrix; on `workflow_dispatch` it runs Node 22 only. Also `pull_request`, restricted to the workflow's own path, so a change to it is proven before merge.
   - **Job:** checks out exactly `sha` (`fetch-depth: 0`), runs `npm test -- --full` on `macos-latest` (a standard label, never a larger runner) with `timeout-minutes: 60`, and sets the same CI git identity and `GH_TOKEN` env as `test-impact-map.yml`.
   - **Verdict:** a `workflow_dispatch` run posts a commit status on the input `sha` (`POST /repos/{owner}/{repo}/statuses/{sha}`, context `macos-release-check`): `pending` at start, then `success`, `failure` or `error` from a final `if: always()` step. The job needs `permissions: statuses: write, contents: read` and `timeout-minutes: 60`. The release reads it with one call, named in the workflow header: `gh api repos/{owner}/{repo}/commits/{sha}/statuses --jq '[.[] | select(.context=="macos-release-check")][0].state'`. A sha that was never dispatched has no such status, and a reader must treat that as missing, never as success. `pull_request` runs post no status.
3. A proof run: dispatch the workflow on the current `main` tip after merge, and get a green verdict for that sha. A failed proof run is reopened on this record, not deferred.

**As built (architecture alignment, Beneficial):** the workflow runs as three jobs.
- `pending` (ubuntu, `statuses: write`) validates the sha and posts `pending`.
- `suite` (`macos-latest`, `contents: read`, `persist-credentials: false`) runs the suite and exposes its outcome as a job output.
- `verdict` (ubuntu, `needs: [pending, suite]`, `if: always()`, `statuses: write`) maps that outcome to `success`, `failure` or `error`.

The split means the code under test never holds the token that writes its own verdict. The permissions above are granted per job, not to one job. The header also tells readers to bound their wait and to treat an expired `pending` as `error`. It says a status appears only once the `pending` job starts, that a non-commit sha gets no status, and that a reader ties a read to its own dispatch through `target_url` or `created_at`. The read call and the status context are unchanged.

## Acceptance Criteria

- [ ] On the PR, the macOS jobs for the three previously failing tests pass under Node 20 and Node 22, and the full Ubuntu and Windows CI stays green.
- [ ] `gh workflow run macos-release-check.yml -f sha=<main tip>` runs the whole suite on exactly that sha (the job log prints `git rev-parse HEAD` equal to the input) and concludes `success`.
- [ ] The verdict for that sha is readable through the single `gh api` call named in the workflow header, and that call reports a failed run as failed and an in-progress run as pending.
- [ ] A sha that was never dispatched has no `macos-release-check` status, and a `pull_request`-triggered run posts none.
- [ ] A `sha` input that is not 40 hex characters fails before checkout, with a message naming the input.
- [ ] The workflow has no `push` trigger, and no `pull_request` trigger beyond its own path.

## Technical Approach

Reproduce first: put the spike's diagnostics into the PR run, printing `command -v node` and `node --version` inside the failing tests' child shells, before changing code. Fix where children pick their `node`. Do not skip or loosen the tests on darwin.

### Key Files

- `tests/bin-lib/hooks/guard-rewrite.test.js` — fix the bash/zsh child node resolution, or the stub PATH ordering
- `tests/risk-flags-cli.test.js` — make child processes run the parent's Node
- `tools/run-tests.js` — read; change only if the root cause is in how the runner starts child processes
- `.github/workflows/macos-release-check.yml` — new workflow (sha-dispatchable macOS full-suite check)
- `.github/workflows/test-impact-map.yml` — read only: the env and setup pattern to mirror

## Gotchas

- Standard `macos-latest` only. Larger runners are billed even on public repos; standard ones are free on this public repo, and about $0.062/min if it ever goes private.
- The macOS runner wait was 1.5–8 min in the spike; the release gate's bounded wait must allow for it (#5838's later pieces).
- The image ships its own Node 24 on `PATH`. `setup-node` prepends its own, but shells that rebuild `PATH` can reorder it.
- Never start `node --test` directly in a local scratch check. Go through `tools/run-tests.js`; a repo guard refuses the direct form.
- The workflow filename and the `macos-release-check` status context are a contract with the qualification engine and the release gate (#5886, #5887); renaming either breaks the gate.
- The `pull_request` trigger is limited to the workflow's own path, and this record's PR changes that file, so the Node 20 and 22 macOS matrix runs on the PR that carries the test fixes.
