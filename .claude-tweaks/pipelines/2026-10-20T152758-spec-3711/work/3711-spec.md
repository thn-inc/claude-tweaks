# 3711: wrap-up Dispatch-claim branch matches every human-run /flow: choose a discriminator that still routes a dispatched run correctly

Surface: backend
**Related:** #3295, #3317, #3377, #3537, #3554, #3595, #3646, #3657, #3658, #3665, #3668, #3695, #3706, #3712

## Current State

`plugin/skills/wrap-up/auto-merge-short-circuit.md`'s **Dispatch-claim branch** decides whether the current call is one of `/claude-tweaks:dispatch`'s own Task calls by checking `claim.runId == basename($PIPELINE_RUN_DIR)`. That test cannot tell the two cases apart. `/flow` claims its own targets at Step 2.8 under the same identity (`plugin/skills/flow/claim-targets.md`: "claim identity is `basename($PIPELINE_RUN_DIR)`"), so every human-run `/flow` that claimed its record matches as well. The consequences:

- **`local-merge`:** a human-run `/flow` stops with `OUTCOME: ready-to-merge` for a dispatcher that does not exist, and nothing merges. This hits `auto:merge`/matured `auto:merge-pending` records and `merge-authorization: pre-authorized` runs alike. `plugin/skills/flow/SKILL.md`'s `pre-authorize-merge` row already calls this "a pre-existing gap in wrap-up's Dispatch-claim branch".
- **`pr-first`:** the merge still happens, but the human run reports through `task-prompt.md`'s Task-call format and never sends its `PushNotification` FYI.
- **A human resuming a dispatched run:** the current prose deliberately counts this as "stands in for" a Task call. Once the dispatching session has gone, nobody is left to act on `ready-to-merge`, so the human-resume case strands in exactly the same way.

The record's three candidate signals were weighed against what the code actually stamps:

- **`run-state.json` `dispatched: true` alone.** It is permanent for the run's lifetime (`plugin/bin/hooks.js` `record-worktree --dispatch`: "only ever written true, never false"). It therefore says "this run was dispatched once", not "this call is a Task call", and keeps misrouting the human-resume case.
- **A stricter, mandatory bind.** It makes the same marker more reliable but has the same per-run problem, and it turns `dispatch/sibling-session-check.md`'s deliberate "a failed bind never blocks dispatch" posture into a hard dependency.
- **A second claim attribute written only by dispatch.** This is circular. Dispatch no longer writes the claim: `/flow` Step 2.8 writes it from inside the Task call, so `/flow` would first have to know it is dispatched.

The chosen discriminator is a per-call one that is already recorded. The same `record-worktree --dispatch` call that writes `dispatched: true` also stamps `sessionId` from `CLAUDE_CODE_SESSION_ID`. A Task-tool subagent shares its dispatching session's `CLAUDE_CODE_SESSION_ID` (measured for interactive sessions, see the Gotchas). The house already depends on that: `plugin/bin/lib/hooks/pre-tool-use.js`'s `checkDispatchConfigGate` gates a Task subagent's git writes only when `classifyOwnership` with the hook's `session_id` returns `'mine'` against that stamped `sessionId`. A human-run `/flow`, or a human resuming in a new session, has a different session id. A resume also re-stamps `sessionId` through the existing re-stamp paths.

The other direction fails safe, which the record's framing did not account for. Suppose a Task call is misclassified as human-run, for example after a failed bind under `local-merge`. It reaches the direct-merge procedure, whose first call runs `git branch --show-current` and aborts unless that returns the integration branch. A cwd-pinned Task call sees the feature branch, so the guard aborts, nothing merges, and the run parks `pending-review`. That costs a missed merge, never a wrong-checkout merge.

## Technical Approach

Treat "is this a dispatch Task call?" as a per-call question, answered by session identity plus the dispatch marker. Neither signal is enough alone: `dispatched: true` is per-run, and a matching session id alone would also match a non-dispatched run the same session started. The two fields are written in the same `record-worktree --dispatch` call, so no new writer, field, or flag is needed. The predicate lives in a pure function so it has unit coverage. The prose keeps calling it through a one-line `node -e`, the same shape the file already uses for `grant-maturation.js`.

`plugin/skills/flow/claim-targets.md` needs no change. The claim identity stays `basename($PIPELINE_RUN_DIR)` and keeps serving claim ownership and release, which is what it is for. It just stops being read as a dispatch signal.

## Gotchas

- **Session-id sharing is measured for interactive sessions only.** Memory `session-id-shared-across-subagents` records it for Task subagents of an interactive session and says to re-verify before relying on it in cloud Routines or headless runs. `checkDispatchConfigGate`'s comment cites #3225's probe from "both the dispatching session and its Task subagent", which is strong indirect evidence. Before merging, the builder confirms from a Routine-fired dispatch run's `run-state.json` and its Task-call hook payloads that the ids match. If the env var is absent in that context, the predicate returns `false`, which is the fail-safe park, not a wrong merge. The PR description reports the result either way.
- **Accepted residual: a human in the same session.** Suppose a human resumes the run in the same top-level session that dispatched it, for example by typing `/flow` there after a Task call failed. That session shares the session id, so the predicate classifies it as a Task call and it stops at `ready-to-merge`, which is today's behavior for that one case. This is narrow and visible, and the human is present to act on it. It is not fixed here.
- **Accepted residual: bind failure.** A dispatched singleton whose bind failed parks `pending-review` under `local-merge` instead of merging, because the branch guard catches it. That is the missed-merge side of the record's original trade, with no wrong-checkout merge possible.
- **Heading text is byte-pinned.** Two existing tests anchor ordering assertions on `**Dispatch-claim branch — check this before merging anything.**`. Rename those anchors in the same commit as the prose, or the suite goes red.
- **`docs/skill-graph.md` is the one place edges live** (CLAUDE.md Cross-references). Update the row's condition text there and do not restate it elsewhere.
