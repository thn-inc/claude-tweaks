# 3510: Stage ledger-backed proposals through one CLI call instead of the dispatch.md three-step prose dance

# Reflect — staged finding 1

**Category:** tangential

Origin: reflect hindsight from #3401

Defer-reason: tangential

## Current State

`plugin/skills/build/dispatch.md` line 14 carries two "append a ledger row, then stage a file, then log STAGED" procedures that an LLM controller performs by hand: the `build-deviation-{N}` staging and, since #3401, the SDD `Ruling:` carry-forward. Each is a three-step prose dance whose coupling is the ledger item number the staged file's `Ledger:` header must name — so the row is appended first, the file second, and the row's Item text is rewritten afterwards when `stage-item.js --allocate` renumbers the id.

#3401's own review found five failure-branch gaps in that prose in a single pass (run ledger `docs/plans/2026-10-17-sdd-ruling-console-ledger.md` rows 20-24: no `stage-item.js` failure branch, an unsanctioned Item-cell rewrite, De-duplication on Append swallowing a second ruling, a reverse write-back ordered before the record number existed, an empty-resolution path `finish-console` rejects). Every one of them is a step a mechanical writer would not have been able to skip. Refs #3401.

## Deliverables

A `--ledger <path>` mode on `plugin/bin/stage-item.js` (or a sibling `bin/carry-forward.js`) that, in one call: appends the ledger row through `bin/lib/wrap-up/ledger-write.js`'s table parser (never De-duplication on Append), allocates the staged id, writes the staged file with `Ledger: {path}#{item}` already filled, prints the actual path, and logs the `STAGED` line via `bin/lib/log-decision/append.js`'s `formatEntry`; on any failure after the append it strips the `(staged/…)` suffix from the row it wrote and logs the Degrade-trace `SKIP` line itself.

`dispatch.md`'s `build-deviation-{N}` and `sdd-ruling-{N}` prose each collapse to one CLI invocation plus the one-liner they pass; the hand-performed ordering, renumbering, failure, and dedupe clauses added by #3401 and its review are deleted, not kept beside the CLI.

Conformance pins in `tests/build-sdd-ledger-residue-carryforward.test.js` and the build-deviation suite point at the CLI call; a CLI test proves the failure branch leaves the row `open` without a staged suffix.

## Acceptance Criteria

`grep -c "stage-item.js" plugin/skills/build/dispatch.md` prints at least `2` and `grep -c "update the just-appended row" plugin/skills/build/dispatch.md` prints `0`.

A CLI test appends a ruling row to a fixture ledger, stages `sdd-ruling-1.md`, and asserts the staged file's `Ledger:` header names the appended item number and the row's Item cell names the path the CLI actually wrote; a second test forces the write to fail and asserts the row is `open` with no `(staged/` substring and a `SKIP … (degraded): condition:` line was logged.

`npm test` passes in full.

## Release Note

Build: SDD ruling and build-deviation carry-forwards now stage through one CLI call, so a failed staging can no longer leave a ledger row pointing at a file that was never written.

## As-built deviations (/build Common Step 4.5)

- Beneficial: the `--ledger` mode also takes `--item` (the Item text; the CLI appends the staged path) and `--label` (the noun its `STAGED`/`SKIP` log steps use), both required, plus optional `--phase` (default `build`) and `--section` (default `/build`); and it requires `--allocate`, so a rollback can only ever remove a staged file this call created exclusively. The spec named only `--ledger <path>`.
- Covered by staged `sdd-ruling-1` (not re-staged here): the call numbers the row, stages the file with `Ledger:` filled, then appends — rather than the Deliverables sentence's append-first order — so no row ever names an unwritten file; the "strip the `(staged/…)` suffix" failure branch therefore becomes "append the row `open` with no suffix".
