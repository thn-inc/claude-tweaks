# 2400: claim-targets.js: unverified-claim leak still present under --keep-going (residual of #2329)

Surface: infra

## Current State

`plugin/bin/lib/claim-targets/claim-targets.js`'s `#2329` fix (PR #2399) closes the
"unverified-claim leak" for the default all-or-abort path: `abort()` now releases a target
whose write reported `ok: true` but couldn't be confirmed by the post-write read-back
(`stopOrSkip`'s new `releaseThisIssue` flag, threaded only through the `'unverified'` call
site).

That fix does not extend to the `--keep-going` path. `stopOrSkip`'s early return —

```js
if (opts.keepGoing) { skipped.push({ issue, reason: skipReason, ...extra }); return null; }
```

— never consults `releaseThisIssue` at all. Under `--keep-going` (multi-target `/flow` runs,
`flow/claim-targets.md`), an unverified target is simply recorded in `skipped` and the loop
continues to the next target -- its own write is never released, regardless of whether it
genuinely landed. `plugin/skills/_shared/issue-claims.md`'s Post-write verification section is
honest about this scope boundary ("downgraded to a per-target skip under `--keep-going`"), and
the existing test `(m3) #2073 under --keep-going: unverified target recorded in skipped, not
claimed, exit 0` pins the current (unfixed) behavior.

Net effect: a target that hits `'unverified'` under `--keep-going` leaks identically to the
pre-#2329 behavior for the abort path -- it rides out its full TTL unreleased and invisible
(no `bot:in-progress` marker pointing at it), every time, not just when the write's own
confirmation happens to lag.

## Deliverables

- Extend `stopOrSkip`'s `--keep-going` branch to also attempt releasing the unverified target's
  own write (mirroring `abort()`'s `extraToRelease` handling), before pushing the `skipped`
  entry -- or make an explicit, documented decision that keep-going intentionally leaves this
  leaked (and say why) rather than the current silent-by-omission behavior.
- Update `issue-claims.md`'s Post-write verification section and the `(m3)` test to match
  whichever behavior is chosen.

## Acceptance Criteria

- An unverified target under `--keep-going` either gets its own write released (and this is
  covered by a new/updated test), or the doc explicitly states and justifies why it does not.
- `npm test` passes.

## Technical Approach

Mirror `abort()`'s existing `extraToRelease`/`releaseThisIssue` handling (landed by #2329/PR
#2399 for the abort path) into `stopOrSkip`'s `--keep-going` early-return branch -- same release
call, gated the same way on the `'unverified'` skip reason, just reached from the branch that
currently returns early without it. If the decision instead is to leave `--keep-going` leaking
deliberately, the Technical Approach is documentation-only: state the reasoning in
`issue-claims.md`'s Post-write verification section rather than leaving it implicit.

### Key Files

- `plugin/bin/lib/claim-targets/claim-targets.js` -- `stopOrSkip`'s `--keep-going` early return
- `plugin/skills/_shared/issue-claims.md` -- Post-write verification section, to update either way
- test file covering the `(m3)` case pinning current `--keep-going` behavior

## Gotchas
