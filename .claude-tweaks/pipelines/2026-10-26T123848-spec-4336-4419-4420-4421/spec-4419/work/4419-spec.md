# 4419: Route resolve-run-dir's adoption dead check through run-liveness and delete isDeadRunDir

Surface: infra

## Current State

`plugin/bin/lib/hooks/run-dir-resolve.js` refuses to adopt a run directory whose own bookkeeping shows it cannot be resumed. The predicate is `deadState(state)` (line 83). It returns `true` for `status: 'interrupted'`, or for `status: 'active'` with a recorded `worktree` that no longer exists on disk. Two things read it:

- `adoptionRefusal(dir)` (line 113, #4151) returns `'dead'` when `deadState` is true, after its unreadable, `release-standalone` and terminal checks. `newestMatch` (line 145) skips every candidate that `adoptionRefusal` refuses and adopts the next-newest one (#1962). This is the only production path. `docs/hooks.md` and `plugin/skills/_shared/pipeline-run-dir.md` (line 30) describe it.
- `isDeadRunDir(dir)` (line 101) is a thin exported wrapper with **no production caller**. Only `tests/hooks-run-dir-resolve.test.js` (lines 292-302: a bare mint is not dead, malformed state fails open) and `tests/bin-lib/run-liveness/index.test.js` (line 235: never throws) use it. `docs/plans/2026-10-25-release-run-dir-adoption-guard-ledger.md` row 13 records this.

#3979 originally planned to route this check through `runLiveness` (`plugin/bin/lib/run-liveness/index.js`). Red-team (2026-10-26) showed that adoptability and liveness are different questions. `deadState` refuses shapes that **cannot be resumed** (an explicit `interrupted` stamp, or a gone worktree). `runLiveness` answers whether a process still owns the run. For an `active` run, a `dead` verdict comes only from the `pid` witness (the owner process is gone, which is exactly a crash that a resuming session should adopt) or the `legacy` witness (no owner block and quiet for 72 hours, a resume after a long weekend). Refusing either would mint a fresh run directory and drop the old run's `config.yml`, staged items and claim. The maintainer ruled (2026-10-26) that adoption does **not** consult `runLiveness`.

This is sub-issue A of #3979.

## Deliverables

- [ ] `adoptionRefusal`'s outcomes are unchanged for every input. The `'dead'` reason keeps exactly `deadState`'s two preconditions. Rename `deadState` to say what it tests (for example `unresumableState`). Its header comment states that these are adoption preconditions (an adopted run needs a live status and its worktree), not a liveness verdict, and that `runLiveness` is deliberately not consulted here (crash-resume).
- [ ] Delete `isDeadRunDir` and its export.
- [ ] Move the two properties its tests pin onto `adoptionRefusal`: a bare mint (no `run-state.json`) and a malformed `run-state.json` never throw. Their reasons stay `null` and `'unreadable-run-state'` respectively, as today. Replace the `run-liveness/index.test.js` line 235 import with an equivalent `adoptionRefusal` assertion, or drop it if the run-liveness suite already pins never-throws itself.
- [ ] `docs/hooks.md`'s `newestMatch` sentences and `_shared/pipeline-run-dir.md` line 30 say "unresumable" (interrupted or worktree gone) rather than "dead", and state that liveness is not part of the adoption decision.

## Acceptance Criteria

1. `git grep -n isDeadRunDir -- plugin tests docs` returns no definition and no call (a plan-ledger mention under `docs/plans/` is fine).
2. Every existing `adoptionRefusal` and `newestMatch` test in `tests/hooks-run-dir-resolve.test.js` passes unchanged. Specifically: `interrupted` gives `'dead'`; `active` with its worktree gone gives `'dead'`; `active` with its worktree present gives `null`; and `active` with no recorded worktree gives `null`.
3. A test with an `active` run whose worktree is present and whose owner pid is gone, built with a real owner block in `run-state.json`, is adopted by `newestMatch`. This pins the crash-resume ruling.
4. `adoptionRefusal` on a bare mint returns `null`, and on malformed JSON returns `'unreadable-run-state'`. Neither throws.
5. `run-dir-resolve.js` does not require `run-liveness`.
6. `node --test tests/hooks-run-dir-resolve.test.js tests/bin-lib/run-liveness/index.test.js` passes, and `npm test` passes.

## Technical Approach

This is a rename and a deletion, with no behaviour change. Keep `adoptionRefusal`'s check order and reason strings exactly as they are. The renamed predicate stays module-private. The documentation edits replace wording only.

### Key Files

- `plugin/bin/lib/hooks/run-dir-resolve.js` — rename `deadState`, delete `isDeadRunDir` and its export, header comment on the adoption/liveness boundary
- `tests/hooks-run-dir-resolve.test.js` — `isDeadRunDir` tests move to `adoptionRefusal`; crash-resume adoption test
- `tests/bin-lib/run-liveness/index.test.js` — line 235 import of `isDeadRunDir` replaced or dropped
- `docs/hooks.md` — `newestMatch` adoption sentences
- `plugin/skills/_shared/pipeline-run-dir.md` — line 30 wording

## Gotchas

- Do not route this check through `runLiveness`. #3979's red-team showed that `dead` on an `active` run is the crash-resume or long-idle resume case, and both must stay adoptable. #4422's conformance scan allows the renamed precondition helper in this file.
- `docs/hooks.md` holds one very long line per bullet. Edit the `newestMatch` sentences in place, and don't reflow the bullet.
- `adoptionRefusal` already requires `./run-integrity` lazily, because of the load-time cycle `run-integrity` → `context` → this module. Leave that as it is.
- Expand-contract: grep `plugin/`, `tests/` and `docs/` for `isDeadRunDir` and `deadState` before deleting.
