# 4336: run-tests-isolation slot-wait test fails when the suite runs with CT_TEST_SUITE_SLOTS raised

Surface: infra

**Related:** #4333

## Current State

`tests/run-tests-isolation.test.js`'s `withSandbox` (line 393) builds each process-level test's child env from `...process.env`, then deletes only `CT_TEST_SUITE_SLOT_HELD` and `NODE_TEST_CONTEXT` (lines 412-413). The slot-count knobs `tools/run-tests.js` reads — `CT_TEST_SUITE_SLOTS` for the full-suite lane and `CT_TEST_SUBSET_SLOTS` for the subset lane (`resolveSlots`, line 129) — leak into the sandboxed runner unchanged.

`run-tests.js waits for a slot held by a live pid, naming the holder` (line 600) pre-writes `slot-0.lock` held by the test's own pid and expects the child runner to block on it. With `CT_TEST_SUITE_SLOTS=2` in the parent env the child sees two slots, takes `slot-1`, never prints the wait line, and the test times out. Reproduced 2026-10-26 on `main`:

- `CT_TEST_SUITE_SLOTS=2 node --test --test-name-pattern="waits for a slot held by a live pid" tests/run-tests-isolation.test.js` → `not ok 1`, `timed out after 60000ms waiting for the slot-wait message`
- the same command without the knob → `pass 1`

The knob is the one `run-tests.js`'s own slot-wait line tells a starved waiter to raise, so a maintainer who follows that advice turns this test red. Found in the #4170 run, whose third full verify used the knob after slot starvation.

## Deliverables

- [ ] `withSandbox` deletes `CT_TEST_SUITE_SLOTS` and `CT_TEST_SUBSET_SLOTS` from `sb.env`, next to the existing `CT_TEST_SUITE_SLOT_HELD` deletion, so every process-level test runs the child with the default slot count of 1 whatever the parent env says.
- [ ] The comment above `withSandbox` names the two slot-count knobs among the cleared variables and says why: the slot tests assume exactly one slot.

## Acceptance Criteria

1. `CT_TEST_SUITE_SLOTS=2 node --test tests/run-tests-isolation.test.js` passes.
2. `CT_TEST_SUBSET_SLOTS=2 node --test tests/run-tests-isolation.test.js` passes.
3. Reverting only the new `delete` lines makes AC 1 fail again on the slot-wait test (`timed out … waiting for the slot-wait message`), proving the fix is what turns it green.
4. `node --test tests/run-tests-isolation.test.js` with neither knob set still passes.
5. `npm test` passes.

## Technical Approach

Two `delete sb.env.…` lines beside `delete sb.env.CT_TEST_SUITE_SLOT_HELD;` in `withSandbox`, plus the comment update. Clearing the knobs in the shared sandbox helper fixes every process-level test at once, rather than pinning a value in the one test that failed, so any other process-level test that assumes a single slot gets the same protection.

### Key Files

- `tests/run-tests-isolation.test.js` — `withSandbox` clears `CT_TEST_SUITE_SLOTS`/`CT_TEST_SUBSET_SLOTS`; its header comment names them

## Gotchas

- Delete the knobs rather than setting them to `'1'`: an explicit value would mask a future change to `resolveSlots`'s default, which the default-path tests exist to pin.
- `CT_TEST_SUITE_SLOT_DIR` is set explicitly per sandbox and must stay; only the slot-count knobs are cleared.
- #4333 (FIFO slot ordering) edits the same test file. Whichever lands second rebases; the two changes don't interact.
