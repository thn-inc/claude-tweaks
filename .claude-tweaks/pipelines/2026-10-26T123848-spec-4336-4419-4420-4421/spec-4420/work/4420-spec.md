# 4420: Route checkResumeFreshness and parentLiveDetail through run-liveness via a shared blocksResume helper

Surface: infra

## Current State

Three production callers depend on a resume-safety answer, and two of the functions involved probe liveness themselves:

- `checkResumeFreshness(runDir, { sessionId, now, thresholdMs })` (`plugin/bin/lib/hooks/resume-freshness.js`, line 50) returns `{ safe, verdict }`, plus `reason` on every unsafe result and `ageMs` on `recent-commit`.
  - These verdicts are safe and return before any probe runs: `no-state`, `own-session`, `not-interrupted`, `no-worktree`, `worktree-gone`.
  - After that it runs its own probes. An in-use `lockVerdict` (line 93) gives `locked`, unsafe. Its own `git log -1` (line 98, under `thresholdMs`, default `RESUME_FRESHNESS_THRESHOLD_MS` = 10 minutes) gives `recent-commit`, unsafe.
  - A failed or empty `git log` (`failure || !stdout`), including an unborn HEAD, gives `indeterminate`, unsafe. It fails closed on purpose; the file header records the 2026-08-16 incident.
  - Otherwise it returns `stale`, safe.
  - A lock that is `unknown`/`orphaned`, or a worktree that `git worktree list` does not list, is treated as not locked and falls through to the commit probe.
- Its callers are:
  - the `check-resume-freshness` verb in `plugin/bin/hooks.js` (line 1464, prints `BLOCKED … (${result.reason})`);
  - `plugin/bin/lib/flow/preflight.js` (line 246, reports `r.verdict` and `r.reason`);
  - `parentLiveDetail` below.

  `plugin/skills/_shared/run-resume-freshness.md` documents each verdict with its remedy. Tests: `tests/hooks-resume-freshness.test.js` and `tests/flow-resume-freshness-citations.test.js`.
- `parentLiveDetail(runDir, runState, opts, deps)` (`plugin/bin/lib/flow/consolidated-pass.js`, line 58):
  - For an `interrupted` run it asks `checkResumeFreshness` and returns `interrupted run ${verdict}: ${reason}`.
  - For any other status it returns `null` early when no worktree is recorded or the worktree is missing. Otherwise it reads the recorded worktree's lock itself (`listWorktrees`, `parseWorktreeList`, `lockVerdict`, line 74).
  - It returns `worktree lock ${lock} (${entry.lockReason || 'no reason'})` for `in-use`/`unknown`, `indeterminate: could not list worktrees to check the parent lock` on a failed listing, and `null` for a worktree the listing does not contain.
  - Tests: `tests/bin-lib/flow/consolidated-pass.test.js`.

`runLiveness` (`plugin/bin/lib/run-liveness/index.js`) always asks five probes: `owner-pid`, `heartbeat`, `worktree-lock`, `last-commit` and `owner-events`. It never throws.
- Its `last-commit` probe imports `lastCommitMs` **from `resume-freshness.js`** (`run-liveness/probes.js` line 12). `lastCommitMs` returns `null` for an unborn HEAD or empty output, which the probe records as `negative` with detail `no-commits`. The comment on `lastCommitMs` says `checkResumeFreshness` is "frozen until #3979".
- Its `worktree-lock` probe (`lockInUse`, `probes.js` line 21) throws, recorded as an `error` entry, on an unknown lock, a failed listing, or an unlisted worktree. Positive detail is `in-use`, with no lock reason. The commit probe's positive detail is `recent`, with no age.
- The owner probes raise `error` entries for causes neither caller ever asked about: a missing `events.jsonl`, `owner-session-mismatch` after a re-stamp, `unreadable-run-state`, and an unparseable heartbeat.

This is sub-issue B of #3979.

## Deliverables

- [ ] Task 0, in the PR body: an equivalence table covering both functions. Write one row per run shape whose old and new decision differ, plus one row per old `indeterminate` source:
  - an unresolvable main checkout;
  - a failed `git worktree list`;
  - a failed `git log`;
  - empty `git log` output or an unborn HEAD;
  - an unparseable timestamp;
  - `parentLiveDetail`'s failed listing.

  The intentional changes listed under Gotchas each get a row.
- [ ] Move `lastCommitMs` and its helper `isUnbornHead` from `resume-freshness.js` into `run-liveness/probes.js`, so `run-liveness` no longer requires `hooks/resume-freshness`. Without this move, the migration creates a require cycle. Drop the export from `resume-freshness.js`. `probes.js` is its only importer, so there is no re-export. Move the tests that cover `lastCommitMs` with it.
- [ ] Export `blocksResume(result)` from `run-liveness`. It considers **only** the `worktree-lock` and `last-commit` evidence entries, the two questions both callers already asked, and returns true when either one is `positive` or `error`. `owner-pid`, `heartbeat` and `owner-events` entries are informational here and never block. A fresh heartbeat for up to 10 minutes after a legitimate SessionEnd must not block a resume. Maintainer ruling, 2026-10-26. (As built, /build Common Step 4.5: a result with no `evidence` array also blocks — a missing answer is never read as "no", the module's fail-closed convention.)
- [ ] `checkResumeFreshness` keeps its five pre-probe returns, in today's order. The two-call dispatch handoff relies on `not-interrupted` returning first. After those, it calls `runLiveness` and maps the two entries, checked in this order:
  1. `worktree-lock` `positive` gives `locked`.
  2. `last-commit` `positive` gives `recent-commit`, with `ageMs`.
  3. Any `error` on either entry, or `last-commit` `negative` with detail `no-commits`, gives `indeterminate`, with the entry's detail as `reason`. The `no-commits` case keeps today's fail-closed outcome for an unborn HEAD or empty log.
  4. Otherwise `stale`, safe.

  A positive always beats an error, which matches today's sequence, where `locked` returned before `git log` ran. Every existing `reason` text is kept. Delete its own lock and `git log` probes.
- [ ] Remove the `thresholdMs` option. No production caller passes it; only the `RESUME_FRESHNESS_THRESHOLD_MS` default is used. Define `RESUME_FRESHNESS_THRESHOLD_MS` from `run-liveness/constants.js`'s `LIVE_WINDOW_MS`, so the resume window and the liveness window cannot drift apart, and keep the "within the last N minutes" reason text derived from it.
- [ ] `parentLiveDetail`'s non-interrupted branch keeps its early `null` returns (no worktree recorded, or worktree missing). After those it calls `runLiveness` and `blocksResume`. It returns `worktree lock in-use` for a positive lock, `worktree recently committed to` for a positive commit, and `indeterminate: {entry detail}` for an error. It also returns `indeterminate: no-commits` when the last-commit probe finds no commit (unborn HEAD or empty log), matching `checkResumeFreshness`'s fail-closed mapping and AC 3.2. Delete its own lock probe and the `listWorktrees`/`lockVerdict` deps it no longer uses. The old `(lockReason)` suffix is dropped. The text travels as the `parent-live` verdict's detail (`consolidated-pass.js` line 129).
- [ ] End-to-end fixtures run the real `runLiveness` against a temporary run-directory tree, with and without an owner block, through `checkResumeFreshness` and `parentLiveDetail`. Existing fixtures inject `probes` stubs, so their outcomes don't depend on the host.

## Technical Approach

Make one commit per step, so each equivalence row can be bisected: the `lastCommitMs` move, then `blocksResume`, then `checkResumeFreshness`, then `parentLiveDetail`. Probes are injected through the existing `opts`/`deps` objects, using `runLiveness`'s `probes` option. Require `run-liveness` lazily inside `checkResumeFreshness` only if a load-order test shows a cycle. `run-liveness/index.js` requires `hooks/run-integrity`, so check before choosing.

## Gotchas

- Intentional changes, all toward blocking. Each gets an equivalence row and a test:
  1. In `checkResumeFreshness`, an `unknown` lock or an unlisted worktree now gives `indeterminate`, where it used to fall through to the commit probe. An `orphaned` lock is unchanged: `lockInUse` returns false for it, a clean negative.
  2. In `parentLiveDetail`, an unlisted worktree now blocks.
  3. `parentLiveDetail`'s non-interrupted branch now also blocks on a commit under 10 minutes old.
  4. In `parentLiveDetail`'s non-interrupted branch, a failed, unparseable or absent last commit now blocks (`indeterminate: …`), where the old branch never read the commit.
- ASSUMPTION — verify at build: nothing matches on the `parent-live` detail text (the lock-reason suffix is dropped). Grep `plugin/` for `parent-live` and `worktree lock` before changing the strings.
- Never let an `error` on `worktree-lock`/`last-commit` fall through to `stale`. `resume-freshness.js` fails closed on purpose.
- The two-call dispatch handoff (`build,test` then `review,polish,wrap-up`) must never trip the resume gate. Its safety rests on `not-interrupted` returning before any probe.
- `blocksResume` deliberately ignores the owner probes. Widening it later turns every missing `events.jsonl` and every just-ended session into a blocked resume. See #3979's red-team.
