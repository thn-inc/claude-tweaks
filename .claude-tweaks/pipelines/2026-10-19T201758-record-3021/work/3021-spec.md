# 3021: review: a fix's re-verify rebuilds the app under the run's still-live ephemeral server, and nothing in the fix path reads `ephemeral-server.txt`

Surface: infra

**Related:** #2677, #2776, #2882, #3001, #3003, #3004, #3013, #3014, #3060

## Current State

In a pipeline run, the ephemeral dev/prod server that QA and `/claude-tweaks:visual-review` use is started detached and recorded in `{run-dir}/ephemeral-server.txt` as `{pid} {port} {worktree-root} detached:{yes|no}` (`plugin/skills/_shared/dev-url-detection.md:135`). It stays up until `/claude-tweaks:wrap-up`'s Section D cleanup, which reads the file's *current* content under the liveness-handle rule, because a later step may have restarted the server and rewritten it (`dev-url-detection.md:171-176`).

`/claude-tweaks:review`'s fix paths rebuild the app under that live server without coordinating with it:

- `plugin/skills/review/step3-routing.md:114`: "If any findings are 'Fix now', make the changes, re-verify per `_shared/deferral-gate.md`'s Re-verification rule (`/claude-tweaks:test`)…"
- `step3-routing.md:116-120`, Parallel fix dispatch (3+ independent fixes): dispatches fix agents, then re-runs `/claude-tweaks:test`.
- `plugin/skills/review/code-mode-steps.md:327` Step 6.7 (Late Findings Routing) applies AUTO-routed design, visual and security findings through the same routing.

Neither file mentions the ephemeral server, and the fix-agent dispatch prompt has no "do not build or start servers" line. A project rule forbidding builds under a live server binds only the orchestrating session, never a fix agent the plugin dispatches.

Observed (plugin 6.136.0, `/claude-tweaks:flow` on a private Next.js 16 app): review Step 6.7 AUTO-applied four visual and design findings. The fixer's verification ran the project's e2e suite, whose `next build` rewrote `.next` in the shared worktree. Meanwhile the run's ephemeral `next start` (pid in `ephemeral-server.txt`) was still serving that directory to QA and visual review. Nothing failed loudly. The server sat on a replaced build.

## Deliverables

1. In `step3-routing.md`'s fix path, sequential and parallel alike (and therefore Step 6.7), add a step before re-verify or fix-agent dispatch: when `{run-dir}/ephemeral-server.txt` names a live server whose worktree is this checkout, stop it first.
2. After re-verify, if a later step still needs a browser (visual review, QA re-runs), restart the server through `dev-url-detection.md`'s ephemeral start. Rewrite `ephemeral-server.txt` with a plain Bash redirect under the existing liveness-handle rule, so Section D kills the current pid. When no later step needs a browser, leave the server stopped and remove the stale line so Section D does not try to kill a dead pid.
3. Add a line to the fix-agent dispatch prompt: "do not run the project's builds, test suites or servers; the dispatcher re-verifies."
4. Add one sentence to `dev-url-detection.md`'s Cleanup section: an in-pipeline step that rebuilds the served app must stop and later restart the server. Point to the review step that does this.

## Acceptance Criteria

- In a pipeline review that applies a fix and re-verifies with a suite that builds the app, no later step is served by a process running a replaced build. The server was stopped before the build and, when still needed, restarted after it with a new pid in `ephemeral-server.txt`.
- Wrap-up's Section D still kills the server that is current at end of run, with no orphan left from before the restart.
- The fix-agent prompt template carries the no-build/no-server line. A conformance test pins it together with the stop and restart step in `step3-routing.md`, and goes red against the current text.
- A standalone review (no run dir, so no `ephemeral-server.txt`) behaves exactly as today.
- `npm test` passes in full.

## Release Note

Code review's fixes no longer rebuild your app underneath the test server the pipeline is still using. The server is stopped and restarted around the rebuild.

## Technical Approach

Stop/restart is chosen over isolating the build output. Build output paths are framework-specific (`.next`, `dist`, `build`), and the plugin cannot redirect them generically without project config. The server lifecycle, by contrast, is already the plugin's own (`ephemeral-server.txt`, the liveness-handle rule, Section D). Reuse the existing ephemeral start/stop procedures from `dev-url-detection.md`; never hand-roll a kill. The fix-agent prompt line keeps verification with the dispatcher, so only one place has to coordinate with the server.

### Key Files

- `plugin/skills/review/step3-routing.md` — Fix-now re-verify (`:114`) and Parallel fix dispatch (`:116-120`) gain the stop/restart step and the fix-agent prompt line
- `plugin/skills/review/code-mode-steps.md` — Step 6.7 (`:327`) inherits it through the routing; confirm no separate re-verify path bypasses it
- `plugin/skills/_shared/dev-url-detection.md` — Cleanup section (`:171-176`) gains the rebuild-under-server sentence
- `plugin/skills/wrap-up/cleanup-procedures.md` — reference for Section D's read of the current `ephemeral-server.txt`; not modified unless the stale-line case needs handling

## Gotchas

- #3001 (ready) adds a no-suites/no-servers rule for Step 3's read-only *lens* agents. This record covers the *fix* path, where building is legitimate but uncoordinated. Keep the two prompt lines consistent in wording, and do not merge them into one rule that would forbid the dispatcher's own re-verify.
- `ephemeral-server.txt`'s worktree field must match this checkout before stopping anything. A sibling run's server on another worktree must never be killed.
- Rewriting `ephemeral-server.txt` must go through a plain Bash redirect from the main checkout's run dir (`_shared/pipeline-run-dir.md`, `[IL-127]`). A worktree-relative path would shadow it and leave Section D killing the old pid.
- A restart costs a cold start. Do it once after the whole fix batch re-verifies, not per finding.
