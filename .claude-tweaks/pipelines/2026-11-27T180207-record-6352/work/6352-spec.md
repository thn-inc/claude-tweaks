## Overview

The maintainer's attention belongs in design, and designs here have been too shallow: builds stop to ask what the design should have settled. This record adds a skill, `/claude-tweaks:design {topic or issue}`, that runs a design session with the maintainer on the top model tier and becomes the entry for anything that will be an order (a parent with parts). This record covers the session up to and including the builder check. Parts, approval and filing follow in the next record.

## Non-Goals

- Steps 8 to 10 (parts and estimate, approve, file the issues).
- Replacing `/superpowers:brainstorming` for a single small fix, which still goes straight to shaping.
- Any hub action, recommended answers on plan-review questions, or picking review lenses while shaping. Those are v7.
- Building anything from a design. The skill must not start building.

## Prerequisites

- The resolver's named exception for this skill's readers (the record this one is blocked by).
- Decided by the maintainer on 2026-11-27, after filing: this work is dispatched now, in parallel with its siblings, and its pull request merges by itself once every gate is green. An earlier line here said it was built by hand and was not for `auto:build`; that no longer holds.

## Deliverables

- [ ] A skill at `plugin/skills/design/` with a `SKILL.md` and lazy-loaded sub-files, invoked as `/claude-tweaks:design {topic or issue}`. It runs as a session with the maintainer, in the repository that holds most of the order's work.
- [ ] Everything is saved as it happens in one folder, `docs/superpowers/specs/{date}-{topic}/`, so a lost session resumes from the files: `evidence.md`, `design.md`, `storyboard.*`, `notes-round-N.md`. On start the skill reads the folder and continues at the first step whose file is missing or unfinished.
- [ ] **Model.** The session and every reader run on the top tier. If the session is on a lower model the skill says so before step 2 and the maintainer decides. Readers are resolved through the resolver's named exception; when it signals a step-down the skill stops and asks, and never lowers a tier by itself. Step 1's searchers are the one exception: they run on the fast tier.
- [ ] **Step 1, Evidence.** Fast-tier searchers look for what exists before any idea is discussed: open and closed issues, merges of the last weeks, run data, the code, earlier designs, and the repository's settings file and settings schema for a feature that is built but switched off. Nothing is proposed until this is shown. Leaves `evidence.md`, every claim with its source.
- [ ] **Step 2, Frame.** With the maintainer: the problem, why now, goals, non-goals, anti-goals, and how they will know afterwards that it was worth it (one thing to measure and for how long, or "not measurable", said plainly). Leaves the frame section of `design.md`.
- [ ] **Step 3, Storyboard.** The cheapest picture of the result, in the form its kind needs: screen sketches (through `/claude-tweaks:design-wrapper shape`), example calls with answers, sample rows before and after, a typed-out session, or a one-page local HTML picture for a system. Leaves `storyboard.*`.
- [ ] **Step 4, Perspectives.** Five fresh readers, each given only the frame and the storyboard: the person using it, the smallest version that would do, which part owns what, the token cost, how it gets introduced. Each returns notes marked serious or minor in a fixed template. The maintainer decides what to do with each note. Steps 3 and 4 repeat until a round has no serious note, at most four rounds. Leaves `notes-round-N.md`, each note with its outcome.
- [ ] **Step 5, Alternatives.** Two or three real ways to do it, with what each gives up. The maintainer chooses. Leaves the approaches section.
- [ ] **Step 6, Pre-mortem.** One fresh reader: "it is three months later and this failed; why?", with evidence for how likely each is. Each answer becomes a change to the design or a risk the maintainer accepts by name. Leaves the pre-mortem section.
- [ ] **Step 7, Builder check.** One fresh reader tries to plan from `design.md` alone and reports only what it would have to guess. Answers already in the conversation go into the document; small ones are settled and marked as the model's call; the rest go to the maintainer in one message.
- [ ] **How it asks.** Every question comes with a recommended answer and its reason. Open questions about what the maintainer wants are asked openly, one at a time. Every decision is appended to a dated list in `design.md` with who made it.
- [ ] Until the next record lands, the skill ends after step 7 by naming `/claude-tweaks:specify {design.md path}` as the next command.
- [ ] Registration: the skill's edges in `docs/skill-graph.md`; `/help`'s workflow diagrams, context flow and reference card; `README.md`; `docs/getting-started.md`; `docs/plugin-structure.md`; the dispatch-site list in `CLAUDE.md`'s Subagent Contract paragraph; and `CLAUDE.md`'s "claude-tweaks Pipeline" entry-point lines.

## Release Note

New skill `/claude-tweaks:design`: a design session that gathers evidence first, tests a cheap picture of the result against five fresh readers, and ends with a pre-mortem and a builder check.

## Technical Approach

Follow `docs/skill-authoring.md` for the skill's structure, frontmatter and interaction patterns, and read `plugin/skills/research/SKILL.md` and `plugin/skills/specify/red-team.md` as the nearest examples of reader fan-out. Each step is its own sub-file loaded when the step starts, so a resumed session loads only what it needs. The readers use a define-in-prompt note template inlined verbatim, with the contract's status line. Keep the readers' briefs short: a reader gets the frame and the storyboard, so each read is small.

## Gotchas

- The name sits beside `/claude-tweaks:design-wrapper`. Whether "design" should be renamed to avoid the clash with "design system" is an open question in the design; the frontmatter description has to tell the two apart either way (`docs/skill-authoring.md`, Frontmatter conventions).
- `CLAUDE.md` has a 150-line budget; a registration there replaces words, it does not add lines.
- A skill reference inside a step body must be the fully-qualified `/claude-tweaks:{skill}` form.
- `docs/superpowers/specs/**` runs no test suite (`.claude-tweaks/verify-scope.json`), so the design folder the skill writes is safe to commit mid-session.
- `/help`'s workflow diagrams must list every skill, and its artifact lifecycle diagram must stay in step with `README.md`'s.
- Each step's completion is a status marker the builder defines (a section heading with a status line in `design.md`, or the file itself for `evidence.md` and `storyboard.*`), and resume reads those markers; add resume tests for steps 5 to 7 and a half-written section.
- The folder's repository is the current checkout unless the maintainer names another at start; the topic slug is derived deterministically from the topic, and an existing folder for the same topic is matched before a new one is made.
- `/claude-tweaks:design-wrapper shape` output is written or copied into the skill's folder. "Creates no issue" means no issue at all in this step, and the skill does not commit.
- Each reader's literal input and output template, including the serious/minor rubric and the outcome vocabulary the refusal gate reads, are written in the skill's note-template sub-file; step 7's reader gets `design.md` without its decisions list.
- "Top tier" for the session and readers is the `frontier` profile through the resolver exception; the interim ending after step 7 is replaced by the next record and its assertions are expected to change.
