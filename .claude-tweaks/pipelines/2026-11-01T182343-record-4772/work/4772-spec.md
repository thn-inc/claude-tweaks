# 4772: Settle refused review-followup- proposals in the open-items ledger

Surface: infra

**Related:** #4439, #4337, #3902, #4792

## Current State

`plugin/skills/wrap-up/refused-proposals.md`'s "## Ledger origin" reopens a refused proposal's ledger item (status back to `open`, note `proposal refused — no defer reason`) and deletes the staged file, but only "when the refused proposal came from a ledger item (`staged/ledger-record-*.md`)". `/review` also stages record proposals: `plugin/skills/review/step3-routing.md` ("Staging a record proposal — a confirmed finding with no patch") writes `staged/review-followup-{n}.md` and writes the finding's open-items ledger row `deferred`, its Resolution naming that staged path, "the way `_shared/ledger-format.md`'s `ledger-record-*` Defer records its staged path". When the Review Console refuses that proposal (no valid `Defer-reason:`), nothing touches the row. It keeps a terminal `deferred` status whose Resolution names a `staged/…` file that nothing will file, and `pack.js`'s `parseLedger` counts it as a complete deferral, because the check reads the Resolution text and never whether the file exists. The staged file dies with the run dir at `close-run`.

`plugin/skills/_shared/ledger-format.md`'s "Resolution-text requirements" says "Terminal statuses are final — a wrong fix gets a new item, never a reopen", and `plugin/skills/ledger/SKILL.md`'s Anti-Patterns row "Reopening resolved items" says the same. The existing `ledger-record-*` reopen already contradicts both, and neither file mentions it.

**Decision (2026-11-01, brainstorming on this record):** Reading A, generalized. A `deferred` row whose staged record proposal the console refuses never completed its deferral, so the refusal returns it to `open`. That is a named exception to "never a reopen", stated once in `ledger-format.md`. The trigger is the row's Resolution naming the refused staged path, so no list of filename prefixes is involved. That covers `ledger-record-*` and `review-followup-*` today, plus any future record-proposal producer that records its staged path the same way. Reading B was rejected. Turning a complete deferral into an incomplete one by rewriting its Resolution moves a terminal row back to blocking, which is a reopen under another name. Adding a new `open` item leaves the old row pointing at a dead path.

## Deliverables

1. `refused-proposals.md`'s "## Ledger origin" keys on the ledger row whose Resolution names the refused proposal's staged path (`staged/{name}`), not on the `ledger-record-*` filename. A matching row gets the existing treatment: status back to `open` with note `proposal refused — no defer reason`, and the staged file deleted, since the ledger item is the durable trace. In a multi-spec run, the matching row is in the ledger of the run dir whose `staged/` holds the item. A proposal no ledger row names keeps the existing no-ledger-origin branch: it stays staged and dies with the run dir. The `--dry-run` preview sentence covers the widened case unchanged.
2. `_shared/ledger-format.md`'s "Resolution-text requirements" states the exception right after "Terminal statuses are final — a wrong fix gets a new item, never a reopen". A `deferred` row whose Resolution names a staged record proposal that the Review Console refuses returns to `open`, because the deferral never completed, and the sentence cites `wrap-up/refused-proposals.md` for the procedure. This is the one canonical statement, and `refused-proposals.md` points at it rather than restating the rationale.
3. `plugin/skills/ledger/SKILL.md`'s Anti-Patterns row "Reopening resolved items" names the exception by pointing at `_shared/ledger-format.md`'s Resolution-text requirements, so the three files state one consistent rule.
4. A conformance test in `tests/deferral-gate-conformance.test.js`, next to the existing #622 `refused-proposals.md` tests, pins the rule.

## Gotchas

- **Timing, which this record does not change.** The refusal runs at Review Console step 7, after the ledger resolve gate. A reopened row does not block the current run. `review-console.md` step 13 sees the `open` row and leaves the ledger file in place with one `SKIP` line, and the row comes back only when a later resolve reads that ledger. The existing `ledger-record-*` reopen already behaves this way, and this record only extends the same treatment.
- **Unattended consoles.** `console-resolve.js` resolves a refused row as `refused`, and `bin/lib/console/residue.js`'s `UNRESOLVED_RESOLUTIONS` is exactly `pending`/`keep-staged`. So a refused proposal never appears in `console-residue.js` or the session-start notice. That is a separate surfacing gap, outside this record's Deliverables.
- **#4439 interaction.** #4439, a sanctioned `ledger-row` settle CLI (not yet built; PR #4535 closed unmerged), decided at plan review that settling a terminal row exits 1, with the incomplete deferral as its one exception. A refused proposal's row is a complete deferral when the console refuses it, so that guard would block this reopen. Whichever of the two builds second must make #4439's terminal-row guard honor the exception defined here in `ledger-format.md`. Read the exception from that file and don't fork it.
- The literal note text `proposal refused — no defer reason` stays byte-identical. Readers may grep it.
- Multi-spec consoles (`flow/multispec-review-console.md` step 2) cite `refused-proposals.md` and inherit the change. The per-spec ledger rule in Deliverable 1 is what keeps the right row reopened.

## Plan Review Clarifications

- Decided by the user at plan review: the refusal reopens the matching row in the run's active ledger (`_shared/ledger-format.md`'s resolution rule; in a multi-spec run, the one ledger shared by every spec). In a multi-spec run, a staged path written into a ledger Resolution is spec-qualified, `spec-{N}/staged/{name}`, because each spec numbers its own `staged/` slots. `_shared/ledger-format.md`'s Resolution-text requirements state this once, and `review/step3-routing.md`'s `review-followup-` ledger write points at it. This replaces Deliverable 1's "the matching row is in the ledger of the run dir whose `staged/` holds the item", which named a ledger that a sequential multi-spec run does not have (`flow/multi-spec.md`: "one ledger for the whole run, at the run-level scope … never a per-spec `spec-{N}/` dir").
- Decided by the user at plan review: only a `deferred` row reopens. `refused-proposals.md`'s Ledger origin condition names `deferred`, matching `_shared/ledger-format.md`'s exception ("a `deferred` row whose Resolution names a staged record proposal … returns to `open`"). A row in any other status, such as an `acknowledged` row whose staged proposal is refused, is left alone.

## Build Alignment

- Beneficial (Common Step 4.5): to keep "one consistent rule" (Deliverable 2), the build also aligned the surrounding text that the widened reopen made wrong. `refused-proposals.md` now gives a ledger-origin variant of the `REFUSED` log line (`; ledger row reopened, staged file removed.`), names the reopened ledger row as a ledger-origin item's way out, and its `--dry-run` sentence covers the staged-file deletion. `_shared/ledger-format.md`'s Defer/Keep bullets now carry the spec-qualified-path pointer, so no bullet tells a multi-spec writer to record a bare `staged/ledger-record-{slug}.md`.
