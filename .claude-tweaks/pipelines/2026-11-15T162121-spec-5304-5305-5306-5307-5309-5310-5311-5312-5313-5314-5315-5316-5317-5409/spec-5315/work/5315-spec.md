# 5315: Queue pull: one queue record with string labels crashes eligibility and blocks every other candidate

Verified-as-of: 8925c9a79d7c0081b17bf73288a679d897948d01

Origin: ledger resolve gate

Defer-reason: blocked-dependency

## Current State

A queue record whose `labels` is a string instead of an array crashes the eligibility step, which stops the whole pull, so every clean candidate in the same queue is never dispatchable (#9001 in #5227's SMalformed fixture).

Blocked by #5230 — fix this in `plugin/bin/lib/dispatch/queue-pull.js` once /claude-tweaks:dispatch runs the queue-pull CLI. Until then the module reproduces the fence on purpose (#5227's parity contract), so a module-only fix would break parity; if the fence (`plugin/skills/dispatch/queue-pull-script.md`) has not been removed by #5231 when this lands, fix both and keep the parity row.

## Deliverables

- [ ] A record with malformed `labels` is excluded on its own (with a Warning naming it), and the rest of the queue is evaluated normally.

## Acceptance Criteria

1. In the SMalformed fixture, #9001 is eligible and the malformed record is excluded with a Warning.

**Decision** (plan review, 2026-11-17): Question 1, Reading A with the existing reason — the skipped record gets a `dispatch-exclusions.json` entry beside its Warning, reusing reason `malformed-blocker` with cause `its labels are not an array` (the entry `unlanded-blockers.js` already writes for this condition); no new exclusion reason is added. Question 2 — a pull that skipped a record for non-array `labels` does not write the queue-order cache, the same way a pull with a failed native-blockers read (#5309), a failed dependency view (#5311) or a failed dependency-freshness search (#5310) does not; every pull over such a queue therefore recomputes and prints the Warning until the record is fixed. The skipped numbers are not stored in the cache blob and no Warning is replayed on a hit.
