# 3393: claims: extract one chained claim-reader shared by specify near-dup refusal and dispatch neighbour pass

Origin: reflect hindsight from #3278

Defer-reason: tangential

## Current State

Two shipped heredocs build the same chained claim reader by hand. They resolve the repo slug with `gh repo view` inside an empty catch, chain the git tip from the first read, and call `claim-store.js`'s `readClaimBlob`. The two copies are `plugin/skills/specify/shaping-mode.md` (near-duplicate refusal) and `plugin/skills/dispatch/queue-pull-script.md` (neighbour-in-flight pass, #3278). #3278's review found that a null slug with a failed git read sends the contents-API read to `repos/null/...`, whose 404 maps to `absent`. A claimed record then reads as unclaimed. The dispatch copy now reports that case as a read failure (`repo-slug-unresolved`). The shaping-mode copy still treats it as absent.

## Deliverables

1. One exported helper in `plugin/bin/lib/issues/claim-store.js` that resolves the slug, chains the git tip, and returns `{content}` or `{failure}` per record, reporting an unresolved slug on the contents-API path as a failure.
2. Both heredocs call the helper instead of hand-building the reader.
3. Unit tests for the helper covering git hit, contents-API hit, 404 absent, unresolved slug, and transport failure.

## Acceptance Criteria

- AC1: With an unresolved slug and a failing git read, both callers treat the record as unreadable, never as absent.
- AC2: The near-duplicate refusal and the neighbour pass produce the same results as today on the gh-present happy path.
