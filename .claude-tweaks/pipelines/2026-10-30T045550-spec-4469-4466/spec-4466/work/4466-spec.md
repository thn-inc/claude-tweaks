# 4466: Below-floor decomposition parents are never closed: the exceeds:false branch says "closes cleanly" but no step closes them

**Related:** #3508, #367

Origin: /claude-tweaks:tidy close-out 2026-10-27 (run 2026-10-27T055458-tidy-standalone)

Defer-reason: tangential

## Current State

`wrap-up/verification-brief-parent-gate.md` says that on `exceeds: false` "the parent closes cleanly: no demo:pending, no brief". Nothing performs that close, though: `/claude-tweaks:demo`'s Approve action is the only place a parent is closed ("nothing else in the system ever closes a parent"), and a below-floor parent never gets a demo gate. Tidy's `parent-gate` scope (`_shared/github-pr-scan-acceptance.md`) also filters below-floor parents out before emitting, so no backstop surfaces them.

## Deliverables

Approach: When the parent gate evaluates `due` with `exceeds: false`, close the parent **only after the last sub-issue has actually closed** — at a post-merge step (`/claude-tweaks:dispatch`'s close-out step 3, or a post-merge hook on the wrap-up merge path), never at the pre-merge mid-close callers (wrap-up Phase 4, wrap-up's auto-merge short-circuit, dispatch's group auto-merge gate), which count the in-run sub-issue as closed before its merge lands. The close posts a comment listing each sub-issue with its closing PR reference. Tidy's `parent-gate` scope surfaces any already-stranded below-floor parent (every sub-issue closed, parent still open) as a Close row instead of filtering it out, as the backstop for anything the post-merge step misses. Nothing ever needs reopening, because the parent is never closed ahead of a merge.

1. Close the parent on the exceeds:false branch, post-merge, when every sub-issue is closed (`github-issues`: comment then `gh issue close --reason completed`; `local-files`: `closeRecord`).
2. The closing comment lists each sub-issue as `- #{n} {title} — closed by PR #{pr}`, read from `closedByPullRequestsReferences`; a sub-issue closed without a PR is listed without the PR suffix. No merge SHAs (plan-review decision, 2026-10-30).
3. Tidy's `parent-gate` scope emits a below-floor parent whose sub-issues are all closed as a Close row (the backstop), instead of filtering it out.
4. Exclude decomposition parents from tidy's `acceptance-gap` scope, so an auto-closed below-floor parent is not flagged for `/claude-tweaks:demo`.
5. The close is idempotent: a parent already closed (with or without the listing comment) is not re-closed and gets no duplicate comment.
6. Update the engine-verify tests and the journey doc that pin the old below-floor `skip` outcome.

## Acceptance Criteria

- A decomposition whose last sub-issue closes below the oversight floor leaves its parent closed, with a comment listing the sub-issues and each one's closing PR reference.
- The parent is closed only after the last sub-issue's merge has landed; a merge that never lands leaves the parent open.
- A below-floor parent left open with every sub-issue closed appears as a Close row in tidy's `parent-gate` scope.
- An auto-closed below-floor parent does not appear in tidy's `acceptance-gap` scope.
- Running the close twice on the same parent posts one comment and one close.

## As-Built Notes (build Common Step 4.5, Beneficial deviations)

- **Post-merge close site:** the Approach names "close-out step 3, or a post-merge hook on the wrap-up merge path". As built it is one shared step, `_shared/pr-first-merge-post-merge.md`'s `### Step 4.0b: Close below-floor parents (#4466)`, run by all six merge paths: dispatch close-out step 7, wrap-up merge-mode step 3, `dispatch/settle-and-merge.md`, `wrap-up/auto-merge-short-circuit.md`, `flow/worktree-merge.md` and `_shared/local-merge-auto-finish.md`. It is a no-op unless the integration branch is the repo's default branch, because GitHub closes `Fixes #N` only there. An armed PR that GitHub merges later is recovered by tidy's backstop, as this spec's Approach provides.
- **Contract exception:** `_shared/auto-mode-contract.md`'s never-reversible list now names Step 4.0b's below-floor close as an exception with a restore contract: a human runs `gh issue reopen`. `_shared/issue-claims.md` points at that one exception. Tidy's parent-side close stays staged, because the exception covers only Step 4.0b.
- **Safety skips:** Step 4.0b skips a parent carrying a `needs:*` label (Worklist rule). It also skips a parent with a sub-issue that Step 4.0 left in `failed[]` or `pendingClose[]`. These are records Step 4.0 handled whose live state may still read `CLOSED`.
- **Closing PR reference:** for a sub-issue this merge closes, the listing uses the merging PR (`$MERGING_PR`) first, because `closedByPullRequestsReferences` carries no merged state and can list an abandoned PR. Other sub-issues use the last reference.
