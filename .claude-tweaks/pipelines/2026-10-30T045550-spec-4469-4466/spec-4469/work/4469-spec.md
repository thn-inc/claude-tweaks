# 4469: tidy acceptance-gap and parent-gate scans: filter closed records server-side instead of fetching every closed issue up to backlog-fetch-limit

**Related:** #2217

Origin: /claude-tweaks:tidy close-out 2026-10-27 (run 2026-10-27T055458-tidy-standalone)

Defer-reason: tangential

## Current State

`_shared/github-pr-scan-acceptance.md` fetches every closed issue (`gh issue list --state closed --limit backlog-fetch-limit`) and filters for acceptance disposition and the oversight floor client-side. This repo has more than 4400 issues, so the fetch hits the 1000 cap on every tidy run. The scan then warns that `[acceptance-gap]` and `[parent-gate]` results may be incomplete (past the cap, sub-issues default to OPEN, so parents can read as incomplete). That warning appeared again on 2026-10-27. #2217 made the truncation loud but did not remove it.

## Deliverables

Approach: Query closed records already narrowed server-side on date, disposition and reason, for example `gh issue list --state closed --search "-label:demo:approved -label:demo:changes-requested reason:completed"`, then apply the existing client-side checks to that smaller set. **The oversight floor stays client-side**: `exceedsOversightFloor` passes a record meeting either the risk or the size axis and fails closed on unscored records, which negated `-label:` search qualifiers cannot express — the example query above is illustrative, not a requirement to encode the floor (a live probe returned 743 rows against the 1000 limit). Keep the truncation warning for the narrowed fetch. GitHub search returns at most 1000 results whatever `--limit` says, so every searched or label-filtered fetch compares against `min(backlog-fetch-limit, 1000)`.

1. Replace the unfiltered closed-record fetch with a server-side filtered query for records lacking an acceptance disposition; the oversight-floor check stays client-side.
2. Under `work-links: native`, narrow the parent-gate state map (`gh issue list --state all --json number,state,labels`) to `--search "has:parent-issue"` (a live probe returned 254 rows, including every sub-issue of the open parents). Other `work-links` modes keep the current fetch.
3. Every searched or label-filtered fetch's truncation warning compares the row count against `min(backlog-fetch-limit, 1000)`.

## Acceptance Criteria

- On this repo a tidy run's acceptance-gap fetch returns fewer rows than backlog-fetch-limit and reports no truncation warning.
- Under `work-links: native`, the parent-gate state-map fetch on this repo reports no truncation warning.
- With `backlog-fetch-limit` above 1000, a searched fetch returning 1000 rows still reports its truncation warning.

## Release Note

Tidy's acceptance checks now cover every closed record without hitting the fetch limit.
