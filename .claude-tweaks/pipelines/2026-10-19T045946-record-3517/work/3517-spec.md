## Current State

The post-merge `windows-regression` workflow (run 39103544055, on `windows-latest`) flagged `tests/dispatch-neighbour-in-flight-mcp.test.js` as newly failing after PR #3441 merged as `c65b3fdbb` (#3392's MCP-transport branch for dispatch's neighbour-in-flight pass). That merge added the file, so it has no earlier Windows baseline. The run's `verify-report` artifact lists it as the only `attributable` file. The other 102 files failing at head were already failing at base `2514e406c`.

The issue excerpt quotes one failure. The run's `tests` log shows four of the file's six tests failing, all with the same assertion:

- `AC1.1: the MCP claim-target snippet prints [9] …` (line 81): `heredoc #0 has no NODE_EVAL_EOF terminator`
- `AC2.1: a stale label with no live claim …` (line 91): `heredoc #1 has no NODE_EVAL_EOF terminator`
- `AC3.1: a failed MCP claim read prints the AUTO line …` (line 99): `heredoc #1 has no NODE_EVAL_EOF terminator`
- `AC3.1: a failed MCP pool list is documented to write [] …` (line 109): `heredoc #0 has no NODE_EVAL_EOF terminator`

The two passing tests (lines 118 and 132) only call `includes` on single-line tokens.

Root cause, checked against the file at `origin/main` `7852fd8bf` (it has not changed since `c65b3fdbb`):

- Lines 18-19 read `plugin/skills/dispatch/mcp-transport.md` and `plugin/skills/dispatch/queue-pull-script.md` with raw `fs.readFileSync(..., 'utf8')`. This repo's `.gitattributes` pins only `tools/upstream-drift/fixtures/**`. A Windows checkout with `core.autocrlf=true` therefore reads both files with `\r\n` line endings.
- `snippet(index)` (lines 33-45) finds a heredoc's end with `text.indexOf('\n' + END, found)`, where `END = 'NODE_EVAL_EOF\n'` (line 23). On CRLF text the terminator line is `\r\nNODE_EVAL_EOF\r\n`, so the search returns -1 and line 43's `assert.notStrictEqual(close, -1, …)` throws. That is the reported error.
- Reproduced on macOS from an `origin/main` tree export. The file passes 6/6 as checked out. After converting the two markdown inputs to CRLF it fails exactly the four tests above, with the same `heredoc #N` messages. Routing both reads through `readText()` makes it pass 6/6 again on the CRLF inputs. This was a CRLF simulation on a POSIX host, not a Windows run.
- Normalizing at read time also matters past the extractor. The extracted snippet is run through `bash -c` (`run`, lines 70-77), and a heredoc carrying `\r` would not match its own `NODE_EVAL_EOF` terminator in bash either.

The repo already has the house fix for this class: `tests/helpers/read-skill.js`'s `readText(absPath)`, which normalizes EOLs (#2763). `skill-prose-conformance-tests` requires every prose suite to read governed markdown through it. This file, added by #3392, does not use it. The production prose (`mcp-transport.md`'s two heredocs at lines 121-124 and 132-141) is correct.

## Technical Approach

This is a test-only change to one file. It follows `.claude/skills/windows-checkout-test-parity/SKILL.md` ("Build CRLF inputs from the LF text") and `.claude/skills/skill-prose-conformance-tests/SKILL.md` ("Prose reads come from the shared helper", plus the Anti-Patterns row on anchoring an extractor on a bare `\n`). Replace the two raw reads with `readText(path.join(ROOT, 'plugin', 'skills', 'dispatch', …))`. Thread an optional `text` argument through `section`/`snippet`, and make the terminator search CRLF-tolerant with a regex or an equivalent pair of `indexOf` probes. Add one `test()` for the CRLF case. Keep `run`'s `bash -c` input LF: every snippet the suite executes comes from the `readText`-normalized `MCP`.

Alternative rejected: a `.gitattributes` `eol=lf` rule for `*.md`. It would change checkout behavior for every Windows user of the repo, and the only `.gitattributes` rule today is a narrow fixture-hash carve-out. `readText()` is the convention that #2763 settled on and that sibling records #3429, #3440 and #3507 apply.

### Key Files

- `tests/dispatch-neighbour-in-flight-mcp.test.js` — use `readText()` for the two markdown reads, parameterize `section`/`snippet` on the source text with a CRLF-tolerant terminator, and add the CRLF case
- `tests/helpers/read-skill.js` — unchanged; the existing `readText()` helper being consumed
- `plugin/skills/dispatch/mcp-transport.md` — unchanged; read-only input (the `## Step 2 — neighbour-in-flight pool (#3278, #3392)` section's two heredocs)
- `plugin/skills/dispatch/queue-pull-script.md` — unchanged; read-only input

## Gotchas

- Scope is this one file. Each sibling "Windows regression: N test file(s) newly failing after …" record (#3429, #3440, #3505, #3506, #3507, #3509, #3518, #3523) covers its own commit and files.
- `tests/dispatch-named-target-exclusion-fixture.test.js` also extracts a `NODE_EVAL_EOF` heredoc. The same run shows it failing at both base and head, so it is a pre-existing Windows failure and not part of this record. `tests/dispatch-per-record-groups-prose.test.js` uses the same `'\nNODE_EVAL_EOF\n'` terminator shape and passed on this run. Leave both alone here.
- Do not run CRLF text through `bash -c`. The CRLF case compares extractions only. A `\r`-bearing heredoc fails in bash for a reason unrelated to the extractor, and that failure would be misread as a regression.
- ubuntu CI cannot see this failure class. The CRLF case is the pin that runs on Linux. Without it, a later edit could reintroduce the raw read or the bare-`\n` terminator and stay green on every PR.
