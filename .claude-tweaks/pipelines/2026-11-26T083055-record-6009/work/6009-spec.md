# 6009: Record a run's tokens by model, list-price cost and minutes in its manifest

Surface: backend
Risk-flags: public-contract

## Overview

Adds the run's cost to its `manifest.json`: tokens by model, the list-price cost of those tokens, and the run's minutes, written when the run closes. The run manifest (#5903) carries run-start facts only (plugin version, lane, ceremony profile, policy hash, base commit, model profile). The design (`docs/superpowers/specs/2026-11-18-pipeline-economy-design.md`, Goal 7 and `## Phase 11`) asks that every run record what it cost and which policy it ran under, in a file Dispatch can read; the policy half shipped as `policyHash`, and this record adds the cost half.

Dollars are list-price equivalents of recorded token usage, one comparable unit, not invoices (the design's Non-goals). The price table that produces them lives today in maintainer-side `tools/pipeline-cost-report/spend.js`, which does not ship; this record moves it into the plugin payload so the shipped close path and the report price tokens identically.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Model and effort per role: record #6010 "Record each role's model and effort in the run manifest".
- Dispatch reading the new fields. Dispatch's manifest parser (thn-inc/dispatch #1958's `parseRunManifest`) stores nine named fields and ignores every other key, so reading `costUsd` is a change in thn-inc/dispatch, tracked there, not here. This record documents the fields in `docs/reference/run-manifest.md`, the contract Dispatch reads.
- Real invoices, subscription accounting, or Claude Code's own `total_cost_usd`.
- A cost for a run whose token rows could not be read: that is `null`, never `0`.
- Changing how `timing.json` attributes tokens to phases.

## Release Note

Every pipeline run now records its token use by model, its list-price cost and its minutes in its run manifest when it closes.

## Technical Approach

The close path already resolves everything cost needs: the token pass resolves the run's main-session and subagent transcripts, and the driver's events carry each worker's usage. Cost re-reads those transcripts' per-request rows rather than `timing.json`'s summed tokens, which carry no model key, no cache-write split and no per-request rows. A pure `deriveRunCost` turns those into the manifest fields, and the existing best-effort `fillRunManifest` writes them. Moving the price table into `plugin/bin/lib/` gives the shipped close path and the maintainer report one table.

Decided while specifying: cost is priced from tokens with the plugin's table for every lane, including the driver, rather than taking the CLI's `total_cost_usd`, so every lane reports in the same unit the design's evidence uses; an unknown model id is listed, never priced at a guessed rate; `minutes` is elapsed time from the run's start to its close, because the design's Goal 1 measures time to a green pull request; the version stays `1`, as the manifest's own Compatibility rule requires for added fields; a partial cost may be upgraded once by a complete one (a close before #5647's attribution, or with a transcript briefly missing, would otherwise freeze a wrong figure), and a complete cost is never rewritten, so a figure Dispatch has copied changes at most from partial to complete.

**Decision (plan-review Q1, partial-to-complete upgrade on a session-lane close):** Reading B. When `writeTimingAtClose`'s `prepare` returns `kept` (timing.json already has token totals) and the stored manifest cost group has `costPartial: true` or `costUsd: null`, the close path re-reads the run's transcripts for per-request cost rows (the same resolution and clipping the token pass uses) and offers the new group to `fillRunManifest`, whose one-upgrade rule decides. `timing.json` is never rewritten on that path (byte-identical). With a complete stored group, the `kept` path reads nothing for cost. Why: the spec's stated rationale for the upgrade (a close before #5647's attribution, or a briefly missing transcript, would freeze a wrong figure) is only met if a real close path can reach it; Reading A would leave AC8a reachable from the unit test alone.

**Decision (plan-review Q2, headless lens-worker spend):** Reading B, under the aggregate rule below. On session lanes, each headless lens-worker dispatch item (`readWorkerDispatches`, #6000: `tokens` but no transcript) is a token source: its `tokens` are added to `tokensByModel` under the item's model id and priced as one aggregate (Q3's rule), and the item counts as a read source. An item with `tokens: null` or no model id is an unread source and sets `costPartial: true`; an unrecognised model id goes to `unpricedModels` as for rows. Transcript-backed dispatch items are not counted from their `tokens` (their rows are already read), so nothing is counted twice. Why: leaving real spend out while the cost reads complete is the worse error; marking every run with workers partial (Reading A) would make the flag meaningless on review-heavy runs.

**Decision (plan-review Q3, driver step `usage` is a session total):** Reading B. A whole-session aggregate (a driver step's `usage`, a headless lens-worker item's `tokens`) is priced at the family's base per-token rates and never at Haiku's per-request long-prompt rate; `priceRequest`'s multiplier applies only to genuine per-request transcript rows. An aggregate with no cache-write split prices its whole write at the 5-minute rate, as for rows. `docs/reference/run-manifest.md` states that Haiku cost from aggregate sources is a lower bound. Why: a lower bound that is documented is honest; charging the 5x rate to a sum of short requests overstates by construction, and the overstated figure is the one Dispatch would copy.

**Decision (standing rule for any further plan-review gap on this record):** the builder settles a remaining two-reading gap itself, logs it to `decisions.md` as an AUTO line naming the reading, and does not stop for it, choosing by this order: (1) never let a figure read as complete when a source was dropped — count it or mark `costPartial`; (2) when a figure must be approximate, under-state and document a lower bound rather than over-state; (3) never change `timing.json`, a closing path's exit code or its timing bound (`TIMING_BOUND_MS`); (4) where this body and the code disagree on a fact, the code governs, and the build logs the correction. Stop only for a gap these four do not decide.

## Gotchas

- `timing.totals.minutes` is the union of phase spans, not elapsed time; do not use it for `minutes`.
- Price by each row's `model` (the model id), never by a dispatch item's `tier`, which is a profile bucket.
- `timing.dispatches` items carry token totals per agent, not per request; that is why cost reads the subagent transcripts' rows instead.
- Verified at build (plan-review round 1): after #5967, `readUsage` rows do NOT carry the cache-write split; this record adds it (see Current State and Key Files). A row that still has no split prices its whole write at the 5-minute rate.
- Count each transcript once: after #5647, the set of transcripts the token pass resolves may include subagent transcripts it also attributes to `timing.dispatches`. Dedupe the transcript paths (by real path) before reading rows, and dedupe rows by `message.id` across files.
- #5969 (make `initRunManifest`'s never-overwrite rule hold under a concurrent fill) also edits `write.js`. A close-path fill can race a late lane fill; keep every new field fill-only-null so a lost update cannot replace a real value with a wrong one.
- The token pass runs detached after close (`spawnTokenPass`) and may run after archival moved the run directory; `at-close.js` already follows a moved directory to its archive twin. Fill the manifest at the path the timing write used.
- The detached token pass must not change any closing path's exit code or timing (`TIMING_BOUND_MS`, 60 s): the fill is synchronous, small, and inside the existing try/catch.
