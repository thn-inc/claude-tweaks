# 4246: Write gate reads << inside ${…} or a same-line $(… <<EOF) as a heredoc opener and strips real commands

Surface: infra

**Related:** #4149, #4210, #4211, #4242, #4244, #4245, #4247, #4248, #4294, #4303, #4309, #4310, #4328, #4329, #4304, #4369

Origin: /claude-tweaks:review of #4149 (refs #4149)

## Current State

In `plugin/bin/lib/hooks/git-command.js`, `scanHeredocsWith` (`:1554`) misreads two shapes and then strips the following lines as a data body:

- It treats a `<<` inside an unquoted `${…}` as a heredoc opener. Bash reads it as literal text.
- It treats a `$(cat <<EOF)` closed on the same line as an opener whose body is the following lines. Bash runs those lines.

The original executed probe ran at the #4149 branch and at 7070c0b8a: `echo ${x:-<<EOF}\n: > /M/zz\nEOF}` and `echo $(cat <<EOF)\n: > /M/zz\nEOF` both gave fileWriteTargets `[]`, and bash writes /M/zz. Found by /claude-tweaks:review of #4149 (lens 3b).

**Re-probed at HEAD (session cwd `/r`), still reproducing:** both probe commands give `fileWriteTargets` `[]`. The routine `git commit -m "$(cat <<'EOF'` + newline + body + newline + `EOF` + newline + `)"` shape also gives `[]`, which is correct because its body is data.

The segment scanners already skip `${…}` via `spans.param` (`git-command.js:76`, `:1173`, `:1836`). The heredoc scanner does not apply the same span to find openers.

## Deliverables

1. Skip `<<` inside an unquoted `${…}` the way `spans.param` already does for the segment scanners.
2. Keep the body visible whenever a `$(` is still open at the opener and closes on the opener line, because the body then belongs to the substitution, not the next lines.
3. Add the probe cases to `tests/hooks-gate-coverage.test.js`.

## Acceptance Criteria

- `fileWriteTargets` reports /M/zz for both probe cases.
- The routine `git commit -m "$(cat <<'EOF' … EOF)"` shape still strips.
- Each new case goes red against the current scanner.
- `npm test` passes.

## Release Note

The worktree write guard no longer misses commands that follow text it wrongly took for the start of a heredoc.

## Technical Approach

Both fixes live in the opener scan. (1) Feed `spans.param` into `scanHeredocsWith`'s skip set so a `<<` inside `${…}` is never an opener candidate. (2) When an opener sits inside a `$(` whose matching `)` falls on the same line, a body cannot exist after that line, so do not start a body on the next line. Per bash, the here-document read for that substitution has no lines to consume before the `)`, so the following lines are ordinary commands. Judge both against real bash 3.2 and 5, per the repo-local `shell-scanner-bash-differential` skill, and time the adversarial shapes through `perf/heredoc-scan-linearity.test.js`.

### Key Files

- `plugin/bin/lib/hooks/git-command.js` — `scanHeredocsWith` opener detection; reuse `spans.param`
- `tests/hooks-gate-coverage.test.js` — the two probe cases plus the routine-shape guard
- `perf/heredoc-scan-linearity.test.js` — confirm the opener-scan change keeps the linear-time budget
- `plugin/skills/_shared/policy-schema-coverage.md` — the heredoc parser-rules prose that names opener exceptions; update when the rules change

## Gotchas

- The fail-closed direction matters. When the scanner is unsure whether a `<<` opens a body, keeping the following lines visible (scanning them) is safe. Stripping them is what fails open. Prefer "not an opener" in ambiguous spans.
- `policy-schema-coverage.md` already documents that a heredoc opened inside a quoted `"$( … )"` is judged by that substitution's own command (#4210). Keep the new same-line-close rule consistent with that paragraph and pin it in prose there.
- #4309 (a backslash-newline-split command substitution in an unquoted heredoc body) and #4310 (a heredoc reader shadowed by a shell function) touch the same scanner. #4242 proposes splitting the lexer out, so expect conflicts.
- The perf linearity suite has an open over-budget case (#4329, the `"$( #"` write-scan case). Do not regress it further.
