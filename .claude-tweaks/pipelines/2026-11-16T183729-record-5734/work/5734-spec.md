# 5734: A typed dispatch command builds a record that carries auto:merge but no auto:build, and the driver may then merge it

Surface: backend

**Related:** #5399, #5416, #5417, #5757
Risk-flags: auth
Risk-flags-unconfirmed: true

## Current State

Since #5584 (merged as PR #5625), a `/claude-tweaks:dispatch #N` line a person types builds a `ready` record that has no `auto:build` label. `resolveBuildAuthority` (`plugin/bin/lib/issues/build-authority.js`) answers `typed` for such a record. It reads only the build grant and never looks at `auto:merge`.

Every reader that authorizes a merge reads the merge grant on its own, without checking `auto:build`:

- The driver's merge step (`plugin/bin/lib/driver/merge.js`). Its entry read and its pre-merge read stop `not-authorized` only when `auto:merge` is absent.
- `evaluateMaturation` (`plugin/bin/lib/issues/grant-maturation.js`). It answers `already-mature` on `hasMergeLabel` alone, and `matured` on an `auto:merge-pending` label past its veto window. Its four callers are the unattended console resolver (`plugin/bin/lib/console/resolve.js`), the console executor's grant re-check (`plugin/bin/lib/reconcile/console-execute.js`), and the snippets in `plugin/skills/wrap-up/auto-merge-short-circuit.md` and `plugin/skills/dispatch/grant-maturation-gate.md`.
- The prose lines that route a run into those gates or authorize a merge directly: the applicability paragraph of `plugin/skills/wrap-up/auto-merge-short-circuit.md`, the matching bullet in `plugin/skills/wrap-up/SKILL.md`, the Auto-merge gate in `plugin/skills/dispatch/settle-and-merge.md`, and the Merge step of `plugin/skills/_shared/express-lane.md`.

`plugin/skills/_shared/work-record.md`'s Grant semantics say `auto:merge` is additive on `auto:build` and "alone is inert", and both that file and `docs/driver.md` say a typed command never implies `auto:merge`. Before #5584 the inert claim held only because no path built a record without `auto:build`. Now a record that carries a merge grant and no build grant (a person removed `auto:build` and left `auto:merge`, or an `auto:merge-pending` matured after `auto:build` was removed) is built by a typed command and then merged on the leftover grant once the merge-check and acceptance judgments pass. A stale or half-removed merge grant widens what the person typed.

The maintainer chose the rule on 2026-11-16: a merge grant counts only together with a live `auto:build` label. A typed run on a record without `auto:build` ends at `pending-review`, and a person who wants it merged types the merge (`/claude-tweaks:wrap-up #N merge`).

## Technical Approach

The rule is stateless. Nothing is carried from admission to the merge: each merge-authorizing read already fetches the record's live labels, and the fix adds the build label to what that read requires. A typed run is by construction a run on a record without `auto:build`, so it ends at `pending-review` with no marker to store, and a run admitted on the label is unaffected as long as the label stays on the record.

Considered and not chosen: a typed-run marker written at admission and read by the merge readers. It needs state that the driver (step events) and the prose lane (`decisions.md`) store differently, a run started on the previous release carries no marker, and a missing marker would have to fail open to keep those runs working.

Two consequences of reading live labels, both intended:

- A person who adds `auto:build` and `auto:merge` while a typed run is in flight has granted both, and the run may merge.
- A person who removes `auto:build` from a label-admitted record mid-run withdraws the merge too, at the next read.

In `plugin/bin/lib/driver/merge.js` the build check sits after the existing `auto:merge` check at both reads and reuses the `not-authorized` reason word with a distinct detail, so nothing that enumerates the merge step's reason words changes. `auto:merge-pending` still does not count in the driver.

In `plugin/bin/lib/issues/grant-maturation.js` the new input is checked first and fails closed: a caller that does not pass it gets `no-build-grant`, so a missed caller refuses merges instead of allowing them. `no-build-grant` is an added state; callers that test `mature` need no other change, and files that enumerate the failing states gain the new name.

## Original request

A typed dispatch command builds a record that carries auto:merge but no auto:build, and the driver may then merge it

## Current State

Found by /claude-tweaks:review of #5584 (gap-sweep, confirmed by an independent tiebreak). `resolveBuildAuthority` answers `typed` for a named, `ready` record without `auto:build` and never reads `facets.grants.merge`. `plugin/skills/_shared/work-record.md` says `auto:merge` is additive on `auto:build` and inert alone, and the #5584 docs say a typed command never implies `auto:merge`. ## Open question

Which reading is intended: (a) a merge grant a person left on a record is honoured once the typed command builds it, so the docs should say so; or (b) a typed run must end at `pending-review` whatever the record carries, so the typed path must refuse or ignore the merge grant (a new reason word or a typed-run marker the merge step reads)?

## Deliverables

- Decide (a) or (b) and state it in `plugin/skills/_shared/work-record.md`'s Grant semantics and `docs/driver.md`.
- For (b): make the typed path end at `pending-review` for such a record, with a test that a record carrying `auto:merge` and no `auto:build` built on a typed command stops `not-authorized` at the merge step.

**Decision (author, 2026-11-16).** Reading (b). A typed run ends at `pending-review` whatever merge grant the record carries: the typed path must not honour `auto:merge` on a record that has no `auto:build`. Reason: `work-record.md` says `auto:merge` is additive on `auto:build` and inert alone, and a typed command grants build authority only; letting a stale or half-removed merge grant ride a person's one-off command widens what the person typed. A person who wants the merge types the merge (`/claude-tweaks:wrap-up #N merge`). Deliverable 2's test applies as written. This record is built and merged before thn-inc/claude-user-config#50 ships `CC_LAUNCHED_BY`, because until then the typed path is closed for every hub-launched session and the gap cannot be reached; after it ships the gap is open. The build records that order in the PR body.
