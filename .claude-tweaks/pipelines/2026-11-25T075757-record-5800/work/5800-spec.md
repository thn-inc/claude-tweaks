# 5800: verify.js waits out its CI window on a HEAD that was never pushed instead of failing fast

Surface: backend
Risk-flags: public-contract
Risk-flags-unconfirmed: true

## Current State

Reported: in a `/claude-tweaks:flow` run, flow's story step committed a story file after the build phase's push. `/claude-tweaks:test`'s scoped `verify.js` then ran on that unpushed HEAD and produced no output for over 20 minutes, until it was stopped by hand. After a manual push the same command took the CI verdict in about 5 minutes. The report reads the silence as `verify.js` waiting for a CI run that could never start.

Premise check at shaping time, against `main`: `verify.js` does not wait in that case. `plugin/bin/lib/verify/ci-source.js`'s `fetchCiVerdict` makes `repos/{owner}/{repo}/commits/{sha}/pulls` its first read. For a commit GitHub does not know, that read returns HTTP 422 `No commit found`, and `isMissingCommit` turns it into the `head-not-pushed` fallback at once, before any CI wait. That code has shipped since 6.164.0 (#4347), and the report is on 6.170.0. What `verify.js` does with the fallback depends on the declaration:

- Under `localRuns: "on-request"` (#5369), `head-not-pushed` ends the run with exit 3 (`EXIT_NO_VERDICT`) and `noVerdictLines`' stderr text, at once.
- Without `localRuns`, every CI fallback runs the suite on this machine, a full suite run (`plugin/skills/test/ci-source.md`: 55+ min locally vs 3.5 min in CI). The only output naming the fallback is the `CI: {suite} — ran locally ({reason})` row in the final report (`plugin/bin/verify.js`, the report rendering). That row prints after the local run ends.

So the 20 silent minutes were almost certainly the local full run of a suite that CI would have answered minutes after a push. The defect stands, with its cause moved: an unpushed HEAD costs a whole local suite run without `localRuns`, and every fallback to a local run is silent until the run ends.

`plugin/skills/test/verification.md`'s "Push first, and exit 3" paragraph already says to push after any commit that moves HEAD, and its "Outcome: the call exited 3" branch already routes `head-not-pushed`: push and re-run once in a `pr-first` run, `--local` otherwise. That routing is written for `localRuns` declarations only.

## Deliverables

1. `head-not-pushed` ends a scoped run with no verdict (exit 3), whatever the declaration's `localRuns` says. In `verify.js`'s CI loop, a `head-not-pushed` attempt stops the loop (later CI-declared suites record `not-consulted`, as on-request does today) and takes the existing no-verdict path: no check runs, no slot is taken, no report or pass stamp is written, the stale `report.json` is removed, and a `noVerdict` verify event is written when `--run` is set. `--local` still skips CI entirely, so it never meets this.
2. `noVerdictLines` keeps its first-line shape, `verify.js: no verdict yet for suite "{suite}" — CI could not answer ({reason})`, which `verification.md` and its conformance test read. For `head-not-pushed`, that line continues `: HEAD {short-sha} is not on the remote; no check ran and no pass stamp was written.` and the next line reads `  Push the branch (commit first if the tree is dirty), then re-run this command,` followed by the existing `--local` line. The `localRuns "on-request"` clause stays on the on-request lines for every other reason.
3. Without `localRuns`, any other CI fallback that sends a suite to a local run prints one stderr line when the fallback is decided, before the slot wait and the local checks start: `verify.js: CI could not answer suite "{suite}" ({reason}) — running it on this machine`. The final report's `CI: … — ran locally (…)` row is unchanged.
4. `plugin/skills/test/verification.md`: the "Outcome: the call exited 3" paragraph says a scoped run exits 3 on `head-not-pushed` under any declaration, and on every other no-answer reason only under `localRuns: "on-request"`. Its existing branches (push and re-run once in a `pr-first` run with a run dir; otherwise `--local`) apply unchanged. The "Push first" paragraph names a commit `/test` itself makes (flow's story step committing a story file) as one that moves HEAD and needs its own push before the scoped call.
5. `plugin/skills/test/ci-source.md`: the Fallback reasons table's `head-not-pushed` row says it exits 3 in both modes and never runs the suite locally. The table's lead-in sentence stops saying every reason runs locally without `localRuns`.
6. Tests: unit coverage in `tests/bin-lib/verify/ci-cli.test.js` (see Acceptance Criteria), plus updates to the prose-pinning conformance suites that read these paragraphs (`tests/pipelines-push-first-local-runs-conformance.test.js`, `tests/verify-local-runs-docs-conformance.test.js`).

## Acceptance Criteria

- A scoped `verify.js` run without `localRuns`, whose CI source answers `head-not-pushed` (fake `gh` returning HTTP 422 `No commit found` on the pulls read), exits 3. No check command is spawned, no `report.json` exists afterward, and stderr's first line starts `verify.js: no verdict yet for suite "` and contains `(head-not-pushed): HEAD ` followed by the short sha.
- The same run under `localRuns: "on-request"` exits 3 with the same `head-not-pushed` first line, which now names the short sha.
- A run without `localRuns` whose CI source answers `no-open-pr-at-head` still runs the suite locally. Its stderr carries `verify.js: CI could not answer suite "{suite}" (no-open-pr-at-head) — running it on this machine` before the check's own output, and the final report row still reads `CI: {suite} — ran locally (no-open-pr-at-head)`.
- With two CI-declared suites and no `localRuns`, a `head-not-pushed` answer for the first records the second as `not-consulted` in the `noVerdict` verify event's `ci` entries.
- `--local` on an unpushed HEAD runs locally with exit 0/1 as before, never 3.
- `verification.md`'s exit-3 paragraph and `ci-source.md`'s `head-not-pushed` row state the any-declaration rule, and the conformance suites named in Deliverables pass.
- `npm test -- --full` passes.

## Release Note

Stop a scoped verification at once when HEAD has not been pushed, instead of running the whole suite locally while CI could answer after a push.

## Technical Approach

In `plugin/bin/verify.js`'s CI loop (the `#4347` / `#5369` block), after `fetchCiVerdict` returns `used: false`, set `stopped = onRequest || verdict.ci.fallback === 'head-not-pushed'`. Widen the `noVerdict` finder from `onRequest ? … : undefined` to also pick a `head-not-pushed` attempt when `onRequest` is false. `noVerdictLines(attempt, { sha, onRequest })` takes the start sha and the mode, and composes the head-not-pushed variant from them. For the early notice, write the stderr line at the `!verdict.used && !stopped` branch when `onRequest` is false. Keep it to that branch so `dirty-tree` and `tree-state-unreadable` skips (`skipCi`) get the same line from one helper. `ci-source.js` itself does not change: `head-not-pushed` is already detected there.

## Gotchas

- Decided while shaping: fail fast reuses the existing `head-not-pushed` detection (the API's 422) instead of the report's proposed `git ls-remote` / `git branch -r --contains` pre-check. The API read is already the first thing the CI path does, it needs no extra process, and it answers the question CI actually depends on (does GitHub know the commit?) rather than one remote-tracking ref.
- Decided while shaping: exit 3 on `head-not-pushed` applies without `localRuns` as well. Pushing takes seconds and a local full run takes up to an hour. Every scoped call site already reaches exit 3 through `verification.md`'s routing, and the roster of runs that never push already passes `--local` on its first call, so none of them meets the new exit. This is a behavior change for a project without `localRuns`, not a removed contract (no flag, verb or field changes), so the record is not labelled `breaking`.
- A just-pushed commit can briefly read as unknown while GitHub indexes it. The result is one exit 3 and one re-run, which `verification.md`'s routing already allows.
- A parallel lane (`ct-verify-stamp`) is editing `verify.js`'s stamp and slot code. This change stays in the CI loop and `noVerdictLines`, so expect catch-up merges, not conflicts in the same hunks.
- #5234 also edits this CI loop (its dirty-tree precondition), two lines above the `head-not-pushed` handling. Whichever lands second takes a catch-up merge.
- #5465 moves the on-request decisions (which suites are not consulted, whether the run ends with no verdict) into one pure function under `lib/verify/`. If it lands first, this record's `head-not-pushed` rule goes into that function as one more input, not back inline in `main()`. If this lands first, #5465 absorbs the rule. #5483 adds a `pr-conflicted` branch to the same exit-3 paragraph of `verification.md`. Merge the prose by hand; the two changes are independent.

## Original request

verify.js waits out its CI window on a HEAD that was never pushed instead of failing fast

**Summary:** With a `ci` block in the scope declaration, a scoped `verify.js` run whose HEAD is not on the remote waits for a CI run that can never start, for the whole CI wait, instead of reporting that HEAD is unpushed.

**Kind:** Defect

**Affected component:** `bin/verify.js` (the `ci` block's CI-verdict wait), `skills/test/verification.md` ("Push first, and exit 3")

**Use case:** In a `/claude-tweaks:flow` run, the build phase exit pushed the branch and CI passed on that HEAD. Flow's automatic story step then committed a new story file, so `/claude-tweaks:test` took `verification.md`'s Mismatch branch and ran the scoped `verify.js`. The new commit had not been pushed: the push-first rule is prose in `verification.md`, and nothing between the story commit and the verify call pushes. `verify.js` looked for CI on HEAD, found no run, and kept waiting. The foreground call hit the 600 s tool ceiling and was moved to the background, where it sat with no output for over 20 minutes until it was stopped by hand. After a manual push, the same command took the CI verdict in about 5 minutes.

Cost: about 20 minutes of wall time and a stopped background task, on a delta that was one YAML file.

What would have caught it: before entering the CI wait, `verify.js` compares HEAD with the remote branch (`git rev-parse HEAD` against `git ls-remote origin <branch>`, or `git branch -r --contains HEAD`). When HEAD is not on the remote, it exits 3 at once with a message naming the unpushed commit (`HEAD <sha> is not on origin/<branch>: push first`), which `verification.md`'s existing exit-3 handling already routes. Optionally, the push-first paragraph could also state that a commit made inside `/test` (the flow's story step) needs its own push.

**Definition:** Ready — the check, its exit code and the message are named above; the existing exit-3 path handles the outcome.

**Plugin version:** 6.170.0

## As Built (architecture alignment, Common Step 4.5)

- `noVerdictLines(attempt, sha)` takes the start sha only: `onRequest` would be unused, since without the key only a `head-not-pushed` attempt reaches the no-verdict path (Beneficial).

- `args.js` USAGE text and the `EXIT_NO_VERDICT` comment state the any-declaration `head-not-pushed` rule; `steps.js` and `tests/bin-lib/driver/run.test.js` drop wording verify.js can no longer produce (Beneficial).
- The early fallback notice is written once, after the no-verdict decision and before the slot wait, rather than at the decision point — staged for the Review Console as `sdd-ruling-1`.
