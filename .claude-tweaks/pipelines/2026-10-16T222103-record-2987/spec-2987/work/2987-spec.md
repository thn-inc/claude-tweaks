# 2987: bin/verify.js pass stamp: reads dirty when a check regenerates a tracked file

Surface: infra

**Related:** #3002

## Current State

`plugin/bin/verify.js` writes the verification pass stamp for any passing full run regardless of tree state (the write gate "never consults dirty", verify.js ~line 547), and `--stamp-status` reports `verifiedHead: true` only when the stored stamp was recorded against a clean tree at the current HEAD (`stampCoversCleanHead`, verify.js ~line 125). The dirty value comes from `gitInfo()` in `plugin/bin/lib/verify/report.js`.

When a check regenerates a tracked file — the reported case is a Next.js production build rewriting `next-env.d.ts` — the tree is dirty at stamp time even though every check passed on the exact HEAD commit. `--stamp-status` then reads `verifiedHead: false`, `/claude-tweaks:review` Step 1.5 re-triggers `/claude-tweaks:test`, and the re-run dirties the tree again. The only way to a verifying stamp is a second run that leaves the build out, or a manual restore-and-restamp.

A second, smaller gap from the same report: `plugin/skills/test/verification.md` gives no guidance for a `--cmd` that needs environment variables or an interpreter-specific import path; the reporter needed two failed runs to learn that a committed wrapper script must put the working directory first on the import path.

## Deliverables

1. `.claude-tweaks/verify-scope.json` accepts a `generated` list of path globs. `verify.js`'s dirty computation for the pass stamp ignores changes to paths matching those globs; any other dirty path still disqualifies the stamp exactly as today.
2. The stamp records which declared-generated paths were dirty at stamp time, so the exemption is auditable.
3. `plugin/skills/test/verification.md` documents the `generated` key (when to use it, and that it must name only files the checks regenerate) and adds a short note on `--cmd` wrappers needing environment variables or a working-directory-first import path.
4. `/claude-tweaks:init`'s verify-scope starter (`plugin/bin/lib/init/verify-scope-starter.js`) accepts the new key without breaking existing scope files.

## Acceptance Criteria

1. A full passing run whose only dirty path matches a declared `generated` glob produces a stamp for which `--stamp-status` reports `verifiedHead: true`, and the stamp lists that path.
2. A full passing run with any other dirty path still produces `verifiedHead: false`.
3. A scope file without `generated` behaves exactly as today.
4. `node --test tests/bin-lib/verify/stamp.test.js` and the verify CLI tests pass, with new cases for 1–3.

## Release Note

Verification can now earn a passing stamp when a check regenerates a declared generated file, instead of forcing a second run.

## Technical Approach

Extend the verify-scope declaration parser to read `generated`, pass the globs into the dirty computation used for the pass stamp (not the general report's `dirty`, which other readers may rely on), and record the exempted paths in the stamp. Option (b) from the original request — exempting any path that was clean before the run and dirtied by it — is rejected: a check that rewrites source (a formatter or `lint --fix`) would then vouch for a tree that differs from HEAD. Explicit declaration keeps that case disqualifying.

### Key Files

- `plugin/bin/verify.js` — stamp write and `--stamp-status` dirty handling
- `plugin/bin/lib/verify/report.js` — `gitInfo()` dirty computation; add a filtered variant for the stamp
- `plugin/bin/lib/verify/stamp.js` — record exempted generated paths in the stamp
- `plugin/bin/lib/verify/declaration.js` — parse `generated` from `verify-scope.json`
- `plugin/bin/lib/init/verify-scope-starter.js` — starter scope file compatibility
- `plugin/skills/test/verification.md` — document `generated` and the `--cmd` wrapper note
- `tests/bin-lib/verify/stamp.test.js` — new cases

## Original request

bin/verify.js pass stamp: reads dirty when a check regenerates a tracked file

**Component:** `bin/verify.js` pass stamp (`--stamp-status`, `verifiedHead`) and `test/verification.md` "Verification pass stamp", plugin version 6.134.1.

**Kind:** Gap.

**What happened.** A project's full check list includes a production build of a Next.js app. That build rewrites a tracked, generated type-declaration file (`next-env.d.ts`) in place, so the working tree is dirty at the moment `verify.js` writes its pass stamp. Every check passed on the exact HEAD commit, but `--stamp-status` then reports `verifiedHead: false`, and `/claude-tweaks:review` Step 1.5 treats `TEST_PASSED=true` plus a non-verifying stamp as "re-trigger `/claude-tweaks:test`". Re-running the same full set dirties the tree again, so the only way to a verifying stamp is a second run that leaves the build out.

**Why it matters.** The stamp's dirty rule exists to stop a pass on uncommitted source from vouching for a commit. A file the checks themselves regenerate is a different case, and today it forces a redundant run (minutes of wall-clock per review) or a manual restore-and-rerun on every project whose build touches a tracked generated file.

**Suggested behaviour.** One of: (a) let `.claude-tweaks/verify-scope.json` declare `generated` paths the stamp's dirty check ignores; (b) have `verify.js` compare the dirty set before and after the run and treat paths that were clean before the run and dirtied only by the checks as non-disqualifying, recording them in the stamp; or (c) document the workaround in `test/verification.md` (restore the generated file, then re-stamp with a check set that does not regenerate it).

**Second, related observation from the same run.** A project with no `.claude-tweaks/verify-scope.json` and a Python test list that needs environment variables has no documented way to express `--cmd tests=` other than a hand-written wrapper script, and a script-driven test runner resolves the project's packages differently from `python -m pytest` (the script's directory, not the working directory, is first on the import path). A short note in `test/verification.md` — "when `--cmd` needs environment variables or an interpreter-specific import path, commit a wrapper in the project and put the working directory first on the import path" — would have saved two failed verification runs.
