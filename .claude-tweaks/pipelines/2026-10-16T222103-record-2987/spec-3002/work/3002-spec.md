# 3002: bin/verify.js: no way to compose a full pass stamp from chunked --no-stamp runs, so a suite longer than the 10-minute foreground cap never verifies HEAD

Surface: infra

**Related:** #2987

## Current State

`plugin/bin/verify.js` writes the pass stamp only for a passing run of the full resolved check set: the write gate requires `fullSet && !parsed.noStamp` (verify.js ~line 568). `plugin/skills/test/verification.md:48` requires any deliberately partial `--cmd` set to pass `--no-stamp`, because the runner cannot tell a partial set from the full one. Both rules are correct on their own.

Together they leave a long suite with no way to earn a stamp. A project whose declared checks take about 25 minutes end to end must split verification into chunks under the harness's 10-minute foreground Bash cap. Every chunk is partial, so every chunk passes `--no-stamp`, and `--stamp-status` never reads `verifiedHead: true`. Every later gate (`/claude-tweaks:review` Step 1.5, the second call of a dispatched two-call group, skip-if-recent) then re-runs the whole set, so the two-call dispatch form pays the full ~25 minutes twice even when HEAD did not move. Agent-written stamps are forbidden (#1921), correctly, so there is no workaround. Reported on plugin 6.136.0.

Why not a single background run: `plugin/skills/test/verification.md:46`'s Foreground rule already permits one full-set run with `run_in_background` when the set exceeds the 600 s foreground cap — but only for the orchestrating session. "A dispatched subagent never backgrounds it — its turn cannot wait on a notification" (the `[IL-108]` family; #1904 stalled waiting on a background verify child's notification that never arrived). `/claude-tweaks:dispatch`'s two-call form runs each `/flow` call as a dispatched subagent, so inside those calls the 600 s cap is hard and chunking is the only sanctioned option. That is the case this record targets.

## Deliverables

1. A per-suite stamp mode: `verify.js --stamp-suite` (or equivalent) records, for a passing chunk, which declared checks passed against which sha and tree state, written by the runner only.
2. `--stamp-status` composes `verifiedHead: true` when every check declared in `.claude-tweaks/verify-scope.json` (types, lint, and each declared suite) has a passing per-suite record at the current clean HEAD.
3. A per-suite record never counts toward a different sha, a dirty tree, or a check it did not run; a failing chunk clears or never writes its record.
4. `plugin/skills/test/verification.md` documents the chunked flow: when to use it, and that `--no-stamp` stays required for ad hoc partial runs.

## Acceptance Criteria

1. Running each declared check in separate `verify.js` invocations with the per-suite mode, all passing at one clean HEAD, makes `--stamp-status` report `verifiedHead: true`.
2. If any declared check has no passing record at the current HEAD, `verifiedHead` stays `false`.
3. A per-suite record from an earlier sha, or written against a dirty tree, does not count.
4. A plain `--no-stamp` partial run still writes nothing.
5. The verify stamp tests pass, with new cases for 1–4.

## Release Note

Long test suites can now be verified in chunks under the 10-minute command limit and still earn a full verification stamp.

## Technical Approach

Store per-suite pass records alongside the existing stamp (same git-dir location, runner-written), keyed by sha and check name. Have `--stamp-status` compute the full-coverage verdict from the declared check list in `verify-scope.json`. Keep the existing full-run stamp unchanged so current callers see no difference.

### Key Files

- `plugin/bin/verify.js` — new flag, write path, and `--stamp-status` composition
- `plugin/bin/lib/verify/stamp.js` — per-suite record read/write
- `plugin/bin/lib/verify/args.js` — flag parsing
- `plugin/bin/lib/verify/declaration.js` — declared check list from `verify-scope.json`
- `plugin/skills/test/verification.md` — chunked-run documentation
- `tests/bin-lib/verify/stamp.test.js` — new cases

## Gotchas

- #2806 (untangling `verify/args.js`'s parseArgs, PR #2836) is in flight on `args.js`; build this after it merges or rebase onto it.
- #2987 changes the same stamp's dirty handling; agree one stamp schema so the two compose.
- A project with no `verify-scope.json` has no declared check list to compose against; per-suite mode should refuse there with a clear message rather than guess.
- The runner stays the only stamp writer; nothing here may add an agent-side write path.
