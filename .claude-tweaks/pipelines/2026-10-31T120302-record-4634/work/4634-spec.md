# 4634: A bundled merge under-reports in a release: only its lowest record is booked and noted

Origin: /claude-tweaks:specify #4552 brainstorm

Defer-reason: tangential

Surface: backend

**Related:** #4552, #4108, #2251, #2580, #2581, #2582, #4199

## Current State

A bundled merge lists every record in its `Fixes` footer, but its subject carries one `(#N)` suffix: the lowest record's (`plugin/bin/lib/release/subject.js`). Three release surfaces read only that one record.

- **Records shipped:** `plugin/skills/release/console.md:20` builds the row from "One line per `(#N)` suffix", and `plugin/bin/lib/release-preflight/pack.js:323` passes each commit's `subject` with no body. That row says a record silently absent "would under-report what the release contains".
- **Bookkeeping:** `plugin/skills/release/bookkeeping.md:19` builds the shipped set from the same suffix, so Step 7's `Shipped in v{version}` comment skips the other bundled records. They still close through their `Fixes` lines at merge.
- **Release notes:** `plugin/bin/lib/compose-subject.js:336` renders only the lowest record's Release Note, and `RELEASE_NOTE_FOOTER_RE` in `plugin/bin/lib/release-notes.js:16` reads one `Release-Note:` line per commit. The composer still requires a note from every bundled record.

**Measured on `main` (2026-10-30):**

- 72 of the 620 composed merges in the last 1,500 commits were bundles.
- Across eight released bundles, seven suffix records got a `Shipped in v` comment (7 of 7) and the other bundled records got none (0 of 18). The eighth bundle had no suffix match.
- 13 non-suffix records sampled from v6.156.2, v6.153.0 and v6.152.0: all 10 with a real note were missing from the Release, for example #4421 and #4041. The other 3 say "No user-visible change". Their numbers do appear, on the suffix commit's `closes` line, with no note text.
- In v6.156.2, 4 of the 6 Highlights bullets say "No user-visible change".

**Why the rule exists:** "never aggregated" is not a design principle. #2580 lists rendering every bundled note as a non-goal, calls it "an accepted scope limitation", and names multiple `Release-Note:` lines per commit as the way to solve it. #2581 repeats it as a known limitation.

**A related defect, from reading the code:** a merge composed with `--keep-open` on its lowest record has a `Refs` line but its suffix still names that record, so Step 7 books it and closes it, against #4199's intent. No release has been checked for a live case. This record's shipped-set rule fixes it.

**Decisions (human-approved 2026-10-30):**

- **Shipped set:** a commit with any `Fixes` or `Refs` line ships its `Fixes` numbers. A commit with neither keeps the `(#N)` suffix rule. A `Refs` record is not booked, because Step 7 closes what it books.
- **Notes:** one `Release-Note:` line per record, including a kept-open record, whose code did ship. Not an agent-written bundle note: #2580 says a note is written once, at spec time, by whoever holds the record's context, and makes release-time rewording a non-goal.
- **Filtering belongs in the renderer**, not the composer, so it also clears the noise from single-record merges and the commit keeps every note.
- **No backfill.** Old records would get comments long after the fact, and old Releases would change without anyone expecting it.

## Deliverables

1. `plugin/bin/lib/compose-subject.js` passes every record's Release Note to `composeSubject`, lowest number first, and `plugin/bin/lib/release/subject.js` writes one `Release-Note:` line per note. A single-record merge composes a byte-identical title and body to today. Update both header comments, which state the old rule.
2. `plugin/bin/lib/release-notes.js` gains one shared extractor that returns every `Release-Note:` line in a commit body, trimmed and in order. `plugin/bin/lib/release-local/commits.js` and `plugin/bin/lib/release-notes-publish.js` both use it, so neither restates the pattern. Parsed commits carry all the notes.
3. `renderReleaseNotes` renders every note and drops, case-insensitively, any note starting with `No user-visible change`. It also removes exact duplicates within the release, and still returns `null` when nothing is left.
4. `plugin/bin/lib/release-local/commits.js`'s `parseCommit` reads the `Fixes #N` and `Refs #N` lines (whole-line matches) into two number lists, and `plugin/bin/lib/release-preflight/pack.js`'s `unreleased` probe passes both through on each commit.
5. `plugin/skills/release/console.md`'s Records shipped row and `plugin/skills/release/bookkeeping.md`'s shipped set use the Decisions' shipped-set rule. Numbers are still deduplicated across commits, and a number whose payload is a pull request is still dropped. `Refs` numbers that nothing else ships render on one nested `Kept open (not booked)` console line.
6. Update `docs/releasing.md` and `docs/journeys/merge-a-record-with-a-conventional-subject-2251.md` wherever they state one note per merge.

## Release Note

A release now lists every record in a bundled merge, carries each one's own release note, and leaves out notes that say there is no user-visible change.

## Technical Approach

The composer change is small because every note is already validated at `compose-subject.js:330`: replace the one-note read with a per-record read. Have the new lines replace the single push at `subject.js:108`, keeping the existing paragraph order so `Release-Note:` still comes before the footers. Look at `parseFixesSpan` in `plugin/bin/lib/flow/closing-links.js` before writing the `Fixes`/`Refs` read; reuse it if it fits a commit body.

### Key Files

- `plugin/bin/lib/compose-subject.js` — one note per record
- `plugin/bin/lib/release/subject.js` — one line per note
- `plugin/bin/lib/release-notes.js` — shared extractor and renderer filter
- `plugin/bin/lib/release-notes-publish.js` — reads through the extractor
- `plugin/bin/lib/release-local/commits.js` — all notes, plus `Fixes`/`Refs`
- `plugin/bin/lib/release-preflight/pack.js` — `fixes` and `refs` on each commit
- `plugin/skills/release/console.md` — Records shipped row
- `plugin/skills/release/bookkeeping.md` — shipped set
- `docs/releasing.md` — release note wording
- `docs/journeys/merge-a-record-with-a-conventional-subject-2251.md` — bundle wording
- `tests/bin-lib/compose-subject.test.js`, `tests/bin-lib/release/subject.test.js`, `tests/bin-lib/release-notes.test.js`, `tests/bin-lib/release-notes-publish.test.js`, `tests/bin-lib/release-local/commits.test.js` — the cases above
- `tests/merge-subject-composer-conformance.test.js` — existing pins

## Gotchas

- `tests/bin-lib/compose-subject.test.js` pins a non-subject note as validated but not rendered (#2580's AC 3). That pin flips here on purpose.
- An older installed build reads only the first `Release-Note:` line and the suffix, so a new-format commit reads as it does today. Nothing breaks during rollout.
- #4552 edits the same composer and `subject.js` title logic. The two touch different paragraphs, but whichever merges second must re-run the composer tests against the other.
- release-please lists the `closes` numbers by parsing the commit body. Never test this with a live release (#2582). Keep the `Fixes` lines in their own paragraph, then confirm on the first real release that a bundle's `closes` numbers still appear.
- A `release: published` re-fire for a release published before this ships renders a different block, so the idempotency check would not match and a second Highlights block could be added. Only the newest release is ever walked, so this window closes with the next release.
- The filter depends on how authors phrase a note, so a differently worded "internal only" note still shows. That is no worse than today.
- A `Refs` record shipping in two merges would otherwise show its note twice, which is why the renderer removes duplicates.
