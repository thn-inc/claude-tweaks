# 4314: Shipped-candidate detector reads a PR's own filed follow-ups as shipped by it, so granted records never dispatch

**Related:** #1984, #4135, #4191

Origin: dispatch queue pull while dispatching #4294, 2026-10-25

Defer-reason: tangential

## Current State

`plugin/bin/lib/issues/shipped-candidate.js`'s `classifyShipped` rates a record `strong` (shipped already) when a merged PR mentions it, merged after the record's `createdAt`, AND either the PR's title matches the record's or the PR's changed files cover every path in the record's `### Key Files`. `/claude-tweaks:dispatch`'s queue pull (`plugin/skills/dispatch/queue-pull-script.md`) drops every `strong` record from `dispatch-groups.json` and stages a Close proposal.

A record filed *during* a PR's build satisfies all of that by construction. The PR mentions it because the build filed it (a wrap-up/reflect/triage follow-up list). The PR touches its Key Files because the follow-up is about the code that PR changed. And its `createdAt` falls before the PR's merge. Two live instances, measured 2026-10-25:

1. **#4135**, Origin "reflect full from #4024". PR #4035 (closes #4024) was opened 2026-10-24T08:24:28Z; #4135 was created 12:33:49Z; the PR merged 15:39:27Z. The mention is the PR's commit message: "the deferred follow-ups filed as #4127 to #4135". Signals: `merged-pr-mention-after-created`, `key-files-covered`. The test #4135 asks for (a previous-release `declaration.js` reader check) is absent from `tests/verify-scope-declaration.test.js` on main.
2. **#4191**, Origin "#2724 triage row spec-gap". PR #4144 (closing refs #2724, #3997) was opened 2026-10-24T15:40:05Z; #4191 was created 17:26:44Z; the PR merged 18:52:32Z. The mention is the PR body's "filed 12 records (#4178–#4191)". Signals: `merged-pr-mention-after-created`, `key-files-covered`.

Both records carry `auto:build`, so every dispatch firing silently excludes them and stages the same false Close proposal again; a human has to drop it each time (one session dropped both twice on 2026-10-25). The mention data `fetchLinkedPRs` returns (`plugin/bin/lib/issues/linked-prs.js`, query built in `plugin/bin/lib/issues/record-dependencies.js`'s timeline selection) carries `{number, title, state, merged, mergedAt}`, not the PR's `createdAt`, so the detector cannot see that the record was filed while the PR was open.

## Deliverables

- The cross-reference timeline query selects the source PR's `createdAt`, and `fetchLinkedPRs` passes it through on each `mentions[]` entry.
- `classifyShipped` skips a mention whose PR was opened before the record was created (the record was filed while that PR was already open, so it is that PR's by-product, never its target). A mention with no `createdAt` keeps today's behavior.
- The dispatch prose that describes the `strong`/`weak` tiers (`plugin/skills/dispatch/queue-pull-script.md`, and `plugin/skills/dispatch/SKILL.md`'s False-positive posture paragraph) states the new exclusion.

## Acceptance Criteria

- A fixture shaped like #4135 (record created after the mentioning PR was opened and before it merged, Key Files all covered by the PR) classifies `none` for that mention, and goes red when the new check is reverted.
- A fixture where the record predates the PR's opening, with the same signals, still classifies `strong`; a mention missing `createdAt` still classifies exactly as today.
- `fetchLinkedPRs` returns `createdAt` on each mention, pinned in `tests/bin-lib/issues/linked-prs.test.js`.
- `node --test tests/dispatch-shipped-candidate-prose.test.js` and the full `npm test` pass.

## Release Note

Dispatch no longer mistakes a follow-up record filed during a PR's build for work that PR already shipped, so those records get built instead of excluded with a false close proposal.
