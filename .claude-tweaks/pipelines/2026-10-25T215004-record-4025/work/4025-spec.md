# 4025: Express lane: build eligible trivial records in one agent without the /flow frame

Evidence: 14-day transcript analysis of this repo (176 main sessions, 5,599 subagent transcripts, 132 archived timing.json files, ~286k tool calls), 2026-10-24.

## Current State

Fast-lane (#1926, #1911, #1910, #1765) prunes steps but keeps the whole frame: claim, manifesto, ledger file, materialize commit, micro-plan + plan audit, PR-early lifecycle, SDD implementer + task reviewer, simplify/journeys/docs-sync checks, full verify, review, reflect, wrap-up, Review Console.

Measured: 39 fast-lane runs — median 53 min, 342 tool round trips, 66M cache-read tokens. #3968 (a two-line markdown citation fix): 26 min, 271 round trips, 593 KB of procedure loaded; the actual edit was made by a haiku implementer in ~40 s at minute 5.7.

## Deliverables

1. A deterministic eligibility gate (`blast-radius.js` + record facets) — e.g. `risk:low`, `size:low`, `ceremony:fast-lane`, ≤ 3 Key Files, none under `plugin/bin/lib/hooks/**` or a multi-consumer `_shared` contract. The rule set is settled in `plugin/bin/lib/express/eligibility.js` (`REASONS` is its single source): the `express-lane` policy key is `true`; `integration-model` is `pr-first`; the record is `risk:low`, `size:low` and `ceremony:fast-lane` with a `type:*` label and no `auto:merge-pending`; it has 1 to 3 Key Files, none a protected path (hook code, `skills/_shared/`, CI and forge config, `CODEOWNERS`, `package.json`, the agent's permission files, the policy and verify-scope files) or a `merge-sensitive-paths` path; no frontend surface (a `Surface:` of web, mobile, desktop or terminal); a spec-shaped body; not already escalated in this run. At check time the diff must stay within the Key Files and test files, within `auto-merge-max-lines`, and touch no protected or merge-sensitive path (a rename's old path included).
2. An express path in /dispatch (and /flow for a single eligible record): one agent reads the record, edits, runs impacted tests (blocked-by record), commits, opens the PR with its closing reference, writes one decisions summary, and arms merge per `merge-authorization`. No ledger, plan file, materialize commit, SDD, review lenses, reflect, or Review Console on the success path.
3. Escalation: a failing test, a gate denial, or a diff outside the eligibility bounds re-routes the record into the normal /flow path, keeping the worktree and branch.
4. Post-merge sampling: a deterministic share of express merges gets the normal review lenses after merge, with findings filed as records — the robustness check stays, off the critical path.

## Acceptance Criteria

- [ ] A #3968-shaped record (two markdown lines) completes end to end in under 5 minutes and under 40 tool round trips (timing.json).
- [ ] An ineligible record (e.g. `risk:medium`) never takes the express path (gate test).

- [ ] Express merges still require CI green.
- [ ] Across a fixture of 10 express merges, post-merge review fires on exactly the configured count.
