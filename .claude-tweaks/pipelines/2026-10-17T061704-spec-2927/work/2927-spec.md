# 2927: visual-review recommendation mode should require a frontend-surface signal, not files: overlap alone

Surface: infra

**Related:** #3009

## Current State

In recommendation mode, `plugin/skills/visual-review/SKILL.md`'s Step 0.5 (lines 79-103) counts a journey as **affected** when any of its `files:` frontmatter entries appears in the changed-file set (step 2, line 86). For each affected journey it then renders `> Recommended follow-up: /claude-tweaks:visual-review journey:{…}` (line 100). Nothing checks whether the change, or the journey, has a browser-renderable surface.

On #2769's review this produced a false recommendation. `plugin/bin/lib/gif/palette.js`, a CLI and agent-only module, is listed in `docs/journeys/walkthrough-gif-capture-2758.md`'s `files:` (line 8), so Step 0.5 recommended a browser walk of a journey that has no page to open. A patch fixing this was staged and approved in run `2026-10-03T110711-record-2769`. By then that run's branch had already auto-merged, so the patch was reverted rather than orphaned.

`plugin/skills/design-wrapper/frontend-detection.md` already defines the frontend-surface signal this needs. Layer 2 (line 68) covers the materialized body-metadata `Surface:` header. Layer 3 (line 5) is the file-extension sniff fallback.

## Deliverables

1. In Step 0.5, gate the "affected journey" verdict on a frontend-surface signal as well as the `files:` overlap. A journey counts as affected only when the run carries a frontend surface per `frontend-detection.md`'s precedence: a materialized `Surface: web|mobile|desktop` (Layer 2), or, when no `Surface:` is present, a UI trigger file in the changed-file set (Layer 3). Cite that file's precedence rather than restating it.
2. When the overlap exists but the surface signal does not, return the existing no-recommendation line, or a variant that names the suppressed journeys and the reason. Never return the `Recommended follow-up` line in that case.
3. Before writing the prose, re-derive the heuristic against a typical consumer web app. In a project whose journeys are mostly browser-navigable, check that a backend-only change touching a journey's `files:` does not suppress a recommendation a human would want, such as an API change behind a visible page. Record the conclusion in `## Gotchas` of the build's plan or the PR body.

## Acceptance Criteria

- A run whose changed files overlap a journey's `files:` but which has no frontend-surface signal (`Surface: backend|infra|terminal`, or no UI trigger file when no `Surface:` is present) does not render a `Recommended follow-up: /claude-tweaks:visual-review journey:` line from Step 0.5.
- A run with `Surface: web` (or a UI trigger file) and a `files:` overlap renders the same recommendation table and follow-up line as today.
- `npm test` passes in full.

## Release Note

Visual review no longer recommends a browser walkthrough when a change only touches non-UI code.

## Technical Approach

This is a prose change in `plugin/skills/visual-review/SKILL.md`, steps 2 and 4 of Step 0.5. The parent (`/claude-tweaks:review` Step 6 code-only) already passes the changed-file list, so the build should also have the parent pass the materialized surface. Alternatively, Step 0.5 can read `Surface:` from the run's materialized header the same way the design wrapper does. Pick whichever needs no new plumbing, and say which in the PR. Recover the staged patch from the archived run, `.claude-tweaks/pipelines/archive/2026-10-03T110711-record-2769/staged/wrap-up-skill-1.md`, if it is still present. Use it as a starting point, not as settled text.

### Key Files

- `plugin/skills/visual-review/SKILL.md` — Step 0.5 (79-103): gate "affected" on a frontend-surface signal
- `plugin/skills/design-wrapper/frontend-detection.md` — read-only: Layer 2/3 precedence to cite
- `plugin/skills/review/SKILL.md` — check what Step 6 code-only passes to recommendation mode; extend it if the surface value is needed

## Gotchas

- Do not fix this by pruning `palette.js` from the journey's `files:`. That entry is legitimate journey traceability, and `docs/journeys/` hygiene belongs to `/journey-health`, not this record.
- The consumer-project check in deliverable 3 is a real risk to address, not a box to tick. A web app's backend change can still break a page, which is why the gate keys on the run's surface rather than on each changed file's extension alone.
- #3009 also edits `docs/journeys/` content (retired backend references). Its overlap with this record is only in the journey files, not in Step 0.5's logic.
