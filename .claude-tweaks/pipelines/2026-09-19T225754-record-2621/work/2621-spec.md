# 2621: harness-health filed findings never populate Premise-check:, so materialize's premise-check machinery never fires for them

## Current State

materialize.js's premise-check machinery (built for #1829: record.js's specShapedBody/PREMISE_CHECK_RE, the author-association-gated execution in materialize.js, and build/SKILL.md's routing of premise.satisfiedAtBase to the Wrap-Up Review Console) is fully wired end-to-end and already exercised in production — but by exactly one filing site today: wrap-up/claude-md-curation.md's over-budget CLAUDE.md filing. toIssuePayload in plugin/bin/lib/harness-health/issue-payload.js (lines 51-58) calls specShapedBody({ header, currentState, deliverables, acceptanceCriteria, filedBy, verifiedAsOf }) and never populates the premiseCheck parameter, even though the parameter and its consumer chain already exist. The identical gap exists in docs-health, journey-health, and code-health's own issue-payload.js modules (confirmed via grep -n "premiseCheck" plugin/bin/lib/{docs,journey,code}-health/issue-payload.js returning nothing).

This was surfaced by /claude-tweaks:wrap-up's Skills curation row during record #2405's own wrap-up, which is the seeded incident: a harness-health-filed "add a CLAUDE.md bullet" finding sat 136 commits stale after an unrelated commit had already added the bullet, caught only via manual grep verification at build time because materialize.js's drift check had nothing but the Verified-as-of age stamp to go on. Full staged analysis: .claude-tweaks/pipelines/2026-09-19T210012-record-2405/staged/wrap-up-skill-1.md.

## Deliverables

Thread Premise-check: through harness-health's toIssuePayload in plugin/bin/lib/harness-health/issue-payload.js for mechanically re-checkable patch findings: additive intent (finding.newString present) checks for that string's absence in finding.target (exit 0 while absent, non-zero once present, mirroring the existing wc -l-over-budget shape's polarity); remove intent checks the opposite way against finding.oldString. new-skill candidates have no existing file content to check against and stay premise-check-less. Needs its own design pass on safe command construction (quoting/escaping oldString/newString — no shell injection, no false "resolved" reads from a substring match against multi-line or punctuation-heavy content) and a null-degradation path (materialize.js's existing "no Premise-check: line" fallback) when a string is too long or multi-line to anchor safely — never guess wrong. Needs its own test coverage: qualifying/non-qualifying finding shapes, escaping edge cases, the null-degradation path.

Scope this record to harness-health only. The identical fix in docs-health/journey-health/code-health's issue-payload.js is a natural, separately-specced follow-up once this approach is proven — not folded in here.

## Acceptance Criteria

A harness-health patch finding whose Current State claim is mechanically re-checkable against its target file's live content carries a Premise-check: line in its filed issue body, so materialize.js's existing premise-check machinery can auto-detect an already-resolved finding before a build starts, instead of relying solely on the Verified-as-of staleness-age signal or manual grep verification. A patch finding whose content can't be safely anchored (too long/multi-line) degrades to no Premise-check: line rather than a wrong one. New-skill candidates carry no Premise-check: line. Test coverage exists for the qualifying/non-qualifying/degradation paths.
