# 2331: Duplicate similarity-detection tokenizer/threshold constants: coordination.js vs issues/near-duplicate.js

Surface: infra

## Current State

Found during a pre-release whole-branch review. Two independently-merged PRs each shipped their
own Jaccard-similarity tokenizer and threshold constant, with no shared source and no test
importing either exported constant — so a change to one can silently invalidate the other's
tests without either noticing:

- `plugin/bin/lib/coordination.js` (confirmed, line 17, #1980): `SUBSTANCE_SIMILARITY_MIN = 0.4`
  + `SUBSTANCE_STOP_WORDS` (line 22).
- `plugin/bin/lib/issues/near-duplicate.js` (confirmed, line 24, #1944):
  `DEFAULT_TITLE_SIMILARITY_THRESHOLD = 0.5` + `STOP_WORDS` (line 30).

A search of `tests/` for either constant name returns zero hits —
`tests/bin-lib/issues/near-duplicate.test.js:66` hardcodes "0.5" in a test name/reasoning
(`'title similarity below the default 0.5 threshold does not fire'`) instead of importing the
real constant.

## Deliverables

- Decide whether these two similarity checks are conceptually the same primitive (in which case
  consolidate into one shared tokenizer/threshold module both import) or genuinely distinct
  enough to justify separate constants (in which case document why, and have each test import
  its own module's real constant instead of hardcoding the value).
- Update `near-duplicate.test.js` to import `DEFAULT_TITLE_SIMILARITY_THRESHOLD` rather than
  hardcoding 0.5.

## Acceptance Criteria

No test hardcodes either threshold as a bare numeric literal; both are imported from their
source module.

## Technical Approach

Read both modules' full similarity-scoring logic (`coordination.js`'s substance-similarity check
and `near-duplicate.js`'s title-similarity check) to judge whether they're the same primitive
applied to different inputs (substance text vs. titles) or genuinely distinct enough to warrant
separate stop-word lists and thresholds — this is the actual judgment call the Deliverables ask
for, not a mechanical decision this shaping pass can make without reading both algorithms'
full bodies. If consolidating: extract a shared tokenizer/stop-word/threshold module both import,
preserving each call site's own threshold value unless the investigation finds a reason to unify
those too. If keeping them separate: add a one-line comment at each constant's definition site
stating why the two are conceptually distinct, and fix the test regardless — the test-hardcoding
fix (Deliverable 2) applies either way. Update `near-duplicate.test.js:66` to import
`DEFAULT_TITLE_SIMILARITY_THRESHOLD` and interpolate it into the test name/assertion instead of
the bare literal `0.5`.

### Key Files

- `plugin/bin/lib/coordination.js` — `SUBSTANCE_SIMILARITY_MIN`/`SUBSTANCE_STOP_WORDS`, possible
  consolidation target
- `plugin/bin/lib/issues/near-duplicate.js` — `DEFAULT_TITLE_SIMILARITY_THRESHOLD`/`STOP_WORDS`,
  possible consolidation target
- `tests/bin-lib/issues/near-duplicate.test.js` (line 66) — fix the hardcoded `0.5`

## Gotchas

- Per a standing memory in this codebase, similarity scores are normalization-sensitive —
  consolidating the two tokenizers is only safe if their actual normalization behavior (case
  folding, punctuation handling, stop-word removal order) genuinely matches; verify with a
  substitution+diff test before assuming they're interchangeable, not just by reading the
  constant values.
- If consolidating, do not silently change either module's effective threshold — a Jaccard
  score computed by a merged tokenizer can differ from the original even at the "same" nominal
  threshold value if the tokenization itself changes; re-verify both modules' existing test
  suites still pass with real (not just literal-matching) behavior preserved.
