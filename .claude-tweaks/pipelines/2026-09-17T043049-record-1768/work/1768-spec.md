# 1768: agent-browser: locator clicks can dispatch without triggering app handlers; screenshot failures (os error 35) persist and cause false QA FAILs

Surface: infra

## Current State

agent-browser's semantic-locator click action can report success without the target app's click handler firing on certain elements (repro: small icon-sized buttons inside table rows in a local Next.js dev app) — confirmed by no network request firing and no state change, while a CSS-selector click, keyboard activation (focus+Enter), and raw mouse coordinates at the same element all behave correctly, so the locator resolved the right element but the synthetic click was not equivalent to a trusted click for it. Independently, the screenshot pipeline intermittently fails with `os error 35` (EAGAIN); once a daemon session hits it, every later screenshot from that daemon returns a dead/stale frame. Together these produced 3 false QA FAILs in a 7-story run — the qa-agent judged steps against a stale frame and reported on-screen hint text as "not rendered" even though page-text reads and the dev server's request log confirmed the POSTs actually fired.

## Deliverables

- Diagnose why a semantic-locator click on certain elements reports success without the element's registered click handler firing, and land a fix or a reliable failure signal — a locator click must never silently report success when the handler didn't run.
- Diagnose the `os error 35` (EAGAIN) screenshot-capture failure and either recover the pipeline (retry/self-heal/restart) or surface the degraded state loudly so a stale frame is never treated as current evidence.
- Ensure the qa-agent skill stops judging a step against a screenshot known to be stale/dead once the pipeline is in the degraded state.

## Acceptance Criteria

- A locator click against the repro'd icon-sized table-row-button case either triggers the same handler a real user click would, or the click action reports failure rather than false success.
- After an `os error 35` screenshot failure, subsequent screenshot captures in the same daemon session either recover automatically, or the session is marked degraded so downstream judgment doesn't trust the frame.
- Re-running the original 7-story QA run (or an equivalent regression case reproducing the same elements) produces no false FAIL attributable to either symptom.

## Technical Approach

Investigate agent-browser's synthetic click dispatch path for semantic-locator resolution versus its CSS-selector dispatch path — since CSS-selector clicks, keyboard activation, and raw-coordinate clicks all work on the same element, the defect is specific to how the locator-click path synthesizes the click event (likely not marked as a trusted event, or dispatched to the wrong target/phase). One option to evaluate against root-causing the synthetic dispatch itself: fall back to a trusted-input dispatch (e.g., CDP `Input.dispatchMouseEvent` at the resolved element's center) when a locator click produces no observable effect — not mandated. For the screenshot pipeline, investigate the daemon's screenshot capture retry/error-handling around `os error 35` (EAGAIN) and either add a bounded retry/self-heal, or a degraded-session flag the qa-agent skill checks before trusting a frame as current.

### Key Files

- `plugin/agents/qa-agent.md` — consumes screenshot and click-action results as evidence; needs the degraded-session awareness so it stops trusting a dead frame
- agent-browser CLI (vendored dependency, not in this repo's own source tree) — owns both the locator-click dispatch path and the screenshot capture pipeline; confirm the vendoring/patch mechanism before starting

## Gotchas

- The vendored agent-browser CLI's synthetic-click and screenshot code live outside this repo's own source in the vendored dependency — root-causing may require patching upstream or a vendored patch layer; confirm the vendoring/patch mechanism before starting.
- The "trusted-input dispatch" fallback and the "self-heal/mark degraded" fallback are both offered as directions in the original report, not mandated fixes — the actual mechanism is left open; do not treat either as the only acceptable design.

## Original request

agent-browser: locator clicks can dispatch without triggering app handlers; screenshot failures (os error 35) persist and cause false QA FAILs

**Summary:** Semantic-locator clicks can report success without the app's click handler ever firing, and the daemon's screenshot pipeline dies permanently on repeated `os error 35` — together these produced 3 false FAILs in a 7-story QA run.

**Kind:** Defect

**Affected component:** agent-browser CLI (vendored) + qa-agent skill

**Repro steps:**
1. Run a QA story against a local Next.js dev app containing small icon-sized buttons inside table rows.
2. Execute `agent-browser --session s find <semantic locator resolving to a row button> click` — the command reports success.
3. Observe the app: no network request fires, no state changes (the click handler never ran). The same element responds correctly to a CSS-selector-based click, keyboard activation (focus + Enter), and raw mouse coordinates at the element's position — so the locator resolved to the right element; the synthetic click was not equivalent to a trusted click for it.
4. Separately, within a long session, screenshot capture intermittently fails with `os error 35` (EAGAIN); once it starts failing, every later screenshot in that daemon's life returns a dead/stale frame.

**Expected vs. actual:**
Expected: a locator click either triggers the same handlers a user's click would or reports failure; a failed screenshot recovers on retry or is surfaced loudly so the qa-agent stops treating frames as current evidence.
Actual: the click reports success while the handler never fires (deterministic on these elements), and the screenshot pipeline stays dead silently — the qa-agent then judges steps on stale frames and reports on-screen hint text as "not rendered" (confirmed via page-text reads and the dev server's request log showing the POSTs fired). 3 of 7 stories in one run were false FAILs; each cost a manual reproduce-and-clear cycle.

Suggested directions: (a) fall back to a trusted-input dispatch (e.g. CDP `Input.dispatchMouseEvent` at element center) when a locator click produces no observable effect; (b) self-heal or restart the screenshot pipeline on repeated `os error 35`, or mark the session "screenshots degraded" so the qa-agent weights evidence accordingly.
