# 3316: Guard the Windows path-separator test class against regrowth on Linux-only CI

Surface: infra

**Related:** #2767 #3313 #3315 #3317 #3318 #2887 #2939 #2986 #2987 #3002 #3022 #3204 #3218 #3246 #3256 #3263 #3269 #3278 #3307 #3338 #3347 #3352

## Current State

CI runs `npm test` on `ubuntu-latest` only (`.github/workflows/test.yml:14`), so the Windows path-separator test class — expected values written with a literal `/` where the code under test produces `path.sep` — is invisible to every merge. After #2767 (PR #3294), the display-ID producers in `plugin/bin/lib/skill-audit/context-cost.js` call `toPosix` with the default `sep` (`context-cost.js:166`, `:226`, `:361`), so dropping one of those calls stays green on Linux. The class has already regrown once: #3080 added a `'/r/tracked-file.js'` expected literal after #3074 fixed its neighbours.

Brainstorming (2026-10-17) settled the guard: a **real Windows run**, not one of the record's three stand-ins (per-seam `path.win32` injection, a win32 path-simulation CI lane, a lint scan). Findings that drove it:

- The repo is public, so `windows-latest` runner minutes cost nothing.
- No path-separator bug has ever been reported from a user's machine. The cost so far is test noise on Windows checkouts (~342 failures on the last measured Windows run, #2767), which hid a real regression at least once (`[IL-160]`).
- The pr-first merge-verification gate (`plugin/skills/_shared/pr-first-merge.md`) waits on every check in a PR's rollup, required or not, and parks after 15 minutes pending. A PR-time Windows job would add its full runtime to every merge, and a path filter on `plugin/bin/`, `tests/`, `tools/`, `scripts/`, `package.json` or workflows would still match 75 of the last 100 merged PRs. So the job runs **after merge, on `main` only**, and adds zero development latency.
- `plugin/bin/verify.js` already does per-test baseline adjudication: `--baseline <ref> --baseline-cmd <name>=<template-with-{file}>` (#3043, `plugin/bin/lib/verify/baseline.js`). It re-runs only the failing files at the base commit in a scratch worktree, counts a failure as baseline only when the same tests fail at base, gives flaky files one isolated retry, and fails closed on anything it cannot classify. The `preExisting` allowlist (#3129) was rejected for this job because it adjudicates per **file**, so a regression inside an allowlisted file — exactly how #3080 regrew — would be masked.

## Technical Approach

The adjudication is entirely `verify.js --baseline`; this record adds only a workflow and a small reporting script around it. `HEAD^1` is the right base on `main` because merges there are squashed (linear history), so each run attributes new failures to exactly one merged PR. Both the HEAD run and the base re-runs happen on the same runner, so anything specific to the runner (CRLF via the runner's default `core.autocrlf`, drive letters, `gh` auth) cancels out instead of reading as a regression.

Gate the issue-filing step on the verify step's outcome (run it with `if: always()` and let the script read the report), so a red verify always reaches the filer. Exit the job non-zero whenever verify reported attributable failures, whether or not the issue was filed. A failure is never silent: no report, an unparseable report, or a failed `gh issue create` also turns the job red.

Repeat issues are not a concern: once a regression is on `main`, the next merge's run treats it as baseline (`HEAD^1` already fails it), so each regression is reported once. The filed issue is the durable record.

Follow `tools/upstream-drift/`'s shape for the script (a `run(argv, deps)` seam with `gh` injectable, a thin CLI wrapper), and the `gh-api-module-pattern` project skill for the `execFileSync` seam.

### Key Files

- `.github/workflows/windows-regression.yml` — new: post-merge `windows-latest` job running `verify.js --baseline HEAD^1`
- `tools/windows-regression/file-issue.js` — new: reads the verify report and files one issue for attributable failures

## Gotchas

- `verify.js` reads `.claude-tweaks/verify-scope.json` (`plugin/bin/lib/verify/declaration.js`), whose `flaky.files` list and `retry.tests` template also apply on the runner. That is intended; don't add a Windows-specific declaration.
- The baseline re-runs check out `HEAD^1` into a scratch worktree on the runner. Windows has the 260-character path limit (#2566, #1782): if the scratch worktree path trips it, set `git config --global core.longpaths true` in the workflow before the verify step rather than shortening paths in `baseline.js`.
- ASSUMPTION — verify at build: `actions/checkout@v4` on `windows-latest` leaves Git's default `core.autocrlf=true`, so the run sees CRLF working copies like a real Windows checkout — confirm by printing `git config core.autocrlf` and `git ls-files --eol` for one tracked `.md` in the first run's log.
- ASSUMPTION — verify at build: the full Windows `npm test` plus baseline re-runs fit in 60 minutes — confirm from the first `workflow_dispatch` run's duration and adjust `timeout-minutes`.
- The first `main` run may fail for reasons outside the path-separator class (CRLF, launcher, flake). Those are still legitimate Windows regressions or pre-existing failures the adjudicator classifies; don't widen this record to fix them. File each separately.
- Not in scope: a PR-time Windows check, options (a)–(c) from the original request, #3318's classification table, and #3313's "N new, M fixed" reporting.

## Open Question

Needs a design decision: which guard keeps the path-separator class from regrowing on ubuntu-only CI? Candidates: (a) inject a path flavor at each repo-display-ID seam and pin it with `path.win32` (cheap per site, but only covers sites someone remembers to inject); (b) a CI lane that runs selected suites under the win32 path-simulation preload (catches regressions, but fs-backed suites are noisy and drive letters stay invisible); (c) a lint-style scan for hard-coded `/` expected values next to a `path.resolve`-returning call (broad, heuristic). Pick one or a combination.
