# 5266: bin/claude-tweaks-statusline.js: re-spawns node + 3 shelled git calls on every render with no cache; cost scales with session count

Surface: terminal

**Related:** #5294 (the hook half), #5121, #4492, #4744, #4754

## Current State

`plugin/bin/claude-tweaks-statusline.js` keeps nothing between renders. Every render runs git through `execSync`, so each call also starts `/bin/sh`:

- `resolveMainProjectDir` (line 84) runs `git rev-parse --git-common-dir` whenever the project dir's `.git` is a file (a linked worktree).
- `readOriginRemote` (line 118) runs `git config --get remote.origin.url` on every render.
- `renderGit` (line 218) runs `git --no-optional-locks status --porcelain -b` on every render.

Measured 2026-11-13 at main 671c9a83c, counting child processes per render with a preload that wraps every `child_process` launcher (`node plugin/bin/claude-tweaks-statusline.js`, three renders each):

| Render | Launches | Processes (node + sh + git) | Median wall |
|---|---|---|---|
| Main checkout | 2 × `sh -c git …` | 5 | 456 ms (machine under load) |
| Linked worktree | 3 × `sh -c git …` | 7 | 367 ms |

Machine-wide on this Mac with about 27 live sessions, the status line rendered 47 times in 30 s at 4 processes each. The remote URL and the git common dir change only when the repo's config or `.git` layout changes, so recomputing them on every render is pure overhead. Branch and dirty state really do change between renders.

The wrapper `~/.claude-tweaks/bin/statusline.js` (`plugin/bin/lib/statusline-wrapper-source.js`) already loads the renderer in-process instead of starting a second Node, so the remaining cost is the git children.

## Deliverables

1. **Main checkout without a spawn.** `resolveMainProjectDir` reads the linked worktree's `.git` file (`gitdir: <path>`, relative to the worktree) and that admin dir's `commondir` file (relative to the admin dir), which is exactly how git computes `--git-common-dir`. With no `commondir` file the common dir is the admin dir itself, as git does. It falls back to today's `git rev-parse --git-common-dir` when either file can't be read or parsed, or when `GIT_DIR` or `GIT_COMMON_DIR` is set in the environment. *As built (Common Step 4.5, Beneficial):* the reader models git's `read_gitfile` and `is_git_directory` exactly, and also defers to git in these cases:
   - the `gitdir:` line is malformed or empty;
   - `commondir` is empty or unreadable for any reason other than ENOENT;
   - HEAD is not a valid ref or object id, or `objects/` and `refs/` are not searchable directories;
   - `GIT_OBJECT_DIRECTORY` is set;
   - on POSIX, the worktree dir, the `.git` file, the gitdir or the common dir is owned by another user (git's `safe.directory` check);
   - `.git` or `commondir` is not a regular file, or contains a NUL;
   - the main repo's config is one git might refuse: the same parse as Deliverable 2, plus `repositoryformatversion` other than 0 or 1 and any `[extensions]` section.

   The gitdir is resolved against the physical directory that holds `.git`, and is realpathed before `commondir` is read, as git does.
2. **Origin URL without a spawn.** `readOriginRemote` reads `<mainDir>/.git/config` and returns the last `url` value in the `[remote "origin"]` section. It falls back to today's `git config --get remote.origin.url` whenever the answer might differ from git's: `<mainDir>/.git` is not a directory; the config can't be read; it has an `[include]` or `[includeIf …]` section; `<mainDir>/.git/config.worktree` exists; any `GIT_CONFIG*` or `GIT_DIR` variable is set; the section header is spelled any other way (for example `[remote.origin]`); the value contains a quote, backslash, `#` or `;`; or the local config has no origin `url` (git may still find one in global or system config). *As built (Common Step 4.5, Beneficial):* the `config.worktree` trigger is replaced by deferring on any `[extensions]` section, which covers it, because git reads `config.worktree` only under `extensions.worktreeConfig`. The reader also defers to git in these cases:
   - `repositoryformatversion` is anything but literal 0 or 1;
   - `<mainDir>/.git` fails `is_git_directory`;
   - `.git/commondir` exists;
   - on POSIX, `<mainDir>` or `.git` is owned by another user;
   - the config is not a regular file, or contains a NUL;
   - `GIT_COMMON_DIR` or `GIT_OBJECT_DIRECTORY` is set (env names are matched case-insensitively);
   - a quote or backslash appears in any section's value;
   - a header or key line has whitespace other than space or tab;
   - the url has edge whitespace that git keeps but the git path's `.trim()` strips.
3. **One git call per render, no shell.** `renderGit` keeps exactly one `git --no-optional-locks status --porcelain -b` per render, launched with `execFileSync('git', [...])` instead of `execSync`. Each fallback in 1 and 2 also uses `execFileSync`. No `execSync` remains in the file.
4. Measure processes per render for both rows above, before and after, and quote the raw output in the PR.

## Acceptance Criteria

- A render in a main checkout or a linked worktree with a plain GitHub `origin` launches exactly one child process, `git --no-optional-locks status --porcelain -b`, and no `/bin/sh`: two processes in total, down from 5 and 7. Measured as in Current State.
- The rendered line is byte-identical with the fast paths on and forced off, for each of these repos: main checkout; linked worktree; submodule checkout; no `origin`; non-GitHub `origin`; `origin` set only in an included config file; `origin` with a quoted value; detached HEAD; unborn branch; dirty tree; a directory that is not a repo.
- Each fallback trigger in Deliverables 1 and 2 reaches git (one test per trigger), and each of those tests goes red when its trigger is removed from the code.
- A source-scan test pins that `claude-tweaks-statusline.js` calls neither `execSync` nor `exec`.
- `npm test` passes, and `npm run test:perf`'s `statusline-render` budget still passes.

## Release Note

The status line starts one git process per refresh instead of up to three shell-wrapped ones, and shows exactly what it showed before.

## Technical Approach

Two small filesystem readers in `claude-tweaks-statusline.js`. Each returns either a definite answer or `null`, meaning "ask git", so every path that is unusual or can't be read lands on today's git call. Strip `\r` from both files' lines so a CRLF checkout parses the same way. Section names in git config are case-insensitive and subsection names are case-sensitive, so `[Remote "origin"]` matches and `[remote "Origin"]` does not. Key names are case-insensitive (`URL = …` matches).

`renderGit` keeps its status call, because dirty state has no cheap invalidation signal: working-tree edits don't touch any file git keeps, so only `git status` can see them. Caching it behind a TTL would let the `●` lag behind a commit until the next render. Claude Code already throttles how often it re-renders the status line, so one status call per render is the floor that keeps behaviour identical.

### Key Files

- `plugin/bin/claude-tweaks-statusline.js` — filesystem readers for the common dir and the origin URL with git fallbacks; `execFileSync` for every git call
- `tests/statusline.test.js` — parity, fallback-trigger, and no-shell tests

## Gotchas

- `git config --get` returns the last of several values. Match that rule, and don't stop at the first `url` line.
- An unborn branch and a detached HEAD come from `renderGit`'s status output, which this record leaves unchanged. Cover them in the parity tests anyway.
- A `.git` file's `gitdir:` path can be relative to the worktree, and `commondir` is relative to the admin dir. Resolve each against its own base.
- `tests/windows-hide-spawn-conformance.test.js` and the `--no-optional-locks` scan both read this file. Keep `windowsHide: true` on every new `execFileSync`.
- Out of scope: the hook-side `git rev-parse` repeats, which are tracked in #5294.

## Original request

bin/claude-tweaks-statusline.js: re-spawns node + 3 shelled git calls on every render with no cache; cost scales with session count

**Summary:** The status line keeps nothing between renders. Every render starts a fresh Node process plus three shell+git processes. With many sessions open, that adds up to a steady chunk of a CPU core.

**Kind:** Defect

**Affected component:** `bin/claude-tweaks-statusline.js` (and the `~/.claude-tweaks/bin/statusline.js` wrapper from `bin/lib/statusline-wrapper-source.js`)

**Repro steps:**
1. Install the status line wrapper and open many concurrent Claude Code sessions (we had about 23 on a 12-core Mac, mostly agentic `/flow`/`/dispatch` runs).
2. Count wrapper invocations machine-wide: poll `pgrep -f 'claude-tweaks/bin/statusline.js'` every 80 ms for 30 s and count distinct pids. We caught 39 in 30 s, so at least 1.3 per second. Short-lived runs slip between samples, so this is a lower bound.
3. Time one render in a normal repo: `/usr/bin/time -p node bin/claude-tweaks-statusline.js <<<'{"cwd":"<repo>","model":{"display_name":"Opus"},"workspace":{"current_dir":"<repo>"}}'`. That gave 0.19–0.23 s wall, 0.06 s user and 0.09–0.13 s system. A bare `node -e ''` costs about 0.03 s, so most of the cost is the child processes, not Node startup.

**Expected vs. actual:**
Expected: a render costs close to nothing when nothing has changed, so the total cost stays roughly flat as sessions are added.
Actual: every render runs `execSync` three times through `/bin/sh` (`git rev-parse --git-common-dir`, `git config --get remote.origin.url`, `git --no-optional-locks status --porcelain -b`). That is 1 node + 3 sh + 3 git processes per render, with no reuse across renders. At ≥1.3 renders/s that is ≥0.25 of a core of steady CPU, about two-thirds of it kernel time from creating processes. It grows linearly with concurrent sessions. On a machine already short on CPU from parallel agents, this is pure overhead.

**Suggestions (any one helps):**
- Cache the rendered line, or at least the git segment, per `cwd` or session in a small tmp file with a TTL of a few seconds; serve from it when it's fresh.
- Cache values that rarely change for much longer: the remote URL and git common dir hardly ever change, so key them on the repo's `.git/config` and `HEAD` mtimes.
- Use `execFileSync('git', [...])` instead of `execSync('git …')` to drop the extra `/bin/sh` per call (3 fewer processes per render).
- Document or use Claude Code's status-line refresh/debounce settings, if any apply.

Related: #5121 (render-cost budget test) measures one render's cost, but nothing bounds the total across sessions.
