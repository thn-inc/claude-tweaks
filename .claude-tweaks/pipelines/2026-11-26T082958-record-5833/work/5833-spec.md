# 5833: wrap-up: Branch finish merges on a console.json merge resolution computed before a later needs-human verdict

## Current State

Under `consoleAutoResolve`, `console-resolve.js --policy console-auto` computes the merge half once and persists it to `{run-dir}/console.json` as `merge.resolution`. `mergeResolution()` in `plugin/bin/lib/console/resolve.js` honours a needs-human verdict only through `needsHumanVerdict(decisions)`, which reads `decisions.md` at that moment.

`wrap-up/execution-and-verification.md`'s Branch finish then routes the pr-first merge on `console.json`'s `merge.resolution` directly, and `_shared/pr-first-merge.md` never re-reads a needs-human verdict. `review-console.md` orders the Auto-merge short-circuit (which logs the `assess-agent-autonomy` merge-check verdict) before the Auto-resolution short-circuit, but nothing mechanical enforces that order.

Observed in run `2026-11-16T183913-record-5770` (#5770, PR #5780): `console-resolve.js` ran at 20:12:39Z and recorded `merge.resolution: merge`; the short-circuit's `needs-human` verdict was logged at 20:13:22Z, 43 seconds later. Only the dispatched agent's manual hold kept the PR from merging.

## Deliverables

1. At Branch finish, before acting on `merge.resolution: merge`, re-evaluate `needsHumanVerdict` against the current `decisions.md`. On a hit, resolve leave-open (`pending-review`) and log one decision line naming the late verdict.
2. Have `console-resolve.js` refuse to resolve the merge half, or mark it stale, when the Auto-merge short-circuit applies to the run (live `auto:build` + `auto:merge`/`auto:merge-pending`) but no merge-check verdict line exists yet.

## Acceptance Criteria

- A test where `decisions.md` gains a needs-human merge-check line after `console.json` records `merge.resolution: merge` shows Branch finish leaving the PR open, never merging.
- A test where `console-resolve.js` runs with the short-circuit applicable and no verdict line yet shows it not resolving `merge`.
- The in-order path (verdict logged before the resolve) is unchanged: existing `console-resolve` tests stay green.

## Release Note

An unattended run no longer merges a PR whose merge check asked for a human, even when the check finished after the Review Console resolved.

## Technical Approach

### Key Files

- `plugin/bin/lib/console/resolve.js` — needsHumanVerdict / mergeResolution: refuse or mark stale before a verdict exists
- `plugin/bin/console-resolve.js` — surface the stale merge half
- `plugin/skills/wrap-up/execution-and-verification.md` — Branch finish re-checks the verdict before merging
- `plugin/skills/wrap-up/review-console.md` — state the ordering requirement as enforced
- `plugin/skills/_shared/local-merge-auto-finish.md` — local-merge finish re-checks the verdict before merging (Decision below)

## Decision

**Decision** (plan-review question 1, 2026-11-26, maintainer-authorized autonomous lane): **Reading B.** Deliverable 1's re-check covers every site that acts on `console.json`'s `merge.resolution: merge`, not only the `pr-first` Branch finish. A merge resolved before a later needs-human verdict is the same hazard under either integration model. Concretely: the `pr-first` Branch finish in `plugin/skills/wrap-up/execution-and-verification.md` and the `local-merge` no-prompt finish in `plugin/skills/_shared/local-merge-auto-finish.md` both run the same single re-check (one helper or CLI call in `plugin/bin/lib/console/resolve.js` / `console-resolve.js`, not two copies) before merging. On a hit, `pr-first` leaves the PR open (`pending-review`). `local-merge` leaves the branch unmerged in that file's existing awaiting-a-human state. Both log the one decision line Deliverable 1 names.

**Decision** (family rule, applies without asking): any further site this plan finds that acts on a merge resolution computed earlier in the run gets the same re-check. Every gap in this family resolves **fail-closed**: whenever the re-check cannot prove that no needs-human verdict exists (`decisions.md` is unreadable, the decision-line append fails, a lock cannot be taken, or the verdict line is malformed), the run leaves the PR or branch unmerged and never merges. The re-check reads `decisions.md` and makes its writes under the same lock. It appends its decision line before it updates `console.json`, so a failed append never leaves a changed `console.json` without its line. Resolve further plan-review gaps of this kind by this rule rather than asking.
