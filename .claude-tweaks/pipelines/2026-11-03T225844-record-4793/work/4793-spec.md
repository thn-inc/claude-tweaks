# 4793: Look up native blocked-by links from another repository by owner and name, not by number alone

Origin: SDD ruling deferred at Review Console (#4553)

Defer-reason: pre-existing-outside-diff

## Current State

`plugin/bin/lib/issues/record-dependencies.js` (`buildNativeDependencyQuery`, with the node projection at its `blockedBy(first:25){ nodes{ number state } }` selection) returns each native blocker as a number only. A blocker linked natively from another repository is therefore looked up by number in this repository.

This was harmless while the numbers only fed ordering, but #4553's `--blocker-landing` makes it load-bearing: a cross-repository native blocker can read as another repository's issue of the same number, causing a false stop or a false `landed`. The file is outside #4553's diff and `buildNativeDependencyQuery` is deliberately unchanged for its dispatch and wrap-up consumers, so the fix was deferred (#4553 final review, Minor 4).

## Deliverables

Project each native blocker's `repository { nameWithOwner }` and carry it with the number, so `--blocker-landing` and the other consumers can skip or separately resolve a blocker that is not in this repository.

Decide the verdict for a cross-repository blocker in `plugin/bin/lib/preflight-records/blocker-landing.js` (undetermined with a stated `via`, never a same-number lookup here) and pin it in the blocker-landing suite.

## Acceptance Criteria

A blocker-landing test with a native blocker whose repository differs from the run's repository does not query this repository's issue of the same number; reverting the repository check turns it red.

`buildNativeDependencyQuery`'s existing dispatch and wrap-up consumer tests still pass unchanged.

## Release Note

A cross-repository native blocker no longer causes a false stop or a false landed verdict in the blocker-landing check.

## Technical Approach

### Key Files

- `plugin/bin/lib/issues/record-dependencies.js` — project the blocker repository
- `plugin/bin/lib/preflight-records/blocker-landing.js` — handle a cross-repository blocker

## Decisions

Answers the plan-review questions (comment 6571698333).

- **Q1 — Decision: Reading B.** In `plugin/bin/lib/preflight-records/blocker-landing.js`, a cross-repository blocker whose native `blockedBy` node `state` is `OPEN` reads `open` (taken from the native node, no extra lookup), so `/flow` stops before the claim. Only a CLOSED cross-repository blocker reads `undetermined` with `via: cross-repository`.
- **Q2 — Decision: Reading B (in scope, not a follow-up).** This record also makes `plugin/bin/lib/wrap-up/pack.js` (around line 732) and `plugin/skills/wrap-up/unblocked-records.md` (around line 67) remove the `crossRepoBlockers` numbers before the `blockedBy.includes(closed)` test, so closing this repository's #N never reports a record blocked natively by `other/repo#N` as unblocked. Add a new test for that case; existing consumer tests stay unchanged.
- **Decided (round 2), Q3: fix here** (answers comment 6588531826). Every reader that names a foreign blocker as this repository's `#N` is fixed in this record: `backlog/overview-mode.md`, `backlog/refine-mode.md`, the `blocked-by:` header in `flow/materialize.md`, and the dispatch queue's Blocked-exclusion report. The rule covers the whole family: any reader or report of a blocker reference names a foreign blocker in its qualified `owner/repo#N` form. If the build finds another such site, it fixes that site too rather than asking.
- **Decided (round 2), Q4: next to the check.** The test that goes red when the repository check is reverted lives in the test file of the module that holds that check (`blocker-landing.test.js` if the check is in `blocker-landing.js`). The end-to-end tests in `preflight-records.test.js` stay as well. The acceptance criterion is the revert-red property; prove it by reverting the check and showing the red run.
- **Decided (round 2), Q5: fail closed.** A foreign blocker whose native state is unreadable reads `open`, not `undetermined`, consistent with Q1. The skip or refusal text says the blocker's state was unreadable (naming `owner/repo#N`), so the stop can be diagnosed and is not a silent fallback.
- **Decided (round 3), Q6: match dispatch** (answers comment 6603271850). A record whose only blocker is an open foreign-repository blocker is classified `granted` in backlog overview, not `dispatchable`, the same way `/dispatch` refuses it.
- **Decided (round 3), Q7: list it, and teach the parser.** `materialize.js` also parses `Blocked by owner/repo#N` lines from the body, and the `blocked-by:` header lists every blocker, foreign ones in the qualified `owner/repo#N` form, as Q3 states.
- **Blanket rule (whole family, so no further round is needed):** every surface that classifies, counts or names a record's blockers treats a foreign blocker exactly as `/dispatch` does (open or unreadable means blocked) and names it `owner/repo#N`. If the build finds another such site, it applies this rule there without asking.
