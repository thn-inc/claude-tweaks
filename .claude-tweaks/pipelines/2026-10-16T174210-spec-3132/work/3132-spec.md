# 3132: reconcile/dispatch Preflight: fresh clone with no origin/HEAD resolves integration branch as null ("no-remote")

Surface: infra
**Related:** #3026, #2734, #2868, #2912, #2935, #3003, #3012, #3014, #3024, #3030, #3031, #3065, #3079

## Current State

`resolveIntegrationBranch` (`plugin/bin/lib/hooks/worktree-reap.js:357`) resolves the integration branch from `.claude-tweaks/policy.yml`'s `integration-branch` key, then an in-process cache, then `git rev-parse --abbrev-ref origin/HEAD`. This repo's `policy.yml` sets no `integration-branch` key, so the `origin/HEAD` read is the only source that resolves anything here. A fresh `git clone` in a cloud/Routine sandbox container leaves the local `refs/remotes/origin/HEAD` symbolic ref unset (`git symbolic-ref refs/remotes/origin/HEAD` fails right after the clone, even though `origin` is configured and `git fetch origin main` succeeds). The resolver therefore returns `null`, and `plugin/bin/lib/reconcile/index.js:110-113` short-circuits every check with `{"skipped":[{"check":"all","reason":"no-remote"}]}`. This was observed in a scheduled `/claude-tweaks:dispatch` Routine firing. Running `git remote set-head origin -a` by hand fixes the session, but every new sandbox container hits the problem again.

The record left the choice of fix open: (a) fix provisioning, through the Setup script or the SessionStart hook, or (b) extend the resolver's fallback ladder with a network read such as `git ls-remote --symref origin HEAD`. Shaping-time evidence on that choice:

- The resolver is documented as offline and cheap. The `preferRemoteTrackingRef` comment above it says "this resolver must stay offline and cheap". Eight modules call it, including the SessionStart reaper, run-integrity, and the pre/post-tool-use hooks. Putting a network call inside it would put network latency on every hook path.
- `scripts/claude-cloud-setup.sh` is generated by `/claude-tweaks:init` Step 14 (`plugin/skills/init/bootstrap/step-14-cloud-routine-parity.md`) and is marked "do not hand-edit". CLAUDE.md's Cloud parity section records that the Setup script was measured not reaching scheduled Routine sandboxes, which is exactly where this failure was observed. Option (a) via the Setup script would not cover the reported case.
- `reconcile` already fetches over the network (`plugin/bin/lib/reconcile/shared-fetch.js`), so a one-time `origin/HEAD` repair inside reconcile costs nothing new in network terms and leaves the shared resolver offline.

## Deliverables

1. In `plugin/bin/lib/reconcile/index.js`, when `resolveIntegrationBranch` returns `null` and an `origin` remote is configured (`git remote get-url origin` succeeds), run `git remote set-head origin --auto` once, then re-resolve. Skip with `no-remote` only when no `origin` remote exists or the re-resolution is still `null`. Record which outcome occurred in reconcile's JSON result so the repair is visible.
2. Keep `resolveIntegrationBranch` itself offline. Do not add any network call to `plugin/bin/lib/hooks/worktree-reap.js`.
3. Add a test in `tests/reconcile.test.js` that builds a real fresh clone (a bare repo cloned into a temp directory, then `git remote set-head origin --delete` so `refs/remotes/origin/HEAD` is absent) with no `integration-branch` policy key, and asserts that reconcile resolves a non-null integration branch instead of returning the `no-remote` skip.
4. Add a test asserting that a checkout with no `origin` remote still returns `{"check":"all","reason":"no-remote"}` unchanged.

## Acceptance Criteria

- [ ] On a fresh clone with no local `refs/remotes/origin/HEAD` and no `integration-branch` policy key, `reconcile --json` resolves a non-null integration branch and does not return the `{"check":"all","reason":"no-remote"}` skip, with no manual `git remote set-head`.
- [ ] Reconcile's JSON result records that it repaired `origin/HEAD` when the repair ran.

## Technical Approach

Repair `origin/HEAD` at the one consumer that already does network work, rather than in the shared offline resolver or the generated Setup script. `git remote set-head origin --auto` asks the remote for its HEAD and writes the local symbolic ref. After it runs, the existing offline `git rev-parse --abbrev-ref origin/HEAD` read succeeds for the rest of the session, so the hook-path callers of `resolveIntegrationBranch` benefit too, with no change. The repair must follow the never-break-a-session invariant in `docs/hooks.md`: a failed `set-head` (no network, auth failure) degrades to today's `no-remote` skip and never throws.

### Key Files

- `plugin/bin/lib/reconcile/index.js` — one-time `git remote set-head origin --auto` repair and re-resolve before the `no-remote` short-circuit; record the repair in the result
- `plugin/bin/lib/hooks/worktree-reap.js` — unchanged; `resolveIntegrationBranch` stays offline (referenced for the AC)
- `tests/reconcile.test.js` — fresh-clone fixture test and no-origin regression test

## Gotchas

- A plain `git clone` normally sets `origin/HEAD`, so the test fixture has to delete it explicitly (`git remote set-head origin --delete`) to reproduce the sandbox state. A fixture that merely clones will pass vacuously.
- Do not hand-edit `scripts/claude-cloud-setup.sh`. It is regenerated by `/claude-tweaks:init` Step 14, and the Setup script is not a reliable path into scheduled Routine sandboxes anyway.
- `git remote set-head --auto` makes a network round-trip. Keep it inside reconcile, never in `resolveIntegrationBranch`, whose callers include the pre/post-tool-use hooks.
- The repair writes a ref in the main checkout's `.git`. That is the same scope as reconcile's existing fetch, but confirm it does not run from inside a worktree against a different gitdir.
- Reconcile runs under a shared wall-clock budget (see related #3026). The `set-head` round-trip counts against it, so bound it with the same timeout reconcile's existing fetch uses.

## Current State
`resolveIntegrationBranch` in `plugin/bin/lib/hooks/worktree-reap.js` (used by `reconcile` and by dispatch's Preflight) resolves the integration branch in this order: (1) `.claude-tweaks/policy.yml`'s `integration-branch` key, (2) an in-process cache, (3) `git rev-parse --abbrev-ref origin/HEAD`. This repo's `policy.yml` sets no `integration-branch` key, so step 3 is load-bearing. A fresh `git clone` of this repo in a cloud/Routine sandbox container does not set the local `refs/remotes/origin/HEAD` symbolic ref (confirmed: `git symbolic-ref refs/remotes/origin/HEAD` fails with "not a symbolic ref" immediately after clone, even though `git remote -v` shows a working `origin` and `git fetch origin main` succeeds). Step 3 therefore returns `null`, and `reconcile --json` short-circuits every check with `{"skipped":[{"check":"all","reason":"no-remote"}]}` on the very first run in a brand-new container — observed directly in a scheduled `/claude-tweaks:dispatch` Routine firing today. Running `git remote set-head origin -a` manually fixes it for the rest of that session, but every new sandbox container hits this fresh since nothing in provisioning sets it.

## Deliverables
1. Either: the project's Setup script (`scripts/claude-cloud-setup.sh`) or the SessionStart hook runs `git remote set-head origin -a` (or equivalent) whenever `origin/HEAD` is unresolvable, before `reconcile` or dispatch's Preflight can run.
2. Or: `resolveIntegrationBranch` falls back further before giving up — e.g. `git ls-remote --symref origin HEAD` (reads the remote's HEAD directly over the network, no local symbolic ref required) — when the local `origin/HEAD` ref is absent.
3. Either fix is acceptable; a decision between "fix provisioning" vs. "fix the resolver's fallback ladder" is itself part of this record's scope.

## Acceptance Criteria
1. A freshly cloned checkout (no local `refs/remotes/origin/HEAD`, no `integration-branch` key in `.claude-tweaks/policy.yml`) resolves a non-null integration branch via `reconcile --json`'s own checks, without a human manually running `git remote set-head`.
2. `reconcile --json` on such a fresh clone does not short-circuit with `{"skipped":[{"check":"all","reason":"no-remote"}]}` when a working `origin` remote exists and is reachable.
3. The fix is verified against an actual fresh clone (not just a checkout that already has `origin/HEAD` set from a prior fix), since that is exactly the gap this record reports.

## Release Note
Fixed: scheduled Routines and fresh cloud sessions no longer fail their first `reconcile`/dispatch Preflight pass with a spurious "no-remote" skip on a brand-new clone.
