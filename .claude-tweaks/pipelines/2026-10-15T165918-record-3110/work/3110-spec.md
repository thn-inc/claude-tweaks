# 3110: Make appendExclusion fail loud instead of clobbering an unreadable dispatch-exclusions.json

Origin: ledger resolve gate — #3104 build, controller ruling on the final whole-branch review, run 2026-10-10T190327-spec-3101-3102-3103-3104

Defer-reason: tangential

## Current State

`plugin/bin/lib/dispatch/exclusions.js`'s `appendExclusion(path, entry)` reads the current file through `readExclusions`. That function returns `[]` when the file is corrupt or unreadable, then writes `[...entries, entry]` back. If `dispatch-exclusions.json` goes bad partway through `plugin/skills/dispatch/queue-pull-script.md`'s passes (a torn non-atomic write, or a concurrent firing sharing the `os.tmpdir()` fallback path), the next `appendExclusion` silently drops every earlier pass's entries and leaves a valid, readable file. `/claude-tweaks:dispatch #N`'s unreadable-file probe (#3104, `plugin/skills/dispatch/exclusions-unreadable-report.md`) then reads `status: "ok"` and reports a really-excluded record as absent from the queue. #3104 closed that misreport for a file that is unreadable at read time, but not for this one.

## Deliverables

- `appendExclusion` reads through `readExclusionsStatus`. On `unreadable` it throws (or exits non-zero from the calling snippet) with the path and error, never rewriting the file from `[]`. On `absent` it creates the file, as today.
- The queue-pull passes that call `appendExclusion` surface that failure as a stop for the firing, instead of continuing with a partial exclusion list.

## Acceptance Criteria

- [ ] With a corrupt `dispatch-exclusions.json`, `appendExclusion` leaves the file byte-identical and raises an error naming the path.
- [ ] A test covers corrupt, absent and valid files for `appendExclusion`.

## Release Note

Dispatch no longer silently drops earlier exclusion entries when its exclusion list is corrupted mid-pull.
