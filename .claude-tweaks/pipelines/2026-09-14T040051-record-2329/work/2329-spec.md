# 2329: claim-targets.js: eventually-consistent read-back race + unverified-claim leak

Surface: infra

## Current State

Found during a pre-release whole-branch review of `plugin/bin/lib/claim-targets/claim-targets.js`
— all three confirmed still true at this shaping pass:

- **Read-back race** (~line 400): post-write verification (#2073) re-reads immediately with no
  retry/backoff (`if (!verifyClaimLanded(deps, repoSlug, issue, opts.runId, knownTip))`). On the
  contents-API transport `knownTip` is `null`, so the read-back hits GitHub's
  eventually-consistent contents API and can legitimately return the pre-write blob — a spurious
  exit 5 on a claim that actually landed. The file's own header already warns against
  eventually-consistent GitHub reads elsewhere.
- **Claim leak on abort** (~line 227, confirmed): `abort()` releases only `claimedThisRun`
  (`releaseClaimedThisRun(deps, repoSlug, opts.runId, claimedThisRun)`). `stopOrSkip(issue,
  'unverified', 'unverified', 5, {})` runs (confirmed, ~line 401) *before* the target is pushed
  onto `claimedThisRun` (the `claimedThisRun.push(issue)` call is one line after the verification
  check), so a target whose claim genuinely landed (just couldn't be verified back) leaks until
  TTL expiry with no `bot:in-progress` marker making it visible.
- **Stale doc comment** (~line 225, confirmed): `abort()`'s comment still enumerates only exit
  codes 3 and 4 ("`exitCode` is 3 for a `contested`/`inFlight` envelope, 4 for a `transient`
  one") — exit 5 (`unverified`) was added without updating it.

## Deliverables

- Add a bounded retry/backoff to the post-write read-back verification when `knownTip` is `null`,
  before declaring exit 5.
- Release (or otherwise make visible) the `unverified` target's claim on abort, not just
  `claimedThisRun`.
- Update `abort()`'s doc comment to include exit 5.

## Acceptance Criteria

- A simulated eventually-consistent stale read on the contents-API path no longer produces a
  spurious exit 5 within the retry window.
- An aborted run with an `unverified` target leaves that claim in a state a later run can
  detect/reclaim before TTL, not silently leaked.
- `abort()`'s doc comment lists exit codes 3, 4, and 5.
- `npm test` passes.

## Technical Approach

For the read-back race: wrap the `verifyClaimLanded` call (~line 400) in a small bounded
retry loop (a few attempts with a short backoff) specifically for the `knownTip === null` case —
the git-CAS path (`knownTip` set) already has a real tip to compare against and doesn't need
this, since a git-CAS success is immediately consistent. Only declare exit 5 after the retry
window is exhausted. For the claim leak: capture the `unverified` issue's claim state (the
context `verifyClaimLanded` already had before failing) and pass it to `abort()` so it can be
released or explicitly flagged alongside `claimedThisRun`'s own release — the goal is that a
genuinely-landed-but-unverified claim doesn't sit invisible until TTL; releasing it (so a later
run can pick it up cleanly) is the safer default over leaving it silently held. Update the
`abort()` doc comment in the same change.

### Key Files

- `plugin/bin/lib/claim-targets/claim-targets.js` — the read-back retry (~line 400), the claim
  leak fix (~line 227, `abort()` and the `unverified` stop path), and the doc comment update

## Gotchas

- The retry must be scoped to the `knownTip === null` (contents-API) path only — the git-CAS
  path's `knownTip`-based verification is already immediately consistent and doesn't need
  (or benefit from) a retry; adding one there would just slow down every claim for no
  correctness gain.
- Releasing an `unverified` claim on abort must not race with the claim that write actually
  produced — verify the release targets the same claim identity (`repoSlug`, `issue`, `opts.runId`)
  the write itself used, so a genuinely different run's claim on the same issue is never touched.
