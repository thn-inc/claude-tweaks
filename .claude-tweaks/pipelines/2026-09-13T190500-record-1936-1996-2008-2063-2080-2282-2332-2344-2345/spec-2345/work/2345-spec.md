# 2345: Subagent Contract: a verdict or findings list from an agent that made zero tool calls is a failed dispatch, not evidence

Surface: infra

## Current State

`_shared/subagent-output-contract.md` is the dispatch-correctness contract: minimal input, the
four-word status line, the A/B/C output templates, model-profile selection, and the third-party
exemption. Every mechanical check it defines is a check on the **shape** of the reply.

In one seven-spec run, a review lens agent (lens 3f, first dispatch) returned six findings, each
citing a file and line numbers, after **zero tool calls** — it read nothing. Its status line was
well-formed and its output template was filled in correctly, so every check the contract defines
passed. It was caught only because the orchestrator happened to inspect the agent's tool-use count
by hand, and re-dispatched a fresh agent (3f-B). The contract that exists specifically to make N
agents independent evidence rather than N echoes has no rule that would have caught it.

The principle is already stated elsewhere in the project, just not where dispatch correctness is
defined: CLAUDE.md's test-count rule ("never accept a subagent's self-reported pass/fail numbers as
a run … a fabricated report is indistinguishable from load here"), and a standing memory entry
recording that agents fabricate fix reports with zero diff. Neither reaches a dispatch site, because
every dispatch site inherits its discipline from the contract file, not from CLAUDE.md's prose.

`subagent-stop.js` already reads the dispatched agent's own transcript (`agent_transcript_path`) to
grade the status line, so the tool-use count for a final reply is derivable at the same seam — this
check need not stay a manual orchestrator habit.

## Deliverables

- State the rule in `_shared/subagent-output-contract.md`: a verdict, findings list, or
  pass/fail claim from an agent whose transcript contains zero tool calls is a **failed
  dispatch**, never evidence. The caller re-dispatches a fresh agent (never resumes the same
  one — the 529/stall precedent: 0/5 resumes succeeded) and never aggregates the reply.
- Put it in the contract's aggregation guidance so every dispatch site enumerated in CLAUDE.md's
  Subagent Contract section inherits it by citation, with no site restating it (CLAUDE.md's
  cross-reference rule). Extend the Exemption section's caller-side normalization sentence to
  name it explicitly: a third-party agent is exempt from the contract, but the caller still
  rejects a zero-tool-use verdict at the boundary.
- Add the mechanical assist at the `subagent-stop.js` seam: count tool calls in the graded
  agent transcript and log a distinct event kind (e.g. `zero-tool-use-verdict`) when a final
  reply carries a verdict shape with no tool call behind it, so the failure is visible in
  `events.jsonl` rather than depending on an orchestrator noticing. Add the kind to
  `bin/friction-events.js` and `reflect/full-mode.md`'s Friction lens vocabulary block.

## Acceptance Criteria

1. `_shared/subagent-output-contract.md` states the zero-tool-use rule, what makes it a failed
   dispatch, and that the remedy is a fresh dispatch rather than a resume.
2. Every dispatch site listed in CLAUDE.md's Subagent Contract section reaches the rule by citation;
   a repo-wide grep finds no site restating it inline.
3. A fixture transcript whose final assistant turn carries a well-formed status line and a findings
   table, with zero tool-use blocks, logs a `zero-tool-use-verdict` event; an otherwise identical
   transcript with one tool-use block logs nothing. Both directions asserted in
   `tests/bin-lib/hooks/`.
4. `node --test tests/reflect-friction-lens-vocab.test.js` passes with the new kind, and `npm test`
   passes.

## Non-Goals

- Grading intermediate turns. The rule applies to the reply the caller consumes, not to every turn a
  long-running dispatch produces (that scoping question is #2041's).
- Any judgment about *how much* tool use is enough. Zero is the only threshold this record sets.

## Technical Approach

Two coupled changes, per the Deliverables above:

1. **Contract text.** Add the zero-tool-use rule to `_shared/subagent-output-contract.md`'s
   aggregation guidance — worded as a hard rule (a zero-tool-use verdict is a failed dispatch,
   never evidence; remedy is a fresh dispatch, never a resume of the same agent). Extend the
   Exemption section's existing caller-side normalization sentence to state explicitly that this
   check applies at the boundary even to a third-party agent otherwise exempt from the contract's
   other structural requirements.
2. **Mechanical assist.** In `bin/lib/hooks/subagent-stop.js`, at the same seam that already reads
   `agent_transcript_path` to grade the status line, count tool-use blocks in the final graded
   turn. When the count is zero and the reply shape carries a verdict/findings/pass-fail claim,
   log a `zero-tool-use-verdict` event (distinct kind, alongside the existing `contract-violation`
   kind) rather than silently passing shape-only checks. Wire the new kind through
   `bin/friction-events.js`'s aggregation and `reflect/full-mode.md`'s Friction lens vocabulary
   block, mirroring how the existing `contract-violation`/`variant` kinds are already wired.

### Key Files

- `plugin/skills/_shared/subagent-output-contract.md` — add the zero-tool-use rule to the
  aggregation guidance and the Exemption section
- `plugin/bin/lib/hooks/subagent-stop.js` — count tool-use blocks in the graded transcript, log
  `zero-tool-use-verdict`
- `plugin/bin/friction-events.js` — aggregate the new event kind
- `plugin/skills/reflect/full-mode.md` — Friction lens vocabulary block, new kind name
- `tests/bin-lib/hooks/` — new fixture-transcript test (zero-tool-use vs. one-tool-use cases)
- `tests/reflect-friction-lens-vocab.test.js` — cover the new kind name

## Gotchas

- This rule targets the *final* reply the caller consumes — do not apply it to intermediate
  turns of a long-running dispatch (explicitly out of scope per Non-Goals; #2041 owns that
  broader scoping question).
- Don't invent a nonzero tool-use threshold ("at least N calls") — this record sets a strict
  zero/nonzero line only; anything more nuanced is future scope, not this record's.
- The contract-text change and the mechanical-assist change are both required by the Acceptance
  Criteria — landing only the mechanical assist without updating the contract text leaves every
  dispatch site's own prompt-level discipline unchanged, and landing only the contract text
  without the hook change leaves the failure mode dependent on manual orchestrator vigilance
  again, the exact gap this record exists to close.
