# 2332: wrap-up/pack.js recordLabels: unbounded concurrent gh fan-out, untested for partial failure

Surface: infra

## Current State

Found during a pre-release whole-branch review of `plugin/bin/lib/wrap-up/pack.js`. `recordLabels`
(confirmed, line 397) changed from a sequential loop to an unbounded `Promise.all` fan-out of
`gh issue view` calls, with no test added for the concurrency or partial-failure semantics.

`tests/bin-lib/wrap-up/pack.test.js`'s only addition in this range is a
`resolveRecords`/`headerRecords` export check — nothing pins that a mid-list `gh` failure still
surfaces correctly, or that N is bounded (an unbounded fan-out over a large record list could hit
`gh`'s own rate limiting).

## Deliverables

- Add a test covering a mid-list `gh issue view` failure in the `Promise.all` fan-out — confirm
  the failure surfaces (doesn't get silently swallowed) and confirm what happens to the other
  in-flight calls.
- Consider whether the fan-out needs a concurrency bound for large record lists.

## Acceptance Criteria

A test exists that fails a middle call in the fan-out and asserts the overall behavior (error
propagation or partial-result handling, whichever is intended) explicitly.

## Technical Approach

Read `recordLabels`'s actual current behavior first (line 397's surrounding function) to
determine what it's *supposed* to do on a partial failure — `Promise.all` itself rejects the
whole batch on the first rejection, so unless the mapped callback already catches per-record
errors internally, a single `gh issue view` failure currently aborts the entire `recordLabels`
call for every record, not just the failing one. Write a test with a fake `gh` runner that fails
on (e.g.) the third of five record lookups and assert whichever behavior is actually intended:
either the whole call rejects (document that this is deliberate, given the caller's own
error-handling expectations) or partial results are still usable (in which case the current code
needs an `allSettled`-style fix, not just a test). For the concurrency-bound question: check
whether this codebase's existing gh-api-module-pattern convention or a sibling call site already
establishes a bound for similar fan-outs (e.g. a `concurrency` option, or a batch-size cap) and
apply the same convention here if large record lists are a realistic scenario for `wrap-up`'s own
callers (multi-spec runs with many records).

### Key Files

- `plugin/bin/lib/wrap-up/pack.js` — `recordLabels` (line 397), possibly needs an
  `allSettled`-style rewrite or a concurrency bound depending on the investigation above
- `tests/bin-lib/wrap-up/pack.test.js` — add the mid-list-failure test

## Gotchas

- Don't assume `Promise.all`'s all-or-nothing rejection semantics are a bug — they may be the
  deliberate, correct behavior for this call site (a wrap-up pack build that can't tolerate a
  partial label set). Read the surrounding code and its caller's own error handling before
  concluding a fix (vs. just documenting+testing the existing all-or-nothing behavior) is needed.
- If a concurrency bound is added, verify it doesn't reintroduce the sequential-loop performance
  regression this `Promise.all` change was presumably meant to fix in the first place — a bound
  should cap peak concurrency, not collapse back to strictly sequential.
