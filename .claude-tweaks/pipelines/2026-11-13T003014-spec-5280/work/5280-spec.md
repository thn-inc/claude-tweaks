# 5280: review: a visual-review or design-wrapper result that arrives after its wait bound is never routed

Surface: backend

**Related:** #4663 (same late-result class for review Step 3's lens coordinator — kept separate), #4557 (the progress-extension rule this reuses), #4831, #4959, #3758, #5076 (open records editing the same wait-rule paragraph or the same rail-tight files — see Gotchas)

## Current State

`_shared/subagent-dispatch-core.md`'s nested-`Agent` rule gives every dispatched agent's children one 60-wait window (`sleep 20` × 60, 20 minutes) per wave. At that bound a **read-only** unit (a lens, a single read, a judge) is self-judged in-session and its child abandoned; "a child result that arrives after its unit was self-judged is ignored; it never changes a verdict already reached". Only a **write-capable** child gets more time: #4557's worktree progress probe grants another 60-wait window while the child keeps changing its worktree, up to 3 windows (60 minutes) per wave. The same rule is restated in `dispatch/task-prompt.md` (both templates' Async-wait discipline item), `dispatch/express-prompt.md`, and `flow/context-handoff.md`'s continuation template; `tests/foreground-execution-instruction.test.js` pins the "ignored; it never changes a verdict" sentence.

`/claude-tweaks:review` Step 6 (visual-review, full mode) and Step 6.5 (design-wrapper review, including the wrapper's Step 3.7 `impeccable-finish-reviewer` and Step 3.8 craft-critic dispatches) are read-only, so they fall in the first-bound self-judge class. Unlike a lens, they drive a browser against a live dev server and gate a merge precondition: CLAUDE.md's rendered-UI check before merge. A busy machine taking screenshots at three viewports exceeds 20 minutes, and in the reported run (plugin 6.165.0) review logged `Steps 6 / 6.5 (degraded): … agents silent at the 60-wait bound; abandoned`, judged them from earlier QA screenshots, and continued to polish. The agents later returned five real findings (legend overflow at 390px, an info icon wrapping from its label on touch, an ambiguous copy sentence, identical accessible names on every row's select, a stale error line on finished items). Nothing routed them to `staged/` or the Review Console; they surfaced only by chance in a report to a parent that had stopped waiting, costing an extra fix agent and a third integration-branch merge.

Both units leave observable progress on disk: visual-review writes `.claude-tweaks/artifacts/screenshots/browse/<session>/NN_*.png` (`visual-review/browser-review.md`), design-wrapper review writes under `.impeccable/review/` (`design-wrapper/modes/review.md`).

Decision (#5280 brainstorm, 2026-11-13): **extend, then stage**. Re-dispatching once before degrading was rejected: an abandoned child cannot be stopped (`TaskStop` refuses a nested child), so a re-dispatch puts two browser agents on the same busy dev server — the load that made the first one slow — and still drops the first child's result.

## Deliverables

1. **Merge-gating read-only units get the progress extension.** `_shared/subagent-dispatch-core.md` defines a merge-gating read-only unit as one whose result feeds the rendered-UI check before merge and whose prompt names an artifact directory it writes to — today review Step 6's visual-review and Step 6.5's design-wrapper review (and that wrapper's Step 3.7/3.8 dispatches). At the bound, before self-judging such a unit, probe its named artifact directory read-only (a file listing with sizes and mtimes, hashed, against the previous probe taken right after launch). While it changed during the last window, log one wait line and grant one more 60-wait window; stop when a whole window passes with no change or at the 3-window (60-minute) ceiling, naming which fired — the same vocabulary, log line shape and ceiling as #4557's worktree probe. Every other read-only unit keeps the first-bound self-judge unchanged.
2. **A late result from a merge-gating unit is staged, not ignored.** When such a unit was self-judged and its result arrives afterwards (while the agent is still in a later step, or on a re-wake after its final reply), the agent stages the result's findings as one item in `{run-dir}/staged/` via `bin/stage-item.js` and logs a `STAGED` decision line naming that file, so the Review Console shows it as a row. It never changes a verdict already reached, and a re-woken agent still repeats its whole final reply (#3722). The "ignored" rule stays for every other unit.
3. **No staging into an archived run.** When the run dir is no longer active (closed or archived — `stage-item.js` exits 3 on a missing or unanchored run dir, and a write after archival recreates the dir), the agent writes nothing there and instead names the late result's findings in its reply.
4. **Every restatement carries the same rule.** `dispatch/task-prompt.md` (both templates), `dispatch/express-prompt.md`, and `flow/context-handoff.md`'s continuation template carry the new facts — in full, or as a short pointer to the shared file where a full restatement would breach the read rail (Gotchas). The shared file names review Step 6 and Step 6.5 as the current merge-gating units, so `review/code-mode-steps.md` needs no edit.
5. **The pre-merge rendered-UI check stays honest.** `_shared/subagent-dispatch-core.md` states that a merge-gating unit self-judged at a bound (from earlier QA screenshots or otherwise) does not satisfy the rendered-UI check before merge, and is surfaced as an explicit decline — the same posture the check already takes for one that silently self-skipped.

## Acceptance Criteria

4. With the run dir archived or closed, the late result writes nothing under `.claude-tweaks/pipelines/` and its findings appear in the agent's reply.
5. `_shared/subagent-dispatch-core.md` names review Step 6 and Step 6.5 as merge-gating units and says a self-judged one does not satisfy the rendered-UI check before merge; a test in `tests/foreground-execution-instruction.test.js` pins both facts.
6. Every edited file stays under `RAIL_BYTES` (`plugin/bin/lib/skill-audit/budgets.js`); the skill-audit rail check passes.
7. `npm test` passes.

## Release Note

Wait longer for visual and design review agents while they are still working, and route any findings they return after the wait to the Review Console instead of dropping them.

## Technical Approach

Extend the existing #4557 paragraph in `_shared/subagent-dispatch-core.md` rather than adding a parallel mechanism: today it is keyed on "write-capable child + worktree"; add a second probe target, "merge-gating read-only unit + named artifact directory", reusing the window/ceiling/log vocabulary. The probe is read-only: e.g. `find "{artifact-dir}" -type f -exec stat …` piped to `git hash-object --stdin`; a failed probe counts as no change (same as the worktree probe), and a missing directory counts as unchanged. The dispatching agent passes the artifact directory in the child's prompt (visual-review's `<session>` screenshot dir; design-wrapper's `.impeccable/review/`), so the probe target is never re-derived.

For staging, pick the staged id prefix at build time: reuse `visual-review-` (already in `CANONICAL_PREFIXES`) if its Review Console section fits late design-wrapper findings too, otherwise add a `review-late-` prefix via the `review-console-section-addition` project skill (every code and prose site, plus its pins). Use `stage-item.js --allocate` so two late results in one run never clobber each other.

Edit the four restatements in the same commit as the shared file; `dispatch/task-prompt.md`'s fenced blocks are `bin/dispatch-prompt.js`'s template source, so no code change is needed there.

## Original request

review: a visual-review or design-wrapper result that arrives after its wait bound is never routed

**Summary:** Once review abandons its visual-review (Step 6) or design-wrapper review (Step 6.5) agent at the 60-wait bound and logs it STAGED (degraded), a result that agent sends later is ignored. A real rendered-UI finding is dropped, and no Review Console row ever shows it.

**Kind:** Defect

**Affected component:** /claude-tweaks:review Steps 6 and 6.5 (visual-review and design-wrapper dispatch), with `_shared/subagent-dispatch-core.md`'s "Ignore a late result" rule

**Repro steps:**
1. Run `/claude-tweaks:flow` on a web-surface record, so review's Step 6 (visual-review) and Step 6.5 (design-wrapper review) dispatch agents.
2. Let either agent take longer than one 60-wait window (20 minutes). A live dev server on a busy machine with screenshots at three viewports is enough.
3. Review logs `STAGED … Steps 6 / 6.5 (degraded): … agents silent at the 60-wait bound; abandoned`, judges them from earlier QA screenshots, and continues to polish.
4. The agents finish later and return findings.

**Expected vs. actual:**
Expected: a late result from a unit that gates a merge precondition (the rendered-UI check before merge) is staged into `staged/` when it arrives, or review re-dispatches that unit once before degrading it. The Review Console then shows its findings.

- identical accessible names on every row's select;

They surfaced only because the late reviewer listed them in a report to a parent that had already stopped waiting. The pre-merge visual check stayed unsatisfied until the top-level session asked the human. One extra fix agent and a third integration-branch merge followed.

**Definition:** Needed — choose between staging a late gating result when it arrives, and re-dispatching the unit once before degrading it
