# 4798: Surface a partial Step 4.0b parent-close instead of recording a clean ran

Origin: /claude-tweaks:release v6.159.0 release-gate review (run 2026-10-31T203907-release-standalone)

Defer-reason: pre-existing-outside-diff

## Current State

When the reconcile post-merge pass (`plugin/bin/lib/reconcile/post-merge.js`, around line 419) leaves a parent unclosed in Step 4.0b (a `gh-failed` or `internal-error` skip, e.g. the close comment posted but the close failed), it still writes a clean `ran` entry carrying only `parentsClosed`. The skips land only in `decisions.md` prose, so `hooks.js` counts the run as `postMergeRan` and SessionStart never reports the parent left open. Found by the v6.159.0 release-gate review (lens 3c, tiebreak confirmed low).

## Deliverables

- [ ] Record Step 4.0b skips that left a parent open as a structured field on the post-merge entry.

- [ ] Have SessionStart count and surface those entries rather than treating them as a clean `ran`.

## Acceptance Criteria

A test drives Step 4.0b to a `gh-failed` skip and asserts the entry is not a clean `ran` and that the SessionStart summary names the parent.

`npm test` passes.

## Decisions

Answers the plan-review questions (comment 6571192593).

- **Q1 — Decision: Reading A.** The Acceptance Criterion stands as written: add one end-to-end test that sends a real `postMerge` run (a fake `closeParents` returning a `gh-failed` skip) through `hooks.js reconcile-background` into SessionStart, and asserts the rendered summary names the parent (`#100 (gh-failed, …)`). Seam tests may stay as well, but they do not satisfy the criterion on their own.
- **Q2 — Decision: Reading B, reported on its own line.** A Step 4.0b step-wide skip (`unreadable-policy`, `invalid-risk-floor`) on a merge whose Step 4.0 closing set is empty does not count as a parent left open and must not render under "left parent record(s) open". Surface it on its own separate line in the summary (the unreadable/invalid policy is still worth reporting). A step-wide skip with a non-empty closing set still counts as partial.
- **Decided (round 2), Q3: Reading B** (answers comment 6587848324). The "nothing to close" condition tests the effective closing set, `closingSet` minus `closedAfterWindow`, not the raw `closingSet`. A PR whose `Fixes` records all closed after the window has nothing left to close.
- **Decided (round 2), Q4: Reading B.** Any step skip that names no parent and no record goes on the separate line whenever the effective closing set is empty. This is not limited to `unreadable-policy`/`invalid-risk-floor`, so a skip kind added later needs no new ruling.
- **The whole family, so the build doesn't have to ask again:** `stepSkips` are reported in every mode, including merge mode and on a failed entry; no mode or outcome drops them. A plan task that changes this reporting carries `Review risk: high`.
- **Decided (round 3), Q5: Reading A** (answers comment 6600420905). When `processRun`'s marker write fails and the entry becomes `skipped / marker-write-failed`, that entry still carries the run's `stepSkips` and `parentFailures`, and every surface reports them on it: merge mode, the background summary, SessionStart, and the reconcile CLI summary. The shape change is additive: new fields on an existing entry, and existing readers ignore them. The family rule "no mode or outcome drops stepSkips" therefore holds with no exemption. If any other replacement or short-circuit entry in `post-merge.js` drops them the same way, it gets the same treatment, with no new ruling needed.
- **Plan marker:** Task 5 carries `Review risk: high`.
