# 5996: Pick an implementer's work profile from its record in code

Surface: backend
Risk-flags: public-contract

## Overview

Adds functions, in code, that picks a build's implementer work profile from its record: a `size:low` record with one or two Key Files gets Fast, every other record Standard. A second function returns the profile one step up, used once when the first attempt fails. A policy value chooses between this rule and today's behaviour, and a CLI exposes both functions to skill prose. The driver (#5997) and the standard lane's task loop (#5999) consume it; this record changes no build by itself.

Today the standard lane picks the implementer's profile from `size:` alone, in prose (`low` → Fast, `medium` → Standard, `high` → Capable), and the driver always launches its implementer on `express-driver-models.implementer` (Standard). Between 8 and 18 November 2026, Opus implementers cost about $3 per standard-lane run, and of 43 tasks a walker sent to Haiku, 13% needed a fix round against 51% for Sonnet at the same average output size. The record rule moves `size:high` records to Standard and puts small, narrow records on Fast in both lanes.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Changing any build's profile. The driver and the standard lane switch to this function in their own records; until they land, nothing reads the policy value.
- An effort per attempt. That is #6002, blocked by #5941 and #5942.
- Retrying in either lane. This record supplies the step-up function only.
- Frontier. No rule here returns it, and a step up from Capable returns `null`.
- Per-task `**Role:**` markers and the `profile=` build token. They keep overriding whatever the record rule returns; the consuming records state the precedence.
- Changing `express-driver-models` or the shipped profile table.

## Release Note

Added a setting that picks a build's implementer model from the record's size and file count, so small, narrow changes run on the cheapest model and no record defaults to the most expensive one.

## Technical Approach

The rule is a pure function so both lanes read one decision: the driver calls it in process with the labels and Key Files it already holds, and the standard lane's prose calls the CLI on the materialized spec. Under `lane` the function reproduces the standard lane's current prose mapping exactly, so moving that prose onto the CLI later is behaviour-neutral; the driver's `lane` behaviour (its `express-driver-models` entry) stays in `launch.js`, because under `lane` the driver record does not call this function at all. The value is read per run (not `policyOnly`), so one run can try `record` without changing the project's file. See Decision Rationale.

## Decision Rationale

- **Why a size-and-file-count rule:** a `size:low` record touching one or two files is the shape the walker already judged mechanical when it chose Haiku, and those tasks needed fewer fix rounds than Sonnet's. Three or more Key Files on a low record means integration across files, which stays on Standard.
- **Why `size:high` goes to Standard, not Capable:** the design's expected effect is that Opus implementers (about $3 per run) fall to near zero. A failed attempt still reaches Capable through the step-up, once.
- **Why the default is `lane`:** every new behaviour in the pipeline-economy design ships off by default and this repository opts in first. A default changes only after 20 runs with the value on show the quality guards no worse.
- **Why one key for both lanes, not one per lane:** the rule is the same decision; one switch keeps a factory or a project from running two different rules by accident. A run can still try it alone through its `config.yml`.
- Rejected: deriving the profile from `risk:` as well. Risk decides how much checking a change gets, not how hard it is to write; the effort record uses risk for the starting effort instead.
