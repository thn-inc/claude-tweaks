# 5219: Driver settle for standalone runs, ceilings, and the usage page

Surface: backend

## Overview

A run started from a terminal or the hub has no dispatch session around it, so nothing settles its stops: the express lane leaves that to `dispatch/settle-and-merge.md`'s Settle and the re-bind in `dispatch/SKILL.md`'s express paragraph. This unit gives `drive.js` its own settle, in code, with no judgment call, implementing the design's "When a run stops" table (`docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`). It also settles the two per-record ceilings and writes the driver's usage page.

Discarding partial work on escalation is deliberate: an express-sized change is cheap to redo, and a standalone run that leaves a claimed record and an orphaned worktree behind is the costlier failure. Dispatch's Settle `failure-check` judgment and its tombstone that closes the PR are not carried over. When the driver is later started from `/claude-tweaks:dispatch` (a later phase of the design), the dispatch session settles instead; this unit adds an explicit flag by which a caller turns the driver's own settle off, default on.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Any model call in a settle path, and any judgment about whether a failure is retryable or a PR should be closed. The PR-closing tombstone and `failure-check` are not carried over.
- Merging, marking a PR ready, or any Phase 2 behavior.
- Entering the driver from `/claude-tweaks:dispatch` (Phase 3): this unit only provides the flag that the later entry will pass.
- Changing `express-lane.js`, `release-claim.js`, `claim-targets.js` or the prose express lane.
- Reading the ceiling policy values or passing them to the worker: the run-loop unit already does that. This unit settles what happens when a ceiling is reached.
- Pinning `docs/driver.md`'s text with any test.

## Current State

- `plugin/bin/lib/driver/run.js` (added by the prerequisite unit) calls `plugin/bin/lib/driver/steps.js` per record and, on a stop, emits its event and leaves the claim, worktree and run directory as they are. This unit hooks `settle.js` in at that point.
- `express-lane.js escalate --run <dir> --issue <n> --reason <failing-test|out-of-bounds|gate-denial|express-error> --detail-file <file>` writes the escalation line to `decisions.md` and exits 1 without writing when `run-state.json` already records the PR (`plugin/bin/lib/express/cli.js:66`, `plugin/bin/lib/express/cli.js:247`). The reason set is closed.
- `express-lane.js check` writes the escalation line itself on every escalating branch, and reports a failed append as `logged: false` in its envelope (`plugin/bin/lib/express/cli.js:308` to `plugin/bin/lib/express/cli.js:338`).
- `plugin/bin/release-claim.js <issue> --run <run-dir> --reason <reason>` strips `bot:in-progress` by default, never deletes a successor's claim (an ownership check; exit 4 when the claim is held by another run, exit 3 when already released) and strips `auto:*` grants only with `--remove-grants` (header comment, `plugin/bin/release-claim.js:1`).
- Outcome rules to carry: `_shared/express-lane.md` Escalation (escalation only before the push; a non-zero exit of `check` or `escalate` is `blocked`, never retried) and Outcomes (`blocked` after the push leaves the PR open; `pending-review` leaves the PR in draft for a human). The express lane has no release step for `pending-review`; a claim for a parked `pending-review` run lapses by its TTL (`plugin/skills/dispatch/reporting.md`, the `pending-review` paragraph).
- The `bot:blocked` label exists in the repository. `tests/helpers/git-fixtures.js` builds real temporary git repositories for tests.
- `docs/REGISTRY.md` maps each documentation page to the code it covers; `docs/driver.md` and `plugin/bin/lib/driver/settle.js` do not exist yet.

## Deliverables

- [ ] `plugin/bin/lib/driver/settle.js`, called by `run.js` when a record stops, implementing the table below with no judgment call.
- [ ] An explicit flag on `drive.js`, `--no-settle`, by which a caller turns the driver's own settle off; default on. With it set, a stop makes none of the settle calls, the final event's `settle` field is `left-to-caller`, and its `stop` object (class, step, `pushed`, reason, detail, and `check`'s `logged` value) carries what the caller needs to settle without re-deriving the classification. `settle` is `none` when the stop's row below has no calls, and `done` when the settle ran.
- [ ] Ceiling stops: a worker ended by either ceiling (envelope reasons `wall-clock-ceiling` and `spend-ceiling` from the launcher unit) is settled as a pre-push failure by the rules below.
- [ ] `docs/driver.md`: a usage page covering how to run it, the outcome words, the event line fields, the settle table (naming `settle.js`'s table as the source of truth) and the worker rights, plus its row in `docs/REGISTRY.md`. The page is documentation, not a contract.
- [ ] The design document's settle table (`docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, "When a run stops") is amended in the same change to match the table below: the contested-claim row, and no release call when no claim was obtained.
- [ ] `tests/bin-lib/driver/settle.test.js`, sized like the `tests/bin-lib/express/` suites, over a fake runner plus one real-git test for the worktree and branch removal.

The settle table (**Closed rule**: these stops are the complete set the settle knows; a stop outside the list is settled as `blocked` and the final event names it as unclassified; a plan review that finds another unlisted stop adds its row as a plan amendment, not as a `needs-human` gap). The row is chosen from the final event's `stop` object that the run-loop unit emits: `class` is `refused`, `claim`, `pre-push`, `blocked` or `none`, and `pushed` is true from the moment the push succeeds. `blocked` covers every stop after the push and a non-zero exit of `check` or `escalate`. As a safety net, a stop classed `pre-push` is settled by the `blocked` row when `pushed` is true or `run-state.json` records a PR, whichever is set; this covers a failed `gh pr create`, where the branch is pushed and no PR is recorded, and a `record-pr` that failed after the PR was created.

| Stop | Settle calls, in order |
|---|---|
| `refused`: not eligible, not admitted, routing off, unreadable record | None. Nothing is written; the event names every reason. |
| `claim`, and `claim-targets.js` reports the record held by another run or in flight (its exit 3) | None. The driver never held the claim, and a label on the record would hide the other run's live claim. The outcome is `blocked` and the event names the exit code. |
| `claim`, any other non-zero exit of `claim-targets.js` (4 transient, 5 unverified write, 6 branch uncreatable, 7 permission denied), or a run directory that could not be minted | 1. one comment on the record naming the step and exit code; 2. `bot:blocked` added to the record. No release call: no run directory exists, and `release-claim.js` needs `--run`; a claim that may have been written (exit 5, or a claim held when the mint failed) lapses by its TTL, and the event says so. |
| `pre-push`: any stop before the push (`express-escalated`) | 1. `express-lane.js escalate` with the reason and a detail file, unless `check` already wrote the line for this stop (its envelope said `logged: true`); 2. one comment on the record naming the reason; 3. `release-claim.js`; 4. `git worktree remove --force` of the record's worktree, only when `stop.created.worktree` is true; 5. `git branch -D` of its local branch, only when `stop.created.branch` is true. The run directory stays: it holds the escalation line. If call 1 itself fails, calls 4 and 5 do not run and the remaining calls are those of the `post-push` row, so no work is discarded without an escalation on record. |
| `blocked`: a stop after the push, or a non-zero exit of `check` or `escalate` | 1. one comment on the PR, only when a PR exists; 2. one comment on the record, both naming the failed step; 3. `bot:blocked` added to the record; 4. `release-claim.js` (no `--remove-grants`). The draft PR, branch and worktree stay. |
| `none` (`pending-review`) | None. The PR stays in draft for a human; the claim is left untouched and lapses by its TTL, as for the prose lane. |

## Acceptance Criteria

1. An escalation before the push, where `check` did not write the line, produces in order: the `express-lane.js escalate` call, one comment on the record naming the reason, the claim release, the worktree removal and the local branch deletion; afterwards, in the real-git test, no worktree for the record and no local branch for it exist. When the stop came from a `check` verdict whose envelope said `logged: true`, the `escalate` call is skipped and the rest runs in the same order; with `logged: false`, `escalate` is called with `check`'s reason and detail. If the settle-time `escalate` call exits non-zero, the worktree removal and the branch deletion do not run, and the record is settled by the `blocked` row (comment, `bot:blocked`, release); a test pins this, and it is the one exception to criterion 7's rule that settle calls continue after a failure.
2. A `blocked` stop after the push produces one comment on the PR and one on the record naming the failed step, adds `bot:blocked`, releases the claim, and removes neither the PR, the branch nor the worktree (no `gh pr close`, no `git worktree remove`, no `git branch -D` in the recorded calls). The same holds for a failed `gh pr create` where the branch is pushed and no PR is recorded (the comment goes to the record only), and for a `record-pr` failure after the PR was created: in both, the worktree and branch are kept.
3. A refusal before the claim makes no forge call that writes (the fake runner records no `gh` call other than reads), and the same holds for a claim refused as held by another run. A failed claim with another exit (4, 5, 6, 7), and a failed run-directory mint, make exactly two writes, the record comment and `bot:blocked`, and no `release-claim.js` call. A pre-push stop whose `stop.created` says this run created neither the worktree nor the branch (for example a leftover refused at the worktree step) removes nothing: no `git worktree remove` and no `git branch -D` is recorded, and a test pins it.
4. With `--no-settle`, a stop makes none of the settle calls, and the final event has `settle: "left-to-caller"` and the structured `stop` object. A stop whose row has no calls has `settle: "none"`.
5. A worker that reaches the wall-clock ceiling (the launcher's `timeout` envelope, reason `wall-clock-ceiling`) is settled as an escalation with reason `express-error` and a detail naming the wall-clock ceiling and its value. A worker stopped by an effective spend ceiling (the launcher's `fail` envelope, reason `spend-ceiling`) is settled the same way, the detail naming the spend ceiling. An overspend only reported after a normal return (`spendOverrun: true`, status `ok`) settles nothing, the run continues to the commit step, and the overspend is named in the final event.
6. No settle path calls a model: `settle.js` does not require `plugin/bin/lib/driver/worker.js` or `roles.js` (asserted on the module's own text with the comment stripper `.claude/skills/bin-source-scan-conformance` names), and a test's fake launcher is never called during settle.
7. A settle call that itself fails does not stop the remaining settle calls (except as criterion 1 states) and is never retried: each failure is an event line with status `fail` and its own `step`, and the final event lists the failed settle steps. A claim release that exits 3 or 4 (already released, or held by another run) is not a failure.
8. A `none` stop makes no settle call. A stop whose class is outside the table's rows is settled by the `blocked` row and named unclassified in the final event.
9. `docs/driver.md` exists, has a row in `docs/REGISTRY.md`, and no test reads it. The design document's settle table is amended as the deliverable states.
10. Comment hygiene: every comment, and the detail file passed to `escalate`, is built from fixed templates filled with the step name and outcome word (closed sets), the reason (a closed set) and a detail reduced as follows: only `A-Za-z0-9 .,:;_()/-` characters, at most 200 characters, `@` replaced by `at `, every absolute path (a leading `/` followed by a segment, or a drive-letter path) replaced by `<path>`, and every token-shaped string (`gh` token prefixes, 40-character hexadecimal runs) replaced by `<redacted>`. A test feeds a hostile detail (an `@` mention, a markdown link, a home-directory path and a token) and asserts none survives.
11. No repeat of a driver escalation. The comment the escalation row posts on the record ends with the fixed marker `<!-- express-driver: escalated -->`. `plugin/bin/lib/driver/admission.js` takes a caller-supplied fact saying whether the record's comments carry that marker in a comment from a trusted author (the same comment-trust check `plugin/bin/lib/express/sampling.js` applies to its review marker comments), and refuses such a record with its own exported reason, `already escalated by the driver`; `plugin/bin/lib/driver/run.js` supplies the fact from the record fetch it already makes. Tests: a record with the marker from a trusted author is refused with that reason and the test goes red when only that gate is removed; the same marker from an untrusted author does not refuse; an unreadable comment list fails closed. A human removes the comment to let the driver take the record again, and `docs/driver.md` says so. No label is added, and neither the prose express lane nor the standard path reads the marker.

## Release Note

Added standalone settle behavior to the pipeline driver: a stopped run now releases its claim and cleans up or labels the record by fixed rules, and a usage page explains how to run it.

## Technical Approach

- **Table in code.** `settle(stop, deps)` maps a stop (`step`, `class`, `pr`, `check` envelope, `reason`, `detail`) to the ordered call list above and runs it over the injected runner, emitting one event line per call through `events.js`. The mapping is a data table plus one function; there is no branch that depends on content judgment.
- **Which stops are which** (the run-loop unit's outcome table is the source; this is what each row consumes). `pre-push`: red test run (`escalate` reason `failing-test`), `check` verdict of `escalate` (its own reason), worker `fail`, `timeout` or ceiling stop, no changed files, commit failure, a refused scope file, a HEAD mismatch or a failed push (reason `express-error`, detail naming the cause). `blocked`: a failed `gh pr create`, `record-pr` or `set-config.js` call, and a non-zero exit of `check` or `escalate`. `none`: green CI, a CI state other than green, or a failed summary entry (all `pending-review`). `claim`: any non-zero exit of `claim-targets.js`, or a failed run-directory mint. `refused`: an admission, eligibility or fetch refusal.
- **Where the settle reads its inputs.** The worktree path and branch name come from the stop object and `run-state.json`'s recorded worktree (the run loop stamped it with `record-worktree`); the PR number from the stop object, else `run-state.json`. Comments are posted with `gh issue comment` and `gh pr comment` and the label with `gh issue edit --add-label`; the driver requires `gh` (an absent `gh` is a refusal at start, exit 2 in the run-loop unit), so there is no MCP path.
- **Comment hygiene.** The repository is public and the detail text comes from untrusted worker, test and `check` output, so criterion 10 reduces it to a small character set, neutralizes mentions and strips paths and tokens; the fixed templates carry everything else. `.claude/skills/fact-validated-narration` names the free-text channels to neutralize.
- **Worktree removal.** Use `git worktree remove --force` and `git branch -D` against the repository's main checkout with explicit `-C`; never the driver's cwd. A worktree already gone is not a failure. Platform handling follows `.claude/skills/windows-checkout-test-parity`.
- **The flag.** `--no-settle` is parsed in `drive.js`, carried on `deps`/options to `run.js`, and read once. The later dispatch entry passes it; this unit adds no caller.

### Data / API Surface

- `settle(stop, deps)` returns `{ calls: [{ step, status }], failed: string[] }`; names are the builder's.
- Final event additions (fields added, none renamed): `settle` (`done` | `left-to-caller` | `none`) and `settleFailed` (list of step names).

## Gotchas

- `check` already wrote the escalation line for any stop that came from its own verdict. Calling `escalate` again for the same stop would write a second line; skip it unless `check` reported `logged: false`.
- `escalate` refuses (exit 1, nothing written) once `run-state.json` records the PR. A stop after the push is therefore never an escalation; the stop classification must come from whether the PR was recorded, not from the failed step's name.
- A non-zero exit of `escalate` or `check` is outcome `blocked`, never `express-escalated` and never retried: no escalation line landed, so the normal path would not know the record left the lane (`_shared/express-lane.md`, Escalation). The settle runs the `blocked` row for it.
- `release-claim.js` is called without `--remove-grants`: the design says the driver "releases the claim" and the grants (`auto:build`) stay, so a human clearing `bot:blocked` can have the record driven again. Its ownership check never deletes a successor's claim (exit 4, nothing written), and an already-released claim exits 3; neither is a settle failure (acceptance criterion 7).
- The design's table lists a failed claim under the `blocked` row, which comments on the PR and the record, labels `bot:blocked` and releases the claim. This unit reads it narrower in two ways, and the design document's table is amended to match. A claim refused because another run holds it (`claim-targets.js` exit 3, "contested or in flight"; `release-claim.js` also has an exit 3, meaning "already released", which is a different thing) is settled with no writes, because adding `bot:blocked` to a record another run is actively working on would mislabel it. Every other claim failure gets the record comment and `bot:blocked` but no release call, because the claim failed before the run directory was minted and `release-claim.js` needs `--run`. Neither claim row has a PR to comment on.
- Removing the worktree discards the partial work on purpose, and the design says the record returns to the queue as if never started and the standard path builds it fresh. The run directory is not removed, so the escalation line stays on record. Decision: a durable marker closes the loop. The escalation comment carries a fixed marker and driver admission refuses a record that has one, so an escalated record goes to the standard path and is not driven again until a human removes that comment (acceptance criterion 11).
- Settle runs only after the launcher has returned its envelope, and the launcher returns only after the worker process has exited (the launcher unit's criterion 4), so no worker can still be writing into a worktree this unit removes or can push after the claim is released.
- The call that releases the claim never uses `--remove-grants`, by the design's wording; a record that escalated therefore keeps its grants (see acceptance criterion 11, which keeps such a record from being driven again).
- Settle comments in the design document and in code name `settle.js`'s table as the source of truth: when the table changes, `docs/driver.md` and the design document's table are updated by hand, since no test reads either.
- A spend ceiling that is only compared after the worker returns (when `--max-budget-usd` does not take effect under subscription login, the launcher unit's probe result) is reported, not settled: the wall-clock ceiling is then the only hard stop.
- No test reads `docs/driver.md`. Update the page when the table or event fields change; nothing will fail if it goes stale, which is the point of the design's no-prose-contract rule.
