# 2941: auto-merge-short-circuit.md singleton path has no mechanical backstop verifying merge-check actually ran before merging

Origin: dispatch drain firing, group 30 (record #2853), discovered after PR #2938 merged

Defer-reason: genuinely-larger (this is a safety-hardening fix to shared dispatch/wrap-up machinery, not something to fold into the record that surfaced it)

Surface: infra

**Related:** #2719, #3088, #2859, #2877, #2902, #2912, #3012, #3037, #3044

## Current State

`plugin/skills/wrap-up/auto-merge-short-circuit.md` gates the single-record fast lane on two layers: Authorization (`auto:merge` present or matured), then Content judgment. Layer 2 is an `assess-agent-autonomy merge-check` invocation (`:57`), and "The verdict must be `auto-merge` to proceed". Today the short-circuit only writes the verdict to `decisions.md` in two cases:

- On the `needs-human` fall-back (`:271`).
- After the merge, inside the `Fast-lane auto-merge: ... outcome {merged|armed|pending-review}` line of the pr-first branch (`:166`).

Before the merge call in the pr-first branch (`:153-166`, which runs `_shared/pr-first-merge.md`), nothing checks that a passing verdict exists. The local-merge branch has the same gap. Whether Layer 2 ran rests on prose discipline alone.

That discipline failed in a live drain firing. The dispatched singleton short-circuit for record #2853 went straight from Authorization to the merge procedure and merged PR #2938 (merged 2026-10-03T14:12:24Z). That PR was an edit to the agent-instruction file `plugin/skills/_shared/github-pr-scan.md`, and no `merge-check` invocation ran. A retroactive `merge-check` found two independent `needs-human` floors (an agent-instruction-file behavior delta, and review's own Medium-severity finding). The correct outcome was `leave-open`/`pending-review`. The content itself was fine (independently reviewed, full suite green), so the gap is procedural.

The bundle path already has a mechanical backstop for this failure mode (#2429). In `plugin/skills/dispatch/settle-and-merge.md`:

- The gate logs a passing verdict as well as a failing one (`:271-280`): `Auto-merge gate: #{n} assess-agent-autonomy verdict auto-merge`.
- Before merging, it re-reads `{run-dir}/decisions.md` once and checks every member's marker in memory (`:282-301`). A missing marker is treated as `needs-human`.
- The local-merge fallback re-runs the same check in dispatch's own thread (`:364-369`).

The singleton short-circuit has no equivalent.

## Deliverables

1. In `auto-merge-short-circuit.md`'s Content judgment layer, log the verdict to `{run-dir}/decisions.md` via `bin/log-decision.js` on both outcomes, before anything else happens. The passing case gets its own line: `Auto-merge short-circuit: #{n} assess-agent-autonomy verdict auto-merge`. This mirrors #2429's "log a passing verdict too" rule. The existing `needs-human` line (`:271`) stays as it is, so `bin/lib/console/resolve.js`'s `needsHumanVerdict` read is unaffected.
2. Immediately before the merge procedure, in both the `pr-first` branch (`_shared/pr-first-merge.md`) and the `local-merge` branch, mechanically re-read `{run-dir}/decisions.md` and confirm this record's passing-verdict marker is present. Use the same one-read pattern as `settle-and-merge.md:282-301`. If the marker is absent, or the record's latest merge-check verdict line is anything other than `auto-merge`, do not merge. Fall through to the normal Review Console path exactly as a `needs-human` verdict does, and log the refusal.
3. A conformance test pins the new procedure text, written in the same style as `tests/auto-merge-short-circuit-ledger-deletion.test.js`: the passing-verdict log step exists, and the re-read check sits before the merge call on both branches. It is proven red against a frozen pre-change excerpt.

## Acceptance Criteria

- A test exercises the check with no passing-verdict line present in a fixture `decisions.md` (Layer 2 skipped) and confirms it reports do-not-merge, so the procedure falls through rather than reaching the merge call.
- A test confirms the normal case: a fixture with the `auto-merge` verdict line passes the check, and the procedure proceeds exactly as today.
- A conformance test asserts that in `auto-merge-short-circuit.md` the verdict-presence re-read precedes the `_shared/pr-first-merge.md` invocation in the pr-first branch, and precedes the merge in the local-merge branch. Each pattern goes red against a frozen pre-change excerpt.
- `tests/console-resolve-conformance.test.js` and `tests/pr-first-merge.test.js` pass unchanged.
- `npm test` passes in full.

## Release Note

The single-record auto-merge fast lane now refuses to merge unless its content-judgment check is confirmed to have run and passed.

## Technical Approach

Port #2429's two-part pattern from `settle-and-merge.md` to the singleton path: log on pass, then re-read before merge. If the check is complex enough to warrant code, consider a small shared helper that both call sites use, so the bundle path and the singleton path cannot drift. One option is a `bin/` CLI or a `bin/lib/` function that takes a run dir plus record numbers and a marker prefix and returns per-record presence. Otherwise inline the same `node -e` one-read snippet `settle-and-merge.md` uses. Either way, the marker text the check searches for must be byte-identical to the text the log step writes.

### Key Files

- `plugin/skills/wrap-up/auto-merge-short-circuit.md` — log the passing verdict at Layer 2, re-read before the merge on both branches, log the refusal
- `plugin/skills/dispatch/settle-and-merge.md` — reference pattern (#2429); update only if a shared helper replaces its inline snippet
- `plugin/bin/lib/console/resolve.js` — `needsHumanVerdict` read; confirm it still matches the unchanged `needs-human` line
- `tests/auto-merge-short-circuit-ledger-deletion.test.js` — style reference for the new conformance suite
- `tests/auto-merge-short-circuit-verdict-backstop.test.js` — new conformance and fixture tests

## Gotchas

- The existing post-merge `Fast-lane auto-merge: ... verdict auto-merge` line (`:166`) is written after the merge. It must not satisfy the pre-merge check, so the search marker has to be a distinct, pre-merge-only string.
- `bin/lib/console/resolve.js` matches any decisions line containing `needs-human` together with `merge-check|assess-agent-autonomy`. The new passing-verdict line must not contain `needs-human`, and the refusal log line must be worded so that `console-resolve.js` resolves this record to `leave-open`, the same outcome as a real `needs-human` verdict.
- `decisions.md` accumulates across a whole run. The check must be scoped to this record's number, so a different record's passing line in the same run can never satisfy it.
- The dispatch-claim singleton path under `local-merge` stops and relays `OUTCOME: ready-to-merge` (`:140-144`) instead of merging. The actual merge then happens in `settle-and-merge.md`'s local-merge fallback, which already re-runs #2429's check, but only against the bundle marker `Auto-merge gate: #{n} ...`. Decide whether the singleton writes that marker too, or whether the fallback learns the singleton's marker. Otherwise a correctly-run singleton verdict would read as missing there.

## Current State

`plugin/skills/wrap-up/auto-merge-short-circuit.md`'s two-layer gate (Authorization, then Content
judgment via `assess-agent-autonomy merge-check`) requires both layers to pass before merging. The
skill prose is unambiguous ("The verdict must be `auto-merge` to proceed").

During this drain firing, the dispatched singleton short-circuit path for record #2853 skipped
Layer 2 entirely — it went straight from Authorization (live `auto:merge` label present) to
`pr-first-merge.md`'s merge procedure, merging PR #2938 (an edit to the agent-instruction file
`plugin/skills/_shared/github-pr-scan.md`) with no `merge-check` invocation at all. Retroactively
running `merge-check` found two independent `needs-human` floors that both applied (an
agent-instruction-file behavior delta, and review's own Medium-severity finding) — the correct
outcome was `leave-open`/`pending-review`, not an autonomous merge.

The content itself was fine (independently reviewed, a real bug found and fixed, full suite green)
— the gap is procedural, not a content defect. By contrast, the **bundle-path** Auto-merge gate in
`dispatch/settle-and-merge.md` already has a mechanical backstop for this exact failure mode (#2429):

mechanical check exists on `auto-merge-short-circuit.md`'s singleton dispatch-claim path — it relies

Add a #2429-equivalent mechanical backstop to `auto-merge-short-circuit.md`'s merge step: before
running `pr-first-merge.md`'s (or `local-merge`'s) merge procedure, verify a `merge-check` verdict
was actually logged to `decisions.md` for this record in this run, and that the verdict is
`auto-merge`. Refuse to proceed to the merge call if no such log line exists or it has any other
verdict.
