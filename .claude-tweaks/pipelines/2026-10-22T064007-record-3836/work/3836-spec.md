# 3836: classifyOwnership and findRunsByWorktreePath still compare worktree paths with the JS-form realpath on a case-insensitive volume

Origin: wrap-up leftover from #3769 (SDD ruling ratified at the Review Console)

Defer-reason: genuinely-larger

## Current State

Record #3769 made `findRunByWorktreePath` (`plugin/bin/lib/hooks/context.js`) case-canonical: both sides of its comparison now resolve through path-guard's `.native` `canonicalRealpath`, so a mis-cased `git worktree remove` target of an assigned worktree is denied. `worktreeMatches` gained an optional 4th `canonical` argument for that; with it omitted, the default branch still compares with the JS `fs.realpathSync`, which keeps the input's letter case on a case-insensitive volume (macOS APFS).

Two callers still use that default branch:

- `classifyOwnership` (`context.js`, the `worktreeMatches({ worktree: binding }, info.repoRoot, info.repoRoot)` call). A same-session `ExitWorktree(remove)` whose recorded binding differs in letter case from git's toplevel classifies as `'foreign'`, so the call is allowed with a warning that wrongly says "recorded by a different session", instead of denied.
- `findRunsByWorktreePath` (the reflect Friction Lens ad-hoc fallback). A mis-cased worktree path misses its ad-hoc run dirs, so friction events drop out of a report. Not a safety decision.

Neither is a regression: before #3769 the assigned-run lookup missed outright. #3769's SDD whole-branch review ruled both out of its acceptance criteria (AC1 covers `git worktree remove` through `findRunByWorktreePath` only); the ruling was ratified at the Review Console.

**Related:** #3736, #3811
