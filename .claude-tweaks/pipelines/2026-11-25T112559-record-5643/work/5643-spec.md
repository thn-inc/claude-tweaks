# 5643: test: the QA pass stamp has no bookkeeping-only exemption, so a ledger commit forces a QA re-run on unchanged code

Surface: infra

**Related:** #4990
Risk-flags: none

## Current State

`plugin/bin/qa-stamp.js --check` decides whether a pipeline's selected QA stories can skip, using `decideQaSkip` (`plugin/bin/lib/verify/qa-stamp.js:57`). Any difference between the stamp's sha and HEAD returns `{ skip: false, reason: 'sha-mismatch' }` (line 62), whatever the commits between them changed. `/claude-tweaks:test`'s pipeline story selection (`plugin/skills/test/SKILL.md`, the QA pass stamp paragraph) runs the selection again on any `skip: false`.

The runner stamp has the exemption the QA stamp lacks. A scoped `verify.js` run whose delta maps only to rules with `suites: []` and no static check selects `mode: 'none'` (`plugin/bin/lib/verify/scope.js`'s `selectScope`), prints `still-verified: bookkeeping-only delta (…)`, and re-stamps HEAD. So after one ledger-only commit the two stamps disagree about the same commit.

Observed (claude-tweaks 6.170.0, filed via `/claude-tweaks:feedback`): a `/flow` test step ran QA, wrote the QA pass stamp, then committed its own QA caveats to the open-items ledger (four lines; the ledger path maps to no suite in `verify-scope.json`). On a context-cap resume, `verify.js` re-stamped HEAD as still verified, but `qa-stamp.js --check` reported `sha-mismatch`. Followed as written, the rule would re-run every selected story against two QA servers. The agent skipped the re-run by judgment and logged the deviation. The same happens without a resume whenever a later call consults the QA stamp after any bookkeeping commit (a dispatched group's second call, the auto-inserted second-call `test`).

## Deliverables

- [ ] `qa-stamp.js --check` accepts an optional `--scope <declaration path>`. When it is given, and the stamp's sha differs from HEAD, the check classifies `stamp.sha..HEAD`:
  - it is a usable anchor (an ancestor of HEAD, per `usableAnchor` in `plugin/bin/lib/verify/changed-files.js`)
  - the tree is clean (the CLI's existing dirty check)
  - the declaration reads clean (`readDeclaration`)
  - `selectScope({ decl, files, stamp: { fullSha: stamp.sha } })` over `changedFiles({ base: stamp.sha })` returns `mode: 'none'`

  When every condition holds, the sha comparison is satisfied and the remaining checks run unchanged (stories-dir match, every selected story covered and its hash unchanged). An all-pass result is `{ skip: true, reason: 'covered-bookkeeping-delta' }`. Any condition failing (not an ancestor, unreadable or missing declaration, `mode` other than `none`) keeps today's `sha-mismatch`.
- [ ] `--check` stays read-only: the bookkeeping path never rewrites the QA stamp. A later check classifies the larger `stamp.sha..HEAD` delta again, so the stamp needs no advance.
- [ ] `decideQaSkip` takes the classification result as an input (for example `bookkeepingDelta: true`), so the rule stays pure and unit-testable. The git and declaration reads stay in the CLI.
- [ ] `plugin/skills/test/SKILL.md`'s QA pass stamp paragraph: pass `--scope .claude-tweaks/verify-scope.json` when the project has a declaration (the same declaration the scoped verify calls pass). On `skip: true` with reason `covered-bookkeeping-delta`, report `QA: skipped — stories already passed at {short-sha}; only bookkeeping commits since`, and log `AUTO {time} — QA skipped: {k} selected stories already passed at {short-sha}, bookkeeping-only delta since (QA pass stamp). Reversibility: high.`
- [ ] `plugin/skills/test/qa-reporting.md`'s QA pass stamp paragraph names the bookkeeping-delta skip in one sentence.
- [ ] Tests: `tests/bin-lib/verify/qa-stamp.test.js` covers the pure rule, and `tests/bin-lib/verify/qa-stamp-cli.test.js` covers the CLI cases in the Acceptance Criteria.

## Acceptance Criteria

1. With a QA stamp at S, a clean HEAD one commit past S whose only change is `docs/plans/x-ledger.md` (mapped to `suites: []`, static false), and `--scope` naming that declaration, `--check` prints `skip: true`, `reason: "covered-bookkeeping-delta"`, `sha` S. The stamp file is byte-identical afterwards.
2. Same setup with a delta that also changes a path mapped to a suite: `skip: false`, `reason: "sha-mismatch"`.
3. Same as AC 1 without `--scope`: `skip: false`, `reason: "sha-mismatch"` (today's behavior).
4. Same as AC 1 with a selected story file changed since the stamp: `skip: false`, `reason: "story-changed: {id}"`.
5. A stamp sha that is not an ancestor of HEAD (rewritten history), or a `--scope` path that does not exist or fails to parse: `skip: false`, `reason: "sha-mismatch"`, and `--check` still exits 0 (status is data).
6. A dirty tree with a bookkeeping-only delta: `skip: false`, `reason: "dirty-tree"`, as today.

## Release Note

A pipeline's QA step no longer re-runs browser stories after a commit that only touched bookkeeping files such as the run ledger: the QA pass stamp now treats that commit the way the test runner's stamp already does.

## Technical Approach

The classification reuses `verify.js`'s own rule rather than a QA-specific path list. A commit is QA-bookkeeping exactly when it is runner-bookkeeping, so the two stamps can no longer disagree about the same commit. The anchor passed to `selectScope` is a synthetic stamp `{ fullSha: stamp.sha }`, which makes `anchorOf` return the QA stamp's sha. No impact context is passed: a bookkeeping delta never reaches an impact rule, and any delta that does is not `none` anyway.

`qa-stamp.js`'s `parseArgs` gains `--scope <path>` (valid with `--check` only; with `--write` it is a usage error, exit 2). A relative path resolves against the repo root (`git rev-parse --show-toplevel`), matching how `verify.js` resolves `--scope`.

### Key Files

- `plugin/bin/qa-stamp.js` — `--scope` flag; delta classification before `decideQaSkip`
- `plugin/bin/lib/verify/qa-stamp.js` — `decideQaSkip` accepts the bookkeeping-delta input; new reason `covered-bookkeeping-delta`
- `plugin/bin/lib/verify/scope.js` — read only: `selectScope` reused
- `plugin/bin/lib/verify/changed-files.js` — read only: `usableAnchor`, `changedFiles` reused
- `plugin/skills/test/SKILL.md` — QA pass stamp paragraph: pass `--scope`; report and log line for the new reason
- `plugin/skills/test/qa-reporting.md` — QA pass stamp paragraph

- `tests/bin-lib/verify/qa-stamp-cli.test.js` — AC 1-6

## Gotchas

- **Decided (2026-11-25, autonomous lane): the check classifies the delta (the record's first option), not a re-ordered stamp write.** Writing the QA stamp after the test step's own ledger commit fixes one ordering only. Any other bookkeeping commit before a later check (a resume, a dispatched group's second call, the auto-inserted second-call `test`) would still mismatch. A hard-coded QA bookkeeping path list was also rejected: it would duplicate the project-owned declaration and drift from it.
- **Decided: `--check` never re-stamps.** `verify.js` re-stamps on a bookkeeping delta, but `qa-stamp.js`'s header contract is that `--check` only reports. The classification is repeatable over a growing delta, so nothing needs advancing.
- **Decided: the exemption trusts the declaration.** A path a project maps to `suites: []` with no static check is one it says affects nothing tested. A project whose rendered content lives under such a path (a docs site, for example) must map it to a suite or a static check to keep QA re-running on it. Say so in the `qa-reporting.md` sentence.
- The `AUTO` log line is `AUTO`, not `STAGED`: it records an applied skip and writes no `staged/` artifact.

## Original request

test: the QA pass stamp has no bookkeeping-only exemption, so a ledger commit forces a QA re-run on unchanged code

**Summary:** After a commit that changes only the open-items ledger, the QA pass stamp check reports `sha-mismatch` and the test step's rule re-runs browser QA, although the code under test is byte-identical to what the stamp covers.

**Kind:** Gap

**Affected component:** /claude-tweaks:test (the QA pass stamp check, `qa-stamp.js --check`)

**Use case:** In a `/claude-tweaks:flow` run, the test step ran QA for the stories its diff selected and wrote the QA pass stamp. It then appended its own QA caveats to the open-items ledger and committed them, which moved HEAD by one bookkeeping-only commit (the ledger path maps to no suite in the project's `verify-scope.json`). The run crossed its context cap and the test step was resumed in a fresh agent. On resume, `verify.js` classified the delta as bookkeeping-only and re-stamped HEAD as still verified, but `qa-stamp.js --check` reported `sha-mismatch` against the same delta, and the test step's rule for that result is to run QA again. The agent skipped the re-run by judgment and logged the deviation. Followed as written, the rule would have re-run every selected story against two QA servers for a commit that touched four ledger lines. The runner stamp already has this exemption (a bookkeeping-only delta prints `still-verified` and re-stamps); the QA stamp does not, so the two stamps disagree about the same commit. The same thing happens without a resume whenever a later step consults the QA stamp after the test step's own ledger commit.

**Definition:** Needed — whether the QA stamp check should classify the delta against `verify-scope.json` like the runner does (and re-stamp), or the test step should write its QA stamp after its ledger commit, is a design choice.
