# 3412: Reconciler releases a run's unfinished record when the run's PR merges without closing it

Surface: backend

**Related:** #3249, #3311, #3348, #3399, #3416

Origin: dispatch close-out of PR #3348, 2026-10-17

Defer-reason: pre-existing-outside-diff

## Current State

`decideRelease` in `plugin/bin/lib/reconcile/release-merged.js` returns `release` (reason `merged: reconciled from PR #N`) for every live or stale claim whose run's PR is `MERGED` (`plugin/bin/lib/reconcile/release-merged.js:47-49`). It never checks whether that PR actually closes the claim's issue. The PR-state join feeding it (`plugin/bin/lib/reconcile/pr-state.js`) requests `number,state,mergedAt,updatedAt,mergeCommit` from `gh pr list` (`PR_LIST_ARGS`, `pr-state.js:548`) and the same set plus `mergeable,mergeStateStatus` from `gh pr view` in the two by-number resolvers — no closing-issue data reaches the decision at all.

A multi-record run's PR can merge with only some of its records shipped. On 2026-10-17, PR #3348 (run `2026-10-17T062549-spec-3307-3308-3306-3309-3310-3311`) was squash-merged on explicit human instruction while the run was still building #3311. The PR body had been edited from `Fixes #3311` to `Refs #3311`, and the merge commit carried `Fixes` lines for #3306-#3310 only. One second after the merge (18:34:09Z), the reconciler released #3311's claim with reason `merged: reconciled from PR #3348` and removed `bot:in-progress` and `auto:build`. That left an open record mid-build, with its owning session still working on it, unclaimed and ungranted. (Verified at shaping time, 2026-10-17: PR #3348's `closingIssuesReferences` lists #3306-#3310 only; merge commit `a39cd61` carries `Fixes` lines for exactly those five; #3311 is still open.)

## Deliverables

- Make `releaseMerged` release a claim on merged-PR evidence only when the merged PR actually closes that issue: its `closingIssuesReferences`, or the merge commit's closing keywords. A record whose run PR merged without closing it keeps its claim (skip reason e.g. `pr-merged-not-closing`). Its later release follows the normal issue-closed / TTL paths.

- Keep the #3249 behavior intact: a fast-lane or console-never-rendered merged run whose PR does close the record still releases and archives.

## Acceptance Criteria

- [ ] A live claim whose run PR is MERGED but does not close that claim's issue is not released, and its labels are untouched.

- [ ] A live claim whose run PR is MERGED and closes the issue is still released, so existing merged-run cleanup is unchanged.

- [ ] A live claim whose run PR is MERGED without closing the issue, and whose issue has since been CLOSED, is released with the `issue-closed` reason — the kept claim's designed exit, so the issue-state fetch must run for this shape.

- [ ] A MERGED PR whose parsed state carries no `closingIssuesReferences` field at all (malformed response, stale fixture) never releases on merged evidence — the claim is kept with a distinct skip reason, never released by default.

- [ ] A regression test reproduces the partial-merge case and fails on the pre-fix `decideRelease`.

- [ ] `npm test` passes.

## Release Note

Fix the reconciler releasing an unfinished record's claim when its run's PR merges without closing it.

## Technical Approach

1. **Carry closing-issue data through the PR-state join** (`pr-state.js`). Add `closingIssuesReferences` to `PR_LIST_ARGS`'s `--json` field list (covers `resolvePrState` and `resolvePrStateAsync`, which share the constant) and to the `gh pr view` field list in both `resolvePrStateByNumber` and `resolvePrStateByNumberAsync`. The field is confirmed available on both `gh pr list` and `gh pr view` (probed 2026-10-17); its shape is `[{ number, repository: { name, owner: { login } }, url }]`. `pickGoverningPr` passes the governing PR object through untouched, so the field reaches `release-merged.js` with no further plumbing. Every other consumer of these resolvers (`reap-merged.js`, `archive-merged.js`, `prune-remote.js`, `archive-branches.js`) reads only the keys it already reads; the bulk GraphQL screen (`resolvePrStatesBulk`) is not used by `release-merged.js` and stays unchanged.

2. **Pure "does this PR close this issue" helper** in `release-merged.js` — `prClosesIssue(prState, issueNumber, repoSlug, mergeCommitMessage)` → `true | false | undefined`. `true` when `closingIssuesReferences` contains an entry whose `number` matches and whose `repository.owner.login/name` matches `repoSlug` (never a same-number issue in another repo), or when `mergeCommitMessage` carries a line-anchored closing keyword for the issue — GitHub's keyword set (`close|closes|closed|fix|fixes|fixed|resolve|resolves|resolved`, case-insensitive) followed by `#N` on a word boundary, the exact `Fixes #n` line shape `bin/lib/compose-subject.js` emits for the squash subject (one line per record). `Refs #N` is deliberately not a match. `false` when the references array is present and neither signal matches. `undefined` only when the parsed PR has no `closingIssuesReferences` array at all.

3. **Widen `decideRelease`** with a fourth argument, `closesIssue` (`true | false | undefined`), keeping `prState` as the raw gh shape. New decision rows, every existing row unchanged:
   - `MERGED` + `closesIssue === true` → `release`, reason `merged: reconciled from PR #N` (today's behavior).
   - `MERGED` + `closesIssue === false` → fall through to issue-closed evidence: `issueState === 'CLOSED'` → `release`, reason `issue-closed`; otherwise `skip`, reason `pr-merged-not-closing`.
   - `MERGED` + `closesIssue === undefined` → same fall-through, skip reason `pr-merged-closing-unknown`. Fail closed: missing closing data never releases on merged evidence.
   `needsIssueEvidence` gains the same argument and returns `true` for a `MERGED` PR whose `closesIssue !== true`, so Phase 2's issue-state fetch actually runs for the kept-claim shape (today it is skipped for every `MERGED` candidate, which would make the `issue-closed` exit unreachable).

4. **Merge-commit message fetch, pooled and gated.** For each `MERGED` candidate whose `closingIssuesReferences` does not already name its issue, fetch the merge commit message once — `repos/{slug}/commits/{mergeCommit.oid}` with `-q .commit.message` through the module's `apiAsync` seam and `runWithConcurrency`, as a step between Phase 1.5 and Phase 2 — so a candidate the references already settle costs nothing extra, and the injectable `ghApi` test seam covers it (a test fake answers `/commits/` paths the same way it answers `/issues/`). A failed fetch leaves the commit signal absent; `prClosesIssue` then decides from the references alone.

5. **Phase 3 wiring.** Compute `closesIssue` per candidate, pass it to `decideRelease`. The existing `c.joinFailure || decision.reason` skip push surfaces the two new reasons unchanged. `removeGrantLabels`/`logGrantRemoval` already key on a `merged:` reason, so a kept claim strips nothing — the incident's `auto:build` removal cannot recur.

6. **Tests** (`tests/bin-lib/reconcile/release-merged.test.js`, `tests/bin-lib/reconcile/pr-state.test.js`):
   - `decideRelease` table rows for every new branch above; rename the existing `merged PR still releases regardless of issue state` case to the closing-PR shape it now pins.
   - `prClosesIssue` fixtures: references include; references exclude plus a `Fixes #N` commit line; `Refs #N` does not count; same-number issue in another repo does not count; field absent → `undefined`.
   - `needsIssueEvidence` returns `true` for `MERGED` + `closesIssue: false`.
   - End-to-end regression in the #3348 shape: live claim, run-state with a resolvable branch, `gh` wrapper answering `pr list` with a `MERGED` PR whose `closingIssuesReferences` name other issues, the `ghApi` fake answering `/commits/` with `Fixes` lines for those other issues and `/issues/{n}` with `OPEN` → `released` is empty, `skipped` carries `pr-merged-not-closing`, and the fake records no `/labels/` DELETE. Prove it goes red on the pre-fix `decideRelease` before keeping it.
   - Update the two existing end-to-end fixtures (Phase 1.5 pool test, #3249 by-number test) so their wrapper JSON carries `closingIssuesReferences` naming the claim's issue — they go red under the fail-closed rule otherwise, which is the rule working, not a regression.
   - `pr-state.test.js`: extend the field-list pins (`requests and returns mergeable/mergeStateStatus (#2367)` and the `PR_LIST_ARGS` users) to assert `closingIssuesReferences` is requested by all four resolvers.

### Key Files

- `plugin/bin/lib/reconcile/release-merged.js` — `decideRelease`/`needsIssueEvidence` gain `closesIssue`; new `prClosesIssue` helper; pooled merge-commit message fetch between Phase 1.5 and Phase 2; Phase 3 passes the verdict through
- `plugin/bin/lib/reconcile/pr-state.js` — `PR_LIST_ARGS` and both by-number resolvers request `closingIssuesReferences`
- `tests/bin-lib/reconcile/release-merged.test.js` — decision-table rows, `prClosesIssue` fixtures, the partial-merge regression, fixture updates for the two existing end-to-end tests
- `tests/bin-lib/reconcile/pr-state.test.js` — field-list pins widened to `closingIssuesReferences`

## Gotchas

- Fail closed on a missing field is a deliberate choice, not an accident: `gh` always returns `closingIssuesReferences` (an empty array when none), so `undefined` only arises from a malformed response or a stale test fixture — and the module's existing posture (`readIssueStateAsync`'s "fail closed, never releases on missing evidence") already treats missing evidence as no release. Expect the two existing end-to-end tests to go red until their fixtures carry the field.
- "Its later release follows the normal issue-closed / TTL paths" means two different mechanisms: the reconciler itself releases a kept claim only on `issue-closed` evidence (reachable for this shape only because `needsIssueEvidence` widens — verify that in the regression, not by inspection); the TTL path is not a reconciler release at all — past `ttlHours`, `classifyClaimBlob` reports the claim `stale` and reclaimable, which `/dispatch`'s claim step honors (`_shared/issue-claims.md`'s TTL section). Do not add a TTL release to this module.
- The merge-commit scan must match the squash subject `bin/compose-subject.js` composes (one `Fixes #n` line per record, line 19's contract) and GitHub's full keyword set; a body-text `Refs #N` — the exact edit that preceded the incident — is non-closing and must stay non-closing in the fixtures.
- Match the repository on `closingIssuesReferences` entries, not just the number: the field can reference an issue in another repository with the same number.
- `archive-merged.js` shares the same merged-PR join and has its own live-run mis-archive on record (#3416, surfaced by the near-duplicate screen); this record touches `release-merged.js` and `pr-state.js` only — report any archive-side gap, do not fold it in.
- The `ghApi` fake in the existing end-to-end tests throws on any unexpected path; the new `/commits/{oid}` call must be answered there, or those tests fail with `unexpected repos/...` rather than a clear assertion.
