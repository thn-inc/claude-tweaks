# 2732: flow: worktree creation doesn't open the draft PR automatically — discovered twice mid-build

Surface: infra

## Current State

`/flow`'s worktree-creation step (`materialize.md`'s worktree-first ordering, `build/worktree-setup.md`) is documented to open the pipeline's draft PR early ("born public" — `_shared/pr-early-run-lifecycle.md`), before any build work happens. In this session's two `/flow` runs (spec-2670-2681, spec-2682), that PR was NOT created automatically at worktree-creation time — a bare `git` worktree was created and a build subagent dispatched directly. Both build subagents independently hit `build/worktree-setup.md`'s own pre-tool-use hook gate (`checkBookkeepingStampsGate`, per `docs/incident-log.md` `[IL-131]`) blocking further edits until a PR was recorded, and both had to improvise: run `record-worktree`/`record-pr` CLI commands and `gh pr create` themselves, mid-task, outside their own declared spec scope.

Session evidence:
- Spec #2670's build agent: "This run's PR-early lifecycle step (`build/worktree-setup.md` Step 6) had not run before I was dispatched — the `pre-tool-use` hook (IL-131) blocked all `Edit` calls until it was satisfied. I completed it: pushed the branch, opened draft PR #2698... This is infrastructure the orchestrating pipeline should normally have done at run start, not part of #2670's own deliverables."
- Spec #2682's build agent: "had to open this draft PR mid-task — the repo's `pr-first` hook blocked further edits until a PR was recorded; used `record-worktree` then `record-pr` CLI commands to satisfy the gate."

**Root cause, narrowed during shaping.** `build/SKILL.md`'s own text (Spec Step 1, ~line 68) already documents the draft-PR call as non-skippable: "Immediately after the materialize commit, in `worktree` mode only: run `build/worktree-setup.md` Step 6 — opens the run's draft PR under `integration-model: pr-first`... Non-skippable, regardless of what Spec Step 2's implementation assessment turns out to find." It also already carries a reactive backstop for exactly this failure mode: `build/SKILL.md`'s Common Step 7 "Bookkeeping assertion" (#2311) checks `run-state.json` for a missing `worktree`/`pr` field at the end of every build phase and backfills it — this is the mechanism [IL-131] traces to, and it's *already shipped*, not a gap this record needs to invent.

Critically, `build/worktree-setup.md` itself states Step 6 "is invoked separately from `build/SKILL.md` Spec Step 1, never from within this numbered procedure" — i.e. Common Step 1 (worktree creation) and Step 6 (open the draft PR) are two *separate* calls, and only `build/SKILL.md`'s own Spec Step 1 sequences them together. This session's `/flow` runs hand-rolled worktree creation (`EnterWorktree` + a bare `Agent` dispatch for "build") rather than literally invoking `/claude-tweaks:build` as a `Skill`-tool call — which means Spec Step 1's own explicit Step 6 call, and Common Step 7's own end-of-phase backfill, were both bypassed entirely, since neither lives in the hand-rolled path at all. A grep of `flow/SKILL.md` for "PR-early"/"draft PR" during this shaping pass returned zero matches — the requirement genuinely isn't stated in `flow/SKILL.md`'s own Step 4 prose at all, only in the two files `build/SKILL.md` cross-references.

This strongly supports root-cause (b) from the original report (a hand-rolled orchestration path, not a gap in `/flow`/`/build`'s own documented-and-enforced sequence) — but the fix still needs a decision on where to close the gap: strengthen `flow/SKILL.md`'s own Step 4 prose so an orchestrator following it by hand (not literally invoking the Skill tool) can't miss the requirement, and/or consider whether Common Step 1 itself should absorb the Step 6 call so the two can't be separated by construction.

## Deliverables

- [ ] Add explicit PR-early language to `flow/SKILL.md`'s Step 4 (currently silent on it — confirmed via grep during shaping) naming the requirement plainly enough that a hand-executing orchestrator (not literally invoking the `Skill` tool) won't miss it, cross-referencing `build/worktree-setup.md` Step 6 and `_shared/pr-early-run-lifecycle.md`.
- [ ] Evaluate whether `build/worktree-setup.md`'s Common Step 1 (worktree creation) should call Step 6 (open draft PR) directly, removing the separate-invocation fragility that let this session's hand-rolled path skip it — implement if the evaluation favors it; document the decision either way if not (e.g. if a real reason keeps them separate, such as a caller that legitimately needs the worktree before deciding whether a PR applies).
- [ ] Confirm `build/SKILL.md`'s existing Common Step 7 Bookkeeping-assertion backstop (#2311) still fires correctly for a *literal* `/claude-tweaks:build` invocation — this record's own investigation didn't find a gap there, only in the hand-rolled path that bypasses `build/SKILL.md` entirely; no changes needed there unless testing turns up a real gap.

## Acceptance Criteria

3. `npm test` passes.

## Technical Approach

Two independent angles, both grounded in the investigation above: (1) a documentation fix to `flow/SKILL.md`'s Step 4, which currently says nothing about PR-early at all; (2) an architectural question about whether `worktree-setup.md`'s Common Step 1 and Step 6 should be coupled rather than two separately-invoked steps — resolve this by reading `build/SKILL.md`'s Spec Step 1 prose (~line 68) and `worktree-setup.md`'s own Step 6 comment about being invoked separately, then deciding whether coupling them removes real flexibility (some caller legitimately needing worktree-without-PR) or is pure accidental fragility.

### Key Files

- `plugin/skills/flow/SKILL.md` — Step 4, where the PR-early requirement needs stating explicitly
- `plugin/skills/build/SKILL.md` — Spec Step 1 (~line 68, the existing non-skippable PR-early call) and Common Step 7 (the #2311 Bookkeeping-assertion backstop)
- `plugin/skills/build/worktree-setup.md` — Common Step 1 (worktree creation) and Step 6 (draft PR open), and its own comment on why they're currently separate calls
- `plugin/skills/_shared/pr-early-run-lifecycle.md` — the push-and-open-draft-PR procedure both Step 6 and the Bookkeeping-assertion backfill call

## Gotchas

- Don't conclude the reactive backstop (#2311's Bookkeeping assertion) is broken — this investigation found no evidence of that; the gap is specific to a hand-rolled orchestration path that bypasses `build/SKILL.md` (and therefore both the Step 6 call and the Common Step 7 backstop) entirely, not a failure of `/claude-tweaks:build`'s own documented sequence when actually invoked.
- If coupling Common Step 1 and Step 6 turns out to have a legitimate reason to stay separate (check for one before assuming there isn't), the fix narrows to the documentation angle alone — don't force a code change the investigation doesn't support.
