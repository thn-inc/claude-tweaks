## Current State

The rule that decides whether a PR's acceptance labeling has landed (`demo:pending` and the Try it walkthrough) has no single definition. Two full copies and one partial copy exist on `main`:

- `plugin/skills/dispatch/close-out.md` step 3 has the full rule. It resolves the run dir from the PR's `claude-tweaks-run:` marker, reads `verify.json`, and falls back to live forge state.
  - Run dir: validated as `flow/claim-targets.md` does, then the run dir or its `archive/` copy.
  - `verify.json`: a multi-spec run reads every `spec-*/verify.json`. Landed means every file exists and its `acceptance-labeling` row's `result` is `pass`/`skip`.
  - Live-state fallback: `demo:pending` is on every `Fixes` record, or the PR has a trusted `<!-- run-comment: brief -->`/`<!-- run-comment: try-it -->` comment, or one of their multi-spec forms.
- `plugin/skills/tidy/actions-github-issues.md`'s `## Arm ready PR` (added by #3877) opens with "apply `dispatch/close-out.md` step 3's landed rule and live-state precheck". It then restates all three parts in full and adds its own deliberate differences:
  - It runs the live checks even when no run dir resolves.
  - It treats a failed read as not landed.
  - It holds the PR rather than running labeling, and reports with a reason vocabulary (`verify.json missing`, `acceptance-labeling: {result}`, `no run dir`, `unreadable: …`).
- `plugin/skills/_shared/pr-first-merge.md` Step 1 states the `verify.json` part of the rule. It then names both callers' differences inline: "`dispatch/close-out.md` step 3 also accepts live labels or brief comments, and tidy's Arm ready PR holds rather than runs this step". That makes the shared contract carry knowledge of its callers.

The review finding is right in substance and wrong in its stated grounds. The tidy → `dispatch/close-out.md` edge is already recorded once in `docs/skill-graph.md`, so the "edges live once" rule is not broken. The real defect is a cross-skill contract restated rather than cited. The next change to "landed" (a new run-comment kind, a new trust rule) has to be made in two or three places, and missing one makes tidy and close-out disagree on whether a PR may merge. #3963 is about to add a third consumer (`_shared/github-pr-scan.md` item 9) that would copy the rule again.

`tests/tidy-arm-ready-pr-acceptance-guard.test.js` pins tidy's restated prose and the pr-first-merge sentence that names tidy.

## Gotchas

- The two callers deliberately differ on the no-run-dir case, and both behaviors must survive. Close-out stops without the live tier. Tidy runs the live tier because it never runs Step 1, so it does not need a run dir. Folding either behavior into the shared predicate changes one caller's behavior.
- Do not move the callers' differences into `_shared/pr-first-merge.md`. Naming its callers inside the shared contract is half of what the finding flagged. The differences belong in the callers, and the edges belong in `docs/skill-graph.md`.
- Tidy's "a failed read holds, never passes" rule belongs in the predicate (a failed read is not landed), not in tidy alone. Close-out's copy is silent on it today, so stating it once in the Landed check tightens close-out to tidy's stricter reading. That is a deliberate convergence: a failed read must never count as landed in a merge gate. Write it down as such, and do not report the refactor as zero-delta for close-out. (Decided during build: an unreadable `verify.json` is not rescued by the live-state tier, and an `unreadable` outcome takes precedence over the other not-landed outcomes — both the stricter readings, staged as SDD rulings for the Review Console.)
- `_shared/pr-first-merge.md` is about 38 KB. Check the repo's skill-size limits with `wc -c` before adding the subsection, and offset growth by removing the restated sentence in Step 1.
