# 4439: Give the open-items ledger a sanctioned append/settle CLI

Origin: reflect full from #4421

Defer-reason: tangential

## Current State

Build, review and wrap-up all append rows to, and settle rows in, the run's open-items ledger (`docs/plans/*-ledger.md`, format in `plugin/skills/_shared/ledger-format.md`). The only sanctioned writer is `plugin/bin/stage-item.js --ledger` (`plugin/bin/lib/stage-item/ledger.js`), which appends a row paired with a staged file, under `{run-dir}/.ledger.lock`, through `atomic-write.js`. A plain row (a deferred minor, a fixed review finding) and a status/resolution settle have no CLI, so a worktree session writes them by hand.

The obvious hand-written forms — `node -e` with quoted table cells or `>=`, a heredoc, `printf … >>` — are refused by the harness's worktree-isolation compound-Bash guard. Run `2026-10-26T123848-spec-4336-4419-4420-4421` (records #4336, #4419, #4420, #4421) logged 42 such refusals (`wd-guard-refusal`, `harness-worktree-isolation`), many of them ledger writes, and finished its ledger edits through ad-hoc scratchpad scripts that bypass the lock and atomic write.

## Deliverables

- [ ] A `plugin/bin/hooks.js ledger-row` verb (or a sibling CLI) that appends one row (`--phase`, `--item`, `--status`, optional `--resolution`) or settles an existing row by number (`--row N --status … --resolution …`), reusing `stage-item/ledger.js`'s lock, re-read and atomic write and `wrap-up/ledger-write.js`'s table parser/serializer, with `escapeLedgerCell` for pipes
- [ ] Validate `--status` against `ledger-format.md`'s closed enum (`open`, `fixed`, `deferred`, `accepted`, `acknowledged`, `observation`) and its resolution-text requirements (`fixed` needs a commit or file ref; `deferred` needs origin, files and trigger)
- [ ] Point the build/review/wrap-up prose that appends or settles ledger rows at the verb

## Acceptance Criteria

1. From a linked worktree, `node plugin/bin/hooks.js ledger-row --ledger <path> --phase build --item "a | b" --status open` appends one row whose Item cell keeps the escaped pipe, under the ledger lock.
2. `--row 3 --status fixed --resolution "abc123"` rewrites only row 3's Status and Resolution cells; `--status resolved` exits non-zero naming the enum.
3. A concurrent append from two processes yields two distinct row numbers (test with two child processes).
4. `npm test` passes.

## Plan Review Clarifications

Decided by the user at plan review (2026-10-30), from the plan-review question comment on this record:

- Q1 (deferred validation): No literal `origin:`/`files:`/`trigger:` labels. `ledger-row` accepts `--status deferred` only when its Resolution (a) names a `staged/…` path or a record reference, or (b) carries exactly one valid `Defer-reason:` from `_shared/deferral-gate.md`. The checks for (a) and (b) reuse `pack.js`'s predicates (`LEDGER_DEFERRED_STAGED_RE`/`namesRecordReference` for `deferredUnstaged`, `hasValidDeferReason`), exported rather than copied. A row accepted only under (b) is written, and the JSON output flags it `incompleteDeferral: true`; the resolve gate settles it later. A `deferred` Resolution meeting neither (a) nor (b) exits non-zero, names the rule, and writes nothing.
- Q2 (terminal rows): Reading A — `ledger-row --row N` reads row N's current Status first. If it is terminal (`fixed`, `deferred`, `accepted`, `acknowledged`, `observation`), the verb exits 1 with nothing written and names the row and its status. The one exception is an incomplete deferral: a `deferred` row whose Resolution names neither a `staged/…` path nor a record reference, per `pack.js`'s `deferredUnstaged` predicate. That row may be settled to any terminal status, since that is its first complete terminal write per `_shared/ledger-format.md`.
