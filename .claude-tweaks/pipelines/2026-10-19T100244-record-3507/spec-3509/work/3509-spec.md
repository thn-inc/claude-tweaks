## Current State

The post-merge `windows-regression` workflow (run 39101919451, on `windows-latest`) found one test file newly failing after PR #3445 merged as `5fe0d5329`. PR #3445 shipped #3161, which made `plugin/skills/specify/record-creation-subissues.md`'s cross-reference fence set `$SPECIFY_DECOMP_MANIFEST` itself and added `tests/specify-crossref-manifest-resolve.test.js` to pin it. Verdict line: `Baseline: adjudicated against 7a649060e — 102 failing file(s): 101 also fail at base, 0 flaky (passed in isolation), 1 attributable`. The run's TAP log shows `ok 11371` (the string-pin test), `not ok 11372` (the standalone-run test), and `ok 11373` (the go-red control). Verified against `origin/main` at `7852fd8bf`, where neither the test file nor the skill file has changed since `5fe0d5329`.

The skill text is correct. The defect is in the test fixture:

- `tests/specify-crossref-manifest-resolve.test.js:15` sets `PLUGIN_ROOT = path.join(REPO_ROOT, 'plugin')`, which is native, so on the runner it is `D:\a\claude-tweaks\claude-tweaks\plugin`. Line 51 passes it unchanged as `CLAUDE_PLUGIN_ROOT` in the env of each `bash -c` fence run.
- Every fence the test runs (the init, accumulate, and cross-reference fences in `record-creation-subissues.md`, near lines 15, 171 and 190) interpolates `${CLAUDE_PLUGIN_ROOT}` into a JavaScript single-quoted literal inside `node -e "..."`: `require('${CLAUDE_PLUGIN_ROOT}/bin/lib/session-tmp.js')`. Bash keeps the backslashes inside double quotes, and JS then reads `\a`, `\c` and `\p` as escapes and drops them. The result is `Cannot find module 'D:aclaude-tweaksclaude-tweaksplugin/bin/lib/session-tmp.js'`. Reproduced on macOS by running that fence shape with `CLAUDE_PLUGIN_ROOT='D:\a\claude-tweaks\claude-tweaks\plugin'`: it prints that exact mangled path.
- The Windows stack trace puts the failure at line 54, the **init** fence's `expectOk`, not at the cross-reference fence. The `$(node -e ...)` substitution fails, `SPECIFY_DECOMP_MANIFEST` comes out empty, and the fence's `writeFileSync('')` exits 1 with `ENOENT`.
- So the go-red control at lines 90-94 passes on Windows without testing anything. It strips the assignment from the cross-reference fence and expects `/fence exited 1: [\s\S]*ENOENT/`. On Windows the init fence already throws that, so the stripped fence never runs. On Linux the control does what it says.

Prior art for exactly this class: PR #3076 fixed `tests/dispatch-not-spec-shaped-exclusion-fixture.test.js:69` the same way, passing `path.join(ROOT, 'plugin').split(path.sep).join('/')` because "the snippet interpolates this into a JS string literal, where a win32 backslash path would be read as escapes". `tests/adopted-branch-collision-snippet-fixture.test.js:23`, `tests/backlog-refine-foldin-no-truncation.test.js:26` and `tests/backlog-overview-foldin-no-truncation.test.js:25` define their `PLUGIN_ROOT` in that forward-slash form. #3076's PR body records that the harness substitutes a forward-slash plugin root at runtime, so the shipped fences are unaffected.

## Release Note

Fixed a /specify decomposition test that failed on Windows because it passed the plugin path with backslashes.

## Technical Approach

The fix is test-side only, following `.claude/skills/windows-checkout-test-parity/SKILL.md` and #3076's precedent. The plugin root reaches the fences as an environment variable that is interpolated into a JS string literal, so the test must hand the fences the same forward-slash form the harness supplies at runtime. This is not a display ID versus native path question: the value is never opened natively by the fence's shell, it is source text for `node -e`. For the go-red tightening, the cheapest change is a step label threaded through the `run`/`expectOk` helpers in `assertCrossrefFenceRunsStandalone`. The test's own string-pin test (lines 69-84) stays as it is.

## Gotchas

- Do not "fix" this by changing the skill fences to read `process.env.CLAUDE_PLUGIN_ROOT` or by normalizing in `plugin/`. The harness already substitutes a forward-slash root (#3076), so the shipped prose works. Only the test's fixture env differs from what the harness provides.
- `tests/specify-ceremony-tally-prose.test.js` runs the same init and accumulate fences with the same unnormalized `PLUGIN_ROOT` (line 74 feeding line 104). It is not this record's failure: it already fails at base on Windows, earlier, at module load. Its `fenceAfter` reads the skill without CRLF normalization (`extraction pattern is out of sync: no bash fence after **Fresh manifest for this invocation.**`), so it was adjudicated as also failing at base. Fixing the CRLF read would expose this same plugin-root failure there. Keep it out of this PR. During the build, check whether a record already covers it (the #2767 umbrella baseline record is the likely home), and file one via `/claude-tweaks:capture` if none does.
- On `windows-latest` the checkout is on `D:` and `os.tmpdir()` on `C:`. The fixture's scratch `root` lives under tmp while `PLUGIN_ROOT` is on the checkout drive. Mixing drives is fine here because nothing compares the two paths. Do not hard-code a drive or root in any expected value.
- This is one of several open `Windows regression:` records (#3429, #3440, #3505, #3506, #3507, #3517, #3518, #3523), each for a different commit and different files. Keep this record to `tests/specify-crossref-manifest-resolve.test.js`.
