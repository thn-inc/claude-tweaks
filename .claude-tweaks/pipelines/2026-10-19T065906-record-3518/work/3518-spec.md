## Current State

The post-merge `windows-regression` workflow (run 39104307191, on `windows-latest`) flagged two test files after PR #3421 merged #3393 (the chained claim reader) as `f6e30ca84`. The run's `verify-report` artifact (`baselineAdjudicated`, base `8356f387f`) breaks it down per test:

- `tests/dispatch-per-record-groups-prose.test.js`: 10/10 pass at base; 11/13 at head. Both new failures are tests that #3393 added: `AC2.1: the neighbour-in-flight heredoc runs offline …` and `AC1.1: the neighbour-in-flight heredoc reports a failed claim read …`.
- `tests/specify-near-duplicate-prose.test.js`: 10/11 at base; 10/13 at head. The test quoted in this record's excerpt, `the shaping-mode.md refusal fence runs and refuses nothing … (#3141)`, **already failed at base** with the same `refusal fence anchors must exist` error. The new failures are #3393's two tests: `AC1.1: the shaping-mode refusal fence reads claims through createClaimReader …` and `AC1.1: an unreadable claim is reported on the output …`.

There are two root causes, both test-side. Verified against `origin/main` at `7852fd8bf`; the only commits since `f6e30ca84` that touch these files (#3366, #3405) changed neither cause.

1. **CRLF anchors (near-duplicate suite).** `tests/specify-near-duplicate-prose.test.js:18` reads skill markdown with a raw `fs.readFileSync`. On a `core.autocrlf=true` checkout, `plugin/skills/specify/shaping-mode.md` arrives with `\r\n` endings, so the fence anchor `'node -e "\n'` (line 96, and again in `refusalFenceBody` at line 147) never matches `node -e "\r\n`. That fails the #3141 test at line 93 and both #3393 tests at lines 155 and 167. The dispatch suite does not have this problem: it already reads through `tests/helpers/read-skill.js`'s `readText`, which turns `\r\n` into `\n`.
2. **Native path spliced into JS source (both suites).** The tests run a skill's embedded node snippet by replacing `${CLAUDE_PLUGIN_ROOT}` with `path.join(ROOT, 'plugin')`: `tests/dispatch-per-record-groups-prose.test.js:134` (`neighbourHeredocCode`), and `tests/specify-near-duplicate-prose.test.js:101` and `:170`. The placeholder sits inside a single-quoted JS string (`require('${CLAUDE_PLUGIN_ROOT}/bin/lib/dispatch/in-flight-neighbours.js')`). A Windows path's backslashes therefore become JS escape sequences: `\a` → `a`, `\c` → `c`. The run shows `Cannot find module 'D:aclaude-tweaksclaude-tweaksplugin/bin/lib/dispatch/in-flight-neighbours.js'`. The near-duplicate tests at lines 93 and 167 have the same defect, currently masked because cause 1 stops them earlier.

The repo already has the fix for cause 2: `tests/auto-merge-short-circuit-verdict-backstop.test.js:28` builds `path.join(ROOT, 'plugin').split(path.sep).join('/')` before splicing it into source.

## Technical Approach

The fix is test-side only, following `.claude/skills/windows-checkout-test-parity/SKILL.md`. Two of its rules apply:

- "A test extracts regions from live skill markdown → a CRLF input proving the extractor still finds the region" covers cause 1.
- Its native-path rule covers cause 2. The value spliced into JS source is a module specifier, not a filesystem path a human pastes into a shell. Forward slashes resolve on every platform, which `tests/auto-merge-short-circuit-verdict-backstop.test.js:28` already relies on.

Folding the #3141 test's inline anchor into `refusalFenceBody` leaves one extractor to keep correct instead of two copies. The CRLF case is the only discriminating check available on Linux CI. The separator fix can only be proven red on a real Windows runner, which is why the workflow dispatch is an acceptance criterion.

## Gotchas

- Keep the scope to the five tests above. `tests/dispatch-neighbour-in-flight-mcp.test.js` is #3517's (a missing `NODE_EVAL_EOF` terminator). Other suites splice `path.join(ROOT, 'plugin')` into code the same way, for example `tests/tidy-release-note-repair-conformance.test.js:83` and `tests/verify-expectations-writer-conformance.test.js:65`; they belong to the Windows baseline or to their own records, not this one.
- Both #3393 `AC1.1` tests depend on `gh` and `git` being unreachable (`env: { ...process.env, PATH: dir }`). On Windows the inherited variable is usually spelled `Path`, and Node's handling of a `Path`/`PATH` pair in a spawned env can leave the original search path in force. If the Windows run shows these tests reaching `gh` (a resolved slug, or a network read), override every case variant of the path variable in the spawned env rather than loosening the assertion.
- Don't fix this in the skill prose. The snippets run under a shell that substitutes `${CLAUDE_PLUGIN_ROOT}` itself; this record changes only how the tests emulate that substitution.
- Line numbers above are as of `origin/main` `7852fd8bf`. Re-anchor on content if the files move.
