# 6284: Re-check open follow-ups whose Key Files a run changed and stage a close or narrowing proposal

Surface: infra

**Related:** #5866
**Related:** #5822
Risk-flags: public-contract, irreversible-side-effect
Risk-flags-unconfirmed: true

## Overview

Open follow-up records go stale when a later run fixes them as a side effect: in origin #5985's evidence, a second run fixed one follow-up (an `html lang` attribute) and half-resolved another (border contrast), and both stayed open until a human noticed. This record adds a per-run re-check at wrap-up: once the run's diff is final and before the Review Console renders, open records whose `### Key Files` intersect the run's changed paths are each judged per deliverable by one dispatched agent against the diff hunks for those files. All deliverables satisfied stages a close proposal; some satisfied stages a narrowing-comment proposal. Both are human calls at every autonomy tier — `_shared/auto-mode-contract.md`'s Never-reversible list forbids closing records and API writes in `auto` — and an approved proposal executes only once the run's merge has landed, because the evidence is this run's diff.

**Complexity:** High
**Estimated tasks:** 7

## Non-Goals

- Closing or commenting automatically at any tier, or adding an exception to the Never-reversible list — that is a governance lever for the maintainer to add deliberately.
- Re-checking the run's own not-yet-created proposals against its own diff (they were staged from the reviewed diff; fix waves settle findings through ledger rows already).
- Re-checking records with no `### Key Files` section, or matching by similarity rather than exact Key File paths.
- Bundling proposals (the sibling bundler sub-issue, which this record is blocked by).
- Any change to how `premise-satisfied-*` proposals (#1829, `plugin/bin/materialize.js`) are produced or executed.

## Deliverables

- [ ] **Candidate selection** in a new `plugin/bin/lib/console/recheck.js` (pure) plus CLI `plugin/bin/recheck-followups.js` (name is the builder's call): open records whose `extractKeyFiles` paths intersect the run's changed paths (`git diff --name-status -M {base}...HEAD`, both the old and new path of a rename and deleted paths included; `{base}` is the run's integration branch per `_shared/integration-branch.md`; the diff is taken at wrap-up, after the last fix wave; a multi-spec run checks the union diff once at the parent against the parent's integration branch), excluding hub paths (`backlogHubPaths` from #6283's `plugin/bin/lib/issues/grouping.js`), `parent-issue` records, `bot:in-progress` carriers, `digest` records, and records this run created or is building. Capped per run by a named constant in `recheck.js` (value is the builder's call; not a policy key); every candidate over the cap is listed in the run's `SCANNED` line, never silently dropped.
- [ ] **Judge dispatch**, in a new cited sub-file `plugin/skills/wrap-up/followup-recheck.md`: one agent per candidate under `_shared/subagent-output-contract.md` (Standard profile, `[Use: Standard]`), given only the record's Deliverables / Acceptance Criteria and the diff hunks for the intersecting files (a per-judge hunk byte cap, value the builder's call; a record whose hunks exceed it is judged `cant-tell` throughout), returning per deliverable `satisfied` (with a verbatim quote of the hunk), `not-satisfied` or `cant-tell`, and a trailing `STATUS:` line. The output template is the builder's call and is inlined verbatim in the dispatch prompt.
- [ ] **Quote check:** a `satisfied` verdict whose quoted text is not found verbatim in that record's intersecting diff hunks counts as `cant-tell` (normalization: strip each line's leading diff marker `+`/`-`/space, collapse runs of whitespace, match within one hunk). A deliverable no hunk touches is `cant-tell`, never `not-satisfied`. The check proves only that the citation is real, not that the deliverable is met: the proposal body shows each deliverable's full text beside its quote so the approving human judges satisfaction. A judge reply with no parseable verdict, or a status other than `DONE`/`DONE_WITH_CONCERNS`, stages nothing for that record and is logged.
- [ ] **Outcome staging:** the truth table is exhaustive — at least one deliverable and every one `satisfied` → stage a close proposal (closing comment quoting the evidence per deliverable); at least one `satisfied` and at least one `not-satisfied` or `cant-tell` → stage a narrowing-comment proposal (which deliverables the run satisfied, with evidence) — so a `cant-tell` blocks a close; no `satisfied` (all `not-satisfied`, all `cant-tell`, or a mix of the two) → nothing staged, logged in the `SCANNED` line. Staged through `stage-item.js` under a new prefix (e.g. `followup-recheck-{N}`, name is the builder's call) whose `SECTION_MAP` row routes to Queue writes with a reason that pins it `pending` regardless of stance and autonomy tier; `CANONICAL_PREFIXES` and every other site in the `review-console-section-addition` project skill's registration set land in the same change.
- [ ] **Console wiring:** `plugin/skills/wrap-up/review-console.md` runs the re-check once before the console renders and records an approval as the item's `console.json` resolution, which is the artifact the executor reads; `plugin/skills/flow/multispec-review-console.md` gains at most a one-line pointer to the sub-file (trimming elsewhere so it stays under 52,500 B). The multi-spec console approves re-check items through its existing Queue writes `Q#` rows (staged at the parent), and its executor runs after the parent's final merge.
- [ ] **Execution after merge only:** an approved proposal executes (close with comment, or narrowing comment) only once the run's merge has landed — `pr-first`: a new step in `plugin/skills/_shared/pr-first-merge-post-merge.md` (outcome `merged`); `local-merge`: after the merge completes in wrap-up's local-merge finish. Each execution logs one `AUTO` line naming the record and the action. Under `work-backend: local-files` (no comments on local records), a close marks the record closed through `local-store.js` with the closing text appended to its body, and a narrowing comment is appended to the body.
- [ ] **Residue:** an approved proposal whose run ends with its PR open (or its merge not completed) is console residue naming the record and the PR — a read-time-derived kind in `plugin/bin/lib/console/residue.js`, listed by `console-residue.js --run`.
- [ ] Tests for every Acceptance Criterion below.
- [ ] Fail-closed guards: a record with zero parseable Deliverables / Acceptance Criteria is never a candidate (named in the `SCANNED` line). The executor re-reads the target record and the merge state immediately before acting and holds the proposal as residue — never executes — when either read fails, a value (PR reference, verdict) is malformed, the record is closed or claimed `bot:in-progress`, or its body changed since staging (body hash or `updatedAt` recorded at staging); each hold logs one `SKIP` line.
- [ ] Residue is terminal: an approved proposal whose PR merges after the run's session ends is not picked up by any later pass — it stays console residue whose `console-residue.js --run` line carries the paste-ready command a human runs to execute it. A PR closed unmerged drops the approval with one logged line and no close or comment.

## Acceptance Criteria

1. With a fixture open-records file and a fixture changed-paths list, an open record whose Key File is in the changed paths is a candidate and one whose Key Files are all outside it is not.
2. A fixture `parent-issue` record, a `bot:in-progress` record, a `digest` record and a record in the run's own set are never candidates even when their Key Files intersect; a candidate whose only intersecting path is a hub is not a candidate.
3. With the cap set to N and N+2 qualifying records, exactly N are returned for judging and the `SCANNED` line written to `decisions.md` names the 2 over-cap record numbers.
4. A fixture verdict with every deliverable `satisfied` stages a close proposal whose body quotes each hunk beside each deliverable's text; a verdict with some `satisfied` and some `not-satisfied` stages a narrowing proposal; a verdict with some `satisfied` and some `cant-tell` stages a narrowing proposal, not a close; an all-`cant-tell` or all-`not-satisfied` verdict stages nothing.
5. A `satisfied` verdict whose quote does not appear in the fixture diff hunks is treated as `cant-tell` (a would-be close becomes a narrowing proposal).
6. `console-resolve.js` resolves the new prefix `pending` at `autonomy: unattended` with `consoleAutoResolve` true; under control mode it resolves `carried` and is not executed.
7. An approved close proposal with the run's PR unmerged is not executed, and `console-residue.js --run {run-dir}` lists it naming the record number and the PR.
8. An approved close proposal after the merge has landed is executed by the post-merge step and logged with one `AUTO` line naming the record.
9. `wc -c < plugin/skills/flow/multispec-review-console.md` prints a value below 52,500 after the change.
10. A fixture rename (`git mv` of a Key File) makes the record a candidate through either path; a deliverable no hunk touches is `cant-tell`.
11. A multi-spec fixture run stages the re-check proposal at the parent, renders it as a Queue writes `Q#` row in the multi-spec console, and its approval is executed only after the parent's final merge.
12. A candidate whose body has no parseable Deliverables or Acceptance Criteria is excluded and named in the `SCANNED` line, never judged.
13. With the merge-state read or the target-record read failing (fake runner), an approved proposal is not executed, stays residue, and logs one `SKIP` line.
14. An approved proposal carrying a malformed PR reference or verdict is not executed, stays residue, and logs one `SKIP` line.
15. An approved proposal whose target record was closed, claimed `bot:in-progress`, or edited (body hash changed) since staging is not executed, stays residue, and logs one `SKIP` line.
16. An approved proposal whose PR is still open when the session ends is listed by `console-residue.js --run` with a paste-ready execute command; one whose PR was closed unmerged is dropped with one logged line and no close or comment is made.

## Technical Approach

The candidate pass is a pure function over (open records, changed paths, hub set, the run's own record numbers, cap). The CLI reads the open records from a passed file (the session record snapshot under `github-issues`, `local-store.js` under `local-files`) and computes the changed paths with `git`; if it shells out, it follows the `gh-api-module-pattern` project skill's injectable-runner seam and CLI wrapper contract. The judge dispatch lives in skill prose (a CLI cannot dispatch agents); a second CLI verb (or the same CLI) takes the judges' verdicts as JSON, applies the quote check and stages the proposals.

### Data / API Surface

- `recheck.js`: `selectCandidates({ openRecords, changedPaths, hubPaths, ownRecords, cap }) -> { candidates: [{ number, intersecting }], overCap: [number] }`; `outcomeFor(verdicts, hunks) -> 'close' | 'narrow' | null` (names are the builder's call).
- Judge verdict, per deliverable: `{ deliverable, verdict: 'satisfied' | 'not-satisfied' | 'cant-tell', quote? }`.
- Staged id: a new prefix, one file per record (e.g. `followup-recheck-{N}.md`), routed to Queue writes, resolving `pending` at every tier.
