# 5119: Ship the machine-wide full-suite slot lock to consumer projects through verify.js

Surface: backend

**Related:** #5150 (lands after this record: rerun concurrency inside one checkout, the per-slot scratch path, timeout back-off), #5117, #4347, #3969, #4333; near-duplicate screen: #4321, #3765, #4591, #4685, #4898, #5075, #3067, #3813, #4128, #4130, #4329, #4362, #4400, #4424, #4492, #4494, #4768, #4769, #4930, #5033, #5133, #5135, #5136, #4499, #4686, #4892, #5069

## Current State

- `tools/run-tests.js` holds this repo's cross-process full-suite slot semaphore: exclusive `wx` lock create (`createLock`, :209), dead-pid reclaim under a `.reclaim` mutex (`readHolder`/`reclaimSlot`, :238/:289), FIFO `ticket-<seq>.json` queueing with a per-ticket `slots` limit (`takeTicket`/`ticketsAhead`/`acquireSlot`, :338/:354/:410, #4333), a separate `subset/` lane for `--files-from` runs (`slotLane`, :143), and a waiting line naming the holder's pid and cwd (:439). Lock dir: `CT_TEST_SUITE_SLOT_DIR`, else `<os.tmpdir()>/ct-test-suite-slots`; slot count from `CT_TEST_SUITE_SLOTS` (default 1); `CT_TEST_SUITE_SLOT_HELD=1` is set for the child so a nested run skips the slot (:577, :633). `tools/` does not ship (ADR 0015), so only this repo's own `npm test` goes through the lock.
- `plugin/bin/verify.js` runs a consumer project's checks with no lock. `runChecks` (`plugin/bin/lib/verify/run.js:142`) runs suites one after another within a run, and flaky retries run serially inside it via `retryHook` (`verify.js:755`, `flaky.js:61`). After the checks, `--baseline` adjudication (`verify.js:840` → `baseline.js` `adjudicate()`) re-runs failing files at base, isolated at HEAD and on retry through `pool(work, concurrency = 4, …)` (`baseline.js:314`, :444, :471, :552), then runs each failing check's full command once more at base (`computeFixed`, :602).
- With N pipeline sessions on one machine, every session's full suite and every session's adjudication run at the same time. Field evidence (machine memory exhaustion on 2026-11-08; a consumer project with about 9 sessions whose shared test database starved on disk syncs) shows the full runs and the adjudication reruns both need a machine-wide bound, and that the right bound depends on the suites' shared resources, not on core count: a 30 min suite × 9 sessions at 1 slot is a queue of several hours.
- `verify.js` never reads `.claude-tweaks/policy.yml` (its header, :6: command resolution stays caller-side, Option A). It reads `.claude-tweaks/verify-scope.json` through `readDeclaration` (`plugin/bin/lib/verify/declaration.js`); a reader that predates a top-level key ignores it (`declaration.js:154`).
- This repo's declaration runs `tests` as `npm test` and its impact subset as `node tools/run-tests.js --files-from {files}`, so a verify.js run here spawns a child that itself takes the same slot.
- #5117 cuts the number of local full runs per pipeline and #4347 takes the full-suite verdict from CI where a `ci` block is declared; neither bounds the runs that stay local.

## Deliverables

1. **Shipped slot-lock module.** Move the lock primitives out of `tools/run-tests.js` into `plugin/bin/lib/suite-slot.js`: `isPidAlive`, `createLock`, `readHolder`, `reclaimSlot`, `ensureOwnDir`, the ticket queue, `acquireSlot`, `releaseSlot`, `slotLane`, `resolveSlots`. `acquireSlot` takes the log prefix and the raise-the-limit hint as parameters (today it hardcodes `run-tests.js:` and `set CT_TEST_SUITE_SLOTS`) and returns `{ lockPath, index }`, where `index` is the slot number it took. `tools/run-tests.js` requires the module and re-exports the names its tests import today. One implementation, one lock dir, one ticket format, so `npm test` and verify.js runs queue in the same lanes.
2. **verify.js takes a slot.** Before spawning its first local check, verify.js takes a slot in one of two lanes (the lane-choice rule is in Technical Approach). It holds the slot through `runChecks`, so flaky retries run under it, and releases it before adjudication. `--baseline` adjudication, including its base-side full run, then takes a full-lane slot of its own and holds it until `adjudicate()` returns. Releasing between the two phases means no process ever holds one slot while waiting for another. The slot is freed on normal exit, on a thrown error, and on SIGINT/SIGTERM/SIGHUP. While it holds a slot, verify.js sets `CT_TEST_SUITE_SLOT_HELD=1` for every child it spawns, so a child that runs `tools/run-tests.js` (or verify.js again) skips the lock instead of deadlocking on it. A verify.js that inherits `CT_TEST_SUITE_SLOT_HELD=1` takes no slot at all. A run whose every suite comes from CI (#4347), or whose selection is `none`, takes no slot.
3. **Slot count resolution: declaration, then policy, then 1.** A new optional top-level `concurrency` block in `verify-scope.json` with one key here, `suiteSlots` (positive integer). Any other key inside the block is a validation error naming the allowed keys, matching the `impact`/`ci` blocks. A new verify.js flag `--default-suite-slots <n>` supplies the fallback used only when the declaration declares no `suiteSlots`. A new policy key `verify-suite-slots` (integer, min 1, default 1), registered per the policy-key-addition skill, is resolved caller-side by `plugin/skills/test/verification.md` and passed as that flag at every invocation. The key is shown in the Pipeline Config Manifesto wherever that skill's checklist puts it. With neither, the count is 1. The same count applies to both lanes. verify.js reads the `concurrency` block from the declaration it already reads under `--scope`; without `--scope` it reads only this block from the default declaration path, and a declaration that fails validation falls back to the flag, then 1, with one stderr line naming the error.
4. **Worker cap env var.** While a slot is held, verify.js exports `CT_TEST_WORKERS` to its children: `max(1, floor(cores / (2 × slots)))`, so the suites running at once together use about half the machine. `os.availableParallelism()` supplies the core count, and a value the caller already set wins. `verification.md` documents how to wire it into `node --test --test-concurrency`, `go test -p` and `pytest -n`.
5. **Waiting line.** A verify.js run that cannot take a slot at once prints one stderr line naming the holder (pid, cwd, since), the lane, and how to raise the limit (`concurrency.suiteSlots` in verify-scope.json, or the `verify-suite-slots` policy key). It prints the line once per wait. The same line is written to report.json as `slot: { lane, index, waitedMs, slots, source }`, where `source` is `declaration`, `flag` or `default`.
6. **Docs.** In `plugin/skills/test/verification.md`, cover the lanes, the resolution order, the held-slot env vars, and the guidance that the right `suiteSlots` depends on what the suites share (one database server, one device, a port range) rather than on core count, with the queue-length arithmetic above as the worked example. Add the policy key row in `plugin/skills/_shared/policy-schema.md` and the new `concurrency` block in the verify-scope declaration docs.

## Acceptance Criteria

- Two concurrent verify.js full runs from different worktrees, sharing one real temp lock dir (`CT_TEST_SUITE_SLOT_DIR`) with a fake spawn: the second run's check spawns only after the first run's last check exits. Pinned by a test that fails when the slot acquisition is removed.
- A lock file naming a dead pid is reclaimed by the next verify.js waiter, under the same dead-pid and reclaim-mutex rules `tools/run-tests.js` applies today. `tools/run-tests.js`'s existing slot tests stay green, run against the moved module.
- `node tools/run-tests.js` and a verify.js full run sharing one lock dir serialize against each other in both orders.
- A verify.js run whose only suite runs an impact subset takes the subset lane and does not wait behind a held full-lane slot.
- A failing scoped run's `--baseline` adjudication takes a full-lane slot: with a full-lane slot held by a live sibling pid, adjudication's first rerun spawns only after that slot is released.
- Slot count: a declaration `concurrency.suiteSlots: 2` beats `--default-suite-slots 3`, which beats the default of 1. Each case shows in `report.json`'s `slot.source`. An unknown key inside `concurrency`, or a non-positive or non-integer `suiteSlots`, fails declaration validation with a message naming the allowed keys.
- A verify.js run started with `CT_TEST_SUITE_SLOT_HELD=1` takes no slot, and every child verify.js spawns while holding a slot sees `CT_TEST_SUITE_SLOT_HELD=1` and a positive-integer `CT_TEST_WORKERS`.
- A waiting run prints exactly one stderr line naming the holder's pid and cwd and the raise-the-limit hint.
- `verify-suite-slots` passes the policy-schema conformance tests, and `verification.md`'s invocations pass `--default-suite-slots`.
- This repo's committed `.claude-tweaks/verify-scope.json` stays readable by the latest release's `declaration.js` (`tests/verify-scope-declaration.test.js`'s previous-reader pin stays green).

## Release Note

Parallel pipeline sessions on one machine now queue their test suites and baseline reruns behind a shared slot instead of running them all at once; a project sets how many may run together in verify-scope.json.

## Technical Approach

**Lane choice (verify.js).** Full lane: no `--scope`, a selection of mode `full` with no impact subset, or `--stamp-suite` (a chunk of the full suite). Subset lane: every other selection that runs a local check (`scoped`, `tool-scoped`, `static-only`, or `full` with the impact suite replaced by its subset command). Adjudication always takes the full lane, whatever lane the checks used: its base-side full run is a full suite, and the field evidence shows adjudication is where load amplifies.

**Acquisition.** Wrap the `runChecks` call (`verify.js:814`) and the `adjudicate()` call (`verify.js:863`) each in `acquire → try { … } finally { release }`. The module's `acquireSlot` is synchronous and polls with `Atomics.wait`, as today. Keep it synchronous: no check is running while verify.js waits, and the wait happens before the `--baseline` signal handlers (`baseline.js:438`) are installed. A signal that lands during the wait exits by default and leaves only the waiter's ticket, which reads as stale once the pid is dead (the module's documented rule). Once a slot is held, verify.js installs SIGINT/SIGTERM/SIGHUP handlers that release the slot and then re-raise the exit code (`128 + signal`). These handlers must work alongside `adjudicate()`'s own handlers, which call `process.exit`: release the slot from a `process.on('exit')` hook that calls `releaseSlot` (synchronous, never throws), so every exit path frees it.

**Held-slot env.** Set `CT_TEST_SUITE_SLOT_HELD=1` and `CT_TEST_WORKERS` on `process.env` for the duration of the hold, restoring the prior values on release. `runOne` spreads `process.env` into every child (`run.js:77`), so retries, adjudication reruns and the base full run all inherit them with no new plumbing. The slot index stays in-process: verify.js passes the adjudication slot's `index` to `adjudicate()` as a new `slot` option (unused until #5150). It is never exported, because a nested process inheriting its parent's index would collide with the parent's own use of it.

**Policy value.** `verify.js` keeps its no-policy boundary. `verification.md` resolves `verify-suite-slots` with `resolve-policy.js` and passes `--default-suite-slots`. The flag's name says it loses to the declaration. That inversion of the usual CLI-over-config order is deliberate: the declaration sits next to the suites the number describes.

## Gotchas

- **Nested deadlock.** This repo's `tests` suite is `npm test` → `tools/run-tests.js`, which takes the same full-lane slot. Without `CT_TEST_SUITE_SLOT_HELD=1` in the child env, verify.js waits on itself forever. Pin it with a test that runs a fake check calling the module's acquire.
- **This repo's own suite runs verify.js tests under a held slot.** `tools/run-tests.js` sets `CT_TEST_SUITE_SLOT_HELD=1` for the whole suite, so every test of the new acquisition must delete that var from the child env and point `CT_TEST_SUITE_SLOT_DIR` at a fresh temp dir, or it tests nothing. The `lock-race-test-seam` skill covers the injectable-clock seam for the race tests.
- **Mixed-version sessions.** A sibling worktree on an older `tools/run-tests.js` uses the same lock dir and ticket format, so it interoperates. A ticket's `slots` limit already lets waiters with different limits share one lane (#4333's floor rule). Do not change the lock dir, file names or ticket JSON shape.
- **The lock dir follows `os.tmpdir()`.** A caller that overrides TMPDIR for its own process (as run-tests does for its children) computes a different dir. That is harmless only because such children also inherit `CT_TEST_SUITE_SLOT_HELD=1`. Keep both env vars together.
- **Not `file-lock.js`.** `plugin/bin/lib/file-lock.js` is a short-wait mkdir mutex with age-based reclaim. This is a long-hold counted semaphore whose holders may legitimately run for hours, so they must never be reclaimed on age. Do not merge the two.
- **Run the repo's tests through `tools/run-tests.js`** (it holds the slot); other sessions may be running suites on this machine.
- **The declaration contract.** `concurrency` is new surface. Follow the `verify-scope-rule-kind` skill's rules for a declaration change, and keep this repo's committed declaration free of `concurrency` in this PR: it needs no override, and the previous-release reader pin must keep reading it.
- The consumer evidence in Current State is a motivating example only. Shipped code and docs stay stack-agnostic.
