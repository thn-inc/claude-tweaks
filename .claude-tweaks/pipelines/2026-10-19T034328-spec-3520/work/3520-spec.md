# 3520: dispatch: serialize or pre-announce the merge order of a near-duplicate pair dispatched in one firing

Surface: infra

**Related:** #3278, #1944, #3366, #2986, #3483, #3187, #3498

## Current State

`/claude-tweaks:dispatch` builds groups one at a time (`plugin/skills/dispatch/SKILL.md` Step 5, #155), and since #3278 every record is its own group. The one concurrency guard left is the neighbour-in-flight pass (`plugin/skills/dispatch/queue-pull-script.md`, `plugin/bin/lib/dispatch/in-flight-neighbours.js`): a candidate waits while a record that shares a linking `### Key Files` entry with it holds a live claim. A `pending-review` group keeps its claim live (`firing-exclusion.md`), so the guard covers both a build still running and a finished build whose PR is still unmerged.

The guard is blind to records whose overlap does not show in Key Files. On 2026-10-17 an explicit-list firing (`#3417,#3419,#3012`) dispatched all three. Neither #3417 nor #3419 had a `### Key Files` section, so no file link existed between them. The cross-group near-duplicate pass (`findNearDuplicates`, `plugin/bin/lib/issues/near-duplicate.js`, #1944) did flag `#3419/#3417` and `#3417/#3012`, but it only prints an `AUTO` line to stderr and is "warning only, never a gate" (`SKILL.md` Step 3). PR #3450 (#3419) merged first, then PR #3485 (#3417) turned `DIRTY` on `docs/donts.md`, `docs/incident-log.md` and `.claude/skills/pre-tool-use-gate-exemptions/SKILL.md`, because both records wrote the same IL-150 entry. Reconciling took about 20 minutes (merge commit `6cc4a8ea4`).

Measured at shaping time (2026-10-18) with today's `findNearDuplicates`:

- Both flagged pairs fired on `body-anchor-overlap` alone (score 1). The real conflict pair, #3417/#3419, shared three `## Current State` anchors: `docs/donts.md`, `fs.realpathSync`, `fs.realpathSync.native`. The pair that merged cleanly, #3417/#3012, shared one (`plugin/bin/lib/hooks/pre-tool-use.js`).
- Across the 143 open records that are neither parent nor parked, pairs sharing an anchor break down as 372 sharing exactly one, 42 sharing two, and 53 sharing three or more. Any anchor-only hit is therefore far too common to defer on. Two or more shared anchors is a usable bar.
- The drain-PR overlap machinery (`drain-pr-overlap.md`) already re-checks each later group against PRs this firing opened, and its Step 6 hold keeps an `auto:merge` group out of the merge decision while an overlapping drain PR is open. Both key on changed-file overlap only, so a near-duplicate pair whose shared files appear only during the build is invisible to them.

The 2026-10-18 brainstorm on this record (via `/claude-tweaks:specify`) decided the direction. The record's option (a), serializing within a firing, was rejected: for a pair without `auto:merge` it means dropping the second record for the whole firing, which overrides an explicit list. Option (b) alone was rejected because it only makes the reconcile predictable. Co-building a pair would reverse #3278, and stacking branches would tie a false-positive partner to another PR's merge. The decided shape: a strong near-duplicate of an in-flight record counts as a neighbour, the same posture #3278 already gives file neighbours, and an explicit list names the predicted conflict and merge order before it dispatches.

## Deliverables

1. **Near-duplicate neighbour relation.** The neighbour-in-flight pass treats an in-flight record as a neighbour of a candidate when, besides today's linking-Key-File rule, `findNearDuplicates` reports a *strong* hit between them. A strong hit means at least 2 shared `## Current State` anchors, or a score of at least 2. Generic anchors never count, since `extractCurrentStateAnchors` already drops them via `isGenericAnchor` (#3141). `findNearDuplicates` hits gain an additive `sharedAnchors: string[]` field so the threshold can be read off the hit. Existing fields and ordering are unchanged. The threshold is one named exported constant, not a magic number repeated at call sites.
2. **Exclusion entry shape.** A near-duplicate neighbour appends the existing `reason: 'neighbour-in-flight'` entry. Each `detail.neighbours[]` element carries `{number, files, signals?, sharedAnchors?}`: `files` stays the shared Key Files (possibly empty), and `signals`/`sharedAnchors` are present only when the near-duplicate rule matched. No new reason is introduced, so `next-ranking.md`'s `groupIsExcluded(..., ['oversized', 'firing', 'neighbour-in-flight'])` call, the bare-drain skip and the `#N`/`#N,#M` "print and dispatch anyway" posture all apply unchanged.
3. **Pool fetch carries titles.** The in-flight pool fetch in `queue-pull-script.md` (`gh issue list --label bot:in-progress ... --json number,body,labels`) adds `title`, and `mcp-transport.md`'s Step 2 pool writes `[{number, title, body, labels}]`, so title similarity can fire. `neighbourClaimTargets` returns the near-duplicate neighbours too, so the MCP path reads their claims.
4. **Report line.** `neighbour-in-flight-report.md` renders a near-duplicate neighbour as `#{m} (near-duplicate: {signals}; shared: {sharedAnchors})`, and a file neighbour exactly as today, `#{m} ({files})`.
5. **Explicit-list predicted conflict.** For `#N,#M,...`, after `selectGroupsForExplicitList` and before Step 4, every strong near-duplicate pair whose members sit in two different selected groups prints one line: `#{A} / #{B} predicted to conflict (near-duplicate: {signals}; shared: {sharedAnchors}); dispatch order #{A} then #{B}, merge #{A} first`. It also logs one `AUTO {time} — dispatch: predicted conflict #{A} / #{B} ...; merge #{A} first. Reversibility: n/a.` line to `decisions.md`. Both still dispatch, in the order already selected.
6. **Pairs persisted for later steps.** The cross-group near-duplicate pass in `queue-pull-script.md` keeps its stderr `AUTO` line and also writes every strong pair, as `[{records: [A, B], signals, sharedAnchors}]`, to a session-scoped `dispatch-near-dup-pairs.json` (`_shared/session-tmp-root.md`). Weak pairs keep the stderr line only.
7. **Drain-PR overlap and auto-merge hold.** `drain-pr-overlap.md`'s Step 4 re-check also counts a hit when this group's member is a strong-pair partner, per `dispatch-near-dup-pairs.json`, of a record that a `dispatch-drain-prs.json` entry closes (`closingIssueNumbers`). Such a hit renders the same warning with `(near-duplicate of #{partner})` in place of a file list. Its Step 6 hold treats a still-open drain PR closing a strong-pair partner as an overlap hit, and logs a line that still matches `bin/lib/console/resolve.js`'s `DRAIN_OVERLAP_HOLD_RE` (`held — overlaps drain PR #{pr} ...`), with the near-duplicate detail after the PR number.
8. **Report block.** `reporting.md`: a dispatched group whose member appears in a strong pair with another group dispatched this firing carries one `predicted conflict with #{partner} (PR #{pr}) — merge #{first} first` line in its report block.
9. **Prose.** `SKILL.md` Step 3's "Near-duplicate candidate warning" paragraph no longer says "warning only, never a gate". It states that weak pairs only warn and strong pairs feed the neighbour guard and the predicted-conflict line, and it cites this record. `queue-pull-script.md`'s reason list entry for `neighbour-in-flight` and its pass comments describe both neighbour rules. `docs/plugin-structure.md`'s `near-duplicate.js` and `in-flight-neighbours.js` descriptions name the new consumer.

## Release Note

Defer a dispatch drain's record while a strong near-duplicate of it is still being built or awaiting merge, and name the predicted conflict and merge order before an explicit-list firing dispatches both.

## Technical Approach

- **Threshold, computed once.** Add `sharedAnchors` to each `findNearDuplicates` hit: the intersection already computed for Signal 3, collected rather than short-circuited at the first match (generic spans never reach it: `extractCurrentStateAnchors` drops them). Export `isStrongNearDuplicate(hit)` and its constant, for example `NEIGHBOUR_MIN_SHARED_ANCHORS = 2`, alongside the existing `MIN_REFUSAL_SCORE`. The rule is `hit.sharedAnchors.length >= 2 || hit.score >= 2`. Every consumer here (neighbour pass, pairs file, explicit-list line) calls that predicate. None re-derives the rule.
- **Neighbour pass.** In `neighbourInFlightExclusions`, after `findInFlightNeighbours` builds the Key-File map, run `findNearDuplicates(candidate, inFlight)` per candidate and merge strong hits into the same per-candidate neighbour list. Key the list on in-flight number, so a record that matches both ways yields one element carrying both `files` and `signals`. Liveness stays the claim-blob read, each in-flight number read at most once, as today. `neighbourClaimTargets` (the MCP split) must return the same union.
- **Explicit list.** The predicted-conflict render reads `dispatch-near-dup-pairs.json` filtered to pairs whose two members land in two different `selectedGroups`. "Dispatch order" is `selectedGroups`' order, which Step 5 already follows, and that is the merge order to announce.
- **Drain-PR overlap.** Step 4's and Step 6's checks gain one extra hit source: `dispatch-near-dup-pairs.json` ∩ `dispatch-drain-prs.json`'s `closingIssueNumbers`. `detectCrossPRFileOverlap` itself is unchanged. The near-duplicate source is a separate small check composed beside it, so its file-overlap contract and tests stay as they are.
- **Why the guard covers the across-firing case.** A drain record deferred this firing becomes eligible again once the partner's claim stops reading live, which happens when its PR merges and the claim is released. A later firing then builds on top of the merged partner, so no persisted cross-firing state is needed.

## Gotchas

- **The threshold is a calibration from two data points.** The ≥2-shared-anchors / score ≥2 bar was chosen at shaping time (a /specify call, not a user decision) from one real conflict (three anchors) and one clean merge (one anchor), plus the queue distribution in Current State. If later firings show records starving or real conflicts slipping through, adjust the one constant. Do not add a second rule beside it.
- **Starvation is bounded by claim liveness, not by time.** A deferred record waits only while its partner's claim reads live. A `pending-review` PR nobody merges keeps the partner live until its claim TTL lapses, so a strong near-duplicate can wait for days. That is the intended trade (the build would conflict anyway), and the neighbour-in-flight report line keeps it visible.
- **`findNearDuplicates` skips `parent-issue` and `parked` records,** and the specify shaping refusal (`shapingRefusal`, `MIN_REFUSAL_SCORE`) reads the same hits. Adding `sharedAnchors` must not change any existing field or score, or the refusal's behavior shifts. AC4 pins that.
- **Keep `detectCrossPRFileOverlap`'s contract untouched.** Flow's multi-spec conflict detection and dispatch's Step 3 cross-PR report both rely on it as a pure file-overlap function.
- **The hold line has a second reader.** `bin/lib/console/resolve.js` parses it with `DRAIN_OVERLAP_HOLD_RE` (`held\s*[-—]\s*overlaps drain PR #(\d+)`). The near-duplicate wording must keep that prefix verbatim, or the `unattended` console auto-resolver silently stops honoring the hold.
- **Same-group pairs stay silent.** A fast-lane bundle's members are co-built, and `bundleFastLaneSingletons` keeps file-sharing records apart already. This record does not add near-duplicate disjointness to bundling.
- **Prose tests pin dispatch text.** Run the full suite before merge, not just the touched suites. `tests/dispatch-drain-overlap-prose.test.js` and the MCP neighbour test read live skill prose.

## Current State

`/claude-tweaks:dispatch` Step 3 logs a near-duplicate warning (`findNearDuplicates`, #1944) when two records landing in different groups share body anchors, and states it is warning-only. On 2026-10-17 an explicit-list firing (`#3417,#3419,#3012`) logged `#3419/#3417` and `#3417/#3012` as near-duplicates and dispatched all three. At close-out, PR #3450 (#3419) merged first and PR #3485 (#3417) turned `DIRTY`: three files conflicted (`docs/donts.md` [IL-150], `docs/incident-log.md` IL-150, `.claude/skills/pre-tool-use-gate-exemptions/SKILL.md`), each edited by both records. Reconciling cost one merge, a hand-resolved three-way prose merge, a full verify and a re-push (about 20 minutes), and the second record also needed an allowlist entry for a file the first had not touched.

## Deliverables

Decide whether an explicit-list or drain firing that has just logged a near-duplicate pair should (a) serialize the pair — dispatch the second record only after the first's PR merges, or hold its second Task call — or (b) keep dispatching both but carry the pair into each affected group's report block and into the drain-PR overlap check as a predicted conflict, so the merge order is named before close-out.

Record the decision in `plugin/skills/dispatch/SKILL.md` Step 3 (Near-duplicate candidate warning) and, for (a), in `sequential-execution.md`; for (b), in `reporting.md` and `drain-pr-overlap.md`.

## Open Question

Serialize a flagged pair (slower drain, no conflicts) or keep dispatching both and surface the predicted conflict in the report (faster, a human reconciles)? The warning-only design (#1944) was chosen to avoid gating selection on a heuristic; the conflict cost observed here is the counter-evidence.
