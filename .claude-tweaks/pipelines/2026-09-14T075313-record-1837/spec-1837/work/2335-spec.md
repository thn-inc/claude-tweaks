# 2335: verify/stamp.js: tmp filename shape changed silently; count-stamp write coverage lost

Surface: infra

## Current State

Found during a pre-release whole-branch review. Migrating `plugin/bin/lib/verify/stamp.js` off
the deleted `writeJsonAtomic` silently changed the temp filename shape from `${jsonPath}.tmp` to
`${basename}.tmp-${pid}` (confirmed, ~line 63: `writeFileAtomic(jsonPath, ...)`): the old
`lib/verify/atomic-write.js` used `const tmpPath = \`${filePath}.tmp\`;` while the replacement
(confirmed, `lib/atomic-write.js:27`) uses `path.join(dir, \`${path.basename(filePath)}.tmp-${process.pid}\`)`.
Any fixture, cleanup script, or `.gitignore` entry keyed on the old literal no longer matches.

Separately, `tests/bin-lib/verify/stamp.test.js:60`'s new pid-suffix pin covers only the
verify-pass stamp write; the count-stamp write migrated in the same commit (confirmed,
`verify.js:374`: `writeFileAtomic(countStampPath, ...)`) is unpinned. The deleted
`tests/bin-lib/verify/atomic-write.test.js` was the only place that had covered the count-stamp
write shape, and nothing replaced that coverage. The legacy bare-SHA twin write two lines below
the count-stamp call (confirmed, `stamp.js:69`: `const tmp = \`${legacyPath}.tmp\`;`) still uses
the old `.tmp` shape, unmigrated.

## Deliverables

- Sweep for any remaining references to the old `.tmp` (no pid suffix) filename shape.
- Add a test pinning the count-stamp write's temp-filename shape, matching the coverage the
  deleted `atomic-write.test.js` used to provide.
- Confirm the legacy bare-SHA twin write's un-migrated `.tmp` shape is intentional (it predates
  the pid-suffix convention) or migrate it too for consistency.

## Acceptance Criteria

The count-stamp write path has an explicit test for its temp-file naming, and the legacy-write
inconsistency is either documented as intentional or fixed.

## Technical Approach

1. `grep -rn '\.tmp"' \| grep -rn "\.tmp\`"` across `plugin/` and `tests/` for any remaining
   reference to the bare (non-pid-suffixed) `.tmp` shape tied to `verify/stamp.js`'s writes
   specifically (a broader repo-wide `.tmp` grep will also hit unrelated call sites — scope the
   sweep to files this migration actually touched).
2. Add a test in `tests/bin-lib/verify/stamp.test.js`, mirroring the existing pid-suffix test at
   line 60 but targeting the count-stamp write (`verify.js:374`) instead of the JSON stamp write
   — same fake-fs assertion pattern (`!Object.keys(fsImpl.files).some((p) => p.endsWith('.tmp'))`
   plus a pid-suffix check on the actual tmp key used).
3. For the legacy bare-SHA twin write (`stamp.js:69`): read the surrounding comment ("The legacy
   bare-SHA twin write just below is untouched (Non-Goals) — independently transitional,
   unrelated to this migration's collision-safety concern") to judge whether leaving it
   unmigrated was a deliberate scoping decision from the original PR, and either add a comment
   confirming that's still the right call, or migrate it to the same `writeFileAtomic` primitive
   for consistency if no reason to keep it separate survives scrutiny.

### Key Files

- `plugin/bin/lib/verify/stamp.js` (lines ~63, ~69) — the migrated JSON-stamp write and the
  still-legacy bare-SHA twin write
- `plugin/bin/verify.js` (line 374) — the count-stamp write, needs test coverage
- `tests/bin-lib/verify/stamp.test.js` (~line 60) — add the count-stamp temp-filename test

## Gotchas

- The legacy twin write's own code comment already states it was deliberately left untouched
  ("Non-Goals") — don't assume this is an oversight without reading that reasoning first; the
  fix may be "confirm and document," not "migrate."
- Scope the `.tmp`-reference sweep to this migration's own affected files — a repo-wide grep for
  bare `.tmp` will surface many unrelated hits (other modules' own temp-file conventions) that
  are out of scope for this record.
