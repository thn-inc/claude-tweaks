# 1840: harness-health: a drift record's Proposed block is a filing-time template snapshot, and nothing tells the builder to re-derive it from the installed template

Surface: infra

## Current State

`toIssuePayload` (`plugin/bin/lib/harness-health/issue-payload.js`) composes every harness-health `patch` finding's Deliverables as two fenced blocks, `**Current:**` (`finding.oldString`) and `**Proposed:**` (`finding.newString`), plus a header line naming asset, section, category (`drift` | `template-conformance` | `best-practice`), classification, and confidence; `specShapedBody` adds the `Verified-as-of: {sha}` stamp. For CLAUDE.md and rules, dimensions 7 and 8 of `_shared/harness-health-analysis.md` judge against the live origin template (`skills/init/claude-md-template.md`, `skills/init/rules-template.md`), and `judge-procedure.md`'s finding schema carries no field naming which template the Proposed text came from or which plugin version rendered it. The body therefore reads as "replace Current with Proposed", and nothing in `flow/materialize.md` or `build/SKILL.md` distinguishes a `by:harness-health` record's Proposed block from authored deliverable text.

Observed on plugin 6.114.1: a Philosophy "No implicit deferrals" drift record filed against the 6.111.0 template was built after the template line had changed wording; the planner re-read the installed template on its own initiative and the whole-branch review confirmed the committed line byte-identical to it. Neither step was required by the record or by `/build`; a builder applying the Proposed block literally would have shipped text the next sweep re-files.

`plugin/bin/lib/hooks/session-start.js` already reads the running plugin's version from `{pluginRoot}/.claude-plugin/plugin.json`; `bin/harness-health.js` resolves `verifiedAsOf` once per run and threads it into `toIssuePayload`. `materialize.js` already parses one body-metadata stamp (`Verified-as-of`) into an envelope field (`drift`) with a stderr sentence on staleness.

## Deliverables

- [ ] **Name the template and its version at filing.** `judge-procedure.md`'s finding schema gains an optional `templateSource` (repo-relative path of the origin template the Proposed text was derived from), set by the judge for every `claude-md`/`rule` finding in the `template-conformance` and `best-practice` categories. `bin/harness-health.js` reads the running plugin's version once per run (the same `{CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` read `session-start.js` performs; `manifest-path.js` is for historical git refs, not the running build) and threads `pluginVersion` into `toIssuePayload` beside `verifiedAsOf`. When `finding.templateSource` is set, the body carries a metadata line `Template: {templateSource} @ {pluginVersion}` (same convention as `Verified-as-of`) and the Deliverables open with one sentence: the Proposed block is a snapshot of that template at that version; at build time re-derive the replacement from the installed template and treat the fence as the intended shape, not the bytes.
- [ ] **Materialize surfaces the version delta.** `record.js`: `extractTemplateStamp(body)` beside `extractVerifiedAsOf`. `materialize.js`: when present, read the installed plugin version (the same `.claude-plugin/plugin.json` read) and add `template: { path, recorded, installed, changed }` to the envelope; when `changed`, print one stderr sentence in the drift sentence's shape ("Proposed block was rendered from {path} at {recorded}; installed is {installed} — re-derive from the installed template before implementing"). Absent line → `template: null`, byte-identical behavior.
- [ ] **Build names the re-read.** `flow/materialize.md` gains a "Template snapshot" paragraph beside the drift paragraphs; `build/SKILL.md`'s writing-plans handoff adds: when `template.changed`, the plan's first task re-reads `{path}` at the installed version and derives the replacement from it, and the PR description quotes the installed template line the commit matches.
- [ ] **Tests.** `tests/bin-lib/harness-health/issue-payload.test.js`: `Template:` line and the snapshot sentence present for a `template-conformance` claude-md finding with `templateSource`, absent for a `drift` skill finding, absent when `pluginVersion` is not supplied. A sibling of `tests/materialize-drift.test.js` for the `template` envelope field and stderr sentence (recorded ≠ installed, recorded = installed, no line, unreadable manifest degrades to `null`). Prose pins for `judge-procedure.md`'s schema field, `materialize.md`'s paragraph, and `build/SKILL.md`'s handoff bullet.

## Acceptance Criteria

1. A harness-health CLAUDE.md `template-conformance` finding files a record whose body carries `Template: skills/init/claude-md-template.md @ {version}` and the snapshot sentence above the Current/Proposed fences; a skill `drift` finding's body is byte-identical to today's.
2. `node bin/materialize.js #N` on such a record reports `template.changed: true` and prints the stderr sentence when the installed version differs, `changed: false` and no sentence when equal, and `template: null` for a record without the line.
3. `build/SKILL.md` and `flow/materialize.md` state the re-derive rule once each; `judge-procedure.md` documents `templateSource`.
4. Replaying the reported case in a fixture (record stamped at an older version, installed template line reworded) yields a plan whose first task names the installed template read; quoted in the PR description.
5. `npm test` green; every existing case in `tests/bin-lib/harness-health/` and `tests/materialize-drift.test.js` passes unchanged.

## Technical Approach

Same shape as the `Verified-as-of` stamp: one optional body-metadata line written by the filer, one optional envelope field read by materialize, one prose consumer in build. Version, not sha, is the right key here — the template ships inside the plugin, so the installed plugin version is what the builder can compare against without a checkout of this repo. Do not rewrite already-filed records; only new filings carry the line.

### Key Files

- `plugin/bin/lib/harness-health/issue-payload.js` — `Template:` line + snapshot sentence when `templateSource` is set; `pluginVersion` param
- `plugin/bin/harness-health.js` — read the running build's version once from `.claude-plugin/plugin.json`; thread it
- `plugin/skills/harness-health/judge-procedure.md` — `templateSource` in the finding schema
- `plugin/bin/lib/issues/record.js` — `extractTemplateStamp`
- `plugin/bin/materialize.js` — `template` envelope field + stderr sentence
- `plugin/skills/flow/materialize.md` — "Template snapshot" paragraph
- `plugin/skills/build/SKILL.md` — writing-plans handoff bullet
- `tests/bin-lib/harness-health/issue-payload.test.js`, `tests/materialize-template-stamp.test.js` — new cases and pins

## Gotchas

- The running plugin's version is the installed build's `.claude-plugin/plugin.json` under `CLAUDE_PLUGIN_ROOT`, not this repo's `plugin/.claude-plugin/plugin.json`, which is ahead of the installed build during development; the sweep and materialize must both read the running manifest.
- `specShapedBody` renders metadata lines before the first `##`; keep `Template:` single-line and plain, never YAML.
- `docs-health`/`code-health`/`journey-health` payloads share the `verifiedAsOf` shape but have no origin template; do not add the line there.
- A `best-practice` finding may cite guidance rather than a template line; `templateSource` is optional, and the line is emitted only when the judge set it.

## Original request

**Summary:** A harness-health CLAUDE.md drift record quotes the template's replacement text as of the plugin version installed when it was filed; by build time a newer plugin can carry different wording, so applying the record's Proposed block literally closes one drift and opens another that the next sweep re-files.

**Kind:** Gap

**Affected component:** `/claude-tweaks:harness-health` (drift-record body for template-derived CLAUDE.md sections) and `/claude-tweaks:build`'s handling of `by:harness-health` records

**Use case:** A drift record for the Philosophy "No implicit deferrals" bullet was filed against the v6.111.0 template and built under v6.114.1, whose `skills/init/claude-md-template.md` line 154 had changed wording in the meantime (same mechanism, more precise phrasing). The record's body reads as a plain "replace Current with Proposed" instruction. The build only avoided re-introducing drift because the planner independently re-read the installed template and its whole-branch review confirmed the committed line byte-identical to that template — neither step was required by the record or by `/build`. A builder that trusted the Proposed block (the natural reading) would have shipped text the harness-health conformance sweep immediately flags again.

**Suggested remedy (either or both):** (a) harness-health drift records for template-derived sections state the template version the Proposed block was snapshotted from and instruct the builder to re-derive the replacement from the *installed* template at build time; (b) `/build`'s materialize step, for `by:harness-health` records carrying `Verified-as-of`, compares the record's plugin version against the installed one and notes a version delta in the plan so the re-read is a named step rather than a planner's initiative.

**Definition:** Clear

**Plugin version:** 6.114.1
