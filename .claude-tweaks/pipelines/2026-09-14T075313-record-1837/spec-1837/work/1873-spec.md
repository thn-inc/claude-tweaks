# 1873: Set meaningful GitHub label colors for risk/priority/size dimensions

Surface: infra

## Current State
`_shared/label-bootstrap.md`'s check-then-create loop creates every canonical label with `gh label create "$NAME" --description "$DESCRIPTION"` and no `--color`, so GitHub assigns each one a random palette color at creation. `bin/lib/issues/labels.js`'s `ensureLabelPayload(name, description)` validates only the description cap; the `LABELS_JSON` arrays every consumer substitutes are `[name, description]` pairs with no color slot. On this repo the result is arbitrary and in places inverted: `risk:low` is red-orange (`D93F0B`) while `risk:high` is blue (`0052CC`); `size:low` and `size:medium` share `E99695`; `priority:low` is purple and `priority:medium` blue. Nothing reads the colors today (the State-of-the-Union dashboard colors these dimensions on its own side), so the cost is human: a label list that cannot be scanned by color, and an API color that would be noise if any consumer started reading it.

The bootstrap's version marker (`claude-tweaks:bootstrapped-v6`) only triggers the create-if-missing loop after a bump; an existing label's color is never touched, so a color convention needs an explicit edit path for repos that already carry the set.

## Deliverables
- [ ] `LABELS_JSON` entries become `[name, description, color]` triples; `ensureLabelPayload(name, description, color)` validates `color` as six hex digits (uppercase-normalized) and rejects a missing or malformed one at construction, the same fail-loud posture the description cap has. The canonical array in `_shared/label-bootstrap.md`'s "Canonical LABELS_JSON — the full work-record taxonomy" section carries the colors.
- [ ] A color convention stated once in `_shared/work-record.md`'s label-family table (the taxonomy home) and applied in `label-bootstrap.md`'s array: severity dimensions grade red → amber → green (`risk:high` `D93F0B`, `risk:medium` `FBCA04`, `risk:low` `0E8A16`; `priority:high` `B60205`, `priority:medium` `FBCA04`, `priority:low` `C2E0C6`); `size:*` grades on one neutral hue by lightness (`size:high` `5319E7`, `size:medium` `8B5CF6`, `size:low` `D4C5F9`); `type:*` reuses GitHub's defaults (`type:bug` `D73A4A`, `type:feature` `A2EEEF`, `type:task` `EDEDED`); `auto:*` one hue, `bot:*` one hue, `needs:*` one hue, `ceremony:*` one hue — each family visually distinct from the graded dimensions.
- [ ] `label-bootstrap.md`'s loop passes `--color "$COLOR"` on create, and gains a reconcile branch on the version-bump path (`SKIP_BOOTSTRAP=false`): for each canonical label that already exists, `gh label edit "$NAME" --color "$COLOR" --description "$DESCRIPTION"` when either differs from the payload, so an existing repo converges to the convention on its next bootstrap; `LABEL_BOOTSTRAP_VERSION` bumps to `7`.
- [ ] Every consumer that substitutes its own `LABELS_JSON` subset (the six files citing `label-bootstrap.md`) is updated to triples, taking colors from the canonical array; `bin/lib/issue-branch-tracking.js`'s standalone `gh label create … --color FBCA04` line is left as is (it is not a canonical label) but noted.
- [ ] Tests: `tests/bin-lib/issues/labels.test.js` covers the color validation (valid, lowercase-normalized, missing, malformed); a conformance test asserts every canonical `LABELS_JSON` entry in `_shared/label-bootstrap.md` is a triple with a valid color and that graded dimensions follow the stated order; `tests/session-tmp-root-migration.test.js` and the other suites that scan `label-bootstrap.md`'s snippet stay green.

## Acceptance Criteria
1. A virgin repo bootstrapped by any consumer ends with every canonical label carrying its convention color; `gh label list --json name,color` on it matches the array.
2. On this repo, one bootstrap under version 7 rewrites `risk:*`, `priority:*`, and `size:*` to the convention without recreating labels or losing their descriptions or issue attachments.
3. `ensureLabelPayload` rejects a pair (no color) and a malformed color before any `gh` call.
4. The convention is written in exactly one place (`_shared/work-record.md`'s family table) with the values in exactly one array (`_shared/label-bootstrap.md`), and the conformance test pins both; `npm test` is green.

## Technical Approach
Extend the existing payload contract rather than adding a second color-only pass: the loop already carries name and description per label, and `gh label create`/`gh label edit` both accept `--color`, so a third array element is the smallest change that reaches every consumer through the one snippet they all cite. The reconcile branch is scoped to the version-bump path so the common `SKIP_BOOTSTRAP=true` case stays at zero `gh` calls (IL-85's cost). GitHub's own default palette is reused where a label maps to a default (bug/enhancement), and the graded dimensions use its well-known red/amber/green triplet so the meaning reads without a legend.

## Gotchas
- `gh label create --color` takes hex without `#`; keep the array values bare and let the conformance test reject a leading `#`.
- The reconcile branch must compare before editing: an unconditional `gh label edit` per label on every bump costs one API call per label per repo, which the marker exists to avoid; edit only on mismatch.
- The `claude-tweaks:bootstrapped-v{N}` marker label itself gets a fixed neutral color so it is visibly bookkeeping.
- Under `work-backend: local-files` there are no GitHub labels; the color is inert there and `ensureLabelPayload` still requires it so the array stays one shape.

## Original request

Right now `risk:*`, `priority:*`, and `size:*` labels (and similar dimension labels) don't appear to have a deliberate color convention set on GitHub — they likely render with default/arbitrary colors. Worth setting real colors that carry meaning (e.g. `risk:high` red, `risk:low` green, `priority:high` amber), the way GitHub's own default label set does for bug/enhancement/etc.

Context: the State-of-the-Union dashboard is adding semantic coloring for these dimensions on its own side (not pulling from GitHub's label colors yet), but if it ever does read real label colors from the API, having a real convention here means that data becomes meaningful instead of noise.
