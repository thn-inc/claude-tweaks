# 2026: verification.md's isolate-and-rerun-once rule has no procedure for a no-parse test failure

Surface: infra

## Current State

`plugin/skills/test/verification.md`'s "Flake handling (tests check only)" section makes the runner the owner of listed-flaky retries (#1925) and keeps one agent-performed isolation step for a failure in an **unlisted** file: re-run that one file (`node --test path/to/file.test.js`), isolated pass → flake, isolated fail → regression. That step presupposes a file name. `bin/lib/verify/flaky.js`'s `planRetry` returns `{ retry: false, reason: 'no-parse' }` when `extractFailingFiles` yields nothing (`sniffFamily` classified the output as `generic`, or the family's failing-file pattern did not match), and `bin/verify.js` records that decision without acting on it; the prose has no branch for it, so a `no-parse` failure is presented as a flat regression with no flake adjudication. Before #1925, the isolate-and-rerun-once rule was unconditional.

"Isolating pre-existing failures by file, not by keyword grep" (the section above the flake handling) is the other half of the same rule and likewise assumes extractable paths. `report.json`'s check entry already carries the retry decision as `retryDecision` (`{ retry: false, reason: 'no-parse' | 'unlisted: […]' | 'no-template' | 'max-retries-0' | 'unreadable-log' }`, written by `verify.js` and carried by `report.js`), so the signal the prose needs exists; nothing in the prose or the stdout summary reads it.

## Deliverables

- [ ] **Two named isolation paths.** `verification.md`'s Flake handling section states them explicitly: **named-file isolation** (today's unlisted-file rule, unchanged) and **whole-suite re-run** for a `no-parse` failure: re-run the `tests` check once through the runner (`node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --cmd tests="{command}"` with the same scope and `--no-stamp`-equivalent posture so a second pass never records a pass stamp on its own), then adjudicate: second run passes → **flake** (reported exactly as the named-file flake is, verdict unchanged); fails again → **regression**. One re-run, never more; the whole-suite cost is stated as the reason this path is the fallback, not the default.
- [ ] **The prose and the summary read the existing decision.** `verification.md` tells the agent to read `retryDecision.reason` from `report.json` (`no-parse` → whole-suite path; an `unlisted:` reason → named-file path) instead of re-deriving the extractor's outcome; `bin/verify.js`'s stdout summary for a failed `tests` check gains the clause `(retry: no-parse — whole-suite re-run applies)` so the path is visible without opening the report.
- [ ] **Pre-existing-failures section cross-reference.** "Isolating pre-existing failures by file" gains one sentence pointing at the whole-suite path for output with no extractable paths, so the two sections agree.
- [ ] **Tests.** `tests/bin-lib/verify/cli.test.js`: stdout carries the no-parse clause for a generic-family failing fixture and no clause for a passing check; the existing `retryDecision` report cases stay unchanged. A prose pin (sized like `tests/verify-scope-declaration.test.js`) asserting the two path names and the one-re-run cap in `verification.md`.

## Acceptance Criteria

1. `verification.md` names both isolation paths, the `no-parse` trigger, the single whole-suite re-run, and the flake/regression adjudication for it; the named-file paragraph is byte-identical to today apart from the new heading.
2. `verification.md` names `retryDecision.reason` as the selector between the two paths; the stdout summary shows the no-parse clause for a `no-parse` failure and nothing for a passing check.
3. A generic-family failing fixture run through `verify.js` twice, with the second run passing, is adjudicated as a flake by the documented procedure and never records a pass stamp from the re-run alone.
4. `npm test` green; existing `tests/bin-lib/verify/*` cases pass with only additive assertions.

## Technical Approach

Restore the old rule's universality without losing #1925's precision: keep named-file isolation as the cheap first path and add the whole-suite re-run only where no file can be named. Read the runner's existing `retryDecision` rather than adding new detection, so the prose and the report agree on which path is in force. Do not add a runner-owned whole-suite retry: a full-suite re-run is minutes of work the agent should choose consciously, per the section's own cost note.

### Key Files

- `plugin/skills/test/verification.md` — Flake handling: two named paths; pre-existing-failures cross-reference
- `plugin/bin/verify.js` — stdout summary clause for a `no-parse` retry decision
- `tests/bin-lib/verify/cli.test.js`, a prose-pin sibling of `tests/verify-scope-declaration.test.js` — new cases

## Gotchas

- The re-run must not write a pass stamp by itself (`stamp.js`'s dirty-tree rule and #1921's stamp semantics stay authoritative); the adjudication is the agent's, the stamp is the runner's.
- `looksPassing` and `extractFailingFiles` are separate: a `no-parse` decision can coexist with a clearly failing exit code, which is exactly the case this record covers. The retry path already strips ANSI before extracting (`verify.js`), so colour alone does not produce `no-parse`; an unknown runner format does.
- `#1837` (shaped in this sweep) adds a vitest dialect and ANSI stripping; once it lands, fewer failures are `no-parse`, but the path still exists for unknown runners.
- Keep the one-re-run cap in prose and in the pin; an unbounded re-run loop is the failure this rule exists to prevent.
