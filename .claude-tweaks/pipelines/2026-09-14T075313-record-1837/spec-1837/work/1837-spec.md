# 1837: bin/verify.js: vitest counts parse as null on colour-coded output, so the suite-count regression caveat never fires

Surface: infra

## Current State

`bin/verify.js` classifies each check's output with `sniffFamily` (`plugin/bin/lib/verify/extract.js`) and parses counts with `parseCounts(text, family)`. Two facts make vitest output unparseable today, and only one of them is the ANSI colour the report names:

1. **The counts path never strips ANSI.** `stripAnsi` exists in `extract.js` (added for #1925's `extractFailingFiles`, whose comment cites this record as the lesson) but is applied only inside `extractFailingFiles`; `sniffFamily`, `parseCounts`, `summaryLine`, and `extractFailingRegion` run on the raw text. A coloured ` FAIL ` or `Tests` line is invisible to the `^FAIL `/`^Tests:` anchors.
2. **Vitest's summary shape is not a recognized family.** `SUMMARY_MARKERS` are jest (`^Tests:.*failed`, `^PASS `/`^FAIL `) and pytest (`^=+ .*(passed|failed).*=+$`); `parseCounts`'s `summary` branch reads only `^Tests:.*$` (colon) or the pytest banner. Vitest prints `Test Files  64 passed (64)` and `Tests  727 passed (727)` — no colon, a `(total)` suffix — so even colour-free vitest output sniffs as `generic` and returns `counts: null`.

`counts: null` is then silent by design at every layer: `report.js` omits the `counts` key (pinned by "counts is omitted from the entry when null"), `verify.js` sets `testCountRegression = null` when `counts.tests` is not a number, and the stdout render prints the CAVEAT line only when a regression object exists. `test/verification.md`'s "Suite-count regression caveat (#881)" section describes the comparison without naming the unparsed case. Neither `run.js` nor `verify.js` sets `NO_COLOR`/`FORCE_COLOR` on the child.

Observed on plugin 6.114.1 (Windows host, pnpm + Vitest 2.x, colour on without a TTY): `counts: null` on both a 64-file and a 43-file suite across two runs, `testCountRegression: null`, while `tests.log` carried both vitest summary lines under escape codes.

Tests: `tests/bin-lib/verify/extract.test.js` (jest and pytest count fixtures; an ANSI case only for `extractFailingFiles`), `report.test.js`, `count-stamp.test.js`, `cli.test.js`.

## Deliverables

- [ ] **Strip ANSI once, before every parser.** In `verify.js`'s check-result composition (the block that calls `sniffFamily`/`summaryLine`/`extractFailingRegion`/`parseCounts`), pass `stripAnsi(text)` to all four; export `stripAnsi` from `extract.js` if it is not already. `extractFailingFiles` keeps its own call (idempotent). The raw log file stays raw.
- [ ] **Recognize vitest.** Add a vitest marker to `SUMMARY_MARKERS` (`^\s*Test Files\s+\d+ (?:passed|failed)` or `^\s*Tests\s+\d+ (?:passed|failed)`) and a vitest branch in `parseCounts`'s `summary` family that reads the `Tests` line: `(\d+) passed`, `(\d+) failed`, `(\d+) skipped`, and the `\((\d+)\)` total, using the same known-category guard as the jest path (an unknown `(\d+) word` phrase blocks derivation rather than guessing). `Test Files` is never used for `counts.tests`; the `Tests` line is.
- [ ] **Belt and braces on colour.** `run.js` spawns the child with `NO_COLOR=1` and `FORCE_COLOR=0` merged into `process.env` (caller values win if already set), so well-behaved runners emit plain text; stripping stays authoritative for runners that ignore both.
- [ ] **Never disable the comparison silently.** When a `tests` check ran, a count stamp is in play, and `counts` parsed `null`, the report entry gains `countsUnparsed: { family }` and the stdout render prints one line in the CAVEAT shape: `CAVEAT: tests counts unparsed (family {family}) — count-stamp comparison skipped; see {logPath}`. `report.testCountRegression` stays `null`. `test/verification.md`'s "Suite-count regression caveat" section gains one sentence naming this line.
- [ ] **Tests.** `extract.test.js`: vitest fixture (coloured and plain) sniffs `summary` and parses `{tests: 727, pass: 727, fail: 0}`; a vitest line with `| 3 failed` parses `fail: 3`; a jest fixture wrapped in ANSI still parses. `report.test.js`: `countsUnparsed` present when set, omitted otherwise. `cli.test.js`: stdout carries the new CAVEAT line for an unparseable `tests` check under `--count-stamp`, and not when counts parse. `run.test.js`: child env carries `NO_COLOR=1`/`FORCE_COLOR=0` without overriding caller-set values.

## Acceptance Criteria

1. `parseCounts(stripAnsi(VITEST_COLOURED), sniffFamily(stripAnsi(VITEST_COLOURED)))` returns `{tests: 727, pass: 727, fail: 0}` for the reported output shape; the plain-text equivalent returns the same.
2. Existing jest, pytest, and TAP count fixtures return byte-identical results; the "never a guess" null cases stay null.
3. `node bin/verify.js --count-stamp {p} --cmd tests="{vitest cmd}"` run twice records `checks.tests.counts.tests` both times and prints the drop CAVEAT when the second run's count is lower (fixture-driven in `cli.test.js`).
4. An unparseable `tests` check under a count stamp prints the `CAVEAT: tests counts unparsed` line and sets `countsUnparsed` in `report.json`; no line appears when counts parse or when no stamp is in play.
5. The child process env includes `NO_COLOR=1` and `FORCE_COLOR=0` unless the caller set either.
6. `npm test` green; every existing case in `tests/bin-lib/verify/*` passes unchanged.

## Technical Approach

Strip at the boundary, once, so no parser needs to know about colour; add the vitest shape as a third summary dialect beside jest and pytest rather than loosening the jest regex (a colon-less `Tests` line must not be confused with a TAP `# tests` block — TAP precedence in `sniffFamily` is pinned). Keep counts fail-toward-absence (#892's rule): the new caveat line makes absence visible; it never fabricates a number.

### Key Files

- `plugin/bin/lib/verify/extract.js` — vitest marker + `parseCounts` branch; export `stripAnsi`
- `plugin/bin/verify.js` — strip before the four parsers; `countsUnparsed`; render the caveat line
- `plugin/bin/lib/verify/run.js` — child env `NO_COLOR`/`FORCE_COLOR`
- `plugin/bin/lib/verify/report.js` — carry `countsUnparsed` into the entry
- `plugin/skills/test/verification.md` — one sentence under "Suite-count regression caveat (#881)"
- `tests/bin-lib/verify/extract.test.js`, `report.test.js`, `cli.test.js`, `run.test.js` — new cases

## Gotchas

- `ANSI_RE` is ESC-anchored on purpose (a literal `[1m` in test output is not a code); keep it, do not widen to bare bracket sequences.
- Vitest prints `Tests` once but `Test Files` too; only the `Tests` line feeds `counts.tests`, or a 64-file suite would be recorded as 64 tests and the drop detector would fire on the wrong axis.
- `count-stamp.js`'s regression compares `previous.tests` to `current.tests` only; the vitest branch must fill `tests` from the parenthesized total when present, else `pass + fail`, matching the jest path's convention.
- Some CI images honour `FORCE_COLOR=1` from the runner's own config over `NO_COLOR`; that is why stripping, not the env, is the fix the acceptance criteria test.

## Original request

**Summary:** `bin/verify.js` records `counts: null` for a `tests` check whose output is vitest's default colour-coded summary (`Tests  64 passed (64)` wrapped in ANSI escape sequences), which silently disables the `--count-stamp` regression comparison the runner documents.

**Kind:** Defect

**Affected component:** `bin/verify.js` (the `tests` summary parser; `_shared`/`test/verification.md`'s "Suite-count regression caveat")

**Repro steps:**
1. In a project whose test command is Vitest (^2.x) with default reporter and colour on (a normal TTY-less `pnpm test` still emits ANSI colour codes on this Windows host), run `node bin/verify.js --count-stamp <path> --cmd tests="pnpm --filter <pkg> test"` twice.
2. Read `report.json` after each run.

**Expected vs. actual:**
Expected: `checks.tests.counts.tests` holds the parsed total (64 test files / N tests here), and the second run compares it against the stamp so a drop would print the documented `CAVEAT:` line.
Actual: `checks.tests.counts` is `null` on both runs (observed twice in one session, on both a core suite of 64 files and a web suite of 43 files), `testCountRegression` is `null`, and no caveat could ever fire — while the raw `tests.log` plainly contains `Test Files  64 passed (64)` / `Tests  727 passed (727)` once ANSI sequences are stripped. The parser appears to match the summary line only when it is free of escape codes.

Suggested fix: strip `\x1b\[[0-9;]*m` before applying the summary regexes (or run the child with `NO_COLOR=1`/`FORCE_COLOR=0` in its env), and surface `counts: null` on a `tests` check as its own visible line rather than silently disabling the comparison.

**Definition:** Clear

**Plugin version:** 6.114.1
