# 2294: bin/materialize.js: --multi-record-slug nests the spec under a second spec-{slug} level inside the per-spec run dir

Surface: infra

## Current State

`bin/materialize.js`'s `--multi-record-slug` handling (confirmed still present, lines ~306-308)
writes the spec under `path.join(opts.runDir, 'spec-' + opts.multiRecordSlug, 'work')` rather
than `path.join(opts.runDir, 'work')` — an existing test
(`tests/bin-lib/issues/materialize-format.test.js:297`, "materialize CLI: --multi-record-slug
writes under spec-{slug}/work/") documents this as the CLI's own intended contract: `--run-dir`
is expected to be the **parent** directory, and `--multi-record-slug` descends into a per-spec
`spec-{slug}/` subdirectory beneath it.

The reported failure is a **contract mismatch at the call site**, not necessarily a bug in the
CLI's own tested behavior: `flow/materialize.md`'s own documented CLI signature says flatly "the
CLI writes `{--run-dir}/work/{n}-spec.md` exactly under whatever path is passed" — it does not
mention `--multi-record-slug` at all, and does not say when a caller should or shouldn't pass it
during a multi-spec run. `flow/multi-spec.md` (line 113) documents `PIPELINE_RUN_DIR` as already
resolving to the per-spec `{parent}/spec-{N}/` subdirectory for a multi-spec run. The reporter's
repro shows a call site materializing the third record of a multi-spec run with
`--run-dir {parent}/spec-C` (already per-spec) **and** `--multi-record-slug A-B-C` together —
under the CLI's own tested contract, that double-supplies the per-spec descent: once via
`--run-dir` already being `spec-C`, and again via `--multi-record-slug` appending a second
`spec-A-B-C` level beneath it, producing
`{parent}/spec-C/spec-A-B-C/work/C-spec.md` instead of the expected
`{parent}/spec-C/work/C-spec.md`.

`opts.multiRecordSlug` has no other use in `materialize.js` besides this one workDir
construction — it carries no other side effect that a fix here would need to preserve.

## Deliverables

- Locate the exact call site (in `/flow`'s or `/build`'s multi-spec materialization sequence)
  that invokes `materialize.js` with both an already-per-spec `--run-dir` and
  `--multi-record-slug` set — determine whether that call site should stop passing
  `--multi-record-slug` (since `--run-dir` has already resolved to the per-spec directory), or
  whether it should instead pass the shared **parent** directory as `--run-dir` and let
  `--multi-record-slug` do the per-spec descent, matching the CLI's own currently-tested
  contract.
- Apply whichever fix resolves the mismatch without breaking the CLI's existing tested contract
  (`materialize-format.test.js:297`) for any caller that correctly relies on the parent+slug
  shape — update that test only if the CLI's contract itself is deliberately changed, with a
  clear reason recorded for the change.
- Update `flow/materialize.md`'s documented CLI signature to state explicitly when
  `--multi-record-slug` should (and should not) be passed alongside `--run-dir`, closing the gap
  that let this mismatch ship silently in the first place.

## Acceptance Criteria

- A multi-spec `/claude-tweaks:flow "#A,#B,#C"` run in `auto` mode with a shared worktree
  materializes each spec's file at `{parent}/spec-{N}/work/{n}-spec.md` — no extra
  `spec-{slug}` nesting level — matching the reporter's own stated expectation and what `/build`'s
  "read it in place" check, the consolidated console's `spec-{N}/work/{n}-spec.md` enumeration,
  and the archive's per-spec `git mv` all already assume.
- `materialize-format.test.js`'s existing `--multi-record-slug` test either still passes
  unchanged (if the fix is call-site-only) or is deliberately updated to reflect a changed CLI
  contract (if the fix changes `materialize.js` itself) — never left silently contradicting the
  new call-site behavior.
- `flow/materialize.md` states the `--run-dir`/`--multi-record-slug` interaction explicitly, so a
  future caller cannot reproduce this same double-nesting by accident.
- `npm test` passes.

## Technical Approach

Grep every call site invoking `materialize.js` with `--multi-record-slug` (already found:
`dispatch/task-prompt.md`'s prompt template — verify whether `/flow`'s own multi-spec sequence,
not just dispatch's fan-out template, has an equivalent invocation) and, for each, determine what
value it actually passes for `--run-dir` at that point in the sequence — a per-spec
`{parent}/spec-{N}` (per `flow/multi-spec.md:113`'s own `PIPELINE_RUN_DIR` documentation) or the
shared parent. The fix is whichever of these restores a single level of per-spec nesting:
(a) stop passing `--multi-record-slug` when `--run-dir` already resolved to the per-spec
directory, or (b) pass the parent directory as `--run-dir` and let `--multi-record-slug` do the
descent, matching the CLI's own currently-tested contract. Prefer (a) unless there's a concrete
reason the call site needs the parent path for something else at that same call — changing the
call site is lower blast radius than changing the CLI's own tested contract, since the CLI's
`spec-{slug}` shape may have other current callers this record hasn't traced.

## Gotchas

- Do not fix this by simply deleting `--multi-record-slug`'s effect from `materialize.js` without
  checking `materialize-format.test.js:297` and every other call site first — that test currently
  documents the flag's nesting behavior as intentional CLI contract, not a leftover bug; changing
  it silently could break a caller this record hasn't traced.
- Windows path handling: the original report was filed on Windows 11 — verify the fix's path
  joining is platform-neutral (`path.join`, already in use, is fine; just don't introduce a
  hardcoded `/` anywhere while touching this code).

## Original request

**Summary:** With `--multi-record-slug`, `bin/materialize.js` writes the spec under `{run-dir}/spec-{N}/spec-{slug}/work/` instead of `{run-dir}/spec-{N}/work/`.

**Kind:** Defect

**Affected component:** bin/materialize.js (`--multi-record-slug`), flow/materialize.md

**Repro steps:**
1. Start a multi-spec `/claude-tweaks:flow "#A,#B,#C"` run in `auto` mode with a shared worktree (`worktree-always: true`), so the parent run dir holds `spec-A/`, `spec-B/`, `spec-C/`.
2. For the third record, materialize with `PIPELINE_RUN_DIR={parent}/spec-C` and `--multi-record-slug A-B-C`.
3. Look for `{parent}/spec-C/work/C-spec.md`.

**Expected vs. actual:**
Expected: the materialized file lands at `{PIPELINE_RUN_DIR}/work/{n}-spec.md` — the path `/build`'s "read it in place" check, the consolidated console's `spec-{N}/work/{n}-spec.md` release-claim enumeration and the archive's per-spec `git mv` all expect.
Actual: the multi-record slug is appended as a second `spec-` directory level beneath the per-spec run dir that `PIPELINE_RUN_DIR` already names: `{parent}/spec-C/spec-A-B-C/work/C-spec.md`. The file had to be moved by hand (one extra commit) before the build could adopt it.

Observed on plugin 6.114.1, Windows 11, a private project on a GHE remote.

**Definition:** Clear

**Plugin version:** 6.114.1
