# 4958: plan review: a record with no Closed rule can stop on needs-human round after round, with no limit

Surface: infra

**Related:** #4588, #4727, #4618

## Current State

`plugin/skills/build/plan-review.md`'s reviewer brief (Dispatch prompt, lines 52-56) classifies a spec gap `needs-human` whenever settling it "would alter or loosen an existing Acceptance Criterion or an observable contract, or it has two defensible readings". Its Reading the reply and Spec gap — needs-human sections then stop the build on the `plan-review-needs-human` HARD-GATE (`_shared/auto-mode-contract.md`'s HARD-GATE / BLOCKED / STOP row) for every such row, at any severity. Nothing bounds how many rounds one record can go through: each resumed build re-runs the review (`plan-review.md` line 7), the re-materialized spec carries the previous answers, and a fresh reviewer finds new gaps.

#4727 added a **Closed rule** to `plugin/skills/specify/spec-template.md` (lines 196-202). That rule turns "another unlisted state" into a plan amendment, but only for deliverables that classify inputs into named states, and only when the record body states the rule. `plan-review.md` does not mention it.

Observed in the 2026-10-31 `/claude-tweaks:dispatch` firing of 10 records (run `2026-10-31T204124-dispatch-standalone`): 10 plan-review attempts across 7 records, at 12-26 minutes each, produced no implementation. All 7 resumes stopped at plan review again. The loop ended only when the human approved writing the open answers, plus a closing decision, into the remaining records' Acceptance Criteria. That decision said plan review may stop the build only for a gap that contradicts an acceptance criterion or a recorded decision. Builds then passed plan review (starting with #4559), and all 10 records merged.

**Decision (2026-11-03, Reading A of the original Open Question, chosen by the maintainer):** once a record has had one answered needs-human round, plan review converges. Only a gap that contradicts an acceptance criterion or a recorded decision stays `needs-human`. Every other gap is settled by the controller as a plan amendment and logged for the Review Console. Accepted cost: the agent settles some gaps that have two defensible readings, and the human sees those only at the console.

## Deliverables

- **Prior-round detection.** In `plan-review.md`'s Reading the reply, before any needs-human row reaches the HARD-GATE, the controller decides whether this record is in a **converged round**. A round is converged when either:
  - the record carries a trusted `<!-- plan-review-question -->` comment (`_shared/pr-run-comments.md`'s Trusted authors), meaning a dispatched or parallel-wave round already asked and the record was re-built; or
  - this build's `work/{n}-spec.md` already carries a `Decided by the user at plan review:` clarification line, meaning a present-human round already answered in this run.

  Read the comments once per review, with `gh issue view {n} --json comments` or MCP `issue_read` `get_comments` when `gh` is absent. Treat a failed read as "not converged", so the gate fails toward today's stop and never toward silently settling. Under `work-backend: local-files` only the spec-line signal applies, since there are no comments.
- **Convergence rule.** In a converged round, a spec-gap row the reviewer or the promotion rule marked `needs-human` stays `needs-human` only when settling it would alter or loosen an existing Acceptance Criterion, or contradict a recorded decision. A recorded decision is a `Decided by the user at plan review:` line, a `**Decision**` paragraph in the spec, or the Closed rule. Every other needs-human row is **settled by plan review**:
  - The controller picks the reading closer to the spec's stated intent. When the row came from a criterion change, that is the reading that keeps the criterion as written.
  - It applies that reading through the existing intent-resolvable sequence (amend spec + plan, one commit, one `AUTO` log line, one record comment, one re-audit).
  - Each such clarification line is attributed `Settled by plan review after an answered round:` and names the reading not taken.
- **Review Console trail.** Each settled row is logged as an `AUTO` decision (`bin/log-decision.js`, `--step "Common Step 1.6 (plan review)"`). The text names the finding, the chosen reading and the rejected reading, plus `--reversibility high`, so the Wrap-Up Review Console lists it. In a standalone build with no run dir, the handoff's `### Plan review amendments (standalone build, if any)` section lists it instead.
- **Reviewer brief unchanged.** The reviewer still classifies exactly as today. Convergence is a controller-side routing rule, so the reviewer's Dispatch prompt block stays byte-identical.
- **Closed rule reconciled.** `spec-template.md`'s Closed rule section gains one sentence: the rule still matters on a record's first round, while later rounds converge under `build/plan-review.md`'s convergence rule anyway.
- **HARD-GATE row.** `_shared/auto-mode-contract.md`'s HARD-GATE / BLOCKED / STOP row names the plan-review needs-human gate. Extend that wording so it reads as limited to first-round gaps and converged-round contradictions, if the row's current text would otherwise overstate when the gate fires.
- **Tests.** Extend `tests/plan-review-hard-gate-conformance.test.js` (or a new sibling suite sized like it) to pin:
  - both prior-round signals;
  - the converged-round classification sentence;
  - the `Settled by plan review after an answered round:` attribution;
  - the fail-toward-stop rule on a failed comment read;
  - the reviewer Dispatch prompt block staying unchanged.

## Acceptance Criteria

- `plugin/skills/build/plan-review.md` defines a converged round by exactly the two signals above, and a failed or unreadable comment read counts as not converged.
- In a converged round, a needs-human spec-gap row reaches the `plan-review-needs-human` HARD-GATE only when settling it would alter or loosen an existing Acceptance Criterion, or contradict a recorded decision. Every other such row is applied through the intent-resolvable sequence, never asked.
- Each settled row produces one clarification line attributed `Settled by plan review after an answered round:` naming the reading not taken, plus one `AUTO` `decisions.md` entry naming the finding and both readings (or a handoff-section entry in a standalone build).
- On a record's first round (neither signal present), routing is unchanged: every needs-human row still reaches the HARD-GATE.
- The reviewer's Dispatch prompt fenced block in `plan-review.md` is byte-identical to `origin/main` before this change.
- `plugin/skills/specify/spec-template.md`'s Closed rule section names the convergence rule and stays consistent with it. `tests/specify-closed-rule.test.js` still passes.
- The new or extended conformance tests fail when the convergence paragraph is reverted.
- `npm test` passes.

## Release Note

Plan review no longer stops a build round after round. Once a record's plan-review question has been answered, later reviews stop only for a gap that contradicts an acceptance criterion or a recorded decision, and settle the rest themselves, listed at the Review Console.

## Technical Approach

The convergence check sits in the controller's routing (Reading the reply, then Spec gap — needs-human), not in the reviewer brief. The reviewer's classification stays the same, its output format is unchanged, and the change is one routing branch evaluated before the HARD-GATE. A settled row reuses the intent-resolvable sequence as-is: same commit, log, comment and re-audit steps. So this adds no new write path and no new staged-item kind. Put the convergence paragraph immediately before the `### Spec gap — needs-human` subsection's HARD-GATE marker, so the gate's own text can say "in a converged round, only rows that survive the convergence rule reach this gate".

- `plugin/skills/specify/spec-template.md` — one sentence reconciling the Closed rule with the convergence rule
- `plugin/skills/_shared/auto-mode-contract.md` — HARD-GATE row wording, only if it overstates when the gate fires
- `tests/plan-review-hard-gate-conformance.test.js` — pins for both signals, the converged classification, the attribution, the fail-toward-stop rule, and the unchanged reviewer prompt

## Gotchas

- `plan-review.md` is pinned by several conformance suites (`tests/build-plan-review-conformance.test.js`, `tests/plan-review-dispatch-relay-conformance.test.js`, `tests/plan-review-hard-gate-conformance.test.js`). Run all three before and after editing, and keep their anchored sentences intact.
- The dispatched-path answer is written into the record **body** (the next build materializes the body, not comments). So the `plan-review-question` comment marks that a round happened, not where the answer lives. Do not try to parse answers out of comments.
- Do not cap rounds with a counter (Reading B was rejected). A record in a converged round can still stop, but only on a genuine contradiction of a criterion or a recorded decision.
- Never edit an Acceptance Criterion's own line when settling. Settled rows append under `## Plan Review Clarifications`, the same as today's intent-resolvable rows.

## Open Question

Which convergence rule should plan review apply once a record has had one answered needs-human round?

Reading A (recommended): after one answered round, only a gap that contradicts an acceptance criterion or a recorded decision stays `needs-human`. Any other gap is settled as a plan amendment and logged for the Review Console. This is the rule that ended the loop in this firing. Its cost is that an agent settles some gaps with two defensible readings, which the human sees only at the console.

Reading B: keep today's classification and add a limit on rounds, parking the record with `needs:definition` when it is reached. Its cost is that no judgment moves to the agent, but the record still stops and the rounds up to the limit are spent.

This changes what the `plan-review-needs-human` HARD-GATE stops for, so a human should choose.
