# 4555: flow/build/review: say what to do when the run is hosted in an agent that cannot dispatch subagents

Surface: infra

## Current State

A `/claude-tweaks:flow` run resumed inside a forked agent (no `Agent`/`Task` tool, no `EnterWorktree`) completed by improvising: all five plan tasks were implemented inline by the same agent, review ran in that same agent, and the worktree was created with a raw `git worktree add` plus `cd`. Nothing in flow or build detected the host shape up front or said what to do.

What already exists (verified in the checkout):

- **Build forbids the improvisation the run fell into.** `plugin/skills/build/SKILL.md:212` (Common Step 2) and `plugin/skills/build/execution-mode-policy.md:21` (record #491) state that `subagent` and `batched` are the only licensed execution strategies, and that an in-session run that skips Task dispatch is "never licensed" because it collapses the dispatch contract's independence. `plugin/skills/flow/SKILL.md:128` pins flow to `subagent` execution. Neither file says how to *detect* a host where `subagent` cannot run, or what to do instead, so a no-dispatch host drifts into the unlicensed path silently.
- **Precedent for detect-and-stop.** `plugin/skills/tidy/console-backfill.md:16`: when running inside a Task agent with no `Agent` tool, it stops and reports that the command must run in the main session — "Never a nested or in-place substitute for the dispatch."
- **The no-`Agent` probe already has a canonical shape.** `plugin/skills/_shared/subagent-dispatch-core.md:77` ("`ToolSearch` finds none, deferred or otherwise"), reused at `plugin/skills/dispatch/task-prompt.md:53` and `plugin/skills/flow/context-handoff.md:86`.
- **Review already degrades per unit, but never says so for the whole run.** A lens whose agents are unavailable gets single-read treatment with `unconfirmed` findings, a `STAGED … single-read coverage` line, and a per-lens caveat in the Step 7 summary and PR verdict comment (`plugin/skills/review/step3-lens-dispatch.md:60`, `:98`). An unavailable tiebreak agent is judged inline with ` Mode: inline.` and a `Tiebreak caveat:` line (`plugin/skills/review/step3-tiebreak.md:119`, `plugin/skills/review/review-summary-template.md:94`). So the issue's claim that review "gets no signal" is only partly true. What is still missing: (a) one run-level statement that *every* lens and tiebreak was judged by the reviewer itself because the host has no `Agent` tool, instead of N per-lens caveats a reader has to add up; (b) any mention that the reviewer may be the same agent that wrote the code.
- **The worktree fallback is documented only for dispatch.** `plugin/skills/dispatch/sequential-execution.md:9` (#447) covers a cwd-pinned dispatching session: plain `git worktree add`, then per-command `cd {worktree} &&` anchoring. `plugin/skills/_shared/worktree-setup.md:90` keeps it separate from adopt-or-create. `plugin/skills/build/worktree-setup.md` (Common Step 1, which flow's build reaches) has no pointer to it.

## Deliverables

1. **Dispatch-capability preflight at flow and build entry.** Before `/claude-tweaks:flow` claims targets or creates a worktree, on both a fresh run and a resume, and before `/claude-tweaks:build` Common Step 2 runs the `subagent` strategy, probe for an `Agent`/`Task` tool using `_shared/subagent-dispatch-core.md:77`'s canonical probe (cite it; don't restate it). When none exists:
   - Do **not** implement the plan inline. Stop the run with a BLOCKED outcome whose message names the cause ("this host has no Agent/Task tool, so the `subagent` execution strategy cannot run") and gives the resume route as a paste-ready command for a top-level session. On a standalone `/build` whose `execution-strategy` is not locked to `subagent-only`, also name `batched` (`/claude-tweaks:build #{n} batched`) as the licensed in-session alternative, for a human to choose explicitly. Never switch to it automatically.
   - When a pipeline run directory resolves, log one `decisions.md` line per `_shared/auto-decision-log.md` (status `SKIP`, text `condition: no Agent/Task tool in this host → fallback: run stopped before build; resume from a top-level session`).
   - Under `/claude-tweaks:dispatch`'s headless call, the stop reports through dispatch's existing `build-test-blocked` channel. Do not add a new outcome word.
2. **Execution-mode policy names the no-dispatch host.** Add a short section to `plugin/skills/build/execution-mode-policy.md` stating that a host with no `Agent`/`Task` tool is exactly the case the #491 decision forbids silent inline execution for, and pointing to Deliverable 1's preflight as the enforcement point.
3. **Run-level review independence marker.** When `/claude-tweaks:review` Step 3 starts in a host with no `Agent` tool (same probe), log one run-level line and carry a single `Independence: degraded — no Agent tool in this host; every lens and tiebreak was judged by the reviewer itself` caveat into the Step 7 summary and the PR verdict comment, through the same channels the existing per-lens caveat uses. When the review runs in the same session that ran build's implementation, the caveat also says so. The existing per-lens and per-tiebreak degrade lines stay unchanged.
4. **Worktree fallback pointer for build.** In `plugin/skills/build/worktree-setup.md`, add one paragraph for a session whose cwd is harness-pinned (cannot move via `EnterWorktree`) that cites `dispatch/sequential-execution.md`'s #447 mechanism instead of restating it.
5. **Prose conformance pins.** Extend the existing suites, or add one sized like them, to pin: the preflight's stop-not-inline rule in flow and build, the run-level `Independence: degraded` caveat in review, and the build worktree pointer to #447.

## Release Note

Stop flow and build cleanly, with a resume command, when they run in a host that cannot dispatch subagents, and flag reviews whose independence was lost.

## Technical Approach

This is prose-only work in the skill files plus conformance tests. No new `bin/` CLI. Detection reuses the existing `ToolSearch`-finds-none probe, cited from `_shared/subagent-dispatch-core.md`. The stop-not-degrade choice follows the standing #491 ruling (`execution-mode-policy.md`) and the `tidy/console-backfill.md:16` precedent, not the issue's suggestion of an `AUTO` inline-degrade line (see Gotchas). Review's marker goes through the caveat channels the #3817 single-read degrade already writes to, so no new Review Console section is needed. Keep every new paragraph short and cite rather than restate (`docs/skill-authoring.md`). Add the skill-graph edge to `docs/skill-graph.md` if a new cross-skill citation creates one.

## Gotchas

- **Departure from the issue's suggested direction 1.** The issue proposes logging an `AUTO` degrade and implementing inline. That conflicts with `build/execution-mode-policy.md`'s "Never licensed" ruling (#491) and this project's `execution-strategy: subagent-only` lock, so this spec stops instead. Reopening inline execution as a licensed fallback means revisiting #491 explicitly, not doing it as a side effect of this record.
- **The issue's direction 2 offered two options; this spec picks (b), a stamp.** Option (a), a `needs-independent-review` status the caller acts on, would need new outcome handling in flow and dispatch. The stamp reuses existing caveat channels. Once Deliverable 1 lands, the same-agent-wrote-and-reviewed case mostly disappears from flow, because build stops first. The marker still matters for a standalone review in a no-`Agent` host.
- The preflight must run before flow's claim and draft-PR creation under `pr-first`. Otherwise a run that can never build leaves a claim and a draft PR behind. On resume, the claim and worktree already exist: the stop leaves them in place for the top-level resume, not torn down.
- A cwd-pinned session that *does* have an `Agent` tool (e.g. flow launched as a Task subagent) is not a no-dispatch host. Deliverable 4 covers it; Deliverable 1 must not stop it.
- ASSUMPTION — verify at build: the `ToolSearch`-finds-none probe reliably reports no `Agent` tool inside a forked agent, as it does in a cloud routine sandbox. Confirm by running the probe in a forked agent before pinning the wording.

## Original request

flow/build/review: say what to do when the run is hosted in an agent that cannot dispatch subagents

**Summary:** flow, build and review do not say what to do when the run's host agent cannot dispatch subagents. Build falls back to inline implementation without saying so, and review's independence can be lost without anyone being told.

**Kind:** Gap

**Affected component:** /claude-tweaks:flow (resume path), /claude-tweaks:build (subagent-driven tasks), /claude-tweaks:review (independent review)

**Use case:**
A `/claude-tweaks:flow` run paused at plan review on a needs-human merge-order question. It was later resumed inside a forked agent, a host with no Task/Agent dispatch and no `EnterWorktree`. The run carried on, but it had to work out the fallbacks itself:

- Build's per-task implementer and reviewer dispatches could not run, so all five tasks were implemented inline by the same agent.
- Review's code review ran inline in that same agent, so it was not independent. The controlling session had to start a second fresh agent to get a real independent review. That review found nothing new, but nothing in the run would have noticed if it had been skipped.
- Worktree entry was replaced by a raw `git worktree add` plus explicit `cd`. That fallback is documented for `/claude-tweaks:dispatch` (#447) but not for flow/build.

`/claude-tweaks:dispatch` documents the cwd-pinned-subagent case (#447). flow, build and review have no matching guidance for a host with no dispatch at all. Build has no stated "implement inline" fallback. Review gets no signal that its independence guarantee is gone, so a same-agent review can be logged as if it were the normal independent review.

Suggested direction:
1. At flow/build entry, detect a host with no dispatch (check whether the Agent/Task tool is present, the same way #447 detects a pinned cwd). Log an `AUTO` degrade line that names the inline-implementation fallback.
2. In review, when the reviewer would be the same agent that wrote the code, either (a) return a `needs-independent-review` status so the caller starts a fresh agent, or (b) stamp the review result `independence: degraded` so wrap-up and the PR checklist show it.
3. Extend the #447 worktree note in dispatch to flow/build's worktree-entry step.

Evidence (from the run's decisions log): "worktree created via raw git worktree add (pinned subagent cannot EnterWorktree)", "Tasks 1-5: implemented inline by the resumed flow (fork agent; no subagent dispatch available)", and a separate later "independent review pass" entry from a second agent.

**Definition:** Clear
