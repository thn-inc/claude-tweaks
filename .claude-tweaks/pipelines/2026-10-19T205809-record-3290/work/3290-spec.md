# 3290: Check same-run staged patches stacked, not only alone, at staging time

Origin: reflect light from #2882

Defer-reason: tangential

**Related:** #3297

## Current State

`plugin/skills/_shared/staged-patch.md` requires every staging site to validate its patch with `git apply --check` against the worktree as it stands. Its Console apply section then applies a run's patches one after another, "against the cumulative pipeline state". Nothing checks a patch against the state left by the patches staged before it in the same run.

Observed in run 2026-10-16T181217-spec-2882 (#2882 review): `staged/review-1.patch` and `staged/review-2.patch` both inserted a new test directly above the same anchor line in `tests/bin-lib/residue/probes-observed.test.js`. Each passed `--check` on its own. With review-1 applied, review-2 failed: `error: patch failed: tests/bin-lib/residue/probes-observed.test.js:214`. Only an extra stacking check, run by hand outside the contract, caught this. Without it, the console would have taken the description-only fallback for a patch that was valid when staged.

## Deliverables

- `staged-patch.md`'s staging gate also checks each new patch stacked on the run's already-staged `.patch` files, in console order: apply the earlier ones to a scratch copy (or a temporary index via `git apply --cached` against a throwaway `GIT_INDEX_FILE`), then `--check` the new one.
- When the stacked check fails but the solo check passes, the staging site re-derives the diff against the stacked state, or re-anchors the hunk, before writing the artifact. If neither works, it logs the conflict in the STAGED line.
- A test pins that two patches with the same insertion anchor are caught at staging time, not at the console.

## Acceptance Criteria

- [ ] Staging a second patch whose hunk context is invalidated by an earlier patch from the same run is reported at staging time, naming both patch paths.
- [ ] Patches that stack cleanly stage exactly as they do today, with no extra log noise.
- [ ] The Console apply section's cumulative-order wording and the staging gate describe the same order.

## Release Note

Staged code-fix proposals are now checked against each other at staging time, so a later patch no longer silently falls back to the description path at the Review Console.
