## Plan Review Clarifications

Answers to the plan-review questions, decided by the maintainer on 2026-11-02.

1. **Oversight floor on `gated`/`resolved` parents: follow the CLI, floor on `due` only.** engine-verify reads `verdict.exceeds` and skips below the floor only when `exceeds === false`, because the CLI's `null` on other states must not read as below the floor. A `gated` parent goes on to the label and brief check. A `resolved` parent, above or below the floor, is skipped as a no-op, as `verification-brief-parent-gate.md` states, with a skip detail that does not cite Step 4.0b. Today a resolved parent above the floor fails with "missing demo:pending label"; that failure goes away.
2. **AC3 uses both fixtures, and compares `closeReason`.** Keep AC3 as written, with a fixture that leaves the run record out of the parent's native sub-issue list, so the CLI's `closeReason` is `not planned`. Add a second fixture with the run record listed, the production shape, where self-inclusion makes `closeReason` `completed`. In both, the test compares the shared core's verdict, including `closeReason`, with `bin/parent-gate.js`'s: the check's row alone reads only state and floor, so it cannot show the difference.
3. **Malformed sub-issue replies stay `unknown`.** `readSubIssueFacts` throws `GhFailure` on a malformed reply (`state` not a string, `labels` not an array), so engine-verify's row stays `unknown` and never becomes `skip`, because a failed read never counts as landed. The core suite pins this for `readSubIssueFacts`, and the existing engine-verify tests stay.
4. **An invalid `risk-floor` renders `unknown`.** engine-verify no longer falls back to `high`; it matches `bin/parent-gate.js`, which exits 2 on the same file, and the test changes with it.
5. **The rule for this family:** any input the CLI refuses or cannot read renders `unknown` in engine-verify, never `skip` or a default. Apply this rule to any further case of this shape rather than stopping to ask.
6. **A pending label outranked by a verdict keeps failing.** This narrows clarification 1. A `resolved` parent skips only when it carries no pending label. A parent whose pending label a verdict outranks, such as `demo:pending` with `demo:changes-requested`, keeps today's failure ("pending label outranked by a verdict — run /demo"), above or below the floor, so a requested change stays visible at wrap-up. This is a deliberate divergence from the CLI, which calls every `resolved` parent a no-op: state it in engine-verify, and pin it with a parent fixture. Every `resolved` shape is then decided: no pending label skips, any pending label fails as today.
7. **One repository per gate evaluation.** Every read engine-verify makes for one parent (the gate's sub-issue reads, `resolveParent`'s body read, and the `labels,comments` read) targets the same `--repo`, so one verdict never mixes two repositories.
8. **Plan review (run 2026-11-03T104639): a refused or unresolvable origin renders `unknown` for every target, parent or not.** The check resolves the origin once per run, before any parent is known, so a non-parent record under `work-links: body-text` now also needs a resolvable origin that `gateOriginRepo` accepts. Settled by clarification 5: "any input the CLI refuses or cannot read renders `unknown` in engine-verify, never `skip` or a default. Apply this rule to any further case of this shape rather than stopping to ask."
