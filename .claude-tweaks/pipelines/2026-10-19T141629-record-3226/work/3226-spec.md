# 3226: Dispatch: repairable missing-config.yml classification + repair-then-continue branch in the two-call gate

Surface: infra

## Overview

The #2837 post-hoc `checkFirstCallArtifacts` check and the two-call gate it feeds currently treat a missing `config.yml` as first-failure-wins: any `missing-config` result routes straight to the two-call gate's §5 teardown, releasing the record as `pr-opened` and stranding a tested, correct PR outside pipeline review (the #3111/#3129/#3138/#3126 shape). This unit adds a `repairable` classification to the artifact check — `missing-config` plus an intact live claim and (under `pr-first`) an intact recorded/pushed PR becomes `repairable: true` — and adds a repair-then-continue branch to the two-call gate and its `sequential-execution.md` mirror: log the repair, dispatch call 2 unchanged, and let `/flow`'s own case-3 adoption rebuild `config.yml` through its sanctioned writer. Every other failure, and `missing-config` with `repairable: false`, keeps the existing §5 teardown.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Changing the #2429 status-line check or its ordering — it still runs first, and a malformed status line is still `BLOCKED` regardless of this unit's repair branch.
- Building the dispatcher-bound run / `checkDispatchConfigGate` early checkpoint — a separate sub-issue of this same decomposition (file-overlap note: that sub-issue edits `sibling-session-check.md`, this one edits `sequential-execution.md` — deliberately disjoint files).
- Changing the first call's model profile — a separate sub-issue of this same decomposition.
- Relaxing the malformed-status-line case — the design doc notes the early checkpoint and the profile change make it rarer in practice, but this unit does not loosen that check.

## Release Note

Dispatch now repairs and continues a build whose only problem is a missing run-configuration file, instead of abandoning a tested, correct pull request outside pipeline review.

## Technical Approach

The `repairable` field is additive and scoped to exactly one failure reason (`missing-config`), so no existing caller or test that checks other failure reasons is affected. The repair itself does no direct file writing — it relies on `/flow`'s own adoption case 3 (already-existing behavior, `steps-and-gates.md:72-80` and `preflight.js`'s `computeAdoption`) to rebuild `config.yml` through the sanctioned writer when call 2 runs. This unit's job is purely the classification (is a repair safe?) and the dispatch-side branch (route to repair instead of teardown).

### Data / API Surface

`checkFirstCallArtifacts`'s return shape gains one new optional field:

```
{ ok: boolean, reason?: string, repairable?: boolean, ...existingFields }
```

`repairable` is present only when `reason === 'missing-config'`; absent (not `false`) for every other `reason` value, and absent on `ok: true`.

### Key Files

- `plugin/bin/lib/policy-schema.js` (read-only) — `resolvePolicyConfig`/`resolvePolicyKeys` (the non-defaulting read, lines ~598-649 house this cluster) is the function this unit calls for `integration-model`; `resolveIntegrationModel` (same file) is the wrong function — it falls through to `detectIntegrationModel` and never fails, so it cannot produce the "policy read fails" signal AC 4 requires.

## Gotchas

- First-failure-wins is the existing, correct behavior for every failure reason other than `missing-config` — do not generalize the repair classification to other reasons; the design doc scopes it to this one case because it is the one case where the remaining evidence (claim, PR) can independently confirm the build is otherwise sound.
- A policy read failure must resolve `repairable: false`, never throw past the check or default to `true` — "never repair on missing evidence" is a stated design invariant, not an incidental default. Use `resolvePolicyConfig`/`resolvePolicyKeys`, not `resolveIntegrationModel` — the latter is documented to never fail (falls through to `detectIntegrationModel`'s own fail-open-to-`local-merge` default), so it cannot structurally produce the failure this AC requires.
- The #2429 status-line check still runs first in both `two-call-gate.md` and `sequential-execution.md` — a malformed status line is `BLOCKED` regardless of this unit's change; the repair branch is reachable only after that check and a `build-test-ok` pass on every other artifact-check dimension. This is now a tested invariant, not only a narrative one — see the Deliverables item and AC 9 above.
- `sequential-execution.md`'s stale `/claude-tweaks:flow {target} wrap-up` reference (~line 32) is a pre-existing bug this unit fixes in passing because it is in the same file section being edited for the repair branch — not a separate unrelated cleanup.
- The claim's own `runId` (not `config.yml`, which is absent on this path) is the comparison value for the "claim live and matching `runId`" check — the same claim record `checkFirstCallArtifacts` already reads for its existing claim checks on every other path.
