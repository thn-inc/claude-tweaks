# 3242: flow preflight: a dispatched first call adopts as case 3 (repair) instead of case 2 (fresh) — Step 1.5/1.8 content counts as prior-run evidence

Surface: infra

**Related:** #3212 (parent), #3225, #3226

Blocked by #3225

## Current State

`/claude-tweaks:flow` intends a dispatch-minted run directory to resolve to adoption **case 2** (fresh run, initialize in place). `plugin/skills/flow/SKILL.md:151`: "A set, existing, anchored directory that is **empty** (no `config.yml` — a run dir `/claude-tweaks:dispatch` Step 4 minted before claiming) is adopted by identity and initialized in place."

As written, that case looks unreachable for a dispatched first call:

- `computeAdoption` (`plugin/bin/lib/flow/preflight.js:125-153`) returns case 2 only when `!hasConfig && !hasOtherContent`, with `hasOtherContent = decisionsHasContent || events.jsonl non-empty || specMaterialized === true` (`:145`).
- Adoption runs in Step 3, after Step 1.8 logs `flow: created open-items ledger …` into `decisions.md` (`SKILL.md:130`). `classifyDecisions` exempts only Step 2.8 claim lines, so the ledger line alone makes `hasOtherContent` true. The materialize commit comes later, in Step 4 (`flow/materialize.md`'s "When this runs"), so it plays no part in a run that follows the documented order.
- Observed: in clean dispatched run #3064, the Step 1.8 ledger line is the first `decisions.md` entry and the materialize commit predates `config.yml`; #3066 shows the same commit-before-config order. So a fresh call 1 most likely resolves to **case 3**, the repair branch for an earlier call, where the `config.yml` write is buried in a backfill checklist (`plugin/skills/flow/steps-and-gates.md:72-80`). This is inferred from code and logs, not yet confirmed by running it.

Case 3 still writes `config.yml`, so this is not what caused #3212's skips (hand-execution was). But it routes every compliant first call through recovery prose that is easy to half-follow, and the adoption note it logs misdescribes a fresh run as a recovery. #3225 adds the `dispatched: true` marker this fix keys on. #3226 relies on case 3 for a call 2 that finds `config.yml` missing, so that path must not change.

## Deliverables

- [x] **Premise probe (first, blocking) — done 2026-10-16, observed case 3.** A scratch probe against origin/main (see this record's 2026-10-16 comment) called `computeAdoption` on a real anchored run dir: claim line only → case 2; Step 2.8 claim + Step 1.8 ledger line (the documented order at Step 3) → case 3 with backfills `[PR-early lifecycle, materialize commit]`. Premise confirmed, so the fix below proceeds. The probe fixture itself still lands as AC 2's test (red before the change, green after).

- [ ] In `computeAdoption`, ahead of the case-3 fallthrough, return case 2 when `run-state.json` has `dispatched: true`, `config.yml` is absent, and `run-state.json` records no `pr`. Key on these structural fields, not on matching the Step 1.8 log text. Don't key on the absence of a claim line: in a compliant call 1, Step 2.8 has already logged it by Step 3.

- [ ] Fail toward today's behavior: an unreadable or malformed `run-state.json` leaves classification exactly as it is now.

- [ ] Update `plugin/skills/flow/steps-and-gates.md`'s adoption-case list so case 2 names the dispatched-call-1 shape explicitly.

## Technical Approach

Add one early return in `computeAdoption` between the case-1 (`hasConfig`) check and the case-3 fallthrough. Read `run-state.json` from the run dir through the existing `deps` file reader. When it parses and carries `dispatched === true` and no `pr`, and `config.yml` is absent, return the same case-2 shape the `!hasOtherContent` branch returns today: initialize in place, no backfills. A read or parse failure falls through to today's logic untouched. Write AC 2's fixture first and confirm it fails (case 3) before changing the code.

## Gotchas

- `dispatched: true` is written by #3225; until that merges no real run carries it, so this rule is inert in production. Build only after #3225 lands.
- #3226's repair path for a call 2 depends on case 3 when `config.yml` is missing. A recorded `pr` in `run-state.json` is what separates that call 2 from a fresh call 1. Do not widen the rule past the `pr` check.
- Don't key on the Step 2.8 claim line: every compliant call 1 has logged it before Step 3 (premise probe, scenario B).
