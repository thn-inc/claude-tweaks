# 6060: Reuse a valid specify-time plan in /build and skip Spec Step 3 and plan review

Surface: infra
Risk-flags: none

## Overview

With `plan-at-specify: on`, a record reaches the build carrying a `Plan:` line that names a plan already written and reviewed at specify time. This record makes `/build`'s Spec Step 2 reuse that plan when it is still valid, skipping Spec Step 3 (writing the plan) and Common Step 1.6 (plan review), and re-plan as today when it is not.

**Complexity:** Medium
**Estimated tasks:** 4-6

## Deliverables

1. Settled at specify (agent call, fails toward re-plan): a stored plan whose Files sections name no path, and a `Plan:` line that does not parse, both fail the check; the build re-plans and logs `plan-reuse failed: files` or `plan-reuse failed: malformed Plan line`.
   A first check in Spec Step 2, run when `plan-at-specify` is `on` and the materialized spec carries a `Plan:` line: `plan-store.js check` with the build's base (the `origin/{integration-branch}` sha the worktree was branched from, resolved at Spec Step 2); then `plan-audit.js {plan} --spec {spec}` as today. The plan is valid only when `check` reports `valid: true` and `plan-audit.js` passes; a missing or unfetchable ref is `failed: ref`.
2. All valid: `plan-store.js read` the plan into `docs/superpowers/plans/{basename}` in the worktree, commit it as `Add the plan reviewed at specify ({commit})`, log `AUTO` with the plan commit, skip Spec Step 3 and Common Step 1.6 with a `SKIP` entry `plan reviewed at specify ({commit})`. Common Step 1.5 runs as today. The `ASSUMPTION — verify at build:` probes that Spec Step 3 runs against the spec's Gotchas still run, since the tree moved. A held record is not `ready`, so no build reads its plan; a `Plan:` line is reused only when the record reached `ready` through the specify planning step.
3. Any check failed, including a `plan-audit.js` failure on the stored plan: log which (`check:{failed}` or `plan-audit`), write a new plan as today. Every `Settled at planning:` and `Decided by the user at planning:` line in the spec is an input to the new plan's brief; a plan that deviates logs the deviation.
4. Materialize keeps the `Plan:` line in the materialized spec: probe whether `materialize.js` strips body lines today; when it does not, this deliverable is a regression test only.
5. Tests pinning both branches and the skip-log text.

## Acceptance Criteria

1. With `plan-at-specify: off` or no `Plan:` line, the build behaves as today with no new log lines (the existing build conformance tests are the oracle; the new pointer in `SKILL.md` changes its text only).
2. A valid stored plan is committed into the worktree and Spec Step 3 and Common Step 1.6 do not run; `decisions.md` holds the `AUTO` and `SKIP` lines.
3. A failed check logs its name and the build writes a new plan.
4. `npm test` passes.
5. A build resumed after a reuse sees the committed plan as an existing plan: the new check does not run again and Common Step 1.6 is not re-decided as skipped-by-reuse a second time.

## Release Note

With `plan-at-specify: on`, a build reuses the plan specify already wrote and reviewed, skipping its own plan step when nothing has changed.

## Plan Review Clarifications

- Decided by the user at plan review: the failure log line has one format, `plan-reuse failed: {reason}`, with `{reason}` one of `ref`, `hash`, `base`, `files`, `plan-audit`, `malformed Plan line` (or `premise`, below) — Deliverable 1's form; Deliverable 3's "`check:{failed}` or `plan-audit`" names the same reasons. Not taken: `check:{failed}` for plan-store failures beside a `plan-reuse failed:` prefix for the rest.
- Decided by the user at plan review: a reversed `ASSUMPTION — verify at build:` probe on the reuse path fails the reuse with reason `premise` and the build writes a new plan, as Spec Step 3 never leaves a plan building on a disproven claim. Not taken: keep the reused plan and only log `premise reversed: …`.
- Decided by the user at plan review: the reuse check sits in Spec Step 2 after the existing-plan search, on the two routes that proceed to Spec Step 3 (no plan, stale plan), so a resumed build finds the committed plan and never reaches it (AC5) and the resume branch is unchanged (Gotcha: "the new check sits before it and must not change it" — before Spec Step 3's plan writing, not before the resume branch). Not taken: literally first, before the plan search, with a skip once this spec's plan is committed.


## Build Alignment Notes

- Beneficial: a non-zero probe exit or off-shape probe output (an unreadable spec, an unwritable session temp) is a BLOCKED infrastructure stop with no reuse verdict logged, not a reuse failure — the spec's reasons judge the plan, and a fault judges nothing.
- Beneficial: a record whose materialize envelope reports `template.changed: true` skips reuse once the probe finds a valid `Plan:` line (SKIP `condition: template changed since filing → fallback: new plan written at Spec Step 3`), so Spec Step 3's #1840 template-delta duty still applies; the seven-reason failure list is unchanged.
- Beneficial: a `Plan:` line naming another record's ref fails as `ref`.
- Beneficial: AC5's stale-plan route is enforced by `git log --diff-filter=A --format=%s -1 -- "{plan}"` — a found plan added by an `Add the plan reviewed at specify` commit never re-enters reuse.
- Beneficial: the check's base is `git merge-base HEAD origin/{integration-branch}`, the newest integration-branch commit HEAD contains after Common Step 1's catch-up — the base the worktree effectively branched from.
