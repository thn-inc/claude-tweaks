# 4854: Gate the gh host seam's GH_HOST injection on a positive GitHub signal, not a forge denylist

Origin: /claude-tweaks:release v6.160.0 release-gate review (run 2026-11-01T182455-release-standalone)

Defer-reason: pre-existing-outside-diff

## Current State

`plugin/bin/lib/repo-resolve.js`'s `resolveGhSpec` (line 159) admits an origin host as a GitHub Enterprise host whenever `GH_ENTERPRISE_TOKEN` or `GITHUB_ENTERPRISE_TOKEN` is set, the remote is not SSH, and the host is not on `NON_GITHUB_FORGES` (line 140, ten SaaS hosts plus `*.visualstudio.com`). `ghOptions` (line ~227) then sets `GH_HOST` to that host on every wrapped `gh` call, and gh sends the enterprise token to whatever `GH_HOST` names. Any self-hosted GitLab, Gitea, Forgejo or Gerrit origin, or an attacker-chosen HTTPS origin, receives the user's work token.

The path needs no user action: the SessionStart hook (`plugin/bin/lib/hooks/session-start.js:261`) reaches `detectIntegrationModel` (`plugin/bin/lib/policy-schema.js:827`), whose `gh repo view` probe runs through `ghOptions`. Reproduced live with gh 2.102.0: origin `https://git.corp.invalid/…` plus only `GH_ENTERPRISE_TOKEN` and an empty `GH_CONFIG_DIR` — plain gh makes no request (`could not find any host configurations`), the seam's `GH_HOST=git.corp.invalid` sends `POST https://git.corp.invalid/api/graphql` with `Authorization: token …`.

The two guards are also bypassable on their own terms (line 140, folded in from the same review): the denylist is exact-match, so `gitlab.com.` (trailing dot) passes, and `isSshRemote` recognises only `ssh://` and scp-style, so `git+ssh://` and `ssh+git://` SSH-config aliases are admitted.

`tests/bin-lib/repo-resolve.test.js:173` and `:322` pin the leaking behaviour (`git.corp.example` admitted on the token alone). Found by the v6.160.0 release-gate review: lens 3b pair reproduced at high, cross-lens debate converged at high (two judges), per-candidate refutation confirmed. Shipped in v6.160.0 over the review's HARD-GATE by an explicit human Proceed.

## Deliverables

- [ ] Admit a non-github.com origin host for `GH_HOST` injection only on a positive signal: a `hosts.yml` key, a `*.ghe.com` host, or an explicit opt-in (`GH_HOST` already exported, or a policy key). Drop the enterprise-token-alone clause.

- [ ] Normalise the host before any forge comparison (trailing dot, case) and treat every ssh scheme (`git+ssh://`, `ssh+git://`) as SSH, so the remaining guards cannot be sidestepped by spelling.

- [ ] Flip `tests/bin-lib/repo-resolve.test.js:173` and `:322` to assert the token alone admits nothing, and add a case per bypass spelling.

## Acceptance Criteria

- [ ] With only `GH_ENTERPRISE_TOKEN` set and origin `https://git.corp.invalid/o/r.git`, `ghOptions` injects no `GH_HOST`.

- [ ] A `hosts.yml` GHE host and a `*.ghe.com` origin still get `GH_HOST` injected.

- [ ] `https://gitlab.com./o/r.git`, `git+ssh://alias/o/r` and `ssh+git://alias/o/r` inject no `GH_HOST`.

- [ ] `npm test` passes.

## Release Note

The plugin no longer sends a GitHub Enterprise token to a non-GitHub git host when GH_ENTERPRISE_TOKEN is set and the repository's origin is a self-hosted forge.
