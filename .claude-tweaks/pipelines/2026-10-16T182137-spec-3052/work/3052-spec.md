# 3052: Evaluate adding continuous repo security scanning to claude-tweaks

Surface: infra

## Current State

The original request says claude-tweaks "ships a /security-review and /code-health skill, run on demand". That premise is partly wrong:

- `/security-review` is a Claude Code built-in. No claude-tweaks skill has that name (`plugin/skills/` has no `security-review` directory).
- claude-tweaks' own security coverage is `/claude-tweaks:code-health`'s `focus=security-hardening` vertical (`plugin/bin/lib/code-health/candidates-security-hardening.js`, registered in `focus-generators.js`). It is judged against `plugin/skills/_shared/criteria-security-hardening.md`, alongside `criteria-security-logic.md` and `criteria-iac-security.md`. `/claude-tweaks:review` also runs a Security Hardening pass in Step 6.6 (`plugin/skills/review/focus-criterion-passes.md`).

claude-tweaks is also not on-demand only:

- `/claude-tweaks:code-health` ships a routine template (`plugin/skills/code-health/routine-template.yml`), so it can already run on a schedule through `/claude-tweaks:routine create code-health`.
- `/claude-tweaks:routine webhook-trigger <skill> --events …` (`plugin/skills/routine/webhook-trigger.md`) attaches a GitHub-event trigger (for example push) to an existing routine. That is a commit-triggered mode in all but name.
- Findings are fingerprinted and deduplicated against open issues before filing, and CI gating exists via `code-health.js status --fail-on` (`plugin/skills/code-health/ci-integration.md`).

The external prompt for this record: OpenAI's Codex Security Cloud watches a repo continuously, reviews every commit, dedupes alerts and prepares ready-to-review fixes. claude-tweaks' health skills deliberately never edit code.

## Deliverables

1. A written recommendation, posted as a comment on this record, answering whether claude-tweaks' security scanning should gain a continuous or commit-triggered mode beyond what `routine` (scheduled and webhook-triggered) plus `code-health focus=security-hardening` already provide. It should cover:
   - scope: per-commit diff versus repo-wide sweep, and which security criteria apply;
   - cost: model tokens per firing, firing frequency, and duplicate-finding noise given the existing fingerprint dedup;
   - the gap, if any, between today's composable path (a routine with a push webhook running `code-health focus=security-hardening`) and a dedicated continuous mode;
   - whether "prepares ready-to-review fixes" conflicts with the health skills' never-edits-code contract.
2. For each change the recommendation endorses, file a backlog record via `/claude-tweaks:capture` with a spec-shaped body, or state explicitly that no change is recommended.

## Acceptance Criteria

- The recommendation comment exists on this record and addresses each of the four points in Deliverable 1, citing the files above for what already exists.
- It states a clear verdict: no change, a documentation-only change (for example a recipe for the routine plus webhook composition), or a specific new capability.
- Every endorsed change has a filed backlog record linked from the comment; no endorsed change is left as prose only.

## Release Note

No user-facing change. This produces an internal recommendation on continuous security scanning.

## Technical Approach

A desk evaluation, with no code or skill edits in this record. Start from the existing composable path (`routine create code-health` plus `routine webhook-trigger code-health --events push`, run with `focus=security-hardening`) and decide whether it already meets the continuous-scanning use case. If it does, the likely outcome is a documentation recipe. If not, name the concrete gap (per-commit diff scoping, latency, cost per push) that a new mode would close.

## Gotchas

- The original request's premise that `/security-review` is a claude-tweaks skill is incorrect: it is a Claude Code built-in. The evaluation must not propose changing it.
- Auto-prepared fixes would cut against the health skills' report-only contract ("never edits code"). Any recommendation in that direction needs its own design record, not a mode flag.
- Firing on every push multiplies model cost by commit volume. Size the cost against this repo's real push cadence (`git log --since` counts), not an assumed one.
