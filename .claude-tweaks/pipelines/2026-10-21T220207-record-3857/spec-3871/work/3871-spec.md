# 3871: Windows regression: 2 test file(s) newly failing after 4b3e6fa7f

Surface: infra

## Current State

The post-merge Windows check on commit 4b3e6fa7f (merged PR #3852) reported two newly failing test files, both on the composed-bundle read-limit rail (`RAIL_BYTES` = 52500, `plugin/bin/lib/skill-audit/budgets.js`):

- `tests/bin-lib/skill-audit/context-cost.test.js` — "rail: every compose call site's max composed bytes fit one Read call" fails with `merge @ wrap-up/auto-merge-short-circuit.md:218 52503 B`.
- `tests/wrap-up-merge-mode-conformance.test.js` — "the composed merge bundle stays within the read-limit rail" fails with `wrap-up/auto-merge-short-circuit.md:218 composes 52503 B > 52500`.

Re-checked against current `main`, this is still live and is a measurement defect, not real growth. `measureComposed` in `plugin/bin/lib/skill-audit/context-cost.js` (line 153) reads each compose source with a raw `fs.readFileSync(p, 'utf8')` and counts `Buffer.byteLength(compose(...))`. On a Windows `core.autocrlf=true` checkout every source line carries a `\r`, so the count includes one extra byte per line. The same module's `measuredTextBytes` (line 56) already normalizes `\r\n` → `\n` before counting, so the two measurements disagree on Windows. Measured on macOS today: the `merge` bundle is **52129 B** LF (all three call sites: `auto-merge-short-circuit.md:218`, `merge-mode.md:25`, `review-console.md:122`). Under a CRLF-read simulation the same bundle measures **52799 B** and the conformance test fails. The rail is meant as a platform-independent content-size proxy.

**Related:** #3702, #3703, #3742, #3751, #3776, #3797, #3802, #3857, #3886, #3890, #3894

## Deliverables

1. `plugin/bin/lib/skill-audit/context-cost.js` — `measureComposed` normalizes each source's content `\r\n` → `\n` at read time (line 153), the same normalization `measuredTextBytes` applies, so composed-byte counts are EOL-independent.
2. A regression test in `tests/bin-lib/skill-audit/context-cost.test.js` that composes from CRLF-converted copies of real sources (e.g. via `crlfCheckoutRead` from `tests/helpers/read-skill.js`, or a temp-dir fixture) and asserts the composed byte count equals the LF count.

## Acceptance Criteria

1. `measureComposed` byte counts are identical for LF and CRLF copies of the same sources. The new test pins it and fails when Deliverable 1's normalization is reverted.
2. Under a CRLF-read simulation, `node --test tests/wrap-up-merge-mode-conformance.test.js tests/bin-lib/skill-audit/context-cost.test.js` passes. Before the fix the merge-bundle rail test fails with ~52799 B.
3. Both files are green on Linux/macOS without the simulation, and the reported LF bytes for the `merge` step are unchanged (52129 B at shaping time, give or take any content change on `main` since).
4. The next post-merge Windows check (`.github/workflows/windows-regression.yml`) lists neither test file.

## Release Note

Fix composed-bundle size checks over-counting on Windows checkouts, which pushed a bundle falsely past its read-limit rail.

## Technical Approach

Normalize at the one raw read in `measureComposed`, matching the module's existing `measuredTextBytes` convention, rather than in each test. Every rail consumer reads `composedBytesReport`, so one fix covers both failing tests. `plugin/bin/lib/compose-context/` (the runtime composer) is out of scope: the rail is a measurement proxy, and the runtime's own bytes are not what these tests pin.

### Key Files

- `plugin/bin/lib/skill-audit/context-cost.js` — `measureComposed` normalizes CRLF at read (line 153)
- `tests/bin-lib/skill-audit/context-cost.test.js` — CRLF-vs-LF composed-bytes regression test
- `tests/wrap-up-merge-mode-conformance.test.js` — no change; passes once the measurement is EOL-independent
- `tests/helpers/read-skill.js` — `crlfCheckoutRead` helper reused (read-only)

## Gotchas

- The bundle has only ~371 B of real headroom (52129 of 52500). The Windows failure was masking how close the merge bundle is to the rail, but that is a separate concern from this measurement fix.
- Do not raise `RAIL_BYTES` to absorb the CRLF inflation. The inflation scales with line count, so any fixed bump just moves the false failure to the next bundle that grows.
