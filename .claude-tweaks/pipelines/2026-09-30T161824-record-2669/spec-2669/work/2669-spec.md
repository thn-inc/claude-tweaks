# 2669: Flag polling-vs-realtime and duplicate-version anti-patterns

Surface: infra

## Current State
Two recurring coding-agent anti-patterns have been identified from an external source (a transcribed Instagram Reel from a developer who has shipped 15+ AI-built apps):

1. **Polling instead of realtime push** — agents building a data flow that needs live updates default to fixed-interval polling (e.g. `setInterval` fetches every few seconds) instead of a realtime push/subscription mechanism when the backend already supports one (e.g. a Supabase/Convex subscription, a websocket, SSE). This looks fine in testing but drains battery and degrades frame rate under real usage.
2. **Duplicate "v2" files instead of in-place edits** — agents avoid replacing working code in place, instead layering a `v2`/duplicate-suffixed file or function on top "just in case." This leaves dead code around, and the agent loses track of which version is actually live, leading to circular, self-breaking edits on later requests.

Anti-pattern 2 is already a standing instruction in this repo's own CLAUDE.md ("don't use feature flags or backwards-compatibility shims when you can just change the code" — see the Philosophy/Don'ts sections) — the external source is independent confirmation that the same failure mode is common enough across coding agents generally to be worth a dedicated automated review check, not just a written instruction the agent might drift from under pressure.

Neither anti-pattern currently has an automated review-lens check.

## Deliverables
1. Add a review-lens check that flags a newly introduced fixed-interval polling loop (`setInterval`/`setTimeout` recursion, or an equivalent polling construct) against a data source that already exposes or could reasonably expose a realtime push/subscription mechanism.
2. Add a review-lens check that flags a newly created file or function with a version-suffix name pattern (`v2`, `-new`, `-copy`, `_updated`, etc.) sitting alongside an unremoved original that the diff did not delete or fully migrate away from.
3. Document that these two checks formalize the existing CLAUDE.md "change code in place" instruction into an automated check, rather than relying on the instruction alone.

## Acceptance Criteria
- The polling check flags a sample diff that adds a fixed-interval polling loop against a realtime-capable backend.
- The polling check does not flag polling against a data source with no realtime alternative available (e.g. a third-party REST API with no push option).
- The duplicate-version check flags a sample diff that introduces a `v2`-suffixed (or equivalent) file/function alongside its unremoved original.
- The duplicate-version check does not flag a legitimate versioned artifact (e.g. an API route intentionally versioned as `/v2/` for external consumers) — the check targets abandoned/duplicated internal code, not a deliberate external contract.
- Documentation for the review-lens (or the relevant skill's checklist) states that these two checks formalize the existing CLAUDE.md instruction into an automated check.

## Release Note

Code review now flags new polling loops where realtime updates are available, and leftover "v2"-style duplicate copies of code.

## Technical Approach

Both checks land in `/claude-tweaks:review`'s lens definitions (`plugin/skills/review/step3-lens-dispatch.md`, "Lens definitions (3a-3f)"), as new question bullets matching those lenses' existing style. The polling check joins 3d (Performance): flag a newly introduced fixed-interval polling loop (`setInterval`/recursive `setTimeout`, or equivalent) against a source that exposes a push/subscription mechanism. The duplicate-version check joins 3a (Convention Compliance): flag a new version-suffixed file or function (`v2`, `-new`, `-copy`, `_updated`) beside an original the diff neither deleted nor migrated away from. Each bullet states its false-positive guard inline (no realtime alternative; a deliberately versioned external contract).

### Key Files

- `plugin/skills/review/step3-lens-dispatch.md` — lens 3d (Performance) gains the polling check; lens 3a (Convention Compliance) gains the duplicate-version check; each carries its false-positive guard

## Gotchas

- The duplicate-version check must not fire on legitimate, deliberately-versioned external-facing artifacts (API routes, published package majors) — only on abandoned/duplicated internal code from indecisive in-place-edit avoidance.
- The polling check must not fire when no realtime alternative exists for the given backend/data source — polling is the correct choice there, not an anti-pattern.
- `step3-lens-dispatch.md` feeds a composed dispatch-contract bundle (#2019); run `npm test` for the prose/byte pins that cover it.
