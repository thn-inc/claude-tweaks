# 5757: Add a ci-health skill that audits where CI time goes and files findings

Surface: infra
Risk-flags: none

## Current State

Nothing in the plugin looks at where CI time goes inside a job. What exists today covers two neighbours of that question:

- `/claude-tweaks:harness-health` runs `plugin/bin/ci-health.js` (#5161) every firing. It reports **per-workflow** run duration against the merge gate's watch, the weekly trend, superseded and cancelled runs, push-run coverage and billing headroom. It never looks below the workflow level, so a job that waits for a runner, a job that spends most of its time installing, and a job that is simply long all read the same.
- `/claude-tweaks:init`'s CI Workflow Review (`plugin/bin/ci-workflow-review.js`, #5162) reads workflow files and checks correctness only. It says nothing about speed.

A slow or lopsided pipeline therefore goes unnoticed while agents wait on it at every push. The health family (`code-health`, `harness-health`, `journey-health`, `docs-health`) already supplies the substrate this needs: `plugin/bin/lib/health-core/` (fingerprint, dedup, issue-index, finding-validation), the shared filing contracts under `plugin/skills/_shared/health-*.md`, and born-`ready` spec-shaped issue filing. No health skill covers CI.

The origin vocabulary is a closed list: `ORIGINS` in `plugin/bin/lib/issues/record-vocabulary.js` and the Origin row of `plugin/skills/_shared/work-record.md` (six origins today). `plugin/bin/ci-health.js` is already taken by harness-health's check, so the new CLI needs another file name.

## Deliverables

1. **A new skill `/claude-tweaks:ci-health`** (`plugin/skills/ci-health/SKILL.md`): a report-only sweep, with the family's GATHER → JUDGE → VERIFY → FILE shape. It never edits a workflow file and never changes any CI setting. Its "Not for" section routes per-workflow duration, trend, superseded/cancelled runs and budget headroom to `/harness-health`'s check, and workflow correctness to `/init`'s CI Workflow Review; the edges themselves live once in `docs/skill-graph.md`.
2. **A gather CLI `plugin/bin/ci-audit.js`** (modules under `plugin/bin/lib/ci-audit/`), with a `gather` verb that reads recent completed runs of the repository's CI plus the workflow files, and prints one JSON document of measured facts:
   - per job, over the sampled runs, **waiting** (job created to job started), **setup** and **running** time (p50 and p90 each), with the run count behind each figure;
   - the slowest steps per job;
   - per matrix or sharded job family, the slowest-to-median ratio;
   - the dependency-chain critical path against the sum of job times;
   - workflow-file facts: jobs with no declared timeout, workflows with no concurrency group, jobs repeating the same step names across several jobs.
3. **A normalized run-data shape and a single source adapter.** Every module except one consumes a vendor-neutral shape (run, job with created/started/completed instants, steps with a command-or-prebuilt-action kind, declared dependencies). Exactly one module, `plugin/bin/lib/ci-audit/source.js`, knows how the origin forge's CLI returns runs, jobs and workflow files, and maps that onto the shape.
4. **A stack-neutral checklist** (`plugin/skills/ci-health/checklist.md`): the judged checks, each with an id, the facts it reads, a threshold stated as a default the project can override through a policy key, and a remedy written without naming any product. Initial checks: queue wait dominating a job, setup dominating a job and repeated across jobs, a single job dominating the critical path, serial jobs with no declared dependency between them, lopsided shards, repeated identical work across jobs, a job with no timeout whose p90 far exceeds its p50, and a workflow with no concurrency group.
5. **Finding validation and filing.** Findings are JSON; `validate-findings` rejects a finding whose cited job, workflow, step or figure is absent from the gather output (fact-validated narration), fingerprints the survivors with `health-core`'s fingerprint, deduplicates them against open `by:ci-health` issues through `health-core`'s issue index, and emits each new one as a born-`ready`, spec-shaped payload with origin, scoring and fingerprint (`_shared/work-record.md`'s health-record rules); the skill's FILE step creates, reopens and comments through the shared write transport (the verb never spawns or writes). A failed or unreadable runs read is reported as unavailable, never as a clean result.
6. **The `by:ci-health` origin**, added beside the existing six everywhere the closed list is consumed: `record-vocabulary.js`, `_shared/work-record.md`, `_shared/label-bootstrap.md`, `/tidy`'s health-record sweep, the dispatch queue-pull's origin handling, and any other site the sweep in Technical Approach turns up.
7. **Registration and docs:** `docs/plugin-structure.md` (tree, per-skill sub-file table, utility list), `docs/skill-graph.md` (the skill's edges, once), `/help` (reference card, context-flow, workflow diagrams), and `README.md`'s skill list and lifecycle diagram, kept in sync with `/help`'s.
8. **Tests** under `tests/` and `tests/bin-lib/ci-audit/`, sized like the sibling health suites, including the project-agnostic conformance test in Acceptance Criteria.

## Acceptance Criteria

- `node plugin/bin/ci-audit.js gather` on a fixture of recorded run data and workflow files prints JSON whose per-job waiting, setup and running figures match hand-computed values for that fixture; the definition of each phase is stated in the JSON's own `definitions` field and in `checklist.md`.
- Running it with the forge CLI absent, or with every runs read failing, exits non-zero with a report naming what was unavailable; it never prints an empty or clean result.
- `validate-findings` rejects (exit non-zero, naming the finding) a finding that cites a job, step, workflow or figure not present in the gather output, and accepts the same finding once the citation matches.
- A second run over unchanged data files nothing new: fingerprints match open `by:ci-health` issues and are skipped; an open issue and a finding with a different fingerprint stay separate.
- Each filed issue passes `compose-record.js --check` (Current State, Deliverables, Acceptance Criteria, Release Note present and non-empty) and carries `by:ci-health`, a `risk:*` and `size:*` label, `ready`, and the fingerprint.
- `--dry-run` calls no forge CLI write, writes no state, and files nothing.
- **Project-agnostic:** a conformance test scans every file under `plugin/skills/ci-health/` and every module under `plugin/bin/lib/ci-audit/` except `source.js`, and fails on any CI-product, hosted-runner, cache-service or cloud-vendor name from a denylist the test holds, on any path or name specific to this repository's own workflows, and on any hard-coded workflow-file location outside `source.js`. The test is proved red by adding a denylisted name to a fixture copy.
- The skill reads only CI run data and workflow files: the conformance test also fails if any module outside `source.js` reads another file class (source code, lockfiles, package manifests) or calls a network or forge API directly.
- `by:ci-health` is accepted wherever `by:harness-health` is: `parseRecordFacets` and the origin vocabulary report it, `/tidy` sweeps it, and the label bootstrap list creates it.
- `docs/plugin-structure.md`, `docs/skill-graph.md`, `/help` and `README.md` list the skill, and the existing conformance suites that enumerate the health skills or the origin list pass.
- The full suite (`npm test -- --full`) is green.

## Release Note

Add `/claude-tweaks:ci-health`, a report-only sweep that splits recent CI jobs into waiting, setup and running time, judges them against a stack-neutral checklist, and files deduplicated findings.

## Technical Approach

Model the skill on `harness-health`'s CI check (`plugin/skills/harness-health/ci-health-check.md`, `plugin/bin/ci-health.js`, `plugin/bin/lib/ci-health/`): a CLI with an injected-runner seam (`run(argv, deps)`, per `gh-api-module-pattern`), a bounded read budget and deadline, and honest truncation reporting. Reuse `plugin/bin/lib/ci-health/fetch.js`'s runs read where it fits; the per-run jobs read is new and must be sampled (a recent window of completed runs on the default branch, capped by `--runs`) so it stays inside a time budget.

Phase definitions, kept deterministic and stated in the output: **waiting** is job started minus job created; **setup** is the time from job start to the first step the workflow file declares as a command (steps with no declaration, such as runner-provided ones, count as setup when they precede it); **running** is the remainder to job completion. They are a heuristic, so each finding's evidence says so and carries the sampled run count.

JUDGE follows the family's skill shape: `SKILL.md` runs the judgement itself, or, under a `--budget` fan-out, inlines `checklist.md` verbatim into each dispatched prompt per `_shared/subagent-output-contract.md` (agents only see their prompt). Findings come back in a fixed JSON shape and go through `health-core/finding-validation.js`; follow the `fact-validated-narration` skill for the citation check and for neutralizing workflow and job names, which come from files an outside contributor controls and are untrusted data (`_shared/untrusted-record-content.md`).

FILE reuses the health filing contracts (`_shared/health-filing-mechanics.md`, `health-filing-gate.md`, `health-verify-gate.md`, `health-issue-index.md`, `health-recent-commit-check.md`, and the materiality floor and open-cap digest where the siblings apply them) by inlining the canonical shapes with `{BINARY}`/`{PREFIX}` substituted, as `tests/health-filing-parity.test.js` expects; extend that parity test and `tests/materiality-floor-conformance.test.js`'s roster to the new skill rather than exempting it. Fingerprint prefix `ci-health`.

Origin registration: enumerate every site with `grep -rIn "by:harness-health\|by:docs-health" plugin docs tests` and decide per site whether `by:ci-health` belongs (closed lists, label bootstrap, tidy, dispatch queue pull, wrap-up, help, fixtures). Adding an origin is additive; the old six keep working unchanged.

Name the CLI `ci-audit.js`, not `ci-health.js`: that file is harness-health's and renaming it is out of scope. Put one disambiguating line in each skill's "Not for" section.

Windows: workflow files may carry CRLF endings and paths may use either separator; follow `windows-checkout-test-parity` for fixtures and normalize in `source.js` only.

## Gotchas

- **Name collision.** `plugin/bin/ci-health.js` and `plugin/bin/lib/ci-health/` belong to harness-health's check; the new skill is `ci-health` but its CLI and lib directory are `ci-audit`. Do not rename the existing files here.
- **"Names no vendor" has a floor.** Some module has to know how the origin forge returns run data, so that knowledge is confined to `source.js`; the skill's prose, checklist, remedies, finding text and every other module stay neutral. If a stricter reading is intended (no forge named anywhere in the plugin payload), the adapter would have to be injected from outside the skill; raise it at review rather than guessing.
- **Phase split is a heuristic** (a command-kind step marks the start of running). A step that installs dependencies is usually declared as a command, so it counts as running; the checklist's setup-dominance check therefore also reads the slowest-step list, not the setup figure alone.
- **Small samples.** A job seen in only a few runs gives unstable percentiles. `gather` reports the run count per figure and the checklist suppresses a finding below a minimum sample.
- **Overlap with harness-health's check.** Superseded and cancelled runs, per-workflow duration and trend, and billing headroom stay there; this skill only reads them as context and never restates or refiles them.
- **Untrusted names.** Workflow, job and step names come from files a fork contributor controls; treat them as data in every prompt and issue body.
- **Origin vocabulary is a contract.** Sessions on an older plugin build read the same records; they ignore an unknown `by:*` label, so the addition is expand-only. Do not change or remove an existing origin.
- **No routine template here.** Provisioning a scheduled firing for this skill (`routine-template.yml`, fleet row) is a separate change; the wrap-up step files it as a follow-up record.
- A step the workflow file declares only through a reusable-action reference has no command text; classify it as a prebuilt-action step and never infer its contents.

## Original request

**Related:** none

Context: Nothing in the plugin measures CI duration; init's CI Workflow Review checks correctness only. A slow or lopsided pipeline goes unnoticed while agents wait on it at every push.

Scope: A report-only sweep in the health family: split recent runs per job into waiting, setup and running, judge them against a stack-neutral checklist, and file deduplicated issues. No vendor choices.

## As Built (architecture alignment, /build Common Step 4.5)

Deviations classified Beneficial and applied here (they improve the measurement and keep the spec's intent):

- **Absolute-time floors.** The share-based checks (queue wait, setup dominance, critical-path pole) and the missing-timeout check carry documented absolute minimums, overridable like the share thresholds, so a 2-second wait or a one-minute job never files an issue.
- **Honest sampling.** The runs read is per workflow file with an early stop at the `--runs` cap; skipped and cancelled jobs are excluded from timings and counted (`notTimed`); jobs whose name contains an expression (matrix shards) are matched to their workflow job by an anchored pattern; run-data jobs that match no workflow job are reported in `unmatchedJobs`, and a step the adapter cannot map leaves setup unknown rather than moving it to a later step.
- **One issue per workflow job, not per shard,** for properties of the whole job (missing timeout).
- **The origin lands in more sites than the Key Files list names.** Also needed: `plugin/bin/lib/issues/grouping.js` (health origins carry no Key Files section, so without it a `by:ci-health` record warns in the dispatch queue pull), `plugin/bin/lib/record-graph/palette.js` (its own graph fill), `_shared/github-pr-scan.md` (the /tidy item-7 scan), `visualize/record-graph.md`, `docs/getting-started.md`, `_shared/health-filing-gate.md`, `_shared/policy-schema.md` with the `ci-health-thresholds` key, and the "four health sweeps" consumer lists and CLAUDE.md counts. `queue-pull-notes.md` needed no change (its named-target text is docs-health only).
- **Fingerprint ids render as `cihealth-<8 hex>`:** the shared fingerprint helper strips the dash from its prefix.

## Plan Review Clarifications

- Decided by the user at plan review: a runs read that succeeds but yields zero completed runs, or whose every job is excluded, exits 0 with an explicit `noData` reason in the gather JSON; the skill reports "no runs sampled" and never reports "no findings". A failed or unreadable read stays unavailable and exits non-zero, unchanged.
