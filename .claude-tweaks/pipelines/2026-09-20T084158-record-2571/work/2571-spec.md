# 2571: check-pr-bookkeeping.js's Step 0 gate is a silent no-op for multi-spec /flow runs

Origin: Review finding on #2472

Defer-reason: genuinely-larger

## Current State

#2472 added a phase-boundary PR-bookkeeping precondition check (`plugin/bin/check-pr-bookkeeping.js` + `plugin/bin/lib/pr-bookkeeping/precondition.js`), wired into `/claude-tweaks:test`'s Step 0 with `$PIPELINE_RUN_DIR`. `checkPrBookkeepingPrecondition` calls the pre-existing `hasMaterializeCommit(worktreeRoot, runDir)` (in `plugin/bin/lib/hooks/pre-tool-use.js`) to detect whether this run's materialize commit has landed. That function derives its git pathspec from `path.basename(runDir)`, on the documented assumption that `runDir` is the *parent* run directory (so the pathspec's trailing `spec-*/work/*` wildcard reaches any nested per-record subdirectory).

In a multi-spec `/flow` run — the pattern `/claude-tweaks:dispatch` uses for every bundled file-overlap group — `flow/multi-spec.md`'s own env-var table documents that each per-spec skill invocation (including `/test`) receives `$PIPELINE_RUN_DIR` = `{parent}/spec-{N}/`, NOT the parent directory. `path.basename()` of that value is `spec-{N}`, not the parent run's id, so `hasMaterializeCommit`'s pathspec never matches the real committed path `{parent-run-id}/spec-{N}/work/{N}-spec.md`.

Confirmed empirically (not just read): a reproduction script (git init + linked worktree + a real materialize commit at the multi-spec path shape) shows `hasMaterializeCommit(worktreeRoot, parentRunDir)` returns `true`, but `hasMaterializeCommit(worktreeRoot, path.join(parentRunDir, 'spec-42'))` returns `false` for the identical commit. `checkPrBookkeepingPrecondition` therefore always resolves `{ok: true, reason: 'not-materialized-yet'}` for a multi-spec per-spec `/test` invocation — the check never reaches its worktree-stamp or PR-stamp logic at all.

This is fail-open (no false HARD-GATE denials, no regression), but it means the new gate provides zero coverage for the exact defense-in-depth scenario #2472 exists to catch, in exactly the run shape `/claude-tweaks:dispatch` uses for bundled groups — undermining the spec's own architecture-alignment claim that placing the check at `/test`'s entry gives "a second, independent layer of defense-in-depth."

## Deliverables

- Determine whether `plugin/bin/lib/hooks/pre-tool-use.js`'s pre-existing `checkBookkeepingStampsGate` (the PreToolUse hook, the *first* defense-in-depth layer) shares this exact blind spot for multi-spec runs — if so, multi-spec runs currently have NO effective defense against the #2472 failure mode from either layer, which raises the stakes on the fix.
- Also determine where `run-state.json` (the `worktree`/`pr` fields `checkPrBookkeepingPrecondition` reads) actually lives for a multi-spec run — shared at the parent, or duplicated per-spec — since `readRunState(runDir)` in `precondition.js` reads from the per-spec `$PIPELINE_RUN_DIR` too, and may have the same "wrong directory" problem independent of `hasMaterializeCommit`.
- Fix `check-pr-bookkeeping.js`'s call site (and/or `hasMaterializeCommit`'s contract) so the check resolves the correct top-level run directory when invoked with a multi-spec per-spec `$PIPELINE_RUN_DIR` — without breaking `hasMaterializeCommit`'s other live caller (`checkBookkeepingStampsGate`) or its single-record contract.
- Add a regression test exercising the multi-spec directory shape end-to-end through `checkPrBookkeepingPrecondition`/`check-pr-bookkeeping.js`'s CLI, mirroring the existing single-record fixtures in `tests/bin-lib/pr-bookkeeping/`.

## Acceptance Criteria

A multi-spec `/claude-tweaks:flow #A,#B` run whose build phase never invokes `pr-early-run-lifecycle.md` (or invokes it and it fails silently) for one of its specs is caught by `/test`'s Step 0 gate before that spec reaches review/wrap-up — verified by a test that reproduces the real multi-spec directory shape (`{parent}/spec-{N}/`), not just the single-record shape.
