# 5226: Driver merge step: mark ready, read the checks, merge and post-merge in code

Surface: backend

**Related:** #5211, #5179

## Overview

This unit gives the pipeline driver its step 10, the merge. After `run.js`'s CI wait ends green, `plugin/bin/lib/driver/merge.js` takes a record whose live labels carry `auto:merge` from a draft PR to a merged one: it marks the PR ready, reads the checks, merges, and runs the post-merge steps, all as program code. It ports the deterministic parts of `plugin/skills/_shared/pr-first-merge.md` (Steps 2 to 3) and `plugin/skills/_shared/pr-first-merge-post-merge.md`; no model holds merge rights and `merge.js` makes no model call. Design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, section "Phase 2 — Merge".

The two judgments that precede an express merge, the merge-check content judgment and acceptance labeling (obligations of `plugin/skills/_shared/express-lane.md` step 9), are not made here. They arrive through an injected supplier that the next unit provides. With no supplier configured the driver never merges and every run ends `pending-review` exactly as in Phase 1, so this unit by itself changes no production behavior.

Outcomes are the Outcome vocabulary of `pr-first-merge.md`: `merged`, `armed`, `pending-review`.

**Complexity:** High
**Estimated tasks:** 8

## Built alongside #5222 and #5229

#5218 builds the run loop as a step table: `steps.js` exports `STEPS`, an ordered array of `{ name, run }`, and `run.js` walks it (#5218, criterion 13). This unit adds the merge as one `STEPS` entry after the CI wait. The entry calls `merge(ctx, deps)` only when the CI wait ended `green` and otherwise returns the context unchanged, so a non-green state keeps Phase 1's outcome (criterion 15 holds as written: the string `gh pr merge` appears only in `merge.js`). `run.js` changes only if the stop handling needs a case it does not have. That keeps this unit from colliding with #5222 (a review step after `check`) and #5229 (a budget loop around the per-record path), which are built at the same time. Step and outcome constants added to `events.js` are appended, never reordered.

## Acceptance Criteria

1. With no supplier on `deps` (the production state after this unit), `merge` makes no call at all (no `gh` call of any kind, no CLI call, no read) and returns `pending-review` with reason `no-supplier`; the run's recorded calls are exactly Phase 1's. With a supplier present, the record's live labels are re-read at that moment (`gh issue view {n} --json labels`): a label set without `auto:merge` (including an empty set, and a record that carries only `auto:merge-pending`) returns `not-authorized`; a failed or unparseable read returns `labels-unreadable`. In all three the PR stays in draft and the fake runner records no `gh pr ready` and no `gh pr merge`. The labels are read again immediately before every `gh pr merge` call, on every entry of the gate: a set without `auto:merge` returns `not-authorized`, and a failed read returns `labels-unreadable`, with no merge call, so an `auto:merge` removed during the supplier call or the bounded watch is honored (a test removes the label between the two reads).
2. Each of these returns `pending-review` with its reason, makes no ready call and no merge call, and leaves the PR in draft: `ctx.summaryLogged` anything but the boolean `true` (`summary-entry-missing`); `integration-model` not resolving `pr-first` for the run, or `run-state.json` carrying no `pr` (`not-pr-first`); `gh` absent (`gh-absent`); the supplier throwing, rejecting or returning something that is not an object with a `mergeCheck.verdict` string and an `acceptance.completed` boolean (`supplier-failed`); a verdict other than the exact string `auto-merge` (`verdict-not-confirmed`); `acceptance.completed` anything but `true` (`acceptance-not-completed`). One table-driven test, one row per reason, which also asserts each reason's residue from the recorded calls, per the residue table in Data / API Surface (PR draft or ready, labels written, comments written).
3. `merge` does not trust the supplier's word that a verdict was confirmed: immediately before the closing-link check it reads the run's `decisions.md` through `confirmFromFile` for the record, and a supplier returning `auto-merge` while that file holds no confirmed `auto-merge` line for the record, an unreadable file, or a later `needs-human` line, returns `verdict-not-confirmed` with no ready and no merge call. The fixture lines are built with `merge-verdict.js`'s own `verdictMarker`.
4. On the happy path, over a fake runner, the calls happen in this order, and the test asserts the whole recorded sequence: the supplier call; `confirmFromFile`; `closing-links.js --mode pre-merge`; `compose-subject.js` with `--tag auto-merge`; the `isDraft` read and `gh pr ready`; the state read, the head-runs read and `ready-run.js`; the second label read; `gh pr merge --squash` with `-t` the composed title, `--body-file` the composed body and `--match-head-commit` the sha `ctx.head` carries; the merged-state read; `post-merge-run.js --run`; then the final event carrying outcome `merged`. When the PR is already ready, the `gh pr ready` call is skipped and the skip is logged. A failed `isDraft` read or a failed `gh pr ready` returns `ready-failed` and no merge call.
5. A red check, a draft-skip workflow with no ready trigger, or checks still pending at the bound never lead to a merge call. Red and `draft-skip-without-ready-trigger:{files}` and `checks-pending-timeout` take the Red path: `bot:parked` added to the record (bootstrapped first per `_shared/label-bootstrap.md`, re-read afterwards, retried once), one comment on the record naming the reason built from a fixed template, the PR left ready; when the label is still missing after the retry the PR is re-drafted with `gh pr ready --undo`, the only re-draft this module makes, and the event says so. An unreadable state, head-runs, ready-run or rollup read returns `state-read-failed` or `checks-read-failed` and parks nothing. A PR whose state is not `OPEN` returns `pr-not-open`, and is neither merged nor parked. One test row per state; the outcome is `pending-review` in all of them.
6. A PR that conflicts (`mergeStateStatus: DIRTY` or `mergeable: CONFLICTING` on any read, or a `gh pr merge` failure carrying a conflict signature) returns `conflict`: one comment on the PR from a fixed template, the PR left ready, no further call. A test asserts that `merge.js`, with comments stripped by the repo's comment stripper, names no `rebase`, passes no `merge` and no `push` as a git subcommand argument, and contains none of `--force`, `--force-with-lease`; a real-git test asserts the branch tip and the integration branch tip are unchanged after a conflict run.
7. A `compose-subject.js` exit 1 (a missing `type:*` label or Release Note, a policy misconfiguration) returns `compose-refused` with the stderr line, reduced as the settle unit's comment hygiene reduces a detail, in the event `detail`. The composer runs before the ready call, so a refusal leaves the PR in draft; a test asserts no `gh pr ready` is recorded.
8. The merge-verification lever is read from the run's own config overlay (`resolve-policy.js --run {run-dir} --values merge-verification`) and is never `off`: the value `off`, an empty value, an unparseable output and a resolver error are all run as `wait`, and the test asserts no merge call is made without the state reads first. Under `merge-when-green` a green read merges via Step 3's `--auto --squash` call, a pending read with `mergeStateStatus: BLOCKED` arms and returns `armed` (nothing torn down, no post-merge call), and a pending read with any other merge state runs the `wait` row. Under `wait` the state is re-read and the head compared before the immediate `--squash` merge.
9. The head guard: the first gate read's `headRefOid` must equal `ctx.head` (the sha `check` verified), else `moving-target` and no merge call. When `headRefOid` then differs between the first read and the re-read, or the state is no longer `OPEN`, the gate re-enters once from the top (the re-entry again requires `headRefOid` to equal `ctx.head`); a second change returns `moving-target`. The `--match-head-commit` value is always `ctx.head`, so the merge call never goes out against any other head. A test covers each: a first read that differs from `ctx.head`, a change between reads, and two changes.
10. The bounded watch is 15 minutes with a 30-second poll as named constants, over an injected clock and sleep, and each poll re-reads the merge state in addition to the checks: a PR that turns conflicting mid-watch returns `conflict` at that poll, not `checks-pending-timeout`. A red result at any poll takes the Red path at once. Time spent in the watch counts as CI wait in the final event's totals.
11. Step 3's failure signatures are table-driven over fixture stderr: the three literal "auto-merge not allowed" wordings and the `enablePullRequestAutoMerge` mutation name, with no conflict or permission-denied wording, degrade to the `wait` row, never to an immediate merge without a state read; a checks-pending or checks-failing wording, a permission-denied wording (`403`, `not accessible`, `must have write access`) and any unrecognized failure each return `merge-refused` with the signature class (`checks`, `permission`, `unrecognized`) named in the event detail and nothing parked; a conflict wording returns `conflict`. Success is confirmed with `gh pr view --json state,mergedAt,autoMergeRequest,statusCheckRollup`: `state: MERGED` is outcome `merged`, `state: OPEN` with `autoMergeRequest` is `armed`, and anything else is `pending-review` with `merge-refused`. A failed confirmation read is retried once; if it still fails the outcome is `pending-review` with `state-read-failed` and the detail says the merge call exited 0 and the state is unconfirmed (no post-merge call is made, and the reconciler's merged-evidence checks complete a merge that did land). A `gh pr merge` exit code of 0 alone is never reported as `merged`. `compose-subject.js` exit 2 returns `gh-absent`.
12. On `merged`, the post-merge sequence runs in this order: `post-merge-run.js --run {run-dir}`; the release-status read (`git describe --tags --contains --first-parent --match 'v*'` after a fetch of the integration branch) and its `release-status` run comment; `hooks.js reconcile --checks mirror,release,archive` with a timeout of at least 150 seconds; removal of the record's worktree and local branch; then the remote branch deletion `gh api -X DELETE repos/{owner}/{repo}/git/refs/heads/{branch}`. A failure of any of these never changes the outcome from `merged`: it is a `fail` event and the final event lists it. The deletion never targets the integration branch (a test with `branch` equal to the integration branch asserts no DELETE call) and treats "reference does not exist" as success. After the reconcile call the driver checks whether the original run directory still exists; when it is gone and `{runRoot}/.claude-tweaks/pipelines/archive/{run-id}/` exists, the remaining log writes and the final event go to that path, and `merge` returns it as `runDir`. When neither exists the final event goes to stdout only and says so; a reconcile call that failed or timed out leaves the original path in use.
13. `express-lane.js verify --run {run-dir} --issue {n}` exits 0 for a fixture run driven to `merged`, and for one driven to `armed` and to `pending-review` after a red check, built the way Phase 1's run leaves the run directory (the claim log, a `check` proceed line, the recorded PR).
14. `merge.js`, with comments stripped by the repo's comment stripper, contains no `require` of the driver's worker, roles or judgments modules, no `launchWorker`, and no spawn of `claude`. The supplier is reached only as `deps.judgments`.
15. Phase 1's run suite (`tests/bin-lib/driver/run.test.js`) passes unchanged apart from the constants update of the deliverables: with no supplier configured, none of its fake-runner tests records a `gh pr merge` or a `gh pr ready` call, and `steps.js` still names neither.

## Release Note

Added a merge step to the pipeline driver: once the judgment step that feeds it is wired in, a run on a record carrying `auto:merge` marks its pull request ready, waits for the checks and merges it.

## Technical Approach

- **Where it runs.** `run.js` calls `merge` once, after its own CI wait ends `green` on the draft PR. A non-green draft state keeps Phase 1's `pending-review`, so the checks the merge reads after mark-ready are the post-ready ones: a workflow that skips drafts only runs once the PR is ready, which is what `ready-run.js` waits for.
- **Entry, in this order.** (1) `deps.judgments` is present, else `no-supplier` with no other call made. (2) `gh` is available (the runner seam reports it before any call), else `gh-absent`; this check comes before the label read so a run with `gh` absent reports `gh-absent`, not `labels-unreadable`. (3) The live label re-read. (4) `ctx.summaryLogged === true`. (5) `integration-model` resolves `pr-first` and the run records a PR (`not-pr-first`). (6) One supplier call, then the verdict and acceptance checks of acceptance criteria 2 and 3. The labels are read once more immediately before the `gh pr merge` call, on every entry of the gate (acceptance criterion 1), because the supplier call and the bounded watch can take minutes. Every failure is `pending-review` and writes no label and no comment; the event names the reason.
- **Closing-link check.** `closing-links.js --run {run-dir} --mode pre-merge`, its result handled as `_shared/pr-checklist-refresh.md`'s "Then check the forge's closing links" says: the action's `keepOpen` feeds the composer; exits 3 to 5 and `gh-absent` warn and proceed, because Step 4.0 of the post-merge file is the backstop; `still-linked` is left for that step.
- **Subject.** `compose-subject.js {n} --tag auto-merge [--keep-open {keepOpen}] --pr {pr} --out-dir {dir}`; the driver reads `title.txt` and `body.md` from that directory and passes the title as an argument, not through a shell, so the composer's single-quoted stdout line is not used. It runs once before the ready call, so a refusal leaves the PR in draft, and again whenever the gate re-enters.
- **Mark ready** (`pr-first-merge.md` Step 2). `gh pr view {pr} --json isDraft`; `true` runs `gh pr ready`, `false` skips it; each logs its AUTO line with `log-decision.js`. The title and checklist refresh of that step does not apply (the express body has no phase checklist).
- **The gate** (Step 2.5). Three reads, then the classification in `classify.js`'s order: `gh pr view {pr} --json state,mergeStateStatus,mergeable,headRefOid,statusCheckRollup`; `gh run list --commit {headRefOid} --limit 100 --json name,workflowName,status,conclusion,url`; `ready-run.js --pr {pr} --sha {headRefOid}`. The driver uses `ready-run.js`'s own state for the ready-run rule, not `pr-checks.js`'s word for it (see Gotchas). The value table is Step 2.5's, restricted to the two values the lane can hold (`merge-when-green`, `wait`); the `off` columns are not ported.
- **Red path.** Never merge. `bot:parked` on the record, one comment `Parked by merge-verification ({value}): {reason} on PR #{n}. Resume once green.` built from a fixed template, the check names reduced by the settle unit's comment hygiene (check names come from workflow YAML, which a fork PR controls), the label re-read, a `decisions.md` AUTO line. The PR stays ready.
- **Step 3.** `compose-subject` output, then `gh pr merge {pr} --repo {owner}/{repo} --auto --squash -t {title} --body-file {body} --match-head-commit {head}` under `merge-when-green`, and the same without `--auto` under `wait` and in the degrade-to-wait case. The failure signatures are the literals `pr-first-merge.md` Step 3 lists. `--match-head-commit` carries the sha `check` verified, so a merge is accepted only against the head the driver's own checks covered.
- **Post-merge** (`pr-first-merge-post-merge.md` Steps 4 and 5). `post-merge-run.js` covers Steps 4.0 and 4.0b (its `verdict` and `failedSteps` go in the final event); Step 4.1's release status; Step 4.2's reconcile; teardown of the worktree and local branch with `git worktree remove` and `git branch -D` against the main checkout with an explicit `-C`, never the driver's cwd; then Step 5's remote deletion. A worktree that is already gone is not a failure; a worktree that refuses removal stays and is named.
- **Injected seams.** Every external call goes through `deps` (runner, `now`, `sleep`, `platform`, file seams) per `.claude/skills/gh-api-module-pattern`, so the bounded watch and the head-moved re-entry are tested with a fake clock.

### Data / API Surface

- `merge(ctx, deps)` returns `Promise<{ outcome: 'merged' | 'armed' | 'pending-review', reason: string | null, detail: string | null, mergeCommit: string | null, runDir: string, ciWaitMs: number, postMerge: { verdict: string | null, failedSteps: string[], failures: string[] } | null }>`. `runDir` is the run directory the final event must be written to (the archive path after a reconcile that archived it); `ciWaitMs` is the time spent in the bounded watch, which `run.js` adds to its CI-wait total; `postMerge` carries `post-merge-run.js`'s `verdict` and `failedSteps` plus the names of any other post-merge step that failed, and is `null` unless the outcome is `merged`.
- `ctx`: `{ record, pr, repo, branch, base, head, runDir, runRoot, mainCheckout, worktree, summaryLogged }`. `repo` is `owner/name`; `head` is the sha `express-lane.js check` verified; `base` the integration ref; `runRoot` and `mainCheckout` are the main checkout's path (the anchor for teardown and for the archive path); `summaryLogged` is set by `run.js` from its own step-8 result.
- `deps` besides `judgments`: the runner, the event writer (the one `events.js` provides, so `merge` emits its own step and `fail` events), the `log-decision.js` writer, `now`, `sleep`, `platform` and the file seams.

## Gotchas

- Mark-ready is the step that is costly to take back (`gh pr ready --undo` exists, but CI has started and the PR is visible to reviewers), so every refusal that can be decided without it is decided before it: the entry conditions, the closing-link check and the subject composition all run first. The prose order composes the subject after the gate; this unit composes earlier on purpose and again before the merge call, because the composed title depends only on the record and the PR's files.
- The gate never merges on a state it could not read. `state-read-failed` and `checks-read-failed` are `pending-review` and park nothing, as in the prose; a read failure is not "no CI".
- A repo with no PR CI parks every express merge: its empty rollup reads pending, never green, under both lane values (`_shared/express-lane.md` step 9).
- `--match-head-commit` is the only head guard on the merge call itself; the re-read and head comparison cover the window before it. Never pass `--admin` and never `--delete-branch`: the remote deletion is the post-merge file's Step 5 and runs after the worktree is gone.
- Never rewrite the integration branch, on any outcome (`pr-first-merge.md`, "Never rewrite the integration branch"). A malformed merge message is left as landed and named in the event.
