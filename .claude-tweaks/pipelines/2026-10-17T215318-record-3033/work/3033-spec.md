# 3033: wrap-up: no convention for a branch that mixes /flow orchestration with direct subagent-driven-development execution

Surface: backend

**Related:** #3035

## Current State

The reported incident: one branch ran `/claude-tweaks:flow` on spec A and spec B. A was built in the pipeline. B was built by running `superpowers:subagent-driven-development` directly against a plan file. The flow run was "deliberately deferring its consolidated multi-spec wrap-up until both specs finished". When B finished, the user said "merge it", and the assistant "force-closed the flow run with `hooks.js close-run` before the consolidated curation ever ran". A standalone `/claude-tweaks:wrap-up` then had no single record to anchor to and "fell back to inferring context from the conversation".

Verified on `origin/main`:
- `plugin/skills/wrap-up/SKILL.md:49-53` accepts one `#N`, or else treats the input as conversation context. `:65-74`: with no argument, it detects from commits and branch, then the conversation, then a materialized header. There is no multi-record or mixed-execution case.
- `wrap-up/SKILL.md:123` and `:171`: under `MULTISPEC_CURATION_DEFER=1`, the per-spec Reflect and engine passes are skipped entirely. `:239`: under `MULTISPEC_REVIEW_DEFER=1`, the per-spec console is skipped. The only thing that performs that deferred work is the parent run's consolidated pass (`plugin/skills/flow/multispec-review-console.md:15-19`, step 0 → `multispec-batch-curation.md`). That pass fires "after every spec's pipeline reaches `/wrap-up`'s Phase 4 … (or stops at a HARD-GATE failure)".
- `plugin/bin/hooks.js:930-985` (`close-run`) flips the run to terminal. Its only advisory is `close-without-wrapup` (`:959-964`, from `lib/hooks/close-run-state.js:127`), which checks whether any wrap-up event was recorded. It does not check whether a deferred consolidated pass ran.
- `plugin/skills/flow/steps-and-gates.md:31-34`: a single step argument resumes from that step onward and reads prior context from files. `:22`: the only step that re-enters a multi-spec parent run is `review-console`, and only after a Halt.
- Nothing in `flow/multi-spec.md`, `wrap-up/SKILL.md` or `docs/skill-graph.md` (the wrap-up ↔ flow row at `:616`) addresses a spec that leaves the pipeline mid-run.

## Deliverables

1. Decision (approved in brainstorming 2026-10-15, revised 2026-10-16): document a convention that uses existing mechanics only. The first-approved premise did not hold: a fresh `/claude-tweaks:flow #B test` starts its own single-spec run and never rejoins the parent multi-spec run. The convention is therefore:
   - B's own tail run (`test` onward) comes first, with its merge decision left open.
   - B is marked `not-run` in the parent manifest via `hooks.js spec-status`.
   - The parent's consolidated pass is the single merge.
   - `close-run` comes last.

   The convention also carries the warning that closing the parent first forfeits the deferred consolidated wrap-up, which is what lost it in the incident. Rejected: declaring mixed execution unsupported, because it strands real mixed runs. Rejected: a `#A,#B` wrap-up mode, a second consolidation path beside `/flow`'s multi-spec console. **Blocked by #3035:** `hooks.js spec-status` refuses today because no CLI creates `manifest.yml`, so step (c) below can't run until #3035 ships.
2. Add a `## Mixed execution (a spec built outside /flow)` section to `plugin/skills/flow/multi-spec.md`. This is the canonical home. It must state:
   - (a) A spec implemented outside the pipeline rejoins at `test` via `/claude-tweaks:flow #B test`. Cite the resume grammar from `steps-and-gates.md`'s Step Arguments rather than restating it.
   - (b) That invocation is its own single-spec run with its own wrap-up and Review Console. It does not feed the parent run's consolidated console.
   - (c) The parent run's spec B is recorded `not-run` through `hooks.js spec-status` (the manifest's only writer), so the consolidated console's Not run / Failed footer names it.
   - (d) The warning: the parent run's deferred consolidated pass must run before `close-run` on the parent. Closing first forfeits Reflect, the curation engine and the console for every spec that ran under `MULTISPEC_CURATION_DEFER=1`, because their per-spec passes were skipped (cite `wrap-up/SKILL.md`'s defer branches) and nothing else performs them.
   - (e) The order:
     1. B's tail run, with its merge decision left open.
     2. The parent's consolidated pass, whose terminal decision is the run's single merge. This is `multispec-review-console.md`'s "Approve all + merge"; "Approve all, leave PR open" defers the merge to a human.
     3. `close-run` last.
3. Add a one-sentence pointer to the new section in `wrap-up/SKILL.md`'s "If no arguments, detect from context" block. It covers the case where two records share one branch, or one record's run is already closed. Do not restate the convention there.
4. Update the wrap-up ↔ flow row in `docs/skill-graph.md` (`:616`) to name the mixed-execution convention as part of that existing edge.
5. Add a conformance test pinning the new prose.

## Gotchas

- `/claude-tweaks:flow #B test` started fresh is a separate single-spec run. Under `pr-first` its wrap-up reaches a merge decision for the shared branch/PR, so the section must tell the reader to leave that one open. The parent console's Shared teardown removes the shared worktree (`multispec-review-console.md:182`), which is why B's tail goes first. Trace both against `steps-and-gates.md`'s adoption cases and `_shared/pr-first-merge.md` before writing.
- The consolidated batch pass scopes its diff from the merge-base with the integration branch (`multispec-batch-curation.md:24`), so B's commits on the shared branch fall inside it. B's own wrap-up then routes overlapping learnings. Name this duplication in the section rather than leaving it implicit.
- Do not describe `close-run`'s `close-without-wrapup` advisory as a guard here. It checks for any wrap-up event and is not specific to the deferred consolidated pass.
- `wrap-up/SKILL.md` is about 36 KB. Keep the pointer to one sentence and measure `wc -c` plus the composed bytes before adding it.

## Original request

wrap-up: no convention for a branch that mixes /flow orchestration with direct subagent-driven-development execution

**Summary:** When one branch builds part of a multi-spec batch through `/claude-tweaks:flow` and another part through `superpowers:subagent-driven-development` run directly, wrap-up's record-identity detection and the multi-spec consolidated wrap-up have no defined way to compose the two.

**Kind:** Gap

**Affected component:** /claude-tweaks:wrap-up (record-identity detection) and /claude-tweaks:flow multi-spec consolidated wrap-up ([MULTISPEC_CURATION_DEFER]/[MULTISPEC_REVIEW_DEFER])

**Use case:**
In a private project, a single feature branch (one PR) ran `/claude-tweaks:flow` on two specs, spec A and spec B. Spec A was built inside the flow pipeline, but spec B was implemented by running `superpowers:subagent-driven-development` directly against a plan file, outside the pipeline. The flow run was deliberately deferring its consolidated multi-spec wrap-up until both specs finished. When spec B's direct execution finished, the user said "merge it", and the assistant force-closed the flow run with `hooks.js close-run` before the consolidated curation ever ran. `/claude-tweaks:wrap-up` was then invoked standalone with no single record identity to anchor to (two records, one PR, one record's run already closed), so it fell back to inferring context from the conversation.

Nothing in the plugin says which of these is the intended behaviour:
(a) every spec in a combined /flow run must stay inside /flow — dropping to direct SDD mid-run is unsupported;
(b) /flow accepts a spec whose implementation happened via direct SDD and folds it into the same consolidated wrap-up;
(c) mixed execution is normal, and wrap-up's record-identity detection gains an explicit multi-record / mixed-execution case instead of falling back to conversation context.

**Definition:** Needed — three viable directions (a/b/c) with no tradeoff chosen yet.

**Plugin version:** 6.136.0
