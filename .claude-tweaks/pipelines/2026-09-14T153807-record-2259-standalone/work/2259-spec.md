# 2259: This repo's migration to the new release process (first consumer)

Surface: infra

## Overview

This repo becomes the first consumer of everything units 1-8 built, and this unit is the acceptance test for the whole design: retro-tag this repo's entire release history from `docs/shipped-versions.tsv`, bootstrap release-please, move the marketplace-mirror step into a `release: published` workflow, retire `plugin/bin/release.js` and its supporting modules, and rewrite every doc that describes the old process. **Scope split:** Deliverables 1-5 (retro-tag, bootstrap, mirror workflow, retirement, docs) land in one PR, in the order below — each step depends on the prior step's artifacts existing. Deliverable 6 ("First release through the new path") is a **separate, post-merge action** taken after that PR merges, not part of the PR's own diff — it cuts an actual release using the now-merged tooling, which by definition cannot happen before the PR that installs that tooling has landed.

**Complexity:** High
**Estimated tasks:** 8

## Non-Goals

- Rewriting this repo's historical CHANGELOG entries into the new release-please grammar — the switch point is a deliberate one-time boundary; pre-boundary entries keep their existing heading form, and the tag-to-CHANGELOG consistency probe (unit 7's generalized version) only asserts headings at or after the bootstrap version.
- Building any of units 1-8's underlying capability — this unit only consumes and configures what they produce; if any of units 1-8 is incomplete, this unit cannot proceed (see Gotchas).

## Current State

- `docs/shipped-versions.tsv`: the historical record of every shipped version this repo has produced — the source this unit retro-tags from, then retires.
- `plugin/bin/lib/release/status.js`'s `iterBumpCommits`: today's mechanism for walking bump commits; explicitly named in the design doc as "the last legitimate use" of that walk — after this unit, nothing in the shipped codebase performs a bump-commit walk again.
- `plugin/bin/release.js` + `plugin/bin/lib/release/{compose,mirror,precheck,run,status,unnamed-records}.js`: this repo's current maintainer-only release tooling. Everything except `precheck.js` and `run.js` is retired by this unit; `precheck.js` gains a `keySource: 'tags' | 'tsv'` parameter in unit 4 and stays shared between `release-local.js` (`'tags'`) and this repo's own tooling until this unit retires the `'tsv'`-calling side, and `run.js` is reused unchanged by unit 4 — neither is deleted here.
- `plugin/bin/lib/shipped-record.js`: bookkeeping helper retired alongside the above.
- `tests/bin-lib/release/`: the test suite for the retired modules, deleted **except** `subject.test.js` (unit 1's own test, which lives in `bin/lib/release/subject.js` and stays — that module is not retired).
- `tests/changelog-coverage.test.js`: today's tag-to-CHANGELOG coverage test for this repo specifically, replaced by unit 7's generalized probe's own test.
- `.github/workflows/`: no `release-please.yml` or `mirror-marketplace.yml` exist yet.
- `CHANGELOG.md`: entirely in this repo's current `## v{version} — {summary}` heading grammar, no boundary marker yet.
- `docs/releasing.md`, `CLAUDE.md` (Versioning/Releasing/commit-style sections), `docs/plugin-structure.md`: all describe the current `release.js`-based process.

## Deliverables

- [ ] **Retro-tag history.** For every line of `docs/shipped-versions.tsv`, resolve the corresponding bump commit via `status.js`'s `iterBumpCommits`, matched **by version string** (the tsv line's own version field is the join key against `iterBumpCommits`'s yielded `{version, sha}` pairs). Before tagging anything, print the full resolved `version → sha → date` triple list for every tsv line and confirm every line resolved to exactly one commit — a tsv line that resolves to zero or more than one commit **aborts the whole retro-tag step with no tags created or pushed** (never silently skipped or partially applied), naming the offending line so it can be fixed by hand before retrying. Once every line resolves cleanly: create an annotated tag `v{version}` dated to that commit (`GIT_COMMITTER_DATE` set to the commit's own date; the tag's own tagger identity is the operator's standard configured git identity — unchanged `git tag -a` behavior, only the committer *date* is overridden), message `v{version} — {summary}` where `{summary}` is exactly the post-em-dash text of that version's existing `## v{version} — {summary}` CHANGELOG heading (not the full entry body). Push all tags to origin. History survives the tsv's own retirement below.
- [ ] **Bootstrap release-please** via unit 3's init bootstrap step, run against the tip of this migration branch immediately after retro-tagging's tags are pushed and before any of this deliverable's own further edits: `release-type: simple`, `extra-files: [{type: json, path: plugin/.claude-plugin/plugin.json, jsonpath: $.version}]`, manifest seeded to the current shipped version, `last-release-sha` pinned to the **newest retro-tag's own commit** (the tag corresponding to the highest version in `shipped-versions.tsv` — i.e., this branch's tip at the moment retro-tagging finished, before this deliverable's own bootstrap edits land) — not the eventual PR merge commit, which doesn't exist yet at bootstrap time. `CHANGELOG.md` gains a one-line boundary comment immediately above the first release-please-generated entry, naming the grammar switch and the version it took effect at.
- [ ] **Marketplace mirror as a workflow.** New `.github/workflows/mirror-marketplace.yml`, triggered on `release: published`: PUTs the catalog entry `{source: git-subdir, url, path: plugin, sha: {release commit}}` into `thomasholknielsen/claude-tweaks-marketplace` — the exact write `plugin/bin/lib/release/mirror.js` performs today, preserving its two invariants (`sha`, never `ref`; no `version` field in the catalog entry). The workflow itself is the enforcement mechanism for the `MARKETPLACE_TOKEN` precondition (Manual Steps) — GitHub has no merge-blocking check tied to a secret's mere existence, so this workflow failing loudly (a clear API-auth error naming the missing/expired secret) at first real use, rather than a required PR check, is the accepted gate; an expired token surfaces through the identical loud-failure path as an absent one (the same GitHub API auth error), needing no separate handling.
- [ ] **Retire**: `plugin/bin/release.js`; `plugin/bin/lib/release/compose.js`, `mirror.js`, `run.js`, `status.js`, `unnamed-records.js` (`precheck.js` is NOT deleted — it was reused by unit 4, re-keyed against tags); `plugin/bin/lib/shipped-record.js`; `docs/shipped-versions.tsv`; `tests/bin-lib/release/` except `subject.test.js`; `tests/changelog-coverage.test.js` (replaced by unit 7's generalized probe's own test); the literal string `kind: release` wherever it appears in prose (`grep -rn "kind: release" plugin/ docs/ tests/` — the same four-directory convention `spec-template.md`'s generated-file grep already uses).
- [ ] **Docs.** `docs/releasing.md` rewritten around `/claude-tweaks:release`. `CLAUDE.md`'s Versioning bullet ("Version lives in plugin.json / bump minor…") becomes "Version is the `v*` tag; release-please bumps plugin.json; `/claude-tweaks:release` cuts it." The Releasing section's invocation line changes to the new skill. The commit-message-style bullet gains: "on `main`, subjects are conventional and plugin-written — feature-branch commits keep the `{Verb} {what} — {detail}` style." `docs/plugin-structure.md`'s CLI list drops the retired entries and gains units 4/5's new CLIs (if not already added by those units). New `docs/decisions/0018-release-please-engine.md` recording design doc stances 1, 3, 5, and 7 as an ADR (chosen because each is hard to reverse, surprising to a newcomer, or a real accepted trade-off).
- [ ] **First release through the new path** (post-merge, not part of the PR above — see Overview). Cut the version that carries this very family of changes through `/claude-tweaks:release`, proving unit 6 end to end against a real release, not a fixture. **No rollback of the PR-1-5 retirement is planned on failure here** — by this point `release.js` and its retired siblings are already gone from main, and there is deliberately no parallel old-path fallback to revert to (a dual-path fallback is exactly what Phase 1-9's design avoids elsewhere in this decomposition). A failure at this step is handled fix-forward, through the same named-partial-state-plus-recovery-command contract unit 6's own Step 6 Verify already provides for any release attempt — debug and re-run `/claude-tweaks:release` (or `bin/release-local.js` directly) against the reported partial state, exactly as any later ordinary release failure would be handled, not as a reason to reinstate the old tooling. Once this step lands cleanly, immediately re-verify AC4 (the CHANGELOG boundary comment) against the newly-generated real entry — release-please's own generation logic is the first thing that could disturb it, and this is the first real chance to observe that.

## Acceptance Criteria

1. The number of new `v*` tags this step creates equals `docs/shipped-versions.tsv`'s line count exactly (measured as a **before/after delta** on `git tag -l 'v*' | wc -l`, not an absolute count — correct even if the repo already carries unrelated pre-existing `v*` tags), measured immediately before the tsv file is deleted in this same PR.
2. `npm test` is green with the retired suites (`tests/bin-lib/release/` minus `subject.test.js`, `tests/changelog-coverage.test.js`) gone and unit 7's generalized-probe test present and passing.
3. The release that ships this family of changes has: an annotated `v*` tag, a GitHub Release, a release-please-generated CHANGELOG entry in the new grammar, and a mirrored marketplace catalog entry whose `sha` field is the release commit's sha (never a branch ref).
4. `CHANGELOG.md` contains exactly one boundary comment, positioned immediately above the first release-please-generated entry, and every entry above the comment keeps its pre-migration `## v{version} — {summary}` heading form unchanged — checked once right after bootstrap, and re-checked after Deliverable 6's real release lands (the second check is the one that actually exercises release-please's own generation logic against the comment).
5. `docs/plugin-structure.md`'s CLI list no longer references `plugin/bin/release.js`, and does reference `plugin/bin/release-local.js` and `plugin/bin/release-preflight.js`.
6. A grep for `plugin/bin/release.js` and each retired `plugin/bin/lib/release/*.js` module name (excluding `precheck.js` and `subject.js`) across `plugin/`, `docs/`, and `tests/` returns zero matches outside `docs/decisions/0018-release-please-engine.md`'s own historical description and `docs/incident-log.md`.
7. The PR description explicitly lists the `MARKETPLACE_TOKEN` human precondition (see Manual Steps below) as a merge precondition, and `mirror-marketplace.yml` fails loudly (a clear error naming the missing secret) rather than silently, when that secret is absent or expired.
8. Retro-tagging's own pre-flight check (Deliverables) aborts with zero tags created when at least one `shipped-versions.tsv` line fails to resolve to exactly one bump commit — proving the abort-on-ambiguity path, not merely the happy path where every line resolves cleanly.

## Technical Approach

This unit runs strictly last because every deliverable above assumes units 1-8 already exist and work: retro-tagging needs nothing from earlier units, but release-please bootstrap needs unit 3's bootstrap step, the mirror workflow needs unit 1's conventional-commit grammar to make sense of `release: published` payloads, and "first release through the new path" needs unit 6's skill to exist and unit 4/5's CLIs to back the local-merge fallback path if pr-first hits a snag. The ordering within this unit's own deliverables list matters too: retro-tagging before release-please bootstrap (so the bootstrap's `last-release-sha` has real prior tags to reason about), bootstrap before retirement (so nothing is deleted before its replacement is confirmed working), and "first release through the new path" last (it is the proof, not a precondition of anything else in this unit).

## Gotchas

- This unit is `Blocked by` units 1 through 8 — every one of them, not a subset; it is explicitly the acceptance test for the whole design, and running it against an incomplete set of prior units would mean bootstrapping release-please against merge subjects that aren't actually conventional yet (unit 1), a local-merge fallback path that doesn't exist (unit 4), or a skill that can't drive the release at all (unit 6).
- `precheck.js`'s collision logic moved into `bin/release-local.js` in unit 4 — do not delete `precheck.js` itself in this unit's retirement pass; only the five modules explicitly listed above are retired.
- **Related:** #1781, #1853, #1863, #1893, #1980, #1981, #1983, #1984 — other open records touching `docs/plugin-structure.md`; re-read its current state before this unit's own edit lands, since unit 4/5 may have already landed their own CLI-list rows by the time this unit runs.
- The marketplace-mirror workflow's two invariants (`sha`, never `ref`; no `version` field in the catalog entry) are load-bearing for how the marketplace resolves plugin versions — carry them forward exactly, do not "simplify" the payload shape while porting it from `mirror.js` into the new workflow.
- Deliverable 6 ("first release through the new path") is explicitly **not** part of the PR the other five deliverables land in — see Overview's scope split. Don't fold it into the same commit/PR under the "one PR" framing elsewhere in this record; that phrase describes deliverables 1-5 only.
- Retro-tagging's abort-on-ambiguity behavior (Deliverables) is a deliberate correctness-over-completeness choice: an incorrect historical tag is worse than a blocked migration, since tags are meant to be a permanent record — never fall back to a best-guess match or skip-and-continue on an unresolved tsv line.

## Manual Steps

- Create a fine-grained GitHub personal access token with `contents: write` scope on `thomasholknielsen/claude-tweaks-marketplace`, and store it as the `MARKETPLACE_TOKEN` secret on this repo, before `mirror-marketplace.yml` can succeed (reason-not-auto: requires-signoff — a human must create and scope a credential with write access to a separate repository; no CLI available to this build can provision that token on the user's behalf). The migration PR's description must state this as an explicit merge precondition.
