Root cause, product-side with test-side siblings. `defaultRunner` in `plugin/bin/lib/health-core/premise-self-check.js` (line 26) runs every Premise-check: command as `execFileSync('/bin/sh', ['-c', command], …)`. On win32, Node resolves the literal `/bin/sh` against the current drive root (`D:\bin\sh`), which does not exist, so the spawn throws `ENOENT` (the test-10 log line above). Both consumers then degrade to their fail-safe answer:

- `premiseReadsUnresolved` reads any throw as `false`. `plugin/bin/harness-health.js validate-findings` (its `premiseSelfCheck`, line 315) therefore drops every composed `Premise-check:` line at filing time. That accounts for cli-validate-findings tests 22–25 and 29 and premise-self-check tests 8 and 11.
- `plugin/bin/materialize.js`'s `computePremise` catches the throw from `runPremiseCheckDefault` (which is `defaultRunner`) and returns `premise: null`. That accounts for materialize AC5.1.

So on any Windows checkout the Premise-check feature is silently off end to end. harness-health files no premise lines, and `materialize.js` never evaluates one, so `satisfiedAtBase` is never detected. Both failures fail safe (nothing is wrongly auto-closed), but neither says why. The literal dates from #2633 (and `materialize.js`'s earlier runner before it). #3552 did not introduce it. #3552 added or rewrote tests that exercise it (cli-validate-findings 23–25, premise-self-check AC4.1, materialize AC5.1). verify.js's per-test baseline coverage (`plugin/bin/lib/verify/baseline.js`: a base run covers a file only when it names every test failing at HEAD) could not cover those tests at `13019828d`, so the three files became attributable. The older tests (cli-validate-findings 22 and 29, premise-self-check 8 and 10) run through the same literal at the base.

## Technical Approach

This is a product fix plus test alignment, following `.claude/skills/windows-checkout-test-parity/SKILL.md`. Its "Take `platform` and `env` as parameters" pattern gives `posixShell(platform)` and `defaultRunner`'s `platform` option; never stub `process.platform`. Its "Pin the win32 output with exact strings" pattern gives the `'sh'` and `'/bin/sh'` pins plus an injected-`exec` argument pin that runs on Linux CI. Its "A Windows-only launch failure must not read as a real answer" rule is why the drop-path test must assert a real exit code. The existing real-shell tests (premise-self-check 7–11, cli-validate-findings 22–25, materialize AC5.1) already serve as the win32 real-process round-trip once the shell resolves, so they get no `skip`. Running them on `windows-latest` is the ground truth.

Why `sh` from PATH on win32:

- Claude Code on Windows runs its Bash tool through Git Bash. A `node` process started from there (how every skill invokes `harness-health.js` and `materialize.js`) inherits Git's `usr\bin` on PATH, and `sh.exe` sits there and in `Git\bin`.
- `windows-regression.yml` runs its steps with `shell: bash`, so the runner's PATH is the same shape.
- PATH-resolved `bash` spawns already pass on `windows-latest` (`tests/session-tmp-resolve-cli.test.js`, `tests/flow-mixed-execution-convention.test.js` and `tests/issue-branch-tracking.test.js` are absent from the latest failing set).
- issue-payload test 25's `cmd.exe` run reached a PATH `grep` (exit 2, not `9009`).

When no `sh` is found, the spawn still throws `ENOENT` and both consumers keep today's fail-safe answer (line dropped, `premise: null`).

The command text itself needs no change. `buildPremiseCheck` (`plugin/bin/lib/harness-health/issue-payload.js`) composes POSIX `sh` with single-quoted operands and forward-slash repo-relative paths (#2857). The out-of-root fallback keeps a native absolute path, which on win32 is `D:\…`. MSYS `grep` accepts that inside single quotes, but only the `windows-latest` run proves it (cli-validate-findings test 25, premise-self-check tests 7 and 8).

## Gotchas

- Do not run the command with `shell: true`. On win32 that is `cmd.exe`, which understands neither `!` nor single quotes. That is exactly issue-payload test 25's Windows failure.
- Do not switch POSIX platforms to a PATH `sh`. `/bin/sh` stays PATH-independent off Windows, and changing it widens the blast radius for no Windows gain.
- Do not add `{ skip: process.platform === 'win32' }` to the real-shell tests to turn the run green. They are the only win32 round-trip for this runner, and skipping them hides a feature that is off end to end on Windows.
- Do not stub `process.platform` in any test. Pass `platform` explicitly.
- The dispatched `windows-regression.yml` run's overall verdict will pass even if these files still fail, because they fail at the integration-branch base too (#3568). Read the per-file logs.
- `tests/windows-hide-spawn-conformance.test.js` treats any `exec(` call under `plugin/bin/` as a spawn. If the injected seam is named `exec`, its call must name `windowsHide` in its own argument text.
- This changes Windows behavior on purpose. From now on, Premise-check: lines filed from Windows are kept when the premise still holds, and `materialize.js` on Windows can report `satisfiedAtBase: true`, as it already does on POSIX.
- Keep this record to the Premise-check runner, its four test files and the listed prose. `tests/dispatch-per-record-groups-prose.test.js` belongs to #3565. Other open `Windows regression:` records (#3429, #3507, #3509, #3562, #3564, #3565, #3581) cover different commits and files.
