## Current State

`dispatch/mcp-transport.md` already documents, as an accepted gap, that `bin/resolve-linked-prs.js`
(the #1224 open-linked-PR exclusion) has no confirmed MCP mapping and fails open (no exclusions)
when `gh` is absent. This run hit that gap for real, not hypothetically: of the 27 candidates in
the eligible queue, record #1594 already had an open PR (#1908, "Fixes #1594") that the automated
check could not detect on this transport. It was caught only because the dispatching session
independently ran a manual, targeted subagent scan of open PR bodies/titles for closing-keyword
references before finalizing the group selection — a step the documented protocol does not
actually specify or require anywhere. Without that improvised check, #1594 could have been
re-dispatched to a second build in parallel with the already-open PR #1908, producing conflicting
work on the same record.

## Deliverables

- [ ] Treat this as evidence for prioritizing a real MCP mapping for the #1224 check (a batched
      equivalent of `closedByPullRequestsReferences`, or an open-PR title/body scan folded
      directly into `queue-pull-script.md`'s MCP branch) rather than leaving it "accepted for now"
      indefinitely.
- [ ] Until a real mapping exists, consider making the manual verification this run improvised a
      documented, required step in `dispatch/mcp-transport.md`'s Step 2 section for the `gh`-absent
      path, so a future firing doesn't have to independently rediscover the same gap and the same
      workaround.

## Acceptance Criteria

1. Either the #1224 check gets a real MCP mapping, or the manual verification workaround is
   promoted from this run's improvisation to a documented, required step for the `gh`-absent
   transport.
