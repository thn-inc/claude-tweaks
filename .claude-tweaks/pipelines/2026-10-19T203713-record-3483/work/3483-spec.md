# 3483: Wrap-up leave-open outcome: re-check PR mergeability after the phase-exit push and merge main when a sibling merge made it DIRTY

Origin: wrap-up of #3298

Defer-reason: tangential

## Current State

When the Review Console resolves the merge half to **leave-open** (`pending-review`), `wrap-up/execution-and-verification.md`'s phase-exit push ships the branch and the run ends. Nothing re-reads the PR's `mergeStateStatus` after that push. On #3298's run the pushed head `eb759e308` was `DIRTY` against `main` (three commits had landed since the fork, one touching the same journey Origin list), so GitHub suppressed the `test` workflow entirely (#3298 wrap-up, `decisions.md` 23:42:18) — the parked PR showed one green label job and no test run, which a human reading the PR would mistake for "checks still pending".

`_shared/pr-first-merge.md` Step 2.5's merge-verification gate reads this state, but only on the merge path. The parked path has no equivalent, so a conflict introduced by a sibling merge during the run is discovered only when a human opens the PR later.

## Deliverables

- [ ] After the wrap-up phase-exit push under `integration-model: pr-first` with a leave-open outcome, read `gh pr view {n} --json mergeStateStatus` once (via `pack.pr`'s shape); on `DIRTY`, merge `origin/{integration-branch}` into the branch in the worktree, resolve nothing automatically beyond git's own auto-merge, and push again — a real content conflict stays `DIRTY` and is reported, never silently left.
- [ ] Log the outcome to `decisions.md` (`AUTO … mergeability: {CLEAN|BLOCKED|DIRTY → merged main as {sha}|DIRTY — conflict in {files}}`) and name it in the phase-trace report's Verdict line and the flow summary's resume-to-merge row, so a parked PR with a suppressed test run is visible from the summary.
- [ ] A conformance test pins the new paragraph in `execution-and-verification.md` and `flow/summary-template.md`'s resume row wording.

## Acceptance Criteria

- A `pr-first` run whose console resolves leave-open and whose PR reads `DIRTY` after the phase-exit push ends with a merge-from-main commit pushed (when git auto-merges cleanly) and a `decisions.md` line naming the merge sha; the flow summary's resume-to-merge row names the merge.
- A run whose PR reads `DIRTY` with a genuine content conflict ends with a `decisions.md` line naming the conflicting file(s) and the Verdict line reads `blocked — conflict with main in {files}`, never "everything shipped".
- A `CLEAN`/`BLOCKED`/`UNKNOWN` read changes nothing beyond the one log line.

## Release Note

A parked pr-first run now notices when a sibling merge made its PR conflict with main, merges main when git can, and says so instead of leaving a PR whose CI never ran.
