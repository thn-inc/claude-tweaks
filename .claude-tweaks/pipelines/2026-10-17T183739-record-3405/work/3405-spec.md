# 3405: Merge-verification reads a partial check rollup as green before every workflow has registered

Origin: wrap-up merge step from #3316

Defer-reason: pre-existing-outside-diff

## Current State

`plugin/skills/_shared/pr-first-merge.md` Step 2.5 classifies a PR's checks from `statusCheckRollup` and its bounded watch keys on `gh pr checks` exit codes. An **empty** rollup reads as pending under `merge-when-green`/`wait`, but a **partial** one, where some workflows have reported and others have not registered yet, reads as green.

Observed on PR #3390 (#3316 wrap-up, 2026-10-17): right after a push, the rollup and `gh pr checks` held only `label-fix-branch` (SUCCESS) and `cleanup-fix-labels` (SKIPPED). The `pull_request` `test` run for the same head (39042323352) existed with status `pending` but was not yet in the rollup. `gh pr checks` exited 0, and the watch returned green. Following the procedure literally would have merged without the test suite.

## Deliverables

- [ ] Before treating a rollup as green, cross-check the workflow runs for the PR head sha (`gh run list --commit {headRefOid}` or the check-suites API): any run for that sha that is not `completed` makes the state pending.
- [ ] Apply the same check in the bounded watch's `RC=0` branch, so "all green" means every workflow triggered for the head has reported.
- [ ] A unit-level seam for the classification (rollup + head-sha runs → green/pending/red), with tests.

## Acceptance Criteria

- A test where the rollup is all SUCCESS/SKIPPED but a run for the head sha is `pending` classifies as pending, not green.
- A test where every run for the head sha is completed and successful classifies as green.
- `pr-first-merge.md` Step 2.5 states the cross-check, and its Signatures section records the PR #3390 capture.

## Release Note

Pipeline merges wait until every CI workflow for the pushed commit has reported, not only the ones that reported first.

_Filed by `wrap-up merge step` via specShapedBody._

## Build deviations (Common Step 4.5)

- **Beneficial — the head-run read reaches every Step 2.5 consumer, not only Step 2.5.** The Deliverables named `pr-first-merge.md` Step 2.5 and a unit seam. The build also wired the seam into `plugin/bin/pr-checks.js` (the shared reader behind `/test`'s and `/review`'s PR-check gate, `_shared/pr-check-gate.md`), and added the head-run read to the consumers that restate Step 2.5's read rather than citing it: `release/execute.md` (release PR merge), `dispatch/resume-confirmation.md`, `tidy/actions-github-issues.md`, `dispatch/close-out.md`. Without these, the same partial-rollup race stayed open on the release and resume paths.
- **Residual, not closed here:** the cross-check sees only workflow runs that already exist; a `pull_request` run not yet created leaves the pre-registration window open. Recorded as an observation in the run ledger for a follow-up record.
