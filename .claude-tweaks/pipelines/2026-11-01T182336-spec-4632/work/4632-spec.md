# 4632: Two findings at paths holding a space can share a truncated Review Console key

Surface: infra

**Related:** #4581, #4038, #4620, #3977, #4621, #4636, #4663, #4679, #4751

## Current State

The Review Console settles a STAGED finding line when a later tiebreak verdict carries the same finding key `{lens}|{path}:{line}` (`plugin/bin/lib/console/resolve.js`, `tiebreakModel`). Both sides of that join build the key with `findingKey` (line ~750), which takes the first `FINDING_PATH` match before `:\d+`. `FINDING_PATH` (line 510) leaves the space out on purpose, because a space joins prose to a path. So a path holding a space keys from its last space onward on **both** sides.

Probed on `main` (2026-11-01): a dropped verdict line for `lens "3b" finding a dir/x.ts:3` parses with `path: "a dir/x.ts"` but `key: "3b|dir/x.ts:3"`, because `parseTiebreakLine` (line 471) sets `key: findingKey(line)` and ignores the whole path its own regex captured. The STAGED lines for `a dir/x.ts:3` and `b dir/x.ts:3` both key `3b|dir/x.ts:3`, so one verdict settles both. A lone space-holding path settles correctly today, because both sides truncate alike. The bug needs two such paths that share a suffix after their last space, at the same lens and line.

Verdict lines are written by code (`plugin/bin/lib/tiebreak.js` `resolveTiebreak`: `` `lens "${finding.lens}" finding ${finding.path}:${shownLine}` ``), so their path is exact. STAGED lines are LLM-written from templates (`plugin/skills/review/step3-lens-dispatch.md`, `step3-debate-and-refutation.md`, `step3-tiebreak.md`, `_shared/multi-agent-coordination.md`) and drift from them. A scan of 2,699 local `decisions.md` files (3,204 lens lines carrying a `finding`/`findings`/`disagreement on` anchor) found 55 where the text after the anchor is not just the path: `finding at plugin/skills/flow/claim-targets.md:272`, `finding Error handling at plugin/bin/lib/feedback/file-feedback.js:144`. Keying a STAGED line from the text after `finding ` would turn those into keys no verdict carries, and lines that settle today would stop settling.

`TIEBREAK_CONFIRMED_RE` (line 468) captures the path as `(\S+)`, so a confirmed verdict at a space-holding path does not parse as a verdict at all.

## Deliverables

- [ ] A tiebreak verdict line keys its finding by the whole path its regex already captures: `parseTiebreakLine` builds `key` from the parsed lens, path and line, not from `findingKey(line)`.
- [ ] `TIEBREAK_CONFIRMED_RE` captures a path holding a space, anchored on the verdict's own `confirmed by tiebreak:` tail, the same way `TIEBREAK_STEP_HEAD` already does with `(.+)`.
- [ ] A STAGED line's location yields an ordered set of candidate keys instead of one key. Each candidate path ends where the `FINDING_PATH` match ends (just before `:{line}`) and starts at a boundary to its left. The shortest candidate is today's `FINDING_PATH` match, and each longer one extends left across a space (or any other character outside the `FINDING_PATH` class) to the start of the previous run. Extension stops at a `"`, an em dash `—`, or the line start.
- [ ] Settlement (`settledAfter`, the `latestStaged` index, the console-verdict `absorbed` check, the `contested` lookup in `coordinationItems`) matches a STAGED location on the longest candidate that some settler's key names, and treats that candidate as the location's key from then on.
- [ ] `lineKeys`'s second (coincidence) location follows the same candidate rule.
- [ ] Tests in `tests/bin-lib/console/resolve.test.js` for every Acceptance Criterion below, each shown failing on `main` before the change (revert the source and see red).

## Technical Approach

The verdict side is exact, so it is the anchor. Only the STAGED side is ambiguous, and it never has to be parsed into one path: it offers every path it could be naming, and the verdict decides which. A candidate set always includes today's key, so no line that settles today stops settling, drifted prose included. Choosing the longest named candidate means `a dir/x.ts` beats `dir/x.ts` when verdicts exist for both.

Keep `findingKey`'s current return value as the shortest candidate (prose settlers still use it, see Gotchas). Add one helper next to it that returns a location's candidate keys, and change `lineKeys` to return candidate sets. Keep the change inside `tiebreakModel`/`coordinationItems`. The STAGED-before-verdict index rule, latest-verdict-wins, and #4583's re-stage handling keep their current semantics, just keyed on the resolved candidate. A later prose settler (debate entry or #3772 `Confirmed` sentence) also settles a location at its shortest key, since prose never carries a whole path; tiebreak verdicts settle only through the resolved candidate.

### Key Files

- `plugin/bin/lib/console/resolve.js` — verdict key from parsed whole path; `TIEBREAK_CONFIRMED_RE` path capture; candidate-key helper; candidate-aware `lineKeys` and settlement lookups in `tiebreakModel` and `coordinationItems`
- `tests/bin-lib/console/resolve.test.js` — space-path collision, lone space path per verdict kind, confirmed-verdict parse, drifted-prose regression, space-free byte-identity
- `plugin/bin/lib/tiebreak.js` — evidence at the finding's own space-holding path (Plan Review Clarifications); `verdictLineRe`'s confirmed alternative anchored on the line end like `TIEBREAK_CONFIRMED_RE`, so the archive tiebreak-coverage gate and the console agree that an agent-written line with text after `Confirmed.` is not a verdict (build alignment, Beneficial)
- `tests/bin-lib/tiebreak.test.js` — findingPath evidence parse, coverage of an anchored confirmed line

## Gotchas

- Prose settlers keep `FINDING_PATH` keys. A converged-positive debate line (`debateConvergedKeys`), the producer's own `Confirmed` AUTO sentence (#3772), and a contested file's `## Positions` bullets (`contestedPositionKeys`) are LLM-written and carry no exact path, so they still key on the shortest candidate. Two space-holding paths sharing a suffix can still both be settled by one such line. That's accepted: no machine-written path exists on those lines to anchor on, and fixing it means delimiting the path in the producer templates (a cross-skill prose contract change) for a case with 0 occurrences in this repo (`git ls-files | grep -c " "` → 0).
- Producer templates are not changed. Delimiting the path at the producer (backticks) was considered and rejected: it touches roughly a dozen template sites and their conformance pins, and drifted lines would still arrive without the delimiter.
- `console.json`'s stored `tiebreak.key` changes only for a verdict whose path holds a character outside `FINDING_PATH` (a space, `,`, `=`). Stored ids are opaque and nothing joins on the stored key.
- `plugin/bin/lib/console/backfill.js` is out of scope. It joins verdicts by tiebreak id (`t.id === tid`), not by key; its `t.key` is its own token id (minted under `LEGACY_LOCATION_RE`). Its line-less path class is #4751's.
- #4581 also edits `findingKey`/`lineKeys` in the same file (aggregate STAGED lines with shortened locations). Whichever lands second rebases onto the other; the two fixes don't conflict in behavior.
- Candidate extension must stay bounded by the stop characters above, or a long prose lead-in multiplies candidates per line for no gain.
