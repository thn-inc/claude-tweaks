# 3497: Decide how a multi-spec run's consolidated pass is re-entered after the parent /flow session has ended

Surface: infra

## Current State

A multi-spec `/claude-tweaks:flow` run in `auto` or `hybrid` mode sets `MULTISPEC_CURATION_DEFER=1` and `MULTISPEC_REVIEW_DEFER=1` on every spec. Each spec then skips its own Reflect, curation engine and Review Console. All three run once, in a single consolidated pass: the parent `/flow` session runs `plugin/skills/flow/multispec-batch-curation.md` and then `plugin/skills/flow/multispec-review-console.md` after the last spec reaches `wrap-up`. Nothing else performs that deferred work.

**Gap.** The pass can only be re-entered after a Halt. The resume-only step `review-console` (`plugin/skills/flow/steps-and-gates.md` lines 22 and 39, and `multispec-review-console.md`'s "On stop (option 3)") is accepted only on a resume after a Halt at the consolidated console. A parent session that ends any other way before the pass runs leaves the run's deferred work unperformed, and nothing offers it again. PR #3484 (#3033) wrote this limit down in `plugin/skills/flow/multi-spec.md`'s `## Mixed execution (a spec built outside /flow)`, in step 3 and the "Already closed?" paragraph. The fallback named there, `/claude-tweaks:wrap-up #{n}` once per record, recovers each record's own Reflect, curation and console, but never the run-level batch pass.

**The pass does not need the parent session.** Every input it reads is on disk. `manifest.yml` holds per-spec status. The parent's `decisions.md`, `staged/` and `engine-state.json` hold the run's state. The diff is taken from the merge-base with the integration branch, and the Halt resume already rebuilds the console from the same parent directory. The gap is the Halt-only gate, not lost state.

**Detection exists today but offers no recovery.** `plugin/bin/lib/hooks/session-residue.js`'s `collectStaleRuns` feeds SessionStart's "unfinished pipeline run(s)" banner (`plugin/bin/lib/hooks/session-start.js`) and `hooks.js check-session-residue`. For each listed run it names only `close-run`, and `close-run` on an unpassed multi-spec parent permanently forfeits the deferred work. There is one precedent for a per-run recovery suffix: `run-integrity.js`'s `shipped-unclosed` verdict appends a `/claude-tweaks:wrap-up` pointer.

**Real-data audit (2026-10-18).** Of 47 multi-spec run directories under `.claude-tweaks/pipelines/` (live and `archive/`), 13 carry a `console.json` and 23 show no sign of a consolidated pass (no `console.json`, no consolidated-console entry in `decisions.md`). Some of the older ones may predate the console. Example: `archive/2026-09-13T233549-record-2280-2281` was archived with review and polish logged clean and no console entry; its `manifest.yml` still reads `running` for both specs. `2026-08-30T105718-spec-1703-1704` is still unarchived, with both specs `pending`.

**Decision (2026-10-18, brainstorm via `/claude-tweaks:specify #3497`).** Widen `review-console` into the re-entry, so it re-enters the same pass rather than adding a parallel path (#3033's constraint). Cut off at landed or archived runs, where the per-record fallback stays the documented, lossy answer. Have the session-start banner name the re-entry command for eligible runs.

**Related:** #2734, #2869, #2912, #3002, #3047, #3048, #3079, #3263, #3284, #3289, #3295, #3297, #3363, #3377, #3416, #3431, #3442, #3483, #3503, #3511, #3515

## Deliverables

1. **`review-console` accepts a second entry condition, ended-parent re-entry,** besides today's Halt resume. Eligible when all of the following hold:
   - the parent run directory exists unarchived under `$RUN_ROOT`, with a `manifest.yml`;
   - its `config.yml` `mode:` is `auto` or `hybrid`;
   - the parent holds no `console.json`;
   - no `manifest.yml` spec has status `pending` or `running`;
   - the run's branch has not landed (`run-integrity.js` does not return `shipped-unclosed`).

   On this entry the batch pass (`multispec-batch-curation.md`) runs first when the parent has no `engine-state.json`. The consolidated console follows, with its normal Shared teardown and `close-run`. An ineligible invocation stops with one message naming the failed condition. When the failed condition is "landed" or "archived", the message points at the per-record `/claude-tweaks:wrap-up #{n}` fallback.
2. **The eligibility rule is implemented once,** as a read-only exported helper under `plugin/bin/lib/`. Both the `review-console` entry check and the session-residue banner consume it, so the two cannot drift apart on what counts as re-enterable. The skill prose cites the helper instead of restating the five conditions.
3. **`collectStaleRuns` appends a re-entry suffix** to an eligible multi-spec parent's line: ` — consolidated pass never ran: /claude-tweaks:flow #{id1},#{id2} review-console`. Ids come from `manifest.yml`'s `specs[].id`. The `shipped-unclosed` line still wins when both apply.
4. **The prose is updated to match:**
   - `steps-and-gates.md`'s two `review-console` passages and `multispec-review-console.md` (its "On stop" paragraph, plus a new re-entry section) state both entry conditions.
   - `multi-spec.md`'s Mixed execution step 3 names the re-entry command instead of "no documented step re-runs the pass".
   - The "Already closed?" paragraph is scoped to landed or archived runs. It keeps the per-record fallback, documented as never recovering the batch pass.

## Release Note

Finish a multi-spec /flow run's consolidated wrap-up after its parent session ended, with `/claude-tweaks:flow #A,#B review-console`; session start now names that command for such runs.

## Technical Approach

Add a pure, read-only eligibility function next to the manifest reader. `plugin/bin/lib/flow/manifest.js` already owns `VALID_STATUSES` (`pending`, `running`, `complete`, `failed`, `not-run`) and manifest parsing. The function takes a run directory and returns `{ eligible, reason, specIds }`, and it reuses `run-integrity.js`'s `checkRunIntegrity` for the landed check rather than re-deriving merge state. `session-residue.js`'s `collectStaleRuns` calls it after its existing `shipped-unclosed` branch, inside the same advisory try/catch, so a helper failure never breaks the scan. The `review-console` prose calls the same helper (a `node -e` require or an existing `hooks.js` verb, whichever is the house pattern for a prose-side bin check) before re-entering. On eligible, the run follows the steps `multispec-review-console.md` already defines: step 0 (batch pass) when `engine-state.json` is absent, then Present → approval → Shared teardown.

### As built (Common Step 4.5 — Beneficial deviations)

- The eligibility helper lives in a new `plugin/bin/lib/flow/consolidated-pass.js` (`checkPassReentry`, `REENTRY_REASONS`), not `manifest.js`. It reads `config.yml`, `run-state.json`, `console.json` (through `plugin/bin/lib/path-guard`), worktree-lock state and git merge evidence, none of which `manifest.js` owns. `manifest.js` is consumed (`readManifest`) unchanged.
- Eligibility carries two conditions beyond Deliverable 1's five. `closed` (run-state status `clean`) routes a `close-run`-closed run to the per-record fallback. `parent-live` (worktree lock held by a live pid, or `checkResumeFreshness` not safe for an `interrupted` run, with the caller's own session exempt) keeps the banner and the re-entry from inviting a second consolidated pass over a live sibling's run. The final whole-branch review found the real window in run `3352-3464`.
- `plugin/bin/lib/hooks/session-start.js`'s relay directive now names the re-entry command for lines that carry one. `tests/bin-lib/flow/consolidated-pass.test.js` and `tests/flow-pass-reentry-conformance.test.js` are new. `docs/journeys/rejoin-a-multispec-run-with-a-spec-built-outside-flow-3033.md` step 5 covers both paths.
- Review fixes (code review, low tier): the banner suffix carries the full run dir, ` — consolidated pass never ran: PIPELINE_RUN_DIR="{dir}" /claude-tweaks:flow #{ids} review-console`, so a pasted command never falls back to the most-recent-slug heuristic, and it is suppressed when any manifest id is not an integer. The relay directive adds "never run either command yourself". The re-entry eligibility command takes the run dir as an argument and fails closed on a non-zero exit or non-JSON output. A degraded online PR check needs the PR confirmed unmerged before the pass runs.

## Gotchas

- **Adopt the parent run directory.** `/claude-tweaks:flow {specs} review-console` has to resolve to the parent directory (`multispec-review-console.md`'s "Locating the parent run directory"). Otherwise Step 2.8 (`claim-targets.md`) mints a fresh run and contests claims the ended parent still holds. This is the same failure `multi-spec.md`'s Mixed execution step 1 avoids with `PIPELINE_RUN_DIR`.
- **Stale `running` statuses.** Older runs never updated their manifest (`2280-2281` reads `running` though the specs finished), so they are correctly ineligible. The ineligible message names the blocking spec and the manual `hooks.js spec-status --run … --spec {id} --status complete` correction instead of failing silently.
- **Banner cap and ownership wording.** The banner shows at most `MAX_REPORTED` (3) runs, so the suffix only reaches those. The banner's existing "only the session owning a run should close it" sentence stays as is; the suffix offers a command and never asserts the run is abandoned.
- **Read-only module.** `session-residue.js` is read-only by contract (header comment), so the helper must not write, append events, or touch git.
- **Pinned banner text.** `tests/hooks-session-start.test.js` and the conformance suites pin banner and skill prose, so run the full suite, not only the touched files.
- **What the batch pass seeds from.** It seeds only from completed specs' `/claude-tweaks:review` Key Learnings. Confirm those are read from per-spec run-directory files on disk, not from the parent session's memory, before claiming re-entry is lossless.

## Current State

Open ledger item 11 of #3033 (PR #3484). A multi-spec `/claude-tweaks:flow` run in `auto` or `hybrid` mode defers every spec's Reflect, curation engine and Review Console to one consolidated pass that the parent `/flow` session runs after the last spec reaches `wrap-up`. That pass is the only thing that performs the deferred work (`plugin/skills/flow/multispec-review-console.md`, `plugin/skills/flow/multispec-batch-curation.md`).

Nothing documented re-runs the pass once the parent session has ended. `plugin/skills/flow/steps-and-gates.md` names `review-console` as the only step that re-enters a multi-spec parent run, and only after a Halt. A parent session that ended before the pass ran leaves a run whose deferred work is lost. The new `## Mixed execution (a spec built outside /flow)` section of `plugin/skills/flow/multi-spec.md` states this limit and falls back to `/claude-tweaks:wrap-up #{n}` once per record, which recovers each record's own Reflect, curation and console but never the run-level batch pass.

## Deliverables

- The chosen re-entry (or the chosen decision not to offer one) is implemented and documented where `multi-spec.md`'s Mixed execution step 3 and "Already closed?" paragraph now state the limit, and those two passages are updated to match.

## Open Question

Should `/claude-tweaks:flow` gain a step that rebuilds the batch curation pass and the consolidated console from an ended parent run's directory, or is the per-record `/claude-tweaks:wrap-up #{n}` fallback the intended answer, documented as lossy? #3033 rejected a second consolidation path beside `/flow`'s multi-spec console, so a new step has to be a re-entry into that same pass, not a parallel one.

## Release Note

A multi-spec run whose parent session ended before its consolidated wrap-up gets a defined way to finish that wrap-up, or a documented statement that it cannot.
