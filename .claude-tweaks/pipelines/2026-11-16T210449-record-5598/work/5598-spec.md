# 5598: Settle a review's lens replies in one call: parse the tables, pair them, log the lines

Surface: backend

**Related:** #5540, #5535, #5214, #5557, #3835
Risk-flags: none

## Current State

A lens reviewer in `/claude-tweaks:review` Step 3 replies with a markdown table (`| Severity | Path:Line | Finding | Evidence |`), or the literal `No findings.`, and a last line `STATUS: {WORD}` (`plugin/skills/review/step3-lens-dispatch.md`, "Per-lens Calibration + Output template"). No code reads that reply. For each lens pair the reviewing session resolves two paths, turns each table into a JSON findings array by hand, writes both with the Write tool, and calls `review-coordination.js categorise-reproduction` (the same file, line 92). At `high` that is seven path calls, fourteen writes and seven pairing calls, and the session types every finding a second time.

Checked on 2026-11-16 at `026e203f3`:

- No module under `plugin/bin` parses the table. `git grep -l 'Path:Line' -- plugin/bin` names `lib/coordination.js`, `lib/console/resolve.js` and `lib/console/finding-outcomes.js`; none splits a table row.
- `normalizeFinding` and `parsePathLine` (`plugin/bin/lib/coordination.js:131` and `:163`) exist because hand transcriptions differ: a combined `Path:Line` key, a split `path` and `line`, `Finding` or `text`.
- The status line's position is checked by the session reading the reply, and by `plugin/bin/lib/hooks/subagent-stop.js` when that hook fires.
- `tools/replay-scratch/counterfactual.js` has a scratch `parseTable`. #5557 turns it into a maintainer tool under `tools/`, which does not ship and which `plugin/` may not require.

#5599 runs the lens reviewers from a workflow script. A script cannot require a module, so it returns each reviewer's reply as text, and everything after that has to be one call into code that ships: read the replies, pair them, log the lines. This record adds that call. #5595 adds the line writer it uses.

Design: `docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 6. The design has the script return findings as structured output. This record keeps the reply as text and parses it in the CLI, because forcing a schema makes the agent answer through a structured-output tool call, which contradicts the brief's own output block (a table, then a status line) that must reach the reviewer unchanged.

## Deliverables

1. **A reply parser.** New `plugin/bin/lib/lens-reply.js`, pure: reply text in, `{ parse, findings, noFindings, overflow, status, statusWord }` out.
   - `findings`: one `{ severity, path, line, text, evidence }` per table row whose first cell is a severity word (`critical`, `high`, `medium`, `low`, `info`, case and `**`/backticks ignored). `Path:Line` is split by `parsePathLine`, the one location parser. A row with no numeric line keeps `line` undefined.
   - A row reading `+N more` sets `overflow` to N and is not a finding. The header and separator rows are skipped. Decided 2026-11-16: a reviewer with `overflow` above 0 is still usable and its lens is still paired, as on the Task path, where the session pairs the fifteen rows the brief allows. The verb lists the reviewer under `overflow` with the hidden count, and the session names it in the review summary. A finding behind the cap was never pairable on either path.
   - A cell boundary is a `|` that is not escaped and not inside a backtick span. When a row still has more than four cells, the surplus joins the Evidence cell. The lens brief's header has four columns (`step3-lens-dispatch.md:136`); the five-column form belongs to other dispatch templates. Cells are mapped by header name when a header row is present, so a column the parser does not know is dropped, never folded into Evidence; with no header row the cells are taken in the brief's order. The surplus rule is for a row with more cells than its header. An unclosed backtick span runs to the end of the row. A row with fewer cells than the header is still a finding when its first cell is a severity word and its second parses as a location, with the missing cells empty. A reply holding both rows and `No findings.` has its `findings` and `noFindings: false`.
   - `parse` is `ok` when the reply holds at least one finding row or the literal `No findings.`, else `unparseable`.
   - `status` is `ok` when the last non-empty line is exactly `STATUS: {WORD}` with one of the four words, `misplaced` when it is not and a status line in the canonical or a lenient form is among the first three or last three non-empty lines, else `missing`. `statusWord` is the word found, or null.
2. **One verb for a whole fan-out.** `review-coordination.js settle-lens-replies <result.json> --ctx-id <id> [--run <dir> --only confirmed|unconfirmed [--hold <file>]]`. The file holds `{ lenses: [{ lens, reviewers }], reviewers: [{ lens, side, text, failed }] }`, the value #5599's script returns, either at the top level or under a top-level `result` key. For each lens the verb parses its replies, gives each reviewer a state, pairs a lens whose two reviewers are both usable with `categoriseReproduction`, and with `--run` logs that lens's lines through #5595's composer under the same `--only` and `--hold` rules. It prints one JSON line. The line is `{ settled: [{ lens, confirmed, unconfirmed, entries, logged }], needsSession: [{ lens, reason, reviewers: [{ side, state, statusWord, text, findingsPath }] }], violations: [{ lens, side, status }], overflow: [{ lens, side, hidden }] }`. `reason` is `single-reviewer` or `reviewer-unusable`. `text` is present for a `not-done` reviewer only and `findingsPath` for a usable one only. `entries` and `logged` are as in #5595 and are absent without `--run`. A lens whose two reviewers both report no findings is settled with empty lists and no line. Exit codes: 0 whenever the input was well formed, also when every lens is under `needsSession`; 2 for a malformed invocation or input; 3 for a run directory that is missing or not anchored. With `--run`, `--only` is required as in #5595, and a `--hold` entry carries `lens` beside the four fields #5595 matches on, because one file covers every lens. Decided 2026-11-16: like #5595's CLI the verb does not de-duplicate log lines; it is called once with `--only confirmed` and once with `--only unconfirmed`. A findings file is written whole each time, so a second call replaces it with the same content.
3. **Reviewer states.** **Closed rule:** a reviewer is exactly one of `failed`, `not-done`, `unparseable`, `status-missing`, `status-misplaced` or `ok`, by the ordered test at the end of this item. A `not-done` reviewer's text is returned so the session can act on the stated reason. No other state exists. An entry whose `text` is neither a string nor null, or whose `failed` is not a boolean, is a malformed input and exits 2. A plan review that finds a seventh state adds its refusal as a plan amendment, never as a `needs-human` gap. Decided 2026-11-16: the states are tested in a fixed order and the first that fits is the reviewer's state, so each reviewer has exactly one: `failed` (`failed: true`, or `text` null or blank after trimming, whatever else the entry holds); `not-done` (the status word, read from the last line or from a misplaced status line, is `BLOCKED` or `NEEDS_CONTEXT`); `unparseable` (`parse` is not `ok`); `status-missing`; `status-misplaced`; `ok`. Decided 2026-11-16: a reply with a table and no status line cannot be told from one that was cut off, so `status-missing` is not usable and its lens goes to `needsSession`. `status-misplaced` is usable and is reported. A last line of `STATUS: DONE_WITH_CONCERNS` is `ok`, with the word in the output.
4. **Lenses it does not settle.** A lens with a reviewer in state `failed`, `not-done`, `unparseable` or `status-missing`, or declared with one reviewer, is not paired and gets no line. The verb lists it under `needsSession` with each reviewer's state, and writes each usable reviewer's findings array to the session-scoped path today's prose uses (`review-{ctx-id}-lens-{LENS}-agent{A|B}.json`, resolved through `plugin/bin/lib/session-tmp.js`), so the session continues with the existing per-pair steps.
5. **Never a clean result from nothing.** A result file with no reviewers, a lens named twice for one side, a side other than `A` or `B`, or a file that is not the shape above exits 2 and writes and logs nothing. A lens is reported as settled only when two usable replies were paired. Decided 2026-11-16: the result file carries the roster, as `lenses: [{ lens, reviewers }]`, `reviewers` being 1 or 2 as the session asked. A file with no `lenses`, a roster lens or side with no entry, or an entry the roster does not name exits 2. So a lens whose reviewers were dropped can never be missing from the output, and "declared with one reviewer" is read from the roster.
6. **Docs.** `docs/plugin-structure.md` describes the verb, its output and its exit codes.

## Technical Approach

The parser is the only new judgment about reply shape. Keep it small and total: every input string gets a result, never a throw. The status rule is `subagent-stop.js`'s canonical and lenient tiers. Checked on 2026-11-16: `subagent-stop.js` exports `detectStatus` and not its two patterns (`CANONICAL_RE`, `LENIENT_RE`, lines 150 and 165). Decided 2026-11-16: the two patterns move, unchanged, into one small module, `plugin/bin/lib/status-line.js`, which the hook and the parser both require, so there is one list and the hook's other requires do not load in the CLI. The lenient form takes a leading `- `, `**Status:**` or a bare word. One test builds a reply from the live output block of `step3-lens-dispatch.md` (its header row, its severity scale, its `+N more` sentence and its status line) and asserts the parser reads it, so a change to the template turns a test red (`.claude/skills/prose-code-twin-pin`).

The verb is a loop over lenses around three existing pieces: the parser, `categoriseReproduction`, and #5595's composer with `appendEntries`. It adds no pairing rule and no line form.

Decide between the bare shape and the `result`-wrapped shape from the file's top-level keys: a top-level `reviewers` array is the bare shape; otherwise a top-level `result` object holding one is the wrapped shape; anything else is the exit-2 case.

The session-scoped paths come from `sessionTmpPath` with the session id from the environment, as `session-tmp-resolve.js` resolves them, so the names match the ones `step3-lens-dispatch.md` tells the session to use. `lens` and `--ctx-id` become part of a file name. Each must be a single plain path segment: `lens` matches `FINDING_LENS_CLASS` (`plugin/bin/lib/console/finding-path.js`) from end to end, and `--ctx-id` holds no path separator, no `..` and no line break. Anything else exits 2 before any file is written. `--ctx-id` names the files and the session id from the environment picks the directory; neither overrides the other. The run directory goes through `anchorRunDir` as in #5595, unchanged; this record adds no path rule.

The new verb follows this CLI's existing hand-written argument parsing. Checked on 2026-11-16: #5533 lists the shared argument parser as not yet specified. If a record has started on it for `review-coordination.js` when this is built, land after it.
