# 3757: verify.js stamps the HEAD it reads after the checks finish, so a mid-run commit gets a pass it never had

Origin: found during #3048 wrap-up (refs #3048)

Defer-reason: tangential

## Current State

`plugin/bin/verify.js` reads `const git = gitInfo()` (line ~543) only after `runChecks` returns (line ~529). It then writes the pass stamp with `sha: git.sha` / `fullSha: git.sha` (lines ~767, ~850). The HEAD it stamps is therefore whatever HEAD is when the checks finish, not the commit the checks ran against.

Observed in run `2026-10-20T124340-record-3048` (#3048 wrap-up). A scoped re-verify started at `0a2899a20`. Commits `fa379674c` (a `.claude/skills` split) and `3c1ffb78b` landed during its ~204 s run. The stamp names `3c1ffb78b` with `verifiedHead: true`, and the next scoped run printed `still-verified: no changes since 3c1ffb78b` without running a single check. A later quiescent `npm test` at `3c1ffb78b` happened to pass (13936 tests, 0 fail), but nothing in the stamp proved that.

## Deliverables

- Snapshot HEAD and dirty state once, before `runChecks`, and use that snapshot for every stamp field that names the verified commit.
- If HEAD or the tree moved by the time the checks finish, write no full-pass stamp for the new HEAD (stamp the start SHA only, or none) and print one stdout line saying the tree moved during the run.

## Acceptance Criteria

- A `tests/bin-lib/verify/cli.test.js` case whose fake check command commits inside the fixture repo shows the stamp does not name the new HEAD, and `--stamp-status` then reports `verifiedHead: false`.
- With HEAD unchanged across the run, the stamp is byte-identical in shape to today's (existing stamp tests pass unchanged).

## Release Note

A verification pass is no longer credited to a commit that landed while the tests were still running.

## Technical Approach

### Key Files

- `plugin/bin/verify.js` — snapshot HEAD before runChecks; refuse a moved-HEAD stamp
- `tests/bin-lib/verify/cli.test.js` — moved-HEAD-during-run case
