# 2541: flow multi-spec: boundary freshness HARD-GATE has no unattended default

Surface: infra

## Current State

The per-spec boundary freshness check introduced by #1074/#1076 (`skills/flow/multispec-freshness.md`, invoked from `multi-spec.md`'s per-spec scaffold) requires an `AskUserQuestion` when `origin/{integration-branch}` has moved past the batch base, even when the run is `auto` and the project's `autonomy` is `unattended`. On an unattended multi-spec run the gate therefore fires at every spec boundary the integration branch has moved past — on an active repository that is most boundaries — and the run stalls with nobody present to answer.

Observed on a two-spec `/claude-tweaks:flow` run (auto, `autonomy: unattended`, plugin 6.123.0, Windows 11 / Claude Code CLI): the gate fired between spec 1 and spec 2 after the integration branch gained three unrelated commits. The controller applied the gate's own option 1 (merge the integration branch, re-validate the spec premises) as a logged ruling because no human was there; the merge was clean and the run completed. The outcome was right, but it was reached outside the contract.

## Deliverables

- [ ] Give the gate an unattended default: under `autonomy: unattended` (the same tier that unlocks `consoleAutoResolve`), auto-select option 1 (merge, re-validate premises) when the merge is conflict-free and the moved hunks do not touch the next spec's declared files, and log it as an `AUTO` decision with the moved commits named
- [ ] Keep the stop for the two cases that need a human: a conflicting merge, or moved hunks that overlap the next spec's files

## Acceptance Criteria

- [ ] An unattended multi-spec run whose integration branch moved by disjoint commits proceeds past the boundary with an `AUTO` line in `decisions.md` and no `AskUserQuestion`
- [ ] The same run with an overlapping or conflicting move still stops at the gate exactly as today
- [ ] `supervised`/`trusted` behaviour is unchanged
- [ ] `npm test` passes, including new coverage for the unattended auto-select path

## Technical Approach

In `skills/flow/multispec-freshness.md`'s per-boundary check, before raising the `HARD-GATE` `AskUserQuestion`, branch on `autonomy: unattended`: attempt the merge, and when it is conflict-free and the incoming diff does not overlap run-modified paths or the remaining specs' Key Files (the same overlap check the gate already computes to decide whether to escalate at all), apply option 1 automatically and log an `AUTO` decisions.md line naming the moved commits. When the merge conflicts, or the diff overlaps declared files, fall through to today's `AskUserQuestion` unchanged — this is the same two-way branch `multi-spec.md`'s own boundary-freshness paragraph already documents (trivial drift merges automatically; a conflict or overlap escalates), just gated on the autonomy tier for which branch of that existing behavior applies without a human present.

### Key Files

- `plugin/skills/flow/multispec-freshness.md` — the per-boundary check and its `HARD-GATE` `AskUserQuestion`
- `plugin/skills/flow/multi-spec.md` — the caller invoking the check per spec boundary

## Gotchas

- The auto-select path must reuse the gate's own existing overlap computation (run-modified paths, remaining specs' Key Files) rather than a separate, potentially-diverging check — two independently-maintained overlap definitions would drift.
- `MULTISPEC_KEEP_GOING` explicitly does not bypass this HARD-GATE today (per `multi-spec.md`) — the new unattended auto-select must not be confused with that env var's bypass; it is a distinct, autonomy-tier-gated default, not a way to skip the escalation cases.
