# 2582: Release notes: pr-first post-publish step

Surface: infra

## Overview

`pr-first` projects (this repo, post-#2259 migration) run release-please,
which has no knowledge of this repo's custom `Release-Note:` trailer and will
not render it anywhere. This sub-issue adds a new step, triggered on
`release: published` (the same event #2259's forthcoming
`mirror-marketplace.yml` uses), that walks the just-published commit range,
extracts every `Release-Note:` trailer, renders them with the shared
`release-notes.js` module (the sibling local-merge sub-issue's deliverable),
and applies the rendered block to both the already-published GitHub Release
body and a follow-up commit appending the same block into CHANGELOG.md's
just-written entry for that version.

This design deliberately runs **after** publish, against the final merged
commit range, rather than editing release-please's own PR branch mid-flight —
editing that branch would depend on undocumented release-please internal
behavior (untested, and this design makes no claim about whether such an
edit would survive into the eventual published release body). Running
post-publish means the only dependencies are `git log` and the `gh` CLI, both
already used elsewhere in this repo's tooling.

**This sub-issue is externally blocked on #2259.** #2259 has not yet
introduced the `release: published` workflow trigger (or
`mirror-marketplace.yml`) this sub-issue attaches to — do not start this
sub-issue's build until #2259 has landed and that trigger/file actually
exists in the checkout.

**Complexity:** Medium
**Estimated tasks:** 8

## Non-Goals

- Depending on or editing release-please's own PR branch mid-flight — this
  design explicitly rejects that approach (see Overview) because it is
  undocumented, untested behavior with no guarantee an edit there survives
  into the published release body.
- Grouping the rendered list under type-derived headings — same non-goal as
  the local-merge sub-issue; this step reuses `renderReleaseNotes` unchanged,
  it does not re-implement or extend its rendering logic.
- Running this step, or any variant of it, as a live release-engine test.
  Per this repo's own convention against invoking a live release engine as a
  test, the fixture test for this sub-issue runs against a fixture repo,
  never a real GitHub release.
- Deciding definitively whether the new step lives inside #2259's
  `mirror-marketplace.yml` or a sibling workflow file — the design doc
  leaves this an open item for the implementation to resolve once #2259's
  actual file layout exists (see Gotchas).

## Deliverables

- [ ] Confirm #2259 has landed and identify its actual `release: published`
      trigger file (`.github/workflows/mirror-marketplace.yml` or whatever
      it turned out to be named) — this is a blocking precondition, not
      optional context-gathering; do not proceed past this point until
      confirmed.
- [ ] Add a new step to that workflow (or a new sibling workflow file
      triggered on the same `release: published` event — pick based on
      #2259's actual file layout, since the design doc explicitly defers
      this call). Resolve the previous/new tag pair via
      `gh release list --json tagName,publishedAt --limit 2` run at step
      time: the two most-recently-published releases, ordered by
      `publishedAt`, are the just-published one (newest) and the previous
      one (second-newest) — this anchors to actual publish order rather
      than a semver or chronological-tag-creation guess. When the call
      returns fewer than 2 releases (this is the first-ever published
      release), treat the step as a no-op on both write targets — the same
      no-op path as "zero `Release-Note:` trailers found," not an error.
- [ ] Once a previous/new tag pair resolves, walk first-parent commits
      between them via `git log --first-parent {previous}..{new}`, extract
      `Release-Note:` footers using the `RELEASE_NOTE_FOOTER_RE` constant
      imported from `plugin/bin/lib/release-notes.js` (the sibling
      local-merge sub-issue's export — never a second hand-typed copy of
      the pattern), and render the result via that same module's
      `renderReleaseNotes` (reused, not duplicated).
- [ ] Create the script module implementing the commit-range-walk →
      extract → render logic above (e.g.
      `plugin/bin/lib/release-notes-publish.js` or an equivalent name —
      implementation's call), taking the previous/new tag pair and returning
      the rendered block (or `null` when no commit in range carries a
      `Release-Note:` footer, or when the first-release no-op above
      applies).
- [ ] Apply the rendered block to the already-published GitHub Release body
      by fetching the current body first (`gh release view <tag> --json
      body -q .body`), checking whether it already contains the exact
      rendered block (idempotency guard — see below), and, when it doesn't,
      concatenating `\n\n### Highlights\n{rendered block}` onto the fetched
      body and writing it back via `gh release edit <tag> --notes-file -`
      (or the equivalent API call) — append via read-then-concatenate-
      then-write, never a bare `--notes` call that would replace the
      release-please-generated body outright. The heading text
      (`### Highlights`) matches the local-merge sub-issue's own pinned
      heading.
- [ ] Apply the same rendered block to CHANGELOG.md via a small follow-up
      commit: locate the just-written entry for this version as the
      content between the first `## ` heading in CHANGELOG.md and the next
      `## ` heading (or end of file) — release-please always prepends its
      newest entry at the top, so this is always the first entry at the
      time this step runs — check whether that entry already contains the
      exact rendered block (the same idempotency guard as the Release body
      above), and when it doesn't, append `\n\n### Highlights\n{rendered
      block}` to the end of that entry and commit the change. Commit using
      the workflow's own `GITHUB_TOKEN` — the same credential class
      release-please's own bot already uses to land its Release PR's merge
      commit directly on the default branch; this follow-up commit is the
      same class of automated, non-human-reviewed maintenance commit, not a
      new precedent for this repo.
- [ ] Add a fixture test exercising the full commit-range-walk → render →
      dual-apply flow against a fixture repo (never a live release) —
      covering: a range with `Release-Note:` trailers present, a range with
      none (a true no-op on both targets), a first-release case (fewer
      than 2 published releases — a no-op), and a re-run of the same tag
      pair (the idempotency guard must skip re-applying to a target that
      already contains the rendered block, on both targets independently).

## Acceptance Criteria

1. Given a fixture commit range containing one or more `Release-Note:`
   trailers, the new script module renders the correct block (identical to
   what `renderReleaseNotes` would produce over the equivalent parsed-commit
   array), fetches each target's current content first, and appends
   `### Highlights\n{block}` to both the fixture GitHub Release body and
   the fixture CHANGELOG.md entry (never replacing existing content).
2. Given a fixture commit range with zero `Release-Note:` trailers, the step
   is a no-op on both targets — no empty block, no error, no CHANGELOG
   commit created, no `gh release edit` call made.
3. Given a fixture `gh release list` response with fewer than 2 published
   releases (first-ever release), the step is a no-op on both targets,
   identical to the zero-trailers case — no previous tag is resolved and no
   commit-range walk is attempted.
4. Given a fixture Release body or CHANGELOG entry that **already contains**
   the exact rendered block (simulating a retried or re-fired
   `release: published` event), the step skips re-applying to that target —
   verified independently for each of the two targets, so a re-run applies
   to neither, one, or both depending on which already carry the block.
5. The fixture test exercising the cases above runs entirely against a
   fixture repo (a local git repo and mocked/fixture `gh` responses, or
   equivalent) and never invokes a live GitHub release or a live `gh
   release edit`/`git push` against this repo or any real repo.
6. The commit-range walk uses `git log --first-parent {previous}..{new}`
   (not a plain `git log`, which would include merge-commit-internal
   history the first-parent walk is meant to exclude) between the tag pair
   resolved from `gh release list`'s two most-recently-published entries.
7. The `Release-Note:` extraction in the new script module imports
   `RELEASE_NOTE_FOOTER_RE` from `plugin/bin/lib/release-notes.js` rather
   than declaring a second copy of the pattern — verified by a grep/code
   check that no second `Release-Note:`-matching regex literal exists in
   the new module.
8. The new script module imports and calls
   `plugin/bin/lib/release-notes.js`'s `renderReleaseNotes` rather than
   reimplementing its filter/map/join logic inline — verified by a code
   review / grep check that no second flat-list-rendering implementation
   exists in the new module.
9. The CHANGELOG.md entry-location logic identifies "the just-written
   entry" as the content between the first `## ` heading and the next
   `## ` heading (or end of file) — verified by a fixture CHANGELOG.md with
   at least two version entries, confirming the block lands in the first
   one only.

## Release Note

Published release notes automatically after each release goes out.

## Technical Approach

This step is intentionally the mirror image of the local-merge sub-issue's
wiring, applied to a different data source (a `git log --first-parent` walk
over a tag range, rather than already-parsed local-merge commit objects) and
a different pair of write targets (a published GitHub Release body plus a
follow-up CHANGELOG.md commit, rather than an in-memory CHANGELOG render).
Reusing `renderReleaseNotes` unchanged, rather than re-deriving rendering
logic here, is the point of extracting it into its own shared module in the
local-merge sub-issue.

## Gotchas

- **Externally blocked on #2259.** The `release: published` trigger this
  sub-issue attaches to does not exist in this repo until #2259 lands — do
  not assume `.github/workflows/mirror-marketplace.yml` exists; verify it
  (or whatever #2259 actually shipped) before starting. Once #2259's actual
  file layout is known and this step's home file is chosen, record that
  decision back into this sub-issue's own `## Key Files` list (edit this
  record) rather than leaving the choice undocumented in git history alone.
- Never invoke a live release engine as a test — this repo's own existing
  convention (cited directly in the design doc's Testing section). The
  fixture test for this sub-issue must run entirely against fixture/mocked
  state.
- Reuse `plugin/bin/lib/release-notes.js`'s `renderReleaseNotes` **and**
  `RELEASE_NOTE_FOOTER_RE` unchanged — do not reimplement either in the new
  script module, even partially.
- `gh release edit` replaces the entire release body — there is no native
  "append" operation. The fetch-current-body-then-concatenate-then-write
  sequence in the Deliverables above is mandatory, not optional; a bare
  `gh release edit <tag> --notes "..."` call would silently destroy the
  release-please-generated body.
- **Idempotency matters because both write targets are appends, not
  replaces.** A retried or manually re-triggered `release: published` event
  must not double-append the same block — the containment check in the
  Deliverables above (skip a target that already has the exact rendered
  block) is what makes a re-run safe, independently per target.
- The follow-up CHANGELOG.md commit lands directly on the default branch
  using the workflow's own `GITHUB_TOKEN`, the same credential class
  release-please's own bot commit already uses — this is not a new
  precedent for direct-to-main automation in this repo.
- This sub-issue is blocked by both sibling sub-issues: the authoring
  contract (Unit 1, defines the `Release-Note:` trailer format) and the
  local-merge rendering unit (Unit 2, provides the shared
  `plugin/bin/lib/release-notes.js` module — both the renderer and the
  exported regex constant — this step reuses) — build order is Unit 1,
  then Unit 2, then this one, and only once #2259 has also landed.
