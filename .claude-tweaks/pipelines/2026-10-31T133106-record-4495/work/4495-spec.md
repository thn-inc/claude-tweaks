# 4495: claim-targets: a missing claims-registry branch is reported as a contested claim (holder null)

Surface: infra

**Related:** #4265, #4269, #4423

## Current State

Claims live as `claims/issue-<n>.json` blobs on the `claims-registry` branch (`plugin/bin/lib/issues/claims.js:13`, `_shared/issue-claims.md`). Nothing creates that branch. A repository whose remote never had it fails its first claim.

Observed on 6.156.1: the first `/claude-tweaks:flow #N` on a repository with no `claims-registry` branch on origin had `claim-targets.js` (flow Step 2.8) exit 3, "contested", with `holder: null`. No other run held the record, so the operator went looking for a competing run that did not exist. The workaround was creating `claims-registry` on the remote by hand from the default branch, after which the claim succeeded (exit 0). Every repository hits this on its first flow run.

What the code does with a missing branch:

- The git transport's read (`plugin/bin/lib/issues/claims-git-cas.js:120-131`) runs `git fetch -q origin claims-registry:<scratch>`. For a missing remote ref that fails, and the catch maps it to `failure: 'transport-failure'`. `classifyGitError` (`:72-84`) has no "couldn't find remote ref" case.
- The contents-API path (`plugin/bin/lib/issues/claim-store.js`) treats a 404 as "absent" (`:141`, `:261`). On a missing branch, a read of `claims/issue-<n>.json?ref=claims-registry` therefore reads as "no claim yet", and the write that follows is refused.
- How that refused write becomes exit 3 with `holder: null` still needs tracing through `claim-targets.js`'s outcome mapping. Most likely a failed write with no readable holder is reported as contested.

## Deliverables

1. Detect "the `claims-registry` branch does not exist on the remote" as its own outcome on both transports. Git: `git ls-remote --heads origin claims-registry` is empty, or the fetch error names a missing remote ref. Contents API: `GET repos/{owner}/{repo}/branches/claims-registry` returns 404. Never fold it into `contested` or a generic transport failure.
2. On that outcome, bootstrap the branch once, then retry the claim. Create `claims-registry` from the default branch's tip (the same base the manual workaround used), CAS-guarded: a create that loses to a concurrent bootstrap (ref already exists) is treated as success and the claim proceeds against the now-existing branch.
3. If the bootstrap itself fails (permissions, protected-ref rule), exit with a dedicated code and message, not 3: `claims-registry branch missing on origin and could not be created: {reason} — create it from the default branch`. Document the new exit code in `claim-targets.js`'s header and in `_shared/issue-claims.md`.

## Acceptance Criteria

- Against a fixture remote with no `claims-registry` branch, `claim-targets.js --targets N` creates the branch and exits 0 with the claim recorded, on both transports.
- Two concurrent first claims (different records) against a branchless remote both succeed. Exactly one branch creation wins and neither run reports contested.
- When branch creation is refused (simulated permission error), the CLI exits with the new dedicated code and the message names the missing branch. It never exits 3.
- A genuinely contested claim (a live holder) still exits 3 with that holder named.
- Tests cover all four cases with fake runners for `claims-git-cas.js`/`claim-store.js`. `release-claim.js` against a branchless remote reports "nothing to release", not an error.

## Release Note

The first pipeline run in a new repository no longer reports a false "someone else is building this" claim conflict. The claim branch is now created automatically.

## Technical Approach

The reporter offered two fixes: auto-create the branch, or exit with a dedicated code. Both are kept, as a ladder. Bootstrapping removes the first-run friction for every repository, and the dedicated code covers the case where creation is not permitted. An orphan branch was considered and rejected: the manual workaround and any existing tooling expect a default-branch-based ref, and an orphan root commit would surprise `git log` readers. Keep the bootstrap in one shared helper both transports call, next to the existing CAS core.

### Key Files

- `plugin/bin/lib/issues/claims-git-cas.js` — missing-ref classification and git bootstrap
- `plugin/bin/lib/issues/claim-store.js` — contents-API missing-branch detection and bootstrap
- `plugin/bin/claim-targets.js` — outcome mapping and the new exit code
- `plugin/bin/release-claim.js` — branchless remote reads as nothing to release
- `plugin/skills/_shared/issue-claims.md` — document bootstrap and the new exit code

## Gotchas

- Callers interpret `claim-targets.js` exit codes (3 and 5 at least: flow Step 2.8, dispatch, specify's drain). Pick an unused code and grep every caller's exit-code handling before adding it.
- A branch-protection ruleset on `claims-registry`'s name pattern could block creation but allow later pushes. Surface the reason verbatim rather than retrying.

## Original request

claim-targets: a missing claims-registry branch is reported as a contested claim (holder null)

**Summary:** On a repo that never used the git claim transport, the first claim exits 3 (contested, holder null) because the `claims-registry` branch does not exist yet.

**Kind:** Defect

**Affected component:** `bin/claim-targets.js` (flow Step 2.8, git claim transport)

**Repro steps:**
1. In a repository whose remote has no `claims-registry` branch, run `/claude-tweaks:flow #N`.
2. Step 2.8 runs `claim-targets.js`.

**Expected vs. actual:**
Expected: the first claim bootstraps the `claims-registry` branch, or the script reports a distinct, actionable error ("claims-registry branch missing on origin; create it from the default branch").
Actual: `claim-targets.js` exits 3 ("contested") with `holder: null`. No other run holds the record, so the operator goes looking for a competing run that doesn't exist.

**Workaround used:** creating `claims-registry` on the remote by hand from the default branch, then re-running the claim (exit 0).

**Why it matters:** every repo hits this on its first flow run, so the plugin's first impression is a false "someone else is building this".

**Suggested fix:** in the git transport, distinguish "ref not found" from "ref exists and holds a live claim". On the former, either create the branch (an orphan or default-branch-based ref, CAS-guarded like other claim writes) or exit with a dedicated code and message.

**Definition:** Clear
