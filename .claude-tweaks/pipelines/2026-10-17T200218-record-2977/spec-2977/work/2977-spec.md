## Current State

The report, filed via `/claude-tweaks:feedback` against plugin 6.129.0 from a private-project run on 2026-10-04, describes a double path. `/claude-tweaks:review` Step 6.7 staged a Design-Quality audit `warning` as `staged/review-design-1.patch`, and `design-wrapper polish` Step 5 then dispatched the same finding's `suggestion` (`harden`), applying the identical `aria-label` edit. The staged patch went stale and had to be removed by hand.

On the current tree this hand-off already exists. It shipped in PR #2389 (merged 2026-09-23, first released in v6.130.0, one release after the reporter's 6.129.0 build), which fixed records #2280 and #2281:

- `plugin/skills/review/code-mode-steps.md:342` (Step 6.7 item 3, "Write the disposition back to the audit cache") sets `dispositionByReview: {status, at}` on the matching audit-cache entry by `id`. The routing outcome maps to a status, and STAGED becomes `staged`.

- `tests/review-polish-disposition-conformance.test.js` pins both halves: the write-back with all five statuses, and polish's check-order ahead of `suggestion`.

The reported scenario (a staged audit finding later re-applied by polish's `harden` dispatch) is therefore the exact case #2389 closes. The reporter's run used a build that predates it. What remains is confirming that and closing the record.

## Original request

review Step 6.7 + design-wrapper polish Step 5: an audit finding is staged as a patch and then applied again by polish's suggestion dispatch

**Summary:** With `polish` still in the run's step list, `/review` Step 6.7 stages a Design-Quality audit `warning` as a patch under the `review-auto-apply-ceiling: low` routing, and `design-wrapper polish` Step 5 then dispatches that same finding's own `suggestion` command (`harden`), which applies the identical edit — the staged patch goes stale and must be removed by hand or reaches the Review Console already applied.

**Kind:** Defect

**Affected component:** `skills/review/code-mode-steps.md` Step 6.7 (late findings routing) and `skills/design-wrapper/modes/polish.md` Step 5 (suggestion-driven dispatch)

**Repro steps:**
1. Run `/claude-tweaks:flow` on a frontend record with the default step list (review then polish), `review-auto-apply-ceiling: low`, `design-critique: auto`.
2. Let `design-wrapper review` produce one audit finding of severity P2/`warning` whose `suggestion` names `harden` (e.g. a missing `aria-label` on an element).
3. Observe `/review` Step 6.7 stage it as `staged/review-design-1.patch` (validated with `git apply --check` at staging time) with a ledger back-reference.
4. Let the polish phase run: Step 5 reads the same audit cache entry and dispatches `harden`, which applies the same edit in the working tree.
5. Run polish's re-verify / reach the Review Console: the staged patch no longer passes `git apply --check`.

**Expected vs. actual:**
Expected: one owner per audit finding — either Step 6.7 defers a finding that polish's suggestion-driven dispatch will take (when `polish` is still in the step list and the suggestion names a non-manual command), logging `deferred to polish (suggestion: {command})`, or polish's Step 5 marks the matching staged patch superseded (rename to `.applied` or delete, with a decisions.md line) when its dispatch lands.
Actual: both consumers read the same audit cache entry with no hand-off between them. In one run in a private project (plugin 6.129.0, 2026-10-04), the review phase staged the patch at 16:21 and the polish phase's `harden` applied the identical `aria-label` edit at 18:35; the operator removed the patch by hand and logged it as superseded. Had it survived to the console, it would have failed the apply check and triggered the slower Invariant re-derivation for an edit already in the tree. Why-chain: `design-wrapper review` writes the cache and `/review` stages in the same pass with no "polish will take this" marker; the two consumers were added by different records. Observed cost: one hand cleanup, no lost work; the double path holds in any project.

**Definition:** Clear — the cheaper fix (defer in Step 6.7 when `polish` remains in the step list) closes the double path; the alternative (polish marks the patch superseded) is a fallback, not an undecided choice.

**Plugin version:** 6.129.0
