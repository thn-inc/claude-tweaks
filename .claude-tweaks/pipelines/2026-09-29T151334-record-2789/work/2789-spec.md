# 2789: dispatch/flow MCP-transport claim-bootstrap wipes an issue's full label set via issue_write

Surface: backend (plugin's own `dispatch`/`flow` Step 2.8 claim-bootstrap, `gh`-absent MCP transport path)

## Current State
During a live `/claude-tweaks:dispatch next` firing (2026-09-28, cloud Routine sandbox, `gh` CLI absent, MCP transport in use per `dispatch/mcp-transport.md`), the dispatched build,test agent's own Step 2.8 claim-bootstrap called `mcp__github__issue_write` with `labels: ["bot:in-progress"]` to add the in-progress marker to #2663 and #2666. This MCP tool **replaces** the full label array rather than appending/merging. It briefly wiped every pre-existing label on both issues. The agent partially restored `ready`+`auto:build` on high-confidence grounds, but no MCP tool exposes label-change history/timeline events, so the original `risk:*`/`size:*`/`priority:*`/`ceremony:*`/`type:*`/`shaped:*` labels could not be mechanically recovered.

Verified post-incident label state:
- #2663: was `[ready, risk:low, size:low, type:feature, auto:build, priority:low, ceremony:standard, shaped:headless]` → now `[ready, auto:build]`.
- #2666: was `[ready, risk:low, size:low, type:feature, auto:build, priority:medium, ceremony:standard, shaped:headless]` → now `[ready, bot:blocked]`.

Root cause: `_shared/github-write-transport.md`'s CRUD mapping for a label-add operation (used at minimum by `flow/claim-targets.md`'s Step 2.8 bootstrap, and possibly other same-shaped call sites in `settle-and-merge.md`/`dispatch/mcp-transport.md`) does not document that `issue_write`'s `labels` parameter is a full-replace, not a merge — so a naive single-label array silently destroys every other label with no warning and no recovery path.

## Deliverables
1. Audit every MCP-transport call site that adds/removes a label via `mcp__github__issue_write` (claim-bootstrap in `flow/claim-targets.md`, Settle's grant-removal/`bot:blocked` steps in `dispatch/settle-and-merge.md`, wrap-up's Section E release-claim label removal) and fix each to read-then-merge: fetch the issue's current `labels` first (a call already being made in most of these flows), compute the full desired set, and pass the complete merged array to `issue_write`.
2. Add an explicit warning to `_shared/github-write-transport.md`'s CRUD mapping table documenting that `issue_write`'s `labels` field is full-replace, not additive/subtractive — the single most important gotcha for anyone adding a new MCP-transport label call site.
3. A regression test (or documented manual-verification step, if no test harness covers MCP call shaping) asserting that a label-add call site never reduces an issue's label count when other labels were present beforehand.

## Acceptance Criteria
- Every audited call site in Deliverable 1 reads current labels before writing, and a live/simulated call against an issue carrying unrelated labels (e.g. `risk:*`, `size:*`) preserves them across a `bot:in-progress`/`bot:blocked`/grant-removal label operation.
- `_shared/github-write-transport.md` states the full-replace behavior explicitly, in the same table row(s) that document the label-add/remove mapping.
- #2663 and #2666 (or whichever records are still open when this ships) have their categorization labels (`risk:`, `size:`, `priority:`, `ceremony:`, `type:`, `shaped:`) manually restored by a human/`/tidy` sweep, since this record's fix prevents recurrence but cannot recover the already-lost data.

## Technical Approach
Grep `bin/lib` and `skills/**/*.md` for `mcp__github__issue_write` / `issue_write` call sites whose `method` writes `labels`, cross-reference against `_shared/github-write-transport.md`'s documented mapping, and apply the read-merge-write fix uniformly rather than patching only the one call site this incident hit.

### Key Files
- `plugin/skills/_shared/github-write-transport.md` — CRUD mapping table, needs the full-replace warning.
- `plugin/skills/flow/claim-targets.md` — Step 2.8 claim-bootstrap, the call site that triggered this incident.
- `plugin/skills/dispatch/settle-and-merge.md` — Settle's label-removal steps, likely the same pattern.
- `plugin/skills/wrap-up/cleanup-procedures-execution.md` — Section E's grant/`bot:in-progress` removal, likely the same pattern.

## Gotchas
- This is a data-loss bug, not just a correctness bug — every prior occurrence (if any, before this one was caught) may have silently wiped labels on other records with nobody noticing, since the symptom (missing categorization labels) doesn't surface as an error anywhere in the pipeline.
- The fix must not assume the record's `labels` field from an earlier fetch in the same call chain is still fresh — a genuine read-immediately-before-write is needed to avoid a stale-read race against a concurrent label change.
