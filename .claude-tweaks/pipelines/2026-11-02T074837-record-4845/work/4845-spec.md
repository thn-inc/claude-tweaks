# 4845: Artifact-overwrite check: attribute only the run's own first-parent commits

Surface: infra

Origin: split out of #4593 at its third plan review (issuecomment-6562062652, Q7) — the maintainer chose Reading A, filing first-parent filtering as its own record

Defer-reason: tangential

**Related:** #4593

## Current State

`plugin/bin/lib/flow/artifact-overwrite-check.js` collects its A/M events with `git log --reverse --diff-filter=AM --name-status -z --format=%H {base}..{head}` (line 350), with no `--first-parent`. Every commit a catch-up merge brought in through its second parent is therefore walked as if it were one of the run's own commits. The raw fallback walk in `plugin/skills/flow/multispec-artifact-namespacing.md` (`git -C "$WORKTREE" log --name-status --diff-filter=AM "{EXPECTED_BASE}..HEAD" -- docs/journeys/ stories/`, the walk used when the tool exits 2 or 3) has the same gap.

This is a false positive today, independent of #4593. Probed on 2026-11-01 (git 2.56.0) with a scratch repo: base; spec A adds `docs/journeys/a.md` (`refs #1`); upstream adds `docs/journeys/up.md` (`refs #999`); the run catch-up merges main; spec B (`refs #2`) edits a line of `up.md`. Today's walk sees `A up.md` (the upstream commit) followed by `M up.md` (spec B), and `checkArtifactOverwrite` returns `clean: false`, with the deleted line traced to the upstream commit "whose refs trailer does not match". Spec B only updated a journey that already existed upstream, so no spec's artifact was overwritten.

The same probe shows why `--first-parent` alone is not enough. On git 2.31 and later it implies `--diff-merges=first-parent`, so the catch-up merge commit itself reports `A up.md` and the false positive comes back, attributed to the merge. Only `--first-parent --no-merges` drops the upstream event: the walk then sees `A a.md` (spec A) and `M up.md` (spec B) with no preceding add, and the path is skipped.

Once #4593 adds manifest-window attribution, upstream commits authored inside a spec's window could additionally be attributed to that spec. The maintainer asked for first-parent filtering on #4593 (issuecomment-6555467984: "Filter to first-parent run commits before attributing"), and #4593's third plan review (issuecomment-6562062652, Q7) split it out into this record.

## Deliverables

1. `checkArtifactOverwrite`'s event walk runs `git log --first-parent --no-merges` over the run range, so a commit reachable only through a catch-up merge's second parent, and the catch-up merge commit itself, are never among the run's own A/M events.
2. In the per-hunk blame test, a deleted line whose blamed commit is not on the run's own first-parent chain (`git rev-list --first-parent {base}..{head}`, catch-up merge commits included) counts as updating content that predates the run's own work, from the base or from upstream, not as a cross-spec overwrite. A line blamed to a catch-up merge commit stays inside the set and keeps failing closed, because a merge carries no `refs #N` trailer, so a conflict resolution that rewrote a spec's lines is never cleared this way. A deleted line with no blame attribution still fails closed, as today.
3. `multispec-artifact-namespacing.md`'s raw fallback walk adds `--first-parent --no-merges`, and the prose names the first-parent scope once, so a manual ruling sees the same event set as the tool.
4. Test fixtures in `tests/bin-lib/flow/artifact-overwrite-check.test.js`:
   - The probe's shape: an upstream-added journey edited by a run spec after a catch-up merge is clean.
   - Through the test file's existing `fakeGit` seam: a run-added journey whose later spec deletes a line that blame attributes to a SHA outside the first-parent chain is clean (Deliverable 2). The same deletion blamed to a first-parent merge commit is still an overwrite.
   - A genuine cross-spec overwrite that sits after a catch-up merge is still reported.

## Acceptance Criteria

- [ ] With a catch-up merge in the range, an upstream commit is never reported as a run event: the probe-shaped fixture returns `clean: true`.
- [ ] The `fakeGit` fixture returns `clean: true` when the deleted line is blamed to a SHA outside the first-parent chain, and `clean: false` when it is blamed to a first-parent merge commit.
- [ ] A genuine cross-spec overwrite after a catch-up merge still returns `clean: false`, naming the overwriting spec's commit.
- [ ] Removing `--first-parent` turns the probe-shaped fixture red. So does keeping `--first-parent` but removing `--no-merges`, since the merge commit re-attributes the upstream add. Both red runs are quoted in the PR.
- [ ] The existing fixtures and the live replays (the #1988–#1997 range and the `729a5ae5e..4706f21db` step insertion) keep their current verdicts.
- [ ] `multispec-artifact-namespacing.md`'s raw walk command includes `--first-parent --no-merges`.
- [ ] `npm test` passes.

## Release Note

Stop the multi-spec artifact-overwrite check from flagging a run's edit to a journey that a catch-up merge brought in from upstream.

## Technical Approach

- In `checkArtifactOverwrite`, add `--first-parent` and `--no-merges` to the A/M `git log` call. Compute the run's own commit set once with `git rev-list --first-parent {base}..{head}` (merges included, unlike the event walk) through the module's injectable `git` runner, and pass it to the blame test so that test checks `runCommits.has(blamedSha)` before the refs comparison. A blamed SHA outside the set is pre-run content and clears that line. A blamed SHA inside the set keeps today's same-refs self-edit test, which a merge commit always fails.
- Update the raw walk command and one sentence of prose in `multispec-artifact-namespacing.md`.
- Build the fixtures with the module's existing scratch-repo helpers in the test file, adding a merge step. Pin `GIT_CEILING_DIRECTORIES`, `HOME` and the author/committer identity the way the existing fixtures do.

### Key Files

- `plugin/bin/lib/flow/artifact-overwrite-check.js` — first-parent, non-merge event walk; the blame test treats a blamed SHA outside the run's own commits as pre-run content
- `plugin/skills/flow/multispec-artifact-namespacing.md` — raw fallback walk gains `--first-parent --no-merges`; name the first-parent scope
- `tests/bin-lib/flow/artifact-overwrite-check.test.js` — catch-up-merge fixtures (upstream-added journey, upstream lines in a run-added journey, overwrite after a merge) plus the two revert-red checks

## Gotchas

- **`--first-parent` implies `--diff-merges=first-parent`** on git 2.31 and later, which makes the merge commit itself report the upstream file changes. `--no-merges` is required alongside it. The second revert-red AC pins this.
- **Conflict-resolution edits inside a catch-up merge are no longer walked.** A merge commit's own resolution is not a spec's edit, so this is intended. Don't add `-m` or `--cc` to bring it back.
- **Blame still runs on `{commit}~1` over full history**, not first-parent. That is correct, because the deleted line's true origin is what matters. Only the run-commit membership test is first-parent.
- **Shares a file with #4593** (`artifact-overwrite-check.js` and its test file). The two are a strong near-duplicate pair, so dispatch holds the later one while the other's claim is live. Whichever lands second rebases onto the first. #4593's window attribution should read its events from the same first-parent walk.
- `bin/check-artifact-overwrite.js` needs no change. Its `--base`/`--head`/`--path` flags and exit codes stay the same.

## Original request

Artifact-overwrite check: attribute only the run's own first-parent commits

Origin: split out of #4593 at its third plan review (issuecomment-6562062652, Q7) — the maintainer chose Reading A, filing first-parent filtering as its own record

Defer-reason: tangential

## Current State

`plugin/bin/lib/flow/artifact-overwrite-check.js` walks `{EXPECTED_BASE}..HEAD` without `--first-parent`, so upstream commits brought in by a catch-up merge are part of the walk. Those commits are authored inside the run's own spec windows, so once #4593 adds manifest-window attribution they can be attributed to whichever spec's window they fall in.

The maintainer asked for this on #4593 (issuecomment-6555467984: "Filter to first-parent run commits before attributing"). #4593's third plan review (issuecomment-6562062652, Q7) kept it out of that record: the plan argued it is a different false-positive shape, since a same-window attribution can only clear a deletion whose deleting and blamed commits both fall in one spec's window.

## Deliverables

1. The overwrite walk collects A/M events with `git log --first-parent --no-merges` over the run range, so a commit reachable only through a catch-up merge's second parent is never one of the run's own events.
2. A deletion whose blamed commit is outside the run's own first-parent commits is treated as updating a pre-existing artifact, not as a cross-spec overwrite.
3. A test fixture with a catch-up merge whose upstream commit falls inside a spec window: the upstream commit is not attributed to that spec, and the test goes red when first-parent filtering is reverted.

## Acceptance Criteria

- [ ] An upstream commit merged in by a catch-up merge, authored inside spec A's window, is never reported as spec A's event.
- [ ] A run with no catch-up merge produces the same verdicts as before.
- [ ] Reverting the first-parent filter turns the new fixture red.

## Release Note

The multi-spec artifact-overwrite check no longer counts upstream commits that a catch-up merge brought in as the run's own edits.
