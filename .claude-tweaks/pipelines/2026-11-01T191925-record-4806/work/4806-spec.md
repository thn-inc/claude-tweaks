# 4806: Pass --hostname on fetch-sub-issues.js GraphQL calls for GitHub Enterprise remotes

Origin: follow-up from #4603 (PR #4678) wrap-up

Defer-reason: tangential

## Current State

`plugin/bin/fetch-sub-issues.js` resolves `{host, owner, repo}` from `--repo` or the origin remote, but only its `--resolve-retries` REST call adds `--hostname` (line 138). The `subIssues` schema probe (`probeSchemaStrict`) and the batched `fetchNativeSubIssues` GraphQL pages never pass the host, so on a GitHub Enterprise Server remote they query github.com. #4603's `plugin/bin/lib/issues/parent-gate.js` works around this for the parent gate; other callers of the fetcher inherit the gap.

Ledger row 40 of #4603's `docs/plans/2026-10-31-parent-gate-cli-ledger.md`.

## Deliverables

- [ ] The schema probe and every batched GraphQL page in `fetch-sub-issues.js` carry `--hostname {host}` right after `graphql` when the host is not github.com, per the `gh-api-module-pattern` skill's `--hostname` rule.
- [ ] Once the fetcher passes the host itself, `lib/issues/parent-gate.js`'s workaround is removed or reduced to a call through the fetcher.

## Acceptance Criteria

- [ ] A fake-runner test asserts the exact argv for a GHE host (`--repo ghe.example.com/o/r`): the probe and each page include `--hostname ghe.example.com`, and a github.com run includes none.
- [ ] The existing `fetch-sub-issues` tests pass unchanged for github.com.

## Release Note

Sub-issue lookups now work on GitHub Enterprise Server repositories instead of silently querying github.com.

## Technical Approach

### Key Files

- `plugin/bin/fetch-sub-issues.js` — pass --hostname on GraphQL calls
- `plugin/bin/lib/issues/parent-gate.js` — drop the hostname workaround
