# 2240: repo-resolve.js: parseRepo rejects non-github.com remotes, so every bin/ CLI fails on GitHub Enterprise

Surface: infra

## Current State

`plugin/bin/lib/repo-resolve.js`'s `parseRepo` hard-codes `github.com` in its regex
(`/github\.com[:/]([^/]+)\/([^/]+?)(?:\.git)?\/?$/`) and is the one shared owner/repo resolver
for `bin/` CLIs (`apply-refine-labels.js`, `backlog-grant-gate.js`, `fetch-sub-issues.js`,
`file-feedback.js`, `link-records.js`, `materialize.js`, `preflight-records.js`,
`release-claim.js`, `repair-claim.js`, `resolve-blockers.js`, `resolve-linked-prs.js`, and
others). #2021 fixed the equivalent `github.com` assumption in `_shared/pr-run-comments.md`'s
`gh` calls (by resolving `{host}` from `gh repo view --json nameWithOwner,url` and passing
`--hostname {host}`), but deliberately left `parseRepo` out of scope as "a wider gap." On a
GitHub Enterprise Server remote, `parseRepo` never matches the non-`github.com` host, so every
one of its callers reports "could not resolve owner/repo" and fails outright — the class of
CLI these callers back (materialization, claim release, blocker/linked-PR resolution, refine
labeling) is used throughout this project's own pipeline, so a GHE-hosted adopter repo cannot
run `/claude-tweaks:flow`, `/claude-tweaks:dispatch`, or `/claude-tweaks:backlog` at all.

## Deliverables

- Widen `parseRepo`'s regex to capture an arbitrary host, not only `github.com` — return
  `{host, owner, repo}` instead of `{owner, repo}`, so existing callers that only destructure
  `{owner, repo}` keep working unchanged.
- Audit `parseRepo`'s callers for which ones invoke `gh` (as opposed to only using
  `{owner, repo}` in a REST/GraphQL URL path or a display string) and, for each `gh`-invoking
  call site, pass the resolved `host` through as `--hostname {host}` (mirroring #2021's fix)
  when `host` is not `github.com`. Callers that never shell out to `gh` (or that already resolve
  the host some other way) need no change beyond the destructuring above.
- Add a regression test in `tests/bin-lib/repo-resolve.test.js` (or wherever this module's
  existing tests live) asserting `parseRepo` matches an SSH and HTTPS remote on a non-`github.com`
  host and still returns the pre-existing `{owner, repo}` shape unchanged for a `github.com`
  remote.

## Acceptance Criteria

- `parseRepo('git@ghe.example.com:acme/widget.git')` and
  `parseRepo('https://ghe.example.com/acme/widget')` both return
  `{host: 'ghe.example.com', owner: 'acme', repo: 'widget'}`.
- `parseRepo('git@github.com:acme/widget.git')` still returns `{host: 'github.com', owner:
  'acme', repo: 'widget'}` — no regression on the existing, common case.
- Every existing caller of `parseRepo` that destructures only `{owner, repo}` continues to pass
  its existing test suite unmodified — the added `host` field must not break existing shapes.
- Every caller identified as `gh`-invoking during the audit above passes `--hostname {host}`
  when `host !== 'github.com'`, and a test exercises at least one such caller against a
  non-`github.com` host (a fake/injected `gh` runner, per this codebase's
  `gh-api-module-pattern` convention) to confirm the flag is actually passed.

## Technical Approach

Widen the regex in `plugin/bin/lib/repo-resolve.js:19` to capture the host segment ahead of
`owner/repo`, e.g. `/^(?:[a-zA-Z0-9._-]+@)?([a-zA-Z0-9.-]+)[:/]([^/]+)\/([^/]+?)(?:\.git)?\/?$/`
(SSH `git@{host}:{owner}/{repo}.git` and HTTPS `https://{host}/{owner}/{repo}` both match; keep
supporting the existing bare `github.com/owner/repo` shape a caller may wrap manually). Return
`{ host: m[1], owner: m[2], repo: m[3] }`. Then grep every call site in the Key Files list below
for a direct `execFileSync('gh', ...)` or `execFileSync('git', ...)` invocation that would need
`--hostname`/`GH_HOST`, per this codebase's `gh-api-module-pattern` skill (the injectable-runner
seam and `-f`/`-F`/path-placeholder conventions for `gh api` calls) — this record's scope is the
`parseRepo` widening plus that audit and the flag-threading it turns up, not a redesign of the
call sites' own logic.

## Gotchas

- The regex must not become so permissive that it misparses a non-GitHub-shaped remote (e.g. a
  plain filesystem path or a non-forge Git host) as `{host, owner, repo}` — anchor on the
  `[host][:/]owner/repo[.git]` shape exactly as the current regex does, only generalizing the
  host segment.
- This record intentionally does not decide whether every caller needs the `host` value threaded
  through to a live `--hostname` flag — some callers may only use `{owner, repo}` for display or
  for constructing a URL where the host is irrelevant. The audit in Deliverables is scoped to
  identifying which callers actually shell out to `gh`/`git` in a way a GHE host would affect;
  don't thread `--hostname` everywhere reflexively.

## Original request

repo-resolve.js: parseRepo rejects non-github.com remotes, so every bin/ CLI fails on GitHub Enterprise

**Related:** #2021

Context: #2021 fixed the GitHub-Enterprise host resolution for `_shared/pr-run-comments.md` and `_shared/pr-early-run-lifecycle.md`'s `gh` calls, but deliberately left `bin/lib/repo-resolve.js`'s `parseRepo` untouched — its regex (`/github\.com[:/].../`) hard-codes `github.com` and is shared by twelve `bin/` CLIs (materialize, claims, release-claim, link-records, resolve-blockers, resolve-linked-prs, and others) that derive `{owner, repo}` from the checkout's `origin` remote.

Scope: On a GHE remote, every one of those twelve callers reports "could not resolve owner/repo" and fails outright, since `parseRepo` never matches a non-github.com host. Widening the regex to accept an arbitrary host (and deciding whether callers need the host value too, not just owner/repo) touches all twelve call sites' blast radius — a documentation-level fix (#2021) should not carry that.
