# 1829: wrap-up CLAUDE.md curation: an over-budget filing carries no Verified-as-of stamp, so materialize's drift check cannot catch a premise satisfied before dispatch

Surface: infra

## Current State

`materialize.js` computes `drift` only from a record's `Verified-as-of: {sha}` body-metadata line (`extractVerifiedAsOf` in `bin/lib/issues/record.js`; `computeDrift` in `plugin/bin/materialize.js`), and a stale stamp produces one stderr sentence ("premise is N commits old … re-derive facts against current HEAD before implementing") and an envelope field; it never stops or re-measures. `drift` is `null` for any record without the stamp — which is every record not filed by the four health sweeps, the only callers that thread `specShapedBody`'s `verifiedAsOf` param (`bin/harness-health.js`, `docs-health.js`, `code-health.js`, `journey-health.js` via their `issue-payload.js`). `flow/materialize.md`'s "Freshness-stamp drift (#117)" and "Named-location drift (#315)" paragraphs describe exactly this.

Wrap-up's CLAUDE.md & rules row opens on the `claudeMdOverBudget` fact (`plugin/bin/lib/wrap-up/facts.js`, `computeClaudeMdOverBudget`), which returns a bare boolean — it discards which target was over and by how much — and the row's filing (`skills/wrap-up/claude-md-curation.md` via `_shared/harness-health-analysis.md`, surfaced as a Console queue write) composes its backlog record without `verifiedAsOf`. So an over-budget record carries a measured claim ("205 lines vs the 150 budget") that no later phase can date or re-measure.

Observed on plugin 6.114.1 in a private project: the record was filed at 205 lines; two days later another record brought the file to 146; a dispatch then built the over-budget record through a full build/review cycle, with `drift: null` at materialize, `claudeMdOverBudget` already `false` at the base, and the premise discovered only at plan time. `_shared/reverify-before-write.md` states the measure-before-you-act posture for writes; nothing applies it to a record's stated premise at run start. #1769 (shaped by this sweep) adds an `ASSUMPTION — verify at build` marker for claims the composer cannot settle; this record is the complementary mechanical case, where the claim *is* a command.

## Deliverables

- [ ] **Measured fact, not a boolean.** `facts.js`: keep `claudeMdOverBudget` (boolean, read by `engine-plan.js` and `registry.js`'s gate) and add a sibling fact `claudeMdBudgetTargets: [{path, lines, budget}]` for every in-scope target, computed in the same pass. Expand-contract: no existing consumer changes; the curation row reads the new fact.
- [ ] **Stamp the filing.** `claude-md-curation.md`: the over-budget record composed by the row's queue write goes through `specShapedBody` with `verifiedAsOf` set to the sha wrap-up read the repo at (the same HEAD `wrap-up-pack.json`'s `state` probe records), a Current State line per over-budget target in the form `` `{path}`: {lines} lines vs the {budget}-line budget (`wc -l {path}` at {sha}) ``, and a new optional body-metadata line `Premise-check: {command}` whose command exits 0 while the premise still holds — for this filing, one `test $(wc -l < {path}) -gt {budget}` per target, joined with `&&` when several.
- [ ] **Materialize runs the premise check.** `record.js`: `extractPremiseCheck(body)` for the `Premise-check:` line, documented beside `VERIFIED_AS_OF_RE` as an optional single-line metadata field. `materialize.js`: when present, run it from the checkout root with the CLI's usual short timeout and add `premise: { command, exit, satisfiedAtBase }` to the envelope (`satisfiedAtBase: true` when exit is non-zero); `null` when the line is absent. On `satisfiedAtBase`, print one stderr sentence in the drift sentence's shape ("premise already satisfied at base: `{command}` exited {n}") and, under a run dir, log a `STAGED` decision (`_shared/auto-decision-log.md`) with a staged note in `staged/` proposing to close the record as already satisfied — never a silent proceed, never a hard stop from the CLI.
- [ ] **Build acts on it.** `flow/materialize.md` gains a "Premise check" paragraph beside the two drift paragraphs; `build/SKILL.md`'s Spec Step 2 (existing-progress check) reads `premise.satisfiedAtBase` from the envelope and, when true, routes to the Review Console's staged close rather than planning — the same surface an unattended run already uses for staged proposals.
- [ ] **Tests.** `tests/bin-lib/wrap-up/facts.test.js` (or the sibling that pins `computeClaudeMdOverBudget`): targets list populated with `lines`/`budget`, boolean unchanged. `tests/materialize-drift.test.js` sibling `tests/materialize-premise-check.test.js`: no line → `premise: null`; exit 0 → `satisfiedAtBase: false`; exit 1 → `true` plus the stderr sentence; a throwing runner degrades to `null`, never a crash (mirroring the drift tests' shapes). A prose pin asserting `claude-md-curation.md` names `verifiedAsOf` and `Premise-check:`, and `materialize.md` carries the paragraph.

## Acceptance Criteria

1. A wrap-up run whose CLAUDE.md exceeds its budget files a record whose body carries `Verified-as-of: {sha}`, the measured `{lines} vs {budget}` line per target, and a `Premise-check:` line; `materialize.js` on that record reports non-null `drift` and non-null `premise`.
2. `computeClaudeMdOverBudget` still returns the same boolean for every fixture in the existing facts test; `claudeMdBudgetTargets` lists each in-scope target with `lines` and `budget`.
3. `node bin/materialize.js #N` on a record whose `Premise-check:` command exits non-zero prints the "premise already satisfied at base" sentence, sets `premise.satisfiedAtBase: true`, and (with `--run-dir`) writes a `STAGED` line and a staged close note; a record with no `Premise-check:` line behaves byte-identically to today.
4. `build/SKILL.md` Spec Step 2 names `premise.satisfiedAtBase` and routes it to the Console's staged close; `flow/materialize.md` documents `Premise-check:` beside the drift paragraphs.
5. `npm test` green; every existing case in `tests/materialize-drift.test.js` and the facts tests unchanged.
6. Replaying the reported sequence in a fixture (file over budget at filing, under budget at base) ends with a staged close proposal and no plan authored; quoted in the PR description.

## Technical Approach

Two hops, both additive: the filing side gets what the health sweeps already have (a stamp) plus the one thing a mechanical premise needs (its command); the materialize side gains one optional metadata line and one optional envelope field. Do not generalize to "re-measure any Current State that looks mechanical" — the filing site knows its command, the reader should not guess one (#1769 covers the non-mechanical case with a marker). The `Premise-check:` command runs in the checkout being materialized, so it is inherently repo-local; the record composer must write only commands that need no network and no plugin path.

### Key Files

- `plugin/bin/lib/wrap-up/facts.js` — `claudeMdBudgetTargets` sibling fact beside `computeClaudeMdOverBudget`
- `plugin/skills/wrap-up/claude-md-curation.md` — over-budget filing: `verifiedAsOf`, measured line, `Premise-check:` line
- `plugin/bin/lib/issues/record.js` — `extractPremiseCheck` beside `extractVerifiedAsOf`; `specShapedBody` renders the optional line
- `plugin/bin/materialize.js` — run the check; `premise` envelope field; stderr sentence; staged close under `--run-dir`
- `plugin/skills/flow/materialize.md` — "Premise check" paragraph
- `plugin/skills/build/SKILL.md` — Spec Step 2 routing on `premise.satisfiedAtBase`
- `tests/materialize-premise-check.test.js`, `tests/bin-lib/wrap-up/facts.test.js` — new cases

## Gotchas

- `specShapedBody` enforces sha shape on `verifiedAsOf`; pass a full or 7+ hex sha, never a ref name.
- Body-metadata lines are plain lines before the first `##`, never YAML frontmatter (`materialize.md`'s own convention note); `Premise-check:` follows the same rule and must be single-line.
- The check runs an arbitrary shell command from a record body — bound it to the filing site's own composer (this plugin writes it), document that materialize runs it, and keep the timeout short; a hostile or broken command degrades to `premise: null` with a stderr note, never a crash (same posture as `computeDrift`'s throwing-runner test).
- `engine-plan.js`'s `claudeMdOverBudget` open/closed labels are pinned by tests; the boolean's name and semantics must not change.

## Original request

**Summary:** A work record filed by wrap-up's CLAUDE.md & rules row from the `claudeMdOverBudget` signal ("CLAUDE.md is 205 lines vs the 150 budget") was later dispatched after an unrelated compression had already brought the file to 146 lines; because the filing carries no `Verified-as-of` stamp, `flow/materialize.md`'s freshness-stamp and named-location drift checks read `null`, and the build phase only discovered at plan time that the acceptance criterion was already met at the branch base.

**Kind:** Gap

**Affected component:** `/claude-tweaks:wrap-up` — `skills/wrap-up/claude-md-curation.md`'s over-budget filing; `skills/flow/materialize.md` — "Freshness-stamp drift (#117)" / "Named-location drift (#315)"

**Use case:** In a private project, wrap-up's CLAUDE.md & rules row filed a record for an over-budget CLAUDE.md (measured at 205 lines). Two days later a separate record compressed the Don'ts to 146 lines. A dispatch firing then claimed and built the over-budget record: materialize's drift stamp was `null` (the filing is not produced by a health sweep, so `specShapedBody`'s `verifiedAsOf` was never set), the plugin fact check `claudeMdOverBudget` already read `false` at build time, and the pipeline still ran a full build/review cycle whose only remaining value was restructuring (a `paths:`-scoped rule) rather than the trim the record asked for. The build disclosed the drift in the PR body and a follow-up record, but nothing stopped or re-scoped the run at the point where the premise was measurable. Two possible fixes, either would do: (1) have the `claudeMdOverBudget` filing stamp `Verified-as-of: {sha}` (and the measured number) the same way the four health sweeps do, so materialize's existing drift check has something to compare; and/or (2) let materialize re-measure a record whose Current State names a mechanical check (`wc -l CLAUDE.md`, a line budget) and surface "premise already satisfied at base" as a first-class stop/decision before the build starts — the same "measure before you act" posture `_shared/reverify-before-write.md` already takes for writes.

**Definition:** Clear — the filing site and the drift check both exist; the gap is the missing stamp between them.
