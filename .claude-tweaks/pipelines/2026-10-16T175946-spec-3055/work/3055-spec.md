# 3055: Evaluate a claude-tweaks mod for Claude Code's new mod system

Surface: infra

## Current State

The original request says claude-tweaks "ships only skills/commands, never a mod". That is accurate about mods, but it understates what the plugin already hooks into:

- **Agent-loop hooks.** `plugin/hooks/hooks.json` registers SessionStart, SessionEnd, PreCompact, PreToolUse, PostToolUse and SubagentStop. All of them route through one dispatcher, `plugin/bin/hooks.js`, with one module per event under `plugin/bin/lib/hooks/`. `pre-tool-use.js`, for example, already intercepts tool calls with deny gates. The contract is in `docs/hooks.md`.
- **Custom UI.** `plugin/bin/claude-tweaks-statusline.js` renders a statusline that includes a context-window segment (`renderContext`). That is the "context/usage indicator" the original request names as an example.
- **Blast radius.** `plugin/bin/blast-radius.js` exists, but as the gather step of `assess-agent-autonomy`'s merge-check (diff size and sensitive paths at merge time). It is not a live tool-call guardrail.
- **Agents.** The plugin also ships one agent (`plugin/agents/qa-agent.md`).

So both example capabilities in the original request already have a non-mod implementation: hooks for interception, and the statusline for UI. The open question is whether mods (TypeScript functions in a plugin that hook the agent loop, intercept tool calls, draw custom UI, or add commands) do any of these better.

## Deliverables

1. A written recommendation, posted as a comment on this record, on whether and where mods fit claude-tweaks. It should cover:
   - for each candidate capability (at minimum the PreToolUse deny gates, the statusline context segment, and a live blast-radius guardrail), what a mod would add over the existing hook or statusline implementation, or a statement that it adds nothing;
   - what a mod would cost relative to today's runtime model: TypeScript versus the plugin's zero-dependency Node `bin/` modules, how mods load, and any build step;
   - whether running a mod beside the existing hook dispatcher would double-handle the same event, and how that would be avoided;
   - a clear verdict: no fit, or the one capability that should become a mod.
2. When the verdict names a capability, a working prototype mod for it. It must not double-handle any event the hook dispatcher already owns.

## Acceptance Criteria

- The recommendation comment exists on this record and addresses each of the four points in Deliverable 1, citing the files above for what already exists and the mod system's published documentation for what mods can do.
- On a no-fit verdict, no code changes land, and the comment states what would change the answer.
- On a positive verdict, the prototype mod loads in Claude Code from this plugin and demonstrably performs the chosen capability. Any hook or statusline code it supersedes is either removed in the same change or left untouched with the mod disabled by default, never both running.

## Release Note

No user-facing change unless the recommendation is positive. In that case, claude-tweaks ships its first Claude Code mod, for the capability the recommendation names.

## Technical Approach

Start with the evaluation. Read the mod system's documentation, then map each candidate onto its existing implementation: `pre-tool-use.js` for interception, `renderContext` in the statusline for UI, `blast-radius.js` for the merge-time size check. A mod is worth it only where the hook or statusline surface cannot do something the mod can, such as drawing UI beyond a statusline line, or reacting inside the agent loop where no hook event fires. Build a prototype only after that comparison names a concrete gap.

### Key Files

- `plugin/hooks/hooks.json` — existing agent-loop hook registrations a mod would sit beside
- `plugin/bin/lib/hooks/pre-tool-use.js` — existing tool-call interception (deny gates)
- `plugin/bin/claude-tweaks-statusline.js` — existing custom UI, including the context-window segment
- `plugin/bin/blast-radius.js` — existing merge-time blast-radius gather, a guardrail candidate
- `docs/hooks.md` — hook dispatcher contract, including the never-break-a-session invariant

## Gotchas

- ASSUMPTION — verify at build: mods are loaded from a plugin's payload alongside hooks, and can be shipped through the existing marketplace. Confirm via the mod system's published documentation before prototyping.
- The hook dispatcher's never-break-a-session invariant (`docs/hooks.md`) must hold for any mod too. A throwing mod in the agent loop is at least as dangerous as a throwing hook.
- `plugin/bin/` is zero-runtime-dependency Node. A TypeScript mod that needs a build step changes the payload's build model, and that is a deliberate decision, not a side effect.
- Moving a PreToolUse gate into a mod would change a shipped contract that several skills depend on. If the verdict points there, follow the expand-contract discipline in CLAUDE.md.
