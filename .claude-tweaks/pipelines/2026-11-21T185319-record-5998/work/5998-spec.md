# 5998: Read each review lens's confirmed-finding rate over this repository's last 20 runs

Surface: backend
Risk-flags: none

## Current State

Phase 10 of `docs/superpowers/specs/2026-11-18-pipeline-economy-design.md` chooses review lenses per run from the diff's facts and "each lens's confirmed-finding rate in this repository over its last 20 runs." No code computes that rate today.

- `plugin/bin/lib/timing/step-yield.js` writes `step-yield.json` per run with `steps[].findings.byLens.<lens>.{raised,both,one,relabeled,tiebreak.byVerdict.*}` (`docs/reference/step-yield.md`). A lens gets a `byLens` entry only when a pair line or tiebreak line names it (`eachFindingScope`), so **a lens that was dispatched and found nothing leaves no trace there**. The rate's denominator (runs in which the lens ran) is not in the yield file.
- `tools/step-yield-report.js` totals the yield across an archive, including a per-lens table. It is a maintainer tool under `tools/`, which does not ship (`docs/decisions/0015-*`), so a shipped selector cannot require it.
- `timing.json`'s `dispatches.items[]` lists each agent with a free-text `description`, `tier` and tokens. Lens agents are identifiable there only through the description the session typed.
- Design evidence (2026-11-08 to 18): 96 runs, 799 confirmed findings, 8.3 per run; lenses 3a and 3f (Haiku) produced 443; 3b and 3d produced 36 and 19 and return nothing over 70% of the time.

## Deliverables

1. A shipped module (proposed `plugin/bin/lib/review-lens/history.js`) that, given the pipelines root(s), returns per lens over the most recent N closed runs **in which that lens ran** (N default 20; "closed" = a run directory holding a readable `step-yield.json`; qualifying runs are filtered first, then the newest N are taken): runs counted, confirmed findings (`both` plus tiebreak `confirmed`, per `docs/reference/step-yield.md`), confirmed findings per run, and the share of runs with at least one confirmed finding. "Most recent" uses the run id's start time, as `tools/step-yield-report.js`'s `recent` rule does; a run whose id has no parseable start time is skipped and listed in the result, never silently dropped. The result shape is `{ lenses: { "<lens>": { runs, confirmed, perRun, shareWithFinding, insufficient } }, skipped: [{path, reason}], errors: [{path, reason}] }`. Lens ids are the Step 3 ids (3a to 3h), the same strings as `byLens` keys and as `lens-dispatch.json`'s `lens` values; both files carry a `v: 1` schema field.
2. A per-run record of which lenses were dispatched: a file the review step writes into the run directory (proposed `lens-dispatch.json`: one entry per lens per review round, `{lens, reviewers: 1|2, path: task|workflow, round}`, a lens dispatched in several rounds counting as one qualifying run), written through one sanctioned run-directory writer the build chooses and names in the module header. History reads it as the denominator. Runs without `lens-dispatch.json` do not count for any lens: there is no legacy derivation from decision lines or `timing.json` descriptions. Until a lens has 20 qualifying runs it reads `insufficient` and the selector runs every tier lens. This warm-up is intended. `lens-dispatch.json` is written on every dispatch path whatever `review-lens-selection` says, so history builds up before anyone opts in.
3. A result that says plainly when a lens has fewer than N qualifying runs (`insufficient: true` with the count), so the selector can fail toward running the lens.
4. `tools/step-yield-report.js` reuses the shipped per-lens confirmed count instead of keeping its own copy, if the two would otherwise compute the same number.

## Acceptance Criteria

- [ ] Over a fixture archive where lens 3d ran in 25 runs and found confirmed findings in 5, the module reports 20 qualifying runs (the most recent 20), and the confirmed count and share computed over those 20.
- [ ] A run where a lens was dispatched (per `lens-dispatch.json`) and produced no finding line counts as a qualifying run with 0 confirmed findings; a run with no dispatch evidence for that lens does not count at all. Each `lens-dispatch.json` entry also records the lens's completion status (`completed` | `failed` | `blocked`). A failed or BLOCKED dispatch is not a qualifying run, and a `reviewers: 1` dispatch is excluded from the rate because it cannot produce `both`.
- [ ] A run that is not closed (no `step-yield.json` and no `run-state.json` with status `clean`, or a live owner) is ignored and listed in `skipped` with reason `run not closed`; it is never an `errors` entry. Only a closed run (clean `run-state.json`) whose `step-yield.json` is missing or malformed is excluded from the count and listed in `errors`. Neither is ever counted as 0 confirmed findings.
- [ ] A multi-spec parent run in which more than one `spec-N` member dispatched the same lens is excluded for that lens and listed in `skipped` with reason `multi-member dispatch`; a parent in which exactly one member dispatched the lens counts once, with the parent's `byLens` yield.
- [ ] A lens with 7 qualifying runs is reported `insufficient: true` with `runs: 7`.
- [ ] An unreadable root or a malformed `step-yield.json` is reported as such, never silently read as an empty archive (`parse-signal-discipline`).
- [ ] A relabeled finding counts for the lens `step-yield.json` credits (`relabeled` is read as `docs/reference/step-yield.md` defines it), and a fixture row pins it.
- [ ] The review step writes `lens-dispatch.json` on both the Task and the workflow dispatch paths (`plugin/skills/review/step3-lens-dispatch.md`, `step3-workflow-dispatch.md`), through a CLI, not a hand-typed file.

## Gotchas

- `step3-lens-dispatch.md` sits at 48,911 B, above the 47,250 B headroom line: put any new prose in a sub-file and add one pointer line.
- Expand-contract: older runs have no `lens-dispatch.json`; the reader must work on an archive that mixes both.
- Archived run directories sort lexically by id; a glob sorted by name puts `2026-08-20…record-590` after `…record-5770`. Order by parsed start time.

## Decision Rationale

- **Why a dispatch record and not the yield file alone.** The yield file has no entry for a lens that ran and found nothing, so a rate read from it alone would overstate every lens and never let 3b or 3d look idle.
- **Why fail toward running.** Fewer than 20 qualifying runs is too little to skip a lens on; a skipped lens that would have found something leaves no trace.

## Plan Review Clarifications

- Settled by plan review after an answered round: "The plan's closed rule differs from AC3's literal 'live owner' clause in two ways. (1) A `clean` run counts as closed even while its owner session is live, and a session usually stays live after its run closes clean. (2) A run that is not `clean` but has a yield is treated as not closed when liveness is `unknown`, though AC3 names only a live owner." Chose Reading A, AC3 as written: a run is not closed when it has no `step-yield.json` and no `run-state.json` with status `clean`, or when its owner is live (`runLiveness` verdict `live`), a `clean` run included; an `unknown` or `dead` owner leaves the run closed. Not Reading B (a `clean` run closed whatever its owner says; a non-`clean` run with a yield closed only on `dead`), which would have amended AC3.
- Settled by plan review after an answered round: "Step 2 drops a run with no `lens-dispatch.json` before step 5 reads its yield. So a closed run whose `step-yield.json` is malformed, but which has no dispatch evidence, is never reported." Chose Reading A, AC6 as written: a malformed `step-yield.json` in a closed run is an `errors` entry whether or not the run has dispatch evidence; a missing yield in a run with no dispatch evidence adds no entry. Not Reading B (read the yield only for runs with dispatch evidence), which would have amended AC6.
