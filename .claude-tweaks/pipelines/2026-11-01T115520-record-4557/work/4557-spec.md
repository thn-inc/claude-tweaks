# 4557: build: a fixed wait budget abandoned a live implementer seconds before it committed, costing a full handoff

Surface: infra

**Related:** #3758, #4030, #4549, #4559, #4589, #3706, #3822, #3835, #3875, #4358, #4363, #4548

## Current State

During a `/flow #N build,test,review,polish auto` run, the build controller dispatched an implementer for a multi-file task (four files plus tests) and waited on it with a fixed 60 x `sleep 20` budget (20 minutes). At the bound it stopped with `STATUS: BLOCKED`, citing the rule that a file-editing child must not be redone in-session. The implementer was healthy and committed its task seconds later. Cost: one false BLOCKED stop, a fresh-agent resume of about 1.7 h wall clock, and the run's third and last allowed context handoff.

The original report could not locate the fixed budget's source. It is the plugin's own contract, not an improvised loop:

- `plugin/skills/_shared/subagent-dispatch-core.md:70` (Foreground Execution Discipline, "Nested `Agent` children"): a dispatched agent keeps its turn alive with "repeated `sleep 20` Bash calls, at most 60 (20 minutes) per wave of children", and never reads or tails a running child's `output_file` (`:74`).
- `plugin/skills/_shared/subagent-dispatch-core.md:96-98`: "a write-capable child (one that edits files) still silent at the bound is never redone in-session ... stop, and end with `STATUS: BLOCKED`". "Silent" means only that no `<task-notification>` has arrived — nothing checks whether the child is still making progress.
- The same primitive and stop rule are restated in the prompts handed to dispatched agents: `plugin/skills/dispatch/task-prompt.md` (item 7 at `:48`/`:65`, first-call template `:153`/`:167`, second-call template `:329`/`:343`), `plugin/skills/dispatch/express-prompt.md` (`:38`/`:52`, `:121`/`:135`), and `plugin/skills/flow/context-handoff.md`'s handoff-child template (`:81`/`:98`).
- `plugin/skills/flow/context-handoff.md:52` already says a top-level session waits on its child with no bound because "a child phase often runs past 20 minutes" — but a handoff child is itself a subagent, so it inherits the 20-minute bound for its own nested implementer dispatches. A handoff-continued build therefore hits it.
- `tests/foreground-execution-instruction.test.js:375-398` pins the primitive (`sleep 20`, at most 60, 20 minutes) to appear exactly once in four copies (core section, task-prompt item 7, both task-prompt call templates); `:138` pins the write-capable never-redone clause; `tests/flow-context-handoff-conformance.test.js:115` pins the handoff template's copy.

Never-redo-in-session is itself correct — an abandoned child keeps running and may still write. The defect is that the stop fires on elapsed time alone, against a write-capable child that is visibly working.

## Deliverables

1. **Progress check at the bound for write-capable children**, in `subagent-dispatch-core.md`'s Foreground Execution Discipline. When the 60-wait bound expires with a write-capable child still outstanding, probe the child's working tree read-only — the worktree path the dispatcher already passed under Working Directory Discipline — with `git -C {worktree} rev-parse HEAD` and `git -C {worktree} --no-optional-locks status --porcelain`, compared against the same probe taken right after the wave launched (and at each later bound). If either value changed, the child is progressing: log one line and grant one further window of the same primitive. Stop with `STATUS: BLOCKED` only when a whole window passes with no change in either value, or when a hard ceiling of 3 windows (60 minutes) per wave is reached; the BLOCKED report names which condition fired (`no progress for one window` or `ceiling reached while progressing`).
   - The probe never reads the child's `output_file` (the existing rule stands) and never writes.
   - Read-only children (a lens, a single read, a judge) keep today's behavior: self-judged at the first bound. The extension applies to write-capable children only.
   - Never-redo-in-session is unchanged on every branch.
2. **Every restated copy updated in the same change**: `dispatch/task-prompt.md` (item 7 and both call templates), `dispatch/express-prompt.md` (both copies), and `flow/context-handoff.md`'s handoff-child template each carry the progress-check extension, worded consistently with the core section. The base primitive (`sleep 20`, at most 60, 20 minutes) stays stated exactly once per copy, so `primitiveCopies`' agreement check keeps its meaning.
3. **Conformance tests**: extend `tests/foreground-execution-instruction.test.js` (and `tests/flow-context-handoff-conformance.test.js` for the template copy) so every copy is asserted to state the progress probe, the one-window-without-change stall condition, and the 3-window ceiling — each new assertion with a discrimination proof that goes red when the clause is removed from any single copy, following the file's existing pattern (`:400`).

## Release Note

Keep waiting on a dispatched implementer that is still committing or changing files at the 20-minute wait bound, instead of stopping the build as blocked — up to 60 minutes, then stop as before.

## Technical Approach

A prose change to the shared contract and its restated copies; no `bin/` code. The probe is two read-only git commands the waiting agent can already run, recorded in the per-wait log line it already writes (the bounded-polling paragraph, `subagent-dispatch-core.md:107`). Take the baseline probe right after the wave launches so the first bound has something to compare against. Keep the base primitive's wording byte-identical in every copy so the existing `PRIMITIVE` regex count holds, and add the extension as a separate sentence that the new assertions match.

The probe reads the child's worktree, which the dispatcher already knows (task prompts pass it per Working Directory Discipline). When a child's worktree is unknown, there is nothing to probe and the existing stop applies.

## Gotchas

- A child running a long test suite can go several minutes with no HEAD or file change; a full 20-minute window with zero change is the stall signal, which a suite run does not normally reach. A child that writes only outside its worktree shows no progress and falls back to today's stop — acceptable.
- A probe that fails (lock contention, a refused command) counts as "no observed change" for that probe, never as progress, and is never retried in another form — the existing wait-call failure rule.
- Byte-pinned prose: `tests/foreground-execution-instruction.test.js` requires the base primitive exactly once per copy — the extension's wording must not restate `sleep 20` ... `at most 60 (20 minutes)`.
- ASSUMPTION — verify at build: the controller that stopped in the reported run was a handoff child (a subagent) waiting on a nested implementer, so the subagent bound applied — confirm via the report's "handoff 3 of 3" against `flow/context-handoff.md:52`'s top-level-unbounded rule; if a top-level session was the one that stopped, `_shared/dispatch-waiting.md` also needs to forbid a fixed poll budget at top level.
