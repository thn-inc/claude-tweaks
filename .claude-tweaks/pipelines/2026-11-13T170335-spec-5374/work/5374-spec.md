# 5374: Add the in-process CLI test helper and entry contract, and convert resolve-policy.js

Surface: backend
Risk-flags: none

## Overview

The test suite starts a fresh node for almost every call to a `plugin/bin` CLI. One full run on main @ 79cd5710d (2026-11-13) started 6,130 node processes, 2,902 of them `plugin/bin` CLIs, and a node start costs 36–52 ms on the measuring machine. Calling the CLI's entry function inside the test process costs microseconds.

This record lays the foundation the rest of the series builds on: the shared test helper that calls a CLI in-process and catches leaked process state, the written entry contract, a conformance test that only lets the list of non-conforming CLIs shrink, and a tool that counts node processes per test file. It proves all four on `resolve-policy.js`, which tests spawn 243 times per run.

**Complexity:** High
**Estimated tasks:** 8

## Technical Approach

Extend the existing `run(argv, deps)` contract; do not add a second entry name. The contract every CLI in this series meets:

- The CLI exports `run(argv, deps)` and `realDeps`. `argv` is `process.argv.slice(2)`. `run` returns an integer exit code, or a Promise of one when the CLI is async.
- The script entry is the last statement of the file: `if (require.main === module) process.exitCode = run(process.argv.slice(2), realDeps);` (async: `run(…).then((code) => { process.exitCode = code; })`).
- The CLI reaches the outside world only through `deps`. Standard io keys, each present only when the CLI uses it: `stdout(text)`, `stderr(text)`, `cwd()` (returns a string), `env` (a plain object, read-only), `stdin()` (returns the whole input as a string), `homeDir()` (returns the user's home directory; real value `() => os.homedir()`). Other seams (`runner`, `now`, `mainRoot`, …) keep their names.
- Above the guarded entry, and in everything `run` calls: no `process.exitCode`, no `process.exit()`, no `process.chdir()`, no write to `process.env`.
- A relative path is resolved against `deps.cwd()`, never left to `path.resolve` or `fs`, which use the real working directory.
- Every child process is started with `cwd: deps.cwd()` and `env: deps.env`. A child started without them inherits the test runner's working directory and environment, so a `gh` or `git` stub on an injected `PATH` is skipped and the real tool runs.

A CLI that already exports `main(argv)` gains `run` and keeps `main` exported while any caller imports it. Removal condition for a kept `main`: no file under `plugin/`, `tests/`, `tools/`, `perf/` or `evals/` imports it.

`hooks.js` is the one standing exception to two rules: its script entry calls `process.exit(code)`, and it has a require-time prefilter block that runs only when it is the entry script. The conformance test names that exception with its reason.

### Data / API Surface

`tests/helpers/run-cli.js`:

- `runCli(cliPath, argv, { env = {}, cwd = process.cwd(), stdin = '', deps = {}, fresh = false } = {})` → `Promise<{ code, stdout, stderr }>`. It requires `cliPath`, builds `{ stdout: collect, stderr: collect, cwd: () => cwd, env: Object.freeze({ ...env }), stdin: () => stdin }`, merges `{ ...cli.realDeps, ...thoseFakes, ...deps }`, and awaits `cli.run(argv, merged)`. `env` is the complete environment the CLI sees; a test that wants the ambient one passes `{ ...process.env, X: '1' }`.
- The fakes also carry `homeDir: () => env.HOME || env.USERPROFILE`, throwing when neither is set. `runCli` refuses a CLI that exports no `realDeps`, with a message naming this contract, so every converted CLI exposes its real seams to the fail-closed rule below.
- Fail-closed runners: after the merge, a key named `runner`, `gh` or `spawn` that still holds the CLI's real value is replaced by a function that throws `runCli: real <key> reached — pass a fake in deps or allowRealRunner: true`.
- Leak guard, around every `runCli` call: record `process.exitCode`, `process.cwd()`, a shallow copy of `process.env`, and `process.listenerCount` for `exit`, `SIGINT`, `SIGTERM`, `SIGHUP` and `uncaughtException`; replace `process.stdout.write`, `process.stderr.write` and `os.homedir` with recorders for the duration of the call; restore them in a `finally`; then reject with one error that names every difference (an `os.homedir()` call counts only when `env.HOME` or `env.USERPROFILE` was injected with a value other than the real one). The recorders exist to fail the test. Output is captured only through the `stdout`/`stderr` deps. `runCli` throws when called while another `runCli` call is still pending, because the guard's snapshots are not sound under overlap.
- `fresh: true` deletes every `require.cache` key under `plugin/bin` before requiring the CLI.
- `spawnCli(cliPath, argv, { env = process.env, cwd, stdin } = {})` → `{ code, stdout, stderr }` from `spawnSync(process.execPath, [cliPath, ...argv], { encoding: 'utf8', windowsHide: true, … })`.

`plugin/bin/resolve-policy.js`:

- `resolvePolicy({ keys, runDir, mcpReachable }, deps)` → `{ code: 0, result, invalidRaw, degrades }` or `{ code: 1, message }`. `deps` keys: `cwd`, `env` (a plain object), `git(args, { cwd, env })`, `readFile(path)`. The core hands `deps.cwd()` and `deps.env` to `computeDerivedDefaults`, which hands them to `detectIntegrationModel` as `opts.env` (the repository root it takes is derived from `deps.cwd()`).
- `run(argv, deps)` → `0` or `1`. It keeps today's flag parsing, messages and output modes (`--values`, `--all`, default JSON).
- `realDeps = { cwd: () => process.cwd(), env: process.env, git, readFile, stdout: (s) => process.stdout.write(s), stderr: (s) => process.stderr.write(s) }`, where `git(args, { cwd, env })` runs real git with the `cwd` and `env` the core passes it (always `deps.cwd()` and `deps.env`), so a test that injects either reaches the child. `git` is not on the fail-closed list: it runs real git against the injected `cwd` and `env`, which is the behaviour under test.

`tools/count-node-procs.js [--files-from <list>] [--json <out>]`: runs `tools/run-tests.js` with `NODE_OPTIONS=--require <preload>` and `CT_COUNT_NODE_LOG=<file>`; the preload appends one JSON line per node process (`pid`, `ppid`, `t`, `argv.slice(1, 6)`, `execArgv.slice(0, 3)`) and never throws. The tool attributes each process to the test file at the top of its parent chain and prints the table. A process whose script is a test file is a test-file process, and one whose script is under `plugin/bin` is a CLI process named by its file. The preload also appends one JSON line at each process's `exit` (`pid`, `t`), and a test file's wall time is the time from its first start line to its last exit line. `--json <out>` writes one object per test file with `file`, `nodeProcs`, `cliProcs` (an object keyed by CLI) and `wallMs`.

`tests/bin-lib/cli-entry-conformance.test.js`: for every `plugin/bin/*.js`, assert, reading each file as text and never requiring it, (1) `module.exports` includes `run`, (2) the file has `require.main === module`, (3) `process.exitCode` and `process.exit(` appear only from the guard line to the end of the file. `NOT_YET` starts as the files that fail at this record's base commit, minus `resolve-policy.js`: `blast-radius.js`, `calibration-report.js`, `claude-tweaks-statusline.js`, `code-health.js`, `compose-subject.js`, `declined-learning.js`, `design-detect.js`, `docs-health.js`, `harness-health.js`, `hooks.js`, `init-verify-scope.js`, `install-statusline-wrapper.js`, `journey-health.js`, `phase-timing.js`, `plan-audit.js`, `reachability-audit.js`, `record-graph.js`, `release-bootstrap.js`, `release-notes-publish.js`, `residue.js`, `resolve-profile.js`, `session-tmp-resolve.js`, `sweep-stray-run-dirs.js`, `verify.js`, `visual-decide.js`, `wrap-up-engine.js`, `wrap-up-state.js` (27). Measured at the base commit with a text scan of all 122 files: 28 files export no `run`, 11 have no guard, and every file that names `process.exitCode` or `process.exit(` above its guard is already among the 28, so no file that exports `run` fails rule 3 and the list holds exactly 27 once `resolve-policy.js` is converted. `hooks.js` stays on the list until #5377 replaces its entry with a named `EXEMPT` entry in the test, with its reason, kept apart from `NOT_YET`; the list itself only shrinks.

## Gotchas

- `resolve-policy.js` is the one CLI every skill calls. Its stdout, stderr and exit code are a public contract: byte-identical output for every case in AC 5.
- `gitRoot()` runs git with no `cwd`, so today it resolves the project from the process working directory. In-process the test runner's working directory is the repo checkout, not the fixture: pass `cwd: deps.cwd()` to that `execFileSync`, or every in-process test resolves this repo's own `policy.yml`.
- Six shipped modules spawn `resolve-policy.js` and parse its stdout (`lib/wrap-up/facts.js`, `lib/phase-exit/phase-exit.js`, `lib/dispatch/queue-pull.js`, `dispatch-prompt.js`, `calibration-report.js`, `release-tip-check.js`). They keep working unchanged, because the script entry is unchanged. Moving them onto the core is #5384.
- `--values` mode writes its warnings to stderr and still exits 0. Keep that: the leak guard must not treat a `deps.stderr` write as a leak.
- `computeDerivedDefaults` runs forge detection for `integration-model` and `merge-verification`, and `detectIntegrationModel(repoRoot, opts)` (`plugin/bin/lib/policy-schema.js:846`) starts `git` (line 852) and `gh` (line 865) with no `env` option today. Tests that ask for those keys stub `gh` on `PATH` through `env`; in-process the stub is skipped and the real `gh` runs unless the probe receives the injected `env`. The same function is called from `plugin/bin/lib/reconcile/index.js`, `plugin/bin/lib/merge-verification.js`, `plugin/bin/lib/hooks/pre-tool-use.js` and others: add `env` to its `opts` with the inherited environment as the default, so those callers do not change.
- `resolveForgeProbeTimeoutMs` (`plugin/bin/lib/policy-schema.js:788`), which `detectIntegrationModel` calls for its `gh` bound, also reads `process.env.CLAUDE_TWEAKS_GH_TIMEOUT_MS` directly (an explicit positive-integer `opts.timeoutMs` returns before that read). Take it from the same injected `env` (default: the inherited environment), or an in-process test that sets that variable through `env` is silently ignored.
- 11 files under `plugin/bin` call `os.homedir()`. None is on `resolve-policy.js`'s path, but the helper's `homeDir` fake and `os.homedir` recorder are what keep a later conversion from writing into the real home directory.
- Build the tool's `NODE_OPTIONS` value with `tools/test-impact/node-options.js`, which already quotes a preload path for a checkout path containing a space, and append to an existing `NODE_OPTIONS` instead of replacing it. `tools/test-impact/tracer.js` is an existing preload of the same kind to model the new one on.
- The preload must not break the process it counts: wrap its whole body in `try { … } catch {}`. Some tests assert on an empty stderr.
- #5319 (in progress) makes a plain local `npm test` run only an impact-selected subset. The tool's no-argument form must run the whole root set, as CI does, so a before/after pair is never two different subsets.
- Write the `NOT_YET` list one file per line in sorted order. Twelve sibling records each delete their own lines from it, and one entry per line lets those deletions merge without conflicts.
- `docs/plugin-structure.md` and `plugin/bin/lib/policy-schema.js` are edited by several records in progress (#5319, #5230, #5229, #5291, #5222). Keep the edits to one added table row and one added `opts` key, and rebase before the final verify run.
- The counts are a floor: a test that spawns with a replaced `env` drops `NODE_OPTIONS`, so its children are not logged. Say so in the tool's output header.
- Windows: `spawnCli` passes `windowsHide: true`; the conformance scan must read files with CRLF line endings the same way (see `.claude/skills/windows-checkout-test-parity`).
- `tests/bin-lib/exit-code-conformance.test.js` and other source-scan suites read `plugin/bin` files as text. Run the full suite before pushing.
- The leak guard reports writes and mutations, never reads. For `resolve-policy.js` the audited ambient reads are the `git` call in `gitRoot()` and the two `process.env` reads on the forge-probe path named above; a read the audit missed is found only by an in-process test that injects a different `cwd` or `env`, and `cli-entry-conformance` scans only the top-level `plugin/bin/*.js` files, not `plugin/bin/lib`.
- `runCli` defaults to `env = {}`: a CLI that starts `git` or `gh` needs `PATH` (and `SystemRoot` on Windows) in the `env` a test passes, or the failure reads as "git not found" and not as a CLI defect. The parity test in AC 4 and every converted test pass an explicit `env`.
- Module-level state in the `resolve-policy.js` closure (for example the forge probe's memos) survives between in-process calls in one file. Give each case that depends on it `fresh: true`, and include one test that runs two different fixture repos back to back in one process and gets each repo's own answer.

## Decision Rationale

Three approaches were weighed. (A) A new uniform `main(argv, { env, cwd, stdin, stdout, stderr })` on every CLI, as first requested: 94 CLIs already export `run(argv, deps)` with function-valued `stdout`/`stderr`/`cwd`, shipped modules import `run`, and the contract file documents it, so this meant either a second entry beside `run` on every CLI or a rename across 94 files, for no measured saving (those CLIs are 14% of the spawned processes). (B) Patching `process.stdout`, `process.argv`, `process.env` and the working directory in the test helper, with no CLI change: it makes the leak the mechanism, cannot intercept `fs.writeSync(1, …)`, runs the 11 unguarded CLIs at require time, and breaks for async CLIs. (C) Extending the existing `run(argv, deps)` contract with five standard io keys, chosen: the same five io concerns and the same return value as (A), in the vocabulary the repo already uses. Expected result for the whole series: about 2,000 fewer node processes per suite run, roughly 90 CPU-seconds at 45 ms each, which is a single-digit percentage of suite wall time on an idle machine and more under load.
