# 3976: Archive the spec header on the run branch before merge (#3855 option a)

Surface: infra

**Related:** #3396 (removes the cause of new unpushed reconcile archive commits; still clears today's divergence), #3813, #3812, #3866 (same wrap-up and pr-first-merge sequencing area; note the file overlap), #3855 (superseded by this project)

## Overview

Under pr-first, a run's materialized header (`.claude-tweaks/pipelines/{run-id}/work/{N}-spec.md`) is committed on the run branch and lands on `main` with the squash merge, at the live run-dir path. Reconcile then archives the run's gitignored half, and the tracked `work/` file is moved only by a later `[reconcile] archive run` commit on the main checkout. For most runs that commit never happens: on 2026-10-22, 258 of 264 tracked live run directories on `origin/main` already had an archive twin, and the `[reconcile] archive run` commits that do happen leave local `main` ahead of origin (#3396), so a fresh worktree branched from that diverged `main` the same day. #3855 asks where the move should happen.

This record implements #3855's option (a), chosen as the project's cutover: wrap-up `git mv`s the header from `work/` (and `spec-{N}/work/`) to `.claude-tweaks/pipelines/archive/{run-id}/...` as the last commit on the run branch, before the merge. The squash then lands it already archived, so a merged pr-first run leaves no live tracked directory on `main` and needs no post-merge `[reconcile] archive run` commit. local-merge projects do the same move before the local merge, with the existing post-merge `archiveRunDir` commit kept only as a fallback for a run merged without it. The same change narrows `.gitignore`'s `work/**` un-ignore to spec headers, so ad hoc agent files stop being committed.

## Release Note

Changed pr-first wrap-up to archive a run's spec header on the run branch before merge, so merged runs no longer leave a stale header in the live pipelines directory.

## Technical Approach

The move is one `git mv` pair per header directory, committed with an explicit pathspec (never the whole index), pushed on the run branch, then the merge proceeds. The move relocates the whole tracked `work/` directory so the live tree is left with nothing tracked; ignored or untracked files stay behind and are archived by the existing gitignored-half move. Because it follows every live-path reader, the readers needing the live path have already finished; resumed runs and later readers go through the shared resolver from the reader record.

The candidate seam is the common pr-first merge procedure, since `_shared/pr-first-merge.md` is the one place all five merge sites share; the move belongs before its Step 2 (mark ready) so the PR a reviewer sees already carries the final tree. local-merge projects keep their own sequencing in `pr-first-merge-appendix.md` and `wrap-up/merge-mode.md`.

### Data / API Surface

No new CLI surface is required if the move is expressed as wrap-up procedure steps using `git mv`; if the builder extracts it into a helper (for example next to `archiveRunDir`'s `workMoves` logic in `archive-merged.js`), it is called with a run directory and a worktree and returns the commit it made or a refusal reason.

## Gotchas

- ASSUMPTION — verify at build: the run's worktree is reachable from every pr-first merge site. `_shared/pr-first-merge.md` removed the checkout requirement ("`gh pr merge` needs no local checkout"), but a `git mv` commit on the run branch needs one. Check each of the five callers listed under Current State for where the worktree is available, and place the move where it is (wrap-up Phase 4 execution runs inside the run's worktree).
- Order matters twice: after every live-path reader (pack, first-call check, bookends), and before the merge. The wrap-up pack is consumed in Phase 3, the Review Console and execution are Phase 4.
- File overlap with open records in this exact sequencing area: #3813 (Phase 4's execution-step commit and push still run after the pr-first merge), #3812 (keep a run's ledger off `main` when its PR merged outside the run's own teardown), #3866 (pr-first-merge Step 4.2 logs to the run dir after reconcile archived it), #3877 (acceptance labeling guard in the same merge procedure), #3847 and #3731 and #3646 (edit `cleanup-procedures-execution.md`). Rebase on `main` before opening the PR and re-read the neighbouring steps; do not assume the Phase 4 order stated above still holds.
- A commit made after `close-run`/`archive-run` cannot read the run directory it just archived. Run the header move before the gitignored half is archived, and never re-read `run-state.json` from the live path afterwards (the Phase 1 verdict is carried as a run-scoped fact for the same reason).
- Commit the move with an explicit pathspec. `archiveRunDir`'s commit hazard (an empty pathspec commits the whole staged index) is fixed in #3975; do not copy that call shape.
- Release gate: this record ships in the same release as #3974 or a later one, never an earlier one. An installed older build that reads a repository whose runs are already archived on their branches sees a run mid-flight across such an upgrade as unmaterialized; that is the expand-contract window, and it is why the reader record merges first and ships first.
- The ordering test is only as good as its anchors: if a neighbouring record renames the step or heading the test looks for, update the anchor in the same change rather than loosening the test.
- Related: #3396 removes the cause of new unpushed reconcile archive commits but still has to clear today's divergence.
- Changing `.gitignore` here does not untrack the existing ad hoc files; the housekeeping PR in #3975 handles stranded directories, and consumer projects with an older, broader un-ignore keep working (it only keeps committing more files), so no migration is required.
- The `.gitignore` template is shipped to consumers through `/init`; `tests/init-port-isolation-conformance.test.js` and `tests/feedback-watermark-prose.test.js` read that bootstrap step, so run both after editing it.
