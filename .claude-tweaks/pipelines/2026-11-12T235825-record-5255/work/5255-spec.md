# 5255: Decide how a dispatch first call whose prompt never dispatched is counted and stopped across firings

Surface: infra

**Related:** #4589, #5091, #3758, #3835, #3963, #4004, #4252, #4300, #4345, #4663, #4735, #4850, #4937, #4961, #5219, #5228, #3706, #5067

## Current State

When `dispatch-prompt.js` exits non-zero for a call, or the prompt hook denies that call's one unchanged resend, the call is never dispatched (`plugin/skills/dispatch/two-call-gate.md` section 2, "A prompt that does not render, or is denied twice (#4589)"). Dispatch logs one `REFUSED` line (`Prompt render failed: exit {code}: {stderr}` or `Prompt denied twice: {reason}`), routes a first call to section 5's `cleanup-only` teardown with `(prompt-not-dispatched: skip the claim release)` and a second call to section 6, and then "The firing goes on to the next group" (section 5's "Prompt not dispatched (#4589)" paragraph).

For a first call that never dispatched, Settle never runs: it runs inside the call (`plugin/skills/dispatch/settle-and-merge.md`, "never in dispatch's main thread"). So no retry is counted, no failure comment is posted and no label changes. `plugin/skills/dispatch/firing-exclusion.md` keeps the group out of the rest of the same firing only. A later firing re-ranks the same record, fails the same way, and the only evidence is one more `REFUSED` line in `decisions.md`.

The two failures have different causes:

- **Render failure (CLI exit non-zero).** The CLI's inputs are nearly all firing-wide: `task-prompt.md`'s template, the resolved policy values, the model profile, the `--run` guard and the session temp path. When one of them breaks, every later group in the firing fails the same way. A per-record cause is possible but rare; the render's only per-record inputs are the issue numbers, the step token and a resume PR URL.
- **Denied twice (hook).** The model resent a prompt that differs from the file the CLI wrote. That is a fault in that one call, not in the firing or the record.

The Claim permission stop (`plugin/skills/dispatch/SKILL.md`, "Claim permission stop (#4899)") is the existing precedent for a firing-wide cause. It stops the firing in every selection form, and `plugin/skills/dispatch/reporting.md` relays it to the human.

Decision (made at `/claude-tweaks:specify` on 2026-11-12; the user skipped the questions and accepted the agent's call): a render failure ends the firing, the same way the Claim permission stop does. A denied-twice call keeps today's behavior and ends that group only. Per-record retry counting for never-dispatched calls was not chosen: it would need Settle logic in dispatch's main thread for a cause that is almost never the record's.

## Gotchas

- A render failure that is really per-record (a malformed resume PR URL, say) stops every firing at that record until a human acts, because the ranking picks it first each time. That is accepted: the cause is rare, and the relay plus the headless notification make it visible at once, unlike today's silent re-selection.
- The express-lane prompt is not rendered by `dispatch-prompt.js` yet (#4735). When #4735 lands, its render failure should take this same stop; that record's own work covers it.
- #5091 adds a blocker-landing relay to the same `reporting.md` block of sibling relays. Whichever lands second takes a rebase there, not a conflict in meaning.
- A second call's render failure follows section 6, whose `cleanup-only` call releases the claim the first call took. Only the firing-stop is new on that path.

## Current State

When `dispatch-prompt.js` exits non-zero for a first call, or the prompt hook denies its one resend, the call is never dispatched and takes the terminal path (`plugin/skills/dispatch/two-call-gate.md:9` and section 5 at line 47, `(prompt-not-dispatched: skip the claim release)`). Settle runs inside the call (`plugin/skills/dispatch/settle-and-merge.md:33`, 'never in dispatch's main thread'), so it never runs: step 4's retry counting (line 145), the failure comment and the labels never happen. `plugin/skills/dispatch/firing-exclusion.md:13-26` excludes the group only for the same firing, so a persistent render failure (nearly always firing-wide: template, policy or env) re-selects the record on every later firing, leaving a REFUSED `decisions.md` line as the only evidence. By contrast the Claim permission stop (`plugin/skills/dispatch/SKILL.md:60`) ends the firing outright.

## Deliverables

Record the decision, then implement it: (1) stop the firing on a render failure, like the Claim permission stop; or (2) count per-record retries for never-dispatched calls in Settle's step-4 accounting, with the failure comment and labels. Update `two-call-gate.md`, `settle-and-merge.md`, `firing-exclusion.md` and `SKILL.md` to match.

Stop the whole firing on a render failure (cheap, matches the firing-wide cause, but one bad record could halt others if the cause is per-record), or count per-record retries for never-dispatched calls (bounded, labelled, but needs Settle logic outside the call)?
