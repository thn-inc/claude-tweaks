# 3945: Add the tiebreak verdict resolver and per-finding verdict coverage check

Surface: infra

## Overview

First strangler-fig step of the tiebreak project: add, alongside the existing Direct-verification override and without touching it, the deterministic half of the tiebreak. A Node module parses one tiebreak agent's reply and resolves it, with fixed rules, into `confirmed`, `drop`, `digest` or `console`. A subcommand on the existing `review-coordination.js` CLI exposes it. A run-dir artifact lists every finding still `unconfirmed` or `contested` after the earlier review passes (the denominator), and a coverage check, wired into the archive refusal path, refuses to archive a run where a listed finding has no tiebreak verdict line in `decisions.md`.

Nothing in the review skill calls this yet (the review step is the next sub-issue), so this record can merge and ship on its own with no behavior change for any existing run.

**Complexity:** Medium
**Estimated tasks:** 7

- Dispatching tiebreak agents or editing any `plugin/skills/**` prose (the review-step sub-issue).

- Changing `categoriseReproduction`, `resolveDebate`, `resolveRefutation` or any line-band constant in `coordination.js`.

## Acceptance Criteria

1. Reply fields: `Verdict: confirmed | refuted | cant-tell`; `Evidence:` a verbatim live-code quote at a stated `path:line` (required for `confirmed` and `refuted`); `Severity:`; `Recommendation: file | drop` plus a one-line reason; a trailing `STATUS:` line. A well-formed reply parses into those fields.
2. `confirmed` with evidence resolves to outcome `confirmed` with severity equal to the lower of the reporter's and the tiebreak's severity. Its log line has the shape `AUTO {HH:MM:SS} — Reproduction: lens "{lens}" finding {path}:{line} … Confirmed. Reversibility: high.`, and a test feeds that line, after a matching `- STAGED` line, through `plugin/bin/lib/console/resolve.js` and asserts the STAGED line is superseded (no console item).
3. `refuted` with evidence resolves to outcome `drop` at every severity, with an `AUTO` log line carrying the quoted evidence; `listInConsole` is `true` exactly when the severity is `high` or `critical`.
4. `cant-tell`, `confirmed` / `refuted` with no `Evidence:`, a malformed or unparseable reply, and any `STATUS:` other than `DONE` all resolve to can't-tell. Each of these four has its own test, and each test is shown failing against a fail-open variant of the resolver (revert the guard, see red).
5. Threshold severity for can't-tell is the higher of the reporter's and the tiebreak's; tiebreak severity absent resolves to the reporter's; neither known resolves to `medium`. can't-tell at `low` gives outcome `digest`; at `medium` or above gives outcome `console` carrying the recommendation. One test per branch, including the neither-known branch. For a `contested` finding the reporter's severity is the higher of the two positions' severities. The same absent / unknown fallbacks apply to the `confirmed` and `refuted` branches: a `confirmed` finding's severity is the lower of the reporter's and the tiebreak's when both are known, the reporter's when the tiebreak's is absent, and `medium` when neither is known; `listInConsole` on a `drop` reads the higher of the two known severities (so a bad drop is never hidden by a low tiebreak severity). A severity string outside `critical | high | medium | low | info` counts as unknown.
6. Parse classes, each with its own test and each mapped to the stated `parse` value and outcome: no recognizable `Verdict:` line with a valid value, an empty reply, or no trailing `STATUS:` line gives `parse: 'could-not-parse'`; a parseable reply whose status is not `DONE` gives `parse: 'ok'` with outcome can't-tell and reason `status:{WORD}`; a parseable `confirmed` / `refuted` reply with no `Evidence:` gives `parse: 'ok'`, outcome can't-tell and reason `no-evidence`. The two signals are distinguishable in the JSON, asserted by a test.
7. The findings artifact round-trips through its writer and reader; the coverage check returns exactly the listed findings whose id has no verdict line, and an empty list when every listed finding has one. Two findings in the same file at the same lens and `path:line` but with different claims get distinct ids and need two verdict lines (a test with a same-key collision; the #3772 matcher keying on lens plus first `path:line` is unchanged and documented as coarser than the id).
8. `archive-run` / `decideArchiveCore` refuse a run whose artifact lists a finding with no verdict line (new, named refusal reason), refuse a run whose artifact is present but unreadable or malformed (distinct reason), archive a run where every listed finding has one, and archive a run with no artifact exactly as before. The #3668, #3370 and #3503 guards keep their order and behavior (their existing tests pass unchanged), and the new check is evaluated after them.
9. The #3772 test uses a STAGED line produced by the real emitter (the `STAGED … Reproduction: lens "{lens}" …` form the review step writes today, captured as a fixture), not a hand-typed one; a `line` that is absent or a range resolves to the first line of the range, or to the can't-tell path when none can be read.
10. Evidence verification: a `refuted` reply whose quote is not in the cited file (fabricated), and one whose quote is in the file but outside ±5 lines of the cited line, each resolve to can't-tell with reason `evidence-unverified`; the same holds for `confirmed`. A quote differing only in whitespace verifies. Each test is shown failing against a no-check variant. A call with no reader injected resolves `confirmed`/`refuted` to can't-tell.
11. `npm test` passes.

## Release Note

Added a deterministic resolver for review tiebreak verdicts and an archive check that every unconfirmed review finding received one.

## Technical Approach

The reply is a small fixed template (the review-step sub-issue inlines it in the dispatch prompt), so parsing is line-oriented: find the `Verdict:`, `Evidence:`, `Severity:` and `Recommendation:` lines and the trailing `STATUS:` line; anything missing or unrecognized is a parse failure surfaced as the could-not-parse signal. Resolution is a pure function of (finding, parsed reply). The log-line builder reuses the existing `AUTO … Confirmed.` shape so the #3772 matcher keeps working with no change to `resolve.js`.

Identity and verdict lines (decided here so every consumer shares one grammar). A finding's `id` is a short hash (first 12 hex characters of SHA-1) of `lens`, `path`, `line` and the whitespace-normalized `claim`, so it is stable across a re-run of the same review pass and distinct for two findings that share a location. Every verdict line, for every outcome, carries the literal marker `tiebreak:{id}`; the coverage check matches on that marker, never on lens plus `path:line`. The confirmed line keeps the existing shape and adds the marker: `AUTO {HH:MM:SS} — Reproduction: lens "{lens}" finding {path}:{line} confirmed by tiebreak:{id}. Confirmed. Reversibility: high.` so the #3772 matcher (lens plus first `path:line` plus the case-sensitive word `Confirmed`) still supersedes the earlier STAGED line. No non-confirmed verdict line may contain the capitalized word `Confirmed` (so a drop or digest line can never supersede a STAGED line by accident); a test asserts it. Drop and digest lines use the form `AUTO {HH:MM:SS} — Tiebreak tiebreak:{id}: lens "{lens}" finding {path}:{line} {dropped|digested}: {reason}. Severity: {sev}. Reversibility: high.`, the drop line also carrying the quoted evidence (the Review Console's read-only "Dropped by tiebreak" block reads drop lines with severity `high` or `critical`). The console outcome is written as a `STAGED` line, because it becomes a Review Console item: `STAGED {HH:MM:SS} — Tiebreak tiebreak:{id}: lens "{lens}" finding {path}:{line} console: {reason}. Severity: {sev}. Recommendation: {file|drop}. Reversibility: high.`; the console sub-issue reads the `Severity:` and `Recommendation:` fields from it. A `Confirmed` line written by an earlier reproduction pass has no marker and so never counts as a tiebreak verdict.

The resolver is a pure function of (finding, parsed reply, `readFile`). Evidence is verified, not just present (maintainer decision, 2026-10-22): a `confirmed` or `refuted` verdict counts only when its quote is found in the cited file near the cited line, so a fabricated or paraphrased quote can neither drop a real finding nor confirm a false one (IL-50, IL-144). Without a reader the evidence counts as unverified, so the fail direction stays toward scrutiny.

### Data / API Surface

- Resolver input: `{ lens, path, line, claim, reporterSeverity, kind }` and the raw reply text. `kind` is carried through to the artifact and the log line and does not change resolution. The reply's cited `Evidence:` `path:line` must name the finding's own `path`; a mismatch counts as no valid evidence.
- Resolver output: `{ outcome: 'confirmed' | 'drop' | 'digest' | 'console', severity, evidence, recommendation, reason, logLine, listInConsole, parse: 'ok' | 'could-not-parse' }`. `Verdict:` is authoritative; a `Recommendation:` that contradicts it (for example `confirmed` with `drop`) is carried verbatim as advisory text and never changes the outcome.
- Findings artifact: a JSON array of `{ id, lens, path, line, claim, reporterSeverity, kind }`.
- Coverage check: `(runDir) -> { artifactPresent: boolean, artifactValid: boolean, missing: [finding ids] }`.

## Gotchas

- Parse-signal discipline: a could-not-parse result must be a distinct signal and must never be indistinguishable from a legitimate outcome (the `parse-signal-discipline` skill in this repo's `.claude/skills/`).
- Fail-toward-scrutiny is the whole point (IL-50): every unrecognized, missing or empty input resolves to can't-tell, never to `drop` or `confirmed`. Prove each guard by reverting it and watching its test go red.
- The archive guards #3668, #3370 and #3503 must keep their order and behavior; add the new refusal without reordering the existing checks in `decideArchiveCore`.
- Enforce the coverage check only when the artifact exists. Runs created before this ships have none and must not be stranded.
- `plugin/bin/lib/console/resolve.js`'s matcher is case-sensitive on `Confirmed` and keys on lens + first `path:line`; the log line's lens quoting and `path:line` must produce the same key as the earlier STAGED line.
- The findings artifact must be written through a writer that respects run-dir anchoring (`IL-127`: a bare relative path from a worktree silently shadows the main checkout's run dir).
- File overlap only (not a dependency): #3206 (parked) also touches `plugin/bin/lib/coordination.js`.
- `decideArchiveCore` has no coverage input today, so its signature gains one (for example an optional fifth parameter, absent meaning today's behavior byte-for-byte); callers that do not pass it are unchanged.
- A run whose tiebreak never produced a reply is still satisfiable: the review step feeds an empty or failed dispatch to the resolver, which yields a can't-tell verdict line (`parse: 'could-not-parse'`), so every listed finding can always get a line. Do not add a waiver mechanism.
- The recovery for a present-but-malformed artifact is to re-run the review step's artifact writer for that run, or delete the artifact if the run predates the tiebreak; the refusal message states both.
- ASSUMPTION — verify at build: `hooks.js`'s `archive-run` handler consults `decideArchiveCore` (or an equivalent), and the new refusal can be added in one place — via reading the `archive-run` module under `plugin/bin/lib/hooks/`.
- Evidence verification is required (maintainer decision 2026-10-22, replacing the red-team ambiguity on this point): never relax it to "present and well-formed", and never let the reader-less path verify.
