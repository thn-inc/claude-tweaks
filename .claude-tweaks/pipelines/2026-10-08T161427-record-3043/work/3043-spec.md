# 3043: Make flow verification workable on a dev checkout with a known non-zero baseline

Origin: reflect full from #3040
Defer-reason: tangential

## Current State

On a Windows development checkout of this repo, three of the pipeline's verification rules cannot all hold at once:

- `test/verification.md` says the runner (`bin/verify.js --cmd tests="npm test"`) must run in the foreground.
- The full suite takes ~982s at 10,565 tests, past the Bash tool's 600s foreground ceiling.
- The suite always exits 1 on this checkout. About 350 failures across ~106 files fail identically at the base commit: Windows path-separator and CRLF-sensitive assertions, plus a few load flakes.

Because the runner exits non-zero, it never writes a pass stamp (`verify.js --stamp-status` → `present:false`). The effects in run `2026-10-08T101832-record-3040` (#3040):

- `/claude-tweaks:test` inside `/flow` cannot use skip-if-recent, so it re-ran the full ~16-minute suite.
- `/claude-tweaks:review` Step 1.5 says to re-trigger `/test` whenever `verifiedHead` is false. That can never resolve here, so the orchestrator had to rule against the instruction.
- Both phases needed hand-written per-file baseline adjudication: a re-run of the failing files at base in a scratch worktree, and flake re-runs.

## Deliverables

- [ ] A sanctioned way to verify against a known baseline. For example, `verify.js --baseline <ref>` re-runs the failing files at the base ref in a scratch worktree, and stamps a pass when the failing-file set is a subset of base's, after flake re-runs. The result is recorded in `report.json` (`baselineAdjudicated: {base, attributable: []}`).
- [ ] `test/verification.md` and `review/code-mode-steps.md` Step 1.5 treat a baseline-adjudicated stamp as verifying HEAD. The re-trigger rule then terminates.
- [ ] `verification.md`'s foreground rule names the case where the full suite exceeds the foreground tool ceiling, and how the orchestrator, not a dispatched agent, may background it.

## Acceptance Criteria

- [ ] On a checkout whose suite fails only on files that also fail at the base ref, `verify.js --baseline origin/main` exits 0 and `--stamp-status` reports `verifiedHead: true`.
- [ ] A failure in a file that passes at base still exits non-zero and names the file.
- [ ] A `/flow` run on such a checkout runs the full suite once, at build Common Step 5, not again at `/test`.

## Release Note

Pipelines on a development machine with known environment-specific test failures can now verify against the base branch instead of re-running the full suite at every phase.
