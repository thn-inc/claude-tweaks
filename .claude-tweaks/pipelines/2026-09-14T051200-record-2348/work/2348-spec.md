# 2348: worktree-setup: adopted worktree can silently resolve to stale main-checkout node_modules

Surface: infra

## Current State

`_shared/worktree-setup.md`'s "Adopt-or-create" gate (confirmed, ~lines 29-65) has an "Already
isolated" (adopt) branch that runs a clean-tree precondition check and a
fetch+merge-against-origin catch-up, but nowhere checks whether the adopted worktree's own
`node_modules` matches its own `package.json`/lockfile — confirmed by grep: zero mentions of
`node_modules`, `npm install`, or `npm ci` anywhere in either `_shared/worktree-setup.md` or
`build/worktree-setup.md`. When the worktree has no local `node_modules` at all, Node's module
resolution walks up to the main checkout's copy, which can be stale relative to the worktree's
own branch (e.g. missing a dependency the branch just added). The result is cascading
`ERR_MODULE_NOT_FOUND` failures across every test that imports the missing dependency — a
misleading, unrelated-looking symptom that costs real investigation time before the actual cause
is found.

Observed live: in a Next.js/TypeScript project, an adopted worktree had no local `node_modules`,
so Node resolved to the main checkout's copy, which predated two dependencies (`unified`,
`remark-parse`) the worktree's own branch had already added. The pre-flight test sweep failed
near-total, unrelated to any actual code change. The fix was running `npm ci` plus a
client-generation step inside the worktree itself.

**Scope note for the builder:** neither worktree-setup file mentions a dependency-install step at
all, for either the adopt path or the fresh-creation path — verify at build time whether a fresh
`EnterWorktree`-created worktree already gets `node_modules` some other way (a symlink, a
documented install step living elsewhere in `build/SKILL.md` or `flow/SKILL.md` rather than in
the worktree-setup files themselves) before assuming this gap is adopted-worktree-specific; if
fresh creation has the identical exposure, the fix belongs in the shared gate both paths already
route through, not only the adopt branch.

## Deliverables

Add a detection-and-message (or auto-install) step to the Adopt-or-create gate's adopt branch:
when the worktree has no local `node_modules` (or one that's stale relative to
`package.json`/the lockfile), either run the install automatically or surface a clear message
naming the mismatch before the caller proceeds to run tests — so a missing/stale dependency
produces an actionable message immediately, not a cascade of misleading
`ERR_MODULE_NOT_FOUND` failures deep into a test run.

## Acceptance Criteria

- Adopting a worktree with no local `node_modules` produces either an automatic install or a
  clear, actionable message before any test/build step runs — not a silent walk-up resolution to
  the main checkout's (potentially stale) copy.
- The check/fix correctly distinguishes "no local `node_modules` at all" from "local
  `node_modules` present and current" — an already-correct worktree pays no extra cost.
- `npm test` passes.

## Technical Approach

Add a check to the Adopt-or-create gate's adopt branch (~line 49, in the same sequence as the
existing clean-tree precondition check and fetch+merge catch-up): test for the presence of a
local `node_modules` directory in the worktree root, and — if missing, or if a cheap staleness
signal is available (e.g. comparing `package-lock.json`'s mtime/hash against a stamp
`node_modules` itself carries, if this project's package manager writes one) — either run the
project's own install command (detected the same way `dev-url-detection.md` already detects a
project's dev/start command, per this codebase's existing conventions for that kind of
detection) or emit a clear warning naming the gap and recommending `npm ci` (or the detected
package manager's equivalent) before proceeding. Prefer surfacing a clear message over a silent
auto-install if there's any ambiguity about which package manager or install command applies —
a wrong auto-install could itself cost more time than the original failure mode.

### Key Files

- `plugin/skills/_shared/worktree-setup.md` — add the check to the Adopt-or-create gate's adopt
  branch (~line 49)
- `plugin/skills/build/worktree-setup.md` — verify whether the fresh-creation path also needs
  this check, per the Current State's scope note

## Gotchas

- Don't assume a specific package manager (npm/pnpm/yarn) — detect it the way this codebase
  already detects other project-specific commands (lockfile presence is usually the simplest
  signal: `package-lock.json` → npm, `pnpm-lock.yaml` → pnpm, `yarn.lock` → yarn).
- An auto-install can be slow (real dependency resolution) — if choosing auto-install over a
  message-only approach, make sure it doesn't silently add significant wall-clock time to every
  worktree adoption without at least logging that it's happening.
- Per the Current State's scope note: confirm whether this is genuinely adopted-worktree-specific
  before landing a fix only in the adopt branch — a fresh-creation gap in the same class would be
  a bigger miss to leave unaddressed.
