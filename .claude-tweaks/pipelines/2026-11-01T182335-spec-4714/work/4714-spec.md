Surface: infra

## Current State

The finding holds, verified at shaping time against `origin/main` (2026-11-01). `renderWorkflowYaml` in `plugin/bin/lib/init/release-bootstrap.js` interpolates the branch bare into two YAML positions of the rendered `.github/workflows/release-please.yml`:

```
on.push.branches:  `      - ${b}`
with.target-branch: `          target-branch: ${b}`
```

Its only guard is the shared `isValidBranchName` (`plugin/bin/lib/branch-name.js`), which rejects whitespace, control characters, `~^:?*[\`, `..`, `//`, a leading `-`, and a trailing `/` or `.lock`. Probed directly: `git check-ref-format --branch` and `isValidBranchName` both accept `${{secrets.X}}`, `#main`, `&x`, `!x`, `"x`, `{a}`, and `@x`. Rendered bare, these produce four distinct failures:

1. **Actions expression injection.** `${{secrets.RELEASE_PLEASE_TOKEN}}` lands as a live expression in `target-branch`. GitHub evaluates `${{ }}` inside quoted scalars too, so quoting alone does not close this.
2. **Broken or re-meaning YAML.** A leading `#` turns the list entry into a comment (a null entry). A leading `&`/`!`/`|`/`>`/`%`/`@`/`"`/`{` is a YAML indicator: an anchor, a tag, a block scalar, a reserved indicator, an unterminated quote, or a flow mapping.
3. **Type coercion.** A git-valid name such as `1.10`, `true`, or `null` parses as a float, boolean, or null, so `target-branch: 1.10` reaches release-please as `1.1`.
4. **Filter-pattern semantics.** `on.push.branches` entries are GitHub filter patterns, not literals. The validator already rejects `*`, `?`, `[`, and `\`, but `+` (a one-or-more quantifier) and a leading `!` (negation) pass through, so `release+1` never triggers on itself and `!x` triggers on everything except `x`.

The practical exposure is low: `--branch` comes from `/claude-tweaks:init` Step 21, which resolves it from the repo's own integration branch (`plugin/skills/init/bootstrap/step-21-release.md`). Anyone who can name that branch already has write access. So this is mainly a correctness defect (an odd but legal integration-branch name renders a broken or wrong workflow), with an injection edge.

`renderWorkflowYaml` runs before any file is written (`bootstrapRelease` builds its files list first), and `bin/release-bootstrap.js` turns a thrown error into exit 1 with the message on stderr. A refusal in the renderer is therefore safe: it writes nothing. Nothing compares an installed workflow against fresh renderer output, and existing files are never overwritten, so changing the rendered text affects new bootstraps only.

The other three `isValidBranchName` callers (`plugin/bin/pre-review-catchup.js`, `plugin/bin/release-bootstrap.js`'s own `--branch` pre-check, `plugin/bin/lib/worktree/remote-branch-collision.js`) only pass the name as a git argv element or forward it to this renderer. These characters are harmless in argv, so tightening the shared validator would refuse legal branch names where they cause no problem.

## Technical Approach

All changes live in `renderWorkflowYaml`.

1. After the `isValidBranchName` check, add `if (branch.includes('${{')) throw new Error(...)`. Keep the message inside the existing `invalid branch name` wording so the current test regex and the CLI's stderr path keep working, naming the Actions-expression reason.
2. Quote with `JSON.stringify`. For a string with no control characters, which the validator already guarantees, JSON string syntax is a valid YAML double-quoted scalar, so no YAML library is needed. The repo has no YAML dependency and should not gain one for this.
3. Build the filter value as `branch.replace(/\+/g, '\\+').replace(/^!/, '\\!')`, then `JSON.stringify` it. GitHub's filter syntax treats a backslash-escaped metacharacter as a literal.
4. Update the two regex pins at `tests/bin-lib/init/release-bootstrap.test.js` (`/branches:\n\s+- develop/`, `/target-branch: develop/`) to the quoted form, and add the new cases next to the existing `renderWorkflowYaml` tests.

Do not change `isValidBranchName`: the fix belongs where the YAML/Actions context exists.

### Key Files

- `plugin/bin/lib/init/release-bootstrap.js` — `renderWorkflowYaml`: `${{` refusal, always-quoted scalars, filter-pattern escaping
- `tests/bin-lib/init/release-bootstrap.test.js` — update the two quoted-form pins; add injection, YAML-indicator, type-coercion, and filter-escaping cases

## Gotchas

- Quoting does not stop Actions expression evaluation: `"${{ secrets.X }}"` is still evaluated. The `${{` refusal is required alongside the quoting, not instead of it.
- Do not quote only when needed using a safe-characters regex. A name made only of safe characters (`1.10`, `true`, `null`, `yes`, `on`) still changes type when plain, and always quoting is simpler and correct.
- Filter escaping applies only to the `branches:` entry. `target-branch` is a literal input to release-please, and escaping it would make release-please target a branch name with a literal backslash.
- Installed workflows written by an earlier bootstrap keep their unquoted form. That is harmless for ordinary names, and the bootstrap never overwrites a file it did not create this run.
- The type label on this record is `type:task`. The work is a defect fix, so a human may want to relabel it `type:bug` before merge so the composed release subject reads as a fix.
