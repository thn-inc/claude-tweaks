## Plan Review Decisions

Answers to the plan-review question posted on 2026-10-31 (build Common Step 1.6), decided by the maintainer:

- **What counts as "a structured field": Reading B.** The floor verdict must not depend on an agent transcribing it. `permittedInitiative`'s `hold` travels as a JSON field the reference sweep writes into `engine-state.json`'s `references` findings, which `plugin/bin/lib/console/resolve.js` already reads; the resolver holds the repair unless that JSON field reads `hold: false` and the staged file's `Hold:` header agrees. Any disagreement, absence or malformed value holds (fails closed).
- **`hold` is computed from the floor conditions regardless of which check fails first** (plan review's high finding): a test-file, causal-set or merge-sensitive repair that is also over budget or over a size cap still gets `hold: true`.
- Task 1 (the per-denial-path decision logic) carries `Review risk: high`.
- **Is an agent-written JSON `hold` enough: no, Node checks the floor itself (Reading B, tightened; answered 2026-11-02).** At `unattended`, the resolver runs the test-path and merge-sensitive checks itself and holds on a hit. It reads the paths from the `diff --git` lines of the staged `wrap-up-reference-*` file, never from the agent-written `target`, `files` or `summary`, and holds when that file has no parseable diff. The reference sweep must write the diff into every staged repair. The causal check stays on the agent-written `hold`, because its `brokenBy` input comes from the agent anyway. The plan's "no engine or CLI change" line is dropped.
- **The four other findings from that plan review are applied:** a non-string `stagePath` counts as no staged file; the "whichever check fails first" test skips the `no files` + `files cap` pair; Task 3 carries `Review risk: high`; `supervised` stays approvable and an unknown or non-string ceiling holds.
- **Does the floor bind the edit actually applied: yes (answered 2026-11-02).** An approved reference repair is applied from the staged diff with `git apply`, so what the resolver checked is what lands; `plugin/skills/wrap-up/execution-and-verification.md` changes accordingly, with a test for this direction. A diff that no longer applies leaves the row pending for a human.
- **Ambiguous candidates are exempt from the diff requirement (answered 2026-11-02).** They carry `Hold: yes` plus a `Held:` line and no diff, and the resolver holds them before it reads any diff. Every other staged repair must carry a real diff, except one whose diff could not be composed (see below).
- **Three smaller findings from that plan review are settled:** the sweep composes each diff on a temp copy with `git diff --no-index`, leaving the shared worktree untouched, including under `--dry-run`; a `sensitivePaths` value that is not an array holds (`!Array.isArray`); the fan-out payload JSON template gains `hold`.
- **Approving a repair with no diff: the human names the target (answered 2026-11-02).** The approving human picks the target, the diff is composed by the same recipe as any other, the floor check re-runs on it, and it lands with `git apply`. At `unattended` the row stays pending.
- **A diff that cannot be composed: hold it with no diff (answered 2026-11-02).** It is staged as held the same way as an ambiguous candidate, so a human sees it on the console.
- **The floor check uses a strict diff parser, proved by probe on 2026-11-02.** Reading only `diff --git` lines is not enough. All three of these patches pass under a `docs/a.md` header, and `git apply` changes `tests/x.test.js`: `---`/`+++` lines naming the test file; a second section with no `diff --git` line; `rename from tests/x.test.js`. `git apply --numstat` lists only the new path for the rename, so it is not a sufficient path source on its own. Every path line in a section (`---`, `+++`, `rename`, `copy`) must agree with that section's `diff --git` line, every section must have one, and anything else holds. Hunk content lines that resemble path lines must not be misread. All three patches become test fixtures.
- **Other findings from that plan review are settled:** the multi-spec console applies an approved reference repair the same way as the single-spec console; the stale rewrite does not use `$PIPELINE_RUN_DIR` or treat every exit 5 as a human being present, and handles exit 3; Task 3 Step 5's grep expectation names `reference-repair.js`; `docs/plugin-structure.md:165` is updated for the widened `--set-item`.
- **A floor hit on a diff composed for a human-named target is shown, and the human may confirm it (answered 2026-11-03).** The console names the path and why it hit; on confirmation the diff lands with `git apply`, otherwise nothing lands. This matches how a held repair that already has a diff behaves: the floor keeps a change from landing without a human, and here a human is approving it. At `unattended` the row stays pending.

## Build deviations (Common Step 4.5, classified Beneficial)

Each tightens "anything else holds"; none loosens a hold. Each was ruled during the build and is staged for ratification at the Review Console (`sdd-ruling-*`).

- **The strict parser also refuses a side containing a quote, backslash, tab or control character, and `old mode`/`new mode` lines.** git reads a quoted or tab-split side as a different file, and a mode line lets an approved repair change an executable bit (both reproduced with real `git apply`). The recipe matches: `b/{path}` is a `cp -p` copy of `a/{path}`, and the diff runs as `git -c core.quotePath=false diff --no-index --no-color --no-ext-diff --no-textconv --no-prefix`, so a non-ASCII path still parses.
- **The merge-sensitive check is also case-folded**, in the resolver's floor and in `permittedInitiative`: a case-insensitive filesystem lands `PACKAGE-LOCK.JSON` on `package-lock.json`. The shared `isSensitivePath` matcher (merge-check floor, express lane) is unchanged.
- **`permittedInitiative` holds an unreadable `sensitivePaths`** (anything but an array of glob strings), matching the resolver; the sweep passes the parsed array, `null` when the policy cannot be read.
- **The `approve` → `pending` rewrite is limited to the Reference repairs section**, and a human's `target {#} {new}` answer is logged as one `AUTO` line at the console stop so Phase 4 can read it back.
