# 3013: /claude-tweaks:test + /review Step 1.5: pr-first gates pass on local verification while the run's PR has a failing required check

Surface: infra

**Related:** #3014

## Current State

Under `integration-model: pr-first`, a run's draft PR exists from run start and is pushed at every phase exit. Its number is recorded as `run-state.json`'s `pr: { number, url }` (`plugin/skills/_shared/pr-early-run-lifecycle.md:356`). Two gates decide whether tests passed, and neither reads that PR's CI state:

- `/claude-tweaks:test`'s pipeline behavior (`plugin/skills/test/SKILL.md:69-73`) sets `TEST_PASSED=true` from local verification alone: `VERIFICATION_PASSED`, or a runner stamp verifying HEAD (`verify.js --stamp-status`).
- `/claude-tweaks:review` Step 1.5, the Test Gate (`plugin/skills/review/code-mode-steps.md:57-100`), checks `TEST_PASSED=true` plus the runner stamp's `verifiedHead`, then reads the QA ledger rows.

The only PR-check read in the pipeline is at merge time. `_shared/pr-first-merge.md:137-160` reads `gh pr view --json state,mergeStateStatus,headRefOid,statusCheckRollup` and classifies the PR red, pending or green. A red rollup sends the run down its Red path.

In the reported run (plugin 6.136.0, a two-call `/dispatch` on a Windows host), the first call's test gate logged PASS at commit X while the PR's required UI CI job was already red at X. A hydration-timing e2e race showed up only on the slower Linux runner and did not reproduce locally even under 20x CPU throttling. The second call noticed only by chance. Without that, the failure would have surfaced only at the merge gate, after review, polish and wrap-up had run on top of a red commit.

## Deliverables

1. **One shared PR-check read.** Add a single read of the run PR's check rollup at HEAD that both gates call, reusing `pr-first-merge.md`'s classification rules (failing conclusions `FAILURE`/`TIMED_OUT`/`ERROR`/`STARTUP_FAILURE` → red; not-`COMPLETED` → pending; empty rollup → pending, or "no CI" when the repo has no PR workflow). Classify only when the rollup's `headRefOid` equals local HEAD. Otherwise the result is `stale` (HEAD not pushed yet) and nothing is concluded. The read is deterministic code with a documented output shape, not prose each gate re-derives.
2. **Test gate.** When `run-state.json` carries `pr`, `/test`'s pipeline branch runs the read after local verification passes. A **red** result fails the gate like a local test failure: it names the failing check and its run URL, and `TEST_PASSED` is not set. **Pending** or **stale** passes with a `TEST_PASSED` caveat naming the pending checks, logged as an `AUTO` line. **No `pr`, `gh` absent, or no CI** fails open exactly as today, with a `SKIP` trace per `_shared/auto-decision-log.md`'s degrade-trace rule.
3. **Review Step 1.5.** The same read runs at review's Test Gate, in the row table at `code-mode-steps.md:100`. A red result stops the gate with the check's name and URL, so a red check that appeared after `/test` ran (the second dispatch call) is caught before review spends effort.
4. **Merge gate unchanged.** `pr-first-merge.md`'s Step 2.5 read stays as the final authority. The new read must not duplicate or alter its classification rules. Cite them from one place.

## Acceptance Criteria

- A unit test drives the shared read's classifier with fixture rollups: a failing completed check at HEAD → red; an in-progress check → pending; `headRefOid` ≠ HEAD → stale; an empty rollup with and without a PR workflow; a `gh` read failure → reported as a read failure, never as green. Prove the red case goes red against a stub that always returns green.
- `/test`'s pipeline branch and `/review` Step 1.5 both cite the shared read. A conformance test pins both citations and the red → gate-failure routing.
- A run with no `run-state.json.pr` (`local-merge`, or standalone `/test`) behaves exactly as today. A test or fixture asserts the fail-open path and its `SKIP` trace.
- `pr-first-merge.md`'s Step 2.5 classification text and its existing tests are unchanged.
- `npm test` passes in full.

## Release Note

Under PR-first runs, the test and review gates now fail when the run's own pull request already has a failing CI check, instead of passing on local results alone.

## Technical Approach

Lift the rollup classification `pr-first-merge.md:137-160` already defines into a small `bin/` reader (the `gh` runner seam and fail-safe conventions of the existing `bin/lib/` CLIs) that returns `{state: red|pending|stale|green|no-ci|read-failed, failing:[{name,url}], pending:[name], headRefOid}`. `/test` and `/review` call it with the PR number from `run-state.json`. The merge gate keeps its own read and may adopt the helper later, but this record does not change its behavior. Treat red as a gate failure rather than a caveat: the incident shows a caveat would ride through to the Review Console unnoticed, which is exactly what happened.

### Key Files

- `plugin/skills/test/SKILL.md` — pipeline behavior bullets (`:69-73`) run the PR-check read after local verification
- `plugin/skills/review/code-mode-steps.md` — Step 1.5 Test Gate (`:57-100`) adds the read and a red-check row
- `plugin/skills/_shared/pr-first-merge.md` — reference for the classification rules (`:137-160`); cited, not modified
- `plugin/skills/_shared/pr-early-run-lifecycle.md` — reference for `run-state.json`'s `pr` field (`:356`)
- `plugin/bin/lib/reconcile/pr-state.js` — resolves PR state by branch or number (`:98`, `:128`) but reads no `statusCheckRollup` today; a candidate home for the reader, or a reference for its `gh` runner/error classification (`classifyExecError`, `:33`)

## Gotchas

- `statusCheckRollup` does not mark which checks are *required*. The merge gate already treats any failing check as red, and this read must match that rather than invent a required-only rule that disagrees with the merge gate.
- A flaky CI check now blocks the test gate. That is intended (it would block the merge anyway), but the failure message must name the check and URL so the fix loop can tell a CI-only race from a local regression.
- Each phase exit pushes, so HEAD is usually on the PR by the time `/test` runs, but not always. The `stale` result must never be read as green or red.
- GitHub populates the rollup seconds after a push, not instantly. An empty rollup on a repo with PR CI is pending, never green (`pr-first-merge.md`'s own empty-rollup rule).
- Gate failures under `auto` mode are HARD-GATEs (`_shared/auto-mode-contract.md`). A red-check failure stops the pipeline like a test failure, which is the point. Do not stage it as a Review Console item instead.

## Original request

/claude-tweaks:test + /review Step 1.5: pr-first gates pass on local verification while the run's PR has a failing required check

**Summary:** Under `integration-model: pr-first`, the `/claude-tweaks:test` gate and `/claude-tweaks:review` Step 1.5 pass on local verification alone while the run's own PR has a failing required CI check at the same commit.

**Kind:** Gap

**Affected component:** `/claude-tweaks:test` (verification gate) and `/claude-tweaks:review` Step 1.5 (test gate), under `integration-model: pr-first`

**Use case:**
In a two-call `/claude-tweaks:dispatch` run (`build,test`, then `review,polish,wrap-up`) on a Windows host, the first call's test gate logged PASS at commit X: every locally run suite was green, and the call handed off a passing run. The run's draft PR, opened at run start under `pr-first`, already had its required UI CI job red at that same commit X. The cause was a hydration-timing end-to-end race that only the slower Linux CI runner exposed; it did not reproduce locally even under 20x CPU throttling. Neither the test gate nor review's Step 1.5 reads the forge's check state, so nothing in the pipeline saw it. The second call noticed only because it happened to run `gh pr checks` while waiting on something else. Otherwise the run would have reached the Review Console and its merge decision with a red required check.

Why it is systemic: under `pr-first` the PR exists from run start (`_shared/pr-early-run-lifecycle.md`) and is pushed at every phase exit, so its checks are always available. Yet the gates treat the local `verify.js` report as the whole verdict. Any project whose CI differs from the dev machine (OS, CPU, browser timing, interpreter version) can pass every local gate with a red PR.

Suggested change: when `run-state.json` carries a `pr` object, have the test gate (and `/review` Step 1.5's `TEST_PASSED` check) read the PR's checks at the current HEAD (`gh pr checks {n}`, or the GraphQL `statusCheckRollup`):
- a completed failing required check → gate failure (or at minimum a `TEST_PASSED` caveat naming the job and run URL), routed like any other test failure;
- pending checks → note them and re-read at the next phase exit (and in the merge procedure, which already has a merge-verification gate);
- `gh` absent or no checks configured → fail open, as today.

**Definition:** Clear

## As-Built Deviations (build, Common Step 4.5)

1. **StatusContext normalization** (Beneficial): `statusCheckRollup` can carry `StatusContext` entries with no `status`/`conclusion`; `classify.js` normalizes `state` into that shape before applying the merge-gate rules, so a finished commit status is not held pending forever.
2. **`no-pr` and `gh-absent` are explicit states** (Beneficial): the reader reports them as their own states (D2 named them as fail-open conditions) so the SKIP trace names the exact cause.
3. **`merge-verification: off` demotes red to a caveat** (Beneficial, from the final review): D2 says red fails the gate; under `off` the merge gate itself merges on red (`pr-first-merge.md` Step 2.5), so the gate matches it rather than stopping a run the merge would let through.
