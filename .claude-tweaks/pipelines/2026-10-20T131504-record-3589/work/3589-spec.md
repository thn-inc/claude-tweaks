# 3589: SubagentStop's immediate-after-async-signal exemption misses the queued_command completion carrier

Origin: reflect full from #3015
Defer-reason: tangential

## Current State

`plugin/bin/lib/hooks/subagent-stop.js`'s `isAsyncWaitSignal` (#2041) treats a reply as reacting to an async checkpoint only when the nearest earlier transcript line is an `isAsync: true` launch result or a user entry with `origin.kind: 'task-notification'`. Real subagent transcripts on Claude Code 2.1.283 and later deliver completion notifications as an `attachment` entry of type `queued_command` whose string `prompt` carries the `<task-notification>` body, which that function does not recognize. A yield composed immediately after such a notification is therefore not exempted by #2041 and is graded as a final reply. #3015 added `countPendingDispatches`, which does read that carrier, so a yield with launches still pending is now exempt; a yield immediately after the LAST completion (nothing pending) is still graded. Found by the #3015 whole-branch review; pre-existing, out of that record's scope.

## Deliverables

1. `isAsyncWaitSignal` recognizes the `queued_command` attachment carrier (a string `prompt` containing `<task-notification>`) the same way `countPendingDispatches` does, sharing one carrier predicate rather than a second copy.
2. A reply immediately after a `queued_command` completion notification is exempt from grading, as one after an origin-shaped notification is today.

## Acceptance Criteria

1. A transcript fixture built from verbatim live `queued_command` completion lines, ending in a non-compliant reply right after the notification, is not blocked.
2. A reply that follows other tool calls after the same notification, with nothing pending, is still blocked.
3. The existing SubagentStop tests pass.

## Release Note

Subagent replies sent right after a queued-command completion notice are no longer graded as missing their status line.
