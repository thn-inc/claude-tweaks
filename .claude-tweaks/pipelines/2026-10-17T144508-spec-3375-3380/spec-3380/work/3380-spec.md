# 3380: Notify when a project's effective superpowers is older than the version claude-tweaks is verified against

Surface: backend

## Overview

Part of the "Build dispatch cost shape" decomposition (origin #3229). The measured 10-task build most likely ran in a project pinned to superpowers 6.3.0 at project scope: user scope and this repository are on 7.0.0, but `~/.claude/plugins/installed_plugins.json` shows several other projects (and many of their worktrees) holding project-scope installs of 6.2.0 or 6.3.0. Writing-plans 7.0.0 added the rule that plans carry signatures and tests rather than complete code ("The implementer writes the body"); a project on 6.3.0 never gets it, and the cost-shape records in this decomposition assume it. Nothing tells such a project it is behind.

This record adds a one-line notice, naming both versions and the update command, when a project's effective superpowers install (a project-scope install overriding user scope) is older than the version claude-tweaks is verified against (7.0.0 after the re-pin record). It is a notice only: it never stops a session and never breaks one.

**Complexity:** Low-Medium
**Estimated tasks:** 3-4

## Non-Goals

- Updating the plugin on the user's behalf, or prompting.
- Any stop, gate or failure: the notice never blocks anything, in any mode.
- Checking other dependencies (code-simplifier, Impeccable).
- Importing anything from `tools/upstream-drift/` into shipped code (it is maintainer-side and does not ship).
- Warning when the effective version is newer than the verified one.

## Deliverables

- [ ] A small module under `plugin/bin/lib/` that resolves the effective superpowers version for the session's working directory, reusing the scope-selection rule already in `plugin/bin/lib/impeccable-engine/index.js` (`selectEntry`: project-scope entries whose `projectPath` is an ancestor of or equal to the working directory, longest wins, realpath-normalised on both sides, then the user-scope entry; extract it to a shared helper or require it, do not copy it). Only `user` and `project` entries are considered (`local` and `managed` are ignored); when several `superpowers@*` plugin keys exist, take the key that yields the matched entry, ties broken by the latest `lastUpdated`. The plugins file is read from `$CLAUDE_CONFIG_DIR/plugins/installed_plugins.json`, defaulting to `~/.claude/plugins/installed_plugins.json` (the resolution `plugin/bin/dream-scan.js` uses). Reading is defensive: a missing, unreadable or malformed file, an unexpected shape, an `installPath` whose `.claude-plugin/plugin.json` is unreadable, or an unparsable version yields no notice and no error (no fallback to the metadata `version`, which can disagree with the files).
- [ ] The floor version the notice compares against, kept as a single constant in shipped code (see Gotchas for why it cannot read the drift manifest), with a test that pins it equal to the drift manifest's superpowers `pinned` value (read through `loadManifest` in `tools/upstream-drift/manifest.js`, selecting `name: superpowers`) so the two cannot drift apart silently. A comment beside the constant, and one line in `.claude/skills/upstream-repin/SKILL.md`, state the intended semantics: the floor is the last verified pin, so a future re-pin of the superpowers entry deliberately raises the notice threshold for every project on the previous version.
- [ ] The notice itself: one line naming the effective version, the floor version, the matched `projectPath` when it differs from the working directory, and the update command for the matched install's scope and marketplace (`claude plugin update superpowers@{marketplace} --scope {project|user}`), rendered at one placement — a SessionStart inform-tier line in `session-start.js` (recommended: it already assembles inform-tier banners and has the working directory) or a status line in `/claude-tweaks:help`. The builder records the choice and its reason in `docs/hooks.md` or the module header. Never a stop.
- [ ] The notice appears once per session: SessionStart also fires on resume, clear and compact (the registration has no matcher), so it is emitted only when the hook payload's `source` is `startup` or absent.
- [ ] Version comparison on the grammar `^v?\d+\.\d+\.\d+$` only: numeric (6.10.0 is newer than 6.9.0), a leading `v` ignored, and anything else (pre-release, build metadata, other text) treated as unparsable and yielding no notice.
- [ ] The module's reader and home directory are injectable, and the existing `tests/hooks-session-start.test.js` cases default to an injected "no install" reader so they never read the maintainer's real `installed_plugins.json`.
- [ ] Tests: older-than-floor, equal, newer, project-overrides-user, ancestor-directory project entry, subdirectory working directory, worktree with no entry of its own, user-only, none installed, two marketplaces, `CLAUDE_CONFIG_DIR` override, malformed file, unreadable `installPath`, pre-release string, and the garbage-input invariant for the chosen hook path.

## Acceptance Criteria

1. With an injected floor of `7.0.0` and a fixture `installed_plugins.json` containing a user-scope superpowers 7.0.0 entry and a project-scope entry for the test project at 6.3.0 (its `installPath` holding a `plugin.json` at 6.3.0), the notice is emitted once and its text contains `6.3.0`, `7.0.0` and `claude plugin update`. (The concrete shipped floor is 7.0.0 only once the re-pin record has merged.)
2. With the project entry absent (user-scope 7.0.0 only), or the effective version equal to or newer than the floor, no notice is emitted and no output differs from before this change. A working directory below a project entry's `projectPath`, and a worktree with no entry of its own that has an ancestor project entry, resolve to that ancestor entry per `selectEntry`'s rule; one with no ancestor entry resolves to the user-scope entry.
3. With a missing, empty, non-JSON or wrong-shape `installed_plugins.json`, or an unreadable `installPath`, the code emits no notice, throws nothing, and the hook (if that placement is chosen) still exits 0 and returns its existing output unchanged.
4. A numeric semver comparison test shows `6.10.0` is not flagged against a `6.9.0` floor and `6.9.0` is flagged against a `6.10.0` floor; `7.0.0-rc.1` and `7.0.0+build` yield no notice.
5. A test asserts the shipped floor constant equals the drift manifest's superpowers `pinned` value; changing either alone turns it red.
6. A second SessionStart invocation with `source` of `resume`, `clear` or `compact` emits no notice; `startup` emits it.
7. The notice adds no `permissionDecision`, no non-zero exit, no `AskUserQuestion` and no new mid-flow stop in any mode, and no file under `plugin/` imports from `tools/`.
8. `npm test` passes, including the garbage-stdin invariant in `tests/hooks-dispatcher.test.js` if `session-start.js` is touched, and `tests/hooks-session-start.test.js` never reads the real plugins file.

## Release Note

Added a one-line notice when a project's superpowers install is older than the version claude-tweaks is verified against, with the update command to run.

## Technical Approach

Resolve the effective install the way Claude Code layers scopes: a project-scope install for the current project beats the user-scope one. Read the version from the installed artifact's own `plugin.json` (via the entry's `installPath`) rather than the metadata `version` field, and emit no notice when the artifact is unreadable — the same stance the drift tool takes ("a version resolved from the artifact itself, never from install metadata", `tools/upstream-drift/manifest.yml` header, `[IL-89]`). Placement is the builder's call: SessionStart already assembles inform-tier banners and has the project directory in hand; a `/claude-tweaks:help` status line is cheaper on context but only seen by users who run `help`. Prefer SessionStart unless its latency budget or the fast/background split in `session-start.js` argues against another synchronous file read.

### Data / API Surface

- New exports: `effectiveSuperpowersVersion(projectDir, { home, readFile })` returning `{ version, scope, installPath } | null`, and `superpowersNotice({ effective, floor })` returning the one-line string or `null` (names are the builder's call; keep both injectable for tests).
- The floor constant lives in shipped code (for example next to `plugin-version.js`) and is mirrored by a test.

### Key Files

- `plugin/bin/lib/superpowers-version.js` — new file (name is the builder's call): effective-version resolution, comparison, notice text
- `plugin/bin/lib/hooks/session-start.js` — notice wiring if SessionStart is chosen
- `plugin/skills/help/SKILL.md` — status line if `/claude-tweaks:help` is chosen
- `plugin/bin/lib/plugin-version.js` — read-only: the defensive version-read pattern to follow
- `plugin/bin/lib/impeccable-engine/index.js` — `selectEntry`/`readInstalledPlugins`: the scope-selection rule to reuse or extract
- `plugin/bin/dream-scan.js` — read-only: the `CLAUDE_CONFIG_DIR` resolution to match

- `tools/upstream-drift/manifest.js` — `loadManifest`, read by the floor-parity test only

- `tests/bin-lib/` — new test directory or file for the version module, following neighbouring suites

## Gotchas

- Steering principle for the whole decomposition: claude-tweaks never files upstream with superpowers and never contradicts SDD's text. This notice only tells a user to update; it changes no behavior.
- `tools/upstream-drift/` is maintainer-side and does not ship (`docs/decisions/0015-plugin-payload-boundary-is-the-plugin-subtree.md`), and nothing under `plugin/bin/` may import from it. The shipped notice therefore cannot read the drift manifest's pin; it needs its own source for the floor version. Resolve this by keeping a floor constant in shipped code plus a repository test that asserts it equals the manifest's superpowers `pinned` value (the test lives under `tests/`, which is also maintainer-side, and may read both). Do not make the shipped code fetch the pin at runtime.
- Never break a session (`docs/hooks.md`): every harness-dispatched hook path exits 0, and a malformed `installed_plugins.json` must degrade to "no notice". Wrap every read and parse; never let an exception escape the hook module.
- ASSUMPTION — verify at build: Claude Code applies a project-scope install to a session whose working directory is the entry's `projectPath` or below it (the rule `selectEntry` already encodes for Impeccable, checked against this same file in #2979), including an ancestor entry such as a home-directory project entry that is older than the user-scope install — via probing which superpowers version a session in a worktree or subdirectory with no entry of its own actually loads; if the layering differs, adjust the matching rule and keep the "unparsable means no notice" fallback. Record the confirmed rule in the module header.
- "Effective" here means installed with a readable artifact; the notice does not consult `enabledPlugins`. A stale install that is not enabled can still produce a notice, an accepted false positive.
- The matched entry's `projectPath` can differ from the working directory (an ancestor entry, or a worktree using its main checkout's entry), and a project-scope `claude plugin update` may act on a different project than the one in the session; the notice names the matched `projectPath` when it differs so the user can run the command from there.
- The `version` field in `installed_plugins.json` is install metadata and `claude plugin update` compares version strings against the local marketplace catalog only (it inspects no files), so a stale catalog reports "already at the latest" without moving anything. Word the notice so the update command is a suggestion; if the catalog may be stale, the line can mention refreshing the marketplace first.
- The update command takes the install's scope: `claude plugin update superpowers@claude-plugins-official --scope project` for a project-scope install, `--scope user` for a user-scope one. Use the marketplace name from the matched installed-plugins key rather than hardcoding `claude-plugins-official`.
- Do not warn when no superpowers install is found; `/claude-tweaks:init` and the dependency checks already own the "not installed" case.
- Keep the notice to one line and show it once per session; the existing SessionStart banners are already numerous and context-costly.

## Revised during build (Common Step 4.5, Beneficial)

- **Matching rule:** the ASSUMPTION probe reversed one case. A project-scope entry whose `projectPath` is the home directory never applies; sessions under it load the user-scope install. `selectEntry` moved to the shared `plugin/bin/lib/installed-plugins.js` and gained an opt-in `excludeHome` that the superpowers resolver passes. Impeccable's call passes no options, so its rule is unchanged. Exact-match entries that still load the user install were observed but not encoded, and the module header records them. The shared helper also skips non-object entries, which Impeccable's `resolve()` used to throw on.
- **Notice copy:** the line ends with `— tell the user once, in your first reply; never run the update yourself`. SessionStart `additionalContext` reaches the model, not the user, so the line names its own relay, as #803 did for the residue banner. It also keeps an autonomous run from treating the update command as an instruction, which would update on the user's behalf against the Non-Goals. It is still one line.
