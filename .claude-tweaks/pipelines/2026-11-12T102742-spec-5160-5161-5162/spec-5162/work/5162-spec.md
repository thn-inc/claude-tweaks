# 5162: Review an existing CI workflow at init: draft skips, path filters, concurrency

Surface: infra

## Overview

The plugin's merge gate assumes a project's PR CI behaves a certain way: it runs on ready PRs, reports on every PR, and does not pile up superseded runs. Nothing checks that assumption. `/claude-tweaks:init` Step 16 classifies only the plugin's own generated `track-issue-fixes.yml`, and `merge-verification.js` detects only that a `pull_request` trigger exists. A workflow that skips draft PRs without re-running on `ready_for_review`, filters PR CI by `paths:` with no always-reporting job, or never cancels superseded runs goes unnoticed until the gate misreads it or the Actions bill grows.

This unit adds a deterministic, report-only review of a project's existing PR-triggered workflows: a new init bootstrap step on first run, and a report-only Update Mode drift row on re-run shaped like the Verify-Scope Drift row, both driven by one CLI with a `--drift --json` mode. It never edits a workflow. It reuses the workflow reader and the remedy convention doc that #5153 introduces rather than writing a second parser.

This is the third of three units from the CI cost visibility design (originally reported in #5154, from a private project). The first unit records CI wall time at the merge gate and the second reports run duration and Actions spend; neither blocks this one.

**Complexity:** Medium
**Estimated tasks:** 8

## Non-Goals

- Editing, regenerating or auto-remediating any workflow. Every finding is a report line citing the remedy in `_shared/ci-skips-drafts.md`.
- Reviewing the plugin's own generated `track-issue-fixes.yml`. Step 16 already classifies it (#5152), and the other init generators are tracked in #5158.
- Detecting or fixing the merge gate's read-after-`gh pr ready` race. That is #5153's behavior change; this unit only detects the workflow shapes that cause it.
- CI systems other than GitHub Actions. Detection stays GitHub Actions-only, matching `merge-verification.js`'s stated intent.
- Run-history analysis, durations or spend (the second unit).

## Release Note

## Technical Approach

The CLI is a thin wrapper over a pure findings function: `reviewWorkflows({workflows, verifyScope})` returns `{reviewed, findings[], unparsed[]}`, so every check is a fixture test. It consumes #5153's reader for trigger types, the draft reference and `unparsed`, and adds only what the five checks need beyond it (`paths:`/`paths-ignore:`, job-level and step-level `if:`, `concurrency`). If #5153's reader already exposes a field the checks need, use it rather than re-deriving it; if it does not, extend the reader in `merge-verification.js` (one parser, not two) rather than adding a parallel parse in the new module.

First-run and re-run share the one CLI: the step-22 bootstrap file calls it without `--drift` for a human-readable table, and the Update Mode row calls it with `--drift --json`, matching how Step 6.6 and its drift row share `init-verify-scope.js`.

### Data / API Surface

CLI: `node plugin/bin/ci-workflow-review.js --root . [--drift --json]`. `--drift --json` prints one line: `{reviewed: number, findings: [{workflow, check, remedy, detail}], unparsed: [{workflow, reason}]}`. `check` is one of `draft-skip-no-ready-for-review | draft-skip-with-ci-source | paths-filter-no-always-reporting-job | no-cancel-in-progress-concurrency | push-all-step-gated`. Exit 0 report, 1 invalid `verify-scope.json` or unreadable workflows directory (stderr carries the reason, stdout empty), 2 usage.

- Report-only is structural: the CLI and both init surfaces never write, edit or regenerate a workflow. The step-22 file states it, and AC9 tests it.
- A workflow the reader cannot parse is its own `unparsed` finding. Never collapse it into "no findings" (`.claude/skills/parse-signal-discipline/`): the drift row's parse failure of the CLI's own output is likewise its own finding, never "no drift".
- The workflow reader is line-based, not a YAML parser (no dependency exists); the checks must tolerate comments, flow and block forms, quoted keys and a leading BOM exactly as `workflowHasPullRequestTrigger` does, and must degrade to `unparsed` rather than guess.
- Check 2 is the draft-skip-plus-`ci`-source case #5153 rules a misconfiguration; detect it by joining the workflow named in `decl.ci[suite].workflow` (matching rule in Deliverables) to the draft-skip predicate. The declared `job` is not matched: any draft skip in the declared workflow fires it.
- Do not review `track-issue-fixes.yml`: Step 16 classifies it and #5158 tracks the other init generators. A project-authored workflow with the same shape is reviewed normally.
