# 5161: Report CI run duration, superseded runs and Actions spend from harness-health

Surface: infra

## Overview

No sweep reads a repository's workflow-run history, so a CI suite that triples in duration, a workflow that starts a runner on every push, a pile of cancelled or superseded runs, or an Actions budget approaching its hard stop all go unreported. This unit adds a deterministic, reporting-only CLI, `plugin/bin/ci-health.js` over `plugin/bin/lib/ci-health/`, and wires it into `/claude-tweaks:harness-health` Step 1 as one more deterministic check beside the composed-bytes and cost-efficiency checks. It reports per-workflow run counts and weekly duration percentiles, the p90 against the merge gate's 900-second watch, the superseded and cancelled share, push-triggered workflows that run on nearly every push, and Actions budget headroom when the token can read billing. It files an issue only on a threshold breach.

This is the second of three units from the CI cost visibility design (originally reported in #5154, from a private project). It is independent of the first unit (recording CI wall time at the merge gate) and of the third (reviewing a workflow file at init).

**Complexity:** High
**Estimated tasks:** 8

## Non-Goals

- Changing the merge gate's 15-minute watch. This unit single-sources the number 900 as a code constant that the gate's prose cites, and pins the two together; the watch value itself does not change.
- A CI-minutes efficiency budget ceiling in `lib/timing/budget.js`. This check reports and, on a breach, files; it sets no per-run budget.
- Per-repository spend. Spend is reported at organisation or user level only, because per-repo usage rows and the repo-filtered summary disagree, and `/timing`'s billable field reads 0 on public repositories.
- Recording the CI time of an individual merge (the first unit) or reviewing workflow files (the third unit).
- Fixing a workflow the check flags. It reports only.
- Adding a fifth health-sweep skill. The check runs inside the existing harness-health firing.

## Deliverables

- [ ] `fetch.js` reads `repos/{o}/{r}/actions/runs` with `--method GET`, `created=>={date}` (default window 30 days, `--days N`), `per_page=100`, paged to a cap of 10 pages (1,000 runs, GitHub's per-query ceiling), each call with an explicit 15 s timeout. Hitting the cap sets `truncated: true` in the envelope and renders `window truncated at 1000 runs: statistics cover the newest runs only`; a truncated window never files an issue. A 401, 403 or rate-limit answer on the runs read is a failed read named in `failures[]` with its status.
- [ ] `stats.js` computes per workflow: run count, whole-window p50 and p90 duration (nearest-rank percentiles over `updated_at` minus `run_started_at`, completed runs only; the API's run is its latest attempt, so a re-run counts once), and weekly p50 buckets for the trend. Buckets are consecutive 7-day windows anchored at the window start (UTC, by `created_at`); a trailing partial bucket is excluded from the trend but included in whole-window figures. `trend` = (p50 of the last full bucket) / (p50 of the first full bucket), labelled `rising` at 1.25 or more, `falling` at 0.8 or less, else `flat`; with fewer than two full buckets or fewer than 5 completed runs in either, `trend` is the literal `insufficient`.
- [ ] `stats.js` computes the superseded share: among a workflow's runs on non-default branches (keyed by `head_repository.full_name` plus `head_branch`), a run is superseded when its `head_sha` is not the head of the newest run by `created_at` for that key, whatever its conclusion; the share's denominator is that workflow's runs on non-default branches. It also counts `cancelled` runs, and flags push-triggered workflows: a workflow's distinct `head_sha` values among its `event: push` runs divided by the distinct `head_sha` values across every workflow's `event: push` runs, at or above 0.9 with at least 10 distinct push `head_sha` values in the window; below that sample floor, or with zero push runs, the rate is `null` and nothing is flagged. The flag is informational and never files an issue (a single push-triggered workflow trivially scores 1.0, which the report line notes).
- [ ] `constants.js` exports `MERGE_GATE_WATCH_SECONDS = 900`, the one code definition of the watch bound; the check compares each workflow's p90 against it.
- [ ] Task 0, before any billing fixture is written: read each billing endpoint once live (where the token allows), record the response field names, and commit fixtures with synthetic values only (never real amounts, plan names or organisation identifiers).

## Release Note

Added a reporting-only check to harness-health that shows workflow run duration trends, superseded and cancelled runs, and Actions budget headroom, and reports quietly when billing cannot be read.

## Technical Approach

Follow the `activity-gather.js` shape: a thin CLI that resolves owner and repo through `repo-resolve.js`, hands injected deps to a pure gather module, and renders a fixed report. Statistics are pure functions over a runs array so every acceptance case is a fixture. Billing is a separate module with its own result envelope so a billing failure can never degrade the run-history half; each half reports `{available, ...}` independently and the failures list names every query that did not complete.

The single-sourcing of 900 is a code constant plus a twin-pin test (the prose-code-twin-pin pattern in `.claude/skills/prose-code-twin-pin/`), not a runtime read: the gate's prose stays executable shell with the literal in place, and the test is what keeps the two equal.

### Data / API Surface

CLI: `node plugin/bin/ci-health.js [--days N] [--repo owner/name] [--min-headroom-pct N] [--file] [--json]`. JSON envelope: `{window: {days, from}, truncated, workflows: [{name, path, runs, skippedRuns, p50Seconds, p90Seconds, weeklyP50Seconds[], trend, superseded, supersededShare, cancelled, pushRunRate, pushesOnNearlyEveryPush}], watchSeconds: 900, billing: {available: true, scope: "org|user", headroomPct: number|null} | {available: false, status, reason}, failures: [{query, error}], breaches: [{kind: "p90-over-watch|headroom-below-floor", workflow?}], filed: {title, number}|null}`. Endpoints, all `gh api --method GET`: `repos/{o}/{r}` (owner type), `repos/{o}/{r}/actions/runs`, `organizations/{org}/settings/billing/usage/summary`, `organizations/{org}/settings/billing/budgets`, `users/{u}/settings/billing/usage`. Exit codes: 0 report (partial allowed), 2 usage or every read failed.

- `gh api` pagination and the `created=>=` filter need `--method GET`; follow `gh-api-module-pattern`'s three value mechanisms (`-f`, `-F`, path placeholders) and the `--end-of-options` argv separators so a repo name can never be read as a flag.
- A superseded run is defined against the newest head of the same non-default `head_branch` in the window; runs on the default branch are never counted superseded (every push there is a distinct commit to keep). State that rule in `stats.js`'s header comment.
- Rebase note: `_shared/pr-first-merge.md` is a hub file touched by about a dozen open records, including #5153 and #5106. This unit changes one sentence there; do not add `Blocked by` edges for them.

- Decided by the user at plan review: when every runs page fails, the CLI exits 2 whatever the billing read returns, and it still prints its full report (the billing line included) to stdout, so nothing it read is lost. A run whose runs half read at least one page and whose billing read failed stays exit 0 (partial). Supports: "every page failing exits 2" (Acceptance Criterion 7), read with "2 (usage, or every read failed)" as "every runs read failed".
- Build alignment (Common Step 4.5, beneficial deviations kept as built): the JSON envelope also carries `ghAbsent`, `minHeadroomPct` and `filingSkipped` (the skip reason under `--file`, else null); each `failures[]` entry is `{query, status, error}`; a `p90-over-watch` breach carries `path` beside `workflow`; `workflows[]` entries also carry `events`, `completedRuns` and `noWorkRuns`. - Decided by the user at review: the window is read one 7-day week per query; a week that still hits the 1,000-run cap is sampled from its newest runs and named in `truncatedRanges`, and a truncated window still files, with the issue body naming the sampled weeks (a failed runs read still files nothing).
