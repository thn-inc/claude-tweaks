# 5160: Record CI wall time at the merge gate

Surface: infra

## Overview

The merge gate reads a PR's checks but records nothing about how long its CI took. `timing.json` is written at wrap-up, before the merge, and the gate writes only `decisions.md` AUTO lines, so a suite that grows from 8 to 26 minutes leaves no trace in the run's timing data. This unit records one `ci-gate` event in the run's `events.jsonl` whenever `_shared/pr-first-merge.md` Step 2.5 reaches a verdict (green before merging, the Red path, or a timeout park), through a sanctioned writer CLI. `lib/timing/derive.js` turns the event into `totals.ciWallMinutes` and a `ciGate[]` list, and `phase-timing.js` renders one line for it.

This is the first of three units from the CI cost visibility design (originally reported in #5154, from a private project). It gives later analysis the data to tell apart the plausible causes of PRs that merged before their final commit's run finished: the draft-skip window (#5153), an explicit `merge-verification: off`, a cancelled run read as green (#3467), or a merge made outside the plugin. The 15-minute watch is not changed here.

**Complexity:** Medium
**Estimated tasks:** 8

## Non-Goals

- Changing the fixed 15-minute bounded watch (`DEADLINE=$(( $(date +%s) + 900 ))` in `_shared/pr-first-merge.md`). This unit produces the evidence for that decision; it does not make it.
- A CI-minutes efficiency budget or ceiling in `lib/timing/budget.js`. Record and report only.
- Recording CI time on the dispatch close-out path, which runs Step 3 without Step 2.5 (see Gotchas). That gap is stated, not closed, because #5153 reorders that path.
- Writing `timing.json` directly. `phase-timing.js` rewrites it from scratch, so the event is the only durable carrier.
- Workflow-run history, superseded-run counts or Actions spend (the second unit of the design) and reviewing a project's workflow files (the third).

## Deliverables

- [ ] A new sanctioned-writer CLI `plugin/bin/ci-gate-record.js`, built to `.claude/skills/gh-api-module-pattern/cli-wrapper-contract.md`: `run(argv, deps)` seam with injected runner, `--run` anchored under `$RUN_ROOT/.claude-tweaks/pipelines/`, exit vocabulary 0 (event written) / 2 (usage or unreadable input) / 3 (anchoring or write refused). It takes `--pr {n} --head-sha {sha} --verdict {green|red|timeout-park} --gate-start-epoch {seconds} --run {dir}`, reads the head runs through the injected `gh run list --commit` runner (explicit 15 s timeout, so a hung `gh` cannot hold the merge path), computes `gateWaitMs` as (writer's own `now` minus `--gate-start-epoch`) in milliseconds, and appends one `ci-gate` event through `appendEvent`. `verdict` and `pendingAtBound` come from the flags only and are never reconciled with the writer's own read.
- [ ] The `ci-gate` event shape: `pr`, `headSha`, `verdict`, `gateWaitMs`, `runsReadAt` (ISO time of the writer's `gh run list` read: the runs are a post-verdict snapshot and may differ from the evidence the verdict used), `runs[]` (each `{workflow, event, status, createdAt, startedAt, updatedAt, attempt, conclusion, databaseId}`, where `workflow` is the `workflowName` field; the workflow path is not fetched), `ciWallMs`, and `pendingAtBound` (present and `true` only for a timeout park). Persisting `event`, `status`, `conclusion` and `attempt` is deliberate: it lets a reader separate cancelled runs, non-PR events and re-attempts from real CI time later without changing the writer.
- [ ] `ciWallMs` = latest `updatedAt` minus earliest `createdAt` over head runs whose `status` is `completed`, whatever their `conclusion` (a cancelled or skipped run is included; its `conclusion` stays in `runs[]`) and whatever their `event`; `null` when there are none. `gh run list` returns each run's latest attempt, so a re-run counts once at its latest attempt. For a timeout park the value is a lower bound and `pendingAtBound: true` says so.
- [ ] `plugin/bin/lib/timing/derive.js` reads `ci-gate` events into `totals.ciWallMinutes` and a `ciGate[]` list (every event, in file order), adding the keys only when at least one event exists. `ciWallMinutes` is the sum, across distinct `pr` values, of each PR's latest event's `ciWallMs` (latest by file order) divided by 60,000 and rounded to one decimal exactly as `verifyMinutes` is (`Math.round(ms / 6000) / 10`); a `null` `ciWallMs` contributes nothing, and an absent event means "not recorded", never "fast" (state this in a comment beside the derivation).
- [ ] `plugin/bin/phase-timing.js` renders one line per run when `ciGate` is non-empty, in the form `CI gate: {verdict}, {ciWallMinutes} min wall{ (lower bound)}, gate waited {gateWaitMinutes} min (PR #{pr})` for each distinct PR's latest event, where the lower-bound marker appears when that event has `pendingAtBound` and `{ciWallMinutes}` is `n/a` when `ciWallMs` is `null`.
- [ ] `plugin/skills/_shared/pr-first-merge.md` Step 2.5 records the gate's start epoch (`date +%s` at its first state read, held in the gate's scratch directory beside `{pr-runs-path}` so it survives separate shell calls) and calls the writer at exactly two sites, each once per gate pass: at the green verdict before the merge attempt, and in the Red path where the park message is composed, passing `--verdict timeout-park` when the reason is `checks-pending-timeout` and `--verdict red` for every other Red reason. A non-zero writer exit logs a `SKIP` decision line and continues. The dispatch close-out gap is stated in prose there, and the prose says a re-entry into Step 2.5 (Red-path resume) is a new gate pass with its own call.
- [ ] Before writing the writer's anchoring tests, a probe run of `resolveTarget` against each refusal case in AC4; any case it does not refuse is filed as its own record through `/claude-tweaks:capture` (not fixed in this unit) and dropped from AC4's list.
- [ ] A test that `plugin/bin/lib/timing/budget.js` and every other reader of `totals` (the consumers are found by `git grep -n "totals\." plugin/bin`) give identical output with and without `ciWallMinutes` present.

## Release Note

Recorded how long a pull request's CI took at the merge gate, so a growing CI suite now shows up in run timing instead of going unnoticed.

## Technical Approach

The writer is the only code that calls `appendEvent` for this event kind, so the event schema lives in one module and the prose cannot drift from it. The call is made where Step 2.5 already holds `{owner}`, `{repo}` and `{headRefOid}`; the one new piece of state is the start epoch captured at its first state read and persisted in the gate's scratch directory, because shell state does not survive between the gate's separate commands. The writer re-reads the head runs itself rather than taking Step 2.5's read as input, which keeps the call shape small and independent of what #5153 and #5106 change in that read; the cost is that the runs are a post-verdict snapshot, which the event records as `runsReadAt`. Putting the data in `events.jsonl` rather than `timing.json` is forced: `phase-timing.js` rebuilds `timing.json` from scratch, and `events.jsonl` is already the input `derive.js` consumes.

The change is additive under the expand-contract rule: a new event kind and new `totals`/`ciGate` keys that older readers ignore, and an absent event changes nothing in today's output.

### Data / API Surface

`ci-gate` event, appended through `appendEvent(runDir, 'ci-gate', data, attribution)`:

```json
{"pr": 123, "headSha": "abc123", "verdict": "green|red|timeout-park", "gateWaitMs": 0, "runsReadAt": "...",
 "runs": [{"workflow": "CI", "event": "pull_request", "status": "completed", "createdAt": "...", "startedAt": "...", "updatedAt": "...", "attempt": 1, "conclusion": "success", "databaseId": 1}],
 "ciWallMs": 0, "pendingAtBound": true}
```

`gh run list --repo {owner}/{repo} --commit {sha} --limit 100 --json createdAt,startedAt,updatedAt,attempt,event,conclusion,status,workflowName,databaseId` is the single read. CLI flags: `--pr`, `--head-sha`, `--verdict`, `--gate-start-epoch`, `--run`, `--repo` (optional override, else resolved from `origin`). CLI exit codes: 0 written, 2 usage or unreadable input (including a failed `gh run list`), 3 anchoring or write refused.

## Gotchas

- Follow `.claude/skills/gh-api-module-pattern/` and its `cli-wrapper-contract.md` exactly: injected runner (`execFileSync`-based `gh`), the `run(argv, deps)` seam, anchored `--run` (a bare relative path from a worktree silently shadows the main checkout's run dir, `[IL-127]`), and the 0/2/3 exit vocabulary.
- The source-scan suites `tests/gh-host-seam-conformance.test.js` and `tests/exit-code-conformance.test.js` apply to any new `plugin/bin/` CLI: route every `gh` spawn through `repo-resolve.js`'s `ghOptions(args, opts)` and use only the allowed exit codes.
- Never write `timing.json` directly: `phase-timing.js` rewrites it from scratch (line 377), so the event is the only carrier.
- Write the event before post-merge Step 4.2 archives the run directory; a late write recreates an archived run dir.
- A writer failure must never block or delay the merge: the prose logs `SKIP {HH:MM:SS} — Step 2.5 (merge-verification gate): ci-gate not recorded ({error})` and continues. Verdict handling is unchanged.
- The dispatch close-out path runs Step 3 without Step 2.5, so it records no `ci-gate` event. State this gap in the Step 2.5 prose; do not close it here, because #5153 reorders that path.
- Rebase coordination: #5153 and #5106 (both `ready`, not started when this was filed) change the same Step 2.5 head-runs read and `plugin/bin/pr-checks.js`. Rebase onto whichever lands first; the writer makes its own `gh run list` read, so it needs no change when they reshape Step 2.5's read, only a re-anchoring of the two call sites. `_shared/pr-first-merge.md` is a hub file touched by about a dozen open records; resolve conflicts, do not add `Blocked by` edges for them.
- `plugin/bin/lib/timing/derive.js` is also touched by #5093, #5092, #5013, #4321 (in progress) and #4259. Keep the change to the `totals` object and one additive derivation so the rebase is mechanical.
- `ciWallMs` for a timeout park is a lower bound (a run was still pending), which is why `pendingAtBound` exists; the render line must say so rather than present it as a duration.
- `ciWallMs` is a span, not billable or summed run time: it includes queue time, idle gaps between runs, cancelled runs and runs of any `event`. That is deliberate (it is the time the gate could have been waiting), and `runs[]` carries `event`, `status`, `conclusion` and `attempt` so a later reader can narrow it. Do not filter at write time.
- The writer must stay a post-hoc recorder: the Red-path call is made after the park decision, so a write failure or timeout can never change a verdict. Two call sites, three verdict values: do not add a third call site for the timeout park.
- The bounded watch value (900 seconds) is single-sourced by the second unit of this design. This unit only reads verdicts and must not touch the watch literal.
- `pr-first-merge.md` is 37,852 B and Step 2.5 is already dense: add the three call sites as short bullets citing the writer, not a restatement of the event schema.
