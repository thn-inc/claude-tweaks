# 5277: drive.js reports CI before the pushed commit's tests have started

Origin: #5215 Phase 1 proof (PRs #5272, #5274, #5276)

Defer-reason: blocked-dependency

## Current State

`drive.js`'s CI step (`ciStep` in `plugin/bin/lib/driver/steps.js`, #5218) polls `pr-checks.js --pr {n}` only while the state is `pending`, then makes one `--run` read and records that state. It runs a few seconds after `gh pr create`, before GitHub has started the test workflow for the pushed commit.

In the Phase 1 proof on 2026-11-12 (#5215), all three records reached a draft PR and the CI step ended within about 5 seconds every time. For #4198 (PR #5272) and #4351 (PR #5276) it recorded `green` while the test shards had not started; they passed about two minutes later. For #3931 (PR #5274) the first poll was not `pending`, so the loop exited, and the one `--run` read a moment later already said `pending`, which became the record's final `ci` value.

The reads that ended the loop were taken while the only checks on the PR were fast workflows that had already finished or been skipped, so the rollup looked complete. The final event's `ci` and the outcome built on it therefore describe CI before it ran. #5226's merge step enters only when this step ends `green`, so it would act on the same early read.

## Deliverables

- [ ] The CI step treats a read other than `pending` as final only after a named settle window has passed since the push and the pushed commit has at least one workflow run. Before that it keeps polling, as it does for `pending`. "At least one run" alone is not enough: for #4198 the commit already had a finished fast workflow (`label-fix-branch`, skipped) when the test workflow had not yet been created, so the settle window is what closes that gap. A commit that still has no workflow run once the window has passed is recorded as `no-ci`. (Build note, Common Step 4.5 — Beneficial: "workflow run" means a GitHub Actions run, while the check rollup also carries commit statuses and third-party check runs. So a `red`/`inherited-red` read keeps its word rather than becoming `no-ci`. A `pending` read that names running checks keeps polling to the bound. `green` with no run stays `no-ci` per AC3. This is ratified or reversed at the Review Console as staged `sdd-ruling-2`.)

- [ ] `stale` keeps polling like `pending`, as #5218's Technical Approach states ("polls it while the state is `pending` or `stale`").

- [ ] The `steps.js` header states the settle window, its value and why it exists.

## Acceptance Criteria

1. Over a fake runner and a fake clock, a `green` read taken inside the settle window does not end the step, even when the commit already has a finished run: the step polls again, and a later `pending` then `green`, read after the window, makes the recorded state `green`.

2. The same holds when the early read is `no-ci`, and when it is `stale`.

3. When the commit still has no workflow run once the settle window has passed, the step records `no-ci` and the final event's `ci` is `no-ci`, not `green`.

4. The commit-run read uses the pushed sha (the `head` that `express-lane.js check` verified), never a branch name.

5. The existing CI-step tests in `tests/bin-lib/driver/run.test.js` pass, changed only where they relied on the early read ending the loop.

## Release Note

The pipeline driver now waits for a pull request's tests to actually start before it reports their result.

## Technical Approach

### Key Files

- `plugin/bin/lib/driver/steps.js` — the CI step waits for a run on the pushed commit; stale keeps polling
- `tests/bin-lib/driver/run.test.js` — pin the early-read cases and the grace-bound no-ci result
