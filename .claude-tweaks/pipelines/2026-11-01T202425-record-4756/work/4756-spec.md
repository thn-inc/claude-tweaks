# 4756: claim-targets: a network blip while bootstrapping the claims branch exits 6 instead of the transient exit 4

Blocked by #4495

Origin: #4495 review (sdd-ruling-1, PR #4723)

Defer-reason: genuinely-larger

## Current State

`claim-targets.js` bootstraps a missing `claims-registry` branch once per run (#4495, PR #4723). In `handleBranchMissing` (`plugin/bin/lib/claim-targets/claim-targets.js`), a bootstrap result that is `!ok && transient` (a secondary rate limit) takes the transient exit 4 path (`claims-branch-bootstrap-rate-limited`); every other `!ok` result exits 6 ("branch missing on origin and could not be created").

`classifyGhApiError` (`plugin/bin/lib/issues/claim-store.js`) recognises ENOENT, the secondary rate limit, 404, 422 and 409; everything else, a permission 403 or 401 included, becomes `failure: 'network-failure'`. So `ensureClaimsBranch` cannot tell a transport failure (network blip, timeout, 5xx) from a permission refusal, and a plain network blip during the bootstrap exits 6: the record is stopped as if the branch were permanently uncreatable.

#4495's review flagged this (5 lenses, tiebreak-confirmed, medium). The unattended Review Console ratified exit 6 as-is (sdd-ruling-1, run `2026-10-31T133106-record-4495`), because changing it needs the classifier split below.

## Deliverables

1. `classifyGhApiError` classifies a permission failure (HTTP 401, and HTTP 403 that is neither a secondary rate limit nor primary rate-limit exhaustion) as its own refusal outcome, distinct from `network-failure`. Every existing caller of `classifyGhApiError` / `defaultGhApi` keeps its current exit behaviour for a 403/401, or is updated deliberately with the change named in the PR.
2. `ensureClaimsBranch` reports a transport-class failure (`network-failure` after the split) as `transient`, so `handleBranchMissing` routes it to exit 4 with its own error name (for example `claims-branch-bootstrap-network-failure`), under `--keep-going` a skip, like the rate-limited case.
3. Every bootstrap failure is classified by one rule, stated in `classifyGhApiError`'s outcomes (after Deliverable 1's split) rather than as a list of HTTP statuses. The rule applies to every call the bootstrap makes: the default-branch read, the tip-sha read, the `POST git/refs` create, and the follow-up branch re-read. (Plan-review round 3: one rule replaces the case lists.)
   - **Transient (exit 4; a `--keep-going` skip):** `network-failure` and `secondary-rate-limit`. `network-failure` covers everything the classifier does not recognise: a transport error, a timeout, a 5xx, a primary rate limit (Deliverable 5), and any HTTP status it has no pattern for (a 400, say). Treating an unrecognised 4xx as transient is accepted; this record does not add patterns for more statuses.
   - **Refusal (exit 6):** the new permission outcome (401/403, Deliverable 1); `gh-absent`; every answer the classifier returns with a status and `failure: null` (404, 409 for example an empty repository, 422), except the lost-race 422 below; and the non-HTTP refusals unchanged from today (a repository that reports no default branch, a default branch that reports no tip sha).
   - **Lost-race 422:** a `POST git/refs` 422 whose follow-up re-read shows the branch exists is success, as today. A 422 whose re-read succeeds and shows no branch is a refusal (a ruleset). A 422 whose re-read fails takes the re-read failure's own class under this rule (Deliverable 6).
   - **Error names:** a `secondary-rate-limit` reports `claims-branch-bootstrap-rate-limited`; a `network-failure` reports `claims-branch-bootstrap-network-failure`, primary rate limit included. (Round 3, decision 1, Reading B.)
4. The exit-code prose that names exit 6 (`plugin/bin/claim-targets.js` usage, `plugin/skills/flow/claim-targets.md`, `plugin/skills/dispatch/settle-and-merge.md`, `plugin/skills/_shared/issue-claims.md`, `docs/plugin-structure.md`) states that a network failure during bootstrap is transient (exit 4), not exit 6.
5. A primary rate-limit 403 or 429 (`API rate limit exceeded`, or `X-RateLimit-Remaining: 0`) is classified `network-failure`, never the new permission outcome, as `plugin/skills/_shared/github-rate-limit.md` already treats it as transient. During the bootstrap it exits 4 with `claims-branch-bootstrap-network-failure`, never 6. (Plan-review decision 2, Reading B; error name pinned by round 3, decision 1, Reading B.)
6. Deliverable 3's rule applied to the 422 re-read: the bootstrap needs the re-read's failure kind, so it can no longer decide from `claimsBranchExists`'s bare `null`. A re-read that fails with `network-failure` exits 4 with `claims-branch-bootstrap-network-failure`; with `secondary-rate-limit`, exit 4 with `claims-branch-bootstrap-rate-limited`; with the permission outcome or `gh-absent`, exit 6. The existing claim-store test "POST git/refs 422 with an unreadable branches endpoint is a refusal" is rewritten to pin the transient outcome for a network-failure re-read. (Plan-review decision 1, Reading B; narrowed by round 2, decision 1, Reading B.)
7. Under `--keep-going` with two or more targets, a transient bootstrap failure on one target does not leave later targets reporting `claims-branch-missing`, which means a bootstrap that reported success. Each later target that finds the branch missing is skipped with the same transient error name the failed bootstrap produced (a `--keep-going` transient skip, like the rate-limited case today). (Plan-review round 2, reviewer note, added by the human.)

## Release Note

A network blip while the plugin creates the claims branch is now retried on a later run instead of stopping the record as if the branch could never be created.
