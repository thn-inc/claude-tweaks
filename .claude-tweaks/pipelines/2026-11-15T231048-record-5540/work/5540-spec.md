# 5540: Review tiebreak: one judge per chunk of findings instead of one per finding

Surface: backend

**Related:** #5148, #4663, #5535, #5214, #4708, #4672, #4828, #3835
Risk-flags: none

## Current State

`plugin/skills/review/step3-tiebreak.md` (Step 3.7 of `/claude-tweaks:review`) sends every finding still `unconfirmed` or `contested` to its own Capable-tier agent, in waves of 8 (`plugin/skills/review/step3-tiebreak.md:29`). Each agent starts fresh, so each pays its own starting context to judge one finding. Each verdict is then settled with two file writes and one `review-coordination.js resolve-tiebreak` call per finding (`plugin/bin/review-coordination.js:189`; #5148 reports 26 writes and 13 calls for 13 findings).

Measured on 2026-11-15 from archived runs (scratch scripts; re-derive before relying on a number):

- In 44 archived reviews, 529 tiebreak agents used 24.6M cache-creation tokens, about as much as one side of the paired lens reviewers in the same reviews.
- A replay judged 60 archived findings from nine reviews with one judge per review. It agreed with the archived verdict on 52 of 60 (87%). A control arm that reran one judge per finding on 14 of those findings agreed on 12 (86%), and the batched judge scored 12 of 14 on the same findings.
- For those 60 findings the archive shows 63 agents, 132k output tokens and 2.83M cache-creation tokens; the replay used 10 agents, 64k output tokens and 0.63M cache-creation tokens.

Design: `docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 2, unit 2.1 (branch `worktree-design-process-efficiency`).

## Deliverables

1. **Chunked dispatch.** Step 3.7 groups its entry set into chunks of at most 8 findings and dispatches one fresh agent per chunk. The prompt lists each finding with its id from `review-findings.json`, claim, severity, location and, for a contested finding, its positions. It tells the agent to judge each finding on its own. The reply carries one block per id with the same four lines as today (`Verdict`, `Evidence`, `Severity`, `Recommendation`).
2. **One settle call per chunk.** `review-coordination.js resolve-tiebreak` accepts a chunk: the chunk's entries and the agent's one reply. It splits the reply by id and runs the existing per-finding settle for each entry, so the outcome vocabulary, the evidence checks and each finding's log line are unchanged. An id missing from the reply, or present twice, resolves that one finding as an empty reply does today; the other findings settle normally. The chunk form settles per finding, not all or nothing, and writes exactly the per-finding artifacts the one-finding form writes today.
3. **The one-finding form keeps working, permanently.** A session on the previous release still calls `resolve-tiebreak` with one entry file and one reply file. That call form, its output and its exit codes do not change, and no removal is planned; a future removal gets its own record with a removal condition.
4. **Failure handling per chunk.** A chunk whose agent returns empty, fails, times out or ends without `DONE` is re-dispatched once as a fresh agent; valid blocks in a failed reply are discarded, not settled. If that fails too, each of its findings takes today's per-finding path (for a dispatched reviewer, the inline rung). A finding whose block is missing or duplicated in an otherwise good reply gets one single-finding re-dispatch, made before the chunk's `resolve-tiebreak` call, so the call settles a missing or duplicated id as can't-tell only after that retry has also failed. A finding therefore gets at most three judge attempts: the chunk agent, the chunk re-dispatch or the single-finding re-dispatch, and the per-finding path.
5. **Carried-over rules.** The lens 3f vacuity rule, the contested-finding positions, the post-fan-out untracked-file sweep and the "never reuse the reporting agent" rule apply per finding exactly as today.
6. **Replay proof.** Run the tiebreak replay harness over at least 20 archived reviews and put the table in the PR: agreement with archived verdicts for the chunked arm and for a one-per-finding rerun arm on the same findings, and tokens for each. The chunked arm uses the real chunking rule (at most 8 per chunk, in entry order), so reviews with more than 8 findings are included and exercise the split.
7. **Record link.** Comment on #5148 that its "resolve a wave in one call" request is delivered here.

## Release Note

`/claude-tweaks:review` now settles unconfirmed findings with one judge per group of up to eight findings instead of one judge per finding, which cuts the step's token cost substantially.

## Technical Approach

Keep the settle logic where it is. `plugin/bin/lib/tiebreak.js` already turns one entry and one reply into an outcome and a log line; add a reply splitter keyed on finding id and call the existing function once per entry. `plugin/bin/review-coordination.js` decides between the chunk form and the one-finding form from the shape of the entries file, so no new flag is needed: an array always takes the chunk form whatever its length (a one-finding chunk included), and the legacy single object is the only trigger of the old path; an empty or malformed entries file takes the one-finding form's existing error exit. If a flag is added anyway, check the audit simplification design's Phase 3 first: it moves every `plugin/bin` CLI onto one argument parser.

The prompt template in `step3-tiebreak.md` changes from one `Finding:` block to a numbered list of finding blocks, each headed by its id, and the reply repeats that id as a line-anchored header on each block. The splitter treats only a line-anchored header whose id is in the chunk's entry set as a block boundary, so an id quoted inside an `Evidence:` line is not a boundary; a test covers an id quoted in evidence. Within the existing wave rule, each wave dispatches up to 8 chunk agents in parallel, as it dispatches 8 finding agents today. Everything the agent is told about evidence, vacuity claims, read-only review, shell discipline and scratch stays.

Chunk order follows the entry set's order. Do not group by lens or by file: the replay did neither.
