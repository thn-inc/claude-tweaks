# 6374: Parse the three Blocked by forms in one module and keep ready off every path while a left-for blocker remains

Refs #6353, PR #6369.

Origin: review of #6353 (PR #6369), digest #5046

Defer-reason: genuinely-larger

## Current State

#6353 (PR #6369) added a third `Blocked by` form for a design part that another repository files later: `Blocked by: {part} (left for owner/name)`. The three forms are parsed in three places that do not share code:

- `Blocked by #N`: `DEP_RE` / `parseDependencies` in `plugin/bin/lib/issues/record-dependencies.js`
- `Blocked by owner/name#N`: `CROSS_REPO_DEP_RE` / `parseCrossRepoDependencies` in `plugin/bin/lib/issues/cross-repo-refs.js`
- `Blocked by: {part} (left for owner/name)`: `SYMBOLIC_LINE_RE` in `plugin/bin/lib/design-session/parts.js`

`plugin/bin/lib/issues/plan-line.js` also has its own `BLOCKED_BY_RE`, which covers the first two forms only.

Only `readyRestorable` (`plugin/bin/lib/issues/ambiguity-resolve.js:52`) checks for the `left for` line. `shapeGate` (`plugin/bin/lib/issues/materialize-format.js`) and its callers do not: the dispatch queue pull (`plugin/bin/lib/dispatch/queue-pull.js`), materialize (`plugin/bin/materialize.js`), compose `validateShaped` (`plugin/bin/lib/compose-record/compose.js`) and express eligibility. The prose paths that add `ready` do not check either: specify shaping stamping, planning-answer step (d), next-mode shape, the decomposition close-out write-back, and the red-team restore. So another path can mark a sub-issue `ready` before the other repository's part exists. With a grant it can then be dispatched. No blocker reader (queue pull, backlog funnel, /flow pre-flight 2.7b, materialize `blocked-by:` header, wrap-up newly unblocked, grant pre-pass, dispatch resume) sees the form at all.

The digest entry #6353's review wrote (#5046):

> [issues] The no-ready-with-symbolic-blocker rule lives only in readyRestorable; shapeGate and its other callers (queue-pull, materialize, compose validateShaped, the re-shape ready grant) never check the Blocked by: ... (left for owner/name) line, so another path can grant ready to a sub-issue whose blocking part is not filed yet. ## Deliverables

1. **One parser for the three forms.** A single module in `plugin/bin/lib/issues/` parses every `Blocked by` line in a body into typed entries: this repository `#N`, foreign `owner/name#N`, and symbolic `{part} (left for owner/name)`. `parseDependencies`, `parseCrossRepoDependencies`, `plan-line.js`'s blocker-line test and every `SYMBOLIC_LINE_RE` reader derive from it. `parts.js` keeps writing the line (`symbolicRef`) but reads it through this module. Change exported names by expand-contract: keep the old exports as thin wrappers until every caller has moved, and note when they can be removed.
2. **A ready-grant gate distinct from `shapeGate`.** It passes when `shapeGate` passes and the body has no symbolic blocker. `validateShaped` keeps accepting the line at create time. `readyRestorable` uses the gate, and so does every path that adds `ready` (derive the list with `git grep -n -l -e "add-label ready" -e readyRestorable -e "ready: true" -- plugin`; do not work from memory). Prose paths call it through a CLI exit code, not a restated rule.
3. **Every blocker reader sees the symbolic form and fails closed.** Follow the `blocker-surface-parity` project skill's surface table. A symbolic blocker always holds: it has no state to read, so it never counts as closed. It is named `{part} (left for owner/name)` the same way on every surface. Surfaces: dispatch queue pull (excluded), backlog funnel and overview (counted blocked), headless grant pre-pass (filtered), /flow pre-flight 2.7b and multi-spec order (stops), materialize `blocked-by:` header (listed), wrap-up newly unblocked (never listed), dispatch resume (not eligible). Cover both `work-links` modes and both transports, or say in the row which one the surface does not support.
4. Update `.claude/skills/blocker-surface-parity/SKILL.md` (the table's Parse row and rule 7) to name the one module and the ready-grant gate.

## Release Note

A design part that waits on another repository's part can no longer be marked ready, counted unblocked or dispatched before that part is filed.

## Technical Approach

### Key Files

- `plugin/bin/lib/issues/record-dependencies.js` — DEP_RE/parseDependencies derive from the one parser
- `plugin/bin/lib/issues/cross-repo-refs.js` — CROSS_REPO_DEP_RE/parseCrossRepoDependencies derive from the one parser
- `plugin/bin/lib/design-session/parts.js` — SYMBOLIC_LINE_RE read through the one parser
- `plugin/bin/lib/issues/plan-line.js` — BLOCKED_BY_RE derives from the one parser
- `plugin/bin/lib/issues/ambiguity-resolve.js` — readyRestorable uses the ready-grant gate
- `plugin/bin/lib/issues/materialize-format.js` — shapeGate and authoredText. The ready-grant gate (`readyGate`) was built in `ambiguity-resolve.js`, next to `readyRestorable`, and its CLI is `plugin/bin/ready-gate.js`. It lives there because `materialize-format.js` loads `record-payload.js` through `policy-schema.js`, and placing the gate in `materialize-format.js` would create a load cycle (build deviation, beneficial).
- `plugin/bin/lib/dispatch/queue-pull.js` — exclude symbolic blockers (through `record-dependencies.js`'s `partitionByOpenBodyBlockers`). `plugin/bin/lib/dispatch/queue-order.js` also stamps its persisted blob with `blockerRules`, so a cache written before this change misses once and cannot replay a symbolic-blocked record as eligible (build deviation, beneficial).
- `plugin/bin/lib/issues/backlog.js` — count symbolic blockers
- `plugin/bin/lib/backlog-grant-gate/backlog-grant-gate.js` — filter symbolic blockers
- `plugin/bin/lib/preflight-records/blocker-landing.js` — stop on symbolic blockers. Built in `plugin/bin/preflight-records.js`, which assembles the blockerLanding entries (build deviation, beneficial).
- `plugin/bin/materialize.js` — list symbolic blockers in the blocked-by header
- `plugin/bin/lib/wrap-up/pack.js` — never report a symbolic-blocked record newly unblocked
- `plugin/bin/lib/dispatch/resume-eligibility.js` — symbolic blocker is not eligible. Built in `plugin/bin/dispatch-resume.js`'s `readOpenBlockers`, which feeds the eligibility check (build deviation, beneficial).
- `plugin/skills/specify/shaping-mode-stamping.md` — cite the ready-grant gate
- `plugin/skills/specify/planning-answer.md` — cite the ready-grant gate
- `plugin/skills/specify/next-mode-shape.md` — cite the ready-grant gate. Left unchanged: Task 7's grep classification found that it adds no `ready` of its own (build deviation, beneficial).
- `plugin/skills/specify/decomposition-mode-closeout.md` — cite the ready-grant gate
- `plugin/skills/specify/red-team.md` — cite the ready-grant gate
- `.claude/skills/blocker-surface-parity/SKILL.md` — name the one module and the gate
