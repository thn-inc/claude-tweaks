# 5217: Headless worker launcher with per-role rights

Surface: backend

**Related:** #3937

## Overview

The pipeline driver (design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, section "Workers") starts a headless `claude -p` process only to write the change. This unit builds that launcher and the per-role rights it applies, and nothing that decides when to launch.

A spawned process inherits the user-level settings of whoever starts it, and those can carry broad allow rules, so `--allowedTools` cannot narrow a worker (allow rules add up). The launcher therefore gives each role a driver-owned settings file with `defaultMode: dontAsk` and a narrow allow list, never bypass mode, and a small starting context. It returns one envelope per launch: status, the structured result, the usage block, turn count and permission denials.

The unit also settles one open question from the design: whether `--max-budget-usd` takes effect under subscription login. The result is written down in the module and in the record's closing comment.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- Deciding when to launch a worker, building the prompt from a record, taking changed files from git, committing, testing or pushing (the run-loop unit).
- Acting on an envelope: settling, claim release or comments (the settle unit).
- Any worker that writes labels, comments, merges or runs `gh` or harness CLIs. No role in this unit or later ones gets those rights.
- Wiring a reviewer or explorer into a run: they are defined here and first used in a later phase of the design.
- Changing `claude` itself, the user's own settings, or any project settings file in the checkout.
- Changing `plugin/bin/lib/impeccable-engine/index.js`: `launchSpec` is imported from it in place, not moved.

## Prerequisites

None. This unit is independent of the admission unit.

## Acceptance Criteria

1. For the implementer role the composed argument list contains every flag named in the second deliverable. A test asserts, for every role, that neither `--dangerously-skip-permissions` nor the string `bypassPermissions` appears in the argument list or in the generated settings file.
2. The generated implementer settings file has `defaultMode: dontAsk`; its allow list is exactly these rules and no others: the `Read`, `Edit` and `Write` tools, `Bash({testCommand} *)` (a `testCommand` parameter, `node --test` for this repository; the named test files are given in the prompt, not in the rule), and read-only git as `Bash(git status *)`, `Bash(git diff *)`, `Bash(git log *)`, `Bash(git show *)` and `Bash(git ls-files *)`; its deny rules cover `gh`, `git push`, `git commit`, `git add` and network commands (`curl` and `wget` at least). A test pins the full allow and deny lists as exact arrays, so a widened allow list turns it red. The role has no `node`, `npm`, `sh`, `bash` or `python` rule other than the `testCommand` one.
3. The reviewer and explorer roles launch with `--restricted` and no `Bash` in their tool list.
4. At the wall-clock ceiling the child is killed and the envelope status is `timeout` with reason `wall-clock-ceiling` (fake runner that never exits, with a short ceiling). The runner contract is: it returns a handle with the child's `pid`, a `kill(signal)` method and a promise for `{ code, stdout, stderr }`; the real runner spawns detached on POSIX. On POSIX the kill reaches the child's process group (SIGTERM, then SIGKILL after a grace period of 5 seconds, a named constant); on win32 it runs `taskkill /T /F /PID {pid}`. The platform is a parameter, and each branch has a test. The envelope is returned only after the child has exited.
5. The envelope carries the usage block, turn count and each permission denial taken from the result. A result that does not satisfy the `--json-schema` schema yields status `fail`, reason `schema`; a non-zero exit of the child yields status `fail`, reason `exit`; a result with permission denials and a schema-valid result stays `ok`, with the denials in the envelope. A test pins the exported envelope field names, so a rename turns it red. The minimum schema is a `status` of `done` or `cannot-complete`, a one-line `title` and a one-to-two-sentence `summary`; the field names may be longer but these three facts are required.
6. After a result that reports permission denials, the launcher makes no second launch: a test asserts the runner is called exactly once and no argument list or settings file with a wider allow list is ever composed.
7. An opt-in live smoke test, skipped unless an environment variable is set so CI never spends tokens, reproduces the probe in a temporary directory: the write runs, and `echo > file` and `curl` are each denied, so the result reports at least one denial for each.
8. The `--max-budget-usd` result under subscription login is written in the module's header comment as literally observed, with the CLI version, date and login type, and is the content of this record's closing comment. The spend-ceiling code path matches it: pass-through (status `fail`, reason `spend-ceiling` when the CLI stops the worker) when effective, post-return comparison (`spendOverrun: true`, status unchanged) when not. Both branches are tested whichever one is live.
9. The windows launch of `claude` is spawned per `.claude/skills/windows-checkout-test-parity`: `platform` and `env` are parameters, the launch spec has an exact-string pin for the win32 shape, and a failure to launch (including a flag the installed CLI does not know) is reported as `fail`, reason `launch-error`, with the launch error named, never as a worker result.
10. The launch environment is built from an allow list of variable names (seeded from Task 0 (f)); a test asserts the `env` the runner receives contains only allow-listed names and excludes `PIPELINE_RUN_DIR`, `CLAUDE_CODE_SESSION_ID`, `GH_TOKEN` and `GITHUB_TOKEN` even when they are set in the parent environment.
11. Two concurrent launches never share a settings file: the launcher owns a per-launch file name under `settingsDir` and removes it when the envelope is returned (a test launches two with a fake runner and asserts distinct paths and removal).
12. Containment of code the test command runs. Task 0 gains an escape probe: with the implementer launched as specified and Claude Code's Bash sandbox turned on in the generated settings (network access denied, writes confined to the working directory; the settings keys are taken from the installed CLI during Task 0), the worker writes and runs a test file that shells out to `curl`, `gh` and `git push`, and the probe records which of the three were reachable. If none was reachable, the generated implementer settings turn the sandbox on for every launch and a test asserts those keys are present. If any was reachable, `Bash({testCommand} *)` is removed from the implementer allow list (the worker only edits, and the driver's own scoped test run judges the change), criterion 2's allow list is amended to match, and a test asserts no rule on the implementer allow list can execute a file the worker wrote. Either way the module header states the probe's literal result and this residual: the driver's own test step runs worker-written code with the driver's rights, as every other lane does today.

## Release Note

Added the headless worker launcher the upcoming pipeline driver uses, with narrow per-role permissions.

## Technical Approach

- **Narrow rights, never bypass.** The settings file is generated by the driver, not read from the project, and passed with `--setting-sources project --settings <file>`, so user-level allow rules do not apply. A denial is counted and reported; the allow list is tuned between runs from that data. There is no code path that retries with wider rights. Decision: the test command stays on the implementer allow list and the worker's Bash runs under Claude Code's sandbox, subject to Task 0's escape probe; if the probe shows `curl`, `gh` or `git push` reachable from a test under the sandbox, the test command is dropped from the allow list instead (acceptance criterion 12).
- **Settings file.** The generated file is per launch, written under `settingsDir` with a unique name, and removed when the envelope is returned. Task 0 (e) decides whether `--setting-sources project` is kept: the checkout's own project settings are the settings a worker in this repository would load.
- **Allow list derivation.** The implementer's rules are fixed by acceptance criterion 2. The test command is allowed as a prefix rule because a permission rule cannot name the files; which files the worker should test is part of the prompt, and the driver's own scoped test run is what the change is judged by.
- **Small starting context.** `--safe-mode`, a short `--tools` list, `--disable-slash-commands` and `--strict-mcp-config`. The project's `CLAUDE.md` text is read by the launcher and passed explicitly; the design keeps workers on `CLAUDE.md` whole and treats trimming as a later experiment.
- **Injected runner, async.** The runner is a spawn, not `execFileSync`, because the wall-clock ceiling needs to kill a live child. Follow `.claude/skills/gh-api-module-pattern`'s injectable-runner seam and its async-fan-out sibling. A fake runner in tests emits a canned result, exits non-zero, or never exits.
- **Windows.** Import `launchSpec` from `plugin/bin/lib/impeccable-engine/index.js` (`plugin/bin/lib/impeccable-engine/index.js:90`) in place; that module is not changed. Tests build expected strings by hand rather than through the code under test.
- **CLI version.** The flags are probed on one CLI version. The version, date and login type go in the header comment next to the Task 0 results; an installed CLI that does not know a flag fails the launch (`launch-error`), and the opt-in smoke test is what detects a changed behavior on a newer CLI.
- **Structured result, never trusted.** The implementer returns a status, a one-line change title and a one-to-two-sentence summary through `--json-schema`; the schema's field names are the builder's. The driver takes changed files from git, not from the worker (the run-loop unit).
- **Spend ceiling outcomes.** When `--max-budget-usd` is effective, a worker stopped by it is envelope status `fail` with the reason naming the spend ceiling. When it is not effective, an overspend is reported in the envelope and does not change the status; the wall-clock ceiling is then the only hard stop.

### Data / API Surface

- `launchWorker({ role, cwd, prompt, ceilings: { wallClockMs, spendCeiling }, testCommand, claudeMdText, settingsDir, platform, env }, runner)` returns `Promise<Envelope>`; names are the builder's.
- `Envelope`: `{ status: 'ok' | 'fail' | 'timeout', reason, result, usage, turns, denials, spendOverrun, ... }`; fields may be added later, never renamed, and a test pins the names. The names and the post-Task 0 shape are written in the module header so the run-loop and settle units consume a stated contract.
- `roles.js` exports the role table: for each role, its tool list, its flag set and a function building its settings object.

- `plugin/bin/lib/driver/roles.js` — new: per-role launch definitions and settings

## Gotchas

- ASSUMPTION — verify at build: `--max-budget-usd` takes effect under subscription login — confirm via Task 0's probe, and write the observed result into the header comment either way.
- ASSUMPTION — verify at build: the worker's JSON result exposes the usage block, turn count and cost figure under stable field names — confirm via Task 0's captured result, and build the fake-runner fixtures from it.
- The permission denials of a worker are data for the driver's event line, never a signal to widen rights. The allow list is tuned from the counts between runs, by a person.
- Never pass `--dangerously-skip-permissions` or `--permission-mode bypassPermissions`, for any role, in any phase: every worker in every phase, including the later judgment workers, runs no `gh`, writes no label, posts no comment and merges nothing (design, "Workers").
- The record body a worker receives is untrusted input; the narrow rights and the driver's own diff-bounds check are what contain it. Do not add prompt wording that asks the worker to refuse instructions as a substitute for rights.
- The Related record (#3937) is about hook writes from a nested `claude -p` session being attributed to the parent run, which can happen when the nested session inherits an exported `PIPELINE_RUN_DIR` or the parent's session id. Compose the launch environment explicitly: pass an `env` to the runner built from an allow list of variable names, and do not export `PIPELINE_RUN_DIR` or the parent's session variables to the worker. Task 0 also records whether `--safe-mode` keeps the plugin's hooks from running in the worker.
- The temporary directory Task 0 probes in is deleted whether the probe confirmed or reversed the assumed behavior.

## Plan Review Clarifications

- Decided by the user at plan review: the test-command rule and the Bash sandbox apply only on platforms where the escape probe ran (macOS when this was built). On every other platform the implementer has no test-command rule and no sandbox block: the worker only edits and reads git, and the driver's own scoped test run judges the change. This refines criteria 2 and 12, which read "its allow list is exactly these rules and no others" and "If none was reachable, the generated implementer settings turn the sandbox on for every launch".
- Decided by the user at plan review: a non-zero exit of the child with nothing on standard output is `fail`, reason `launch-error`; a non-zero exit that printed a result object, or other output, is `fail`, reason `exit`. This refines criteria 5 and 9, which read "a non-zero exit of the child yields status `fail`, reason `exit`" and "a failure to launch (including a flag the installed CLI does not know) is reported as `fail`, reason `launch-error`".

## As Built

Where the build departs from the text above under the authority the second deliverable gives Task 0, or adds to it without changing its intent:

- The implementer launches with `--restricted` in place of `--setting-sources project`: Task 0's probe (e) showed a project-level allow rule in a trusted checkout widened the worker under `--setting-sources project`, and did not under `--restricted`.
- The prompt travels on standard input and the project's `CLAUDE.md` text through `--append-system-prompt-file`, so neither is on the command line. The runner contract therefore also takes `input`, and its promise also carries `signal`.
- The envelope carries two fields beyond those the third deliverable lists: `costUsd` (the result's cost figure) and `detail` (a short description on `fail` and on a child that survived the kill).
- The launcher refuses, before it writes anything: a working directory or settings directory that is not an absolute path, a settings directory equal to or inside the working directory, a prompt that is not a string, an empty platform, a wall-clock ceiling that is not a positive number within the timer's range, and a schema keyword it cannot check. A structured result whose title spans more than one line is `fail`, reason `schema`.
- The opt-in live smoke test goes beyond criterion 7: it also checks that a Write into `.git` is denied and that `.git/config` and `.git/hooks` are unchanged after two `git log --output` attempts.
- Criterion 4 has one exception (ratified at the Review Console): after the kill at the wall-clock ceiling the launcher waits `REAP_DEADLINE_MS` (5 seconds) for the child to exit. If it has not, the envelope is returned as `timeout` / `wall-clock-ceiling` with `detail: 'child {pid} did not exit after kill'`, while the child may still be alive. On win32 the deadline starts when `taskkill` is started. A launcher that waited without bound would hang the driver that called it.
- Task 0's item (e) is half done (ratified at the Review Console): the project-level rights-leakage probe ran and is why every role launches with `--restricted`. The user-level half did not run, because a scratch home directory has no subscription login and a worker launched there stops at "Not logged in" before any rule is consulted. It is an unprobed residual, stated in the `roles.js` header; `--restricted` is expected to ignore user-level rules as it ignored the project-level one, but that is not shown.
- Criterion 12's "writes confined to the working directory" is narrower than what was observed (ratified at the Review Console; Claude Code CLI 2.1.322, macOS, 2026-11-12). Network access was denied, and writes under the system temporary directory, to `.git/config` and to `.git/hooks` failed. A write under the CLI's own per-user scratch root in `/tmp` succeeded, and reads are not restricted: code the worker ran read files under both temporary roots and listed the home directory. Both are stated residuals in the `roles.js` header.
