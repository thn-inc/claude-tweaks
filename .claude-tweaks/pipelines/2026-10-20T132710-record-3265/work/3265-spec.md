# 3265: visual-decide stop leaves no server-stopped marker when the daemon exits without running its SIGTERM handler (win32)

**Related:** #3130, #3071, #3027

Origin: #3130 wrap-up staged finding (wrap-up-skill-1), run 2026-10-16T155630-record-3130

Defer-reason: tangential

## Current State

`cmdStop` in `plugin/bin/lib/visual-decide/cli.js` sends `SIGTERM`, then `waitFor`s until either the `server-stopped` marker exists or `!pidAlive(info.pid)`. It writes the marker itself (`writeStoppedMarker`) only when `waitFor` times out, which is the zombie-PID case #3130 fixed.

On win32, `process.kill(pid, 'SIGTERM')` terminates the daemon unconditionally and its `SIGTERM` handler (`process.on('SIGTERM', stop)`, which writes `server-stopped`) never runs. `waitFor` then settles through `!pidAlive`, `settled` is true, and no marker is written. After a clean `stop`, `status` can then report the server as crashed rather than stopped. The same holds anywhere the PID dies without running its handler, such as SIGKILL by an outside actor between the signal and the poll.

The stuck-PID test in `tests/bin-lib/visual-decide/cli.test.js` is skipped on win32, and CI is ubuntu-only, so nothing exercises this path today. Reasoning from documented Node behavior; not observed on a Windows run.

## Deliverables

- In `cmdStop`, write the `server-stopped` marker whenever the wait settles without the marker present (PID gone or timeout), not only on timeout, so `stop` always leaves the marker behind.

- Add a platform-independent test: simulate a daemon whose PID disappears without writing the marker, and assert `stop` leaves `server-stopped` in place and `status` reports stopped.

### Key Files

- `plugin/bin/lib/visual-decide/cli.js` — `cmdStop` marker write
- `tests/bin-lib/visual-decide/cli.test.js` — handler-less exit case

## Acceptance Criteria
