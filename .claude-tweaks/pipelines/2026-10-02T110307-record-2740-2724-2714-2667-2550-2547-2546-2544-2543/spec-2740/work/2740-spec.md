# 2740: build: SDD reviewer dispatches lack a tree-immutability rule and the first-line status token

Surface: infra

## Current State

Task reviewers dispatched by `/claude-tweaks:build`'s subagent-driven-development (SDD) loop (`plugin/skills/build/dispatch.md` and related SDD prompt composition) are told they are read-only but not how to run a discrimination check safely, and none of the SDD templates demand the Subagent Contract's first-line status token — so one reviewer reverted a file in the shared worktree, and every SDD subagent reply this run was logged as a `contract-violation`.

A multi-spec `/flow` run in one shared worktree: a task reviewer wanted to prove a new test discriminates, so it ran `git checkout -- <source file>` in place, watched the test fail, and restored the file — the tree ended up clean, but a concurrent implementer on the same worktree would have lost its edit, and the controller only noticed by reading the report. Separately, the run's `friction-events.js` output listed 15 `contract-violation` events, all of them SDD subagents whose first line was a markdown heading ("### Spec Compliance", "## Strengths", "### Finding Verdicts") or an in-body "Status: DONE" — the templates never ask for the DONE/DONE_WITH_CONCERNS/NEEDS_CONTEXT/BLOCKED first line (the Subagent Contract's own required status line, `_shared/subagent-output-contract.md`), so the detector fires on every one and the Friction lens has to discount them by hand.

## Deliverables

- Every reviewer dispatch composed by `/build`'s SDD loop states explicitly: "never mutate the working tree — a discrimination check that needs a reverted or edited file runs in a scratch `git worktree add`, never in place." This is a prompt-text addition to the reviewer/re-review dispatch composition, not a mechanical enforcement (SDD reviewers run in a shared worktree by design, so this is a stated rule the agent must follow, the same way other read-only dispatch constraints in this codebase are prompt-stated rather than sandboxed).
- Prepend the Subagent Contract's first-line status-token requirement (`DONE`/`DONE_WITH_CONCERNS`/`NEEDS_CONTEXT`/`BLOCKED`) to the SDD implementer/reviewer/re-review templates, so their replies satisfy the same contract every other dispatched subagent in this codebase already follows.
- Confirm the `friction-events.js` `contract-violation` detector recognizes the corrected SDD templates' status line correctly after the template change (it should stop over-firing once the templates comply, with no detector change needed — verify this rather than assuming it).

## Acceptance Criteria

- The SDD implementer, task-reviewer, and re-review prompt templates in `/build`'s dispatch composition each open with the required status-token line and state the tree-immutability rule (scratch worktree for any discrimination check that needs to revert/mutate a file).
- A fresh SDD dispatch run produces zero `contract-violation` events attributable to a missing/malformed status line on an SDD subagent reply.
- `npm test` passes.

## Release Note

Made review subagents leave the working tree untouched and open their reply with a status line.

## Technical Approach

Locate every SDD dispatch prompt composition site in `plugin/skills/build/dispatch.md` (and any sibling file it delegates to for implementer/reviewer/re-review prompt text) and add both requirements inline in the composed prompt block itself — per `docs/skill-authoring.md`'s "Everything the agent must satisfy goes inside the inlined block" rule, a requirement stated only in the surrounding skill prose never reaches the dispatched agent. Cross-reference `_shared/subagent-output-contract.md` for the canonical status-token wording rather than inventing new phrasing.

### Key Files

- `plugin/skills/build/dispatch.md` — the SDD dispatch composition site(s) needing both additions
- `plugin/skills/_shared/subagent-output-contract.md` — canonical status-token wording to reuse verbatim
- `plugin/bin/friction-events.js` (or wherever the `contract-violation` detector lives) — verify, don't just assume, that it correctly recognizes the corrected templates' status line post-fix

## Gotchas

- The tree-immutability rule is prompt-stated, not mechanically enforced — a reviewer that ignores the instruction can still mutate the shared worktree; this record's fix reduces the chance of a repeat, it doesn't eliminate the underlying shared-worktree risk architecturally.
- Don't assume the `contract-violation` detector itself is broken — the 15 false positives this session came from the templates never emitting the required first line at all, not from the detector misreading a compliant line. Verify the detector's behavior against a corrected template rather than also rewriting detector logic that may already be correct.
