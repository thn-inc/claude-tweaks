# 4834: hooks.js: decide whether an unknown-flag refusal should exit non-zero

Surface: terminal
**Related:** #4777, #4318, #3646, #3721, #3875, #3975, #3976, #4353, #4548, #4576, #4772, #4798

## Current State

Since #4777 every `plugin/bin/hooks.js` verb refuses an undeclared flag before its handler runs. The guard in `main()` prints `claude-tweaks: usage: {usage}` on **stdout** and returns **0**: the #1012/#1143 shape. `tests/hooks-help-guard.test.js` pins it for `--help`/`-h`, and `tests/hooks-js-flag-strict.test.js` and `tests/archive-run-verb.test.js` pin it for undeclared flags. One branch serves two different requests:

- `--help` / `-h` anywhere in the argument list: the caller asked for usage, so stdout and exit 0 are right.
- An undeclared `--flag`, or a declared value flag followed by another `--` token (the value-position refusal, `firstUnknownFlag`): the caller made a mistake, but the reply looks like success.

The second case is silent for two kinds of caller:

- A caller that captures stdout as a value. `RUN_ROOT=$(node … hooks.js resolve-run-dir --root-only --typo) || exit 1` gets the usage line as its path and does not stop.
- A caller that stops only on a non-zero exit, as skill prose does around `check-pass-reentry`, `close-run` and `resolve-console`.

The same file already treats an unknown **verb** as an error: `main()` writes `claude-tweaks: unrecognized hooks.js subcommand '{cmd}'` plus the usage listing to stderr and returns 1 (#1586). An unknown flag on a known verb is the same class of caller mistake, yet it answers like a successful `--help`.

The #4777 caller audit found no caller in `plugin/` that passes an undeclared flag to a hooks.js verb, so no shipped call path changes behavior. Only a mistyped call does. Harness-dispatched hook events (`EVENTS`) never reach this guard: it runs only for `VERBS` entries. The never-break-a-session exit-0 rule (`docs/hooks.md`) is therefore untouched.

   - Any other refusal: an undeclared flag, or a value flag followed by a `--` token. Write nothing to stdout. Write two lines to stderr: a first line naming the problem, then the usage line. Return 1.

## Release Note

A mistyped flag on a claude-tweaks run-management command now fails with exit 1 and an error on stderr, instead of printing usage and exiting 0 as if it had succeeded.

## Technical Approach

The design choice: `--help` and `-h` are requests and keep the #1143 shape. A mistyped flag is an error, so it takes the shape the same file already uses for a mistyped verb (#1586): stderr, a first line naming the problem, exit 1. The rule is uniform across all verbs. A per-verb choice (exit 1 only for value-returning and gate verbs) was rejected. It would add a third per-verb table next to `VERBS` and `KNOWN_FLAGS`, and it would leave the advisory `check-*` verbs answering a caller's mistake with exit 0.

Exit 1 rather than the conventional usage-error 2: every existing refusal in this dispatcher exits 1, and skill prose already treats exit 1 as a stop. A second non-zero code would carry no information any caller reads.

## Gotchas

- Do not route `--help` through the new error branch. #1143 pins `--help` exiting 0 on stdout for every verb, and agents use it to read a verb's arguments before running it for real.
- The guard must stay ahead of `resolveRunArg` and every lib call. Moving the refusal to stderr must not move it later in `main()`, or a mistyped flag could again touch `run-state.json` before refusing.
- Callers that discard stderr (`2>/dev/null`) see only the exit code. That is the intended signal; never echo the refusal on stdout as a fallback.
- `EVENTS` dispatch (harness hooks) must stay outside this guard. A non-zero exit there would break the never-break-a-session invariant.

## Build Clarifications

- Architecture alignment (Beneficial, /build Common Step 4.5): the two refusal lines are written with `fs.writeSync(2, …)` inside one `try { … } catch {}`, and the branch still returns 1. If stderr is unusable (closed with `2>&-`: EBADF; or EPIPE), the refusal still exits 1. Without the catch, the throw would reach the entry's `.catch(() => process.exit(0))` and become the silent exit-0 shape this record removes. `tests/hooks-js-flag-strict.test.js`'s `#4834: an unusable stderr still refuses with exit 1` pins it.
