# 5706: wait-for.js never reports a child whose transcript quotes <task-notification> outside a completion carrier (pending: null)

## Current State

`wait-for.js agents` (shipped by #5602) decides that a child agent is finished from the stop marker the `SubagentStop` hook writes: one `{agentId, at, blocked, pending}` line per stop in `ct-agent-stops-{session}.jsonl`. A stop counts as final only when `pending` is `0`; `pending: null` and `pending` above 0 are both "not final".

The hook takes `pending` from `countPendingDispatches` (`plugin/bin/lib/hooks/subagent-stop.js`), the count #3015 wrote for the contract gate. That scan returns `null` for the whole transcript as soon as any line holds the literal `<task-notification>` outside a carrier it recognizes (the `return null; // a notification in a carrier not recognized above` branch). #3015 chose that fail-closed rule for the gate, where `null` means "grade as before".

For the marker the same rule fails the wrong way. The text that tells an agent how to wait quotes the token: the Async-wait item in `plugin/skills/dispatch/task-prompt.md`'s Context pack, which reaches every dispatched call and which an agent is told to forward to every agent it dispatches, and `plugin/skills/_shared/subagent-dispatch-core.md`'s Foreground Execution Discipline section. So:

- A dispatched child's own prompt (the first user message of its transcript) quotes the token, and every stop of that child is written with `pending: null`.
- An agent that reads a skill file quoting the token gets it in a tool result line.
- An agent that forwards the wait rule writes the token into its own `Agent` tool call, an assistant line. These are the agents that have children to wait for.

The late whole-branch review of #5602 tallied real stop payloads and found about 6% of stops with `pending: null`. For those children `wait-for.js agents` returns `bound: "call"` until the 20-minute window ends, which is the wait the `sleep 20` loop gave. #5604 switches the wait instructions to `wait-for.js`, so it should not ship while this holds.

`recordStop` and `grade()` share one count through `memo.pending`, so a stop parses its transcript once. `tests/hooks-subagent-stop-marker.test.js` pins the marker's `pending` to `countPendingDispatches` on fixtures that never quote the token; `tests/hooks-subagent-stop.test.js` holds the #3015 gate tests.

Separately (#5707): `tests/bin-lib/wait-for/marker.test.js`'s `AC10.3: a symlink, a dangling one included, is refused unread` skips on win32 with the reason "creating a symlink needs a privilege on win32". Nothing measured that claim, and `.claude/skills/windows-checkout-test-parity/SKILL.md` says CI allows symlinks (#5380). `.github/workflows/windows-regression.yml` runs on pushes to `main` and on `workflow_dispatch`, never on a pull request.

**Decision (author, 2026-11-16).** The stop marker gets its own count; the contract gate keeps #3015's rule unchanged. The marker's count does not treat the agent's own prompt (the first user message), or any other text the agent was given rather than received as a completion, as an unrecognized `<task-notification>` carrier. A `<task-notification>` in a carrier that is unrecognized after the prompt still yields `null` in both counts. Reason: the gate's fail-closed rule decides whether a reply is blocked, and nothing measured says it is wrong; the marker only decides when a wait returns, and its failure mode is a wait that never sees a finished child. Two counts with one shared scan keep the gate's behaviour byte-for-byte. This record is built before #5604. Its pull request also runs the windows-regression workflow on the branch head and settles #5707 with the result for `tests/bin-lib/wait-for/marker.test.js`.

## Technical Approach

Keep one scan function and let it produce both answers. The simplest shape: the loop in `countPendingDispatches` moves into an internal function that tracks two "indeterminate" flags, one per count, and returns `{ gate, marker }`. Every `null` return that both counts share sets both flags; the unrecognized-carrier branch sets the gate flag always and the marker flag only when the line is none of the three skipped shapes. `countPendingDispatches(lines, replyIndex)` stays exported and returns `gate`, so its callers and tests see no change. `grade()` stores both in the memo (`memo.pending` for the gate, a second key for the marker), and `recordStop` reads the marker key, computing both when `grade()` returned before the count.

Why skipping is safe for the marker: a skipped line is never a completion, so skipping changes neither the launch list nor the completed set. The marker count can only move from `null` to a number, and that number is never below the true pending count. A real completion always reaches the agent from the harness, in an origin-shaped entry or a `queued_command` attachment; it never arrives as the prompt, a tool result or the agent's own output (the header comment's source 6 already states the tool-result half).

The first user message is identified by position and shape, not by content. A forked agent's transcript holds the parent's history before the fork boundary, where the scan already resets; the build decides with a fixture which user message is a fork's own prompt.

The tally for Deliverable 1 is a scratch script, not a shipped tool: it runs the scan over each subagent transcript at the reply index the hook would use and groups the `null` results. It is not committed.

For Deliverable 5, `windows-regression` on `workflow_dispatch` compares against the merge-base with the default branch and files an issue only on `main`, so a branch run reports without filing.
