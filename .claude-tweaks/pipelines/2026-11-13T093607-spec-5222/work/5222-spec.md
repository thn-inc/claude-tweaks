# 5222: Driver reviewer step: one read-only reviewer whose findings count only with a failing test

Surface: backend

## Overview

The pipeline driver (design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, section "Phase 4 — One reviewer, wider lane") takes a named record to a green draft PR. This unit adds one reviewer worker between the passing test run and the push. The reviewer returns findings; a finding counts only if it comes with a test file that fails. The driver writes that file into the worktree, runs the project's test command on that one file, and treats a red run as a confirmed finding. A green run, a run that fails to load, and any evidence that is not a test file are discarded. The driver never executes a command string a reviewer supplies.

A confirmed finding gets one fix round: the implementer worker is started again with the finding and the failing test, then the commit, the scoped test run and `express-lane.js check` run again, with the evidence test kept as a regression test. A test still red after that round, or a diff now out of bounds, escalates the record with a reason naming the finding. With no confirmed finding the run proceeds to the push.

The step is controlled by a policy value with three settings: off, on, and on only for records beyond the express bounds (the default). Records inside today's express bounds therefore run exactly as in Phase 1. This unit registers that key; the lane bounds that make a record "beyond" admissible are the next unit's. Until that unit widens a bound, no record the driver admits is beyond the express bounds, so under the default the step does not run in a real run; this unit's tests run it with the always-on setting, and the next unit adds the end-to-end check that a widened record passes through the review step before the push.

**Complexity:** Medium
**Estimated tasks:** 8

## Built alongside #5226 and #5229

#5218 builds the run loop as a step table: `steps.js` exports `STEPS`, an ordered array of `{ name, run }`, and `run.js` walks it (#5218, criterion 13). This unit adds the review step as one `STEPS` entry after `check` and before the push, with its logic in `review.js`. The fix round runs inside the review step by calling the existing commit, scoped-test and `check` step functions again, and the step updates the context's `head` and runner pass stamp from the second `check`, which is how criterion 15's push guard sees them. It does not change the loop in `run.js`, which changes only if the stop handling needs a case it does not have. That keeps this unit from colliding with #5226 (a merge step after the CI wait) and #5229 (a budget loop around the per-record path), which are built at the same time. Step and outcome constants added to `events.js` are appended, never reordered.

## Acceptance Criteria

1. The reviewer is launched through the launcher with the `reviewer` role. Its composed argument list contains `--restricted`, its tool list contains no `Bash`, and neither `--dangerously-skip-permissions` nor `bypassPermissions` appears in the argument list or in a generated settings file (a test over the real `roles.js`).
2. The reviewer's result must satisfy the finding schema: an array of findings, each with a string `path`, an integer `line` of at least 1, a non-empty one-sentence `claim`, and an `evidence` object. A result that is not valid against the schema, an envelope with status `fail` or `timeout`, and an unparseable result each stop the record at the review step before the push, with a `stop` or `fail` event; none is read as "no findings". An empty findings array is a valid result and yields zero findings. A single finding that does not satisfy the schema is discarded and counted, and the rest are still processed.
3. Evidence is exactly a test file: `evidence` must be an object with a string `path` and a string `content`. Evidence in any other shape (a `command` or `cmd` field, a bare string, a URL, a diff, an object with extra fields that name something to run, or a missing `content`) is discarded and counted. A test feeds a finding whose evidence carries a command string such as `touch marker` and one whose `path` contains shell metacharacters (`;`, `$(...)`, a backtick, a space, a newline): neither string is ever executed, and no call recorded by the fake runner after the reviewer returns has an argument list or shell string taken from the reviewer's result, apart from the test command with the validated evidence path as one argument. The test command is spawned without a shell.
4. Path rules, each with its own test that goes red when only that rule is removed. A discarded finding is counted and its evidence is never written. A path is discarded when it: is absolute (including a drive-letter or `file:` or other scheme prefix, in any letter case); has a `..` or `.` segment before or after normalization; carries a percent-encoded dot or separator (`%2e`, `%2f`); uses a backslash; ends with a slash; begins with `-` (it would be read as a flag); is empty or over a named length bound; is not a test file by `isTestPath` (`plugin/bin/lib/issues/blast-radius.js:55`); is a protected or merge-sensitive path by `isProtectedPath` and the run's merge-sensitive paths; or names anything that already exists in the worktree (tracked, untracked, a directory, a symlink, or a dangling symlink, by `lstatType`), so evidence can never overwrite an existing test. The resolved parent directory, by `canonicalRealpath`, must be inside the worktree's own canonical path; a parent that is a symlink leaving the worktree, or that cannot be resolved, discards the finding. A path that merely contains `test` as a substring of a component (`src/latest/widget.js`, `src/contest.js`) is judged by `isTestPath`, not by substring, and is discarded.
5. Content rules: `content` must be a non-empty string no larger than a named byte bound. Content that is empty, not a string, or over the bound is discarded and counted. Every named bound in this record (path length, content size, finding cap, evidence-run wall clock, event-text length) is a constant the builder picks and states in `review.js`'s header, and each is pinned by a test at its edge; the evidence-run wall-clock bound must be smaller than the per-record wall-clock ceiling #5219 defines.
6. At most a named number of findings (the builder's value) are evaluated, in the order the reviewer returned them; the rest are counted as discarded. When two findings name the same evidence `path`, the first is evaluated and the second is discarded and counted (it would otherwise overwrite the first's file).
7. A valid finding's evidence file is written into the worktree and the project's test command is run on that one file, with a named wall-clock bound. The finding is confirmed only when the Task 0 rule classifies the run as reproduced (a test case ran and failed). A passing run, a run that fails to load (syntax error, throwing `require`), a run with no test case, a run that times out, and an output the rule cannot place are each discarded, each with its own test built on the Task 0 fixtures. Every discarded evidence file is removed before any later step, so the worktree's `git status --porcelain` is empty when the step ends with no confirmed finding, and the run then proceeds to the push step with `check`'s `head` guard unchanged. A failure to write or to remove an evidence file stops the record at the review step. The test command is spawned with the worktree as its working directory and the path relative to the worktree root as one argument. After every evidence run the driver compares the worktree's `git status --porcelain` with its expectation (the evidence files written so far and nothing else): a tracked file modified, or an untracked file other than an evidence file, stops the record at the review step, since test code that touches the tree is not a reproduction. A run that exceeds its wall-clock bound kills the whole child process tree (the launcher's kill primitive from #5217, which has a POSIX process-group branch and a win32 `taskkill /T` branch) and counts as discarded; a test has the evidence test write a second file and asserts the stop.
8. With at least one confirmed finding, exactly one fix round runs: the implementer worker is launched once more, as a fresh launch whose prompt is the first launch's prompt (record body, Key Files, limits) plus each confirmed finding with its evidence test's path and full content, then the driver rewrites each evidence file from the content it recorded (criterion 9), then the commit of the changed files by explicit path (the evidence test files included), the scoped test run, a direct run of every kept evidence test, and `express-lane.js check`, in that order. Over a fake runner the implementer is launched exactly twice in the whole run, never three times, whatever the second round returns. All confirmed findings share the one round.
9. The driver rewrites each evidence file from the content it recorded when it confirmed the finding immediately after the fix-round implementer returns and before the commit, so the committed evidence test is byte-identical to the one that was red, whatever the implementer did to it (a deleted file is recreated; an edited one is overwritten). Tests: the implementer fixture deletes the evidence file and changes nothing else, and the record escalates because the evidence test is still red and nothing else was fixed; the implementer fixture edits the evidence file into a passing test, and the committed content still equals the recorded content.
10. The record escalates, with no second fix round (the fake runner records no third implementer launch), and the stop's `detail` names the finding (its path, line and claim), when any of these holds after the fix round: a kept evidence test is still red; the scoped test run is red; `check` returns `escalate` (including out of bounds); the fix-round worker returns `fail` or `timeout` or changes no file (that is, no path outside the evidence files differs from the pre-fix HEAD); the commit fails. The stop is a pre-push stop, so its outcome is `express-escalated`, as for every pre-push stop in `drive.js`.
11. Reviewer-authored text (the claim, the path) that enters an event line or a stop `detail` is one line, no longer than a named bound, with `#N` references and closing keywords removed and `@` mentions neutralized, by the same normalizer `drive.js` applies to the worker's title (a test feeds a claim that holds a newline, `fixes #12` and `@someone`).

The step emits exactly one `review` event when it runs, carrying `returned`, `reproduced` and `discarded` counts, and the reviewer's `usage` and `denials`; a test pins the field names and that `returned` equals `reproduced` plus `discarded` for fixtures covering discard-by-schema, discard-by-evidence-shape, discard-by-path, discard-by-run and over-the-cap. The step name is a constant in `plugin/bin/lib/driver/events.js`, pinned like the others there.

The record-level rule reads the record's size label (from `parseRecordFacets`) and its Key File count (from the same extraction the eligibility gate uses): a size label that is missing or not `low` counts as beyond the express bounds, and so does a Key File count above `EXPRESS_MAX_KEY_FILES` (the test derives the limit from that constant, not from a literal 3). With the default, a record inside the express bounds (size `low` and at most that many Key Files, the two record-level bounds today's express lane applies) starts no reviewer worker, emits no `review` event, and the recorded calls and event lines for a Phase 1 happy-path fixture are identical to what they were before this unit. After a fix round the push uses the `head` the second `check` returned and the runner pass stamp written by the second scoped run, never the first run's: a test has the fake runner return different heads from the two `check` calls and asserts the push guard compares the worktree's HEAD with the second, and that a HEAD that equals only the first head stops the record at the push step with no push. ## Release Note

Added a single evidence-based reviewer to the pipeline driver, which accepts a finding only when it comes with a test that fails.

## Technical Approach

- **Where it runs.** `run.js` calls the review step after the scoped test run and `express-lane.js check` have passed, and before the push. It is skipped (no worker, no event) when the policy value, applied to the record's size label and Key File count, says so.
- **"Beyond the express bounds" is a record-level rule.** The step is on under the default when the record's size label is not `low` or its Key File count exceeds the express limit (`EXPRESS_MAX_KEY_FILES`, `plugin/bin/lib/express/eligibility.js:16`). The diff-level line bound is not part of the rule: a record inside the express record-level bounds runs as in Phase 1, and the next unit decides what the line bound is when the step is on. The rule is a pure function exported from `review.js` so the next unit's admission can call it.
- **Closed rule (states of the reviewer's output).** The states this step knows are: a valid result with findings; a valid result with none; a result not valid against the schema; an envelope with a status other than `ok`; and, per finding, valid or discarded (criteria 2 to 7). A state outside the list is refused as a step failure, never read as "no findings"; a plan review that finds another unlisted state applies this rule as a plan amendment adding that state's refusal, not as a `needs-human` gap.
- **Evidence runs without a shell.** The runner is called with an argument list (the test command's own words plus the validated path), never a command string built from reviewer text.
- **The evidence path is relative to the worktree root.** It is joined to the worktree's canonical path only after every rule in criterion 4 has passed; the file is created exclusively (it must not exist), its parent directories may be created inside the worktree, and a created directory is removed with a discarded file if it holds nothing else.
- **The fix round reuses the Phase 1 steps.** Commit, scoped test and check are the existing step functions called a second time with the evidence files added to the explicit path list; the one place `run.js` differs is that it may now commit twice, so any code that assumed a single commit per run is revisited. The second commit's message is built by the same normalizer and form as the first.
- **Stop reason.** The stop carries the existing structured stop shape from `drive.js`; this unit adds no field to it, only a `detail` that names the finding. Every stop below is a pre-push stop (class `pre-push`, outcome `express-escalated`, the settle unit then discards the partial work as for any pre-push stop); the only difference is the event status:

  | Stop | Event status |
  |---|---|
  | Reviewer envelope `fail` or `timeout`, result not valid against the schema, unparseable result | `fail` |
  | Evidence file cannot be written or removed; the tree changed outside the evidence files during an evidence run | `fail` |
  | Fix-round worker `fail` or `timeout`; commit fails | `fail` |
  | Kept evidence test still red; scoped tests red; `check` returns `escalate`; fix round changed nothing outside the evidence files | `stop` |

- **The reviewer is told the Key Files.** Its prompt names the record's Key Files and says a fix must stay inside them. A real defect whose fix needs a path outside the Key Files makes `check` return `escalate` as out of bounds after the fix round; that is the intended outcome (such a record belongs on the standard path), not a gap this unit closes.

### Data / API Surface

- `reviewRequired({ record, policyValue })` returns `{ on: boolean, reason: string }` (the reason names the policy value or the record bound that decided it). It is a pure function of the record and the resolved policy value, so its answer is the same wherever it is called for one record; the run loop computes it once per record and reuses it, and the next unit's admission receives that same `on`. Function and field names beyond `on` are the builder's; a later rename of the exported function or of the policy key's spellings follows the expand-then-contract discipline, since the key's spellings enter users' `policy.yml`.
- Reviewer result schema: `{ findings: [{ path, line, claim, evidence: { path, content } }] }`; field names may be longer, the five facts are required.
- `review` event: the standard event fields plus `detail: { returned, reproduced, discarded }`, `usage`, `denials`.
- Policy key: an `enum` with three values (off, on, on-beyond-the-express-bounds); the builder names the key and the three spellings, states them in the doc row and in `docs/driver.md`, and the default is the beyond-the-express-bounds setting.

## Gotchas

- ASSUMPTION — verify at build: `plugin/bin/lib/driver/steps.js`, `run.js`, `events.js`, `roles.js`, `worker.js` and `docs/driver.md` have the shapes the Phase 1 records (#5216 to #5219) describe, including the envelope fields and the stop structure — confirm via `git grep -n -F "launchWorker" -- plugin/bin/lib/driver` once #5219 has landed, and adapt the call sites named above to what is there.
- ASSUMPTION — verify at build: the launcher accepts a per-call result schema for the reviewer role (the implementer's schema is the one #5217 names) — confirm in `plugin/bin/lib/driver/worker.js` once #5217 has landed; when it does not, adding the parameter is part of this unit and stays backward compatible for the implementer role.
- ASSUMPTION — verify at build: the scoped `bin/verify.js` invocation includes a newly added test file in the diff in its impacted set — confirm by running it over a fixture worktree with one added test file; when it does not, the direct run of the kept evidence tests (criterion 8) is the regression proof and the gap is stated in `docs/driver.md`.
- Discarded evidence files must be removed before any later step: the driver commits "the changed files git reports", so a stray evidence file would be committed by the fix-round commit or fail the clean-tree expectations of the push step.
- The evidence test is untrusted code run with the driver's own rights. That is the accepted residual the design names, stated in `docs/driver.md` (criterion 14); it is not mitigated here and the step adds no new capability to any worker. The reviewer's tool list never gains Bash to "make the evidence runnable"; the driver runs it.
- Reproduction is a classification of the test command's output, so it is only as good as Task 0's rule for that command. A project whose test command's output the rule cannot place never confirms a finding; that fails closed (the finding is lost, nothing false is confirmed).
- A red test proves only that the reviewer's assertion fails, not that the assertion is right: a wrong expectation confirms a wrong finding and the fix round then changes code to satisfy it. The design accepts this (a red run confirms), the residual is stated in `docs/driver.md` (criterion 14), and the scoreboard's rework figure is where it would show up. It is not mitigated here.
- Considered and not done: running the evidence test with a scrubbed environment. The evidence test must run the way the driver's own test step runs, or a green or red result would not mean the same thing; the stated residual is that it holds the driver's rights. A narrower launch environment for test runs would be its own design change.
- Do not weaken the discard-on-green rule into "keep the finding as a note". A finding without a failing test is not a finding.
- `check` and `escalate` refuse once the PR exists (`plugin/bin/lib/express/cli.js:247-250`), which is why this step must complete before the push.
- One fix round for all confirmed findings, not one per finding: the design says a confirmed finding gets "exactly one fix round", and a per-finding round would let a long findings list keep the implementer running without bound.
- The spend and wall-clock ceilings (#5219) apply to the reviewer and to the fix-round implementer like any worker; reaching either is a failure of that step and stops the record by the same rules.
