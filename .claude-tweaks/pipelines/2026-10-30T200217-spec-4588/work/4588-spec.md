# 4588: Add a dispatch resume form for a build that stalled with its PR still open

Surface: backend

**Related:** #4589, #4580, #4518, #4265, #3706, #3901, #4030, #4264, #4345, #4492, #4494, #4495, #4499, #4596, #4615

## Current State

A dispatched build that stops before the test gate (a BLOCKED first call, a plan-review question, a crashed or rate-limited child) leaves a draft PR, a kept worktree and an archived run. `/claude-tweaks:dispatch #N` then refuses the record: Step 2's queue drops it as `open-pr` (`queue-pull-script.md`, `partitionByOpenLinkedPR`) and the `#N` bullet in `dispatch/SKILL.md` stops on that exclusion. `close-out` only handles a finished `pending-review` PR, and `resume-confirmation.md` only re-enters a run whose directory still exists.

Resuming #3903 on 2026-10-30 took a hand-assembled sequence: `check-sibling-sessions`, `resolve-run-dir --create`, `EnterWorktree(path)` on the existing worktree, `record-worktree --dispatch`, `compose-context --phase first-call`, then `task-prompt.md`'s first-call template with a hand-written resume note, the second call, and a handoff continuation. Nothing in the skill describes this path.

Since this record was filed, two merges changed what resume runs into:

- **#4518 / #4423 (claim in-flight stop).** `bin/lib/claim-targets/claim-targets.js` now exits 3 with `{inFlight: [{issue, link}]}` ("Claim in-flight … not re-claiming", `flow/claim-targets.md`) in two cases: a `pr-opened:` tombstone whose PR is still OPEN (`tombstoneInFlightPr`), and a TTL-expired, unreleased (`'stale'`) claim whose run marker `claude-tweaks-run: {runId}` sits on an open PR (`staleClaimInFlightPr`). A dispatched first call runs with `DISPATCH_HEADLESS=1`, so that card is terminal there. Which state a stalled build leaves decides whether resume hits this stop:
  - Settled failure: dispatch's Settle releases the claim with a `failed:` tombstone (#4589 today reads `reason: "failed: plan-review-needs-human"`). A `failed:` tombstone is neither `pr-opened:` nor `'stale'`, so `/flow`'s claim re-claims it by conditional write. No stop.
  - Unsettled death: the session died before Settle (crash, 429, closed terminal), so the claim was never released and expires into `'stale'`. Its `runId` marker is on the still-open draft PR, so the claim stops in-flight. This is exactly the record resume exists for, and today it cannot be claimed at all.
  - `pr-opened:` tombstone: the build finished and settled `pending-review`. That PR is close-out's, not resume's.
- **#4580 (PR rebind).** `pr-early-open.js` now rebinds a reused OPEN PR's body to the current run when it names a different run. A resumed run's fresh run id no longer breaks `pr-checklist.js`, so resume needs no PR-body step of its own.

## Deliverables

1. `/claude-tweaks:dispatch resume #N`: a new Input-table form in `dispatch/SKILL.md`. Eligibility (decided 2026-10-30 on the plan-review questions, issuecomment-6532612775):
   - **PR:** found from the head branch `worktree-dispatch-record-N` (an open draft PR whose body's `claude-tweaks-run:` marker names a run id matching `RUN_ID_SHAPE` with slug `record-N`), never from `dispatch-exclusions.json` — a record carrying `bot:in-progress` is dropped by the queue's label pre-filter before the `open-pr` pass and has no exclusion entry.
   - **Claim blob:** a `failed:` tombstone, an `abandoned:` tombstone (a crashed or rate-limited first call whose `cleanup-only` release wrote it), or a `'stale'` claim. `failed:`/`abandoned:` re-claim by the ordinary conditional write; `'stale'` uses deliverable 3.
   - **Labels:** `auto:build` present and no `bot:blocked` (a human re-grants via `/claude-tweaks:backlog refine` after answering whatever blocked the build; resume never originates or restores a grant). `bot:in-progress` is accepted only together with a `'stale'` claim.
   - **Worktree:** when the stalled worktree exists, `git status --porcelain` in it must be empty. A worktree with uncommitted edits is refused before anything is minted, with a line listing the dirty paths and the manual remedy (commit or discard them, then re-run). Resume never commits or pushes the leftover edits itself (question 1).
   - **Prior run directory:** checked under `pipelines/archive/{runId}` first. Eligible when archived, absent, present holding only `work/` residue, or present with a provably dead owner. "Dead owner" is decided by the owner-process probe alone (decided 2026-10-31 on issuecomment-6533615614, question 1): the `run-state.json` owner block's process is not live, or there is no `run-state.json`, or `run-state.json` carries no owner block; the resuming session's own session id never counts as a live owner. Only a proven death counts (decided 2026-10-31 on issuecomment-6540061358, question 4): the owner process is gone, its pid was reused, or the owner block has no pid. An owner block recorded on another host is refused, never read as dead. Commit, heartbeat and worktree-lock recency do not make an owner live here — the sibling-session check deliverable 2 runs (repeated after entering the worktree) is what refuses a live session working in that worktree. A present directory with a dead owner is archived (`hooks.js archive-run`) before the new run dir is minted; a live owner is refused. A present directory with no `run-state.json` (which `archive-run` refuses) is not archived: resume logs it to `decisions.md` and leaves it to reconcile's orphaned-run cleanup (question 3).
2. It runs the sibling-session check, mints a fresh run dir, enters the existing worktree by path (re-creating it from the PR head branch when the worktree was reaped), binds it with `record-worktree --dispatch`, and dispatches the normal two-call sequence with handoff continuations, reusing the open PR. PR-body rebind is left to `pr-early-open.js` (#4580); resume adds no PR-body write.
3. Passing the claim stop: `claim-targets.js` gains a `--resume-pr <url>` flag. When a target's in-flight check (`tombstoneInFlightPr` or `staleClaimInFlightPr`) returns a `link` equal to that URL **and** the blob is `'stale'`, the target takes the ordinary conditional-write re-claim instead of exit 3, and the claim's log line names the adopted PR. A `pr-opened:` tombstone, or an in-flight link that differs from `--resume-pr`, still exits 3 unchanged. `/flow` forwards the flag only when its invocation carries `RESUME_PR=<url>`, and `task-prompt.md`'s first-call template sets that only for `dispatch resume`.
4. The first call's prompt carries a resume context block derived from the archived run (prior run id, last logged phase, open defects named in its final `decisions.md` entries) instead of hand-written prose.
5. Refusals:
   - A record whose open PR belongs to a different record, or whose prior run is live in a sibling session, is still refused with the existing `open-pr` line.
   - A record whose claim blob is a `pr-opened:` tombstone is refused with a line naming `/claude-tweaks:dispatch close-out #N` as the remedy.
   - A record whose claim is `'live'` is refused as already claimed.

## Acceptance Criteria

- [ ] `claim-targets.js --resume-pr <url>` re-claims a `'stale'` blob whose in-flight link equals `<url>`, and still exits 3 for a `pr-opened:` tombstone or a mismatched link (unit test in the claim-targets suite).
- [ ] `dispatch resume #N` on a record whose first call crashed (`abandoned:` tombstone) and whose prior run directory was left un-archived with a dead owner archives that directory, claims the record and completes the two-call sequence.
- [ ] `dispatch resume #N` on a record carrying `bot:blocked`, or lacking `auto:build`, is refused with a line naming `/claude-tweaks:backlog refine #N` as the remedy.
- [ ] `dispatch resume #N` refuses, before minting a run dir, a record whose stalled worktree has uncommitted edits, and the refusal lists the dirty paths.
- [ ] `dispatch resume #N` refuses a record whose prior run directory's owner block was recorded on another host.
- [ ] `/claude-tweaks:flow` without `RESUME_PR` keeps today's in-flight stop for the same blob (existing #4423 tests stay green).
- [ ] `dispatch #N` behaviour for the same record is unchanged (still refused, now naming `dispatch resume #N` as the remedy in `open-pr-exclusion-report.md`'s line).
- [ ] Within `plugin/skills/dispatch/`, only the `open-pr` exclusion line names `dispatch resume #N` (decided 2026-10-31, question 2; narrowed the same day on issuecomment-6540061358 question 2 — `/tidy`'s existing "Resume open PR" offer in `tidy/scan-procedures.md` is out of scope and unchanged): `dispatch #N`'s "already claimed" refusal for a record still carrying `bot:in-progress` with a `'stale'` claim is unchanged, and `dispatch/SKILL.md`'s `#N` bullet is not edited.
- [ ] A unit test pins the resume eligibility rule:
  - own stalled draft PR with a `failed:`/`abandoned:` tombstone or `'stale'` claim → eligible;
  - prior run dir present with a live owner → refused; dead owner or `work/`-only residue → eligible;
  - `bot:blocked` or no `auto:build` → refused;
  - foreign PR → refused;
  - live sibling run → refused;
  - `pr-opened:` tombstone → refused toward close-out;
  - `'live'` claim → refused.

## Technical Approach

Eligibility is one pure function: inputs are the claim blob, the open PR (head, body), and the run-dir state; output is eligible or a refusal reason. It lives beside `bin/lib/dispatch/exclusions.js` so `SKILL.md`'s resume bullet and the `open-pr` report line read the same verdict. The claim flag stays narrow: it changes only the `'stale'` + matching-link branch of `claim-targets.js`. That keeps #4423's protection for every caller that does not name the PR, because a resumed run names exactly the PR it is continuing.

## Gotchas

- `staleClaimInFlightPr` fails open (returns null) on a gh error. A resume whose check errors re-claims anyway, which is today's behaviour too, so `--resume-pr` adds no new failure mode there.
- `issue-claims-stale-open-pr-conformance.test.js` pins `RUN_ID_SHAPE` copies across prose files. Any new prose copy of the run-id regex must use the same `.source`.
