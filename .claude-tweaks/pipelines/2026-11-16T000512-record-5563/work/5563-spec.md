# 5563: Keep a bounded number of releases in CHANGELOG.md, set by a policy key

Surface: backend
Risk-flags: none

**Related:** #5508, #5356, #2771, #4443, #5562

## Current State

`CHANGELOG.md` grows with every release and nothing bounds it. Measured on `origin/main` on 2026-11-15 (re-derive before relying on a number):

- 557 KB, 5,531 lines, 335 release sections. 88 commits changed the file in the last 30 days.
- The newest 25 sections take 72 KB, the newest 50 take 197 KB, the newest 100 take 297 KB.
- 61 sections are in release-please's form (`## [6.170.0](compare-url) (date)`). The other 274 are older, hand-written sections (`## v2.2.0 — title (date)`).
- The repository has 320 `v*` tags and 61 GitHub releases. A release-please section has a GitHub release; an older one does not.

Who touches the file:

- release-please prepends a section in the release PR. `plugin/bin/release-local.js` does the same for projects on `local-merge` (`prependSection`).
- `plugin/bin/lib/release-notes-publish.js` rewrites the newest section to add its Highlights block and commits the file, from `.github/workflows/mirror-marketplace.yml` after a release is published.
- `plugin/bin/lib/residue/probes/release.js` reads the file through `git show` and reports every `v*` tag at or after the release-please bootstrap version that has no section, and every section with no tag. `/claude-tweaks:tidy`'s Backfill action then adds the missing heading.
- `plugin/bin/lib/changelog.js` (`extractChangelogRange`) gives `/claude-tweaks:init`'s update check the sections between two versions.
- `plugin/bin/residue.js` reads it with a 64 MiB output buffer, set after the file, then a quarter of Node's 1 MiB default, was on course to overflow it and make the probe fail silently.

Design: `docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 8, unit 8.2. The design says to link to GitHub releases for the sections removed. That holds for the 61 release-please sections and not for the 274 older ones, so the trimmed file also names the commit at which it was last whole.

## Deliverables

1. **A policy key**, `changelog-max-releases`: an integer, default `0`, where `0` means the file is never trimmed. Registered per `.claude/skills/policy-key-addition`.
2. **One trim function** in `plugin/bin/lib/changelog.js`: given the file text and a count, it keeps the header, the newest `count` sections and a footer, and returns the new text and the versions it removed. It recognises every heading form `HEADER_RE` in `plugin/bin/lib/changelog.js` matches: `## vX.Y.Z — title`, `## [X.Y.Z](url) (date)` and `## X.Y.Z (date)`. Run on text that is already within the bound, it returns the text unchanged.
Decided 2026-11-15: newest means file order. The function keeps the first `count` sections as they appear and does not sort. The header is everything before the first line `HEADER_RE` matches and is kept byte-identical. A `## ` line `HEADER_RE` does not match belongs to the section above it, or to the header when it comes first (AC10). The trim function never edits header prose; this repository's header, which describes sections a trim removes, is edited by hand in the opt-in record.
3. **The footer.** One section at the end of the file, written only by the trim function. It gives two routes to removed notes. The first is the commit recorded at the first trim, by full sha, with the command that prints the file at that commit: that file holds every section up to the newest release of that time, including sections that have no tag. The sha is set once and never changes. The second covers anything trimmed later: a release's notes are in the file at its own tag (`git show v<version>:CHANGELOG.md`), without the Highlights block, which is added after the tag. When the repository has a GitHub origin the footer also carries a permanent link to the file at the recorded commit and a link to the releases page.
Decided 2026-11-15: two routes, as Deliverable 3 now states: the commit recorded once at the first trim, and the file at a release's own tag for anything trimmed later. AC9 covers a version removed by a second trim.
4. **Trim at release.** With the key above zero, the trim runs where the file is already rewritten after a release: in `release-notes-publish.js` for `pr-first`, in the same commit as the Highlights block, and in `release-local.js` for `local-merge`. A release never fails because of the trim: on any error the file is left as it was and one line says so.
Decided 2026-11-15: both engines read the key through the policy reader in `plugin/bin/lib/policy.js`, from the checkout they run in; the workflow checks out the repository, so the committed `policy.yml` is there. A `policy.yml` that exists and cannot be read prints `changelog trim: policy unreadable ({reason}); not trimmed`, a different outcome from a silent `0`. In `release-notes-publish.js` the trim runs whether or not there is a Highlights block to add: the early returns for fewer than two releases and for no `Release-Note:` trailers skip only the Highlights work. A commit that carries only a trim has the subject `chore: trim CHANGELOG.md to the newest {n} releases`; one that carries both keeps the Highlights subject. A failed trim never stops the Highlights or the release: the engine prints `changelog trim: failed ({reason}); file left untrimmed` and exits as it would have. The release reports as released, per `.claude/skills/driver-skill-outcome-taxonomy`: nothing failed to land.
5. **Readers respect the floor.** `residue/probes/release.js` reports no finding for a version older than the oldest section of a file that carries the footer. `extractChangelogRange` says when the requested range reaches below the floor, and `plugin/skills/init/bootstrap/version-check.md` tells the reader the summary is partial in that case.
Decided 2026-11-15: the floor is the version of the oldest retained section, compared with the comparator the probe already uses (`versionGte`). A file that carries the footer keeps its floor whatever the key's value, `0` included: turning the key off stops further trims and does not make the probe ask for removed headings. A footer removed by hand removes the floor (AC5's second case). `/claude-tweaks:tidy`'s Backfill action inserts a heading above the footer, in version order; its row in `plugin/skills/tidy/SKILL.md` gains that clause. Valid key values are integers of 0 or more. The footer is not a section and is not counted. Any other value resolves to the default (AC15).
6. **This repository does not opt in here.** The key ships at its default `0`. The PR carries a proof on a copy: the trim to 50 run on a copy of this repository's `CHANGELOG.md`, not committed.
Decided 2026-11-15: the opt-in is its own record, blocked by this one and built once this release is the installed plugin, so no running session's `/claude-tweaks:tidy` reads a trimmed file with a probe that does not know the floor. Why the key exists: at the current release rate the file grows by about 300 KB a month (82 tags in 30 days; the newest 25 sections take 72 KB); repository-wide text searches hit it, and open records #5535 and #5536 exclude it by hand in their sweeps; and each release rewrites the whole file. A count is not a byte bound: 50 sections are 197 KB today and could be more. The key bounds growth, not size.
7. **Docs.** `docs/releasing.md` and `plugin/skills/_shared/policy-schema.md` describe the key, the footer and where older notes are.

**Decision (plan review Q1, 2026-11-16).** A range is partial only when a removed version can fall inside it. The footer gains one more line, `Newest release removed: v{version}`, rewritten by every trim that removes a section (the recorded commit line stays fixed). `extractChangelogRange` reports `partial: true` when the file carries a footer and `oldVersion` is older than that version, and `partial: false` otherwise, including when `oldVersion` equals it. AC6 covers both sides: a range starting below the newest removed version is partial; a range starting at it is not.

**Decision rule for any further gap (author, 2026-11-16).** Where this record leaves a choice between readings and no Decision above settles it, the build does not stop for it. It takes the reading that, in this order: keeps a run on the previous plugin release working; puts the rule in code and not in skill prose; stays inside this record's Key Files. It states the choice in the PR body. A criterion that can only be observed after a merge or a release is met by filing one parked measurement record through `/claude-tweaks:capture` that carries the check and its bound.

## Technical Approach

Section boundaries: a line that starts with `## ` followed by a version in any of those three forms opens a section; the footer's own heading must not match any of them, so no reader takes it for a release.
Decided 2026-11-15: the footer's heading is `## Older releases`, which `HEADER_RE` does not match. Under it: a line `Full file up to v{version}: commit {full sha}` with `git show {sha}:CHANGELOG.md`, the tag rule, and the two links when there is a GitHub origin. `plugin/bin/lib/changelog.js` exports one helper that finds and parses the footer; the trim function, the release probe, `extractChangelogRange` and the Highlights writer all use it and none holds its own pattern. The trim function takes the text, the count, and the commit and repository URL for a first footer; on a later trim it reads them from the footer already there (AC8, AC11).

The footer needs a commit, and a repository URL when there is one. `release-local.js` serves projects with no forge, so the sha is the part that always exists; read the origin through the helpers `.claude/skills/gh-api-module-pattern` names, and leave the links out when there is none. Use the commit the engine has just before it trims; never a branch name.
Decided 2026-11-15: an engine trims on the default branch after its release commit exists, and records that branch's tip before the trim commit. Before writing the footer it checks that commit is an ancestor of the default branch (`git merge-base --is-ancestor`); if not, it does not trim and prints the failure line (AC14). This record trims no real file, so no branch commit is ever recorded.

`release-notes-publish.js` already commits `CHANGELOG.md` with the workflow's token. The trim rides in that commit, so no new workflow permission is needed. Check that the step still does nothing when it has no Highlights to add and nothing to trim.

Do not trim inside release-please's own PR. The release PR's diff stays what release-please rendered.

## Gotchas

- `plugin/skills/_shared/policy-schema.md` is 49,189 bytes against a 52,500-byte read limit. Keep the key's row short and put any longer description where `.claude/skills/policy-key-addition` says detail goes.
- `/claude-tweaks:tidy`'s Backfill action adds a heading for any tag the release probe reports. If the probe does not respect the floor, the next tidy puts every trimmed heading back.
- A release may be cut by a session on the previous plugin release, or by the workflow at an older checkout. That code does not trim and does not know the footer. Confirm that release-please's prepend, `prependSection` and the Highlights writer on the base commit all leave a footer at the end of the file intact.
Decided 2026-11-15: AC12 covers the two writers this repository owns. release-please's own prepend cannot run in a test; the opt-in record checks the first release PR after the opt-in and stops if the footer moved. Ordering: with the key off no file is trimmed, so this release changes nothing for a project that has not opted in. A build older than this release that reads a trimmed file reports the trimmed versions at or after the bootstrap version as missing, and its `/claude-tweaks:tidy` would add their headings back; `docs/releasing.md` says to opt in only once every session runs this release or newer.
- #5508 is open on the release PR's version and changelog being cut short when release-please reads too few commits. It edits the release skill, not these files; do not fold it in.
- `CHANGELOG.md` is outside the `plugin/` payload. An installed plugin has no copy, and `version-check.md` already skips silently then.
- Use `.claude/skills/gh-api-module-pattern` for any new `git` or `gh` call, and `.claude/skills/driver-skill-outcome-taxonomy` if a release step's reported outcome changes.

## Release Note

A new policy key, `changelog-max-releases`, keeps only the newest releases in `CHANGELOG.md` and links to the rest. It is off by default.

## Build Clarifications

- Beneficial (architecture alignment, build): `release-local.js` trims only after the release has fully landed (release commit, tag, push, hook), in its own `chore: trim …` commit pushed through the same ancestry-checked push; a failed hook means no trim. Trimming before the push let the unchanged diverged-origin recovery (`git rebase` + `git tag -f`) move the tag onto the trimmed file and orphan the footer's commit. Deliverable 4's "an engine trims on the default branch after its release commit exists" still holds.
- Beneficial (architecture alignment, build): under `pr-first` the trim runs only where a `release: published` workflow runs `bin/release-notes-publish.js` — today only this repository's own workflow does; the shipped `policy-schema.md` row says so. Wiring that step into consumer projects is a follow-up record, not this one.
