# 5297: Cut the test suite's process churn from fixture git repos

Verified-as-of: 671c9a83c98cf199f2b2dcb72a5c0398b0839ff5

## Current State

Measured 2026-11-13 on a 12-core Mac. One `node --test --test-concurrency=6` run spawned 1,300–2,100 processes a second for minutes; machine-wide kernel CPU time reached 47%, and idle fell to 10%. In a 25 s capture, 7,460 of 13,002 new processes descended from that one run, and most were git calls from tests that build throwaway repos.

Exact counts for two fixed file sets, run through `node tools/run-tests.js --files-from <list>` with `CT_TEST_CONCURRENCY=6` on main @ 671c9a83c. Git processes were counted as one `GIT_TRACE2_EVENT` file per process:

| Set | Tests | git processes | of which `maintenance run --auto` | non-git children of git | node processes |
|---|---|---|---|---|---|
| A: tests/hooks-pre-tool-use, hooks-session-start, hooks-teardown-run, issue-branch-tracking, reconcile-archive-residue, load-delta-cli | 355 | 3,632 | 391 | 153 | 34 |
| B: tests/bin-lib/verify/cli-baseline, cli-flaky-preexisting, cli-scope-integration, cli-slot-queue | 82 | 2,527 | 249 | 0 | 436 |

Where the processes come from:

- **Auto-maintenance.** Every fixture `git commit`, `push`, `fetch` and `merge` starts `git maintenance run --auto`. Nothing turns off `maintenance.auto` or `gc.auto` for test repos. `tools/run-tests.js` builds the `node --test` child's env (`{ ...process.env, TMPDIR, TMP, TEMP, CT_TEST_SUITE_SLOT_HELD }`) and sets no git config. A prototype that exported `GIT_CONFIG_COUNT=2 maintenance.auto=false gc.auto=0` into that env cut set A from 3,632 to 3,285 git processes, and all 355 tests still passed. 44 maintenance runs survived, all under `git-receive-pack`: git's local transport strips `GIT_CONFIG_*` from the receiving side, so a bare fixture origin needs `receive.autogc=false` in its own config.
- **Per-test fixture construction.** Each test builds its repos from scratch with spawns. Set A ran `init` 174 times, `commit --allow-empty` 108, `config user.email/name` 114, `clone` 46 and `push` 44, plus the upload-pack, receive-pack, pack-objects and rev-list processes each push or clone starts. Set B ran `init` 87 times and `config user.*` 174. The builders are duplicated across files:
  - `tests/helpers/reconcile-fixtures.js` (origin/seed/main triple);
  - four inline copies of the same triple in `tests/hooks-session-start.test.js` (around lines 439, 907 and 1104);
  - `tests/hooks-teardown-run.test.js`'s `fixtureRepo()`;
  - `tests/helpers/git-fixtures.js`'s `gitRepo()` and `originWithTwoClones()`;
  - `tests/bin-lib/verify/cli-helpers.js`.
- **A shell for every `git --version`.** `plugin/bin/lib/deps.js`'s `has(cmd)` runs `execSync(\`${cmd} --version\`)`, which spawns `/bin/sh -c git --version` and then git. That is 2 processes on every SessionStart hook: 105 of them in set A, and on every real user session start. The same file already has `findOnPath`, a spawn-free PATH scan that `playwrightCliMessage()` uses.

Out of scope: set B's 436 node processes come from verify.js tests that run real nested `node --test` fixture suites. Cutting those is a different fix, and it gets its own record.

## Deliverables

1. `tools/run-tests.js` adds `maintenance.auto=false` and `gc.auto=0` to the `node --test` child's env as `GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` entries. They are appended after any `GIT_CONFIG_COUNT` entries the caller already exported, never replacing them. The env is built by a pure exported function with a unit test beside the existing run-tests.js tests.
2. `plugin/bin/lib/deps.js`'s `has(cmd)` answers presence with `findOnPath` (PATH scan, PATHEXT on win32) instead of `execSync` through a shell. Its existing tests are updated to match.
3. A shared template-repo helper in `tests/helpers/`. It builds a named fixture (a single repo, or an origin/clone set) once per test process, and hands each caller a fresh copy via `fs.cpSync`. Absolute paths recorded in `.git/config` (remote URLs) are rewritten in the copy by a file edit, not a spawn. The commit identity lives in the template's config, so callers no longer run `git config user.*`. Bare origins get `receive.autogc=false`.
4. The fixture builders named in Current State move onto the helper wherever the test does not depend on building the repo itself: the inline triples in hooks-session-start, reconcile-fixtures.js, hooks-teardown-run's `fixtureRepo()`, git-fixtures.js's `gitRepo()`/`originWithTwoClones()`, and the verify cli-helpers repo init. A builder left as-is is named in the PR body with the reason.
5. The PR body reports before/after counts for sets A and B, measured the same way as Current State: git processes, maintenance runs, non-git children of git, and node processes. It also includes the measuring script.

## Plan Review Clarifications

- Decided by the user at plan review: on darwin, a `has()` hit at `/usr/bin/{cmd}` counts as present only when a real developer dir holds `usr/bin/{cmd}` — the `/var/db/xcode_select_link` target or `/Library/Developer/CommandLineTools` — read without spawning, so a Mac with only the `xcode-select` shim still gets the install hint today's `git --version` probe produces. Amended at build (Common Step 4.5, beneficial): the developer dir follows xcode-select's own precedence — `DEVELOPER_DIR` (an `.app` path maps to its `Contents/Developer`) decides alone when set; otherwise the link target; with no link, `/Applications/Xcode.app/Contents/Developer`, then `/Library/Developer/CommandLineTools` — so a Mac with working git through either default never gets a false "not found". (Spec: "`plugin/bin/lib/deps.js`'s `has(cmd)` answers presence with `findOnPath` (PATH scan, PATHEXT on win32) instead of `execSync` through a shell.")
