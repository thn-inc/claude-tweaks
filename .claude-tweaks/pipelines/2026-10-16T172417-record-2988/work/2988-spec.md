# 2988: docs-health verify-commit: parallel judges can race the shallow-clone deepen fetch

Origin: ledger resolve gate

Defer-reason: genuinely-larger

## Current State

`plugin/bin/lib/docs-health/commit-ref.js`'s `verifyCommits` deepens a shallow clone with a single unconditional `git fetch --unshallow` when it finds `is-shallow-repository: true` (commit-ref.js lines ~181-199). Under `docs-health --budget > 1`, multiple parallel judge agents can each call `verifyCommits` against the same shared, shallow checkout concurrently. Nothing coordinates them: two (or more) processes can race the same `--unshallow` fetch on the same repo. The loser(s) see a `git fetch` failure (the first fetch already mutated the shallow boundary under them) and report `unverifiable`, even though the repo's history actually completes moments later once the winner's fetch lands. Separately, a repository too large to finish deepening within the module's `DEEPEN_TIMEOUT_MS` (120000ms) bound re-pays that same 120s fetch attempt on every single invocation, since nothing remembers that a prior deepen attempt in this run already timed out.

## Deliverables

- [ ] Add a coordination mechanism (e.g. a lock file under the repo's `.git` directory, or an in-process/cross-process mutex keyed by the resolved repo root) so concurrent `verifyCommits` calls against the same shallow repo serialize their `--unshallow` fetch rather than racing it
- [ ] A losing/waiting caller should block on (or retry after) the winner's fetch completing, then classify against the now-deepened history, rather than immediately reporting `unverifiable`
- [ ] Cache a same-run "deepen already attempted and timed out" signal (keyed by repo root) so a repo too large to deepen within `DEEPEN_TIMEOUT_MS` does not re-pay the full 120s fetch attempt on every subsequent call in the same `docs-health` invocation

## Acceptance Criteria

A new test in `tests/bin-lib/docs-health/commit-ref.test.js` (or a sibling file) simulates two concurrent `verifyCommits` calls against the same shallow clone fixture (`commit-fixtures.js`'s `cloneOf(origin, { depth: 1 })`) and asserts: (1) at most one real `git fetch --unshallow` is issued against the repo, and (2) both callers' results classify commits against complete history (no `unverifiable` outcome caused solely by the race) once the shared deepen completes. A second test asserts that a simulated deepen-timeout is not retried with a full fresh 120s fetch on a second call within the same process run.

## Release Note

No user-visible change — this hardens `docs-health`'s internal commit-verification path for the `--budget > 1` parallel-judge case; the `verify-commit` CLI's own output contract is unchanged.
