# 5790: Reuse unchanged read-only git answers within one learned-skills capture() or land() call

Origin: record #5770 Task 3 trace attribution (product-code repeats it may not fix)

Defer-reason: pre-existing-outside-diff

## Current State

Record #5770 traced every git process its `tests/bin-lib/learned-skills/` suites start (trace2 plus a per-call stack attribution, bracketed per `capture()`/`land()` call, 3,356 git calls over 303 calls). Inside a single `capture()` or `land()` call, product code under `plugin/bin/lib/learned-skills/` asks git the same read-only question more than once with no state-changing git call or target write between the two reads. #5770 forbids product-code changes, so it lists them here.

- `atHead()` (`learned-skills.js:589`, a `git diff HEAD -- <rel>`) is asked up to four times in a row by `resetToHead()` (`:601`, `:612`, `:617`, `:619`) when the tree is already at HEAD, and once more by `settle` (`:693`) with only read-only calls between.
- In the join path, the step-3 diff (`:476`) or the join diff (`:552`) is followed by `atHead()` (`:601`) with only read-only calls (`apply --check -R`, `rev-parse --short HEAD`) between; the first read already answers whether the tree differs from HEAD.
- `sameContent()` (`:372-380`) runs `hash-object --stdin --path=<rel>` on byte-identical input two or more times in one call (`:377`, `:378`, reached via `same(...)` at `:567` and `treeHolds` at `:603-604`, `:688-695`). The result is a pure function of the bytes and fixed config.
- `statusOf` (`:458`) asked at `:617` is asked again at `:672` (`finish`), and `:512` → `:617`, with only read-only calls between.
- `writeStage()` (`:248`) runs `rev-parse --short HEAD` once per staged entry inside one `land()` call (`land.js:185` → `:225`); HEAD cannot change there.

The first four fire mostly on fault/settle paths (they dominate in the capture matrix tests); the `writeStage` repeat fires on ordinary multi-entry staging. Each re-read is part of a function written to re-check state after steps that may change it, so a cache must be invalidated by every state-changing call, not keyed only by argv.

## Deliverables

1. Within one `capture()` call, a read-only git question (`diff HEAD -- <rel>`, `status`, `hash-object` of identical bytes) whose answer cannot have changed since the last identical ask reuses that answer. Any state-changing git call or write to the target invalidates it.

2. Within one `land()` call, `writeStage()` reads `rev-parse --short HEAD` once, not once per staged entry.

3. Failure handling is unchanged: every re-check that follows a step that can change tree or index state still reads git.

## Acceptance Criteria

- [ ] A test pins, for one `resetToHead()` on a tree already at HEAD, that `diff HEAD -- <rel>` runs once.

- [ ] A test pins that `land()` with N staged entries runs `rev-parse --short HEAD` once.

- [ ] A test shows a cached answer is discarded after a state-changing git call (an `apply`, `checkout`, `add` or `rm` between two asks re-reads).

- [ ] Every existing test under `tests/bin-lib/learned-skills/` passes unchanged, including the `core.autocrlf=true` variants.

- [ ] The PR body reports git processes for `tests/bin-lib/learned-skills/` before and after, counted with `GIT_TRACE2_EVENT` per file as #5770 did.

## Plan Review Clarifications

- Decided by the user at plan review: the worktree has a single writer during one `capture()` call, so "Any state-changing git call or write to the target invalidates it" means a state-changing git call or a write made through capture's own `deps` seams; a write to the target by another process between two identical asks is out of scope (Reading A, chosen). Reading not taken (B): durability re-checks — `finish()`'s residue `status` and `settle`'s `atHead` asks — always bypass the cache.
