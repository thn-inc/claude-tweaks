# 6119: Let dispatch's session drain leave driver-routable records to a drive.js --budget script job

Surface: backend
Risk-flags: public-contract

## Overview

Phase 13's expected effect is that the main session's share of cost goes to zero for driver records. A `drive.js --budget` script job drives records with no model session, but a dispatch session drain started at the same time still selects the same driver-routable records and walks them through its driver route (`drive.js --check`, mint, bind, a background call, read the final line, settle), all from a model session. The two are kept apart only by the claim race. This record adds a policy value under which dispatch's session drain leaves driver-routable records to the script job and never selects them, while `drive.js --budget` still does.

## Non-Goals

- Starting or scheduling the script job. That is a Dispatch job (thn-inc/dispatch) set up by this phase's trial sub-issue.
- Changing which records the driver admits: the predicate is the driver's own, never a copy.
- Records in bundles: the queue pull already keeps a driver-routable record out of fast-lane bundles (#6011), so only singleton groups are affected.

## Current State

- `plugin/bin/lib/express/queue.js` `expressQueuePolicy` builds `driverRoutable(issue)`: routing, pre-screen eligibility, the reviewer gate and the widened-reviewer rule. It is used only as `keepSingleton`, to keep such records out of bundles.
- `plugin/bin/lib/dispatch/queue-pull.js` `PASSES` is the ordered exclusion registry. `STAYING_EXCLUSION_REASONS` (the exclusions that keep a group in `dispatch-groups.json` but unselectable) is also `budget.js`'s `UNSELECTABLE_REASONS`, so a new staying exclusion would make the budget loop skip the same records too.
- `plugin/bin/lib/driver/budget.js` calls `deps.queuePull({ …, omit: [] })`.
- The driver's escalation marker is a trusted comment (`settle.js` `hasDriverEscalationMarker`), read by the driver's eligibility step from a live fetch with comments. The queue pull's data carries no comments, so `driverRoutable` cannot see it.
- `express-driver` (`plugin/skills/_shared/policy-schema-express-driver.md`) is `off`, `split` or `on`, and is `policyOnly`.

## Release Note

A project can now leave driver-ready records to a scheduled `drive.js --budget` job, so dispatch sessions no longer pick them up.

## Technical Approach

Reuse `driverRoutable` from `expressQueuePolicy` as the exclusion's predicate: export it beside `keepSingleton` rather than rebuilding it, so bundling and the exclusion can never disagree. The exclusion runs only over singleton groups, after grouping. The marker check is the one fact the pull lacks. Fetching comments for the few records the exclusion would remove keeps the pull's cost flat for every project that leaves the value at `session`.

The key is `express-driver-runner` and the exclusion reason is `driver-lane`; both are final. Under `express-driver: on` and `split` the exclusion set is exactly the singleton groups `driverRoutable` accepts, since that predicate already encodes the routing mode. Under `off` the value is ignored, with one stderr line per pull, printed only when the value is `script`. `driver-lane` joins `STAYING_EXCLUSION_REASONS`, and `runBudget` passes `omit: ['driver-lane']` (the pull's `omit` option takes reasons or ids, `queue-pull.js` header), so the budget loop's own pull still selects those records although its `UNSELECTABLE_REASONS` is the same registry. The marker check uses `hasDriverEscalationMarker` as its only predicate. The comment read is an injected dependency of the pull, made once for all candidate records: a record whose read fails or returns partial data stays selectable. `driverRoutable` now gates two sites, bundling and this exclusion, and a comment at its definition names both.

## Gotchas

- The starvation risk is the design's weakest point. A record that `driverRoutable` accepts from pulled data but the driver refuses on its live fetch would sit excluded from the session drain while the driver keeps refusing it. The marker is the known case and this record covers it. List any other live-fetch-only refusal reason in `steps.js`'s eligibility (open linked PRs and open blockers are already excluded by other passes) and cover each, or record why none exists.
- The live-fetch audit is a deliverable, not a judgment left to the builder. List every refusal reason in `steps.js`'s eligibility step that needs live-fetched data `driverRoutable` cannot see. Cover each in the exclusion's live check, or record why none is needed. A test enumerates eligibility's refusal reasons and fails when one is neither visible to `driverRoutable` nor covered by the live check, so a reason added later cannot silently starve excluded records.
- `script` with no script job running leaves driver-routable records unbuilt. That is the operator's choice, which is why the default is `session`. Say so in the schema row.
- Under `script`, the exclusion report prints one warn-tier line per pull naming every record it excluded (`driver-lane: left to the script job: #a, #b`). A lane that no job is draining then shows in every dispatch firing. No staleness bound returns a record to the session pool, because that would undo the opt-in whenever the job runs less often than the bound.
- `.claude/skills/dispatch-queue-exclusion-addition` lists the sites a new exclusion reason lands in. Read it before adding the pass.
- #6062 (in progress) edits `plugin/bin/lib/express/queue.js` and `plugin/bin/lib/dispatch/queue-pull.js`, the same files: it is a blocker of this record, so build on its merged result.
