# 4756: claim-targets: a network blip while bootstrapping the claims branch exits 6 instead of the transient exit 4

Blocked by #4495

Origin: #4495 review (sdd-ruling-1, PR #4723)

Defer-reason: genuinely-larger

## Current State

`claim-targets.js` bootstraps a missing `claims-registry` branch once per run (#4495, PR #4723). In `handleBranchMissing` (`plugin/bin/lib/claim-targets/claim-targets.js`), a bootstrap result that is `!ok && transient` (a secondary rate limit) takes the transient exit 4 path (`claims-branch-bootstrap-rate-limited`); every other `!ok` result exits 6 ("branch missing on origin and could not be created").

`classifyGhApiError` (`plugin/bin/lib/issues/claim-store.js`) recognises ENOENT, the secondary rate limit, 404, 422 and 409; everything else, a permission 403 or 401 included, becomes `failure: 'network-failure'`. So `ensureClaimsBranch` cannot tell a transport failure (network blip, timeout, 5xx) from a permission refusal, and a plain network blip during the bootstrap exits 6: the record is stopped as if the branch were permanently uncreatable.

#4495's review flagged this (5 lenses, tiebreak-confirmed, medium). The unattended Review Console ratified exit 6 as-is (sdd-ruling-1, run `2026-10-31T133106-record-4495`), because changing it needs the classifier split below.

## Deliverables

1. `classifyGhApiError` classifies a permission failure (HTTP 401, and HTTP 403 that is neither a secondary rate limit nor primary rate-limit exhaustion) as its own refusal outcome, distinct from `network-failure`. Every existing caller of `classifyGhApiError` / `defaultGhApi` keeps its current exit behaviour for a 403/401, or is updated deliberately with the change named in the PR.
2. `ensureClaimsBranch` reports a transport-class failure (`network-failure` after the split) as `transient`, so `handleBranchMissing` routes it to exit 4 with its own error name (for example `claims-branch-bootstrap-network-failure`), under `--keep-going` a skip, like the rate-limited case.
3. Exit 6 stays for genuine refusals only: permission 401/403, a ruleset 422 whose branch re-read succeeds and shows no branch, and 404.
4. The exit-code prose that names exit 6 (`plugin/bin/claim-targets.js` usage, `plugin/skills/flow/claim-targets.md`, `plugin/skills/dispatch/settle-and-merge.md`, `plugin/skills/_shared/issue-claims.md`, `docs/plugin-structure.md`) states that a network failure during bootstrap is transient (exit 4), not exit 6.
5. A primary rate-limit 403 or 429 (`API rate limit exceeded`, or `X-RateLimit-Remaining: 0`) stays transient, as `plugin/skills/_shared/github-rate-limit.md` already classifies it, either as `network-failure` or as its own rate-limit outcome. During the bootstrap it exits 4, never 6. (Plan-review decision 2, Reading B.)
6. A bootstrap `POST git/refs` that answers 422 and whose follow-up `claimsBranchExists` re-read fails (returns `null` on a network failure) is transient: it exits 4 with `claims-branch-bootstrap-network-failure`, not 6. The existing claim-store test "POST git/refs 422 with an unreadable branches endpoint is a refusal" is rewritten to pin the transient outcome. (Plan-review decision 1, Reading B.)

## Acceptance Criteria

- [ ] A unit test feeds `classifyGhApiError` an HTTP 403 (not a secondary rate limit) and an HTTP 401 and gets the new refusal outcome, not `network-failure`; it fails against the current classifier.
- [ ] A `claim-targets` test with a bootstrap whose create call fails with a transport error (no HTTP status) exits 4 with the new error name, and under `--keep-going` skips that target; it exits 6 against the current code.
- [ ] A `claim-targets` test with a bootstrap refused by a permission 403 still exits 6 and prints the one-line reason.
- [ ] The secondary-rate-limit bootstrap case still exits 4 (`claims-branch-bootstrap-rate-limited`).
- [ ] No remaining exit-code prose says a network failure during bootstrap exits 6.
- [ ] A `classifyGhApiError` test with a primary rate-limit 403 (`API rate limit exceeded`, no `Retry-After`) gets a transient outcome, not the new refusal outcome.
- [ ] A claim-store test with `POST git/refs` → 422 followed by a failed (`null`) branch re-read gets a transient result, and a `claim-targets` test with that bootstrap exits 4 with `claims-branch-bootstrap-network-failure`.

## Release Note

A network blip while the plugin creates the claims branch is now retried on a later run instead of stopping the record as if the branch could never be created.

- `tests/bin-lib/issues/claim-store.test.js` — classifier and bootstrap cases
- `tests/bin-lib/claim-targets/claim-targets.test.js` — exit 4 vs exit 6 bootstrap cases
