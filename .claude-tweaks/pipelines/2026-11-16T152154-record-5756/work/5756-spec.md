# 5756: Even out the test shards: one shard per run takes about twice as long as the others

Surface: infra

**Related:** #5685, #5387
Risk-flags: none

## Current State

The PR gate (`.github/workflows/test.yml`) runs `npm test -- --shard i/4`. `tools/run-tests.js`'s `assignShards` deals test files heaviest-first onto the lightest shard, weighing each file by `tools/test-durations.json` plus a 150 ms per-file startup cost. A file missing from that map weighs the median measured file, 24 ms, so about 0.17 s with the overhead.

The record's premise needs correcting. Measured on the 12 most recent green `test.yml` runs (2026-11-16), the "Run this shard of the suite" step took:

- Shard 1/4: 55-198 s, median about 77 s. It was the slow shard in 2 of 12 runs.
- Shards 2, 3 and 4 were each the slow shard in several runs (4 once, 2 four times, 3 four times, 1 twice).
- Every run has exactly one shard at 120-200 s while the other three sit at 55-90 s. The slow shard rotates from run to run, so the wait is set by one outlier shard per run, not by shard 1.

Cause, from the CI logs and the downloaded shard TAP output:

- `tools/test-durations.json` was last refreshed on 2026-11-14, before #5229/#5230 landed. 135 of the 1,268 test files are absent from it (34-37 per shard, per the `unmeasured in tools/test-durations.json` line every shard prints).
- Four of the largest test files in the repo are unmeasured: `tests/bin-lib/driver/run.test.js` (415 KB, the largest), `tests/bin-lib/dispatch/queue-pull.test.js` (246 KB), `tests/bin-lib/driver/merge.test.js` (208 KB) and `tests/bin-lib/driver/review.test.js` (123 KB). Each weighs about 0.17 s in the partition, the same as a trivial file, so they are dealt last, onto whichever shard happens to be lightest, and which shard that is shifts as PRs add or remove files.
- `queue-pull.test.js` alone runs about 125 s. In the run where shard 2 took 191 s, its `#5227 parity` describe blocks took 91.6 s, 16.6 s and 16.1 s in one process, and a file is the smallest unit the partition can place. Even a perfect partition leaves the shard holding that file at 125 s or more, so the roughly 100 s target also needs the file split.
- The largest measured file in the map is 20 s (`tests/bin-lib/verify/cli.test.js`), so no already-measured file is oversized.

## Deliverables

1. Refresh `tools/test-durations.json` with `node tools/run-tests.js --record-durations tools/test-durations.json` on a quiet machine (`docs/journeys/ci-test-gate.md` documents the procedure), so every committed test file has an entry.
2. Read the refreshed map for any file above 40 s. Split each such file along its top-level `describe` boundaries into sibling files, moving shared fixtures and helpers into a helper module under `tests/helpers/` rather than copying them. `tests/bin-lib/dispatch/queue-pull.test.js` is the known case: its four `#5227 parity` describe blocks (AC1, AC5 portability, AC4 fetch failures, AC7.2 files inputs) become separate files. Re-run `--record-durations` after the split so the map reflects the new files.
3. Add two guards to `tests/run-tests-shard.test.js`, so the cause cannot return unnoticed: (a) every committed test file larger than 100 KB has an entry in `tools/test-durations.json`, with a failure message naming the refresh command; (b) no entry in `tools/test-durations.json` exceeds 40,000 ms, with a failure message telling the author to split the file.
4. Record the before/after shard times in the PR description (the 12-run table above against the PR's own green `test.yml` run).

## Release Note

Even out the PR test gate's four shards so one slow shard no longer sets a roughly 3-minute wait.

## Technical Approach

Refresh first, so the refreshed numbers say which files still need splitting rather than guessing. The refresh is a whole-suite run: use `--record-durations` on a quiet machine, with no sibling agents running tests, because concurrent load inflates the per-file numbers and skews the weights (the `PER_FILE_OVERHEAD_MS` comment in `tools/run-tests.js` explains the overhead model). The partition itself (`assignShards`) is sound: it deals heaviest-first onto the lightest shard, and with stale inputs it still estimated 314 s on each of the four shards in the logged run, so the estimate is balanced and the actuals are not. Leave the algorithm unchanged.

Splitting `queue-pull.test.js`: the file's own helpers sit above line 2678 and are shared by every describe block; `tests/bin-lib/dispatch/queue-pull-fixtures.js` and `queue-pull-oracle.js` already exist beside it. Move the shared helpers into one new module in that same directory and import it from each new file, keeping the existing tests' names byte-identical so the test-impact map and the `#5227` references still resolve. Live references to the old file name that this change must update: `docs/journeys/select-the-dispatch-queue-with-the-queue-pull-cli-5227.md` (lines 8 and 50), the comments naming it in `plugin/bin/lib/dispatch/queue-pull.js` (lines 36, 65, 1154; the last says the test "pins this list", so the pinning test must stay in a file that still exists), and the `docs/plugin-structure.md` row for the directory. Run `git grep -n "queue-pull.test"` again at build time, since the list moves.

The size guard uses 100 KB as the floor because only a handful of files are that large, so a typical new test PR never has to refresh the map. A new file that crosses it fails the guard and names the one command that fixes it. Files below the floor stay unmeasured-tolerant, as today.

## Gotchas

- Do not "fix" the algorithm. `assignShards` is balanced by its own estimates; the imbalance comes from unmeasured heavy files and one file larger than a shard's fair share.
- The record's claim that shard 1 is the heavy one does not hold in the 12-run sample. A PR that only reorders or pins shard 1 would not help; check the result against all four shards, in more than one run.
- Run the refresh with nothing else running. A load-inflated map overweights whatever file happened to run during the spike, which recreates the same kind of skew.
- Windows regression sharding is a separate job and a separate record (#5685). Leave `tools/windows-regression` alone. It reads the same `tools/test-durations.json`, so a complete map helps it too, but its own shard count and command-line length limit are not in scope here.
- #5387 (open, `ready`) changes `plugin/bin/lib/dispatch/queue-pull.js` to call sibling CLIs in-process. It may shorten the parity tests and will edit the same module this change touches only in comments. If it merges first, re-measure `queue-pull.test.js` before deciding whether the split is still needed.
- The `tests/bin-lib/driver/*.test.js` files are large but their run time is unknown until the refresh. Split them only if the refreshed map puts them over 40 s.
