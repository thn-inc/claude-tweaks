# 2567: shared-primitives: the fixed 5 s GH_TIMEOUT_MS makes the first gh call fail on a GitHub Enterprise Server host

Surface: infra

## Current State

`plugin/bin/lib/shared-primitives.js` hard-codes `const GH_TIMEOUT_MS = 5000;` (line 55) and exports it for every direct `gh` subprocess call across the plugin. Consumers include `plugin/bin/claim-targets.js`, `plugin/bin/materialize.js`, `plugin/bin/lib/compose-subject.js`, `plugin/bin/lib/repo-resolve.js`, `plugin/bin/lib/reconcile/release-merged.js`, `plugin/bin/lib/worktree/cherry-pick-provenance.js`, `plugin/bin/lib/hooks/teardown-run.js`, and `plugin/bin/lib/issues/claim-store.js`.

Against a GitHub Enterprise Server host behind corporate networking, the first `gh` call of a session regularly exceeds 5 s (observed 5-10 s cold-call latency). When that happens, `reconcile`'s `release` check (`release-merged.js`) misclassifies the slow response as `network-failure`, and `claim-targets.js` / `release-claim.js` / `resolve-blockers.js` fail outright until a human retries once `gh` is "warm." There is currently no way to raise this bound — it is a single unconditional module constant, not a policy-driven or environment-driven value.

## Deliverables

1. A configurable timeout bound for `GH_TIMEOUT_MS`, resolved with precedence: env override > project policy (`.claude-tweaks/policy.yml`) > the existing 5000ms default.
2. A new policy key (e.g. `gh-timeout-ms`) registered in `plugin/bin/lib/policy-schema.js` alongside its validation (positive integer, sane upper bound).
3. One automatic retry on a `gh` subprocess timeout in the shared runner path (`runClassified`/`runClassifiedAsync` in `shared-primitives.js`), so a single slow cold call does not fail the calling CLI outright.
4. `reconcile`'s `release` check stops reporting `network-failure` for a call that times out only because the configured bound was too low and a retry would have succeeded — the retry must run before that classification is emitted.

## Acceptance Criteria

- With no env override and no policy key set, `GH_TIMEOUT_MS`-driven behavior is unchanged (default remains 5000ms) — existing tests for `shared-primitives.js` and its consumers pass unmodified.
- Setting the new policy key in `.claude-tweaks/policy.yml` to a higher value (e.g. 10000) raises the effective timeout used by every consumer listed in Current State, verified by a unit test that stubs the runner and asserts the timeout value passed to the underlying subprocess call.
- An env override (e.g. `CLAUDE_TWEAKS_GH_TIMEOUT_MS`) takes precedence over the policy key when both are set, verified by a unit test covering the precedence order.
- A `gh` call that times out once and then succeeds on retry returns the successful result to the caller, not a `network-failure` classification — verified by a unit test using a fake runner that fails the first invocation with a timeout and succeeds the second.
- A `gh` call that times out on both the initial attempt and the retry still surfaces a clear, distinguishable failure (not silently swallowed) — verified by a unit test asserting the final classification/error after both attempts are exhausted.
- `npm test` passes in full after the change.

## Technical Approach

Add a policy key (`gh-timeout-ms`) to `plugin/bin/lib/policy-schema.js` following the existing key-registration pattern in that file, with a numeric validator and documented default (5000). Read it via `plugin/bin/lib/policy.js`'s existing resolution helper rather than re-implementing YAML lookup. Resolve the effective timeout in `shared-primitives.js` with precedence env var > policy > hard-coded default, computed once per process (not per call) to avoid re-reading policy on every `gh` invocation.

Add a single automatic retry to the shared runner functions (`runClassified`/`runClassifiedAsync`) gated specifically on a timeout classification (not on every failure — a real auth error or a 404 should not be retried). The retry uses the same resolved timeout value; it is not a second, longer window.

Update `plugin/bin/lib/reconcile/release-merged.js` so the `network-failure` classification is only emitted after the retry (built into the shared runner) has also failed, so a single slow cold call under the old fixed bound no longer reaches that classification at all once the retry exists.

### Key Files

- `plugin/bin/lib/shared-primitives.js` — resolve `GH_TIMEOUT_MS` from env/policy/default instead of a fixed constant; add the one-retry-on-timeout behavior to `runClassified`/`runClassifiedAsync`.
- `plugin/bin/lib/policy-schema.js` — register the new `gh-timeout-ms` policy key with validation and documented default.
- `plugin/bin/lib/policy.js` — no structural change expected; used to resolve the new key via its existing helper.
- `plugin/bin/lib/reconcile/release-merged.js` — confirm/adjust the `network-failure` classification path now that a timeout is retried once before that classification is reached.
- `plugin/bin/claim-targets.js`, `plugin/bin/materialize.js`, `plugin/bin/lib/compose-subject.js`, `plugin/bin/lib/repo-resolve.js`, `plugin/bin/lib/worktree/cherry-pick-provenance.js`, `plugin/bin/lib/hooks/teardown-run.js`, `plugin/bin/lib/issues/claim-store.js` — consumers of `GH_TIMEOUT_MS`; no code change expected beyond picking up the new resolved value automatically via the shared export, but each needs a read-through to confirm none re-derives its own fixed timeout locally.

## Gotchas

- The retry must be scoped to timeout classifications only — retrying an auth failure or a real 404 against a slow host would mask a different bug as a timeout.
- A retry doubles worst-case latency for a genuinely down host; keep the retry count at exactly one (per the record's own proposal) rather than escalating to a backoff loop, to avoid turning a fast failure into a slow one.
- Per `gh-api-module-pattern`'s CLI deps contract, `shared-primitives.js`'s runner functions take an injectable runner — the retry logic must be exercised through that seam in tests (a fake runner), not by shelling out to a real slow `gh` call.
- Reading policy on every `gh` invocation would add filesystem I/O to a hot path; resolve the effective timeout once per process and cache it.
