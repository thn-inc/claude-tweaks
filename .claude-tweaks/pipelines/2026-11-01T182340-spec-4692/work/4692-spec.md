# 4692: Merge mode's MERGED-PR next step may dead-end: does cleanup-only resolve an archived run?

Surface: backend

**Related:** #4718, #4798, #4797, #4251

## Current State

`plugin/skills/wrap-up/merge-mode.md`'s Preconditions stop on any PR that is not `OPEN`. For a `MERGED` PR (an `armed` run's auto-merge, or a human merge on GitHub, landing before `/claude-tweaks:wrap-up #{n} merge` is typed) the report names `/claude-tweaks:wrap-up #{n} cleanup-only` as the next step. `tests/wrap-up-merge-mode-conformance.test.js` pins that sentence (`merged-pr-next`).

Probed on 2026-11-01 (shaping, against `origin/main` afac7a84d and the installed 6.156.1 build):

- **`cleanup-only` cannot reach an archived run.** `plugin/skills/wrap-up/flags.md`'s `cleanup-only` bullet skips Phase 1, and Phase 1 is where wrap-up resolves its run dir, so the flag's run-dir lookup is unstated. The only resolver it could fall back to is Phase 1's: `resolve-run-dir --spec-slug {slug}` without `--archived`. Against the real archived run `.claude-tweaks/pipelines/archive/2026-10-31T145027-spec-4704/` (`status: clean`, `pr` object present, `worktree: null`, `worktreeAtClose` set), `PIPELINE_RUN_DIR= hooks.js resolve-run-dir --spec-slug spec-4704` exits 1, `no pipeline run directory resolved`. Phase 1's own fallback on that miss is `--standalone … --create`, which mints a stray `-standalone` dir. So the next step merge mode names either finds nothing or creates exactly the shadowing dir merge mode's own Resolve-the-run section refuses to mint.
- **The reconciler does not finish an archived run's post-merge closes either.** `plugin/bin/lib/reconcile/post-merge.js`'s `candidateRuns` reads only `listRunDirsWithState` (live dirs plus live `clean` dirs). `archive/` is outside that walk, which merge-mode.md line 13 already states. The archived case is the common one for merge mode: wrap-up's Phase 4 closes and archives a `pending-review` pr-first run while its PR is still open. When that PR later merges outside a session, `_shared/pr-first-merge-post-merge.md` Steps 4.0 (reopen what the merge closed by mistake) and 4.0b (close below-floor parents) never run for it. Worktree reap (`reap-merged.js`, keyed on the worktree list) and claim release (`release-merged.js`) do not depend on the run dir being live.
- For a merged run that is still live (an `armed` run inside the 10-minute merge grace), the reconciler's `post-merge`, `archive-merged`, `reap-merged` and `release-merged` checks complete it convergently, guarded by the run's post-merge marker (`MARKER_STEP` in `decisions.md`) and a per-run `.post-merge.lock`.

Decision (agent call, made at shaping after the requester skipped design questions): merge mode finishes the post-merge work itself when it finds the PR already `MERGED`, on the run it has already adopted and bound to `#{n}`, live or archived. It does not hand off to `cleanup-only`. `cleanup-only` does not learn to adopt archived runs: archived is terminal (#208), and its one real caller, `/claude-tweaks:dispatch`'s first-call-failure teardown, always passes an inherited `PIPELINE_RUN_DIR`. `cleanup-only`'s run-dir lookup is still stated, so it can never mint a stray dir.

Inside the grace, use the in-session arguments, so the settle poll still catches the closes GitHub makes about 2 s after the merge. Take and release the same per-run `.post-merge.lock` claim, then write the marker, so a background reconcile pass and this session never both run them. Prefer calling one entry point that `post-merge.js` exports or a `hooks.js` verb exposes over restating its arguments in prose. ## Release Note

Fix `/claude-tweaks:wrap-up #N merge` on an already-merged PR: it now finishes the post-merge work itself, including for an archived run, instead of pointing at `cleanup-only`, which could not find that run.

## Technical Approach

Merge mode already holds everything the already-merged path needs. That is the run adopted through `--archived`, bound to `#{n}` by `config.yml`'s `spec:`, with `{worktree-path}` falling back to `worktreeAtClose`. It also has the exact post-merge step list its own `merged` outcome runs. The already-merged path is that list minus the merge, plus the guards that make it safe to run late and twice: the reconciler's marker and lock, and the reconciler's bounded reopen window instead of the in-session 15 s poll. Writes into an archived run go to the path it was adopted from, as Resolve-the-run already states. Step 4.2's reconcile never re-opens an `archive/` run.

The live-run case (`armed`, merged within the grace window) takes the same path. The marker and lock make it safe against a background reconcile pass racing the session. Whichever runs first writes the marker, and the other one no-ops.

## Gotchas

- Do not run Step 4.0 with the in-session arguments on a late merge. Its reopen covers every record closed after `mergedAt`, and without the reconciler's `--close-window-ms` bound a deliberate close made days later gets reopened.
- An archived run is terminal (#208) for adoption by any resolver except merge mode's read-only `--archived` path. Do not widen `--archived` to `cleanup-only` or any other caller: `pipeline-run-dir.md`'s `--archived` bullet names merge mode as its only caller on purpose.
- Writes into `archive/{run-id}/decisions.md` must go to the adopted path. A write to the live path would recreate a live dir for an archived run-id, which `resolve-run-dir` then refuses as a resurrected copy.
- The installed 6.156.1 build predates #4677 (`--archived` is ignored there), so a live probe needs this checkout's `plugin/bin/hooks.js`, not the plugin cache copy.
- #4797 (open) replaces `post-merge.js`'s hand-rolled `takeClaim` with a liveness-checked, owner-released claim. Call whatever claim `post-merge.js` exports at build time, never a copy of it, so the two paths keep sharing one lock.
- Do not use `--settle-ms 0` on a merge younger than `MERGE_GRACE_MS`. GitHub closes `Fixes` records about 2 s after the merge, so a zero settle can read them as still open and skip a reopen that was owed.

## Current State

`plugin/skills/wrap-up/merge-mode.md`'s Preconditions handle a PR that is already `MERGED`. That happens when an `armed` run's auto-merge lands before the human types `merge`. In that case the report names `/claude-tweaks:wrap-up #{n} cleanup-only` as the next step.

After #4677, merge mode can adopt a closed or archived run through `resolve-run-dir --archived`. So it can now reach that branch for a run that reconcile has already archived.

`plugin/skills/wrap-up/flags.md` says `cleanup-only` skips Phases 1-4 and runs only `cleanup-procedures.md`'s items. Nothing states how it resolves its run dir. Phase 1's resolver ignores `archive/` and refuses a closed run (#4151), so on an archived run `cleanup-only` may find nothing, or mint a stray `-standalone` dir. That was raised as a Minor in #4677's whole-branch review and not verified.

## Deliverables

- Probe what `/claude-tweaks:wrap-up #{n} cleanup-only` does for a run already closed and archived after its PR merged.
- Make merge mode's MERGED-PR next step point somewhere that works for that state.
