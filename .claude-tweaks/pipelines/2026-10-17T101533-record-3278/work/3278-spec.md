# 3278: dispatch: transitive file-overlap grouping through hub files starves records in oversized groups

Surface: infra

**Related:** #1228, #1365, #1420, #3014, #3226, #2912, #2975, #3079, #3160, #3338, #3362

## Current State

Dispatch's queue pull (`plugin/skills/dispatch/queue-pull-script.md`) partitions the authorized queue with `groupByFileOverlap` (`plugin/bin/lib/issues/grouping.js`), the transitive closure (union-find) of shared `### Key Files` entries. A record is then dispatched together with its whole group: `plugin/skills/dispatch/SKILL.md`'s `#N` form pulls "its whole file-overlap group," and `plugin/skills/_shared/issue-claims.md`'s Group claiming rule forbids claiming one member alone. Bare drain skips any group over `dispatch-group-size-guard` (default 10) entirely (`oversized-group-report.md`, #1228).

**The filed framing ("hub files") was checked and is wrong.** Hub-path exclusion already ships (#1365): a path cited by at least `max(3, ceil(pool × 0.1))` eligible records never links two records, and bare-directory entries never link anything (#1420). A reproduction on 2026-10-17 against the live queue gave these numbers:

- 61 eligible records, so the hub threshold is 7.
- The most-cited paths: `plugin/bin/hooks.js` and `plugin/skills/review/code-mode-steps.md` are cited by 4 records each, and `docs/hooks.md` by 3. The hub exclusion never fires.
- One 18-record group (3289, 3266, 3226, 3079, 3047, 3035, 3030, 3026, 3021, 3018, 3015, 3014, 3004, 2986, 2977, 2887, 2869, 2734), held together by 25 direct, real overlaps on specific files.
- Inside it, tight sets that really do share a file: 4 records on `hooks.js`, 4 on `code-mode-steps.md`, 3 on `flow/manifesto.md`. These sets are joined by single-file links such as `flow/multi-spec.md`, `policy-schema.js`, `build/SKILL.md` and `issues/autonomy.js`.

Lowering the hub threshold to break the chain would also split the 4 `hooks.js` editors, the one case where concurrent builds really collide. The underlying defect is that dispatch answers "these two must not be in flight at the same time," a relation between pairs, with "build the whole chain as one run." The chain grows transitively until no member can be dispatched: by name only as an 18-record bundle, and under bare drain not at all.

Dispatch already builds groups one at a time within a firing (`SKILL.md` Step 5). Conflicts that do happen at merge already have a handler: `plugin/skills/_shared/pr-first-merge.md`'s Conflict path merges `origin/main` and retries, or parks the PR `pending-review` for a human.

**Decided (2026-10-17 brainstorm on this record):**
- Each record dispatches as its own group.
- The only guard against concurrent overlap: a record waits while one of its direct neighbours holds a live claim.
- Everything else is left to the existing post-build conflict path.

## Deliverables

1. Dispatch's queue pull stops grouping by transitive file overlap. Every eligible record is its own group before fast-lane bundling. `groupByFileOverlap` itself is unchanged, because flow's multi-spec conflict detection, parallel waves, `preflight-records` and ranking's overlap set all keep using its full-chain output.
2. A new pure function in `grouping.js` returns, for each eligible candidate, its in-flight direct neighbours.
   - A neighbour is a record holding a live claim that shares at least one linking file with the candidate. A linking file is never a bare directory and never a hub path.
   - Hub paths are computed with the same `computeHubPaths` rule and constants `groupByFileOverlap` uses, over the candidates plus the in-flight records.
   - The function returns `[{ number, files }]` per candidate.
3. A neighbour-in-flight pass in the queue pull:
   - Its pool is open records carrying `bot:in-progress`, confirmed live by reading their claim blob with `classifyClaimBlob`. The label alone never counts.
   - For each candidate with an in-flight neighbour it appends `{reason: 'neighbour-in-flight', records: [n], detail: {neighbours: [{number, files}]}}` to `dispatch-exclusions.json`.
   - The reason does not remove the candidate: it stays in `dispatch-groups.json`.
4. Bare drain's ranking excludes groups with a `neighbour-in-flight` member (the same `groupIsExcluded` reasons list `oversized` and `firing` use), so the record is picked up by a later firing. `#N` and `#N,#M` print a one-line report naming the neighbour and shared files, then dispatch anyway, the same posture oversized groups get.
5. Fast-lane bundling (`bundleFastLaneSingletons`) never puts two records that share a linking file in the same bundle. Disjointness used to hold because separate groups were disjoint by construction; that no longer holds once every record is its own group.
6. The size guard and its policy key `dispatch-group-size-guard` stay. A group can still exceed the guard only when `dispatch-fastlane-bundle-cap` is configured above it, and the prose says so.
7. Prose updates:
   - `dispatch/SKILL.md` Steps 2-3, including the `#N` bullet and the reporting line for the new reason.
   - `queue-pull-script.md`'s reason list.
   - `next-ranking.md` and `firing-exclusion.md`, for the reasons list.
   - `oversized-group-report.md`.
   - `_shared/issue-claims.md`'s Group claiming: claiming every member now applies to fast-lane bundles only.
   - `dispatch/design-notes.md`: record this decision and the three rejected alternatives from the original request.
8. Unit and conformance coverage per the Acceptance Criteria below.

## Release Note

Dispatch no longer chains a record to every record its files transitively overlap with; each record builds on its own, waiting only while a record that shares a file with it is mid-build.

## Technical Approach

Change dispatch's use of the grouping helpers, not `groupByFileOverlap` itself. In the queue-pull grouping script, replace the `groupByFileOverlap(items)` call with one group per eligible record. Then compute in-flight neighbours and pass the same neighbour relation into `bundleFastLaneSingletons` through a new option (for example a `conflicts(a, b)` predicate or an adjacency map), so bundling stays disjoint. Run the size guard last, as today.

**Getting the in-flight pool.** Take the open-issues fetch the script already holds and keep the records carrying `bot:in-progress`. Narrow them to those sharing a linking file with at least one candidate. Only for those, read the claim blob with the readers the near-duplicate refusal in `/claude-tweaks:specify`'s shaping mode already uses: `readClaimBlob`, chained from the first read's git tip so the whole pass costs one fetch, then `classifyClaimBlob`. Treat a record as in flight only on `live`.

**Failure handling.** A read failure fails open: count the record as not in flight and log one `AUTO` line. That is consistent with the decision to leave conflicts to the post-build path, rather than inventing a new reason to starve a record.

**Wiring the new reason.** Append the exclusion with the existing `appendExclusion`. Add `'neighbour-in-flight'` to the `groupIsExcluded` reasons in `next-ranking.md`'s script, and to `firing-exclusion.md`'s matching statement. Add the reason to the named-form report the way `oversized` is reported: a report line, not a removal.

## Gotchas

- **Byte headroom is tight.** `queue-pull-script.md` is 46,248 B and `dispatch/SKILL.md` is 46,022 B, against a 51,200 B `CEILING_BYTES`; `_shared/issue-claims.md` is 45,048 B. The neighbour pass may need its own sibling sub-file, cited from the queue pull, rather than inline growth.
- **Leave `groupByFileOverlap` alone.** It has five other consumers: ranking's `computeOverlapSet`, `preflight-records`, flow's `waves.js` (which deliberately disables hub exemption), flow's multi-spec conflict detection, and `/help`. Changing its semantics would silently change all of them.
- **The `bot:in-progress` label is a projection that outlives builds.** Gating on it alone would recreate today's starvation through stale labels. Only a `live` claim counts.
- **Accepted gaps (decided, not to be fixed here):**
  - Two firings that pick neighbouring records at the same moment both build, and the second resolves at merge.
  - A conflict at the same lines parks the PR `pending-review` for a human.
  - Settle's existing note that `close-run` has already run when a conflict is found at auto-merge.
  - Tests that pin exact bytes across files can turn two green branches red at merge with no textual conflict. File-overlap grouping never caught that, before or after this change.
- **No `breaking` label.** No flag, policy key, exported function or hook payload is removed or renamed. The `#N` form's behaviour narrows, from "whole chain" to "the record or its fast-lane bundle," and that goes in the release note.

## Current State

`groupByFileOverlap` (`plugin/bin/lib/issues/grouping.js`) builds dispatch's file-overlap groups as the transitive closure of shared `### Key Files` entries. High-fan-in hub files (`plugin/bin/hooks.js`, `docs/hooks.md`, `plugin/skills/review/code-mode-steps.md`, `plugin/skills/build/SKILL.md`) chain records that share no file into one group.

Observed 2026-10-16 (plugin 6.140.0): `/claude-tweaks:dispatch #3000,#3034,#3014` resolved #3014 to a 20-record group (size guard 10). #3014 directly overlaps only #3226 (`plugin/bin/lib/flow/preflight.js`, `plugin/skills/flow/steps-and-gates.md`); the rest joined through chains such as #3226 → #3018 (`policy-schema.js`) → #2734 (`flow/manifesto.md`) and the `hooks.js`/`docs/hooks.md` cluster. The group mixes two "Evaluate…" research records with `risk:high` #2734.

Effect: no member can be dispatched by name without bundling all 20, because `_shared/issue-claims.md`'s group-claim rule forbids claiming a member alone, and bare drain excludes oversized groups entirely (`oversized-group-report.md`, #1228). All 20 records starve unless a human bypasses dispatch with a direct `/claude-tweaks:flow`.

## Deliverables

- A grouping change in `plugin/bin/lib/issues/grouping.js` so that one hub file no longer merges otherwise-unrelated records into a single oversized group.

- Matching prose updates in `plugin/skills/dispatch/SKILL.md` Step 3 and `plugin/skills/dispatch/oversized-group-report.md`.

- Unit coverage in the grouping tests: a fixture of records chained only through a hub file must not form one group.

## Open Question

Which grouping rule replaces plain transitive closure? There are three viable directions, and none is chosen yet:

1. **Exclude hub files from the overlap key.** Drop any path that appears in more than N queue records' Key Files. This is simple, but it lets two records that really do edit the same hub file build concurrently and conflict at merge.

2. **Split oversized groups at their weakest edges.** Cut the edges that rest on a single shared file until each component fits under the guard. This keeps real conflicts together, but it needs a deterministic cut rule so racing firings converge on the same split.

3. **Let `#N` select only the named record's direct-overlap neighborhood.** This leaves bare drain unchanged. It is the smallest change, but it doesn't help bare drain, where the whole group still starves.
