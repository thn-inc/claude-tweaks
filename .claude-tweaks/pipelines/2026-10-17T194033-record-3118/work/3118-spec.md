# 3118: build: Common Step 5 has no rendered check for a `surface: web` record, so a plan's final "full verification incl. browser pass" task loses its browser pass when folded into it

Surface: backend

## Current State

A `surface: web` plan ended with a verification task: "run the full suite, then do a real-browser pass at 390 px and 1280 px in both themes before review." The controller ruled the task "runs as Common Step 5, not as an SDD task", citing `dispatch.md`. "Step 5 ran the suites with no browser." The browser pass then ran only at `/flow`'s later `/review` visual check. It found a medium defect (a sentence pushed off-screen at phone width) and four lows, which cost a fix wave and a scoped re-review after the full code review had already run.

Verified on origin/main (0af440d76):

- `plugin/skills/build/dispatch.md:19`, in the whole-branch reviewer instruction: "Common Step 5 runs the full suite once, after the review's fix wave … and is the producer of the runner-written pass stamp". No text says what happens to a plan task's non-runner steps. The fold is the controller's inference from that sentence.
- `plugin/skills/build/SKILL.md:266-272` (Common Step 5) runs `skills/test/verification.md`, which covers types, lint, and tests only. It has no rendered-check branch and no SKIP for a planned step that did not run.
- The SKIP convention to reuse: `_shared/auto-decision-log.md:151` (Degrade-trace rule), written with `log-decision.js --status SKIP --section "/build"` (as at `dispatch.md:17`). The standalone carrier is `build/handoff-template.md:42-52` ("Skipped steps — the no-run-dir carrier").

## Deliverables

1. Decision (approved in brainstorming, 2026-10-15): narrow the fold. Common Step 5 absorbs only a folded plan task's test-runner work (types, lint, tests via `test/verification.md`). Every other step that task names — a browser check, a manual check, a script — either runs as its own build step or is logged as an explicit `SKIP` line, so it is never silently dropped. Rejected: adding `/browse` to Step 5, which puts a browser dependency in every web build's verification. Also rejected: a plan-authoring check that moves browser steps out of verification tasks, which doesn't catch existing plans.
2. `build/dispatch.md`: right after the `:19` "Common Step 5 runs the full suite once" sentence, add the fold rule. A plan task folded into Common Step 5 contributes only its runner checks. Each other step it names runs after Step 5 passes and before Common Step 7's handoff: a browser check through `/claude-tweaks:browse`, a script by running it. A step that cannot run (no browser backend, no dev server, a truly manual check) writes `SKIP {time} — {plan task} step "{step}" (skipped): {condition} → not run by /build; surfaced for /review. Reversibility: n/a.` via `log-decision.js --status SKIP --section "/build"`. Standalone `/build` lists it in the Step 7 handoff's Skipped steps section instead.
3. `build/SKILL.md` Common Step 5: one short sentence pointing at the Deliverable 2 rule. It must also apply under the `batched` execution strategy, which never reads `dispatch.md`'s subagent procedure.

## Original request

build: Common Step 5 has no rendered check for a `surface: web` record, so a plan's final "full verification incl. browser pass" task loses its browser pass when folded into it

**Summary:** `build/dispatch.md` makes Common Step 5 the single full-suite run. A controller therefore folds a plan's last task ("full verification, no new code") into Step 5. But Step 5 runs only the verification runner (types, lint, tests), so any other step in that task, such as a real-browser pass at phone and desktop widths, is silently dropped.

**Kind:** Gap

**Affected component:** `skills/build/SKILL.md` Common Step 5 (Final Verification) and `skills/build/dispatch.md` (the final-review instruction that names Step 5 as the one full-suite run)

**Use case:** A `surface: web` record's plan ends with a verification task: run the full suite, then do a real-browser pass at 390 px and 1280 px in both themes before review. Three earlier tasks had each reported their narrow-width behaviour as unverified. The project expects someone to look at the rendered page before the code reviews read it, because finding layout defects only at review has cost it a fix round before.

During the build, the controller ruled that the task "runs as Common Step 5, not as an SDD task", citing `dispatch.md`, and Step 5 ran the suites with no browser. The final reviewer flagged the missing browser pass, and the controller ruled it satisfied by `/flow`'s later `/review` visual check. That check then found a medium defect (a sentence pushed off-screen at phone width) and four lows. Fixing them took a fix wave and a scoped re-review, after the full code review had already run.

Nothing in `/build` gives the browser step a place:
- Step 5 has no rendered-check branch for a web surface.
- `dispatch.md`'s "runs the full suite once" reads as covering the whole verification task.
- No `SKIP` degrade-trace records that a planned browser step did not run.

**Definition:** Needed — whether the fix belongs in Step 5 (run a rendered check through `/claude-tweaks:browse` when the record is `surface: web` and the plan names a browser step) or in the fold rule (Step 5 absorbs only a plan task's runner checks, and any other verification step runs as its own build step or logs a `SKIP`) is a maintainer design choice.

**Suggested fix:** at minimum, say in `dispatch.md`/Step 5 that folding a plan's verification task into Step 5 covers only what the runner runs. Any other step that task names (a real-browser pass, a manual probe) either runs before `/build` hands off or is logged as a `SKIP` with its condition, so `/review` and the human can see it was not done. Optionally, give Step 5 a rendered-check branch for `surface: web` records.

**Plugin version:** 6.138.0
