# 3298: Merge-subject --scope: define where the scope comes from and pass it from every merge fence

Surface: infra

**Related:** #3269, #3297, #3377, #3405

## Current State

`plugin/bin/compose-subject.js` is the one command every merge fence runs to get a Conventional-Commits merge subject. #3028 added `--scope <token>` to it: `plugin/bin/lib/compose-subject.js:84-87` parses the flag and `plugin/bin/lib/compose-subject.js:293` hands it to `composeSubject`, which renders `type(scope)[!]: {title} (#N)` and refuses a non-token or over-long scope (`plugin/bin/lib/release/subject.js:77-86`). Nothing resolves the value: there is no `.claude-tweaks/policy.yml` key, no record field, and no derivation rule, so an agent at a merge fence has to invent one.

Six composer call lines exist across five fence files, and only one file mentions the flag. `plugin/skills/_shared/pr-first-merge.md:277` and `plugin/skills/_shared/pr-first-merge.md:315` (the two squash sites) are covered by the prose at `plugin/skills/_shared/pr-first-merge.md:292`, "Append `--scope {scope}` when the project's commit convention requires `type(scope):`"; the four local-merge fences — `plugin/skills/_shared/local-merge-auto-finish.md:118`, `plugin/skills/wrap-up/auto-merge-short-circuit.md:268`, `plugin/skills/dispatch/settle-and-merge.md:400`, `plugin/skills/flow/worktree-merge.md:63` — say nothing about scope. `docs/journeys/merge-a-record-with-a-conventional-subject-2251.md:29` states the limitation: "today only `_shared/pr-first-merge.md` Step 3 instructs this; the four local-merge fences don't yet".

Three facts constrain the design. `policy.yml` is read by a flat `key: value` parser (`parseFlatLines`, `plugin/bin/lib/policy-schema.js:335`) — a nested map is not an option, but a comma-separated list value is an existing convention (`readListKey`, `plugin/bin/lib/policy.js:91`). The composer's only subprocess seam is a `gh` runner (`realDeps`, `plugin/bin/lib/compose-subject.js:203-215`); it has no git runner, though `GIT_TIMEOUT_MS` (`plugin/bin/lib/shared-primitives.js:256`) already exists for one. The local release engine already parses `type(scope):` headers (`HEADER_RE`, `plugin/bin/lib/release-local/commits.js:15`), so nothing downstream of the merge commit changes.

`tests/merge-subject-composer-conformance.test.js:16` pins the four local sites (`LOCAL_SITES`) and `tests/merge-subject-composer-conformance.test.js:41` pins the composer call-line shape (`COMPOSER_CALL`, a regex that today accepts any flags between the record numbers and `--shell`); `tests/merge-subject-composer-conformance.test.js:26` caps `pr-first-merge.md` at 31,304 bytes.

**Decision (brainstorm 2026-10-17, user said "go").** The scope source is project policy, resolved inside the composer, never a per-record field: `commit-scope` (one constant token) and `commit-scope-paths` (a comma-separated list of `{path-prefix}={token}` pairs, matched against the merge's changed files). An explicit `--scope` on the command line wins over both — the auto-mode contract's CLI-arg-over-policy precedence. A per-record field was rejected: it adds `/claude-tweaks:specify`-time ceremony on every record for a value that is a property of the repo's layout, not of the work, and an agent setting it would have to guess from paths anyway. Resolving inside the composer rather than in each fence's shell is what makes the five fences compose identical subjects with no per-fence conditional — the fences differ only in the `--range` they pass.

The parking comment's scope check against the work repo was not run — this machine has no GitHub Enterprise host authenticated and no clone of that repo. The design covers all three of that comment's non-close outcomes (one constant scope, a scope that varies by folder, or both), so that data decides only which keys a given project sets, not whether this ships. A project with no scope convention sets neither key and is unaffected.

## Deliverables

1. **Pure resolver** `plugin/bin/lib/commit-scope.js`: `parseScopePaths(entries)` turns the `commit-scope-paths` list — `readListKey`'s already-split, trimmed entries; the key is schema-typed `list`, like `merge-sensitive-paths` — into ordered `{prefix, token}` pairs (split each entry on the first `=`, trim both sides, throw a usage error naming the entry when it has no `=` or an empty side); `resolveCommitScope({ explicit, constant, pairs, changedPaths })` returns `{ scope, source, note }` where `source` is one of `explicit`, `paths`, `constant`, `none`. Rules: `explicit` non-empty → it. Else when `pairs` is non-empty: for each changed path take the longest prefix that is a string-prefix of it (a path matching no prefix contributes nothing); collect the distinct tokens; exactly one → `{ scope, source: 'paths' }`; zero or more than one → fall through, and for more than one set `note` to the sorted token list. Then `constant` non-empty → `{ scope, source: 'constant' }`; else `{ scope: null, source: 'none' }`. The resolver never validates token characters — `composeSubject` already does, so a policy-sourced bad token fails with the existing message.

## Release Note

Merge commits can carry a Conventional-Commits scope on every merge path, resolved from one documented project setting instead of being invented at the merge fence.

## Technical Approach

Resolution lives in one place, the composer, because the composer is already the one command every fence runs — a shell conditional on six fence lines would put the precedence rule in six places. The pure resolver is a separate module so its precedence rules are unit-testable with plain arrays, while `plugin/bin/lib/compose-subject.js` owns only the policy read, the `git diff --name-only` call through the new injectable `gitRunner`, and the exit-code mapping (the gh-api-module-pattern runner seam and CLI wrapper contract).

Two keys rather than one polymorphic value: `parseFlatLines` keeps every policy value a single string, so a constant and a path map in one key would need an in-band grammar to tell them apart. Two keys give a clean ladder — explicit flag, then path-derived, then constant, then unscoped — and let a monorepo set both (the constant catches a merge whose paths match nothing or span packages). An ambiguous or unmatched path set never errors: Conventional Commits permits an unscoped subject, and a mixed-package merge genuinely has no single scope; the stderr note keeps the fallback visible.

`--range` is passed by every fence rather than inferred by the composer: under local-merge the composer runs from the main checkout, under pr-first from wherever the pipeline stands, so a guessed `main...HEAD` would be wrong in at least one of them. Each fence already holds both ref names as resolved placeholders. A fence that omits `--range` still composes an unscoped subject unless `commit-scope-paths` is set, in which case the composer refuses loudly — a silently unscoped subject on a project that configured scopes is the parse-signal failure the loud exit prevents.

Expand-contract: both flags and both keys are additive; no existing invocation changes meaning, and this repo sets neither key.

## Open Question

Where should a merge site read `{scope}` from? Options: (a) a single project-wide `commit-scope` policy key, (b) a per-record field set at `/claude-tweaks:specify` time, (c) a rule derived from the diff's top-level path, or a precedence over several of these.
