# 3115: build/plan-authoring-checks: enumerate every test caller when a task adds a dependency to an existing function

Surface: infra

## Current State

`/claude-tweaks:build` runs every check in `plugin/skills/build/plan-authoring-checks.md` before finalizing a plan (`plugin/skills/build/SKILL.md:130`: "one bold paragraph per check; the file, not this sentence, is the list"). The file holds 24 bold-paragraph checks (24,601 bytes, well under the 45 KB per-file ceiling in `plugin/bin/lib/skill-audit/context-cost.js:31`).

The closest existing rule is the **Consumer-enumeration check** (`plan-authoring-checks.md:51`, from #2594). It fires only "when a plan task changes which rows of a shared table or frame a reader returns". It then enumerates every consumer of that reader and classifies each as pick-one or list-all. No check covers a task that gives an **existing function a new external dependency or side effect**: a store or network read, a new pipeline stage, a new environment requirement. In that case every test that calls the function, in any test module, needs the same stub or fixture.

The observed failure (original request below): a plan task added a configuration-store read to an export job's existing `run()`. The plan stubbed the read only in `run()`'s own test module. Two CI-allowlisted cases in another test module also call `run()`; with the change they reached the real store and failed. Every per-task review passed, because each compares its own diff against its own brief. Only the whole-branch review's focused test run caught it, at the cost of one Critical finding, one fix-wave item and a ~30-minute local re-run.

## Deliverables

1. Add one new bold-paragraph check to `plugin/skills/build/plan-authoring-checks.md`, placed directly after the Consumer-enumeration check: **Dependency-caller enumeration check (extends the Consumer-enumeration check)**. It must state:
   - **Trigger:** a plan task adds an external dependency or side effect to an existing function (a store, network or filesystem read, a new stage or subprocess, a new required environment variable or config key).
   - **Action:** grep every test directory in the repo, not only the function's own test module, for callers of that function. List each caller module in the task's Files block (`Modify:`/`Test:`) together with the stub or fixture that caller needs.
   - **Why:** a per-task review compares the task's diff against its own brief, so an unlisted caller module in another test file passes every task review and fails only at the whole-branch review or in CI. Use the incident above as the archetype, in the file's existing one-sentence-archetype style, with no project names.
   - **Check B hook:** `Scope keywords:` can name the function, so `plan-audit.js` Check B's fs-walk surfaces caller test files the plan's task list omitted. This mirrors the Consumer-enumeration check's closing sentence.

## Acceptance Criteria

- `plan-authoring-checks.md` contains a bold paragraph headed `Dependency-caller enumeration check` immediately after the Consumer-enumeration check paragraph.
- The paragraph names the trigger (a new external dependency or side effect on an existing function, with the store, network or filesystem read, new stage, and new environment requirement examples).
- The paragraph requires grepping every test directory for callers and listing each caller module, with its stub or fixture, in the task's Files block.
- The paragraph names `Scope keywords:` as the Check B hook for surfacing omitted caller files.

## Release Note

Add a plan-authoring check so a build plan that gives an existing function a new dependency also lists every test that calls it, before any task runs.

## Technical Approach

A prose-only, one-paragraph addition to a single file. It extends the existing Consumer-enumeration check by analogy rather than widening that check's trigger. That keeps the two failure classes distinct: changed return rows need consumer classification, while a new dependency needs a stub in every caller. Following the file's convention, each check is one self-contained bold paragraph with a trigger, an action, a why, and an archetype. `SKILL.md:130` treats the file as the list, so no other file restates the checks.

### Key Files

- `plugin/skills/build/plan-authoring-checks.md` — new Dependency-caller enumeration check paragraph after the Consumer-enumeration check

## Gotchas

- Indirect callers matter. A test that calls a wrapper around the changed function hits the same dependency. A one-level grep for the function's own name misses them. The paragraph should tell the author to follow wrappers one level up, or to name the affected test command, so the gap surfaces at authoring time.
- Keep the archetype project-neutral, matching the file's existing archetypes: describe "an export job's entry point" and "a configuration-store read", not the reporting project's own module names.

## Original request

build/plan-authoring-checks: enumerate every test caller when a task adds a dependency to an existing function

**Summary:** The plan-authoring checks have no rule for a task that gives an existing function a new external dependency. A test module the plan never listed breaks, and only the whole-branch review catches it.

**Kind:** Gap

**Affected component:** `skills/build/plan-authoring-checks.md` (Consumer-enumeration check)

**Use case:** A plan task gave an existing entry-point function (an export job's `run()`) a new external dependency: a configuration-store read on every call. The plan stubbed that read in the function's own test module only. Two cases in another test module also call `run()`; both are in the project's CI allowlist. With the change they reached the real store and failed, so the CI Python job would have gone red.

Every per-task review passed, because each compares its own diff against its own brief. Only the whole-branch review's focused test run caught it, at the cost of one Critical finding, one fix-wave item and one ~30-minute local Spark re-run.

The Consumer-enumeration check (#2594) covers a reader whose returned rows change. It does not cover a function that gains a new external dependency or side effect, where every test calling the function, in any module, needs the same stub. Proposed: when a plan task adds an external dependency or side effect to an existing function (a store or network read, a new stage, a new environment requirement), the plan greps `tests/` for every caller across all modules. It then lists each caller module in the task's Files block, together with the stub or fixture that caller needs.

**Definition:** Clear
