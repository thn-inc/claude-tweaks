# 2592: Multi-spec review verdict PR comment: later spec silently overwrites earlier spec's verdict

Surface: backend

## Current State

`plugin/skills/_shared/pr-run-comments.md`'s `verdict` comment kind uses one marker
(`<!-- run-comment: verdict -->`) per PR, found-and-updated-in-place per its "Post-or-update
procedure" — designed for a single-spec run where a re-triggered review edits the same comment.

A multi-spec `/claude-tweaks:flow` run shares one PR across every spec (`flow/multi-spec.md`).
Each spec's own `/claude-tweaks:review` Step 7 posts this same `verdict`-marked comment
independently. Observed directly on run `2026-09-18T054643-spec-2580-2581` (PR #2586, records
#2580 and #2581): #2580's review posted a verdict comment; #2581's review, following the exact
same documented procedure, found the existing marker and updated it in place — silently
replacing #2580's verdict content with #2581's. Nothing in `pr-run-comments.md` names this
multi-spec case or says what should happen instead.

## Deliverables

- [ ] Decide the intended multi-spec shape for the `verdict` comment kind: one comment per spec
      (would need a spec-qualified marker, e.g. `<!-- run-comment: verdict:{spec} -->`, and a
      change to the "one comment per kind per run" framing), or one running combined comment
      that each spec's review appends its own section to rather than replacing the whole body.
- [ ] Update `pr-run-comments.md`'s Comment kinds / Post-or-update procedure to document the
      chosen shape explicitly for multi-spec runs, the same way `flow/multispec-pr-checklist.md`
      already documents the phase-checklist's own multi-spec (cumulative, never-reset) shape.
- [ ] Update `review/code-mode-steps.md` Step 7's verdict-comment composition instructions to
      match.

## Acceptance Criteria

1. A second spec's review verdict in a multi-spec run no longer silently discards the first
   spec's verdict content from the PR's `verdict` comment.
2. `pr-run-comments.md` states the multi-spec behavior explicitly, mirroring how it already
   states the single-spec re-run-edits-in-place behavior.

## Release Note

Fixed the multi-spec Review verdict PR comment silently overwriting an earlier spec's verdict in the same run.

## Technical Approach

Recommend the spec-qualified-marker shape (`<!-- run-comment: verdict:{spec} -->`, one comment
per spec) over the appended-sections alternative: `pr-run-comments.md`'s existing Post-or-update
procedure already finds-and-updates by exact marker text, so a spec-qualified marker reuses that
same find-or-create logic unchanged per spec, whereas the appended-sections shape needs new
logic to locate and replace only this spec's own section within a shared comment body without
disturbing siblings' sections — more moving parts for the same outcome. This is a
recommendation for the build to weigh, not a foreclosed decision — the Deliverables above still
name both candidates.

Whichever shape is chosen, `review/code-mode-steps.md` Step 7's comment-composition call
(`<!-- run-comment: verdict -->` as currently hardcoded) needs the spec identifier threaded
into the marker it composes, and `pr-run-comments.md`'s Comment kinds table (currently listing
`verdict` as a single per-PR marker) needs its multi-spec behavior stated explicitly, the same
way `flow/multispec-pr-checklist.md` already documents the phase-checklist's cumulative shape
for the same multi-spec-shared-PR situation.

### Key Files

- `plugin/skills/_shared/pr-run-comments.md` — Comment kinds table (`verdict` row) and the
  Post-or-update procedure
- `plugin/skills/review/code-mode-steps.md` — Step 7's verdict-comment composition (the
  `<!-- run-comment: verdict -->` literal)

## Gotchas

- The chosen shape must not break `/claude-tweaks:wrap-up`'s or any other consumer's expectation
  that the `verdict` marker is a single, PR-wide comment kind — grep for `run-comment: verdict`
  across `plugin/skills/**/*.md` before finalizing the shape, to catch any other reader of this
  marker beyond the two files named above.
- This is a real, live-observed bug (not a hypothetical) — a regression test reproducing the
  two-spec-same-PR sequence (post spec A's verdict, then post spec B's verdict, assert both
  survive in some form) is worth adding alongside the fix, not just a unit test on the
  marker-matching logic in isolation.
