# 2986: _shared/git-discipline.md phase-exit push: does not notice a conflicting PR

Surface: infra

## Current State

Under `integration-model: pr-first`, every phase that commits ends with a phase-exit push (`plugin/skills/_shared/git-discipline.md`, "Phase-exit push" section, line 36). That section pushes and handles push failure (warn and continue), but never reads the PR's merge state.

When the integration branch moves during a long build and the run's draft PR starts to conflict, GitHub runs no `pull_request` workflows for the conflicting PR. The PR shows no CI jobs at all, which reads exactly like "CI pending". In the reported run (plugin 6.134.1), the conflict (`mergeStateStatus: DIRTY`) was found only because the orchestrator happened to query the PR. Pipeline Step 2.5's divergence check runs once at start, and multi-spec re-checks only at the finish step, so a conflict that appears mid-run goes unnoticed until the merge decision.

The repo already reads PR merge state elsewhere: `plugin/bin/lib/reconcile/pr-state.js`'s `resolvePrStateByNumber` returns `mergeable`/`mergeStateStatus` (#2367), and `_shared/github-pr-scan.md` flags `DIRTY` pending-review PRs. The catch-up procedure exists too ("Catching a branch up with `main`", same file).

## Deliverables

1. After each successful phase-exit push, when `run-state.json` carries a `pr` object, read the PR's merge state via `resolvePrStateByNumber`, best-effort and fail-open.
2. When it reports `DIRTY`, state it in the phase output and log an `AUTO` decision-log entry naming the PR and phase.
3. In `auto` mode, run "Catching a branch up with `main`" (fetch, merge in the worktree, resolve per the merge-conflict procedure, re-push) before the next phase starts. In `interactive`/`hybrid`, surface the conflict and the catch-up command; do not add a new mid-flow stop.
4. A merge-state read failure, or a state of `UNKNOWN`, logs nothing alarming and changes nothing.

## Acceptance Criteria

1. A phase exit on a run whose PR reports `mergeStateStatus: DIRTY` prints a conflict line and writes one `AUTO` entry to `decisions.md`.
2. In `auto` mode the next phase starts on a branch that has been caught up with the integration branch, and the re-push triggers the PR's `pull_request` workflows.
3. A run with no `pr` in `run-state.json`, a `local-merge` run, and a `current-branch` run behave exactly as today.
4. A failed or `UNKNOWN` merge-state read never stops or slows a phase beyond the one read.

## Release Note

Pipeline runs now notice when their draft PR starts conflicting with the base branch, instead of finding out at merge time.

## Technical Approach

Add a short "Post-push merge-state check" paragraph to the Phase-exit push section that calls a small CLI (or an existing `hooks.js` subcommand) wrapping `resolvePrStateByNumber`, so the check is mechanical rather than an agent-composed `gh` call. Reuse the existing catch-up procedure for the auto-mode remedy; do not add a second merge procedure.

### Key Files

- `plugin/skills/_shared/git-discipline.md` — Phase-exit push section gains the merge-state check and its auto-mode remedy
- `plugin/skills/_shared/pr-early-run-lifecycle.md` — cross-reference from the PR lifecycle
- `plugin/bin/lib/reconcile/pr-state.js` — `resolvePrStateByNumber`, reused
- `plugin/bin/hooks.js` — if the check is exposed as a subcommand
- `docs/hooks.md` — document any new subcommand

## Gotchas

- GitHub computes mergeability asynchronously; immediately after a push `mergeable` is often `UNKNOWN`. Treat `UNKNOWN` as no signal (optionally one short delayed re-read), never as a conflict.
- Auto catch-up merges into the run's branch mid-pipeline; it must use the worktree-scoped push form (`git -C {worktree} push origin {branch}`) and must not run when the worktree has uncommitted changes.
- The phase-exit push's failure posture is "degrade per attempt, never persist" — the new check must follow it.

## Original request

_shared/git-discipline.md phase-exit push: does not notice a conflicting PR

**Component:** `_shared/git-discipline.md` "Phase-exit push" / `_shared/pr-early-run-lifecycle.md` (pr-first integration model), plugin version 6.134.1.

**Kind:** Gap (the skill has no opinion where it should).

**What happened.** In a single-record `/flow` run under `integration-model: pr-first`, the build phase's exit push landed on a draft PR whose base branch had moved during the build and now conflicted in two files. The forge runs no `pull_request` workflow for a PR in a conflicting state, so the PR showed no CI jobs at all. Nothing in the phase-exit procedure reads the PR's merge state, so the run carried on to the test step with CI silently absent; the conflict was found only because the orchestrator happened to query the PR's checks and then its `mergeStateStatus`.

**Why it matters.** The pipeline's Step 2.5 divergence check is a point-in-time check at pipeline start, and the multi-spec flow re-checks only at the final finish step. A long build (hours) has a real window for the base to move. A conflicting PR costs a merge plus a full re-verification, and that is cheapest to learn at the first phase exit, not at the merge decision. A missing CI run also reads exactly like "CI pending".

**Suggested behaviour.** After each phase-exit push, when `run-state.json` carries a `pr` object: read the PR's merge state (`gh pr view {n} --json mergeable,mergeStateStatus`, best-effort, fail-open). When it reports a conflict, say so in the phase output and log an `AUTO` decision; in `auto` mode, run the existing catch-up (fetch the integration branch, merge in the worktree, resolve per the merge-conflict procedure) before the next phase instead of after the last one. A forge that reports a stale conflicting state can be told apart by attempting the merge locally.

**Evidence shape (scrubbed).** Push at commit A: PR checks list only push-triggered workflows. `mergeStateStatus: DIRTY`. After merging the base and pushing commit B: all `pull_request` jobs run.
