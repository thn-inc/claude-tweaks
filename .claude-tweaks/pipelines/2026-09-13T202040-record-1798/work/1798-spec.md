# 1798: worktree-isolation guard: refuses non-git Bash commands as too complex and denies the owning session its own record-pr stamp

Surface: backend

## Overview

This spec scopes narrowly to symptom #1 of the original report: `checkBookkeepingStampsGate`'s `record-pr` branch (`plugin/bin/lib/hooks/pre-tool-use.js`) denied a genuinely owning session's own git-mutation call three times before eventually landing, on a Windows/Git Bash `worktree-always` dispatch firing.

**Symptom #2 (the Bash guard refusing non-git commands as "too complex to verify") is out of scope here — it is a duplicate of #1785.** That record already correctly investigated and attributed this to the Claude Code harness's own worktree-session guard, not this plugin's code (`plugin/bin`/`plugin/hooks` carry none of the quoted refusal strings), and is already shaped and `ready` with its own deliverables (documentation + upstream report). Do not re-scope that symptom here.

A concrete, testable hypothesis for symptom #1: `hooks.js record-worktree` stamps `worktree` and `sessionId` together in one `writeRunState` call, but deliberately *omits* `sessionId` when `process.env.CLAUDE_CODE_SESSION_ID` is falsy at that moment ("an env-less re-record must not clobber a previous stamp" — `plugin/bin/hooks.js` ~line 596-598). If that env var doesn't reliably propagate into a dispatched Task's Bash subprocess on Windows/Git Bash, `runState.sessionId` never gets set, and `isForeignSessionCall` (`ctx.runState.sessionId` vs `ctx.input.session_id`) can never resolve `true` for the rest of that run — meaning it can never rescue a genuinely-owning call either, since it only distinguishes "provably foreign" from "not provably foreign," and the `record-pr` branch's exemption is `isForeignSessionCall` alone (unlike the `record-worktree` branch, which also falls back to `hasDistinctOwnedRun` — `plugin/bin/lib/hooks/pre-tool-use.js` ~line 1128, deliberately not folded into the `record-pr` branch per that function's own header comment). This is a hypothesis, not a confirmed root cause — Task 0 below verifies it empirically before the rest of this spec's shape is decided.

## Original request

## Summary

The worktree-isolated session guard refuses non-git Bash commands as "too complex to verify that it stays inside the worktree", and denies the run's own `record-pr` bookkeeping stamp against its own worktree, forcing workarounds a headless dispatch firing has to script around.

## What happened

Observed on one `/claude-tweaks:dispatch` two-call firing (run `2026-09-02T170511-record-291`, `/flow #291 review,polish,wrap-up`), Windows / Git Bash, `worktree-always: true`:

1. `bookkeeping-stamp-deny` fired three times in a row (17:12:08, 17:12:17, 17:12:42) on the first call's `hooks.js record-pr` stamp — the run's own worktree, the run's own PR. The stamp eventually landed (`run-state.json` carries the `pr` object), so the denial was a false positive on the owning session. The dispatch task prompt already pre-scripts a "re-stamp the worktree assignment once and retry" workaround for exactly this, which is a sign the gate misfires often enough to need one.
2. In the second call, the Bash guard refused commands containing no git operation at all:
   - `cat > "<scratchpad>/patch.js" <<'EOF' … EOF` (a heredoc writing a file outside the repo) — refused as "too complex to verify".
   - `cd hub && pnpm --filter @dispatch/worker exec tsc --noEmit 2>&1 | tail -3; echo "tsc-exit=${PIPESTATUS[0]}"` — refused because "pnpm with the text exec inside a construct too complex to verify … cannot be shown not to be git".
   - `node bin/residue.js --base "$(git merge-base origin/master HEAD)" …` — refused for a read-only `git merge-base` inside a command substitution.
   Each was re-issued as a plain, split command and then ran fine, so the guard's policy condition (a git mutation targeting another checkout) never actually matched.

## Expected

A read-only git call (`merge-base`, `rev-parse`, `log`, `diff`), a heredoc to a non-repo path, or a pipe/`PIPESTATUS` around a non-git command should not trip the worktree guard; and the owning session's own `record-pr` stamp should never be denied for its own worktree.

## Suggested fix

- Classify by the presence of a git *mutation* verb (`commit`, `push`, `merge`, `rebase`, `checkout`, `worktree add/remove`, `reset`, `branch -d`) rather than by command complexity; treat `$(git <read-only>)` substitutions as allowed.
- Skip the heredoc/pipe complexity refusal when the command contains no `git` token at all.
- Log the `bookkeeping-stamp-deny` reason (which check failed) so an owner-session false positive is diagnosable from `events.jsonl`.

## Evidence

- `events.jsonl` for the run above: three `bookkeeping-stamp-deny` entries with `stamp: "record-pr"` and the run's own worktree path.
- Session transcript: three "Refusing to run it — a worktree-isolated session's git operations must target its own worktree" refusals on the commands quoted above, each followed by an accepted plain re-issue.
