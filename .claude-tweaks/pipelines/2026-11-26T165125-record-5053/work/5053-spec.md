## Release Note

Answer a plan-review question by replying `/answer …` on its comment, and the next dispatch folds the answer into the issue and resumes the build on its existing PR.

## Technical Approach

The reply parser and section writer are one pure module so that #5172's terminal path can write the same section without a second implementation. The CLI is a thin `gh` shell over it. The waiting label replaces the headless `bot:blocked` block for this stop only. The restart is a separate bare-drain step that reuses `resume.md` unchanged from Step 3 on, so the queue pull and its fenced twin in `queue-pull-script.md` are not touched.

**Decision** (D1 — what counts as a reply): GitHub issue comments are flat, so a "reply" is a trusted-author comment created after the newest trusted question comment whose first non-blank line starts with `/answer`. Quote-replies and arbitrary later comments do not count. Why: the form is fixed and greppable, a human can type it from a phone, and it keeps discussion comments out of the spec.

**Decision** (D2 — waiting label): a new `needs:answer` label, not `needs:decision`. Why: `needs:decision` resolves by applying a `**Proposed:**` action at `/claude-tweaks:backlog refine` (`refine-record.md`), and a plan-review question has no action to apply. Specify's planning hold also lives on `needs:decision` and is answered by `/claude-tweaks:specify`, so a shared label would route one record to two answer paths.

**Decision** (D3 — headless posture): the plan-review stop keeps `auto:build`/`auto:merge` and adds no `bot:blocked`. Why: the grants were human-given and the stop is not an authorization failure. The answer itself comes from a trusted human, and the resumed build re-runs plan review and every later gate. Keeping `bot:blocked` would make every headless stop need a re-grant, which defeats the restart.

**Decision** (D4 — where the restart lives): a bare-drain Step 2.5 over `needs:answer` records, not a change to the queue pull's `open-pr` exclusion. Why: the exclusion is shared by the module and its fenced script twin, it feeds the open-pr report, and it is what keeps an unanswered record out. A label-keyed sweep touches neither, and it reuses `resume.md`'s eligibility verdict verbatim.

**Decision** (D5 — budget and order): answered resumes run before the ranked queue, oldest question first, each eligible one consuming one budget unit. Why: they are already-started builds with a PR, a plan and an answer, so they are the cheapest to finish. A refused resume spends nothing, the same rule as a refused `drive.js --budget` record.

**Decision** (D6 — section format): one section per question comment, placed before `## Original request`:

```
## Plan-review answers ({question createdAt, YYYY-MM-DD})

Question: {question comment url}

**Decision** (answer by @{login}, {reply url}):

{fence}text
{reply text with the leading /answer token removed}
{fence}
```

`{fence}` is a backtick run one longer than the longest backtick run in the reply, and at least three long. A later reply to the same question appends another `**Decision**` block to that section. Why: the `**Decision**` paragraph is what #4958's converged round reads as a recorded decision. The fence keeps the human's text quoted rather than authored, so the placeholder gate and the `## Original request` boundary (`#1839`, `#4351`) treat it as content, with no checker change. The URL makes ingest idempotent.

**Decision** (D7 — typed resume clears the label): `dispatch resume #N` removes `needs:answer` before dispatching, with or without a reply. Why: a human typing resume has answered on the body or chosen to re-run anyway. If plan review stops again, it re-adds the label.

**Decision** (D8 — authority for a sweep-originated resume): `dispatch-resume.js --queue` requires the real `auto:build` label. Why: the sweep is a queue pick, not a typed command, and `drive.js --budget` applies the same rule to records its loop picks (`docs/driver.md`, Build authority).

**Decision** (D9 — the plugin never authors an answer): no skill or CLI posts an `/answer` comment. Why: `comment-trust.js`'s trust limit (#3358) cannot tell the maintainer from an agent under the maintainer's account, the same reason `accept-verdict.js` refuses to author a verdict marker. #5172's terminal path writes the section into the body directly through `appendAnswers`.

**Decision** (D11 — plan review, 2026-11-26, question https://github.com/thn-inc/claude-tweaks/issues/5053#issuecomment-7198113959): Reading B. The answer is ingested only after an eligible resume verdict, in both the Step 2.5 sweep (`--check`, then `dispatch-resume.js --queue`, then the ingest) and a typed `dispatch resume`. A refused resume leaves the body and `needs:answer` untouched, so the next bare drain retries it. Why: Reading A would strand an answered record with no label and only a generic `stuck:open-pr` row, the exact gap this record closes. Deliverables 5 and 7 above are worded to match.

**Decision** (D12 — headless sweep resume, plan review 2026-11-26): `bin/dispatch-prompt.js` and `bin/lib/dispatch/task-prompt.js` currently refuse `--resume-verdict` combined with `--headless`. D7's sweep-originated resume in a headless firing needs that combination, so both accept it for a sweep-originated resume. A typed resume still never passes `--headless`.

**Decision** (D10 — records stopped before this ships): no migration. Records already `bot:blocked` by the old headless rule keep the refine-and-resume path. A typed-drain stop without the label can be opted in by adding `needs:answer` by hand, which the sweep then picks up. Why: older builds still run in live sessions (expand-contract), and a back-fill would need to guess which `bot:blocked` records came from plan review.

## Gotchas

- `appendAnswers` must use the repo's fence helpers (`bin/lib/markdown-blocks.js`), not a hand-rolled fence. An unclosed or too-short fence would let reply text end the authored scan early (#4351) or swallow `## Original request`.
- GitHub caps an issue body at 65,536 characters. When the appended body would exceed it, the CLI exits 4 without writing and keeps `needs:answer`, and the human answers on the body and runs `dispatch resume #N`.
- Two sessions can ingest the same reply at once. Idempotency by reply URL plus the read-back keeps the result single, but the read-back must count URL occurrences rather than only test for presence.
- Ingesting edits the body, so `lastEditedAt` moves past the question comment and the next plan review reads the round as converged. That is correct here because a human answered. #5337's open question about automation edits is unaffected.
- `bin/stuck-open-prs.js` builds the `stuck:open-pr` set. Excluding `needs:answer` records from the rendered stuck rows may need a change there, or in attention-mode's merge script, whichever owns the row dedupe.
- The `dispatch-queue-exclusion-addition` skill does not apply: no queue exclusion is added (D4).
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(auth): …`, `Proof(public-contract): …`.

## Acceptance Criteria

A trusted reply to the question comment, then a bare dispatch, ends with the record body carrying the answers section and the build resuming on its existing draft PR with no human command; an untrusted reply or a non-reply comment changes nothing.

A human-typed drain's plan-review stop leaves the record labelled `needs:answer`; `/backlog attention` lists it with the question text; the label is removed when the answer is ingested.

`dispatch-resume.js` (or the eligibility module) reports answered vs unanswered; queue-pull tests cover answered (re-admitted), unanswered (excluded), and answered-but-ineligible (excluded with the resume refusal line).
