# 3025: hooks.js close-run: a bare run-id `--run <basename>` is rejected, and the rejection exits 0

Surface: infra

## Current State

`node bin/hooks.js close-run --run <basename>` cannot close a run dir when given only its basename, and it reports that failure with exit 0:

- `resolveRunArg` resolves an explicit `--run` value as `path.resolve(cwd, candidate)` (`plugin/bin/hooks.js:357`), so a bare run id becomes `<cwd>/<basename>`, which is not a directory, and the call returns `invalidRunArg`.
- The `close-run` handler prints `claude-tweaks: --run path rejected: … — run not closed` (`plugin/bin/hooks.js:921`) and still returns 0, so the run stays `active` and a scripted caller can't tell this apart from a successful close.
- Callers pass basenames to this verb on purpose. `plugin/skills/dispatch/SKILL.md:100` defines `$RUN_ID` as the run directory's basename, and `plugin/skills/dispatch/SKILL.md:173` runs `close-run --run "$RUN_ID"` (#2430's drain-termination cleanup). The SessionStart/residue notices (`plugin/bin/lib/hooks/session-start.js:127`, `plugin/bin/hooks.js:1251`) print `close-run --run <dir>` next to a list of basenames. So dispatch never closes a run dir it minted, and the exit 0 hides it.
- `tests/hooks-dispatcher.test.js` (around lines 400, 411, 428) currently asserts exit 0 for a rejected `close-run --run`.
- Every other verb's `--run path rejected` branch (`plugin/bin/hooks.js:630`, `:828`, `:885`, `:979`, `:1013`, `:1032`, `:1128`, `:1180`, `:1205`) also exits 0. That is the same class of problem but outside this record's scope (see Gotchas).

## Deliverables

1. In `resolveRunArg` (`plugin/bin/hooks.js`): when the cwd-relative reading of `--run` is not a directory **and** the value contains no path separator, resolve it under `<main-checkout>/.claude-tweaks/pipelines/<value>` (via `wtDetect.mainCheckoutRoot(cwd)`), and use it only when that is a directory. The existing anchoring, shape, and initialization checks then run unchanged against the resolved path. Every verb that shares `resolveRunArg` gets basename resolution.
2. `close-run` returns exit 1 when `--run` is rejected (`invalidRunArg`), including the missing-value case.
3. `tests/hooks-dispatcher.test.js` is updated to cover the new behavior: the existing rejected-`--run` assertions expect exit 1 for `close-run` (and still expect 0 for the other verbs), plus two new tests. One shows a bare basename closing its run. The other shows a bare basename that names no run dir being rejected with exit 1.

## Acceptance Criteria

- From a project root that has `.claude-tweaks/pipelines/2026-07-01T090000-spec-1/` initialized, `hooks.js close-run --run 2026-07-01T090000-spec-1` exits 0, prints no `--run path rejected` line, and leaves `run-state.json` at `status: clean`.
- `hooks.js close-run --run 2026-07-02T090000-spec-9`, where no such directory exists under pipelines/, exits 1 and prints `--run path rejected: 2026-07-02T090000-spec-9 — run not closed`.
- `hooks.js close-run --run <path-to-nonexistent-dir>` and `hooks.js close-run --run` with no value both exit 1, and neither one touches any other run's `run-state.json`.
- A value that contains a path separator never falls through to the pipelines/ lookup. Path-shaped values resolve exactly as before.
- A basename resolved under pipelines/ still goes through the existing `[IL-127]` anchoring check: a pipelines dir outside the main checkout is never adopted.
- Every `--run path rejected` branch other than `close-run` still exits 0, and the existing tests for those verbs still pass unchanged.
- `node --test tests/hooks-dispatcher.test.js` passes.

## Release Note

Fixed closing a pipeline run by its short run id, and made a failed close report a non-zero exit code.

## Technical Approach

The record proposes a minimal, local change. Add a fallback branch in `resolveRunArg` right after the `path.resolve(cwd, candidate)` line. It applies only to separator-free values that are not cwd-relative directories, and it uses only `isDirectory` (`plugin/bin/hooks.js:149`) and `wtDetect.mainCheckoutRoot` (`plugin/bin/hooks.js:22`, already used at `:363`), so no new dependency is introduced. Because the fallback runs before the existing `isRealDir`/anchoring logic, the rest of the function is unchanged. Separately, add `return 1;` to `close-run`'s `invalidRunArg` branch only. The record's own Proposed fix section below gives the exact diff, which was verified by the reporter on Windows (the same 4 pre-existing Windows-only failures before and after).

### Key Files

- `plugin/bin/hooks.js` — `resolveRunArg` basename fallback; `close-run` exit 1 on a rejected `--run`
- `tests/hooks-dispatcher.test.js` — update the exit-code assertions for rejected `close-run`; add tests for a bare basename that resolves and one that does not

## Gotchas

- The basename fallback sits in the shared `resolveRunArg`, so `record-pr`, `spec-status`, `teardown-run`, `archive-run`, and the other `--run` verbs also start accepting basenames. That is intended. Confirm that `hooks-help-guard`, `hooks-spec-status`, `hooks-worktree-local-fallback-disclosure`, and the teardown-gate suites still pass.
- Making every other verb's `--run path rejected` branch exit non-zero is deliberately **not** part of this record. That decision is wider and touches every verb's scripted callers, so the record leaves it as the reporter's open choice. Don't fold it in here.
- Run the cwd-relative reading first. A run dir that really sits under cwd must still win over the pipelines/ fallback, so the fallback triggers only when the cwd-relative path is not a directory.
- Exit 1 changes behavior for any caller that relied on exit 0 after a rejected close. dispatch's Step 3 cleanup line is the documented caller. Check that it doesn't run under `set -e` in a way that would now abort the firing, or note it in the PR.

## Original request

hooks.js close-run: a bare run-id `--run <basename>` is rejected, and the rejection exits 0

**Summary:** hooks.js close-run --run <basename> is rejected (cwd-relative resolution) and the rejection exits 0, so dispatch's drain-termination close-run never closes the run dir

**Kind:** Defect

**Affected component:** hooks.js close-run (bin/hooks.js resolveRunArg)

**Repro steps:**
1. In a project with a run dir `.claude-tweaks/pipelines/<timestamp>-record-<N>/`, from the main checkout (or any worktree), run `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" close-run --run <timestamp>-record-<N>` (just the basename, as `skills/dispatch/SKILL.md:173` does with `$RUN_ID`).
2. Check the exit code and the run dir's `run-state.json`.

**Expected vs. actual:**
Expected: the basename resolves to the run dir under the main checkout's `.claude-tweaks/pipelines/` and the run is closed; a `--run` value that cannot be resolved exits non-zero so a scripted caller can tell "not closed" from closed.
Actual: `claude-tweaks: --run path rejected: <timestamp>-record-<N> — run not closed`, exit 0. The run stays `active`. Passing the absolute path works.

**Root cause:** `bin/hooks.js:357` resolves an explicit `--run` as `path.resolve(cwd, candidate)`, so a bare run id becomes `<cwd>/<basename>`, which is not a directory; execution falls through to `hooks.js:523` (`return { runDir: null, invalidRunArg: ... }`), the `close-run` handler prints the rejection at `hooks.js:921` and returns 0 at `hooks.js:962`. But the docs pass basenames to this verb: `skills/dispatch/SKILL.md:100` defines `$RUN_ID` as "that run directory's basename", `SKILL.md:173` runs `close-run --run "$RUN_ID"`, and the SessionStart/residue notices (`bin/lib/hooks/session-start.js:127`, `hooks.js:1251`) print `close-run --run <dir>` next to a list of basenames. So #2430's drain-termination cleanup never closes a minted run dir, and the exit 0 hides it. (Exit-0-on-rejection is currently pinned by `tests/hooks-dispatcher.test.js:400,411,428`; every other verb's `--run path rejected` branch also exits 0 — same class, out of scope here.) Fix: when the cwd-relative reading is not a directory and the value has no path separator, resolve it under `<main-checkout>/.claude-tweaks/pipelines/`; every existing anchoring/shape/initialization check still runs against the resolved path. Also make `close-run` exit 1 on a rejected `--run`.
