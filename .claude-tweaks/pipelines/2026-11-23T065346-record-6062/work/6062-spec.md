# 6062: Key the dispatch queue-order cache on every grouping setting, not only the stamp

Surface: backend

**Related:** #6011

The dispatch queue pull reuses a persisted group order (the queue-order blob) whenever its grouping stamp matches and no queue record changed. The stamp names only which halves of `keepSingleton` are on (`per-record`, `+express`, `+driver`), not the settings each half reads. A pull after a policy change with an unchanged queue therefore replays the old grouping. The driver half (#6011, PR #6045) answers differently for one record under one stamp depending on `express-driver` (`split` vs `on`), `express-driver-max-size`, `express-driver-max-key-files` and `express-driver-review`; the express half already has the same gap for `integration-model`, `merge-sensitive-paths` and `dispatch-fastlane-bundle-cap`. This record gives the cache a key covering every grouping input, express and driver halves alike.

It must land before pipeline economy Phase 7 raises `express-driver-max-size` for its driver trial: that change is exactly the policy edit the cache would mask, so the first drain after it could bundle driver-routable records until any queue record changes.

**Non-goals:**
- Changing what any existing grouping stamp value means, or the four values #6011 added. Stamp values stay as they are.
- Changing which records either half keeps out of bundles.
- Raising `express-driver-max-size` or any other bound. That is Phase 7.

**Approach:** Add the fingerprint as a new blob field rather than folding settings into the stamp string: older plugin versions read the stamp with exact-match rules, and a new stamp value would also work for them, but a fingerprint keeps the four stamp values readable and puts the settings comparison in one field. `expressQueuePolicy` already holds every value the fingerprint needs after its two resolver calls; returning a `fingerprint` beside `grouping` adds no resolver call. A failed policy read keeps today's disabled behavior, with the fingerprint of the disabled shape.

**Gotchas:**
- The queue-order blob is shared state that live sessions on older plugin versions also read and write. Add the field; never change what `grouping` or an existing stamp value means.
- `dispatch-fastlane-bundle-cap` is read in `grouping.js`, not in `expressQueuePolicy`; the grouping-input list must include it anyway, since it changes the groups.

**Decision** (plan review on draft PR #6105, 2026-11-23): Reading B. The fingerprint also covers `work-links`. A cache hit replays the persisted blocker exclusions as well as the groups (`queue-pull.js:635-643`), and `work-links` decides which exclusions a pull computes, so it is a grouping input under this record's own rule. The one owner of the grouping-input list (Deliverable 4) owns `work-links` too, even though it is read outside `expressQueuePolicy`: both callers (`queue-pull.js` and `queue-pull-script.md`'s embedded script) feed the `work-links` value they already read into the fingerprint, with no extra resolver call. AC7's test covers that read as well.

## Deliverables

- [ ] The queue-order blob gains an additive settings-fingerprint field: a stable hash over every policy value that changes the groups a pull computes — `express-lane`, `express-driver`, `integration-model`, `merge-sensitive-paths`, `express-driver-max-size`, `express-driver-max-key-files`, `express-driver-review`, `dispatch-fastlane-bundle-cap` — computed from the values the pull actually used, written beside `grouping`.
- [ ] `cacheUsable` reuses a blob only when its stamp matches, its freshness signal matches, and its fingerprint equals the current one. A blob with no fingerprint (written by an older plugin version) is never reused by a reader that computes one: it recomputes.
- [ ] Both callers — `queue-pull.js` and `queue-pull-script.md`'s embedded script — pass the current fingerprint to `cacheUsable` and write it into the blob, so the parity test stays green.
- [ ] One place owns the list of grouping inputs (exported beside `expressQueuePolicy`), so a future grouping input cannot be added to the policy read without the fingerprint seeing it.

## Acceptance Criteria

1. With an unchanged queue, a pull whose `express-driver-max-size` differs from the persisted blob's (same stamp `per-record+express+driver`) does not reuse the blob: `cacheUsable` returns false and the groups are recomputed.
2. The same holds, one case each, for a change to `express-driver` (`split` ↔ `on`), `express-driver-max-key-files`, `express-driver-review`, `integration-model`, `merge-sensitive-paths` and `dispatch-fastlane-bundle-cap`.
3. With every grouping input unchanged and an unchanged queue, `cacheUsable` still returns true (the cache keeps working).
4. A persisted blob with no fingerprint field is not reused by the new reader; an older reader that ignores the field still reads a new blob under its existing stamp rules (expand-contract: no existing field changes meaning).
5. The fingerprint is order-independent and stable across runs for equal inputs (`merge-sensitive-paths` given in a different order hashes the same).
6. The queue-pull parity test between `queue-pull-script.md`'s embedded script and `bin/lib/dispatch/queue-pull.js` passes over its fixtures.
7. A test fails when a new key is added to `expressQueuePolicy`'s policy read without being added to the grouping-input list.
8. With an unchanged queue, a pull whose `work-links` differs from the persisted blob's does not reuse the blob: `cacheUsable` returns false, and both the groups and the blocker exclusions are recomputed.

## Release Note

The dispatch queue pull no longer reuses a cached group order after a change to a setting that decides how records are grouped.
