# 5227: Queue pull as a module and CLI, alongside the embedded scripts

Surface: backend

## Overview

This unit moves `/claude-tweaks:dispatch`'s queue selection out of two embedded scripts and into a module, with a thin CLI over it. Today a model reads `plugin/skills/dispatch/queue-pull-script.md` (52,104 bytes) and runs the bash it carries to produce the session-scoped `dispatch-groups.json` and `dispatch-exclusions.json`, then reads `plugin/skills/dispatch/next-ranking.md` (4,928 bytes) and runs its script to pick the next group. The module `plugin/bin/lib/dispatch/queue-pull.js` and the CLI `plugin/bin/queue-pull.js` produce the same files from the same inputs, so a program, not a model, can select the queue. Design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, section "Phase 5 — Queue selection in the driver".

This is the first step of a three-step strangler-fig: the module is built beside the scripts here, the cutover is a separate unit, and the scripts' removal is a third. The embedded scripts and `plugin/skills/dispatch/SKILL.md` stay byte-identical in this unit and the scripts stay the path `/claude-tweaks:dispatch` runs, so nothing changes for any consumer project. What this unit adds is the second implementation and the evidence that the two agree: a parity test that runs both over the same fixtures.

The ranking is in scope because the design's done criterion is "the same records, in the same order, as a dispatch drain": the pull produces the pool and `next-ranking.md` orders it, so selecting the same records in the same order needs both.

**Complexity:** High
**Estimated tasks:** 8

## Non-Goals

- Any consumer change: `plugin/skills/dispatch/SKILL.md`, `queue-pull-script.md`, `next-ranking.md`, `mcp-transport.md`, `queue-pull-notes.md` and the report sub-files are not edited. The cutover is the next unit's.
- Removing or shortening either script (the removal unit's).
- Changing which records the queue selects or in what order. The module reproduces the scripts, including any behavior that looks like a defect; a defect found while extracting is filed as its own record, because fixing it in the module would turn the parity test red on purpose.
- New exclusion reasons, new passes, or moving a pass.
- `drive.js --budget` (a later unit of this parent).

## Prerequisites

None. This unit has no blocker and can start at once.

- [ ] The same module reproduces the script's other outputs: `dispatch-fastlane-bundles.json`, `dispatch-near-dup-pairs.json`, `dispatch-crosspr-overlap.json`, the staged Close proposals and `AUTO` lines, the queue-order cache write-back and the shipped release times.

## Acceptance Criteria

1. Over a fixture set that exercises every exclusion reason the script's header bullets list at build time (today `blocked`, `oversized`, `neighbour-in-flight`, `not-spec-shaped`, `open-pr`, `target-missing`, `shipped`, `unlanded-blocker`, `malformed-blocker`), on both transports and on both the cache-hit and cache-miss paths, the module's `dispatch-groups.json` and `dispatch-exclusions.json` are identical to the embedded script's (the same entries, in the same order), and so is every other output the script writes: `dispatch-fastlane-bundles.json`, `dispatch-near-dup-pairs.json`, `dispatch-crosspr-overlap.json`, `dispatch-linked-prs.json`, the staged Close proposals, the `AUTO` and `Warning:` lines (text and channel), the `writeOrder` payload and the `writeReleaseTimes` file. "Identical" means JSON-equal after the normalizations the test header lists and nothing else: a frozen clock for the oracle (a preloaded stub of `Date`) and a substitution of the scratch directory and run id in paths.
2. Each exclusion reason has a fixture in `queue-pull.test.js` that goes red when that pass is removed from the module: for every registry entry that writes a reason, running the module with that pass omitted (the `omit` option of `queuePull`, which is part of its contract) yields output that differs from the expected entries for that reason's fixture, and each informational pass's output file likewise differs when its pass is omitted. The reasons that remove candidates leave the record out of `dispatch-groups.json`, and `oversized` and `neighbour-in-flight` leave it in; the parity fixtures show both.
3. A fixture whose candidate qualifies for several passes yields the same single reason the script yields: `not-spec-shaped` before `open-pr`, `target-missing` and `shipped` (no `gh` probe is made for a candidate it excluded), and a candidate excluded by `open-pr` or `target-missing` is never classified `shipped`.
4. A fetch failure takes the same fail-open or fail-closed path as the script does for that pass, shown per pass with one fixture each that forces that pass's fetch to fail in both the oracle and the module and compares what each does: a pass the script fails open on (the registry marks each) prints one `Warning:` or `AUTO` line, on the channel the script uses, and excludes nothing. The registry's `failOpen` values are asserted from those oracle runs, not from this record. The script stops the pull on two things per `.claude/skills/dispatch-queue-exclusion-addition`, decision 4: `appendExclusion` refusing a corrupt `dispatch-exclusions.json` and an unreadable `dispatch-groups.json`. The oracle fault-injection runs confirm that list; if the script also stops on something else (a failed subprocess under a shell option, an unset variable), the registry records it and the module reproduces it, and a failed cache write-back never fails the pull. A corrupt `dispatch-exclusions.json` makes the CLI exit with the stop code (4), no later pass run and the file left as it was.
5. Empty and malformed inputs: an empty queue yields the same files as the script yields for an empty queue; a candidate whose `labels` is not an array, whose `body` is not a string, or whose `Blocked by` line names no valid issue number is handled as the script handles it (`not-spec-shaped` or `malformed-blocker`), and one such candidate never changes another candidate's verdict.
6. Ranking: for fixtures covering every priority band, a tie within a band (oldest first), a group whose best member is not its first member, a group excluded by each of `oversized`, `firing` and `neighbour-in-flight`, a `--priority` filter that matches nothing, and an empty pool, `rankNext` returns the same group (or `null`) as `next-ranking.md`'s script. Two groups whose best members have equal `createdAt` rank in the order the script's sort yields, and a pool whose timestamps arrive as snake_case `created_at` (aliased with `aliasMcpTimestamps`) ranks the same as the same pool with camelCase timestamps. An absent or unreadable `dispatch-exclusions.json` reads as no exclusions, as the script does.
7. On the `files` transport with `gh` absent from `PATH`, the module and the CLI produce the files `mcp-transport.md`'s procedure produces, including `dispatch-crosspr-overlap.json` as `[]`. For each `files` input listed under Technical Approach, a fixture with the file missing and one with it malformed (unparseable, or the wrong shape) has the module and the oracle agree on the outcome: the in-flight pool and claim map and the foreign states fail open as `mcp-transport.md` states, and the queue and dependency-freshness inputs stop the pull as the script does. With `--transport gh` and `gh` absent, the CLI exits with the contract's missing-dependency code and a message naming the `files` transport; it never falls back to it silently.
8. No file under `plugin/skills/` appears in this record's own diff against its merge-base with the integration branch (a diff of the merged state would also list other records' edits to the scripts). In particular `queue-pull-script.md`, `next-ranking.md`, `SKILL.md`, `mcp-transport.md` and `queue-pull-notes.md` are untouched.
9. `queue-pull.js --help` exits 0 before any probe of `gh`, git or policy; a malformed invocation (an unknown flag, a value-taking flag as the last argument, an empty value) exits with the contract's malformed-invocation code and prints the usage text; the header comment and the usage text state every exit code.
10. `docs/plugin-structure.md` lists `queue-pull.js` in the command reference and names the new module in the `plugin/bin/lib/dispatch/` entry.
11. The registry drives the run: `queuePull` iterates `PASSES` in array order (position in the array is position in the run), and a test asserts that the set of reasons in `PASSES` equals the set of reasons in the script's header bullets plus nothing, so a pass added to the script without the module turns the suite red. Every registry field has a fixed value set: `removes` and `bypass` and `runsOnCacheHit` are booleans, `failOpen` is `open`, `stop` or `n/a`, and `mcp` is `same`, `skipped-empty`, `fails-open` or `agent-fetched`.

## Technical Approach

- **Derive before extracting.** Per `.claude/skills/shared-contract-extraction`'s first step, derive the list from the scripts, not from this record: the nine reasons above, every `$DISPATCH_*` file a pass writes or reads, and every site `.claude/skills/dispatch-queue-exclusion-addition` names. Re-derive it after every upstream merge: open records edit the script (for example #5087, #5072 and #5071), so the pass list this record names can be stale by build time.
- **Each pass is a function over `deps`.** The pass bodies call the modules and CLIs the script calls today. A CLI the script runs as a subprocess (`resolve-blockers.js`, `resolve-linked-prs.js`, `dispatch-unlanded-blockers.js`) is called through the injected runner the way the script calls it, or through its library function when it has one, whichever keeps the fake-runner fixtures honest; the module does not reimplement their logic.
- **Same writer, same files.** Exclusion entries go through `appendExclusion`, the one sanctioned writer. The two main files are written at the paths `session-tmp-resolve.js` would resolve for the same session id, so the CLI's output is a drop-in for the script's.
- **The pass registry** is the single list the passes, the parity fixtures and (after the cutover) the tests that today derive `REMOVING_REASONS` from the header bullets all read. Position in the array is position in the run.
- **Transports.** `gh`: the module fetches through the runner. `files`: it reads the raw JSON the agent wrote and aliases snake_case timestamps with `aliasMcpTimestamps`. The inputs, from `mcp-transport.md`: `$DISPATCH_QUEUE_RAW` (the open `auto:build` list), `$DISPATCH_DEP_FRESHNESS` (the dependency-freshness read), `$DISPATCH_IN_FLIGHT_RAW` (`[{number, title, body, labels}]` for the open `bot:in-progress` records, `[]` when the fetch failed), `$DISPATCH_IN_FLIGHT_CLAIMS` (an object keyed by record number whose value is the claim blob's decoded content or parsed claim, `null` for not found, or `{"failure": "..."}`; `{}` when nothing was read; a number left out counts as a failed read) and the file named by the `DISPATCH_FOREIGN_STATES` environment variable (an object keyed `owner/name#N` whose value is the state string in any case or `null`; unset or unreadable changes nothing, and a ref left out or `null` still excludes as `owner/name#N (state unreadable)`). The CLI takes each path as a flag defaulting to the session-scoped path the script would resolve. The oracle for the `files` parity fixtures is the script run the way `mcp-transport.md` says to run it: raw JSON written to the input paths, the neighbour-in-flight block replaced by the documented four steps, and no `gh` on `PATH`.
- **Parity oracle.** The parity test drives the script's bash block under a scratch session id with shims for `gh` and `git` first on `PATH`. The shims and the module's fake runner consume one shared canned-response table keyed on the full argv; an unmatched call fails the test on both sides. The CLIs the script runs as subprocesses (`stage-item.js`, `log-decision.js`, `dispatch-unlanded-blockers.js`, `resolve-blockers.js`, `resolve-linked-prs.js`) run for real in the oracle, with their own `gh` calls reaching the shim. The oracle is the script at this record's merge-base after merging the integration branch; a script that changes upstream during the build is re-merged and the module follows. The module's own fixtures also run without bash. On a win32 host the parity test reports an explicit skip naming the reason (no bash oracle) and the module fixtures still run; platform handling follows `.claude/skills/windows-checkout-test-parity`.
- **Lifecycle until the removal.** The parity test is the gate that keeps the two implementations equal while both exist. Until the removal unit lands, a change to a pass in either script lands with the matching module change in the same pull request, and the module is authoritative after the cutover unit lands.
- **Cache.** The queue-order cache lives on the `health-state` branch. Fixtures never touch a real remote: the runner serves the cache reads, and a failed write-back is a best-effort miss that never fails the pull, as in the script.

### Data / API Surface

- `queuePull(options, deps)` returns `{ groups, exclusions }` and writes the session-scoped files; options include `transport`, the `files` input paths, and `omit` (a list of pass reasons to skip, for the red-when-removed fixtures); `rankNext(groups, exclusionEntries, { priority })` returns the top group or `null`. The CLI selects the ranking mode with a flag on the same command (its name is the builder's), `--help` wins over every mode, and the transport is an explicit flag (`--transport gh|files`) that never silently falls back.
- `PASSES`: the exported ordered registry, one `{ reason, removes, bypass, runsOnCacheHit, failOpen, mcp }` entry per pass (value sets in criterion 11); an informational pass has a `null` reason.
- Exit codes: the vocabulary `resolve-blockers.js` and its siblings use (0 success, 1 malformed invocation, 2 missing dependency, 3 the remote call failed) plus 4 for a pull that stopped on either stop in criterion 4, with the cause on stderr; stated in the header comment and the usage text.

### Key Files

- `plugin/bin/lib/dispatch/queue-pull.js` — new: the passes, the registry, `rankNext`, both transports
- `plugin/bin/queue-pull.js` — new: thin CLI entry
- `tests/bin-lib/dispatch/queue-pull.test.js` — new: per-reason, ranking and parity fixtures
- `docs/plugin-structure.md` — list the CLI and the module

## Gotchas

- `appendExclusion` is the one sanctioned writer (#3110: it refuses a corrupt file rather than clobbering earlier passes' entries). Writing the file with `fs.writeFileSync` loses every earlier pass's entries and the `firing` entries SKILL.md's Loop appended between pulls.
- The truncate step keeps `firing` entries; the module must too, or a drain re-selects a record it already attempted.
- `oversized` and `neighbour-in-flight` stay in `dispatch-groups.json`; the other seven reasons remove. Whether a reason removes is part of its contract (`.claude/skills/dispatch-queue-exclusion-addition`, decision 1), so the registry and the fixtures pin it per reason.
- The MCP path's documented gaps are behavior, not bugs to improve on here: `dispatch-crosspr-overlap.json` is `[]`, `dispatch-linked-prs.json` stays `{}`, and the landing judgment fails open. A module that did better on the `files` transport would fail parity.
- Parity runs the oracle in a scratch session id and a scratch directory; never against the real session-scoped files, the real `health-state` branch or the real forge.
- ASSUMPTION — verify at build: the script's bash block can be driven whole, in one process, under PATH shims for `gh` and `git`, with `CLAUDE_PLUGIN_ROOT` pointed at this checkout's `plugin/` — confirm by running the block once over a one-record fixture before writing the fixture set. If the block cannot run whole, the oracle is the script's passes extracted and run one by one, as the existing fixture tests do, and the closing comment lists the behaviors then pinned only by module fixtures read from the script (cross-pass order, criterion 3's single-reason result, the truncate that keeps `firing` entries) so a later maintainer knows where a regression would not be caught by an oracle.
- ASSUMPTION — verify at build: the `files` inputs listed under Technical Approach are the complete set the agent writes, and the dependency-freshness read's shape is the one the script's cache check expects; confirm by reading `mcp-transport.md`'s Step 2 sections and the script's cache-check block for every `$DISPATCH_*` path the agent is told to write.
