# 3066: Refuse a flaky retry when spec-reporter failures cannot all be attributed to a file

Origin: v6.138.0 release review (lens 3c error-handling), refs #3043
Defer-reason: genuinely-larger

## Current State

`verify.js`'s `--scope` flaky-retry hook (`plugin/bin/verify.js:383`) builds its retry plan from `extractFailingFiles(plain, sniffFamily(plain))` and nothing else. `planRetry` (`plugin/bin/lib/verify/flaky.js:12-21`) only checks that every *named* file is on the allowlist. `applyRetryResults` (`flaky.js:37`) then sets `exitCode: 0` once those files pass on rerun.

Before #3043, `sniffFamily` had no `spec` family. Node's default reporter output sniffed as `generic`, `extractFailingFiles` returned `[]`, and the hook refused with `no-parse`, failing closed. #3043 added `SPEC_MARKERS` (`extract.js:36-41`), so spec logs now name files from their `test at` lines. Any failure without such a line, such as a failure outside a test file or a process-level failure, is silently dropped from the plan. A passing rerun of the named allowlisted files can therefore turn a check that also carries an unattributed failure into exit 0.

`plugin/bin/lib/verify/baseline.js` already guards this exact case with `countUnmatchedFailures` and the spec-entries == fail + cancelled check. The retry hook does neither. TAP output had the same gap before #3043. This release extends it to `npm test`'s default reporter. It is reachable only when a project declares a flaky allowlist.

Evidence: v6.138.0 release whole-branch review, staged `review-4.md`. Direct read of `verify.js:383`, `flaky.js`, and `git show v6.137.0:plugin/bin/lib/verify/extract.js` `sniffFamily`.

## Deliverables

- [ ] The retry hook refuses (`retry: false`, a named reason such as `unattributed-failures`) whenever the log carries a failure `extractFailingFiles` did not name — the same accounting `baseline.js` applies (`countUnmatchedFailures` > 0, or spec entries ≠ `ℹ fail` + `ℹ cancelled`) — for the spec and TAP families alike.
- [ ] A test pinning the refusal on a spec log with one allowlisted failing file plus one unattributed failure.

## Acceptance Criteria

- [ ] A spec-reporter log with an allowlisted failing file and an extra failure that has no `test at` test-file location yields `retryDecision.retry === false` and the check keeps its non-zero exit.
- [ ] A spec log whose every failure is an allowlisted file still retries and passes as today.
