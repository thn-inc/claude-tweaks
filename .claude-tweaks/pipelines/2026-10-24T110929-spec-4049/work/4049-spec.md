Surface: backend

## Current State

The SDD-ruling deferral gate (#3880) withholds an `sdd-ruling-*` Review Console row from auto-ratify unless its staged file's header shows it safe. It has two trigger points, and at both, a staged file that could not be read collapses into the same reason a file that *was* read but carries no classifiable header gets: `sdd-ruling-unclassified`.

- **Reconciler path** — `plugin/bin/lib/reconcile/console-execute.js`'s `readInsideRunDir(base, rel)` returns `null` for four distinct situations: `stagedPath` absent / non-string / empty; an absolute path or one with a `..` segment; a path whose real location (symlinks followed, via path-guard's `resolveWithin`) falls outside the run dir; and an `fs.readFileSync` failure. `readRulingTexts` stores that `null` per item id, and `decideConsoleExecute` passes it to `sddRulingDeferralReason` (`plugin/bin/lib/console/resolve.js`), whose first line maps `null`/`undefined` to `SDD_RULING_REASONS.UNCLASSIFIED`. The resulting `rulingGateGaps` entry is `{ id, reason: 'sdd-ruling-unclassified' }` whichever of the four happened.
- **Console-resolve path** — `resolve.js`'s `readSnapshot` reads each staged `.md` through `readText`, which returns `null` on any read error; `stagedItems` then calls `sddRulingDeferralReason(s.text)` for an `sdd-ruling-*` name, so an unreadable file resolves `pending — sdd-ruling-unclassified` too.
- **Prose twin** — `plugin/skills/wrap-up/review-console-appendix.md`'s `sdd-ruling-*` bullet states this conflation outright ("…a value other than `yes`/`no`, or an unreadable file resolves `pending — sdd-ruling-unclassified`"), and `tests/build-sdd-ruling-deferral-gate.test.js` pins that sentence.

The safety posture is correct today and must stay so: every one of these cases withholds the row for a human. What is lost is the *reason*. A reviewer looking at a held row cannot tell "the ruling forgot its `Defers:` header" (fix the staged file) from "the staged file is missing or unreadable" (re-stage it) from "the `stagedPath` was rejected — e.g. a symlink planted inside the run dir that escapes it" (a tamper signal worth naming). Decision recorded in this record's brainstorming pass (2026-10-24): the finding holds as a diagnosability gap, not a safety bug — fix it by naming the read failure as its own reason.

## Release Note

Show why an SDD ruling row was held when its staged file could not be read: the Review Console now names it `sdd-ruling-unreadable` (no path, rejected path, missing file, or failed read) instead of folding it into `sdd-ruling-unclassified`.

## Technical Approach

Keep `sddRulingDeferralReason(text)` a pure header classifier and move the read-failure decision to the two callers, which are the only places that know a read was attempted.

**Reconciler.** `readInsideRunDir` cannot get the cause from path-guard's `resolveWithin` (`plugin/bin/lib/path-guard/index.js`): it returns `null` both for a leaf that resolves outside the root and for a leaf `resolveLeaf` reports `missing`/`dangling`/`unreadable`. Call `resolveLeaf` and `isAncestorOrSelf` (both already exported) directly instead — or add an opt-in cause-reporting variant to path-guard, leaving `resolveWithin`'s return contract untouched for its other callers — and map `missing`/`dangling` to `not-found`, `unreadable` to `read-failed`, and a resolved leaf outside the canonical run-dir root to `path-rejected`. Then change `readInsideRunDir` to return `{ text }` on success or `{ error: '<cause>' }` on failure, and have `readRulingTexts` keep returning a per-item map — either of those result objects, or a parallel `{ texts, errors }` pair; pick whichever keeps `decideConsoleExecute`'s `ctx` contract the smaller change. Both functions are internal to this module (`readRulingTexts` is exported for tests only), so the shape change needs no expand-contract migration — but update the `ctx` doc comment above `decideConsoleExecute` and the `#3880` comment above `readRulingTexts`, which both describe the `string|null` shape. In `decideConsoleExecute`'s ruling loop: a known read error produces `{ id, reason: SDD_RULING_REASONS.UNREADABLE, detail }`; otherwise call `sddRulingDeferralReason(text)` as today.

**Console-resolve.** `readSnapshot` already knows which names it attempted to read (`.patch`, `.md`, shadow-dup). In `stagedItems`'s `sdd-ruling-` branch, treat `s.text === null` on an attempted read as `UNREADABLE`; an `sdd-ruling-*` name readSnapshot never reads (a non-`.md` extension) stays `UNCLASSIFIED`. Carrying an explicit `readError` flag on the staged entry is cleaner than re-deriving "was it attempted" from the extension; either is acceptable. No `detail` here — the only cause on this path is a failed read of a file `readdir` just listed.

**`detail` is additive.** `rulingGateGaps` entries gain an optional `detail` key only for `UNREADABLE`; existing consumers that read `id`/`reason` are unaffected, and the `reason` string stays a member of `SDD_RULING_REASONS` (the single source the conformance test enumerates).

## Gotchas

- Fail-closed must survive the refactor. Every path that today yields `null` must still yield a gap; a new `{ error }` shape that some branch forgets to check would silently let a row through as floor-clearing. The "still withheld" AC exists for this.
- Do not change `resolveWithin` itself to return a cause: other callers depend on its `string|null` contract. A null root (`canonicalRealpath` of the run dir failing) is `read-failed`, not `path-rejected`.
- The ruling-loop default in `decideConsoleExecute` — an item id *missing* from `ctx.rulingTexts` reads as unclassified — is a different case (detect never produced an entry) and is out of scope here — the `ctx.rulingTexts` guard is #4048's subject; leave it `UNCLASSIFIED`.
- `tests/build-sdd-ruling-deferral-gate.test.js` line ~47 asserts the literal phrase "or an unreadable file resolves". Update that assertion in the same change as the appendix edit, or the full suite goes red; its every-reason loop will also fail until the appendix names `pending — sdd-ruling-unreadable`.
- `readSnapshot` sets `text: null` *by construction* for staged names it never reads. Don't let the console-resolve change reclassify those as unreadable — key on "a read was attempted," not on `text === null` alone.
- `docs/plans/2026-10-22-sdd-deferral-ruling-gate-ledger.md`, `docs/superpowers/plans/2026-10-22-sdd-deferral-ruling-gate.md`, and the archived #3880 run spec also mention the old reason set. They are historical artifacts and stay as written.
- Not a breaking change: no reason value is renamed or removed, and `detail` is an optional new key. Rows that used to read `unclassified` because of a failed read now read `unreadable` — both are `pending`, so nothing that was held becomes auto-ratified.
