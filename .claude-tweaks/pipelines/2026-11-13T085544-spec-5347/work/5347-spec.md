# 5347: Express-lane runs record no spec: in config.yml and no materialized header, so merge mode and the wrap-up pack cannot bind the record

Origin: wrap-up merge mode of #5338 (express lane run)

Defer-reason: genuinely-larger

## Current State

An express-lane run directory never records which record it is for, in either place later steps read. `plugin/bin/lib/express/cli.js:345` builds `configSet` as `mode=auto,ceremony-profile=fast-lane,integration-model=pr-first,merge-verification=…` with no `spec:` line, and `set-config.js` refuses a `spec` key (it is not a policy lever), so the express procedure cannot add one. The normal path's `manifesto-write.js` writes `spec:` (its header, line 23). The lane also writes no `work/{n}-spec.md` materialized header.

Two later steps read those places. `wrap-up/merge-mode.md`'s Resolve the run binds the adopted run with "its `config.yml` `spec:` value must equal `{n}`", so an express run has nothing to compare. `wrap-up-pack.js` resolves records from materialized headers or a manifest, so its `claim` probe fails with `records unresolved — no materialized header or manifest found` (`plugin/bin/lib/wrap-up/pack.js:664`).

Observed merging #5338 with `/claude-tweaks:wrap-up #5338 merge` (run `2026-11-13T063616-spec-5338`, PR #5345). The binding had to be judged from the run dir's name, the claim and the PR's `Fixes #5338` line and logged by hand, and the claim pack probe returned `ok: false` before teardown.

## Deliverables

- An express run's `config.yml` carries `spec: {n}`. The express procedure writes it, through `configSet` or a sanctioned run-pin key on `set-config.js` the way `integration-model` already is, so `merge-mode.md`'s binding check reads it like any other run.
- `wrap-up-pack.js` resolves an express run's record. Either the lane writes a materialized header, or the pack falls back to the config's `spec:` value, so the `claim` probe returns `ok: true`.
- A test pins both: an express `check` → `set-config` sequence leaves `spec:` in `config.yml`, and the pack's `claim` probe on such a run resolves the record.

## Acceptance Criteria

- [ ] After an express run's step 7, `config.yml` holds `spec: {n}`, and `merge-mode.md`'s binding check passes on it without a hand-logged decision.
- [ ] `node plugin/bin/wrap-up-pack.js --run {express-run-dir} --only claim` prints a `claim` entry with `ok: true` for an express run.
- [ ] `git grep -n -F 'records unresolved — no materialized header or manifest found' -- plugin/bin/lib/wrap-up/pack.js` still matches (the error stays for a run that truly names no record), and the new test fails on the current code.

## Release Note

Express-lane runs record which issue they are for, so merging one with wrap-up merge mode binds it without a manual check.

## Technical Approach

### Key Files

- `plugin/bin/lib/express/cli.js` — write spec into the express configSet
- `plugin/bin/set-config.js` — accept spec as a run pin if the configSet route is not used
- `plugin/bin/lib/wrap-up/pack.js` — resolve an express run record from config.yml spec
- `plugin/skills/_shared/express-lane.md` — state that step 7 records the run record
