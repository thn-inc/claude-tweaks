# 2821: flow / verification-brief / demo: a finished feature run never tells the human how to use or verify what was built

Surface: infra

## Current State

When a feature run finishes, none of its closing surfaces tell the human how to use or check what was built: which page to open, which steps to take, what result to expect. The filed use case was a four-spec `/flow` bundle that merged and deployed in one session. The user then had to ask in chat what had been completed and how to use it.

Verified against the tree:

- `plugin/skills/flow/summary-template.md` has these sections: Spec, Timing, Key Outputs, Manual Steps Required, Actions Performed, Creative Opportunities, Depth Opportunities and Next Actions (lines 10-87). `plugin/skills/flow/multispec-summary.md` has Timing, Manual Steps Required and Per-Spec Details (lines 8-39). Neither template has a section aimed at the user, and nothing anywhere in `plugin/skills/` renders a walkthrough of how to use the result.
- `plugin/skills/wrap-up/verification-brief.md:52-80` makes the non-parent Verification Brief depend on `exceedsOversightFloor` (`plugin/bin/lib/issues/oversight-floor.js`, #367). On `exceeds: false` it skips Steps 1-4: no `demo:pending`, no observation plan, no brief. `plugin/skills/wrap-up/verification-brief-parent-gate.md:228-238` applies the same risk-only gate on the parent path. Part 2 of that brief, the walkthrough of the primary path, is the only walkthrough aimed at a human, so a run below the floor gets none.
- `plugin/skills/demo/SKILL.md` Step 2 (lines 78-166) runs Prepare/Validate/Show from the brief's `### Observation plan`. The user found that output reads like an agent procedure.

## Deliverables

1. **One shared "Try it" block.** Define a single shared shape for a human walkthrough of each feature: precondition (deployed? data sync? feature flag?), access tier or login, entry point (route, page or command), steps, and expected result. Build it from the spec's Deliverables and Acceptance Criteria plus the QA stories that passed. For a non-web surface, use the observation plan's Entry point command instead of a route. Put it in one place (a new `_shared/` contract, or `_shared/observation-plan.md` if it fits there) and have every consumer cite it rather than copy it.
2. **Pipeline summaries.** `flow/summary-template.md` gets a mandatory `### Try it` section for each spec. `flow/multispec-summary.md` gets one section per spec plus a section for the end-to-end path across specs.
3. **Walkthrough no longer depends on the oversight floor.** In both `wrap-up/verification-brief.md` and `verification-brief-parent-gate.md`, the floor continues to gate the `demo:pending` label and the sign-off ceremony only. The walkthrough is produced on every feature delivery, including runs below the floor, where it appears in the summary or PR without a full brief.
4. **Demo shows the walkthrough first.** `/claude-tweaks:demo` renders the same Try it content at the top of its Show step, before Prepare/Validate output. That way `/demo #N` and the pipeline summary always present the same walkthrough.
5. Update the `node --test` prose suites that pin these templates or the floor-gate wording in the same change.

## Acceptance Criteria

- A `/flow` run on a record below the oversight floor (`exceedsOversightFloor` returns `exceeds: false`) still ends with a `### Try it` section in its Pipeline Summary, and that section names an entry point, steps and an expected result.
- A multi-spec run's summary has one Try it section per spec plus one section for the end-to-end path.
- A record below the floor still gets no `demo:pending` label and no sign-off ceremony, so floor-gating of the label is unchanged.
- `/claude-tweaks:demo #N` on a record whose brief has a Try it block shows that block before any Prepare/Validate output.
- The Try it shape is defined in exactly one file. `flow/summary-template.md`, `flow/multispec-summary.md`, `wrap-up/verification-brief.md` and `demo/SKILL.md` cite it and do not restate its fields.
- `npm test` passes in full.

## Release Note

Finished feature runs now end with a "Try it" walkthrough that says where to go, what to do and what to expect, even for low-risk changes.

## Technical Approach

Start with the shared block, because the other three surfaces depend on it. Most of its content already exists in the green QA stories (URL, steps, assertions) and in the spec's ACs, so the block is mostly a human-readable rendering of evidence already produced, not a new data source. Next, split the floor gate in `verification-brief.md`: one decision for the walkthrough (always) and one for `demo:pending` plus sign-off (gated). Keep the #2383 `oversightExempt` recording unchanged, because that tracks the label and not the walkthrough. Change the summary templates and demo's Show step last.

### Key Files

- `plugin/skills/flow/summary-template.md` — add the mandatory `### Try it` section for each spec
- `plugin/skills/flow/multispec-summary.md` — add Try it sections per spec plus an end-to-end path section
- `plugin/skills/wrap-up/verification-brief.md` — split the oversight-floor gate (walkthrough always; label and ceremony gated)
- `plugin/skills/wrap-up/verification-brief-parent-gate.md` — same split on the parent path
- `plugin/skills/demo/SKILL.md` — Show step renders the Try it block first
- `plugin/skills/_shared/observation-plan.md` — candidate home for the shared Try it shape, or the new `_shared/` file cites it
- `plugin/bin/lib/issues/oversight-floor.js` — read-only; its semantics do not change

## Gotchas

- This touches four skill surfaces. If the builder finds it larger than one agent-sized change, split it at the shared block: the shared shape plus the summary templates first, then the verification-brief gate split and the demo change.
- Do not remove the floor gate on `demo:pending`. The gate is correct for the ceremony. What the record objects to is only that it also hides the walkthrough.
- A run with no green QA stories (a backend or infra surface) still needs a Try it block. Build it from the ACs and an observation-plan Entry point command, and never leave it empty or render it as placeholder text.
- `/claude-tweaks:demo`'s legacy-brief path (`demo/legacy-brief-compatibility.md`) reads briefs without an Observation plan, so keep that path working.

## Original request

flow / verification-brief / demo: a finished feature run never tells the human how to use or verify what was built

**Summary:** A finished feature run never tells the human how to use or verify what was built — the closing surfaces (multi-spec Pipeline Summary, Review Console, parent-gate Verification Brief, `/claude-tweaks:demo`) report gates, commits and console rows, not "open this page, do this, expect that".

**Kind:** Gap

**Affected component:** `/claude-tweaks:flow` (summary-template.md / multispec-summary.md), `wrap-up/verification-brief.md` + `verification-brief-parent-gate.md` (oversight-floor gate), `/claude-tweaks:demo`

**Use case:**
A four-spec `/flow` bundle (data layer + three UI/AI consumers) completed, merged and deployed in one session. The user then had to ask, in chat, "tell me how I can use these new features — what did we actually complete?". Nothing the pipeline had produced answered that for a person:

- The Pipeline Summary lists build/test/review/polish outcomes, timing, manual steps and survey recommendations — nothing about the features from the user's side.
- The Review Console lists auto-applied decisions and staged patches — an audit surface, not a walkthrough.
- The parent-gate Verification Brief — the one artifact whose Part 2 is "a walkthrough of the feature's primary path" — was skipped by design: the parent's sub-issues maxed at `risk:medium` against a `risk-floor: high`, so `exceedsOversightFloor` returned false and no brief was composed. The only human-facing walkthrough is therefore gated on risk, which is the wrong trigger: a low-risk feature still needs to be found and tried by the person who asked for it.
- `/claude-tweaks:demo`'s output (Prepare/Validate/Show driven by an observation plan) reads as an agent-facing procedure; the user's verbatim assessment was "not super satisfied with the demo skill in its current output".

What the user wants, by default and independent of the oversight floor: every feature delivery ends with a human "Try it" section — per feature: the route or page to open, the login tier it needs, the steps (click/type), the expected result, and any precondition (deployed? data sync run? feature flag?). For a bundle, one section per spec plus the end-to-end path across them. `/claude-tweaks:demo` should consume and present the same walkthrough rather than a separate observation-plan shape, so the two never diverge.

**Suggested shape:**
1. `flow/summary-template.md` and `multispec-summary.md` gain a mandatory `### Try it` section (per spec: precondition, tier, route, steps, expected), composed from the spec's Deliverables/ACs plus the QA stories that passed — the stories already encode URL + steps + assertions, so the walkthrough is mostly a human-readable rendering of the green stories.
2. The parent-gate/non-parent Verification Brief's Part 2 walkthrough is produced regardless of the oversight floor; the floor should only gate the `demo:pending` label and sign-off ceremony, not the existence of the walkthrough.
3. `/claude-tweaks:demo` renders that same `Try it` content as its Show phase (and can keep Prepare/Validate as optional automation), so a human running `/demo #N` gets the walkthrough first.

**Definition:** Clear
