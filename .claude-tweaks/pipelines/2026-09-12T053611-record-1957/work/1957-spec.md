# 1957: Build-time guard: warn before reusing another record's branch that has an open PR

Surface: backend

## Overview

Extends `build/worktree-setup.md`'s Step 1.6 (Remote-only stale branch check) pattern to a second collision shape it doesn't cover: a build session reusing code (via `git cherry-pick`) from a *different* record's branch without checking whether that source branch already has an open PR. Record #1821 is the concrete incident this closes: its build cherry-picked a commit from `origin/worktree-record-1224` believing it abandoned, but that branch backed PR #1852 — still open, review-passed, awaiting a human merge decision — producing two open PRs with byte-identical implementation, caught only by an off-lens manual cross-reference during review.

**Premise correction (verified before shaping):** the originating record's Open Question section names "this run's own applied review/code-mode-steps.md Cherry-Pick Provenance Check" as an existing review-time backstop. It does not exist — `grep -rln "cherry.pick\|Cherry-Pick" plugin/skills/review/` returns nothing, and the only cherry-pick mentions anywhere in `plugin/skills/` (`_shared/policy-schema-coverage.md`, `_shared/routine-template-schema.md`, `_shared/git-discipline.md`) are unrelated generic guidance about cherry-picking a commit to the correct branch. Whatever the record's author believed had landed either never merged or was reworded/removed since filing. This spec's own Acceptance Criteria do not assume that backstop exists, and do not depend on it.

**Complexity:** Medium
**Estimated tasks:** 4-5

## Non-Goals

- #1944 (specify/dispatch-time near-duplicate *record* detection) — a different, earlier pipeline stage catching duplicate *issue content*, not duplicate *code* reused via cherry-pick. Distinct mechanism, distinct spec; this spec does not touch it.
- A review-time Cherry-Pick Provenance Check — since no such check currently exists (see Premise correction above), adding one is out of scope here; this spec is the build-time guard only, the earliest of the (at most two, now) points that could catch this.
- Detecting a manual, non-`git cherry-pick` port of code (copy-pasted by hand, or `cherry-pick`d without `-x`) — no git-native trailer exists in that case, so this spec cannot mechanically catch it. Stated as an accepted limitation, not solved here — the same class of documented, accepted gap Step 1.6 itself carries for its own remote-lookup failure case.

## Current State

- `plugin/skills/build/worktree-setup.md` (~line 86), Step 1.6 "Remote-only stale branch check": probes `git ls-remote --heads origin "{name}"` for THIS record's own deterministic branch name, and on a match, renders a stop card with three options (reuse/delete/rename) via `AskUserQuestion` interactively, and states plainly this condition is **not** a lever `_shared/auto-mode-contract.md` lists as silenceable — auto mode renders the card and hard-stops before any worktree is created, mirroring `flow/claim-targets.md`'s claim-contest HARD-GATE posture. This spec's new check reuses that exact UX/auto-mode shape for a different trigger condition.
- No existing code anywhere detects a cherry-picked commit's source branch or checks that branch for an open PR — confirmed by the premise correction above; this is new detection logic, not an extension of dormant existing logic.
- `git cherry-pick -x <sha>` appends a `(cherry picked from commit <sha>)` trailer to the resulting commit message — a git-native, always-present signal when `-x` is used; `git cherry-pick` without `-x` appends no such trailer.

## Deliverables

- [ ] Add a new check to `build/worktree-setup.md`, positioned to run after each commit lands in the build worktree (mirroring wherever Step 1.6's own check point sits in the build sequence — check point 2.5/verification-cycle territory, not Step 1's pre-worktree-creation window, since this needs commits that don't exist until build work has started): scan the new commit's message for a `(cherry picked from commit {sha})` trailer.
- [ ] When a trailer is found, resolve which remote branches contain `{sha}` (`git branch -r --contains {sha}`), excluding this record's own branch.
- [ ] For each such branch, check for an open PR (`gh pr list --repo {owner}/{repo} --head "{branch}" --state open --json number,url,isDraft`) — mirror Step 1.6's own fail-open posture on a lookup failure (log the degrade distinctly, don't treat an unreachable check as "no PR found").
- [ ] When an open PR is found on a source branch, render a stop card mirroring Step 1.6's exact template shape (see Key Files below for the literal card and options to adapt), naming the cherry-picked commit, its source branch, and the found PR's number/URL. Options: (1) stop and route to the existing PR (reuse/resume), (2) proceed anyway with an explicit, informed choice to duplicate it (recorded in `decisions.md` when chosen). **Interactive mode:** `AskUserQuestion` with these two options, recommending (1). **Auto mode:** same posture as Step 1.6 — not a silenceable lever, hard-stop always; render the card and stop the build before proceeding past this commit.
- [ ] State the `-x`-flag limitation explicitly in the new check's own prose (a manual port or a `cherry-pick` without `-x` is not caught) — don't imply broader coverage than the mechanism actually provides.

## Acceptance Criteria

1. A build worktree commit carrying a `(cherry picked from commit {sha})` trailer, where `{sha}` is contained by a remote branch backing an open PR, triggers the stop card — verified by a test fixture reproducing #1821's exact shape (a cherry-picked commit whose source branch has an open PR).
2. A build worktree commit with a cherry-pick trailer whose source branch has **no** open PR does not trigger any stop — proceeds normally.
3. A build worktree commit with **no** cherry-pick trailer (an ordinary authored commit) is never scanned by this check — no added overhead on the common case.
4. Auto mode renders the same stop card and hard-stops (does not silently continue) — verified by a test asserting no `auto`-mode bypass exists for this specific check, mirroring how Step 1.6's own test coverage asserts the same for its check.
5. `node --test` coverage for this new check passes, and `npm test` shows no regressions.

## Technical Approach

Reuses Step 1.6's exact interaction shape (stop card template, `AskUserQuestion` options, "not a silenceable auto-mode lever" posture) rather than inventing new UX for a structurally identical decision — the fact pattern differs (cherry-picked-code collision vs. same-name-branch collision) but the human decision being made ("this might already be someone else's live work — reuse it or explicitly choose to duplicate it") is the same shape both times.

The trigger condition is deliberately narrow (the `-x` trailer only) rather than a broader patch-id/content-similarity heuristic — a git-native, zero-false-positive signal that catches the exact incident class (#1821) without the maintenance burden or false-positive risk of comparing patch content across every commit. The accepted gap (manual ports) is named explicitly rather than solved, consistent with Step 1.6's own precedent of documenting rather than closing every conceivable variant of its guarded condition.

### Key Files

- `plugin/skills/build/worktree-setup.md` — Step 1.6 (~line 86) is the template to mirror for card format/options/auto-mode posture; the new check is a new step/section in the same file, positioned after commits can exist in the build worktree.

## Gotchas

- The "review-time Cherry-Pick Provenance Check" and "#1944" mentioned in this record's original Open Question are, respectively, nonexistent (verified above) and a different mechanism at a different pipeline stage (specify/dispatch-time record-content duplication, not build-time code-reuse detection) — don't conflate either with this spec's own scope.
- This check only fires on `-x`-flagged cherry-picks. Do not attempt to close the manual-port gap in this spec — it's a stated, accepted limitation, not an oversight to fix here.
- `git branch -r --contains {sha}` can return multiple branches (a shared ancestor commit, or the source branch merged into others) — check every returned branch for an open PR, not just the first; the stop card should name the specific branch(es) with an open PR found, not merely "a branch."

## Current State

build/worktree-setup.md's Step 1.6 (Remote-only stale branch check) only guards a record's own deterministically-named branch. It has no equivalent guard for a build session that identifies and reuses code from a DIFFERENT record's branch (a cherry-pick, a manual port, or similar prior-art reuse) without checking whether that source branch already has an open PR. Record #1821 is the proof: its build cherry-picked commit 1893db5b7 from origin/worktree-record-1224, believing it abandoned -- but that branch backs PR #1852, still open, already review-passed, awaiting a human merge decision for issue #1224. The result: two open PRs (#1852 and #1821's own #1942) with a byte-identical implementation, undetected until this run's review caught it via an off-lens manual cross-reference.

## Deliverables

Extend build/worktree-setup.md (or add a sibling check alongside Step 1.6) so that whenever a build session identifies and reuses code from another record's branch, it checks whether that source branch has a currently open PR before proceeding -- and if so, stops and offers the same kind of decision Step 1.6 already gives for a same-name collision: reuse/resume the existing PR, or proceed only with an explicit, informed choice to duplicate it.

## Open Question

Needs a design pass before this is buildable: (1) exact trigger condition -- what counts as "reusing another record's branch" (cherry-pick trailer detection? patch-id match? explicit human instruction to reuse?); (2) UX -- how the stop is presented mid-build; (3) auto-mode behavior -- does auto mode stage-and-continue or hard-stop. Related but distinct from two other proposals for the same root cause: #1944 (specify/dispatch-time near-duplicate record detection -- stops before either side builds) and this run's own applied review/code-mode-steps.md Cherry-Pick Provenance Check (a review-time backstop for when both this and #1944 miss). This is the build-time guard -- the earliest of the three points to catch it.
