# 6117: Give drive.js --budget the drain-overlap hold, with its own list of the run's PRs

Surface: backend
Risk-flags: none

## Overview

`drive.js --budget <n|all>` drives records one after another with no drain-overlap hold. Its merge step can mark a PR ready and merge it while a PR this same budget run opened earlier, still open (armed, held or at `pending-review`), changes the same files or closes a strong near-duplicate partner. Dispatch's driver route closes this gap by passing `--in-flight-prs` and `--near-dup-pairs` to each `drive.js` call, but `--budget` refuses both flags and builds no list of its own. This record makes the budget loop keep the list itself and hand it to every record it drives, so a drain run as a script job has the same hold a dispatch drain has.

## Non-Goals

- PRs opened by other sessions or other budget runs. A dispatch drain's merge-time hold lists only its own drain's PRs (`plugin/skills/dispatch/drain-pr-overlap.md` Step 6), and this keeps that scope.
- Accepting `--in-flight-prs` or `--near-dup-pairs` beside `--budget`. The loop owns both inputs, so the flags stay refused there (exit 2).
- Any change to the hold itself (`plugin/bin/lib/driver/merge.js`'s drain-overlap check and its reason words).

- `driveRecord` (`run.js`) already returns `final`, whose `pr` field carries the record's PR number when one was opened.

## Release Note

A budget-driven driver run now holds a merge that overlaps a PR the same run opened earlier, as a dispatch drain does.

## Technical Approach

The loop already has a session id and a temp directory, and the merge step already reads a file. So the loop writes the file dispatch would have written and sets the two `shared` fields that `--in-flight-prs` / `--near-dup-pairs` set for a named run. `merge.js` is unchanged. Every write goes through `deps` (budget.js makes no file call itself: add a `writeFile` dependency to `realDeps` if none exists, and inject it in tests). Resolve the path with `sessionTmpPath(sessionId, 'dispatch-drain-prs.json')`, the same helper and session id the queue pull uses for `dispatch-near-dup-pairs.json`, so both files sit in one directory.

The session id is the `sessionId` constant `runBudget` mints once per invocation and passes to every pull, so every pull and the list file share one directory. The loop holds the list as an in-memory array and rewrites the whole file after each append, and it is strictly sequential, so no reader sees a partial write. A failed write sets a sticky loop-level flag that overrides the per-record `shared.inFlightPrsFile` assignment for the rest of the invocation: the path is a sibling that does not exist (`dispatch-drain-prs.missing.json`), and `merge.js` already maps a `readFile` failure on the list to `in-flight-unreadable`. A held record is still driven up to its merge step and reported; the hold is the only change. The append reads `final.pr` whatever the record's stop class. `shared.nearDupPairsFile` is recomputed after every pull with an existence check and is `null` when the file is absent. Pair entries are `{ records: [a, b] }` record numbers that `merge.js` matches against each listed PR's `closingIssuesReferences`, so a pair naming a record outside this run holds nothing.

### Data / API Surface

- The file's shape is the subset `merge.js`'s `inFlightNumbers` reads: an array of `{ number }`. Dispatch's own list (`drain-pr-overlap.md` Step 5) carries `files` and `closingIssueNumbers` too. The driver re-reads both live (`gh pr view --json state,files,closingIssuesReferences`), so the loop does not need to store them.

### Key Files

- `plugin/bin/lib/driver/budget.js`: modify (list file, appends, `shared` fields per driven record)
- `plugin/bin/lib/driver/run.js`: modify (USAGE text; `realDeps` write dependency if absent)
- `plugin/bin/drive.js`: modify (header comment)
- `plugin/bin/lib/session-tmp.js`: read (path helper)
- `plugin/bin/lib/driver/merge.js`: read (the hold's file reader; unchanged)
- `docs/driver.md`: modify
- `tests/bin-lib/driver/budget.test.js`: modify

**Decision** — the drain-PR list file `dispatch-drain-prs.json` is left in place when a `--budget` run ends (Reading A), as the queue pull leaves its own session files (`dispatch-near-dup-pairs.json`) in the same `ct-session-drive-{ts}-{pid}/` directory; the `budget.js` header says so. Removing only this one file would still leave the directory and its sibling files behind, so cleanup of session temp directories is a separate concern, out of scope here. The new budget tests name the list and missing-list files as string literals (`'dispatch-drain-prs.json'`, `'dispatch-drain-prs.missing.json'`), never by importing new `budget.js` exports, so the AC7 revert check fails on missing behaviour rather than on an undefined import. (Answered 2026-11-26 in the maintainer-authorized autonomous lane, for plan-review question https://github.com/thn-inc/claude-tweaks/issues/6117#issuecomment-7183500099.)

## Gotchas

- `shared` is one object for the whole invocation. Set the two fields before each `driveOne` call and never clear them between records, because the named-record path reads them from `shared`, not from `ctx`.
- The record's own PR is in the list by the time a later record runs, which is harmless: `merge.js` ignores the own PR. But the list must be appended to only after `driveOne` returns, never before the record's own merge step.
- The queue pull removes `dispatch-near-dup-pairs.json` at its start and rewrites it (#5409), so re-check whether it exists after each pull rather than once per invocation.
- Open records touching the same files (informational, no blocker): #5884, #5661, #5659 (merge.js, settle.js, worker.js) and #5653, #5657 (run.js). Re-read each at build and rebase onto whichever has merged.

## Plan Review Clarifications

- Settled by plan review after an answered round: the spec did not say what happens to the run after `driveOne` throws. Chose Reading A: a throw still ends the run (exit 2, as today); the broken-list mark and its one stderr line are the only additions, so no later record is driven and none can merge over an unlisted PR, and the "every later driven record holds" clause applies in practice to the no-final-line case (AC8). Not Reading B (catch the throw, count the record and keep looping), which would change the exit code and summary line of a run whose `driveOne` throws.
