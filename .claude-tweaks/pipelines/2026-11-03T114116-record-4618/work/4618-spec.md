# 4618: Risk flags at intent time

Surface: infra

## Overview

**Risk flags at intent time.** Invisible risk — things clicking around in dev cannot reveal — is controlled when the work is shaped, never discovered at merge time. During `/claude-tweaks:specify` the work is classified against a fixed set of **invisible-risk categories**:

- data migrations / schema changes
- auth, permissions, access control
- public contracts other consumers depend on (APIs, file formats, hook payloads, labels)
- irreversible side effects (deletions, outbound sends, payments)

The project may extend the list in policy (`risk-categories`). Each detected flag is **recorded on the work record** so every downstream step can read it. A **kept** flag means (1) the acceptance target is forced to `local` (the human's verdict precedes merge) and (2) the plan **must contain a specific proof** for the risk (for example a migration rehearsed against a data copy; a test that an unauthenticated request is still refused); the packet shows that proof in its own section.

Interactive vs headless (designer's call): in an interactive `/specify` the detected flags are shown and the human **keeps or removes** each one. In a **headless** run (no human present) a detected category is **kept** (more caution, consistent with "automatic machinery may only add caution") and the record is **marked so the flag is shown at the next human touchpoint**, where it can be removed. Existing backlog records are **not** reclassified in bulk; they are classified when next shaped. In practice the classification hook is `/specify`, since brainstorming is third-party. Only the human removes a flag, and removal is logged to the decision log.

**Contract decisions this record pins:**

- **Line grammar (body metadata, committed; `local-files` uses the same body lines, parity test included).** `Risk-flags: migrations, auth` (comma-separated lowercase slugs from the built-in set `migrations`, `auth`, `public-contract`, `irreversible-side-effect` plus policy `risk-categories`) or `Risk-flags: none` (classified, nothing flagged). Absent line = unclassified legacy record, read as no flags (existing backlog is not reclassified). A present line that is malformed or names an unknown slug is read as **unknown = all four built-in categories flagged** (highest caution is "all of them", so there is no ordering question). Built-in slugs are frozen; a flag whose category was later dropped from policy stays flagged. Optional `Risk-flags-unconfirmed: true` marks a headless-kept flag set.
- **One sanctioned writer.** `plugin/bin/lib/issues/record.js` exports `addRiskFlags(body, slugs)` (add or preserve only) and `removeRiskFlag(body, slug, { humanConfirmed })`, which refuses unless `humanConfirmed === true` and which only the interactive `/specify` path (and the human batch in `/backlog refine`) call. A source-scan conformance test (`bin-source-scan-conformance` skill) fails on any other writer of the `Risk-flags` line in `plugin/bin`, and the skill prose says all body rewrites go through these functions.
- **Headless means no human is reachable:** `/specify --chained`, a headless `/backlog refine`, a dispatch-bound or Routine run, or any `AskUserQuestion` that errors, times out or is auto-answered. The fail direction is always keep: a detected flag is kept and `Risk-flags-unconfirmed: true` is written, never removed.
- **Removal logging.** An interactive removal logs to `decisions.md` when a run directory resolved; with none, it posts a record comment `Risk flag {slug} removed by the maintainer during shaping` (the durable log). The human's keep/removal also clears `Risk-flags-unconfirmed`. `/backlog refine` (human present) displays and can confirm unconfirmed flags through the same writer; `/claude-tweaks:accept` shows them because the packet's Risk-proofs input is a `flag` fact carrying `unconfirmed: true`, produced by this record into the packet gather, so no separate accept code is needed.
- **Plan proof.** A plan satisfies a kept flag when one plan step contains a line `Proof(<slug>): <text>` with `<text>` at least 20 characters and not merely restating the category name. The classifier appends a `## Gotchas` bullet to a flagged record telling the planner to include one such line per kept slug. The plan-audit check reads `Risk-flags:` from the materialized spec the CLI already receives (ASSUMPTION — verify at build: confirm the plan-audit input includes the spec; if not, add a `--spec` input). Unparseable plan or flag line: the check reports `could-not-parse` distinctly (gating, never silent pass), per the `parse-signal-discipline` and `plan-audit-check-addition` skills.
- **Until the consumers ship** (target resolution, local park, tripwire), a kept flag is recorded and audited only; its forcing effect arrives with the target-resolution record.
- **Guarantee limit.** The classifier sees only the declared text (Deliverables, Acceptance Criteria, Key Files); a record that omits the sensitive path gets no flag here. The diff tripwire record (#4619) is the backstop for that gap and is Related, not a prerequisite.

## Non-Goals

- Not the diff tripwire (separate record; it cross-checks the declaration against the actual diff).
- Not target resolution or the local park (separate records; they consume the kept flags).
- Not a bulk reclassification of the existing backlog.
- Not changing brainstorming (third-party); the hook lives in `/specify`.

## Acceptance Criteria

1. A record whose Key Files include a `migrations/` path or whose Deliverables mention a schema change is classified with the migrations category and the flag line appears on the created record.
2. Interactive shaping presents the flags and a "remove" answer drops the flag and writes a removal entry to `decisions.md` (when a run directory exists); a "keep" answer leaves it.
3. Headless shaping never drops a detected flag: with no human reachable, the flag is kept and `Risk-flags-unconfirmed: true` is written (test with the headless path and no `AskUserQuestion` available).
4. `plan-audit` fails (non-zero, naming the slug) for a record carrying a kept flag whose plan has no `Proof(<slug>): ...` line of at least 20 characters, passes when one exists per kept slug, reports `could-not-parse` for an unparseable plan or flag line, and does nothing for a record with no flags or an unclassified record (no new failures in existing plan-audit tests).
5. A malformed `Risk-flags:` line or one naming an unknown slug reads as all four built-in categories flagged (a single shared parse function returning `{ flags, status: 'ok' | 'unknown' | 'unclassified' }`, which every reader uses), never as "no flags"; an absent line reads `unclassified` (no flags); `Risk-flags: none` reads `ok` with an empty list. Pinned by a test for each of the three states.
5a. `removeRiskFlag` without `humanConfirmed: true` refuses; the source-scan conformance test fails when a second writer of the `Risk-flags` line is planted; an `AskUserQuestion` that errors or times out leaves the flag kept and sets `Risk-flags-unconfirmed: true`.
6. An existing backlog record with no flag lines is not reclassified by any batch operation; it is classified only when next shaped.
7. `npm test` passes.

## Release Note

Added risk-flag classification when you shape work, so changes touching migrations, auth, public contracts or irreversible actions require a specific proof and a local check before merge.

## Technical Approach

The classifier is judgment plus deterministic matching: category keywords and policy path globs give the deterministic floor; the agent's classification may add flags, never silently drop one. Recording is monotonic from the machine's side. The plan-audit check reads the same flag lines the classifier wrote, so there is one source of truth on the record.

### Data / API Surface

- Categories: `migrations`, `auth`, `public-contract`, `irreversible-side-effect`, plus policy extras.
- Record lines: `Risk-flags: a, b` and optional `Risk-flags-unconfirmed: true`.
- Plan-audit finding: category name plus the plan path.

## Gotchas

- Headless means "no human reachable", not "auto mode": `_shared/auto-mode-contract.md`'s no-new-mid-flow-stops rule applies; headless shaping stages the flag display for the next touchpoint instead of stopping.
- A flag must never be removable by any automated path; only the human, and the removal is logged. The sanctioned-writer plus source-scan test above is the enforcement; skill prose that rewrites record bodies must call the writer.
- Do not re-use the `risk:low/medium/high` label name space for flags: `risk:*` is the scoring axis.
- Parity siblings: the same flag lines must be readable from `local-files` records (`facets` or body lines per `local-store.js`'s documented key set; do not invent frontmatter keys, use body lines).
- The classifier's evidence sentence is derived from untrusted record text; neutralize it before rendering in a prompt or packet.

## Plan Review Decisions

Decided by the maintainer on 2026-11-02, who accepted these readings in session. Where a decision conflicts with the text above, the decision wins.

- **Removal on an `unknown` line: Reading A.** A human removal on a `Risk-flags:` line that reads `status: 'unknown'` is refused. The flag stays kept and unconfirmed, and nothing is logged until the line is repaired. The chosen reading gets a test, including the confirm path with a partial answer.
- **Same-family decisions: accepted as the plan makes them.** Control mode: the built-in categories, the line and plan-audit Check G run with control mode off, and only the `risk-categories` and `risk-path-globs` policy keys wait for `control-mode: on`. Unknown slug in Check G: a well-formed line naming an unknown slug needs a proof per widened flag and can be satisfied, while a malformed line is could-not-parse and fails however many proofs exist. Unaudited paths: a flagged record is ineligible for the micro-plan path and the express lane, and the trivial-plan skip path still runs the proof check.

Round 2, decided by the maintainer on 2026-11-03:

- **`Proof(<slug>)` as a packet fact: Reading B.** Add `proof` to `FACT_KINDS` and to the `risk-proofs` entry of `SECTION_KINDS` in `plugin/bin/lib/wrap-up/packet-contract.js`, as an additive contract change. `packet-validate.js` gets its own ruling for a `proof` fact with status `not-run`, so a planned proof never reads as verified.
- **Already-shaped records: Reading B.** An explicit single-record `/specify #N` always runs the Risk flags step, so the flag lines alone can turn a no-op into a body write. Batch paths stay excluded (AC6), and the exclusion holds on every batch path.

Round 3, decided by the maintainer on 2026-11-03:

- **How an unconfirmed flag reaches the packet reader: Reading A.** `plugin/bin/lib/wrap-up/packet-render.js` labels every Risk-proofs line that cites a `flag` fact carrying `unconfirmed: true`, for example `(flag unconfirmed)`, with a render test. The label comes from the fact, so no narrator can leave it out.
- **Decision-log status for a human removal: Reading B.** A human removal of a risk flag is logged `KEPT-PROMPT`, the status for a decision a human answered inline, never `AUTO`. Task 4's removal test pins the status. The removal text (`Risk flag {slug} removed by the maintainer during shaping`) is unchanged, so a reader that matches on the text is unaffected.
- **Same-family plan decisions: accepted as the plan has them.** (1) A `risk-proofs` claim whose non-flag refs are only `proof` facts routes on the proofs: `failed` goes to Tried to break, `skipped`/`not-run` goes to a new `planned` bucket rendered inside Risk proofs as `(planned, not verified: ...)`, and only all-`passed` proofs keep a verified risk proof. (2) Proof facts enter the gather through a new `--proofs <file>` input, with the gather setting kind, `status: 'not-run'` and source itself; `--flags` entries gain an optional `unconfirmed`, so existing callers' facts stay byte-identical. (3) Wrap-up Phase 1 snapshots the plan into the run directory with `acceptance-packet.js snapshot --plan`; with no single matching plan, `--plan` is omitted and a `SKIP` is logged, so a flagged record's risk-proof claim shows as visibly dropped. (4) `removeRiskFlag` and `confirmRiskFlags` throw `RISK_FLAGS_UNKNOWN` on an unreadable line rather than returning the body unchanged; the CLI catches it and reports `refused` in its envelope with exit 0.

Round 4, decided by the maintainer on 2026-11-03:

- **Persistence of a human removal: Reading A.** A logged human removal does not persist. A flag the deterministic floor detects again counts as detected: a headless re-shape re-adds it as unconfirmed, and the next interactive touch asks the human again. `spec-template.md` and the Risk flags section say so. No `Risk-flags-removed:` line or other new line contract is added.
- **Which flags an interactive re-shape asks about: every flag in `settle`'s kept set.** That covers the floor's matches, the agent's own additions (passed with `--add`) and every flag already on the record, confirmed or not, as the plan has it. A confirmed flag the floor no longer detects is asked about too, so it is not silently marked unconfirmed again.
