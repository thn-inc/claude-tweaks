# 2779: bin/verify.js: --cmd has no cross-platform env-var passthrough for the spawned check process

Surface: infra

**Related:** #2806 (untangle verify/args.js parseArgs — both records edit `plugin/bin/lib/verify/args.js`; build order matters, coordinate before dispatching both)

## Current State

`verify.js --cmd <name>=<command>` spawns each check's command via a child shell with no way to set an environment variable for just that one check's process, portably across platforms.

A caller of `verify.js` needs to set an environment variable for one named check's spawned process only (e.g. to gate an optional/expensive code path off for that check). On Windows the runner spawns via `cmd.exe`, so a POSIX-style `VAR=val command` prefix inside the `--cmd` value fails outright (`'VAR' is not recognized as an internal or external command`). The only workaround found was writing a throwaway wrapper script (a `.bat` file on Windows: `set VAR=val` then the real command) instead of passing the env var inline to `--cmd`.

## Deliverables

A repeatable `--cmd-env <check-name>=<KEY=VALUE>` flag that sets environment variables for that named check's spawned process via the child_process `env` option (not shell syntax) — works identically across `cmd.exe` and POSIX shells, with no wrapper script needed.

## Acceptance Criteria

- `verify.js --cmd foo="node check.js" --cmd-env foo=MY_VAR=1` spawns `foo`'s process with `MY_VAR=1` set in its environment, verified cross-platform (or, if only one platform is available to test on, verified via the child_process `env` option's documented behavior rather than shell-syntax parsing).
- A `--cmd-env` naming a check not declared via `--cmd` produces the same class of clear error `verify.js` already gives for other `--cmd`-name mismatches (per the existing `--cmd-name-vs-declaration` check noted in `bin/verify.js`).
- Omitting `--cmd-env` entirely leaves existing `--cmd`-only invocations unaffected (backward compatible, no behavior change for callers not using the new flag).
- `npm test` passes in full after the change.

## Release Note

Added a way to pass environment variables to verification checks that works the same on Windows and POSIX shells.

## Technical Approach

Add `--cmd-env` parsing to `plugin/bin/lib/verify/args.js` alongside the existing `--cmd` parsing, validating the `<check-name>=<KEY=VALUE>` shape and cross-checking the named check exists among declared `--cmd` names (mirroring the existing name-vs-declaration validation noted at `bin/verify.js`'s AC5/L13 comment). Thread the resolved per-check env map through to wherever the spawn actually happens (likely `plugin/bin/lib/verify/run.js`), merging it into the child_process `env` option for that check's spawn call only — not via shell-syntax prefixing, which is what breaks under `cmd.exe`.

### Key Files

- `plugin/bin/lib/verify/args.js` — add `--cmd-env` flag parsing and validation
- `plugin/bin/lib/verify/run.js` — thread the per-check env map into the spawn call's `env` option
- `plugin/bin/verify.js` — the CLI entrypoint documenting available flags

## Gotchas

- Must use child_process's `env` option, not a shell-syntax `VAR=val` prefix — that's precisely the cross-platform failure this record exists to fix, so reintroducing shell-syntax passthrough anywhere in the implementation would not actually solve the problem.
- The per-check env map should merge with (not replace) the spawned process's inherited environment, unless there's an existing `verify.js` convention for env isolation that says otherwise — check current spawn behavior before assuming.
