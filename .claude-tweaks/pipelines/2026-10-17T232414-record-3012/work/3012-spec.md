# 3012: Tolerate paraphrased claim-log/PR-early-lifecycle lines in the bookkeeping-stamps PreToolUse gate

Origin: reflect light mode from #2694, lens "Friction"
Defer-reason: tangential

## Current State

`plugin/bin/lib/hooks/pre-tool-use.js`'s bookkeeping-stamps gate (`hasClaimLogFor` /
`hasLoggedPrEarlyStep1`, and their siblings) recognizes a prior call's Step 2.8 claim or
PR-early-run-lifecycle step only by matching `decisions.md` against an exact-format regex
(e.g. `claimed #\d+ \(bin/claim-targets\.js, transport: [a-z-]+\)`). A two-call
`/claude-tweaks:dispatch` handoff whose first call logged the same, substantively-true event in
different prose (observed live: `2026-10-06T063143-record-2694`'s first call logged "flow: claimed
issue #2694 via MCP transport (gh CLI unavailable); tombstone reclaim from prior run..." instead
of the exact template) is denied at the second call's first push, even though the claim was real,
live, and independently verifiable against the claims-registry blob.

## Deliverables

- Loosen `hasClaimLogFor`'s (and the sibling PR-early-lifecycle check's) recognition to accept a
  claim/PR-early-lifecycle line that is semantically equivalent but not byte-exact to the
  documented template — e.g. a looser regex, or a structured marker the log line carries
  alongside its free-text prose, so a correctness-preserving round trip isn't required purely to
  satisfy the gate's string match.
- Alternatively (lower-risk, no regex loosening): document the exact-format requirement more
  prominently in `flow/claim-targets.md`'s "Log the claim (mandatory, #2492)" section, so a
  deviating log line is caught at write time rather than discovered at the next push.

## Acceptance Criteria

- A claim (or PR-early-lifecycle) event logged in materially-equivalent but differently-worded
  prose by an earlier call in the same run no longer blocks a later call's first push in the same
  run, OR the write-time contract is tightened enough that this divergence cannot occur in
  practice.

## Gotchas

- Do not loosen the match so far that a genuinely missing claim (never logged at all) passes —
  the gate's whole purpose is catching exactly that case. Any looser recognition must still
  require the claimed issue number and the "claimed" semantics to be unambiguously present.

## Release Note

No user-visible change: a bookkeeping gate accepts paraphrased, but substantively equivalent, claim-log lines instead of requiring byte-exact phrasing.
