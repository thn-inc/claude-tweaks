# 5768: Stop the git auto-maintenance processes that still start inside test runs

**Related:** #5324, #5297

Verified-as-of: c059556fc34954c27371c25ebd65f99e79a4eb0a

## Current State

#5297 switched git's auto-maintenance off for the suite: `gitFixtureConfigEnv` in `tools/run-tests.js` appends `maintenance.auto=false` and `gc.auto=0` to the `GIT_CONFIG_COUNT`/`KEY_n`/`VALUE_n` environment of the runner's child, and `withMaintenanceOff` in `tests/helpers/git-template.js` does the same around a template build.

A full-suite profile on main at 8646f7c (2026-11-16, `node tools/run-tests.js --full`, git trace2 per test file) still counted 559 `git maintenance run --auto --quiet --detach` processes, every one a child of another git process. Each is a wasted process start, and a detached one can touch `.git/objects` while a later step reads it.

Three ways the environment config fails to reach a git process are visible in the code. Which of them accounts for the 559 has not been measured:

- **The receiving side of a local push.** Git's local transport strips `GIT_CONFIG_*` from the receive-pack side, so a push into a local bare origin starts maintenance unless the origin's own config says `receive.autogc = false`. `disableReceiveAutoGc` in `tests/helpers/git-template.js` writes that line, but only `originWithTwoClones`, the reconcile fixtures and `tests/hooks-session-start.test.js` call it. In the profile `tests/bin-lib/issues/claims-git-cas.test.js` shows 45 pushes, 45 receive-packs and 44 maintenance runs.
- **Code under test that drops environment config.** `gitEnv` in `plugin/bin/lib/staged-patch/stack-check.js` deletes `GIT_CONFIG_COUNT` and its keys on purpose (#3997) and points the global and system config at nothing, so every commit `tests/bin-lib/staged-patch/stack-check.test.js` makes under `gitEnv()` runs without the runner's settings. Only the fixture repo's own config can reach those.
- **Tests that overwrite the count.** `tests/archive-run-verb.test.js` and `tests/bin-lib/residue/cli.test.js` build an environment with their own `GIT_CONFIG_COUNT` and `GIT_CONFIG_KEY_0`, which replaces the runner's entries instead of appending to them. Whether a maintenance run follows depends on what the child then does.

Sibling records filed with this one rebuild the fixtures in `tests/bin-lib/issues/claims-git-cas.test.js`, `tests/bin-lib/reconcile/prune-remote.test.js`, `tests/bin-lib/pre-review-catchup/cli.test.js`, `tests/bin-lib/learned-skills/` and `tests/bin-lib/staged-patch/stack-check.test.js`, and switch maintenance off in those fixtures themselves. This record attributes them but does not edit them.

## Deliverables

1. An attribution of every maintenance process in one traced run: the test file, the parent git command, and why the config did not reach it. The table goes in the PR body. The pipeline's own full verify run can carry the trace (`GIT_TRACE2_EVENT=<absolute path of an empty directory>` writes one file per git process).
2. Each class is closed at the most central point that works, so new tests are covered without knowing about it. Candidates, to be probed before one is relied on: a runner-written config file that survives the local transport (check whether `GIT_CONFIG_SYSTEM` or `GIT_CONFIG_GLOBAL` reaches receive-pack, and what the tests that set those to `/dev/null` then lose), a shared bare-origin builder that always calls `disableReceiveAutoGc`, and the fixture repo's own `.git/config`. Product code keeps its environment scrubbing.
3. A test that the attribution shows starting maintenance because it replaced the inherited `GIT_CONFIG_COUNT` entries appends to them instead, where the test does not depend on replacing them.
4. A test that keeps it closed: a push into a bare origin from the shared builder, and a commit in a fixture repo, start no maintenance process (counted by trace2 files, in the style of `tests/helpers-git-template.test.js`).

## Acceptance Criteria

- [ ] A traced run over every test file named in deliverable 1's table, less the sibling-owned files listed in Current State, shows zero `maintenance` git processes. Any that remain are listed in the PR body with the reason they cannot be closed.
- [ ] The PR body gives the maintenance process count and the total git process count for those files, before (at the branch's merge-base with main) and after (at HEAD), measured back to back on the same machine.
- [ ] The new test in deliverable 4 fails when the fix is reverted. The PR body quotes that red output.
- [ ] Every touched test file reports the same number of tests as before, all passing; no test is deleted, skipped or loosened, and test concurrency is unchanged.
- [ ] The full suite and the Windows regression job pass.
