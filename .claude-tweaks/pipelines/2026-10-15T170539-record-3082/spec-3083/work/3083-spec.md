# 3083: wrap-up: ephemeral-server stop orphans shell children on Windows; use a tree kill

Surface: infra

## Current State

`/claude-tweaks:wrap-up` stops a pipeline-started ephemeral dev server in Section D of `plugin/skills/wrap-up/cleanup-procedures-execution.md` (lines 223-236). Step 2 (line 228) reads `{run-dir}/ephemeral-server.txt` (`{pid} {port} {worktree-root} detached:{yes|no}`) and stops the server with `kill {pid}`. It adds a process-group kill (`kill -- -{pid}`) only when the record reads `detached:yes`, and forbids it for `detached:no`. Step 3 (line 229) treats an already-gone PID as "already stopped". Step 4 confirms the port is free and deletes the record.

On Windows the group kill can never run. `plugin/skills/_shared/dev-url-detection.md`'s Ephemeral server start Ownership rule (line 128) says Windows has no detach primitive, so it always records `detached: no`. Section D then kills only the leader PID. A dev command that spawns children through a shell (`npm run …`, or a launcher that starts a mock API and an app server with `shell: true`) leaves those children running and holding their ports. The next run's server start fails with EADDRINUSE, or the run silently reuses a stale server. This was observed with a two-server QA launcher (original request below).

The same leader-only stop exists on two other paths:

- `/claude-tweaks:flow`'s multi-spec teardown (`plugin/skills/flow/multispec-review-console.md` line 162) kills the shared server "once here". It cites Section D rather than restating the kill, so it inherits whatever Section D says.
- The standalone path in `dev-url-detection.md` (line 176) stops the server with `lsof -ti tcp:{port} | xargs kill`. `lsof` does not exist on Windows (the same file says so at line 111), so on win32 this path has no working stop at all.

`tests/ephemeral-server-handoff-conformance.test.js` pins Section D's current wording (its test "Section D kills the process group when detached:yes and never when detached:no", lines 58-66). No `plugin/` file mentions `taskkill` today.

This applies whatever the `detached:` field reads, because on Windows it is always `detached:no` and `/T` scopes the kill to the PID's own descendants, never the caller's shell. ## Release Note

Fix ephemeral dev servers leaving child processes running on Windows after wrap-up: the server is now stopped with a process-tree kill, so its ports are freed.

## Technical Approach

A prose-only change to two skill files plus one conformance test. Section D is the single source for the pipeline stop path, and `/flow`'s multi-spec teardown already cites it, so one edit covers both pipeline paths. The standalone path in `dev-url-detection.md` gets the matching win32 branch. `taskkill /T` ends the PID and every process it started, which is what the POSIX `detached:yes` group kill does through `setsid`. The win32 branch keeps the same "only servers this pipeline started" boundary, because it targets only the recorded PID.

### Key Files

- `plugin/skills/wrap-up/cleanup-procedures-execution.md` — Section D steps 2 and 3: the win32 tree-kill branch and its already-gone rule
- `plugin/skills/_shared/dev-url-detection.md` — Windows Ownership bullet (line 128) and the standalone stop (line 176)
- `plugin/skills/flow/multispec-review-console.md` — no edit expected; confirm line 162 still only cites Section D
- `tests/ephemeral-server-handoff-conformance.test.js` — new assertions for the win32 wording

## Gotchas

- `taskkill /F` exits non-zero both when the process is already gone and on access-denied. Only the not-found case counts as "already stopped". Anything else is a real cleanup failure and must be reported as one.
- A Windows server started by the Bash tool may run under a POSIX shell layer (Git Bash or MSYS), where `$!` can be the shell's PID rather than the Windows PID. Confirm the recorded PID is one `taskkill` accepts. If it is not, the build must report that as a finding rather than fall back silently.
- Record #3082 (`ready`) also edits `plugin/skills/_shared/dev-url-detection.md` and `tests/ephemeral-server-handoff-conformance.test.js`. Building both at once will conflict in those files, so sequence them.
- Step 4 ("Confirm the port is free") gets no new mechanism here. `dev-url-detection.md`'s `node -e` port probe already works on every platform.

## What happens

Section D stops the recorded server with `kill {pid}`, and adds a process-group kill (`kill -- -{pid}`) only when the server was started `detached:yes`. On Windows, `dev-url-detection.md` always records `detached: no` (no detach primitive), so only the leader PID is killed. A dev command that spawns children through a shell (for example `npm run …`, or a launcher that starts a mock API and an app server with `shell: true`) leaves those children running and still holding their ports.

## Why it matters

The next run's server start then fails with EADDRINUSE on the orphaned port, or the run silently reuses a stale server. We saw this with a two-server QA launcher: the mock API kept its port after the leader was killed.

## Suggested direction

On win32, stop the recorded PID with a tree kill: `taskkill /PID {pid} /T /F`. An already-gone PID is still not an error, as in POSIX step 3. The same applies wherever the plugin stops a server it started itself.
