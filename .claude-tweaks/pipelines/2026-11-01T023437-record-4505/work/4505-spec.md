# 4505: bin/ gh calls: GitHub Enterprise host dropped again (regression of #2538)

Surface: infra

**Related:** #2538, #3193, #3878, #3931, #3976, #3990, #4058, #4076, #4077, #4085, #4086, #4087, #4088, #4110, #4113, #4209, #4217, #4287, #4343, #4345, #4346, #4366, #4433, #4456, #4492

## Current State

#2538 (closed) taught `wrap-up-pack`, `resolve-blockers`, `materialize` and `preflight-records` to derive the GitHub host from `origin`. It added `plugin/bin/lib/repo-resolve.js`: `parseRepo` returns `{host, owner, repo}`, `repoSlug` returns a host-qualified `host/owner/repo` off github.com, and `repoResolutionNote` covers the rest. The fix was per call site. 30 `plugin/bin` files still spawn `gh` directly (`execFileSync('gh'` / `spawnSync('gh'` / `execFile('gh'`), and nothing enforces that a new call site passes the host.

Observed on 6.156.1, origin `https://<org>.ghe.com/<org>/<repo>.git`, `gh` authenticated to that host, `GH_HOST` not exported. A `pr-first` `/claude-tweaks:flow #N` through `/claude-tweaks:wrap-up #N merge` showed:

- `pr-checklist.js --run … --phase wrap-up` exits 5: `gh pr view failed on PR #N: spawnSync gh ETIMEDOUT`, 3/3, and also via `phase-exit.js`, so the checklist row stays unflipped. `plugin/bin/pr-checklist.js:170` calls `gh pr view <n> --json body` with no repo or host.
- `compose-subject.js N --tag human-approved --pr N` exits 3: `gh issue view N failed: spawnSync gh ETIMEDOUT`. Its GraphQL fallback already passes `--hostname` (`plugin/bin/lib/compose-subject.js:217`); the `issue view` path does not.
- `wrap-up-engine.js verify` reports acceptance-labeling `unknown`: its GraphQL call resolves `<org>/<repo>` on github.com ("Could not resolve to a Repository"). `plugin/bin/lib/wrap-up/engine-verify.js:1022` passes `--repo owner/repo`, not `repoSlug(...)`.
- The `wrap-up-pack.js` probes also reached github.com.
- With `GH_HOST=<org>.ghe.com` exported, every one succeeded. Plain `gh … -R <org>.ghe.com/<org>/<repo>` worked in the same session, so the fault is the missing host, not connectivity.

## Deliverables

1. One shared `gh` invocation seam in `plugin/bin/lib/` (extend `repo-resolve.js` or add a sibling) that resolves `origin`'s host once per process and, off github.com, sets `GH_HOST` in the child env. Explicit `-R`/`--repo`/`--hostname` args still win. It leaves each call site's existing `timeout` (where one is set, `GH_TIMEOUT_MS`) and `windowsHide: true` in place.
2. Route every `gh` call site in `plugin/bin/**` through the seam. That covers at least `pr-checklist.js`, `compose-subject.js`'s `issue view` path, `lib/wrap-up/engine-verify.js` (and switch its `--repo` arguments to `repoSlug`), and the `wrap-up-pack` probes. Keep per-site `--hostname`/host-qualified `--repo` where the host can come from a caller-supplied repo; the seam covers only origin-derived calls with no explicit host.
3. A conformance test that fails if any `plugin/bin/**/*.js` file spawns `gh` outside the seam, with an explicit allow-list for the seam itself and for call sites that already pass a host-qualified `-R`.
4. A behavioral test that runs `pr-checklist.js` and `compose-subject.js` against a fake `*.ghe.com` origin with a fake `gh` on PATH, and asserts the child saw `GH_HOST=<org>.ghe.com` or a host-qualified `-R`.

## Acceptance Criteria

- On a `*.ghe.com` origin with no `GH_HOST` exported, `pr-checklist.js`, `compose-subject.js`, `wrap-up-engine.js verify` and the `wrap-up-pack` probes all send their `gh` calls to the enterprise host (the fake-`gh` test sees the host).
- On a github.com origin, the `gh` argument lists and child env are unchanged: no `GH_HOST` is injected, and existing call-shape tests pass as they are.
- The conformance test fails when a raw `execFileSync('gh', …)` is added to any `plugin/bin` file (verified by adding one), and passes with the seam in place.
- An exported `GH_HOST` set by the user is never overwritten.
- **Decision (plan review, 2026-10-31):** `GH_HOST` is injected only for a known GitHub host: one ending in `.ghe.com`, one listed in gh's `hosts.yml`, or any host when an enterprise-token env var is set. SSH host aliases such as `github-work` get no injection. Deliverable 1 is amended to this. (Plan-review Q1: Reading B.)
- **Decision (plan review, 2026-10-31):** Any explicit `-R`/`--repo`/`--hostname` suppresses injection; a bare `owner/repo` slug means github.com, per `repoSlug`'s contract. (Q2: Reading A.)
- **Decision (plan review, 2026-10-31):** Closing rule: the decisions above settle this record's spec. Any further edge case the plan reviewer finds in these areas is the implementer's judgment, not a needs-human gap: the plan records the chosen behaviour, and the review step checks it. Plan review stops the build only for a gap that contradicts an Acceptance Criterion or a decision above.

## Release Note

On GitHub Enterprise remotes, the PR checklist, merge-subject, wrap-up verification and wrap-up probes now talk to your enterprise host without exporting `GH_HOST` by hand.

## Technical Approach

#2538 fixed this per call site, and new call sites regressed it. The reporter offered `-R <host>/<owner>/<repo>` per call or `GH_HOST` in the child env. Both go into one seam: `GH_HOST` covers subcommands that take no `-R` (`gh api graphql`), and host-qualified `-R` stays where a call already names the repo. The conformance test is what keeps a future call site from regressing again, so it is a deliverable, not a nice-to-have.

### Key Files

- `plugin/bin/lib/repo-resolve.js` — host resolution and the shared `gh` seam
- `plugin/bin/pr-checklist.js` — `gh pr view` at :170 through the seam
- `plugin/bin/lib/compose-subject.js` — `issue view` path through the seam; drop the :217 one-off
- `plugin/bin/lib/wrap-up/engine-verify.js` — `--repo` at :1022 to `repoSlug`, GraphQL through the seam
- `plugin/bin/wrap-up-pack.js` — probes through the seam
- `tests/` — conformance scan over `plugin/bin/**` plus the fake-`ghe.com` behavioral test

## Gotchas

- Do not resolve the host by running `git remote get-url origin` from the hook hot path on every call. Memoize per process, and fall back to "no host" (github.com) when `origin` is absent, as `parseRepo` returning null already implies.
- The win32 path simulation preload does not exercise this. Use the fake-`gh` PATH shim the existing gh-absent tests use, which is symlink-only on PATH.
- `GH_HOST` changes which host `gh auth` checks. A user authenticated to both hosts is unaffected, but log `repoResolutionNote` once, so a wrong derivation is visible.

## Original request

bin/ gh calls: GitHub Enterprise host dropped again (regression of #2538)

**Summary:** On a GitHub Enterprise Cloud remote (`<org>.ghe.com`), several `bin/` CLIs call `gh` without the enterprise host, so they time out or resolve the repo on github.com. Exporting `GH_HOST` by hand works around it. This looks like a regression of #2538.

**Kind:** Defect

**Affected component:** `bin/` CLIs that shell out to `gh` without passing the remote's host: `pr-checklist.js` (also reached through `phase-exit.js`), `compose-subject.js`, `wrap-up-engine.js verify` (acceptance-labeling check), and the `wrap-up-pack.js` probes.

**Repro steps:**
1. Use a project whose `origin` is a GitHub Enterprise Cloud host (`https://<org>.ghe.com/<org>/<repo>.git`), with `gh` authenticated to that host and no `GH_HOST` exported.
2. Run a `pr-first` `/claude-tweaks:flow #N` through wrap-up and its merge (`/claude-tweaks:wrap-up #N merge`).

**Expected vs. actual:**
Expected: every CLI derives the host from `origin`, as #2538's fix made `wrap-up-pack` / `materialize` do, and talks to the enterprise host.
Actual:
- `pr-checklist.js --run … --phase wrap-up` exits 5 with `gh pr view failed on PR #N: spawnSync gh ETIMEDOUT`, reproduced 3/3 times. Via `phase-exit.js`, this leaves the PR checklist row unflipped.
- `compose-subject.js N --tag human-approved --pr N` exits 3 with `gh issue view N failed: spawnSync gh ETIMEDOUT`. With `GH_HOST=<org>.ghe.com` it succeeds.
- `wrap-up-engine.js verify` reports acceptance-labeling as `unknown` with `gh api graphql … -f owner=<org> -f repo=<repo>` → `Could not resolve to a Repository with the name '<org>/<repo>'`. The graphql call goes to github.com.
- `release-claim.js` worked when `GH_HOST` was exported; it wasn't tried without it.
- In the same session, plain `gh … -R <org>.ghe.com/<org>/<repo>` calls worked fine. The fault is the missing host, not connectivity.

**Suggested fix:** route every `gh` invocation in `bin/` through the shared repo resolver's host: pass `-R <host>/<owner>/<repo>`, or set `GH_HOST` in the child env. Add a test that runs each CLI against a fake `*.ghe.com` remote, so a new call site can't regress silently.

## Architecture Alignment (build, 2026-11-01)

Beneficial deviations, kept as built:

- **Deliverable 3's allow-list is narrower than specified.** The spec allowed exempting "call sites that already pass a host-qualified `-R`". Instead every `gh` spawn is wrapped in `ghOptions` (an explicit `-R` makes the seam step back on its own, per Decision Q2), and the conformance scan's allow-list holds only three non-spawn `'gh'` literals: the `residue/probes/forge.js` argv (its runner applies `ghOptions`, pinned by the suite), a timing record and a transport enum. A future spawn therefore cannot skip the seam by passing `-R`.
- **An explicit `--repo` pins its own host for its CLI's `gh` calls** (`explicitRepoGhHost`/`pinExplicitRepoHost` in `repo-resolve.js`). Without it, a CLI given a bare `--repo owner/name` on a GHE origin sent some calls to github.com (through `--repo`) and others to the origin host (injected), splitting one record across two hosts. With it, Decision Q2's "a bare `owner/repo` slug means github.com" holds for every call that CLI makes. A user-exported `GH_HOST` still wins (AC4), and materialize keeps the pin out of the record-authored Premise-check command.
