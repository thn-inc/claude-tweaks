## Current State

- `merge-check` (`plugin/skills/assess-agent-autonomy/merge-check.md`, Step 2) renders `needs-human` for any diff that carries an agent-instruction file, unless an attempt to name a behavior change comes up empty. `.claude/skills/**` is in that class.
- Wrap-up's Skills row (`plugin/skills/wrap-up/skill-curation.md` 7.6 step 2) auto-applies an additive, high-reversibility, high-confidence skill edit as a working-tree edit. The controller's serial-commit pass (`plugin/skills/wrap-up/curation-engine.md`, section 4) then commits it on the run's own branch, in the run's worktree. That puts it in the diff `merge-check` judges: `blast-radius.js` measures merge-base..HEAD of that branch. A learned-skill edit exists to change what future agents do, so the refutation attempt cannot come up empty.
- The Auto-merge short-circuit (`plugin/skills/wrap-up/auto-merge-short-circuit.md`) runs after the curation rows, so the skill commit is already on the branch when it calls `merge-check`. `/claude-tweaks:dispatch`'s group settle reaches the same verdict on the same branch.
- The CLAUDE.md & rules row (`plugin/skills/wrap-up/claude-md-curation.md`) is stage-only, so it never commits an instruction file mid-run. The Skills row is the only curation row that commits one before the merge decision.
- Measured 2026-11-13 over every run directory since 2026-10-20, live and archived: 70 runs logged a `merge-check` verdict, 37 `auto-merge` and 33 `needs-human`. 22 of the 33 name a `.claude/skills/` edit in the rationale. 10 of those mention wrap-up on the same line, and the three read in full attribute the edit to wrap-up's Skills row. Re-checked at shaping time: #3574's `decisions.md` line reads `verdict needs-human` with blast radius `implFiles 1, implLines 11`, review PASS with zero findings, and the only reason given is `.claude/skills/windows-checkout-test-parity/SKILL.md, wrap-up Skills row commit 2aa9539db`.
- Other examples: #3670, #3491, #3820, #3892, #4816.
- Effect: a record with a live `auto:merge` grant, a clean review and a small diff still parks as `pending-review` whenever its own wrap-up learned something.
- Prior art for a wrap-up side PR: `plugin/skills/wrap-up/residue-sweep.md`'s `pr-first` landing path. It provisions a scratch worktree (`plugin/skills/_shared/scratch-worktree.md`), pushes, and opens a PR stamped `<!-- wrap-up-residue-pr -->`, armed under `housekeeping-auto-merge`. `plugin/skills/_shared/github-pr-scan.md`'s `repo-wide` item 9 arms marker-stamped housekeeping PRs, and arms a run-marker PR whose linked records all carry `auto:merge`.
- Related direction: #4608 (the human owns intent and acceptance; the machine owns everything between).

## Technical Approach

The fix goes at the single commit site, the serial-commit pass in `curation-engine.md` section 4, so it covers both callers that judge the run's branch: wrap-up's short-circuit and dispatch's group settle. `merge-check.md` and `blast-radius.js` do not change. Once the edit is off the branch, the judged diff is the record's change by construction, and nothing is filtered out of the judgment (that was option C, rejected).

The ordering inside the controller pass:

1. **Overlap test first.** Before the serial-commit pass, take the record's own changed paths: `git diff --name-only {mergeBase}..HEAD` in the run worktree, with `mergeBase` from the wrap-up pack's `blastRadius.mergeBase`. A Skills-row applied finding whose `targetPath` is in that set follows today's path.
2. **Capture, then revert.** For each other Skills-row applied finding: `git add -N -- {targetPath}` for a new file, then `git diff -- {targetPath}` to a run-dir file. Revert with `git checkout -- {targetPath}`, or remove the file for a new one. Then confirm `git status --porcelain -- {targetPath}` is clean before moving on. The existing audit step (a real modification must exist) still runs first, so a payload violation drops or downgrades exactly as today.
3. **Land.** After the pass, run `learned-skills-pr.md` once if any patch was collected. Under `local-merge`, skip it and stage every collected patch instead.

Copy the new sub-file's shape from `residue-sweep.md`'s `pr-first` branch: scratch worktree, `git -C "{worktree-path}" push origin {branch}` as its own call, `pr-early-run-lifecycle.md` Step 1/Step 3 reuse, and log before exiting the worktree. Drop the arming step entirely, and replace the local-merge fallback with staging. `merge-check.md` is read-only reference here: its floor is what this record preserves.

## Gotchas

- Item 9 has two arm routes. A housekeeping marker arms under `housekeeping-auto-merge`, and a run-marker PR arms when its linked records all carry `auto:merge`. Copying the run PR's body template carries the run marker and the closing keyword, and the sweep would then arm an instruction change on the record's own grant. Compose the body from scratch.
- The scratch worktree branches from the integration branch tip, not the run's branch. A patch generated against the run's branch applies cleanly only when the record did not touch that file (deliverable 4's test). The `git apply --check` failure path still has to exist, because the integration branch can move under a long run.
- The judge's edit sits uncommitted in the shared run worktree. A later phase's catch-all commit (Phase 4 step 12) would sweep a non-reverted edit back onto the run's branch. The revert must land before any later commit, and the clean-status check proves it.
- Console-approved skill updates (Review Console "On approval" step 2) are out of scope. A human, or the console's own resolution stances, approved them, and they commit on the run's branch as today.
- Multi-spec runs share one worktree and one curation pass per consolidated wrap-up. The overlap test uses the union of every member's changed paths.
- Plain `refs #{n}` in the PR body does not populate `closingIssuesReferences`. Verify that against the live API before relying on it, since item 9 reads linked records from it.
- This plugin repo's own `plugin/skills/**` edits are record-owned changes, not Skills-row output (7.2 scans `.claude/skills/` only). They keep hitting the floor, by design (the 6 runs naming a plugin instruction file).
- Deliverables 1-4 are the shaping agent's calls under the user's no-questions instruction, not the user's rulings. Re-open any of them in the build's plan review if it is wrong.
