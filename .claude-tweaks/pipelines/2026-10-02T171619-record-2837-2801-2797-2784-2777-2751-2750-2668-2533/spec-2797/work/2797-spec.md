# 2797: Consider a jev-model-router-style per-turn model/effort picker

Surface: infra

## Current State

`jev-model-router` picks model and reasoning effort per Claude Code turn via a non-blocking hook. claude-tweaks today has model-profile selection guidance for subagent dispatch (Fast/Standard/Capable, per the Subagent Contract referenced in CLAUDE.md's Model Selection section), but no automatic per-turn picker for the *main* session's own model/effort choice — that decision is currently manual (`/fast` toggle, explicit model selection). Whether an automatic per-turn picker would meaningfully improve on the current manual/subagent-scoped approach, versus adding complexity for marginal gain, has not been evaluated.

## Deliverables

Investigate `jev-model-router`'s actual mechanism (what signals it uses to pick model/effort, how it hooks into the turn lifecycle) and decide whether a similar fast decision-layer fits claude-tweaks' build/flow lifecycle specifically — not the main interactive session broadly, since that's Claude Code's own territory, not this plugin's. Scope the evaluation to where claude-tweaks itself dispatches subagents (build/flow/dispatch's Task and Agent calls) and whether an automatic picker there would improve on the Subagent Contract's existing static Fast/Standard/Capable model-profile guidance.

## Evaluation Outcome

**`jev-model-router`'s actual mechanism (web-researched, not assumed).** Sources: [Pulumi — "Route every Claude Code message to the right model with jev"](https://www.pulumi.com/blog/route-every-claude-code-message-to-the-right-model-with-jev/), [emergent.sh — "jev router routes claude code tasks cheapest"](https://emergent.sh/news/jev-router-routes-claude-code-tasks-cheapest), [aitmpl.com mod listing](https://aitmpl.com/component/mod/productivity/jev-model-router). It installs as a Claude Code Templates "mod" (`npx claude-code-templates@latest --mod productivity/jev-model-router`), running as a pass-through proxy on `localhost:4000` that intercepts the session's own outbound requests. On each new user message (not on tool steps or background/subagent tasks — those inherit the session's established tier or default to Haiku) it makes one live call to a small decision model ("Jev", TypeSafe's System One) carrying a few hundred tokens of message+session context, at ~$0.00003 and a few-hundred-ms latency. That call answers three typed questions: (1) a 4-way task classification (`mechanical`→Haiku 4.5, `routine`→Sonnet 5, `complex`→Opus 5.5, optional `deep`→Fable 5.1), (2) a safety gate that force-escalates to the top tier if the request plausibly touches production/credentials/permissions/billing (probability ≥0.7), and (3) a policy check that blocks a downgrade below a reference tier if the message itself claims a tier was pre-decided (≥0.5 confidence) — an explicit anti-gaming/prompt-injection guard. Each tier has its own confidence floor (Haiku ≥85%, Sonnet ≥60%, Opus/Fable ≥30%); below floor, it falls back to the more capable of the top two candidates. It then rewrites only the `model` field (plus whatever else a smaller model can't accept) before forwarding to Anthropic. Decisions are logged by default.

**Comparison against this project's existing mechanism.** Read in full: `plugin/skills/_shared/subagent-dispatch-core.md`'s Model Selection section (the section CLAUDE.md's Subagent Contract points to; `subagent-output-contract.md` itself just redirects there), and `plugin/bin/resolve-profile.js`. claude-tweaks' mechanism is structurally almost the inverse of jev's on every axis that matters:

| Axis | jev-model-router | claude-tweaks today |
|---|---|---|
| Scope | Every turn of the live interactive session | Per-dispatch, at `Task`/`Agent` call sites only (explicitly never the main session — out of scope here per the Gotchas, and also out of scope for jev structurally, since jev skips tool/subagent steps) |
| Classification basis | Live LLM call reads *this instance's* actual message content/context, per turn | Static: the skill author hard-codes a profile (`[Use: Fast\|Standard\|Capable]`) into the dispatch prompt at authoring time, based on the *task's type*, not its per-instance content |
| Resolution mechanism | Inference call to a decision model, non-deterministic, costs tokens+latency per turn | Pure config lookup (`resolve-profile.js`): per-invocation override > `policy.yml` project policy > static table, then a stance shift — zero inference calls, deterministic given inputs |
| Adaptation to difficulty | Predictive — classifies before running, every time | Reactive — ships at the declared profile; the contract's own upgrade path is "upgrade one profile when the agent comes back `BLOCKED` for reasoning reasons," not a pre-run guess |
| Safety/anti-gaming | Explicit escalation gate + anti-prompt-injection downgrade guard, because the classified input is arbitrary, adversarial user text | Not applicable in the same way: the "input" being classified is the dispatcher's own authored prompt, not arbitrary live user text — there's no equivalent gaming surface for a skill-authored dispatch |
| Frontier/Capable gating | Confidence-threshold-driven per call | Explicit, enumerated singleton slots only (`frontier-run-cap`, interactive-context precondition, per-run tally) — a structural ceiling, not a per-call probability |

**Why a jev-style live picker does not carry over to claude-tweaks' dispatch sites.** jev-router earns its keep because the thing it classifies — the next thing a human types into an interactive session — is unpredictable in content and difficulty from one turn to the next, so a fresh per-turn judgment call adds real information. claude-tweaks' dispatch sites are the opposite shape: each site (`/review`'s review-angle agents, `/test`'s qa-prompts scouts, `/dispatch`'s build/test fan-out, etc.) is invoked repeatedly with a *known, fixed task shape* that the skill author already classified once, at authoring time, into a work profile — "a review-angle agent over one file is Standard-class work," "a search scout is Fast-class work." The complexity that varies, varies by *which dispatch site*, not by the live content of a given invocation the way an interactive chat message does. Adding a live classification call ahead of every dispatch would mean paying inference cost and latency, N times per pipeline run, to re-derive a classification the skill author already encoded for free in the `[Use: {Profile}]` line — without jev's actual value proposition (reacting to unpredictable per-turn content) applying, since the content shape at a given dispatch site is not unpredictable in the way a user's next chat message is. Where within-site variance *does* exist (e.g. one review target file is trivial, another is gnarly), the existing reactive upgrade path (`BLOCKED` → bump one profile) already handles it without paying the classification tax on every dispatch's happy path — and avoids the failure mode the Subagent Contract's own rationale calls out ("an under-powered agent on judgment work returns confident nonsense shaped exactly like a finding"): a live classifier that misjudges difficulty produces exactly that failure mode, just earlier in the pipeline, and jev's own design needs a dedicated safety-escalation gate to guard against it — overhead with no clear counterpart benefit here.

**Decision: keep the static Fast/Standard/Capable/Frontier guidance as-is; no per-dispatch automatic picker is adopted.** Rationale, so the question isn't silently re-raised: (1) the static table is per-invocation overridable via `policy.yml` and the resolver's `cliOverride`, which already gives a human (not a live model) the lever jev gives an inference call — without the added cost, latency, or non-determinism; (2) the reactive `BLOCKED`→upgrade path already covers the within-task-type difficulty variance a live classifier would otherwise be approximating; (3) the Frontier singleton ceiling is an explicit, auditable, enumerated set of slots — a structural guarantee a confidence-threshold-driven live picker could not reproduce without its own new governance layer; (4) jev's core value (reacting per-turn to unpredictable live human input) doesn't transfer to dispatch sites whose task shape is fixed and known at authoring time. No proposal is made to integrate a jev-style picker at `build`/`flow`/`dispatch`'s `Task`/`Agent` call sites; this evaluation is the record that the comparison was made and the static approach was deliberately retained.
