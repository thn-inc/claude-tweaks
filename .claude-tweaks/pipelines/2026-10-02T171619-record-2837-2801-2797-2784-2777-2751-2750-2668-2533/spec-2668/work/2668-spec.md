# 2668: Add XSS / upload / webhook-signature checks to security checklist

Surface: infra

**Related:** #2624, #2625, #2751

## Current State

The pre-launch security checklist from #2624 landed (PR #2774). Its two main pieces:

- `plugin/skills/_shared/criteria-security-hardening.md`: a criteria fragment. It has "What the generator hands you", "What to flag", "What NOT to flag", "Scope boundary", and "Severity calibration" sections, plus "Copy-paste prompts (one per check, runnable standalone)" lettered (a)–(c).
- `plugin/bin/lib/code-health/candidates-security-hardening.js`: a static generator that emits `{ file, kind, evidence }` candidates. It has one `scan*` function per kind, driven by directory and signal regexes such as `ROUTE_DIR_RE` and `AI_GUARD_SIGNAL_RE`.

The criteria file is registered in `plugin/bin/lib/code-health/criteria.js` as the `security-hardening` focus, and the generator is loaded by `focus-generators.js`. Tests live in `tests/bin-lib/code-health/candidates-security-hardening.test.js`.

It covers exactly three kinds today: `client-secret`, `missing-ownership-check`, and `unguarded-ai-endpoint`. Three well-known gaps from a transcribed source (Instagram Reel) are uncovered, each with a standard mitigation:

1. **XSS via unescaped output.** User-submitted text rendered into HTML without escaping runs script in another user's session.
2. **Unrestricted file uploads.** An upload handler with no type/size validation, served from an executable path, can lead to remote code execution.
3. **Unverified payment webhooks.** A "payment succeeded" callback (e.g. Stripe) accepted without verifying its signature can be forged.

## Deliverables

1. Three new candidate kinds in `candidates-security-hardening.js`, each with its own `scan*` function and signal regexes, flagging only when no mitigating signal appears nearby:
   - `unescaped-output`: raw-HTML sinks such as `dangerouslySetInnerHTML`, `innerHTML =`, `v-html`, `{!! !!}`, or `| safe` with no sanitizer signal.
   - `unrestricted-upload`: upload middleware or handlers such as `multer`, `formidable`, `busboy`, `request.files`, or `UploadFile` with no type or size limit signal.
   - `unverified-webhook`: webhook route files with no signature-verification signal such as `constructEvent`, `verifySignature`, `timingSafeEqual`, or a `*-signature` header check.
2. `criteria-security-hardening.md` extended for the three kinds:
   - "What the generator hands you" lists six kinds.
   - "What to flag", "What NOT to flag", and "Severity calibration" each gain entries for the new kinds.
   - "Copy-paste prompts" gains (d), (e), and (f) in the same voice as (a)–(c).
3. The cross-reference: the file's header line cites #2668 alongside #2624, and "Scope boundary" names the three added checks.
4. Generator tests for each new kind: one vulnerable fixture that is flagged, and one mitigated fixture (sanitized output, validated upload, signature-verified webhook) that is not.

## Technical Approach

Follow the existing generator's shape: a per-kind `scan*` function that matches a sink or handler regex on route or client files, then checks a text window (`windowAround`) for a mitigating-signal regex before pushing a candidate. Read `scanUnguardedAiEndpoint` first as the closest model (sink present, guard absent). Then write the criteria entries and prompts by reading prompts (a)–(c) and matching their structure.

### Key Files

- `plugin/bin/lib/code-health/candidates-security-hardening.js` — three new `scan*` functions and their signal regexes
- `plugin/skills/_shared/criteria-security-hardening.md` — new kinds across every section, prompts (d)–(f), header and scope-boundary cross-reference
- `tests/bin-lib/code-health/candidates-security-hardening.test.js` — vulnerable and mitigated fixtures per new kind

## Gotchas

- Siblings #2663 (legal/compliance questions) and #2666 (secrets-manager and rotation check) extend the same two files. Build them sequentially, not in parallel groups, or expect merge conflicts in the kind list and the prompt lettering.
- This record is stamped `size:low` / `ceremony:fast-lane` from before shaping, when it read as prose-only. With three generator kinds plus tests it is closer to medium. Confirm at `/claude-tweaks:backlog refine` before granting.
- Keep the checks stack-agnostic. The signal lists should cover several frameworks and read as "a mitigation is visibly present", not require one vendor's API.
- A static scan only sees the absence of a recognized mitigation, the same limitation the existing ownership and AI-endpoint checks document. Say so in the new "What NOT to flag" entries.
