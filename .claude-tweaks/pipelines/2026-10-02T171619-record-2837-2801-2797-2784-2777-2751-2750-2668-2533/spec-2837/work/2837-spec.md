# 2837: Dispatch two-call gate passes a first call that bypassed /flow — gate on run artifacts, not just STATUS/OUTCOME

Verified-as-of: c8f389a605ecf680a27528bafef1ef995959fd64

Defer-reason: tangential

## Current State

`dispatch/two-call-gate.md` section 2 dispatches the second (`review,polish,wrap-up`) call on `DONE`/`DONE_WITH_CONCERNS` **and** `OUTCOME: build-test-ok` alone. `sequential-execution.md` mechanically checks only that the status line is present and well-formed (#2429). Nothing checks that the first call actually ran `/claude-tweaks:flow`, so a self-reported `build-test-ok` from an agent that implemented the record directly passes the gate.

Observed in firing `2026-09-29T140150-dispatch-standalone` (explicit list of 11 records, first calls on the Standard profile with `task-prompt.md`'s first-call template inlined verbatim):

- **#2806, attempt 1** (run dir `2026-09-29T154722-record-2806`): reported `STATUS: DONE` / `OUTCOME: build-test-ok` but never invoked the `/flow` Skill. It implemented the refactor directly, left commit `6fc4e2ded` unpushed, and the run dir held only `context/`: no `decisions.md`, `run-state.json`, `config.yml`, no claim, no `bot:in-progress`, no PR. Its `MANIFEST:` line pointed at `context/claims.md`.
- **#2806, attempt 2** (after resetting the worktree): invoked `Skill claude-tweaks:flow "#2806 build,test"`, then skipped Step 2.8 (claim), the Manifesto (`config.yml`), `run-state.json` and the PR-early push. It implemented directly and materialized the spec *after* the code commit. Again reported `build-test-ok`.
- **#2805**: live claim and draft PR #2822, but no `config.yml`/`run-state.json` (the second call backfilled them).
- **#2792**: full build, but PR-early never ran; the branch stayed unpushed until the second call opened PR #2831.

The dispatching session caught #2806 only by inspecting the run dir by hand. Had #2806 carried `auto:merge`, the second call would have reviewed and possibly merged work that never took a claim or went through PR-early.

This recurs after #1826 (closed 2026-09-23, itself a recurrence of #1013/#1129/#1145), which covered the same "run dir empty despite build commits" symptom. The gate itself was never given an artifact check, so the class remains reachable.

## Deliverables

1. A mechanical first-call artifact check, run by the dispatching session the moment the first call returns and **before** the two-call gate dispatches the second call. It checks that: `{minted-run-dir}/run-state.json` and `config.yml` exist; the claim blob `claims/issue-{n}.json` on `claims-registry` is live with `runId === basename(PIPELINE_RUN_DIR)` for every group member; and, under `integration-model: pr-first`, `run-state.json` records a `pr.number` whose head branch exists on `origin`. Implement it as a small `bin/` CLI or `bin/lib/dispatch/` function (injectable runner seam per the gh-api-module-pattern), not prose alone.
2. `two-call-gate.md` section 2 and `sequential-execution.md`'s "The loop" treat a failed artifact check exactly like a missing/malformed status line (#2429): never dispatch the second call, route through the section 5 terminal path, and log one `decisions.md` line naming which artifact was missing.
3. Unit tests for the check: a fully-formed run passes; each missing artifact (no `run-state.json`, no `config.yml`, claim absent, claim held under a different `runId`, pr-first with no recorded PR) fails with a distinct reason.

## Acceptance Criteria

- [ ] A first call that reports `build-test-ok` but left no claim under the minted run id is never followed by a second-call dispatch, and the firing log names the missing claim.
- [ ] A first call with a live claim but no `config.yml`/`run-state.json` fails the check with a reason naming the missing file.
- [ ] Under `pr-first`, a first call with no recorded PR (or an unpushed head branch) fails the check.
- [ ] A normal, fully-formed first call (claim + `run-state.json` + `config.yml` + pushed PR) passes and the second call dispatches unchanged.
- [ ] `two-call-gate.md` section 2 states the artifact check as a gate condition alongside STATUS/OUTCOME, and cites the check's module.
- [ ] `npm test` passes.
