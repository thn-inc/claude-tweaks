# 2784: Subagent Contract: no canonical bounded-polling idiom for a long external wait

Surface: infra

## Current State

No canonical bounded-polling idiom exists for a subagent that must wait on a genuinely long external process (e.g. a live CI run or cloud deploy taking many minutes) without violating the "never run_in_background, never end a turn on a passive wait" rule.

A subagent's own work required verifying a live external process spanning many minutes (a CI run, a cloud deployment dispatch) across several such waits in one session. The rule correctly forbids backgrounding plus a passive wait (a background task's completion notification never reaches an orchestrator watching a dispatched agent) but offers no first-class alternative pattern for this shape of task. The only compliant approach found was a hand-rolled bounded polling loop repeated across several tool calls (a shell `while` loop checking a condition every ~15s, bounded to a fixed iteration count, re-invoked when the loop exhausted its bound without the condition resolving).

This worked, but:
- It's easy to get subtly wrong — the natural first instinct is backgrounding plus a wait, exactly the forbidden pattern.
- From outside, "an agent doing bounded polling with real tool calls" and "an agent stuck in a silent loop" are hard to distinguish without inspecting the transcript. A coordinating session watching the dispatched work sent live check-in interruptions during a genuinely-compliant polling sequence, which turned out to be false alarms once investigated.

## Deliverables

Document a canonical bounded-polling idiom for "wait on a genuinely long external process without backgrounding": the exact loop shape, the iteration/timeout budget, and what to log so an external observer can tell "polling as designed" apart from "stuck."

## Acceptance Criteria

- The canonical idiom is documented in the dispatch/subagent-contract shared guidance (the exact home to be confirmed against this repo's current shared-contract layout — `plugin/skills/_shared/subagent-output-contract.md` is the most likely fit, since it already owns the dispatch-behavior conventions this gap sits alongside).
- The documented idiom specifies: the loop shape (a bounded check-interval loop, not backgrounding), a concrete iteration/timeout budget (not left open-ended), and a logging convention that lets an external observer distinguish "polling as designed, still within budget" from "appears stuck."
- A subagent following the documented idiom for a multi-minute external wait no longer needs to hand-roll the pattern from scratch, and a coordinating session reading its progress has a documented signal to check before interrupting.

## Release Note

Documented a standard way for subagents to wait on long external processes without looking stuck.

## Technical Approach

Locate the existing "never run_in_background, never end a turn on a passive wait" rule's canonical home in this repo's shared skill guidance (search `plugin/skills/_shared/` and `docs/skill-authoring.md` for where dispatch/subagent behavioral rules already live) before adding the new idiom — it should sit alongside that rule, not in a new, disconnected location. Compose the idiom from the pattern already proven to work in practice: a bounded check-interval loop (real tool calls, not a background process) with a fixed iteration cap, re-entered when the cap is exhausted without resolution, plus a per-iteration log line naming what's being waited on and the current iteration count — that log line is what lets an external observer tell "polling as designed" apart from "stuck."

### Key Files

- `plugin/skills/_shared/subagent-output-contract.md` — most likely home for the new idiom, alongside existing dispatch-behavior conventions (confirm before writing; the exact section may differ)
- `docs/skill-authoring.md` — cross-check for whether dispatch/polling conventions are documented there instead

## Gotchas

- Confirm the actual canonical location of the existing no-background-wait rule before adding the new idiom next to it — this record's own research did not pin the exact file, only the most likely candidate.
- The logging convention (Acceptance Criteria) matters as much as the loop shape itself — the real-world cost this record documents (false-alarm interruptions from a coordinating session) came specifically from the *absence* of a way to externally distinguish compliant polling from a stuck loop, not from the polling mechanism itself being wrong.
