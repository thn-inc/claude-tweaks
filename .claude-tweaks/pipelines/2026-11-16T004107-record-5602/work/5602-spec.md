# 5602: Add wait-for.js: a foreground command that blocks until a child agent, CI or a process changes state, or a bound passes

Surface: backend

**Related:** #5604, #5601, #5066, #4959, #5168, #5134, #5210, #5543, #4366, #5211, #4524, #4989, #5147
Risk-flags: none

## Current State

Subagents wait by calling `sleep` over and over. Measured on 2026-11-16 over the 30 days from 2026-10-17, across every project on this machine that uses the plugin: 30,932 transcripts, 29,484 of them subagent transcripts, each tool call counted once by its id (scratch script; re-derive before relying on a number).

- 54,241 Bash calls begin with `sleep`: 5.9% of all 916,043 Bash calls. 54,034 of them (99.6%) are in subagents, where they are 7.8% of 696,991 Bash calls. The design measured 52,181 and 5.6% on 2026-11-15 over a window that starts nine days earlier.
- The count is rising: 1,187 in the week of 2026-10-19, 10,822 and 9,983 in the next two, 31,992 in the week of 2026-11-09.
- 53,509 (99.0%) ask for exactly 20 seconds, the number the plugin's own prompts name. 98.6% return within two seconds of the time asked for.
- 1,138 subagent transcripts (3.9%) hold all of them: a median of 11 each, 122 at the 90th percentile, 2,671 at most. They form 6,043 separate waits; 1,567 of those are ten sleeps or longer.
- The harness refused 150 sleep calls. All 150 asked for more than 20 seconds, out of 281 that did. A longer sleep is not a way to make fewer calls.

What the sleeps wait for, classified by what the agent probed between sleeps or chained to the sleep, and by an earlier `Agent` launch in the same transcript when nothing was probed:

| Target | Sleep-led calls | Share |
|---|---|---|
| A child agent's completion notification | 52,132 | 96.5% |
| A background process or its log | 429 | 0.8% |
| An agent's or background task's output file | 276 | 0.5% |
| CI checks on a pull request or a workflow run | 211 | 0.4% |
| A child worktree's git state (the at-bound progress probe) | 166 | 0.3% |
| A verify or test run | 101 | 0.2% |
| A dev server or browser | 86 | 0.2% |
| A test-suite slot | 57 | 0.1% |
| Other or unclassified | 576 | 1.1% |

87.6% of the calls are a sleep that follows a sleep with nothing probed in between. The design's unit names CI checks, a background verify and a sibling agent as the targets. Together those are under 2%. The wait that matters is the keep-alive rule in `plugin/skills/_shared/subagent-dispatch-core.md` (line 72): "repeated `sleep 20` Bash calls, at most 60 (20 minutes) per wave of children". Under that rule the child's `<task-notification>` is what tells the agent a child has reported; the sleeps only keep the turn alive until it arrives.

What exists already:

- `gh pr checks --watch` blocks until checks finish. It has no bound, and it reads only the check rollup. `plugin/bin/pr-checks.js` exists because the rollup alone reads green too early: it also lists the head commit's workflow runs and the ready-run requirement, and classifies through `plugin/bin/lib/pr-checks/classify.js` into `green`, `red`, `inherited-red`, `pending`, `no-ci`, `stale` or `read-failed`. It reads once and exits 0 in every state.
- `plugin/bin/ci-gate-record.js` records how long CI took after a verdict. It never waits.
- `plugin/bin/verify.js` is itself a blocking command. It polls a CI job up to `waitSeconds` (`plugin/bin/lib/verify/ci-source.js`) and exits 3 when CI gave no verdict. It queues for a suite slot with no bound (`plugin/bin/lib/suite-slot.js`, `acquireSlot`). #5134 and #5168 own those two waits.
- The pipeline driver polls CI and the merge in-process (`plugin/bin/lib/driver/steps.js`, `plugin/bin/lib/driver/merge.js`). A prose-lane agent cannot call either.
- Nothing lets an agent block on a child agent. The `SubagentStop` hook (`plugin/bin/lib/hooks/subagent-stop.js`) runs when a subagent stops, and its payload carries `session_id`, `agent_id` and `agent_transcript_path`. Its `run` returns at once when the session owns no pipeline run or the agent type is a third-party one, and returns before any pending count for a reply that ends with a valid status line. It calls `countPendingDispatches` (the stopping agent's own async launches that have not reported, ignoring launches older than 60 minutes) only for a reply that is not compliant. So on the paths most stops take, the hook reads no transcript and computes no count.
- Observed on 2026-11-16 in one dispatched subagent of an interactive session, Claude Code 2.1.325: `CLAUDE_CODE_SESSION_ID` is set in the subagent's Bash shell and equals the root session's id; `CLAUDE_PLUGIN_ROOT` is not set; and the `agentId` in an async `Agent` launch result is the name of the child's transcript file (`agent-{agentId}.jsonl`) under the root session's `subagents` directory. The hook's payload for a nested child's stop was not observed.
- `plugin/bin/lib/hooks/contract-retries.js` keeps a per-session file under the OS temp directory, keyed by session id. `plugin/bin/lib/suite-slot.js` exports `isPidAlive`.
- `plugin/skills/test/verification.md`'s Foreground rule records the two Bash-tool facts the bounds rest on: a call with no explicit `timeout` is moved to the background after about 120 seconds, and 600,000 ms is the largest `timeout`.

Design: `docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 4, unit 4.1. The design leaves "one command with targets or one per target" to the builder. This record takes one command with targets: one exit-code contract, one bound, one output line and one name for the prompts to state, in a file that has 8 bytes of headroom today.

## Deliverables

1. **Probe first; the probe gates the rest.** Before any fixture is written, capture how the harness behaves and commit the result as `docs/reference/blocking-wait-probe.md`, with the observed output quoted and the Claude Code version named. The waiter is always a dispatched agent. Probe three waiters: a dispatched `Agent` subagent of an interactive session, a subagent of a headless `claude -p` worker, and a context-handoff child. For each, record:
   - whether `SubagentStop` fires when the waiter's own child finishes, and whether the payload's `session_id` equals the `CLAUDE_CODE_SESSION_ID` in the waiter's Bash shell;
   - whether the payload's `agent_id` equals the `agentId` in the waiter's launch result;
   - whether the child's completion notification, arriving while a foreground Bash call blocks, is delivered when that call returns;
   - whether a foreground Bash call may run 540 seconds with `timeout` 600000.
   Decided 2026-11-16: if any of the four answers is "no" for any of the three waiters, the build stops after Deliverables 1 and 2, opens its pull request with those two, and reports the probe file as its result with `NEEDS_CONTEXT`. Deliverables 3 to 6 are then re-shaped by a human from the probe's facts. A wait that cannot see a child's stop would notice a finished child up to nine minutes late where `sleep 20` notices it within 20 seconds, and the other signals (the child's transcript, its output file) are ones the wait rule forbids reading.
2. **The table as a tool.** `tools/wait-polls.js` prints the counts and the target table above as JSON. It takes the flags `tools/guard-refusals.js` takes for the same job: `--projects-dir`, `--since-days` (default 30), `--until` and `--match`. Its top-level keys are `window`, `transcripts`, `bashCalls`, `sleepLed` (each split into `main` and `subagent`) and `targets`. It reads the transcript store once per real directory and counts a tool call once by its id. It has one test over a fixture store. The pull request carries its output for the 30 days before the build.
3. **A stop marker.** On each `SubagentStop` whose payload has an `agent_id`, a `session_id`, and an `agent_transcript_path` that differs from `transcript_path`, the hook appends one JSON line to `ct-agent-stops-{session_id}.jsonl` under the OS temp directory:
   `{"agentId": "<agent_id>", "at": <epoch seconds>, "blocked": <true|false>, "pending": <integer|null>}`
   - `blocked` is true when the hook answered this stop with `decision: "block"`.
   - `pending` is `countPendingDispatches` for the stopping agent's transcript, and `null` when the transcript cannot be read or its shape is indeterminate.
   - The marker is written on every path, the two early returns included, after the hook has its answer. A failed write changes nothing the hook returns.
   - One module, `plugin/bin/lib/wait-for/marker.js`, owns the file name, the line shape, the writer and the reader. The hook requires it lazily, so a load fault costs only the marker.
   Decided 2026-11-16: the hook computes the pending count for every such stop, which adds one transcript read per subagent stop on the paths that read none today. A marker without the count would have to be taken as final, and a child that ended its turn with its own children still running would then be reported while its notification is still held.
4. **`plugin/bin/wait-for.js`**, with the logic in `plugin/bin/lib/wait-for/`. One command, three targets:
   - `agents --ids <a,b>`: returns when a listed agent has a final stop that no earlier call returned. A stop is final when `blocked` is false and `pending` is 0. A `null` count is not final.
   - `ci --pr <n>` or `ci --run <id>`: returns when the pull request's checks, read and classified as `pr-checks.js --pr` does, are in any state but `pending`, or when the workflow run's status is `completed`.
   - `pid --pid <n>`: returns when the process is gone.
5. **One contract for all targets.**
   - Bounds: `--max-seconds` (default 100, at most 570) bounds one call. `--window-seconds` (default 1,200, at most 3,600) bounds a wait that spans calls, and the command keeps that window itself, per session. The first call for a target opens a window; a later call for the same target joins it. An `agents` call joins an open window when every id it lists belongs to that window; a `ci` or `pid` call joins the window of the same pull request, run or pid. A window closes when a call returns at its deadline, or when an `agents` call returns with no listed id left pending. The call after a deadline opens the next window. The nearer bound ends the call; when both pass at the same poll, `bound` is `deadline`.
   - Decided 2026-11-16: the command keeps the window; the caller passes no deadline back. A caller that repeated its first call with a deadline flag of its own would open a fresh window each time and never reach a bound.
   - Loop: poll, and if nothing changed sleep in-process for the interval or the time left to the nearer bound, whichever is shorter; poll once more at the bound. The interval is one second for `agents` and `pid` and 30 seconds for `ci`.
   - Output: one JSON line with `target`, `state`, `changed`, `elapsedSeconds`, `deadlineEpoch`, `window` (1 for a first window, one more for each window of the same target that ended at its deadline) and, at a bound, `bound` (`call` or `deadline`). `agents` adds `reported` and `pending` (lists of ids) and `stops` (the number of stop lines in the session's file, 0 when it is absent). `ci --pr` puts the classifier's state in `state`; `ci --run` puts the run's status in `state` and adds `conclusion`.
   - Exit codes: 0 the state changed; 3 a bound passed with no change; 2 a malformed invocation or a source that cannot be read. No exit 1.
   - Each final stop is returned once. The call that returns it records it as delivered through `marker.js`, and a later call that lists the same id waits for a later stop. So a child that was resumed after it reported can be waited on again by the same id, and no sequence of calls can return the same stop twice.
   - `ci`: a read that fails on the first poll exits 2. A read that fails after a good one counts as `pending`, and the output's `readFailures` counts them.
   - The process prints no transcript content and reads no transcript.
6. **Docs.** `docs/hooks.md` describes the stop marker and the read it adds. `docs/plugin-structure.md` lists the CLI and the tool. The CLI's usage text says that a verify run and a suite slot are waited on by `verify.js` itself.

**Decision rule for any further gap (author, 2026-11-16).** Where this record leaves a choice between readings and no Decision above settles it, the build does not stop for it. It takes the reading that, in this order: keeps a run on the previous plugin release working; puts the rule in code and not in skill prose; stays inside this record's Key Files. ## Technical Approach

Follow `.claude/skills/gh-api-module-pattern` and its `cli-wrapper-contract.md`: the logic is an exported `run(argv, deps)` that returns an exit code, and every side effect (`runner`, `now`, `sleep`, `stdout`, `stderr`, `env`, the liveness check) goes through `deps`, so no test waits in real time except the two real-process tests.

The marker file. The hook keys it by the payload's `session_id`; the CLI by `CLAUDE_CODE_SESSION_ID`, or `--session` when given. The probe's first question is whether those two are the same value. The path comes from one function in `marker.js` that both sides call. The id becomes part of a file name, so the function returns no path for an id that holds any character other than a letter, a digit, `-` or `_`. Lines are appended, never rewritten, so two stops at once cannot lose one. The delivered stops and the open windows are kept in a second per-session file beside the first, appended the same way, which is why every target needs the session id. The plugin never deletes either; a stop line is about 100 bytes and the OS clears its temp directory.

What the marker's fields mean is a contract between the hook and the CLI. AC8's round trip pins the shape. Whoever changes when the hook blocks a stop, or what `countPendingDispatches` counts, changes which stops are final: #5066 and #5543 edit the same file.

`ci --pr` calls the same read and classification `pr-checks.js --pr` uses; it does not parse `gh pr checks` output. `stale` means the pull request's head is not the local head, and the caller decides what that means.

`--max-seconds` defaults to 100 because a Bash call with no explicit `timeout` is moved to the background after about 120 seconds. An agent that passes `timeout` 600000 passes `--max-seconds 540`. If the probe measured other limits, the default stays 20 seconds under the measured default window and the cap 30 seconds under the measured largest timeout, and the probe file says so.

What the prompts may rely on: the target names, the flag names, the exit codes, the `bound` values and the output keys named above. #5604 states them in skill prose, so a change to any of them is a change to that prose in the same pull request. The defaults and the caps are tunable; #5604 states only `--max-seconds 540` and `timeout` 600000, and relies on the default window being 20 minutes.

The argument parser follows the contract in unit 3.1 of `docs/superpowers/specs/2026-11-15-audit-simplification-design.md` (branch `worktree-design-audit-simplification`): an unknown flag and a missing value are usage errors, `--help` exits 0. AC7 pins it. `plugin/bin/lib/cli-args.js` does not exist on 2026-11-16. If it exists when this is built, use it; if not, that unit's migration of every `plugin/bin` CLI covers this one, and nothing is recorded here.

## Gotchas

- The transcript store is reachable through several directory names on a machine with more than one account: on the measuring machine eight names resolve to one directory, and a walk over all of them counted every call eight times. A fork's transcript also replays its parent's history. Resolve each root to its real path, read main transcripts before subagent ones, and count by tool-use id. `tools/guard-refusals/transcripts.js` (`scanStore`) already walks the store and counts by id; reuse its walk where it fits.
- No suite-slot target and no verify target. `verify.js` is the blocking command for a verify run. #5168 gives its slot wait a bound and an exit code, and #5134 keeps its CI wait under the foreground ceiling. #5210 covers a queued run that was moved to the background. Together those two targets are 0.3% of sleep-led calls.
- Nothing reads `wait-for.js` after this record. The prompts are changed by #5604, which this record and #5601 block, so that a run on the previous release, whose prompts say `sleep 20`, is never told to call a command it does not have.
- The hook runs on every subagent stop in every session. Read `docs/hooks.md` first: the hook never breaks a session, and it prints nothing new. The comment at the third-party exit in `subagent-stop.js` says an exempt stop pays no transcript read; Deliverable 3 changes that on purpose, and the comment is updated with it.
- `countPendingDispatches` ignores a launch older than 60 minutes, so a stop can read as final while a child that old still runs and the harness still holds the notification. The caller is not misled for long: a final stop is returned once, the caller's next call waits for a later stop, and 60 minutes is also the wave's ceiling.
- A marker with no line for a listed id looks the same as a child that is still running. `stops: 0` at a bound, in a session where children have finished, is the sign that the hook wrote nothing; the probe file is where to look.
- #4366 and #5211 list `plugin/bin/pr-checks.js`. Import from it; do not move its code.
- A real-process test that spawns a child and waits for it must hold on Windows. Read `.claude/skills/windows-checkout-test-parity`. The marker path is built with `path.join` from `os.tmpdir()`.
