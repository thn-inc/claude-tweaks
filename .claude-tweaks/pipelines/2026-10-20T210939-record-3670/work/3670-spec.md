## Current State

#3562 fixed `tests/pipeline-run-dir-adoption-anchoring.test.js` for Windows checkouts: it read live skill markdown with a raw `fs.readFileSync(…, 'utf8')` and applied a bare-`\n` fence regex, which matches nothing once `core.autocrlf=true` gives the doc `\r\n` endings. Four of them also run what they extract, so a second Windows layer can sit behind the CRLF one, as #3517, #3555, #3565 and #3587 found: `\r` left in a captured snippet breaks `bash -c`; a native backslash `CLAUDE_PLUGIN_ROOT` interpolated into a heredoc turns into JS escapes; and a literal `/bin/sh` resolves to `<drive>:\bin\sh` on win32 and throws `ENOENT`. #3565's sweep records `verify-expectations-writer-conformance.test.js:66`'s `/bin/sh` spawn as masked behind the CRLF extraction failure, with no open record owning it.

2. For each file that runs what it extracts (`tidy-release-note-repair-conformance`, `dispatch-firing-exclusion`, `multispec-not-run-callsite`, `verify-expectations-writer-conformance`), check the second layer and fix it test-side: a forward-slash `CLAUDE_PLUGIN_ROOT` where one is interpolated into a script, and no literal `/bin/sh` spawn target (`verify-expectations-writer-conformance.test.js:66` — use `bash` from the inherited `PATH`, as the sibling `bash -c` suites that pass on `windows-latest` do).

4. Before opening the PR, re-run the sibling grep above and re-check open records; drop any file another record claims by then and record the grep output in the PR body.

## Release Note

Fixed ten skill-prose tests that failed only on Windows checkouts because of line endings.

## Technical Approach

Test-side only, following `.claude/skills/windows-checkout-test-parity/SKILL.md`'s "Build CRLF inputs from the LF text" pattern and its Anti-Patterns row "Treating a CRLF fix as the whole Windows fix for a test that extracts and runs a skill's shell snippet". `readText()` is the repo's single EOL-normalizing read for governed markdown; `skill-prose-conformance-tests` already requires it for every prose suite. Normalize at the read, not with a `\r?\n`-tolerant regex: a suite that runs its extracted snippet would still hand `bash -c` a snippet full of `\r` (reproduced in #3562's scratch run).

## Gotchas

- Do not add a `.gitattributes` `eol=lf` rule for `tests/` or the skill files; the parity skill scopes it to the hashed upstream-drift fixtures on purpose.
- Do not build a CRLF case from a raw read: on a Windows checkout that yields `\r\r\n` (#3523). Build it from the `readText()` value.
- The second-layer failures are inferred for most files, not observed: the CRLF extractor failure masks them on Windows today. Investigate whatever shape the dispatched Windows run shows; never add a win32 skip to turn a run green.
- If this proves too large for one PR, split it along the read-only / extract-and-run line — the four extract-and-run files each need their own Windows proof.
