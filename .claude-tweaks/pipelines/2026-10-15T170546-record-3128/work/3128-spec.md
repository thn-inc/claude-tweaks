# 3128: Add an event-driven unblock path for watch-item records blocked on a future /specify run

Origin: reflect light from #1350

Defer-reason: tangential

## Current State

Record #1350 (and #649 AC2 before it) is a "standing watch-item" whose acceptance criterion can
only be confirmed by observing a live `/claude-tweaks:specify` decomposition run over 2+
`ceremony:standard` sub-issues at the moment it happens — the observing session must be the one
that ran it, since the evidence is that session's own transcript. Nothing currently triggers a
re-check at the right moment; instead, each attempt is a manual re-check that almost always finds
"no qualifying run occurred in this session" and closes unmerged. This is now 4 attempts deep
(2026-08-29, PR #2011, PR #3006, and this one), each paying a full build+test+review+wrap-up
pipeline pass to re-confirm the same non-event.

## Deliverables

A mechanism for a `/specify` decomposition run that produces 2+ `ceremony:standard` sub-issues to
itself record (to a durable, cross-session-readable location — e.g. a dated note under
`docs/plans/` or a small append-only log) that a qualifying run occurred, with enough detail
(timestamp, sub-issue count, transcript pointer if available) for a future watch-item record to
consume without needing to be the observing session itself. This decouples "a qualifying event
happened" from "the one record that cares about it happened to be running at the time."

## Acceptance Criteria

The next `/specify` decomposition run producing 2+ `ceremony:standard` sub-issues writes a
discoverable record of that fact; a subsequent re-check of a watch-item record like #1350 can
confirm or refute its AC from that record without requiring the original observing session's own
transcript.

## Release Note

No user-visible change: internal mechanism for closing out watch-item backlog records more
reliably.
