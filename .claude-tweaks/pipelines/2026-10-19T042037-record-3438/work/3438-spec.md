# 3438: claims: reuse claim-store resolveRepoSlug in claim-targets.js repoSlugOf

Origin: reflect hindsight from #3393

Defer-reason: tangential

## Current State

#3393 exported `resolveRepoSlug(runGh?)` from `plugin/bin/lib/issues/claim-store.js` (a `gh repo view --json nameWithOwner` lookup that resolves to `null` on a thrown or empty answer). `plugin/bin/lib/claim-targets/claim-targets.js` still keeps its own `repoSlugOf(gh)` doing the same lookup, but it lets a thrown `gh` error propagate rather than resolving to `null`. The two are therefore not drop-in equal: `repoSlugOf`'s single call site (`claim-targets.js` ~line 269) wraps it in `runClassified` and distinguishes a timeout (retried) from other errors, which a null-swallowing resolver would hide.

## Deliverables

1. Decide whether the timeout-vs-error classification at the single `repoSlugOf` call site needs the thrown error (likely yes).
2. Either give `resolveRepoSlug` a throwing variant `repoSlugOf` can share, or record in `claim-targets.js` why the two resolvers must stay separate.

## Acceptance Criteria

- AC1: `claim-targets.js` has no private `gh repo view` slug resolver, or a comment names why it must differ from `resolveRepoSlug`.
- AC2: `claim-targets.js`'s existing tests pass unchanged on the gh-present happy path and on a failing `gh repo view`.
