# 6102: verify.js: a wholly operational record still runs every suite at build's final verification

Surface: infra

**Related:** #5075, #5093, #5210, #5929
Risk-flags: none

## Current State

A scoped `verify.js --scope … --integration-branch {ref}` run with no usable stamp anchor anchors on the integration-branch merge-base only when the declaration has an `impact` block. `selectScope` (`plugin/bin/lib/verify/scope.js:53`) reads `if (base === null && decl && decl.impact) base = fallbackBase || null;`, and every other declaration falls to the `base === null` branch and returns `{ mode: 'full', suites: '*' }` with `matched: []`. `plugin/bin/verify.js:763` already computes `fallbackBase` (the merge-base that `resolveBase` returned) for any declaration whenever `--integration-branch` is passed with no anchor and no `--base`. The gate is only in `selectScope`. `tests/bin-lib/verify/scope.test.js`'s `no impact block is unchanged: no impact key, fallbackBase ignored` pins today's behavior for a non-impact declaration (`EXAMPLE`, `stamp: null`, `fallbackBase: MB` gives `mode: 'full'`, `base: null`).

The first verification in a fresh worktree (build Common Step 5) never has a stamp, so a consumer project whose declaration has no `impact` block runs every suite there, even when the branch's whole diff since the merge-base maps to `suites: []`. The filed occurrence (claude-tweaks 6.176.0, a wholly operational record) ran about 4.5 minutes of suites plus a slot wait for a diff of `work/{n}-spec.md` and `docs/plans/*-ledger.md`. `report.json` showed `scope.mode: "full"`, `matched: []`. A second occurrence (comment on this record) ran the full suite three times, and a known flaky test failed the gate each time on a branch with no code.

This repo's own declaration has `impact`, so it already anchors on the merge-base (#4024). The gap is in every consumer declaration without it.

**Decision** (2026-11-25, autonomous lane authorized by the maintainer; answers the plan-review question of 2026-11-25): **Reading B.** The merge-base anchor extends only to declarations that carry a `ci` block (in addition to `impact` ones, which already anchor). A declaration with neither stays `full` on a first scoped run. Reason: the anchor trusts that the integration branch at the merge-base is verified by its own CI. A `ci` block is the declaration's own statement that CI exists, while a project without one (typically `local-merge`, no forge CI) has nothing else checking the merged-in tip. The reported occurrence had a `ci` block (its run hit `ci-job-not-found`), so Reading B fixes it.

**Family rule for related questions:** the merge-base fallback applies if and only if all of these hold: no usable stamp anchor, `--integration-branch` given, no explicit `--base`, and `decl.impact || decl.ci`. Everything else behaves exactly as today. The trust question is keyed on the declaration's own content, never on policy keys such as `integration-model`, which `verify.js` does not read. Mark Task 1 `**Review risk:** high` as the plan review suggested.

## Release Note

On a project whose verify-scope declaration takes suites from CI but has no impact map, the first scoped verification in a new worktree now checks only what the branch changed since the integration branch, so a branch of non-code files runs no test suite.

## Technical Approach

One condition in `selectScope` changes. The anchoring invariant is kept: every non-full mode's `base` is either the stamp's `fullSha` or the merge-base, and the stamp `verify.js` writes for a non-full pass already records `fullSha: sel.base`, so the next scoped run anchors on that merge-base stamp and later deltas chain as they do for impact declarations. Merge-narrowing (#3072) applies once that stamp exists, as it does today.

The trust assumption is the one #4024 already made for impact declarations: the integration branch at the merge-base is covered by its own CI, so a branch's first scoped run needs only the suites its own diff selects.

## A wholly operational record still pays for a full local suite run at build's final verification

**Kind:** gap

**What happened.** `/claude-tweaks:build` Spec Step 2.5 (`build/manual-steps.md`) routes a record whose Deliverables are all operational (no source change) straight to Common Step 5. There, the scoped `verify.js --scope … --integration-branch master` call had no pass stamp to anchor on (first verification in a fresh worktree), so it forced `mode: full` and ran every suite locally (about 4.5 minutes of suites, plus a wait for a suite slot held by another checkout's run). That happened although the branch's whole diff against the integration branch was two files (the materialized `work/{n}-spec.md` and the run's `docs/plans/*-ledger.md`), both of which the project's `verify-scope.json` rules map to `suites: []`. `report.json` showed `scope.mode: "full"`, `matched: []`, `changedFiles` = those two paths, `base` = the merge-base. The PR was a draft, so CI could not answer either (`ci-job-not-found`).

**Why it matters.** The verification proves nothing about the record's work: the tree under test is the integration branch's own tip plus two non-code files, which that branch's CI already covered. On a machine where suites queue behind sibling sessions, it is the longest step of an otherwise minutes-long operational run.

**Suggested direction.** When there is no stamp anchor but `--integration-branch` resolves a merge-base, classify the branch's own diff against that merge-base with the declaration's rules; if every changed path maps to no suite and no static check, select `none` (or `static-only`) and stamp, the same outcome a bookkeeping-only delta gets from a stamp anchor. Alternatively, let a wholly operational record (as Spec Step 2.5 already detects) pass that fact to Common Step 5.
