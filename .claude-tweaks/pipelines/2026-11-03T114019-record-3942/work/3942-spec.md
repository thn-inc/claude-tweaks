# 3942: Ratifying a deferral SDD ruling at the Review Console files no backlog record

**Related:** #3880
Origin: build final review of #3880

Defer-reason: genuinely-larger

## Current State

At the Wrap-Up Review Console, ratifying an `sdd-ruling-*` item (`apply`, per `wrap-up/review-console-appendix.md`'s `sdd-ruling-*` bullet) writes its ledger row to `accepted` and files nothing; only `reverse` composes a record proposal (`staged/ledger-record-sdd-ruling-{N}.md`). #3880 added a safe-deferral class that console-auto ratifies at `unattended`: `Defers: yes` with exactly one valid `Defer-reason:` header (including `tangential` and `pre-existing-outside-diff`). That deferred work ends as a terminal `accepted` row, the ledger is deleted once nothing is open, and the work reaches no backlog record. This contradicts CLAUDE.md's "No implicit deferrals" and `_shared/deferral-gate.md`'s premise that a `Defer-reason:` goes with a record. It is not a regression: before #3880 every ratified ruling was dropped the same way. Found by #3880's final whole-branch review (finding I-3). The ratify contract is shared by the single-run console (`review-console.md` step 1 and step 7), the multi-spec console (`flow/multispec-review-console.md`), the interactive Override vocabulary (`review-console-interactive.md`), the on-PR console (`_shared/console-on-pr.md`, `_shared/console-execution.md`, `bin/lib/reconcile/console-execute.js`), and `finish-console`.

## Deliverables

Ratifying a deferral ruling (`Defers: yes`, or any `Defer-reason:` header line, with a valid reason) composes a record proposal via `specShapedBody`, the same way `reverse` does today. Current State is the ruling and the finding it deferred; Deliverables is the deferred work; the record carries the staged file's own `Defer-reason:` value. The proposal routes through the console's record-creation step in the same pass. Once the record exists, the ledger row is written `deferred` with Resolution `ratified → #{n}`; if creation fails or is refused, the row stays `open`.

Ratifying a `Defers: no` ruling (a settled design decision) keeps today's `accepted` write-back unchanged.

Apply the same rule at every console surface that ratifies a ruling: single-run, multi-spec, interactive, on-PR/reconciler execution, and `finish-console`.

Add a conformance test pinning the ratify-files-a-record rule in `wrap-up/review-console-appendix.md` and its code twin, if one exists.
- **Decision (2026-11-03, maintainer, answering the plan-review question on this record): a human ratify of a gate-withheld deferral ruling files the record.** The withheld cases are `Defers: yes` with no `Defer-reason:`, more than one reason, an invalid reason, no `Defers:` line, and a single valid `Defer-reason: needs-human-decision`. For a missing, multiple or invalid reason, the filed record's `Defer-reason:` is derived from `_shared/deferral-gate.md`'s Fix-now criteria the way `reverse` derives one. For `needs-human-decision`, the human's tick is the decision, and the staged reason is carried onto the record. `sddRulingRatifyAction` separates "not auto-ratifiable" (kept in `rulingGateGaps`, so an unattended console still holds these rows) from "not ratifiable", and returns `file-record` for any deferral a human ratifies.
- **Decision (2026-11-03, maintainer, second plan-review round): the three `sdd-ruling-unclassified` header shapes.** Several agreeing `Defers: no` lines with no `Defer-reason:` are a settled decision: a human ratify writes `accepted` with no record, the same as a single `Defers: no`. Conflicting `Defers:` lines (`yes` and `no`), a `Defers:` value that is neither `yes` nor `no`, and a missing `Defers:` line each file a record on a human ratify. An empty staged ruling file is not ratifiable: nothing is filed and the row stays `open`.
- **Closing decision (2026-11-03, maintainer):** plan review may stop this build only for a gap that contradicts an acceptance criterion or a recorded decision on this record. Any other gap is settled as a plan amendment and logged for the Review Console, never asked.

## Acceptance Criteria

Ratifying a `Defers: yes` `sdd-ruling-*` item with a valid `Defer-reason:` produces a backlog record carrying that reason, and the ledger row is `deferred` with the record number.

Ratifying a `Defers: no` ruling still writes the row `accepted` with no record.

A refused or failed record creation leaves the row `open`, never `accepted` or `deferred` without a record number.

`npm test` passes in full.

A human ratify (a tick, or Approve all at a human-present console) of each gate-withheld deferral case (no reason, more than one reason, an invalid reason, no `Defers:` line, `needs-human-decision`) files one record and writes the row `deferred` with that record's number; the same rows stay held, unfiled, under unattended console auto-resolution.

A human ratify of a ruling whose header carries several agreeing `Defers: no` lines and no `Defer-reason:` writes the row `accepted` with no record; conflicting `Defers:` lines, a `Defers:` value other than `yes`/`no`, or a missing `Defers:` line files one record and writes the row `deferred` with its number; an empty staged ruling file files nothing and leaves the row `open`.

Plan review stops this build only for a gap that contradicts an acceptance criterion or a recorded decision on this record; every other gap is settled as a plan amendment.

## Architecture Alignment (build, 2026-11-03)

- Beneficial deviation: `readHeader` (`plugin/bin/lib/console/sdd-ruling.js`) now counts every `Defers:` header line, an empty or multi-word value included, so the human-ratify rule above can classify conflicting and non-`yes`/`no` values. Because the unattended console-auto gate (`sddRulingDeferralReason`) reads the same parse, a header such as `Defers: no` plus a stray `Defers:` or `Defers: not sure` line is now held as `sdd-ruling-unclassified` instead of auto-ratifying as a settled `no` — a fail-closed tightening of the gate this record's withheld-rows criterion relies on.
- Beneficial deviation: `finish-console` refuses an `accepted` ledger write-back for a ruling whose staged file is not a settled `Defers: no` (a deferral, an unclassified header, or an empty/blank/unreadable file), mapping the row to its staged file by the row's `(staged/…)` Item note, else by the file's `Ledger:` header number — the mechanical form of "never `accepted` … without a record number" on the Approve-all path.
