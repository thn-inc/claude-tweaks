# 3065: claim-targets: a gh timeout while resolving the repo slug exits 2 (usage error) instead of the transient-failure exit 4

Surface: infra

## Current State

`bin/claim-targets.js` resolves the repo slug once, before claiming anything, via `repoSlugOf` (`plugin/bin/lib/claim-targets/claim-targets.js:85-89`, a single `gh repo view --json nameWithOwner` call). Any exception from that call goes down the usage-error path: it prints `claim-targets: could not resolve repo slug — {err}` followed by the full `USAGE` text, and returns exit `2` (`claim-targets.js:210-215`). An empty slug does the same (`:216`).

So a `gh` timeout (`spawnSync gh ETIMEDOUT`) is reported as "malformed invocation or missing dependency", the same class as a bad `--targets` value. The CLI already has a transient class for exactly this: exit `4` with a `{transient: [...], released, releaseFailed}` envelope (`claim-targets.js:314`, `:400`; usage line `:40`). `/flow`'s Step 2.8 renders a "Claim failed (transient)" card for exit 4, and treats exit 2 as a hard stop, "a bug in this call" (`plugin/skills/flow/claim-targets.md:255-257`, `:274-275`). That doc line explicitly lists "repo resolution failed" under exit 2 today.

The `gh` timeout bound is `GH_TIMEOUT_MS` (`plugin/bin/lib/shared-primitives.js:85`, default 5000 ms). It can be overridden by `CLAUDE_TWEAKS_GH_TIMEOUT_MS` or the `gh-timeout-ms` policy key (`plugin/bin/lib/policy-schema.js:123`). The same module already ships the retry-once primitive this case needs: `isTimeoutError` (`shared-primitives.js:162`) and `runClassified(fn, mapError, { retryOnTimeout: true })` (`:166`). Per `plugin/skills/_shared/policy-schema.md:221`, `reconcile`'s `release-merged.js`, `preflight.js` and `pr-state.js` already use it. `claim-targets.js` does not.

Observed (original request below): on a GitHub Enterprise host, the slug lookup took 2.3–3.6 s under contention from Step 2.8's file-overlap scan (`bin/preflight-records.js`), hit the 5000 ms bound, and exited 2 twice in a row. Raising the timeout to 30000 ms claimed all three targets on the first try.

## Deliverables

1. Route `repoSlugOf`'s `gh` call through `runClassified(..., { retryOnTimeout: true })`, so that a single timeout is retried once at the same bound before anything is reported.
2. Reclassify slug-resolution failures in `run()`:
   - **A timeout that survives the retry** (`isTimeoutError`) exits `4`. stdout carries the CLI's existing transient envelope, with every requested target listed as `{issue, error}`, and `released: []` / `releaseFailed: []` since nothing was claimed yet. stderr carries one line naming the timeout and the `gh-timeout-ms` / `CLAUDE_TWEAKS_GH_TIMEOUT_MS` override, and never the `USAGE` text.
   - **`gh` absent (ENOENT) and an empty slug** stay exit `2` (a genuine missing dependency or misconfiguration), but stop printing the `USAGE` text, which describes argv and is irrelevant to either cause.
   - **Under `--keep-going`**, the documented contract is that the CLI never exits 3, 4, or 5. A post-retry timeout therefore records every target in `skipped` with `reason: 'transient'` and exits 0, matching every other transient site.
3. Update `plugin/skills/flow/claim-targets.md`'s exit-code table. Exit `2` no longer covers repo-resolution timeouts; exit `4`'s description covers the pre-claim slug-resolution timeout.
4. Add tests in `tests/bin-lib/claim-targets/claim-targets.test.js`, using the module's injectable `gh` runner:
   - a timeout that succeeds on retry (claims proceed, exit 0);
   - a timeout on both attempts (exit 4, transient envelope, no `USAGE` text on stderr);
   - the same double timeout under `--keep-going` (exit 0, every target skipped as transient);
   - ENOENT (still exit 2).

## Acceptance Criteria

- With a fake `gh` that throws an `ETIMEDOUT` error on the first `repo view` call and succeeds on the second, `run()` claims normally and returns 0.
- With a fake `gh` that throws `ETIMEDOUT` on both calls, `run()` returns 4. stdout parses as `{transient: [{issue, error}, ...]}`, with one entry per requested target, plus empty `released`/`releaseFailed`. stderr does not contain the `USAGE` string.
- The same double timeout with `--keep-going` returns 0, and every target appears in `skipped` with `reason: 'transient'`.
- A fake `gh` that throws ENOENT still returns 2, and stderr does not contain the `USAGE` string.
- `plugin/skills/flow/claim-targets.md`'s exit-2 bullet no longer lists repo-resolution timeouts, and its exit-4 bullet names the slug-resolution timeout case.
- `node --test tests/bin-lib/claim-targets/*.test.js` passes.

## Release Note

Fix claim-targets reporting a slow GitHub response as a usage error. A repo-slug timeout is now retried once, then reported as a transient failure.

## Technical Approach

Reuse `runClassified` and `isTimeoutError` from `shared-primitives.js` rather than adding a local retry loop, matching the three reconcile callers. `repoSlugOf` runs before any claim, so the transient exit needs no release step. Build the envelope directly instead of going through `abort()`, or pass empty claimed sets to it, whichever keeps the envelope shape identical to the existing transient sites. Leave the global 5000 ms default alone; projects on GitHub Enterprise already have `gh-timeout-ms`.

### Key Files

- `plugin/bin/lib/claim-targets/claim-targets.js` — `repoSlugOf` retry via `runClassified`; slug-failure classification in `run()`
- `plugin/bin/lib/shared-primitives.js` — reused `runClassified` / `isTimeoutError` (no change expected)
- `plugin/skills/flow/claim-targets.md` — exit-code table (exit 2 and exit 4 bullets)
- `tests/bin-lib/claim-targets/claim-targets.test.js` — new timeout, keep-going and ENOENT cases

## Gotchas

- The original report's suggestion (c), running Step 2.8's overlap scan after the claim or limiting its concurrency, is not adopted. `flow/claim-targets.md` already orders the overlap warning "Before claiming" (line 86), so the contention comes from concurrent tool calls, not the documented order. Retry plus correct classification fixes the operator-facing defect without touching the step order.
- `gh repo view` failing with a real auth or 404 error is not a timeout. `isTimeoutError` is deliberately narrow (`shared-primitives.js:160-163`), so those must not be retried or reclassified as transient.
- `/claude-tweaks:dispatch`'s task prompt also invokes this CLI (`plugin/skills/dispatch/task-prompt.md:30`), with `--keep-going` available. Confirm its exit handling treats the new exit-4 slug case like any other transient.
- ASSUMPTION — verify at build: `runClassified` passes the timed-out error's `code`/`killed` through unchanged when wrapping a `spawnSync`-based runner. Confirm with the test's fake runner throwing a real-shaped `{ code: 'ETIMEDOUT' }` error.

## Original request

claim-targets: a gh timeout while resolving the repo slug exits 2 (usage error) instead of the transient-failure exit 4

**Summary:** `bin/claim-targets.js` reports a `gh` ETIMEDOUT during repo-slug resolution as exit 2 ("malformed invocation or missing dependency") and prints the usage text. Its 5 s `gh` timeout is also tight when `/flow`'s own Step 2.8 overlap scan is running `gh` calls at the same time.

**Kind:** Defect

**Affected component:** `bin/claim-targets.js` (`repoSlugOf`), `bin/lib/shared-primitives.js` (`GH_TIMEOUT_MS`), `skills/flow/claim-targets.md` (Step 2.8)

**Repro steps:**
1. On a GitHub Enterprise host with ~280 open issues, run `/claude-tweaks:flow #A,#B,#C` (three records).
2. Step 2.8 runs the file-overlap warning scan (`bin/preflight-records.js` over the open queue) and, in parallel, `bin/claim-targets.js --run-id <id> --targets A,B,C`.
3. While the scan is fetching, `gh repo view --json nameWithOwner` takes 2.3–3.6 s. Under that contention the 5000 ms `GH_TIMEOUT_MS` expires.

**Expected vs. actual:**
Expected: a `gh` timeout is classified as a transient `gh` failure (exit 4 with the "Claim failed (transient)" card), or the slug lookup retries once with backoff.
Actual: `claim-targets: could not resolve repo slug — spawnSync gh ETIMEDOUT`, then the usage text, exit 2. This happened twice in a row and pointed the operator at a malformed invocation. Re-running with `CLAUDE_TWEAKS_GH_TIMEOUT_MS=30000` claimed all three targets on the first try.

Suggested fix: (a) map a slug-resolution spawn error/ETIMEDOUT to exit 4; (b) retry slug resolution once with backoff, or give it a longer timeout than per-call `gh` reads; (c) optionally run Step 2.8's informational overlap scan after the claim, or limit its concurrency.

**Definition:** Clear

**Plugin version:** 6.137.0
