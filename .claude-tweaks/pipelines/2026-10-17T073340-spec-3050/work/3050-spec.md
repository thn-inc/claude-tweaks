# 3050: pr-early-run-lifecycle: Spec summary is never refreshed after build logs a premise reversal

Surface: infra

## Current State

In a `pr-first` run, the draft PR body is composed once at run start by `_shared/pr-early-run-lifecycle.md`'s body template (`plugin/skills/_shared/pr-early-run-lifecycle.md:185`). Its `### Spec summary` is "one-paragraph summary from the materialized spec's Overview section". After that, the PR body changes in two places, both in `plugin/skills/_shared/pr-checklist-refresh.md`:

- the Phase-checklist update (`:20`), which runs at every phase exit;
- the Pre-merge title/description refresh (`:76`). Its step 2 (`:107`) re-runs the phase-checklist update, and its step 4 (`:131-133`) re-reads only the record title.

Neither touches `### Spec summary`.

Build can legitimately change the mechanism the spec described. `build/SKILL.md:122` verifies `ASSUMPTION — verify at build:` markers before planning and logs each outcome to `decisions.md` as `confirmed` or `reversed`. A reversed assumption is folded into the plan as the corrected fact. Spec Step 3 planning can also reverse a premise on its own judgment. Neither path feeds back into the PR's Spec summary, and the reversal entries share no single canonical marker that a later step could key on.

Observed (reporter, plugin 6.137.0, `pr-first` dispatch run): the record specified reading the deployed commit from a health endpoint and refusing when the run's sha is not a descendant of it. Build logged a premise reversal: literal ancestry would refuse every legitimate deploy, so the implementation judged age on the integration branch's line and read the commit from a different source. Build's phase exit added accurate Build notes, but `### Spec summary`, the first thing a merge reviewer reads, still described the original mechanism. A manual review-time read caught it (about 2 minutes, nothing merged stale).

## Deliverables

1. Give build-time premise reversals one canonical `decisions.md` marker: a fixed phrase such as `premise reversed:` followed by the original claim and what replaced it. Apply it in `build/SKILL.md`'s assumption-verification step (`:122`, the `reversed` outcome) and wherever Spec Step 3 records that the plan departs from a spec premise.
2. In `pr-checklist-refresh.md`'s Phase-checklist update, add one step: when this run's `decisions.md` carries at least one `premise reversed:` entry, re-compose the PR body's `### Spec summary` paragraph from the implemented behavior. Prefix it with a one-line note naming each reversed premise (for example `Revised during build: {original claim} → {implemented behavior}`). Write it with the same transport and best-effort posture as the checklist edit. Because the pre-merge refresh re-runs this procedure unconditionally (step 2), the summary is current at merge time without a separate pre-merge step.
3. Keep the rewrite idempotent. A Spec summary that already carries the `Revised during build:` note for every reversal entry is left unchanged.

## Acceptance Criteria

- `build/SKILL.md` names the `premise reversed:` marker for both the assumption-verification `reversed` outcome and a Spec Step 3 premise departure.
- `pr-checklist-refresh.md`'s Phase-checklist update names the Spec-summary rewrite, its trigger (one or more `premise reversed:` entries in this run's `decisions.md`), the `Revised during build:` note, and the idempotency rule.
- With no reversal entry, the Phase-checklist update leaves `### Spec summary` byte-unchanged.
- A failed Spec-summary edit is logged and never blocks the phase exit or the merge, the same posture `pr-checklist-refresh.md:137` gives a stale title or checklist.
- `npm test` passes, including any conformance tests that pin `pr-checklist-refresh.md` or `pr-early-run-lifecycle.md` prose.

## Release Note

Refresh a pull request's spec summary when the build changes a premise, so reviewers never read a description the code no longer matches.

## Technical Approach

Hook the rewrite into the Phase-checklist update rather than adding a new pre-merge-only step. That procedure already runs at build's phase exit, the earliest point a reversal is known, and it re-runs at pre-merge. So one change covers both of the reporter's suggested insertion points. A canonical marker is needed because today's reversal lines are free-form, and a rewrite keyed on prose wording would silently miss entries.

### Key Files

- `plugin/skills/build/SKILL.md` — canonical `premise reversed:` decision-log marker
- `plugin/skills/_shared/pr-checklist-refresh.md` — Spec-summary rewrite step in the Phase-checklist update
- `plugin/skills/_shared/pr-early-run-lifecycle.md` — note on the body template that `### Spec summary` may be rewritten after a reversal

## Gotchas

- The PR body's delimiter handling differs between a `gh` read and an MCP read (`pr-checklist-refresh.md` uses separate marker pairs for the checklist span). The Spec-summary rewrite must locate its span the same transport-aware way, or it will corrupt the body on the MCP path.
- In a multi-spec run sharing one PR, the Spec summary is a single paragraph. Decide in the plan whether reversal notes from several specs append to one note line. Never let one spec's rewrite drop another's note.
- Re-composing "from the implemented behavior" is an agent judgment at phase exit. Keep it to one paragraph, as the template defines, and never invent behavior not visible in the diff.

## Original request

pr-early-run-lifecycle: Spec summary is never refreshed after build logs a premise reversal

**Summary:** The PR-early draft PR's `### Spec summary` is composed once from the record body at run start. Nothing refreshes it after build logs a Spec Step 3 premise reversal, so the PR can describe a mechanism its own diff does not implement.

**Kind:** Gap

**Affected component:** _shared/pr-early-run-lifecycle.md (Spec summary composition) / _shared/pr-checklist-refresh.md (phase-exit update and pre-merge refresh)

**Use case:** In a `pr-first` dispatch run, the record said: read the deployed commit from a health endpoint, then refuse when the run's sha is not a descendant of it. During build, Spec Step 3 logged a premise reversal in `decisions.md`. Literal ancestry would refuse every legitimate deploy, so the implementation judged age on the integration branch's line instead, and read the commit from a different source. Build's phase exit added accurate Build notes to the PR body but left `### Spec summary` as it was. The pre-merge refresh (`pr-checklist-refresh.md` step 4) only re-reads the record title. So the PR's summary, which is the first thing a human merge reviewer reads, contradicted its own code. Only a manual read of the PR body during review caught it.

The pipeline already holds the signal it needs: the Spec Step 3 "premise reversed" decision line. Suggested change: when `decisions.md` carries a Spec Step 3 premise-reversal entry, have build's phase-exit PR update re-compose the `### Spec summary` paragraph from the implemented behaviour, or flag it for rewrite. Alternatively, add that check to the pre-merge refresh, next to the title refresh.

Observed once. Cost was one PR-body read and edit at review exit (about 2 minutes). Nothing was merged with the stale text.
