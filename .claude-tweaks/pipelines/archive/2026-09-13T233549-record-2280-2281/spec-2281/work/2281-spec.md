# 2281: review Step 6.7 and design-wrapper polish route the same audit finding two contradictory ways

Surface: backend

## Overview

`review/code-mode-steps.md`'s Step 6.7 (Late Findings Routing) and `design-wrapper/modes/polish.md`'s Step 5 (suggestion-driven dispatch) both independently consume the same `source: "audit"` findings from the shared cache `docs/plans/YYYY-MM-DD-{feature}-audit.json` (`design-wrapper/modes/review.md`'s Step 5, the cache's sole producer) — Step 6.7 routes each finding by severity under the run's ceiling (low → AUTO, medium/high → STAGED, critical → KEPT-PROMPT), while polish's Step 5 independently applies whatever command each finding's own `suggestion` field names, with no awareness of what review already decided. When both run in the same `/claude-tweaks:flow` (review, then polish, per the pipeline order), polish's blind suggestion-driven dispatch can re-derive and auto-apply a finding review had just staged for a human — bypassing the ceiling entirely.

**Design resolved before shaping (the record's own two-option Open Question):** traced the actual cache mechanism directly. Both Step 6.7 and polish's Step 5 read the exact same JSON structure (`review.md` Step 5's documented cache shape: `{spec, written_at, findings: [{id, source, category, severity, message, suggestion}, ...]}`), and nothing currently writes back to it after review resolves a finding's routing — that's the actual gap, not a missing precedence rule. Option (a) — polish defers to review's routing via a disposition field on the cache entry — is directly buildable on this existing shared structure with no new plumbing. Option (b) — review leaves suggestion-bearing audit findings to polish entirely — is rejected: it would mean a **high-severity** audit finding carrying a `suggestion` never reaches Step 6.7's ceiling-aware human-staging at all, unconditionally auto-applied by polish regardless of severity — the opposite of what Step 6.7 exists to guarantee.

**Complexity:** Low
**Estimated tasks:** 2-3

## Non-Goals

- Any change to Step 6.7's own severity-routing rules (`step3-routing.md`'s AUTO/STAGED/KEPT-PROMPT thresholds) — this spec only adds a write-back of the *outcome*, not a change to how that outcome is decided.
- Any change to `craft-critic` or `critique` finding handling — the disposition field applies only to `source: "audit"` cache entries, the only kind polish's Step 5 three-way table dispatches by `suggestion` at all (`craft-critic` entries are Step 4's context, never Step 5's dispatch key, per `polish.md`'s own three-way consumption table).
- Cross-run or cross-invocation coordination — this only guards the in-flow ordering (review's Step 6.7, then polish's Step 5, within one `/claude-tweaks:flow` run) where both read the same cache file the same run produced.

## Technical Approach

Reuses the cache file both consumers already share rather than inventing new inter-skill plumbing (a lock file, an env var, a separate coordination artifact) — the fix is entirely a read-modify-write on data that already flows through both files. The skip check in `polish.md` is a presence check on the field (any value means "review already handled this"), not a value-based branch, since polish never needs to know *which* terminal status review chose — only that review already decided.

## Gotchas

- The write-back must be a read-modify-write against the existing cache file, never a fresh overwrite — `review.md` Step 5's own cache write already happened earlier in the same run (it's the producer), and Step 6.7's write is a later, additive update to the same file, not a second production pass.
- Scope the disposition field to `source: "audit"` entries only — `craft-critic` entries have no `suggestion`-driven dispatch path in polish's Step 5 to guard against (they're Step 4's context, consumed differently), so writing a disposition onto them would be inert but also potentially confusing; don't do it.
- The ordering guarantee (review's Step 6.7 before polish's Step 5, within one flow run) is what makes this fix sufficient — this spec does not need to solve for review and polish running concurrently or out of order, which the current pipeline structure doesn't produce.

## Original request

**Summary:** An Impeccable `audit` finding can be staged for a human by review Step 6.7 and, minutes later, auto-applied by `design-wrapper polish`'s suggestion-driven dispatch of the same finding's `suggestion` — the two files never say which route wins.

**Kind:** Gap

**Affected component:** skills/review/code-mode-steps.md (Step 6.7 Late Findings Routing) and skills/design-wrapper/modes/polish.md (Step 5 suggestion-driven dispatch)

**Use case:** In a `/claude-tweaks:flow` run, `audit` reported two accessibility findings on a form (a missing `aria-describedby`; two show/hide toggles sharing one accessible name), each carrying `suggestion: harden`. Review Step 6.7 routed them by severity under the run's ceiling — one staged for the Review Console (high), one auto-applied (medium). The flow's polish phase then ran `design-wrapper polish`, whose Step 5 dispatches the `harden` command each cached finding's `suggestion` names — which would re-derive and apply the very finding review had just staged for a human, bypassing the ceiling. The executing agent noticed and had polish honour review's routing (logged as a KEPT-PROMPT-shaped anomaly note), but nothing in either file states the precedence, so the next run may resolve it the other way.

Two viable fixes, no preference stated here: (a) polish's suggestion-driven dispatch skips any cached audit finding review Step 6.7 already routed — the cache entry could carry review's disposition (`applied` / `staged`) and polish dispatches only unrouted ones; or (b) Step 6.7 leaves audit findings that carry a usable `suggestion` to polish and routes only critique/critic findings.

**Definition:** Needed — two directions ((a) polish defers to review's routing via a disposition field on the cache entry; (b) review leaves suggestion-bearing audit findings to polish) with no tradeoff made yet.
