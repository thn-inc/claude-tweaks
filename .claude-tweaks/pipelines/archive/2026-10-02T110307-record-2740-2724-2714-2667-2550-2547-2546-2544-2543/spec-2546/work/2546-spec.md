# 2546: wrap-up: a docs-only standalone run loads ~330 KB of procedure prose; a persisted oversized read doubled the largest file

Surface: infra

## Current State

A standalone `/claude-tweaks:wrap-up` run on a docs-only change (measured at plugin version 6.126.0) read roughly 240 KB of plugin procedure files across 20 reads plus ~93 KB across three skill bodies — 31% to 43% of the session's total tool-result bytes for an 11-turn session producing a 7-insight, 23-row console. One concatenated read of `review-console.md` + `summary-template.md` exceeded the Read tool's size cap, was persisted to disk, and was then read back in full — 46.6 KB, the session's single largest tool result.

The named files remain large today (current byte counts, up from the version measured): `wrap-up/cleanup-procedures-execution.md` 33,868 B, `wrap-up/review-console.md` 30,786 B, `_shared/pr-first-merge.md` 30,804 B, `_shared/ledger-format.md` 29,392 B, `wrap-up/curation-engine.md` 26,376 B, `reflect/full-mode.md` 24,625 B, `_shared/worktree-setup.md` 21,023 B, `wrap-up/review-console-interactive.md` 19,456 B, `wrap-up/console-template.md` 17,652 B, `wrap-up/summary-template.md` 15,328 B — roughly 249 KB across these ten files alone.

`plugin/bin/wrap-up-engine.js`'s `render` verb already supports `--section trace|console` (usage line: `wrap-up-engine.js render --run-dir <dir> [--strict] [--section trace|console] [--start-at n]`, `bin/wrap-up-engine.js:43-44`), backed by `renderTrace`/`renderConsoleSections`/`renderConsoleSectionsMulti` in `bin/lib/wrap-up/engine-render.js` — an established, tested precedent for the engine emitting a scoped excerpt rather than the caller reading a whole file. The `--section` argument is currently validated against exactly two literal values (`bin/wrap-up-engine.js:280`: "`--section` must be 'trace' or 'console'").

## Deliverables

1. Split `plugin/skills/wrap-up/review-console.md`, `plugin/skills/wrap-up/curation-engine.md`, `plugin/skills/wrap-up/cleanup-procedures-execution.md`, and `plugin/skills/_shared/pr-first-merge.md` each into a short operative head (the "read every run" procedure) and a reference appendix (worked examples, historical rationale, signature captures, edge-case prose) — the appendix loaded only on the specific branch that needs it, cited from the head rather than inlined.
2. Extend `bin/wrap-up-engine.js`'s `render` verb to accept a new `--section procedure:<name>` value alongside the existing `trace`/`console` values, emitting the phase-scoped procedure excerpt for `<name>` rather than requiring the calling skill to read the whole source file.
3. Update the four split files' own callers (wherever `wrap-up/SKILL.md` or a sibling procedure currently instructs "read `{file}.md`") to read the operative head unconditionally and the appendix only when the branch it gates is actually taken — following this repo's existing "read X only when Y holds" gating convention already used elsewhere in the skill set.
4. Fix (or confirm already-fixed, at current byte sizes) the size-cap-triggered persisted-read case: a concatenated read of two files exceeding the Read tool's size cap should not be needed once `render --section` can emit the specific procedure excerpt each caller actually needs — verify this specific `review-console.md` + `summary-template.md` combination no longer requires a concatenated read after the split.

## Acceptance Criteria

- Each of the four named files (`review-console.md`, `curation-engine.md`, `cleanup-procedures-execution.md`, `pr-first-merge.md`) has a clearly delimited operative head and reference appendix, with the head alone sufficient for the common-case run (no appendix read needed for the majority of wrap-up runs on a typical change).
- `wrap-up-engine.js render --section procedure:<name>` for each of the split files' registered procedure names emits only that file's operative-head excerpt, verified by a unit test asserting the emitted markdown excludes the appendix content.
- `render --section` still rejects an unrecognized value with the same usage-error behavior it has today (`bin/wrap-up-engine.js:280`), now extended to recognize the `procedure:<name>` prefix form alongside the literal `trace`/`console` values — a malformed or unknown `procedure:` name errors clearly rather than silently returning empty output.
- A standalone `/claude-tweaks:wrap-up` run on a docs-only change (the same class of run the record measured) reads measurably less procedure-file content than before the split — verified qualitatively by reading the updated `wrap-up/SKILL.md` procedure and confirming it now gates each appendix read behind the branch that needs it, matching the existing "read X only when Y holds" convention.
- `npm test` passes in full after the change, including any byte-pin conformance tests on the split files (update the pins to the new head-only sizes where such tests exist).

## Release Note

Reduced how much instruction text a docs-only wrap-up loads.

## Technical Approach

For each of the four target files, identify the operative head — the procedure steps a run executes on every invocation regardless of branch — and the reference appendix — worked examples, historical rationale (`#nnnn` incident narratives), and signature/edge-case prose consulted only when a specific branch or edge case is hit. Split the appendix into a sibling file (naming convention: `{original-name}-appendix.md`, or per whatever sibling-file naming convention `docs/plugin-structure.md`'s per-skill sub-file table already documents for this skill), and replace the inlined appendix content in the head with an explicit citation ("see `{appendix-file}.md` for {topic} — read only when {condition} holds"), following this repo's existing gated-read convention rather than inventing a new one.

Extend `bin/wrap-up-engine.js`'s argument parsing (`bin/wrap-up-engine.js:79` region) to recognize a `procedure:<name>` value for `--section`, and extend `bin/lib/wrap-up/engine-render.js` with a new render function (or generalize the existing `renderConsoleSections` pattern) that reads the registered procedure-head file for `<name>` and emits it, following the same `{ markdown }` return shape the existing render functions use. Register each of the four split files' operative-head content under a stable procedure name in this new mechanism.

Update every call site currently instructing a full-file read of one of the four target files (search `wrap-up/SKILL.md` and its sibling procedure files for each filename) to instead invoke `render --section procedure:<name>` for the head, and gate the corresponding appendix file behind whatever specific branch condition already exists in that call site's own prose.

## Gotchas

- Splitting a file changes what a byte-pin conformance test measures (per `skill-prose-conformance-tests`'s byte-pin convention) — any existing test pinning one of the four target files' size or content needs its pin updated to the new head-only shape, not left asserting against content that moved to the appendix.
- The appendix files still ship with the plugin and still count toward total plugin size — this change reduces per-run *read* volume, not total shipped content; don't conflate the two when reporting the fix's effect.
- `render --section procedure:<name>` is a new, permanent CLI surface — per this repo's expand-contract discipline for shipped skill contracts, once a skill's prose depends on this exact flag shape, changing it later is a breaking change to a consumer (the installed build reading this repo's own committed config with older code) and needs the same migration discipline as any other shipped contract change.
- The observed 46.6 KB persisted-and-reread case was specifically a *concatenated* read of two files exceeding the size cap — confirm the fix actually eliminates the need for that specific concatenation (both files being split, or the calling procedure no longer needing both in one turn) rather than just shrinking each file individually while the caller still reads both together.
- The measured byte counts in this record's Current State are already stale relative to the record's own filed measurement (plugin version 6.126.0 vs. the current build) — re-measure actual read volume after the split lands, rather than assuming the filed percentages still hold exactly.
