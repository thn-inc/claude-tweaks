# 2714: SubagentStop hook flags a dispatched agent's own interim progress-update replies as contract violations

Surface: infra

# Reflect — staged finding 1

**Category:** tangential

## Origin

refs #2563 (reflect full-mode, Friction lens, this run)

## Current State

`bin/lib/hooks/subagent-stop.js` logs a `contract-violation` event whenever a dispatched agent's reply does not end with the canonical `STATUS: {WORD}` line as its last non-empty line. This run observed 5 such events, every one logged against this dispatched agent's own **interim progress-update replies** sent between async `Agent`-tool notifications while 8 nested review-lens agents (and later, one code-simplifier agent) were completing — e.g. "2 of 8 back. Lens 3b-b (Security) surfaced two HIGH findings...". None of these replies claimed to be a final reply; each one explicitly stated more work was pending, and the dispatch's actual final reply (this run's own eventual STATUS line) does conform. `skills/reflect/full-mode.md`'s own Friction-lens text already anticipates the hook can over-report and names one carve-out ("a dispatch declaring its own first-line contract") — that carve-out doesn't cover this shape: a dispatched agent that must itself fan out to nested async work and yield control across multiple turns before its own final reply, per the `Agent` tool's documented async-notification mechanism (`_shared/subagent-output-contract.md`'s dispatch-facing sections). Every such interim turn currently reads as a false-positive contract violation, and the false-positive count scales with how many nested async agents a dispatch fans out to (5 events from 9 nested dispatches on this run alone).

The detector already has one related filter: `isAsyncWaitSignal`/`asyncWaitCheckpoint` in `subagent-stop.js` suppresses logging when the *immediately preceding* transcript entry is itself an async signal (a task-notification, or a tool result flagged `isAsync: true`) — reply text reacting directly to "a background dispatch just launched or reported in" (#2041). The gap this record describes is narrower: an interim reply composed after the agent has already done other work following that signal (dispatching further nested agents, reading their output) no longer has an async signal as its immediately preceding entry, so the existing filter doesn't catch it even though the reply is still legitimately mid-dispatch, not a final answer.

## Deliverables

1. `bin/lib/hooks/subagent-stop.js`'s contract-violation detection distinguishes a legitimate interim, mid-dispatch reply (more nested async work still pending) from an actual final-reply contract breach — via a lightweight marker convention, an explicit interim-status vocabulary word, or equivalent — so a dispatch that fans out to nested async `Agent` calls does not accumulate one false-positive `contract-violation` event per interim turn.
2. `skills/reflect/full-mode.md`'s Friction-lens carve-out list is updated to name this case explicitly (or superseded once the detector itself handles it), so a future reflect pass does not need to re-derive the same "these were never real violations" judgment call from scratch.

## Acceptance Criteria

1. A dispatched agent whose session sends N interim replies (each explicitly stating pending nested work) before its real final `STATUS: {WORD}` reply produces zero `contract-violation` events for those N interim replies.
2. A dispatched agent that genuinely ends its final reply without a conformant `STATUS: {WORD}` line still produces exactly one `contract-violation` event — the fix narrows false positives without weakening real detection.
3. `friction-events.js`'s own Membership-rule documentation (`skills/reflect/full-mode.md`) reflects whichever mechanism resolves this — either the detector no longer over-reports this shape, or the carve-out list explicitly names it.

## Release Note

Stopped subagents' progress updates from being flagged as contract violations.

## Technical Approach

Extend the existing `isAsyncWaitSignal`/`asyncWaitCheckpoint` machinery in `bin/lib/hooks/subagent-stop.js` (confirmed present) rather than adding a parallel detection path: today it only suppresses a reply whose *immediately preceding* transcript entry is an async signal, which misses an interim reply composed after intervening tool calls (e.g. dispatching further nested agents). The most direct extension is a marker convention the dispatched agent's own interim replies can carry (an explicit interim-status word, distinct from the terminal `STATUS: {WORD}` vocabulary, that this detector recognizes as "more async work pending, do not grade this as a final reply") — read alongside `_shared/subagent-output-contract.md`'s dispatch-facing sections, since that file and this detector need to agree on the same convention. Whichever mechanism is chosen, update `classifyViolationVariant`'s call site (or add a sibling check before it) so a recognized interim marker returns `{}` (no log) the same way the existing `asyncWaitCheckpoint`/lenient-compliance branches do, and update `skills/reflect/full-mode.md`'s Friction-lens carve-out list to either name the new marker convention or note the detector no longer over-reports this shape.

### Key Files

- `plugin/bin/lib/hooks/subagent-stop.js` — the `contract-violation` detection logic, specifically the `isAsyncWaitSignal`/`asyncWaitCheckpoint` filter this extends
- `plugin/skills/_shared/subagent-output-contract.md` — the dispatch-facing contract that needs to agree with the detector on whatever interim-reply convention is chosen
- `plugin/skills/reflect/full-mode.md` — the Friction-lens carve-out list this record's Deliverable 2 updates

## Gotchas

- This is a detection/logging gap, not a behavioral bug in the dispatched agents themselves — nothing about the reviewed record's own code is at fault. Do not conflate with `contract-violation` events that ARE real (a dispatch whose actual final reply lacks the status line).
- `_shared/subagent-output-contract.md`'s dispatch-facing sections and the `Agent` tool's own async-notification documentation are the two places that would need to agree on whatever marker/vocabulary convention is chosen.
- The existing `isAsyncWaitSignal` filter already covers the narrower case (a reply immediately reacting to an async signal) — verify at build time that any new marker convention composes with that existing filter rather than duplicating or bypassing it.
