# 6051: Settle plan-review detail questions in code and ask only design-level, hard-to-undo or contradictory ones

Surface: infra
**Related:** #5292, #5053
Risk-flags: none

## Overview

Build's plan review (`plugin/skills/build/plan-review.md`, Common Step 1.6) sends a spec gap to the human whenever settling it would alter an Acceptance Criterion or an observable contract, or has two defensible readings. Almost every low-level detail question meets that test (#4265: which `error` string a release returns; #4786: which file holds a one-sentence pointer), and #5292 measured 271 plan-review questions over 157 of 714 runs. The maintainer decided on 2026-11-21 that human planning time goes only to design-level and hard-to-undo questions; everything else the agent settles, writes down, and shows at acceptance.

This record adds that rule as one shared file and a policy value, and makes build-time plan review route by it. It is the base every other record of the plan-with-spec design builds on.

**Complexity:** Medium
**Estimated tasks:** 5-7

## Deliverables

1. **Shared rule** `plugin/skills/_shared/planning-decisions.md`: the three asked classes and the settled path.
   - (a) design-level: settling it changes what the record or its design doc says the work is for, who it serves, its shape, or a goal, non-goal or anti-goal.
   - (b) hard to undo: the question falls in a risk category the record keeps in `Risk-flags:`. When it plainly falls in a category the record does not flag, the flag is added first through `bin/risk-flags.js` (add, never drop), the question is asked, and the plan owes that flag's Check G proof.
   - (c) contradiction: no reading keeps every Acceptance Criterion and recorded decision intact.
   - Every other question is settled: among readings that keep every AC and recorded decision, take the one closer to stated intent (the criterion-as-written reading when the row came from a criterion change).
   - Line forms: `Settled at planning: {finding} — chose {reading}; not {other reading}` and `Decided by the user at planning: …`, under an additive `## Planning Decisions` section that never edits an existing criterion's line.
   - Asking: one `AskUserQuestion` per question set (max four per call), recommended reading first and marked Recommended, then the other reading, then `Stop the build` (build) or `Leave for later` (specify).
2. **Policy value** `planning-decisions: ask-all | asked-classes`, default `ask-all` (today). Name settled with `.claude/skills/policy-key-addition`.
3. **Build-time routing** in `plan-review.md` under `asked-classes`: settled rows go through the intent-resolvable sequence into the worktree's `work/{n}-spec.md` under `## Planning Decisions` (replacing `## Plan Review Clarifications`) plus the record comment, one `AUTO` log line per settled row. The live record body is never edited. The converged-round rule and its `Settled by plan review after an answered round:` lines retire under `asked-classes`; under `ask-all` everything stays as today.
4. **Narrowed HARD-GATE**: under `asked-classes`, only (a), (b) and (c) rows reach `plan-review-needs-human`. `auto-mode-contract.md`'s row and every consumer that restates the gate's trigger say so.
5. **Tests**: extend the two conformance suites (or one sibling suite of the same size) to pin the three classes, the line forms, and the `ask-all` default.
6. **Classifier and doubt rule.** The plan reviewer's reply row is classified by the build's plan review against `_shared/planning-decisions.md`. Class (b) is bounded to the declared categories (the four built-ins plus policy `risk-categories`); a question that does not plainly fall in one is settled, never asked. The shared file carries two worked examples per side: #4265 and #4786 settled, a migration question and an auth question asked.
7. **Tie-break.** When two readings keep every Acceptance Criterion and recorded decision intact and sit equally close to the stated intent (the record body and its design doc), take the one that changes fewer observable contracts.
8. **Output forms.** The record comment carries the `Settled at planning:` line verbatim. The `AUTO` line reuses the step label that `plan-review.md`'s existing `AUTO` lines carry. Under `ask-all` the `## Plan Review Clarifications` heading and everything around it stay exactly as today.
9. **Answered round.** Under `asked-classes` a row an answered round returns is settled with a `Decided by the user at planning:` line and never asked again.
10. **Consumer audit.** `git grep -F` for `plan-review-needs-human` and for `Plan Review Clarifications` (excluding `.claude-tweaks/pipelines`, `docs/superpowers/plans` and `docs/plans/*-ledger.md`); every consumer that restates the gate's trigger or reads the heading is updated or listed in Key Files with the reason it stays.
11. **Policy key rulings.** Run `.claude/skills/policy-key-addition`: decide `policyOnly` versus `policySourceExcluded`, and the Manifesto row. Verify how a build older than the key treats an unknown `planning-decisions` value before this repository's `policy.yml` opts in (expand-contract).

## Acceptance Criteria

1. With `planning-decisions` unset, every plan-review path, prompt and log line is byte-identical to today's (a test compares the default branch's text).
2. With `asked-classes`, a needs-human row outside (a)/(b)/(c) produces a `Settled at planning:` line in the worktree spec, an `AUTO` decision line and a record comment, and no `AskUserQuestion`, no question comment and no `failed:plan-review-needs-human`.
3. With `asked-classes`, a row in (a), (b) or (c) reaches the HARD-GATE in every posture exactly as today, and its question offers the recommended reading first.
4. A row naming an unflagged risk category adds the flag via `bin/risk-flags.js` before asking; a test pins the add-never-drop rule.
5. `_shared/planning-decisions.md` is the only file stating the three classes; plan-review.md cites it.
6. `npm test` passes.
7. Settling holds in every posture (`auto`, `confirm`, `interactive`, `hybrid`): a row outside (a), (b) and (c) never reaches `AskUserQuestion` in any of them.
8. A question outside the four built-in categories and the policy `risk-categories` is settled; a test pins the doubt rule with one borderline row.
9. The `ask-all` byte-identity test compares against a frozen fixture of today's `plan-review.md` default-branch text, so adding the pointer and the new sub-file does not change it.

## Release Note

Plan review can stop asking about low-level details: with `planning-decisions: asked-classes` it settles them itself, records each call, and asks only design-level, hard-to-undo or contradictory questions.

## Plan Review Clarifications

- Decided by the user at plan review: an asked row's recommended reading (Deliverable 1's "recommended reading first and marked Recommended") is the reading `## Settled path` would pick — the one closer to stated intent, the criterion-as-written reading on a criterion-change row; for a class (c) row, where that rule cannot choose, it is the reviewer's Reading A. Not taken: always the reviewer's Reading A as the row gives it.

## Build Deviations (Beneficial)

- Deliverable 1(b)'s flag on a blocking path (a dispatched call or `parallel`-wave member): adding it to the worktree spec alone is lost when the resumed build re-materializes from the record, so the implementing plan would owe no Check G proof. As built, the question comment names `{slug}` and asks the answerer to add it to the record body's `Risk-flags:` line with their `**Decision**`, and the answered round re-runs `risk-flags.js add` (without asking) for a row that plainly falls in an unflagged declared category (`build/plan-review-asked-classes.md` steps 2 and 5). The live record body is still never edited by the build.
