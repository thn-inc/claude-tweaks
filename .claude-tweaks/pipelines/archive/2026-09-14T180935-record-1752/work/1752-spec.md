# 1752: dispatch/next-ranking.md: unify ad hoc per-reason exclusion-list files into one mechanism

Surface: infra

## Current State
`/claude-tweaks:dispatch` keeps four session-scoped exclusion files, each with its own shape, producer, reader, and report:

| File | Shape | Written by | Read by |
|---|---|---|---|
| `dispatch-blocked-excluded.json` | `{number, blockedBy: number[]}[]` | `queue-pull-script.md` (removed from the pool) | `blocked-exclusion-report.md` |
| `dispatch-open-pr-excluded.json` | `{number, pr}[]` | `queue-pull-script.md` (removed from the pool) | `open-pr-exclusion-report.md`; SKILL.md's `#N` / `#N,#M` forms (reason lookup, #1973) |
| `dispatch-oversized-excluded.json` | `{records: number[], size, threshold}[]` | `queue-pull-script.md` (stays in the pool) | `next-ranking.md` (excludes), `oversized-group-report.md` |
| `dispatch-firing-excluded.json` | `number[]` | SKILL.md's Loop per `firing-exclusion.md` (append per iteration) | `next-ranking.md` (excludes) |

Every one is read with an inline `fs.existsSync(p) ? require(p) : []` and filtered with hand-written `Set` logic inside a `node -e` block embedded in the skill's markdown; `next-ranking.md`'s bash block alone carries two different key derivations (`keyOf(g)` for oversized record-sets, member membership for firing numbers). The next exclusion reason (a residue class, a maintainer deny-list, a freshness veto) copies the pattern a fifth time or forces this refactor later. No `bin/` module owns the concept: `bin/lib/dispatch/` holds `artifact-verdict.js`, `ceremony-derive.js`, `queue-order.js` only.

## Deliverables
- [ ] `bin/lib/dispatch/exclusions.js`: one module owning the shape and the file — `readExclusions(path)` → `{ reason, records: number[], detail }[]` (absent/unreadable → `[]`), `appendExclusion(path, entry)`, `excludedNumbers(entries, reasons)` → `Set<number>`, and `groupIsExcluded(group, entries, reasons)` (true when any member is in the set, the semantics `firing-exclusion.md` and `next-ranking.md` already use), with unit tests in `tests/bin-lib/dispatch/exclusions.test.js`.
- [ ] One session-scoped `dispatch-exclusions.json` replacing the four files: `queue-pull-script.md` writes `blocked` (`detail: { blockedBy }`), `open-pr` (`detail: { pr }`), and `oversized` (`detail: { size, threshold }`) entries through `appendExclusion` after truncating the file at the start of its run; SKILL.md's Loop appends `firing` entries through the same call per `firing-exclusion.md`'s rule (unchanged trigger conditions).
- [ ] `next-ranking.md`'s script filters with `groupIsExcluded(g, entries, ['oversized', 'firing'])` — one derivation, no `keyOf` vs member split; the `#N` / `#N,#M` reason lookup reads `open-pr` entries from the same file.
- [ ] The three report files and `blocked-exclusion-report.md` read the one file filtered by reason, rendering byte-identical lines to today; `firing-exclusion.md` and `dispatch/SKILL.md` name the new file and the reason vocabulary.
- [ ] `tests/dispatch-firing-exclusion.test.js` (which extracts and executes `next-ranking.md`'s bash block) updated to seed `dispatch-exclusions.json` entries instead of two files; `tests/session-tmp-root-migration.test.js` and `tests/node-e-snippet-syntax.test.js` stay green (they scan the same blocks).
- [ ] `docs/plugin-structure.md` gains the new module wherever it lists `bin/lib/{name}/` modules (it names the directory convention, not each file, today — add a line only if a per-module list exists); `_shared/session-tmp-root.md` enumerates no dispatch file names, so it needs no edit.

## Acceptance Criteria
1. Exactly one session-scoped exclusion file is written or read anywhere under `plugin/skills/dispatch/`; `grep -rn "excluded.json" plugin/skills` returns no match.
2. All four reasons survive with their current pool semantics: `blocked` and `open-pr` still remove candidates from `dispatch-groups.json` in the queue pull; `oversized` and `firing` still leave groups in the pool and are excluded only by the ranking script.
3. Each report renders the same line text as before for the same inputs; the `#N` form still names the linked PR for an `open-pr` exclusion.
4. `tests/dispatch-firing-exclusion.test.js`'s four scenarios (absent file, one excluded group, all excluded → `null`, bundle-member match) pass against the new shape; `exclusions.js` has its own unit coverage; `npm test` is green.
5. Adding a fifth reason requires one `appendExclusion` call site and one report, no new file or filter logic — demonstrated by a test that seeds an unknown reason and shows the ranking ignores it while `readExclusions` returns it.

## Technical Approach
Move the concept into code and leave the skills as callers: the markdown scripts already shell out to `node -e` with `${CLAUDE_PLUGIN_ROOT}/bin/lib/...` requires, so `require('${CLAUDE_PLUGIN_ROOT}/bin/lib/dispatch/exclusions.js')` inside those blocks is the same pattern `session-tmp.js` is loaded with today. One file rather than one-per-reason: the readers already differ only by reason, and a single array with a `reason` field is what makes the fifth reason a one-line append. Keep the pool split (`blocked`/`open-pr` removed at queue pull; `oversized`/`firing` filtered at ranking) exactly as is — the record is about the file mechanism, not the exclusion semantics.

## Gotchas
- `dispatch-blocked-excluded-body.json` is an intermediate of the body-text blocker pass, not an exclusion list; leave it alone.
- The reports' "drain + zero-eligible silence" exception keys on report content, not file presence; reading one file for all reasons must not change when a report is omitted.
- `tests/dispatch-firing-exclusion.test.js` extracts the bash block by a fenced-code regex; keep the block's fence and the `eval "$(node -e …)"` prologue shape so the extraction still matches.
- Truncate-then-append in the queue pull must happen once at the start of `queue-pull-script.md`, before the blocked pass — the firing entries appended by the Loop live in the same file and must survive the per-iteration re-pull, so the truncation drops only non-`firing` entries (`readExclusions` → filter → rewrite), never the whole file.
