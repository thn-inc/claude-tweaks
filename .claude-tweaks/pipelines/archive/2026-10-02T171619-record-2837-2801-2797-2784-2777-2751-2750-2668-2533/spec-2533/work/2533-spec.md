# 2533: dispatch task-prompt's foreground-execution warning doesn't distinguish shell background from Agent-tool async notification

Surface: infra

## Current State

`plugin/skills/dispatch/task-prompt.md` carries the identical "Foreground execution (required)" paragraph verbatim in two places (lines 74-78 and 176-180, one per two-call task-prompt template): "run `npm test` and every other long-running command in the foreground of this turn ... never with `run_in_background`. Never end this turn waiting on a background test run, fix-round, or child agent's completion notification; a dispatched agent that yields this way is never re-woken and the run stalls silently (#1965)."

This wording does not distinguish shell-level `run_in_background` (a genuine headless-stall risk — a dispatched agent's own top-level turn ending with nothing pending to resume it) from the `Agent` tool's own built-in async notification mechanism, which `plugin/skills/_shared/dispatch-waiting.md` documents as the plugin's normal, relied-upon operating mode: "The task-notification that arrives when a dispatched agent finishes is the **primary resume signal** — it is what actually wakes the dispatcher... after dispatching a wave of parallel agents, let their completion notifications drive the next turn." `plugin/skills/review/step3-lens-dispatch.md`'s Low-tier single-read dispatch (line 48) explicitly dispatches one `Agent` per in-scope lens (3b, 3c) at `low` tier and depends on this exact notification mechanism to resume review Step 3.

During a `review,polish,wrap-up` dispatch call (record #2436), Step 3's low-tier single-read lens dispatch launched two async `Agent` tool calls (lens 3b and 3c). Reading task-prompt.md's foreground-execution clause literally as also covering the `Agent` tool's built-in notification (not just shell `run_in_background`), the reviewing session performed the same 3b/3c analysis synchronously in the main thread as a hedge — duplicating work Step 3's own contract already handles asynchronously. Both dispatched agents then returned their completion notifications reliably, within the same turn sequence, moments later — the hedge was unnecessary in this instance, but the ambiguity that caused it is structural, not a one-off misreading.

## Deliverables

1. Rewrite `task-prompt.md`'s "Foreground execution (required)" paragraph (both occurrences, lines 74-78 and 176-180) to explicitly scope the "never end this turn waiting on a ... child agent's completion notification" clause to the case it actually targets: THIS dispatched session's own top-level turn ending with nothing else pending to resume it (the genuine stall risk `#1965` names).
2. Explicitly distinguish that stall risk from an in-turn `Agent`-tool dispatch (a lens-dispatch fan-out, a reproduction pair) whose completion notification the harness is expected to deliver back into the same ongoing turn sequence — cite `_shared/dispatch-waiting.md`'s existing convention rather than restating it, per this repo's degrade-clause/convention-citation discipline (`plan-authoring-checks.md`'s Degrade-clause convention check applies the same discipline to this kind of citation).
3. Confirm the clarified wording does not weaken the original stall-risk warning for genuine shell `run_in_background` usage — the fix narrows the clause's scope, it does not remove the warning.

## Acceptance Criteria

- `task-prompt.md`'s foreground-execution paragraph, in both occurrences, no longer reads as prohibiting an in-turn `Agent`-tool dispatch whose notification is expected to resume the same turn sequence (e.g. `step3-lens-dispatch.md`'s low-tier single-read `Agent` dispatch).
- The clarified wording still unambiguously prohibits shell `run_in_background` for `npm test` and other long-running commands, and still warns against a dispatched session ending its own top-level turn with nothing pending (the `#1965` stall risk) — no regression on the original warning's coverage.
- The clarified wording cites `_shared/dispatch-waiting.md`'s existing "primary resume signal" convention rather than re-deriving or restating it inline.
- A future headless `/flow review,polish,wrap-up` dispatch call can launch Step 3's lens-dispatch `Agent` calls (per `step3-lens-dispatch.md`'s Low-tier single-read dispatch) without a reviewing session needing to guess whether doing so risks a silent stall.
- Both occurrences of the paragraph in `task-prompt.md` stay byte-identical to each other after the edit (matching the file's existing convention of two verbatim copies, one per call template) — a fix landed in only one occurrence would leave the ambiguity live in the other call's prompt.
- `npm test` passes in full after the change (including any conformance test pinning this paragraph's text, if one exists).
