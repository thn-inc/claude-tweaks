# 2777: specify: red-team should demand adversarial inputs when a spec prescribes a path/URI/identity guard

Surface: infra

## Current State

When `/claude-tweaks:specify` shapes a record whose Deliverables prescribe the algorithm of a security-shaped check keyed on a path, URI, hostname or identity string, its red-team (`plugin/skills/specify/red-team.md`) only probes the substring-spoof case; the resulting spec's test list is what every later review compares the code against, so dot-segment and mount-prefix bypasses reach the last review lens before anything probes them.

**Real incident this record generalizes from:** a record shaped by `/claude-tweaks:specify` prescribed a guard — "allow the feature only when the storage root is a sandbox root — the URI path contains a `sandbox` segment; otherwise refuse" — together with its test list. The red-team probed "the word `sandbox` inside the storage-account name" and nothing else. The build's task review and the whole-branch review both validated the implementation against that text (12 root shapes probed, none containing a dot segment) and passed it. Only the Security lens of `/claude-tweaks:review`, the last gate, found that `<scheme>://<account>/sandbox/../artifacts` passed the guard while the storage layer normalizes it to the production-equivalent root, and that a mounted-storage prefix was treated as a local path.

Why it is systemic (reflect's near-miss chain walk, causal: systemic):
1. The spec prescribed the guard's algorithm and its test cases; every later reviewer compared the code to that text.
2. The plan carried the spec's test list verbatim, so no adversarial case existed to fail.
3. The first two review layers compare code to spec; only the lens pass probes inputs — so a security-shaped check receives adversarial input for the first time at the last gate.

Cost: one extra fix dispatch plus one full re-verification run (about eight minutes) after two reviews had already approved the guard; at a `low` review tier the lens would not have run and the bypass would have shipped.

## Deliverables

Extend `/claude-tweaks:specify`'s red-team (`red-team.md`) so that, when an Acceptance Criterion or Deliverable prescribes a decision keyed on a path, URI, hostname, or identity string, the red-team requires the AC to enumerate adversarial inputs before the spec is marked shaped: dot segments (`.`/`..`) before and after normalization, mount/scheme variants, uppercase schemes, percent-encoding, trailing slashes, and the "substring in the wrong component" case it already covers.

## Acceptance Criteria

- `red-team.md` documents the new detection trigger (an AC/Deliverable prescribing a path/URI/hostname/identity-keyed decision) and the adversarial-input checklist it now requires (dot segments pre/post normalization, mount/scheme variants, uppercase schemes, percent-encoding, trailing slashes, substring-in-wrong-component).
- Re-shaping a record matching the incident's own guard shape (a path/URI containment check) via `/claude-tweaks:specify` produces an Acceptance Criteria section enumerating the new adversarial cases, not just the substring-spoof case it already covered.
- `plugin/skills/review/step3-lens-dispatch.md`'s Security lens (`3b`) and the new red-team checklist are checked for consistency — pulling from the same probe list, per the filed suggestion, so the shaping gate and the last review lens probe the same adversarial set rather than diverging.

## Release Note

Made the spec red-team demand adversarial inputs whenever a spec guards on a path, URL, or identity.

## Technical Approach

Add a detection step to `red-team.md`'s existing procedure: scan the composed Acceptance Criteria/Deliverables text for path/URI/hostname/identity-guard language (containment checks, prefix/segment matching, "must be under X root" phrasing) — the same class of language the incident's own guard used. When detected, require the AC to name the adversarial-input checklist above before the spec can be marked shaped, mirroring how the existing substring-spoof case is already required. Cross-reference `step3-lens-dispatch.md`'s Security lens (3b) to pull from the same checklist where practical, so the two checks stay in sync rather than drifting into two separately-maintained adversarial-input lists.

### Key Files

- `plugin/skills/specify/red-team.md` — the red-team procedure to extend with the new detection trigger and checklist
- `plugin/skills/review/step3-lens-dispatch.md` — Security lens (3b), to cross-reference for probe-list consistency

## Gotchas

- The detection trigger (path/URI/hostname/identity-guard language) needs to be specific enough to fire on the real pattern (containment/prefix/segment checks) without false-triggering on every record that merely mentions a file path — over-triggering would add checklist ceremony to unrelated records and train users to ignore it (the same anti-pattern `challenge/SKILL.md`'s framing-check explicitly warns against for its own signal).
- The adversarial-input checklist (dot segments, mount/scheme variants, percent-encoding, etc.) should stay a single source of truth shared between this red-team check and the review Security lens, not two independently-maintained copies that drift apart over time — Acceptance Criteria 3 above exists specifically to catch that drift at build time, not just at this record's own merge.
