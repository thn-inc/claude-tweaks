# 2750: Add an ownability/maintainability check to the review lens

Surface: infra

## Current State

`/claude-tweaks:review`'s lens system (`plugin/skills/review/step3-lens-dispatch.md`, `### 3a`-`### 3f`) currently dispatches six lenses — Convention Compliance, Security, Error Handling, Performance, Architecture, Test Quality — none of which asks whether a human on-call owner would understand and accept responsibility for the code under review. `/claude-tweaks:code-health`'s own checklist (`plugin/skills/code-health/SKILL.md`) is similarly scoped to correctness/debt classes, not comprehension risk. As a result, code that passes every existing lens — tests green, conventions followed, no security/perf/architecture flags — can still be the kind of output a teammate would hesitate to own: dense, unexplained, or relying on implicit context no PR description states. The filed source (a senior engineer's account of deleting 3,000 lines of working, tested AI-generated code because the team couldn't explain it) is an anecdote illustrating the gap, not a technology choice to justify.

## Deliverables

- A new lens, `### 3g: Ownability`, added to `plugin/skills/review/step3-lens-dispatch.md`'s Lens definitions section (3a-3f), following the existing lenses' own format (scope, what it flags, output shape).
- A short rubric embedded in that lens definition: the concrete question a reviewer (human or agent) applies — could an on-call engineer debug this at 3am without the PR description open? — expressed as checkable signals (unexplained non-obvious control flow, a mechanism with no comment or spec context explaining *why*, a diff whose Deliverables/AC don't mention why this shape was chosen), not a vague restatement of the question itself.
- The new lens wired into `code-mode-steps.md`'s Step 3 lens dispatch/debate/routing exactly as 3a-3f already are, so it participates in the same fan-out, debate, and Step 3 Routing consolidation as the existing six.

## Acceptance Criteria

- `plugin/skills/review/step3-lens-dispatch.md` documents lens `3g: Ownability` in the same structural shape as `3a`-`3f` (a scope line, concrete flag signals, and an output/finding shape consistent with the other lenses).
- `code-mode-steps.md`'s Step 3 lens list includes 3g alongside 3a-3f (dispatch, debate-and-refutation, and Step 3 Routing all iterate the full lens set, not a hardcoded 3a-3f range).
- Running the new lens against a sample diff that is dense/unexplained but otherwise clean (passes tests, follows conventions, no security/perf/architecture issues) produces at least one ownability finding — verified by hand-testing the lens against one such diff before merge.
- The rubric is stated as concrete signals a reviewer checks, not as an open-ended restatement of "would someone understand this."

## Release Note

Added a review lens that checks whether new code is easy for the team to own and maintain.

## Technical Approach

Add lens 3g following the existing 3a-3f pattern in `step3-lens-dispatch.md`: a scope description (what content class the lens reads — the diff plus the record's Deliverables/Technical Approach for stated rationale), the flag signals (control flow with no explaining comment or spec cross-reference; a diff whose composed record gives no reason for the specific mechanism chosen; dense multi-concern functions with no narrative), and the finding output shape matching 3a-3f's existing convention. Update `code-mode-steps.md`'s Step 3 lens enumeration and `step3-debate-and-refutation.md`/`step3-routing.md` wherever they name the lens set explicitly (both files iterate lenses generically per a quick read of their current content, so this may be a no-op beyond the two files above — confirm before assuming a third edit site).

### Key Files

- `plugin/skills/review/step3-lens-dispatch.md` — add `### 3g: Ownability` to the Lens definitions section (after 3f)
- `plugin/skills/review/code-mode-steps.md` — extend Step 3's lens fan-out to include 3g

## Gotchas

- The rubric must resolve to concrete, checkable signals — a lens whose only instruction is "would a teammate understand this?" produces inconsistent findings across runs. Anchor it the way 3a-3f anchor their own scope (specific content patterns to flag), not a restated question.
- This lens necessarily overlaps in spirit with Architecture (3e) and Convention Compliance (3a) — scope it narrowly to *comprehension/ownership* risk (would a maintainer accept responsibility for this) rather than duplicating those lenses' existing structural/convention checks, or Step 3 Routing's consolidation will just collapse near-duplicate findings.
- "Flags at least one comprehension risk when present" (AC 3) needs a concrete sample diff to hand-test against before merge — pick or construct one that is deliberately dense/unexplained-but-clean so the AC is actually falsifiable, not asserted.
