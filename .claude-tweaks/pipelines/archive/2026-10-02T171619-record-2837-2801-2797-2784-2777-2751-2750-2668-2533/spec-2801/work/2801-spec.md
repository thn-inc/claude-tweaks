# 2801: Evaluate the Haiku+Opus "Advisor Pattern" for cost/quality

Surface: infra

## Current State

A named "Advisor Pattern" (a cheap/fast model executes, a stronger model advises/reviews) is reported externally to beat a mid-tier model alone at lower cost. claude-tweaks currently has no documented practice of this shape — model selection today is either a single model for the whole task, or the existing Subagent Contract's static Fast/Standard/Capable profile per dispatch, not a two-model advise/execute split within one task.

## Deliverables

Evaluate the Advisor Pattern against one representative claude-tweaks task (a build, a review, or a similarly-scoped unit of work) by running it once under the pattern (a fast/cheap model executing, a stronger model reviewing/advising) and once under the current default approach for the same task, then compare cost and output quality between the two runs.

## Acceptance Criteria

- One sample task is run both ways (Advisor Pattern vs. current default), with actual token/cost figures and a quality comparison (not just cost) reported for both.
- A recommendation is recorded: adopt the pattern for some class of claude-tweaks work (naming which), or don't, with the comparison data as the stated justification either way.
- If adopted, the recommendation states specifically which of claude-tweaks' own workflows (build, review, dispatch, etc.) it would apply to — not a blanket claim it should replace all current model selection.

## Release Note

No user-visible change: measured whether pairing a fast executing model with a stronger advising model improves cost and quality.

## Technical Approach

Pick one bounded, representative task (small enough to run twice affordably, substantial enough that quality differences would actually show) and execute it under both configurations, capturing real cost and quality data from each run rather than estimating. Compare against the Subagent Contract's existing static Fast/Standard/Capable guidance to determine whether the Advisor Pattern is complementary (a specific dispatch shape within that existing framework) or a genuinely separate mechanism.

### Key Files

- `plugin/skills/_shared/subagent-output-contract.md` — the existing model-selection guidance to compare the pattern against

## Gotchas

- A single sample task's comparison is a screening signal, not a proof — state the recommendation's confidence level accordingly rather than over-generalizing from one data point.
- Cost and quality can trade off in either direction depending on task shape — don't assume the externally-reported result (Advisor Pattern beats mid-tier alone) transfers unchanged to claude-tweaks' own task shapes without actually measuring it here, which is exactly what this record's Deliverable requires.

## Original request

Evaluate the Haiku+Opus "Advisor Pattern" for cost/quality

Context: A named 'Advisor Pattern' (cheap model executes, stronger model advises/reviews) reportedly beats a mid-tier model alone at lower cost.

Scope: Evaluate the pattern against a sample claude-tweaks task and compare cost/quality to the current default.

## Evaluation Outcome

### Sample task

A single bounded, representative implementation task, run three times via the Agent tool: implement a CommonJS `formatByteSize(bytes)` utility (binary 1024-unit human-readable byte formatting, with `TypeError` on negative/non-finite input) plus a `node --test` suite, in an isolated scratch directory per dispatch. The same task spec (byte-for-byte identical requirements) was given to each dispatch independently — no agent saw another's output except the advisor, by design.

- **Advisor Pattern condition:** `Fast` (haiku) executed the task from scratch, self-tested, and reported done. `Capable` (opus) then reviewed the Fast agent's two files (given inline, not via shared filesystem context) against the same spec, with instructions to hand-trace boundary cases and decide ACCEPT AS-IS vs FIX REQUIRED.
- **Current-default condition:** `Standard` (sonnet) executed the identical task from scratch, alone, self-tested, and reported done.

### Token figures (actual, from each dispatch's `<usage>` block)

| Dispatch | Profile | Model | Subagent tokens | Tool uses | Duration |
|---|---|---|---|---|---|
| Executor | Fast | haiku | 41,361 | 4 | 40.7s |
| Advisor | Capable | opus | 58,870 | 4 | 51.3s |
| **Advisor Pattern total** | — | — | **100,231** | 8 | ~92s |
| Single-pass | Standard | sonnet | 60,770 | 4 | 48.5s |

The Advisor Pattern condition cost **~65% more tokens** than the Standard single-pass condition (100,231 vs. 60,770). This is the opposite of the externally-reported result that the pattern beats a mid-tier model alone at *lower* cost — on this task shape, it did not. (Token usage is used as the cost proxy per this record's own framing; no real per-token dollar pricing was applied, and the comparison also excludes the dispatcher's own orchestration/verification overhead, which is common to any dispatch shape and not unique to either condition.)

### Quality comparison

Both the Fast (haiku) and Standard (sonnet) implementations independently produced the **identical latent bug**: the unit-selection loop decides the display unit on the unrounded value, then `toFixed(1)` rounds the displayed value afterward — so a value just under a unit threshold (e.g. `1048575.9999` bytes) renders as `"1024.0 KB"` instead of correctly rolling over to `"1.0 MB"`. Independently verified by direct execution (not taken on either agent's self-report):

```
FAST     formatByteSize(1048575.9999)   -> "1024.0 KB"   (wrong)
STANDARD formatByteSize(1048575.9999)   -> "1024.0 KB"   (wrong, same bug)
FAST     formatByteSize(1073741823.95)  -> "1024.0 MB"   (wrong)
STANDARD formatByteSize(1073741823.95)  -> "1024.0 MB"   (wrong, same bug)
CAPABLE-FIX on both inputs              -> "1.0 MB", "1.0 GB"  (correct)
```

Neither Fast's nor Standard's self-written test suite included a near-threshold boundary case, so neither agent's own "all tests pass" self-report (11/11 and 8/8 respectively) surfaced the bug — this matches this project's own standing rule never to accept a subagent's self-reported pass/fail as verified fact. The Capable advisor, reviewing only the Fast agent's output, found and fixed the bug and added boundary-case tests (independently re-run here: 20/20 pass against the fix, and confirmed both buggy implementations fail on the new boundary inputs while the fix passes).

**So: on this task, the single-pass Standard model was not "good enough" — it reproduced the identical defect the cheaper Fast model did.** The Advisor step caught a real correctness bug, not a cosmetic one, that a stronger model working alone also missed. Quality: Advisor Pattern wins, clearly, on this data point. Cost: Advisor Pattern loses, clearly, on this data point. The two axes trade off in opposite directions here, which is exactly the outcome this record's own Gotchas section warned not to assume away.

### Confidence

**Low-to-moderate, single data point.** One task, one risk shape (unit-conversion/rounding boundary logic). This is a screening signal, not proof — it should not be read as "the Advisor Pattern is worth 65% more tokens in general," nor as "a mid-tier model alone is unreliable in general." It specifically shows that *for logic with a subtle numeric/boundary failure mode*, an independent second-model review has a realistic chance of catching what both a cheap and a mid-tier single pass miss, at a real (non-trivial) token cost.

### Recommendation

**Do not adopt the Advisor Pattern (Fast-executes + Capable-advises) as a replacement for the Subagent Contract's existing Standard-profile default dispatch for implementation work.** On this data point it costs ~65% more tokens than the current default for a comparable-scope task, so it is not a cost win, contradicting the externally-reported claim as applied to claude-tweaks' own task shapes (per this record's own Gotchas).

**Do adopt a narrow, targeted version of it: an additional Capable-tier correctness-review pass specifically for numeric/boundary-sensitive implementation logic (unit conversions, offset/rounding arithmetic, off-by-one-prone parsing) inside `/claude-tweaks:build`**, structured the same way the Subagent Contract's existing enumerated Capable singleton verdict-gate slots already work (`_shared/subagent-dispatch-core.md`'s "The enumerated slots" table — e.g. `/review`'s gap-sweep, `/specify`'s red-team) rather than as a new blanket default. Concretely: when `/build`'s implementer dispatch touches logic in this risk class, add one additional Capable-profile review dispatch of just that logic (inline-provided, not a shared-filesystem fan-out) before accepting the implementer's self-test as sufficient — the same shape this evaluation ran, not a change to `/build`'s default Standard-profile selection for everything else. This does not extend to `/review`, `/dispatch`, or any other workflow absent the same numeric/boundary-logic risk profile — the recommendation is scoped to that risk class, not to "build" as a whole.
