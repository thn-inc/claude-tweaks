# 2751: Add per-agent identity and scoped-credential hardening checks

Surface: infra

## Current State

`plugin/skills/_shared/criteria-security-hardening.md` and its generator, `plugin/bin/lib/code-health/candidates-security-hardening.js`, currently detect exactly three candidate kinds — `client-secret`, `missing-ownership-check`, `unguarded-ai-endpoint` (that file's own "Scope boundary" section names the vertical's exact three-check ownership, #2624). None of the three check for agent/tool identity separation, scoped-vs-broad tool permissions, or credential lifetime — the class of risk the filed source (an article framing prompt injection as an authorization failure, not a detection problem) argues for: assume injection succeeds, and limit what a compromised agent call can actually reach. claude-tweaks' own subagent dispatch (`plugin/skills/_shared/subagent-output-contract.md`) has no documented per-agent identity or credential-scoping check today.

## Deliverables

- A fourth candidate kind for the security-hardening generator (`candidates-security-hardening.js`) and a matching criteria section in `criteria-security-hardening.md`, following that file's existing per-check format (What to flag / What NOT to flag / a copy-paste prompt), covering: agents/tools sharing one broad-access identity or token instead of distinct, scoped identities; and delegation chains (one agent calling another, or a tool call) with no audit-log/trace of who delegated to whom.
- A one-time, hand-run application of the new check against claude-tweaks' own dispatch model (`_shared/subagent-output-contract.md`, `bin/hooks.js`'s dispatch-adjacent code) reported as a pass/fail per mitigation in this record's own PR description or a follow-up comment — this is a self-audit exercise, not a generator capability, since the generator's own scope (per its file header) is scanning *other* AI-built apps' source, not this plugin's own architecture.

## Acceptance Criteria

- `criteria-security-hardening.md` documents the new candidate kind in the same structural shape as the existing three (What to flag / What NOT to flag / one copy-paste prompt), and `candidates-security-hardening.js` emits it for a recognizable pattern (a shared/hardcoded credential or token reused across multiple call sites with no per-caller scoping, or a delegation call with no accompanying log/trace statement).
- Running `/claude-tweaks:code-health --focus=security-hardening` (or the equivalent focus-mode invocation) against a fixture containing the new pattern produces at least one finding of the new kind.
- The dispatch self-audit (Deliverable 2) is written up as a pass/fail per mitigation (identity separation, scoped permissions, credential lifetime, delegation audit) against claude-tweaks' actual subagent contract — not asserted without the write-up.

Detection signal: a credential/token variable name or literal reused verbatim across two or more distinct call sites that look like separate callers/agents (heuristic, approximate — the criteria doc's own "What NOT to flag" convention applies: false positives get filtered at judgment time, not generation time). ## Gotchas

- The record's two Acceptance Criteria pull in different directions: AC 1 (a generator check for *any* scanned codebase) is the vertical's normal shape; AC 2 (apply it to dispatch's own credential model) is a one-time self-audit, not a capability the generator itself gains. Treat them as two separate deliverables, not one mechanism doing both — conflating them risks either under-scoping the generator change or over-scoping it into a self-monitoring feature nobody asked for.

## Self-Audit: Dispatch Identity & Credential Hardening

One-time, hand-run application of the `shared-agent-identity` criteria (new fourth check, this record) against claude-tweaks' own dispatch model. Sources read in full: `plugin/skills/_shared/subagent-output-contract.md`, `plugin/skills/_shared/subagent-dispatch-core.md`; `plugin/bin/hooks.js` skimmed for dispatch-adjacent code via `grep -in "session|credential|token|identity"`. This is a prose write-up, not a new automated check — the generator's stated scope is scanning *other* AI-built apps' source, not this plugin's own architecture.

### 1. Identity separation — FAIL

Dispatched agents (`Agent`/`Task` calls) do not receive a distinct identity of any kind. A dispatched agent authenticates through the same ambient session credentials as the dispatcher — there is no per-agent principal, API key, or token minted at dispatch time. The one identity-shaped value in the system, `CLAUDE_CODE_SESSION_ID`, is explicitly documented (and confirmed by this read) to be the opposite of a per-agent identity: it is **identical across every subagent of a session** and is used in `plugin/bin/hooks.js` (`resolveRunUnambiguous`'s `callerIdentity = { sessionId, cwd }`, `ownedRun = ctxLib.resolveRun(cwd, process.env, input.session_id)`) purely to scope *filesystem/run-directory ownership* — which session's pipeline run a given `.claude-tweaks/pipelines/{run}` directory belongs to, so two concurrent sessions don't corrupt each other's `run-state.json`. That is a concurrency-safety boundary, not an authorization boundary: it says "which session owns this directory," never "which agent is allowed to do what." Model Selection's "Session-inherit protection" (`subagent-dispatch-core.md`) reinforces the same picture from the other direction — a dispatch either gets an explicit `model` override or inherits the session's model, but in both cases it inherits the session's *authentication*, never a distinct one of its own.

### 2. Scoped permissions — PARTIAL

Two different mechanisms exist, at two different strengths, and neither is what the source article's mitigation describes (narrowly scoped, agent-specific tool permissions):
- **Mechanically enforced, but scoped to filesystem location, not tool/API capability:** during worktree-mode pipeline runs, the PreToolUse hook denies a commit whose resolved checkout differs from the run's recorded worktree assignment (`subagent-dispatch-core.md`'s Working Directory Discipline, "mechanically enforced ... the plugin's PreToolUse hook denies commits whose resolved checkout differs from the run's recorded worktree assignment"). This is real, structural scoping — but it scopes *where on disk* a write may land, not *which tools or endpoints* an agent may call.
- **Advisory only, not enforced:** Input Discipline's point 4 ("Constraints that prevent overreach" — "Do not modify other files," "Read-only") is prompt text the dispatcher is instructed to include. Nothing in the contract or in `hooks.js` mechanically blocks a dispatched agent from ignoring that instruction and calling a tool outside its stated scope; compliance depends on the agent choosing to follow the prompt, the same trust model the source article argues is insufficient once injection is assumed to succeed.
- Tool/credential access itself (which MCP servers, which `gh`/`git` operations, which file paths are readable at all) is governed by the top-level session's own permission settings, inherited wholesale by every dispatched agent — there is no per-dispatch narrowing of that set today.

### 3. Credential lifetime — FAIL

No credential is minted per dispatch at all, so there is nothing with a lifetime to bound. Every dispatched agent uses the same long-lived session authentication for its entire run, for as long as the agent is alive — there is no short-lived, on-demand token issued at dispatch time and revoked at completion. This is a direct consequence of Identity separation's finding above (#1): a lifetime policy presupposes a distinct, mintable credential, which does not exist in this architecture.

### 4. Delegation audit — PARTIAL

A trace exists, but it is not a purpose-built "who delegated to whom, with what scope" authorization log:
- `subagent-stop.js` (referenced throughout `subagent-output-contract.md`'s Implementer Status Protocol section) writes `contract-violation` and `zero-tool-use-verdict` events to the run directory's `events.jsonl`, keyed off each dispatched agent's `agent_transcript_path` — this is real, persisted evidence of dispatch outcomes.
- The Model Selection section's `frontier-tally.log` records how many Frontier-tier dispatches a run has spent, and the resolver's per-session failure blacklist (keyed by `CLAUDE_CODE_SESSION_ID`) records model-level failures.
- But none of this is framed as, or queryable as, a delegation-chain audit log — there is no record shaped like "agent A invoked agent B at time T with scope S." The `events.jsonl` entries are keyed to debugging the *contract* (did the agent reply correctly, did it do real work), not to recording *delegation* for security review. The hook that writes most of this is also explicitly best-effort ("the event fires unreliably for Task dispatches, claude-code#27755" — `subagent-output-contract.md`), so even the debugging-shaped trail that does exist is not guaranteed complete.

### Summary

The source article's four mitigations are 1 fail, 1 partial-but-real (filesystem scoping only), 1 fail (no credential to bound), 1 partial-but-incidental (a debugging trail exists, not a security audit log) — net: claude-tweaks' dispatch model relies on prompt-level trust (Input Discipline's "constraints that prevent overreach") and one structural filesystem guard, not on the identity/credential separation the source argues an injection-resilient design needs. The worktree-pinning guard (#2) is the one mitigation that is both real and mechanically enforced; everything else here is either absent or advisory. This write-up is evidence for a possible follow-up record (distinct identity per agent, a delegation-chain audit log), not a claim that one is being filed by this record — per the Gotchas section above, this record's own scope is the generator check and this self-audit, not remediating what it finds.
