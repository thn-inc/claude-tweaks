# 1160: residue.js's suiteRun() has no maxBuffer — a passing suite over ~1MB of TAP output reports a false 'suite exit 7' finding

Origin: reflect wrap-up from #1011
Defer-reason: out-of-scope-for-current-diff

## Current State

`plugin/bin/residue.js`'s `suiteRun()` (the closure it passes to `probeSuite`, around line 89) calls
`execFileSync('npm', ['test'], { cwd, encoding: 'utf8', timeout: 600000, stdio: ['ignore', 'pipe', 'ignore'] })`
with no `maxBuffer` option. Node's `child_process` default `maxBuffer` is 1 MiB (1048576 bytes). This
repo's own `npm test` TAP output is now measured at ~1,050,057 bytes (5570+ tests, each producing
several YAML diagnostic lines) — just over that default.

Reproduced directly (2026-08-20, this repo, worktree `worktree-dispatch-record-1011`, HEAD at the
tip of a fully green branch — `npm test` run independently via the shell exits 0 with 5570 pass /
0 fail):

```
node -e "
const { execFileSync } = require('child_process');
try {
  execFileSync('npm', ['test'], { cwd: process.cwd(), encoding: 'utf8', timeout: 600000, stdio: ['ignore','pipe','ignore'] });
} catch (err) {
  console.log('code=', err.code, 'status=', err.status);
}
"
# => code= ENOBUFS status= 7
```

`residue.js --scope blast-radius` (and presumably every other scope) therefore now reports a
permanent, false `suite` finding — `test suite exit 7 — test command exited 7` — on every
invocation against this repo's current test suite size, regardless of whether the suite actually
passes. `probeSuite`'s own header comment states "A suite that could not be run … reports
`ran: false` — never green", but this ENOBUFS case is misclassified as `ran: true` with a failing
finding (`suite.js`'s `result.code === 0` check is the only path to a clean report; ENOBUFS never
produces `code === 0`), when the correct read for a buffer overflow is closer to `ran: false,
reason: 'could not run …'` — the suite was never actually observed to fail, the *harness* failed
to capture it.

Confirmed via `git log` (`git log --oneline --grep="499" -i`) that this ENOBUFS gap is independent
of #499/#1011's own blast-radius-scope work — `suite.js` and its caller in `residue.js` are
untouched by either.

## Deliverables

- [ ] Set an explicit, generous `maxBuffer` (e.g. 16-64 MiB, or `Infinity`) on the `execFileSync`
      call in `residue.js`'s `suiteRun()`, so a large-but-passing suite's TAP output is never
      truncated into a false failure.
- [ ] Consider whether `suite.js` should treat an `ENOBUFS`/buffer-overflow error distinctly from a
      genuine non-zero test exit code (e.g. `ran: false, reason: 'test output exceeded capture
      buffer'`) rather than reporting a fabricated `remedy: record` finding either way — the harness
      failing to capture output is a different fact than the suite actually failing, and the two
      should not render identically to a wrap-up ledger reader.
- [ ] Add a regression test using a stubbed `run()` that simulates an `ENOBUFS`-shaped error
      (`err.code === 'ENOBUFS'`, no usable `stdout`) and asserts the probe does not report a
      `remedy: record` finding claiming the suite failed.

## Acceptance Criteria

1. Running `residue.js` (any scope) against a repo whose test suite passes but produces >1 MiB of
   TAP output reports no `suite` finding.
2. A genuine test failure (small suite, real `not ok` lines) still reports correctly — this fix
   must not mask real failures, only the buffer-truncation artifact.
3. `npm test` passes in full.

## Why this matters

`residue-sweep.md` and the Wrap-Up Review Console treat a `suite` finding as `remedy: record` —
visible, not auto-fixed, but still surfaced as something needing attention on every single
wrap-up run against this repo from now on (the suite is only going to grow), for a condition that
has nothing to do with the code actually under review. Left unfixed, every future wrap-up either
has to independently re-verify and dismiss this exact finding (as this record's own wrap-up did)
or, worse, someone eventually trusts the probe's over the real `npm test` result and treats a
green branch as red.
