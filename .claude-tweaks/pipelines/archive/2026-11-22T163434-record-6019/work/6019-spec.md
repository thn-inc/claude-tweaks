# 6019: Let a protected path require the driver's reviewer instead of refusing

Surface: backend
**Related:** #5423
Risk-flags: auth

## Overview

The driver refuses every record with a Key File on the protected-path list ("protected path" refused 68 of 142 build-authorized ready records in the 2026-11-18 funnel, `docs/superpowers/specs/2026-11-18-pipeline-economy-design.md`). Its post-build diff check then refuses any protected path the diff touches. This record adds a policy value choosing whether a protected path refuses (`refuse`, the default and today's behaviour) or requires the reviewer (`reviewer`).

Under `reviewer`, a record with protected Key Files is admitted when the reviewer is on for it, and the driver's diff check lets protected paths through for that record. The record then always ends at `pending-review` for a human merge, through the widening list and merge stop the risk-and-ceremony sub-issue builds (widening `protected-path`). A protected path in the diff that no Key File named also adds the widening, so the record ends at `pending-review`.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- The list's contents, or making it editable (sibling sub-issue). This record reads whatever `isProtectedPath` answers.
- `merge-sensitive-paths`. A merge-sensitive path keeps refusing in eligibility and in the diff check, unchanged.
- The express lane. `bin/express-lane.js check` without the new flag, and every express eligibility call, behave exactly as today.
- The reviewer's evidence-path guard (`review.js`, which refuses an evidence file written under a protected path). It stays as it is.

## Release Note

The pipeline driver can be set to take records that touch protected paths, with its reviewer on, and always leaves them for a human to merge.

## Technical Approach

Same shape as the risk-and-ceremony sub-issue: relax in eligibility behind a driver-only option, make the widened record need the reviewer in admission and `reviewRequired`, and stop it at merge. The diff check is the new part. The protected-path test must still run on every changed path, rename sources included, so the record is known to touch one. Only its effect changes from a violation to a reported fact, and only when the driver asks for it.

### Data / API Surface

- Policy key (proposal `express-driver-protected-paths`): `{ type: 'enum', values: ['refuse', 'reviewer'], default: 'refuse', policyOnly: true, category: 'merge-safety', tier: 'advanced' }`.
- `evaluateRecordEligibility(issue, { ..., protectedPathsNeedReviewer })`
- `evaluateDiffBounds(files, { ..., reportProtectedPaths })` returns `{ withinBounds, violations, implLines, changedFiles, protectedPaths }`.
- `express-lane.js check ... [--protected-paths reviewer]` (exact flag settled by the builder, a value-taking flag like `--max-lines` since `parseArgs` makes every flag take a value).
- The widening value `'protected-path'`.

### Key Files

## Gotchas

- `parseArgs` in `cli.js` makes every flag take a value (`--max-lines <n>`). A boolean flag would be refused as "requires a value", so give the new flag a value.
- `evaluateDiffBounds` reads `oldPath` from the input entry at the same index, because `classifyDiffFiles` drops it. Keep that when moving protected matches into the new field.
- The funnel in `tools/pipeline-cost-report/funnel.js` keys `protected path: {p}` by its head. The refusal string is unchanged, so the funnel needs no edit for this record.
- Do not edit `.claude-tweaks/policy.yml`. The trial sub-issue sets the trial values.
- A protected path the diff touches but the Key Files did not name is still outside the Key Files, so `outside Key Files: {p}` refuses it unless it is a test file. The widening from check matters for protected test files (e.g. a test under a `hooks/` directory) and renames.
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(auth): …`.
- The eligibility option follows the key alone, so admission produces the reviewer-off refusal; the `check` flag additionally requires `ctx.reviewer.on === true`. A protected path is never passed without the reviewer running.
- Key Files beyond the list above: `plugin/bin/lib/driver/merge.js` and `plugin/bin/drive.js` are only read (the `widened-admission` stop and the `--check` line come from the sibling); the widening helper's home is `plugin/bin/lib/express/eligibility.js`.
- The merge-sensitive test runs on every changed path before protected matches move into `protectedPaths`, so a path matching both stays a violation.
- A `check` that rejects the new flag (an older build) makes the driver refuse, never pass the path.

## Decision Rationale

See the risk-and-ceremony sub-issue's Decision Rationale. The default `refuse` reproduces today.

Harm model (maintainer, 2026-11-21): the protected list guards two different harms. A merge-time path (hook code, shared contracts, CODEOWNERS, policy and verify-scope files) only matters once merged, so a reviewer plus a human merge at `pending-review` controls it. A build- or push-time path acts before any merge: a pushed workflow runs in CI on the draft PR, `package.json` scripts run in CI and in the driver's test step, git hooks run on commits, and agent settings change what the next worker launch in the worktree may do. `reviewer` mode therefore never admits the build-time families.

- A `protected-path` widening the driver adds after `check` reports protected paths reads `admitted widened by protected-path` in merge entry's stop detail, the same as one added at eligibility; `merge.js` is not changed for it, and the check's proceed line in `decisions.md` names the reported paths. Supported by: "`plugin/bin/lib/driver/merge.js` and `plugin/bin/drive.js` are only read".

## Build Alignment (Beneficial deviations, applied to this spec)

- The build-time subset is not a hand-kept copy: `eligibility.js` holds one frozen `PROTECTED_FAMILIES` table whose entries each declare `buildTime`, and `PROTECTED_PATH_RES` / `BUILD_TIME_PROTECTED_RES` derive from it, so a new protected family must declare its kind (a partition test goes red otherwise).
- Admission's widened reviewer-off reason now names every widening source: `record is admitted widened (above low risk, with a non-fast-lane ceremony or a protected Key File) and the reviewer step is off for it`.
- `plugin/bin/lib/driver/plan-lane.js` (landed upstream by #6053 after this spec was written) is a reader of the driver policy family too; it resolves `express-driver-protected-paths` and asks the same protected-path widening question as the eligibility step and the queue pull.
- The driver's own fallback proceed line in `decisions.md` (written when `check` reports `logged: false`) carries the same protected-path note as `check`'s own line.
