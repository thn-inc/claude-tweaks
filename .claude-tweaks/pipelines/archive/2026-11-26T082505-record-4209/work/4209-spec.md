# 4209: reconcile: pruneResidueFailures drops an escalated entry whose retry resolve failed, orphaning its path

Surface: infra

**Related:** #4202, #4180, #4253, #3193, #3977, #3990, #4217, #4285, #4289

Origin: #4202 whole-branch review (Minor 4)

Defer-reason: needs-human-decision

## Current State

- `pruneResidueFailures` (`plugin/bin/lib/reconcile/cache.js:393-415`) deletes a `residueFailures` entry whose path is gone from disk (`delete failures[key]`, `:403`) *before* its best-effort resolve. It keeps that deletion whatever the resolve returns. A failed resolve is only reported, through the returned `failures` list (`:409-411`).
- Since #4202, an archive success resolves an escalated `structurally-stuck` entry through `clearResidue` (`:300`), which keeps the entry when that resolve fails (`:315`; pinned by `tests/bin-lib/reconcile/cache.test.js:432`, "#2724 clearResidue: an escalated entry whose resolve returns resolution-failed is kept for the next pass"). The same pass's prune then retries exactly once and drops the entry regardless. So a resolve that fails twice in one pass (a `gh` outage) leaves the path orphaned on the consolidated record.
- This drop-on-failure posture is deliberate. #1892 Deliverable 3 documents it ("a resolution failure still drops the cache entry"), and two tests pin it: `cache.test.js:352` ("…triggers exactly one resolve call… and is still dropped") and `:371` ("a resolve failure (gh absent / network) still drops the cache entry, never throws").
- #4202's convergence only drops an orphan on a later edit of the record. When the orphan was the last listed path, the record stays open until an unrelated stuck dir is escalated or resolved.
- `recordResidueError` (`:264`) already records the last failed op and reason on a kept entry (#4180), as `lastResidueError`. The cache schema has no retry counter today.

## Deliverables

1. Make `pruneResidueFailures` keep an escalated entry whose resolve did not land, the way `clearResidue` already does, so the next pass retries it. "Did not land" means a status outside `RESIDUE_RESOLVED_STATUSES` (`:288`) or a throw.
2. Bound the gh-absent posture so a machine with no `gh` does not retry forever. Count failed prune retries on the entry and drop it after a fixed bound, never reverting to drop-on-first-failure. Document the bound beside the existing #1892 comment (`cache.test.js:325`) and in the function's header.
3. Update the two tests that pin the old posture (`cache.test.js:352`, `:371`) to the new contract, and keep the non-escalated drop test (`:328`) unchanged.

## Acceptance Criteria

- [ ] A `tests/bin-lib/reconcile/cache.test.js` test: an escalated entry whose path is gone and whose injected resolve returns `resolution-failed` survives `pruneResidueFailures`. It fails when the change is reverted.
- [ ] A test pins the bound: after the configured number of failed prune retries the entry is dropped, and the returned `failures` list still reports each failed resolve.

## Release Note

Reconcile no longer forgets a stuck run directory's escalation when GitHub is briefly unreachable.

## Technical Approach

Move the `delete failures[key]` for escalated entries to after the resolve, and delete only on a resolved status or once the retry bound is reached. Store the count on the entry itself (for example `pruneRetries`), next to the `lastResidueError` field #4180 added (`cache.js:65`). That way the bound survives across passes and needs no new cache key. Non-escalated entries keep today's immediate drop, since they never had a GitHub-side record to resolve.

### Key Files

- `plugin/bin/lib/reconcile/cache.js` — `pruneResidueFailures` keep-on-failure plus retry bound; entry schema comment (`:65`)
- `tests/bin-lib/reconcile/cache.test.js` — new keep and bound tests; rewrite the `:352` and `:371` pins

## Gotchas

- This reverses a documented decision (#1892 Deliverable 3). The record was filed with `Defer-reason: needs-human-decision` for that reason, and the reversal is the subject of this record, not a side effect. A reviewer should confirm the chosen bound before merge. The bound's value is the one open choice, and it is left to the plan to propose.
- `pruneResidueFailures` is reason-agnostic by design (`cache.test.js:325-327`, shared with #1811's structurally-stuck prune). The keep-on-failure rule applies to every escalated entry, not only `structurally-stuck`.
- #4253 (open, `ready`) retries a failed residue *escalation* in the same `cache.js`, and its Key Files overlap this record. Its retry bound and this one should share one counter shape and one bound constant, never two parallel conventions. Whichever lands second adopts the first one.
- Callers read the returned `{ failures }` list for reporting. Keep reporting each failed resolve even when the entry is kept, so a gh outage stays visible in the reconcile output.

## Decisions

**Decision** — prune retry bound (plan-review Question 1, 2026-11-26, maintainer-authorized autonomous lane): Reading A. The bound is 5 failed prune retries, counted per reconcile pass: one increment per pass in which the entry's resolve did not land. The entry is dropped on the pass that records the 5th failure. Export it as one named constant, `RESIDUE_RETRY_LIMIT = 5`, from `plugin/bin/lib/reconcile/cache.js`. Rejected: a wall-clock bound. It adds a timestamp comparison and a clock dependency, and passes already track the thing that matters, which is how many times the resolve was attempted. One pass per SessionStart means 5 passes ride out a multi-session `gh` outage. A gh-absent machine gives up after 5 cheap ENOENT spawns per entry.

**Decision** — counter name and shape: store the count on the entry as an op-neutral `residueRetries` integer, next to `lastResidueError`. Do not call it `pruneRetries`. #4253 has not landed, so this record sets the shape, and #4253 adopts the same field and the same `RESIDUE_RETRY_LIMIT` constant. A test pins the constant's value.

**Decision** — reporting: a kept entry's failed resolve is reported exactly once per pass. If the same failure would reach the reconcile output both through `lastResidueError` and through the returned `failures` list (`plugin/bin/lib/reconcile/index.js` concatenates both), deduplicate so the output shows it once. A test asserts the once-per-pass count.

**Decision** — `residue-summary.js`: a kept escalated entry whose path is gone still counts as stuck. Its GitHub-side record is still unresolved, and that unresolved record is the signal the summary reports. No `residue-summary.js` change is needed beyond what keeps that true.

**Decision** — the task carries `Review risk: high`, because it reverses the documented #1892 Deliverable 3 posture.
