# 5294: Hooks re-run the same git rev-parse up to 15 times per call — reuse repoInfo within and across hook processes

Related: #5266, #5261, #4760

## Current State

Companion to #5266 (the status line half). Measured 2026-11-13 on this Mac with about 27 live sessions: in a 30 s window `hooks.js pre-tool-use` ran 48 times at about 6 processes each and `hooks.js post-tool-use` 47 times at about 2 each, mostly `git -C <cwd> rev-parse --show-toplevel --git-dir --git-common-dir --show-superproject-working-tree`.

Counting child processes per run with a preload that wraps every `child_process` launcher (main at 671c9a83c, this repo with three unfinished runs under `.claude-tweaks/pipelines/`):

| Hook run | Processes (node + children) | Of which the four-flag rev-parse |
|---|---|---|
| pre-tool-use, Bash `git status`, main checkout | 2 | 1 |
| pre-tool-use, AskUserQuestion / Agent / Write outside the repo | 3 | 2 |
| pre-tool-use, Edit in the main checkout (deny) | 5–6 | 2–3 |
| pre-tool-use, Bash `npm test > out.txt` in a linked worktree | 16 | 15 |
| pre-tool-use, Edit in a linked worktree | 16 | 15 |
| post-tool-use, Bash `git commit -m x` in a linked worktree | 18–19 | 15–16 |

Every one of those rev-parse calls asks the same question about the same directory. `wtDetect.repoInfo` (`plugin/bin/lib/hooks/worktree-detect.js`) has no memo, and its callers multiply: `classifyOwnership` (`plugin/bin/lib/hooks/context.js`) calls `repoInfo(cwd)` once per candidate run directory, so every unfinished run adds one git spawn to every hook call. `resolveRun`'s `callerRepoInfo` memo is per-call only, and `hooks.js` resolves `runDir` and `ownedRun` separately before `pre-tool-use.js` asks again.

The answer (toplevel, git dir, common dir, superproject) only changes when the checkout's `.git` entry, the linked worktree's admin dir, or the repo config changes, all of which can be checked with a few `stat` calls. Under load one rev-parse costs 0.4–2.5 s (`git-exec.js` header, #134), so repeats are expensive exactly when the machine is busy.

## Deliverables

1. **Per-process memo in `repoInfo`.** Cache each definitive answer keyed on the resolved directory, and validate it on every hit against a filesystem signature: the nearest `.git` entry found by walking up (path, file or directory, inode); for a `.git` file, its `gitdir:` target and that admin dir's inode and `commondir`; the common dir's `config` mtime and size. A mismatch re-asks git. Never cache an indeterminate answer (timeout, spawn failure, no git), so #134's retry behaviour is unchanged. A call that passes `opts.timeoutMs` bypasses the cache.
2. **Cross-process reuse.** Persist the same validated entries per user so the next hook process skips the spawn: one small JSON store, atomically replaced, capped by entry count with oldest-first eviction, read and written inside try/catch so a broken store never breaks a session or changes a verdict. Bypass the store (but keep the in-process memo) when any git discovery variable is set (`GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_CEILING_DIRECTORIES`, `GIT_DISCOVERY_ACROSS_FILESYSTEM`). Give the store location an env override, and point `tools/run-tests.js` at a per-run temp dir so test fixtures never write into the user's home.
3. Document the cache, its signature, and its bypass rules in `docs/hooks.md`.
4. Measure child processes per pre-tool-use and post-tool-use run for the six rows above before and after, and quote the raw output in the PR.

## Acceptance Criteria

- Within one process, repeated `repoInfo` calls on the same directory spawn git once (a test counting `execFileSync` calls).
- A warm store answers `repoInfo` in a fresh process with zero git spawns, and returns the same object a cold call returns.
- The cached answer is not reused after each of these, every case proven red by disabling the signature check: the linked worktree is removed; it is removed and re-added at the same path; `git init` runs in a directory that was previously not a repo; the linked worktree's admin dir is pruned while its `.git` file stays.
- An indeterminate answer (`timeoutMs: 1`) is never cached, and the next normal call answers definitively (the existing #134 tests keep passing).
- A corrupt, unreadable or unwritable store leaves `repoInfo`'s answer unchanged (a test for each).
- After the change, pre-tool-use for an Edit in a linked worktree runs at most node + 1 git cold and node + 0 rev-parse warm, measured the same way as Current State. No allow/deny verdict changes across `tests/hooks-pre-tool-use.test.js`, `tests/hooks-gate-coverage.test.js` (including the #4303 call-count pin) and `tests/bin-lib/hooks/classify-ownership.test.js`.
- `npm test` passes.
