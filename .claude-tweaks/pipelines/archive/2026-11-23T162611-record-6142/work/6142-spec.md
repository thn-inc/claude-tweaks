# 6142: Treat a dispatch blocker as landed only when its closing merge carried the implementation

## Current State

`plugin/bin/lib/preflight-records/blocker-landing.js` classifies a blocker `landed` when any candidate closing commit is reachable from the integration branch. It never looks at what that commit changed.

On 2026-11-23 #6000 was closed by PR #6061, whose squash `46e21cbf6` added only the materialized spec, the plan and the ledger (`.claude-tweaks/pipelines/*/work/6000-spec.md`, `docs/superpowers/plans/…`, `docs/plans/…-ledger.md`): the run was still building. None of #6000's Key Files (`plugin/bin/lib/driver/roles.js`, `plugin/bin/review-lens-workers.js`, …) were touched. The check read #6000 as `landed`, so `/claude-tweaks:dispatch #6003` claimed #6003, opened draft PR #6121 and ran a build against a launcher that did not exist. The build agent noticed and stopped with `failed:blocker-landing` after about 7.5 minutes.

## Deliverables

1. In `blocker-landing.js`, a reachable closing commit counts as `landed` only when its diff touches at least one path in the blocker's `### Key Files`. A reachable commit that touches none of them, or only pipeline bookkeeping (`.claude-tweaks/pipelines/**`, `docs/superpowers/plans/**`, `docs/plans/*-ledger.md`), gets a distinct verdict (for example `hollow`) carrying the PR number.

2. A blocker with no `### Key Files` section keeps reachability as the rule, with the bookkeeping-only check from deliverable 1 still applied.

3. The queue pull (`plugin/bin/lib/dispatch/unlanded-blockers.js`) excludes a record whose blocker is `hollow` as `unlanded-blocker`, and its report line says why: `#N waits — blocker #M was closed by #PR with no implementation`. `bin/preflight-records.js --blocker-landing` prints the same verdict.

**Decision (plan review Q1, several reachable candidate commits):** a blocker is `landed` when **any** reachable candidate commit (the closer or a merged `closedByPullRequests` reference) is non-hollow. Probe and read the files of every reachable candidate until one is non-hollow. The blocker reads `hollow` only when every reachable candidate is hollow, and the verdict names the PR of the first hollow candidate. Do not stop at the first reachable candidate: a hollow closer must not hide a later PR that did carry the implementation. This keeps the current rule (any reachable candidate counts) and adds the content check to it.

**Decision (plan review Q2, a reachable commit with an empty file list):** follow Deliverable 1 as written. On a blocker that has `### Key Files`, a reachable commit whose file list was read successfully and came back empty touches none of them, so it is `hollow`. On a blocker with no Key Files it stays `landed`, because there is no non-bookkeeping path to require. This decision covers only a read that succeeded and returned zero files. A failed file read is not an empty list and keeps whatever failure handling the plan gives it.

## Acceptance Criteria

- [ ] A blocker whose reachable closing commit touches only `docs/superpowers/plans/x.md` and `.claude-tweaks/pipelines/r/work/1-spec.md` is not `landed`, and its dependent is excluded as `unlanded-blocker` with the no-implementation reason.

- [ ] A blocker with Key Files `a.js` whose closing commit touches only `b.js` is not `landed`.

- [ ] A closing commit that touches a Key File is `landed`, unchanged.

- [ ] A blocker without Key Files whose closing commit touches a non-bookkeeping file is `landed`, unchanged.

- [ ] A fixture replaying squash `46e21cbf6`'s file list against #6000's Key Files excludes the dependent (#6003's case).

- [ ] A blocker whose first reachable candidate is hollow but whose later reachable candidate touches a Key File is `landed` (Q1 decision).

- [ ] A blocker with Key Files whose only reachable candidate returns an empty file list is `hollow`; the same empty list on a blocker without Key Files is `landed` (Q2 decision).

## Release Note

Dispatch no longer builds a record whose blocker was closed by a merge that carried no implementation.

## Build Alignment Notes

- Beneficial (build Common Step 4.5): "touches at least one path in the blocker's `### Key Files`" is matched on normalized entries — a trailing `:N`, `:N-M` or `#L…` suffix is stripped, `\`, `./` and `..` are canonicalized (`canonicalPath`), an entry ending `/` prefix-matches, an entry with `*` glob-matches (`globToRegExp`), and a renamed file's `previous_filename` counts as touched. Key File entries are record text, so an exact-string match would read a real implementation `hollow`.
