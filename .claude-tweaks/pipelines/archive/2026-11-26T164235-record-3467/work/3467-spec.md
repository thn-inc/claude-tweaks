# 3467: Merge-verification classifies a cancelled or action_required CI run as green

Verified-as-of: 6ebb484d71cc753d74ca967edfa6f45f3e41fe83

Origin: review of #3405 (three lenses reported it; the behavior mirrors the pre-existing rollup rule)

Defer-reason: needs-human-decision

## Current State

`plugin/bin/lib/pr-checks/classify.js` treats only `FAILURE`, `TIMED_OUT`, `ERROR` and `STARTUP_FAILURE` as failing (`FAILING_CONCLUSIONS`, pinned equal to `_shared/pr-first-merge.md` Step 2.5's list by `tests/pr-check-gate-conformance.test.js`). A completed check or head run whose conclusion is `CANCELLED`, `ACTION_REQUIRED` or `STALE` is therefore neither red nor pending, so a PR whose `test` run was cancelled reads green and can merge without the suite having passed. #3405 extended the same rule to the head-sha workflow runs (`classify.test.js` pins a cancelled head run as green); the rollup behavior pre-dates it.

## Deliverables

- [ ] Decide the policy: which non-success conclusions block a merge (cancelled, action_required, stale), weighing false parks on runs superseded by a newer push (`test.yml` sets `cancel-in-progress: true`, but those runs belong to older shas, not the head).
- [ ] Apply it to `FAILING_CONCLUSIONS`, Step 2.5's prose list, and the head-run path together, with tests.

**Decision** (2026-11-26, maintainer, recorded by the orchestrating session; answers Deliverable 1): **hold, don't fail.** On the PR head commit, when the newest run of a check (grouped by check name, newest by start time, ties by id) concluded `CANCELLED`, `ACTION_REQUIRED` or `STALE`, `classifyRollup` returns `pending`: not red, not green. The PR then follows the existing pending path (wait, then park at the bound). `SKIPPED` stays green-compatible. A cancelled run followed by a successful rerun of the same check still reads green, because only the newest run counts.

- **Why pending and not red:** nothing failed, so the remedy is a rerun, not a fix round. Red would send an agent into a fix round for a non-failure.
- **Evidence:** across the last 150 merged PRs (read 2026-11-26), no head commit carried a cancelled, action_required or stale conclusion, so false holds cost about nothing. The same PRs carried 204 `SKIPPED` conclusions (the fix-label jobs), which is why skipped must stay green. `test.yml`'s `cancel-in-progress` cancels runs of older shas only, and the rollup is read at the head.
- **AC amendment:** the conformance pin keeps `FAILING_CONCLUSIONS` equal to Step 2.5's prose list, and gains a second pinned list for these held conclusions, equal between `classify.js` and the prose. The existing `UNVERIFIED_CONCLUSIONS` (#5153) minus `SKIPPED` is the starting set.

**Decision** (2026-11-26, plan-review round 1, recorded by the orchestrating session under the maintainer's standing authorization to settle plan-review questions; answers Question 1 of the plan-review comment on this record): **Reading B. Every merge gate that reads CI follows the held rule, the learned-skills drain included.** `plugin/bin/lib/learned-skills/drain.js`'s second scan stops reading held conclusions as red: it excludes `HELD_CONCLUSIONS`, imported from `classify.js` (never a local copy), so a held newest run reaches the drain as `classifyRollup`'s `pending`, and a cancelled run replaced by a newer successful rerun of the same check reads green there too. `tests/bin-lib/learned-skills/drain.test.js`'s cancelled cases (about :510 and :579) change to expect `pending`. A completed conclusion that is neither held nor in `['SUCCESS','NEUTRAL','SKIPPED']` still reads red.
- **Why:** the Decision above rejects red for a non-failure, since the remedy is a rerun, not a fix round. The drain pins Step 2.5's table, so a second, stricter rule in one consumer is the divergence that pin exists to prevent. Held is never green, so the drain still never merges on a held check.
- **Same build, from the plan review:** (1) the Step 2.5 bounded-watch loop treats a held check as still pending, never green. Probe the exit code `gh pr checks` gives for a cancelled check first, and build to the observed value. (2) Newest-run ordering accepts REST-shaped head-run rows (`run_started_at`, then `created_at`, ties by `id`) as well as GraphQL-shaped ones. (3) The classifier task carries a `**Review risk:** high` marker.
- **Family rule (apply without asking):** any further reader of rollup or head-run conclusions that this change touches, or that plan review finds (a CLI, a skill's prose list, a test fixture), follows the same rule: newest run per check name; `FAILING_CONCLUSIONS` → red; `HELD_CONCLUSIONS` → pending; `SUCCESS`/`NEUTRAL`/`SKIPPED` → green-compatible. One shared list, imported from `classify.js` and pinned to the prose.

## Acceptance Criteria

- A `cancelled` `test` check or head run at the PR head no longer reads green (per the decided policy).
- The prose list, `FAILING_CONCLUSIONS` and the conformance pin stay equal.

## Plan Review Clarifications

- Settled by plan review after an answered round: "The spec does not decide whether 'newest run per check name' also governs red, or only held." The reading taken is Reading A. Newest-per-check decides only the held rule, and a `FAILURE`-class row stays red even when a newer success supersedes it, which is today's red behaviour unchanged. The reading not taken is Reading B, where red also reads only the newest row per check. Reading B would loosen an observable merge contract, turning red into green for a superseded failure.

## Build Alignment Notes

- **Beneficial (Common Step 4.5):** a completed held row with no check name cannot be grouped by name, so `heldChecks` counts it as held on its own (fail closed) in every merge gate, where it previously read green. The spec's newest-per-name rule is silent on unnamed rows. The appendix's held-rule note states this.
- **Update the spec (Common Step 4.5):** the Step 2.5 bounded watch maps a held state from `gh pr checks` (deduplicated newest-per-check within the rollup only). A cancelled rollup job whose newer run of the same name exists only as a head run therefore keeps the watch waiting until the bound and parks as `checks-pending-timeout`, whose remedy is a rerun and never a merge. `classifyRollup` reads that case green. The fence takes the fail-closed direction, and the appendix's Rationale notes record it.

## Release Note

Pipeline merges no longer treat a cancelled CI run as passing.
