## Original request

build: SDD implementer and reviewer briefs omit the worktree shell constraint, so nested agents hit the harness Bash guard repeatedly

**Summary:** In a worktree-isolated `/flow` run, the implementer, reviewer and mutation-probe subagents that build Common Step 2 dispatches were refused by the harness worktree Bash guard 25 times in one run, because their briefs do not carry the shell constraint documented in `_shared/scratch-worktree.md` §7.

**Kind:** Gap

**Affected component:** build Common Step 2 dispatch prompts (implementer, spec/quality reviewer, final whole-branch reviewer)

**Objective:** run efficiency (avoidable failed tool calls)

**Measurement:** 25 `wd-guard-refusal` events in one run (`friction-events.js`), across roughly 10 dispatched subagents; refused shapes were `cat >> file <<'EOF'` heredocs, `cd <dir> && ...` compounds, `sed -i` loops for mutation testing, and `mklink /J` / `git worktree add` into a temp dir.

**Cost this session:** about 25 refused calls, each followed by a retry in a different shape; no wrong results, only wasted turns.

**Use case:** The parent session runs `/flow` from inside a worktree (the default git strategy). Every nested agent inherits the harness's worktree Bash guard, but the briefs build composes for them say nothing about it, so each agent rediscovers the rule by being refused. The parent brief stated the rule, yet it did not reach the second-level dispatches.

**Suggested direction:** inline a short "Shell constraint" paragraph (the §7 rule: plain single commands; no heredocs, `$(...)`, `cd X && ...`, pipes into `node -e`; use the Write/Edit tools and `git -C`) into every Common Step 2 dispatch template, and into the mutation-probe instructions specifically, since `sed -i` loops are the most common refused shape.

**Definition:** Clear

## Plan Review Clarifications

- Decided by the user at plan review: the scratch checkout keeps the probed `git -C {worktree} worktree add --detach {session-scratch}/disc-{id} HEAD` shape and adds a check that `git -C {disc-path} rev-parse HEAD` prints the reviewed commit's SHA; on a mismatch the check has no evidence and tears down. ## Architecture Alignment (build)

- **Beneficial: the scratch checkout always lives in the session scratchpad.** The Gotcha made the session scratchpad conditional on the probe refusing the run-dir path, but the probe's run-dir row (b) passed. The recipe still says "never under the run directory or inside the shared worktree". The run directory sits in the main checkout, which a worktree-isolated session's Write/Edit cannot reach, and that is #4672's direction. Run-dir row (b) is recorded in the PR's probe table as passing and is deliberately unused.
- **Beneficial: the recipe states who fills each placeholder, and it is a two-hop paste on /build's path.** Deliverables 2–3 only say "cite the recipe". Reviews showed that an agent cannot read the recipe, and that /build pastes it before any task commit exists. So `build/dispatch.md`'s #2740 sentence now says /build fills `{plugin-root}` and `{worktree}`, and SDD fills `{reviewed-sha}`, `{base-sha}` and `{id}` per dispatch. The lens 3f procedure gained a dispatcher-side paragraph: `{reviewed-sha}` is HEAD when the bundle is built, `{base-sha}` is `git merge-base {base} HEAD` (or HEAD for uncommitted scope), and an uncommitted-work scope takes the No-git fallback. This was not just a cite in the criterion bullet. As a result, `review/step3-lens-dispatch.md` grew to 51,479 B, not a net shrink, which is still within the 52,500 B rail.
- **Beneficial: evidence rules beyond the spec's create/run/teardown list.** The recipe adds four rules:
  - A green run counts only after a control turned red in the same checkout. A control that stays green means the run did not load the scratch copy.
  - A module or binary resolution failure has no evidence (`NODE_PATH` covers CommonJS `require` only).
  - A failed teardown reports `DONE_WITH_CONCERNS`. The `worktree list` check looks for the agent's own `{disc-path}`, not any `disc-` entry, so a sibling's live checkout is not misread as a leak.
  - `{id}` includes the round, so re-reviews never collide.

  Each rule closes a false-evidence path the reviews found.
- **Beneficial: the no-git fallback mirrors the repo layout and reads base content without mutating the tree.** It writes each file the test loads at its repo-relative path under `{disc-path}`, takes base content from the read-only `git -C "{worktree}" show {base-sha}:{path}`, runs per step 4, and ends with `rm -r "{disc-path}"`. This is the Technical Approach's "adapted so nothing is restored in the shared worktree", made concrete.
