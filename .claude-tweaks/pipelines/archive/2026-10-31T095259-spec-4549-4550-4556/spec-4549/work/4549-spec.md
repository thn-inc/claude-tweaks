# 4549: pr-first-merge: Fixes lines in the squash commit message do not close records when the integration branch is not the default branch

Surface: infra

## Current State

A `pr-first` run PR whose base is a non-default integration branch (for example `develop` on a repo whose default branch is `main`) leaves every record it fixes open after it merges. The field report: a six-record `/claude-tweaks:flow` bundle squash-merged into `develop`, its composed message carried one `Fixes #N` line per record, none of the six closed, and they were closed by hand.

Three plugin surfaces are involved, all checked against `origin/main` at `d4d40c982` (after #4597 merged):

- `plugin/skills/_shared/pr-first-merge.md` Step 3 (lines ~326-334) states the composed merge-commit message is "what GitHub scans for closing keywords on a non-default integration branch ... an explicit merge commit message is what makes closing work on any integration branch". That is wrong. GitHub acts on closing keywords in a commit message, or in a PR body, only when the commit or PR lands on the **default** branch. The sibling file `plugin/skills/_shared/pr-first-merge-post-merge.md` Step 4.0b (lines ~41-46) already states the correct rule ("GitHub closes `Fixes #N` records and a PR's other closing links only on the default branch, so a merge into any other branch leaves its sub-issues open"), so the two shared contracts contradict each other.
- `plugin/bin/closing-links.js --mode post-merge` (Step 4.0) only guards the opposite direction. Its candidate set (line ~321) is `[...linked, ...keepOpen].filter((x) => !expected.includes(x))`: it reopens records the merge closed *by mistake*, and never reads the `expected` (Fixes-span) records at all. On a non-default base nothing closes, so it reports `nothing-closed` with every Fixes record still open and nothing flagged. The post-merge `gh pr view --json` field list (line ~231, `state,mergedAt,body,closingIssuesReferences,url,mergeCommit`) does not include the PR's base branch, so it cannot tell the two cases apart today.
- Since #4597, the same CLI also emits `closingSet[]` (line ~382): `linked` minus every record the guard reopened, could not settle, or still sees pending. Its comment says "A Fixes-block record is never read ... both count as closed". On a non-default base that assumption is false: those records are still `OPEN`. It does no harm today only because Step 4.0b is itself a no-op whenever the integration branch is not the default branch, and tidy's `parent-gate` backstop recovers those parents later.

## Deliverables

On a non-default integration branch they close nothing, and Step 4.0's post-merge step closes the records itself (Deliverable 2). Keep the reason the composer still writes the lines: they are what closes the records when the integration branch *is* the default, and they travel with the commit when it is later promoted.
2. **`closing-links.js --mode post-merge` closes the Fixes records on a non-default base.** After confirming the PR is `MERGED` with a Fixes span, read the PR's `baseRefName` (add it to the post-merge field list) and the default branch of the PR's own repo (`scope`). When they differ, read each `expected` (Fixes-span) same-repo record's state. For each one still `OPEN`, close it as completed with a comment naming the PR and the base branch, for example `Closed by claude-tweaks: PR #{n} merged into {base}, which is not the default branch, so GitHub does not act on its closing keywords.` Log one `AUTO` line per closed record (reversibility `high (gh issue reopen)`), and one `SKIP ... (degraded)` line per record whose read or close failed, naming the hand-close fallback. Add `closed[]`, `closeFailed[]` and `nonDefaultBase: true` to the post-merge envelope when this path ran. Fold them into the worst-wins `action` so a failed close can never read as `nothing-closed`: `reopen-failed > close-failed > close-pending > reopened > closed > nothing-closed`. On the non-default path, `closingSet[]` is the `expected` records confirmed `CLOSED` (closed by this pass, or found already closed), never `linked`, and never a `closeFailed[]` record. On the default branch the behavior, including `closingSet[]`, is unchanged.

Step 4.0b's exit-0 action list adds `close-failed` and `closed`. Its "no-op unless the integration branch is the default branch" gate is removed for the PR-merge entry: after a PR merge it uses `closingSet[]` as printed on either branch, since on a non-default base that set now holds only records the CLI confirmed `CLOSED`. A `closeFailed[]` record's parent is skipped and named in the closing summary, the same treatment a `failed[]` reopen gets. The no-PR local-merge entry keeps its non-default no-op (Gotchas). Update the post-merge envelope and action-vocabulary text for `closing-links.js` in `docs/plugin-structure.md` and the CLI's own usage/header comment.
4. **Tests.** Add CLI cases to `tests/bin-lib/flow/closing-links-cli.test.js` for: a non-default base with an open Fixes record (closed, `AUTO` logged, `action: closed`, the record in `closingSet`); a non-default base whose close fails (`closeFailed[]`, degraded `SKIP`, `action: close-failed`, the record absent from `closingSet`); a non-default base whose Fixes record is already closed (no close call, record in `closingSet`, not in `closed[]`); a failed default-branch read (no close call, degraded `SKIP`, no `closingSet`); and the default base (no close call, behavior unchanged). Update the usage-string assertion (line ~371) and any prose pins in `tests/closing-links-prose-conformance.test.js` and `tests/below-floor-parent-close-conformance.test.js` that the reworded Step 3, 4.0 and 4.0b text breaks.

## Release Note

Records a run PR fixes now close when the PR merges into an integration branch that is not the repo's default branch, where GitHub would otherwise leave them open.

## Technical Approach

Keep the change inside the existing post-merge pass of `closing-links.js`. It already reads the PR, parses the Fixes span (`expected`), holds a `log`/`degraded` decision-log writer, and returns a worst-wins envelope with `closingSet[]`. Add `baseRefName` to the post-merge `gh pr view --json` field list. Read the default branch once for the PR's own repo (`scope`, from the PR URL), through the injected `deps.gh` runner so the CLI tests can fake it, for example `gh api repos/{owner}/{repo} --jq .default_branch` with the owner and repo filled from `scope`. Here the default branch is the right question (where GitHub's auto-close works), not the integration branch, so this read is not an integration-branch resolution under `_shared/integration-branch.md`. `plugin/bin/lib/merge-verification.js` has a private `readDefaultBranch` doing a similar read, but it shells out directly with no injectable runner and reads the cwd repo, so do not reuse it here. If the default-branch read fails, do not guess: log a degraded `SKIP` naming the unchecked Fixes records, leave them alone, and omit `closingSet[]` rather than closing on an unverified premise.

The non-default close pass runs after the existing keep-open reopen loop, over `expected` only. That set is disjoint from the reopen loop's candidates by construction, so neither pass can undo the other.

### Key Files

- `plugin/bin/closing-links.js` — post-merge: read `baseRefName` and the default branch, close the open Fixes records on a non-default base, build `closingSet[]` from the confirmed-closed Fixes records on that path, add the new envelope fields and actions, update the usage text and header comment
- `plugin/skills/_shared/pr-first-merge.md` — Step 3: correct the closing-keyword claim (lines ~326-334)
- `plugin/skills/_shared/pr-first-merge-post-merge.md` — Step 4.0: describe the close and the `closeFailed[]` report; Step 4.0b: action list, and drop the non-default no-op for the PR-merge entry

- `tests/below-floor-parent-close-conformance.test.js` — prose pins on Step 4.0b, if the rewording breaks them

## Gotchas

- Closing at the integration-branch merge matches `_shared/integration-branch.md`'s definition of that branch, "where finished work lands". The alternative, leaving records open until a later promotion into the default branch closes them through the carried commit messages, depends on a promotion merge that keeps those messages (a squash promotion would not), and that is not guaranteed. A record closed here that a human reopens could be closed again by that promotion. That is accepted and harmless.
- Step 4.0b's non-default no-op exists because the sub-issues stayed open. Once Deliverable 2 closes them and `closingSet[]` holds only confirmed-closed records, leaving the gate and its rationale in place would contradict the new behavior, which is why Deliverable 3 rewrites it rather than leaving the stale sentence in place.
- The no-PR local merge entry of Step 4.0b reads `Fixes #{n}` lines from the pushed merge commit and never runs `closing-links.js`. A local merge pushed to a non-default branch has the same keyword limitation, so that entry keeps its non-default no-op. Closing those records is out of scope here.
- An `armed` outcome never reaches Step 4.0, and the reconciler does not run the CLI. So an `armed` PR that GitHub later merges into a non-default branch still leaves its Fixes records open. That is the same reach gap Step 4.0's existing reopen guard already documents for `armed` PRs. Scope here is the confirmed-`merged` path.
- `tests/integration-branch-conformance.test.js` scans `plugin/skills/**/*.md` only, so the new default-branch read in `plugin/bin/closing-links.js` does not trip it. Any new prose in the two `_shared` files that spells the resolver command must cite `_shared/integration-branch.md` or the test fails. `pr-first-merge-post-merge.md` already names it.
- #4597 (merged) introduced `closingSet[]` and its tests. Read its cases in `closing-links-cli.test.js` (around lines 600-740) before adding the non-default ones, so the new path follows the same fixture shape.
- Related: #4550 is the same non-default-branch blind spot in Step 2.5's `merge-verification` derivation (`plugin/bin/lib/merge-verification.js`). That is a separate fix and file, not folded in here.

pr-first-merge: Fixes lines in the squash commit message do not close records when the integration branch is not the default branch

**Summary:** `_shared/pr-first-merge.md` Step 3 says an explicit merge-commit message makes closing keywords work on any integration branch, but a squash merge into a non-default `develop` whose commit message carried six `Fixes #N` lines closed none of them, and `closing-links.js --mode post-merge` reported `nothing-closed` and left every record open.

**Kind:** Defect

**Repro steps:**
1. Use a repo on a GitHub Enterprise Cloud host (`<org>.ghe.com`) whose default branch is `main`, with `integration-model: pr-first` and `integration-branch: develop`.

3. Run `closing-links.js --mode post-merge` for the PR.

**Expected vs. actual:**
Expected: the six records close, either because GitHub honours the commit-message keywords or because the post-merge step notices records still open after a merge into a non-default branch and closes them (or tells the operator to).
Actual: all six stayed open. The post-merge step reported `nothing-closed` without flagging them, and they had to be closed by hand.

GitHub's documentation says closing keywords only take effect when the commit or PR lands on the default branch, so the claim in `pr-first-merge.md` (around line 331, "an explicit merge commit message is what makes closing work on any integration branch") looks wrong rather than host-specific. When the integration branch is not the default branch, the post-merge step probably needs to close the `Fixes` records itself.

## Plan Review Clarifications

- Decided by the user at plan review: when the PR's base or the repo's default branch cannot be read, the post-merge `action` is a new `base-unchecked`, ranked `reopen-failed > close-failed > base-unchecked > close-pending > reopened > closed > nothing-closed`, so unchecked Fixes records never read as `nothing-closed` (spec: "Fold them into the worst-wins `action` so a failed close can never read as `nothing-closed`").
- Decided by the user at plan review: the base is read before the keep-open reopen loop; on a non-default base the loop reads each candidate once with no will-close polling and reports no `pendingClose`, since nothing the merge carries can close there (spec: "On a non-default base nothing closes").
- The default branch is read with `gh repo view {host}/{owner}/{repo} --json defaultBranchRef -q .defaultBranchRef.name` for the PR's own host, so a GitHub Enterprise Cloud PR (`<org>.ghe.com`) resolves against its own host (spec Original request: "Use a repo on a GitHub Enterprise Cloud host (`<org>.ghe.com`)").
