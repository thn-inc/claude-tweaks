# 4550: pr-first-merge: merge-verification derives off for any non-default integration branch, so a PR merges without waiting for the CI it does run

Surface: infra

## Current State

On a `pr-first` repo whose integration branch is not the default branch (for example `develop`, default `main`), a run PR merges while its own CI is still pending. The field report: a PR workflow runs on PRs into `develop`, `develop` has no branch protection or required checks, `merge-verification` is unset, and the merge went ahead with checks pending. The reporter avoided a blind merge only by waiting for CI by hand and merging with `--match-head-commit`.

Checked against `origin/main` at `d4d40c982`:

- **The derivation returns `off` for any non-default integration branch.** `plugin/skills/_shared/policy-schema-coverage.md` lines ~64-75 (the `merge-verification-derivation` block) and its code twin `plugin/bin/lib/merge-verification.js` `deriveMergeVerification` (lines ~175-203) apply four branches in order. Branch (2) returns `off` when no `.github/workflows/*.yml` has a `pull_request`/`pull_request_target` trigger. Branch (3) returns `merge-when-green` when the integration branch is the default branch. Branch (4) (line ~202, `return target === fallback ? 'merge-when-green' : 'off'`) returns `off` for every other integration branch, even though branch (2) has already established that PR CI exists. Parent #558 chose this as a deliberate opt-in default ("a repo whose long-lived integration branch is non-default opts in with a one-line override"). The code only sees a non-default integration branch through the `integration-branch:` key in `policy.yml` (or a stale `origin/HEAD`), so the repro needs that key set.
- **Under `off`, Step 2.5 does not wait on pending checks.** `plugin/skills/_shared/pr-first-merge.md` Step 2.5 (from line ~111) always reads the PR state (`statusCheckRollup` plus `gh run list --commit {headRefOid}`, line ~151) and classifies it green, pending or red. In the per-value table (lines ~205-207), however, the `off` row's Pending cell is "Step 3 as written". On a repo with no required checks, Step 3's `gh pr merge --auto --squash` either merges immediately (line ~193, the #540 mechanism) or fails with the `Pull request is in clean status` signature (line ~357) and degrades to an immediate `--squash` (lines ~369-378). Both paths merge while checks are pending. The table's own text calls this "the #540-shaped race the lever exists to close", and line ~207 names "a non-default integration branch" as one way a repo derives `off`.
- **Simply flipping branch (4) would park healthy runs.** The workflow scan reads trigger *presence* and ignores `pull_request: branches:` filters. A repo whose workflows run only on PRs into `main` would derive `merge-when-green` for `develop`, and under that value an empty rollup reads as pending (lines ~178-189). Every `develop` PR would then sit through the 15-minute bounded watch and park as `checks-pending-timeout`.
- **The per-run lever cannot tell derived from explicit.** `/claude-tweaks:flow`'s Manifesto writes all 13 lever values into the run's `config.yml` (`plugin/skills/flow/manifesto.md` lines ~167-182), so `resolve-policy.js --run {run-dir} merge-verification` reports `source: run-config` even when the value was derived. Without `--run`, `resolve-policy.js merge-verification` (JSON mode) reports `source: default` when `policy.yml` has no `merge-verification` key, and `source: policy` when it does.
- **Consumers.** Every merge site applies Step 2.5 rather than restating it: `dispatch/settle-and-merge.md`, `flow/worktree-merge.md`, `wrap-up/merge-mode.md`, `wrap-up/auto-merge-short-circuit.md`, `dispatch/resume-confirmation.md`, `dispatch/close-out.md`, and `release/execute.md`. The release path resolves the lever with its own `--values` call (line ~137) but follows Step 2.5's rows apart from five listed deltas, none of which concerns `off`. The express lane overrides `off` to `merge-when-green` (`_shared/express-lane.md`), so it is not affected. Tidy's housekeeping arm bypasses Step 2.5 entirely; that is #4467.

## Release Note

Merges into a non-default integration branch such as `develop` now wait for the PR's own pending checks instead of merging while CI is still running.

## Technical Approach

Fix the merge-time gate, not the derived default. `merge-verification` is a repo-level value computed before any PR exists (the Manifesto, preflight and express lane all resolve it with no PR in hand), and its only CI signal is workflow-trigger presence, which ignores branch filters. Step 2.5 already reads the evidence that matters, the PR's own rollup and head runs, under every lever value. Letting a derived `off` act on *observed* pending checks closes the race without parking repos whose CI never runs on the integration branch. An empty rollup stays green under `off`, because only `merge-when-green`/`wait` can assume CI exists by construction.

Telling a derived `off` from an explicit one takes the project-level read without `--run`, because the Manifesto copies every lever into the run's `config.yml` and the run-level `source` becomes `run-config`. Treat a project-level read failure (non-zero exit, unparseable JSON) as derived: the conservative outcome is a bounded wait, never a blind merge, consistent with Step 2.5's existing "never as `off`" rule for an unreadable lever.

This change is prose only, in the shared gate and the release path. No `bin/` change: `resolve-policy.js` already prints `{value, source}` in JSON mode.

## Gotchas

- **Residual empty-rollup window.** Right after a push, GitHub can take a few seconds to populate the rollup. Under a derived `off` an empty rollup still proceeds, so a merge in that window is not caught. Merge sites usually run well after the last push, and the head-run read (`gh run list --commit`) often shows queued runs earlier than the rollup does. Accepted: closing it would bring back the 15-minute park on repos with no PR CI on the integration branch.
- **Flipping branch (4) was rejected.** It would have read workflow-trigger presence as "CI runs on this branch", which a `pull_request: branches: [main]` filter makes false (Current State). The derivation and its pinned tests stay as they are.

That wording stays: a derived `off` with pending checks no longer reaches Step 3 while pending, and once the watch reads green the `wait` row's green cell merges through Step 3's immediate `--squash` form.
