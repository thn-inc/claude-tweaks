# 6011: Keep driver-routable records out of dispatch's fast-lane bundles

Surface: backend
Risk-flags: public-contract

## Overview

`/claude-tweaks:dispatch` hands a record to the pipeline driver only when the record is a singleton group (`plugin/skills/dispatch/driver-route.md`, Closed rule: "a bundle group → today's path; the route is never consulted"). The queue pull folds every `ceremony:fast-lane` singleton into a fast-lane bundle unless `keepSingleton` keeps it apart, and `keepSingleton` keeps apart only records the express lane would take (`plugin/bin/lib/express/queue.js`). The driver admits a wider set: its own size and Key File bounds (`express-driver-max-size`, `express-driver-max-key-files`), a record beyond the express bounds when its reviewer is on, and no ceremony label at all (`eligibilityOptions`, `plugin/bin/lib/driver/steps.js:277`). Today the two bounds are equal (`express-driver-max-size: low`, 3 Key Files), so no record falls in the gap: on 2026-11-21 all 15 records `drive.js --check` admits came out of a replay of `buildDispatchGroups` as singletons. Pipeline economy Phase 7 raises `express-driver-max-size` to `medium` for its 20-record trial. From then on, a `ceremony:fast-lane` record inside the driver's bounds but outside the express bounds is bundled, and a bundle never reaches the driver.

This record keeps a record the driver would take out of fast-lane bundles whenever `express-driver` resolves `split` or `on`, the same way the express lane keeps its own records out (#4025), so a record the driver's routing, size, Key File and reviewer rules admit reaches `driver-route.md` as a singleton. The driver's other admission checks (build grant, open blockers, open linked PRs, escalation) are not asked here: a record those refuse runs the ordinary path as a singleton instead of inside a bundle (Gotchas).

**Complexity:** Medium
**Estimated tasks:** 4

## Non-Goals

- Routing a member out of a bundle that has already formed at Step 5. Members of a bundle share one branch and one PR (`_shared/issue-claims.md`'s group-claim rule), so the record is kept out when groups are built, not taken out later.
- Changing which records the driver admits. The predicate here asks the driver's own question; it adds no rule of its own.
- Raising `express-driver-max-size` or any other bound in this repository's policy. That is Phase 7.
- The live proof on a real drain (#5571).

## Deliverables

- [ ] `expressQueuePolicy` keeps a `ceremony:fast-lane` record out of bundles when either the express lane would take it (today's rule) or the driver would: `express-driver` resolves `on`, or `split` and the issue number is even; the driver's pure eligibility (`preScreen` with `eligibilityOptions`) passes; and `reviewerGateReason` does not refuse it. The driver half applies whatever `express-lane` resolves, because the driver lane does not need the express lane on (`driver-route.md`'s Closed rule). Inputs: `keyFiles` is `extractKeyFiles(issue)` (`plugin/bin/lib/issues/grouping.js`); `reviewerOn` is `reviewRequired({ issue, keyFiles, policyValue: <express-driver-review> }).on`; `bounds` is `{ sizeCeiling: <express-driver-max-size>, maxKeyFiles: <express-driver-max-key-files> }`. An unreadable input (a `keyFiles` that is not an array, a non-integer issue number under `split`, an `express-driver` value other than `on`, `off` or `split`) never keeps the record: it is bundled.
- [ ] The grouping stamp names the driver half, so a blob computed with it is never reused by a pull without it, and the reverse: a new mode value beside `per-record` and `per-record+express`, never a changed meaning for an existing one. The two new values are `per-record+driver` (driver half on, express lane off) and `per-record+express+driver` (both on).
- [ ] A failed policy read, on either resolver call, makes `expressQueuePolicy` behave as disabled for that pull, as the express half does today: `keepSingleton` is `() => false`, `grouping` is `per-record`, one stderr line names the failed read. With `express-lane` not `true` and `express-driver` `off`, the second call is not made, so a project using neither lane pays no extra policy read.
- [ ] `plugin/skills/dispatch/driver-route.md`'s bundle row states that the queue pull keeps a driver-routable record out of bundles, so a bundle has no member the driver would take.

## Release Note

Records the pipeline driver can build now reach it as their own dispatch group instead of being folded into a fast-lane bundle.

## Technical Approach

The predicate asks the driver's own question so the two can never drift: compose `preScreen(issue, eligibilityOptions(policy), { evaluateRecordEligibility })`, the `split` rule and `reviewerGateReason` with `reviewRequired`'s answer, all already exported and pure. Change `expressQueuePolicy` itself rather than its callers, because the module path and the embedded script both call it and their parity test must stay green.

### Data / API Surface

- `expressQueuePolicy(deps) → { enabled, grouping, keepSingleton }` keeps its shape. `enabled` stays the express half's flag; `keepSingleton(issue)` becomes express-eligible OR driver-routable; `grouping` gains a driver variant from `groupingMode`.
- `groupingMode(expressEnabled, driverEnabled)` gains the second argument; the four combinations map to four distinct stamps (AC12), and `groupingMode(false)` and `groupingMode(true)` keep their current values. `enabled` stays the express half's flag; with only the driver half on, `enabled` is false and `grouping`/`keepSingleton` are the driver variant, so the frozen disabled value applies only when both halves are off.
- Policy keys read with `runDir: null`, in the two calls the function already makes: the first reads `express-lane` and `express-driver` (replacing today's single `express-lane` read); the second, made only when either is on, reads `integration-model`, `merge-sensitive-paths`, `express-driver-max-size`, `express-driver-max-key-files` and `express-driver-review`.

### Key Files

- `plugin/bin/lib/express/queue.js` — the driver half of `keepSingleton` and the grouping stamp
- `plugin/bin/lib/driver/admission.js` — exports `routingReason`, the one `split` rule, with no behavior change
- `plugin/bin/lib/dispatch/queue-order.js` — `groupingMode`'s driver variant
- `plugin/skills/dispatch/driver-route.md` — the bundle row's sentence
- `tests/bin-lib/express/queue.test.js` — ACs 1-7 and 10
- `tests/bin-lib/dispatch/queue-order.test.js` — AC12
- `tests/bin-lib/driver/admission.test.js` — AC11

## Gotchas

- `split` is read through `routingReason` (`admission.js:75-86`), exported by this record and called as is; never a second copy of the even/odd rule.
- Import `eligibilityOptions` from `plugin/bin/lib/driver/steps.js` and `preScreen` from `plugin/bin/lib/driver/budget.js`; edit neither. Both are on many open records' Key Files (#5264, #5321, #5942 among them). `admission.js` changes only by one added export.
- The queue-order blob is shared state that live sessions on older plugin versions also read. A new stamp value is safe for them, since an exact-match reader that meets an unknown stamp recomputes; changing what an existing stamp means is not.
- `expressQueuePolicy` is called up to three times per pull (`queue.js` header comment); the call structure above adds no resolver call. `queue-pull-script.md`'s embedded script calls this same module, so it needs no edit and AC8 only confirms it.
- The predicate asks only part of the driver's admission (routing, size, Key Files, reviewer). A kept record the driver then refuses at `driver-route.md`'s check, or one past `drive.js --budget`, runs the ordinary path as its own singleton and its own PR where a bundle would have shared one. That PR-count cost is accepted: it is bounded by the number of driver-routable records, which Phase 7 raises on purpose.
- A session on an older build groups the same queue under its own rule and stamp. Claims (`_shared/issue-claims.md`) decide which session builds a record, as for any grouping change between versions; the stamp only stops one build from reusing the other's cached order.
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(public-contract): …`.

## Build Deviations (Beneficial)

- A failure to load the driver modules (or `eligibilityOptions` throwing) disables the policy for the pull with its own stderr line, `express-driver: driver modules failed to load, fast-lane bundling unchanged this pull: …`, instead of being reported as a failed policy read; Deliverable 3's failed-read line now names only a read that failed (final-review fix wave, ecdc889f9c).
- With both halves on, the express half runs first and short-circuits when it keeps the record; each half's per-record check has its own try, so a record that throws in both halves writes one stderr line per half (two lines), matching the express half's existing one-line-per-record fallback per half (Task 2, 3db3576b3a).
