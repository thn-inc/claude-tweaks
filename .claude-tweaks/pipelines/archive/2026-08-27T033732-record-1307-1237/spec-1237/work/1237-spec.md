# 1237: wrap-up engine-record.js recordResult/amendResult and wrap-up-engine.js runRecord/runAmend duplicate lookup and parsing logic

Surface: backend

## Current State

`plugin/bin/lib/wrap-up/engine-record.js`'s `recordResult` (line 262) and `amendResult` (line 324)
duplicate three things: the row lookup (`state.results` read, `worklistRows(state.worklist).find(r
=> r.id === payload.rowId)`, "unknown rowId" throw), the `validateDispositionForRow` call, and the
`stored` object's field-picking (`rowId`, `target: row.target`, `result`, `detail`, `findings`,
`read`, `gapDetection` — deliberately never `{ ...payload }`, per the `IL-01` comment on both
functions). `plugin/bin/wrap-up-engine.js`'s `runRecord` (line 185) and `runAmend` (line 224)
similarly duplicate the `engine-state.json`-exists precondition check, the stdin-read-then-`JSON.parse`
block (with its own try/catch and `process.exit(1)` on bad JSON), and the trailing
"read `decisions.md`, print its last line" block.

## Deliverables

Factor the shared logic identified above into named helper functions and have both call sites in
each file use them, while preserving every behavior that currently diverges between the two:

- In `engine-record.js`: a shared helper for row lookup + "unknown rowId" throw + the `stored`
  object's field-picking, used by both `recordResult` and `amendResult`.
- In `wrap-up-engine.js`: shared helpers for the `engine-state.json` existence check, the stdin
  JSON-parse block, and the "print the last `decisions.md` line" block, used by both `runRecord`
  and `runAmend`.

## Acceptance Criteria

- `recordResult` and `amendResult` (`engine-record.js`) share one row-lookup/field-picking helper;
  each function's own divergent behavior is unchanged: `recordResult` still rejects a `row.gate ===
  'closed'` row and an already-recorded `rowId`, still calls `appendTelemetry` (unless `dryRun`),
  and still appends a `SCANNED` `decisions.md` line via `buildScannedLine`; `amendResult` still
  requires the `rowId` to already be recorded (throwing "nothing to amend" otherwise), never calls
  `appendTelemetry`, and still appends an `AMENDED` line via `buildAmendedLine`.
- `runRecord` and `runAmend` (`wrap-up-engine.js`) share helpers for the `engine-state.json`
  existence check, the stdin-JSON-parse block, and the final `decisions.md`-last-line print; each
  command's distinct exit codes are unchanged — exit `2` when `engine-state.json` is missing, exit
  `1` when stdin isn't valid JSON or the underlying `recordResult`/`amendResult` call throws.
- `node --test tests/bin-lib/wrap-up/engine-record.test.js` and the other `wrap-up-*` suites listed
  under `find tests -iname "*wrap-up*"` still pass unmodified — the extraction is behavior-preserving,
  not a functional change.

## Technical Approach

Extract the row-lookup/field-picking logic out of `recordResult`/`amendResult` into a private helper
in `engine-record.js`, and the stdin-parse/precondition/decisions-read logic out of
`runRecord`/`runAmend` into private helpers in `wrap-up-engine.js`. Keep each function's own
divergent branches (already-recorded rejection, telemetry, SCANNED-vs-AMENDED line; exit-code
choice) inline at the call site rather than folding them into the shared helper, so the helper stays
a pure "look up the row" / "read and validate the payload" step and the two callers keep their
distinct control flow.

### Key Files

- `plugin/bin/lib/wrap-up/engine-record.js` — extract the shared row-lookup + `stored`-object
  field-picking logic out of `recordResult` (line 262) and `amendResult` (line 324) into one helper
- `plugin/bin/wrap-up-engine.js` — extract the shared `engine-state.json` precondition check, stdin
  JSON-parse block, and decisions.md-last-line print out of `runRecord` (line 185) and `runAmend`
  (line 224) into helpers
- `tests/bin-lib/wrap-up/engine-record.test.js` — existing coverage that must keep passing unmodified

## Gotchas

- `recordResult` and `amendResult` are intentionally NOT identical: `recordResult` rejects an
  already-recorded row and writes telemetry; `amendResult` requires the row to already be recorded
  and never writes telemetry (the original `recordResult` call already counted it once). The
  extraction must not accidentally collapse these two into one shared code path.
- `runRecord` and `runAmend` intentionally use different exit codes for a missing `engine-state.json`
  (2, a malformed invocation) versus a bad payload (1, so the model retries with a fixed payload) —
  preserve this distinction in any shared precondition/parse helper.
- No dedicated test currently pins the exact duplication between these four functions beyond the
  existing `engine-record.test.js` suite's black-box behavior coverage — run it (and the other
  `wrap-up-*` suites) before and after the extraction to confirm no behavioral drift, per this repo's
  `npm test` re-run guidance for isolating flake from real regressions.
