# 2775: File-overlap-group dispatch builds skip materialize.md's per-record gate; bundle claim log doesn't satisfy bookkeeping-stamp-deny (IL-131)

Surface: infra

Origin: reflect (full mode) from #2269
Defer-reason: needs-human-decision

## Current State

A dispatch-minted, two-call file-overlap-group run (`/flow "#A,#B,..." build,test` then `/flow "#A,#B,..." review,polish,wrap-up`, sharing one `PIPELINE_RUN_DIR`) can reach its second call with `{run-dir}/work/` completely empty and no `config.yml` — `materialize.md` states its per-record Materialization hard gate runs "early (Step 1)... before the pipeline proper starts," but the group build for #2672/#2671/#2655/#2624/#2269 (run `2026-09-22T143002-record-2269`) built and passed test/review on its own merits without ever writing a `work/{n}-spec.md` or `spec-{n}/work/{n}-spec.md` for any of its 5 records.

This left the second call needing to retroactively backfill all 5 records' materialized headers before `wrap-up-pack.js`'s record-resolution ladder would even resolve (`claim`/`ledger`/`recordLabels` probes all failed "records unresolved — no materialized header or manifest found" until the backfill landed).

Separately, but plausibly the same root cause, the materialize-commit push was denied by the `bookkeeping-stamp-deny` gate (IL-131): it requires a literal per-issue `Step 2.8: claimed #{n}` log line, but the group's original claim (the first call's own Step 2.8) logged one free-text `AUTO` entry covering all 5 issues at once — a shape `_shared/issue-claims.md`'s own documented "Group claiming" convention appears to condone (one combined claim-acquisition pass over the whole group), but that this specific enforcement gate's literal per-issue string check does not recognize.

Both gaps cost the affected run an extra round-trip each, and are not one-off: they would recur on every dispatch-orchestrated file-overlap-group bundle built as one atomic commit rather than `/flow`'s standard per-record multi-spec sequential pipeline — which is exactly the shape file-overlap grouping exists to produce (`bin/lib/issues/grouping.js`'s `groupByFileOverlap`).

## Deliverables

Pick one direction (or both, if they turn out complementary rather than redundant):

1. Make `/claude-tweaks:dispatch`'s file-overlap-group build path invoke `materialize.md`'s per-record materialization (writing `spec-{n}/work/{n}-spec.md` for every group member, per `materialize.md`'s documented Multi-record layout) before the first call's own build step runs, so a group build is never missing this audit trail — the same way a normal multi-spec `/flow` run already materializes each record before building it.
2. Make `_shared/issue-claims.md`'s documented group-claim log format literally satisfy `bookkeeping-stamp-deny`'s IL-131 check — either change the group-claim log line to a shape the gate already recognizes (a per-issue `Step 2.8: claimed #{n}` line per group member, even when written in one batched command), or teach the gate to also recognize a single bundle-claim `AUTO` entry naming every issue in the group.

## Acceptance Criteria

- A fresh dispatch-orchestrated file-overlap-group run's second call (`review,polish,wrap-up`) finds `wrap-up-pack.js`'s `claim`/`ledger`/`recordLabels`/`unblocked` probes already resolving records without any retroactive backfill.
- The group build's materialize commit (or its claim-log entry) pushes cleanly on the first attempt — no `bookkeeping-stamp-deny` denial for a group whose claim was genuinely and correctly acquired.
- `npm test` passes in full after the change.

## Release Note

Fixed grouped dispatch builds so every record in the group is materialized and its claim bookkeeping passes.

## Technical Approach

Investigate both directions before committing to one: read `dispatch/SKILL.md`'s file-overlap-group build-call construction to confirm whether it truly skips `materialize.md`'s Step 1 gate (Deliverable 1's premise) or whether materialization runs but writes to a location the second call's resolution ladder doesn't check. Separately, read `bookkeeping-stamp-deny`'s exact check (the gate flagged as IL-131 in the incident log) against `_shared/issue-claims.md`'s documented group-claim log shape to confirm the literal-string mismatch (Deliverable 2's premise). The two deliverables are independent fixes to independent symptoms that happened to surface together in one incident — implementing one does not require the other, but both may be worth doing since both gaps recur on every group build.

## Gotchas

- Both symptoms surfaced together in one incident (run `2026-09-22T143002-record-2269`) but may have independent root causes — verify each premise (materialization truly skipped vs. gate literal-mismatch) before assuming both need the same fix.
- Fixing Deliverable 2 by relaxing `bookkeeping-stamp-deny`'s check must not weaken the invariant IL-131 exists to protect (a genuine claim actually happened) — the fix should recognize the *documented* group-claim shape specifically, not loosen the check generally.
- `npm test` passing (AC 3) is a floor, not sufficient proof the fix works — the real verification is a fresh dispatch-orchestrated group run reaching its second call cleanly, which isn't something the unit-test suite alone can exercise; note this limitation when reporting AC 3 satisfied.
