# 2725: capture: `work-types: native` branch runs `gh issue create --type`, which the current gh CLI rejects

Surface: infra

## Current State

`plugin/skills/capture/SKILL.md`'s `work-types: native` filing branch (line ~199) runs:

```bash
gh issue create \
  --title "$TITLE" \
  --body-file "/tmp/capture-${CLAUDE_CODE_SESSION_ID}-body.md" \
  --type "$TYPE" \
  --label by:capture
```

The filer reported this failed against `gh` 2.92.0 (2026-04-28) with `unknown flag: --type`, requiring a 3-step workaround (create without the flag, GraphQL-lookup the repo's issue types, GraphQL `updateIssue(issueTypeId:)`) — the same fallback mechanism `backlog/refine-record.md`, `specify/shaping-mode-stamping.md`, and `_shared/console-on-pr.md` already use elsewhere in this codebase for the identical native-type-setting need.

**Premise re-check during shaping:** the currently-installed `gh` (2.96.0, 2026-07-02) *does* support `--type` — `gh issue create --help` documents it (`--type name  Set the issue type by name`, with a worked example) and it is not rejected. So the flag was added to `gh` somewhere between 2.92.0 and 2.96.0, after the filer's environment predates it. This means the original bug's specific claim ("gh has no such flag") is no longer universally true — but this plugin ships to many projects' environments, each with whatever `gh` version happens to be installed there, so both "flag exists" and "flag doesn't exist" are live cases in the field, not a closed question this repo's own current `gh` answers definitively.

## Deliverables

- Make the `work-types: native` filing branch tolerant of both `gh` behaviors: attempt `gh issue create ... --type "$TYPE"` first: on success, done (no fallback needed, no wasted GraphQL round-trip on modern `gh`). On failure specifically matching an unknown-flag rejection (not any other `gh issue create` failure — a real auth/network/validation error must still surface as-is, not silently swallowed into the fallback), fall back to today's already-implemented workaround: create without `--type`, then set the native type via the GraphQL `updateIssue(issueTypeId:)` mutation, reusing the exact mechanism `backlog/refine-record.md`/`specify/shaping-mode-stamping.md`/`_shared/console-on-pr.md` already carry (don't reinvent a fourth copy — extract or reference the existing one if it isn't already a shared helper).
- Update `plugin/skills/capture/SKILL.md`'s `work-types: native` branch text to describe this detect-then-fallback shape instead of the current bare `--type` call.

## Acceptance Criteria

- On a `gh` version that supports `--type` (confirmed: 2.96.0), `/claude-tweaks:capture` with `work-types: native` files the issue with its type set in a single `gh issue create` call — no fallback GraphQL calls fire.
- On a `gh` version that rejects `--type` as unknown, the same capture flow still succeeds, ending with the issue's native type set via the existing GraphQL fallback — matching today's (post-workaround) behavior, not a regression.
- A real `gh` auth/network/validation failure on the initial `gh issue create` call is NOT silently absorbed into the unknown-flag fallback path — it surfaces as a genuine capture failure, same as before this record's fix.
- `npm test` passes.

## Release Note

Fixed native issue types failing on the current GitHub CLI when capturing a record.

## Technical Approach

Detect the unknown-flag case from `gh`'s own exit behavior/stderr text for an unrecognized flag (distinct, testable string) rather than version-sniffing `gh --version` — a flag's presence is what actually matters, and sniffing the version string is one more thing to keep in sync with `gh`'s own release cadence. Reuse whichever of the three existing call sites' GraphQL `updateIssue(issueTypeId:)` invocation is most reusable as-is (`backlog/refine-record.md`, `specify/shaping-mode-stamping.md`, or `_shared/console-on-pr.md`) rather than writing a fourth copy of the same mutation.

### Key Files

## Gotchas

- Don't assume the currently-installed `gh` version's behavior (flag works) generalizes to every consuming project's environment — this plugin ships broadly, and the filer's own repro (gh 2.92.0) is real evidence the flag was absent in a recent-enough release to still be in the field.
- Distinguish an unknown-flag rejection from every other `gh issue create` failure mode carefully — a broad catch-and-fallback would mask real auth/network/validation errors as if they were a version-compatibility issue.
