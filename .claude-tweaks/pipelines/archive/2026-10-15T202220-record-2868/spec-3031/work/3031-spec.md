# 3031: dispatch: Step 5's group worktree is not based on the integration branch (`EnterWorktree(name:)` takes no base ref)

Surface: infra

## Current State

`/claude-tweaks:dispatch` Step 5 (`plugin/skills/dispatch/SKILL.md:227`) has the dispatching session create and enter each group's worktree "via `/superpowers:using-git-worktrees`, exactly as a normal `/claude-tweaks:flow` invocation would", which ends in `EnterWorktree(name:)`. `plugin/skills/_shared/worktree-base-ref.md:15` documents that `EnterWorktree` has no base-ref parameter. What it branches from depends on the harness setting:

- Under `worktree.baseRef: fresh`, it branches from `origin/<default-branch>`.
- Under `head`, it branches from the session's current HEAD. For group N+1 in a multi-group drain that is group N's own branch, because the dispatching session is still in group N's worktree.

The dispatched `/flow` then runs `plugin/skills/_shared/worktree-setup.md`'s post-creation catch-up, which only *merges* `origin/{integration-branch}`. It never rebases, and flow forbids resetting.

Observed case: a pr-first project whose integration branch is `develop`, where `origin/main` is not an ancestor of `origin/develop`, with a headless drain under `baseRef: fresh`. The group's worktree branched from `origin/main` and kept 19 main-only commits after catch-up. The headless ride-along check (`_shared/worktree-setup.md:172`, #1780) counted them in `origin/{integration-branch}..HEAD` and stopped the run, and the branch had to be hand-reset. Without that check, those commits would have ridden into the PR.

A cwd-pinned dispatching session already creates group worktrees with a plain `git worktree add` (`plugin/skills/dispatch/sequential-execution.md:18`, #447). That is the same mechanism the fix generalizes.

`plugin/skills/dispatch/SKILL.md` is 46,053 bytes, against `CEILING_BYTES` = 46,080 (`bin/lib/skill-audit/context-cost.js`, pinned by `tests/timing-prose-conformance.test.js:55`). That leaves 27 bytes of headroom.

## Deliverables

   - From the main checkout, as separate single-command calls: `git fetch origin {integration-branch}`, then `git worktree add .claude/worktrees/{name} -b worktree-{name} origin/{integration-branch}`. `{integration-branch}` comes from `_shared/integration-branch.md` and `{name}` from `build/worktree-setup.md`'s Worktree name derivation.
   - Then `EnterWorktree(path: ".claude/worktrees/{name}")`, never `EnterWorktree(name:)`, with the base-ref reason.
   - A `git worktree add` that fails because the path or branch already exists maps onto `sibling-session-check.md`'s Worktree-resume skip.
   - A cwd-pinned dispatching session runs the same `git worktree add` and skips only the `EnterWorktree`.
2. Rewrite Step 5's worktree-creation clause in `plugin/skills/dispatch/SKILL.md` to point at that section. It says the worktree is based on `origin/{integration-branch}` and never created with `EnterWorktree(name:)`, and it drops the "exactly as a normal `/claude-tweaks:flow` invocation would" phrasing. Net bytes added to SKILL.md must keep the file at or under `CEILING_BYTES`.

## Release Note

Fixed headless dispatch so each group's worktree starts from the integration branch, not the default branch or the previous group's branch.

## Technical Approach

The root cause is that `EnterWorktree(name:)` cannot take a base, so the base has to be set before entry. Creating the worktree explicitly with `git worktree add … origin/{integration-branch}` and then joining it by path is the minimal mechanism that fixes this under both `fresh` and `head`, and the cwd-pinned dispatcher path already uses it (#447). The reporter considered and deferred the alternative: let catch-up rebase a fresh branch with no commits of its own when HEAD is not an ancestor of the integration branch. That would also fix interactive `/flow`, but it collides with flow's "never reset or discard" rule, so it is a maintainer design decision and out of scope here. The procedure goes in `sequential-execution.md` rather than SKILL.md because SKILL.md has almost no room left under the context-cost ceiling. The original request below carries the reporter's diff.

### Key Files

- `plugin/skills/dispatch/sequential-execution.md` — new "Creating the group's worktree" section
- `plugin/skills/dispatch/SKILL.md` — Step 5 clause rewritten to link it, within the byte ceiling
- `tests/dispatch-sequential-execution-conformance.test.js` — Step 5 + new-section conformance test

## Gotchas

- SKILL.md has only 27 bytes of headroom (46,053 of 46,080). The reporter's diff adds about 83 bytes and was written when the file was already over the limit, at 46,442. Measure with `wc -c` after editing. The replacement clause must be no longer than the text it removes, or trim elsewhere in Step 5.
- Separate single-command calls are mandatory in this repo's worktree sessions. Compound `&&` Bash is refused, so keep the fetch and the `worktree add` as two fences.
- Out of scope, flagged by the reporter: interactive `/claude-tweaks:flow` has the same base problem through `build/worktree-setup.md`'s `EnterWorktree(name:)` path whenever the integration branch differs from the default branch. Fixing that needs a design decision on rebasing in catch-up versus the never-reset rule, and it belongs in its own record.
- This project itself runs `worktree.baseRef: head` (`_shared/worktree-setup.md:172`), so the observed symptom here would be group N+1 inheriting group N's branch rather than main-only commits. The fix covers both.
