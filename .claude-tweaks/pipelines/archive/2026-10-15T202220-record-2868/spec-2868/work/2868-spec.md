# 2868: Dispatch headless self-report: detection-ladder-check3-gh-unreachable

Surface: infra

## Current State

A scheduled `/claude-tweaks:dispatch` bare-drain Routine running v6.131.0 stopped at Preflight in a cloud sandbox class with these properties:

- `gh` is installed.
- `gh api` REST calls work. `gh api user` succeeds, so the token is valid.
- Every GraphQL-backed `gh` subcommand fails with `HTTP 403: GitHub GraphQL is not available from Claude Code sessions; use the REST API …`. This was observed for `gh repo view --json owner,name` and `gh issue list`.
- The `mcp__github__*` tools work.

The gap still exists in this repo (checked against the tree):

- `plugin/skills/_shared/forge-detection.md:11` defines check 3 as `gh repo view --json owner,name` exits 0. That command is GraphQL-backed.
- `plugin/skills/dispatch/SKILL.md:78-88` selects the transport on check 2 alone: "`gh` present → proceed exactly as always; `gh` absent → proceed via the GitHub MCP path documented in `mcp-transport.md`". Check 3 is then a hard gate on whichever transport was selected.
- `plugin/skills/dispatch/mcp-transport.md:16-24` gives check 3 an MCP equivalent (a bounded `list_issues` probe), but only for the `gh`-absent case.

So in a sandbox where `gh` is present but GraphQL is blocked, the firing takes the `gh` transport, fails check 3, and has no legal path to the MCP transport, even though that transport is already built and reachable.

## Deliverables

1. Add a third transport-selection outcome to dispatch's Preflight: **`gh` present but GraphQL blocked**. Detect it when check 3's `gh repo view` probe fails with the GraphQL-unavailable signature. Match `GitHub GraphQL is not available`, not every non-zero exit, so a real auth or reachability failure still hard-stops as it does today. When detected, select the MCP transport (`mcp-transport.md`) for the rest of the firing and evaluate check 3 with its existing `list_issues` probe.
2. Document the new branch in `dispatch/SKILL.md`'s Preflight paragraph and in `mcp-transport.md`'s Preflight sections. Update `_shared/forge-detection.md`'s check-3 row to say that dispatch routes the GraphQL-blocked signature to MCP, while its fail-open consumers (`/help`, `/tidy`) are unchanged.
3. Log the transport choice to the firing's `decisions.md` (an `AUTO` entry naming the GraphQL-blocked signature) so a later reader can tell this firing took the MCP path deliberately.

## Acceptance Criteria

- With `gh` on PATH and a `gh repo view` failure whose stderr contains `GitHub GraphQL is not available`, dispatch Preflight selects the MCP transport and does not stop. A prose conformance test pins the branch and the exact signature string.
- With `gh` on PATH and a `gh repo view` failure without that signature (for example, an unauthenticated token), Preflight still stops on check 3 and files the headless self-report as it does today.
- `gh`-absent behavior is unchanged.
- `npm test` passes in full.

## Technical Approach

The record offered two alternatives: (a) make check 3 REST-only (`gh api repos/{owner}/{repo}`), or (b) route the GraphQL-blocked case to the MCP transport. This record chooses (b), and the evidence in the record itself settles it. `gh issue list`, which dispatch's queue pull depends on, fails with the same 403. So (a) alone would only move the failure from check 3 to Step 2's queue pull. The MCP transport already covers every dispatch call site (`mcp-transport.md:26-34`, "every call site that used to be `gh`-only end to end … now has a confirmed, live-verified MCP path"), so (b) reuses a tested path instead of building a REST bridge.

## Dispatch Preflight — Detection Ladder check 3 failed

`/claude-tweaks:dispatch next` (scheduled Routine, headless/bare drain form) stopped at Preflight because check 3 of `_shared/forge-detection.md`'s three-check ladder fails in this sandbox class.

**Check 1 (GitHub remote exists):** pass — `origin` resolves to `https://github.com/thomasholknielsen/claude-tweaks`.

**Check 2 (gh CLI installed):** pass — `gh version 2.89.0 (2026-03-26)` is present, so Preflight's branch logic selects the `gh` CLI transport (never loads `dispatch/mcp-transport.md`'s gh-absent fallback).

**Check 3 (`gh repo view --json owner,name` exits 0):** FAILS.

```
$ gh repo view --json owner,name
HTTP 403: GitHub GraphQL is not available from Claude Code sessions; use the REST API (gh api repos/{owner}/{repo}/...). For review threads, auto-merge, and draft/ready-for-review use the CCR routes on api.github.com: GET /repos/{owner}/{repo}/pulls/{n}/ccr/review_threads, POST /repos/{owner}/{repo}/pulls/{n}/ccr/comments/{comment_id}/resolve (or /unresolve), PUT or DELETE /repos/{owner}/{repo}/pulls/{n}/ccr/auto_merge, POST /repos/{owner}/{repo}/pulls/{n}/ccr/ready_for_review, POST /repos/{owner}/{repo}/pulls/{n}/ccr/convert_to_draft. (https://api.github.com/graphql)
```

This is not an ordinary auth failure — `gh auth status` also fails ("token in GH_TOKEN is invalid"), but `gh api user` (a plain REST call) succeeds and confirms the token is in fact valid, authenticated as `thomasholknielsen`. `gh issue list` (also GraphQL-backed) fails identically to `gh repo view`. The sandbox's outbound proxy appears to hard-block GitHub GraphQL calls specifically, redirecting callers to the REST API / CCR routes instead, while leaving REST-based `gh api ...` calls and the `mcp__github__*` tools (confirmed working this firing — used to search for and file this very report) fully functional.

**Gap this exposes:** `dispatch/SKILL.md`'s Detection Ladder only branches on "gh absent" vs. "gh present and working" (check 2's own doc: "gh present → proceed exactly as always; gh absent → proceed via the GitHub MCP path"). There is no branch for "gh present, authenticated via REST, but GraphQL-dependent subcommands blocked by sandbox policy" — a class this environment falls squarely into. As written, this firing has no legal path forward: it can't use the gh CLI transport (check 3 hard-fails) and isn't allowed to fall back to the MCP transport (gh isn't "absent").

**Suggested fix (for a human to evaluate, not applied here):** either (a) make check 3 REST-only — e.g. `gh api repos/{owner}/{repo}` in place of `gh repo view --json owner,name`, which uses GraphQL internally — or (b) extend check 2's branch condition so a GraphQL-signature failure on check 3 also routes to the already-built MCP transport, since `mcp__github__*` tools are confirmed reachable in this same sandbox.
