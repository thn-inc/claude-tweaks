# 1373: changelog-coverage.test.js false-blocks stale feature branches when origin/main ships mid-firing

Origin: reflect (full mode, from #808)
Defer-reason: tangential

## Current State

`tests/changelog-coverage.test.js` compares the local working tree's `docs/shipped-versions.tsv`/`CHANGELOG.md` against a live `git fetch origin main` walk. A long-running worktree branch created before a later `main` release will always fail these two assertions until it rebases, even though the branch's own diff never touches a changelog/version file. This has now been independently confirmed and accepted twice in the same firing — #800's ledger (`docs/plans/2026-08-24-compose-record-cli-ledger.md` item #2, for version 6.105.0) and #808's own ledger (`docs/plans/2026-08-24-record-808-demo-validate-precondition-ledger.md` item #1, for version 6.106.0) — each requiring a fresh `git fetch origin main` + isolated `node --test` investigation to confirm the failure is pre-existing drift, not a real regression, before it could be accepted on the test gate.

## Deliverables

- Either: teach the test (or the gate that runs it) to recognize "this branch's base predates the missing version" and downgrade to a non-blocking warning automatically, so a stale worktree doesn't need a fresh per-session investigation every time; or, short of a code change, add one sentence to CLAUDE.md's test-run guidance (near the existing "failure count that varies run-to-run" note) naming this specific pattern by name, so a future session recognizes it in one read instead of re-deriving the same fetch-and-diff-isolation proof from scratch.

## Acceptance Criteria

- A worktree branch based on an older `main` release no longer needs a fresh investigation to accept this exact failure class — either the gate self-recognizes it, or CLAUDE.md names it explicitly enough that a session can cite the existing pattern instead of re-proving it.
