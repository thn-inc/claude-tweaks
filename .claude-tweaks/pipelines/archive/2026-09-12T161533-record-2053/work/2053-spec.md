# 2053: process.exit() after a pending stdout/stderr write in health-core library functions (churn-report.js, mark.js, retry-cli.js) -- same truncation risk #1903's guard-scoped check doesn't cover

Surface: backend

## Overview

Three `plugin/bin/lib/health-core/*.js` shared library functions call `process.exit()` directly after a pending stdout/stderr write, invoked from deep inside all four health-suite CLIs' (`code-health.js`, `harness-health.js`, `journey-health.js`, `docs-health.js`) own correctly-guarded `main()` — outside `#1903`'s new `exit-code-conformance.test.js`, which by design scopes only to a file's own `require.main === module` entry-point guard and does not follow the call graph into library functions a guard invokes. Same truncation risk class as #1176/#1313/#1535/#1903, one level removed from the guard.

**Design resolved before shaping (the record's own open Deliverables choice):** fix the three call sites directly rather than extend the mechanical check to be call-graph-aware. All four CLIs' `main()` functions already use the established `process.exitCode = N; return;` pattern everywhere else in the same files (confirmed by reading `code-health.js`'s `main()`, ~lines 38-195) — converting these three functions to return an exit code instead of exiting directly is a small, in-pattern refactor, not a new convention. Building genuine call-graph analysis into a mechanical text/regex-based scan would be materially more complex and fragile than the direct fix, for a bug class with exactly three known instances.

For the "prevent recurrence" half (AC2 below), a scoped mechanical rule is enough: no file under `plugin/bin/lib/health-core/**` may call `process.exit()` directly. Checked against every other `process.exit()` call site in `plugin/bin/lib/` today (`grep -rn "process\.exit(" plugin/bin/lib/`) — the only other hits are in `plugin/bin/lib/statusline-wrapper-source.js`, which is a guard-less whole-script file (no `require.main` guard, no `module.exports`) already correctly covered by #1903's own existing carve-out ("a guard-less file with no `module.exports`, treated as the whole script") — so a `health-core/**`-scoped rule has zero false positives against the current tree and needs no exemption list.

## Non-Goals

## Technical Approach

Mirror the existing `process.exitCode = N; return;` convention already used throughout all four CLIs' `main()` functions rather than introducing a new signaling shape — the three library functions become ordinary value-returning functions (return a numeric code or `undefined`), and each caller applies that value to `process.exitCode` exactly like every other branch already does. The scoped conformance-test addition is a flat directory sweep (`plugin/bin/lib/health-core/*.js`, checked for the literal `process.exit(` substring/regex, same class of check `#1903`'s existing test already performs), not a call-graph walk — kept simple because the failure class here doesn't need more than "these specific shared files must never exit directly."

## Current State

`plugin/skills/gh-api-module-pattern/SKILL.md`'s CLI wrapper contract documents the `require.main === module` guard rule (`process.exitCode = ...`, never `process.exit()` directly) because `process.exit()` immediately after a pending stdout write can truncate that write for a piped consumer. #1903 just added `tests/bin-lib/exit-code-conformance.test.js`, a mechanical scan for this pattern -- but by design it scopes only to each file's own `require.main === module` entry-point guard (or a guard-less file with no `module.exports`, treated as the whole script). It deliberately does not follow the call graph into library functions a guard invokes.

Three `plugin/bin/lib/health-core/*.js` library files (shared across the four health-suite CLIs -- `code-health.js`, `harness-health.js`, `journey-health.js`, `docs-health.js`) each export a function that calls `process.exit()` directly after a stdout or stderr write, invoked from deep inside those CLIs' own (correctly-written) `main()` flow -- outside any entry-point guard, so `#1903`'s new test cannot see them:

- `plugin/bin/lib/health-core/churn-report.js` line 47: `process.stdout.write(...); process.exit(1);` -- writes a churn table to stdout, then exits immediately when the `--fail-on-high-churn` threshold is exceeded. Line 23 has the same pattern on the stderr usage-error path (`process.exit(2)`).
- `plugin/bin/lib/health-core/mark.js` line 36: `process.stderr.write(...); process.exit(2);` on a usage error.
- `plugin/bin/lib/health-core/retry-cli.js` lines 29 and 36: same stderr-then-exit pattern on two usage-error paths.

This is exactly the class of bug #1176/#1313/#1535/#1903 have been closing one instance at a time -- just one level removed from the guard itself, in a spot the new mechanical check's scope (by design, per its own record's literal deliverable text) does not reach.

## Deliverables

- Decide whether the mechanical check's scope should extend to library functions invoked from an entry-point guard (a call-graph-aware check), or whether these three call sites should instead be fixed directly (buffer the output and return a value for the guard to act on, e.g. `process.exitCode = ...` in the CLI's own `main()`, rather than exiting deep inside the library function) -- a product/design call on how far the mechanical check's contract should reach.
- Whichever direction is chosen, fix the three call sites (`churn-report.js:23,47`, `mark.js:36`, `retry-cli.js:29,36`) so they no longer call `process.exit()` after a pending write.

## Acceptance Criteria

1. None of `churn-report.js`, `mark.js`, `retry-cli.js` call `process.exit()` after a stdout/stderr write reachable from any of the four health-suite CLIs' own entry-point guard.
2. Whatever mechanical or manual check is chosen to prevent recurrence is documented in `gh-api-module-pattern/SKILL.md` or a follow-up to `exit-code-conformance.test.js`.
