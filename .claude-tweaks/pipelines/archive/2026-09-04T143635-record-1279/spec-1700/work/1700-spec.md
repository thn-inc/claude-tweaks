# 1700: Health-sweep issue-fingerprint dedup silently breaks on gh-absent (MCP) transport — GitHub MCP server strips HTML comments from issue bodies

Surface: infra

## Current State

`_shared/health-issue-index.md` and `_shared/github-write-transport.md` document the `gh`-absent fallback for a health sweep's issue-index rebuild: use `mcp__github__list_issues` (or `issue_read get`), project into `{ number, state, labels, fingerprint }`, and `bin/lib/health-core/issue-index.js`'s `loadIssueIndex` keys a lookup map by each entry's `fingerprint` field. That field is only ever populated by extracting the `<!-- work-fingerprint: {id} -->` HTML comment embedded in the issue body (`bin/lib/issues/record.js`'s `extractFingerprint`, regex `FP_RE_WORK`).

Verified live during a real firing (2026-08-30): fetched all 14 `by:docs-health` issues via both `mcp__github__list_issues` (labels filter, no state filter) and `mcp__github__issue_read` (`get` method, issue #1637 specifically) — every returned `body` has its `<!-- work-fingerprint: ... -->` HTML comment stripped. None of the 14 bodies contain any `<!--`-prefixed span at all, despite `gh`-based reads of the same issues (per this project's own filing convention) always appending that marker as the literal last line of the body.

This is the same root cause `_shared/pr-early-run-lifecycle.md` already documents for PR bodies (`pkg/github/minimal_types.go`'s `convertToMinimalPullRequest` calls `sanitize.Sanitize()`, whose `bluemonday.StrictPolicy()` strips every `<!-- ... -->` span as a prompt-injection defense) — but that file's "Root cause" section scopes the finding to PR reads only. The same sanitization evidently also applies to issue reads (`list_issues`/`issue_read`), which that file does not mention and which none of the four health-sweep skills' dedup logic accounts for.

**Consequence:** on any `gh`-absent firing (the default in a cloud Routine sandbox) of `/claude-tweaks:docs-health`, `/claude-tweaks:harness-health`, or `/claude-tweaks:journey-health`, `loadIssueIndex` receives an issue array where every `fingerprint` is null/undefined, so its `if (issue.fingerprint)` guard populates an empty map regardless of how many matching issues already exist open. Every finding's `decide()` call then has nothing to match against by fingerprint, so a finding identical to one already filed and still open will file again as a duplicate rather than being suppressed — silently, with no error, on every headless firing. This is the same failure class as #163 (which fixed the empty-vs-unavailable-index distinction) but via a different mechanism: here the index fetch *succeeds* and *is* non-empty, it just carries no usable fingerprint data.

The originating run avoided actually filing a duplicate only because manual inspection of all 14 fetched bodies' visible text (title + Doc/Section fields, still present) confirmed none referenced that run's target doc — that manual cross-check is not a substitute for the fingerprint match and does not scale to a large open-issue count.

## Deliverables

Adopt the same fix `_shared/pr-early-run-lifecycle.md` already specifies for PRs: a plain-text companion form of the fingerprint marker that survives HTML-comment stripping, written alongside the existing HTML-comment form on every health-sweep issue body (the write path is unsanitized on both transports, so writing both costs nothing), with the `gh`-absent read path (the MCP `list_issues`/`issue_read` projection step in each of the four health sweeps' GATHER OPEN ISSUES instructions, and `bin/lib/issues/record.js`'s `extractFingerprint`) taught to key on the plain-text form when the HTML-comment form comes back stripped.

## Acceptance Criteria

1. `_shared/pr-early-run-lifecycle.md`'s "Root cause" section (or a shared successor) documents that MCP body sanitization strips HTML comments from issue reads (`list_issues`, `issue_read`) as well as PR reads, with the same live verification method used to discover this.
2. Health-sweep issue bodies carry a plain-text companion fingerprint marker alongside `<!-- work-fingerprint: {id} -->`, written on every transport.
3. `extractFingerprint` (or the health-sweep GATHER OPEN ISSUES step that calls it) recovers a usable fingerprint from an MCP-fetched, comment-stripped body via the plain-text companion.
4. A `gh`-absent dedup test (fixture: an MCP-shaped issue list with comments stripped, matching an existing filed finding) demonstrates the finding is now suppressed rather than re-filed.

## Technical Approach

Reuse `_shared/pr-early-run-lifecycle.md`'s already-specified plain-text companion marker pattern rather than inventing a new mechanism for issues: extend `bin/lib/issues/record.js`'s fingerprint-write path to also emit a plain-text companion line alongside the existing `<!-- work-fingerprint: {id} -->` HTML comment, and extend `extractFingerprint` to fall back to parsing that plain-text form when the HTML-comment form is absent from a fetched body (the MCP-stripped case). Update each of the four health-sweep skills' GATHER OPEN ISSUES sections so their `gh`-absent MCP projection step reads the plain-text companion when the HTML-comment marker comes back stripped. Document the extended (PR + issue) scope of the sanitization root cause in `_shared/pr-early-run-lifecycle.md` and/or `_shared/health-issue-index.md` / `_shared/github-write-transport.md`.

### Key Files

- `bin/lib/issues/record.js` — fingerprint write (`extractFingerprint`, `FP_RE_WORK`) and the new plain-text companion emit/read logic
- `plugin/skills/code-health/SKILL.md` — GATHER OPEN ISSUES step, MCP projection fallback
- `plugin/skills/harness-health/SKILL.md` — GATHER OPEN ISSUES step, MCP projection fallback
- `plugin/skills/journey-health/SKILL.md` — GATHER OPEN ISSUES step, MCP projection fallback
- `plugin/skills/docs-health/SKILL.md` — GATHER OPEN ISSUES step, MCP projection fallback
- `plugin/skills/_shared/health-issue-index.md` — documents the `gh`-absent fallback and `loadIssueIndex` fingerprint keying
- `plugin/skills/_shared/github-write-transport.md` — CRUD mapping and sanitization notes
- `plugin/skills/_shared/pr-early-run-lifecycle.md` — "Root cause" section to extend from PR-only to PR+issue scope

## Gotchas

- The write path is unsanitized on both transports (confirmed by this record's own evidence), so writing the plain-text companion alongside the HTML comment costs nothing and is safe to do unconditionally, not just as a gh-absent-specific branch.
- `bin/lib/health-core/issue-index.js`'s `loadIssueIndex` currently trusts a present-but-empty fingerprint silently (`if (issue.fingerprint)`) — the fix should not regress the already-fixed #163 empty-vs-unavailable-index distinction while closing this separate stripped-fingerprint gap.
