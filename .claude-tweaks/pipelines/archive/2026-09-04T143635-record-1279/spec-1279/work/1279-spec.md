# 1279: Materiality digest: no defer-reason vocabulary for direct-filing sweeps, no dedup, no summary surfacing

Origin: review
Defer-reason: genuinely-larger

The materiality digest mechanism (`_shared/materiality-floor.md`, shipped by #1261) has three gaps only surfaced once real adopters (#1262) started routing findings to it — none fixable within #1262's own scope since #1262's Non-Goals bar changing the contract itself, and two require actual code (not prose).

## Current State

#1262's final whole-branch review (spec #1262, "Migrate the ten adopter files to cite `_shared/materiality-floor.md`") found:

1. **No `Defer-reason:` vocabulary for the four health sweeps' digest entries.** `_shared/materiality-floor.md`'s Entry format makes `Defer-reason: {value}` a mandatory field, and that value's vocabulary is defined by `_shared/deferral-gate.md` — but `code-health`, `docs-health`, `harness-health`, and `journey-health` never run through the deferral gate at all (they file spec-shaped issues directly via `recordPayload`/`specShapedBody`, per #1262's own Current State: "These do NOT cite the deferral gate"). There is no defined value these four sweeps can legitimately write into a materiality-digest entry's `Defer-reason:` field. #1262's own citations correctly route below-floor health-sweep findings to the digest, but leave this field unaddressed — an agent executing the sweep has no well-formed value to write.

2. **No dedup on materiality digest entries — spurious promotion after repeated firings.** The pre-existing per-origin cap digest (`_shared/health-filing-digest.md`) solves this explicitly via a fingerprint fold (`expandDigestFingerprints`) that lets a re-encountered finding dedupe against its own existing digest entry instead of re-appending. The materiality digest has no equivalent — `tidy/digest-sweep.md` has no dedup step of its own. A below-floor finding that a scheduled health sweep re-encounters on every firing gets a fresh entry appended each time; `digest-sweep.md`'s own cluster-promotion procedure fires once ≥3 entries share the same `{area}` — so a genuinely low-value, repeatedly-recurring finding becomes a first-class issue after 3 firings, inverting the contract's entire purpose (reducing issue volume for low-materiality findings).

3. **The digest comment URL and `filed/digested/cap` accounting never reach any adopter's own summary.** `_shared/materiality-floor.md`'s Deliverables state "the run's single digest comment URL... appears once in the caller's own summary output," but none of the ten adopter files' report/handoff/summary formats were updated to actually surface it, and the four health sweeps' existing `filed: N, digested: M, cap: {CAP}` throttle line (from the pre-existing cap-digest mechanism) does not count materiality-digest routings at all — so a run's actual digest activity is invisible in every caller's own output.

## Deliverables

- [ ] Decide and document a `Defer-reason:` (or equivalent) vocabulary answer for direct-filing producers (the four health sweeps today; possibly other future non-gate-routed adopters) — either extend `bin/lib/issues/record.js`'s closed `DEFER_REASONS` set with a value describing "no deferral gate applies, filed directly by a proactive sweep," or define an explicit, contract-stated exception in `_shared/materiality-floor.md` for this producer class.
- [ ] Design and implement a dedup mechanism for materiality digest entries — likely a fingerprint-based fold analogous to `_shared/health-filing-digest.md`'s `expandDigestFingerprints`, reconciled with `tidy/digest-sweep.md`'s existing cluster-promotion threshold so a genuinely-recurring-but-still-low-value finding does not spuriously promote.
- [ ] Wire the digest comment URL and a digest-specific count into each adopter's own summary/report format — likely ten distinct small edits (one per adopter's own summary shape) plus updating the four health sweeps' `filed/digested/cap` line to also report materiality-digest routings separately from cap-digest routings.
- [ ] `tests/materiality-floor-conformance.test.js` and/or a new suite covering the dedup mechanism and vocabulary answer once designed.

## Acceptance Criteria

1. A health-sweep-originated materiality digest entry has a well-formed `Defer-reason:` (or documented equivalent) value, with a test pinning it.
2. Re-running a sweep against an already-digested, unchanged finding does not append a second entry, and does not contribute toward cluster-promotion's ≥3 threshold a second time.
3. At least one adopter's own summary output surfaces the run's digest comment URL when a digest routing occurred this run; the four health sweeps' throttle line reports a materiality-digest count distinct from the cap-digest count.
4. `npm test` passes.
