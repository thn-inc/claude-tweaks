# 2625: Add GDPR account-deletion vs. backup-retention check

Surface: infra

## Current State
Deleting a user from the production database on account deletion leaves their personal data intact in rolling database backups (e.g. a 30-day retention window), which can violate GDPR right-to-erasure. Rewriting, decrypting, and recompressing terabytes of backup data to scrub one user on every deletion request is operationally expensive and can overwhelm production systems. Cryptographic erasure — encrypting each user's sensitive data with a unique per-user key and destroying only that key on deletion — makes the backup copy unreadable without ever touching the backup itself. This project's pre-launch security hardening checklist (#2624, open, priority:medium) is being built for AI-built apps but currently has no check for this specific data-retention/right-to-erasure gap.

Update (shaping, 2026-09-30): #2624 has shipped as `plugin/skills/_shared/criteria-security-hardening.md`, and its "Scope boundary" section explicitly excludes this check. It therefore lands standalone, in the `privacy-pii` criterion.

## Deliverables
1. Add a data-retention/right-to-erasure check — as a new row in the pre-launch security checklist being built under #2624, or as its own standalone policy row if #2624 lands first without this scope — that flags whether the app's backup/retention strategy leaves deleted users' data readable, and whether per-user field-level encryption is in place for data that lands in backups.
2. Document the cryptographic-erasure pattern (per-user key encryption + key destruction on deletion) as the recommended fix when a project keeps rolling backups containing user PII.
3. Ship a copy-paste prompt, matching this pipeline's existing pattern for this class of check, that walks a codebase through checking for this specific gap.

## Acceptance Criteria
1. Running the check against a sample app flags whether a deleted user's data would remain readable in existing backups after an account-deletion flow runs.
2. The shipped documentation/policy content notes its relationship to the pre-launch security checklist (#2624) so the two records' scope doesn't duplicate — whichever lands first, the other references it rather than re-deriving the same check.
3. The check (and its copy-paste prompt) works standalone and as a step within `/claude-tweaks:review` or a security-review pass.
4. The documented recommended-fix pattern (cryptographic erasure) is described generically enough to apply across storage backends, not tied to one specific database or cloud vendor's backup product.

## Release Note

Added a privacy check that flags when deleted users' data stays readable in backups, with a cryptographic-erasure fix pattern.

## Technical Approach

#2624 has shipped (`plugin/skills/_shared/criteria-security-hardening.md`) and its Scope boundary explicitly excludes this check, so it lands standalone in `plugin/skills/_shared/criteria-privacy-pii.md` — the generalist `privacy-pii` criterion (`criteria.js`) that already applies to frontend/backend/data areas. Add a "What to flag" bullet for the concrete code pattern (an account-deletion path that removes live rows while backups keep plaintext PII, with no per-user key to destroy), a severity-calibration entry, and a copy-paste prompt in the style of criteria-security-hardening.md's "Copy-paste prompts" section. Document cryptographic erasure (per-user key encryption, key destruction on deletion) generically as the recommended fix. Repoint criteria-security-hardening.md's Scope boundary bullet at the new home.

## Gotchas

- Keep the fix pattern vendor-neutral (acceptance criterion 4).
