# 1323: teardown-run doubles the .claude-tweaks path when --run already points at archive/

Surface: backend

## Current State

`plugin/bin/lib/hooks/teardown-run.js` derives the main-checkout root from the passed `--run`
path with fixed relative arithmetic:

```js
const root = path.resolve(runDir, '..', '..', '..'); // {root}/.claude-tweaks/pipelines/{run-id}
```

This assumes `runDir` is always exactly `{root}/.claude-tweaks/pipelines/{run-id}` (3 levels below
root). When `--run` instead points at an **already-archived** run — `{root}/.claude-tweaks/pipelines/archive/{run-id}`,
4 levels below root — the same arithmetic only climbs 3 levels and lands on `{root}/.claude-tweaks`
instead of `{root}`. That wrong `root` is then passed into `archiveRunDir(root, runDir)`
(`plugin/bin/lib/reconcile/archive-merged.js`), which re-joins `.claude-tweaks/pipelines/archive/{run-id}`
onto it — producing a doubled path: `{root}/.claude-tweaks/.claude-tweaks/pipelines/archive/{run-id}`.

Reproduced live twice in the same session: once from this run's own wrap-up (`teardown-run --run
".../archive/2026-08-23T171038-record-326"`), and a second, pre-existing instance discovered in
the same doubled location for an unrelated record (`2026-08-22T111227-record-1160`) — meaning at
least one other session hit the same bug independently before this one. Both were recovered by
hand (`mv` back to the correct `archive/{run-id}/` path; no data was lost, but it required manual
discovery — nothing surfaced the mismatch automatically).

The bug is reachable via `wrap-up/cleanup-procedures-execution.md` Section C step 5's own
documented invocation: `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" teardown-run --run "$RUN_DIR" --merged`
— when `$RUN_DIR` has already been re-pointed at its archived location earlier in the same wrap-up
(e.g. after `reconcile`'s own Step 4.2 archival already ran, and a caller re-derives `$RUN_DIR`
from the archived `run-state.json` before calling `teardown-run`), the doubling triggers.

Confirmed against the live code at `plugin/bin/lib/hooks/teardown-run.js:72` — the fixed
`path.resolve(runDir, '..', '..', '..')` arithmetic described above is exactly what's there today.
The codebase already has a depth-independent alternative for this exact problem:
`mainCheckoutRoot()` (`plugin/bin/lib/hooks/worktree-detect.js`) walks upward from a given path
looking for the nearest `.git`, so it resolves the correct root regardless of how many levels
`runDir` sits below it — 3 for a live run, 4 for an already-archived one. This is the same
git-based anchoring mechanism `_shared/pipeline-run-dir.md`'s Anchoring section already documents
as canonical for every other `--run`-accepting subcommand.

## Deliverables

- [ ] Replace `teardown-run.js`'s fixed-depth `root` derivation (line 72) with a call to
  `mainCheckoutRoot(runDir)` (imported from `./worktree-detect`, the same module `bin/hooks.js`
  itself already imports it from), removing the `path.resolve(runDir, '..', '..', '..')`
  arithmetic entirely rather than special-casing the `archive/` segment.
- [ ] Add a regression test in `tests/hooks-teardown-run.test.js` (the existing suite for this
  module) covering `--run` pointed at an already-archived path — assert the archive call lands at
  the correct (not doubled) path.

## Acceptance Criteria

1. `teardown-run --run {archive/{run-id}}` does not create a `.claude-tweaks/.claude-tweaks/...`
   doubled path.
2. The new regression test fails against the current (unfixed) code and passes after the fix.

## Technical Approach

Swap the fixed relative-path arithmetic for the existing git-based anchoring helper, which is
depth-independent by construction (it walks up from the given path to the nearest `.git`, not a
fixed number of `..` segments):

```js
const { mainCheckoutRoot } = require('./worktree-detect');
const root = mainCheckoutRoot(runDir);
```

`mainCheckoutRoot` returns `null` when no `.git` is found walking up from `runDir` — an
input-validation case the current fixed arithmetic has no equivalent for (it always returns some
path, right or wrong). Decide how `teardownRun()` should behave on `null` (e.g. skip the archive
step and report why, matching the module's existing try/skip/report posture for every other step)
as part of this change.

### Key Files

- `plugin/bin/lib/hooks/teardown-run.js` — replace the fixed `path.resolve(runDir, '..', '..', '..')` at line 72 with `mainCheckoutRoot(runDir)`
- `plugin/bin/lib/hooks/worktree-detect.js` — no change; this is the existing `mainCheckoutRoot()` implementation being reused
- `tests/hooks-teardown-run.test.js` — add the regression test for an already-archived `--run` path

## Gotchas

- Don't assume this is the only caller that could pass an archive-relative path — grep every
  `teardown-run` call site (`wrap-up/cleanup-procedures-execution.md`, any `bin/lib/reconcile/*`
  caller) for whether `$RUN_DIR` could already be archive-pointed at that call site before fixing
  just the one path this incident exercised.
- `mainCheckoutRoot()` can return `null` (no `.git` found, or an unreadable/unparseable gitdir) —
  the current fixed-arithmetic code has no such failure mode, so callers relying on `root` always
  being a usable path need this case decided explicitly, not left to propagate a `null` into
  `archiveRunDir`/`runGit` downstream.
