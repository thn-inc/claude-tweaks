# 2066: Fast-lane bundle membership is lost on a dispatch queue-order cache hit, and the bundle-report file is never read

Surface: infra

## Current State

`plugin/skills/dispatch/queue-pull-script.md`'s queue pull persists its file-overlap grouping through `bin/lib/dispatch/queue-order.js` (`readOrder`/`writeOrder`, #1571) so a later drain in the same freshness window skips dependency verification and the native blocker query. #1910's fast-lane bundling (`grouping.js`'s `bundleFastLaneSingletons`) runs on the cache-miss path and writes `dispatch-fastlane-bundles.json` (`{records: number[]}[]`) naming the groups it created, "so the Reporting section can call out a fast-lane bundle distinctly from an ordinary file-overlap group." Two gaps, both confirmed in the file at 2026-09-09:

- The cache-hit branch writes `echo '[]' > "$DISPATCH_FASTLANE_BUNDLES"` unconditionally (the "Cache-hit default" comment around line 62), and the cache-miss write-back persists only `groups` and `excluded` — never which of those groups are bundles. A drain that created a bundle and then hits the cache reports zero bundles while `dispatch-groups.json` still carries the bundled group.
- No file other than `queue-pull-script.md` mentions `dispatch-fastlane-bundles.json` (`grep -rln` over `plugin/skills` and `plugin/bin`). `dispatch/reporting.md` — the per-group report block #2009's split created; #2009 is now closed, so the blocker the original request named is gone — renders a bundled group as an ordinary multi-spec group with no indication it was assembled automatically.

## Deliverables

- Persist bundle membership in the queue-order cache: extend the record `writeOrder` stores with a `bundles: number[][]` field (each entry the member numbers of one fast-lane bundle, matching the existing file's shape), and on a cache hit derive `dispatch-fastlane-bundles.json` from `persisted.bundles` instead of writing `[]`; treat a persisted record without the field as an empty list so a pre-upgrade cache still reads.
- Wire the file into `dispatch/reporting.md`'s per-group block: when the dispatched group's member set equals an entry in `dispatch-fastlane-bundles.json`, the block's header line names it a fast-lane bundle (`fast-lane bundle: #a, #b, #c — assembled by bundleFastLaneSingletons, cap {n}`) instead of the ordinary multi-spec group line; the `decisions.md` selection entry for that group carries the same phrase.
- Add cache-round-trip coverage in `tests/bin-lib/dispatch/` (or the existing queue-order suite): write a bundle, re-read on a simulated cache hit, assert the bundle file is regenerated with the same members; and a conformance test pinning that `reporting.md` names the bundle file as a read.

## Acceptance Criteria

- With a cache hit whose persisted order contains one bundle, `dispatch-fastlane-bundles.json` after the pull lists exactly that bundle's members; with no persisted bundles it lists `[]` — both pinned by a unit test over `queue-order.js` and the cache-hit script block.
- A pre-existing cache record with no `bundles` field is read without error and yields `[]`.
- `dispatch/reporting.md`'s per-group block references `dispatch-fastlane-bundles.json` and renders the bundle header for a matching group; a conformance test asserts the file is named there, and `grep -rln dispatch-fastlane-bundles plugin/skills` returns both `queue-pull-script.md` and `reporting.md`.
- `npm test` passes.

## Technical Approach

The bundling step already knows which groups it created — capture that list in the same `node -e` block that calls `bundleFastLaneSingletons` and pass it into the `writeOrder` call alongside `groups`/`excluded` (the CAS write-back stays the single writer). On the cache-hit path, replace the `echo '[]'` with a `writeFileSync` of `persisted.bundles || []` in the block that already writes `persisted.groups`/`persisted.excluded` (lines ~80-85). In `reporting.md`, add one sentence to the group-block header rule keyed on set-equality with a bundle entry, and mirror it in the SKILL.md Step 3 selection log line so the bundle is visible in `decisions.md` before the Task calls run. Keep `SKILL.md` under its size ceiling by pointing at `reporting.md` for the wording.

### Key Files

- `plugin/skills/dispatch/queue-pull-script.md` — cache-hit default (line ~66) and the cache-miss write-back: persist and restore `bundles`
- `plugin/bin/lib/dispatch/queue-order.js` — `writeOrder`/`readOrder` and the blob builder (`{computedAt, runId, freshnessSignal, groups, excluded}` around line 85-95): add the optional `bundles` field
- `plugin/skills/dispatch/reporting.md` — per-group block: fast-lane bundle header keyed on `dispatch-fastlane-bundles.json`
- `plugin/skills/dispatch/SKILL.md` — Step 3 selection log line names the bundle; no other change (size ceiling)
- `tests/bin-lib/dispatch/queue-order.test.js` — round-trip and missing-field cases (new file; only `artifact-verdict.test.js` exists in that directory today)
- `tests/dispatch-prompt-bundle-citations.test.js` — conformance pin that `reporting.md` reads the bundle file

## Gotchas

- Set-equality, not subset: a bundle's members may later be partially excluded by the open-PR or blocked-by filters on the cache-miss path; a group that no longer equals a persisted bundle entry must render as an ordinary group, not a stale bundle.
- The queue-order cache is CAS-written under racing firings (the script's own comment); the `bundles` field must ride the same single write, never a second file.
- `dispatch/SKILL.md` sits at ~35.8 KB against its ceiling — put the wording in `reporting.md` and reference it, or the byte-ceiling conformance test fails.
- `bundleFastLaneSingletons`' selection is oldest-first within a priority band; persisting member numbers, not group indices, keeps the cache stable across re-orderings.

## Original request

Fast-lane bundle membership is lost on a dispatch queue-order cache hit, and the bundle-report file is never read

Origin: whole-branch review (e4fd2b2a8..884ed7ea, gating v6.120.0) — regression in #1910's fast-lane bundling feature (PR #2055)

## Current State

In `plugin/skills/dispatch/queue-pull-script.md` (around line 260), on a queue-order cache hit, `DISPATCH_FASTLANE_BUNDLES` is unconditionally defaulted to `[]` and never recomputed from the cached groups, and the cache-miss write-back only persists `groups`/`excluded` — never which groups are bundles — so bundle membership is lost from the cache entirely. A run that creates a fast-lane bundle and hits the cache on a later drain within the same cache window reports zero fast-lane bundles via `dispatch-fastlane-bundles.json`, even though the cached groups still include one. Separately (around line 163), `dispatch-fastlane-bundles.json` is written specifically so "the Reporting section can call out a fast-lane bundle distinctly," but no skill file's Reporting section actually reads or references it — write-only dead data, so an operator reviewing a drain that silently merged several fast-lane records into one run sees an ordinary multi-spec group with no indication it was an automatic bundle.

## Deliverables

- [ ] Persist bundle membership in the queue-order cache write-back (not just `groups`/`excluded`), and recompute `DISPATCH_FASTLANE_BUNDLES` from the cached data on a cache hit instead of defaulting to `[]`.
- [ ] Wire `dispatch-fastlane-bundles.json` into an actual Reporting section consumer (dispatch's own reporting, per the already-deferred Deliverable in #1910/#2055: "Reporting section names the bundle" — blocked on #2009's SKILL.md size ceiling).

## Acceptance Criteria

- [ ] A cache-hit run that previously created a fast-lane bundle still reports it via `dispatch-fastlane-bundles.json`.
- [ ] A dispatch report distinguishes a fast-lane bundle from an ordinary multi-spec group.
