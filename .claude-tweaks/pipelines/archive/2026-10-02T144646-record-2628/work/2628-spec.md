# 2628: Add App Store rejection checklist for vibecoded apps

Surface: infra

## Current State
AI-built/vibecoded mobile apps commonly get rejected by Apple App Store review for a recurring cluster of well-known, documented reasons: Stripe checkout instead of in-app purchase, Google sign-in present but no Apple sign-in, no way for a user to delete their account, a broken or incomplete demo/reviewer login, broken iPad layout, screenshots that don't match the shipped app or show paid features without labeling them as paid, dead support/privacy links, "coming soon" placeholder screens, comment/UGC features with no report path, and a broken restore-purchases button. No existing claude-tweaks check walks a codebase through Apple App Store submission requirements specifically; the existing pre-scale and security work (#2622, #2624, #2625) covers backend scaling and data handling, not store-review compliance.

## Deliverables
1. Add an "App Store submission readiness" checklist — either as a new skill or as policy rows on an existing review skill (whichever integration point exists once this is built) — covering: Apple sign-in parity with any other social sign-in, in-app purchase vs. external payment links, account-deletion flow, demo/reviewer login completeness, iPad layout, screenshot accuracy including paid-feature labeling, live support/privacy links, no coming-soon placeholders, a moderation/report path for UGC comment features, and a working restore-purchases button.
2. Ship a copy-paste prompt, matching this pipeline's existing pattern for this class of check, that scans a mobile app's codebase/config for each of the ten gaps above.

## Acceptance Criteria
1. Running the check against a sample mobile app codebase flags any of the ten gaps that are present.
2. Documentation distinguishes this store-review checklist's scope from the existing pre-launch/pre-scale hardening checks (#2622, #2624, #2625) so a reader doesn't confuse app-store compliance with backend scaling/security.
3. The check (and its copy-paste prompt) works standalone and as a step within `/claude-tweaks:review` or `/claude-tweaks:build`.
4. Each of the ten checklist items maps to a specific, checkable condition in a codebase or app config (e.g. "grep for a Stripe checkout SDK call alongside no `StoreKit`/`RevenueCat` import" for the payment-method item), not a vague prose reminder.

## Release Note

Added an App Store submission readiness checklist for generated apps.

## Technical Approach
Add the checklist as a new prompt/heuristic in the same style as this pipeline's other copy-paste-prompt checks, choosing the integration point (new skill vs. rows on an existing review skill) based on whichever shape the existing review-skill surface supports by the time this is built. Each of the ten items becomes one checkable row: a description of the Apple-review failure mode, and a concrete signal to grep/inspect for in a mobile codebase (SDK imports, Info.plist/AndroidManifest entries, presence/absence of an account-deletion API call, screenshot metadata, etc.).

### Key Files
- Whichever file the App Store readiness checklist lands in (a new skill directory, or an existing review skill's policy file) — to be determined based on the review-skill surface's shape at build time
- A documentation note distinguishing this checklist's scope from #2622/#2624/#2625

## Gotchas
This is a mobile-specific (iOS App Store) checklist; it does not cover Google Play's parallel review criteria, which differ in several respects (e.g. Play doesn't mandate Apple/Google sign-in parity the same way). Scope this record to Apple App Store review only, and treat Play Store review as a separate future record if pursued. The exact integration point (new skill vs. existing skill's policy rows) can't be pinned until whatever review-skill surface exists at build time is inspected.
