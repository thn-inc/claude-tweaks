# 1183: #280 run-dir fallback adopts arbitrary dirs; twin guard blind to nested spec-N and archive layouts

Defer-reason: pre-existing-outside-diff
Surface: backend

## Current State

The #280 worktree-local `--run` fallback in `plugin/bin/hooks.js` (~line 121) is materially weaker than its documentation. Confirmed on three sub-claims:

- It adopts ANY unanchored directory containing a `decisions.md`/`run-state.json`/`config.yml` — no pipelines-path, run-id-shape, or same-repo-worktree containment check — so `hooks.js record-worktree --run /some/project` (any project with a top-level config.yml) writes run-state/events into an arbitrary directory the old code rejected unconditionally.
- The authoritative-twin guard joins only `basename(dir)`, so a worktree shadow of a nested multi-spec run dir (`pipelines/{parent}/spec-967`) computes a mainCandidate of `pipelines/spec-967` (never exists) and the shadow is adopted even though the anchored copy exists — condition (b) structurally never fires for the exact layout flow/SKILL.md exports as PIPELINE_RUN_DIR.
- Same miss for a run archived to `pipelines/archive/{id}`.

This revives the IL-127 shadow class. `_shared/pipeline-run-dir.md` documents the fallback as scoped to "a --run candidate that resolves inside a linked worktree", which the code never verifies. No test covers any of the three shapes.

## Deliverables

- Enforce the documented containment: the candidate must resolve inside a linked worktree of the repo, under a pipelines path with a run-id-shaped segment.
- Fix the twin check to compare the candidate's pipelines-relative path (nested spec-N and archive/ layouts included), not basename.
- Tests for all three confirmed shapes.

## Acceptance Criteria

- `record-worktree --run /some/project` with a stray config.yml is rejected as unanchored.
- A worktree shadow of `pipelines/{parent}/spec-N` is refused when the anchored copy exists.

## Technical Approach

Replace the current unanchored-directory-with-marker-files check with an explicit containment check: resolve the candidate against `git worktree list` for the current repo (confirming it's inside a linked worktree, not just any directory with marker files), then require the path segment following the pipelines root to be run-id-shaped (matching the same run-id pattern `materialize.js`'s anchoring check already validates). For the twin guard, replace the `basename(dir)` comparison with a comparison of the candidate's path *relative to its own pipelines root* against the main checkout's pipelines root at the same relative path — this naturally covers both the nested `spec-N` layout and the `archive/{id}` layout without special-casing either, since both are just different relative-path shapes under the same pipelines root.

### Key Files

- `plugin/bin/hooks.js` — the #280 worktree-local `--run` fallback (~line 121) and the authoritative-twin guard
- `plugin/skills/_shared/pipeline-run-dir.md` — the containment contract this code is meant to enforce
- `tests/` — new coverage for the three confirmed shapes: arbitrary-directory adoption, nested `spec-N` shadow, and `archive/{id}` shadow

## Gotchas

- This is the same IL-127 shadow-directory class already fixed once elsewhere in this codebase (the pipeline-shadow PreToolUse guard) — check whether that fix's containment logic can be reused/shared rather than reimplemented independently here, since divergent containment logic across the two mechanisms is exactly how this kind of regression happens again.
- The basename-only twin check is the subtler of the three sub-claims to fix correctly — a naive "compare full paths" replacement can still miss the archive/{id} layout if the archive root isn't treated as equivalent to the live pipelines root; verify against all three confirmed shapes, not just the nested spec-N one.
