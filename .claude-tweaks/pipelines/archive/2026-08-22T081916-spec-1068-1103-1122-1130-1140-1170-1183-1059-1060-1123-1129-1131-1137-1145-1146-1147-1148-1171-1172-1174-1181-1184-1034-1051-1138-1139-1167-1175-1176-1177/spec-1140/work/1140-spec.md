# 1140: Wrap-up curation fan-out races apply-capable judges on one shared git index

Surface: backend
Defer-reason: pre-existing-outside-diff

## Current State

`plugin/skills/wrap-up/curation-engine.md`'s parallel-dispatch rule (section 4) fans out 3+ open fact-gated registry rows as concurrent Task agents. The apply-or-stage rows' judges (`skill-curation.md` 7.6, `docs-health-integration.md`, `journey-curation.md`) may auto-apply additive findings **with their own `git add`/`git commit`** — but the fan-out shares one worktree, so concurrent judges race on the git index. Observed live in run 2026-08-20T153031-spec-1065 (#1065's wrap-up): the Skills-row judge reported its edit "swept into a sibling's commit" with a fabricated commit hash; the controller audit found the edit actually uncommitted in the working tree, and a sibling judge independently reported seeing another row's in-flight modification. The engine serializes `record` calls in the main thread but nothing serializes the judges' own commits.

## Deliverables

- [ ] Close the race structurally — pick one: (a) fan-out judges become stage-only (apply/commit moves to the main thread after all payloads return, preserving the `applied` disposition by having the controller commit each returned patch serially), or (b) the fan-out dispatch instruction forbids judge-side `git add`/`git commit` and has judges return the edit as a patch for serial application, or (c) per-judge commit serialization via an explicit lock. Document the choice in `curation-engine.md` section 4.
- [ ] The controller-side audit that caught this (verify each payload's claimed `commit` exists in `git log` and its file list matches) becomes a documented step rather than improvisation.

## Acceptance Criteria

1. Concurrent fan-out judges can no longer produce interleaved/swept commits or fabricated commit attributions — the chosen mechanism makes it structurally impossible, not advisory
2. `curation-engine.md` documents the mechanism; a conformance or unit test pins whatever mechanical half exists
3. `npm test` passes in full

## Technical Approach

Option (a) — stage-only judges, controller commits serially — is the strongest structural fix: it removes the shared-index race entirely rather than managing it, and matches the compose-then-write-once idiom already used elsewhere in this plugin (e.g. `specify/shaping-mode.md`). Whichever option is chosen, the controller-side audit (verifying each payload's claimed commit exists via `git log` and matches its stated file list) should land regardless, since it's what caught this instance and has no dependency on which structural fix is picked.

### Key Files

- `plugin/skills/wrap-up/curation-engine.md` — section 4 (parallel dispatch), where the chosen mechanism is documented
- `plugin/skills/wrap-up/skill-curation.md`, `docs-health-integration.md`, `journey-curation.md` — the apply-capable judges whose dispatch instructions change under options (a) or (b)

## Gotchas

- The observed failure produced a fabricated commit hash in a judge's own report — any fix must also make a false "applied" claim structurally impossible to report, not just prevent the underlying git-index race
- A per-judge lock (option c) is the weakest of the three structural options — it still leaves judge-side commits as the mechanism, just serialized; prefer (a) or (b) unless there's a reason a controller-side serial-commit pass can't work here
