# 1068: materialize.md's worktree-first work/ commit ordering is unreachable under the pipeline-shadow guard for a genuinely new run

Surface: backend

## Current State

`bin/materialize.js` enforces (#790/[IL-127]) that `--run-dir` must resolve under the main
checkout root, never inside a linked worktree — it writes `{run-dir}/work/{n}-spec.md` at
whatever path is passed. Separately, `bin/lib/hooks/pre-tool-use.js`'s `checkPipelineShadowGuard`
(#692, also IL-127) refuses any `mkdir`/write that would create a **new** (not already on disk)
`.claude-tweaks/pipelines/{run-id}` directory inside a linked worktree.

`skills/flow/materialize.md`'s "When this runs" section documents a third, different behavior:
"create the worktree first, then scaffold the run dir and materialize inside it — the file is
written and committed on the feature branch, where it is already in the right place... Only
`work/` is created — inside the worktree, at the matching relative path under the worktree's own
filesystem location." That path is exactly what the pipeline-shadow guard refuses for a
genuinely new run (the timestamped run-dir segment does not yet exist inside the worktree), and
`materialize.js` itself refuses to target a worktree-relative `--run-dir` at all.

Confirmed live during #663's flow build,test pass: `mkdir -p` for a fresh
`.claude/worktrees/record-663/.claude-tweaks/pipelines/{new-run-id}/work` was denied by the
pipeline-shadow guard; `materialize.js --run-dir {worktree-relative-path}` was separately refused
by its own anchoring check. Writing `work/{n}-spec.md` at the main-checkout-anchored run dir
(the CLI's actual, working behavior) leaves the file un-committable from inside a worktree-isolated
session (`Write`/git-commit against the main checkout are themselves gated).

Three older `work/` commits already exist on this same worktree's branch history (records #539,
#194, #672) — per `pre-tool-use.js`'s own comment, these are "pre-anchoring run directories
already sitting in a worktree ... tolerated transitionally ... sunset 2026-11-07", not evidence
the documented procedure currently works for a fresh run.

## Deliverables

- [ ] Reconcile `materialize.md`'s "worktree-first" work/ commit ordering with the pipeline-shadow
      guard and `materialize.js`'s anchoring check — either exempt a `work/` subdirectory write
      from the shadow guard (it's the one documented, intentional exception to the run-dir
      anchoring rule per materialize.md's "Committed as audit trail, never gitignored" section),
      or update materialize.md/build/flow's SKILL.md to describe how `work/{n}-spec.md` actually
      reaches the worktree branch today
- [ ] Add or update a test pinning whichever behavior is chosen, so the two mechanisms
      (`checkPipelineShadowGuard`, `materialize.js`'s `isAnchored` check) can't silently diverge
      from the documented contract again

## Acceptance Criteria

1. A fresh `/flow #{n} build,test` run in `worktree` mode (no pre-existing run-dir on disk in the
   worktree) can materialize and commit `work/{n}-spec.md` on the feature branch without any agent
   needing to route around a hook denial
2. `materialize.md`'s "When this runs" section and the actual enforced behavior agree
3. `npm test` green

## Technical Approach

Likely the pipeline-shadow guard (`shadowPipelineRunDir` in `pre-tool-use.js`) needs a narrow
carve-out: allow creating exactly a `work/` (or `spec-{N}/work/`) leaf under a run-dir segment
that does not yet exist in the worktree, while still refusing `config.yml`/`decisions.md`/
`staged/` writes there. `materialize.js`'s own `isAnchored` check would then need the same
carve-out, or a `--worktree-work` mode that targets the worktree path directly for `work/` while
still reading/writing nothing else there.

### Key Files

- `plugin/bin/lib/hooks/pre-tool-use.js` — `shadowPipelineRunDir`/`checkPipelineShadowGuard`, the carve-out target
- `plugin/bin/materialize.js` — `isAnchoredUnderRoot`/anchoring check, needs the matching carve-out
- `plugin/skills/flow/materialize.md` — "When this runs" section, update if the documented ordering changes instead

## Gotchas

- Do not simply relax the guard for all worktree writes under `.claude-tweaks/pipelines/` — the
  guard's entire purpose (IL-127) is to stop `config.yml`/`decisions.md`/`staged/` from ever
  landing somewhere a later `git worktree remove` destroys
- The transitional tolerance for pre-anchoring run directories sunsets 2026-11-07 — whatever fix
  lands here should not depend on that tolerance window
