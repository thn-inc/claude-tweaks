# 1103: reconcile/archive-run: git-mv-failed leaves a corrupted double-nested archive dir; close-run-before-archive makes a run invisible to reconcile

Surface: backend

## Current State

`bin/hooks.js archive-run` (`bin/lib/reconcile/archive-merged.js`'s `archiveRunDir`) has two related defects, both hit while manually completing wrap-up for record #133 (2026-08-20):

1. **`iterRunDirsWithState` skip-if-clean vs. the intended `close-run`-then-archive ordering (`bin/lib/hooks/context.js` line 129: `if (state && state.status === 'clean') continue;`).** The normal wrap-up sequence writes `status: 'clean'` to a run's `run-state.json` as the terminal marker — but `archiveRunDir` (`archive-merged.js`) only writes that status *after* moving the run dir into `archive/`, at the archive destination. If something (e.g. a manual `close-run` call made before archival, as happened here) sets `status: 'clean'` on the run dir at its *original*, pre-archive location, `iterRunDirsWithState`'s skip-if-clean filter makes that run dir permanently invisible to `reconcile`'s `archive-merged` convergence pass — it will never be picked up automatically again. The direct `hooks.js archive-run --run <dir>` verb bypasses this filter and can still target it directly, but that's a non-obvious, undocumented escape hatch.
2. **`archiveRunDir` git-mv failure leaves a corrupted double-nested directory instead of failing atomically.** When `git mv` on the run dir's `work/` subtree fails (observed reason: `git-mv-failed` — in this case because `work/{n}-spec.md` was never actually git-committed anywhere, despite `_shared/pipeline-run-dir.md` stating "work/{n}-spec.md ... is git-tracked and must be committed onto the feature branch"), the function is documented to return `{ok: false, reason: 'git-mv-failed'}` without completing further moves. In practice, after the failed call, the original run dir had vanished from its live location and its full contents (including `work/`) were found nested one level too deep at `archive/{run-id}/{run-id}/...` instead of `archive/{run-id}/...` — i.e. the failure was not atomic, and the resulting state was neither "still live" nor "cleanly archived."

## Deliverables

- Root-cause the double-nesting: identify what actually performed the wholesale directory move after `archiveRunDir` reported `git-mv-failed` (a plain `fs.renameSync` fallback? a second concurrent reconcile pass? `archiveOrphanedMint`'s path taken unexpectedly?) and fix it to fail atomically (either don't move anything on git-mv failure, or complete the move correctly).
- Decide and implement the right behavior when `work/{n}-spec.md` is untracked at archive time (the invariant in `_shared/pipeline-run-dir.md` assumes it always reaches the main checkout via merge — confirm whether `/flow`'s materialize step can legitimately leave it untracked in the main checkout's run dir, e.g. when a caller writes directly into `$RUN_DIR` outside the canonical worktree-commit-then-merge path, and either enforce the invariant earlier or make archival tolerate an untracked `work/`).
- Either close the `iterRunDirsWithState` skip-if-clean gap (make `archive-run` reachable via the normal `reconcile` convergence pass even when `status: 'clean'` was set before archival), or document the ordering requirement clearly enough that a manual/out-of-band wrap-up doesn't hit it by surprise.

## Acceptance Criteria

1. A run dir whose `run-state.json` is prematurely marked `status: 'clean'` before archival is either still reachable by `reconcile`'s convergence pass, or the ordering requirement is documented at the `close-run` call site.
2. `archiveRunDir` never leaves a double-nested `archive/{id}/{id}/...` directory on a `git-mv-failed` path — either the move doesn't happen at all, or it completes correctly.
3. A regression test in `tests/bin-lib/reconcile/` covers the git-mv-failure path's atomicity.

## Technical Approach

Instrument or trace `archiveRunDir`'s call graph on the `git-mv-failed` path first (`bin/lib/reconcile/archive-merged.js`) to find what performs the actual double-nested move — that's the root-cause deliverable and determines the shape of the atomicity fix. Once found, either make the failure path a true no-op (nothing moves until `git mv` on `work/` itself succeeds) or restructure the move so a mid-failure state can't nest. Separately, decide the untracked-`work/`-at-archive-time question by tracing whether `/flow`'s materialize step (`skills/flow/materialize.md`) can leave `work/{n}-spec.md` uncommitted in the main-checkout run dir under any legitimate call path (a direct `$RUN_DIR` write outside worktree-commit-then-merge) — this determines whether the fix is "enforce the invariant earlier" or "make archival tolerate the gap." The skip-if-clean ordering hazard (`bin/lib/hooks/context.js` line 129) is independent of the other two and can land as either a code fix (widen `iterRunDirsWithState`'s filter to also catch a pre-archive `clean` status) or a documentation fix at the `close-run` call site.

### Key Files

- `plugin/bin/lib/reconcile/archive-merged.js` — `archiveRunDir`, the git-mv-failed atomicity bug and the untracked-`work/` handling
- `plugin/bin/lib/hooks/context.js` — `iterRunDirsWithState`, the skip-if-clean ordering hazard (~line 129)
- `plugin/skills/_shared/pipeline-run-dir.md` — the `work/{n}-spec.md` git-tracked invariant this bug violates
- `tests/bin-lib/reconcile/` — new regression coverage for the git-mv-failure atomicity path

## Gotchas

- #953 is a narrower instance-remediation record for the same "work/{n}-spec.md untracked -> archive-run git-mv-failed" root cause (a different orphaned run dir, record-229) — it fixes one stuck run dir, not the tooling defect class (atomicity + the skip-if-clean ordering hazard) this record covers. Don't let a fix here be scoped down to only what #953 needed.
- The corrupted double-nested layout observed in practice (`archive/{id}/{id}/...`) was manually flattened by hand as a recovery step — that manual repair is not evidence the underlying atomicity bug is fixed.
