# 1034: visualize: diagram output stays the same plain node-graph template regardless of how content-rich the request is

Surface: infra

## Current State

The `/claude-tweaks:visualize` skill always produces the same plain box-and-arrow SVG diagram for a given type, regardless of how rich or explanatory the user's request actually is, instead of adapting the page's visual density, illustration, and prose to the content being visualized. The skill resolves `<type>` and the generation path (Step 1), then always emits the same generic construct for that type — boxes connected by arrows, short labels, a handful of small callout cards — per Step 4's "author the `<svg>` content directly for the diagram type and topic" instruction (or the enhanced path's container-based graph). This happens identically whether the source material is a one-line description or four dense strategy documents. There is no step in the workflow that reasons about content richness or source-material depth — the type→construct mapping and fragment-generation instructions are the same for every invocation of a given type, so output richness stays roughly constant regardless of how much the topic could support.

## Deliverables

- Add a content-richness judgment to `/claude-tweaks:visualize`'s workflow — before or alongside Step 1's type→construct mapping, assess how much narrative/illustrative weight the source material warrants (a one-line description vs. several dense documents covering strategy, risk, and multiple workstreams).
- Scale the output's visual and textual density accordingly: a topic backed by substantial source material should be able to produce a richer documentation-style page (diagram plus real explanatory sections, more illustration, more text) rather than always defaulting to the same minimal node-and-arrow graph.
- Apply the same richness scaling to both the standard path (Step 4's direct `<svg>` authoring) and the enhanced path (`d2-enhanced-path.md`'s container-based graph).

## Acceptance Criteria

1. A `/claude-tweaks:visualize architecture` request backed by several dense source documents produces visibly more illustrative/textual content than the same request backed by a one-line description.
2. The richness judgment is a documented step in the skill's workflow (Step 1's type→construct mapping, or a new step ahead of it), not an implicit expectation.
3. Both the standard Step 4 path and the enhanced `d2-enhanced-path.md` path respect the same richness scaling.

## Technical Approach

Add a content-richness assessment as part of (or immediately before) Step 1's type→construct mapping — judge source-material depth (line count, number of documents, breadth of topics covered) and map it to a density tier the same way `<type>` already maps to a construct. Step 4's "author the `<svg>` content directly" instruction and `d2-enhanced-path.md`'s enhanced-path generation both need to read this tier and scale their output accordingly (more callout cards, richer illustration, more explanatory prose for a high tier; today's minimal node-and-arrow graph for a low tier).

### Key Files

- `plugin/skills/visualize/SKILL.md` — Step 1's type→construct mapping, Step 4's fragment generation
- `plugin/skills/visualize/d2-enhanced-path.md` — the enhanced container-based graph path

## Gotchas

- The richness tier must apply consistently across both generation paths (standard Step 4 and enhanced `d2-enhanced-path.md`) — a fix that only scales one path leaves the other producing the same flat output for rich source material.
- Don't conflate "more content" with "more clutter" — the goal is a documentation-style page that scales its explanatory depth to match the source material, not simply a bigger diagram with the same information density.
