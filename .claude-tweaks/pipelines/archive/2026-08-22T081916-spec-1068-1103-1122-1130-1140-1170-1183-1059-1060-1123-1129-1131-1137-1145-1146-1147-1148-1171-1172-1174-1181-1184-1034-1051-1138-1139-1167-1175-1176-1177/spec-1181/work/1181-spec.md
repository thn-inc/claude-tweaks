# 1181: Unnamed-merge gate: reconcile archive-move re-adds shipped specs to the unnamed set

Defer-reason: pre-existing-outside-diff
Surface: backend
Origin: observed live during the v6.104.0 release (2026-08-21).

## Current State

The unnamed-merge gate (`unnamedRecordsGate` in `plugin/bin/lib/release/unnamed-records.js`, #768) lists every record whose materialized spec file was newly *added* between the last version bump and HEAD (`materializedRecordsSince`, using `git diff --name-status {lastBump}..HEAD -- .claude-tweaks/pipelines/`, keeping only `A`-status lines). Two independent things push already-shipped records back into that set:

1. **Historical-CHANGELOG blind spot (confirmed root cause).** After collecting candidates, the gate checks whether each one is named in `summary` (the in-progress release's own text) and, failing that, only `parseChangelogVersions(...)[0]` — the single *newest* CHANGELOG.md entry. A record whose spec file re-enters git several releases after it actually shipped (e.g. via a manual reconcile catch-up commit) is invisible to this check unless it happens to be re-mentioned in the immediately preceding release. Reproduced directly against this repo's own history: comparing the v6.104.1 bump (`103b3ecc`) to the current HEAD, `git diff --name-status 103b3ecc..HEAD -- .claude-tweaks/pipelines/` reports `172-spec.md`, `345-spec.md`, and `230-spec.md` as plain `A` additions under `.claude-tweaks/pipelines/archive/...` — all three landed via commit `6250a11d` ("Archive spec-172, record-345, record-230 pipeline run work files (#1196)"), a manual catch-up commit for local pipeline-run directories that had never previously been committed to git. `CHANGELOG.md` shows #172 actually shipped in **v6.99.0** (line ~78/80: "github-pr-scan MCP fallback (#172)") — five releases before v6.104.1 — so the single-entry check never finds it.
2. **Same-cycle materialize-then-archive (not actually a bug).** A record like #899 or #316, newly built and merged within the *current* release window, gets archived by an automated `[reconcile] archive run ...` commit before the release lands. Verified live: each individual archive commit (`c6ef7cd6`, `6280c299`, etc.) correctly shows `R100` (a detected rename) in isolation, and the gate already skips non-`A` statuses — but the full multi-commit range diff nets out to a plain `A` at the archive path, because the record's non-archive path was created *and* removed entirely inside the diffed range and leaves no `D` for git to pair against. This case is legitimate: the record is genuinely new to this release and must still be named (and already is, via the release-summary text) — Deliverable/AC below must not suppress it.

Observed live: the v6.104.0 dry-run's unnamed set grew from 43 to 65 records after a single reconcile archive commit landed — 18 of the 22 additions were archive-move noise (#172, #226, #229, #250, #545, #630, #636, #744, #861, #967–#970 already carried by earlier CHANGELOG entries; #133, #280, #663, #666, #670 with no in-range work commits), forcing a hand-audited `--allow-unnamed` override.

## Deliverables

- In `unnamedRecordsGate`, replace the single-entry CHANGELOG check (`parseChangelogVersions(...)[0]`) with a scan across **every** parsed entry, so a record named in any past release — not only the newest one — clears the unnamed set.
- Leave the existing rename-status filtering (`cols[0] !== 'A'`) untouched — it already correctly excludes genuine intra-commit `git mv` renames (confirmed still works via `R100` detection on real `[reconcile] archive run` commits); the fix is scoped to the CHANGELOG lookback, not the git-diff parsing.
- A test fixture reproducing the historical-CHANGELOG case: a candidate record named only in an *older* (non-newest) CHANGELOG entry must clear the unnamed set.

## Acceptance Criteria

- A record already named in any past CHANGELOG.md entry (not just the newest one) is never reported as unnamed, regardless of how many releases separate it from HEAD.
- A record whose spec file is genuinely new this cycle — added and archived entirely within the diffed range, with no CHANGELOG mention anywhere — still gets flagged as unnamed unless the current release's own `summary` names it.
- A `[reconcile] archive run` commit between two bumps adds zero records to the unnamed set for specs whose original path existed (in git) before the previous bump.

## Technical Approach

In `plugin/bin/lib/release/unnamed-records.js`'s `unnamedRecordsGate`, change:

```js
const newest = parseChangelogVersions(deps.readFile(CHANGELOG))[0];
const haystack = newest ? `${newest.title}\n${newest.body}` : '';
unnamed = recordsNamedIn(haystack, unnamed).missing;
```

to scan every entry `parseChangelogVersions` returns (it already parses the whole file into an ordered list, not just the newest heading — confirmed in `plugin/bin/lib/changelog.js`), concatenating every entry's title+body into the `recordsNamedIn` haystack instead of slicing to `[0]`. `recordsNamedIn`'s own range-aware and exact-mention matching (`status.js`) needs no change — it already handles a `#699-#701` range or a bare `#700` mention; it's only ever been given the wrong (too-narrow) haystack.

No change is needed to `materializedRecordsSince`'s git-diff/rename handling — that logic is already correct for the case it targets (confirmed live: `R100` renames inside a single `[reconcile] archive run` commit are detected and filtered).

### Key Files

- `plugin/bin/lib/release/unnamed-records.js` — `unnamedRecordsGate`'s CHANGELOG-lookback step, widen from `[0]` to all entries
- `plugin/bin/lib/changelog.js` — `parseChangelogVersions` (already returns every entry; no change needed, referenced for the fix)
- `tests/bin-lib/release/unnamed-records.test.js` — add the historical-CHANGELOG fixture

## Gotchas

- The original problem statement (git-mv rename pairing) is real but already handled correctly by the existing `cols[0] !== 'A'` filter for a single commit's diff — it is not the reproducible cause of the live 43→65 regression. The reproducible cause is the CHANGELOG-lookback being limited to the newest entry; verify against this repo's own history (`git diff --name-status 103b3ecc..HEAD -- .claude-tweaks/pipelines/` plus `grep -n '#172\b' CHANGELOG.md`) before assuming the rename-based framing if re-deriving this fix independently.
- Don't blanket-exclude every path under `pipelines/archive/` from the "newly added" scan (the Deliverable's originally-suggested alternative) — that would also swallow genuinely new same-cycle records that get archived before their release lands (e.g. #899, #316 in the v6.105.0 dry-run), which must still be flagged unless named in the current release's own summary.

A `[reconcile] archive run ...` commit that moves a run dir under `.claude-tweaks/pipelines/archive/` re-adds the spec file at a new path, so records whose work shipped in earlier releases (or that never shipped user-facing work at all) re-enter the unnamed set. ## Deliverables

- Make the gate ignore spec-file additions whose commit also *deletes* the same-named spec at a non-archive path (a rename/move), or exclude paths under `pipelines/archive/` from the "newly added" scan when the identical spec content existed pre-bump.
- A test with an archive-move fixture proving a previously-shipped record does not re-enter the unnamed set.

## Acceptance Criteria

- A `[reconcile] archive run` commit between two bumps adds zero records to the unnamed set for specs whose original path existed before the previous bump — and still flags a genuinely new spec added only under archive/.
