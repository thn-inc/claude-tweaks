# 1145: build/worktree-setup.md's post-materialize Steps (4.5 record-worktree, 6 PR-early-lifecycle) didn't fire for record #375's run

Origin: reflect light from #375
Defer-reason: tangential
Surface: backend

## Current State

`build/worktree-setup.md` Step 6 is documented to push the branch and open a draft PR (`_shared/pr-early-run-lifecycle.md`'s "Run start" procedure) immediately after the worktree's materialize commit, unconditionally, on every `pr-first` run. During record #375's review/polish/wrap-up leg (a resumed pipeline run adopting a run directory a prior call had already minted and used for build+test), wrap-up's Auto-merge path discovered: no `run-state.json` existed anywhere for this run (neither in the main-checkout run directory nor the worktree), `origin/worktree-record-375` did not exist, and no PR existed for the branch. This means Step 6 never ran, or ran and failed silently with no recorded evidence, during the prior call's build phase — despite `config.yml` recording `integration-model: pr-first` and the build/test/materialize/review decisions.md entries showing the pipeline otherwise proceeded normally through build and test. Wrap-up's own `hooks.js reconcile` call later confirmed a second, related gap: `run-state.json` (created only when wrap-up itself ran `record-pr`) carries no `worktree` field either, so `worktree-setup.md` Step 4.5's `record-worktree` call evidently didn't fire for this run either — `reconcile`'s per-run archival step skipped this run's directory with reason `no-worktree` as a direct consequence, leaving cleanup to be done by hand instead of converging automatically.

## Deliverables

- Investigate why `build/worktree-setup.md` Step 4.5 (`record-worktree`) and Step 6 (`_shared/pr-early-run-lifecycle.md`'s Run-start procedure) both did not fire for this run, despite `pr-first` being the resolved integration model and the worktree strategy being in effect.
- Determine whether this is reproducible (a gap in Step 4.5/6's invocation conditions, an error swallowed without a `decisions.md` log line, or a code path that only some callers of `worktree-setup.md` exercise — this run was a resumed pipeline run adopting a run directory a prior call had already minted, which may be relevant) or was a one-off.
- If reproducible: harden Step 6 so a failure to push/open the PR is never silent — either it always logs an explicit `AUTO`/degrade line to `decisions.md` (per `_shared/pr-early-run-lifecycle.md`'s own "On failure" clause, which already specifies this — check whether that clause actually executes), or a later phase (e.g. review's test gate, or wrap-up's Phase 1) positively checks for the expected `run-state.json.pr`/`run-state.json.worktree` fields on a `pr-first` worktree run and surfaces the gap immediately rather than only at the merge attempt.

## Acceptance Criteria

1. A root-cause account exists for why Steps 4.5 and 6 didn't produce a recorded worktree, a pushed branch, a PR, or a decisions.md log line for this run.
2. Either a fix lands (Step 4.5/6, or a downstream check, catches this failure mode going forward), or the investigation concludes this was a one-off with a stated reason and no fix is needed.

## Technical Approach

Start with the "resumed pipeline run adopting a run directory a prior call had already minted" shape named in the Deliverables as possibly relevant — trace whether `worktree-setup.md`'s Steps 4.5/6 are gated on a condition (e.g. "only runs on a freshly-created worktree") that a resumed/adopted run silently fails to meet, versus genuinely swallowing an error with no log line. Check `_shared/pr-early-run-lifecycle.md`'s own "On failure" clause first to confirm whether it actually executes on this path — if the clause exists but the log line never appeared in this run's `decisions.md`, that's strong evidence the clause itself isn't reached rather than that it fired and was silent.

## Resolution

Investigated per Deliverable #1/#2. This record is a duplicate of an already-shipped fix, discovered chronologically after this record was filed.

1. **Root cause (AC1):** #375's run matches `flow/steps-and-gates.md`'s "Adopting an inherited run directory" **case 3** exactly — a resumed run adopting a run directory a prior call had already minted for build+test, whose directory carries real content (`decisions.md`, `work/{n}-spec.md`) but no `config.yml`. Before the fix below existed, a call re-entering this shape had no explicit recovery step for the worktree stamp or the draft PR, so both `build/worktree-setup.md` Step 4.5 (`record-worktree`) and Step 6 (PR-early-lifecycle push+PR) silently never ran on the resuming call — they were never re-triggered, and the run's `config.yml`-less state gave no other hook to fire them from.
2. **Reproducible, not a one-off:** the identical symptom is independently documented on a *different* run (#663, still-open issue #1106) — confirming this is a general shape, not specific to #375's run.
3. **Fix already shipped (AC2):** commit `581f123c` ("flow: add the missing case for an inherited run dir with content but no config.yml — refs #1013"), dated 2026-08-21T05:45:52Z — after #1145 was filed (2026-08-20T19:34:04Z, 4 minutes after #375 closed) — added exactly this case-3 recovery text to `flow/steps-and-gates.md` (lines 70-73, confirmed live in current HEAD): when the adopted run's `run-state.json` is missing or lacks a `worktree` field, run `record-worktree` now; when `integration-model: pr-first` and there is no `pr` field, run `_shared/pr-early-run-lifecycle.md`'s push-and-open-draft-PR procedure now, before proceeding. This directly satisfies Deliverable #3's ask (a later phase positively checks for the expected `run-state.json` fields and surfaces/fixes the gap, rather than only failing silently at merge time).
4. **Already regression-tested:** record #1129, built earlier in this same session, added `tests/dispatch-flow-rundir-handoff.test.js` coverage pinning this exact case-3 recovery text stays present — so the fix this record needed is not only shipped but already guarded against silent regression.

**Ruling (AC1/AC2):** No further claude-tweaks-side fix needed — the gap this record describes was closed by commit `581f123c` (refs #1013) before this build session, independently of this record, and confirmed still live and test-covered. #1106 (tracking the same symptom on record #663's run) is very likely also resolved by the same fix, but is out of scope to close here — it belongs to a different record and isn't part of this run's manifest.
