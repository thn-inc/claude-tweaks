# 1184: sanitizeWorktreeName emits names git/EnterWorktree reject — doubled, leading/trailing, and slice-cut slashes

Surface: backend

## Current State

`plugin/bin/lib/worktree/name.js`'s `sanitizeWorktreeName` splits a candidate worktree name on `/`, sanitizes each segment's characters, drops empty segments (`.filter(Boolean)`), rejoins with `/`, then caps the result at `MAX_LEN` (64) via `.slice(0, MAX_LEN)`.

Verified live against the currently shipped module (2026-08-21). Commit `0108c53a` — a same-day, separate whole-branch-review fix batch — already added the `.filter(Boolean)` empty-segment drop this record's origin review was reacting to, so two of the three originally-reported inputs no longer reproduce:

- `sanitizeWorktreeName('flow//spec-1')` → `'flow/spec-1'` — **already fixed**; the doubled slash collapses correctly. Covered by `tests/bin-lib/worktree/name.test.js`'s "a doubled slash collapses" case.
- `sanitizeWorktreeName('flow/spec-1/')` → `'flow/spec-1'` — **already fixed**; the trailing slash is dropped. Covered by the same file's "a trailing slash is dropped" case.
- A 63-char first segment + `/rest` (68 chars total) still reproduces a genuine, currently-untested bug: `sanitizeWorktreeName('a'.repeat(63) + '/rest')` → 64 `'a'` characters ending in a trailing `/` (the slice lands exactly on the `/` at index 63). The `.slice(0, MAX_LEN)` cap runs *after* the empty-segment filter, so it can cut mid-string and leave a trailing `/` the filter never sees. Git ref rules forbid a trailing `/`, and no case in `name.test.js` covers a slice landing on a segment boundary.

Of the three inputs the origin review (range `b517ee68..origin/main`) verified, only this third one is still open.

## Deliverables

- In `sanitizeWorktreeName`, re-trim a trailing `/` left over after the `MAX_LEN` slice.
- A regression test for the slice-boundary case (a segment long enough that the 64-char cap lands exactly on a `/`).

## Acceptance Criteria

- `sanitizeWorktreeName('a'.repeat(63) + '/rest')` returns a name with no trailing `/`, and the result matches `tests/bin-lib/worktree/name.test.js`'s existing `VALID` charset regex.
- The existing doubled-slash and leading/trailing-slash regression tests in `name.test.js` continue to pass unchanged — this record doesn't touch that logic.

## Technical Approach

After the existing `.slice(0, MAX_LEN)` call, strip one trailing `/` if present (e.g. `.replace(/\/$/, '')`). This only matters when the cap falls exactly on a segment boundary; a slice landing mid-segment needs no change since each segment's characters are already sanitized before the join.

### Key Files

- `plugin/bin/lib/worktree/name.js` — add the trailing-slash re-trim after the `MAX_LEN` slice in `sanitizeWorktreeName`
- `tests/bin-lib/worktree/name.test.js` — add the slice-boundary regression test

## Gotchas

- The origin review verified all three symptoms against a slightly older tree; commit `0108c53a` (same day) independently fixed the empty-segment-filter part of this same failure class as part of an unrelated whole-branch-review fix batch. Only the slice-boundary case survived to this record — re-verify against the current tree before starting, in case a further fix has landed since this record was shaped.
