# 1171: sweep-shadow: partial-failure sweep reads as clean (silent exit 0) and retries duplicate entries

Defer-reason: pre-existing-outside-diff
Surface: backend

## Current State

`plugin/bin/lib/hooks/sweep-shadow.js`: the shadow decisions.md relocation (readFileSync/appendFileSync/unlinkSync ~lines 146–154) and the staged/ readdir (~line 101) are unguarded, and `hooks.js`'s `.catch(() => process.exit(0))` (~line 554) converts any mid-sweep throw into a silent exit 0. A failed partial sweep is indistinguishable from a clean no-op sweep to the caller (curation-engine.md §4 keys its AUTO log on `sweep:` diagnostic lines). Additionally the append-before-unlink ordering duplicates entries on retry: if appendFileSync succeeded but unlinkSync failed, the next run re-appends the same entries into the anchored decisions.md.

## Deliverables

- Distinguish a failed sweep from a clean sweep at the hooks.js seam (per the never-break-a-session invariant: still exit 0, but emit a diagnostic line the caller can log).
- Make the relocation idempotent on retry (e.g. content-presence check before append, or unlink-then-append with the entry buffered).
- Tests: mid-sweep throw yields the failure diagnostic, not silence; a retried relocation does not duplicate entries.

## Acceptance Criteria

- A read-only staged/ dir produces a visible failure diagnostic, not a clean-sweep report.
- Two consecutive runs over the same shadow file leave exactly one copy of each entry.

## Technical Approach

Wrap the unguarded relocation block (readFileSync/appendFileSync/unlinkSync, ~lines 146–154) and the staged/ readdir (~line 101) in their own try/catch inside `sweep-shadow.js`, emitting a `sweep: failed — {reason}` diagnostic line on catch rather than letting the throw propagate to `hooks.js`'s blanket `.catch(() => process.exit(0))`. For idempotency, buffer the entry in memory, `unlinkSync` first, then `appendFileSync` — reversing today's append-then-unlink order so a mid-operation failure leaves the shadow file either fully intact (unlink not yet attempted) or fully consumed (unlink succeeded, append is what's retried), never in the duplicate-producing state where append already landed but unlink didn't.

### Key Files

- `plugin/bin/lib/hooks/sweep-shadow.js` — the relocation block (~146–154) and staged/ readdir (~101)
- `plugin/bin/hooks.js` — the `.catch(() => process.exit(0))` seam (~554) that needs the diagnostic line surfaced through it
- `plugin/skills/wrap-up/curation-engine.md` — §4, the caller that keys its AUTO log on `sweep:` diagnostic lines

## Gotchas

- The never-break-a-session invariant still applies — the fix must keep `hooks.js` exiting 0 on a sweep failure; it changes what gets logged, not the exit code.
- Reversing the unlink/append order changes the failure mode's shape (from "append succeeded, unlink failed → duplicate on retry" to "unlink succeeded, append failed → data momentarily only in memory") — make sure the new order's own failure case is covered by the idempotency test, not just the old one.
