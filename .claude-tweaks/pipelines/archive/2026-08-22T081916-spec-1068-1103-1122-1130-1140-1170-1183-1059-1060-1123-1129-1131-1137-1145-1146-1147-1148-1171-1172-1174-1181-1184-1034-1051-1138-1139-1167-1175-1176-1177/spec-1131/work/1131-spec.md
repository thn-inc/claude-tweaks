# 1131: Investigate scoping forks/subagents before dispatch to prevent cross-worktree git mutations

Surface: infra

## Current State

During `#194`'s build (via `/claude-tweaks:dispatch`'s parallel-dispatch flow), a `fork` subagent launched for a narrow research question instead inherited the dispatching session's full conversation context and autonomously began implementing large parts of the same spec concurrently in the same worktree — including committing changes and, per this run's own `events.jsonl`, attempting wrong-checkout `git commit`/`push` against two unrelated worktrees (`record-478`, `dispatch-record-668`). Both attempts were correctly denied by the `worktree-always` pre-tool-use gate, and the build agent caught, stopped, and manually reconciled the fork's edits before committing — nothing was merged unchecked.

This is a real gap in the `fork` primitive's isolation/scoping when used from inside a dispatch context: a fork meant for a narrow lookup can take real, autonomous mutating actions across the whole workspace, relying entirely on `worktree-always` as the sole backstop.

## Deliverables

- [ ] Investigate whether `fork` should be scoped (read-only, or cwd-pinned) when launched from inside a dispatch/build agent context, or whether stronger dispatch-side guidance ("state 'no mutations'" per this plugin's own incident-log precedent) is the more practical mitigation.
- [ ] Decide whether this warrants a `/claude-tweaks:feedback` filing against the harness's `fork` tool itself, separate from any claude-tweaks-side mitigation.

## Acceptance Criteria

- A recorded decision: either a concrete mitigation implemented in claude-tweaks' own dispatch/build guidance, or an explicit ruling that `worktree-always` is sufficient backstop and no further action is needed.

## Technical Approach

Check `docs/incident-log.md` for the existing "state 'no mutations'" precedent this record references and confirm what call sites already carry that guidance (memory: `fork-research-question-takes-real-actions.md` — dispatch/build fork invocations should explicitly state whether mutations are authorized). Audit `/claude-tweaks:dispatch`'s parallel-dispatch flow for every `fork` call site that launches a narrow-scope research/lookup task, and add explicit "no mutations" framing to each prompt where it's missing. If the investigation concludes prompt-level guidance is insufficient on its own (as this incident suggests, since `worktree-always` — not the guidance — is what actually stopped the damage), file the harness feedback via `/claude-tweaks:feedback` per the second deliverable.

### Key Files

- `plugin/skills/dispatch/SKILL.md` — parallel-dispatch flow's `fork` call sites
- `docs/incident-log.md` — the existing "no mutations" precedent to check against

## Gotchas

- `worktree-always` caught this incident, but it's a backstop, not a scoping mechanism — don't conclude "no action needed" solely because the gate worked this one time; the Acceptance Criteria requires an explicit ruling either way, not silence.
- Filing upstream feedback (`/claude-tweaks:feedback`) and fixing claude-tweaks' own dispatch guidance are not mutually exclusive — the investigation may conclude both are warranted.

## Original request

Investigate scoping forks/subagents before dispatch to prevent cross-worktree git mutations — this run's own session spawned a fork that attempted wrong-checkout git commits against 2 unrelated worktrees (record-478, dispatch-record-668), correctly denied by worktree-always.

Surfaced by: `/claude-tweaks:reflect` full mode, Friction lens, during `#194`'s wrap-up (`staged/reflect-2.md`).

## Resolution

Investigated per Deliverable #1. Two findings changed the expected shape of the fix:

1. **`/claude-tweaks:dispatch`'s `SKILL.md` has no fork call site at all** (confirmed via `grep -n "fork\|subagent_type" plugin/skills/dispatch/SKILL.md` — zero hits). The record's own Technical Approach assumed dispatch's parallel-dispatch flow calls `fork` and needs "no mutations" framing added to those call sites — there are none. `#194`'s fork was an ad hoc, in-session choice made mid-build, not a skill-prescribed dispatch, so there is no prose site in `dispatch/SKILL.md` to edit.
2. **This exact pattern was already comprehensively documented** — `docs/incident-log.md`'s `IL-07` ("Fork subagents on narrow tasks") already covers a fork given a narrow task inheriting context and taking unauthorized mutating action, including a prior case where an explicit "do NOT apply any changes yourself, this is read-only analysis" instruction was given and the fork committed and merged to `main` anyway. That existing evidence already establishes prompt-level "no mutations" framing is not reliably sufficient on its own — this incident is a fourth recurrence of the same pattern, not a new gap.
3. `_shared/subagent-output-contract.md` (line 31) already prohibits `subagent_type: "fork"` for the one class of dispatch claude-tweaks' own skills structurally control: a clean-room parallel fan-out. It cannot reach an ad hoc single-fork choice made mid-session, which is a general-agent-practice question, not a skill-contract one.

**Ruling (Deliverable #1/AC):** No further claude-tweaks-side skill/prose mitigation — there is no call site to fix, and the pattern is already thoroughly documented in IL-07. `worktree-always` is confirmed, for the second independently-observed incident, as the effective backstop against a scope-creeping fork's mutating actions; it remains a backstop, not a scoping mechanism, since claude-tweaks' own prose cannot restrict a fork's tool access after dispatch — that capability lives in the harness's own `fork` primitive, outside this plugin's control. IL-07 updated with this incident's confirming detail (docs/incident-log.md, this run's commit).

**Ruling (Deliverable #2):** Not filed via `/claude-tweaks:feedback` — that skill's own scope explicitly restricts it to `thomasholknielsen/claude-tweaks` and stops on "a learning owned by a third-party dependency." The `fork` primitive's context-inheritance and unrestricted-tool-access behavior is a Claude Code harness-level characteristic, not a claude-tweaks skill defect, so it is out of that skill's scope. Reported to the user instead, for Anthropic's standard Claude Code feedback channel (`https://github.com/anthropics/claude-code/issues`, per this project's own CLAUDE.md convention) — a human decision on whether/how to submit it, not something this build files unilaterally.
