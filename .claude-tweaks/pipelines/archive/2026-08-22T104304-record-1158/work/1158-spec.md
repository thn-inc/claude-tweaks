# 1158: bin/materialize.js writes work/{n}-spec.md under the main-checkout-anchored --run-dir, never inside the invoking worktree

Origin: discovered during /claude-tweaks:build #1011's Spec Step 1 (record materialization)
Defer-reason: tangential

## Current State

`plugin/bin/materialize.js`'s anchoring guard (`isAnchored`/`isAnchoredUnderRoot`, called before any write) rejects any `--run-dir` whose nearest `.git` ancestor is a `.git` FILE (the linked-worktree/submodule marker) — see `plugin/bin/lib/hooks/worktree-detect.js`'s `isAnchoredUnderRoot`, which explicitly returns `false` for that case (`[IL-127]`'s anti-shadow guard). This forces `--run-dir` to always resolve under the **main checkout**, never a linked worktree.

The CLI then writes `work/{n}-spec.md` at `path.join(opts.runDir, 'work', ...)` (materialize.js line ~196-198) — directly under whatever `--run-dir` resolved to. Since `--run-dir` is always main-checkout-anchored (by the guard above), `work/{n}-spec.md` always lands in the **main checkout**, never inside the invoking worktree's own filesystem tree.

This contradicts `plugin/skills/_shared/pipeline-run-dir.md`'s Anchoring section, which states as a load-bearing consequence: "`work/{n}-spec.md` is the exception and stays inside the worktree. It is git-tracked and must be committed onto the feature branch; it reaches the main checkout by merge." A git worktree's working directory is filesystem-disjoint from the main checkout's — a file physically written under the main checkout cannot be `git add`/`git commit`-ed from a worktree session, since a worktree-isolated session's git operations are refused against the shared checkout entirely (this project's own PreToolUse gate: "a worktree-isolated session's git operations must target its own worktree").

Reproduced 2026-08-20 during `/claude-tweaks:build #1011` (dispatch worktree `dispatch-record-1011`): `node plugin/bin/materialize.js 1011 --run-dir "$PIPELINE_RUN_DIR" --repo thomasholknielsen/claude-tweaks --ceremony fast-lane` wrote `1011-spec.md` under the main checkout's `.claude-tweaks/pipelines/2026-08-20T211123-record-1011/work/`, not under the worktree's own `.claude-tweaks/pipelines/2026-08-20T211123-record-1011/work/`. Worked around manually this run by `cp`-ing the file into the worktree's matching relative path and committing it there.

## Deliverables

- [ ] Decide the correct fix shape: either (a) `materialize.js` itself detects when cwd is inside a linked worktree and writes `work/` at the worktree-mirrored relative path instead of joining onto the (necessarily main-checkout-anchored) `--run-dir`, or (b) the calling skill procedure (`build/SKILL.md` Common Step 1 / `flow/SKILL.md` Step 4.2, both of which already state the worktree-first ordering) is documented to `cp` the CLI's output into the worktree and commit it there, matching what this run did manually.
- [ ] Whichever shape is chosen, update `skills/flow/materialize.md`'s "When this runs" section (and the "Consumers that state this ordering" list it names) so the documented sequence matches what the CLI + callers actually do.
- [ ] Add regression coverage in `tests/bin-lib/materialize.test.js` (or equivalent) asserting the fix: given a `--run-dir` resolving under the main checkout and a cwd inside a linked worktree, the materialized file ends up somewhere `git add` from the worktree can actually reach.

## Acceptance Criteria

1. A `/claude-tweaks:build #{n}` (or `/claude-tweaks:flow`) run in `worktree` mode produces a materialized `work/{n}-spec.md` that is committable from the worktree session that created it, without a manual `cp` workaround.
2. `skills/flow/materialize.md`'s documented sequence matches the actual code path (CLI behavior, or CLI + caller-copy step) — no reader following the doc ends up with an uncommittable file the way this run did.
3. `npm test` passes in full.

## Why this matters

Every `worktree`-mode `/build`/`/flow` invocation against a record hits this exact CLI invocation shape (`--run-dir` resolved per `_shared/pipeline-run-dir.md`, i.e. always main-checkout-anchored) — this is not an edge case, it is the default path. Left unfixed, every such run either silently produces an uncommittable materialized file (never lands on the feature branch, so the audit trail `materialize.md`'s "Committed as audit trail, never gitignored" section promises is missing) or requires the same manual `cp` workaround this run applied ad hoc.
