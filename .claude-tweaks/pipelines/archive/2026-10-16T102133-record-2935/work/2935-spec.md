# 2935: reconcile: gitCommittedToRemoval treats an unresolvable registered entry as absent (fail-open branch)

Surface: infra

**Related:** #3132

## Current State

`gitCommittedToRemoval(real, root)` (`plugin/bin/lib/reconcile/reap-merged.js:116-121`) gates the win32 long-path fallback in `attemptLongPathRemoval` (`:133`). It runs `git worktree list --porcelain` and finds the target's entry with `(safeReal(wt.path) || wt.path) === real` (`:119`). It returns `!entry || entry.prunable`. In other words, "no matching entry" reads as "git committed to removal", which permits a force-delete.

`safeReal` (`plugin/bin/lib/hooks/worktree-detect.js:18-20`) swallows every `realpathSync` error and returns `null`. When resolution fails for a registered entry, the comparison falls back to the raw porcelain path against the already-resolved `real`. On any path that differs from its realpath (a symlinked ancestor, macOS `/private` prefixes) that comparison misses. A still-registered, healthy worktree then reads as absent, and the gate opens. The header comment (`:115`) says "An unreadable list fails closed", but this per-entry branch is fail-open.

Reaching it requires `realpath` to fail with something other than ENOENT on an intact, registered worktree directory that resolved moments earlier in the same pass, for example an ancestor permission change or a symlink loop. This is hardening, not a live bug. Found by the v6.134.0 release review (lens 3b, single agent, direct-verified, low).

## Deliverables

1. In `gitCommittedToRemoval`, a registered entry whose path fails to resolve with any error other than ENOENT makes the function return `false` (fail closed). Such an entry can never be silently treated as non-matching.
2. A registered entry whose path fails with ENOENT is treated as non-matching. A path that does not exist cannot be the existing target directory, so this keeps today's mid-deletion behavior.
3. `gitCommittedToRemoval` gains an injectable realpath seam, for example an optional third `{ realpath = fs.realpathSync }` argument, so a test can force a non-ENOENT failure on one entry. Existing callers keep the two-argument form.
4. The header comment above the function states the per-entry fail-closed rule alongside the existing "unreadable list fails closed" sentence.

## Acceptance Criteria

- A unit test in `tests/bin-lib/reconcile/reap-merged.test.js` injects a realpath that throws a non-ENOENT error (for example `EACCES`) for the target's registered entry, and asserts `gitCommittedToRemoval` returns `false`. Prove it goes red against the current `safeReal(wt.path) || wt.path` fallback.
- A unit test whose injected realpath throws ENOENT for a non-target entry still returns the same result as today for the target.
- The existing #2566 tests in that file (the mid-deletion finish case at `:606-617` and the dirty/locked refusal cases) pass unchanged.
- `npm test` passes in full.

## Release Note

The worktree-reap long-path fallback now refuses to force-delete when a registered worktree's path cannot be resolved, instead of treating it as already removed.

## Technical Approach

Replace the `safeReal(wt.path) || wt.path` fallback with an explicit try/catch around the injected realpath. On ENOENT, the entry is non-matching. On any other error, short-circuit the whole function to `false`. Keep `safeReal` itself unchanged, because it is shared with `flow-preflight.js`, `hooks.js`, `context.js` and `pre-tool-use.js`, and those callers rely on its null-on-any-error contract.

### Key Files

- `plugin/bin/lib/reconcile/reap-merged.js` — `gitCommittedToRemoval`: per-entry fail-closed resolution, injectable realpath, header comment
- `tests/bin-lib/reconcile/reap-merged.test.js` — non-ENOENT and ENOENT injection tests

## Gotchas

- Do not change `safeReal` in `plugin/bin/lib/hooks/worktree-detect.js`. Several other modules depend on it returning `null` for any failure. The fix belongs at this one call site.
- Fail closed means the function returns `false` as soon as any registered entry is unresolvable for a non-ENOENT reason, even if that entry might not be the target. An unresolvable entry cannot be proven not to be the target, and a false `false` only routes to the existing removal-failed escalation, which is the safe outcome.
- The mid-deletion test at `:606-617` is skipped on some platforms (`MID_DELETE_SKIP`). Check that the new injection tests do not depend on a real mid-deletion state, so they run everywhere.
