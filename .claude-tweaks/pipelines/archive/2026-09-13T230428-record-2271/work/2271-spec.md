# 2271: skills/flow, skills/review: skill guidance doesn't warn dispatched subagents that Monitor/background-task notifications never reach them

Surface: infra

## Current State

Pipeline skill guidance that instructs starting a background verification loop or subagent
dispatch and then "waiting for the notification" reads naturally as correct for a top-level
interactive session (where Monitor and background-task completion notifications do arrive) but
does not warn that a dispatched subagent (an `Agent`/`Task`-invoked session) never receives such
notifications the way a top-level session does — waiting there hangs indefinitely with no signal
anything is wrong until an external caller intervenes.

Filed via `/claude-tweaks:feedback` at plugin v6.118.0, citing a harness-level
`contract-violation` event log recording 13+ occurrences of an agent narrating "waiting for the
background task/Monitor notification to arrive" and stopping mid-turn across a single build
phase (main session and multiple dispatched subagents), plus 2 more in a separate review/wrap-up
session for the same unit of work — corrected only when an external coordinator explicitly
stated the limitation. `skills/review/step3-lens-dispatch.md`'s existing "Hung or non-responsive
single-read agent" section (current build, ~line 50) already covers the adjacent but distinct
case of a *reviewing* agent waiting on a *dispatched* agent that goes silent; it does not cover
this record's scenario — a dispatched subagent itself instructed to background a verification
loop and wait for a notification that will never arrive in its own context.

## Deliverables

- Grep this repo's skill directories fresh at build time for every place a skill instructs
  starting a background verification loop, `Monitor`, or subagent dispatch and then "waiting for
  the notification/completion" — this record's own citations (`skills/flow`, `skills/review`)
  are a starting point, not a guaranteed-current file:line list, since guidance text shifts
  between plugin versions (filed against v6.118.0; current build is newer).
- At each such location, state the limitation once, explicitly, near wherever it first
  introduces Monitor or background-task usage for a verification loop or subagent dispatch: a
  dispatched subagent does not receive Monitor or background-task completion notifications the
  way a top-level session does — run long verification loops in the foreground with a generous
  timeout instead of backgrounding them and waiting for a notification, when running as (or
  dispatching) a subagent.
- Do not duplicate the warning at every call site if a shared `_shared/*.md` fragment already
  covers dispatch mechanics for the affected skills (e.g. `_shared/subagent-dispatch-core.md`) —
  add it there once and cite it, per this codebase's own shared-contract-extraction convention,
  if that fragment is already the canonical home for dispatch-mechanics guidance the affected
  skills already cite.

## Original request

**Summary:** Pipeline skill guidance that instructs starting a background verification loop or subagent dispatch and then "waiting for the notification" does not warn that a dispatched subagent never receives such notifications the way a top-level session does.

**Kind:** Gap

**Affected component:** skills/flow, skills/review (and any other pipeline skill instructing background verification loops or subagent dispatch)

**Use case:** Pipeline skills (e.g. `/claude-tweaks:flow`'s polish/re-verify guidance, `/claude-tweaks:review`'s Step 3 dispatch notes) instruct starting a long-running background command or subagent and then "waiting for the notification" -- phrasing that reads naturally as correct guidance for a top-level interactive session, where Monitor and background-task completion notifications do arrive. They do not arrive the same way for a dispatched subagent (an `Agent`/`Task`-invoked session): waiting on one there hangs indefinitely, with no signal that anything is wrong until an external caller intervenes.

This produced a real, repeated, systemic cost on one run I observed, in a private project: the harness's own contract-violation event log recorded 13+ instances of an agent narrating "waiting for the background task/Monitor notification to arrive" and stopping mid-turn across a single build phase (main session and multiple dispatched subagents, none self-corrected mid-run), plus two more in a separate review/wrap-up session for the same unit of work -- corrected only when an external coordinator explicitly stated the limitation. The pattern recurred independently across at least three different agent instances (a build session, its dispatched implementer/reviewer subagents, and a separate review session), all following the same skill-authored background-verification patterns.

**Suggested resolution:** State the limitation once, explicitly, near wherever a pipeline skill first introduces Monitor or background-task usage for a verification loop or subagent dispatch: a dispatched subagent does not receive Monitor or background-task completion notifications the way a top-level session does -- run long verification loops in the foreground with a generous timeout instead of backgrounding them and waiting for a notification, when running as (or dispatching) a subagent.

**Evidence:** A harness-level contract-violation event log recorded 13+ occurrences during a single build phase's own event log, plus 2 more in a separately-run review/wrap-up session against the same unit of work, before an external correction stopped the pattern. Cost: at minimum two full agent turns spent narrating an unresolvable wait before correction; the build-phase recurrence count suggests a materially larger cost there, uncorrected for the run's duration.

**Definition:** Clear

**Plugin version:** 6.118.0
