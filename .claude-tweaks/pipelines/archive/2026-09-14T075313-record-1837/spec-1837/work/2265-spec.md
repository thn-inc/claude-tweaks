# 2265: Migrate Subagent Contract canonical status-line rule and subagent-stop.js detection

Surface: backend

## Overview

The Subagent Contract (`plugin/skills/_shared/subagent-output-contract.md`) currently requires
every dispatched subagent's reply to open with one of `DONE` / `DONE_WITH_CONCERNS` /
`NEEDS_CONTEXT` / `BLOCKED` as the literal first line. This has failed in production three
separate times (`#606`, `#1653`, `#1868`) despite explicit `WRONG:` examples at every dispatch
site — models reliably produce a clear concluding verdict but are unreliable at *opening* with one
before any reasoning. This unit is the keystone of a 5-unit decomposition (parent #2264): it moves
the canonical status signal to a labeled trailing line and makes the mechanical checker in
`plugin/bin/lib/hooks/subagent-stop.js` lenient about exact position. Every other unit in this
decomposition (WU2-WU5, each `Blocked by` this one) edits inline dispatch-prompt copies of the
same rule, and each of those edits must match the canonical text this unit establishes — so this
unit lands first.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Changing `subagent-stop.js`'s best-effort, non-blocking posture — it remains a diagnostic log,
  never a gate. This migration adds no new enforcement mechanism.
- Retrofitting `plugin/skills/harness-health/judge-procedure.md` (~228) or
  `plugin/skills/harness-health/SKILL.md` (~69) — their entire reply *is* the status line
  ("reply with nothing but a single status line"), so the narration-creeps-in-before-it failure
  mode this migration targets cannot occur there. Left as a follow-up for a later record.
- Changing the four status words themselves, their routing meaning, or the Template A/B/C content
  that follows the status line.
- Editing any of the other 21 dispatch-site files that carry an inline copy of the old
  position-asserting instruction — those are WU2 through WU5 in this same decomposition, each
  `Blocked by` this unit.
- Hook-side reply rewriting (stripping narration before the check runs) — rejected in the design
  doc's Rationale: it silently edits the audit trail, so the logged reply no longer matches what
  the subagent actually said.

## Technical Approach

Exactly the design doc's Decision section (New canonical format + Checker leniency subsections) —
reproduced here since the design doc is deleted once this decomposition lands:

**New canonical format.** The reply's last non-empty line must read exactly `STATUS: {WORD}`. A
labeled line, not a bare trailing word, because a bare trailing word risks colliding with prose
that happens to end in a matching token ("...the tests are done" reads as ambiguous;
"...the tests are done\nSTATUS: DONE" does not). The label makes the line unambiguous and
trivially greppable: `grep -E '^STATUS: (DONE|DONE_WITH_CONCERNS|NEEDS_CONTEXT|BLOCKED)$'` against
the last non-empty line of a reply.

**Checker leniency (subsumes rollout safety).** `subagent-stop.js`'s detection changes from "does
the first line match `STATUS_RE`" to the three-tier check in Deliverables above. This single
fallback rule does double duty: it is the mechanical leniency that tolerates ordinary model drift
(the status word landing one line off from where the contract technically wants it), and it is
also what makes the format migration itself safe with no explicit transition period to manage — a
dispatch's full round-trip (prompt sent, subagent replies, reply checked) happens within one Task
call, using whichever plugin version is loaded when the *check* runs, not when the *prompt* was
sent. An in-flight dispatch given an old-format prompt (status word first) whose reply is checked
after this migration ships is still accepted by the lenient fallback's first-K-lines check.

### Data / API Surface

The informational log variant from Deliverable 3 must be distinguishable from a hard
`contract-violation` in the logged event's own fields (e.g. an added `variant: 'lenient'` /
`variant: 'canonical'` / absent-for-hard-violation field, or equivalent) — the design doc's own
wording is "log an informational `contract-violation` event variant... visible for someone to
notice a dispatch site is still using the old shape, but never a hard failure." Name the exact
field/shape chosen in this deliverable's own commit; downstream consumers of the friction-events
log (`bin/lib/hooks/friction-events` or equivalent) are out of this unit's scope to update, per
Non-Goals — a consumer keying on the `contract-violation` event name alone (with no `variant`
check) will keep treating the informational variant as a hard violation until it is separately
updated; this is an accepted, intentional boundary of this unit's scope, not an oversight.

### Detection Boundary Rules (resolved during Step 5 red-team review)

- **Tier-2 match shape.** The lenient fallback matches either the bare status word OR a labeled
  `STATUS: {WORD}` line (tier-1's own exact pattern, just off-position) as the first token of a
  candidate line — after stripping the same optional `- ` / `**Status:**` prefixes the existing
  `STATUS_RE` already strips. Either form landing in the candidate window is lenient-compliant.
- **Window counts non-empty lines only**, matching tier-1's own "last non-empty line" convention —
  blank lines never count toward the first-3/last-3 window, and the two windows may overlap for a
  short reply (≤6 non-empty lines total); checked as a union, not a strict partition.
- **Canonical exact-match is on the trimmed line** (trailing whitespace ignored) and is
  case-sensitive — `STATUS: done` does not match tier 1 (it may still match tier 2's bare-word
  check if `done` itself were a valid word, which it isn't, so an all-lowercase reply always falls
  through to genuine-violation, unchanged from today's case-sensitive behavior).
- **Table-row exclusion.** A candidate line that is a markdown table row (starts with `|` after
  trimming) is excluded from the tier-2 window — this prevents a Template A findings table's own
  cell content (which may itself contain a matching word) from producing a false lenient-compliant
  match when the reply's real trailing status line is missing or malformed.
- **Decorated variants are an accepted gap, not a blocking one.** A bolded canonical line (e.g.
  `**STATUS: DONE**`) matches neither tier 1 exactly nor the existing prefix carve-outs (which
  target a different contract's bold `**Status:**` bullet shape, not this new line) — left
  unhandled by design, consistent with the checker's best-effort, non-blocking posture.
- The two existing false-positive carve-outs (a dispatch declaring a different contract; an absent
  `agent_transcript_path`) and `isExemptAgentType` are unaffected and still evaluated before either
  detection tier runs.
- **Template B/C placement.** The trailing status line is the reply's absolute last non-empty line,
  after all of that template's own required content — identical to every other site's rule, just
  with no findings table to follow it.

## Gotchas

- **Related:** #2036 — "SubagentStop hook misattributes contract-violation to main-session
  narration." Cross-link only, not a dependency: #2036 is a genuinely separate bug (the hook reads
  the wrong transcript source, attributing a violation to main-session narration instead of the
  actual subagent reply) in the same function this unit touches. Do not fold #2036's proposed
  exemption into this unit's scope — leave its own resolution to its own record.
- `STATUS_RE` already carries two documented false-positive carve-outs (a dispatch declaring a
  different contract shape, e.g. `superpowers:subagent-driven-development`'s bold `**Status:**`
  bullet; an absent `agent_transcript_path`) — preserve both when rewriting the detection function,
  they are orthogonal to the position-leniency change this unit makes.
- `isExemptAgentType` (third-party plugin agent exemption, `#1596`) is untouched by this migration
  — it gates whether the check runs at all, not how the status line is located within a reply that
  does get checked.
- The two structurally-immune harness-health files (Non-Goals above) already comply with the *old*
  first-line rule by construction ("nothing but a single status line") and will also comply with
  the *new* trailing-line rule by the same construction (their one line is simultaneously first and
  last) — no migration risk there, which is exactly why they're a low-priority follow-up rather
  than in-scope here.
- Keep `subagent-stop.js`'s best-effort, non-blocking posture completely unchanged — this is a
  detection-shape change only, never a new gate.
- **Accepted duplication tradeoff (raised in Step 5 red-team).** This decomposition's other 4
  units (WU2-WU5) each carry their own inline dispatch-prompt copy of the same canonical rule
  rather than a single centralized reference — consistent with how every dispatch site in this
  plugin already works today (agents only see their own prompt; a shared-file reference would not
  reach them, per the Subagent Contract's own "Letting agents read sibling files" anti-pattern).
  Centralizing the canonical *text* into one file the *human maintainer* edits once (as opposed to
  what each dispatched *agent* sees) is a real architectural question worth its own record, but is
  out of scope for a status-line migration and not required for this unit's acceptance.
