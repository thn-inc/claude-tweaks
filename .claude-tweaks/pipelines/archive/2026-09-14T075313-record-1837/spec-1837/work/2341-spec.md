# 2341: bin/verify.js: only one reserved "types" check name, but a monorepo can have N independent typecheck commands

Surface: infra

## Current State

`bin/verify.js` (the shared `/claude-tweaks:test` and `/claude-tweaks:build` verification
runner) reserves only one `"types"` check name for the fail-fast-before-tests tier, alongside
`"lint"` — confirmed by grep: the literal strings `'types'`/`'lint'` are hardcoded at multiple
points (`verify.js:212`'s `allowed` set, `:265`'s static-check branch, `:281`'s `staticNames`
filter, `:387` and `:451`'s `suitesRun` filters). A monorepo can have multiple independent
typecheck commands with no way to give more than one that treatment.

A pnpm/npm workspace monorepo with multiple independently-typed packages (e.g. three packages
each needing their own `tsc --noEmit`, with no single command that covers all three) wants
typecheck and lint to run independently of whether `tests` happens to pass. Naming the extra
typecheck commands something else (e.g. `types-core`, `types-worker`, `types-web`) demotes them
to the "any other name" tier, which runs serially **after** `tests` succeeds under the same
fail-fast policy — so when `tests` fails for a reason unrelated to any of the typechecks (e.g. a
flaky test-hook timeout under concurrent machine load), all three typechecks get skipped
(`skipped: fail-fast`) even though none of them actually depend on `tests` passing. A caller then
has to notice the `skipped: fail-fast` rows and re-run each typecheck command by hand, outside
the runner, to get a real signal.

Reproduction: `node bin/verify.js --cmd types-core="..." --cmd types-worker="..." --cmd
types-web="..." --cmd lint="..." --cmd tests="..."` where `tests` fails for any reason —
`report.json` shows `types-core`/`types-worker`/`types-web` as `{"skipped": "fail-fast"}` even
though each is independent of `tests`.

## Deliverables

Choose and implement one of:

- **(a) Widen the reserved tier**: let multiple checks share the reserved pre-`tests` tier — e.g.
  any `--cmd` name prefixed `types:` or `types-` joins the same concurrent-with-lint,
  fail-fast-before-tests group the single `types` name gets today. This requires updating every
  hardcoded `'types'`/`'lint'` comparison site (`verify.js:212`, `:265`, `:281`, `:387`, `:451`)
  to a prefix-match instead of an exact-string match.
- **(b) Document the workaround**: explicitly document that a monorepo with N independent
  typecheck commands should invoke them as their own `verify.js` call, or combine them into one
  compound `--cmd types="a && b && c"`, rather than as N separately-named checks — so the
  fail-fast-skip behavior is expected rather than surprising.

## Acceptance Criteria

- Whichever option is chosen, a monorepo with multiple independent typecheck commands has a
  documented, working path to get fail-fast-before-tests treatment for all of them (not just one
  named `types`) — either because the runner now supports it natively (option a), or because the
  documented workaround (a compound `--cmd` or multiple `verify.js` invocations) is proven to
  work and is referenced from `bin/verify.js`'s own usage/help text or its skill documentation.
- If option (a): every one of the five hardcoded `'types'`/`'lint'` comparison sites is updated
  consistently — a partial update (e.g. widening the `allowed` set at line 212 but not the
  `suitesRun` filters at 387/451) would produce an inconsistent runner.
- `npm test` passes.

## Technical Approach

Read all five call sites (`verify.js:212, 265, 281, 387, 451`) together before choosing an
approach — they must all agree on what counts as a "types-tier" check name, or the runner's
own internal bookkeeping (`suitesRun`, `staticNames`, the `allowed` set) will disagree with each
other. If choosing (a), define the widened match once (a shared predicate or regex, e.g.
`/^types(-|$)/`) and use it at every site rather than duplicating the pattern five times. If
choosing (b), the fix is documentation-only — add the guidance to `bin/verify.js`'s own
`--help`/usage text and to whichever skill file documents its `--cmd` naming convention for
callers.

### Key Files

- `plugin/bin/verify.js` (lines 212, 265, 281, 387, 451) — the five call sites that would need a
  consistent widened match under option (a)
- Skill documentation for `/claude-tweaks:test` / `/claude-tweaks:build`'s verify.js invocation
  convention — where option (b)'s guidance would live, or where option (a)'s new naming
  convention would need documenting either way

## Gotchas

- This is a genuine design choice between (a) runner capability vs. (b) documented workaround —
  the record's own Deliverables frame both as valid; don't treat one as obviously correct without
  weighing the blast radius of changing shared verification-runner logic (option a) against the
  lower-risk, purely-documentary option (b).
- If choosing (a), verify the widened match doesn't accidentally capture an unrelated check name
  a caller might legitimately want in the post-tests tier (e.g. a check literally named
  `types-of-fun` that has nothing to do with typechecking) — a prefix match on `types-`/`types:`
  is a judgment call about false-positive risk, not a free lunch.
