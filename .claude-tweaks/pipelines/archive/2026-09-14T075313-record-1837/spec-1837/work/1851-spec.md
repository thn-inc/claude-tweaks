# 1851: docs-health: a staleness record's `Doc:` field and title carry the registry doc id (relative to `docs/`, no extension), not a repo-relative path — the named location does not resolve verbatim

Surface: infra

## Current State

`toIssuePayload` (`plugin/bin/lib/docs-health/issue-payload.js`) renders the header line as `**Doc:** ${finding.target} | **Section:** … | **Category:** … | **Misleads:** … | **Classification:** …` and the title as `Doc {category}: ${finding.target} — ${finding.section}`, where `finding.target` is the registry doc id: `scope.js` walks `docs/**` and sets `id` to the path relative to `docs/` with the `.md` extension stripped (`{ kind: 'doc', id, path }`, `path` being the absolute file path). The judge template writes `"target": "{target.id}"` into every finding, `validate-finding.js` requires `target` as a string, and the fingerprint basis is `['assetType', 'target', 'section', 'description']` (`fingerprint.js`), so `target` must stay the id for dedup and for the `--target <id>` round-trip. Nothing in the filed body states the repo-relative path; `flow/materialize.md`'s "Named-location drift (#315)" then tells every builder to treat `plans/2026-08-30-…-ledger` as a hypothesis and grep for it, on a location the filer itself mis-stated.

Observed on plugin 6.114.1 across two consecutive dispatch builds in a downstream project: each build located the doc by grepping for the stale hash and logged the `plans/` → `docs/plans/` mismatch as a ledger observation. This repository's own open docs-health records carry the same shape in their titles (`Doc staleness: plans/…-ledger — Freshness`).

The id → path mapping is a pure function (`docs/{id}.md`), so no new finding field or CLI output is needed to render a resolvable location. `tests/bin-lib/docs-health/issue-payload.test.js` pins that the body starts with `**Doc:**` and carries the fingerprint marker.

## Deliverables

- [ ] **Resolvable location in the body and title, id kept for identity.** In `toIssuePayload`, derive `docPath = docs/${finding.target}.md` and render the header as `**Doc:** {docPath} | **Id:** {finding.target} | **Section:** … | …` (the remaining fields unchanged) and the title as `Doc {category}: {docPath} — {section}`. `finding.target`, the fingerprint basis, `payload.target`, and the marker stay byte-identical, so existing records still dedup against new findings for the same doc and section.
- [ ] **Nested-docs correctness.** For an id containing directory segments (`plans/2026-…`), `docPath` is `docs/plans/2026-….md`; for a `--dir <path>` audit that walks a root other than `docs/`, use that root as the prefix (`scope.js` exposes it, or thread the resolved `docsRoot` alongside `verifiedAsOf`), never a hardcoded `docs/`.
- [ ] **Prose.** `skills/docs-health/SKILL.md` Step 6 (filing) gains one sentence: the body's `Doc:` field is the repo-relative path and `Id:` is the registry id `--target` accepts. `flow/materialize.md`'s Named-location drift paragraph gains a clause: a `by:docs-health` record's `Doc:` path is resolvable as written and needs only an `ls`, not a grep.
- [ ] **Tests.** `issue-payload.test.js`: the header starts with `**Doc:** docs/{id}.md` and carries `**Id:** {id}`; the title uses the path; `payload.target` and the fingerprint are unchanged for the same input (assert equality against a fixture computed before the change); a nested id renders `docs/plans/….md`; a non-default docs root renders under that root. A prose pin for the two sentences.

## Acceptance Criteria

1. For a finding with `target: 'plans/2026-08-30-x-ledger'`, `toIssuePayload` renders a body starting with `**Doc:** docs/plans/2026-08-30-x-ledger.md | **Id:** plans/2026-08-30-x-ledger |` and a title `Doc {category}: docs/plans/2026-08-30-x-ledger.md — {section}`.
2. `payload.target`, `payload.fingerprint`, and `extractFingerprint(payload.body)` are identical before and after the change for the same finding, pinned by a test.
3. Filing the same finding twice still dedups (the existing dedup path keyed on the fingerprint marker is unchanged, covered by the existing dedup tests).
4. `SKILL.md` Step 6 and `materialize.md` carry the sentences above once each.
5. `npm test` green; every existing case in `tests/bin-lib/docs-health/` passes with only the two header/title assertions updated.

## Technical Approach

Render, don't re-key: the id remains the identity everywhere (fingerprint, `--target`, `payload.target`), and only the human-facing header and title change to the resolvable path. Compute the path in the payload composer from the id and the docs root rather than adding a `path` field to the finding schema, so the judge template and `validate-finding.js` are untouched. Records already filed keep their old text; nothing rewrites them.

### Key Files

- `plugin/bin/lib/docs-health/issue-payload.js` — `docPath` derivation; header `Doc:`/`Id:` fields; title
- `plugin/bin/docs-health.js` — thread the resolved docs root into `toIssuePayload` only if `--dir` audits need a non-`docs/` prefix
- `plugin/skills/docs-health/SKILL.md` — Step 6 sentence
- `plugin/skills/flow/materialize.md` — Named-location drift clause
- `tests/bin-lib/docs-health/issue-payload.test.js` — updated header/title assertions; identity-stability, nested-id, and docs-root cases

## Gotchas

- The `**Doc:**` prefix is pinned by an existing test ("body starts directly with the header line"); keep the field first so that assertion needs only its expected value changed.
- `harness-health`, `code-health`, and `journey-health` payloads have their own header conventions; this change is docs-health only.
- Titles are not a dedup key (dedup is fingerprint-marker based), so the title change cannot re-file already-tracked findings; state that in the PR description with the dedup test named.
- A `--target <id>` invocation still accepts the id; do not accept the path there, or the round-trip contract in `SKILL.md`'s CLI section changes.

## Original request

**Summary:** `/claude-tweaks:docs-health` files its records with `**Doc:** {target}` where `{target}` is the sweep's doc id — "the doc's path relative to `docs/`, without the `.md` extension" (the same id `--target <id>` accepts). The record's title reuses it. A reader or builder who takes the record at its word (`plans/2026-08-30-spec-253-254-255-digest-full-page-ledger`) looks for a top-level `plans/` directory that does not exist; the file is `docs/plans/2026-08-30-spec-253-254-255-digest-full-page-ledger.md`. Every docs-health record therefore ships with a named location that `flow/materialize.md`'s "Named-location drift" note (#315) tells the builder to treat as a hypothesis and grep for — drift that the filer itself introduces, on every record, rather than drift that a later refactor caused.

**Kind:** Gap

**Affected component:** `bin/lib/docs-health/issue-payload.js` (the `**Doc:** ${finding.target} | **Section:** …` kind line and the derived title), i.e. `/claude-tweaks:docs-health` Step 6's filing payload; the same id also drives the record's `docshealth-*` fingerprint, so any change must keep the fingerprint basis stable.

**Use case:** Two consecutive dispatch-driven builds of docs-health records against a downstream project (records for `plans/2026-08-31-finish-rebrand-repo-folder-rename-ledger` and `plans/2026-08-30-spec-253-254-255-digest-full-page-ledger`) each had to locate the target by grepping for the stale hash the record described, then log the `plans/` → `docs/plans/` mismatch as a build-ledger observation. The upstream repository's own docs-health backlog shows the same shape (`Doc staleness: plans/2026-08-25-record-1424-ledger — Freshness`, etc.), so this is the filer's convention, not a downstream configuration.

**Suggested remedy:** Keep the doc id for the fingerprint and the `--target` round-trip, but make the record body state a resolvable location — e.g. `**Doc:** docs/plans/…-ledger.md` (repo-relative, from `next-target`'s `path` field, which the CLI already returns alongside `id`) with the bare id retained in a separate `**Id:**` field or the fingerprint comment. Alternatively keep `Doc:` as the id but add a `**Path:** {repo-relative}` field beside it, so `materialize.md`'s named-location verification has a path to `ls` instead of a grep target to infer.

**Definition:** Clear
