# 1983: docs-health filings and tidy's cleanup sweep aren't coordinated -- a docs-health-filed ledger correction can target a file tidy is about to delete

Surface: infra

## Current State

Three skills touch the same fact, "does the doc a `by:docs-health` record names still exist", at three different times, and only one of them acts on it:

- `/claude-tweaks:docs-health` files a record from a scan of the doc as it exists at scan time; `bin/lib/docs-health/issue-payload.js` renders the doc id in the `Doc:` header (a repo-relative path once #1851 lands). Re-verifying at filing time cannot help here: in the observed case the deletion happened *after* filing and *before* dispatch.
- `/claude-tweaks:tidy` proposes deleting orphaned `docs/plans/*-ledger.md` files (`scan-procedures.md`'s ledger glob) with a "quick judgment read" that no open record references the ledger's filename or slug, and its GitHub issue scan separately proposes closing a `by:docs-health` record whose flagged doc is gone (this sweep staged exactly that: `staged/tidy-close-issue-1.md` for #1878, deleted in #1969, and `staged/tidy-close-issue-2.md` for #1776, deleted in #1819). Both are judgment reads and both wait for `tidy --approve`.
- `/claude-tweaks:dispatch`'s queue pull (`queue-pull-script.md`) excludes blocked, oversized, and open-linked-PR records (#1224) but never checks whether a record's named target exists at the integration tip; `flow/materialize.md`'s Named-location drift note (#315) leaves that to the builder, inside the build.

Observed 2026-09-05/06: #1776, #1804, and #1818 each burned a build attempt against the retry ceiling and stopped at the HARD-GATE because tidy PR #1819 had deleted their target ledgers; every failure was handled correctly and every build was wasted. #1984 (sibling, shaped alongside this record) covers the neighbouring case, a record whose deliverables are already shipped on `main`, at the same pre-flight site.

## Deliverables

- [ ] **Named-target extraction, once.** `plugin/bin/lib/issues/named-target.js` exporting `namedTarget(record) → { path } | null`: for `by:docs-health` records, the `Doc:` header value when it is a repo-relative path, else `docs/{id}.md` derived from the pre-#1851 id form; for other origins `null` (this record does not guess targets from prose; #1769's marker and #1829's `Premise-check:` line cover authored claims).
- [ ] **Dispatch excludes a record whose target is gone.** `dispatch/queue-pull-script.md`: after the open-linked-PR exclusion, for every eligible record with a non-null `namedTarget`, test existence at the integration tip (`git cat-file -e {ref}:{path}`, one spawn per such record, never a checkout read); a missing path excludes the record into `dispatch-target-missing-excluded.json`, logs `AUTO … — dispatch: #N excluded, named target {path} absent at {ref}`, and stages one Close proposal per excluded record in the run's `staged/` using tidy's `Close (GitHub)` proposal shape (`Finding`/`Proposed`/`Rows`/`Commands`), so the next `tidy --approve` closes it and no build is minted. The record keeps its labels; nothing is written to GitHub by dispatch.
- [ ] **Tidy's delete proposal bundles the closes.** `tidy/scan-procedures.md`'s ledger Delete recommendation replaces the "quick judgment read" with a mechanical pass over the session record snapshot: every open record whose `namedTarget` (or body text) names the ledger's path or slug is listed in the same staged Delete proposal as a Close row, so approval deletes the file and closes its records in one action; no ledger is deleted while a referencing record stays open and unproposed.
- [ ] **Tests.** `tests/bin-lib/issues/named-target.test.js` (both header forms, non-docs-health → `null`). A prose pin (sized like `tests/dispatch-*` conformance tests) asserting the queue-pull exclusion step, its log line, the staged-close shape, and `scan-procedures.md`'s mechanical Close-row rule; `docs/plugin-structure.md` lists the module.

## Acceptance Criteria

1. `namedTarget` returns `docs/plans/x-ledger.md` for a `by:docs-health` record in either header form and `null` for a `by:capture` record.
2. In a fixture queue where a `by:docs-health` record's target is absent at the integration tip, the queue pull writes the record to `dispatch-target-missing-excluded.json`, logs the line, stages a Close proposal, mints no run directory for it, and selects the remaining records exactly as before.
3. A tidy run whose ledger Delete proposal targets a file named by an open record renders that record as a Close row inside the same proposal.
4. Replaying #1776/#1804/#1818 against a tip where #1819 has merged yields three exclusions and three staged closes and zero build attempts; quoted in the PR description.
5. `npm test` green; existing dispatch and tidy conformance tests pass with only additive assertions.

## Technical Approach

Put the check where the wasted work starts (dispatch), reuse the proposal shape tidy already uses so approval stays one surface, and make tidy's own delete step carry its consequences instead of relying on a judgment read. Reject (a): re-verifying at filing time cannot see a later deletion. Keep the target extraction narrow (docs-health only) so this record never guesses at authored prose; the sibling #1984 adds the "already shipped" heuristic at the same pre-flight site with its own false-positive posture.

### Key Files

- `plugin/skills/dispatch/queue-pull-script.md` — target-existence exclusion, log line, staged Close proposal
- `plugin/skills/tidy/scan-procedures.md` — ledger Delete proposal bundles Close rows mechanically
- `tests/bin-lib/issues/named-target.test.js`, a dispatch/tidy prose-pin sibling — new cases

## Gotchas

- Existence is checked at the integration tip, not the working tree: a worktree session's tree may lag, and a dirty tree must not hide a deletion.
- The queue-order cache (#1571) persists groups/excluded; the new exclusion must be part of the persisted `excluded` so a cache hit does not resurrect the record.
- `tidy --approve` applies staged proposals; dispatch writing into `staged/` under its own run dir is the same shape sweep uses (attention's Tidy row globs `*-sweep-standalone*`; add the dispatch run-dir glob there only if the row must surface these too, and say so in the record if it does).
- Never close on GitHub from dispatch; the staged proposal is the write path and stays human-approved.

## Original request

Surface: infra

## Current State

During a `/claude-tweaks:dispatch --budget all` drain (2026-09-05/06), three separate docs-health-filed records (#1776, #1804, #1818) all hit an identical build-time HARD-GATE: their target `docs/plans/*-ledger.md` file had already been deleted by an unrelated tidy sweep (PR #1819, "Tidy: delete 2 completed execution plans + 8 orphaned pipeline ledgers") before the dispatch drain ever reached them. Each record's own Acceptance Criteria was unsatisfiable -- there was nothing left to edit. All three were caught cleanly by the build gate and Settle's failure-classification path (no code lost, no false auto-merge, no auto:build stripped prematurely), but three separate build attempts were wasted on a coordination gap between two of this plugin's own health-sweep/hygiene skills.

## Deliverables

- [ ] Decide and implement one of: (a) docs-health's own filing step re-verifies the target file/row still exists immediately before creating a record (a live check, not just at scan time), or (b) tidy's cleanup sweep checks for an open issue referencing a ledger file before deleting it, or (c) some combination of both
- [ ] Add regression coverage for whichever mechanism is chosen

## Acceptance Criteria

1. A docs-health-filed record whose target was deleted between filing and dispatch either never gets `auto:build` in the first place, or dispatch recognizes the mismatch and skips/closes it without burning a build attempt against the retry ceiling
2. Existing docs-health and tidy test suites still pass

## Technical Approach

Two independent skills currently operate with no shared state about "in-flight backlog records reference this file" -- docs-health's scan-and-file step and tidy's own cleanup sweep. The cheapest fix is likely (a): a live existence check right before the record-creation write in docs-health's own filing path, at negligible cost since it's already reading the file to compute the finding. (b) is more invasive (tidy would need to grep open issues for a path reference before every delete) but closes the gap from the other direction too.

### Key Files

- `plugin/skills/docs-health/SKILL.md` (or its filing sub-file) -- filing step
- `plugin/skills/tidy/SKILL.md` / `step-6-auto.md` -- the cleanup sweep that deleted the ledgers in PR #1819

## Gotchas

- Whichever fix is chosen must not slow down docs-health's or tidy's own sweep meaningfully -- both already run against a large repo tree.

Filed per this project's no-implicit-deferrals rule -- discovered live during a `/claude-tweaks:dispatch` drain (three independent instances, same root cause), real and reproducible, but out of scope for that drain's own per-record diffs.
