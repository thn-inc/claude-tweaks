# 1886: ceremony-profile propagation: no "fast mode" reaches the superpowers brainstorming/writing-plans handoff

Surface: backend

## Overview

Feedback report: claude-tweaks' ceremony concept never reaches the `/superpowers:brainstorming` handoff, so a user who wants a lower-ceremony architectural design pass (fewer per-section approval stops) has no sanctioned way to get one — they discovered "just say 'no need to present all sections - just go'" only by trial, mid-session.

**Design resolved before shaping (the record's own three candidate directions):** the record's own framing of option (a) — "propagate `ceremony-profile` into the handoff" — doesn't hold up. `ceremony-profile` (`_shared/ceremony-profile.md`) is **diff-derived per #1545**: it's computed from a run's actual code changes, which don't exist yet at the point brainstorming runs for a from-scratch design (the user's exact case — a brand-new subsystem, no code yet). There is no existing signal to propagate at that point in the lifecycle. Option (c) — a claude-tweaks-owned light design wrapper reimplementing brainstorming's Q&A/section-by-section flow — is rejected as disproportionate: it would duplicate a substantial third-party (superpowers) skill's own logic for a gain fully covered by the cheaper alternative below, and creates exactly the "two places that can drift" risk this repo avoids elsewhere.

The actual fix: (1) a new **static** policy key (`.claude-tweaks/policy.yml`, read before any run starts — unlike the diff-derived per-run `ceremony-profile`), read at `/specify`'s own brainstorming-invocation sites (the only claude-tweaks-owned points that call `/superpowers:brainstorming`) and passed as an explicit natural-language instruction into the `Skill` tool's `args`, asking the session to consolidate per-section approvals into one combined presentation once the decision-carrying clarifying questions are answered and the approach is chosen — never removing the final approval gate (`_shared/ledger-format.md`/brainstorming's own HARD-GATE stays intact; this reduces *how many times* it's asked, not *whether*); (2) documenting the ad-hoc "just go" convention the user actually used, as a sanctioned override for any single session regardless of the policy default.

**Complexity:** Medium
**Estimated tasks:** 3-4

## Non-Goals

- Modifying `superpowers:brainstorming` itself — it's a third-party plugin file; this spec only changes what instructions get embedded in claude-tweaks' own invocation of it.
- A claude-tweaks-owned design wrapper reimplementing brainstorming's flow (option c) — rejected above as disproportionate.
- Propagating the diff-derived `ceremony-profile` signal into brainstorming — rejected above; no such signal exists yet at brainstorm time for new work.
- Changing brainstorming's behavior for the Spike or Bounded paths — those already present a short in-chat design with a single approval; only the Architectural path's per-section gating is addressed here.

## Technical Approach

Mirror the existing pattern other `pipeline-behavior` policy keys already use (read via `resolve-policy.js`, gate a behavior change on the resolved value) rather than inventing a new plumbing mechanism. The instruction text is inlined into the `Skill` tool's `args` string — the same mechanism `/claude-tweaks:specify` already uses to pass the record's title/body or topic as brainstorming's input — so no new invocation seam is needed, only conditional text composition before the existing call.

- `plugin/skills/specify/SKILL.md` — the three invocation sites (~lines 81, 89, 90) and the new "just go" documentation note

## Gotchas

- Do not name the new key `ceremony-profile` or anything that reads as an alias of the existing diff-derived concept (`_shared/ceremony-profile.md`) — they are genuinely different mechanisms (static project policy vs. per-run diff-derived signal) and conflating the names would mislead a future reader into thinking one derives from or controls the other.
- The consolidation instruction must never claim to skip the final approval gate — brainstorming's own HARD-GATE ("Do NOT invoke any implementation skill... until approved") is a third-party invariant this spec does not and cannot override; the instruction only asks for fewer *mid-design* approval stops, not zero approvals.
- This only reaches brainstorming when invoked via `/specify`'s three owned call sites. A user invoking `/superpowers:brainstorming` completely standalone (outside any claude-tweaks skill) is out of this spec's reach by construction — document the "just go" convention as the fallback for that case too, since it works regardless of invocation path.

## Original request

**Summary:** claude-tweaks' ceremony profile (fast-lane vs standard) never reaches the superpowers skills it hands design work to, so there is no supported way to run superpowers:brainstorming / writing-plans in a low-ceremony "fast mode".

**Kind:** Gap

**Affected component:** ceremony-profile propagation to superpowers handoffs (build / specify → superpowers:brainstorming, superpowers:writing-plans)

**Use case:**
In a private project, a new subsystem (an overhang/support detector for 3D-print slicing) was brainstormed through the superpowers brainstorming skill that claude-tweaks delegates architectural design to. That skill's architectural path presents the design section by section, with an approval prompt after every section. After the two decision-carrying questions (gate policy, source of truth) and the approach choice were answered, the user stopped the ceremony: "no need to present all sections - just go", and asked that claude-tweaks' maintainer be told they would like a fast mode for superpowers as well.

claude-tweaks already has a ceremony concept of its own (`ceremony-profile: fast-lane | standard` in the run's config.yml, derived from the diff for headless firings per #1545, with a condensed fast-lane digest proposed in #1765) — but it is scoped to claude-tweaks' own review/wrap-up phases. Nothing carries that setting into the superpowers skills the pipeline invokes, and nothing documents a sanctioned low-ceremony way to run them. The user's desired shape: keep the two or three questions that carry a real decision up front, then go straight to the written spec → plan → execution with the spec-review gate as the single approval point, instead of an approval after every design section.

Possible directions: (a) have build/specify pass a ceremony hint into the superpowers handoff (e.g. an explicit "light" instruction in the invocation that tells brainstorming to skip per-section approvals once the approach is approved), (b) document in claude-tweaks' handoff docs that the user may say "just go" and that the pipeline treats that as fast-lane for the remainder of the design step, or (c) ship a claude-tweaks-owned light design wrapper. This is the same family as #771 (a superpowers skill with no awareness of a claude-tweaks mode).

**Definition:** Needed — three viable directions above (propagate a hint into the handoff, document a "just go" convention, or wrap the design step), no preference stated by the user beyond wanting a fast mode.
