# 1447: reconcile: move-failed stuck on /Users/thomasholknielsen/Code Workspaces/claude-tweaks/.claude-tweaks/pipelines/2026-08-20T193642-record-231

Surface: backend

**Related:** #1446

## Current State

Reconcile's convergence check 4 (`plugin/bin/lib/reconcile/archive-merged.js`) archives run
directories whose PR has merged. When a `git mv`/`fs.renameSync`/`fs.mkdirSync` call inside
`archiveRunDir` or `archiveOrphanedMint` throws, the surrounding `catch {}` block discards
the caught error entirely and returns `{ ok: false, reason: 'move-failed' }` with no record
of *why* the filesystem operation failed (four sites: `archiveOrphanedMint`'s top-level
catch, the top-level entries loop, the per-spec `mkdirSync`, and the per-spec entries loop).

`trackArchiveResult` (the #644 Deliverable 2 choke point that runs the consecutive-failure
counter and escalation) forwards `result` into `recordResidueFailure` and `escalateResidue`
but never passes a `lastError` — even though both already accept and render one:
`cache.js`'s `recordResidueFailure` takes an optional `lastError` option, and
`escalate-residue.js`'s `residueBody` renders a `**Last error:** {lastError}` line when
present. The sibling check in the same module family, `reap-merged.js`'s
`trackReapResidue`, already threads `lastError: rm.failure` (the captured git-worktree-remove
error text) through to both calls — `archive-merged.js` is the one convergence check that
doesn't follow this pattern.

The result: reconcile has now escalated three consecutive `move-failed` passes on the same
run directory (#1447, `.claude-tweaks/pipelines/2026-08-20T193642-record-231`) into a filed
issue with no `**Last error:**` line at all — there is no way to tell from the issue whether
this is `EACCES`, `ENOENT`, `EEXIST`, `ENOTEMPTY`, `EXDEV` (cross-device rename), or something
else, so the stuck path can't be diagnosed without reproducing it locally.

## Deliverables

- Every `catch` block in `archiveOrphanedMint` and `archiveRunDir` that currently returns
  `reason: 'move-failed'` (or `'move-failed-partial-revert'`) binds the caught error and
  includes it as `lastError` (the error's `.message`) on the returned result object.
- `trackArchiveResult` reads `result.lastError` and forwards it into both the
  `recordResidueFailure(root, 'move-failed', dir, { lastError })` call and the `escalate({
  ..., lastError })` call — mirroring `reap-merged.js`'s `trackReapResidue` exactly.
- No behavior change to the mkdir-failed/git-mv-failed/commit-failed/ls-files-failed/
  readdir-failed/tracked-entry/close-failed reasons or to any non-`move-failed` code path —
  this is additive diagnostic threading only, scoped to the `move-failed` family.

## Acceptance Criteria

- A unit test on `archiveRunDir` (or `archiveOrphanedMint`) that forces an `fs.renameSync`/
  `fs.mkdirSync` throw asserts the returned result carries a non-empty `lastError` string
  containing the underlying error's message.
- A unit test on `trackArchiveResult` — alongside the existing threshold/escalation tests in
  `tests/bin-lib/reconcile/archive-merged.test.js` (search `trackArchiveResult`) — asserts
  that when `result.lastError` is set, the injected `escalate` fake is called with a matching
  `lastError` field, and that `recordResidueFailure`'s cache entry for the path also carries
  it (readable back via the cache file's `residueFailures[reason:path].lastError`).
- `pnpm test` equivalent for this repo (`npm test`) passes, including the full
  `tests/bin-lib/reconcile/` suite.
- No change to `escalate-residue.js`, `cache.js`, or `reap-merged.js` — both already support
  `lastError` end-to-end; only `archive-merged.js`'s catch sites and `trackArchiveResult`
  change.

## Technical Approach

In `plugin/bin/lib/reconcile/archive-merged.js`:

1. `archiveOrphanedMint` — change `catch {` to `catch (err) {` and add `lastError: err &&
   err.message` to the returned `{ ok: false, reason: 'move-failed', ... }` object.
2. The top-level entries loop inside `archiveRunDir` (the `fs.renameSync(src, dest)` call
   whose catch calls `revertPlainMoves`) — bind the error the same way and include
   `lastError` on both the `'move-failed'` and `'move-failed-partial-revert'` return paths.
3. The per-spec `fs.mkdirSync(specArchiveDir, ...)` catch — same treatment.
4. The per-spec entries loop's `fs.renameSync(src, dest)` catch — same treatment as (2).
5. `trackArchiveResult` — thread `result.lastError` into the `recordResidueFailure` call's
   options object and into the `escalate({...})` call's payload, matching
   `reap-merged.js`'s `trackReapResidue` (`plugin/bin/lib/reconcile/reap-merged.js`) line for
   line.

This does not retroactively add diagnostics to #1447's already-filed issue (its `lastError`
was never captured), but the next time reconcile escalates a still-`move-failed` path — on
#1447's own path, if it's still stuck, or any future occurrence — the filed issue will carry
a real `**Last error:**` line, making the underlying cause diagnosable without reproducing it
locally. Whether to manually re-run reconcile against #1447's specific stuck path (on the
machine where it lives) to capture and act on the newly-surfaced error is a follow-up, not
part of this record's scope.

### Key Files

- `plugin/bin/lib/reconcile/archive-merged.js` — bind caught errors at all four `move-failed`
  catch sites; thread `result.lastError` through `trackArchiveResult`
- `plugin/bin/lib/reconcile/reap-merged.js` — reference pattern (`trackReapResidue`) to mirror
- `tests/bin-lib/reconcile/archive-merged.test.js` — add lastError-threading coverage next to
  the existing `trackArchiveResult` tests

## Gotchas

- `recordResidueFailure` (`cache.js`) already falls back to a prior stored `lastError` when a
  new call omits one (`lastError || (existing && existing.lastError) || null`) — passing
  `undefined`/`null` on a call that genuinely has no error is safe and matches existing
  behavior; only the `move-failed`-producing catch sites need a real value threaded through.
- Don't widen this to capture `err.code` (e.g. `EACCES`) in addition to `.message` — `.message`
  already contains the code on Node's standard fs errors (e.g. `"EACCES: permission denied,
  rename '...' -> '...'"`), and `reap-merged.js`'s existing pattern (`rm.failure`, a plain
  string) sets the precedent for a single string field, not a structured error object.
- The four catch sites are independent — a partial-revert path (`revertPlainMoves`) already
  runs before the return in two of them; capturing `lastError` must not change what gets
  reverted or when, only what's attached to the return value afterward.
