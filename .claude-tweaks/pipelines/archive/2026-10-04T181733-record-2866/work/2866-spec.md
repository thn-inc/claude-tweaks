# 2866: docs-health: verify proposed replacement text against unshallowed history before filing

Surface: infra

## Current State

`/claude-tweaks:docs-health` filed #2785 proposing replacement text for a dangling commit-hash
citation ("squashed into `15553cf`", "`41dc8424f` is not a resolvable object in this repository").
#2785's own build phase, running against full history, found both claims in the *proposed
replacement* were wrong: `41dc8424f` is a real commit that is unreachable from `main`, and
`15553cf` never touches the files in question (the actual landing commit is `cdb32b046`). The
record had to be corrected against its own proposed fix text.

Verified on main at shaping time (2026-10-04): `plugin/skills/docs-health/judge-procedure.md`
point 6 tells the judge to check stated facts against `git log`, but nothing under
`plugin/skills/docs-health/` or `plugin/bin/lib/docs-health/` checks whether a cited or proposed
commit hash exists or is reachable from the integration branch, and nothing detects a shallow
clone (`git grep` for `is-shallow-repository` / `unshallow` under `plugin/bin` returns nothing).
The existing mechanical checks follow one pattern: a helper in `plugin/bin/lib/docs-health/`,
exposed as a `bin/docs-health.js` subcommand (for example `check-freshness`), called from the
judge procedure's prose.

A first dispatch attempt (run `2026-10-04T180312-record-2866`) stopped at `/flow`'s materialize
gate because this record lacked a Release Note; no code was written.

## Deliverables

1. A helper in `plugin/bin/lib/docs-health/` that classifies a commit hash against full repository
   history into one of four outcomes: reachable from the integration branch; exists but
   unreachable from it; does not exist; unverifiable (history could not be made complete, so no
   verdict is given).
2. A `bin/docs-health.js` subcommand exposing it (for example
   `verify-commit <sha>... --root <dir> --integration-branch <name>`), JSON output, following the
   existing subcommands' argument and exit-code conventions.
3. `judge-procedure.md` point 6: for any finding whose Proposed text cites a commit hash (or
   whose Current text is a dangling-hash citation), run the subcommand on every hash in the
   Proposed text before filing, and either file only verified-reachable hashes or mark the
   citation explicitly as unresolvable or unreachable in the Proposed text.
4. Tests covering the four outcomes against real throwaway git repositories, including a shallow
   clone.

## Acceptance Criteria

- A proposed hash reachable from the integration branch classifies as reachable; a hash that
  exists but is unreachable from it classifies as exists-unreachable; an unknown hash classifies
  as not-found. Each is asserted in a committed test against a real git repository.
- In a shallow clone, the helper never reports reachable or not-found from the shallow view
  alone: it either completes history first and then classifies, or returns unverifiable.
  Asserted in a committed test that builds a real shallow clone.
- `judge-procedure.md` point 6 instructs the filing pass to run the subcommand on every commit
  hash in a finding's Proposed text before filing, and a conformance test fails if that
  instruction is removed.
- `npm test` passes.

## Release Note

Documentation health checks no longer propose a replacement commit citation without first
checking that the commit exists and is reachable in the repository's full history.

## Technical Approach

Follow the `check-freshness` pattern: pure classification logic in a new
`plugin/bin/lib/docs-health/` module over an injectable git runner (the repo's
`gh-api-module-pattern` seam), with `bin/docs-health.js` doing argument parsing and output.
Existence is `git cat-file -e <sha>^{commit}`; reachability is
`git merge-base --is-ancestor <sha> <integration-ref>`. Shallow detection is
`git rev-parse --is-shallow-repository`; when shallow, either deepen (`git fetch --unshallow`, or
a targeted fetch of the integration branch) or return unverifiable, never a verdict from the
shallow view. Point 6 in `judge-procedure.md` gains one instruction naming the subcommand, placed
beside the existing `check-freshness` call.

### Key Files

- `plugin/bin/lib/docs-health/` — new module classifying a commit hash (four outcomes)
- `plugin/bin/docs-health.js` — new subcommand wiring and usage line
- `plugin/skills/docs-health/judge-procedure.md` — point 6 instruction to run it before filing
- `tests/bin-lib/docs-health/` — new unit and CLI tests with real git repository fixtures
- `docs/plugin-structure.md` — register the new module and subcommand

## Gotchas

- Deepening a shallow clone is a network side effect and can be large; prefer a bounded fetch of
  the integration branch, and treat any fetch failure as unverifiable rather than as not-found.
- A hash that exists but is unreachable from the integration branch is a distinct outcome from
  one that does not exist; #2785 had both, and collapsing them would repeat its error.
- Abbreviated hashes can be ambiguous; resolve with `git rev-parse --verify --end-of-options
  <sha>^{commit}` and treat an ambiguous prefix as its own failure rather than picking one.
- `judge-procedure.md` is prose consumed by an agent; check its size-ceiling headroom before
  adding text, and keep the new instruction beside the existing point 6 checks.
