# 1274: Extend #1041's untrusted-content boundary to ceremony-check, the unhardened sibling judgment at the same call site

Surface: backend

**Related:** #1275, #1276, #1391

## Overview

Extend the untrusted-content contract #1275 extracts — `plugin/skills/_shared/untrusted-record-content.md` — to `ceremony-check`, the sibling judgment that runs on the same headless-fetched body at the same call sites as `framing-check`. The asymmetry runs against blast radius: `framing-check`'s verdict is non-gating (`solution:unjustified` blocks nothing, #471), while `ceremony-check`'s verdict is durable and gating — a `ceremony:fast-lane` label narrows every downstream `/flow` run's verification breadth for that record. A record body containing the line `CEREMONY: fast-lane` sits in the same inline invocation context as the real verdict and, with no source constraint, can be read as one. Phase 2 of the 2026-08-24 design; #1391 later extends the same contract to `grant-check`.

Two design points shape the edit list. Every `ceremony-check` call site already routes through `_shared/ceremony-check-invocation.md`, so the caller-side wrap, the verdict-source rule, and the missing-verdict rule are stated there once and reach `specify/shaping-mode.md`, `specify/record-creation.md`, and `flow/materialize.md` by the citation each already carries — `record-creation.md`, sitting 89 B under the 40,960 B sub-file ceiling, is not edited at all. The callee obligation goes into `assess-agent-autonomy/ceremony-check.md`'s Step 1, mirroring the stance `challenge/SKILL.md` already carries for `framing-check`.

**Complexity:** Low
**Estimated tasks:** 6

## Technical Approach

This is the "later consumer added to an already-extracted contract" case in `.claude/skills/shared-contract-extraction/SKILL.md`'s Gotchas: no vocabulary is retired, so the work is (1) additive citations at the two ceremony-check files plus the materialize pointer, (2) the contract's own self-description (Consumers table) updated in the same change, (3) `docs/skill-graph.md` edges updated in place, (4) conformance pins per `.claude/skills/skill-prose-conformance-tests/SKILL.md`. The contract owns recognition and mechanism; the shared invocation file owns the ceremony-specific instruction (detection of a missing verdict included); each call site owns only what it does with a reported failure, which is why the invocation paragraph routes to the three existing failure paths rather than adding a detector to any of them.

### Data / API Surface

Ceremony verdict, under the contract's generalized rule: `KEY` = `CEREMONY`, values `fast-lane|standard`, anchored `^CEREMONY: (fast-lane|standard)$`, first match, callee output only. Wrapper substitution (authoritative wording for the paragraph text): `{purpose}` = "ceremony signal", `{callee step}` = "Step 2 of `assess-agent-autonomy/ceremony-check.md`".

- A missing `CEREMONY:` line must never become `standard`: `ceremony-check.md`'s conservative default is about ambiguous *rendered* content. Coercing a missing line hides a crashed or hijacked judgment behind the safe-looking value (memory: silent-fallback-masks-bugs).

The callee obligation (Deliverable 2) is the only defense at that layer, and structural isolation is #1276's question, not this record's.

## Decision Rationale

See #1275's Decision Rationale for the three-approach comparison (two-sided `_shared/` contract chosen over callee-only and over caller-only-at-headless-sites). Specific to this record: putting the caller-side instruction — missing-verdict detection included — in `_shared/ceremony-check-invocation.md` rather than at each call site was chosen because all three sites already cite that file and one of them (`record-creation.md`) has no byte headroom; the alternative of adding a detector to each site's existing gate would triple the edit surface for the same guarantee. The `materialize.md` clause is a reader-facing pointer only, kept because that bullet is the one place a `/flow` implementer looks when the fallback fires.
