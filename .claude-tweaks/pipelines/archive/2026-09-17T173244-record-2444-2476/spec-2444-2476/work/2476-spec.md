# 2476: post-tool-use.js checkWindowsLongpaths conflates real check failures with a definitive 'unset' answer

Surface: infra

## Current State
`checkWindowsLongpaths` in `plugin/bin/lib/hooks/post-tool-use.js` (around line 524-530, landed via #1785/#2432) runs `runGit(['config', '--get', 'core.longpaths'])` and treats any non-`'true'` stdout as "core.longpaths is not enabled" — including when `result.failure` is `'timeout'`, `'spawn'`, or `'no-git'` (the check never actually ran). It then unconditionally calls `logWindowsLongpathsEvent(ctx, { result: 'unset', value: result.stdout })` and surfaces the same warning message for both cases.

The sibling function 20 lines below, `checkWorktreeStaleness`, already draws this exact distinction correctly: it logs `result: 'check-failed'` and skips the message when `fetch.failure`/`revList.failure` is set, rather than asserting a fact it doesn't know. This file's own header comment (lines 14-18) states the indeterminate/definitive distinction matters "only where a gate acts on the answer" — this is exactly such a site.

Found by two independent reproduction-pair agents during the whole-branch pre-release review after v6.124.0 (base 05d7d6cc5..75f71e366), confirmed severity: medium.

## Deliverables
- [ ] `checkWindowsLongpaths` distinguishes a real `runGit` failure (`result.failure` set) from a definitive git-config answer, matching `checkWorktreeStaleness`'s existing `'check-failed'` convention
- [ ] On a real failure, skip the "core.longpaths is not enabled" warning (the check didn't run, so the fact is unknown) and log a distinct result value (e.g. `'check-failed'`) rather than `'unset'`
- [ ] Add test coverage for the forced timeout/spawn/no-git branches (currently only success and real-git-config-unset are covered — `tests/hooks-post-tool-use-worktree-staleness.test.js`)

## Acceptance Criteria
1. A forced `runGit` failure (timeout/spawn/no-git) on the `core.longpaths` check never produces the "not enabled" warning and never logs `result: 'unset'`
2. `events.jsonl` can distinguish "checked, found unset" from "check didn't run" for this event, same as it already can for worktree-staleness events
3. New tests exercise the failure branches and would fail against the current code

## Technical Approach

In `checkWindowsLongpaths` (`plugin/bin/lib/hooks/post-tool-use.js:524-530`), split the current
single `if (!result.failure && result.stdout === 'true')` branch into two checks, mirroring
`checkWorktreeStaleness`'s existing shape (same file, line 571):

1. `if (result.failure) { logWindowsLongpathsEvent(ctx, { worktree: worktreePath, result: 'check-failed', reason: result.failure }); return null; }` — a real check failure never asserts "not enabled" and never returns the warning `systemMessage`.
2. The existing `result.stdout === 'true'` → `'enabled'` branch is unchanged.
3. Everything else (a clean, non-failing `--get` that returned non-`'true'` stdout, including empty stdout for a genuinely unset key) keeps today's `result: 'unset'` logging and warning.

No change to `checkWorktreeStaleness` itself — it's the reference pattern, not part of this fix.

## Gotchas

- Don't change the message text or the `'enabled'`/`'unset'` result values for the two paths that
  already work correctly (real true, real non-true) — only the previously-uncovered failure path
  changes behavior.
- The fix is a direct structural mirror of code already in the same file 20 lines away — no new
  pattern to invent, just apply the existing one.
