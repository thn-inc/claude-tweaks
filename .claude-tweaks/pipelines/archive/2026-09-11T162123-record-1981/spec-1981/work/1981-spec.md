# 1981: bin/resolve-linked-prs.js is a near byte-for-byte copy of resolve-blockers.js

Surface: infra

## Current State
`plugin/bin/resolve-linked-prs.js` (115 lines) and `plugin/bin/resolve-blockers.js` (123 lines) are the same CLI with two names: identical `isPos`/`parseNumbers`/`parseArgs`, identical `realDeps` (the `ghAvailable`/`remoteUrl` pair from `bin/lib/repo-resolve.js`, a 30 s `execFileSync('gh', …)` runner with the same fetch-sub-issues precedent comment, stdout/stderr), identical `run()` control flow and exit-code map (0 ok, 1 malformed, 2 `gh` absent or unresolvable repo, 3 fetch threw), identical `--repo` override plus `origin` fallback, identical `module.exports` shape and `require.main` guard. `diff` reports 78 differing lines, all in the header comment, the `USAGE` string, the imported fetch function (`fetchNativeDependencies` vs `fetchLinkedPRs`), the error-message prefix, and the per-number result shape. The second file's own header says it mirrors the first "exactly".

The record's wider claim does not hold: `resolve-policy.js` (205 lines) and `resolve-profile.js` (176 lines) share none of this scaffold — no `--repo`, no runner timeout, no `realDeps`, no repo resolution, no `require.main` guard; they are key-resolver CLIs over `policy-schema.js` with their own argument grammar. What all four share is only the stated *shape* ("thin argument-parsing shell over a `bin/lib/` function, injectable runner"), which is a convention, not code. Two files duplicate; the other two do not.

## Deliverables
- [ ] `plugin/bin/lib/number-list-cli.js` exporting `makeNumberListCli({ name, usage, fetch, mapResult, requiresGh, runnerTimeoutMs })` → `{ run, parseArgs, parseNumbers, realDeps }`, holding the shared scaffold once: `isPos`/`parseNumbers`, `parseArgs` (positional comma list, `--repo`, `--help`), `realDeps` with the 30 s runner and its precedent comment, repo resolution via `bin/lib/repo-resolve.js`, the exit-code map, and the `{ [n]: value }` result assembly through `mapResult(n, fetched)`.
- [ ] `resolve-blockers.js` and `resolve-linked-prs.js` reduced to a header comment, the factory call with their own `usage`, `fetch`, `mapResult`, and error prefix, `module.exports = { run, parseArgs, parseNumbers, parseRepo }` (the same four names each file exports today; the tests import `run`), and the `require.main` guard.
- [ ] `tests/resolve-blockers-cli.test.js` and `tests/resolve-linked-prs-cli.test.js` pass unmodified; a new `tests/bin-lib/number-list-cli.test.js` covers the factory's parse/exit-code contract once (malformed list, `--repo` missing value, unknown flag, `gh` absent, unresolvable repo, fetch throw → 3, `--help` → 0).
- [ ] `docs/plugin-structure.md`'s command reference keeps both CLIs listed; the `bin/lib/` convention line needs no change (a flat sibling module, not a nested `_shared/`).
- [ ] `resolve-policy.js` and `resolve-profile.js` are named in the closing comment as out of scope (no shared code with the pair); no factory is forced on them.

## Acceptance Criteria
1. `diff` between the two CLIs after the change touches only the header comment and the factory-argument object; neither file defines `parseNumbers`, `parseArgs`, or `realDeps` itself.
2. Both existing CLI test files pass byte-for-byte unmodified (each imports `run` and asserts the exit codes and messages); the four-name export shape is kept for API stability even though only `run` is imported today.
3. The factory's own test covers every exit code the two CLIs document (0, 1, 2, 3) and the `--help` path.
4. `npm test` is green; `resolve-policy.js` and `resolve-profile.js` are byte-identical to before.

## Technical Approach
Extract exactly the duplicated block and nothing else: the two files' `diff` is the specification of what stays per-CLI (usage, fetch, result shape, error prefix). `repo-resolve.js` already owns `parseRepo`/`ghAvailable`/`remoteUrl`, so the factory composes it rather than re-deriving repo resolution. Keeping the four-name export shape means the tests are the regression net without edits, which is also what proves "pure extraction". Widening to the policy/profile CLIs would mean inventing a shared abstraction over files that share no code; that is declined here and recorded in the closing comment so the review finding is answered rather than silently narrowed.

## Gotchas
- The runner timeout comment (30 s, fetch-sub-issues precedent, not #1154's 5 s default) is load-bearing; move it into the factory verbatim rather than leaving a bare number.
- `parseRepo` is re-exported from each CLI today; keep the re-export so any external caller of the four-name shape is unaffected, and do not wrap it.
- The two CLIs' error prefixes (`resolve-blockers.js:` / `resolve-linked-prs.js:`) appear in test assertions; the factory takes the prefix as a parameter and never derives it from `process.argv`.
- The record's pre-v6.117.0 review counted four scaffolds; the sanity check found two, so the title's "4th near-identical" framing is corrected in this body, not in the title.
