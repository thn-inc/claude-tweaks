# 5224: Driver lane bounds as policy values, with the reviewer required beyond the express bounds

Surface: backend

## Overview

The driver lane's bounds are the express lane's: the size label it accepts (`low`), the largest number of Key Files (three), and the implementation-line bound the post-build check applies. With the evidence-based reviewer of #5222 in place (design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, section "Phase 4 — One reviewer, wider lane"), those three bounds can widen one step. This unit turns them into policy values whose defaults equal today's express values, so the lane is widened later by editing policy, and makes the reviewer a condition of the wider lane: a record, or a diff, beyond the express defaults but inside the driver's policy is accepted only when the reviewer step is on for it.

This unit changes no default. The widening the design describes (size medium, more Key Files) is made later by a policy edit, with its exact values decided from the scoreboard, not here.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- Choosing or setting any widened value. Every default equals today's express value.
- The reviewer step itself, its policy key and its evidence rules (#5222). This unit consumes its "is the reviewer on for this record" answer.
- Any change to the prose express lane: `plugin/skills/_shared/express-lane.md` is untouched, and `express-lane.js gate` and `check` return today's verdicts when the new options are absent.
- Accepting a `size:high` record under any policy value, relaxing the risk, frontend-surface, protected-path, merge-sensitive-path or shape rules, or changing `auto-merge-max-lines` or the normal auto-merge path.
- Settling a stop, the worker launcher, or the scoreboard.

## Release Note

Made the pipeline driver's size, Key File and diff-line limits configurable policy values, with the reviewer required for anything beyond the express limits.

## Technical Approach

- **Options, not a second function.** `evaluateRecordEligibility` gains two optional `opts` fields next to `allowAbsentCeremony`, and only the size line and the Key File line change. The line bound needs no new option on `evaluateDiffBounds`, because it already takes `maxLines`; the gap is that nothing can hand `check` a different value, which is what the new flag fixes.
- **"Beyond the express bounds" is #5222's record-level rule.** A record is beyond them when its size label is not `low` or its Key File count exceeds `EXPRESS_MAX_KEY_FILES`. #5222 exports the function that says whether the reviewer is on for a record; admission and `steps.js` call it, and admission stays pure by receiving the answer as an input. As built, the record-level half is one exported predicate, `isBeyondExpressBounds` in `plugin/bin/lib/express/eligibility.js`, which admission and the eligibility step both call, so the two cannot define "beyond" differently.
- **Closed rule (admission states for this unit).** The states this unit adds to admission are: beyond the express bounds and the reviewer on (admitted by this rule); beyond the express bounds and the reviewer not on (refused, reviewer reason); inside the express bounds (this rule does not apply). Any other combination is refused with a reason naming the unreadable input; a plan review that finds another unlisted state applies this rule as a plan amendment adding that state's refusal, not as a `needs-human` gap.
- **Effective line bound.** The bound `check` applies is the driver's value when that key is set and the reviewer is on for the record, else the express bound (by passing no flag). A driver value below the express bound narrows the lane for reviewer-on records on purpose (a record the reviewer has looked at may be held to a tighter bound if a project chooses); turning the reviewer off returns it to the express bound. A Key File limit below the express limit is likewise permitted: eligibility refuses on it whatever the reviewer value, and "beyond the express bounds" stays defined against `EXPRESS_MAX_KEY_FILES`. A set `express-driver-max-lines` that the resolver accepts but that is not a safe integer of at least 1 (an all-digit value past 2^53) is a run-level fatal in the driver's policy step. A malformed value resolves to the default per AC4/AC5 and passes no flag.
- **Defaults.** The size and Key File defaults are literal values equal to the express ones, with the equality pinned by test. The line bound's default is derived, not literal: unset means "the express bound", so a project that tuned `auto-merge-max-lines` sees no change in its express or driver runs. `_shared/policy-schema.md`'s "Derived-default keys" section lists the two live shapes; pick one deliberately and state it in the row, with the resolver's output for unset, set and malformed input taken from the code.
- **The reviewer-on answer is a pure function of the record and the resolved reviewer policy value** (#5222), computed once per record and passed to admission as a boolean and reused for the `check` flag decision, so admission and `check` cannot disagree. As built (Reading A, decided at plan review), the one `reviewRequired` call happens in the eligibility step, which needs the answer to append the reviewer reason to an eligibility refusal; it is stored as `ctx.reviewer` and read by admission, the `check` step and `reviewRecord` in `plugin/bin/lib/driver/review.js`, which no longer computes its own answer and fails closed when `ctx.reviewer` is missing.
- **Policy keys.** Follow `.claude/skills/policy-key-addition` site by site: rows, tier `advanced`, key-count pin, doc rows stating what the resolver returns for unset, set and malformed input (from the code, not from intent), and the `policyOnly` flag on all three.

If the rows do not fit, move one section with no citers and no byte pins to a pointer-stub sibling, as `.claude/skills/policy-key-addition` site 4 describes.
- All three keys are `policyOnly: true`: they bound what autonomous machinery may take on, so a run-config overlay must not widen them. Name all three in the `policyOnly` bullet of `plugin/skills/_shared/policy-schema-coverage.md` (find it by that bullet's text).
- Do not add a parallel `maxLines` option to `evaluateDiffBounds`. It already has one, and a second would let the two disagree.
- Do not read `auto-merge-max-lines` in the driver and pass it as the flag: omitting the flag is what keeps `check` the single place the express bound is read, and the key is read there with whatever overlay handling `check` applies. Reading it in two places is the drift the express lane's code-twin convention exists to avoid.
- ASSUMPTION — verify at build: a diff between the express and driver line bounds survives the later merge path. The driver ends `pending-review` in Phase 1, and a later merge step may apply its own diff-size judgment (`auto-merge-max-lines` is described as a weighted guideline, `plugin/bin/lib/policy-schema.js:90`) — confirm via `git grep -n -F "auto-merge-max-lines" -- plugin/bin plugin/skills/assess-agent-autonomy` when the merge phase is shaped. If the merge path re-refuses such a diff, a widened-lane record still ends `pending-review` rather than merging; that is not a defect of this unit, but it limits how far the widening can pay off, and the merge phase's record must account for it.
- Pinning a widened value as a default in any test or doc row would turn a later policy edit into a contract change. Tests set widened values explicitly and assert the defaults separately.
- The eligibility reasons are a wire contract: `plugin/bin/lib/express/eligibility.js` says callers and reports match them verbatim. Keep the existing strings byte-identical when the options are absent; add, never reword.
- A widened Key File limit moves the diff-bound side too: `check` compares every changed non-test path with the record's Key Files, so a record with more Key Files has more files its diff may touch. That is the intended effect; it is bounded by the line bound and the reviewer.
