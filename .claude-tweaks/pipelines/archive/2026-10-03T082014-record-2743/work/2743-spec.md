# 2743: Upstream gap report — `design-wrapper polish` has no way to honour spec-pinned copy

Surface: infra

## Current State

The polish phase dispatches Impeccable's refinement set (`polish`, `clarify`, `harden`) and every suggestion-driven command over the changed UI files. On a record whose spec pins its copy ("See demo", "Play demo", "Open the page", "What's new", "How to") and whose e2e suite asserts those strings with `exact: true`, `clarify` (UX copy) and `onboard`/`distill` would rewrite exactly the strings the suite and the spec fix, and `polish` would restyle reviewed pages that the record's Non-Goals say may only gain one element. The controller had to replace the documented dispatch with a hand-scoped fix wave to keep the pipeline green — the polish step is unusable as written on any spec with asserted copy.

Verified during shaping: `skills/design-wrapper/modes/polish.md`, `skills/flow/polish-execution.md`, and `skills/design-wrapper/command-map.md` all exist as named — the premise is confirmed against this repo's own file layout, not just the filer's claim.

## Deliverables

- A pinned-copy constraint mechanism: `polish` mode (and the other Impeccable dispatch commands it fans out to — `clarify`, `harden`, `onboard`/`distill`) accepts, or derives from the run, a list of strings no dispatched command may change — sourced from the record's spec-quoted strings and/or e2e assertions using `exact: true` (`ADMIN_STRINGS`-style constants, per the filer's example) — passed as a fixed suffix/constraint on every Impeccable dispatch this phase makes.
- A way to skip `clarify` (or any dispatched command) entirely when the spec pins copy that command would otherwise rewrite.
- A scope option restricting the refinement set to files the record actually created, rather than every UI file the diff touched — so an unrelated already-reviewed page isn't restyled by `polish` just because it happened to be in the changed-files list.

## Acceptance Criteria

- A record whose spec pins specific copy strings (verified via its own text or `exact: true` e2e assertions) completes the polish phase with those exact strings unchanged.
- A record can opt out of `clarify` (or another named Impeccable command) for a run where its spec's pinned copy makes that command's rewrite behavior unsafe.
- The refinement set's default scope can be restricted to record-created files, not the full changed-file diff, when a record's Non-Goals call for it.
- `npm test` passes.

## Release Note

Added a way for design polish to leave spec-pinned copy unchanged.

## Technical Approach

Extract the pinned-copy string list from two sources the filer's own evidence names: the record spec's quoted strings (parseable from Deliverables/Acceptance Criteria text — look for quoted literals) and, where present, `exact: true` e2e assertions in the record's own test files. Thread this list through `flow/polish-execution.md`'s dispatch composition as a constraint every Impeccable command invocation in `design-wrapper/command-map.md` receives — the constraint should read as a hard "do not change" list each dispatched command's own prompt states explicitly, not a post-hoc diff check (catching a rewrite after it happens is more expensive than preventing it via the dispatch prompt itself).

### Key Files

- `plugin/skills/design-wrapper/modes/polish.md` — polish mode's own dispatch logic, where the pinned-copy constraint and per-command skip option need to be added
- `plugin/skills/flow/polish-execution.md` — the `/flow`-side orchestration of the polish phase, where the constraint list is likely derived from the run's own spec/e2e context
- `plugin/skills/design-wrapper/command-map.md` — the Impeccable command dispatch mapping (`polish`, `clarify`, `harden`, `onboard`/`distill`) each command's prompt composition needs to accept and honor the constraint

## Gotchas

- The pinned-copy list should come from real spec content (quoted strings, `exact: true` assertions), not a manually-maintained separate config — deriving it wrong (too narrow) reproduces this bug in a new form; deriving it too broadly (treating every quoted word as pinned) could over-constrain polish on records that never intended copy pinning.
- The file-scope restriction (record-created files only) is a real behavior change from today's "every touched file" default — confirm this doesn't silently skip a UI file a record legitimately modified (not just created) but that also needs polish attention; the restriction should be opt-in per the record's own Non-Goals signal, not a blanket default change.
