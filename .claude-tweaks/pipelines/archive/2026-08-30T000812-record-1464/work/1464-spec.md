# 1464: EnterWorktree: `fresh` baseRef doesn't reliably pick up a just-merged origin/<default-branch> commit

Surface: infra

## Current State

- `plugin/skills/_shared/worktree-base-ref.md` documents `EnterWorktree`'s `fresh` baseRef as a harness-owned, unversioned behavior that has been directly observed resolving stale — branching from a local ref rather than the freshly fetched `origin/<default-branch>` its own name implies. That prior observation is tracked as `IL-106` in `docs/incident-log.md`.
- `plugin/skills/_shared/worktree-setup.md`'s "Post-creation catch-up" section mandates an unconditional `git fetch` + `git merge` immediately after every worktree-creation call, regardless of creation path or whether `worktree.baseRef` is configured correctly. It's cited by every worktree-creation call site in this plugin (`build/worktree-setup.md`, `flow/validation.md`, `_shared/scratch-worktree.md`, `dispatch/SKILL.md`).
- `plugin/bin/lib/hooks/post-tool-use.js`'s `checkWorktreeStaleness` (#307) is a PostToolUse backstop hook that fires on every `EnterWorktree` call: it fetches `origin/{integration-branch}` and warns via a `systemMessage` telling the agent to run the catch-up above if the new worktree is measurably behind. It resolves the integration branch via `resolveIntegrationBranch` (`plugin/bin/lib/hooks/worktree-reap.js:318-327`), whose fallback profile is policy.yml's `integration-branch:` value, then `origin/HEAD`.
- `tests/hooks-post-tool-use-worktree-staleness.test.js` covers the backstop's tool-result parsing (`Created`/`Entered` phrasing, missing/malformed tool result, `git worktree list --porcelain` fallback), fetch failure, and an argument-injection guard — but every one of its fixtures pins `integration-branch:` in `.claude-tweaks/policy.yml` via the shared `setupProject()` helper. None exercises `resolveIntegrationBranch`'s other fallback rank, `origin/HEAD` — the resolution path a project with no pinned policy value relies on for this exact hook.

## Deliverables

- [ ] Add a test to `tests/hooks-post-tool-use-worktree-staleness.test.js` that omits the `integration-branch:` policy pin, sets up `origin/HEAD` explicitly (`git remote set-head origin -a` after `git remote add`, since adding a remote alone does not set it), and asserts `checkWorktreeStaleness` still emits the warn-tier `systemMessage` when the resulting worktree is behind.
- [ ] If that test exposes a real failure in the `origin/HEAD` fallback path, fix it in `resolveIntegrationBranch` (`plugin/bin/lib/hooks/worktree-reap.js`) or its caller so the backstop fires reliably without a pinned policy.
- [ ] Add a one-line cross-reference to issue #1464 in `docs/incident-log.md`'s `IL-106` entry, noting it as an independently reported instance of the same staleness pattern.

## Acceptance Criteria

1. `node --test tests/hooks-post-tool-use-worktree-staleness.test.js` includes a passing test that exercises `checkWorktreeStaleness` with no `integration-branch:` pinned in `.claude-tweaks/policy.yml`, confirming the warn-tier `systemMessage` fires when the worktree is behind the branch resolved via `origin/HEAD`.
2. `npm test` passes in full.
3. `docs/incident-log.md`'s `IL-106` entry references issue #1464.

## Technical Approach

This repo already runs two independent layers of defense against exactly the symptom #1464 reports (see Current State): the mandatory Post-creation catch-up procedure every worktree-creation call site is supposed to run, and the `checkWorktreeStaleness` warn-tier backstop hook that fires unconditionally on every `EnterWorktree` PostToolUse event regardless of whether a call site remembered the catch-up. Both are already tested. The actionable gap this record closes is narrower: the backstop hook's own test suite never exercises the code path a project without a pinned `integration-branch` policy value depends on (`origin/HEAD` resolution), so a regression there would silently disable the warning — producing precisely the "nothing signals staleness" experience #1464 describes — with no test to catch it.

Reuse the existing `setupProject()`/`harnessWorktreeOf()`/`advance()` fixtures in `tests/hooks-post-tool-use-worktree-staleness.test.js`; the new test differs only in skipping the `integration-branch:` policy.yml write and instead pointing `origin/HEAD` at the base branch directly on the `main` fixture repo.

### Key Files

- `tests/hooks-post-tool-use-worktree-staleness.test.js` — new test exercising the `origin/HEAD` fallback rank of `resolveIntegrationBranch`
- `plugin/bin/lib/hooks/worktree-reap.js` — `resolveIntegrationBranch` (only touched if the new test finds a real defect)
- `docs/incident-log.md` — cross-reference #1464 in the `IL-106` entry

## Gotchas

- The original report's suggested fix — making `EnterWorktree`'s `fresh` baseRef path perform its own `git fetch` before branching — is not implementable from this plugin: `EnterWorktree` is a harness-native tool that exposes no base-ref parameter (`_shared/worktree-base-ref.md`), so this plugin cannot influence which ref it branches from. Any further hardening belongs in the two layers this plugin does own (Post-creation catch-up, the `checkWorktreeStaleness` backstop), not in `EnterWorktree` itself.
- `git remote add origin {path}` alone does not set `origin/HEAD` — the new fallback test must explicitly run `git remote set-head origin -a` (or `-b {branch}`) after adding the remote, or `resolveIntegrationBranch`'s `git rev-parse --abbrev-ref origin/HEAD` will fail exactly like the existing no-remote fixture, and the test won't actually exercise the fallback-success path it's meant to cover.
- This record's `type:task` classification (test-coverage/documentation hardening) is not a denial of the original report — the underlying `EnterWorktree` staleness behavior is a genuine defect, tracked as such and left as `bug` on the tracker. It's a defect this plugin cannot fix at the source, so this record's own deliverable is defensive-coverage hardening around it instead.

## Original request

EnterWorktree: `fresh` baseRef doesn't reliably pick up a just-merged origin/<default-branch> commit

**Summary:** EnterWorktree's `fresh` baseRef sometimes branches from a stale origin/<default-branch> point despite a confirmed-current remote-tracking ref.

**Kind:** Defect

**Affected component:** EnterWorktree tool

**Repro steps:**
1. Confirm `origin/<default-branch>` is current (fetch + rev-parse).
2. Call EnterWorktree with `fresh` baseRef (the default) to create a new worktree.
3. Check `git merge-base --is-ancestor <the-just-confirmed-commit> HEAD` in the new worktree.

**Expected vs. actual:**
Expected: the new worktree branches from the current `origin/<default-branch>` tip, per EnterWorktree's own documented behavior ("branches from origin/<default-branch>").
Actual: across 4 consecutive EnterWorktree calls in one session, the resulting branch point was behind a commit already confirmed present on `origin/<default-branch>` moments earlier. Worked around manually each time with an explicit `git fetch` + `git merge origin/<default-branch> --no-edit` immediately after EnterWorktree. Low cost per instance, but silent — nothing in EnterWorktree's own output signals the branch point may be stale.

Suggested fix: the `fresh` baseRef path should perform its own `git fetch` (or otherwise re-resolve `origin/<default-branch>` at call time) immediately before branching, rather than appearing to use a cached or otherwise-stale ref.

**Definition:** Clear
