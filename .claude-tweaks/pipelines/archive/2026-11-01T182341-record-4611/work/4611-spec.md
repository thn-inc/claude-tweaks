# 4611: Acceptance packet: schema, canonical marker comment, new sections

Surface: infra

## Overview

Replace wrap-up's Verification Brief with an **acceptance packet** for every project — universal, not gated on control mode. The packet is what the human finds at the acceptance control point: it makes validating a finished feature cheap, and it is the only artifact `/accept` and Dispatch both read. Control mode (separate units) later adds the stop-removing behaviors; the packet itself is a plain improvement that ships for everyone, migrated expand-contract.

Sections, in order (design section 6):

1. **What changed** — user-facing summary, not a diff tour.
2. **Recording** — the walkthrough of the feature in use (filled by the recording record; a placeholder section here).
3. **Test guide** — numbered manual steps, each with a direct link that lands in the right state (role, test data). Credentials are referenced by vault entry name, never embedded as session tokens or passwords.
4. **Couldn't test** — what the agent could not verify and why (no backend, no dev server, needs a real device, needs real credentials). **A check that skipped itself is listed here, never shown as silence.**
5. **Tried to break** — the negative stories and edge cases run, with results.
6. **Least confident** — where the agent's judgment is weakest ("if I were you I'd poke here"); sourced from review's low-confidence findings.
7. **Risk proofs** — present only when risk flags were kept (the specific evidence per flag; filled by the risk-flag record).
8. **Decisions left for you** — carried-forward items (filled by the control-mode records); omitted when empty.
9. **Deploy status** — target and, for `dev`, whether the feature is confirmed live (filled by the dev-target record; for `local` it states the target).

**Canonical copy:** a marker-block comment on the work record (a GitHub comment; the PR links to it). The run-dir copy is a working copy and is never read after the run. **One packet per work item; re-posting updates the same comment in place** (find by marker, edit by comment id), never a second comment. **Fact-validated narration:** every claim in sections 3-7 cites a gathered fact (story report, screenshot, test output, review finding) and the citations are validated against the gathered fact set, following the repo's gather / narrate / render pattern as `/activity` implements it (`plugin/bin/lib/activity/gather.js` and `render.js`; the `fact-validated-narration` skill is the checklist).

Anti-goals this record carries: a "tested X" claim with no run behind it; a skipped check that shows as nothing; packet links that point at a build lacking the feature (deploy status owns that); secrets reaching a public surface (the recording record owns redaction, but this record must never embed credential-shaped values in the Test guide).

**Contract decisions this record pins (the packet contract file states them; later records cite it):**

- **Marker and lookup.** The canonical comment carries `<!-- acceptance-packet: v1 -->` on its first line (registered in `_shared/pr-run-comments.md`'s marker registry). A writer lists the work record's comments, keeps those that carry the marker and pass `comment-trust.js`, and edits the earliest by comment id; extra marker comments are reported, never edited or deleted. If the matched comment cannot be edited by the current identity, the run reports that visibly and posts nothing (never a second packet). The PR gets one idempotently appended body line `Acceptance packet: {comment url}`; with no PR (the `local-merge` model) there is no link and none is needed. Under `local-files` the packet lives in the record body between `<!-- acceptance-packet:start -->` and `<!-- acceptance-packet:end -->` and is replaced in place between the delimiters.
- **Facts and claims.** A fact is `{ id, kind, status, reason?, source }` with `kind` one of `change`, `check`, `story`, `finding`, `link`, `recording`, `flag`, `decision`, `deploy`; `status` one of `passed`, `failed`, `skipped`, `not-run`; ids are stable strings such as `check:unit-tests` or `story:login#negative-2`. A claim is `{ section, text, refs[] }` with `section` one of `what-changed`, `test-guide`, `tried-to-break`, `least-confident`, `risk-proofs`. Section-to-kind table (in the contract): what-changed cites `change`; test-guide cites `story` and `link`; tried-to-break cites `story` and `check`; least-confident cites `finding`; risk-proofs cites `flag` plus the proof fact. Sections 2 (Recording), 8 (Decisions) and 9 (Deploy status) render facts of kind `recording`, `decision` and `deploy` directly and are not narrated claims. `schemaVersion: 1` is one constant used by the facts file and the marker alike; later records add fact kinds only by extending the contract's table.
- **Validation policy: visible drop.** `validatePacket` drops any claim whose `refs` is empty, names an absent fact, or names a fact incompatible with the claim, and the packet always states `N claims were dropped for missing evidence` (and lists them in the run-dir working copy). It never posts silently thinner. Compatibility: a claim asserting verification (tested, verified, works) may cite only `passed` facts; a claim citing a `failed` fact renders under Tried to break with the failure; one citing `skipped` or `not-run` moves to Couldn't test.
- **The expected check set comes from outside the facts.** Gather derives the checks and stories expected for the work (the spec's Acceptance Criteria and verify expectations, the planned stories) independently of what ran; an expected check with no result fact renders under Couldn't test as `not run`, so a self-skipped check cannot be silent. Gather is `plugin/bin/lib/wrap-up/packet-gather.js` (deterministic; a partial gather renders a stated `partial` note); narration is an LLM step in the wrap-up prose; wrap-up runs gather, narrate, validate, render, post in that order.
- **Failure contract.** If the post or edit fails, the pending acceptance label is not applied and the failure is reported. The reader function `readPacket(comments)` in the same module applies the reader rules: an unknown `schemaVersion` reads as unreadable (stated, no second packet), duplicates resolve to the earliest trusted comment, an untrusted-author marker is ignored, and the run-dir copy is never consulted (a test proves a stale local copy is ignored).
- **Links.** Test-guide links must be http(s) on the local base URL host or the `dev-base-url` host only; any other host is refused. A shared constant defines the credential-shaped key set, matched case-insensitively after normalization in query, fragment and userinfo: `token`, `access_token`, `password`, `passwd`, `secret`, `session`, `sessionid`, `jwt`, `auth`, `key`, `api_key`, `sig`, `signature`, `x-amz-signature`. The Recording record reuses this one constant for its redactor. When the deploy section is not confirmed live, each Test-guide link carries `(link unverified: deploy not confirmed live)`.
- **Facts-poor and infra items.** A section with nothing to say renders one line stating why (`not applicable: no UI surface`), never an empty heading. For `Surface: infra`/`backend` work the Test guide lists commands to run instead of links. For decomposed work the packet lives on the parent (the feature-acceptance record owns the gate); a sub-issue's wrap-up posts nothing and the existing parent-gate routing stands.
- **Size.** The renderer caps the comment at 60,000 characters (GitHub's limit is 65,536) and truncates by omitting whole items with a stated `truncated: N items omitted` line.
- **Section 1 is cited too.** `what-changed` claims cite `change` facts (changed files, commits), so every narrated section is validated.
- **Old brief.** All five Routing call sites land in `verification-brief.md`, so replacing its template migrates them at once; the old section map (The ask to What changed; What shipped to What changed; Confirmed to Test guide and Tried to break; Observation plan to Test guide) is a table in the contract. Briefs already posted stay readable through `plugin/skills/demo/legacy-brief-compatibility.md` (kept until the final cleanup record). A work item with only a legacy brief comment gets a new packet comment; the legacy comment is left untouched, and "exactly one" applies to packet comments.

## Acceptance Criteria

1. Given facts containing a story report with one failed and one skipped check, `renderPacket` outputs the skipped check under `Couldn't test` (with its reason) and the failure under `Tried to break`; nothing is omitted silently (a test counts input checks against rendered rows).
2. A claim in the Test guide whose `refs` cites a fact id absent from the gathered facts is dropped by `validatePacket`, and the rendered packet states `1 claim was dropped for missing evidence`; a claim with no `refs` is dropped the same way; a "verified" claim citing a `failed` fact renders under Tried to break with the failure; one citing a `skipped` fact moves to Couldn't test. Each is pinned by a test.
2a. An expected check (derived from the spec's Acceptance Criteria or planned stories) with no result fact at all renders under Couldn't test as `not run`.
2b. `readPacket` returns the earliest trusted marker comment among duplicates, ignores an untrusted-author marker, reports `schemaVersion: 2` as unreadable, and never reads the run-dir copy.
2c. When the post or edit fails (fake runner returns an error) the pending acceptance label is not applied and the failure is reported.
2d. A packet that would exceed 60,000 characters is truncated by whole items with a `truncated: N items omitted` line.
3. Wrap-up's second run on a work item that already has a packet comment edits that comment (same comment id) and the work item ends with exactly one comment carrying the marker (test against the fake runner).
4. A narrative string containing `[x](https://evil.example)` or a forged `## Couldn't test` heading is rendered as inert prose (brackets escaped, newlines collapsed).
5. The packet contract states, and a conformance test pins, that credentials appear only as vault entry names and that the link rules above hold: a link to a host other than the local base URL host or `dev-base-url` is refused; a link carrying any key from the shared credential-key constant in its query, fragment or userinfo is refused after case and percent-encoding normalization (tests for `TOKEN=`, `tok%65n=`, `#sig=`, `user:pass@`, `sessionid=`); a benign `/docs/token-guide` path is accepted. For a `Surface: infra` record the Test guide lists commands and renders no links; sections with nothing to say render a one-line reason.
6. The five call sites in `verification-brief.md`'s Routing table still resolve and still apply the pending acceptance label; existing wrap-up tests pass unchanged apart from intended renames.
7. `npm test` passes.

## Technical Approach

Three-stage gather / narrate / render. Gather is deterministic and writes a facts file in the run directory (working copy). The narration step is judgment and writes a narrative with `refs[]` per claim. The renderer is deterministic and trusts only the facts. The canonical copy is the posted comment, found by its marker and edited in place; the run-dir copy is never read afterward. The packet is the same artifact for control mode on or off — only which sections are populated differs.

### Data / API Surface

- Marker: a fenced marker block comment, versioned (`schemaVersion: 1`), following the repo's other marker-comment convention (`_shared/pr-run-comments.md`); author-trust-gated on read (`plugin/bin/lib/issues/comment-trust.js`).
- Facts: `{ checks[], stories[], findings[], links[], decisions[], deploy }` with stable ids that `refs[]` cite.
- Sections 2, 7, 8, 9 render a stated placeholder (`not recorded`, `no kept risk flags`, none, `target: local`) until their owning records populate them.

## Gotchas

- Replacing, not adding: two packets on one item is the failure mode; the old template is replaced in place in `verification-brief.md`, not kept beside the new one.
- Do not read the run-dir copy after the run; `/accept` and Dispatch read GitHub (AC 2b proves the reader ignores a stale local copy).
- The authenticated identity that posted the packet may differ on a re-run (cloud, Routine); AC 2c's failure path covers "cannot edit". Concurrent wrap-up runs on one record are prevented by the record claim; if one slips through, last write wins and the loser reports.
- The gather step must never silently pass a failed gather: a partial gather renders a stated "partial" note, mirroring `/activity`'s Partial gather handling.
- `tests/try-it-contract-conformance.test.js` and other prose-pinning tests fail when prose moves; run the whole suite (not only touched files) before merge.
- The wrap-up skill text must stay within its size ceiling; put packet detail in the new `_shared` contract and cite it.
- Parent-linked sub-issues keep today's routing (the parent carries the gate) until the feature-level-acceptance record changes it.
