# 3696: Windows regression: 3 test file(s) newly failing after 4faf39155

Surface: infra

**Related:** #2767, #3599, #3644, #3693, #3695, #3698, #3699, #3702, #3703

## Current State

The post-merge Windows check on 4faf39155 (PR #3660) reported three newly failing files. Re-checked against `origin/main` at `fa8286fc8` and the latest Windows run (39414412621 at 63ce07e5a):

- **`tests/path-containment-conformance.test.js`: already fixed.** `plugin/bin/check-staged-stack.js:88` hand-rolled a `startsWith('..' + path.sep)` containment test, and #3692 (64158e1e8) replaced it with `isPathContained`. The file is no longer in the Windows failing set. Nothing remains to do for it.
- **`tests/bin-lib/staged-patch/cli.test.js` and `tests/bin-lib/staged-patch/stack-check.test.js`: still failing, and the cause is a shipped-code defect.** `plugin/bin/lib/staged-patch/stack-check.js:28` (`defaultGit`) sets `GIT_CONFIG_GLOBAL: os.devNull`. On win32 `os.devNull` is `\\.\nul`, and Git for Windows rejects it on every call (`fatal: unable to access '\\.\nul': Invalid argument`, seen in run 39377732537's `tests.log`). As a result, `git apply --numstat` in `walkStack` fails for every patch, and every patch lands in `skipped`, including a single clean one. That gives `targetUnapplicable`, which makes the CLI exit 2 at `check-staged-stack.js:153-156` (the `2 !== 1` assertion), and `targetConflict === null`, which causes the `TypeError` at `stack-check.test.js:69`. About 7 tests in `cli.test.js` and about 14 in `stack-check.test.js` fail this way. The two quoted in the report are just the first of each.

User impact on Windows: `check-staged-stack.js` reports every staged patch as not applicable, so `console-resolve.js`'s `stackVerdicts` marks them all `stale` and the Review Console auto-applies nothing.

The test fixtures pass on Windows only because they use the literal `'/dev/null'`, which Git for Windows maps to `nul` (`tests/helpers/git-fixtures.js:111`).

## Deliverables

1. In `plugin/bin/lib/staged-patch/stack-check.js`, build `defaultGit`'s env through a small exported function that takes `platform` (default `process.platform`) and sets `GIT_CONFIG_GLOBAL` to a value Git for Windows accepts on win32 (`'nul'`, or the literal `'/dev/null'` the fixtures already prove works), and to `os.devNull` elsewhere.
2. Add a Linux-runnable pin in `tests/bin-lib/staged-patch/stack-check.test.js`: the env built for `'win32'` never carries `\\.\nul`, and the one built for `'linux'` is `/dev/null`.
3. Grep `plugin/bin` for any other `os.devNull` passed to git as a config path and fix it the same way. At `fa8286fc8`, `stack-check.js:28` is the only hit.

## Acceptance Criteria

1. The env builder returns a `GIT_CONFIG_GLOBAL` without `\\.\nul` for `platform: 'win32'`, and `/dev/null` for `platform: 'linux'`.
2. The win32 pin fails when the builder is reverted to `os.devNull`.
3. `grep -rn "os.devNull" plugin/bin` shows no git config-path use.
4. `node --test tests/bin-lib/staged-patch/` passes, and `npm test` passes.
