# 3602: build plan-authoring: a spec's "verify X / change Y only if" Technical Approach step can vanish from the plan unflagged

Surface: infra

## Current State

A spec's `## Technical Approach` and `## Gotchas` often hold conditional verification steps, such as "read the rows back from file A and file B, and change those readers only if the data-model change breaks them". These steps are neither Deliverables nor Acceptance Criteria. Nothing between `/claude-tweaks:specify` and the final whole-branch review checks that the build plan carries them:

- `plugin/bin/lib/plan-audit/parser.js` (`AC_HEADING_RE`, line ~250) reads only the spec's `## Acceptance Criteria` section for Check E. Check E (`plugin/bin/lib/plan-audit/checks.js`, "Check E — Acceptance-criterion clause coverage (#3099)") is warn-only and matches AC clauses only.
- `plugin/skills/build/plan-authoring-checks.md` holds the prose plan-authoring checks (return-shape widening, blocking-verification downgrade, deictic re-resolution, and so on). None of them turns a spec's verify-then-maybe-change sentence into a plan task.

A consumer project hit this through `/claude-tweaks:feedback` (fingerprint `feedback-31e632cd`). A spec named two API route files to read back, but the plan touched neither. Check E flagged every AC as uncovered by keyword, which was noise, and said nothing about the dropped step. Both per-task reviews passed. Only the final whole-branch review found the defect the spec had predicted, which cost one extra fix wave.

## Deliverables

1. **Prose check in `plugin/skills/build/plan-authoring-checks.md`:** a new check stating that every sentence in the spec's `## Technical Approach` or `## Gotchas` that tells the builder to verify, read back, or change something only if a condition holds becomes either a plan task or an explicit step inside one, and that the task's `Files:` block names the files the sentence reads.
2. **Mechanized warn-only check in `plugin/bin/plan-audit.js`:** a new check letter, a sibling of Check E (Check E stays AC-only). It extracts every repo path containing a `/` named in the `--spec` file's `## Technical Approach` (including its `### Key Files` list) and `## Gotchas`, and reports each path that no plan task's `Files:` block lists. It is warn-only, `ok` is always `true`, and it is skipped without `--spec`, exactly like Check E. A plan suppresses an entry with a waiver line of the same shape Check E uses (`Waived {path}: {reason}`). Root-level files with no `/` (`CLAUDE.md`, `package.json`) are a known gap: bare basenames are never read as paths (run ledger row 10).
3. Document the new check's result handling in `plugin/skills/build/plan-audit.md`'s Result interpretation, with the same amend-the-plan, no-stop, `log-decision.js` posture as `checkE.uncovered`, and add it to the file's opening check enumeration and the JSON envelope key list.

## Acceptance Criteria

1. Given a spec whose `## Technical Approach` names `src/a.js` and `src/b.js`, and a plan whose tasks list neither in any `Files:` block, the new check reports both paths. With a task listing `src/a.js` and a `Waived src/b.js: …` line, it reports neither.
2. A path named only in `## Acceptance Criteria` or `## Deliverables` is never reported by the new check.
3. Without `--spec`, the new check's envelope entry is `{ok: true, skipped: 'no-spec'}`, and the audit's exit code never changes because of the new check.
4. A spec section the parser cannot read (an unbalanced code span or fence) is reported as unparsed, never as fully covered.
5. `plan-authoring-checks.md` contains the new verify-then-maybe-change check, and `plan-audit.md` lists the new check letter in its opening enumeration and documents its result key.
6. Each new test fails when its asserted behavior is reverted.
7. `npm test` passes.

## Release Note

Plan audit now warns when a file the spec's Technical Approach says to verify or read back appears in no plan task.

## Technical Approach

Follow the project skill `.claude/skills/plan-audit-check-addition/` for every registration site: the check-letter enumerations, the `summaryLine`, the envelope key (no new flag, so no `USAGE` change), and the warn-only versus gating decision (warn-only here, since path extraction from prose is a heuristic). Reuse Check E's spec-reading seam in `parser.js`, generalized to read a named `##` section, and its waiver-line parser. Extract paths from backtick code spans that look like repo paths, so bare words are never treated as paths. Compare against the union of every task's `Files:` bullets (`FILES_HEADER_RE` in `parser.js`), normalizing `./` prefixes and line suffixes like `:88`. Apply `parse-signal-discipline`: an unreadable section must produce a distinguishable `unparsed` entry.

As built (architecture alignment, beneficial deviations): besides an exact match after normalization, a spec path also counts as listed, and a waiver also covers it, when the `Files:` or waiver path ends with `/` plus the spec path on a whole path segment (`via: 'suffix'`). This keeps the check quiet on this repo's plugin-relative citations (`_shared/x.md` for `plugin/skills/_shared/x.md`) without any quoted-text or substring fallback. A line containing a double-backtick code span, an unclosed fence inside a section, and an earlier unclosed fence that swallows a section heading are each reported as `unparsed`, never as covered or absent.

## Gotchas

- Check E's keyword-coverage noise was part of the original report: "every AC uncovered" on a well-covered plan. Do not copy its quoted-text fallback into the new check. Path matching is exact after normalization, so it should be quiet on a well-formed plan.
- Key Files lists routinely include files a build only reads. Those are exactly the paths this check exists to catch, so a read-only path still needs a task that names it or an explicit waiver. Say so in `plan-audit.md`, so authors do not read the warning as a false positive.
- The `plan-audit-check-addition` skill notes that check-letter enumerations went stale on each of the last two additions. Grep the repo for the enumeration phrasing before declaring the sweep complete.

## Original request

build plan-authoring: a spec's "verify X / change Y only if" Technical Approach step can vanish from the plan unflagged

**Summary:** A spec's Technical Approach verification step ("read back / change only if") can drop out of the build plan with no check flagging it; only the final whole-branch review catches the resulting defect.

**Kind:** Gap

**Affected component:** skills/build (plan-authoring-checks.md) + bin/plan-audit.js Check E

**Use case:**

## What happened

A spec's Technical Approach said, in so many words: "before committing to how the `<affected views>` show it, read the actual rows back from `<api route file A>` and `<api route file B>` … change those readers only if `<the spec's data-model change>` breaks them." The plan `/superpowers:writing-plans` produced had no task touching either file. `plan-audit.js` Check E (AC-clause coverage, warn-only) listed every Acceptance Criterion as uncovered by keyword, which is noise on a well-covered plan, but it reads only `## Acceptance Criteria`, so it said nothing about the dropped Technical Approach step. Both per-task reviews passed, because each reviewed only its own task's diff. The final whole-branch review was the first to find the defect the spec had predicted: the data-model change did break route A's reader, and a user-facing summary that route serves would have been wrong on every run. The fix needed one more fix wave and re-review.

## Gap

A spec's Technical Approach and Gotchas hold conditional verification steps ("verify X against Y", "change Z only if …") that are neither deliverables nor acceptance criteria. Nothing between `/specify` and the final review checks that the plan carries them.

## Proposal

- **plan-authoring-checks.md:** a check that turns every "verify / read back / change only if" sentence in the spec's Technical Approach or Gotchas into a plan task, or an explicit step naming the files it reads.
- **plan-audit.js:** extend Check E, or add a sibling check, to flag a file path named in the spec's Technical Approach that no task's `Files:` block lists. Warn-only, like Check E.

## Evidence

Final whole-branch review finding (Important), fixed in a follow-up commit with a regression test. The plan file's task list had no entry for either named file.
