# 2545: harness-health validate-findings: a Skills curation judge pushes the health-state cursor to the remote once per analysed skill

Surface: infra

## Current State
`skills/wrap-up/skill-curation.md`'s Skills curation row mandates running `bin/harness-health.js validate-findings` once per analysed skill. That command records its health-state cursor by pushing a commit directly to the remote `health-state` ref on every call. In a standalone `/claude-tweaks:wrap-up` run whose Skills row analysed 4 candidate skills, this produced four separate remote pushes as a side effect of what is meant to be a read/judge step — confirmed by `git ls-remote origin health-state` advancing once per call. The Skills curation judge is otherwise a fan-out agent forbidden any git mutation, so this remote-write side effect is inconsistent with the row's own no-mutation contract, and adds latency plus remote noise proportional to the number of skills analysed in a single row.

## Deliverables
1. Change `bin/harness-health.js validate-findings`'s default behavior to record the health-state cursor locally only (no remote push).
2. Add an explicit way to push the accumulated cursor once — either a `--push` flag on `validate-findings` or a separate `harness-health.js push-cursor` subcommand.
3. Update `skills/wrap-up/skill-curation.md` so the Skills curation row's per-skill judge calls `validate-findings` without pushing, and the controller (row end, or Phase 4) performs exactly one push of the accumulated cursor state.

## Acceptance Criteria
- Running `bin/harness-health.js validate-findings` against N candidate skills in a single wrap-up Skills row produces zero remote pushes to `health-state`, verified by `git ls-remote origin health-state` showing no change in ref sha across the N calls.
- The new push mechanism (`--push` flag or `push-cursor` subcommand), invoked once after the row completes, produces exactly one remote push carrying the accumulated cursor state from all N local recordings — verified by `git ls-remote origin health-state` advancing exactly once and the pushed commit containing the same cursor data the N local calls would have produced individually.
- `skills/wrap-up/skill-curation.md`'s Skills curation row text is updated to reflect the new no-push-by-default call, plus the single controller-side push call and where in the row's lifecycle (row end, or Phase 4) it happens.
- A fan-out Skills curation judge, run per this updated procedure, performs zero git mutations of any kind (matching the existing no-mutation contract already asserted for that judge in other respects).

## Release Note

Stopped the skills curation step from pushing health-state updates to the remote once per skill.

## Technical Approach
Add a local-only cursor write path to `bin/harness-health.js validate-findings` (or confirm one already exists and simply stop the remote push from firing on that path), gated behind a default now flipped away from pushing. Add the explicit push mechanism as a thin wrapper around the existing git-push logic already implemented for the remote `health-state` ref. Update `skill-curation.md`'s prescribed step text to call the non-pushing form per-skill and the pushing form once, at the row's natural end point.

### Key Files
- `plugin/bin/harness-health.js` — `validate-findings` subcommand; flip the default to local-only recording, add `--push` flag or `push-cursor` subcommand
- `plugin/skills/wrap-up/skill-curation.md` — Skills curation row prescribed steps; update per-skill call to the non-pushing form, add the single controller-side push call

## Gotchas
- Confirm no other caller of `validate-findings` relies on its current always-push behavior before flipping the default — a sweep of call sites is warranted (`grep -r "validate-findings" plugin/`).
- If the local cursor recording mechanism doesn't already exist independent of the push, this may require adding local persistence, not just suppressing an existing push — check `bin/harness-health.js`'s current implementation before assuming the local-write path is already there.
- The single controller-side push must aggregate cursor state from all N per-skill local recordings correctly — verify the pushed commit reflects all N skills' findings, not just the last one recorded.
