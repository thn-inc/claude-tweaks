# 2499: Flaky allowlist: tests/reconcile.test.js

Surface: infra

Origin: wrap-up leftover from #2028
Defer-reason: pre-existing-outside-diff

## Current State

`tests/reconcile.test.js:1491` (`reconcile(): FAST_CHECKS runs the preflight and the shared
fetch concurrently, not serially (#872)`) failed once in a full `npm test` run (8988 tests,
127s; elapsed 463ms vs. an expected ~200ms concurrency window), during #2028's wrap-up.
Isolated re-run (`node --test tests/reconcile.test.js`) passed cleanly, 103/103, the same test
completing in 323ms. No change in #2028's own diff (bookkeeping-only: a materialized spec file,
a plan, and a ledger) touches `reconcile()`, its preflight, or its shared-fetch path — this is a
timing-sensitive assertion racing against machine load from the full suite, not a regression.

The test asserts `elapsed < HEALTH_DELAY_MS * 2` (400ms) after `Promise.all`-dispatching a mocked
`ghHealthCheckAsync()` (artificially delayed 200ms) alongside the real `sharedFetchAsync()` call
(`plugin/bin/lib/reconcile/index.js:207-209`, a genuine local-fixture `git fetch` — not
artificially delayed). Widening the margin further (e.g. 3x/600ms) would reduce false failures
under load but also erodes the test's ability to actually catch a regression to serial
execution: a serial run only adds `sharedFetchAsync`'s own real (likely small) duration on top of
the 200ms mock delay, so a wide enough margin to absorb load jitter risks being wide enough to
also absorb an actual serial regression — the margin and the detection power trade off directly
against each other on a wall-clock assertion. `.claude-tweaks/verify-scope.json` has no `flaky`
key today — the allowlist schema this record's second option proposes doesn't exist yet and would
be a new subsystem built for one test.

## Deliverables

- [ ] Either loosen the timing assertion (e.g. widen the window, or assert ordering/concurrency
      via a mechanism other than wall-clock elapsed time), or add `tests/reconcile.test.js` to
      `.claude-tweaks/verify-scope.json`'s `flaky.files` allowlist with a `maxRetries: 1` entry
      and a per-suite `retry` command template (`"retry": {"tests": "node --test {file}"}` —
      the project's only declared suite key is `tests`).

## Acceptance Criteria

- Under contended machine load (a concurrent `npm test` run on the same host), this test no
  longer fails on timing alone — either the assertion tolerates load, or the allowlist entry
  retries it once and the retry passes.
- The test still fails if `FAST_CHECKS` regresses to serial dispatch of the preflight and the
  shared fetch (no loss of detection power as a side effect of the fix).

## Technical Approach

Recommended: replace the wall-clock margin with a deterministic overlap assertion, not a wider
threshold. Record each call's own start/end timestamp inside the test (wrap `ghHealthCheckAsync`
and `sharedFetchAsync` — or intercept via the same mock-injection points the test already uses
for `ghHealthCheckAsync`, adding an equivalent timing wrapper around `sharedFetchAsync` if one
isn't already injectable) and assert the two calls' `[start, end]` windows overlap (e.g.
`healthStart < fetchEnd && fetchStart < healthEnd`). Concurrent dispatch always overlaps; serial
dispatch never does, regardless of how fast or slow the machine is that run — this is immune to
load-induced jitter in a way no wall-clock threshold can be, without sacrificing the ability to
catch a genuine regression to serial execution.

Prefer this over both options the record's Deliverables originally proposed: widening the
existing margin trades detection power for stability (see Current State); the `flaky.files`
allowlist route requires designing and building a new `verify-scope.json` schema field and its
consuming retry logic for the sake of one flaky test, a disproportionate lift for this record's
actual scope. If the overlap-based rewrite proves impractical during implementation (e.g. the
current mock-injection points for `sharedFetchAsync` don't support timing instrumentation
cleanly), fall back to widening the margin as documented above, but only as a fallback — not the
default plan.

- This is a test-only change — no production code in `plugin/bin/lib/reconcile/` should need to
  change for either the recommended fix or the fallback.
