# 2500: Flaky allowlist: tests/hooks-git-exec.test.js

Surface: infra

Origin: wrap-up leftover from #2028
Defer-reason: pre-existing-outside-diff

## Current State

`tests/hooks-git-exec.test.js:186,204` (`CT_HOOKS_GIT_TIMEOUT_MS env override raises the
budget…` and `an explicit opts.timeoutMs still wins…`) deliberately race a `timeoutMs: 1`
override against a real `git rev-parse` subprocess and assert the timeout branch fires. During
#2028's wrap-up: full `npm test` — 1 fail (this file). Three isolated re-runs (`node --test
tests/hooks-git-exec.test.js`) — 2 failed (same assertion, `null` where `'timeout'` was
expected — the subprocess completed inside 1ms under a lightly-loaded run), 1 passed clean
(18/18). No change in #2028's own diff (bookkeeping-only) touches `runGit`/`runGitAsync` or any
caller in `hooks.js`. Same machine-load-timing-race shape as the sibling flaky-allowlist
proposal for `tests/reconcile.test.js` (#2499).

`plugin/bin/lib/hooks/git-exec.js`'s own header comment (lines 7-12) names the fix technique
directly: the module deliberately calls `cp.execFileSync(...)` via property access rather than a
destructured import specifically so "a test's `t.mock.method(cp, 'execFileSync', ...)`" can
intercept it — this module was built anticipating exactly this kind of mock-injection test need,
but the two flaky tests don't use it; they race a real subprocess against wall-clock time
instead. `classify()` (`git-exec.js:77-87`) determines `FAILURE.TIMEOUT` from `err.code ===
'ETIMEDOUT' || err.killed === true || err.signal === 'SIGTERM'` — a synthetic error carrying any
one of those is classified identically to a real timeout kill, so a mock can exercise the same
classification logic under test without spawning a real process or waiting on real time.

## Deliverables

- [ ] Rewrite both races (`tests/hooks-git-exec.test.js:186` and `:204`) to use
      `t.mock.method(cp, 'execFileSync', ...)` (the technique `git-exec.js`'s own header comment
      already names) throwing a synthetic error with `killed: true, signal: 'SIGTERM'` instead of
      racing a real `git rev-parse` subprocess against `timeoutMs: 1` — deterministic regardless
      of machine load, no wall-clock dependence at all.
- [ ] If a genuinely real-subprocess-timeout test still has independent value (e.g. an
      integration-style smoke test that `execFileSync`'s own timeout mechanism actually fires),
      keep at most one such test and move it out of the main suite's default fast path, or accept
      it as the allowlist fallback below — but the two tests this record targets should not stay
      wall-clock races once the mock-based rewrite lands.

## Acceptance Criteria

- Under contended machine load, neither test fails on timing alone — the mock-based rewrite makes
  both deterministic, not merely more tolerant.
- Both tests still correctly distinguish the two behaviors they exist to pin: the env-var budget
  override applies when `opts.timeoutMs` is absent, and an explicit `opts.timeoutMs` still wins
  over the env var when both are present.
- `npm test` passes, including 10+ consecutive isolated runs of `tests/hooks-git-exec.test.js`
  with no timing-related failure (verifying the race is actually eliminated, not just less
  likely).

## Technical Approach

For each of the two tests, replace the real `runGit(['rev-parse', ...], dir, { timeoutMs: 1 })`
call (or `runGitAsync`'s twin) with a `t.mock.method(cp, 'execFileSync', () => { const e = new
Error('mock timeout'); e.killed = true; e.signal = 'SIGTERM'; throw e; })` stub scoped to that
test (restored via the mock's own teardown or a `finally`, matching the existing
`CT_HOOKS_GIT_TIMEOUT_MS` env-var save/restore pattern already in both tests). Call `runGit`
exactly as today; only the underlying subprocess call is intercepted, so the env-var-vs-opts
precedence logic under test runs unmodified. `runGitAsync`'s twin (line ~175, the earlier
`Promise.all` shape test) is a different test not targeted by this record — check whether it
shares the same race and needs the identical treatment as part of this fix, since it calls
`runGitAsync(..., { timeoutMs: 1 })` against a real subprocess too.

## Gotchas

- Don't mock `execFileSync` so broadly that it also intercepts the *success* path other tests in
  this file rely on — scope the mock to only the two tests being rewritten, restored immediately
  after each.
- Same underlying flakiness family as #2499 (`tests/reconcile.test.js`) — both are wall-clock
  races against real subprocess/timer completion under load — but the fixes diverge: #2499's
  concurrency assertion has no real-subprocess mock point available and needs an overlap-based
  rewrite, while this record's tests are racing a subprocess that `git-exec.js` was already built
  to let a test intercept.
