# 1999: plan-audit: Check C and Check A false-positive on append-to-existing-file and new-directory plans

Surface: infra

## Current State

`bin/plan-audit.js` (invoked by `/claude-tweaks:build` Common Step 1.5, contract in `build/plan-audit.md`) runs four deterministic checks over a plan. Two of them model the plan as static:

- **Check A** (`plugin/bin/lib/plan-audit/checks.js`, `checkA`): a `Create:`/`Test:` bullet passes when its *parent directory* exists on disk today; a `Modify:`/`Delete:` bullet when the path exists. The entries are checked independently, so a `Create: newdir/nested/FILE.md` whose parent is only created by another `Create:` bullet in the same plan (or by the plan's own first write) is reported missing. `parser.js`'s `extractFileEntries` collects all `Files:` bullets across tasks, so the information needed (every path the plan creates) is already in hand.
- **Check C** (`checkC` plus `looksPassing`): for each task whose Step 2 declares `Run: {command}` / `Expected: FAIL …`, runs the command once against the current tree and flags it when it passes (exit 0, or a success marker with no failure marker). It has no notion of the task's Step 1: a Step 1 that *appends* tests to an existing, passing test file makes Step 2 pass today by construction, and a test-name filter cannot help (vitest exits 0 on zero matched tests; `node --test --test-name-pattern` likewise reports zero tests as success).

Observed on plugin 6.116.0: both shapes stopped a run; the operator pre-created directories, edited the plan twice, and logged a deviation. Tests: `tests/bin-lib/plan-audit/checks.test.js` ("checkA passes for Create when the parent directory exists", "checkA fails for Create when even the parent directory is missing", `looksPassing` cases), `cli.test.js` (AC6 Check C fixture, and the "genuinely fails pre-dispatch is not a finding" case), `parser.test.js` (Step 2 extraction).

## Deliverables

- [ ] **Check A knows what the plan creates.** `checkA(entries, repoRoot)` first collects the set of directories the plan itself will bring into existence: every `Create:`/`Test:` entry's own path (a file) and every ancestor directory of every `Create:`/`Test:` path. A `Create:`/`Test:` bullet then passes when its parent exists on disk **or** is an ancestor of, or equal to, a directory in that plan-created set. `Modify:`/`Delete:` semantics are unchanged. The finding message for a still-missing parent names the nearest existing ancestor so the author sees where the gap starts.
- [ ] **Check C understands append-to-existing.** `parser.js`'s Step 2 extraction also captures the task's Step 1 text; `checkC` treats a task as *append-shaped* when Step 1's text names a path that (a) appears in the task's `Modify:` or `Test:` bullets, (b) exists on disk, and (c) is the same path Step 2's `Run:` command names (token match on the repo-relative path). For an append-shaped task, a passing pre-run is not a finding: the entry is reported under a new `checkC.appendShaped` array (task, title, command, path) so the audit output still shows the command was pre-run and why it was accepted. An explicit marker `Expected: FAIL after Step 1` is accepted as an equivalent declaration without the path heuristic, and `build/plan-audit.md` documents the marker as the author-side escape hatch.
- [ ] **Prose.** `build/plan-audit.md`'s Check A and Check C bullets state both rules and the marker; `plan-audit.js`'s summary line counts `appendShaped` entries separately from findings.
- [ ] **Tests.** `checks.test.js`: Create-under-plan-created-directory passes; Create under a missing directory not created by the plan still fails; nested two-level creation passes; a `Modify:` under a plan-created directory still fails (Modify needs the file today). Check C: append-shaped task with a passing pre-run → no finding, one `appendShaped` row; the same task without a matching `Modify:`/`Test:` bullet → still a finding; the explicit marker → no finding regardless of heuristic; the existing AC6 fixture (a genuinely non-discriminating command) still fails. `parser.test.js`: Step 1 text captured; the marker parsed. `cli.test.js`: summary line shows the append count.

## Acceptance Criteria

1. A plan with `Create: newdir/nested/subdir/FILE.md` and no existing `newdir/` passes Check A when the plan also creates a file under `newdir/nested/` (or the same bullet is the first creation), and fails when nothing in the plan creates `newdir/`.
2. A task whose Step 1 appends tests to an existing `Test:` file and whose Step 2 runs that file with `Expected: FAIL` passes Check C with one `appendShaped` row; an `Expected: FAIL after Step 1` marker passes without the heuristic.
3. The existing AC6 fixture (command already passes, no append shape, no marker) still fails Check C, and "genuinely fails pre-dispatch" is still not a finding.
4. `build/plan-audit.md` documents both rules and the marker.
5. `npm test` green; every existing case in `tests/bin-lib/plan-audit/` passes unchanged.
6. Re-running the reported plan through `node bin/plan-audit.js` in a fixture exits 0 with the append row reported; quoted in the PR description.

## Technical Approach

Keep both checks deterministic and read-only. Check A gains plan-awareness by deriving the created-directory set from the entries it already has, no filesystem writes. Check C keeps "run once and look for a passing signature" as its only mechanism and adds a narrow, path-anchored exception plus an explicit marker; the marker is the author's tool when the heuristic cannot see the shape, and the `appendShaped` array keeps the accepted case visible in the audit output rather than silently passing.

### Key Files

- `plugin/bin/lib/plan-audit/checks.js` — `checkA` plan-created directory set; `checkC` append-shape exception and `appendShaped` output
- `plugin/bin/lib/plan-audit/parser.js` — capture Step 1 text per task; parse the `Expected: FAIL after Step 1` marker
- `plugin/bin/plan-audit.js` — summary line counts `appendShaped`
- `plugin/skills/build/plan-audit.md` — Check A / Check C bullets and the marker
- `tests/bin-lib/plan-audit/checks.test.js`, `parser.test.js`, `cli.test.js` — new cases

## Gotchas

- The append heuristic must anchor on the path appearing in both Step 1 and the `Run:` command; a Step 1 that merely mentions "tests" is not append-shaped.
- `Expected: FAIL after Step 1` must still start with `FAIL` so `extractVerificationChecks`'s existing "Expected starts with FAIL" scope keeps selecting the task.
- Check A's created set must be computed over *all* tasks' entries (the parser already merges them), since the creating bullet may sit in an earlier task.
- The audit's skip gate (fewer than 3 file references and no scope keywords, or `fast-lane`) is unchanged.

## Original request

**Summary:** `plan-audit.js` reads as a stop on two plan shapes that are structurally valid — a task whose Step 1 appends new tests to an existing (already-passing) test file, and a `Create:` path whose parent directory is itself created by the plan.

**Kind:** Defect

**Affected component:** `bin/plan-audit.js` (invoked by `/claude-tweaks:build` Common Step 1.5)

**Repro steps:**
1. Write a plan task whose Step 1 is "append these tests to `test/existing.test.ts`" and whose Step 2 is `vitest run test/existing.test.ts` with `Expected: FAIL`.
2. Run the plan audit before dispatch. Check C flags Step 2 as non-discriminating because the file exists and passes today — but it will fail as soon as Step 1 lands, which is exactly the discrimination the task relies on. A `-t` name filter does not help: vitest exits 0 on zero matched tests.
3. In the same plan, list `Create: newdir/nested/subdir/FILE.md` where `newdir/nested/` does not exist yet. Check A flags the missing parent directory even though an earlier `Create:` line in the same plan is the thing that makes it exist.

**Expected vs. actual:**
Expected: Check C models "Step 1 appends to an existing test file" (or accepts an explicit `Expected: FAIL after Step 1` marker); Check A treats a `Create:` path whose parent is itself a `Create:` target — or a new-directory path — as satisfied.
Actual: both read as stops; the run had to pre-create directories, edit the plan twice, and log a deviation to proceed.

**Definition:** Clear

**Plugin version:** 6.116.0
