# 2749: Add an autonomous-agent blast-radius check to hardening practice

Surface: infra

## Current State

OpenAI's own autonomous coding agents reportedly attacked RubyGems.org's supply-chain infrastructure — a vendor's unattended agents causing real infra harm, not a third-party attacker. `dispatch` runs as this user's own unattended agent hub with no documented check on what an autonomous build/dispatch agent is allowed to reach (registries, network egress, credential scope). No existing claude-tweaks check evaluates an agent's blast radius before granting it unattended/`auto:build` trust.

**Verified during shaping:** "blast radius" already appears in this codebase (`dispatch/SKILL.md`, `dispatch/configuration.md`, `dispatch/settle-and-merge.md`, `code-health/SKILL.md`) — but every existing use is the record-scoring sense: how bad a *specific code change* could be if it goes wrong (the `risk:*` label's own "blast radius, reversibility" criteria, `_shared/work-record.md`'s Scoring axis). None of the existing usages audit the *agent's own outer boundary* — what registries, network destinations, or credentials an unattended dispatch/build agent can actually reach, independent of any one task's content. This record's proposal is a genuinely distinct, not-yet-built capability, not a duplicate of the existing risk-scoring mechanism.

## Deliverables

- A hardening check (a lens, or a new row in `/code-health` or `/security-review`) that asks what an autonomous agent's tool/network/credential scope actually is, not just whether a given task behaves correctly — distinct from the existing `risk:*` scoring, which judges a specific change's blast radius, not the agent's standing reach.
- Guidance for scoping dispatch-style unattended agents to least-privilege registry/network access (what should an unattended build agent NOT be able to reach, by default).

## Acceptance Criteria

- The check runs standalone and as a step within `/review` or `/security-review`.
- Applying it to dispatch's own agent-trust config reports pass/fail per scope dimension (registry access, network egress, credential scope — whichever dimensions the implementation settles on).
- `npm test` passes.

## Release Note

Added a hardening check for how much an autonomous agent's tools, network, and credentials can reach.

## Technical Approach

Scope the check's dimensions concretely before implementing — the record names three candidates (registries, network egress, credential scope) but the actual claude-tweaks/dispatch environment (this plugin runs inside Claude Code's own tool sandbox, not a bespoke agent runtime) may only meaningfully audit a subset of these; ground the check in what's actually inspectable/configurable in this environment rather than a generic checklist copied from the source incident's different context (OpenAI's own agent infrastructure is architecturally different from a Claude Code plugin's dispatch mechanism). Integrate as a new check function alongside `/security-review`'s existing checks (the closer thematic fit — credential/scope auditing is security-review's territory) or as a `/code-health` finding category, whichever existing skill's own scan structure fits the "run standalone and as a step within an existing skill" AC most naturally — read both skills' existing check-registration patterns before choosing.

### Key Files

- `plugin/skills/security-review/` or `plugin/skills/code-health/` — the more likely home for the new check, pending a structural fit decision at build time
- `plugin/skills/dispatch/configuration.md` — dispatch's own agent-trust config, the concrete target the AC's "applying it to dispatch's own config" needs to run against
- `plugin/skills/_shared/work-record.md` — the existing `risk:*` Scoring axis, cited here only to confirm this record's proposal is distinct from it, not to be modified

## Gotchas

- Don't conflate this with the existing `risk:*`/blast-radius record-scoring mechanism — that's per-task judgment already in place; this record's check is about the agent's own standing capability boundary, a different question entirely.
- The source incident (OpenAI agents vs. RubyGems) involved a different agent architecture than this plugin's own dispatch mechanism — treat it as motivating evidence that this class of risk is real, not as a template to copy literally; ground the actual check dimensions in what's true of *this* environment.
