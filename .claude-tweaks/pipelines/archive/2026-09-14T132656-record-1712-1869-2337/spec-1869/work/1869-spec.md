# 1869: bin/wrap-up-state.js: reports `UNPUSHED (no upstream)` for a pr-first branch that origin already has

Surface: infra

## Current State
`bin/lib/wrap-up/state.js`'s `readState` derives push status from the configured upstream only: it runs `git rev-parse --abbrev-ref --symbolic-full-name @{u}`, and when that fails it sets `upstream: null` and `pushed: false` — the comment reads "Absent an upstream there is nowhere for the work to have gone, so it is unpushed". `bin/lib/wrap-up/render.js` then prints `{head} — {commits}, UNPUSHED (no upstream)`, and `bin/wrap-up-state.js` uses `state.upstream` to pick which reflog to read. That premise is false for every `pr-first` run: `_shared/pr-early-run-lifecycle.md`'s Step 2 and `_shared/git-discipline.md`'s phase-exit push use `git push origin {branch}` with no `-u`, so `@{u}` stays unset (or, since #1860, points at the branch-off point `origin/main` when the worktree was created with `-b {branch} origin/main`) while `refs/remotes/origin/{branch}` is up to date after every push. The State block that `wrap-up/summary-template.md` says to render verbatim therefore claims UNPUSHED for work that origin already holds, and the reporter had to run `git branch --set-upstream-to` by hand to get a truthful line.

The ref the helper needs is already local: `git push origin {branch}` updates `refs/remotes/origin/{branch}` in the pushing checkout, so no fetch is required to judge a push this run made; a fetch would only matter for pushes made elsewhere, which the wrap-up State block is not asked to cover.

## Deliverables
- [ ] `readState` gains a remote-ref fallback: when `@{u}` is unset, or resolves to a ref other than `origin/{branch}`, it checks `git rev-parse --verify --quiet --end-of-options refs/remotes/origin/{branch}`; when that ref exists, `ahead`/`behind` are computed with `rev-list --left-right --count refs/remotes/origin/{branch}...HEAD` and `pushed` follows the same `ahead === 0` rule. The result carries a new `remoteRef` field (`'origin/{branch}'` or `null`) and a `pushedVia: 'upstream' | 'remote-ref' | null` field; `upstream` keeps reporting the configured `@{u}` (or `null`) unchanged.
- [ ] `render.js` distinguishes the three shapes: `pushed (origin/{branch}; no upstream configured)` when `pushedVia === 'remote-ref'`; the existing `pushed`/`UNPUSHED ({upstream})` lines when `pushedVia === 'upstream'`; `UNPUSHED (no upstream, origin/{branch} absent)` when neither ref exists. The unknown case (`pushed === null`) keeps its current wording.
- [ ] `bin/wrap-up-state.js`'s reflog read uses `state.remoteRef` when `state.upstream` is null, so the concatenated-reflog logic sees the remote-tracking ref's updates too.
- [ ] Tests in `tests/bin-lib/wrap-up/state.test.js` (fake-runner style, beside the three existing `pushed` cases): no upstream + remote ref present + ahead 0 → `pushed: true`, `pushedVia: 'remote-ref'`; no upstream + remote ref present + ahead 2 → `pushed: false`; no upstream + no remote ref → `pushed: false`, `remoteRef: null`; inherited upstream (`origin/main`) + remote ref present → judged by the remote ref, not `@{u}`; existing cases unchanged. `tests/bin-lib/wrap-up/render.test.js` pins the three rendered lines.
- [ ] `docs/plugin-structure.md`'s `plugin/bin/lib/wrap-up/` line (the family-1 sentence that says `state.js` reads branch/upstream/ahead-behind/pushed facts) names the remote-ref fallback in one clause.

## Acceptance Criteria
1. On a branch pushed with `git push origin {branch}` and no upstream configured, `node bin/wrap-up-state.js --since <base>` renders a `pushed` line naming `origin/{branch}`; after one more local commit it renders `UNPUSHED` with the ahead count.
2. On a branch whose `@{u}` is the inherited `origin/main` (the #1860 shape) but whose `refs/remotes/origin/{branch}` matches HEAD, the line reads pushed, not `UNPUSHED (origin/main)`.
3. A branch that was never pushed still renders UNPUSHED, and a failed `rev-list` read under either ref still yields `pushed: null` (unknown), never a definite false.
4. All existing `state.test.js` and `render.test.js` cases pass unmodified; `npm test` is green.

## Technical Approach
Helper-side fallback rather than `-u` on the lifecycle's first push: the fallback fixes the State block for branches pushed by any tool (the record's own second point), needs no change to the three skill files that spell the push command, and does not interact with `hasNoUpstreamYet` in `pre-tool-use.js`, which since #1860 already reads `@{u}` vs `origin/{branch}` and would need re-verification if the lifecycle started setting upstreams. The `--end-of-options` separator before the ref follows the repo's `git` argument rule (#1686's citation).

### Key Files
- `plugin/bin/lib/wrap-up/state.js` — `readState` (the `@{u}` read, `ahead`/`behind`, the `pushed` rule and its comment).
- `plugin/bin/lib/wrap-up/render.js` — the `UNPUSHED (no upstream)` line and its siblings.
- `plugin/bin/wrap-up-state.js` — `state.upstream` reflog selection.
- `tests/bin-lib/wrap-up/state.test.js`, `tests/bin-lib/wrap-up/render.test.js` — fake-runner fixtures.
- `plugin/skills/_shared/pr-early-run-lifecycle.md`, `plugin/skills/_shared/git-discipline.md` — read-only: the push form that leaves `@{u}` unset.

## Gotchas
- `git branch --show-current` returns empty on a detached HEAD; the fallback must skip the remote-ref probe when `branch` is null, keeping today's detached-HEAD output.
- A remote named anything other than `origin` is out of scope; the lifecycle pushes to `origin` by contract (`_shared/integration-branch.md`), so hard-code it and say so in the comment rather than parsing `branch.{name}.remote`.
- The ordering rule stays: `pushed` is judged against whichever ref was chosen, never against both; a configured upstream that equals `origin/{branch}` takes precedence and the fallback is not consulted.
- `pushedVia` is additive on the JSON shape `--json` emits (#1930); no existing consumer reads the new field, so the shape change is backward compatible.

## Original request
**Summary:** `wrap-up-state.js --since <base>` rendered `Branch <branch> — 12 commits, UNPUSHED (no upstream)` for a branch whose every commit was already on `origin` (the phase-exit push had just printed `<old>..<new> <branch> -> <branch>`). The pr-first lifecycle pushes with `git push origin {branch}` — never `-u` — so `@{u}` is unset on every pr-first run and the helper's "pushed" judgment is wrong for exactly the runs whose State block the wrap-up summary is told to render verbatim.

**Kind:** Defect

**Affected component:** `bin/wrap-up-state.js` (push-status derivation), with `skills/_shared/pr-early-run-lifecycle.md` Step 2 / `skills/_shared/git-discipline.md`'s phase-exit push as the reason `@{u}` is never set

**Cost this session:** one manual `git branch --set-upstream-to` to make the State block truthful, plus a Verdict line that had to be written from the push output instead of the helper — the opposite of what `summary-template.md` asks for ("never assert it landed from memory").
