# 1712: flow multi-spec: shared PR phase-checklist has no polish row, so a later frontend spec's polish is invisible on the PR

Surface: infra

## Current State
`_shared/pr-early-run-lifecycle.md` composes the shared draft PR body once, at run start (Step 3), including the phase checklist between the `phases-start`/`phases-end` markers. Two rules there decide whether a `polish` row exists:

1. Creation: "Omit a `polish` row when the record's `surface:` is `backend` (polish never runs)". In a multi-spec `/claude-tweaks:flow` run the PR is opened once, before spec 1's build, so "the record" is spec 1 and the rule never looks at specs 2..N.
2. Skip: "a skipped phase's row is removed at that phase's own would-be exit rather than predicted at creation". In a multi-spec run, spec 1's would-be polish exit removes the row even when spec 2 is frontend and will run polish minutes later.

`flow/multispec-pr-checklist.md` (#921) makes the rows cumulative and run-level (never reset per spec) but says nothing about rows that were never created or were removed by an earlier spec's skip. Net effect, as observed on a five-spec batch at 6.111.0 with a backend spec first: specs 2-4 ran real polish and the PR's checklist shows no polish row at all; the evidence lives only in each spec's `decisions.md` and `manifest.yml`.

## Deliverables
- [ ] Creation rule widened in `_shared/pr-early-run-lifecycle.md` Step 3: omit the `polish` row only when **every** record in the run has `surface: backend` — for a multi-spec run, read the batch's surfaces from the parent `manifest.yml`'s `specs[]` (the same list Step 3 already walks to emit one `Fixes #{m}` line per record); a single-record run keeps the current single-surface rule unchanged. `flow/steps-and-gates.md`'s phase-exit paragraph restates the creation rule ("omitted at PR creation only for a backend `surface:`") and is updated to the every-record wording in the same change.
- [ ] Skip rule scoped in the same file's Phase-checklist update section: in a multi-spec run, a spec's would-be polish exit never removes the row; the row stays `- [ ] polish` until some spec's real polish exit flips it, or the Pre-merge title/description refresh removes a still-unchecked `polish` row when no spec in the run ran polish. Single-record runs keep the current would-be-exit removal.
- [ ] `flow/multispec-pr-checklist.md`: one paragraph stating the run-level polish-row rule (present when any spec can run polish; checked by the first spec that does; removed at pre-merge only if none did), pointing at the two `pr-early-run-lifecycle.md` rules above.
- [ ] `flow/multi-spec.md`'s "PR phase-checklist convention" section gains one sentence naming the polish-row rule.
- [ ] Conformance assertions in `tests/pr-early-run-lifecycle.test.js`: the creation rule names the every-record condition and `manifest.yml`'s `specs[]`; the skip rule names the multi-spec deferral to the pre-merge refresh; `multispec-pr-checklist.md` carries the polish-row paragraph.

## Acceptance Criteria
1. For a multi-spec run whose first spec is backend and any later spec is frontend, the Step 3 template as documented yields a `- [ ] polish` row on the shared PR at creation.
2. For a multi-spec run whose every spec is backend, the row is omitted at creation exactly as today.
3. A backend spec's would-be polish exit in a multi-spec run leaves the row in place; a frontend spec's polish exit flips it to `- [x] polish`; the pre-merge refresh removes only a row still unchecked at that point.
4. Single-record runs: creation and skip behavior byte-identical to today's prose.
5. The conformance suite pins each of the three prose changes; `npm test` is green.

## Technical Approach
Prose-only change across three skill files plus test pins; no `bin/` code reads or writes the polish row (the checklist update is the compose-then-write-once `gh pr edit` procedure each phase skill performs). The creation rule's data source already exists at Step 3 (the `Fixes` enumeration walks `manifest.yml`'s `specs[].id`); extend that walk to `specs[]`'s surface facet, read per `flow/materialize.md`'s Resolution (the `surface:` lift rule `multi-spec.md` Step 3 pre-flight already applies), so the rule needs no new lookup. The pre-merge refresh (its step 2 re-runs the checklist update unconditionally) is the natural place for the deferred removal, since it is the last write before undraft.

### Key Files
- `plugin/skills/_shared/pr-early-run-lifecycle.md` — Step 3 template and the "Omit a `polish` row" rule; Phase-checklist update section's skipped-phase sentence; "Multi-spec runs share one PR" paragraph; Pre-merge title/description refresh step 2.
- `plugin/skills/flow/multispec-pr-checklist.md` — cumulative-rows rationale; add the polish-row paragraph.
- `plugin/skills/flow/multi-spec.md` — "PR phase-checklist convention (shared PR)" section.
- `plugin/skills/flow/steps-and-gates.md` — the polish phase-exit paragraph that restates the creation rule.
- `tests/pr-early-run-lifecycle.test.js` — existing prose pins for the checklist template.

## Gotchas
- `no-polish` on the step list is run-wide and still removes the row at the would-be exit (single-record) or at pre-merge (multi-spec); the rule change is about surface, not about the explicit escape hatch.
- Dispatch bundles (`dispatch/SKILL.md` file-overlap groups) share the same Step 3 template and the same `specs[]` walk, so the every-record condition applies to them too; say so in the Step 3 prose rather than leaving bundles to the single-record rule.
- The `surface:` facet can be absent on a record; the creation rule must count an absent surface as "can run polish" (only an explicit `backend` omits), because the real polish decision is made at runtime by `flow/steps-and-gates.md`'s decision tree and detection layer 2 — creation must never pre-empt it toward omission.
- Do not add a per-spec axis to the checklist; #921 declined it deliberately and `manifest.yml`'s `specs[].phase` remains the per-spec source.

## Original request
**Summary:** A multi-spec `/claude-tweaks:flow` batch's shared PR checklist is seeded once at PR creation from the *first* spec's surface, so when that first spec is backend (correctly omitting the polish row per the plugin's own rule) but a *later* spec in the same batch is frontend and genuinely runs polish, the PR checklist has no row to reflect that polish ever happened.

**Kind:** Gap

**Affected component:** `pr-early-run-lifecycle.md`'s phase-checklist template, as used by `/claude-tweaks:flow`'s multi-spec mode

**Use case:** A 5-spec multi-spec `/flow` batch where spec 1 is backend (`Surface: backend`) and specs 2-4 are frontend (`Surface: web`, `Design-intent: quiet`). The shared PR is opened at spec 1's build step; its phase checklist is seeded from spec 1's surface and correctly omits the polish row (backend specs skip polish). Specs 2-4 are genuinely frontend and each runs a real polish phase — design-intent-driven fixes get applied and logged to each spec's own `decisions.md`/`manifest.yml` — but the shared PR's checklist template has no per-spec-id axis, so there's no row anywhere on the PR itself showing that polish ran, or what it found. The only place this is visible is inside each spec's own run-directory audit trail, not the PR a reviewer would actually look at.

**Definition:** Clear — the fix is a well-defined widening of the template (e.g. a single run-level polish row that appears once any spec in the batch needs it, rather than deriving polish applicability from only the first spec), not an open design question.

**Plugin version:** 6.111.0
