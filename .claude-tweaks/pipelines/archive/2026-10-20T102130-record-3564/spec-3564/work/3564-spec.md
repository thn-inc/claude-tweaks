Verified against `origin/main` at `1c8cda70b`, where the test file is unchanged since `31d2ce142`.

Exactly one of the file's eight tests fails: `AC2.1 retired limit sentences are gone from every skill file` (line 108). The assertion that fails is the doctored-corpus control at line 127, not the real-corpus check:

```
+   'flow\\x.md: no documented step re-runs the pass'
-   'flow/x.md: no documented step re-runs the pass'
```

Root cause, test-side only. The test's own `walk()` helper (lines 110-118) lists files with `fs.readdirSync(dir, { recursive: true })`. Node joins recursive entries with the native separator, so on win32 the doctored file comes back as `flow\x.md`. The helper then uses that native relative path directly as a display ID (`hits.push(\`${f}: ${phrase}\`)`, line 115), and the control compares the result with the forward-slash literal `'flow/x.md: …'`. The display-ID producer is the test, not plugin code; no file under `plugin/` is involved. The real-corpus assertion `assert.deepEqual(real.hits, [])` passes on Windows only because a clean corpus yields no hits. On a real regression its message would carry the same backslash IDs.

CRLF plays no part. `collapse()` folds `\r` into whitespace, and the file's other section extractors already use `\r?$` and `split(/\r?\n/)`. The other seven tests pass in both Windows logs.

Reproduced in scratch on macOS with a win32 simulation. A `--require` preload makes recursive `fs.readdirSync` return `\`-joined entries, lets `fs.readFileSync` accept `\` the way Windows fs does, and sets `path.sep` to `\`. Run against the `origin/main` copy of the test and `plugin/`:

- Unsimulated, pre-fix: `# pass 8` / `# fail 0`.
- Simulated, pre-fix: `not ok 6 - AC2.1 …`, with the same `+ 'flow\\x.md: …'` / `- 'flow/x.md: …'` diff as the Windows log, and `# pass 7` / `# fail 1`.
- Simulated and unsimulated, with `toPosix` applied at the hit producer: `# pass 8` / `# fail 0`.

The simulation cannot show drive letters, real Windows fs semantics or `path.win32.join` behavior. It reproduces only the separator Node puts into recursive `readdirSync` entries, which is exactly what this failure turns on.

Sibling grep on `origin/main`. `git grep -nE "readdirSync\([^)]*recursive" -- '*.js'` finds this file's line 111 as the only recursive-readdir site in the repo. No `globSync` or async recursive `readdir` call exists. The broader class, a native relative path used as a display ID and compared with `/` keys, also fails on the same latest Windows run in eight other files. All eight are pre-existing baseline failures, not attributable to #3531, and all are out of scope here (see Gotchas).

## Release Note

Fixed a flow conformance test that failed on Windows because it compared a backslash file path with a forward-slash one.

## Technical Approach

This is a test-side fix that follows the "Display IDs and native paths are two contracts" rule in `.claude/skills/windows-checkout-test-parity/SKILL.md`. A path the code shows or compares as an ID uses `/` on every OS and is normalized at its producer with `shared-primitives.js`'s `toPosix(p, sep = path.sep)`. A path later opened with `fs` stays native. The producer here is the test's own `walk()`, which builds the hit string from a native recursive-readdir entry. So the fix goes there, and the expected literal stays as it is. The skill rejects per-fixture `.replace(/\\/g, '/')` patches and `path.join`-built expectations for display IDs, because they hide a producer that is still wrong.

The `sep` parameter on `hitId` follows the skill's injection pattern: the default stays `path.sep` for the real walk, and the pin passes `path.win32.sep` explicitly. That is the same seam `tests/bin-lib/shared-primitives.test.js` uses for `toPosix` itself. Do not stub `process.platform`.

Verified in scratch: two added lines (the `toPosix` require and the `hitId` helper with its pin) plus the changed `push` turn the simulated run from 7/1 to 8/0, and the unsimulated run stays 8/0.
