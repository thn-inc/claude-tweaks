## Technical Approach

The fix is test-side only, following `.claude/skills/windows-checkout-test-parity/SKILL.md`. Three of its rules apply:

- "A test extracts regions from live skill markdown → a CRLF input proving the extractor still finds the region" covers causes 1 and 2. `readText()` is the repo's single normalizing read. Normalizing again inside the extractor is what lets the CRLF case go red on Linux CI, as #3518 did with `refusalFenceBody`.
- The Anti-Patterns row "Treating a CRLF fix as the whole Windows fix for a test that extracts and runs a skill's shell snippet" covers the masked backslash-root layer in cause 2 and in the named-target sibling. #3517 and #3518 already fixed the identical shape this way (`tests/dispatch-neighbour-in-flight-mcp.test.js:74`, `tests/dispatch-per-record-groups-prose.test.js`'s `PLUGIN_DIR`).
- "Keep a win32-only real-process round-trip as the ground truth" is why cause 3 prefers running the block through a real shell on Windows over skipping it.

The pool-fetch test's `PATH` moves from the spawn env into the script because the spawn env's `PATH` is also what Node uses to find the shell. Overriding it there forces an absolute shell path, and Windows has no portable one. Assigning `PATH` inside the script leaves the shell lookup on the inherited environment and still hides `gh` from the block. All of the block's remaining commands (`echo`, redirections) are shell builtins.

The product-side question of whether a real Windows Claude Code install hands Git Bash a backslash `CLAUDE_PLUGIN_ROOT` belongs to #3555. This record does not touch the heredocs.

## Gotchas

- Do not fix the CRLF failures with a `.gitattributes` `eol=lf` rule, and do not loosen the extractors to accept `\r\r\n` or bare `\r`. The parity skill keeps `.gitattributes` scoped to the hashed upstream fixtures on purpose.
- Do not build a CRLF case from a raw read (`raw.replace(/\n/g, '\r\n')`). On a Windows checkout that yields `\r\r\n` (#3523). Build it from the `readText()` value and assert there is no `\r\r\n`.
- The pool-fetch test passes for the wrong reason if `gh` is reachable but fails for an unrelated cause, such as no auth or no git repo in cwd. That is why its go-red control plants a succeeding `gh` stub instead of relying on the real CLI. Keep the in-script `PATH` line as the block's first line, so nothing in the block runs before it.
- If the Windows run fails the pool-fetch test only on the `AUTO — dispatch: …` stderr match while the empty-pool assertion passes, suspect em-dash encoding through Git Bash's `echo`. Set a UTF-8 locale in the spawned env (`LC_ALL: 'C.UTF-8'`) rather than loosening the regex.
- Fixing only the excerpted test misses its siblings. The `per-record` excerpt names a test that #3518 already fixed; the failing one is the pool-fetch test. Read each file's isolated log from the dispatched run, not the record's excerpt, before calling the fix done.
- Keep the scope to these four files. `cli-validate-findings` (#3563) and `verify-expectations-writer-conformance` (#3562) also spawn `/bin/sh`, but their own records own them. Other open `Windows regression:` records (#3429, #3507, #3509, #3562, #3563, #3564, #3581) cover other commits and files.
