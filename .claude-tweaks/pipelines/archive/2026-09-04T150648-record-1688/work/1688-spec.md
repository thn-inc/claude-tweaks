## Current State

#1674 bounded `hasMaterializeCommit`'s git log to `{integration}..HEAD` so a materialize commit inherited from an unrelated merged run stops arming the IL-131 gate. `resolveIntegrationBranch` (`worktree-reap.js`) resolves that name from two sources only: an `integration-branch:` policy key, or `origin/HEAD`.

Neither is available in a no-remote `local-merge` project: there is no `origin`, and the policy key is normally unset (`policy-schema.js` documents it as needed only when the active branch is not the default). Such a repo still has a real local integration branch that materialize commits merge into — it is simply not *resolvable*. #1674 falls back to the pre-fix unbounded walk there, so the false positive it exists to fix persists for that whole project class.

This was reproduced during review: a bare no-remote repo, a materialize-shaped commit on `main`, then `git worktree add` a fresh branch off that HEAD. `resolveIntegrationBranch(wt)` returns `null`; `hasMaterializeCommit(wt, runDir)` returns `true` — the fresh worktree is armed against a commit it never made.

A second, related gap: `resolveIntegrationBranch` returns a **local** branch name, which can lag `origin/{integration}`. When HEAD has already merged `origin/{integration}` in — which `_shared/worktree-setup.md`'s post-creation catch-up does routinely — the lagging local ref leaves those merged-in commits inside the range and reproduces the same inherited-history arm. `review/code-mode-steps.md` states this repo's own house rule: never trust a bare local branch name, because a long-lived worktree's local tracking branch routinely drifts behind its remote.

## Deliverables

- [x] A third resolution source for the range bound when policy and `origin/HEAD` both come up empty — a local default-branch probe (`main`/`master`), scoped only to `hasMaterializeCommit`'s own range bound (`resolveLocalDefaultBranchBound` in `pre-tool-use.js`), never to the shared `resolveIntegrationBranch` — the reaper and `run-integrity.js` must keep "nothing resolved -> no safe measurement" per `_shared/integration-branch.md`'s per-consumer table (a local-branch guess there once reaped a worktree holding genuinely unmerged work).
- [x] The stale-local-ref case: `resolveIntegrationBranch` now upgrades a resolved local name to its already-on-disk `origin/{name}` remote-tracking ref when one exists (`preferRemoteTrackingRef`, no fetch) — applied to the policy-configured path in the shared resolver, and to `hasMaterializeCommit`'s own resolved bound (whichever of the three sources produced it) at its call site.
- [x] Tests covering a no-remote repo with inherited history (now returns `false`, was `true`) and a local ref lagging its remote-tracking counterpart.

## Gotchas

Resolved by keeping the new local-default-branch probe scoped entirely to `pre-tool-use.js`'s own call site, never inside the shared `resolveIntegrationBranch` — see `_shared/integration-branch.md`'s per-consumer table and its Anti-Patterns entry on this exact hazard.
