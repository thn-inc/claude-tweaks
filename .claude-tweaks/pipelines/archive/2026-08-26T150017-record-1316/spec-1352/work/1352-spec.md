# 1352: backlog grant: add gh-absent MCP fallback (blocks scheduled grant Routines)

Surface: backend

## Current State

- `plugin/skills/backlog/SKILL.md`'s Preflight section (`grant` mode paragraph) runs `_shared/forge-detection.md`'s Detection Ladder as an unconditional hard gate before any `gh` command for `grant` mode — there is no MCP-fallback branch.
- `_shared/forge-detection.md`'s check 2 note ("Check 2 does not gate on its own for a transport-aware consumer") already carves out an escape hatch for "a consumer with a documented MCP fallback," naming `/claude-tweaks:dispatch`'s `dispatch/mcp-transport.md` as the example — `backlog/grant-mode.md` and `backlog/SKILL.md` cite no such doc, so grant mode falls into the "no MCP fallback still stops at check 2" branch.
- `dispatch/mcp-transport.md` is the working reference implementation: a small delta-only doc (39 lines) documenting which of dispatch's `gh` call sites have a confirmed MCP-tool equivalent, loaded only when Preflight detects `gh` is absent.
- `_shared/github-write-transport.md` is the canonical CRUD mapping (list-by-label, create, edit/label, comment, close, get-single, list-comments) between `gh` CLI calls and GitHub MCP tools (`list_issues`, `issue_write`, `add_issue_comment`, `issue_read`) — it covers every call site `grant-mode.md` needs *except* the Cap-tracking section's `gh search issues --match comments` full-text comment search, which has no row in that table.
- `backlog/grant-mode.md`'s own `gh` call sites: Step 1's `gh issue list --label ready --state open` fetch, Step 4's `gh issue view "$ISSUE" --json labels` (bot:blocked probe) and `gh issue edit` (grant/re-authorize), the Audit format's comment post, and the Cap tracking section's `gh search issues --match comments "grant-mode-audit: date=..."` (today's grant count).
- `backlog/grant-mode.md`'s own Concurrency section already treats every label write here as idempotent — two overlapping firings at worst repeat the same write, no lock needed today under the `gh` transport.
- `_shared/issue-claims.md` documents the one durable MCP-compatible write-lock primitive in this codebase (`create_or_update_file`'s omitted/stale-`sha` compare-and-set, one level down from `gh`'s ref-level CAS), built for `/flow`'s claim lock — a candidate mechanism if a Cap-tracking redesign needs an atomic counter, but not yet shown to be required for grant mode's existing label writes.
- `capture/SKILL.md`'s own `gh issue create` on-failure branch degrades any `gh` failure (not-installed, broken, or a transient API error) straight to a local `unsynced: true` record — it has no MCP-first attempt at all.
- #65 (closed) hit this same failure class in `durable-state.js`'s health-state writes; its actual resolution moved those writes off both `gh` and MCP entirely, onto raw Git Data API primitives (`_shared/github-write-transport.md`'s own header note) — the fix stayed subsystem-local rather than establishing a reusable gh-absent pattern that transfers here.

- [ ] A resolved mapping (new CRUD-mapping row in `_shared/github-write-transport.md`, or a documented redesign) for the Cap-tracking section's `gh search issues --match comments` call, which the existing table doesn't cover.
- [ ] `backlog/SKILL.md`'s Preflight section (`grant` mode paragraph) updated to load the new fallback doc when `_shared/forge-detection.md` check 2 resolves `gh` absent, instead of treating grant mode as a check-2 hard-gate with no branch.
- [ ] `_shared/forge-detection.md`'s check-2 note updated to also name `backlog/mcp-transport.md` alongside `dispatch/mcp-transport.md` as a documented-fallback consumer, so that note stays the one place naming every transport-aware consumer.
- [ ] A written decision on whether `_shared/issue-claims.md`'s file-blob lock is needed anywhere in the new grant-mode MCP path — record the reasoning (grant-mode's existing Concurrency section already treats label writes as idempotent-and-lock-free) rather than reusing the lock reflexively.

## Technical Approach

Mirror `dispatch/mcp-transport.md`'s shape exactly: a short, delta-only doc loaded by `/claude-tweaks:backlog` only when Preflight's Detection Ladder check 2 resolves `gh` absent, stating which of `grant-mode.md`'s `gh` call sites map onto which GitHub MCP tool. Do not restate `_shared/github-write-transport.md`'s CRUD table — cite it, the same way `dispatch/mcp-transport.md` does, and add the one missing row (or documented workaround) for full-text comment search.

Concretely:

- Step 1's `gh issue list --label ready --state open --json ...` → `_shared/github-write-transport.md`'s "List open issues by label" row (`list_issues`, filtered by label + state).
- Step 4's `gh issue view "$ISSUE" --json labels` (bot:blocked probe) → that file's "Get a single issue by number" row (`issue_read`, get mode).
- Step 4's `gh issue edit --remove-label/--add-label` (grant + re-authorize) → that file's "Edit labels / body" row (`issue_write`, update mode).
- Audit format's comment post → that file's "Comment" row (`add_issue_comment`).
- Cap tracking's `gh search issues --repo ... --match comments "grant-mode-audit: date=${TODAY}"` has no row today. `_shared/github-write-transport.md` already bans `search_issues`/`gh issue list --search` for find-by-marker/dedup lookups (three real duplicate-digest incidents, #1016/#1079/#1089) because both ride an eventually-consistent index — the same objection applies to a full-text comment search used for a same-day count. Resolve this deliberately rather than copying the banned pattern: either find and document a consistent MCP-side equivalent, or redesign the cap-tracking read (e.g., a `list_issues`-then-`issue_read`-comments walk, bounded the same way the rest of this mode already bounds its reads) — state the choice and why in the new doc.
- Update `backlog/SKILL.md`'s `grant` mode Preflight paragraph (the line describing an unconditional "hard gate before any `gh` command") to branch exactly as `_shared/forge-detection.md`'s check-2 note already describes for a transport-aware consumer: `gh` absent → load `backlog/mcp-transport.md` and proceed; still a hard gate on checks 1 and 3 regardless of transport.
- Add `backlog/mcp-transport.md` to `_shared/forge-detection.md`'s check-2 note's example list, alongside `dispatch/mcp-transport.md`.
- Evaluate `_shared/issue-claims.md`'s file-blob CAS lock against grant-mode's actual write pattern before reusing it: `grant-mode.md`'s own Concurrency section already argues every label write here is idempotent and lock-free under the `gh` transport; check whether the MCP transport's `issue_write` calls preserve the same idempotency (a plain field update, not a ref-level CAS) before deciding a lock is unneeded here too, rather than assuming parity.
- Separately, read `capture/SKILL.md`'s on-failure branch (`gh issue create` failing for any reason falls back to a local `unsynced: true` record) and judge whether "not installed" deserves an MCP-first attempt before that fallback, or whether the existing degrade is an acceptable design for a lower-stakes, human-reconcilable path (`/claude-tweaks:tidy`'s Sync findings already reconcile `unsynced` records later) — this is a judgment call to record, not a mechanical port of the grant-mode fix.

## Gotchas

- `dispatch/mcp-transport.md`'s mappings were verified against a live cloud run (the bridge plan, Task 10) before check 2 stopped gating dispatch unconditionally — a prior attempt at that same bridge shipped the gate change before finishing the read-path bridge and produced an unstructured `gh: command not found` crash instead of a clean stop. Don't repeat that ordering mistake here: write and verify (or explicitly flag as unverified) `backlog/mcp-transport.md`'s mappings before flipping `backlog/SKILL.md`'s Preflight gate.
- `_shared/github-write-transport.md`'s ban on `search_issues`/`gh issue list --search` for find-by-marker/dedup lookups is not a style preference — it caused three real duplicate-digest production incidents (#1016, #1079, #1089) via an eventually-consistent search index. Cap tracking's `gh search issues --match comments` is exactly this pattern; don't just add a naive MCP `search_issues` equivalent without addressing the same consistency risk the ban already flags.
- #65's resolution for the structurally similar health-state gh-absent gap did not produce a reusable "gh-absent → MCP" pattern — it moved those writes to raw Git Data API primitives instead, bypassing both `gh` and MCP. Don't assume #65's fix transfers directly; the reusable precedent for this issue is `dispatch/mcp-transport.md`, not #65.
- Grant mode's Concurrency section reasons about idempotency under the `gh` transport specifically (a plain label add repeats harmlessly). Verify the same idempotency claim holds for whichever MCP tool call replaces it before treating the "no lock needed" conclusion as automatically portable.
- `backlog/SKILL.md`'s Preflight section documents three separate `grant`-adjacent stops (`overview`, `refine`'s grant sub-stage, and `grant` mode itself), each with its own hard-gate/local-files-stop wording — this record's scope is `grant` mode's own paragraph only; don't touch the `local-files`-driver stop wording for any of the three, which is unrelated to this gap (that stop fires regardless of `gh` presence, on a different axis entirely).
