# 1316: Health-sweep/capture filing should check recently-merged commits for the described symptom before filing

Surface: infra

## Current State

#1068 (filed 2026-08-20T15:29:59Z) described `materialize.js`'s `--run-dir` anchoring check and the pipeline-shadow guard refusing a genuinely-new worktree-relative run-dir write. Commit `73478c8b` (refs #959) fixed exactly this the following day (2026-08-21T06:55), with pinning tests covering the identical scenario. #1068's title and body are near-duplicates of #959's own description of the bug it fixed. Nothing caught the overlap before #1068 reached `/flow`'s build queue as `ready` — it was discovered only during that build, after materialization, worktree creation, and a draft PR were already spent on it.

Filed by the `reflect` skill via `specShapedBody` during record #1068's build (staged during multi-spec run `2026-08-22T081916`, resolved via the batch Review Console). This is a process-improvement request to health-sweep and `/claude-tweaks:capture` filing generally, not a fix to #1068 or #959 themselves (both already resolved).

## Deliverables

- Before a health-sweep or `/claude-tweaks:capture` filing lands as a new record, check whether a commit merged in the last N days (e.g. 14) already touches the same key files / addresses the same described symptom — via commit-message grep against the finding's own key terms, or a semantic-similarity pass against recently-closed issues referencing those files.
- If a strong match is found, surface it at filing time (attach as a comment/note on the new record, or hold it for human triage) instead of silently letting it reach `ready`.

## Acceptance Criteria

1. A finding whose described symptom was fixed by a commit within the lookback window is flagged before or at filing time, not discovered mid-build.
2. False-positive rate stays low enough that this doesn't become filing-time noise — a near-miss/heuristic match surfaces for human judgment, it doesn't block filing outright.

## Technical Approach

Two mechanisms are named as candidates, not mandated — either is acceptable as long as AC1/AC2 hold: (a) commit-message grep against the finding's own key terms/file paths over the lookback window's `git log`, or (b) a semantic-similarity pass against recently-closed issues that reference the same files. The check runs at filing time, in whichever of health-sweep's four sweep skills and `/claude-tweaks:capture` currently composes and writes a new record's body — a shared helper is likely the right shape given multiple callers, but that's an implementation choice for the build, not asserted here. On a strong match, attach a comment/note to the new record rather than blocking filing outright, matching AC2's noise-tolerance requirement.

### Key Files

- `plugin/skills/capture/SKILL.md` — the `/claude-tweaks:capture` filing path this check needs to run inside
- The four health-sweep skills (see `plugin/skills/_shared/` and `docs/plugin-structure.md` for the current roster) — each sweep's own filing step needs the same check
- `plugin/bin/lib/issues/` — likely home for a shared "recent-commit/closed-issue overlap" helper, if one is introduced

## Gotchas

- Scope this to a shared helper if multiple filing call sites need the identical check — duplicating the grep/similarity logic per sweep skill would drift.
- The lookback window (N days) and match-strength threshold are tuning knobs with no measured baseline yet — start conservative (fewer false positives) and adjust from real filing-time signal, per AC2.
- This is itself a health-sweep/reflect-filed record, dogfooding the exact gap it describes — the shaping session found no other candidate duplicate for this record's own topic.
