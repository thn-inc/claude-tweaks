# 2080: parseLedger silently counts an unrecognized Status value as terminal

Surface: backend

## Overview

`plugin/bin/lib/wrap-up/pack.js`'s `parseLedger` (~line 269) classifies a ledger row as blocking via `status === 'open'` alone — any other value (a typo, a synonym, an out-of-enum write) falls through as silently terminal. `_shared/ledger-format.md` already documents this exact gap in prose (line 49: "Writing an out-of-enum value does not fail loudly — `parseLedger`... counts only `open` as blocking, so anything it does not recognize is silently treated as terminal"), but nothing mechanically detects it. Seven out-of-enum rows already exist in two historical ledger files.

**Design resolved before shaping (the record's own Open Question):** traced `pack.ledger`'s consumers directly — it is `ledgerProbe`'s return value verbatim, and `wrap-up/SKILL.md` line 208 already gates the Resolve Gate on `pack.ledger.total > 0`. The record's three candidate surfaces aren't real alternatives: a fact-pack `unrecognizedStatus` count is the necessary data-plumbing fix (nothing else can exist without it first), and a warning line in the nothing-left-behind gate is simply how that count reaches a human — both are needed together. A repo-wide `harness-health`/`docs-health` mechanical check (the third candidate) is disproportionate here: it would exist to catch *future* drift across the whole historical ledger corpus, but the actual violation set is fixed and small (7 rows, 2 files) — cheaper and more honest to correct them directly as a deliverable than to stand up new scanning infrastructure for a closed, finite backlog.

**Complexity:** Low
**Estimated tasks:** 2-3

## Non-Goals

- A new `harness-health`/`docs-health` mechanical check sweeping the live ledger corpus repo-wide — rejected above as disproportionate; the fact-pack fix covers every future wrap-up run's own ledger, and the 7 known historical violations are fixed directly instead.
- Any change to the status enum itself (`_shared/ledger-format.md`'s five terminal values plus `open`) — this spec detects and reports drift from the existing enum, it does not expand it.

## Acceptance Criteria

1. `parseLedger` (and `ledgerProbe`) return a distinguishable `unrecognized` count (and the set of distinct unrecognized values) for rows whose status is neither `open` nor a terminal enum value — verified by a fixture ledger containing an out-of-enum row.
2. A fixture wrap-up run whose ledger carries an out-of-enum status row renders the new warning line; a ledger with zero out-of-enum rows renders no such line.
3. `pack.ledger.total`/`.open`/`.byPhase` shapes are unchanged for existing consumers (`wrap-up/SKILL.md`'s `total > 0` gate condition) — no regression to the existing gate-open condition.
4. `grep -c "| staged |\|| resolved |"` (or equivalent) over the two named ledger files returns 0 after the fix; the corrected rows retain their original Item/Resolution text unchanged, only the Status cell is corrected.
5. `_shared/ledger-format.md` line 49's prose no longer claims the unrecognized case is silently treated as terminal.
6. `npm test` passes in full, no regressions.

## Technical Approach

Extend `parseLedger`'s existing per-row loop with an `else` branch on the same `status` check already there — no new parsing pass, no new file reads. The warning line is additive prose in an already-existing gate section, not a new gate or a new blocking condition (an out-of-enum status was never `open`, so it was never blocking before, and this spec doesn't change that — it only makes the previously-invisible case visible). The 7 historical corrections are plain text edits to already-known row/file locations, requiring no further lookup.

## Gotchas

- Do not conflate "unrecognized" with "blocking" — an out-of-enum row must remain non-blocking (it was never `open`), only newly *visible* as a data-quality warning. Changing it to block the gate would be a behavior change well beyond this record's scope.
- The 7 row corrections only touch the Status cell — do not alter Item/Resolution text, which is historical record of what actually happened and is independently valuable.
- `docs/` is maintainer-side, not part of the shipped plugin payload (per this repo's CLAUDE.md Structure section) — the 7-row correction has no effect on the plugin's runtime behavior; it's data hygiene only. Do not let this fact become a reason to skip the mechanical fix in `pack.js`/`SKILL.md`, which *does* ship and *does* affect every future wrap-up run's own ledger.

## Current State

`plugin/bin/lib/wrap-up/pack.js`'s `parseLedger` (~line 269) classifies a ledger row as blocking
via `status === 'open'` alone:

```js
const status = (cells[3] || '').toLowerCase();
byPhase[phase] = byPhase[phase] || { open: 0, total: 0 };
byPhase[phase].total += 1;
if (status === 'open') { open += 1; byPhase[phase].open += 1; }
```

Any other cell value — including a typo, a synonym, or an out-of-enum write — falls through as
terminal with no signal. This is the exact failure shape `parse-signal-discipline` exists to
prevent: the unparseable/unrecognized case must be distinguishable from the legitimately-resolved
case, not silently folded into it.

|---|---|---|

| `deferred` | 16 | yes |

Seven out-of-enum writes already exist, across `2026-09-05-record-1634-ledger.md` and
`2026-09-05-spec-1921-...-ledger.md`; an eighth was proposed (and caught at review) in record
#1971's own materialized spec. None were flagged by any mechanism — `parseLedger` treated them all
as non-blocking.

## Open Question

Where should the unrecognized-status signal surface, and what does it owe under

check against the live ledger corpus. This needs a design call on where the count surfaces before
it can be scoped as agent-sized work — not guessed at inside a curation dispatch.
