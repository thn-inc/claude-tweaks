# Spec: #2346 — Plugin commit call sites have no bounded git index.lock retry

Surface: infra

## Current State

`bin/lib/reconcile/archive-merged.js`, `bin/lib/release/run.js`, and `bin/release-local.js`
each run `git commit` via `execFileSync`-shaped runners with no retry. A transient
`index.lock` collision (a sibling agent's git call, or a PostToolUse hook, in the same
checkout) surfaces as a hard failure of a reconcile or release step. The precedent shape
already exists: `bin/lib/feedback/file-feedback.js`'s `withTransientRetry(runner, { waitMs,
maxRetries, sleep })` wraps `gh` calls the same way, with injectable `sleep` for tests.

## Deliverables

- New `plugin/bin/lib/git-retry.js` exporting `withIndexLockRetry(gitRunner, { attempts,
  waitMs, sleep })`: retries ONLY on a stderr signature naming `index.lock`
  (`Unable to create ... index.lock` / `another git process seems to be running`), bounded
  (~15 attempts at 2s), injectable `sleep`, never unlinks a lock file.
- Route the three named commit call sites through it.
- Cite the new rule once from skill prose that instructs a hand-written `git commit` (grep
  for a documented procedure calling `git commit` directly).

## Acceptance Criteria

1. `withIndexLockRetry` retries on an `index.lock` stderr signature and does NOT retry on any
   other git failure (fake runner: fails twice on index.lock then succeeds -> one commit, no
   error; fails once on unrelated error -> fails on first attempt, no retry).
2. Never unlinks a lock file -- asserted directly.
3. Bounded: always-failing fake runner exits after the configured attempt count with the
   original git error; injected `sleep` makes the test instant.
4. Each of the three named commit call sites routes through the helper (grep proves no direct
   ['commit', ...] call bypasses it), and `npm test` passes.

## Non-Goals

- Replacing `file-lock.js`'s directory mutex (different resource).
- Any change to what the commits contain or when they run.
