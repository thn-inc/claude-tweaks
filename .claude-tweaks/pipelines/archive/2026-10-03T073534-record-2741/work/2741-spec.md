# 2741: Add a harness cost-efficiency lens to claude-tweaks

Surface: infra

## Current State

A HarnessTax study found harness choice alone can move inference cost up to 5x for the same model on the same task, with no comparable change in success rate. A minimal four-tool harness (read/write/edit/bash) reached the study's cost-success Pareto frontier on two benchmarks; richer harnesses added cost without matching accuracy gains. Models did not consistently perform best inside their own vendor's harness (an alternative harness won 9 of 12 comparisons across Anthropic and OpenAI models).

**Verified during shaping:** no existing claude-tweaks mechanism already covers this — grepped `harness-health/`, `code-health/`, and `review/` skill directories for "footprint"/"overhead"/"per-invocation load" and found nothing; this is a genuinely new capability, not a duplicate of an existing lens.

**Evidence caveat, worth noting for the build:** the cited study measures cost/harness effects on *other* harnesses generically, not claude-tweaks' own skills specifically — no internal measurement yet exists showing any particular claude-tweaks skill or subagent definition is actually disproportionately overhead-heavy. This record's own external-evidence basis justifies building a measurement tool; it does not yet establish that any specific finding it would surface is real. The lens's own first real output (run against this repo's own skills) is what turns the general external claim into project-specific evidence — treat the initial run's findings as hypotheses to verify, not confirmed problems.

## Deliverables

- A claude-tweaks lens or skill that estimates a session's context/tool-definition overhead versus a minimal baseline, so bloated skill or subagent definitions are visible.
- A policy row usable by `/code-health` or `/review` flagging skills whose tool definitions or context load are disproportionate to the task.

## Acceptance Criteria

- Running the lens against an existing claude-tweaks skill reports its estimated per-call overhead versus a minimal-harness baseline.
- The check integrates as a step in `/review` or `/harness-health` without requiring a new standalone command.
- `npm test` passes.

## Release Note

Added a check that flags skills and subagents whose definitions cost more context than they need.

## Technical Approach

Define "minimal baseline" concretely before implementing the estimator — the cited study's four-tool (read/write/edit/bash) reference point is a reasonable starting definition, but claude-tweaks' own skills routinely need more than those four (Skill, Agent, AskUserQuestion, etc.), so the baseline needs a claude-tweaks-specific interpretation rather than a literal four-tool floor. Measure what's actually knowable statically — a skill's own file size, its tool-definition count/verbosity, and its `_shared/*.md` citation depth (files it pulls in) — rather than attempting to measure live per-call token cost, which varies by conversation and isn't reproducible from the skill file alone. Decide the integration point (`/review` vs `/harness-health`) based on which existing skill's own scan cadence and audience best fits a "is this skill bloated" finding — `/harness-health`'s own charter (skill/rule/template drift) is the closer match on its face, but confirm against that skill's actual scope before assuming.

### Key Files

- `plugin/skills/harness-health/` — the more likely integration point (skill/rule drift is its existing charter); confirm scope fit here first
- `plugin/skills/review/` — the alternative integration point if harness-health's scope doesn't fit
- `plugin/skills/code-health/` — checked during shaping and ruled out as already covering this (no existing footprint/overhead mechanism found)

## Gotchas

- Don't treat the cited study's specific numbers (5x cost swing, 9-of-12 comparison) as claims about claude-tweaks itself — they're motivation from a third-party study of different harnesses, not a measurement of this codebase. The build's own first real findings are what actually validate (or don't) whether this repo has the problem the study describes elsewhere.
- The study source has "no stable article URL" (per the original filer) — cite it as motivating context only, never as a verifiable reference a reader could follow up on directly.
