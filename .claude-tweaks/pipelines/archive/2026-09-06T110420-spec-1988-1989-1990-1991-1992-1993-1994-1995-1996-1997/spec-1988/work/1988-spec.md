# 1988: compose-context.js: per-run skill-context composer CLI — `when:` markers, condition resolution from the run, fallback contract

Surface: backend

## Overview

Build the foundational primitive every later unit in this decomposition depends on: `plugin/bin/compose-context.js`, a new CLI over a new module `plugin/bin/lib/compose-context/` (flat sibling directory, per `docs/plugin-structure.md`'s module convention) that resolves a run's already-known condition set, strips the branches of `<!-- when: key=value --> … <!-- /when -->` marker pairs the run didn't take, concatenates the named source files in argv order, and writes one bundle a skill step reads once instead of reading every source file separately. This is Phase 1 of the parent design (#1987) and the vertical slice everything else in this decomposition builds on.

**Complexity:** Medium
**Estimated tasks:** 6

- Fencing any existing shared-contract file with `when:` markers — that migration work is Phase 2 (separate sub-issues of #1987), not this record. This record ships the composer with zero production markers in place.

- Changing the existing per-file 40 KB ceiling test's pass/fail behavior — untouched here.
- Touching any dispatch or review subagent prompt template — that is Phase 3 work.

## Deliverables

- [ ] `plugin/bin/compose-context.js` — CLI entry point: `node bin/compose-context.js --run <run-dir> --step <name> <source-file>...`, following `build-review-context.js`'s `run(argv, deps)` injectable-runner seam and `require.main` guard shape.
- [ ] `plugin/bin/lib/compose-context/compose.js` — marker parse/strip/concatenate logic, plus two pure exported functions: `stripMarkers(text)` (removes marker lines only, keeps every branch) and `compose(sources, conditions)` (the full strip-and-concatenate given resolved conditions) — both exported for U3 and later phases to reuse directly.
- [ ] `plugin/bin/lib/compose-context/resolve-conditions.js` — resolves the six-key condition set from the run: `integration-model` via `resolveIntegrationModel(repoRoot)`; `mode` from `{run}/config.yml`'s `mode:` line (present-but-missing-`mode:`-line resolves `unresolved`, same as no `config.yml` at all; a present line whose value is outside the four-value vocabulary is a malformed marker input, not a resolver concern — the resolver only ever emits a value from the vocabulary or `unresolved`); `attendance` (`headless` when resolved `autonomy` is `unattended`, else `attended`; `unresolved` whenever the underlying `autonomy` resolution itself is `unresolved` — it never independently defaults to `attended`) via `resolvePolicyKeys(['autonomy'], {policyRaw, runConfigRaw})`; `transport` (`gh` or `mcp`) via `command -v gh` semantics (an `execFileSync('gh', ['--version'])` success check — this is the module's one and only shell-out; it takes an injectable `deps.execFileSync` the same way every other CLI in this codebase injects its runner seam, per the `gh-api-module-pattern` skill, precisely so this one check is fakeable in tests); `worktree-policy` (`always`/`optional`) via `resolvePolicyKeys(['worktree-always'], {policyRaw, runConfigRaw})` — the same function and precedence `attendance` uses, not a bespoke read; `work-backend` (`github-issues`/`local-files`) from the CLAUDE.md `work-backend:` line, read from `$RUN_ROOT`'s CLAUDE.md (the main checkout, never the run's own cwd — the same `$RUN_ROOT`-vs-cwd-worktree distinction `[IL-127]` already established elsewhere in this codebase, so a worktree-run session doesn't silently read the wrong file).
- [ ] `plugin/bin/lib/compose-context/index.js` — module entrypoint tying the above together for the CLI.
- [ ] Marker grammar: `<!-- when: key=value -->` … `<!-- /when -->` on their own lines; exactly one `key=value` pair per marker; nesting depth of at most 1 — an inner marker's branch is combined with its enclosing outer marker by AND semantics (the inner block is kept only when BOTH its own condition matches AND the outer block itself is being kept; an inner block inside an outer block being stripped is stripped along with it, and its own validity is still checked — a malformed inner marker is still a malformed-marker error even inside a branch this run doesn't take, since ALL markers in a source are validated before any stripping occurs, regardless of which branch the run ends up keeping); a marker pair must open and close inside the same source file. The six-key/value vocabulary itself (the closed list in Data / API Surface below) is validated inside this module (`compose.js`/`resolve-conditions.js`), not injected by the caller — a caller never supplies its own key list.
- [ ] Unresolvable-key handling: when a key cannot be resolved (no `config.yml` on a standalone run, no policy file present), keep BOTH branches for that key and list the key under `unresolved` in the header and the JSON line — never drop a branch.
- [ ] Output contract: writes `{run}/context/{step}.md` beginning with one line `<!-- resolved: integration-model=... mode=... attendance=... transport=... worktree-policy=... work-backend=... -->` naming every key's resolved value or `unresolved`, in that fixed canonical order (the same order as the six-key list in Data / API Surface below — not argv order, not discovery order), followed by the sources concatenated in argv order with untaken blocks removed and marker lines stripped.
- [ ] stdout contract: exactly one JSON line `{path, bytes, sources, unresolved}` per successful run.
- [ ] Exit-code vocabulary: `0` success; `2` malformed invocation (bad/missing flags — no source file or line to name, so stderr is just the usage message) OR malformed marker (unclosed marker, unknown key, unknown value, nesting depth > 1, a close-without-open — these DO name the offending file and line on stderr) — on either `2` case, write nothing to `{run}/context/{step}.md`, and leave any bundle already present at that path from a prior successful call untouched (never partially overwritten, never deleted — a failing call is a no-op on disk); `1` filesystem failure (cannot read a source, cannot write the output path).
- [ ] Regenerate the bundle on every call — never cache it, since conditions can change mid-run (e.g., the Manifesto is re-answered) and a stale bundle would be exactly the kind of silent shadow copy `_shared/pipeline-run-dir.md` already warns against.
- [ ] `docs/plugin-structure.md` Commands block gains a one-line entry for this CLI, matching the existing `build-review-context.js`/`log-decision.js` entry format (usage line, one-sentence purpose, exit codes, module path, test path).
- [ ] `docs/skill-authoring.md` gains a "Conditional blocks and the composer" section immediately after the `**Size:**` paragraph (line 21 today): marker syntax, the six-key vocabulary, the call-site form (`node "${CLAUDE_PLUGIN_ROOT}/bin/compose-context.js" --run "$PIPELINE_RUN_DIR" --step {step} {files}` then "read `{run}/context/{step}.md`"), the mandatory fallback sentence every call site must carry ("if the compose command is unavailable or exits non-zero, read the named source files directly"), the rule that a fenced block never holds the only copy of a heading/Step label/anchor another file cites, and "composition over fragmentation" as the standing response to future ceiling pressure.

## Technical Approach

### Data / API Surface

Marker grammar (line-anchored, one marker per line):
```
<!-- when: {key}={value} -->
… branch content …
<!-- /when -->
```
Six condition keys, in this fixed canonical order (used identically in the `resolved:` header and anywhere else the key set is enumerated) and their vocabularies: `integration-model` (`pr-first`|`local-merge`), `mode` (`auto`|`confirm`|`interactive`|`hybrid`), `attendance` (`headless`|`attended`), `transport` (`gh`|`mcp`), `worktree-policy` (`always`|`optional`), `work-backend` (`github-issues`|`local-files`). CLI invocation: `node bin/compose-context.js --run <run-dir> --step <name> <source-file>...`. stdout: one JSON line, `{path: string, bytes: number, sources: string[], unresolved: string[]}`. `compose(sources, conditions)`'s `sources` parameter is an array of `{path: string, content: string}` objects (already-read file content, not bare paths the function reads itself) — the CLI reads each source file and passes its content in; `stripMarkers(text)` takes a single content string. This exact shape is what U3's `context-cost.js` measurement work imports and calls directly.

## Gotchas

- Follow `build-review-context.js`'s and `log-decision.js`'s `run(argv, deps)` injectable-runner seam and exit-code vocabulary exactly — this is a documented convention (`gh-api-module-pattern` skill), not a per-CLI choice.
- Read `plugin/bin/lib/run-dir-guard.js` before writing any new anchoring logic — the guard already exists and this CLI must reuse it rather than reimplement it.
- A malformed marker must write nothing to the output path and name the offending file and line on stderr — a partial write on a `2` exit is worse than no output, since a caller might otherwise read a truncated bundle as complete.
- Never cache the composed bundle across calls in the same run — conditions can change mid-run (e.g., the Pipeline Config Manifesto gets re-answered), and a cached bundle would silently shadow the current resolved state, the same class of bug `_shared/pipeline-run-dir.md` already documents for a different mechanism.
- `stripMarkers(text)` and `compose(sources, conditions)` must be genuinely reusable pure functions with no CLI-only state, since U3's `context-cost.js` measurement work and later-phase call sites both import them directly rather than shelling out to the CLI.
- `resolve-conditions.js`'s `transport` check is this module's one and only `execFileSync` call (`gh --version`) — inject it via `deps` exactly like every other CLI in this codebase, so it's fakeable in tests. `compose.js` and `index.js` genuinely shell out to nothing. Either way, the whole module still follows the CLI wrapper contract's `run(argv, deps)` seam and exit-code vocabulary, per that skill's explicit note that the contract covers run-directory writers like `log-decision.js` and `stage-item.js` on the same basis, regardless of whether a given file inside the module happens to shell out.
- This record's own dependency graph has no blockers (it's Phase 1's first record) — nothing here waits on any other sub-issue in this decomposition. Every other sub-issue in this batch (#1989-#1997) is likewise still open/unbuilt at spec time: this record's own Deliverables are the first real implementation of the composer, not a consumer of one that already exists.

## Build deviations (architecture alignment, /build Common Step 4.5)

Two deviations from the Deliverables above shipped, both classified **Beneficial** (an improvement on the spec's own intent) and applied as-built; the spec is updated here rather than the code reverted:

1. **`integration-model` never uses forge detection.** The Deliverables name `resolveIntegrationModel(repoRoot)`; as built, `resolve-conditions.js` resolves `integration-model` only from the run's `config.yml` pin or `policy.yml` (via `resolvePolicyKeys`) and reports `unresolved` otherwise. `policy-schema.js`'s `detectIntegrationModel` fails open to `local-merge` on any error — offline, expired token, no `gh` — indistinguishably from a real answer, which would silently drop every `pr-first` branch (the exact "drop a branch on a guess" this record forbids), and it spawns `git remote get-url` plus a live `gh repo view` per call (~2s) against a bundle regenerated every step. Every `/flow` run pins the value at the Manifesto, and `_shared/integration-model.md`'s run-scoped stability rule says in-run reads take the pin. The `gh --version` transport probe is therefore genuinely the module's only shell-out.
2. **Fenced code blocks are literal to the parser.** The marker grammar above is line-anchored; as built, lines inside a fenced code block (``` or ~~~, closed only by a fence of the same character and at least the opener's length, per CommonMark) are text — never markers, never validated, never stripped. Without this, a `_shared/*.md` file that documents the grammar either mangled its own example or refused to compose.

Two further rulings recorded at plan time and carried into the build: `stripMarkers` validates the grammar and throws `MarkerError` on malformed input (one grammar, one validator — #1990's measurement caller wraps it); the CLI takes `bin/lib/run-dir-guard.js`'s anchored-or-outside run-dir rule with exit 2 and is registered as a fourth boundary shape in `_shared/pipeline-run-dir.md`.
