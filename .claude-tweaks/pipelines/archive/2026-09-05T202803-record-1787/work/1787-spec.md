# 1787: wrap-up engine's journey candidate-matching drops CRLF-encoded journeys

# Ledger item 2 — staged backlog proposal

**Category:** bug

Origin: /claude-tweaks:wrap-up run for record #1222 (Phase 2 curation, Journeys row), 2026-09-02.
Defer-reason: genuinely-larger — pre-existing, unrelated to #1222's own diff, and a proper fix needs a new regression test in a file with no existing coverage of this function.

## Current State

`parseJourneyFilesList` in `plugin/bin/wrap-up-engine.js` (used by the `plan` CLI command's
`buildJourneyFrontmatter`, which feeds `engine-plan.js`'s `resolveFrontmatterOverlapScope` for the
Journeys curation row) splits journey frontmatter on `\n` only. A journey file with CRLF (`\r\n`)
line endings — `docs/journeys/verify-wrap-ups-closure-checklist-900.md` is a live example in this
repo — leaves each `- path` line in the parsed frontmatter array carrying a trailing `\r`. The
match regex `/^\s*-\s+(.+)$/` cannot consume it: JavaScript regex `.` excludes `\r` as a line
terminator, and `$` (without the `m` flag) requires the true end of the string, not "before a
trailing `\r`". The regex match fails entirely on the first `- path` line, the loop's `if (!m)
break;` fires immediately, and the whole `files:` list silently parses to `[]`.

Net effect: any CRLF-encoded journey drops out of `/claude-tweaks:wrap-up` Phase 2's Journeys-row
candidate scan (`journey-curation.md`'s J1 check) — the wrap-up run proceeds as if that journey has
zero overlap with the current diff, even when its own `files:` frontmatter names files the diff
actually touched. Reproduced live: isolating `parseJourneyFilesList` + `gatherFacts` against
`docs/journeys/verify-wrap-ups-closure-checklist-900.md` (frontmatter lists
`plugin/bin/lib/wrap-up/engine-verify.js` and `plugin/bin/wrap-up-engine.js`, both changed by
record #1222) returns `parsed files: []` and `overlap: false`, even though
`changed.has('plugin/bin/lib/wrap-up/engine-verify.js')` is `true`.

No functional harm was caused in this specific run — the journey text was independently confirmed
accurate by direct read during the same wrap-up pass — but the candidate computation itself is
silently wrong on any CRLF checkout, which is common on Windows without a normalizing
`.gitattributes` entry for `docs/journeys/*.md`.

## Deliverables

- [ ] Make `parseJourneyFilesList` (`plugin/bin/wrap-up-engine.js`) CRLF-tolerant — e.g. normalize
      the content (`content.replace(/\r\n/g, '\n')`, or split on `/\r\n|\n/`) before the existing
      line-based parse, rather than reworking the match regex line by line.
- [ ] Add a regression test pinning CRLF frontmatter parsing for this function (no existing test
      file covers it today — check `tests/wrap-up-engine-run-dir-anchoring.test.js` and
      `tests/bin-lib/wrap-up/` for the right home, or add a new focused test file).
- [ ] Consider whether other frontmatter/markdown parsers in `plugin/bin/lib/wrap-up/` and
      `plugin/bin/wrap-up-engine.js` share the same LF-only assumption (e.g. the Skills/Docs rows'
      own file-reading paths) — scope this only if a quick grep turns up an obviously shared helper;
      otherwise file a separate record rather than widening this one.

## Acceptance Criteria

1. A journey file with CRLF line endings and a `files:` frontmatter list correctly contributes its
   listed files to the Journeys row's candidate-overlap computation (verified by the new
   regression test).
2. Existing LF-encoded journeys continue to parse identically (no regression).
3. `npm test` stays fully green.
