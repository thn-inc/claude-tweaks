# 1710: Hoist release-claim.js's run-dir anchoring check before the destructive write (parity with repair-claim.js)

Surface: infra

## Current State

`plugin/bin/repair-claim.js` used to evaluate `resolveTarget` (the run-dir anchoring check that warns "decisions.md will not be written") only *after* the destructive claim write; a fix wave (spec 1608) hoisted it before the write (commit 387b53f4e), so line 116 of `repair-claim.js` now resolves the target and emits its stderr warning before the repair operation runs. `plugin/bin/release-claim.js` has the identical pre-existing ordering bug: `release.releaseClaim(...)` runs at line 130, and `resolveTarget` runs only afterward at line 139, so an operator with an unanchored or missing `--run` dir sees the no-log warning only *after* the release has already tombstoned the claims-registry blob. This was out of #1608's scope, flagged by that fix wave's implementer, and left untouched.

## Deliverables

- [ ] `plugin/bin/release-claim.js`: compute `resolveTarget` and emit the `not-anchored`/`missing` stderr warnings before the `release.releaseClaim(...)` call, keeping `formatEntry`/`appendEntry` after (they need the outcome) — the same pure hoist commit 387b53f4e applied to `repair-claim.js`.
- [ ] Extend `tests/bin-lib/release-claim/cli.test.js` only if any existing assertion pins warning ordering; exit-code semantics and the logging-is-bookkeeping posture stay byte-identical.

## Acceptance Criteria

- [ ] With a missing or unanchored `--run` dir, the stderr warning is emitted before any write reaches the claims registry (observable in the deps-injected test by call ordering).
- [ ] `node --test tests/bin-lib/release-claim/*.test.js` passes unchanged in count.

## Technical Approach

Move the existing `try { target = resolveTarget(...) } catch { target = { ok: false, reason: 'missing' } }` block in `plugin/bin/release-claim.js` (currently after the `release.releaseClaim(...)` call) to run before it — a pure reordering, no new logic, mirroring the exact hoist commit 387b53f4e already applied to the equivalent block in `plugin/bin/repair-claim.js`. `formatEntry`/`appendEntry` stay after the destructive call, since they need its outcome (`r`) to compose the log entry text. No change to `resolveTarget`, `release.releaseClaim`, `formatEntry`, or `appendEntry` themselves — only the call order in the CLI's own flow.

### Key Files

- `plugin/bin/release-claim.js` — the CLI whose `resolveTarget`/`release.releaseClaim(...)` call order needs hoisting (current order: release call at line ~130, `resolveTarget` at line ~139)
- `plugin/bin/repair-claim.js` — the sibling file already fixed (commit 387b53f4e) with `resolveTarget` at line ~116, before its own destructive call; the reference pattern to mirror
- `tests/bin-lib/release-claim/cli.test.js` — extend only if an existing assertion pins warning ordering

## Gotchas

- This is a pure call-order hoist, not a logic change — `resolveTarget`, `release.releaseClaim`, `formatEntry`, and `appendEntry` themselves stay untouched; only their sequencing in the CLI's own flow changes, mirroring the already-landed precedent exactly.
