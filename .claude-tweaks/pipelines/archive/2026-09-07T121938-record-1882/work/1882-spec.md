# 1882: splitFrontmatterFence silently returns null for every file on a CRLF (core.autocrlf=true) checkout — breaks frontmatter parsing repo-wide, not just one test

## Current State

While independently verifying #1806's test results (raw artifact re-derivation, not trusting the prior call's `decisions.md` claim), I found that `tests/bin-lib/skill-audit/context-cost.test.js`'s "measureDescriptions finds every shipped skill" test fails on this Windows checkout — not just for one file (as #1880 already covers for the byte-ceiling check), but for **all 35 shipped skills at once**: every single one measures `chars: 0, description: null`.

Root cause, distinct from and more severe than #1880's byte-inflation issue: `plugin/bin/lib/health-core/frontmatter-list.js`'s `splitFrontmatterFence(content)` does:

```js
const lines = content.split('\n');
if (lines[0] !== '---') return null;
const closeIdx = lines.indexOf('---', 1);
```

`fs.readFileSync(path, 'utf8')` performs no newline translation, so on a checkout with `core.autocrlf=true` (this repo's actual Windows-checkout setting — confirmed via `git config core.autocrlf` and `git ls-files --eol`, which shows `i/lf w/crlf` for the files checked), every line in `content` ends with a literal `\r` character. Splitting only on `'\n'` leaves `lines[0]` as `'---\r'`, which never strictly-equals `'---'` — so `splitFrontmatterFence` returns `null` for **every** frontmatter-fenced file on such a checkout, regardless of content.

This is a different and broader failure mode than #1880 (which is about a byte-count threshold shifting near a ceiling for one file). Here, the parser itself silently returns "no frontmatter" for every file, all the time, on any CRLF checkout. `frontmatter-list.js` is shared by six production call sites (not just this test):

- `plugin/bin/lib/skill-audit/context-cost.js` (`measureDescriptions`)
- `plugin/bin/lib/skill-audit/argument-hint.js`
- `plugin/bin/lib/journey-health/scope.js` (`files:` field)
- `plugin/bin/lib/harness-health/scope.js` (`paths:` field)
- `plugin/bin/lib/docs-health/freshness.js` (`files:` field)
- `plugin/bin/lib/issues/local-store.js` (record frontmatter — `work-backend: local-files`'s own record store)

Every one of these silently returns empty/no-match results (not an error) on a Windows `core.autocrlf=true` checkout, which is worse than a loud failure: `local-files`-backend record frontmatter parsing (via `local-store.js`) breaking silently on Windows is a correctness bug with no test currently pinning it directly (this repo runs `work-backend: github-issues`, so it wasn't caught here).

## Deliverables

- [ ] Fix `splitFrontmatterFence` (and any other line-based parsing in this module) to normalize line endings before splitting — e.g. `content.split(/\r?\n/)` — so behavior is identical regardless of the checkout's `core.autocrlf` setting.
- [ ] Audit the six listed call sites for the same raw `\n`-only split assumption elsewhere in their own logic (not just via this shared helper).
- [ ] Add a regression test constructing CRLF-content input directly (not relying on `core.autocrlf` being set, which is checkout-configuration-dependent and not exercised by CI's own checkout) — the existing corpus-scan tests only caught this because they happen to run in a checkout where it fires.

## Acceptance Criteria

1. `splitFrontmatterFence` and `parseFrontmatterListField` return identical results for byte-identical *content* regardless of whether that content uses LF or CRLF line endings.
2. `tests/bin-lib/skill-audit/context-cost.test.js`'s "measureDescriptions finds every shipped skill" test passes on a `core.autocrlf=true` checkout.
3. A new unit test in `tests/bin-lib/health-core/` (or wherever `frontmatter-list.js`'s existing tests live) constructs a CRLF fixture directly and asserts `splitFrontmatterFence` parses it the same as its LF equivalent.
