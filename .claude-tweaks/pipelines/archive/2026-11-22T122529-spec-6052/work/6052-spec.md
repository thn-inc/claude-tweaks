# 6052: Store a reviewed plan on refs/claude-tweaks/plans/{n} with a Plan: body line and a staleness verdict

Surface: infra
Risk-flags: public-contract

## Overview

A plan written at specify time has to live somewhere between specify and build. Plans run 17 to 91 KB, over the 65,536-character issue body limit, and a branch or PR would trip queue-pull's open-PR exclusion. The design keeps each plan on a hidden git ref, `refs/claude-tweaks/plans/{n}`, names it from the record with a `Plan:` body line, and lets the build ask one CLI whether the plan is still valid.

This record builds that store: the writer, the reader, the body-line grammar, the spec hash and the staleness verdict. Specify (writer) and build (reader) call it in later records.

**Complexity:** Medium
**Estimated tasks:** 6-8

## Non-Goals

- Calling it from specify or build.
- Deleting refs of closed records (#6055).

## Current State

- Plans are written by `/superpowers:writing-plans` under `docs/superpowers/plans/` inside the build's worktree and land on main with the PR.
- `plugin/bin/lib/plan-audit/` parses a plan's Files sections (Check A); reuse that parse for the staleness check.
- `plugin/bin/lib/issues/record.js` holds body-line parsers (for example the `Risk-flags:` reader in `record-risk-flags.js`).
- `.claude/skills/gh-api-module-pattern` describes the injectable runner seam and CLI wrapper contract every `plugin/bin` CLI follows.

## Deliverables

1. **CLI** `plugin/bin/plan-store.js` (name the builder's call), three verbs:
   - `write --record N --plan-file F --base SHA --spec-file S`: create one commit whose parent is `SHA` and whose only change adds `F` at `docs/superpowers/plans/YYYY-MM-DD-{feature}-{n}.md`; point `refs/claude-tweaks/plans/{n}` at it; push it to `origin` (no push under `work-backend: local-files`); print `{ref, commit, specHash, line}` where `line` is the `Plan:` body line.
   - `read --record N --commit SHA --out DIR`: fetch the ref, check it names `SHA`, write the plan file into `DIR`.
   - `check --line L --spec-file S --base SHA [--repo-root R]`: print a verdict `{valid, failed}` where `failed` names the first failing check of: ref fetches and names the commit; hash matches; no file the plan names changed between the plan commit's parent and `SHA`.
2. **Body line** `Plan: refs/claude-tweaks/plans/{n} {plan-commit-sha} spec-sha256:{hash}`, one parser and one composer in `plugin/bin/lib/issues/`.
3. **Spec hash**: sha256 over the `##` sections from `## Overview` through `## Planning Decisions` in body order (through the last `##` section when `## Planning Decisions` is absent; sections after it, such as `## Original request`, are not covered). Excluded: the preamble metadata lines (`Surface:`, `Design-intent:`, `Ui-stack:`, `Visual-reference:`, `Parent:`, `Risk-flags:`, `Risk-flags-unconfirmed:`, `Risk-flags-added-by-tripwire:`, `Acceptance-target:`, `**Related:**`, `Blocked by`), the `Plan:` line and the `work-fingerprint` marker lines. Normalization: CRLF to LF, trailing whitespace stripped per line, one final newline.
4. **No-ref fallback**: when the ref cannot be created or pushed, `write` exits with a distinct code and prints why, so the caller writes no `Plan:` line.
5. Tests under `tests/bin-lib/plan-store/`.
6. **Update semantics.** `write` on an existing ref force-updates it with a lease on the observed remote sha, so a re-specify after the base moved replaces the plan; two racing writers lose cleanly (the loser exits with the no-ref code).
7. **Names and paths.** The plan file keeps the basename of `--plan-file` (the caller composes `YYYY-MM-DD-{feature}-{n}.md`); `write` commits it at `docs/superpowers/plans/{basename}` and `read --out DIR` writes that same basename.
8. **Transport.** `read` and `check` fetch with the explicit refspec `refs/claude-tweaks/plans/{n}:refs/claude-tweaks/plans/{n}` (a default fetch does not carry the namespace). Under `work-backend: local-files` the ref stays local and `write` still prints the `Plan:` line; a reader in another clone gets `failed: ref`, by design.
9. **Exit codes and verdicts.** Follow `.claude/skills/gh-api-module-pattern`'s CLI wrapper vocabulary; the no-ref code is distinct, named in USAGE and pinned by a test. `check` prints `{valid, failed}` on stdout, exit 0 when valid and 1 when not. Anything it cannot determine (fetch error, unresolvable base) reads `valid: false`, never valid. `failed` is one of `ref`, `hash`, `files`, `base`.
10. **Files check.** The path set is the Modify and Test entries of the plan's Files sections (Check A's parse); Create entries are ignored. A path that is modified or deleted between the plan commit's parent and `SHA` counts as changed; a rename counts as a delete plus an add.

## Acceptance Criteria

1. `write` then `read` round-trips the plan file byte-for-byte in a temp repo with a bare remote.
2. The commit's parent is the given base and its tree differs from the base only by the plan file.
3. Settled at specify (agent call, fails toward re-plan): an empty named-path set reads `failed: files`, and a malformed `--line` exits 2 with the verdict `valid: false`, so the build re-plans in both cases.
   `check` reports `valid: true` for an unchanged pair; `failed: hash` after editing a covered section; still valid after editing `Risk-flags:` or `**Related:**`; `failed: files` after the base moves a file the plan names; `failed: ref` when the ref is missing or names another commit.
4. A push failure yields the no-ref exit code and no `Plan:` line printed.
5. `npm test` passes.
6. `write` on a record whose ref already exists replaces it with a newer plan; the old commit is no longer the ref's target.
7. On a push failure the local ref is removed (or restored to its prior value) and the remote ref is unchanged.
8. `check` reports `failed: base` for a `SHA` that does not resolve in the repo.

## Plan Review Clarifications

- Decided by the user at plan review: when `write` pushes and the push succeeds but the local `update-ref` then fails, the remote ref is the store — `write` exits 0, prints the `Plan:` line, and warns on stderr that the local ref was not updated (Reading B). Under Deliverable 4 ("when the ref cannot be created or pushed, `write` exits with a distinct code"), "created" means created on the remote when pushing; with no push (`work-backend: local-files`) the local ref is the store, so a local `update-ref` failure exits with the no-ref code. Reading not taken (A): exit no-ref and delete the just-pushed remote ref.

## Build Alignment

Beneficial deviations the build kept. Each one sharpens the spec's own intent:

- Deliverable 8's refspec is forced: `+refs/claude-tweaks/plans/{n}:refs/claude-tweaks/plans/{n}`. A real-git probe showed that an un-forced fetch is rejected as non-fast-forward once a re-specify replaces the plan (Deliverable 6). That would leave a reader on the stale commit.
- `check` runs its checks in the order ref → hash → base → files, and the first failure wins. The files check needs a resolved base, so `base` (Deliverable 9's fourth verdict) comes before it.
- Deliverable 10's files check counts any change to a named Modify or Test path between the plan commit's parent and `SHA` as changed: modified, deleted, added or type-changed, with renames counted as delete plus add. Counting more fails toward a re-plan, which is the direction Deliverable 9 favors.
- `write` refuses, with exit 1 and no `Plan:` line, when the base already holds the plan file byte-for-byte. The commit would change nothing, so AC2 could not hold and `read`/`check` would always reject it.
- One basename rule (`isPlanBasename` in `plugin/bin/lib/plan-store/ref.js`) governs both `write` and the read path: no `/`, no `\`, no NUL, no leading `-`, not `.` or `..`. Without it, a crafted plan commit's basename could write outside `read --out` on Windows.
- `plugin/bin/lib/issues/record-risk-flags.js` exports `RISK_FLAG_LINE_KEYS`, so the spec hash's `Risk-flags*` exclusions come from the one module that owns those lines. That module is outside the Key Files.
