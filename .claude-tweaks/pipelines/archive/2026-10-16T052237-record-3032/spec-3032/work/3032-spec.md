# 3032: claim-targets.js: an `alreadyOwned` (self-owned) claim never gets `bot:in-progress`, so a held claim reads as unclaimed

Surface: infra

## Current State

`bin/claim-targets.js` adds the `bot:in-progress` label in exactly one place: `ensureAndAddLabel` (`plugin/bin/lib/claim-targets/claim-targets.js:94`, called at `:457`), reached only after a fresh claim write is verified and pushed onto `claimedThisRun` (`:455`). The self-owned branch (`:348-351` — a `live`/`stale` blob whose `runId` equals `--run-id`) pushes the issue onto `alreadyOwned` and `continue`s without touching the label.

That leaves a held claim unlabeled when a first attempt's write lands but reports a transient failure: `stopOrSkip(..., 'transient', ..., 4, ...)` (`:286`) runs with `releaseThisIssue = false`, so `abort()` (`:265`) neither labels nor releases the issue. Flow Step 2.8's retry then reads the blob as self-owned, exits 0 with `alreadyOwned: [N]`, and never repairs the label. The same gap applies when a first attempt's `ensureAndAddLabel` threw into `labelFailures`.

Two downstream consumers treat `bot:in-progress` as the claim's projection:
- dispatch's queue-pull pre-filter (`plugin/skills/dispatch/queue-pull-script.md:143`, `!i.facets.bot.inProgress`) keeps the record eligible, and `plugin/skills/dispatch/firing-exclusion.md:30-34` skips the `firing` exclusion for `pending-review` on the stated assumption that such a group holds `bot:in-progress` — so the same firing re-selects an already-dispatched record;
- the second Task call's `dispatch-missing-claim-fallback` HARD-GATE (`plugin/skills/dispatch/task-prompt.md:291-294`) refuses the merge and reports `pending-review` although this run holds the claim.

`plugin/skills/flow/claim-targets.md:141-144` documents the label only "On a successful claim". The existing `(g)`/`(g2)` self-owned tests (`tests/bin-lib/claim-targets/claim-targets.test.js:674-711`) assert no re-claim write, not the absence of a label call, and `makeGh` already supports `fail: { labelAdd: true }` (`:124`).

## Deliverables

1. In `plugin/bin/lib/claim-targets/claim-targets.js`'s self-owned branch, re-assert `bot:in-progress` via `ensureAndAddLabel(deps.gh, issue)` before `continue` — best-effort, a thrown error pushed onto `labelFailures` (same shape as the fresh-claim path), never changing the exit code. No second claim comment is posted.
2. Extend `plugin/skills/flow/claim-targets.md`'s claim paragraph (`:141-144`) to state that an `alreadyOwned` target gets the same `bot:in-progress` re-assert (no second comment), and why (a resumed claim may never have been labeled; the queue pull's `bot:*` pre-filter and dispatch's second-call state-check both read that label).
3. Add a `(g3)` test case next to `(g)`/`(g2)` in `tests/bin-lib/claim-targets/claim-targets.test.js`.

## Acceptance Criteria

- With `makeGh({ fail: { labelAdd: true } })`, the same self-owned target still exits 0 and reports `labelFailures: [{ issue: N, error: 'label add failed' }]`.
- The new `(g3)` case fails against the current `claim-targets.js` and passes with the fix (verified by reverting the code change).
- The existing `(g)`/`(g2)` cases still pass: no claim write is attempted for a self-owned target.

## Release Note

Fix a resumed dispatch claim never getting its `bot:in-progress` label, which let the drain re-select an already-dispatched record and parked its PR.

## Technical Approach

Mirror the fresh-claim path's label block inside the self-owned branch: a `try { ensureAndAddLabel(deps.gh, issue) } catch (e) { labelFailures.push({ issue, error: errText(e) }) }` before `continue`. `gh issue edit --add-label` is idempotent, so re-asserting on an already-labeled record is harmless. The reporter's proposed diff in `## Original request` is a usable starting point; it was verified against 6.136.0 (40/41 failing without, 41/41 with).

### Key Files

- `tests/bin-lib/claim-targets/claim-targets.test.js` — new `(g3)` case

## Original request

claim-targets.js: an `alreadyOwned` (self-owned) claim never gets `bot:in-progress`, so a held claim reads as unclaimed

**Summary:** claim-targets.js alreadyOwned path never adds bot:in-progress, so a claim that landed during a transient-failed first attempt stays unlabeled; dispatch's second-call HARD-GATE then parks the PR and the drain re-selects the already-dispatched record

**Kind:** Defect

**Affected component:** claim-targets CLI (bin/lib/claim-targets/claim-targets.js) + flow Step 2.8 (skills/flow/claim-targets.md)

**Repro steps:**
1. In a pr-first project, run a `/claude-tweaks:dispatch` drain (`--budget 2` or more) with an `auto:build` record #N at the top of the queue.
2. The group's first Task call runs `/claude-tweaks:flow #N build,test`; Step 2.8 runs `bin/claim-targets.js --run-id <runId> --targets N`, and the claim write hits a transient network failure (exit 4) — but the blob actually landed on `claims-registry` under this runId/sessionId. Deterministic repro: a `ghApi`/`gitRunner` stub whose write persists the blob and then returns `{ failure: 'network-failure' }`.
3. Flow retries Step 2.8: the CLI exits 0 with `{"claimed":[],"alreadyOwned":[N],...}`.
4. Check #N's labels / label event history, then let the drain continue to the second Task call and the next iteration.

**Expected vs. actual:**
Expected: a claim this run genuinely holds carries `bot:in-progress` whether it was claimed fresh or found `alreadyOwned`, so the second call's state-check passes and the queue pull excludes #N.
Actual: #N never receives `bot:in-progress` (its label event history shows it was never added). (a) The second Task call's `dispatch-missing-claim-fallback` HARD-GATE (`skills/dispatch/task-prompt.md:291-294`: claim live AND `bot:in-progress` present) refuses the merge and reports `pending-review` although the claim is held by this run. (b) The drain's next queue pull keeps #N eligible (no `bot:*` label), `firing-exclusion.md` does not append a `firing` exclusion for `pending-review`, and the next ranking re-selects the already-dispatched record in the same firing; a manual `appendExclusion(..., { reason: 'firing' })` was needed.

**Root cause:** the `bot:in-progress` label is added in exactly one place: `ensureAndAddLabel` at `bin/lib/claim-targets/claim-targets.js:457-461`, reached only after a fresh write is verified and pushed onto `claimedThisRun` (`:449-455`). The self-owned branch at `:348-351` (`identity.runId === opts.runId` on a `live`/`stale` blob) pushes onto `alreadyOwned` and `continue`s without touching the label. On the first attempt, a write that reports `failure`/`secondaryRateLimit` (`:391-402`) goes through `stopOrSkip(..., 'transient', ..., 4, ...)` with `releaseThisIssue = false` (`:286-288`), so `abort()` neither labels nor releases this issue — a write that landed despite the reported failure leaves a live, unlabeled blob, and the retry's `alreadyOwned` path never repairs it. (The same gap applies if a first attempt's `ensureAndAddLabel` threw into `labelFailures`.) `skills/flow/claim-targets.md:141-144` documents the label only "On a successful claim", but two downstream consumers treat the label as the claim's projection: the queue pull's pre-filter (`skills/dispatch/queue-pull-script.md:143`, `!i.facets.bot.inProgress`; `SKILL.md:128`) and the second-call HARD-GATE (`task-prompt.md:291-294`); `firing-exclusion.md:30-34` skips the `firing` exclusion for `pending-review` on the stated assumption that such a group holds `bot:in-progress`. Fix: re-assert the label (idempotent `gh issue edit --add-label`, best-effort, failures into `labelFailures`) on the `alreadyOwned` path too, and document it in `claim-targets.md`. That repairs both consequences at the source. (Defense-in-depth alternative, not in the diff: have `firing-exclusion.md` append a `firing` entry for every group this firing dispatched regardless of outcome, or have the queue pull consult the claims registry — heavier, since it adds a registry read per candidate.)
