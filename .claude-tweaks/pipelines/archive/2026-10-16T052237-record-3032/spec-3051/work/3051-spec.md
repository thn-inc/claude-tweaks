# 3051: claims-git-cas: fixed 10 s git timeout fails claim reads on a loaded machine

Surface: infra

## Current State

`plugin/bin/lib/issues/claims-git-cas.js` runs every git call through `defaultRunner` (`:76`), which passes a fixed `timeout: GIT_TIMEOUT_MS` with `GIT_TIMEOUT_MS = 10000` (`:74`) and offers no override. When a call is killed on the timeout:

- `readClaimBlobGit`'s fetch path returns `failure: 'transport-failure'` from a bare `catch` (`:119-121`).
- `classifyGitError` (`:60-71`) falls through to `{ kind: 'transport-failure' }` for any unmatched error, a timeout kill included.

So a slow-but-healthy remote is indistinguishable from an unreachable one. `bin/verify-run-bookends.js` reads live claims through `readClaimBlobGit` (`:30`) and reports any read failure as `read-failed: transport-failure` (`:113-114`).

The repo already solved the same problem for `gh` in #2567. `GH_TIMEOUT_MS` in `plugin/bin/lib/shared-primitives.js:138` (`resolveGhTimeoutMs`) resolves env `CLAUDE_TWEAKS_GH_TIMEOUT_MS` > policy key `gh-timeout-ms` (`plugin/bin/lib/policy-schema.js:123`, integer 1000-60000, default 5000; read via `plugin/bin/lib/policy.js:105`) > default. It is lazily resolved and cached per process. `shared-primitives.js:162` exports `isTimeoutError` (the `ETIMEDOUT` / `killed` / `SIGTERM` check).

Observed (reporter, plugin 6.137.0): about seven concurrent dispatch sessions on one machine against a GitHub Enterprise remote. `verify-run-bookends` failed three times in a row on a live, healthy claim because the claims-branch fetch exceeded 10 s; a hand-timed fetch took 8.6 s, and the fourth attempt passed.

## Deliverables

1. Make the claims-git-cas timeout configurable, mirroring #2567. Add a `git-timeout-ms` policy key in `policy-schema.js` (integer, 1000-120000, default 30000, category `housekeeping`, tier `advanced`), a `policy.js` reader, and an env override `CLAUDE_TWEAKS_GIT_TIMEOUT_MS`, with precedence env > policy > default, resolved lazily and cached. `claims-git-cas.js`'s `defaultRunner` uses the resolved value instead of the fixed `GIT_TIMEOUT_MS`.
2. Tell a timeout apart from other transport failures without changing the failure vocabulary. When the underlying error satisfies `isTimeoutError`, `readClaimBlobGit` and the other `transport-failure` returns in `claims-git-cas.js` add `timedOut: true` to their result. `failure` stays `'transport-failure'`, so `claim-store.js:344-350` and every other consumer behave exactly as before.
3. `verify-run-bookends.js` names the timeout in its missing-bookend reason (for example `read-failed: transport-failure (timed out after {ms} ms)`) when `timedOut` is set.
4. Document `git-timeout-ms` in `plugin/skills/_shared/policy-schema.md` next to `gh-timeout-ms`.

## Acceptance Criteria

- With no env var or policy key, the claims-git-cas runner uses 30000 ms; `CLAUDE_TWEAKS_GIT_TIMEOUT_MS=45000` yields 45000; a `git-timeout-ms: 20000` policy value yields 20000 when the env var is unset; an out-of-range or non-numeric value falls back the same way `gh-timeout-ms` does. Covered by tests next to the existing `gh-timeout-ms` resolution tests.
- A runner stub throwing a timeout-shaped error (`killed: true` / `signal: 'SIGTERM'` / `code: 'ETIMEDOUT'`) makes `readClaimBlobGit` return `failure: 'transport-failure'` and `timedOut: true`. A non-timeout error returns `failure: 'transport-failure'` with no `timedOut`. Covered in `tests/bin-lib/issues/claims-git-cas.test.js`.
- `verify-run-bookends` reports the timeout wording when `timedOut` is set, covered by its test.
- `claim-store.js`'s behavior on a git transport failure, including the contents-API fallback, is unchanged, and the existing claim-store and claims-git-cas suites pass.
- `policy-schema.md` and `policy-schema.js` agree on the new key (any existing schema/prose conformance test passes).

## Release Note

Let claim checks wait longer on slow git remotes (now configurable, default 30 s) and report a timeout as a timeout instead of a generic transport failure.

## Technical Approach

Reuse the #2567 shape exactly: env, then policy key, then default, lazily cached. Reuse the shared `isTimeoutError` helper. A distinct `timedOut` flag is used instead of a new `failure: 'timeout'` value. `claim-store.js` and `claim-targets.js` branch on the existing failure vocabulary, and a new value would need a consumer sweep for a purely diagnostic gain. Retry-with-backoff (the reporter's last idea) is left to callers. With a 30 s bound, the observed 8.6 s fetch passes on the first attempt.

### Key Files

- `plugin/bin/lib/issues/claims-git-cas.js` — resolved timeout in `defaultRunner`; `timedOut` flag on timeout-shaped transport failures
- `plugin/bin/lib/shared-primitives.js` — `GIT_TIMEOUT_MS` resolution alongside `GH_TIMEOUT_MS` (or a sibling resolver in the same shape)
- `plugin/bin/lib/policy-schema.js` — `git-timeout-ms` key
- `plugin/bin/lib/policy.js` — `git-timeout-ms` reader
- `plugin/bin/verify-run-bookends.js` — timeout wording in the missing-claim reason
- `plugin/skills/_shared/policy-schema.md` — document `git-timeout-ms`
- `tests/bin-lib/issues/claims-git-cas.test.js` — `timedOut` cases

## Gotchas

- `shared-primitives.js` is required on `pre-tool-use.js`'s hot path (its own header). Keep the git-timeout resolution lazy, as `GH_TIMEOUT_MS` is, so no policy read happens unless claims-git-cas actually runs git.
- A larger timeout lengthens the worst case of a genuinely unreachable remote, now up to 30 s per git call. This is accepted: claim operations are not on an interactive hot path, and the env/policy override lets a fast-network project lower it.
- `policy-schema.js` and `policy-schema.md` are a code/prose twin. Add the key to both in the same change.

## Original request

claims-git-cas: fixed 10 s git timeout fails claim reads on a loaded machine

**Summary:** `claims-git-cas` runs every git call with a hard-coded 10 s timeout, so a claim read against a slow but healthy remote is killed and reported as a transport failure.

**Kind:** Defect

**Affected component:** `bin/lib/issues/claims-git-cas.js` (`GIT_TIMEOUT_MS`), reached via `bin/verify-run-bookends.js`

**Repro steps:**
1. Run several `/claude-tweaks:dispatch` sessions at once on one machine against a GitHub Enterprise remote, so a single-ref fetch of the claims branch takes 8-10 s.
2. Let a `/claude-tweaks:flow` build,test call reach its end-of-call `verify-run-bookends` check while its claim is live.
3. The claim read's `git fetch` exceeds `GIT_TIMEOUT_MS = 10000` in `defaultRunner`, `execFileSync` kills it, and `classifyGitError` maps the kill to `transport-failure`.

**Expected vs. actual:**
Expected: a claim read on a slow but healthy remote succeeds, or the failure names the timeout so the caller can tell "remote slow" from "remote unreachable".
Actual: the bookends check failed three times in a row on the timeout while the claim was live and healthy; a manual fetch of the same branch, timed by hand, took 8.6 s; the fourth attempt passed. About seven sibling dispatch sessions were running on the machine.

**Suggested fix:** raise the default (30 s), allow an environment override (for example `CLAUDE_TWEAKS_GIT_TIMEOUT_MS`), and classify an `ETIMEDOUT` / killed-by-signal exec error as its own `timeout` kind so callers can retry it with backoff instead of treating it as a hard transport failure.

**Definition:** Clear

**Plugin version:** 6.137.0
