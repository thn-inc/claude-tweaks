# 1264: capture: absorb-by-default — recommend absorbing high-similarity captures into existing records

Surface: backend

## Overview

Make absorb-into-existing the recommended default in `/capture` when similarity to an existing open record is high. Today capture computes related records and offers "Absorb into record {N}" as a conditional option 3; a third of the last week's 512 filed issues carried `by:capture`, many duplicating or fragmenting intent that an existing record already holds. The change: at high similarity — an existing open record covers the **same file/subsystem AND the same kind of change** (both criteria defined below) — absorb becomes the recommended first option interactively (new-issue one click away, nothing silently merged); headless paths absorb only at a strict structural bar, filing fresh on anything ambiguous, because a wrong auto-merge is invisible while a duplicate is visible and mergeable later. This is deliberately the cheap first intervention against the capture-duplication share; its effect is re-checked by parent #1260's success measure (birth-rate re-audit ~2 weeks after the floor's adopter migration ships).

**Complexity:** Low
**Estimated tasks:** 5

## Non-Goals

- No change to the born-ready chain contract (`/capture` → `/specify #{n} --chained` shapes exactly one record per invocation) — an absorbed capture never enters the chain; the existing record's own lifecycle stands.
- No new similarity engine — no scoring model, no embeddings; the judgment is the two concrete criteria below over data from capture's candidate search, whose **field set this record does widen** (see Technical Approach — a wider fetch, not a new lookup mechanism).
- No absorb into closed records, `parent-issue` carriers, or `bot:in-progress` carriers (label vocabulary per `_shared/work-record.md`'s taxonomy) — filing fresh with a `Related:` line stays correct for all three.
- No change to `/feedback` or any other filer.

## Deliverables

- [ ] **High-similarity definition** stated in `plugin/skills/capture/SKILL.md` as two concrete criteria, both required: (a) **same file/subsystem** — the candidate's body (its `### Key Files` section when spec-shaped, else its title subject) and the capture's `Context:`/`Scope:` text name at least one identical file path or the same named module/subsystem; (b) **same kind of change** — identical `type:{t}` value (the family vocabulary is `_shared/work-record.md`'s Type axis, `TYPE_LABELS` in `record.js`) AND the same operation on that subject (matching verb-plus-target: both dedupe X, both fix the same named failure, both extend the same surface — a judgment anchored on a shared named artifact, never a text-similarity score).
- [ ] **Interactive routing:** when exactly one candidate meets both criteria, absorb renders as option 1 `(Recommended)`; when several qualify, recommend the one with the highest count of shared file paths, tie-broken by most-recently-updated; low/ambiguous similarity keeps today's ordering. Nothing is silently merged.
- [ ] **Absorb mechanics:** the capture's content lands on the existing record as a body-append under `## Absorbed: {YYYY-MM-DD} — {captured title}` (or a comment instead when the post-append body would exceed 55,000 characters, against GitHub's 65,536 cap), via `_shared/github-write-transport.md`, compose-then-write-once; the existing record's `size:` label is re-judged by re-applying `_shared/work-record.md`'s size heuristic to the combined body and raised when that re-judgment says so (never lowered); `priority:` is never written — when the addition suggests higher priority, say so in the output for the human. Every absorb names the target record and what was appended in the skill's rendered output, and invalidates the session record snapshot per the existing convention (cited, not restated).
- [ ] **Headless bar** (`--defer-reason=`/agent-driven and any chained path): absorb only when criterion (a) is met by a shared **literal file path** named in both AND criterion (b)'s type values are identical — the operation-match judgment is replaced by the structural path requirement headlessly; anything short files fresh with `**Related:** #N`. The absorb's own appended heading (date + captured title on the target record) is the always-present audit trail; when a run directory resolves, additionally log `AUTO {time} — capture absorbed into #{N} (shared path + same type). Reversibility: medium (append is visible on #{N}).` per `_shared/auto-decision-log.md`.
- [ ] **Candidate fetch widening:** the candidate search's field set gains `labels`, and the top candidate(s) get one `gh issue view {n} --json body` follow-up read before judging — the same search-narrow-then-fetch-full two-step `/specify`'s case 5 uses. Non-Goals' "no new engine" stands; this is a field widening of the existing lookup.
- [ ] `tests/capture-absorb-default.test.js` — pins each rule with its own content-anchored assertion: the recommended-ordering rule and its two-criteria definition, the multi-candidate tie-break, the headless structural bar and its fail-toward-filing default, never-lower-size, never-write-priority, the three exclusions as one enumerable list, the 55,000-char body-vs-comment threshold, and the `AUTO` log line.

## Technical Approach

An ordering-and-mechanics change inside capture's existing Immediate Routing plus one widened fetch. The absorb write path composes: fetch target body → append section → single `gh issue edit --body-file` → `size:` label raise in the same edit call when warranted → snapshot invalidation. The interactive AskUserQuestion continues to follow the repo's Interaction style directive (one call, recommended option first). The `## Absorbed:` heading must land under the record's existing sections, never rewriting the spec-shaped content above it.

## Gotchas

- `capture/SKILL.md` has ~2.5KB ceiling headroom — prefer tightening the existing option-3 prose over adding a parallel section; measure `wc -c` after.
- Never absorb on title similarity alone — similarity scores are normalization-sensitive; both criteria anchor on concrete shared artifacts (a file path, a type value, a named operation target), never a score.
- Re-scoring goes through the label permission matrix: `size:` yes (capture already stamps scoring), `priority:` never (human/refine territory).
- The absorbed-into record may be `ready` and already spec-shaped — the append lands under its own heading, never rewriting the spec sections above it.
- The widened candidate fetch adds one `gh issue view` round-trip per judged candidate — judge at most the top 2 candidates to keep the interactive path fast.
