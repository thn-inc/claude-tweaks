# 1263: specify: decomposition collapse rules — no single-leaf parents, two-leaf parents only when dependency-ordered

Surface: backend

## Overview

Stop `/specify`'s decomposition mode from creating parents that do no tracking work. Measured 2026-08-22 (methodology: native `sub_issues` API counts over the prior week's `parent-issue`-labeled issues; baseline recorded in parent #1260's Overview): 6 of the 26 decomposition parents created in the prior 7 days had ≤1 sub-issue — a parent plus one leaf is two issues, a parent guard, and a sub-issue link for one unit of work. New rules: a decomposition yielding **1 work unit always collapses** (no parent — shape in place or create one ready record); **2 units keep a parent only when dependency-ordered** (a `Blocked by` edge between them, an internal-conflict flag from Step 2's implicit-dependency detection, or the strangler-fig `early-production` flag-then-remove shape, where the parent tracks the sequence) — two independent units become two `Related:`-cross-linked ready records with no parent; **3+ units are unchanged** (the strangler-fig `established` three-unit shape is 3+ and never collapses). `--granularity` never overrides collapse: the flag tunes sizing targets, not ceremony. When dependency-ness at 2 units is ambiguous, keep the parent — ambiguity resolves toward tracking, never toward collapse.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- No change to shaping mode, the parent-record guard (`specify/SKILL.md` case 1), or how existing parents are handled — this sub-issue only changes when NEW parents come into existence.
- No change to the Sizing Guidelines' targets or the `--granularity` flag's sizing semantics.
- No retroactive cleanup of existing single-leaf parents (tidy territory, not this change).
- No change to Step 5 red-team, Step 6 self-review, or Step 7 design-doc deletion — they operate on whatever records exist, parent or not.
- No audit of Step 2's implicit-dependency detection itself — this record trusts its outputs as-is (its known defects, e.g. #1228's false giant bundles, err toward MORE detected dependency, which under these rules errs toward keeping the parent — the safe direction).

## Technical Approach

The collapse decision is a routing step, not new machinery: everything downstream (Step 2.5, red-team, self-review, Step 7 deletion, Step 9 summary/commit) already operates per-record and needs only conditional prose where it references "the parent". The design doc for a collapsed decomposition is still deleted per Step 7 — collapse changes record count, not artifact lifecycle; the surviving record(s) absorb the doc per Step 3's Rules exactly as sub-issues do today.
