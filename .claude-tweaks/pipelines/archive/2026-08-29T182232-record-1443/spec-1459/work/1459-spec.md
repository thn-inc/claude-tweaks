# 1459: bin/materialize.js hard-requires `gh` with no MCP fallback, unlike other GitHub-write call sites

Surface: backend

## Current State

`plugin/bin/materialize.js`'s `realDeps.ghView` (line ~94) shells straight to `gh issue view {n} --repo {owner}/{repo} --json number,title,body,labels,url`; `run()` hard-exits 2 (line ~150) via `deps.stderr('materialize.js: \`gh\` is required (work-backend: github-issues)\n')` when `deps.ghAvailable()` is false, before any record fetch happens.

`plugin/skills/_shared/github-write-transport.md`'s CRUD mapping (lines 18-28) documents `gh issue view {n} --json state,...` ↔ `issue_read` (get mode) as the read-side transport pair for "Get a single issue by number" — but that mapping is a **skill-prose** branch, taken by the LLM-harness turn itself, never by a Node subprocess. Two sibling CLIs in the same directory already state this constraint explicitly and deliberately decline to grow an MCP path into themselves: `plugin/bin/release-claim.js`'s header comment (`gh` absent → exit 2, pointing the caller at the MCP path documented in `_shared/github-write-transport.md`/`_shared/issue-claims.md`, "deliberately not grown into this CLI") and `plugin/bin/lib/reconcile/pr-state.js:6-9` ("a Node subprocess cannot see an agent session's MCP tools"). No `bin/lib/*` helper for invoking an MCP tool from a Node script exists anywhere in this repo, and the repo's own precedent is that none should be added — it would be dead code no subprocess can drive.

The bug's own discovery note names the actual workaround the original reporter used: a live MCP `issue_read` call, followed by hand-composing the header/file — bypassing `materialize.js`'s tested `shapeGate`/`liftMetadata`/`composeHeader`/`composeFile` pipeline (`plugin/bin/lib/issues/materialize-format.js`) entirely. `plugin/skills/flow/steps-and-gates.md`'s inherited-run-dir case-3 recovery (~lines 70-78) still documents this same bypass as the sanctioned recovery path today: "run `materialize.md`'s Composing the file + commit step now" rather than invoking the CLI.

- [ ] Update `plugin/skills/flow/steps-and-gates.md`'s inherited-run-dir case-3 recovery text to point at the new `--record-json` path instead of "hand-compose the header/file" — closing the exact gap the bug report's discovery note hit.

## Technical Approach

The issue's original ask — "add an MCP-backed implementation selected the same way [`github-write-transport.md`'s] write-side transport already picks between `gh` and MCP" — does not fit this call site: that file's transport choice is a skill-prose branch taken by the LLM-harness turn, which alone can call MCP tools. `materialize.js` is a plain Node subprocess and cannot invoke an MCP tool itself, per the two sibling-CLI precedents cited in Current State.

The correct mirror of the existing pattern sits one level removed: give the **calling skill** — which already runs inside the LLM harness and already has MCP access whenever `gh` is absent — a way to hand `materialize.js` the already-fetched record instead of asking the CLI to fetch it itself. Add `--record-json <path>`: when present, `run()` reads the file and `JSON.parse`s it in place of the `deps.ghView(...)` call (materialize.js lines ~158-164); `deps.ghAvailable()` is only consulted when `--record-json` is absent. Everything downstream — `shapeGate`, drift computation, `liftMetadata`, `composeHeader`, `composeFile`, the write — is unchanged, since it already operates on the parsed `record` object regardless of how it arrived.

### Key Files

- `plugin/bin/materialize.js` — add `--record-json` to `parseArgs`/`USAGE`, branch `run()` between file-read and `ghView`, update the header comment's exit-code documentation.
- `plugin/skills/flow/materialize.md` — document the new flag and the gh-absent invocation shape (its own "**`bin/materialize.js ...`**" usage line, near the top).
- `plugin/skills/flow/steps-and-gates.md` — update the case-3 recovery text (~line 74) to invoke the CLI with `--record-json` instead of hand-composing.
- `tests/materialize-record-json.test.js` (new) — coverage for the `--record-json` path, following the existing `fakeDeps`/`gitRepo` fixture pattern already established in `tests/materialize-drift.test.js`.

## Gotchas

- A Node subprocess cannot invoke an MCP tool — this is a hard platform constraint, stated independently in `plugin/bin/release-claim.js`'s header and `plugin/bin/lib/reconcile/pr-state.js:6-9`, not a gap specific to this CLI. Any future record-read call site tempted to "add an MCP fallback directly in the CLI" hits the same wall; the `--record-json`-style input-injection pattern is the general answer, not a one-off for this file.
- Keep the `--record-json` JSON shape identical to `gh issue view {n} --json number,title,body,labels,url`'s output — `record.labels` must stay the same array-of-`{name}` (or bare-string) shape `parseRecordFacets` already expects, so a skill composing this file from an MCP `issue_read` response must reshape MCP's label representation to match, not pass it through raw.
- Don't let `--record-json` bypass the `--run-dir` anchoring guard (materialize.js lines ~125-148, [IL-127]/#790/#959) — that check runs before either input path and must stay unconditional.
