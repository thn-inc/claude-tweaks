# 1443: Audit parseRepo's other 8 callers for unguarded '.'/'..' owner/repo segments

Surface: backend

## Current State

The shared `parseRepo` (`plugin/bin/lib/repo-resolve.js`) accepts any non-`/` owner/repo segment, including `.`/`..` — its regex only excludes literal `/`. `fetch-sub-issues.js`'s own review (#1153, Step 3 lens 3b) confirmed this and was fixed at that one call site (commit `f8208739`): its `--resolve-retries` REST retry call interpolates `owner`/`repo` directly into a `gh api` path string rather than using `gh`'s bound-variable mechanism (`-f`/`-F`), so a crafted `--repo owner/..` value would reach that path. That fix was deliberately scoped to `fetch-sub-issues.js` alone, to keep #1153's blast radius to one file.

`parseRepo` has 9 total callers (per its own header comment) — `fetch-sub-issues.js` plus 8 others, confirmed by grep: `resolve-blockers.js`, `release-claim.js`, `preflight-records.js`, `materialize.js`, `link-records.js`, `file-feedback.js`, `claims.js`, `backlog-grant-gate.js`. None of these 8 has been audited for whether it, too, interpolates `owner`/`repo` into a `gh api` path/query string without a bound-variable placeholder — that per-caller reachability audit is what this record scopes. Not confirmed reachable in any of the 8 yet.

## Deliverables

Audit each of `parseRepo`'s 8 other call sites for whether it accepts an untrusted `--repo` value that reaches a `gh api` path or query string without its own guard or without using `gh`'s bound-variable mechanism. Based on the audit outcome, either:

- Tighten the shared `parseRepo` regex itself to reject `.`/`..` segments at the source (closes the gap for all 9 callers at once), or
- Add the same narrow per-caller guard `fetch-sub-issues.js` got (#1153, commit `f8208739`) wherever a caller is confirmed reachable.

## Acceptance Criteria

- Each of the 8 callers (`resolve-blockers.js`, `release-claim.js`, `preflight-records.js`, `materialize.js`, `link-records.js`, `file-feedback.js`, `claims.js`, `backlog-grant-gate.js`) is checked against a crafted `.`/`..` owner/repo or remote-URL value.
- Either every caller confirmed reachable rejects the crafted value (guard added, with a regression test per caller, following the pattern in `tests/fetch-sub-issues-cli.test.js`), or the shared `parseRepo` regex itself rejects `.`/`..` segments at the source.
- Every caller's existing test suite still passes after whichever fix is applied.

## Technical Approach

For each of the 8 callers, trace how `opts.repo`/`remote` flows from `parseRepo`'s return value to any `gh api`/`gh issue`/`gh pr` call the same file makes: does it reach a path segment or query string via string interpolation (vulnerable, per the `fetch-sub-issues.js` precedent), or only via `-f`/`-F`/native flags that `gh` binds safely? If tightening the shared regex instead, verify it still accepts every legitimate owner/repo shape exercised by each caller's existing tests (e.g. hyphens, underscores, org names) before landing the change — a single regex change affects all 9 callers at once, so the existing test suites across all 9 files are the regression net for that path.

## Gotchas

- A caller rejecting `.`/`..` is only a defect if that caller actually reaches a `gh api` path/query with the unguarded value — several of the 8 may only ever pass `owner`/`repo` through `-f`/`-F` bound variables, in which case there is nothing to fix there and the acceptance criteria's "reachable" qualifier is satisfied trivially for that file.
- Tightening the shared regex is the lower-effort, single-point fix but touches all 9 callers' behavior at once — verify no caller's existing tests rely on an owner/repo value the tightened regex would newly reject.
