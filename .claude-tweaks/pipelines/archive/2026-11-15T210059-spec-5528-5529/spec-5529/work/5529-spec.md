# 5529: Make code-health status --fail-on refuse when it cannot trust the local cache

Surface: infra
Risk-flags: public-contract

**Related:** #5528 (the other Phase 0 fix from the 2026-11-15 audit simplification design; independent, no shared file), #5440 (also edits `plugin/bin/code-health.js`, in a different function)

## Overview

`code-health.js status --fail-on regressed|risk-high` is documented as a gate for CI or a pre-push hook. It counts findings in a local cache file that git ignores. When that file is absent, as on a CI runner or in a checkout where the sweep never ran, every count is zero and the gate exits 0. It reports a pass it did not earn. A corrupt cache does the same, or crashes with the exit code that means "gate failed".

This record makes the gate refuse when it cannot trust its input: with `--fail-on`, it exits 2 with a message unless the cache is a regular file inside the checkout holding a well-formed cache object. The documentation is corrected to say what the gate reads and what it cannot detect. It is unit 0.2 of the 2026-11-15 audit simplification design.

**Complexity:** Low
**Estimated tasks:** 4

## Non-Goals

- Making the gate work on a fresh checkout by reading issue state from GitHub or from the `health-state` branch. That would be a new feature; this record only stops the false pass.
- Detecting a stale cache. A cache left by an old sweep, or by a sweep on another branch, still yields a verdict. The documentation states this limit; nothing checks freshness.
- Finding the cache of another checkout. The gate reads under `--root`, or the current directory when `--root` is absent. It does not resolve the main checkout from a linked worktree.
- Changing the status line. Its fields, including `closed:`, stay exactly as they are.
- Changing plain `status` (no `--fail-on`). It stays informational, exits 0 with or without a cache file, and keeps today's behaviour on a malformed cache.
- Changing `churn-report --fail-on-high-churn`, the `status` subcommands of the other three health CLIs, or how `validate-findings` reads the cache.

## Prerequisites

None.

## Current State

- The gate: `cmdStatus` in `plugin/bin/code-health.js` (starts at `:64`) reads `readCache(root)` at `:76` and exits 1 only when the cache holds a `regressed` entry (`--fail-on regressed`) or an `open`/`regressed` entry with `risk: 'high'` (`--fail-on risk-high`).
- A missing or corrupt file reads as empty: `readCache` in `plugin/bin/lib/health-core/cache.js:19-22` returns `{}` when the read or the parse throws.
- A malformed entry crashes: `cmdStatus` takes `Object.values(cache)` and reads `f.status` on each with no guard (`plugin/bin/code-health.js:77-85`). A `null` value throws, and Node exits 1, the code this command uses for "gate evaluated and failed".
- The file is local to one checkout: `.gitignore:43` ignores `.claude-tweaks/code-health/`. Its path is `cachePath(root)`, `plugin/bin/lib/health-core/cache.js:18`, re-exported by `plugin/bin/lib/code-health/cache.js:96`. `cmdStatus` and `validate-findings` both resolve `root` as `args.root || ctx.cwd()` (`plugin/bin/code-health.js:65` and `:148`), so each checkout and each linked worktree has its own cache.
- A sweep usually leaves the file but not always: `validate-findings` calls `writeCache(root, cache)` at `plugin/bin/code-health.js:286`, inside an `if (!args.dryRun)` block and a try/catch that reports a write failure as non-fatal. A `--dry-run` sweep and a failed write leave no file.
- The documentation: `plugin/skills/code-health/ci-integration.md:7` says "Use `status [--fail-on regressed|risk-high]` to integrate code-health state into CI or pre-push hooks", and `:18-19` describe the exit codes in terms of "cache entries" without saying the cache is local. `plugin/skills/code-health/SKILL.md:320` points at that file.
- Tests: `tests/bin-lib/code-health/status-v2.test.js` has eleven cases, including "status --fail-on regressed exits 0 when no regressed entries" and "status --fail-on with an unrecognized value exits 2". `tests/code-health-misc/cli.test.js` also runs `status`.

## Deliverables

- [ ] In `--fail-on` mode, `cmdStatus` accepts the cache only when every one of these holds: the path `cachePath(root)` is a regular file and not a symlink; it resolves to a location inside `root`; its content parses as JSON to a plain object; and every value in that object is itself a plain object. It reads and parses the file once and computes the counts from that object.
- [ ] When the cache is not accepted, `status` prints one line to stderr, `status: --fail-on cannot evaluate: {path}: {reason}`, prints nothing to stdout, and exits 2. `{reason}` is one of three strings, defined in one table in `plugin/bin/code-health.js`:
  - `no cache file (no sweep has written one under this root)` — nothing exists at the path.
  - `not a regular file inside the checkout` — a symlink of any kind at the path (dangling, pointing inside the checkout, or pointing outside it), a directory, any other non-file, or a path that resolves outside `root`.
  - `not a readable code-health cache` — a read error, invalid JSON, JSON that is not a plain object, or an object with a value that is not a plain object.
- [ ] **Closed rule.** The accept condition above is the whole test. *Exhaustive:* a cache that fails it is never evaluated, whatever state it is in. *Refused with a named remedy:* every such state gets the exit-2 line with one of the three reasons. *Amendment, not escalation:* a plan review that finds a state fitting none of the three reasons adds a reason to the table, to the list in `ci-integration.md` and as a case in acceptance criterion 6, in the same change, as a plan amendment and not as a question for a human.
- [ ] With `--fail-on` and an accepted cache, behaviour is unchanged, including an empty `{}` cache exiting 0. Plain `status` is unchanged.
- [ ] `plugin/skills/code-health/ci-integration.md`'s Regression and Risk Gating section states: the gate reads the local, git-ignored cache under `--root` or the current directory; each checkout and linked worktree has its own cache, so a hook that runs elsewhere passes `--root` naming the checkout the sweep ran in; exit 2 means the gate could not evaluate and is a setup problem, not a finding; the gate cannot tell a stale cache from a fresh one; and it is not suited to a fresh CI checkout.
- [ ] Tests for the refusal cases and for the unchanged cases.

## Release Note

Changed the code-health status gate to stop with a clear error when it has no trustworthy local sweep data, where it used to pass silently.

## Technical Approach

Refuse instead of guessing. An absent cache file and an empty cache are different facts: the first means no sweep wrote one here, the second means a sweep ran and found nothing to gate on. `readCache` collapses them, and it also turns an unreadable or corrupt file into an empty cache, so `cmdStatus` inspects the file itself before reading when `--fail-on` is set.

The gate finds its input at a conventional path that no caller names, and that input decides a pass or fail verdict. That makes the lookup a trust decision, which is why a symlink is refused here, including one that stays inside the checkout: a regular-file test is one rule with no cases to argue about.

Exit 2 is used because this CLI already uses it for a gate that cannot evaluate (`--fail-on` with an unrecognized value, `plugin/bin/code-health.js:67-75`), and exit 1 already means the gate evaluated and failed. A hook treats both as failure; the message is what tells them apart.

Two alternatives were put to the maintainer on 2026-11-15 and set aside. Retiring `--fail-on` would remove the false pass for good, but leaves it in place through a deprecation period and removes a gate that works in a pre-push hook on the checkout that runs the sweep. Rebuilding the gate on issue state would make it meaningful in CI, but is a feature with its own design questions.

### Data / API Surface

Exit codes for `status`: 0 informational or gate passed; 1 gate evaluated and failed; 2 gate could not evaluate (unrecognized `--fail-on` value, or `--fail-on` with a cache that is not accepted).

Refusal line, stderr: `status: --fail-on cannot evaluate: {path}: {reason}`, with `{reason}` one of the three strings in Deliverables. Tests assert the exit code, the empty stdout and the path; they do not pin the reason wording.

### Key Files

- `plugin/bin/code-health.js` — `cmdStatus`: the accept test, the reason table and the refusal
- `plugin/skills/code-health/ci-integration.md` — say what the gate reads, its limits, and the exit-2 case
- `tests/bin-lib/code-health/status-v2.test.js` — refusal cases and unchanged cases

## Gotchas

- This is a behaviour change to a documented command. A CI job that runs the gate on a fresh checkout, and a pre-push hook that runs it from a worktree other than the one the sweep ran in, both go from a silent pass to exit 2. That is the point of the fix; the pull request description must say so.
- `status` resolves `root` from `--root` or the injected `cwd` (see the two cwd cases in `status-v2.test.js`). Check for the cache file under that same resolved root.
- Use `cachePath` from the cache module; do not rebuild the path by hand.
- Do the file checks with `plugin/bin/lib/path-guard` (`lstatType`, `resolveWithin`), not `fs.existsSync` or `fs.realpathSync`. `tests/path-guard-conformance.test.js` counts both tokens per file under `plugin/bin`, and `plugin/bin/code-health.js` has no entry in its allowlist today. `lstatType` reports every symlink as a symlink, which is what the regular-file test needs; `resolveWithin` returns no path for a location outside `root`, which covers a symlinked parent directory.
- The symlink cases in acceptance criterion 6 cannot run on a Windows checkout without symlink rights. Guard them the way the repository's other symlink tests do; `.claude/skills/windows-checkout-test-parity` describes the pattern.
- #5440 (open, not started) extracts the health CLIs' shared `run()` wiring and also edits `plugin/bin/code-health.js`. The two changes are in different functions; whichever lands second rebases.
- `plugin/skills/code-health/ci-integration.md` and `SKILL.md` may be pinned by `tests/bin-lib/code-health/skill-md.test.js`. Run the full suite before calling the change done.
