# 1248: resolve-policy.js --values with a comma-joined lever list silently returns nothing

Surface: backend

## Current State

`plugin/bin/resolve-policy.js`'s argument parser (`main()`, lines 54-76) collects every
non-flag argv token into a `keys` array via `keys.push(arg)` — it never splits a token on
`,`. Confirmed by direct invocation in this checkout:

```
$ node plugin/bin/resolve-policy.js --values auto-mode,worktree-always
                                          # one blank line — no lever values printed
$ node plugin/bin/resolve-policy.js --values auto-mode worktree-always
default-on
true
```

A single comma-joined token (`auto-mode,worktree-always`) is looked up as one literal,
unrecognized key — `resolvePolicyConfig` returns `{error: "unknown-key"}` for it — and
`--values` mode's own per-key logic (line 183: `if (!entry || entry.error !== undefined ...)
return ''`) prints that as an empty line, which reads as "no output" for a single-key call.
The *working* multi-key form is already used correctly elsewhere in this codebase —
`bin/lib/wrap-up/facts.js:131` calls `execFileSync(scriptPath, ['--values',
'harness-health-scoped-rule-budget', 'harness-health-always-loaded-budget'], ...)`, passing
each lever as its own argv element rather than joining them with a comma.

No file in `plugin/skills/**` or `docs/**` currently documents the comma-joined
`--values a,b,c` invocation shape — grepped `--values` across `plugin/` and `docs/` and
found only single-key calls (`manifesto.md:20`, `manifesto.md:139`) and the correct
multi-argv-token form (`facts.js:131`). The comma-joined shape the original report describes
was most likely typed live against a real run (`Origin:` #818's dispatch session) rather than
copied from a doc that still shows it today, so deliverable (b) — a docs-only fix — has
nothing left to correct; option (a) is what this record implements.

## Deliverables

Make `resolve-policy.js` accept a comma-joined lever list under `--values` (and, for
consistency, under the default JSON-envelope mode too, since both modes share the same
`keys.push(arg)` collection loop) by splitting each non-flag argv token on `,` before pushing
its parts into `keys`. `--values auto-mode,worktree-always` and
`--values auto-mode worktree-always` must resolve identically.

## Acceptance Criteria

- `node plugin/bin/resolve-policy.js --values auto-mode,worktree-always` prints two lines
  (one per lever, same order as given), matching what
  `node plugin/bin/resolve-policy.js --values auto-mode worktree-always` already prints today.
- `node plugin/bin/resolve-policy.js auto-mode,worktree-always` (default JSON-envelope mode)
  prints one JSON object keyed by both lever names, matching
  `node plugin/bin/resolve-policy.js auto-mode worktree-always` today.
- A single unknown key, comma-joined or not, still resolves to `{"error": "unknown-key"}` for
  that key specifically (splitting must not change per-key error semantics).
- `--all` is unaffected — it still rejects any key arguments (comma-joined or not) with its
  existing mutual-exclusivity error, since it takes no key arguments at all.
- Existing resolve-policy spawn tests continue to pass; a new test covers the comma-joined
  multi-key form for both `--values` and the default JSON mode.

## Technical Approach

In `main()`'s argument-parsing loop (`plugin/bin/resolve-policy.js`, the `else { keys.push(arg); }`
branch), split `arg` on `,` and push each non-empty resulting piece instead of the raw token:
`keys.push(...arg.split(',').filter(Boolean))`. This is the only change needed — every
downstream consumer (`resolvePolicyConfig`, the `--values` line-per-key mapper, the default
JSON-envelope `JSON.stringify(result)`) already operates on `keys` as a flat array of
independent lever names, so splitting earlier in the pipeline is sufficient; no other function
needs to change. Confirmed no `POLICY_KEYS` entry (`plugin/bin/lib/policy-schema.js`) contains
a literal comma, so the split cannot fracture a legitimate single key name.

### Key Files

- `plugin/bin/resolve-policy.js` — split each key-position argv token on `,` in the
  argument-parsing loop before pushing into `keys`
- `tests/bin/resolve-policy.test.js` (or wherever the existing spawn tests for this CLI live —
  locate via the "Existing resolve-policy spawn tests" acceptance criterion) — add coverage for
  the comma-joined multi-key form under both `--values` and default JSON mode

## Gotchas

- Do not special-case the split to `--values` mode only — the default JSON-envelope mode
  shares the exact same `keys.push(arg)` loop, and leaving it unsplit there would create a new
  inconsistency between the two modes rather than closing the one that exists today.
- `--all` must keep rejecting key arguments outright; don't let the comma-split accidentally
  make `--all a,b` resolve into `--all` plus two keys.
- The `model-profiles` key already has a dedicated `--values` rejection (line 90-94) since it
  has no scalar form — verify a comma-joined list containing `model-profiles`
  (`--values auto-mode,model-profiles`) still trips that same rejection after the split, not a
  silent partial resolution.

## Current State

`plugin/bin/resolve-policy.js`'s documented `--values <comma-joined-lever-list>` form
(`skills/flow/manifesto.md`'s Compute recommendations section shows it resolving several
Manifesto levers in one call) returns no output at all when invoked with a comma-joined list of
lever names, rather than either an error or a per-lever JSON envelope. Observed while manually
initializing a Pipeline Config Manifesto for a run directory dispatch had pre-minted but left
empty (no `config.yml` yet) — the documented one-call form silently produced nothing, and only
falling back to one `resolve-policy.js <lever>` call per lever (the single-key form) actually
resolved each value.

## Deliverables

Either (a) fix `resolve-policy.js` so `--values a,b,c` actually resolves a comma-joined list and
returns one JSON envelope per lever, matching what `manifesto.md`'s own worked example implies it
does, or (b) if multi-value `--values` was never actually meant to accept a comma-joined list,
correct `manifesto.md`'s Compute recommendations section so it stops showing that invocation
shape and shows the real one-call-per-lever form instead.

## Acceptance Criteria

`node plugin/bin/resolve-policy.js --values <lever1>,<lever2>,...` either returns a JSON envelope
per named lever, or `manifesto.md` no longer documents that shape as the way to resolve several
levers at once — whichever is chosen, the doc and the CLI's actual behavior agree.
