# 1919: record-snapshot: the --state all union snapshot at backlog-fetch-limit silently drops the oldest open records, and the open-count cap check cannot see it

Origin: /claude-tweaks:specify Step 1 landscape scan for the #1904 pipeline-ceremony decomposition (2026-09-05)
Defer-reason: tangential

## Current State

`_shared/record-queue-fetch.md`'s Session-scoped record snapshot fetches `gh issue list --state all --limit {backlog-fetch-limit}` (default 1000) with `bin/lib/issues/record-snapshot.js`'s `UNION_FIELDS`, newest-first. This repo has more than 1000 issues in total, so the snapshot is capped: on 2026-09-05 it returned exactly 1000 records of which 153 were open, while `gh issue list --state open --limit 1000` returned 160 — the seven oldest open records (#44, #123, #126, #127, #137, #159, #193, …) fell outside the cap because closed records newer than them fill the slots. The only truncation warning in the fetch block fires when the *open* count equals the limit (`issues.length === Number(process.env.FETCH_LIMIT)` after the `state === 'OPEN'` filter), which can never trigger in this shape — the open subset is far below the limit while the union is at it. Every consumer of the snapshot (`/specify` Step 1's Overlap Analysis and File Reference Map, `/capture`'s born-ready trust fetch, `_shared/trust-table.md`, `/help`, `/tidy`, `/backlog`, `/visualize` via the open-only narrowing) therefore audits against an incomplete open set without any signal, on any repo whose total issue count exceeds the limit.

## Deliverables

- [ ] The snapshot's read-fresh-or-fetch block checks the *union* length against the limit (`all.length === limit`) and, when at the cap, performs one additional `--state open --limit {limit}` fetch and merges any open records missing from the union (dedup by `number`) before writing the snapshot — so the open set is always complete even when the union is capped.
- [ ] The existing open-count warning stays; a second warning names the union cap when it fired: `WARNING: the --state all snapshot hit backlog-fetch-limit ({n}); open records were completed by a second open-only fetch — closed-record coverage is truncated at the {n} newest`.
- [ ] `bin/lib/issues/record-snapshot.js` exports a `mergeOpenIntoUnion(union, open)` helper (pure) so the fence's node block calls it rather than hand-rolling the merge; unit test in `tests/bin-lib/issues/record-snapshot.test.js` with a capped fixture.
- [ ] `_shared/record-queue-fetch.md`'s Session-scoped record snapshot section documents the two-fetch shape and the cap semantics in one sentence; `_shared/policy-schema.md`'s `backlog-fetch-limit` row notes that the limit bounds closed-record coverage, never open completeness.

## Acceptance Criteria

1. With a fake `gh` returning 1000 union rows (150 open) and 160 open-only rows, the snapshot file holds 1010 records, all 160 open numbers present, and the cap warning text appears on stderr.
2. With a union below the limit, exactly one `gh` call is made and no cap warning fires (today's behavior).
3. `mergeOpenIntoUnion` dedups by `number` and preserves the union's field set on merged rows.
4. `grep -c 'second open-only fetch' plugin/skills/_shared/record-queue-fetch.md` is 1.
