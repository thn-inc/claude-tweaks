# 6018: Admit driver records by risk and ceremony with the reviewer on, ending at pending-review

Surface: backend
**Related:** #5262, #5884
Risk-flags: auth

## Overview

The pipeline driver refuses every record whose risk label is not `low` and every record whose ceremony label is not `fast-lane` (or absent). In the 2026-11-18 funnel over 142 build-authorized ready records, "risk is not low" refused 57 and "ceremony is not fast-lane" refused 49 (`docs/superpowers/specs/2026-11-18-pipeline-economy-design.md`, `### The driver lane`). This record lets the driver admit both, but only with its evidence reviewer on, and makes every record admitted this way end at `pending-review` so a human merges it.

It adds one policy value, the highest risk label the driver admits (`low`, `medium` or `high`; default `low`, which reproduces today). With `express-driver-review` set to `on`, a ceremony label other than `fast-lane` no longer refuses; under the default `beyond-express` (and under `off`) it refuses as today, so every default reproduces today. A record admitted because its risk is above `low` or its ceremony is not `fast-lane` never merges on its own, even with `auto:merge`: the driver's merge step stops at `pending-review` before it launches any judgment worker. This is the pending-review mechanism the protected-path record (sibling sub-issue) reuses.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- Protected paths. The sibling sub-issue adds the protected-path mode and reuses this record's widening list and merge stop.

- The express lane (`bin/express-lane.js`, `/flow`'s express path). Its eligibility must not change: every new option is passed only by the driver and defaults to today's rule.
- Forcing `pending-review` on records admitted by the existing size and Key File widening (#5224). Those keep today's merge behaviour.
- A factory-layer ceiling for the new key. Phase 11 of the design builds the factory layer and the stricter-of rule, and this key is one it will cover.
- Running the 20-record trial (sibling sub-issue).

## Release Note

The pipeline driver can be set to take records above low risk or outside the fast-lane ceremony, with its reviewer on, and always leaves them for a human to merge.

## Technical Approach

Extend the #5224 pattern, don't add a parallel one. Eligibility applies the ceilings and the driver-only relaxations. Admission's reviewer rule decides whether the widened record needs the reviewer. `reviewRequired` turns the reviewer on for it under `beyond-express`. A single pure helper in `eligibility.js` returns the widening list from the labels, so admission, `reviewRequired` and `steps.js` read one answer.

The merge stop goes in `entry()`, not after the gate, so a widened record spends no judgment-worker launch. The detail lists the widenings in the `pending-review` event, so the human merger sees why.

### Data / API Surface

- Policy key (proposal `express-driver-max-risk`): `{ type: 'enum', values: ['low', 'medium', 'high'], default: 'low', policyOnly: true, category: 'merge-safety', tier: 'advanced' }`.
- `evaluateRecordEligibility(issue, { ..., riskCeiling, allowAnyCeremony })`: both are optional and absent for every express caller.
- `widenings({ labels, riskCeiling, anyCeremony }) -> Array<'risk'|'ceremony'>`: pure, exported from `eligibility.js`.
- `evaluateAdmission(facts)` gains `widenedBy` in its input (or computes it) and the new reviewer-off reason in `ADMISSION_REASONS`.
- `merge.js` `REASONS` gains `widened-admission`.
- `drive.js --check` verdict line: `{"admitted": bool, "reasons": [...], "widenedBy": [...]}`.

### Key Files

- `plugin/bin/lib/express/eligibility.js`: risk ceiling option, ceremony relaxation, the `widenings` helper
- `plugin/bin/lib/driver/admission.js`: reviewer rule extended to widenings, new reason
- `plugin/bin/lib/driver/review.js`: `reviewRequired` turns on for widenings under `beyond-express`
- `plugin/bin/lib/driver/steps.js`: `POLICY_KEYS`, `eligibilityOptions`, `ctx.widenedBy`, the `--check` verdict line
- `plugin/bin/lib/driver/merge.js`: `entry()` stop and the `REASONS` entry
- `plugin/bin/lib/policy-schema.js`: the new key row
- `plugin/skills/_shared/policy-schema.md`: express-driver rows moved out, pointer left
- `plugin/skills/_shared/policy-schema-express-driver.md`: new split file holding the express-driver rows plus the new key
- `tools/pipeline-cost-report/funnel.js`: `VALUE_HEADS` for any value-bearing new reason

## Gotchas

- `REASONS` in `eligibility.js` is a wire contract ("callers and reports match these verbatim"). Add new strings, never change `REASONS.risk` or `REASONS.ceremony`, because the express lane and the cost report's funnel match them.
- `allowAbsentCeremony` reads raw label names because `facets.ceremony` is null for both an absent and an unrecognised label. The new relaxation must keep refusing an unrecognised spelling for the same reason.
- `eligibilityStep` calls `reviewRequired` with the verdict's own `keyFiles` *after* eligibility, so ceremony cannot be relaxed "only when the reviewer is on" inside eligibility. Relax it in eligibility and refuse in admission's reviewer rule, exactly as #5224 does for size.
- The budget loop pre-screens with `eligibilityOptions(policy)`. Pass the new options through that one function, so the pre-screen and the step ask the same question.
- #5942 is in progress on `steps.js` and `review.js`. This record is blocked by it, so rebase onto it rather than merging around it.
- `.claude-tweaks/policy.yml` must not change here. This repository opts in through the trial sub-issue.
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(auth): …`.
- Every `express-driver-review` value is covered by the fixture matrix: with the reviewer off a widened record is refused, with it on it is admitted, except that a ceremony widening needs `express-driver-review: on` itself (under `beyond-express` a `ceremony:standard` record refuses as today). A record that is both size-widened (#5224) and risk- or ceremony-widened takes the pending-review stop for the Phase 7 widening; the size widening does not suppress it.
- `widenings()` is called for a record eligibility already admitted, so its inputs are recognised labels: `risk` when the label is `medium` or `high`, `ceremony` when a recognised `ceremony:*` label other than `fast-lane` is present and the caller passes the relaxation flag (`express-driver-review: on`); an absent ceremony label widens nothing. `widenings()` decides `risk` by scanning every `risk:*` label name, never the parsed facet, which keeps only the last match: a record carrying both `risk:low` and `risk:medium` widens, whatever the label order. An unreadable or unlabelled risk, an unrecognised ceremony and a value outside the enum refuse in eligibility and never reach it.
- The ceiling-refusal reason embeds the ceiling, so its literal string (settled at build, and distinct from `REASONS.risk`) gets a `VALUE_HEADS` entry. "Unreadable ceiling" means a non-enum value passed directly to the pure function. A policy-file typo never reaches it, because the resolver has already turned it into `low` (see the Decision paragraph).
- The `--check` verdict line only gains a `widenedBy` key. Readers must ignore unknown keys; `funnel.js` `parseVerdict` is the one in-repo reader, and a test feeds it the extended line.
- An older installed build meeting the new key in a committed `policy.yml` ignores it, and the default reproduces today. The trial sub-issue is the first to commit the key.

## Decision Rationale

- The maintainer chose `low | medium | high` on 2026-11-21. Unlike `express-driver-max-size`, `high` is allowed: every record admitted this way waits for a human merge, so the reviewer plus the human gate the risk.
- Only Phase 7's widenings (risk, ceremony, protected path) force `pending-review`. #5224's size widening keeps its merge path, since the design's "admitted by any of these" names these three.
- Defaults reproduce today (`## Policy model`: every new behaviour ships as a policy value whose default reproduces today).
- Ceremony relaxes only under `express-driver-review: on` (maintainer, 2026-11-21): the default `beyond-express` must reproduce today, and a third key for it was not wanted. The trial (#6021) sets `on`.
- The merge stop recomputes the label widenings and fails closed on a missing `ctx.widenedBy` (maintainer, 2026-11-21), so a resumed run, a separate merge invocation or a label change between admission and merge cannot take the merge path.

**Decision** (maintainer, 2026-11-22, answering plan review on draft PR #6047): an invalid `express-driver-max-risk` value falls back to `low` (Reading A). Every other driver key behaves this way, the resolver's `invalid: true` keeps the typo visible in the policy check, and the fallback never widens what the driver takes on. The spec's earlier "refuses with its own reason, never a fallback" wording is replaced above.
