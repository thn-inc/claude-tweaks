# 1469: grant-veto-window-hours: schema-valid 0 is silently overridden with no documentation (#1315 follow-up)

Defer-reason: tangential

## Current State

#1315 hardened `grant-maturation.js`'s `evaluateMaturation` so a non-positive or non-finite `vetoWindowHours` falls back to the 24h default (`vetoWindowHours > 0` instead of `>= 0`). Surfaced during #1315's final whole-branch review (Minor finding, not a merge blocker for that record): `plugin/bin/lib/policy-schema.js` declares `grant-veto-window-hours` as `{ type: 'integer', default: 24 }` with no `min`, and `isValidValue`'s integer branch accepts any integer including `0` and negatives — so `grant-veto-window-hours: 0` in `policy.yml` validates cleanly and resolves to `0`. After #1315's fix, a project that intentionally set the value to `0` (to disable the veto window) now silently gets a 24h window instead, with nothing in `_shared/policy-schema.md`, `_shared/work-record.md`, or the module's own comments documenting this floor.

## Deliverables

- Either (a) add `min: 1` to the `grant-veto-window-hours` schema entry in `plugin/bin/lib/policy-schema.js` so an operator gets validation feedback instead of a silent override, keeping the module guard as belt-and-braces, or (b) document the new hard 24h floor in `_shared/policy-schema.md`'s `grant-veto-window-hours` row and in `grant-maturation.js`'s `vetoWindowHours` parameter comment (currently reads "when absent or invalid" without noting non-positive now counts as invalid).
- If option (a) is chosen, cover the new `min` constraint with a test in the schema's existing validation test suite.

## Acceptance Criteria

- A project configuring `grant-veto-window-hours: 0` either gets explicit validation feedback (option a) or has documented, discoverable evidence that `0` is treated as invalid and floors to 24h (option b).
- If option (a) is implemented, a test asserts `0` (and negative integers) fail schema validation for this key.
