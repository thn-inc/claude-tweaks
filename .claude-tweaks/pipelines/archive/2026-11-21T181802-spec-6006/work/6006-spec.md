# 6006: Add a factory policy layer below the repository's policy.yml

Surface: backend
Risk-flags: auth, public-contract

## Overview

Adds a factory policy layer: a source of policy values that sits below a repository's `.claude-tweaks/policy.yml` and above the schema default, so one setting can apply to every repository a factory drives. Today a key resolves from the run's `config.yml`, then the repository's `policy.yml`, then the schema default, and nothing sits above the repository. Dispatch already stores variables at instance, repository and environment scope and merges them into the environment of every run it starts, so the layer is delivered as an environment variable that carries the values (it reaches cloud sandboxes, where no user file exists), with a user-level file for interactive sessions.

This record builds the layer in the canonical resolver (`resolvePolicyKeys` / `resolvePolicyConfig` and the block-key readers behind `bin/resolve-policy.js`), with a new `source: 'factory'` attribution. Readers that bypass the resolver, and driver workers' stripped environment, are the next record; the stricter-value rule for ceiling keys is the one after. The design is `docs/superpowers/specs/2026-11-18-pipeline-economy-design.md`, `## Policy model` and `## Phase 11`.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- The stricter-of-factory-and-repository rule for ceiling keys. Here every key, ceiling keys included, keeps repository over factory; the ceiling record changes that.
- Readers that read `policy.yml` without going through `resolvePolicyKeys` (`bin/lib/policy.js`'s `parsePolicy` family, `bin/hooks.sh`'s no-node `policy_verdict`, the other direct readers) and passing the variable through the driver worker's `ENV_ALLOW`. That is record #6007 "Make every policy reader see the factory layer".
- Any change to what Dispatch sets. Dispatch already merges stored variables into a run's environment.
- A factory value read from a run's `config.yml`. The run overlay keeps its place above both files.
- New policy keys. The layer carries existing keys only.

## Deliverables

- [ ] `plugin/bin/lib/policy-factory.js` (new): `readFactoryPolicy({ env, homeDir, readFile })` returns `{ raw, origin }` where `raw` is the text of the factory layer or `null`, and `origin` is `env`, `file`, `env+file` or `null`. Sources: the environment variable `CLAUDE_TWEAKS_FACTORY_POLICY`, whose value is policy text in `policy.yml`'s own format (flat `key: value` lines and indented block keys, newline-separated); and the file `~/.claude-tweaks/factory-policy.yml`. When both are present they merge per key with the environment variable winning (a flat key or a whole block key present in the variable replaces the file's). The merge runs per canonical key after `RENAMED_KEYS` alias normalization, keeping every top-level chunk of a key within one source, and `raw` is the winning chunks' text, not a re-serialization. A variable map block (`model-profiles`, `express-driver-models`) that does not parse yields to the file's block only when the file holds that key and its block parses, with its own warning (`resolve-policy: warning: {key} has invalid value "{first line}" in CLAUDE_TWEAKS_FACTORY_POLICY — using ~/.claude-tweaks/factory-policy.yml's block`); otherwise the variable's block is kept and the resolver flags it `invalid` exactly as it would a malformed `policy.yml` block. `risk-path-globs` is never judged by the reader, since its rows are validated against `risk-categories`, which only the resolver sees, so the variable's block always wins. A chunk the resolver's `parseFlatLines` cannot see (an empty value, a quoted key) does not count as present, so it never hides a file value. An empty or whitespace-only variable counts as absent. A file that does not exist is absent; any other read error is reported once on `stderr` (`resolve-policy: warning: could not read ~/.claude-tweaks/factory-policy.yml ({code}) — factory file ignored`) and the file is treated as absent, never thrown. A file that is a dangling symlink reads as absent (ENOENT, silent); a symlink to a readable file is read, because the file is the user's own and not repository content.
- [ ] `resolvePolicyKeys` accepts `factoryRaw` and adds a third source named `factory` after `policy`, parsed and alias-normalized exactly as the other two. Precedence per key becomes run-config (non-`policyOnly`) → policy → factory → schema default, and a value from it resolves `{ value, source: 'factory' }`. An invalid factory value resolves the schema default with `invalid: true` and `onInvalid` called, the same no-cascade rule the other sources follow. Both derived defaults walk the three-source list, so `autonomy` set only in the factory layer derives `housekeeping-auto-merge`.
- [ ] Block keys merge per row, repository row over factory row: `express-driver-models` (per role) and `risk-path-globs` (per category) in `policy-schema.js`, `model-profiles` (per profile) in `model-profiles/policy-fragment.js`. A block that resolves with any row from the factory layer reports `source: 'factory'` when every row came from it and `source: 'policy'` otherwise; a malformed factory block is `invalid` on its own and never drops the repository's rows; a block whose repository side is empty or malformed resolves from the factory rows with `source: 'factory'`; a block set in neither layer is unset, as today.
- [ ] `resolvePolicyConfig` and `resolvePolicy` read the layer through `readFactoryPolicy` with `deps.env` and `deps.homeDir()` (`callerDeps` already carries both), and return `factoryOrigin` beside `policySource`. `warningLines` adds one stderr note when the factory layer supplied any requested key: `resolve-policy: note — factory layer ({origin}) supplied {keys}`, in every output mode, stdout and exit code unchanged. `--all` decorates entries unchanged apart from the new `source` value. `factoryOrigin` is not added to the CLI's stdout JSON: only the stderr note carries it, and under `--all` every key counts as requested.

- [ ] `plugin/bin/lib/policy-factory.js` exports `FACTORY_REFUSED_KEYS = ['merge-authorization', 'control-mode', 'deploy-command']`, the one list of keys the factory layer may not supply (#6007 reads the same constant). A refused key present in the factory text is never applied: it resolves exactly as if the factory layer did not set it, `onInvalid` is called for it, and `warningLines` writes `resolve-policy: warning: {key} is not settable from the factory layer — ignored`, in every output mode. Why each is refused: `merge-authorization` is a per-run human pre-authorization (`policySourceExcluded`) and must never be a standing default; `control-mode` is the single human-in-control switch, which #5830 ruled is set in `policy.yml` or not at all; `deploy-command` is an executed string specific to one repository. Every other key, `autonomy` and the trust lists (`owned-owners`, `trusted-authors`) included, is settable: a factory owner choosing them for every repository is the purpose of the layer, a repository tightens `autonomy` by setting it, and #6008's ceiling rule keeps a repository from loosening a factory bound. The factory variable comes from the factory's environment, never from a pull request's content, so a base-branch-only read of a trust list keeps its guarantee.

## Release Note

Added a factory policy layer, set by an environment variable or a user-level file, that supplies policy values to every repository that does not set them itself.

## Technical Approach

The factory layer is one more raw-text source handed to the pure resolver, so every rule the resolver already applies (aliases, validation, invalid-no-cascade, `policyOnly`, derived defaults) applies to it unchanged. Reading the variable and the file is the only new I/O, and it sits in one module so the next record can reuse it for the direct readers.

Decided while specifying: the variable carries policy text in `policy.yml`'s format rather than JSON, so one parser serves both and block keys need no second encoding; the file lives in the existing `~/.claude-tweaks/` directory; the variable wins over the file per key, because Dispatch sets the variable per run and the file is the interactive fallback; block keys merge per row because a factory that sets profile efforts through `model-profiles` must not lose them when a repository overrides one profile.

### Data / API Surface

- `readFactoryPolicy({ env, homeDir, readFile }) -> { raw: string | null, origin: 'env' | 'file' | 'env+file' | null }`
- `FACTORY_POLICY_ENV = 'CLAUDE_TWEAKS_FACTORY_POLICY'`, `FACTORY_POLICY_REL_PATH = '.claude-tweaks/factory-policy.yml'` (relative to the home directory), both exported.
- `resolvePolicyKeys(keys, { policyRaw, runConfigRaw, factoryRaw, onInvalid })`; entry `source` gains `'factory'`.

## Decision Rationale

- Ceilings take the stricter value only in record #6008, so this record ships the layer alone and keeps every existing precedence test meaningful: one change per record.
- Every new behaviour in the design ships with a default that reproduces today. Here that default is "no variable, no file", so this record needs no policy key of its own.
