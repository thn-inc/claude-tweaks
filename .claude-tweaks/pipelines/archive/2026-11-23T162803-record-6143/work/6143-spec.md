# 6143: Refuse to ready or merge a pipeline PR while its run is still building

## Current State

A `pr-first` run opens a draft PR at run start (`_shared/pr-early-run-lifecycle.md`). Its body carries a `claude-tweaks-run:` marker and a phases checklist. Nothing stops another session from running `gh pr ready` and `gh pr merge` on that draft mid-run.

On 2026-11-23 PR #6061 (run `2026-11-23T062258-record-6000`, build in progress, every phase unchecked) was marked ready and merged 5 seconds later at 06:55:38Z by a session merging a batch of PRs (#6064 and #6065 went the same way). The merge closed #6000. Reconcile's post-merge then released the claim, stripped `auto:build` and archived the run as if it had finished, and the release bot posted "Shipped in v6.177.0" on #6000. #6003, which depends on #6000, was then dispatched against code that did not exist. Recovery took a reopened issue, a hand-written decision, a new draft PR (#6138) and a restarted run.

## Deliverables

1. A PreToolUse gate in `plugin/bin/lib/hooks/pre-tool-use.js`. A Bash call running `gh pr ready <n>` or `gh pr merge <n>` (any flags) is denied when PR n's body carries a `claude-tweaks-run: {id}` marker naming a run under `$RUN_ROOT/.claude-tweaks/pipelines/` that is **in flight** (defined below). The deny reason names the run and its owning session. The owning session (`run-state.json` `sessionId`) is allowed, and so is every caller when `run-state.json` records no `sessionId`. The gate fails open when the PR body, the run state or the run's phase-exit evidence cannot be read, per `docs/hooks.md`'s never-break-a-session invariant.

2. Reconcile's post-merge (`plugin/bin/lib/reconcile/post-merge.js`, `release-merged.js`) does not settle a hollow merge as a success. A merge is **hollow** when its PR's marker names a run that is in flight at reconcile time. For a hollow merge, reconcile does not release the claim as merged, strip `auto:build` or archive the run. Instead it posts one comment on the record naming the merge, and reconcile's summary reports it. Unlike the gate, reconcile fails closed. If the check cannot finish for a marker-bearing PR, that PR is held, not settled, and the summary reports it. This covers an unreadable run state or phase-exit evidence, and a throw anywhere in the hollow-merge check. The next pass retries it. A PR with no marker is not a pipeline PR and settles as today.

**In flight** (one definition, shared by both deliverables): the run's `run-state.json` is non-terminal, and its `build` or `test` phase has not finished. A phase has finished when either of these holds:
- its row in the PR's phases checklist is checked;
- the run's own `decisions.md` records that phase's exit, as the entry `bin/phase-exit.js` writes under that phase's section.

The checklist row is only a fast pre-filter. The phase-exit record decides.

## Acceptance Criteria

- [ ] Hook test: `gh pr merge 123 --squash` against a fake PR whose marker names an active run with `build` unchecked is denied; the same command from the run's owning session is allowed; an unreadable PR is allowed.

- [ ] Hook test: `gh pr ready 123` behaves the same way as the merge case above.

- [ ] Hook test: a run whose `run-state.json` has no `sessionId` is allowed. So is an active run whose `build` and `test` rows are unchecked but whose `decisions.md` records both phase exits.

- [ ] Reconcile test: a merged PR whose marker names an active run with `build` unchecked and no `build` phase-exit record leaves the claim, `auto:build` and the run directory in place, posts one comment, and appears in the summary. A run with `build` finished but `test` unfinished behaves the same.

- [ ] Reconcile test: a merged PR whose run is clean and whose phases are all checked settles exactly as today.

- [ ] Reconcile test: a merged PR whose run is still non-terminal but whose `decisions.md` records the `build` and `test` phase exits settles exactly as today, even with those checklist rows unchecked. This is the normal pr-first merge by the run's own wrap-up, and the owner merge that lands after a failed checklist refresh.

- [ ] Reconcile test: when the hollow-merge check throws or cannot read a marker-bearing PR's run state, that PR is held and reported, not settled. A PR with no marker settles as today.

## Decisions

**Decision (plan-review Q1, hollow-merge predicate):** use "run non-terminal **and** `build` or `test` not finished", evaluated at reconcile time, instead of the original "non-terminal at merge time **or** `build` unchecked". Read literally, the original holds every normal pr-first merge, because a run's own wrap-up merges while `run-state.json` is still non-terminal. `test` is included because a merge after build but before test still ships untested code. Deliverable 2 and the reconcile ACs above state the amended rule.

**Decision (plan-review Q2, checklist authority):** the checklist stays cosmetic, and the run's own phase-exit record decides whether a phase finished. Do not make the checklist authoritative or block merges on it. `_shared/pr-checklist-refresh.md` documents the row as best-effort, never a merge blocker. Its refresh can fail on a `gh` error and cannot run in a `gh`-absent sandbox. Making it a merge blocker would change a contract that live runs on older releases read, and would stop correct merges in exactly those environments. `phase-exit.js` writes the local `decisions.md` entry in the same call that flips the row, so that entry survives a failed refresh.

**Decision (plan-review follow-ups):** reconcile fails closed and the gate fails open. If reconcile's whole hollow-merge check fails, it must hold the affected PRs, never pass empty hold sets that let release and archive go ahead; that repeats #6061. The gate allows every caller when `sessionId` is absent, because with no recorded owner it cannot tell the owner from a stranger, and breaking a session is the worse failure.

## Release Note

Another session can no longer mark a pipeline's draft PR ready or merge it while its build is still running, and a merge that lands mid-build is reported instead of being treated as shipped.

## Technical Approach

### Key Files

- `plugin/bin/lib/hooks/pre-tool-use.js` — add the in-flight-run gate for gh pr ready / gh pr merge
- `plugin/bin/lib/reconcile/post-merge.js` — detect a hollow merge and skip success settlement
- `plugin/bin/lib/reconcile/release-merged.js` — do not release the claim on a hollow merge
- `tests/bin-lib/reconcile/post-merge.test.js` — hollow-merge fixtures

## Plan Review Clarifications

- Settled by plan review after an answered round: a multi-spec run's phase exits land in `{run}/spec-{N}/decisions.md`, so "the run's own `decisions.md`" is the run's `decisions.md` plus every `spec-{N}/decisions.md`, and a phase has finished when any of them records its exit. Not taken: only the parent `decisions.md` counts, which would hold a bundle's correct merge after a failed checklist refresh. (Finding: in a multi-spec run the phase-exit entries land in `{parent}/spec-{N}/decisions.md`, which a reader of the parent file alone never sees.)
- Settled by plan review after an answered round: the gate's owner is the run-state's `sessionId` only, as Deliverable 1 says ("The owning session (`run-state.json` `sessionId`) is allowed"). `dispatchSessionId` is not an owner. A dispatched run's own merge comes after its build and test exits, when the run is no longer in flight. Not taken: also treating the dispatching session as owner, which loosens the deny. (Finding: the plan widened the owner exemption to `dispatchSessionId`, which the spec does not name.)
- Settled by plan review after an answered round: a `build` or `test` row that is absent from the phases checklist, or a PR body with no phases checklist at all (an express-lane body, or a phase whose row was removed as skipped), counts as finished. Only a present, unchecked row sends the check to the phase-exit record, since the row is the pre-filter. Express-lane runs never call `bin/phase-exit.js`, so reading an absent row as unfinished would hold every express merge whose session ended before close-run. Not taken: an absent row is unfinished unless `decisions.md` records the exit. (Finding: the spec's definition lists only a checked row or a recorded exit as finished.)
