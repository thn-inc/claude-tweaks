# 4833: pr-early-open logs "reopened PR" after a gh exit 0 without confirming the PR is OPEN

Surface: infra

Origin: reflect full from #4640

Defer-reason: tangential

**Related:** #4492, #4494, #4499, #4812

## Current State

`openPrEarly` in `plugin/bin/lib/flow/pr-early-open.js` picks a CLOSED prior-attempt PR for the branch and calls `deps.gh(['pr', 'reopen', String(pick.number), '--repo', repo])`. Today "the call did not throw" is the whole success test (`reopenRejected === null`). On that test alone it logs `reopened PR #{n} for {branch} (retry)`, rebinds an adopted PR's body, records the PR in `run-state.json`, pushes, and returns outcome `reopened`. It never reads the PR's state after the reopen.

Observed on run `2026-11-01T165322-record-4640`: `decisions.md` has `AUTO 17:57:27 — log-decision: PR-early run lifecycle: reopened PR #4789 for worktree-dispatch-record-4640 (retry)`, yet `gh api repos/thn-inc/claude-tweaks/issues/4789/events` lists only `closed` (16:42:27Z) and `head_ref_deleted` (16:42:52Z), with no `reopened` event. The PR stayed CLOSED. The first PR-checklist refresh (18:37:51) was refused as a run-marker mismatch, and the phase-exit recovery at 18:39 opened a replacement draft PR #4832, about 40 minutes after the log claimed success.

The record's "defect in `deps.gh`" hypothesis was ruled out on 2026-11-01. The CLI's runner is `execFileSync('gh', args, …)` (`plugin/bin/pr-early-open.js:104`), wrapped at lines 182-189 so that it only tags timeouts and rethrows. Any non-zero `gh` exit throws, so `gh` 2.102.0 really did exit 0 on that reopen. In this code the reopen also runs before Step 2's push, so when a prior run's head branch was deleted, the head ref does not exist on the remote at reopen time. In the observed run it had been deleted at 16:42:52Z.

The create path already handles a PR it cannot see clearly. `lookForLanded` re-lists open PRs for the head after a failed `gh pr create`, and it adopts a PR that turns out to exist.

## Deliverables

1. After a non-throwing `gh pr reopen`, `openPrEarly` re-lists the branch's PRs with the existing `listPrs()` read and requires the picked PR to read `state: OPEN`. Only then does it log `reopened PR #{n} for {branch} (retry)`, rebind, record, push, and return `reopened`.
2. When the re-read shows the picked PR still not OPEN, the call takes the existing rejected-reopen path in the same invocation. `reopenRejected` is set to the picked number, so the result carries `reopenRejected` for the caller's pointer-comment repoint. One distinct `decisions.md` line names the cause: `reopen of closed PR #{n} for {branch} exited 0 but the PR still reads {state}; creating`. Then a new draft PR is created through the existing create path.
3. When the re-read itself fails (the `gh pr list` call throws or returns a non-array), the reopen is unconfirmed. It is handled like item 2, and the line says `could not confirm reopen of closed PR #{n} for {branch} ({error}); creating`. The existing create path's `lookForLanded` adopts the PR if the reopen did land. When the adopted PR is the picked prior-attempt PR, it is rebound to this run (`rebind(n, 'reopened')`) before the result returns, so a landed reopen never leaves a body naming the old run.
4. The cause of the exit 0 is researched from `gh`'s own source for the installed version (`pkg/cmd/pr/reopen` in cli/cli at the tag matching `gh --version`). Do not create, close or reopen any real PR to reproduce it. The PR that fixes this states which branch of that command's code returns 0 without reopening, or states plainly that the source does not explain it.
5. Fake-`gh` tests in `tests/bin-lib/flow/pr-early-open.test.js` cover:
   - a reopen that exits 0 while the re-list still shows CLOSED, which ends in outcome `opened` with `reopenRejected` set;
   - a re-list that throws after the reopen;
   - the existing confirmed-reopen tests, updated so their `lists` sequence returns OPEN on the confirming read.

## Acceptance Criteria

- [ ] A reopen that exits 0 with the confirming list still showing the PR CLOSED never writes the `reopened PR #{n} … (retry)` line, never records that PR, and returns outcome `opened` with `reopenRejected: {n}` and the new PR's number.
- [ ] That case's `decisions.md` contains the `exited 0 but the PR still reads CLOSED; creating` line.
- [ ] A confirming list that throws produces the `could not confirm reopen` line and reaches the create path. When the create path's `lookForLanded` then finds the picked PR OPEN, the result is that PR and its body is rebound to this run.
- [ ] A reopen whose confirming list shows OPEN behaves exactly as today: the same log line, rebind, record, push, and `reopened` outcome. The existing reopen tests pass with only their `lists` fixtures extended.
- [ ] Removing the post-reopen confirmation turns the CLOSED-after-reopen test red. The red run is quoted in the PR.
- [ ] The fixing PR's description records the source-level finding for item 4, or says the source does not explain it.
- [ ] `npm test` passes.

## Release Note

Stop the early draft-PR step from reporting a reopened PR that GitHub never reopened. It now opens a fresh draft instead.

## Technical Approach

- In `openPrEarly`'s CLOSED branch, after the `try { deps.gh(['pr', 'reopen', …]) }` succeeds, call `listPrs()` inside its own try. Treat `find((p) => p.number === pick.number && p.state === 'OPEN')` as the confirmation. On no match or a throw, set `reopenRejected = pick.number` and log the matching item 2 or item 3 line. The block that follows then skips straight to the create path, as it does for a thrown reopen.
- The existing `if (reopenRejected !== null) log('reopen of closed PR … was rejected; creating')` line must not double-log for the new cases. Keep one line per cause.
- For item 3's rebind, compare `created.number` with the remembered `pick.number` after the create path. When they match and the PR came from `lookForLanded`, run `namesOtherRun` and `rebind` on it.
- Tests use the suite's existing `harness({ lists: [...] })` sequence to return OPEN, CLOSED or an Error on the confirming read.

### Key Files

- `plugin/bin/lib/flow/pr-early-open.js` — confirm OPEN with a `listPrs()` re-read after a non-throwing reopen; route an unconfirmed reopen to the create path with its own `decisions.md` line; rebind a landed picked PR
- `tests/bin-lib/flow/pr-early-open.test.js` — CLOSED-after-reopen and failed-confirmation cases; extend the existing reopen tests' `lists` fixtures

## Gotchas

- **`plugin/bin/pr-early-open.js` needs no change.** Its runner already throws on any non-zero exit (Current State). Item 4 can still find that `gh` returns 0 without reopening, but that is `gh`'s behavior, and the state read is the fix either way.
- **Don't reproduce against the real repo.** Opening, closing and reopening throwaway PRs to watch `gh` writes public state and notifications. Item 4 is source research only.
- **The reopen still runs before the push.** Moving the push ahead of the reopen could change whether GitHub accepts a reopen whose head ref was deleted, but it also changes the push-then-create order the existing tests pin. That is out of scope here. The confirmation makes the order safe either way.
- **The phase-exit recovery that opened #4832 later is a separate path.** This record keeps its behavior unchanged. After this fix it should no longer be needed for this case.
