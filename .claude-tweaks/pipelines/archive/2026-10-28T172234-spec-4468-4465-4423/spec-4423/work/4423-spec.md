# 4423: Claim step re-claims a TTL-expired claim whose run still has an open draft PR, so /flow #N rebuilds finished work

Origin: reflect full from #3315
Defer-reason: tangential

## Current State

`plugin/bin/lib/issues/claim-store.js`'s `tombstoneInFlightPr` is the only in-flight-PR check in `/flow`'s Step 2.8 claim (`plugin/bin/lib/claim-targets/claim-targets.js:454`). It runs only for a `pr-opened:` tombstone. A claim whose 72h TTL expired while its run was still mid-pipeline classifies `'stale'` and is re-claimed through a conditional write, with no PR check at all.

#3315 is the observed case. Dispatch's first call finished the build and opened draft PR #3927 (2026-10-22). The second call never ran, and the claim expired on 2026-10-25. A `/claude-tweaks:flow #3315` with `build` in the step list would have minted a fresh run, re-claimed the stale claim, and rebuilt from scratch alongside the open PR. `steps-and-gates.md`'s case-5 resume check only applies when `build` is absent from the step list. `/tidy`'s needs-decision comment on #3315 (2026-10-26) also proposed releasing the stale claim without naming the open PR. The 2026-10-26 run caught this only through a manual `gh pr list` before claiming.

## Deliverables

- In the stale branch of `claim-targets.js`, before the conditional write, look for an open PR that carries the stale claim's `runId` in its `claude-tweaks-run:` marker. When one exists, stop with the same in-flight card and resume routing the `pr-opened:` tombstone case already uses.
- `/tidy`'s stale-claim release proposal names an open marked PR when one exists, and recommends resuming its `### Resume` line rather than a plain release.

## Acceptance Criteria

- A claim-targets test: a stale blob whose `runId` matches an open PR's run marker returns the in-flight envelope (exit 3) and writes nothing. A stale blob with no such PR still re-claims as it does today.
- A tidy test: the stale-claim needs-decision proposal for a record with an open marked PR names the PR and its resume command.

## Release Note

`/flow` no longer starts a duplicate build for a record whose earlier run's claim expired while that run's draft PR was still open. It points you at the existing PR's resume command instead.

## Build Notes (architecture alignment — Beneficial deviations)

- **Contract sweep beyond Key Files.** The MCP open-PR listing is a second documented PR-read exception, so `_shared/github-write-transport.md` and `dispatch/mcp-transport.md` were reworded to stop calling `pull_request_read` the only one. The in-flight stop now also comes from a stale claim, so `dispatch/settle-and-merge.md`, `dispatch/resume-confirmation.md` and `flow/claim-targets.md` were updated. `tidy/collection-routing.md` and `tidy/actions-github-issues.md` were updated to carry the new Yours routing.
- **A failed stale check is visible, still fail-open.** `staleClaimInFlightPr` takes an optional `onError` callback, and any error a callback throws is swallowed. `claim-targets.js` uses it to write one stderr warning and then reclaims. The spec's fail-open behavior is unchanged.
- **Tidy never releases on a failed listing.** A failed open-PR listing (on whichever transport ran) degrades to Manual review with a SKIP note, never an unchecked Release. A Release writes a `swept:` tombstone that neither in-flight check sees, which would reopen the gap this record closes.
- **Untrusted Resume line is shape-checked.** The Yours row renders `Resume open PR #{number} ({url}) — {line}` only for a `PIPELINE_RUN_DIR="…/{runId}" /claude-tweaks:flow …` line under the body's `### Resume` heading whose run-dir basename equals the matched `runId`. Otherwise it renders `Resolve open PR #{number} ({url}) before any release`.
- **No duplicate Yours rows.** A `[claim]` Resume/Resolve row for `#{n}` supersedes `_shared/github-pr-scan.md` item 10's `[unsettled]` row for the same `#{n}`. The rule lives in `tidy/collection-routing.md`; item 10 is unchanged.
