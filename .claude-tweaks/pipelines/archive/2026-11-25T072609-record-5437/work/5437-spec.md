# 5437: verify.js CI source: one transient gh timeout drops every CI-sourced suite to a full local run

Surface: backend
Risk-flags: none

## Current State

`verify.js --scope`, under a declaration with a `ci` block, takes each CI-declared suite's verdict from the PR's CI job on HEAD (`plugin/bin/lib/verify/ci-source.js`'s `fetchCiVerdict`, #4347). Every `gh` read there goes through the local `gh(args, timeout = GH_TIMEOUT_MS)` helper, which calls the injected `runner` exactly once. `GH_TIMEOUT_MS` is 5 s (`plugin/bin/lib/shared-primitives.js`), and the job-log read uses `LOG_TIMEOUT_MS` (30 s). Only `ENOENT` (→ `gh-unavailable`) and a missing commit (HTTP 404/422 → `head-not-pushed`) are classified. Every other error, a timeout included, becomes `CiFallback('gh-error: …')` at once, and the suite runs locally, or, under `localRuns: "on-request"`, the run exits 3 with no verdict.

Observed in a consumer project (plugin 6.167.0): one `spawnSync gh ETIMEDOUT` on the first read (`repos/{owner}/{repo}/commits/{sha}/pulls`), on a machine loaded by sibling sessions, sent all three CI-declared suites to a local run (`CI: <suite> — ran locally (gh-error: spawnSync gh ETIMEDOUT)`). The local core run took about 6 minutes and failed 3 timing-sensitive tests in a file the branch never touched, while the PR's CI on the same sha was green. An identical re-run minutes later took all three suites from CI and passed. Avoiding that local run is the reason the CI source exists (`plugin/skills/test/ci-source.md`: 55+ min locally vs 3.5 min in CI).

## Deliverables

1. In `fetchCiVerdict`, a `gh` read that fails with a timeout is retried before it counts as a failure. A timeout is an error whose `code` is `ETIMEDOUT`, or which carries a non-null `signal` (the child was killed when its `timeout` elapsed). At most 3 attempts in total (`GH_MAX_ATTEMPTS = 3`), with backoff waits of 1 s and then 2 s (`GH_RETRY_BACKOFF_MS = [1000, 2000]`). The waits go through the existing injected `sleep`, so tests never sleep for real. The retry lives in the one `gh` helper, so it covers every read: the PR lookup, the PR detail read, each poll's runs and jobs reads, and the job-log read, including the read that drops `--allow-escape-sequences`. The helper becomes `async`, and every call site awaits it.
2. Only timeouts are retried. `ENOENT` still throws `gh-unavailable` on the first attempt. A missing commit (HTTP 404/422) still yields `head-not-pushed` with no retry. Any other error (an HTTP 4xx or 5xx response, unparseable JSON) keeps today's immediate handling.
3. When a read needed more than one attempt and still failed, its `gh-error` fallback reason names the attempt count: `gh-error after {k} attempts: {errText}` (e.g. `gh-error after 3 attempts: spawnSync gh ETIMEDOUT`). `{errText}` is the last attempt's error, so a timeout followed by an HTTP 500 reports `gh-error after 2 attempts: HTTP 500 …`. A read that failed on its single attempt keeps today's exact text, `gh-error: {errText}`. The PR-detail read's errors are swallowed today, and they still are, after its retries.
4. `plugin/skills/test/ci-source.md`'s Fallback reasons table: the `gh-unavailable` / `gh-error: …` row states that a timed-out read is retried up to 3 attempts first, and that the reason then reads `gh-error after {k} attempts: …`.
5. Unit tests in `tests/bin-lib/verify/ci-source.test.js`, using the existing fake-runner and fake-sleep seams (see Acceptance Criteria).

## Acceptance Criteria

- A stubbed runner that throws an `ETIMEDOUT` error once on the `commits/{sha}/pulls` read and then returns valid JSON for every read yields `used: true`. The fake `sleep` records exactly one wait, of 1000 ms, before the second attempt.
- A runner that throws `ETIMEDOUT` on every attempt of the first read yields `used: false` with `fallback` exactly `gh-error after 3 attempts: spawnSync gh ETIMEDOUT` (the stub's error message). The runner is called 3 times for that read, and the fake `sleep` records waits of 1000 then 2000 ms.
- A runner whose error has `signal: 'SIGTERM'` and no `code` is retried the same way.
- A runner that throws `ENOENT` yields `fallback: 'gh-unavailable'` after exactly one runner call, with no `sleep`.
- A runner that throws an HTTP 422 `No commit found` error yields `fallback: 'head-not-pushed'` after exactly one runner call.
- A runner that throws a non-timeout error (stderr `HTTP 500`) on the first read yields `fallback` beginning `gh-error: ` (no attempt count) after exactly one runner call.
- A timeout on one poll read (the runs list), followed by success, does not end the wait: the poll completes and the verdict is `used: true`.
- The full `tests/bin-lib/verify/` suite passes.

## Release Note

Retry a timed-out GitHub read up to three times before a CI-sourced verification falls back to running the suite locally.

## Technical Approach

Inside `fetchCiVerdict`, replace the synchronous `gh` closure with an async one that loops up to `GH_MAX_ATTEMPTS`: call `runner(args, { cwd, timeout })`. On `ENOENT`, throw `CiFallback('gh-unavailable')` as now. On a timeout (`isTimeout(err)`: `err.code === 'ETIMEDOUT' || (err.signal != null)`) with attempts left, `await sleep(GH_RETRY_BACKOFF_MS[attempt - 1])` and try again. Otherwise set `err.ciAttempts = attempt` and rethrow. A small `ghErrorReason(err)` builds `gh-error after {k} attempts: …` when `err.ciAttempts > 1`, else `gh-error: …`. Use it at the two sites that build a `gh-error` reason today: the pulls-read catch and the outer catch. `ghJson` becomes async (`await gh(args)`). Every `ghJson`/`gh` call site gains `await`, the escape-flag fallback in the log read included. Export `GH_MAX_ATTEMPTS` and `GH_RETRY_BACKOFF_MS` so tests assert against the constants. Backoff time counts toward `waitedMs` naturally, since `now()` is read at fallback time.

### Key Files

- `plugin/bin/lib/verify/ci-source.js`: async `gh` helper with timeout-only retry, `ghErrorReason`, exported retry constants
- `tests/bin-lib/verify/ci-source.test.js`: retry, no-retry and reason-text cases
- `plugin/skills/test/ci-source.md`: Fallback reasons row for `gh-error` names the retry

## Gotchas

- Decided while shaping: 3 attempts total with 1 s / 2 s backoff, retrying timeouts only. A loaded machine is the observed cause, and a short backoff costs seconds against a 6-55 minute local run. Non-timeout errors are not transient enough to justify the wait.
- The job-log read has a 30 s timeout, so its worst case grows to about 93 s. That is still far below a local suite run. A green job whose log never arrives still stands without a log, as today.
- `verify.js` itself does not change: it already awaits `fetchCiVerdict`. A parallel lane (`ct-verify-stamp`) is editing `verify.js`'s stamp and slot code, so keep this change inside `ci-source.js` to avoid overlap.
- Use the injected `sleep` and `now` in tests. A real backoff would add 3 s per timeout case to the suite.
- #5657 moves every `gh` spawn, `ci-source.js`'s `defaultRunner` included, onto a shared `makeGhRunner`. This record's retry sits above the runner, in `fetchCiVerdict`'s `gh` helper, so either order works, but whichever lands second takes a catch-up merge in `ci-source.js`. #5095 raises the 5 s `gh` default. That lowers how often the retry fires and does not replace it, since a loaded machine can stall any single call.

## Original request

verify.js CI source: one transient gh timeout drops every CI-sourced suite to a full local run

`verify.js --scope` with a `ci` block takes each declared suite from the PR's CI job. In `bin/lib/verify/ci-source.js`, every `gh` read goes through `gh(args, timeout = GH_TIMEOUT_MS)` with no retry. Any error other than ENOENT or a missing commit becomes `CiFallback('gh-error: …')`. One `spawnSync gh ETIMEDOUT` on the first read (`repos/{owner}/{repo}/commits/{sha}/pulls`) therefore sends the suite to a full local run.

Observed in a consumer project (plugin 6.167.0):
- All three CI-declared suites printed `CI: <suite> — ran locally (gh-error: spawnSync gh ETIMEDOUT)`.
- Sibling sessions had the machine loaded. The local core run took about 6 minutes and failed 3 timing-sensitive tests in a file the branch never touched.
- The PR's CI run on the same sha was green.
- An identical re-run minutes later took all three suites from CI and passed.

The fallback cost a long local run plus a false red result the caller had to sort out. Avoiding that cost is the reason the CI source exists (ci-source.md: 55+ min local vs 3.5 min in CI).

**Proposed:** on a timeout (`ETIMEDOUT` or a signal), retry the `gh` read once or twice with a short backoff before falling back. Name the retry in the `fallback` reason, e.g. `gh-error after 3 attempts: spawnSync gh ETIMEDOUT`. Other error classes keep today's immediate fallback.

**Acceptance:**
- A stubbed runner that throws ETIMEDOUT once, then returns valid JSON, yields `used: true`.
- A runner that times out on every attempt yields `fallback: 'gh-error …'` naming the attempt count.
- ENOENT still yields `gh-unavailable` with no retry.
