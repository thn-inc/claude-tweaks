# 1596: Harden or mechanically enforce the subagent-output-contract's status-line-first rule

Title: Harden or mechanically enforce the subagent-output-contract's status-line-first rule
Type: task

# Ledger item 20 (from #903 review, reflect full-mode near-miss, CAUSAL: systemic)

**Origin:** ledger resolve gate, spec #903 wrap-up reflect (full mode)
**Defer-reason:** tangential

## Current State

During #903's review, 2 of 8 dispatched Step-3 lens agents violated
`plugin/skills/_shared/subagent-output-contract.md`'s status-line-first rule — each led with a
confirmatory sentence before its `DONE_WITH_CONCERNS` status word, the exact "WRONG" example the
contract itself calls out. This was caught only via `friction-events.js`'s `contract-violation`
log (`bin/lib/hooks/`'s detection), not by the dispatching agent at the time — no re-prompt was
issued, though the contract requires one on format violation. No actual harm resulted this run
(findings were still extracted correctly downstream), but the rule currently has no mechanical
enforcement at the point a dispatching agent consumes a subagent's reply — it relies entirely on
that agent's own per-notification vigilance, which failed twice in a single 8-agent dispatch here.

## Deliverables

- Either: strengthen the contract's own prompt language (a stronger negative example, or moving
  the status-line instruction to be even more prominent), or add a mechanical check the dispatcher
  is instructed to run against every subagent reply before treating its content as valid (does the
  literal first line match the required vocabulary exactly).
- Consider whether `friction-events.js`'s existing `contract-violation` detection could be
  surfaced back to the dispatching agent in-run (rather than only visible via a later
  Friction-lens reflect pass), closing the loop faster.

## Acceptance Criteria

1. A future dispatch of 8 similarly-prompted lens agents produces zero unremediated
   `contract-violation` events, OR every violation triggers an actual re-prompt per the contract's
   existing (but unenforced) rule.

_Filed by `ledger resolve gate` via specShapedBody._

## Blocked / Future Work

The Deliverables' second bullet ("Consider whether `friction-events.js`'s existing
`contract-violation` detection could be surfaced back to the dispatching agent in-run") and a
stronger mechanical-enforcement option (forcing a violating subagent to retry via the
`SubagentStop` hook's own decision-control output, if `permissionDecision`/`permissionDecisionReason`
is genuinely supported for that event — unconfirmed this run, two lookups disagreed) are not
implemented here. This build ships the two changes that don't depend on unverified hook-platform
behavior: an `agent_type`-based exemption fix to the existing detector (removing a real
false-positive source), and moving the contract's negative example into the literal dispatch
template every subagent's own prompt now carries. Filed as a follow-up rather than guessed at.
