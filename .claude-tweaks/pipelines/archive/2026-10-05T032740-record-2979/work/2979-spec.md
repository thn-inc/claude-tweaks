# 2979: Add the impeccable-engine module and CLI: resolve, run, output-shape validators

Surface: infra

## Overview

Add one module that every `design-wrapper` consumer uses to find and run Impeccable's engine, replacing the per-mode `.mjs` script resolution that broke when Impeccable 4.2.2 retired those scripts. From 4.2.2 onward `skills/impeccable/scripts/` ships a POSIX launcher, `scripts/impeccable` (plus `impeccable.cmd`), for a self-contained engine binary with its own version line (plugin 4.2.2 → engine 0.1.3, 4.3.1 → 0.1.5, 4.4.0 → 0.1.6, 4.5.0 → 0.1.11, read from each install's `VERSION` file).

The module gates on output shape, not on a pinned version: it runs whatever engine the active install provides, validates each verb's output against its documented shape, and reports a named failure on a mismatch. It never downloads anything. This is the first unit of the migration in the parent record; units for Layer 0, `doctor`, `explore` and the direction contract all call this CLI.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Changing any skill prose — the consumer rewrites are separate sub-issues of the same parent.
- The `live-*`, `detect`, `comp-spec`, `context` and other engine verbs. `live` mode needs only skill resolution; `test` mode keeps its separate `impeccable-cli` contract.
- Re-pinning the manifest, re-recording fixtures or rewriting `tests/impeccable-plugin-contract.test.js` (the closing sub-issue owns those).
- Supporting Impeccable installs older than 4.2.2 — they resolve to `upgrade-required`.

## Prerequisites

None.

## Current State

- Resolution today is prose only: `plugin/skills/design-wrapper/impeccable-plugin.md:48` documents `resolveImpeccablePlugin({searchRoot}) -> {root, version} | null`, an exact-pin glob over the plugin cache, and its script-path table (`impeccable-plugin.md:67-69`) points at `context-signals.mjs`, `doctor.mjs` and `concept-seed.mjs`, none of which exist at 4.2.2+.
- Seam pattern to follow: `plugin/bin/link-records.js` (`// argv -> exit code. All I/O through deps so tests never touch gh or git.`, line 57) over `plugin/bin/lib/issues/link.js`.
- Install metadata: `~/.claude/plugins/installed_plugins.json` carries one `impeccable@impeccable` entry per scope; on the maintainer machine (2026-10-04) user scope is 4.4.0 and this repo's project scope is 4.5.0. Engines are cached under `~/.impeccable/bin/<VERSION>/impeccable`; that cache holds 0.1.0, 0.1.3, 0.1.5 and 0.1.6, not 0.1.11.
- Launcher resolution order (read from the 4.4.0 launcher text): `$IMPECCABLE_BIN`, sibling `bin/<os>-<arch>/impeccable`, `~/.impeccable/bin/impeccable` (probe-validated), `~/.impeccable/bin/<VERSION>/impeccable`, `impeccable` on PATH (probe-validated), then a network download from `github.com/pbakaus/impeccable/releases` verified by a `.sha256` sidecar. `IMPECCABLE_LAUNCHER_PROBE=1` disables the download and exits 127 when nothing is found. `engine-probe` prints `impeccable-engine <version>`.
- Tests: `tests/bin-lib/` holds one directory per module (for example `tests/bin-lib/docs-health/`), using `node --test` with temp directories.

## Deliverables

- [ ] `plugin/bin/lib/impeccable-engine/index.js` exporting `resolve(opts, deps)` and `run(verb, args, opts, deps)`, both never throwing — every failure is a returned value.
- [ ] `resolve`: (1) read `installed_plugins.json` and select the `impeccable@impeccable` entry by scope precedence. A project-scope entry matches when `path.relative(realpath(projectPath), realpath(mainCheckoutRoot))` is empty or does not start with `..` and is not absolute; among several matching project-scope entries the longest `projectPath` wins; with no matching project-scope entry, the user-scope entry is used; with neither, `{ok: false, reason: "not-installed", fix: "/plugin install impeccable@impeccable (Impeccable 4.2.2 or later)"}`. An unreadable or malformed `installed_plugins.json` also returns `not-installed`, with `detail` naming the parse error; (2) missing `<installPath>/skills/impeccable/scripts/impeccable` → `{ok: false, reason: "upgrade-required", fix}`; (3) run `IMPECCABLE_LAUNCHER_PROBE=1 <launcher> engine-probe`, parse `impeccable-engine <version>`; exit 127 → `{ok: false, reason: "engine-not-installed", fix}` where `fix` is the literal command `<launcher> engine-probe` to run once with network access; (4) success → `{ok: true, pluginRoot, launcher, pluginVersion, engineVersion, scope}`, where `pluginRoot` is the entry's `installPath` — `native-routing.md` and `review` mode derive upstream file paths (`reference/ios.md`, `agents/impeccable-finish-reviewer.md`) from it.
- [ ] `run` for exactly four verbs, always with `IMPECCABLE_LAUNCHER_PROBE=1`, the project root as cwd, and a timeout of 60 000 ms (overridable through `opts.timeoutMs`; the process is killed when it expires): `signals` (JSON; validated against the Layer 0 field table in `impeccable-plugin.md` — top-level `setup`, `critique`, `git`, `devServer`, and `setup.{hasProduct, productPath, hasDesign, designPath, hasCode, platform}` with their documented types); `doctor` (`doctor --json` only — `--fix` is rejected by the module itself; validated as JSON with a `findings` array whose every item is an object with a string `severity` — deliberately shallower than `signals`, because the field-by-field shape `/tidy` depends on is established by the `doctor` sub-issue's real capture, which extends this validator); `concept-seed` (passes through only `--scope`, `--mode`, `--from`, `--candidate-count`; validated as text whose first non-empty line matches the unanchored `/CONCEPT SEED \(key: [^)]+\)/`, so a leading scope word such as `SURFACE` is allowed); `surface-brief` (`surface-brief read <target>` only; validated as text, returned verbatim).
- [ ] Failure values from `run`: `shape-mismatch` (names the first failing field in the Layer 0 field table's declaration order, or the failing line), `exec-failed` (exit code plus the last 20 lines of stderr), `timeout`, or a `resolve` failure passed through unchanged.
- [ ] `plugin/bin/impeccable-engine.js` CLI: `resolve` and `run <verb> [args...]`, printing one JSON envelope to stdout. Exit 0 for every resolved outcome, `ok: false` included (failures are data the caller branches on); exit 2 only for a usage error (unknown verb, `--fix`, an argument outside a verb's allowlist, or any argument after `resolve`).
- [ ] Unit tests under `tests/bin-lib/impeccable-engine/` covering every `resolve` outcome and every `run` failure value with fake launchers (small shell scripts) in `fs.mkdtempSync` directories and a fake `installed_plugins.json` — never a real binary, never the real plugin cache.
- [ ] `docs/plugin-structure.md` registers the module and the CLI.

## Release Note

Added an internal helper that finds and runs the Impeccable design engine without ever downloading it, as the base for restoring design checks on Impeccable 4.2.2 and later.

## Technical Approach

Pure logic over injected `deps` (`readFile`, `exists`, `spawn`, `homedir`, `mainCheckoutRoot`), following `plugin/bin/link-records.js`'s `run(argv, deps)` seam so tests never touch the real filesystem layout or a real engine. Validators are plain functions in the same module, one per verb, each returning `{ok}` or `{ok:false, field}`.

### Data / API Surface

- `resolve() -> {ok:true, pluginRoot, launcher, pluginVersion, engineVersion, scope:"project"|"user"} | {ok:false, reason:"not-installed"|"upgrade-required"|"engine-not-installed", fix}`
- `run(verb, args) -> {ok:true, value} | {ok:false, reason:"shape-mismatch"|"exec-failed"|"timeout"|<resolve reason>, detail, fix?}` — `value` is the parsed JSON for `signals`/`doctor`, the raw text for `concept-seed`/`surface-brief`.
- CLI: `impeccable-engine.js resolve`, `impeccable-engine.js run <signals|doctor|concept-seed|surface-brief> [args]`.

### Key Files

- `plugin/bin/lib/impeccable-engine/index.js` — new module: resolve, run, validators
- `plugin/bin/impeccable-engine.js` — new CLI wrapper
- `tests/bin-lib/impeccable-engine/resolve.test.js` — new resolve-outcome tests with fake installs
- `tests/bin-lib/impeccable-engine/run.test.js` — new run/validator tests with fake launchers
- `docs/plugin-structure.md` — register the module and CLI
- `plugin/skills/design-wrapper/impeccable-plugin.md` — read only: the Layer 0 field table the `signals` validator encodes

## Gotchas

- `signals`, `context` and `concept-seed` ignore `--help` and execute; `concept-seed` contacts Impeccable's catalog service. Never call them with `--help` expecting usage text, in code or in tests.
- `IMPECCABLE_LAUNCHER_PROBE` is internal to Impeccable's launcher. The closing sub-issue adds a manifest assertion on the launcher text so an upstream change becomes visible. If upstream removes it, the fallback is to probe the cached binary paths directly (`IMPECCABLE_BIN`, the sibling binary, `~/.impeccable/bin/<VERSION>/impeccable`).
- ASSUMPTION — verify at build: Claude Code selects a project-scope plugin install over the user-scope one for sessions inside that project, and records `projectPath` as the main checkout (not a `.claude/worktrees/*` path) — via Claude Code's plugin documentation or a `/plugin` listing from the main checkout and from a worktree; record the evidence in the module's header comment. If either is false, implement the observed rule instead, record it the same way, and update this record's AC3 cases to match.
- "Never download" covers the engine binary only. Network calls the engine makes itself while running a verb (`concept-seed` contacting Impeccable's catalog service) are upstream behaviour, documented by the consumers, not blocked here.
- The failure-reason values (`not-installed`, `upgrade-required`, `engine-not-installed`, `shape-mismatch`, `exec-failed`, `timeout`) are a contract: sibling sub-issues document and test against them, so export them as a frozen list and treat any rename or addition as a breaking change for those consumers.
- ASSUMPTION — verify at build: `concept-seed --scope direction` prints a header matching `/CONCEPT SEED \(key: /` like the observed `SURFACE CONCEPT SEED (key: …)` for `--scope surface` — via one real run on an install whose engine is cached (4.4.0 at user scope today). If it does not, widen the validator to the observed header and record the literal output in the module's header comment.
- The engine is cached per engine version: in this repo (project scope 4.5.0, engine 0.1.11 not cached) `resolve` returns `engine-not-installed` until 4.5.0's launcher has run once with network access. That is a correct result, not a bug.
- Use `node --test 'tests/bin-lib/impeccable-engine/*.test.js'` (glob form); a bare directory argument fails on node 22.

## Decision Rationale

- **Engine only.** The `.mjs` path served exactly one version (4.0.2); keeping it would mean two code paths for one legacy pin. Installs without the launcher get a clean `upgrade-required` skip.
- **Gate on output shape, not version.** The engine version moves faster than the plugin (four engine versions across four plugin releases), so a version pin would break on every release; shape validation fails only when the contract actually changes.
- **Never download.** A design-review helper fetching binaries from the network as a side effect is unacceptable in cloud sandboxes and Routines; an absent engine degrades with a paste-ready fix instead.
- **One module plus CLI.** Rejected: prose-only binding (shape checks no test can run, resolution restated in three modes) and per-mode helpers (three copies of the resolver).
