# 2580: Release notes: authoring contract

Surface: infra

## Overview

Every merged record should contribute one plain-language, verb-first note to
the release that ships it — the way Claude Code's own GitHub releases already
read ("Added a visible warning when memory usage is critical…", "Fixed
sessions getting stuck endlessly retrying…"), never a raw conventional-commit
subject or an internal module name. This sub-issue is the foundational unit
of that design: it makes `## Release Note` an unconditionally-required spec
section and threads it through the composer every merge site already calls,
so no later unit has anything to build against until this one lands.

`plugin/bin/lib/release/subject.js`'s `composeSubject` is, per its own header
comment, "the ONE merge-subject/body composer every merge site calls" — pr-first
squash merges and all four local-merge call sites. Adding a required
`releaseNote` parameter here, validated the same way `breaking`/
`migrationNote` already are, is the single contract change every one of those
call sites inherits without changing its own logic.

**Complexity:** Medium
**Estimated tasks:** 8

## Non-Goals

- Retroactively backfilling notes for already-merged records — a record
  merged before this ships has no note; the renderer (Unit 2/Unit 3, not this
  sub-issue) skips it rather than erroring.
- Grouping the public list under type-derived headings ("Features"/"Bug
  Fixes") — out of scope for this authoring-contract unit; the flat-list
  rendering decision belongs to the rendering units.
- Enriching or rewording the note automatically at release time (e.g. an LLM
  pass over merged PRs) — the note is authored once, at spec time, by whoever
  holds the record's context.
- Anything in `plugin/bin/release.js` / `plugin/bin/lib/release/{compose,run,
  status,unnamed-records,mirror}.js` — that tooling is retiring under #2259;
  building this into it would be thrown away the moment #2259 lands.
- Rendering every record's note in a multi-record bundle merge. A bundle
  (`compose-subject.js` invoked with several `--fixes` numbers producing one
  commit) still requires every record in it to carry a non-empty
  `## Release Note` section, but only the subject record's note is threaded
  through into the rendered `Release-Note:` trailer — matching how `summary`
  already behaves for bundles today. Solving that fully (e.g. multiple
  `Release-Note:` lines per commit) is out of scope for this decomposition.

## Current State

- Spec authoring: `plugin/skills/specify/spec-template.md` composes a fixed
  set of sections into a record's body (`## Current State`, `## Deliverables`,
  `## Acceptance Criteria`, …) and conditionally stamps `## Breaking Change`
  when the `breaking` label is set. There is no `## Release Note` section
  today.
- Structural check: `plugin/skills/_shared/work-record.md`'s spec-shaped-body
  check (`plugin/bin/lib/compose-record/compose.js`'s `validateShaped`,
  `REQUIRED_SECTIONS = ['Current State', 'Deliverables', 'Acceptance
  Criteria']`) verifies only those three sections are present and non-empty.
- Composer: `plugin/bin/lib/release/subject.js`'s `composeSubject({ ...,
  breaking, migrationNote })` already throws `ComposeSubjectError` on an
  empty/missing `migrationNote` when `breaking` is set, and inserts a
  `BREAKING CHANGE:` paragraph into the commit body. There is no
  `releaseNote` parameter and no `Release-Note:` paragraph today. **Verified
  current paragraph order** (`composeSubject`'s `paragraphs` array, in
  order): summary (when present) → `[{tag}]` (when present) →
  `Fixes #n` line(s) → `BREAKING CHANGE: {note}` (when `breaking`) — the
  `BREAKING CHANGE:` paragraph is pushed **last**, after `Fixes`, not
  directly after the summary/tag paragraph.
- CLI wrapper: `plugin/bin/lib/compose-subject.js` derives `composeSubject`'s
  inputs from a GitHub record via `gh issue view`, using a generic
  `extractSection(body, heading)` helper (already parameterized by heading
  text — the same function this design reuses, not a hardcoded one) to
  derive `migrationNote` when the `breaking` label is present, and fails
  loudly with the literal message
  `` `compose-subject.js: breaking is set on #${numbers} but the record carries no non-empty "## Breaking Change" section` ``
  when that section is absent or empty on a `breaking`-labeled record. There
  is no equivalent `releaseNote` derivation today. `compose-subject.js` also
  supports composing a **bundle** — multiple record numbers in one call
  (`opts.numbers`), with `subjectRecord = records[0]` — where `summary` is
  derived from `subjectRecord.body` only, while `migrationNote` is
  aggregated (joined) across every `breaking`-labeled record in the bundle.
- Tests: `tests/bin-lib/release/subject.test.js` and
  `tests/bin-lib/compose-subject.test.js` cover the existing
  `breaking`/`migrationNote` validation and extraction paths respectively.
  `tests/merge-subject-composer-conformance.test.js` pins `composeSubject`'s
  exact output shape (paragraph ordering, footer text) against a byte-level
  fixture.

## Deliverables

- [ ] Add `## Release Note` to `plugin/skills/specify/spec-template.md` as an
      unconditionally-required section (alongside Current State/Deliverables/
      Acceptance Criteria, in the same body-template block those three live
      in), documented as one plain-language, verb-first sentence with no
      record numbers, file paths, or internal identifiers — with an example
      matching the file's existing example style (mirror the file's own
      Example paragraph pattern used for other sections).
- [ ] Extend `plugin/skills/_shared/work-record.md`'s spec-shaped-body check
      description and `plugin/bin/lib/compose-record/compose.js`'s
      `REQUIRED_SECTIONS` array to include `'Release Note'` — a record with a
      missing or empty `## Release Note` section fails `validateShaped` the
      same way a missing `## Current State` does today.
- [ ] Add a required `releaseNote` string parameter to
      `plugin/bin/lib/release/subject.js`'s `composeSubject`: throws
      `ComposeSubjectError` citing the record number when `releaseNote` is
      empty, missing, or not a string — unconditional, unlike `breaking`/
      `migrationNote`'s label-gated validation (every call composes a
      release note, not just breaking-change calls).
- [ ] Insert a new `Release-Note: <line>` paragraph into the commit body
      `composeSubject` assembles, positioned after the existing summary/tag
      paragraph and before the `Fixes #n` footer. Because `BREAKING CHANGE:`
      is pushed last today (after `Fixes`, per the verified order in
      Current State above), this insertion needs no reordering of existing
      paragraphs — the resulting order becomes: summary → `[{tag}]` →
      **`Release-Note: {line}`** → `Fixes #n` → `BREAKING CHANGE: {note}`.
- [ ] Derive `releaseNote` the same way `summary` is already derived, not the
      way `migrationNote` is: from `subjectRecord.body` only
      (`records[0]`), never aggregated across a bundle's other records. A
      commit body can carry exactly one `Release-Note:` line (the
      single-line-trailer constraint below), so a multi-record bundle merge
      (`compose-subject.js` invoked with several `--fixes` numbers) still
      requires **every** record in the bundle to carry a non-empty
      `## Release Note` section (the unconditional check validates the
      whole bundle), but only the subject record's note is what ends up
      rendered in the release notes — document this explicitly as an
      accepted scope limitation of bundle merges, not an oversight.
- [ ] Document, in `subject.js`'s own header comment or the function's inline
      comment (matching how the `BREAKING CHANGE:` single-line constraint is
      documented today), that `Release-Note:` is a single-line trailer: like
      `BREAKING_FOOTER_RE` in `bin/lib/release-local/commits.js`
      (`/^BREAKING[ -]CHANGE: ?(.*)$/m`), a `Release-Note:` footer parser only
      round-trips the first line of whatever `## Release Note` section
      content was composed in, regardless of how many lines that section
      actually contained at compose time.
- [ ] Extend `plugin/bin/lib/compose-subject.js` to derive `releaseNote` via
      `extractSection(subjectRecord.body, 'Release Note')` (subject record
      only — see the bundle decision above), checking **every** record in
      `records` (not just `breakingRecords`) for a non-empty `## Release
      Note` section before composing, and failing loudly with a message in
      the identical shape as the existing check —
      `` `compose-subject.js: record(s) #${numbers} carry no non-empty "## Release Note" section` ``
      (structurally identical prefix/format to the existing
      `breaking is set on #... but the record carries no non-empty "##
      Breaking Change" section` message, `Release Note` substituted for
      `Breaking Change`, and unconditional rather than `breaking`-gated).
- [ ] Add a deliverable to grep and enumerate every existing
      `composeSubject(` call site and test fixture that constructs a
      `composeSubject({...})` call directly (not just the two files this
      unit edits) — the four local-merge call sites
      (`settle-and-merge.md`, `auto-merge-short-circuit.md`,
      `local-merge-auto-finish.md`, `worktree-merge.md`) and any fixture in
      `tests/` that builds a `composeSubject` payload inline — and update
      each to pass `releaseNote`, since this required-parameter change
      breaks any caller that omits it.
- [ ] Add one sentence of authoring guidance to
      `plugin/skills/specify/spec-template.md`'s `## Release Note` section
      for a record with no end-user-visible effect (an internal refactor, a
      chore, an infra-only change): the note should describe what changed
      from the perspective of someone reading the release notes, even when
      that's "no user-visible change" phrased plainly (e.g. "Improved
      internal test coverage for the release composer") — never omitted,
      since the section stays unconditionally required regardless of
      user-visibility.

## Acceptance Criteria

1. `composeSubject` throws `ComposeSubjectError` naming the record number
   when called with an empty string, missing, or non-string `releaseNote` —
   verified by a `subject.test.js` case mirroring the existing missing-
   `migrationNote`-on-`breaking` test shape.
2. `composeSubject` called with a non-empty `releaseNote` produces a commit
   body whose paragraphs appear in exactly this order: summary → `[{tag}]`
   → `Release-Note: {line}` → `Fixes #n` → `BREAKING CHANGE: {note}` (the
   last only when `breaking` is set) — verified by a `subject.test.js` case
   asserting exact paragraph order via string search/split, not a full
   byte-pin (that's `merge-subject-composer-conformance.test.js`'s job, item
   4 below).
3. `plugin/bin/lib/compose-subject.js`, run against a fixture bundle where
   the subject record's body contains a non-empty `## Release Note`
   section, derives `releaseNote` from that subject record only (via
   `extractSection(subjectRecord.body, 'Release Note')`) and passes it
   through to `composeSubject` — verified by a `compose-subject.test.js`
   case, including a multi-record bundle case confirming a non-subject
   record's own `## Release Note` content is validated-but-not-rendered
   (present-and-non-empty is still required on it, per AC below, but its
   text never appears in the composed output).
4. `plugin/bin/lib/compose-subject.js`, run against a fixture record (or any
   record in a bundle) whose body has no `## Release Note` section (or an
   empty one), fails loudly with
   `` `compose-subject.js: record(s) #${numbers} carry no non-empty "## Release Note" section` ``
   — verified by a `compose-subject.test.js` case, and this failure fires
   for every record composed, regardless of whether the `breaking` label is
   present on any of them.
5. `tests/merge-subject-composer-conformance.test.js`'s byte-pinned fixture is
   updated to include the new `Release-Note:` paragraph in its expected
   output, and the full suite (`npm test`) passes with this fixture updated.
6. `plugin/skills/_shared/work-record.md`'s spec-shaped-body check documents
   `## Release Note` as a fourth required section, and
   `plugin/bin/lib/compose-record/compose.js`'s `REQUIRED_SECTIONS` array
   literally includes `'Release Note'` — verified by a
   `compose-record`-level test (new or extended) asserting a body missing
   `## Release Note` fails `validateShaped` with a `missing section: ##
   Release Note` gap.

## Technical Approach

`composeSubject`'s existing `breaking`/`migrationNote` pairing is the direct
model: same validation shape (throw `ComposeSubjectError` citing the record
number), same paragraph-insertion mechanism, same "one contract change, every
call site inherits it, no call site changes its own logic" property this
design explicitly calls out. The only structural difference is that
`releaseNote` validation is unconditional — every commit gets a release note,
not just breaking-change commits — where `migrationNote` validation is gated
behind the `breaking` flag.

### Key Files

- `plugin/skills/specify/spec-template.md` — add `## Release Note` to the
  body template's required-sections list, with an example.
- `plugin/skills/_shared/work-record.md` — extend the spec-shaped-body check
  description to name the new required section.
- `plugin/bin/lib/compose-record/compose.js` — add `'Release Note'` to
  `REQUIRED_SECTIONS`.
- `plugin/bin/lib/release/subject.js` — add the `releaseNote` parameter,
  validation, and the `Release-Note:` paragraph insertion to `composeSubject`.
- `plugin/bin/lib/compose-subject.js` — derive `releaseNote` via
  `extractSection(body, 'Release Note')`, unconditionally, with the loud
  missing-section failure.
- `tests/bin-lib/release/subject.test.js` — new/extended cases for the
  `releaseNote` throw and paragraph-insertion behavior.
- `tests/bin-lib/compose-subject.test.js` — new/extended cases for the
  extraction and loud-failure behavior.
- `tests/merge-subject-composer-conformance.test.js` — re-pin the
  byte-level fixture to include the new paragraph.

## Gotchas

- The `Release-Note:` footer is single-line by construction — mirrors
  `BREAKING_FOOTER_RE`'s existing behavior in
  `bin/lib/release-local/commits.js` (`/^BREAKING[ -]CHANGE: ?(.*)$/m`),
  which already silently captures only the first line of a multi-line
  `## Breaking Change` section. No write-side truncation happens either —
  `composeSubject` writes whatever multi-line string `releaseNote` contains
  verbatim into the `Release-Note: {line}` paragraph, exactly as
  `migrationNote`/`BREAKING CHANGE:` already does today; it's the read-side
  regex (Unit 2/Unit 3's job, not this one's) that only ever captures the
  first line. State this constraint explicitly in the new code/docs rather
  than leaving it to be rediscovered the way the existing one was — and this
  applies repo-wide to every merge now, not just `breaking`-labeled ones, so
  the single-line requirement is worth restating prominently in the spec
  template's `## Release Note` section itself, not just in this record.
- `composeSubject` is called from pr-first squash merges and all four
  local-merge call sites (per its own header comment, "the ONE merge-subject/
  body composer every merge site calls") — a required-parameter change here
  is inherited everywhere with no call-site logic changes, but also means
  every existing caller and every existing test fixture that constructs a
  `composeSubject` call must be checked for a now-missing `releaseNote`
  argument, not just the two files named above (see the grep/enumerate
  deliverable above).
- **Rollout friction is expected, not a bug to design around.** Once this
  ships, any in-flight open record (specified before this contract landed)
  or any hand-authored merge that bypasses `/specify`'s spec template will
  hit `compose-subject.js`'s loud failure at merge time until it's
  re-shaped to add a `## Release Note` section. This is the same posture
  the existing `breaking`/`## Breaking Change` check already has for
  `breaking`-labeled records, just unconditional now — do not add an
  escape hatch or default value for a missing section; the parent record's
  stated goal is "no exceptions, no opt-in field to remember," and a
  default would silently reintroduce the raw-commit-subject behavior this
  design exists to replace.
- `extractSection(body, heading)` is already a generic, heading-parameterized
  helper (confirmed in `plugin/bin/lib/compose-subject.js` — it's the exact
  same function the existing `extractSection(body, 'Breaking Change')` call
  uses) — `extractSection(body, 'Release Note')` needs no new matching
  logic, only a new call with a different heading string, and inherits
  whatever case/whitespace matching rule the existing call already has.
- The "no record numbers, file paths, or internal identifiers" authoring
  constraint on `## Release Note` is documentation-only prose guidance,
  deliberately unenforced by any validator in this sub-issue — the same
  trust model the rest of `spec-template.md`'s "No Placeholders" section
  already relies on (author self-polices; nothing here adds automated
  linting of note *content*, only of section *presence*).
- This sub-issue is the foundation for Units 2 and 3 (local-merge rendering,
  pr-first post-publish) — they consume the `Release-Note:` trailer format
  this sub-issue defines, including the subject-record-only bundle
  decision above. Land this one first.
