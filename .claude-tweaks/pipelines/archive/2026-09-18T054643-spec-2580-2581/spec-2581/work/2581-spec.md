# 2581: Release notes: local-merge rendering

Surface: infra

## Overview

Once the authoring contract requires a single-line `Release-Note:` trailer on
every merge commit (the sibling sub-issue this one depends on), `local-merge`
projects (`bin/release-local.js`) need to actually surface those notes:
extracting the trailer from parsed commits, rendering the collected notes as
a flat public-facing bullet list, and wiring that list into the CHANGELOG
entry `release-local`'s changelog module already writes per version. This
sub-issue also introduces the one new shared module both this unit and the
pr-first sub-issue reuse for rendering — `plugin/bin/lib/release-notes.js` —
so the rendering logic itself is written exactly once.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Grouping the rendered list under type-derived headings ("Features"/"Bug
  Fixes"). Claude Code's own release-notes format — the target this design
  copies — is a flat list where each line's leading word ("Added", "Fixed",
  "Changed", "Improved") already carries the category; deriving a heading
  mechanically from a commit's `feat`/`fix`/`chore` type would misclassify
  the moment a `chore` record is user-visible or a `fix` reads better as a
  "Changed". `renderReleaseNotes` is deliberately headerless and
  ungrouped — do not add grouping logic to it in this sub-issue or any
  later one without revisiting this decision explicitly.
- The pr-first (`release: published` workflow) rendering path — that is the
  sibling "pr-first post-publish step" sub-issue, which reuses this
  sub-issue's `release-notes.js` module rather than duplicating its logic.
- Retroactively backfilling notes for commits merged before the authoring
  contract shipped — `renderReleaseNotes` silently skips any commit whose
  `releaseNote` field is absent or empty; this is not an error case.

## Current State

- Commit parsing: `plugin/bin/lib/release-local/commits.js`'s `parseCommit`
  already extracts a `BREAKING CHANGE:` footer via `BREAKING_FOOTER_RE`
  (`/^BREAKING[ -]CHANGE: ?(.*)$/m`) and stores it as a field on the parsed
  commit object. There is no equivalent `Release-Note:` extraction today.
- Changelog rendering: `plugin/bin/lib/release-local/changelog.js`'s
  `renderSection` writes a `### ⚠ BREAKING CHANGES` block (when present)
  followed by type-grouped commit sections, into the version-heading entry
  it composes for `CHANGELOG.md`. There is no highlights/release-notes block
  today.
- No `plugin/bin/lib/release-notes.js` module exists yet — this sub-issue
  creates it.
- Tests: `tests/bin-lib/release-local/commits.test.js` covers `parseCommit`'s
  existing footer-extraction behavior (including the `BREAKING CHANGE:`
  case). `tests/bin-lib/release-local/changelog-fixture.test.js` pins a
  captured example of `renderSection`'s rendered output against a byte-level
  fixture.

## Acceptance Criteria

1. `parseCommit`, given a commit body containing a `Release-Note: Fixed the
   thing.` footer (conventional-subject path), returns a parsed commit
   object with `releaseNote === 'Fixed the thing.'`.
2. `parseCommit`, given an unconventional-subject commit body containing a
   `Release-Note:` footer, still extracts it — `releaseNote` is set on the
   returned object in the unconventional early-return branch exactly as it
   is in the conventional branch — verified by a `commits.test.js` case
   mirroring the existing unconventional-subject `BREAKING CHANGE:` test.
3. `parseCommit`, given a commit body containing a multi-line
   `Release-Note:` section (composed from a multi-line `## Release Note`
   spec section that slipped past Unit 1's authoring-time single-line
   constraint), returns only the first line as `releaseNote` — verified by
   a `commits.test.js` case with a deliberately multi-line fixture.
4. `parseCommit`, given a commit body with no `Release-Note:` footer, returns
   a commit object where `releaseNote === null` (matching
   `BREAKING_FOOTER_RE`'s `breakingNote` field shape exactly — always
   present, `null` when absent — not omitted and not `''`).
5. `parseCommit`, given a commit body containing both a `BREAKING CHANGE:`
   and a `Release-Note:` footer, extracts both independently with no
   cross-match — verified by a `commits.test.js` combined-footer case.
6. `renderReleaseNotes([])` returns `null`.
7. `renderReleaseNotes`, given a commit whose `releaseNote` is a
   whitespace-only string (e.g. `'   '`), treats it as absent — no bullet
   is rendered for that commit.
8. `renderReleaseNotes` given a mix of commits with and without `releaseNote`
   returns a string containing exactly one `* {note}` line per commit that
   has a non-empty-after-trim note, in the same order as the input array,
   with zero lines for commits that don't.
9. `renderSection`, given a set of parsed commits where at least one carries
   a `releaseNote`, produces output containing a `### Highlights` block
   positioned after `### ⚠ BREAKING CHANGES` and before the first
   type-grouped section — verified by a `changelog-fixture.test.js` case
   re-pinning the captured fixture to include this block.
10. `renderSection`, given a set of parsed commits with a `releaseNote` but
    no `BREAKING CHANGE:` footer, still produces the `### Highlights` block
    (positioned first, since there's no breaking-changes block to follow) —
    verified by a `changelog-fixture.test.js` case.
11. `renderSection`, given a set of parsed commits where none carries a
    `releaseNote`, produces output with no highlights/release-notes block at
    all (not an empty one) — verified by a `changelog-fixture.test.js` case.

## Technical Approach

`renderReleaseNotes` refines the design doc's own sketch with a trim, since a
whitespace-only `releaseNote` must not render as a blank bullet:

```js
function renderReleaseNotes(commits) {
  const lines = commits
    .filter((c) => c.releaseNote && c.releaseNote.trim())
    .map((c) => `* ${c.releaseNote.trim()}`);
  return lines.length ? lines.join('\n') : null;
}
```

`parseCommit`'s new extraction should sit directly alongside the existing
`BREAKING_FOOTER_RE` extraction in the same function, importing
`RELEASE_NOTE_FOOTER_RE` from `release-notes.js` rather than declaring a
second copy of the pattern locally.

## Gotchas

- `Release-Note:` extraction must use the one `RELEASE_NOTE_FOOTER_RE`
  constant exported from `release-notes.js` — never a second hand-typed
  regex literal in `commits.js` or the pr-first sub-issue's own module.
  Exporting it from this shared module (rather than each consumer typing
  its own copy) is what keeps the pattern from silently drifting between
  the two consumers over time.
- `renderReleaseNotes` must return `null`, not `''` or `undefined`, on empty
  input — `changelog.js`'s `renderSection` branches on `!= null` to decide
  whether to render the block at all; returning an empty string would render
  an empty, headed block with no content, which is exactly the placeholder-
  looking failure mode this design is built to avoid.
- **Known, accepted limitation — bundled/multi-commit-in-one merge.** Like
  `BREAKING_FOOTER_RE` today, `RELEASE_NOTE_FOOTER_RE` is a single-match
  (`/m`, not `/g`) pattern: if one parsed "commit" body happens to embed
  more than one original commit's footers (a squash of several original
  commits into one merge commit), only the first `Release-Note:` line
  survives extraction. This is not a new regression this design
  introduces — it's the same pre-existing limitation `BREAKING_FOOTER_RE`
  already has for `BREAKING CHANGE:` footers — and is the same
  subject-record-only bundle scope limitation Unit 1 documents at the
  `compose-subject.js` layer. Out of scope to fix here.
- This sub-issue is blocked by the authoring-contract sub-issue (Unit 1) —
  it needs the `Release-Note:` trailer format Unit 1 defines before its own
  `parseCommit` extraction has anything real to test against. Do not start
  this sub-issue's build before Unit 1 has merged.
