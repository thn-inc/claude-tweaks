**Origin:** ledger resolve gate, spec #903 review

## Current State

`plugin/bin/lib/plan-audit/parser.js`'s `parseStep2` returns `null` both when a task genuinely
has no TDD Step 2 and when it has a Step 2 whose wording/Run: format didn't match the parser's
patterns. `checks.js`'s `checkC` silently `continue`s either way with zero diagnostic output.
#903's review fix broadened the wording match to also accept "verify they fail" but deliberately
did not chase the further "confirm FAIL" + fenced-code-block-Run: drift observed in a real,
current plan (`docs/superpowers/plans/2026-08-26-sweep-residue-needs-decision-marker.md`) — that
is a moving target for regex matching, and the durable fix is structural.

## Deliverables

- `parseStep2` (or a sibling function) reports a distinct "Step 2 present but unparseable" signal
  instead of collapsing into the same `null` as "no Step 2 at all".
- `checkC` surfaces that signal as a warning (not a hard failure) in its JSON envelope, naming the
  task and its raw Step 2 text so a human can judge whether the plan needs updating to the
  canonical template or the parser needs to learn a legitimately new shape.

## Acceptance Criteria

1. A task with a Step 2 header matching no known wording variant, but bearing `- [ ]`/`- [x]`
   checkbox syntax, produces a distinct signal (not silently indistinguishable from "no Step 2").
2. `plan-audit.js`'s output surfaces this signal without failing the exit code on its own.
3. Regression test against the real `2026-08-26-sweep-residue-needs-decision-marker.md` plan
   shape (fenced-code-block Run:, "confirm FAIL" wording) demonstrating the new signal fires.
