# 1751: build/worktree-setup.md: stale claim that /flow's multi-spec creation always runs Step 4.5 (Adopted branch exception)

Surface: infra

## Current State
`plugin/skills/build/worktree-setup.md`'s "Still run Step 4.5 (record the assignment) even on this skip path" paragraph justifies the unconditional per-record restamp by contrasting two creators: "`/flow`'s multi-spec up-front creation already runs this file's full procedure (including Step 4.5) when it creates the shared worktree, but `dispatch/sequential-execution.md`'s `EnterWorktree` call stamps nothing". That contrast is stale. Since #1750 (commit `2359c3b02`), `flow/multi-spec.md` Step 1 runs `_shared/worktree-setup.md`'s Adopt-or-create gate first, and its **Adopted** branch (session already isolated, clean tree) is "a pure detection-plus-skip with no state mutation beyond recording the current branch name" — no `record-worktree`, no Step 4.5. Only the **Created** branch runs this file's full procedure. Under this project's `worktree-always` policy an interactive `/flow` is always already isolated, so the Adopted branch is the common case, not the exception.

The unconditional re-run still covers it by accident: every per-record `/build` Common Step 1 skip path runs Step 4.5 regardless of why creation was skipped. The risk the review named is that a future editor reads the parenthetical, concludes `/flow` already stamps, and weakens or removes the re-run — reopening #778 (no `run-state.json` `worktree` stamp, E1 denies the first commit) for every Adopted multi-spec run.
