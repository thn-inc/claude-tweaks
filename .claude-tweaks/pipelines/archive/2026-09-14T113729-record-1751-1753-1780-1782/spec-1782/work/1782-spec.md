# 1782: worktree-setup.md's Post-creation catch-up has no guidance for Windows Filename-too-long merge failures

Surface: infra

## Current State

`plugin/skills/_shared/worktree-setup.md`'s Post-creation catch-up section prescribes an unconditional `git fetch origin {integration-branch}` + `git merge origin/{integration-branch}` in every new worktree, and its "Fail open on fetch/merge command failure" paragraph routes *every* non-conflict failure (no remote, no network, never-pushed branch) to log-and-proceed. Nothing in the plugin mentions `core.longpaths` or the `Filename too long` error (grep of `plugin/`, `docs/`, `CLAUDE.md` on 2026-09-09: zero hits). This repo tracks 29 paths longer than 180 characters (longest 225) under `.claude-tweaks/pipelines/**/spec-*/work/{n}-spec.md`; with a Windows checkout prefix those exceed the default 260-character limit, and `core.longpaths` is off by default in Git for Windows.

Observed 2026-09-02 on a Windows checkout: the catch-up merge failed with `Filename too long`, the section's prose classified it as a connectivity-style failure to proceed past, and recovery needed three undocumented moves — enable `core.longpaths`, then clean up the self-aborted merge (git had already dropped `MERGE_HEAD`, so `git merge --abort` had nothing to do, and the retry failed with "untracked working tree files would be overwritten" because the first attempt left the incoming files as untracked additions), via `git reset --hard HEAD` and `git clean -f -d` on the leftovers, before the merge succeeded.

The mechanical backstop for this section is `plugin/bin/lib/hooks/post-tool-use.js`'s EnterWorktree staleness warn (#307): after a `Created worktree at …`/`Entered worktree at …` tool result it fetches and, when the branch is behind, emits a `systemMessage` pointing at the catch-up; it never fetches or merges on the caller's behalf. It has no platform awareness. Tests: `tests/hooks-post-tool-use-worktree-staleness.test.js`. The original request's third deliverable names `/superpowers:using-git-worktrees`' Step 1b/Step 3 as the proactive-check site; that skill ships with the superpowers plugin, not this repo, so the proactive check belongs on this plugin's own EnterWorktree hook.

Secondary rough edge named in the report: from a worktree session the Bash-shape guard refuses `git -C <main-checkout> …` diagnostics; the section's opening paragraph already points at the shell constraint and `docs/donts.md`, which is where that belongs if it is not already covered.

## Deliverables

- [ ] **Name the failure mode in the catch-up section.** In `worktree-setup.md`'s Post-creation catch-up, insert a paragraph immediately before "Fail open on fetch/merge command failure" headed in the same bold style: a `Filename too long` (Windows) failure is a fixable local misconfiguration, not a connectivity failure, and must not take the fail-open path. Procedure: `git config --get core.longpaths`; when unset or `false`, `git config core.longpaths true` (repo-local: linked worktrees share the main checkout's `.git/config`, so one setting covers every worktree of this repo; `--global` is the operator's choice, not the procedure's) and retry the merge. State that the fail-open paragraph's "no origin / no network / never pushed" list is exhaustive for that path and this error is excluded from it.
- [ ] **Document the recovery sequence.** In the same paragraph: after a `Filename too long` merge, `git merge --abort` reports nothing to abort (no `MERGE_HEAD`); the retry fails on the leftover untracked files. Recovery: confirm the worktree is fresh (`git log --oneline origin/{integration-branch}..HEAD` prints nothing and `git status --porcelain` shows only untracked leftovers), then `git reset --hard HEAD` and `git clean -f -d -- {leftover paths}`, then retry. Say explicitly that the reset is safe *only* under that check and never on a worktree with commits or edits of its own, and cross-reference `_shared/git-discipline.md`'s "never reset or discard" rule as the default this paragraph carves out.
- [ ] **Proactive nudge on Windows.** In `post-tool-use.js`'s EnterWorktree handler, before the staleness fetch, when the platform is `win32` and `git config --get core.longpaths` is not `true`, emit a warn-tier `systemMessage` naming the setting and the catch-up section; log a distinct `events.jsonl` entry the way the staleness check logs `clean`/`stale`/fetch-failed. Never set the config from the hook (#307's Non-Goals: warn only). Non-Windows platforms skip the check with no log entry.
- [ ] **Tests.** `tests/hooks-post-tool-use-worktree-staleness.test.js`: nudge fires on `win32` with `core.longpaths` unset, does not fire when it is `true`, does not fire on `darwin`/`linux` — inject the platform through the module's existing deps seam, or add one `platform` option alongside it if the seam has none. A prose pin (in `tests/integration-branch-conformance.test.js` or a sibling file that already reads `worktree-setup.md`) asserts the section names `core.longpaths` and `Filename too long` and that the new paragraph precedes the fail-open paragraph.
- [ ] **The `git -C` diagnostic rough edge.** One sentence in the catch-up section's opening paragraph (the one that already points at the shell constraint): diagnosing the main checkout from a worktree session uses filesystem reads, not `git -C <main>`; cite `docs/donts.md`'s existing entry if one covers it, otherwise add a one-line rule there with a why-clause and no incident narrative.

## Acceptance Criteria

1. `worktree-setup.md`'s Post-creation catch-up names `Filename too long`, `core.longpaths`, and the repo-local scope rationale, in a paragraph that appears before "Fail open on fetch/merge command failure", and that paragraph says the fail-open path excludes this error.
2. The same paragraph documents the no-`MERGE_HEAD` symptom, the freshness check, and the reset-then-clean recovery, with the "fresh worktree only" condition stated explicitly and `_shared/git-discipline.md` cited.
3. On `win32` with `core.longpaths` unset, an EnterWorktree tool result produces a `systemMessage` naming `core.longpaths`; with it set to `true`, or on any other platform, no such message — all three cases covered by tests that inject the platform.
4. The hook never writes git config (assert no `config` argv reaches the exec seam in the win32 test).
5. `npm test` green; every existing case in `tests/hooks-post-tool-use-worktree-staleness.test.js` unchanged.
6. The `git -C` rough edge is stated once (catch-up paragraph or `docs/donts.md`, with a cross-reference from the other), not twice.

## Technical Approach

Prose first, hook second. The doc change is the deliverable the report asked for; the hook nudge is this plugin's equivalent of the "proactive check" the report placed in a third-party skill. Keep the nudge in the existing EnterWorktree handler and reuse its logging helper pattern so `events.jsonl` readers see one more result value rather than a new event kind. Platform detection must be injectable for tests; do not spawn `git config` on non-Windows at all (spawn budget, and the check is meaningless there). The 260-character claim is Windows' default `MAX_PATH`; the doc does not need the number, only the error string and the setting.

### Key Files

- `plugin/skills/_shared/worktree-setup.md` — new paragraph before "Fail open on fetch/merge command failure"; one sentence in the opening paragraph
- `plugin/bin/lib/hooks/post-tool-use.js` — EnterWorktree handler: win32 `core.longpaths` nudge + log entry
- `tests/hooks-post-tool-use-worktree-staleness.test.js` — three platform/config cases; no-config-write assertion
- `tests/integration-branch-conformance.test.js` — or a sibling that reads `worktree-setup.md`: prose pin
- `docs/donts.md` — one-line `git -C` rule only if no existing entry covers it

## Gotchas

- Linked worktrees share `.git/config` with the main checkout; a per-worktree `git config` write lands in the shared file. That is why repo-local scope is enough and why the doc must not suggest `--worktree` scope (requires `extensions.worktreeConfig`).
- `git clean -f -d` without a pathspec deletes every untracked file in the worktree; the doc must show the pathspec form and the freshness check first.
- The staleness handler's fetch has a 20 s timeout; the `git config --get` call is local and must use the short local-op budget, not that one.
- The hook runs on every PostToolUse; gate the new check on tool name `EnterWorktree` first, platform second, so non-Windows sessions pay nothing.

## Current State

`_shared/worktree-setup.md`'s Post-creation catch-up (`git fetch origin {integration-branch}` /
`git merge origin/{integration-branch}`) is documented as unconditional and required before
anything else runs in a freshly created worktree. On Windows, this repo's own history contains
many deeply nested `.claude-tweaks/pipelines/{ISO-timestamp}-{spec-slug}/spec-{n}/work/{n}-spec.md`
paths — one observed example exceeds 190 characters in the `pipelines/` segment alone before the
repo root or the `work/{n}-spec.md` suffix is even added. Windows' default (non-long-path) path
limit is ~260 characters, and `core.longpaths` is not enabled by default (neither globally nor
per-repo).

Reproduced live on 2026-09-02 during a fresh `EnterWorktree` + Post-creation catch-up: the
documented `git merge origin/{integration-branch}` failed outright with `Filename too long`
while materializing one of these nested paths, before `core.longpaths` was enabled. After
enabling it (a one-time git-config change, not currently mentioned anywhere in
`worktree-setup.md` or `using-git-worktrees`'s Quick Reference), the merge succeeded.

Two secondary failure modes were also observed in the same sequence, both worth noting since a
future session may hit them in either order relative to the long-path fix:

1. **Filename-too-long can leave a partially-applied merge.** The failed merge attempt (before
   `core.longpaths` was set) left new files from the incoming diff as untracked additions in the
   worktree, with no `MERGE_HEAD` (the merge had already self-aborted) — a `git merge --abort`
   found nothing to abort, and a naive retry of the merge failed a second time with "untracked
   working tree files would be overwritten," since those leftover untracked files collided with
   the same incoming content. Recovery required `git reset --hard HEAD` (safe here only because
   the worktree was freshly created with no prior work) followed by `git clean -f -d` on the
   specific leftover paths, before the merge could be retried cleanly.
2. **The harness's `worktree-always` Bash guard blocks `git -C <other-repo>` and other
   "too complex to verify" git-adjacent commands from a worktree session** — this is almost
   certainly correct behavior for its stated purpose (never let a worktree-isolated session touch
   git state outside itself), but it means a session cannot easily *diagnose* what state the main
   checkout is in without first working around the guard (e.g., using plain filesystem checks
   instead of `git -C`). Not a bug — just a real, currently-undocumented rough edge worth naming
   in `worktree-setup.md` for a future session's benefit, since the natural instinct when
   something looks wrong in the main checkout is to `git -C` into it and look.

## Deliverables

- Add a Windows-specific note to `_shared/worktree-setup.md`'s Post-creation catch-up section (or
  a new subsection) naming the long-path failure mode directly: when `git fetch`/`git merge` fails
  with `Filename too long` (or the equivalent Windows error text), check and enable
  `core.longpaths` (scope — global vs. repo-local — left to that section's own judgment) before
  retrying, rather than treating it as a generic "fail open on fetch/merge command failure" case
  (which the file's existing prose would otherwise route this into, incorrectly treating a fixable
  local misconfiguration as an unfixable connectivity problem).
- Document the safe recovery sequence for a merge that fails with `Filename too long` mid-apply
  (self-aborted, no `MERGE_HEAD`, untracked leftover files) — `git reset --hard HEAD` (safe only
  on a freshly created worktree with no prior commits — the section should say so explicitly) then
  `git clean -f -d` on the affected paths, before retrying.
- Consider whether `using-git-worktrees`'s own Step 1b (Git Worktree Fallback) or Step 3 (Verify
  Clean Baseline) should proactively check/set `core.longpaths` on Windows before the first
  fetch/merge is attempted, rather than only after a first failure — avoids the failed-merge
  cleanup dance above entirely on a machine that hasn't set this yet.

## Acceptance Criteria

- `_shared/worktree-setup.md`'s Post-creation catch-up section names the `Filename too long`
  Windows failure mode and its fix (`core.longpaths`) explicitly, distinct from the existing
  generic "fail open on fetch/merge command failure" guidance for connectivity problems.
- The same section (or a cross-referenced one) documents the reset-then-clean recovery sequence
  for a self-aborted, partially-applied merge left by this failure mode.
- A fresh `EnterWorktree` + Post-creation catch-up on a Windows machine with `core.longpaths`
  unset, against a repo whose tracked paths exceed ~260 characters, either succeeds without manual
  intervention (if the proactive-check deliverable above is adopted) or fails with guidance a
  session can follow without needing to rediscover the fix from first principles (if only the
  documentation deliverable is adopted).
