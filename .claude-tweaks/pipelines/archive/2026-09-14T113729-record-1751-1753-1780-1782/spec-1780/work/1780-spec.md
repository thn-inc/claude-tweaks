# 1780: flow Step 2.5 branch-divergence check: an unpushed local commit ahead of origin/{integration-branch} rides into a dispatched record's PR unreviewed

Surface: backend

## Overview

`_shared/worktree-setup.md`'s Post-creation catch-up unconditionally merges `{EXPECTED_BASE}` (the branch's pre-creation local HEAD) into every freshly created worktree — by design, since claude-tweaks's `worktree.baseRef: head` setting deliberately starts every worktree from the current local integration branch, which may legitimately carry unpushed `[reconcile]` merge commits or in-progress integration state (`_shared/worktree-base-ref.md`). That means local-ahead-of-origin content riding into a new worktree is this project's normal, expected behavior — not drift to be warned about on every occurrence.

The gap is narrower than "local-ahead is bad": it's that a `DISPATCH_HEADLESS=1` firing has nobody present to judge whether that particular ride-along content belongs in *this* record's PR. An interactive human running `/flow` can see their own local branch state before proceeding; a headless dispatch cannot. This spec adds a headless-only detection + hard-stop, mirroring the existing "Claim contested"/"Claim in-flight" stop shape `flow/claim-targets.md` already uses for an analogous headless pre-flight condition (`dispatch/settle-and-merge.md`'s Settle procedure), rather than inventing a new mechanism.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Changing worktree creation behavior for a human-present `/flow` invocation — today's silent ride-along stays exactly as-is there, since a human can judge it directly.
- Resetting, discarding, or refusing to merge `{EXPECTED_BASE}`'s local-ahead commits — `_shared/worktree-setup.md`'s Post-creation catch-up explicitly states "never reset or discard" and exists precisely to prevent losing locally-committed-but-unpushed work; this spec never weakens that guarantee.
- Any path-based or scope-based diffing of which specific files the ride-along commit(s) touch — at worktree-creation time no record-specific commit exists yet, so temporal position alone identifies ride-along content; no heuristic is needed.
- Updating `/review` Step 2's merge-provenance detection to separately recognize a linear ride-along commit — the headless hard-stop in this spec prevents the harmful case (an unreviewed ride-along merging under a dispatched record's closing keyword) at the source, making that defense-in-depth addition unnecessary for closing this gap. Track it separately if wanted later.

## Technical Approach

The detection is deliberately unconditional on file scope or content — at the moment Post-creation catch-up's `{EXPECTED_BASE}` merge completes, the new worktree has done zero record-specific work yet (no build commits exist), so any commit the branch is ahead of `origin/{integration-branch}` by is, by construction, pre-existing local state rather than this record's own future work. No scope/path diffing is needed to distinguish "legitimate" from "incidental" ride-along content; the check only needs to know whether `DISPATCH_HEADLESS=1` was set, which gates the entire step.

The stop itself reuses `flow/claim-targets.md`'s established shape rather than inventing new plumbing: a static card (no `AskUserQuestion`), a `_shared/headless-self-report.md` dedup-by-marker self-file so the condition leaves a durable trace even though nobody reads the Task call's output directly, and a `release-claim.js --reason "failed: {gate}"` release identical in form to the existing claim-contest/in-flight stops. This keeps the new condition indistinguishable in shape from the two the pipeline already knows how to surface and act on.

## Gotchas

- `worktree.baseRef: head` is this project's deliberate setting (`_shared/worktree-base-ref.md`), chosen specifically so a worktree inherits the local integration branch's in-progress state (merged specs, `[reconcile]` commits) rather than a possibly-stale remote default. Do not treat local-ahead-of-origin as inherently wrong anywhere outside the `DISPATCH_HEADLESS=1` path — it is this project's normal operating state, and a check that warns on it unconditionally would produce constant false-positive noise on ordinary reconcile-driven activity.
- `_shared/worktree-setup.md`'s Post-creation catch-up section states explicitly, twice, "never reset or discard" for merge conflicts on the `{EXPECTED_BASE}`/origin merges — this spec's new step must never touch that invariant; it only detects and reports, after the merges have already completed successfully.
- The record's own originally-quoted log line ("origin/{integration-branch} ahead=0; local HEAD … is 1 commit ahead …") does not correspond to any text in the current shipped `_shared/worktree-setup.md` or `flow/validation.md` — whatever produced that exact wording either predates the current file content or was misremembered when filing; don't search for or try to preserve that literal wording when authoring the new step's own log/card text.
- Mirror `dispatch/settle-and-merge.md`'s existing `DISPATCH_HEADLESS=1` claim-contest/in-flight invocation of `_shared/headless-self-report.md` byte-for-byte in structure (same dedup lookup, same self-file shape, same release-claim.js flags) — don't paraphrase or simplify it, since the two stop shapes need to behave identically from a dispatch-drain's perspective.

## Original request

**Summary:** `/flow`'s Step 2.5 branch-divergence check treats "local ahead of origin" as a non-failure and the worktree is cut from local HEAD, so under `/claude-tweaks:dispatch` an unpushed local commit rides into the record's PR — merged under that record's `Fixes #N`, reviewed by nobody under the record's own scope.

**Kind:** Gap

**Affected component:** `/flow` Step 2.5 branch-divergence check (`flow/validation.md`) and `build/worktree-setup.md`'s worktree creation

**Use case:** A `/claude-tweaks:dispatch` firing ran `/flow #N build,test` on a machine whose local integration branch was 1 commit ahead of its origin counterpart (an `/init` update-mode refresh that had not been pushed). Step 2.5 logged `2.5 branch-divergence OK (origin/{integration-branch} ahead=0; local HEAD … is 1 commit ahead of origin/{integration-branch} — unpushed local commit will ride on this branch)` and proceeded. The record's PR diff against the origin tip therefore carried the unrelated commit — the `/init`-generated files (CLAUDE.md, plugin settings, a regenerated cloud-setup script) plus other unrelated edits — alongside the record's own one-line docs change. That inherited commit contained a `set -u` crash in the generated cloud-setup script (companion defect report on `/init` Step 14); it surfaced only because review ran its lenses over the whole base-to-HEAD diff. The record's own scope had nothing to do with it, `merge-check` could not have returned `auto-merge` on a diff touching CLAUDE.md, and the run parked at `pending-review` on a docs record that was itself clean. The check treats "behind"/"diverged" as the failure conditions; for a dispatched, headless run "ahead" is the wrong non-failure: whatever is ahead has never been reviewed under this record's scope, will merge under this record's closing keyword, and inflates `merge-check`'s blast radius for a change that is not the record's.

Expected, one of: (a) cut the run's worktree from `origin/{integration-branch}` (the fetched upstream tip) rather than local HEAD when `/flow` runs under dispatch or `worktree-always`, so a record's PR carries only that record's work; or (b) treat local-ahead-of-origin as a pre-flight WARNING at minimum — surfaced in the Manifesto FYI and the PR body — and as a hard stop for a `DISPATCH_HEADLESS=1` firing (nobody is present to accept the ride-along), with the resume hint "push or stash the local commit(s) first". Either way, `/review` Step 2's merge-provenance idea (content that arrived from base is not this branch's work) should recognise this shape too — a linear ride-along commit is not a merge commit, so the current check never fires on it. The reporting project is adding a local CLAUDE.md Don't about the habit, but the plugin-side gap is what lets the habit turn into an unreviewed merge.

**Definition:** Needed — two viable directions (cut the worktree from the origin tip vs. warn/stop on local-ahead) with no stated preference yet.
