# 3543: Reconcile: a stale or mistyped stamped pr.number strands the run silently

Surface: backend

**Related:** #3581, #3416, #2986, #3503, #3193, #3295, #3297, #3339, #3363, #3469, #3470, #3544, #3551, #3565, #3579

## Current State

#3416 (PR #3533) made reconcile resolve a run's PR by its stamped `run-state.json` `pr.number` before any branch-name lookup. The two places:
- `archive-merged.js` `resolveRunPrState` (both archive loops);
- `release-merged.js` Phase 1.5.

A stale or mistyped stamp strands the run silently:
- `pr-state.js` `resolvePrStateByNumber` and `resolvePrStateByNumberAsync` call `gh pr view {n}` with stderr ignored. A PR number that exists nowhere makes gh exit 1, and `classifyByNumberError` maps every non-`gh-absent` failure to `'network-failure'`.
- So archive skips such a run on every pass with `network-failure`, and release skips with `network-failure` or `invalid-arguments`. The run is never archived, and its claims are held until the claim TTL.
- `network-failure` is not in `STRUCTURALLY_STUCK_REASONS` (`archive-merged.js` line 1425), so `trackStuckSkip` never escalates it. The failure direction is safe (nothing is archived or released wrongly), but the skip is silent and reads as a transient outage.

**Probe (2026-10-19, `gh` against `thn-inc/claude-tweaks`, PR number 999999 that does not exist):**
- `gh pr view 999999 --json number,state` exits 1, stdout empty, stderr `GraphQL: Could not resolve to a PullRequest with the number of 999999. (repository.pullRequest)`. Only prose distinguishes it from an outage.
- `gh api graphql` with `repository(owner,name){pullRequest(number:999999){number}}` exits 1, and its stdout carries structured JSON: `{"data":{"repository":{"pullRequest":null}},"errors":[{"type":"NOT_FOUND","path":["repository","pullRequest"],…}]}`. The `errors[].type` / `path` fields are GitHub's GraphQL API contract, not message text. `data.repository` being non-null proves the repo resolved, so the null PR is a real absence.
- `gh api repos/{owner}/{repo}/pulls/999999 --include` returns `HTTP/2.0 404`. But a 404 also covers an inaccessible or missing repository, so it cannot tell "no such PR" from "no such repo".

**Design decision (option c, made by the shaping agent under the user's standing "go"; the open question is resolved):**
- Classify not-found distinctly, from the structured GraphQL signal only, never from stderr text.
- Never fall back to the branch lookup for it, because that would reintroduce the reused-branch misattribution #3416 fixed for exactly this stale-stamp case.
- Escalate it through the existing structurally-stuck machinery, so a stale stamp surfaces instead of skipping forever.

Option (a) with branch fallback was rejected for the misattribution reason. Option (b) alone, escalating every repeated `network-failure`, was rejected: it would page on a long genuine outage, and the reason would still read as an outage.

The other by-number callers already treat any non-object return as "no answer":
- `plugin/bin/lib/flow/consolidated-pass.js` line 145 (`degraded` text);
- `plugin/skills/_shared/github-pr-scan.md` pending-review loop (`typeof r === 'object'` gate);
- `plugin/skills/dispatch/close-out.md` re-check.

So a new string value is backward-compatible there.

## Technical Approach

Add one internal helper in `pr-state.js`, `confirmPrNotFound(repoRoot, number)` plus an async twin. It builds the GraphQL query with typed variables, runs it with stdout piped and stderr ignored, and on any throw reads `e.stdout`: `gh api graphql` exits 1 on a GraphQL error but still writes the JSON body to stdout, per the probe. It returns `true` only on the exact structured match. `classifyByNumberError` stays the mapper for the primary call. Each by-number resolver wraps its `runClassified` result: when the result is `'network-failure'`, it consults the helper and returns `'pr-not-found'` on a match. The repo slug comes from `repoSlugOf(repoRoot)`; if it cannot resolve, the helper returns `false`, and the result stays `'network-failure'`.

## Gotchas

- `gh api graphql` exits non-zero on any GraphQL error, but still prints the response body to stdout, so the helper must read `e.stdout` from the thrown error, not only a successful return.
- A `null` `data.repository` (wrong slug, no access) must never classify as `'pr-not-found'`. That is an access or transport problem, and escalating it would misreport.
- Escalation is time-gated by the existing `isStaleDir(dir, STRUCTURALLY_STUCK_TTL_MS)` check (7 days), so a fresh run with a typo stamp skips quietly until then. That reuses today's stuck policy rather than adding a second clock, which is a deliberate call.
- The confirm probe costs one extra GraphQL call only on a by-number failure, never on success. A long real outage pays one extra failing call per probe, bounded by the same timeout.
- `release-merged.js` has no stuck escalation of its own. The stale stamp surfaces through `archive-merged.js` for the same run dir, which holds the same `run-state.json`.
