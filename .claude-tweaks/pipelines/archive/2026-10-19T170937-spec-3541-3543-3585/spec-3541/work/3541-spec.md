# 3541: Impeccable resolve() can report upgrade-required for a project-scope entry Claude Code does not load

Surface: backend

**Related:** #3415, #3380, #3414, #3498

## Current State

The open question is answered: Claude Code does not rank install records by scope or version. It takes the **first applicable record in the plugin's `installed_plugins.json` array, in file order**.

**The rule (Claude Code 2.1.302, read from the bundled source; minified names `QP`/`gJt`/`ZI`).** For each plugin key, the session uses the first record in that key's array for which one of these holds:

1. its `scope` is `user` or `managed` (applies everywhere);
2. its `projectPath` equals the session's project directory exactly;
3. the canonical git root of its `projectPath` equals the canonical git root of the session directory. The canonical root is the nearest enclosing git checkout, with a linked worktree mapped to its main checkout through its `.git` file's `gitdir` → `commondir`. The walk goes up through path components that no longer exist, so a record for a deleted worktree still resolves to its main checkout.

Scope is not ranked. A `user` record listed before a project record wins, and the reverse. An exact-path project record does not beat an earlier same-checkout record. Only on Windows does a second pass retry the match ignoring path spelling (Claude Code's gh-74612).

**Probe, 2026-10-19.** Method: Claude Code 2.1.302 headless `claude -p` runs, reading the stream-json init event's `plugins` list plus `--debug` plugin-loading lines, with hooks disabled. The `installed_plugins.json` hash was the same before and after. Each line below is what the session loaded; the arrays are the records on the maintainer machine.

- `impeccable@impeccable` array: `[user 4.6.0, memenu-app 3.0.6, synology-nas 3.0.6, …]`. memenu-app, synology-nas, claude-tweaks and unifi-network-config-kajeroedvej all loaded user 4.6.0, because the user record is first.
- `superpowers@claude-plugins-official` array: `[memenu-app/.claude/worktrees/flow-spec-304-305-306-307-308-309 6.3.0, user 7.0.0, memenu-app 6.3.0, synology-nas 6.2.0, …]`. memenu-app loaded 6.3.0 (index 0 is the same checkout). synology-nas loaded user 7.0.0 (index 0 is another repo, index 1 is user, and its own 6.2.0 record at index 3 never gets reached).
- `claude-tweaks@claude-tweaks-marketplace` array: `[memenu-app/.claude/worktrees/flow-spec-304-… 6.113.0, user 6.145.0, memenu-app 6.108.0, …]`. memenu-app loaded **6.113.0**: a record for a worktree directory that no longer exists, chosen over memenu-app's own exact-path 6.108.0 record. Only the first-in-order plus same-checkout rule produces that.

Neither marketplace declarations nor enabled-plugin settings decide it. memenu-app and synology-nas enable the same plugins and declare the `impeccable` marketplace alike.

This also explains the home-directory findings of #3380 and #3415. Each home-directory record sits after the user record in its array, so the user record wins by order. Home records are not skipped by any rule. `excludeHome` encodes a coincidence of one machine's array order.

**Where the plugin diverges.** `selectEntry` in `plugin/bin/lib/installed-plugins.js` currently does this:
1. picks the longest ancestor-or-self `project` record;
2. otherwise the first `user` record;
3. ignores `local` and `managed`;
4. with `excludeHome`, skips a home-directory record.

That differs from Claude Code in three ways:
- it ranks project above user;
- it matches any ancestor path, where Claude Code matches only the exact path or the same git checkout, so a record for a non-git parent folder never applies to a session in a subfolder;
- it never matches a sibling worktree's record of the same repository.

Both resolvers call it with `{ excludeHome: true }`:
- `resolve()` in `plugin/bin/lib/impeccable-engine/index.js` (line 163), which for memenu-app picks the 3.0.6 record and reports `upgrade-required` while sessions there run 4.6.0;
- `effectiveSuperpowersVersion` in `plugin/bin/lib/superpowers-version.js` (line 101), which also sorts the records by `lastUpdated` before selecting. That sort destroys the file order Claude Code relies on.

Both files' header comments carry probe notes recorded as "observed, not encoded" (`installed-plugins.js`) or "unexplained" (`superpowers-version.js`). This rule now explains them.

**Separate UX gap.** When `installed_plugins.json` carries Impeccable records but none applies, `resolve()`'s `!entry` branch (`impeccable-engine/index.js` line 165) returns `not-installed` with no `detail`.

## Deliverables

1. Rewrite `selectEntry(entries, projectPath, deps)` in `plugin/bin/lib/installed-plugins.js` to Claude Code's rule. It returns the first entry, in array order, that applies; otherwise `null`. An entry applies when:
   - its `scope` is `user` or `managed`;
   - or its realpathed `projectPath` equals the realpathed session path;
   - or `canonicalGitRoot(projectPath)` equals `canonicalGitRoot(sessionPath)`, both non-null.

   Records of any other scope (`project`, `local`) match only through the path conditions. Non-object entries stay skipped.
2. Add `canonicalGitRoot(p, deps)` to the same module, exported for tests:
   - walk up from `p` to the first directory holding a `.git`, continuing through components that do not exist;
   - if `.git` is a directory, return that directory;
   - if it is a file whose `gitdir:` target holds a `commondir`, return the main checkout (the parent of the resolved common git dir);
   - otherwise return the directory itself; with no `.git` anywhere, return `null`.

   All filesystem reads go through injected `deps` so tests stay hermetic.
3. Remove the `excludeHome` option and the home-directory skip, and drop `{ excludeHome: true }` from both call sites.
4. In `plugin/bin/lib/superpowers-version.js`:
   - delete the `lastUpdated` sort so each plugin key's records keep their file order;
   - keep the cross-marketplace flattening, in `Object.keys` order, so a key's records stay contiguous;
   - widen the scope filter to admit `managed` and `local` records, which the new rule can select.
5. Rewrite the header comments of `installed-plugins.js` and `superpowers-version.js`. Each states the rule, the Claude Code version it was read from (2.1.302), and the 2026-10-19 probe, and drops the superseded "Confirmed / Reversed / observed, not encoded" notes.
6. In `resolve()` (`plugin/bin/lib/impeccable-engine/index.js`), when the plugin key has at least one record but `selectEntry` returns `null`, return `not-installed` with a `detail`. The detail names how many records exist and that none applies to the session path, for example `3 install records for impeccable@impeccable, none applies to /path (project records for other checkouts; no user or managed record)`. `FAILURE_REASONS` stays unchanged.
7. Update the tests that pin the old semantics to the new rule. The current ancestor, longest-path and excludeHome assertions describe behavior Claude Code does not have; replace them with the cases in Acceptance Criteria. The tests:
   - `tests/bin-lib/installed-plugins.test.js`
   - `tests/bin-lib/path-guard/callers-characterization.test.js`
   - `tests/bin-lib/impeccable-engine/resolve.test.js` (AC6.1)
   - `tests/bin-lib/superpowers-version.test.js`
8. Update `docs/plugin-structure.md` lines 65-66, which describe `selectEntry`/`excludeHome`.

## Acceptance Criteria

- `selectEntry([user, project(P)], P)` returns `user`, and `selectEntry([project(P), user], P)` returns `project(P)`.
- With `P` a git checkout and `P/.claude/worktrees/w` absent on disk, `selectEntry([project(P/.claude/worktrees/w) A, user B, project(P) C], P)` returns `A`.
- With `W` a linked worktree of checkout `P` (a `.git` file whose `gitdir` holds a `commondir`), a session at `W` selects a `project(P)` record listed before the user record.
- A `project(F)` record for a non-git folder `F` applies to a session at exactly `F`. It does not apply at `F/sub`: with no other record, `selectEntry` returns `null`.
- A `managed` record applies to any session path. A `local` record applies to its own path.
- `canonicalGitRoot` returns `null` when no ancestor holds a `.git`.
- Fixture mirroring the memenu-app case: records `[user 4.6.0, memenu-app 3.0.6]`, each install dir carrying a launcher and plugin.json. `resolve({ projectPath: memenu-app })` selects the 4.6.0 install, not `upgrade-required`.
- `resolve()` with Impeccable records present but none applying returns `{ ok: false, reason: 'not-installed' }` with a `fix` and a `detail` naming the record count. `FAILURE_REASONS` deep-equals its value before this change.
- `effectiveSuperpowersVersion` returns the first applicable record in file order. A fixture whose later record has the newer `lastUpdated` still returns the earlier one.
- `git grep -n excludeHome -- plugin/` prints nothing.
- The `installed-plugins.js` header names Claude Code 2.1.302, the first-applicable-in-file-order rule, and the 2026-10-19 probe.
- `npm test` passes.

## Technical Approach

Keep `selectEntry`'s signature minus the `opts` argument. It becomes one `find` over `entries` with an `applies(entry)` predicate, so array order alone decides, exactly as in Claude Code.

`canonicalGitRoot` mirrors Claude Code's `.git`-file resolution:
- read `<dir>/.git`;
- if it is a file starting `gitdir:`, resolve `<gitdir>/commondir` against the gitdir;
- the main checkout is the common dir's parent when the common dir's basename is `.git`.

Memoize it per call (a `Map` local to one `selectEntry` invocation), not in module state. Compare canonical roots after `safeRealpath`, so a symlinked or mis-cased path still matches, as today.

In `resolve()`, the `not-installed` detail is built from the plugin key's own records: count, and whether any user or managed record exists. Nothing else in the result shape changes.

## Gotchas

- The rule is Claude Code internal behavior, read from one minified build (2.1.302). It can change in a later release, so the header must name the version, and a future probe should be re-run against `npx`-pinned builds rather than trusted forever.
- Array order is `installed_plugins.json`'s file order. Never sort the records, and never iterate them through a structure that loses order.
- A stale record, one whose worktree directory was deleted, still matches through its main checkout. That is real Claude Code behavior (memenu-app loads claude-tweaks 6.113.0 this way), so keep it rather than filtering out missing paths.
- `tests/path-guard-conformance.test.js` pins each file's count of `realpathSync`/`existsSync` tokens. A new `existsSync` (or `realpathSync`) in `installed-plugins.js` needs a matching allowance with a reason, or the call must route through the injected `deps`.
- The Windows spelling-insensitive second pass (Claude Code gh-74612) is out of scope. `fs.realpathSync.native` already canonicalizes case on the platforms the resolvers run on.
- Which of several `superpowers@{marketplace}` keys loads when more than one is installed is not settled by this probe. Flattening keys in `Object.keys` order is a builder's call, kept as today.
