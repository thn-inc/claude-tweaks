# 3585: Decide whether the comment stripper should model regex literals instead of only detecting its mis-parses

Surface: infra

**Related:** #3536, #3573, #3494, #3317, #3414, #3478, #3493, #3541, #3565, #3568, #3574, #3581

## Current State

`tests/helpers/strip-comments.js` `stripComments` does not model regex literals. #3536 and #3573 added `stripperVerdict`, which detects a mis-parse only when the stripped text stops compiling, meaning live code was blanked.

**Measurement (2026-10-19).** The current stripper was compared, file by file, against exact comment blanking computed from the `acorn` 8.14.0 tokenizer's comment ranges (used as offline ground truth only, never as a dependency). The corpus was every `.js`/`.cjs` file under `plugin/bin` (419 files, 1,133 regex literals, 78 of them containing a quote, backtick, `/*` or `//`) and under `tests/` (837 files).

- The current stripper differs from exact blanking in **23 `plugin/bin` files and 39 `tests/` files**. `stripperVerdict` returns `ok` for every one of them.
- In all 23 `plugin/bin` cases the direction is the same: **no live code blanked, but comment text kept** (121 to 6,662 characters per file). A quote or backtick inside a regex literal opens a fake string that swallows the comments after it. Examples: `plugin/bin/lib/code-health/candidates-dead-code.js` (6,662 characters kept), `plugin/bin/lib/issues/grouping.js` (4,203), `plugin/bin/lib/impeccable-engine/index.js` (2,338).
- This direction can never trip `stripperVerdict`, because a kept comment still compiles. The record's premise that "no `plugin/bin` file trips either case today" holds only for the detectable direction.

The four scans that consume the stripper are `tests/windows-hide-spawn-conformance.test.js`, `tests/git-status-optional-locks.test.js`, `tests/path-guard-conformance.test.js` and `tests/bin-lib/exit-code-conformance.test.js`. Today they read comment prose as code in those 23 files. A comment that quotes a forbidden call shape can raise a false finding, and a comment that names a required token (for example `windowsHide`) can satisfy a scan that the code itself does not.

**Spike.** A throwaway regex-aware stripper using the previous-significant-token heuristic (below) matched exact blanking on **all 1,256 files (0 differences)**. Time over the corpus: 134 ms for `plugin/bin`, 370 ms for `tests/`, versus the current regex's 57 ms each.

**Decision (made by the shaping agent under the user's standing "go"; the open question is resolved).** Model regex literals at the root, and keep `stripperVerdict` as the backstop. The measured silent blind spot is not residual: it affects 5.5% of `plugin/bin` files. The heuristic closed all of it on this corpus.

## Deliverables

1. Replace `stripComments` in `tests/helpers/strip-comments.js` with a single-pass, dependency-free scanner. It keeps strings, template literals (including nested `${…}` code, scanned recursively) and regex literals verbatim, and blanks comments as today: every non-newline character becomes a space, so offsets and line numbers stay stable.
2. Regex-versus-division follows the previous significant token. A `/` that is not a comment opener begins a regex literal when:
   - nothing precedes it;
   - or the previous token is a punctuator other than `)`, `]` or `}`;
   - or the previous token is one of the keywords `return`, `typeof`, `instanceof`, `in`, `of`, `new`, `delete`, `void`, `throw`, `case`, `do`, `else`, `yield`, `await`.

   Otherwise it is division. Inside a regex, `[…]` character classes and backslash escapes are honored, and trailing flags are consumed.
3. Keep the exported surface unchanged (`stripComments`, `stripperVerdict`, `STRIPPER_VERDICT_MESSAGES`), and keep the hashbang line intact. Rewrite the header comment: what is modeled now, the heuristic and its known ambiguity (`}` and `)` before a `/` are read as division), and that `stripperVerdict` remains the backstop for the compile-breaking direction.
4. Add regression cases to `tests/helpers-strip-comments.test.js`:
   - a regex containing `'`, `"` and a backtick, followed by a `//` comment, which must be blanked;
   - a regex with `//` and `/*` inside a character class, which must be kept verbatim;
   - division (`a / b // c`, `x) / 2`), which must not open a regex;
   - `return /re/` and `typeof /re/`;
   - a template literal with a nested `${ '/' + "`" }`;
   - an escaped slash in a regex.
5. Run the four consuming scans after the swap. A scan finding that the kept comment text used to mask, or a false finding that disappears, is handled in this change: a real finding is fixed or allow-listed with a reason by that scan's own convention, never by weakening the stripper.

## Technical Approach

Port the spike's shape:
- one `scanCode(start, inBrace)` loop that tracks the previous significant token (identifier or keyword, number, string, template, regex, punctuator);
- a `scanTemplate` that recurses into `scanCode` for each `${` and returns at its matching `}`, using a brace-depth counter local to that call;
- comments blanked into an output character array.

Strings stop at an unescaped matching quote or a newline, as the current regex does. Keep `compiles` and `stripperVerdict` unchanged.

## Gotchas

- The heuristic misreads a regex directly after `)` (as in `if (x) /re/.test(y)`) or after a block-closing `}`. Neither shape occurs in the 1,256-file corpus. Such a misread is either caught by `stripperVerdict` (code blanked) or would keep a comment (the old failure mode), so it is never worse than today.
- The kept-comment fix can change what the four scans see in 23 `plugin/bin` files. Expect possible new or vanished findings, and treat each as a real scan result rather than a stripper bug.
- `acorn` was used only to measure. It must not become a dependency of the helper or the tests (the record requires no external dependency).
- The scanner is about 2.5 times slower than the current regex: under 0.4 s for all of `tests/`, negligible against the suite.

## Current State

`tests/helpers/strip-comments.js` does not model regex literals. A quote or backtick inside a regex, or an unescaped `/*` or `//` in a character class, can blank live code after it.

#3536 and #3573 made that mis-parse *detectable*: `stripperVerdict` reports a file whose stripped text stops compiling, and the four scans that use the stripper (windows-hide, git-status, path-guard, exit-code) fail on it. A mis-parse whose stripped text still compiles is not detected; the helper header states that caveat. No `plugin/bin` file trips either case today.

## Deliverables

Decide whether to close the class at its root, by making `stripComments` recognize regex literals, rather than relying on detection alone.

If yes, implement it in `tests/helpers/strip-comments.js` with no external dependency, and keep `stripperVerdict` as the backstop.

## Open Question

Regex-versus-division is ambiguous at the character level. Is a previous-significant-token heuristic (a `/` after a punctuator, an operator, a keyword such as `return`/`typeof`, or the start of input begins a regex) accurate enough over the 419 `plugin/bin` files, or does the residual blind spot (a mis-parse that still compiles) not justify the extra stripper logic, since detection already fails loudly on the common shapes?
