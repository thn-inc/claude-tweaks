# 1296: capture: sweep the headless absorb bar against the auto-mode reversibility floor, batch mode, and work-types

Surface: infra

## Current State

Spec #1264 gave `/claude-tweaks:capture` a **headless absorb bar**: an agent-driven filing (`$PIPELINE_RUN_DIR` set, `--source`, or `--defer-reason=`) that matches an existing record on a shared literal file path plus an identical `type:{t}` absorbs into it instead of filing, logging `AUTO {time} — capture absorbed into #{N} … Reversibility: medium`. Its final independent review found three sibling contracts the new bar was never swept against. One (the `_shared/auto-mode-contract.md` silences-table row) was fixed inside that review (`bd91e34e`); the three below need decisions this review deliberately did not make on its own.

- **The `AUTO` status contradicts the reversibility floor it declares.** `_shared/auto-mode-contract.md`'s "Reversibility / confidence floors" section: "A skill MAY auto-resolve a decision only when ALL of these hold … Reversibility `high`", and its canonical procedure block says "If reversibility != high OR confidence != high OR severity > low → **stage instead**". `capture/SKILL.md`'s headless bar logs an `AUTO`-status entry whose own text reads `Reversibility: medium`. Either the classification or the status is wrong, and the file says both. The sibling precedent cuts against `AUTO`: `tidy/step-6-auto.md`'s github-issues Absorb row is "Stage — visible to collaborators; **never auto-applied per the auto-mode contract's reversibility floor**". The counter-argument (not adjudicated here) is that capture's absorb is *more* reversible than tidy's precisely because of the carve-out this spec added — it appends under a delimited dated `## Absorbed:` heading rather than integrating content indistinguishably, so deleting that one section restores the prior body exactly. That argument, if accepted, makes the honest value `high`; it is a loosening of a governance floor, which a review must not apply unilaterally.
- **Batch mode is un-swept.** `capture/batch-mode.md`'s Routing section: "`absorb:N` is not offered at the batch level (each entry would need its own target record) — an entry needing `absorb:N` should be filed singly instead." Batch mode is the *primary* agent-driven filing path (`--batch` carries `--source`/`--defer-reason=` uniformly across entries), so the headless bar reads as applying to exactly the invocations batch mode says never absorb. The two texts are reconcilable — batch mode's sentence is about the batch-level `--route` arg while the bar is a per-entry filing-time judgment inside the per-entry loop, which `batch-mode.md` says runs "exactly the same per-item pipeline `SKILL.md`'s Workflow Step 1 already runs" — but neither file states the precedence, so an agent reading either one alone gets a defensible answer that contradicts the other.
- **`work-types: none` silently disables the bar.** Criterion (b) is an identical `type:{t}` label match, and `capture/SKILL.md` itself stamps Type "only when `work-types: labels`". On a project configured `work-types: none` (a supported value — `_shared/work-record.md`'s Config keys table) criterion (b) is unevaluable, so the bar never fires and every agent-driven capture files fresh. That is the safe direction and matches "fail toward filing", but it is undocumented: the feature is a silent no-op on those projects with nothing saying so. Distinct from #1295's `local-files` mapping, which is the *backend* axis, not the work-types axis.

Related but out of scope: #1295 (capture/SKILL.md's byte-ceiling split, the `local-files` absorb mapping, the Immediate-Routing ordering prose). This record is the cross-contract sweep, not the capture-file work; the byte ceiling is why none of it can land in `capture/SKILL.md` before #1295's split.

## Deliverables

- **Adjudicate the reversibility classification.** Either (a) reclassify capture's headless absorb as `Reversibility: high`, with the delimited-append rationale stated once (and `tidy/step-6-auto.md`'s row updated to say why *its* absorb differs — integrate vs append — so the two rows stop looking contradictory), or (b) keep `medium` and change the headless bar to file fresh with `**Related:** #N` plus a `STAGED` absorb proposal for the Review Console, per the contract's own "stage instead" procedure. Update `capture/SKILL.md`'s log line, `tests/capture-absorb-default.test.js`'s AUTO-line pin, and — if (b) — `_shared/auto-mode-contract.md`'s Capture silences row (`bd91e34e`) to match.
- **State the batch-mode precedence** in `capture/batch-mode.md`'s Routing section: whether the per-entry headless bar fires inside the per-entry loop (and, if so, that `absorb:N`'s absence at the *batch* level is only about the batch-wide `--route` arg), or whether batch filings are exempt from the bar entirely.
- **Document the `work-types` axis** where the bar's criterion (b) is defined: under `work-types: none`, criterion (b) cannot be evaluated and the bar never fires — every agent-driven capture files fresh. One sentence, landed after #1295's split frees the bytes.
- `tests/capture-absorb-default.test.js` extended with a pin per resolved deliverable; the existing 18 pins stay green.

## Acceptance Criteria

- No `AUTO`-status log line in `plugin/skills/**` declares a reversibility below `high` — or, where one does, the file states the contract exemption it relies on. `grep -rn "Reversibility: med" plugin/skills/` returns only lines whose surrounding text is a `STAGED` entry.
- `capture/batch-mode.md` names the headless absorb bar and states whether it fires per entry; `grep -in "headless absorb" plugin/skills/capture/batch-mode.md` matches.
- The `work-types: none` behavior is stated once alongside criterion (b).
- `node --test tests/capture-absorb-default.test.js` passes with the pre-existing 18 pins unmodified except where a resolved deliverable deliberately changes their target text.
- `npm test` passes.

## Technical Approach

This is a cross-contract sweep, not new capability — each deliverable is a documentation/contract-adjudication task landing in a different file. Deliverable 1 requires a governance decision first (reversibility classification: reclassify to `high` with a stated append-vs-integrate rationale, or keep `medium` and switch the bar to file-fresh-plus-stage per the contract's own procedure) — pick one of the two named alternatives, then apply its own listed downstream edits (`capture/SKILL.md`'s log line, the test pin, and conditionally `auto-mode-contract.md`'s Capture silences row). Deliverables 2 and 3 are prose additions stating an existing (but currently unstated) precedence/behavior — no new mechanism, just making an implicit rule explicit in the file that already governs it. Deliverable 4 extends the existing conformance suite with pins matching whichever text landed from 1–3, leaving the 18 existing pins untouched except where a resolution deliberately changes their target text.
