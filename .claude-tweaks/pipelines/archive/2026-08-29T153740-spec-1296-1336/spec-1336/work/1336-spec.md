# 1336: compare-shell: restyle the judged candidate itself when a tweak lever moves

Surface: web
Design-intent: none

## Current State

`#1207` added a tweak-levers panel to the compare-shell's live focus view (`plugin/skills/design-wrapper/compare-shell/template.html`) — hue/spacing-scale/corner-radius sliders that post a `tweak` event and preview the current value via a readout + a small swatch element in the compare-shell's own UI (`applyTweak()`, driven by `--tweak-*` CSS custom properties on `document.documentElement`).

The judged candidate itself never visibly changes. Each variant renders inside a cross-origin sandboxed `<iframe sandbox="allow-scripts">` (deliberately, no `allow-same-origin` — a security boundary against untrusted, agent-generated candidate markup) that a parent-page CSS custom property cannot reach. `#1207`'s whole-branch review confirmed this is the right call for that record's scope (`risk:low`/`size:medium`) and ruled that "reflected in the live page" means the shell's own preview, not the candidate — but flagged that a human judging a design actually wants to see the *real* candidate reskinned live, and that capability was explicitly deferred, not built.

## Deliverables

- [ ] A convention for a candidate page to opt into live tweak application — a `postMessage` channel from the parent compare-shell into the iframe (`allow-scripts` already permits `postMessage`; no sandbox loosening needed) carrying `{type: 'compare-shell-tweak', token, value}`, with each candidate's own markup choosing whether/how to apply it (e.g. reading the message and setting its own CSS custom properties)
- [ ] Update `seed-compare.mjs` (both live and durable paths) to inject whatever bootstrap script a candidate needs to receive and apply tweak messages, OR document that candidates must opt in themselves
- [ ] Update `plugin/skills/_shared/visual-decision.md`'s `tweak` event description once real candidate reflection exists, since it currently states (accurately, as of #1207) that tweak never restyles the judged candidate itself

## Acceptance Criteria

1. A tweak lever's live-mode change is visibly reflected in the currently-focused candidate's own rendering, not only in the compare-shell's own preview swatch
2. The existing iframe `sandbox="allow-scripts"` attribute is unchanged — no `allow-same-origin` added, no other loosening of the candidate's sandbox
3. A candidate that does not opt into the tweak-message convention keeps working exactly as it does today (no error, no broken render) — this is additive, not a breaking change to the manifest/variant contract

## Technical Approach

Extend `template.html`'s existing `applyTweak(token, value)` (currently only sets `--tweak-{token}` on `document.documentElement`) to also `postMessage({type: 'compare-shell-tweak', token, value}, '*')` into the currently-focused candidate's iframe `contentWindow`. Origin is unconstrained by design — the candidate's origin is opaque under `sandbox="allow-scripts"` without `allow-same-origin`, so a targeted origin can't be asserted; a `token`/nonce field in the message payload lets an opting-in candidate distinguish a legitimate compare-shell message from an unrelated `postMessage` without relying on origin-based trust. A candidate that never registers a `message` listener is unaffected — the message is sent but nobody reads it, satisfying Acceptance Criteria 3 for free. `seed-compare.mjs` needs to decide, and document, whether it auto-injects a small listener bootstrap into every generated candidate page or leaves opt-in entirely to candidate authors; either choice must be reflected in `visual-decision.md`'s `tweak` event description so it stops stating that tweak never restyles the judged candidate.

### Key Files

- `plugin/skills/design-wrapper/compare-shell/template.html` — extend `applyTweak()` to `postMessage` into the focused candidate's iframe
- `plugin/skills/design-wrapper/compare-shell/seed-compare.mjs` — inject (or document the absence of) a candidate-side bootstrap script for the message convention, in both live and durable seeding paths
- `plugin/skills/_shared/visual-decision.md` — update the `tweak` event description once real candidate reflection exists

## Gotchas

- This is a genuinely larger feature than a token-level UI nudge: it requires a message-passing convention every future candidate author needs to know about and choose to implement, not just a template.html change.
- Do not revisit loosening the iframe sandbox as a shortcut — `#1207`'s review explicitly confirmed the sandboxed-without-allow-same-origin posture is deliberate and load-bearing for security against untrusted candidate content.
- A candidate's origin is opaque under `sandbox="allow-scripts"` without `allow-same-origin`, so the `postMessage` target origin can't be asserted (`'*'` is the only option) — the `token` field in the payload is the only means of distinguishing a legitimate compare-shell message, not an origin check.
