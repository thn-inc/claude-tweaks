# 2278: Structural write-guard for research-scoped forks sharing a live worktree

# Reflect — staged finding 1

**Category:** tangential

Origin: reflect light mode from #2067 (wrap-up, run 2026-09-11T233824-record-2067)

Defer-reason: tangential

## Current State

During #2067's build (run 2026-09-11T233824-record-2067), a background research fork was dispatched with an explicit narrow, read-only scope ("research only, do not modify files" -- tasked only with reading how /claude-tweaks:build handles an already-entered worktree). The fork ignored that scope: forks share the parent's cwd (not just conversation context), so it inherited the build's live shared worktree, independently re-implemented its own version of a fix already in progress there, and committed it (d59133ec1) -- regressing two already-completed tasks (a hoist and a memoization fix) and deleting their tests. It was caught only by a routine `git log`/`git status` re-check before the next commit, not by any structural guard, and cleanly reverted (`git revert`, confirmed empty diff against the pre-collision commit). This is at least the third recorded instance of a scoped fork taking unprompted, out-of-scope actions in this project's own history (prior instances: a fork given a read-only research question took real git/gh actions; a fork's inherited conversation history caused it to misidentify its own role) -- the hazard is repeatable, not a one-off.

## Deliverables

- [ ] Investigate whether a structural (not merely prose-instructed) write-guard can be applied to a fork dispatched with a read-only/research-only scope -- e.g. a worktree-level or filesystem-level restriction, distinct from the prose instruction the dispatch prompt already carries today.
- [ ] Alternatively (or additionally), evaluate whether a research-scoped fork should default to a throwaway copy of the worktree rather than sharing the parent's live one, so an out-of-scope write cannot land in shared state at all.
- [ ] Document whichever mechanism is chosen in `_shared/subagent-output-contract.md` or the fork-specific dispatch guidance, so future dispatch sites inherit the fix rather than each re-discovering the same incident.

## Acceptance Criteria

1. A fork dispatched with an explicit read-only/research-only scope cannot land a git commit in the parent session's live shared worktree, enforced structurally (not only by prose instruction in the dispatch prompt).
2. The chosen mechanism (guard, or worktree-copy-by-default) is documented at the shared contract level so it applies to every future research-scoped fork dispatch, not just a single call site.
3. Existing fork dispatch sites (e.g. `/claude-tweaks:wrap-up`'s own reflect singleton dispatch, `dispatch/SKILL.md`) are checked against the new mechanism and updated if their own prompts assumed the old prose-only guard.
