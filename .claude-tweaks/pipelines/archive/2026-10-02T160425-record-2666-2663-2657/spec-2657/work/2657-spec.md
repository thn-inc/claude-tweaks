# 2657: Add JWT algorithm-confusion checks to the security hardening checklist

Surface: backend

## Current State
A social-media Reel (hook-only caption; transcribed) names a three-point JWT validation check: (1) reject tokens with `alg: none` explicitly, since some JWT libraries accept unsigned tokens by default; (2) enforce the expected signing algorithm server-side, closing the algorithm-confusion attack where an attacker submits an HMAC-signed token using the server's RSA public key as the HMAC secret; (3) always set short token expirations and use a refresh-token flow, since an unexpiring JWT functions as a permanent access key once stolen. This overlaps with, and is meant to extend, the pre-launch security hardening checklist filed as `#2624` (secrets in client bundle, RLS/ownership checks, AI-endpoint auth/rate-limiting) — that record covers authorization and secret-handling gaps but not JWT-specific token-validation attacks. `#2624` itself is currently unbuilt (open, `priority:medium`, no skill implementation exists yet) — there is no live checklist artifact to append rows to today.

## Deliverables
1. Three JWT-validation checklist rows, each with a copy-paste audit prompt matching the pattern `#2624` establishes for its own rows: (a) explicit `alg` allowlist that rejects `none` and any algorithm outside the expected set; (b) server-side enforcement of the expected signing algorithm (rejecting a client-supplied `alg` header value that doesn't match what the server expects to verify with); (c) short-lived access tokens paired with a refresh-token flow, flagging any JWT issued with no expiration or an excessively long one.
2. Documentation of the dependency on `#2624`: if `#2624` ships its checklist/skill first, these three rows get appended directly to it; if this record ships first, it stands alone as an independent JWT-focused checklist file that `#2624`'s eventual implementation is expected to fold in, with an explicit cross-reference in both directions so the two never diverge into duplicate content.
3. A worked example (a sample app snippet or a described scenario) for each of the three checks, demonstrating what a violation looks like, to ground the audit prompt in something a builder can pattern-match against.

## Acceptance Criteria
- Running the `alg: none` check's audit prompt against a sample JWT-verification code path that accepts an unsigned or unexpected-algorithm token flags a violation naming the specific weakness (missing algorithm allowlist).
- Running the algorithm-confusion check's audit prompt against a sample verification path that doesn't pin the expected algorithm server-side (e.g., calls a JWT library's verify function without an explicit `algorithms:` option) flags a violation.
- Running the token-lifetime check's audit prompt against a sample token-issuance path with no expiration claim, or an expiration longer than a stated short-lived threshold, and no refresh-token flow, flags a violation.
- Running all three checks against a sample app that correctly allowlists algorithms, pins the expected algorithm server-side, and issues short-lived tokens with a refresh flow produces no false-positive flags.
- The checklist rows' documentation states explicitly that they extend `#2624` rather than duplicate it, and names the current build-order dependency (which record ships the checklist artifact first).

## Gotchas

This record may ship first as a standalone JWT checklist; whichever record ships second must fold the other in and add the cross-reference, rather than leaving two independent, silently-diverging checklists.
