# 2666: Add secrets-manager + rotation check to the security checklist

Surface: backend

**Related:** #2665

## Current State
A social-media Reel (hook-only caption; transcribed) gives a three-step fix for long-lived hard-coded API keys: (1) move secrets to a dedicated secrets manager (Doppler, Infisical, or AWS Secrets Manager are named as examples) that fetches at runtime instead of bundling secrets at deploy time — not a `.env` file or the hosting platform's dashboard; (2) dual-key rotation — generate the new key, deploy it, verify traffic against it, then revoke the old one, so two keys remain valid during the transition window (zero downtime); (3) automate the rotation schedule (e.g. a cron job every 30 days) so a leaked key's blast radius is capped at the rotation interval instead of being unbounded. This extends the pre-launch security checklist (`#2624`), which currently covers "no secrets in client bundle" but not secret-storage or rotation strategy — a related but distinct concern (a secret can be correctly kept server-side and still be a long-lived, unrotatable, single point of compromise). `#2624` is currently unbuilt (open, no shipped skill implementation).

## Deliverables
1. A checklist row verifying secrets live in a dedicated secrets manager fetched at runtime, rather than a `.env` file committed or deployed alongside the app, or values entered only into the hosting platform's dashboard with no independent management layer.
2. A checklist row verifying a documented key-rotation procedure exists, specifically one that supports dual-key validity during a transition window (new key generated and deployed, traffic verified, then the old key revoked) rather than a rotation that requires downtime or breaks in-flight requests.
3. A checklist row verifying the rotation schedule is automated (e.g., a scheduled job) rather than manual-only or undocumented, so a leaked key's exposure window is bounded by the rotation interval instead of being open-ended.
4. Documentation cross-referencing `#2624`, explicitly distinguishing this record's scope (where secrets live and how they're rotated) from `#2624`'s "no secrets in client bundle" check (whether a secret leaks into client-visible code at all) — the two are complementary, not overlapping.

## Acceptance Criteria
- The secrets-manager check, run against a sample app whose secrets are read only from a `.env` file with no dedicated secrets-manager integration, flags a violation.
- The secrets-manager check, run against a sample app that fetches secrets at runtime from a dedicated manager (any of Doppler, Infisical, AWS Secrets Manager, or an equivalent), passes without a false-positive flag.
- The rotation-procedure check flags an app with no documented rotation procedure at all, and passes an app whose documented procedure supports dual-key validity during a transition window.
- The rotation-schedule check flags a rotation procedure that is manual-only (no automation, no defined interval), and passes one wired to a scheduled job with a defined interval.
- Documentation cross-references `#2624` by number and states explicitly how this record's scope differs from `#2624`'s existing "no secrets in client bundle" row.

## Release Note

Added a security checklist item for storing secrets in a secrets manager and rotating them.

## Technical Approach
Since `#2624` has no shipped skill implementation yet, land this as a standalone secrets-lifecycle checklist section (same pattern already established for `#2657`, `#2663`, and `#2665`'s own additions to the same unbuilt `#2624`), written to merge cleanly into `#2624`'s eventual body/skill once that record ships. None of the three checklist rows are name-specific to a particular secrets-manager vendor — the check verifies the *properties* (runtime fetch vs. deploy-time bundling; dual-key rotation support; automated schedule), detectable via looking for the absence of raw secret values in deploy-time config/build artifacts and the presence of a secrets-manager SDK/client library import, rather than hardcoding a check for any one named vendor's API.

### Key Files
- A new checklist file (path determined by whichever skill or doc structure `#2624`'s implementation adopts, e.g. under `plugin/skills/` if a security-checklist skill is created, or `docs/reference/` if it remains a static checklist) — holds the three secrets-lifecycle rows and their audit prompts.
- `#2624`'s own body/eventual implementation file — cross-reference added once both records have landed, with an explicit scope-boundary note distinguishing this record's rows from `#2624`'s existing client-bundle-secrets row.

## Gotchas
- `#2624` is unbuilt as of this shaping — there is no live checklist artifact to append rows to today; this record may ship first as a standalone section, and whichever record ships second must fold the others in with cross-references, avoiding silently-diverging checklists (same build-order caveat already noted on `#2657`, `#2663`, `#2665`).
- Detecting "secrets fetched at runtime from a dedicated manager" via static inspection is inherently approximate — an app could import a secrets-manager SDK but still hardcode a fallback secret elsewhere, or could correctly avoid `.env` files while using a home-grown runtime-fetch mechanism this check wouldn't recognize as a "dedicated manager." Frame findings as "likely mismatch, flag for human review" rather than a definitive pass/fail, consistent with how `#2663`'s privacy-policy-accuracy check is already framed.
- Do not conflate this record's rotation-procedure/schedule checks with `#2624`'s client-bundle-secrets check — a secret can pass `#2624`'s row (never appears in client code) while still failing every row this record adds (no manager, no rotation, no schedule); keep the two checklist rows sets and their pass/fail logic independent.
