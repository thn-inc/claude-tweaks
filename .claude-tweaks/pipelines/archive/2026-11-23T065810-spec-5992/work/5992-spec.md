# 5992: Replay task and whole-branch reviewers, and measure what task reviews catch that the whole-branch review would not

Surface: backend
Risk-flags: none

## Overview

Adds the task and whole-branch reviewers to the review replay, plus a counterfactual arm that answers the design's first Phase 14 question: what do task reviews catch that the whole-branch review would not? For each archived task review that asked for fixes, the run's own whole-branch review prompt is replayed against the branch as it stood just before that fix, and scored on whether it raises the task reviewer's findings. With the same roles replayable under effort arms, this also covers the task and whole-branch parts of the effort question. The design's evidence: Opus task reviews needed fixes 39% of the time and Sonnet ones 13.5%, while the whole-branch review still reported a Critical or Important issue in 70% of runs after every task review passed. Nobody knows how much of the task reviews' catch the whole-branch review would have made on its own (`docs/superpowers/specs/2026-11-18-pipeline-economy-design.md`, Phase 14).

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Removing task reviews or changing any reviewer's tier or effort. The live replay run decides that.
- Matching findings by meaning with a model judge. Matching is by location. A finding with no location is reported as unlocated, not as caught or missed.
- Replaying plan reviews or re-reviews (the `re-review` role).
- Changing the lens role or the tiebreak replay. Shared input readers (`readRunInput`'s archived-run `work/` fallback, `originRefsOf`'s ref parsing) are fixed for all roles, lens included: the whole-archive extracts could not write without them, and the lens output schema is unchanged (Review Console, build-deviation-1).

## Deliverables

- [ ] `extract-reviews --role task` and `--role whole-branch`: select dispatches by role (whole-branch through `isWholeBranch`), take the prompt from the transcript, or from the file a pointer prompt names, with exclusion `prompt-file-gone` when that file no longer exists. Take the range from the prompt's own sha pair: the first sha is the base and the second the head. A sha that is not in the clone excludes the slot as `commit-not-in-clone`. Rewrite as the lens role does: shas, the worktree path, spec and plan paths (the plan is in the tree at head), and the `[Effort: …]` line removed. Archived findings per slot: the verdict, and each `Critical`, `Important` and `Minor` item with its location when it has one, read by a per-item parser added in `reviews-score.js` (`parseReviewCounts` only counts items).
- [ ] `extract-reviews --role task-vs-branch`: for each archived task review whose verdict is `Needs fixes` with at least one `Critical` or `Important` item, one slot replaying that run's archived whole-branch prompt against the range from the whole-branch prompt's base to the head that task review reviewed. A run with no usable whole-branch prompt excludes its task reviews as `no-whole-branch-prompt`. A task-review prompt with no reviewed head is `no-sha-range`. When a run has several whole-branch dispatches, the first one, the review's own pass, supplies the prompt and the base. Each `Needs fixes` task review is its own slot, even when two reviews cover one task. The slot's archived findings are the task review's `Critical` and `Important` items.
- [ ] `score-reviews` sections, per arm:
  - `task`: verdict agreement with the archive (Approved or Needs fixes) in total and by archived tier; recall of the archived `Critical` and `Important` items that have a location; items per review by severity.
  - `wholeBranch`: recall of the archived located items; items per review by severity; the share of reviews reporting a Critical or Important item (the design's first quality guard).
  - `taskVsBranch`: of the located task-review items, the share the whole-branch replay raised (a replay item `near` it), by severity and by the task reviewer's archived tier; and the list of items not raised, each with run, path, line, severity and text, so a human can read what only the task review caught.
  - In every section, archived items with no location are counted as `unlocated`, outside every share. `near` is `counterfactual.js`'s rule (same repository-relative path, lines within `NEAR_LINES`, 5), shared with the lens role and the tiebreak scoring, and a path mismatch is not near. A share's denominator is located items; the unit of a slot is one task review.
- [ ] A control for `task-vs-branch`: each slot gets a sibling slot replaying the same whole-branch prompt at the branch's final head, scored on the same located task items. `taskVsBranch` reports that `baselineRecall` beside the caught share, by severity.
- [ ] A reply that does not parse (`parseTaskVerdict` null for a task slot; for a whole-branch or `task-vs-branch` slot, no `Critical`/`Important`/`Minor` heading and no line matching `no issues`, case-insensitive) is `notJudged` with `could-not-parse`, and the command exits 3.
- [ ] The journey from the second sub-issue gains a section for the three roles. `USAGE` lists the roles.
- [ ] Tests: fixtures for a run with two task reviews (one `Approved`, one `Needs fixes` with a located Important item and an unlocated Minor item) and one whole-branch review, with a git history in which the task's fix is a separate commit.

## Acceptance Criteria

1. On the fixture, `extract-reviews --role task-vs-branch` writes exactly one slot, for the `Needs fixes` task review. Its clean repository's head tree equals the fixture's commit that task review reviewed, not the branch's final head. The test compares `git ls-tree -r` output.
2. That slot's prompt is the archived whole-branch prompt with the replay shas, and it contains neither the task reviewer's prompt nor its reply text.
3. `score-reviews` on a fixture workflow directory, where the replayed whole-branch reply raises an Important item 2 lines from the task's located item, reports `taskVsBranch` caught 1 of 1 and an empty not-raised list. With a reply raising nothing near it, the count is 0 of 1 and the not-raised list holds that item.
4. The unlocated Minor item is counted as `unlocated: 1` and is not in any denominator.
5. `--role task` on the `Approved` review, replayed with a reply that reads `Task quality: Needs fixes`, counts one verdict disagreement.
6. A pointer prompt whose file is gone is excluded as `prompt-file-gone` and produces no prompt file.
7. On the fixture, `--role task-vs-branch` writes two slots for the `Needs fixes` review, one at the task-reviewed head and one at the final head, and `score-reviews` reports both `caught` and `baselineRecall` for it.

## Gotchas

- The whole-branch prompt's "What Was Implemented" still describes the whole branch when it is replayed against an earlier head, so the replay may report later work as missing. That noise does not affect `taskVsBranch`, which only asks whether the task's own located items were raised. Do not rewrite the description, because a hand edit would make the prompt differ from the archive in more than the range. A reviewer told the work is complete may treat in-progress files differently, so the earlier-head replay is checked against a control: the same whole-branch prompt replayed at the branch's final head, scored on the same located task items. `taskVsBranch` reports that baseline recall beside the caught share.
- A task review's reviewed head is the task's commit before its fix round, so the fix is not in that tree. Check this on the fixture (criterion 1), because getting the head wrong would turn every replay into a review of already-fixed code and push the caught share to zero.
- The head is the task's commit before its fix round because a fix round is re-reviewed under the `re-review` role, which this record does not select. Add a fixture whose task-review prompt range ends after the fix and assert that it is not read as pre-fix.
- Only runs with both a task-review range and a usable whole-branch prompt survive, which skews the sample toward one era of prompt templates. Score output shows retained and excluded counts per reason and per archived tier beside every share, and a share is not an archive-wide figure.
- A pointer prompt's file is read as the reviewer saw it. The `[Effort: …]` line is removed by the same canonical match the lens role uses.
- `isWholeBranch` and `LOCATION_RE` may not be exported today. Export them in place, with no copy and no behaviour change in the cost report. `tests/pipeline-cost-report/` must still pass unchanged.
- Task-review items are prose bullets. `LOCATION_RE` takes the first `path.ext:line` in an item. An item that cites several locations is caught when any one of them is `near` a replay item. Report this rule in the journey.

## Plan Review Clarifications

- Decided by the user at plan review: the `task-vs-branch` range ("the range from the whole-branch prompt's base to the head that task review reviewed") uses the whole-branch prompt's base when it is an ancestor of the task-reviewed head, and otherwise `git merge-base` of the two; the slot records `baseFrom: whole-branch | merge-base`, and a pair with no merge base is excluded as `no-merge-base`. Not taken: diffing the whole-branch base literally, which on a run that merged main in before its whole-branch review shows main's newer commits as reverted.
- Decided by the user at plan review: AC1's "writes exactly one slot" means exactly one slot at the task-reviewed head, beside its final-head control sibling (AC7's second slot); the control always runs. Not taken: an opt-in control flag.
- Decided by the user at plan review: the control's "branch's final head" is the head the archived whole-branch prompt names, so the control is the archived whole-branch review replayed exactly. Not taken: the run's last branch commit, which includes fix waves after the whole-branch review.

## Build Deviations (Beneficial, /build Common Step 4.5)

- The three roles live in a new module, `tools/review-replay/reviews-branch.js`, beside `reviews-extract.js` rather than inside it. This keeps the lens extract path separate, and both roles share `renderSlot`, `promptOf`, `strippedReply` and `readRunInput`.
- A pointer prompt is any prompt that both says its instructions are in or from "this file" (or "Read this file") and carries exactly one absolute path alone on its own line; the same-line form `(it is your prompt …):` also counts. The one-line shape the Current State describes matched 2 of 204 real pointer prompts. A cited file that reads but has no sha pair, while the prompt has one, is a hybrid prompt: the original prompt is replayed.
- The fixtures are built at test time by `tests/review-replay/reviews-fixture.js` (`buildBranchFixture`), not committed under `tests/fixtures/review-replay/reviews/`. This follows the lens role's fixture builder, which needs a real git history.
- `parseReviewCounts` is rebuilt on a shared walker, `walkReviewItems`, exported from `guards.js` and used by the per-item parser, so there is no copy. `tests/pipeline-cost-report/` passes unchanged.
- The spec does not list these exclusion and count keys, but the build adds them so a reply that does not parse is never scored as a review that found nothing:
  - `items-unparsed`: an archived task-vs-branch reply that has a verdict but no parseable items.
  - `recall.replayItemsUnparsed` and `itemsUnparsed`: the same case, counted in the scores.
  - Task-vs-branch totals: `{ reviews, slots, byTaskTier, notQualifying }`, counted in task reviews.

  Qualification (Needs fixes plus at least one Critical or Important item) is read from the raw reply before the tier and prompt checks, so only qualifying reviews can be excluded.
- In Deliverable 5, "a line matching `no issues`" means a line that starts with "No issues", after optional bullets or emphasis. The phrase mid-sentence does not mark an empty review.
