# 1467: claim-targets.js group claim/release does one git-CAS round-trip per issue instead of amortizing the fetch

Surface: backend

## Current State

`plugin/bin/lib/claim-targets/claim-targets.js`'s group claim/release loop (`run()`) performs one full git-CAS round-trip (`git fetch` + a later `git push`) per issue, sequentially, via `claimStore.readClaimBlob`/`writeClaimBlob`. `readClaimBlobGit` (`plugin/bin/lib/issues/claims-git-cas.js`) deliberately re-fetches the branch tip on every call ("always the live remote tip, never a locally-cached one") so a batch of N issues costs N sequential fetches against the same `claims-registry` branch instead of fetching the tip once and chaining each write's resulting commit sha as the next read's starting point.

## Deliverables

- Design a batch-aware calling convention that lets a caller supply an already-known tip sha to `readClaimBlobGit`/`writeClaimBlobGit` instead of always re-fetching, while preserving each op's own correctness (a write's resulting commit becomes the next read's trusted tip only when that write actually landed; any rejection still falls back to a fresh fetch for that item).
- Wire `claim-targets.js`'s group loop onto the new convention so a batch of N issues costs O(1) fetches in the common (no-contention) case instead of O(N), while keeping today's per-issue correctness guarantees (a write to issue A must never be trusted as the tip for issue B if A's write itself was rejected or fell back to the contents API).

## Acceptance Criteria

- [ ] A batch group claim (`bin/claim-targets.js`) of N issues performs a bounded, sub-N number of `git fetch` calls in the no-contention case, verified by a spy-count test
- [ ] Existing per-issue correctness tests in `tests/bin-lib/claim-targets/claim-targets.test.js` and `tests/bin-lib/issues/claims-git-cas.test.js` still pass unchanged
- [ ] A test covers the mixed-outcome case (issue A's write rejected/fell back) proving issue B's read does not trust a stale or wrong tip as a result

## Technical Approach

Add an optional "known tip" parameter to the existing read/write seam rather than changing its shape — `readClaimBlobGit`/`writeClaimBlobGit` already accept a `runner` dep and `writeClaimBlobGit` already takes an `expectedTipSha`; `readClaimBlobGit` needs the equivalent so it can skip its own `fetch`+`rev-parse` and go straight to `git show {knownTip}:{path}` when the caller supplies one. `claimStore.readClaimBlob`/`writeClaimBlob` thread this through as an additional optional argument, defaulting to "fetch fresh" so every non-batch caller (`release-merged.js`, `release-claim.js`) is unaffected.

`claim-targets.js`'s `run()` loop tracks one `knownTip` variable across its per-issue iteration: seeded from the first issue's read, updated to a write's resulting commit sha only on `write.ok === true`, and reset to `null` (forcing a fresh fetch) whenever an item's read/write falls through to the contents-API path, is rejected, or hits a transport failure — since the contents-API write path can move the same `claims-registry` branch tip without producing a git commit sha this loop can chain from. The existing per-issue disambiguation/retry logic inside `writeClaimBlob` (rejected-push-vs-unrelated-activity, `MAX_CAS_ATTEMPTS`) is unchanged; only the *starting* lease for each item's first read changes.

### Key Files

- `plugin/bin/lib/issues/claims-git-cas.js` — `readClaimBlobGit` gains an optional pre-known tip sha that skips the internal `fetch`/`rev-parse` and reads directly via `git show {tip}:{path}`
- `plugin/bin/lib/issues/claim-store.js` — `readClaimBlob`/`writeClaimBlob` thread the optional known-tip through to the git-CAS calls, unchanged default (fetch fresh) for existing non-batch callers
- `plugin/bin/lib/claim-targets/claim-targets.js` — `run()`'s per-issue loop carries a `knownTip` variable, updated from each landed write's commit sha, reset to `null` on any fallback/rejection/transport-failure for that item
- `tests/bin-lib/claim-targets/claim-targets.test.js` — spy-count assertion on the injected git runner's fetch calls across a multi-issue batch; mixed-outcome test (one issue's write rejected/falls back) proving the next issue's read does not trust a stale or wrong tip
- `tests/bin-lib/issues/claims-git-cas.test.js` — cover the new known-tip read path on `readClaimBlobGit` independently of the batching caller

## Gotchas

- The compare-and-swap lease is a **git tip sha** when read via git-CAS but a **contents-API blob sha** when read via the contents-API fallback — these are two different shapes and, per `claim-store.js`'s existing comments on `writeClaimBlob`, must never be threaded across a transport fallback. The batch loop's `knownTip` must be discarded (forcing a fresh fetch) the moment any item in the batch falls back to the contents API, not just for that one item — the contents-API write can move the same `claims-registry` branch tip without producing a git commit sha the loop can chain from.
- A rejected git-CAS push (`--force-with-lease`) can mean either a genuine contest or unrelated activity elsewhere on the branch; `writeClaimBlob` already disambiguates this with a fresh read and retries up to `MAX_CAS_ATTEMPTS`. The batch convention changes only the *starting* lease for the next item's first read — it must not shortcut or duplicate that existing per-write disambiguation logic.
- `readClaimBlob`/`writeClaimBlob`'s signatures are shared by non-batch callers (`release-merged.js`, `release-claim.js`) that must keep working unchanged — the known-tip addition should be an optional parameter following the same additive pattern the file already uses for `gitRunner`, not a required one.
