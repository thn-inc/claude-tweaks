# 1466: claims-git-cas.js duplicates durable-state.js's generic CAS primitive

Surface: infra

## Current State

`plugin/bin/lib/issues/claims-git-cas.js` hand-rolls a git compare-and-swap (CAS) engine for the claims-registry blob lock: it fetches the `claims-registry` branch tip, reads a single raw-string blob per issue via `git show`, and writes via its own read-tree/update-index/write-tree/commit-tree sequence followed by `git push --force-with-lease` as the atomic test-and-set. It classifies failures into `missing-path`, `contested`, `secondary-rate-limit`, and `transport-failure`, a distinction `claim-store.js`'s contents-API-fallback logic depends on (`readClaimBlobGit`/`writeClaimBlobGit`), and has no internal retry loop — retries are the caller's job.

`plugin/bin/lib/health-core/durable-state.js`'s `createNamespacedState` already implements a generic version of the same mechanism: git tree/commit primitives (`hash-object`/`mktree`/`commit-tree`/plain `push` as the CAS), a `{key, file, default, serialize?}`-driven multi-file namespace read/write, and its own internal CAS retry loop (`MAX_CAS_ATTEMPTS` with backoff/jitter, plus a post-failure re-fetch to distinguish "actually landed" from a genuine rejection). It targets the `health-state` branch, always JSON-parses file content, and collapses every write failure to `{ok, error}` with no conflict/secondary-rate-limit distinction. `plugin/bin/lib/issues/merge-lane-breaker.js` already reuses it directly for its own `breaker.json`/`watched.json` namespace.

The two engines have diverged with no cross-reference between them: different target branches, different content shape (raw string vs. JSON-parsed multi-file), different failure classification (four-way vs. binary), and different retry ownership (caller-driven vs. built-in).

## Deliverables

- Evaluate whether `claims-git-cas.js`'s read/write primitives can be re-expressed on top of `createNamespacedState` (or a shared lower-level primitive extracted from both), given the real differences: `claims-git-cas.js` writes/reads a single raw-string blob per issue with its own conflict/secondary-rate-limit classification consumed by `claim-store.js`'s contents-API-fallback logic, while `createNamespacedState` reads/writes JSON-parsed multi-file namespaces with a simpler write-only conflict signal (no fallback-transport concept).
- If consolidation is viable, migrate `claims-git-cas.js` onto the shared primitive (or extract one both can share) and retire the duplicated tree/commit plumbing.
- If not viable without changing `createNamespacedState`'s contract, document why in both files' header comments so a future reader doesn't re-propose a naive merge.

## Acceptance Criteria

- [ ] A design decision is recorded (consolidate, or documented as intentionally separate) with the specific API-shape differences that drove the call
- [ ] If consolidated: `tests/bin-lib/issues/claims-git-cas.test.js` and `tests/bin-lib/health-core/durable-state.test.js` both still pass, and no consumer's observable behavior changes
- [ ] If kept separate: both files cross-reference each other's header comments so a correctness fix in one prompts a check of the other

## Technical Approach

1. Enumerate the exact API-shape gaps between the two engines before deciding feasibility:
   - `createNamespacedState`'s `showFile` always `JSON.parse`s the blob content; `claims-git-cas.js` needs the raw string back untouched.
   - `createNamespacedState`'s `writeState` collapses every failure to `{ok, error}`; `claim-store.js`'s fallback to the contents API depends on distinguishing `conflict` from `secondaryRateLimit` from a generic transport failure.
   - `createNamespacedState` hardcodes `HEALTH_STATE_BRANCH`; `claims-git-cas.js` targets `CLAIMS_BRANCH` — the branch would need to become a parameter.
   - `createNamespacedState`'s internal `MAX_CAS_ATTEMPTS` retry loop (with backoff/jitter and a post-failure re-fetch check) has no counterpart in `claims-git-cas.js`, which is retried by its caller instead.
2. Decide viability: if a `raw`/non-JSON file-spec option, a failure-classification passthrough, and a `branch` parameter can be added to `createNamespacedState` without changing `createDurableState`'s byte-identical behavior (pinned by its own test suite) or `merge-lane-breaker.js`'s existing contract, migrate `claims-git-cas.js`'s `readClaimBlobGit`/`writeClaimBlobGit` onto the extended primitive and delete the duplicated tree/commit plumbing in `claims-git-cas.js`.
3. If any gap can't be closed without complicating the four existing health-skill callers or `merge-lane-breaker.js`, keep the two engines separate and write the specific reason into both files' header comments, with each header cross-referencing the other by path.
4. Either way, verify `claim-store.js`'s own caller-side retry logic and (if migrated) `createNamespacedState`'s internal retry loop don't double-retry the same conflict.

### Key Files

- `plugin/bin/lib/issues/claims-git-cas.js` — the claims-registry CAS engine; either migrated onto the shared primitive or given the "kept separate" header note
- `plugin/bin/lib/health-core/durable-state.js` — `createNamespacedState`, the generic CAS primitive; either extended to absorb the raw-blob/branch/classification gaps, or given the reciprocal header note
- `plugin/bin/lib/issues/claim-store.js` — sole consumer of `claims-git-cas.js`'s read/write functions and their conflict/secondaryRateLimit signal; must keep working unchanged either way
- `plugin/bin/lib/issues/merge-lane-breaker.js` — existing second consumer of `createNamespacedState`; the regression surface if the primitive's contract changes

## Gotchas

- `createNamespacedState`'s `showFile` always JSON-parses; any consolidation needs a non-JSON read/write path added without disturbing the four existing health-skill callers that rely on JSON parsing.
- `claim-store.js`'s contents-API fallback depends on `conflict` vs. `secondaryRateLimit` vs. generic `transport-failure` surviving as distinct signals — `createNamespacedState`'s current `{ok, error}` shape doesn't carry that distinction today.
- `createNamespacedState` retries internally (with backoff/jitter and a landed-anyway re-fetch check); `claims-git-cas.js` has no such loop today, so migrating it changes retry timing/semantics that `claim-store.js`'s own caller-side retry wasn't written against — check for double-retry.
- If the call is "keep separate," the acceptance criteria require both header comments to name the *specific* API-shape differences, not a generic "these are different" note.
