# 2554: build: records whose Deliverables are wholly operational have no lane — zero-code runs pay materialize/plan/PR ceremony and two full verifications

Surface: infra

## Current State
A `ready` record whose every Deliverable is an operational action (dispatch a deploy workflow, trigger a job run through an API, apply infrastructure, then verify the live result) with no source file changes has no dedicated lane in `/claude-tweaks:build` or `/claude-tweaks:flow`:
- `build/SKILL.md`'s Spec Step 2.5 ("Classify and Seed Manual Steps") is written assuming a spec has a `## Manual Steps` section. When the record's `## Deliverables` list *is* the operational work (no separate Manual Steps section), the executor has to infer both that the Deliverables are the triage input and that inline auto-execution with `decisions.md` logging is the licensed path — `execution-mode-policy.md` otherwise forbids main-thread execution, and nothing in the current prose states the ops-only case explicitly.
- Spec Step 3 and Common Steps 1.5, 1.7, 2, 3, 6, 6.5 then all resolve to `SKIP`, producing nine degrade-trace lines for a run with no plan to write and no task to dispatch.
- Common Step 5 verifies the tree and stamps the materialized commit. The build phase's own exit then commits the run ledger (`docs/plans/*-ledger.md`), which changes `HEAD`, so the verification stamp's sha no longer matches. `/claude-tweaks:test`'s Skip-if-recent (`test/verification.md`) sees this mismatch and re-runs the full suite. Observed on one run in a private project: two separate ~10-minute full verifications triggered by a diff whose only change was two markdown files (the ledger and one plan file).

## Deliverables
1. Update `build/SKILL.md`'s Spec Step 2.5 to state explicitly: when a record carries no `## Manual Steps` section but its `## Deliverables` are wholly operational actions, the Deliverables list itself is the triage input for inline auto-execution (with `decisions.md` logging), and a record whose Deliverables are *all* operational proceeds directly to Common Step 5 with one consolidated SKIP entry instead of one SKIP per code-oriented step.
2. Update `test/verification.md`'s Skip-if-recent logic so a stamp still verifies `HEAD` when every commit between the stamped sha and `HEAD` touches only pipeline-bookkeeping paths (`docs/plans/*-ledger.md`, `.claude-tweaks/pipelines/**/work/*.md`) — reusing the same "bookkeeping-only delta" classification the multi-spec `test` step already applies elsewhere (classified `none`).
3. (Optional, if scoped in during build) a `/claude-tweaks:flow` fast path for wholly-operational records: build (materialize + inline ops execution + one verification) → test (skip by stamp, using the widened Skip-if-recent from Deliverable 2) → review (spec compliance judged against the live operational evidence, not a diff) → wrap-up.

## Acceptance Criteria
- A record whose `## Deliverables` are all operational actions and carries no `## Manual Steps` section, run through `/claude-tweaks:build`, produces exactly one consolidated SKIP entry in the degrade trace for the code-oriented steps (Spec Step 3, Common Steps 1.5/1.7/2/3/6/6.5) instead of one per step.
- The same record's Spec Step 2.5 output shows the Deliverables list was read as the triage input for inline auto-execution, with corresponding `decisions.md` log entries for each operational action taken.
- After Common Step 5's verification stamp and the build phase's own ledger commit, a subsequent `/claude-tweaks:test` run recognizes the ledger-commit-only delta as bookkeeping-only (per the widened Skip-if-recent logic) and does NOT re-run the full suite — verified by comparing wall-clock duration or an explicit skip-reason log entry against the pre-fix two-full-verification behavior.
- The bookkeeping-only-delta classification in `test/verification.md` matches the same classification already used by the multi-spec `test` step for `none`-classified deltas, confirmed by reading both code paths and checking they resolve to the same path-pattern set (or a documented superset).
- If Deliverable 3 is included: a wholly-operational record run through `/flow` completes build→test→review→wrap-up with zero SKIP-triggered full-suite re-runs caused solely by the ledger commit.

## Release Note

Added a lighter build path for records whose work is entirely operational.

## Technical Approach
This is a documentation/prose change to two skill files (`build/SKILL.md`, `test/verification.md`) plus, optionally, a fast-path addition if scoped into Deliverable 3. No new code artifacts are required for Deliverables 1-2 — both are skill-authoring changes to existing markdown prescribing agent behavior. Deliverable 2's path-pattern set should be derived from (or a superset of) whatever pattern the multi-spec `test` step already uses for its `none` classification, to avoid two divergent definitions of "bookkeeping-only."

### Key Files
- `plugin/skills/build/SKILL.md` — Spec Step 2.5 ("Classify and Seed Manual Steps"); add the ops-only Deliverables-as-triage-input case and the consolidated-SKIP behavior
- `plugin/skills/test/verification.md` — Skip-if-recent logic; widen the stamp-still-valid condition to tolerate a bookkeeping-only delta between stamped sha and `HEAD`
- `plugin/skills/flow/SKILL.md` (or its materialize/phase sub-files) — only if Deliverable 3 is scoped in, add the fast-path sequencing for wholly-operational records

## Gotchas
- Confirm the exact path-pattern set the multi-spec `test` step already uses for its `none` (bookkeeping-only) classification before writing a new one for Skip-if-recent — duplicating a slightly different pattern set risks the two mechanisms disagreeing on what counts as bookkeeping-only.
- Widening Skip-if-recent must not create a hole where a real code change disguised as touching only `docs/plans/*-ledger.md`/`.claude-tweaks/pipelines/**/work/*.md` paths escapes verification — those paths should genuinely never carry source-code changes, but worth a sanity check against the path patterns' actual scope.
- Deliverable 3 (the `/flow` fast path) is explicitly optional in the original request — scope it in only if the maintainer wants the full lane, not just the two prose fixes that address the immediate double-verification cost.
