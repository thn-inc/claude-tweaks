# 1073: apply-refine-labels.js — label edit + comment share one try/catch, losing partial success on comment failure

Origin: ledger resolve gate

Defer-reason: needs-human-decision

## Current State

plugin/bin/apply-refine-labels.js run() runs a Flag-back-style action's label edit (deps.gh(editArgs)) and its follow-up comment call (deps.gh([...issue comment...])) inside one try block (~line 130-142). Only after both succeed does ok.push/appendEntry fire. A comment-call failure after a successful edit throws into the outer catch (~line 165), so the whole action lands in failed even though the label change already landed on the issue — no ok entry, no decisions.md line, and the JSON summary error message describes only the comment failure, not the edit that actually succeeded.

## Deliverables

- [ ] Split the edit and comment gh calls into separate try/catch inside the loop body.
- [ ] Log the edit's success independently (its own appendEntry call) before attempting the comment.
- [ ] Push to failed only for whichever specific step actually threw.
- [ ] Add a test asserting the label-only decisions.md line exists when the comment step is the one that fails (the existing ok/failed summary shape read by tests/apply-refine-labels.test.js may need to widen to a per-step result — update those assertions too).

## Acceptance Criteria

A batch action whose label edit succeeds but whose follow-up comment call fails still produces a decisions.md line (or ok entry) recording the label's edit as landed, distinct from the comment's own failure — with a test proving it.
