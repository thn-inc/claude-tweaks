## Current State
During record #815's `/build` phase (a prior, separate `/flow` invocation), `build/worktree-setup.md`'s `record-worktree` call was never made — `run-state.json` was never written for run `2026-08-26T215430-record-815`, even though two commits landed successfully in its worktree (`c963104b2`, `f6837385f`). The commit-tracking PostToolUse hook's event log for those two commits, and a `worktree-staleness` check, were instead appended into an unrelated, unrecorded run's `events.jsonl` (`2026-08-26T212441-record-769`) — the same session's previously-active run, matched by `sessionId` rather than by the worktree path the commits actually happened in. Because `run-state.json` was missing, `build/worktree-setup.md`'s "non-skippable" PR-early lifecycle (`[IL-131]`) also never ran: no branch was pushed and no PR was opened until a later `/flow review,polish,wrap-up` catch-up call (this run) diagnosed the gap, re-stamped the worktree assignment via `hooks.js record-worktree`, pushed the branch, and opened/recorded draft PR #1519 by hand.

## Deliverables
1. Root-cause why the `/build` phase's `record-worktree` call was skipped for this run (a build-side omission, a race, or a resolver bug) -- check whether other recent single-record dispatch runs show the same gap.
2. Decide whether `bin/lib/hooks/context.js`'s commit-event/worktree-staleness logging should refuse the session-scoped `sessionId` fallback silently, and instead surface a loud warning (or hard-fail) when no run's `run-state.json.worktree` matches the cwd a commit actually happened in -- silent misattribution into an unrelated run's audit trail is worse than a visible gap.

## Acceptance Criteria
A fresh single-record `/dispatch` -> `/flow` run's `/build` phase reliably calls `record-worktree` before its first commit (verified via a new or existing test), and the commit-event/staleness hooks either match the owning run correctly or emit a diagnosable warning instead of silently attributing to the wrong run.
