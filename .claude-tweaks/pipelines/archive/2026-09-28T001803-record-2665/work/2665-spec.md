# 2665: Add Cloudflare WAF/rate-limiting config check for auth endpoints

Surface: backend

**Related:** #2663

## Current State
A social-media Reel (hook-only caption; transcribed) states a concrete claim: an unconfigured Cloudflare setup still passes credential-stuffing traffic, scrapers, and vulnerability scanners straight through to the origin even though Cloudflare sits in front of it — because rate limiting on auth endpoints, bot management on high-value pages, and custom WAF rules for known attack patterns are opt-in, not default. Cloudflare being "in front of" an app is not itself a security control — the actual hardening comes from the specific rules configured within it. This is directly relevant to this environment: Cloudflare Tunnel already runs for the homelab (per `claude-user-config:cloudflare`), and the same opt-in-not-default gap applies to any app-level Cloudflare zone in front of an AI-built app. This extends the pre-launch security checklist (`#2624`), which is currently unbuilt (open, no shipped skill implementation).

## Deliverables
1. A Cloudflare-hardening checklist row verifying rate limiting is configured specifically on auth-path routes (login, signup, password-reset) — not merely a blanket zone-level rate limit that doesn't distinguish auth endpoints from the rest of the app.
2. A checklist row verifying bot management (or, at minimum, Bot Fight Mode) is enabled on high-value pages — checkout, account creation, any endpoint attractive to credential-stuffing or scraping traffic.
3. A checklist row verifying custom WAF rules exist for known attack signatures relevant to the app's stack, rather than relying solely on Cloudflare's default managed rules.
4. A verification mechanism for each row: where the Cloudflare API can confirm a rule's existence and scope (e.g., listing rate-limiting rules and checking their match expression targets auth paths specifically), prefer an API-based check; where that isn't practical, a manual-review prompt naming exactly what to look for in the Cloudflare dashboard.

## Acceptance Criteria
- The rate-limiting check, run against a sample Cloudflare zone configuration with a rate-limiting rule scoped only at the zone level (no path-specific match), flags that auth endpoints aren't specifically covered.
- The rate-limiting check, run against a sample configuration with a rate-limiting rule whose match expression targets `/login`, `/signup`, and `/password-reset` (or equivalent), passes without a false-positive flag.
- The bot-management check flags a zone with Bot Fight Mode (or full bot management) disabled, and passes a zone with it enabled.
- The WAF check flags a zone relying only on Cloudflare's default managed ruleset with no custom rules, and passes a zone with at least one custom rule targeting a named attack pattern.
- Documentation cross-references `#2624` by number, noting the build-order dependency (whichever of the two records ships first stands alone; the other folds it in) the same way `#2657`/`#2663` already establish for their own additions to the same still-unbuilt checklist.

## Technical Approach
Since `#2624` has no shipped skill implementation yet, land this as a standalone Cloudflare-hardening checklist section (same pattern as `#2657`'s JWT checks and `#2663`'s legal/compliance items against the same unbuilt `#2624`), written to merge cleanly into `#2624`'s eventual body/skill once that record ships. Where a check can be automated, use the Cloudflare API (rate limiting rules, bot management settings, and WAF custom rules are all queryable via Cloudflare's REST API) to inspect a zone's actual configuration rather than trusting a self-report that "Cloudflare is enabled." Where API access isn't available or configured for this check to run against, fall back to a manual-review prompt naming the specific dashboard setting to inspect (mirroring `#2663`'s automatable-vs-manual-reminder split for its own checklist rows).

### Key Files
- A new checklist file (path determined by whichever skill or doc structure `#2624`'s implementation adopts, e.g. under `plugin/skills/` if a security-checklist skill is created, or `docs/reference/` if it remains a static checklist) — holds the three Cloudflare-hardening rows and their audit prompts/API-check logic.
- `#2624`'s own body/eventual implementation file — cross-reference added once both records have landed.

## Gotchas
- `#2624` is unbuilt as of this shaping — there is no live checklist artifact to append rows to today; this record may ship first as a standalone section, and whichever record ships second must fold the other in with a cross-reference, avoiding silently-diverging checklists (same build-order caveat as `#2657`/`#2663`).
- An API-based check requires a Cloudflare API token with read access to the relevant zone's rate-limiting, bot-management, and WAF settings — the check's documentation should state this prerequisite explicitly rather than silently failing or reporting a false pass when no token is configured.
- "Rate limiting configured on auth endpoints" is a judgment call about what counts as an auth-path match expression (exact-path match vs. a broader pattern that happens to include auth paths) — the check should flag an ambiguous or overly broad match expression for human review rather than confidently passing or failing it.
- Distinguish this checklist item from a general "is Cloudflare enabled" check — the entire point of this record (per the source claim) is that zone-level presence doesn't imply endpoint-specific hardening; the checklist rows and their pass/fail logic must reflect that distinction, not collapse back into a blanket check.
