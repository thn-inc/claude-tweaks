# 2634: simplify dispatch: caller can observe a still-in-flight async Task write as "done"

Surface: infra
Origin: reflect light from #2621
Defer-reason: tangential

**Related:** #2533, #2714

## Current State

`/claude-tweaks:simplify`'s Step 2 dispatches the `code-simplifier:code-simplifier` subagent via the `Agent` tool, which runs asynchronously: the dispatch returns immediately, and the agent's final state is only known once its completion notification (its reply ending in the `STATUS:` line Step 2's own output template requires) arrives. The paragraph at `plugin/skills/simplify/SKILL.md:87` ("When dispatched with file-path scope …") tells the caller to "diff them against its own change scope and revert anything outside it" but never says *when* — nothing ties the check to that completion signal.

During record #2621's review Step 5, the caller ran `git status` shortly after dispatch, saw one out-of-scope file modified, reverted it (`git checkout --`), and moved on. The agent was still running: it went on to write a second, larger wave of out-of-scope edits (a `cmdNextTarget` refactor in `harness-health.js`) that a later, unrelated check caught and a second `git checkout --` pass had to clean up. A diff-and-revert check run before the agent has returned has no guarantee it is looking at final state.

## Deliverables

1. Amend the file-path-scope paragraph in `plugin/skills/simplify/SKILL.md` Step 2 so the diff-and-revert check has an explicit precondition: it runs only after the subagent's reply — carrying Step 2's required `STATUS:` line — has been received, never against an ad hoc `git status` poll taken while the dispatch may still be running.
2. State the consequence of a premature check in the same paragraph, briefly: edits the agent writes after an early revert survive into the caller's commit.

## Acceptance Criteria

1. `plugin/skills/simplify/SKILL.md` Step 2's file-path-scope paragraph names receipt of the subagent's final reply (its `STATUS:` line) as the precondition for the diff-and-revert check.
2. The same paragraph says a working-tree check taken before that reply is not the agent's final state and must not drive a revert.
3. No other step of `/claude-tweaks:simplify` changes, and `npm test` passes (prose conformance suites pin skill text repo-wide).

## Release Note

Clarified that /simplify's out-of-scope revert check waits for the simplifier agent to finish, so late edits can no longer slip past it.

## Technical Approach

A prose-only change to one paragraph. The record's original second option — a new "wait for this dispatch" primitive — is not taken: the completion notification already exists and is the plugin's established "agent is done" signal (`plugin/skills/dispatch/task-prompt.md` forbids ending a turn to wait on one, which is compatible — the caller simply does the check in the turn that receives the reply). Naming the existing signal as the precondition closes the race without new machinery.

- `plugin/skills/simplify/SKILL.md` — Step 2's file-path-scope paragraph gains the completion-precondition sentence

## Current State

`/claude-tweaks:simplify`'s Step 2 dispatches the `code-simplifier:code-simplifier` subagent via the `Agent` tool, which is asynchronous — the dispatch call returns immediately with an `agentId`, and the caller is told "you know nothing about its results until [a] notification arrives." Step 2's own guidance ("Before committing the returned changes, the caller should diff them against its own change scope and revert anything outside it") assumes the caller can check `git status`/`git diff` once, right after dispatch, and see the agent's *final* state. During this review's Step 5 (record #2621), the caller (this flow run) checked `git status` shortly after dispatch, saw one out-of-scope file modified, reverted it (`git checkout --`), and moved on — only to find on a later, unrelated check that the agent had *continued writing* after that revert, producing a second, larger wave of out-of-scope edits (a `cmdNextTarget` refactor in `harness-health.js`) that required a second `git checkout --` pass to reach a clean tree. Because the Agent tool's async notification is the only reliable "the agent is truly done" signal, and the coordinating call cannot poll/sleep-loop for it, a caller that does the diff-and-revert check on its own initiative (rather than waiting for the completion notification) has no guarantee it is looking at final state.

## Deliverables

Clarify `skills/simplify/SKILL.md` Step 2's diff-and-revert guidance to state explicitly that the revert check must run only after the dispatch's completion notification has been received (not on an ad hoc `git status` poll), or provide an explicit "wait for this dispatch" primitive callers can use without violating the "never end this turn waiting" constraint documented elsewhere in this same plugin's dispatch guidance.

## Acceptance Criteria

`skills/simplify/SKILL.md`'s Step 2 names the completion-notification requirement (or an equivalent wait primitive) as a precondition for the diff-and-revert check, so a caller following the instructions as written cannot repeat this race.
