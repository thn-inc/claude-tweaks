# 1493: Tidy residue: needs:decision markers, committed run-dir staged/, and --approve

Surface: backend

## Overview

Gives tidy's record-scoped findings a durable, tracker-visible residue channel (the
`needs:decision` marker, alongside the existing staged-file mechanism), makes tidy's repo-scoped
residue survive a headless `pr-first` firing by committing the run directory itself instead of
leaving it only in a sandbox that gets discarded, and adds `tidy --approve` as the re-entry point
for either kind. Today a headless tidy's staged proposals are invisible until a human happens to
run tidy interactively again in the same environment — this closes that gap without inventing a
new residue container.

## Non-Goals

- Does not change tidy's Action Vocabulary, its aggressiveness-tier routing table's actual
  disposition logic (Delete/Defer/Absorb/Open parent gate stay exactly as risky/reversible as
  today), or which findings Auto-apply vs. Stage at which tier.
- Does not build a standing residue-container issue or a dismissal-memory file — the parent design
  doc explicitly rejects both; the committed run directory is the whole mechanism for repo-scoped
  residue.
- Does not change the digest sweep (`digest-sweep.md`) or the materiality floor — those are a
  separate, already-existing residue path for below-floor findings, untouched here.

## Technical Approach

The marker write is additive to the existing Stage mechanism — do not replace
`{run-dir}/staged/` with the marker; the run directory stays the authoritative, structured
representation of *what was proposed*, and the marker is purely a tracker-visible pointer to it
plus the resolution channel Phase 2's `attention`/`refine #N` already know how to render. The
`--approve` command is a re-entry into Step 6's own existing Approve logic against a named run
directory, not a new approval mechanism.

## Gotchas

- **Do not conflate "staged" with "marked."** A finding can be staged (in `{run-dir}/staged/`)
  without a human ever seeing it if nobody runs `attention` or a later tidy firing; the marker is
  what makes it visible on the tracker independent of anyone remembering the run directory
  existed. Both must be written together for a Stage-tier finding — writing only one defeats half
  of this record's purpose.
- **The loop-safety comparison must be content-aware, not marker-presence-only.** A record with an
  unresolved tidy comment about *one* stale-close reason should still collect a *different* new
  finding (say, an Absorb proposal that arose later) — compare the `Proposed:` text, not just
  "does this record have any tidy marker at all," or a second, genuinely new finding gets
  silently swallowed.
- **`pr-first`'s commit-scope change touches the same Step 7.5 section Phase 3 does not touch, but
  double-check for drift** — this record and Phase 3 both edit tidy-adjacent and backlog-adjacent
  files respectively; they don't share a file, but confirm no other in-flight record is mid-edit
  on `tidy/SKILL.md`'s Step 7.5 section before starting.
- **`tidy/step-6-auto.md` is 33,845 bytes and `tidy/SKILL.md` is 38,164 bytes** — both have real
  but not generous headroom under the 40,960-byte ceiling; check actual byte counts before writing
  into either, and prefer a new sub-file (e.g. `tidy/approve-mode.md`) for the `--approve`
  procedure's full write-up rather than inlining it into `SKILL.md` if the addition would push it
  close to the limit.
- **A marker write is two API calls (label + comment), not one — a crash or rate-limit between
  them leaves a half-written marker** (label with no comment, or an orphaned comment with the label
  already cleared by something else). Write the comment first, then the label, so a failure after
  only the first call leaves no misleading `needs:decision` label with nothing explaining it; a
  later tidy or `attention` pass that finds the label without a matching comment should treat it as
  inconsistent state and re-derive/repair rather than silently trusting the label alone.
- **Confirm `.claude-tweaks/pipelines/` isn't excluded by `.gitignore` before relying on `git add`
  to pick up the run directory.** If it's currently gitignored (even by a broad `tmp/`- or
  `pipelines/`-style pattern), Step 7.5's `git add` silently no-ops on those paths and this
  record's core guarantee — the audit trail surviving past sandbox discard — silently fails with no
  error. Check the repo's actual `.gitignore` and either confirm the path is already trackable or
  add the necessary un-ignore rule as part of this record's own changes.
