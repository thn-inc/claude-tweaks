# 1608: Ship a repair-claim.js CLI mirroring release-claim.js for issue-claims.md's unreadable-blob repair

Surface: backend

## Current State

`_shared/issue-claims.md`'s "Repairing an unreadable claim blob" subsection (`plugin/skills/_shared/issue-claims.md:198`, added by #1246) documents a manual repair/force-release procedure for a claim blob stuck in the `'unreadable'` state: read the blob at `claims/issue-<number>.json` on `CLAIMS_BRANCH` and capture its blob sha from the read response (ordinary response metadata, available even when the content doesn't parse), confirm via the classify call that the outcome really is `'unreadable'`, conditionally overwrite with `sha` set — either `releasePayload`-shaped tombstone content (force-release) or `claimPayload`-shaped content (repair-and-claim) — and log the override durably, the one write in that file that must never go unlogged.

This mirrors `bin/release-claim.js`'s mechanics almost exactly (read → classify → conditional PUT carrying the read sha → log; its exit `5` is precisely its refusal to touch an `'unreadable'` blob), but unlike `release-claim.js` and `claim-targets.js` there is no CLI wrapper: a human or `/tidy` run must hand-assemble the `gh api`/MCP calls from the prose each time, with the sha capture and content shape both easy to mistype.

Verified at shaping time (2026-08-29): the subsection exists at the cited location, and both sibling CLIs exist under `plugin/bin/`.

## Deliverables

- [ ] A `plugin/bin/repair-claim.js <issue> --run <run-dir> --mode <release|reclaim> --reason <reason>` CLI — or, if implementation shows the shared logic dominates, an equivalent repair mode on `release-claim.js`; decide at build time and record the choice in the PR — performing the documented sequence: read the blob and capture its sha, confirm the content classifies `'unreadable'` on that same fresh read, conditional-overwrite with the captured sha using `releasePayload`-shaped (`release` mode) or `claimPayload`-shaped (`reclaim` mode) content, and log the override.
- [ ] The CLI follows the repo's CLI wrapper contract (injectable `run(argv, deps)` seam, explicit exit-code vocabulary, run-dir anchoring guard) and reuses the existing classify/CAS helpers (`bin/lib/issues/claims.js`, `bin/lib/issues/claims-git-cas.js`, `bin/lib/release-claim/`) rather than duplicating their mechanics.
- [ ] `_shared/issue-claims.md`'s "Repairing an unreadable claim blob" subsection updated to reference the CLI as the primary path, keeping the manual gh/MCP steps as the transport-detail fallback — the same posture the file's Release bullet already takes toward `release-claim.js`.
- [ ] A `tests/bin-lib/` suite covering: refusal when the blob does not classify `'unreadable'`, the sha-carrying conditional overwrite in both modes, the rejected-write (sha changed) path, and the override log line.

## Acceptance Criteria

- [ ] Given a claim blob classified `'unreadable'`, running the CLI in `release` mode writes a `releasePayload`-shaped tombstone using the blob's own current sha; in `reclaim` mode it writes `claimPayload`-shaped content the same way.
- [ ] The CLI refuses (non-zero exit, nothing written) when the blob does not classify `'unreadable'` on a fresh read — a live, tombstone, or stale claim is never overwritten by this tool; those states are `release-claim.js`'s and the acquire path's territory.
- [ ] A conditional-overwrite rejection (sha changed between read and write) exits non-zero with nothing retried blind, mirroring the subsection's own "re-read and reassess" instruction.
- [ ] The CLI logs the override (who/when/why) per the subsection's step 4 requirement — an AUTO line in `<run-dir>/decisions.md` when the run dir resolves anchored under the main checkout, with the exit code reflecting the repair outcome, never whether the log write succeeded (logging is bookkeeping, not a gate, matching `release-claim.js`'s documented posture); every repair/force-release call is logged, none silently succeeds.
- [ ] `npm test` passes with the new suite included.

## Technical Approach

Mirror `release-claim.js`'s structure: a thin argv parser in `plugin/bin/repair-claim.js` plus a `bin/lib/repair-claim/` module (flat sibling directory, per the repo's `bin/lib/{name}/` convention), built on the same injectable-runner seam and calling the existing classify/conditional-PUT helpers in `claims.js`/`claims-git-cas.js` rather than reimplementing them. Exit-code vocabulary modeled on `release-claim.js`'s: `0` repaired; distinct non-zero codes for the not-`'unreadable'` refusal, the CAS rejection, and malformed invocation / `gh` absent (`2`, matching the sibling). Decision-log append via `bin/lib/log-decision/append`'s `resolveTarget` guard, exactly as `release-claim.js` does, refusing a worktree-local shadow run dir. The gh-absent MCP path stays the manual read-classify-write procedure in `_shared/issue-claims.md` — deliberately not grown into this CLI, matching `release-claim.js`'s own documented posture.

### Key Files

- `plugin/bin/repair-claim.js` — new CLI entry point (or a repair mode on `plugin/bin/release-claim.js` if build-time inspection favors that; record the choice)
- `plugin/bin/lib/repair-claim/` — new module holding the repair sequence (or an extension of `plugin/bin/lib/release-claim/`)
- `plugin/bin/lib/issues/claims.js`, `plugin/bin/lib/issues/claims-git-cas.js` — reused classify/CAS helpers; no expected change
- `plugin/skills/_shared/issue-claims.md` — "Repairing an unreadable claim blob" subsection repointed at the CLI as primary path
- `tests/bin-lib/repair-claim/` — new suite

## Gotchas

- The refusal check must run against a fresh read, not a cached classification — the blob can change between an operator noticing it and the CLI running; the second acceptance criterion pins this.
- The overwrite destroys content that, despite failing to parse, may encode a real holder's identity. The logging requirement is the safety net; keep it bookkeeping-not-a-gate for the exit code, but never skip it silently.
- `release-claim.js`'s exit `5` (`'unreadable'` → refuse) is the exact inverse of this CLI's gate (`'unreadable'` → proceed, anything else → refuse). If the mode-on-`release-claim.js` variant is chosen at build time, keep the two gates from sharing a code path in a way that could invert either.
- The false-`'unreadable'` case (a wrapper-object extraction mistake at the read — the subsection's step 2 note) is not repairable state: fix the read instead. The CLI must not offer a bypass for it.
