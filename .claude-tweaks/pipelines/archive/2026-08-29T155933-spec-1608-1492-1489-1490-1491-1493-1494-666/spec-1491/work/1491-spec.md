# 1491: Specify: bare invocation drains the queue with --budget (next deprecated)

Surface: backend

## Overview

Changes `/claude-tweaks:specify`'s bare invocation (no record ref, no design-doc path, no topic)
from an input-shape error into **drain mode**: repeat `next-mode.md`'s claim → framing-guard →
shape-or-route → release loop over the ranked eligible backlog until `--budget <n|all>` attempts
are spent or the eligible set is empty. `next` becomes a deprecated alias for `--budget 1`. This
turns a once-per-record headless unit into a once-per-session one, matching how cheap and frequent
this hygiene pass is meant to be run (the design doc's core friction complaint: a human running
`specify next` N times to clear N eligible records).

## Non-Goals

- Does not change `specify`'s explicit input forms (`#N`, `#N,#M,...`, `#A-#B`, a design-doc path,
  a topic) — those are unaffected; only the *bare, no-argument* invocation changes meaning.
- Does not change the Framing Guard's routing logic, the parent-record guard, or the
  `needs:definition` redirect — drain mode calls the identical per-record procedure `next-mode.md`
  already implements, just in a loop.
- Does not build `/claude-tweaks:sweep` (Phase 7) — this record only makes `specify` itself
  drainable; the orchestrator that calls it is a separate, later record.

## Current State

- `specify/SKILL.md`'s Input section documents `next` as "the headless-safe form... Selects,
  claims, and shapes exactly one eligible unshaped backlog record per firing; zero eligible
  records is a cheap no-op." A bare invocation with no argument at all is not currently a
  recognized input shape — `SKILL.md`'s Resolve-the-input cases 1-5 all expect *something* in
  `$ARGUMENTS`.
- `specify/next-mode.md`'s Selection step (`next-mode.md:143`) picks exactly one record: "Exactly
  one record, by dispatch's own ranking." The Claim/Framing-Guard/Shape/Release steps that follow
  all operate on that single picked record.
- `specify/next-mode.md`'s Zero-eligible case (`next-mode.md:163`) reports "nothing eligible this
  firing" and exits cleanly with no self-report — this is drain mode's natural loop-exit
  condition, already written.
- `_shared/policy-schema.md` and `bin/lib/policy-schema.js`'s `POLICY_KEYS` have no `specify-budget`
  entry.
- `specify/routine-template.yml`'s `kickoff` is `specify next`.

## Deliverables

- [ ] `specify/SKILL.md` Input section: bare `$ARGUMENTS` (empty string — distinct from any
      recognized shape in Resolve-the-input cases 1-5) resolves to **drain mode**, unconditionally
      — an interactive (human-present) bare invocation drains immediately with no confirmation
      prompt, identically to a headless firing; there is no separate "ask before draining" path.
      `--priority <band>` composes with bare exactly as it composed with `next` today (restricts
      the candidate pool before ranking). `--budget` combined with any explicit-input form (`#N`,
      `#N,#M,...`, `#A-#B`, a design-doc path, or a topic) is rejected with a one-line notice —
      `--budget` applies to bare invocation only. `--budget 0` or a negative value is a hard input
      error (`"'--budget {value}' is not valid — must be a positive integer or 'all'"`), rejected
      before any fetch. Reject `phase-N`, `--surface`, `--granularity`, and `--chained` combined
      with bare drain, with the same one-line-notice posture `next` already documents for those
      flags.
- [ ] `_shared/policy-schema.md` / `bin/lib/policy-schema.js`'s `POLICY_KEYS`: add
      `specify-budget`, type integer, default `5`, category `pipeline-behavior` — the default
      attempt count for a bare drain invocation with no `--budget` flag.
- [ ] `_shared/work-record-config.md` or the `#762`-landed shared grammar file (see Prerequisites):
      define `--budget <n|all>` — `n` caps the number of claim-attempt cycles this firing performs
      (an attempt is a claimed record that is then shaped, routed, or fails — not a shaping
      success specifically); `all` loops until the eligible set (re-queried fresh each iteration,
      since a shaped or routed record leaves it) is empty, with no upper cap.
- [ ] `specify/next-mode.md`: change Selection from "pick the single top-ranked record" to "the
      ranked list" — the Claim/Framing-Guard/Shape/Release sequence runs once per record, in
      ranked order, until `--budget` attempts are spent or the ranked list is empty. **Each
      iteration re-fetches the eligible set fresh and re-sorts it by the existing ranking rule
      (priority-band-then-age)** — a full re-derivation, not a filter over a frozen initial list —
      so a record that becomes ineligible mid-run (shaped, routed, or claimed by a concurrent
      session) is naturally absent from the next iteration's fetch, and a record that newly
      becomes eligible mid-run is naturally picked up. A record the Framing Guard routes to
      `needs:definition` mid-run is excluded from this run's remaining iterations by the same
      worklist rule that excludes it from any future run's eligibility query (Phase 1) — no
      special-case skip logic needed beyond the fresh re-fetch. **A lost claim race** (another
      session claims the top-ranked record between this iteration's fetch and its own claim
      attempt) **does not consume a `--budget` unit** — the loop retries immediately against the
      next-ranked candidate from a fresh fetch, exactly as if the lost record had never appeared;
      only a record this firing successfully claimed counts as an attempt.
- [ ] `next-mode.md`'s close-out: report `{shaped: N, routed: M, failed: K}` — three counts, plus,
      in the same rendered summary, each count's own list of record refs. **`failed` is populated
      by exactly one outcome**: this firing claimed a record but the Shape or Release step raised
      an error before completing (a genuine procedural failure — a write-path exception, a
      malformed body the shape step can't process) — never a lost claim race (which the previous
      bullet excludes from budget entirely) and never a Framing-Guard route (which is `routed`,
      not `failed`). Keep the existing "render Next Actions only when a human is present" rule — a
      headless drain firing (Routine, or `/sweep`) renders nothing, exactly as `next` does today.
- [ ] `next` becomes a **deprecated alias** for `--budget 1` — identical observable behavior
      (claims and shapes/routes exactly one record, same zero-eligible no-op), one warn-tier
      deprecation notice per invocation. Document it in a new `specify/deprecated-aliases.md`
      (mirroring `dispatch/deprecated-aliases.md`'s shape) with a removal condition: once
      `.claude-tweaks/policy.yml`, `reference-card.md`'s argument grammar, and
      `specify/routine-template.yml` cite only bare-with-`--budget`, checked at the next minor
      release.
- [ ] `specify/routine-template.yml`: change `kickoff` from `specify next` to bare `specify`, with
      no explicit `--budget` — the Routine adopts the new multi-record default (`specify-budget`'s
      policy value, `5` unless a project overrides it) rather than pinning `--budget 1` to
      preserve today's one-record-per-firing cadence. Each weekday firing now shapes/routes up to
      five records instead of one; state this cadence change plainly in the template's own
      `notes:` field so it isn't mistaken for an oversight later.
- [ ] `shaped:headless` stamping is unchanged — every record drain mode shapes still gets it,
      exactly as `next` mode's single-record path does today.

## Acceptance Criteria

1. Given three eligible unshaped records and `--budget 2`, a bare `specify --budget 2` firing
   shapes or routes exactly two of them (whichever the ranking picks first), releases both claims,
   and its close-out names the third record as remaining/not attempted this run.
2. `specify next` (typed directly) behaves identically to `specify --budget 1` — one deprecation
   notice, exactly one record claimed and shaped/routed, same zero-eligible no-op when nothing
   qualifies.
3. `--budget all` against a five-record eligible set drains all five in one firing (assuming none
   route to `needs:definition` and get excluded mid-run), reporting `{shaped: 5, routed: 0, failed:
   0}` (or the actual split, if any route).
4. `tests/specify-next-mode.test.js` is re-pointed to assert the loop behavior (not a single pick)
   and stays green; a new or extended test asserts the `{shaped/routed/failed}` close-out shape.
5. A headless drain firing (simulated as a Routine invocation, no human present) renders no
   `## Next Actions` block, matching `next`'s existing posture exactly.

## Technical Approach

The loop body is `next-mode.md`'s existing Claim → Framing Guard → Shape → Release sequence,
completely unchanged in its per-record logic — only the *driver* around it changes, from "call it
once" to "call it up to `--budget` times, re-querying eligibility before each call so a record
this run already shaped or routed doesn't reappear." Do not duplicate the Claim/Guard/Shape/
Release procedure inline in a new loop wrapper; restructure `next-mode.md` so that procedure is
the loop body directly.

## Gotchas

- **"Attempt" and "success" are not the same count.** A record that routes to `needs:definition`
  (the Framing Guard) still consumes one `--budget` unit even though it isn't "shaped" — the
  design doc is explicit that budget counts attempts, since a routed record still paid for a
  framing-guard LLM call. Don't let the close-out's `shaped` count silently double as the loop's
  own termination counter.
- **Re-query eligibility before every iteration, not once at the start.** A stale in-memory list
  from the start of the run would let drain mode attempt a record another concurrent session (or
  this run's own prior iteration) already claimed or routed — the existing per-record Claim step
  already handles a lost-race claim conflict; re-querying before each pick is what keeps that the
  only race drain mode has to handle, rather than inventing a second one from a stale list.
- **`next-mode.md` is 27,534 bytes** — comfortable headroom under the 40,960-byte ceiling for this
  record's loop restructuring.
- **This record and #762 may race on the same new file.** If #762 lands first, add `--budget`
  there as one more flag in its established grammar; if this record lands first, keep the new
  `_shared/record-batch-input.md` (or wherever `--budget` lands) minimal — just the flag this
  record needs — so #762's later extension is additive, not a rewrite.
