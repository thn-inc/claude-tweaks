# Backlog proposal — `0.x` pre-major bump rule in the pack and the local engine (#2256, ledger row 102)

**Category:** backlog-proposal
**Severity:** medium
**Reversibility:** high
**Source:** `/review` whole-branch review of #2256 (minor M7), confirmed by the release skill's own gate
**Defer-reason:** pre-existing-outside-diff
**Proposed title:** Honour release-please's `bump-minor-pre-major` — a breaking commit on a `0.x` line bumps the minor, not the major

## Current State

`plugin/bin/lib/release-local/bump.js` maps any breaking marker to `major`, and `plugin/bin/lib/release-preflight/pack.js`'s `proposedVersion` reuses that rule (via `bin/lib/release/compose.js`). release-please, by default (`bump-minor-pre-major: true` behaviour on `0.x`), does not bump `0.x` to `1.0.0` on a breaking change. On a `0.x` pr-first repository the console therefore renders a major and `/claude-tweaks:release`'s major-bump HARD-GATE holds a release that release-please would ship as `0.(x+1).0`; the console's gating version and the engine's shipped version then disagree on every breaking change.

## Deliverables

- [ ] `bump.js`: when the base is `0.x`, a breaking marker yields `minor` (and a `feat` yields `patch` when `bump-patch-for-minor-pre-major` is set) — read from `release-please-config.json` when present, default `true`
- [ ] `pack.js`'s `proposedVersion` carries `part` computed by the same rule, and its `value` names `preMajor: true` so the console can say why
- [ ] `release/console.md`'s major-bump gate reads `proposedVersion.value.part`, not a recomputation; tests in `tests/bin-lib/release-local/bump.test.js` and `tests/bin-lib/release-preflight/pack.test.js`

## Acceptance Criteria

1. Base `0.4.2` + a `feat!:` commit → `bump.js` proposes `0.5.0`; base `1.4.2` + the same → `2.0.0`.
2. The pack on a `0.x` fixture with a breaking commit reports `part: minor`, `preMajor: true`.
3. `/claude-tweaks:release --dry-run` on that fixture renders no major-bump HARD-GATE.
