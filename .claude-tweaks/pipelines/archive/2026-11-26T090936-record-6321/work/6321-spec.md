# 6321: Count only no-work fail/exit launches toward drive.js --budget's two-in-a-row worker-stop rule

Surface: backend
Risk-flags: auth
Risk-flags-unconfirmed: true

**Related:** #5265, #5321, #5653

## Current State

#6118 (PR #6316) gave `drive.js --budget` a `worker-stop` end. One of its rules is two-in-a-row: when two consecutive driven records' implementer launches both count as launch failures, the run ends. `countsTowardLaunchStreak` (`plugin/bin/lib/driver/worker.js`) decides what counts. It returns true for reason `launch-error` and for every `fail`/`exit` envelope (`worker.js:361-364` on origin/main `f3ec6efcc1`). `classify` (`worker.js`) gives reason `exit` to every result object with a non-zero exit code, `is_error: true` or a subtype other than `success`. That set includes workers that ran and failed their own record (`error_max_turns`, `error_during_execution`, an API error partway through). So two records in a row that each fail on their own work end the run `worker-stop`, and the run then deletes the first record's escalation comment. #6118's own Non-Goal says the opposite: "a worker that ran and failed its record … keeps today's settle". A record that always fails this way could therefore stay unescalated across firings. #6118 shipped the spec's literal counting set, and the PR #6316 Review Console ratified it (ruling `sdd-ruling-2`, ledger row 4). This record narrows that set.

The count crosses three files. `steps.js:875,888` calls `countsTowardLaunchStreak(envelope)` once per record and stores the result as `ctx.implementerLaunch.counts`. `run.js:525` copies it into the record's facts. `budget.js:350-356` reads only `facts.implementerLaunch.counts`, so `budget.js` never sees the envelope, and the narrowing belongs entirely in `worker.js`. The envelope already carries `turns` (`num_turns`) but not `duration_api_ms` (`ENVELOPE_FIELDS`, `worker.js:233`).

A live probe on 2026-11-26 (below, under Decisions) found that a worker which did no work reports `num_turns: 1`, not 0, and `duration_api_ms: 0`. A worker that ran reports `duration_api_ms` above 0.

## Release Note

A budget-driven driver run no longer stops early, or deletes an escalation comment, when two records in a row fail on their own work.

## Technical Approach

In `classify`'s `envelope` helper, read `obj.duration_api_ms` the way `turns` reads `num_turns`, but guarded (`typeof v === 'number' && Number.isFinite(v) && v >= 0 ? v : null`), and append `apiDurationMs` to the returned object and to `ENVELOPE_FIELDS`. Change `countsTowardLaunchStreak` to `env.reason === 'launch-error' || (env.status === 'fail' && env.reason === 'exit' && env.apiDurationMs === 0)`. `steps.js`, `run.js` and `budget.js` need no code change: the narrowed boolean flows through the existing `implementerLaunch.counts` fact. The free-text `result` is never read.

## Overview

#6118 (PR #6316) gave `drive.js --budget` a `worker-stop` end, with a two-in-a-row rule: two consecutive driven records whose implementer launches both ended non-`ok` end the run. Two kinds of envelope count toward that rule: reason `launch-error`, and status `fail` with reason `exit`. `worker.js` assigns `reason: exit` to any result object with `is_error` or a non-`success` subtype, and that includes `error_max_turns` and `error_during_execution`. The first record's escalation comment is then deleted, which contradicts #6118's own Non-Goal: "a worker that ran and failed its record … keeps today's settle". A record that always exhausts its turns can therefore stay unescalated across firings. #6118 shipped the spec's literal counting set, and the PR #6316 Review Console ratified it (ruling `sdd-ruling-2`, ledger row 4). This record narrows the set.

## Non-Goals

- Changing the shared-cause classification (`launch-error`, or the structured `terminal_reason: "api_error"` / `api_error_status` / `api_error_type` signal).
- Changing the repeat cap or the marker-free settle.
