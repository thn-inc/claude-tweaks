# 2043: bin/verify.js tests cmd example fails on Windows under cmd.exe (env-prefix syntax)

## Current State
`package.json`'s `test` script (`"test": "CT_HOOKS_GIT_TIMEOUT_MS=60000 node --test $(find tests tools/upstream-drift/tests -name '*.test.js' | sort)"`) uses two POSIX-only shell constructs: a `VAR=value command` env-prefix, and `$(...)` command substitution to enumerate test files. `npm test` on Windows runs this under `cmd.exe`, which supports neither, so it fails immediately with `'CT_HOOKS_GIT_TIMEOUT_MS' is not recognized as an internal or external command`. `plugin/skills/test/verification.md`'s Step 2 documents `bin/verify.js --cmd tests="npm test"` as this repo's canonical verification invocation; `verify.js` just shells out to whatever string a `--cmd` value carries (`spawnImpl(command, {shell: true})`, `plugin/bin/lib/verify/run.js:41`), so it inherits the failure unchanged rather than causing it. (The original request's claim that this exact failure was "already documented in this project's own memory notes" doesn't hold — no repo doc, `docs/incident-log.md`, or session memory records this specific pairing; related but distinct Windows-portability incidents exist, e.g. a path-backslash-in-string-literal bug `[IL-154]`.)

## Deliverables
- [ ] A small portable Node script (e.g. `tools/run-tests.js`) that: walks `tests/` and `tools/upstream-drift/tests/` for `*.test.js` files in JS (no shell glob), matching today's `find tests tools/upstream-drift/tests -name '*.test.js' | sort` output exactly; sets `process.env.CT_HOOKS_GIT_TIMEOUT_MS = process.env.CT_HOOKS_GIT_TIMEOUT_MS || '60000'` before spawning; spawns `node --test <files>` with `stdio: 'inherit'` and exits with the child's exit code.
- [ ] `package.json`'s `test` script updated to `"node tools/run-tests.js"` (or equivalent), removing the env-prefix and `$(...)` constructs entirely — fixing the shell portability at the source, so `verification.md`'s documented `--cmd tests="npm test"` invocation needs no Windows-specific alternative and stays unchanged.

## Acceptance Criteria
1. The new script's resolved file list is identical (same set, no additions or omissions) to `find tests tools/upstream-drift/tests -name '*.test.js' | sort`'s current output (549 files as of this writing) — verify by diffing the two lists.
2. `npm test`'s underlying invocation contains neither a POSIX env-prefix (`VAR=value cmd`) nor `$(...)` command substitution (verified by inspection; a live `cmd.exe` run isn't available on this build's host, so this AC is a code-shape check, not an on-host proof).
3. `CT_HOOKS_GIT_TIMEOUT_MS` still resolves to `60000` during `npm test` when the caller hasn't set it (unchanged from today — `plugin/bin/lib/hooks/git-exec.js`'s `resolveTimeout` reads it via `process.env`).
4. `npm test` still passes in full on this (POSIX) host after the change.

## Technical Approach
Fix the shell-portability problem once at its source (`package.json`'s script) rather than teaching every consumer — `verify.js`'s documented example, any human running `npm test` directly — a Windows-specific workaround. `CT_HOOKS_GIT_TIMEOUT_MS`'s default is a widen-for-tests override, not a correctness requirement: `resolveTimeout` (`git-exec.js`) already falls back to `DEFAULT_TIMEOUT_MS` when the env var is unset or non-numeric, so even a script bug that failed to set it would degrade to today's production timeout rather than break test execution outright — the script should still set it, though, to keep parity with today's wider test-only timeout.

### Key Files
