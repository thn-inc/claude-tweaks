# 3074: hooks/hooks.json: if-gated Bash entries fan out to all 28 pre-tool-use + 18 post-tool-use launches on commands with $VAR or loops

Surface: infra

**Related:** #2702, #2713, #2727, #2732, #2776, #2783, #2813, #2961

## Current State

`plugin/hooks/hooks.json` registers the identical command `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" pre-tool-use` 28 times in the `PreToolUse` `Bash` group, and `... post-tool-use` 18 times in the `PostToolUse` `Bash` group. Each copy sits behind its own `if` predicate (`Bash(git commit *)`, `Bash(sed *)`, `Bash(env -*)`, `Bash(git worktree *)`, ...). Verified on `origin/main` at `5f835e5e5`: 46 `"if"` entries total.

When Claude Code cannot statically evaluate the `if` predicates against a command (any `$VAR` expansion, or a `for`/`while` loop), it runs every if-gated handler. That is the right fail-safe for a gate, but it does not deduplicate identical command strings. So one such Bash call launches `bin/hooks.js pre-tool-use` 28 times and `post-tool-use` 18 times, and the command doesn't run until all 28 pre launches finish. The issue measured this on claude-tweaks 6.138.0 with Claude Code 2.1.295 on Windows 11 + Git Bash (the original request below has the probe table).

On Windows, each launch is `bash -> bash -> node (Volta shim) -> cmd -> node` plus 0-4 `git` processes. So one fanned-out call starts about 250-400 OS processes. About 17% of Bash calls in a day of transcripts had this shape (`for n in ...; do gh issue view $n; done`, `P=...; "$P/..."`). On a machine running ~25 parallel sessions with endpoint AV, this drove a sustained ~45 new processes/s and a run queue of 50-170 on 16 logical CPUs.

The per-pattern layout is a recorded decision. `plugin/skills/_shared/policy-schema-coverage.md` declines an unconditional `Bash` matcher on measured cost: **42.0 ms idle / 67.9 ms under contention** per `bin/hooks.js pre-tool-use` invocation. It cites that cost three times: for the `sed`/`perl` breadth trade-off, for leaving bare shell redirection (`>`, `>>`) ungated, and for leaving path-qualified git (`/usr/bin/git`) / `env FOO=1 git` ungated. `plugin/bin/lib/hooks/git-command.js` restates it in the comment above `WRITE_SHAPES`. Tests pin the per-pattern layout: `tests/hooks-gate-coverage.test.js` ("every WRITE_SHAPES entry has a matching hooks.json if-matcher (#70)", plus the `env git` and `Bash(env -*)` predicate pins) and `tests/hooks-dispatcher.test.js` ("PreToolUse Bash `if` patterns include Bash(git worktree *)").

`plugin/bin/hooks.js` eagerly `require`s about ten modules at load time (`./lib/hooks/context`, `sibling-sessions`, `../lib/flow/manifest`, `resume-freshness`, `staged-inventory`, `session-residue`, `worktree-detect`, `close-run-state`, `teardown-run`, `run-integrity`) before `main()` reads stdin. So no cheap early exit exists today.

## Deliverables

1. `plugin/hooks/hooks.json`: replace the 28 if-gated `PreToolUse` `Bash` entries with **one** entry (same command, no `if`), and the 18 if-gated `PostToolUse` `Bash` entries with **one** entry (same command, no `if`). No other matcher group changes.
2. A dependency-light Bash prefilter module, `plugin/bin/lib/hooks/bash-prefilter.js`. Given the parsed hook payload and the event, it returns whether the full handler must run. For `tool_name: "Bash"` it returns "run" when the command string contains, as a shell word anywhere in the string, any command word the old predicates keyed on. Pre-tool-use words: `git`, `env`, `mkdir`, and every `WRITE_SHAPES` entry (imported from `git-command.js`, never retyped). Post-tool-use words: `git` and `env`. Otherwise it returns "skip". The filter must be a **superset** of the old predicates' coverage, including compound commands (`cd x && git commit`), env-assignment prefixes (`FOO=1 git commit`), and the loop/`$VAR` shapes that triggered the fan-out. Anything it cannot read (unparseable stdin, missing `tool_input.command`, a non-Bash `tool_name`) returns "run" (fail-open to the full handler, never to a silent skip).
3. `plugin/bin/hooks.js`: for the `pre-tool-use` and `post-tool-use` events, read stdin once and consult the prefilter **before** any of the heavy modules are loaded. On "skip", exit 0 with no stdout. On "run", hand the already-read input to the existing path unchanged. This needs the top-level requires to become lazy (loaded on first use) and `main()` to accept pre-read input rather than calling `ctxLib.readStdin()` itself. The never-break-a-session invariant holds: every new path exits 0.
4. Measure and record the new costs in `plugin/skills/_shared/policy-schema-coverage.md`, using the same method as the existing figure (N=30 invocations, idle and under three concurrent test suites): (a) the prefilter skip path, (b) the full path. Rewrite the three "declined on cost" passages against the new layout. Every Bash call now spawns the hook once per event; the remaining marginal cost of covering bare redirection or path-qualified git is a prefilter widening plus parser work, not a matcher change. State that plainly rather than leaving the old 42/68 ms rationale standing. Update the `WRITE_SHAPES` header comment in `git-command.js` to match.
5. A `perf/` timing budget (`perf/hooks-prefilter.test.js`, run by `npm run test:perf`, like `perf/statusline-render.test.js`) that spawns `bin/hooks.js pre-tool-use` with a non-matching Bash payload and asserts the skip path stays under a budget set from deliverable 4's measurement.
6. Retarget the pinning tests. In `tests/hooks-gate-coverage.test.js`, the if-matcher-per-`WRITE_SHAPES` test and the `env git`/`Bash(env -*)` predicate tests become pins that the prefilter's word set covers every `WRITE_SHAPES` entry, `git`, `env`, and `mkdir`. In `tests/hooks-dispatcher.test.js`, the `Bash(git worktree *)` test becomes a pin that each `Bash` group has exactly one entry and no `if`. Add a new `tests/hooks-bash-prefilter.test.js` covering the deliverable 2 cases.

## Release Note

Bash commands that use shell variables or loops no longer launch the claude-tweaks hook dozens of times. Each Bash call now launches it at most once per hook event, which cuts process churn and command latency on busy machines.

## Technical Approach

Collapse the registration to one unconditional handler per event, and move the "is this command interesting?" decision into the dispatcher. The dispatcher's job is to make the uninteresting case cost one `node` startup and nothing else.

- **Prefilter:** a word-boundary scan of the raw command string (split on whitespace and shell operators `;`, `&&`, `||`, `|`, `(`, `)`, `` ` ``, `$(`, newlines). A token matches when it equals a covered word or ends in `/{word}` (path-qualified). The scan deliberately does not parse quoting or expansions. A false "run" costs only the full handler's module load, which is what today's undecidable case already pays, 28 times over. A false "skip" silently drops enforcement, so every ambiguity resolves to "run". The word set derives from `git-command.js`'s exported `WRITE_SHAPES` plus the literal `git`/`env`/`mkdir` additions, kept in one exported constant the tests pin. `git-command.js` requires only `path`, so importing it on the fast path is cheap. Confirm that while implementing; if it gains a heavier dependency, move `WRITE_SHAPES` to a leaf module instead.
- **Dispatcher ordering:** `hooks.js` gains an early branch at the top of `main()` for the two tool-use events. It reads stdin (a minimal synchronous `fs.readFileSync(0)` inside the prefilter module, so `context.js` isn't needed to read it), parses JSON in a try/catch, and asks the prefilter. The ten eager top-level requires move behind accessor functions or inline `require` at their use sites. `EVENT_MODULES` is already lazy. The payload-boundary test (#419) requires string-literal requires; keep every new require a string literal.
- **`main()` input:** `ctxLib.parseInput(ctxLib.readStdin())` becomes "use the pre-read input when provided". Stdin can only be read once, so the fast path must pass what it read through to the full path.
- **Measurement:** reuse the original measurement's shape (30 sequential spawns of `node bin/hooks.js pre-tool-use` with a fixed payload on stdin, idle and with three `npm test` suites running) for both a skip payload and a target payload, and record both.

## Gotchas

- **This reverses a recorded decision; it doesn't contradict it.** The 42/68 ms figure was the cost of running the *full* handler on every Bash call. It was correct when the alternative was 0 launches for most calls. It is wrong as a comparison against today's real average (about 0.17 x 46, so roughly 8 launches per call). The rewrite of `policy-schema-coverage.md` must show the new arithmetic, not just delete the old figure.
- **Simple commands pay something they don't pay today.** `echo hi` currently launches 0 hooks. After the change it launches 1 pre and 1 post, each a full `node` startup (the skip path). That is the deliberate trade. Deliverable 4's skip-path measurement is what keeps it honest, and deliverable 5's perf budget keeps it from regressing.
- **Post-tool-use side effects may currently fire 18 times on a fanned-out call** (for example commit breadcrumbs appended to `events.jsonl`). Collapsing to one handler changes that to once. That is a fix, not a regression, but a test asserting a breadcrumb count could notice. Check `tests/hooks-post-tool-use*.test.js` for count assertions before assuming none exist.
- **The prefilter must never be narrower than Claude Code's own `if` matching.** Claude Code strips `NAME=value` prefixes and splits compound commands before matching. A filter that only checks the first word would skip `cd x && git commit` and silently drop the commit gate. Hence the anywhere-in-the-string scan.
- **Payload-boundary test (#419):** making requires lazy must keep each one a string literal (`require('./lib/hooks/context')`), never a computed path, or the boundary test fails.
- **Upstream dedup is not a plugin deliverable.** Claude Code not deduplicating identical handler commands when `if` can't be decided is a Claude Code harness behavior, not a claude-tweaks defect. `/claude-tweaks:feedback` cannot file it. Report it to Anthropic separately if wanted. This record's fix doesn't depend on it.

### Build-time deviations (architecture alignment, /build Common Step 4.5)

- **Beneficial: early gate instead of lazy requires.** Technical Approach said to move `bin/hooks.js`'s ten eager top-level requires behind accessors. The build instead puts the prefilter gate (`require('./lib/hooks/bash-prefilter')` plus `earlyGate`) at the very top of the file, above those requires, inside a try/catch that falls through to the full path. It reaches the same goal (the skip path never loads the heavy modules, pinned by a `require.cache` probe test) with a 13-line diff instead of a refactor of every require site.
- **Beneficial: load-independent perf budget.** Deliverable 5 called for a fixed skip-path budget. An absolute 30–60 ms budget flaked under machine load, so `perf/hooks-prefilter.test.js` runs interleaved control/skip/full triplets instead. It asserts `skipCost < fullCost / 2` (the discriminator: disabling the early gate makes skip ≈ full) plus a 60 ms absolute ceiling.
- **Spec correction: Deliverable 8 scope.** Path-qualified git (`/usr/bin/git`) and `env` with its own assignments/flags are now covered end to end. The prefilter reaches them by basename and word, and `gitTargets` resolves them, so they are not follow-up gaps. The follow-up record covers bare `>`/`>>` redirection only.
- **Prefilter widened during the final review.** It now treats `=` as a separator and strips quotes anywhere in a piece. That reaches same-command literal assignments (`G=git; $G commit`), which the handler's `substituteVars` resolves; the first cut silently skipped them, a worktree-always deny bypass. Known limits that remain: concatenated expansion (`${G}t`) and command substitution producing the program name (`$(echo git)`).

## Original request

hooks/hooks.json: if-gated Bash entries fan out to all 28 pre-tool-use + 18 post-tool-use launches on commands with $VAR or loops

**Summary:** When Claude Code cannot statically resolve a Bash command against the `if` predicates (any `$VAR` expansion or a `for`/`while` loop), every if-gated handler in the `Bash` group runs, so a single tool call launches `bin/hooks.js pre-tool-use` 28 times and `bin/hooks.js post-tool-use` 18 times.

**Kind:** Defect

**Affected component:** `hooks/hooks.json` (PreToolUse / PostToolUse `Bash` groups) → `bin/hooks.js`

**Repro steps:**
1. claude-tweaks 6.138.0 (also seen on 6.137.0), Claude Code 2.1.295, Windows 11 + Git Bash.
2. While polling `Win32_Process` for new `bash.exe` processes whose command line contains `hooks.js` and whose parent is the session's `claude.exe`, issue these Bash tool calls one at a time:
   - `echo probe-simple`
   - `for i in 1; do echo probe-loop-$i; done`
   - `mkdir -p "$TEMP/probe-dir"`
   - `echo "probe-subst $(echo x)"`
   - `sed -n '20,40p' <some file> | cut -c1-900`
3. Count hook launches (pre / post) per tool call.

**Expected vs. actual:**
Expected: one launch per matching `if` pattern, i.e. at most one `pre-tool-use` (and one `post-tool-use` where a PostToolUse pattern matches) per Bash call.

| Command | Expected pre / post | Actual pre / post |
|---|---|---|
| `echo probe-simple` | 0 / 0 | 0 / 0 |
| `for i in 1; do …; done` | 0 / 0 | **28 / 18** |
| `mkdir -p "$TEMP/probe-dir"` | 1 / 0 | **28 / ~18** |
| `echo "… $(echo x)"` | 0 / 0 | 0 / 0 |
| `sed -n … \| cut …` | 1 / 0 | 1 / 0 |

The 28 `pre-tool-use` launches start within ~100 ms of each other, and the command does not run until all 28 have finished.

**Why:** `hooks/hooks.json` registers the identical command 28× (PreToolUse) and 18× (PostToolUse), each behind its own `if`. When the matcher cannot decide, Claude Code runs the handler (fail-safe, which is right for a gate) and does not deduplicate identical command strings across the entries. The per-pattern layout was chosen in `skills/_shared/policy-schema-coverage.md` to avoid paying ~42–68 ms per Bash call for an unconditional matcher, but whenever the matcher can't decide it costs 28 + 18 launches instead of 1 + 1.

**Measured impact (one Windows machine running ~25 parallel sessions):**
- Each hook launch is `bash → bash → node (Volta shim) → cmd → node` plus 0–4 `git` and their conhosts: about 5–9 OS processes. One fanned-out Bash call ≈ 250–400 processes.
- About 17% of Bash tool calls across one day of transcripts (rough regex for `$VAR` / loop shapes) have the fan-out shape. Common agent idioms (`for n in 1 2 3 4; do gh issue view $n …; done`, `P=…; "$P/…"`) trigger it constantly.
- Hook launches were the dominant source of a sustained ~45 new processes/s. With endpoint AV scanning every spawn, that drove the run queue to 50–170 on 16 logical CPUs. A trivial `python …; for …; do diff …; done` call took 16 s end to end, most of it waiting on hooks.

**Suggested fix:** one unconditional entry per event in each `Bash` group (same command, no `if`), with the cheap command-shape filter done at the top of `bin/hooks.js` before heavier modules load. Average cost becomes 1 pre + 1 post launch per Bash call, versus today's ≈ 0.17 × 46 ≈ 8. Separately, Claude Code not deduplicating identical handler commands when `if` can't decide may be worth raising with Claude Code itself.
