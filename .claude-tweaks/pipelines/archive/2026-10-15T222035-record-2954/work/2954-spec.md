# 2954: release-preflight: reports "nothing to release" when changes arrive through merge commits (first-parent walk)

Surface: infra

**Related:** #3088

## Current State

`/claude-tweaks:release`'s preflight pack (`plugin/bin/lib/release-preflight/pack.js`) builds its `unreleased` and `proposedVersion` probes (`:285-295`) from one memoized history (`:265`). That history is `conventionalHistory(deps.git, tipRef)` from `plugin/bin/lib/release-local/commits.js`. Its `readCommits` (`commits.js:76-85`) runs `git log --first-parent ... {lastTag}..{ref}`.

The first-parent walk was chosen for the local engine. `commits.js`'s header (`:2-4`) says `--no-ff` merges are "one composer-written subject each", because `bin/compose-subject.js` writes a conventional merge subject. A `pr-first` consumer repo whose PRs land as GitHub-default `--no-ff` merges ("Merge pull request #N from org/branch") breaks that assumption. The only first-parent commit since the tag is an unconventional merge subject, so `bumpPart` returns `none`. `proposedVersion` then throws `nothing to release: 1 commit(s) since v0.2.0, none feat/fix/breaking` (`pack.js:295`), and SKILL.md Step 2 stops the run.

Meanwhile release-please, which is the `pr-first` engine, considers every commit reachable from the tip but not from the tag. It opens "release 0.3.0" for the same range. The pack and the engine disagree.

Reported via `/claude-tweaks:feedback` against plugin 6.133.0, with repro: `release-type: python`, release-please on `develop`, tag `v0.2.0`, then one `--no-ff` PR merge whose branch carries a single `feat(scope): ...` commit.

## Deliverables

1. `readCommits`/`conventionalHistory` in `commits.js` gain an opt-in all-parents mode, for example a `{ firstParent: false }` option. It runs `git log {lastTag}..{ref}` without `--first-parent`, and the default stays first-parent. This is an additive flag rather than a default flip, because `release-local.js` (the only other caller, per `git grep`) depends on first-parent semantics.
2. In `pack.js`, when the resolved engine is `pr-first` (release-please), the `history` dependency uses the all-parents walk, so `unreleased` and `proposedVersion` match release-please's own commit range. Under `local-merge`, the pack keeps the first-parent walk, which matches `release-local.js`'s engine.
3. `lastTag` resolution is unchanged. The commit range still excludes everything reachable from the tag, by full reachability.

## Acceptance Criteria

- A test in `tests/bin-lib/release-preflight/pack.test.js` builds a fixture repo with tag `v0.2.0`, then a `--no-ff` merge whose subject is `Merge pull request #1 from org/feat` and whose second parent carries one `feat(x): y` commit. Under `integration-model: pr-first`, `proposedVersion` is `0.3.0` (allowing for the fixture's pre-major flags) and `unreleased.commits` includes the `feat` commit. Prove it goes red against the current first-parent walk.
- The same fixture under `integration-model: local-merge` keeps today's first-parent result, so the local engine's semantics are unchanged.
- `tests/bin-lib/release-local/commits.test.js` passes unchanged, and gains a case asserting the new option includes second-parent commits.
- `tests/bin-lib/release-preflight/acceptance.test.js` and `cli.test.js` pass unchanged.
- `npm test` passes in full.

## Release Note

The release preflight no longer reports "nothing to release" when feature commits arrive through GitHub merge commits under release-please.

## Technical Approach

Thread an options object through `conventionalHistory(git, ref, opts)` into `readCommits`, and drop `--first-parent` from the argv when `opts.firstParent === false`. In `pack.js`, build `history` lazily with `needEngine() === 'pr-first' ? { firstParent: false } : {}`. Engine resolution can fail, so make the history dependency report an `engine unresolved` failure, following the pack's existing dependency-naming convention (`:258-263`), rather than silently picking a walk.

### Key Files

- `plugin/bin/lib/release-local/commits.js` — `readCommits`/`conventionalHistory`: opt-in all-parents walk
- `plugin/bin/lib/release-preflight/pack.js` — `history` dependency: choose the walk by engine
- `tests/bin-lib/release-preflight/pack.test.js` — `--no-ff` GitHub-merge fixture under both engines
- `tests/bin-lib/release-local/commits.test.js` — all-parents option case

## Gotchas

- Do not flip `readCommits`' default. `plugin/bin/release-local.js` is its only other caller and relies on first-parent, so that one composer-written subject equals one changelog entry. `release-notes-publish.js:108` runs its own separate `git log --first-parent` and is out of scope.
- Under an all-parents walk, this repo's own `pr-first` merges, which carry a composer-written conventional subject plus the branch's `{Verb} {what}` commits, contribute both the conventional merge subject and unconventional branch commits. `bumpPart` must still compute the highest bump correctly with unconventional entries mixed in. Check that `unreleased.commits` consumers in `plugin/skills/release/` tolerate the longer list.
- A history-depends-on-engine coupling means a pack with an unresolved engine now degrades `unreleased`/`proposedVersion` too. Make sure that degradation reads as `engine unresolved`, never as a false `nothing to release`.
- The reporter's alternative (fall back to the open release PR's title version) was not chosen. It masks the divergence rather than fixing the pack's range, and it is unavailable before release-please has opened a PR.
