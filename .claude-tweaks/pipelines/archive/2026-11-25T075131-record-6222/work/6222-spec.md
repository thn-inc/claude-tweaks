# 6222: Close a Windows-regression record once main's full Windows run no longer fails its files

**Related:** #4725, #4764, #5303, #5322, #5451, #5694, #4790, #4286, #6203, #6021

## Current State

`tools/windows-regression/file-issue.js` (run by `.github/workflows/windows-regression.yml`'s `file` job on every push to `main`) only ever opens or comments on `Windows regression: … newly failing after {sha}` records. On a passing verify outcome `run()` returns `0` straight after `classify(report)` ("pass — nothing to file"), and on a failing one `fileOrComment` files or comments. Nothing ever closes a record whose files have since been fixed, so fixed records stay open, and the ones `/specify` shaped stay `ready` + `auto:build` in the dispatch and driver queues.

Measured 2026-11-24: of 17 open Windows-regression records, 5 named only files that main's latest full Windows run (45372736400 at 88cdbe82, `npm test -- --full`, 36,338 tests, `flakyPassed: []`, `timedOut: []`) no longer listed in `baselineAdjudicated.failingFiles`. Those were #4725 (fixed by #5694), #4764 (#4286), and #5303, #5322 and #5451 (#4790), each fixed 1-3 weeks before. The pipeline driver claimed #4725 and built PR #6203 for a failure #5694 had already fixed eight days earlier. Its change weakened the test, and only the whole-branch review stopped it. All five were closed by hand with that run as evidence.

The report already carries everything the close decision needs: `baselineAdjudicated.failingFiles` (every file failing at head, pre-existing ones included), `timedOut`, `flakyPassed`, and `checks.tests.command`/`exitCode`. Each record body lists its files under `### Newly failing test files` as `` - `path` `` bullets, which `composeIssue` writes.

## Deliverables

1. On `refs/heads/main`, on every run whose report is readable, pass or fail, `file-issue.js` lists open `type:bug` issues whose title starts with `TITLE_PREFIX` and that carry a `### Newly failing test files` list. It closes (`--reason completed`) each one where none of its listed files is in the head's failing set, with a comment naming the run URL, the head sha, and the files. It runs after filing or commenting, so a file that fails at this head is never closed by the same run that reports it.

2. The head's failing set is `baselineAdjudicated.failingFiles` when adjudication ran. It is empty only for a raw pass of the full suite (`checks.tests.exitCode === 0`). In every other case it is unknown: the run skips closing altogether and prints one stderr line.

3. No close happens when the run is not a full-suite run (`checks.tests.command` lacks `--full`), when any test file timed out (`baselineAdjudicated.timedOut` non-empty), or when a listed file is in `flakyPassed`. A record with no parseable file list (the `(not adjudicated)` and `no verify report` shapes, or an edited body) is never closed. A record carrying `bot:in-progress` gets a comment saying its files now pass, not a close, so its claimant settles it.

4. Any `gh` failure while listing, closing or commenting is one stderr line and never changes the CLI's exit code (still `0` on pass, `1` on fail).

## Acceptance Criteria

1. `tests/windows-regression-file-issue.test.js` covers, against an injected `gh` fake:
   - a pass run closes a record whose files are all absent from the failing set;
   - a fail run closes a stale record while filing the new one;
   - a record with one still-failing file stays open;
   - a timed-out, non-`--full`, or flaky-passed run closes nothing;
   - a `(not adjudicated)` record is never closed;
   - a `bot:in-progress` record is commented on, not closed;
   - a throwing `gh` leaves the exit code unchanged.

2. Reverting the close logic turns each close-asserting test red (revert proof).

3. The CLI's header comment and exit-code block describe the close behaviour.

4. `npm test` passes.

## Release Note

No user-facing change. Maintainer-side: the post-merge Windows check now closes its own regression records once their test files pass again on main, so already-fixed records stop reaching the build queue.
