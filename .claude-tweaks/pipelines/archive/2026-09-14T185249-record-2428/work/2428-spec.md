# 2428: dispatch: no policy lever to relax merge-check's needs-human verdict, and no batch-settle command for parked PRs

Surface: backend

## Overview

Add a `/claude-tweaks:dispatch --settle-parked` flag that reviews every open PR parked by `_shared/pr-first-merge.md`'s merge-verification Red path (`bot:parked`) in one batch pass, instead of a human looping ad hoc `gh pr merge` calls per PR. This does not change what merge-check classifies as `needs-human`, and does not touch `_shared/policy-schema.md` or the `autonomy` ceiling — it only collapses the per-PR "do you want to look?" click that `resume-confirmation.md` already asks, one at a time, into a single batch decision. A human drives this command by definition; it is never invoked by a scheduled Routine.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Reclassifying any `needs-human` verdict or adding a policy lever to relax merge-check's judgment — record #2428's other named direction (a policy lever), explicitly declined for this spec; a future record may revisit it
- Parallel resume of multiple parked PRs — each resume re-adopts a worktree and re-enters `/claude-tweaks:flow ... wrap-up` with its own Review Console; running two of those concurrently against one session isn't supported by this plugin's architecture
- Any change to `resume-confirmation.md`'s single-PR resume path — `--settle-parked` is a new entry point that reuses its freshness-probe and re-adopt mechanics, not a replacement for it

## Current State

- Parking: `plugin/skills/_shared/pr-first-merge.md`'s Red path (`## Red path — never merge; park`) bootstraps `bot:parked` on the record and posts a comment naming the failing check(s)/reason
- Resume: `plugin/skills/dispatch/resume-confirmation.md` — the existing per-PR `AskUserQuestion` confirm ("Confirm before resuming"), its freshness probe (`check-resume-freshness`), and the re-adopt-and-resume mechanics into `/claude-tweaks:flow ... wrap-up`
- Discovery today: `_shared/github-pr-scan.md`'s `repo-wide` scope surfaces parked PRs as part of `/claude-tweaks:tidy`'s and `/claude-tweaks:help`'s scans, but nothing batches them for action — a human currently finds each one separately and resumes it separately
- Dispatch's existing flag-parsing and input-routing logic: `plugin/skills/dispatch/SKILL.md`'s `## Input` section

## Deliverables

- [ ] Add `--settle-parked` to `/claude-tweaks:dispatch`'s Input grammar — mutually exclusive with a ref/budget drain, same standalone-form posture as `refine --reset-breaker` (human-present only, never Routine-fired; reject the flag with a one-line notice if combined with a ref or `--budget`)
- [ ] Fetch every open PR carrying `bot:parked` (`gh pr list --label bot:parked --state open --json number,title,...`), resolve each one's run-dir from its `claude-tweaks-run:` body marker, and for each run a fresh freshness probe (`resume-confirmation.md`'s existing `check-resume-freshness`) plus a current CI/mergeability read (`gh pr view {n} --json state,mergeStateStatus,statusCheckRollup`, the same shape `_shared/pr-first-merge.md`'s Step 2.5 state read already uses). A row whose probe returns `BLOCKED` (worktree live, or recently committed) is excluded from the batch table and reported in a separate "excluded — still live" line, never silently dropped
- [ ] Render one batch table — target, PR #, park reason (parsed from the original park comment posted by the Red path), fresh CI status, files-changed count — and one `AskUserQuestion`, **multi-select** (distinct from `resume-confirmation.md`'s single-select), letting the human pick which subset to resume; unpicked rows stay parked, untouched
- [ ] For each selected PR, sequentially (never parallel — see Non-Goals): skip `resume-confirmation.md`'s own per-PR `AskUserQuestion` (the batch step already made that decision) but run everything after it unchanged — a second, closer-to-the-write freshness re-probe (state can drift between batch-confirm and this PR's turn in the sequence), then `PIPELINE_RUN_DIR="{run-dir}" /claude-tweaks:flow "{target}" wrap-up`, letting that run's own Review Console render before moving to the next selected PR
- [ ] A PR whose second (pre-resume) freshness check now fails `BLOCKED` reports it, leaves it parked, and continues to the next selected PR — never aborts the rest of the batch

## Acceptance Criteria

1. `/claude-tweaks:dispatch --settle-parked` combined with a ref (`#N`) or `--budget` reports the mutual-exclusion error and performs no fetch
2. Given 3 open `bot:parked` PRs where 1 is currently `BLOCKED` (a live worktree), the batch table shows exactly the 2 eligible PRs plus one separate "excluded — still live" line naming the third
3. The batch `AskUserQuestion` accepts a multi-select subset (e.g. select 1 of 2 eligible rows) and resumes only the selected PR, leaving the unselected PR's `bot:parked` label and worktree untouched
4. A selected PR whose second freshness probe (immediately before resume) returns `BLOCKED` — simulated via a worktree commit landing between batch-confirm and its turn — is reported and skipped, and the batch continues to resume the next selected PR rather than stopping
5. Resuming a selected PR invokes `/claude-tweaks:flow "{target}" wrap-up` with `PIPELINE_RUN_DIR` set to that PR's own resolved run-dir, not a newly-minted one

## Technical Approach

Reuse `resume-confirmation.md`'s freshness-probe and re-adopt mechanics directly rather than reimplementing them — `--settle-parked` is a new *entry point* into that existing machinery (a batch fetch + one multi-select confirm + a sequential loop), not a parallel implementation of resume logic. `merge-check.md`'s `needs-human` classification logic is untouched by this work entirely.

### Key Files

- `plugin/skills/dispatch/SKILL.md` — add `--settle-parked` to the `## Input` grammar table and its own section describing the flag's fetch/batch-confirm/sequential-resume procedure
- `plugin/skills/dispatch/resume-confirmation.md` — no logic change; `--settle-parked`'s sequential loop calls into this file's freshness-probe and re-adopt steps, skipping only its own per-PR `AskUserQuestion`
- `plugin/skills/_shared/github-pr-scan.md` — the `bot:parked` fetch shape this deliverable's discovery step should reuse rather than reinvent, since `repo-wide` scope already queries this label

### Package Dependencies

None beyond what `gh` CLI calls this plugin already depends on.

## Gotchas

- `--settle-parked`'s batch `AskUserQuestion` must be multi-select — `resume-confirmation.md`'s existing per-PR question is single-select by design (one PR, one yes/no); reusing that question's shape here would only let the human resume one PR at a time, defeating the point of batching
- Never resume two selected PRs in parallel — each resume re-adopts a worktree and its own `/claude-tweaks:flow ... wrap-up` invocation renders its own Review Console; there is no supported way to run two Review Consoles concurrently against one session
- The freshness probe must run twice per selected PR: once to build the batch table (so the human sees current state before choosing), and once again immediately before each individual resume (state can drift in the gap between batch-confirm and a PR's turn in the sequence, especially for the last PR in a long batch)

## Original request

Filed via `/claude-tweaks:feedback` as record #2428:

**Summary:** Under `autonomy: unattended`, records that merge-check parks as `needs-human` (e.g. an agent-instruction-file diff, or a large diff) still require an explicit later human action, but the plugin provides no configurable lever to relax specific needs-human classes and no single command to settle a batch of already-parked, already-reviewed PRs at once.

**Kind:** Gap

**Affected component:** skills/_shared/assess-agent-autonomy (merge-check), skills/dispatch

**Use case:** A dispatch drain of 15 groups ended with 10 PRs parked `pending-review` under `autonomy: unattended` (reasons: missing `auto:merge` grant, an agent-instruction-file touch, a large diff, a tooling defect). The project owner's actual appetite, demonstrated by instructing "merge all the PRs" with zero per-PR changes requested, was far more permissive than the configured gate. There is no policy lever to let an owner declare which needs-human classes they consider auto-mergeable under unattended autonomy, and no dedicated command to review/merge a batch of already-parked PRs together rather than looping ad hoc `gh pr merge` calls.

**Resolved via brainstorming (2026-09-14):** classified Bounded; batch-settle command chosen over a policy lever (the record's own stated open design choice) — see this spec's Deliverables/Technical Approach above for the approved design.
