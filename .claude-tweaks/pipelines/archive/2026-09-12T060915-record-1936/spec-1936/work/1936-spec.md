# 1936: Resolve SubagentStop blocking-decision platform support and implement forced in-run retry (follow-up from #1596)

Surface: infra

## Current State

`plugin/bin/lib/hooks/subagent-stop.js` (E3, warn tier) reads the stopping subagent's transcript, exempts third-party `agent_type`s (#1596), and on a missing status line appends one `contract-violation` event to the owning run's `events.jsonl`; its header states "Never blocks" and that the event fires unreliably for Task dispatches (claude-code#27755). On a violation it returns a warn-tier `systemMessage` naming the missing status line; on every other path it returns `{}`. `plugin/hooks/hooks.json` registers it under `SubagentStop`. `_shared/subagent-output-contract.md` documents the hook as best-effort logging and tells the dispatcher to re-prompt by hand. #1596 (closed) shipped the exemption and a stronger dispatch template and deferred in-run enforcement because two lookups of the Claude Code hooks reference disagreed on whether `SubagentStop` accepts a blocking decision.

Lead, not yet the answer: the hooks reference (`https://code.claude.com/docs/en/hooks`, read 2026-09-09) lists `SubagentStop` in its exit-code-2 table as "Prevents the subagent from stopping" and describes a `hookSpecificOutput` block with a `blockSubagentStop`-style flag and reason field; `permissionDecision` is documented for the tool events only, so the field names #1596 tested were the wrong ones. The exact field names and whether the blocked subagent actually continues must be captured from a live run, not from a summary. #1868 (open, `needs:definition`) holds the wider "which enforcement point" question for status-word violations; this record is the mechanical probe that decides whether the hook-side option is available at all.

Tests: `tests/subagent-contract-clauses.test.js` pins the contract prose; `subagent-stop.js`'s exemption logic is tested with fake `ctx` objects in `tests/hooks-log-modules.test.js`.

# In-run enforcement follow-up from #1596

**Origin:** #1596 build (deferred, scope-down decision — see that record's Blocked / Future Work section and its materialized spec at `.claude-tweaks/pipelines/2026-09-05T174526-record-1596/work/1596-spec.md`)

## Current State

#1596 shipped an `agent_type` exemption fix to `plugin/bin/lib/hooks/subagent-stop.js` and a
strengthened dispatch template in `plugin/skills/_shared/subagent-output-contract.md`, but did not
implement forcing a violating subagent to retry in-run via the `SubagentStop` hook's own
decision-control output. Whether `SubagentStop`'s JSON output actually supports
`permissionDecision: "block"` / `permissionDecisionReason` (the way `Stop`'s documented decision
control does) was not confirmed within that build's investigation budget — two lookups against
Claude Code's own hooks reference (`https://code.claude.com/docs/en/hooks`) disagreed, and the
session hit a rate limit before a third, decisive lookup could run.

## Deliverables

  subagent whose reply is deliberately malformed, have `subagent-stop.js` attempt the
  `permissionDecision: 'block'` response, and confirm from the subagent's own transcript/behavior
  whether it was actually forced to continue rather than stopping) before implementing the
  forced-retry mechanism either way.
- If confirmed supported: implement the forced-retry mechanism in `subagent-stop.js`, scoped to
  non-exempt `agent_type`s only (reuse #1596's exemption check), with a one-retry cap per
  `(session_id, agent_id)` — mirror `resolve-profile.js`'s session-scoped model-failure-blacklist
  convention (`${os.tmpdir()}/ct-model-failures-${sessionId}.json`) for the retry-count file

  write itself fails.
- If confirmed unsupported: close this record noting the platform limitation, and consider
  whether `friction-events.js`'s existing `contract-violation` detection could instead be surfaced
  back to the *dispatching* agent in-run some other way (e.g. via `hookSpecificOutput.additionalContext`
  on a different, dispatcher-facing hook event) rather than acting on the violating subagent itself.
