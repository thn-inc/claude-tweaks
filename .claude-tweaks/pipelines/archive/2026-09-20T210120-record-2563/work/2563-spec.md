# 2563: wrap-up-pack.js: ledger probe reports 0 items for a slug-named ledger file

Surface: infra

## Current State
`bin/lib/wrap-up/pack.js`'s `ledgerProbe` (called from `bin/wrap-up-pack.js`) locates a run's ledger file via `namesRecord(file, n)`, which requires the ledger filename to contain the record number at a `-{n}-` or `-{n}.` boundary (added per #1930 review M5, to stop a bare substring test from letting a ledger's date prefix accidentally match a record number). However, `_shared/ledger-format.md`'s Location section defines the canonical ledger filename as `docs/plans/YYYY-MM-DD-{feature}-ledger.md`, where `{feature}` is the plan/spec **topic slug** — not the record number. For a real single-record pr-first run observed directly, the ledger was named `docs/plans/{date}-{topic-slug}-ledger.md` and held 6 items (3 open), but `namesRecord` never matched because the record number never appeared in the filename as a `-{n}-`/`-{n}.` token at all — the filter in `ledgerProbe` (`pack.js` line 350) silently excluded the file, and `wrap-up-pack.js` reported 0 ledger items. Because wrap-up's Phase 3 ledger gate reads this probe's count, a run with genuinely open ledger items would pass the gate as if the ledger were empty.

## Deliverables
1. `ledgerProbe`'s file-selection logic locates the run's ledger by the same rule `_shared/ledger-format.md`'s Location section actually defines — matching on the run's known plan/spec topic slug (or, when unavailable, on a broader signal that still excludes unrelated ledgers) rather than requiring the bare record number to appear in the filename.
2. The `namesRecord` record-number-boundary check (or its replacement) still prevents the originally-fixed #1930 regression: a ledger whose date prefix happens to contain digits matching the record number must not be treated as this run's ledger by coincidence alone.
3. The fix respects `_shared/ledger-format.md`'s resolution rule: when a run dir resolves and `{run-dir}/ledger.md` exists, that's the active ledger (gated no-worktree case); otherwise fall back to the `docs/plans/*-ledger.md` glob, filtered to the run's own ledger.

## Acceptance Criteria
1. Given a run whose ledger is `docs/plans/{date}-{topic-slug}-ledger.md` (slug unrelated to the record number, matching the observed real-world case), `ledgerProbe` locates that file and reports its actual item counts (open/total/byPhase) rather than 0.
2. Given a run whose ledger filename happens to embed a `spec-N` style slug matching the record number, `ledgerProbe` still locates and counts it correctly (no regression on the case the current code already handles).
3. Given two ledger files in `docs/plans/` — one belonging to this run and one from an unrelated run whose date prefix's digits coincidentally match this run's record number — `ledgerProbe` counts only the run's own ledger, not the unrelated one (the #1930 regression this fix must not reintroduce).
4. Given a gated no-worktree run where `{run-dir}/ledger.md` exists, the probe (or its caller) uses that file as authoritative per `_shared/ledger-format.md`'s resolution rule, not the `docs/plans/` glob.
5. A wrap-up run with the fix applied and 3 open ledger items present causes Phase 3's ledger gate to see a non-zero open count (verified by re-running the repro: single-record `/claude-tweaks:flow #N build,test` then `review,polish,wrap-up` under `integration-model: pr-first`).

## Technical Approach
- Change `ledgerProbe`'s file-selection predicate in `bin/lib/wrap-up/pack.js` to resolve the run's ledger via its actual topic/spec-slug association (the same value the run used when it wrote the ledger — likely available from run-state or the run's own recorded plan/spec metadata) rather than the record number appearing literally in the filename.
- Keep a positive-match discipline equivalent to `namesRecord`'s original anti-false-positive intent (AC 3) — the replacement must still reject an unrelated ledger from another run/date, just keyed on the correct identifying value (topic slug or run association) instead of the record number.
- Wire in `_shared/ledger-format.md`'s stated resolution order: check `{run-dir}/ledger.md` first when it exists (gated no-worktree case), fall back to the `docs/plans/*-ledger.md` glob otherwise.
- Verify against both fixture shapes in tests: a ledger named with the record number (current passing case) and a ledger named with an unrelated topic slug (the newly-reported failing case).

### Key Files
- `plugin/bin/lib/wrap-up/pack.js` — `namesRecord` (line 344-346) and `ledgerProbe` (line 348-365); replace the record-number filename match with topic/run-association-based resolution, preserving the anti-false-positive guarantee.
- `plugin/bin/wrap-up-pack.js` — CLI entry point invoking the probe; no logic change expected beyond what `pack.js` handles.
- `plugin/skills/_shared/ledger-format.md` — Location section defining the canonical filename shape and the `{run-dir}/ledger.md` resolution rule; consult when implementing, no edit expected unless the resolution rule itself needs clarifying language.

## Gotchas
- The original #1930 fix existed specifically to stop a false-positive (a date-prefix digit match), so the replacement resolution logic must be validated against that same false-positive scenario, not just the newly reported false-negative one — see AC 3.
- If the run's topic/spec-slug association isn't reliably available to `ledgerProbe` at the point it runs (e.g. no run-state or plan metadata carries it), the fallback behavior needs to be decided explicitly rather than silently reverting to the broken record-number match — flag this as an open design question if the association turns out not to be readily available in `pack.js`'s existing `inputs`.
- This bug means Phase 3's ledger gate can currently pass silently on runs with genuinely open items — worth checking whether other consumers of `ledgerProbe`'s output share the same blind spot.
