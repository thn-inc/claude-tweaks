# 1985: dispatch's cross-PR overlap check only runs once at drain start -- misses overlap between PRs the same drain opens

Surface: infra

## Current State

`dispatch/queue-pull-script.md` fetches open PRs once per firing (`gh pr list --state open --json number,files,closingIssuesReferences --limit 100` into `dispatch-open-prs.json`), runs `grouping.js`'s `detectCrossPRFileOverlap(groups, openPRs)` once, and writes `dispatch-crosspr-overlap.json`; `cross-pr-overlap-report.md` renders one warning line per entry before Step 3 and states it is a warning only, never a gate. `dispatch/SKILL.md` Step 5 then dispatches the selected groups one at a time, sequentially, each group opening its own draft PR at run start (`_shared/pr-early-run-lifecycle.md`, recorded as `pr` in the group's `run-state.json`), and Step 6's Auto-merge gate (`settle-and-merge.md`) judges each `auto:merge` group with `merge-check` before merging. Nothing between groups re-reads the PR list, so a PR opened by group 1 is invisible to group 2's overlap check, and the Auto-merge gate never asks whether the PR it is about to merge overlaps another PR the same drain opened.

Observed 2026-09-05/06 (`--budget all`): #1480 and #1596, dispatched sequentially, each edited the same paragraph of `plugin/skills/_shared/subagent-output-contract.md`; both PRs built, reviewed, and passed; the conflict surfaced only when a human tried to merge both.

`detectCrossPRFileOverlap` is pure and takes any PR list, so the missing piece is the input (the drain's own PRs) and two call sites, not a new algorithm. Tests: `tests/bin-lib/issues/grouping.test.js` covers the function; `tests/dispatch-*` conformance tests pin the skill prose.

## Deliverables

- [ ] **The drain keeps its own PR list.** `dispatch/SKILL.md` Step 5: after each group's first Task call returns with a recorded PR (or after the second call, when the first did not open one), read the group's `run-state.json` `pr.number`, fetch that one PR's changed files (`gh pr view {n} --json number,files,closingIssuesReferences`), and append the entry to a session-scoped `dispatch-drain-prs.json` (`_shared/session-tmp-root.md`). One `gh pr view` per dispatched group; no repeated `gh pr list`.
- [ ] **Re-check before each subsequent mint.** Step 4, for every group after the first: run `detectCrossPRFileOverlap([group], preDrainOpenPRs ∪ drainPRs)` and, for each hit against a drain PR, render `cross-pr-overlap-report.md`'s warning line with the suffix "(opened by this drain, group {k})" and log `STAGED … — dispatch: group [{issues}] overlaps drain PR #{pr} on {files}; dispatched anyway, serialize before merge`. Still a warning, never a gate; the group dispatches.
- [ ] **Hold auto-merge on a live drain overlap.** `settle-and-merge.md`'s Auto-merge gate, before `merge-check`: if the group's PR overlaps (by the same function) any other drain PR that is still open, the gate falls back to the Review Console for that group with the log line `AUTO … — Auto-merge gate: group [{issues}] held — overlaps drain PR #{pr} on {files}; merge order is a human call. Reversibility: n/a.`; once the overlapping PR has merged or closed, the next firing's gate proceeds normally (the check re-reads state, it does not persist a hold).
- [ ] **Report file.** `cross-pr-overlap-report.md` gains a "Second and third invocation" paragraph naming the two new sites, the drain-PR list, and the unchanged pre-drain report.
- [ ] **Tests.** `grouping.test.js`: `detectCrossPRFileOverlap` over a union of pre-drain and drain PR lists attributes the hit to the drain PR (a `source` or ordering the caller can read); prose pins (sized like `tests/dispatch-budget-drain.test.js`) for Step 5's list write, Step 4's re-check and log line, the Auto-merge gate's hold and log line, and the report paragraph.

## Acceptance Criteria

1. In a fixture drain of three groups where group 2's key files overlap group 1's PR files, group 2's mint step logs the `STAGED` overlap line naming group 1's PR and still dispatches; group 3 (no overlap) logs nothing new.
2. With `auto:merge` on both overlapping groups, the second group's Auto-merge gate logs the held line and routes to the Review Console instead of merging while the first PR is open; after the first PR merges, a re-run of the gate proceeds.
3. The pre-drain overlap report and `dispatch-crosspr-overlap.json` are byte-identical to today for the same queue.
4. Exactly one `gh pr view` per dispatched group is added; no additional `gh pr list` calls.
5. `npm test` green; the existing grouping and dispatch conformance tests pass with only additive assertions.
6. Replaying the #1480/#1596 sequence in a fixture logs the overlap at group 2's mint and holds the second auto-merge; quoted in the PR description.

## Technical Approach

Two trigger points, both cheap: the mint-time re-check catches the overlap as early as the pipeline can know it (the first PR exists), and the gate-time hold is the one place where the cost of being wrong is a conflicting auto-merge. Feed both from the drain's own list rather than re-listing all open PRs, so cost scales with groups dispatched, not with repository size. Keep the pre-drain report unchanged and keep the warning non-gating at mint; only the merge is held, and only by routing to the console the drain already has.

- `plugin/skills/dispatch/settle-and-merge.md` — Auto-merge gate hold and log line
- `plugin/skills/dispatch/cross-pr-overlap-report.md` — second/third invocation paragraph
- `plugin/bin/lib/issues/grouping.js` — `detectCrossPRFileOverlap` attribution of the matched PR's source (additive)
- `tests/bin-lib/issues/grouping.test.js`, a `tests/dispatch-*` prose-pin sibling — new cases

## Gotchas

- The queue-order cache (#1571) must not cache the drain-PR list across firings; it is per firing by construction (session tmp), and Step 4's re-check unions it with the persisted pre-drain snapshot.
- A group that opened no PR (local-merge, or a degraded PR-early lifecycle) contributes nothing to the list; log that once so a silent gap is visible.
- The Auto-merge gate's hold must read the overlapping PR's *current* state; a PR merged mid-drain releases the hold on the next evaluation.
- `--limit 100` on the pre-drain list is untouched; the drain list is bounded by `--budget`.

## Current State

`dispatch/cross-pr-overlap-report.md`'s cross-PR file-overlap check runs exactly once, at Step 2's queue pull, before that firing's drain has dispatched anything -- it can only see open PRs that already existed at that moment. During a live `--budget all` drain (2026-09-05/06), two candidates dispatched sequentially in the *same* firing (#1480, #1596) each independently edited the same paragraph in `plugin/skills/_shared/subagent-output-contract.md`. Neither PR existed when the pre-drain overlap check ran, so it reported clean for both; the resulting merge conflict was discovered only when a human later asked to merge both PRs and hit it directly. Both PRs individually built, reviewed, and passed cleanly -- the overlap was invisible to the pipeline the whole time it was happening.

## Deliverables

- [ ] Decide where a per-group overlap re-check should run inside a drain that dispatches multiple groups sequentially -- candidates: immediately before a group's second call reaches its Auto-merge gate, or right before minting each new group's run directory (Step 4) using the drain's own in-flight PR list instead of (or in addition to) the pre-drain snapshot
- [ ] Implement the chosen check and surface a finding when a group's key files overlap another PR opened *by this same drain*, not just PRs that predate it

## Acceptance Criteria

1. A `--budget all` (or `--budget N>1`) drain that dispatches two groups touching the same file surfaces that overlap to the human before both PRs sit open unmerged and conflicting, or at minimum before either is auto-merged
2. The existing pre-drain overlap report continues to work unchanged for pre-existing PRs

## Technical Approach

The current report (`dispatch/cross-pr-overlap-report.md`) already has the shape needed (`gh pr list` + key-file comparison) -- the gap is purely *when* it runs. Re-running it once per group, right before that group's Auto-merge gate, would catch this case at low marginal cost (one extra `gh pr list` call per group in a drain, not per firing). Needs design thought on exactly which trigger point and how much extra API cost is acceptable for a large drain.

## Gotchas
