# 1984: dispatch has no pre-build check for a record whose deliverables are already shipped on main

Surface: infra

## Current State

`/claude-tweaks:dispatch`'s queue pull (`dispatch/queue-pull-script.md`) excludes blocked, oversized, and open-linked-PR records; the open-PR exclusion (#1224) reads each candidate's `closedByPullRequestsReferences` connection through one batched GraphQL query built in `bin/lib/issues/record.js` (`i{n}: issue(number){ closedByPullRequestsReferences(first:10){ nodes{ number state } } }`, fetched by `bin/lib/issues/linked-prs.js`) and `partitionByOpenLinkedPR`. That connection only lists PRs linked by a closing keyword, so a merged PR that resolved a record while merely mentioning it is invisible to the pull, and the record stays eligible with a live `auto:build`.

Observed 2026-09-05/06: #1791 (created 2026-09-02) was resolved by PR #1803 (merged 2026-09-03), whose body references `#1791` with no closing keyword; #1484 by PR #1857 (its body references `#1484`, `#1124`, `#1730`, `#1858`). Both were caught only because an agent re-verified deliverables by hand before dispatching; each would otherwise have burned a build cycle to discover the same thing mid-pipeline. Key Files existence is a weak signal on its own: a record's Key Files name files to *modify*, which exist before and after the work.

Sibling: #1983 (shaped alongside) adds the "named target no longer exists" exclusion at the same pre-flight site; #1944 adds a title-similarity tokenizer this record can reuse.

## Deliverables

- [ ] **Fetch mentions, not only closers.** Extend the batched query in `record.js` with each candidate's cross-reference timeline: `timelineItems(itemTypes:[CROSS_REFERENCED_EVENT], first:20){ nodes{ ... on CrossReferencedEvent { source { ... on PullRequest { number title state merged mergedAt } } } } }`; `linked-prs.js` returns them beside the closers. One query, no per-record spawn.
- [ ] **A two-tier heuristic, documented as one.** `bin/lib/issues/shipped-candidate.js` exporting `classifyShipped(record, mentions, opts)` → `{ tier: 'strong' | 'weak' | 'none', pr, signals }`: a mention by a **merged** PR merged after the record's `createdAt` is the base signal (`weak`); it becomes `strong` only when, additionally, the PR's title token similarity to the record's title is at or above the threshold (the #1944 tokenizer when present, else a local Jaccard with the same normalization) **or** the PR's changed files (`gh pr view --json files`, fetched only for `weak` candidates, capped at 5 per pull) cover every path in the record's `### Key Files`. A record with no `### Key Files` and no title match can never be `strong`. Mentions by open or closed-unmerged PRs are ignored.
- [ ] **Act by tier.** `queue-pull-script.md`, after #1983's target-existence step: `strong` → exclude for this pull into `dispatch-shipped-excluded.json`, log `AUTO … — dispatch: #N excluded, shipped by merged PR #M ({signals})`, and stage one Close proposal in tidy's `Close (GitHub)` shape naming the PR and signals; `weak` → keep the record eligible, log one `AUTO … — dispatch: #N mentioned by merged PR #M without a closing keyword; dispatching anyway` line, and append the PR to the record's dispatch context so the build's Spec Step 2 checks it first; `none` → nothing. Dispatch never closes on GitHub; the staged proposal is the only write path. The exclusion is recomputed every pull and the proposal is fingerprint-deduplicated, so an unresolved candidate is surfaced, not silently re-selected, each firing.
- [ ] **Posture, written down.** A "False-positive posture" paragraph in `dispatch/SKILL.md` Step 2: `strong` requires two independent signals; a genuinely open record can only be excluded when a merged PR both mentions it and either matches its title or touches all its Key Files, and the exclusion costs one human approval, never a close; `weak` never blocks. Name the residual false negative (a resolving PR that never mentions the record) as accepted.
- [ ] **Tests.** `tests/bin-lib/issues/shipped-candidate.test.js`: fixtures for the #1791/#1803 and #1484/#1857 shapes → `strong`; a merged PR mentioning the record in a "refs #N, follow-up" sense with unrelated title and files → `weak`; an open PR mention → `none`; no Key Files and no title match → never `strong`. `linked-prs` tests for the extended query shape. A prose pin for the queue-pull step, the two log lines, and the posture paragraph.

## Acceptance Criteria

1. `classifyShipped` returns `strong` for both observed instances' fixtures, `weak` for a mention-only fixture, and `none` for an open-PR mention.
2. In a fixture queue, a `strong` record is written to `dispatch-shipped-excluded.json`, logged, and staged as a Close proposal; no run directory is minted for it; a `weak` record is dispatched with the extra log line and context.
3. The batched GraphQL query carries the timeline selection and `linked-prs.js` returns mentions without a second network round trip; changed-file fetches happen only for `weak`-tier candidates and are capped.
4. `dispatch/SKILL.md` states the false-positive posture and the accepted false negative.
5. `npm test` green; existing `linked-prs` and queue-pull conformance tests pass with only additive assertions.
6. Replaying the drain of 2026-09-05/06 in a fixture excludes #1791 and #1484 with staged closes and zero build attempts; quoted in the PR description.

## Technical Approach

Make the mention the trigger and require a second, independent signal before anything changes, because the record's own gotcha is right: skipping a live record is the expensive mistake. Reuse the batched query so the pull's cost stays one round trip; fetch changed files lazily and capped. Keep every effect staged: exclusion for the firing plus a proposal, never a close.

## Gotchas

- `timelineItems` returns mentions from any repository; filter to this repo's PRs before classifying.
- A PR that mentions many records (PR #1857 mentions four) is a `strong` candidate only for the records its title or files actually match; the mention alone is `weak` for the rest.
- The queue-order cache (#1571) persists `excluded`; recompute this exclusion on every full pull and include it in the persisted set so a cache hit stays consistent.
- Order the pre-flight steps: open-PR exclusion (#1224) → target-missing (#1983) → shipped (this record); a record excluded earlier is never re-classified here.

## Original request

Surface: infra

## Current State

During a `/claude-tweaks:dispatch --budget all` drain (2026-09-05/06), ranking surfaced two records (#1484, #1791) whose full deliverable set was already shipped on `main` via an earlier, unrelated PR (#1857 and #1803 respectively) -- but neither PR's own commit(s) stamped a per-issue `Fixes #N` closing keyword for the record it actually resolved, so both records stayed open with a live `auto:build` grant despite there being no code left to write. Both were caught by a human/agent manually re-verifying the record's deliverables against current `main` before dispatching a build -- had that check not happened, dispatch would have burned a full build cycle discovering the same thing at the worst possible point (mid-pipeline).

## Deliverables

- [ ] Give dispatch's queue-pull step (or a cheap pre-flight immediately before minting a group's run directory) a lightweight "is this record's own deliverable already present on `main`?" check -- scoped to avoid false positives (a record whose Key Files/Deliverables already exist verbatim is a strong signal; a record with no Key Files section can't use this check at all)
- [ ] When the check fires, skip dispatching a build and instead surface the record for a quick human/agent decision (close directly with an explanation, same as the two manual instances this record documents) rather than silently continuing to re-select it every firing

## Acceptance Criteria

1. A record whose full deliverable set is verifiably already on `main` is flagged before a build attempt starts, not discovered mid-build
2. The check has a documented false-positive/false-negative posture (it's a heuristic, not a guarantee) and never blocks a genuinely-still-open record

## Technical Approach

The two live instances both resolved the same way: check the record's `### Key Files` paths for existence, and/or search for an already-merged PR whose title/body closely matches the record's own title, referencing the record's number without a closing keyword. Either signal alone is weak; both together (files exist AND a plausible unlinked PR is found) is a reasonably strong heuristic. This needs design thought before implementation -- a naive version risks false-positiving on a record that's genuinely still open but happens to share file paths with unrelated already-merged work.

### Key Files

- `plugin/skills/dispatch/queue-pull-script.md` -- candidate pre-flight site
- `plugin/skills/dispatch/SKILL.md` Step 3/4 -- where a pre-build check would plug in

## Gotchas

- False positives here are worse than false negatives: incorrectly skipping/closing a genuinely-open record is a much bigger mistake than occasionally still dispatching a build for something already shipped (the status quo, which at least fails safely at build time).

Filed per this project's no-implicit-deferrals rule -- discovered live during a `/claude-tweaks:dispatch` drain (two independent instances, same root cause), real and reproducible, but the design work needed is bigger than this drain's own scope.
