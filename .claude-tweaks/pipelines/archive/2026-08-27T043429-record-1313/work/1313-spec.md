# 1313: Fix compute-then-exit truncation risk in release.js and review-coordination.js

Surface: backend
Defer-reason: pre-existing-outside-diff

## Current State

While resolving #1176 (write-then-process.exit() truncation across `plugin/bin/*.js`), the sweep found two files using a related but structurally distinct idiom that #1176's own scope rule ("a `process.exit(N)` directly preceded, same function, no unrelated statements between, by a stream write") excluded:

- `plugin/bin/release.js:124`: `process.exit(main(process.argv));`
- `plugin/bin/review-coordination.js:106`: `process.exit(run(process.argv.slice(2)));`

Both call `process.exit()` with the return value of a function that may itself write to stdout/stderr just before returning — several function-return layers removed from the exit call, so it doesn't literally match #1176's "same function" rule, but it is the same underlying async-write-vs-exit race in effect: if `main()`/`run()`'s last statement is a stdout/stderr write immediately before returning, a piped consumer can still see truncated output.

## Deliverables

- For each file, change `process.exit(fn(...))` to `process.exitCode = fn(...);` and let the top-level statement fall through normally (no function to add a `return` to — these are already the last statement in the module).
- Verify each file's own function (`main()` / `run()`) doesn't have any code after its own final write that assumes an immediate hard-stop.

## Acceptance Criteria

1. Both files exit with the same status code as before for a representative success and failure case.
2. `npm test` passes in full.

## Technical Approach

Same mechanical pattern as #1176: `process.exitCode = <value>;` instead of `process.exit(<value>)`. Since these are the final statement in each module (no enclosing function to restructure), this is a direct swap with no additional control-flow changes needed — verify by reading each file's `main()`/`run()` in full first, per #1176's own safety rule, before assuming so.
