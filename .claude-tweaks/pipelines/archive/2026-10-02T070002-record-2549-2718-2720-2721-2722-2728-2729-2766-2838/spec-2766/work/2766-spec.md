# 2766: tests/bin-lib/log-decision/append.test.js flakes on Windows under load (atomic-rename EPERM) — allowlist it, or bound the rename retry in atomic-write.js

Surface: infra

Origin: consolidated Review Console, run `2026-09-21T213441-spec-2697-2757-2758-2759` (Queue write, staged at `spec-2697/staged/flaky-allowlist-tests-bin-lib-log-decision-append.test.js.md`)

Defer-reason: tangential

## Current State

During #2697's Common Step 5 full verification (runner `verify.js`, tree `d5343fdf7`, 9360 tests /
9012 pass / 343 fail), `tests/bin-lib/log-decision/append.test.js` failed once — the **only** failing
file not in the run's batch pre-flight baseline (run ledger #2, 103 files).

Failing test: ``appendEntry: concurrent `node bin/log-decision.js` processes against the same run dir
never drop an entry``. Failure: `worker 2 exited 3: could not write decisions.md (EPERM: operation not
permitted, rename '…decisions.md.tmp-26780' -> '…decisions.md')` — a Windows atomic-rename collision
between concurrent writers under machine load.

Nothing on the branch touched `plugin/bin/lib/log-decision/`. Isolated re-run
`node --test tests/bin-lib/log-decision/append.test.js`: 9/9 pass. So the failure is load-dependent,
not a regression.

## Deliverables

Pick one of two mutually exclusive routes and state why the other was not chosen:

1. **Allowlist the test.** Add `tests/bin-lib/log-decision/append.test.js` to
   `.claude-tweaks/verify-scope.json`'s `flaky.files`. If the declaration carries no `retry` template
   for the `tests` suite yet, add it alongside: `"retry": "node --test {file}"` and
   `"maxRetries": 1`. Without **both**, the entry is incomplete (`test/verification.md`'s Flake
   handling).
2. **Fix the product behavior the test guards.** The test asserts a real concurrency property, and on
   Windows `fs.rename` over an open target returns `EPERM`. A bounded, Windows-only retry loop in
   `plugin/bin/lib/atomic-write.js`'s rename would make the guarded behavior actually hold rather than
   declaring its test flaky. This is the better outcome if the retry is cheap to bound correctly —
   `log-decision.js` is a sanctioned run-dir writer that concurrent sibling agents genuinely hammer.

## Acceptance Criteria

Route 1: a `verify.js` run whose `tests/bin-lib/log-decision/append.test.js` fails once retries it and
reports the file as passing; the `flaky.files` entry carries both `retry` and `maxRetries`.

Route 2: the concurrent-writers test passes under deliberate contention on this Windows box (run it
with sibling load, quote the raw output), with no allowlist entry added; `atomic-write.js`'s retry is
bounded and covered by its own regression test.

## Release Note

Stopped a decision-log test from failing intermittently on Windows under load.

## Technical Approach

Start with Route 2's feasibility check: read `plugin/bin/lib/atomic-write.js`'s current rename call. If it already has any retry scaffolding, a bounded Windows-only `EPERM` retry (a handful of attempts with a short backoff, gated to `process.platform === 'win32'`) is likely a small, contained addition. If the rename is a bare single-shot call with no surrounding structure, Route 1 (allowlist) is the cheaper, lower-risk choice — `.claude-tweaks/verify-scope.json`'s `flaky.files` shape is documented in `test/verification.md`'s Flake handling section. Whichever route is chosen, the record's own AC requires stating why the other was declined — this is not optional per the Deliverables text.

### Key Files

- `.claude-tweaks/verify-scope.json` — Route 1's allowlist entry (`flaky.files`, `retry`, `maxRetries`)
- `plugin/bin/lib/atomic-write.js` — Route 2's bounded rename retry
- `tests/bin-lib/log-decision/append.test.js` — the guarded concurrency property; Route 2 adds a regression test near this one if the fix lands here instead
- `plugin/bin/log-decision.js` — the sanctioned run-dir writer this test guards

## Gotchas

- The two routes are mutually exclusive by design — don't do both. Route 1 accepts the flake as an environmental Windows limitation; Route 2 asserts the underlying behavior should actually hold. Pick based on how cheap a *correctly bounded* retry actually is once `atomic-write.js`'s current rename call is read — don't assume either route without that read first.
- This is a Windows-only failure mode (`EPERM` on `fs.rename` under concurrent access) — a fix or allowlist entry must not regress the passing behavior on macOS/Linux CI.
