# 2721: backlog refine: closing summary's dependency-repair count doesn't disclose when the documented detection method was substituted

Surface: infra

Origin: by:feedback (self-referential session evaluation, /claude-tweaks:feedback bare invocation)

**Related:** #2729

## Current State

`refine-mode.md`'s Step 5 documents the Dependency-repair lane's detection method precisely: attach native blocked-by links via `buildNativeDependencyQuery`, then run `findUnresolvedDependencyProse` over the result (confirmed present in `refine-mode.md`). In a session on 2026-09-20, this mechanized method was not run; instead, every candidate record's body was read directly by hand as part of the priority-lane synthesis pass, and no "blocked by" prose was found in that manual read. The rendered closing summary reported "0 dependency-repair" exactly as it would if the documented mechanized check had run and found nothing — with no line disclosing that a different, less rigorous method actually produced that zero.

## Deliverables

- When a refine run's closing summary reports a lane count for a check whose documented mechanism was not run in full (a manual substitute was used instead), state that substitution inline next to the count — e.g. "0 dependency-repair (manual body read, not the native-link+prose-scan pipeline)" — rather than rendering the same bare count a fully-mechanized run would produce.
- Consider whether this same disclosure obligation applies to any other lane in `refine-mode.md`/`refine-lanes.md` whose detection has more than one implementation path.

## Acceptance Criteria

- A refine closing summary distinguishes, per lane, between "checked via the documented mechanism, found nothing" and "checked via a substitute method, found nothing" wherever the two can diverge in confidence.

## Release Note

Made backlog refine's summary say when a check ran by a substitute method instead of the documented one.

## Technical Approach

Extend `refine-closing-summary.md`'s closing-summary render (the same file #2729 targets for its mechanical-tally fix — related, but a distinct concern: that record makes the *count* itself trustworthy, this one makes the *method* behind a zero-or-low count disclosed) to carry an optional method-substitution annotation per lane. The natural point to detect the substitution is wherever `refine-mode.md`'s Step 5 actually invokes (or skips) `buildNativeDependencyQuery`/`findUnresolvedDependencyProse` — if that step's own procedure was bypassed in favor of a manual read, the closing-summary composer needs that fact as an explicit signal (a flag or note carried alongside the lane's own count) rather than inferring it after the fact from `decisions.md`. For the second (exploratory) deliverable, audit every lane in `refine-mode.md`/`refine-lanes.md` for lanes with more than one detection path (mechanized vs. manual/fallback) and decide per-lane whether the same annotation is warranted.

### Key Files

- `plugin/skills/backlog/refine-closing-summary.md` — the closing-summary render this record adds the method-substitution annotation to
- `plugin/skills/backlog/refine-mode.md` — Step 5's Dependency-repair lane, where the native-link+prose-scan pipeline is documented and where a substitution would need to be flagged
- `plugin/skills/backlog/refine-lanes.md` — candidate location for the cross-lane audit the second deliverable asks for

## Gotchas

- The second deliverable is exploratory ("consider whether...") — the Acceptance Criteria above cover only the Dependency-repair lane explicitly; a build should treat generalizing to other lanes as a judgment call to make and document, not a mandatory expansion.
- This is a disclosure fix, not a correctness fix to the detection itself — a manual read that happens to be accurate still produces a correct "0," this record only asks that the audit trail say which method produced it.
