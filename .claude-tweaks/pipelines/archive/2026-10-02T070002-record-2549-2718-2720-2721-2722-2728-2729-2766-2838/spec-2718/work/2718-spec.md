# 2718: backlog refine: grant-check dispatch has no pre-check that the ready+ungranted population is still current before spending the judgment budget

Surface: infra

Origin: by:feedback (self-referential session evaluation, /claude-tweaks:feedback bare invocation)

**Related:** #2719, #2720

## Current State

`/claude-tweaks:backlog refine`'s grant sub-stage (`refine-mode.md` Step 3) computes its worklist once, then spends real wall-clock time generating a `RECOMMEND_BUILD`/`RECOMMEND_MERGE` judgment (via `assess-agent-autonomy grant-check`) for every candidate in `.grantSlice.selected`, before Step 5's pre-write reverify ever checks whether that judgment's premise still holds. In a session on 2026-09-20, a full whole-queue `/claude-tweaks:backlog refine` sweep computed grant-check judgments for 40 ready-but-ungranted records (parallelized across 5 Task-agent dispatches to make the volume tractable) — and by the time Step 5's reverify ran, a concurrent actor (another session or a scheduled Routine) had already fully processed the entire same 40-record population: every record already carried a `priority:*` label and either a grant (`auto:build`/`auto:merge`) or `needs:decision`. All 40 of this run's freshly computed grant-check judgments were discarded as stale at write time — the reverify step correctly caught the race, but only after the (expensive) judgment pass had already run to completion with no cheaper earlier signal available.

Step 3 already has one comparable pattern at its own entry point: the "Merge-lane circuit breaker reset offer," which reads a best-effort breaker signal before the grant-sweep runs. This record's freshness check is the analogous idea applied to the population itself rather than a breaker flag.

## Deliverables

- Add a cheap, mechanical pre-dispatch freshness check immediately before the grant-check judgment pass fires (e.g., a lightweight `gh issue list --label ready --state open` count/diff against Step 1's own fetched population, or a re-check of just the candidate numbers' current grant/priority state) — when the population has shrunk or already resolved since Step 1's fetch, short-circuit before spending the judgment budget on now-stale candidates, not just before the write.
- Document this check in `refine-mode.md`'s Step 3, alongside the existing merge-lane circuit-breaker offer that already runs at this sub-stage's start.

## Acceptance Criteria

- A grant sub-stage run where the candidate population has already been fully processed by a concurrent actor since Step 1's fetch detects this before dispatching any grant-check judgment calls, and reports the skip plainly instead of running the full judgment pass first.
- A grant sub-stage run where the population is still current (the common case) pays no additional round-trip cost from this check — the freshness probe is cheap relative to the judgment pass it guards.

## Release Note

Added a quick freshness check before backlog refine spends effort on grant checks.

## Technical Approach

Insert the freshness check at the start of `refine-mode.md`'s Step 3, right after the existing merge-lane circuit breaker reset offer and before `.grantSlice.selected` is handed to the per-record `grant-check` dispatch loop. The cheapest option: re-fetch just the label state of the candidate numbers already in `.grantSlice.selected` (a single `gh issue list --state open --json number,labels -q '...'` filtered to those numbers, or an equivalent batched read) and compare against Step 1's own fetched snapshot — if every (or substantially all) candidates already carry a grant or `priority:*`+resolution since that snapshot, short-circuit the whole sub-stage with a plain report line, the same way the circuit-breaker offer already short-circuits on a tripped breaker. This reuses Step 5's own reverify comparison logic conceptually (same "live label state vs. captured premise" check), just run once up front over the whole slice instead of once per record after the judgment pass.

### Key Files

- `plugin/skills/backlog/refine-mode.md` — Step 3's opening (the merge-lane circuit breaker offer is the closest existing precedent), and the `.grantSlice.selected`/`.grantSlice.remaining` read this check gates
- `plugin/skills/backlog/merge-lane-reset.md` — the existing best-effort breaker-read pattern this check's own "cheap, best-effort, run before the expensive pass" shape mirrors

## Gotchas

- This check is deliberately best-effort and approximate — a population that's *partially* stale (some records resolved, most not) should still proceed with the judgment pass for the records that are still fresh, not abort the whole slice; only a fully- or substantially-resolved population justifies the short-circuit, mirroring the "cheap enough to not matter in the common case" acceptance criterion.
- Don't duplicate Step 5's own pre-write reverify logic wholesale — this is a coarser, cheaper up-front signal to avoid wasted judgment-pass cost, not a replacement for Step 5's own per-record correctness check, which still must run regardless of whether this new check fires.
