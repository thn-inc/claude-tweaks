# 2720: assess-agent-autonomy grant-check: no parallel-fan-out shape, so a caller who parallelizes it loses the Step 3.5 body-cache reuse

Surface: infra

Origin: by:feedback (self-referential session evaluation, /claude-tweaks:feedback bare invocation)

**Related:** #2718, #2719

## Current State

`/claude-tweaks:backlog refine`'s grant sub-stage (`refine-mode.md` Step 3) documents `assess-agent-autonomy grant-check` as a sequential, once-per-record `Skill()` invocation. `grant-check.md`'s own Step 1 caches the fetched record body at a session-tmp path (`assess-grant-{n}.json`, confirmed present) specifically so Step 3.5's body-shape re-verification can reuse it instead of a second `gh issue view` round-trip. On a large batch (this session's whole-queue sweep had 40 grant-check-eligible records), running 40 sequential `Skill()` calls in the main thread is impractical, so the session instead parallelized the pass across 5 ad-hoc Task-agent dispatches — each agent ran its own `gh issue view` calls directly rather than through the documented session-tmp caching path (subagents don't share the orchestrating session's `$CLAUDE_CODE_SESSION_ID`-keyed cache directory). Step 3.5 then had to re-fetch every one of the ~34 grant-recommended bodies a second time, exactly the round-trip the cache exists to avoid.

## Deliverables

- Document a sanctioned parallel-fan-out shape for the grant-check pass on a large batch — either a Task-agent dispatch template (mirroring `_shared/subagent-output-contract.md`'s Template A/B/C pattern) that writes each result to a shared, orchestrator-readable location Step 3.5 can still consume, or an explicit statement that grant-check is sequential-only and a caller facing a large batch should reduce via `--budget` rather than parallelize by hand.
- If a fan-out shape is added, specify how Step 3.5's body-cache reuse extends to it (e.g., the dispatch prompt writes the fetched body to the orchestrator's own session-tmp path before returning, rather than only to the subagent's ephemeral context).

## Acceptance Criteria

- A grant-check pass run against a 40-record batch, however dispatched, produces no more than one `gh issue view`/body-fetch round trip per record across the whole grant-check + Step 3.5 pipeline.
- The chosen shape (fan-out template or sequential-only statement) is stated in `refine-mode.md`'s Step 3, not left to be improvised per-caller.

## Release Note

Added a parallel way to run autonomy grant checks on large batches without losing cached record bodies.

## Technical Approach

Decide first whether a fan-out template is actually worth adding, or whether the simpler fix — stating in `refine-mode.md`'s Step 3 that `grant-check` is sequential-only, and that a batch above some size should be split via `--budget` across multiple refine invocations rather than parallelized by hand — is the better tradeoff (mirrors the existing `_shared/subagent-output-contract.md` guidance that dispatch templates cost real overhead and aren't a default). If a fan-out template is chosen instead: the dispatch prompt for each Task-agent must write its fetched record body to the *orchestrator's* session-tmp path (`assess-grant-{n}.json`, the same path `grant-check.md`'s Step 1 already writes to sequentially) before returning its verdict, rather than only holding it in the subagent's own ephemeral context — this is what lets Step 3.5 find and reuse the cached body regardless of which path populated it. Either way, `refine-mode.md`'s Step 3 needs to state the decision explicitly so it isn't re-improvised by the next large-batch session.

### Key Files

- `plugin/skills/backlog/refine-mode.md` — Step 3, where the grant-check invocation shape (sequential vs. a documented fan-out) needs to be stated
- `plugin/skills/assess-agent-autonomy/grant-check.md` — Step 1's session-tmp caching path (`assess-grant-{n}.json`), which a fan-out shape would need to extend rather than bypass
- `plugin/skills/_shared/subagent-output-contract.md` — the Template A/B/C pattern a fan-out shape would follow, if that's the chosen resolution

## Gotchas

- Don't build a fan-out template speculatively if the simpler "sequential-only, split via `--budget`" resolution is judged sufficient — the Deliverables explicitly offer both, and the Acceptance Criteria are satisfied by either.
- If a fan-out template is added, verify it doesn't reintroduce the exact caching gap this record describes for a *different* consumer — any future step that expects `assess-grant-{n}.json` to exist after a grant-check pass needs the fan-out path to actually write it, not just the sequential path.
