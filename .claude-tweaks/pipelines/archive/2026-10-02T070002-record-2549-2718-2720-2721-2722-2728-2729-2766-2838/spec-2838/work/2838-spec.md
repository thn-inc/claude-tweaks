# 2838: Dispatch Step 4 mint adopts a live sibling session's same-slug run dir and resumes its worktree

Verified-as-of: c8f389a605ecf680a27528bafef1ef995959fd64

Defer-reason: tangential

## Current State

`dispatch/SKILL.md` Step 4 mints each group's run dir with `hooks.js resolve-run-dir --spec-slug "record-{n}" --create`. That command still runs resolution-order step 2 (newest directory matching the slug) before minting (`_shared/run-dir-resolution.md`), so it returns an **existing** `record-{n}` directory whenever one is present, including one a live sibling session minted seconds earlier.

Observed in firing `2026-09-29T140150-dispatch-standalone`, group #2785:

- A separate live session (pid 88799) minted `2026-09-29T184002-record-2785` at 18:40:02Z, created worktree `dispatch-record-2785`, and merged `origin/main` into it at 18:40:08Z.
- About two minutes later, this firing's `resolve-run-dir --spec-slug record-2785 --create` returned that sibling-owned directory instead of minting a fresh one. This firing then ran `compose-context.js` against it, rewriting the sibling's `context/claims.md` and `context/merge.md` (identical plugin build and sources, so almost certainly byte-identical, but an unauthorized write into another session's run dir all the same).
- `EnterWorktree(name: "dispatch-record-2785")` then **resumed** the sibling's existing worktree rather than failing. `check-sibling-sessions --record 2785` flagged pid 88799 only when re-run from inside it.

The Step 4 sibling-session check had run earlier (clean, at queue-pull time), not immediately before the mint, so the window between the queue pull and the mint was unguarded. The firing stood down and touched nothing further. On a slower read the two sessions would have built the same record in the same worktree under one run dir.

Related: the "dispatch claim race window: mint to worktree entry" pattern already noted in agent memory. This is the same window, widened to cover the mint itself.

## Deliverables

1. A mint-only mode for `resolve-run-dir` (e.g. `--create --fresh`, or `--create` that skips step 2 whenever `--standalone` is absent). It always creates a new timestamped directory and never adopts an existing same-slug one. Use it at dispatch Step 4 and at `flow/claim-targets.md`'s direct-invocation mint. Keep adopt-if-exists behavior for the read-only resolution callers that depend on it.
2. Dispatch Step 4 re-runs `check-sibling-sessions --record {n}` for every group member **immediately before** the mint, not only at queue-pull time. A positive result stops that group, exactly as `sibling-session-check.md` already specifies.
3. Dispatch Step 5 refuses to enter a pre-existing `dispatch-record-{n}` worktree. If the worktree-creation call reports it resumed an existing worktree, the dispatching session exits it with `keep`, logs the sibling conflict, and skips the group without dispatching either call.
4. Tests for (1): a pre-existing same-slug directory is not returned under the mint-only mode; a fresh directory is created and returned.

## Acceptance Criteria

- [ ] With a `record-{n}` run dir already present under `.claude-tweaks/pipelines/`, dispatch Step 4's mint returns a **new** directory, never the existing one.
- [ ] A sibling session holding `record-{n}` (live worktree lock) at mint time stops that group before any write into any run dir.
- [ ] An existing `dispatch-record-{n}` worktree is never resumed by dispatch Step 5; the group is skipped and the skip is logged.
- [ ] Read-only `resolve-run-dir` callers (no `--create`) keep their current adopt-newest-matching behavior.
- [ ] `npm test` passes.

## Release Note

Two sessions dispatching the same record no longer end up sharing one run directory and worktree.
