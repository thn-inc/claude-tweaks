# 3784: Make flow's resume-to-merge row workable for an unattended run

Surface: infra

**Related:** #3712, #3749, #3783, #3595, #3467, #3488, #3672, #3696, #3706, #3740, #3762

## Current State

`flow/summary-template.md`'s Resume-to-merge row renders `PIPELINE_RUN_DIR="{run-dir}" /claude-tweaks:flow "{target}" wrap-up` ("resume to re-offer the merge decision") for every `pr-first` run ending `armed` or `pending-review`. When the run's autonomy ceiling grants `consoleAutoResolve` (`unattended`), the resume cannot offer that decision:

- `wrap-up/review-console.md`'s Auto-resolution short-circuit resolves the console with zero `AskUserQuestion` calls. Its merge half resolves `leave-open` again for a record lacking `auto:merge` (the #1802/#1966 ungranted-member carve-out).
- `bin/console-resolve.js` on a run dir whose `console.json` already carries `resolved: true` re-renders the stored console and re-resolves nothing (`console-resolve.js` lines 161-199).
- `pre-tool-use.js`'s Review Console ask gate (#3712) denies any `"Review Console"`-headed question at that ceiling.

So the recommended row re-parks the PR. Observed on #3712 (PR #3749, 2026-10-20). The summary recommended the row, and the user typed "okay go ahead with next", meaning "merge it right there". The merge only happened because the orchestrator ran `_shared/pr-first-merge.md` by hand. Along the way the PR had gone DIRTY because a sibling PR (#3711) landed its own `IL-166` first. The orchestrator resolved the conflict by hand (renumbering the branch's entry to IL-167 and every citation the branch added), re-ran the full suite, and merged. `_shared/pr-first-merge.md`'s Conflict path today stops at any remaining conflict marker ("unresolvable headlessly") and reports `pending-review`.

The nearest existing human-confirmed merge path, `dispatch/close-out.md`, does not fit this case:

- Its direct form resolves the PR from a still-held claim, which wrap-up releases as `pr-opened`.
- Its step 3 skips acceptance labeling on the assumption that wrap-up already ran it. #3783 covers that gap.
- Its step 2 stops on `mergeStateStatus: DIRTY`.

## Release Note

When an unattended run parks its PR, the summary's recommended next step now merges it in the same session when you say go ahead, and resolves a conflict with main itself when it safely can.

## Technical Approach

Merge mode is a thin entry over the existing merge procedure, not a new merge implementation. It resolves the run, checks the three preconditions, then follows `_shared/pr-first-merge.md` exactly as `review-console.md`'s "Approve all + merge" step does. It reads the same composed `merge` bundle via `bin/compose-context.js` and falls back to the two source files. The only new behavior is the attended Conflict-path branch, gated on the caller being merge mode. Every other `pr-first-merge.md` caller (dispatch's Auto-merge gate, the wrap-up short-circuit, `worktree-merge.md`, the release merge) keeps headless semantics. The summary row is a render-time condition read from the run's resolved ceiling (`bookkeepingPermissions(ceiling).consoleAutoResolve`, `bin/lib/issues/autonomy.js`), the same predicate `pre-tool-use.js`'s ask gate uses.

## Gotchas

- `gh pr merge --auto` on this repo fails with "Protected branch rules not configured". That error matches none of Step 3's recognized signatures, so as written it lands in branch 5 (ready plus comment, `pending-review`). It also appears when the PR has just gone DIRTY. Merge mode re-reads `mergeStateStatus` before accepting that outcome:
  - `DIRTY` takes the Conflict path.
  - `CLEAN` with green checks takes Step 2.5's `wait`-row immediate `--squash`, which is what #3749 needed.

  Whether Step 3 should recognize the signature itself is a separate question, out of scope here.
- The squash merge means cleanup Section C's own-worktree removal needs the `git merge-tree --write-tree` containment proof, not an ancestry check.
- Reconcile's `archive` check moves the run dir. Finish every `decisions.md` write before Step 4.2's reconcile, or a late write recreates the archived dir.
- Acceptance labeling (Step 1) must run before the merge closes the record. Merge mode runs it unconditionally rather than trusting that wrap-up did (#3783 adds the mechanical check).
- `/claude-tweaks:wrap-up` already parses `resume` and `cleanup-only`. Keep `merge` distinguishable from both in the token parser, and reject `merge` combined with `cleanup-only`.

## Open Question

What should a human run to merge a `pending-review` PR from an `unattended` run? Candidates:
1. **`/claude-tweaks:dispatch close-out #{n}`.** It is an existing human-confirmed merge path for `pending-review` PRs (`dispatch/close-out.md`, tag `human-approved`). Two caveats: its direct form resolves the PR from a still-held claim, which wrap-up releases as `pr-opened`, so the bare form may be the only one that works; and its step 3 skips acceptance labeling (see #3783).
2. **Grant `auto:merge` on the record, then resume.** This needs `console-resolve.js` to recompute the merge half on a re-run instead of re-printing the stored `console.json`, a behavior change to verify first.
3. **A dedicated merge entry for an adopted run** (e.g. `/claude-tweaks:wrap-up resume merge`) that runs `_shared/pr-first-merge.md` Steps 1-4 directly.
