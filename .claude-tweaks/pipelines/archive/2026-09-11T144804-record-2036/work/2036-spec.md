# 2036: SubagentStop hook misattributes contract-violation to main-session narration

# Reflect — staged finding 1

**Category:** tangential

**Related:** #2041 — same subagent-stop contract-violation misattribution cluster

## Current State

`bin/lib/hooks/subagent-stop.js`'s E3 check (Subagent Contract status-line check) is meant to
read the *dispatched subagent's own* last assistant message and flag it when it's missing the
`DONE`/`DONE_WITH_CONCERNS`/`NEEDS_CONTEXT`/`BLOCKED` status line. Across this run's two pipeline
calls (build/test in the first call, review in this one), it fired `contract-violation` three
times (`events.jsonl` at `12:04:05`, `12:12:50`, `12:15:50`), and in each case the logged
`firstLine` reads as the **main session's own status narration** while waiting on an async
Agent-tool dispatch — text like "Simplify subagent (…) is running against the two doc files.
I'll pause here and report status until it c[ompletes]" and "Waiting on the code-simplifier
subagent to return before proceeding to review Steps 6-7 …" — not a subagent's own reply.
(Recurred four more times later in this same wrap-up phase while awaiting the four Phase 2
curation agents, for seven total across this run.)

The handler's own code comment anticipates a *related* false-positive and exempts it: a last
assistant message that carries a narration text block **alongside a `tool_use` block** (e.g.
"Waiting for the other task to finish." immediately before calling `Monitor`/`SendMessage`)
returns `null` (no violation) at line 55 of `subagent-stop.js`, since the turn continues after
the tool result returns. But the project's own documented-correct pattern
(`agent-tool-async-wait-pattern.md` in user memory: "while waiting on an Agent-tool dispatch's
async notification, end the turn with a status message and no tool call") produces a last
assistant message with narration text and **no** `tool_use` block — exactly the shape the
existing exemption does not cover, so it falls through to the STATUS_RE check and fails it,
even though the session did exactly the recommended thing.

This suggests either (a) `ctx.input.agent_transcript_path`/`transcript_path` on a `SubagentStop`
event is resolving to the *main* session's transcript rather than the dispatched subagent's own
transcript in this environment, or (b) the exemption at line 55 needs to also cover "last
assistant turn is narration-only, immediately preceding a session-ending wait for an async
notification" the same way it already covers "narration immediately before a same-turn tool
call." Either way the practical effect is the same: a session following the documented-correct
async-wait convention gets a spurious `systemMessage` ("claude-tweaks: a subagent reply is
missing the Subagent Contract status line…") and a noise entry in `events.jsonl`.

## Deliverables

- [ ] Confirm root cause: does `SubagentStop`'s `transcript_path`/`agent_transcript_path` resolve
      to the dispatching session's own transcript rather than the dispatched subagent's, under
      some condition (e.g. the async-notification pattern specifically)? Or is the exemption at
      `subagent-stop.js` line 55 simply too narrow?
- [ ] Fix the root cause: either correct the transcript-path resolution, or widen the
      narration-only exemption to also cover a last-assistant-message with no `tool_use` block
      that immediately precedes a session-ending async wait (distinguishing it from an actual
      subagent reply that's genuinely missing its status line).
- [ ] Verify the fix does not silently swallow real subagent contract violations — the check must
      stay best-effort/non-blocking (per the file's own header comment) but should stop firing on
      compliant main-session narration.

## Acceptance Criteria

1. A session that follows `agent-tool-async-wait-pattern.md`'s documented convention (status
   message, no tool call, while awaiting an async Agent-tool notification) no longer produces a
   `contract-violation` event or the associated `systemMessage`.
2. A dispatched subagent whose own final reply genuinely omits the required status line still
   produces the `contract-violation` event — the fix narrows the false-positive without
   disabling the real check.
