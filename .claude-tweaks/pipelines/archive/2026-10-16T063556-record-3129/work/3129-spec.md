# 3129: Let verify.js stamp a pass when the only failures are declared pre-existing/unrelated

Origin: reflect light from #1350

Defer-reason: tangential

## Current State

`verify.js` only writes the pass stamp on a clean exit 0 across the full resolved check set. This
checkout is shallow (`git rev-parse --is-shallow-repository` → true, ~53 commits), so 3
`git merge-base --is-ancestor <pinned-sha> HEAD` precondition tests fail deterministically
regardless of diff content, plus one unrelated stale-PID process-liveness test
(`tests/bin-lib/visual-decide/cli.test.js`) that also reproduces on isolated re-run in this
sandbox. Every review of a docs-only or low-risk record in this environment re-derives the same
"these 4 failures are pre-existing and unrelated" conclusion by hand (isolation runs, direct
`git merge-base` reproduction) because the runner's stamp is binary and never reflects a
declared-pre-existing-failure allowance — this cost was paid identically by at least one prior
attempt on #1350's own history and again by this run.

## Deliverables

Extend `.claude-tweaks/verify-scope.json`'s declaration format with a `preExisting` (or similarly
named) list of known-failing test files/patterns — analogous to the existing `flaky.files`
mechanism — that `verify.js` treats as non-blocking for stamp purposes: when every failing test in
a run is in this declared set, write the pass stamp (with a field noting which pre-existing
failures were present) instead of leaving the run permanently un-stamped.

## Acceptance Criteria

A run whose only failures are listed in the new declaration still writes `claude-tweaks-verify-pass.json`
(scoped, as today), with a field recording the declared pre-existing failures that were present; a
run with any other failure still does not stamp.

## Release Note

No user-visible change: internal verification-runner behavior for environments with known,
declared pre-existing test failures (e.g. a shallow clone).
