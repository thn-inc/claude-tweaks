# 1421: policy-schema: detectIntegrationModel has no MCP fallback, silently defaults to local-merge when gh is absent

Surface: backend

## Current State

`detectIntegrationModel` (`plugin/bin/lib/policy-schema.js:525-538`) is the code twin of `_shared/forge-detection.md`'s ladder: it runs `git remote get-url origin`, then `gh repo view --json owner,name`, and fails open to `local-merge` if either `execFileSync` call throws — including when `gh` itself is simply not installed. Two production call sites depend on this: `bin/resolve-policy.js`'s CLI (`--values integration-model`), invoked via Bash from an agent turn, and `plugin/bin/lib/hooks/pre-tool-use.js`'s `resolveRunPinnedIntegrationModel` (the bookkeeping-stamps gate), invoked as a lifecycle hook with no agent turn active.

This behavior is already documented as a known, deliberate limitation, not a silent gap: `_shared/integration-model.md` states outright that "detection is gh-only — a Node subprocess cannot see an agent session's MCP tools, so an MCP-only sandbox... detects local-merge even though it could, in principle, integrate through GitHub via MCP," and names the intended mitigation as pinning `integration-model: pr-first` explicitly in `.claude-tweaks/policy.yml`. `/claude-tweaks:init`'s Step 20 (`init/bootstrap/step-20-integration-model.md`) already offers exactly this pin, interactively, for any GitHub-backed project. `docs/incident-log.md`'s IL-63 independently rules out the literal fix this record's Deliverables originally proposed: "Don't design a module assuming MCP tools can be called from a spawned subprocess... A module that shells out to do its own network I/O must signal what needs writing and let the calling skill's own prose drive the actual MCP call, not attempt it itself" — so `detectIntegrationModel` cannot synchronously invoke `list_issues`/`get_me` from inside the function.

This project's own `.claude-tweaks/policy.yml` has no `integration-model:` key set at all — the exact gap Step 20 exists to close, and the proximate cause of the observed run (2026-08-24T221615-dispatch-standalone) resolving `local-merge` in a gh-absent sandbox.

## Deliverables

- [ ] Pin `integration-model: pr-first` in this repo's own `.claude-tweaks/policy.yml` — the zero-risk, already-designed, one-line fix for the exact failure this record observed, available today via `/claude-tweaks:init`'s Step 20 offer or a direct edit.
- [ ] Give `detectIntegrationModel` an optional injectable reachability override (e.g. a second `{ mcpReachable }` argument) that short-circuits straight to `pr-first` when set `true` and a GitHub remote exists, without attempting any MCP call itself — consistent with IL-63, the override is supplied by the caller, never resolved inside the function.
- [ ] Wire `bin/resolve-policy.js`'s CLI to accept a `--mcp-reachable` flag that forwards into the override above, so a calling skill running inside an agent turn (mirroring `dispatch/mcp-transport.md`'s Preflight check 3 substitution — a bounded `list_issues`/`get_me` call) can pass its own MCP-derived reachability result through the CLI boundary instead of leaving detection to fall open to `local-merge`.
- [ ] Leave `pre-tool-use.js`'s `resolveRunPinnedIntegrationModel` (the bookkeeping-stamps gate) unchanged — it runs as a lifecycle hook with no agent turn active, so no MCP call is ever possible there; document this explicitly as a permanent, structural gap rather than an oversight.
- [ ] Add a one-line note to `_shared/integration-model.md`'s "Detection is gh-only" paragraph and to `detectIntegrationModel`'s own code comment, cross-referencing IL-63, so a future contributor doesn't rediscover via a live failure that an MCP call can't be added inside the function.

## Acceptance Criteria

1. This repo's `.claude-tweaks/policy.yml` carries `integration-model: pr-first`, and `resolveIntegrationModel`/`bin/resolve-policy.js --values integration-model` return `pr-first` here without shelling out to `git`/`gh` at all (explicit value wins outright, per the existing resolution ladder).
2. `detectIntegrationModel(repoRoot, { mcpReachable: true })` resolves `pr-first` for a repo with a real GitHub origin remote, even when the `gh` `execFileSync` call is faked to throw (`ENOENT`/non-zero exit) — proving the override bypasses the `gh` probe without requiring `gh` to be present.
3. `detectIntegrationModel(repoRoot)` (no override, or `{ mcpReachable: false }`) is unchanged: `gh` absent still resolves `local-merge`, exactly as today — existing tests in `tests/integration-model.test.js` stay green with no edits.
4. `bin/resolve-policy.js --values integration-model --mcp-reachable` (flag present, `gh` faked absent, real GitHub remote) resolves `pr-first`; omitting the flag preserves today's `local-merge` fail-open behavior.
5. `_shared/integration-model.md` and `detectIntegrationModel`'s code comment both cross-reference IL-63 and state plainly that `pre-tool-use.js`'s hook call site cannot use the override (no agent turn to source an MCP result from).
6. `npm test` green, including the new pin tests.

## Technical Approach

The naive fix this record was originally filed as — have `detectIntegrationModel` itself perform an MCP-equivalent reachability check when `gh` is absent — is not buildable as stated: IL-63 (`docs/incident-log.md`) already establishes that a spawned-subprocess-style module cannot invoke MCP tools directly, since those are only callable from the invoking agent's own turn. `pre-tool-use.js`'s call site reinforces this: it runs as a lifecycle hook with no agent turn in progress at all, so there is no MCP call to make there under any design.

The buildable version keeps `detectIntegrationModel` a pure, synchronous function and pushes the actual MCP call to the one call site that already runs inside an agent turn — `bin/resolve-policy.js`'s CLI, invoked via Bash from skill prose. Add an optional second parameter, `detectIntegrationModel(repoRoot, opts)`, where `opts.mcpReachable === true` short-circuits past the `gh repo view` probe straight to `pr-first` (still gated on the existing git-remote-exists check — an MCP reachability signal is meaningless with no remote to integrate through). `resolveIntegrationModel` forwards its own `opts` straight through unchanged. `bin/resolve-policy.js`'s CLI gains a `--mcp-reachable` boolean flag (parsed alongside its existing `--values`/`--run` flags) that sets `opts.mcpReachable` before calling `detectIntegrationModel`; a calling skill that has already run its own `list_issues`/`get_me` bounded MCP probe (mirroring `dispatch/mcp-transport.md`'s Preflight check 3 substitution) passes `--mcp-reachable` only when that probe succeeded.

This deliberately narrows the record's scope from "detectIntegrationModel handles gh-absence everywhere" to "the CLI-invoked call site can be bridged by its caller; the hook call site permanently cannot" — the honest ceiling IL-63 imposes, not a workaround for it.

### Key Files

- `plugin/bin/lib/policy-schema.js` — `detectIntegrationModel` gains the optional `{ mcpReachable }` override; `resolveIntegrationModel` forwards `opts`
- `plugin/bin/resolve-policy.js` — CLI gains `--mcp-reachable` flag, forwarded into `detectIntegrationModel`
- `tests/integration-model.test.js` — new tests pinning both the override behavior (AC2-4) and the unchanged no-override behavior (AC3)

## Gotchas

- IL-63 is load-bearing here, not background reading: it is the reason this record's Deliverables/Acceptance Criteria differ from the literal ask in `## Original request` below. A build that tries to make `detectIntegrationModel` call an MCP tool directly will hit the exact wall IL-63 documents.
- `pre-tool-use.js`'s hook call site is the highest-consequence consumer of `detectIntegrationModel` (it backs the bookkeeping-stamps merge gate) and is also the one call site this fix structurally cannot help — no agent turn is active when a lifecycle hook fires. Don't scope-creep the fix into "solving" that call site; document the gap instead (Deliverables item 4/5).
- Faking `gh` absence for the new tests needs care: `detectIntegrationModel` calls `execFileSync('gh', ...)` directly, with no injectable runner seam (unlike the `gh-api-module-pattern` skill's convention elsewhere in this repo). The existing test file (`tests/integration-model.test.js`) uses real subprocesses throughout, not fakes — the cheapest way to force a `gh`-absent condition without adding a runner seam is a `PATH` override in the test's `execFileSync`/`spawnSync` options (an empty or `gh`-free `PATH`), not mocking `child_process`.
- This repo's own `.claude-tweaks/policy.yml` had no `integration-model:` key before this record — Deliverable 1 (pinning it) is a live, zero-risk config change that closes the originally-observed failure immediately, independent of whether the code-level override (Deliverables 2-3) ships in the same pass.

## Current State

`detectIntegrationModel` (`plugin/bin/lib/policy-schema.js`) shells `gh repo view --json owner,name` directly to confirm forge reachability before defaulting to `pr-first`, with no MCP fallback -- unlike the rest of this plugin's gh-absent support (`_shared/github-write-transport.md`'s CRUD mapping, `dispatch/mcp-transport.md`, and the Detection Ladder's own check-2-no-longer-gates-alone rule). In a live gh-absent sandbox (a cloud Routine container with no gh CLI, GitHub reachable only via the MCP tools) this makes `detectIntegrationModel` always fall back to `local-merge`, even on a GitHub-backed project whose `.claude-tweaks/policy.yml` sets no explicit `integration-model` override and that CLAUDE.md documents as defaulting to `pr-first`. Observed live during `/claude-tweaks:dispatch next` (run 2026-08-24T221615-dispatch-standalone): `bin/hooks.js reconcile --json` resolved `local-merge-model` and skipped mirror/release/archive/remote-prune/console entirely, purely because `gh` was absent, not because the project actually wants local-merge. The same function backs `resolve-policy.js`'s own integration-model default, so every skill that reads it (dispatch's reconcile, /flow's Manifesto, wrap-up's Section C branch, the Auto-merge gate) silently runs the wrong integration model in any gh-absent environment with no policy override set.

## Deliverables

- `detectIntegrationModel` (or its `gh repo view` reachability probe specifically) should route through the same gh-present/MCP-fallback detection the rest of the plugin already uses, per `_shared/github-write-transport.md`'s Detection section -- e.g. an MCP-equivalent reachability check (a bounded `list_issues` or `get_me` call) when `gh` is absent, mirroring dispatch's own Preflight check 3 MCP substitution.
- A regression test pinning the failure mode: with `gh` unavailable (or its invocation faked to fail) and a real `origin` remote pointing at a real repo, `detectIntegrationModel` should still resolve `pr-first` when reachability can be confirmed via the fallback path, not silently default to `local-merge`.
- Document (a code comment or _shared/integration-model.md note) that this detection depends on either `gh` or the fallback being reachable, so a future gh-absence-driven regression here is caught faster than a live dispatch firing discovering it by observed behavior.

## Acceptance Criteria

- In a fixture/test double where `gh` is unavailable but the MCP-equivalent reachability check would succeed, `detectIntegrationModel` resolves `pr-first` for a repo with a real GitHub origin remote.
- Existing gh-present behavior is unchanged (confirmed by existing tests staying green).
- `npm test` green including the new pin test.
