# 1480: subagent-stop.js contract-violation check false-fires against an orchestrating background-job session's own interim narration turns

Origin: reflect full mode from #1228
Defer-reason: tangential

## Current State

`plugin/bin/lib/hooks/subagent-stop.js` checks the last assistant text of a SubagentStop-triggering
event against `STATUS_RE` (`^(DONE|DONE_WITH_CONCERNS|NEEDS_CONTEXT|BLOCKED)\b`) and logs a
`contract-violation` event when it doesn't match. When the session receiving this check is itself
running as a background job (dispatched via the Agent tool by an outer orchestrator — e.g. a
`/claude-tweaks:dispatch` two-call handoff), every one of that session's own turn boundaries while
waiting on its own parallel Task-tool dispatches is independently checked, even though the
subagent-output-contract's status-line requirement applies only to a dispatched subagent's own
*final* reply — never to the orchestrating session's legitimate interim narration turns. During
record #1228's own review+polish+wrap-up dispatch, 8 lens-review agents plus a code-simplifier
agent were dispatched in parallel; the orchestrating session narrated one line per completion
notification per its own "Narrate" convention. `friction-events.js --run <that run>` returned 15
`contract-violation` events for the run — all 15 are verbatim excerpts of the orchestrating
session's own narration text, not any dispatched agent's reply. All 9 real dispatched Task agents
that run correctly emitted a valid status line as their first reply line; zero genuine violations
occurred. The file's own header comment already documents one known false-positive source ("a
dispatch whose own template specifies a different first-line contract") but not this second class.

## Deliverables

- Extend `subagent-stop.js`'s existing "Known false-positive source" header comment to name this
  second class: a background-job session's own interim narration turns, checked independently of
  its dispatched subagents' replies. Documenting the limitation is sufficient given the hook is
  warn-tier/best-effort and never blocks — no behavioral change required.

## Acceptance Criteria

- The false-positive comment block names both known sources.
- A future reader of `events.jsonl`'s `contract-violation` entries for a background-job-orchestrated
  run understands why a high count there does not necessarily indicate genuine subagent contract
  violations.
