# 1931: flow-preflight.js: one fact pack for the second call's adoption, freshness, levers, PR, stamp, and changed-file reads

Surface: backend
**Related:** #1826, #1858

## Overview

On record #1535's dispatched run, the second Task call spent 24 minutes before review's first judgment: run-dir adoption (cases 1–5 of `flow/steps-and-gates.md`), the resume-freshness probe, the staged-inventory check, the Manifesto FYI render from `config.yml`, the auto-inserted suite run, and change analysis — each read its own tool call with a reasoning turn between. The Phase 1 sub-issue removes the suite run when the runner stamp matches; this unit collapses the remaining reads into one call. `bin/flow-preflight.js --run <dir> --steps <list>` returns, in one JSON: the adoption case and its note line, `check-resume-freshness` and `check-staged-inventory` results, `config.yml`'s levers for the FYI table, `work/{n}-spec.md` presence, the PR record and phase-checklist state, the current runner stamp, and the shared changed-file set. `/flow` Step 3 renders the Manifesto FYI from the pack and proceeds; the adoption-case note lines are unchanged in wording.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Changing adoption semantics, the freshness probe's `BLOCKED` rule, or any Manifesto lever computation — the pack reads what the existing CLIs compute.
- The first call's preflight (claim, materialize, PR-early) — those are writes, not reads, and stay where they are.
- Wrap-up's pack (`wrap-up-pack.js`), reflect depth, console auto-resolution — Phases 7a/7c.
- `confirm`/`hybrid` Manifesto approval — the pack feeds the render; the approval stop is unchanged.

## Technical Approach

Same shape as `wrap-up-pack.js`: one process, concurrent reads, per-field envelopes, anchored `--run`. The adoption predicates move from prose into a tested module, with the prose citing the module's literals — the same prose-to-code migration `bin/plan-audit.js` (#903) made for plan-audit Checks A/B/C.

## Gotchas

- Red-team resolution: adoption cases 4 and 5's predicates and note literals are copied verbatim from `steps-and-gates.md`'s existing prose (this unit relocates existing literals into `preflight.js` as constants, it does not invent new case logic) — add fixtures/tests for cases 4 and 5 mirroring cases 1-3's fixture-based test pattern.
- Red-team resolution: split the single Prerequisites row into two — #1921 (Phase 1: `--stamp-status`) and #1922 (Phase 2a/2b: `--changed-files`) — both `blocked-by`.
- Red-team resolution: the BLOCKED-verdict-as-data safety concern is closed by the prose-pin conformance test itself: it must confirm `steps-and-gates.md`'s adoption section actually contains a literal check-and-stop on `freshness.verdict === 'BLOCKED'` immediately after the `flow-preflight.js` call (not merely describes the behavior) — a missing or wrong check fails that conformance test, which is the process backstop; no separate non-zero exit code is added.
- Red-team resolution: `--steps` is metadata-only (echoed in the output's `steps` field for provenance) — `gatherPreflight` always computes every field unconditionally regardless of the `--steps` value, mirroring `wrap-up-pack.js`'s own all-fields-always design.
- Red-team resolution: when `run-state.json` carries no `pr` object at all (fresh run, pre-PR-early, or `local-merge`), `pr.ok` is `true` with `value: null` (a legitimate "no PR yet" state) — distinct from `ok: false`, which means the probe itself failed to run (e.g. `gh` absent while a PR number IS recorded).
- Red-team resolution: the `work/*-spec.md` "committed on the branch" predicate is checked against `$RUN_ROOT`'s view of the branch (the main checkout, per `_shared/pipeline-run-dir.md`), never the cwd worktree — consistent with this record's own anchoring rule for `--run` itself.
- Red-team resolution: valid `levers[].source` values are the same vocabulary `resolve-policy.js --values` already emits (e.g. `default` | `config.yml` | `cli-override` | `project-policy`) — cited rather than invented; a single lever's resolution failure degrades that entry's own value to `null` with an error string, never the whole `levers` field.
- Red-team resolution: `spec.value.record` is parsed from the `work/{n}-spec.md` filename's numeric prefix — the same convention `flow/multi-spec.md` and `materialize.md` already use to name spec files.
- Red-team resolution: never spread a parsed `run-state.json`/`config.yml` object after computing derived fields — e.g. spreading a stale `config.yml`'s raw keys after computing `pack.levers` would let an old, unresolved lever value silently override the freshly-resolved one; always spread parsed file contents first, then apply computed/derived fields on top.

- `flow/SKILL.md` has ~820 bytes of headroom; measure first. `steps-and-gates.md` should shrink (probe commands replaced by field reads).
- The adoption note literals are contract text other tests may pin (`tests/dispatch-worktree-anchoring.test.js`, `tests/flow-claim-preflight.test.js`); move them, do not reword them, and keep a single source.
- `checkResumeFreshness`'s `BLOCKED` must stop the pipeline exactly as today — the pack carries the verdict; the skill still stops. Never let "the pack returned" read as "safe to adopt".
- Anchoring under `$RUN_ROOT` is the main checkout's git common dir, never the cwd worktree (`_shared/pipeline-run-dir.md`, `[IL-127]`).
- `gh` absent → `pr.ok: false` and the skill's MCP/no-forge path; never fabricate checklist state.
- Do not spread parsed `run-state.json`/`config.yml` after derived fields.
- `refs #N` in commits.

## Decision Rationale

See the Phase 1 sub-issue's Decision Rationale for the design-wide rationale. Specific to this unit: the second call's preflight is reads followed by one judgment (adopt or stop), so it is one process; moving the adoption predicates into code is the `plan-audit.js` precedent for prose that had drifted from what agents actually did.
