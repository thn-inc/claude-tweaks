# 1929: Tokens per phase: transcript usage join, procedure bytes loaded, tool round-trips, and guard-denial counts in phase-timing.js

Surface: backend
**Related:** #1785, #1867, #1876, #1894

## Overview

Minutes and tokens do not move together: the wrap-up tail is model latency over tiny tool results, while procedure loading is tokens that cost money and context headroom but little wall-clock. The Phase 6a sub-issue gives every phase its minutes; this unit gives it the second axis. The session transcript (`~/.claude/projects/{slug}/*.jsonl`) records `usage` (`input_tokens`, `output_tokens`, `cache_read_input_tokens`, `cache_creation_input_tokens`) on every assistant message with a timestamp, and its tool-result blocks carry the bytes each `Read` returned. `bin/phase-timing.js --transcript <path>` joins each message's timestamp to the phase table, sums per phase into `timing.json`'s `tokens` block, and derives two more columns — **procedure bytes loaded** (sum of `Read` results under `plugin/skills/**` per phase) and **tool round-trips** per phase. It also counts `gate-denial`, `wd-ambiguous`, and `wd-deny` events per run, so the four filed guard false-positive records (#1785, #1867, #1876, #1894) can be prioritized by measured cost rather than anecdote. A missing or unreadable transcript leaves the columns blank with a one-line note, never fails the summary.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Minutes, `verify` events, `phases[]`, the Timing table's existence — Phase 6a.
- Judging the transcript's content (`_shared/transcript-judge.md`'s consumers) — this reads only `usage`, timestamps, and tool-result sizes.
- Changing how Claude Code writes transcripts or where; the locator reads what exists.
- Per-subagent token attribution beyond the dispatch calls' own agent transcripts (each Task call has its own transcript; nested subagents inside it are summed into that call).

## Technical Approach

Pure derivation over two files (events, transcript) joined on timestamps; the locator is the only environment-dependent part and is isolated behind injectable `fsImpl`/`homeDir`. Everything degrades to blank columns with a note, because the timing table must never fail the summary.

## Gotchas

- Red-team resolution: `--auto-transcript` is for the single-session case (flow/wrap-up's own orchestrator transcript, cwd+session-keyed) only — dispatch's two Task-call transcripts are NOT auto-discovered by `locateTranscripts`; dispatch's own SKILL.md line passes both explicitly via the repeatable `--transcript` flag, since the orchestrator already holds both paths from having dispatched them. When multiple candidates legitimately overlap for a single session (e.g. a resumed session), the CLI picks the most-recently-modified file and emits a note naming the discarded candidates.
- Red-team resolution: `procedureBytes`/`toolRoundTrip` are attributed using the `tool_result` message's OWN timestamp (arrival/completion time), not the paired `tool_use` call's timestamp — results, not requests, are what "happened" from a phase-boundary perspective.
- Red-team resolution: `tests/fixtures/timing/record-1535/` (events.jsonl + manifest.yml) is created by Phase 6a (the timing-telemetry unit) as a shared fixture directory; this unit extends the SAME directory with a synthetic transcript file rather than duplicating it — confirm the directory exists (from Phase 6a) before adding to it.
- Red-team resolution: the slug-derivation rule (`replace every / with -`) is stated as provisional pending fixture confirmation in `transcript.test.js` — that pinned fixture assertion IS the re-verification trigger: if Claude Code's own path-to-slug scheme ever changes, the fixture assertion goes red and signals a re-derivation of `TRANSCRIPT_SLUG_RULE`.
- Red-team resolution: when exactly one of {worktree, sessionId} is present in `run-state.json`, `locateTranscripts` proceeds using whichever key is available (a partial search) rather than requiring both — only when BOTH are absent does it emit the note line and stop.
- Red-team resolution: `procedureBytes`'s path match happens after normalizing the `Read` tool_use's input path to be relative to the run's recorded worktree/cwd, then testing that relative path against `plugin/skills/**` — this is robust to absolute-path differences between a worktree checkout and the main checkout.
- Red-team resolution: a transcript line is "malformed" (skipped, never fatal) when it fails JSON parsing OR when it parses but lacks a `timestamp` or `message.role` field.
- Red-team resolution: `readUsage` returns one row per message (not per `tool_result` block) — `procedureBytes` sums across every `plugin/skills/**` `Read` result within that message; `toolRoundTrip` is true if the message contains at least one `tool_result` block.
- Red-team resolution: a row's token fields (`inputTokens`/`outputTokens`/`cacheRead`/`cacheCreate`) populate only on assistant-typed rows (zero otherwise); `toolRoundTrip`/`procedureBytes` populate only on rows containing `tool_result` content (zero/false otherwise) — the two field groups are mutually exclusive per row by message type, so `joinTokens` sums each independently with no double-counting.

- The design doc claimed `bin/lib/transcript-judge/` "already locates and reads transcripts"; it does not — only the watermark helper exists. Build the locator here and pin the slug rule empirically (memory: `session-transcript-slug-tracks-cwd`; a worktree switch moves the transcript dir).
- Never read transcripts from another user's home or another session's directory into a report — the locator is keyed on the run's own recorded worktree and session id; if both are absent, emit the note line and stop.
- Transcripts can be tens of MB: stream line-by-line (`readline`), never `readFileSync` whole; skip malformed lines.
- `tool_use`/`tool_result` pairing is by `id`; a `Read` result's byte size is the result text length, not the file's size on disk.
- `dispatch/SKILL.md` has ~280 bytes of headroom; the token clause must be net-zero (trim adjacent words) or go into a sub-file the Reporting section cites.
- Tokens are reported, never used to gate anything — no policy lever.
- `refs #N` in commits.

## Decision Rationale

See the Phase 1 sub-issue's Decision Rationale for the design-wide rationale. Specific to this unit: two axes because the wrap-up tail and procedure loading fail on different ones; transcript `usage` because it is the only per-message token record the harness writes; guard-denial counts because each is a wasted turn and the four filed false-positive records deserve a measured priority.
