# 1921: Runner-written verify stamp: verify.js writes the JSON pass stamp, /test and /review read it, the SDD reviewer stops running the suite

Surface: backend
**Related:** #1784

## Overview

The second Task call of a dispatched group re-runs types, lint, and the full suite on a tree the first call already verified, because `/claude-tweaks:test`'s only skip signal (`VERIFICATION_PASSED` + `VERIFICATION_SHA`) lives in the first call's conversation and never crosses the two-call boundary. Inside the first call, superpowers' subagent-driven-development (SDD) whole-branch reviewer runs the full suite once more before build's Common Step 5 runs it as the producer of `VERIFICATION_PASSED`. Measured on plugin 6.114.1 (#1904): three full-suite runs per clean standard group, ~6 min each.

This unit makes the verification runner (`bin/verify.js`) the sole writer of a SHA-bound, scope-labelled JSON pass stamp, and makes `/claude-tweaks:test`'s Skip-if-recent rule and `/claude-tweaks:review` Step 1.5's pipeline branch read that stamp when the conversation signal is absent. It also instructs the SDD whole-branch reviewer not to run the full suite, pins the upstream SDD step that instruction targets, and states the foreground-verification rule once. The guarantee kept: a verdict derives from a runner-written artifact bound to the exact SHA under review; any commit or dirty tree still forces a run. Closes #1784 (the agent-written stamp let a `pass:false` run stamp a pass) as a consequence: agents never write the stamp again.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- Diff-aware scoping of what to run when HEAD moved — that is Phase 2 (the scoping engine sub-issue and its pipeline wiring). In this unit, any mismatch still means a full run.
- Flaky-test retry — Phase 3.
- Skipping the SDD whole-branch review itself — Phase 4. This unit only stops the reviewer from running the suite.
- Changing `verify.js`'s Option A boundary: it still never reads `.claude-tweaks/policy.yml` or CLAUDE.md.
- Threading `VERIFICATION_PASSED` through dispatch's context pack (#1542 forbids carrying a prior call's conclusions).

## Technical Approach

The runner is the only component that knows whether the set it ran was the full resolved set and whether it passed, so it is the only legitimate stamp writer. The stamp is an artifact in the same sense as `report.json` (the design's classification: "the verdict comes from the artifact, not the claim"), which is why the second call may read it under `task-prompt.md`'s re-derive rule. Expand-contract on the file format: JSON is canonical from this release; the bare-SHA twin is written for one minor release so an installed build running older skill text still finds it; removal is recorded in `_shared/policy-deprecations.md`.

### Data / API Surface

`{git-dir}/claude-tweaks-verify-pass.json` (written only by `verify.js`, only on a passing full run in this unit):

```json
{
  "sha": "abc123",
  "dirty": false,
  "scope": "full",
  "fullSha": "abc123",
  "base": null,
  "changedFiles": [],
  "suitesRun": ["tests"],
  "flakyRetried": [],
  "reportPath": "/abs/.git/worktrees/x/claude-tweaks-verify/report.json",
  "at": "2026-09-05T14:07:09Z"
}
```

`scope` enum (reserved for later units, written as `full` only here): `full | scoped | static-only | none`. Anchoring invariant every later consumer relies on: `scope: full ⇒ fullSha === sha`; any other scope ⇒ `fullSha` is the last full pass's SHA and `base === fullSha`.

`verify.js --stamp-status [--git-dir <dir>]` → `{present, sha, head, dirty, scope, fullSha, match, reportPath, legacy}` on stdout, exit 0. `verify.js --no-stamp` suppresses both stamp writes.

## Gotchas

- Red-team resolution: "full resolved set" has no independent canonical check-name list — verify.js trusts that the caller's `--cmd` flags ARE the complete set (Option A: the caller resolves commands, per Phase 2a's Gotchas). A caller invoking a deliberately partial `--cmd` set without `--no-stamp` gets an incorrectly-labeled `scope: "full"` stamp; this is a caller-contract responsibility, not something `verify.js` can independently verify.
- Red-team resolution: `--stamp-status`'s `dirty` field is recomputed fresh from the current working tree (via `gitInfo()`) at read time, never echoed from the stored stamp — a tree that goes dirty after a clean full pass (same SHA, no new commit) reports `match: false`, not a stale `true`. Add a test case for this (clean pass, then a dirty edit with no commit, then `--stamp-status`).
- Red-team resolution: `readStamp`'s fallback order is: JSON present and parses → use it (regardless of the bare file's state); JSON present but unparseable → `null` (no fallback to the bare file); JSON absent → try the bare file; bare file absent or unparseable → `null`.
- Red-team resolution: the legacy bare-SHA file's removal condition is recorded in `_shared/policy-deprecations.md` per this unit's own Deliverables; that file's own sweep (referenced by `/tidy`/`harness-health`) is the acting mechanism — no new tracking needed here.
- Red-team resolution: `suitesRun` names every check whose name is exactly `tests` (or, more generally, every check name that is neither `types` nor `lint`) — this is the same two-name exclusion `run.js`'s fail-fast policy already uses, reused here rather than invented fresh.
- Red-team resolution: the SDD-reviewer-stops-running-the-suite change is an instruction-text change (no code path to unit-test); its verification is the `tools/upstream-drift/manifest.yml` assertion (AC7) plus a build-time whole-branch review confirming the composed dispatch prompt actually omits a full-suite run — accepted as a soft mitigation, consistent with every other SDD-invocation-text change in this codebase.
- Red-team resolution: the stamp write gate is `report.pass === true` AND full resolved set — `dirty` is not a write-gating condition; a passing run on a dirty tree still writes the stamp with `dirty: true` (harmless, since `--stamp-status`'s match rule already requires `dirty === false`).
- Red-team resolution: AC8's 5 pre-existing-failure list is a snapshot from the design session — re-run `npm test` against current `main` before relying on it and reconcile the list if it has drifted; do not trust the record's list as automatically current.
- Red-team resolution: `--stamp-status` outside any git checkout (no `--git-dir`, cwd not in a repo) prints `{present: false}` and exits 0 — the same graceful-degrade posture `verify.js` already takes for `--log-dir`'s mkdtemp fallback.

- `verify.js`'s Option A boundary is load-bearing: the runner may read git and its own files, never `.claude-tweaks/policy.yml` or CLAUDE.md. `--stamp-status` is a read of the runner's own artifact, which stays inside that boundary.
- Never write the stamp when any check carries `skipped: "fail-fast"` or `exitCode !== 0` — the whole point of #1784. The count stamp is different: it is rewritten regardless of outcome by design (#881), so do not "unify" the two writers.
- The stamp lives in the *checkout's* git dir (`git rev-parse --git-dir`, per-worktree under `.git/worktrees/<name>/`), never the common dir — a sibling worktree's pass must not satisfy this one. `gitInfo()` already shells to git from cwd; reuse it.
- Worktree Bash-shape guard: every command in the skill prose must be one plain command — no `;`, `&&`, two `$(...)`. That is the whole reason the runner resolves its own default paths.
- `tests/bin-lib/verify/snippet-conformance.test.js` byte-pins the Step 2 invocation; edit both sides in the same task. Conformance tests pin prose repo-wide, so run the full `npm test` before opening the PR, not just `tests/bin-lib/verify/`.
- `build/SKILL.md` is at 36,959 bytes against the 40 KB per-invocation ceiling (`tests/bin-lib/skill-audit/context-cost.test.js`); measure `wc -c` before and after edits and keep the delta near zero.
- The SDD reviewer instruction lives in the invocation text `build/dispatch.md` composes — the third-party skill file is never edited. Superpowers is pinned at 6.3.0 in `tools/upstream-drift/`; check the exact literal of its whole-branch review step there before writing the assertion.
- Intermediate commits use `refs #N`, never `closes #N`; the PR description carries `Fixes #1784` so the merge closes it.
- Do not spread caller-supplied JSON after derived fields when composing the stamp (`appendEvent`'s comment in `bin/lib/hooks/context.js` states the rule).

## Decision Rationale

- **Runner writes the stamp, not the agent.** An agent-written stamp is a claim; a runner-written one is an artifact bound to the report it summarizes. #1784 showed the agent stamping a failing run.
- **JSON, with a legacy bare-SHA twin for one release.** Consumers need `scope`, `fullSha`, and `reportPath`; the bare SHA cannot carry them. The twin keeps an installed build's older skill prose working (expand-contract, CLAUDE.md's contract-change rule).
- **Skip-if-recent reads the artifact only when the conversation signal is absent.** The first call's `VERIFICATION_PASSED` keeps precedence; the stamp is the second call's path. Threading the flag through the context pack was rejected because #1542 bounds the pack to environment facts, never a prior call's conclusions.
- **Reviewer does not run the suite; build does, once, after the fix wave.** `[IL-120]`'s guarantee (a full pass before verification is declared) moves one step later in the same call and does not weaken; `[IL-108]` says keep slow shared-resource work in the controller.
- **Pin the upstream step.** The drift manifest's motivating failure is an instruction that targets an upstream literal which silently changes. Two units (this one and Phase 4's) instruct that step.
- **Rejected:** downgrading by file extension (markdown is under test in this repo — `[IL-120]`, `[IL-140]`); collapsing the two calls (loses the clean-room review, the last independent judgment on fast-lane records).
