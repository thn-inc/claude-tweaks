# 1186: fetch-sub-issues/resolve-blockers: trailing --repo silently queries the wrong repo; null survives into byParent

Surface: backend
Origin: pre-release delta review (range b517ee68..origin/main), confirmed finding deferred to backlog by the same human decision as #1170-#1177.
Defer-reason: pre-existing-outside-diff

## Current State

`plugin/bin/fetch-sub-issues.js`'s `parseArgs` (~line 44) parses `--repo` as
`else if (a === '--repo') { opts.repo = argv[++i]; }` — a trailing `--repo` with no following
value sets `opts.repo = undefined` with no error, and the run falls through to the
`origin`-remote fallback (`bin/repo-resolve.js`'s `remoteUrl`), silently querying the wrong
repository at exit code 0. `plugin/bin/resolve-blockers.js`'s `parseArgs` (~line 44) parses
`--repo` identically (`else if (a === '--repo') opts.repo = argv[++i];`) and has the same gap.
This violates `gh-api-module-pattern`'s explicit pair-structure validation rule ("Every
malformed-input class must actually reach its malformed code ... validate positivity and
pair-structure explicitly"). Sibling CLIs in the same directory already implement the correct
pattern for a value-taking flag — `plugin/bin/preflight-records.js` (~line 38),
`plugin/bin/link-records.js` (~line 41), and `plugin/bin/file-feedback.js` (~line 46) all use
`const v = next(); if (!v || v.startsWith('--')) return { error: 'missing value for --repo' };`.
Neither `fetch-sub-issues.js` nor `resolve-blockers.js` has a test pinning the trailing-`--repo`
case (`tests/fetch-sub-issues-cli.test.js`, `tests/resolve-blockers-cli.test.js`).

Related, lower-severity finding from the same review: `plugin/bin/lib/issues/native-dependencies.js`'s
`fetchNativeSubIssues` (~line 86) builds each parent's sub-issue list with
`.map((s) => s && s.number).filter((v) => v !== undefined)`. GraphQL connection list elements are
nullable, so a `null` node survives the `map` as `null` and passes the `!== undefined` filter
unchanged — `byParent` can end up with a `null` entry, and downstream consumers (e.g.
`fetch-sub-issues.js`'s own stdout serialization) can then render or forward a `#null` reference.
No test in `tests/bin-lib/issues/native-dependencies.test.js` pins a `null` connection node.

## Deliverables

- [ ] `fetch-sub-issues.js`'s `parseArgs`: `--repo` uses the sibling pair-structure pattern (`const v = next(); if (!v || v.startsWith('--')) return { error: 'missing value for --repo' };`) instead of the bare `argv[++i]` assignment.
- [ ] `resolve-blockers.js`'s `parseArgs`: the identical fix for its own `--repo` branch.
- [ ] `native-dependencies.js`'s `fetchNativeSubIssues`: change the `byParent` filter from `.filter((v) => v !== undefined)` to `.filter((v) => Number.isInteger(v))` so a `null` connection node is dropped, not just `undefined`.
- [ ] Tests for all three: a trailing value-less `--repo` case for each CLI, and a `null`-node case for `fetchNativeSubIssues`.

## Acceptance Criteria

1. `node plugin/bin/fetch-sub-issues.js 12 --repo` (no value following `--repo`, as the last argv token) exits 1, prints a `missing value for --repo` usage message to stderr, and makes no `gh`/network call (assert via the injectable `runner`/`ghAvailable` deps never being invoked).
2. `node plugin/bin/resolve-blockers.js 12 --repo` (same trailing-flag shape) exits 1 with the same usage-message and no-network-call behavior.
3. `--repo` followed by another flag (e.g. `fetch-sub-issues.js 12 --repo --help`) is also rejected as a missing value, not silently treated as `opts.repo = '--help'`.
4. A `fetchNativeSubIssues` call whose GraphQL response includes a `null` connection node for some parent's sub-issues produces a `byParent` entry for that parent with the `null` entry dropped and every genuine sub-issue number retained (order preserved for the non-null entries).
5. `--repo owner/name` (the valid, well-formed case) is unaffected on all three code paths — no regression in the existing happy-path tests for either CLI.

## Technical Approach

Both CLIs' `parseArgs` functions are hand-rolled arg loops (no argument-parsing library — consistent
with every other `plugin/bin/*.js` CLI in this codebase). The fix is a narrow, local change to each
file's existing `--repo` branch, replacing the bare `argv[++i]` read with the same guarded
`next()`-and-validate shape `preflight-records.js`, `link-records.js`, and `file-feedback.js`
already use for their own `--repo` flags — no new abstraction, just matching the established
sibling pattern so all `--repo`-accepting CLIs in `plugin/bin/` validate pair-structure the same
way. `fetch-sub-issues.js`'s loop uses a plain index variable (`for (let i = 0; ...)`), so the
guard reads `argv[i + 1]` before consuming it, matching that file's existing style (compare
`file-feedback.js`'s `next()` helper, which isn't present in `fetch-sub-issues.js`/
`resolve-blockers.js` today — introduce it only if it keeps the diff smaller than inlining the
`argv[i + 1]` check, since both are equally correct). `resolve-blockers.js`'s loop is structured
identically, so the same shape applies verbatim.

`native-dependencies.js`'s fix is a one-line filter predicate change — `Number.isInteger(v)` instead
of `v !== undefined` — which also has the side benefit of rejecting any other non-numeric junk
(e.g. `NaN`) that `s && s.number` could theoretically produce, not just `null`/`undefined`.

### Key Files

- `plugin/bin/fetch-sub-issues.js` — `parseArgs`'s `--repo` branch (~line 44): validate pair-structure before assigning `opts.repo`.
- `plugin/bin/resolve-blockers.js` — `parseArgs`'s `--repo` branch (~line 44): identical fix.
- `plugin/bin/lib/issues/native-dependencies.js` — `fetchNativeSubIssues`'s `byParent` filter (~line 86): `.filter((v) => Number.isInteger(v))`.
- `tests/fetch-sub-issues-cli.test.js` — add the trailing-`--repo` and flag-as-value cases.
- `tests/resolve-blockers-cli.test.js` — add the equivalent cases for this CLI.
- `tests/bin-lib/issues/native-dependencies.test.js` — add a `null`-connection-node case for `fetchNativeSubIssues`.

## Gotchas

- Both CLIs are injectable-runner modules (`run(argv, deps = realDeps)`) per `gh-api-module-pattern` — the new tests assert on the fake `deps.runner`/`deps.ghAvailable` never being called on the rejected-input path, not on real `gh` output; no network access needed for these tests.
- `fetch-sub-issues.js`'s `unknown argument` branch (`else if (a.startsWith('--')) { return { error: ... } }`) currently runs *after* the `--repo` branch in the `else if` chain — the pair-structure fix must stay inside the existing `--repo` branch so a genuinely unknown flag (e.g. `--bogus`) still falls through to that later branch unchanged.
- `resolve-blockers.js` parses its `<n>` positional before entering the flag loop (`argv[0]`) — the `--repo` fix only touches the loop starting at `i = 1`; don't touch the positional-parsing branch.
- The `null`-connection-node fix in `native-dependencies.js` changes filter semantics for *all* callers of `fetchNativeSubIssues`, not just `fetch-sub-issues.js`'s CLI wrapper — confirm no other caller relies on `byParent` retaining a `null`/`undefined` placeholder for a missing node (a grep of `fetchNativeSubIssues(` call sites at build time is the cheap check).
