# 1185: fetch-sub-issues: transient probe failure misreported as exit 4 capability absence

Surface: backend

## Current State

`plugin/bin/fetch-sub-issues.js` (~line 84): a transient failure of the probeSchema introspection call is misreported as capability absence — `runGraphQLProbe` catches ALL failures to `{subIssues: false}`, so the CLI exits 4 ("subIssues field unavailable on this host") instead of 3 (network/API failure), contradicting its own documented exit ladder. Consequence: on a single probe timeout/5xx, the trust-table exit-4 Fallback runs the per-parent REST loop for EVERY parent (N paginated calls on the same possibly-flaky network replacing 1 GraphQL call), and an operator debugging the message hunts for a GHE schema gap that does not exist. The fail-safe-to-false posture was designed for /init's one-time persisted driver choice (`capabilities-probe.js`'s module header), not a per-invocation CLI whose caller treats 3 and 4 differently.

Confirmed against the live code: `runGraphQLProbe` (`plugin/bin/lib/issues/capabilities-probe.js:40-48`) wraps the runner call, `JSON.parse`, and the `extract` callback in one `try` and returns the same `fallback` value on any failure inside it. `probeSchema`'s fallback is `{ subIssues: false, dependencies: false }` (line 63) — indistinguishable, from the caller's side, from a genuinely old GHE schema. `fetch-sub-issues.js:86-89` then branches only on `probeSchema(...).subIssues` being falsy and always returns 4, even when the underlying cause was a thrown error.

## Deliverables

- Distinguish "the probe ran and the field is genuinely absent" from "the probe call itself failed" (runner throw, `JSON.parse` throw) for `fetch-sub-issues.js`'s call path specifically — without changing `probeCapabilities`/`probeIssueTypes`'s existing fail-safe-to-false behavior, which `/init`'s one-time persisted driver choice still wants.
- Map the "probe call failed" case to exit 3 in `fetch-sub-issues.js`, with a network/API-failure stderr message distinct from the existing exit-4 "subIssues field unavailable on this host" message.
- Add fake-runner test coverage for both paths: a throwing runner and a runner returning a clean response with the field absent.

## Acceptance Criteria

- A throwing probe runner causes `fetch-sub-issues.js` to exit 3 with a network-failure message.
- A successful probe call that reports the `subIssues` field genuinely absent still exits 4, unchanged.
- `probeCapabilities`/`probeIssueTypes` (used by `/init`'s capabilities probe) keep failing safe to `false` on any error — their contract and callers are untouched.

## Technical Approach

Give `capabilities-probe.js` a way for a caller to observe "the call/parse layer threw" separately from "extract ran and reported absent," without changing `probeSchema`'s own fail-safe return value for its existing callers (`probeCapabilities` inside `/init`'s capabilities probe). One approach: split `runGraphQLProbe`'s single try block so the runner-call + `JSON.parse` step and the `extract` step are distinguishable to an opt-in caller — e.g. a sibling function (or an options flag) that rethrows the underlying error instead of returning `fallback`, used only by `fetch-sub-issues.js`'s call site; `probeSchema`/`probeCapabilities`'s existing signature and fail-safe behavior stay exactly as they are for every other caller.

In `fetch-sub-issues.js`, wrap the probe call (~line 86) in its own `try`/`catch`: on a caught error, write a network/API-failure stderr message and `return 3`, mirroring the existing `catch` around `fetchNativeSubIssues` (lines 92-102) that already does this for the main GraphQL call. On a clean call reporting `subIssues: false`, keep today's exit-4 message and return value unchanged.

### Key Files

- `plugin/bin/lib/issues/capabilities-probe.js` — split "probe call failed" from "field genuinely absent" for an opt-in strict caller, leaving `probeSchema`/`probeCapabilities`'s existing fail-safe behavior for `/init` untouched.
- `plugin/bin/fetch-sub-issues.js` — catch the new failure signal around the probe call (~line 86) and return exit 3 with a network-failure message instead of falling through to exit 4.
- `tests/bin-lib/issues/capabilities-probe.test.js` — add fake-runner coverage for the new strict path (throw vs. clean-false).
- `tests/fetch-sub-issues-cli.test.js` — add coverage asserting exit 3 on a throwing probe runner and exit 4 (unchanged) on a successful probe reporting the field absent.

## Gotchas

- `probeCapabilities`/`probeIssueTypes`'s existing fail-safe-to-false behavior must stay unchanged — `/init`'s persisted driver choice still wants a low-ceremony best-effort probe; only `fetch-sub-issues.js`'s call path needs the throw/false distinction.
- `runGraphQLProbe`'s single `catch` today covers three different failure modes (runner throw, `JSON.parse` throw, `extract` throw) — an `extract` that itself throws on a malformed-but-parseable response is still a probe failure, not a clean `false`, and the fix must route it the same way as a runner/parse throw, not treat it as "field absent."
