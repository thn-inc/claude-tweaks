# 2433: specify: never emit a /claude-tweaks:feedback-filing deliverable for a component the spec itself places outside the plugin

## Current State

`/claude-tweaks:specify` can materialize a spec whose own `## Current State` / `## Technical
Approach` section correctly identifies the affected component as living outside the plugin (a
third-party dependency, or in this case the Claude Code harness itself) — and still carry a
Deliverable/Acceptance-Criterion directing `/claude-tweaks:feedback` to file an upstream report
against that component. `feedback/SKILL.md`'s own scope line is explicit: "Do not use this skill
to file against any repository other than `thomasholknielsen/claude-tweaks`." — and
`learning-routing.md`'s classifier would route a genuine harness/dependency quirk with no owning
claude-tweaks artifact to D4 (memory) or D2 (project doc), never D5, since D5 requires the learning
to name a `/claude-tweaks:*` skill, a `skills/_shared/*` contract, or a `bin/*.js` behavior. A spec
that both correctly diagnoses "this is not ours" and then asks for a `/claude-tweaks:feedback`
filing anyway is internally contradictory.

Reproduced by #1785 (materialized 2026-09-14): its `## Current State` explicitly corrects the
originally-filed attribution ("The record as filed attributes the guard to
`bin/lib/hooks/pre-tool-use.js`. That attribution is wrong ... this is harness behavior"), yet its
Deliverables still directed: "File one upstream report through `/claude-tweaks:feedback` targeting
the Claude Code harness." That deliverable is structurally unreachable — `/claude-tweaks:feedback`
Step 2 would itself stop ("If it is not D5, stop") before ever reaching Step 3's self-reference
check. The build's own SDD fix-loop noticed the filing couldn't happen but reasoned it via an
inapplicable self-reference collapse (which only fires for a learning that already reached D5)
rather than catching that the learning never qualified as D5 in the first place.

## Deliverables

- Add a check to `/claude-tweaks:specify`'s spec-composition step (wherever a "Suggested change"
  from an `## Original request` becomes a Deliverable naming `/claude-tweaks:feedback`): before
  emitting a feedback-filing Deliverable, run the same classification `learning-routing.md`'s
  classifier and `feedback/SKILL.md` Step 2 would apply — does the record's own Current State /
  affected-component analysis place the subject inside the plugin (a `/claude-tweaks:*` skill,
  `skills/_shared/*` contract, or `bin/*.js` behavior)? If not, never emit the feedback-filing
  Deliverable/AC.
- When the check fails, route the spec's language instead per `learning-routing.md`'s own
  Non-claude-tweaks-upstream paragraph ("Report it to the user, name the owner, and stop") or its
  D4/D2 outcome — whichever this repo's spec-authoring convention should surface as — rather than
  silently omitting the concern.

## Acceptance Criteria

- A spec whose Current State / Technical Approach already identifies the affected component as
  outside the plugin (third-party harness, dependency, or corrected mis-attribution) never carries
  a Deliverable or Acceptance Criterion directing `/claude-tweaks:feedback` to file against that
  component.
- `/claude-tweaks:specify`'s own spec-shape validation (or a `/claude-tweaks:challenge` lens) catches
  this class of solution-baked, unfileable deliverable before the spec reaches `ready`.
- Regression case: re-run `/claude-tweaks:specify` against a record shaped like #1785 (an originally
  mis-attributed harness quirk, corrected in the same spec) and confirm no feedback-filing
  Deliverable is emitted.
