# 5916: Report the three quality guards for pipeline changes

Surface: backend
Risk-flags: none

## Overview

Adds a `guards` section to `tools/pipeline-cost-report.js`. It prints the three quality guards `docs/superpowers/specs/2026-11-18-pipeline-economy-design.md` checks every model, lane or review change against, for the runs before and after a given date. Without it, a phase that makes the pipeline cheaper has no stated way to show it did not make the output worse. See #5914 for the Decision Rationale.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Judging whether a guard moved enough to matter. The section prints figures; a person reads them.
- Lens-review results by tier or by lens, and task-review and plan-review results. #5925 reports those.
- Any change under `plugin/`.

## Current State

- Run facts: each run directory's `timing.json` lists subagents under `dispatches.items[]` with `agentId`, `description`, `role` (`implementer`, `task review`, `re-review`, `whole-branch review`, `plan review`, `lens reviewer`, `unlabelled`), `tier`, `parentAgentId` and `startTs`.
- Reports: a subagent's report is the last assistant `text` block of `{slug}/{session-id}/subagents/agent-{agentId}.jsonl`.
- Whole-branch review reports list issues as top-level items under `#### Critical`, `#### Important` and `#### Minor` headings and carry a `Ready to merge?` verdict; task review reports carry a `**Task quality:**` verdict line. Measured on 2026-11-18 over 103 whole-branch reviews, 5 could not be counted.
- Baseline, 8 to 18 November 2026: 70% of whole-branch reviews report a Critical or Important issue; 49% of tasks implemented on Sonnet pass their task review with no fix round. Guard 3 has no baseline.

## Deliverables

- [ ] Section `guards` in `tools/pipeline-cost-report.js`, taking `--split <YYYY-MM-DD>` and `--runs <n>` (default 20): figures for the last `n` runs before the split date and the first `n` on or after it. `--split` is required. Runs on one date order by full directory name; a column with fewer than `n` runs prints the runs it has and the actual `n`; a directory with no leading date is excluded and counted as unparsed; a run present at the top level and under `archive/` is read from the top level.
- [ ] Guard 1: the share of whole-branch reviews reporting at least one Critical or Important issue, with the mean count of each severity per review. An item is a top-level list line under a heading; a `None` or `N/A` line counts zero; a report with at least one of the three headings is parsed (an absent heading counts zero), and one with none is unparsed. A missing transcript file or an error-text reply is unparsed.
- [ ] Guard 2: the share of implementation tasks with no `re-review` dispatch, overall and per first implementer tier. A task is the set of dispatches sharing a parent agent and task number and holding at least one `implementer` dispatch; its tier is that of the earliest `implementer` dispatch by `startTs`; a dispatch group with no `implementer` dispatch is unparsed.
- [ ] Guard 3: bug records created within 14 days after a pull request merged that list, under `### Key Files`, a file that pull request changed; reported as a count and per merged pull request. A bug record is one labelled `type:bug`. A pull request's changed files come from `gh pr view {n} --json files` and are matched exactly against a Key Files path after stripping backticks, a trailing `:line` and a trailing ` — note`. The pull requests scanned are those merged between the first and the last run date of the column; a bug record matching several of them counts once; the per-pull-request figure is that count over the merged pull requests scanned. A bug record with no `### Key Files` section is unparsed.
- [ ] Every guard prints the number of items it could not parse beside its figure.
- [ ] Tests for each guard over fixture run directories, transcripts and forge responses.

## Acceptance Criteria

1. On a fixture of four whole-branch review reports, two with an item under `#### Important` and two with only `#### Minor` items, guard 1 prints 50%.
2. A whole-branch review report with none of the three headings is counted as unparsed and left out of the share's numerator and denominator.
3. On a fixture run with three tasks, where one task's dispatches include a `re-review`, guard 2 prints 67% overall and attributes each task to the tier of its first `implementer` dispatch.
4. Tasks are keyed by run directory, parent agent and task number, so task 1 of two different runs is counted twice.
5. On a fixture where a bug record created 10 days after a merge lists a changed file and another created 20 days after does not qualify, guard 3 counts one.
6. With `--split 2026-11-19 --runs 2` over a fixture of five dated runs, the before column uses the two latest runs dated earlier than the split and the after column the two earliest dated on or after it.
7. `--json` prints the same figures under a `guards` key.

## Release Note

Added three quality measures to the maintainer cost report so a cheaper pipeline can be checked against the quality of its output.

## Technical Approach

A fourth reader module beside the three #5914 adds, sharing its CLI, its `deps` seam and its run-directory enumeration. Guard 2 needs no report text: it reads `timing.json` alone. Guards 1 and 3 parse text and forge data and therefore report what they could not parse.

### Data / API Surface

- `--json` adds `guards: { split, runs, before: { wholeBranch, firstPass, postMergeBugs }, after: { ... } }`, Shares are fractions from 0 to 1. `wholeBranch`: `{ share, meanCritical, meanImportant, n, unparsed }`; `firstPass`: `{ share, byTier, n, unparsed }`; `postMergeBugs`: `{ count, perPr, mergedPrs, unparsed }`.
- A run's date is the leading `YYYY-MM-DD` of its directory name.

### Key Files

- `tools/pipeline-cost-report.js` — adds the `guards` section and its two flags
- `tools/pipeline-cost-report/guards.js` — new: the three guard readers
- `tests/pipeline-cost-report/guards.test.js` — new

### Package Dependencies

- none beyond Node's built-ins and the `gh` CLI

## Gotchas

- A run directory can exist both at the top level of `.claude-tweaks/pipelines/` and under `archive/`. Keep one copy per run name.
- Fifteen task-review approvals in the measured window still listed Critical or Important items. Guard 1 reads the whole-branch review only, and counts issues, not the verdict word.
- Two whole-branch review replies in the window were `API Error 403` text. Count those as unparsed.
- The task-review tier follows the plan's review-risk flag, so Opus reviews the riskier tasks. Report guard 2 per implementer tier, never per reviewer tier.
- ASSUMPTION — verify at build: the heading words `#### Critical`, `#### Important`, `#### Minor` are what the installed `/superpowers:subagent-driven-development` reviewer prompt asks for — via reading five whole-branch review reports from recent run transcripts before writing the parser. If the observed headings differ, parse the observed ones and record them in the pull request.
- ASSUMPTION — verify at build: the task number is parsed from a dispatch's `description` — via reading one `dispatches.items[].description` in a recent run's `timing.json` before writing the grouping; where no task number can be read, the dispatch group is unparsed.

## Plan Review Clarifications

- Decided by the user at plan review: on "figures for the last `n` runs before the split date and the first `n` on or after it", only pipeline runs are eligible. A run directory counts toward `n` when it holds a `timing.json` or its name carries a `spec-` or `record-` segment; other directories (such as `*-adhoc-standalone`, `*-release-standalone`) are left out of both columns and do not count toward `n`. Reading not taken: every dated directory counts toward `n`.
- Decided by the user at plan review: on "Tasks are keyed by run directory, parent agent and task number", a task is also keyed by the record number its dispatch description carries (`Implement #5830 Task 1`); a dispatch whose description names no record inherits the record of the one `implementer` dispatch with that task number under the same parent. Task 1 of two records dispatched under the same parent in one multi-spec run counts twice. The record body's Acceptance Criterion 4 carries the amended wording. Reading not taken: key exactly as written and let same-numbered tasks merge.
- Decided by the user at plan review: on the role `whole-branch review`, guard 1 reads the dispatches labelled `whole-branch review` plus `unlabelled` dispatches whose description starts with `final review` (case-insensitive), such as `Final review for #5865`; the guards module applies this rule itself, with nothing under `plugin/` changed. Reading not taken: role `whole-branch review` only.
- Decided by the user at plan review: on "`--split` is required", `--section all` with no `--split` skips the guards section — the Markdown prints `Guards: not run — --split <YYYY-MM-DD> not given.` and `--json` prints `guards: { skipped: "--split not given" }`; `--section guards` with no `--split` still exits 2. Reading not taken: `--section all` without `--split` exits 2.
- Settled by plan review after an answered round: on "The run-eligibility rule contradicts its own examples. It names `*-adhoc-standalone` and `*-release-standalone` as excluded, but real standalone runs hold a `timing.json`", the name decides for standalone runs: a run is eligible when its name carries a `spec-` or `record-` segment, or when it holds a `timing.json` and its name does not end in `-standalone`. A `*-standalone` run is left out even when it holds a `timing.json`, which keeps the decision's "only pipeline runs" and its two named examples. Reading not taken: any run holding a `timing.json` is eligible, so standalone runs count toward `n`.
- Settled by plan review after an answered round: on "Multi-spec runs whose dispatch descriptions name no record still merge different records' tasks under one key", in a run with more than one member, a task group whose record is unresolved (`''`) and whose `implementer` dispatches carry differing descriptions is counted as 1 unparsed, not as one task. Reading not taken: merge the record-less same-numbered tasks into one task.
- Settled by plan review after an answered round: on "Some real reports arrive through a `SubagentHandback` tool call, not a final text block", a subagent's report is its last assistant `text` block, or the `input.message` of its last `SubagentHandback` tool call when that call comes after the last `text` block. Reading not taken: read the last `text` block only, so handback reports stay unparsed.
- Settled by plan review after an answered round: on "When the same implementer is dispatched twice for one record, the plan treats it as ambiguous and leaves the review's record blank", a dispatch whose description names no record inherits record R when every same-numbered `implementer` dispatch under that parent that names a record names R. Reading not taken: inherit only when exactly one such `implementer` dispatch exists.
