# 5925: Report review results by role and tier

Surface: backend
Risk-flags: none

## Overview

Adds a `reviews` section to `tools/pipeline-cost-report.js` that reports what each kind of review in the build pipeline returned: task review, plan review and lens review, by model tier and, for lens review, by lens. `docs/superpowers/specs/2026-11-18-pipeline-economy-design.md` rests three later phases on these figures (lenses chosen per run, the plan made with the spec, and whether task reviews stay), and its Phase 1 promises a report that reproduces them. #5914 and #5916 cover spend and the three quality guards only, so without this record the figures exist once, from scratch scripts, and cannot be re-read after a change. See #5914 for the Decision Rationale.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Replaying a review on a different model. That is `tools/review-replay.js` and the design's Phase 14; this section reports what the reviews that ran did return.
- The whole-branch review share and the first-pass rate, which #5916 reports as guards.
- Judging whether a review earns its cost. The section prints figures.
- Any change under `plugin/`, including the per-lens rate as a live input to lens selection (the design's Phase 10 builds that).

## Current State

- Run facts: each run directory's `timing.json` lists subagents under `dispatches.items[]` with `agentId`, `description`, `role` (`task review`, `re-review`, `whole-branch review`, `plan review`, `lens reviewer`, and others) and `tier` (`fast`, `standard`, `capable`, `frontier`).
- Reports: a subagent's report is the last assistant `text` block of `{slug}/{session-id}/subagents/agent-{agentId}.jsonl`.
- Lens identity: `tools/review-replay/archive.js` `readRun` returns `lensAgents`, one `{agentId, lens, side}` per lens reviewer, read from its `timing.json` description with `LENS_RE` (`Lens 3a convention A` is lens `3a`, side `A`; `archive.js:123-125`). A tiebreak judge's description starts `Tiebreak` and is never a lens agent (`archive.js:125`).
- Findings: a run's `review-findings.json` is an array of findings with `id`, `lens`, `path`, `line`, `claim`, `reporterSeverity` and `kind`.
- Verdicts: `readRun` returns `verdicts` (`{id, lens, path, line, verdict}` with `verdict` `confirmed` for a tiebreak confirmation, `refuted` or `cant-tell`) and `pairConfirmed` (locations both reviewers of a pair raised, from `Reproduction: lens … reproduced` lines), both read from the run's `decisions.md` (`archive.js:31-33`, `36-37`); `matchVerdicts` matches verdicts to findings; `tools/review-replay.js baseline` prints them per run.
- Outcomes: each finding location's disposition is a `decisions.md` line: `Step 3 Routing: applied … fix at {path}:{line}` (fixed), `STAGED Step 3 Routing: … finding … at {path}:{line}` (staged for a human), a digest or materiality-floor routing line (deferred), and a refuted-by-tiebreak or declined line (dismissed). A location with lines of more than one class takes the first of fixed, staged for a human, deferred, dismissed.
- Multi-spec runs: each member's review artifacts (`decisions.md`, `timing.json`, `review-findings.json`) sit in `{run}/spec-{N}/`, not in the top-level run directory, and `listRuns` enumerates only top-level and `archive/` directories.
- Measured once on 2026-11-18 over runs dated 2026-11-08 or later, by scripts attached to this record as a comment: task review needs fixes in 39% of 242 Opus reviews and 13.5% of 209 Sonnet reviews; plan review finds gaps in 99% of 103 reviews, 5.2 each; lens review confirmed 799 findings over 96 runs, of which 63% were fixed, 29% dismissed, 5% staged for a human and 3% deferred; 40 of 1,200 lens reports could not be parsed. That measurement read top-level run directories only, so it saw no confirmed finding in a multi-spec run.

## Deliverables

- [ ] Section `reviews` in `tools/pipeline-cost-report.js`, honouring the tool's `--since`, `--until` and `--json`. A run's date is the leading `YYYY-MM-DD` of its directory name; a multi-spec run is read as one run per `spec-{N}` member directory, dated by its parent, and the parent directory itself is not read when it has members.
- [ ] Task review (the `task review` role only; `re-review` dispatches are counted and printed beside the table, not in it), per reviewer tier: reviews, the share approved and the share needing fixes, the count of Critical, Important and Minor items (an item is a top-level list line under its heading) among those needing fixes, and the share of fix requests resting on Minor items only.
- [ ] Plan review: reviews, the share with at least one finding, findings per review, findings by kind (a kind outside the four known is bucketed `other`), and the number of runs whose decision log records a stop to ask a human during plan review.
- [ ] Lens review, per tier and per lens: reviewer agents, the share returning no finding, and findings per agent by severity.
- [ ] Lens review, per run and per lens: confirmed findings, split into those both reviewers of a pair raised and those a tiebreak judge confirmed, plus refuted and can't-tell counts.
- [ ] Lens review outcomes: of the confirmed finding locations, the share fixed, dismissed, staged for a human and deferred, by the routing lines in Current State; a confirmed location with no routing line is printed as `unrouted` and left out of the shares.
- [ ] `--json` carries, per lens, `yield.byLens[lens] = { runs, agents, confirmed, rate, unparsed }` over the `n` most recent runs (`--runs`, default 20, ordered by date then full directory name) in which that lens had at least one reviewer agent and the confirmed figures were readable; `rate` is `confirmed / agents` over those runs, null when `agents` is 0. A run unreadable for the confirmed figures takes no slot in `n` and is counted in `unparsed`. A later phase reads this shape: it changes by adding fields, never by renaming one.
- [ ] Every figure prints the number of reports or runs it could not parse beside it, and those are never counted in a share.
- [ ] Tests for each part over fixture run directories and transcripts, the fixtures trimmed from real excerpts; `reviews.js` opens with a header comment listing each report format it parses and the one the build observed.

## Acceptance Criteria

2. A task-review report with no verdict line is counted as unparsed and appears in neither share.
3. On a fixture of two plan-review reports, one with three finding rows and one stating no findings, the section prints 50% with a finding and 1.5 findings per review.
4. On a fixture run with two reviewers on lens `3a` returning two findings and none, and two on lens `3b` returning none, the per-lens table prints `3a` with a 50% no-finding share and one finding per agent, and `3b` with 100% and zero.
5. On a fixture run whose recorded verdicts confirm one finding raised by both reviewers and one confirmed by a tiebreak judge, and refute a third, the run's confirmed count is two with one in each column and one refuted.
6. With `--runs 2` over a fixture of three dated runs in which lens `3a` ran, the `--json` output's rate for `3a` uses the two latest of them.
7. A run that exists both at the top level of the pipelines directory and under `archive/` is counted once.
8. On a fixture run directory with two `spec-{N}` member directories, each holding its own timing, decisions and findings, the confirmed figures count two runs and none from the parent.
9. A lens report that opens "No findings." and continues in prose with no finding row counts as no-finding; a reviewer whose transcript is missing is unparsed and in neither the share's numerator nor its denominator.
10. On a fixture of three confirmed finding locations, one with an applied-fix routing line, one with a `STAGED` routing line and one with none, the outcomes print fixed 50%, staged 50% and one `unrouted`.

## Technical Approach

A fifth reader module beside those #5914 and #5916 add, sharing the CLI, the injected `deps` and the run-directory enumeration, which owns the rule that a run present at the top level and under `archive/` is read from the top level. Role and tier come from `timing.json`; verdict and issue counts come from each report's text; lens agents, confirmed (tiebreak), pair-confirmed, refuted and can't-tell come from `readRun` in `tools/review-replay/archive.js`, not from a second parser; the routing outcomes are read from the same `decisions.md` text with the line classes in Current State. Each parser is written from the report formats found in real transcripts first, and reports what it could not read.

### Data / API Surface

- `--json` adds `reviews: { taskReview: { byTier }, planReview: { reviews, withFindings, findingsPerReview, byKind, humanStops }, lens: { byTier, byLens, perRun, outcomes, yield: { runs, byLens } } }`, each figure with `n` and `unparsed`.
- Lens identifier: `lensAgents[].lens` from `readRun` (`3a` to `3j`); the pair letter is its `side`.
- As built (Beneficial deviations, Common Step 4.5): `lens.unreadable` counts runs whose timing items the walk read but `readCost` threw on (a null `dispatches.items` entry), so they sit in no lens figure rather than reading as zero agents; `readVerdicts` excludes such a unit as `timing-unreadable`, so it is unparsed in the per-run, outcome and yield figures (humanStops still reads its decisions.md text); `planReview.humanStops.planReviewUnits` counts the run units whose log has a non-SKIP Common Step 1.6 line, and the stop line prints against it; a verdict-line lens name led by a lens id (`3b Security`) or written as its word (`security`, `error-handling`) counts under the id, any other name verbatim.

## Gotchas

- Each lens runs on one fixed profile today (`plugin/skills/review/step3-lens-dispatch.md`: convention 3a and test quality 3f on Fast, security, errors, performance, architecture and ownability on Standard, UX on Capable), so the per-tier lens table is a comparison of lenses, not of models. Say so in the output.
- "Confirmed" is the tiebreak judge's verdict or a pair's agreement, not ground truth; many confirmed info-severity findings are left unfixed.
- The task-review tier follows the plan's review-risk flag, so Opus reviews the riskier tasks. Print the tiers side by side without a difference column.
- Eleven lens reports in the measured window opened with "No findings" and then continued in prose. Count a report as no-finding only when it holds no finding row.
- The 2026-11-18 figures came from top-level run directories only; reading multi-spec members raises the counts, so check the rates, not the counts, against them.
- A member directory with no `decisions.md` review lines is unparsed for the confirmed figures, never zero.
