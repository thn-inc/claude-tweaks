# 1887: backlog refine: bare sweep and refine #N are two disjoint action surfaces for one human-owed list

Surface: infra

## Current State

`backlog/SKILL.md`'s Input routing loads two different procedures for one command: bare `refine` → `refine-mode.md` (fetch, Priority/Related synthesis, grant-check, body-shape re-verification, then Step 4's lanes in the precedence Re-authorize → Grant → Flag-back → Needs-decision → Priority → Dependency repair → Needs you, one batch confirm, Step 5 apply); `refine #N[,#M...]` → `refine-record.md`'s per-record decision resolver (fetch the named records' unresolved `<!-- needs-decision: … -->` comments and `bot:blocked` state, one batch table, one confirm, apply with its own write mechanics, then strip `needs:decision`). `refine-record.md` states the split explicitly: "`refine-mode.md`'s whole-queue sweep never loads this file, and this file never runs that sweep", and gives the reason — `refine-mode.md` sits at the 40,960-byte per-file ceiling (36,761 bytes today; `refine-lanes.md` 28,799; `refine-record.md` 13,298).

The sweep's Needs-decision lane is the *producer* side only: it stamps `needs:decision` on records `grant-check` refused, and `grant-lane-decision.md`'s idempotence check renders one annotation line and writes nothing for a record that already carries an unresolved proposal. So a bare sweep never resolves an existing proposal, and the resolver never grants. `attention-mode.md` encodes the split in its launchers: `needs:decision` rows say `run /claude-tweaks:backlog refine #{n} — proposed: …`, `shaped:headless (no grant)` rows say `run /claude-tweaks:backlog refine to grant via the sweep's Grant lane`, and the file notes the resolver "has no grant path for a `shaped:headless`-only row". Neither form's closing summary names the rows it skipped or the other command.

Observed on plugin 6.114.1 after a sweep: 15 attention rows (8 `needs:decision`, 7 `shaped:headless`) needed two invocations with non-overlapping effects, and the wrong order makes the bare sweep annotate around records the resolver would clear a minute later.

Headless posture (`refine-headless.md`, `--source routine|sweep`) runs the labeling lanes and the grant chain without a click; it never resolves proposals, which is correct — those are human decisions. Tests: `tests/backlog-refine-headless.test.js`, `backlog-refine-closing-render.test.js`, `backlog-refine-body-reverify.test.js`, `backlog-refine-reverify-before-write.test.js`.

## Technical Approach

Fold the resolver into the sweep as a lane, not the sweep into the resolver: the sweep already owns the fetch, the single confirm, `refineAutoApply`, and the closing summary, so the resolver contributes only a population and a write shape. Keep the resolver's text where it is to respect the byte ceiling, and make `refine-mode.md` cite it the way Step 4 already cites `refine-lanes.md`. The headless boundary is the one design constraint to hold: proposals are resolved by humans only, so the lane exists in every render but applies only human-present.

## Original request

**Summary:** `backlog attention` unifies *discovery* of everything a human owes into one ranked list, but *acting* on that list is split across two forms of the same command that cannot substitute for each other — bare `refine` (labeling lanes + grant lane, skips any record carrying `needs:decision`) and `refine #N[,#M...]` (resolves `needs:decision`/`bot:blocked` proposals only, no grant lane) — so a human has to know which label each row carries to pick the right invocation.

**Kind:** Gap

**Affected component:** `/claude-tweaks:backlog` — `refine-mode.md` (bare sweep), `refine-record.md` (per-record resolver), `attention-mode.md` (the list both are meant to drain)

**Use case:** After a `/claude-tweaks:sweep` in a private project, `backlog attention` listed 15 actionable rows: 8 carrying `needs:decision` (each with a "proposed: …" line from the headless grant chain or tidy) and 7 `shaped:headless (no grant)`. Draining that list takes two invocations with non-overlapping effects: `refine #N,#M,...` acts on the 8 proposals but reports nothing to do for the 7 ungranted specs; bare `refine` grant-checks the 7 but only renders an annotation for the 8 and moves on (`grant-lane-decision.md`'s idempotence check). Run in the wrong order, the bare sweep annotates around records the list form would have cleared a minute later. Nothing in either form's output tells the human the other form exists for the rows it skipped, and the attention table's per-row launchers are the only place the split is visible.

Proposed: one `refine` entry point that drains the whole attention list — the per-record decision rows rendered as their own lane (proposal pre-filled, one choice per row, same write mechanics as `refine-record.md` today) alongside the existing Grant/Priority/Related/Flag-back lanes, under the existing single batch-confirm. The `#N[,#M...]` form can stay as a scoped filter over the same unified render rather than a different mode. The two write shapes have different blast radius (applying a stated proposal vs. mass-granting `auto:build`/`auto:merge`), so they should stay visually distinct lanes with distinct `[auto-applied]` stamping under `refineAutoApply`, but not distinct commands. Alternative if the split is deliberate: make each form's report name the rows it skipped and the exact other-form command that handles them.
