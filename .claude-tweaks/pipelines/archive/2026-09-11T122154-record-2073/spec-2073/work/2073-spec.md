## Current State

Two observations from the `2026-09-07T113113-dispatch-standalone` drain, re-read against the claims registry and the release contract at 2026-09-09:

- **#1973 — a genuine gap.** The group's second Task call (`review,polish,wrap-up`) found no `claims/issue-1973.json` blob and no `bot:in-progress` label after the first call had committed real code (`e4ba91700`); it re-claimed and logged a `KEPT-PROMPT` safety finding at 2026-09-08T08:47:49. The blob on `claims-registry` today is a tombstone written later by the reconciler (`merged: reconciled from PR #2061`), so the registry no longer shows what the first call wrote or failed to write. Nothing in `_shared/issue-claims.md`'s Release triggers table releases a claim between a group's two calls, so either the first call's claim write reported success without landing (the git-CAS path in `bin/lib/issues/claims-git-cas.js`, driven by `bin/lib/claim-targets/claim-targets.js`) or something outside the contract released it.
- **#1594 — by contract, not a gap.** Its tombstone reads `pr-opened: spec 1594`, released 2026-09-05T16:43 by `/wrap-up`'s cleanup item 7 — `pr-opened:` is a documented Release trigger — and `bin/lib/release-claim/release.js` strips `bot:in-progress` on every release by default (#1631). The record therefore correctly carries no claim and no `bot:in-progress` while PR #1908 is open. What keeps it off the queue is `record.js`'s `partitionByOpenLinkedPR` (#1224): `dispatch-open-pr-excluded.json` lists any candidate whose open PR will close it, before any selection form reads the pool. The original request's "looks re-selectable" reading missed that exclusion; the `pending-review`-retains-`bot:in-progress` observation on #1919 was a run that had not yet reached cleanup item 7.

So the second suspected mechanism (a wrap-up path wrongly removing the label on `pending-review`) is the designed behavior, and the record reduces to the first: a claim write that can report success without persisting, and the absence of any post-write verification that would make that failure loud.

During a `/claude-tweaks:dispatch --budget all` drain (2026-09-07T113113-dispatch-standalone), the claim/lock protecting a record was found missing after real work had already landed, on at least two separate records:

- **#1973**: the second (review,polish,wrap-up) call found no `claims/issue-1973.json` blob on `claims-registry` and no `bot:in-progress` label, despite the first (build,test) call having already committed real code (`e4ba91700`). Re-claimed and proceeded; logged as a `KEPT-PROMPT` safety finding in that run's `decisions.md` at 2026-09-08T08:47:49.
- **#1594**: a resumed stale run (abandoned since 2026-09-05, real committed work, PR #1908) reported `OUTCOME: pending-review` from its review/wrap-up call, but the issue currently carries no `bot:in-progress` label -- unlike every other `pending-review` record from the same firing (e.g. #1919), which correctly retains it. `auto:build` and `auto:merge` are both still present, so the record currently looks re-selectable by a fresh dispatch queue pull despite having an open, ready PR (#1908) already covering it.

## Why This Matters

`bot:in-progress` (backed by the `claims/issue-{n}.json` blob on `claims-registry`) is the mechanism `_shared/issue-claims.md` and the queue-pull's eligibility filter (`!facets.bot.inProgress`) rely on to prevent two dispatch firings -- or two groups within one firing -- from claiming and building the same record concurrently. If the claim/label can silently fail to persist (or gets released prematurely) while real committed work and an open PR still exist, a later dispatch firing could legitimately re-select the record, mint a fresh worktree, and either duplicate the work or collide with the still-open PR's branch.

## Suspected Mechanism (not yet root-caused)

Two candidate gaps, not mutually exclusive:
1. `claim-targets.js` / the underlying git-CAS write to `claims-registry` can report success without the write actually landing (a possible race or silent failure in the git-trees blob write), so a later read finds nothing.
2. Some path in wrap-up's own label handling (`release-claim.js`'s `--remove-in-progress`, or a Review Console branch) may be removing `bot:in-progress` on a `pending-review` outcome when it should only be removed on `merged`/`abandoned` per `_shared/issue-claims.md`'s Release triggers table.

## Deliverables

- Reproduce with a targeted test: claim a record, verify the blob write actually lands (not just the CLI's exit code), across a few repeated runs to catch any race.
- Audit every code path that can remove `bot:in-progress` (`release-claim.js`, the Review Console's various outcome branches, `settle-and-merge.md`'s Settle procedure) against `_shared/issue-claims.md`'s Release triggers table -- confirm `pending-review` is never one of them.
- If the gap is in the git-CAS write itself, add a post-write verification read (the same git-trees read `_shared/issue-claims.md` already documents) inside `claim-targets.js`, and fail loudly (not silently) if the blob doesn't actually land.

## Acceptance Criteria

- AC1: A record whose build+test call committed real code, followed by a `pending-review` outcome from review/wrap-up, always retains `bot:in-progress` afterward (verified by a regression test, not just manual inspection).
- AC2: `claim-targets.js` cannot report success on a claim write that didn't actually persist -- either it verifies the write landed before returning success, or it surfaces a distinct non-zero exit code when the post-write read doesn't confirm it.
