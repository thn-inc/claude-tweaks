# 2090: tidy: Step 7's stale-claim Release has no CLI executor — release-claim.js refuses non-owner (skipped-not-owner), so a sweep must hand-roll the claim-store tombstone overwrite

Surface: infra

## Current State
`/claude-tweaks:tidy`'s claim scan (`skills/tidy/scan-procedures.md`, Step 4.7) recommends **Release** for two claim shapes — a blob `classifyClaimBlob` classifies `'stale'` (past its TTL), and any claim on a closed issue — and defers execution to Step 6 batch approval. The prose then says "Releasing = the current-blob conditional overwrite with the tombstone content `releasePayload` generates (reason `swept: stale claim` or `swept: issue closed`)", and names no executor. `skills/_shared/issue-claims.md`'s Release triggers table likewise routes "Stale or orphaned claim in hygiene pass" to "`/tidy` Step 4.7 (after batch approval)" with those two reasons, and its Release bullet points at `bin/release-claim.js` as the one-command form.

`bin/release-claim.js` cannot perform a sweep release. `bin/lib/release-claim/release.js`'s `releaseClaim` treats `'live'` and `'stale'` identically as held (`isHeld`) and refuses when the blob's `runId` differs from `--run`'s basename (`skipped-not-owner`, exit 4 via the `EXIT` map). A tidy run's `runId` is the tidy run, never the crashed dispatcher's, so every sweep release is refused by construction. `bin/repair-claim.js` refuses too — it accepts only an `'unreadable'` blob and is documented as "the exact inverse of release-claim.js's exit 5". `bin/lib/reconcile/release-merged.js` releases on merge evidence and skips with `no-run-state` when the run dir is gone (cloud-side runs). The observed outcome (feedback, plugin 6.118.0): seven approved `[claim] … — Release (crashed or abandoned run)` rows with no executor, released by ~40 lines of hand-rolled `node -e` against `claim-store.js`, which skipped `releaseClaim`'s write-conflict re-verification, `--remove-grants`, and the run's `decisions.md` log line.

Two remedies were proposed: a sweep flag on `release-claim.js`, or a dedicated `bin/sweep-release-claim.js`. The flag wins: the read → classify → tombstone PUT → conflict re-verify → comment → label-removal sequence is the same, only the ownership rule differs, and a second CLI would duplicate the safety net `release.js` accumulated (#817, #1468, #1631). One thing the proposal understated: the sweep must also cover a `'live'` claim on a **closed** issue (the scan's first Release row), which the record's "stale, never live" wording would leave without an executor again.

## Technical Approach
The ownership check in `releaseClaim` becomes:

```js
if (isHeld) {
  const holder = JSON.parse(blob.content).runId;
  const sweepOk = sweep && (classified.state === 'stale' || (classified.state === 'live' && sweep.issueClosed === true));
  if (holder !== runId && !sweepOk) { result.outcome = 'skipped-not-owner'; result.holder = holder; return result; }
  if (sweepOk && holder !== runId) result.sweptFrom = holder;
}
```

The conflict re-verification after the PUT already tolerates "held by a successor" and "gone" as already-released, and fails closed on "still held by this run" — under sweep, "still held by the original holder" must also fail closed (the tombstone was not written), so the `holderAfter === runId` branch extends to `holderAfter === result.sweptFrom`.

The issue-state read lives in the CLI, not in `release.js`, so the library stays transport-free (the same split `repair-claim.js` uses); the CLI passes a boolean, and a failed state read aborts before the release (never assume closed).

## Gotchas
- A `'stale'` classification is TTL-based (`isStale`), and a live run can legitimately outlive its TTL; the sweep still runs only after tidy's Step 6 batch approval — the flag makes the approved action executable, it does not make the decision autonomous. Say so in the CLI header comment.
- `bin/repair-claim.js` stays as is: an `'unreadable'` blob remains Manual review in the scan table and is never swept.
- `release-merged.js`'s `no-run-state` skip is a different lane (merge evidence, no approval) and is not changed here.
- `--sweep` and `--remove-grants` compose: a swept `abandoned:`-style release keeps grants by default (the standing retry request, per `_shared/issue-claims.md`'s Grant revocation section); tidy's Release action does not pass `--remove-grants`.
- The `gh`-absent MCP path keeps the manual read-classify-write sequence `_shared/issue-claims.md` already documents; the flag is `gh`-path only, like the rest of the CLI.

## Original request
**Summary:** `/claude-tweaks:tidy` Step 7's "Release stale claim" action has no working CLI path — `bin/release-claim.js` refuses any claim whose blob `runId` differs from `--run`'s (`skipped-not-owner`, exit 4), and a tidy sweep is by definition not the owner, so the documented "current-blob conditional overwrite with `releasePayload`'s tombstone" has to be hand-rolled against `claim-store.js`.

**Kind:** Gap

**Affected component:** `/claude-tweaks:tidy` Step 4.7/7 (`skills/tidy/scan-procedures.md` "Releasing = …", `skills/_shared/issue-claims.md` Release bullet) vs `bin/release-claim.js` / `bin/lib/release-claim/release.js`

**Use case:** Running `/claude-tweaks:tidy` interactively on a private project (plugin 6.118.0) surfaced 7 claims classified `stale` by `classifyClaimBlob` (each past its 72h TTL; their unattended dispatch runs had ended with draft PRs open and no local run dir). Step 6 batch approval accepted the 7 `[claim] … — Release (crashed or abandoned run)` rows. Step 7 then had no executor for them:

1. `node bin/release-claim.js <n> --run <tidy-standalone-run-dir> --reason "swept: stale claim"` returns `{"outcome":"skipped-not-owner","holder":"<original run id>"}` and exit 4 for every one — `release.js`'s ownership rule (`holder !== runId → skipped-not-owner`) is correct for wrap-up's own release but structurally excludes a sweep, whose `runId` is the tidy run.
2. `bin/repair-claim.js` refuses too (exit 4): it only accepts an `'unreadable'` blob, and these are well-formed `'stale'` blobs.
3. `bin/lib/reconcile/release-merged.js` had already skipped them with `no-run-state` (the runs were cloud-side; no local `run-state.json`).

What worked was reimplementing the documented sweep release by hand in a `node -e` script: `claimStore.readClaimBlob({ghApi}, repo, n)` → confirm `classifyClaimBlob(...).state === 'stale'` → `claimStore.writeClaimBlob({ghApi}, repo, n, {content: releasePayload({runId: <tidy run id>, reason: 'swept: stale claim', …}).tombstoneContent, sha, expectedContent, message})` → `gh issue comment` with `commentBody` → `gh issue edit --remove-label bot:in-progress`. That is ~40 lines a tidy run should not have to author, and it bypasses `release-claim.js`'s conflict re-verification, `--remove-grants`, and decisions.md logging.

Proposed: either (a) a `--sweep` (or `--force-release-stale`) flag on `bin/release-claim.js` that permits releasing a blob whose `classifyClaimBlob` state is `stale` (never `live`) when `--run` is a tidy/sweep standalone run, writing the same `releasePayload` tombstone with reason `swept: stale claim`/`swept: issue closed` and logging to that run's decisions.md, or (b) a dedicated `bin/sweep-release-claim.js` that `skills/tidy/actions-github-issues.md` names as the Release action's executor. Either way, `skills/tidy/scan-procedures.md` Step 4.7 ("Releasing = the current-blob conditional overwrite…") should point at the CLI instead of describing the write in prose.
