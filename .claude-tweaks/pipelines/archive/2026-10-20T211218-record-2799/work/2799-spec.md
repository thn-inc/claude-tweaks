# 2799: Trim skill/AGENTS.md descriptions per newer-model guidance

Surface: infra

**Related:** #2679 (a practice to re-audit verification prompts on Claude model bumps — adjacent but distinct: that record is about verification-prompt wording specifically, this one is about skill/description trimming)

## Current State

External guidance (attributed to newer-model best-practice advice) argues that skill descriptions should shrink and that pre-reading doc stacks written for older, weaker models should stop, on the premise that a more capable model needs less hand-holding prose to trigger and use a skill correctly. claude-tweaks currently has ~40+ skills, many with substantial `SKILL.md` files and multi-file lazy-loaded sub-documents (per `docs/skill-authoring.md`'s conventions), whose descriptions and content depth have not been audited against this specific guidance.

## Deliverables

Audit a representative sample of claude-tweaks' skill descriptions and frontmatter against the trimming guidance, and produce findings: which descriptions carry verbosity that no longer earns its keep for a newer model, and which genuinely need their current depth (a skill whose triggering accuracy or correctness depends on detailed disambiguation, not verbosity for its own sake). Apply trims only where the finding is clear-cut; leave ambiguous cases as documented findings for a human decision rather than trimming speculatively.

## Acceptance Criteria

- At least a representative sample of skill descriptions/frontmatter (not necessarily all ~40+) is reviewed against the guidance, with findings stated per-skill (trim / keep-as-is / needs-human-judgment), not a blanket assertion.
- Any trims actually applied preserve triggering accuracy — verified by checking the trimmed description still matches this project's own skill-selection conventions (`docs/skill-authoring.md`'s Frontmatter conventions section) and doesn't remove disambiguating detail that exists for a documented reason (e.g. distinguishing near-identical skill names).
- Findings and any applied changes are summarized in the record's own closing report or a linked doc, not left implicit in a diff alone.

## Release Note

Trimmed skill descriptions that no longer help newer models pick the right skill.

## Technical Approach

Read `docs/skill-authoring.md`'s Frontmatter conventions section first to understand this repo's existing description-writing rules before trimming against external guidance — the two may already agree, or the external guidance may conflict with an already-deliberate convention here, in which case that conflict itself is a finding worth stating rather than silently picking one side. Sample a cross-section of skills (a few long-description ones, a few already-terse ones) rather than attempting all ~40+ in one pass, given the record's own scope is an audit, not a mandated full rewrite.

### Key Files

- `docs/skill-authoring.md` — this repo's existing frontmatter/description conventions, the baseline to compare external guidance against
- A sample of `plugin/skills/*/SKILL.md` frontmatter blocks — the actual audit targets (specific files depend on which sample is chosen)

## Gotchas

- Don't trim indiscriminately — a skill's description length sometimes exists specifically to disambiguate from a near-identical skill name or to state a hard trigger condition precisely; removing that in the name of brevity could regress triggering accuracy, which is a worse outcome than the verbosity the record is trying to fix.
- If this repo's own `docs/skill-authoring.md` conventions already conflict with the external trimming guidance, surface that conflict explicitly as a finding rather than silently reconciling it one way — that's a decision for a human, not this shaping pass or the eventual build.
