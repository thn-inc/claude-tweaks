# 1456: build/worktree-setup.md: pr-early run lifecycle did not push/open a PR at build start

**Related:** #1548

Surface: backend

## Current State

A worktree-strategy, `pr-first`-project pipeline run reached `/review`'s own phase-exit push step with no `pr` field in `run-state.json`, and the branch had never been pushed to `origin`. `_shared/pr-early-run-lifecycle.md`'s "Run start: push, then open (or reuse) the draft PR" procedure — documented to run from `build/worktree-setup.md` Step 6, immediately after `build/SKILL.md` Spec Step 1's materialize commit — apparently did not execute during `/build`.

The repro was a small, fast-lane-ceremony record whose build implemented the fix directly rather than through the full multi-step build procedure (a materialize-then-implement-directly shortcut). Nothing failed loudly and no degrade line was logged to `decisions.md` — the gap was only caught because a later phase (`/review`) happened to check `run-state.json`'s `pr` field and `git ls-remote --heads origin {branch}` directly.

This is notable against existing mitigation: `docs/hooks.md` documents a mechanical **bookkeeping-stamps gate** (`pre-tool-use.js`'s `checkBookkeepingStampsGate`, added for `[IL-131]`) that is supposed to deny a covered Edit/Write/commit/push once a run's materialize commit has landed without both the worktree stamp (`record-worktree`) and, under `pr-first`, the PR stamp (`record-pr`) — with an explicit exemption when `decisions.md` already carries a `PR-early run lifecycle: ... FAILED` degrade line. In this occurrence, neither the PR ever opened nor any degrade line was logged, which means either the gate didn't fire on this record's build path, or the build path never produced the materialize-commit precondition the gate keys off.

Two closed issues cover similar symptoms on the same lifecycle: #1106 "Verify PR-early run lifecycle always fires on a pr-first build run" and #838 "PR-early run lifecycle: pr object missing at wrap-up, no push, no degrade log." Both were closed before this occurrence (plugin version 6.106.0), so if the root cause is the same, this is a regression rather than a fresh instance.

## Deliverables

1. Root-cause why the PR-early lifecycle procedure (`build/worktree-setup.md` Step 6 / `_shared/pr-early-run-lifecycle.md`) did not fire, and why the mechanical bookkeeping-stamps gate (`pre-tool-use.js`'s `checkBookkeepingStampsGate`) neither blocked the gap nor left a trace, on a fast-lane-ceremony record whose build took a materialize-then-implement-directly shortcut.
2. Fix the gap so that every worktree-strategy, `pr-first` build either opens and pushes the draft PR per `_shared/pr-early-run-lifecycle.md`, or explicitly logs a degrade line to `decisions.md` explaining why not — independent of which internal build shortcut a record's ceremony profile takes.
3. Add regression coverage (`tests/bin-lib/hooks/` or the appropriate existing suite) that exercises this specific shortcut path and asserts the PR-early lifecycle either fires or degrades loudly, rather than silently no-opping.

## Acceptance Criteria

- On a worktree-strategy, `pr-first` build following a fast-lane-ceremony record's shortcut path, `run-state.json`'s `pr` field is populated and the branch is pushed to `origin` by the time `/build` finishes — OR `decisions.md` carries an explicit `PR-early run lifecycle: ... FAILED` degrade line explaining why not.
- The bookkeeping-stamps gate (`pre-tool-use.js`'s `checkBookkeepingStampsGate`) denies a covered commit on this shortcut path exactly as it does on the full multi-step build path, unless the documented degrade-line exemption applies.
- A test exercises the fast-lane-ceremony / materialize-then-implement-directly shortcut path and asserts the PR-early lifecycle procedure fires or degrades loudly — it must fail against the pre-fix behavior and pass after the fix.
- The fix does not regress the previously-closed #1106/#838 scenarios or widen the gate's deny surface in a way that risks the never-break-a-session invariant (`docs/hooks.md`'s ambiguity-resolves-to-allow posture).

## Technical Approach

Use `/superpowers:systematic-debugging` to trace where a fast-lane-ceremony record's shortcut build path diverges from `build/SKILL.md` Spec Step 1's documented procedure — that step's own prose already flags this exact failure mode as non-skippable ("Common Step 1's worktree-assignment stamping and this Step 6 draft-PR call both run before any judgment about whether further code changes are needed... A record found already-satisfied still needs its own PR and its own worktree stamp," citing `[IL-131]`), so confirm whether the shortcut path actually reaches that code path at all, or bypasses it structurally.

Once the divergence point is found, check whether `checkBookkeepingStampsGate`'s scoping rules have a hole specific to this shortcut — its ownership check, its "run's pin, not a fresh detection" `integration-model` resolution, its `prExempt` caching, or its `hasNoUpstreamYet` first-push exemption — or whether the gate's own precondition (a materialize commit having landed on the run's branch) never gets satisfied on this path, causing it to no-op via its documented ambiguity-resolves-to-allow posture rather than genuinely being satisfied.

Fix at the source (skill prose in `build/worktree-setup.md`/`build/SKILL.md`, and/or hook logic in `pre-tool-use.js`) and add the regression test named in Deliverables.

## Gotchas

- This may be a regression rather than a fresh gap: #1106 and #838 (both closed) covered similar PR-early-lifecycle failure symptoms, and this occurrence is on plugin version 6.106.0, after both closed — confirm whether their fixes still hold or were reintroduced before assuming new territory.
- The bookkeeping-stamps gate's ambiguity-resolves-to-allow posture (no materialize commit yet, no resolved run, or a target outside a linked worktree all no-op) is deliberate, per the never-break-a-session invariant — any fix must close the actual gap rather than widen the deny surface into a hard block that risks denying a legitimate commit.
- The report doesn't pin down which specific internal build shortcut fired (a `ceremony-profile: fast-lane` skip vs. some other materialize-then-implement-directly path) — `build/SKILL.md` only documents `ceremony-profile: fast-lane` as skipping plan-audit and architecture-alignment, not Spec Step 1's materialize/worktree/PR-open sequence, so confirm the actual mechanism before assuming that skip is what's implicated here.
