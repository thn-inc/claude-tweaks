# 5903: Write a run manifest.json when minting a run directory

Surface: backend
Risk-flags: public-contract
Risk-flags-unconfirmed: true

## Current State

Needed by the factory floor design (dispatch PR #1894, a draft awaiting approval: `docs/superpowers/specs/2026-11-18-factory-floor-design.md`, Phase 3 "The manifest" and "Station visits"). The design makes claude-tweaks write a small per-run file that dispatch copies into each station visit's `manifest`, so a lane comparison on the scoreboard can name the plugin version that produced each run (the driver design's scoreboard asks for "cost, wall clock, attempts, shipped lines, lane and plugin version"). Thomas's call 9 in the design: the manifest is a file claude-tweaks writes, not something dispatch infers from a session's environment. This is the second change outside dispatch; the first is #5902 (station events), which is shaped and uses the same lane vocabulary. Nothing in this record depends on #5902 being built first.

No run manifest exists today: `git grep -n "manifest\.json" -- plugin` matches nothing. The name `manifest.yml` is taken by a different file (the multi-spec parent run's spec list, written by `hooks.js manifest-init`; `plugin/bin/check-artifact-overwrite.js` reads it), and `plugin/bin/lib/flow/manifest.js` exports a `writeManifest` for that file, so the new module must not reuse either name. Checked against the checkout at `main`:

- **Where run directories are minted.** One chokepoint: `resolve()` in `plugin/bin/lib/hooks/run-dir-resolve.js` (reached by `node plugin/bin/hooks.js resolve-run-dir --create`). It has two creating branches, both ending in `ok(dir, true)`: the standalone branch (`{ts}-{name}-standalone`, pre-populated with `staged/` and an empty `decisions.md`) and the spec-slug branch (`{ts}-{slug}`, `fs.mkdirSync(dir)` only, the shape `/flow`, `/claude-tweaks:dispatch` and the driver use). Callers: `plugin/bin/hooks.js` (`runResolveRunDir`), the driver's claim step (`plugin/bin/lib/driver/steps.js`, `specSlug: drive-{n}`, via `plugin/bin/lib/driver/run.js`'s `resolveRunDir` dep) and `plugin/bin/lib/dispatch/queue-pull.js` (`dispatch-standalone`). `plugin/bin/wrap-up-engine.js` also does `mkdirSync(args.runDirPath)`, but for a path its caller already resolved.
- **Plugin version.** `resolvePluginVersion(env)` in `plugin/bin/lib/plugin-version.js` reads `CLAUDE_PLUGIN_ROOT/.claude-plugin/plugin.json` and returns `undefined` on any failure. It reads the running build, never the repository's own `plugin/.claude-plugin/plugin.json`, which is ahead of the installed one (`plugin/bin/harness-health.js` notes why).
- **Resolved policy.** `resolvePolicy({ keys, runDir }, deps)` in `plugin/bin/resolve-policy.js` is the library entry (the CLI is a thin shell over it); its key list is `POLICY_KEYS` in `plugin/bin/lib/policy-schema.js`. Two keys, `integration-model` and `merge-verification`, run forge detection, which can call `gh`, so a hash taken at mint must leave them out or it would put a network call in every mint.
- **Ceremony profile and lane are not known at mint.** `ceremony-profile` (`fast-lane` or `standard`) is a `config.yml`-only lever computed by the Pipeline Config Manifesto (`computeLevers` in `plugin/bin/lib/flow/manifesto-write.js`, written through `setConfigLever` in `plugin/bin/lib/set-config/write.js`), after the mkdir-only mint, and the ceremony escape hatch can downgrade it later through `plugin/bin/set-config.js`. The lane is known at mint only for the driver (`specSlug: drive-{n}`); `plugin/bin/express-lane.js gate` decides `express` and `/flow` is `standard`, both after the mint (a dispatch-minted run the driver adopts with `--run` is minted as `unknown`). Lane vocabulary is #5902's: `standard | express | driver | unknown`.
- **Model profile.** `plugin/bin/lib/model-profiles/profiles.js` reads four policy keys (`model-profiles`, `model-stance`, `model-ceiling`, `frontier-run-cap`); `model-stance` (`economy | default | max-rigor`) and `model-ceiling` (a profile name, unset by default) are the run-level ones.
- **Where a run dir may be written.** Run dirs live under the main checkout's `.claude-tweaks/pipelines/` (`mainCheckoutRoot` in `plugin/bin/lib/hooks/worktree-detect.js`). A worktree session's Edit and Write tools are refused there, so a new run-dir file goes through a bin writer (the sanctioned-write family: `log-decision.js`, `stage-item.js`, `set-config.js`, `write-run-artifact.js`). `.gitignore` already ignores `.claude-tweaks/pipelines/*/*`, so a top-level `manifest.json` is untracked with no new ignore line. `plugin/bin/lib/atomic-write.js` is the tmp-plus-rename primitive the neighbouring writers use.

**Related:** #5902, #5655, #5441, #5650, #4718, #4850, #5387, #5482, #5906

## Deliverables

1. **A manifest module**, `plugin/bin/lib/run-manifest/write.js`, exporting `initRunManifest(runDir, facts, deps)` and `fillRunManifest(runDir, fields, deps)`. `initRunManifest` writes `{run-dir}/manifest.json` atomically (`atomic-write.js`) and never overwrites an existing file. `fillRunManifest` reads the file, sets only fields that are currently `null` (never a field that already has a value, with one exception: `ceremonyProfile`, which the escape hatch may legitimately change, so a `set-config` downgrade overwrites it), and rewrites it atomically. Both never throw and never change a caller's outcome: a failure is dropped with one stderr line, the posture the `decisions.md` touch in `run-dir-resolve.js` already has. A manifest that is missing when `fillRunManifest` runs (a run minted before this shipped, an adopted run) is created by it with the unknown fields `null`.
2. **The file format** (version 1), one JSON object, written with sorted two-space indentation so a diff is readable. Fields are added in later versions and never renamed or retyped; a reader ignores fields it does not know.
   - `v`: `1`.
   - `runId`: the run directory's basename.
   - `createdAt`: ISO-8601 UTC, the time of the first write.
   - `pluginVersion`: string or `null` (`resolvePluginVersion`; `null` when it returns `undefined`).
   - `lane`: `standard | express | driver | unknown`, the same vocabulary and the same `unknown` rule as #5902's station events. Written as `unknown` unless the minting caller says otherwise; never guessed.
   - `ceremonyProfile`: `fast-lane | standard | null`; `null` until the Manifesto or a `set-config` call sets it.
   - `policyHash`: `"sha256:" + hex`, or `null` when the policy could not be read. The hash is over the canonical JSON (keys sorted, no whitespace) of `{key: resolved value}` for every `POLICY_KEYS` entry except `integration-model` and `merge-verification`, with no per-run `config.yml` overlay (none exists at mint). It is a fingerprint for "same policy or not", not a copy of it; the values themselves are not written.
   - `baseCommit`: 40-hex sha or `null`, the tip of the integration branch the run will build from, as resolved by the same code that creates the run's worktree (see Gotchas for what must be confirmed), read at mint.
   - `modelProfile`: `{ "stance": "economy|default|max-rigor", "ceiling": "<profile name>|null" }` from the resolved `model-stance` and `model-ceiling`, or `null`.
3. **Mint hook.** `resolve()` in `run-dir-resolve.js` calls `initRunManifest` at both creating branches, after the directory exists, passing `lane: 'driver'` when the spec slug matches `drive-{n}` and `unknown` otherwise. `resolve-run-dir` still prints only the directory path on stdout and keeps its exit codes. A mint with `--create` that finds an existing run (`created: false`) writes nothing.
4. **Fill hooks.** `plugin/bin/lib/flow/manifesto-write.js` calls `fillRunManifest` with `ceremonyProfile` and `lane` (`standard` for a `/flow` run) after it writes `config.yml`; `plugin/bin/lib/set-config/write.js` does the same when the key written is `ceremony-profile`; `plugin/bin/lib/express/cli.js`'s `gate` verb fills `lane: 'express'` when it returns `eligible: true` and a `--run` was given; the driver's `--run` adoption (`plugin/bin/lib/driver/adopt.js`) fills `lane: 'driver'` on a dispatch-minted run, since the driver mints nothing there. Each is best-effort and independent of the others.
5. **A reference page**, `docs/reference/run-manifest.md`, documenting the fields above, which writer sets each, and the rule that fields are only ever added.
6. **Tests** beside the neighbouring suites: the module (format, atomic write, no overwrite, fill-only-null, the `ceremonyProfile` exception, swallowed failure, never throws on an unreadable run dir), `tests/hooks-run-dir-resolve.test.js` (both creating branches write a manifest; the `--create` stdout and exit codes are unchanged; an existing-run adoption writes none), the Manifesto and `set-config` fills, and the express gate fill.

## Acceptance Criteria

- `hooks.js resolve-run-dir --create --spec-slug foo` creates the run directory and a `manifest.json` in it with `v: 1`, `runId` equal to the directory name, `pluginVersion` equal to the version in `CLAUDE_PLUGIN_ROOT/.claude-plugin/plugin.json`, `lane: "unknown"`, `ceremonyProfile: null`, a `policyHash` starting `sha256:`, a 40-hex `baseCommit` and a `modelProfile`; stdout is still exactly the directory path.
- `--spec-slug drive-5` writes `lane: "driver"`; `--standalone tidy` writes `lane: "unknown"` and still pre-populates `staged/` and `decisions.md`.
- Re-resolving an existing run (steps 1-2 of the resolution order) writes no manifest and leaves an existing one byte-identical.
- After the Manifesto writes `config.yml` for a `/flow` run, `manifest.json` has `ceremonyProfile` equal to the `ceremony-profile` lever and `lane: "standard"`; a later `set-config.js --key ceremony-profile --value standard` run changes `ceremonyProfile` and no other field.
- `express-lane.js gate --issue N --run <dir>` returning `eligible: true` sets `lane: "express"`; a verdict of `eligible: false` leaves `lane` untouched.
- Two policies that resolve to the same values hash equal; changing one non-forge policy value changes `policyHash`; changing only `integration-model` does not.
- With `CLAUDE_PLUGIN_ROOT` unset, `pluginVersion` is `null`; with `.claude-tweaks/policy.yml` unreadable, `policyHash` is `null`; with no git, `baseCommit` is `null`. In each case the mint succeeds and the file is written with the other fields.
- With the run directory read-only, `resolve-run-dir --create` still prints its path or fails exactly as it did before this change, and no other command's result or exit code changes.
- `manifest.json` is not counted as run initialization: a directory holding only `manifest.json` is still rejected by `resolveRunArg`'s initialized-run check (`decisions.md`, `run-state.json` or `config.yml`), and the orphaned-mint sweep still archives it.
- `git grep -n "manifest\.json" -- plugin/skills` matches no instruction for a skill to write it; the writers are code only.
- The full test suite and lint pass.

## Release Note

Write a manifest.json into each new pipeline run directory recording the plugin version, lane, ceremony profile, policy hash, base commit and model profile, for the dispatch factory floor.

## Technical Approach

One small module owns the format and the two writes. The mint chokepoint, `resolve()` in `run-dir-resolve.js`, calls the init write; the three places that learn the missing facts later (the Manifesto, `set-config`, the express gate) call the fill write, each with the one fact it owns. The module reads the plugin version, policy and model keys through the existing library entries (`resolvePluginVersion`, `resolvePolicy`) rather than shelling out, hashes with `crypto`, and reads the base commit with one bounded `git rev-parse` in the main checkout. Lane is passed in by the caller and is never inferred, which keeps it the same contract as #5902's station events.

The mint is deliberately still cheap and still bare: no `gh` call (the two forge-derived policy keys are left out of the hash), one local git read, one file write. `manifest.json` is not an initialization marker; the initialized-run check and the orphaned-mint sweep keep reading only the files they read today.

### Key Files

- `plugin/bin/lib/run-manifest/write.js` — new: `initRunManifest`, `fillRunManifest`, the format and the policy hash

- `plugin/bin/lib/flow/manifesto-write.js` — fill `ceremonyProfile` and `lane` after the `config.yml` write

## Gotchas

- **Field and file names are not settled by the dispatch side yet.** They are this record's reading of the design's Phase 3 ("plugin version, lane and ceremony profile, a hash of the resolved policy, the base commit, and the model profile") and are subject to the design's Phase 0 fixture confirmation, as are the lane and station names shared with #5902. Dispatch copies the object into each visit's `manifest` jsonb and adds `machineId`, `account` and `model` itself; the design leaves the manifest's exact shape to the builder, so this record's format is the contract and the design needs a line pointing at it.
- **A bare mint has no manifest facts beyond the first four.** `ceremonyProfile` is `null` and `lane` is usually `unknown` until a later step fills them. A reader (dispatch) must treat `null` and `unknown` as "not known yet or never known", not as an error, which matches the design's "a visit with no readable manifest says the rest is unknown". A run that never reaches the Manifesto (an interactive run, a standalone tidy) keeps `ceremonyProfile: null` for good.
- ASSUMPTION — verify at build: `baseCommit`. The worktree is created later by `plugin/skills/build/worktree-setup.md` (and `drive.js` for the driver), so the commit it branches from is not fixed at mint. Read how those resolve their base (`_shared/integration-branch.md`) and use the same ref at mint; if they disagree for some route, fill `baseCommit` from the worktree step instead and keep the mint value only when nothing else sets it. Confirm which with one real run of each route.
- ASSUMPTION — verify at build: `resolvePolicy` is cheap and offline for every key except `integration-model` and `merge-verification`. Confirm from the key list in `policy-schema.js` that no other key triggers a probe, and keep the excluded set in one constant next to the hash so a correction is a one-line change.
- ASSUMPTION — verify at build: a top-level `manifest.json` does not disturb `hooks.js`'s `resolveRunArg` initialized check, the orphaned-mint classification in `plugin/bin/lib/reconcile/archive-merged.js` (read its classifier, not only `archiveOrphanedMint`, which moves every entry) or `plugin/bin/sweep-stray-run-dirs.js`, and the tests that pin the mkdir-only mint shape (`tests/hooks-run-dir-resolve.test.js` around "mkdir-only mints a bare run directory", `tests/dispatch-flow-rundir-handoff-fixture.test.js`). The acceptance criterion above holds only if all four agree; the plain-mint test's "no `decisions.md`/staged" assertion stays true.
- A policy hash is a fingerprint of resolved values at mint, so editing `.claude-tweaks/policy.yml` mid-run is not reflected. Hashing at mint is the point (the policy the run started under); say so on the reference page.
- Archival moves the whole run directory, so the manifest travels to `archive/{run-id}/` with the rest. Dispatch reads either location, and must not assume the live path.
- The manifest holds no secrets: values are a version, enum names, a sha and a hash. It is not written to the record, a PR or a staged file.
- The name `manifest.yml` is the multi-spec parent run's spec list and is read by `check-artifact-overwrite.js`. Do not merge the two or reuse `plugin/bin/lib/flow/manifest.js`; the new module lives in `run-manifest/` for that reason.
- #5655 (one run-dir anchoring guard) and #5441 (the run-dir guard accepting a directory it should not) change the guard code near `resolveRunArg`; this record touches the mint in `run-dir-resolve.js`, not the guard, so they should not conflict, but check their state before building and take whichever lands first as the base.
- If one build pass is too big, the natural split is the module and the mint hook first, then the three fill hooks.
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(public-contract): …`.

- Plan review (intent-resolvable): `baseCommit` is resolved with the shared integration-branch resolver, `worktree-reap.js`'s `resolveIntegrationBranch` (Deliverables 2: "as resolved by the same code that creates the run's worktree"), and documents the integration tip at mint, not the worktree's first commit.

## Build deviations (as built)

- Beneficial (applied at build, Common Step 4.5): a fill into a multi-spec `spec-N/` child directory that holds no manifest creates none and returns no change (the repo's rule that a `spec-N` child dir is never written for run-level artifacts; `docs/hooks.md`), so a ceremony downgrade in a multi-spec run does not nest a second manifest whose `runId` is not a run id.
- Beneficial (applied at build, Common Step 4.5): `fillRunManifest` type-checks the four facts it can set (`pluginVersion`, `policyHash`, `baseCommit`, `modelProfile`) and treats `lane: 'unknown'` as unset, so a caller cannot retype a field the format fixes ("Fields are added in later versions and never renamed or retyped") and the mint's `unknown` lane can still be filled by the Manifesto ("sets only fields that are currently `null`", with `unknown` the mint's value for an unset lane).
- Approved at the Review Console (build-deviation-1): `baseCommit` is read once at mint, as the tip of the integration branch (`resolveIntegrationBranch`'s `origin/{name}` ref); nothing fills it later from the worktree step. The reference page states it as the integration tip at mint, not the worktree's first commit, and it is `null` when no remote ref resolves.
