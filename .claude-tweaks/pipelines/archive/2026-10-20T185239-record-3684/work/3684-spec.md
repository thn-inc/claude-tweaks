# 3684: finish-console: decide whether a ledger row it cannot flip should stop it before steps 1-2 land

Surface: backend

**Related:** #3659, #2713, #3289, #3295, #3353, #3507, #3515, #3557, #3577, #3636, #3641, #3665, #3687

## Current State

- `plugin/bin/wrap-up-engine.js`'s `runFinishConsole` (the Review Console's Approve-all bookkeeping call, `wrap-up/review-console.md` step 11) writes in a fixed order: step 1 `verify-expectations.json`, step 2 the `decisions.md` outcome lines, step 3 the ledger flips. Steps 1 and 2 run before the ledger is even located.
- Step 3 can fail for reasons that are fully knowable before anything is written. `resolveLedgerPath` can return `ok: false` (`ambiguous`, `rejected`, `unattributable`, or no ledger), the ledger file can be unreadable, and `flipLedgerRow` throws on a row it cannot parse (for example a raw `|` inside a cell that a writer failed to escape — #3512, `_shared/ledger-format.md` line 37). Every one of these stops the call with steps 1-2 already landed. Step 3 already flips every row in memory and writes the ledger once at the end, so the ledger itself is never half-written; only the cross-artifact ordering is exposed.
- The #2544 comment above `validateFinishConsolePayload` justifies the best-effort ordering by saying a re-run "re-derives the same state rather than duplicating it". That holds for `verify-expectations.json` (read-modify-write), but step 2 is `appendEntry`, so a re-run after a step-3 failure appends the Approve-all header and every outcome line a second time. The operator's documented recovery path therefore leaves a duplicated decision log.
- `resolveLedgerPath` and `flipLedgerRow` (`plugin/bin/lib/wrap-up/ledger-write.js`) are pure with respect to the ledger: they read and return text and write nothing. A dry run of both costs one file read and no new transaction machinery.
- **Decision (this shaping pass, recorded as the shaper's call; the user asked for no questions):** pre-flight. #2544 declined *cross-file transactionality* for three unrelated artifacts; a validation pass is not that. It moves the failures that are predictable from the payload and the ledger file ahead of every write, and leaves only genuine I/O failures (a write that fails mid-call) on the existing best-effort path.

## Deliverables

- [ ] In `runFinishConsole`, when the payload names any ledger updates, resolve the ledger path, read it, and apply every `flipLedgerRow` in memory **before step 1**. On any failure, print the same stderr detail step 3 prints today (the named `ledger[i]` and its error, or the resolution reason) with "nothing written" in place of "steps 1-2 already completed", set exit code 1, and return without writing `verify-expectations.json`, `decisions.md`, or the ledger.
- [ ] Step 3 writes the flipped text the pre-flight already computed (one `writeFileAtomic`), so the rows are not parsed twice. A failure of that write keeps today's "steps 1-2 already completed" message, since only I/O can fail there now.
- [ ] Rewrite the #2544 atomicity comment to state the new contract: payload, ledger resolution and every row flip are validated before any write, and only a write failure can leave earlier steps landed. Drop the claim that a re-run never duplicates `decisions.md` lines.
- [ ] Update `_shared/ledger-format.md` line 37's last sentence, which today says `finish-console --approve-all` "stops at step 3 after steps 1-2 have already landed", to say it refuses before writing anything.
- [ ] In `tests/bin-lib/wrap-up/finish-console-cli.test.js`, rewrite the two cases that pin today's order: "a ledger update but no ledger file anywhere … verify-expectations.json still written (step 1 already completed)" (it asserts `/steps 1-2 already completed/`) and "rejects an unknown ledger item number". Both must now assert exit 1 and that `verify-expectations.json`, `decisions.md` and the ledger are byte-identical to their pre-call state (absent files stay absent). Add a third case for a row carrying an unescaped `|`, asserting the same. Each case goes red when the pre-flight is removed.

## Release Note

Approving a wrap-up Review Console no longer half-applies when a ledger row can't be updated; it stops and names the row before writing anything.

## Technical Approach

Hoist step 3's resolve, read and flip loop into a pre-flight block between `validateFinishConsolePayload` and step 1, keeping its error branches and messages (reworded to "nothing written"). Hold the resulting `{ path, text }` and have step 3 only call `writeFileAtomic`. No change to `ledger-write.js`: `resolveLedgerPath` and `flipLedgerRow` are already side-effect free. The run-state read that picks the worktree (`readRunState(args.runDir)?.worktree || process.cwd()`) moves with the block unchanged.
