# 2462: residue-sweep's documented --own-pr carve-out (#2437) was never wired into bin/residue.js/forge.js/pack.js

Origin: wrap-up of #2413 (review/reflect pass) — discovered while running residue-sweep.md as documented and finding the --own-pr flag it names does not exist

Defer-reason: pre-existing-outside-diff

## Current State

Commit bc1754dac (`Fix bundle: residue own-PR carve-out, root-safe test skips, pending-review PR staleness check (#2437)`, already merged to main) claims: "residue.js/forge.js/pack.js: --own-pr carve-out excludes a pr-first run's own recorded PR from residue findings, reporting it via ownPr instead". `plugin/skills/wrap-up/residue-sweep.md` was updated accordingly and now documents a `--own-pr {run-state pr.number}` flag and an `ownPr` result field consumers should branch on.

The actual code was never wired: `bin/residue.js`'s `parseArgs` recognizes only `--base`, `--scope`, `--integration-branch`, `--json`, `--no-suite` — no `--own-pr`. `bin/lib/residue/probes/forge.js`'s `probeForge` has no `ownPr` concept at all; it only ever tags a PR `scope: 'blast-radius'` (this run's own head branch) or `'observed'` and always includes it in `findings` with `remedy: 'record'`. `bin/lib/wrap-up/pack.js` (the `wrap-up-pack.js` CLI's residue field, which `residue-sweep.md` says to read first) never references `ownPr`/`own-pr` anywhere either. Confirmed by grepping all three files for `own-pr`/`ownPr` — zero matches outside the prose file.

Concretely observed while wrapping up #2413 (a pr-first run): `wrap-up-pack.js`'s `residue.value.results` returned this run's own open PR (#2461) as an ordinary `{kind: 'pr', scope: 'blast-radius', remedy: 'record'}` finding — not the documented `ownPr: {number, headRefName}` side-channel — forcing the wrap-up run to manually recognize and special-case it instead of the tooling doing so automatically.

## Deliverables

Add `--own-pr <number>` to `bin/residue.js`'s `parseArgs`, thread it through to the forge probe.

`bin/lib/residue/probes/forge.js`: when a PR's number matches the passed own-PR number, exclude it from `findings` and report it on a separate `ownPr: {number, headRefName}` field (or `null`) on the probe's return value, per what `residue-sweep.md` already documents.

`bin/lib/wrap-up/pack.js`: pass `--own-pr` (sourced from `run-state.json`'s `pr.number`, omitted on a `local-merge` run) when it shells out to the residue CLI for the `residue` fact-pack field, so `pack.residue.value.ownPr` is populated the same way the manual CLI invocation is documented to behave.

Add or extend a test (`tests/bin-lib/residue/**` and/or `tests/bin-lib/wrap-up/pack.test.js`) asserting the own-PR carve-out actually excludes the PR from `findings` and populates `ownPr` — the gap this record reports is exactly the kind a byte-level prose-vs-behavior conformance check would have caught at merge time.

## Acceptance Criteria

`node bin/residue.js --base <sha> --scope blast-radius --own-pr <n> --json` excludes PR `#<n>` from `findings` and reports it under a top-level `ownPr` field when that PR is open with head == this run's branch.

`wrap-up-pack.js`'s `residue` field's `value.ownPr` is populated the same way for a `pr-first` run with a recorded `run-state.json` `pr.number`, and is `null`/absent for a `local-merge` run.

A new or extended automated test fails on the pre-fix code and passes after the fix (proving the gap this record reports is real, not a misreading of the CLI's current behavior).
