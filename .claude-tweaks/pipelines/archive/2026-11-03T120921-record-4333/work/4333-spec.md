# 4333: Make the test-suite slot in tools/run-tests.js FIFO so a queued run cannot starve

Origin: reflect full from #4134

Defer-reason: tangential

## Current State

`tools/run-tests.js` bounds concurrent full suites with a slot lock (`acquireSlot`, #3969). A waiter polls on a 2 s sleep and takes the first slot it finds free, so the wait is not FIFO: a run that arrives later can win a slot ahead of one already waiting.

Seen during #4134's final verify: a full `verify.js` run queued at 17:34 waited about 1 h 40 m for a slot while runs started as late as 18:07 took the slot ahead of it, then ran 7434 s under load. A queued run can starve behind newer arrivals with no upper bound. Recorded as an observation in the #4134 open-items ledger (row 6).

## Deliverables

- [ ] Make `acquireSlot` grant slots in arrival order (a ticket or arrival-ordered queue in the slot directory), so a waiter is served before any later arrival.

- [ ] Keep the existing guarantees: a dead holder's slot is reclaimed, the subset lane and full-suite lane stay separate, and a nested run holding `CT_TEST_SUITE_SLOT_HELD=1` still skips the wait.

## Acceptance Criteria

- [ ] A test in `tests/run-tests-isolation.test.js` starts N+2 waiters against N slots in a known arrival order and asserts they acquire in that order.

- [ ] The same test fails when `acquireSlot` is reverted to the poll-and-take-first behavior.

- [ ] A stale ticket left by a killed waiter does not block the queue behind it.

## Release Note

Queued test-suite runs now take their slot in the order they arrived, so a run no longer starves behind newer arrivals.

## Plan-review answers (2026-11-03)

Answers to the plan-review questions posted on this record (2026-11-02). Apply them as rules.

1. **A live waiter never loses its place.** A ticket is stale only when its pid is dead, when its pid is the caller's own pid, or when it can't be parsed and is older than `staleUnparseableMs`. These are the same rules `readHolder` applies to slot locks. A ticket's age never makes a live pid's ticket stale. Drop the heartbeat entirely: the per-poll `utimesSync`, `staleTicketMs`, the `staleAfterMs` addition to `readHolder`, and their three tests ("old heartbeat removed", "fresh ticket not removed", "refreshes its heartbeat"). A waiter that finds its own ticket gone (`ENOENT`, now only a manual delete) takes a new tail ticket instead of crashing, and keeps that test. The queued log line names the ticket path, so a human can delete a ticket whose pid was reused or whose waiter is stopped. State that residual risk, the same one slot locks already accept, in the comment above `acquireSlot`.
   Why: a heartbeat can't tell a sleeping laptop from a dead waiter. After a sleep it reorders the queue, which breaks "a waiter is served before any later arrival". Liveness by pid already covers AC3's killed waiter and matches the lock contract.
2. **FIFO is per slot index, not one global head.** Each ticket records its `slots` limit. A waiter may try `slot-<i>` only when no earlier live ticket has `slots > i`. A ticket whose limit can't be read counts as unlimited and blocks every index. With one shared limit this is exactly "the lowest live ticket only". Keep the queued line's "set CT_TEST_SUITE_SLOTS to raise the limit" wording and journey Step 4 as they are. Add one test: an earlier `slots:1` ticket with `slot-1` free; a later `slots=2` arrival takes `slot-1` at once, and a third `slots=1` arrival still waits.
   Why: a later arrival only takes a slot that earlier waiters can't use, so nobody starves and the documented knob stays true. A strict global head would leave usable slots idle while protecting nobody.
3. **Scope.** Nothing has shipped; every deliverable stays. Note one limit in the header comment: a checkout of `run-tests.js` from before this change ignores tickets and can jump the queue until its worktree catches up.
