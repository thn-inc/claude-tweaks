# 5314: Queue pull reuses a prior pull's session files when a later fetch returns empty, and writes the stale groups back

## Current State

The queue pull leaves `dispatch-eligible*.json` from a previous pull in place when a later queue fetch returns empty, and exits 0 on that stale data. #5227's Task 9 D1 fixture shows it compounds: the stale groups are written back under the new freshness signal, so a third pull cache-hits on them.

Blocked by #5230 — fix this in `plugin/bin/lib/dispatch/queue-pull.js` once /claude-tweaks:dispatch runs the queue-pull CLI. Until then the module reproduces the fence on purpose (#5227's parity contract), so a module-only fix would break parity; if the fence (`plugin/skills/dispatch/queue-pull-script.md`) has not been removed by #5231 when this lands, fix both and keep the parity row.

## Deliverables

- [ ] An empty queue fetch clears (or never reads) the previous pull's per-session eligibility and group files.

- [ ] The write-back step never records groups that this pull did not compute.

- [ ] The D1 fixture's expectation in `queue-pull.test.js` flips from "reproduces the stale reuse" to the corrected outcome.

## Acceptance Criteria

1. An empty queue fetch after a non-empty pull yields an empty eligible set and exit 0, with no `dispatch-eligible*.json` content from the earlier pull.

2. A third pull after that does not cache-hit on the earlier pull's groups.

**Decision** (plan review, 2026-11-17): Reading B — a failed open-numbers fetch stops the pull at the group-building check, as a fresh session already does (fence exit 1, CLI exit 4), with no eligibility file from the earlier pull and no cache write-back. It is never read as "no open issues". Acceptance criterion 1 is read as: a well-formed empty (`[]`) queue fetch after a non-empty pull yields an empty eligible set and exit 0, with no `dispatch-eligible*.json` content from the earlier pull. The D1 fixture (a failed open-numbers fetch on the second pull) expects the stop.
