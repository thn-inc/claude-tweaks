# 1223: wrap-up verify verb: verify-expectations.json never populates the issues key, leaving carrier-commit/acceptance-labeling dead-code-skipped on current-branch runs

Origin: record #900's wrap-up verify verb (plugin/bin/lib/wrap-up/engine-verify.js), whole-branch re-review finding #5, 2026-08-21.
Defer-reason: genuinely-larger

## Current State

`review-console.md`'s new "On approval" step 10 (added to close finding C4 of the original whole-branch review) writes `verify-expectations.json` with only `{version, memory, upstream}`. The spec's own schema also defines an `issues` key ("written by... only when no materialized header exists — current-branch runs"), and `engine-verify.js`'s `resolvedIssueNumbers()` already has a real, tested fallback path reading `exp.issues` when no `work/*-spec.md` header is found — but nothing ever populates that key, so the fallback is dead code. A `carrier-commit`/`acceptance-labeling` verify run on a current-branch (non-materialized) record permanently renders "no resolved issue numbers found" and skips, even though the console genuinely knows the resolved issue number(s) at write time.

## Deliverables

- [ ] At the same point `review-console.md`'s new step 10 writes `verify-expectations.json`, detect whether a materialized header exists under `${RUN_DIR}/work/*-spec.md` (record mode) and, when it does not, also populate the `issues` array from this run's own identified record number(s) (Phase 1's record identity — a `#`-prefixed argument, branch/commit reference, or a multi-record current-branch run's resolved set).
- [ ] Leave `issues` absent (or empty) when a materialized header does exist — `resolvedIssueNumbers()`'s header-read path already takes priority and should stay the primary source.

## Acceptance Criteria

1. A current-branch (non-materialized) record's verify run resolves real issue numbers from `verify-expectations.json`'s `issues` key, and `carrier-commit`/`acceptance-labeling` no longer permanently skip for that mode.
2. A materialized (worktree/pr-first) record's verify run is unaffected — its header-derived issue numbers still take priority.
3. `npm test` stays green.
