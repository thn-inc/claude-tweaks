# 1484: record-worktree silently corrupts an unrelated run's run-state.json when --run is omitted and a flag typo is treated as the worktree positional

Surface: infra

## Current State

`bin/hooks.js record-worktree` (bin/hooks.js:150-181) has two compounding gaps discovered live during #923's review+polish+wrap-up dispatch call:

1. **No `--run` validation/requirement.** When `--run` is omitted, `resolveRunArg` falls through to `resolveRunDir`'s "newest non-terminal run" default — which, in a repo with many concurrent pipeline runs (the normal state under this project's own dispatch/flow usage), can resolve to a run directory that has nothing to do with the caller's intent. There is no confirmation, no dry-run, no "which run did you mean" surfaced to the caller.
2. **No flag/usage validation.** `record-worktree --help` (a natural first probe when unsure of a CLI's exact flags) is not recognized as a help request at all — `--help` is silently consumed as `rest[0]`, i.e. the **worktree positional argument**, and the command proceeds to write `{worktree: "<cwd>/--help", status: "active", sessionId: "<current session>"}` into whatever run directory the default resolution above landed on.

Combined, an agent that runs `record-worktree --help` (or any malformed invocation) without an explicit `--run` silently corrupts an unrelated, unowned run's `run-state.json` — overwriting its `worktree` and `sessionId` fields with garbage — with a success message (`claude-tweaks: worktree recorded for {basename}`) that gives no indication anything went wrong. In this incident it clobbered the dispatching session's own standalone bookkeeping run dir (`{ts}-dispatch-standalone`), mid-run, requiring a manual repair (`fs.writeFileSync` to strip the bad fields back out — not git-recoverable, since `run-state.json` is gitignored).

Confirmed still live against the current checkout (`plugin/bin/hooks.js`'s `record-worktree` branch, ~line 243): `resolveRunArg` (line 96) only special-cases the literal `--run` flag — any other `--`-prefixed token in `rest` (e.g. `--help`) still falls straight through to `const worktreeArg = rest[0]` and, when a fallback `runDir` resolves, into the `writeRunState` write path unchanged. `#38`'s earlier fix added `--run <path>` support (explicit-path validation, anchoring under the main checkout, the worktree-local-fallback disclosure) but did not touch this separate flag-as-positional gap.

## Deliverables

- [ ] `record-worktree` (and, for consistency, `record-pr`/`close-run` — same `resolveRunArg` seam) rejects any argv token starting with `--` where a positional path/worktree argument is expected, with a clear usage error, rather than silently accepting it as the value
- [ ] `record-worktree`/`record-pr` require an explicit `--run` (or otherwise refuse to fall back to the "newest non-terminal run" default) — or, if the default must stay for some existing caller, print a loud disclosure line naming which run dir the default resolved to, so a mismatch is at least visible in the tool's own stdout
- [ ] Add `--help`/`-h` handling (or a documented "no such thing as help in this dispatcher" convention consistently applied) so an unrecognized flag can never silently become a positional value

## Acceptance Criteria

1. `record-worktree --help` (no `--run`) exits with a usage error and writes nothing, rather than mutating any run's `run-state.json`
2. `record-worktree <positional-only, no --run>` either refuses (preferred) or prints the resolved run dir's path loudly enough that `node --test`-level fixtures can assert on it
3. A new `tests/bin-lib/hooks/` (or wherever `record-worktree`'s existing suite lives) regression test pins case 1 above
4. `npm test` green — full suite

## Technical Approach

The fix lives in `bin/hooks.js`'s `record-worktree`/`record-pr` branches (bin/hooks.js:150-181, :246-273) and/or the shared `resolveRunArg` helper they both call. Validate `rest[0]` doesn't start with `-` before treating it as a path; consider requiring `--run` outright for both verbs, since every real caller in the skill prose already passes it explicitly (`_shared/pipeline-run-dir.md`'s citing sites) — the fallback exists for convenience but its failure mode is silent cross-run corruption, which is worse than a hard requirement.

### Key Files

- `plugin/bin/hooks.js` — `record-worktree`, `record-pr` command branches
- `plugin/bin/lib/hooks/context.js` — `resolveRunArg`, `writeRunState`
- Existing test suite for `record-worktree`/`record-pr` (grep for it under `tests/`)

## Gotchas

- `run-state.json` is gitignored, so a corruption from this bug is not git-recoverable — manual repair (as done live in #923's dispatch) is the only remedy today. This raises the value of preventing the corruption over merely detecting it after the fact.
- Any fix must not break the legitimate no-`--run` callers already documented elsewhere in the skill prose (if any exist) — audit call sites before tightening validation.
- `resolveRunArg` (plugin/bin/hooks.js:96) is shared by more callers than just `record-worktree`/`record-pr` — `spec-status`, `close-run`, and others also call it (see the additional `resolveRunArg` call sites in `bin/hooks.js`). A fix placed inside `resolveRunArg` itself changes behavior for all of them; a fix placed only in the `record-worktree`/`record-pr` branches leaves the others as-is. Decide and state which, since the Deliverables only name `record-worktree`/`record-pr`/`close-run` explicitly.
