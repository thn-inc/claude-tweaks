# 2502: build: a record whose deliverables are all already on the base branch still opens a bookkeeping-only PR instead of stopping with a close proposal

Surface: infra

## Current State

When `/claude-tweaks:build` (inside a dispatched `/claude-tweaks:flow`) finds every deliverable of a record already present on the base branch, it has no documented "already shipped" exit. Instead it commits a "verified already implemented, no code changes" plan doc, opens a draft PR carrying only bookkeeping files, and the pipeline runs test, review, polish and wrap-up through to `pending-review` instead of stopping and staging a Close proposal for the record.

Observed in this repo, 2026-09-14: record #2028 had already been shipped by PR #2234 (merged 2026-09-12; PR title ends "(#2028, #2032)", commit message says `refs #2028`). The queue pull's shipped-candidate exclusion did not catch it (#2449 tracks that separate miss). The dispatched flow (run `2026-09-14T212627-record-2028`) then:

1. Materialized the spec and found "every deliverable and acceptance criterion in the materialized spec is already present in pack.js/console-resolve.js and already covered by (#2028)-tagged tests."
2. Committed a plan doc saying so, because the build skill has no rule for this case — the run's own grep of `build/*.md` and `flow/*.md` for "already implemented", "no code changes", "nothing to build" found nothing, so the agent improvised a verification-only commit.
3. Opened draft PR #2497 via the pr-early lifecycle: five `chore:` commits, two doc files, zero implementation lines.
4. Ran the full test suite twice, reviewed the "bookkeeping-only" diff as PASS, derived ceremony down to fast-lane, filed two flaky-test issues, and reported `OUTCOME: pending-review`.

Cost: 34 minutes and about $11.50 of headless runtime for a PR that then has to be closed unmerged by a human, on a record that had already been verified as already-shipped twice before (a backlog-refine needs-decision comment and a prior run's wrap-up comment both recommended closing it).

## Deliverables

- Give `/claude-tweaks:build`'s implementation-assessment step a documented "already shipped" exit: when every deliverable and acceptance criterion is satisfied on the base branch with zero implementation diff needed, stop with a distinct outcome (e.g. `OUTCOME: already-shipped`) instead of proceeding to a bookkeeping-only commit.
- On that outcome, stage the same Close proposal the queue-pull shipped-candidate exclusion (#1984/#1892's machinery) already stages for the pre-dispatch case, so the two "already shipped" detection points converge on one proposal shape.
- Avoid opening a PR for this outcome — or, if the pr-early lifecycle has already opened a draft PR by the point the already-shipped exit is detected, close that draft PR rather than leaving it open.
- Release the record's claim on this exit path.
- Ensure the second `review,polish,wrap-up` dispatch call is never made for a run that exits `already-shipped` at the first (`build,test`) call — dispatch's report should surface this as a no-op, not a `pending-review` PR.

## Acceptance Criteria

- A record whose materialized spec's every deliverable and acceptance criterion is already satisfied on the base branch, with zero implementation diff required, exits `build` with `OUTCOME: already-shipped` — no bookkeeping-only commit, no draft PR left open.
- The same run stages a Close proposal for the record (reusing the shipped-candidate exclusion's proposal shape) and releases the record's claim.
- `/claude-tweaks:dispatch`'s two-call sequencing skips the second (`review,polish,wrap-up`) call entirely when the first call reports `already-shipped`, and its own report surfaces the record as a no-op rather than `pending-review`.
- A reproduction fixture built from the #2028/PR#2234 shape (deliverables/AC already satisfied, zero-diff materialization) exercises the new exit path.
- `npm test` passes.

## Technical Approach

Add an "already shipped" check to build's implementation-assessment step, run after materialization confirms the spec against the base branch: if every Deliverables/Acceptance Criteria item is already satisfied with no code diff needed, short-circuit before any commit or PR-open step, emit `OUTCOME: already-shipped`, and hand off to the same Close-proposal staging path #1984/#2449's shipped-candidate machinery already produces (reuse, don't reimplement, the proposal shape). Wire dispatch's sequential-execution logic to read this outcome from the first call and skip minting the second `review,polish,wrap-up` Task call when it fires — the same kind of outcome-gated branching `dispatch/sequential-execution.md` already uses for other early-exit outcomes. If a draft PR was already opened by the pr-early lifecycle before this check runs, close it as part of the same exit (never leave a bookkeeping-only draft PR open for a human to find and close by hand).

### Key Files

- `plugin/skills/build/SKILL.md` — the implementation-assessment step gaining the `already-shipped` exit
- `plugin/skills/dispatch/sequential-execution.md` — the two-call dispatch orchestration that must skip the second call on this outcome
- `plugin/bin/lib/issues/shipped-candidate.js` — the existing Close-proposal shape to reuse, not reimplement
- `plugin/skills/_shared/pr-early-run-lifecycle.md` — the draft-PR-open step this exit may need to close
- `tests/` — a fixture pinning the #2028/PR#2234 shape (zero-diff materialization → `already-shipped`)

## Gotchas

- This is a distinct gap from #2449 (the pre-dispatch shipped-candidate exclusion missing #1892/PR#2287) — that fix prevents dispatch from ever picking an already-shipped record in the first place; this record's fix is the backstop for when a record still reaches `build` despite that. Both should converge on the same Close-proposal shape, but neither replaces the other.
- Don't judge the fix by "the merge would have been safe anyway" — the cost here (34 minutes, ~$11.50, a PR a human has to close by hand) is the defect, independent of whether the underlying content was harmless.
