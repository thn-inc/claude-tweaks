# 1564: file-feedback.js: dedup lookup dies with spawnSync gh ENOBUFS on large repos, aborting every filing

Surface: backend

## Current State

bin/file-feedback.js's fingerprint-dedup lookup lists the target repo's issues with full bodies through a spawnSync call whose output buffer overflows on a large repo (~1,500+ issues), so every filing attempt dies with filing-failure: spawnSync gh ENOBUFS before gh issue create is ever reached.

Repro: target a repo with 1,500+ issues, many with multi-KB bodies; write a well-formed drafts file; run node bin/file-feedback.js --drafts <path> --repo <owner>/<large-repo>. Actual: filing-failure: spawnSync gh ENOBUFS. Observed 2026-08-27 while wrap-up's Review Console filed an approved upstream report against thomasholknielsen/claude-tweaks (landed as #1561 only via a manual gh issue create fallback).

## Deliverables

- Bound the dedup lookup's read so it no longer buffers every issue's full body in one spawnSync call — pagination, a body-stripping filter, or at minimum a raised maxBuffer.
- Verify the fix against a repo-shaped fixture with 1,500+ issues and multi-KB bodies.

## Acceptance Criteria

- node bin/file-feedback.js --drafts <path> --repo <owner>/<large-repo> against a repo with 1,500+ issues, many with multi-KB bodies, files the draft successfully instead of dying with spawnSync gh ENOBUFS.
- A regression test reproduces the ENOBUFS condition (a fixture repo shape at or above the failure threshold) and fails without the fix.
- npm test passes with the new coverage.

## Key Files

- plugin/bin/file-feedback.js / plugin/bin/lib/feedback/file-feedback.js — the dedup lookup's spawnSync gh call and its default maxBuffer
- plugin/skills/_shared/github-write-transport.md — the plain-list-plus-in-process-marker-match dedup rule the fix must keep satisfying

## Gotchas

- The fix must preserve the marker-match dedup semantics _shared/github-write-transport.md documents.
- The repo most likely to trip this is the plugin's own — prioritize a fixture large enough to actually reproduce the threshold.

## Investigation Findings

Confirmed root cause by direct read of plugin/bin/lib/feedback/file-feedback.js:

- `findDuplicate` (line ~161) runs `runner(['issue', 'list', '--repo', repo, '--state', 'all', '--json', 'number,title,body,createdAt', '--limit', '10000'])` — full bodies, unbounded, per `_shared/github-write-transport.md`'s plain-list-plus-in-process-marker-match dedup rule (deliberately not `--search`, per #1016/#1079/#1089).
- `defaultRunner` (line ~25) called `execFileSync('gh', args, { encoding: 'utf8', stdio: ['ignore', 'pipe', 'pipe'] })` with no `maxBuffer` override — Node's default is 1MB, easily exceeded by 1,500+ full issue bodies (multi-KB each).

Fix chosen: raise `maxBuffer` (the Technical Approach's "at minimum" option), since narrowing the list's fields would break `findByMarker`'s in-process body-substring/regex match — the marker text lives inside the body field itself, so the body must still cross the pipe in full for every issue; a `--jq` prefilter would need the same marker-matching logic gh-side (out of scope, and `_shared/github-write-transport.md`'s existing plain-list-plus-in-process-match rule is deliberately simple to keep). Added `GH_MAX_BUFFER = 64 * 1024 * 1024` (64MB — a ~1,500-issue full-body list is a few MB at most; 64MB is a comfortable multiple), applied to every `defaultRunner` call (create/view/list) since a larger ceiling costs nothing when actual output is small, and exported the constant for the regression test to consume directly.

**Regression test added** (`tests/bin-lib/feedback/file-feedback.test.js`):
- `"#1564: a 1,500-issue full-body list reproduces ENOBUFS at Node's default maxBuffer"` — spawns a real child process producing a ~4.5MB JSON payload (1,500 issues x 3KB bodies) through `execFileSync` with no `maxBuffer` override, asserting it throws.
- `"#1564: GH_MAX_BUFFER comfortably covers the same 1,500-issue full-body list"` — pins `GH_MAX_BUFFER`'s type/adequacy first (`typeof === 'number'` and `> 5MB`), since `execFileSync` treats an explicit `maxBuffer: undefined` as "no limit" rather than "use the 1MB default" — without that guard the functional assertion below it would pass even if the export were removed, silently defeating the test. Verified this exact discrimination gap by reverting the code fix (git stash) and confirming the test failed red (`typeof feedback.GH_MAX_BUFFER` was `'undefined'`) before restoring the fix and re-confirming green.

`tests/bin-lib/feedback/file-feedback.test.js` runs 39/39 green with the fix in place.
