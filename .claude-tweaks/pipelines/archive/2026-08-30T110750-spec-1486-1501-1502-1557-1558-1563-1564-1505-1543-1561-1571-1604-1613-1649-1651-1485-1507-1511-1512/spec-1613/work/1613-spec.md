# archiveMerged's skip vocabulary has no escalation path for structurally-stuck (non-move-failed) run dirs

## Current State

`archiveMerged()`'s only escalation path is `trackArchiveResult`, which records a failure streak (and eventually files an issue) only when `move-failed` recurs. Every other skip reason (`no-worktree`, `no-branch`, `no-pr`, `console-unresolved`, `console-never-rendered`, `local-behind-merge`, `merge-commit-unknown`) is dropped every pass with zero automated visibility. #1290's review pass identified a concrete reachable shape (an archive-twin dir routed permanently into `no-worktree`/`no-branch`) that is now permanently un-escalatable, plus a related persistent-stat-failure case in `isOrphanedMint`'s `definitelyAbsent()`.

## Deliverables

1. Distinguish an ordinary transient skip (run still genuinely in flight) from a state that looks structurally stuck, for the three reasons that can never self-resolve without external intervention once the underlying resource is gone: `no-worktree`, `no-branch`, `no-pr`.
2. Track a persistent skip toward the existing residue-escalation machinery (`trackResidue`/`recordResidueFailure`/`escalateResidue`), reusing the established `RESIDUE_ESCALATE_THRESHOLD` pattern rather than inventing a parallel one.
3. Never escalate an ordinary in-flight run dir, regardless of pass count.

## Acceptance Criteria

- A run dir that has genuinely been stuck at `no-worktree`/`no-branch`/`no-pr` for longer than a defined TTL accumulates toward escalation and eventually files an issue via the existing `escalateResidue` path.
- A run dir freshly created (or freshly transitioned into one of these reasons) is never escalated, no matter how many reconcile passes observe it before the TTL elapses.
- `archiveMerged`'s skip-in-place behavior for these reasons is otherwise unchanged (AC3 from #1290's original archive-twin test still holds — never auto-resume, never collide into a twin).

## Investigation Findings

**#1290's archive-twin trigger is not yet built.** `gh issue view 1290` (checked during this record's investigation) shows the archive-twin `isOrphanedMint` corroboration described in this record's Current State as the motivating concrete scenario — but the literal reproduction path (mint an archive-twin dir, observe it silently un-escalated forever) requires #1290's own archive-twin machinery, which is present in `isOrphanedMint`/`definitelyAbsent()` already (confirmed in the current `archive-merged.js`), so the scenario is real and reachable today, not blocked on unbuilt code. Scoping decision: rather than writing a fix narrowly targeted at the archive-twin case specifically, implemented a **generalized** staleness-based escalation mechanism keyed on the skip *reason* (`no-worktree` / `no-branch` / `no-pr`) rather than on how the dir arrived at that reason — this transparently covers the archive-twin shape (which resolves to `no-worktree` or `no-branch`) without needing to special-case it, and also covers the plain "worktree torn down, run dir never cleaned up" case, which is the overwhelmingly more common way a dir reaches these reasons.

**Implementation** (`plugin/bin/lib/reconcile/archive-merged.js`):
- Added `STRUCTURALLY_STUCK_TTL_MS = 7 * 24 * 60 * 60 * 1000` (7 days) and `STRUCTURALLY_STUCK_REASONS = new Set(['no-worktree', 'no-branch', 'no-pr'])`.
- Added `isStructurallyStuck(dir, reason, now)`: true only when `reason` is in the stuck set AND the dir's mtime is older than the TTL.
- Added `trackStuckSkip(root, repoSlug, dir, reason, { escalate })`: no-ops unless `isStructurallyStuck` is true, then delegates to the existing `trackResidue(..., 'structurally-stuck', dir, { failed: true, ... }, { escalate })` — reusing the pre-existing consecutive-failure-count + escalate-once machinery (`RESIDUE_ESCALATE_THRESHOLD`) rather than a parallel counter.
- Extended `trackArchiveResult`'s success branch to also call `recordResidueSuccess(root, 'structurally-stuck', dir)` alongside its existing `move-failed` reset, so a dir that eventually resolves (archived successfully) clears any accumulated stuck-count.
- Wired `trackStuckSkip` at the three skip sites that can produce a `STRUCTURALLY_STUCK_REASONS` value: the `no-worktree` skip, the `no-branch` skip, and the generic `decision.action === 'skip'` branch from `decideArchive` (which can itself surface `no-pr` among other reasons — `trackStuckSkip`'s own reason-set gate is what keeps non-qualifying reasons like `console-unresolved` or `local-behind-merge` inert here).
- 7-day TTL chosen to comfortably exceed any legitimate in-flight run duration (multi-day human review, `hybrid`/hold states) while still catching genuinely abandoned dirs well before they'd otherwise sit invisible indefinitely; mirrors the existing `ORPHAN_MINT_TTL_MS` (24h) and `ADHOC_SUPERSEDED_TTL_MS` (30 days) as a third TTL in the same file's family, sized to its own risk profile (a dir with recoverable *state* — unlike an orphaned mint with no state at all — deserves more benefit of the doubt before escalating).

**Bug caught while writing the integration test**: the first version of the new integration test's `stuckDir`/`freshDir` fixtures had no `config.yml`, which caused `isOrphanedMint`'s own pre-existing 24h mtime sweep (line 736, evaluated *before* the no-worktree/no-branch skip this test means to exercise) to archive `stuckDir` first — the assertion `result.skipped.some(...reason === 'no-worktree')` failed because the dir was never reaching the skip path at all. Fixed by adding `config.yml` to both fixtures (marking them "adopted," i.e. a Manifesto ran), matching this record's own framing that the scenario is about adopted-but-stuck dirs, not orphaned mints.

**Second bug caught after the config.yml fix**: the test still failed the same assertion, for a different reason — the fixture set `state.worktree` to a truthy (but nonexistent) path. `archiveMerged`'s actual `no-worktree` check (`if (!state || !state.worktree)`) only fires when the field is missing/empty; since our fixture's `state.worktree` was a truthy string, that check was skipped, and the code fell through to `worktrees.find(w => path.resolve(w.path) === path.resolve(state.worktree))` — which fails to match (the worktree was never actually created via `git worktree add`), producing reason `'no-branch'`, not `'no-worktree'`. Corrected the test's expected reason to `'no-branch'`, which is the realistic reason a torn-down-worktree run dir actually reaches in current code — not a defect in the implementation, a wrong assumption in the first draft of the test.
