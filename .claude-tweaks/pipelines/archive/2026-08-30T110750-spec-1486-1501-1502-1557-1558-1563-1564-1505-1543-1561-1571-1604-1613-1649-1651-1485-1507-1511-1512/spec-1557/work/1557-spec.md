# 1557: dispatch next's top pick is a 68-record mega-bundle chained via shared core-infra key files — no group-size ceiling before headless build

Surface: backend

Related: #1654

Origin: /claude-tweaks:dispatch next, scheduled Routine firing, run 2026-08-27T141617-dispatch-standalone

## Current State

Running this project's `dispatch next` Routine firing, Step 2's file-overlap queue pull (`groupByFileOverlap` in `bin/lib/issues/grouping.js`) produced 8 groups from 76 `auto:build`-eligible open records. One of those 8 groups — the one ranked first by Step 3's `next` ordering (highest-priority-then-oldest representative: #1012, `priority:high`, created 2026-08-20) — contains **68 of the 76 eligible records**, spanning issues filed between 2026-08-14 and 2026-08-25 across completely unrelated concerns (specify decomposition, dispatch queue-pull, hooks dispatch, reconcile, tidy, materialize.js, auto-decision-log, etc.).

The 68-member cluster is not driven by one dominant hub file — `groupByFileOverlap`'s union-find merges any two records that name the same exact `### Key Files` path, and this repo's plugin architecture means many otherwise-unrelated bug/task records legitimately cite the same small set of core infrastructure files (`plugin/bin/lib/hooks/pre-tool-use.js` appears in 8 of the 68 members' Key Files, `tests/` in 8, `plugin/bin/hooks.js` in 7, `plugin/bin/lib/hooks/context.js` in 6, `plugin/bin/residue.js` and `docs/donts.md` in 5 each, several `SKILL.md`/`_shared/*.md` files in 4 each). Each shared reference is individually correct — but transitively, this chains 68 independent records into one "file-overlap group," which `dispatch`'s own contract (`skills/dispatch/SKILL.md` Anti-Patterns: "Claiming a single member of a file-overlap group without its partners") requires be claimed and built together, in one `/flow` invocation, by a single Task-tool subagent, with no group-size ceiling anywhere in the current design.

This firing declined to dispatch this group automatically rather than claim and attempt to build 68 unrelated records as one unreviewable unit of headless work, and filed this record instead. No records were claimed, no branches created, no labels changed by this firing.

## Deliverables

Decide and implement a bound on file-overlap group size before a group is eligible for automatic (`next`-form) dispatch — candidate directions (not prescriptive):

- (a) A `dispatch-max-group-size` policy key that routes an oversized group to a human decision (e.g. render it in `bare` mode's batch table instead of auto-selecting it, or skip it and log/notify) rather than ever entering `next`'s auto-select path.
- (b) A "hub file" allowance list or frequency threshold in `groupByFileOverlap` that stops treating a small set of near-universally-cited core files (hooks.js, pre-tool-use.js, tests/, etc.) as grouping keys, since two records that only share a common infra file rarely need to land in the same branch/PR.
- (c) Some combination of (a) and (b).

Whichever direction is chosen, update `skills/dispatch/queue-pull-script.md` / `bin/lib/issues/grouping.js` accordingly, and document the new behavior in `skills/dispatch/SKILL.md`'s Configuration table. Add a regression test reproducing this shape: N records each citing one small shared file each, chained transitively via 2-3 "hub" files shared by several records apiece, that currently collapse into one group — the fix should keep them separate (or otherwise route them away from unattended `next` dispatch).

## Acceptance Criteria

- A `dispatch next` Routine firing against a queue containing this kind of transitively-chained mega-group either (a) does not select it for automatic dispatch, routing it to a human decision instead, or (b) the grouping algorithm itself no longer produces a 60+ member group from records that don't substantively share implementation surface.
- A new test pins the chosen behavior against a reproduction of today's shape.
- `npm test` passes with the new coverage.
- No change to the existing, correct behavior for a small, substantively-related file-overlap group (e.g. 2-3 records touching the same feature's actual files) — this record is about the unbounded-size case only, not file-overlap grouping in general.

## Technical Approach

Start with a design decision among (or a combination of) the three candidate directions in Deliverables. Once decided, implement in `groupByFileOverlap` and update `dispatch/SKILL.md`'s Configuration table to document the new behavior.

### Key Files

- `plugin/bin/lib/issues/grouping.js` — `groupByFileOverlap`, the union-find grouping algorithm to bound or filter
- `plugin/skills/dispatch/queue-pull-script.md` — Step 2's file-overlap queue-pull procedure
- `plugin/skills/dispatch/SKILL.md` — Configuration table (new policy key, if adopted) and the "claim file-overlap groups together" contract

## Gotchas

- The fix must not change behavior for a small, substantively-related file-overlap group (2-3 records touching the same feature's actual files) — this record is about the unbounded-size/hub-file case only.
- The three candidate directions are separable and offered as suggestions, not a single prescribed fix — decide before implementing rather than picking the first option reflexively.

## Investigation Findings

**Both candidate directions (a) and (b) are already shipped in the current codebase**, apparently by later work (#1228, #1365) that postdates this record's filing:

- **(a) size guard:** `grouping.js` exports `GROUP_SIZE_GUARD_DEFAULT = 10` and `partitionGroupsBySizeGuard`. `skills/dispatch/queue-pull-script.md` reads the `dispatch-group-size-guard` policy key (schema default `10`, `_shared/policy-schema.md:128`) and calls `partitionGroupsBySizeGuard`, writing excluded groups to `dispatch-oversized-excluded.json` — read only by `next`'s headless selection (Step 3), never by `bare`/explicit-list forms, matching this record's own AC exactly ("a human present, explicitly naming it, is itself the required surfacing").
- **(b) hub-file exclusion:** `groupByFileOverlap` already excludes any path cited by ≥3 records (or ≥10% of the batch) from acting as a union-find bridge (`HUB_PATH_MIN_COUNT`/`HUB_PATH_FRACTION`, #1365) — extensively tested in `tests/bin-lib/issues/grouping.test.js` ("N otherwise-unrelated items sharing only one hub-like path stay as N singletons", etc.). The original incident's own measured citation counts (pre-tool-use.js 8/68, tests/ 8/68, hooks.js 7/68, context.js 6/68, residue.js/donts.md 5/68 each) are all well above this threshold — under today's defaults, none of those files could bridge records together at all.

**Remaining real gap found: `dispatch-group-size-guard` was never added to `skills/dispatch/SKILL.md`'s Configuration table**, even though the record's own Deliverables explicitly asked for that documentation step and the mechanism itself was built. Added the missing row (kept size-headroom-conscious — this file sits close to the 40 KB ceiling; see `docs/donts.md`'s hard-ceiling headroom rule).

**Added regression test** (`tests/bin-lib/issues/grouping.test.js`, "#1557 reproduction") reproducing the actual incident shape — ~70 records, each citing one item-specific file plus two of five above-hub-threshold "core" files (rotating pairs, so the core files transitively chain into one component the way the original 68-record group's multiple shared references did) — confirming: (1) with today's defaults, hub-path exclusion keeps every resulting group small (no group over 3 members); (2) with hub exclusion synthetically disabled (simulating a future regression or an as-yet-unseen shape that clears it), the records DO collapse into one 70-member group, and the size guard independently excludes that group from `next`'s within-guard (headless-eligible) set — proving the two layers are independent defenses, not a single point of failure.

No further code change made — AC bullets 1 and 2 already hold, AC bullet 3 is satisfied by the new test above, and AC bullet 4 (no behavior change for small legitimate overlaps) is unaffected since neither existing mechanism was modified, only documented and additionally regression-tested.
