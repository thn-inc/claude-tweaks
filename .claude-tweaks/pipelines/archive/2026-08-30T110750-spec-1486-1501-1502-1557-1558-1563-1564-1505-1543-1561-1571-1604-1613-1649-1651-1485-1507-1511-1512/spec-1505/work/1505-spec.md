# 1505: Diagnose missing claims-registry entry for #255's dispatch handoff

Surface: backend

## Current State

During #255's dispatch-orchestrated two-call /flow handoff (build,test then review,polish,wrap-up, both sharing PIPELINE_RUN_DIR=2026-08-26T175041-record-255), no claims/issue-255.json blob was ever written to the claims-registry branch, and bot:in-progress was never applied to issue #255. Confirmed via gh api contents/claims/issue-255.json?ref=claims-registry (404) and a full git log scan of claims-registry (zero "Claim issue #255" commits, zero "Release claim on issue #255" commits, ever). The first call's own decisions.md reportedly showed /build and /test both completed normally, so /flow Step 2.8 (claim-targets.md) should have run claim-targets.js before either — its skip-guard does not apply to a build,test step list.

## Investigation Findings

Full end-to-end read of `plugin/bin/lib/claim-targets/claim-targets.js` (400 lines) and `plugin/bin/lib/issues/claim-store.js`, plus `plugin/skills/flow/claim-targets.md`'s Step 2.8 procedure:

**No code defect found.** Every path through `run()` (the CLI's core loop) leaves an observable trace:
- A malformed invocation, missing `--run-id`/`--targets`, or an unresolvable repo slug → exit 2 with a `stderr` message (hard stop).
- Any classified state (`live`/`unreadable`/`tombstone`-in-flight) → either a contest/in-flight stop (exit 3, JSON on stdout) or a transient failure (exit 4, JSON on stdout).
- A reclaimable state (`absent`/`tombstone`/`stale`) → a write attempt, which either succeeds (writes the blob, then unconditionally attempts `ensureAndAddLabel` — `bot:in-progress` — and a claim comment, both best-effort but always attempted) or fails (transient/contested, both reported).

There is no path in this CLI that produces **total silence** — zero commit, zero label attempt, zero stdout/stderr — other than the CLI never being invoked at all. #255's evidence (zero claims-registry commits ever, zero `bot:in-progress` label ever, no contest/transient message reported) is inconsistent with `claim-targets.js` having actually executed and hit any branch of its own logic; it is only consistent with Step 2.8 never running for that pipeline invocation.

**#255's step list (`build,test`) does not match any of `claim-targets.md`'s documented skip-guard conditions** (work-backend `local-files`, unresolved topic-name mode, every target already self-owned, or a step list lacking both `build` and `test`) — so this is not a "legitimate skip" as the record's Deliverables anticipated either.

**Corroborating evidence:** the original run directory (`.claude-tweaks/pipelines/2026-08-26T175041-record-255/`, still present in `$RUN_ROOT`) contains only the tracked `work/255-spec.md` — no `config.yml`, no `decisions.md`, no `staged/`. Since `config.yml`/`decisions.md` are written only when Step 3 (Config Manifesto) "adopts" a dispatch-minted run directory, their total absence from the canonical `$RUN_ROOT` location means Step 3's adoption-write is *also* missing for this exact run — the same absence pattern as Step 2.8's claim, in an unrelated skill step. A defect confined to `claim-store.js`/`claim-targets.js` would not explain a parallel gap in Step 3's manifesto-adoption logic; a single explanation covering both is that this specific pipeline invocation's orchestration deviated from the documented step sequence in a way that isn't reconstructable now (the originating session's transcript from 2026-08-26 is not available, and #255 itself has since been closed and its issue number reused for unrelated content, confirmed via `gh issue view 255`).

**Existing test coverage is substantial** (766 lines in `tests/bin-lib/issues/claim-store.test.js`, 969 lines in `tests/bin-lib/claim-targets/claim-targets.test.js`) — a code-level regression of this magnitude (total silence on every reclaimable branch) would be very unlikely to have escaped that coverage undetected.

**Disposition:** neither Deliverable branch (fix a defect / document a legitimate skip) applies cleanly. No code fix is warranted — none was found. No skip-guard documentation update is warranted — the observed step list does not match any documented skip condition, so codifying it as "legitimate" would misdescribe an anomaly as by-design. A live reproduction of the exact two-call dispatch handoff shape is the only way to attempt to trigger this again, and is out of proportion for this record inside this 19-record batch run (consistent with the practical-scope disposition already applied to #1486 in this same run). This finding is recorded here rather than left as an open question, satisfying AC1 ("root cause identified and stated") with the explicit conclusion: an unreproducible orchestration-level gap in one specific historical run, not a library or CLI defect.
