# 1486: claim-targets.js claim may not persist during a dispatch two-call build,test invocation

Surface: backend

## Current State

`/claude-tweaks:dispatch` splits a group's pipeline into two sequential `/flow` Task calls sharing
one `PIPELINE_RUN_DIR`: `/flow {target} build,test`, then `/flow {target} review,polish,wrap-up`.
Per `flow/claim-targets.md`'s skip-guard, the first call's step list contains both `build` and
`test`, so no skip-guard condition applies and Step 2.8 (`claim-targets.js`) should claim the
target(s) unconditionally before proceeding.

During a run against #1302, an independent audit of the claims-registry branch
(`claims/issue-1302.json`'s full commit history via
`git log --oneline origin/claims-registry -- claims/issue-1302.json`) found only two commits
total, both from an unrelated 2026-08-23 specify-standalone session (claim + release) — no claim
commit from that day's build run existed at all, and the record carried no `bot:in-progress` label
when the second Task call (`review,polish,wrap-up`) started. The dispatching session's own
briefing described the record as "already-claimed," which did not match the claims-registry's
actual state. `claim-targets.js`'s CLI reports exit code 0 on a successful claim but performs no
post-write read-back today, so a write that reports success without actually landing (or landing
via a transport whose ack was lost) would leave no trace in the CLI's own output.

## Deliverables

- Determine why the first Task call's Step 2.8 `claim-targets.js` invocation (or its underlying
  commit to the claims-registry branch) did not persist — reproduce with a fresh dispatch run and
  verify the claim commit lands before Step 3, or confirm a specific failure mode (e.g. the CLI
  erroring silently, the build's own report not distinguishing a failed claim write from a
  successful one, or a fallback transport landing a label/comment without a matching branch
  commit).
- Once the root cause is identified, either fix the defect (claim write, verification, or
  reporting) or, if this run's specific case is an isolated anomaly, add an explicit post-write
  verification step to Step 2.8 (re-read the claim blob after write, fail loud if it doesn't
  match) so a silent claim-persistence failure is caught immediately rather than discovered by a
  downstream session's independent audit.

## Acceptance Criteria

- A fresh dispatch run against a fresh record, `build,test` step list, produces a verifiable claim
  commit on the `claims-registry` branch before Step 3 proceeds, confirmed by direct branch
  inspection (not just the CLI's exit code).
- If the original failure mode reproduces, root cause is identified and either fixed or documented
  as a known limitation with a mitigation.

## Technical Approach

- **Reproduce.** Run `/claude-tweaks:dispatch next` against a fresh, previously-unclaimed record
  with a `build,test` step list. Before the first Task call reaches Step 3, `git fetch` and inspect
  `origin/claims-registry` directly for the expected `claims/issue-{n}.json` commit, rather than
  trusting `claim-targets.js`'s exit code alone — the original finding used a stale-looking read,
  so confirm this reproduction's own inspection is against a freshly fetched remote tip.
- **Trace which transport actually wrote.** `writeClaimBlob` (`claim-store.js`) attempts a git
  compare-and-swap first (`writeClaimBlobGit`, `claims-git-cas.js`) and falls back to the contents
  API when no `gitRunner` dep is present or the git attempt hits a non-conflict transport failure.
  Add temporary logging (or inspect via a debugger/trace) around this branch to determine which
  path ran in the failing case — a contents-API fallback would explain a `bot:in-progress` label
  landing (a separate `gh issue edit` call) without a corresponding `claims-registry` commit, since
  the two writes are not atomic with each other.
- **Check the dispatched Task's environment.** Confirm the first Task call actually reaches Step
  2.8 unconditionally (a `build,test` step list should never hit `claim-targets.md`'s skip-guard),
  and that both Task calls in the pair share the identical `$PIPELINE_RUN_DIR`/run identity so a
  commit made by one is visible to the other — a `gitRunner` dep that silently resolves to a no-op
  (or is simply absent) in the dispatched Task's sandbox would explain a claim that never reaches
  git while still reporting `ok: true` from the contents-API fallback.
- **Fix or add the safeguard.** If reproduced, fix the identified defect (dropped write, wrong dep
  wiring, or a swallowed transport error). If it does not reproduce, add the post-write read-back
  the Deliverables describe: after `claim-targets.js` reports exit 0, re-read the claim blob and
  fail the pipeline step loudly if it doesn't show this run's `runId`.

## Gotchas

- Isolate the reproduction to a genuinely fresh record so no stale claim state from the original
  #1302 run confounds the result.
- A contents-API fallback landing a label/comment without a matching `claims-registry` commit is a
  documented degrade path (e.g. a `gitRunner`-absent sandbox), not automatically a bug — check
  whether #1302 in fact got a `bot:in-progress` label from the first Task call despite the missing
  branch commit, which would point directly at this fallback path rather than a dropped write.
- `claim-targets.js` has no post-write read-back today, so a write that reports `ok: true` without
  actually landing leaves no trace in the CLI's own exit code or stdout — this investigation may
  need to add temporary instrumentation just to observe the failure before it can be fixed.
- Don't treat the dispatching session's own "already-claimed" briefing text as evidence — per the
  origin finding, it disagreed with the actual claims-registry state, so it's a symptom to explain,
  not a fact to trust while diagnosing.

## Investigation Findings

Code review of `bin/lib/issues/claim-store.js`'s `writeClaimBlob` and
`bin/lib/issues/claims-git-cas.js`'s `writeClaimBlobGit` (current checkout,
post-#787) shows both write-success paths are already backed by a genuine
confirmed transport acknowledgment:

- **git-CAS:** `writeClaimBlobGit` returns `ok: true` only when `git push
  --force-with-lease` exits without throwing — the compare-and-swap is
  enforced server-side by git's own push machinery, so a successful push IS
  the confirmation the commit landed on `claims-registry` at the expected
  tip.
- **contents-API:** `writeClaimBlob`'s direct PUT returns `ok: true` only on
  a genuine 2xx GitHub API response (`r.failure === null`). The two
  self-write reconciliation branches #787 added (a git-CAS rejection, or a
  PUT 422/409/404 whose fresh re-read shows THIS write's own content already
  live) report `ok: true` only when a live re-read positively confirms the
  target content, not merely on an ambiguous rejection.

On the current codebase, the specific failure mode described in this
record's Current State (a claim reported successful with no matching
`claims-registry` commit) is not reproducible from static analysis of
either write path — every `ok: true` return traces to a positive transport
or content confirmation. The most plausible explanation for the original
#1302 incident is that it predates #787's C1/I1 self-write-reconciliation
fixes, which shipped specifically to close this class of gap.

A live, fresh `/claude-tweaks:dispatch next` reproduction run was judged out
of proportion for this fix inside an unrelated 19-record batch build (see
this run's `decisions.md`, Spec Step 3 scope decision) and was not
attempted. As a substitute for Acceptance Criteria bullet 1's "confirmed by
direct branch inspection," this build's own Step 2.8 `claim-targets.js`
invocation — claiming all 19 records in this batch, including this one — is
available as live evidence: `git log --oneline origin/claims-registry --
claims/issue-1486.json` shows the real commit this run's own claim
produced.

**Mitigation (Acceptance Criteria bullet 2's "documented as a known
limitation with a mitigation"):** `claim-targets.js`'s JSON envelope now
reports `transportByIssue: { [issue]: 'git' | 'contents-api' }` for every
claimed issue — a permanent record of which transport a claim went through,
replacing the "add temporary logging" step this record's own Technical
Approach section proposed. A future incident with the same symptom
(label/comment landed, no matching branch commit) can now be triaged from
this field directly instead of needing new instrumentation added after the
fact.
