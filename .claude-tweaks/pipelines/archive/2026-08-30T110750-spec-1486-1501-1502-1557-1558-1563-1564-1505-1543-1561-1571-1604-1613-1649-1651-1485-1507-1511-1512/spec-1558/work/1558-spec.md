# 1558: detectIntegrationModel shells `gh repo view` directly — always falls back to local-merge in a gh-absent sandbox even when GitHub is reachable via MCP

Surface: backend

Origin: /claude-tweaks:dispatch next, scheduled Routine firing, run 2026-08-27T141617-dispatch-standalone

## Current State

`bin/lib/policy-schema.js`'s `detectIntegrationModel(repoRoot)` (the code twin `skills/_shared/forge-detection.md` names: "`bin/lib/policy-schema.js`'s `detectIntegrationModel` replicates checks 1 and 3 of this ladder in code") resolves `pr-first` vs `local-merge` by shelling out directly:

```js
try {
  execFileSync('gh', ['repo', 'view', '--json', 'owner,name'], opts);
} catch {
  return 'local-merge';
}
return 'pr-first';
```

When `gh` is absent from the sandbox (the documented, expected case in a cloud Routine container — `skills/dispatch/mcp-transport.md` exists specifically to bridge this), this `execFileSync` throws immediately (command not found), and `detectIntegrationModel` returns `local-merge` unconditionally — regardless of whether the repository is actually GitHub-backed and reachable. There is no MCP-aware fallback here, unlike `dispatch/SKILL.md`'s own Preflight Detection Ladder (checks 1-3), which explicitly branches to an MCP path (`mcp-transport.md`) when `gh` is absent but a GitHub MCP server is available.

**Reproduced live** during a `dispatch next` Routine firing, in the exact sandbox: `gh` is absent (`which gh` exits 1); `git remote get-url origin` succeeds (a real GitHub remote); `mcp__github__list_issues` against this repo succeeds (confirmed reachable + authenticated). Yet `node bin/hooks.js reconcile --json` (which calls `resolveIntegrationModel` -> `detectIntegrationModel` under the hood) reported `local-merge`, and only after discovering and fixing an unrelated issue (`origin/HEAD` symref unset in this container, fixed via `git remote set-head origin main`) did reconcile stop skipping with `no-remote` — but `resolveIntegrationModel` still read `local-merge`, confirmed by re-reading `detectIntegrationModel`'s source and finding the un-bridged `gh repo view` call above.

This matters beyond cosmetics: `integration-model` gates a wide surface (`_shared/integration-model.md`) — PR-vs-local-merge machinery in `/flow`, `/dispatch`'s Settle/Auto-merge gate paths, `merge-verification` derivation (`bin/lib/merge-verification.js`), reconcile's mirror/release/archive checks. A genuinely GitHub-backed, MCP-reachable project running in a `gh`-absent sandbox (any cloud Routine container without `gh` installed) silently downgrades to the `local-merge` fallback path everywhere this function's result flows, even though `pr-first` is this project's actual configured/intended model per CLAUDE.md's Integration model section.

## Deliverables

Node code invoked via `execFileSync` (this function, run as a plain subprocess) has no route to an MCP tool call — MCP tools are only reachable from the agent conversation, not from spawned subprocess code — so this is a real architectural gap, not a one-line fix. Candidate directions (not prescriptive; the actual fix needs a design decision):

- An injectable override: let a caller that already knows GitHub is MCP-reachable (e.g. a skill that already ran `mcp-transport.md`'s Preflight probe) pass that verdict in — an env var (e.g. `CLAUDE_TWEAKS_GH_REACHABLE=1`) or a `deps`-seam parameter threaded through `resolveIntegrationModel`/`resolveMergeVerification`'s callers — so a `gh`-absent-but-MCP-reachable session doesn't have to re-derive reachability purely from subprocess-visible signals.
- A cheaper/different subprocess-visible signal that doesn't require `gh` — e.g. treat "git remote exists + this project's own `work-backend: github-issues` config key is set" as sufficient evidence of `pr-first`-eligibility when `gh` is absent, deferring only to the full `gh repo view` check when `gh` is actually present. (Weaker: doesn't confirm reachability/auth, only configuration intent.)
- Document the gap explicitly and require `.claude-tweaks/policy.yml`'s `integration-model` key to be set explicitly for any project that expects `pr-first` behavior in a `gh`-absent sandbox — turns a silent downgrade into a documented, deliberate opt-out (least invasive, but pushes the burden onto every affected project's own config rather than fixing detection).

Whichever direction is chosen, keep `_shared/forge-detection.md`'s "Code twin" note accurate — it currently asserts checks 1 and 3 are replicated with no stated divergence from the prose ladder's own MCP-aware check 2/3 branching, which this record shows is not quite true today.

## Acceptance Criteria

- In a `gh`-absent sandbox where the repo is genuinely GitHub-backed and MCP-reachable, `resolveIntegrationModel`/`detectIntegrationModel` resolves `pr-first` (or the chosen fix's equivalent), not an automatic `local-merge` downgrade — for a project whose actual configuration/intent is `pr-first`.
- A regression test reproduces today's gap (gh absent, real remote, mock/injected MCP-reachable signal) and passes only once fixed.
- `_shared/forge-detection.md`'s "Code twin" note is updated to state the chosen resolution accurately.
- `npm test` passes with the new coverage.
- No behavior change for a genuinely `gh`-present sandbox, or a genuinely local-merge/no-forge project.

## Technical Approach

Choose among the three candidate directions in Deliverables — an injectable override/deps-seam parameter letting a caller that already confirmed MCP reachability pass that verdict in, a cheaper subprocess-visible signal (e.g. git remote + `work-backend: github-issues` config) used only when `gh` is absent, or documenting the gap and requiring `integration-model` to be set explicitly for `gh`-absent projects. Whichever is chosen, update `detectIntegrationModel`/`resolveIntegrationModel` and every documented consumer, and correct `_shared/forge-detection.md`'s "Code twin" note to state the resolution accurately.

### Key Files

- `plugin/bin/lib/policy-schema.js` — `detectIntegrationModel`, the un-bridged `gh repo view` call
- `plugin/skills/_shared/forge-detection.md` — the "Code twin" note asserting no divergence from the prose ladder
- `plugin/skills/dispatch/mcp-transport.md` — the existing MCP-aware bridge pattern `dispatch/SKILL.md`'s own Preflight ladder already uses, as prior art for whichever direction is chosen
- `plugin/bin/lib/merge-verification.js` — a downstream consumer of `resolveIntegrationModel`'s result

## Gotchas

- Node code invoked via `execFileSync` has no route to an MCP tool call — MCP tools are only reachable from the agent conversation, not from spawned subprocess code — so this is a real architectural gap, not a one-line fix.
- No behavior change should occur for a genuinely `gh`-present sandbox, or a genuinely local-merge/no-forge project — the fix is scoped to the `gh`-absent-but-MCP-reachable case only.

## Investigation Findings

**Candidate direction 1 (injectable override) was already substantially shipped, by #1421** — `detectIntegrationModel(repoRoot, opts)` already accepts `opts.mcpReachable` and short-circuits past the `gh repo view` probe (`plugin/bin/lib/policy-schema.js:539-554`). `bin/resolve-policy.js`'s own `--mcp-reachable` flag already threads it through `computeDerivedDefaults` for both `integration-model` and `merge-verification`. `_shared/forge-detection.md`'s "Code twin" note already documents this exact override as "the one sanctioned exception" — the record's premise that this note asserts *no* divergence no longer matches the current doc.

**The actual remaining gap: `bin/lib/reconcile/index.js`'s own `resolveIntegrationModel(root)` call (line 106, pre-fix) never forwarded `mcpReachable` at all** — the exact call path this record's own live reproduction hit (`node bin/hooks.js reconcile --json`). Every other production caller either already threads `mcpReachable` (resolve-policy.js) or has no agent turn to source it from at all (pre-tool-use.js's PR-stamp branch, already documented as a permanent, structural gap — IL-63 — not a bug to fix).

**Fix implemented:** `reconcile(opts)` now accepts `opts.mcpReachable` (forwarded into `resolveIntegrationModel`) and, test-only, `opts.resolveIntegrationModel` (an injectable override, mirroring `pre-tool-use.js`'s own `deps.resolveIntegrationModel` pattern — real gh-absent-but-remote-present fixtures are fragile/environment-dependent to construct reliably). `bin/hooks.js`'s `reconcile` CLI verb gained a `--mcp-reachable` flag (same contract/wording as `resolve-policy.js`'s own flag) forwarding into `reconcile()`'s new option — this is the flag an agent that already ran `mcp-transport.md`'s Preflight probe should pass when invoking `node bin/hooks.js reconcile` directly. Internal hook-context callers (session-start.js, pre-compact) pass no such flag and are unaffected — matching today's behavior exactly, since they have no probe to source it from either.

Covered by: a unit test on `reconcile()`'s forwarding (`tests/reconcile.test.js`, "forwards opts.mcpReachable into resolveIntegrationModel") and a CLI-level smoke test confirming `--mcp-reachable` is accepted (a no-remote fixture skips before the flag can matter, so it stays deterministic).

`_shared/forge-detection.md`'s "Code twin" note needed no edit — already accurate.
