# 1501: bookkeeping-stamps gate's #989 no-upstream-yet push exemption did not fire for a real first push (repro-resistant)

Surface: backend

## Current State

During a `/claude-tweaks:flow #1432 review,polish,wrap-up` run resuming a case-3 (missing `config.yml`) inherited pipeline run directory, `_shared/pr-early-run-lifecycle.md`'s Step 2 push (the branch's first push to origin, establishing upstream tracking) was denied by `checkBookkeepingStampsGate` (`plugin/bin/lib/hooks/pre-tool-use.js`) with the PR-stamp deny message, even though the push should have matched the `#989` one-shot `hasNoUpstreamYet` exemption (lines ~1007-1020).

Reproduction attempts:
- The real `git push origin <branch>` (with and without an explicit `-C <worktree>`), issued via the actual Bash tool from a session isolated to the worktree, was denied on every retry, identically worded.
- Directly replaying an equivalent synthetic `PreToolUse` payload through `node bin/hooks.js pre-tool-use < payload.json` (matching `cwd`, `tool_name: "Bash"`, the same literal `git -C ... push origin ...` command string, and `session_id`) returned exit 0 (allow) every time it was tried.
- Directly calling `checkBookkeepingStampsGate` with a manually constructed `ctx` (same `runState`, same `commandGitTargets` from the real `gitTargets()` parser) also returned `{}` (allow).

So the exemption logic is provably correct in isolation, but the real harness invocation denied the push anyway — the discrepancy between the real invocation's payload and every reproduction attempt could not be pinned down from inside the worktree-isolated session (no way to capture the real hook's actual stdin).

Workaround used to unblock the run: logged the mandatory `PR-early run lifecycle: ... FAILED` degrade line via `bin/log-decision.js` (itself exempt from this gate, since it is not a git command), which set `hasLoggedPrDegrade` true and let the retry push through cleanly.

## Deliverables

- Reproduce the discrepancy between the real `PreToolUse` hook invocation and a synthetic replay for a `git push` establishing upstream tracking for the first time in a `pr-first` run whose materialize commit already landed and whose worktree stamp is recorded but PR stamp is not.
- Instrument or otherwise capture the real hook's received stdin payload during the failure (a debug env var gate, or a temporary capture in a controlled repro) to compare byte-for-byte against a synthetic payload.
- Fix the `#989` exemption (or the payload construction feeding it) so a genuinely upstream-less first push is never denied by this gate.

## Acceptance Criteria

- A first-time `git push` establishing upstream tracking, issued from a `pr-first` run with a landed materialize commit, recorded worktree stamp, and no recorded PR, succeeds without needing the FAILED-degrade-line workaround.
- A regression test pins the fixed shape (or, if the root cause turns out to be environmental/non-reproducible in `node --test`, the investigation's findings are recorded here with why no test could be written).

## Technical Approach

Start by capturing the real hook's actual stdin during a live failure — the synthetic-replay reproduction path (`node bin/hooks.js pre-tool-use < payload.json`) and the direct `checkBookkeepingStampsGate` unit-level call both currently return allow, so the discrepancy must live in some field of the real invocation's payload (cwd, tool_name, session_id, or the exact command string as PreToolUse actually delivers it) that none of the manual reproductions have matched yet. Add a temporary debug capture (env-gated) inside the real hook path to dump the received payload the next time this fires for real, then diff it byte-for-byte against the synthetic payloads already tried. Once the differing field is identified, fix either the `#989` exemption's matching logic or the payload construction feeding it so a genuinely upstream-less first push is never denied.

### Key Files

- `plugin/bin/lib/hooks/pre-tool-use.js` — `checkBookkeepingStampsGate`, the `#989` `hasNoUpstreamYet` exemption (lines ~1007-1020)
- `plugin/bin/hooks.js` — the `pre-tool-use` CLI entrypoint used for synthetic replay
- `plugin/bin/log-decision.js` — the exempt-from-this-gate workaround call used to unblock the run

## Gotchas

- The exemption logic is provably correct in isolation (both a synthetic hook replay and a direct `checkBookkeepingStampsGate` call with a manually constructed context returned allow) — the bug is in some field of the real invocation's payload that the reproductions haven't matched, not in the exemption's own logic.
- No way to capture the real hook's actual stdin was available from inside the worktree-isolated session that first hit this — the fix will likely need a temporary capture added ahead of the next live occurrence.
- If the root cause turns out to be environmental/non-reproducible in `node --test`, record why no regression test could be written rather than leaving Acceptance Criterion 2 silently unmet.

## Investigation Findings

Built the debug-capture instrumentation Deliverable 2 asks for:
`CT_HOOKS_DEBUG_CAPTURE` (env var, unset by default) appends one JSON line
per `pre.run()` call — `input`, `cwd`, `runDir`, `runState`, `ownedRun` — to
the named file, best-effort (a write failure never breaks the real gate
call). Covered by 3 new tests in `tests/hooks-pre-tool-use.test.js`. This is
buildable and testable now; it is not itself the fix.

Deliverables 1 (reproduce) and 3 (fix) remain genuinely blocked on a live
capture, per this run's own scope decision (see `decisions.md`) not to chase
a hook-internals repro inside an unrelated 19-record batch build. One
plausible hypothesis worth recording for whoever captures the next live
occurrence: `bin/hooks.js`'s dispatcher falls back to `process.cwd()` when a
PreToolUse payload's `cwd` field is absent or empty
(`const cwd = typeof input.cwd === 'string' && input.cwd ? input.cwd : process.cwd();`).
If the real harness's PreToolUse payload for a Bash call issued from inside
a worktree-isolated session ever carries a stale or empty `cwd` — a
harness-side cwd-tracking gap, not a bug in this gate's own logic — the
`hasNoUpstreamYet` check in `checkBookkeepingStampsGate` would run against
whatever `process.cwd()` resolves to for the hook subprocess (plausibly the
main checkout) instead of the worktree, and `@{u}` would resolve against the
main checkout's own tracked branch (which has an upstream), making the
exemption fail to fire — matching the observed symptom exactly, and matching
every reproduction attempt's outcome (a synthetic payload with an explicitly
correct `cwd` field always allowed). This is unconfirmed without a live
`CT_HOOKS_DEBUG_CAPTURE` trace and is not acted on here — a speculative fix
for an unconfirmed cause risks masking a real future denial.
