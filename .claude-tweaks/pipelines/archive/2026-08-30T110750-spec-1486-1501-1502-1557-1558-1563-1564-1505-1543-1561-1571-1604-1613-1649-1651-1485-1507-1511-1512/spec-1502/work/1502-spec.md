# 1502: pre-compact hook can mark a live multi-spec run "clean", letting a concurrent reconcile archive it mid-pipeline

Surface: backend

## Current State

The context-compaction hook stamped an ACTIVE multi-spec run's `run-state.json` as `status: clean` / `worktree: null` while its worktree and PR were still live, and a concurrent session's reconcile pass then archived the whole run directory mid-pipeline.

Repro steps:
1. Start a long multi-spec `/flow` run with `worktree-always: true` and a live PR.
2. Trigger a context-compaction event partway through the run (a long session naturally hits this).
3. While that run is still active, run a concurrent session's reconcile pass (e.g. via `/claude-tweaks:dispatch` on an unrelated record).

Actual: the pre-compact hook stamped `status: clean` / `worktree: null` on the still-active run, and the concurrent reconcile then moved the entire run directory into the archive path mid-pipeline. Detected only because a downstream step reported an expected subdirectory missing; recovered by moving the directory back and re-stamping it active with its worktree and PR restored. No pipeline state was actually lost this time, but the failure mode is structural, not a one-off race.

Related: possibly the same problem area as two prior closed reports (#1130, #208) about pre-compact/session-end-boundary run-state corruption and premature archival — those describe test-fixture data leaking into a resumed run's state and an archived run being resurrected by later writes; this report is a genuinely active, still-in-progress run being marked clean and archived out from under itself, which may be a distinct edge case in the same mechanism rather than the same bug.

## Deliverables

- Identify why the pre-compact hook's `run-state.json` status stamping marked this still-active run `clean`/`worktree: null` while its worktree and PR were genuinely still live.
- Fix the pre-compact hook so it never marks a run `clean` while its worktree still exists and its PR is still open.
- Add (or harden) a guard in the reconcile archival pass so it never archives a run directory whose stamped `status` disagrees with directly-observable evidence (an existing worktree, an open PR) — defense in depth against a future stamping bug reintroducing this failure mode.
- Determine whether this is the same underlying mechanism as #1130/#208, or a distinct edge case, and record the conclusion.

## Acceptance Criteria

- A long multi-spec `/flow` run under `worktree-always: true` with a live PR survives a mid-run context-compaction event without its `run-state.json` being marked `clean`/`worktree: null`.
- A concurrent reconcile pass run against a genuinely active run (live worktree, open PR) never archives it, even if the run's own status stamp were somehow wrong — the reconcile-side guard catches it independently.
- A regression test reproduces this scenario (a compaction event on an active run, followed by a concurrent reconcile pass) and fails without the fix.
- `npm test` passes with the new coverage.

## Technical Approach

Trace the pre-compact hook's run-state stamping logic (`plugin/bin/lib/hooks/pre-compact.js`) to find where it derives `status`/`worktree` — likely a stale or default value being written instead of the run's actual live state. Cross-reference against #1130/#208's prior fixes in the same area to determine whether this is a regression of the same mechanism or a new edge case. On the reconcile side, add a pre-archival check in the archive pass that independently verifies the run has no live worktree and no open PR before archiving, rather than trusting the stamped `status` field alone.

### Key Files

- `plugin/bin/lib/hooks/pre-compact.js` — the pre-compact hook's `run-state.json` status stamping
- `plugin/bin/lib/hooks/context.js` — shared run-state read/derive helpers the pre-compact hook likely calls into
- `plugin/bin/lib/reconcile/archive-merged.js` — the archival pass that moved the run directory into the archive path

## Gotchas

- No pipeline state was actually lost this time — the run was manually recovered (directory moved back, re-stamped active with worktree/PR restored) — but the failure mode is structural and will recur under the same race without a fix.
- #1130 and #208 are prior closed reports in the same problem area (pre-compact/session-end-boundary run-state corruption and premature archival) but describe different symptoms (test-fixture data leaking into resumed state; an archived run resurrected by later writes) — don't assume this is the identical bug without checking whether either prior fix already covers this scenario.

## Investigation Findings

**Deliverable 1 (root cause) — `pre-compact.js` does not, and structurally
cannot, write `status`/`worktree`.** Current code (`bin/lib/hooks/pre-compact.js`)
only ever writes `{ lastEvent: 'pre-compact' }` via `writeRunState`'s merge
semantics (`{...prev, ...patch}`) — it never touches `status` or `worktree`.
`git log --oneline -- plugin/bin/lib/hooks/pre-compact.js` shows exactly one
commit (a repo-wide file move, #418), confirming this file's content has
never substantively changed. The bug report's attribution to "the
pre-compact hook" does not match any mechanism this file can perform, on
any version of this codebase.

The actual writer of `{status: 'clean', worktree: null}` is
`closeRunState` (`bin/lib/hooks/close-run-state.js:64`), invoked by the
`close-run`/`teardown-run` `bin/hooks.js` commands. Its foreign-owner guard
(`prev.sessionId !== callerSessionId`) only refuses an implicit close on a
**provable** identity mismatch — a run whose `run-state.json` never
recorded a `sessionId` at all reads as `foreignOwner: false` regardless of
who calls, so an unrelated session's bare `close-run` (no explicit `--run`,
landing on "the newest non-terminal run" via the fallback resolver — the
same resolution shape already flagged as a hazard for `record-worktree`)
could close a genuinely live run around the same wall-clock time as an
unrelated compaction event, without ever going through pre-compact.js. This
is the more precise mechanism than the report's own hypothesis, and matches
the observed symptom without requiring pre-compact.js to be involved at
all.

**Deliverable 3 (reconcile-side archival guard) — already shipped as #1544**
(`d1084bdb7`, "archive-merged: archive a status:clean run dir once its PR
is confirmed merged"). `archiveMerged`'s clean-status sweep
(`iterCleanRunDirs` → `decideArchive`) calls `resolvePrState` — a live
`gh pr list --head {branch}` query, never a cached field — and skips
archival outright when the PR's live state isn't `MERGED` (`reason:
'pr-open'`/`'pr-closed-unmerged'`), independent of whatever the run's own
`status` stamp says. AC bullet 2 ("even if the run's own status stamp were
somehow wrong — the reconcile-side guard catches it independently") is
already satisfied by this existing code.

**Deliverable 2 (fix) — implemented, scoped to the actual mechanism found
in Deliverable 1, not to pre-compact.js.** `closeRunState`'s implicit-close
path now also refuses (`status: 'refused-live-worktree'`) when
`prev.sessionId` is absent AND `prev.worktree` still exists on disk —
narrow and deliberate: it fires only when the foreign-owner check had
nothing to compare (no recorded owner at all), never when a sessionId is
recorded and matches the caller (teardown-run's own legitimate self-close,
which always finds its own worktree still present at this point in its own
sequence, is unaffected — the foreignOwner comparison already passes
there). See `bin/lib/hooks/close-run-state.js`, `bin/hooks.js`'s `close-run`
command, and `bin/lib/hooks/teardown-run.js`'s new `refused-live-worktree`
handling. Covered by 5 tests in `tests/bin-lib/hooks/close-run-state.test.js`.

AC bullet 3 ("a regression test reproduces this scenario... and fails
without the fix") is satisfied at the unit level (`closeRunState` called
directly with a no-sessionId, live-worktree run-state) rather than via a
full compaction-plus-concurrent-reconcile integration scenario — the latter
would need to simulate two concurrent sessions and a real `gh`-backed PR,
disproportionate for what Deliverable 1's finding shows is actually a
same-mechanism, single-function fix.
