# 1561: worktree-always: close-run and wrap-up telemetry leave .claude-tweaks/wrap-up-outcomes.tsv dirty and uncommittable in the main checkout

Surface: infra

## Current State

Under worktree-always, close-run (and the wrap-up engine's telemetry append) mutate .claude-tweaks/wrap-up-outcomes.tsv in the main checkout, while the policy's write gate blocks git commit there — and the tsv's path is not in the gate's exempt list. Observed 2026-08-27 on a worktree-always: ON project (a private headless automation hub, plugin version 6.108.0). The only sanctioned route is provisioning a scratch worktree; in practice sessions end with the file left dirty.

## Deliverables

One of the following (a design decision, not prescriptive):

- (a) Add .claude-tweaks/wrap-up-outcomes.tsv to the write gate's exempt list.
- (b) Route close-run and the wrap-up engine's telemetry append through a sanctioned commit path.
- (c) Gitignore the file, if its history is not meant to be durable.

## Acceptance Criteria

- Under worktree-always: ON, running close-run and/or a wrap-up engine telemetry append no longer leaves the tsv as an uncommittable dirty tracked file in the main checkout.
- calibration-report.js's existing consumption of the tsv continues to work unchanged.
- A regression test pins the chosen behavior.
- npm test passes with the new coverage.

## Key Files

- plugin/bin/hooks.js — close-run subcommand
- plugin/bin/wrap-up-engine.js — the wrap-up engine's telemetry append
- plugin/bin/calibration-report.js — the tsv's consumer
- plugin/skills/_shared/policy-schema-coverage.md — the write gate's exempt-path coverage block

## Gotchas

- #1395 covers a related but distinct problem (exemptions for untracked/gitignored targets) — don't conflate the two fixes.
- If choosing (c) gitignore, confirm calibration-report.js doesn't rely on the tsv's git history being durable before removing it from tracking.

## Investigation Findings

Checked this repo's own state first: `git ls-files | grep wrap-up-outcomes` returns nothing, and `.gitignore` already contains `.claude-tweaks/wrap-up-outcomes.tsv` (added by commit `51b328046`, 2026-08-08, "Ignore wrap-up outcome telemetry file — local state, IL-06 explicit-entry convention" — option (c) was already chosen and applied, well before this record's own 2026-08-27 observation date, and the file has never been tracked in this repo's history at all).

This means the bug as described cannot reproduce in THIS repo. The report's own text says it was "Observed ... on a private headless automation hub" — a *different*, consumer project with the plugin installed, not this dev repo. `.gitignore` is per-project state; this repo's own root `.gitignore` has zero effect on any other project's repo.

**Root cause found**: `/claude-tweaks:init`'s Step 4 gitignore-suggestion template (`plugin/skills/init/bootstrap/step-04-gitignore-suggestions.md`) — the block every *consumer* project's `.gitignore` gets seeded from — never included the `.claude-tweaks/wrap-up-outcomes.tsv` line, even though this repo's own root `.gitignore` has carried it since before that template gap was ever noticed. A consumer project seeded from the incomplete template has no gitignore rule for the tsv; if any subsequent broad `git add` (or similar) ever swept it in, it becomes a tracked file that `close-run`/the wrap-up engine keep appending to, and under `worktree-always` a commit of exactly that file is refused (no exempt path) — a permanently uncommittable dirty file, matching the report exactly.

**Fix implemented** (option (c), applied at the layer that was actually missing it — the init suggestion template, not this already-correct repo):

1. `plugin/skills/init/bootstrap/step-04-gitignore-suggestions.md`: added `.claude-tweaks/wrap-up-outcomes.tsv` to the suggested `.gitignore` block (alongside `routine-environment-cache.yml`/`init-state.yml`), extended the prose paragraph to explain the line and cite #1561, and added a migration-check table row so an existing consumer project whose `.gitignore` predates this line gets it added on a re-run of init's Step 4.
2. No change to `plugin/bin/calibration-report.js` — AC2 is satisfied trivially (untouched).
3. No change needed to `plugin/bin/hooks.js`'s `close-run` or `plugin/bin/wrap-up-engine.js`'s telemetry append — both already write to a path this repo's own `.gitignore` correctly ignores; the gap was purely in what gets propagated to *other* projects via `/claude-tweaks:init`.

**Regression tests added** (`tests/feedback-watermark-prose.test.js`, extending the file's existing `step-04`/`.gitignore` parity-test section): one test pinning the template's fenced suggestion block contains the `wrap-up-outcomes.tsv` line, one pinning this repo's own root `.gitignore` still contains it (guarding against an unrelated future edit accidentally dropping either copy). `tests/feedback-watermark-prose.test.js` runs 26/26 green.

**Recovery for an already-stuck consumer project**: re-running `/claude-tweaks:init` picks up the new migration-check row and adds the missing line; a project whose tsv is *already* tracked additionally needs one manual `git rm --cached .claude-tweaks/wrap-up-outcomes.tsv` commit (from within an authorized worktree under `worktree-always`) to actually untrack the file — the gitignore line alone does not retroactively untrack an already-committed path. This one-time step is out of scope for an automated fix here (AC1 is about steady-state behavior once the fix is adopted, not an automatic migration of already-broken installs) and is noted here rather than left undocumented.
