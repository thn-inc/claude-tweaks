# 5050: Decide the gh bound for the four generic exec seams that ignore gh-timeout-ms

Surface: infra

**Related:** #4856, #3974, #4217, #3931, #4620, #4892, #5004, #3822, #4736, #4829, #3193, #3878, #3990, #4128, #4209, #4244, #4310, #4345, #4347, #4366, #4431, #4433, #4456, #4565, #4737, #4763, #4794, #4913, #4960, #4967, #4993, #5048, #4108, #4443, #4499, #4686

## Current State

Four exec seams set one fixed `timeout: 30000` for every child process they spawn, whatever the command:

| Seam | Where the 30 s is set | `gh` spawns | `git` spawns | `node` spawns |
|---|---|---|---|---|
| `plugin/bin/console-resolve.js` | `defaultExecFile`, line 110 | 2 | 2 | 0 |
| `plugin/bin/lib/flow/preflight.js` | `EXEC_OPTS`, line 29 | 1 (`gh pr view`) | 0 | 2 (`verify.js --stamp-status`, `--changed-files`) |
| `plugin/bin/lib/release-preflight/pack.js` | `EXEC_OPTS`, line 24 (sync `git` runner line 113, async runner line 114) | 5 | 9 call sites through `deps.git` | 0 |
| `plugin/bin/lib/wrap-up/pack.js` | `EXEC_OPTS`, line 35 (`execBounded`, plus a direct `pr-checks.js` spawn at line 665) | 1 | 0 | 4 |

Two policy keys already exist for exactly these commands, and each one defaults to 30 s:

- `gh-timeout-ms`, through `GH_BATCH_TIMEOUT_MS` in `plugin/bin/lib/shared-primitives.js`, which is `max(30000, gh-timeout-ms)`. #4815 introduced it and moved every batched `gh` runner onto it. It left these four seams alone because they are not batched runners and none was in that diff.
- `git-timeout-ms`, through `GIT_TIMEOUT_MS` in the same module. It defaults to 30000 and can be set up to 120000.

So on a slow host, which is the case both keys exist for, a `gh` or `git` call through one of these seams is still killed at 30 s however high the project raised the key. The record was filed citing `console-resolve.js:86`; the timeout now sits at line 110.

The two seams that run `node` (`flow/preflight.js`, `wrap-up/pack.js`) also get a test pinning their `node` bound at 30000.
- Update the `gh-timeout-ms` and `git-timeout-ms` summaries in `plugin/bin/lib/policy-schema.js` so they no longer understate their consumers. ## Technical Approach

Decision (2026-11-04, human-approved in `/claude-tweaks:specify #5050`): the bound follows the command, not the seam. The open question was "batched read or fixed 30 s?", and it is answered by neither. These seams' `gh` calls take the existing `GH_BATCH_TIMEOUT_MS`, and their `git` calls take the existing `GIT_TIMEOUT_MS`. A new policy key was rejected because it would duplicate these two. `GH_TIMEOUT_MS` was rejected because its 5 s default would lower the bound. `node` spawns stay at a fixed 30000, because no key governs them.

Each seam keeps its single options object for `maxBuffer` and `windowsHide`, and picks `timeout` per spawn from the command name. Read the getters at spawn time, not at module load, so a test can vary the env var per probe.

`tests/helpers/gh-timeout-probe.js` already captures the `timeout` a `gh` spawn carries, by stubbing `child_process.execFileSync` and evicting the module cache. It covers the synchronous runners: `console-resolve.js`'s `defaultExecFile`, `flow/preflight.js`'s `execFile` and `release-preflight/pack.js`'s `git` runner. The asynchronous runners (`execFileAsync` in `flow/preflight.js` and `release-preflight/pack.js`, and `execBounded` in `wrap-up/pack.js`) need either an equivalent `execFile` stub or the seam's injected `deps`. `wrap-up/pack.js` already passes its options into `deps.execFile`, so a fake there sees them directly. In `release-preflight/pack.js` and `flow/preflight.js` the options live in the default-deps factory, so the test has to exercise that factory. A probe that passes a fake `deps` would bypass the line under test. Extending the helper to take the env-var key and the command name is the natural reuse.

## Gotchas

- #4856 ("Route every gh call's timeout through GH_TIMEOUT_MS") originally listed `console-resolve.js` too, with the opposite bound: `GH_TIMEOUT_MS`, a 5 s default. On 2026-11-04 it was narrowed to its other three files, and `console-resolve.js` belongs to this record. If the two records land in one dispatch group, through the shared `policy-schema.js` key file, this record's bound wins for `console-resolve.js`.
- Three of the seams also cap each probe at `PROBE_TIMEOUT_MS = 60000` through `withTimeout`: `flow/preflight.js`, `release-preflight/pack.js` (which imports it from `wrap-up/pack.js`) and `wrap-up/pack.js`. That outer timer cannot interrupt a synchronous spawn: `execFileSync` blocks the event loop until it returns. So a raised `git-timeout-ms` (up to 120 s) does take effect on `release-preflight/pack.js`'s synchronous `git` runner. An asynchronous `gh` call raised to its 60 s maximum can still be cut by the 60 s probe cap when the probe did other work first. This record leaves `PROBE_TIMEOUT_MS` unchanged.
- `GH_BATCH_TIMEOUT_MS` and `GIT_TIMEOUT_MS` are memoized once per process. Destructuring one at require time freezes it before a test can set the env var, which is why the probe helper evicts the module cache.
- `flow/preflight.js` spawns `node verify.js` for the stamp and changed-files reads. Those must stay at 30000, so don't key the timeout on anything but the command name.
- The `wrap-up/pack.js` comment above `EXEC_OPTS` says every subprocess gets "a 30 s wall clock". Reword it to describe the per-command bound.
