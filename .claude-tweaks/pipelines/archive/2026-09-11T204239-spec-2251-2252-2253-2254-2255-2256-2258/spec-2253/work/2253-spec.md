# 2253: Init bootstrap, detection, and the two policy keys

Surface: infra

## Overview

`/claude-tweaks:init`'s detection already has a release-process row (`init/detection-tables.md:102`, "Release process (semantic-release, changesets, manual tags)") but it detects and writes the result nowhere — a dangling finding. This unit gives that finding a destination: a new bootstrap step that, on a clean or already-plugin-shaped repo, writes the release-please engine's config files and the two new policy keys (`release-hook`, `release-train`) that later phases read; on a conflicting existing release tool, it refuses and reports rather than layering a second engine on top.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- Implementing the release-please workflow's actual runtime behavior, or the local engine — this unit only writes the config files and policy scaffolding; Phase 4 (the local engine) and the `googleapis/release-please-action` itself do the release work.
- Migrating this repo's own release process — that is Phase 8 (a separate, later unit), which consumes this unit's bootstrap step but is not part of it.
- A generic "any release tool" wrapper — conflict detection intentionally refuses to coexist with semantic-release/changesets/a foreign release-please config rather than trying to support them (design doc stance 7).
- Monorepo / multi-language-stack `release-type` resolution — this unit assumes one dominant stack per repo (matching this plugin's own single-package structure) and resolves exactly one `release-type` value; a repo where more than one stack-table row matches is out of scope, handled by falling through to `simple` (see Deliverables) rather than by a precedence rule.
- Defining `release-hook`/`release-train`'s consumption contract — this unit ships schema scaffolding only (type, default, tier, and the policy.yml rows). What actually reads and acts on these two keys is unit 4 (`release-local.js`, `release-hook`) and unit 6 (the `/claude-tweaks:release` skill, `release-train`) — both separate, later units.

## Acceptance Criteria

1. A fresh Node repo with no release tooling and `integration-model: pr-first` ends an init run with all three files present (`release-please.yml`, `release-please-config.json`, `.release-please-manifest.json`), `release-type: node`, and manifest version `0.1.0`.
2. The identical fresh-repo fixture with `integration-model: local-merge` ends init with `release-please-config.json` and `.release-please-manifest.json` present (same `release-type`/version), but no `release-please.yml` workflow file — the workflow is pr-first only.
3. A repo with an existing `.changeset/` directory ends init with none of the three files written, and the init summary's `release` line reads `conflict — changesets` (or the equivalent detected-tool name). A repo with only manual `v*` tags and no other release-tool marker does **not** trigger `conflict` — it proceeds through the `fresh` path.
4. `bin/lib/policy-schema.js`'s `release-hook` and `release-train` entries are both `core: false` and each carry a non-empty `summary`; `tests/policy-schema-metadata.test.js` passes with both included, and confirms this unit adds no new `core: true` key (a relative check against the schema's existing core count, not a hardcoded absolute number that would need updating whenever an unrelated key changes tier).
5. `.claude-tweaks/policy.yml` after a fresh bootstrap contains both `release-hook` and `release-train` as commented-out rows (not active values), consistent with how other non-core keys are seeded at bootstrap time.
6. Re-running init on a repo where the previously-detected conflicting tool has since been removed no longer reports `conflict` and proceeds to write the three files on that subsequent run.
7. Re-running init a second time on a repo this same step already bootstrapped (the `already-bootstrapped` verdict) writes nothing and does not error, clobber, or duplicate the existing files — proving the idempotent no-op path, distinct from AC6's conflict-cleared path.
8. `.release-please-manifest.json`'s seeded version, on a fixture with tags `v1.9.0` and `v1.10.0` both present, resolves to `1.10.0` (semver precedence) — proving the comparator is semver-aware, not a lexicographic string sort that would incorrectly prefer `1.9.0`.

## Technical Approach

The bootstrap step depends on `step-20-integration-model.md`'s output because the engine choice (`pr-first` → release-please workflow + config, `local-merge` → config only, no workflow file) is exactly the `integration-model` policy value — this unit introduces no new engine-selection key of its own (design doc stance 4). Detection is deliberately a purpose-built presence check rather than a forced fit into `_shared/existing-convention-detection.md`'s genre-grammar procedure (see Current State) — the three-way vocabulary is reused, the underlying mechanics are not, since that file's ≥3-file floor and grammar-parse step solve a different problem (naming-convention agreement across many files) than "does exactly one of these markers exist."

## Gotchas

- Neither `release-hook` nor `release-train` is a Manifesto lever (the design doc says so explicitly), so `auto-mode-contract.md`'s five-site policy-lever checklist does not apply to this unit — do not add Manifesto wiring for these two keys.
- Both new keys are non-core by design — a schema change that accidentally promotes one to core would silently widen what the Manifesto surfaces by default; AC4's check is phrased relative to the schema's existing core count so it stays correct even if an unrelated future change alters that count for a different reason.
- Conflict detection's refusal is deliberate product scope, not a gap to fill later: the design doc explicitly treats coexisting with semantic-release/changesets/a foreign release-please config as the failure mode being designed against, not a feature to add support for. Manual `v*` tags alone are explicitly excluded from conflict evidence (Deliverables) — a project that already tags releases by hand is exactly the common case this bootstrap step exists to onboard, not a conflict to refuse.
- `step-21-release.md` branches on the `integration-model` value (pr-first vs. local-merge) — `tests/integration-model.test.js`'s existing consumer-citation check scans every file mentioning `integration-model` and fails if it doesn't cite `_shared/integration-model.md`'s consumer section. Write that citation into this new file rather than leaving it implicit; no new test is needed, the existing generic scan already covers a newly-added file automatically.

## Build deviations (Beneficial — applied, /build Common Step 4.5)

- **Code twin + CLI.** The Key Files named prose only, but ACs 1-3 and 6-8 are fixture-shaped and AC 8 needs a semver comparator, so the step's whole decision lives in `plugin/bin/lib/init/release-bootstrap.js` (detection, stack table, seeding, renderers, `bootstrapRelease`) behind `plugin/bin/release-bootstrap.js` (one JSON line, exit 0 on every verdict); `step-21-release.md` calls the CLI. The prose stack table stays canonical, pinned to `RELEASE_STACK_TABLE` by `tests/init-release-bootstrap-conformance.test.js`.
- **`already-bootstrapped` requires both files.** Exactly as the Deliverable says (config *and* manifest present and matching) — a shaped config with no manifest is `fresh`, so a half-written bootstrap re-runs to completion instead of reading as done.
- **`release-hook` accepts whitespace.** The schema's generic `string` type rejects whitespace (a branch-name guard), which would have made `npm run deploy` silently resolve to nothing; the row carries `allowWhitespace: true`, honored by `isValidValue`.
- **Template section registered.** `## Releasing` is added to `PROJECT_AUTHORED_SECTIONS` in `plugin/bin/lib/init/claude-md-conformance.js`, which the existing template-conformance suites require for any new template section.
