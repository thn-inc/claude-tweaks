# 2251: Merge-time conventional subject and the `breaking` label

Surface: infra

## Overview

Today the plugin composes merge subjects/bodies at two integration points (pr-first `gh pr merge -t/-b` and local-merge `git merge --no-ff -m`) with no shared vocabulary — a human or subagent's free-form feature-branch commit text becomes the merge subject verbatim. This unit makes the merge subject **Conventional Commits**-shaped on both paths, written by the plugin at merge time rather than left to whatever the branch happened to contain, and introduces a `breaking` compatibility label so a `!`/`BREAKING CHANGE:` footer can be derived mechanically. It is the foundation the whole release-skill design depends on: release-please (Phase 4/5) reads exactly this vocabulary to compute version bumps and CHANGELOG entries, and the local engine (Phase 4) reads the identical grammar for byte-compatible output.

The composer is a single new module (`bin/lib/release/subject.js`) called from every merge site so the mapping (`type:feature` → `feat`, `type:bug` → `fix`, `type:task` → `chore`, `breaking` → `!` suffix + `BREAKING CHANGE:` footer) lives in exactly one place.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- Implementing release-please or the local release engine itself — this unit only produces the conventional-commit vocabulary those engines will read (Phase 4/5, tracked separately).
- Inferring `breaking` from diff content or LLM judgment — the label is stamped only by `/specify` shaping mode reading explicit acceptance-criteria language, or set by hand. A missed breaking change is an accepted risk (design doc's Risks section), not something this unit's logic tries to detect automatically.
- Changing squash-vs-`--no-ff` policy per project — pr-first squashes and local-merge stays `--no-ff` are both already-decided defaults (see Gotchas); this unit does not add a policy lever to change that pairing.
- Sanitizing or normalizing an already-malformed title (an existing conventional-style prefix, a stray `(#N)` suffix already present, control characters) — `composeSubject` trusts the record title is clean free-form text, the same trust boundary the rest of this repo's merge tooling already extends to record titles.
- Stamping `breaking` on a build reached via `/claude-tweaks:build {design-doc-path}` (bypassing `/specify` entirely) — only `/specify` shaping mode's stamping rule (Deliverable 6) infers `breaking` from acceptance-criteria language. A design-doc-direct build leaves the label unstamped, which reads as "not breaking" — the same accepted-risk default this unit's other Non-Goal already states for diff-inferred detection, extended to this second entry path.

## Acceptance Criteria

1. A pr-first merge of a `type:feature` record #N lands on the integration branch as exactly one commit whose subject is `feat: {title} (#N)` — provable via `git log --first-parent -1 --format=%s` in an integration test fixture.
2. A `breaking`-labelled record's merge subject carries the `!` suffix (`feat!: …`) and the merge commit body ends with a `BREAKING CHANGE: {note}` line sourced from the record's stated migration note.
3. `composeSubject` truncates a title long enough to exceed 72 characters total (word-boundary cut, `…` appended) while always preserving the literal `(#{number})` suffix intact (never truncated away); the `!` breaking suffix, when present, is counted inside the 72-character budget before truncation runs.
4. `plugin/skills/_shared/work-record.md`'s Compatibility row and `record.js`'s facet accessor round-trip: a record labelled `breaking` reads back `facets.breaking === true`; an unlabelled record reads back `false` (never `undefined`), matching the presence-only convention.
5. The four local-merge sites (`local-merge-auto-finish.md:114`, `auto-merge-short-circuit.md:218`, `settle-and-merge.md:330`, `worktree-merge.md:63`) all source their `-m` subject from `composeSubject`, not four independent compositions — a grep for the prior free-form pattern at each site returns zero matches outside historical references.
6. `pr-first-merge.md`'s byte count after this edit is smaller than before the edit, or grows by no more than 500 bytes — net-small, so it does not collide with #2002's separate byte-ceiling work on the same file, verified by the mechanical byte-ceiling test (see Gotchas).
7. `composeSubject` throws a usage error (never emits a malformed subject) when called with `breaking: true` and an empty `migrationNote`, and when called with a `type` that isn't one of `feature`/`bug`/`task`.

## Technical Approach

The composer is deliberately one new module rather than four independent edits, because release-please (Phase 4) and the local engine (Phase 4) both need to parse this exact grammar back out later — a single source of truth for subject shape means the parser side only has to trust one writer. `--squash` (not `--merge`) is required on the pr-first path specifically because release-please walks every commit reachable since the last tag, not first-parent only; a branch commit that happens to look conventional would otherwise become its own spurious CHANGELOG bullet and could nudge the computed bump (design doc stance 3). Local-merge stays `--no-ff` because the local engine reads `--first-parent`, so branch-commit noise never reaches it — the two merge strategies are paired with their respective reader semantics, not a stylistic choice.

The `breaking` label is presence-only (no `breaking:high`/`breaking:low` tiers) because the only downstream consumer, `composeSubject`, needs a boolean, and `/specify`'s stamping rule reads it from acceptance-criteria language that is itself binary (does this AC name a contract change or not) — a tiered axis would have no consumer to read the extra granularity.

## Gotchas

- `pr-first-merge.md` is 30,404 bytes today and open record #2002 is separately bringing the composed merge bundle under the 40 KB composed-bytes ceiling — coordinate rather than fight that budget; this unit's edit must be net-small. Sequencing: whichever of this unit and #2002 lands second re-baselines its own byte accounting against the file's *then-current* size (not the 30,404-byte figure quoted here), so AC 6's mechanical byte-ceiling test measures the live file, never a stale constant. **Related:** #2002.
- The pr-first/`--squash` and local-merge/`--no-ff` pairing is deliberate, not incidental: release-please reads every reachable commit since the last tag (not first-parent), so squash is what keeps main to one conventional commit per PR; the local engine reads `--first-parent`, so `--no-ff` never leaks branch-commit noise into it. Changing one without the other breaks the grammar the later phases depend on.
- **Accepted interim risk:** squashing changes reconcile's branch-pruning proof — `bin/lib/reconcile/prune-remote.js:68` currently skips a branch that is not cherry-equivalent, and squash commits have different patch ids than the branch commits they came from, so remote pruning silently stops working for squash-merged branches for as long as this unit is landed without unit 2 (#2252, `Reconcile under squash`). This unit does not touch reconcile itself. The window is bounded, not open-ended: unit 2 is already queued directly behind this one (`Blocked by` this unit, no other blocker), so the accepted risk is "reconcile under-prunes for the duration between this unit's merge and unit 2's merge," not an indefinite gap — land the two close together rather than treating unit 2 as optional follow-up work.
- The `type:task` → `chore` mapping is deliberate: release-please's default config treats `chore` as invisible to changelog/bump (unless it's the release commit itself), matching this repo's own taxonomy where `type:task` records are maintenance work, not user-facing capability.
