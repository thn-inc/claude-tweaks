# 2255: Release preflight fact pack `bin/release-preflight.js`

Surface: infra

## Overview

The `/claude-tweaks:release` skill's Step 1 needs a single fact pack gathering everything the console renders (engine, unreleased commits, proposed version, open release PR state, CI status, hook status) before any of the skill's own decision logic runs. Splitting this into its own anchored, read-only CLI — rather than inlining the gathering into the skill's own SKILL.md — keeps the skill's own file agent-sized and follows the same `run-directory-fact-packs` discipline every other pipeline-phase fact pack in this repo already uses.

**Complexity:** Low
**Estimated tasks:** 5

## Non-Goals

- Any decision logic, console rendering, or mutation — this unit is read-only fact-gathering only. The `/claude-tweaks:release` skill itself (a separate, later unit) consumes this pack's output.
- Local-merge-specific fields beyond what both engines share — `releasePr` and `ciTip` are meaningful primarily under pr-first; under local-merge they resolve to `{ok: true, value: 'none'}`/`{ok: true, value: 'n/a'}` rather than being omitted, so every consumer can read the same field shape regardless of engine.

## Current State

- `run-directory-fact-packs` (skill): the canonical pattern this unit follows — anchored read-only CLI, `{ok, value | error}` envelope per field, 0/2/3 exit vocabulary, location/freshness/phase trace obligations.
- No `bin/release-preflight.js` or `bin/lib/release-preflight/` exist yet.
- `_shared/pipeline-run-dir.md`: the resolution order this unit's run-dir-or-scratch write decision follows — already used by other fact packs in this repo.
- `plugin/bin/lib/issues/record.js`: the conventional-commit-adjacent parsing this unit's `unreleased` field reuses (it needs the same first-parent-commits-since-tag walk unit 4's `commits.js` performs, read-only here rather than as a release action).

## Deliverables

- [ ] `plugin/bin/release-preflight.js` — `run(argv, deps)` CLI entry point per `gh-api-module-pattern`'s contract; anchored to the resolved run directory (or the scratch dir when none exists) per `run-directory-fact-packs`.
- [ ] `plugin/bin/lib/release-preflight/pack.js` — gathers each field as an independent `{ok, value} | {ok: false, error}` envelope, never letting one field's failure abort the others:
  - `engine` — `pr-first` or `local-merge`, read from the `integration-model` policy value via the same policy-schema reader every other consumer of that key already uses (`_shared/work-record-config.md`'s config-key table). An unset or unresolvable `integration-model` value resolves this field to `{ok: false, error: 'integration-model unresolved'}` rather than guessing — every other field that depends on `engine` (`releasePr`, `hook`) also degrades to `{ok: false, error: 'engine unresolved'}` in that case, since neither branch can run.
  - `lastTag` — the most recent `v*` tag reachable from the integration branch tip.
  - `unreleased` — first-parent commits since `lastTag`, each with its conventional-commit parse (type, breaking marker, subject) — reuses the same header regex unit 4's `commits.js` defines, read-only here (no bump computed, no files written).
  - `proposedVersion` — the semver bump `unreleased`'s commit set implies, using the same precedence unit 4's `bump.js` defines.
  - `releasePr` — pr-first: the open release-please PR's number/state/mergeable, or the literal string `none` when no release PR is open. local-merge: `none`.
  - `ciTip` — the status of checks on the integration branch's current tip commit.
  - `openReleasePrConflict` — `true` when the open release PR's most recent commit on the PR branch was authored by anyone other than the release-please bot (`github-actions[bot]`, or the app identity the pinned `googleapis/release-please-action` runs as) — a mechanical, checkable signal: a human-edited release PR always carries at least one non-bot commit on top of the bot's own render. `false` when every commit on the PR branch is bot-authored, or when no release PR is open (mirrors `releasePr`'s `none` case).
  - `hook` — `true` when the pr-first `release: published` workflow file is present, or the `release-hook` policy key is set under local-merge; `false` otherwise.
- [ ] Field envelope shape: every field above is `{ok: true, value}` or `{ok: false, error}` — never a bare value and never a thrown exception that aborts the whole pack.
- [ ] Written to `$PIPELINE_RUN_DIR/release-preflight.json` when a run directory is resolved, else the session scratch dir — per `run-directory-fact-packs`'s location rule.
- [ ] Exit vocabulary: `0` pack written successfully (regardless of individual field `ok`/`error` mix — a degraded field is not a CLI failure), `2` usage error, `3` could not resolve a git repository / no `origin` / not inside a valid checkout at all (a structural precondition failure, distinct from any one field degrading).
- [ ] `tests/bin-lib/release-preflight/pack.test.js` — `run(argv, deps)` fake-runner unit tests: one case per field's `ok`/`error` shape, plus the pr-first vs local-merge branching for `releasePr`/`hook`.
- [ ] `docs/plugin-structure.md` — add this CLI's row to the CLI list, alongside unit 4's.

## Acceptance Criteria

1. On a fixture repo with an unreleased `feat:` commit since the last tag: the written pack's `proposedVersion.value` is a minor bump over `lastTag.value`, and `unreleased.value` lists that commit with its parsed type.
2. On a fixture repo with zero commits since the last tag: `unreleased.value` is an empty array and `proposedVersion.ok` is `false` with an error naming "nothing to release" (this pack never itself exits 3 for that case — exit 3 is reserved for a structural precondition failure, not an empty-but-valid pack; the empty state is a normal, successfully-written pack).
3. A field that fails independently (e.g., no `origin` remote configured, so `ciTip` cannot resolve) still allows every other field to resolve and be written — the pack file contains `ciTip: {ok: false, error: ...}` alongside successfully-resolved sibling fields, not a thrown exception that drops the whole pack.
4. When `$PIPELINE_RUN_DIR` is set, the pack is written to `$PIPELINE_RUN_DIR/release-preflight.json`; when unset, it is written to the session scratch dir instead — both paths are exercised by the test suite.
5. Under `local-merge`, `releasePr.value` is the literal string `none` and `hook.value` reflects the `release-hook` policy key's presence, not a workflow-file check.
6. On a fixture repo with `integration-model` unset or unresolvable, `engine.ok` is `false` and both `releasePr.ok` and `hook.ok` are also `false` (each naming `"engine unresolved"`) — proving the field degrades explicitly rather than silently guessing an engine.
7. On an open release PR whose most recent commit is authored by a non-bot identity, `openReleasePrConflict.value` is `true`; on the same PR with only bot-authored commits, it is `false` — both branches of the detection are exercised by the test suite.
8. Under `local-merge`, the identical fixture from AC1 (one unreleased `feat:` commit since the last tag) produces the same `unreleased.value`/`proposedVersion.value` shape as the pr-first case — proving these two fields are engine-agnostic, not silently pr-first-only.

## Technical Approach

This unit is deliberately narrow — a read-only anchored CLI, no writes beyond its own fact-pack file — following `run-directory-fact-packs`'s existing discipline exactly (the same shape `preflight.json`/`timing.json`/`console.json` already use elsewhere in this repo's pipeline run directories) rather than inventing a new envelope convention. Splitting this out from the `/claude-tweaks:release` skill itself (rather than inlining Step 1's gathering into `SKILL.md`) is a direct response to file-size pressure: the skill's own 8-part structure plus three sub-files is already substantial, and folding a multi-field fact-gathering procedure into it would push it toward the same byte-ceiling problems `pr-first-merge.md` and `tidy/scan-procedures.md` are already managing elsewhere in this decomposition.

### Data / API Surface

- Output file shape (`release-preflight.json`): `{ engine: Envelope, lastTag: Envelope, unreleased: Envelope, proposedVersion: Envelope, releasePr: Envelope, ciTip: Envelope, openReleasePrConflict: Envelope, hook: Envelope }` where `Envelope = {ok: true, value: any} | {ok: false, error: string}`.

### Key Files

- `plugin/bin/release-preflight.js` — new; CLI entry point.
- `plugin/bin/lib/release-preflight/pack.js` — new; the field-gathering logic.
- `tests/bin-lib/release-preflight/pack.test.js` — new; fake-runner unit tests.

## Gotchas

- This unit reuses unit 4's conventional-commit regex and bump precedence *by reference* (the same logic, applied read-only) — reading unit 4's module for its regex/precedence definition doesn't require unit 4's PR to have merged first (static reference content, same as unit 4's own citation of unit 3's stack table), but do not let the two modules' parsing drift apart; if `bin/lib/release-local/commits.js`'s regex changes after this unit ships, this unit's own copy (or a shared extraction, whichever the implementer chooses) must move with it.
- **Related:** #1781, #1853, #1863, #1893, #1980, #1981, #1983, #1984 — other open records touching `docs/plugin-structure.md`; re-read that file's current state before appending this unit's row.
- A degraded field (`ok: false`) is not the same as the whole CLI failing (exit non-zero) — `run-directory-fact-packs`'s own contract is explicit that per-field degradation and CLI exit status are independent signals; do not conflate them.
- The run-dir-or-scratch fallback (Deliverables) is the documented default `run-directory-fact-packs` itself specifies for a CLI invoked with no resolved run directory — it is not a bypass of that pattern's anchoring guard, it *is* what the guard permits when no run directory exists to anchor to. Confirm against that skill's own text before assuming a special case is needed here.

## Build deviations (Beneficial — applied, /build Common Step 4.5)

- **Exit 3 is structural only** — not inside a git checkout, or a run directory that does not resolve under the main checkout; "no origin" degrades `ciTip`/`releasePr` as data with exit 0, per AC 3 (ruling 1; the wording gap is staged as build-deviation-1).
- **`engine` reads the explicit `integration-model` policy value only** — no forge detection, so AC 6's "never guess" holds (ruling 2).
- **The tip is `origin/{branch}` when that ref exists locally, else `refs/heads/{branch}`**, `{branch}` from `integration-branch` else `main`; every git-derived value carries `tipRef` (ruling 3).
- **A release PR** is an open PR on a `release-please--` head branch or titled `chore(…): release <version>` (rulings 4, 9); **a bot author** carries a `[bot]` suffix on login/name or a `[bot]@users.noreply.github.com` email (ruling 5).
- **`hook`** under pr-first is a workflow declaring a `release:` trigger with `published`; under local-merge a `release-hook` set to anything but `false/off/none/null` (ruling 6).
- **No prior tag** degrades `lastTag`; `unreleased` covers the full first-parent history and `proposedVersion` bases on `.release-please-manifest.json` else `0.0.0` — the local engine's first-release rule (ruling 7).
- **Reuse, not a copy**: `release-local/commits.js` gained an optional `ref` (default `HEAD`) instead of a second parser; `wrap-up/pack.js` exports `withTimeout` so the three packs share one bound (ruling 8).
- **Run-dir resolution**: `--run`, else `PIPELINE_RUN_DIR`, else a fresh scratch directory under the system temp dir (path on stderr) — the pattern's documented fallback, both explicit sources anchored like the sibling packs.
