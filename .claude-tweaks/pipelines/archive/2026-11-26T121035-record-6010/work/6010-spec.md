# 6010: Record each role's model and effort in the run manifest

Surface: backend
Risk-flags: public-contract

## Overview

Adds, to a run's `manifest.json`, the model and effort each role in the run actually ran at: the session that walked the run, implementers, task reviewers, lens reviewers, the whole-branch and plan reviewers, and, in the driver lane, the implementer, reviewer, merge-check and acceptance workers. The design (`docs/superpowers/specs/2026-11-18-pipeline-economy-design.md`, `## Phase 11`) lists "lane, model and effort per role" among the run facts; lane shipped with #5903, and this record adds the rest. Phases 9, 14 and 15 change which model and effort each role runs at and judge each change over 20 runs, so each run has to record what each role ran at, not what policy asked for: the design's own evidence found that effort followed the session rather than the profile for 60% of subagent turns.

**Complexity:** Medium
**Estimated tasks:** 5

## Non-Goals

- Setting a role's model or effort. #5941 and #5942 set effort on launches; this record only records it.
- Tokens and cost: record #6009 "Record a run's tokens by model, list-price cost and minutes in its manifest", which this one extends.
- Dispatch reading the field: a change in thn-inc/dispatch, as for the cost fields.
- Reclassifying the role vocabulary. Roles come from the existing `roleOf` table in `plugin/bin/lib/timing/derive.js` and the driver's role names; an agent `roleOf` cannot place stays `unlabelled`.

## Deliverables

- [ ] `readUsage` additively returns each row's effort as an `effort` key present only on a row whose request recorded one (a row with none has no `effort` key, and readers treat a missing key as `null`; see the Decision below), with no change to the fields its callers read, and the subagent dispatch items carry an `efforts` tally (`{ "<level>": turns }`) beside `rawModel`.
- [ ] `plugin/bin/lib/run-manifest/roles.js` (new): `deriveRoles({ timing, events })` returns `roles`: `{ "<role>": { agents, models: { "<model id>": agents }, efforts: { "<level>": turns } } }`. Session lanes: one `session` role from the main-session rows (`agents: 1`, its model ids and efforts; subagent rows are excluded), plus one entry per `roleOf` role over the dispatch items, where `agents` counts every dispatch item, an agent whose transcript could not be read counts in `agents` under model `unknown` and adds no efforts, and an agent's model is the `rawModel` `aggregateDispatches` already derives. Driver lane: one entry per driver role from the worker step events (the step event the launch writes to `events.jsonl`, carrying `role`, the launched `model`, `usage` and `sessionId`): model and effort come from the worker's transcript when its `sessionId` resolves (what ran), else `model` from the launch and effort from the launch's `--effort` when set, else `unknown`. `manifest.lane` selects the source, so a run is single-lane and `roles` holds one lane's names: a `driver` run reads events only, every other lane reads `timing` only. A transcript effort outside `low`/`medium`/`high`/`max` is kept as the string seen, since the set is illustrative, and a `roles` value that fails the shape check leaves the existing manifest untouched with one stderr line.
- [ ] `fillRunManifest` accepts `roles`, fill-only-null with a shape check, in the close-path fill record #6009 adds.
- [ ] `docs/reference/run-manifest.md` documents `roles`: the role names and where each comes from, that `efforts` counts turns while `models` counts agents, and that `unknown` means the transcript recorded no effort.
- [ ] Tests: `tests/bin-lib/run-manifest/roles.test.js`, and transcript fixtures with and without the effort field.

## Acceptance Criteria

1. `readUsage` over a fixture transcript whose assistant lines carry an effort of `high` on two turns and `medium` on one returns those efforts per row; over a fixture with no effort field no row carries an `effort` key (so `row.effort ?? null` is `null` per row), and every existing `readUsage` test passes unchanged.
2. `deriveRoles` over a fixture timing with three implementer dispatches (two on `claude-sonnet-5-5` at `medium`, one on `claude-opus-5-5` at `high`) and one dispatch described `lens 3a` returns `implementer: { agents: 3, models: { "claude-sonnet-5-5": 2, "claude-opus-5-5": 1 }, efforts: {…} }` with the effort turn counts from the fixtures, and `lens reviewer: { agents: 1, … }`.
3. A dispatch whose description no `roleOf` pattern matches counts under `unlabelled`.
4. A driver-lane fixture `events.jsonl` with an implementer launch on `sonnet` and a reviewer launch on `opus`, neither with an effort, gives `implementer` and `reviewer` entries with those models and `efforts: { unknown: 1 }` each when no worker transcript resolves.
5. After the close path fills a fixture run, `manifest.json` carries `roles` and every other field unchanged; closing again changes nothing.
6. The main session appears as `session` with its own model ids and effort counts.

## Release Note

Every pipeline run now records the model and reasoning effort each of its roles actually ran at in its run manifest.

## Technical Approach

Record what ran, read from the transcripts and driver events, not from policy: the same data the timing pass already reads, plus one more field per transcript line. Roles reuse `roleOf` so the manifest and `timing.json`'s `byRole` buckets name roles the same way.

Decided while specifying: `efforts` counts turns, because one agent can change effort between turns and the design's effort evidence is per turn; `models` counts agents, since an agent runs on one model; a role with no recorded effort says `unknown` rather than inferring it from the profile, since the evidence shows the profile and the recorded effort differ.

**Decision** (2026-11-26, plan-review question on this record, Reading B): `effort` is present only on a `readUsage` row whose request recorded an effort; a row with none carries no `effort` key, and every reader treats a missing key as `null`. This follows `readUsage`'s existing `asks`/`answers` precedent (#5556) and the Gotcha that an existing row's shape never changes, so the whole-row `deepEqual` in `tests/bin-lib/timing/transcript.test.js` stays unchanged. AC1 and Deliverable 1 above are amended to match. Where this record's Current State is contradicted by what the transcripts or driver events on disk actually hold (for example, effort is recorded on `type: "api-request"` lines at `params.output_config.effort`, not on assistant lines, in Claude Code 2.1.302 to 2.1.325; driver step lines carry no `role` field, so the role comes from the step name; `timing.json` holds no main-session rows), the build follows what is on disk, logs it as a reversed premise and states the source in the test fixture's header and `docs/reference/run-manifest.md`. Such a contradiction is not a needs-human question, as long as the Deliverables and Acceptance Criteria still hold.

## Gotchas

- The effort field path is confirmed on this checkout (Current State), but it is Claude Code's transcript format and can change: Task 0 re-reads one main-session and one subagent transcript, records the field path, values and Claude Code version in the test fixture's header, and a test fails when a fixture transcript with assistant turns yields no effort at all, so a format change shows as a red test and not as a quiet `unknown` everywhere. Where a subagent transcript lacks the field, record `unknown` and say so in `docs/reference/run-manifest.md`.
- `roleOf`'s patterns place the description `lens 3a` under `lens reviewer` (`^((review|delta) )?lens \d`, `plugin/bin/lib/timing/derive.js`), so AC2's fixture holds.
- Driver role names are a manifest contract once this lands: renaming one in `plugin/bin/lib/driver/roles.js` changes `roles` keys, so a rename names this record in its description.
- #5967 also adds fields to `readUsage` (`message.id`, the cache-write split). Add the effort field the same additive way and rebase on it; never rename or reshape an existing row field.
- Driver role names must come from `plugin/bin/lib/driver/roles.js`, not a second list typed here.
- A worker transcript lives under the worker's own session id; resolving it is optional. A worker whose transcript is not found records `unknown`, never a guessed effort.
