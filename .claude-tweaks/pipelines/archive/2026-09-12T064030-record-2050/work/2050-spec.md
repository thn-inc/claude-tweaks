# 2050: Task-tool subagents can't be redirected to a pre-existing worktree via EnterWorktree(path=) in this harness

# Reflect — staged finding 1

**Category:** tangential

Origin: reflect full mode from #1875
Defer-reason: tangential

## Current State

`dispatch/task-prompt.md`'s two-call contract assumes the dispatching session enters a group's
worktree once and both Task calls transparently inherit that cwd. In this remote/cloud harness
that assumption failed on this very run: the first Task call was launched with `isolation:
"worktree"`, which creates its own new worktree rather than having the dispatching session enter
one first (there is no Agent-tool parameter to pin a subagent's Bash sandbox to an
already-existing worktree path). The second Task call was then launched plainly and instructed to
call `EnterWorktree(path: ...)` to switch into the first call's worktree before starting work;
`EnterWorktree` reported success and updated the agent's logical cwd, but every subsequent Bash
call in that agent was refused by the worktree-isolation guard because its underlying execution
sandbox stayed hard-pinned to the dispatching session's own worktree — a lower-level restriction
`EnterWorktree`'s path-switch does not propagate through for a pinned subagent. The second call
reported `BLOCKED: worktree-inaccessible` and could do no work. The dispatching session had to
adapt by entering the target worktree itself and running `/claude-tweaks:flow #1875
review,polish,wrap-up` directly in its own thread instead of via a second Task call — which
forfeits the two-call contract's whole reason for existing (conversational isolation between
build and review, so review re-derives its verdict from artifacts rather than trusting the
build's own claims).

## Deliverables

- [ ] Confirm whether this is specific to the current Claude Code Remote / cloud-session
      execution model, or reproducible in other harnesses this plugin targets.
- [ ] If reproducible broadly: document the constraint in `dispatch/sequential-execution.md` or
      `task-prompt.md`, and decide on a supported adaptation — e.g. always running the second
      call inline in the dispatching session's own thread on this harness class, with an explicit
      note about the conversational-isolation cost this reintroduces — rather than leaving each
      dispatching session to rediscover and improvise the same workaround.
- [ ] If narrow (a specific harness quirk): file it as a known limitation with a detection
      signal dispatch can check before attempting the second Task call, so a future firing fails
      fast with a clear message instead of burning a full Task-call round-trip to discover it.

## Acceptance Criteria

1. A future dispatch firing on this harness class either avoids the failed pattern by
   construction, or fails with a clear, actionable message on the first attempt rather than a
   generic `BLOCKED: worktree-inaccessible` report.

## Gotchas

- **Deliverable 1 (confirm harness-specificity) is not empirically confirmed by this build.**
  This run was expressly policy-restricted from making any Task/Agent dispatch of its own (a
  sibling build in the same drain, working record #2067, had let a research-scoped fork exceed
  its stated read-only remit), and reproducing #1875's exact failure requires launching a real
  two-call Task dispatch — the same mechanism the record is about. Rather than fabricate a probe
  result, this build read `EnterWorktree`'s own current tool schema/documentation directly
  (no live call) and found language that, read literally, already describes the redirect #1875
  found impossible: a `path`-based switch "also works ... from agents whose working directory
  was pinned at launch (subagent isolation or explicit cwd)," scoped to "only ... this agent, not
  the parent session." Whether that reflects a harness fix shipped since #1875, or a
  documented-but-not-yet-reliable capability, is genuinely unconfirmed — no live two-call
  dispatch was run to check either way. Treat this as an open question a future dispatch firing
  that hits this exact shape should resolve (see the Removal condition on the new
  `docs/incident-log.md` entry below).
- **What this build did instead:** documented the incident and the current-vs-historical
  discrepancy in `docs/incident-log.md` (`IL-155`), added a corresponding rule to `docs/donts.md`,
  and added a caution paragraph to `dispatch/sequential-execution.md`'s existing `#447`
  cwd-pinned-dispatcher section — the section that already owns the sanctioned alternative (the
  `cd {worktree-path} &&` prefix mechanism) for exactly this "second call needs the first call's
  worktree" situation. This satisfies Acceptance Criterion 1's first branch ("avoids the failed
  pattern by construction") for the documented dispatch contract, which never used
  `isolation: "worktree"` or a joining `EnterWorktree(path=)` to begin with — the gap closed here
  is making that avoidance explicit and citable rather than something a future dispatching
  session has to rediscover under pressure, the same way #1875 did.
- **Deliverable 3's path (narrow limitation, detection signal) was chosen over deliverable 2's**
  (broad reproducibility, contract rewrite) because the underlying observation is a single
  incident (#1875) on one harness class, and this build cannot broaden or narrow that evidence
  base without the same forbidden live dispatch. The "detection signal" deliverable 3 asks for is
  the caution paragraph itself, read *before* attempting the pattern, plus the `IL-155` citation
  telling a future agent exactly what failed last time and what remains unverified — rather than
  a runtime check, since the current dispatch contract never attempts this pattern and so has
  nothing to detect at runtime.
