# 2257: Release lifecycle wiring

Surface: infra

## Overview

Once `/claude-tweaks:release` (unit 6) exists, every lifecycle skill that currently offers a "Cut the release" Next Action row with nothing to hand off to needs to actually point at it — and the release-tracking logic scattered across `pr-first-merge-post-merge.md` and `tidy/scan-procedures.md`'s residue probe needs to move from `release.js status`'s bump-commit walk to the tag-based model this whole design establishes. This unit is the wiring pass: every reference, diagram, and probe that names the release process gets updated to the new reality.

**Complexity:** High
**Estimated tasks:** 8

## Non-Goals

- Building or changing `/claude-tweaks:release` itself (unit 6) or either engine (units 3/4) — this unit only wires existing lifecycle skills to reference what those units produce.
- This repo's own migration — that is Phase 8 (a separate, later unit); this unit changes the plugin's shipped skill prose, not this repo's own release configuration.

## Technical Approach

`git describe --contains {sha}` resolves purely from **tag ancestry** in the commit graph — it walks forward from `{sha}` to the nearest reachable tag, regardless of that commit's own subject text or whether it was produced by a squash or a merge commit. This unit's actual precondition is therefore not unit 1's subject-composer format — it is simply that a `v*` tag exists on the integration branch reachable forward from the merge commit being looked up, which is true for any release cut after this design's tagging convention (design doc stance 1) takes effect, independent of unit 1 specifically. This unit is not `Blocked by` unit 1 for that reason (correcting an earlier draft's conflated rationale); it remains `Blocked by` unit 6 because it wires lifecycle skills to reference a skill that must exist first. Ambiguity handling: `git describe --tags --contains --first-parent {sha}` restricted to first-parent ancestry returns at most one tag name in the normal case; a commit not yet contained in any tag (unreleased on main) returns a non-zero exit, read as the literal string `unreleased` per Deliverables above — never treated as an error.

The `scan-procedures.md` net-zero constraint is a real design pressure, not a nice-to-have: the file is already past the 40 KB warning tier documented in `docs/plugin-structure.md`, so this unit's generalization edit should look for prose it can delete (the old this-repo-specific description of the triple check) to offset whatever the generalized version needs to add.

**"Bootstrap version" anchor.** The generalized residue probe (Deliverables) needs a per-project anchor for "every tag at or after X" — defined as the version value `.release-please-manifest.json` held at the commit that first introduced that file to the repo (unit 3's bootstrap step writing it for the first time). This requires no separate marker file: `git log --diff-filter=A --format=%H -- .release-please-manifest.json` finds that commit, and the manifest's content at that revision is the anchor value. For this repo specifically, unit 9's own boundary comment in `CHANGELOG.md` names the same version redundantly for human readers, but the probe's mechanical anchor is always the manifest's first-commit value, not the comment.
