# 1769: specify: decomposition states cross-unit premises as facts without verification

Surface: infra

## Current State

`/claude-tweaks:specify`'s decomposition path composes each sub-issue's `## Current State` and `### Key Files` from Step 1's landscape pass (`plugin/skills/specify/decomposition-mode.md`, Step 1 item 5 — "identify existing files, schemas, APIs, and patterns that the new work will build on") and writes them in the same declarative voice whether a claim was observed in the tree or inferred from the design doc. Nothing between composition and `gh issue create` checks a current-state claim against the actual checkout. The one verification step that exists at composition time is `_shared/dependency-narration-check.md` (cited from `shaping-mode.md` only, not from the decomposition loop), and it catches a different defect: narrating another record's unmerged follow-up as landed. Shaping mode also has a one-paragraph "cheap sanity check" for human-filed defect reports that name a file, function, or error string (`plugin/skills/specify/shaping-mode.md`, the paragraph above its Dependency-narration check subsection) — decomposition has no equivalent, and neither path distinguishes a verified observation from an assumption in the written body.

Observed cost (feedback from a private project's four-spec decomposition on plugin 6.114.0): one spec asserted a dependency subsystem was absent and would need stubbing when it was present on the branch; another justified its trigger condition with "an existing module already reads this field for these rows" when the module never read the field. Both claims were falsifiable with one grep. Both survived to build and final review respectively, where the build phase re-derived the true state and the review ledgered a write-only data gap as a follow-up record.

`spec-template.md` already has the vocabulary for the unverifiable case at a different scope: its "Empirical Premise-Check Deliverables" section handles assumptions about third-party CLI/API behavior via a blocking Task 0, and its self-check list ("No Placeholders") rejects files referenced but not defined in `Key Files`. It has no rule that a `## Current State` claim about *this repo's* existing code must carry evidence or be marked as an assumption. `/claude-tweaks:build` hands "the full spec content (including Current State, Gotchas, and acceptance criteria)" to `/superpowers:writing-plans` (`plugin/skills/build/SKILL.md`, the writing-plans handoff) and treats every sentence as a constraint.

Related but distinct: #490 (closed) propagates *planned* sibling changes into Key Files via `crossReferenceKeyFiles`; this record is about the truth of *current-state* claims. #178 (closed wontfix) proposed a `falsified` vocabulary for brainstorming briefs, not for composed spec bodies.

## Deliverables

- [ ] **Premise verification step in the decomposition loop.** In `plugin/skills/specify/record-creation-subissues.md`'s per-sub-issue Body composition — after the body is composed, before the Ceremony and Framing calls — add a bounded verification pass over the composed `## Current State` and `### Key Files`: every claim that a named file, module, subsystem, or symbol exists or is absent, or that a named module reads/writes/calls a named field or function, gets one `git ls-files`/`git grep -n -F` probe against the checkout the decomposition runs in. Caps stated in the prose so the pass stays one step (at most 2 probes per claim, at most 12 per sub-issue — the same cap shape `challenge/SKILL.md`'s bare-`#N` evidence search uses). A confirmed claim keeps its sentence and gains an inline citation (`path:line`, or the `git ls-files` hit for existence claims). A contradicted claim is rewritten to what the tree shows before the body is filed. The pass is a content judgment applied by the model, not a new `bin/` CLI.
- [ ] **`ASSUMPTION — verify at build` marker for unverifiable claims.** A claim the probe cannot settle at decomposition time (a sibling unit's not-yet-built output, an external system, a runtime behavior no grep reaches) moves out of `## Current State`'s declarative voice into a `## Gotchas` bullet with the literal prefix `ASSUMPTION — verify at build:` followed by the claim and what would confirm it. Define the marker once in `plugin/skills/specify/spec-template.md`'s `## Gotchas` section (one template bullet showing the shape), and add one line to its "No Placeholders" self-check list: a `## Current State`/`### Key Files` sentence asserting a fact about existing code with neither an evidence citation nor the marker is incomplete.
- [ ] **Share the check with shaping mode.** Hoist the rule into a new `plugin/skills/_shared/premise-verification.md` (what to probe, the caps, the citation form, the marker), cited from both `record-creation-subissues.md`'s new step and `shaping-mode.md`'s existing "cheap sanity check" paragraph (which becomes a one-sentence pointer plus its human-filed-defect-report delta). Add the `_shared` file's row to `docs/skill-graph.md` (owned by `/specify`, the only citing skill) per CLAUDE.md's stated-once rule.
- [ ] **Build-side consumer.** In `plugin/skills/build/SKILL.md`'s writing-plans handoff (the "Context to provide" list), add one bullet: every `ASSUMPTION — verify at build:` bullet in the spec's `## Gotchas` is verified against the worktree before `/superpowers:writing-plans` is invoked, and its outcome (confirmed / reversed, with the probe) is logged as one `decisions.md` line per `_shared/auto-decision-log.md`; a reversed assumption is surfaced in the plan's context as the corrected fact, not silently dropped.

## Original request

**Summary:** When `/claude-tweaks:specify` decomposes a design doc into N work-unit specs, each spec's Current State / Key Files sections state claims about sibling units and existing code as settled facts with no verification step — in one 4-spec decomposition two such premises were false and survived until build/final-review time.

**Kind:** Gap

**Affected component:** /claude-tweaks:specify (design-doc decomposition)

**Use case:**
Decomposing one design doc into four sequential work-unit specs in a private project. Two cross-unit premises were written as facts and were wrong:

1. One spec asserted a dependency subsystem was absent and would need stubbing — it was present on the branch the whole time; the build phase had to re-derive the true state before proceeding.
2. Another spec justified its trigger condition with "an existing module already reads this field for these rows" — the module never read the field at all; the final review found the produced data was write-only, and the gap had to be ledgered as a follow-up record.

Both claims were falsifiable with a grep in seconds. The gap: decomposition has no premise-verification step, and the spec format gives a verified observation and an unverified assumption the same voice, so downstream phases inherit errors as constraints.

Suggested directions: (a) verify each cross-unit/current-state claim against the actual tree at decomposition time (the same discipline the spec-research phase applies to UI claims) and cite the evidence; or (b) mark unverifiable claims explicitly as `ASSUMPTION — verify at build`, so the build phase treats them as inputs to check rather than facts to build on. Related but distinct from #490 (cross-referencing forward-declared sibling changes): this is about the truth of current-state claims, not the propagation of planned ones.

**Definition:** Clear

**Plugin version:** 6.114.0
