# 2538: wrap-up-pack / resolve-blockers / materialize / preflight-records: on a GitHub Enterprise remote the host is never derived, so every child gh call needs GH_HOST exported by hand

Surface: infra

## Current State

On a GitHub Enterprise remote, `wrap-up-pack.js`'s `unblocked` probe always reports `ok: false`, and `resolve-blockers.js`, `materialize.js`, and `preflight-records.js` fail with "Could not resolve to a Repository" unless the caller both exports `GH_HOST=<enterprise host>` and passes `--repo owner/name` — the plugin never derives host or repo from `origin`. #2425 fixed the `--repo` half of the pack probe; the `GH_HOST` half and the three sibling CLIs remain unfixed as of 6.123.0. Confirmed against the current files: none of `wrap-up-pack.js`/`resolve-blockers.js`/`materialize.js`/`preflight-records.js` reference `GH_HOST` or `nameWithOwner` today.

A private project hosted on a GitHub Enterprise host (origin `https://<enterprise-host>/<org>/<repo>.git`) running `/claude-tweaks:flow` with `work-backend: github-issues` hits this on every wrap-up: the fact pack's `unblocked` probe fails ("could not resolve owner/repo — pass --repo owner/name"), forcing the operator to re-run `resolve-blockers.js` by hand with `GH_HOST` exported and `--repo` passed; `materialize.js` fails the same way at every spec boundary even with `--repo` given, since `gh` never infers the host outside a clone.

## Deliverables

- [ ] Add a shared helper that derives `{host, ownerRepo}` once from `git remote get-url origin` (or `gh repo view --json nameWithOwner,url` run inside the checkout)
- [ ] Thread the derived `GH_HOST` env var and `--repo owner/name` flag into every child `gh` call in `wrap-up-pack.js`'s `unblocked` probe, `resolve-blockers.js`, `materialize.js`, and `preflight-records.js`
- [ ] Have each of the four CLIs print the derived repo/host so a mismatch is visible to the operator

## Acceptance Criteria

- [ ] On a GitHub Enterprise remote, `wrap-up-pack.js`'s `unblocked` probe, `resolve-blockers.js`, `materialize.js`, and `preflight-records.js` all resolve the correct repository with no manually exported `GH_HOST` or passed `--repo`
- [ ] Existing github.com-hosted behavior is unchanged (no regression when there's no enterprise host to derive)
- [ ] `npm test` passes, including new coverage for the derivation helper

## Technical Approach

Add one small derivation helper (host + owner/repo from `git remote get-url origin`, falling back to `gh repo view --json nameWithOwner,url` run inside the checkout) and call it once per invocation in each of the four CLIs, exporting `GH_HOST` and passing `--repo` to every child `gh` call those files make — the same shape #2425 already applied to `wrap-up-pack.js`'s `--repo` half, extended to cover `GH_HOST` there and both flags in the three sibling CLIs.

### Key Files

- `plugin/bin/wrap-up-pack.js` — the `unblocked` probe; already has partial `--repo` handling from #2425 to extend with `GH_HOST`
- `plugin/bin/resolve-blockers.js` — needs both `GH_HOST` and `--repo` derivation
- `plugin/bin/materialize.js` — needs both `GH_HOST` and `--repo` derivation
- `plugin/bin/preflight-records.js` — needs both `GH_HOST` and `--repo` derivation

## Gotchas

- `gh` does not infer the host outside a clone — a derived `GH_HOST` must be exported into the child process environment, not just computed and discarded.
- Keep the github.com case a true no-op: deriving and passing `--repo`/`GH_HOST` unconditionally must not change behavior (or introduce a new failure mode) for the common non-Enterprise case.
