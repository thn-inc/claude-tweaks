# 2561: compose-subject.js: `--json issueType` is rejected by gh 2.92 on GitHub Enterprise Server, so every pr-first merge subject fails to compose

Surface: infra

## Current State
`bin/compose-subject.js` (backed by `bin/lib/compose-subject.js`) always requests `gh issue view {N} --json number,title,body,labels,issueType`. Against a GitHub Enterprise Server host running gh 2.92.0, the server answers `Unknown JSON field: "issueType"` and the CLI process exits 3 before the script's own fallback logic — `typeOf`, which already knows how to derive a type from the `type:*` label — ever runs. `_shared/pr-first-merge.md` Step 3's `SUBJECT_EXPORTS=$(node compose-subject.js …) || exit 1` treats that non-zero exit as fatal, so every pr-first merge on this gh/GHES combination is blocked before a subject can compose at all.

A verified workaround exists: calling `bin/lib/compose-subject.js`'s exported `run(argv, deps)` with a custom `runner` that strips `,issueType` from the requested field list and separately injects `issueType` via a GraphQL query (`issue { issueType { name } }`) — which the same gh/GHES combination serves without error — produces a subject that merges normally.

## Deliverables
1. `compose-subject.js`'s `gh issue view` call no longer fails outright when the host rejects the `issueType` REST field — the failure is caught and treated as "native type unavailable," not as a fatal error.
2. When the REST `issueType` field is unavailable, the script falls back to whichever of these it already implements: the existing `typeOf` label-based derivation (`type:*` label), and/or a GraphQL fetch (`issue { issueType { name } }`) for the native type, in that preference order (label-based first, since it requires no extra request; GraphQL fetch when a native type is wanted and no `type:*` label is present).
3. The subject composes successfully end-to-end on a gh/GHES combination that rejects the REST `issueType` field, provided the target issue has either a `type:*` label or a native GraphQL-visible issue type.
4. If neither a `type:*` label nor a GraphQL-visible native type is available, the script still composes a subject (type omitted or defaulted), rather than exiting non-zero — matching the existing tolerance the script presumably already has for a genuinely typeless issue on a host where `issueType` REST works fine.

## Acceptance Criteria
1. Given a gh/GHES combination where `gh issue view {N} --json …,issueType` returns `Unknown JSON field: "issueType"` and exit 3, `compose-subject.js` does not exit non-zero for that reason alone — it retries or falls back instead of propagating the raw `gh` failure.
2. Given the same environment and a target issue carrying a `type:*` label, the composed subject reflects that label's type value.
3. Given the same environment and a target issue with no `type:*` label but a native issue type visible via the GraphQL `issue { issueType { name } }` query, the composed subject reflects the GraphQL-derived type value.
4. Given the same environment and a target issue with neither signal, `compose-subject.js` still exits 0 and produces a subject (with type omitted/defaulted), rather than failing the whole compose step.
5. On a gh/host combination where the REST `issueType` field IS supported (the common case, unaffected by this record), `compose-subject.js`'s existing behavior and output are unchanged — the fallback path only activates on the specific unknown-field failure, not unconditionally.
6. `_shared/pr-first-merge.md` Step 3's merge flow completes successfully (reaches the merge step) on a GHES host running gh 2.92.0, using a record with a `type:*` label.

## Technical Approach
- In `bin/lib/compose-subject.js`, wrap the `gh issue view` call (or the specific `--json` field request) so that an `Unknown JSON field: "issueType"` failure is caught and distinguished from other `gh` failures (e.g. by checking stderr content or exit semantics) rather than allowed to propagate as a generic fatal error.
- On catching that specific failure, retry the `gh issue view` call without `issueType` in the field list, then apply the fallback order: (a) existing `typeOf` label-based derivation from the labels already fetched, (b) a supplementary GraphQL query (`gh api graphql` with `issue { issueType { name } }`) to fetch the native type when no `type:*` label is present and a native type is still wanted.
- Ensure the retry/fallback path is injectable via the existing `run(argv, deps)` seam (per `gh-api-module-pattern` skill's runner convention) so it's testable with a fake runner that simulates the unknown-field rejection, matching the verified manual workaround already described in the record.
- Confirm `_shared/pr-first-merge.md` Step 3's `|| exit 1` still fires for genuine fatal failures (auth failure, issue not found) — the fix narrows what counts as fatal, it doesn't remove the guard.

### Key Files
- `plugin/bin/compose-subject.js` — CLI entry point; no logic change expected beyond what the lib function below handles.
- `plugin/bin/lib/compose-subject.js` — home of the `gh issue view` call, the `typeOf` fallback, and the `run(argv, deps)` seam; add the catch/retry/GraphQL-fallback logic here.
- `plugin/skills/_shared/pr-first-merge.md` — Step 3's `SUBJECT_EXPORTS=$(node compose-subject.js …) || exit 1` call site; no change expected if the fix keeps the exit code contract for genuine fatal failures, but verify.

## Gotchas
- The catch condition for "unknown field, retry without it" must key on the specific `Unknown JSON field: "issueType"` failure text (or an equivalent structured signal), not on `gh issue view` exit codes generally — a genuine auth or not-found failure must still propagate as fatal, per AC 6's implicit negative control.
- The GraphQL fallback query depends on the authenticated host actually exposing `issue { issueType { name } }` — the record's own repro confirms this works on the affected gh/GHES combination, but a host that also rejects the GraphQL shape needs the label-based fallback to still work standalone.
- Adding a retry adds a second `gh` invocation on the fallback path — acceptable for a merge-time script, but avoid retrying on every call when the REST field already works (AC 5's "unchanged on unaffected hosts" requirement).
