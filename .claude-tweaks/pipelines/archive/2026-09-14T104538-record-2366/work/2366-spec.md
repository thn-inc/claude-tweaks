# 2366: dispatch/task-prompt.md: first build,test call has no re-derive-from-artifacts check before reporting DONE

Surface: infra

## Current State

`plugin/skills/dispatch/task-prompt.md`'s two Task-call templates are asymmetric on report fidelity. The second call (`review,polish,wrap-up`) carries an explicit instruction, right before its `OUTPUT FORMAT` section:

> CRITICAL: your review step must re-derive its verdict from raw artifacts -- the actual diff, the actual test-output log in the run directory -- never from a prior claim, whether that claim lives in conversation ... or in a file the first call wrote (decisions.md, ledger entries, staged proposals). Treat every such file's claims as unverified until checked against the artifact it claims to summarize.

with a concrete artifact reference immediately after it (`verify.js --stamp-status`/`report.json` via `bin/lib/dispatch/artifact-verdict.js`'s `deriveTestVerdict`). The first call (`build,test`) has no equivalent instruction anywhere in its own fenced template — it goes straight from the ephemeral-dev-server note to `OUTPUT FORMAT (required)` with nothing between that requires its own `DONE`/`build-test-ok` claim to be checked against an actual artifact before being reported.

This asymmetry produced a real incident this session: a first-call report claimed "5/5 clean under load" with no supporting artifact in the run directory. It surfaced only because an unrelated sibling agent's own discrepancy report prompted the orchestrator to demand reconciliation — nothing in the first call's own template would have caught it otherwise. Measured this session: 2 of roughly 24 dispatched build/review reports (~8%) were later found unsupported or incomplete by independent re-verification.

## Deliverables

- Add a `CRITICAL` instruction to the first call's fenced template in `dispatch/task-prompt.md`, structurally mirroring the second call's (same wording pattern, same placement — immediately before `OUTPUT FORMAT (required)`): the first call's own `DONE`/`build-test-ok` claim must be backed by an actual artifact existing in the run directory at report time (the test-output log / `verify.js --stamp-status` + `report.json`, or whichever artifact the underlying `/claude-tweaks:flow build,test` invocation actually wrote), never asserted from narrative or memory of an earlier pass.
- Keep the instruction's scope accurate to what's different about the first call: unlike the second call (which distrusts a *prior* call's claim), the first call IS the producer — so the instruction should read as "confirm your own claim against the artifact you just produced," not copy the second call's "never trust a prior claim" framing verbatim where it doesn't fit.

## Acceptance Criteria

- [ ] `dispatch/task-prompt.md`'s first-call fenced template contains a `CRITICAL` instruction, placed immediately before its `OUTPUT FORMAT (required)` section, requiring the reported `OUTCOME`/`STATUS` to be checked against an actual artifact rather than asserted.
- [ ] The added instruction is worded for the first-call's own role (self-verification of a freshly produced claim), not a verbatim copy of the second call's prior-claim-distrust wording.
- [ ] A prose-conformance test (mirroring the pattern the repo already uses for pinning skill prose, e.g. `tests/ceremony-profile-roster.test.js`'s style) asserts both templates carry a `CRITICAL` re-derive-from-artifacts instruction, so a future edit to either can't silently drop it behind a green suite.
- [ ] `npm test` passes.

## Technical Approach

Edit `plugin/skills/dispatch/task-prompt.md`'s "## First call — build,test" fenced block, inserting a new paragraph directly before the existing `OUTPUT FORMAT (required)` line — the same position the second call's own `CRITICAL` paragraph occupies relative to its `OUTPUT FORMAT` line. Model the wording on the second call's instruction (`## Second call` section, the paragraph beginning "CRITICAL: your review step must re-derive its verdict from raw artifacts") but adapt the framing: the first call has no *prior* call's claim to distrust — it's confirming its own freshly-produced result — so phrase it as requiring the actual test-output artifact to exist and match before the call reports `DONE`/`build-test-ok`, rather than reusing "never trust a prior claim." Then add or extend a prose-conformance test asserting both call templates carry this instruction (grep for the literal `CRITICAL:` + an artifact-reference phrase in each fenced block), following the existing `tests/ceremony-profile-roster.test.js` pattern for pinning prose against a live corpus.

## Original request

dispatch/task-prompt.md: first build,test call has no re-derive-from-artifacts check before reporting DONE

**Summary:** `dispatch/task-prompt.md`'s first (`build,test`) Task-call template has no requirement to re-derive its own claims from actual artifacts before reporting `DONE`, unlike the second (`review`) call, which produced at least one unsupported "all clean" report this session.

**Kind:** Defect

**Affected component:** dispatch/task-prompt.md (first-call `build,test` template)

**Objective:** Report fidelity

**Repro steps:**
1. Dispatch a group's first Task call (`build,test`) per `dispatch/task-prompt.md`'s first template.
2. Have it report a verification claim (e.g. "5/5 clean under load") without the underlying artifact actually existing in the run directory, or with a stale/incomplete premise inherited from an earlier record's own already-merged fix.
3. Note that the second (`review`) call's template explicitly instructs "re-derive your verdict from raw artifacts, never trust a prior claim" — but no equivalent instruction applies to the first call before *it* reports `DONE` in the first place.

**Expected vs. actual:**
Expected: a `DONE` status line from the first call implies its own claims are backed by artifacts that actually exist at the time it's reported.
Actual: one first-call report this session claimed "5/5 clean" verification with no supporting artifact in the run directory. It was caught only because an unrelated sibling agent's own discrepancy report prompted the orchestrator to explicitly demand reconciliation before trusting it — nothing in the first call's own template would have caught it otherwise.

**Measurement:** 2 of roughly 24 dispatched build/review reports this session were later found unsupported or incomplete by independent re-verification (~8%).

**Cost this session:** One full re-verification cycle, plus one corrective follow-up fix to an already-merged record's own claim, that would not have happened without an orchestrator or peer agent independently checking rather than trusting the narrative.

**Proposed fix:** Give the first-call template the same "re-derive from raw artifacts before claiming DONE" instruction the second call already carries, rather than deferring all verification skepticism to the second call.
