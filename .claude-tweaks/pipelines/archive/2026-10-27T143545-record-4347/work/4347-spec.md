# 4347: Take the full-suite verification from the PR's CI run instead of a local run when the declaration names one

Origin: speed analysis of the #4026 dispatch (run 2026-10-25T132807-record-4026)

Defer-reason: tangential

## Current State

Build's Common Step 5 and `/test` Step 1 run the full suite locally through `verify.js` (`plugin/skills/test/verification.md`). The runner writes the pass stamp that `verify.js --stamp-status` and `artifact-verdict.js`'s `deriveTestVerdict` read.

Concurrent pipeline sessions on one machine compete for CPU. On 2026-10-25 the #4026 run (`2026-10-25T132807-record-4026`, PR #4277) spent 55 min on one local full run and 1h34 on a second, while #4027, #4140 and #4317 ran their own suites. An unloaded local run takes about 20 min.

The same suite (~17,900 tests) already runs on every PR push in `.github/workflows/test.yml` (ubuntu-latest, Node 20, 15-min timeout). On PR #4277 it took 3.5 min (run 40216510908, 17:26:55Z to 17:30:30Z). Every phase exit already pushes the run branch, and the merge gate (`merge-verification: merge-when-green`) already requires that check green. So today the local full run duplicates a check that is faster, contention-free, free for this public repo, and required anyway.

## Deliverables

- `.claude-tweaks/verify-scope.json` can declare a CI source for a suite (workflow file and job name). Without one, behavior is unchanged, so consumer projects are not affected.

- With a CI source declared, `verify.js`'s full-suite run for that suite requires HEAD to be pushed and equal to the run PR's head. It waits for the declared job's run on that exact head SHA (bounded wait, polling, never backgrounded) and writes the pass stamp from the job's conclusion. The stamp records `source: ci` with the run id and URL.

- A failed CI run fetches the failing test files from the job log and re-runs only those locally for baseline adjudication (the existing `baseline.js` path). A test that is red at the fork point or passes on isolated re-run is adjudicated exactly as a local failure would be.

- Fallback to the local full run, with the reason named in `report.json`, when no CI run for the head SHA appears within the wait (a DIRTY PR gets no `pull_request` runs, the workflow did not trigger, Actions is down), when the run was cancelled, or when `gh` is unavailable.

- `deriveTestVerdict` and `/test`'s Skip-if-recent read accept a `source: ci` stamp the same as a local one.

- `verification.md` states what the CI pass does not cover: macOS and Node 22 (the local platform), and Windows (still post-merge via `windows-regression.yml`).

## Acceptance Criteria

- [ ] With the CI source declared and a green CI run on HEAD, Common Step 5 writes a full-scope pass stamp with `source: ci` and runs no local suite.

- [ ] A red CI run whose only failures are red at the fork point is adjudicated a baseline pass, and only the failing files were re-run locally.

- [ ] A red CI run with a real failure fails verification and names the failing tests from the CI log.

- [ ] A head SHA with no CI run within the wait (simulated DIRTY PR) falls back to the local full run, and `report.json` names the fallback reason.

- [ ] Without a declared CI source, `verify.js` output and stamps are byte-identical to today's.

- [ ] Each new branch has a test that fails against the current `verify.js`. The gh calls go through the injectable runner seam, never the network.

## Release Note

Projects can point final test verification at their CI run, so a pipeline waits a few minutes for CI instead of running the whole suite on a busy local machine.

## Technical Approach

### Key Files

- `plugin/bin/verify.js` — CI-backed full-suite mode: wait for the declared check run on HEAD, stamp from its result
- `plugin/bin/lib/verify/declaration.js` — accept a declared CI source (workflow, job) for a suite
- `plugin/bin/lib/verify/stamp.js` — pass stamp records its source (local or ci, with run id and URL)
- `plugin/bin/lib/verify/baseline.js` — adjudicate a CI failure against the base by re-running only the failing files
- `plugin/bin/lib/dispatch/artifact-verdict.js` — deriveTestVerdict accepts a ci-sourced stamp
- `plugin/skills/test/verification.md` — document the CI-backed mode, its fallbacks and what it does not cover
- `plugin/skills/build/SKILL.md` — Common Step 5 uses the CI-backed mode when declared
- `.claude-tweaks/verify-scope.json` — declare this repo's test.yml test job as the CI source
