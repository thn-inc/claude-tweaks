# 2705: pr-first-merge: auto-merge reporting doesn't read the actual check conclusion

Surface: infra

## Current State

The pr-first integration path's auto-merge convention (`_shared/pr-first-merge.md`, or the calling skill that invokes it) calls `gh pr merge {n} --auto --squash` when a PR's status checks are still `IN_PROGRESS`, then reports the outcome as "merged once CI passed" based solely on the PR's `state` transitioning to `MERGED`. `gh pr merge --auto` merges immediately once GitHub's own merge-readiness conditions are satisfied — which, on a repository with no *required* status checks configured, can mean immediately, regardless of whether an in-progress check later passes or fails. The reporting language ("queue an auto-merge so it merges once that passes") implies the merge is gated on that specific check's conclusion, but nothing in the sequence ever reads that check's final `conclusion` field to confirm it actually passed before or as part of the merge. Concretely observed: `test` check `IN_PROGRESS` at 18:50:21Z, "I'll queue an auto-merge so it merges once that passes" at 18:50:28Z, `gh pr merge --auto --squash` at 18:50:31Z, PR `state: MERGED` at `mergedAt: 2026-09-20T18:50:30Z` — merged 9 seconds after the check was last observed in progress, with no subsequent read of that check's conclusion.

## Deliverables

- In `_shared/pr-first-merge.md` (or wherever the `--auto` merge call and its result reporting are documented), require reading the relevant status check's `conclusion` (via `gh pr view --json statusCheckRollup`) after a `gh pr merge --auto` call resolves to `MERGED`, and state explicitly in the reported outcome whether the check had actually completed and passed by then, or whether the repository has no required checks and the merge proceeded independent of the check's state.
- Note in that file that `gh pr merge --auto` on a repo with no required checks is not equivalent to "wait for checks to pass" — name this distinction explicitly so a caller doesn't infer gating behavior that isn't there.

## Acceptance Criteria

- A caller following `_shared/pr-first-merge.md`'s auto-merge procedure reads and reports the actual check conclusion (or its absence/irrelevance) rather than inferring "merged once CI passed" from the PR's `state` field alone.
- The file states plainly whether this repository's branch protection requires the `test` check before merge, so future callers don't have to re-derive that fact per-run.

## Release Note

Made auto-merge reporting read the actual check result before calling a merge green.

## Technical Approach

Locate the `--auto`-merge call site in `_shared/pr-first-merge.md` and add a post-merge (or, where the merge is not yet resolved, a post-arm) read of `gh pr view {n} --json statusCheckRollup` to extract the named check's `conclusion`. Compose the reported outcome from that read rather than from the PR's `state` alone: "merged, {check} concluded {conclusion}" when a required check resolved before merge, or "merged — this repository has no required status checks, so the merge did not wait on {check}'s outcome" when it doesn't. Add a one-time note near the top of the auto-merge procedure documenting this repository's actual branch-protection configuration (required checks or their absence) so this doesn't need re-deriving per run.

### Key Files

- `plugin/skills/_shared/pr-first-merge.md` — the `--auto` merge call and its result-reporting language

## Gotchas

- This is a reporting-fidelity fix, not a merge-mechanics change — do not add an actual wait-for-check-conclusion gate unless the record's own scope is later widened; the Acceptance Criteria only ask for accurate reporting of what already happened.
- Verify the actual branch-protection state (`gh api repos/{owner}/{repo}/branches/{branch}/protection` or the repo settings UI) rather than assuming from this record's evidence alone — the observed 9-second merge is consistent with "no required checks" but should be confirmed directly before documenting it as fact.
