# 2747: Upstream defect report — `hooks.js teardown-run --merged` cannot finish on a GitHub Enterprise remote and orders the branch delete before the worktree removal

Surface: infra

## Current State

After a merged multi-spec run (`flow/multispec-review-console.md` Shared teardown step 7), `teardown-run --run <archived run> --merged` reported: `worktree: skipped — removal failed`, `branch: skipped — delete failed for <branch>`, `remote ref: skipped — Command failed: gh api --method DELETE repos/<owner>/<repo>/git/refs/heads/<branch>`. Two causes: (1) the `gh api` call carried no host argument, so on a GitHub Enterprise-hosted repo it targeted github.com and failed; (2) the worktree removal had half-reaped the worktree (its `.git` file was gone and `git worktree list` showed `prunable`) but reported failure, and the local branch delete then failed because git still considered the branch checked out there — a `git worktree prune` first would have let both succeed.

Verified during shaping: `plugin/bin/lib/hooks/teardown-run.js`'s `ghApiDelete` helper (line ~30) calls `gh api --method DELETE ...args` with no host/hostname argument, and the branch-delete path (line ~235-236) shows no `git worktree prune` step ahead of it — both causes are confirmed present in the current code, not already fixed. `plugin/bin/lib/repo-resolve.js` exists and is the codebase's own existing mechanism for resolving `host/owner/repo` for a GHE remote — the fix should reuse it rather than inventing new host-resolution logic.

## Deliverables

- Resolve the forge host via `bin/lib/repo-resolve.js` (the existing mechanism) and pass it to every `gh` call `teardown-run` makes, including the `ghApiDelete` helper's `gh api --method DELETE` call — so a GHE-hosted repo's remote-ref deletion targets the correct host instead of defaulting to github.com.
- Before attempting the local branch delete, check whether the worktree removal left the worktree registration in a `prunable` state (`git worktree list` porcelain output) and, if so, run `git worktree prune` first, then retry the branch delete — rather than reporting a failure that a simple prune would have resolved.
- Report all three teardown outcomes (worktree, branch, remote ref) with their underlying error text on failure, not just a generic "skipped" — so a human diagnosing a teardown failure doesn't have to reproduce the command by hand to see the real `gh`/git error.

## Acceptance Criteria

- `teardown-run --merged` against a GitHub Enterprise-hosted repo successfully deletes the remote ref, using the correct host resolved via `repo-resolve.js`.
- A worktree left in a `prunable` state by a partially-successful removal no longer blocks the subsequent branch delete — the prune-then-retry sequence resolves it automatically.
- A teardown failure (any of the three steps) reports the underlying error text in its output, not just "skipped."
- `npm test` passes.

## Release Note

Fixed run teardown on GitHub Enterprise remotes and made it remove the worktree before deleting the branch.

## Technical Approach

Reuse `repo-resolve.js`'s existing host-resolution output directly in `teardown-run.js`'s `gh` invocations (the `ghApiDelete` helper and any other `gh` call site in that file) — this is a straightforward plumbing fix, not new logic, since the resolution mechanism already exists and is used elsewhere in the codebase. For the prune-before-retry fix, check the worktree's state via `git worktree list --porcelain` (or equivalent) immediately after a reported removal failure, and only retry the branch delete after a prune succeeds — don't blindly prune-and-retry on every failure without first confirming the `prunable` state, since a genuinely different failure (e.g. permissions) shouldn't be masked by an unconditional retry.

### Key Files

- `plugin/bin/lib/hooks/teardown-run.js` — `ghApiDelete` (host-resolution fix) and the branch-delete path (prune-before-retry fix)
- `plugin/bin/lib/repo-resolve.js` — the existing host-resolution mechanism to reuse

## Gotchas

- Don't unconditionally retry the branch delete after any failure — only after confirming (via `git worktree list`) that the worktree is genuinely in a `prunable` state; a different underlying cause (e.g. a real permissions error) should still surface as a real failure, not be silently retried into a second, equally-doomed attempt.
- This is a Windows + GHE-specific repro, but the host-resolution fix and the prune-before-retry fix are both platform-independent — verify the fix doesn't regress teardown on a plain github.com-hosted repo (the common case in this repo's own CI).
