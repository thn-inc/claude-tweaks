# 1460: Bookkeeping-stamps gate misattributes a scratch worktree to an unrelated dangling pipeline run

## Current State

bin/lib/hooks/pre-tool-use.js's checkBookkeepingStampsGate resolves ctx.runDir via ctxLib.resolveRunDir(cwd, process.env) with no session-id filtering, deliberately picking the newest non-terminal pipeline run repo-wide. When a scratch worktree with no run-state.json of its own (e.g. /tidy's or /wrap-up's Step 7 housekeeping worktree per _shared/scratch-worktree.md) is created while an unrelated dangling non-terminal run exists (materialize commit landed, no worktree ever recorded — observed live against .claude-tweaks/pipelines/2026-08-23T204821-record-361, status interrupted, PR #1339), any Edit/Write/NotebookEdit or git-write Bash call inside that unrelated scratch worktree is denied with a message instructing: node hooks.js record-worktree --run "{dangling-run-dir}" "{scratch-worktree}". Following that remediation would stamp the scratch worktree as belonging to the dangling run, corrupting that other (possibly still-live-sibling) run's run-state.json. isForeignSessionCall can't rescue this case: the dangling run's runState.sessionId is unset (no worktree was ever recorded for it), so owner is empty, isForeignSessionCall returns false, and the deny stands. hasDistinctOwnedRun exists in the same file but per its own comment is deliberately not folded into this branch's foreign-session check. Reproduced live: /tidy's Step 7.5 worktree-always handling (EnterWorktree, fetch+merge catch-up, zero commits made) hit this gate on its first file write attempt, with no legitimate way to proceed short of corrupting an unrelated dangling run's state.

## Deliverables

- A way for checkBookkeepingStampsGate (or its caller) to recognize a scratch worktree never registered as belonging to any pipeline run's Common Step 1/materialize flow, and skip the gate for it entirely — e.g. a marker file scratch-worktree.md's procedure writes at creation time, a distinct code path for non-build worktree callers, or resolveRunDir excluding runs whose worktree field was never set from the newest-non-terminal fallback pool when the calling worktree has no independent evidence of belonging to that run
- Regression test reproducing this exact scenario: a dangling interrupted run with a landed materialize commit and no recorded worktree, plus a separate unrelated scratch worktree created afterward, asserting the scratch worktree's writes are NOT denied

## Acceptance Criteria

- A scratch worktree created per _shared/scratch-worktree.md while an unrelated dangling non-terminal run (materialize commit landed, no worktree recorded) exists in the same repo can Edit/Write/commit without being denied by checkBookkeepingStampsGate
- The fix does not weaken the gate's real purpose (catching a genuine /build session that skipped record-worktree for its OWN run) — a real /build worktree missing its own run's worktree assignment must still be denied
- A regression test is added under tests/ pinning the fixed behavior
