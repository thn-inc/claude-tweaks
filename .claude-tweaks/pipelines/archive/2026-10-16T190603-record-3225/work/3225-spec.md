# 3225: Dispatch: bind the run to the worktree before call 1, and gate commits on config.yml existing

Surface: infra

## Overview

A checkpoint inside `/claude-tweaks:flow` is skipped by exactly the agents that skip `/flow` — so the checkpoint this unit adds is set up by the dispatching session and enforced by a hook, not by `/flow` itself. The dispatching session binds the minted run to the group's worktree, marked `dispatched: true`, before it dispatches the first Task call; a new `pre-tool-use.js` gate then denies a `git commit` in that bound worktree until `{runDir}/config.yml` exists, naming the cause ("`/claude-tweaks:flow` Step 3 (Manifesto) has not written config.yml") and the remedy. This turns a bypassing first call's eventual deviation into a fast, pre-implementation deny instead of a 20-40 minute build followed by the post-hoc #2837 artifact check.

## Release Note

Added an early safeguard that stops dispatch's automated first build from committing code before it has written its required run configuration, catching a skipped setup step before any work lands instead of after a full build cycle.

## Technical Approach

The binding write (`record-worktree --dispatch`) and the gate (`checkDispatchConfigGate`) are two halves of one mechanism: the dispatching session marks a run as "must have config.yml before any commit," and the gate enforces that mark on every subsequent git-write call inside the bound worktree, regardless of which agent or call is running at the time — it resolves the run via the existing `resolveRun`/`classifyOwnership` composite (session id AND recorded worktree binding, #1098/#1099), the same resolution every other `pre-tool-use.js` gate already uses, not session id alone. The gate is purely additive — a run with no `dispatched` marker (every non-dispatched run in the codebase today) sees no behavior change at all.

## Gotchas

- `.claude/skills/pre-tool-use-gate-exemptions/` is this project's own skill documenting the unwritten exemption discipline every existing `pre-tool-use.js` deny gate already follows (reproduced independently in two prior review findings, per that skill's own description) — read it before writing the new gate's scope checks, rather than re-deriving the exemption list from scratch.
- `record-worktree --dispatch` failing in dispatch Step 5 is logged and does not block dispatch — the run then simply lacks the early checkpoint, and the #2837 backstop still applies; this is a design decision from the design doc's Error handling section, not an oversight to "fix" by making the flag's write hard-block dispatch.
- The gate fails open on every ambiguous case (no run resolved, unreadable `run-state.json`, no `dispatched` marker) — never a crash, per CLAUDE.md's never-break-a-session invariant (`docs/hooks.md`).
- Expect friction from out-of-order runs. In the #3212 firing, #3064 (materialize commit 19:25:49, `config.yml` 19:26:57) and #3066 (commit 07:00:02, Manifesto logged 07:00:20) both committed before writing `config.yml`, and both still finished with complete artifacts. This gate denies that ordering once. That is intended because it enforces the documented order, but the deny text decides whether one deny costs a retry or a stall.
- A known limit, accepted by the design doc: an agent can still create `config.yml` by hand (e.g. via `set-config.js`) to get past this gate, exactly as #3126 hand-wrote bookkeeping stamps to get past `checkBookkeepingStampsGate`. The unchanged #2837 post-hoc artifact check is the backstop for that case — this unit does not need to also prevent hand-written `config.yml`.

## Build Deviations

- **Beneficial (applied):** the deny reason goes beyond naming the cause and the Step 3 remedy. It also states that a `record-worktree` re-stamp does not clear the deny and that the deny does not count toward any re-stamp/retry budget (`dispatch/task-prompt.md`'s first-commit re-stamp rule would otherwise turn the common out-of-order first call into a BLOCKED stall). It gives an in-flow remedy ("if you are already running /claude-tweaks:flow, run its Step 3 now") before the Skill-tool remedy. This came from the whole-branch review, commit c14634a8a. The `config.yml` existence check also runs before the git-spawning checks, so a steady-state dispatched run pays nothing.
- **Update the spec (staged for the Review Console, `staged/build-deviation-{1,2,3}.md`):** (1) dispatch Step 5 had no existing `record-worktree` call, so the `--dispatch` bind is a new call; (2) `commandGitTargets` covers commit/push/mv/rm/update-ref/apply, not merge/rebase; (3) `checkBookkeepingStampsGate` keys on the session-agnostic `ctx.runDir`, not the composite resolution. The new gate uses `ctx.ownedRun` plus `classifyOwnership === 'mine'`, because the premise probe measured `ctx.runDir` resolving an unrelated sibling run.
