# 1778: Pipeline-shadow guard has no #1493/#1494 carve-out for tidy/sweep-standalone run-dir mirroring

Surface: infra

## Current State

`shadowPipelineRunDir` (`plugin/bin/lib/hooks/pre-tool-use.js`, the function above `checkPipelineShadowGuard`) denies any Edit/Write/NotebookEdit target or Bash write/mkdir target that would create a run directory under `.claude-tweaks/pipelines/` inside a linked worktree when that run-dir name does not yet exist there. Its only carve-out is `WORK_SPEC_TAIL_RE` (#959), tested against the path tail *below* the run-dir segment; the run-dir name itself (`relParts[0]`) is computed and never inspected. The comment block at the top of the file's exemption section already names `*-tidy-standalone*`/`*-sweep-standalone*` audit files (#1493/#1494) as the gitignore exception, but no code implements a matching carve-out.

The documented procedure that collides with this: `plugin/skills/tidy/step-7-5-worktree-always.md`'s `pr-first` branch says that before the housekeeping `git add`, the run copies `decisions.md`, `report.md`, and `staged/**` from the `$RUN_ROOT`-anchored run dir into the worktree's own copy of that path and commits the worktree copies, because a worktree cannot `git add` a main-checkout path. `.gitignore` un-ignores exactly those three shapes under `*-tidy-standalone*` and `*-sweep-standalone*` (its #1493/#1494 block), and `_shared/pipeline-run-dir.md`'s Anchoring section describes the same exception. The first `mkdir -p .claude-tweaks/pipelines/{id}-sweep-standalone/staged` inside the scratch worktree is a new run-dir creation to the guard, so it is denied with the "refusing to create ... a NEW pipeline run directory inside a linked worktree" message (observed live 2026-09-02 during a `/claude-tweaks:sweep` run at tidy Step 7.5).

Net effect today: under `worktree-always: true` + `pr-first`, a tidy or sweep housekeeping commit can never carry its audit trail. The trail stays real at the main-checkout path (writes there pass `checkWorktreeRequired`'s `.claude-tweaks/pipelines/` prefix exemption) but never lands on the integration branch, contradicting the gitignore and skill text.

Existing coverage: `tests/hooks-pipeline-shadow-guard.test.js` (167 lines) pins the deny shapes plus #959's allow and negative-control cases using `tests/helpers/git-fixtures`' `gitRepo`/`linkedWorktreeOf`; its last negative control asserts a new `decisions.md` in an ordinary run dir is still denied, which must keep holding for non-standalone names.

## Technical Approach

A two-regex, name-plus-tail check inserted right after `WORK_SPEC_TAIL_RE.test(tail)` in `shadowPipelineRunDir`. Keying on the run-dir *name* is new for this guard; keep the name regex anchored (`/-(?:tidy|sweep)-standalone/`) so a `spec-{slug}` nesting or an `archive/` parent cannot match (the `.gitignore` block is explicitly top-level-only, "never spec-*/-nested"). Use `path.sep`-agnostic character classes the way `WORK_SPEC_TAIL_RE` does. Cross-check the prior-art dimensions the #959 carve-out established (directory form vs file form, `cp` shape, nested negative control) and cover each in the new tests. No change to `checkWorktreeRequired` — the main-checkout writes already pass its prefix exemption.

## Gotchas

- The guard runs unconditionally (not gated on `worktree-always`), so the new carve-out also applies on projects without the policy; that is correct — the `.gitignore` exception is not policy-gated either.
- Order matters: return `null` for the carve-out before the `fs.statSync` existence check, exactly like #959, or the first `mkdir -p` of the run dir still fails because the run dir does not exist yet.
- `mkdirTargets`/`fileWriteTargets` (Bash parsing) feed the candidates; `cp` is already a recognised write shape (existing test), so no parser change is needed.
- Sweep's own run dir is minted by `/claude-tweaks:sweep` Step 0 and tidy runs inside it, so the `-sweep-standalone` name is the one a sweep-driven tidy hits; both names must be covered.
- A worktree copy of `decisions.md` diverges from `$RUN_ROOT`'s the moment the run logs another line; the skill text already says `$RUN_ROOT` stays authoritative until merge. Do not "fix" that here.

## Current State

`checkPipelineShadowGuard`/`shadowPipelineRunDir` in `plugin/bin/lib/hooks/pre-tool-use.js` denies
any Edit/Write/NotebookEdit/Bash write or mkdir that would create a NEW top-level directory under
`.claude-tweaks/pipelines/` inside a linked worktree — intended to stop a worktree-local shadow of
pipeline run state (`[IL-127]`). The only carve-out implemented is `WORK_SPEC_TAIL_RE` (#959),
which matches `work[/{n}-spec.md]` (or `spec-{slug}/work[/{n}-spec.md]`) tails only.

`.gitignore` (lines 18-30) and `_shared/pipeline-run-dir.md`'s Anchoring section (plus
`tidy/SKILL.md` Step 7.5) document a second, separate exemption for `*-tidy-standalone*` and
`*-sweep-standalone*` run directories: under `worktree-always: true` + `integration-model:
pr-first`, a worktree-isolated tidy/sweep run is supposed to mirror that run's `decisions.md`,
`report.md`, and `staged/**` into the worktree's own copy of the run-dir path, then `git add`+
commit them there (#1493/#1494) — those specific paths are the ones `.gitignore` un-ignores.

`shadowPipelineRunDir` has no code path implementing #1493/#1494 at all — it only checks the tail
against `WORK_SPEC_TAIL_RE`. Reproduced live on 2026-09-02 during a `/claude-tweaks:sweep` run:
inside a worktree at Step 7.5, `mkdir -p .claude-tweaks/pipelines/{sweep-run-id}/staged` (following
the documented mirror-then-commit procedure verbatim) was denied with "refusing to create ... a NEW
pipeline run directory inside a linked worktree" — indistinguishable from a genuine shadow attempt,
because the guard never inspects the run-dir's own NAME, only the tail beneath it.

Net effect: a worktree-run tidy/sweep housekeeping commit can never land. The audit trail
(decisions.md, staged proposals) stays real and readable at the main-checkout path — writes there
are separately exempted by `checkWorktreeRequired`'s own `.claude-tweaks/pipelines/` prefix
exemption — but is permanently uncommitted, contradicting the documented and gitignore-encoded
design.
