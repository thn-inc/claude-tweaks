# 2676: wrap-up verify: carrier-commit check only matches the literal "Fixes #N", missing GitHub's other closing keywords

Surface: infra

## Current State
`plugin/bin/lib/wrap-up/engine-verify.js`'s `carrier-commit` check (`registerCheck('carrier-commit', …)`, line ~320) verifies that each resolved issue in a wrap-up run has a "carrier commit" that closed it. The check currently greps the branch log for the literal string `Fixes #{n}` only (line ~330: `deps.git(['log', '--grep=Fixes #${n}', ...])`), and, when a PR-first fallback is needed, checks the PR body for the same literal string (line ~345: `prBody.includes('Fixes #${n}')`).

GitHub recognizes a broader set of closing keywords in commit messages and PR bodies — `close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved` (case-insensitive, optionally `owner/repo#N`) — any of which actually closes the linked issue on merge. Because this check only recognizes the literal `Fixes #N` form, a run whose commits used any other recognized keyword (e.g. `Closes #N`) fails the check with `missing` populated for every record, even though GitHub's own state shows the issues correctly closed. This was observed on a real four-record standalone wrap-up (commits used `Closes #N`; all four issues were CLOSED at merge time; `verify` still exited 3 and `execution-and-verification.md`'s exit-3 → BLOCKED rule fired incorrectly), on plugin 6.127.0.

The repo already has a reusable mechanism for checking an issue's actual closing state via GraphQL: `plugin/bin/lib/issues/linked-prs.js`'s `fetchLinkedPRs` resolves each candidate issue's `closedByPullRequestsReferences` connection in one batched call — this is the "ground truth" data source the bug report's proposed fix references.

A related, separately-tracked false-negative in the same verify table is #2552 (`run-dir-archived`) — not in scope here, but worth being aware the verify table has more than one known false-negative row.

## Deliverables
1. Replace the `carrier-commit` check's branch-log grep (line ~330) with a case-insensitive match over GitHub's full recognized closing-keyword set (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`), each optionally preceded by `owner/repo` before the `#N`, matching against `#{n}` as a whole reference (not a substring of a larger number).
2. Apply the same keyword-set widening to the PR-body fallback check (line ~345), which currently has the identical literal-`Fixes` narrowing.
3. Add a ground-truth fallback: when neither the branch-log grep nor the PR-body check finds a carrier commit for an issue, query the issue's actual state via `gh issue view N --json state` (or reuse `plugin/bin/lib/issues/linked-prs.js`'s `fetchLinkedPRs`/`closedByPullRequestsReferences` connection) and treat a CLOSED state backed by a closing PR/commit reference as a pass on its own, rather than failing purely because no commit message matched a keyword pattern.
4. Keep the existing `fail` behavior for a genuinely-open issue with no matching commit and no closing reference — the fix narrows false negatives, it does not weaken the check's ability to catch a real missing carrier commit.

## Acceptance Criteria
- `carrier-commit` passes for a run whose closing commit message uses any of GitHub's recognized closing keywords (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`), case-insensitive, with or without an `owner/repo#N` prefix — not just the literal `Fixes #N` form.
- The PR-body fallback check recognizes the same keyword set as the branch-log check (no longer just `Fixes #N`).
- `carrier-commit` passes for an issue that is CLOSED with a `closedByPullRequestsReferences`/closing-commit reference, even if no commit message in the branch range matched any keyword pattern textually (the ground-truth fallback).
- `carrier-commit` still fails (`missing` populated) for an issue with no matching commit message, no matching PR body reference, and no closing-PR-reference-backed CLOSED state — a genuinely missing carrier commit is still caught.
- `tests/bin-lib/wrap-up/engine-verify.test.js` gains test cases covering: a `Closes #N` commit (currently would fail, should now pass), a `Resolves #N` commit, case-insensitivity (`FIXES #N`), and the ground-truth CLOSED-state fallback path.
- Existing passing test cases in `tests/bin-lib/wrap-up/engine-verify.test.js` for the `carrier-commit` check (including the literal `Fixes #N` case) continue to pass.

## Gotchas
- Preserve the existing pr-first/local-merge branching logic (the comment at lines ~312-318) — the fix is about widening keyword matching and adding a ground-truth fallback, not restructuring when the PR-body check applies vs. the branch-log check.

## Original request

wrap-up verify: carrier-commit check only matches the literal "Fixes #N", missing GitHub's other closing keywords

**Summary:** `wrap-up-engine.js verify`'s `carrier-commit` check greps the branch log for the literal `Fixes #N` only, so a run whose closing commits used GitHub's other closing keywords (`Closes #N`, `Resolves #N`, `Fixed #N`, etc.) fails the check even though GitHub closed the issues on merge.

**Kind:** Defect

**Affected component:** `bin/lib/wrap-up/engine-verify.js` (`registerCheck('carrier-commit', …)`), and the `skills/wrap-up/execution-and-verification.md` exit-3 → BLOCKED rule that consumes it

**Repro steps:**
1. On a `local-merge` project, fix a record in a worktree and commit with a footer line `Closes #N` (GitHub's documented closing keyword) instead of `Fixes #N`.
2. Rebase-merge to the integration branch; GitHub closes issue #N.
3. Run `/claude-tweaks:wrap-up #N`; at Phase 4's Verify step, `node bin/wrap-up-engine.js verify --run-dir <run-dir> --base <sha>`.

**Expected vs. actual:**
Expected: `carrier-commit` passes — the range contains a commit whose message closes #N with any keyword GitHub recognizes (`close`, `closes`, `closed`, `fix`, `fixes`, `fixed`, `resolve`, `resolves`, `resolved`, case-insensitive, optionally `owner/repo#N`), and the issue is in fact closed.
Actual: `deps.git(['log', '--grep=Fixes #N', …])` finds nothing, `missing` fills with every record, the row reads `fail — no carrier commit found for #N, …`, verify exits 3, and the skill's rule forbids the closure line on a run that closed all its records. Observed on a four-record standalone wrap-up (commits used `Closes #N`; all four issues showed CLOSED at merge time), plugin 6.127.0.

Proposed fix: match with a case-insensitive regex over GitHub's closing-keyword set (`--grep` with `-i -E '(close[sd]?|fix(e[sd])?|resolve[sd]?) #N\b'`, or read the log once and match in JS), and — since the issue's own state is the ground truth — treat a `gh issue view N --json state` of CLOSED with a `closedByPullRequestsReferences`/closing-commit reference as a pass on its own. The PR-body fallback has the same literal-`Fixes` narrowing (`prBody.includes('Fixes #N')`) and should use the same set.

**Related:** #2552 (run-dir-archived, the other false-negative row in the same verify table)

**Definition:** Clear
