## Release Note

Add a `learned-skills-auto-merge` setting that lets wrap-up's learned-skill update PRs merge on their own once CI passes; it is on by default only at `autonomy: unattended`.

## Technical Approach

Mirror `housekeeping-auto-merge`'s entry and derivation, except where the Decision below says otherwise; do not reuse that key (it would widen what a housekeeping grant means in every consumer project). Run the `policy-key-addition` skill's checklist.

**Decision** (2026-11-23, answering the plan-review question on this issue): **Reading B, plus the indirect route closed.** `learned-skills-auto-merge` is `policyOnly: true`, so a run config can never set it, and it stays factory-settable (not in `FACTORY_REFUSED_KEYS`): the factory layer is the maintainer's own user-wide consent, like `policy.yml`. The derived default reads `autonomy` with the run-config source skipped, because otherwise a run config carrying `autonomy: unattended` would turn the key on and defeat `policyOnly`. Why: the key removes a human-review floor, and a run's own agent writes that run's config (the same reason `control-mode` became `policyOnly` in #5830). `housekeeping-auto-merge`'s own derivation is not changed by this record. Rule for any further question of who may set this key or the inputs it derives from: pick the option where only `policy.yml` or the factory layer can turn it on, and never a run config.
