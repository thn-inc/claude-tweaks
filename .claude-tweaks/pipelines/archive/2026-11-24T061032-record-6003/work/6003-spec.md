# 6003: Run review lenses as lean headless workers behind review-lens-dispatch: worker

Surface: backend
Risk-flags: public-contract

## Current State

`review-lens-dispatch` (`plugin/bin/lib/policy-schema.js`, #5599) takes `task` (default) or `workflow`. The workflow path falls back to the Task dispatch whenever the Workflow tool is absent, which includes every review run inside a dispatched or continuation agent (`/claude-tweaks:dispatch` runs review inside a Task agent), per #5825.

#6000 in this decomposition adds a `lens-reviewer` role and `plugin/bin/review-lens-workers.js`, which runs lens briefs as headless `claude -p` workers and returns the workflow script's reply shape. A headless worker is started through Bash, so it is reachable from inside a Task agent, where the Workflow tool is not.

## Deliverables

1. A third value `worker` for `review-lens-dispatch` (additive; `task` stays the default), added with `.claude/skills/policy-key-addition`.
2. Step 3 prose for the worker path in a new sub-file (proposed `plugin/skills/review/step3-worker-dispatch.md`), with one pointer line in `step3-lens-dispatch.md`: compose each lens brief once, write the lenses file, call the launcher (its interface is read from the merged #6000: `--run <dir> --lenses-file <json>`, the workflow script's reply shape), and settle with `review-coordination.js settle-lens-replies` exactly as the workflow path does. Lens 3f is never sent to the launcher (#6000's launcher rejects it); the dispatcher routes 3f to the Task path in the same review and settles every reply set in one `settle-lens-replies` call. With `review-lens-selection: adaptive`, the lens set comes from the selection CLI.
3. Fallback to the Task dispatch with one `Step 3 lens dispatch (worker fallback)` `SKIP` line naming the condition (no `claude` binary, launch error, every worker failed, settle exit 2). The unit of fallback is the lens: only lenses whose workers failed or timed out re-dispatch on the Task path, and their replies merge into the same single `settle-lens-replies` call as the worker replies. The two fail-closed reply shapes reach `needsSession`/`skipped` exactly as on the workflow path (settle exits 0 on both) and are never a worker-fallback condition. Two acceptance criteria below cover the partial and fail-closed-shape cases. Lenses kept off the worker path (3f, if the role record keeps it off) dispatch on the Task path in the same review.
4. One real review run on the worker path at build: per lens, worker first-turn tokens, total tokens and confirmed findings, quoted in the PR beside the numbers of a paired re-run of the same diff on the Task path (a single sample, labelled anecdotal, since lens output varies run to run). The repository opts in by setting `review-lens-dispatch: worker` in its committed `.claude-tweaks/policy.yml`, which is what the parked record's trigger counts.
5. File a parked measurement record (Defer-reason: blocked-external; trigger: 20 worker-path reviews after this repository opts in, or 30 days): per lens pair, confirmed findings and total tokens on the worker path against the Task path, the Haiku-lens 100k ceiling checked, and the fallback share by condition; outcome a default-flip record or a stated reason to keep the current default. Fallback counts by condition are read from the `worker fallback` `SKIP` lines in `decisions.md`.

## Acceptance Criteria

- [ ] With `review-lens-dispatch: task` or `workflow`, Step 3 is unchanged (prose pins and the existing workflow-path tests stay green).
- [ ] With `worker`, Step 3 calls the launcher and settles through `settle-lens-replies`; a stubbed launcher failure logs one `worker fallback` `SKIP` line and the review completes on the Task path.
- [ ] With `worker`, a review where one lens's workers fail and the others succeed re-dispatches only the failed lens on the Task path and settles all replies in one `settle-lens-replies` call; the succeeded lenses are not run twice.
- [ ] With `worker`, the two fail-closed reply shapes (a one-line `No findings` plus prose; a `[skill]` tag in the severity cell) reach `needsSession`/`skipped` exactly as on the workflow path and log no `worker fallback` line; every first-call settle exit 2 is the fallback condition `settle exit 2`.
- [ ] A review run inside a Task agent (the `/claude-tweaks:dispatch` shape) takes the worker path rather than falling back, shown by a dispatched probe (a Task agent runs the review with `worker` set; the evidence is no `worker fallback` line and launcher output in the run directory) that states its preconditions (`claude` on PATH, auth inherited) and its expected outcome when they fail.
- [ ] An older build reading `review-lens-dispatch: worker` resolves to the `task` path with no hard failure, shown by a probe or the older build's resolver test. `worker` is a permanent third value. Its removal condition, written beside the key in `policy-schema.js`, is tied to #5825's outcome. If #5825 flips the default to `workflow`, `worker` stays only if this record's parked measurement shows it cheaper than `workflow` with no fewer confirmed findings; otherwise it is removed one minor release after that ruling. This repository's committed `.claude-tweaks/policy.yml` must not set `worker` until a release carrying the value has shipped and is the installed plugin.
- [ ] A mixed review (3f on the Task path, the other lenses on workers) settles through one `settle-lens-replies` call, shown by a test with a stubbed launcher.
- [ ] The build's real run reports every Haiku lens worker under 100k total tokens (the design's own ceiling), or the PR says which one was over and by how much; an overrun is reported, not a build failure.
- [ ] The parked measurement record is filed and linked.

## Release Note

Review can run its lens reviewers as lightweight headless workers with `review-lens-dispatch: worker`, including when review runs inside a dispatched agent.

## Gotchas

- `step3-lens-dispatch.md` is 48,911 B, within 10% of the 52,500 B read rail: new prose goes in the sub-file.
- The key's removal condition (`policy-schema.js` comment, #5599) names `task` and `workflow`; update it to state what happens to `worker`. Expand-contract: a run on an older plugin reading `worker` must not break. Check what an older build's policy audit does with an unknown value (#5825 found it reports the key unrecognised).
- `settle-lens-replies` leaves two real reply shapes fail-closed (#5836, #5599 comments). The worker path inherits them; do not loosen them here.
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(public-contract): …`.

## Decision Rationale

- **Why a third dispatch value and not a replacement.** #5825 decides whether `workflow` becomes the default. The worker path is measured beside it, not instead of it.
- **Why the worker path matters most inside dispatched agents.** There the workflow path always falls back, so without workers a dispatched review keeps the 51k-token Task agents.

**Decision** (plan-review question 1, 2026-11-24, run `2026-11-24T044846-record-6003`): Reading B. `settle-lens-replies` exits 0 on both fail-closed reply shapes (probed on `plugin/bin/review-coordination.js` `settleLensReplies`), so no settle exit 2 is ever caused by one. AC4 and Deliverable 3 are restated: the two shapes reach `needsSession`/`skipped` exactly as on the workflow path and are never a worker-fallback condition, and every first-call settle exit 2 is the fallback `settle exit 2`. This matches the workflow path, where a first-call settle exit 2 is fallback condition 5 (`plugin/skills/review/step3-workflow-dispatch.md`, Settle section). The fail-closed shapes themselves stay untouched (Gotchas).

**Decision** (plan-review question 2, 2026-11-24): Reading A. "A test with a stubbed launcher" (AC2, AC3, AC7) means a test that produces the reply from `review-lens-workers.js` / `runLensWorkers` with a fake runner (the injectable-runner seam), not hand-written launcher-shaped JSON. It covers four cases: one lens failed, one side failed, every side failed, and nothing on stdout. Each reply is fed through `merge-lens-replies` and `settle-lens-replies`. Prose-conformance pins may sit beside it but never stand in for it. The ACs stay as written.
