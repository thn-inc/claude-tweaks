# 2593: plan-audit Check C: executes a `git stash push` found in Step 2 prose - the Run: extractor takes the first backticked span with no VCS-mutation refusal

Surface: infra

## Current State
`bin/plan-audit.js`'s Check C (`bin/lib/plan-audit/checks.js`'s `checkC`) pre-runs each task's Step 2 verification command against the live repo to confirm it currently fails (per `plan-audit.md`'s documented contract that Check C is read-only). The command is extracted by `bin/lib/plan-audit/parser.js`'s `extractStep2Verification`, which matches `/^Run:\s*(.+)$/m` anywhere within the Step 2 window — not anchored to the heading itself — then takes the **first backticked span** found on that matched line as the command to run (`parser.js` lines 102-107):

```js
const runMatch = window.match(/^Run:\s*(.+)$/m);
...
const backtickedCmd = runMatch[1].match(/`([^`]+)`/);
const command = (backtickedCmd ? backtickedCmd[1] : runMatch[1]).trim();
```

This means any line starting with `Run:` inside the Step 2 window — including a prose line that merely *mentions* a command in prose, such as `Run: never run \`git stash push -u -m tag\` here; use a WIP commit instead` — gets its first backticked span extracted and executed verbatim as the verification command by `checkC` (`checks.js` line 192: `const { exitCode, output } = run(command, repoRoot);`). `checkC` performs no inspection of `command` before executing it — there is no check anywhere in the current code for VCS-mutating commands (`git stash`, `git commit`, `git push`, `git reset`, `git checkout`, `git switch`, `git clean`, `git rebase`, `git merge`, `gh` writes, or any compound form via `&&`/`;`/`|`).

This was observed in production on 2026-09-18 (plugin 6.126.0): a plan's Step 2 prose contained the phrase above, `checkC` executed the extracted `git stash push -u -m tag` against the live worktree, and an untracked plan file was swept off the shared stash stack — the same stash stack every worktree and sibling session shares. Recovery required a manual `git stash apply <sha>`, a drop-by-tag, and a plan rewrite removing the phrase. `plan-audit.md` documents Check C as read-only; this is a violation of that documented contract, not new intended behavior.

## Deliverables
1. `extractStep2Verification` (or a new validation step downstream of it) identifies a genuine verification command — either a fenced ` ```Run:``` `-style code block, or a `Run:` line whose backticked span is the *entire* remainder of the line after `Run:` (i.e., the line is `Run: \`{command}\`` with nothing else) — and treats any other shape (prose containing a `Run:`-prefixed line with an embedded backticked span that isn't the whole remainder) as unparseable, not as an extractable command.
2. `checkC` refuses to execute any extracted command whose first token, or any token immediately following a `&&`, `;`, or `|` segment separator, is a VCS-mutation verb: `git stash`, `git commit`, `git push`, `git reset`, `git checkout`, `git switch`, `git clean`, `git rebase`, `git merge`, or any `gh` subcommand that writes (`gh issue create/edit/close`, `gh pr create/merge/close`, etc. — the write-vs-read split `gh-api-module-pattern` skill or existing `gh` write-detection logic in the repo already draws, reused rather than redefined here).
3. A refused command is reported under the audit's `warnings` output (not `findings` — it isn't a task-verification result, it's a check-mechanism refusal), naming the task, the refused command, and the reason (VCS-mutation refusal).
4. The audit summary lists every command Check C actually executed, so a reader can confirm what ran without needing to reproduce the audit.

## Acceptance Criteria
1. Given a plan whose Task N Step 2 window contains `Run: never run \`git stash push -u -m tag\` here; use a WIP commit instead` followed by an `Expected: FAIL` line, running `node bin/plan-audit.js <plan-file>` does NOT execute `git stash push -u -m tag` against the repo — `git stash list` before and after the audit run is unchanged.
2. Given the same plan, the audit's `warnings` output includes an entry for Task N naming the refused command and a VCS-mutation-refusal reason (not a generic "unparseable" reason, since the extraction pattern technically matched — this is a refusal, not a parse failure).
3. Given a plan whose Task N Step 2 has a genuine verification command in the correct shape (`Run: \`npm test -- path/to/test.js\`` as the entire remainder of the line, or an equivalent fenced block), `checkC` still executes that command exactly as it does today — the fix does not regress the legitimate pre-run path.
4. Given a plan whose Step 2 verification command is a compound shell command with a VCS-mutation verb after a `&&`/`;`/`|` (e.g. `npm test && git commit -am wip`), Check C refuses the whole command — the per-segment check catches mutation verbs that aren't the first token of the whole line.
5. The audit's output (whatever format it currently renders — findings/warnings/summary) lists every command Check C executed during that run, for at least the passing case in AC 3.
6. A plan whose Step 2 verification command is a non-VCS, non-mutating command (e.g. `npm test`, `node script.js`) continues to execute and produce findings exactly as before — the fix is scoped to VCS/gh-write mutation verbs, not a general command whitelist that would break existing passing plans.

## Technical Approach
- In `bin/lib/plan-audit/parser.js`'s `extractStep2Verification`, tighten the `Run:` line match so that a backticked span is only treated as the command when it is the entire remainder of the `Run:` line (after trimming) — i.e., `runMatch[1].trim()` equals the backticked span itself (including its backticks) — or when the verification is expressed as a fenced code block under the `Run:` label. A `Run:` line whose backticked span is only part of a longer prose sentence should return `null` (or a distinct "prose, not a command" signal) rather than extracting the first backtick match.
- In `bin/lib/plan-audit/checks.js`'s `checkC`, before calling `run(command, repoRoot)`, tokenize `command` by shell segment separators (`&&`, `;`, `|`) and check each segment's first token against a VCS-mutation verb list (`git stash|commit|push|reset|checkout|switch|clean|rebase|merge`, `gh` write subcommands). On a match, skip execution for that check and push an entry to a new `warnings`-shaped refusal record instead of calling `run`.
- Extend `checkC`'s return shape to carry the list of executed commands (for the audit summary requirement, AC 5) alongside the existing `findings`/`warnings`/`appendShaped`.
- Reuse any existing gh-write-detection logic already in the repo (check `bin/lib/issues/github-write-transport.md`'s described split, or similar, before hand-rolling a new gh-write verb list) rather than inventing a second classification of "which gh subcommands write."

### Key Files
- `plugin/bin/lib/plan-audit/parser.js` — `extractStep2Verification` (lines 93-108); tighten the backtick-extraction condition per Deliverable 1.
- `plugin/bin/lib/plan-audit/checks.js` — `checkC` (lines 176-214); add the VCS-mutation refusal check before `run(command, repoRoot)` is called, and extend the return shape to list executed commands.
- `plugin/skills/plan-audit.md` (or wherever the Check C contract prose lives — confirm exact path) — already documents Check C as read-only; verify no wording change needed, since this fix restores rather than changes the documented contract.
- `plugin/bin/plan-audit.js` — CLI entry point; confirm the audit summary rendering picks up the new executed-commands list.

## Gotchas
- The VCS-mutation verb list must be conservative but complete enough to catch the incident class described — a partial list that misses e.g. `git rm` or `git tag -d` leaves the same class of destructive-mutation risk open. Cross-check against any existing mutation-verb list elsewhere in the repo (hooks, other guards) before finalizing this one, to avoid two divergent lists.
- Tightening `extractStep2Verification`'s match condition (Deliverable 1) risks making some currently-working plans' genuinely-intended `Run:` lines newly unparseable if their formatting is looser than assumed (e.g. trailing whitespace or a trailing comment after the backticked command) — verify against a sample of real existing plans before landing, and prefer a targeted fix (distinguishing "backtick is the whole line" from "backtick is embedded in a longer sentence") over an overly strict pattern.
- The compound-command per-segment check (Deliverable 2/AC 4) needs to handle shell quoting correctly — a VCS verb appearing inside a quoted string argument (not as an actual command token) must not trigger a false refusal; a naive string-split on `&&`/`;`/`|` risks this edge case for quoted arguments containing those characters.
- This bug represents a real security/safety gap (arbitrary destructive command execution from plan file content) with production impact already observed — treat the fix as data-loss-prevention-critical, not a cosmetic parser tweak.
