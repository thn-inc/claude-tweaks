# 4128: Decide whether test-impact fetch may overwrite a fresher local map with an older CI map

Surface: terminal

Origin: ledger resolve gate (#4024, ledger row 24)

Defer-reason: needs-human-decision

**Related:** #4024, #4131, #4130, #3822, #4217, #4310, #4333, #4347, #4424, #4462

## Current State

`tools/test-impact.js fetch` picks the newest successful `push`/`workflow_dispatch` main run whose head commit is an ancestor of `HEAD`. It skips the download only when the cached map's `commit` equals that run's head commit and the map is not `dirty` (`tools/test-impact.js:285`). Any other cached map gets overwritten. That includes a valid map a developer traced on their branch at a commit that descends from the CI commit, and the result is an older map with fewer reads.

When this record was filed, keeping a local map was not obviously safe, because `trace --allow-dirty` could produce a map from a tree its `commit` does not describe (ledger row 27). #4131 has since closed that gap:

- `trace` records `dirty: true` for such a map;
- `plugin/bin/lib/verify/impact.js:155` refuses it as `map-dirty`;
- `fetch` already treats a dirty cached map as not current.

A cached map that parses, came from a passing suite and is not dirty was therefore traced with no tracked changes at its `commit`. It is still not identical to a CI map, in three ways:

- `trace` ignores untracked files when judging dirty (`--untracked-files=no`), so an untracked file can contribute reads;
- a developer may trace on another Node version, and the map records `node`, but `impact.js` never reads it;
- a developer may trace on another platform, which the map does not record.

The map decides which tests run, so these differences could in principle change the selection. Keeping the map in `fetch` adds no new trust, though: `verify.js` already uses any such local map as-is whenever `mapProblem` finds nothing wrong, without calling `fetch`. This record only stops `fetch` from being stricter than the reader it serves. Whether local maps should be trusted at all is a separate question that this record does not change.

**Decision (human-approved 2026-10-30):** `fetch` keeps a cached map that is valid and at least as new as the CI map on the same line of history. Otherwise it takes the CI map.

How much this matters: `verify.js` runs `impact.fetch` only when the cached map already has a problem (`plugin/bin/lib/verify/impact.js:152-159`, `:257`). Every such problem either fails the keep rule below or leaves the CI map no better, so `verify.js`'s behaviour does not change. The rule decides what happens when someone runs `fetch` by hand, and it stops `fetch` from ever replacing a better map with a worse one.

## Deliverables

1. Widen `tools/test-impact.js` `fetch`'s cache check so it keeps the cached map with no download when all of these hold:
   - it parses (`ok`), `exitCode === 0`, and it is not `dirty`;
   - its `commit` equals the chosen run's `headSha`, or `git merge-base --is-ancestor --end-of-options {headSha} {cachedCommit}` succeeds;
   - its `commit` is an ancestor of `HEAD` (`git merge-base --is-ancestor --end-of-options {cachedCommit} HEAD`).
2. Log the outcome on stdout, matching today's `fetch: map at … already current` line. Name both commits when the kept map is newer than the CI one, e.g. `fetch: cached map at {cachedCommit} descends from CI map {headSha}, kept → {out}`.
3. A git error on either ancestry check, such as an unknown commit, counts as "not kept", and `fetch` downloads as today.
4. Update the header comment, and any doc that describes `fetch`'s cache rule, to state the new rule.

## Acceptance Criteria

1. A clean, passing cached map whose commit descends from the chosen CI commit and is an ancestor of `HEAD` is kept. No `gh run download` call is made, exit is 0, and the log line names both commits.
2. The same cached map with `dirty: true` is replaced: one download.
3. A cached map with `exitCode !== 0` that descends from the CI commit is replaced.
4. A cached map on a diverged line, where the CI commit is not its ancestor, is replaced.
5. A cached map that descends from the CI commit but is not an ancestor of `HEAD` is replaced. An example is a map left from another branch.
6. A cached map whose ancestry check makes git error is replaced, and `fetch` does not exit non-zero because of that error.
7. The existing fetch cases in `tests/test-impact-cli.test.js` still pass unchanged. That includes the no-op at the chosen commit and the dirty map at the chosen commit being replaced.
8. Revert the widened check and show that the AC1 test fails.
9. `npm test` passes.

## Release Note

`tools/test-impact.js fetch` no longer replaces a fresher, clean local test-impact map with an older CI map.

## Technical Approach

Leave the existing equality short-circuit in place and add one branch next to it. That branch runs only when the cached map is valid, passing and clean, and its commit differs from `headSha`. It makes two `deps.git(['merge-base', '--is-ancestor', ...])` calls, each in its own try/catch, using the same pattern as the run-selection loop above it. The tests reuse the file's `mapText` helper and its fake `deps.git`, which answers per argument list.

### Key Files

- `tools/test-impact.js` — `fetch`'s cache check (around line 285)
- `tests/test-impact-cli.test.js` — the fetch section (around line 435): new keep/replace cases
- `plugin/bin/lib/verify/impact.js` — read only: the map-problem reasons that decide when `verify.js` calls `fetch`

## Gotchas

- Do not relax the downloaded-map checks: commit equals `headSha`, `exitCode` 0, not dirty. The new rule applies to the cached map only.
- Keep the `--end-of-options` guard on both new `merge-base` calls, because `cachedCommit` comes from a file.

## Current State

`tools/test-impact.js fetch` skips the download only when the cached map's `commit` equals the chosen CI run's head commit. A locally traced map at a newer commit (a developer ran `trace` on their branch) is replaced by an older ancestor map from CI on the next fetch, losing the fresher reads. `verify.js` runs `impact.fetch` only when the cached map has a problem (missing, stale, not an ancestor), so this happens only after such a problem, which limits the cost to one re-trace. A local map can also be traced with `--allow-dirty`, from a tree the map's commit does not describe (ledger row 27), which is why preferring it is not obviously safe.

## Open Question

Should `fetch` keep a cached map whose commit descends from the chosen CI commit (fresher, but locally produced and possibly from a dirty tree), or always take the CI map (older, but clean and from main)?
