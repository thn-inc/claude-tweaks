# 6057: Plan each sub-issue in /specify's decomposition mode after self-review

Surface: infra
Risk-flags: none

## Overview

Decomposition mode creates sub-issues at Step 3, links them at Step 4, red-teams them at Step 5 and self-reviews at Step 6, and Steps 3 to 9 may run in a subagent that cannot ask questions. Under `plan-at-specify: on`, planning must run once every sub-issue number exists (it names the ref and plan path) and the bodies are final, and it must run where a human can answer. This record adds the shaping-mode planning step to decomposition mode after Step 6, in specify's own session.

**Complexity:** Medium
**Estimated tasks:** 4-5

## Non-Goals

- The planning step itself (the shaping-mode record builds it; this record calls it).
- Parent records, which are never planned.

## Deliverables

1. After Step 6 (single-threaded) or after the mechanical handoff returns (delegated), specify runs the planning step per created sub-issue in its own session, dispatching planners and reviewers in parallel, one question batch for all sub-issues.
2. Each sub-issue gets one more body write carrying its `## Planning Decisions` section and `Plan:` line; a held sub-issue loses `ready` and gets `needs:decision` as in shaping mode, in the same planning pass as the body write, with the label edit a separate call after it. A held sibling does not hold the sub-issues that depend on it.
3. The mechanical handoff never plans; its prompt and summary say so.
4. Step 9's summary reports per sub-issue: planned, held, skipped (plan-less lane) or no-ref.
5. Tests pinning the placement and the parent exclusion.
6. **Interface.** Planning calls `planning.md`'s multi-record entry (from #6056), which takes N sub-issue numbers and returns one question batch and one outcome per record. Outcomes: `planned` (a `Plan:` line was stored), `held` (an asked-class question is unanswered), `skipped` (a plan-less lane takes it, per #6053), `no-ref` (`plan-store.js` reported no ref). A parent (a record carrying the `parent-issue` label) is never planned.
7. **Bodies.** Planning re-fetches each sub-issue's body from the forge after Step 6 (or after the handoff returns), so Step 5's red-team edits are always in what the reviewer reads.
8. **Delegated case.** The main thread appends the planning outcomes to the handoff's returned summary; the handoff itself never plans. Under `on` the dispatcher composes a sentence saying so into the handoff prompt; with `off` the prompt is unchanged.
9. **Headless.** With no human reachable (`/sweep`'s specify drain, a Routine) the question batch is not asked: a sub-issue with an asked-class question is held with `needs:decision` as in shaping mode.

## Acceptance Criteria

1. With `plan-at-specify: off`, decomposition mode is byte-identical to today's.
2. With `on`, every created non-parent sub-issue ends planned, held, skipped or no-ref, and Step 9 lists which.
3. Red-team edits from Step 5 are present in the body the reviewer reads.
4. No planning question is asked inside the mechanical-handoff subagent.
5. `npm test` passes.

## Release Note

With `plan-at-specify: on`, decomposing a design doc also plans and reviews each sub-issue.
