# 2401: Investigate: record #2329 built with no landed claims-registry claim (not the #2329 race itself)

Surface: infra

## Current State

Investigating record #2329's own claim state during its `/claude-tweaks:review`/`/wrap-up` pass
turned up an anomaly worth a dedicated look, separate from #2329's own fix.

- `claims/issue-2329.json` on the `claims-registry` branch shows a claim created at
  `2026-09-14T04:43:00.847Z` and released 12 seconds later at `2026-09-14T04:43:12.575Z`
  (reason `pr-opened: spec 2329`, linking PR #2399); both a claim comment and a release comment
  are posted on issue #2329 itself. **Correction:** an earlier pass of this investigation
  asserted the file had never existed (`git log --all -- claims/issue-2329.json` returning zero
  commits); that check was run without `origin/claims-registry` fetched locally and produced a
  false negative. `git show origin/claims-registry:claims/issue-2329.json` and
  `gh issue view 2329 --json comments` both show the real history. See Investigation Findings
  for why the corrected evidence still supports the same underlying anomaly.
- Yet the record was fully built: worktree `worktree-record-2329`, commits `19641f1f9`
  (materialize, `2026-09-14T06:12:33+02:00`) and `03233821d` (the fix itself,
  `2026-09-14T06:12:46+02:00`), pushed branch, draft PR #2399, and a full passing `npm test`
  (8783/8783) -- all present and real, and both commits predate the claim blob above by roughly
  30 minutes.
- This **rules out** the "unverified-claim leak" scenario #2329 itself fixes: that scenario
  requires a Step 2.8 write to land as a real commit just before the build, unconfirmed by its
  own read-back. The one blob that exists here was created *after* the build commits, not
  before, and was released 12 seconds later -- inconsistent with being the original Step 2.8
  claim (which must precede materialize) and far more consistent with a later pass (most
  plausibly the record's own `/wrap-up` Section E bookkeeping, which creates a claim-if-absent
  before writing a release tombstone) backfilling registry state after the fact. Either way, no
  live claim covered the actual build window, so this is not an instance of the bug #2329/PR
  #2399 fixes -- it's a distinct gap in whatever process claimed (or should have claimed) this
  record before building it.
- Per `plugin/skills/flow/claim-targets.md`, any non-zero `claim-targets.js` exit (3/4/5) should
  stop the pipeline **before** the Config Manifesto -- no worktree, no build. Since the build
  demonstrably happened, the claim step must have either reported success without a real write
  landing, or never run at all for this target.
- A related irregularity in the same run directory
  (`.claude-tweaks/pipelines/2026-09-14T040051-record-2329/`): `config.yml` was **never written**
  despite `decisions.md` already showing populated `/build` and `/test` entries (recovered via
  `steps-and-gates.md`'s adoption "case 3" during this review/wrap-up pass). `events.jsonl` shows
  a `pre-compact` event and a `session-end` (`reason: clear`, a different `sessionId`) in the
  ~6-minute window right after build+test completed and before this review/wrap-up pass started
  -- consistent with session-boundary instability around this specific run, though not confirmed
  as the root cause.

## Deliverables

## Technical Approach

Start from the two candidate root causes the Current State already narrows this to: (1) a bypass
path that reaches `/flow`'s build steps without ever calling `bin/claim-targets.js` for this
target -- audit every caller that can set `PIPELINE_RUN_DIR` to a dispatch-shaped value without
going through `/dispatch`'s own claim-then-hand-off flow; (2) a session-boundary/compaction
interaction around the Manifesto write -- the `pre-compact`/`session-end` events in the same
window are circumstantial, not confirmed, so reproducing that timing (or instrumenting the claim
step to log unconditionally, including a no-op/skip) is the concrete next step for either avenue.
This is explicitly open-ended: the Acceptance Criteria accepts either a root-cause explanation
or a mechanical safeguard, since the root cause may not be reproducible from historical evidence
alone.

## Investigation Findings

**Confirmed root cause (corrected during review).** An earlier pass of this investigation
asserted `claims/issue-2329.json` had never existed on `claims-registry`; that was a false
negative from running `git log --all` without `origin/claims-registry` fetched locally (see
Current State's Correction note). The real timeline, cross-checked against
`git show origin/claims-registry:claims/issue-2329.json`, `gh issue view 2329 --json comments`,
and the commit graph: #2329's materialize commit (`19641f1f9`) landed at
`2026-09-14T06:12:33+02:00` and its fix commit (`03233821d`) at `06:12:46+02:00` -- both real
code landing on the branch. The one claim blob that exists for issue #2329 was created at
`2026-09-14T04:43:00.847Z` UTC, roughly **30 minutes after** those commits, and released 12
seconds later (`04:43:12.575Z`, reason `pr-opened: spec 2329`, linking PR #2399 -- #2329's real
PR). A claim created after the work it is supposed to cover, then released within seconds,
cannot be the Step 2.8 claim a normal `/flow` run makes before `/build` starts -- it reads as a
later pass (most plausibly the record's own `/wrap-up` Section E bookkeeping, which creates a
claim-if-absent before writing a release tombstone) backfilling registry state after the fact,
not evidence that a live claim ever covered the actual build window. So the underlying anomaly
this investigation set out to explain is still real and still confirmed -- record #2329 reached
a full build and a landed fix commit with **no live claim covering that window** -- the
corrected evidence is more precise than "the file never existed," and strengthens rather than
undermines the conclusion. This is a second, earlier instance of exactly the failure mode #2492
diagnosed for issue #2322: a build/test dispatch can complete with nothing at build time
enforcing that a live claim exists.

Separately, and independent of this record's own timeline: `checkBookkeepingStampsGate`'s
`hasLoggedClaim` check (added by commit `0120f1fad`, #2526, landed 2026-09-20 -- six days after
#2329's build) is the first mechanical enforcement of `/flow` Step 2.8's claim-log step; before
that commit, Step 2.8 was prose-only ("no code path enforcing it independent of the
orchestrating agent's own compliance" -- `claim-targets.md`'s own words, written by #2492/#2525
the same day). Note this check is narrower than "a live claims-registry entry exists": it
verifies `decisions.md` logged the Step 2.8 claim call, which is a different (and more directly
checkable) signal than claims-registry state itself. It is nonetheless the only mechanical
safeguard that exists today, and it is closed today (verified live: this very run's own `git
push` was denied by `checkBookkeepingStampsGate` until its Step 2.8 claim was logged, see this
run's `decisions.md`).

**Secondary finding: stale documentation now corrected.** `claim-targets.md`'s "Known gap"
paragraph was never updated after #2526 shipped, so it still asserted (as of this
investigation) that no mechanical backstop existed -- contradicted by the very hook this
record's own build triggered. A pinning test (`tests/flow-claim-preflight.test.js`) enforced
the stale wording. Both are corrected in this build (see commit "Correct stale
claim-targets.md known-gap prose -- mechanical backstop shipped in #2526").

**Unconfirmed, separate anomaly (not resolved by this investigation).** The Current State's
second anomaly -- #2329's run directory never getting a `config.yml` despite `decisions.md`
showing populated `/build`/`/test` entries, with `pre-compact`/`session-end` events in the
same window -- remains circumstantial. It is plausibly unrelated to the claim-gap root cause
above (a session-boundary/compaction interaction, not a claim-enforcement gap) and is not
reproducible from available historical evidence. No further action taken on it here; flagged
for a human to judge whether it merits its own record if it recurs.
