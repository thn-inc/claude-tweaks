# Ledger item 19 (from #903 review, reflect hindsight evaluation 5)

**Origin:** ledger resolve gate, spec #903 review/hindsight
**Defer-reason:** tangential

## Current State

`/claude-tweaks:reflect` hindsight mode (invoked during #903's review) surfaced a general,
reusable pattern: a mechanized deterministic check that parses loose, real-world prose (not a
formal grammar) needs an explicit could-not-parse signal, never a silent `null`/skip that
collapses into a false negative. This is the exact shape of #903's own ledger item 18 (Check C's
`parseStep2`), but the lesson generalizes beyond plan-audit — any future "mechanize a hand-run
prose check" work in this repo is at risk of the same failure mode. No existing project skill
under `.claude/skills/` obviously covers this general lesson (the closest, `gh-api-module-pattern`,
is scoped to `gh`/`git`-shelling CLI conventions, not parser API design).

## Deliverables

- Either a new short section in an existing relevant skill, or a small new skill, stating the
  rule: when mechanizing a prose heuristic into a deterministic check, the "couldn't parse this
  input" case must be a distinguishable return value/signal, never silently identical to "this
  input legitimately doesn't apply."
- Cite #903's `plugin/bin/lib/plan-audit/parser.js` `parseStep2` as the worked example.

## Acceptance Criteria

1. A reader of the target skill can find this guidance when writing a new mechanized/deterministic
   check over free-form text.
2. The guidance names the concrete anti-pattern (collapsing "doesn't apply" and "couldn't parse"
   into one `null`/skip) and the concrete fix shape (a distinguishable signal + a surfaced warning).
