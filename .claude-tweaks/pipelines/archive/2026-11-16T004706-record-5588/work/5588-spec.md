# 5588: Rewrite git -C on the session's own worktree and an unquoted $? before the harness guard reads them

Surface: backend

**Related:** #4448, #4217, #5057, #5204, #4931, #4353, #4216
Risk-flags: none

## Current State

Claude Code's worktree-isolation guard refuses a Bash call it cannot show stays inside the session's worktree. The guard is harness code; the plugin cannot change what it accepts. What the plugin can change is what the guard is shown: `plugin/bin/lib/hooks/guard-rewrite.js` (#4028) rewrites five shapes in PreToolUse and returns the result as `hookSpecificOutput.updatedInput`, which the harness applies before its guard and then re-checks (`docs/reference/pretooluse-updatedinput-worktree-guard.md`). The five rule ids are `drop-redundant-cd`, `inline-literal-assignment`, `plugin-root-placeholder`, `node-eval-separator` and `quote-escaped-space`.

The process-efficiency design (`docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 3, unit 3.2) says "for each shape that only reads, the scanner admits it". How this differs from the design: 96.7% of the refusals it counted come from the harness guard, so there is nothing for a plugin scanner to admit. This record adds rewrite rules for the read-only shapes whose meaning is fully known from the text.

Measured on 2026-11-16 with a scratch classifier over the harness refusals of 2026-10-17 to 2026-11-16 (12,363 refusals, 3,606 of them read-only), and the last 14 days of that window (3,857 refusals, 1,186 read-only):

- **`git -C <the session's own worktree>`.** 729 refused commands name the session cwd in `git -C`; 442 only read, 269 of those in the last 14 days. 252 were refused as "redirects git through a glob pattern that expands at runtime": a `-C` plus a glob pathspec, for example `git -C "<worktree>" grep -n x -- plugin/bin/*.js`.
- **`git -C .`.** 65 refused commands, 54 read-only ("points git at a directory computed at runtime (-C .)").
- **An unquoted `$?` after a command.** 1,722 refused commands end a step with `; echo exit=$?` or the like; 171 only read. `plugin/skills/_shared/scratch-worktree.md` section 7 has this row for `gh`; the same refusal happens after a `git` read.

## Deliverables

1. **Rule `drop-git-C-cwd`.** It removes a `-C <dir>` that changes nothing:
   - `git -C . <rest>` becomes `git <rest>`, wherever the `git` command word sits in the command. `.` is the directory the shell is in at that point, so the two are the same command.
   - `git -C <literal> <rest>` becomes `git <rest>` when the literal spells the session cwd, by the same test `drop-redundant-cd` uses (the spelling equals the cwd after trailing slashes are trimmed, and both resolve to the same real path), and the text holds no `cd`, `pushd` or `popd` as a whole word.
   It declines on a second `-C`, on a `-C` that is not the first option after `git`, on an operand that holds `$`, a backtick, a glob character or `~`, and on anything `inDoubt` declines on.
   Decided 2026-11-16: the rule acts on a `git` word only where `atCommandStart` places it in the `TOP` context, and only when `commandWordsPlain` holds for the command, so `source`, `.`, `eval`, `trap`, a reserved word or a computed command word makes it decline, as they do for the two inlining rules. A `git` reached through `env`, `command`, `xargs`, an assignment prefix or a substitution is left alone. The operand is one of the three forms `LEADING_CD` accepts: single-quoted, double-quoted with no `$`, backtick or escape, or a bare word; a glued `-C<dir>` declines. The `cd`, `pushd` and `popd` test applies to the literal form only and looks for whole words anywhere in the text, quoted or not: a false match costs one rewrite and nothing else. `git -C .` needs no such test. The text `GIT_` anywhere makes the rule decline (4 of the window's refused `git -C` commands set such a variable). The literal form rests on the premise `drop-redundant-cd` already rests on: the shell starts in the cwd the hook input names.
2. **Rule `quote-exit-status`.** An unquoted top-level argument word made of one or more of the characters `A-Za-z0-9_.:=/-` followed by `$?` at its end is double-quoted: `echo exit=$?` becomes `echo "exit=$?"`. It declines when the command text holds `IFS`, when the word is a command word or an assignment, and on anything `inDoubt` declines on.
   Decided 2026-11-16: a bare `$?` is left alone, because its quoted form is refused too (probed 2026-11-16: `git rev-parse --short HEAD; echo "$?"` was refused, `…; echo "exit=$?"` ran). The rule fires only when the command text names `git` or `gh` as a whole word: `ls README.md; echo exit=$?` ran unrefused in the same probe, and a command the guard already accepts is not touched. It declines when the command word of the word's own command is `export`, `declare`, `local`, `readonly`, `typeset` or `env`, where a `name=value` argument is an assignment.
3. **Rule order.** `RULES` becomes: `drop-redundant-cd`, `inline-literal-assignment`, `plugin-root-placeholder`, `node-eval-separator`, `quote-escaped-space`, `drop-git-C-cwd`, `quote-exit-status`. `drop-git-C-cwd` runs after the two inlining rules so `W=/abs/wt; git -C "$W" log` is first inlined and then judged. The comment above `RULES` says so.
   Decided 2026-11-16: `drop-git-C-cwd` runs after `quote-escaped-space`, so `git -C /w/my\ wt log` is requoted and then judged in the same pass. The comment above `RULES` gives both reasons for the rule's place.

## Technical Approach

Both rules reuse the module's `scan()` contexts: act only on text in the `TOP` context, find command position with `atCommandStart`, and return `null` on doubt. Read the cwd test from `dropRedundantCd` and share it; do not write a second spelling comparison.

`drop-git-C-cwd` must keep `git -C` operands that are quoted with spaces working: the operand is one quoted span or one bare word. After removal, exactly one blank stays between `git` and the next word.

A rewrite never carries a permission decision and the harness re-checks the rewritten text, so a write is judged exactly as before; Deliverable 5 pins that its target does not move.
Decided 2026-11-16: `drop-git-C-cwd` fires only when the word after the operand is one of `log`, `show`, `diff`, `status`, `grep`, `rev-parse`, `rev-list`, `ls-files`, `ls-tree`, `merge-base`, `cat-file`, `blame`, `describe`, `for-each-ref`, `show-ref` and `check-ignore`. Dropping the option gives the same command for any subcommand, but the rewritten text is what the harness's permission rules then read, and how a rule written for the `-C` spelling treats the plain one was not measured. Keeping the rule to reads keeps that question away from writes, and reads are what this phase is for. The reference doc records the question as not measured. `quote-exit-status` changes no command word and is not restricted.

The transcript measurements in Current State were made before #5587, which adds effect and rewrite fields to `tools/guard-refusals.js`. If #5587 has landed, re-derive the three counts with it and put the fresh numbers in the PR.
