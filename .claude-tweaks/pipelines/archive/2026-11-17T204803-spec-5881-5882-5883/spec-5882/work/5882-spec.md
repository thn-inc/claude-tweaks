# 5882: Block releases while any open record carries the release-block label

Surface: backend
Risk-flags: public-contract

## Current State

A critical or high review finding about already-merged code has no durable effect on releases. In v6.171.0, a delta review found a high-severity security finding at `plugin/skills/_shared/skill-load-gate.md:8`, and it shipped because the release gate question was answered "Proceed". The answer lives only in that run's archived `decisions.md`. Nothing stops the next release, and nothing marks the finding as release-relevant.

The release-as-promotion design (parent #5838) needs a durable, explicit "do not release" signal. The rolling post-merge review and the release's own delta review will both set it, and every release gate will refuse while it is set.

## Deliverables

1. A `release-block` label, added to the bootstrap list in `_shared/label-bootstrap.md` with a description naming the clearing act.
2. `plugin/bin/release-block.js`, following the `gh-api-module-pattern` skill's runner seam and CLI wrapper contract:
   - `check` lists open records carrying `release-block`. Exits: 0 none; 1 blocked, printing JSON with each record's number, title and URL; 2 usage error; 3 state unreadable. Unreadable is never reported as clear. The repo resolves from `origin` like the other `plugin/bin` gh CLIs (`--repo` overrides). The query sets an explicit `--limit` (or pages), so a truncated list is never read as clear. A missing label reads as none (exit 0); auth and network errors exit 3. The exit-1 JSON shape and `stamp`'s exits (0 stamped or already stamped, 2 usage or no such record, 3 write failure) are part of the stable contract.
   - `stamp --record <n> --finding "<category> at <file:line>"` adds the label (bootstrapping it if missing) and posts one comment naming the finding and how to clear the block. The label is added before the comment, so a partial failure leaves a block with no comment, never the reverse. Re-stamping an already-labelled record is a no-op (no second comment). For a finding with no file:line, `--finding` reads `<category> at general`.
3. `plugin/skills/_shared/release-block.md`, the contract: what sets a block (any critical or high finding the rolling review or a release's delta review files as a record; or a human); how it clears (close the record, or remove the label — an explicit act); what a release does while one is open; and the gh-absent (MCP) equivalents of `check` and `stamp`.
4. `/claude-tweaks:release` runs `release-block.js check` before Step 3 and on every path, interactive and `--train`. A blocked release stops before any review or suite work, naming every blocking record. Under `--train` it ends `HELD` with `release-held.md` naming them. Register the stop as a HARD-GATE in `_shared/auto-mode-contract.md`. The check runs at a new Step 1.5, directly after Step 1's fact pack, before any review or suite work (Step 3's tree check, whole suite and review), and Step 4's console shows the block state (blocked records, or none). `--train` HELD reuses the existing `release-held.md` schema and HELD reason vocabulary; no autonomy ceiling clears the block, and the next firing re-runs `check`. When `gh` is absent, `check` takes the MCP path with the same exit codes, and an unavailable transport is exit 3.
5. When the release's Step 8 disposition files a critical or high finding as a record, it stamps `release-block` on that record (`disposition.md`).

**As built (architecture alignment, Beneficial):**
- Step 4 re-runs `check` just before rendering the console and holds the release before Step 5 on a block (`HELD`, `release-held.md`, no question), because a review run takes hours and a block can be stamped meanwhile; an unreadable re-read stops it `failed`.
- Any exit other than 0–3, or exit 1 without the `{"blocked":true,…}` line, is treated as unreadable (`failed`), so a crashed CLI never reads as clear or as an unnamed hold.
- `check --records-json <path>` takes already-fetched MCP rows with the same validation and exit codes, so the gh-absent path reuses the CLI rather than restating its rules.
- `stamp`'s `--finding` grammar (`isValidFinding`, linear) accepts a file part with spaces or colons and a line range (`a.js:12-15`); a `decisions.md`-only row with no category uses its severity word.
- A HELD reason phrase `release-block — {n} open record(s)` joins the HELD vocabulary, and a Step 1.5 hold reports `records: not computed (held at Step 1.5)`.

## Acceptance Criteria

- [ ] With one open record labelled `release-block`, `/claude-tweaks:release` stops before Step 3 with a message naming `#N` and its title; no review and no suite run starts.
- [ ] Under `--train`, the same state ends the firing `HELD`, and `release-held.md` names the record.
- [ ] With no such record, release behaviour is unchanged.
- [ ] When the label query fails, `check` exits 3 and the release stops, reporting "release-block state unreadable"; it never proceeds.
A malformed query result (output that is not parseable JSON, or a record missing its number, title or url) exits 3, state unreadable, never 0. Acceptance criterion: a fixture returning malformed JSON, and one returning a record without `url`, each make `check` exit 3 and the release stop.
- [ ] Step 8 filing a critical or high finding as a record leaves that record carrying `release-block` plus a comment naming the finding. Medium and low findings are not stamped.
- [ ] A closed record carrying the label does not block.
- [ ] A truncated or failed list read never reads as clear: `check` exits 3.
- [ ] Step 4's console shows the release-block state.

## Release Note

Releases now stop while any open record carries the `release-block` label, naming each blocking record; closing the record or removing the label lifts the block.

## Technical Approach

`release-block.js` is a thin CLI over `gh issue list --label release-block --state open` and `gh issue edit/comment`, with the injectable runner seam (`gh-api-module-pattern`). The release reads its exit code, never its prose.

### Key Files

- `plugin/bin/release-block.js` — new CLI (`check`, `stamp`)
- `plugin/skills/_shared/release-block.md` — new contract
- `plugin/skills/_shared/label-bootstrap.md` — add the `release-block` label
- `plugin/skills/_shared/auto-mode-contract.md` — register the release-block stop as a HARD-GATE

- `plugin/skills/release/disposition.md` — stamp critical/high findings filed as records

## Gotchas

- The rolling review (#5885) and the promotion gate (#5887) will call `stamp` and `check`; keep both verbs' exit codes stable once merged (expand-contract).
- Never infer "clear" from an empty result when the query itself failed: exit 3 is distinct from exit 0.
- A human clearing the block by removing the label is the durable form of today's "Proceed" override.
- The block is enforced inside the skill. A release that bypasses it (a manual tag, merging release-please's PR by hand) is not stopped; accepted, per the design.
- Clearing needs no stated reason: closing the record or removing the label is the explicit act. A clearing comment is recommended, not required.
