# 5883: Add a release-state branch store with a forward-only reviewed-through marker

Surface: backend
Risk-flags: public-contract

## Current State

The release-as-promotion design (parent #5838) needs two small pieces of shared state that outlive any run directory and are writable from both a local session and a cloud Routine sandbox, where `gh` may be absent:
- a **reviewed-through marker**: how far the rolling post-merge review has reviewed main;
- a **merge-pause flag**: built by #5884 on top of this store.

Run directories are local and per-run, and archived runs are never pushed, so a cloud Routine cannot read them. A bare git ref cannot reliably be moved over the MCP transport.

The precedent is `_shared/issue-claims.md`'s `claims-registry` branch (`plugin/bin/lib/issues/claim-store.js`). It holds JSON blobs on a dedicated branch, writes them compare-and-set on both transports (`git push --force-with-lease`, or a contents-API PUT carrying the blob sha), and creates the branch when it is missing (`ensureClaimsBranch`, `plugin/bin/lib/issues/claim-store.js:668`).

## Deliverables

1. `plugin/bin/lib/release-state/store.js`: read and compare-and-set write of a named JSON file on a dedicated `release-state` branch.
   - Mirrors `claim-store.js`'s transport handling and missing-branch creation.
   - Three distinct read outcomes: absent, present, unreadable.
   - `absent` only on a confirmed missing branch or missing file; malformed JSON, auth, 5xx and rate-limit failures are `unreadable`. `init` uses create-if-not-exists compare-and-set semantics, not a prior read. The compare-and-set is per file, and the store is the sole writer API for every file on the branch (the merge-pause flag shares it).
2. A marker file `reviewed-through.json` holding `{sha, advancedAt, run}`, with `advanceMarker(targetSha, run)`:
   - It moves only forward along `origin/main`'s first-parent line, so the target must be a first-parent descendant of the current marker.
   - A losing compare-and-set re-reads: a marker already at or past the target is success; otherwise it retries once.
   - `initMarker(sha)` is allowed only when no marker exists.
   - Advancing to the current marker's own sha is a successful no-op (no write). A retry after a lost compare-and-set re-validates the target against the freshly read marker. The file carries `version: 1`, `advancedAt` as ISO-8601 UTC and full 40-hex shas; `init` writes `run: "init"`.
   - The descent check needs a fetched, full-history `origin/main`: the CLI fetches it, and a shallow or stale clone that cannot answer exits with a distinct "insufficient history" code, never "refused". Without a local clone it uses the compare API.
3. `plugin/bin/release-state.js`, following the CLI wrapper contract (`gh-api-module-pattern`):
   - `marker read` prints JSON, with `{absent: true}` when there is no marker.
   - `marker advance --to <sha> --run <id>`.
   - `marker init --to <sha>`.
   - Documented exit codes: ok, backwards or non-descendant refused, contested after retry, unreadable, usage.
4. `plugin/skills/_shared/release-state.md`, the contract: the branch, file shapes, writer rules, exit codes, and the gh-absent (MCP contents-API) procedure.

## Acceptance Criteria

- [ ] Advancing the marker from A to a first-parent descendant B succeeds, and `marker read` then prints B.
- [ ] Advancing to a commit that is not a first-parent descendant of the current marker, or to an older one, exits with the documented "refused" code and writes nothing.
- [ ] Two concurrent advances from the same base: one wins, the other re-reads and reports success when the marker is at or past its target. A test proves this through an injected read seam (`lock-race-test-seam` skill), not by racing two processes.
- [ ] On a remote with no `release-state` branch, the first write creates it, and a read reports `absent`, distinct from `unreadable`.
- [ ] A failed read exits with the documented "unreadable" code and never reports `absent`.
- [ ] `marker init` refuses when a marker already exists.
- [ ] Advancing to the current marker's own sha exits ok and writes nothing.
- [ ] A shallow or stale checkout exits "insufficient history", not "refused".
A marker file that parses as JSON but lacks a valid 40-hex `sha`, or carries an unknown `version`, reads as `unreadable`: never `absent`, and never a marker. Acceptance criterion: each malformed shape exits with the documented unreadable code.
A force-push or history rewrite can orphan the marker, leaving its sha off `origin/main`'s first-parent line. `marker advance` then exits with a distinct `orphaned` code, not `refused`. Recovery is a guarded `marker reset --to <sha> --run <id>` verb: it requires the current marker to be orphaned, or `--force` with a logged reason; it requires the target to be on `origin/main`'s first-parent line; and it logs the reset. Acceptance criteria: an orphaned marker yields the `orphaned` code, and `marker reset` succeeds only under those guards.

## Release Note

No user-visible change.

## Technical Approach

Lift the transport-neutral compare-and-set from `claim-store.js` rather than re-deriving it. If that means extracting a shared helper, follow the `lib-module-split` skill. First-parent descent is checked with `git merge-base --is-ancestor` plus membership in `git rev-list --first-parent origin/main`; the `merge-shape-landed-proof` skill covers the shape.

## Gotchas

- `main` is unprotected and busy, and the store's branch is not `main`. Never write state to `main`: every write would trigger CI and race the fleet.
- The gh-absent path must be real. The rolling review runs in cloud Routine sandboxes (CLAUDE.md, Cloud parity).
- A marker that only moves forward is what makes a stale or replayed Routine firing harmless.
- Public contract: the `release-state` branch name, the `reviewed-through.json` shape and the exit codes are frozen once merged; the `version` field is the expand-contract seam. If a shared helper is extracted from `claim-store.js`, its claims-registry tests stay green.
