# 2364: dispatch: no skill to close out approved pending-review records (verify CI, merge, deploy)

Surface: infra

## Current State

`/claude-tweaks:dispatch` parks a group's PR as `pending-review` when it has no `auto:merge` grant, or `assess-agent-autonomy`'s `merge-check` mode declines auto-merge (`dispatch/SKILL.md`'s Auto-merge gate, `dispatch/settle-and-merge.md`). Under `integration-model: pr-first`, this PR is already public and current (`_shared/pr-early-run-lifecycle.md` opened it at run start; every phase exit since has pushed to it) — `dispatch/reporting.md`'s own note on parking states the branch "never waited on parking to become public in the first place."

Two distinct resumption paths already exist for a **still-active dispatch session**: `dispatch/reporting.md`'s "resuming a parked run" (re-invoking the same session to answer its Review Console) and `resume-confirmation.md`'s confirm-before-resume gate. Neither applies to this record's actual gap: a `pending-review` PR that a human reviews and approves **directly on GitHub**, days or weeks after the dispatching session ended, with no live session left to resume. For that case, nothing in the plugin re-verifies the PR's CI is still green (rather than stale from an earlier infrastructure blip), converts a still-draft PR to ready, flags a PR that quietly went from clean to conflicting while parked, or performs the merge (and any deploy) once approval is confirmed — all of it currently done by hand with raw `gh`/`git` commands. `/tidy`'s Step 4.8 (`_shared/github-pr-scan.md`'s `repo-wide` scope) already **surfaces** exactly this class of PR as a `STAGED` finding (report-only, per its documented "never edits" posture) — but surfacing is not closing out.

## Deliverables

- A close-out capability for an approved `pending-review` PR, covering at minimum: (1) re-verify CI is currently green (not a stale prior result), (2) convert a still-draft PR to ready-for-review/merge, (3) detect and flag a PR that has gone from mergeable to conflicting since it was parked, (4) merge on confirmed approval, with an optional deploy step where the project has one.
- A confirmation gate before merge — mirroring `resume-confirmation.md`'s existing "confirm before resuming" posture (unconditional at every `autonomy` tier, including `unattended`) — since this closes out a PR with no live session's Review Console already having asked the merge question.
- Decide where this capability lives: extending `/tidy`'s Step 4.8 `pending-review` surfacing from report-only into an actionable close-out lane (it already does the discovery work), or a new bare-drain-style mode on `/claude-tweaks:dispatch` that re-adopts a `pending-review` group's claim and runs the close-out sequence headlessly. Either integration point reuses existing machinery (`assess-agent-autonomy`'s `merge-check`, `_shared/pr-first-merge.md`'s merge mechanics, the claims protocol for re-adoption) rather than inventing a parallel one — this decision is left to the build step, not prescribed here.

## Acceptance Criteria

- [ ] Given a `pending-review` PR whose CI last ran before an infrastructure outage, the close-out re-runs or re-checks CI before treating it as green.
- [ ] Given a still-draft `pending-review` PR with human approval, the close-out converts it to ready before merging.
- [ ] Given a `pending-review` PR that has gone from clean to conflicting while parked, the close-out flags it rather than attempting a merge.
- [ ] Given a clean, approved, CI-green `pending-review` PR, the close-out merges it (and runs any project deploy step) only after an explicit confirmation gate — never silently, at any `autonomy` tier.
- [ ] The chosen integration point (extended `/tidy` Step 4.8, or a new `/dispatch` mode) is documented in `docs/plugin-structure.md`'s command reference and, if a new mode, added to `docs/skill-graph.md`'s edges per CLAUDE.md's cross-reference rule.
- [ ] `npm test` passes.

## Technical Approach

Reuse existing machinery rather than building parallel logic: `assess-agent-autonomy`'s `merge-check` mode for the mergeability/CI judgment, `_shared/pr-first-merge.md` for the actual `gh pr merge` mechanics, and the issue-claims protocol (`_shared/issue-claims.md`) to re-adopt a `pending-review` group's original claim (still held, since parking never releases it) rather than starting a fresh one. `resume-confirmation.md`'s existing `AskUserQuestion` shape and Recommended-derivation rule are the direct model for this record's own confirmation gate — read that file before designing a new one, since the two must never disagree on the same PR's state if a human could reach either path for the same PR. Start the "where does this live" decision (see Deliverables) by reading `/tidy`'s Step 4.8 surfacing logic (`_shared/github-pr-scan.md`) and `dispatch/reporting.md`'s parking/resumption sections side by side.

### Key Files

- `plugin/skills/dispatch/reporting.md` — `pending-review` parking semantics, read-only reference
- `plugin/skills/dispatch/resume-confirmation.md` — the confirmation-gate model to follow
- `plugin/skills/dispatch/settle-and-merge.md` — the Auto-merge gate and merge-check invocation this reuses
- `plugin/skills/_shared/pr-first-merge.md` — the merge mechanics to reuse, not re-invent
- `plugin/skills/_shared/issue-claims.md` — re-adopting a still-held `pending-review` claim
- `plugin/skills/tidy/actions-github-issues.md` / `_shared/github-pr-scan.md` — the existing `pending-review` surfacing this record extends, if that integration point is chosen
- `docs/plugin-structure.md`, `docs/skill-graph.md` — update per whichever integration point is chosen

## Gotchas

- Merging without a fresh confirmation is exactly the auto-mode contract's concern this repo already legislates against — see `resume-confirmation.md`'s note on why that confirmation "carries no `autonomy`-ceiling carve-out (unconditional at every tier, including `unattended`)"; this record's own confirmation gate must hold the same line, not a weaker one, even though it runs outside a live dispatch session.
- A `pending-review` PR's original claim is still held (parking never releases it) — re-adopting it at close-out time must go through the same read-then-classify protocol as any other claim operation, not assume it's free to take.
- `/tidy`'s Step 4.8 is documented as report-only ("never edits") — extending it into an actionable close-out lane is a deliberate posture change for that scope specifically, not a blanket precedent for the rest of `/tidy`.
