# 2070: session-start.js resolves CLAUDE_PLUGIN_ROOT twice in run() with different, disagreeing fallbacks

## Current State
`plugin/bin/lib/hooks/session-start.js`'s `run()` (line 56) reads `process.env.CLAUDE_PLUGIN_ROOT` twice: once implicitly via `resolveBuildLine()` (line 80, called with no args so it defaults to `process.env` — the function's own signature at line 43 is `resolveBuildLine(env = process.env)`), and again explicitly at line 97 (`const pluginRoot = process.env.CLAUDE_PLUGIN_ROOT || '${CLAUDE_PLUGIN_ROOT}';`) for the stale-runs report line. The two reads currently agree at runtime (nothing mutates the env var between them), but a future normalization fix (trimming, validation) applied to one read has no shared place to land and is easy to apply to only one of the two.

## Deliverables
- [ ] Capture `process.env.CLAUDE_PLUGIN_ROOT` once as a local (e.g. `const pluginRootEnv = process.env.CLAUDE_PLUGIN_ROOT;`) near the top of `run()`.
- [ ] Pass that single captured value into `resolveBuildLine`'s call at line 80 as `resolveBuildLine({ CLAUDE_PLUGIN_ROOT: pluginRootEnv })`, preserving `resolveBuildLine`'s existing `(env = process.env)` signature unchanged (it is exported and directly unit-tested with `env`-object arguments in `tests/hooks-session-start.test.js` — lines 217, 225, 231, 241 — so the signature itself must not change).
- [ ] Derive line 97's fallback from the same captured value: `pluginRootEnv || '${CLAUDE_PLUGIN_ROOT}'`.

## Acceptance Criteria
1. A single `process.env.CLAUDE_PLUGIN_ROOT` read feeds both the build-line message and the stale-runs report line (verify by inspection, or by a test injecting a custom `ctx`/env stand-in and confirming both derived values track a single source).
2. All four existing `resolveBuildLine` tests (`tests/hooks-session-start.test.js:214-243`) pass unchanged — the function's signature and behavior are untouched, only its caller changes.
3. `run()`'s existing stale-runs report tests are unaffected by the fallback expression's source change (same literal fallback string, same value when the env var is set).

## Technical Approach
`resolveBuildLine`'s null-fallback (skip the build line when plugin root is unknown) and line 97's display-placeholder fallback (`'${CLAUDE_PLUGIN_ROOT}'`, a shell-substitutable token shown in a copy-pasteable report command) serve genuinely different purposes for genuinely different consumers — this isn't a case where the two fallback *values* should be unified into one. What should be shared is the single upstream read of the env var itself, so a future validation/trimming step has exactly one place to apply, per the record's own stated risk (a fix applied to one site and missed on the other). Capturing the raw value once and threading it into both consumers (rather than changing `resolveBuildLine`'s tested signature) is the surgical fix.

### Key Files
- `plugin/bin/lib/hooks/session-start.js` — `resolveBuildLine` (line 43, signature must stay stable), its call site (line 80), the second read (line 97)
- `tests/hooks-session-start.test.js` — existing `resolveBuildLine` tests (lines 214-243) that must keep passing unchanged

## Gotchas
- Do not change `resolveBuildLine`'s `(env = process.env)` signature to take a raw string — it is exported and its existing tests call it with `env`-shaped objects (`{CLAUDE_PLUGIN_ROOT: root}`, `{}`). Wrap the shared value in a one-key object at the call site instead.
- Line 97's comment ("Hoisted once and reused below") already documents a *different*, already-fixed duplicate-computation issue (the `.map` previously computing the same expression twice) — don't conflate that with this record's two-separate-functions issue.
