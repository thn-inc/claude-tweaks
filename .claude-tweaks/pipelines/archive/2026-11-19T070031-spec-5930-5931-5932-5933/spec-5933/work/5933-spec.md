# 5933: Require evidence and cap the records a run files

Surface: backend
Risk-flags: public-contract

## Overview

Adds two frictions to records an agent files from a run, each a policy value that is off by default: the item must carry an evidence line, and a run may file only so many records. An item that fails either goes to the digest, where it stays visible, can still be promoted, and expires if nobody does. Filing needs no evidence today, and nothing counts what a run files; runs filed 317 records in the 11 days to 18 November 2026, about two per merged pull request. See #5930 for the Decision Rationale.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- Running a test to prove it fails. The check is that the item names its evidence in a checkable form.
- Records a human types through `/claude-tweaks:capture`.
- Records filed outside a run by the health sweeps, the reconciler or `/claude-tweaks:feedback`.
- Refusing an item outright. An item that fails a friction is routed to the digest, never dropped and never left stuck.

## Deliverables

- [ ] Policy key `filed-record-evidence` (the name is final): `off` (default) or `required`.
- [ ] With `required`, an agent-raised item whose verdict would be `file` and whose reason is `pre-existing-outside-diff`, `genuinely-larger` or `tangential` needs `--evidence {kind}:{ref}`. Without valid evidence the verdict is `digest`, rule `no-evidence`.
- [ ] **Closed rule for evidence:** the kinds are exactly `test` and `ref`. `test:{path}` is valid when the path names an existing file inside the working tree. `ref:{id}` is valid when the id matches `#{digits}` or `IL-{digits}`. Any other kind, an empty ref, or a path outside the working tree is invalid evidence, which is treated as none. `test:{path}` is resolved with `realpath` against the git top level of the working tree the CLI runs in, and is valid only when the result is a regular file whose real path stays under that top level; an absolute path, a scheme prefix, a percent escape, a trailing slash, a directory, or a symlink whose target leaves the tree is invalid. The other four reasons (`needs-human-decision`, `blocked-external`, `blocked-dependency`, `needs-verification`) need no evidence. A reason added to `DEFER_REASONS` later is exempt until this list names it, and a test fails when a `DEFER_REASONS` member is in neither group. The check is form-only on purpose: a speed bump that cannot detect a fabricated citation, with `ref` existence and relevance out of scope. A plan review that finds another unlisted state adds its handling as a plan amendment, never as a needs-human gap.
- [ ] Policy key `run-filed-record-cap` (the name is final): a non-negative integer, unset by default (no cap).
- [ ] With a cap and `--run {dir}`, the CLI appends one line to a tally file in that run directory for each `file` verdict it gives, and once the tally has reached the cap the verdict is `digest`, rule `run-cap`. Without `--run` there is no cap. A `--run` that fails the anchoring guard exits non-zero with a line naming the path and gives no verdict; it is never read as uncapped.
- [ ] **Cap semantics:** the CLI reads the tally count (non-empty lines), applies the cap clause, and appends a line only when the final verdict is `file` for an agent-raised item. The cap applies to every agent-raised item that would otherwise file, exempt reasons included. A `high` or `critical` severity files regardless and is counted, so the tally can pass the cap through that bypass alone, and the next call without such a severity then prints `digest`. A `--human` call is never tallied. Only the line count is read, so tally content cannot be malformed. The cap is best-effort under concurrency: parallel callers in one run can each read the count before any appends, so a run can file up to the cap plus the number of simultaneous callers; each single-line append is atomic. A repeated call for the same item is counted again.
- [ ] Precedence, extending #5932's: human input files; a `high` or `critical` severity files and is counted; a listed digest reason digests; the three-axis floor; then evidence; then the cap.
- [ ] `specShapedBody` accepts `provenance.evidence` and writes an `Evidence: {kind}:{ref}` line right after `Defer-reason:`; `plugin/skills/_shared/deferral-gate.md`'s "Where the reason lives" names the line for staged proposals and created records.
- [ ] `plugin/skills/_shared/materiality-floor.md`'s command form gains `--evidence` and `--run`.
- [ ] `plugin/skills/_shared/deferral-gate.md` says how a producer writes the evidence line: `Evidence: test:{path}` naming a test file that covers the defect, or `Evidence: ref:{id}` naming an existing record or incident. `plugin/skills/_shared/materiality-floor.md`'s command form tells a routing site to pass `--evidence` with that line's value when the item carries one, and to omit the flag otherwise.
- [ ] This repository's `.claude-tweaks/policy.yml` sets `filed-record-evidence: required` and `run-filed-record-cap: 1`.
- [ ] Tests for both frictions, the precedence and the tally.

## Release Note

Added two optional limits on follow-up work a pipeline run files: each record must name its evidence, and a run can file only a set number of records.

## Technical Approach

Both frictions are clauses in the one routing function, so the verdict stays `file`, `digest` or `refused` and every routing site gets the cap without change. Evidence is different: a site passes `--evidence` only when the item's proposal already carries an `Evidence: test:…` or `Evidence: ref:…` line. Review and reflect findings carry a file-and-line pointer, which is neither, so with `required` an agent item with one of the three evidence-requiring reasons and no such line goes to the digest. The maintainer chose this strict reading on 2026-11-19: a named test file, or an existing record or incident number, is the only evidence, and digesting the rest is the intended friction. Evidence is checked for form, cheaply and offline: an agent that must name a test file or an existing record or incident has to have one. The tally is the CLI's own file in the run directory, written through the repository's run-directory writer conventions, because no existing file records filings in one form.
