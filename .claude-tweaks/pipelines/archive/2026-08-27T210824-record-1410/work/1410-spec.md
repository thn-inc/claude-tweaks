# 1410: hooks: ask-user-question events can be attributed to the wrong concurrent pipeline run's events.jsonl

Surface: backend

## Current State

During record #1194's `/claude-tweaks:wrap-up`, this run's own `{run-dir}/events.jsonl` contained
one `ask-user-question` entry whose question text referenced records #1275/#800/#1369 — none of
which belong to record #1194's pipeline run. This run's own genuine interactive decision (a
git-strategy choice made at session start) never appeared in the log at all. Every entry in the
file carried `"attribution":"fallback"`.

Confirmed by reading `plugin/bin/lib/hooks/context.js`'s `resolveRun` (lines 218-246): when a
session's identity is known but the run it should own was never stamped with that ownership
(`state.sessionId` unset — e.g. no `record-worktree` call landed yet, or `PIPELINE_RUN_DIR` isn't
set), `resolveRun` falls through to `attribution: 'fallback'` and returns the newest run dir under
`cwd` whose `state.sessionId` is empty and that isn't an unadopted mint — regardless of which
session's worktree that run dir actually belongs to. With 3+ sibling pipeline runs active
concurrently, more than one run dir can be unowned at the same instant (each hasn't reached its own
ownership-stamping call yet), so "newest unowned run" is not the same guarantee as "this session's
own run." `post-tool-use.js`'s `logAskUserQuestion` (line 518) calls `ctxLib.appendEvent(ownedRun.dir,
'ask-user-question', ..., ownedRun.attribution)` using whatever `resolveRun` handed back, with no
further check that the resolved dir actually belongs to the calling session.

`/claude-tweaks:reflect`'s Friction lens reads `events.jsonl` to judge pipeline-inflicted friction
for a given run, so a misattributed event feeds it evidence from a run it was never part of.

## Deliverables

- Determine why `resolveRun`'s `'fallback'` branch (context.js:232-245) is reachable at the point
  `logAskUserQuestion` needs a run dir for an `AskUserQuestion` call made mid-session — i.e. why this
  session's own run wasn't already ownership-stamped by the time the question fired.
- Decide whether the `ask-user-question` write path should instead drop the event (never write
  under `'fallback'` attribution) or attribute it more conservatively when ownership can't be
  confirmed, and implement that decision in `post-tool-use.js`'s `logAskUserQuestion` and/or
  `context.js`'s `resolveRun`/`appendEvent`.
- Ensure `/claude-tweaks:reflect`'s Friction lens is never fed another run's `ask-user-question`
  events as a result of this fix.

## Acceptance Criteria

- [ ] Root cause of the `'fallback'`-attribution misroute identified and stated (which code path
      leaves a session's own run unowned at the moment an `ask-user-question` event needs logging)
- [ ] Fix applied so a concurrent sibling run's `ask-user-question` event is never written into
      this run's own `events.jsonl` (either by refusing to log under unconfirmed attribution, or by
      resolving ownership correctly before logging)
- [ ] Regression test added covering the concurrent-runs case: two sibling run dirs, neither yet
      ownership-stamped, and an `ask-user-question` event fired in one session's context

## Technical Approach

Investigate and fix within `plugin/bin/lib/hooks/context.js`'s `resolveRun` (the attribution
decision) and `plugin/bin/lib/hooks/post-tool-use.js`'s `logAskUserQuestion` (the write call that
consumes it). `resolveRun`'s own comment block (context.js:194-217) already documents the
`'fallback'`/`'session'`/`'env'`/null-dir distinction and the "guessing here is what cross-
contaminated events.jsonl" risk for the general case — this record is the concrete case where that
documented risk fires under real concurrency. Whatever fix is chosen must not weaken the sanctioned
exception already carved out for console execution (context.js:209-217), which deliberately acts on
a run its owning session has already exited.

### Key Files

- `plugin/bin/lib/hooks/context.js` — `resolveRun`'s `'fallback'` branch and `appendEvent`'s
  `attribution === 'fallback'` gate (line 495) are the attribution logic to fix
- `plugin/bin/lib/hooks/post-tool-use.js` — `logAskUserQuestion` (line 518) is the call site that
  writes an `ask-user-question` event using `ownedRun.attribution`
- `tests/bin-lib/hooks/` — regression test for the concurrent-runs, neither-side-ownership-stamped
  case belongs alongside this suite's existing `context.js`/`post-tool-use.js` coverage

## Gotchas

- This is reported as an observation from one run's audit trail (record #1194's), not independently
  reproduced in isolation — confirming the exact concurrent-timing window (both sibling runs unowned

- Any fix touching `resolveRun`'s ownership-fallback semantics must preserve the console-execution
