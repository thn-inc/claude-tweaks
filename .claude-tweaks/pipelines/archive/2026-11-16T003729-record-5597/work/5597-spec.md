# 5597: Count agents started by a workflow script in timing.json

Surface: backend

**Related:** #5555, #5556, #5557, #5466, #5495, #5013, #5093, #5092, #4259, #3872
Risk-flags: none

## Current State

`timing.json` counts a run's subagents and their tokens from two places. `readDispatches` (`plugin/bin/lib/timing/transcript.js:268`) reads the `agent-{id}.jsonl` and `agent-{id}.meta.json` files that sit directly in a session's `subagents/` directory. `classifyToolCall` (`plugin/bin/lib/timing/turn-class.js:185`) classes an `Agent` or `Task` tool call as `dispatch`, and a phase's `subagents` number is that count (`plugin/bin/lib/timing/derive.js:368`).

An agent started by a workflow script is in neither. Observed on 2026-11-16 in the files of two workflow runs made on 2026-11-15 with Claude Code CLI 2.1.325 (5 and 24 agents):

- The agents' transcripts are one level down: `{session}/subagents/workflows/{runId}/agent-{id}.jsonl`, each with an `agent-{id}.meta.json`, beside one `journal.jsonl` per run.
- The meta file's keys are `agentType` (`workflow-subagent`), `description` (the label the script gave the agent), `workflowPhase`, `spawnDepth`, `model` (the alias the script passed: `haiku`, `sonnet` or `opus`), `isBuiltIn`, `requestShape`, `requestNonInteractive` and `pickedEffortModel`. The one Task agent meta sampled has `toolUseId` and `launchedWithDefaults` and no `workflowPhase`.
- The transcripts carry `message.usage` rows like any subagent transcript (3 of the 27 lines in the one sampled).
- `journal.jsonl` has one `started` line per agent (`agentId`, `label`, `phase`) and one `result` line per agent.
- `{session}/workflows/{runId}.json` holds the run's `agentCount`, `totalTokens`, `durationMs` and `status`.
- The Claude Code documentation does not describe this layout. It says only that a run's script and results live under the session directory.

So a run that starts agents through a workflow reports them nowhere: `timing.json`'s `dispatches` lists none of them, and the phase's `subagents` count is unchanged, because the `Workflow` call is classed `other`. A step that moves from Task dispatch to a workflow would then look cheaper than it is. Two things are about to do that: the review replay tool (#5557) starts about 70 agents through a workflow, and #5599 moves the review step's lens reviewers onto one. #5599's done criterion compares cost between the two dispatch forms, so it needs both counted the same way.

Other readers of `subagents/` that also see only its direct children: `plugin/bin/skill-load-report.js:239`, `plugin/bin/lib/skill-audit/transcript-load.js`, `plugin/bin/lib/timing/context-gauge.js`, `tools/guard-refusals/transcripts.js:98` and `tools/replay-scratch/counterfactual.js`.

Design: `docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 6 (its unverified item on how a workflow agent's transcript and token use reach `timing.json`).

## Deliverables

1. **Workflow agents are dispatches.** `readDispatches` also reads every `workflows/{runId}/` directory under the `subagents/` directory it is given. Each item it returns gains `workflowRunId` and `workflowPhase`, both `null` for a Task agent. Token totals, the run window, the model tier (from the meta file's `model`, which `resolveTier` already reads) and the role (from `description`, through `roleOf`) work as they do for a Task agent.
2. **The same refusals.** A symlinked `workflows/` directory, run directory or agent file is not followed, and an entry that cannot be proven a regular file is skipped and named, exactly as `readDispatches` treats the direct children today. A run directory with no agent file is named in the result, not silently empty. The function still never throws. Decided 2026-11-16: `notFound` keeps its one-string shape and is set only when no item came from any scanned directory. A direct directory with no agent file beside a `workflows/` directory that yields items is not `notFound`. Each run directory's own problem (a symlink, an unreadable directory, no agent file) is one string in a new array key, `dirNotes`, in the wording the direct directory gets today with the run directory's path; `phase-timing.js` adds them to its `notFoundDirs` lines. A workflow agent whose meta file is missing or unreadable is still an item, with `workflowRunId` set from the directory name, `workflowPhase` `null` and the note a Task agent gets. Window clipping and `excludedOutsideWindow` apply to every scanned directory alike, and the phase count uses the clipped list.
3. **The call is a dispatch turn.** `classifyToolCall` classes a `Workflow` tool call as `dispatch`.
4. **A phase's `subagents` counts agents.** For a phase, `subagents` is the number of `Agent` and `Task` calls in its span plus the number of workflow agents whose first transcript row falls in its span. The `Workflow` call itself adds none. With no workflow agent in a run, every number in `timing.json` is what it is today. Decided 2026-11-16: `subagents` stops reading the `dispatch` turn-class count. Each usage row gains `agentCalls`, the number of `Agent` and `Task` calls in it; `joinTokens` sums that per phase and adds the workflow agents it is given. Three numbers then differ by design, and the docs of Deliverable 6 say so: the `dispatch` turn class counts calls (`Agent`, `Task` and `Workflow`), `subagents` counts agents, and `dispatches` lists the agents whose transcripts were found. #5556's per-step agent count reads `subagents`. A workflow item carries no `toolUseId`; checked on 2026-11-16, no file under `plugin/bin/lib/timing/`, `plugin/bin/phase-timing.js` or `tools/efficiency-report.js` names that key, so nothing joins a dispatch item to a call by it.
5. **Other readers.** The PR carries a table of the five readers named above: for each, whether it now sees workflow agents and why. Each one left unchanged that should see them is named in one follow-up record filed through `/claude-tweaks:capture`. The rule for "should see them": a reader whose output totals subagent tokens, context or agent counts for a session must include workflow agents; a reader that only identifies one caller's transcript need not. Each row states which of the two its reader is.
6. **Docs.** The header comment of `transcript.js` and `docs/plugin-structure.md` describe both layouts and say the workflow one was observed on CLI 2.1.325 and is not documented.

## Technical Approach

Keep one listing rule. `readDispatches` already pairs meta and transcript by agent id, refuses symlinks and reads usage through `readUsage`; give it the list of directories to scan (the `subagents/` directory, then each run directory under `workflows/`) and reuse the per-directory body. Agent ids are unique per session, so the two layouts cannot collide.

`subagentsDirFor` maps a transcript path to its `subagents/` directory. A path that points at a workflow agent's own transcript (`…/subagents/workflows/{runId}/agent-{id}.jsonl`) resolves to the session's `subagents/` directory, not to the run directory. This is a change to `subagentsDirFor` and has its own test. Its two callers are `plugin/bin/phase-timing.js:281` and `plugin/bin/lib/timing/context-gauge.js:205`; both pass the transcript paths they located or were given, which are main transcripts in every documented call, so neither changes behaviour for those, and the reader table of Deliverable 5 has a row for each. Agents a workflow agent starts itself (`spawnDepth` above 1) were not observed: they are read when their files sit in the same run directory and are otherwise not found, and the docs say so.

For Deliverable 4, the workflow agents' start times come from the items `readDispatches` returns (`startTs`). `joinTokens` stays pure: it takes the workflow agents' start times as a third argument. #5555 moves the code that calls it from `plugin/bin/phase-timing.js` into a module under `plugin/bin/lib/timing/`. If #5555 has landed when this is built, change the call there; if not, change it in `phase-timing.js`. Decided 2026-11-16: a workflow agent is placed by its own start (`startTs`) under the rule `joinTokens` already applies to a usage row: the innermost phase whose `[start, end)` holds it. An agent that starts outside every phase counts in `unattributed.subagents` and in the run total. An agent with no `startTs` is in `dispatches` with its `notFound` note and in no count. The `Workflow` call is not the anchor, because a run can outlive the phase that started it and each agent's tokens are spent where it runs.

Fixtures are hand-written and hold only what a test asserts: a few usage rows and the meta keys. No real transcript is copied in.

## Gotchas

- The layout is undocumented and observed on one CLI version. Read it defensively: an unknown file or a missing key is a note in the result, never a throw and never a zero-filled row. #5596's probe document re-checks the layout; if it has landed and differs, follow it. Decided 2026-11-16: the run file's `agentCount` is the cross-check. When `{session}/workflows/{runId}.json` is readable and its `agentCount` differs from the number of agents found in that run's directory, `dirNotes` gets one string with both numbers; an absent run file adds no note. `totalTokens` is not compared, because what it sums is not documented. A workflow agent's tokens are in its own transcript only: the main transcript's rows are the main session's own turns, as with an `Agent` call, so nothing is counted twice. This record is not blocked by #5596: it reads the layout observed on CLI 2.1.325 and notes anything else.
- `timing.json` is read by `tools/efficiency-report.js`, the budget check and the summary templates, and from #5556 on by the step yield writer, whose per-step agent count comes from this data. The new item keys are additions; no existing key changes meaning except a phase's `subagents`, and that changes only for a run that has workflow agents.
- #5555 (in progress) restructures `phase-timing.js` and writes `timing.json` when a run closes. #5556, #5466, #5495, #5013, #5093, #5092 and #4259 edit `plugin/bin/lib/timing/derive.js`; #3872 edits `transcript.js`. Rebase on whichever has landed.
- A run on the previous plugin release may be closed by this release's code, and the reverse. A session directory with no `workflows/` directory is the common case and must cost one failed directory read, nothing more.
- A twelve-hour session's transcripts are large. `readUsage` streams; keep it that way for workflow agents.
- A workflow agent's `description` is whatever label its script chose. Only a label a `ROLE_PATTERNS` entry matches gets a role; the rest are `unlabelled`, and growth there is the drift signal, as today. #5599 labels its agents `lens {lens} A` and `lens {lens} B`, which the `lens reviewer` pattern in `ROLE_PATTERNS` matches (`/^((review|delta) )?lens \d/i`, `derive.js:440`), and its AC2 pins those labels. #5557's replay labels are its own and may read `unlabelled`; that changes the role table only, never a count or a token total.
- Read `.claude/skills/windows-checkout-test-parity` before asserting a path in a test, and `.claude/skills/parse-signal-discipline` for the difference between "no workflow directory" and "could not read it".

## Build Decisions

Recorded by /build Common Step 4.5 (decision rule: keep the previous release working, rule in code, inside Key Files).

- `readDispatches` items carry `workflowRunId`/`workflowPhase` (null for a Task agent), but `timing.json` drops the two keys from an item when both are null, so a run with no workflow agents stays byte-identical (AC8). A `timing.json` consumer reads a missing key as null.
- `notFound` is null whenever any scanned directory had an agent id, so a window that clips every agent keeps today's `items: []`, `notFound: null`.
- Run-directory problems use the direct directory's wording with the noun `workflow run directory` (or `workflows/ directory`); an empty run directory gets only its `no agent-* transcripts in` note, the run-file cross-check is skipped for it (AC6: one note).
- A run file that is absent, not a regular file, unreadable or unparsable adds no note: it only feeds the `agentCount` cross-check.
- `joinTokens` reads a usage row with no numeric `agentCalls` (a hand-built or older row) as its `turnClasses.dispatch` count; `readUsage` sets `agentCalls` on user rows only.
- The run window clips workflow agents (Deliverable 2) but not main-transcript rows, so an `Agent` call after the last event still counts in `unattributed.subagents` while a workflow agent started then is excluded from every count. AC9's unattributed case is met for an agent starting inside the event window after the last phase closes.
