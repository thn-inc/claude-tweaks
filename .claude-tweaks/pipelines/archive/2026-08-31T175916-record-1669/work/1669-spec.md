# 1669: backlog-grant-gate.js's new 30s runner timeout may hard-fail the exact large-backlog fetch it was fixing for

Defer-reason: tangential

## Current State

`plugin/bin/backlog-grant-gate.js:21` — the ENOBUFS fix (commit 3c824aea9, "Fix ENOBUFS crash in backlog-grant-gate.js's gh/git runners") widened the shared `runner`'s `execFileSync` options with `maxBuffer: 64 * 1024 * 1024` and `timeout: 30000`. That `runner` is reused for every `gh` call this file makes, including the large `--state all` batched backlog fetch (up to `backlog-fetch-limit`, default 1000 records, full bodies) that the file's own adjacent comment says "routinely exceeds" the 1MB `execFileSync` buffer default — the exact call the maxBuffer widening was meant to fix. Previously `execFileSync` carried no timeout at all (verified empirically against the pre-fix code — no 5-second default as an earlier comment claimed), so a slow-but-successful fetch always eventually completed. The new 30000ms timeout applies to that same large fetch, so a `gh issue list --state all` taking longer than 30s on a large backlog or slow network now hard-fails with `ETIMEDOUT` instead of eventually succeeding.

## Resolution

**Branch taken: not confirmed as a live issue — no code change.**

The concern is already moot in the current tree. Reading `plugin/bin/backlog-grant-gate.js`'s
`realDeps.runner` (line 101) and its git history:

- Commit `3c824aea9` ("Fix ENOBUFS crash in backlog-grant-gate.js's gh/git runners", 2026-08-29
  17:30 UTC+2) is the one this record flags — it added `maxBuffer: 64MB` and `timeout: 30000` to
  the shared `runner`.
- Commit `50368110c` ("Address whole-branch review findings on the ENOBUFS fix (#1658)",
  2026-08-29 17:45 UTC+2 — 15 minutes later, same day) already **removed** the 30s timeout from
  that exact runner, for exactly the reason this record raises: "the fetch it bounds scales with
  `backlog-fetch-limit` and can legitimately exceed 30s, and this CLI runs unattended (scheduled
  Routine) with no human to retry a spurious timeout-kill." The current code (line 94-101) carries
  an explanatory comment documenting this decision and applies **no timeout at all** to the `gh`
  runner — only `maxBuffer: LARGE_MAX_BUFFER_BYTES` (consolidated in the same commit into
  `shared-primitives.js`).
- This record was evidently filed (via an automated `/code-review` pass, per its own Technical
  Approach section) against a tree state that predates or missed commit `50368110c` landing — the
  observation was accurate at the moment `3c824aea9` alone was visible, but the very next commit
  in the same session already fixed it.

No reproduction against a live large-backlog fetch is needed: there is no `timeout` value left on
the runner to exceed. `npm test` passes unchanged (no code modified this build).
