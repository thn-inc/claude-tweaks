# 2249: timing/derive.js NESTED_PARENT missing three real nested-invocation sites (deepen, stories, feedback)

Surface: infra

## Current State

`tests/timing-nested-parent-roster.test.js` (added for #2030) scans build/test/review/design-wrapper/wrap-up/flow/`_shared` for real nested `/claude-tweaks:{name}` Skill-tool invocations and asserts each is either a `PHASES` member, a `plugin/bin/lib/timing/derive.js` `NESTED_PARENT` key, or an allowlisted descriptive-only mention. The scan found three genuine nested invocations that are none of those:

- `plugin/skills/flow/SKILL.md:80` — "Run `/claude-tweaks:stories` with the detected URL" (flow's automatic story generation).
- `plugin/skills/flow/SKILL.md:195` / `plugin/skills/flow/survey.md:69` — "invoke `/claude-tweaks:deepen <changed-source-files>`" (flow's Depth Opportunities survey).
- `plugin/skills/wrap-up/review-console.md:126` / `plugin/skills/flow/multispec-review-console.md:115` — "invoke `/claude-tweaks:feedback --pre-confirmed`" (Review Console upstream-feedback filing).

None of `stories`, `deepen`, `feedback` are in `NESTED_PARENT`, so a `skill_invoked` event for any of them currently opens its own new top-level phase row in `derive.js`'s output rather than nesting into the enclosing phase (`build`'s stories generation, `wrap-up`'s Review Console, etc.) — exactly the "spurious top-level phase" behavior `derive.js`'s own roster comment warns about. The conformance test (#2030) allowlists these three by name, with a pointer to this issue, rather than silently deciding the phase-attribution question itself.

**Resolved here** — all three follow the same pattern as `NESTED_PARENT`'s nine existing entries
(`simplify`, `reflect`, `visual-review`, `capture`, `design-wrapper`, `challenge`,
`assess-agent-autonomy`, `ledger`, `journeys`): each is a skill dispatched *as a sub-step* of a
larger pipeline skill's own procedure, never itself a top-level pipeline phase (`build`, `test`,
`review`, `polish`, `wrap-up`, `merge`). `stories` (flow's automatic story generation) is the
direct analogue of already-nested `journeys` (also a doc/artifact-generation sub-step of build).
`deepen` (flow's Depth Opportunities survey) is the direct analogue of already-nested `reflect`/
`simplify` (analysis passes run as pipeline sub-steps). `feedback` (Review Console's
upstream-feedback filing) is the direct analogue of already-nested `capture` (a filing action
invoked as a pipeline sub-step). None of the three is ever a user-facing standalone pipeline
stage the way `build`/`review`/`wrap-up` are.

## Deliverables

- Add `stories`, `deepen`, and `feedback` to `plugin/bin/lib/timing/derive.js`'s `NESTED_PARENT`
  map, each mapped to `'enclosing'` — matching the nine existing entries' shape exactly.
- Remove `stories`, `deepen`, and `feedback` from `tests/timing-nested-parent-roster.test.js`'s
  allowlist (they're no longer an unresolved gap once they're `NESTED_PARENT` members).

## Acceptance Criteria

1. `tests/timing-nested-parent-roster.test.js` no longer needs `deepen`/`stories`/`feedback` in
   its allowlist — they've moved to `NESTED_PARENT` instead.
2. A `skill_invoked` event for `stories`, `deepen`, or `feedback` nests into its enclosing phase
   in `derivePhases()`'s output rather than opening a new top-level phase — covered by a test
   case mirroring the existing `NESTED_PARENT` entries' own test coverage in
   `tests/bin-lib/timing/derive.test.js` (or wherever the existing nine entries are tested).
3. `npm test` stays green.

## Technical Approach

Add three entries to the existing `NESTED_PARENT` object literal in
`plugin/bin/lib/timing/derive.js` (~line 21), each `'enclosing'` — the identical value every
existing entry already uses (`isTopLevel()` at line 55 only checks map membership, not the
value, so `'enclosing'` is the only value this map currently uses; keep it consistent). Then
remove the three names from `tests/timing-nested-parent-roster.test.js`'s `ALLOWLIST` and add
(or extend) a test case asserting each nests correctly, following whatever pattern the existing
nine entries' own coverage already uses.

### Key Files

- `plugin/bin/lib/timing/derive.js` — add three entries to `NESTED_PARENT` (~line 21)
- `tests/timing-nested-parent-roster.test.js` — remove the three names from `ALLOWLIST`
- `tests/bin-lib/timing/derive.test.js` (or the actual location of `NESTED_PARENT`'s existing
  test coverage — verify at build time) — add coverage for the three new entries

## Gotchas

- This record resolves the phase-attribution question itself (all three nest) rather than
  leaving it open, based on direct structural analogy to `NESTED_PARENT`'s nine existing
  entries — every one of them is a sub-step skill invoked from within a larger pipeline
  procedure, exactly the shape `stories`/`deepen`/`feedback` share. If a maintainer disagrees
  that one of the three should nest, that's a five-minute label removal from the map, not a
  structural problem with this fix.
- Do not add a fourth, differently-shaped value to `NESTED_PARENT` (e.g. naming a *specific*
  parent phase) — every existing entry uses the literal string `'enclosing'`, and `isTopLevel()`
  only checks map membership, so introducing a new value shape would be unused complexity.
