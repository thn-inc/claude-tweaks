# 2339: shipped-candidate.test.js doesn't cover the 'never upgrade tier on missing data' rule

Surface: infra

## Current State

Found during a pre-release whole-branch review of `tests/bin-lib/issues/shipped-candidate.test.js`.
The test named "no Key Files section and no title match can never classify strong" only asserts
`tier === 'weak'`; it never covers the module's stated "never upgrades a tier on missing data"
rule (confirmed, `shipped-candidate.js:27`'s comment: "a PR absent from this map is simply 'files
not fetched for it,' which the files-based strong signal treats the same as 'files don't cover
everything' — it never upgrades a tier on missing data"). No existing test supplies a record with
Key Files, no title match, and no `prFiles` entry at all — the actual missing-data path the
comment describes.

## Deliverables

Add a test case supplying a record with a Key Files section, no title match, and no `prFiles`
entry, asserting the module does not upgrade the tier on that missing data.

## Acceptance Criteria

The new test fails if the missing-data guard is removed from `shipped-candidate.js`, proving it
actually exercises the rule.

## Technical Approach

Add a test case to `tests/bin-lib/issues/shipped-candidate.test.js`, alongside the existing "no
Key Files section and no title match can never classify strong" test, using a record that DOES
carry a `### Key Files` section (unlike the existing test) but whose corresponding PR number has
no entry in `opts.prFiles` — asserting the result stays `tier: 'weak'`, not `'strong'`, proving
the missing-`prFiles`-entry path is treated as "files don't cover everything" rather than
silently upgrading. Verify the test actually discriminates per the Acceptance Criteria: comment
out or bypass the missing-data guard in `shipped-candidate.js` locally and confirm the new test
fails, before considering it done.

### Key Files

- `tests/bin-lib/issues/shipped-candidate.test.js` — add the missing-`prFiles`-entry test case

  tested

## Gotchas

- The test must supply a record that genuinely has a `### Key Files` section (the existing
  no-Key-Files test doesn't exercise this path at all) — the distinguishing setup is Key Files
  present + no title match + no `prFiles` entry, not merely "no `prFiles` entry" alone.
- Per this record's own Acceptance Criteria, verify the test discriminates by temporarily
  removing the guard and confirming a failure — don't skip this verification step.
