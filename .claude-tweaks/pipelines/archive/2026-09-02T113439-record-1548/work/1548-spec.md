# 1548: /build's worktree-setup does not reliably invoke pr-early-run-lifecycle's draft-PR-at-run-start step

**Related:** #1456

Origin: reflect light from #1404
Defer-reason: tangential

## Current State

`_shared/pr-early-run-lifecycle.md`'s "Run start: push, then open (or reuse) the draft PR" procedure is supposed to run once per pipeline run, from `build/worktree-setup.md` Step 6, immediately after the materialize commit — making every `pr-first` run "born public" (draft PR at run start, every phase pushes). On run `2026-08-27T061932-record-1404` (record #1404), the build/test phases completed two commits (materialize + fix) with no upstream branch configured and no PR opened at all — `decisions.md` had zero `PR-early run lifecycle` entries, and no `run-state.json` existed in the run directory until `/claude-tweaks:review`'s own phase-exit recovered it manually (pushed the branch, created draft PR #1547, recorded it via `hooks.js record-pr`). `pr-early-run-lifecycle.md`'s own "Phase-checklist update" section anticipates this exact degraded state (a `pr-first` run with no upstream configured) and documents a recovery path — which is what let review self-heal here — but the run-start step that should have prevented the gap in the first place did not fire.

## Deliverables

Investigate why `build/worktree-setup.md` Step 6 did not invoke the PR-early run lifecycle for this run (or any systemic reason a `pr-first` build phase might skip it — e.g. ceremony-profile: fast-lane trimming a step it shouldn't, or a code path that silently no-ops when `gh` calls are slow/deferred). Fix the root cause so a fresh `pr-first` build phase reliably opens (or logs a degrade for) the draft PR at run start, per the file's own mandate. Add or strengthen a test that would have caught this specific gap (a build-phase run with `integration-model: pr-first` completing without a `run-state.json.pr` field and without a matching `decisions.md` degrade line).

## Acceptance Criteria

- A fresh `pr-first` build phase run either opens a draft PR at run start or logs one of `pr-early-run-lifecycle.md`'s documented degrade lines (push failure, `gh pr create` failure) — never silently neither.
- A regression test exists that fails against the observed gap (no PR, no degrade log) and passes once fixed.
- No change to the recovery path documented in `pr-early-run-lifecycle.md`'s Phase-checklist update section — it remains the correct fallback for a genuinely degraded run.

## Evidence

`decisions.md` for run `2026-08-27T061932-record-1404` had no `PR-early` entries before this review step; `git rev-parse --abbrev-ref --symbolic-full-name @{u}` failed (no upstream) at review's phase-exit; `gh pr list --head worktree-dispatch-record-1404 --state all` returned an empty list — confirming no PR was ever attempted, not merely one that failed and degraded silently (a degrade would still log).

## Cost this session

Low — one extra recovery pass (push, `gh pr create`, `record-pr`, retroactive checklist backfill across 3 `gh pr edit` calls) inside `/claude-tweaks:review`'s phase-exit, a few extra tool calls. Not blocking, but the same gap on an unattended dispatch run without a review-phase recovery path would leave a `pr-first` record silently running local-only for its entire lifecycle.
