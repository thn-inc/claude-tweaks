# 6118: End a drive.js --budget run when workers cannot launch, and settle that stop without the escalation marker

Surface: backend
Risk-flags: auth, public-contract

## Overview

`drive.js --budget` ends early only on a claim stop whose cause every later claim would meet (`claim-targets.js` exit 2, 6 or 7). A worker that cannot launch for a reason every later record would meet too gets no such stop: an expired login, an exhausted usage limit, a missing `claude` binary or an unauthenticated host. The loop goes on to the next record. Each record's pre-push stop is then settled as `express-escalated`, and settle posts the trusted `<!-- express-driver: escalated -->` comment, which keeps the driver from ever taking that record again until a person deletes the comment. Under `--budget all`, one expired login would escalate every admitted record out of the driver lane. A script job has no session to notice this. This record adds the missing stop, and settles the failure without the marker.

## Non-Goals

- Retrying or waiting for a usage limit to reset. The run ends, and the next scheduled firing tries again.
- Changing what an ordinary per-record worker failure does: a worker that ran and failed its record (red tests, `cannot-complete`, a spend or wall-clock ceiling on one record) keeps today's settle.
- Deciding how headless workers authenticate on env-authenticated hosts. That is #5259. This record only makes the failure stop the run cleanly.

## Release Note

A budget-driven driver run now stops when workers cannot launch, instead of escalating every remaining record out of the driver lane.

## Technical Approach

Classify once in the worker module, where the envelope is built, and carry the verdict up through `ctx` to `driveRecord`'s facts. The loop then decides whether the run ends, as it already does for claim exits, and settle decides how the stopping record is cleaned up. The two-in-a-row rule is the fallback for causes no structured field shows: two consecutive launches failing before a record's own work is a stronger signal of a shared cause than of two bad records. The first of the two keeps its ordinary per-record settle (it cannot be known at the time), and that cost is documented.

The worker-stop `detail` names the record number and the closed `reason` value only, never the worker's `result` text. A record that took the #5997 relaunch is one record: the facts and the two-in-a-row counter use its first launch's envelope. The counter is per `runBudget` invocation and is never carried across firings. When (b) is dropped because the probe finds no structured field, an expired login or an exhausted limit reaches `worker-stop` only through the two-in-a-row rule, so the first such record is still escalated by the ordinary settle; `docs/driver.md` documents that cost. Before adding `worker-stop`, grep every reader of the summary line's `ended` and `status` for an exhaustive switch: a reader that does not know the value must treat it as a stop, never as a clean end.

**Decision** (plan review, question 1, 2026-11-26): Reading B. When a streak of one is open (the previous driven record's implementer launch counted toward the two-in-a-row rule) and the next record's launch also counts, the previous record's escalation comment is deleted whichever rule ends the run, shared-cause or two-in-a-row. The two rules are evaluated together for the record that ends the run, not as "shared-cause first, return". The summary line's `detail` names both records and their closed `reason` values. Why: the record body's intent is that a shared cause never moves a record out of the driver lane, and a counting failure followed by a shared-cause failure is the strongest evidence that the first one had the same cause. A budget test pins the case (Acceptance Criteria).

**Decision** (standing rule for later plan-review questions on this record): where this spec is silent on an interaction between the shared-cause rule, the two-in-a-row rule and settle, pick the reading under which no record leaves the driver lane because of a cause every record would meet, while a record that fails on its own still gets today's escalation; record the choice in the plan and pin it with a test. On the forge-facing side, ambiguity resolves fail-closed: a reader that does not know `worker-stop` treats it as a stop, and a failed comment delete is named on stderr and in `detail` and never changes the exit code. The escalation comment id reaches the loop through `driveRecord`'s facts (settle returns it; carry it as `escalationCommentId`, `null` when none was posted).
