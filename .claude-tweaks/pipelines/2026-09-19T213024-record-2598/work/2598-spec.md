# 2598: dispatch/task-prompt.md's second-call template contradicts itself on run-dir archival for OUTCOME: merged

Origin: scheduled dispatch Routine firing, 2026-09-18T08:14Z (run `2026-09-18T081427-dispatch-standalone`, group run `2026-09-18T082615-record-1739-2336`)

Defer-reason: tangential — found while dispatching #1739/#2336 to a successful merge (PR #2596); the dispatch task itself completed correctly (the dispatching session closed the gap manually), this is a follow-up on the template defect observed along the way.

## Current State

`plugin/skills/dispatch/task-prompt.md`'s second-call template (review,polish,wrap-up) contains two directly contradictory instructions about who archives the run directory when `OUTCOME: merged`:

- The "Working directory" paragraph states, unconditionally: "Worktree removal and run-dir archival are the dispatching session's responsibility, not yours — do NOT call `ExitWorktree` or `git worktree remove`, and do NOT archive the run directory yourself, **on any outcome (merged, armed, pending-review, ready-to-merge, failed, or blocked)**."
- The `integration-model: pr-first` outcome-vocabulary paragraph, two sections later, states: "`merged` means you also completed claim release and run-dir archival directly (that procedure's Step 4) — but not worktree removal..."

A dispatched second-call agent hit this directly on 2026-09-18: it completed claim release but treated the explicit, outcome-enumerated "do NOT archive… on any outcome (merged, …)" sentence as controlling, and left the run directory unarchived, flagging the contradiction back to the dispatching session rather than guessing. The dispatching session then closed and archived the run directory manually. No data was lost, but every future `pr-first` + `merged` second call will hit the same ambiguity and (correctly, per the more specific sentence a careful reader would find) either skip archival or have to stop and ask, unless one of the two paragraphs is fixed to agree with the other.

## Deliverables

- [ ] Reconcile the two paragraphs in `plugin/skills/dispatch/task-prompt.md`'s second-call template so they agree on whether the second call archives the run directory when `OUTCOME: merged` under `integration-model: pr-first`.
- [ ] If the outcome-vocabulary paragraph is correct (the second call does archive on `merged`), the "Working directory" paragraph's blanket "on any outcome (merged, armed, ...)" list should drop `merged` (and possibly `ready-to-merge`, if `local-merge`'s labeling-only stop also doesn't archive) or otherwise carve out the exception explicitly.
- [ ] If the "Working directory" paragraph is correct (the dispatching session always archives, even on `merged`), the outcome-vocabulary paragraph's "run-dir archival directly" clause should be removed or corrected to say the dispatching session does it instead.
- [ ] Cross-check `skills/dispatch/settle-and-merge.md` (cited by the outcome-vocabulary paragraph as "that procedure's Step 4") for which behavior it actually documents, and align both `task-prompt.md` paragraphs to match it rather than picking arbitrarily.

## Acceptance Criteria

1. `task-prompt.md`'s second-call template no longer contains two paragraphs that give opposite instructions for the same case (`OUTCOME: merged` under `pr-first`).
2. A dispatched second-call agent reaching `OUTCOME: merged` has exactly one correct action to take regarding run-dir archival, sourced from a single unambiguous instruction.
