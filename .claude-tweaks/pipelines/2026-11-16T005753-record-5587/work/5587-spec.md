## Current State

`tools/guard-refusals.js` (#4028) reads the local transcript store and counts the Bash calls refused by Claude Code's own worktree-isolation guard ("This session is isolated in the worktree … Refusing to run it …"). That guard is part of the harness. It is not `plugin/bin/lib/hooks/pre-tool-use.js`. For each refusal the tool prints a reason (`tools/guard-refusals/trace.js`, read from the refusal's own clause), the detector shapes it matches (`tools/guard-refusals/shapes.js`, one per refused row of `plugin/skills/_shared/scratch-worktree.md` section 7) and the skill fence it was copied from.

It does not say three things the process-efficiency design needs (`docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 3, unit 3.1):

- **Which guard refused the call.** The design counted 13,628 "worktree guard refusals" and planned to change "the guard's command scanner". Measured on 2026-11-16 over 2026-10-17 to 2026-11-16 (30 days, 30,633 transcript files, 1,267,498 tool calls, 44,136 tool errors), with a scratch scan beside the tool:
  - 12,363 calls were refused by the harness guard with the `Refusing to run` tail (12,334 Bash, which is the tool's own count, and 29 Monitor). That is 28% of all tool errors, and 84.8% of them are in subagent transcripts.
  - 407 Write and Edit calls were refused by the harness with a different tail ("Edit the worktree copy of this file instead of the shared-checkout path"). The tool does not count these.
  - 432 calls were denied by this plugin's own PreToolUse gates: 326 by the worktree-always gate (`checkWorktreeRequired`: 314 Bash, 8 Edit, 4 Write), 73 by the bookkeeping-stamps gate, 18 by the dispatch-prompt gate, 10 by the teardown gate, 4 by the Review Console ask gate and 1 by the pipeline shadow guard. The tool counts none of these.
  - So the harness produced 96.7% of the refusals and the plugin 3.3%.
- **Whether the refused command only reads.** A scratch classifier over the 12,363 harness refusals gave: 3,606 read-only (29.2%), 4,865 that write (39.4%), 3,892 whose effect the text does not show (31.5%; `node <script>` 789, `node -e` 639, `python3` 450, `playwright-cli` 243). Of the plugin's 314 worktree-always Bash denials, 282 write, 28 are not shown by the text and 4 only read; `gitTargets` and `fileWriteTargets` at HEAD resolve no target for those 4.
- **Whether the plugin's own rewriter already covers the command.** `plugin/bin/lib/hooks/guard-rewrite.js` rewrites five shapes before the harness guard reads them. A transcript holds the command the model wrote, not the rewritten one. Run over the refused commands, `rewriteForGuard` changes 400 of the 6,441 refused after the rewriter's first release (v6.154.1, 2026-10-25), 129 of them by `quote-escaped-space`. #4216 asks for this count by hand.

Two more measurements from the same run:

- The reason table leaves 878 of 12,334 refusals (7.1%) as `other`. The largest unnamed clauses: "runs playwright-cli with a value computed at runtime" (139), "runs a command whose name is computed at runtime" (124), "runs env with the text …" (93), "feeds python text naming git" (33), "names git more than once in a single command" (31), "runs awk with a program that can execute commands" (22), "uses a subshell" (21), "evaluates … arithmetically" (18), "working directory … is in a different worktree" (18).
- The shape detectors leave 7,919 refusals (64%) `unclassified`, and 1,392 (11%) trace to a skill fence. The design's "at least 95% of refusals" cannot be met by detector shape, so this record keys the table on guard, reason and effect.

Every account's `projects` directory on the measuring machine is a link to the same store, so one `--projects-dir` run covers all of them.

## Deliverables

1. **The guard of each refusal.** `tools/guard-refusals/transcripts.js` records every `is_error` tool result that one of these produced, for any tool, with a `guard` value:
   - `harness-command`: the isolation clause followed by `Refusing to run` (today's rows, plus Monitor).
   - `harness-file`: the isolation clause followed by "Edit the worktree copy of this file".
   - `plugin:<gate>`: a result that starts with `PreToolUse:<Tool> hook error: claude-tweaks` or with `claude-tweaks`, followed by a colon or a space (the teardown gate's text starts `claude-tweaks teardown gate`), and carries one gate's deny text. Gates: `worktree-always`, `lost-cwd`, `powershell-opaque`, `pipeline-shadow`, `teardown`, `bookkeeping-stamps`, `dispatch-config`, `wd-enforcement`, `review-console-ask`, `dispatch-prompt`. A deny text that matches no gate is `plugin:other`.
   A Bash result that merely prints text containing `claude-tweaks:` (a failed `cat` of a skill file, a CLI's own error line after `Exit code N`) is not a denial.
   Decided 2026-11-16: the gate names are this tool's own labels. Each is matched by a fragment of its deny text, the first match winning in this order (every fragment was found in the two source files on 2026-11-16): `teardown` by "teardown gate" or "is assigned to run"; `worktree-always` by "this project requires an isolated worktree for"; `lost-cwd` by "this command changes directory more ways than"; `powershell-opaque` by "hands this guard literal (or base64) script text"; `pipeline-shadow` by "a NEW pipeline run directory inside a" or "the command has changed directory more ways than"; `bookkeeping-stamps` by "resolves integration-model: pr-first and"; `dispatch-config` by "has not written config.yml"; `wd-enforcement` by "is active in worktree"; `review-console-ask` by "which grants consoleAutoResolve"; `dispatch-prompt` by "this Agent prompt names run". `teardown` is first because one of its texts also holds the `pipeline-shadow` wording.
2. **The effect of each refused command.** A new module `tools/guard-refusals/effect.js` exports `classifyEffect(command)`, which returns `{ effect, why }` with `effect` one of `read`, `write`, `unknown`:
   - `write` when `plugin/bin/lib/hooks/git-command.js` reports a target (`fileWriteTargets`, `mkdirTargets`, or `gitTargets` with an action in `GATE_COVERAGE.gitActions`), or when a command word or subcommand is in the module's own write table (`git commit`, `git fetch`, `gh pr merge`, `gh api` with a write method or fields, `sed -i`, `rm`, …).
   - `read` only when every command word in the call, inside `$( )` and backticks too, is on a reader allowlist (for `git` and `gh`, a read-only subcommand allowlist), and no output redirect names a file. `2>&1`, `>&2` and a `/dev/null` target are not writes.
   - `unknown` otherwise, with the program named in `why` (`node script`, `node -e`, `python3`, `playwright-cli`, `bash`, an unlisted word).
   The rule that matters: a command that can write is never `read`. An unlisted word is `unknown`, never `read`.
   Decided 2026-11-16: `effect.js` owns and exports both tables. `WRITE_WORDS` maps a command word to what makes it write: `sed` with `-i`, `perl` with `-i`, `dd` with `of=`, `find` with `-delete` or `-exec`, `curl` with `-o` or `-O`, `sort` with `-o`; `rm`, `mv`, `cp`, `tee`, `install`, `ln`, `truncate`, `mkdir`, `touch` and `chmod` with any argument. `READERS` lists the words that only read, with `GIT_READ` and `GH_READ` as subcommand lists. `sed`, `find`, `curl` and `sort` without their writing flag are `read`; `perl` and `dd` without theirs are `unknown`, because their programs can write. `gh api` is `read` for a GET (given, or the default when no field flag is present) and for `graphql` whose literal query text starts with `query` or `{`; it is `write` for another method, a field flag on a REST path with no GET, or a literal `mutation`; it is `unknown` when the query comes from a file or a variable. `GATE_COVERAGE` is read from `plugin/bin/lib/hooks/pre-tool-use.js`, which exports it.
3. **The class of a refused read.** A `harness-command` row with `effect: read` gets `readClass`: `other-checkout` when the guard refused where git points (reasons `git-redirect-shared` and `cd-shared`, and the "is in a different worktree" clause), else `shape`.
   Decided 2026-11-16: the second value is `shape`, not `own-worktree`. The row was refused for how the command is written, which says nothing about where it reads.
4. **The rewriter's verdict.** Each `harness-command` Bash row gets `rewrite`: the rule ids `rewriteForGuard` applies to the command at HEAD, given the cwd the transcript entry recorded and `deps.isLinkedWorktree` returning true (the worktree may be gone). A row with no recorded cwd gets `null`. `transcripts.js` keeps the entry's `cwd` for this.
   Decided 2026-11-16: `rewrite` is `[]` when no rule changes the command, the list of rule ids when one does, and `null` when the entry has no cwd. It means "the rules in the tool's own checkout change this text", never "the hook ran in that session". The tool passes `deps.canonicalRealpath` as a function that returns its argument with trailing slashes trimmed, because the session's worktree may be gone; `drop-redundant-cd` is then judged on spelling alone. Each row also carries `ts`, the transcript entry's timestamp.
5. **Named reasons for the clauses above.** `trace.js`'s reason table gains an id for each of the nine clauses listed in Current State, each matched only when no existing pattern matches.
   Decided 2026-11-16: the ids are `playwright-runtime`, `computed-command-name`, `env-text`, `python-git-text`, `git-twice`, `awk-program`, `subshell`, `arithmetic` and `other-worktree-cwd`, in the order of the clauses in Current State. 6. **Output.** The JSON gains `guards` (count per guard), `byEffect`, `byReadClass`, `byRewrite` and the per-row fields; the text table gains a "by guard" and a "by effect" block. `calls`, `refusals`, `perPipeline`, `byReason`, `byShape`, `byFence` and `top` keep their present meaning and count what they count today (Bash and Write calls, and those calls' `Refusing to run` refusals), so #4216's baseline (mean 9.94, median 6) stays comparable.
   Decided 2026-11-16: Monitor rows, `harness-file` rows and `plugin:*` rows appear only in `guards` and the new blocks. Both harness tails (`Refusing to run it` and `Refusing to run there`) are `harness-command`. A row of a file tool (Write, Edit, NotebookEdit) has `effect: write`; a row of any other tool that is not Bash has `effect: unknown`. The "Edit the worktree copy" fragment lives in `transcripts.js`, not in `plugin/bin/lib/hooks/harness-refusal.js`. An `is_error` result that matches no guard is not a row.

## Technical Approach

The tool already requires `plugin/bin/lib/hooks/harness-refusal.js` for the isolation clause; requiring `git-command.js` and `guard-rewrite.js` the same way is in keeping. Reuse `lexShell` in `shapes.js` for quote, comment and heredoc handling in `effect.js`, so there is one lexer in `tools/guard-refusals/`.

`effect.js` is an allowlist in the read direction. A reader with a flag that writes (`sed -i`, `find -delete`, `find -exec`, `curl -o`, `sort -o`) is listed with the flag. A heredoc body is data for a reader and makes an interpreter `unknown`.

A plugin denial is found from the result text, not from the call: the transcript does not record which hook answered. Keep the fragments in one table in `transcripts.js`.

Measured cost: shape detection takes about 32 ms per refusal (6.5 s for 200), mostly `node-git-text` and `sed-var-path`, and the full 30-day run took more than ten minutes. No test pins a time. A scratch run on 2026-11-16 took about 1.2 ms per row for an effect verdict and 1.9 ms for a rewrite verdict (200 rows); the PR states the built tool's figures.

## Build Alignment Notes

Beneficial deviations kept as built (Common Step 4.5), each a stricter reading of Deliverable 2's rule "a command that can write is never `read`":
- `curl` is also `write` with a request body (`-d`, `--data*`, `--json`, `-F`, `--form*`, `-T`, `--upload-file`), a non-GET/HEAD `-X`, or local-output flags beyond `-o`/`-O` (`-D`, `-c`, `-K`, `--trace`, `-w '%output{…}'`, …), matching the `gh api` rule that a remote mutation is a write.
- `less` with a log-file flag, `file -C`, and `git config` write flags given by unique abbreviation are `write`.
- `tree`, `xxd`, `hostname` and `date` are not readers (each has a writing form), so they are `unknown`; so is a relative path command word (`./x`).
- A reader with a write flag, or `git` judged read, whose argument word starts with an expansion or holds an unquoted expansion is `unknown` (`why: 'computed argument'`); a `git -c` key that can run a program (`core.*`, `alias.*`, `*.pager`, `*.editor`) is `unknown`; a hazardous leading assignment (`PATH`, `BASH_ENV`, `LD_PRELOAD`, `LESSOPEN`, …), including through `export`, is `unknown`.
- A Bash row whose command was cut at the 20000-character store cap carries `truncated: true` and is `unknown` (`why: 'truncated'`), and each `rows` entry keeps the whole stored command.
