# 3997: staged-patch gitEnv leaks env-injected git config (GIT_CONFIG_COUNT/GIT_CONFIG_PARAMETERS) into its isolated git calls

Surface: infra

**Related:** #2767, #3703, #3953

## Current State

This record was filed from #3922's wrap-up. #3922's AC3 proxy run reported 11 failures in `tests/bin-lib/staged-patch/stack-check.test.js` and `cli.test.js` under a `core.autocrlf=true` checkout, and the record attributed them to the engine's sensitivity to the working tree's line endings. **That premise does not hold on current main.** Re-probed on 2026-10-24 against `7359a29e2`:

- A clone with local `core.autocrlf=true` (CRLF working tree; `stack-check.js` checks out "with CRLF line terminators"): **63/63 pass**.
- A `GIT_CONFIG_GLOBAL` file carrying `core.autocrlf = true`: **63/63 pass**.
- Real `windows-latest` CI (`windows-regression` run 40085228979 at `5ea8cb7a4`; its line-ending diagnostics print `core.autocrlf` = `true` and `w/crlf` for the working tree): all 11 named tests report `ok` in the uploaded `verify-logs/tests.log` (e.g. `ok 7563 - AC1.1: overlapping-context edits re-derive onto the earlier patch`).

What does reproduce is narrower. With `core.autocrlf=true` injected **through the environment** (`GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.autocrlf GIT_CONFIG_VALUE_0=true`), exactly these 11 fail, on an LF checkout as well as a CRLF one, so the checkout's line endings are not the trigger. All 11 sit on the re-derive path (`rederive` in `plugin/bin/lib/staged-patch/stack-check.js`). Its `git merge-file` step reports `conflict in f.txt` because the scratch repo's `git apply` now writes CRLF.

The cause: `gitEnv` (`plugin/bin/lib/staged-patch/stack-check.js:27`) isolates git config by setting `GIT_CONFIG_GLOBAL` to the null device and `GIT_CONFIG_NOSYSTEM=1`. Its comment at `:35` says "Every git call runs with the user's and system config switched off". But it spreads `process.env` without removing `GIT_CONFIG_COUNT` / `GIT_CONFIG_KEY_<n>` / `GIT_CONFIG_VALUE_<n>`, or `GIT_CONFIG_PARAMETERS` (what `git -c key=value` exports to its child processes). So config carried in the environment still reaches every git call the engine makes (`defaultGit`, `:38`). The test fixtures repeat the gap: `stack-check.test.js:16` and `cli.test.js:15` each hand-roll `FIXTURE_ENV` with the same two keys. `stack-check.js` is the only `plugin/bin` module that sets `GIT_CONFIG_NOSYSTEM` (`git grep -l GIT_CONFIG_NOSYSTEM -- plugin/bin`), so no sibling engine shares the gap.

## Deliverables

These sit alongside its existing `GIT_DIR` / `GIT_WORK_TREE` / `GIT_INDEX_FILE` deletes. Its comment names env-carried config as part of what is switched off.

- [ ] A unit test beside the existing `#3696` `gitEnv` tests in `stack-check.test.js`: an input env carrying all four key shapes yields an output with none of them, and the input object is not mutated.
- [ ] When this ships, a closing comment on this record states that the CRLF-checkout premise does not reproduce and cites the Windows run above, so the 11-failure figure is not re-chased as a Windows defect.

## Release Note

Make the staged-patch check ignore git config passed through environment variables, so a `git -c` or `GIT_CONFIG_*` setting can no longer change its verdicts.

## Technical Approach

In `gitEnv`, after the `{ ...env }` spread, delete `GIT_CONFIG_PARAMETERS` and `GIT_CONFIG_COUNT`, then every key matching `^GIT_CONFIG_(KEY|VALUE)_\d+$`. This is the same delete-from-the-copy pattern the function already uses for the repo pointers, and it still never mutates the input (the existing `#3696` test asserts this). Leave the `GIT_CONFIG_GLOBAL` / `GIT_CONFIG_NOSYSTEM` assignments and the win32 `/dev/null` branch exactly as they are. In the two test files, set `FIXTURE_ENV = gitEnv()`. `stack-check.test.js` already imports `gitEnv` (`:13`). `cli.test.js` needs the import from `../../../plugin/bin/lib/staged-patch/stack-check`.

### Key Files

- `plugin/bin/lib/staged-patch/stack-check.js` — `gitEnv` scrubs env-carried config; comment at `:35` updated
- `tests/bin-lib/staged-patch/stack-check.test.js` — `FIXTURE_ENV` built from `gitEnv()`; new scrub unit test beside the `#3696` tests
- `tests/bin-lib/staged-patch/cli.test.js` — `FIXTURE_ENV` built from `gitEnv()`

## Gotchas

- Do not scrub `GIT_AUTHOR_*` / `GIT_COMMITTER_*`. `windows-regression.yml` sets them in the job env, and fixture commits depend on them. Only config-injection keys are in scope.
- The 11-failure figure depends on env injection. Do not try to reproduce it with a CRLF checkout or a global gitconfig, since both pass today. Use the AC's command.
- `GIT_CONFIG_PARAMETERS` uses git's quoted `'key'='value'` format, space-separated for several entries. The scrub deletes the whole variable and never parses it.
- ASSUMPTION — verify at build: #3922's proxy run produced its 11 failures through env-injected config rather than a CRLF checkout. Confirm via #3922's run notes, if any survive. This is not needed for the fix, which is correct either way.

Origin: wrap-up leftover from #3922

## Current State

A `core.autocrlf=true` checkout run (base `d024839335` vs branch tip `a54ee41c3`, done as #3922's own AC3 proxy for the post-merge Windows regression check) still fails 11 tests in `tests/bin-lib/staged-patch/stack-check.test.js` and `tests/bin-lib/staged-patch/cli.test.js` after #3922's own fix landed (CRLF-checkout failures dropped from 53 to 15 overall, and these 11 are among the remainder). The re-derive path in `plugin/bin/lib/staged-patch` runs `git apply`/`git diff` against a CRLF temp repo, so the results flip between an LF and a CRLF working tree. This is not a raw-read-of-governed-markdown bug (#3922's own class) — `plugin/bin/lib/staged-patch` and its tests are untouched by #3922's diff — it looks like a real Windows behavior of the staged-patch engine itself (its re-derive/stacked-check logic is sensitive to the working tree's line-ending convention, independent of any test reading a file the wrong way).
