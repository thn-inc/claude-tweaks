# 2681: Replace agent-browser auth vault with playwright-cli session-state persistence

Surface: infra

## Overview

Replaces `agent-browser`'s credential-vault auth model (`agent-browser auth login/save/list <vault-name>`) with `playwright-cli`'s native `state-save`/`state-load` session-state persistence, so QA story authentication no longer depends on `agent-browser`. `auth: { vault: "<name>" }` in story YAML keeps its field name and shape — it now names a captured session-state JSON file rather than a credential entry, so no existing story file needs editing for this reason. This is the last of the two capability gaps (`press`, already handled by the pre-existing `#2670`; auth, here) blocking full removal of the `agent-browser` dependency — once this ships, the parent decomposition's other sub-issue can retire `plugin/skills/browse/agent-browser-reference.md` and close the two upstream defect reports as moot.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Fixing or patching `agent-browser`'s own vendored CLI defects (locator-click dispatch, screenshot `os error 35`) — those are addressed by retiring the dependency entirely, not by patching it (see the parent decomposition's other sub-issue).
- Building a credential-replay auth model — session-state persistence was chosen instead (see the parent record's Decision Rationale): no new secret-storage code, at the cost of the session expiring and needing periodic manual re-capture.
- Active session-expiry detection or a pre-flight validity check for a captured session-state file — expiry is handled fail-forward (see Gotchas), matching the existing missing-vault precedent.
- Editing existing story YAML files' `auth:` blocks — the `vault: "<name>"` field shape is unchanged. (Authoring one new throwaway auth-gated test story fixture for Task 0/the manual QA verification below, when no suitable existing story is available, is in scope and not covered by this exclusion — it edits no existing story.)
- Migrating the `press` story action — already covered by the pre-existing `#2670`.
- Guaranteeing session-state persistence for non-cookie auth mechanisms. `playwright-cli state-save`/`state-load` captures cookies and `localStorage` only — OAuth redirect flows, MFA challenges, and server-bound session tokens that require re-authentication per browser instance are out of scope and not guaranteed to work; the original `agent-browser` vault made no stronger guarantee here either, so this is not a regression.

## Release Note

Replaced the browser-automation auth vault with a Playwright session-state file, removing agent-browser from the QA story authentication path.

## Technical Approach

Session-state persistence, not credential replay: `playwright-cli`'s native `state-save`/`state-load` commands (confirmed live at v0.1.21 via `npx @playwright/cli@latest --help`) capture and restore raw browser storage state (cookies, localStorage) rather than replaying a username/password. This trades zero new secret-storage code for the session eventually expiring and needing periodic manual re-capture — an accepted trade-off (see Gotchas).

## Gotchas

- Storage location is `.claude-tweaks/auth-state/<vault-name>.json` — a bare filesystem path, not a CLI-managed store.
- `auth: { vault: "<name>" }` keeps its existing field name and shape in story YAML — it now names a session-state file, not a credential entry — so no existing story file needs editing purely because of this migration.
- The capture procedure is manual by design: a human runs `playwright-cli open <login-url>`, logs in directly in the visible browser, then runs `playwright-cli state-save .claude-tweaks/auth-state/<vault-name>.json`, then closes the session. No credential ever touches the LLM or this repo's tooling, the same guarantee the vault made, by a different mechanism (the human types the password into the browser, not into a command the LLM composes).
- **Expiry handling is deliberately fail-forward — not a gap.** There is no active pre-flight validity check for a captured session-state file. A later step fails naturally against a stale session — concretely, the story's first authenticated action after `state-load` fails against an unauthenticated page (a login-redirect, or a 401/403-shaped response), which is distinguishable from a real regression because it fires immediately after `state-load`, not partway through an otherwise-passing story — matching the existing missing-vault UX precedent in `auth-resolution.md` ("expected to fail until fixed, not a defect"). This is a considered trade-off, not an omission: building detection machinery for session expiry was explicitly weighed and rejected as disproportionate for a one-time local dev/CI setup command with no live production traffic at stake. Do not add such machinery without revisiting this decision.
- **Missing session-state file** gets identical UX to today's missing-vault path in `auth-resolution.md`: print the capture command, then `AskUserQuestion` (interactive) / tag `needs-auth-vault` and stage the install hint (auto mode) — only the printed command text changes.
- `<vault-name>` needs no new sanitization or collision policy: it is a locally authored config identifier chosen by whoever runs the capture procedure (never attacker- or user-input-controlled), the same trust level the old vault's own `<vault-name>` argument already had.
- No dedicated `node --test` suite targets `qa-agent.md` or the `stories/*` auth files today (confirmed unchanged since `#2645`) — `npm test`'s existing suite is unaffected by this change and stays the only mechanical gate; the manual QA run above is this record's actual verification, not a new automated test.
