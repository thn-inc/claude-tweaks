# 5773: verify.js: ask git each read-only question once per invocation

**Related:** #5378, #5294

Verified-as-of: c059556fc34954c27371c25ebd65f99e79a4eb0a

## Current State

One `verify.js` run starts about six git processes before and around the tests it runs, and a third of them repeat a question the same process already asked.

Probed on 2026-11-16 at c059556f, by logging every git child of `tests/bin-lib/verify/cli-stamp-discovery.test.js`: 90 `verify.js` processes made 585 git calls (6.5 each), and 183 of those calls had the same arguments as an earlier call in the same process.

| Call | Count over 90 runs | Asked from |
|---|---|---|
| `rev-parse --show-toplevel` | 156 | `realGit(scopeCwd).repoRoot()` in `lib/verify/baseline.js`, reached from `checkoutRoot` and from `scopeSelfPath` in `plugin/bin/verify.js` |
| `rev-parse HEAD` | 137 | `lib/verify/report.js` (the tree-state read), from four places in `verify.js` |
| `status --porcelain` | 137 | the same tree-state read |
| `rev-parse --git-dir` | 90 | `lib/verify/report.js`, from three places in `verify.js` |

Not every repeat is waste. The tree-state read (`rev-parse HEAD` plus `status --porcelain`) runs before and after the suites on purpose, because the tree can change while they run. A second read with nothing in between is waste.

This matters beyond the tests. In the full-suite profile on main at 8646f7c, five verify CLI test files start 4,464 git processes, 3,155 of them from spawned `verify.js` runs (`cli.test.js` 1,073, `impact-cli.test.js` 942, `ci-cli.test.js` 912, `cli-scope-integration.test.js` 771, `cli-stamp-discovery.test.js` 766). Every real verify run in a pipeline pays the same repeats.

`plugin/bin/lib/hooks/repo-info-cache.js` (#5294) is the existing pattern for remembering a git answer in memory: one multi-flag `rev-parse` answers several questions, and the memo is keyed on directory and git-relevant environment.

## Deliverables

1. A trace of one `verify.js` invocation in each mode (whole suite, `--scope`, `--baseline`, impact-selected, CI-answered), listing its git calls in order and marking each same-arguments, same-directory, same-environment repeat with whether anything that could change the answer ran in between. The table goes in the PR body.
2. The repeats with nothing in between are removed: the toplevel, the git directory and the common directory are read once per invocation (one `rev-parse` with several flags can answer them together), and a tree-state read is reused until the next point where the tree may have changed.
3. The memory lives for one process only, is keyed on the directory and the git-relevant environment, and is never written to disk. A read after the suites ran, after a baseline worktree was created or removed, or in another directory asks git again.
4. The injected `execImpl` and `deps` seams keep working. A test that stubs git by argument shape is updated to the merged call without losing an assertion.
5. The PR body reports git calls per invocation per mode, and git processes for the five test files, before and after.

## Acceptance Criteria

- [ ] In a traced invocation of each mode, no git call repeats with the same arguments, directory and environment unless the PR body names it and says what may have changed between the two calls.
- [ ] A test pins the number of git calls a whole-suite invocation makes around a no-op suite, counted through the injectable exec seam (no wall clock). It goes red when one removed repeat is restored; the PR body quotes that red output.
- [ ] A test shows freshness: a tree change made while the suites run is seen by the read after them.
- [ ] Total git processes across the five verify CLI test files fall to at most 3,571 (80% of the 4,464 measured at 8646f7c). Otherwise the PR body names the remaining shortfall and attributes it.
- [ ] The counts come from `GIT_TRACE2_EVENT=<absolute path of an empty directory>` around `CT_TEST_CONCURRENCY=6 node tools/run-tests.js --files-from <list>`, with the before count re-taken at the branch's merge-base with main and the after count at HEAD, back to back on the same machine.
- [ ] `verify.js` prints the same report, writes the same `verify-report.json` fields and exits with the same codes as before: the existing verify tests pass with changes only to stubbed call shapes, and no test is deleted, skipped or loosened.
- [ ] The full suite and the Windows regression job pass.

## Release Note

verify.js starts fewer git processes on each run.

## Technical Approach

### Key Files

- `plugin/bin/verify.js` — read toplevel, git dir and tree state once per invocation
- `plugin/bin/lib/verify/baseline.js` — reuse the invocation's repo-root answer
- `plugin/bin/lib/verify/report.js` — reuse the tree-state and git-dir reads
- `plugin/bin/lib/verify/impact.js` — reuse the toplevel and common-dir answers
- `plugin/bin/lib/verify/changed-files.js` — reuse the HEAD read
- `tests/bin-lib/verify/cli.test.js` — pin the per-invocation git call count
