# 4554: pr-early-open: a gh timeout is reported as "gh is not available" and routed to the MCP path

Surface: infra

**Related:** #4505, #4492, #4578

## Current State

`bin/pr-early-open.js` checks `deps.ghAvailable()` before any `gh` work (`plugin/bin/pr-early-open.js:170`). When that check returns false, it prints `gh is not available — open the draft PR through mcp__github__create_pull_request …` and exits 2. Callers read exit 2 as "`gh` absent" and switch to the MCP path (`plugin/skills/build/worktree-setup.md:174`).

`ghAvailable` (`plugin/bin/lib/repo-resolve.js:35-43`) runs `gh --version` with `timeout: GH_TIMEOUT_MS` and returns `false` from a bare `catch` on **any** error. A timeout kill is one of those errors. It means the binary spawned and is present, but the probe still reports it as absent. `GH_TIMEOUT_MS` defaults to `DEFAULT_GH_TIMEOUT_MS = 5000` (`plugin/bin/lib/shared-primitives.js:94`). It can be overridden with the `CLAUDE_TWEAKS_GH_TIMEOUT_MS` env var or the `gh-timeout-ms` policy key (`plugin/bin/lib/policy-schema.js:134`, range 1000-60000).

Once the probe passes, a later `gh` call that times out reaches the outer `catch` (`plugin/bin/pr-early-open.js:243-244`). That handler prints `internal(errText(e))`, the bare `spawnSync gh ETIMEDOUT`, and exits 1. Neither override knob is mentioned.

Observed on a slow GitHub Enterprise host (one `gh repo view` took ~18 s). The first call exited 2 and was misrouted to MCP. Retries exited 1 with the bare `ETIMEDOUT`. Setting `CLAUDE_TWEAKS_GH_TIMEOUT_MS=60000` got `{"outcome":"opened",…}`. The run cost three failed calls plus a manual read of `shared-primitives.js`.

Prior art for both halves already exists. `isTimeoutError` (`plugin/bin/lib/shared-primitives.js:248`, exported) recognizes a timeout kill. `plugin/bin/lib/claim-targets/claim-targets.js:316-319` already prints a timeout hint naming both knobs.

`ghAvailable` is the shared probe for about 20 `plugin/bin` CLIs (`materialize.js`, `release-claim.js`, `link-records.js`, `pr-checks.js`, …). All of them misroute the same way on a timed-out probe, so the classification fix belongs in the shared probe.

## Deliverables

1. `ghAvailable` in `plugin/bin/lib/repo-resolve.js` reports `gh` as present (returns `true`) when the `gh --version` probe fails because it timed out (`isTimeoutError(err)`). Every other failure returns `false` as it does today, so a spawn `ENOENT` (genuinely absent) still reads as absent. The probe keeps its boolean return and its injectable `deps.execFileSync` seam, and no caller changes its call.
2. `plugin/bin/pr-early-open.js`'s outer `catch` adds a hint when the caught error satisfies `isTimeoutError`. The hint names the effective timeout in ms and both override knobs, the `CLAUDE_TWEAKS_GH_TIMEOUT_MS` env var and the `gh-timeout-ms` policy key, with wording that matches `claim-targets.js`'s existing hint. The CLI still exits 1, which callers already route to "finish by hand".
3. Tests.
   - In `tests/bin-lib/repo-resolve.test.js`: a fake runner that throws a timeout-shaped error (`code: 'ETIMEDOUT'`, and separately `killed: true` / `signal: 'SIGTERM'`) makes `ghAvailable` return `true`, and a runner throwing `code: 'ENOENT'` makes it return `false`.
   - In `tests/bin-lib/flow/pr-early-open.test.js`: a `gh` dep that throws a timeout-shaped error makes `run` exit 1 with stderr naming `CLAUDE_TWEAKS_GH_TIMEOUT_MS` and `gh-timeout-ms` and *not* containing `gh is not available`.

## Acceptance Criteria

- [ ] `ghAvailable({ execFileSync: () => { throw Object.assign(new Error('spawnSync gh ETIMEDOUT'), { code: 'ETIMEDOUT' }); } })` returns `true`.
- [ ] `ghAvailable` returns `true` for a thrown error carrying `killed: true` and no `code`, and `false` for a thrown error with `code: 'ENOENT'`.
- [ ] `pr-early-open.js` run with a `gh` dep that throws a timeout-shaped error exits 1, and its stderr contains `CLAUDE_TWEAKS_GH_TIMEOUT_MS` and `gh-timeout-ms`.
- [ ] On that same path, stderr never contains `gh is not available` and the CLI never exits 2.
- [ ] The existing `ghAvailable: false` cases in `tests/bin-lib/flow/pr-early-open.test.js` still exit 2 with the unchanged `gh is not available` message.
- [ ] `node --test tests/bin-lib/repo-resolve.test.js tests/bin-lib/flow/pr-early-open.test.js` passes, and each new test goes red when its production change is reverted.

## Release Note

Report a slow `gh` as a timeout that names the `CLAUDE_TWEAKS_GH_TIMEOUT_MS` / `gh-timeout-ms` override, instead of claiming `gh` is not installed.

## Technical Approach

In `repo-resolve.js`, import `isTimeoutError` alongside the existing `GH_TIMEOUT_MS` import from `./shared-primitives`. Change the `catch` to `catch (err) { return isTimeoutError(err); }`. A timed-out probe proves the binary exists, so the run stays on the `gh` path. If `gh` really is too slow, the next real call times out and gets the hint from Deliverable 2, rather than a misroute to MCP.

In `pr-early-open.js`, import `isTimeoutError` from `./lib/shared-primitives` (already imported for `GH_TIMEOUT_MS`). In the final `catch (e)`, append the hint line when `isTimeoutError(e)`, for example: `gh timed out after ${GH_TIMEOUT_MS} ms — raise it with the CLAUDE_TWEAKS_GH_TIMEOUT_MS env var or the gh-timeout-ms policy key (max 60000)`. Keep the exit code at 1.

### Key Files

- `plugin/bin/lib/repo-resolve.js` — `ghAvailable` returns `true` on a timeout-classified probe failure
- `plugin/bin/pr-early-open.js` — timeout hint in the outer `catch`
- `plugin/bin/lib/shared-primitives.js` — reference only: `isTimeoutError`, `GH_TIMEOUT_MS`, `CLAUDE_TWEAKS_GH_TIMEOUT_MS`
- `plugin/bin/lib/claim-targets/claim-targets.js` — reference only: existing hint wording to match
- `tests/bin-lib/repo-resolve.test.js` — timeout vs `ENOENT` classification tests
- `tests/bin-lib/flow/pr-early-open.test.js` — timeout-path exit code and stderr test

## Gotchas

- `gh --version` is local-only, so a 5 s timeout on it is unusual. The report's exit-2 message can only come from the `ghAvailable` branch, though, so the probe did fail on that host (a cold start, or gh's own startup work). Do not "fix" this by dropping the timeout from the probe. The bound is deliberate (`repo-resolve.js:29-34`, #2567).
- `ghAvailable` is shared by about 20 CLIs. This change alters only their timeout case, which today misroutes to the MCP path for a `gh` that is present. Callers' own tests inject `ghAvailable` as a stub and are unaffected. Do not widen the `true` case beyond `isTimeoutError`: a non-zero exit from `gh --version` (a broken install) stays "absent".
- `isTimeoutError` also matches `signal === 'SIGTERM'`. That matches every other consumer of the helper, so keep the shared definition and do not add a local variant (`docs-health/commit-ref.js` has its own copy, which is out of scope).
- #4505 also edits `plugin/bin/lib/repo-resolve.js` (the GHE host seam), and #4492 edits `plugin/bin/pr-early-open.js`. Expect a merge-time rebase. The changes touch different functions.
- `openPrEarly`'s internal `gh` calls may convert some failures into a logged degrade (exit 3) before they reach the outer `catch`. This record covers only the outer-`catch` path the report observed (`spawnSync gh ETIMEDOUT`, exit 1).

## Original request

pr-early-open: a gh timeout is reported as "gh is not available" and routed to the MCP path

**Summary:** On a slow GitHub Enterprise host, `pr-early-open.js`'s first `gh` call hit the 5 s default timeout, and the CLI reported `gh` as missing (exit 2, "open the draft PR through mcp__github__create_pull_request"). `gh` was installed and authenticated.

**Kind:** Defect

**Affected component:** `bin/pr-early-open.js` (its `gh`-availability classification), with `bin/lib/shared-primitives.js`'s `DEFAULT_GH_TIMEOUT_MS = 5000` as the trigger.

**Repro steps:**
1. Use a GitHub Enterprise host where a single `gh repo view --json nameWithOwner,url,defaultBranchRef` takes ~18 s (measured with `time`).
2. Run `/claude-tweaks:build` in `pr-first` mode, so Spec Step 1 calls `node bin/pr-early-open.js --run … --target "#N" --fixes N --title … --summary-file …` with `GH_HOST` set and no `CLAUDE_TWEAKS_GH_TIMEOUT_MS`.
3. First attempt: exit 2, `pr-early-open.js: gh is not available — open the draft PR through mcp__github__create_pull_request, per the "gh absent" row …`.
4. Retries: exit 1, `pr-early-open.js: spawnSync gh ETIMEDOUT`.
5. `CLAUDE_TWEAKS_GH_TIMEOUT_MS=60000` with the same command: `{"outcome":"opened",…}`.

**Expected vs. actual:**
Expected: a `gh` call that times out is reported as a timeout. The message should name `CLAUDE_TWEAKS_GH_TIMEOUT_MS` (the env var already exists) and keep the run on the `gh` path.
Actual: the first timeout is classified as `gh` being absent, which sends the caller to the MCP fallback for a tool that is present. The later `ETIMEDOUT` error doesn't mention the timeout knob either, so the fix had to be found by reading `shared-primitives.js`. Cost: three failed calls plus a manual diagnosis before the draft PR could open.
