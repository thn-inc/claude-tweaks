# 2391: wrap-up-pack.js resolveRecords spec-* rung never worktree-mirrors materialized headers

Surface: infra

## Current State

`bin/lib/wrap-up/pack.js`'s `resolveRecords` ladder has three rungs: (a) the run dir's own
`work/*-spec.md` headers, (b) the worktree's mirror of that same run dir (via `worktreeMirror`),
and (c) a parent multi-spec run's `manifest.yml` ids plus any `spec-*/work/` headers found by
`deps.readdir(runDir)`. Only rungs (a) and (b) apply worktree-mirroring; rung (c) reads `spec-*`
subdirectories directly from `runDir` (the main-checkout path `--run` anchors to), never from the
worktree.

For a `/claude-tweaks:dispatch` file-overlap group (2+ records sharing one worktree/branch/PR),
`materialize.md` writes each record's header to `{run-dir}/spec-{n}/work/{n}-spec.md` and commits
it on the feature branch -- so on a real pr-first run it exists only inside the worktree's own
working tree, never in the main-checkout run dir, exactly the same reason rungs (a)/(b) already
mirror. Observed live on run `2026-09-14T000308-record-2283-2338` (group #2283,#2338):
`node bin/wrap-up-pack.js --run "$RUN_DIR"` returned `recordLabels`, `claim`, `ledger`, and
`unblocked` all as `{ok: false, error: "records unresolved -- no materialized header or manifest
found"}` even though both `spec-2283/work/2283-spec.md` and `spec-2338/work/2338-spec.md` existed
and were readable inside the worktree.

## Deliverables

Extend rung (c) in `resolveRecords` (`bin/lib/wrap-up/pack.js`) to also check
`worktreeMirror(runDir, worktree)` for `spec-*/work/` headers and the mirrored `manifest.yml`,
the same way rung (b) mirrors rung (a) -- falling back to the existing `runDir`-only read when no
worktree resolves or the mirror has nothing.

## Acceptance Criteria

- A fixture reproducing this run's shape (main-checkout run dir with no `work/` or `spec-*/`
  entries; a separate worktree dir carrying `spec-{n}/work/{n}-spec.md` for 2+ records) resolves
  `records` via a new `worktree-manifest`-shaped source, not `unavailable`.
- The four probes that depend on `resolveRecords` (`recordLabels`, `claim`, `ledger`, `unblocked`)
  succeed against that fixture instead of returning `records unresolved`.
- Existing `resolveRecords`/`wrap-up-pack` tests continue to pass unchanged.

## Technical Approach

Mirror rung (b)'s existing pattern (`worktreeMirror(runDir, worktree)`) into rung (c): when the
direct `runDir`-anchored `spec-*/work/` read finds nothing, resolve the worktree mirror path the
same helper rung (b) already uses, and re-run the same `spec-*/work/` + `manifest.yml` read
against that mirrored path before falling back to `unavailable`. No new mirroring mechanism --
reuse the existing `worktreeMirror` helper rungs (a)/(b) already call.

### Key Files

- `plugin/bin/lib/wrap-up/pack.js` -- `resolveRecords`'s rung (c), and the `worktreeMirror` helper
  to reuse
- test fixture covering the group-overlap shape this record reports (main-checkout run dir empty,
  worktree carrying `spec-{n}/work/{n}-spec.md` for 2+ records)

## Gotchas

- The fix must preserve rung (c)'s existing `runDir`-only behavior for the common single-record
  or no-worktree case -- the worktree-mirror check is an additional fallback, not a replacement
  for the direct read.
