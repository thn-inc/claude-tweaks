# 2385: wrap-up-pack.js: residue/state/blastRadius probes hardcode "main" instead of the canonical integration-branch ladder

Surface: infra

**Related:** #2422 (same hardcoded-`main`-vs-integration-branch-ladder theme, different file)

## Current State

`bin/lib/wrap-up/pack.js`'s `resolveHeader` (the function backing `bin/wrap-up-pack.js`'s
`residue`, `state`, and `blastRadius` probes) resolves the integration branch at line 233-238:

```js
const policy = {
  integrationBranch: values['integration-branch'] || '',
  ...
};
const integrationBranch = policy.integrationBranch || 'main';
sources.integrationBranch = policy.integrationBranch ? 'policy' : 'default';
```

It only ever consults `resolvePolicy`'s `integration-branch` key. When that key is unset (no
`.claude-tweaks/policy.yml` pin), it falls straight to the literal string `'main'` -- never
consulting `skills/_shared/integration-branch.md`'s canonical ladder (routine template ->
policy.yml -> CLAUDE.md prose -> git/`gh repo view` default -> per-consumer fallback), which
exists precisely so callers don't each hardcode their own guess.

On a repository whose actual default branch is not `main` (e.g. `master`), with no
`integration-branch:` policy key set, this causes `residue`/`state`/`blastRadius` to fail:
`could not resolve merge base of "main" and HEAD"` (`blastRadius`) or `"base unresolved -- no
merge-base against the integration branch"` (`residue`/`state`). `sources.integrationBranch`
then reports `"default"` -- i.e. the pack's own provenance trace correctly shows it never
consulted policy.yml, CLAUDE.md, or git/gh at all.

`skills/wrap-up/residue-sweep.md` already documents the correct pattern for a sibling caller:
"`--integration-branch` must always be passed explicitly -- never rely on the CLI's own
default... resolve `{ref}` via `skills/_shared/integration-branch.md`'s canonical ladder before
invoking the CLI." `pack.js`'s `resolveHeader` is the one caller that still bypasses this.

## Deliverables

- `resolveHeader` in `bin/lib/wrap-up/pack.js` resolves `integrationBranch` via
  `skills/_shared/integration-branch.md`'s canonical ladder (minus the routine-template rank,
  which has no meaning inside this CLI -- policy.yml -> CLAUDE.md prose -> git/`gh repo view`
  default), not a bare `policy.integrationBranch || 'main'` fallback.
- `sources.integrationBranch` reports which ladder rank actually resolved the value (e.g.
  `'policy'`, `'git-default'`), not just the binary `'policy'`/`'default'` it reports today --
  so a reader of the pack's own provenance trace can tell which rank fired.

## Acceptance Criteria

- On a repository whose actual default branch is not `main`, with no `integration-branch:` key
  in `.claude-tweaks/policy.yml`, running `node bin/wrap-up-pack.js --run <run-dir>` resolves the
  real default branch (via git/`gh repo view`) instead of hardcoding `main`, and the
  `residue`/`state`/`blastRadius` probes run to completion instead of failing on an unresolved
  merge base.
- `inputs.sources.integrationBranch` in the pack's output reflects the actual resolution source,
  never silently reporting `'default'` when a real ladder rank (git/gh, or CLAUDE.md prose) fired.
- A repository that already sets `integration-branch:` in `.claude-tweaks/policy.yml` is
  unaffected -- this fix only changes what happens when that key is absent.
- Existing tests covering `pack.js`'s header resolution still pass; add a test covering the
  non-`main`-default, no-policy-key case this record reports.

## Technical Approach

Replace `pack.js`'s bare `policy.integrationBranch || 'main'` fallback with a call into
`skills/_shared/integration-branch.md`'s canonical resolution -- the same git/`gh repo view`
default-branch lookup `residue-sweep.md` already instructs its own callers to perform before
invoking `bin/residue.js` directly. Reuse whatever resolver function backs that lookup elsewhere
in `bin/lib/` (check for an existing `resolveIntegrationBranch`-shaped helper before writing a
new one -- `bin/lib/reconcile/` and `bin/resolve-policy.js` both touch this same ladder and may
already export a reusable piece). Thread the resolved value's source rank through to
`sources.integrationBranch` so the pack's own provenance trace stays accurate.

### Key Files

- `plugin/bin/lib/wrap-up/pack.js` -- `resolveHeader`'s integration-branch fallback (line ~233-238)
- `plugin/skills/_shared/integration-branch.md` -- the canonical ladder this fix must follow, not restate
- `plugin/skills/wrap-up/residue-sweep.md` -- the existing sibling-caller pattern to mirror

## Gotchas

- Workaround used to file this record: invoking `bin/residue.js` and `bin/blast-radius.js`
  directly with an explicit `--base`/`--integration-branch master`, bypassing `pack.js`'s own
  (broken) resolution for those two fields -- confirms the underlying probes work correctly once
  given the right branch name; the defect is isolated to `pack.js`'s own resolution step.
- `merge-size-probe.js`, `release/precheck.js`, and `release-preflight/pack.js` carry similar
  `|| 'main'` fallbacks (found via a repo-wide grep while shaping this record) -- out of scope
  for this record, which is filed specifically against `wrap-up-pack.js`'s probes; worth a
  follow-up capture if they prove to have the same defect.

## Original request

wrap-up-pack.js: residue/state/blastRadius probes hardcode "main" instead of the canonical integration-branch ladder

**Summary:** `bin/wrap-up-pack.js`'s `residue`, `state`, and `blastRadius` probes all failed on a repository whose default branch is not literally named `main`, with `could not resolve merge base of "main" and HEAD`. `skills/_shared/integration-branch.md` documents a canonical resolution ladder (explicit arg -> routine template -> `policy.yml`'s `integration-branch:` key -> CLAUDE.md prose -> git/`gh repo view` default -> per-consumer fallback) specifically so callers don't each hardcode their own guess, but this tool's `main` fallback bypasses that ladder entirely.

**Kind:** Defect

**Affected component:** `bin/wrap-up-pack.js`

**Repro steps:**
1. In a repository whose actual default branch is `master` (not `main`), with no `integration-branch:` key set in `.claude-tweaks/policy.yml`.
2. Run `node bin/wrap-up-pack.js --run <a valid pipeline run dir>`.

**Expected vs. actual:**
Expected: the tool resolves the integration branch via `_shared/integration-branch.md`'s ladder (landing on the repo's actual default via `gh repo view --json defaultBranchRef` / `git remote show origin`) and the `residue`/`state`/`blastRadius` probes run normally.
Actual: all three probes fail with `error: "could not resolve merge base of \"main\" and HEAD"` (`blastRadius`) or `"base unresolved -- no merge-base against the integration branch"` (`residue`/`state`), and the pack's own `inputs.sources.integrationBranch` reports `"default"` -- i.e. it never consulted policy.yml, CLAUDE.md, or git/gh at all.

**Definition:** Clear -- cite `_shared/integration-branch.md` in `wrap-up-pack.js` the same way `residue-sweep.md` already instructs its own caller to resolve `{ref}` before invoking `bin/residue.js` directly. Workaround used this run: invoke `bin/residue.js` and `bin/blast-radius.js` directly with an explicit `--base`/`--integration-branch master`, bypassing the pack's own (broken) resolution for those fields.

**Plugin version:** 6.123.0
