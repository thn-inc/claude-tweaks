# 2736: wrap-up: start-of-run residue is flagged once and never resurfaced at the Review Console

Surface: infra

## Current State

At session start, the SessionStart hook surfaced 3 unfinished pipeline runs (`record-2585`, `record-2539`, `record-1936` — one interrupted, two active, each with an open PR) and 1 standalone run with unapproved staged proposals (`2026-09-19T185831-sweep-standalone`), each with its own resolution command, correctly declining to touch any of them (ownership could not be confirmed — a listed run might be live in a sibling session). This is the correct safety behavior.

However, this residue was surfaced exactly once, at the very top of the session, and never resurfaced again — not at either Review Console this session ran, not in the final closing summary — across a session that ran for roughly 8.6 hours. A one-time-only notice easily gets lost in a long transcript, especially one with a multi-hour unattended stretch in the middle (see the separate merge-authorization finding filed alongside this one).

## Deliverables

- [ ] Have `/claude-tweaks:wrap-up`'s Review Console (both the single-spec and multi-spec/consolidated forms) re-check for any residue that was flagged at this session's own start and remains unresolved (same detection the SessionStart hook already runs — unfinished `.claude-tweaks/pipelines/` runs, unapproved `staged/` proposals on a standalone run), and render a short "still-pending from earlier" line pointing back at it, rather than treating the SessionStart notice as sufficient for the whole session's duration.
- [ ] Ensure this resurfacing check does not attempt to resolve or act on the residue itself — it is informational only, preserving the existing ownership-safety posture (a listed run may belong to a sibling session).

## Acceptance Criteria

1. A `/claude-tweaks:wrap-up` Review Console rendered later in a session that started with unresolved residue includes a line naming that residue and its resolution command, without attempting to act on it.
2. The check adds no new `AskUserQuestion` stop — it is a passive, informational re-surface only.
3. `npm test` passes.

## Technical Approach

Re-run the same residue-detection logic the SessionStart hook already implements (unfinished `.claude-tweaks/pipelines/` run directories, unapproved `staged/` proposals) as a read-only check inside the Review Console's own render step, rather than duplicating the detection rules by hand — find the hook's existing implementation and call the same underlying check (or its result, if already cached/logged somewhere this session) instead of re-deriving the unfinished-run/staged-proposal criteria independently, which would risk the two checks drifting apart over time.

### Key Files

- `plugin/skills/wrap-up/review-console.md` — the single-spec Review Console render, where the new "still-pending from earlier" line is added
- `plugin/skills/wrap-up/console-template.md` — the shared console template both single- and multi-spec forms compose from, if the addition belongs at that shared layer rather than duplicated in each
- SessionStart hook's own residue-detection implementation (the code that produced this session's own opening notice) — the logic to reuse, not reimplement

## Gotchas

- Preserve the ownership-safety posture exactly — this check must never attempt to close, resume, or otherwise act on a residue item it finds, even one that looks obviously abandoned; a listed run may be live in a sibling session, same as the original SessionStart notice already warns.
- Don't add a new `AskUserQuestion` for this — Acceptance Criteria 2 is explicit that this stays a passive, informational line, not a new stop competing with the console's own existing decision points.
