# 4593: flow artifact-overwrite check: flags a spec's own review fix as an overwrite when commits carry no refs #N trailer

Surface: backend

## Current State

The multi-spec artifact-overwrite completion check (`plugin/skills/flow/multispec-artifact-namespacing.md`, run before the Consolidated Review Console) calls `plugin/bin/check-artifact-overwrite.js`. It finds every `docs/journeys/` or `stories/` path that one commit in the run added and a later commit modified. A hunk with deletions passes only if one of three extension tests in `plugin/bin/lib/flow/artifact-overwrite-check.js` accepts it: same-spec self-edit, list reflow, or step-markup reformat. Anything else is reported as an overwrite (exit 1), which HARD-GATEs the run.

The same-spec self-edit test (`artifact-overwrite-check.js:310`, `const selfEdit = commitRefs.size > 0 && setsIntersect(commitRefs, blamedRefs)`) attributes commits only through a `refs #N` trailer on the commit message (`extractRefs`, `:85`). Most of the pipeline's commit sites (stories, review fix waves, wrap-up) write no such trailer; only `plugin/skills/build/micro-plan.md:66` asks for `refs #{n}`. In a run where neither commit has a trailer, the test can never match. A spec's own review fix to a story or journey file it added earlier in the same run then trips the HARD-GATE as a false positive, and the run stops for a manual ruling. This is the most common legitimate edit of that kind.

The run already records which spec was running when. Every `spec-status` call appends `{ phase, status, at }` to `specs[].phases[]` in the multi-spec run's `manifest.yml` (`plugin/bin/lib/flow/manifest.js`'s `transitionSpec`, `spec.phases.push({ phase, status, at: nowIso })`), and `startedAt` is set on a spec's first `running` transition. `readManifest(runDir)` is exported from the same module. The check does not read the manifest today.

## Deliverables

- **Manifest-window attribution fallback.** `checkArtifactOverwrite` accepts an optional `manifest` (or `runDir`) input. A commit is attributed to spec ids in this order:
  1. its own `refs #N` trailer, when present (unchanged);
  2. otherwise, the single spec whose manifest window contains the commit's author date. A spec's window runs from its first recorded transition (`startedAt`, else its earliest `phases[].at`) up to the next spec's first recorded transition. The last spec's window is open-ended.
  3. otherwise the commit is unattributed (an empty set, as today).

  The same-spec self-edit test then compares these attributions for the deleting commit and every blamed commit. A commit whose author date falls inside no window, or inside more than one, stays unattributed. The fallback never guesses.
- **CLI flag.** `plugin/bin/check-artifact-overwrite.js` gains an optional `--run <dir>` flag that reads `manifest.yml` from that directory and passes it through. Without the flag, or with no readable manifest there, behavior stays as it is today, refs-only. An unreadable or unparseable manifest named by `--run` is the walk's own failure (exit 3), never a silent fall back to refs-only.
- **Distinct unattributable reason.** When a self-edit judgment fails because the deleting commit or a blamed commit has no attribution from either source, the `overwrites[]` entry's `reason` says so explicitly ("unattributable — no refs trailer and no manifest window"). It must not reuse the "refs trailer does not match" wording, so whoever makes the manual ruling can tell a missing attribution from a confirmed cross-spec deletion. The entry still fails closed: it stays in `overwrites[]`, and the exit code is still 1.
- **Procedure update.** `plugin/skills/flow/multispec-artifact-namespacing.md`'s invocation passes `--run "{parent}"`, the multi-spec parent run directory that holds `manifest.yml`. Its test-1 description names both attribution sources and their order.
- The module header comment's description of test 1 is updated to match.

## Acceptance Criteria

- [ ] Fixture: spec A adds `stories/x-A.yaml`, and a later commit inside spec A's manifest window changes one of its lines. Neither commit carries a `refs` trailer. With the manifest supplied, the result is `clean: true`.
- [ ] Fixture: same history, but the modifying commit's author date falls inside spec B's window. The result is still an overwrite: one entry for that path and commit.
- [ ] Fixture: the same untrailered self-edit with no manifest supplied still reports an overwrite. Its `reason` contains `unattributable`, not `refs trailer does not match`.
- [ ] Fixture: a commit with a `refs #N` trailer is attributed by the trailer even when its author date falls in a different spec's manifest window (the trailer takes precedence).
- [ ] Fixture: an author date that falls before every spec's first transition leaves the commit unattributed.
- [ ] `check-artifact-overwrite.js --run <dir>` with no `manifest.yml` in `<dir>` exits 3, and stderr names the missing manifest.
- [ ] Each new attribution test goes red when the manifest fallback is removed.
- [ ] Every existing test in `tests/bin-lib/flow/artifact-overwrite-check.test.js` and `tests/bin-lib/flow/check-artifact-overwrite-cli.test.js` still passes unchanged.

## Release Note

A multi-spec `/claude-tweaks:flow` run no longer stops at the artifact-overwrite gate when a spec's own review fix edits a story or journey file that the same spec added earlier in the run.

## Technical Approach

Attribution becomes a per-commit function that the existing `getRefs` cache wraps. It tries the trailer first, then the manifest window looked up by the commit's author date (`git log -1 --format=%aI {sha}`, fetched alongside `%B` in the same call so the walk does not add a git call per commit). `selfEdit` keeps its current shape over the attribution sets. Parse the manifest with `manifest.js`'s `parseManifestYaml`/`readManifest` rather than adding a second YAML reader. Window computation is a small pure function over `multispec.specs` (ordered by first transition) so it can be unit-tested without git.

Alternatives the record offered, and why they lose:
- **Namespace-suffix attribution** (`-{N}` in the filename): this names the file's owner, not the author of the deleting commit. Spec B editing spec A's `-A` file is exactly the overwrite the check exists to catch, so the suffix cannot separate the self-edit from the real overwrite.
- **Writing `refs #{N}` trailers at every commit site**: the check's stated design (`multispec-artifact-namespacing.md`) is to verify the outcome from git history "rather than trusting that every present-and-future write path" follows a convention. A trailer convention spread across build, stories, review, and wrap-up commit sites, including subagent-authored commits, is that kind of trust. It is also incomplete for commits made before the convention lands.

### Key Files

- `plugin/bin/lib/flow/artifact-overwrite-check.js` — manifest-window attribution fallback, the unattributable reason string, and the header comment
- `plugin/bin/check-artifact-overwrite.js` — `--run <dir>` flag, manifest read, and exit 3 on an unreadable manifest

- `tests/bin-lib/flow/artifact-overwrite-check.test.js` — untrailered self-edit, cross-window, trailer-precedence, and out-of-window fixtures
- `tests/bin-lib/flow/check-artifact-overwrite-cli.test.js` — `--run` flag and missing-manifest exit 3
- `tests/multispec-artifact-namespacing-conformance.test.js` — keep passing against the updated command block

## Gotchas

- Use the commit's **author** date, not the committer date. A rebase or cherry-pick rewrites the committer date to the time of the rewrite, which would move a commit out of its spec's window. The author date is preserved.
- Fixture commits must pin `GIT_AUTHOR_DATE` (and `GIT_COMMITTER_DATE`) explicitly. Commits made seconds apart in a test otherwise all land in one window, and the cross-window fixture would pass for the wrong reason.
- Manifest windows apply only to a shared-worktree (sequential) multi-spec run. Parallel-wave members build in their own worktrees, so their windows can overlap. The "more than one window, unattributed" rule is what keeps an overlap from being read as a self-edit.
- `#4590` adds two more extension tests (step renumber, reference-preserving `Origin:` line) to the same module and the same procedure doc. It is a sibling change, not a dependency. Whichever lands second rebases its header-comment and doc edits onto the other's.

## Original request

flow artifact-overwrite check: flags a spec's own review fix as an overwrite when commits carry no refs #N trailer

**Summary:** The multi-spec artifact-overwrite completion check reports a spec's own review-fix edit to its own namespaced artifact as a cross-spec overwrite (a HARD-GATE) whenever the run's commits carry no `refs #N` trailer — which the pipeline's own commit sites never write.

**Kind:** Defect

**Affected component:** /claude-tweaks:flow — multi-spec artifact-overwrite completion check (`skills/flow/multispec-artifact-namespacing.md`, `bin/check-artifact-overwrite.js`, `bin/lib/flow/artifact-overwrite-check.js`)

**Repro steps:**
1. Run a two-spec `/flow` in one shared worktree (specs A then B).
2. Spec A's `/stories` commit adds a namespaced story file, e.g. `stories/x-A.yaml`.
3. Spec A's own review fix wave changes one line in that file (two locator strings updated to match a copy change made in the same commit).
4. None of the run's commits (build, stories, review fix waves) carry a `refs #A` trailer.
5. At end of run, `check-artifact-overwrite.js --base {EXPECTED_BASE} --path docs/journeys/ --path stories/` runs over the run's range.

**Expected vs. actual:**
Expected: the edit is recognised as a same-spec self-correction (both commits are spec A's; the manifest phase timestamps put both inside spec A's test/review window, spec B started hours later; the file carries spec A's `-A` namespace suffix), so the check passes.
Actual: exit 1 with one overwrite reported. The "same-spec self-edit" test requires the deleting commit and the blamed commit to share the same `refs #{N}` trailer, so it can never match in a run whose commit sites don't write that trailer. The procedure treats this as a HARD-GATE before the consolidated console, so the run stops for a manual ruling on a false positive — the most common legitimate edit shape (a spec correcting its own artifact during review).

Suggested fixes (any of):
1. When neither commit has a `refs #N` trailer, fall back to spec attribution from the run's `manifest.yml` phase windows (`specs[].phases[].at`), or from the artifact's own `-{N}` namespace suffix (a file namespaced to spec A, modified while spec A is the running spec, is a self-edit).
2. Have the pipeline's commit sites (build, stories, review fix waves, wrap-up) write a `refs #{N}` trailer in multi-spec runs, so the existing test works.
3. At minimum, report "unattributable (no refs trailer)" as its own verdict instead of an overwrite.

**Definition:** Clear

**Plugin version:** 6.156.1

Related (different false-positive shape in the same check): #4590.

## Plan Review Clarifications

Answered by the maintainer, 2026-10-31, in response to the plan-review question on this record:

- **Q1 (AC7 scope): Reading B.** "Each new attribution test goes red when the manifest fallback is removed" covers only the fixtures whose expected verdict depends on the fallback (AC1, AC2, AC4, AC5). AC3 (no manifest) is proven by reverting its unattributable reason string instead; the pure `computeSpecWindows`/`attributeByWindow` unit tests are exempt.
- **Q2 (mixed-execution runs): Reading B.** Window attribution turns off whenever the manifest names a `not-run` spec — the check falls back to today's refs-only behavior for that run, so it never produces a false clean. This also covers a default-mode run that stopped after a failure (it too keeps refs-only behavior).

Second plan-review round (2026-11-01, question issuecomment-6551069601):

- **Q3 (window end): Reading A.** Keep the Deliverables rule as written: a spec's window ends at the next spec's first recorded transition (the last spec's window is open-ended). Window attribution is switched off for a `parallel` run, which falls back to today's refs-only check, per the Gotcha "Manifest windows apply only to a shared-worktree (sequential) multi-spec run". The procedure tells a parallel run apart by omitting `--run` for it (or an equivalent explicit signal); no max-based window end.
- **Q4 (run whose last spec failed): Reading B.** Window attribution is also switched off when any spec's status is `failed`, not only when the manifest names a `not-run` spec. This keeps Q2's intent: a run stopped by a failure keeps today's refs-only behavior.
