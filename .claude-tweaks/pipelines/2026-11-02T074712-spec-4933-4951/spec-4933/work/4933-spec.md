## Release Note

Issue commands now stop with an error naming the host when your git origin is not a recognized GitHub host, instead of sending gh and your enterprise token there; export GH_HOST with that host to confirm it is GitHub Enterprise.

## Technical Approach

### Decision

**Refuse.** When an issues CLI derives a host from the git origin and that host carries no positive GitHub signal (it is not `github.com`, does not end in `.ghe.com`, is not a key in gh's `hosts.yml`, and no `GH_HOST` is exported as an explicit opt-in), the CLI does not pass it to gh as `--repo host/owner/repo` or `--hostname`. It exits non-zero with an error naming the unknown host and the opt-in (export `GH_HOST={host}` if it really is GitHub Enterprise). A user-typed `--repo host/owner/repo` is kept as given.

Why: this matches gh's own behavior, since a bare `gh issue view` in such a repo already fails with "none of the git remotes … point to a known GitHub host". Accepted cost: a repo whose origin is on GitLab (or another forge) but which tracks issues on github.com must export `GH_HOST=github.com` or add a GitHub remote.

Rejected alternative, drop: fall back to a bare `owner/repo`. That sends the github.com token instead and acts on whatever same-named repo exists on github.com, possibly a stranger's, while looking like normal operation.

`GH_HOST` reading: an exported `GH_HOST` is the user's explicit choice of host, the same rule the seam already applies (`ghOptions` returns early when `GH_HOST` is in the env; `explicitRepoGhHost`'s "the user's value wins"). When it matches the origin host, that host passes through host-qualified; when it names another host, the origin host is not named at all, the slug is bare, and gh goes to the exported host. That is what makes the `GH_HOST=github.com` workaround above work.

### Shape

One gate function in `repo-resolve.js`, called at each producer's origin branch only (the `opts.repo ? … : parseRepo(remote)` ternary in each CLI; `repoSpecOf` for the hook side). Host normalization happens inside the gate, so every downstream consumer (`repoSlug`, `repoResolutionNote`, the lib modules' `--hostname` threading) receives one normalized host and needs no change. The gate cannot live in `ghOptions`: by the time a call reaches the seam, its argv already carries `--repo`/`--hostname` and `hasExplicitHostArg` sends it through untouched.

## Gotchas

- A GitHub Enterprise Server user who relies on `GH_ENTERPRISE_TOKEN` alone (no `hosts.yml` key, no exported `GH_HOST`, host not on `.ghe.com`) gets refused where the CLIs ran before. That is the decision, not a regression; the error text must give them the opt-in.
- #4951's drafted fix for `stuck-open-prs.js` (`resolveGhHost(process.cwd()) || 'github.com'`) is the rejected drop behavior. Build #4951 on this record's gate instead; it lands in the same flow.
- #4952's planned rewrite of the `gh-api-module-pattern` skill says a `--hostname` is "omitted when it returns null", which is also the drop shape; it should point at this record's gate and its refusal.
- #4806 (in progress) edits `fetch-sub-issues.js`'s `--hostname` threading; expect a rebase on that file. #4794 plans to host-qualify `repoSlugOf` slugs in reconcile and `claim-store.js`; any host it adds must come from this gate.
- `repoSpecOf`'s fallback (`git-exec.js:223-227`) returns `host: null` for a remote `parseRepo` cannot read, such as an `ssh://` URL; #4857 owns that case. Do not widen it here, and do not turn a null host into a refusal without that record's decision.
- A new post-merge `failure` word is a vocabulary change: grep `plugin/bin` and `plugin/skills` for the existing words (`no-remote`) to find every reader before adding it.
- Each CLI keeps its own exit-code vocabulary (the `gh-api-module-pattern` skill's CLI wrapper contract); reuse the code each one already returns for an unresolvable owner/repo rather than inventing one.

## Open Question
