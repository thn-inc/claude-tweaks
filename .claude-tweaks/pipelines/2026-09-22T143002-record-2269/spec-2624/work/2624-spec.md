# 2624: Add pre-launch security hardening checklist for AI-built apps

Surface: infra

## Current State

The plugin has no dedicated pre-launch security check for the failure patterns common in AI-generated web apps: secrets embedded in the client bundle instead of server-side env vars, routes returning user data with no per-user ownership check (missing Supabase RLS or equivalent), and AI-model-calling endpoints with no auth, per-user rate limiting, input-length cap, or provider spend alert. `plugin/skills/code-health/SKILL.md` already has an extension point built for exactly this kind of repo-wide, criterion-driven check — `focus=<vertical>` mode (documented in `code-health/SKILL.md`'s "Focus Mode" section): a deterministic generator produces a fixed candidate set repo-wide, and the focus pins its own judging criterion in place of `criteriaForArea`'s area-type lookup, while dedup/fingerprint/file-issue (Steps 2, 5+) run unchanged. `plugin/skills/review/SKILL.md`'s Code-Mode Procedure already has a precedent for a component-skill step invoked mid-pipeline: Step 6.5 (Design Quality Pass via `/claude-tweaks:design-wrapper`) and Step 6 (visual-review recommendation).

A structurally parallel record, #2622 ("Add a pre-scale hardening skill for AI-coded apps"), proposes a new standalone skill (`/scale-readiness`) walking a codebase through a different but adjacent set of checks (query/background-job/caching/pooling/monitoring). #2625 ("Add GDPR account-deletion vs. backup-retention check") is a third, already-shaped, narrower security-adjacent check (cryptographic erasure for backup retention). None of the three currently cross-reference each other's scope boundary in a shared doc.

## Deliverables

1. A security-hardening check covering exactly the three named categories: (a) no secrets in the client bundle (server-side env vars only), (b) per-user ownership checks / RLS-equivalent enforcement on every table/route returning user data, (c) auth + per-user rate limiting + input-length cap + provider spend alert on every AI-model-calling endpoint.
2. One copy-paste prompt per check (three total), matching the prompt-pattern convention already used elsewhere in the pipeline (e.g. the verbatim-command style prompts in existing skill sub-files) — each prompt runnable standalone by a user without invoking the full skill.
3. Implemented as a new `focus=<vertical>` criterion + candidate generator in `plugin/skills/code-health/`, following the existing Focus Mode extension pattern (`code-health/SKILL.md`'s Focus Mode section, `focus-mode.md`'s registry lookup) rather than a parallel bolt-on mechanism.
4. A new step in `plugin/skills/review/SKILL.md`'s Code-Mode Procedure invoking this check as a component skill (mirroring Step 6.5's Design Quality Pass pattern), so it also runs "as a step within /review."
5. Documentation in the new criterion/generator's own file (or `code-health/SKILL.md`'s Focus Mode section) explicitly stating the scope boundary against #2622 (performance/scale) and #2625 (GDPR/backup retention) — what this check owns vs. what it explicitly does not, so future work doesn't duplicate scope across the three.
6. `docs/skill-graph.md` updated per CLAUDE.md's "Every relationship between skills is stated once" convention, since this adds a new cross-skill edge (code-health focus criterion invoked from review).

## Acceptance Criteria

- Running `/claude-tweaks:code-health focus=<the-new-vertical-name>` against a sample vibecoded app fixture containing all three violation patterns (a client-bundle secret, a route missing an ownership check, an unthrottled AI-calling endpoint with no spend alert) flags a distinct finding for each of the three categories.
- Running the same check against a fixture with none of the three violations present produces zero findings for this criterion (no false positives on clean code).
- `plugin/skills/review/SKILL.md`'s Code-Mode Procedure invokes the new check as a numbered step, and `/claude-tweaks:review {n}` on a spec-record touching client/server boundary code exercises that step.
- The new criterion's own documentation (or `code-health/SKILL.md`) states, in prose, how its scope differs from #2622's pre-scale hardening and #2625's GDPR/backup-retention check — no overlapping category is claimed by two of the three.
- `docs/skill-graph.md` lists the new edge (the new review step invoking the code-health focus criterion).
- `npm test` passes in full after the change.

## Technical Approach

Add a new focus-mode vertical to `code-health`'s generator registry (per `focus-mode.md`'s registry lookup convention — never hand-listed in `SKILL.md` itself, per that file's own IL-40 note), with a dedicated candidate generator that scans for: (a) client-bundle files (build output or client-side source under a recognized framework's client directory) containing a literal API-key/secret pattern, (b) route/handler files returning user-scoped data with no visible ownership predicate (a `WHERE user_id = ` -shaped filter, an RLS policy reference, or equivalent) in the same file or its immediately-composed query, (c) route/handler files calling a recognized AI-model SDK/API with no visible auth middleware, rate-limit decorator/middleware, input-length validation, or spend-alert/budget-check reference nearby. Each candidate is judged by a dedicated criterion (per `criteriaForArea`'s pinning pattern) rather than the generic area-type lookup, following the existing Focus Mode contract exactly (Steps 2 and 5+ unchanged, only scoping/candidate-generation and criterion selection are new).

Wire this focus criterion into `plugin/skills/review/SKILL.md` as a new step in the Code-Mode Procedure, following the Step 6.5 Design Quality Pass precedent: a numbered step that invokes the code-health focus run as a component skill and folds its findings into the review's own summary (Step 7), governed by its own contract per that pattern (Next-Actions omitted when invoked from `/review`, per the Component-Skill Contract convention `review/SKILL.md` already documents for its other component steps).

Write the three copy-paste prompts as literal, standalone text blocks in the new criterion's documentation — one per check category — so a user can run any single check manually without invoking the full skill, matching the pattern the record itself asks for ("matching the pattern already used elsewhere in the pipeline").

## Gotchas

- The client-bundle-secret detection heuristic risks false positives on legitimate public keys (a Stripe publishable key, a public API endpoint identifier) that are safe to ship client-side — the criterion must distinguish "looks like a secret pattern" from "is actually a private/server-only credential," or it will flag safe code and train users to ignore the check.
- The per-user-ownership-check heuristic is necessarily approximate — it can only detect the *absence* of a recognizable ownership predicate near the query, not verify that an existing predicate is actually correct (scoped to the right user, not bypassable). This is a "flag for human review" check, not a formal proof.
- Detecting "no rate limiting middleware nearby" for AI-calling endpoints depends on recognizing whatever middleware/decorator convention the target codebase uses — this will vary widely across frameworks (Express middleware, Next.js route handlers, a custom decorator), so the generator's coverage boundary (per IL-110's convention that every generator states its own coverage boundary) must be explicit about which frameworks/patterns it recognizes and which it does not.
- Overlap risk with #2622 and #2625 is real: #2622's pre-scale skill and this check both touch "endpoint hardening" territory (rate limiting appears in both problem statements), and #2625's GDPR check is a narrower security-adjacent concern. The scope-boundary documentation (Deliverable 5) is not optional polish — without it, a future contributor extending any of the three is likely to duplicate a check the others already own.
- This record's own Deliverables text hedges on exact placement ("such as /security-review or /code-health, or a small standalone skill") — `/security-review` in that phrasing refers to the separate, personal top-level skill outside this plugin (not a `claude-tweaks:` skill), so the only in-plugin candidates are `/code-health`'s focus-mode extension point (chosen here) or a wholly new standalone skill; the Focus Mode route was chosen because it reuses an existing, tested mechanism (dedup, fingerprinting, issue-filing) rather than duplicating that machinery in a new skill.

- Add a pre-launch security checklist to claude-tweaks (new policy rows on an existing skill such as /security-review or /code-health, or a small standalone skill) covering: no secrets in the client bundle, per-user ownership checks / RLS on every table, and auth + rate limiting + spend alerts on every AI-calling endpoint.
- Ship one copy-paste prompt per check, matching the pattern already used elsewhere in the pipeline.

Acceptance Criteria:
- Running the check against a sample vibecoded app flags a violation in each of the three categories when present.
- Docs note how this relates to the existing pre-scale hardening work (issue #2622) so the two don't duplicate scope.
- Works standalone and as a step within /review or /build.
