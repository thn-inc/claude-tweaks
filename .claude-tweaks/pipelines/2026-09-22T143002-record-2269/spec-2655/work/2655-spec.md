# 2655: Add a UI/UX heuristics review lens

Surface: infra

**Related:** #2628

## Current State
A social-media Reel (hook-only caption; transcribed) lists roughly 20 UI/UX heuristics — reduce choices per screen, use large targets, favor familiar patterns, group related info, chunk content, keep interactions under 400ms, highlight the primary action, keep key actions nearby, put essentials first, end flows memorably, show visible progress, simplify complex interfaces, use sensible defaults, prevent errors proactively, make errors recoverable, keep patterns consistent, visually connect related elements, reduce task time, reveal complexity gradually, and make completion feel close. No existing claude-tweaks skill applies a UX-heuristics lens during review or build — the closest existing checks (#2622, #2624, #2625, #2628) are backend/security-focused and don't touch interaction-design quality.

## Deliverables
1. A reusable UI/UX heuristics checklist (the ~20 items above, normalized into policy-row form: heuristic name, what it flags, and an example violation) stored where a review-stage skill can load it — either as a new section of an existing review skill (`/claude-tweaks:review` or `/claude-tweaks:visual-review`) or a new lightweight lens file under that skill's directory.
2. Wiring so a build/review pass can run the checklist against a rendered screen or component and flag violations — e.g., "no visible progress on a long-running operation," "primary action not visually highlighted," "more than N top-level choices on one screen."
3. A short usage note (in the hosting skill's own docs) describing when the lens applies (Surface: web/mobile/desktop records) versus when it doesn't (backend/infra work with no rendered UI).

## Acceptance Criteria
- The checklist exists as a standalone, reusable artifact (a markdown lens file or skill section) — not merely restated in this issue's text.
- The checklist enumerates each of the ~20 heuristics as a distinct, checkable row (heuristic + what a violation looks like), not a single paragraph.
- Running the checklist against at least one sample screen or component that violates a known heuristic (e.g., a long-running action with no progress indicator) produces a flagged finding naming that specific heuristic.
- Running the checklist against a sample screen with no violations produces no false-positive flags for the heuristics it does check.
- The lens is invocable from at least one existing review-stage skill's normal flow (`/claude-tweaks:review` and/or `/claude-tweaks:visual-review`), not only as a standalone document nobody calls.

## Technical Approach
Normalize the ~20 heuristics from the source Reel into a policy-row table (name | signal to look for | example violation), mirroring the existing policy-row conventions already used elsewhere in this repo's review-stage skills. Host the table as a new lens file cited by whichever existing review skill already inspects rendered UI, rather than duplicating review-orchestration logic. Gate invocation on `Surface: web/mobile/desktop` records (per the repo's existing frontend-detection signal) so backend/infra records never pay for a UX pass that doesn't apply to them.

### Key Files
- `plugin/skills/visual-review/SKILL.md` — candidate host for the new UX-heuristics lens invocation during a visual review pass.
- `plugin/skills/review/SKILL.md` — alternate/additional candidate host if the lens should also run during code review of UI-affecting changes.
- `plugin/skills/design-wrapper/frontend-detection.md` — existing Surface-detection signal to gate when the lens applies.
- A new lens file, path determined by whichever host skill is chosen (e.g. `plugin/skills/visual-review/ux-heuristics-lens.md`) — holds the normalized ~20-item checklist.

## Gotchas
- The heuristics originate from a single unsourced social-media Reel, not a cited UX research source — treat each item as a heuristic prompt to check for, not a hard rule to enforce mechanically; some (e.g. "sub-400ms interactions") may not be measurable without instrumentation this repo doesn't have, and should be phrased as a manual-inspection prompt rather than an automated metric check.
- Overlap risk with Impeccable's existing design-critique surface (`impeccable:impeccable-finish-reviewer`) — confirm this lens complements rather than duplicates checks Impeccable already performs before finalizing which skill hosts it.
- Keep the checklist's scope to UI/UX heuristics only; do not fold in the existing backend/security checks (#2622, #2624, #2625, #2628) it's meant to sit alongside.
