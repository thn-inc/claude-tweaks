# 3023: teardown-run and residue.js: post-merge cleanup reports a clean result when the state is not clean

Surface: infra

## Current State

Two post-merge cleanup checks report a clean result when the state is not clean.

**1. `teardown-run --merged` leaves the worktree directory on disk.** In `plugin/bin/lib/hooks/teardown-run.js:222-242`, when `git worktree remove` fails and `git worktree list --porcelain` shows the entry as `prunable`, the code runs `git worktree prune`. On success it reports `worktree: removed via prune {path} (removal had failed: {rm.stderr || 'no error text'})`. Prune only removes the *registration*. Nothing checks that the directory itself is gone. `wrap-up-engine.js verify`'s `worktree-removed` check (`plugin/bin/lib/wrap-up/engine-verify.js:262-279`) likewise reads only `git worktree list`, so it reports `pass` while the directory remains.

Reported (plugin 6.136.0, Windows, a `pr-first` run resumed after compaction so `ExitWorktree remove` refused): output read `worktree: removed via prune … (removal had failed: no error text)`, exit 0, and `verify` reported `worktree-removed: pass`. The whole directory was still on disk and had to be removed by hand. The failed removal's cause was lost: `rm.stderr` was empty, so "no error text".

**2. The residue release probe reads a stale local `HEAD`.** `plugin/bin/lib/residue/probes/release.js:68` reads `git show HEAD:CHANGELOG.md` and compares it against `git tag -l v*`. In a main checkout whose local integration branch is behind its remote (15 commits in the report, where the mirror fast-forward had been skipped as dirty), a tag fetched from the remote has its CHANGELOG heading only on the remote ref. The probe emits a `kind: release`, `remedy: auto` finding ("tag vX.Y.Z exists … but CHANGELOG.md at HEAD has no version heading"). Acted on, it would open a housekeeping change adding an entry that already exists upstream.

## Deliverables

1. **teardown-run**: after a successful prune fallback, check that `effectiveWorktreePath` no longer exists on disk. If it still exists, report `worktree: registration pruned but directory still present at {path}` as a distinct, non-clean outcome, not "removed". When `rm.stderr` is empty, include `rm`'s exit status (and stdout, if any) in the message so the cause is recoverable.
2. **verify `worktree-removed`**: `fail` when the run's worktree path still exists on disk, even if `git worktree list` no longer names it. The detail names the path.
3. **release probe**: read the CHANGELOG from the integration branch's remote-tracking ref (`origin/{integration-branch}`, resolved per `_shared/integration-branch.md`) instead of `HEAD`, when that ref exists and contains the tag's commit. When the local branch is behind its remote and no remote ref is readable, return `ran: false` with a stated reason (`local integration branch is behind its remote — CHANGELOG check skipped`) rather than a finding.

## Acceptance Criteria

- A `tests/hooks-teardown-run.test.js` case simulates removal failure plus a successful prune while the directory remains. It asserts the "directory still present" outcome and that the output is not "removed". Prove it goes red against the current code.
- A `tests/bin-lib/wrap-up/engine-verify.test.js` case asserts `worktree-removed: fail` when the worktree is unlisted but its directory exists, and `pass` when both are gone.
- A residue release-probe test with a repo fixture where the tag's CHANGELOG heading exists only on the remote-tracking ref asserts no finding. A fixture where the heading is genuinely missing on the remote ref still asserts the finding.
- Existing `tests/bin-lib/residue/` suites pass.
- `npm test` passes in full.

## Release Note

Post-merge cleanup no longer reports a worktree as removed when its folder is still on disk, and no longer proposes CHANGELOG fixes that already exist upstream.

## Technical Approach

Both fixes make the check observe the state it claims: a filesystem `existsSync` on the worktree path after prune and in `verify`, and a remote-ref read for the CHANGELOG. Keep teardown's non-masking intent (`teardown-run.js:226-228`: prune only on the `prunable` state). The new disk check only refines what "success" means after that prune. Resolve the integration branch through the existing shared resolver, never a hard-coded `main`.

### Key Files

- `plugin/bin/lib/hooks/teardown-run.js` — prune fallback (`:222-242`): post-prune directory check, richer failure text
- `plugin/bin/lib/wrap-up/engine-verify.js` — `worktree-removed` check (`:262-279`): on-disk path check
- `plugin/bin/lib/residue/probes/release.js` — CHANGELOG read (`:68`) from the remote integration ref, behind-remote skip
- `tests/hooks-teardown-run.test.js` — directory-still-present case
- `tests/bin-lib/wrap-up/engine-verify.test.js` — unlisted-but-present case
- `tests/bin-lib/residue/probes-git.test.js` — remote-ref CHANGELOG cases, or a new release-probe test file beside it

## Gotchas

- Read `docs/hooks.md` before touching `teardown-run.js`. Teardown must never break a session, and a non-clean outcome should be reported, never thrown.
- `verify`'s `worktree-removed` currently matches the worktree by spec slug (`engine-verify.js:267-268`), not by an exact path. The on-disk check needs the actual path. Read it from `run-state.json`'s `worktree` field rather than guessing from the slug.
- On Windows, a directory can survive removal because a process still holds a handle in it. The disk check must report it, never retry-delete in a loop.
- The release probe runs in consuming projects too (`release.js:1-4`). A project with no remote, or no remote-tracking ref, must keep today's `HEAD` behavior instead of skipping silently.

## Original request

teardown-run and residue.js: post-merge cleanup reports a clean result when the state is not clean

**Summary:** Two post-merge cleanup steps report a clean result on Windows when the state is not clean: `teardown-run --merged` leaves the worktree directory on disk, and the residue release check reads a stale local checkout.

**Kind:** Defect

**Affected component:** `bin/hooks.js teardown-run`; `bin/residue.js` (release probe, as run by `bin/wrap-up-pack.js`)

**Repro steps:**

1. `teardown-run`: on Windows, finish a `pr-first` run whose PR was squash-merged, from a session that no longer owns its worktree (resumed after a context compaction, so `ExitWorktree remove` refuses). Run `close-run`, `ExitWorktree keep`, then from the main checkout `node bin/hooks.js teardown-run --run <archived run dir> --merged`.
2. Residue: in a main checkout whose local integration branch is several commits behind its remote (15 in this case, plus one local reconcile archive commit, so the mirror fast-forward had been skipped as "dirty"), run a standalone `/claude-tweaks:wrap-up`, which runs `wrap-up-pack.js` and its residue probe with `--scope blast-radius`.

**Expected vs. actual:**

1. Expected: the worktree directory is gone, or the command says it is still there. Actual: the output reads `worktree: removed via prune <path> (removal had failed: no error text)`, exit 0. `git worktree list` no longer names the worktree, but the whole directory is still on disk. `wrap-up-engine.js verify` then reports `worktree-removed: pass`. The directory had to be removed by hand. The removal's own error text is also lost ("no error text"), so the cause cannot be read from the output.
2. Expected: no finding, since the remote integration branch's CHANGELOG already has the heading for the latest tag. Actual: a `kind: release`, `scope: blast-radius`, `remedy: auto` finding, "tag vX.Y.Z exists … but CHANGELOG.md at HEAD has no version heading", because `HEAD` is the stale local branch. With `remedy: auto` this would open a housekeeping change to add an entry that already exists upstream.

**Suggested fix:**

1. After the prune fallback, check that the directory is gone and report "directory still present" (and a non-zero or distinct outcome) when it is not; keep the failed removal's stderr in the message. `verify`'s `worktree-removed` row could check the path on disk as well as the worktree list.
2. Have the release probe read the CHANGELOG from the fetched remote integration ref (the same ref the run's base was resolved from) instead of the working tree's `HEAD`, or skip the check with a stated reason when the local branch is behind its remote.

**Definition:** Clear

**Plugin version:** 6.136.0
