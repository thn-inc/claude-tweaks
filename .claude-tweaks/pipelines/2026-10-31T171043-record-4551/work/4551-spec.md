# 4551: wrap-up engine-verify: acceptance-labeling finds parents only through native sub-issue links, ignoring work-links: body-text Parent lines

Surface: backend

## Current State

`wrap-up-engine.js verify`'s `acceptance-labeling` check (`plugin/bin/lib/wrap-up/engine-verify.js`, registered around line 823) redirects each run record to its parent before checking `demo:pending`, per `verification-brief.md`'s Routing rule (a resolvable-parent sub-issue never carries its own `demo:pending`; its parent carries one gate for all of them). Both halves of that redirect only understand `work-links: native`:

- `resolveParent(n, deps, cwd)` (around line 680) resolves the parent solely through `fetchNativeParent` (GraphQL `Issue.parent`, `plugin/bin/lib/issues/native-dependencies.js`). Under `work-links: body-text`, the sub-issue's parent is recorded only as a `Parent: #N` metadata line in the sub-issue's own body (`specify/spec-template.md`, `_shared/work-record.md`'s `Parent: #N` entry, written by `specify/record-creation-subissues.md`). No native link exists, so `fetchNativeParent` returns null. The sub-issue is then treated as a standalone leaf, and the check reports `#{n}: missing demo:pending label`, which is a false `fail`.
- `enumerateSubIssues(parent, deps, cwd)` (around line 709) lists the parent's sub-issues only through the REST `issues/{parent}/sub_issues` endpoint. Under `body-text` that endpoint returns nothing, so once the parent lookup is fixed, every parent would hit the `no sub-issues enumerated` gather failure and render the whole check unknown.

The skill prose already defines the body-text behavior. `wrap-up/verification-brief-parent-gate.md`'s **Resolve the parent** reads the `Parent: #N` line under `body-text`. Its **Enumerate the parent's sub-issues** resolves `work-links` via `resolve-policy.js` and, under `body-text`, parses the parent's own task list with `parseSubIssues` (`plugin/bin/lib/issues/record-dependencies.js`, re-exported by `record.js`). The engine check is the code twin of that procedure, but it implements only the native branch. `work-links` defaults to `body-text` (`plugin/bin/lib/policy-schema.js`), so every project that never set the key hits this. This repo sets `work-links: native` in `.claude-tweaks/policy.yml`, which is why its own runs never surfaced it.

No code parser for the `Parent: #N` line exists today. `record-dependencies.js` parses `Blocked by #N` (`parseDependencies`) and parent task lists (`parseSubIssues`), but not the sub-issue-side `Parent:` line. Skills read that line by eye.

Distinct from #3508 and #4093, which concern how a gated or resolved parent is judged once a parent *is* found. This record is about finding the parent at all under `body-text`.

**Related:** #4617, #3508, #3813, #3963, #3975, #4108, #4362, #4492, #4494, #4501, #4505, #4591, #4609, #4610, #4611

## Deliverables

1. Add a pure `parseParent(body)` to `plugin/bin/lib/issues/record-dependencies.js`. It is a line-anchored `^Parent: #(\d+)\b` match (multiline, first match wins), returns the number or `null`, and mid-line mentions do not count. That matches the existing `DEP_RE`/`SUB_ISSUE_RE` conventions in the same file. Export it there and through `record.js`, like `parseSubIssues`.
2. Make `resolveParent` in `engine-verify.js` branch on the resolved `work-links` value. Read it from the repo root's `.claude-tweaks/policy.yml` through `resolvePolicyKeys(['work-links'], { policyRaw })`, the same way `resolveRiskFloor` reads `risk-floor`, so the schema default (`body-text`) applies when the key is unset.
   - `native`: unchanged (`fetchNativeParent`).
   - `body-text`: fetch the sub-issue's body (`deps.gh(['issue', 'view', n, '--json', 'body'], cwd)`) and return `{ ok: true, parent: parseParent(body) }`. A failed or unparseable fetch returns `{ ok: false, error }`, so the check renders `unknown`, never `fail`.
3. Make `enumerateSubIssues` branch the same way. Under `body-text`, fetch the parent's body, take the sub-issue numbers from `parseSubIssues`, and read each one's `state` and label names. The result is the same `{ number, state, labels }` shape `parentGateState` already consumes. An empty task list stays a gather failure, as it is today for an empty native enumeration.
4. Resolve `work-links` once per check run, not once per record.
5. Unit tests in `tests/bin-lib/wrap-up/engine-verify.test.js` cover the body-text path with an injected `deps.gh`/`deps.git` and a fixture policy. Tests in `tests/bin-lib/issues/record.test.js` cover `parseParent`.

## Release Note

Fix wrap-up's acceptance-labeling check falsely failing sub-issues in projects that link records with `Parent: #N` body lines instead of native sub-issue links.

## Technical Approach

Mirror the prose procedure in `wrap-up/verification-brief-parent-gate.md` (**Resolve the parent** and **Enumerate the parent's sub-issues**) in code, branching on one `work-links` read.

- Add `PARENT_RE = /^Parent: #(\d+)\b/m` beside `DEP_RE`/`SUB_ISSUE_RE` in `record-dependencies.js`, plus `parseParent(body)`. It takes the first match; the metadata block carries at most one `Parent:` line.
- In `engine-verify.js`, add `resolveWorkLinks(repoRoot)` next to `resolveRiskFloor` (same `policy.yml` read and `resolvePolicyKeys` call). Call it once at the top of the `acceptance-labeling` handler and pass the value into `resolveParent` and `enumerateSubIssues` as an extra argument. Keep `resolveParent`'s exported signature backward-compatible: a missing argument means `native`, so existing direct callers and tests keep their behavior.
- For the body-text enumeration, read each sub-issue's state and labels with one batched call rather than N `gh issue view` calls where practical: `gh issue list --state all --json number,state,labels` filtered to the parsed numbers, or per-number `gh issue view {n} --json state,labels`. Either way, upper-case `state` the way the native path does.

### Key Files

- `plugin/bin/lib/issues/record-dependencies.js`: add `PARENT_RE` and `parseParent`, and export it
- `plugin/bin/lib/issues/record.js`: re-export `parseParent` alongside `parseSubIssues`
- `plugin/bin/lib/wrap-up/engine-verify.js`: `resolveWorkLinks`, plus the `work-links` branches in `resolveParent`, `enumerateSubIssues`, and the `acceptance-labeling` handler
- `tests/bin-lib/wrap-up/engine-verify.test.js`: body-text fixtures for the parent redirect, the gate-not-due, no-parent, and fetch-failure cases
- `tests/bin-lib/issues/record.test.js`: `parseParent` cases

## Gotchas

- The `Parent: #N` line is written only under `work-backend: github-issues` + `work-links: body-text`, and only when `/specify`'s Step 2.6 kept a parent (`_shared/work-record.md`). A collapsed decomposition produces parentless records legitimately, so a missing line must resolve `parent: null`, never an error.
- `enumerateSubIssues` treats zero sub-issues as a gather failure on purpose (an empty answer must not read as "every sub-issue closed"). Keep that for the body-text path. A parent body with no task list is `unknown`, not a due gate.
- Read `work-links` from the repo root's policy file (`repoRoot`), not the worktree cwd, the same as `resolveRiskFloor`. A worktree's copy of `policy.yml` can lag main.
- This repo itself runs `work-links: native`, so a local dogfood run never exercises the new branch. The unit tests are the only proof, which is why the revert-to-red AC exists.
