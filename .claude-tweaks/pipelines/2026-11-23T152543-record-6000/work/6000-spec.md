# 6000: Add a read-only lens reviewer worker role and a launcher that runs lens briefs as headless workers

Surface: backend
Risk-flags: auth

## Current State

Review lens reviewers run as in-session Task agents (`plugin/skills/review/step3-lens-dispatch.md`) or as agents of the plugin workflow `review-lens-fanout` (`plugin/workflows/review-lens-fanout.js`, opt-in via `review-lens-dispatch: workflow`). The design (`docs/superpowers/specs/2026-11-18-pipeline-economy-design.md`, `## Evidence`) measured a median first-turn prompt of about 51k tokens for an in-session subagent against about 6k for a driver worker. Phase 10 asks for lens reviewers "launched as lean workers, so a Haiku lens stays under 100k tokens."

The driver already launches lean headless workers: `plugin/bin/lib/driver/worker.js` (the `claude -p` launcher, `--restricted`, generated `--settings`, the envelope) and `plugin/bin/lib/driver/roles.js` (per-role tool lists and settings, with the probed-platform rules in its header). Its reviewer role (`plugin/bin/lib/driver/review.js`) is read-only. No role fits a review lens: a lens must read the review context bundle, the files in scope, and `git diff/show/log` output for the reviewed range.

The workflow script's return shape `{ started, lenses: [{lens, reviewers}], reviewers: [{lens, side, text, failed}] }` is what `review-coordination.js settle-lens-replies` reads.

## Deliverables

1. A `lens-reviewer` role in `roles.js`: Read, plus Grep/Glob where probed per platform (see #5258), plus read-only git commands (`git diff`, `git show`, `git log`, `git grep`) only on sandbox-probed platforms with the sandbox block `roles.js` already generates. No Write, no Edit, no network. On a platform outside `SANDBOX_PROBED_PLATFORMS` the role has no Bash, so a lens brief that needs `git show` or `git log` cannot run there: the launcher marks that side `failed: true` with the reason `platform`, and the dispatcher falls back to the Task path (never an empty review). The probe covers repository-config-driven program starts as well as flags: textconv and external diff via `.gitattributes`, `core.pager`, `core.fsmonitor`, `-c` and `GIT_*` environment, `git grep --open-files-in-pager`, with `--no-ext-diff` and `--no-textconv` pinned where the probe needs them; the role header says that widening the allow list means re-probing. The effort for the role comes from #5942's mechanism. Load `.claude/skills/headless-worker-launch` first and follow it: probe what each allowed command can write or start, not only that denied commands are denied, and record the results in the module header with CLI version, platform and date.
2. A launcher CLI (proposed `plugin/bin/review-lens-workers.js --run <dir> --lenses-file <json>`): input = the same `{ lenses: [{ lens, brief, model, reviewers }] }` the workflow script takes; it launches one worker per side with the brief as the prompt and the lens's model, in parallel with a named concurrency bound and a named per-worker timeout (both constants in the module header, values chosen at build), `side` labelled exactly as `plugin/workflows/review-lens-fanout.js` labels it, and prints the workflow script's return shape so `settle-lens-replies` reads it unchanged. A worker that fails, times out or returns blank text is `text: null, failed: true` with a `reason` (`launch`, `auth`, `timeout`, `blank`, `platform`) on stderr and in the launcher's log, not in the reply shape; a model reply of "No findings." is a valid reply, never `blank`; one worker's failure never touches another's reply. The launcher's exit code is 0 when it printed the reply shape, and 2 on a malformed call.
3. Token accounting: every lens worker's usage is counted in the run's `timing.json` (`dispatches`), as #5597 did for workflow agents, so a worker path never looks cheaper than it is. The launcher is the writer; the usage source (the worker envelope or its transcript) and the entry fields, including first-turn tokens and a `kind: worker` tag, are chosen at build and documented in the module header.
4. A live smoke test (opt-in, like `tests/bin-lib/driver/worker.test.js`'s AC7): one Haiku lens worker on an archived lens brief and context bundle; quote its first-turn prompt tokens and total tokens. Target: total under 100k (the design's own ceiling for a Haiku lens; an overrun is reported in the PR, not a build failure). The fixture is a named archived brief with a large diff, and the opt-in switch is the same environment variable `worker.test.js` uses for AC7. The launcher rejects a lens `3f` entry before any worker starts: that side returns `failed: true` with `reason: excluded`, pinned by a unit test. The worker-path dispatcher (#6003) routes 3f to the Task path.

- [ ] The probe matrix covers the repository-config vectors named in Deliverable 1, each with a negative test, and the role's effort is set through #5942's mechanism and pinned by a test.
- [ ] Each allowed git command was probed for writes (including `--output=<path>`) and program starts under the generated settings, and the module header records the result, CLI version, platform and date.
- [ ] The launcher's output for a two-lens, four-worker fake runner is byte-equal in shape to what `settle-lens-replies` accepts; a fake worker that exits non-zero yields `failed: true` for that side only.
- [ ] Lens worker tokens appear in `timing.json` `dispatches` for a run that used the launcher.
- [ ] The live smoke result (first-turn and total tokens for one Haiku lens worker) is quoted in the PR.
- [ ] A lens worker runs with the reviewed worktree as its working directory, and the context bundle reaches it inlined in the prompt; the launcher writes nothing into the reviewed worktree. A test pins both.
- [ ] A worker whose envelope records a permission denial for a git command is `failed: true` with reason `denied`, even when its text is "No findings."; a fake-runner test pins it.
- [ ] The launcher's worker environment pins git configuration and `GIT_ATTR_SOURCE` as the built-in read-only command Decision states; a probe with a repository configured with an external diff and a textconv driver shows which program starts remain, and `roles.js`'s header records them as the accepted sandbox-contained residual risk.

## Gotchas

- #5942 (launch driver workers at their role's effort) edits `roles.js` and `worker.js` and has a pipeline run in flight; build after it merges and take its effort mechanism for the new role.
- Lens 3f's discrimination checks create a scratch checkout and run tests (`step3-lens-dispatch.md`, "Lens 3f scratch checkout"). A read-only role cannot do that. 3f stays off the worker path unless a probe shows a contained right; say which in the PR.
- Headless worker authentication on env-authenticated hosts is undecided (#5259); the launcher must report a launch failure as a failure, never as an empty review.
- A lens brief embeds untrusted diff text; the worker's rights, not the prompt, are what contain it. The `auth` flag here means the worker's launch credentials and rights: no credential beyond what `claude -p` needs reaches the generated settings, and no network is granted.
- The reply shape is a contract with `settle-lens-replies` (`review-coordination.js`) shared by the workflow script and this launcher: the build adds a test that runs both producers' output through it, so neither can drift alone.
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(auth): …`.

## Decision Rationale

- **Why reuse the driver's launcher.** Its rights were probed and recorded (`roles.js` header); a second launcher would need the same probes and would drift.
- **Why the workflow script's return shape.** One settle path (`settle-lens-replies`) for every dispatcher keeps pairing and logging in tested code.

**Decision (plan review Q1, working directory):** Reading A. The worker runs in the reviewed worktree, so relative paths, `git grep` and an unranged `git diff`/`git show` all see the reviewed branch. The launcher inlines the context bundle in the prompt rather than copying it into the worktree, so the reviewed tree is never written to.

**Decision (plan review Q2, admitted git forms):** Reading A. The launcher appends one fixed system-prompt note (`--append-system-prompt-file`) listing the exact admitted command forms and telling the worker to run them as written. Because a refused read could still end in "No findings.", a worker whose envelope records a git permission denial is `failed: true` with reason `denied` (added to Deliverable 2's reason list), so the dispatcher falls back instead of counting an empty review.

**Decision (plan review Q3, effort):** Reading A, keeping the criterion as written. The effort comes from `roleLaunch('lens-reviewer', policy)`, the role's own `DRIVER_ROLE_PROFILES` row, and a test pins that row. No per-lens effort helper.

**Decision (Task 2 probe, built-in read-only git commands):** Pin the git environment in the launcher, then accept whatever the sandbox still contains as a stated residual in the `roles.js` lens-reviewer header. The CLI's own read-only command table admits bare `git diff`, `git log -p` and `git show` with no allow rule, and they start the external diff, textconv or fsmonitor program the repository's config names. No deny rule is added for them, since it would also refuse the pinned forms. Instead the launcher's worker environment stops git reading system and global config and overrides the program-starting keys (for example `diff.external`, `core.attributesFile`, `core.fsmonitor`) through `GIT_CONFIG_COUNT` entries, and sets `GIT_ATTR_SOURCE`. A live probe against a repository configured with an external diff and a textconv driver then records which program starts remain (the last acceptance criterion). Those that remain are the accepted residual. Why the residual is acceptable: the programs come from the user's own git config, so the reviewed change can only choose among already-configured programs through its tracked `.gitattributes`; the Task 2 probe (CLI 2.1.325, git 2.56.0, macOS, 2026-11-23) showed each such program's write outside the working directory and its network reach refused by the sandbox; and that residual is narrower than the implementer role's, which already runs worker-written code under the same sandbox. Bash stays on the role on sandbox-probed platforms only, as Deliverable 1 states. Resume from the pushed Tasks 1-2 on branch `worktree-dispatch-record-6000` (`89f4b46be`), not from scratch.

**Decision (built-in read-only git commands, maintainer 2026-11-23, hub item 1119):** Sandbox plus pinned environment. Claude Code 2.1.325 runs bare `git diff`, `git log -p` and `git show` without an allow rule, and those can start external diff or textconv programs that the repository's git configuration names. (1) The launcher neutralises what the environment can before any worker starts: no system or global git config (`GIT_CONFIG_NOSYSTEM=1`, `GIT_CONFIG_GLOBAL` pointed at an empty file), `diff.external` cleared and textconv disabled through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`, and `GIT_ATTR_SOURCE` set to the empty tree. A probe pins each setting with a negative test. (2) Whatever program start the probe still shows is accepted as a stated residual risk, contained by the sandbox (no writes outside it, no network), and written into `roles.js`'s header with the CLI version, platform and date. A diff can name a driver in `.gitattributes` but cannot define what it runs, which only repository configuration can do.

## Plan Review Clarifications

- Settled by plan review after an answered round: "Task 3 says 'The run dir is never inside the reviewed worktree'. But `--run` must pass the shape-3 guard, which only accepts a directory strictly inside `<checkout>/.claude-tweaks/pipelines/`. So when the reviewed worktree is the main checkout, `worker-dispatches.jsonl` and its `.lock` land inside the reviewed tree." Chose Reading A, keeping the criterion "the launcher writes nothing into the reviewed worktree" as written: the CLI refuses (exit 2) a `--run` that lies inside `--cwd`, and the live smoke and the AC8 fixtures review a worktree separate from the checkout that anchors the run dir. Not taken: Reading B, excluding the gitignored `.claude-tweaks/pipelines/` subtree from "the reviewed tree".

## Build Alignment Notes

- Beneficial (build Common Step 4.5): the launcher checks that the installed git honours `GIT_ATTR_SOURCE` (`gitHonoursAttrSource` in `roles.js`, a functional probe, not a version check) before any worker starts; a git that ignores it fails every side with reason `platform`, so the tracked-`.gitattributes` closure never silently fails open on an older git.
- Beneficial (build Common Step 4.5): lens-reviewer workers launch with a pre-minted `--session-id`, so a worker that times out or fails before its result object still has its transcript found and its tokens counted in `timing.json` (Deliverable 3: a worker path never looks cheaper than it is).
- Beneficial (build Common Step 4.5): the `denied` check reads every command position of a denied Bash command (compound, env-prefixed, keyword- and wrapper-prefixed, `sh -c`), not only a command that starts with `git`, per AC9's "a permission denial for a git command".
