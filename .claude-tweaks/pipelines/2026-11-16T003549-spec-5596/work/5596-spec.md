# 5596: Probe what a plugin-shipped workflow can do, and record it

Surface: infra

**Related:** #5557, #4359
Risk-flags: auth
Risk-flags-unconfirmed: true

## Current State

Phase 6 of the process-efficiency design runs the review step's lens reviewers from a workflow script the plugin ships. That rests on how Claude Code's Workflow tool behaves, and part of that is not established. Nothing in this repository uses the tool yet: `plugin/` has no `workflows/` directory, and `plugin/hooks/hooks.json` has no matcher for it.

What is established, with its source:

| Fact | Source |
|---|---|
| A plugin ships workflow scripts as `.js` files in `workflows/` at its root; the name is `{plugin}:{meta.name}`; `plugin.json` takes an optional `workflows` field | Claude Code documentation (plugin components, manifest reference, workflows pages), read on 2026-11-16 |
| Two installed marketplace plugins do this: `claude-security` (`workflows/scan.js`, `meta.name` `scan`, allowed in its skill as `Workflow(claude-security:scan)`) and `code-modernization`, whose command calls `Workflow({ name: "code-modernization:modernize-harden-scan", args })` and falls back to `scriptPath: "${CLAUDE_PLUGIN_ROOT}/workflows/harden-scan.js"` when the name is not known | Their files on this machine, read on 2026-11-16 |
| A script is plain JavaScript beginning with `export const meta = {...}`; it has `agent()`, `parallel()`, `pipeline()`, `phase()`, `log()` and `args`; it cannot read files, start a process, read the clock or require a module | The tool's authoring reference, CLI 2.1.325 |
| Resume works in the same session only; leaving the session stops the run; there is no mid-run input | Documentation |
| A plain headless `claude -p` session lists the tool | Probed on 2026-11-15, CLI 2.1.325 |
| The plugin's PreToolUse hook fires for a tool call made by a workflow agent (a `Write` into the main checkout was denied) | Probed on 2026-11-15 |
| `agent(prompt, { model })` accepts `haiku`, `sonnet` and `opus`; each agent's `meta.json` records the alias | Two workflow runs of 2026-11-15 (5 and 24 agents), files read on 2026-11-16 |
| A run's files: `{session}/workflows/{runId}.json` (holds `args`, `result`, `agentCount`, `totalTokens`, `status`) and `{session}/subagents/workflows/{runId}/` (`journal.jsonl`, `agent-{id}.jsonl`, `agent-{id}.meta.json`) | The same two runs. The documentation does not state this layout |
| A Task-dispatched agent has no Workflow tool | Observed on 2026-11-16: the dispatched agent that wrote this record had none, CLI 2.1.325 |
| The pipeline driver's workers are launched with a fixed `--tools` list drawn from `Read`, `Write`, `Edit`, `Bash`, `Grep` and `Glob`, so they have no Workflow tool | `plugin/bin/lib/driver/roles.js:245` and `:449` |

What is not established: starting a plugin-shipped workflow by name from this plugin; whether a skill step that names the workflow is accepted as the opt-in the tool requires (the documentation names a typed request and `ultracode`, not a skill); any size limit on `args` or on the returned value; whether the call returns its result in the tool result or later, and what the documented 10-minute hold in a headless session does to a longer run; whether a workflow agent can use the Skill tool and MCP tools; whether `SubagentStop` fires for a workflow agent and with which `agent_type`; whether a cloud session or a scheduled Routine has the tool.

Design: `docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 6 and "Evidence: workflows".

## Deliverables

1. **Start by name (first, with a stop).** From a throwaway plugin directory holding `workflows/probe.js` (later deliverables add one skill and one `SubagentStop` hook to it), loaded with `--plugin-dir`, start the workflow as `{plugin}:{meta.name}` with an `args` object, and read back a value the script computed from `args`. Then start it through `scriptPath` under the plugin root. If neither form starts, the build stops with status BLOCKED. Decided 2026-11-16: a stop here writes no document and opens no PR. The build posts one comment on this record with both commands, both failures verbatim and the CLI version, and ends with status BLOCKED. This record then stays open, so #5599 stays blocked. Every acceptance criterion except AC2 applies only to a build that did not stop here.
2. **Who can start it.** One row per initiator, each with the command used: a top-level interactive session where the model reads a skill step that names the workflow; a plain headless `claude -p` session, with the allow rule or permission mode it needs; a Task-dispatched agent; a driver worker as `roles.js` launches it; a cloud session; a scheduled Routine. Decided 2026-11-16: every child session runs with this machine's user settings as they are, because the question is whether an ordinary session can start the workflow. Each row records the permission mode, and a start that needed an allow rule is `yes-with: {rule}`. The skill-step row is probed by a `claude -p` child whose prompt tells the model to use the probe plugin's one skill, whose single step names the workflow; the row is labelled a headless stand-in. A row for a person at a terminal is added only when the build session is interactive and has the tool itself; otherwise it reads `not probed: needs a person at a terminal`. The driver-worker row is a real launch: a child started with the arguments `plugin/bin/lib/driver/roles.js` builds for a role (line 449 at `026e203f3`: `-p --safe-mode --restricted --tools … --disable-slash-commands --strict-mcp-config`), answered by whether `Workflow` is in its init event's tool list. Reading the file is not a probe. One more row starts the workflow by name under `--restricted` alone and records whether the tool list or the start changes.
3. **Size and delivery.** An `args` object of 100,000 bytes reaches the script whole (the script returns its length). A returned value of 100,000 bytes: where the whole value is readable, and which field of the tool result names that place. Whether the tool result arrives when the run ends or earlier. A run longer than 10 minutes in a headless session: finished or cut. The long run is one `haiku` agent told to run the single command `sleep 660` and reply with one word. "Finished" is the workflow's returned value arriving in the child's stream; "cut" is the stream ending, or the tool result arriving, without it. The row quotes the last event either way. Deliverable 5's layout check runs before the delivery row, which reads the run file. "No field names the place" is a valid result.
4. **What an agent can do.** Inside `agent()`: a Skill tool call, an MCP tool call, a Bash call, a nested `Agent` call. Whether `SubagentStop` fires for the agent and the `agent_type` and transcript path its payload carries. Whether a reply with no schema comes back as the agent's final text, byte for byte. The Skill call targets the probe plugin's own skill. The MCP call targets a tool of whichever MCP server the child's init event lists; with none listed the row reads `not probed: no MCP server in the child session`. The `SubagentStop` row uses a hook registered in the probe plugin's own `hooks/hooks.json` that appends its payload to a file in the scratch directory. For the byte-for-byte row the agent is told to reply with a fixed 2,000-character string the script also holds, and the script returns whether the two are strictly equal. Two more rows: the agent's working directory (`pwd`) against the session's, and the permission mode its tool calls run under.
5. **Where the run's files are.** Confirm or correct the layout in the table above on the CLI version the probe runs on, and state whether `agent-{id}.jsonl` carries `message.usage` rows.
6. **The record of it.** `docs/reference/workflow-tool-probe.md`: one row per probe with the initiator, the exact command, the CLI version, the date, the observed output verbatim, and what it means for the records that depend on it (#5597, #5599). A probe that could not be run says `not probed: {reason}`.
7. **Teardown.** The throwaway plugin directory, any scratch working directory and any Routine created for the probe are deleted whether the probes pass or fail. Nothing under `plugin/` is in the PR's diff.

## Technical Approach

Run the probes that need the tool from child sessions the build starts itself: `claude -p --plugin-dir {probe plugin} --model haiku --output-format stream-json --verbose` in an empty scratch working directory, with a prompt that tells the model to call the workflow and print the result. This is how the 2026-11-15 probes were run. The stream's init event lists the session's tools, which answers the "has the tool" rows without a model turn deciding anything. A build session that has the tool itself may run the interactive row directly.

The probe script is a few lines: validate `args`, start one or two agents with fixed one-line prompts, return what they said plus `JSON.stringify(args).length`. Keep every probe to the smallest model that answers it.

For the Task-dispatched row, the probing session dispatches one agent whose prompt asks only for its tool list.

For the scheduled Routine row, create one one-off Routine whose prompt asks for the session's tool list, read its result, and delete it. If the build session cannot create a Routine, the row is `not probed: {reason}`. That is accepted because #5599 falls back to the present dispatch wherever the tool is absent (its Deliverable 4), so a wrong guess there costs nothing. The cloud session row is the same question asked in a cloud session, and neither row needs the probe plugin.

Use the installed CLI. If a result is needed for a newer release, run that exact version with `npx -y @anthropic-ai/claude-code@{version}` from the scratch directory, never by upgrading the shared install.

## Gotchas

- This record is the maintainer's approval to start the probe workflows it describes, in the child sessions it describes. It approves nothing else.
- The probe plugin lives in the session's scratch directory, never under `plugin/`: a file there would ship.
- A child `claude -p` session inherits this machine's user settings, including a broad Bash allow rule. Give each child an empty scratch working directory and a prompt that asks for nothing but the probe.
- The SessionStart hook of this plugin creates `.claude-tweaks/` in a child session's working directory when the child loads it. The children load the user's installed plugins, so the directory appears; teardown deletes the scratch working directory whole. Do not narrow a child with `--setting-sources project`: `.claude/skills/headless-worker-launch` records that it let a project allow rule widen rights.
- The file layout under `subagents/workflows/` is undocumented and may change between CLI versions. State the version beside it.
- `ultracode` does not fire from `claude -p`. No probe may depend on it.
- Read `.claude/skills/headless-worker-launch` for how this repository probes a launch flag and records the result, and `plugin/skills/specify/empirical-premise-check-deliverables.md` for the probe-target, teardown and verbatim-capture rules this record follows.
- #5557 starts workflows for its replay and is in progress. It does not depend on this record; if it has recorded a result this record needs, cite it.
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(auth): …`. The flag fired on this record's text about permission modes and allow rules. The proof must show that the probes change no permission: no settings file is edited, no allow rule is added, and every child session and any Routine is gone after teardown.
