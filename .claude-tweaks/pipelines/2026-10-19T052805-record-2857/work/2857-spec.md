# 2857: Make harness-health Premise-check paths portable across machines

Surface: backend

**Related:** #2601

## Current State

`plugin/bin/harness-health.js validate-findings` composes a `Premise-check:` command for each mechanically re-checkable patch finding, through `buildPremiseCheck` in `plugin/bin/lib/harness-health/issue-payload.js` (#2621). It also self-checks that command at filing time (#2633, `premiseReadsUnresolved` in `plugin/bin/lib/health-core/premise-self-check.js`, run with `cwd: root`).

`cmdValidateFindings` resolves `--root` to an absolute path. `resolveTargetPath` (`plugin/bin/lib/harness-health/scope.js`) returns the scanned file's absolute path, and `buildPremiseCheck` puts that path into the command verbatim. So every filed line hard-codes the filing machine's absolute path, for example `! grep -qF -- '…' '/home/user/repo/.claude/skills/auth.md'`.

`plugin/bin/materialize.js`'s `runPremiseCheckDefault` runs the command through `runPremiseCommand(command, { timeoutMs })` and passes no `cwd`, despite its own comment ("run from the checkout root") and `plugin/skills/flow/materialize.md`'s "runs that command from the checkout root". It actually runs in materialize's process cwd.

For a finding filed by a scheduled Routine (a cloud sandbox path) or from another machine, the absolute path doesn't exist in the building checkout. Both polarities then exit 0: the additive `! grep …`, and the removal `! test -r … || …`. That means "unresolved": the check fails safe, but auto-close is silently inert for exactly the Routine-filed findings it exists for. `docs/journeys/harness-health-premise-check.md` records this as a known limitation tracked here, and its step-3 red flag currently *requires* the kept path to be absolute.

Memory-target findings (`--memory-dir`, outside the repo) have no repo-relative form.

## Deliverables

1. **Path form decided (approved in brainstorming, 2026-10-15).** A target under the sweep root is composed with its repo-relative POSIX path. A target outside the root (memory files under `--memory-dir`, or any other path not under `root`) keeps its absolute path. Same-machine materialize still auto-closes it, and elsewhere it fails safe exactly as today.
2. `buildPremiseCheck(finding, targetPath, root)` composes with that form. `toIssuePayload` threads `root` through from `cmdValidateFindings` (via `dedupAndDispatch`'s existing `toIssuePayload` hook), and an absent `root` keeps today's absolute behavior.
3. `materialize.js`'s `runPremiseCheckDefault` runs the command with `cwd` = the checkout root (`git rev-parse --show-toplevel` resolved from materialize's own working directory). When the root can't be resolved, `computePremise` degrades to `null` ("no premise check"), never a crash, matching its existing throw-to-null posture.
4. `docs/journeys/harness-health-premise-check.md`: the step-3 red flag ("a kept line whose target path isn't absolute") is reworded to the new contract (in-repo targets relative, out-of-repo absolute). The step-5 known-limitation paragraph tracking #2857 is replaced by the new behavior.
5. Tests:
   - `tests/bin-lib/harness-health/issue-payload.test.js`: an in-repo target gives a relative path, an out-of-repo target stays absolute, and both polarities (additive and removal) are covered.
   - `tests/materialize-premise-check.test.js`: compose a finding's command under temp root A, place the target file under temp root B, run materialize's premise runner from B (cwd elsewhere inside B). It reads "unresolved" (exit 0) while the anchor is absent in B, and "resolved" (non-zero) once present.

## Acceptance Criteria

- [ ] When the checkout root can't be resolved, `premise` is `null` and materialize does not throw.

## Release Note

Harness-health premise checks filed by scheduled runs now detect already-fixed findings on any machine.

## Technical Approach

Compose-side: in `buildPremiseCheck`, when `root` is given and `path.relative(root, targetPath)` neither starts with `..` nor is absolute, use that relative path (normalized to `/` separators) in place of `targetPath`. Otherwise keep `targetPath` unchanged. Both `shQuote(targetPath)` sites (the `test -r` guard and the `grep`) use the same chosen path.

Run-side: give `runPremiseCheckDefault` the checkout root as `cwd`. Resolve it once per materialize run through the existing git helper materialize already uses, or a plain `git rev-parse --show-toplevel`, inject it via `deps` so tests can supply a temp root, and pass it to `runPremiseCommand`'s existing `cwd` option. That option is already threaded to `execFileSync`, and `premise-self-check.js`'s `defaultRunner` already accepts it.

### Key Files

- `plugin/bin/lib/harness-health/issue-payload.js` — `buildPremiseCheck` gains a `root` parameter and composes a repo-relative path for in-root targets; `toIssuePayload` threads `root`
- `plugin/bin/harness-health.js` — `cmdValidateFindings` passes `root` to `toIssuePayload`
- `plugin/bin/materialize.js` — `runPremiseCheckDefault` runs with `cwd` = the checkout root; the root is resolved once and injectable via `deps`
- `docs/journeys/harness-health-premise-check.md` — step-3 red flag and step-5 known-limitation paragraph updated to the new contract
- `tests/bin-lib/harness-health/issue-payload.test.js` — relative/absolute composition cases
- `tests/materialize-premise-check.test.js` — cross-root file-then-materialize case

## Gotchas

- Records filed before this change keep their absolute paths. They still fail safe ("unresolved") off-machine and still work on the filing machine, so no migration is needed.
- `wrap-up/claude-md-curation.md`'s over-budget composer (`test $(wc -l < {path}) -gt {budget}`) already emits repo-relative paths such as `CLAUDE.md`. Today it only works when materialize happens to run from the repo root. The `cwd` fix in Deliverable 3 makes it correct regardless, which is a side benefit, not a scope expansion.
- `materialize.js`'s author-association gate is unchanged: an untrusted author still means no command runs, whatever the path form.
- A relative path must never be computed against a `root` that is itself relative. `cmdValidateFindings` already resolves `root` absolute (#2633 review follow-up), so keep that ordering.

## Current State

`plugin/bin/harness-health.js validate-findings` composes a `Premise-check:` command for each patch finding (#2621) and self-checks it at filing time (#2633).

The path inside that command is the target file's path under `--root`. `harness-health/SKILL.md` Step 6 passes `--root "${ROOT:-$PWD}"`, and since this run `cmdValidateFindings` resolves `--root` to an absolute path. So every filed line bakes in the **filing machine's absolute path**, for example `! grep -qF -- '…' '/home/user/repo/.claude/skills/auth.md'`.

`plugin/bin/materialize.js` runs that command later with `execFileSync('/bin/sh', ['-c', command])`, with no `cwd` of its own, from whichever checkout builds the record. For a finding filed by a scheduled Routine (a cloud sandbox path) or on a different machine, the file doesn't exist at that absolute path:

- the additive form `! grep …` exits 0, which reads as "unresolved";
- the removal form `! test -r … || …` also exits 0.

The check fails safe and never closes a record wrongly. But auto-close is silently inert for exactly the Routine-filed findings it exists for.

## Deliverables

1. Decide the portable path form: repo-relative to the checkout root, or another anchor.
2. Make `validate-findings` compose `Premise-check:` lines with that form.
3. Pin `materialize.js`'s run contract to match, so the command runs with `cwd` = the checkout root.
4. Add a test that files a finding under one root and materializes it under a different root.

## Open Question

Should a filed `Premise-check:` path be repo-relative, with materialize running it from the checkout root, or is there a reason to keep absolute paths (for example, a finding against a file outside the repo, such as a `--memory-dir` memory file)? Memory-target findings have no repo-relative form, so the answer may need to be per asset type.

## Architecture Deviations (build, Common Step 4.5)

- **Beneficial — relativization anchor is the git top-level of `--root`, not `--root` itself.** Spec Deliverable 1 said "a target under the sweep root is composed with its repo-relative POSIX path". Built: `cmdValidateFindings` resolves `premiseRoot` (the git top-level of the absolute `--root`, spelled in `--root`'s own path form) and passes it to `toIssuePayload` as a new `premiseRoot` option; `buildPremiseCheck` relativizes against it and the filing-time self-check runs from it. A non-git `--root` passes none (absolute paths, fail-safe). Why: `materialize.js` runs from `git rev-parse --show-toplevel`, so a subdirectory `--root` composed paths that materialize resolved against the wrong file and could falsely read "resolved" (whole-branch review Important #1, fixed in 5daaeac3c). `repoRoot` still feeds `### Key Files` only.
- **Beneficial — `plugin/bin/harness-health.js` changed for the anchor, not for root threading.** `cmdValidateFindings` already passed `repoRoot: root` (#2975); the change adds `resolvePremiseRoot` and the `premiseRoot` option instead.
