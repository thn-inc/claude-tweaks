# 4794: Host-qualify the origin-derived repo slug so a GHE origin's reconcile and claim-store gh calls reach the origin's host

Origin: ledger resolve gate (wrap-up of #4505)

Defer-reason: genuinely-larger

## Current State

#4505 put every `gh` spawn in `plugin/bin` behind `ghOptions` (`plugin/bin/lib/repo-resolve.js`), which injects `GH_HOST` for a GitHub Enterprise origin. Decision Q2 (Reading A) left one class unchanged: a bare `--repo owner/repo` slug derived from origin (not typed by the user) means github.com, because the slug carries no host.

`repoSlugOf` (`plugin/bin/lib/hooks/git-exec.js:207`) drops the host. Its callers in `plugin/bin/lib/reconcile/` (`archive-merged.js`, `release-merged.js`, `reap-merged.js`, `post-merge.js`, `pr-state.js`) pass that bare slug to `gh --repo` and to `repos/${slug}/…` API paths, and `plugin/bin/lib/issues/claim-store.js`'s `openPrListArgs` (`--repo ${owner}/${repo}`) does the same. On a GHE origin those calls therefore still go to github.com. The slug also feeds slug comparisons across the reconcile family, so host-qualifying it touches unrelated systems (ledger row 2 of `docs/plans/2026-10-31-gh-host-seam-ledger.md`).

## Deliverables

- [ ] Make the origin-derived slug carry its host off github.com (`repoSlug`-style `host/owner/repo`), or add a host-aware sibling of `repoSlugOf`, and move the reconcile callers and `claim-store.js` onto it.

- [ ] Keep every slug comparison and every `repos/…` API path consistent with the new spelling, so a github.com origin stays byte-identical.

- [ ] Extend `tests/gh-host-seam-behavior.test.js` with a GHE-origin case per migrated caller.

## Acceptance Criteria

- [ ] With a `*.ghe.com` origin and no `GH_HOST` exported, a reconcile pass and `stale-claim-pr.js` send every `gh` call to the origin's host (asserted through a recording runner, not by reading the source).

- [ ] With a github.com origin, the argv and env of every migrated call are byte-identical to today's.

- [ ] `node --test tests/gh-host-seam-behavior.test.js tests/gh-host-seam-conformance.test.js` passes.

## Release Note

Reconcile and claim-store `gh` calls now reach the right host when your origin is a GitHub Enterprise server.

## Decisions

Answers the plan-review question (comment 6563106486).

- **Decision: Reading B, with the divergence fixed in this record.** The origin-derived slug is host-qualified only for hosts the #4505 gh seam already treats as GitHub Enterprise (`resolveGhHost(cwd)` in `plugin/bin/lib/repo-resolve.js`: `*.ghe.com`, a gh `hosts.yml` key, or an enterprise token on a non-SSH remote). github.com, SSH-alias origins (e.g. `git@github-work:acme/widgets.git`) and unknown hosts stay bare and byte-identical to today.
- **Also in scope (not a follow-up):** align `plugin/bin/lib/reconcile/post-merge.js` and `plugin/bin/lib/hooks/teardown-run.js` (today: the raw remote host via `repoSpecOf` in `plugin/bin/lib/hooks/git-exec.js`) to the same seam rule, so one reconcile pass applies one host rule. This also stops those two paths sending gh calls to an SSH alias name gh cannot reach. Add a test covering an SSH-alias origin on each aligned path.
- **Decided (round 2): Reading B** (answers comment 6577849746). An explicit, user-typed host-qualified `--repo` on `stale-claim-pr.js` names its own host and is trusted, following #4505 Decision Q2 (an explicit `--repo` names its own host and the seam steps back). This applies to any host, including one the seam does not know; a wrong host then fails loudly at `gh`. Record this in the spec's Decisions.
- **The whole host rule, so the build doesn't have to ask again:** a host-qualified `--repo`, whether typed by the user or derived from origin under the round-1 seam rule, names the host every `gh` call and every PR-url match uses. When `GH_HOST` is exported on a GHE origin, PR-url matching uses that `GH_HOST` value, not github.com. Every host comparison (PR-url matching, tombstone URL checks including the MCP path in `_shared/issue-claims.md`) is case-insensitive and ignores a trailing dot. A bare `--repo owner/repo` typed by the user still means github.com.
- **Decided (round 3), Q1: Reading B** (answers comment 6599272346). ADR 0030's origin-host gate wins over this spec's earlier "post-merge and teardown stay bare" text. On an SSH-alias or unknown-host origin, post-merge and teardown keep refusing. The `repoSlugOf` paths are also routed through `gateOriginRepo`, so every path in one pass applies the same rule (ADR 0030's) and "one host rule" holds. Do not revert or weaken #4933's gate. The SSH-alias cases become tests that pin the refusal.
- **Decided (round 3), Q2: Reading B.** Rewrite the agent-composed `stale-claim-pr.js` invocations in the tidy prose and the MCP-path prose (`_shared/issue-claims.md`) so the host comes from origin through the seam. Drop `--repo` where the CLI derives the repo from origin; otherwise pass the host-qualified slug. Update the tidy conformance pin to match. A bare `--repo` typed by a user still means github.com (round 2); no agent-composed call relies on that default.
- **Minor rulings, so the build doesn't have to ask again:** an exported but empty `GH_HOST` is treated as unset on every path (Task 1 and Task 5 agree). Task 1 carries `Review risk: high`. The spec's enterprise-token clause follows `resolveGhHost`, which is the one place that resolves the host.
- **Decided (round 4), Q1: Reading B** (answers comment 6610295573). Every path the #4933 gate blocks (release, post-merge, archive, reap, pr-state, stale-claim-pr, and any other gated caller) reports the reason `unknown-host` with the gate's refusal text. None reports `no-repo-slug` or `network-failure` for a gated origin. Fix the alias advice once, in the shared gate refusal text, in this record: for an SSH alias (e.g. `git@github-work:...`) it tells the user to set `GH_HOST` to the real host the alias maps to (e.g. `GH_HOST=github.com`), never to the alias name. Pin the corrected text with a test.
- **Decided (round 4), Q2: one host for both.** `stale-claim-pr.js` resolves the host once and uses that same value both to list PRs and to match PR links. Precedence: a host-qualified `--repo` first, then an exported non-empty `GH_HOST`, then github.com. This amends round 2: a bare `--repo` means github.com only when `GH_HOST` is unset or empty, which matches how `gh -R` itself behaves.
- **Whole family, so the build doesn't have to ask again:** any command that both calls `gh` and compares a host (listing vs matching, tombstone URL checks, the MCP path) takes both from one resolved host value, never from two separately derived ones. If the build finds another split site, it applies this rule there without asking.
- **Plan markers:** Tasks 4 and 8 carry `Review risk: high`; the build applies the reviewer's 3 medium plan defects.
- **Decided (round 5), Q1: AC2 holds** (answers comment 6623713599; decided by the dispatching session under the user's standing instruction to finish this drain without further questions). On a github.com origin, every argv and env stays byte-identical to today, whether or not `GH_HOST` is exported: no host qualification is added (`--repo acme/widgets` stays bare). `gh`'s own `GH_HOST` handling already sends a bare `-R` to that host, so the host reached is unchanged, and github.com users see no behaviour change. The round-4 "one host for both" rule is satisfied because the PR-url matching side resolves the same host (`GH_HOST` when exported and non-empty, else github.com).
- **Decided (round 5), Q2: yes, ghOptions too.** "An exported but empty `GH_HOST` is treated as unset on every path" includes `ghOptions` (#4505). Fix it there so one reconcile pass never splits across hosts (release on github.com and residue escalation on GHE).
- **Review defects, in scope, all fixed in this record:**
  - (high) Origin parsing normalizes before any host comparison: credentials (`user:token@`), an explicit port, and the `ssh://` scheme form of a `*.ghe.com` origin all reduce to the same host, so one pass never splits.
  - (low) The sibling-sessions claim read is bound to the hook's working directory.
  - (low) The agent-composed `stale-claim-pr.js` re-run, when origin doesn't parse and `GH_HOST` is unset, falls back to github.com explicitly, per the round-4 precedence. Pin it with a test.
- **No claim-targets exception:** per round 3 Q1, every path in a pass applies ADR 0030's rule. claim-targets on an SSH-alias or unknown origin reports `unknown-host` with the corrected refusal text, like the other gated paths, rather than silently listing on github.com.
- **Decided (round 6), Q1: Reading A** (answers comment 6624536575; decided by the dispatching session under the user's standing instruction to finish this drain without further questions). The gate also refuses on the normalized host. A credentialed, ported or `ssh://` origin on an unknown host or an SSH alias reports `unknown-host`, exactly as its plain spelling does. Task 1 shows, with fixtures, that no cloud-sandbox proxy-remote shape parses under the normalized read. Any shape that does parse is carved out by name and pinned with a test.
- **Decided (round 6), Q2: Reading B.** On the MCP `--listing` leg only, pass `--repo "github.com/{owner}/{repo}"` (the MCP's host), so listing and matching share one host. Pin it in Task 14's conformance tests.
- **Decided (round 6), Q3: Reading B.** When a non-empty `GH_HOST` names a host other than github.com, `pr-state-batch.js` does not run, and the per-item calls answer. The argv of every call that still runs is unchanged. Widen the split-site sweep to plain `'github.com'` literals and fix any other site it finds by the same rule.
- **Decided (round 6), Q4: Reading A.** No scp-style refusal ever names its own host as a `GH_HOST` value. Every scp host gets the alias advice plus the generic "if it is GitHub Enterprise, export `GH_HOST` as that server's host". HTTPS refusals stay byte-identical.
- **Blanket rule, so this family needs no further rounds:** (1) whether an origin is refused depends only on its normalized host, never on how its URL is spelled; (2) every `gh` call and host comparison within one command or one reconcile pass uses one resolved host; (3) no refusal text ever tells the user to set `GH_HOST` to an alias or an unverified host name. If the build finds another site or case these cover, it applies the rule there without asking.
- **Plan defect, in scope:** add Task 7's GHE-origin behaviour cases (AC1.1 and AC2.1) for `prune-remote` and `archive-branches` in `tests/gh-host-seam-behavior.test.js`, and add Task 7 to Deliverable 3's coverage row.
