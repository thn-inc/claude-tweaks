# 5153: pr-first-merge Step 2.5: checks are read right after gh pr ready, so a project whose CI skips draft PRs is read green and merged unverified

Surface: infra

## Current State

Verified against `origin/main` at `c1fa86602` on 2026-11-10:

- **No wait between undraft and the first checks read.** In `plugin/skills/_shared/pr-first-merge.md`, Step 2 runs `gh pr ready` (around line 97). Step 2.5's first checks read follows (`gh pr view … --json state,mergeStateStatus,mergeable,headRefOid,statusCheckRollup` around :154, then `gh run list --commit {headRefOid} … --json name,workflowName,status,conclusion,url` around :160). In between there is only a policy read (`resolve-policy.js … merge-verification`) and a scratch-path resolve. Nothing waits for the workflow run that the `ready_for_review` event starts.
- **Draft-time results classify green.** `plugin/bin/lib/pr-checks/classify.js`'s `classifyRollup` returns green when every rollup entry is `SUCCESS`/`NEUTRAL`/`SKIPPED` and every head run is completed. `tests/bin-lib/pr-checks/classify.test.js:65` pins "all SUCCESS/NEUTRAL/SKIPPED at HEAD is green", and the Step 2.5 prose twin says the same. Nothing in the classifier, `bin/pr-checks.js`, or the Step 2.5 prose compares a run's creation time with anything. The head-runs read fetches no time or event fields.
- **The re-read before merging cannot see the gap.** The `wait` row compares only `headRefOid` and `state`, and `gh pr ready` changes neither. The bounded watch's `RC=0` branch re-reads head runs by sha and status only.
- **Pending is the only thing that saves it.** `gh pr checks` exits 0 on a rollup of only skipped and successful entries. The bounded watch maps exit 8 ("no checks reported") to pending and parks after its fixed 15-minute deadline (`DEADLINE=$(( $(date +%s) + 900 ))`). A `StatusContext` in state `PENDING` normalizes to pending (`classify.js`'s `normalizeEntry`), so a deliberately pending commit status does hold the gate.
- **Live evidence from the reporting project** (a private repository): a `gh pr checks` call made right after `gh pr ready` listed only the draft-time skipped jobs. The new run had not registered, and a commit status deliberately left pending was the only thing keeping the exit code at 8. Appendix capture (e) in `pr-first-merge-appendix.md` records the same not-yet-registered shape right after a push. #3405's head-runs read covers the case where `gh run list` already shows the run, but not the window before GitHub creates it.
- **Default trigger types are worse.** A repository whose `pull_request` workflow uses the default trigger types (`opened, synchronize, reopened`, no `ready_for_review`) but skips drafts with a job-level `if: github.event.pull_request.draft == false` gets **no run at all** on undraft. Its draft-time SKIPPED results stay the final state for that head, and the gate reads them as green permanently.
- **Nothing reads trigger types.** `plugin/bin/lib/merge-verification.js`'s `workflowHasPullRequestTrigger` only detects that a `pull_request`/`pull_request_target` trigger is present. It reads neither `types:` nor any draft condition, and nothing in `plugin/` or `tests/` mentions `ready_for_review`.
- **The dispatch close-out path is worse still.** `plugin/skills/dispatch/close-out.md` step 1 reads CI before step 3 undrafts the PR. Step 5 then runs `pr-first-merge.md`'s Step 3 directly, with no Step 2.5. So the CI read predates the ready event entirely.
- **`git-discipline.md` justifies per-phase pushes on API budget alone** (around line 86: "measured at ≥50× headroom against the GitHub API budget … per-phase cadence is free regardless of phase count"). Under pr-first, every phase push to the draft PR runs the project's `pull_request` CI. The reporting project measured 176 of 312 pull-request CI runs in 30 days on superseded commits, billing 3,120 minutes (35% of its Actions usage). That is why projects reach for a draft skip.
- **The `ci` verification source and a draft skip collide.** `plugin/bin/lib/verify/ci-source.js` (#4347) picks the open PR whose head matches. There is no draft check, so in practice it reads draft-PR CI. A job skipped by a draft condition completes with conclusion `skipped`, which falls back to a local run (`ci-job-skipped`, documented in `plugin/skills/test/ci-source.md`). A workflow gated off entirely, with no run, stalls verify for the full `waitSeconds` (default 900) before `no-ci-run-within-wait`.
- **This repository is not exposed.** Its own `.github/workflows/test.yml` uses bare `pull_request:` with no draft skip.

## Deliverables

1. **Ready-run requirement in the classifier.** `classifyRollup` accepts two optional inputs:
   - `readySince`: the `createdAt` of the PR's latest `ReadyForReviewEvent`.
   - `readyWorkflows`: the PR-triggered workflows that declare `ready_for_review` in their `types`.

   Head runs carry `createdAt`, `event` and their workflow identity. When both inputs are set, each workflow in `readyWorkflows` must have a head run with a `pull_request`/`pull_request_target` event created at or after `readySince`. Until one exists the verdict is **pending**, with the missing workflows named (`awaitingReadyRun`). Red still wins over pending. Both inputs absent means today's behaviour, byte for byte.
2. **Draft skip with no ready trigger.** A PR workflow whose text gates jobs on `github.event.pull_request.draft` but whose trigger types do not include `ready_for_review` (including default types) never runs again after undraft. The gate refuses to classify that head green:
   - It parks with reason `draft-skip-without-ready-trigger`, a new Red-path reason, naming the workflow file and the one-line fix (add `ready_for_review` to `types`).
   - Under an explicit `off` it is logged, not acted on, matching how an explicit `off` treats a red read today.
3. **Workflow reader.** `merge-verification.js` gains a reader that returns, per workflow file:
   - whether it has a PR trigger;
   - its declared `types` for `pull_request`/`pull_request_target` (flow `[a, b]` and block-list forms);
   - whether it references `github.event.pull_request.draft`;
   - a distinct `unparsed` signal when a `types:` value is present but unreadable.

   `unparsed` resolves conservatively: the workflow is treated as requiring a ready run, and the requirement is named in the park reason if it is never met. It is never silently read as "no requirement".
4. **Merge gate prose.** `pr-first-merge.md` Step 2.5 is updated in three places:
   - Its reads add the timeline read (`ReadyForReviewEvent` `createdAt`, last one) and `createdAt,event` plus workflow identity on the head-runs read.
   - Its classification adds the ready-run rule and the `draft-skip-without-ready-trigger` park.
   - The bounded watch's `RC=0` branch applies the same rule, so `gh pr checks` exiting 0 on draft-time results resumes the watch rather than taking the green path.

   The fixed 15-minute watch is unchanged.
5. **Close-out ordering.** `dispatch/close-out.md` re-reads CI after its step 3 undraft and before the confirmation gate, with the same ready-run rule. A pending result stops the candidate, as step 1's existing pending rule already does.
6. **"CI skips drafts" convention.** A new shipped reference, `plugin/skills/_shared/ci-skips-drafts.md`, documents:
   - **Workflow shape:** `types: [opened, synchronize, reopened, ready_for_review]` plus a job-level `if: github.event.pull_request.draft == false`.
   - **Pending-status pattern:** the draft-time run sets a commit status to `pending`, and the ready-time run flips it to `success` as its first step. This is defence in depth for readers other than this gate, such as `_shared/github-pr-scan.md`'s `NON_BLOCKING` set, and for adopters on older plugin versions.
   - **Path filters:** a workflow-level `paths:` filter leaves a docs-only PR with no checks reported when no other workflow reports on that head, which the bounded watch reads as pending and parks after 15 minutes. When another workflow does report (for example the generated tracking workflow's `label-fix-branch`), the rollup is non-empty and the filtered-out CI simply never appears. Use job-level conditions behind a small always-run job instead, so the CI workflow always reports.
   - **Coexistence with the `ci` verification source:** see Technical Approach for the ruling.
   - **Why projects reach for a draft skip:** the Actions-minute cost of per-phase pushes.
7. **`git-discipline.md` rationale.** The per-phase push rationale counts Actions minutes alongside the API budget. Each push to a draft PR runs the project's PR CI unless the project follows the draft-skip convention. The convention is the mitigation; cadence stays per-phase for durability and visibility.
8. **`ci-source.md` coexistence ruling.** `plugin/skills/test/ci-source.md` states the same ruling and links the convention.

## Release Note

Make the pr-first merge gate wait for the CI run that marking a PR ready starts, and refuse to merge a PR whose CI skips drafts but never runs on ready. Document a supported "CI skips draft PRs" setup.

## Technical Approach

**Ready timestamp.** Read it from the PR timeline, not from a clock the session took:

```
gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){timelineItems(itemTypes:[READY_FOR_REVIEW_EVENT],last:1){nodes{...on ReadyForReviewEvent{createdAt}}}}}}' …
```

It is durable, server-clocked like run `createdAt`, survives a re-entered gate, and serves the close-out path that never ran Step 2 in the same session. If there is no such event, the PR was never a draft, so the requirement does not apply. A failed read is `state-read-failed`, never "no requirement".

**Workflow identity.** Match head runs to workflows by the workflow file path, not the display name. A `name:` can be missing or duplicated. The REST runs listing (`repos/{o}/{r}/actions/runs?head_sha=…`) carries `path`. If the plan keeps `gh run list`, it must prove a name-to-file mapping that is unambiguous for the fixture set.

**Where the workflow files come from.** Read them from the PR head checkout, the run's worktree. `pull_request` events run the head's workflow definitions.

**Coexistence ruling for the `ci` source and draft skips** (stated in the convention and `ci-source.md`). A project picks one of two shapes:
- **CI on drafts plus a `ci` declaration.** The pipeline's full-suite verdicts come from draft-PR CI, there are no local full-suite runs, and every phase push costs Actions minutes.
- **CI skips drafts and no `ci` declaration.** Verification runs locally during the pipeline, and CI runs once at ready, which the gate now waits for.

Declaring both is a misconfiguration. With a job-level skip it degrades harmlessly: every verify falls back on `ci-job-skipped` after one poll. With a workflow-level gate it costs a `waitSeconds` stall per verify. Detecting the conflict automatically belongs to #5154's init CI-workflow review, not to this record.

Keep `bin/pr-checks.js`'s read in step with the classifier's new inputs so `/claude-tweaks:test`'s gate and the merge gate agree (`tests/pr-check-gate-conformance.test.js` pins the twin).

## Gotchas

- Do not change the fixed 15-minute bounded watch. A CI run longer than the watch still parks with `checks-pending-timeout`, as today. Whether the watch should change is a separate question, and #5154's CI-duration recording is the evidence for it.
- A repository that declares `ready_for_review` without skipping drafts pays one extra wait per merge, for a second run on the same sha. That is the correct trade (the gate cannot know the second run is redundant), and the convention says to declare `ready_for_review` only alongside a draft skip.
- Detecting a draft condition from workflow text is a heuristic, and a reusable workflow (`uses:`) can hide the condition. A miss leaves today's behaviour; a false hit parks with a named reason a human can override. Fail closed, never silently green (parse-signal discipline).
- `_shared/github-pr-scan.md`'s `NON_BLOCKING = {SUCCESS, SKIPPED, NEUTRAL}` and `/tidy`'s Arm-ready-PR reuse are deliberately out of scope. They classify ready PRs the plugin did not undraft. The pending-status pattern in the convention covers them.
- The Red path's re-draft (`gh pr ready --undo`) followed by a later re-ready produces a newer `ReadyForReviewEvent`. Always take the last one.
- Neighbouring records:
  - #5106 changes the same Step 2.5 read (compare the recorded head to the branch tip first).
  - #3467 changes the same classifier (cancelled or `action_required` read as green).
  - #4467 covers `--auto` merging immediately on repositories without required checks.

  Rebase onto whichever lands first. None of them blocks this one.

## Original request

pr-first-merge Step 2.5: checks are read right after gh pr ready, so a project whose CI skips draft PRs is read green and merged unverified

**Summary:** Under `pr-first` every phase exit pushes to a draft PR, so a project's `pull_request` CI runs in full on each of the six or more pushes a run makes. The project-side fix is to skip CI while the PR is a draft and run it on `ready_for_review`, but the merge procedure cannot be used safely with that shape: Step 2 runs `gh pr ready` and Step 2.5 reads the check rollup and the head runs with no wait for the run the ready event starts.

**Kind:** Defect

**Affected component:** `_shared/pr-first-merge.md` (Step 2 to Step 2.5), with `_shared/git-discipline.md`'s per-phase push rationale

**Repro steps:**
1. Give a project a CI workflow with `on: pull_request: types: [opened, synchronize, reopened, ready_for_review]` whose jobs carry `if: github.event.pull_request.draft == false`.
2. Run a `pr-first` pipeline to the merge step. The head commit's rollup now holds only draft-time results: the CI jobs as `SKIPPED`, plus `label-fix-branch` / `cleanup-fix-labels` from the generated tracking workflow.
3. Step 2 undrafts the PR. Step 2.5 then reads `gh pr view --json … statusCheckRollup` and `gh run list --commit {headRefOid}` after only a policy read and a scratch-path resolve.

**Expected vs. actual:**
Expected: the gate waits for the head run that `ready_for_review` triggers before it classifies the PR.
Actual: every rollup entry is `SUCCESS`/`NEUTRAL`/`SKIPPED` and every listed head run is completed, so the PR classifies green; under `wait` it merges immediately, and under `merge-when-green` on a repository without required checks `--auto` merges immediately too. The re-read before merging compares only `headRefOid` and `state`, neither of which `gh pr ready` changes. This is derived from the procedure's text and from appendix capture (e), which records the same not-yet-registered shape right after a push; it was not observed in a live merge.

**Why projects reach for the draft skip:** in one private project over 30 days, 176 of 312 pull-request CI runs were on commits a later push superseded, 63 of them cancelled mid-run. Those runs billed 3,120 minutes, 35% of the repository's Actions usage. `_shared/git-discipline.md` justifies the per-phase cadence on API budget alone ("per-phase cadence is free regardless of phase count"); Actions minutes are not part of that reasoning.

**Suggested fix:**
1. After `gh pr ready`, when the repository's `pull_request` workflow declares `ready_for_review`, require a head run created at or after the ready call (with a short bounded settle) before classifying green.
2. Document a supported "CI skips drafts" convention. A workaround that the gate already honors today: the draft-time run sets a commit status to `pending`, and the ready-time run flips it to `success` as its first step, so the rollup reads pending in the gap.
3. Note the constraint the gate puts on path filters: a workflow-level `paths:` filter on a docs-only PR leaves no checks reported, which the bounded watch maps to pending and waits out for 15 minutes before parking. A job-level `if` behind a small always-run job avoids that.
4. Note that a declared `ci` verification source polls draft-PR CI, so it and a draft skip cannot both be used.

**Definition:** Clear
