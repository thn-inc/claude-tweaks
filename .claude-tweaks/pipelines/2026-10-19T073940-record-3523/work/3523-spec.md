## Current State

The post-merge `windows-regression` workflow (run 39105151251, on `windows-latest`) found one test file newly failing after PR #3428 merged as `21ef3dc91`. That commit (#3400's change) added `tests/wrap-up-multispec-defer-still-live.test.js`; the file does not exist at the base `ac7ba9360`, so this failure is genuinely new rather than an inherited one. Exactly one test in it fails: `the defer paragraph is still found as one paragraph under CRLF line endings` (line 61), with `expected exactly one MULTISPEC_REVIEW_DEFER branch paragraph` / `0 !== 1`. Verified against `origin/main` at `7852fd8bf`, where the test file is unchanged since `21ef3dc91`.

Root cause, test-side only. The test's `live()` helper (line 23) reads `plugin/skills/wrap-up/execution-and-verification.md` with a raw `fs.readFileSync(FILE, 'utf8')`. The CRLF test (line 62) then builds its CRLF input with `live().replace(/\n/g, '\r\n')`. On a Windows checkout with `core.autocrlf=true` the read already returns `\r\n` line endings (this repo's `.gitattributes` pins only `tools/upstream-drift/fixtures/**`), so the replace turns every `\r\n` into `\r\r\n`. `deferParagraph`'s split regex `/\r?\n\r?\n/` cannot match a `\r\r\n\r\r\n` paragraph break, the file never splits into paragraphs, and no chunk starts with `**MULTISPEC_REVIEW_DEFER branch:**`. Reproduced in scratch against the `origin/main` copy of the skill file: the current transform finds 1 paragraph from an LF read and 0 from a CRLF read; LF-normalizing the read first finds 1 from both.

The other tests in the file pass on a CRLF checkout and are out of scope: `deferParagraph(live())` already splits on `\r?\n`, `SENTENCE` is a single line, and the engine-source pins (`checkBody`'s `'\n});'` search and the one-line skip pin) hold under `\r\n`. A repo-wide grep of `tests/` for `.replace(/\n/g, '\r\n')` on `origin/main` found no other site applying it to a live file read: every other hit converts an in-test string literal (`tests/bin-lib/flow/pr-body-premise-reversal.test.js`, `tests/comment-trust-conformance.test.js`, `tests/bin-lib/verify/extract.test.js` and others), which is the pattern the `windows-checkout-test-parity` project skill prescribes.

## Technical Approach

Test-side only, following `.claude/skills/windows-checkout-test-parity/SKILL.md`'s "Build CRLF inputs from the LF text" rule: a CRLF case must be built from the LF string with `.replace(/\n/g, '\r\n')`. A raw read of a tracked file is not LF text on a Windows checkout, so the read has to be normalized first. `tests/helpers/read-skill.js`'s `readText()` (`fs.readFileSync(absPath, 'utf8').replace(/\r\n/g, '\n')`) is the repo's single normalizing read for exactly this case. The skill's Anti-Patterns row for doctoring a go-red control on a raw read (`tests/wrap-up-record-resolution-conformance.test.js`, #3395) is the same move applied to the same class of defect. The engine-source reads (`engineSource()`) need no change.

## Gotchas

- Do not "fix" this by loosening `deferParagraph`'s split regex to tolerate `\r\r\n`. That would hide a malformed fixture rather than build a correct one, and `\r\r\n` never occurs in a real checkout.
- Do not add a `.gitattributes` `eol=lf` rule for the skill file or `tests/` as the fix. The parity skill keeps `.gitattributes` scoped to the hashed upstream fixtures on purpose, and the CRLF test exists precisely to prove the extractor survives a CRLF checkout.
