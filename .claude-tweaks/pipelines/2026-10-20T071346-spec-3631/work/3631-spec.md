# 3631: Stale-superpowers notice names no remedy for a record whose worktree directory was deleted

Surface: backend

**Related:** #3414, #3675

## Current State

- #3541 made `selectEntry` (`plugin/bin/lib/installed-plugins.js`) follow Claude Code 2.1.302's first-applicable rule. Under that rule a project or local record for a worktree directory that no longer exists still applies to a session in the same git checkout, because `canonicalGitRoot` walks up through missing path components to the main checkout. memenu-app hits this today: it loads claude-tweaks 6.113.0 and superpowers 6.3.0 from the deleted `.claude/worktrees/flow-spec-304-…` record, which sits first in each key's array.
- `superpowersNotice` (`plugin/bin/lib/superpowers-version.js:117`) reports such a selected record honestly ("this install is recorded for {path}, which no longer exists; it applies here because that path belongs to the same git checkout") but names no remedy beyond the generic `claude plugin update … --scope {scope}` line, so the reader cannot tell whether that command reaches the stale record.
- **Probed 2026-10-20 on Claude Code 2.1.302** (installed native build, scratch `CLAUDE_CONFIG_DIR`, a local marketplace with a dummy plugin `p@m`, a scratch git repo with a project or local record for the main checkout and one for a linked worktree that was then removed). This answers the record's former open question:
  - `claude plugin update p@m --scope project` run from the main checkout updated the deleted worktree's record — the first applicable one in file order — and left the main checkout's own record alone. With the two records' order reversed, the same command updated the main checkout's record instead. So `update` picks exactly the record `selectEntry` picks, and the notice's existing update command already fixes the stale version.
  - `claude plugin update p@m` (auto scope) from the main checkout behaved identically.
  - `claude plugin uninstall p@m --scope project` from the main checkout removed the **main checkout's own** record and left the deleted worktree's record in place, so uninstall matches `projectPath` exactly and is the wrong remedy from there.
  - After `mkdir -p` of the deleted worktree path, `claude plugin uninstall p@m --scope project` run from that recreated directory removed the stale record and kept the main checkout's.
  - `--scope local` behaved identically on all three (update picks the first applicable record; uninstall from the main checkout removes its own record; uninstall from the recreated directory removes the stale one).
  - `claude plugin uninstall p@m --scope local` against project-scope records failed with "installed in project scope, not local".

## Technical Approach

Only the `lstatType(...).type === 'missing'` branch of `superpowersNotice` changes: its suffix grows from one clause to the recorded-for clause plus the remove-instead remedy, built from `effective.projectPath`, `effective.marketplace` and `effective.scope`. The update command and the "never run the update yourself" tail stay as they are; the probe showed the update command already reaches the stale record. Keep the notice one line, since it is an inform-tier SessionStart banner. Quote the path in the `mkdir -p` command, because project paths here contain spaces (`Code Workspaces`).

## Gotchas

- The probe ran against `claude plugin` 2.1.302 only. A later Claude Code that changes `uninstall`'s exact-path match or `update`'s first-applicable pick would make the notice wrong; the header note is what a future re-probe compares against.
- Never send the user to run anything inside a directory that is gone without the `mkdir -p` first; that is the reason the existing suffix withholds a "run from" clause for a missing path.
- The notice tells the user what to run; it must keep its "never run the update yourself" instruction to the agent, and the remove remedy falls under the same rule.
