# 3020: build-review-context.js: the shared review bundle has no size bound and is unreadable on an ordinary feature diff

Surface: backend

**Related:** #2956, #3017

## Current State

`/claude-tweaks:review` Step 3 builds one shared context bundle and hands its path to every lens agent. The bundle has no size bound. Reported: a 32-file feature diff gave `bytes` 1,970,636 with `emptySections` empty, and a follow-up comment on 6.138.0 reports a 1,274,411-byte bundle (16 files) where one file was a ~900 KB captured-API `.jsonl` fixture. In both cases the controller dropped the bundle and gave agents the file list instead, a path the dispatch contract does not describe. `--files-from` is the only escape hatch today.

Verified on `origin/main`:
- `plugin/bin/lib/review-context/build.js:64-75`: `buildContext` appends `===== {f} =====` and the file's whole working-tree content for every in-scope file, whatever its size. The only degraded case is a failed read, which goes into `emptySections`.
- `build.js:79`: returns `{ dir, contextPath, bytes, files, emptySections }`. `bytes` is computed but nothing ever checks it.
- `build.js:39-43`: the module's own comment already says a section can degrade safely because "the full diff at the top still carries that file's change". This is the same argument a stub section relies on.
- `plugin/bin/build-review-context.js:74-75` prints that object as one JSON line. Lines 6-7 of the header comment list its fields.
- `plugin/skills/review/step3-lens-dispatch.md:68` documents the printed line as `{dir, contextPath, bytes, files, emptySections}`, and `:70` explains `emptySections`. `docs/plugin-structure.md:189` repeats the same field list.
- `tests/bin-lib/review-context/build.test.js` covers the bundle shape (line 69) and the CLI end to end (line 118). It has no size case.

## Deliverables

1. Decision (approved in brainstorming, 2026-10-15): cap each file's section. A file's full content is inlined only when it is under a per-file cap of 64 KB, held in a named exported constant. Larger files get a stub section instead, because the full diff at the top of the bundle already carries their hunks. Stubbed files are listed in a new `oversizeSections` field of the printed JSON line. Lockfiles and `*.jsonl` are always stubbed. The design keeps the single `contextPath` that every lens prompt relies on. Rejected: excluding generated files only, because it gives no general bound and any large hand-written file still floods the bundle. Rejected: splitting the bundle per file with an index, because it changes every consumer of `contextPath`.
2. `build.js`: add an exported constant, `PER_FILE_CAP_BYTES = 64 * 1024`, and an exported always-stub matcher. The matcher covers `*.jsonl` and named lockfiles (at least `package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `Cargo.lock`, `Gemfile.lock`, `poetry.lock`, `composer.lock`), matched on basename.
3. `buildContext`:
   - A file the matcher catches gets a stub without being read.
   - Other files are read as now. When content is over the cap (measured with `Buffer.byteLength`), the full content is replaced by a one-line stub that gives the file's byte size and points to the diff above and to reading the live file.
   - Push each stubbed path to `oversizeSections`, in file order, and add the field to the return value.
   - A failed read still goes to `emptySections` and never to `oversizeSections`.
4. CLI header comment, `step3-lens-dispatch.md:68-70` and `docs/plugin-structure.md:189`: name `oversizeSections` in the printed field list. In `step3-lens-dispatch.md`, add one sentence beside the `emptySections` paragraph saying stubbed sections degrade the same way, and that the lens reads the live file when it needs the full content.
5. **Diff block (extension approved 2026-10-16).** Apply the same rule to the diff at the top of the bundle. An added or deleted file whose hunk text exceeds `PER_FILE_CAP_BYTES`, or any always-stub match (lockfile or `*.jsonl`), has its hunk replaced by one marker line, `[{N} bytes of diff elided for {path} — see oversizeSections]`. Its path joins `oversizeSections`. A *modified* file's hunks stay whole, since they are the review's subject. Split the diff per file on the `diff --git` headers git emits, rather than re-running git per file.
6. Tests in `tests/bin-lib/review-context/build.test.js` (see Acceptance Criteria).

## Release Note

Cap each file in /review's shared lens bundle at 64 KB and always stub lockfiles and `.jsonl`, so lens agents can read the bundle on ordinary feature diffs.

## Technical Approach

### Key Files
- `plugin/bin/lib/review-context/build.js`: adds the cap constant and the always-stub matcher, adds stub sections in `buildContext`, and adds `oversizeSections` to the return value.
- `plugin/bin/build-review-context.js`: updates the header comment's field list. The JSON line passes the result through unchanged.
- `plugin/skills/review/step3-lens-dispatch.md`: updates the printed-line field list at :68 and adds the stub-degradation sentence next to :70.
- `docs/plugin-structure.md`: updates the field list at :189.
- `tests/bin-lib/review-context/build.test.js`: adds the cap, boundary, always-stub and CLI-field cases.
- `tests/bin-lib/review-context/prose.test.js`: pins `oversizeSections` in both prose files.

## Gotchas

- Deliverable 5 bounds added and deleted files' diff hunks, but a *modified* file's hunks are deliberately left whole, so a huge rewrite of an existing file can still make `bytes` large. No prose may claim the whole bundle is strictly bounded. `--files-from` remains the escape hatch.
- Dedupe `oversizeSections`: a file stubbed in both the diff block and its own section is listed once.
- The stub line must not look like file content. Lens agents report `Path:Line` from the live file (`step3-lens-dispatch.md`'s file-native rule), so keep the stub to one clearly marked line.
- Keep `readFile` as the only file seam, because the tests inject it to anchor paths to the fixture repo (`build.test.js:38-43`). Measure size from the content that was read rather than adding a `stat` call the fake does not provide.
- Check the name matcher before reading, so a deleted lockfile counts as stubbed rather than empty. State that order in a code comment.

## Original request

build-review-context.js: the shared review bundle has no size bound and is unreadable on an ordinary feature diff

**Summary:** `build-review-context.js build` writes one context file holding the full diff plus every changed file in full, with no size bound; on a 32-file feature diff it came out at about 1.97 MB, far more than a dispatched lens agent can read, so the bundle that `step3-lens-dispatch.md` tells the controller to hand to every lens went unused.

**Kind:** Defect

**Affected component:** `bin/build-review-context.js` (and `skills/review/step3-lens-dispatch.md`, which hands its output path to every lens agent)

**Repro steps:**
1. On a feature branch whose diff includes a few large files (here: an implementation plan of about 940 lines and several test files of a few thousand lines each, 32 changed files in all), run `node bin/build-review-context.js build --base <base> --branch HEAD --run <run-dir>`.
2. Read the printed JSON line: `bytes` was 1,970,636 for `files` 32, with `emptySections` empty.
3. Follow `step3-lens-dispatch.md` and give each lens agent the bundle path as its shared context.

**Expected vs. actual:**
Expected: a bundle a lens agent can read in one or two calls, or a build that reports the bundle is too large and says what to hand the agents instead (for example the diff alone, or one file per changed path with an index).
Actual: the build succeeds silently at any size. A lens agent handed a 2 MB file must page through it in many reads, most of it unchanged test code, before it reaches the hunks; the controller's practical choice is to drop the bundle and give each agent the file list and the diff scope, which the dispatch contract does not describe.

**Definition:** Needed — either cap and degrade (diff plus changed hunks with context, full files only below a size bound), or split the bundle per file with an index. The size bound itself is an open choice.

**Plugin version:** 6.136.0

## Build Deviations (Common Step 4.5 — classified Beneficial)

1. **Always-stub diff elision covers modified files too.** Deliverable 5 / the first Gotcha read as "a modified file's hunks stay whole"; as built, a lockfile or `*.jsonl` has its diff chunk elided for every change type (a modified 20,000-line `package-lock.json` alone produced a 538 KB bundle), while the over-cap elision stays added/deleted-only — modified hand-written files' hunks are still never elided. Matches Deliverable 1 ("never worth inlining") and the Release Note's "readable on ordinary feature diffs".
2. **Git-config-independent diff parsing.** The diff runs as `git -c core.quotePath=false diff --no-color --no-ext-diff --src-prefix=a/ --dst-prefix=b/`, and `--name-only` with `-c core.quotePath=false`, so `diff.noprefix` or non-ASCII paths cannot silently defeat elision; non-ASCII paths now read correctly instead of landing in `emptySections` under a quoted name.
3. **Stub wording names where to look.** A stub says the change is in the diff above, that the diff was elided too, or — for an elided or deleted path — to run the quoted `git diff {base}...{branch} -- '{path}'` (changed at review: the original `git show {base}:{path}` read the base tip, not the merge-base, and did not escape the path).
