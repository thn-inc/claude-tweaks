## Release Note

Fixed a run-directory test that failed on Windows checkouts because of line-ending and path-format differences.

## Technical Approach

The change is test-side only and follows the "Build CRLF inputs from the LF text" pattern in `.claude/skills/windows-checkout-test-parity/SKILL.md`, plus its two-layer Anti-Patterns row from #3517. `readText()` (`fs.readFileSync(p, 'utf8').replace(/\r\n/g, '\n')`) is the repo's single EOL-normalizing read for governed markdown. `skill-prose-conformance-tests` already requires it for every prose suite.

This suite extracts the snippets and then executes them, so normalizing at the read is the right fix, not a CRLF-tolerant regex. The scratch run showed that a `\r?\n`-only regex fix still hands bash a snippet full of `\r`.

The test-5 assertion changes because the shared snippet's step-2 output is a bash-side path. Under Git Bash it is MSYS-form, so it can never byte-equal a native `path.join` result. The test's claim is which directory gets selected, and the basename carries that claim on every platform. `path.basename` splits on both `/` and `\` on win32, so it handles the MSYS string there too.

Tests 1-4 keep their full-path assertions:

- Test 1 (shared snippet) resolves to `''`, which skips the `startsWith` check.
- Test 2 (shared snippet) passes the native env value through unchanged.
- Tests 3-4 (wrap-up) get native paths back from `resolve-run-dir`.

The `windows-regression.yml` dispatch is the ground truth for whether those predictions hold.

Make Deliverables 1-3 together in one commit. Then run the doctoring checks, then the dispatch. File the Deliverable 4 record during the build, not after merge.

## Gotchas

- Do not fix this by making the extraction regexes `\r?\n`-tolerant alone. The captured snippet keeps its `\r`s, and `bash -c` fails with `syntax error near unexpected token $'in\r'`, as the scratch run reproduced. The general advice in `skill-prose-conformance-tests` to "write `\r?\n`" covers extract-and-compare suites. This suite extracts and then executes.
- Do not add a `.gitattributes` `eol=lf` rule for the skill files or `tests/` as the fix. The parity skill scopes `.gitattributes` to the hashed upstream-drift fixtures on purpose.
- Do not "fix" test 5 by translating MSYS paths inside the skill snippet, or by changing `run-dir-resolution.md`. The snippet is the documented reference implementation, and its paths are correct for the shell that runs them. The mismatch exists only in the test's JS-side comparison.
- Test 5's MSYS-path failure is inferred from Git Bash's `pwd` behavior, not observed, because the CRLF failure masks it on Windows today. If the Windows dispatch shows test 5 failing with a different shape, investigate that shape and do not skip the test on win32. One possibility is an empty `resolved` because a non-GNU `find` resolved first on `PATH`.
- A `workflow_dispatch` of `windows-regression.yml` on a branch baselines against the branch's previous commit (`HEAD^1`, see #3568). If the fix is already in that commit, the adjudication verdict proves nothing. Read this file's per-test `ok` / `not ok` lines in the run's log.
- Keep this record to this one test file plus the Deliverable 4 capture. The other unclaimed siblings have the same CRLF shape but different extractors. Some also run what they extract, so a backslash `CLAUDE_PLUGIN_ROOT` second layer may apply to them, as in #3555 and #3587. Each needs its own Windows proof.
