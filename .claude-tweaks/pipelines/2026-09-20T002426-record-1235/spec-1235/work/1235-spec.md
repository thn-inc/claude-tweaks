# 1235: reconcile/cache.js does per-item read-modify-write instead of batching

Surface: backend

## Current State

`plugin/bin/lib/reconcile/cache.js`'s `recordResidueFailure` and `recordResidueSuccess` each call `readCache(root)` then `writeCache(root, ...)` — a full synchronous read-modify-write of `.claude-tweaks/reconcile-cache.json` on every call. Both are invoked once per item inside a loop by their two callers, `reap-merged.js` (`removal-failed` residue) and `archive-merged.js` (`move-failed` residue), so a reconcile pass touching N items does N separate read+write round-trips against the same file instead of one read before the loop and one write after. Confirmed against the current file — this is a deliberate per-entry-atomicity tradeoff (each item's residue state is durable the instant it's recorded, even if a later item in the same pass throws), not an oversight.

## Deliverables

- [ ] Refactor `reap-merged.js` and `archive-merged.js` to read `reconcile-cache.json` once before their item loops, accumulate `recordResidueFailure`/`recordResidueSuccess` updates against an in-memory copy, and write once after the loop completes
- [ ] Decide and document the atomicity tradeoff: batching means a process crash mid-loop loses residue updates for every item processed so far in that pass, not just the unprocessed ones — record the decision (keep per-entry writes, or accept the batched risk) as a code comment at the call site

## Acceptance Criteria

- [ ] A reconcile pass processing N items performs exactly one read and one write of `reconcile-cache.json` per caller (`reap-merged.js`, `archive-merged.js`), not N of each
- [ ] The atomicity tradeoff decision is documented at the call site
- [ ] `npm test` passes, including existing reconcile-cache coverage

## Technical Approach

Read the cache once before the item loop in each caller, mutate an in-memory copy per item (reusing `recordResidueFailure`/`recordResidueSuccess`'s existing key/count logic), and write once after the loop — while deciding whether to keep or drop per-entry atomicity, since a process crash mid-loop after batching would lose the whole pass's not-yet-flushed residue updates instead of just the unprocessed items.

### Key Files

- `plugin/bin/lib/reconcile/cache.js` — `recordResidueFailure`/`recordResidueSuccess`, the read-modify-write pair in question
- `plugin/bin/lib/reconcile/reap-merged.js` — one of two per-item callers (`removal-failed` residue)
- `plugin/bin/lib/reconcile/archive-merged.js` — the other per-item caller (`move-failed` residue)

## Gotchas

- Batching trades per-entry durability for efficiency — a crash mid-loop after batching would lose residue updates for every item processed so far in that pass, not just the unprocessed ones. Any future implementation needs to weigh that against the write-volume savings.
