# 2613: tidy claims-registry audit: documented full-scan procedure has no batched alternative, inviting a sampling shortcut that produced a 93% false-positive rate

Surface: infra

## Current State

`/claude-tweaks:tidy`'s Step 4.7 claims-registry audit (`issue-claims-backstops.md`, "Primary: list the `claims/` blob keyspace") documents a full list-then-classify-each-blob procedure with no batched alternative and no explicit warning that sampling the keyspace is unsafe — every blob genuinely needs checking, since a claim's presence/staleness is a binary fact, not something a statistical sample can approximate.

Observed directly this session: an earlier standalone tidy run against this repo's claims-registry (now ~1000 blobs) sampled only ~10 of them instead of following the documented full listing, and flagged 14 issues as having "no active claim." The run's own report already carried a stated Concern about this sampling gap. On mandatory pre-write re-verification (this session), 13 of those 14 (93%) turned out to have real, non-expired claims from active sessions — the batch was almost entirely false positives, caught only because the re-verification step exists.

Root cause (confirmed by reading the existing code): `plugin/bin/lib/issues/claims-git-cas.js`'s `readClaimBlobGit` already amortizes the branch-tip fetch across a batch (#1467's `knownTip` seam), but still reads each blob's content with its own `git show {tip}:{path}` subprocess call — one spawn per blob. The no-git-CAS fallback (`claim-store.js`'s `readClaimBlobContentsApi`) is worse: one network round-trip per blob, with no batched-content endpoint on GitHub's REST contents API. Neither path scales to a ~1000-blob registry without either taking real time or inviting exactly the sampling shortcut that produced this session's false-positive batch.

## Deliverables

- Add `readClaimBlobsGitBatch(issueNumbers, { tip, ... })` to `claims-git-cas.js`: one `git ls-tree -r {tip} -- claims/` call to confirm the full blob set, then one `git cat-file --batch` call fed every target blob's sha via stdin, parsing the streamed multi-blob output — replacing N `git show` calls with 2 total subprocess invocations for the git-CAS transport, regardless of registry size.
- Wire the claims-registry audit scan (`issue-claims-backstops.md`'s "Primary: list the `claims/` blob keyspace" procedure) to call the new batched path when a `gitRunner` is available, falling back to today's existing per-blob behavior only when it is not (contents-API-only environments) — that fallback path is explicitly out of scope for batching here (see Technical Approach).
- Add an explicit statement to `issue-claims-backstops.md`: sampling this check is unsafe — a claim's live/stale/unreadable state is a binary per-issue fact, not something a statistical sample can approximate — with a pointer to the batched path so a future session under time/cost pressure has a documented non-shortcut instead of an implicit expectation.

## Acceptance Criteria

- The documented claims-registry audit procedure scales to a registry with hundreds-to-thousands of blobs without requiring one subprocess call or one API round-trip per blob, on the git-CAS transport.
- `issue-claims-backstops.md` explicitly states that a partial/sampled scan of this check is not an acceptable substitute for the full listing.
- `npm test` passes, including new coverage: (1) `readClaimBlobsGitBatch` returns identical per-blob classification to N sequential `readClaimBlobGit` calls against the same fixture claims-registry; (2) a mocked-runner call-count assertion proves the batch path issues exactly 2 subprocess invocations regardless of blob count.

## Technical Approach

Batch the git-CAS transport; leave the contents-API-only fallback as-is. The git-CAS path (`claims-git-cas.js`) already has everything needed to batch: a known branch tip (via `knownTip`, already amortized across a batch per #1467) and `git`'s own `cat-file --batch` command, which reads an arbitrary list of object shas from stdin and streams their content on stdout in one process — the standard efficient way to bulk-read git blobs, vs. one `show` per blob. `git ls-tree -r {tip} -- claims/` gives the full path→sha mapping for the `claims/` subtree in one call; the shas for the target issue numbers' paths feed directly into `cat-file --batch`.

The contents-API-only fallback (no local git access — a `gh`-only sandbox) is scoped out: GitHub's REST contents API has no batched-content endpoint, and a GraphQL-aliased batch query would need its own investigation and is a narrower, already-documented-as-degraded transport (the git-CAS path is the common case any full-registry audit runs from, since it requires a local checkout with the `claims-registry` ref reachable — the same requirement the existing `gitRunner`-present branch already assumes). This fix closes the dominant cost driver, not every driver; the remaining API-only gap is a smaller, already-accepted-degrade case, not a new one this record introduces.

### Key Files

- `plugin/bin/lib/issues/claims-git-cas.js` — new `readClaimBlobsGitBatch`, alongside the existing single-blob `readClaimBlobGit`/`writeClaimBlobGit`
- `plugin/skills/tidy/issue-claims-backstops.md` — wire the audit procedure to the batched path; add the sampling-is-unsafe statement
- `plugin/skills/_shared/issue-claims.md` — cited by the audit procedure for per-blob "stale/unreadable/live" classification rules; unchanged, but read alongside the above to confirm the batch path's output still classifies each blob per those existing rules
- `tests/bin-lib/issues/claims-git-cas.test.js` — new coverage for the batch read

## Gotchas

- Any batched-fetch replacement must still classify each blob per `_shared/issue-claims.md`'s existing "stale/unreadable/live" rules — this is about the fetch mechanism's cost, not the classification logic.
- `git cat-file --batch`'s output framing (each object preceded by a `{sha} {type} {size}\n` header line) needs careful parsing to correctly split concatenated blob contents — a naive line-split will corrupt any blob content containing embedded newlines (claim blobs are small JSON-ish text today, but the parser should not assume that silently).
- The contents-API-only fallback is unchanged by this record — a future session hitting the sampling temptation from that transport (no local git access) still has only the per-blob path available; that gap is named explicitly in Technical Approach rather than silently left unaddressed.

## Breaking Change

None — this adds a new function to an internal library module and updates a skill's internal audit procedure. No public flag, CLI verb, exported function signature, or `_shared/*.md` convention that external consumers rely on is removed or renamed.
