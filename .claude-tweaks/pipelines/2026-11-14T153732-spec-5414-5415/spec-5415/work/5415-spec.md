# 5415: Driver: a worker index flag lets the test and evidence runs judge code that is not at HEAD

Surface: backend

Origin: ledger resolve gate (#5222 wrap-up, raised by the row 15 fix)

**Related:** #5414, #5423, #5354, #5224, #5226, #5229, #5232, #5264, #5333, #4493, #5339
Risk-flags: none

## Current State

`git update-index --skip-worktree <file>` or `--assume-unchanged <file>` makes git stop reporting a file's worktree changes: git status, `git diff` and the driver's commit step (`commitStep`, `plugin/bin/lib/driver/steps.js`) no longer see an edit, so the worktree copy can differ from HEAD unnoticed.

The driver judges the worktree copy in two places: the scoped test step (`testStep`, `plugin/bin/lib/driver/steps.js:613`, which the review fix round calls again) and each evidence run (`runEvidence`, `plugin/bin/lib/driver/review.js:609`, which serves both the reviewer's evidence runs and the fix round's direct runs of kept tests). Either can pass on bytes that are never committed. CI on push runs HEAD and would catch a difference, so the harm is a wrong green verdict from the driver and a red PR, not broken code merged.

Who can set the flag:

- The worker itself, during its launch, cannot: `git update-index` is not on the implementer's allow list, and the index lives in the shared git directory outside the worktree, where the `darwin` sandbox denies writes (`docs/driver.md`, Worker rights).
- Worker-written code can, when the driver itself runs it with its own rights outside the sandbox: the scoped test step and the evidence runs execute the worker's tests. Such code can set a flag and rewrite a source file before the run judges it.

#5222 (squash `d3962cda8`) closed this for the evidence files themselves: before each fix-round direct run the file on disk must hold the recorded bytes (`inWorktreeAsRecorded`, `review.js`). Every other tracked file is still open to it.

A blanket stop on any flag would false-stop a sparse-checkout worktree, where git sets the skip-worktree flag itself.

Decision (brainstormed with the maintainer, 2026-11-14): compare the flagged set against a baseline taken when the worktree is created, at every point where worker-written code has run, and stop on any newly flagged path. Clearing new flags was rejected (it rewrites the index under a run already gone wrong and ends in a stop anyway), and hashing every tracked file by bytes was rejected (slow on a large repo, and the flag comparison already covers it).

**Decision** (maintainer, at plan review, 2026-11-14): a worktree with `core.ignoreStat` true is refused up front. In such a repo git marks every path it updates in the index assume-unchanged, so the driver's own `git add` would tag the worker's files and the post-test flag check would stop every record. So the `worktree` step reads `git -C {wt} config --bool core.ignoreStat` once the worktree exists, before the baseline and before any worker runs. When it prints `true`, the step stops the record with status `fail` and a fixed detail naming the setting. An unset value, `false`, and a config read that fails with git's "not set" exit (1) all pass; any other read failure stops with `fail`. `docs/driver.md` names the refusal beside the flag rule. The single baseline and AC4 stay as written, with no exclusion of paths the driver staged itself. The plan-review question was https://github.com/thn-inc/claude-tweaks/issues/5415#issuecomment-6882428314.

## Deliverables

- [ ] After `worktreeStep` (`plugin/bin/lib/driver/steps.js:374`) creates the worktree, the driver reads the flagged set once with `git ls-files -v -z` (tag `S` = skip-worktree; a lowercase tag = assume-unchanged) and keeps it on the run context as the baseline.
- [ ] The flagged set is read again, and compared with the baseline, after each implementer launch (`runImplementer`, `steps.js:453`, shared by the implementer step and the fix round), after the scoped test step (`testStep`), and after each evidence run (`runEvidence`). Any path flagged now and not in the baseline stops the record with status `fail`, its detail naming at most a few of the new paths (neutralized) and their total count.
- [ ] A failed `ls-files` read, at the baseline or at any check point, stops the record with status `fail`.
- [ ] `docs/driver.md` states the rule, that flags present when the worktree is created never count, and that CI on push remains the backstop.
- [ ] Tests in `tests/bin-lib/driver/run.test.js` and `tests/bin-lib/driver/review.test.js` for every acceptance criterion below.

## Acceptance Criteria

1. Over a fake runner, a skip-worktree flag that appears after the implementer launch stops the record at the `worker` step with status `fail`, and no commit step runs.
2. A flag that appears during the scoped test step stops the record at the `test` step with status `fail`, and no `check` or push runs.
3. A flag that appears during an evidence run stops the record at the `review` step with status `fail`, for a reviewer evidence run and for a fix-round direct run (two tests).
4. An assume-unchanged flag (lowercase `ls-files -v` tag) that appears after a check point stops the record the same way as a skip-worktree flag.
5. A worktree whose baseline already holds `S`-tagged paths (a sparse checkout) runs the Phase 1 happy path to the push: flags already in the baseline never stop the record.
6. An `ls-files` read that fails, at the baseline and at a check point, stops with status `fail` (two tests).
7. The stop detail lists at most the named cap of new paths plus the total count, and a flagged path holding a newline, `fixes #12` and `@someone` reaches the detail neutralized.
8. On the Phase 1 happy path, the recorded calls differ from before only by the baseline read plus one read after each check point (implementer launch, scoped test step, and each evidence run when the review step runs), and the event lines are unchanged.
9. `docs/driver.md` names the newly-set-flag stop, using the word `skip-worktree` in that rule's own sentence.

## Release Note

The pipeline driver now stops a record when code it runs hides a file's changes from git, so its test and evidence verdicts always judge what gets committed.

## Technical Approach

- One helper reads the set: `git -C {wt} --no-optional-locks ls-files -v -z`, split on NUL, each entry `{tag} {path}`; a path counts as flagged when its tag is `S` or a lowercase letter. The comparison is set difference against the baseline (a flag cleared since the baseline is not a stop).
- The baseline lives on the run context next to the worktree path, set by `worktreeStep` once the worktree exists; every check point compares against that one baseline, never against the previous check point.
- The check runs after the worker or test process has exited, before the step judges its result, so a stop names the flag instead of a test outcome built on hidden bytes.
- Every stop here is a pre-push stop like the other `worker`, `test` and `review` stops; no new stop class, outcome or event field.

### Key Files

- `plugin/bin/lib/driver/steps.js` — flag-set reader and comparison helper; baseline in `worktreeStep`; checks after `runImplementer`'s launch and after `testStep`
- `plugin/bin/lib/driver/review.js` — check after each `runEvidence` call
- `docs/driver.md` — the newly-set-flag rule and its baseline
- `tests/bin-lib/driver/run.test.js` — worker, test-step, sparse-baseline and read-failure tests; happy-path call fixtures gain the reads
- `tests/bin-lib/driver/review.test.js` — evidence-run tests

## Gotchas

- Many existing fixtures script the fake runner's git calls in order; the new reads shift them, so update fixtures by adding the reads, never by loosening the call assertions.
- #5414 adds HEAD reads around the same `runImplementer` launch and touches the same call-order fixtures; whichever record lands second adds its reads on top of the other's, and the two checks stay separate (a moved HEAD and a newly set flag are different stops).
- #5423 would run the evidence child under the implementer's sandbox, which would also stop evidence code from writing the index. Keep the evidence-run check point anyway: the scoped test step stays unsandboxed, and the check is cheap defense in depth if containment fails.
- Never clear a flag to recover the run: the decision is to stop, and clearing it would erase the evidence of what the code did.
- `ls-files -v` reads the whole index, so its cost grows with the repo; keep the reads to the stated check points rather than adding more.
- The other index-level tricks (a `.gitattributes` filter, `core.fsmonitor`) are outside this record; `steps.js` already reads the scope file by raw bytes for the same reason.
