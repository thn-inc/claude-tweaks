# 5414: Driver: decide how worker self-commit messages reach the branch

Surface: backend

Origin: ledger resolve gate (#5222 wrap-up, ledger row 14)

**Related:** #5354, #5415, #5224, #5226, #5229, #5232, #5264, #5333, #3875, #4496, #5339, #5412
Risk-flags: none

## Current State

The pipeline driver writes every commit message itself: the commit step (`plugin/bin/lib/driver/steps.js`, `commitStep`) builds it from the worker's title through `normalizeTitle`, so a message cannot carry a line break, a live `@` mention or an issue-closing keyword.

A worker is not meant to commit at all. The implementer's generated settings deny `git commit` and `git add`; on `darwin` its Bash runs in a sandbox whose writes are confined to the worktree, and a commit writes the shared git directory outside it; on any other platform the implementer has no Bash (`docs/driver.md`, Worker rights). A worker commit therefore means those rights failed.

The code still tolerates one:

- `runImplementer` (`plugin/bin/lib/driver/steps.js:453`), which both the implementer step and the review fix round call, never reads HEAD around the launch, so a worker commit, `git reset` or branch switch goes unnoticed. The commit step then commits whatever is left on top, and the worker's own commits reach the branch and the PR with the worker's unnormalized messages.
- The review fix round (`plugin/bin/lib/driver/review.js:1074-1075`) carries on when the commit step reports nothing to commit, so a fix worker that committed everything itself passes.
- `docs/driver.md` (One fix round) states that carry-on, and `tests/bin-lib/driver/run.test.js:3343` ("fix round: an evidence file the worker committed itself, unchanged, passes") pins it.

Decision (brainstormed with the maintainer, 2026-11-14): refuse. A moved HEAD after a worker launch stops the record. Squashing under the driver's message was rejected because it launders an escape, and rewriting messages because it is the most code and keeps whatever else the worker's commits carry (author, trailers, signatures).

## Deliverables

- [ ] `runImplementer` reads HEAD (`git rev-parse --verify --end-of-options HEAD`) before the worker launch and again after the worker returns, whatever the worker's status; a different HEAD, or HEAD unreadable on either side, returns status `fail` whose detail names only the two shas (never worker text).
- [ ] The review fix round's nothing-to-commit carry-on in `plugin/bin/lib/driver/review.js` is removed: a fix-round commit step that is not `ok` stops the round, as any other commit failure does.
- [ ] `docs/driver.md`: the One fix round sentence about a worker that committed everything itself is replaced by the refusal rule, and Worker rights gains one line stating that a worker launch after which HEAD has moved stops the record.
- [ ] Tests in `tests/bin-lib/driver/run.test.js` for every acceptance criterion below; the test at line 3343 is rewritten to expect the stop.

## Acceptance Criteria

1. Over a fake runner, an implementer-step worker whose launch is followed by a different HEAD stops the record at the `worker` step with status `fail`, and the stop's detail contains both full shas. No commit step, test step or push runs after it.
2. A worker that moves HEAD to an earlier commit (a `git reset`) stops the same way as one that adds a commit.
3. A review fix-round worker that moves HEAD stops the record at the `review` step with status `fail`, and no commit, scoped test or second `check` runs after it.
4. HEAD unreadable before the launch, and HEAD unreadable after it, each stop with status `fail` (two tests); in the before case no worker is launched.
5. A worker whose status is `fail` or `timeout` and that also moved HEAD still reports the moved HEAD: the HEAD check runs before the status is judged, so the stop's detail names the move.
6. A fix-round worker that leaves nothing to commit stops the round: the test formerly named "fix round: an evidence file the worker committed itself, unchanged, passes" now asserts a stop and no push.
7. On the Phase 1 happy path, the recorded calls differ from before only by the two HEAD reads around each implementer launch (one launch without the review step, two with a fix round), and the event lines are unchanged.
8. The stop detail carries no text from the worker's result: a test whose worker title holds a newline, `fixes #12` and `@someone` asserts none of them reach the detail.
9. `docs/driver.md` no longer states that a fix round carries on when the worker committed everything itself (`grep -F "committed everything itself" docs/driver.md` matches today and returns nothing after the change), and Worker rights names the moved-HEAD stop.

## Release Note

The pipeline driver now stops a record when a worker moves the branch itself, instead of keeping commits the worker was never allowed to make.

## Technical Approach

- Read HEAD with the same `gitIn(deps, wt, ['rev-parse', '--verify', '--end-of-options', 'HEAD'])` form `steps.js` already uses for the push guard, and require a full sha as `review.js` does (`FULL_SHA_RE`).
- The check lives in `runImplementer` only, so the implementer step and the fix round (`launchImplementer` in the deps `review.js` receives) share it; `review.js` keeps its own `preFixHead` read for the diff it already makes.
- The stop is a pre-push stop like every `worker` and `review` stop, so it settles the same way; no new stop class, outcome or event field.

### Key Files

- `plugin/bin/lib/driver/steps.js` — `runImplementer`: HEAD read before and after the launch, moved or unreadable HEAD returns `fail`
- `plugin/bin/lib/driver/review.js` — fix round: remove the nothing-to-commit carry-on
- `docs/driver.md` — One fix round sentence replaced; Worker rights line added
- `tests/bin-lib/driver/run.test.js` — new tests, the line 3343 test rewritten, happy-path call fixtures gain the HEAD reads

## Gotchas

- Many existing fixtures script the fake runner's git calls in order; the two new HEAD reads per launch shift them, so update fixtures by adding the reads, never by loosening the call assertions.
- Worker-written code also runs under the driver's own rights in the driver's test step and the review evidence runs, outside the worker sandbox, and could commit there. This record does not add a check around those runs: the runner pass stamp and the push guard already compare HEAD with what `check` verified, so a moved HEAD there stops before the push.
- A worker-authored git client hook that runs inside the driver's own `git commit` or `git push` is #5354's scope, not this record's; the check here judges only the worker launch.
- Never fall back to resetting HEAD to recover the run: the decision is to stop, and a reset would discard evidence of what the worker did.

## Current State

The pipeline driver normalizes the commit message it writes itself: the commit step builds it with `normalizeTitle`/`neutralize` (`plugin/bin/lib/driver/events.js`), so a worker-supplied title cannot carry a line break, a live `@` mention or an issue-closing keyword.

A worker can also run `git commit` itself. Those commits reach the branch, and the PR, with whatever message the worker wrote: the implementer step already accepts partial self-commits (`plugin/bin/lib/driver/steps.js`), and since #5222 the review fix round carries on when the fix worker committed everything itself (`plugin/bin/lib/driver/review.js`, `docs/driver.md` One fix round).

The #5222 whole-branch review triaged this as OK to defer: the self-commit acceptance predates #5222 in the implementer step, and the fix round only extends it.

## Deliverables

- [ ] Decide one behavior for worker self-commits, applied to both the implementer step and the review fix round
- [ ] Implement it in `steps.js` and `review.js`, with tests in `tests/bin-lib/driver/run.test.js`
- [ ] State the behavior in `docs/driver.md`

## Open Question

Should the driver refuse worker self-commits (stop the step), squash them under its own normalized message (soft reset to the pre-worker HEAD, then the commit step), or keep them and only rewrite their messages through normalizeTitle/neutralize?
