# 1989: Merge-path markers: fence pr-first-merge.md and pr-early-run-lifecycle.md by integration-model and transport; wrap-up's merge row reads one composed `merge` bundle

Surface: backend

## Overview

Migrate the merge path — the vertical slice the parent design (#1987) measures Phase 1 against — onto U1's composer: fence the existing `pr-first`/`local-merge` branches inside `plugin/skills/_shared/pr-first-merge.md` (30,166 B) and `plugin/skills/_shared/pr-early-run-lifecycle.md` (28,446 B) with `when:` markers, without rewriting a single sentence of the prose being fenced, then switch the two consumer files that run the merge procedure — `plugin/skills/wrap-up/cleanup-procedures-execution.md` Section C's merge row and `plugin/skills/wrap-up/auto-merge-short-circuit.md` — to compose a `merge` bundle and read it instead of reading both sources directly. Every other citing file (roughly 30 per source) keeps reading the sources unchanged.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Fencing any file other than the two named sources — `pipeline-run-dir.md`, `auto-mode-contract.md`, `worktree-setup.md`, `issue-claims.md`, `github-pr-scan.md`, and the rest are later Phase 2 sub-issues.
- Switching any citing file besides the two named consumers — every other citer of `pr-first-merge.md`/`pr-early-run-lifecycle.md` (roughly 30 files) keeps reading the sources directly, unchanged, per the parent design's stated scope.
- Rewriting or improving the fenced prose — this record fences text that already exists; the review question per fence is "is this sentence really pr-first-only / gh-only", never "can this sentence be improved".
- Building the composed-bytes measurement itself — that is the sibling U3 record; this record's byte-identity proof is a plan-time verification step, not a permanent measurement.
- Resolving #1728, #1875, #1793, or #1795 — these `needs:decision` records also touch the same two files; this record's markers are rebased onto whatever lands first from them, not blocked on their resolution.

## Technical Approach

Fencing is purely additive to the two source files — every fenced block's content is byte-identical to what already exists; only marker lines are inserted around it. The review for each fence is "is this sentence really pr-first-only / gh-only" — a sentence that reads correctly under both branches is left unconditional, not fenced defensively.

## Gotchas

- `[IL-144]`: never delete text while fencing — every fenced block's content must remain byte-for-byte what it was before this change; the byte-identity proof exists specifically to catch an accidental deletion.
- Never fence a heading, a `**Step N**` label, or an anchor another file cites by name — grep every known citer of both source files for the heading text before fencing, not after.
- #1728 and #1875 (both `needs:decision`, both edit `pr-early-run-lifecycle.md`) and #1793/#1795 (both `needs:decision`, both edit `cleanup-procedures-execution.md`) are gotchas to rebase around, not blockers — do not wait for them; re-verify the byte-identity proof against `origin/main` at PR time since one of them may have landed first.
- The byte-identity proof is deliberately a plan-time verification step, never a committed fixture — a fixture would freeze these two files against every future edit, defeating the point of migrating them onto a living composition mechanism.
- Assumption carried from the design doc: shared contracts carry every branch of a condition the run has already resolved once (883 KB of files carry both `pr-first` and `local-merge` prose repo-wide) — this record is the first of several planned migrations (Phase 2) that generalize the same fix; treat this record's own approach as the template later Phase 2 records copy, not as a one-off.
