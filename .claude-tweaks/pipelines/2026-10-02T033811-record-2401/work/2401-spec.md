# 2401: Investigate: record #2329 built with no landed claims-registry claim (not the #2329 race itself)

Surface: infra

## Current State

Investigating record #2329's own claim state during its `/claude-tweaks:review`/`/wrap-up` pass
turned up an anomaly worth a dedicated look, separate from #2329's own fix.

- `claims/issue-2329.json` has **never existed** on the `claims-registry` branch, at any point:
  `git log --all -- claims/issue-2329.json` returns zero commits. No claim comment was ever
  posted on issue #2329, and `bot:in-progress` was never applied.
- Yet the record was fully built: worktree `worktree-record-2329`, commits `19641f1f9`
  (materialize) and `03233821d` (the fix itself), pushed branch, draft PR #2399, and a full
  passing `npm test` (8783/8783) -- all present and real.
- This **rules out** the "unverified-claim leak" scenario #2329 itself fixes: that requires the
  write to have actually landed as a real commit (just not confirmed by the read-back). A landed
  write always leaves a commit + blob; here neither exists. So this is not an instance of the bug
  #2329/PR #2399 fixes -- it's a distinct gap in whatever process claimed (or should have claimed)
  this record before building it.
- Per `plugin/skills/flow/claim-targets.md`, any non-zero `claim-targets.js` exit (3/4/5) should
  stop the pipeline **before** the Config Manifesto -- no worktree, no build. Since the build
  demonstrably happened, the claim step must have either reported success without a real write
  landing, or never run at all for this target.
- A related irregularity in the same run directory
  (`.claude-tweaks/pipelines/2026-09-14T040051-record-2329/`): `config.yml` was **never written**
  despite `decisions.md` already showing populated `/build` and `/test` entries (recovered via
  `steps-and-gates.md`'s adoption "case 3" during this review/wrap-up pass). `events.jsonl` shows
  a `pre-compact` event and a `session-end` (`reason: clear`, a different `sessionId`) in the
  ~6-minute window right after build+test completed and before this review/wrap-up pass started
  -- consistent with session-boundary instability around this specific run, though not confirmed
  as the root cause.

## Deliverables

- Determine how record #2329 was actually dispatched/built: did something invoke
  `bin/claim-targets.js` for it at all, and if so, what did it report? (No surviving process
  logs from the original session were available for this investigation -- this may require
  instrumenting the claim step, or catching the failure mode live on a future occurrence.)
- If the claim step can silently be skipped (e.g., a caller invoking `/flow` directly with a
  hand-set `PIPELINE_RUN_DIR` shaped like a dispatch-minted one, bypassing `/dispatch`'s own
  claim-then-hand-off flow), consider whether `claim-targets.md`'s skip-guard or `/flow`'s Step
  2.8 needs a stronger invariant here.
- If it's a session-boundary/compaction interaction (the `config.yml`-never-written symptom),
  consider whether Manifesto writes need to be more robust to a mid-pipeline session
  interruption, beyond the existing case-3 recovery path (which handled it retroactively here
  but didn't prevent the underlying gap).

## Acceptance Criteria

- A documented explanation (or a reproduction) of how a record can reach a full build without a
  landed claim, OR a mechanical safeguard added that would have caught this case (e.g., `/build`
  or `/test` refusing to proceed past a certain point without a verified live claim under the
  invoking run's own identity).

## Technical Approach

Start from the two candidate root causes the Current State already narrows this to: (1) a bypass
path that reaches `/flow`'s build steps without ever calling `bin/claim-targets.js` for this
target -- audit every caller that can set `PIPELINE_RUN_DIR` to a dispatch-shaped value without
going through `/dispatch`'s own claim-then-hand-off flow; (2) a session-boundary/compaction
interaction around the Manifesto write -- the `pre-compact`/`session-end` events in the same
window are circumstantial, not confirmed, so reproducing that timing (or instrumenting the claim
step to log unconditionally, including a no-op/skip) is the concrete next step for either avenue.
This is explicitly open-ended: the Acceptance Criteria accepts either a root-cause explanation
or a mechanical safeguard, since the root cause may not be reproducible from historical evidence
alone.
