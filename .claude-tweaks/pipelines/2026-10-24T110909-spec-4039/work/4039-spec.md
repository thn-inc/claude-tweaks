# 4039: verification-brief: under pr-first with the merge left open, the brief's screenshot commit lands on an already-merged branch

Surface: infra

**Related:** #3813, #3508, #3835, #3915, #3942, #3963, #3976, #4045

## Current State

`plugin/skills/wrap-up/verification-brief.md` Step 4 ("Compose and post the brief") commits the
1-3 selected screenshots to `docs/demo-evidence/{record}/` "on this run's current branch", then
embeds them in the Verification Brief via a commit-SHA-pinned `raw.githubusercontent.com` URL. It
never checks whether that branch's PR is still open, and it never pushes the commit itself — it
relies on the later phase-exit push in `execution-and-verification.md`.

Where labeling sits relative to the merge depends on the path:

- **Leave-open** (the filed report's case): Phase 4's execution step (`execution-and-verification.md`,
  the Acceptance labeling bullet) commits the evidence before the closing-keyword carrier commit
  and the last phase-exit push, and no merge runs — so in-run, the evidence rides the open PR. The
  report's premise that labeling "only runs after a human merges" does not hold for the in-run flow.
- **Auto-merge short-circuit** (`auto-merge-short-circuit.md`, "acceptance labeling runs first,
  before the merge") and dispatch's group gate (`dispatch/settle-and-merge.md`) both label before
  merging.
- **Console "Approve all + merge"** under `pr-first`: the branch-finish merge runs at
  `review-console.md` step 13, *before* Phase 4's execution step, so acceptance labeling — and
  this screenshot commit — runs after `gh pr merge` and lands on the already-merged branch. #3813
  (ready, still open) proposes fixing that ordering for the whole execution step by moving the
  merge after the last tree-changing action.

The gap #3813 does not cover is the **late re-run**: when verify's `acceptance-labeling` check fails, wrap-up reports
`BLOCKED` and stops with the PR left open. If a human merges the PR before acceptance labeling is
re-run (a later `/claude-tweaks:wrap-up`, or a manual fix-up after the `BLOCKED` verdict), Step 4
commits onto a branch whose PR is already merged or closed. That commit never reaches the
integration branch, the worktree can't be removed without losing it, and the brief's SHA-pinned
URLs resolve only while the orphaned commit stays reachable. The filer's consumer project needed a
follow-up PR by hand to land the evidence.

## Deliverables

1. **PR-state check before the screenshot commit** in `verification-brief.md` Step 4: before
   committing, resolve the state of the PR for the branch checked out in the run's worktree —
   open, merged/closed, or no PR at all (`local-merge`, or a degraded `pr-first` run with no `pr`
   object).
2. **Open PR or no forge — commit and push.** Commit exactly as Step 4 does today, then push that
   commit explicitly to the branch's upstream, so a re-run after the run's last phase-exit push
   still lands its evidence on the open PR. Under `local-merge` (no PR) keep today's commit-only
   behavior — `local-merge` has no forge branch to push to for the brief's purposes.
3. **PR merged or closed — route the evidence to its own branch and PR.** Do not commit to the dead
   branch. Instead: create a fresh `demo-evidence/{record}` branch off the up-to-date integration
   branch, commit only the `docs/demo-evidence/{record}/` screenshots there, push it, and open a
   small evidence-only PR whose body references the record with `Refs #{record}` (never a closing
   keyword — the record's own closure already happened or belongs to its original PR). Embed the
   new commit's SHA in the brief. The evidence PR is left open for a human to merge — it is never
   auto-merged, since no `auto:merge` grant covers it.
4. **Report the routing.** Log which branch Step 4 took to `decisions.md` per
   `_shared/auto-decision-log.md` (`AUTO` status, rationale = the resolved PR state) when a run
   directory resolves, and name the evidence PR's URL in the brief and in the run's summary output
   when the merged/closed branch ran.
5. **Conformance test** pinning the three-way routing in Step 4's prose (open/no-forge,
   merged/closed, the explicit push, the `Refs` not-closing reference).

## Acceptance Criteria

- `verification-brief.md` Step 4 states a PR-state check that runs before the screenshot commit and
  names three outcomes: open PR, merged or closed PR, and no PR.
- On an open PR, Step 4 instructs an explicit push of the evidence commit to the branch's upstream
  immediately after committing it.
- On a merged or closed PR, Step 4 instructs creating a `demo-evidence/{record}` branch off the
  integration branch, committing only `docs/demo-evidence/{record}/` there, pushing it, and opening
  an evidence-only PR whose body carries `Refs #{record}` and no closing keyword
  (`Fixes`/`Closes`/`Resolves`).
- On a merged or closed PR, the brief's embedded raw URLs use the evidence-branch commit's SHA,
  never the dead branch's.
- Step 4 states the evidence PR is left open for a human and is never auto-merged.
- Step 4 states the routing decision is logged per `_shared/auto-decision-log.md` when a run
  directory resolves, and that the evidence PR's URL is named in the brief and the summary.
- `local-merge` behavior (commit on the current branch, no push, no PR) is unchanged.
- A new `node --test` suite under `tests/` asserts each of the above phrases in
  `verification-brief.md` Step 4's section, and fails when the merged/closed branch is removed.
- `npm test` passes.

## Technical Approach

Prose change to `verification-brief.md` Step 4's **Screenshot commit** paragraph, plus one
conformance test. Insert the PR-state check as the paragraph's first instruction, then branch.

PR-state detection is the builder's call. Two existing seams: `bin/pr-merge-state.js --run
{run-dir} --phase wrap-up` already prints `state: not-open` for a closed or merged PR (but needs a
resolvable run dir — on a late re-run the run dir may already be archived, so pass the archive path
per `_shared/timing-render.md`'s archive-path rule, or fall back to a direct
`gh pr view {branch} --json state`). Prefer reusing an existing resolver over a new `gh` call
shape; if none fits a run-dir-less re-run, a direct `gh pr view` read is acceptable. A read failure
(`read-failed`, `gh-absent`) must not silently fall through to the dead-branch commit — treat an
unreadable state as "cannot verify the branch is live" and take the evidence-branch route, or stop
and report, rather than committing blind (builder's call between those two; either is fail-loud).

The evidence branch is cut from a freshly fetched integration branch (`origin/main` or the
project's configured integration branch per `_shared/integration-model.md`) — never from the
stale local ref. Use `git -C {worktree} ...` forms per this repo's git-discipline conventions;
`git switch -c` in the run's worktree is fine because that worktree's own branch is already
merged. The evidence PR uses `gh pr create` (or the MCP transport per
`_shared/github-write-transport.md` when `gh` is absent).

`docs/REGISTRY.md`'s `docs/demo-evidence/{record}/*` row needs no change unless the builder adds
wording about the evidence PR — check it once.

## Gotchas

- Do not move acceptance labeling earlier on the leave-open path (the report's first suggestion):
  it already runs before the handoff there, so reordering fixes nothing. The console merge path's
  ordering is #3813's fix — do not reorder the console or Phase 4 here; this record's Step 4 check
  is the defense that holds on every path, including before #3813 lands and after it.
- `verification-brief.md` is a conformance-pinned file — several suites already read it
  (`tests/try-it-contract-conformance.test.js`, `tests/pr-run-comments.test.js`,
  `tests/verify-expectations-writer-conformance.test.js`, and others); run the full suite, not just
  the new test.
- A squash merge leaves the original branch commit reachable through GitHub's `refs/pull/{n}/head`,
  which is why existing in-run SHA-pinned URLs keep resolving after a squash — do not "fix" the
  in-run path's SHA pinning while here.
- The parent-gate brief (`verification-brief-parent-gate.md`) commits no screenshots today; this
  change does not need to reach it.
- Under `work-backend: local-files` the brief embeds a relative repo path, not a raw URL; the
  merged/closed route still applies (the evidence must reach the integration branch) but the embed
  stays relative.
- `local-merge` late re-runs are out of scope: there is no forge PR state to read, and a late
  re-run commits onto whatever branch the user has checked out, which is already the integration
  branch in the common case.

## Original request

verification-brief: under pr-first with the merge left open, the brief's screenshot commit lands on an already-merged branch

**Summary:** When the Review Console resolves the merge half to `leave-open` (no `auto:merge` grant), wrap-up's acceptance labeling — and with it `verification-brief.md` Step 4's screenshot commit to `docs/demo-evidence/{record}/` "on this run's current branch" — only runs after a human merges the PR. That commit then lands on a branch whose PR is already merged, so it never reaches the integration branch. The brief's SHA-pinned raw URLs work only as long as that orphaned commit stays reachable.

**Kind:** Gap

**Affected component:** `skills/wrap-up/verification-brief.md` Step 4 (screenshot commit), with `review-console.md`'s leave-open path

**Use case:** A pr-first run whose console left the PR open for a human merge, then got acceptance labeling after that merge (a later wrap-up, or the verify check `acceptance-labeling` failing on a missing `demo:pending`). The evidence commit needed a follow-up PR just to land on master, and the worktree couldn't be removed without losing it.

**Suggested change:** On the leave-open path, run acceptance labeling (or at least the screenshot commit and push) before the console hands the merge to the human, so the evidence rides the same PR. Alternatively, have Step 4 detect a merged PR and commit the evidence to a fresh branch with its own PR.

**Definition:** Needed — commit evidence before the human merge, or route a post-merge evidence commit to its own PR
