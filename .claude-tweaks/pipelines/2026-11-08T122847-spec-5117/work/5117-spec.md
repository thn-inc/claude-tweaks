# 5117: Cut redundant local full-suite runs in pipelines — affected-set per task, no worktree baseline run

## Current State

One `/claude-tweaks:flow` spec with K plan tasks runs roughly **K+3 full test suites locally**, each sized to the whole machine (`node --test`, `go test`, jest and xdist all default to about one worker per core) and only one of them routed through `verify.js`. With several parallel sessions this is the dominant local memory cost.

Where the full runs come from (superpowers 7.0.0, the installed version):
- `using-git-worktrees/SKILL.md` Step 3 “Verify Clean Baseline” runs the full suite on worktree creation. `plugin/skills/build/worktree-setup.md:148` endorses it (“The skill handles: … baseline test verification”). It runs **before** the Step 4 catch-up merge, so it tests a stale tree that Common Step 5 retests anyway.
- `subagent-driven-development/implementer-prompt.md:47-48`: “run the full suite once before committing”, once per task. `test-driven-development/SKILL.md` (Verify GREEN) reinforces it: “Other tests means the project’s suite”.
- The SDD final-review fix wave (one fix subagent under the implementer rules) runs it again.
- Build Common Step 5 runs the full suite through `verify.js`. This is the only run that writes the pass stamp.

The plugin already overrides the final whole-branch reviewer (“focused tests only, never the full suite”, `plugin/skills/build/dispatch.md:19`), and superpowers’ own task reviewers are focused-only. Implementers get nothing about test scope: `build/dispatch.md:14` only adds a foreground rule, and it hardcodes `npm test` there and in `plugin/skills/dispatch/task-prompt.md` (lines 157 and 347). That is wrong for Go, Python, or any other non-npm consumer.

Base health is already covered elsewhere: `verify.js` baseline adjudication compares failures against `origin/{integration-branch}`, and CI runs on the integration branch.

Related work this record does not duplicate: #3969 added a machine-wide suite slot lock and a `--test-concurrency` cap, but only in this repo’s maintainer-side `tools/run-tests.js`, so consumer projects running Go or other suites get no such cap. #4321/#4024 impact-select Common Step 5’s run (Node-traced). #4347 (PR #4476) moves Step 5’s full run to the PR’s CI run when declared. #4421 already directs implementers touching `plugin/bin/` to run two repo-wide scans “alongside its focused tests”. None of these changes the per-task implementer full-suite run or the worktree baseline run, which happen before Step 5.

## Deliverables

1. **No worktree baseline full run inside pipelines.** When `/claude-tweaks:build` creates a worktree inside a pipeline (`PIPELINE_RUN_DIR` set), its invocation of `/superpowers:using-git-worktrees` directs that skill to skip Step 3 “Verify Clean Baseline”. Dependency install still runs. `build/worktree-setup.md` step 3 states the override and why: the run predates catch-up, Common Step 5 plus baseline adjudication own pre-existing failures, and CI owns base health. Standalone `/build` keeps today’s behavior.

2. **Affected-set testing for implementers and the fix wave.** The SDD invocation instruction in `build/dispatch.md` Common Step 2 directs every per-task implementer dispatch, and the final-review fix dispatch, to run the **affected test set** (tests covering the files and packages the task touched) in place of superpowers’ “full suite once before committing”, and states that Common Step 5 runs the full suite once for the branch. TDD red/green focused runs are unchanged. The same rule applies to the `batched` strategy’s `/superpowers:executing-plans` invocation (its per-task “run tests” and final “run the whole suite”).

3. **No hardcoded `npm test` in shipped dispatch prompts.** `build/dispatch.md:14`, `dispatch/task-prompt.md:157`, and `dispatch/task-prompt.md:347` say “the project’s test command” (resolved per `plugin/skills/test/verification.md` Step 1) instead of `npm test`. The foreground rule itself is unchanged.

4. **Upstream pins.** `tools/upstream-drift/manifest.yml` pins the two newly overridden superpowers surfaces (the implementer-prompt full-suite line and the `using-git-worktrees` Step 3 baseline section), alongside the existing pin on SDD’s `## Final Review`. An upstream rewording then shows up as drift instead of silently re-enabling full runs.

5. **Conformance tests** pinning the new prose: the affected-set rule in the SDD invocation instruction, the pipeline baseline-skip in worktree setup, and the absence of a literal `npm test` instruction in the dispatch prompt templates.

## Release Note

Pipelines now run the full test suite once per branch instead of once per plan task plus a worktree baseline run, which cuts local CPU and memory load when several sessions run in parallel.

## Plan Review Clarifications

- Decided by the user at plan review: AC1's "names Common Step 5 as the single full-suite run" reads as Common Step 5's verification run, full or impact-selected when `.claude-tweaks/verify-scope.json` declares `impact` (`plugin/skills/test/verification.md`'s Re-verify scoping table). The rule says "Common Step 5's verification run (full, or impact-selected when declared) is the branch's one suite run". Where the impact map applies, CI owns the full run.
- Decided by the user at plan review: the affected test set ("tests covering the files and packages the task touched") is, when the project declares `impact`, what `verify.js --scope` selects from the impact map (`plugin/skills/test/impact-selection.md`). Otherwise it is the tests scoped to the touched packages or paths, plus any test that reads or imports a touched file.
