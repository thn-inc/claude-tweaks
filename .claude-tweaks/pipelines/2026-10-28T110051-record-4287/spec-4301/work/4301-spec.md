# 4301: Windows regression: 1 test file(s) newly failing after 2a21fbee9

Surface: infra

**Related:** #4149, #4166, #3064, #4286, #4289, #4242, #4244, #4246, #4303, #4287, #4299, #4385, #4388, #3982, #3995

Origin: windows-regression.yml post-merge check on 2a21fbee9 (PR #4166, #4149)

## Current State

The post-merge Windows check on 2a21fbee9 (run 40199814543) reports one new failure in `tests/hooks-gate-coverage.test.js`: "#4149 cwd cap: a push and a mkdir past the cap resolve in the overflow cwd" (`:1340`). Its first assertion fails, `gitTargets(cmd('git push'), '/r', opts).some((t) => t.dir === path.resolve('/main'))`. The run's isolated log for the file (`verify-logs/tests-isolated-tests+hooks-gate-coverage.test.js.log`) shows this as the file's only failure. #4149 added the test in that same commit.

The cause is a spelling mismatch between the fixture and the expectation. The block's `opts` is `{ overflowCwd: '/main' }` (`:1317`), a POSIX literal. Past `CWD_SET_CAP`, `forEachShellSegment` collapses the cwd set to that value as given (`plugin/bin/lib/hooks/git-command.js:1945-1946`), and a `git push` with no `-C` takes its `dir` straight from that cwd (`resolvedGitSegments`, `:851`). On win32 the dir stays `/main`, while `path.resolve('/main')` is `D:\main`. The write and mkdir assertions pass because those targets go through `pathImpl.resolve` on the file path. Linux and macOS cannot see the difference, because `path.resolve('/main')` is `/main` there. Probed at HEAD with an injected `pathImpl: path.win32` on macOS, the push dirs are `["/main","/r","\\a16",…]`: the overflow and start cwds stay as given, while the `cd`-derived cwds and every mkdir/write target go through `pathImpl.resolve`.

Production is not affected. The only production caller, `pre-tool-use.js:55`, passes `wtDetect.mainCheckoutRoot(cwd) || cwd`, which is a native absolute path built with `path` operations (`worktree-detect.js:50`), so the collapsed cwd already uses the same spelling as `path.resolve`.

## Deliverables

1. In `tests/hooks-gate-coverage.test.js:1342`, expect the push target `dir` to be the `'/main'` literal the walk passes through unresolved, not `path.resolve('/main')`. Keep the mkdir assertion on the next line as it is, because `mkdirTargets` resolves its target.
2. No change to `git-command.js`.

## Acceptance Criteria

- All `#4149 cwd cap` tests pass under `node --test tests/hooks-gate-coverage.test.js` on macOS/Linux, with the same test count.
- The push assertion still discriminates. On Linux it fails when the cap collapse is disabled locally, for example by raising `CWD_SET_CAP` above 20, because the push then resolves under the uncapped `/r`, `/a0`…`/a19` set and never under the overflow cwd.
- A `windows-regression.yml` dispatch on the branch shows the test passing and no newly failing test in `hooks-gate-coverage.test.js` versus its base.
- `npm test` passes.

## Technical Approach

Follow the repo-local `windows-checkout-test-parity` skill's `path.resolve` Anti-Patterns row: "A path the code passes through unresolved stays literal: `gitTargets`'s cwd `'/repo'` is one." Two alternatives were considered. Feeding `overflowCwd: path.resolve('/main')` would also pass, but it changes a fixture input the rest of the block shares in order to suit one assertion. Resolving the overflow cwd inside `forEachShellSegment` (`pathImpl.resolve(o)`) was rejected. The walk's own start cwd (`:1941`) is also used as given, so normalizing only the overflow value would leave the set half-normalized. It would also change the security write gate with no production symptom behind it, because the production caller already passes a native path.

### Key Files

- `tests/hooks-gate-coverage.test.js` — the #4149 cwd-cap push assertion (`:1342`)
- `plugin/bin/lib/hooks/git-command.js` — reference only (`forEachShellSegment`, `resolvedGitSegments`)
- `plugin/bin/lib/hooks/pre-tool-use.js` — reference only (the production `overflowCwd`)

## Gotchas

- Several open records edit `git-command.js`'s lexer half (#4244, #4246), and #4242 proposes splitting it out. This record touches only the test file, but a rebase may still shift the block's line numbers.
- If a future change makes `mainCheckoutRoot` return a git-printed `D:/…` spelling, the production collapse would then mix spellings with `cd`-derived cwds. That is a separate production defect, not this record's.
- Windows proof needs a real `windows-regression.yml` dispatch after the last code change. Linux cannot show the separator difference.
