# 2677: flow: multi-spec mode has no option to build independent specs in parallel worktrees

Surface: infra

## Current State
`/claude-tweaks:flow`'s multi-spec mode (`plugin/skills/flow/multi-spec.md`) runs every record's pipeline **sequentially** in one terminal (line ~3: "flow runs each one's pipeline sequentially in one terminal"). When `worktree` mode is used, all records share **one worktree for the whole run** (line ~128: "a sequential run uses one shared worktree for the whole run — NOT one per record"), accumulating on a single feature branch, finished once at the end.

The run already builds a dependency DAG from each target's `blocked-by:` declarations (lines ~22-33: "Build the DAG — for each target in the list, add edges from each prerequisite to the target itself, from its `blocked-by:` entries") and detects a circular dependency before running. It also already has a cross-spec file-overlap conflict detector (`multispec-conflict-detection.md`, using the shared `groupByFileOverlap` primitive from `bin/lib/issues/grouping.js` — the same primitive `/claude-tweaks:help`'s dashboard and `/claude-tweaks:specify`'s creation-time check use) — but this detector only produces a **warning footer** in the Pipeline Preview; it never changes execution order or concurrency (`multispec-conflict-detection.md`'s Anti-patterns: "never auto-reorder to dodge a conflict").

So the DAG-building and overlap-detection groundwork both already exist, but nothing in the current design uses the DAG to identify mutually-independent siblings and build them concurrently — every record runs one after another regardless of whether the DAG shows true independence. A real 6-spec run demonstrated the cost: two specs shared only a common upstream dependency (not each other) and were therefore independently buildable once that dependency merged, but ran fully sequentially anyway, paying the full build→test→review→wrap-up cost for both instead of overlapping them.

## Deliverables
1. Decide the concurrency model for independent-subset execution, choosing between the two options the original report names (or a third if research surfaces one), with recorded rationale:
   - **(a) Separate worktrees per independent spec** with a merge-back step before the consolidated Review Console — simpler to reason about, but multiplies worktree/PR bookkeeping and complicates the consolidated Review Console's single-PR model.
   - **(b) One shared worktree, parallelized non-conflicting builds within it** — preserves the current single-PR/single-worktree design, but requires real conflict detection between concurrently-building specs (upgrading the existing warning-only `groupByFileOverlap` check into an actual concurrency gate, not just a footer).
2. Extend the existing DAG-building step (`multi-spec.md` lines ~22-33) to identify, from the already-built dependency graph, which subset of targets are mutually independent (no `blocked-by:` edge between them, directly or transitively) at any given point in the run.
3. Implement the chosen concurrency model so the identified independent subset builds concurrently instead of strictly sequentially, while records with real dependency edges still run in dependency order.
4. Update `multi-spec.md` and any of its per-topic sub-files (`multispec-run-dir-layout.md`, `multispec-pr-checklist.md`, `multispec-review-console.md`, `multispec-progress-banner.md`, `multispec-failure-handling.md`, etc.) that assume strictly sequential execution, so they correctly describe the new concurrent-subset behavior.
5. Gate the new behavior behind an opt-in flag/mode (per the original report: "There is currently no flag or mode that lets a user opt into parallel-worktree execution") — sequential remains the default so existing behavior is unchanged unless a user explicitly requests parallel execution.

## Acceptance Criteria
- A decision is recorded (in this record's resolution, a linked design note, or a code comment at the decision point) naming which concurrency model was chosen and why, referencing the tradeoffs named in the original report.
- Given a multi-spec run whose DAG contains at least one pair of mutually-independent targets (no direct or transitive `blocked-by:` edge between them), those targets build concurrently under the new opt-in flag/mode — verified by a test or a documented manual repro showing overlapping build windows (e.g. timestamps, or a scripted DAG scenario in a test file).
- Given a multi-spec run whose DAG is a strict linear chain (every target `blocked-by:` the previous), behavior under the new flag/mode is unchanged from today's sequential execution — no regression on the common case.
- Without the new flag/mode, `/claude-tweaks:flow`'s behavior is byte-for-byte unchanged (still sequential, still single shared worktree under `worktree` mode) — this is strictly additive, opt-in behavior.
- If concurrency model (b) is chosen: the existing warning-only `groupByFileOverlap` conflict check (`multispec-conflict-detection.md`) is upgraded to actually prevent (not just warn about) two file-overlapping targets from building concurrently — they still run, but sequentially relative to each other even while other independent targets run in parallel.
- If concurrency model (a) is chosen: the merge-back step before the consolidated Review Console is implemented and documented, and the Review Console's single-PR model (`multispec-review-console.md`) is updated to describe how per-spec worktree results reconcile into it.

## Original request

flow: multi-spec mode has no option to build independent specs in parallel worktrees

**Summary:** `/claude-tweaks:flow`'s multi-spec mode has no option to build mutually-independent specs in parallel — every spec runs its full build→test→review→wrap-up cycle sequentially on one shared worktree, even when two specs' own `blocked-by:` graph shows no dependency between them.

**Kind:** Gap

**Affected component:** `/claude-tweaks:flow` (multi-spec mode)

**Use case:** A 6-spec multi-spec run decomposing one design doc took several hours end-to-end, almost entirely because every spec ran strictly one-after-another on the same shared worktree. Most of the graph was a linear chain (each spec explicitly blocked-by the previous), so sequential execution was actually correct there — but two of the six specs were siblings: one was blocked-by an earlier spec only, and the other was blocked-by that same earlier spec (not by each other), meaning once their shared dependency merged onto the branch, both were independently buildable. `/flow`'s multi-spec mode had no mechanism to recognize this and build them concurrently on separate worktrees (merging back into the shared branch once each finished) — it built them one after the other regardless, paying the full sequential build+test+review+wrap-up cost for both. For a decomposition whose dependency graph is wider/shallower than mine (e.g., three or more units that only share one common foundation dependency), the wasted wall-clock from full linear sequencing compounds significantly. There is currently no flag or mode that lets a user opt into parallel-worktree execution for the independent subset of a multi-spec run's own dependency graph — the mode is unconditionally serial today.

**Definition:** Needed — open choice between (a) fully separate worktrees per independent spec with a merge-back step before the consolidated review console, vs. (b) some other concurrency model that keeps one shared worktree but parallelizes non-conflicting spec builds within it. Both are viable; (a) is simpler to reason about but multiplies worktree/PR bookkeeping and complicates the consolidated Review Console's single-PR model, while (b) preserves the current single-PR/single-worktree design but requires real conflict detection between concurrently-building specs. No stated preference here — this report is the gap, not the design.

**Plugin version:** 6.126.0
