# 2733: flow: decide whether a dependency-derivable spec-sequencing conflict should self-resolve instead of asking

Surface: infra

## Current State

`/flow`'s pipeline processed a 3-record batch (`#2681,#2670,#2682`) where `#2682`'s own spec body hard-required `#2670`/`#2681` to be genuinely merged into `main` first (its Deliverable #1: "confirm #2670 and #2681 are actually merged... verify it fresh at execution time," with an explicit escalation clause for exactly this situation). Running all 3 together in one shared multi-spec worktree (the documented default) would have had `#2682`'s build execute against an unmerged, still-in-progress branch — a false premise its own spec explicitly anticipated and would have caught via a build-time stop, per its escalation clause.

This session chose to stop and ask the user how to sequence the run (`AskUserQuestion`, 3 options) rather than let the pipeline's own documented fallback (option 2: proceed, let `#2682`'s build discover and report the false premise per its own escalation clause) run automatically. The user picked the safer restructuring option (split into two `/flow` runs).

This is a genuine judgment call, not a clear-cut bug — worth a design decision rather than an assumed answer:

- **For asking:** the alternative (proceeding, then having `#2682`'s build agent discover the problem) wastes a full build dispatch's worth of work discovering something the orchestrator could have determined for free by reading both specs' `blocked-by:`/Deliverables text before starting. A structural coupling this severe (a downstream record's own build gate would fail against the chosen batch shape) seems like exactly the kind of thing Step 2.6's shape check exists to catch — but Step 2.6 explicitly does NOT hard-stop under default `auto` (`SKILL.md`'s own "When NOT to Use" note: "under flow's own default auto mode, a Step 2.6 hard-fail auto-resolves to 'proceed anyway'"), and this particular signal (a downstream spec's premise-check literally requiring prior specs to be merged, in a mode that groups them into one shared unmerged worktree) doesn't match any of Step 2.6's enumerated hard-fail signals (cross-task dependency chains, file-scope leakage, oversized tasks) — so nothing in the documented pre-flight actually catches it today.
- **Against asking:** `_shared/auto-mode-contract.md`'s stance is that `auto` mode should resolve derivable decisions itself and log them, reserving human stops for genuinely undecidable choices or HARD-GATEs. This decision (whether records with a "must be actually merged first" premise-check belong in the same shared-worktree batch as their own blockers) is mechanically derivable from each record's own body text, without needing a human's judgment.

`flow/multi-spec.md` already has two relevant mechanisms this record's investigation confirmed exist: "Dependency-aware ordering" (topologically sorts records against their `blocked-by:` edges, reconciled with the user's given order) and "Cross-spec conflict detection" (Step 5, warns on overlapping `### Key Files`, via the same `groupByFileOverlap` primitive `/help` and `/specify` already use). Neither currently reads a downstream record's body prose for a *merge-required* premise-check the way this case needed — dependency ordering only sequences by `blocked-by:` edges (which #2682 may or may not have carried structurally), and conflict detection only looks at file overlap, not prose-stated merge preconditions.

## Deliverables

- [ ] Decide: should `/flow`'s multi-spec pre-flight (`multi-spec.md`'s Dependency-aware ordering / Cross-spec conflict detection) add a new structural signal — a downstream spec's body containing a premise-check that requires an in-batch prerequisite to be already-merged (not just already-built) — and either hard-fail-and-auto-split the batch (matching this session's outcome) or downgrade to a ledger note the way other soft signals do?
- [ ] If yes: implement the signal and its `auto`-mode resolution (auto-split into sequential single/sub-batch runs vs. proceed-with-ledger-note, per whichever this decision lands on).
- [ ] If no (asking a human here was correct and should stay a stop): document why this specific signal is intentionally exempt from `auto`'s "resolve derivable decisions itself" default, so a future session doesn't file this same finding again.

## Acceptance Criteria

1. A documented decision exists (in `multi-spec.md` or `_shared/auto-mode-contract.md`) for this specific case, whichever way it resolves.
2. If a new signal is added, a `/flow` run against a batch with this shape resolves it per the new decision, with no `AskUserQuestion` under default `auto` (or a justified one, if the decision keeps it as a stop).
3. `npm test` passes.

## Technical Approach

Start from `multi-spec.md`'s two existing detection mechanisms (Dependency-aware ordering, Cross-spec conflict detection) rather than inventing a third, parallel one — the new signal (a downstream body's merge-required premise-check) is closer in shape to dependency ordering (it's about sequencing, not file overlap) so extending that section is the more natural fit if the decision favors building it. A reasonable detection heuristic: scan a to-be-batched record's body for language matching an existing-prerequisite-must-be-merged pattern (this record's own #2682 example phrased it as an explicit Deliverable #1 with an escalation clause) cross-referenced against which other records in the same batch that language names — but the exact heuristic is itself part of what Deliverable 1's decision should settle, not pre-decided here.

### Key Files

- `plugin/skills/flow/multi-spec.md` — "Dependency-aware ordering" and "Cross-spec conflict detection" sections, the two existing mechanisms this decision extends or documents an exemption from
- `plugin/skills/flow/SKILL.md` — Step 2.6's shape-check hard-fail signal enumeration (cross-task dependency chains, file-scope leakage, oversized tasks) and its "auto mode resolves to proceed anyway" note, the boundary this record's new signal would sit next to
- `plugin/skills/_shared/auto-mode-contract.md` — the "resolve derivable decisions itself" stance this record's Deliverable 3 (if "no") would document an exemption from

## Gotchas

- Don't build a detector before Deliverable 1's decision is actually made — this is a design-decision record first, an implementation record second; a build that jumps straight to code without resolving which way the decision goes risks building the wrong signal.
- The concrete example (#2682's Deliverable #1 language) is one instance, not necessarily representative of how every future spec would phrase a merge-required premise-check — whatever heuristic gets built should be tested against more than this one worked example if practical.
