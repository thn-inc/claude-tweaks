# 5232: Route driver-admitted singletons from /claude-tweaks:dispatch to drive.js

Surface: backend

**Related:** #4735, #4365

## Overview

This unit is Phase 3 of the pipeline driver design (`docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, section "Phase 3 — Entry from `/claude-tweaks:dispatch`"), following Phase 1 (refs #5215) and Phase 2 (refs #5223). It lets `/claude-tweaks:dispatch` hand an eligible singleton to the driver as one background call, so the session spends tokens on the launch and one final event line instead of an express-agent conversation.

Today `plugin/skills/dispatch/SKILL.md`'s Express lane paragraph routes an eligible singleton to the prose express agent (`express-prompt.md`) after Step 4's run-directory mint. This unit adds a route in front of it. When `express-driver` resolves `split` or `on` (read once per firing, alongside `express-lane`), the session asks the driver whether it would take the record, and if so runs `drive.js` in the background and reads only its final event line. Whether the driver takes a record is always asked of the driver, never re-derived in prose.

Two driver CLI additions make that possible: `drive.js --check #N` (the verdict as one JSON line, no writes) and `drive.js #N --run <dir>` (adopt the run directory and the worktree dispatch already created, mint and create neither). The route's text lives in a new sub-file, `plugin/skills/dispatch/driver-route.md`, read only when `express-driver` is not `off`. The phase's done criterion is acceptance criterion 8 below.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Any change to `express-prompt.md`, the express gate (`express-lane.js gate`), or the prose express lane's behavior. It stays as it is and is the path every record the driver does not take follows.
- Queue selection. Dispatch's drain keeps owning it in this phase; moving it into the driver is Phase 5 (#5229, #5230).
- The driver's own settle (#5219) and any change to what it does on a standalone stop. This unit only passes the flag that turns it off.
- Bundles and multi-record groups: the route applies to a singleton group only, as the express lane does.
- A `/claude-tweaks:flow` entry to the driver, and any hub code.
- A new Subagent Contract dispatch site: the driver call is a Bash call, not a Task dispatch, so no skill-graph edge is added.

## Acceptance Criteria

1. `drive.js --check #N` prints one JSON line carrying the eligibility and admission verdict and every reason, and makes no write of any kind. A test over a fake runner records every call the command makes and asserts none is a claim, a run-directory or worktree creation, a file write, or a forge write (reads of the record are allowed), for an admitted record and for each class of refused one.
2. `drive.js #N --run <dir>` adopts the given run directory and the worktree it is run from, and mints and creates neither. A directory that is missing, or not anchored under the main checkout, or a working directory that is not a linked worktree of that checkout, is refused with exit 3 and nothing written. The adopted run's claim `runId` is the given directory's basename. Test cases this guard must pass, each its own test: a run directory with dot segments that leaves the checkout once normalized (`{main}/.claude-tweaks/pipelines/x/../../../elsewhere`); the same path with a trailing slash; a symlink under the pipelines directory that resolves outside the checkout; a worktree-local shadow `.claude-tweaks/pipelines` directory; a path that contains the main checkout's path as a substring of another component; and a working directory that is the main checkout itself. Each is refused with nothing written. Percent-encoding, uppercase schemes and mount prefixes do not apply to a filesystem path and are not tested.
3. With `express-driver` resolving `off` (or unreadable, or an unknown value), a dispatch firing reads no part of `driver-route.md` and makes no `drive.js` call. `plugin/skills/dispatch/SKILL.md` names `driver-route.md` only in the one conditional pointer, names no `drive.js` call, and `express-driver` is resolved by the same `resolve-policy.js` call as `express-lane`.
4. Under `split`, an even-numbered record the driver accepts is handed to the driver and an odd-numbered one follows today's path, with the parity decided only by `drive.js --check`'s verdict: `driver-route.md` states no parity rule and no eligibility rule of its own. A `--check` that does not admit, in any of the ways the Closed rule table lists, takes today's path for that record.
5. Each outcome word of the driver's final event line is handled as stated below, and an outcome word outside this list, a missing final line, a final line that is not one JSON object, or any non-zero exit that left no parseable final line (the `--run` guard's exit 3 included) is treated as `blocked` through `two-call-gate.md` section 5: a guard failure is a dispatch-side defect, never silently routed onward.
   - `merged`, `armed`, `pending-review`: the group ends once `express-lane.js verify --run "{minted-run-dir}" --issue {n}` exits 0; non-zero is `blocked`.
   - `express-escalated`: re-bind with `hooks.js record-worktree --run "{minted-run-dir}" "{worktree}" --dispatch`, then the ordinary first call on the same run directory and the same worktree, which still exist because the driver ran with its settle off.
   - `blocked`: `two-call-gate.md` section 5 and dispatch's Settle.
   - a refusal (the verdict changed between the check and the run): the driver's refusal outcome word, which the driver emits only for a refusal that wrote nothing (no claim, no PR); today's path for that record, with one `SKIP` line.
   Once the call returns, `drain-pr-overlap.md`'s Step 5 list write runs as it does after the express call. The group counts for `settle-and-merge.md`'s Drain-overlap hold like any auto-merge group. Decision: the driver applies the hold itself, in code. The route hands `drive.js` the drain's in-flight PR list and the driver stops at `pending-review` on any shared path before it marks its PR ready (acceptance criterion 9). The merge stays driver code on this route too, so no model performs it.
6. The session makes no `sleep` call while the driver runs, waits for the background task's completion notification, and reads only the final event line.
7. `plugin/skills/dispatch/SKILL.md` is under `RAIL_BYTES` (52,500 bytes) after the change, and the existing `STEP5_FACTS` and `LOOP_FACTS` in `tests/dispatch-express-routing-prose.test.js` still pass without being loosened.
8. On one live drain with at least one driver-accepted record, that record completes through the driver, and the session's own token use for it (the launch and the summary read) is quoted in this record's closing comment.

Before the driver's merge step (refs #5226) marks its PR ready, it reads the changed paths of its own PR and of each listed PR from the forge; if any path is shared, the run ends `pending-review` with the overlapping PR named in the event detail and the PR left in draft. ## Technical Approach

- **Where the route sits.** Step 5's Express lane paragraph keeps its text and its pinned facts. The new route runs before it, in the same place: after Step 4's mint, before `sibling-session-check.md`'s bind. A record the driver does not take falls through to the express gate unchanged, so a record refused by `--check` is never worse off than today.
- **Asking the driver.** `drive.js --check #N` prints the eligibility and admission verdict as one JSON line and exits 0 whenever it printed a verdict, admitting or refusing; a non-zero exit means no verdict could be computed. Under `split` that verdict already refuses odd issue numbers (#5216). Dispatch reads one boolean from the line and the reasons for the log, and nothing else.
- **Who does what, in order.** Dispatch: Step 4 mints the run directory; Step 5 creates and enters the group's worktree; `sibling-session-check.md`'s bind runs without `--dispatch`; `drive.js --check`; then `drive.js #N --run`. The driver: claims the record itself (the express procedure's step 1 is also run by its agent, `express-prompt.md`: "run step 1's claim yourself"), under the adopted run directory, so the claim `runId` is that directory's basename; then everything after, up to its outcome. Dispatch's bind is the only bind before the call; `express-escalated` is the only case that re-binds. A refusal writes nothing before admission is re-confirmed, so falling through to the express gate or the normal path is clean. After `express-escalated` the claim, worktree, branch and run directory stay (the express lane's Escalation rule, which the design's settle-off carries over); after `blocked`, whatever the driver already pushed (a draft PR, commits) stays for `two-call-gate.md` section 5 and Settle, as after an express `blocked`.
- **Why the driver, not the express gate, decides.** The driver's admission is the express gate's own `evaluateRecordEligibility` with the ceremony-label option (design, Eligibility), so every express check except the ceremony-label rule still applies to a record the driver takes; the express gate is not also run for it.
- **Adopting the run.** Dispatch has already minted the run directory and (Step 5) created and entered the group's worktree. `drive.js #N --run <dir>` uses both: the directory must be anchored under the main checkout, the same guard the other run-directory CLIs apply (`resolveTarget` in `plugin/bin/lib/log-decision/append.js`), and the worktree is the one the command is run from. The record is bound without `--dispatch`, as the prose express path binds it, because the #3225 config gate guards a `/flow`-framed run and the driver writes `config.yml` only once its PR exists.
- **Settle off.** The call passes the flag from #5219, because here the dispatch session settles (the design's "When a run stops": the dispatch session's own hand-back and Settle apply, and the driver does not settle).
- **Waiting and reading.** One background Bash call. Step 5 is sequential, one group at a time, so no other group of this session is waiting on it. The session ends its turn on the completion notification; it never polls with `sleep`. It then reads only the last line of the call's own output (a bounded `tail -n 1` of the output file the harness names for the background task, run as one plain command), which is the final event line (`{ ts, run, record, step, status, ms, ... }` carrying the outcome word and the PR number, per the design's Event lines); a non-zero exit is read the same way. The run directory's `driver-events.jsonl` is not the read source, because a merge archives the run directory. When Step 5's cwd-pinned-subagent case applies (#447), the call is prefixed with `cd {worktree-path} &&` exactly as every command of the prose calls is.
- **Logging a decline.** A record that takes today's path after a `--check` that did not admit, or after a refusal, gets one `SKIP` line per `_shared/auto-decision-log.md`'s Degrade-trace rule, written with `log-decision.js --run "{minted-run-dir}" --status SKIP --step "Driver route"` and `--text-file` (the reasons come from a CLI, not from this skill's own text). The session writes no model-selection log line for a driver group, since no Task call resolved a model; the final event line's `costUsd` and `turns` are that record.
- **Mapping outcomes.** As in acceptance criterion 5, the express paragraph's mapping applied to the driver's outcome word instead of an express call's status line.
- **Where the text lives.** `driver-route.md`, read only when `express-driver` is not `off`; `SKILL.md` carries a one-line conditional pointer. Because `SKILL.md` has 44 bytes of headroom, the pointer and the added `express-driver` read need their length trimmed elsewhere in the file first. Which text to trim is the builder's choice: the plan lists each trimmed passage with the tests that pin it, and no pinned fact in any `tests/*.test.js` over `SKILL.md` is loosened. The Phase 5 edit of this file (#5230) needs room too, so the builder aims to end at least 1,000 bytes under `RAIL_BYTES`; that is advisory, and acceptance criterion 7's bound is `RAIL_BYTES` itself.

## Gotchas

- Dispatch's Step 5 forbids a call creating a worktree of its own, and the driver's step 3 creates one for a standalone run. That is why `--run` also adopts the current worktree here; a `--run` that adopted only the directory would leave two worktrees for one record and break the `express-escalated` continuation, which needs the same worktree.
- A merge archives the run directory, so the final line is read from the background call's own output, and the post-merge `express-lane.js verify` reads the archived copy, as the prose paragraph already does.
- `express-escalated` re-binds with `--dispatch`; the first bind did not use it. Reusing the first bind's form for the re-bind leaves the #3225 config gate unarmed for the ordinary first call.
- The route decision never reads the record's labels or number itself. A prose parity or eligibility rule would drift from `admission.js`, and `split` exists to compare like records, so a drifted rule corrupts the comparison.
- The prose express lane stays the comparison baseline, so any trim of `SKILL.md` that touches the Express lane paragraph must keep every fact `STEP5_FACTS` pins.
- Do not add a skill-graph edge or a Subagent Contract site for the driver call: it is a Bash call.
- `drive.js --check` is read-only by contract; if admission needs a fact only a write can produce, it reports the reason as unknown and refuses, never writes to find out.

## Decision Rationale

- The driver is asked, not re-derived: eligibility, authorization and the `split` parity live in `admission.js`, so a prose copy in the dispatch skill would be a second statement of record that drifts.
- The route lives in a sub-file read only when `express-driver` is not `off`, because every consumer project runs the dispatch skill and `SKILL.md` is at the Read rail; a default-off feature should cost an `off` firing nothing.
- The driver does not settle under dispatch because dispatch's own Settle and hand-back already own claim, worktree and run-directory teardown, and a second settle would race it.
- Phase 3 leaves queue selection with dispatch; the design moves it into the driver only in Phase 5.

## As Built (architecture alignment, /build Common Step 4.5)

Places where the build is better than the spec, kept as built:

1. **Reading the output.** The route reads the output with `tail -n 3 {output-file}`, not `tail -n 1`. The harness appends a blank line and `[exited with code N]` after the output of a background call (probed at build, logged as premise reversed). The final event line is the last JSON line above that.
2. **Failed bind.** A bind that prints no `worktree recorded for` line is a Closed-rule state the spec does not list. It produces one refusal line and one `SKIP`, then today's path, so `--run` never runs unbound.
3. **`--run` refusals.** `--run` also refuses with exit 3, writing nothing, in three more cases:
   - the run directory is not a direct child of `{main}/.claude-tweaks/pipelines`;
   - its `run-state.json` names a different worktree;
   - the worktree has a detached HEAD.
   
   `--run` also requires the settle-off flag and exactly one record.
4. **Escalation line.** Under `--run`, the driver still writes the express lane's escalation line on a pre-push escalation (`settle-escalate`) whenever the check step did not already log it. Without that line, `/build`'s already-shipped assessment would read the driver worker's unmerged commits as proof that the record had shipped. If the escalate write fails, the outcome is `blocked`.
5. **No-claim releases.** The new `driver-no-claim` parenthetical (route, `two-call-gate.md` §5, `wrap-up/cleanup-procedures-execution.md` Section E, `wrap-up/flags.md`) skips the claim release in three cases:
   - after a driver call that left no final line and no `Step 2.8: claimed #{n}` line (an absent `decisions.md` counts as no line);
   - after a driver claim stop on `claim-exit-2`;
   - after a driver claim stop on `claim-exit-3` or `claim-exit-6`.
   
   This keeps dispatch from posting a false release comment, or editing a foreign tombstone, on a record this run never claimed.
6. **Near-duplicate hold.** The near-duplicate hold applies whenever the firing's queue pull wrote `dispatch-near-dup-pairs.json`, bare drains included. That is the clarification's "passes it whenever this firing wrote that file" taken literally, and `driver-route.md` states it as deliberate: it holds more, never less.
