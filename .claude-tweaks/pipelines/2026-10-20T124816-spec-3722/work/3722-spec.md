# 3722: Nested-dispatch rule: a late re-wake loses the final report; qualify the never-re-woken claims

Origin: #3714 probe comment

Defer-reason: genuinely-larger

## Current State

#3722's probes (evidence: https://github.com/thn-inc/claude-tweaks/issues/3722#issuecomment-6294932708) showed that native re-wake cannot replace the `sleep 20` keep-alive. A dispatched agent that ends its turn with a nested child live is held open and re-woken only in interactive Claude Code 2.1.302. Headless 2.1.263, 2.1.274, 2.1.290 and 2.1.299 never re-wake it, and the child's result goes to the top-level session instead. Headless 2.1.302 and 2.1.304 run the nested `Agent` call synchronously. The `sleep 20` loop from #3078 stays correct in every setting measured, so it is kept.

The probes found a real bug in that rule. In interactive 2.1.302 the harness holds a dispatched agent's result while any nested child it launched is still live. `TaskStop` cannot stop a nested child: "Task [id] is owned by [id]; agent [id] cannot stop it." So a child abandoned at the bound keeps running, and when it finishes it re-wakes the agent after the agent's final reply. The rule then says to "repeat that final `STATUS:` line unchanged". The dispatcher keeps only the agent's latest reply, so it received the bare `STATUS: DONE_WITH_CONCERNS` and lost the full report. The same instruction appears in `_shared/subagent-dispatch-core.md`'s nested-children paragraph, `dispatch/task-prompt.md` item 7, and both fenced templates.

`_shared/subagent-dispatch-core.md`'s "Background work" paragraph states "A dispatched agent is never re-woken once its turn ends". Item 7 says "Once your turn ends nothing re-wakes you", and both templates say a backgrounded run "is never re-woken". These claims are false in interactive 2.1.302, where nested children and a `Monitor` watch both re-wake the agent. What holds everywhere is narrower: the agent cannot count on being re-woken. The SubagentStop hook already skips grading an `INTERIM_STATUS:` reply and a stop with nested dispatches still pending (#3015), so it needs no change.

## Deliverables

Change the late-re-wake instruction in all four copies of the nested-children rule (`_shared/subagent-dispatch-core.md`, `dispatch/task-prompt.md` item 7, both fenced templates): a late notification that re-wakes the agent after its final reply is answered by repeating the whole final reply unchanged, not only its `STATUS:` line, because the dispatcher keeps only the latest reply.

In `_shared/subagent-dispatch-core.md`'s nested-children paragraph, record that an abandoned child cannot be stopped (`TaskStop` refuses a nested child) and keeps running, and that the harness may hold the agent's final result until it finishes. The bound caps the wait, not the delivery.

Qualify the never-re-woken claims: the core "Background work" and "Bounded polling" paragraphs, item 7's "nothing re-wakes you", both templates' "it is never re-woken", `build/dispatch.md`'s "is never re-woken", and `review/step3-lens-dispatch.md`'s Foreground note ("none reaches a dispatched agent") say the agent cannot count on being re-woken. The core paragraph alone carries the measured mode/version facts and cites #3722's evidence.

Update `tests/foreground-execution-instruction.test.js`: retarget the SHARED_RULE late-re-wake pattern to the whole-final-reply wording, and add a go-red proof that a copy reverting to "repeat that final `STATUS:` line" fails. Leave the `sleep 20` x 60 primitive pin unchanged.

## Acceptance Criteria

All four copies say a late re-wake after the final reply repeats the whole final reply unchanged, and none still says to repeat only the `STATUS:` line. The agreement test passes, and it goes red when any one copy is reverted.

The core nested-children paragraph states that an abandoned nested child cannot be stopped and may hold back the agent's final result until it finishes.

No copy states the never-re-woken claim unqualified. The core "Background work" paragraph names the measured facts: interactive 2.1.302 holds the agent open, headless 2.1.299 and older do not re-wake it, and headless 2.1.302+ runs nested calls synchronously.

The `sleep 20`, at most 60 (20 minutes) per wave, primitive is unchanged in all four copies, and its agreement test still passes.

## Release Note

A dispatched review whose nested reader overruns its wait no longer loses its final report to a late wake-up.
