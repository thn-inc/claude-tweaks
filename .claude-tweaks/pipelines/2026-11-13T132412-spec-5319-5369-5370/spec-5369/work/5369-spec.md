# 5369: verify.js: a localRuns declaration key that runs CI-declared suites on the developer machine only with --local

**Related:** #5319 (the plain `npm test` half of the same decision), #5134 (CI wait versus the 600 s foreground ceiling), #5353 (a conflicted PR), #5368 (slot-lane wait for a one-second suite), #5173, #5135, #5093

Verified-as-of: 79cd5710d803946af6d845e8f430fbc9c8ef84f0

## Current State

`verify.js` already has both halves of "runs on a developer machine are impact-selected, the whole suite runs in CI". Impact selection (#4024, `plugin/skills/test/impact-selection.md`) narrows a suite to the test files a change can affect. The CI source (#4347, `plugin/skills/test/ci-source.md`) lets a `--scope` run take a `ci`-declared suite's verdict from the PR's CI job at HEAD instead of running it. The PR's CI job runs the whole suite on every push, and under `pr-first` the merge gate (`plugin/skills/_shared/pr-first-merge.md` Step 2.5) does not merge until the PR's checks and head workflow runs are green.

The runner treats the CI source as optional, though. Whenever CI cannot answer, it runs the suite on this machine "exactly as selected", and a run with no `--scope` never asks CI at all. Measured on the maintainer Mac between 9 and 13 November 2026, from 91 `verify` events in 38 pipeline runs and from each worktree's last `report.json`:

1. **Unscoped runs.** 21 of the 91 runs passed no `--scope` and ran every suite's full command: 149 minutes of test time, not counting slot waits.
2. **HEAD not pushed.** Of the nine scoped runs whose report is still on disk, six fell back with `head-not-pushed` and ran their impact subset on this machine: 156 to 613 test files and 118 to 341 seconds of test time each. One of them was the 591-file subset in the 13 November load measurement (CPU at 100%, load 50 to 110, two test runs causing about three quarters of all process creation).
3. **Fallback to the full command.** When selection cannot narrow (2 of 62 selections) and CI cannot answer, the full command runs here.

4. **A red CI job always runs the suite here.** `plugin/bin/lib/verify/ci-source.js` downloads the job log with `gh api repos/{owner}/{repo}/actions/jobs/{id}/logs`. `gh` 2.103.3 refuses to print a response that contains terminal escape sequences unless `--allow-escape-sequences` is passed (stderr: "the response contains terminal escape sequences; pass --allow-escape-sequences to output it anyway"), and the `test` job's merged log contains them, so the download fails every time. On 13 November all four CI-answered runs whose report is still on disk carry "its log could not be fetched". A green job still passes without its log, but a red job falls back with `ci-log-unavailable` and the suite runs here. In #5319's build that was a 180-second slot wait and a 284-second whole-suite run on this machine for a failure CI had already found.

Each of those runs repeated work the PR's `test` job does on the same commit minutes later. The instructions to pass `--scope` and to push first were already written in the skills when these runs happened, so the runner itself has to be able to refuse. A project needs a way to say "this suite's verdict comes from CI; run it here only when asked", and the runner needs an outcome that means "no verdict yet, push first" instead of quietly running the suite.

Only nine reports could be read because `report.json` is overwritten by every run and the `verify` event does not record whether CI answered.

This record adds the declaration key and the runner behaviour. The follow-up record (blocked by this one) changes the pipeline skills to use it and opts this repo in.

## Deliverables

- [ ] **Declaration key.** A top-level `localRuns` key in `.claude-tweaks/verify-scope.json` with the one value `"on-request"`, valid only together with a `ci` block. A reader older than the key ignores it, because the validator has no check for unknown top-level keys. Without the key nothing changes.
- [ ] **Runner (`plugin/bin/verify.js`), under the key.**
  - A `--scope` run without `--local` takes every selected CI-declared suite from CI. When CI cannot answer one of them, the run stops before any check starts, exits 3, writes no pass stamp, and prints the suite, the `ci-source.md` fallback reason and the two ways on: push the branch and re-run, or pass `--local`. The printed text must be enough for a caller that has never read the new skill prose.
  - Exit 3 is new. It means "no verdict yet" and is never a test failure.
  - A run with `--local` does not consult CI and runs each selected suite here as selected: the impact subset, or the full command when selection falls back.
  - A run with neither `--scope` nor `--local` exits 2 and names both flags, so running every suite's full command here is always a stated choice.
  - Suites with no `ci` source, `types`, `lint`, the local flaky retry after a red CI job, and `--baseline` adjudication behave as today.
- [ ] **CI log download.** The job-log download passes `--allow-escape-sequences`, and retries once without the flag when `gh` rejects it as an unknown flag (an older `gh`). Under the key, a red CI job whose log still cannot be downloaded fails the suite and names the run URL, with no run on this machine: the verdict is CI's, and `--local` reproduces it here. Without the key that case keeps today's local fallback.
- [ ] **`--local` without the key** means the same thing: CI is not consulted and the selected suites run here.
- [ ] **Audit trail.** The `verify` event, and through it `timing.json`'s verify entry, records for each CI-declared suite whether CI answered and the fallback reason, and whether `--local` was passed.
- [ ] **Docs.** `ci-source.md`, `suite-slots.md` and `docs/plugin-structure.md` describe the key, the flag and exit 3. `ci-source.md`'s statement that every other outcome "runs the suite locally" is limited to a declaration without the key.
- [ ] **Tests** in the existing suites: declaration validation, each runner outcome through the CLI, and the event fields.

**Decision** (unscoped runs under the key). Only an unscoped run that would run a CI-declared suite on this machine exits 2. A run whose `--cmd` set names no CI-declared suite (only `types`, `lint`, or suites with no `ci` source) runs as it does without the key. The Deliverable line "A run with neither `--scope` nor `--local` exits 2" is read as "a run naming a CI-declared suite", which is what acceptance criteria 3 and 6 already say together.

**Decision** (`--stamp-suite` under the key). A `--stamp-suite` chunk of a CI-declared suite is a local run of that suite. Without `--local` it exits 2 and names `--local`; it does not consult CI. With `--local` it runs here as today. A chunk of a suite with no `ci` source is unaffected. `plugin/skills/test/ci-source.md` and `plugin/skills/test/stamp-composition.md` say so.

**Decision** (anything this record leaves open). A CI-declared suite never runs on this machine without `--local`. Everything else behaves as it does without the key. When two outcomes could apply to one run, "no verdict yet" (exit 3) is decided before any check or retry starts. Plan review applies this rule without asking.

These three decisions were written on 2026-11-13 by the session that shaped this record, under the maintainer's instruction to decide this design. They are listed for ratification at the run's Review Console (PR #5371), and reversing one is a small change before merge.

## Acceptance Criteria

1. With `localRuns: "on-request"` and a `ci` source for a suite, a `verify.js --scope` run at a HEAD that is not pushed exits 3 before running any check, prints `head-not-pushed` and both ways on, and writes no pass stamp. With a CI answer available for HEAD, the same call takes the verdict from CI and runs no test of that suite on this machine.
2. The same call with `--local` makes no `gh` call and runs the impact subset here. When selection falls back, it runs the full command here.
3. Under the key, `verify.js --cmd tests=…` with neither `--scope` nor `--local` exits 2 and names both flags. With `--local` it runs the full command.
4. Without the key, a run without `--local` behaves exactly as before, including the local fallback when CI cannot answer. No existing test changes its expected output.
5. A declaration that carries `localRuns` with no `ci` block fails validation and the error names the key. So does any value other than `"on-request"`.
6. Under the key, a suite with no `ci` source still runs here without `--local`, and `--stamp-status` and `--changed-files` are unaffected.
7. The `verify` event of a run carries, for each CI-declared suite, whether CI answered and the fallback reason, and whether `--local` was passed.
8. `ci-source.md`, `suite-slots.md` and `docs/plugin-structure.md` name the key, the flag and exit 3, and no shipped doc still says a CI-declared suite always falls back to a local run.
9. The job-log download's `gh` argv carries `--allow-escape-sequences`, pinned by a test whose fake runner fails without the flag and answers with it; a runner that rejects the flag as unknown gets one retry without it. Under the key, a red CI job with no downloadable log exits 1, names the run URL, and runs no test of that suite here.

## Release Note

A project can now keep CI-declared test suites off the developer machine: with `"localRuns": "on-request"` in its verify declaration, `verify.js` takes those suites from the PR's CI job and runs them locally only with `--local`.
