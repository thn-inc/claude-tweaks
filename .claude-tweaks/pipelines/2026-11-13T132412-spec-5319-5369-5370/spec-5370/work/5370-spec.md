# 5370: Pipelines push first and take CI-declared suites from the PR's CI job; this repo opts in to localRuns

**Related:** #5369 (the runner key this record uses; blocks this record), #5319 (the plain `npm test` half of the same decision), #5133 (absorbed here: the push before build's verify), #5134, #5353, #5368, #5173

## Current State

#5369 gives `verify.js` a `localRuns: "on-request"` declaration key: under it a CI-declared suite runs on the developer machine only with `--local`, a scoped run that CI cannot answer exits 3 ("no verdict yet"), and an unscoped run without `--local` exits 2. Nothing uses the key yet. The pipeline skills still produce the three kinds of redundant run measured on the maintainer Mac between 9 and 13 November 2026 (91 `verify` events in 38 pipeline runs, plus each worktree's last `report.json`):

1. **Unscoped runs inside pipelines.** 21 of the 91 runs passed no `--scope` and ran every suite's full command (149 minutes of test time, not counting slot waits). They came from build's Final Verification in spec runs 5218, 5219, 5229, 5297 and 5340 on 12 and 13 November, from five release runs, and from two multi-spec runs. `plugin/skills/test/verification.md`'s Re-verify scoping table lists Build Common Step 5 as "full (impact-selected … when the declaration has `impact`; taken from the PR's CI job … when it has `ci`)". Only `impact-selection.md`'s Full mode section says that step runs the scoped invocation.
2. **HEAD not pushed.** Of the nine scoped runs whose report is still on disk, six fell back with `head-not-pushed` and ran their impact subset here (156 to 613 test files each). `plugin/skills/build/SKILL.md`'s Common Step 5 says a `ci` block "needs HEAD pushed first", but the phase-exit push comes after that step. #5133 records why: the explicit push instruction was cut to fit `RAIL_BYTES`, which left the CI source inert at its main call site.
3. **Standalone is always full.** `verification.md` gives a standalone `/claude-tweaks:test` the whole suite by rule, whoever invoked it.

This repo declares `impact` and `ci`, runs `pr-first`, and its merge gate (`plugin/skills/_shared/pr-first-merge.md` Step 2.5, `merge-verification: merge-when-green` by default) waits for the PR's checks and head workflow runs. CI is `ubuntu` on Node 20 (`.github/workflows/test.yml`), so it does not cover macOS, Node 22 or Windows.

No document states when a run on a developer machine is the whole suite and when it is the subset, what an impact-map miss can let through, or what catches it.

## Deliverables

- [ ] **Scoping table** (`plugin/skills/test/verification.md`, which every site cites). Build Common Step 5 is listed as `scoped`, like every other pipeline site. A project with no declaration still runs the full procedure. `impact-selection.md`'s Full mode section and `plugin/skills/build/SKILL.md`'s Common Step 5 say the same.
- [ ] **Push first.** With a `ci` block, a `pr-first` worktree run pushes its branch before each scoped invocation. This is #5133's deliverable. `build/SKILL.md` stays under `RAIL_BYTES`: the detail lives in `test/verification.md`.
- [ ] **Exit 3 handling, under the key.** On exit 3 with `head-not-pushed` or `no-open-pr-at-head` the site pushes, or records the PR, and re-runs once. On a second exit 3, or on any other reason, it re-runs with `--local` and logs one `AUTO` decision naming the reason. This adds no stop in `auto` mode. A run with no PR to push to (`local-merge`, `current-branch`, a standalone session on a branch without a PR) passes `--local` on its first call.
- [ ] **Standalone `/claude-tweaks:test`** under the key runs the scoped invocation. A new `full` argument runs every suite's full command here (`--local`, no `--scope`). "Standalone is always full" stays the rule for a project without the key.
- [ ] **Release.** `/claude-tweaks:release`'s verification before the version bump asks for the whole suite on this machine by name. It is the one deliberate whole-suite run on a developer machine per version, and the only one on macOS and Node 22.
- [ ] **This repo opts in.** `.claude-tweaks/verify-scope.json` gains `"localRuns": "on-request"`.
- [ ] **Close-time suite probe.** `plugin/bin/residue.js` runs a bare `npm test` as its suite probe and reads exit 0 as a green suite. Since #5319 a plain `npm test` in this repo runs the impact-selected subset, or nothing at all on a checkout with no changes against `origin/main`, so that reading can be a green suite from zero tests (found by #5319's whole-branch review). Under the key the probe does not run `npm test`: it reports the suite as not run on this machine, with a reason that names the declared CI job. Without the key the probe is unchanged.
- [ ] **Driver test step.** `plugin/bin/lib/driver/steps.js`'s `testStep` (the express lane behind `drive.js`) runs `verify.js --scope` before the branch is pushed and treats any non-zero exit as a test failure. Under the key that call exits 3 (`head-not-pushed`). The step pushes first where it has a PR to push to, and otherwise passes `--local`, and it never reports exit 3 as a failed test (found while planning #5369).
- [ ] **Decision document** `docs/decisions/0032-whole-suite-runs-in-ci-local-runs-on-request.md`, with the same content in `plugin/skills/test/impact-selection.md` for consumers. Acceptance criterion 5 lists the required content.
- [ ] **Conformance tests** pin the changed prose (the scoping row, the push-first rule, the exit 3 handling, the `full` argument), each shown to go red on a revert.

**Decision** (standalone `/claude-tweaks:test`). A standalone run never pushes: someone asked for a check here, and a push is a side effect they did not ask for. With no open PR at the branch, its first call passes `--local`, as the Exit 3 handling Deliverable says. With an open PR, it runs the scoped invocation. On exit 3 it re-runs once with `--local` and prints the reason and the push hint: "push the branch and re-run to take the suite from CI". It never stops without a verdict. This replaces the plan's "Standalone never pushes … reports the no-verdict line" and the spec's push-and-re-run for the standalone case only. Pipeline sites keep push-first.

**Decision** (a `--local` fallback whose selection resolves to the whole suite). This is accepted and named as the one exception. When CI cannot answer after a push and one re-run, the `--local` re-run runs what selection chose, and that is the whole suite when selection cannot narrow: a missing or stale map, a full-suite rule such as a change to `tools/run-tests.js`, or a stale stamp anchor. The decision document and `impact-selection.md` state it under "The rule" as the exception, with its trigger and its rarity, and `verify.js` is not changed for it. The run's `AUTO` line already names the fallback reason.

**Decision** (the CI wait inside a dispatched subagent). A dispatched subagent cannot hold a Bash call past 600 s, and `ci.tests.waitSeconds` is 900. In that context the `verify.js` call runs with a 600 s timeout. When the call ends while it is still waiting on CI, the same command runs once more: the CI run keeps going, so the second call finds it finished or nearly finished. A call that times out is never treated as exit 3 and never triggers `--local`. `waitSeconds` stays 900 for interactive and top-level sessions. The text goes in `plugin/skills/test/verification.md`'s Push first paragraph, beside the Foreground rule.

**Decision** (anything this record leaves open). Plan review settles it without asking. It picks the reading that keeps every acceptance criterion and recorded decision as written and runs nothing on this machine that the PR's CI job can answer. A side effect nobody asked for, such as a push from a standalone run, is never the chosen reading. The choice is logged as an `AUTO` entry for the Review Console.

These four decisions were written on 2026-11-14 by the session that shaped this record, under the maintainer's instruction to decide this design. They are listed for ratification at the run's Review Console (PR #5371), and reversing one is a small change before merge.

## Acceptance Criteria

1. `verification.md`'s scoping table lists Build Common Step 5 as scoped, and no pipeline site's instruction reads as the unscoped command when a declaration exists. A conformance test pins this and goes red when the row is reverted.
2. #5133's two acceptance criteria hold: a pipeline build with a `ci` block pushes HEAD before Common Step 5's `verify.js` run, and the `rail:` tests pass for `build/SKILL.md` and its composed bundle.
3. In a `pr-first` worktree pipeline in this repo, build's Final Verification pushes first and its `report.json` shows `used: true` for the `tests` suite's `ci` entry. An exit 3 never ends a run in `auto` mode: the re-run with `--local` is logged as one `AUTO` decision that names the reason.
4. Under the key, `/claude-tweaks:test full` runs the whole suite on this machine and `/claude-tweaks:test` with no argument does not. `/claude-tweaks:release`'s pre-bump verification runs the whole suite on this machine. The `full` argument appears in the skill's argument hint and in `/help`'s reference card.
5. The decision document and `impact-selection.md` state all of the following.
   - **The rule.** On a developer machine a CI-declared suite runs as the whole suite only when someone asks for it by name (`/claude-tweaks:test full`, `verify.js --local` with no `--scope`, the release's pre-bump run). Every pipeline verify takes it from the PR's CI job, and runs the impact subset here only when CI cannot answer.
   - **What a miss is.** A test whose result a change affects but which selection leaves out. The causes are reads the tracer cannot see (`#` imports, a package's self-reference, a native addon's content, a non-node child's reads, a wrapper such as `xargs` or `timeout`), reads that differ between CI's trace environment and this machine, and reads a test gained after the map was traced without the test file itself changing (the map may trail HEAD by up to 200 commits).
   - **How CI catches it.** When CI answers a pipeline's verify, CI ran the whole suite on that commit, so a miss cannot pass. When `--local` ran the subset, the miss passes on this machine and the PR's `test` job on the same head is red. The merge gate reads the PR's check rollup and its head workflow runs, parks a red PR and waits on a pending one, so the change does not merge.
   - **What CI does not catch.** A failure that happens only on macOS, on Node 22 or on Windows and that the map also misses. CI runs ubuntu on Node 20, and Windows is checked after merge. The release's whole-suite run on the developer machine is the remaining check before a version ships.
   - **Who enforces the gate.** The merge gate is the plugin's. A merge made outside it is stopped only when the repository protects its integration branch with the `test` check required.
6. `tests/verify-scope-declaration.test.js` accepts this repo's declaration with the key, and `verify.js --scope` in this checkout reads it without a validation error.
7. With the key, `residue.js` without `--no-suite` reports its suite probe as not run, with a reason naming the declared CI job, and never starts `npm test`. Without the key it runs `npm test` as before. A test covers both cases.
8. Under the key, the driver's test step does not fail a run on exit 3: a test drives `testStep` against a `verify.js` stand-in that exits 3 and sees either a push followed by a second call, or a call carrying `--local`, and never a `failed` test outcome for that exit.

## Release Note

Pipelines now push before verifying and take CI-declared test suites from the PR's CI job, so a project that sets `"localRuns": "on-request"` no longer runs those suites on the developer machine unless asked (`/claude-tweaks:test full`).
