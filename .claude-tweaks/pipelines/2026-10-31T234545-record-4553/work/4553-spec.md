# 4553: flow: a closed blocker is treated as satisfied even when its merge never reached the integration branch

Surface: infra

**Related:** #3721, #3822, #3873, #3878, #3974, #3975, #3976, #3977, #3982, #4038, #4108, #4118, #4191, #4217, #4289, #4292, #4344, #4353, #4366, #4471, #4531, #4551, #4603, #4610

## Current State

A record's `blocked-by` prerequisite counts as satisfied as soon as the blocking issue is closed. Nothing checks that the blocker's code ever reached the integration branch the dependent run builds from.

- **Multi-spec out-of-run check.** `plugin/skills/flow/multispec-dependency-ordering.md`, section "Targets with a dependency on a target NOT in the run", reads: status `complete` → "fine, dependency satisfied"; `pending`/`in-progress` → hard fail. A closed issue is `complete`.
- **`preflight-records.js` data.** `plugin/bin/lib/preflight-records/preflight-records.js` `buildRecords` (lines ~127-147) emits `blockedBy` plus `openBlocker`. Under `work-links: native`, `openBlocker` is `hasOpenNativeBlocker(node)` (`plugin/bin/lib/issues/record-dependencies.js:108`): only `state === 'OPEN'` counts, so a closed blocker reads `false`. Under `work-links: body-text`, `openBlocker` is `null` ("undetermined by this driver"), and nothing downstream resolves blocker state mechanically. The query builder `buildNativeDependencyQuery` (`record-dependencies.js:64`) asks only for `number state` per blocker, with no closing-PR or commit data.
- **Single-record `/flow #N`.** It runs no `blocked-by` check at all. `flow/SKILL.md` Step 2 (2.5-2.9) and `flow/validation.md` hold no prerequisite substep, and `materialize.md`'s reader table lists the `blocked-by` header field only for multi-spec ordering. Dispatched runs are filtered upstream by `dispatch/queue-pull-script.md`'s open-blocker exclusion (`openBlockerIds`, OPEN-state only), which also treats a closed blocker as satisfied.
- **Merge-state gate.** `plugin/bin/lib/preflight-records/merge-gate.js` is a different check. It covers only *in-run* blockers whose own text demands "merged to the integration branch". It does not look at out-of-run blockers or at git reachability.

**Incident (reported against 6.156.1):** a blocker issue was closed by a PR merged into the production branch instead of the configured integration branch. The dependent record's pre-flight reported `openBlocker: null`, and the run built on an integration-branch base without the blocker's code. The gap surfaced only mid-build, when the implementer found the pre-blocker version of a file the spec assumed was already changed.

**Prior art for the reachability primitive:** `plugin/bin/lib/reconcile/archive-merged.js` `localHasMerge` (~line 737) and `plugin/bin/lib/docs-health/commit-ref.js` (~line 148) both classify a commit against the integration ref with `git merge-base --is-ancestor`.

**Probed API surface (2026-10-30, live against this repo):** the GraphQL `Issue` exposes `stateReason`, `timelineItems(itemTypes:[CLOSED_EVENT], last:1)` → `ClosedEvent.closer` (`PullRequest { number merged baseRefName mergeCommit{oid} }` | `Commit { oid }`), and `closedByPullRequestsReferences(first:N, includeClosedPrs:true)`. REST `repos/{o}/{r}/compare/{base}...{sha}` returns `status` (`identical`/`behind` = the sha is an ancestor of base).

## Deliverables

1. **Blocker-landing module.** New `plugin/bin/lib/preflight-records/blocker-landing.js`. It has three parts:
   - A pure batched, aliased GraphQL query builder. For each blocker number it requests `state`, `stateReason`, the last `ClosedEvent.closer`, and merged `closedByPullRequestsReferences` with `mergeCommit{oid}`.
   - A pure classifier mapping one blocker node plus a reachability answer to `{ blocker, verdict, commit, via }`. The verdict is one of:
     - `open`: the blocker is still OPEN.
     - `landed`: at least one candidate closing commit is reachable from `origin/{integration-branch}`.
     - `unlanded`: there are candidate commits, but none is reachable.
     - `not-applicable`: closed with `stateReason` `NOT_PLANNED` or `DUPLICATE`, which carries no code.
     - `undetermined`: closed `COMPLETED` with no closing PR or commit found, or a reachability probe failed.
   - An injectable-runner fetch function (`gh-api-module-pattern` seam). It resolves reachability per candidate commit through the REST compare API (`identical`/`behind` → reachable; `ahead`/`diverged` → not; any error → undetermined for that candidate). This means no local `git fetch` and no dependence on the caller's checkout.

   Candidate commits are taken from the `ClosedEvent.closer`: a merged PR's `mergeCommit.oid`, or a `Commit`'s `oid`. When the closer is null (a manual close), they fall back to every merged `closedByPullRequestsReferences` PR's `mergeCommit.oid`.
2. **`preflight-records.js --blocker-landing`.** A new additive flag on `plugin/bin/preflight-records.js`, paired with the existing `--integration-branch` (default `main`). It runs the module over every record's **out-of-run** blockers: blockers not among the positional numbers, since in-run blockers are built inside the same run. Each record in the envelope gains `blockerLanding: [{blocker, verdict, commit, via}]`. Without the flag, the output is byte-identical to today's. The flag is documented in `--help` and the header comment. Under `--records-json` (no `gh`), every out-of-run closed blocker reads `undetermined`, and one stderr line names why.
3. **Multi-spec rule.** Update `plugin/skills/flow/multispec-dependency-ordering.md`'s out-of-run section and `plugin/skills/flow/multi-spec.md` Validation step 3's call so that `/flow` passes `--blocker-landing` and applies these rules per out-of-run blocker:
   - `open` → hard fail (today's `pending` rule, now mechanical).
   - `unlanded` → hard fail, stopping before Step 2.8 claims anything. The message names the blocker, its closing commit, and `origin/{integration-branch}`. It gives two paste-ready escapes: merge that commit into the integration branch, or remove the `blocked-by` edge.
   - `landed` / `not-applicable` → satisfied.
   - `undetermined` → proceed, and write one `SKIP` line per blocker to the run's decision log (`log-decision.js`), naming the reason.
4. **Single-record pre-flight substep.** Add a new substep to `/flow` Step 2 (`plugin/skills/flow/SKILL.md`'s Step 2 list plus its procedure in `plugin/skills/flow/validation.md`). For one record target, it runs `preflight-records.js {n} --blocker-landing --integration-branch "$INTEGRATION_BRANCH"` (`$INTEGRATION_BRANCH` per `_shared/integration-branch.md`) and applies the same per-verdict rules as Deliverable 3. Every blocker of a single-record run is out-of-run, so this is the identical rule. It returns BLOCKED on `open`/`unlanded`, before Step 2.8 claims. For a record with no `blocked-by` edges it makes no extra call. Multi-spec runs keep using Validation step 3's single call and never run this substep a second time.
5. **`gh`-absent path.** `plugin/skills/flow/multispec-preflight-failure.md` states that under the `--records-json` path, blocker landing is `undetermined`, with the logged `SKIP` that implies.
6. **Tests** under `tests/bin-lib/preflight-records/`:
   - Classifier cases for all five verdicts, including:
     - a closer PR merged into a non-integration base, the incident shape (`unlanded`);
     - a null closer with a merged `closedByPullRequestsReferences` fallback;
     - mixed candidates where one is reachable (`landed`);
     - a compare-API error (`undetermined`).
   - A CLI test that `--blocker-landing` excludes in-run blockers, and that output without the flag is unchanged.

- A closed blocker whose closer PR's merge commit compares `behind` or `identical` against `origin/{integration-branch}` yields `landed`. A blocker closed `NOT_PLANNED` or `DUPLICATE` yields `not-applicable`. A `COMPLETED` blocker with a null closer and no merged closing PR yields `undetermined`.

## Release Note

Stop `/flow` before it builds when a closed blocker's merge never reached the integration branch.

## Technical Approach

Keep the reachability judgment in one pure module beside `merge-gate.js` and `waves.js`, wired through the existing `preflight-records.js` call. That way multi-spec gets it in the call it already makes, and single-record gets it from one new call. The new GraphQL builder is separate from `buildNativeDependencyQuery`, which stays unchanged for its dispatch and wrap-up consumers. It queries the *blockers* (not the dependents), so it works identically under `work-links: native` and `body-text`: blocker numbers come from the existing `blockedBy` field either way.

Reachability goes through the REST compare API rather than local `git merge-base --is-ancestor`. The pre-flight runs before any worktree exists and may run from a stale or shallow checkout. Compare answers against the remote integration branch with no fetch and no local state. The archive-merged and commit-ref modules remain the house examples for the three-way reachable / unreachable / unverifiable split, and the classifier mirrors that split (`undetermined` = unverifiable).

"Landed if any candidate commit is reachable" is deliberate. A blocker closed by a production hotfix PR and separately merged into `dev` by a second PR must pass. Requiring every candidate to land would block real work.

`unlanded` stops before claiming, because the pre-flight already returns BLOCKED for hard fails and the auto-mode contract permits pre-Manifesto pre-flight stops. A warning-and-continue would reproduce the incident: a full build on a base missing the prerequisite.

## Gotchas

- **Single-record behavior change.** Today `/flow #N` ignores `blocked-by` entirely, so after this change a human-invoked run with an *open* out-of-run blocker stops where it used to build. This matches `flow/SKILL.md`'s own anti-pattern row ("Running flow on specs with unmet prerequisites") and multispec-dependency-ordering's "the dependency check is the same regardless" rule. Dispatched runs are unaffected, because dispatch's queue already excludes open blockers.
- **Cherry-picks read `unlanded`.** A blocker fix cherry-picked onto the integration branch has a different sha from the closer PR's merge commit, so it stops the run. The stop message names the commit so a human can confirm, and the remove-the-edge escape covers it.
- **Manual closes are common here.** Under `pr-first` with an integration branch that differs from GitHub's default, GitHub does not auto-close the issue on merge. A manually closed issue has a null `closer`, and resolves only through a `closedByPullRequestsReferences` link from a closing keyword in the PR body. Without that link the verdict is `undetermined` (proceed + `SKIP`), never a stop.
- **Compare-API cost.** There is one REST call per candidate commit, and only for closed out-of-run blockers. Records without `blocked-by` edges pay nothing.
- **Dispatch's queue-pull scope.** Dispatch's queue-pull open-blocker exclusion still treats a closed blocker as satisfied when *selecting* a record. The `/flow` pre-flight is where the landing check binds. A dispatched record with an unlanded blocker is still selected by dispatch, then stopped by `/flow`'s Step 2 substep.
