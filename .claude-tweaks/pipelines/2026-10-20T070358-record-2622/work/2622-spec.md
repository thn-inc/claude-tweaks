# 2622: Add a pre-scale hardening skill for AI-coded apps

Surface: backend

## Current State

- The record asks for pre-scale hardening checks on AI-coded apps: "N+1 queries, unindexed columns, unpaginated lists", slow external work (AI calls, email, third-party APIs) running "inline on the request path instead of as a background job", and no "load test, caching pass, connection-pool cap, or alerting baseline" before launch.
- `/code-health`'s `focus=<vertical>` mode is the shipped home for checklist-style verticals. The registry autoloads eight generators (`plugin/bin/lib/code-health/focus-generators.js:44-51`). `docs/getting-started.md:116` says "eight verticals shipped".
- The scope is already reserved: `candidates-prelaunch.js:12-18`, `candidates-security-hardening.js:31`, `candidates-app-store-readiness.js:18`, `criteria.js:172` and three `criteria-*.md` Scope boundary lines name "#2622's pre-scale hardening" as out of their scope.
- `candidates-prelaunch.js` is the closest model. It returns `{ candidates, scannedFiles, discoveryFailed, notApplicable, checklist }`, and `checklist` lists every item on every firing with `group: 'automated'|'manual'` and `status: pass|fail|manual` (`:80-98`, `:431-449`). Manual items are never machine-judged.
- The rotating sweep already has overlapping criteria: `scalability` (`criteria.js:31-35`; `criteria-scalability.md` flags unbounded queries, N+1, missing indexes) and `observability` (`criteria.js:90-94`). Fingerprints hash `criterion + areaId + anchor` (`fingerprint.js:36-43`), and `dedup.js` matches on fingerprint only.

## Deliverables

1. Decision (approved in brainstorming, 2026-10-15): build this as a new `/code-health` focus-mode vertical, `focus=scale-readiness`, modelled on `candidates-prelaunch.js` and `candidates-security-hardening.js`. It runs static checks only. The k6 load test is a manual checklist item reported to the human, because code-health never runs anything against a live app. Rejected alternatives:
   - A standalone `/scale-readiness` skill: it adds a new surface and diverges from how the sibling checklist records shipped. Those were #2624 `security-hardening`, #2693 `prelaunch` and #2628 `app-store-readiness`, each as a focus vertical.
   - Closing the record: the scope is already reserved by four sibling verticals.

   The record's "step within `/review` or `/build`" criterion is explicitly not carried. `/review` participation is a per-vertical choice that `prelaunch` also declined.
2. Write a generator, `candidates-scale-readiness.js`, with automated candidate kinds for:
   - queries: a query call inside a loop or `.map(async`, a list query with no limit or take, and a `where` field with no `@@index`/`@unique` in a Prisma schema
   - inline slow work: an AI-SDK, email-send or third-party fetch call in a route/handler file with no queue or background-job signal
   - caching: a repo-level "no cache layer signal" alongside DB-backed routes
   - pooling: a DB client constructed per request, or a pool with no max
   - monitoring: no error-tracking or APM dependency

   The load test (k6 against signup, login and the main dashboard, recording p95 and error rate before and after) is a `group: 'manual'` checklist row. Every checklist row also carries a `phase: 'pre-launch'|'pre-scale'` field (queries, background jobs and load test are pre-launch; caching, pooling and monitoring are pre-scale). The generator sets `notApplicable: true` when the repo shows no server/data-access signal.
3. Add the criterion `scale-readiness` in `criteria.js` and the fragment `plugin/skills/_shared/criteria-scale-readiness.md`. The fragment gets What to flag / What NOT to flag / Severity calibration / Scope boundary / Reporting sections, including the row-status reconciliation rule `criteria-prelaunch.md` uses. Its Scope boundary covers `scalability`/`observability` overlap and the sibling verticals.
4. Add every `focus-mode.md` row the vertical needs: a Coverage pointer, a Criterion pinning row, and an F2 exact not-applicable line. Update the `docs/getting-started.md` count and list to nine.
5. Repoint the sibling scope-boundary mentions of "#2622" to name `focus=scale-readiness`.

## Release Note

Added `/code-health focus=scale-readiness`. It flags N+1 and unpaginated queries, slow work done inline on requests, missing caching, connection-pool, and monitoring setup, and lists a load test for you to run before launch.

## Technical Approach

Follow the `code-health-focus-vertical` project skill's registration set and its five pitfalls:
- require `./focus-generators` before `./candidates-dead-code`
- anchor repo-level items to a real file (for example `package.json#no-monitoring`), never a directory
- use real-framework fixtures
- add a row-status reconciliation rule
- re-derive any path gate copied from `security-hardening`

File discovery reuses `listTrackedFiles` from `candidates-dead-code.js`. The route/handler path heuristic can start from `ROUTE_DIR_RE` (`candidates-security-hardening.js:148`), and the AI-call recognition can start from `AI_CALL_PATTERNS` (`:166`). Re-check both against App Router `route.ts` files before you reuse them. Write each limitation into the module header's Coverage block: text-window co-occurrence rather than AST, JS/TS only, presence-not-quality for repo-level signals, and an index check limited to a schema file the generator can parse.

## Gotchas

- **Cross-criterion double filing.** An N+1 site can be flagged by both the rotating `scalability` criterion and this vertical. Their fingerprints differ because the criterion is part of the hash, and `dedup.js` matches fingerprints only. The fragment's Scope boundary must tell the judge to treat an open `scalability` issue at the same anchor as covered.
- Probe this repo's own shape before writing a "not applicable" premise. The generator must skip test, fixture, example and build-output directories, as `prelaunch` does.
- The sibling-comment repoints (Deliverable 5) touch prose that is not test-pinned, so grep for `#2622` across `plugin/` after editing.
- No open related records. #2624 and #2625 are closed.

## Original request

Add a pre-scale hardening skill for AI-coded apps

Current State:
- AI-coded apps ship for a single tester and hit real limits at their first real traffic spike (N+1 queries, unindexed columns, unpaginated lists).
- Slow or external work (AI model calls, email, third-party APIs) often still runs inline on the request path instead of as a background job.
- No standard load test, caching pass, connection-pool cap, or alerting baseline runs before a launch or scaling event.

Deliverables:
- A new claude-tweaks skill (e.g. `/scale-readiness`) that walks a codebase through the query, background-job, caching, pooling, and monitoring checks in one pass.
- A k6 load-test step simulating concurrent users on signup, login, and the main dashboard, reporting before/after p95 and error rates.
- Policy rows for each check so `/code-health` or `/review` can flag violations without re-deriving the checklist.

Acceptance Criteria:
- Skill runs standalone and as a step within `/review` or `/build`.
- Running it against a sample app reports pass/fail for each of the six checks.
- Docs distinguish the pre-launch subset (queries, background jobs, load test) from the pre-scale subset (caching, pooling, monitoring).
