# 5534: Remove the bare-SHA verify stamp twin and the --stamp-status legacy key

Surface: infra
Risk-flags: none

## Overview

`plugin/bin/verify.js` writes two pass stamps after a full passing run: the JSON stamp `{git-dir}/claude-tweaks-verify-pass.json`, and a bare-SHA twin `{git-dir}/claude-tweaks-verify-pass` kept so that builds running pre-#1921 skill prose could still find a stamp. The twin was the expand half of a contract change and was documented as written "for this release only". It first shipped in v6.119.0; the plugin is at v6.170.0. This record executes the contract half: the twin write, the bare-file read fallback, the `deps.legacy` option, the `legacy` key of `--stamp-status`, the deprecation entry and every sentence that describes the twin.

It is unit 1.1 of the 2026-11-15 audit simplification design (transitional code whose recorded removal condition is met). The recorded condition asks for a grep that returns nothing, but the grep matches the line that quotes it, so it can never be satisfied as written; the timing clause (first minor release after v6.119.0) passed at v6.120.0 on 2026-09-08. The design doc (`docs/superpowers/specs/2026-11-15-audit-simplification-design.md`, unit 1.1) waives the unsatisfiable grep and applies the timing clause; Deliverable 1 still runs the grep so that the waiver is visible in the pull request.

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Removing `anchorOf`'s `sha` fallback in `plugin/bin/lib/verify/stamp.js:108-111`. It also serves a JSON stamp that has no `fullSha`, which `tests/bin-lib/verify/stamp.test.js:199-204` treats as valid.
- Deleting bare-SHA files that already sit in existing checkouts' git directories. Once nothing reads the file it is inert, and code to clean it up would be new transitional code with its own removal condition.
- Any change to what the JSON stamp contains, when it is written, or how `--scope` and `--changed-files` use it.
- Changing `verify.js`'s entry shape or moving its CLI tests in-process.
- Recording the executed removal condition anywhere but the pull request and the release note. The deprecation entry is deleted with the twin, and git history at the deleting commit keeps its text.
- A conformance test that compares the four `--stamp-status` key lists. Whether to pin more prose is the policy question #4964 asks; this record aligns the lists once and checks them against the CLI's output.

## Release Note

Removed the old bare-SHA verification stamp that was written alongside the JSON stamp for one release.

## Technical Approach

Follow `.claude/skills/removal-condition-execution/SKILL.md`: run the condition's own check and report it, delete rather than renumber, sweep framing words as well as identifiers, retarget pins rather than only deleting them, and say for each behaviour whether it goes with the twin or stays on its own rationale.

One behaviour changes and is intended: a checkout whose only stamp is a bare-SHA file reads as having no stamp. `--stamp-status` reports `present: false` and a `--scope` or `--changed-files` run there takes a full run. Such a checkout can only come from a build older than v6.119.0, which is unsupported (one plugin version per checkout, shared git directories included). The readers of `--stamp-status` degrade on `present: false`: `first-call-artifact-check.js` reports `stamp-absent` as a note, never a gate, and review Step 1.5 re-verifies an unstamped HEAD through the runner.
