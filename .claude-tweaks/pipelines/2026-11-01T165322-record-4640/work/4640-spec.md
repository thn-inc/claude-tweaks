# 4640: plan-audit: --task-markers reads '**Review risk:** high (reason)' as no risk, silently

Surface: infra

## Current State

`plugin/bin/plan-audit.js --task-markers {plan}` reads each task's optional `**Role:**` / `**Review risk:**` markers (#3378) and prints `{"markers", "tasks": [{index, title, role, risk}], "findings"?}`. `/build`'s per-task tier forwarding (`plugin/skills/build/dispatch.md`, the "Per-task role/review-risk tier forwarding (#3378)" paragraph) is its one consumer: a task reported `risk: "high"` gets a Capable task review; `risk: null` falls back to the run's `size:`-derived tier.

The parser (`plugin/bin/lib/plan-audit/parser.js`, `extractTaskMarkers`) captures everything after the key to end of line (`RISK_MARKER_RE = /^\*\*Review risk:\*\*[ \t]*(.*)$/m`, same shape for `ROLE_MARKER_RE`), trims it, and recognizes it only on an exact whole-value match against the closed sets `TASK_MARKER_RISKS = ['high']` / `TASK_MARKER_ROLES = ['transcription', 'integration', 'judgment']`. So `**Review risk:** high (a read-once/write-last ordering, and branching on computed state)` yields `riskRaw = "high (a read-once/…)"`, `risk: null`. The same holds for a `**Role:** judgment (needs design judgment)` line.

The mis-parse is then invisible end to end:

- `checkTaskMarkers` (`plugin/bin/lib/plan-audit/checks.js`) records a `findings` entry, but `--task-markers` (`plugin/bin/plan-audit.js`) only embeds it in the stdout JSON — exit 0, nothing on stderr. `plugin/skills/build/plan-audit.md` documents findings as warn-only, never exit-changing.
- `dispatch.md`'s tier-forwarding paragraph never reads `findings` at all — it keys only on `markers` and each task's `role`/`risk`.
- `plugin/skills/build/plan-authoring-checks.md` documents the syntax as `**Review risk:** high` but never says the value must stand alone on the line, and a trailing reason reads as valid to a human author.

Net effect: a task its author explicitly marked high-risk silently drops from a Capable review to the unpinned tier. Putting the reason on its own line (`**Review risk:** high`, then `Why: …`) parses correctly — confirmed by the reporter on plugin 6.156.1.

**Related:** #3986, #4618, #4549, #4559 (near-duplicate screen: shared Key Files / body anchors only — no title similarity; #4618 adds a different risk axis to plan-audit and shares `plan-audit.js`/`checks.js`)

## Deliverables

1. **Accept a trailing annotation after a recognized marker value.** In `extractTaskMarkers`, a `**Role:**` / `**Review risk:**` value is recognized when its leading token is in the closed set and is either the whole value or is followed by whitespace (the annotation after it is ignored). `**Review risk:** high (reason)` → `risk: "high"`; `**Role:** judgment — needs design judgment` → `role: "judgment"`. A leading token not in the closed set (`medium`, `hgih`, `high-ish`) stays unrecognized (`null`) exactly as today. `roleRaw`/`riskRaw` keep carrying the full raw trimmed line value.
2. **Make an unrecognized marker value visible on stderr.** When `--task-markers` produces any `findings` entry, print one warning line per finding to stderr naming the task index, title, field, and raw value (e.g. `plan-audit.js: warning: task 3 "X" — unrecognized Review risk value "medium"; the task reads as unmarked`). Stdout JSON and the exit code (0) are unchanged — findings stay warn-only per `plan-audit.md`.
3. **Surface findings in `/build`'s tier forwarding.** `dispatch.md`'s Per-task role/review-risk tier forwarding paragraph: when the `--task-markers` output carries `findings`, log one decision-log line naming each offending task/field/value (via `log-decision.js`, status per `_shared/auto-decision-log.md`'s Status semantics — not `STAGED`, since nothing is staged) and continue dispatch with those tasks treated as unmarked — never a stop.
4. **Document the accepted shape.** `plan-authoring-checks.md`'s marker paragraph and `plan-audit.md`'s `--task-markers` paragraph state that a trailing annotation after the value is allowed and ignored, and that an unrecognized value is now warned on stderr as well as listed in `findings`.

## Acceptance Criteria

- `node plugin/bin/plan-audit.js --task-markers plan.md` on a plan with `### Task 1: X` followed by `**Review risk:** high (a read-once/write-last ordering, and branching on computed state)` prints task 1 with `"risk": "high"`, no `findings` key, exit 0.
- The same for `**Role:** judgment (needs design judgment)` → `"role": "judgment"`, and for a value followed by an em-dash annotation (`**Review risk:** high — reason`).
- `**Review risk:** high` and `**Role:** transcription` with no annotation still parse exactly as today (existing `tests/bin-lib/plan-audit/parser.test.js` / `cli.test.js` #3378 cases stay green unmodified).
- `**Review risk:** medium`, `**Review risk:** high-ish`, and `**Role:** trivial` still yield `null` plus a `findings` entry carrying the full raw value; `--task-markers` exits 0 and writes one stderr warning line per finding naming the task index, field, and raw value.
- A plan with no findings writes nothing to stderr under `--task-markers`.
- `dispatch.md`'s tier-forwarding paragraph names the `findings` field and the decision-log line it writes; `tests/plan-task-markers-conformance.test.js` (or a sibling conformance test) pins that the paragraph references `findings`.
- `plan-authoring-checks.md` and `plan-audit.md` each state that a trailing annotation after the marker value is ignored.
- New unit tests in `tests/bin-lib/plan-audit/parser.test.js` and `tests/bin-lib/plan-audit/cli.test.js` cover the annotated forms and the stderr warning, and each goes red when the parser change (respectively the stderr write) is reverted.
- `npm test` passes.

## Release Note

Fix plan-audit's task markers silently ignoring `**Review risk:** high` when a reason follows the value on the same line, and warn about unrecognized marker values instead of dropping them quietly.

## Technical Approach

Parser: keep `ROLE_MARKER_RE` / `RISK_MARKER_RE` capturing the full line (so `roleRaw`/`riskRaw` and the findings' `value` stay the raw text), then derive the recognized value from the leading token — e.g. `const lead = raw.split(/\s/, 1)[0]` and recognize `lead` when it is in the closed set. Splitting on whitespace (not on any non-word character) is what keeps `high-ish` / `high,` unrecognized rather than read as `high`; decide in the build whether a directly-attached separator like `high,` should also be accepted, and test whichever way it lands. `checkTaskMarkers` must use the same recognition rule as `extractTaskMarkers` (today it re-tests `TASK_MARKER_RISKS.includes(t.riskRaw)` against the raw value — switch it to test the recognized `t.risk`/`t.role` being null while the raw is non-null, so an annotated valid value is not reported as a finding).

CLI: in the `parsed.taskMarkers` branch of `plan-audit.js`, after computing `findings`, write each to `process.stderr` before the stdout JSON line; leave `process.exitCode` untouched.

Skill prose: the `dispatch.md` change is one sentence inside the existing tier-forwarding paragraph; keep the `markers: false` branch byte-for-byte as the paragraph promises.

### Key Files

- `plugin/bin/lib/plan-audit/parser.js` — `extractTaskMarkers`: leading-token recognition for Role / Review risk
- `plugin/bin/lib/plan-audit/checks.js` — `checkTaskMarkers`: finding iff raw present and recognized value null
- `plugin/bin/plan-audit.js` — `--task-markers` branch: one stderr warning line per finding
- `plugin/skills/build/dispatch.md` — tier-forwarding paragraph: log `findings` to the decision log, continue with the task unmarked

## Gotchas

- `tests/plan-task-markers-conformance.test.js` pins the marker syntax in `plan-authoring-checks.md` with `/\*\*Review risk:\*\* (\S+)`/` and the dispatch tier wording — edit the prose so those pins still match, or update the pins in the same change.
- The `markers` flag semantics are unchanged: a recognized key with an unrecognized value still sets `markers: true`.
- Keep the matcher same-line-only (`[ \t]*`, never `\s*`) — `parser.js`'s own comment explains why `\s` would read into the next line.
- Exit code for findings must stay 0 — `plan-audit.md` documents findings as warn-only and `dispatch.md` runs this call unconditionally before SDD dispatch.
