# 2999: design-wrapper review mode: Step 3.6 cites review-seed-capture.md, which does not ship

Surface: infra

**Related:** #2733, #2799, #2954, #2955, #2977

## Current State

The report, filed via `/claude-tweaks:feedback` against 6.134.1, says that `plugin/skills/design-wrapper/modes/review.md` Step 3.6 (`:50-57`) cites `review-seed-capture.md` "in this directory", and that the file "does not ship", based on `ls skills/design-wrapper/`.

The file does ship, one level down from where the reporter looked. `review.md` lives in `plugin/skills/design-wrapper/modes/`, so "this directory" is `modes/`, and `plugin/skills/design-wrapper/modes/review-seed-capture.md` is tracked there. It has existed since the plugin-payload move (`68074d781`, 2026-08-17). It is also present in every installed cache build checked on this machine, including the reporter's own version (`…/claude-tweaks/6.134.1/skills/design-wrapper/modes/review-seed-capture.md`, as well as 6.131.0, 6.134.0, 6.139.1 and 6.140.0). The skill directory's top level (`plugin/skills/design-wrapper/`) holds `SKILL.md` and shared sub-files, while mode files and their own sub-files sit in `modes/`. An executor that resolves "this directory" against the skill root rather than the citing file's own directory gets ENOENT, which is exactly the reported symptom.

So nothing is missing. The defect is that the citation is easy to resolve against the wrong base directory.

## Deliverables

1. Make Step 3.6's citation unambiguous by naming the path relative to the skill root (`modes/review-seed-capture.md`) or stating "this `modes/` directory", so an executor resolving from the skill root finds it. Keep it a citation and do not restate the procedure.
2. Close this record with a comment telling the reporter the file ships at `skills/design-wrapper/modes/review-seed-capture.md` in 6.134.1 and later, and naming the citation-wording change.
