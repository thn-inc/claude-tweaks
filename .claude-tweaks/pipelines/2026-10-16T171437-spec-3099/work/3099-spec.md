# 3099: plan-audit: Check A passes a plan that drops one clause of a multi-clause acceptance criterion

Surface: infra

## Current State

`/claude-tweaks:build`'s Common Step 1.5 audits the plan before SDD dispatch with `node "${CLAUDE_PLUGIN_ROOT}/bin/plan-audit.js" {plan-file}` (`plugin/skills/build/SKILL.md:182`, procedure in `plugin/skills/build/plan-audit.md`). The CLI takes only a plan file (`plugin/bin/lib/plan-audit/args.js` `USAGE`: `plan-audit.js <plan-file> [--repo-root <dir>] [--count-tasks] [--bytes]`). It never reads the spec.

Its five checks (`plugin/bin/lib/plan-audit/checks.js`) are Check A (plan `Files:` paths exist, `checkA` at line 54, returning `{ ok, missing, missingDetail }`), Check B (scope-keyword sweep), Check C (verification-command pre-check), Check D (control-byte scan), and the headroom check. **None of them compares the plan against the spec's Acceptance Criteria.** The original request says Check A "matches the plan against the spec's Deliverables and cites acceptance criteria only by number". That attribution does not match the code: Check A only checks that file paths exist, so its `ok: true, missing: []` meant "every planned path exists", not "every criterion is covered".

Today, plan-to-spec coverage is checked only by prose judgment:

- `/superpowers:writing-plans`' own self-review, a third-party step, and the `Spec coverage` self-review line in `plugin/skills/build/micro-plan.md:67` for fast-lane micro-plans.
- `plugin/skills/build/dispatch.md`'s instruction to forward the spec's `## Acceptance Criteria` excerpt into every per-task review.

The observed failure (original request below): one numbered acceptance criterion carried three clauses separated by sentences and semicolons. The plan covered two of them. The dropped clause was a counting invariant and the only test guarding an assumption a correctness proof rested on. plan-audit passed. Only the whole-branch review caught the gap, costing one extra fix dispatch and a scoped re-review that a pre-dispatch check could have saved.

## Deliverables

1. **New check, Check E (acceptance-criterion clause coverage), in `plugin/bin/lib/plan-audit/checks.js`.** Given the spec's `## Acceptance Criteria` section and the plan text:
   - Split each criterion (a numbered item or a `-` bullet) into clauses on sentence boundaries and `;`.
   - Give each clause a stable id, `AC{item}.{clause}` (1-based).
   - Report a clause as covered when the plan names its id, or quotes its text, in a task's test step or in a spec-coverage map row. Report it as waived when the plan carries a line `Waived AC{item}.{clause}: {reason}`.
   - Return `{ ok: true, uncovered: [{id, clause}], waived: [{id, reason}], unparsed: [{item, raw}] }`. Check E is warn-only: `ok` is always `true`, so the CLI exit code is unchanged.
2. **A distinguishable could-not-parse signal**, per the repo's `parse-signal-discipline` project skill. A spec with no `## Acceptance Criteria` section, or a criterion item the splitter cannot break into clauses, lands in `unparsed`. It is never silently reported as "fully covered".
3. **CLI input:** add an optional `--spec <path>` flag to `plugin/bin/lib/plan-audit/args.js` and `plugin/bin/plan-audit.js`. Check E runs only when `--spec` is given. Without it, the envelope's `checkE` reads `{ ok: true, skipped: 'no-spec' }`. The existing call shapes (`--count-tasks`, `--bytes`, plain audit) keep working unchanged.
4. **Build wiring (`plugin/skills/build/SKILL.md` Common Step 1.5 and `plugin/skills/build/plan-audit.md`):** pass `--spec {run-dir}/work/{n}-spec.md` (the materialized spec) when one exists. Document Check E in "What each check covers" and in Result interpretation. A non-empty `uncovered` means the plan author amends the plan before dispatch, either naming each clause id in a task's test step or adding a `Waived` line. Under auto mode this happens without a prompt and is logged via `log-decision.js`. A non-empty `unparsed` is surfaced as a warning and logged, never treated as covered.
5. **Plan-authoring rule (`plugin/skills/build/plan-authoring-checks.md`):** one paragraph telling the plan author to cite `AC{item}.{clause}` ids in each task's test step (or a spec-coverage map table), so Check E can match coverage by id rather than by fuzzy text.
6. **Tests** under `tests/bin-lib/plan-audit/`: `checks.test.js` cases for full coverage, one dropped clause (the original incident's shape: three clauses in one numbered item, two covered), a waived clause, and an unparseable criterion. `parser.test.js`/`cli.test.js` cases for `--spec` and the `skipped: 'no-spec'` envelope.

## Acceptance Criteria

- `plan-audit.js {plan} --spec {spec}` on a spec whose AC item 2 has three clauses, against a plan citing only `AC2.1` and `AC2.2`, reports `checkE.uncovered` containing `AC2.3` with that clause's text.
- The same plan with a `Waived AC2.3: {reason}` line reports `AC2.3` under `waived`, not `uncovered`.
- A spec with no `## Acceptance Criteria` section yields a non-empty `checkE.unparsed`, not an empty `uncovered` list.
- Without `--spec`, the JSON envelope carries `checkE: { ok: true, skipped: 'no-spec' }`, and the exit code and every other check's output match the current behavior.
- Check E never sets `ok: false`. A plan with uncovered clauses still exits `0` when Checks A-D and headroom pass.
- `build/plan-audit.md` documents Check E's coverage rule, its waiver line, and its Result-interpretation handling. `build/SKILL.md` Common Step 1.5 passes `--spec` when the materialized spec exists.
- `build/plan-authoring-checks.md` tells plan authors to cite `AC{item}.{clause}` ids.
- `npm test` passes.

## Release Note

Add a plan-audit check that warns before a build starts when the plan leaves a clause of an acceptance criterion uncovered.

## Technical Approach

Add a pure `checkE(specText, planText)` to `checks.js`, next to the existing checks and following their `{ok, ...}` envelope convention. Add clause splitting to `parser.js`, keeping one parser module. Thread `--spec` through `args.js` and `plan-audit.js` the same way `--repo-root` is threaded. Make Check E warn-only rather than a stop: clause splitting is a prose heuristic, and a hard gate on a heuristic would block builds on false positives. The incident's cost was one fix dispatch, so a pre-dispatch warning that prompts a plan amendment is proportionate. Use id citation (`AC{item}.{clause}`) as the primary match, so coverage does not depend on fuzzy text similarity. Quoted clause text is accepted as a fallback.

## Gotchas

- Splitting on `;` and sentence ends will mis-split clauses that contain inline code with semicolons or abbreviations ("e.g."). Strip code spans before splitting. Prefer reporting an item as `unparsed` over guessing.
- ASSUMPTION — verify at build: plans written by `/superpowers:writing-plans` often carry a "Spec coverage map" table, per the original request. Plans are deleted after a build, so this checkout cannot confirm it. Confirm by reading the current upstream writing-plans template before relying on the table as a coverage source.
- `/superpowers:writing-plans` is third-party, so its template cannot be changed here. The id-citation rule reaches plan authors only through `plan-authoring-checks.md`, which `/build` already hands to plan authoring.
- The micro-plan path (`micro-plan.md`, fast-lane) skips `plan-audit.js` entirely. Check E does not apply there by construction, the same as Check D's documented exception.
- `plan-audit.md` lists Check A/B/C and headroom as sharing one skip gate. Decide explicitly whether Check E shares that gate. It reads only text already in memory, like Check D, so running it on the skip path too is defensible. Record the ruling in `plan-audit.md`.

## Original request

plan-audit: Check A passes a plan that drops one clause of a multi-clause acceptance criterion

**Summary:** plan-audit's coverage check passes a plan that drops one clause of a multi-clause acceptance criterion.

**Kind:** Gap

**Affected component:** `bin/plan-audit.js` (Check A, run by `/claude-tweaks:build` before SDD dispatch)

**Use case:**
- **What was dropped:** a spec's acceptance criterion carried three clauses in one numbered item, separated by sentences and semicolons. The written plan covered two of them. The missing clause was a counting invariant (an entity with several instances counts once per recipient). That clause was the only test guarding an assumption a correctness proof rested on.
- **Why plan-audit missed it:** Check A reported `ok: true, missing: []`. It matches the plan against the spec's Deliverables and cites acceptance criteria only by number, so the criterion counted as covered once any task cited its number.
- **How it surfaced:** the whole-branch review after all tasks were built caught the gap as its one Important finding. That cost one extra fix dispatch and a scoped re-review, work a pre-dispatch check could have saved.

**Suggested direction:** a per-clause coverage check.
- Split each numbered acceptance criterion into clauses (sentences, `;`).
- Require every clause to be named by some task's test step, or waived by an explicit plan ruling.
- Report uncovered clauses as Check A warnings, quoting the clause text.

Many plans already carry a "Spec coverage map" table, which the check could read.

**Definition:** Clear

**Plugin version:** 6.138.0
