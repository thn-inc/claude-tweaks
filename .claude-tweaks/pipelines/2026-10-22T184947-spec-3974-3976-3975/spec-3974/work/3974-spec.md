# 3974: Resolve a run's spec header at its live or archived path in every reader

Surface: infra

## Overview

A run's materialized spec header (`work/{N}-spec.md`, or `spec-{N}/work/{N}-spec.md` for a multi-spec parent) is committed on the run branch on purpose, and six readers depend on finding it at the live run-dir path `.claude-tweaks/pipelines/{run-id}/`. The cutover record in this project (#3976) moves that header to `.claude-tweaks/pipelines/archive/{run-id}/` on the run branch just before merge, so a merged pr-first run leaves no live tracked directory on `main` (#3855, option a). That move is only safe once every reader can find the header at either location.

This record is the expand step, before any move happens. It adds one shared resolver that returns a run's header location at the live path or the archived path, on the filesystem and inside a git tree, and migrates all six readers onto it. No file moves; behavior for every run that exists today is unchanged.

**Complexity:** Medium
**Estimated tasks:** 7

## Non-Goals

- No `git mv` of any header and no wrap-up change; that is #3976, which is blocked by this record.
- No `.gitignore` change.
- No change to `materialize.md`'s contract text; it changes when the move lands.
- No new reader beyond the six named, and no reader restating the dual-path rule after this record: each calls the resolver.

## Prerequisites

None. This record is a pure expand step and can be built first.

## Release Note

Changed spec-header checks to find a run's header at either its live or archived location, with no change to existing runs.

## Technical Approach

One resolver, imported by all six readers, so the dual-path rule exists in one place. The resolver takes the run id rather than a pre-joined path, because the archived path replaces the `{run-id}` parent segment (`pipelines/archive/{run-id}`), not just a tail. Every reader derives the run id as `path.basename(runDir)`; `archiveRunDir` names the archive directory after the same basename, so the two always agree.

For the git-tree readers the resolver returns an ordered pathspec list (live first, then archived) and the readers keep their own git invocation (`cat-file`, `ls-tree`, `log`), so each retains its own failure semantics. For the filesystem readers (`pack.js`, `first-call-artifact-check.js`) it takes an ordered list of base roots (the run dir's checkout root, then the worktree mirror's root, the same order those readers use today) and returns existing header files. Precedence is root by root: within a root, live before archived and flat `work/` before `spec-{N}/work/`. The resolver does no mirror discovery itself; the caller supplies the roots, which keeps the main-checkout anchoring rule (`_shared/pipeline-run-dir.md`, IL-127) the caller's.

### Data / API Surface

`plugin/bin/lib/run-header.js`:

- `headerRelPaths(runId, recordNumber)` returns the ordered list of repo-relative POSIX paths for one record (live flat, live `spec-{N}`, archived flat, archived `spec-{N}`), for readers that need concrete paths (`git cat-file -e`).
- `headerPathspecs(runId)` returns the `git log` and `ls-tree` pathspecs covering `work` and `spec-*/work/*` at both locations, for readers that enumerate.
- `findHeaderFiles(roots, runId, recordNumber)` returns the existing header files for one record on the filesystem, in the precedence order above (the caller applies its own `record:` line check and falls through to the next file).
- `listHeaderDirs(roots, runId)` returns every existing header directory as `{ dir, location: 'live' | 'archived', specN: number | null }` for enumerating readers (`pack.js`, `getMaterializedRecordNumbers`); where one record appears in both locations, the earlier in precedence wins.

## Gotchas

- `git log` pathspecs: a wildcard directory component followed by a literal tail never matches. `spec-*/work` does not match; `spec-*/work/*` does (the comment in `hasMaterializeCommit` records this as empirically verified). Keep the trailing wildcard in the archived spec pathspec as well: `pipelines/archive/{run-id}/spec-*/work/*`.
- `hasMaterializeCommit` is range-bound to `{integration}..HEAD` so a merged run's materialize commit, inherited by later worktrees, does not arm the gate against runs that never materialized (#1674). After the move, the archived path is part of the squash on `main`, so the range bound must still exclude it for an unrelated run; AC 4(b) pins this. When the integration branch cannot be resolved the function falls back to the unbounded walk (documented in its own comment); the archived pathspecs inherit that fallback and the same over-arming risk, which this record does not change.
- The gh-absent cloud bookends check (`isSpecCommitted`) must keep passing after the move lands; it is the reason cloud parity depends on this record.
- `git cat-file -e HEAD:<path>` cannot glob; the resolver must hand it concrete candidate paths, not pathspecs.
- A run resumed after the move still has to read as materialized, so the dispatch first-call check must accept the archived location too.
- File overlap with open records: `pre-tool-use.js` with #3875 and #3847, `pack.js` with #3686. Rebase on `main` before opening the PR and re-run the affected suites.
- The dual-path rule is permanent, not a compatibility shim: while a run is in flight its header lives at the live path, and only at wrap-up does it move. There is no removal condition; the live candidates stay for as long as runs have a live phase.
- The filesystem readers keep the `record:` line check: a header at the archived path whose `record:` line names another number must not count either.
- Apply the `windows-checkout-test-parity` skill to the new path-matching tests (POSIX separators in git pathspecs, native separators on the filesystem side).
- Per the `pre-tool-use-gate-exemptions` skill, `hasMaterializeCommit` arms a deny gate; widening what counts as materialized widens what the gate sees, so check each deny gate that consumes it for an exemption-scope change; AC 5 pins the one gate that does.
