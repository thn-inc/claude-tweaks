# 3950: Settle the existing Review Console backlog once and retire the direct-verification override

Surface: infra

## Overview

Decommission step: settle the existing Review Console backlog once, then retire the Direct-verification override. Consumer projects have the same residue as this repo (2026-10-22 count here: 445 unresolved items across 185 runs, 156 of those runs already acknowledged; 191 findings, 149 reflect items, 105 unmapped-prefix `pending` plus `shadow-dup` items), so the settling ships as a `plugin/bin` CLI plus a skill-driven procedure. A Node CLI cannot dispatch agents, so the split is: the CLI enumerates, splits and emits a work list and later rewrites resolutions; the procedure (hosted by a skill the builder picks, for example a `/claude-tweaks:tidy` mode) dispatches the review tiebreak per finding against current `main`, feeds replies to the resolver, files can't-tell items of severity medium or higher through the console sub-issue's path, and applies the staged-kinds outcomes to reflect and other items. Each item's resolution in `console.json` is rewritten to its final outcome with an audit line (an acknowledgement stamp alone is not enough), and a run is acknowledged when all its items are settled. Resumable and idempotent.

The same record then decommissions the override: retire the Direct-verification override text in `plugin/skills/review/step3-lens-dispatch.md`, or keep it as an interactive-only shortcut that emits a verdict line; decide and record why, under expand-contract.

## Deliverables

- [ ] A shipped CLI (`plugin/bin/{name}.js` plus a `plugin/bin/lib/console/` module; builder names them) that enumerates every closed or archived run (run-state `clean`, or a run under `archive/`; live runs are skipped and reported, never backfilled while their owner may still write) whose `console.json` holds `pending` / `keep-staged` items, acknowledged consoles included, splits a legacy decision line bundling several findings into one item per finding, and emits a work list; it also has an apply mode, the only writer of `console.json`, that rewrites each item's resolution with an audit record and acknowledges a run once all its items are settled. Contract (defined by this record, additive under expand-contract): the work list is JSON `{ mainSha, runs: [{ runDir, items: [{ itemId, itemHash, kind, finding?, claimText?, section }] }] }`; apply takes `{ runDir, itemId, itemHash, outcome, source, ref? }` entries, refuses an entry whose item no longer matches `itemHash` or is already settled, and writes the new resolution plus an additive audit field `settled: { outcome, source, ref, at }` (`source` is one of `tiebreak`, `staged-kind`, `digest`; `ref` is the filed record number or digest entry). Allowed final resolutions are the console's existing non-unresolved values (`applied`, `apply`, `approve`, `filed`, `refused`, `dropped` from the console sub-issue) plus an additive `digested`; none of them may appear in `UNRESOLVED_RESOLUTIONS`, and a test runs the residue reader over the CLI's output to prove it. `--dry-run` prints a summary (counts per outcome, number of records that would be filed) before anything is filed.
- [ ] The skill-driven procedure (host skill chosen by the builder; it runs in the main session, so tiebreak agents are dispatched from it, not nested): per finding, dispatch the review tiebreak against current integration branch (resolved per `_shared/integration-branch.md`; the question becomes "is this still a problem today?") in bounded batches, feed the replies to the resolver, and apply this disposition table to every item class:

  | Item | Outcome |
  |---|---|
  | tiebreak `confirmed` (the defect is real on today's code), `refuted` | `confirmed` at severity medium or higher: filed through the console sub-issue's path; `confirmed` at low: digest; `refuted`: dropped with the quoted evidence in the audit record |
  | tiebreak can't-tell, severity medium or higher (unknown severity counts as medium), or the tiebreak cannot locate the cited code | filed through the console sub-issue's path (never an automatic drop) |
  | tiebreak can't-tell, severity low | digest with a `Defer-reason:` stating the tiebreak could not tell |
  | legacy item with no recoverable claim text (only `finding {path}:{line} not reproduced`), or a claim too thin to judge (no `path` or no claim text) | digest with a `Defer-reason:` stating no claim was recorded |
  | reflect items, unmapped-prefix `pending` items, `shadow-dup-*` items | the staged-kinds sub-issue's outcome for that kind; a kind it does not map goes to the digest with a `Defer-reason:` naming the unmapped prefix |

  Digest entries are written through the standard digest path in the current main checkout (`_shared/materiality-floor.md`), carrying the settled run's id as provenance, not into the closed run's directory.
- [ ] Resumable and idempotent, with a fixed order per item: look up the item's filing key (the same `work-fingerprint` the console sub-issue uses, over lens, path and normalized claim) among open and closed records, file or digest if absent, record the filed `ref` in the audit record, and only then apply the resolution; a crash between filing and applying therefore re-runs into a dedup hit, never a twin. Builds on #3816's fix where it lands first; the backfill's own ids are the fallback if it does not cover split items.

## Technical Approach

Split by what can and cannot be deterministic. The CLI does the walk, the legacy-line split, id assignment, the work list and the rewrite; it never judges. The procedure does the judging by dispatching the tiebreak per finding (the same dispatch the review step uses, so the same subagent contract) and routing replies through the resolver's outcomes. Because 445 items is a large fan-out, the procedure works in bounded batches and records progress in the rewritten `console.json`, which is what makes it resumable.

Order inside the record: CLI and tests first, then the procedure, then the acceptance run on this repo, then the override decision (last, so the decision uses the experience of the run).

## Gotchas

- Per-item rewrites need collision-free item ids (#3816): `coordinationItems` truncates ids to 58 characters, so two bundled findings can share an id. Do not rewrite by that id until it is fixed.
- An acknowledgement stamp alone is not a settlement: rewrite the item's resolution, or the data keeps lying and the next reader re-counts it.
- Consumer projects have un-backfilled archives; the CLI must run there with no assumptions about this repo's layout (resolve the run root per `plugin/skills/_shared/pipeline-run-dir.md`, never from a worktree's relative path: IL-127).
- The backfill files real backlog records (can't-tell items of severity medium or higher); do not add or remove any `auto:*` or `bot:*` label on any record, and cite only issue numbers confirmed to exist.
- File overlap only (not a dependency): #3876, #3835, #3737, #3754 and #3381 also edit `plugin/skills/review/step3-lens-dispatch.md` or its tests; re-read the file's byte count at build time.
- ASSUMPTION — verify at build: a Task subagent can run the tiebreak dispatch for the backfill from a host skill invoked in the main session (no nested dispatch is required) — via the probe the review sub-issue records for #3817. If the host skill is itself run inside a Task agent, fall back to serial dispatch in smaller batches from the main session, and stop and report rather than inventing a nested path.
- Legacy items are judged against today's code, so a drifted line number or moved file is the normal case: "cannot locate the cited code" is a can't-tell, never evidence that the finding is fixed and never an automatic drop.
- Filing volume is unbounded in a consumer project (every can't-tell finding of medium or higher becomes a record): always show the `--dry-run` summary first, and process in batches so a run can be stopped between them.
