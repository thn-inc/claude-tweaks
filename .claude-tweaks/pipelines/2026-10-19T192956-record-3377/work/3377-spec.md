# 3377: Add a Capable plan review before Task 1 of a Spec Mode build

Surface: backend

## Overview

Part of the "Build dispatch cost shape" decomposition (origin #3229, a feedback report from a measured 10-task subagent-driven build). In that build, 3 of the 5 Important findings from the top-tier final review were spec or plan-level gaps — behaviour the spec left undecided, or two tasks disagreeing about a contract — found after all the code was written and fixed in an 18-minute fix wave plus a re-review. SDD's own pre-flight scan ("Before dispatching Task 1, scan the plan once for conflicts") runs on the controller and hunts contradictions between and within tasks; it does not look for spec gaps or undecided behaviour.

This record adds a new `/build` Common Step between plan audit (Common Step 1.5) and execution dispatch (Common Step 2), Spec Mode only: one dispatched reviewer on the Capable profile reads the materialized spec and the plan once and returns findings in three classes — spec gap (the spec does not decide something the plan must decide), undecided behaviour (an input class, failure mode or UI state no task covers) and cross-task contract (one task produces what another consumes and they disagree). It explicitly does not redo SDD's pre-flight conflict table. A spec gap resolvable from the spec's own intent amends the in-run materialized spec before Task 1; a spec gap that needs a human becomes a deliberate new HARD-GATE stop; the other two classes amend the plan.

**Complexity:** Medium-High
**Estimated tasks:** 6-8

## Non-Goals

- Redoing SDD's pre-flight conflict table (cross-task and within-task contradictions, written to the SDD ledger). The reviewer's brief tells it to skip that class.
- Editing the live issue body at any point. An intent-resolvable spec amendment lives in the worktree's materialized spec and is posted once as a comment on the record; nothing is staged for the Review Console.
- Running in design mode (no materialized spec, no record) — same skip as architecture alignment.
- Changing SDD's per-task loop, or filing anything upstream with superpowers.
- The per-task tier markers (a separate record, which adds one check to this record's reviewer once both exist).

## Release Note

Added a top-tier plan review before the first build task that catches spec gaps and undecided behaviour early, and stops the build for a human decision when the spec cannot answer.

## Technical Approach

The reviewer reads two files and returns a findings table in Template A shape with an added `Class` column (spec gap / undecided behaviour / cross-task contract) so the controller routes mechanically rather than paraphrasing. The controller (the `/build` session) applies the per-class handling; the reviewer is read-only. Placement relative to Common Step 1.7 (Design Pre-Build) is the builder's call; running the plan review before 1.7 is recommended because plan amendments should land before design references are pre-loaded for implementers.

### Data / API Surface

- Output template (builder finalizes): `| Severity | Class | Resolution | Path:Line | Finding | Evidence | Suggested resolution |`, "No findings." when clean, at most 7 rows with a "+N more" row, trailing `STATUS: {WORD}` line. `Resolution` is filled only for spec-gap rows and `Evidence` must cite a spec sentence for `intent-resolvable`. Routing keys on Class and Resolution, never on Severity; `low` and `info` findings are logged only and amend nothing.
- Decision-log entries per `_shared/auto-decision-log.md`: `AUTO` for an amendment applied, `SKIP` for a skipped step. No `STAGED` entry: nothing is staged.
- Human-needed gate in headless runs: a `gh issue comment` carrying the question, then `bot:blocked` (bootstrapped per `_shared/label-bootstrap.md`) and removal of `auto:*` grants, mirroring `dispatch/settle-and-merge.md` Settle steps 5-6 but without the retry-ceiling counter (this gate blocks directly).

## Gotchas

- Steering principle for the whole decomposition: claude-tweaks never files upstream with superpowers and never contradicts SDD's text. This step runs before SDD starts and adds a review SDD does not have; it must not instruct SDD to skip or alter its own pre-flight scan.
- The materialized spec lives in the worktree's copy of `work/{n}-spec.md` in worktree mode, not under `$PIPELINE_RUN_DIR`, and reaches the main checkout only on merge (`plugin/skills/flow/materialize.md`). Amend that copy — amending a path under the run directory silently edits nothing the later phases read (`[IL-127]` shadow-copy hazard).
- Anti-goal: a plan review that rules on spec gaps in the SDD ledger only, leaving the spec that `/test`, `/review` and `/wrap-up` judge against unchanged. The amendment must land in the materialized spec.
- Anti-goal: any new mid-flow stop in `auto` mode that is not added to the auto-mode contract's HARD-GATE list deliberately. The human-needed spec gap is that deliberate addition; every other finding class resolves without a stop.
- The Capable reviewer is a dispatch the Subagent Contract governs: `Frontier` is reserved for contract-enumerated singleton slots, so this stays Capable regardless of `profile=frontier`.
- "Someone is present" means `DISPATCH_HEADLESS` is not `1`. `plugin/skills/dispatch/task-prompt.md` (First call section) has the dispatching session add `DISPATCH_HEADLESS=1` to the `/claude-tweaks:flow` invocation exactly when the firing came from a scheduled Routine drain with nobody present, and omit it when a human typed the command. Interactive `/flow` in `auto` where the user has since walked away is accepted as "present" (the stop waits for them); that is the stated cost of making this a real stop. ASSUMPTION — verify at build: a human-typed `/dispatch #N` runs the build in a Task subagent that cannot call `AskUserQuestion`, so the stop there must surface as a `BLOCKED` report that the dispatching session (where the human is) relays — via reading `dispatch/SKILL.md`'s Settle handling of a `BLOCKED` build call and `_shared/headless-self-report.md`; define that relay in this record rather than leaving a stop nobody can answer.
- ASSUMPTION — verify at build: the retry-ceiling path in Settle is not the right mechanism for this gate (a human-needed spec gap should block on the first occurrence, not after three failed attempts) — via reading `dispatch/settle-and-merge.md` steps 5-6 and `_shared/issue-claims.md`'s rule that `bot:blocked` removes all `auto:*` labels.
- The new HARD-GATE row is a contract change under the repo's expand-contract discipline: add the row, update every consumer that enumerates the HARD-GATE list, and never rename an existing gate. Known consumers at record-writing time (2026-10-17): `plugin/skills/_shared/auto-mode-contract.md` line 208 (the row itself) and `plugin/skills/_shared/auto-mode-card.md` line 36 (restates the gate families); grep the repo for "plan-audit hard-fails" and "plan validation" to find any others, including under `plugin/skills/flow/` and `plugin/skills/dispatch/`.
- Amending the spec after the plan was written can trip `build/SKILL.md`'s plan-staleness rule on a resumed build ("has the spec evolved since the plan was written?"). Committing the spec amendment together with the plan amendment, in the same commit, is what keeps the pair consistent; say so in the sub-file.
- Decided (2026-10-17): the live record body is never edited and nothing is staged. The record comment is the durable trace on the issue; the worktree's amended spec reaches `main` only on merge. Do not add a Review Console apply path or a new staged-item kind.
- This record shares `plugin/skills/build/SKILL.md`, `plan-audit.md`, `plan-authoring-checks.md` and `plugin/bin/lib/plan-audit/checks.js` with #3310 (ready, in progress) — build after it merges and re-read the files. Other ready records touching `build/SKILL.md` (#3118, #3079, #3060, #3004) and `build/dispatch.md` (#3118, #3004, #2869) may land first; expect rebasing, and `docs/skill-graph.md` is shared with #3033.
- Measure byte headroom before adding to `plugin/skills/build/SKILL.md`: 5,205 bytes remain. The pointer must be a few lines; everything else lives in the new sub-file.
- Trivial-plan threshold: reuse Step 1.5's existing triviality language ("fewer than 3 file references and no `Scope keywords:`") unless the builder can justify a different measure; do not invent a second definition of "trivial" without citing why.
