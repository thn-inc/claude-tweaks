# 5268: Turn on the worker read block and re-open only the test command's toolchain

Origin: #5217 SDD ruling 5, reversed by the user

Defer-reason: needs-human-decision

## Current State

`implementerSettings` in `plugin/bin/lib/driver/roles.js` (#5217) turns the sandbox on for the implementer worker on the sandbox-probed platforms (`SANDBOX_PROBED_PLATFORMS`, today `darwin`), but leaves `permissions.blockReadsOutsideWorkingDirectories` off. That was #5217's SDD ruling 5; the user reversed it on 2026-11-12.

Probed on 2026-11-12 with Claude Code CLI 2.1.322 on macOS, through a test file the worker ran with the allowed test command. With the settings as generated, that code read a canary file placed under the home directory, listed the home directory, opened `.zshrc` and `.npmrc` there and listed `~/.ssh`. The worker's Read tool was already refused outside the working directory.

With `permissions.blockReadsOutsideWorkingDirectories: true` and `sandbox.filesystem.allowRead` set to the Node toolchain's root, all of those reads failed with EPERM, the toolchain's own `node` still ran (same version as before), and the toolchain stayed unwritable. `.gitconfig` stayed openable, apparently a CLI carve-out so `git` works. Without the `allowRead` entry, the earlier #5217 probe found that a toolchain installed under the home directory becomes unreachable and a different `node` runs.

Re-opening the toolchain as a working directory (`--add-dir` or `permissions.additionalDirectories`) is not an option: the CLI documentation says those directories also become writable by sandboxed commands.

## Deliverables

- [ ] `implementerSettings({ testCommand, platform, readPaths })` takes `readPaths`, an array of absolute directory paths. On a sandbox-probed platform it sets `permissions.blockReadsOutsideWorkingDirectories: true` and `sandbox.filesystem.allowRead` to `readPaths`. Off those platforms neither key is set.

- [ ] A pure helper `toolchainRoot(testCommand, deps)` in `roles.js` that resolves the test command's first word on `PATH` and returns its install root: the directory above `bin/` when the resolved real path sits in a `bin` directory, otherwise the binary's own directory, or `null` when the binary is not found. `PATH` lookup and `realpath` are injected seams.

- [ ] `launchWorker` takes an optional `readPaths`. When it is absent it passes `[toolchainRoot(testCommand)]` (or `[]` when that is `null`), so the block is on for every implementer launch on a probed platform.

- [ ] The live smoke test (`AC7` in `tests/bin-lib/driver/worker.test.js`, `DRIVER_LIVE_SMOKE=1`) gains a step: code run through the test command tries to read a canary file the test places under the home directory, and the read must fail while the test command itself runs. The test removes the canary.

- [ ] The `roles.js` header records the probe above in place of the paragraph that says the read block is not turned on.

## Acceptance Criteria

1. `implementerSettings({ testCommand: 'node --test', platform: 'darwin', readPaths: ['/opt/tool'] })` returns settings whose `permissions.blockReadsOutsideWorkingDirectories` is `true` and whose `sandbox.filesystem.allowRead` deep-equals `['/opt/tool']`. For `platform: 'linux'` neither key is present.

2. A `readPaths` entry that is not a string or not an absolute path throws a `TypeError` naming the entry, before anything is written. An empty array is accepted: the block is on and nothing is re-opened.

3. With fake seams, `toolchainRoot('node --test', deps)` returns `/h/.nvm/versions/node/v22` when `node` resolves to `/h/.nvm/versions/node/v22/bin/node`, returns the binary's directory when it does not sit in a `bin` directory, and returns `null` when `node` is not on `PATH`.

4. Over a fake runner, a `launchWorker` call with no `readPaths` writes a settings file whose `allowRead` holds the derived toolchain root, and a call with `readPaths` given writes exactly those paths.

5. Neither the generated settings nor the launch argument list contain `additionalDirectories` or `--add-dir` for any role.

6. With `DRIVER_LIVE_SMOKE=1` on macOS, the smoke test's test-command step runs and its read of the home-directory canary fails.

## Release Note

The pipeline driver's implementer worker can no longer read your home directory; only the test command's own toolchain stays readable.

## Technical Approach

### Key Files

- `plugin/bin/lib/driver/roles.js` — readPaths in implementerSettings, toolchainRoot helper, header
- `plugin/bin/lib/driver/worker.js` — pass readPaths, derived from the test command when absent
- `tests/bin-lib/driver/roles.test.js` — pin the read block, allowRead and toolchainRoot
- `tests/bin-lib/driver/worker.test.js` — pin the derived readPaths; extend the live smoke test
