# 4317: dispatch close-out update: durable resume marker and resume-state correctness for an update that already pushed

Origin: wrap-up from #4273 (SDD rulings 5 and 6, review low-confidence findings)

Defer-reason: genuinely-larger

## Current State

Close-out's update path (`plugin/skills/dispatch/close-out-update.md`, shipped by #4273 in PR #4295) records an in-flight update only as a local worktree, `.worktrees/close-out-{number}` in the checkout that ran it. That worktree is the resume marker. A `BEHIND` update is pushed to GitHub by `gh pr update-branch` before the full suite verifies it, and a `DIRTY` resolution is pushed in step 5 before the CI re-read in step 6. If the worktree is removed, or close-out is next run from another clone, the PR looks `CLEAN` and the merge gate can reach `--match-head-commit` with a head whose full-suite stamp lives only in the removed worktree. #4273 scoped the guarantee to the checkout holding the worktree (SDD ruling 6, `genuinely-larger`).

The final SDD review of #4273 also left four Minors open (ruling 5): NB1 the step-7 keep-rule wording can strand a resume (safe, but stuck), NB2 an already-pushed resolution is no longer in `origin/{head}..HEAD`, so a resume mislabels `{conflicted-files}` and `{update-method}`, NB4 the `{update-clause}` is keyed on "ran" rather than "handed off", NB3 (deviation only) an agent that proceeds past a failed `git worktree add` or checkout could merge unstamped. The review round on #4273 added two low-confidence single-agent findings in the same area: a post-push stop (`CI pending after update`, `CI failing after update`, `head moved`, `BEHIND after update`) tears the worktree down so the re-run has no update clause, and step 3 does not check that `git fetch origin {base}` moved the ref.

## Deliverables

1. A GitHub-side marker for an update close-out pushed but has not yet seen merged and verified (a PR label or run comment per `_shared/pr-run-comments.md`, written before the push in step 5 and before `gh pr update-branch` in step 2, cleared only after the verified merge or an explicit human decline). Close-out reads it in step 2 so a re-run from any checkout is routed to a re-verify instead of the plain merge gate.

2. Resume correctness: recover `{conflicted-files}`, `{update-method}` and `{resolution-commit}` from the marker or the PR history instead of `origin/{head}..HEAD` (NB2), reword step 7's keep rule so a resume cannot be stranded (NB1), key `{update-clause}` on a handed-off sha (NB4), and stop on a failed `git worktree add` or checkout rather than continuing (NB3).

3. Check that `git fetch origin {base}` moved `origin/{base}` before the step 3 merge, and keep the update note across a post-push stop.

4. A gh-absent branch for the update path (`gh pr update-branch`, `gh run list`, `gh pr checks --watch` have no MCP mapping today; `close-out.md` Preflight accepts `gh` or its MCP fallback), or an explicit stop with a named reason when `gh` is absent.

5. Conformance pins in `tests/close-out-pr-state-contract-conformance.test.js` for each new clause, each with a go-red mutation in the existing one-to-one tables.

## Acceptance Criteria

A close-out re-run from a different checkout, after an earlier run pushed an update that failed verification or CI, does not reach the merge confirmation without a passing full-suite `verify.js` stamp on the current head.

A resumed update reports the same `{conflicted-files}`, `{update-method}` and `{resolution-commit}` as the run that made it.

No path continues past a failed `git worktree add`, checkout or fetch.

A close-out run without `gh` either completes the update through the MCP transport or stops with a named reason before touching the PR.

Every new clause has a pin and a go-red mutation, and `npm test` passes.

## Release Note

Close-out's in-place PR update survives a re-run from another checkout without merging an unverified head.
