# 2564: dispatch: queue-pull-script.md's multi-line `node -e` blocks silently no-op on Windows Git Bash, so the whole queue pull produces nothing

Surface: terminal

## Current State
`plugin/skills/dispatch/queue-pull-script.md` embeds 27 multi-line `node -e "…"` blocks, starting with an `eval "$(node -e …)"` prelude that defines every `DISPATCH_*` shell variable used by the rest of the queue-pull procedure. `plugin/skills/dispatch/next-ranking.md` embeds the same shape. On Windows (Git Bash 5.x, Node 24.11), a multi-line string passed as a `node -e` argument exits 0 but produces no output at all — confirmed by direct reproduction (`node -e "console.log('a')"` prints; a two-line equivalent does not). Because the prelude produces nothing, `DISPATCH_QUEUE_RAW` and its siblings are never set, every later block that references them fails with `unbound variable`, and the queue pull's output file (`dispatch-groups.json`) ends up empty. The skill runs silently wrong rather than failing loudly at the point of the actual defect.

`plugin/skills/_shared/scratch-worktree.md` already documents shell-constraint guidance recommending script files over inline Node for exactly this class of cross-shell fragility, but `queue-pull-script.md` and `next-ranking.md` predate or don't yet follow that guidance. Related record #2544 covers the same underlying pattern (steps prescribed as inline JS module calls with no CLI verb) for the wrap-up/reflect/feedback skills — this record is the dispatch-specific instance.

A verified workaround exists: a preprocessor that rewrites each `node -e` block into a `.cjs` file (prepending `process.argv.splice(1, 1)` to preserve argv positions) before running it, restoring correct behavior on the affected shell.

## Deliverables
1. `queue-pull-script.md`'s logic — currently expressed as 27 inline multi-line `node -e` blocks plus the `eval "$(node -e …)"` prelude — is restructured so it runs identically across every supported shell, including Windows Git Bash. The two directions the record itself weighs: (a) extract the logic into a CLI (e.g. `bin/dispatch-queue-pull.js`) that writes the same session-scoped JSON files the current inline blocks produce, invoked as a single-line command from the skill; or (b) collapse each multi-line `node -e` block into a single-line equivalent that Git Bash's argument-passing handles correctly. Pick whichever direction keeps the skill's existing output contract (the same `DISPATCH_*` variables / `dispatch-groups.json` shape) intact with the least duplication.
2. `next-ranking.md`'s equivalent multi-line `node -e` blocks receive the same treatment, for consistency and to close the identical failure mode there.
3. The chosen fix aligns with `_shared/scratch-worktree.md`'s existing shell-constraint guidance (prefer script files over inline Node) rather than introducing a second, divergent convention.

## Acceptance Criteria
1. Given Windows Git Bash 5.x with Node 24.11 (or an equivalent simulated environment), running `queue-pull-script.md`'s procedure end-to-end produces a populated `dispatch-groups.json` (matching what it would produce on macOS/Linux bash for the same input queue state) rather than an empty file.
2. Given the same environment, no step in the procedure raises `unbound variable` or `Unexpected end of JSON input` due to an unset `DISPATCH_*` variable.
3. On macOS/Linux bash (the currently-working case), the fixed procedure's output is unchanged — the fix does not alter behavior on shells where the original inline blocks already worked.
4. `next-ranking.md`'s equivalent blocks pass the same cross-shell test (produces correct output on Windows Git Bash, unchanged output on macOS/Linux bash).
5. If a failure occurs in either script's logic post-fix, it surfaces as a loud, attributable error (not a silent empty-output no-op) — the specific silent-failure mode this record reports must not recur even for an unrelated future bug in the same code.

## Technical Approach
- Investigate `queue-pull-script.md`'s 27 `node -e` blocks and the `eval "$(node -e …)"` prelude to inventory exactly what each computes and what shell variables/files it produces.
- Choose between: (a) a new `bin/dispatch-queue-pull.js` CLI that consumes the same inputs and writes the same session-scoped JSON outputs the current inline logic produces, called with a single-line invocation from the skill; or (b) converting each block to a single-line `node -e` form. Prefer (a) when the logic is substantial enough to warrant a testable, named entry point (consistent with `_shared/scratch-worktree.md`'s stated preference for script files); prefer (b) only for blocks trivial enough that a CLI would be pure overhead.
- Apply the same fix shape to `next-ranking.md`'s equivalent blocks.
- Verify cross-shell correctness by simulating the Windows Git Bash multi-line-argument behavior (a two-line `node -e` producing no output) as a test case, or by testing on an actual Windows Git Bash environment if available.
