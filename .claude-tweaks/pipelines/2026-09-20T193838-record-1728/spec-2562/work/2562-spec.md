# 2562: reflect: Defer-filed records carry no native issue type under `work-types: native`, so the merge-subject composer later refuses them

Surface: infra

## Current State
Under project policy `work-types: native` and `work-backend: github-issues`, `/claude-tweaks:capture`'s create path stamps the native GitHub issue type via GraphQL `issueTypeId` when it files a record. `/claude-tweaks:reflect`'s Defer path (`full-mode.md`) creates records through a different path — `gh issue create` via `recordPayload`/`specShapedBody` in `_shared/work-record.md`, with `filedBy: 'reflect'` — and that path does not stamp a native issue type or a `type:*` label. A record filed this way arrives untyped. When it is later built, granted `auto:build`, dispatched, and reaches the pr-first merge, `bin/compose-subject.js` cannot resolve a Type for the merge-subject line and exits 1 with a "no resolvable Type" usage error, blocking the merge until a human manually stamps a type. Observed live: a wrap-up had to log a manual "Stamped native issue type Task" action to unblock the merge — the exact gap `compose-subject.js`'s Type-resolution contract assumes every create path already closes.

## Deliverables
1. Update `/claude-tweaks:reflect`'s Defer path (`full-mode.md`) and/or `_shared/work-record.md`'s `recordPayload`/`specShapedBody` create logic so that, when `work-types: native`, the same native-type stamping mechanism `/claude-tweaks:capture` already uses (GraphQL `issueTypeId`) runs on record creation.
2. As a fallback for any create path that cannot resolve/stamp a native type at creation time (or when `work-types: labels`), stamp a `type:*` label instead, so `compose-subject.js`'s Type resolution never depends on a later human action regardless of which create path produced the record.
3. Confirm any other plugin create path that files records directly (not just `/claude-tweaks:reflect`'s Defer path) also stamps a type or label at creation — sweep call sites of `recordPayload`/`specShapedBody`/`gh issue create` used by plugin skills.

## Acceptance Criteria
- Under `work-types: native`, running `/claude-tweaks:reflect full` on a merged record and accepting a Defer recommendation produces a new record whose native GitHub issue type is set at creation time (not left empty) — verified by `gh issue view <new-issue> --json issueType` (or the equivalent field) showing a non-empty type immediately after creation, with no manual stamping step.
- Under `work-types: labels`, the same Defer-created record instead carries a `type:*` label at creation time, verified the same way via `gh issue view <new-issue> --json labels`.
- A record created through this path, when later built, granted `auto:build`, dispatched, and merged via the pr-first path, reaches `bin/compose-subject.js` without a "no resolvable Type" exit — verified by running the merge-subject composition against the newly created record's actual labels/type and confirming it resolves without error.
- The sweep from Deliverable 3 identifies every `recordPayload`/`specShapedBody`/direct `gh issue create` call site in the plugin's skills, and each site is either confirmed to already stamp a type/label at creation or is fixed to do so.

## Technical Approach
Locate the exact stamping call `/claude-tweaks:capture`'s create path uses for `work-types: native` (the GraphQL `issueTypeId` mutation) and reuse the same helper/pattern from `/claude-tweaks:reflect`'s Defer path and `_shared/work-record.md`'s shared `recordPayload`/`specShapedBody` creation logic, rather than reimplementing type resolution independently in each skill. For the `work-types: labels` fallback, reuse whatever label-stamping convention other create paths already follow (bootstrap-if-needed pattern, e.g. `gh label create "type:task" ... || true`) so the default type assigned to a Defer-filed record (likely `type:task`, since these are typically maintenance/follow-up records) is consistent with how `/claude-tweaks:specify`'s own shaping pass assigns `type:*`.

### Key Files
- `plugin/skills/reflect/full-mode.md` — Defer path; add type/label stamping to the creation step
- `plugin/skills/_shared/work-record.md` — `recordPayload`/`specShapedBody` shared creation logic; the natural place to centralize type stamping so every consumer of this shared path gets it, not just reflect
- `plugin/skills/capture/SKILL.md` (or wherever its GraphQL `issueTypeId` stamping lives) — reference implementation to reuse/extract from
- `plugin/bin/compose-subject.js` — the consumer whose Type-resolution contract this closes; no change expected here, but useful for confirming the exact resolution logic being satisfied

## Gotchas
- If `work-record.md`'s shared creation path is where the fix lands, check every existing consumer of `recordPayload`/`specShapedBody` (not just reflect) to make sure the fix doesn't introduce an unexpected type/label onto a create path that intentionally handles typing differently.
- Decide what native type (or `type:*` label) a Defer-filed record should default to when the record's content doesn't obviously map to bug/feature/task — a defer recommendation from `/claude-tweaks:reflect` is very likely `type:task` in the overwhelming majority of cases, but confirm this doesn't blindly overwrite a case where the reflect skill already has better signal about the record's nature.
- This is a create-time fix; existing already-filed Defer records that are still untyped are not automatically retrofitted by this work — decide separately (out of scope here unless folded in) whether a backfill sweep of existing untyped reflect-filed records is warranted.
