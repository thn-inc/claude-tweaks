# 2636: bookkeeping-stamps gate: claim-log branch (#2526) is dead code due to short-circuit ordering + regex/log-format mismatch

Surface: infra

## Current State
`checkBookkeepingStampsGate` in `plugin/bin/lib/hooks/pre-tool-use.js` opens with:

```js
if (runState.worktree && (runState.pr || runState.prExempt)) return {};
```

Record #2526 added a new claim-log enforcement branch (`if (!runState.claimExempt) { ... }`, ~line 1590) positioned *after* this short-circuit and after `hasMaterializeCommit`. Its own inline comment argues the ordering is safe because "by the time `runState.worktree` is ever set at all, `claimExempt` must already have been memoized." That invariant does not hold: `runState.worktree` and `runState.pr` are typically both stamped within the first few minutes of any real pipeline run (Common Step 1 / PR-early lifecycle), well before the claim-log branch's own precondition (`hasMaterializeCommit`) is reached on a later covered git call. Once both are set, the top short-circuit returns `{}` immediately on every subsequent call, so the claim-log branch never executes.

Verified against pipeline run `2026-09-20T002426-record-1235` (a 13-record bundle, one of whose records was #2526 itself): `events.jsonl` shows zero `claim-log`-stamp `bookkeeping-stamp-deny` events and zero `wd-foreign-session` events across 43 commits made after the #2526 commit (`ae4e7b7da`) landed, even though a direct replay of `getMaterializedRecordNumbers()`/`hasLoggedClaim()` against that exact run directory shows all 13 record numbers would classify as "missing claim" if the branch were ever reached.

Separately, even were the ordering fixed, `hasLoggedClaim()`'s regex (`Step 2\.8: claimed #${n}\b`) only matches a *single-target* claim log line. A multi-record `/flow` invocation's actual Step 2.8 log line (`flow/claim-targets.md`'s batch form) reads e.g. "Step 2.8: Claimed all 13 targets under run ... (claim-targets.js exit 0)" — no per-number "claimed #{n}" substring at all. Every multi-record run would misclassify every one of its targets as missing a claim.

## Deliverables
1. Move the `#2526` claim-log check (or an equivalent precondition) so it runs before the `runState.worktree && (runState.pr || runState.prExempt)` short-circuit — or otherwise restructure so the check is reachable in the real pipeline timeline, not only in a theoretical window that closes before the code enforcing it can ever be live.
2. Fix `hasLoggedClaim()` (or the multi-record Step 2.8 logging convention in `flow/claim-targets.md`) so a legitimate multi-target claim (the batch line format demonstrated above) is recognized — either by emitting one `Step 2.8: claimed #{n}` line per target in addition to the batch summary, or by relaxing the regex to also recognize the batch form.
3. Add a regression test that exercises the *real* shape: a run whose `run-state.json` already has both `worktree` and `pr` set (the common case for any call after the first few minutes of a run) plus a materialize commit, asserting the claim-log check still fires when a claim is genuinely missing.

## Acceptance Criteria
1. A synthetic run with `run-state.json.worktree` and `run-state.json.pr` both already set, a landed materialize commit, and NO claim logged for one of its materialized record numbers is denied (or the appropriate warn/deny per `isForeignSessionCall`) by `checkBookkeepingStampsGate` — proving the branch is reachable in the post-stamp steady state, not only in a narrow pre-stamp window.
2. A synthetic multi-record run whose `decisions.md` carries only `flow/claim-targets.md`'s real batch-claim line (`Step 2.8: Claimed all N targets under run ...`) is NOT denied for any of its legitimately-claimed targets.
3. `tests/hooks-bookkeeping-stamps-gate.test.js`'s existing fixtures (which hand-write the intended single-target `Step 2.8: claimed #{n}` line) still pass unchanged.
4. `npm test` green.

## Technical Approach
Restructure `checkBookkeepingStampsGate` in `plugin/bin/lib/hooks/pre-tool-use.js` so the claim-log enforcement branch (added in #2526) runs before, or independently of, the `runState.worktree && (runState.pr || runState.prExempt)` short-circuit — the short-circuit must not be able to bypass a claim-log check that is meant to gate every covered git call, not just calls in a narrow pre-stamp window. Separately, fix the single-target-only regex in `hasLoggedClaim()` (or change `flow/claim-targets.md`'s batch logging convention) so a legitimate multi-target claim is recognized — either emit one `Step 2.8: claimed #{n}` line per target alongside the batch summary line, or relax the regex to also match the batch form (`Step 2.8: Claimed all N targets under run ...`). Add the regression test described in Deliverable 3, using a synthetic `run-state.json` that reflects the real post-stamp steady state (both `worktree` and `pr` already set) rather than the narrow theoretical pre-stamp window the current code assumes.

### Key Files
- `plugin/bin/lib/hooks/pre-tool-use.js` — `checkBookkeepingStampsGate`: reorder or restructure the claim-log branch (~line 1590) relative to the `runState.worktree && (runState.pr || runState.prExempt)` short-circuit
- `plugin/bin/lib/hooks/pre-tool-use.js` — `hasLoggedClaim()`: fix or relax the single-target-only regex (`Step 2\.8: claimed #${n}\b`) to also recognize the multi-record batch claim form
- `plugin/skills/flow/claim-targets.md` — alternatively (or additionally), adjust the batch-claim logging convention to emit per-target `Step 2.8: claimed #{n}` lines
- `tests/hooks-bookkeeping-stamps-gate.test.js` — add the new regression test(s) covering the real post-stamp-steady-state shape and the multi-target batch-claim shape; verify existing fixtures still pass unchanged

Because the branch has never actually executed in a real run, there's no live-run evidence yet of what a *correct* denial looks like end-to-end; the regression test in Deliverable 3 is the first real exercise of that path.
