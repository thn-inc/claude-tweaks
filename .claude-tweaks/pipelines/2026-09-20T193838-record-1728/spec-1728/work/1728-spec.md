# 1728: dispatch: build,test call's claim/materialize/PR-open bookends silently no-op in gh-absent (MCP-transport) sandboxes

Surface: backend

## Current State

`#1486`/PR #1707 (merged ~06:15 UTC 2026-08-31, less than an hour before this run) fixed a claim-persistence defect in the dispatch two-call `build,test` → `review,polish,wrap-up` flow, but the fix (`plugin/bin/lib/claim-targets/claim-targets.js` and friends) is built entirely on `deps.gh` — a generic runner shaped like `gh(args)` — with no MCP-native branch. `claim-targets.js`'s own header states every side effect (`ghApi`, `gh`, ...) goes through `deps`, but nothing in that file substitutes a GitHub-MCP-tool-backed implementation when `gh` the CLI is genuinely absent from the sandbox.

This run (`/claude-tweaks:dispatch next` fired from a scheduled Routine in a cloud sandbox with no `gh` CLI installed — confirmed via `command -v gh` → exit 1) reproduced the *same failure class* #1486 described, immediately after that fix landed, but with a wider blast radius:

- The first Task call (`build,test`) reported `DONE` / `OUTCOME: build-test-ok` and committed `c25cd63`, but:
  - **No claim was ever persisted** to the `claims-registry` branch for this run's identity (`2026-08-31T061940-record-833`). The only prior claim history on `claims/issue-833.json` was an unrelated 2026-08-25 run, already released stale by `/claude-tweaks:tidy` on 2026-08-29.
  - **No `work/833-spec.md` was materialized.**
  - **No `config.yml` was written** to the run directory.
  - **No PR was opened at run start**, despite `integration-model: pr-first` (`.claude-tweaks/policy.yml`) documenting a PR born at run start (`_shared/pr-early-run-lifecycle.md`).
- The second Task call (`review,polish,wrap-up`) independently audited raw artifacts, found none of the above bookends had landed, and recovered by hand: reclaimed #833 under its own run identity via the MCP conditional-write path (`create_or_update_file` against the stale tombstone's blob sha, per `_shared/issue-claims.md`), and opened PR #1727 itself mid-run instead of at run start.

This is the same recovery pattern #1486's own second-call audit used originally — meaning the fix in PR #1707 did not close the gap for the MCP-transport path, only (at most) the `gh`-CLI path. The recovery worked this time only because the second call happened to run a thorough raw-artifact audit; nothing in the pipeline forces that audit, so a second call that trusts the first call's `DONE`/`build-test-ok` report at face value would leave the record permanently unclaimed with no PR, indistinguishable from a healthy run until the retry ceiling or a human eventually notices.

## Deliverables

- [ ] Identify every Step 2.8/materialize/PR-open call site in `flow/claim-targets.md`, `flow/materialize.md`, and `_shared/pr-early-run-lifecycle.md`'s implementation that assumes `deps.gh`/the `gh` CLI is present, with no MCP-backed equivalent wired in for a `gh`-absent sandbox.
- [ ] Either wire an MCP-backed `deps.gh`-shaped adapter into these call sites (mirroring the pattern `dispatch/mcp-transport.md` already documents for dispatch's own queue pull), or make the failure loud instead of silent — a `build,test` call that cannot claim/materialize/open-PR should report `BLOCKED`/`build-test-blocked`, never `DONE`/`build-test-ok`.
- [ ] Add the same post-write read-back #1486/PR #1707 was supposed to add, verified specifically against a `gh`-absent sandbox this time (the original fix's own verification apparently only covered the `gh`-CLI transport).

## Acceptance Criteria

- A fresh `/claude-tweaks:dispatch next` run against a fresh record, in a sandbox with no `gh` CLI installed, produces a verifiable claim commit on `claims-registry`, a materialized `work/{n}-spec.md`, a written `config.yml`, and an opened PR — all before the first Task call reports `DONE`/`build-test-ok` — confirmed by direct inspection, not the call's own self-report.
- If any of these cannot be made to work on the MCP transport, the first Task call reports `BLOCKED`/`build-test-blocked` instead of a false `build-test-ok`, so the two-call gate (`dispatch/two-call-gate.md`) never dispatches a second call on top of an unclaimed, unopened run.

## Technical Approach

Same investigation shape as #1486, extended to the MCP-transport branch specifically:

- Confirm which of `claim-targets.js`'s `deps.gh` calls actually executed in this sandbox (none should have succeeded if `gh` is genuinely absent from `PATH`) versus which silently no-op'd or were skipped by a caller-side guard.
- Trace `flow/materialize.md`'s and `_shared/pr-early-run-lifecycle.md`'s own call sites the same way — this record's build call skipped spec materialization and PR-open too, not just the claim, so the root cause may be one shared upstream guard (e.g. a `gh`-presence check that silently skips a whole block of Step 2.x rather than erroring) rather than three independent defects.
- Cross-reference against `dispatch/mcp-transport.md`, which documents MCP substitutions for dispatch's own Step 2 queue pull but says nothing about `/flow`'s internal Step 2.8/materialize/PR-open — suggesting those were never bridged to MCP at all, unlike dispatch's own queue-pull path (the bridge plan referenced there, `docs/superpowers/plans/2026-08-02-dispatch-mcp-bridge.md`, deleted `d83f0720`, may only have covered dispatch's own call sites).

## Gotchas

- Don't assume this is identical to #1486's root cause just because the symptom (missing claim) matches — that fix already merged and evidently didn't prevent recurrence here, so treat this as a distinct, MCP-transport-specific investigation rather than a re-verification of the same fix.
- The second call's recovery (reclaim + late PR-open) left the record in a consistent, non-broken end state (`pending-review`, claim released, PR #1727 open) — this is not data loss, but a reliability gap: the recovery depended on the second call happening to audit raw artifacts rather than trust the first call's report, which is not guaranteed behavior.
- This sandbox's `gh`-absence is not an edge case for this repo's own scheduled Routines — `/claude-tweaks:dispatch next` is exactly the routine-fired form, and cloud Routine sandboxes are exactly where `gh` is most likely to be absent (per CLAUDE.md's Cloud parity section). Every future `next`-form firing in such a sandbox risks the same silent bookend gap.
