# 2658: specify: investigate whether decomposition-mode record-creation has a retry-duplicate hazard

Surface: infra

## Current State
`#2626` and `#2627` were created 9 seconds apart from the same `/claude-tweaks:specify` decomposition run of `docs/superpowers/specs/2026-09-20-playwright-cli-browser-driver-design.md` — `#2626` carried the pre-red-team body, `#2627` the red-teamed final version. `#2626` was closed as a duplicate after a live sibling session had already claimed it and opened a PR against it. This investigation confirms the mechanism that makes this possible: `plugin/skills/specify/record-creation.md`'s "Idempotency (resume path)" section (lines 16-59) builds a fingerprint→number map once per Step 3 invocation from a session-scoped snapshot, and its own prose (line 61) states the required behavior explicitly — *"immediately before each individual create — a kept parent included, and not just once against the batch list above — re-check that record's fingerprint against the map... On every successful create, add the new record's fingerprint and number to the in-memory map before moving on."* That sentence is the entire enforcement mechanism: there is no literal bash conditional implementing this re-check anywhere in either `record-creation.md` (parent creation, lines 69-120) or `record-creation-subissues.md` (sub-issue creation, lines 51-96) — both files go straight from composing the record payload to calling `gh issue create`/`gh issue edit` with no `if fingerprint in map: skip` guard in the code shown to the executing agent. The idempotency check exists only as a natural-language instruction the agent is expected to remember and apply on every iteration of a per-sub-issue loop, with no mechanical enforcement (no CLI helper, no script-level gate) making a skipped check visible or impossible. This is exactly the class of hazard the issue's Scope section asked to rule in or out: a retry-without-idempotency-check path is not present as an intentional retry loop, but the *absence of code-level enforcement* for the idempotency check that is supposed to run before every create means an agent under time pressure, mid-way through a multi-sub-issue loop, distracted by a red-team pass between two creates (as `#2626`/`#2627`'s pre-/post-red-team body difference suggests), or working from ambiguous tool output can create a duplicate without violating any coded rule — because there isn't one to violate. A genuinely concurrent sibling session remains a live alternative explanation and is not ruled out by this finding; both mechanisms can independently produce the observed 9-second-apart duplicate.

## Deliverables
1. Convert the prose-only idempotency re-check (`record-creation.md` line 61) into a mechanically enforced step: either an explicit bash conditional inlined at each create call site that looks up the fingerprint in the already-built `$SPECIFY_EXISTING_FINGERPRINTS` map and skips the `gh issue create`/`gh issue edit` call when a match is found, reusing the mapped number instead — or a small helper (e.g., a `bin/lib/issues/` function) both `record-creation.md`'s parent-creation block and `record-creation-subissues.md`'s sub-issue-creation block call before every create, so the check is structurally impossible to skip rather than dependent on the executing agent remembering a paragraph of prose.
2. Update the in-memory fingerprint map on every successful create (as the same prose already specifies) via the same mechanical path, so a same-run collision between two units that happen to slugify to the same name is caught the same way a prior-run or concurrent-session collision is.
3. A short note in `record-creation.md`'s Idempotency section documenting this hardening and referencing this record, so a future reader understands why the check moved from prose to code.

## Acceptance Criteria
- `record-creation.md`'s parent-creation block and `record-creation-subissues.md`'s sub-issue-creation block each contain an explicit, inspectable check (a bash conditional or an equivalent helper call) that consults the fingerprint map before calling `gh issue create`/`gh issue edit`, not only a prose instruction to do so.
- Simulating a resumed decomposition run (a fingerprint already present in `$SPECIFY_EXISTING_FINGERPRINTS`) causes the check to skip the create and resolve to the existing record's number, verified by a test or a manual dry run against a fixture map.
- Simulating a fresh fingerprint (no match in the map) causes the check to proceed to the normal create path unchanged.
- The map is demonstrably updated in-memory after each successful create within the same run (a second unit with a colliding fingerprint in the same batch is caught, not just a fingerprint from a prior run).
- Docs note that this hardening addresses the `#2626`/`#2627` duplicate-creation hazard's confirmed mechanism (prose-only enforcement), while leaving the genuine-concurrent-session explanation as a still-open, independent possibility.

## Technical Approach
Do not build a separate idempotency subsystem — the fingerprint map, its construction, and its intended check-before-create semantics already exist and are correctly designed in `record-creation.md`'s Idempotency section; the gap is purely that the check was never translated from prose into the literal bash shown at each create call site. Add the missing conditional directly at both call sites (parent creation in `record-creation.md`, sub-issue creation in `record-creation-subissues.md`), reading from the same `$SPECIFY_EXISTING_FINGERPRINTS` file already built and already in scope at both points, and write the newly-created fingerprint back into that same file (or an in-memory equivalent within the loop) immediately after each successful create, matching the update timing the existing prose already specifies.

### Key Files
- `plugin/skills/specify/record-creation.md` — add the missing bash conditional before the parent's `gh issue create` calls (lines 109-120), consulting and updating `$SPECIFY_EXISTING_FINGERPRINTS`.
- `plugin/skills/specify/record-creation-subissues.md` — add the missing bash conditional before each sub-issue's `gh issue create` calls (lines 78-96), consulting and updating the same fingerprint map.
- `plugin/bin/lib/issues/record.js` — home of `extractFingerprint`, already used to build the map; a new small helper here (e.g., a `checkFingerprint`/`recordFingerprint` pair) is a candidate location if the hardening is implemented as a shared function rather than inlined bash at each site.

## Gotchas
- This is a documentation-and-procedure fix, not a code-behavior fix in the traditional sense — `record-creation.md`/`record-creation-subissues.md` are skill markdown files that an LLM agent executes by reading and following, so "enforcement" here means making the check unambiguous and impossible to silently skip in the instructions themselves (or backing it with an actual CLI helper), not compiling anything.
- The genuinely-concurrent-sibling-session explanation for `#2626`/`#2627` is not ruled out by this finding and should not be treated as disproven — both mechanisms (prose-only enforcement skipped, and two live sessions decomposing the same design doc) can independently produce a duplicate, and this record's fix only closes the first one.
- Verifying the fix without a live duplicate-creation incident requires either a synthetic test harness around the bash snippets (hard, since these are prose-embedded shell fences meant for an LLM executor, not a standalone script) or a careful manual dry run with a fixture fingerprint map — plan for the latter unless `bin/lib/issues/record.js` gains an extractable, directly-testable function per the Technical Approach's helper option.
