# 2970: Multi-spec runs: brief and timing run-comments still share one unqualified marker per PR

Origin: review of #2860 (run 2026-10-04T162837-record-2860)

Defer-reason: tangential

## Current State

`plugin/skills/_shared/pr-run-comments.md` spec-qualifies only the `verdict` kind under a multi-spec run (`<!-- run-comment: verdict:{spec} -->`, section "Multi-spec verdict comments (#2592)", lines 41-61). The `brief` and `timing` kinds still carry one unqualified marker per PR (Comment kinds table, lines 31-32; Consumer table, lines 116-117).

`plugin/skills/wrap-up/verification-brief.md` Step 4 (lines 308 and 317-319) composes `<!-- run-comment: brief -->` and `<!-- run-comment: timing -->` with no `$MULTISPEC_PARENT_DIR` branch, and posts via the find-or-update procedure. Acceptance labeling is not on `wrap-up/execution-and-verification.md`'s `MULTISPEC_REVIEW_DEFER` skip list (line 9), so each spec's wrap-up in a multi-spec `/flow` run reaches that step against the one shared PR. Spec B's find-by-marker then matches spec A's `brief` (and `timing`) comment and replaces it in place — while spec A's issue keeps a pointer comment saying its Verification Brief is on the PR. This is the same overwrite hazard #2592 fixed for `verdict`.

Not yet observed live: the one multi-spec PR inspected (#2856) carries no `brief` or `timing` comment at all. The gap is established from the prose, so the first deliverable is to confirm which multi-spec paths actually reach Step 4 per spec (direct `/flow #A,#B` versus a dispatch bundle, whose group gate posts one brief for the whole closing set).

## Deliverables

1. Trace which multi-spec paths post `brief` and `timing` per spec to the shared PR, and record the result in `pr-run-comments.md`.
2. For every path that does: rule the multi-spec shape for `brief` and `timing` in `pr-run-comments.md` (spec-qualified marker like `verdict:{spec}`, or an explicitly stated single run-level comment — `timing` may suit the latter, since `flow/multispec-summary.md` already renders one parent-level Timing table), and make `verification-brief.md` Step 4 compose it.
3. Extend `tests/pr-run-comments.test.js` to pin the ruled shape for both kinds.

## Acceptance Criteria

- `pr-run-comments.md` states, for `brief` and for `timing`, what a multi-spec run posts to the shared PR, and no kind posted per spec is left with a bare shared marker.
- `verification-brief.md` Step 4 composes the ruled marker when `$MULTISPEC_PARENT_DIR` is set, and the single-spec markers are unchanged.
- A conformance test fails when either rule is removed.

## Release Note

Multi-spec pipeline runs keep every spec's Verification Brief and timing on the shared PR instead of the last spec's replacing the earlier ones.
