# 5604: Wait instructions name wait-for.js instead of sleep 20, and a parked record measures the result after 30 days

## Current State

Every instruction that tells a dispatched agent how to wait names `sleep`. Checked on 2026-11-16 at `026e203f3`:

- The keep-alive rule for nested `Agent` children says "repeated `sleep 20` Bash calls, at most 60 (20 minutes) per wave of children". Its one definition is the Foreground Execution Discipline section of `plugin/skills/_shared/subagent-dispatch-core.md` (line 72). After #5601 removes the four template copies from the dispatch prompts, two more copies remain: item 7 of the Context pack in `plugin/skills/dispatch/task-prompt.md` and the `Async-wait discipline (required):` paragraph of the template in `plugin/skills/flow/context-handoff.md`.
- The same section's "Bounded polling for a long external wait" paragraph gives `sleep 20 && gh run view {id} --json status,conclusion` as the pattern for a CI run or a deploy (line 131).
- `flow/context-handoff.md` line 52 restates the bound in prose ("`sleep 20` at most 60 times, 20 minutes").
- `docs/skill-graph.md`'s `_shared/subagent-dispatch-core.md` row describes the rule and its copies. Four files under `docs/journeys/` state it with the same numbers: `hand-a-phase-to-a-fresh-agent-at-the-context-cap-4027.md`, `keep-a-second-reader-in-a-dispatched-review-3078.md`, `keep-waiting-on-a-progressing-implementer-4557.md` and `route-a-late-rendered-ui-review-result-5280.md`.
- `tests/foreground-execution-instruction.test.js` pins the primitive (`PRIMITIVE`, `EXPECTED_PRIMITIVE = '20/60/20'`) and the sentences around it (`SHARED_RULE`, `PROGRESS_CHECK`) in every copy.
- Under the rule, the child's `<task-notification>` is what tells the agent a child has reported. The sleeps only keep the turn alive until it arrives.

The bound is a count of calls, not elapsed time, which #4959 reports as a defect: waits that return early end the 20 minutes early.

#5602 adds `plugin/bin/wait-for.js`, and this record is built after it and #5601 have merged. Nothing reads the command until this record lands. What this record's prose relies on, from #5602:

- `wait-for.js agents --ids <a,b>` blocks until a listed child agent has stopped for good, or a bound passes. `wait-for.js ci --pr <n>`, `ci --run <id>` and `pid --pid <n>` do the same for a pull request's checks, a workflow run and a process.
- `--max-seconds` bounds one call (default 100, at most 150). The command keeps a 20-minute window per wait by itself: every call of one wait prints the same `deadlineEpoch` and `window` number, and the call after a deadline opens the next window. The caller passes no deadline.
- It prints one JSON line and exits 0 on a change, 3 at a bound (`"bound":"call"` or `"bound":"deadline"`) and 2 on a failed call.
- A stop is returned by one call only, so repeating a call never returns the same stop twice.
- #5602 ships the `agents` target only if its probe (`docs/reference/blocking-wait-probe.md`) showed that a child's stop reaches a waiting subagent in an interactive session, under a headless worker and in a handoff child. If #5602 merged with its probe and tool only, this record is not built; it goes back to shaping.

Measured on 2026-11-16 over the 30 days from 2026-10-17 (#5602's Current State has the table): 54,034 of the 696,991 Bash calls subagents made begin with `sleep` (7.8%). 53,509 of those (99.0%) are exactly `sleep 20`, the primitive this prose names, and 96.5% wait on a child agent's notification.

Design: `docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 4, unit 4.1, last part: "the prompts name it".

## Deliverables

1. **The keep-alive rule names the command.** In the core section, item 7 and the handoff template, the wait on nested children is one invocation line, stated once per copy:
   `node "{plugin-root}/bin/wait-for.js" agents --ids {ids} --max-seconds 150`
   (the core section writes `${CLAUDE_PLUGIN_ROOT}` where the two prompt copies write `{plugin-root}`). The rule states:
   - `{ids}` are the agent ids of the children whose notification has not arrived and that no call has reported, comma-separated (build alignment: `agents` returns each stop once, so a reported child left in `{ids}` would hold the next call for its full 150 s);
   - every call is a foreground Bash call with no `timeout` parameter: the command returns within 150 seconds, under the 180-second ceiling #5602's probe measured for a dispatched agent;
   - exit 0 means a listed child stopped: its notification is in hand or arrives next, and the agent calls again while any child is outstanding;
   - exit 3 with `"bound":"call"` means call again;
   - exit 3 with `"bound":"deadline"` means the 20-minute window is over, and the at-bound rule applies as it does today; when that rule grants another window, the next call is that window;
   - exit 2, or a call the harness blocks, is a failed wait call. The present sentence covers it unchanged: it is not a wait, it is never retried in another form (a `sleep` included), and every child still outstanding is treated as silent at the bound;
   - the command's output line is the wait's log line, so the agent writes no separate one.
2. **The windows keep their meaning.** A window is 20 minutes by the clock. Five sentences are reworded, and only these:
   - "repeated `sleep 20` Bash calls, at most 60 (20 minutes) per wave of children" becomes the invocation line and "20 minutes per wave of children";
   - "each wait logged per the bounded-polling paragraph below (what is waited on, the iteration against the bound, how many children are still pending)" becomes the last bullet above;
   - "grant one more 60-wait window" becomes "grant one more 20-minute window";
   - "(a longer, wrapped or backgrounded sleep)" names a `sleep` of any length among the forms a failed call is never retried in;
   - "is not a wait and never counts toward the bound" says a failed call does not move the window's deadline.
   Unchanged, word for word: the read-only probe commands, "stop when a whole window passes with no change", the ceiling of 3 windows (60 minutes) per wave, the two stop reasons, "A failed wait call counts as no wait but ends its window", the read-only self-judge at the first bound, the rendered-UI exception, never reading a running child's `output_file`, and never redoing a write-capable child in-session.
3. **The bounded-polling paragraph names the command.** For a pull request's checks it names `wait-for.js ci --pr`, for a workflow run `wait-for.js ci --run`, for a local process `wait-for.js pid`, each called as the `agents` form is (foreground, no `timeout`, `--max-seconds 150`) with the same three exit codes: 0 read the result, 3 with `call` call again, 3 with `deadline` do what the paragraph says today for an exhausted bound. For any other external condition (a deploy, a log line) the paragraph keeps its present wording, a bounded check-interval loop of foreground calls, without the `sleep 20 && gh run view` example. Decided 2026-11-16: no generic target is added for those conditions. The targets the command does not cover are 1,096 of the 54,034 sleep-led calls (2.0%), and the parked record's per-target table shows whether one of them is worth a target.
4. **Restatements follow.** `flow/context-handoff.md` line 52, the `_shared/subagent-dispatch-core.md` row of `docs/skill-graph.md`, and the four journey files state the new primitive.
5. **Tests.** `tests/foreground-execution-instruction.test.js` pins the invocation line and each reworded sentence in every copy, each with a go-red proof; `PRIMITIVE` and `EXPECTED_PRIMITIVE` are replaced by the invocation line and the 20-minute window. One test byte-pins the invocation line as it appears in the core section and runs it against the real CLI.

## Gotchas

- Done for the design means a 30-day replay of new transcripts shows sleep-led Bash calls in subagents under 0.5% of their Bash calls. That can be seen only after a release has been in use, so it is the parked record's job, not a criterion here. The threshold can be reached through the keep-alive rule alone: the sleeps that wait on anything but a child agent are 1,902 calls in the measured window, 0.27% of subagent Bash calls. The measurement reads one machine's transcript store; cloud routine runs are not in it, and the parked record says so.
- #4959 asks for the same sentence to measure elapsed time. The command's window does that. If #4959 lands first, keep its wording for elapsed time and replace only the primitive; if this lands first, #4959's first two criteria are met and its test criterion is re-read against the new patterns.
- #4989, #5147, #4663 and #5254 edit the same copies or their tests. Rebase on whichever has landed, under the ownership rule in the Technical Approach.
- #5066 adds a hook check that a dispatched implementer did not start a long command with `run_in_background`. A `wait-for.js` call is a foreground call and is outside that check. #5066 also edits `tests/foreground-execution-instruction.test.js`.
- A run in flight on the previous release holds a prompt that says `sleep 20`. Nothing here makes that fail. An agent that reads the new prose has the command, because the prose and `wait-for.js` ship in one plugin version and the prompt names the dispatching session's own plugin root. If the root is wrong or unfilled, every CLI call in the prompt fails, this one with exit 127 or 2; that is a failed wait call, and the rule's own terminal path applies: the children are treated as silent at the bound.
- The merge gate's 15-minute bounded watch in `_shared/pr-first-merge.md` is a shell loop inside one Bash call and keeps its two `sleep 30` lines. It is not a sleep-led call, and thirteen open records list that file. It is out of scope here; the parked record's per-target table shows whether CI waits remain worth a follow-up.
- AC2 and AC3 bind skill prose and the journeys, the text an agent is told to follow. Docs elsewhere that describe the old rule (the incident log, the changelog) are history and stay.
- The harness moves a dispatched agent's foreground Bash call to the background after 180 seconds, with or without `timeout` (`docs/reference/blocking-wait-probe.md`, from #5602), which is the failure the foreground rule exists to prevent. `--max-seconds 150` keeps every call under that ceiling, and the command refuses a larger value. Its default of 100 seconds covers an agent that passes no flag, and its default 20-minute window bounds the whole wait.
- Read `.claude/skills/skill-prose-conformance-tests` for the byte-pinned snippet and the go-red proofs.
