# 3063: verify.js has no per-check or per-run timeout — a hung test file hangs verification (and baseline adjudication) forever

Origin: ledger resolve gate
Defer-reason: genuinely-larger

**Related:** #3064

## Current State

`plugin/bin/lib/verify/run.js`'s `runOne` spawns each check, and since #3043 each baseline base or isolated per-file run, with no timeout. A test file that never exits (a leaked handle, a deadlock under load) hangs `verify.js` indefinitely. The orchestrator then cannot tell "slow" from "hung", and `--baseline`'s scratch worktree is never removed.

Evidence: #3043's final whole-branch review (follow-up M1/timeouts) and ledger row 18.

## Deliverables

- [ ] Add an optional per-run timeout to `runOne`. On expiry it kills the child tree and records the run as `{timedOut: true}` with a null exit code. A null exit is never adjudicated and never passes.
- [ ] Add a `--cmd-timeout <name>=<ms>` flag for checks. Baseline base and isolated runs get a bounded default derived from the check's own timeout.
- [ ] A timed-out baseline run is no evidence: the file stays attributable, and stdout names the timeout.

## Acceptance Criteria

- [ ] A check whose command sleeps past its timeout ends the run with exit 1, a `timedOut` entry in `report.json`, and no stamp.
- [ ] A `--baseline` per-file run that times out leaves its file attributable, with a stdout line naming the timeout.
