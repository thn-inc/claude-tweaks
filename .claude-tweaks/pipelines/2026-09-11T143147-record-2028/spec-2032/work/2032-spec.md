# 2032: recordLabels and ghReadGrants issue sequential gh calls per record instead of Promise.all

## Current State
`recordLabels` (`plugin/bin/lib/wrap-up/pack.js:393-400`) loops sequentially over `inputs.records`, `await`ing one `gh issue view {n} --json labels` call per record, instead of running the independent per-record calls concurrently via `Promise.all` — `pack.js` already uses `Promise.all` elsewhere in the module (line 452, over its top-level probe set). A multi-record flow run with N=4-5 backlog records pays N sequential gh round-trips (network latency, ~300-800ms each) instead of running concurrently, adding seconds of unnecessary wall-clock time to the wrap-up fact pack that gates release.

`ghReadGrants` (`plugin/bin/console-resolve.js:73-84`, not `plugin/bin/lib/console/resolve.js` as originally cited — that file only *consumes* it via the `readGrants` dependency) is a different shape: its per-record `execFile('gh', [...], {cwd})` calls are synchronous (`execFile` there defaults to `execFileSync`-based `defaultExecFile`, line 51), not `await`ed promises. `readSnapshot` (`plugin/bin/lib/console/resolve.js:120-138`) calls `deps.readGrants(members)` synchronously inside a plain `try/catch` and `resolveAll` (`resolve.js:292`) itself is not `async`. Converting `ghReadGrants` to `Promise.all` would require first converting its `execFile` primitive to an async form, then threading `async`/`await` through `readSnapshot`, `resolveAll`, and `console-resolve.js`'s own `run()` — a materially larger, structurally invasive change to a file whose header comment says it deliberately "resolve[s] ... in one process," not a drop-in loop conversion. That part of the original request doesn't hold as scoped and is left out of this record's deliverables.

## Deliverables
- [ ] Convert `recordLabels`'s `for (const n of inputs.records) { await gh(...) }` loop (`pack.js:393-400`) to `Promise.all(inputs.records.map(async (n) => { ... }))`, preserving the `{[n]: labels[]}` output shape.

## Acceptance Criteria
1. `recordLabels` issues its per-record `gh` calls concurrently.
2. No behavioral change to the returned data shape (`{[recordNumber]: string[]}`) or error handling (a rejected call still surfaces the same way it does today).
3. Existing `tests/bin-lib/wrap-up/pack.test.js` `recordLabels` assertions (lines 122-123, 139, 221, 318-321, 326-329, 425-426) pass unchanged.

## Technical Approach
Mirror the existing `Promise.all` idiom already used in this file (`pack.js:452`) rather than introducing a new pattern.

### Key Files
- `plugin/bin/lib/wrap-up/pack.js` — `recordLabels` (line 393)
- `tests/bin-lib/wrap-up/pack.test.js` — existing `recordLabels` coverage to keep green

## Gotchas
- `ghReadGrants` (`plugin/bin/console-resolve.js:73`) is out of scope for this record: it's exec-synchronous, not async/await, and its result is consumed synchronously by `resolveAll`/`readSnapshot` — converting it would ripple through the whole console-resolve call chain, a separate and larger-scoped change than "convert a loop."
- `claim` (`pack.js`, a few lines below `recordLabels`) has the identical sequential-loop shape and is not part of this record's scope either — the original request named only `recordLabels` and `ghReadGrants`.
