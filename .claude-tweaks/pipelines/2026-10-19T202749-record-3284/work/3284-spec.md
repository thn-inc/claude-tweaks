# 3284: dispatch two-call split (build,test / review,polish,wrap-up) leaves no verify.js pass stamp for the second call to trust

## Current State

Under `dispatch/SKILL.md`'s two-call pattern (`/flow {target} build,test` then, in a fresh
Task-tool dispatch, `/flow {target} review,polish,wrap-up` against the same run dir), the first
call's `/test` phase logged its result to `decisions.md` as a plain summary line
(`npm test: full suite green at HEAD {sha}: {n} pass, 0 fail, {m} skipped`) rather than through
`test/verification.md`'s stamped `verify.js` invocation, which writes the runner-level pass stamp
`verify.js --stamp-status` reads. On this run (#3034), the second call's review Step 1.5
(`node bin/verify.js --stamp-status`) found `present: false` at the same HEAD the first call had
already verified, so it had no choice but to re-run the full suite from scratch (~117s) rather
than trusting the first call's already-passing result.

## Deliverables

1. Confirm whether `/claude-tweaks:test`'s own invocation path always writes the stamp, or
   whether some call shape (standalone CLI, a particular dispatch route) can log a pass without
   it, as observed here.
2. If a gap exists, close it so a `/flow {target} build,test` first call's test phase always
   leaves a stamp the second call's review-gate can trust.

## Acceptance Criteria

- A fresh two-call dispatch run (`build,test` then `review,polish,wrap-up` against the same
  `PIPELINE_RUN_DIR`) shows `verify.js --stamp-status` returning `verifiedHead: true` at the
  second call's review Step 1.5, with no full-suite re-run.

## Release Note

No user-visible change — internal pipeline-plumbing fix so a dispatched two-call run's second
call trusts the first call's own test pass instead of re-running it.

## Suggested resolution

Audit `/claude-tweaks:test`'s dispatch-context code path (the one `dispatch/SKILL.md`'s first
call invokes) against `test/verification.md`'s stamped-invocation requirement; add the stamp
write there if missing.
