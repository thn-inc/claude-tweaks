# 4899: claim-targets: a permission-denied claim read or write exits 4 as a transient retry

Surface: backend

**Related:** #4264, #4265, #4664, #4736, #4794, #3706, #3878

## Current State

`classifyGhApiError` (`plugin/bin/lib/issues/claim-store.js`) returns `permission-denied` for a plain HTTP 401/403 (#4756), and the claims-branch bootstrap routes that to a refusal (exit 6). The per-target claim read and write sites in `plugin/bin/lib/claim-targets/claim-targets.js` still send it to `stopOrSkip(issue, 'transient', 'transient', 4, { error })`. So a revoked or under-scoped token exits 4 with `error: 'permission-denied'` as if a re-run could succeed. Under `--keep-going` the run skips that target and tries the next one with the same token. Under `/claude-tweaks:dispatch` it settles as an ordinary failed attempt: a failure comment, one attempt counted toward `dispatch-retry-ceiling`, and eventually the ceiling stripping the record's grants even though the record did nothing wrong.

Exit 6 is not the right home: it means the `claims-registry` branch is missing and creating it was refused, and its envelope is `{branchMissing: {branch, reason}, ...}`. A refused read on a branch that exists is a different fact.

`settle-and-merge.md` treats the claims-branch-missing stop as a pre-flight stop (no classification, no attempt counted, no failure comment, a headless self-report under `DISPATCH_HEADLESS=1`). `firing-exclusion.md` and `docs/journeys/act-on-a-contested-claim.md` have a drain move on to its next record after such a stop.

## Deliverables

The decision, made with the human while shaping this record: a claim read or write that GitHub refuses for permissions is a stop that needs a person, not a failed attempt. One rule covers it: **`read.failure` or `write.failure` equal to `permission-denied` in the per-target claim loop is exit 7.** Every other failure at those sites keeps its current exit.

1. `claim-targets.js` gains exit 7. A `permission-denied` claim read or write calls `abort({ permissionDenied: { issue, operation, reason } }, 7)`, not `stopOrSkip`, so it stops the run with or without `--keep-going` and releases claims this run already took (the same release path every abort uses; `released`/`releaseFailed` are in the envelope). `operation` is `read` or `write`. `reason` is GitHub's error text when the claim store carries it, else `permission-denied`. stderr carries one line with the remedy. The USAGE text and the comments at both sites are updated.
2. `plugin/skills/flow/claim-targets.md` adds an exit-7 bullet with its own static card, `## Flow: Claim permission denied`, naming the target, the operation and the reason, and telling the reader to check the token's access to the repository and the `claims-registry` branch. It does not suggest re-running, and has no `AskUserQuestion`. The "On exit 3, 4, 5, or 6" paragraph includes 7.
3. `plugin/skills/dispatch/settle-and-merge.md` treats this stop as a pre-flight stop, like the claims-branch-missing stop: failing-check-name `flow-step-2.8-claim-permission-denied` for the headless self-report under `DISPATCH_HEADLESS=1`, and steps 3-7 skipped (no `failure-check` classification, no attempt counted against `dispatch-retry-ceiling`, no failure comment, no `bot:blocked`, grants untouched).
4. A dispatch firing stops at the first such stop and attempts no further group, in every selection form, because every group uses the same token. `plugin/skills/dispatch/SKILL.md` states this beside its Repo-wide infra outage stop, and `firing-exclusion.md` and `next-ranking.md` name the stop without describing a move to the next record. The firing's report names the record and the stop.
5. `docs/plugin-structure.md`'s claim-targets exit-code line and `docs/journeys/act-on-a-contested-claim.md` describe exit 7 and the new card, and no longer say a claim read or write 401/403 exits 4.

## Release Note

A claim read or write that GitHub refuses for permissions now stops the run and says which token access to fix, instead of counting as a failed attempt to retry.

## Technical Approach

Add `7` beside the other exit codes and route the two `permission-denied` sites through `abort` before their existing `stopOrSkip` calls. The classifier does not change. Exit 7 is new surface that the CLI and its consumers ship together in one plugin version, so there is no expand-contract window: a consumer reading an older CLI simply never sees it.

## Gotchas

- Bootstrap permission failures stay exit 6. This record changes only the per-target claim loop.
- Other callers of the classifier keep their exits: `list-claims.js`, `dispatch-resume.js`, `release-claim.js` and the dispatch first-call artifact check are out of scope.
- An unrecognised rate-limit-style 403 would now stop a firing where it could have retried. That is accepted: no attempt is counted, no grant is lost, and the next firing tries again.
- Releasing claims on the way out can itself be refused by the same token. `releaseFailed` reports that, and the claim lapses via its TTL. The exit stays 7.
- `--steps` and `--resume-pr` behave as before; a `--resume-pr` re-claim that is refused also exits 7.
- This is not a breaking change: exit 7 adds surface, and every consumer of the exit code ships in the same plugin.
