# 4281: Windows: worktree and write guards fail open when a Bash command names a quoted native D:\ path

Origin: #2767 class split — classification of windows-regression run 40169646104 (main 6a41ebe3a)

## Current State

In `plugin/bin/lib/hooks/git-command.js`, `isUnresolvable` (line 135) returns true for any token containing `\` (line 143). Lines 124-129 explain why: `tokenize` (line 94) is not escape-aware. `resolveCd` (159), the `-C` branch of `skipGlobalFlags` (301), `updateAssignment` (197) and `resolveWriteTarget` (525) all call it. An unprovable target means no target ("ambiguity resolves to allow", 519-520), and the deny gates in `pre-tool-use.js` need positive evidence (line 2047). A command naming a Windows path therefore gets no deny and no event.

There are two shapes:

- **Quoted native path, a real gap.** Examples: `mkdir -p "D:\…"` (pipeline-shadow-guard) and `git -C "D:\…\wt" push` (`hooks-pre-tool-use.test.js:1323`). Bash keeps these backslashes: single quotes keep all of them, and double quotes keep any not followed by `$`, `` ` ``, `"`, `\` or newline. So a Windows session gets past the worktree-isolation, shadow run-dir, policy.yml and teardown guards.
- **Unquoted native path, an unrealistic fixture.** Examples: `` `tee ${target}` ``, `` `sed -i … ${path.join(repo, 'a.js')}` `` and `cd D:\…`. Bash strips these backslashes, so `D:\a\_temp\x` becomes `D:a_tempx`. No real session sends this command.

24 tests in 5 files fail (lines as of 988cc584d). `:1638` comes from #4279 (run 40197254500): `` git -C "${main}" commit `` gets no deny.

## Deliverables

- Make `tokenize` produce each word's bash value: single-quoted text stays as it is, double-quoted text loses `\` only before `$`, `` ` ``, `"`, `\` or newline, and unquoted `\x` becomes `x`. Keep the per-token quote flags.
- Narrow `isUnresolvable`: a backslash left in that value is a literal path character. The `$`, backtick, `~` and flag rules stay. (As built: an unquoted stray final `\` is the one exception, since bash 3.2 drops it and bash 5 keeps it. `settleStrayBackslash` resolves it under `path.win32`, where both readings name the same path, and leaves it unresolvable under POSIX, as at base.)
- Pass `pathImpl` (default `path`) through `forEachCommandSegment` to `resolveCd` and `resolveWriteTarget`, and expose it as an option on `gitTargets`, `fileWriteTargets`, `mkdirTargets` and `teardownTargets`. A quoted `D:\repo\a.js` resolves through `path.win32`, and a drive-relative `D:a.js` stays unprovable. (As built: unprovable only across drives. A same-drive `D:a.js` resolves against the cwd, which is how Windows resolves it. The cross-drive fail-open is stated in `docs/hooks.md`.)
- (As built, to keep the guard closed) Strip NUL from the command before the walk, so the in-band stray-`\` marker never meets typed input. Have the prefilter's `hasFileRedirection` take `pathImpl` and anchor a drive-named redirect value at its drive root, so it stays a superset of `fileWriteTargets`.
- Add a shared test helper that single-quotes a path for Bash fixtures, and use it for every H fixture that interpolates a native path.
- Add a row to the Anti-Patterns table in `.claude/skills/windows-checkout-test-parity/SKILL.md` for unquoted native paths in Bash fixtures.
