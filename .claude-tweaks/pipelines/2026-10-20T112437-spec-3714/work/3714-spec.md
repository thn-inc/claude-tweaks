# 3714: Probe a harness-sanctioned wait for the nested-dispatch keep-alive

Origin: reflect hindsight from #3078

Defer-reason: tangential

## Current State

The nested-dispatch keep-alive rule (#3078) keeps a dispatched agent's turn alive with repeated foreground `sleep` Bash calls until every nested `Agent` child reports. On Claude Code 2.1.302 a standalone foreground `sleep` over 20 s is blocked inside a dispatched subagent with the message "To wait for a condition, use Monitor with an until-loop ... Do not chain shorter sleeps to work around this block." `sleep 20` still runs, so staged/review-1.patch (#3078) returns to `sleep 20` x 60, but that is exactly the chained-shorter-sleeps shape the block message discourages, and a future harness release may block it too.

## Deliverables

Probe, in a dispatched subagent, whether a `Monitor` (or other harness-sanctioned) wait keeps the turn alive and lets a nested child's `<task-notification>` arrive in-turn; post the raw outcome on this record

If it works, replace the sleep loop in `_shared/subagent-dispatch-core.md`'s nested-children paragraph, `dispatch/task-prompt.md` item 7 and both fenced templates with that primitive, keeping the per-wave bound and the blocked-wait fallback

Update `tests/foreground-execution-instruction.test.js`'s primitive-agreement test to the new primitive

## Acceptance Criteria

A posted probe comment shows a nested child's notification arriving in-turn under the sanctioned wait primitive on the current Claude Code version, and all four copies of the rule name that primitive (the agreement test passes and goes red on a mismatched copy) — or the probe shows no sanctioned primitive works, and the record closes with that evidence and the sleep-20 loop kept.
