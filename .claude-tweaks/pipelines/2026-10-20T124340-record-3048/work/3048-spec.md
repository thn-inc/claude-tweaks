# 3048: test: pipeline QA story selection reads only post-stamp changes, so it can skip the build's own UI change

Surface: infra

**Related:** #3047

## Current State

`/claude-tweaks:test`'s pipeline path with `VERIFICATION_PASSED=true` and stories present (`plugin/skills/test/SKILL.md:70`) selects QA stories by `source_files` ∩ `node bin/verify.js --changed-files --integration-branch {ref}`. `--changed-files` (`plugin/bin/verify.js:156`, `changedFilesMode`) resolves its base through `resolveBase` (`plugin/bin/lib/verify/changed-files.js:54`) with this precedence: `--base` first, then the checkout's own verification-stamp anchor whenever it is usable and not equal to HEAD (`:62-77`), and only then the `--integration-branch` merge-base (`:78-84`).

In a `/flow` run, `/build` Common Step 5 writes the stamp. Bookkeeping commits follow (for example `/stories` committing a new story YAML), so by the time `/test` selects stories the stamp anchor is an ancestor of HEAD but not HEAD. The changed-file set is then only the post-stamp bookkeeping, never the build's own source changes. Observed (reporter, plugin 6.136.0): the set was a single `stories/*.yaml` file. No story's `source_files` matched it, the Layer-3 UI sniff found no UI trigger file in it, and the documented path would have reported `QA: skipped — no affected stories` for a build that had just changed three admin-UI components. The reporter selected stories by hand against `git diff --name-only <merge-base>..HEAD`.

The stamp anchor is the right base for re-running tests (`affected`, `verification.md`'s Re-verify scoping table): the stamp records what was already verified. It is the wrong base for QA story selection, because the stamp says nothing about QA. `plugin/skills/test/design-gate.md:9` reads the same `--changed-files` set to decide which files the design CLI gate judges, so it has the same blind spot.

## Deliverables

1. Add an opt-in `--ignore-stamp` flag to `verify.js --changed-files` (parsed in `plugin/bin/lib/verify/args.js`, honored by `changedFilesMode`/`resolveBase`). It skips the stamp anchor and resolves the base from `--base` or the `--integration-branch` merge-base, keeping the existing exit-1 and `warning: resolved base equals HEAD` semantics. Reject it outside `--changed-files` the way the other read-only flags are rejected.
2. Switch `test/SKILL.md`'s pipeline QA story selection (`:70`) to `verify.js --changed-files --ignore-stamp --integration-branch {ref}`, so selection compares story `source_files` against the run's own branch diff.
3. Switch `test/design-gate.md:9`'s `<changed-files>` resolution to the same `--ignore-stamp` form.
4. Leave `/claude-tweaks:test affected` (test re-runs) and `verification.md`'s Re-verify scoping unchanged — they keep the stamp-anchored set.

## Acceptance Criteria

- With a stamp anchored at commit A, a later source commit B, and a bookkeeping commit C on HEAD, `verify.js --changed-files --integration-branch {ref}` still returns only C's files, and `--changed-files --ignore-stamp --integration-branch {ref}` returns B's and C's files (the merge-base diff). Both cases are covered in `tests/bin-lib/verify/changed-files.test.js` and/or `cli.test.js`.
- `--ignore-stamp` with no resolvable `--base`/`--integration-branch` base exits 1 with a message, never an empty list.
- `--ignore-stamp` combined with a non-`--changed-files` mode is a usage error (exit 2), covered by `args.test.js`.
- `test/SKILL.md`'s QA selection and `design-gate.md` both name the `--ignore-stamp` form; the `affected` mode does not.
- The existing `verify` suites (`node --test tests/bin-lib/verify/*.test.js`) pass.

## Release Note

Select pipeline QA stories against the run's full branch diff, so a build's own UI changes are never skipped because a verification stamp was written before them.

## Technical Approach

An additive flag keeps every existing `--changed-files` caller's behavior unchanged. Flipping the default would change the `affected`/`--scope` semantics that rely on the stamp anchor. The alternative of passing `--base $(git merge-base …)` from the skill prose was rejected: that hand-rolls merge-base resolution (`preferOriginRef`, degenerate-base handling) that `resolveBase` already owns.

**Kind:** gap

## What happened

Inside a `/flow` run, `/build` Common Step 5 writes the verification pass stamp. `/stories` then commits a new story YAML, and `/test` (with `VERIFICATION_PASSED=true` and stories present) selects stories by `source_files ∩ verify.js --changed-files`. Because `--changed-files` resolves its base to the stamp's `fullSha` whenever that sha is an ancestor of HEAD, the set at that point is only the post-stamp commits — here a single `stories/*.yaml` file. No story's `source_files` matched it, the Layer-3 UI sniff found no UI trigger file in that one-file set, and the documented path would have reported `QA: skipped — no affected stories` for a build that had just changed three admin-UI components.

## Expected

The pipeline's QA selection should compare story `source_files` against the run's own change set (the branch diff from its merge-base / the run's materialize base), not against "changes since the last verification stamp", which in a pipeline is almost always just the bookkeeping that follows `/build`.

## Workaround used

Selected stories manually against the branch diff (`git diff --name-only <merge-base>..HEAD`) and logged the deviation to `decisions.md`.

## Suggested fix

Give `/test`'s pipeline selection its own base (the run's materialize commit's parent, or `--integration-branch` merge-base) instead of the stamp-anchored `--changed-files`, or add a `--since-base` mode to `verify.js --changed-files` that ignores the stamp.
