# 4615: Acceptance target resolution and the local pre-merge park

Surface: infra

## Overview

Resolve **where the human's check runs** and implement the `local` path's pre-merge park.

**Agent-side checking always happens locally, before merge** (stories including negative ones, walkthrough recorded). The **human's check** runs on the run's *acceptance target*: `local` or `dev`.

**Resolution precedence (highest wins): a kept risk flag (forces `local`) > a per-item override (set at intent time, "I want to try this one locally") > the policy default `acceptance-target`.** Absent everything, the default is `local` (today's behavior).

**`local` target behavior (designer's call).** A `local` run does not stay alive waiting for a human. It ends **parked at "awaiting local acceptance"** with the PR open (the existing `pending-review` park shape), the run directory archived, and the claim released. `/claude-tweaks:accept #N` later **recreates a worktree from the PR branch and starts the app from it**, then walks the human through the packet. The verdict question for a local target:

- **Accept and merge** (Recommended)
- **Accept, I'll merge**
- **Broken: here's what I saw** (the verdict handler record resumes the same PR branch)

"Same run" in the design means same PR and branch, not a live process.

**Contract decisions this record pins:**

- **Scope.** `acceptance-target` and the park are read only when `control-mode` is `on` (the policy-keys record's rule); outside control mode behavior is exactly today's.
- **Insertion point.** The stop-before-merge branch sits in `_shared/pr-first-merge.md` at the step immediately before `gh pr merge`, after wrap-up's phases and the Review Console have run (under control mode the console is not a stop). In a multi-spec series a parked spec does not stop its siblings; each spec resolves its own target and the others continue.
- **Durable park state (the run directory is archived and is not authoritative).** A parked-local item is exactly: the PR is open and unmerged, the record carries `accept:pending`, and the acceptance packet's Deploy-status section states `target: local`. The run reports outcome `pending-review` with reason `awaiting-local-acceptance`, but the durable state is the label plus the packet. `/accept`, tidy, dispatch and the console identify a parked item from those two facts only. The packet and recording persist in the packet comment (the packet record), the resolved target and its reason are written into the packet's Deploy-status section, and the PR head SHA at park time is recorded there too.
- **Park cleanup order.** (1) packet posted and `accept:pending` applied, (2) target, reason and head SHA written into the packet, (3) run directory archived through the existing archive-run entry point, (4) claim released through the existing release-claim entry point, (5) worktree removed last. State is durable after steps 1-2, so a failure at 3-5 is reported and leaves the item re-enterable; it never leaves a half-parked item with no packet.
- **No auto-merge of a parked item.** Every auto-merge, tidy, dispatch and merge-prompt path already consults the pending acceptance label before arming a PR (see `tests/tidy-arm-ready-pr-acceptance-guard.test.js`); this record extends those guards and tests to `accept:pending` and adds the case "target local, packet says awaiting-local-acceptance". A parked item has no timeout and no nagging; it stays visible through the pending acceptance label in the existing needs-you lists.
- **Resolver inputs.** `resolveAcceptanceTarget({ keptRiskFlags, itemOverride, policyDefault })`: `keptRiskFlags` is a `string[]` of category slugs (`[]` means no flags; `null` or any non-array means unreadable); `itemOverride` is `'local'`, `undefined` (absent) or anything else (invalid); `policyDefault` is `'local'`, `'dev'`, `undefined` (absent) or anything else (invalid). Output `{ target, reason }` with `reason` one of `risk-flag`, `item-override`, `policy`, `default`, `invalid-input` (any unreadable or invalid input resolves `local` with this reason). `dev` requires an affirmative valid `policyDefault: 'dev'` with a readable empty flag list.
- **The item override can only select `local`.** The override line is `Acceptance-target: local` (exactly one occurrence, lowercase), stamped only by `/claude-tweaks:specify`'s interactive path. Anything else (duplicate, a different value, `dev`) is invalid and yields `invalid-input` toward `local`. Widening an override to `dev` would need the trusted-origin classifier and is deliberately left out; the machinery may only add caution.
- **`/accept` re-entry mechanics.** `git fetch origin {headRefName}` then `git worktree add .claude/worktrees/accept-{N} origin/{headRefName}` (never reusing a stale directory); the app starts from the project's documented start command via the dev-url-detection contract (its `local` branch; this record adds the recreated-worktree case to that file), and is stopped when the verdict is given or the session ends. Before offering "Accept and merge", compare the PR head SHA with the SHA recorded at park time; if it moved, say so and re-run the checks before merging (a moved base triggers the same re-validation). "Does not modify the branch" means HEAD is unchanged and `git status --porcelain` shows no tracked-file changes; ignored build artifacts are allowed. After the verdict the recreated worktree is removed. "Accept and merge" merges through the normal pr-first merge discipline (required checks, no bypass).
- **A local target that cannot be run.** When the app cannot be started locally (no start command, no UI surface such as `Surface: infra`, missing dependencies), `/accept` says so plainly and offers "Accept (agent checks only)" and "Broken: here's what I saw" without running anything, and the packet's Couldn't-test section already carries the reason; the park never becomes a dead end.
- **Re-entry after "Broken".** Owned by the verdict-handler record (#4614); this record only hands it the choice. Its open question about the re-entry mechanism (the design's "halted-run resume path" does not fit an archived run) is recorded there and noted in Gotchas below.

## Acceptance Criteria

1. Precedence: with a kept risk flag, a `dev` item override and a `dev` policy default, the result is `{ target: 'local', reason: 'risk-flag' }`; with no flag, a `local` override and a `dev` default it is `local` by `item-override`; with neither it follows policy; with nothing set it is `local` by `default`. Each of the four rows is a test.
2. Every invalid or unreadable input resolves to `{ target: 'local', reason: 'invalid-input' }` (never `dev`): `itemOverride` of `'dev'`, `'staging'`, `''` or duplicated; `keptRiskFlags` of `null`, `undefined`-as-unreadable (`null` is unreadable, `[]` is no flags), a string, or an array holding a non-string; `policyDefault` of `'staging'` or `42`. An absent `policyDefault` with no flags and no override is `local` by `default`. A well-formed `dev` item override has no effect (only `local` is honored).
2a. With `control-mode` off, `resolveAcceptanceTarget`'s output is not consulted and the pipeline behaves exactly as before (existing merge tests pass untouched).
3. A run whose target resolves to `local` ends with the PR open and unmerged, outcome `pending-review` with reason `awaiting-local-acceptance`, the packet carrying `target: local` and the head SHA, `accept:pending` applied, the run directory archived, and the work-claim released; after the run, `git worktree list` shows no worktree for the branch and the claim file/label is gone (assert via the fake runner and fixtures). A forced failure at archive, release or worktree removal is reported and the item remains identifiable as parked from the label plus packet alone.
3a. In a two-spec series where one spec parks, the other spec still proceeds to its own target.
3b. A PR parked for `awaiting-local-acceptance` is not merged, closed or reaped by the auto-merge path, tidy, dispatch, or the merge-prompt path (one test per path).
4. `/claude-tweaks:accept #N` on such an item with no local worktree runs `git fetch` and `git worktree add .claude/worktrees/accept-{N}` from the PR branch, starts the app, and leaves the branch HEAD unchanged with no tracked-file changes before the verdict (assert HEAD sha and `git status --porcelain`); the worktree is removed after the verdict; when the PR head differs from the recorded park-time SHA, "Accept and merge" is withheld until the checks are re-run.
4a. When the app cannot be started (no start command or `Surface: infra`), `/accept` prints that plainly and offers "Accept (agent checks only)" and "Broken: here's what I saw" without running anything.
5. The verdict question lists exactly "Accept and merge (Recommended)", "Accept, I'll merge", and "Broken: here's what I saw" for a local target.
6. A `dev` resolution does not park and behaves exactly as today's merge path.
7. `npm test` passes.

## Release Note

Added acceptance-target resolution so work flagged as risky, or marked for local trial, stops before merge with its pull request open until you accept it locally.

## Technical Approach

Keep resolution a pure function with the precedence encoded once; every other site reads its output. The park reuses the existing pending-review semantics so tidy, dispatch and the Review Console already know how to treat a parked PR; only the reason string and the `/accept` re-entry are new. The claim release and run archive follow the repo's existing end-of-run discipline (`_shared/pipeline-run-dir.md`, the worktree-discard rules); do not invent a parallel cleanup path.

### Data / API Surface

- `resolveAcceptanceTarget` as above.
- Park state: reason `awaiting-local-acceptance` on the PR (label or marker comment, per the existing park shape).
- Per-item override: `Acceptance-target: local` body metadata line (the only honored value; `dev` or any other value is invalid and fails closed toward `local`).

## Gotchas

- Fail closed toward `local` on every unreadable input; `dev` must require an affirmative resolved value.
- The park must not hold a live worktree: `/superpowers:finishing-a-development-branch` and `/tidy` treat a lingering worktree on a parked PR as residue, which is the "residue pile under a new name" anti-goal.
- The verdict-handler record (#4614) carries an open question about re-entry after "Broken": the design's "existing halted-run resume path" resumes a console-halted run via a live run directory, which this park deliberately archives. This record is unaffected (it only parks and hands the choice over), but do not build any resume dependency here.
- Open record #4467 (shares `pr-first-merge.md`) is mid-change on when a PR merges immediately; rebase onto it. Open records #3976 and #3731 touch the same area (archive-before-merge, recorded pid/port proof) and are Related, not blockers.
- An unanswered local park is never auto-promoted to accepted or auto-merged.
