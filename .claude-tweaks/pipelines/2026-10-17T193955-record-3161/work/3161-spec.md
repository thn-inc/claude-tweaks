# 3161: specify crossReferenceKeyFiles fence depends on a shell variable not shared across Bash calls

Origin: reflect light from #3128 (fix-wave + re-review, 2026-10-15)

Origin: reflect light from #3128 (fix-wave + re-review, 2026-10-15)

Defer-reason: tangential

## Current State

In `plugin/skills/specify/record-creation-subissues.md`'s decomposition-mode per-sub-issue loop, the "Cross-reference forward/backward Key Files" fence (`crossReferenceKeyFiles`, ~lines 192-201) reads the shell variable `$SPECIFY_DECOMP_MANIFEST` as if it were inherited from an earlier Bash tool call — the "Accumulate this unit for the cross-reference pass below" fence, earlier in the same per-unit loop.

Claude Code's Bash tool does not persist shell variables across separate tool invocations (each bash fence in a skill file, when followed as prose, is executed as its own distinct Bash call). When an agent actually executes these fences as separate calls — the normal execution model — `$SPECIFY_DECOMP_MANIFEST` is empty inside the cross-reference fence's own invocation, and the fence's `node -e` snippet calls `readFileSync('')`, which throws.

This exact defect class was found and fixed in a sibling fence during #3128's build: the new "Ceremony tally" step (added by #3128, same file) originally depended on the same inherited-variable assumption, was caught as a genuine latent bug by independent review, and was fixed by having that fence re-resolve `$SPECIFY_DECOMP_MANIFEST` itself via the deterministic `sessionTmpPath(process.env.CLAUDE_CODE_SESSION_ID, 'specify-decomp-manifest.json')` call — the same resolution the "Accumulate" and "Fresh manifest for this invocation" fences already use. The pre-existing `crossReferenceKeyFiles` fence has the identical defect but was left untouched, confirmed out of scope for #3128 by both that fix-wave's implementer and its scoped re-reviewer.

## Deliverables

Apply the identical fix to the `crossReferenceKeyFiles` fence: have it independently re-resolve `$SPECIFY_DECOMP_MANIFEST` via the same `sessionTmpPath(...)` call (per `plugin/skills/_shared/session-tmp-root.md`'s convention) rather than relying on a shell variable inherited from an earlier, separate Bash call. No change to the fence's actual cross-reference logic — only to how it locates the manifest file it reads.

## Acceptance Criteria

A conformance test (companion to the existing `tests/specify-decomposition-crossref-prose.test.js` and the #3128 precedent in `tests/specify-ceremony-tally-prose.test.js`) extracts the real `crossReferenceKeyFiles` bash fence from the live skill file and either (a) asserts it re-resolves `$SPECIFY_DECOMP_MANIFEST` via `sessionTmpPath` rather than reading an unset inherited variable, or (b) executes the fence in isolation (no inherited shell state, mirroring real per-call execution) against a scratch manifest and asserts it succeeds instead of throwing on an empty path.

## Release Note

No user-visible change — internal fix to a /specify decomposition-mode skill fence so it does not crash when executed as a separate Bash call (the actual execution model), rather than relying on a shell variable that does not survive across Bash tool invocations.
