# 5377: Run the hooks.js hook-event tests in-process

Surface: backend
Risk-flags: none

## Overview

Hook events (`pre-tool-use`, `post-tool-use`, `user-prompt-submit`, `session-start`, …) reach `hooks.js` with a JSON payload on stdin. After #5375 the dispatcher takes injected io, but the event modules under `plugin/bin/lib/hooks/` still read `process.env` themselves, so an in-process event call would run against the test runner's environment. Tests therefore still spawn: about 240 `hooks.js` processes per suite run in the six files this record converts.

This record passes the injected environment into the event modules and moves those tests onto the in-process helper.

**Complexity:** High
**Estimated tasks:** 7

## Release Note

## Technical Approach

Add `env` to the object `main` hands each event module (`{ input, runDir, runState, ownedRun, cwd, env }`) and replace each `process.env` read in the modules with it. A helper that reads the environment several layers down takes `env` as a parameter, defaulting to nothing: a missing `env` is a programming error in this path, never a silent fall back to `process.env`, because that fallback is exactly the hole this record closes.

The JSON result is written through the deps `stdout` that #5375 introduced. Its real value on the event path stays a synchronous `fs.writeSync(1, …)`, as today, so a large payload is never truncated by process exit.

Why `run(argv, deps)` and not a new `main`: see #5374's Decision Rationale.

The entry contract, set by #5374:

- The CLI exports `run(argv, deps)` and `realDeps`. `argv` is `process.argv.slice(2)`. `run` returns an integer exit code, or a Promise of one when the CLI is async.
- The script entry is the last statement of the file: `if (require.main === module) process.exitCode = run(process.argv.slice(2), realDeps);` (async: `run(…).then((code) => { process.exitCode = code; })`).
- The CLI reaches the outside world only through `deps`. Standard io keys, each present only when the CLI uses it: `stdout(text)`, `stderr(text)`, `cwd()` (returns a string), `env` (a plain object, read-only), `stdin()` (returns the whole input as a string), `homeDir()` (returns the user's home directory; real value `() => os.homedir()`). Other seams (`runner`, `now`, `mainRoot`, …) keep their names.
- Above the guarded entry, and in everything `run` calls: no `process.exitCode`, no `process.exit()`, no `process.chdir()`, no write to `process.env`.
- A relative path is resolved against `deps.cwd()`, never left to `path.resolve` or `fs`, which use the real working directory.
- Every child process is started with `cwd: deps.cwd()` and `env: deps.env`. A child started without them inherits the test runner's working directory and environment, so a `gh` or `git` stub on an injected `PATH` is skipped and the real tool runs.

## Gotchas

- `pre-tool-use.js` is the write gate. A read that silently falls back to the wrong environment changes what the gate allows. Run `tests/hooks-gate-coverage.test.js`, `tests/guard-refusals/shapes.test.js` and the shell-scanner suites after every change to it, and read `.claude/skills/pre-tool-use-gate-exemptions` before editing.
- Hook processes are started by the harness with the harness's own environment; `CLAUDE_CODE_SESSION_ID` comes off the payload, not the environment (comment at `hooks.js:2212`). Keep that source.
- `session-start` spawns a detached `reconcile-background` child. In-process it would still spawn; tests that assert on the child keep a real process, and a converted `session-start` test must stub the spawn through its existing seam.
- The prefilter block at the top of `hooks.js` consumes stdin before `main` runs when the file is the entry script (`EARLY`). In-process there is no `EARLY`; stdin comes from `deps.stdin()`.
- A hook module that throws must still end in exit 0 when run as a script. In-process the rejection reaches the test; assert it there instead of expecting code 0.
- Open pull requests edit `hooks.js` and `pre-tool-use.js` (#5298, #4530, #4527, #4504). Rebase before the final verify run.
- The forge degrade memo (#4830: `isFreshForgeDegradeMemo` and `FORGE_DEGRADE_MEMO_TTL_MS`, 60 s, in `plugin/bin/lib/hooks/pre-tool-use.js`) is scoped to a run, not to a process. In one test file, in-process cases that share a run directory also share the memo, so give each forge-degrade case its own run directory.
- The "today" counts come from one full-suite run on main @ 79cd5710d (2026-11-13) with a `NODE_OPTIONS=--require` preload that logs every node process. They are a floor: a test that spawns with a replaced `env` drops `NODE_OPTIONS`, so its children were not counted. Re-measure before starting.
- `node --test` runs each test file in its own process, so in-process state is shared only between the tests of one file.
- A CLI that relied on process exit to drop an open handle, timer or signal listener keeps the test file alive in-process. `run` closes what it opens.
- A test stays on a real process only when the process is its subject (a signal, a lock held across processes, a detached child, a closed stderr, `process.exit` timing). Use `spawnCli` for it and list it in the PR body.
- A test that fakes `gh` or `git` with a stub on `PATH`, or isolates the home directory with `HOME`, works in-process only when the CLI passes `deps.env` to every child it starts and reads the home directory through `deps.homeDir()`. Convert such a test by threading `env` to the child, or by injecting a fake `runner` through `deps`. If neither fits this record, leave the test on `spawnCli` and list it; never let it run with the stub silently skipped.
- Source-scan suites read `plugin/bin` files as text and pin their shape; `tests/bin-lib/exit-code-conformance.test.js` reads each file's last `require.main` block. Run the full suite before pushing, not only the converted files.
