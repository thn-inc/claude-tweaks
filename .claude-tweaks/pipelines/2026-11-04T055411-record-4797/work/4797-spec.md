# 4797: Replace post-merge.js hand-rolled takeClaim with a liveness-checked, owner-released claim

Origin: /claude-tweaks:release v6.159.0 release-gate review (run 2026-10-31T203907-release-standalone)

Defer-reason: pre-existing-outside-diff

## Current State

The reconcile post-merge pass serializes per-run work with `takeClaim` in `plugin/bin/lib/reconcile/post-merge.js` (around line 160), an exclusive-create plus rename-aside claim written beside the existing `plugin/bin/lib/file-lock.js`. It reclaims a holder by mtime age alone (`CLAIM_STALE_MS`, 10 minutes, no pid liveness probe, no heartbeat), and `releaseClaim` unlinks the claim without checking that the caller still owns it. A pass suspended or stalled past 10 minutes can therefore be taken over while still live, and when it resumes its release deletes the successor's claim, letting two passes run Step 4.0b on the same PR. Found by the v6.159.0 release-gate review (lens 3e reproduced, lens 3a pair; cross-lens debate settled on low severity); the #4668 review had already listed the hand-rolled lock as an open ledger item.

## Deliverables

- [ ] Make the per-run `.post-merge` claim reclaim only a dead holder (pid liveness, as `lib/file-lock.js` does) or a provably stale one, and release only when the caller still owns it (owner token).

- [ ] Prefer reusing `plugin/bin/lib/file-lock.js` over the hand-rolled claim; if it cannot serve, state why at the call site.

## Acceptance Criteria

A test holds a claim from a live pid past `CLAIM_STALE_MS` and shows a second `takeClaim` refuses it.

A test shows a release by a caller whose claim was taken over leaves the successor's claim in place.

`npm test` passes.

## Decisions

Answers the plan-review question (comment 6571420214).

- **Decision: Reading B.** Keep an age backstop that reclaims a claim whose holder pid still reads alive, to cover a reused pid. Size it the way `plugin/bin/lib/reconcile/background-lock.js` sizes `STALE_LOCK_MS` (5 min, 2.5x headroom over `BACKGROUND_BUDGET_MS`): derive the value from the post-merge pass's real worst-case duration bound (its budget / gh-timeout bound) with comparable headroom, so a live, merely slow holder is never mistaken for abandoned. Record the chosen value and its derivation in the spec and in a code comment next to the constant. A claim with no readable owner keeps the `CLAIM_STALE_MS` (10 min) reclaim; release still requires the owner token.
- **Decided (round 2): Reading B, heartbeat** (answers comment 6588131797). The post-merge claim holder refreshes the claim's mtime on every `gh` call, and the refresh lives in the shared gh-call path, not in each per-record loop, so a loop added later is covered without remembering to heartbeat. The age backstop then measures idle time since the last refresh, not total hold time.
- **Sizing:** a live holder has at most one `gh` call in flight, bounded by the `gh-timeout-ms` ceiling (120 s). Size the backstop at 2.5× that ceiling (5 min), the same ratio `background-lock.js` uses (STALE_LOCK_MS = 2.5 × BACKGROUND_BUDGET_MS). Derive it from the ceiling constant rather than a hand-typed literal, and record the value and derivation in the spec's Decisions. This replaces round 1's "worst-case duration" sizing: a live holder is never reclaimed for any PR size, including merge mode (no pass budget).
- **Limit to state in the spec:** work between `gh` calls that is not itself a `gh` call is not heartbeated; no such stretch may approach the backstop. If the plan finds one, it refreshes there too.
- **Decided (round 3), Q1: Reading B** (answers comment 6600883351). AC1's "held by a live pid past `CLAIM_STALE_MS`" is about total hold time for a holder that keeps refreshing its claim. A refreshing holder is never idle for 5 minutes, so it is never reclaimed however long it holds the claim. The 5-minute idle backstop applies only to a holder that stopped refreshing.
- **Decided (round 3), Q2: stop it in the heartbeat.** The heartbeat is a compare-and-refresh. Before each `gh` call it checks that the claim still names this holder. If the claim was taken over, it refreshes nothing and the pass stops before making that call, so a woken, suspended holder never runs Step 4.0/4.0b alongside its successor. The check lives in the shared gh-call path that already holds the heartbeat, not as separate checks in `closing-links.js` and `below-floor-parent-close.js`. Expand Key Files to whatever files that touches. The Release Note's no-duplicate-pass promise stays true; write a test that pins a taken-over holder stopping.
- **Decided (round 3), Q3: 5 minutes, stated honestly.** The `gh-timeout-ms` ceiling on this path is 60 s with no retry. The backstop is 5 minutes: at least 2.5 × that ceiling (150 s, the `background-lock.js` ratio), rounded up to cover non-`gh` work between calls, because wrongly reclaiming a live holder costs more than reclaiming a few minutes late. Correct the spec's "120 s" wording to this derivation.
- **Plan marker:** Task 2 carries a `Review risk:` line (high if it touches the claim release path).
- **Decided (round 4), Q4: Reading B** (answers comment 6617606486; decided by the dispatching session under the user's standing instruction to finish and close out this drain without further questions). A holder whose claim was taken over still writes `decisions.md` lines for every GitHub change it already made (a parent closed below the oversight floor, a record reopened), each marked as coming from a superseded holder, so no external mutation goes unlogged. It does not write the run marker, the retry line or the "degraded" skip lines; those belong to the successor that now owns the run. The pass's returned result still carries the changes too.
- **The reviewer's three no-decision fixes are in scope:** the SessionStart summary counts parents closed by a holder that later lost its claim; the pass re-checks claim ownership before every log write, not only before its last `gh` call (a takeover after the last call stops the marker write); and an existing but unreadable claim file is treated as ownerless under the 10-minute rule, never a permanent `claim-failed`.
