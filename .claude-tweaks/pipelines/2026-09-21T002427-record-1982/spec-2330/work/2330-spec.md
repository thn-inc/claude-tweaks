# #2330 — archive-merged.js: work-twin-conflict failure reasons never escalate to residue tracking

Materialized from GitHub issue #2330 (labels: ready, risk:low, size:low, type:bug, auto:build, auto:merge, priority:low, ceremony:fast-lane, shaped:headless). Same file-overlap group as #2346 (both touch `archive-merged.js`). See #2346's spec note re: pre-existing PR #2403 — this run re-implements independently since that prior run's claim was already released/stale.

## Deliverables

Extend `trackArchiveResult`/`STRUCTURALLY_STUCK_REASONS` (or add an equivalent path) so a `work-twin-conflict`/`work-twin-resolve-failed[-partial-revert]` result accumulates toward the same residue-escalation streak as the existing structurally-stuck reasons, rather than being silently dropped every pass.

## Acceptance Criteria

A reconcile run that repeatedly hits `work-twin-conflict` on the same run dir eventually escalates (streak-based issue filing), the same way a repeated `no-worktree`/`no-branch`/`no-pr` result does today.

## Technical Approach

Widen `trackArchiveResult`'s early-return guard (~line 1083, currently `if (result.reason !== 'move-failed') return;`) to also accept `work-twin-conflict` and `work-twin-resolve-failed`/`work-twin-resolve-failed-partial-revert`, routing them into the same `trackResidue(...)` call the `move-failed` path already uses. Prefer passing the specific reason string through to `trackResidue` (rather than generically reusing `'move-failed'`) so `escalate-residue.js`'s filed-issue title/body names the actual failure.

## Gotchas

- `STRUCTURALLY_STUCK_REASONS` (line ~1030) governs a different mechanism (`isStructurallyStuck()`) than `trackArchiveResult`'s own residue tracking — don't conflate the two.
- `work-twin-resolve-failed-partial-revert` is a worse state than a clean `work-twin-conflict` — the escalated issue's body should distinguish the two.

## Key Files

- `plugin/bin/lib/reconcile/archive-merged.js` — widen `trackArchiveResult`'s reason guard (~line 1083).
