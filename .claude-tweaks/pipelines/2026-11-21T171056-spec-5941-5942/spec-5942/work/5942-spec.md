# 5942: Launch driver workers at the effort their role's profile names

Surface: backend
Risk-flags: public-contract

## Overview

Makes the pipeline driver launch each headless worker at the effort its role's work profile names, when the project has turned that on. Today no driver launch sets an effort, so a worker runs at whatever the harness picks for a headless session. #5941 adds the policy value and the resolver's `launchEffort` field for agents launched inside a session; this record carries the same value to `claude -p` workers through the `--effort` flag.

**Complexity:** Low
**Estimated tasks:** 4

## Non-Goals

- Choosing a lower effort for any role, or retrying a failed worker at a higher one. That is the design's Phase 9.
- A separate effort setting per driver role. A role's effort is its profile's.
- Changing what any role is allowed to do, or its ceilings.

## Current State

- `composeArgs` in `plugin/bin/lib/driver/roles.js` builds the worker's argument list (lines 439-456). It emits `--model` only when a `model` option is given (line 454) and has no effort option.
- `claude --help` on Claude Code 2.1.325 lists `--effort <level>` with the levels `low`, `medium`, `high`, `xhigh` and `max`.
- Workers launch with `--safe-mode --restricted`, which ignores user, project and local settings, so a settings file cannot supply an effort.
- #5917 makes `launchTracked` (`plugin/bin/lib/driver/launch.js`) resolve each role's profile through `resolve()` in `plugin/bin/lib/model-profiles/profiles.js` and pass the model to the launch, and adds `model` to each worker line in `driver-events.jsonl`.
- #5941 makes `resolve()` return `launchEffort`: the profile's effort under `model-effort: profile`, `null` under `inherit` and for a Fast resolution.
- The effort a driver worker runs at today has not been measured.

## Deliverables

- [ ] `composeArgs` takes an `effort` option and emits `--effort {level}` when it is given. A level outside the five the flag accepts throws before any process starts.
- [ ] `launchTracked` passes the `launchEffort` from the same resolution that gives the role its model. A `null` passes no flag. `launchTracked` never computes an effort itself and makes the level it passed available to the event line. A bad effort in a `model-profiles` row throws in `resolve()` (`plugin/bin/lib/model-profiles/profiles.js`, the unknown-effort check) before `composeArgs` is called, so the run stops before any process starts.
- [ ] Each worker step's line in `driver-events.jsonl` carries `effort`: the level the worker was launched with, or `null` when no flag was passed. It is the requested level, not an observation of what ran. Every worker launch writes its own line, a one-retry relaunch and a continuation included, with the level that launch was given; the roles are every role `plugin/bin/lib/driver/roles.js` defines, judgment workers included. `null` means no flag was passed, whether the key is `inherit` or the resolution is Fast; a reader must not tell the two apart.
- [ ] The live smoke probe is re-run per `.claude/skills/headless-worker-launch` with one launch that passes `--effort medium` and one that passes none, and the module header of `plugin/bin/lib/driver/worker.js` records, dated, the effort each worker's transcript shows (the `"effort"` field on its assistant turns) and the level a launch with no flag shows, so `effort: null` has a documented meaning. The probe is the first task, before any code: a transcript that shows another level than the one passed, or none at all, fails it, and the record does not merge.
- [ ] `docs/driver.md` documents the flag, when it is passed, and the event field.
- [ ] Tests: the argument list with and without the option, the refusal of an unknown level, the event field, and that `launchTracked` passes `resolve().launchEffort` unchanged.

## Acceptance Criteria

1. With `model-effort` unset, the argument list composed for every role holds no `--effort`.
2. With `model-effort: profile` and no other model key, the implementer's argument list holds `--effort {launchEffort}` and the reviewer's does too, `launchEffort` being what `resolve()` returns for that role's profile under the inputs the driver call site passes; with the shipped table and no stance, ceiling or cap that is `high` for both.
3. With `model-effort: profile` and a `model-profiles` row giving `standard` the effort `medium`, the implementer's argument list holds `--effort medium`.
4. With `model-effort: profile` and the implementer's role mapped to `fast`, its argument list holds no `--effort`.
5. `composeArgs` called with `effort: 'extreme'` throws, and no process starts.
6. After a driver run with `model-effort: profile`, every `worker` step line in `driver-events.jsonl` has an `effort` field equal to the level that launch was given; with the key unset the field is `null`.
7. The module header of `worker.js` records a dated probe showing the transcript effort of a worker launched with `--effort medium` and of one launched with none, and that `--effort` is accepted by a launch under `--safe-mode --restricted`. A failed probe stops the build and is reported.
8. A `model-profiles` row giving a role's profile an unknown effort stops the run before any worker starts, because `resolve()` throws first.

## Release Note

Made pipeline driver workers launch at the effort their role's work profile names when the project sets `model-effort: profile`.

## Technical Approach

One more value out of the resolution #5917 already makes per launch, and one more flag in `composeArgs`. No new policy key: the switch and each profile's effort are the ones #5941 and `model-profiles` already provide, so a driver worker and an in-session agent on the same profile run at the same effort when both resolve under the same stance, ceiling and cap. See #5941 for the Decision Rationale.

**Decision** (plan review, 2026-11-21): Deliverable 3 stands as written. The review step's fix round relaunches the implementer (`review.js` `fixRound` → `runImplementer` → `launchTracked`), and that relaunch writes its own `driver-events.jsonl` worker line carrying the effort it was launched with, the same way a one-retry relaunch or a continuation does. The `review` line carries only the reviewer's effort. The two levels can differ: with `model-profiles: standard: effort: medium`, the fix-round relaunch runs at `medium` while the reviewer (capable) runs at `high`, and each line must record its own launch's level. Not a `fixEffort` key on the `review` line, and not "one level per step line".

### Data / API Surface

- `composeArgs({ …, effort })`: optional; one of `low`, `medium`, `high`, `xhigh`, `max`.
- `driver-events.jsonl` worker lines gain `effort: "<level>" | null`. Additive; readers that ignore unknown fields are unaffected.
- The review fix round's own `worker` line (the Decision) is a sub-step line written through `ctx.events.emit` before the `review` line, and carries `fix: true`; the station mirror maps it to no station events, since the `review` line already binds the fix session (`fixSessionId`). Added at build (architecture alignment, Beneficial).
