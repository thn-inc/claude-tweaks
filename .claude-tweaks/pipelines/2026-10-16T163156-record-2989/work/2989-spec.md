# 2989: friction-events.js can attribute an unrelated session's events to a run directory before its pipeline starts

Origin: reflect full from #2866

Defer-reason: pre-existing-outside-diff

## Current State

This run's own `friction-events.js --run {run-dir}` call (the Friction lens's required input, `reflect/full-mode.md`) returned 9 `ask-user-question` entries and 2 `contract-violation` entries dated within ~9 minutes of this run directory's creation timestamp, all about an unrelated topic ("Impeccable design-wrapper engine migration," "seven units," "red-team findings on seven records") that has nothing to do with #2866 (a docs-health commit-hash verifier). No other active run directory's `run-state.json` names this same worktree path, so these events were logged directly into this run's own `events.jsonl` rather than pulled in by the documented cross-worktree union (`findRunsByWorktreePath`). The content and the ~2-hour gap between these events and this run's own Manifesto entry both point to a different piece of work having been logged against this run's event log before the real #2866 pipeline actually started.

## Deliverables

- [ ] Investigate how `events.jsonl` entries for an unrelated piece of work ended up attributed to a run directory before its own pipeline started — likely a gap in the hook event-logging path (`plugin/bin/lib/hooks/*.js`) for the window between a run directory being minted (dispatch's mkdir-only step) and it actually being claimed/initialized
- [ ] `plugin/bin/friction-events.js` (or its hook-side writer) should not attribute events logged before a run directory's own `config.yml`/claim exists to that directory at all, or should at least make such pre-claim events distinguishable from genuine in-run friction

## Acceptance Criteria

A test reproducing the window between a run directory's mkdir-only mint and its first real claim/config.yml write asserts that `friction-events.js` either excludes events logged in that window from the run's own friction report, or tags them distinctly from genuine in-run friction so a Friction-lens pass cannot mistake them for this run's own operator experience.

## Release Note

No user-visible change — this hardens the Friction reflect lens's own input data against misattributed events from an unrelated piece of work.
