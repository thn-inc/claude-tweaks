# 5556: Write a step yield file per closed run: what each step cost and produced

Surface: backend

**Related:** #4558, #4526, #5540, #5541, #4663, #3381, #4359
Risk-flags: none

## Current State

A run directory records what each step cost (`timing.json`: minutes, tokens and subagents per phase) and what each step decided (`decisions.md`, `events.jsonl`), but nothing joins the two. To learn what `/claude-tweaks:review` produced for its tokens, a maintainer writes a script that greps `decisions.md`. The 2026-11-15 measurements were made that way (`tools/replay-scratch/review-yield.js` on branch `worktree-design-process-efficiency`): over 419 archived reviews, 18% of findings were reported by both paired reviewers, and the script could not classify a share of the lines it met.

Where the facts are today:

- Pair outcome lines (`Reproduction: lens "…" finding … reproduced. Confirmed.`, `… not reproduced. Staged to Review Console …`, and four more forms) are written by the reviewing session from templates in `plugin/skills/review/step3-lens-dispatch.md`. No code defines their form. `review-coordination.js categorise-reproduction` computes the split and logs nothing.
- Tiebreak verdict lines are written by code (`plugin/bin/lib/tiebreak.js`, through `review-coordination.js resolve-tiebreak --run`). `plugin/bin/lib/console/resolve.js` exports `parseTiebreakLine`; `plugin/bin/lib/log-decision/append.js` has `parseEntry`.
- `review-findings.json` (in 196 of 2,948 run directories) lists the findings sent to tiebreak, with id, lens, path, line, severity and kind. It does not list findings both reviewers reported.
- `plugin/bin/lib/hooks/post-tool-use.js` appends an `ask-user-question` event when a question is answered. It records the questions and the answer, not when the question was asked.
- `events.jsonl` has `commit` and `verify` events.
- `plugin/bin/lib/calibration/decisions-classifier.js` classifies a decision line by status.

Design: `docs/superpowers/specs/2026-11-15-process-efficiency-design.md`, Phase 5, unit 5.2. The file this record adds is read by the scoreboard in the dispatch repository (unit 5.4), by Phase 6's done criterion and by Phase 7's design.

## Deliverables

1. **One function.** A module under `plugin/bin/lib/timing/` takes a run directory and returns the step yield object. It reads `timing.json` when present, `decisions.md`, `events.jsonl` and `run-state.json`, and nothing outside the run directory except the transcripts the timing writer already resolves. No model turn. Its phase spans come from `derivePhases` over `events.jsonl` (`derive.js`: `{ events, manifest?, runState?, now? }` in, `{ phases, totals }` out, no `timing.json` or transcript needed), so a run with no `timing.json` still gets its steps and only the cost fields are `null`. The file is `step-yield.json` in the run directory, beside `timing.json`; its name is a constant exported by the module, and `steps` is an array in phase order.
2. **Per step.** One entry per phase the run had: minutes, tokens (input, output, cache read, cache creation), agents, and what the step produced: commits, verify runs and their results, and decision lines by status (`AUTO`, `STAGED`, `SKIP`, `FAILED`, and the rest of the log's closed vocabulary).
3. **Review.** The review entry also holds, per lens and in total: findings raised, findings both paired reviewers reported, findings one reviewer reported, and tiebreak results by verdict (`confirmed`, `refuted`, `cant-tell`) and by outcome (`confirmed`, `drop`, `digest`, `console`). A `judge: none` line (#5541) is its own outcome, `none`, whether or not #5541 has landed. Each of the six pair-line forms in `step3-lens-dispatch.md` adds to exactly one counter: a `reproduced` line (severity contested included) counts a finding both reviewers reported, and the other forms count findings one reviewer reported, except a vacuity downgrade, which relabels a finding already counted and adds none. The per-form assignments, including the two-finding coincidence line and the refuted absence claim, are written once in the reader module and in the document, and AC3's per-template test covers each form.
4. **Questions.** Each entry holds the questions asked during that step and the minutes each waited for its answer. A question whose ask time cannot be established is listed with `waitedMinutes: null`. A question belongs to the step whose span holds its ask time, or its answer time when the ask time is unknown; an asked question with no recorded answer also has `waitedMinutes: null`.
5. **Nothing is dropped silently.** A line or event the function does not recognise is counted under `unparsed` for its step, with up to five samples. A cost field with no source is `null`, never `0`.
6. **Written when a run closes.** The closing paths that write `timing.json` (#5555, which this record is blocked by) also write `step-yield.json`, under the same rule: the close never fails or stalls on it, inside the same named time bound, and a failure logs one `SKIP` line. The file is derived data: every close rewrites it whole from the run directory (a temporary file, then a rename), and no existing file takes precedence.
7. **Schema.** The file has a `schemaVersion`. `docs/reference/step-yield.md` describes every field, its source and when it is `null`, which source `waitedMinutes` came from, and the pair-line mapping table. Per-lens and per-status keys are documented as patterns, and the status set comes from one named list the module imports, not a second copy. It is the contract the dispatch repository reads.
8. **Archive report.** `tools/step-yield-report.js` runs the same function over every run directory under a pipelines root, in memory, for runs that have no yield file, and prints totals and per-lens review numbers, with `--json`. It replaces `tools/replay-scratch/review-yield.js`, which is deleted.
9. **Docs.** `docs/hooks.md` and `docs/plugin-structure.md` name the file and the tool.

**Decision rule for any further gap (author, 2026-11-16).** Where this record leaves a choice between readings and no Decision above settles it, the build does not stop for it. It takes the reading that, in this order: keeps a run on the previous plugin release working; puts the rule in code and not in skill prose; stays inside this record's Key Files. It states the choice in the PR body. A criterion that can only be observed after a merge or a release is met by filing one parked measurement record through `/claude-tweaks:capture` that carries the check and its bound.

## Acceptance Criteria

- [ ] AC1: For a fixture run directory with a known `decisions.md`, `events.jsonl` and `timing.json`, the function returns the expected object. The fixture has at least: one finding both reviewers reported, one reported by one reviewer and confirmed by tiebreak, one refuted, one can't-tell, one question, one verify event and one line of an unknown shape.
- [ ] AC2: The unknown line appears under `unparsed` with its text, and no count includes it. The test fails if the line is dropped.
- [ ] AC3: Tiebreak lines are read with `parseTiebreakLine` and log entries with `parseEntry`. The pair-line forms get one reader module that holds their patterns, and a test reads `plugin/skills/review/step3-lens-dispatch.md` and fails when a template there no longer matches its pattern. The yield module itself holds no pattern for a log line.
- [ ] AC4: A run directory with no `timing.json` yields entries with `null` cost fields and correct produced counts.
- [ ] AC5: A question whose ask time is known has `waitedMinutes` equal to the gap between ask and answer; one whose ask time is unknown has `null`. One test each.
- [ ] AC6: Closing a fixture run through each closing path leaves the yield file. With the yield function stubbed to throw, each path's result and exit code are unchanged and one `SKIP` line is logged.
- [ ] AC7: `tools/step-yield-report.js` over the archive reproduces `review-yield.js`'s totals for the same runs (findings raised, reported by both, tiebreak confirmed and refuted), or the PR lists each difference and its cause. The share of review lines left `unparsed` across the archive is under 2%, where review lines are the decision lines attributed to the review step. The bound takes precedence: a reader for a legacy shape no current writer emits is written when it is needed to meet the bound, and if the bound is still missed the PR names the shapes that remain.
- [ ] AC8: `docs/reference/step-yield.md` lists every key the function can emit. A test fails when the function emits a key the document does not name. A golden file of key paths and their nullability also fails the test when a key is removed or its type changes without a `schemaVersion` bump.
- [ ] AC9: A fixture with a decision line and an event on each side of a phase boundary attributes each to the phase whose span holds it, and a change to `derivePhases`'s boundary rule turns the test red.

## Technical Approach

Name the file and the keys once, in the module, and have the document test read the module's own key list.

Ask time for a question: the `ask-user-question` event is written when the answer arrives. Either add an event when the question is posed (a `PreToolUse` write for `AskUserQuestion`, read `docs/hooks.md` first) or read the ask time from the transcript's tool-use row, which the timing reader already streams. Choose one and state why in the PR. The first works for runs whose transcript is gone; the second needs no hook change. Record the chosen source and its limits in `step-yield.md` under `waitedMinutes`.

Attribute a decision line, an event or a question to a step by the phase spans `derivePhases` already computes. Do not write a second phase model.

The pair-line patterns are additive: a reworded template adds a pattern and never replaces one, so archived runs keep parsing. The test's failure message names the template, the pattern and this rule. Phase 6 of the design moves the pair-line write into `categorise-reproduction`; the reader and its test then follow that writer, and `step-yield.md` says so.

Multi-record runs: one yield file per directory that gets a `timing.json`.

The dispatch repository reads this file; a field is added, never renamed, without a `schemaVersion` change and a note in the document.

- Read `.claude/skills/run-directory-fact-packs` and `.claude/skills/parse-signal-discipline` before writing the reader, and `.claude/skills/prose-code-twin-pin` and `.claude/skills/skill-prose-conformance-tests` before writing the two tests that read prose.

- The pair-line test pins prose other records edit. A sibling that rewords a template turns this test red at merge; the fix is to update the pattern in the same change.
- #5540 changes how tiebreak verdicts are settled (one call per chunk) and #5541 adds a `judge: none` token to some verdict lines. Both keep the per-finding line's form; count a `judge: none` line under outcome `none`, whether or not #5541 has landed.
- Older runs log reviews in older line shapes ("legacy shape" appears in current console output). The report's `unparsed` share is the measure of how many; do not write parsers for shapes no current writer emits unless AC7's 2% bound needs it.
- `tools/efficiency-report.js` reads `timing.json` across the archive. Leave it as it is; the new report reads yield.
- `plugin/bin/write-run-artifact.js` allows three artifact names (#4671). This file is written by code in-process, not through that CLI.
- `tools/replay-scratch/` exists only on branch `worktree-design-process-efficiency` until that branch merges. If it is not on `main` when this is built, read `review-yield.js` from the branch for AC7 and skip the deletion.
- `derivePhases`'s span rule decides which step each line and question belongs to, and the dispatch scoreboard's per-step numbers depend on it. Say so in a comment at `derivePhases` and in `step-yield.md`.
- #5557 deletes `tools/replay-scratch/` except `review-yield.js`. This record deletes `review-yield.js`; whichever of the two records lands last removes the then-empty directory.
