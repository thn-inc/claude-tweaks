# 4559: build dispatch: size:low → Fast puts a cheapest-tier implementer on git-running tasks, and it ignored the no-stash rule

Surface: infra

## Current State

`/claude-tweaks:build`'s subagent strategy (`plugin/skills/build/dispatch.md`, the **subagent** bullet) maps the header's `size:` to a per-task implementer profile, `low` → Fast, `medium` → Standard, `high` → Capable. It forwards a no-stash rule to every per-task implementer in this form: "never run `git stash` or `git stash pop`". The same two-command wording appears in `plugin/skills/dispatch/task-prompt.md` (both Task() calls, lines ~216 and ~409) and `plugin/skills/dispatch/express-prompt.md` (~line 75). The canonical rule, `plugin/skills/_shared/subagent-dispatch-core.md` line 45, says "Never run `git stash` in any form". Naming only `git stash` and `git stash pop` lets a reader infer that other subcommands, such as `drop` and `clear`, are allowed.

Observed incident (plugin 6.156.1): a `size: low` record's 2-task plan sent Task 2 (5 files: a new module, middleware wiring, docs) to a Fast (haiku) implementer in a shared worktree. While investigating a test, the implementer ran a compound Bash command containing `git stash drop`. That dropped the only entry on the repo-wide stash stack, a rebase `--autostash` entry left by the main checkout. The only signal was the implementer's own self-report. Recovery needed the dangling `On <branch>: autostash` commit plus `git stash store`, done by hand after asking the user.

Verified at shaping time:

- Nothing in `/build` or SDD compares `git stash list` before and after an implementer dispatch. No `plugin/bin` CLI reads the stash stack. A quieter implementer would have lost the user's work with no trace.
- The preventive hook does not cover this shape. `plugin/bin/lib/hooks/pre-tool-use.js`'s `checkGitStashWarn` (lines ~890-938) warns only on bare `stash`, `pop`, `push`, `save`, or a flag-first form. Its comment and `docs/hooks.md` line 13 class `drop`, `clear`, and `apply` as "read-only" and leave them silent. `drop` and `clear` are the stack-destroying subcommands. The compound command does reach the handler, because the Bash prefilter keys on the `git` word (`tests/hooks-bash-prefilter.test.js`, #3074), but the gate then deliberately ignores `drop`.
- `tests/dispatch-no-stash-conformance.test.js` pins the presence of the no-stash prose in `task-prompt.md` and `build/dispatch.md`. It does not pin which subcommands that prose names.

## Deliverables

1. **Forwarded rule names every stack-mutating form.** Reword the no-stash instruction in `plugin/skills/build/dispatch.md` (subagent bullet), `plugin/skills/dispatch/task-prompt.md` (both calls) and `plugin/skills/dispatch/express-prompt.md` to match `_shared/subagent-dispatch-core.md`'s "in any form". It must explicitly name `pop`, `drop`, `clear`, `push`/bare `git stash`, `save` and `store`. It keeps the existing alternatives: `git show <rev>:<path>` for a baseline, and a WIP commit to set work aside. `git stash list` and `git stash show` stay allowed as read-only.
2. **Stash-guard CLI.** Add a new `plugin/bin/stash-guard.js`, following the repo's `run(argv, deps)` CLI seam and injectable git runner, with two verbs:
   - `snapshot --repo <dir> --out <file>` writes the current stash stack, `[{sha, subject}]`, read via `git -C <dir> stash list --format=%H%x00%gs` (NUL-separated, never split on spaces), to `<file>` as JSON.
   - `compare --repo <dir> --baseline <file>` re-reads the stack and prints one JSON line `{removed: [{sha, subject}], added: [{sha, subject}]}`. Exit 0 = unchanged, 3 = changed, 2 = usage, unreadable baseline, or a git failure. With `--restore`, each removed entry is re-stored with `git -C <dir> stash store -m "<subject>" <sha>`, and the output reports `restored`/`restoreFailed` per sha. A failed restore prints the exact paste-ready `git stash store -m "<subject>" <sha>` command on its own line.
3. **Controller wraps every per-task implementer dispatch.** In `build/dispatch.md`'s subagent bullet, in the same invocation instruction that forwards the no-stash rule, direct `/superpowers:subagent-driven-development` to run `stash-guard.js snapshot` before each per-task implementer dispatch, and `stash-guard.js compare --restore` after it returns, before that task's review. Paths go to the run dir when `$PIPELINE_RUN_DIR` resolves, else to a session-scoped temp file per `_shared/session-tmp-root.md`. On a change:
   - Removed entries are restored automatically and logged `AUTO {time} — Stash guard: implementer for task {k} removed stash entr{y,ies} {sha subject …}; restored via git stash store. Reversibility: high.` with `log-decision.js --section "/build"`.
   - A failed restore logs `FAILED` with the paste-ready recovery command, and that command also appears in the Step 7 handoff (standalone `/build`: the handoff only).
   - Added entries (the implementer pushed onto the stack) are logged and listed in the handoff, never popped automatically.
   - The task's implementer result is treated as `DONE_WITH_CONCERNS` and the stash change is named to the task reviewer.
   - No new mid-flow stop. The data-preserving action runs automatically, and the evidence lands in the decision log and the Review Console's view of it.
4. **Hook warns on the destructive subcommands.** Widen `checkGitStashWarn`'s `mutatesStack` to include `drop` and `clear`, which currently stay silent. Keep it a warning (no deny), with the same linked-worktree condition. Correct the comment and `docs/hooks.md` line 13, which call `drop`/`apply` read-only. `apply` stays silent: it does not change the stack.
5. **Profile floor: decided, not adopted.** Do not add a "floor git-running implementers at Standard" rule (the record's suggested direction (a)). Every SDD per-task implementer commits, so "git-running" covers every implementer. The floor would quietly retire `low` → Fast and the `transcription` → Fast marker mapping across all builds. Deliverables 1-4 cover every profile tier, not just Fast. State this decision in one sentence beside the `size:` → profile mapping in `build/dispatch.md`, so a later reader does not re-propose it without new evidence.

## Acceptance Criteria

- `build/dispatch.md`, both `task-prompt.md` calls and `express-prompt.md` each forbid `git stash` "in any form" and name `drop` and `clear` explicitly. `tests/dispatch-no-stash-conformance.test.js` asserts `drop` and `clear` are named in each region (including `express-prompt.md`). - A forced restore failure (injected runner) reports the sha under `restoreFailed` and prints a `git stash store -m "…" <sha>` line.
- A stash subject containing spaces, a colon, and a quote round-trips intact through `snapshot` → `compare --restore`.
- `build/dispatch.md`'s subagent bullet directs SDD to run `snapshot` before and `compare --restore` after every per-task implementer dispatch. It names the `AUTO` and `FAILED` decision lines and the handoff surfacing. A conformance assertion pins the `stash-guard.js` invocation in that bullet.

It stays silent for `git stash list`, `git stash show` and `git stash apply`. Each case is covered in `tests/hooks-pre-tool-use.test.js`.
- `docs/hooks.md` no longer describes `drop` as read-only.

- `npm test` passes.

## Release Note

Protect the shared git stash during builds: `/build` now snapshots the stash before each implementer task and restores any entry the implementer dropped, and the stash warning hook now fires on `git stash drop` and `git stash clear`.

## Technical Approach

The incident had two failures: the forwarded rule invited a too-narrow reading, and nothing detected the violation. Fix both, plus the hook layer that was supposed to catch it, rather than raising the model tier. A tier floor reduces the odds of a violation without detecting one, and it is not limited to "git-running" tasks, since every implementer commits.

- Wording (Deliverable 1) is a prose edit in four places. Keep each copy's local phrasing (`--` vs em dash) and cite `_shared/subagent-dispatch-core.md` as the canonical rule where the copy already does.
- `stash-guard.js` follows the `gh-api-module-pattern` skill's CLI wrapper contract: an injectable `execFileSync` runner, `--end-of-options` before user-derived git args where applicable, and exit codes 0/2/3. Identity is the stash commit sha (`%H`), never the `stash@{n}` index, which shifts whenever any entry is added or removed. Restore uses `git stash store`, which only writes a reflog entry for an existing commit. It touches no worktree, so it is safe to run automatically.
- The snapshot/compare instruction sits in `build/dispatch.md` next to the existing forwarded no-stash rule. SDD's controller is the session running `/build`, so the commands run in the controller's own worktree with `--repo` set to it. The stash stack is repo-wide, so any worktree of the checkout sees the same stack.
- Hook change: add `next === 'drop' || next === 'clear'` to `mutatesStack` in `checkGitStashWarn`, and update its header comment.

## Gotchas

- Concurrent sibling sessions share the stash stack. A sibling legitimately dropping its own entry during an implementer dispatch looks the same as an implementer drop, and `--restore` brings it back. This false positive is accepted: an extra entry costs one `git stash drop`, while a lost one can cost the user's work. The `AUTO` line names the sha, so it can be undone.
- A `git stash pop` by an implementer both removes the entry and applies its changes to the implementer's worktree. Restoring the entry puts it back on the stack but does not undo the applied changes. The task review and the build's own test gate own any contamination of the task diff. The `DONE_WITH_CONCERNS` hand-off to the reviewer is what makes it visible there.
- Never key entries by `stash@{n}`. Indices shift on every push or drop.
- Read stash subjects NUL-separated (`%x00`). Subjects routinely contain spaces and colons (`On main: autostash`), and `git stash store -m` must get the subject back verbatim.
- `apply` stays silent in the hook. It changes the worktree, not the stack, and widening it would warn on the documented WIP-recovery flow.
- Related: #4548 (the same forwarded-rule list, missing a process-kill rule). Both edit the same forbidden-operation instructions in `build/dispatch.md`, so they may conflict if built concurrently.

## Original request

build dispatch: size:low → Fast puts a cheapest-tier implementer on git-running tasks, and it ignored the no-stash rule

**Summary:** `/claude-tweaks:build`'s `size:` → profile bridge sent a Fast (haiku) per-task implementer to a multi-file task in a shared worktree. The implementer ran `git stash drop` in a compound Bash command, even though the dispatch said in plain words never to run `git stash`. It dropped the only entry on the repo-wide stash stack, which was another checkout's `autostash`.

**Kind:** Defect

**Affected component:** `skills/build/dispatch.md`: the subagent bullet's `size:` → model-profile mapping (`low` → Fast) and its "Forbid `git stash` in every per-task implementer dispatch" instruction.

**Repro steps:**
1. Run `/claude-tweaks:flow #N` on a record whose header carries `size: low`, with a 2-task plan whose Task 2 touches 5 files (a new module, middleware wiring, docs).
2. `/build` dispatches each SDD implementer on Fast (haiku), per `dispatch.md`'s `low` → Fast mapping. The dispatch text includes the no-stash rule verbatim.
3. Have another checkout of the same repo hold a stash entry (here, a rebase `--autostash` left over in the main checkout).
4. The Task 2 implementer investigates a test, runs a compound command containing `git stash drop`, and reports it afterwards as a concern.

**Expected vs. actual:**
Expected: no per-task implementer ever mutates the shared stash. If one does, the pipeline notices before the next dispatch.
Actual: the stash entry was dropped, and the only signal was the implementer's own self-report. Recovery needed the dangling `On <branch>: autostash` commit and `git stash store`, after asking the user. Nothing in `/build` compares `git stash list` before and after a dispatch, so a quieter implementer would have lost the user's work silently.

**Suggested direction:**
- (a) Floor git-running implementers at Standard, whatever `size:` says.
- (b) Have the controller snapshot `git stash list` before each implementer dispatch and diff it afterwards. A changed stash becomes a stop card naming the dropped sha and the `git stash store` recovery command.

**Definition:** Clear
