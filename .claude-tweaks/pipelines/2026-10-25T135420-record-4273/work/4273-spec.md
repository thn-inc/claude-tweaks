# 4273: dispatch close-out: offer an update-from-main path for a DIRTY or BEHIND PR instead of a flag-only stop

Origin: dispatch close-out of #4028 (PR #4205), 2026-10-25 — user asked whether close-out never rebasing is feedback for claude-tweaks

Defer-reason: tangential

## Current State

`plugin/skills/dispatch/close-out.md` step 2 stops a candidate whose `mergeStateStatus` is `DIRTY` ("rebase and re-verify first") and its Anti-Patterns table forbids rebasing because it "changes PR content without the author present". That reasoning is inherited from `_shared/github-pr-scan.md` item 11, a scheduled sweep that really does run with nobody present. Close-out is human-present by construction: `close-out-confirmation.md` gates every merge on an `AskUserQuestion`, with no autonomy carve-out, and `close-out.md`'s own Reporting section says never to schedule it headless. So the premise behind the ban is false in this mode.

Close-out also has no branch for `BEHIND` with no conflicts (no `gh pr update-branch` path).

Observed 2026-10-25 closing out #4028 (PR #4205): close-out stopped on `DIRTY`, and the user had to ask for the update by hand. The session then merged `origin/main` into the branch. Three conflicts resolved cleanly as text, yet one test failed afterwards: `tests/pr-run-comments.test.js` AC1.1, #4065's pin that no fixed `/tmp/{kind}-comment` path remains. Only the full suite caught it; it was fixed in `80e469dcc` before the merge. The real hazard is a resolution that silently drops one side's intent, not the act of updating.

## Deliverables

1. `close-out.md` step 2: on `DIRTY`/`CONFLICTING`, offer an "update from {integration-branch}" option instead of a hard stop. The update merges `origin/{integration-branch}` into the PR branch (never a rebase or force-push), resolves conflicts, runs the full suite through `verify.js`, pushes, and re-reads CI fresh before the confirmation gate.
2. On `BEHIND` with no conflicts, offer the same update via `gh pr update-branch`, followed by the same CI re-read.
3. `close-out-confirmation.md`: when an update ran, the question says so and names the conflicted files and the resolution commit, so the human reviews what changed before confirming the merge.
4. Reword the Anti-Patterns row so the ban applies to the headless item-11 sweep and to updating without a passing full suite, not to a human-present close-out. `_shared/github-pr-scan.md` item 11 stays flag-only.

## Acceptance Criteria

- A `DIRTY` candidate is offered an update option rather than only a stop; declining leaves the PR exactly as before.
- A PR updated by close-out is never merged without a passing full-suite `verify.js` stamp matching the new HEAD and a green CI read on that HEAD.
- The confirmation question names that an update ran, the conflicted files, and the resolution commit.
- No path rebases or force-pushes the PR branch.
- `github-pr-scan.md` item 11 remains flag-only, and the close-out conformance tests are updated to pin the new branch.

## Release Note

Closing out a parked PR that has fallen behind or conflicts with main can now update it in place, re-verified, instead of stopping.
