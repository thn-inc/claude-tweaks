# 6001: Choose review lenses per run in code from the diff's facts and each lens's yield, behind a policy key

Surface: backend
Risk-flags: public-contract

## Current State

`/claude-tweaks:review` Step 3 picks its agent-dispatched lenses from the resolved `review-effort` tier alone (`plugin/skills/review/step3-lens-dispatch.md`, "Lens scope by review-effort tier": `low` 3b,3c; `medium` +3a,3f; `high`+ adds 3d,3e,3g,3h). On top of that the session applies a prose rule, "skip a lens if it doesn't apply to this change type" (e.g. Performance on a docs-only diff), and at `low` a no-executable-content skip of 3b/3c (`step3-tier-variants.md`). The session decides those skips by reading; nothing in code does.

Design evidence (`docs/superpowers/specs/2026-11-18-pipeline-economy-design.md`, `### What the reviews return`): 8.3 confirmed findings per run over 96 runs; lenses 3b and 3d produced 36 and 19 confirmed findings and return nothing over 70% of the time; the two Haiku lenses (3a, 3f) produced 443 of 799.

The per-lens rate comes from #5998 in this decomposition.

## Deliverables

1. A pure selection function (proposed `plugin/bin/lib/review-lens/select.js`): input = the tier's lens set, the diff's facts, and the per-lens history (#5998's `history.js` result: `lenses.<id>.{runs, confirmed, shareWithFinding, insufficient}` plus `errors`; a missing, unreadable or malformed history reads as `insufficient` for every lens, so the full tier set runs, with the reason logged); output = the lenses to dispatch, and for each tier lens left out a one-line reason. **No model chooses.** Rules, each a named constant:
   - The tier's set is the ceiling: a lens the tier excludes is never added.
   - A lens with `insufficient` history runs.
   - A lens whose confirmed-finding share over its last 20 runs is at or above a floor runs on every diff it applies to. A lens below the floor is also forced to run once every M reviews in which the tier allows it (M is a named constant chosen from the replay), so its window keeps moving. The replay counts the confirmed findings a skipped lens would have lost by severity, not only by count.
   - A lens below the floor runs only when a diff fact calls for it. The facts are computed from the diff in code: changed paths and kinds (prose, source, test, config, workflow), whether any changed line is executable content (the `low`-tier definition in `step3-tier-variants.md`), shell or `child_process` invocations added, a protected or risk path touched (`risk-path-globs`), the record's `Risk-flags:`, new files or new modules, hook or per-call paths. Each lens declares the facts that call for it (3b: executable content that runs a command, takes a path or untrusted text, or touches a risk path; 3d: source in a per-call or per-file loop path such as hooks, the test runner, or a git/gh call in a loop; and so on).
2. A CLI (proposed `plugin/bin/review-lens-select.js --run <dir> --tier <t> --base <ref>`) that computes the facts, reads history (pipelines root resolved per `_shared/pipeline-run-dir.md`), prints the selection as JSON, and logs one `SKIP` line per left-out lens with its reason through `log-decision.js`. The JSON is `{ tier, selected: [<lens id>], skipped: [{lens, reason}], fallback: null | "<reason>" }`, documented in the module header and pinned by a test; the Task path and the workflow `lenses` args both read it. `--run` is the log target only; history is read from the pipelines root. The full-tier fallback logs one `AUTO` line naming its reason.
3. Policy key (proposed `review-lens-selection`: `tier` | `adaptive`, default `tier`, added with `.claude/skills/policy-key-addition`). `tier` reproduces today exactly. With `adaptive`, Step 3 dispatches the CLI's set on every dispatch path (Task, workflow).
4. Step 3 prose: a new sub-file (proposed `plugin/skills/review/step3-lens-selection.md`) and one pointer line in `step3-lens-dispatch.md`; the workflow path (`step3-workflow-dispatch.md`) builds its `lenses` args from the same set.
5. A replay at build: run the function over at least 40 archived reviewed runs, each with only the strictly earlier runs as its history (the first 20 replayed runs read as `insufficient`), as a scratch script whose output is pasted into the PR, and report, per lens, how many lens agents it would have skipped and how many confirmed findings those skipped lenses produced in those runs. Quote it in the PR. The floors and fact lists are tuned on the older part of the archive and scored on a held-out newer slice of at least 20 runs. The pass bar is zero lost confirmed findings on held-out runs whose diff facts were computable. A miss is reported in the PR and blocks this repository's opt-in until the rule is retuned.
6. File a parked measurement record (Defer-reason: blocked-external, trigger: 20 `adaptive` reviews after this repository opts in, or 30 days): confirmed findings per run no lower than 8.3 with fewer lens agents, read from `step-yield.json` and `lens-dispatch.json`, and the design's three quality guards no worse; outcome a default-flip record or a stated reason to keep `tier`.

## Gotchas

- `step3-lens-dispatch.md` is 48,911 B, above the 47,250 B headroom line of the 52,500 B rail: new prose goes in the sub-file.
- `#5929` adds a whole-fan-out skip for a bookkeeping-only diff in `code-mode-steps.md`; the selector must agree with it, not duplicate it. A bookkeeping-only diff never reaches the selector.
- The skip rule must stay mechanical. A prose "skip if it doesn't apply" rule left beside it would let the session override the code. With `adaptive` on, the prose rule is replaced, not kept as a second filter.
- Under `tier` the existing prose skip rule and the `low`-tier skip stay exactly as today; only `adaptive` replaces them with the code's facts. On the Task path the session still executes the CLI and dispatches its set, so fidelity rests on the prose; `lens-dispatch.json` (#5998) beside the CLI output is the mechanical comparison the parked record reads.
- Floors and fact lists are tuned from the build replay, never guessed. Record each constant's source in the module header.
- Risk proof required: this record carries kept risk flags, so one plan step must contain, per slug, a line `Proof(<slug>): <text>` with a specific proof of at least 20 characters. Lines: `Proof(public-contract): …`.

## Decision Rationale

- **Why the tier stays the ceiling.** The tier is the review's cost and depth decision (`review-effort-derivation.md`); selection narrows within it and never widens it, so no review gets more expensive.
- **Why a key, default `tier`.** Design policy model: every new behaviour ships as a policy value whose default reproduces today; a default changes only after 20 runs show the quality guards no worse.
- **Why the measurement is a parked record.** It needs released runs; the build replay supplies the paired evidence beforehand.

**Decision (plan review Q1, `risk-path-globs` gating):** Reading A. The selector reads `risk-path-globs` only when control mode is on, gated exactly as `plugin/bin/accept-park.js` gates it. With control mode off, only the built-in protected-path list (`express/eligibility.js`'s `isProtectedPath`) and the record's `Risk-flags:` set the "risk path touched" fact. The key's existing contract and doc row stay unchanged.
