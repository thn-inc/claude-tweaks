# 5584: Build a record named in a typed dispatch command without an auto:build label

Surface: backend

**Related:** #4608, #4623, #4624, #5232, #5225, #5231, #5053, #5558, #5387
Risk-flags: auth
Risk-flags-unconfirmed: true

## Current State

`/claude-tweaks:dispatch` and the pipeline driver build a record only when it carries the `auto:build` label. Decision 0.2 of `docs/superpowers/specs/2026-11-15-process-efficiency-design.md` (answered 2026-11-15) changes one case: a command the maintainer types that names the record carries its own build authority. A run a hub or a routine starts still needs the label. The design read the cost of the refusal from session transcripts of 2026-10-08 to 2026-11-15: a refine, a label confirmation and a second dispatch for a record the maintainer had just named.

Where the label is required today (checked on 2026-11-16):

- `plugin/bin/lib/dispatch/queue-pull.js` fetches the pool with `--label auto:build` (`QUEUE_ARGV`, line 190) and filters it on `facets.grants.build` (line 425). A record without the label is never in `dispatch-groups.json`, so no selection form can pick it.
- `plugin/skills/dispatch/SKILL.md`: the `#N` bullet says "confirm it currently carries `auto:build` and no `bot:*` label". The `#N[,#M,#O...]` bullet reports "no `auto:build` grant" for a named record that is not in the pool.
- `plugin/bin/lib/driver/admission.js` line 122 refuses with `record lacks auto:build` (`ADMISSION_REASONS.noBuildGrant`). `plugin/bin/lib/driver/steps.js` runs it for every record, named or picked by `--budget`.
- `plugin/bin/lib/dispatch/resume-eligibility.js` line 341 refuses `dispatch resume #N` with `not-granted` when the label is absent.
- `plugin/bin/claim-targets.js` does not check the label. Neither does `/claude-tweaks:flow #N` (`plugin/skills/flow/claim-targets.md` reads the open queue "not filtered to `auto:build`"). A person can already build an ungranted record by typing `/claude-tweaks:flow #N`. Only the dispatch and driver entries refuse.
- `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md` states the rule this record reverses: its Eligibility section ("Naming a record on the command line is not authorization") and item 8 of "Calls made in this document that were not discussed".

What the plugin knows today about who started a run:

- Nothing, in code. No file under `plugin/bin` reads `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ATTENDED` or a `CC_*` variable. Whether a person is present is judged by the model from prose (`plugin/skills/dispatch/task-prompt.md`'s `--headless` decision, `SKILL.md`'s Next Actions rule). `SKILL.md` and `plugin/skills/_shared/headless-self-report.md` assume the `#N` forms "always run with a human present".
- `autonomy: unattended` is a policy tier, not a presence signal. `isNestedSession` in `plugin/bin/lib/hooks/context.js` is about a run's owner process.
- `plugin/bin/lib/hooks/user-prompt-submit.js` sees every prompt a person submits, before a slash command is expanded. It records a typed `/claude-tweaks:<skill>` first line as a `skill_invoked` event with `source: "user"`, only into a run the session owns, and ignores the arguments. A Skill call the model makes fires no `UserPromptSubmit` event (the module's header comment).
- Measured on 2026-11-16 on Claude Code 2.1.325, in a Bash child of a terminal session: `CLAUDE_CODE_ENTRYPOINT=cli`, `CLAUDE_CODE_SESSION_ATTENDED=1`, `CLAUDE_CODE_REMOTE` unset, stdin not a terminal.
- A session opened by `cc hub spawn` has the same environment as one a person launched. `cc hub spawn` belongs to `cc-router` in the `claude-user-config` plugin (repository `thn-inc/claude-user-config`); it opens a terminal tab whose first prompt is the command it was given. Both kinds of session carry `CC_POSTURE`, and the spawned one carries nothing more. Only a headless run the hub starts has a marker, `CC_HUB_RUN` (that plugin's `skills/hub/reference/contract.md`, version 0.13.0). So no code can tell a spawned session from a person's today.

## Technical Approach

**The rule.** `resolveBuildAuthority({ number, labels, named, env, proof, stdinIsTTY, now })` returns `{ authority, reasons }`. Closed rule: the rows below are every state. A state not listed is `none`, with one line naming it and the remedy `/claude-tweaks:backlog refine #N`. A plan review that finds another state adds its row as a plan amendment, not as a question.
Decided 2026-11-16: authority is per record, never per group. The queue pull adds only a record that is both in `--named` and answered `typed`; an ungranted record the command did not name is never fetched into the pool, so no pass can bundle it. A number in `--named` with no proof entry of its own is `none`, whatever the other numbers have. The passes treat a `typed` record exactly as a `label` record, so a bundle may hold both. In the driver, `named` is true only for a number in `drive.js`'s own arguments.

| State | Answer |
|---|---|
| `labels` is not an array | `none` (labels unreadable) |
| labels carry `auto:build` | `label`, as today; nothing else is read |
| the command did not name the record (a drain, `--budget`, a bundle member the command did not name) | `none` |
| named, labels lack `ready` | `none`; the remedy is `/claude-tweaks:specify #N` |
| named, `ready`, inside a Claude Code session, and every session condition holds | `typed` |
| named, `ready`, outside a Claude Code session, and every terminal condition holds | `typed` |
| anything else | `none`, with each failed condition named |

"Inside a Claude Code session" means `CLAUDECODE` or `CLAUDE_CODE_SESSION_ID` is set. Every comparison is exact string equality. An unset, empty or other value fails its condition.

Session conditions, all required:

1. `CLAUDE_CODE_ENTRYPOINT` is `cli`. A headless `claude -p` run and an SDK process have another value.
2. `CLAUDE_CODE_SESSION_ATTENDED` is `1`.
Decided 2026-11-16: conditions 1 to 3 only rule out runs known not to be a person's: a headless run, a cloud sandbox, a hub's headless run. None of them shows a person is present; condition 4 and the proof carry that. A value the probe table does not list reads as `none`, so a Claude Code release that changes a value takes the typed path away and does not widen it. The one change that would widen it, a headless run reporting `cli`, is what the parked record's re-run of rows (a) and (d) looks for.
3. `CLAUDE_CODE_REMOTE` and `CC_HUB_RUN` are unset or empty. The first marks a cloud sandbox, where a Routine runs; the second marks a headless run a hub started.
4. The launcher says a person launched the session: when `CC_POSTURE` or `CC_LAUNCHED_BY` is set, `CC_LAUNCHED_BY` must be `user`. When neither is set, no launcher is in play and the condition holds. `cc-router` does not export `CC_LAUNCHED_BY` yet, so on a machine that launches through `cc` the label stays required until the companion change ships there. That is the fail-closed direction.
Decided 2026-11-16: the variable is `CC_LAUNCHED_BY` and its values are `user` and `hub`. Only the exact value `user` passes; `hub`, an empty value and any other value fail. `docs/hooks.md` records the variable, the two values and its owner, `skills/hub/reference/contract.md` in `thn-inc/claude-user-config`.
5. The proof names the record: `typed-dispatch.json` is a regular file under this session's temp directory, parses, carries this session's id, and its time for the record is not later than `now` and not older than `TYPED_DISPATCH_MAX_AGE_MS`, a named exported constant of 30 minutes.

Terminal conditions, all required: stdin is a terminal; `CI` is unset or empty; conditions 3 and 4 above. Only `drive.js` is run this way: the queue pull and `dispatch-resume.js` pass `stdinIsTTY: false`, so outside a session they answer `none`. `drive.js` run by the model inside a session takes the session conditions, so it needs the proof for that record.

The proof file's shape is `{ "v": 1, "sessionId": "<id>", "records": { "<n>": "<ISO time>" } }`, written to a temporary name in the same directory and renamed. One helper in `build-authority.js` writes it and one reads it; the hook and the three callers use those and hold no path or pattern of their own. No caller names the file, so the reader treats it as untrusted: it uses `lstat`, reads only a regular file, and never follows a link. A missing file is the ordinary case and is reported in the refusal line as "no typed command on record for #N". A link of any kind, a file that does not parse and a file over the size bound are reported as "typed-command proof unreadable".

A proof is not consumed. It stands for "the maintainer typed this record's number into this session" until it ages out, so the queue pull, a later `drive.js` call from the same session and `dispatch resume` all get the same answer.
Decided 2026-11-16: the bound is 30 minutes and the proof is still not consumed. It has to last only from the typed prompt to the admission that follows it; the dispatch step before the pull is given 150 seconds. A failed run is retried by typing the command again, which writes a new proof. Authority is re-derived at every use from the record's live labels: a record that lost `ready`, or gained `bot:blocked`, `bot:parked` or `parked`, is refused by the rule or by the gate that already refuses a granted record in that state (AC15). A call the model starts inside the 30 minutes gets the answer the typed command got; that is accepted.

**What this guards against, and what it does not.** It refuses a run started by a routine, a headless worker, a hub spawn or the model's own Skill call. It does not stop a session that writes the proof file by hand, as nothing stops a session that adds the label by hand today.

**Sites.** The four refusals in Current State are the only gates on the label. Other readers of `facets.grants.build` (`plugin/bin/lib/issues/backlog.js`, `pending-authorization.js`, `plugin/bin/lib/dispatch/stuck-open-pr.js`, `plugin/bin/lib/record-graph/encode.js`, `materialize-format.js`) report or sort and do not change.
Decided 2026-11-16: this record retires an invariant: a record being built may now carry no `auto:*` label, and `plugin/skills/_shared/work-record.md` says so. One consumer is fixed here. `plugin/skills/dispatch/settle-and-merge.md` step 6 removes `auto:build` without reading the labels first; if removing an absent label fails the edit, `bot:blocked` does not land (AC16; the Gotchas name the check). AC11 covers the code this record adds. What `/claude-tweaks:backlog` shows for a typed record at `pending-review` is reported, not changed (AC17). No source scan for other label readers is added: the three gates call the one rule and their tests show it.

**Queue pull.** The named records are added after the pool fetch and before the first pass, so the passes and their registry are untouched and no exclusion reason is added. The filter at line 425 accepts a record the rule answered `typed` for. `--run` is resolved by `resolveTarget` in `plugin/bin/lib/log-decision/append.js`, the guard `log-decision.js` already uses; no second guard is written. The retained script in `plugin/skills/dispatch/queue-pull-script.md` gets nothing: it has no `--named`.

**Driver and #5232.** #5232 (open, not built) hands a singleton from dispatch to `drive.js --check #N`. With this record the driver reads the same proof through the same rule, so that route needs no extra flag for a typed record.

**CLI flags.** The audit design's Phase 3 moves every `plugin/bin` CLI onto one argument parser. Its parent, #5533, lists that phase as not yet specified on 2026-11-16, so `--named` and `--run` go into `queue-pull.js`'s own parser. If that phase has reached `queue-pull.js` when this builds, add them through the shared parser.
