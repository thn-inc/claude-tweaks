# 3191: /claude-tweaks:capture should search open PRs for overlap before filing, not just recently-merged commits

Surface: infra

**Related:** #3047

## Current State

`/claude-tweaks:capture`'s `github-issues` filing step (`plugin/skills/capture/SKILL.md`, Backend Selection, the **Recent-commit overlap check** paragraph immediately after the `gh issue create` calls) screens a just-filed record against recently-merged commits only, via `_shared/health-recent-commit-check.md` → `findRecentCommitOverlap` (`plugin/bin/lib/issues/recent-commit-check.js`, a pure `git log` subject grep over a 14-day window, minimum 2 shared key terms from `deriveKeyTerms(title)`). Nothing in capture's filing path looks at **open pull requests**, so work already in flight on an open PR is invisible at filing time until it merges.

Two other screens exist and do not cover this case:
- `capture/routing.md`'s absorb-visibility search matches open *records* in the session snapshot, but its headless bar absorbs only on a literal path match plus a matching `type:{t}`, and absorb never targets a `bot:in-progress` carrier, so an agent-driven filing against an in-flight record files fresh.
- `/specify`'s Near-duplicate candidate check (`shapingRefusal`, `plugin/bin/lib/issues/near-duplicate.js`, #3141) refuses a title-similar `ready` candidate with a live claim or open linked PR, but only at shaping time, after the duplicate is already filed.

Observed cost (verified against GitHub): #3155 (`bin/verify.js baseline adjudication mangles failing-file paths in a space-containing checkout path`) had its fix open as PR #3172 from 2026-10-15T18:30Z until it merged 2026-10-16T04:55Z. During that window three more `by:capture` records described the same defect: #3178 (18:42Z), #3185 (19:13Z), #3189 (19:30Z), plus #3171 filed three minutes before the PR opened. #3185's closing comment reads "Duplicate of #3155 (already has an open fix in flight, PR #3172) — I filed this before checking open PRs for overlap". It was caught only because #3119's review ran an unrelated open-PR listing (its Cherry-Pick Provenance Check). Measured with the shipped `deriveKeyTerms`, each of the three PR-window titles shares at least 3 key terms with PR #3172's title (3, 5, and 4 respectively; `verify` in all three), well over the 2-term threshold, so the existing term-overlap heuristic, run against open PR titles, would have flagged every one.

## Deliverables

- [ ] A pure open-PR overlap function in `plugin/bin/lib/issues/recent-commit-check.js` (beside `findRecentCommitOverlap`, reusing `deriveKeyTerms` and `DEFAULT_MIN_TERM_MATCHES`). Input: a candidate title plus an already-fetched open-PR list (`[{ number, title, url }]`). Output: the strong matches, ranked by matched-term count with `matchedTerms` per entry, or `null` when nothing matches or the input is unusable. No network inside the function. The caller fetches.
- [ ] `plugin/skills/capture/SKILL.md`'s `github-issues` filing step runs an **open-PR overlap check** before `gh issue create`: one `gh pr list --state open --json number,title,url --limit {N}` call, its output written to a temp file and handed to the new function. A non-null result is held, then posted as one triage comment on the new record right after `gh issue create` succeeds. The comment names up to 5 PRs (`#{number} {title}`) and says it is a heuristic screen, not a verdict. It sits beside the existing Recent-commit overlap check comment and is never a block, hold, or absorb.
- [ ] Fail open everywhere: a `gh pr list` failure, a non-JSON response, or a thrown function means no comment, and filing proceeds exactly as today. A retry or replay of an already-screened payload does not post the comment a second time (the same once-per-payload rule the commit check states).
- [ ] Unit tests in `tests/bin-lib/issues/recent-commit-check.test.js` for the new function. Fixtures are the real incident titles: PR #3172's title against #3178/#3185/#3189's titles (each must match), an unrelated open-PR title sharing at most one term (must not match), and empty, malformed, or non-array PR input (must return `null`).

## Technical Approach

Keep the matching logic in one module so the two screens cannot drift. Add the open-PR function to `recent-commit-check.js` next to `findRecentCommitOverlap`, with the same term derivation, stopword list, and 2-term threshold. The only differences are the data source (PR titles instead of `git log` subjects) and ordering by match strength (PRs have no single meaningful date). Keep it pure: the module header promises "never the network, never `gh`", so `gh pr list` runs in capture's skill prose, its JSON goes to a session-scoped temp file, and a `node -e` call reads the file and calls the function. The `node -e` call follows the commit check's own invocation shape, and the file handoff follows the near-duplicate check's never-inline-titles rule, since a PR title with an apostrophe breaks shell quoting.

Ordering inside capture's filing step:
1. Before `gh issue create`, run the open-PR screen and hold its result.
2. Run `gh issue create` (each branch: native-type a/b/c, or labels) unchanged.
3. Post the existing Recent-commit overlap comment, then the new open-PR comment if the held result is non-null. These are two separate comments, so each keeps its own provenance line.

The search runs before filing, and the comment posts after it, because only a filed record can carry a comment and the record says triage note, not block. Running the search first also lets a human-present capture show the match in its "Added:" presentation line without an extra prompt.

### Key Files

- `plugin/bin/lib/issues/recent-commit-check.js` — add the pure open-PR overlap function and export it; update the header comment to name both screens.
- `tests/bin-lib/issues/recent-commit-check.test.js` — new cases for the open-PR function, using the real #3155-incident titles as fixtures.

## Gotchas

- Scope is capture only. `_shared/health-recent-commit-check.md` is also cited by `/code-health`, `/docs-health`, `/harness-health`, `/journey-health`, and `/intake`. Do not add the open-PR step to that shared file, or it would silently widen to every health-sweep filing loop and change their per-finding `gh` call count. Extending the screen to the sweeps is a separate decision.
- `--limit` sizing: `gh pr list` defaults to 30. Size `{N}` per `_shared/github-write-transport.md`'s "Sizing the list-then-filter window" so a busy queue does not truncate away the matching PR. Use a plain `gh pr list`, never `--search` (`dedup-lookup.js`'s header: the Search API is eventually consistent and the wrong tool for an existence check).
- Noise: open PRs whose own title restates an issue title (`... (#3155)`) match on the same terms the issue would. That is the intended signal, but keep the threshold at the module default rather than lowering it. The test fixtures pin both directions.
- `gh`-absent environments: capture's `github-issues` branch already falls back to the local driver when `gh` is unusable (its own Decision #1352), so the open-PR step simply does not run there. No MCP path is needed for this screen.
- `deriveKeyTerms` does not split hyphenated tokens (`--baseline`, `space-containing` stay whole), which is why #3189 matched on 4 terms rather than more. The threshold still clears comfortably on the incident titles. Do not widen tokenization in this record, because it would also change the commit screen's behavior for all six of its citers.
- Do not reuse `bot:in-progress` as the in-flight signal. #3141 already established it is a projection that outlives the build, and an open PR is the direct evidence.
