# 3269: pr-first-merge Step 3 misses the 'Protected branch rules not configured' auto-merge signature

Origin: dispatch close-out of #3001 (PR #3235)

Defer-reason: pre-existing-outside-diff

## Current State

`plugin/skills/_shared/pr-first-merge.md` Step 3 branch 1 recognizes the auto-merge-not-enabled case by the stderr wording `Auto merge is not allowed for this repository`, or a paraphrase containing `auto-merge` and (`not allowed` or `not enabled`). On 2026-10-16, `gh pr merge 3235 --auto --squash` on this repo instead failed with:

```
GraphQL: Pull request Protected branch rules not configured for this branch (enablePullRequestAutoMerge)
```

That is the same condition: auto-merge cannot be armed because the base branch has no protection rules. But it matches neither form, so a literal reading falls through to branch 5 ("anything else"), degrades to ready+comment and parks a PR that is green, CLEAN and human-confirmed as `pending-review`. The #3001 close-out merged it only by treating the message as branch 1 by hand: under `merge-when-green` that means the `wait` row, re-reading state, then an immediate `--squash`.

## Deliverables

- Add this signature to branch 1's recognized set. Match on `enablePullRequestAutoMerge` together with `Protected branch rules not configured`, so the auto-merge-unavailable family routes to branch 1's per-lever handling instead of branch 5.
- Do the same anywhere else that classifies this stderr. Check `dispatch/settle-and-merge.md`'s Auto-merge gate, `actions-github-issues.md`'s `## Arm ready PR`, and any `bin/` code that parses `gh pr merge` failures; grep `Auto merge is not allowed` repo-wide.
- Add a conformance or unit test pinning the new signature next to the existing one.

## Acceptance Criteria

- Under `merge-when-green` with a green rollup, a `gh pr merge --auto` failure carrying `Protected branch rules not configured for this branch (enablePullRequestAutoMerge)` routes to branch 1, not to ready+comment.
- The test fails when the new signature is removed from the classifier or prose.

## Release Note

Auto-merge arming now recognizes the "Protected branch rules not configured" failure and routes it to the auto-merge-unavailable handling instead of a generic failure.


## Absorbed: 2026-10-18 — pr-first-merge: second auto-merge refusal wording, "Pull request is in clean status"

Origin: dispatch close-out of #3398 (PR #3427) and #3370 (PR #3434), 2026-10-18.

The same branch-1 condition surfaces under a second GraphQL wording. On PR #3427 (green rollup, `mergeStateStatus: CLEAN`, undrafted, no required checks), `gh pr merge 3427 --auto --squash` failed twice with:

```
GraphQL: Pull request Pull request is in clean status (enablePullRequestAutoMerge)
```

GitHub refuses to arm auto-merge on a PR it could merge right now. PR #3434 in the same close-out hit the `Protected branch rules not configured` wording above on its first attempt, and a retried `--auto` call then merged it immediately (exit 0, `state: MERGED`, `autoMergeRequest: null`) — the Step 2.5 "arming is an immediate merge" case, not an arm.

Additional deliverables:

- Match on `enablePullRequestAutoMerge` together with `is in clean status` as a second branch-1 signature, alongside the `Protected branch rules not configured` one above — or match on the `(enablePullRequestAutoMerge)` mutation suffix alone, since every wording seen so far carries it and all mean "cannot arm".
- Add the new wording to the same conformance/unit test.

Additional acceptance criterion:

- Under `merge-when-green` with a green rollup, a `gh pr merge --auto` failure carrying `Pull request is in clean status (enablePullRequestAutoMerge)` routes to branch 1 (the `wait` row: re-read, then immediate `--squash`), not to ready+comment.
