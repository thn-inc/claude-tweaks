# 4177: Windows regression: 1 test file(s) newly failing after 5fbf792bd

Surface: infra

## Current State

The post-merge `windows-regression` run on `5fbf792bd` (#4006, run 40113021243) attributed 7 failures in `tests/bin-lib/verify/cli.test.js` as new. They are the #4006 tests AC1.1, AC2.1, AC3.1, AC5.1, AC6.1 and AC9.1, plus "#4006: discovery resolves from a subdirectory of the checkout". #4006's discovery code is not the cause. The same run fails 46 tests in that file. The #3002 `--stamp-suite` composition tests and most `--scope` tests were already failing on Windows, and the baseline comparison classed them as pre-existing.

The shared cause is the test fixtures' shell quoting. `plugin/bin/lib/verify/run.js` spawns every `--cmd` string with `{ shell: true }`, which is `/bin/sh` on POSIX and `cmd.exe` on win32. The fixtures write their check commands in POSIX single-quote form so a `JSON.stringify`'d path can sit inside the script:

- `scopedRepo()`'s `unitCmd` (`tests/bin-lib/verify/cli.test.js:711`) is `` `node -e 'require("fs").writeFileSync(${JSON.stringify(marker)}, "ran")'` ``, reused by `mergedScopedRepo()` and by every #3002/#4006 composition test.
- 11 more literal `node -e '…'` commands in the same file, at lines 328, 911, 951, 952, 1022, 1029, 1046, 1079, 1080, 2049 and 2726.

`cmd.exe` does not treat `'` as quoting, so node receives a broken `-e` script and exits 1. Every test whose check must pass then fails at `run.code === 0` or reads a missing per-suite record. Of the 46 Windows failures in the file, 44 trace to these commands, directly or through `scopedRepo`/`mergedScopedRepo`. The comment at `cli.test.js:907` (and its twin above the `#1801 shape` test) records why outer single quotes were chosen: a double-quoted `-e` script cannot hold a `JSON.stringify`'d double-quoted path. That constraint is real on `/bin/sh` too, so the portable form cannot just swap the quote characters.

The defect is confined to the tests. `.claude-tweaks/verify-scope.json` declares no single-quoted command, and the `node -e '…'` snippets under `plugin/skills/` run in Claude Code's Bash tool, not through `verify.js --cmd`. #4174's end-to-end test uses `node -e 0` and passed the Windows run on `c300bb076`.

**Related:** #2767 (the Windows full-suite baseline umbrella: CRLF and path-separator classes; this cmd.exe-quoting class is not among its named buckets), #4006, #4020, #4055 (both the out-of-class unreadable-log test below); near-duplicate screen: #3489, #3702, #3703, #3751, #3953, #3982, #3983, #3993, #3995, #4042, #4121, #4135, #4146

## Deliverables

- Replace each single-quoted fixture command in `tests/bin-lib/verify/cli.test.js` (`scopedRepo`'s `unitCmd` and the 11 literal sites) with a form that both `/bin/sh` and `cmd.exe` parse identically. Pass every path, and every `{base}`/env value the script needs, to the `-e` script as a `process.argv` argument rather than splicing it into the script text, so no quote nests inside another.
- Do it through one small helper in the test file, so later tests reuse it instead of re-deriving the quoting.
- Update the comment at `cli.test.js:907` and its twin above the `#1801 shape` test to state the new rule (argv, not splicing) and why: `cmd.exe` gives `'` no meaning.
- Add a source-scan assertion in the same file that fails if a `node -e '` command literal reappears in it.

## Technical Approach

A shell-neutral command shape for both shells:

```js
const nodeWriteCmd = (file, content) => `node -e "require('fs').writeFileSync(process.argv[1], process.argv[2])" ${q(file)} ${q(content)}`;
```

Here `q` double-quotes an argument. In a double-quoted string, `/bin/sh` treats only `$`, backtick, `\` and `"` specially, and `cmd.exe` treats only `%` and `"`. The script body above contains none of them, and the paths and values travel as separate argv entries. Pick `q` so a Windows path (`D:\a\_temp\…`) reaches node byte-exact under both shells. Pass the raw path in double quotes, not `JSON.stringify`, which would double every backslash. Check a value containing `{base}` and an env read (lines 911, 1046, 2726) against `plugin/bin/lib/verify/file-template.js`'s win32 refusals before choosing its shape.

Prove it on Windows by dispatching `windows-regression.yml` on the pushed branch (`gh workflow run windows-regression.yml --ref <branch>`). The workflow exists on `main`, and a dispatch compares against the branch's merge-base with `main`. Read the downloaded `verify-report` artifact's `verify-logs/tests.log` for the failing set. CI's own `test` job is Linux-only and cannot show the Windows result.

### Key Files

- `tests/bin-lib/verify/cli.test.js` — the 12 single-quoted fixture commands, the new shell-neutral helper, the two quoting comments, and the new source-scan assertion
- `plugin/bin/lib/verify/run.js` — read-only: the `{ shell: true }` spawn whose per-platform shell sets the constraint
- `plugin/bin/lib/verify/file-template.js` — read-only: win32 refusals the `{base}`-carrying fixture commands must not trip

## Gotchas

- 2 of the file's 46 Windows failures have other causes, and this record does not fix them. Both predate #4006. One is the unreadable-log test at line 199, which depends on file permissions and is already filed as #4020 and #4055. The other is the stale-scratch-worktree test at line 3407, which compares a forward-slash `D:/a/...` path and stays under #2767's baseline.
- Do not "fix" this by switching `run.js` away from `shell: true` or forcing `bash`. `--cmd` is the caller's whole shell string by design (`run.js`'s header), and users' Windows commands rely on `cmd.exe`.
- The windows-regression workflow runs only on pushes to `main`, plus manual dispatches. A green PR `test` check says nothing about Windows, which is how all 44 of these failures shipped.
- `cmd.exe` expands `%VAR%` even inside double quotes. Keep `%` out of every fixture command.
