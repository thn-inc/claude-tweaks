# 2254: The local engine `bin/release-local.js`

Surface: infra

## Overview

No-forge (`local-merge`) projects have no engine to compute versions, bump manifests, or write CHANGELOG entries — release-please only exists for GitHub-backed `pr-first` projects. This unit builds `bin/release-local.js`, a plugin-owned CLI that reads first-parent conventional-commit history since the last tag, computes a semver bump, edits the manifest and CHANGELOG, tags, and (optionally) runs a `release-hook` command — emitting **byte-compatible** artifacts (same tag scheme, same CHANGELOG grammar) so a project can move between `pr-first` and `local-merge` with no format discontinuity in its history.

**Complexity:** High
**Estimated tasks:** 8

## Non-Goals

- Anything for `pr-first` projects — this is the `local-merge`-only engine; release-please remains the pr-first engine, untouched by this unit.
- Publishing to a registry or deploying — `release-hook` is the project's own escape hatch for that; this CLI only runs the hook command and surfaces its exit code (design doc stance 6).
- Re-implementing `plugin/bin/release.js`'s marketplace-mirror or `docs/shipped-versions.tsv` logic — those are this repo's own maintainer tooling, retired in Phase 8 (a separate unit), not generalized here.
- Assuming `local-merge` implies no `origin` remote at all — `local-merge` describes the *integration model* (no PR-based workflow), not the presence or absence of a git remote. A local-merge project may still push to a remote (a self-hosted mirror, a private GitLab, or even a GitHub remote used only for backup/pull, never for PRs); this unit's push step and `changelog.js`'s compare-URL logic both branch on whether `origin` exists and parses as a GitHub remote, independent of the `integration-model` value.

## Current State

That pr-first call site keeps working unchanged until Phase 8 (a separate, later unit) retires `release.js` and re-points it; this unit does not touch that call site.

## Deliverables

- [ ] `plugin/bin/release-local.js` — the CLI entry point, `run(argv, deps)` per `gh-api-module-pattern`'s contract.
- [ ] `plugin/bin/lib/release-local/commits.js` — `git log --first-parent {lastTag}..HEAD`, parsed with a conventional-commit header regex `^(\w+)(\([^)]*\))?(!)?: (.+)$` plus `BREAKING CHANGE:` footer detection. An unparseable subject is reported as `unconventional` in the plan output, never silently dropped — the plan surface is the "could not parse this" signal (`parse-signal-discipline`). **First-release case (no prior tag):** when no `v*` tag exists in the repo at all, `lastTag` resolves to the sentinel value `null` and the commit range becomes every first-parent commit reachable from `HEAD` (the equivalent of `git log --first-parent HEAD`, no `{lastTag}..` bound) — this is a normal, expected state for a repo's first-ever release, not an error.
- [ ] `plugin/bin/lib/release-local/bump.js` — bump derivation: a `!` suffix or `BREAKING CHANGE:` footer → major; any `feat` commit (no breaking marker) → minor; else at least one `fix` → patch; a history of only `chore`/`docs`/etc. → `none` (exit 3, nothing to release). On the first-release case (`lastTag` is `null`), the same precedence applies over the full commit range; a first release with no `feat`/`fix`/breaking commits at all still exits `3`.
- [ ] `plugin/bin/lib/release-local/manifest.js` — reuses the stack-detection table unit 3's `step-21-release.md` defines (`package.json` `.version`, `pyproject.toml` `[project].version`/`[tool.poetry].version`, `Cargo.toml` `[package].version`, or a `simple`-type `extra-files` JSON path / regex) — cited by reference, not re-derived; if unit 3 changes that table's shape before this unit lands, this unit's copy moves with it (not a hard build-order block — the table is static reference content). Byte-preserving edits implemented as a raw string/regex splice that locates and replaces only the version token's own characters — never a `JSON.parse`+`stringify` round-trip or a TOML re-emit, either of which risks reformatting the surrounding file (reordering keys, changing indentation) and silently violating the byte-preserving AC.
- [ ] `plugin/bin/lib/release-local/changelog.js` — prepends a new section in the release-please grammar: compare URL derived from `origin` when it parses as a GitHub remote (independent of `integration-model` — see Non-Goals), omitted otherwise; no PR links under local-merge (there are none to link). The exact byte grammar this module targets is captured as part of this unit's own build (see the fixture deliverable below), not pre-supplied by this spec.
- [ ] Reuse `plugin/bin/lib/release/precheck.js` and `plugin/bin/lib/release/run.js`'s clean-tree/branch guard and fetch → ancestry-recheck → push ordering — no duplicate implementation of either. `precheck.js` gains a `keySource: 'tags' | 'tsv'` parameter rather than being silently re-keyed in place: this repo's own pr-first `plugin/bin/release.js` passes `'tsv'` (its existing, unchanged behavior, until Phase 8 retires that call site entirely) and this unit's `release-local.js` passes `'tags'` — the same module serves both without either caller's collision detection silently changing behavior out from under it.
- [ ] Sequence wiring: guard → plan → (`--dry-run`: print plan, exit 0) → manifest + CHANGELOG edit → one commit `chore(release): v{version}` → `git tag -a v{version} -m "v{version}"` → push branch and tag (skipped when no `origin` configured) → run `release-hook` if the `release-hook` policy key (unit 3's schema entry, read from `.claude-tweaks/policy.yml` via the shared policy-schema reader) is set, surfacing its exit code as the CLI's own exit code when it fails. Exit vocabulary: `0` released, `1` git/engine failure — nothing written, **or** a partial state where the commit/tag landed locally but the subsequent push failed, reported as a named partial state with an explicit recovery command exactly per `run.js`'s existing "do NOT re-run" pattern; `2` usage error; `3` nothing to release; `4` collision detected; `5` hook failed after the tag (and its push, when `origin` exists) already fully landed — exit 5 carries the identical "named partial state with a recovery command" obligation as exit 1 (the git/tag side is done and must not be re-run; only the hook needs re-invoking).
- [ ] `tests/bin-lib/release-local/changelog-fixture.test.js` — a real release-please-generated CHANGELOG section, captured as part of this unit's own build (run release-please once against a representative commit set, or source a section this repo's own Phase 3/8 bootstrap later generates) and committed as a fixture file; asserts `changelog.js` reproduces it byte-for-byte from the equivalent commit list (excluding PR links, which don't exist under local-merge). This fixture is the mechanism behind the byte-compatibility guarantee (design doc stance 4) — a release-please upgrade that changes its own output grammar fails this test first, which is the intended alarm, not a false positive to silence.

## Acceptance Criteria

1. On a fixture repo with `v1.2.0` tagged and two `fix:` commits plus one `feat:` commit since: `--dry-run` reports proposed version `1.3.0`, three CHANGELOG bullets, and "no hook configured" — and writes nothing to disk.
2. The same fixture run live (no `--dry-run`) lands the manifest edit, the CHANGELOG section, the `chore(release): v1.3.0` commit, and the `v1.3.0` annotated tag; `git describe --contains HEAD` afterward prints `v1.3.0`.
3. A commit history containing only `chore:`-type commits since the last tag exits `3` and writes nothing to disk (no commit, no tag, no manifest edit).
4. `tests/bin-lib/release-local/changelog-fixture.test.js` passes: `changelog.js`'s output for the fixture's commit list matches the captured release-please section byte-for-byte, excluding PR-link text.
5. A history with a `feat!:` commit or a `BREAKING CHANGE:` footer computes a major bump, even when other commits in the same range are only `fix:`/`chore:`.
6. Every exit code in the vocabulary (0/1/2/3/4/5) is exercised by at least one `run(argv, deps)` fake-runner unit test, including a distinct case for exit 1's push-failure-after-commit-and-tag partial state (separate from exit 5's hook-failure partial state).
7. On a fixture repo with **no prior `v*` tag** and one `feat:` commit: `--dry-run` reports proposed version `0.1.0`'s next minor equivalent per `bump.js`'s precedence (i.e., the first release computes from the full first-parent history with `lastTag` treated as `null`, not as an error) — proving the first-release path is a supported case, not an unhandled edge.
8. `precheck.js` called with `keySource: 'tsv'` (simulating `release.js`'s existing pr-first call) and called with `keySource: 'tags'` (this unit's own call) both resolve collision detection correctly against their respective sources in the same test file — proving the parameterized reuse doesn't silently change the tsv-keyed caller's behavior.

## Technical Approach

`commits.js`'s unparseable-subject handling is the one place this unit must resist the "silent fallback" failure mode: an unconventional subject in the range is real signal (someone bypassed the composer, or a merge commit slipped through) and must surface in the plan output rather than being quietly excluded from the bump calculation — excluding it silently would understate the actual set of changes being released. `manifest.js`'s byte-preserving requirement exists because a reformatting edit (e.g., a JSON pretty-printer changing key order or indentation) would produce an unreviewable diff on every release; only the version token itself should change.

### Data / API Surface

- `commits.js` conventional-commit header regex: `^(\w+)(\([^)]*\))?(!)?: (.+)$` — capture groups: type, optional scope, optional `!`, subject text. `BREAKING CHANGE:` footer detected as a line starting with that literal text anywhere in the commit body.
- `bump.js` precedence: `major` (breaking marker present) > `minor` (any `feat`, no breaking) > `patch` (at least one `fix`, no `feat`/breaking) > `none` (no `feat`/`fix`/breaking commits at all).

## Gotchas

- `run.js:67-74`'s "do NOT re-run" partial-state pattern exists because a naive retry after a partial failure (e.g., commit landed but tag push failed) can double-apply a version bump — reuse that exact guard rather than writing a new one; a named partial state with an explicit recovery command is the contract, not a bare error message. This obligation applies identically to exit 1 and exit 5 — both describe a state where local git history has already changed and must not be blindly re-run.
- The changelog fixture is the contract between engines (design doc's Testing section) — treat a failing fixture as "release-please's grammar moved, go re-capture the fixture," never as "loosen the assertion to make it pass."
- `precheck.js` gains a `keySource` parameter rather than being re-keyed in place — this repo's own pr-first `plugin/bin/release.js` keeps calling it with `'tsv'` unchanged until Phase 8 retires that call site entirely; this unit's `release-local.js` is the only caller passing `'tags'`. Do not leave a dual-read path inside `precheck.js` itself that checks both sources for one call — each caller passes exactly one `keySource` and gets exactly that source's collision check.
- `manifest.js`'s stack-detection table is unit 3's `step-21-release.md` content, cited by reference — reading it doesn't require unit 3's PR to have merged (it's static reference content), but if unit 3's table shape changes materially before this unit lands, re-sync this unit's copy rather than letting the two silently diverge.

## Build deviations (Beneficial — applied, /build Common Step 4.5)

- **Commit links follow the GitHub-origin condition.** The bullet's `([sha7](repo/commit/sha))` needs a repo URL exactly as the compare URL does; without a GitHub `origin` the heading is `## X.Y.Z (date)` and bullets are bare (plan ruling 1).
- **Hidden commit types render only when breaking**, per release-please's default `changelog-sections` (docs/style/chore/refactor/test/build/ci) — the byte-compatibility guarantee covers what release-please would have rendered (ruling 2).
- **First-release base is the current manifest version** (`.release-please-manifest.json`, then the stack manifest, then `0.0.0`), so Step 21's seeded `0.1.0` + `feat` releases `0.2.0` (ruling 3; AC 7).
- **`.release-please-manifest.json` and `package-lock.json` are spliced too** — release-please updates both; the lockfile splice is structural (root + `packages[""]`), never a counted occurrence (rulings 4 and 9).
- **`java`/`ruby`/`dotnet` refuse with a pointer to `simple` + `extra-files`; `go` is tag-only** (ruling 5; staged as build-deviation-2).
- **Integration branch = policy `integration-branch`, else `main`, `--branch` overrides** (ruling 6).
- **`BREAKING-CHANGE:` is a synonym of `BREAKING CHANGE:`**, as the Conventional Commits spec declares (ruling 7).
- **`manifest.js` skips only path absence**; a bad ref propagates (ruling 8).
- **Plan claims stay in precheck, through `deps.listPlanFiles`** — `docs/superpowers/plans/*.md` when present, exactly as `release.js` provides it (ruling 10).
- **Partial states name exactly what landed**: writes are tracked at the call site, and a hook that throws after the tag (and push) is exit 5, never "not pushed" (ruling 11).
- **`precheck.js` keeps `'tsv'` as the default** so `plugin/bin/release.js`'s two-argument call is byte-for-byte the pre-change path; `run.js` exports its guard and ancestry-checked push and calls them itself.
