# 2252: Reconcile under squash

Surface: infra

## Overview

Once unit 1 switches the pr-first merge from `--merge` to `--squash`, `reconcile`'s remote branch-pruning proof breaks silently: `bin/lib/reconcile/prune-remote.js`'s `decideRemotePrune` relies on `isCherryEquivalent` (patch-id comparison) to prove a branch's commits are already on the integration branch before deleting the remote ref, and a squash commit has a different patch id than the branch commits it came from — so every squash-merged branch would be skipped as `not-cherry-equivalent` forever, and remote branches would silently stop being pruned. This unit adds a second, squash-aware proof so reconcile keeps working under the new merge strategy.

**Complexity:** Low
**Estimated tasks:** 5

## Non-Goals

- Changing the merge-commit (`--no-ff`) pruning path — `isCherryEquivalent` remains the proof there, unchanged.
- Anything about the local-merge engine or subject composition — this unit only touches reconcile's pruning/archival proof logic, gated on unit 1's squash change already having landed.

## Current State

- `plugin/bin/lib/reconcile/prune-remote.js`: `decideRemotePrune` (around line 61) currently gates deletion on `isCherryEquivalent`; line 68 emits `not-cherry-equivalent` and skips the branch whenever that check fails — the sole failure reason today.
- `plugin/bin/lib/reconcile/archive-branches.js`: shares the same `isCherryEquivalent` helper for its own archival decision.
- `docs/reconcile-checks.md`: documents today's single proof (cherry-equivalence) as the only signal these two checks use.
- `tests/bin-lib/reconcile/prune-remote.test.js` and `tests/bin-lib/reconcile/archive-branches.test.js`: today's fixtures cover only merge-commit (`--no-ff`) branches.

- [ ] `not-cherry-equivalent` is renamed `not-proven-merged` and is emitted only when **neither** proof holds (cherry-equivalence for merge-commit history, nor the new squash-provenance proof for squash history) — a branch proven by either path is eligible for pruning.
- [ ] `plugin/bin/lib/reconcile/archive-branches.js`: same shared helper and dual-proof logic applied to `isCherryEquivalent`'s archival call site — calling the identical `squash-provenance.js` helper `prune-remote.js` uses, not a second implementation, for parity with the pruning check.

## Acceptance Criteria

1. Fixture: a branch squash-merged via PR #N (its PR state `MERGED`, integration-branch tip carries a commit subject ending `(#N)`) is pruned by `decideRemotePrune`.
2. Fixture: the same branch shape but with no merged PR and no matching subject is skipped, and the emitted reason is exactly `not-proven-merged` (not the retired `not-cherry-equivalent` name).
3. Every existing merge-commit (`--no-ff`, cherry-equivalent) fixture in both test files continues to pass unchanged — this unit adds a second proof path, it does not remove or weaken the first.
4. `archive-branches.js`'s archival decision reaches the same pruned/skipped outcome as `prune-remote.js` on the identical squash-merged fixture, because both call the same `squash-provenance.js` helper — not merely coincidentally-matching independent logic.
5. A branch whose PR is `MERGED` but whose matching `(#N)`-suffixed commit is no longer reachable on the integration branch tip (a rewritten/force-pushed history fixture) is skipped with `not-proven-merged`, never pruned — the dual proof fails safe rather than trusting PR state alone.
6. The vocabulary sweep's grep for `not-cherry-equivalent` returns zero unaddressed consumers outside historical references (archived records, the incident log) — every live doc, test, and prior pinned-vocabulary assertion is updated in the same change.

## Technical Approach

The subject-suffix match is deliberately narrow — it looks for the literal `(#{N})` suffix unit 1's composer always appends, not a fuzzy title match — so a squash commit that happens to reuse similar wording from an unrelated PR can't false-positive the proof. Combining "PR state is MERGED" with "the tip carries this PR's own subject suffix" gives two independent signals that must both hold, which is deliberately stronger than either alone: PR state alone could be stale relative to a force-pushed integration branch, and a subject-suffix match alone (without confirming PR state) could match a coincidentally-similar squash commit from a different, still-open PR.

## Gotchas

- This unit is `Blocked by` unit 1 (the merge-time subject/squash change) — there is no squash-merge subject suffix to match against until that unit's `composeSubject` lands and pr-first merges actually start squashing. `squash-provenance.js` imports its suffix-matching pattern from unit 1's `bin/lib/release/subject.js` rather than re-deriving it, so the two modules cannot silently drift apart.
- **Related:** #1732, #1811, #1892 — other open records touching `docs/reconcile-checks.md`; re-read that file's current state before editing, since a concurrent record may have already changed section numbering or nearby prose.
- **Vocabulary-pin exception:** record #1082 pinned the per-branch `reason` vocabulary as fixed ("no new per-branch reasons"). This unit's `not-cherry-equivalent` → `not-proven-merged` rename is a deliberate, documented exception to that pin — run the vocabulary sweep (Deliverables, above) first, and update #1082's own pinned-list test if it still runs, rather than letting this unit's change silently fail that test or silently drift past it unnoticed.
- `resolvePrStatesBulk`'s `MERGED` state is a GitHub-reported fact, not a local git computation — the subject-suffix scan is what proves *which* commit corresponds to that merge, since squash strips per-commit branch identity. The scan is bounded to commits since the branch's own fork point, never a full unbounded history walk, and a force-pushed/rewritten integration-branch tip that no longer carries the matching commit fails safe to `not-proven-merged` (skipped, not pruned) rather than trusting PR state alone.
