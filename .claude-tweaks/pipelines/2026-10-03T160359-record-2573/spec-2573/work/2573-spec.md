# 2573: upstream-drift checkOneFixture cannot assert plain-text stderr, only JSON

Surface: infra

## Current State
`checkOneFixture` in `tools/upstream-drift/checks.js` (lines 330-380) replays a manifest fixture command and asserts its observed output against `expect`. The function hard-requires the named stream (`expect.stream`, `stdout` or `stderr`) to parse as JSON — `tryParseJson(streams[wanted].trim())` — and returns a mismatch if it doesn't, including a special case that names when the JSON payload landed on the other stream instead. This makes it impossible to write a fixture for a command whose failure output is plain text rather than JSON. This was discovered while auditing #2480 (Impeccable CLI Rust-engine shim): the engine-locate/download failure path writes a plain-text message to stderr and exits 127, but there is no way to assert that exact behavior as a fixture today — only a JSON-shaped stderr/stdout payload is expressible.

## Deliverables
1. Extend `checkOneFixture` to support a plain-text/substring assertion mode on a named stream, as an alternative to the existing JSON-parse assertion — expressible via a new `expect` field (e.g. `expect.contains` or `expect.textMatch`) that, when present, asserts a substring match on `streams[expect.stream]` instead of requiring JSON parse.
2. Update the manifest schema/validation (`tools/upstream-drift/manifest.js`) to accept the new field alongside the existing `exit`/`stream`/`keys` fields, validating that a fixture specifies either the JSON-mode fields or the new text-mode field, not an ambiguous mix.
3. Add a fixture to `tools/upstream-drift/manifest.yml` (or a test-only manifest) exercising the plain-text stderr case from #2480 (or an equivalent), to prove the new mode round-trips a real plain-text failure.

## Acceptance Criteria
1. A fixture whose `expect` includes the new text-mode field and a substring that appears in the named stream's actual output passes `checkOneFixture`.
2. A fixture whose `expect` includes the new text-mode field and a substring that does NOT appear in the named stream's actual output returns a `mismatch` result with a detail naming the expected substring and which stream was checked.
3. Existing JSON-mode fixtures (using `expect.keys`) are unaffected — `checkOneFixture`'s existing JSON-parse path and its stdout/stderr swap detection continue to work exactly as before for fixtures that don't use the new field.
4. The manifest validation in `manifest.js` accepts fixtures using the new text-mode field without requiring the JSON-mode `keys` field, and still validates `exit`/`stream` are present as it does today.
5. A fixture reproducing the #2480 plain-text-stderr/exit-127 case round-trips correctly (passes when the actual behavior matches, fails with an informative detail when it regresses).

## Release Note

Added a plain-text assertion mode to upstream-drift fixtures, so a command that fails with plain-text output can be checked like one that emits JSON.

## Technical Approach
Add a new optional `expect` field for text/substring assertion, checked in `checkOneFixture` before or alongside the existing JSON-parse branch: if the text-mode field is present, skip the JSON-parse requirement entirely and instead check `streams[wanted].includes(expectedSubstring)`, returning a `mismatch` with a clear detail (naming the expected substring and observed stream) on failure. Keep the existing JSON-parse path unchanged for fixtures that don't opt into the new field — the two modes should be mutually exclusive per fixture, decided by which `expect` fields are present. Update `manifest.js`'s fixture validation to allow this new field and to require that a fixture uses exactly one assertion mode (JSON-mode via `keys`, or text-mode via the new field) rather than allowing both or neither silently.

### Key Files
- `tools/upstream-drift/checks.js` — `checkOneFixture` (lines 330-380): add the text/substring assertion branch, keep the JSON-parse path unchanged for non-opted-in fixtures
- `tools/upstream-drift/manifest.js` — fixture schema validation: accept the new `expect` field, enforce mutually-exclusive assertion mode
- `tools/upstream-drift/manifest.yml` — add or extend a fixture exercising the plain-text-stderr case from #2480
- `tools/upstream-drift/tests/manifest.test.js` — add test coverage for the new field's validation
- `tools/upstream-drift/tests/checks.test.js` (if it exists; otherwise the relevant checks test file) — add test coverage for the new text-mode assertion branch in `checkOneFixture`

## Gotchas
The two assertion modes (JSON-parse vs. text/substring) must stay mutually exclusive per fixture — allowing both to be specified together would create ambiguous validation semantics. The existing stdout/stderr-swap detection in the JSON-parse path is a load-bearing anti-regression check (comment at checks.js:361-366 calls it "the single most important case this function exists to catch"); the new text-mode path does not need to replicate that specific swap-detection logic unless a plain-text payload swap becomes a realized failure mode worth catching, but should not regress the existing JSON-mode swap detection.
