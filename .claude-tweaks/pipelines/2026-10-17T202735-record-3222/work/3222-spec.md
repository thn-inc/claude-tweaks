# 3222: engine-verify.js: acceptance-labeling false-fails a sub-issue whose parent gate isn't due yet

Surface: backend

## Current State

`wrap-up-engine.js verify`'s `acceptance-labeling` check (`plugin/bin/lib/wrap-up/engine-verify.js`, registered at ~L679 as of 2026-10-17; the original report's ~L511-547 has since moved) fails a sub-issue that was wrapped up correctly whenever its parent's acceptance gate is not yet due.

For each resolved issue the check calls `resolveParent()`. When a parent exists it takes `target = parent`, then requires `demo:pending` on that target unconditionally (~L743: `failing.push(\`#${target}: missing demo:pending label\`)`). It never enumerates the parent's sub-issues and never calls `parentGateState({ subIssues, parentLabels })` (`plugin/bin/lib/issues/acceptance.js:100`). The Parent-Gate Procedure (`plugin/skills/wrap-up/verification-brief-parent-gate.md`, "Evaluate the gate") documents the `incomplete` state as a deliberate no-op: siblings are still open, so no label lands on the sub-issue or the parent.

Observed (reported against 6.129.0, re-confirmed in the current source): with parent #P holding eight sub-issues, one closed and seven open (including the run's own #S), `verify` renders `| acceptance-labeling | fail | #P: missing demo:pending label |` and exits 3. `plugin/skills/wrap-up/execution-and-verification.md` treats that as BLOCKED, so no closure line is written. This hits every wrap-up of a sub-issue that isn't the last open one.

The parent path also skips the oversight-floor check. Its non-parent counterpart is `oversightExemptSet` (~L146), which already exempts below-floor records from `demo:pending`.

## Deliverables

1. In the `acceptance-labeling` check, after a parent target resolves, enumerate the parent's sub-issues and compute `parentGateState({ subIssues, parentLabels })`. Treat the run's own resolved records as CLOSED (self-inclusion: they are being closed by this wrap-up).
2. Require `demo:pending` plus a Verification Brief on the parent only when the computed state is one where the Parent-Gate Procedure would have labeled it (`due`/`gated`/`resolved`) **and** the parent-path oversight floor is exceeded (`maxRiskTier` + `exceedsOversightFloor(..., { sizeFloor: null })`). Otherwise return `skip` with the reason (e.g. `parent gate #P not due — 6 sibling sub-issue(s) open`, or `parent #P below oversight floor`).
3. A sub-issue enumeration failure renders the check `unknown` (a gather failure), never `fail`, matching the file's existing could-not-gather convention.
4. In `execution-and-verification.md`, state that `verify --run-dir` must be passed the original (pre-archive) run-dir path. Passing the archive path after Section B archived the run makes `run-dir-archived` report `original path still present`.

## Acceptance Criteria

- A unit test drives the check with a resolvable parent whose sub-issues include open siblings (gate `incomplete`) and asserts `result: 'skip'` with a detail naming the parent and the open-sibling count. It must not return `fail`.
- A unit test with every sibling closed (gate `due`) and the parent above the oversight floor but missing `demo:pending` still asserts `fail` (`#P: missing demo:pending label`), so the check keeps catching a genuinely ungated parent.
- A unit test with a due gate but a parent below the oversight floor asserts `skip`.
- A unit test where sub-issue enumeration throws asserts `result: 'unknown'`.
- `execution-and-verification.md` carries the pre-archive `--run-dir` note.
- `npm test` passes in full.

## Release Note

Wrap-up verification no longer blocks closing a sub-issue just because its parent's acceptance gate isn't due yet.

## Technical Approach

Reuse the existing primitives rather than re-deriving gate logic: `parentGateState` from `acceptance.js`, and the parent-path oversight-floor helpers the Parent-Gate Procedure already uses. Fetch sub-issues through the same `deps.gh` seam `resolveParent` uses, so the check stays testable with the injected runner. Keep the existing non-parent path and the `oversightExemptSet` narrowing unchanged. The new logic only applies once `resolved.parent` is non-null, and it runs before the `demo:pending` label read.

### Key Files

- `plugin/bin/lib/wrap-up/engine-verify.js` — `acceptance-labeling` check: compute the parent gate state and floor before requiring `demo:pending`
- `plugin/bin/lib/issues/acceptance.js` — `parentGateState` (consumed, not changed)
- `plugin/skills/wrap-up/execution-and-verification.md` — pre-archive `--run-dir` note
- `plugin/skills/wrap-up/verification-brief-parent-gate.md` — source of truth for the gate states and the floor rule (read, not changed)
- `tests/bin-lib/wrap-up/engine-verify.test.js` — new parent-gate cases beside the existing `acceptance-labeling` tests

## Gotchas

- Self-inclusion matters. At verify time the run's own sub-issue may still be OPEN on GitHub (closure happens via the merge or a later step), so counting it as open would make the gate permanently `incomplete` for the last sibling and hide a genuinely due gate.
- Several sub-issues in one run can share one parent. The existing dedupe-by-target loop must still check that parent once, with every run-resolved sibling treated as closed.
- Line numbers in the original report (~L511-547) are stale. Locate the check by its `registerCheck('acceptance-labeling', …)` call.

## Original request

engine-verify.js: acceptance-labeling false-fails a sub-issue whose parent gate isn't due yet

**Summary:** `wrap-up-engine.js verify`'s acceptance-labeling check fails a sub-issue that was wrapped up correctly when its parent gate isn't due yet. That blocks the closure line.

**Kind:** Defect

**Affected component:** `bin/lib/wrap-up/engine-verify.js` (`acceptance-labeling` check), invoked by `/claude-tweaks:wrap-up` Phase 4 "Verify execution"

**Repro steps:**
1. In a `work-backend: github-issues`, `work-links: native` project, take a parent record #P with eight sub-issues. One is closed and the other seven are open, including the one being run (#S).
2. Run `/claude-tweaks:flow #S` through to wrap-up (in a private project, pr-first, PR merged).
3. At Phase 4's acceptance-labeling step, `verification-brief.md` routes #S to the Parent-Gate Procedure. `parentGateState` evaluates `incomplete` because siblings are still open. Per `verification-brief-parent-gate.md` "Evaluate the gate", no label is applied to #S or #P. This is correct.
4. Run `node bin/wrap-up-engine.js verify --run-dir <project-root>/.claude-tweaks/pipelines/<run-id> --base <base-sha>`.

**Expected vs. actual:**
Expected: `acceptance-labeling` renders `skip` (or `pass`) with a detail like "parent gate #P not due — 6 sibling sub-issue(s) open", since `incomplete` is a documented no-op.
Actual: `| acceptance-labeling | fail | #P: missing demo:pending label |`, exit 3. `execution-and-verification.md` treats that as BLOCKED, so no closure line is written. This hits every wrap-up of a sub-issue that isn't the last one.

**Cause:** `engine-verify.js` ~L511-547 resolves `target = parent` via `resolveParent()` and then requires `demo:pending` on the target unconditionally. It never enumerates the parent's sub-issues and never calls `parentGateState({ subIssues, parentLabels })` (`bin/lib/issues/acceptance.js`). It also skips the parent-path oversight-floor check (`maxRiskTier` + `exceedsOversightFloor(..., { sizeFloor: null })`), which is the parent-path counterpart of the `oversightExemptSet` exemption.

**Suggested fix:** after resolving a parent target, enumerate its sub-issues and compute `parentGateState`. For self-inclusion, treat the run's own resolved records as CLOSED. Require `demo:pending` plus a brief only when the state is `due`/`gated`/`resolved` and the risk floor is exceeded. Otherwise return `skip` with the reason.

**Secondary (minor):** if Section B has already archived the run and `--run-dir` is given the archive path, `run-dir-archived` reports `original path still present: <path>`. The check has to be passed the original (pre-archive) path, and `execution-and-verification.md` could say so explicitly.
