# 5368: A CI-answered verify run waits minutes in the full slot lane to run a one-second suite

Surface: infra

**Related:** #5319, #5169, #5168, #5257, #5189, #5753, #5653, #5075, #5378, #5465, #5466, #5498, #5511, #5210, #5333, #5427, #5859
Risk-flags: none

## Current State

`verify.js` picks the checks' slot lane with `chooseLane` (`plugin/bin/lib/verify/slot.js:45`). The caller (`plugin/bin/verify.js:1055`) sets `fullSuiteRuns` when any local command other than `types`/`lint`, the impact subset or the tool-scoped command runs. So any declared suite running its own full command sends the whole run to the full lane, whatever that suite's size. `plugin/skills/test/suite-slots.md`'s Lanes table states the same rule ("any local suite runs its full command: a `--cmd`, or a declared suite command").

In this repo, `journeys` is a declared suite (`.claude-tweaks/verify-scope.json`, `checks.tests.journeys`, eleven test files) that runs in about one second. Almost every pipeline writes a `docs/journeys/` file, so almost every scoped run selects it. When the `tests` suite is answered by CI (the `ci` block, `localRuns: "on-request"`), `journeys` is the only local suite, and the run still queues in the full lane behind whole-suite runs from every project on the machine.

Measured (2026-11-13, each worktree's last `report.json`): three CI-answered runs waited 447, 545 and 954 s for a full-lane slot, then ran `journeys` in 0.8 to 2 s. A run with a 591-file impact subset plus `journeys` was classed `full`, not `subset`. Across 91 `verify` events from 9 to 13 November, slot waits were 16.5 of 23.6 hours of verify time. Later occurrences (record comments) show a 784 s wait for a 0.9 s run, and a dispatched subagent hitting its 60-wait bound and stopping `BLOCKED` twice.

`plugin/bin/lib/verify/declaration.js` keeps the `concurrency` block strict (an unknown key there is an error for older readers), but it has no check on unknown top-level keys: its `ci` comment says "A reader that predates the key ignores it". A new top-level key can therefore be committed to this repo's declaration in the same change without breaking a run on an older installed build.

## Deliverables

- [ ] New optional top-level declaration key `subsetLaneSuites`: an array of declared suite names. `readDeclaration` validates it (an array of strings, each a declared suite, no duplicates, and never the `impact.suite`, since that suite's full command is the whole-suite run the full lane exists for), returns it on the parsed declaration (`[]` when absent), and reports each violation as a declaration error in the existing style.
- [ ] `verify.js`'s lane computation: a declared suite listed in `subsetLaneSuites` that runs its own declared command does not count toward `fullSuiteRuns`. A `--cmd` suite always counts, even under a listed name, because its command is the caller's, not the declaration's. Nothing else about lane choice changes.
- [ ] `plugin/skills/test/suite-slots.md`'s Lanes table: the full row excludes suites listed in `subsetLaneSuites`, and the subset row includes them, with one line saying what the key is for (a small declared suite that should not queue behind whole-suite runs). `report.json`'s `slot.lane` already reports the chosen lane, and the doc says so.
- [ ] This repo's `.claude-tweaks/verify-scope.json` gains `"subsetLaneSuites": ["journeys"]`.
- [ ] Tests: `tests/bin-lib/verify/declaration.test.js` covers the validation cases; `tests/bin-lib/verify/cli-slot.test.js` covers a CI-answered run plus a listed small suite (lane `subset`), an impact subset plus a listed small suite (lane `subset`), and an unlisted declared suite (lane `full`, unchanged).

## Acceptance Criteria

1. With `subsetLaneSuites: ["journeys"]`, `tests` answered by CI and `journeys` running locally, `report.json` `slot.lane` is `subset`.
2. With `subsetLaneSuites: ["journeys"]`, `tests` running an impact subset and `journeys` its declared command, `slot.lane` is `subset`.
3. With `subsetLaneSuites` absent, or the local suite not listed, a declared suite's full command still takes `slot.lane` `full`.
4. `--cmd journeys=…` takes the full lane even when `journeys` is listed.
5. `readDeclaration` rejects `subsetLaneSuites` that is not an array of strings, names an undeclared suite, repeats a name, or names `impact.suite`, each with its own error naming the key.
6. A declaration without the key parses exactly as before (no new field values change for existing declarations except the `[]` default).

## Release Note

A declaration can list small test suites under `subsetLaneSuites`, so a verification whose only local suite is one of them no longer waits behind whole-suite runs for a full-lane slot.

## Technical Approach

The key lives at the top level, not in `concurrency`, because older readers reject unknown `concurrency` keys and ignore unknown top-level ones. So committing it to this repo's declaration is safe for runs in flight on the previous release (they keep today's lane). The lane rule stays "the commands that run decide the lane". The key only marks which declared commands the project vouches are small.

In `verify.js`, the `fullSuiteRuns` predicate gets one more exclusion: `c` is a declared suite (its command is the declaration's own command for that name, not a `--cmd` override) and `decl.subsetLaneSuites` includes `c.name`. Pass the parsed list into the same scope as `impactSubset` and `toolScopedCommand`.

## Gotchas

- **Decided (2026-11-25, autonomous lane): option 1, per-suite opt-in, as a top-level key.** The record's objection to option 1 (older readers reject unknown `concurrency` keys) does not apply at the top level, because `declaration.js` ignores unknown top-level keys. Option 2 (only the impact suite's full command takes the full lane) was rejected: it is implicit, and wrong for a project whose other declared suites are large, such as an e2e suite. Option 3 (a third lane) was rejected: one more slot pool on the machine for what one exclusion achieves.
- **Decided: not blocked by #5169.** Whether slots are keyed by machine or by shared resource does not change which lane a run takes, so the two records are independent.
- **Decided: `impact.suite` cannot be listed.** That suite's full command is exactly the whole-suite run the full lane serializes.
- Lane ct-verify-ci is editing `verify.js`'s CI-source code at the same time. This change touches only the `fullSuiteRuns` predicate near the checks' slot hold, so expect a catch-up merge, not a logic conflict.
- `cli-slot.test.js` cases drive real lock dirs: give each case its own `CT_TEST_SUITE_SLOT_DIR` so it never queues behind a real run on the machine.

## Current State

`plugin/skills/test/suite-slots.md` puts a `verify.js` run in the full lane when "any local suite runs its full command". The rule does not look at how large that suite is.

In this repo `journeys` is a declared suite of nine test files that runs in about one second (`.claude-tweaks/verify-scope.json`, `checks.tests.journeys`). Every pipeline writes a `docs/journeys/` file, so almost every scoped run selects it and therefore queues in the full lane, behind whole-suite runs.

Measured on 2026-11-13 from each worktree's last `report.json`:

- The three runs whose `tests` suite was answered by CI (worktrees `record-5230`, `record-5268`, `learned-skills-pr-5290`) ran no test of that suite on this machine. They still waited 447, 545 and 954 seconds for a full-lane slot, then ran `journeys` in 0.8 to 2 seconds.
- A run with a 591-file impact subset plus `journeys` (`record-5291`) was classed `full`, not `subset`.

Across the 91 `verify` events logged between 9 and 13 November, slot waits were 16.5 of 23.6 hours of total verify time.

This is wall time, not CPU: the slot is held for a second. It still delays every pipeline phase that verifies, and it makes a CI-answered run look as slow as a local one.

## Deliverables

- [ ] A rule for which lane a run takes that follows the size of what it will spawn, so a run whose only local suite is small does not queue behind whole-suite runs.
- [ ] `plugin/skills/test/suite-slots.md`'s Lanes table states the rule, and `report.json`'s `slot.lane` reports the lane chosen under it.
- [ ] Tests in `tests/bin-lib/verify/cli-slot.test.js` cover a CI-answered run plus a small declared suite, and an impact subset plus a small declared suite.

## Open Question

How does the runner know a declared suite is small? Three candidates, none chosen:

1. A per-suite opt-in in the declaration's `concurrency` block (for example a list of suites that always take the subset lane). Simple and explicit, but the project must keep the list right, and older readers reject unknown `concurrency` keys, so it needs a reader release before any project commits it.
2. Lane by the suite that declares `impact`: only that suite's full command (and any `--cmd` suite) takes the full lane, every other declared suite takes the subset lane. No new key, but wrong for a project whose other declared suites are large.
3. A third lane for suites that are neither the impact subset nor a whole suite. Keeps both existing lanes' meaning, at the cost of one more slot pool on the machine.

The answer also depends on #5169 (whether slots should be keyed by shared resource rather than by machine).
