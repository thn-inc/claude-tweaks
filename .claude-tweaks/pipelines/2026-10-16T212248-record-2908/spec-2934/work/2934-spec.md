# 2934: wrap-up engine-verify: carrier-commit fallback runs one gh issue view per issue instead of reading state from the batched query

Surface: infra

## Current State

`plugin/bin/lib/wrap-up/engine-verify.js`'s `registerCheck('carrier-commit', ...)` has a ground-truth fallback for issues with no textual carrier commit (`missingTextual`). It first calls `fetchLinkedPRs` once for every number in `missingTextual` (`engine-verify.js:392-394`). That is one batched, aliased GraphQL call built by `buildLinkedPRQuery` (`plugin/bin/lib/issues/record.js:729-735`). The loop that follows (`engine-verify.js:398-405`) then runs one `deps.gh(['issue', 'view', String(n), '--json', 'state'], cwd)` per issue that has a closing-PR reference, only to learn whether that issue is `CLOSED`.

The same per-issue alias in `buildLinkedPRQuery` already selects `number`, `closedByPullRequestsReferences` and `timelineItems`. Selecting `state` there too would let the fallback read the issue state from the batched result and drop the per-issue subprocess. `fetchLinkedPRs` (`plugin/bin/lib/issues/linked-prs.js:40-83`) builds each Map value as `{ openPR, mentions, hasClosingPRReference }` (`:81`), so the new field has to be passed through there as well.

The impact is small: zero to a few issues per wrap-up verify. This is a cleanup, not a defect. Found by the v6.134.0 release review (lens 3d, reproduced by both agents, refutation not-refuted; ledger row 2).

## Deliverables

1. `buildLinkedPRQuery`'s per-issue alias also selects the issue's own `state`. The field is additive, so existing consumers that ignore it are unaffected.
2. `fetchLinkedPRs` passes that value through on each Map entry, for example as `issueState`. The name must not collide with the existing PR-level `state` inside `mentions`.
3. The carrier-commit fallback in `engine-verify.js` reads the issue state from the batched `fetchLinkedPRs` result instead of calling `gh issue view` once per issue. When the batched field is missing, the issue is treated as still missing, which matches today's degrade-to-`stillMissing` posture.

## Acceptance Criteria

- With N issues in `missingTextual`, all of them carrying a closing-PR reference, the carrier-commit check makes exactly one `gh` call. A test in `tests/bin-lib/wrap-up/engine-verify.test.js` counts the injected `deps.gh` invocations and asserts this. Prove it goes red by restoring the per-issue `gh issue view` loop.
- A fallback issue whose batched state is `CLOSED` with a closing-PR reference passes, and one whose state is `OPEN` stays in `stillMissing`, matching current behavior.
- `tests/bin-lib/issues/linked-prs.test.js` asserts the new pass-through field.
- `tests/resolve-linked-prs-cli.test.js`, `tests/bin-lib/issues/shipped-candidate.test.js`, `tests/bin-lib/issues/record.test.js` and the dispatch eligibility tests pass unchanged.
- `npm test` passes in full.

## Release Note

Wrap-up's carrier-commit check now reads issue state from its existing batched query, with no extra GitHub call per issue.

## Technical Approach

Add `state` next to `number` in the alias string inside `buildLinkedPRQuery`. In `fetchLinkedPRs`, read `node.state` and set it on the result entry under a distinct name (`issueState`). In `engine-verify.js`, replace the `deps.gh(['issue', 'view', ...])` try/catch with `entry.issueState`. The existing `stillMissing` logic stays as it is.

### Key Files

- `plugin/bin/lib/issues/record.js` — `buildLinkedPRQuery`: select the issue's `state` in each alias
- `plugin/bin/lib/issues/linked-prs.js` — `fetchLinkedPRs`: pass the issue state through on each Map entry
- `plugin/bin/lib/wrap-up/engine-verify.js` — carrier-commit fallback: read the batched state and remove the per-issue `gh issue view`
- `tests/bin-lib/wrap-up/engine-verify.test.js` — runner-call-count test for the fallback
- `tests/bin-lib/issues/linked-prs.test.js` — pass-through field assertion

## Gotchas

- Fake GraphQL responses in existing tests (`linked-prs.test.js`, `resolve-linked-prs-cli.test.js`, `engine-verify.test.js`) will not carry `state` on the issue node. The engine-verify fallback must treat a missing `issueState` as not-closed, so those fixtures still pass and a malformed response never reads as `CLOSED`.
- `mentions[].state` is a PR's state, while the new field is the issue's state. Keep the names distinct so `shipped-candidate.js`'s `classifyShipped` never confuses them.
- `buildLinkedPRQuery` is also used by `/dispatch`'s open-linked-PR exclusion (`partitionByOpenLinkedPR`). An extra scalar field in the alias is harmless there, but check that no test pins the exact query string. At shaping time `git grep` found none outside `record.js` itself.
