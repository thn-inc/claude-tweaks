# 2259: This repo's migration to the new release process (first consumer)

Surface: infra

## Overview

This repo becomes the first consumer of everything units 1-8 built, and this unit is the acceptance test for the whole design: retro-tag this repo's entire release history from `docs/shipped-versions.tsv`, bootstrap release-please, move the marketplace-mirror step into a `release: published` workflow, retire `plugin/bin/release.js` and its supporting modules, and rewrite every doc that describes the old process. **Scope split:** Deliverables 1-5 (retro-tag, bootstrap, mirror workflow, retirement, docs) land in one PR, in the order below — each step depends on the prior step's artifacts existing. Deliverable 6 ("First release through the new path") is a **separate, post-merge action** taken after that PR merges, not part of the PR's own diff — it cuts an actual release using the now-merged tooling, which by definition cannot happen before the PR that installs that tooling has landed.

**Complexity:** High
**Estimated tasks:** 8

## Non-Goals

- Rewriting this repo's historical CHANGELOG entries into the new release-please grammar — the switch point is a deliberate one-time boundary; pre-boundary entries keep their existing heading form, and the tag-to-CHANGELOG consistency probe (unit 7's generalized version) only asserts headings at or after the bootstrap version.
- Building any of units 1-8's underlying capability — this unit only consumes and configures what they produce; if any of units 1-8 is incomplete, this unit cannot proceed (see Gotchas).

## Current State

- `docs/shipped-versions.tsv`: the historical record of every shipped version this repo has produced — the source this unit retro-tags from, then retires.
- `plugin/bin/lib/release/status.js`'s `iterBumpCommits`: today's mechanism for walking bump commits; explicitly named in the design doc as "the last legitimate use" of that walk — after this unit, nothing in the shipped codebase performs a bump-commit walk again.
- `plugin/bin/release.js` + `plugin/bin/lib/release/{compose,mirror,precheck,run,status,unnamed-records}.js`: this repo's current maintainer-only release tooling. Everything except `precheck.js` and `run.js` is retired by this unit; `precheck.js` gains a `keySource: 'tags' | 'tsv'` parameter in unit 4 and stays shared between `release-local.js` (`'tags'`) and this repo's own tooling until this unit retires the `'tsv'`-calling side, and `run.js` is reused unchanged by unit 4 — neither is deleted here.
- `plugin/bin/lib/shipped-record.js`: bookkeeping helper retired alongside the above.
- `tests/bin-lib/release/`: the test suite for the retired modules, deleted **except** `subject.test.js` (unit 1's own test, which lives in `bin/lib/release/subject.js` and stays — that module is not retired).
- `tests/changelog-coverage.test.js`: today's tag-to-CHANGELOG coverage test for this repo specifically, replaced by unit 7's generalized probe's own test.
- `.github/workflows/`: no `release-please.yml` or `mirror-marketplace.yml` exist yet.
- `CHANGELOG.md`: entirely in this repo's current `## v{version} — {summary}` heading grammar, no boundary marker yet.
- `docs/releasing.md`, `CLAUDE.md` (Versioning/Releasing/commit-style sections), `docs/plugin-structure.md`: all describe the current `release.js`-based process.

## Deliverables

- [ ] **Retro-tag history.** For every line of `docs/shipped-versions.tsv`, resolve the corresponding bump commit via `status.js`'s `iterBumpCommits`, matched **by version string**. Before tagging anything, print the full resolved `version → sha → date` triple list for every tsv line and confirm every line resolved to exactly one commit — a tsv line that resolves to zero or more than one commit **aborts the whole retro-tag step with no tags created or pushed**. Once every line resolves cleanly: create an annotated tag `v{version}` dated to that commit, message `v{version} — {summary}`. Push all tags to origin.
- [ ] **Bootstrap release-please** via unit 3's init bootstrap step, run against the tip of this migration branch immediately after retro-tagging's tags are pushed: `release-type: simple`, `extra-files: [{type: json, path: plugin/.claude-plugin/plugin.json, jsonpath: $.version}]`, manifest seeded to the current shipped version, `last-release-sha` pinned to the newest retro-tag's own commit. `CHANGELOG.md` gains a one-line boundary comment immediately above the first release-please-generated entry.
- [ ] **Marketplace mirror as a workflow.** New `.github/workflows/mirror-marketplace.yml`, triggered on `release: published`: PUTs the catalog entry `{source: git-subdir, url, path: plugin, sha: {release commit}}` into `thomasholknielsen/claude-tweaks-marketplace`.
- [ ] **Retire**: `plugin/bin/release.js`; `plugin/bin/lib/release/compose.js`, `mirror.js`, `run.js`, `status.js`, `unnamed-records.js` (`precheck.js` is NOT deleted); `plugin/bin/lib/shipped-record.js`; `docs/shipped-versions.tsv`; `tests/bin-lib/release/` except `subject.test.js`; `tests/changelog-coverage.test.js`; the literal string `kind: release` wherever it appears in prose.
- [ ] **Docs.** `docs/releasing.md` rewritten around `/claude-tweaks:release`. `CLAUDE.md`'s Versioning bullet becomes the new one. New `docs/decisions/0018-release-please-engine.md`.
- [ ] **First release through the new path** (post-merge, not part of the PR above).

## Acceptance Criteria

1. The number of new `v*` tags equals `docs/shipped-versions.tsv`'s line count exactly.
2. `npm test` is green with the retired suites gone and unit 7's generalized-probe test present and passing.
3. The release that ships this family of changes has an annotated `v*` tag, a GitHub Release, a release-please-generated CHANGELOG entry, and a mirrored marketplace catalog entry.
4. `CHANGELOG.md` contains exactly one boundary comment.
5. `docs/plugin-structure.md`'s CLI list no longer references `plugin/bin/release.js`.
6. A grep for retired module names returns zero matches outside the ADR and incident log.
7. The PR description lists `MARKETPLACE_TOKEN` as a merge precondition.
8. Retro-tagging's own pre-flight check aborts with zero tags created on ambiguity.
