# 4960: dispatch: a merged group's worktree can be deleted while the dispatching session is still in it, stranding the session

**Related:** #4895, #4959

## Current State

`plugin/skills/dispatch/SKILL.md` Step 5 says that under `pr-first` the reconciler reaps a merged group's worktree only "once no live session holds it (`reap-merged.js` skips own-cwd and locked worktrees)". `isOwnCwd` compares the worktree against the cwd of the process running reconcile, and `isWorktreeLocked` reads git's worktree lock. Neither check sees a dispatching session in another process that holds no lock.

Observed in the 2026-10-31 firing, on plugin 6.156.1, for #4551 (PR #4724) and #4548 (PR #4730): the worktree was gone right after the merge while the dispatching session was still in it. Bash reported `Working directory ... was deleted; shell cwd recovered`, and `gh` then failed with `not a git repository`. `EnterWorktree` failed outside a git repo, and a `cd` into the next worktree left the harness refusing commands because the session was still isolated in the deleted one. The session recovered with `ExitWorktree(action: "keep")` followed by `EnterWorktree(path)`.

What removed the worktree is not established: the retained run events show only `worktree-reap-skipped` entries (`pr-open`) and no reap entry. The refusal text comes from the harness; the plugin only classifies it (`plugin/bin/lib/hooks/harness-refusal.js`). `plugin/skills/dispatch/sequential-execution.md` has no recovery step for this state.

## Deliverables

- Identify what removes the worktree, using a reproduction or added logging, and record the answer on this record.
- Make the removal path honour a live dispatching session that is in the worktree, so `SKILL.md`'s statement is true.
- Add the recovery sequence (`ExitWorktree(action: "keep")`, then `EnterWorktree(path)`) to `sequential-execution.md`, for a worktree that disappears anyway.

## Acceptance Criteria

- [ ] The removal path is named on this record, with the evidence.
- [ ] A test shows the named path skipping a worktree held by a live session running in another process, and is shown red without the fix.
- [ ] A removal of a worktree in a merged run leaves a reap entry in that run's events.
- [ ] `sequential-execution.md` states the recovery sequence and warns against a plain `cd`.

## Release Note

A dispatch run across several records no longer loses its working directory when one record's PR merges.

## Technical Approach

### Key Files

- `plugin/bin/lib/reconcile/reap-merged.js` — honour a live session held outside the calling process
- `plugin/bin/lib/hooks/worktree-reap.js` — share the held-by-a-live-session check
- `plugin/skills/dispatch/sequential-execution.md` — add the recovery sequence
- `plugin/skills/dispatch/SKILL.md` — keep the Step 5 reap statement accurate
