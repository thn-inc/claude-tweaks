# 4613: Rewrite /demo as /claude-tweaks:accept

Surface: infra

## Overview

Rename and rewrite `/claude-tweaks:demo` as `/claude-tweaks:accept`, the acceptance step. It is **the same flow from two entries**:

- **Automatic, at pipeline end:** produce the acceptance packet (or reuse the one wrap-up already posted), post it, mark the record `accept:pending`.
- **On demand, `/claude-tweaks:accept #N`:** walk the human through the same packet: open the links, show the recording, step through the test guide, then ask the verdict.

**Re-running on an item that already has a packet reuses it and refreshes only what is stale** (deploy status, links to an older deploy). It never builds a second packet. The same verdict comes from either surface (terminal or Dispatch) and has the same effect; the verdict handler itself is a separate record.

Keep from today's `/demo`: the verdict labels (renamed to `accept:*` by the expand record), follow-up record mechanics (a separate record reworks them), the Verification Brief / Try-it block as packet input, the Prepare / Validate / Show observation plan, and the **no-record path** for this session's unrecorded work. Drop: the standalone-only restriction, and the terminal question as the only way to give a verdict.

`/demo` stays as a **deprecated alias** with one warn-tier deprecation notice per invocation and a **recorded removal condition** (the repo's deprecated-alias convention, see `plugin/skills/specify/deprecated-aliases.md` and `plugin/skills/dispatch/deprecated-aliases.md`). The removal condition recorded here is exactly this text, quoted by the notice and by `plugin/skills/demo/deprecated-aliases.md`, and is what the final contract-cleanup record waits on: **`/demo` may be removed when all three hold, checked at each minor release: (a) `grep -rFn "claude-tweaks:demo" plugin docs README.md` finds no match outside the alias stub, the alias doc, `docs/incident-log.md`, `docs/decisions/` and `docs/plans/`; (b) at least two minor releases (versions of `plugin/.claude-plugin/plugin.json`) have shipped after the release containing this change; (c) the maintainer has confirmed Dispatch emits `accept:*` labels.** The alias doc lives in `plugin/skills/demo/` (the aliased skill's own directory, as `specify/` and `dispatch/` do for theirs).

**Contract decisions this record pins:**

- **Single owner of the packet.** The packet module (the packet record) owns creating and refreshing it; `/accept` never builds one by itself. The automatic entry is the lazy-loaded sub-file `plugin/skills/accept/automatic-entry.md`, which the five call sites in `wrap-up/verification-brief.md`'s Routing table reach; it calls the packet module (which finds the packet by marker and creates it only if absent), then applies `accept:pending` only when the record carries no verdict label of either vocabulary (read through the label-expand record's precedence function). **The automatic entry never prompts, never blocks and returns after labelling**, so auto mode's no-new-mid-flow-stop rule holds; every interactive step (walking the guide, asking the verdict) belongs to the on-demand entry only. The standalone-only restriction `/demo` had protected nothing the packet-centric flow needs once the automatic entry is non-interactive; drop it.
- **Staleness.** The refreshable fields are a closed list: the Deploy-status section, the base URL of Test-guide links, and the Recording link. Staleness test: compare the `deploy.ref` fact stored in the packet with the current ref from the deploy-status source when that source exists; when it does not, or is unavailable, leave the field as is and mark it `unverified`. Nothing else is ever rewritten by `/accept`; a human-edited packet keeps the human's edits outside those three fields. A missing, duplicated or deleted marker comment follows the packet reader rules (the packet record): missing means build, duplicate means the earliest trusted wins, never a second packet.
- **Packet states `/accept` handles** (each with minimal behavior): awaiting local acceptance (start the app from the PR branch, then walk); waiting for deploy (show the deploy status, skip the link step, say so plainly); live on dev (walk the guide with dev links); no recording (say so, walk the rest); already accepted or closed (show the recorded verdict and stop; no second verdict); no packet and a resolvable record (build via the packet module, then walk). An unhandled state prints a one-line message naming the state and stops; it does not guess.
- **Labels written.** During the expand window `/accept` writes `accept:*` and removes the `demo:*` twin when present; `/accept #N` on a record carrying only `demo:pending` reads it as pending, and on a verdict removes it and writes the `accept:*` verdict. `/demo` (the alias) forwards, so it too writes `accept:*`.
- **Verdict handling until the verdict-handler record lands.** The interim is `/demo`'s existing verdict mechanics under the `accept:*` labels, confined to one sub-file `plugin/skills/accept/verdict-interim.md` that the verdict-handler record (#4614, which follows this record) replaces wholesale and deletes; Dispatch-given verdicts are not handled until then, and the skill says so. The parent-close behavior of `/demo`'s Approve step (close a parent once its sub-issues are accepted, keyed on `isParentIssue`) carries over unchanged into `/accept`'s Approve step until the feature-level-acceptance record changes it.
- **No-record path selection.** It is taken only for `/claude-tweaks:accept` with no `#N` argument and unrecorded work in this session. A `#N` that does not resolve is an error and never falls back to the no-record path.
- **Sub-files.** `entry-paths.md`, `browser-verdict.md`, `design-contract-section.md` and `follow-up-record.md` move to `plugin/skills/accept/` (git mv; no pointer stubs left in `demo/`); `legacy-brief-compatibility.md` stays in `plugin/skills/demo/` (readers of legacy briefs) until the final cleanup record. After the moves, sweep every path citation, including tests and the `files:` frontmatter of journey docs.

## Release Note

Added `/claude-tweaks:accept`, an acceptance step that walks you through a finished feature's packet and takes your verdict, and kept `/claude-tweaks:demo` as a deprecated alias.

## Technical Approach

Treat this as a rename plus a rewrite behind a stable alias, expand-contract style: add `accept`, make `demo` forward, migrate callers, and leave removal to the contract record. The skill's flow is packet-centric: find the packet by its marker comment; if absent, build it (the packet record's module); if present, refresh stale facts; then step the human through it and ask for the verdict. Both entries converge on one code path so behavior cannot diverge by surface. `local-files` backend: the packet and interactive verdict work through the existing `acceptance:` field; Dispatch-given verdicts and revert-now are GitHub-only and say so when unavailable.

### Data / API Surface

- Invocation: `/claude-tweaks:accept [#N]`; automatic entry is called from wrap-up/flow, not typed.
- Reads: the packet marker comment (GitHub) or the record's packet section (`local-files`).
- Writes: the pending acceptance label; verdicts through the verdict handler.
