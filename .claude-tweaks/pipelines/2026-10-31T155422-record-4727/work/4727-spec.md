# 4727: specify: require a Closed rule for specs whose deliverable classifies states

Verified-as-of: f9dfd856f61b51abc268bd06e61113de6a29245c

Origin: reflect full from #4588

Defer-reason: tangential

## Current State

Record #4588 (dispatch resume) specified an eligibility verdict: a list of claim, label, worktree, PR and run-directory states that make a stalled build resumable. The spec listed the eligible states but said nothing about states it did not list.

Plan review (`plugin/skills/build/plan-review.md`, lines 53-54) classifies a gap as `needs-human` whenever settling it would alter an observable contract or has two defensible readings. Every unlisted state qualified, so each review pass found new ones and stopped the build on the `plan-review-needs-human` HARD-GATE. Run `2026-10-30T200217-spec-4588` logged four such stops (`decisions.md` KEPT-PROMPT 21:17:29, 22:15:34, 07:25:48, 10:49:23), with 3, 2, 4 and 2 needs-human gaps. Each stop meant a question set on the record, a human answer, a spec re-materialization, a plan amendment and a fresh review.

The fourth answer set added a **Closed rule** to the spec: the eligible states are exhaustive, any unlisted state is refused with one line naming the state and the remedy, and a plan review that finds another unlisted state applies the rule as a plan amendment, never as a `needs-human` gap. The fifth review pass applied it to a new state finding and the build proceeded with no further stop (`decisions.md` AUTO 11:12:40).

Probe: `git grep -n -i -e 'exhaustive' -e 'closed rule' origin/main -- plugin/skills/specify plugin/skills/build/plan-review.md` matched only two unrelated lines (`specify/mechanical-handoff.md:16`, `specify/red-team.md:81`). Neither /specify's spec template nor plan review names a closed rule for a state-classification deliverable.

## Deliverables

1. In `/claude-tweaks:specify`, when a spec's deliverable classifies inputs into named states (an eligibility verdict, a refusal ladder, a status classifier), require a Closed-rule bullet beside the state list. It says the listed states are exhaustive, that an unlisted state is refused with a line naming it and its remedy, and that plan review applies the rule as an amendment rather than escalating. Put the guidance in the spec template or in a sibling deliverable-guidance file, the way `gate-authoring-deliverables.md` and `empirical-premise-check-deliverables.md` already handle their deliverable types.

2. Add a conformance test that fails when that guidance is removed.

## Acceptance Criteria

- /specify's spec-shaping guidance names the Closed rule for state-classification deliverables, with its three parts: exhaustive, refused with a named remedy, and amendment rather than escalation in plan review.

- A conformance test fails when the guidance is deleted.

- `npm test` passes.

## Release Note

Specs for state-classifying features now state up front that unlisted states are refused, so plan review stops escalating each newly found state to a human.

### Key Files
