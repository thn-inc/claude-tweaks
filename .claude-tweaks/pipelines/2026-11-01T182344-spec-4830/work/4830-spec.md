# 4830: Decide how a hung-forge run avoids paying the forge probe on every hooked call (follow-up to #4578)

Surface: infra

**Related:** #4578, #4829, #4344, #4686, #3193, #3975, #3990, #4209, #4217, #4433, #4451, #4456, #4499, #4551, #4565, #4611, #4736, #4737, #4794, #4824

## Current State

Record #4578 made forge detection (`detectIntegrationModel`, `plugin/bin/lib/policy-schema.js`) honour `gh-timeout-ms`, retry once on a timeout (`FORGE_PROBE_ATTEMPTS = 2`), and report a degraded detection through an `onDegrade` callback. The PreToolUse PR-stamp gate (`checkBookkeepingStampsGate` in `plugin/bin/lib/hooks/pre-tool-use.js`) falls back to fresh detection through `resolveRunPinnedIntegrationModel` only when the run has no `integration-model` pin. It bounds that probe with `HOOK_FORGE_PROBE_TIMEOUT_MS` (5000 ms per attempt), so one detection can take up to about 15 s (5 s for the `git remote` probe plus two 5 s `gh` attempts).

Two #4578 decisions interact:

- **Q5:** a degraded detection is never cached as `prExempt`. The gate sets `modelResolved = false` when `onDegrade` fires, so the next covered call detects again.
- **Q10:** the Manifesto never pins a degraded detection into `{run-dir}/config.yml` (`manifesto-write.js` logs a `SKIP` and writes the config without the pin).

Together they mean that when `gh` is hung, nothing is remembered anywhere. Every covered PreToolUse call (Edit/Write/NotebookEdit and Bash git commit/push in the run's worktree, once the materialize commit has landed and no PR is recorded) runs the whole probe again. That costs up to about 15 s per hooked call until `gh` recovers. The verdict on a degraded call is already fail-open: the model reads `local-merge`, nothing is denied, and nothing is persisted. So the cost is pure latency, not a correctness gap.

Decision (made at shaping, 2026-11-01; the maintainer chose not to answer questions): **a run-scoped degrade memo with a 60 s TTL**, stored in `run-state.json`. The Technical Approach explains why this beats the other two options.

## Deliverables

1. A run-scoped degrade memo in the PR-stamp gate. When fresh forge detection degrades, the gate writes `forgeDegradedAt` (epoch milliseconds) to `{run-dir}/run-state.json` through `ctxLib.writeRunState`. The gate never writes `prExempt` on this path, so Q5's rule holds.
2. Memo read in the fresh-detection fallback. The memo is consulted only after the run-pin check has fallen through, so a pinned run never reads it. If `forgeDegradedAt` is a finite number and `0 <= now - forgeDegradedAt < FORGE_DEGRADE_MEMO_TTL_MS`, the gate skips detection and treats the call exactly as a fresh degrade: model `local-merge`, `modelResolved = false`, no `prExempt`. Any other value (absent, non-numeric, in the future, or expired) means detect again.
3. Memo lifecycle. On an expired or absent memo the gate probes. A fresh degrade rewrites `forgeDegradedAt` with the current time. A clean detection (any non-degraded result) clears it by writing `forgeDegradedAt: null`, and the gate then continues as it does today, which includes persisting `prExempt` for a clean non-`pr-first` result.
4. A new constant `FORGE_DEGRADE_MEMO_TTL_MS = 60000` in `plugin/bin/lib/policy-schema.js`, next to `HOOK_FORGE_PROBE_TIMEOUT_MS` and exported with it. Its comment gives the derived worst case: at most one 15 s probe per 60 s of hooked activity while `gh` stays hung.
5. Update `docs/hooks.md`'s "The run's pin, not a fresh detection" bullet. It should say that a degraded detection is never persisted as `prExempt` but is memoized as `forgeDegradedAt` for `FORGE_DEGRADE_MEMO_TTL_MS`, and that a clean detection clears the memo.
6. Tests in `tests/hooks-bookkeeping-stamps-gate.test.js`, or `tests/hooks-pre-tool-use.test.js` where that suite's fixtures fit better. Use `fakeGh` from `tests/helpers/fake-gh.js` so the real probe path runs, not the `deps.resolveIntegrationModel` override.

## Acceptance Criteria

1. **Probe count across calls.** Set up a run with no `integration-model` pin, a landed materialize commit, and no recorded PR, with `fakeGh({ first: 'hang' })`. Three consecutive covered gate calls inside the TTL leave the fake `gh` invocation count at exactly 2 (one degraded detection of two attempts). `run-state.json` then carries a numeric `forgeDegradedAt` and no `prExempt`. Against the current code the count is 6, so the test goes red.
2. **Expiry re-probes.** Backdate `forgeDegradedAt` past `FORGE_DEGRADE_MEMO_TTL_MS` (edit `run-state.json` directly, or inject a clock). The next covered call probes again: the count rises by 2 under `'hang'` and `forgeDegradedAt` is refreshed.
3. **Recovery clears the memo.** With an expired memo and a fake `gh` in `'fail'` mode (a definitive exit, so the clean result is `local-merge`), the next covered call clears `forgeDegradedAt` and persists `prExempt: true`, which is today's clean-`local-merge` behavior.
4. **Untrusted memo values fail open to probing.** A `forgeDegradedAt` set in the future, or set to a non-numeric value, does not suppress detection: the covered call probes.
5. **Pinned runs ignore the memo.** A run whose `config.yml` pins `integration-model` never spawns `gh`, even when `run-state.json` carries a fresh `forgeDegradedAt`.
6. **Existing #4578 Q5 tests stay green unchanged.** These are "a degraded detection never persists prExempt" (AC15.2) and "the override receives an onDegrade callback; a clean local-merge still persists prExempt".
7. Each new test case goes red against the pre-change code (prove it by reverting the change). `npm test` passes.

## Release Note

When `gh` hangs during a pipeline run, hooked tool calls no longer each wait up to 15 s for forge detection. The hook now re-probes at most once a minute until `gh` recovers.

## Technical Approach

### Decision and rationale

Three options were weighed:

- **Run-scoped degrade memo with a TTL (chosen).** It turns "up to 15 s per hooked call" into "at most one 15 s probe per 60 s". It reproduces the verdict a fresh degrade would give (fail-open allow, no `prExempt`), so it changes only latency, never a gate outcome. Q5's never-cache rule exists so that a later call can still see `pr-first` and enforce. The memo keeps that property because it expires after 60 s and a clean detection clears it, so recovery is noticed within one TTL. A permanent `prExempt` would never notice.
- **Shorter probe after the first degrade.** Rejected. It still costs at least one full `gh` timeout on every hooked call (5 s with one attempt), and it adds a second timeout path through `detectIntegrationModel` for less benefit.
- **Accept the cost.** Rejected. At several hooked calls a minute, 15 s each makes a session unusable while `gh` hangs, which is close to breaking `docs/hooks.md`'s never-break-a-session invariant.

TTL 60 s is a constant, not a policy key. Nobody has asked to tune it, and adding a key costs a registration across the policy schema, the Manifesto, and the docs. It can be promoted to a policy key if someone does ask.

### Placement

The memo belongs to the gate's fresh-detection fallback, not to `detectIntegrationModel`. The detector is shared by the CLI callers (`resolve-policy.js`, `precondition.js`, `phase-exit.js`), which run once per invocation and must keep reporting a degrade live. The builder chooses whether the memo read sits in `resolveRunPinnedIntegrationModel` (it already has `runDir`, and the read must come after the pin check) or in the gate around that call. The `deps.resolveIntegrationModel` test override path is not required to honour the memo.

### Key Files

- `plugin/bin/lib/hooks/pre-tool-use.js` — `checkBookkeepingStampsGate`'s `!runState.pr` branch and `resolveRunPinnedIntegrationModel`: read, write, and clear `forgeDegradedAt`
- `plugin/bin/lib/policy-schema.js` — new exported `FORGE_DEGRADE_MEMO_TTL_MS` next to `HOOK_FORGE_PROBE_TIMEOUT_MS`
- `plugin/bin/lib/hooks/context.js` — `writeRunState` (used, not changed; a `null` patch value overwrites the field)
- `docs/hooks.md` — the "The run's pin, not a fresh detection" bullet: describe the memo
- `tests/hooks-bookkeeping-stamps-gate.test.js` — new probe-count, expiry, recovery, and untrusted-value cases next to the existing #4578 Q5 cases
- `tests/hooks-pre-tool-use.test.js` — pinned-run-ignores-memo case next to the existing `resolveRunPinnedIntegrationModel` #4578 tests
- `tests/helpers/fake-gh.js` — the counting fake (`'hang'` / `'fail'` modes), used, not changed

## Gotchas

- Use `0 <= now - forgeDegradedAt < TTL`, not just `now - forgeDegradedAt < TTL`. With the one-sided check, a future timestamp (clock skew, or a hand-edited file) gives a negative age and suppresses detection forever.
- Do not reuse `prExempt` or any other permanent flag for the memo. Q5's whole point is that a degraded result must be able to flip to `pr-first` and enforce once `gh` recovers.
- Each `'hang'` probe costs real wall-clock time: two 5 s attempts per detection, because the gate hardcodes `HOOK_FORGE_PROBE_TIMEOUT_MS`. Keep the number of degrading calls in the new tests small, and do not skip them for being slow. They are the only proof the memo cuts the probe count.
- The comment at the top of the `!runState.pr` branch says `phase-exit.js`'s `prPushReleased` mirrors this branch's release rules (#4026). The memo does not change any release outcome, only whether the probe runs, so `phase-exit.js` needs no matching change. Confirm this rather than assume it.
- #4344 (`auto:build`, `ready`) extracts the PR-stamp release rule out of this same branch, so the two records' changes to `pre-tool-use.js` will likely conflict. Whichever lands second rebases onto the first.
- #4829 is a sibling #4578 follow-up. It is about surfacing the degrade in reconcile, the express lane, and the preflight, not about probe cost, so it does not overlap in behavior.
- SessionStart also probes with `HOOK_FORGE_PROBE_TIMEOUT_MS`, but only once per session. That is out of scope here.
