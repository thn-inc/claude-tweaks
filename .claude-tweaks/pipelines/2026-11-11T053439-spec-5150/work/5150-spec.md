# 5150: verify.js baseline adjudication: concurrency=4 per-file reruns share one checkout's test resources, and each adjudication's random scratch path leaks a path-derived resource

Surface: backend

**Related:** #5119 (prerequisite: the shipped slot lock, the adjudication full-lane slot and its `index`), #3064, #3111, #3063; near-duplicate screen: #4424, #3067, #4769, #3765, #5069, #5075

## Current State

- `adjudicate()` (`plugin/bin/lib/verify/baseline.js:312`) runs three phases of per-file reruns, one after another: base-side runs in the scratch worktree (:444), isolated HEAD runs in the caller's checkout (:471), and retries of isolated failures, also in the caller's checkout (:552, #3111). Each phase goes through `pool(work, concurrency = 4, …)` (:158, default at :314), and nothing in verify.js passes `concurrency`. So up to 4 runs of a project's test command share one checkout at once. A project whose test command assumes one runner per checkout gets 4 concurrent runners on whatever that checkout owns: a test database named from the checkout path, a port, a cache dir. Field evidence: two simultaneous resets on one per-checkout test database, one blocked on a relation lock. That produces spurious hook timeouts, which make more files fail and so feed more adjudication.
- Timeouts are already recognized as evidence that proves nothing. A rerun's `timedOut` routes the file to `attributable` (:560-569), and the extractor drops timed-out or cancelled entries under `conclusiveOnly` (`extract.js:262` `INCONCLUSIVE_RE`, `cancelledCount` :317). Neither changes how many reruns run at once.
- Flaky retry (`flaky.js:61` `runRetries`) is already serial, one file and one attempt at a time. After #5119 it runs under the held slot.
- `realGit().addWorktree` (`baseline.js:108`) checks the base out under a fresh `mkdtemp` parent (`ct-verify-base-*`) on every adjudication, and `removeWorktree` (:123) deletes it afterwards. Any resource a project derives from the checkout path is therefore minted anew per adjudication and never reclaimed. Field evidence: 175 of 191 per-checkout test databases on one machine matched no live worktree.
- #3064's signal handling removes the scratch on SIGHUP/SIGINT/SIGTERM (`baseline.js:438`). An uncatchable kill (SIGKILL, Windows TerminateProcess) leaves it behind, and `findStaleBaselineWorktrees` (:147, called at `verify.js:446`) only names stale `ct-verify-base-*` worktrees, never removes them: a sibling session's live scratch looks identical.
- After #5119, adjudication runs holding a machine-wide full-lane slot whose `index` is unique among live holders, and verify.js passes that index to `adjudicate()` as `slot`.

## Deliverables

1. **Configurable rerun concurrency, serial by default.** A new key `concurrency.reruns` (positive integer) in the `verify-scope.json` `concurrency` block #5119 adds. It is the most per-file reruns that run at once in one checkout, in any phase. With no `reruns` declared, every phase runs one rerun at a time. A project whose test command tolerates several runs sharing one checkout declares `reruns` above 1 to opt in. The value reaches `adjudicate()` through its existing `concurrency` option, and verify.js passes it explicitly. No policy key: whether two runs of the test command can share a checkout is a property of that command, and the declaration is where the command lives. A policy value could drift away from the command it describes.
2. **Timeout back-off: never fan out on timeout evidence.** A failing check carries timeout evidence when it timed out (`timedOut`), when its log's failing region matches the extractor's inconclusive markers (`INCONCLUSIVE_RE`) or reports a non-zero cancelled count, or when it matches an entry of a new `concurrency.timeoutPatterns` key: a list of literal substrings a project declares for its own runner's timeout wording, matched against the ANSI-stripped log. When any check given to `adjudicate()` carries timeout evidence, every phase runs serially whatever `reruns` declares. When any rerun in a phase times out, the later phases run serially too. The queue half of the back-off is #5119's full-lane slot: adjudication already waits behind every other full-lane holder. Flaky retry needs no change: it is already serial and runs under the slot, and a delay before it would only hold the slot longer without lowering load.
3. **Stable scratch path per slot.** When `adjudicate()` receives a `slot` index its own process took, the base checkout goes at `<os.tmpdir()>/ct-verify-base/<repo-key>/slot-<index>/wt`. `<repo-key>` is the first 12 hex digits of the sha256 of the realpath of the git common dir. Repeated adjudications reuse at most one path per slot per repository, whatever the base sha. Before `git worktree add`, any worktree registered at that path, and any directory left there, is removed. It is this slot's own leftover from a killed run, and the held slot makes the path exclusively ours. After adjudication the worktree is removed as today, and the path is reused on the next adjudication. With no slot index (verify.js inherited `CT_TEST_SUITE_SLOT_HELD=1` and took none), `addWorktree` keeps today's fresh `mkdtemp` path, and `findStaleBaselineWorktrees` keeps naming those.
4. **Report.** `report.json`'s `baselineAdjudicated` gains `concurrency: { declared, used, reason }` and `scratch: { path, reused }`. `reason` is `default-serial`, `declared`, `timeout-evidence: <check>` or `phase-timeout: <phase>`. `reused` is true when the stable path held a leftover that was removed first. The stdout summary prints one line when timeout evidence forced serial reruns.
5. **Decision record.** A new ADR under `docs/decisions/` (next free number) records two decisions with the evidence above. First, the serial-unless-declared default. Second, the stable per-slot path chosen over a project-declared teardown command, and why: #3064 removal runs only on catchable exits, so a teardown would be skipped by exactly the uncatchable kills that leak. It would also run project code inside a signal handler that races `process.exit`. The stable path bounds the leftovers to slots × repositories even after a SIGKILL, and a project can reclaim them by name.
6. **Docs.** In `plugin/skills/test/verification.md`'s baseline adjudication section, cover `reruns`, `timeoutPatterns`, the serial default and how to opt in, the stable scratch path, and the reuse contract below. Add both keys to the verify-scope declaration docs next to `suiteSlots`.

## Acceptance Criteria

- A declaration with no `reruns`: in each of the base, isolated-HEAD and retry phases, the fake `runOne` never has more than one call in flight. Pinned by a test recording the peak in-flight count per `cwd`, which fails against today's default of 4.
- `concurrency.reruns: 3` with 6 failing files: the peak in-flight count per phase is 3.
- `concurrency.reruns: 4` with a failing check that carries timeout evidence: the peak in-flight count is 1 in every phase, and `concurrency.reason` names the check. One test per evidence source: `timedOut`, an inconclusive-marker log, a cancelled-count log, a declared `timeoutPatterns` match.
- `concurrency.reruns: 4` where a base-phase rerun times out: the isolated-HEAD and retry phases have a peak of 1 and `reason` is `phase-timeout: baseline`.
- Two sequential adjudications holding slot index 0 at two different base shas use the same scratch path, and the tmpdir gains no new `ct-verify-base-*` entry.
- A leftover worktree registered at the slot's path (a killed earlier run) is removed before `git worktree add`, the adjudication completes, and `scratch.reused` is true.
- An adjudication with no `slot` keeps a fresh `ct-verify-base-*` path, as today.
- `reruns` must be a positive integer and `timeoutPatterns` an array of non-empty strings. Any other value fails declaration validation, and the `concurrency` block's allowed-key list names both.
- The ADR exists and states both decisions with their reasoning.
- This repo's committed `.claude-tweaks/verify-scope.json` stays readable by the latest release's `declaration.js`.

## Release Note

Baseline adjudication now reruns failing files one at a time unless the project declares otherwise, never fans out when failures look like timeouts, and reuses one scratch checkout per slot instead of creating a new one each run.

## Technical Approach

- **Concurrency resolution.** In `adjudicate()`, compute the phase limit once: start from `concurrency` (verify.js passes the declared `reruns`, else 1), forced to 1 by the check-level timeout evidence. After the base phase, force 1 again if any base run timed out, and the same after the isolated phase for the retry phase. Detect timeout evidence with a small exported helper in `extract.js` (`timeoutEvidence(text, family, patterns)`), so `INCONCLUSIVE_RE` stays the extractor's single source.
- **Scratch path.** Give `realGit()` an `addWorktree(sha, { slot })` variant that builds the stable path, verifies any existing path is a directory under `<os.tmpdir()>/ct-verify-base/` before removing it (the path guard for an `rm -rf`), runs `git worktree remove --force` and then `git worktree prune` on it, and adds the worktree. `removeWorktree` removes only `wt` and leaves the `slot-<index>` parent in place. The signal handlers at `baseline.js:438` are unchanged.
- **verify.js.** Pass `concurrency: decl.concurrency.reruns ?? 1` and `slot` (from #5119) into `adjudicate()`. Without `--scope`, take the `concurrency` block from the same default-path read #5119 adds.

## Gotchas

- **Reuse contract.** A project that derives a resource from the checkout path now sees that resource reused across adjudications at different base shas, so it must tolerate starting from another commit's state. That is the same contract its resource already lives with in an ordinary worktree as HEAD moves. Document it rather than resetting anything for the project.
- **Only an own slot index.** Never derive the stable path from an inherited env var. This repo's suite runs many verify.js tests at once under one slot held by `tools/run-tests.js`, and a shared index there would put concurrent adjudications on one path.
- **Residual risk accepted.** The slot module's documented once-only race (two reclaimers of one dead lock) can at worst let two adjudications share a path once. A run in a checkout that vanished underneath it produces no evidence and routes to `attributable` or an adjudication error, never to a false pass. State this in the ADR.
- **A slower adjudication for this repo.** This repo's own declaration does not declare `reruns`, so its adjudications go serial. Do not add `reruns` to the committed declaration in this PR: the previous-release reader pin must keep reading it, and the `verify-scope-rule-kind` skill's previous-reader rule applies.
- `timeoutPatterns` entries are literal substrings, never regexes: no ReDoS surface, and no escaping question for the project.
- Stay stack-agnostic: no runner-specific timeout wording in shipped code beyond what `INCONCLUSIVE_RE` already carries. A project supplies its runner's own wording through `timeoutPatterns`.
- Run the repo's tests through `tools/run-tests.js`; other sessions may be running suites on this machine.

## Original request

verify.js baseline adjudication: concurrency=4 per-file reruns share one checkout's test resources, and each adjudication's random scratch path leaks a path-derived resource

**Summary:** `bin/lib/verify/baseline.js`'s `adjudicate()` runs base, isolated-HEAD and retry per-file reruns through `pool(work, concurrency = 4, …)`. The HEAD-side reruns all execute in the same checkout, so a project whose test command is "one runner per checkout" (here, one test database per worktree, files serialized) gets 4 concurrent runners on one shared resource. There's no knob to lower it. Separately, `addWorktree` checks the base out at a fresh `mkdtemp` path every time, so any per-checkout resource a project derives from its path (a test database, a port, a cache dir) is created anew for every adjudication and never cleaned up.

**Kind:** Defect

**Affected component:** `bin/verify.js` baseline adjudication (`bin/lib/verify/baseline.js` — `adjudicate()`'s `concurrency = 4` default; `defaultGit().addWorktree`)

**Repro steps:**
1. A Node project whose vitest suites share one Postgres test database per checkout: each suite TRUNCATEs every table in `beforeEach`, the database name is derived from a hash of `git rev-parse --show-toplevel`, and `fileParallelism: false` keeps it to one runner per checkout. `verify-scope.json` declares the per-package test commands.
2. Make a branch where 4+ test files fail (e.g. by timing out under load), and run verify.js with baseline adjudication.
3. Watch `pg_stat_activity` during the isolated-HEAD phase.

**Expected vs. actual:**
Expected: per-file reruns in one checkout respect the project's one-runner-per-checkout contract, or the concurrency is configurable (e.g. a `verify-scope.json` / policy key, default 4, settable to 1). The base checkout's path is stable per base sha (or the project gets a cleanup hook), so path-derived resources aren't minted once per adjudication.
Actual: up to 4 runners TRUNCATE the same database at once. Observed: two TRUNCATEs on one test database at the same moment, one blocked on `Lock:relation`. That causes spurious hook timeouts, which in turn make more files fail and feed more adjudication — a positive feedback loop under load. With about 9 pipeline sessions on one machine, the shared Postgres checkpointer stalled for about 9 h. Every adjudication also created a new `ct-verify-base-*` checkout and therefore a new test database. 175 of 191 per-checkout test databases on the machine matched no live worktree.

**Definition:** Clear

**Related:** #5119 (machine-wide full-suite slot lock: it serializes full runs *across* worktrees, but neither the 4-way rerun parallelism *within* one checkout nor the per-adjudication scratch path), #3111.

**Plugin version:** 6.164.0

## Plan Review Clarifications

- Decided by the user at plan review: a shared stable path is guarded, not accepted as residual risk — this corrects the Gotchas' "Residual risk accepted" claim, which is false: a second run's leftover cleanup removes the first run's live checkout and re-adds it at another base sha, and holders of one index under different `CT_TEST_SUITE_SLOT_DIR` values collide on every run. (a) `<repo-key>` folds in the slot lock base dir the index was taken under (`holdSlot`'s `defaultSlotBase(env, tmpdir)` value), so holders from different lock dirs never share a path; (b) before a base-side run's log counts as evidence, the scratch worktree's HEAD must equal the adjudication's base sha, and a mismatch is never evidence — the file routes the way an unusable base run routes today (flaky on a clean isolated run, else attributable; a base full run leaves `fixed` null with a named reason), never "fails at base". With (b), a collision costs evidence, never a false pass; the ADR states the residual risk that way.
- Decided by the user at plan review: a stable-path guard failure (a symlinked or other-user `ct-verify-base` root, a non-directory leftover, a slot directory outside the root, an unresolvable common dir or lock dir) keeps the fallback to a fresh `mkdtemp` path with one stderr line, and `report.json`'s `baselineAdjudicated.scratch` gains `fallback: <reason>`, absent when the stable path was used (and when no slot was held), so the leak is visible.
- Decided by the user at plan review: `concurrency.used` is per phase, `used: { baseline, isolated, retry }`, each the limit that phase ran under; a phase that spawned no rerun reports `null`, and all three keys are always present.
