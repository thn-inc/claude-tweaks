# 3389: Review Console renders every curation-engine finding as {row}:undefined — resolve.js reads f.target, the engine stores targetPath

**Related:** #3402 (absorbed into this record)

Origin: wrap-up of #3373 (observed in its Review Console); independently captured as #3402 from the multi-spec Review Console of run 2026-10-17T100123-spec-3368-3365

Defer-reason: tangential

## Current State

`plugin/bin/lib/console/resolve.js`'s `engineItems` (lines 334 and 336) builds each curation-engine finding's console item id as `` `${rowId}:${f.target}` ``. The engine never stores a `target` on a finding: `wrap-up-engine.js record` keeps the payload's own `targetPath` field (`curation-engine.md` section 3's payload contract), and `engine-state.json`'s `results.<row>.findings[]` carries `targetPath`, not `target` (`target` exists only at the row level, e.g. `"Skills"`). So every applied or staged engine finding renders in the console table and in `console.json` as `skills:undefined` / `docs:undefined` / `journeys:undefined`. Observed twice: in #3373's wrap-up, the Skills row's applied finding (commit 13a5a3512) rendered as `skills:undefined`; on run 2026-10-17T100123-spec-3368-3365's parent console, three Skill-updates rows were all labelled `skills:undefined`. The resolution and reason columns are right; only the item label is lost, so the operator cannot tell which file each applied row refers to without opening `engine-state.json`. Two findings on the same row also collide on one id.

## Deliverables

In `engineItems`, derive the id from the finding's `targetPath`, falling back to `f.target` for any older `engine-state.json` whose findings still carry that field, and to the row's `target` only when a finding carries neither, so each engine item has a distinct, readable id.

Add a test in the console-resolve suite (`tests/bin-lib/console/`) that feeds an `engine-state.json` with two applied findings on one row, each with its own `targetPath`, and asserts both ids name their files and differ. The test must be proven red against the current code before the fix lands.

## Acceptance Criteria

A Review Console rendered from an `engine-state.json` whose Skills row holds an applied finding with `targetPath: ".claude/skills/x/SKILL.md"` shows the item id `skills:.claude/skills/x/SKILL.md`, never `skills:undefined`.

`console-resolve.js --run <dir> --policy console-auto` renders `skills:.claude/skills/{name}/SKILL.md` for an applied Skills finding, never `skills:undefined`.

Two applied findings on the same engine row produce two distinct console item ids.

`npm test` passes.

## Release Note

Fixed: the Wrap-Up Review Console now names the file each curation finding touched instead of showing "undefined".
