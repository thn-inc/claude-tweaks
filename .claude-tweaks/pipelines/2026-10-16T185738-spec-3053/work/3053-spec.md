# 3053: Assess listing claude-tweaks on Anthropic's new Claude plugin portal

Surface: infra

## Current State

claude-tweaks ships through its own marketplace today, not through any first-party discovery surface:

- The plugin manifest is `plugin/.claude-plugin/plugin.json`: name, description, version, author, repository, MIT license, keywords, one agent. Only the `plugin/` subtree ships (`docs/decisions/0015-plugin-payload-boundary-is-the-plugin-subtree.md`).
- Releases go out through release-please. `.github/workflows/mirror-marketplace.yml` then writes the catalog entry into `thn-inc/claude-tweaks-marketplace`'s `.claude-plugin/marketplace.json`, pinned by `sha` and with no `version` field (`docs/releasing.md`). Users install through that marketplace.
- The plugin depends on other plugins being present: Superpowers (several `/superpowers:*` skills) and code-simplifier (its `code-simplifier:code-simplifier` subagent). It also expects Node 18+ for its `plugin/bin/` executables and hooks (CLAUDE.md's Stack table).

The external prompt for this record: Anthropic has launched a plugin portal for Claude (source link in the original request below).

## Deliverables

1. A written go/no-go on listing claude-tweaks on the portal, posted as a comment on this record. It should cover:
   - whether the portal accepts Claude Code plugins of this shape: skills, hooks, `bin/` executables, one agent, and dependencies on other plugins. A portal aimed at MCP-based Claude plugins may not fit;
   - what listing requires (manifest fields beyond today's `plugin.json`, a review process, versioning rules) and how each requirement maps onto the current release-please and marketplace-mirror flow;
   - how the Superpowers and code-simplifier dependencies would be expressed or satisfied for a portal user;
   - what listing would cost to maintain alongside the existing marketplace: two catalogs to keep in sync, and review turnaround on every release.
2. When the verdict is go, file the concrete listing work as a backlog record via `/claude-tweaks:capture` with a spec-shaped body. Name each required manifest or workflow change. Otherwise, state explicitly why not, and what would change the answer.

## Acceptance Criteria

- The comment exists on this record, addresses each of the four points in Deliverable 1, and cites the portal's own published requirements for every requirement it names.
- It states a clear verdict: go, no-go, or not yet (with the condition that would flip it).
- A go verdict has a filed backlog record linked from the comment; no listing step is left as prose only.

## Release Note

No user-facing change. This produces an internal go/no-go on listing claude-tweaks on Anthropic's plugin portal.

## Technical Approach

A desk evaluation, with no manifest, workflow, or skill edits in this record. Read the portal's published submission requirements first. Then diff them against `plugin/.claude-plugin/plugin.json` and the release and mirror flow in `docs/releasing.md`. The plugin-dependency question is the most likely blocker, so settle it early.

### Key Files

- `plugin/.claude-plugin/plugin.json` — current manifest the portal requirements are diffed against
- `.github/workflows/mirror-marketplace.yml` — current catalog-publish step a portal listing would sit beside
- `docs/releasing.md` — current release and versioning flow

## Gotchas

- ASSUMPTION — verify at build: the portal lists Claude Code plugins (skills, hooks, executables) rather than only MCP-connector-style Claude plugins. Confirm this from the portal's own submission documentation before evaluating anything else.
- `plugin.json` carries the single version authority, and the marketplace entry deliberately carries no `version` field. A portal that requires its own version field would reintroduce a second version source, which needs a deliberate decision.
- Listing does not replace the existing marketplace. Existing users install from `thn-inc/claude-tweaks-marketplace`, so any go verdict keeps that path working.
