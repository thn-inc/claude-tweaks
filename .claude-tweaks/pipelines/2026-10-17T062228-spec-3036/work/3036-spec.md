# 3036: flow: Step 1.8 creates the open-items ledger before the run's worktree exists, so under `worktree-always` it cannot land in `docs/plans/`

Surface: infra

## Current State

`plugin/skills/flow/SKILL.md` creates the open-items ledger in Step 1 (Validate Input), item 8 (line ~130), and logs `AUTO {time} — flow: created open-items ledger {path}` (#1800), which `review/code-mode-steps.md`'s QA Ledger Check later reads. The run's worktree is created later: in Step 4's build step under `materialize.md`'s worktree-first ordering, or at Execution in `flow/multi-spec.md`'s "Shared worktree" step 1.

`plugin/skills/ledger/SKILL.md`'s Create writes `docs/plans/YYYY-MM-DD-{feature}-ledger.md`, or `{run-dir}/ledger.md` when `run-state.json` has no `worktree` field. `_shared/ledger-format.md:15`'s "No-worktree run exception" applies that alternate under `worktree-always: true`; it was designed for a wrap-up-only run that never gets a worktree.

At Step 1.8 a session that is not already isolated has no `worktree` field yet, so under `worktree-always` every option fails:

1. Writing `docs/plans/` from the main checkout is denied by the `worktree-always` PreToolUse gate.
2. Following the exception's momentary condition gives a run that will have a worktree a gitignored, never-committed run-dir ledger, which also shadows any later `docs/plans/` ledger through the "check `{run-dir}/ledger.md` first" rule.
3. Deferring creation (what the observed 6.136.0 run did) leaves a window in which a finding has no ledger to land in.

`materialize.md` already moved the spec write behind worktree creation for the same reason; the ledger step was not moved with it. When the session is already isolated (adopt path), Step 1.8 works.

## Deliverables

1. Create the ledger immediately after the run's worktree is created or adopted, before any build task can raise a finding: `build/worktree-setup.md`'s post-creation steps for a single-spec run, `multi-spec.md`'s "Shared worktree" step 1 for a multi-spec run. Keep Step 1.8 only for `current-branch` runs and already-isolated sessions.
2. Narrow the No-worktree run exception so it cannot fire for a run that will create a worktree: key it on the run's resolved git strategy or the wrap-up-only shape, not on `run-state.json`'s momentary lack of a `worktree` field.
3. Emit #1800's creation log line at the new point so the QA Ledger Check still finds it.

## Acceptance Criteria

1. Under `worktree-always`, a `/flow` run started from a non-isolated session gets its ledger at `docs/plans/...` inside the run's worktree, created before the first build task, with no gate refusal.
2. No run that creates a worktree ends with a `{run-dir}/ledger.md`.
3. A wrap-up-only run with no worktree still gets its run-dir ledger.
4. The QA Ledger Check finds the creation log line in both the single-spec and multi-spec paths.

## Release Note

`/flow` runs under `worktree-always` now create their open-items ledger in the worktree before building, so early findings are never dropped.

## Technical Approach

Move ledger creation from `flow/SKILL.md` Step 1.8 to the worktree-ready points, leaving a short Step 1.8 that handles only the no-worktree strategies, and change the exception's condition in `_shared/ledger-format.md` and `ledger/SKILL.md`'s Create from "no `worktree` field" to the resolved strategy. Update the QA Ledger Check only if the log line's location changes in a way it reads.
