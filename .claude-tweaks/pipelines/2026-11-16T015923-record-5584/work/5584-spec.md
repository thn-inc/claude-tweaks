# 5584: Build a record named in a typed dispatch command without an auto:build label

Surface: backend

**Related:** #4608, #4623, #4624, #5232, #5225, #5231, #5053, #5558, #5387
Risk-flags: auth
Risk-flags-unconfirmed: true

## Current State

`/claude-tweaks:dispatch` and the pipeline driver build a record only when it carries the `auto:build` label. Decision 0.2 of `docs/superpowers/specs/2026-11-15-process-efficiency-design.md` (answered 2026-11-15) changes one case: a command the maintainer types that names the record carries its own build authority. A run a hub or a routine starts still needs the label. The design read the cost of the refusal from session transcripts of 2026-10-08 to 2026-11-15: a refine, a label confirmation and a second dispatch for a record the maintainer had just named.

Where the label is required today (checked on 2026-11-16):

- `plugin/bin/lib/dispatch/queue-pull.js` fetches the pool with `--label auto:build` (`QUEUE_ARGV`, line 190) and filters it on `facets.grants.build` (line 425). A record without the label is never in `dispatch-groups.json`, so no selection form can pick it.
- `plugin/skills/dispatch/SKILL.md`: the `#N` bullet says "confirm it currently carries `auto:build` and no `bot:*` label". The `#N[,#M,#O...]` bullet reports "no `auto:build` grant" for a named record that is not in the pool.
- `plugin/bin/lib/driver/admission.js` line 122 refuses with `record lacks auto:build` (`ADMISSION_REASONS.noBuildGrant`). `plugin/bin/lib/driver/steps.js` runs it for every record, named or picked by `--budget`.
- `plugin/bin/lib/dispatch/resume-eligibility.js` line 341 refuses `dispatch resume #N` with `not-granted` when the label is absent.
- `plugin/bin/claim-targets.js` does not check the label. Neither does `/claude-tweaks:flow #N` (`plugin/skills/flow/claim-targets.md` reads the open queue "not filtered to `auto:build`"). A person can already build an ungranted record by typing `/claude-tweaks:flow #N`. Only the dispatch and driver entries refuse.
- `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md` states the rule this record reverses: its Eligibility section ("Naming a record on the command line is not authorization") and item 8 of "Calls made in this document that were not discussed".

What the plugin knows today about who started a run:

- Nothing, in code. No file under `plugin/bin` reads `CLAUDE_CODE_ENTRYPOINT`, `CLAUDE_CODE_SESSION_ATTENDED`, a `CC_*` variable, or a transcript's `promptSource` or `turnOrigin`. Whether a person is present is judged by the model from prose (`plugin/skills/dispatch/task-prompt.md`'s `--headless` decision, `SKILL.md`'s Next Actions rule). `SKILL.md` and `plugin/skills/_shared/headless-self-report.md` assume the `#N` forms "always run with a human present".
- `autonomy: unattended` is a policy tier, not a presence signal. `isNestedSession` in `plugin/bin/lib/hooks/context.js` is about a run's owner process.
- `plugin/bin/lib/hooks/user-prompt-submit.js` sees every prompt submitted to a session, before a slash command is expanded. It records a `/claude-tweaks:<skill>` first line as a `skill_invoked` event with `source: "user"`, only into a run the session owns, and ignores the arguments.
- A session opened by `cc hub spawn` has the same environment as one a person launched. `cc hub spawn` belongs to `cc-router` in the `claude-user-config` plugin (repository `thn-inc/claude-user-config`); it opens a terminal tab whose first prompt is the command it was given. Both kinds of session carry `CC_POSTURE`, and the spawned one carries nothing more. Only a headless run the hub starts has a marker, `CC_HUB_RUN` (that plugin's `skills/hub/reference/contract.md`, version 0.13.0). So no code can tell a spawned session from a person's today.

## Deliverables

1. **Regression probe first.** The build shows, on the Claude Code version it runs under, that a typed command is accepted and that a scheduled and a peer-delivered one are refused. It runs live cases in throwaway sessions launched the way the first probe launched them (a clean environment, a pty), with the line `/claude-tweaks:dispatch #N` for a closed record, so the dispatch that follows refuses it.
   Gating cases: (a) typed at an idle prompt; (g) a prompt the model scheduled for itself (`ScheduleWakeup` with the line as its prompt); (h) a message another session delivered over the session socket: `cc hub send <target> "<the line>"`, or, where `cc-router` is not installed, a second session whose model calls `SendMessage` with the line as the text. Reported cases: (b) typed while the session is busy; (c) given on the launch line of an interactive session; (i) given on the launch line of a resumed session.
   Part 1, before any code. A scratch `UserPromptSubmit` hook logs its payload and does not block. For each case the build records the payload's `prompt_id` and every transcript row with that `promptId` that is not a tool result: its key names, and the values of `turnOrigin`, `origin.kind`, `promptSource`, `isMeta` and `sessionId`, and whether `message.content` is the command form. It also records whether the row was in the file when the turn's first Bash call ran. The test is the row test's markers and command parts, as Technical Approach states them, applied by reading the fields: (a) must have one row that passes both; (g) and (h) must have no row that passes the markers part. If either fails, the build ends `BLOCKED` with the capture.
   Part 2, once Deliverables 2 and 3 exist. The cases run again with the worktree's plugin loaded (`claude --plugin-dir`), so the shipped hook writes the pointer. A new maintainer-side script, `tools/typed-command-probe.js --session <id> --record <n> [--config-dir <dir>] [--tmpdir <dir>]`, then calls the shipped `readTypedCommand` with that session's id, config directory and temp directory and prints the pointer entry, each candidate row's marker fields (never its text) and the answer. It must print `typed` for (a) and `not-typed` for (g) and for (h).
   Outcome rule: if (a) is refused, (g) or (h) is accepted, or a gating case cannot be run (no route delivers the line for (h), for one), the build ends `BLOCKED` with the capture and ships nothing. It does not change the check to make a case pass. The PR and `docs/hooks.md` carry the table of all six cases with the Claude Code version, and `docs/hooks.md` carries the steps, so the probe can be run again after a Claude Code upgrade.
Decided 2026-11-16: (b), (c) and (i) are judged by the same check as every other prompt and are not stop rows. A refusal of one of them keeps the label required for that way of giving the command, which is the safe direction; the PR says which were accepted.
Decided 2026-11-16: a launch-line command is the launcher's to mark. For (c) and (i) the probe also records every key whose presence or value differs from the row of (a), ids and times aside. If one separates both from (a), the row test's markers part requires the value (a) has, AC18 gains a `not-typed` fixture built from the captured (c) row, and `docs/hooks.md` records the field. If none does, the transcript cannot tell a launch line from a typed line; condition 4 is then the only refusal for a launcher, and `docs/hooks.md` says so in those words. The check does not refuse every first prompt of a session to close this: 133 of the 176 measured dispatch rows are first prompts, and a person who opens a session and types the command is the case decision 0.2 is for.
2. **The prompt pointer.** `user-prompt-submit.js` gains a second writer, independent of the first and of any owned run. When the first line of the prompt is `/claude-tweaks:dispatch` followed only by a record list (`#N`, `#N,#M,…`) or by `resume #N`, and the payload carries a `prompt_id` and a `session_id` that are each 1 to 64 characters of `[A-Za-z0-9-]`, it records each named number with that prompt id and the current time in `dispatch-prompts.json` under the session's temp directory (`plugin/bin/lib/session-tmp.js`). The hook cannot tell who sent the prompt, so the file is a pointer and not a proof: it is written for a scheduled or a delivered line too. Any other argument on the line (`next`, `--budget`, `--priority`, `close-out`, `--settle-parked`, an unparseable element) writes nothing. A payload whose `prompt_id` or `session_id` is missing or not of that shape writes nothing. An existing entry for the same record is replaced; entries for other records are kept. The hook still never writes stdout and never fails the prompt.
Decided 2026-11-16: one exported function, `parseTypedDispatch(firstLine)` in `build-authority.js`, is the whole grammar. It reads the record list with `parseExplicitIssueList` (`plugin/bin/lib/issues/grouping.js`), the parser the dispatch skill names for its list form, and accepts a list only when that parser reports no invalid element. Trailing spaces and a trailing `\r` are ignored. A form it does not know writes nothing, which keeps the label required; the refusal line for a named record with no pointer ends `(a typed command with any other argument records nothing)`.
3. **The transcript check.** `readTypedCommand({ number, env, now, … })` in a new `plugin/bin/lib/issues/typed-command.js` establishes the proof of typing. It reads the pointer for the record, finds the session's own transcript, looks up the pointer's prompt id in it, and answers `typed` only when a row with that id is a `/claude-tweaks:dispatch` command naming the record that the transcript marks as typed by a person, inside the time bound. Every other outcome is a refusal with one reason word: no transcript, more than one, a transcript that cannot be read, no row for the prompt id, a marker field that is missing or has any other value, a row that is another command, a row outside the bound. The steps are in Technical Approach. `plugin/bin/lib/timing/transcript.js` gains the one function that reads rows by prompt id; `locateTranscripts` finds the file.
4. **One rule for build authority**, in a new pure module `plugin/bin/lib/issues/build-authority.js`. Given a record's labels, whether the command named it, the environment, the transcript check's answer and whether stdin is a terminal, it returns `label`, `typed` or `none`, with the reasons for `none`. The rule is in Technical Approach. Every site in Deliverables 5 to 7 calls it; none restates it.
5. **Queue pull.** `queue-pull.js --transport gh` takes `--named <n[,m…]>` and, with it, a required `--run <firing run dir>`. For each named record that is not in the fetched pool it fetches the record, runs the transcript check, applies the rule, and on `typed` adds the record to the pool before any pass runs, so every existing pass judges it as it judges a granted record. It prints one line per named record without the label, saying it is built on the typed command or why it is not, and appends one `AUTO` line per `typed` record to the firing's `decisions.md` through `plugin/bin/lib/log-decision/append.js`. A fetch of a named record that fails is `labels-unreadable`. A pull that admitted a `typed` record neither reads nor writes the queue-order cache: a cache hit reuses the stored groups, so a stored pool that holds a typed record would hand it to a later drain that has no typed command, and a stored pool without it would drop it from this pull. Under `--transport files`, `--named` admits nothing and prints the refusal line.
Decided 2026-11-16: `--run` takes the value the firing already passes to `hooks.js close-run --run` (`$RUN_ID`: a run directory's basename, or its path), whether the firing minted that run directory or adopted it. The CLI resolves a basename under the main checkout's `.claude-tweaks/pipelines/` and then requires `resolveTarget` to accept the result.
6. **Resume.** `dispatch-resume.js --issue N` runs the transcript check for `N` and calls the rule with `named: true`, its injected environment and clock, and `stdinIsTTY: false`. It passes the answer to `resume-eligibility.js`, which refuses `not-granted` only when the answer is `none`. A `bot:blocked` record is refused as today. A typed `/claude-tweaks:dispatch resume #N` and a typed `/claude-tweaks:dispatch #N` both name record `N` for every reader: `parseTypedDispatch` returns the numbers a line names, and the row test asks only whether the record is among them.
7. **Driver.** `evaluateAdmission` takes the rule's answer as one more fact and refuses `record lacks auto:build` only when it is `none`. The admission step computes it: `named` is true for a record given on the command line and false under `--budget`. `drive.js #N` typed at a terminal is the second way to `typed` (Technical Approach). The admission event line carries `authority`. A stop's detail is the unchanged refusal text, then `; typed command not accepted: ` and the rule's reason words, comma-separated.
Decided 2026-11-16: the reason words are a closed list exported by `build-authority.js`: `not-named`, `not-ready`, `held`, `labels-unreadable`, `entrypoint`, `not-attended`, `remote`, `hub-run`, `launcher`, `no-session-id`, `no-pointer`, `pointer-unreadable`, `pointer-other-session`, `expired`, `no-transcript`, `transcript-unreadable`, `no-prompt-row`, `not-typed`, `other-command`, `not-a-terminal`, `ci`. The queue pull's refusal line and the resume refusal use the same words.

The driver design's Eligibility bullet and its call 8 are rewritten to the new rule, citing this record. `docs/driver.md`, `docs/hooks.md` and `plugin/skills/_shared/work-record.md`'s Grant semantics say when a typed command stands in for the label and that it writes no label. `docs/hooks.md` also carries the second writer and its file, the probe table, and the transcript fields the check reads, stated as observed on the probed Claude Code versions and not as a documented contract. ## Technical Approach

**The rule.** `resolveBuildAuthority({ number, labels, named, env, typedCommand, stdinIsTTY })` returns `{ authority, reasons }`. Closed rule: the rows below are every state. A state not listed is `none`, with one line naming it and the remedy `/claude-tweaks:backlog refine #N`. A plan review that finds another state adds its row as a plan amendment, not as a question.
Decided 2026-11-16: authority is per record, never per group. The queue pull adds only a record that is both in `--named` and answered `typed`; an ungranted record the command did not name is never fetched into the pool, so no pass can bundle it. A number in `--named` with no pointer entry of its own is `none`, whatever the other numbers have. The passes treat a `typed` record exactly as a `label` record, so a bundle may hold both. In the driver, `named` is true only for a number in `drive.js`'s own arguments.

| State | Answer |
|---|---|
| `labels` is not an array | `none` (labels unreadable) |
| labels carry `auto:build` | `label`, as today; nothing else is read |
| the command did not name the record (a drain, `--budget`, a bundle member the command did not name) | `none` |
| named, labels lack `ready` | `none`; the remedy is `/claude-tweaks:specify #N` |
| named, labels carry `bot:blocked`, `bot:parked` or `parked` | `none` (`held`) |
| named, `ready`, inside a Claude Code session, and every session condition holds | `typed` |
| named, `ready`, outside a Claude Code session, and every terminal condition holds | `typed` |
| anything else | `none`, with each failed condition named |

"Inside a Claude Code session" means `CLAUDECODE` or `CLAUDE_CODE_SESSION_ID` is set. Every comparison is exact string equality. An unset, empty or other value fails its condition.

Session conditions, all required. Conditions 1 to 4 read the environment and condition 5 reads the transcript; they are independent layers, and each refuses on its own:

1. `CLAUDE_CODE_ENTRYPOINT` is `cli`. A headless `claude -p` run has `sdk-cli` (probe row (d)).
2. `CLAUDE_CODE_SESSION_ATTENDED` is `1`. A `claude -p` run has `0`.
Decided 2026-11-16: conditions 1 to 3 only rule out runs known not to be a person's: a headless run, a cloud sandbox, a hub's headless run. None of them shows a person is present; condition 4 and the transcript check carry that. A value the probe table does not list reads as `none`, so a Claude Code release that changes a value takes the typed path away and does not widen it. The one change that would widen it, a headless run reporting `cli`, is what the parked record's re-run of row (d) looks for.
3. `CLAUDE_CODE_REMOTE` and `CC_HUB_RUN` are unset or empty. The first marks a cloud sandbox, where a Routine runs; the second marks a headless run a hub started.
4. The launcher says a person launched the session: when `CC_POSTURE` or `CC_LAUNCHED_BY` is set, `CC_LAUNCHED_BY` must be `user`. When neither is set, no launcher is in play and the condition holds. `cc-router` does not export `CC_LAUNCHED_BY` yet (thn-inc/claude-user-config#50, open on 2026-11-16), so on a machine that launches through `cc` the label stays required until that change ships there. That is the fail-closed direction.
Decided 2026-11-16: the variable is `CC_LAUNCHED_BY` and its values are `user` and `hub`. Only the exact value `user` passes; `hub`, an empty value and any other value fail. `docs/hooks.md` records the variable, the two values and its owner, `skills/hub/reference/contract.md` in `thn-inc/claude-user-config`.
5. The transcript shows that a person typed the command for this record: `readTypedCommand` answers `typed`.

Terminal conditions, all required: stdin is a terminal; `CI` is unset or empty; conditions 3 and 4 above. No transcript is read: there is no session. Only `drive.js` is run this way: the queue pull and `dispatch-resume.js` pass `stdinIsTTY: false`, so outside a session they answer `none`. `drive.js` run by the model inside a session takes the session conditions, so it needs the transcript check for that record. A Bash child of a session has `CLAUDECODE` and `CLAUDE_CODE_SESSION_ID` set and stdin not a terminal, in a Task subagent too (measured on 2026-11-16, Claude Code 2.1.325), so a model-run `drive.js` cannot take the terminal path.

**What a typed command stands in for.** The `auto:build` label, and nothing else. `ready` is still required, so the record was shaped. The risk flags are kept and the plan still owes their proof. `auto:merge` is never implied, so a typed run ends at `pending-review` for a person to read. Every gate a granted record passes still runs. It does not replace the trust verdict of `/claude-tweaks:backlog refine`; decision 0.2 accepts that for a record the maintainer names, as `/claude-tweaks:flow #N` already does. In a list, each number is named by the person and is judged on its own.

**The pointer.** `{ "v": 1, "sessionId": "<id>", "records": { "<n>": { "promptId": "<id>", "at": "<ISO time>" } } }`, written to a temporary name in the same directory and renamed. `typed-command.js` holds the one writer and the one reader; the hook and the three callers hold no path or pattern of their own. No caller names the file, so the reader treats it as untrusted: it uses `lstat`, reads only a regular file of at most 64 KiB, and never follows a link. It carries no path. A missing file or entry is the ordinary case and is reported as "no typed command on record for #N".

**The transcript check.** `readTypedCommand` runs these steps in order. The first that fails is the answer.

| Step | Requirement | Reason when it fails |
|---|---|---|
| 1 | `env.CLAUDE_CODE_SESSION_ID` is 1 to 64 characters of `[A-Za-z0-9-]` | `no-session-id` |
| 2 | the pointer is a regular file of at most 64 KiB that parses to the shape above | `no-pointer` when absent, else `pointer-unreadable` |
| 3 | its `sessionId` equals the reader's | `pointer-other-session` |
| 4 | it has an entry for the record, with a well-formed `promptId` and `at` | `no-pointer` when absent, else `pointer-unreadable` |
| 5 | `at` is not later than `now` and not older than `TYPED_DISPATCH_MAX_AGE_MS` | `expired` |
| 6 | `locateTranscripts({ sessionId, configDir, homeDir })` returns exactly one file, and its basename is `<sessionId>.jsonl` | `no-transcript` |
| 7 | the file reads to its end | `transcript-unreadable` |
| 8 | at least one candidate row exists | `no-prompt-row` |
| 9 | a candidate row passes the row test | `not-typed`, `other-command` or `expired` |

A candidate row is a line that parses to an object with `type: "user"`, a `promptId` equal to the pointer's, a `sessionId` equal to the reader's, `isSidechain` not `true`, `message.role: "user"`, and a `message.content` that is not an array holding a `tool_result` block. A line that does not parse is skipped.

The row test has three parts, all required:

- Markers: `turnOrigin` is the string `human`; `origin` is an object whose `kind` is the string `human`; the `isMeta` key is absent or `false`; the `promptSource` key is absent or the string `typed`; none of the keys `scheduledTaskId`, `scheduledFireId`, `wakeupSource` and `queueSkipSlashCommands` is present. Every measured scheduled row carries `scheduledTaskId` (59 of 59), 686 of the 689 peer rows carry `queueSkipSlashCommands`, and none of the 176 dispatch command rows carries any of the four. So a version that marked a delivered row human would still be refused by them.
- Command: `message.content` is a string that is, whole, `<command-message>claude-tweaks:dispatch</command-message>`, a newline, `<command-name>/claude-tweaks:dispatch</command-name>`, a newline, `<command-args>ARGS</command-args>`, with `ARGS` on one line; and `parseTypedDispatch("/claude-tweaks:dispatch " + ARGS)` names the record.
- Time: `timestamp` parses, is not later than `now` and is not older than the bound.

The answer is `typed` when any candidate passes all three. Otherwise the reason is `expired` when a candidate passed markers and command, else `other-command` when a candidate passed markers, else `not-typed`.

Decided 2026-11-16: the check accepts one row shape, the command form marked human, because that is what all 176 measured dispatch rows are. A plain-text row a person typed that holds the command line is refused (`other-command`): the slash command was not run as a command. `promptSource` may be absent, as measured, or `typed`, the value the same versions write on a typed plain prompt; `queued` and every other value refuse.
Decided 2026-11-16: the command, the record number and the time are read from the transcript row, not from the pointer. The pointer supplies only the prompt id and a cheap early exit on age. So a pointer written by hand that names a prompt a person typed for something else gains nothing: the row is not a dispatch command for that record. `promptId` is shared inside a turn, which is why the row is matched on its content as well as its id.
Decided 2026-11-16: the transcript is found by session id alone and never by the working directory or by a path from the pointer. A session keeps its transcript under the slug of its launch directory, so a lookup by the current directory misses it from a worktree. Exactly one file must be found; a session id with two files is refused. The config directory is `env.CLAUDE_CONFIG_DIR` when it is not empty, else `.claude` under the home directory, the resolution `locateTranscripts` already applies. `locateTranscripts` resolves links and keeps only a file whose real path is inside the real projects root, so a linked `projects` directory is read and a `{id}.jsonl` link that leaves the root is not.
Decided 2026-11-16: the check carries no list of Claude Code versions. It reads fields; a version whose rows lack them, rename them or give them another value is refused by the row test. A version that keeps the names and changes their meaning is what the parked record's re-run looks for.
Decided 2026-11-16: the check does not wait or retry. A row that is not in the file yet reads as `no-prompt-row` and the label stays required. Deliverable 1 records whether the row was there at the turn's first Bash call.

The row reader is synchronous, because `run()` in `queue-pull.js` and in `dispatch-resume.js` is synchronous (checked on 2026-11-16). It is a new exported function in `plugin/bin/lib/timing/transcript.js`, `readPromptRows(filePath, promptId, { fsImpl })`: it reads the file in fixed-size chunks, splits lines, parses only a line that contains the prompt id, and returns the parsed rows. It never loads the file whole. `readUsage` in that module is asynchronous and returns usage rows without these fields, so it is not the function to call; `locateTranscripts` and `statTranscriptOrThrow` are.

A typed command is not consumed. It stands for "the maintainer typed this record's number into this session" until it ages out, so the queue pull, a later `drive.js` call from the same session and `dispatch resume` all get the same answer.
Decided 2026-11-16: the bound is 30 minutes, counted from the transcript row's `timestamp`, and the typed command is still not consumed. It has to last only from the typed prompt to the admission that follows it; the dispatch step before the pull is given 150 seconds. A failed run is retried by typing the command again, which writes a new pointer. Authority is re-derived at every use from the record's live labels: a record that lost `ready`, or gained `bot:blocked`, `bot:parked` or `parked`, is refused by the rule or by the gate that already refuses a granted record in that state (AC15). A call the model starts inside the 30 minutes gets the answer the typed command got; that is accepted. The answer has three callers, the ones in Deliverables 5 to 7. A new caller calls `resolveBuildAuthority` and never reads the pointer or the transcript itself.

**What this guards against, and what it does not.** The environment conditions refuse a routine, a headless worker and a hub's headless run, and condition 4 refuses a session a launcher opened and marked. The model's own Skill call fires no hook and leaves no pointer. A prompt the model scheduled and a message another session delivered, a hub answer included, leave a pointer and are refused by the transcript check. Three things it does not stop, stated in `docs/hooks.md` in these terms:

- A session that appends a forged row to its own transcript and writes a pointer to it by hand. Nothing stops a session that adds the label by hand today.
- A launcher that sets neither `CC_POSTURE` nor `CC_LAUNCHED_BY`, gives the session a terminal and puts the command on the launch line, unless the probe finds a field for it (Deliverable 1). Condition 4 passes when no launcher variable is set, so a launcher is covered only once it marks its sessions. `cc` is covered by thn-inc/claude-user-config#50, whose body fixes the two values and says "add values, never rename"; that repository owns the name and the values, and this plugin only reads them.
- A wrapper that gives `drive.js #N` a terminal outside a session.

**Sites.** The four refusals in Current State are the only gates on the label. Other readers of `facets.grants.build` (`plugin/bin/lib/issues/backlog.js`, `pending-authorization.js`, `plugin/bin/lib/dispatch/stuck-open-pr.js`, `plugin/bin/lib/record-graph/encode.js`, `materialize-format.js`) report or sort and do not change.
Decided 2026-11-16: this record retires an invariant: a record being built may now carry no `auto:*` label, and `plugin/skills/_shared/work-record.md` says so. One consumer is fixed here. `plugin/skills/dispatch/settle-and-merge.md` step 6 removes `auto:build` without reading the labels first; removing an absent label fails the whole edit (measured by the first build), so `bot:blocked` would not land (AC16). AC11 covers the code this record adds. What `/claude-tweaks:backlog` shows for a typed record at `pending-review` is reported, not changed (AC17). No permanent source scan for other label readers is added: the three gates call the one rule and their tests show it.
Decided 2026-11-16: the build runs one audit as a plan step, because the retired invariant has more readers than the gates. `git grep -n -E "auto:build|grants\.build" -- plugin` matched 72 files on `main` on 2026-11-16, 17 under `plugin/bin` and 55 under `plugin/skills`. The PR lists every hit that removes a grant label or acts on a record a run has claimed, each marked `reads live labels`, `best-effort per label`, `report only` or `fixed here`. The removal sites known today each get a row: `release-claim.js --remove-grants`, `plugin/bin/lib/reconcile/release-merged.js`, Settle steps 3 and 6 and `plugin/skills/build/plan-review.md`. A site outside the Key Files that would fail or mislead for a claimed record with no grant is filed through `/claude-tweaks:capture` with a spec-shaped body, not fixed here.

**Queue pull.** The named records are added after the pool fetch and before the first pass, so the passes and their registry are untouched and no exclusion reason is added. The filter at line 425 accepts a record the rule answered `typed` for. `--run` is resolved by `resolveTarget` in `plugin/bin/lib/log-decision/append.js`, the guard `log-decision.js` already uses; no second guard is written. The retained script in `plugin/skills/dispatch/queue-pull-script.md` gets nothing: it has no `--named`.

**Driver and #5232.** #5232 (open, not built) hands a singleton from dispatch to `drive.js --check #N`. With this record the driver runs the same check through the same rule, so that route needs no extra flag for a typed record.
