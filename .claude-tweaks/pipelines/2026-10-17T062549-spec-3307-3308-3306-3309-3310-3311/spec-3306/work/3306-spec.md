# 3306: Add the skill-size rail: budgets.js plus read-limit checks for skill files, bundles, and descriptions

Surface: infra

**Related:** #3304

## Overview

Adds `plugin/bin/lib/skill-audit/budgets.js`, the single source of truth for every skill-size number. Adds with it the one blocking size check that replaces the `CEILING_BYTES` cliff: a **rail** derived from the Read tool's limits (25,000 tokens and 2,000 lines, Claude Code 2.1.283), applied to every shipped skill `.md` file and to every composed bundle at a compose call site, plus a per-description cap at the CLI's 1,536-char skill-listing max.

This is the expand step of the strangler-fig rollout tracked by parent #3305: the rail is added **alongside** today's gates. `CEILING_BYTES`, the 260/8,700-char description ceilings, and every existing assertion stay untouched here; #3310 (cutover) and #3311 (decommission) remove them. The principle: a size limit blocks CI only where it guards a real platform limit. A file over 25,000 tokens cannot be read in one Read call ("File content (N tokens) exceeds maximum allowed tokens (25000). Use offset and limit parameters…"), and Read returns at most 2,000 lines without offset/limit. Skill files get both rails. A composed bundle is consumed by a single Read of `$PIPELINE_RUN_DIR/context/{step}.md` (e.g. `/flow` reads `$PIPELINE_RUN_DIR/context/manifesto.md` after composing it), so it gets the byte rail. Its line count is bounded by the sum of its sources' lines and sits far below 1,600 today, so the line rail is checked per source file only.

The rail sits at 80% of the cap, about twice today's largest file (46,248 B, `plugin/skills/dispatch/queue-pull-script.md`; longest file 670 lines). What stops the merge race is not the margin alone. Files stop clustering just under a cliff that work targets, as 19 files did under 40,960 B, so no plausible pair of concurrent PRs crosses the rail. The exact margin is a judgment call, recorded as such.

## Technical Approach

`budgets.js` holds constants plus two pure helpers, and does no I/O. The live-corpus tests use `context-cost.js`'s existing enumeration (`measureSkills`, `measureSubFiles`, `composedBytesReport`, `measureDescriptions`) and compare against `budgets.js`. Byte measurement stays `measuredBytes` (CRLF-normalized, marker-stripped). Line counts come from the same normalized text (`text.split('\n').length`).

`DESCRIPTION_MAX_CHARS` carries no `RAIL_RATIO` margin, on purpose. The CLI counts description characters exactly, so there is no estimation error to absorb. The byte and line rails carry the margin because `BYTES_PER_TOKEN` is an estimate.

### Data / API Surface

```js
// plugin/bin/lib/skill-audit/budgets.js
READ_TOKEN_CAP          // 25000 — Read tool default cap (Claude Code 2.1.283)
READ_LINE_CAP           // 2000 — Read returns up to 2000 lines without offset/limit
BASH_OUTPUT_CAP_CHARS   // 30000 — Bash inline output cap; informational, NOT a rail (skill prose instructs Read, never cat)
RAIL_RATIO              // 0.8
RAIL_TOKENS             // Math.floor(READ_TOKEN_CAP * RAIL_RATIO)
RAIL_LINES              // Math.floor(READ_LINE_CAP * RAIL_RATIO)
BYTES_PER_TOKEN         // calibrated (Task 0), rounded down to 1 decimal
RAIL_BYTES              // Math.floor(RAIL_TOKENS * BYTES_PER_TOKEN)
DESCRIPTION_MAX_CHARS   // 1536 — skillListingMaxDescChars default; exact count, no margin
LISTING_BUDGET_FRACTION // 0.01 — skillListingBudgetFraction default
LISTING_CHARS_PER_TOKEN // 4
listingBudgetChars(contextTokens) -> Math.floor(contextTokens * LISTING_CHARS_PER_TOKEN * LISTING_BUDGET_FRACTION)
overRail(entries: Array<{file|name, bytes, lines?}>) -> entries.filter(e => e.bytes > RAIL_BYTES || (typeof e.lines === 'number' && e.lines > RAIL_LINES))
```

## Gotchas

- Two more platform limits were verified on 2026-10-16. **Read returns at most 2,000 lines** without offset/limit; that is the `RAIL_LINES` rail. **Bash output is capped at 30,000 characters** inline (overflow is saved to a file and previewed). That cap is why #611 saw a 34.3 KB file "truncate" when read with `cat`. It is deliberately **not** a rail: skill prose instructs the Read tool, and a 30,000-char rail would sit below files shipping today. Export it with a comment saying so, so nobody re-derives a "single-read ceiling" from a `cat` truncation again.
- Calibrate with the Read tool in the build session itself. Its token count is the counter the cap applies to. A guessed ratio (e.g. "4 bytes/token") is exactly the kind of unverified constant this redesign removes. If Read cannot be invoked, stop and report; never fall back to a guess.
- The calibration is a point-in-time snapshot against one CLI version. Re-run Task 0 when a Claude Code release changes the Read limits or the tokenizer. #3304 tracks drift checks on Claude Code behavior this repo depends on, and the 20% rail margin absorbs small tokenizer drift in the meantime.
- Write calibration samples to the session scratchpad, never `/tmp` (Bash writes under `/tmp` do not persist across calls in this harness) and never inside the repo.
- `measureDescriptions` takes the plugin root (`plugin/`). Passing the repo root throws `ENOENT … /skills`.
- Today's description total (8,616) already exceeds `listingBudgetChars(200000)` (8,000), before counting other plugins' skills. The diagnostic surfaces that; deciding what to do about it is out of scope here.
- Prove each new assertion discriminates: run it once against a fixture that must fail, and see red before trusting green.
