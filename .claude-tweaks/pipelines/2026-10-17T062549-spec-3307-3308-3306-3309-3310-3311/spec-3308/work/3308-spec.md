# 3308: Add a corpus-relative size-outlier signal to the bloat scan

Surface: infra

## Overview

Adds a corpus-relative **size-outlier** signal to `bloat.js`, the mechanical bloat detector that `/claude-tweaks:harness-health` runs over a target skill file (and `/wrap-up` and `/init` run through `_shared/harness-health-analysis.md`). Today its size signal is "over the 50 KB soft ceiling" (`CEILING_BYTES`), an absolute number that became a target. The replacement asks a coherence question instead: is this file much larger than its siblings? That is the "this file is doing too much" smell, judged against the corpus the file actually lives in, so a consumer project is judged against its own distribution and not against this plugin's.

The threshold has **two tiers**, so small corpora still get a signal:

| Corpus files (after dedup) | Threshold | Why |
|---|---|---|
| ≥ 20 | 95th percentile (nearest-rank) | Enough files for a percentile to mean something |
| 5–19 | 3 × the corpus median | Under 20 files a nearest-rank p95 is the largest file itself, so it could never flag anything. A median multiple is the statistic the existing long-row signal already uses (`ROW_LENGTH_MULTIPLE` × median) |
| < 5 | none: `NO BASELINE` | Too few files to call anything an outlier |

This is the expand step of parent #3305's strangler-fig rollout. `sizeOutlier` is added **beside** the existing `overCeiling`/`headroom` fields, and both judging procedures learn to weigh it as dimension-9 evidence. #3310 (cutover) stops citing the 50 KB ceiling in that prose; #3311 (decommission) deletes `overCeiling`, `headroom`, and the `ceiling` option.

Terminology: `hasFindings` (the report helper) counts `sizeOutlier` the same way it counts `overCeiling` today. It means "this file has evidence lines to print". It does **not** make the signal a filed finding: like the other three bloat signals, `sizeOutlier` is evidence the judge weighs, never a record on its own, and nothing here blocks CI.

## Acceptance Criteria

1. **p95 tier.** For 20 fixture files sized 1,000 B … 20,000 B in 1,000 B steps, `auditCorpus(...).sizeBaseline` is `{ usable: true, sample: 20, method: 'p95', threshold: 19000 }` (nearest-rank, the 19th value), and only the 20,000 B file has `sizeOutlier: true`.
2. **Median tier.** For 10 fixture files, nine of 1,000 B and one of 5,000 B, `sizeBaseline` is `{ usable: true, sample: 10, method: 'median-multiple', threshold: 3000 }`, and only the 5,000 B file is an outlier.
3. **Floor.** With 4 files, `sizeBaseline.usable === false`, `method === null`, no file has `sizeOutlier: true`, and the report contains `size baseline: NO BASELINE`.
4. **Boundary.** A file exactly at the threshold is not an outlier; one byte above is.
5. **Dedup.** A corpus list containing the target path twice (plus 19 distinct siblings) yields `sample: 20`, not 21.
6. **Suppression.** `bloatReport(target, corpus, { sizeOutlier: false })` never prints a `size-outlier:` line.
7. **Unchanged.** Every pre-existing `bloat.test.js` assertion passes unchanged, and `overCeiling` / `headroom` are still returned with today's values.
8. **Prose twin.** Both prose files' signal lists name the same five signals, and both carry the new guard bullet, pinned by the conformance assertion.
9. `npm test` passes.

## Release Note

Health checks now flag a skill file that is much larger than its siblings, judged against the project's own skills rather than a fixed byte limit.

## Technical Approach

Nearest-rank percentile, deterministic and dependency-free: sort the byte sizes ascending, then `threshold = sizes[Math.ceil(0.95 * n) - 1]`. The median tier uses the existing `median()` helper, so the row and size signals compute "median" the same way. Measure with the raw `fs.statSync().size` that `auditCorpus` already uses, so the baseline and the reported bytes agree. `sizeBaseline` mirrors the row baseline's result shape (`usable`, `sample`); "parallel" refers to that shape, not to the statistic.
