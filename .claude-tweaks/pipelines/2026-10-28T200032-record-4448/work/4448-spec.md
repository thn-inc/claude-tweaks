# 4448: Write gate misses a write behind a NAME=value, env or sudo prefix

**Related:** #4303, #4244

Origin: /claude-tweaks:build of #4303 (run 2026-10-25T143627-spec-4303), SDD Task 2 parked finding and final-review ruling

Defer-reason: genuinely-larger

## Current State

In `plugin/bin/lib/hooks/git-command.js`, a NAME=value assignment prefix, an `env` prefix or a `sudo` prefix hides every write shape. Each of these resolves `[]`, while bash 3.2 and 5 write or commit in the main checkout:

- `X=1 cp a /main/f.js`
- `sudo cp a /main/f.js`
- `X=1 tee /main/f.js`
- `X=1 sed -i s/a/b/ /main/f.js`
- `cd M; x+=1 git commit -m x` and `x+=1 git -C M commit -m x`

A quoted name goes the other way. `"x"=1 cd /main` is read as an assignment plus a cd, but bash 3.2 and 5 run `x=1` as a command ("command not found") and stay put. That is a fail-open: from the main checkout, `"x"=1 cd /wt; cp a f.js` resolves only `/wt/f.js`, while bash writes the main checkout's `f.js`.

Compound keywords and the `builtin`/`command`/`pushd` prefixes are #4244's scope, not this record's. While in visitSegment, also replace the `while ((next = …) > cdLead)` assignment-in-condition loop (`git-command.js:~736`) with a plain loop.

## Deliverables

1. Skip leading NAME=value and NAME+=value words, and the `env [-i] [NAME=value…]` and `sudo [opts]` prefixes, before reading the write-shape, git and cd lead.
2. Read a quoted-name assignment as bash does.
3. Pin each shape with its bash 3.2 and 5 verdicts.

## Acceptance Criteria

- Every shape above resolves the path bash writes, so the write gate denies it from a worktree of a worktree-always repo.
- `"x"=1 cd /main` resolves no cd, so `"x"=1 cd /wt; cp a f.js` from the main checkout resolves the main checkout's `f.js`.
- The base comparison is clean apart from the listed shapes.
- Each rule has a red-turning mutant.
- The four scanner suites pass.

## Release Note

The worktree-always guard now blocks a write into the main checkout behind a NAME=value, env or sudo prefix.
