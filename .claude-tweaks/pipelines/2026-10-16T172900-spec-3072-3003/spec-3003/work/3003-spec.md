# 3003: test: a dispatched group's second call re-runs the first call's QA at an unchanged HEAD

Surface: infra

## Current State

`/claude-tweaks:dispatch` hands a record to `/claude-tweaks:flow` in two calls: `build,test`, then `review,polish,wrap-up`. In the second call `/flow` auto-inserts `test` before `review`. That `test` run reaches `plugin/skills/test/SKILL.md`'s pipeline branch "runner stamp verifying `HEAD`" (`SKILL.md:73`): it skips verification, then selects QA stories by `source_files` ∩ the changed-file set from `verify.js --changed-files --integration-branch {ref}` (`SKILL.md:70`).

When the stamp's anchor equals HEAD, that changed-file set is the whole branch diff, not an empty set. This is deliberate since #2486: `resolveBase` in `plugin/bin/lib/verify/changed-files.js:54-77` runs with `requireNonDegenerate: true` from `plugin/bin/verify.js`'s `changedFilesMode` (`verify.js:157-171`). It skips an anchor identical to HEAD whenever `--integration-branch` is given, and falls through to the merge-base. `test/SKILL.md:120` still says "the stamp's `fullSha` wins whenever it is still an ancestor of HEAD", which no longer describes the `--integration-branch` call it sits next to.

Nothing records that QA already passed at a given commit. The verification stamp (`{git-dir}/claude-tweaks-verify-pass.json`, `verification.md:132`) covers types/lint/tests only. The QA run directory (`.claude-tweaks/artifacts/screenshots/qa/{timestamp}_{hex}`, `qa-procedures.md:71-73`) is supposed to receive `{RUN_DIR}/report.json` at Phase 5 (`qa-reporting.md:74`), but in the reported run (plugin 6.136.0) the first call's QA run directory held only screenshot folders. The second call had no artifact to read, so it re-dispatched all fourteen affected stories on the same commit.

## Deliverables

1. **QA pass stamp.** When a pipeline QA run passes with every selected story green, write a QA pass stamp bound to the commit: `{sha, dirty, stories: [ids], storiesDir, at, reportPath}`. Write it in the checkout's own git dir, next to the verification stamp and with the same per-worktree, never-tracked posture, so both dispatch calls in one worktree read it. A dirty tree or any failed or skipped story writes no stamp.
2. **QA skip on a covering stamp.** In `test/SKILL.md`'s pipeline story selection (both the `VERIFICATION_PASSED=true` branch and the runner-stamp-verifies-HEAD branch), check for a QA pass stamp first. When its `sha` equals HEAD, the tree is clean, and every story the selection would run is in the stamp's `stories` list, skip QA. Report `QA: skipped — stories already passed at {short-sha}`, set `TEST_PASSED=true`, and log one `AUTO` line per `_shared/auto-decision-log.md`. Any mismatch runs the normal selection unchanged.
3. **Correct the base-resolution prose.** Rewrite `test/SKILL.md:120`'s "the stamp's `fullSha` wins whenever it is still an ancestor of HEAD" clause so it matches #2486's behavior: under `--integration-branch`, an anchor equal to HEAD falls through to the integration-branch base.
4. **Find why `report.json` was missing.** Determine why the first call's QA run directory held no `report.json`, and either fix the path so Phase 5 always writes it on a pipeline run, or state in the PR why the reported run took a path that legitimately skips it.

## Acceptance Criteria

- A test drives the QA-skip decision with a stamp whose `sha` equals HEAD on a clean tree and a selected story set contained in the stamp's `stories`, and asserts the skip. Variants with a different `sha`, a dirty tree, or one selected story missing from the stamp each assert that QA runs. Prove the skip case goes red against today's behavior.
- A test asserts that a failed or partially-skipped QA run writes no QA pass stamp.
- `verify.js --changed-files --integration-branch` behavior is unchanged: the existing #2486 tests in `tests/` pass without edits.
- `test/SKILL.md`'s `affected` bullet no longer claims the stamp anchor always wins, and a conformance assertion pins the corrected clause.
- `npm test` passes in full.

## Release Note

A dispatched record's second pipeline call no longer re-runs QA stories that already passed on the same commit.

## Technical Approach

Model the QA stamp on the verification stamp (`verification.md:132`): a small JSON file in the git dir, written by deterministic code, not by agent prose. That means a `bin/` writer/reader (or an extension of an existing `bin/lib/verify/` module) that the test skill calls after Phase 5 and before story selection. Keep the skip rule a pure function (stamp, HEAD, dirty, selected ids → skip or run) so the tests above drive it without git or a browser. Leave `--changed-files` alone: #2486's degenerate-anchor fall-through is correct for "what differs from the integration branch". The QA question is a different one, answered by the new stamp.

### Key Files

- `plugin/skills/test/SKILL.md` — pipeline story-selection bullets (`:70`, `:73`) consult the QA pass stamp; `affected` bullet prose (`:120`) corrected
- `plugin/skills/test/qa-reporting.md` — Phase 5 writes the QA pass stamp after a fully green run; `report.json` write path
- `plugin/skills/test/qa-procedures.md` — QA run-dir generation (`:71-73`), the point where the stamp check slots in
- `plugin/bin/lib/verify/changed-files.js` — reference only for the #2486 degenerate-anchor rule; not modified
- `plugin/bin/verify.js` — home for a QA-stamp read/write mode, or reference only if a new `bin/` module is added instead

## Gotchas

- Do not "fix" `--changed-files` to return an empty set when the anchor equals HEAD. #2486 made that fall-through deliberate because an empty diff looked like a clean result to callers asking the integration-branch question.
- A QA pass is only reusable for the same story definitions. If story YAML under `STORIES_DIR` changed since the stamp was written, the stamp must not cover it. Either include a content hash of the selected story files in the stamp, or treat any story-file change in the working tree or since `sha` as a mismatch.
- The verification stamp lives per worktree. Both dispatch calls run in the same group worktree, so a git-dir stamp reaches the second call. A run-dir stamp would not, because each `/flow` call may resolve its own run directory.
- ASSUMPTION — verify at build: the missing `report.json` came from an early exit or interrupted Phase 5 rather than from a path that never writes it — confirm by tracing `qa-reporting.md` Phase 5 from the pipeline entry and reproducing one dispatched `build,test` call.

## Original request

test: a dispatched group's second call re-runs the first call's QA at an unchanged HEAD

**Summary:** In `/dispatch`'s two-call hand-off, the second call's auto-inserted `test` step skips verification on the runner stamp but re-runs every affected QA story, even when HEAD is exactly the commit the first call's QA passed on.

**Kind:** Defect

**Affected component:** `/claude-tweaks:test` (pipeline QA selection), as reached through `/claude-tweaks:dispatch`'s two-call gate and `/claude-tweaks:flow`'s auto-inserted `test`

**Repro steps:**
1. Dispatch a record with a web surface and QA stories whose `source_files` overlap the diff.
2. The first call (`build,test`) passes verification and QA; HEAD carries a full runner stamp.
3. The second call (`review,polish,wrap-up`) starts with no commits in between; `/flow` auto-inserts `test` before `review`.
4. `verify.js --stamp-status` reports `verifiedHead: true` with `fullSha` equal to HEAD. `verify.js --changed-files --integration-branch <ref>` returns the merge-base as `base` and the whole branch diff as `files`.

**Expected vs. actual:**
Expected: QA that already passed on this exact commit is recognised — either through a QA pass artifact bound to the SHA, the way the verification stamp is, or because the changed-file set since the last full pass is empty.
Actual: the whole affected-story set is dispatched again. `test/SKILL.md` says the stamp's `fullSha` wins as the base whenever it is an ancestor of HEAD, but with `fullSha` equal to HEAD the tool returned the merge-base. The first call also left no `report.json` in its QA run directory (only screenshot folders), so the second call had no artifact to read the earlier result from and could not treat the first call's `decisions.md` line as evidence. In the run that surfaced this, fourteen stories ran twice on the same commit.

**Definition:** Clear

**Plugin version:** 6.136.0
