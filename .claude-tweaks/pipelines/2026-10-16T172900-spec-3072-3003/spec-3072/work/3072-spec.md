# 3072: verify.js: a scoped re-verify after merging the integration branch mid-run selects every suite the merged-in files touch

Surface: infra

## Current State

`verify.js --scope` picks its base through `resolveBase` (`plugin/bin/lib/verify/changed-files.js:54-89`). A usable stamp anchor (the last full pass) always wins (`:62-77`). `--integration-branch` is consulted only when no usable anchor exists, or, for `--changed-files` callers that set `requireNonDegenerate`, when the anchor equals HEAD (`:72-76`, #2486). The `--scope` call site (`plugin/bin/verify.js:273`) never sets that flag. So once a full pass is stamped, the scoped change set is always `anchor..HEAD`, and passing `--integration-branch` changes nothing.

`--base` is refused outright when it differs from the anchor (`verify.js:300-302`). The refusal message suggests `--integration-branch` instead, which, per the above, has no effect while the anchor is usable.

The gap this creates (observed; original request below): a `/claude-tweaks:flow` run recorded a full pass at A. It then merged `origin/develop` into its branch during review, and re-verified review fixes with `--scope`. `anchor..HEAD` contained 133 files, 123 of them from the merge and byte-identical to the integration-branch tip. All UI suites were selected (about 37 extra minutes), although the branch's own changes were Python-only. `verify.js --changed-files --integration-branch develop` with no anchor returns exactly the 10 own-work files.

`plugin/skills/test/verification.md`'s "Re-verify scoping (#1923)" table (line 64) says the review-fix re-verify is "scoped". Its scoped invocation passes `--integration-branch {ref}`, but the section never says that the flag is ignored while an anchor is usable.

## Deliverables

1. In `verify.js --scope`, when `--integration-branch {ref}` is given, a usable anchor exists, and HEAD's history contains a merge commit made after the anchor whose other parent is reachable from `{ref}`: narrow the scoped file set. It becomes `changed(anchor..HEAD)` intersected with `changed({ref}..HEAD)`, where the second set is the paths whose content at HEAD differs from the integration-branch tip. Files that arrived through the merge, unchanged from the integration tip, drop out. When no such merge exists, behavior is unchanged.
2. Report the narrowing so a reader can audit what was skipped. Add the count of excluded merge-identical paths, and the integration ref used, to the scope's `report.json` entry and to the existing `AUTO … Verification scoped` decision-log line format in `plugin/skills/test/verification.md`.
3. Fix the `--base` refusal message (`verify.js:301`) so it no longer implies that `--integration-branch` overrides the anchor. Name the merge-narrowing behavior instead.
4. Update `verification.md`'s "Re-verify scoping" section with one paragraph: after an integration-branch merge, the scoped invocation's existing `--integration-branch {ref}` narrows the set to the branch's own delta. No call-site changes are needed, since every scoped site already passes the flag.
5. Add tests in `tests/bin-lib/verify/changed-files.test.js`, or a new `scope` test beside it, using a temporary git repo fixture:
   - anchor, then integration-branch merge, then own-work commit, selects only own-work paths;
   - no merge after the anchor leaves the selection unchanged;
   - a merged-in path the branch then edited stays selected.

## Acceptance Criteria

- In a fixture repo, given a full-pass anchor at A, a merge of the integration branch adding N files, and one own-work commit touching 1 file, `verify.js --scope … --integration-branch {ref}` selects only that 1 file's suites. `report.json` records N excluded merge-identical paths.
- In a fixture with no integration-branch merge after A, the selected file set equals `anchor..HEAD`, identical to current behavior.
- A file that came in through the merge and was then modified by the branch remains in the selected set.
- Without `--integration-branch`, a `--scope` run's selection is unchanged in every fixture.
- The `--base` refusal message no longer says `pass --integration-branch instead`. `verification.md` documents the post-merge narrowing in the Re-verify scoping section.
- `node --test tests/bin-lib/verify/*.test.js` passes.

## Release Note

Fix scoped re-verification after merging the integration branch mid-run: only the branch's own changes now select suites, not every file the merge brought in.

## Technical Approach

Keep `resolveBase`'s anchor-first contract intact. The anchor still bounds "what changed since the last full pass", and the `base === fullSha` invariant `verify.js` relies on (`:287-297`) is untouched. Add the narrowing as a filter after `changedFiles({ base: resolvedBase })` (`verify.js:306`): compute `git diff --name-only -z {ref} HEAD` and intersect. Detect the post-anchor merge with `git rev-list --merges {anchor}..HEAD`, checking whether any merge's second parent is an ancestor of `{ref}`. Use `preferOriginRef` the same way `resolveBase` does, so `{ref}` resolves identically.

### Key Files

- `plugin/bin/verify.js` — narrowing filter after `changedFiles` under `--scope`; `--base` refusal message (`:301`)
- `plugin/bin/lib/verify/changed-files.js` — reused `resolveBase`/`changedFiles`/`preferOriginRef`; possible helper for the merge detection
- `plugin/skills/test/verification.md` — Re-verify scoping section and the scoped decision-log line format
- `tests/bin-lib/verify/changed-files.test.js` — fixture tests for the narrowing

## Gotchas

- Merge-identical files are excluded on the premise that the integration tip already passed its own CI. A semantic interaction between the branch's changes and merged-in files can still exist. The narrowing is a deliberate tradeoff that `report.json` must make visible (Deliverable 2), never a silent skip.
- #3048 (ready) adds an `--ignore-stamp` flag to `verify.js --changed-files` and also edits `changed-files.js`'s base resolution. Expect a Key Files overlap; whichever lands second rebases onto the other's `resolveBase`.
- Do not change the `--changed-files` (`requireNonDegenerate`) path's semantics here; that is #2486's and #3048's territory.

## Original request

verify.js: a scoped re-verify after merging the integration branch mid-run selects every suite the merged-in files touch

**Summary:** After a run merges its integration branch into its own branch, `verify.js --scope` stays anchored on the pre-merge full pass and selects every suite the merged-in files touch, with no sanctioned way to scope to the branch's own delta.

**Kind:** Gap

**Affected component:** bin/verify.js (`--scope` / stamp anchor), test/verification.md "Re-verify scoping"

**Use case:**
A `/claude-tweaks:flow` run (pr-first, worktree) recorded a full verification pass at commit A. During `/claude-tweaks:review`, the run merged `origin/develop` into its own branch so a review fix could see a method develop had just added. It then re-verified the review fixes with:

    verify.js --cmd tests=... --cmd ui-static=... --cmd ui-unit=... --cmd ui-build=... --cmd ui-e2e=... --scope .claude-tweaks/verify-scope.json

The scope stayed anchored on the pre-merge full pass A and reported "Scope: full — 133 changed file(s) since A; suites: all". 123 of those files arrived through the integration-branch merge. They were byte-identical to the integration branch tip, which had already passed CI on its own PRs. The branch's own changes touched only Python files, but the run paid for every UI suite, roughly 37 extra minutes for the e2e and UI build.

Trying to scope to the run's own work instead was refused:

    verify.js ... --scope .claude-tweaks/verify-scope.json --base origin/develop
    --scope: --base origin/develop conflicts with the stamp anchor <A>; omit --base (pass --integration-branch instead) or clear the stamp

`verify.js --changed-files --integration-branch develop` with no anchor yields exactly the run's 10 own-work files, so the information to scope correctly is already there.

There is no sanctioned way to re-verify "the delta this branch introduces relative to the integration branch it just merged" once a stamp anchor exists. Neither `test/verification.md` nor the refusal message says whether `--integration-branch` overrides the anchor. The only options left are clearing the stamp (losing the anchor) or running every suite the merge touched.

Suggested direction: when HEAD's history contains a merge of the integration branch made after the anchor, compute the scoped change set as anchor-delta minus the files whose content equals the integration-branch tip. Equivalently, re-anchor on the merge-base with the integration branch when that merge-base descends from the anchor. Alternatively, document in `test/verification.md`'s re-verify scoping table which flag to pass after an integration-branch merge.

**Definition:** Clear

**Plugin version:** 6.137.0

## Build-time deviations (Common Step 4.5, Beneficial)

- **Deliverable 1 — pre-anchor branch edits are never trusted.** Beyond `changed(anchor..HEAD) ∩ changed({ref}..HEAD)`, the kept set also includes every path the branch touched as of the anchor (`merge-base(anchor, ref)..anchor`), and the `{ref}..HEAD` diff runs with `--no-renames`. Whole-branch review reproduced two cases where the literal intersection rule excluded paths the branch itself changed (a deletion paired as a rename; a conflict resolved in `{ref}`'s favour), leaving an empty set that stamped HEAD verified with zero checks run. Commit 19beefc3c.
- **Deliverable 2 — the report names the excluded paths, not just the count.** `report.json` `scope.mergeNarrowing` is `{ref, excluded, excludedFiles}` and stdout carries a `merge-narrowed:` line, so an auditor can see exactly what was skipped. Commit 278a23519.
