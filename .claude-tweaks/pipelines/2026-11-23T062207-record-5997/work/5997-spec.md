# 5997: Launch the driver implementer at the record's profile and retry once one profile up

Surface: backend
Risk-flags: public-contract

## Overview

Under `implementer-tier: record`, the pipeline driver launches its implementer worker on the profile the record rule picks (Fast for a `size:low` record with one or two Key Files, Standard otherwise) instead of `express-driver-models.implementer`. When the first worker reports it cannot complete, or the driver's test step finds red tests, the driver relaunches the implementer once, one profile up, on top of what the first attempt left, with the failure appended to its prompt. A second failure leaves the lane exactly as a first failure does today. Under `lane`, the default, the driver behaves as today.

Today a failed worker or a red test step ends the record's time in the driver lane: the record escalates to the standard lane, where a whole pipeline run starts over. A Fast first attempt is only worth trying if a cheap failure costs one more worker launch, not a full standard-lane run.

**Complexity:** Medium
**Estimated tasks:** 6

## Current State

- Launch: `plugin/bin/lib/driver/launch.js`'s `roleModel(role, policy)` reads the implementer's profile from `express-driver-models` and resolves it through `resolve()` (`plugin/bin/lib/model-profiles/profiles.js`) as an unattended launch, so `model-profiles` and `model-ceiling` apply; a role it cannot resolve throws `DRIVER_MODEL_REFUSED`. `launchTracked(shared, deps, ceilings, opts)` calls it with `opts.role` and returns `{ envelope, model }`.
- Worker step: `workerStep` in `plugin/bin/lib/driver/steps.js` calls `runImplementer(ctx, deps, {})`. A result of `cannot-complete` returns `status: 'stop'` (`worker could not complete: …`); a launch failure returns `status: 'fail'`. Its event line carries `tests` and `model`.
- Test step: `testStep` (`plugin/bin/lib/driver/steps.js`, a `pre-push` stop class) runs `verify.js` scoped; red tests stop the step and the run escalates the record out of the lane (`settle`'s escalate row, `plugin/bin/lib/driver/settle.js`).
- Fix-round precedent: the review step's one fix round (`plugin/bin/lib/driver/review.js`, `fixRound`) relaunches the implementer through `runImplementer` with `extraPrompt` appended to the first prompt, the first commit kept, and checks HEAD moved.
- Record facts: the admission step puts the record's labels on `ctx.issue.labels` and its Key Files on `ctx.keyFiles` (`plugin/bin/lib/driver/steps.js`, the admission call to `deps.evaluateAdmission`). `ctx.keyFiles` comes from `extractKeyFiles`, whose per-origin branches differ from the standard lane's count, so this record counts with #5996's `keyFileCount` on the record body instead.
- Step order: `STEPS` runs the worker step, then a commit step (the worker never commits; `runImplementer` treats a moved HEAD as a failure), then the test step, the check step and the review step. `fixRound` runs its own launch, then `commit.run`, then `test.run`.
- Event readers: `events.js` says fields may be added to an event, never renamed; it does not promise one `worker` line per run.
- Ceilings: `readCeilings` (`launch.js`) reads `express-driver-wall-clock-minutes` and `express-driver-spend-ceiling-dollars`; each launch gets them as `ceilings`.

Every other role is unchanged under both values. A throw from #5996's functions refuses the launch as `DRIVER_MODEL_REFUSED`.
- [ ] Under `record`, exactly two outcomes trigger a relaunch, once, at `stepUp(firstProfile)`, before any escalation: a worker step ending `cannot-complete`, and a test step ending red. A worker step ending `fail` (a launch error, a ceiling, a result that is neither `done` nor `cannot-complete`) never relaunches and leaves the lane as today.
- [ ] The relaunch is one helper in `plugin/bin/lib/driver/steps.js` that reuses `fixRound`'s wiring: launch through `runImplementer` with `extraPrompt`, then the commit step, then the test step. ## Acceptance Criteria

1. With `implementer-tier: record`, a `size:low` record with 2 Key Files launches its implementer on the Fast profile's model (`haiku` by default); with 3 Key Files, or a `size:high` record, on Standard's (`sonnet`).
2. With the key unset, and with `implementer-tier: lane`, the implementer launches on the model `express-driver-models.implementer` resolves to, as before this change, for every size.
3. With `record`, a first worker on Fast that returns `cannot-complete` after editing a file is followed by exactly one implementer launch on Standard's model, whose prompt contains the first worker's reason and whose worktree still holds that edit; the commit step and the test step then run.
4. With `record`, a red test step after a Fast first attempt is followed by exactly one implementer launch on Standard's model whose prompt names the failing test files, then the commit step, then a second test-step run; when that run is green the record continues to the check and review steps.
5. With `record`, a second failure after a relaunch, in each combination (red tests then `cannot-complete`, `cannot-complete` then red tests, red tests twice, red tests then a worker `fail`), produces the outcome word and escalation a single failure of the second kind produces with the key unset, its detail names the relaunch, and no further worker-or-test-step launch follows.
6. With `record` and `model-ceiling: fast`, a failed Fast first attempt is not relaunched, and its event line names the clamp.
7. With `record`, every implementer launch writes one worker line in `driver-events.jsonl` carrying `model`, `profile` and `attempt`, and the relaunch's line carries `escalatedFrom` and `trigger`.
8. With `record`, a first worker ending `fail` (a launch error, or a spend-ceiling stop) is not relaunched, and after a green relaunch the review fix round, when it runs, launches on the relaunch's profile.
9. `plugin/bin/lib/driver/worker.js`'s module header records a dated probe of three Fast workers' result envelopes under `--safe-mode --restricted`, with the model, the CLI version and the re-probe triggers.

## Decisions

**Decision (plan review Q1, red tests that change the worktree):** Reading A (user decision 2026-11-23, replacing the earlier Reading B). A red test step always triggers the relaunch, as Deliverable 2 and AC4 say, whether or not the test run left the worktree different from HEAD. There is no `tree-changed` no-relaunch case. The relaunch's commit step stages whatever git reports changed, test-written bytes included, and the second test run, `check`'s bounds and CI judge those bytes like any worker edit.

**Decision (plan review Q2, stepped-up profile does not resolve):** Reading A. When `resolve()` throws for the stepped-up profile (for example a `model-profiles` row naming an unknown model), it counts as a relaunch whose launch is refused: the stop is `DRIVER_MODEL_REFUSED`, no `worker` line is written for the refused relaunch, and the stop's detail names the relaunch. A misconfigured profile fails loudly instead of quietly skipping the step-up.

## Release Note

Made the pipeline driver start small records on the cheapest model and retry a failed attempt once on the next model up, before handing the record to the full pipeline.

## Technical Approach

The record rule supplies the first profile; `stepUp` supplies the second. The relaunch reuses the review fix round's mechanics (`runImplementer` with `extraPrompt`, then commit, then test) rather than a new launch path, so the worker contract, the stash and hook containment, and the commit checks are the ones already proven. Continuing on the first commit keeps whatever the first attempt got right and costs the second worker only the delta. See the parent record for why a failed verify or a blocked report is the trigger.

## Gotchas

- Read `.claude/skills/headless-worker-launch` and `.claude/skills/driver-step-addition` first: a changed launch needs a re-run probe recorded in the module header, and a step or event change has registration sites that tests pin and readers (console, timing) that parse worker lines.
- #5942 edits `launchTracked` and the worker event line at the same time (adding `--effort` and an `effort` field). Read `launchTracked` as merged before planning; keep both fields when rebasing.
- `steps.js` is large and touched by many open records; prefer a small helper over inline growth, and re-derive line positions from identifiers.
- A relaunch must not reach the push: the test step must be green on the relaunch's HEAD before the push step runs, exactly as for a first attempt.
- ASSUMPTION — verify at build: a Fast driver worker returns a result envelope that meets `RESULT_SCHEMA` (`plugin/bin/lib/driver/roles.js`) — via the live smoke probe above. If it cannot, stop and report; do not ship a Fast first attempt that always fails into the relaunch.
- ASSUMPTION — verify at build: the record body is on `ctx.issue` when the implementer launches (the admission step fetched it to extract Key Files) — via reading the admission fetch. If it is not, fetch it once in the same step, never re-derive the count from `ctx.keyFiles`.
- ASSUMPTION — verify at build: the test step's verify run leaves a report with `failingFiles` the driver can read (`plugin/bin/lib/verify/pre-existing.js` names the field) — via one red driver test step. If no report is reachable, the relaunch's `extraPrompt` uses the fixed missing-report text.
