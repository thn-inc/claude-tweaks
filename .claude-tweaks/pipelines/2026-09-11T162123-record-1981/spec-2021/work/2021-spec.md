# 2021: PR run-comment find step returns nothing on GitHub Enterprise — verdict comment is re-created instead of updated

Surface: infra

## Current State
`_shared/pr-run-comments.md`'s post-or-update procedure resolves `{owner}/{repo}` once with `gh repo view --json nameWithOwner` and then passes it as `--repo {owner}/{repo}` to `gh pr view … --json comments` (find), `gh pr comment` (create), and runs `gh api graphql` with no host (update). `gh repo view` works on a GitHub Enterprise Server checkout because it reads the remote, but a bare `OWNER/REPO` value handed to `--repo` is resolved by `gh` against its default host, `github.com`, unless `GH_HOST` is set or the value carries the host as `HOST/OWNER/REPO`; `gh api` likewise targets `github.com` unless `--hostname` is given. On a GHE host the find step therefore queries the wrong server, returns nothing, and the procedure takes the create branch every time — a second review in the same run posts a duplicate verdict instead of updating the first, the exact duplicate the "One comment per kind per run" rule exists to prevent. The reporter confirmed the shape: `gh api repos/{owner}/{repo}/issues/{n}/comments` without `--hostname` 404s against github.com, while the same call with `--hostname {ghe-host}` lists the comment.

The reporter's suggestion (fall back to REST, store the numeric id, PATCH) treats the symptom; the cause is the missing host in every `gh` call the procedure makes. `gh api graphql` and `updateIssueComment` are available on GHE, so the GraphQL path can stay once the host is supplied. The same `github.com` assumption also sits in `bin/lib/repo-resolve.js`'s `parseRepo` regex (`/github\.com[:/]…/`), used by twelve `bin/` CLIs to derive `{owner, repo}` from `origin`; on a GHE remote every one of them reports "could not resolve owner/repo". That is a wider gap than this record and is split out below.

## Deliverables
- [ ] `_shared/pr-run-comments.md` Step 1 resolves the host together with the name: `gh repo view --json nameWithOwner,url` → `{host}` from the URL's authority and `{owner}/{repo}` from `nameWithOwner`; every `--repo` in the procedure becomes `--repo {host}/{owner}/{repo}` (the `HOST/OWNER/REPO` form `gh` accepts), and the `gh api graphql` update call gains `--hostname {host}`. On `github.com` the rendered commands are equivalent to today's.

## Acceptance Criteria

## Technical Approach
Supply the host, keep the mechanism: `gh` already knows how to talk to GHE when told the host, and the URL `gh repo view` returns is the one place the host is already available inside the repo without parsing the remote by hand. Changing three `--repo` values and one `--hostname` flag fixes find, create, and update together; switching to REST would add a second identity (numeric id) to `run-state.json` and a second update path to keep in sync, for a problem that is host resolution, not API family. `parseRepo` is left to its own record because its twelve callers include claims, materialize, and release, a blast radius this documentation-level fix should not carry.

## Gotchas
- `gh repo view --json url` returns the web URL (`https://{host}/{owner}/{repo}`); take the host from it rather than from `git remote get-url`, whose SSH form (`git@host:owner/repo.git`) needs a second parser.
- `_shared/github-write-transport.md`'s MCP path is unaffected: the MCP server is configured per host and takes `owner`/`repo` only.
- Existing PRs on github.com projects keep working unchanged; the only behavior change is on hosts other than `github.com`, which today fail every call.
- The `gh api graphql` mutation needs `--hostname` even when `--repo` is host-qualified elsewhere; the two flags are independent in `gh`.

## Original request
**Summary:** On a GitHub Enterprise Server host, the run-comment find step in `_shared/pr-run-comments.md` returns nothing even when the verdict comment already exists, so a second review in the same run posts a duplicate instead of updating it.

**Kind:** Gap

**Affected component:** `_shared/pr-run-comments.md` post-or-update procedure

**Use case:** A multi-review pipeline run posts a verdict comment on a PR after the first review, then needs to find and update that same comment after a later review in the same run, on a GitHub Enterprise Server host.

**Repro steps:**
1. On a GHE host, post a run comment on a PR whose body starts with `<!-- run-comment: verdict -->`.
2. Run the find step: `gh pr view {n} --repo {owner}/{repo} --json comments --jq '.comments[] | select(.body | startswith("<!-- run-comment: verdict -->")) | .id'`.
3. Observe it prints nothing, even though the comment is visible on the PR.
4. Also try `gh api repos/{owner}/{repo}/issues/{n}/comments` without `--hostname` — it 404s against github.com instead of the GHE host.

**Expected vs. actual:**
Expected: the find step returns the existing comment's id so the update path runs.
Actual: the find step returns nothing on GHE, so a fresh comment is created instead of the existing one being updated.

What worked instead: `gh api --hostname {ghe-host} repos/{owner}/{repo}/issues/{n}/comments` (REST) lists the comment with a numeric `id`, and `gh api --hostname {ghe-host} -X PATCH repos/{owner}/{repo}/issues/comments/{id} -F body=@file` updates it in place.

**Suggestion:** in the find step, fall back to the REST listing (with `--hostname` derived from the repo's remote) when the GraphQL listing is empty, keep the numeric id in `run-state.json` next to the `pr` object, and use REST PATCH for the update.
