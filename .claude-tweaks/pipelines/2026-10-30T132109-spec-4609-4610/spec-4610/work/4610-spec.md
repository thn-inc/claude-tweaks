# 4610: Add accept:* verdict labels alongside demo:* (expand step)

Surface: infra

## Overview

Expand step of the `demo:*` to `accept:*` rename (the acceptance verdict vocabulary), per the expand-contract discipline: create and read the new labels alongside the old, remove nothing. A later record (the contract step) removes `demo:*` once every reader is migrated and the removal condition holds.

New vocabulary (proposed names from the design):

| Label | Meaning | Effect |
|---|---|---|
| `accept:pending` | acceptance packet posted, awaiting the human | none; visible in Dispatch |
| `accept:approved` | human accepted | record closes (if not already) |
| `accept:changes-requested` | human says broken | follow-up per the verdict handler (separate unit) |

Plus a **machine-readable verdict comment marker**: a fenced marker block (like the plugin's other marker comments) carrying the human's note and the fix-forward / revert-now choice. It is how a verdict given on a surface that can only set a label plus a comment (Dispatch) carries its payload. It is untrusted input on read: the parser must reject malformed or forged blocks, and only a comment whose author passes the existing comment-trust rule may drive behavior.

Design constraints this record carries: labels are the contract between claude-tweaks and Dispatch (neither calls the other); an unanswered `accept:pending` is never treated as accepted; verdicts route work and do not feed an autonomy/trust ladder; the `local-files` backend uses its existing `acceptance:` frontmatter field with the new vocabulary (verdicts from Dispatch and revert-now are GitHub-only and say so when unavailable).

**Contract decisions this record pins:**

- **No writer switch here.** This record adds the read side, bootstrap rows and the marker module. `/demo` keeps writing `demo:*` until the accept-skill record switches the writers to `accept:*`; Dispatch (a separate repo) starts writing `accept:*` when its own side ships. Until then a record may carry either vocabulary, and older installed builds see only `demo:*`.
- **Mixed-label precedence is most-conservative-wins:** `changes-requested` beats `pending` beats `approved` beats no verdict, across both vocabularies, and the result is one disposition. A record with `accept:approved` and a stale `demo:pending` therefore resolves `pending` (needs a human), and any `changes-requested` from either vocabulary wins. The `record-vocabulary.js` comment that says the labels have "no precedence" is replaced by this rule.
- **`demo:approved-batch` gets a counterpart, `accept:approved-batch`**, with the identical meaning (the approval came from a batch action, not an individual verdict). `trust.js` treats the two exactly alike, so a batch approval under the new vocabulary is excluded from the trust table the same way.
- **Verdict marker format.** One single-line HTML comment in a comment body: `<!-- accept-verdict: {"v":1,"verdict":"changes-requested","choice":"fix-forward","note":"text"} -->`. `v` must be `1` (an unknown version parses as no verdict); `verdict` is `approved` or `changes-requested`; `choice` is required with `changes-requested` and rejected with `approved`; `note` is a string capped at 2000 characters (longer is rejected, not truncated); unknown fields are rejected; the JSON must escape `<` and `>` as `<`/`>` so a note can never close the comment early. Module `plugin/bin/lib/issues/accept-verdict.js` exports `renderVerdictMarker(obj)` and `parseVerdictMarker({ body, authorAssociation })` returning `{ ok: true, verdict } | { ok: false, reason }`. Register the marker in `_shared/pr-run-comments.md`'s marker registry so later records cite it.
- **Label versus marker.** The marker counts only when its `verdict` equals the record's current verdict label; a mismatch (label `accept:approved`, marker `changes-requested`) yields no action and a visible "verdict label and comment disagree" note. A label with no marker is a verdict with no note and no choice; what to do with it is the verdict-handler record's rule.
- **Trust limit.** The author-association gate cannot tell the maintainer from an agent running under the maintainer's account. The plugin never authors a verdict marker itself (only Dispatch or the human does), and the handler acts only on records, never widening scope; the residual risk is the one `comment-trust.js` already documents (`#3358`) and is stated in `_shared/work-record.md` next to the marker.
- **Prose rule.** Skill prose names the acceptance facet and cites the shared contract (`_shared/work-record.md`); only the contract files (`work-record.md`, `label-bootstrap.md`, `work-record-permission-matrix.md`) list both label spellings. Tests that pin prose spelling or the display badge may be updated to match; tests that pin behavior may not be weakened.
- **Removal condition for the `demo:*` read path** is recorded by the accept-skill record (it owns the alias's removal condition) and executed by the contract-cleanup record; this record adds a guard so the old spelling cannot spread: a test fails on any new literal `demo:` label string under `plugin/bin` outside an allowlist (the files listed in Current State at the time of this change).

## Non-Goals

- Not removing `demo:*` or the `/demo` skill (the Phase 8 contract record does that).
- Not the verdict handler's actions (fix forward, revert now) — that is the separate verdict-handler record; this record only makes the vocabulary and marker readable and writable.
- Not deciding whether `trust.js` should stop reading acceptance verdicts at all (separate follow-up; its revert detector is reused by `merge-lane-breaker.js`). Its `demo:*` reads migrate like any other consumer here.

## Technical Approach

Expand only: add the new, read both, remove nothing. Centralize the mapping so a reader asks one function (`acceptance.js`) rather than comparing label strings; where a reader compares strings today, route it through the shared constant list. Treat the verdict comment as the same class of input as the `run-comment` and `grant-mode-audit` markers: it is a comment writable by anyone who can comment, so presence proves nothing; trust comes only from GitHub's attested author association, and the parser fails closed.

## Build Clarifications

Ruled during build, each staged for ratification at the Review Console:

- A `/demo` verdict replaces any prior acceptance label the record carries, each removal conditional on the fetched labels; it still adds only `demo:*`. A single-record Approve also clears held batch labels. Without this, most-conservative-wins makes a later Approve on a rejected record read `changes-requested`.
- `/demo` fetches the fresh brief when any pending label is present, even one a verdict outranks.
- The wrap-up, parent-gate and `/demo` bootstrap lists also create the four `accept:*` labels. Creating a label is not applying it.
- The verdict marker sits alone on its line at column 0, before any code fence; `note` is optional and its cap counts `String.length`. Inline spans and indented blocks are rejected through the column-0 rule, not a mask.
