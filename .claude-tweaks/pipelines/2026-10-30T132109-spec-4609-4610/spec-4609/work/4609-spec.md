# 4609: Add control-mode policy keys

Surface: infra

## Overview

Foundation record for the "Human in control" feature: a pipeline for a human who owns exactly two decisions, **intent** (brainstorm/plan) and **acceptance** (using the built feature), with nothing asked in between. This unit adds the policy keys every later unit reads, and nothing else — no behavior changes when the keys are absent.

Keys to add (names are proposals from the design; the builder may rename for consistency with `_shared/policy-schema.md`, keeping the meanings, and records the final names in the schema summary strings):

| Key | Type | Default | Meaning |
|---|---|---|---|
| `control-mode` | enum `off`/`on` | `off` | The single switch. `on` implies `autonomy: unattended` behaviours (extended by later units), merge authorization for trusted-origin unflagged records, the acceptance-target default, and reading the deploy declaration and `owned-owners`. An enum (not a boolean) so a future third state is not a breaking rename. Individual levers keep working as overrides. |
| `acceptance-target` | enum `local`/`dev` | `local` | Where the human's check runs. `local` = the pipeline stops before merge with the PR open; `dev` = the pipeline merges, then checks dev. Overridable per work item (later unit). Absent = today's local "try it" behavior. |
| `deploy-reach` | enum `on-merge`/`command`/`none` | `none` | How code reaches dev: automatically on merge, via a project-declared command the plugin runs, or not at all. |
| `deploy-command` | string | unset | The command run when `deploy-reach: command`. |
| `deploy-live-workflow` | string | unset | Live signal, form 1: name of the CI workflow whose success means dev has the change. |
| `deploy-version-url` | string | unset | Live signal, form 2: a URL returning the deployed version or sha. |
| `dev-base-url` | string | unset | Base URL so every packet link targets dev, not localhost. |
| `dev-test-account` | string | unset | Vault entry name (never a credential) of the dedicated test account the read-only dev smoke check signs in with. |
| `deploy-wait-seconds` | integer (min 0) | `900` | Upper bound of the in-session wait for the declared live signal; `0` means do not wait. |
| `deploy-poll-seconds` | integer (min 1) | `30` | Poll interval inside that wait. |
| `owned-owners` | list | `[]` | GitHub owners (user or org) whose repos count as "owned" besides the current repo's owner. |
| `trusted-authors` | list | `[]` | GitHub logins trusted as record roots besides the repo owner. |
| `risk-categories` | list | `[]` | Project-extended invisible-risk categories, added to the four built-ins (data migrations/schema changes, auth/permissions/access control, public contracts other consumers depend on, irreversible side effects). |
| `risk-path-globs` | map (category to list of globs) | `{}` | Per-category sensitive path globs (for example `migrations/**`, `src/auth/**`) the diff tripwire reads. |

**Contract decisions this unit pins (so later units do not each invent their own):**

- **Precedence.** `control-mode: on` supplies defaults for the levers it implies at *skill-default* precedence (below CLI arg, pipeline config and project policy in the existing order CLI arg > pipeline config > project policy > skill default), so any explicitly set lever, including `autonomy: supervised`, wins for that lever. In this unit `control-mode` does **not** change `autonomy`'s resolved value; the composition is the control-mode-switch record's job. State this rule in the `control-mode` summary string and in `policy-schema.md`.
- **Read-only-under-control-mode keys.** `acceptance-target`, the deploy keys (including `deploy-wait-seconds`/`deploy-poll-seconds`), `dev-base-url`, `dev-test-account`, `owned-owners`, `trusted-authors`, `risk-categories` and `risk-path-globs` are only consulted by consumers when `control-mode` is `on`; with it off, behavior is exactly today's regardless of their values. State this in each summary string.
- **Built-in category slugs (canonical identifiers, cited verbatim by later records):** `migrations` (data migrations / schema changes), `auth` (auth, permissions, access control), `public-contract` (public contracts other consumers depend on), `irreversible-side-effect` (deletions, outbound sends, payments). `risk-categories` entries are additional slugs (lowercase letters, digits, hyphens). A `risk-path-globs` key that is neither a built-in slug nor listed in `risk-categories` is rejected.
- **List element rules.** `owned-owners` and `trusted-authors` hold GitHub owner or user logins only: non-empty strings with no `/`, no `@` prefix and no whitespace; the schema rejects other elements on the existing invalid-value path; consumers compare case-insensitively (GitHub logins are case-insensitive). A login does not say whether it is a user or an org; ownership and trust only need the login. The repo's own owner is added implicitly by the consumer, not by the config.
- **Cross-key combinations are not validated in this unit** (for example `deploy-command` with `deploy-reach` other than `command`, both live-signal keys set, `acceptance-target: dev` with `deploy-reach: none`); the dev-target record states the semantics of each combination at its consumer. Document in each summary string which key is meaningful only alongside which other.
- **`deploy-command` is an executed string.** Its summary string says so, and the dev-target record must read it only from the trusted base branch's `policy.yml`, never from a PR head.
- **Fail closed.** An unrecognized `control-mode` value must never behave as `on`: consumers compare `=== 'on'`, never `!== 'off'`; a single exported helper `isControlModeOn(value)` (in the policy module) is the one comparison site.
- **Key names are frozen for this decomposition.** The 17 sibling records cite them verbatim. A rename is allowed only if the same change updates every record that cites the old name (find them from the parent's Leaves table) and keeps the old name accepted-but-deprecated per expand-contract.

## Non-Goals

- No change to any existing key's meaning or default (expand-contract: add, never rename in place).
- Not the `/init` setup questions (separate unit) and not the stop switch.
