# 5915: Stop the driver worker running the whole test suite

Surface: backend
Risk-flags: none

## Overview

The pipeline driver's implementer worker stops running the project's whole test suite. Its prompt tells it to run only the tests for the files it changed, and the bare suite command leaves its allowed commands. The driver's own test step stays the gate. In the three driver runs of 2026-11-12 the model worked 2.1 to 2.6 minutes of an 18 to 25 minute worker step; the rest was the worker running all 24,848 tests three times per record. See #5914 for the Decision Rationale.

**Complexity:** Low
**Estimated tasks:** 4

## Non-Goals

- The driver's own test step, which keeps running `verify.js` after the commit.
- Why 37 to 40 tests fail inside the worker's sandbox. This record removes the run that shows them.
- The reviewer's evidence runs, which already run one named test file each.
- Choosing the worker's model: #5917.

## Current State

- Prompt: `plugin/bin/lib/driver/steps.js` sets `const TEST_COMMAND = 'npm test'` (line 100) and `workerPrompt` emits the single line `` `Test command: ${TEST_COMMAND}` `` (line 584). Nothing else in the prompt says when to run tests or what to do with the output.
- Launch: the implementer launch passes `testCommand: TEST_COMMAND` (lines 712 and 1306), which is what puts the suite command on the worker's allow list.
- Allow rule: `implementerSettings` allows `Bash(<testCommand> *)` (`plugin/bin/lib/driver/roles.js` line 305), and `assertTestCommand` accepts only `[A-Za-z0-9 ._/:=-]` (line 257), so a `{files}` placeholder is rejected and a runner prefix also admits a no-argument whole-suite run.
- Gate: the driver's test step runs `verify.js` with `--scope` when `.claude-tweaks/verify-scope.json` exists, and `--cmd tests=npm test` when it does not (lines 894-938).
- Targeted form: this repository's `.claude-tweaks/verify-scope.json` declares `"command": "node tools/run-tests.js --files-from {files}"` under `impact` (line 17). Other projects may declare none.
- Result: the worker's result schema (`RESULT_SCHEMA`, `plugin/bin/lib/driver/roles.js` line 193) has no test field, and no driver code reads whether the worker ran tests.
- Observed: each of the three worker transcripts holds three `npm test` runs of 4.5 to 10 minutes, each printing `# tests 24848`, often piped through a different `grep`.

## Deliverables

- [ ] `workerPrompt` replaces the `Test command:` line with a test instruction: run only the test files that cover what you changed, by explicit path; never run the whole suite; the driver runs the full check after you finish.
- [ ] When the worktree's `verify-scope.json` declares an `impact.command`, the instruction names that command with its `{files}` placeholder as the form to use. A file with no `impact.command`, an empty one, or one that cannot be parsed takes the no-declaration path.
- [ ] The implementer's allow list no longer carries the bare suite command.
- [ ] The implementer's test command is the declaration's `impact.command` cut before its trailing ` {files}` placeholder (this repository: `node tools/run-tests.js --files-from`), so the composed allow rule is `Bash(node tools/run-tests.js --files-from *)`. The worker writes its list file, one test path per line, inside the worktree and passes that path.
- [ ] With no declaration, an `impact.command` that does not end with ` {files}`, or a cut command holding a character outside `[A-Za-z0-9 ._/:=-]`, the worker gets no test command: the launch omits `testCommand`, and the prompt says not to run tests because the driver runs the check after the commit.
- [ ] `docs/driver.md` states that the worker runs targeted tests only and that the driver's test step is the gate.
- [ ] Tests for the prompt text and the allow list in both cases: a declaration present, and none.

## Acceptance Criteria

1. With a `verify-scope.json` whose `impact.command` is `node tools/run-tests.js --files-from {files}`, the composed worker prompt contains that command and does not contain a line beginning `Test command: npm test`.
2. With no `verify-scope.json`, the composed prompt tells the worker not to run tests, names no test command, and the launch passes no `testCommand`.
3. In both cases no rule in the implementer settings the launch composes matches `npm test`, `npm test -- --full`, or `node tools/run-tests.js` with no `--files-from` argument; with the declaration present the settings hold `Bash(node tools/run-tests.js --files-from *)`.
4. The driver's test step is unchanged: a test that asserted its `verify.js` arguments before this change passes unmodified.
5. A live driver run on one record, quoted in the pull request, shows a worker transcript with no command whose output contains a `# tests` total above 1,000, and a worker step of five minutes or less.

## Release Note

Shortened pipeline driver runs by having the worker run only the tests for the files it changed.

## Technical Approach

The worker never needed the suite: the driver commits the worker's change and then runs the scoped check itself, and a failure there already stops the record before the push. The change is to what the worker is told and allowed. The targeted command comes from the project's own declaration so nothing here is specific to this repository; a project with no declaration gets the instruction without a named command.

### Data / API Surface

- `workerPrompt(ctx, { minutes, dollars, maxLines })` gains the resolved targeted command, read from the same `verify-scope.json` the test step already locates.
- The launch's `testCommand` option carries the targeted form, or is omitted when there is none.

### Key Files

- `plugin/bin/lib/driver/steps.js` — `TEST_COMMAND` use in `workerPrompt` and in the implementer launch
- `plugin/bin/lib/driver/roles.js` — how `testCommand` becomes an allow rule in `implementerSettings`
- `tests/bin-lib/driver/run.test.js` — prompt and settings assertions
- `docs/driver.md` — the worker's test rule

## Gotchas

- Read `.claude/skills/headless-worker-launch` before changing an allow rule: an allow rule is probed for what it lets the worker write or start, not only for what it denies, and the probe results are recorded in the module header.
- The test step also reads `TEST_COMMAND` for its no-declaration path (line 937). Leave that use alone.
- This repository refuses a direct `node --test` run in some contexts (`tools/direct-test-run-guard.js`). The targeted form here is the declared `node tools/run-tests.js --files-from {files}`, not `node --test`.
- ASSUMPTION — verify at build: `implementerSettings` derives the allowed test rule from the `testCommand` option alone — via reading `implementerSettings` in `plugin/bin/lib/driver/roles.js`.
- ASSUMPTION — verify at build: inside the worker's sandbox the impact map is unreadable, so a bare `npm test` falls back to the whole suite — via one `--check`-admitted live run, or by reading `tools/run-tests.js` lines 34-43 against the sandbox's read rules.
- `node tools/run-tests.js --files-from <list>` runs exactly the files the list names and never consults the impact map (`tools/run-tests.js` header comment, lines 14 and 41), so this repository's targeted form cannot widen to the whole suite. The driver passes a project's declared command through unchanged; a declared command that can widen by itself is that project's declaration to fix.
- Test execution by the worker is advisory and unobserved: `RESULT_SCHEMA` has no test field and this record adds none.
- The worker's targeted command and the gate's scope come from one `verify-scope.json` read; resolve it once per run through the test step's own locator so the two cannot diverge.
- ASSUMPTION — verify at build: a failing test step stops the record rather than returning to the worker, so a regression the worker no longer sees ends the run at the gate — via reading the test step and its result handling in `plugin/bin/lib/driver/steps.js` lines 894-938; a rise in records stopped there is an accepted cost, visible in the first record's funnel.
- AC5's live run needs a record the driver admits (`node plugin/bin/drive.js --check #N`); a change that legitimately needs a broad test selection is judged by the pull request's reviewer, not by the `# tests` count alone.

## Architecture Alignment (build, Beneficial)

Recorded at `/build` Common Step 4.5; each extends the spec's intent where it was silent.

- The worker step's event line carries an additive `tests` field naming the path taken: `declared`, `none`, `unreadable` (a git read or JSON parse threw) or `unsupported-platform` — so a failed read is distinguishable from no declaration.
- On a platform outside `SANDBOX_PROBED_PLATFORMS` the implementer has no Bash, so no targeted command is resolved there: the prompt gets the do-not-run-tests line and the launch passes no `testCommand`.
- The worker's list file has a fixed location, `.claude-tweaks/pipelines/worker-test-files.txt` (a run artifact the commit step never stages), and the driver removes it after each implementer launch, best-effort, after checking both parent directories are real directories.
- "Resolve it once per run through the test step's own locator" is implemented once per record (cached on the record's ctx, shared by the first launch and the review fix round), reading `origin/{ref}`'s blob through the test step's `scopeBaseBlob` — per record matches the test step's own per-record read.
