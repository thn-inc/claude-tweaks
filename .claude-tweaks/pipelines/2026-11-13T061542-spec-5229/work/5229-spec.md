# 5229: drive.js --budget N: the driver picks its own records

Surface: backend

## Overview

This unit teaches `drive.js` to pick its own records. `drive.js --budget <n|all>` selects records with the queue-pull module and ranking from the sibling unit #5227, keeps those the driver's admission accepts, and drives up to `n` of them one at a time in the order a dispatch drain would use. With it the dispatch hub can start a drain with no Claude session at all. Design: `docs/superpowers/specs/2026-11-11-pipeline-driver-design.md`, section "Phase 5 — Queue selection in the driver".

A record the admission refuses was never driven and does not consume budget; a record that is driven counts whatever its outcome. `--budget` and named records are mutually exclusive. Flag semantics follow `plugin/skills/_shared/record-batch-input.md`'s "The `--budget` flag" section; this unit states the driver's own rules where that file leaves them to the caller (rejecting `--budget 0` and a negative value, and the combination with named records).

**Complexity:** Medium
**Estimated tasks:** 6

## Non-Goals

- Any change to what the queue pull selects or in what order: this unit calls the module and does not alter it.
- Parallel records: one at a time, as in the rest of the design.
- Hub code: how the hub starts `drive.js` is a separate design in the dispatch repository.
- Entry from `/claude-tweaks:dispatch` (Phase 3 of the design) and any change to the skill's drain.
- A prose contract for the driver, or any test that reads skill prose: `docs/driver.md` is documentation, pinned by nothing.
- A default budget. Without `--budget` and without named records, `drive.js` is a usage error; there is no policy key for a default.

## Acceptance Criteria

1. On a fixture queue, `--budget all` drives the same records, in the same order, as the sequence obtained by iterating the module's queue pull and ranking over the same fixture the way a dispatch drain's Loop does (rank, take the top group, add its members to the `firing` entries, pull again), each group contributing its member records in the group's own order, restricted to the records the driver's admission accepts. The expected sequence in the test is computed by calling the module directly, never by re-deriving the order in the test. A fixture with a priority band, a tie within a band, a multi-record fast-lane bundle whose first member the admission refuses (the remaining members are still driven, in order) and a group excluded as `oversized` covers the ordering.
2. `--budget 0`, a negative value, a non-integer (`1.5`), an empty value, a non-numeric value other than `all`, and `--budget` as the last argument with no value are each a usage error: exit 2 with the usage text, and the fake runner records no call at all (no policy read, no `gh`, no module call).
3. `--budget` together with a named record (`drive.js --budget 2 #12`) is a usage error with the same exit and no calls. `--budget` given twice is a usage error. `drive.js` with neither named records nor `--budget` is a usage error.
4. Budget accounting: a record counts when the per-record path returns `claimed: true`, whatever its outcome (`pending-review`, `express-escalated` or `blocked`). A record refused by admission or by the pre-screen, a record whose claim is lost to another run (`claim-targets.js` exit 3, contested or in flight) and a record whose claim fails any other way (exits 4, 5 or 6, or a claim obtained and then a run directory that cannot be minted) consumes nothing. Each of these joins the attempted set, so it is not selected again in this invocation. A fixture with `--budget 2` over singleton groups whose first record is refused, second driven to `blocked`, third lost to a contested claim and fourth and fifth driven to `pending-review` ends after the second and fourth records are driven, and leaves the fifth untouched.
5. With `express-driver` resolving `off`, `--budget` drives nothing and writes nothing: the policy is read before the pull, so the fake runner records no `gh` call, no module call and no file write; one event names the refusal, the run-level summary line carries `ended: policy-refused` with all counters 0, and the exit code is 0.
6. Termination: no record is selected twice in one invocation, whatever happened to it the first time (the loop passes every member of every group it has handled, attempted or skipped by the pre-screen, to the ranking as `firing` entries, in memory). With `--budget all` over a fake queue that returns the same admission-refused record on every pull, the run ends after one attempt at it; over an empty queue it ends with zero driven. A queue whose top record is permanently ruled ineligible by the pre-screen is skipped once and the run reaches the records ranked below it and then stops. A test with a queue that never shrinks asserts the run stops.
7. A claim refused for permission (`claim-targets.js` exit 7) ends the run, with the rest of the budget unused, as dispatch's Claim permission stop ends a firing. That record gets the Phase 1 settle for a failed claim (a comment and `bot:blocked`, no release call) and is counted in `permissionStopped`.
8. Selection failures are not an empty queue: a failed pull before any record is driven exits 1 with the module's error named and nothing driven; a failed re-pull after some records were driven ends the run with `ended: pull-failed` and exit 1, and the records already driven keep their own outcomes. An unreadable policy exits 1 with nothing driven.
9. Exit codes follow the Phase 1 vocabulary: 0 when the loop ended normally, whatever each record's outcome; 1 for an unreadable policy or a failed pull; 2 for a usage error or an absent `gh` or `git`. The run-level summary line carries `budget` (the request), and a counter per attempted record, so every attempted record is in exactly one: `driven`, `refused` (admission), `skipped` (pre-screen), `contested` (claim exit 3), `claimFailed` (claim exits 4, 5, 6 or a failed mint) and `permissionStopped` (claim exit 7); plus `ended` (`budget`, `exhausted`, `permission-stop`, `pull-failed` or `policy-refused`) and `status` (`ok` for `budget`, `exhausted` and `policy-refused`; `stop` for `permission-stop`; `fail` for `pull-failed`). A test pins the counters' sum against the number of records handed to the loop.
10. `docs/driver.md` documents the flag, the rule that a refused or contested record does not consume budget while a driven one does, the termination rule and the exit codes, and `docs/plugin-structure.md`'s `drive.js` line names `--budget`.
11. Pre-screen: a record the pre-screen skips causes no live fetch and no `claim-targets.js` call (fake runner), and a record whose pulled data lacks a field the eligibility function needs (no `labels`, a non-string `body`) is passed through to the full per-record path rather than skipped.

## Technical Approach

- **The module is the selector.** The loop calls `queuePull` and `rankNext` from #5227 and never reorders, filters or re-derives selection beyond what the criteria above state. Each iteration pulls fresh, as dispatch's Loop and the `--budget` semantics do, so a record claimed by a sibling run leaves the pool between iterations. The unit of selection is the group, as in dispatch: `rankNext` returns one group, and because it skips a whole group that has any member under a `firing` entry, the loop drives that group's members before it pulls again and marks all of them attempted at once.
- **Grouping policy.** The pull runs with the grouping policy dispatch applies under the same `express-lane` value (`expressQueuePolicy`). The driver does not need `express-lane` on, so with it off, fast-lane records can arrive inside a bundle; a bundle is not driven as a unit, its members are driven one at a time in the bundle's order, each through the per-record path. A member driven earlier in the bundle holds a live claim by the time the next pull happens, which is why the next pull may then skip a later group as `neighbour-in-flight`; that is the module's behavior, as it is for dispatch.
- **Admission is the run loop's own first steps.** The loop does not call `evaluateAdmission` separately: it runs the Phase 1 per-record path, whose first steps (policy, one fetch, eligibility, admission) refuse before the claim with outcome `refused`. The budget counts from the claim, so the refusal outcome is what leaves a record uncounted. The pre-screen only saves the live fetch for records the pulled data already rules out.
- **Settle is unchanged.** Each driven record settles by the Phase 1 rules (`--no-settle` included); the loop adds no settle behavior.
- **Event lines.** The loop adds one step name for the run-level summary; no existing field is renamed. Per-record lines are the per-record path's.

### Data / API Surface

- `drive.js #N [#M…]` | `drive.js --budget <n|all>`; the two forms are exclusive.
- Run-level summary event: `{ ts, run: null, record: null, step: 'budget', status, ms, detail?, budget, driven, refused, skipped, contested, claimFailed, permissionStopped, ended }`; the step-name constant is added next to the others in `events.js` (added by #5218), with the pinning test updated in the same change. ## Gotchas

- ASSUMPTION — verify at build: the Phase 1 units (#5216, #5218, #5219) have merged with the names this record uses (`evaluateAdmission`, the per-record path in `run.js`, the outcome words, `--no-settle`, `events.js`, `docs/driver.md`) — confirm via `git ls-files plugin/bin/drive.js plugin/bin/lib/driver docs/driver.md` and by reading the merged files' headers; where a name differs, use the merged one.
- ASSUMPTION — verify at build: `claim-targets.js` exit 3 means contested or in flight and exit 7 means permission denied (`plugin/skills/flow/claim-targets.md` Step 2.8 and `.claude/skills/claim-targets-stop-addition`) — confirm by reading `plugin/bin/claim-targets.js`'s header. This unit adds the `{ outcome, claimed, claimExit }` return to the merged per-record path.
- The driver's eligibility gates are stricter than the queue's: the queue admits every `auto:build` record, the driver refuses `ceremony:standard` and everything else outside the express gates, so most pulled records are refused by the eligibility function. The pre-screen runs that same function over the pulled data so that a pull of several hundred records does not cost a live fetch each; it may skip but never admit. What it cannot see is live state (a new blocker or open PR, a claim), so those refusals still cost one live fetch each; that cost is accepted and bounded by the number of records that pass the pre-screen.
- The pre-screen works on minutes-old data. A record it skips may have become eligible since; the next invocation picks it up. A record it lets through is checked live by the per-record path. A maintainer who tightens eligibility in #5218 changes the pre-screen with it, because both call the same function.
- Two budget runs started at once can select the same record. The claim decides: the loser sees exit 3 and consumes nothing.
- `neighbour-in-flight` groups are skipped by the ranking, so a budget run never drives a record that shares a Key File with a live claim; this comes from using the same `rankNext`, not from code in the driver.
- A defect in selection found while testing is a defect in the module (#5227) or in the queue pull itself: file it as its own record rather than patching around it in the loop.
