# 4631: Console backfill records a truncated path for a finding at a path holding @ or [id]

Origin: wrap-up leftover from #4582

Defer-reason: pre-existing-outside-diff

## Current State

`plugin/bin/lib/console/backfill.js` keeps the old path class in `LOCATION_RE` (line 27) and in the `loc` regex at line 337, after #4582 widened `findingKey`'s class in `console/resolve.js`. A backfilled finding at `app/[id]/page.tsx:9` records the path `/page.tsx`, and one at `packages/@scope/x.ts:4` records `scope/x.ts`, so a tiebreak reading that path fails its evidence check and any filed record names the wrong file. #4582 left this alone because `backfillItemId` hashes the finding key: widening the class re-ids a stored backfill item at such a path, and a re-run could file it twice.

## Deliverables

- [ ] Use `FINDING_PATH` (exported from `console/resolve.js`) in `LOCATION_RE` and the line 337 `loc` regex.
- [ ] Keep a re-run of the backfill idempotent for an item stored under its old truncated-path id.

## Acceptance Criteria

A staged line for `app/[id]/page.tsx:9` backfills with `path` `app/[id]/page.tsx`.

A backfill re-run over a run whose stored item carries the old truncated-path id files no second record.

## Release Note

Backfilled review findings in files whose paths contain characters such as `@` or brackets now name the right file.

## Technical Approach

### Key Files

- `plugin/bin/lib/console/backfill.js` — adopt the shared finding-path class without re-iding stored items
