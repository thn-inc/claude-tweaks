# 2663: Add legal/compliance pre-launch questions to the security checklist

Surface: backend

**Related:** #2657

## Current State
A social-media Reel (caption states the claim directly; no transcription needed) names three pre-launch questions builders should answer before shipping: (1) do you have cyber liability insurance, (2) have you read your platform's terms of service, and (3) does your privacy policy actually match what your app does. This is adjacent to two existing open records: the pre-launch security hardening checklist (`#2624`, secrets in client bundle, RLS/ownership checks, AI-endpoint auth/rate-limiting) and the GDPR account-deletion vs. backup-retention check (`#2625`) — the "privacy policy matches the app" question specifically overlaps with `#2625`'s data-handling scope, since both are ultimately about whether stated data practices match actual ones. Neither `#2624` nor `#2625` has a shipped checklist/skill implementation yet.

## Deliverables
1. A privacy-policy-accuracy checklist row: an automatable comparison between claims made in a privacy policy document (data collected, third-party services/processors named, retention practices stated) and the app's actual data flows (API calls to third-party services, data fields collected in forms/schemas, retention logic in the codebase) — flagging a mismatch (e.g., an analytics or ad SDK integrated in code but not named in the policy).
2. A terms-of-service pre-launch reminder line: explicitly documented as a manual reminder to read the hosting/platform's ToS before launch, not an automated check — no attempt to parse or verify ToS compliance programmatically, since that's not something a code check can reliably assess.
3. A cyber-liability-insurance pre-launch reminder line: same manual-reminder treatment as the ToS item — a business/financial decision outside any code check's scope.
4. Documentation cross-referencing both `#2624` (the general pre-launch security checklist this item is meant to join) and `#2625` (the GDPR/data-retention check this item's privacy-policy-accuracy row overlaps with), so the checklist and the more specific GDPR check don't silently diverge on what "policy matches practice" means.

## Acceptance Criteria
- The privacy-policy-accuracy check is implemented as an automatable row: given a sample privacy policy document and a sample codebase using at least one third-party service (e.g., an analytics SDK) not mentioned in that policy, the check flags the mismatch.
- The privacy-policy-accuracy check produces no false-positive flag when run against a sample app whose privacy policy correctly names every third-party service actually integrated.
- The ToS and cyber-liability-insurance items appear in the checklist as clearly labeled manual-reminder lines (not run as automated checks), with prose explicitly stating why they aren't automatable.
- The checklist documentation cross-references `#2624` and `#2625` by number, explaining the overlap between this item's privacy-policy-accuracy row and `#2625`'s GDPR scope so a future reader/builder of either doesn't duplicate the other.

## Technical Approach
Since `#2624` has no shipped skill implementation yet, land this as a standalone checklist section (mirroring the approach taken for `#2657`'s JWT checks against the same still-unbuilt `#2624`), written so it merges cleanly into `#2624`'s eventual body/skill once that record ships. The automatable privacy-policy-accuracy check needs two inputs: the privacy policy's stated third-party services/data practices (parsed from the policy document, likely via a simple keyword/entity extraction rather than full NLP) and the codebase's actual third-party integrations (grep for known SDK/API-client imports and outbound API call patterns) — compare the two lists and flag services present in code but absent from the policy. The ToS and insurance items need no implementation beyond a documented reminder line; do not build a mechanism to verify either, since neither is code-inspectable.

### Key Files
- A new checklist file (path determined by whichever skill or doc structure `#2624`'s implementation adopts, e.g. under `plugin/skills/` if a security-checklist skill is created, or `docs/reference/` if it remains a static checklist) — holds the three legal/compliance items and the privacy-policy-accuracy audit prompt.
- `#2624`'s own body/eventual implementation file — cross-reference added once both records have landed.
- `#2625`'s own body — cross-reference added noting the privacy-policy-accuracy row's overlap with GDPR account-deletion/backup-retention scope.

## Gotchas
- `#2624` and `#2625` are both unbuilt as of this shaping — there is no live checklist artifact to append rows to today; this record may ship first as a standalone section, and whichever record ships second must fold the others in with cross-references, avoiding silently-diverging checklists (same build-order caveat as `#2657`).
- The privacy-policy-accuracy check's automation is inherently approximate — keyword/entity matching between a policy document and codebase imports will miss paraphrased policy language or indirect data flows (e.g., a third-party service called via a proxy/wrapper with a generic name); the check should be framed as "flags likely mismatches for human review," not a guarantee of policy accuracy.
- Do not attempt to automate the ToS or insurance items even partially — the record's own framing (from Instagram Reel caption, direct claim, not transcribed) is explicit that these are non-code-inspectable business decisions, and a false-positive-prone automated version of either would undermine trust in the rest of the checklist.
