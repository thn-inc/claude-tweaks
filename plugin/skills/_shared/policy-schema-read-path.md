## Canonical read path — output, derived defaults and --all

For shell-variable capture, `--values` prints one plain value per line in request order instead of the JSON envelope — coerced values render natively (`true`, `14`); an unset no-default key and an unknown key each print an empty line (the same empty string the retired grep pipeline produced); `model-profiles` and `risk-path-globs` have no scalar form and are invocation errors under `--values`. A present-but-invalid value prints its schema default on stdout with exit 0, and gets one stderr line naming the key, the rejected value and the default (#4141). JSON mode carries `invalid: true` instead. List-typed keys (e.g. `merge-sensitive-paths`) resolve to the raw comma-separated string in both modes when configured — callers split on `,`; only the unset default is a JSON `[]`, which `--values` renders as an empty line (same empty-means-none reading as the retired grep).

The `${CLAUDE_PLUGIN_ROOT}` spelling is a model-resolved placeholder, not a live env var — the substitution contract is `docs/skill-authoring.md`'s "Plugin-root references (`CLAUDE_PLUGIN_ROOT`)" section; follow it, it is not restated.

Output is a single JSON object keyed by requested key. Each key resolves to the envelope `{value, source}` with `source ∈ run-config | policy | factory | default`; precedence is run `config.yml` (when `--run` is given) → `policy.yml` → the factory layer (`## Factory layer` below) → schema default. Integers and booleans come back as native JSON types. Optional envelope fields:

- `"renamed-from"` — the value arrived via a `RENAMED_KEYS` alias (deprecated key name in the source file)
- `"invalid": true` — a present-but-rejected value degraded to the schema default; distinct from known-but-unset, which is `source: "default"` with no flag
- `"repoInvalid": true` — a block key whose `policy.yml` block is malformed resolved from the factory layer's rows instead (`source: "factory"`, no `invalid` flag); never set otherwise
- `{"error": "unknown-key"}` — the requested key is not in the schema (no value/source)

**Derived-default keys** come in two shapes; both are live, so a new derived key picks one deliberately and states the choice in its row.

*Shape A — resolve-time derivation, no static default* (`integration-model`, `merge-verification`): the `POLICY_KEYS` row carries no static `default`; the derivation's one prose statement lives in `_shared/policy-schema-coverage.md`'s `merge-verification` derivation section and `_shared/integration-model.md`'s forge-detection ladder with a code twin in `bin/lib/` (`policy-schema.js`'s `detectIntegrationModel`; `merge-verification.js`'s `deriveMergeVerification`); `bin/resolve-policy.js` computes it only for an *absent* key (`source: "default"`, no `invalid` flag), never overwriting an `invalid: true` envelope; and `/claude-tweaks:help`'s policy mode renders the default as `computed (…)`.

*Shape B — in-loop derivation over a static base default* (`housekeeping-auto-merge`, #580; `learned-skills-auto-merge`, #6109): the row keeps a static `default` as the base (`false`, the `supervised` base), so schema default and effective default differ; the derivation runs inside `bin/lib/policy-schema.js`'s `resolvePolicyKeys` (`deriveHousekeepingAutoMerge`, `deriveLearnedSkillsAutoMerge`); it fires for any entry that resolved `source: "default"` — unset **and** set-but-invalid (the `invalid: true` flag survives, the value is derived) — and keeps `source: "default"` because that field is the derived-vs-explicit attribution surface its consumers read. Pick B when an existing consumer must keep reading the value as a plain default; A otherwise. `/claude-tweaks:help`'s policy mode renders an explicitly-set B default as `computed (derived from autonomy)` for `housekeeping-auto-merge` and `computed (derived from autonomy and control-mode)` for `learned-skills-auto-merge`; the Notable-defaults finding covers core-tier keys only, so it surfaces `housekeeping-auto-merge`'s unset/derived divergence and not the advanced-tier `learned-skills-auto-merge`'s, both per that skill's own render contract (#636).

Consolidating the two is deferred until a further derived lever appears (#580's ledger). Adding a lever of either shape also walks `_shared/auto-mode-contract.md`'s "Adding a new policy lever" checklist when it is Manifesto-visible.

`--all` emits the whole resolved config in one call: every schema key mapped to its `{value, source}` envelope plus its metadata fields and shape (`summary`, `category`, `tier`, `type`, `default` — `default` is JSON `null` when the row has none, which consumers read as "no default"). It composes with `--run`, takes no key arguments, and is mutually exclusive with `--values`. Renderers (the `/claude-tweaks:help` policy mode, init's policy review) consume this instead of enumerating key names by hand.

## Factory layer

A user-wide policy layer below the repository's `.claude-tweaks/policy.yml` and above the schema default (#6006), for a setup that is the same in every repository. Two inputs, read only by `bin/lib/policy-factory.js`'s `readFactoryPolicy`: the `CLAUDE_TWEAKS_FACTORY_POLICY` variable (policy text, same syntax as `policy.yml`) and `~/.claude-tweaks/factory-policy.yml`. They merge per key, the variable winning; a block key (`model-profiles`, `risk-path-globs`, `express-driver-models`) comes whole from the variable when it holds one. The one exception: a variable `model-profiles` or `express-driver-models` block that does not parse yields to the file's block, with a stderr warning, only when the file holds that key and its block parses; otherwise the variable's block is kept. `risk-path-globs` is never judged by the reader — the resolver checks its rows against `risk-categories` later. A flat variable line the resolver would not read (an empty value, a quoted key) sets nothing, so the file's value for that key stays. A literal `\n` in the variable is not decoded: a one-line value holding `\n` is one key's invalid value, not two keys — and Dispatch's hub editor takes a single line, so set a multi-line value through its `POST /api/config-values` API. `CT_FACTORY_POLICY_FILE`, when set to an absolute path, names the factory file in place of `~/.claude-tweaks/factory-policy.yml` (a relative value turns the file off); it is read from the caller's injected env like the variable, and `tools/run-tests.js` points it at a path inside its run root that never exists, so no suite reads the machine's own file. `.claude-tweaks/policy.yml` stays the only repository config home — the factory layer is never a second place a repository's config lives.

- **Source.** A value that resolved from the layer carries `source: "factory"`, and every consumer treats it as explicit, exactly like `policy` (it is not a default). `policySourceExcluded` keys discard both standing layers, `policy` and `factory`.
- **Block rows.** `model-profiles`, `risk-path-globs` and `express-driver-models` merge per row, the repo row over the factory row (`bin/lib/model-profiles/policy-fragment.js`'s `mergeBlockRows`); the block's source is `factory` when the factory side parses and the repo side is absent or malformed, or parses with no rows while the factory side has rows; otherwise `policy`. When the repo block is malformed and the factory rows supply the value, the entry also carries `repoInvalid: true`, so a JSON consumer still sees the broken `policy.yml` block. Any non-empty `risk-categories` line in `policy.yml` decides the allowed risk slugs alone; the factory's categories apply only when `policy.yml` has none.
- **Refused keys.** `merge-authorization`, `control-mode`, `deploy-command`, `release-hook`, `protected-paths` and `express-driver-runner` are not settable here (`FACTORY_REFUSED_KEYS`). `merge-authorization` is a per-run human pre-authorization (`policySourceExcluded`) and must never be a standing default; `control-mode` is the single human-in-control switch, which #5830 ruled is set in `policy.yml` or not at all; `deploy-command` is an executed string specific to one repository; `release-hook` is an executed string specific to one repository (decided at plan review); `protected-paths` is a repository-layout list, and Phase 11 sets its factory semantics as a floor, not a replacement; `express-driver-runner` (#6119) is a fact of one repository (whether a script job drains it), so a user-wide `script` would leave every other project's driver-routable records unbuilt. Every other key, `autonomy` and the trust lists (`owned-owners`, `trusted-authors`) included, is settable, and the factory variable comes from the factory's environment, never from a pull request's content. The resolver ignores a refused key's factory line and writes `resolve-policy: warning: {key} is not settable from the factory layer — ignored` to stderr, once per requested refused key the factory text holds.
- **stderr, every output mode** (stdout and exit code unchanged), in this order: the main-checkout note when the policy was read from the main checkout (`resolve-policy: note — {root} has no .claude-tweaks/policy.yml; read the main checkout's {policyPath}`), the reader's warnings (an unreadable file: `resolve-policy: warning: could not read ~/.claude-tweaks/factory-policy.yml ({code}) — factory file ignored`; a variable block that did not parse: `resolve-policy: warning: {key} has invalid value "{first line}" in CLAUDE_TWEAKS_FACTORY_POLICY — using ~/.claude-tweaks/factory-policy.yml's block`), the refused-key warnings, one `resolve-policy: warning: {key} has a malformed block in the factory layer — ignored, using the repository's rows` per requested block key whose factory block did not parse beside a usable `policy.yml` block, then, when a requested key resolved from the layer, `resolve-policy: note — factory layer ({origin}) supplied {keys}`; `origin` is `env`, `file` or `env+file`. Under `--values`, an invalid value the factory layer supplied gets the invalid-value warning with ` in the factory layer` after the quoted value (`resolve-policy: warning: {key} has invalid value "{raw}" in the factory layer — using default "{default}"`); the line for a `policy.yml` or run-config value is unchanged.
- **Readers outside the layer.** Only `resolvePolicyConfig` and `bin/resolve-policy.js` (and the callers that go through them) see the layer today; `bin/lib/policy.js`'s `parsePolicy` and `readRiskPolicy`, `bin/accept-park.js`, `bin/resolve-profile.js` (its `model-profiles` rows), `bin/lib/compose-context/`'s condition resolver and `bin/console-resolve.js`'s `owned-owners` read do not yet (#6007).
- **Trust.** #5963 (symlink refusal) and #4685 (base-branch trust keys) are open and not in the tree. No site in `plugin/bin` treats `source === 'policy'` as proof of repository origin today; the one `=== 'policy'` comparison was the `policySourceExcluded` guard, which now discards both standing layers. A change that starts treating `policy` as repository-origin proof must handle `factory` in the same change.

## Metadata fields — the three fields

Every `POLICY_KEYS` row carries three human-facing fields alongside its shape: `summary`, `category`, and `tier`. `tests/policy-schema-metadata.test.js` pins completeness (a future lever cannot ship metadata-less), the category set against the mapping table in `_shared/policy-schema.md`'s Metadata fields section, the core-tier cap, and the no-duplication rule — the same prose↔constant pattern as `tests/hooks-gate-coverage.test.js`.

- **`summary`** — one plain-language sentence stating *what changes when you move this lever* (style target ≤ ~120 chars; hard test ceiling 140). It never restates the key name or type, and carries no implementation citations. This is a different altitude from each key's Meaning column in `_shared/policy-schema.md`'s key sections: the summary is for a project owner scanning their config; the Meaning prose is the deep contract for skill authors. Neither replaces the other, and no summary text may be duplicated into `_shared/policy-schema.md` (test-enforced).
- **`category`** — one of the values in `POLICY_CATEGORIES` (exported beside `POLICY_KEYS`). `_shared/policy-schema.md`'s Metadata fields mapping table assigns every key-bearing section of that file to a category; it is many-sections-to-one-category, and a key may individually carry a different category than its section when its subject genuinely differs (the section mapping is orientation, the per-key field is truth).
- **`tier`** — `core` or `advanced`. Decision rule: `core` = levers that change what the pipeline may *do without a human* — enforcement gates, autonomy/trust posture, merge/execution defaults, integration identity. Tuning caps, thresholds, retention, and cosmetic/reporting knobs are `advanced`. The core tier is capped at 12 keys (enforced, not advisory).

## Control mode — how the keys apply

Inert unless a row names its owner (#4609, #4608). `control-mode: on` implies its levers at skill-default precedence: an explicitly set lever wins, and the resolved `autonomy` value is unchanged — the bookkeeping ceiling composes control mode below an explicit `autonomy` (`_shared/autonomy-ceiling.md`'s Precedence). Every other key in the table below, and the two risk keys in `_shared/policy-schema.md`'s Control mode section, is consulted only when it is `on`. `isControlModeOn` in `bin/lib/policy.js` is the one comparison site (exactly `on`). A list is written on one line as `a,b`: a quoted or bracketed list is rejected and a dash-style block is ignored. `owned-owners` and `trusted-authors` entries are logins, compared case-insensitively by consumers; `risk-categories` entries are slugs. An entry is never empty and holds no `@`, `/`, inner space or bracket other than a trailing `[bot]` (`a, b` is fine). On a flat key a `#` ends the value even inside quotes, so `deploy-command` stops there; `deploy-command`, `deploy-live-workflow` and `dev-test-account` reject a value left inside an unclosed quote (a `"` opens anywhere, a `'` at a word start) or a blank quoted one, and drop outer quotes only when they enclose the whole value. URL keys are written unquoted.
