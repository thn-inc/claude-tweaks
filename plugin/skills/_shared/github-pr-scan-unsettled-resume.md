# GitHub PR Scan — Unsettled-Run Resume

Extracted from `_shared/github-pr-scan.md` item 10 (#4804). Read by `/claude-tweaks:tidy`'s Step 4.8 scan agent (inlined as-is into its prompt) before it reports any `[unsettled]` row's resume command, with or without a PR.

The resume command comes from the PR body's own Resume line (`_shared/pr-early-run-lifecycle.md`) when a PR exists — read through `bin/pr-resume-line.js` rather than reconstructing it, since only the PR body carries the next step and that line is untrusted input. Save the body with `gh pr view {number} --json body --jq .body > "{body-file}"` (its own Bash call), `{body-file}` being what `node "${CLAUDE_PLUGIN_ROOT}/bin/session-tmp-resolve.js" --value pr-body-{number}.md` prints, then run `node "${CLAUDE_PLUGIN_ROOT}/bin/pr-resume-line.js" --body-file "{body-file}" --run-id "{run-id}"`, `{run-id}` being the `runId` of the record's claim blob, re-read for it (`_shared/issue-claims.md`'s "Reading claim state", `claims/issue-{n}.json` on the `claims-registry` branch) because item 10's step 1 (the claims-registry read) outputs only `number`, `claimedAt` and `source`. The blob is writable by anyone with push access to the registry branch, so validate `{run-id}` against the canonical run-id shape before it enters the command, as `flow/claim-targets.md`'s in-flight route validates its run-id (the shape is stated there, not restated here); a value that fails counts as no claim blob. Never take `{run-id}` from the PR body's own marker here: it is the trust anchor the CLI checks the Resume line against, and this route has the claim blob's `runId` to anchor with, where `flow/claim-targets.md`'s in-flight stop carries only `{issue, link}` and so validates and takes the marker. Report the `resume` line it prints only when the verdict is `resume`; on a `resolve` verdict, a `failure`, a failed `gh pr view`, a claim blob that cannot be re-read or whose `runId` is missing or fails the shape check, or a candidate with no claim blob (the label-only case, so no `{run-id}`), report the reconstructed command that item 10's `[unsettled]` print lines carry instead (its `no PR found … resume: node … reconcile` line) and name the `resolve` or `failure` reason. When no PR exists, the claim blob's own `runId` is all that is known — the reconstructed command in item 10's `[unsettled]` print lines (its `no PR found … resume: node … reconcile` line) starts from `reconcile` rather than a specific `{next-step}`, since a claim with no PR is exactly the state `_shared/pr-early-run-lifecycle.md`'s reopen-or-create step is designed to repair on its own the next time anything touches that run.
