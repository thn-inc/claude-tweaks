## Comment ordering

Anything that must land on the PR posts **before** the merge call (Step 3) — the verdict/brief
comments from `_shared/pr-run-comments.md` already do, per their own citing sites' phase-exit
ordering. Anything this procedure itself posts (the conflict/degrade comment) is
**after**-the-fact information about why the merge didn't complete, so it posts once the outcome
is known, never speculatively before.

## Rationale notes

Named rationale and history moved out of `pr-first-merge.md`'s operative head (#5153), each cited from its original place.

- **Header history.** `pr-first-merge.md` supersedes and closes #335 (the two independently-authored auto-merge implementations these three files carried) and #299 (the fast-lane `git -C "$RUN_DIR"` worktree/branch anchoring defect — obsolete once merge needs no checkout at all).
- **Step 1, why order is load-bearing.** The merge closes the record(s) via its `Fixes` lines, so labeling must land while every record is still open. A caller that merges before labeling silently drops acceptance sign-off. Step 1 is unchanged from the citing files' own gate: this procedure does not touch layers 1-2, only execution.
- **Step 2, where the draft comes from.** The PR was opened as a draft at run start (`_shared/pr-early-run-lifecycle.md`); a re-entry may find it already undrafted.
- **Step 1.5 incident.** One occurrence (Dispatch hub run #9, 2026-08-26, group [#251]) reached this merge step with a curation-row commit still pending, landing after the merge instead of before it.
- **Step 1.5, why a missing `engine-state.json` skips the guard.** Phase 2 had nothing open (every registry row closed), or the run took `curation-engine.md` section 6's prose fallback, which writes no `engine-state.json`.
- **Step 1.5, why exit `0` suffices.** This is the exact check Phase 2's own Step 3 already ran once (`curation-engine.md` section 2) — re-running it here is idempotent (`render` performs no writes) and catches a Phase 2 that was skipped, interrupted, or that this merge step is reached ahead of, out of documented order. Exit `0` means every worklist row Phase 2 opened has a recorded result — and, by `curation-engine.md` section 4's own sequencing (the serial-commit pass runs, and every applied finding's commit lands, strictly **before** the `record` call that produces that recorded result), every applied finding's commit has therefore already landed too. Nothing further to check: nothing this procedure could add to a `git status` scan tells it more than `render --strict`'s own exit code already does.
- **Step 2, why the already-ready guard exists.** (Empirically, `gh pr ready` on an already-ready PR is itself a harmless no-op — exit 0, a `! Pull request … is already "ready for review"` warning on stderr, no error — so this guard is not error-avoidance. It exists to keep the decision log accurate: an unconditional call would log "undrafted" every re-entry even when nothing changed.)
- **Bounded watch is fixed, not a policy key.** `merge-when-green` (arming) is the no-wait path, `wait` is its fallback, and a repo where 15 minutes is chronically wrong should enable required checks/auto-merge rather than tune a knob (parent #558's one-lever decision; this bullet is the timeout's own rationale, cited from `pr-first-merge.md`'s Bounded watch).
- **Why the `Fixes` lines are restated.** So the merge commit message's `Fixes` lines are the PR body's (`_shared/pr-checklist-refresh.md`'s pre-merge refresh), restated in `pr-first-merge.md`'s Step 3 because GitHub closes records from them only when the merge lands on the repo's default branch, and the lines travel with the commit when it is later promoted; on a non-default integration branch they close nothing, and, on a `merged` outcome, `pr-first-merge-post-merge.md`'s Step 4.0 closes those records itself (after an `armed` merge, the reconciler's Step 4.0 does — #4599).
- **Step 3 eval-guard.** Why: the worktree Bash guard refuses `eval` and a `gh` argument computed at runtime, and every pr-first merge runs from a worktree session (#3522).
- **Armed outcome, who observes `merged`.** Either this same session observes it later (unlikely — sessions don't poll) or the reconciler does at its next trigger point (`_shared/pr-run-comments.md`'s consumer table).
- **Armed outcome, when cleanup converges.** The reconciler's trigger points (`_shared/pr-run-comments.md`'s consumer table): session-start, dispatch queue-pull, routine kickoffs, tidy, all converge on the merged-PR evidence eventually.
- **Sequential multi-branch merges.** The invoking session serializes them one at a time. Each later branch's own single update-from-base attempt merges from whichever tip the just-advanced integration branch now has — a genuinely later branch's conflict is checked against real current state, not a stale snapshot from before the earlier branches merged.
- **A ready run that verified nothing (#5153).** A post-ready run that concluded `skipped`, `cancelled`, `action_required` or `stale` counts for nothing: the ready-run read skips it and the newest remaining run decides. That closes a race: a push made seconds before `gh pr ready` can start a `synchronize` run created after `readySince` whose payload still says `draft: true`, so its draft-skipped jobs skip, and close-out's update-then-Mark-ready sequence is the likeliest trigger. Such a run no longer satisfies the requirement. The cost: a ready workflow whose post-ready runs all skip never gets a counted run, so the run parks with `checks-pending-timeout (no run since ready: {file})` naming that file — failing closed, never silently green.
- **Step 2.5, why the head runs are read.** The rollup lists only the checks GitHub has registered so far, so a partial rollup — some workflows reported, others not yet registered — reads green while a sibling workflow is still pending.
- **Step 2.5, why a held conclusion reads pending (#3467).** A `CANCELLED`, `ACTION_REQUIRED` or `STALE` run did not fail, so the remedy is a rerun, not a fix round. `SKIPPED` stays green because draft-time fix-label jobs skip. A newer successful run of the same check reads green because only the newest counts, and `cancel-in-progress` cancels runs of older shas. The code twin orders by the start-time fields `startedAt`, `run_started_at`, `createdAt` and `created_at` (the first present), then by the id fields `databaseId` and `id`. A held row with no name cannot be grouped, so it holds on its own.
- **Step 2.5, why an empty rollup on a DIRTY or CONFLICTING PR is a conflict (#3607).** A branch that conflicts with its base gets no `pull_request` workflow runs, so its rollup stays empty and waiting only parks it as `checks-pending-timeout`.
- **Step 2.5, why an empty rollup otherwise reads pending.** GitHub populates the rollup seconds after a push, not instantly, so an empty one means the checks have not reported yet.
- **Never rewrite the integration branch, why.** The PR's recorded `mergeCommit`, merged-PR landed-proofs and release tooling key on the commit GitHub created, so a rewrite orphans them and re-authors that commit (#3325 → `9c9f5e722`, #3347).
- **Step 2, why this procedure may undraft.** GitHub blocks merging (auto or immediate) on a draft PR by default, and this procedure only runs after both authorization and content-judgment layers already passed.
- **Step 2.5, why `merge-when-green`/`wait` imply PR CI.** `_shared/policy-schema-coverage.md`'s coverage block derives those values only when a `pull_request`-triggered workflow exists, and an explicit value is a statement that CI is expected.
- **Step 3 item 1, why not an immediate merge.** The immediate merge is exactly the race both values exist to close.
- **Step 3 item 2, why no auto-merge is left to arm.** It was already ruled out by reaching item 2 from branch 1, or `--auto` itself is not what failed — a plain `--squash` attempt hit this directly.
- **Step 3 item 5, why the conservative branch.** The conservative branch is always safe, while guessing wrong on a real failure (e.g. treating a genuine conflict as a transient blip and retrying) is not.
- **Step 3, why `{title-arg}` is pasted verbatim.** It is already POSIX single-quoted, so a `$(…)`, backtick, or `'` in the title stays inert.
- **The shape, what the merge no longer needs.** No `close-run`-before-merge relief, branch-switch guard, push-from-worktree rule or scratch-worktree conflict procedure.
- **Conflict path, why re-enter Step 2.5.** The pushed head has its own CI to read before any merge.
- **Conflict path, how a human resolves it.** Check out the branch, resolve, push — no scratch-worktree ceremony.
- **Red path, why it never prompts.** A park is a HARD-GATE-class stop written as park-and-surface: the `_shared/auto-mode-contract.md` strict rule holds, so there is never a mid-pipeline prompt; the human-facing surface is dispatch's resume confirmation (`dispatch/SKILL.md`, "Confirm before resuming").
- **Red path, why names never go inline.** Check names come from the PR's own workflow YAML (third-party-controlled on a fork PR).
- **Bounded watch, why head runs are counted from the saved file.** The worktree guard refuses a `--jq` program inside the loop (`_shared/scratch-worktree.md` §7).
- **Bounded watch, known fail-closed divergence (#3467).** The watch's held mapping reads `gh pr checks` states, which gh deduplicates newest-per-check within the rollup only. A cancelled rollup job whose newer run of the same name exists only as a head run, and not in the rollup, keeps the watch waiting until the bound. It then parks as `checks-pending-timeout`, whose remedy is a rerun, never a merge. `classifyRollup` reads that case green. The fence takes the conservative direction because the merge bundle has no byte room for a cross-source comparison, and a rerun registers its check run in the rollup in the ordinary case.

## Forge-cooperation path

Cited from Step 2.5. A merge attempt rejected by *org-owned required checks* — the state read shows `mergeStateStatus: BLOCKED` with every rollup entry green (required reviews or org-owned required checks the forge is enforcing) — is the forge enforcing a stricter policy than the lever (classified from the state read, never a stderr string — capture (b) in the Signatures section below). Report it as such, arm `--auto` (Step 3's own call — the merge lands when the forge is satisfied), and stop: never retry-loop, never suggest bypassing protection.

## PR-event settle window (#3468)

Cited from Step 2.5's settle bullet. GitHub creates a PR's `pull_request` workflow run a few seconds after the push, so a read in that gap sees only the push-triggered runs. When those are green, the head reads green before the PR's own CI exists. Neither the rollup nor `gh run list --commit` can show a run GitHub has not created yet.

- **The rule.** With PR CI and no head run whose `event` is `pull_request` or `pull_request_target`, the PR reads pending until 60 seconds after the latest known of: the PR's `createdAt`, and the earliest head run GitHub created under any event. With no head run at all, the head commit's committer date stands in for the run time. Any time the rule needs that cannot be read (a missing or unparseable PR `createdAt`; no parseable run `createdAt` and no committer date) keeps it pending: never green, and the bound parks it. After the window, the absence of a PR-event run means none applies (a path-filtered PR) and the other rules decide. Red still wins inside the window. Code twin: `bin/lib/pr-checks/classify.js`'s `prEventSettle` (`PR_EVENT_SETTLE_MS`), which `classifyRollup`, `pr-checks.js`, the driver merge gate and the learned-skills drain all apply.
- **Why the PR's `createdAt` bounds the start.** A PR opened after its head was pushed gets its `pull_request` run only once it opens, so a window anchored on the push alone would already be closed.
- **Evidence.** Over the last 25 merged PRs (read 2026-11-26), GitHub created the `test` `pull_request` run 2 to 19 seconds after the push. In 9 of the 25, the push-only `track-issue-fixes` run had already completed 1 to 17 seconds before that, so a read in that gap saw only green. #5153's ready-run check closes this window only for workflows that skip draft PRs, and it reports `not-applicable` in this repository.
- **Cost.** A normal PR waits nothing extra. A path-filtered PR waits 60 seconds once.
- **Never arms `--auto`.** A read pending only on the settle window takes the `wait` row even when `mergeStateStatus` is `BLOCKED`: an armed merge lands as soon as the forge's required checks pass, and those need not include the PR workflow GitHub has not created yet, so arming would end the window early.
- **The bounded watch assumes PR CI.** Its `0)` arm passes `hasPrCi: true` under every lever it runs under, and so do the driver merge gate and the learned-skills drain (`bin/lib/driver/merge.js`'s `classify`, `bin/lib/learned-skills/drain.js`'s `judgePr`). Under a derived `off` on a repo with no PR workflow, each costs at most one 60-second wait, never a park.
- **Accepted residual: clock skew** (plan review, #3468). `now` is the local clock, while the anchor is GitHub's `createdAt` or the committer's date, so local-clock skew of more than the window can shorten or lengthen it. Not taken: reading `now` from GitHub's own clock. The pending bound still parks a window that never closes.
- **Rejected: matching workflow path filters against the PR's changed files.** It would re-implement GitHub's `branches`/`paths`/`paths-ignore`/`types` semantics, and every divergence would be a false green or a false hold.

## Why `--auto` alone is not a wait

(Task 0, captured on this repo.) On a repository with no required status checks, `gh pr merge --auto --squash` **merges immediately** — exit `0`, empty stdout and stderr, `autoMergeRequest: null`, the PR `MERGED` while its `test` check was still `pending`. There is no distinguishing signature: `--auto`'s success looks identical whether it armed or merged. That is the #540 mechanism itself. So "arm `--auto`" is a genuine wait **only when the state read shows the forge would hold the merge** — `mergeStateStatus: BLOCKED` while checks are pending (required checks / rulesets configured); anywhere else, arming *is* an immediate merge and this gate must not lean on it. That is why the pending column keys on `mergeStateStatus`, not on `--auto`'s exit code.

## Resume-to-merge

`dispatch/SKILL.md`'s "Confirm before resuming" confirmation applies this same lever as a single read-then-decide over both of Step 2.5's reads (the state read, the head-run `gh run list` read and the ready-run read; a not-yet-completed head run reads pending, a failing one red, an `awaiting` ready run pending, `draft-skip-without-ready-trigger` red; on a `DIRTY`/`CONFLICTING` PR those two take Step 2.5's conflict-first rule, the Conflict path, first) (green → proceed; red → surface in the confirmation; pending with `mergeStateStatus: BLOCKED` → arm `--auto`, since the forge is what holds it; pending with any other `mergeStateStatus` → do **not** arm — on an unprotected repo arming *is* an immediate merge (capture (a)), so the confirmation itself carries the choice: wait for green, or leave parked) — a human is present on resume, so it never runs the bounded watch.

No signature distinguishes "armed" from "merged" — only the follow-up `gh pr view` does (Step 3.6).
- (b) merge rejected by required checks: not captured — this repo has no branch protection or rulesets (`gh api repos/{owner}/{repo}/branches/main/protection` → HTTP 404 "Branch not protected"; `…/rules/branches/main` → `[]`); classification for this path rests on the state read (`mergeStateStatus: BLOCKED` with a green rollup), never on a stderr string.
- (c) `gh pr checks {n} --watch --fail-fast` on a failing check: rows like `test	fail	35s	https://github.com/…/actions/runs/…` (each check name / `pass`|`fail`|`pending`|`skipping` / duration / URL), `exit=1`. (c2) `gh pr checks {n}` while a check is still running: `test	pending	0	https://…`, `exit=8`.
- (d) `gh pr view {n} --json state,mergeStateStatus,statusCheckRollup` — green (open draft PR #588, read-only): `{"mergeStateStatus":"CLEAN","rollup":[{"conclusion":"SUCCESS","name":"label-fix-branch","status":"COMPLETED"},{"conclusion":"SUCCESS","name":"test","status":"COMPLETED"},{"conclusion":"SKIPPED","name":"cleanup-fix-labels","status":"COMPLETED"}],"state":"OPEN"}`; failing rollup entry: `{"conclusion":"FAILURE","name":"test","status":"COMPLETED"}` (observed on #591 after merge, `mergeStateStatus: UNKNOWN` — the value GitHub reports once a PR is `MERGED`); the `mergeStateStatus` value of an *open* PR with failing checks was not captured (the probe merged via (a) before its checks failed) — which is why red is classified from `statusCheckRollup[].conclusion`, not from `mergeStateStatus`.
- (e) PR #3390 (#3316 wrap-up, 2026-10-17): right after a push the rollup and `gh pr checks` held only `label-fix-branch` (`SUCCESS`) and `cleanup-fix-labels` (`SKIPPED`), and `gh pr checks` exited `0`; the `pull_request` `test` run 39042323352 for the same head existed with status `pending` but was not yet in the rollup. Re-captured on PR #3425 (2026-10-17): the rollup listed `test` `IN_PROGRESS` beside those two, and `gh run list --commit {full sha}` listed the `test` run `in_progress` (its `conclusion` empty) next to the completed `push` run; the same command with the abbreviated sha `26d1037664` returned `[]`.
- Also captured: `gh pr merge` against an already-merged PR: stderr `! Pull request {owner}/{repo}#{n} was already merged`, `exit=0` — a no-op, not an error; the state read (`state: MERGED`) catches it first.
- (f) PR #5156 (2026-11-11): the `ReadyForReviewEvent` `createdAt` was `2026-11-11T00:45:28Z`, and the head's only `pull_request` run, `test.yml` run 42931704440, was created `2026-11-11T00:29:06Z`. This repo's bare `pull_request:` (default types) starts no run on ready, so every run on that head predates `readySince`. The ready-event window the gate waits through is the same not-yet-registered shape as capture (e).
- (g) `gh pr checks` held-state exit codes, from gh v2.103.3's own source (`cli/cli` `pkg/cmd/pr/checks/aggregate.go`, `checks.go`; re-read on the installed gh for #3467, bucket mapping unchanged; no PR in this repo's last 1,000 carried a held conclusion, so there is no live sample): `CANCELLED` → bucket `cancel`, counted in neither `Failed` nor `Pending`, so a lone cancelled check exits `0`; `ACTION_REQUIRED` → bucket `fail`, exit `1`; `STALE` → bucket `pending`, exit `8`; `STARTUP_FAILURE` → bucket `pending`, exit `8` (a mid-watch `STARTUP_FAILURE` parks as `checks-pending-timeout` at the bound, pre-existing; red only on a Step 2.5 entry read). With `--json` the command returns before its exit-code logic, so it exits `0` once checks exist; the `no checks reported` error still fires. gh keeps only the newest entry per check name/workflow/event, by `startedAt`. The watch therefore re-reads `--json name,state` on exit `0` or `1` and maps `FAILING_CONCLUSIONS` to red and `HELD_CONCLUSIONS` to pending.
