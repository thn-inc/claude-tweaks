## `worktree-always` coverage — canonical

**This block is the single statement of what the gate intercepts.** Every other file cites it; none restates the list. `bin/lib/hooks/pre-tool-use.js`'s exported `GATE_COVERAGE` constant is its machine counterpart, and `tests/hooks-gate-coverage.test.js` asserts the two agree — so widening the gate fails a test until this block is updated.

That binding exists because the list has drifted before. The gate was widened twice on 2026-07-20 (`push` in `c8f929e1`, `cp`/`mv`/`tee` in `cab6142b`) and neither commit swept the prose describing it; five skill files went on documenting the pre-widening gate, three of them prescribing procedures the widened gate denies (#138).

<!-- gate-coverage:begin -->
- Tools: `Edit`, `Write`, `NotebookEdit`
- Git actions: `commit`, `push`, `mv`, `rm`, `update-ref`, `apply`
- Bash write shapes: `cp`, `mv`, `tee`, `sed`, `perl`, `install`, `ln`, `truncate`, `dd`
- Bash redirections: `>`, `>>`, `>|`, `&>`, `&>>`
- Exemptions: `.claude-tweaks/pipelines/`, `.claude-tweaks/policy.yml`, an allowlisted `policy-only` commit, an allowlisted `delete-only or ff-integration-branch` push, and a write target that is `gitignored` in its own repo
<!-- gate-coverage:end -->

`sed` and `perl` count only for an **in-place** edit (`-i`, `-i.bak`, `--in-place`, or a bundled `-pi`/`-ni`). A plain read such as `sed -n '…p' file` is not a write and stays allowed everywhere, including the main checkout.

**The cost that buys.** `hooks.json` registers one unconditional `Bash` handler per tool-use event, and `bin/lib/hooks/bash-prefilter.js` keys on a command *word*, not its flags. So every `sed` reaches the full handler — read-only invocations included, where it resolves no target and allows. What that breadth costs is the *marginal* cost, because every Bash call already pays the prefilter's skip path (an `echo hi` payload, 57.8 ms best idle / 97.9 ms best under contention): full path minus skip path, **about 49 ms idle (106.5 − 57.8) and about 54 ms under three concurrent test suites (152.3 − 97.9)**, best of 30 on this repo's Windows box (Node 24, 16 cores; the full path is a `git commit` payload in a non-policy repo, 106.5 ms best / 134.2 ms median idle and 152.3 ms best / 304.3 ms median under contention in absolute terms; #3074; a Windows measurement, not comparable to the older figures this replaced). The figure is an upper bound for read-only `sed`, which resolves no target and allows, so the handler's work there is only the module load and the parse. The skip path, not a bare `node -e ""` launch (54.8 ms idle / 87.5 ms contention, best; a baseline that would read the cost as only 6% higher idle and 19% higher under contention) and not the absolute full-path figures, is the baseline, because it is what every Bash call already pays; quoting 106.5 / 152.3 ms as the cost is the real error, overstating it about twofold or more. The arithmetic is the trade the issue measured: before #3074, about 17% of Bash calls in one day of transcripts had a `$VAR`/loop shape and fanned out to 28 + 18 launches (≈ 8 launches per call on average); after it, every Bash call costs 2 launches, one per event. Breadth was chosen over precision deliberately: the prefilter keys on the command *word* `sed`/`perl`, not their flags, and narrowing it to flag patterns would miss `sed -ni`, `sed --in-place`, and `perl -pi -e`, reintroducing exactly the silent-gap class this covers. A false negative here is invisible; the latency is not.

**What the gate can see at all.** It is a `PreToolUse` hook, so it inspects *tool calls* — `Edit`/`Write`/`NotebookEdit` inputs and the command string of a `Bash` call. Git and filesystem work performed by the plugin's own Node code via `execFileSync` never passes through a tool call and is therefore never gated: `bin/lib/health-core/durable-state.js`'s `git push` to the `health-state` branch is the standing example, and it is correct as written. Do not "fix" such a call by routing it through Bash.

**Not covered — deliberately (#976/IL-141).** `git commit`/`git push`/`git mv`/`git rm`/`git update-ref`/`git apply` are the only git subcommands this gate classifies as a write; `git merge`, `git rebase`, `git cherry-pick`, `git reset`, `git checkout`, `git switch`, `git restore`, `git stash`, `git pull`, `git fetch`, and every other git subcommand pass freely. The four plumbing verbs above were added because each is UNAMBIGUOUSLY a write in every ordinary invocation; the excluded ones each have a common, genuinely non-mutating shape (`git stash list`/`show`, a path-less `git reset`, `git checkout <branch>` with no path args, …) that this gate's one-level subcommand check cannot distinguish from the mutating form without resolving a second token — the coverage stays narrow rather than pattern-matching every git subcommand indiscriminately. Extend evidence-driven, on a real incident, not speculatively (`bin/lib/hooks/git-command.js`'s `PLUMBING_WRITE_SUBCOMMANDS` carries the same rationale). Two write shapes remain uncovered:

- **Opaque program strings** (`python -c`, `sh -c`, `awk`). The write target lives inside a program this cannot parse, so no matcher and no latency budget would help.
- **A win32 drive-relative path on another drive** (`D:repo` from a `C:\…` session cwd, #4281). Windows resolves it against drive D's own current directory, which the hook cannot see, so the guard parsers report no target and the call is allowed rather than gated on a fabricated one. A same-drive value (`C:x` from `C:\…`) resolves and is gated.

**Bare shell redirection is covered (#3080).** `git-command.js`'s `redirectWriteTargets` resolves `>`, `>>`, `>|`, `&>`, `&>>`, and fd-prefixed `N>`/`N>>` targets for every segment `fileWriteTargets` scans, regardless of command word, so `echo`/`printf`/`cat`/a bare `> f` are all reached, not just the shapes above, and so is a `cd` line, whose redirect lands in the cwd before the cd (`cd sub > f` writes `f` where the line starts, #4281). The operator may stand alone (`cmd > f`), be glued to its target (`cmd >f`, or a quoted target as in `echo foo>"x y"`), or be glued to a preceding word (`echo foo>x`, #4015), including a word that holds a quoted span (`echo "hi">x`) or an escaped character (`echo foo\ bar>x`, #4210). Only a `>` that is outside every quote and not itself escaped is an operator, in any position: `echo "foo>x"`, `echo foo">"x`, `echo ">x"`, `--body "> quoted reply"`, `echo foo\>x`, and a `>` that a `$VAR` expands to stay literal, and so does a `>` inside a `$( … )`, `${ … }`, or backtick nested in double quotes (`echo "$(jq ".a>1" f)"`), which resolves no target. A glued redirect also needs the bare part of the word before it to hold no `$`, backtick, or `(`, since each can put the `>` inside an expansion or arithmetic (`((i>0))`); the one exception is a word that is exactly one balanced bare group, a subshell, command substitution, or process substitution (`(ls)>out`, `$(date)>x`, `diff <(a) <(b)>out`). A `>` inside a `[[ … ]]` or `(( … ))` body is a comparison and never counts. `bash-prefilter.js`'s `hasFileRedirection` reuses the same parser (`forEachShellSegment` + `redirectRawTargets`, each value resolved through `resolveWriteTarget`) rather than a second scanner, so the prefilter never skips a target the parser reports. A win32 drive-relative target (`> D:x`) resolves only against a cwd on its own drive, so the prefilter anchors it at that drive's root rather than its placeholder cwd (#4281). It was declined once on the per-redirecting-call marginal cost quoted above; re-measured after landing (same methodology, this repo's macOS dev box, best of 20): a redirection-bearing skip-path call (`cmd 2>&1`, `cmd > /dev/null`) costs about the same as the plain skip path (both ~0.5 ms over bare-Node control, full path ~15 ms) — the added scan is pure-JS parsing with no heavier `require`, so it doesn't move a redirecting call onto the full-handler cost at all. An fd duplication (`>&2`, `2>&1`) and a `DEVNULL_LIKE` sink (`/dev/null`, `/dev/stdout`, `/dev/stderr`) are excluded from both the parser and the prefilter, which is what keeps the common `2>&1`/`> /dev/null` shapes cheap. A heredoc body is data for the program it is fed to, not shell, so the scan drops each body and its closing delimiter first (`stripHeredocBodies`, #3989): a `>` inside `node x.js <<EOF … EOF` is never a redirection, while a redirect after the closing delimiter or on the opener line still is. A body is stripped only when every command on the opener line is a data reader: `cat`, `tee`, `gh`, `read`, `node`, `python`, `python3`, `jq`, `wc`, or `git` given a data subcommand (`commit`, `tag`, `notes`, `apply`, `am`, `hash-object`, `interpret-trailers`, `update-ref`, `cat-file`, found after git's global flags, so `git bisect run sh` and `git rebase -x sh` are not readers; git behind a `-c`/`--config-env` flag or a `NAME=value` prefix, even behind a wrapper, is no reader for any subcommand, since configuration can make it run a command that reads stdin, as `git -c core.fsmonitor='sh -s' commit -F -` runs its body). The reader is named bare or by absolute path (`./cat` does not qualify, nor does a program word containing `$` or a backtick) and may sit behind a reader wrapper (`sudo`, `doas`, `env`, `nice`, `time`, `nohup`, `command`, `exec`; its option flags and `NAME=value` are skipped, the same bare-or-absolute rule applies to it, and `env -S`/`--split-string`/`-P` make the line a non-reader). The line's commands are cut at segment separators and at every unquoted lone `&` (not `&&`, `&>`, `>&`, `<&`, `|&`), so a backgrounded command is a command of its own. A neighbour command whose own program is `cd`, `mkdir`, `true`, `:`, `echo` or `printf` also passes, and so does `git add` (after git's global flags) unless it reads pathspecs from stdin (`--pathspec-from-file`) or carries a `-c`/`--config-env` flag or a leading `NAME=value` (configuration can make it run a command, as `git -c core.fsmonitor='sh -s' add` runs its stdin); none passes when it carries `$(` or a backtick, and behind a wrapper those words are not readers. Nor is a reader whose command carries `$(` or a backtick anywhere, quoted or not, unless it is the heredoc's own command, no pipe feeds it, and every substitution stands before its first `<<`: in a pipeline element the substitution runs with that element's stdin, so `cat <<'EOF' | jq "$(bash)"` runs its body, and a redirection word after the `<<` is expanded with the body already on fd 0, so `cat <<'EOF' > "$(bash)"` runs it too, while bash expands the own command's words before the `<<` first, so `gh pr create --title "$(git log -1 --format=%s)" --body-file - <<'EOF'` still strips (a `${ … }` expansion and an arithmetic `$(( … ))` are no substitution, though `$((cmd) )`, whose first unbalanced `)` is not doubled, is a `$(` holding a subshell, and a heredoc opened inside a quoted `"$( … )"` is judged by that substitution's own command, so a `"$(cat <<'EOF' … EOF)"` message strips its body while `"$(bash <<'EOF' … EOF)"` keeps it, #4210). The scan keeps a body, failing closed, on what it checks — the opener line, plus a structure left open on an earlier line: the body has no closing delimiter (the text from that opener on is kept as written); the delimiter is unquoted and the body holds `$(` or a backtick (bash expands it); the opener line ends in `|`, `&&`, or `||` (a later command receives the body); the opener line carries an unquoted group or process-substitution token (`(`, `{`, `>(`, `<(`; the quote handling is escape-aware) or ANSI-C `$'` quoting; any command on the line is not a data reader, so `while read l; do …; done <<EOF` keeps its body by design; or an earlier line, or the opener line itself, ends with an unquoted paren, brace or backtick left open (`(`, `$(`, `<(`, `{`, …) or an `if`/`for`/`while`/`until`/`select`/`case` without its closer, or carries an unquoted `$'`, after which every later body is kept. A kept body is scanned as its own chunk, from fresh quote state and the cwd at its opener, and the outer scan resumes after its delimiter with its own cwd, so a quote or `cd` in body prose never reaches the outer text. A kept body whose opener line names no known shell (`sh`, `bash`, `zsh`, `dash`, `ksh`, `mksh`, `ash`), such as one fed to `make -f -` or `at`, may not run as one script, so it is also scanned whole, with no inner heredoc planned. Two parser rules: in an unquoted-delimiter heredoc a line ending in an odd run of backslashes directly before `\n` is joined with the next line before the delimiter comparison (backslash-CR-LF does not continue, and a quoted delimiter never joins), and `<<` inside an unclosed `$[ … ]` or `(( … ))`/`$(( … ))` is arithmetic, not an opener; both span lines, and the single parens inside a `((` are counted, so `((cd x && ls) | cat)` closes at its last `)`. A body written to a file and executed later (`cat > s.sh <<EOF … EOF; bash s.sh`) is not covered: it is the documented opaque-program gap. The prefilter applies the same stripping, so the two never disagree.

Do not write a procedure that depends on the opaque-program-string gap: it is an unpatched hole, not a supported bypass. And do not add a `fileWriteTargets` branch without the matching prefilter word (or, for redirection, without going through `hasFileRedirection`) in `bin/lib/hooks/bash-prefilter.js` — the full handler never runs, so the branch is dead code that reads exactly like a fix. `tests/hooks-bash-prefilter.test.js`'s differential corpus runs a hand-kept command list through the five guard parsers (`gitTargets`, `fileWriteTargets`, `mkdirTargets`, `teardownTargets`, `powershellOpaqueCommand`) and fails when a command one of them targets is skipped by the prefilter — a new parser or word needs its own corpus line — precisely because that asymmetry hid `sed -i` for months.

**Non-bare `git` invocations (#590).** `gitTargets` (`bin/lib/hooks/git-command.js`) recognizes three shapes a real shell treats identically to a bare `git commit`/`git push`: an env-var-assignment prefix (`FOO=1 git commit`), the `env` builtin wrapping the real command (`env git commit`, `env -i git commit`), and a directory-qualified executable ending in `/git` (`/usr/bin/git commit`). Hook-side coverage is end to end for every shape: `bash-prefilter.js` scans the whole command string for a `git`/`env` word anywhere, as a shell word or a path basename, and `gitTargets` returns a target for each (probed on the #3074 branch: `gitTargets('/usr/bin/git commit -m x', '/r')`, `'env -i git commit -m x'`, `'env FOO=1 git commit -m x'`, `'env git commit -m x'`, and `'FOO=1 git commit -m x'` each return `[{action: 'commit', dir: '/r'}]`):

- **Env-var-assignment prefix** (`FOO=1 git commit`) — covered: the prefilter's `git` word scan reaches it regardless of the leading `NAME=value`.
- **Bare `env git ...`** — covered: reached via the `env` and `git` words.
- **Path-qualified (`/usr/bin/git ...`)** — covered: the prefilter takes path basenames, so it is reached, and `gitTargets` recognizes it. This was declined while `hooks.json` keyed on literal leading command words; the single-handler layout removed that limit.
- **`env` with its own flags/assignments (`env -i git ...`, `env FOO=1 git ...`)** — covered: reached via `env`/`git`, and `gitTargets` resolves the wrapped command.

**The path exemptions.** File writes targeting a path under the repo's own `.claude-tweaks/pipelines/` are allowed from anywhere — that directory is plugin-owned, gitignored pipeline bookkeeping (run config, the auto-decision log, staged proposals), not the project work this gate isolates. It applies to file-write targets only: a `git commit`/`git push` target is the command's *working directory*, so exempting those by prefix would permit any commit merely issued from inside a run dir. The exemption also fails closed — a relative or unresolvable path is never exempt.

**A shell-variable path is unresolvable by construction, and unresolvable means unguarded, not denied.** The gate matches the literal command *text* — it never runs a shell to expand variables first, and its parser only substitutes a variable's value when the SAME command string assigns it (`RUN_DIR=...; sed -i ...`). A variable exported by an *earlier* command — the realistic shape for `$RUN_DIR`/`$PIPELINE_RUN_DIR`, which skills resolve once and reuse across turns — is never substituted. When the target stays unresolvable this way, the parser fabricates no guess and recognizes no write target at all, so this gate allows the write unconditionally: `sed -i ... "$RUN_DIR/config.yml"` runs for real, with the actual shell expanding the variable, entirely outside this gate's checks and the `.claude-tweaks/pipelines/` exemption's own audit trail (confirmed by `tests/hooks-pre-tool-use.test.js`'s "an unprovable target on a new shape fabricates nothing" case — the result is `{}`, i.e. allow). Only when the variable IS assigned inline and resolvable does the ordinary exemption logic even run — a resolved path under `.claude-tweaks/pipelines/` is allowed, one that resolves elsewhere inside the policed repo is denied (`tests/hooks-pre-tool-use.test.js`'s in-command-variable cases). This is documentation-only — the gate's posture here is already correct by design (never fabricate a guess), not a bug to fix. The practical upshot: a hand-rolled `sed -i` on `config.yml` gets no reliable protection either way, so skip it entirely and use `bin/set-config.js` (`_shared/pipeline-run-dir.md`'s Sanctioned-write CLIs), which takes `--run <run-dir>` as a separate argument rather than a pre-built path string, so there is nothing left for the gate to fail to resolve.

The second (#537): an `Edit`/`Write`/`NotebookEdit` — the three file tools only, never a Bash write shape (`tee`/`cp`/`sed -i`/…), which stays gated for this file — whose target, once fully resolved to a real path (symlinks followed, `..` normalized, on-disk casing canonicalized), IS the repo root's `.claude-tweaks/policy.yml` — exact identity, never containment, so a symlinked alias resolves to the same allow and `policy.yml` itself being swapped for a symlink elsewhere resolves to the same deny. Alongside it, `git commit` is allowed when the **entire command string** matches an allowlist grammar — exactly `git commit` plus one or more `-m`/`--message` args and an optional `--no-verify`, in any order, and nothing else: no other flag, no pathspec, no shell operator (`&&`, `;`, `|`, `` $() ``, backticks), no env-var prefix, no path to `git` other than the bare word — **and** the staged set (`git diff --cached --name-status`) is provably one row — an Add, Modify, or Delete of `.claude-tweaks/policy.yml`; a rename or copy *into* that path is rejected on its status letter, since `--name-only` would collapse it to a single misleading line. A third exemption (#658) admits a content-free, ref-only `git push`: the **entire command string** matches `git [-C <path>] push <remote> --delete <branch>` or `git [-C <path>] push <remote> :<branch>` — one optional `-C`, one remote, one branch, nothing else, the same no-other-flag/no-shell-operator/no-env-var-prefix/no-path-to-git discipline as the commit allowlist, minus the staged-set check (a push's ref target is determined by the command text alone, unlike a commit's content). Any other `git push` — a content push, or a delete-shaped attempt riding a compound command or an extra flag — stays gated. A fourth exemption (#2542) admits a fast-forward push of the CANONICAL integration branch: the entire command string matches the bare `git push <remote> <branch>` shape (no `--force`/`-f`, no `+`-prefixed or `:`-refspec, no other flag, the same no-shell-operator/no-env-var-prefix/no-path-to-git discipline), `<remote>` is `origin`, `<branch>` resolves to the project's own integration branch (the same policy-key-then-local-probe resolution `hasMaterializeCommit` already uses just below), and a live `git merge-base --is-ancestor origin/<branch> <branch>` proves the push adds no divergent history. Unlike the delete-only exemption, this one needs a real git query — a fast-forward is a fact about ref state a command string alone can never establish. Any other push of the integration branch — a non-fast-forward, a force, or a push with no resolvable remote-tracking ref to compare against — stays gated. All four exemptions fail closed: anything unprovable about a path, a command's grammar, the staged set, or ref ancestry keeps the deny.

The third path exemption (#1395): an exemptible write target — a file tool target OR a Bash write-shape target (`cp`/`mv`/`tee`/`sed -i`/…, unlike the fileTool-only `.claude-tweaks/policy.yml` exemption above) — whose fully-resolved path `git check-ignore -q` proves ignored in its OWN repo. Motivation: a gitignored runtime `.env` a docker compose in the main checkout reads is not the project work this gate isolates, even though writing it looks mechanically identical to a genuine wrong-checkout code write. Keyed on the write's TARGET only, never the invoking command's shape as a whole — `cp realfile.js .env` still resolves correctly (only `.env`, the destination, is checked; a tracked source file is never exempted by association). Fails closed on any git ambiguity: `check-ignore`'s exit `1` with no stderr is a genuine "not ignored" negative, never conflated with a real git failure (a fatal error, a timeout, a missing git) — see `isUntrackedOrIgnored`'s own header comment in `pre-tool-use.js`. Every allow through this exemption leaves a `gate-exempt-gitignored` breadcrumb event in the owning run's `events.jsonl`, unlike the other two path exemptions, which leave none — the issue's explicit auditability ask.

The issue also asked for a second, standalone "untracked, but not gitignored" branch via `git ls-files --error-unmatch`. That branch was built during triage and then deliberately reverted: git has no signal that distinguishes an existing, never-`git add`ed *deploy/scratch* artifact from existing, never-`git add`ed *real project content* (both read back identically — a non-zero, no-match exit — regardless of the path's actual purpose). Trusting untracked status alone would have blanket-exempted every not-yet-committed file created during ordinary iterative development, and — because neither `check-ignore` nor `ls-files` follow symlinks, answering only for the literal pathname — would have let a Bash write-shape (`tee`/`cp`) rewrite `.claude-tweaks/policy.yml` itself before its first commit, defeating both spec #537's Non-Goal (a shell rewrite of the enforcement file stays gated) and its symlink-swap identity defense. Proven empirically: three existing tests in `tests/hooks-policy-exemption.test.js` broke against the naive implementation before it was reverted. `isUntrackedOrIgnored`'s own header comment in `pre-tool-use.js` carries the full account.

**Consequence for procedures.** A `git push` from the main checkout is denied even after `close-run` clears the E1 worktree assignment (that clears wrong-checkout enforcement, not this policy) — unless the push is the bare branch-delete shape above (optionally with one `-C <path>`), which is exempt for exactly that post-teardown moment: once a worktree is gone there is nothing left to "retry inside" it, so `git push <remote> --delete <branch>` (or the `:<branch>` refspec form) is allowed straight from the main checkout. A merge followed by a content push must therefore be **two separate Bash calls** — the merge from the main checkout, the push from inside a linked worktree. Chaining them into one command gets the whole invocation denied before either half runs, since the gate inspects the full command string up front — this includes chaining a branch delete onto anything else, which loses its own exemption the same way. Two exceptions run from a main checkout without a worktree: an isolated `.claude-tweaks/policy.yml` edit plus its allowlisted, policy-only-staged commit, and a bare branch-delete push. Any push shape outside the allowlist — including one that only resembles a branch delete — is denied with a message naming the sanctioned fallback: `gh api -X DELETE repos/{owner}/{repo}/git/refs/heads/{branch}` or `gh pr merge --delete-branch`.

## Teardown gate coverage — canonical

**This block is the single statement of what the teardown gate intercepts** (`bin/lib/hooks/pre-tool-use.js`'s `GATE_COVERAGE.teardownTools`/`teardownGitCommands` are its machine counterpart; `tests/hooks-gate-coverage.test.js` pins the two). The gate denies teardown of a worktree recorded as a **non-terminal** (`active`/`interrupted`) pipeline run's assignment — `close-run` is the sanctioned exit, and clearing the assignment lifts the gate. It is run-*targeted* rather than run-independent: it fires only when a recorded assignment matches the teardown target, and every ambiguity (unresolvable target, no match, recorded path gone, corrupt run-state, unconfidently-parsed command) resolves to allow. Foreign-owned runs get a warn instead of a deny, with a `wd-foreign-teardown` event on the target run. The companion warn tier lives in `close-run` itself: closing a run with no recorded wrap-up invocation appends `close-without-wrapup` and prints a warning — never a block, because dispatch's close-before-merge is sanctioned and human-typed wrap-ups leave no ledger event (measured, spec #371 finding (e)). `skills/wrap-up/cleanup-procedures-execution.md`'s Section C closes the run (step 3.6) immediately before removing the worktree (step 4) — the sanctioned exit this gate's own deny message points to.

## `merge-verification` derivation — canonical

<!-- merge-verification-derivation:start -->
The single prose statement of the derived default (code twin: `bin/lib/merge-verification.js`'s `deriveMergeVerification`; every other file cites this block rather than restating it). Four branches, first match wins, no fall-through:

1. `integration-model` (`_shared/integration-model.md`) resolves `local-merge` → `off`. Short-circuits before any workflow read.
2. No PR-triggered CI → `off`. Detection reads only `{root}/.github/workflows/*.yml|*.yaml` and looks for a top-level `on:` naming `pull_request` or `pull_request_target` in any legal shape — bare string, flow array, block list, or mapping key. Trigger *presence* is a deliberate proxy for "CI verification is requested"; enforcement (branch protection) is out of scope. GitHub Actions-only by intent — a repo on another CI system derives `off` and opts in with the one-line explicit value.
3. Integration branch is the repository default branch → `merge-when-green`.
4. Any other (non-default) integration branch → `off`.

Branches 3–4 obtain both branches through the canonical resolution in `_shared/integration-branch.md` (its rank 3 `integration-branch:` policy key, else the rank-5 GitHub-default half) via the shared code resolver, never a hand-rolled detection. Every failed lookup — no `gh`, API error, no upstream, unreadable workflow file — resolves toward `off`, the permissive default, never toward the stricter value.
<!-- merge-verification-derivation:end -->
