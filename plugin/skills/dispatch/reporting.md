# Dispatch — Reporting

Per-firing output is one group's outcome (a drain firing with M ≤ `{budget}` groups: one report block per dispatched group) — there is **no consolidated multi-group console**. (See `SKILL.md`'s When to Use above.)

**A set of PRs is never uniformly mergeable on outcome labels alone.** Before any report — or any human instruction acted on in batch ("merge all these"), treats several PRs as ready to merge, verify each PR's own run individually: read that run's `manifest.yml` `specs[].status`/`specs[].phase` (`flow/multispec-pr-checklist.md`'s per-spec source of truth) and give any run that never reached wrap-up its own row saying so, rather than letting a group-level `pending-review`/`merged`/`blocked` label stand in for it. The PR's phase checklist corroborates that read, never replaces it — it is cumulative, run-level, and best-effort (`_shared/pr-checklist-refresh.md`).

**Fast-lane bundle header (#2066).** Before rendering a dispatched group's report block, check this run's `dispatch-fastlane-bundles.json` (`queue-pull-script.md`'s Step 2 output): when the group's member-number set equals (set-equality, not subset) an entry in that file, the block's header line names it a fast-lane bundle — `fast-lane bundle: #a, #b, #c — assembled by bundleFastLaneSingletons, cap {n}` — instead of the ordinary multi-spec group line. A bundle later partially excluded by the open-PR or blocked-by filters no longer equals its persisted entry, so a partial match renders as an ordinary group, never a stale bundle header.

**Predicted-conflict line (#3520).** In an explicit-list firing, a dispatched group whose member appears in a strong pair with another group dispatched this firing (`near-duplicate-pairs.md`'s `predictedConflicts` over `dispatch-near-dup-pairs.json`) carries one line in its report block, before the timing line: `predicted conflict with #{partner} (PR #{pr}) — merge #{first} first`. `{pr}` is the number of the `dispatch-drain-prs.json` entry (`drain-pr-overlap.md`'s Step 5 write) whose `closingIssueNumbers` includes `{partner}`, left out with its parentheses when none does; `{first}` is the earlier-dispatched member of the pair. Omitted when the group is in no such pair.

Each group's block ends with one timing line read from `{run-dir}/timing.json` (`bin/phase-timing.js --run "$PIPELINE_RUN_DIR" --markdown --transcript <call-1 transcript> --transcript <call-2 transcript>`, #1928) — never composed by hand: `timing: call-1 {m}m · call-2 {m}m · verify {n} run(s) ({modes}) · {k} tokens in / {m} out` — not `--auto-transcript`, which only sees the current session; omitted when the CLI printed a `tokens: transcript not found` note. An express group's block names its outcome as `express: {outcome}` (`_shared/express-lane.md`'s Outcomes), and its timing line passes the one express call's transcript to `phase-timing.js` in place of the two calls' (an `express-escalated` group passes it ahead of the ordinary calls').

A headless (Routine-fired) firing's report has nobody live to read it — the durable trace is the label state change, the claim-comment trail, and `decisions.md`, not a rendered console. Over time, a human sees the aggregate picture via `/claude-tweaks:tidy`'s own periodic sweep (`tidy/SKILL.md`).

`pending-review` outcomes park the group's `/flow`-created run dir, not the branch — at `supervised`/`trusted`, an unanswered Review Console `AskUserQuestion` during a headless firing is not an error, it is the expected resting state until a human resumes that session or the branch directly, or the claim's TTL expires and a later firing supersedes it. (At `unattended`, `consoleAutoResolve` completes the console instead of resting on it — see `_shared/autonomy-ceiling.md` and `wrap-up/review-console.md`'s Auto-resolution short-circuit.) Under `integration-model: pr-first` (`_shared/integration-model.md`), the branch itself never waited on parking to become public in the first place: `_shared/pr-early-run-lifecycle.md` opened its draft PR at run start, and every phase exit since has kept it current.

**Resuming a parked run.** "Resumes that session" above is not literal — the Task-tool subagent that hit the console has already exited by the time anyone reads this report, and there is no way to re-attach to it.

**Confirm before resuming.** Before running the re-invocation below — including when a human triggers the resume conversationally (e.g. replying "merge!" in chat) rather than by typing the command directly — read `resume-confirmation.md` in this skill's directory and follow it: the `AskUserQuestion` shape, the Recommended-derivation rule (shared with `review-console-interactive.md`'s merge confirmation, so the two can never disagree on the same PR state), why this stays a separate stop from the Review Console rather than folding the two together, why it carries no `autonomy`-ceiling carve-out (unconditional at every tier, including `unattended`), how the confirmation's values are sourced live, the resume-freshness probe, and the actual re-adoption mechanism.

`PushNotification` fires only at the retry ceiling, for auto-merge FYIs (Step 6's Settle procedure and Auto-merge gate, both in `settle-and-merge.md`), and for a headless plan-review needs-human block (sent by the blocked build itself, `build/plan-review.md`) — never per-firing just because a firing happened, to avoid notification fatigue.

**`already-shipped` groups report as a no-op, never `pending-review` (#2502).** When the first call's `OUTCOME` is `already-shipped` (`build/SKILL.md`'s Spec Step 2 "Already-shipped assessment", routed through `two-call-gate.md` §7), the group's report block states plainly that the record's deliverables were already on the base branch, names the staged Close proposal, and stops — no `pending-review` line, no timing line implying a review is waiting, and no `PushNotification` (nothing here is an FYI worth a notification; the record simply needed no work). This is the case the whole outcome exists to distinguish from a genuine review-pending build.

**A handed-off call is reported as a continuation, never a failure (#4027).** When a call reported `OUTCOME: handoff` and was continued (`two-call-gate.md` section 8), its group's block carries one line per continuation, `call-{1|2} handed off; continued with {NEXT_STEPS} ({n} of 3 this run)`, `{n}` counting the run's handoffs across both calls, and then reports the outcome of the call's last continuation like any other. Its timing line's `phase-timing.js` call passes each continuation's transcript as one more `--transcript` (the flag repeats). Only a refused handoff (a malformed `NEXT_STEPS`, or the run's fourth handoff, past the bound) reports as `build-test-blocked`/`blocked`, and it names that reason.

**Plan-review questions are relayed, not dropped (#3377).** When a group's first call reports `ISSUE #{n}: failed:plan-review-needs-human`, its report block quotes the record's `<!-- plan-review-question -->` comment (its link and each question) and closes with the next step: answer by editing #{n}'s body, then re-run `/claude-tweaks:dispatch #{n}` (or, when the firing was headless and the record is now `bot:blocked`, re-grant `auto:build` at `/claude-tweaks:backlog refine` first). The dispatched Task call cannot ask the human itself (no `AskUserQuestion` in a subagent) — this block is the stop's human-facing half. A non-headless block keeps `auto:build` with the claim released, so a later Routine drain may re-pick the still-unanswered record and block it headlessly (then `bot:blocked`) — answering on the record promptly avoids that spent run.
