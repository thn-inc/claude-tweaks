# Dispatch Step 2.5 — Answered Resumes (bare drain only)

Referenced by `SKILL.md` Step 2.5. Runs on the bare drain only, after Step 2's queue pull and before Step 3's ranking; the `#N`, `#N,#M,...`, `close-out` and `resume` forms never run it. It restarts, on its own draft PR, each record a plan-review stop left waiting (`build/plan-review.md`: a question comment, `needs:answer`, the grants kept) once a human has answered it (#5053). It never posts an `/answer` comment: a reply is only ever the human's. `{budget}` is the drain's, resolved as Step 3's Bare (drain) bullet resolves it, before this step runs.

**1. List.** Run `gh issue list --label needs:answer --state open --json number --limit {backlog-fetch-limit}` (`{backlog-fetch-limit}`: `node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-policy.js" --values backlog-fetch-limit`). An empty list prints `[]` with exit 0, also when the label does not exist yet: nothing to resume, go to Step 3. A non-zero exit prints its stderr line and goes to Step 3 with the whole budget. When Preflight took the MCP path (`gh` absent), skip this step and print `answered records not resumed: gh absent`, since the check below needs `gh`.

**2. Check.** For each number `{n}`, run `node "${CLAUDE_PLUGIN_ROOT}/bin/plan-review-answer.js" --issue {n} --check`, a read that writes nothing. Exit 3 (no trusted `/answer` reply yet, or no question comment): leave the record untouched. Exit 2 or 4: print its stderr line and leave the record untouched. Exit 0: keep the record, with the `questionCreatedAt` its JSON line carries.

**3. Order.** Sort the kept records by `questionCreatedAt`, oldest first.

**4. Verdict.** For each kept record in that order, while `{budget}` attempts remain, run `node "${CLAUDE_PLUGIN_ROOT}/bin/dispatch-resume.js" --issue {n} --queue` (`resume.md` Step 2's verdict; `--queue` accepts only the real `auto:build` label, never a typed command's stand-in). Refused (exit 3): print its `line`, or its `remedy` in its place under `resume.md` Step 2's rule; spend nothing and write nothing. The body and `needs:answer` stay as they were, so the next bare drain retries the record. Exit 2 or 4: print the stderr line; it too spends nothing and writes nothing.

**5. Ingest, then resume.** On an eligible verdict (exit 0), run `node "${CLAUDE_PLUGIN_ROOT}/bin/plan-review-answer.js" --issue {n}`, the ingest: it folds the trusted replies into the body's `## Plan-review answers` section and removes `needs:answer`. On its exit 0, run `resume.md` Steps 3-8 for the record, with step 4's verdict as Step 2's, and render the first call with `--headless` exactly when this firing is headless (`task-prompt.md`'s "Before rendering this template" decision); the second call never takes it, as for any group. This resume spends one `--budget` unit. Report it as Step 3's loop reports an iteration. An ingest exit 2 prints its stderr line, dispatches nothing and spends nothing. An ingest exit 4 prints its stderr line and runs `gh issue edit {n} --add-label needs:answer`, since the write may have landed and removed the label (a read-back failure, or an edit that timed out after GitHub applied it); with the label back, the next drain's `--check` reads the record as answered and retries it. It dispatches nothing and spends nothing.

A stop inside Steps 3-8 ends that record's resume, not the drain, and its unit stays spent. Every stop before Step 7 dispatches (Step 3's staged-index or archive stop, Step 4's mint failure, Step 5's worktree add or entry failure, Step 6's `record-worktree` failure, Step 6a's stop, Step 7's render failure) finds the record without `needs:answer` while its draft PR still holds it in the open-pr exclusion, so re-add the label with `gh issue edit {n} --add-label needs:answer` before the stop ends the resume or the firing: the answers are already in the body, so the next sweep's check reads the record as answered (exit 0) and retries the resume. A stop after Step 7 dispatched leaves the record without `needs:answer`, so this firing's report names it for a human. A Claim permission stop or Render-failure stop still ends the firing. Step 8's Step 1 close-out waits for the drain's own loop termination (Step 3). When this step dispatched anything, re-run Step 2's queue pull before Step 3 ranks, as Step 3's loop does after each dispatch. The rest of `{budget}` goes to Step 3.

**Why check, verdict, ingest — in that order.** The check writes nothing, so a record without an answer costs one read. The ingest is the write: it changes the body and removes `needs:answer`. Running it only after an eligible verdict means a refused resume leaves the record as the human left it, still labelled, so the next drain finds it again; an ingest ahead of a refused verdict would strip the label from a record nothing resumed. Why the stop keeps the draft PR: `design-notes.md`.
