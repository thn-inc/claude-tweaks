# Dispatch — Queue-Pull Notes

Loaded by `/claude-tweaks:dispatch` Step 2 on demand. Nothing here changes the queue pull `bin/queue-pull.js` runs — it explains it. Read it when this repo sets `work-links: native` (the `bin/resolve-blockers.js` branch that pull runs), when either pull returns exactly its `--limit` cap (the CLI prints a `--limit`-cap `Warning:` line), or when diagnosing a record that should have been in the queue and wasn't.

"The first pull" and "the second pull" below name the CLI's queue fetch (`--label auto:build`, `--limit 500`) and its open-issues fetch (`--limit 200`); the retained `queue-pull-script.md` mirrors both. "Above" throughout refers to that pull, not to anything in this file.

Two bulk calls plus a small, bounded fallback — the second pull is a cheap existence check for `parseDependencies`' targets (an open blocker under `work-links: body-text`; a record isn't eligible while any `Blocked by #N` line still names an open issue), but `--limit 200` can silently truncate that pull on a repo with more open issues than that. Rather than raise the cap and still have the same failure mode at a higher threshold, any referenced dependency number the capped pull didn't confirm as open gets one targeted `gh issue view --json state` check of its own — bounded by how many distinct blockers this firing's `auto:build`-eligible records actually reference (typically a handful), not by the repo's total open-issue count. Grouping still runs before claiming, unlike the pre-grants design, so the full issue body/labels/createdAt needed for eligibility, dependency-checking, and `extractKeyFiles` is already in hand from the first pull. A `Blocked by owner/name#N` line is another repository's issue: `bodyForeignBlockers` (`bin/lib/issues/cross-repo-states.js`) looks up every such ref in one batched call through `bin/resolve-foreign-blockers.js`, and `partitionByOpenBodyBlockers` drops the candidate while that blocker is open or its state is unreadable — a failed lookup reads unreadable (fail closed, one `Warning:` line) — naming it `owner/name#N` or `owner/name#N (state unreadable)`; a CLOSED one does not block (#4793). The queue-order cache (#1571) is never a hit while any `auto:build` body declares such a line (`queue-order.js`'s `cacheUsable`), because a foreign issue closing changes nothing in its freshness signal and a hit would replay the stale verdict (#4793); for the same reason a hit never replays a persisted exclusion that names a foreign blocker.

The **first** pull (`--label auto:build`, `--limit 500`) is the actual candidate pool every later step operates on — unlike the second pull's targeted per-dependency fallback above, there is no equivalent per-record recovery for a truncated queue pull, since a silently-dropped record's number was never fetched at all. `--limit 500` is a high-enough ceiling that truncation should be rare in practice, but on a repo with more than 500 open `auto:build` records the pull would still silently drop the oldest same-priority ones — exactly what `next`'s own oldest-first tie-break (Step 3) exists to surface first. The CLI's `--limit`-cap Warning catches exactly this (the retained script's `QUEUE_RAW_COUNT` check mirrors it): an exact-cap-count result logs a stderr warning for this firing rather than failing silently with no trace at all.

**`work-links: native` support.** Under `work-links: native`, one call to `bin/resolve-blockers.js` (the single-invocation CLI wrapping `bin/lib/issues/native-dependencies.js`'s `fetchNativeDependencies` — the same underlying function `flow/materialize.md` and `wrap-up/unblocked-records.md`'s equivalent native-mode check use for this mode) resolves every eligible candidate's native `blockedBy` state in one batched, aliased GraphQL request, keyed by number. The script then drops any candidate for which `record.js`'s `openBlockerRefs` is non-empty — this repository's `openBlockerIds` (the identical OPEN-state filter `partitionByOpenNativeBlockers` applies, already computed, so the script reads it instead of re-deriving it from a raw GraphQL response) less any foreign numbers, plus each foreign blocker that is not CLOSED, named `owner/name#N` (suffixed ` (state unreadable)` when its state could not be read; #4793) — naming the blocker id(s) for `SKILL.md` Step 2's Blocked-exclusion report, the same outcome `partitionByOpenBodyBlockers`/`parseDependencies` already produces for an open `Blocked by #N` body-text line under `work-links: body-text`. The two modes are mutually exclusive per record, mirroring `flow/materialize.md`'s existing `blocked-by` driver/work-links branching — a project mid-migration with stale body-text lines under `native` is out of scope. The call fails safe: on any error (network, auth, `gh` absent, or a schema mismatch — e.g. a GitHub Enterprise host exposing only `issueDependenciesSummary`, not `blockedBy`) the script logs a warning and falls back to no native filtering for that run rather than crashing Step 2's queue-build entirely — a missed native-dependency check degrades to the pre-`work-links: native` behavior, not a hard failure of headless dispatch.

The same fallback also triggers when `gh` itself is absent — there is no GraphQL passthrough on the MCP path, so a `work-links: native` project running headless without `gh` degrades to no native filtering for that run, identically to any other query failure. This is not a new code path — it's the existing on-error fallback reached via a capability check instead of a failed call.

**Re-selection guard for a `pr-opened:`-released record (#2073).** A record whose claim was
released with reason `pr-opened: spec {n}` (`_shared/issue-claims.md`'s Release triggers table)
correctly carries no claim and no `bot:in-progress` afterward — `bin/lib/release-claim/release.js`
strips that label on every release by default (#1631), including this one. What actually keeps
such a record off the queue is **not** `bot:in-progress` but the open-linked-PR exclusion
described above (`partitionByOpenLinkedPR`, `reason: 'open-pr'` in this run's session-scoped
`dispatch-exclusions.json`): the record's open PR still closes it, so the first pull's exclusion
removes it from `dispatch-groups.json` before any selection form reads the pool, the same as any
other in-flight-PR candidate. Reading the label state alone (no `bot:in-progress`,
`auto:build`/`auto:merge` still present) as "this record looks re-selectable" misses that
exclusion — check `dispatch-exclusions.json`'s `reason: 'open-pr'` entries first.

**The cross-PR overlap report's open-PR pull (#1579)** is a separate, third bulk call (`gh pr list --state open --json number,files,closingIssuesReferences --limit 100`), unrelated to the two pulls above — it feeds `SKILL.md` Step 3's Cross-PR overlap report, not eligibility. Same truncation posture as the first pull: `--limit 100` caps it to the 100 most-recently-updated open PRs, with the identical exact-cap stderr warning convention. Since this report is informational only (never a gate), a truncated pull or an outright `gh pr list` failure both degrade to a smaller (or empty) result set rather than a fallback query — there is nothing more targeted to fall back to for "which open PRs exist," unlike the per-dependency existence check above.

## Where four exclusion passes sit, and why

These paragraphs moved here from the comments heading each pass in `queue-pull-script.md` (#4792), which now keep one line apiece pointing at this section. Read them when changing a pass's position or posture; running the script needs none of them.

**Not-spec-shaped pass (#2829).** It runs unconditionally, right after grouping and bundling complete (both the cache-hit and cache-miss branches leave `$DISPATCH_GROUPS` populated by then), and before every `gh`-backed probe: a candidate whose cached body fails `/flow`'s Materialization hard gate (`shapeGate`) would otherwise be claimed and handed to `/flow`, where it fails mid-build — the failure counts against `dispatch-retry-ceiling`, and a correctness-classified failure makes Settle revoke `auto:merge` (#2786's evidence). It makes no `gh` or network call: `shapeGate` is pure, run against the body already fetched into `$DISPATCH_GROUPS`. It sits ahead of the #1224 open-PR pass and the #1984 shipped-candidate classification so an excluded candidate costs neither pass's `gh` calls (the open-PR pass's batched GraphQL call, the shipped pass's up-to-5 live `gh pr view` calls) and never gets a staged Close proposal from the shipped pass. Like the open-pr, target-missing and shipped passes (and unlike oversized), it removes the excluded candidate from `$DISPATCH_GROUPS` unconditionally, with no `#N`/`#N,#M,...` bypass — the exclusion is computed once, before any selection form reads `$DISPATCH_GROUPS`.

**Open-linked-PR pass (#1224).** It runs unconditionally (both cache branches leave `$DISPATCH_GROUPS` populated) and independent of `$WORK_LINKS`: unlike the native blocked-by check, PR linkage is not a dependency-tracking policy choice, and unlike the queue-order cache (#1571) a PR opening or closing after the cache was written is exactly the kind of transient state the freshness signal (built from `auto:build` issues' own `updatedAt`/`state`) never observes, so skipping it on a cache hit would silently reintroduce the bug #1224 fixed. It makes one batched aliased GraphQL call across every candidate still in `$DISPATCH_GROUPS` (after blocked-by, native, oversized and not-spec-shaped filtering — there is no point checking a candidate already excluded for another reason), via `bin/resolve-linked-prs.js` (`record.js`'s `buildLinkedPRQuery` + `bin/lib/issues/linked-prs.js`'s `fetchLinkedPRs`).

**Named-target existence pass (#1983).** It runs unconditionally, right after the open-linked-PR exclusion and before the read-only cross-PR overlap report: a record whose named target no longer exists at the integration tip is not merely unlikely to build, its Acceptance Criteria is unsatisfiable by construction (the observed shape: a `by:docs-health` ledger correction whose flagged doc a since-merged tidy sweep already deleted). It checks the integration tip, not the working tree (`flow/materialize.md`'s Named-location drift note): a worktree session's tree may lag, and a dirty tree must not hide a deletion.

**Unlanded-blocker pass (#4792).** It runs unconditionally, after the shipped-candidate classification and its Close-proposal staging and before the neighbour-in-flight pass, so a candidate an earlier pass removed adds nothing to its query and a removed candidate is never checked for in-flight neighbours. Landing state is transient — a blocker's closing commit can reach `origin/{integration-branch}` at any moment — so, like the open-linked-PR pass, it runs on a cache hit too. `bin/dispatch-unlanded-blockers.js` hands the remaining candidates, already fetched, to one `preflight-records.js --prefetched-json --blocker-landing --work-links "$WORK_LINKS"` call (no per-record `gh issue view`), so the verdicts are exactly the ones `/flow` Step 2.7b computes before claiming. All candidates are that call's positional numbers, so a blocker that is itself a candidate is in-run and not judged; such a blocker is open, and the `blocked` pass already removed its dependents. A blocker linked natively or declared by a `Blocked by owner/name#N` body line in another repository is never in-run, whatever its number: a CLOSED one reads `undetermined` (`via: cross-repository`) and keeps the candidate, its `AUTO` line naming it `owner/name#N`; an open or state-unreadable one is the `blocked` pass's (#4793). One record's blocker fault never turns the pass off for the pull, and that record is not dispatched (#4792's Q3 and Q4): a record whose blocker declaration cannot be checked is excluded as `malformed-blocker` instead. The CLI screens it out of the call first (`malformedRecords`: a `Blocked by` number that is no valid issue number or is above 2147483647, under every `work-links` value, a non-string body, non-array labels), and a record the call names as missing from the native dependency response is dropped with the call re-run once without it. Every other candidate is still checked, and the record is eligible again on the first pull after its blocker declaration can be checked. Otherwise the pass fails open, because Step 2.7b re-checks before any claim: an `undetermined` verdict keeps the candidate (2.7b proceeds on it too) with one `AUTO` line. Only a whole-call failure — a non-zero `preflight-records.js` exit the CLI cannot pin on a record, unparseable output, or an empty `$INTEGRATION_BRANCH` — prints one `Warning:` line and excludes no `unlanded-blocker` record (the `malformed-blocker` exclusions stand), and only a refused exclusions write (`appendExclusion` on a corrupt file) or an unreadable `$DISPATCH_GROUPS` stops the pull (#3110). An `open` verdict is not this pass's to exclude: the `blocked` pass owns open blockers.
