Flake handling — the runner-owned flaky retry, the agent's named-file / whole-suite isolation pass, and the flaky-allowlist proposal for `verification.md`'s tests check. Read when a `tests`-family check fails or the runner prints a `CAVEAT: flaky-retried:`/`CAVEAT: flaky-allowlist:` line. "Step 3" in this file means `verification.md`'s report step.

# Flake handling (tests check only)

The runner owns flake retries (#1925). Runner-owned retry applies to spec/TAP output (`node --test`'s default `spec` reporter or TAP) and to jest and vitest output whose failures fully account (#3480: jest's distinct `FAIL` test files must equal `Test Suites: N failed`, vitest's `Test Files N failed`). Any unattributed signal refuses with `unattributed-failures: {N}`. For either dialect that is a `FAIL` line naming no test file, a coverage or global setup/teardown failure line, Node's `Node.js v…` crash trailer, or more than one summary line. For jest it is also an obsolete-snapshot line, an interrupted `N of M total` run, or a log whose last non-empty line is not jest's `Ran all test suites…` trailer (a crash after or instead of the summary, #3674; counted only when no other unattributed signal already fired). A `--silent` run's `Time:` line and a yarn/pnpm failure trailer also end a run normally; other text after the trailer (jest's open-handle warning, another wrapper's lines) still refuses. For vitest it is also its `Errors` block (the larger of the `Errors` count and the `Unhandled Errors`/`Unhandled Rejection`/`Source Errors` banner, never their sum) or any skipped test file. Vitest has no such guard: its summary (stdout) and failure blocks (stderr) can each end the log. A pytest suite never retries — it refuses with `no-accounting-guard: summary` (or `no-parse` first, when no failing file can be named), since its collection `ERROR`s sit outside every `FAILED` line, so it has no failure-accounting guard (#3204). A project lists known-flaky test files — repo-relative paths or globs (the same `**`/`*` forms `rules[].match` accepts) — in `.claude-tweaks/verify-scope.json`'s `flaky.files`, with a per-suite `retry` command template (`{file}` substituted; `flaky.maxRetries` default 1, ceiling 2). `flaky.files` entries must match the failing-file paths exactly as the suite's own output prints them (relative to the runner's cwd; an absolute path under the cwd is relativized) — a suite run from a package directory prints package-relative paths, and a repo-relative entry then never matches; the run fails safe (an ordinary failure, no retry) and `retryDecision.reason` names the unmatched path — a glob is matched against the same printed path. On a `tests`-family failure under `--scope`, the runner extracts the failing test files from the log (ANSI stripped) and, only when **every** failing file is allowlisted, re-runs those files serially in log order — each up to `maxRetries` attempts, stopping at a file's first pass, failing the run on the first file that exhausts its attempts (`report.json.checks.{suite}.retryFailed`). A retried pass reads `pass (flaky-retried: {files})` in the table; `report.json` carries `checks.{suite}.flakyRetried` and `retryAttempts` (one `{suite}-retry-{file-slug}-{i}.log` per attempt), the pass stamp carries `flakyRetried`, and a `CAVEAT: flaky-retried: {files} — passed on isolated rerun; see {log}` line renders under the table — present it verbatim in Step 3, never folded into the row, and log `AUTO {time} — Flaky retry: {files} passed on isolated rerun (declared in verify-scope.json). Reversibility: high.` per `_shared/auto-decision-log.md`. The count stamp keeps a per-file `flakyHits` counter; from 5 hits the runner also prints `CAVEAT: flaky-allowlist: {file} retried {n} times — file a fix or remove it from the allowlist` and sets `report.json.flakyEscalation` — `/claude-tweaks:wrap-up`'s leftover routing (`wrap-up/leftover-routing.md`) turns that into a backlog record. A file baseline adjudication (`verification.md`) classes **flaky** counts into the same `flakyHits` map, allowlisted or not (#3062), and each `flakyEscalation` entry carries `onAllowlist`: for a file not on `flaky.files` (`onAllowlist: false`) the caveat instead reads `CAVEAT: flaky-allowlist: {file} baseline-flaky {n} times — not on flaky.files; a staged proposal to add it is pending review`, and when `--run` names an anchored run directory the runner itself stages `staged/flaky-allowlist-{slug}.md` with its own `STAGED` decision — present that caveat verbatim, and never stage a second proposal for the file or edit `flaky.files` yourself. An unlisted failing file, a log with no parseable test file, a pytest (or ambiguous summary) log — no accounting guard (#3204), a suite with no `retry` template, `maxRetries: 0`, an unreadable log, or a failing path the shell cannot be handed safely (`unsafe-path: [{file} ({why})]` — a non-plain path is quoted for the platform's shell, and a template that wraps `{file}` in quotes has that wrapper replaced; any other quote or escape character in the template, a control character, a leading `-` in the path, or on win32 a `%`/`"`/`!`/trailing `\` in it refuses) means an ordinary failure with no retry — `checks.{suite}.retryDecision.reason` says which. `types`/`lint` are deterministic and never retried; a run without `--scope` never retries.

When a `tests`-family failure is not resolved by the runner's own retry — an unlisted file, an unattributed failure, or no `flaky` declaration at all — the agent performs one isolation pass before treating it as a confirmed regression. Read `checks.{suite}.retryDecision.reason` from `report.json` to choose which of the two paths below applies: an `unlisted: […]` reason selects **named-file isolation**, and so does an `unsafe-path: […]` reason (every failing file is allowlisted and the failure list is complete, but the runner refused to hand a path to the shell — quote that path yourself when re-running it); a `no-parse` reason (`sniffFamily` classified the output as `generic`, or the family's failing-file pattern didn't match — no file could be named), an `unattributed-failures: {N}` reason (#3066 — every named file is allowlisted, but the log also carries `N` failure(s) `extractFailingFiles` could not attribute to any test file, so the named-file list is a known undercount; a jest/vitest log reaches it too, #3480), or a `no-accounting-guard: {family}` reason (#3204 — the log's output family, e.g. `summary` for pytest or an ambiguous jest/vitest log, has no failure-accounting guard, so its named-file list can never be trusted as complete) selects **whole-suite re-run** — named-file isolation would silently skip the unattributed failure(s). `bin/verify.js`'s stdout summary marks a failed `tests`-family check with the clause `(retry: no-parse — whole-suite re-run applies)` when the reason is `no-parse`, so the path is visible without opening the report.

## Named-file isolation

For a failure in an **unlisted** file, `verification.md`'s "Isolating pre-existing failures by file" still applies, agent-performed, once: re-run that one file in isolation (`node --test path/to/file.test.js`) — isolated pass → **flake** (machine load), isolated fail → **regression**.

**Bracketed path segments (#2745, Windows).** `node --test` treats its path argument as a glob — on Windows, a path containing a literal `[`/`]` segment (a Next.js dynamic-route directory, e.g. `app/users/[id]/page.test.js`) is interpreted as a character class and silently matches zero files instead of the one file named, rather than erroring. This reproduces on Windows only — macOS/Linux `node --test` have not shown the same bracket-globbing behavior in this project's testing. When the file to isolate has a bracketed path segment, skip the bare invocation above and run it through `tsx --test` with the path quoted instead: `npx tsx --test "app/users/[id]/page.test.js"` (add `tsx` as a dev dependency if the project doesn't already carry one) — `tsx`'s own test runner does not glob its path argument. Treat an isolation run against a bracketed path as inconclusive, not as a pass/fail verdict, if neither form is available (no `tsx`, and the bare form reports zero tests found rather than a real pass or fail) — report the gap rather than recording a false flake or false regression. An isolated pass is reported as a flake — the run's verdict is unchanged from the pre-existing adjudication, never reported as failed — and the allowlist proposal below is staged non-blocking alongside it: it never changes the run's verdict. When it passes, do not add the file to `flaky.files` yourself. When a pipeline run directory resolves (`_shared/pipeline-run-dir.md`), stage a proposal instead — `node "${CLAUDE_PLUGIN_ROOT}/bin/stage-item.js" --run "$PIPELINE_RUN_DIR" --id flaky-allowlist-{slug} --file {proposal}.md` (kind `flaky-allowlist`; `{slug}` is the file path with `/` → `-`; the proposal names the file for `flaky.files` and, when the failing suite has no `retry` template yet, the template to add alongside it — it is incomplete without both), logging `STAGED {time} — Flaky allowlist proposal: {file} passed one isolated rerun. Stage path: staged/flaky-allowlist-{slug}.md. Reversibility: high.` Standalone (no pipeline run directory resolves — this file is shared by `/build`, `/test`, `/deepen`, `/simplify`, and three of them commonly run standalone), report the same proposal inline in Step 3's report as a finding for the user to apply. Check the ledger first: `verification.md`'s "Pre-existing failures" covers the distinct case of a failure already tracked before this spec's own changes, and only failures it does not cover get diagnosed here.

## Whole-suite re-run

When no file can be named (`retryDecision.reason === 'no-parse'`), or the named-file list is a known undercount (`retryDecision.reason` starts with `unattributed-failures`), or the log has no accounting guard at all (`retryDecision.reason` starts with `no-accounting-guard`), `verification.md`'s "Isolating pre-existing failures by file" does not apply — there is no (complete) path to isolate. Re-run the `tests` check once through the runner instead: `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --cmd tests="{command}"` with the same scope and `--no-stamp` (a second pass must never record a pass stamp on its own — `stamp.js`'s dirty-tree rule and #1921's stamp semantics stay authoritative; the adjudication is the agent's, the stamp is the runner's). Pass the **same full `--cmd` set** the failed run passed — not the failing check alone — and use that check's own declared name: under `--scope` the runner refuses a set missing any check the selection requires (`--scope: mode {mode} requires --cmd for: {names}`, exit 2), and when the declaration maps suites, `tests` is not a valid `--cmd` name at all (`--scope: --cmd "tests" is not types, lint, or a declared suite`, exit 2) — substitute `--cmd {suite}="{command}"` for the failing suite exactly as the scoped invocation in `verification.md`'s "Re-verify scoping" does. Then adjudicate: the second run passes → **flake**, reported exactly as the named-file flake is (the run's verdict is unchanged from the pre-existing adjudication); the second run fails again → **regression**. One re-run, never more — the whole-suite cost is exactly why this path is the fallback, not the default.
