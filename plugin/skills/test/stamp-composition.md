Pass-stamp composition — the generated-path exemption, `--cmd` wrappers, and chunked verification for `verification.md` Step 2.5. Read when a declared check regenerates a tracked file, a `--cmd` needs a wrapper, or the declared checks exceed the foreground command cap.

# Pass-stamp composition

**Generated-path exemption (#2987).** A dirty tree normally disqualifies the stamp outright (`stamp.dirty` mirrors `report.dirty`) — but when one of the declared checks itself regenerates a tracked file in place (a production build rewriting `next-env.d.ts`, say), that rule forces a redundant second run on every pass. `.claude-tweaks/verify-scope.json`'s `generated` key names the path globs those checks regenerate — the same repo-relative-path-or-glob form `preExisting`/`flaky.files` use. When every path dirty at the run's start or end (the two reads the stamp's own `dirty` combines, #3757) matches one of those globs, the stamp still records `dirty: false` and carries the exempted paths verbatim as `generatedExempt: [path, …]` for audit; any other dirty path still disqualifies the stamp exactly as before `generated` existed — a rename counts both its new path and its deleted source, so a non-generated file renamed into a generated path still disqualifies. Name only files the checks actually regenerate; a glob that would also cover the declaration itself (`**`, `.claude-tweaks/**` — checked against both `.claude-tweaks/verify-scope.json` and whatever path `--scope` named) is a declaration error — this exemption is scoped to the pass **stamp** alone; `report.json`'s own `dirty` field is never touched, since other readers rely on it meaning "the tree has any uncommitted change at all". A scope file with no `generated` key behaves exactly as today. `--stamp-status --scope <declaration>` re-derives the same exemption against the live tree (`liveGeneratedExempt`), so a stamp stays verifying while the only dirty paths are declared-generated ones; a bare `--stamp-status` never does. A `--scope` that cannot be read (missing or invalid), or that is ignored because `--git-dir` names another checkout, is reported as `scopeError` rather than read as "no `--scope` given"; status still exits 0.

**`--cmd` wrapper note.** When a `--cmd` needs environment variables `--cmd-env` can't express cleanly, or an interpreter whose default import/module path differs from this process's cwd (a script-driven test runner resolves packages from the script's own directory first, not the working directory), commit a small wrapper script in the project rather than hand-building a `cd`/env-prefixed `--cmd` string, and put the working directory first on the wrapper's own import/module path. A wrapper that gets this backwards resolves packages against its own directory instead of the project's, which can silently pick up the wrong package version or fail to find one that is actually installed.

**Chunked verification (#3002).** A project whose declared checks (`.claude-tweaks/verify-scope.json`'s `types`/`lint`/suites) take longer end to end than the harness's foreground command cap must split them into several `verify.js` invocations — each one, by definition, a partial `--cmd` set, so each must pass `--no-stamp` (`verification.md` Step 2) and none alone ever earns the single full-set pass stamp. `--stamp-suite` (requires `--scope`) is the way a chunked run still earns a trustworthy verified-HEAD stamp: pass it alongside `--no-stamp` on every chunk, naming that chunk's checks with explicit `--cmd` flags (a map-form declaration's own commands are not auto-selected under `--stamp-suite`, so a chunk with no `--cmd` is a usage error), and the runner records, per check that actually passed in that chunk, a per-suite pass record keyed by sha and tree state (never on a tree dirty outside the declared `generated` paths, nor when HEAD moved mid-run) — a check that failed has any existing record cleared rather than left stale. A chunk that records nothing says why in a `CAVEAT: --stamp-suite recorded no per-suite pass this run — …` line; `--stamp-suite` with `--git-dir` is a usage error. Use it only when genuinely chunking a long suite under the foreground cap, never as a substitute for `--no-stamp` on an ordinary ad hoc partial run (a plain `--no-stamp` run with no `--stamp-suite` writes nothing extra, exactly as before).

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --run "$PIPELINE_RUN_DIR" --scope .claude-tweaks/verify-scope.json --no-stamp --stamp-suite --cmd types="tsc --noEmit" --cmd lint="eslint ."
node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --run "$PIPELINE_RUN_DIR" --scope .claude-tweaks/verify-scope.json --no-stamp --stamp-suite --cmd tests="npm test -w packages/api"
```

Once every check declared in the scope file has its own passing per-suite record at the current clean HEAD (across however many chunks it took, run sequentially — never in parallel against the same checkout), `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --stamp-status --scope .claude-tweaks/verify-scope.json` reports `verifiedHead: true` and a `suiteComposed: {declared, covered, missing, complete: true}` object — composed independently of (and in addition to) the single full-set stamp's own `match`/`verifiedHead` fields, which stay exactly as they were for a project that never chunks. A `--stamp-status` call with no `--scope` never looks at per-suite records at all (`suiteComposed: null`), same as today.
