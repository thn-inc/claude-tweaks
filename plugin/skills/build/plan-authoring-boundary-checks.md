# Plan-Authoring Checks — Cross-Boundary Premises

Read from `plan-authoring-checks.md`'s **Cross-boundary checks:** pointer, only when a plan depends on something outside this change's own code: a producer deployed separately from its consumer, or a schema this project does not own. Same purpose as that file: each check targets a failure that reads as correct to a task-level review comparing plan text against implemented code.

**Producer-freshness check:** when a plan task adds a consumer — a CI gate, a parser, a probe reader — of an artifact (a stdout marker line, a manifest field, a JSON key) that only code from this same change produces, and the two ship through different deployment paths (the consumer in a workflow that runs on merge, the producer in a wheel/bundle/image deployed separately), the plan must name (a) what the consumer sees on its first post-merge run before the producer is deployed, (b) whether that outcome is a refusal, a silent pass, or a crash, and (c) the ordering an operator must follow — and the consumer's own error message must name the precondition. A plan that reads complete to every task review can still ship an unnamed rollout-ordering precondition: the consumer and producer each look correct against their own task, and only a live deploy sequence exposes the gap. A deploy-workflow gate that read a marker line only a same-branch build artifact emits surfaced this exact shape at whole-branch review — an Important finding, a fix wave, and documentation updates in four places, none of which the plan itself had flagged.

**Upstream-schema premise check:** when a spec or plan asserts a semantic about a schema this project does not own (a flag's meaning, a column's role, what a seed/backfill writes, which index enforces uniqueness), the plan must cite the DDL, migration, or model definition that proves it — read at authoring time, with the relevant line quoted — or mark the sentence `unverified`. A premise that names a migration file by path is trivially checkable and must be checked: a task-level review comparing plan text against implemented code agrees with a restated premise exactly as readily as a proven one, because both sides restate the same claim rather than checking it against the schema's own definition. A per-item vs. per-resource flag mix-up is the archetype — a plan asserted that a per-item flag in an upstream migration's link table reproduced old single-owner semantics and cited the migration by path, but only restated the claim as a Global Constraint rather than proving it; `plan-audit.js` passed, two implementers and two task reviews executed it faithfully, and only the whole-branch review, which opened the migration's actual seed and index definitions, found the filter dropped every attached-but-not-current row. A plan may declare `Premise-refs: {path or URL}` lines naming what it claims to have read; `plan-audit.js` reports any local path that does not resolve to an existing file as a distinct finding from Check B's unplanned-file list — a scope mismatch and an unverifiable citation are different findings — while a URL is recorded but never fetch-verified (Check B has no network access).
