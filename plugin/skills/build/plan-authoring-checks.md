# Plan-Authoring Checks

Run these checks while finalizing a plan in Spec Step 3 or Design Step 3, before handing it off for execution. Each exists because the failure mode it targets reads as correct to a task-level review that only compares plan text against implemented code — both sides agree with the plan, so nothing downstream catches the gap unless it is checked here, at authoring time.

**Plan-authoring check (return-shape widening):** when the plan's tasks grow an existing function's return shape — or widen a shared data structure's row/entry shape — grep the repo for tests asserting against that return value — `notDeepEqual`-style discrimination checks, hard-coded object-literal comparisons — and for prose citing a literal count derived from it. A widened return shape can silently defang the assertion and leave the count stale. Flag any hits before finalizing the plan.

**Blocking-verification-downgrade check:** when a plan task exists specifically to verify a live/external contract (a real API response, a real hook payload, a real third-party behavior) before implementing against it, and that task gets scoped down during authoring to something that doesn't touch live data (a re-read of documentation, a type declaration, a spec citation) — flag it explicitly rather than letting the downgrade pass silently. Name the downgrade in the plan or the ledger so it reads as a stated risk, not an invisible one.

**Deictic-reference re-resolution check:** when a plan task instructs a text reorder — moving a paragraph relative to other text that cross-references it — re-resolve every deictic reference ("above", "below", "the following", "the preceding") in both the moved text and the text it moves past, and write the task's `replacing:`/`with:` blocks with the post-move direction already applied. A self-contradictory pair (one clause saying "above" and another "below" about the same paragraph) reads as correct inside each task's own diff, so a task-level review comparing plan text against implemented code has nothing to catch — only a whole-file read resolves the direction. Re-check the deictics as part of the reorder edit itself; a later fix round that corrects the ordering will not correct them, because the reorder is right in isolation.

**Ordering-fix location check:** when a plan fixes a bug by placing an action in skill prose "before Y" or "after Z", locate where Y actually executes — grep the skill's files for Y's procedure or command (`pr-first-merge.md`, `gh pr merge`) rather than trusting the order of a canonical list that names it — and list in the plan every reader and writer of the action's target between its new position and Y. Then look for a sibling site that already states the same ordering rule and match both of its halves. #3595's plan put the ledger delete "before item 4's merge", following `cleanup-procedures.md`'s list, but under `pr-first` that merge runs at `review-console.md`'s On approval step 6, so the delete landed ahead of the ledger's last two writers (step 7's reopen and step 11's `finish-console`, which exits 1 once the file is gone). Three task reviews passed it and only the whole-branch review caught it, while `flow/multispec-review-console.md`'s Shared teardown step 0 already ordered the same delete after the ledger's last reader and writer and before the merge.

**Verbatim-command run-once check:** when a plan task's replacement text dictates a runnable command verbatim (`gh api`, a GraphQL query, `jq`, `curl`), run that command once against the live target in a read-only form before dispatching, and record the output in the plan; a command with no safe read-only form is flagged in the plan as unverified. Transcription plus a task review cannot catch a command that cannot execute — both sides agree with the (possibly wrong) authored text — and when the same plan also dictates the test, TDD is circular: red→green proves agreement with the plan, not with reality. Two shipped `gh api` flag defects in one session (#608's `-f` placeholder fix inverted into #610's `-F` coercion bug, pinned by its own plan-authored test) are the incident behind this check.

**Degrade-clause convention check:** before a plan task writes a new "when X is unavailable, do Y" clause into a skill or `_shared/` contract, grep `plugin/skills/_shared/` for the same unavailability condition (`gh absent`, `no MCP fallback`, `MCP transport`, and the like) and cite whatever established convention already covers it, inline, rather than restating the behaviour uncited. An uncited degrade clause reads to a reviewer as a fresh, unsupported exception to the file's general transport policy, and the review cycle spent adjudicating that is pure waste — the convention already existed.

**Copied-config re-derivation check:** when a plan's Technical Approach instructs copying an existing file "as a starting point," flag every field in the copied file that encodes a security- or capability-relevant grant — tool allowlists, permission scopes, resource limits, transport credentials — for explicit re-derivation against the new context's actual reachable code path. "Copy X" must never implicitly mean "copy X's grants too": a copied grant is over-broad by default, and it reads as correct to every reviewer comparing plan text against implemented code, because both sides agree. #970's own build copied `allowed_tools: [Bash, Read, Edit, Write, Grep, Glob, Task]` verbatim into a new routine template whose reachable path needs a fraction of it — it survived the task review and the whole-branch review, and was caught only by an independent security lens.

**Renumbering-completeness check:** when a plan task inserts or removes a row in an enumerated, numbered structure — a composition table, an ordered list cited elsewhere — require the task's own verification step to search for the affected fact in at least three independent forms: the number itself ("row N"), any prose bucket/category list restating membership, and any cardinal-word count ("six buckets", "eleven walkthroughs"). One grep pattern, however carefully refined, can only see the representation it was tuned for; three rounds of the same build each caught one form and were structurally blind to the next. Write all three greps into the plan, not a single pattern to be narrowed later.

**Batched-plan marker.** When a plan bundles several same-shape edits into one dispatch (SDD's "Batch small same-shape work"), the author writes `**Execution:** batched` in the plan header (before the first `### Task` heading) or `[batch]` in that task's title. `plan-audit.js --count-tasks` reads exactly those two markers, and a fast-lane single-task plan without one qualifies for the whole-branch review skip (roster tag `sdd-whole-branch-review`, `_shared/ceremony-profile.md`) — so the marker is what keeps a bundled plan reviewed. A `ceremony: fast-lane` + `size: low` plan in which every task inlines its complete code — pure transcription, no judgment left to the implementer — is written as one batch even when its tasks differ in shape (#3123): put `**Execution:** batched` on its own header line, and add a separate plain header line telling the executor to send every task to one implementer as a single brief and review the combined diff once, extending SDD's batch rule to transcription-only plans — `**Batch:** send every task to one implementer as a single brief; review the combined diff once.` Never append that instruction to the marker line: the marker match is anchored at end of line, so any trailing text silently reads as `batched: false`. The marker alone does not make SDD batch — it only keeps the whole-branch review — so the instruction line is what saves the per-task dispatches; the result is one implementer, one batch review, and the whole-branch review kept as the gate. A plan where any task leaves code for the implementer to write, or where a task needs its own tests or review surface, stays per-task (SDD's "Reserve one-dispatch-per-task").

**Adjacent-task merge.** When two adjacent tasks touch the same files, the second only builds on the first's output (consumes it, or is made safe by it), and the second adds no separately reviewable surface (no behavior or test a reviewer would judge on its own), write them as one task — e.g. "add a column" plus the one-line type or constant that exposes it; "add a job" plus "remove the code it replaces"; "add a column" plus "a pure function over it" only when both tasks' tests sit in the same test file the first task already edits. Each separate task costs an implementer dispatch and a task review even when the second only consumes the first's output (#3379). This is plan granularity, not SDD's batch rule — the **Batched-plan marker.** paragraph covers same-shape edits across files and fast-lane transcription plans (#3123); this one covers sequential same-file tasks: it takes no marker and leaves `plan-audit.js --count-tasks`' `batched` value unchanged, and only the `tasks` count drops. Keep the tasks separate when the second has tests or behavior of its own that a reviewer would judge separately, touches different files, or is independently risky; a merged task still gets its one task review. Under `ceremony-profile: fast-lane` a plan that reaches `tasks: 1` with `batched: false` skips the whole-branch review (roster tag `sdd-whole-branch-review`), so never merge a multi-task plan down to a single task to reach that skip — merge only while at least two tasks remain.

**Behavioral-claim check:** when a plan task writes prose asserting a runtime effect — "X makes the next run do Y", "the hatch downgrades the record", "after this the stamp is written" — name, in the plan, the code path or config write that produces that effect, or mark the sentence unverified. A claim carried verbatim from a spec bullet reads as correct to every reviewer comparing plan text against implemented prose, because both sides agree; only a probe against the mechanism catches it. #1926's Deliverable 4 asserted that the ceremony escape hatch makes "the record's next run run `standard`" — nothing re-stamps the `ceremony:*` label, so the claim was false in three files until the whole-branch review grepped for the writer (`specify/shaping-mode-stamping.md` is the only one); #1923's Gotchas encoded two false premises the same way.

**Already-satisfied ruling check:** when a plan rules a Deliverable or Acceptance Criterion already satisfied because some producer emits the required artifact, cite a count over real archived run artifacts (live `.claude-tweaks/pipelines/*/decisions.md`, archived `.claude-tweaks/pipelines/archive/*/decisions.md`, multi-spec runs under `spec-{N}/`, or the equivalent store) showing the artifact present where the consumer reads it; the producer's own doc text is not evidence. A documented-but-never-executed producer reads as satisfied to every reviewer comparing doc to doc, which is the gap the consumer's gate exists to catch. #2775's plan ruled the per-target claim-log line already satisfied from `flow/claim-targets.md`'s hand `log-decision.js` call; 33 of 48 dispatch runs since #2861 hit the claim-log deny, and the whole-branch review's correction cost a write-side redesign, a fix wave and a scoped re-review.

**Byte-pin check:** when a plan task grows a `plugin/skills/**/*.md` file, measure it against `RAIL_BYTES` (52,500 B, the Read-limit rail, `wc -c` against `plugin/bin/lib/skill-audit/budgets.js`'s constant) and record the headroom it leaves in the plan — this is the only size limit that blocks: no per-file byte pin exists any more (decision 0024), and `tests/skill-size-single-source.test.js` fails the suite if a plan or a later edit adds one outside `budgets.js`. A file near the rail is cut, or has a genuinely lazy section moved out; a plan that budgets against a tighter number than the rail actually in force hands the implementer an impossible paragraph, and the implementer's way out is to cut the content the task exists to add. #1931's Task 3 did exactly that — the pack-adoption paragraph was trimmed to the two regexes the (since-deleted) conformance pin enforced, losing the source-vocabulary and error-handling rules, and it took a review round, seventeen wording trims, and a second round restoring two of them to land the paragraph the plan had written.

**Consumer-timing check:** when a plan task pre-gathers a value for a named consumer — a fact pack, a cache, a snapshot handed to a later step — trace, in the plan, three things per field: where the data actually lives at gather time (not where the spec says it lives), whether the consumer's own procedure mandates a freshness step (a `git fetch`, a live re-read) immediately before its read, and whether the consumer runs before or after the gather. A field that fails any of the three is not a pre-gatherable fact and belongs out of the plan, not in it. #1930's plan carried ten probes straight from the record's deliverable list: the record numbers were read from a `work/` directory the main-checkout run dir never holds (the headers are committed on the branch, in the worktree's mirror), `mergeSize` fed a step whose text mandates a fetch after the pack is gathered, and `release` fed a step that runs only after the merge — all three passed every task review, because the plan text and the implementation agreed, and surfaced only when the whole-branch review ran the pack against the build's own run directory.

**Step-position check (extends the Consumer-timing check):** when a plan task writes prose for a step that runs late in its skill's lifecycle — a wrap-up Phase 4 item, a post-merge step, a re-run after a `BLOCKED` verify verdict — trace, in the plan, where the session stands when that step runs: its cwd, its checked-out branch, and whether the run's worktree, branch, and live run directory still exist. Take the answer from the merge and cleanup steps ordered before it, never from the cwd and branch the plan is authored in. #4039's plan keyed the demo-screenshot commit on "this run's current branch" and logged to a bare `$PIPELINE_RUN_DIR`; under `pr-first` the console's merge path has already removed the worktree and branch (cleanup item 4) and archived the run directory (item 8) by then, so the step runs from the main checkout on the integration branch. Only the whole-branch review caught it, as a Critical: the plan's read would have pushed evidence to the integration branch.

**Gate-over-producers check:** when a plan task adds a validation gate (a conformance scan, a lint rule, a check step) over an existing output, enumerate that output's producers — grep the routing/collection tables that feed it — and every alternate shape the output can take, then trace each gate row against both before finalizing the plan. A gate traced only against its own template reads as complete to a task-level review that compares the gate's rows to the template's fields, but misses producers the template never enumerated and alternate output shapes the gate doesn't cover. #685's tidy-report conformance scan is the worked example: two Important final-review findings and one review-lens finding all landed in this same blind spot — the gate was traced against the report template but not against the report's own producers (`scan-procedures.md`'s Yours routing — record-less `[doctor]`/`[health]` rows) or the report's alternate output shape (the digest). The same tracing applies when a plan mechanizes a judgment the model used to make from context — a verdict it held in its head, a lever it read from policy: list every producer of the evidence the new reader consumes and every policy lever the manual path resolved, because the mechanized reader sees only what is written. #1932's console resolver read a `needs-human` verdict from `decisions.md` that only one of the two auto-merge paths logged, and computed grant maturity against a hardcoded veto window the manual path had always resolved from `grant-veto-window-hours` — both survived six task reviews and were caught only by the whole-branch review.

**Sole-site and producer-side check:** when a plan states that one site is the only caller, composer, or writer of something ("`registry.js:130` is the single composition site"), write the grep that proves it and its output into the plan, not the conclusion alone — and when a plan adds a row, bullet, or case to a step that only *reports* or *consumes* (a report-only hard case, a rewrite-table row, a console section), name the upstream step that produces the input it reads and extend that step in the same task. Anchor the proving grep on the stable side of the construct — the field or call being compared (`\.path\s*[!=]==?`, plus the reversed form `[!=]==\s*[\w.]+\.path\b`) — and leave the other operand unconstrained: a pattern that guesses the other side's name (`\.path === [a-zA-Z]+(Path|Dir|wt)\b`) proves only that no site uses a name it did not guess. #3695's plan grepped that guess and called two strict compares the only ones, missing `e.path === cwd` in `post-tool-use.js` and `context.js`; SDD's task and whole-branch reviews passed the claim, and only review lens 3a's stable-side grep found the other two. A sole-site claim without its grep is a fact the controller remembers rather than one the plan carries, and every reviewer downstream inherits it; a consumer row without its producer reads as complete against the spec's deliverable list while never firing. #1927's dispatch carried "the only `serviceVars(` call" as a fact — `cli.js`'s `env` subcommand was the second, caught by the implementer, not by review — and its plan landed the report-only test-database bullet in `step-06-5-port-isolation.md` §3 while §1's detection inputs never scanned `vitest.config.*` or a database-name literal; the bullet was inert until the whole-branch review traced §3 back to §1.

**Real-input probe check:** when a plan creates a reader or derivation over recorded data — an events log, an archive, a manifest, a transcript — name in the plan at least one *real* recorded input (an archived run dir, a captured log) the finished reader is run against before the whole-branch review, and record what it printed. A hand-built fixture proves only the author's own model of the data: every timestamp in it was chosen to make the boundaries come out, so it cannot contain the shapes the author did not think of. #1928's `derive.js` passed its synthesized-fixture tests and six task reviews with `totals` that exceeded the run's wall clock on every real archived run (a `merge` span overlapping a still-open `build`, and a `worktree-reaped` terminal event seventeen hours after the session ended) — both found only when the whole-branch review ran the CLI on three archived runs, and the first fix over-corrected in the other direction because its test asserted a bound (`<= 40`) instead of the exact value the real input demanded. Name the input, run it, pin the exact numbers.

**Independent-count check (extends the Real-input probe):** a real-input probe that merely prints a plausible-looking number has not verified anything — pair it with an independent count over the same input that the reader did not compute (a `jq` over the raw file, a `wc -l`, a `sort -u | wc -l` on the ids the reader keys on) and reconcile the two before the plan is final. #1929's Task 3 ran the probe the plan demanded, on the real transcript, and its total looked right; the whole-branch review's `jq` over the same file found 3,770 assistant lines carrying 1,427 unique `message.id`s — Claude Code writes one line per content block, each repeating the turn's cumulative `usage` — so the printed tokens were ~3× the truth and every review before the last one accepted them. The third-party format's structural invariant (one usage per turn, not per line) was never stated as a premise, so nothing tested it; name the invariant the reader relies on and count it directly.

**Consumer-portability check:** when a plan task writes shipped code under `plugin/**` containing a literal that encodes this repository's own configuration — a branch name (`main`), a remote (`origin`), an owner/repo slug, a label set — name the existing resolver or policy key that supplies that value in a consumer project, and add a test with a non-default value. A corpus or real-input probe run against this repo alone cannot catch the gap, because every record it reads shares the literal, and a conformance test guarding prose and command sites does not read library code. #2733's `merge-gate.js` baked `main` into `MERGE_STATE_RE`; three task reviews passed it and only the whole-branch review caught it, at the cost of a fix wave and a scoped re-review (`2e10d142f`, #2677's squash carrying #2733's branch-parameterized `buildMergeStateRe`).

**Source-scan lint check:** when a plan task writes code under `plugin/bin/`, check each API its steps name against the source-scan suites that walk that tree (`tests/path-guard-conformance.test.js`, `tests/windows-hide-spawn-conformance.test.js`, …) and write the sanctioned form into the step — a bare `fs.existsSync`/`fs.realpathSync` fails the path-guard scan unless it routes through `plugin/bin/lib/path-guard` (`lstatType`, `resolveWithin`, …). Plan audit and task review run no such scan, so a miss surfaces at the full-suite gate: #4006's planned `fs.existsSync` cost a second full run.

**Real-writer fixture check (extends the Real-input probe check):** when a plan task adds a check that reads state another module writes — run-state, a manifest, a ledger — at least one of its tests must produce that state by calling the real writer, never by hand-written JSON. The probe check above is phrased for readers over recorded data, so a verifier reading a sibling module's state does not visibly fall under it, and a fixture is only the author's model of what the writer emits. #3023's `engine-verify.test.js` fixtures hand-wrote `status:'closed'`, but `closeRunState` writes `status:'clean', worktree:null`; the check never fired in the real flow through three task reviews, and the whole-branch review's Critical cost an opus fix wave and a scoped re-review (`5c8e2a2e0`, #3023, added the `closeRunState` to `runVerify` test).

**Moved-prose pin check:** when a plan task moves, renames, or re-wraps prose inside `plugin/skills/**/*.md`, discover the task's test dependencies by grepping `tests/` for two or three distinctive phrases from *each moved block* — not for the file's path — and list every hit in the task as a file it must re-point, leaving the go-red probe on the path the literal was absent from before the change. A conformance test that asserts a moved sentence by its content never mentions the file the sentence lives in, so a path grep reads as complete while missing it entirely. #2697's plan grepped for `demo/SKILL.md` and `feedback/SKILL.md` and missed two content pins (`tests/feedback-dedup-search-scrub-conformance.test.js`'s "dedup fingerprint basis" and `tests/feedback-watermark-prose.test.js`'s "Skip check runs first"); both went red mid-execution, cost two fix commits and a scoped re-review, and left the plan's Files list wrong for two tasks.

**Prose-held pin check (extends the Moved-prose pin check):** run that check's phrase grep over `plugin/` as well as `tests/` (`git grep -n -F '{phrase}' -- tests plugin`), and for every hit outside the moved file, grep `tests/` for that file's basename; a test that reads it makes the hit a pin, listed in the task as a file it must re-point. Some suites keep their anchors in skill prose rather than in the test: `tests/ceremony-profile-roster.test.js` reads its exemption literals from `_shared/ceremony-profile.md`'s "Mentions that are not skips" table and matches them against other skill files, so a `tests/`-only grep reads as complete while missing them. #3319's plan grepped only `tests/` before rewording `flow/steps-and-gates.md`'s phase-exit paragraph; the table's `removes it at polish's would-be exit` anchor stopped matching, the roster test went red, and only the whole-branch review caught it, at the cost of one fix wave and a scoped re-review.

**Derived-value probe check (extends the Verbatim-command run-once check):** when the command a plan pins runs against a value the code *resolves at runtime* — a remote URL, a login, a repo slug, a config value — run the probe with the value that resolver actually returns on this machine, printed by the same resolver the code uses, never with a value the author already knows to be correct. A probe against a hand-picked correct input proves the argv shape and nothing at all about resolution; when the derived value cannot be obtained, record the probe in the plan as shape-only rather than as coverage. #2757's Task 0 ran every `gh` query against the hand-picked canonical slug while the CLI derives its slug from `origin`, which still carried the pre-transfer name — four of six queries silently returned zero rows on the first live run, after surviving every task review and the whole-branch review, and cost an extra fix dispatch, a review of it, and a full re-run of the task.

**Empty-value probe check (extends the Derived-value probe check):** when a plan has an agent substitute a runtime-resolved value into a command — a branch name, a ref, a path, an id — run that command once with the value the resolver returns in its degenerate case, empty or unset, and record in the plan what it does; a filter that silently drops on an empty value widens the query instead of failing, and every probe with a real value still passes. #3572's plan probed `gh pr list --head {current-branch} --state merged` on three real branches and its git check on five refs, none of them empty. On a detached HEAD `{current-branch}` is empty, and `gh pr list --head "" --state merged --json number --jq length` prints `30` with exit 0, so a clean detached worktree read as merged; the SDD task review missed it too, and only review lens 3c caught it, fixed in a review round (373ae7a00).

**New-skill suite-set check:** when a plan adds a `plugin/skills/{name}/SKILL.md`, name in that task the fixed set of suites every new skill trips — `skill-catalog-completeness`, `argument-hint-mirrors`, `skill-conventions`, and `tests/bin-lib/skill-audit/{house-structure,anti-patterns,context-cost,csc-registry}` — and budget explicitly for the mechanical pins inside them: `context-cost`'s per-skill `description` character ceiling *and* its corpus-wide description budget (a new skill consumes both, and the corpus one is invisible from the new file alone), plus the standalone-skill `PIPELINE_RUN_DIR_EXEMPT` entry `csc-registry` requires. #2757's plan named four suites and neither skill-audit one: the description shipped over its ceiling with the corpus over budget (one fix round at the task review), and the missing Component-Skill-Contract exemption surfaced only as a new failing file at Common Step 5 (a second fix commit, after verification).

**Reachability check:** when a task adds or changes a branch that executes only past a gate — a numeric threshold, a table or buffer reset, a retry count, or a position in a linear prose procedure — the task's test must *reach the gate*, not merely name it. State in the task brief the concrete input that crosses the threshold (the table index, the byte count, the frame count) or the clause ordering that must hold, and require the test to assert on **post-gate output** — a decode, a round-trip, a reachability probe — never on the presence of the gate's own code or prose. A test whose maximum observed value sits below its own stated threshold has not covered the branch. Two instances in one run: #2758's LZW mid-stream table reset emitted its clear code at the post-reset width instead of the pre-reset one, permanently desyncing the bitstream of every real 1280x720 GIF, while the test nominally covering that path peaked at table index 491 of the 4096 threshold and never triggered a reset; #2759's new `--upstream` routing paragraph landed *after* `feedback/SKILL.md` Step 2's unconditional stop clause, making the whole new dispatch path unreachable by the skill's own linear prose, while every conformance assertion pinned the presence of literals and none their order. Both suites were green; both were caught only by an independent decode and a live probe agent. This generalizes the existing discrimination rule from "the literal was absent before" to "the gated behavior fires now".

**Guard-branch discrimination check (extends the Reachability check):** when a task adds a guard — a null check on a parent object, a depth counter, an exact-path match — the task's test list names, for each guard, an input on which only that guard decides the outcome, and the plan states that deleting the guard turns that test red. A fixture that also trips a neighbouring condition pins the outcome, not the guard, so the guard can be deleted with the suite still green. Two of three specs in one run shipped such a guard. #3543's null-`data.repository` check was never isolated, because its fixture's `path: ["repository"]` already failed the exact-path match. #3585's `${}` brace-depth counter had a mutant that survived every unit test and the 1,275-file corpus. Both surfaced only when the whole-branch review mutated the code, at the cost of a fix-wave item each.

**Inserted-guard re-proof check (extends the Guard-branch discrimination check):** when a fix inserts a precondition guard ahead of an existing check, the plan names each check downstream of the new guard and re-proves each one's test by mutating that check, not only the new guard. A fixture the new guard now rejects first never reaches the checks after it, so their tests stay green with those checks deleted. #3945's F2 fix wave put the ±5-line evidence guard ahead of `plugin/bin/lib/tiebreak.js`'s past-EOF guard and window check; their tests stopped catching a regression there, and the scoped re-review still marked F2 ADDRESSED (squash `f007f1c32`, PR #3954).

**Mirror-surface enumeration check:** when a task adds or changes a flag on a skill, take the flag's syntactic mirrors from the Argument-hint mirror surfaces table in `docs/skill-authoring.md` — the one enumeration, walked for every skill by `tests/argument-hint-mirrors.test.js` — never from a remembered count (a flag whose `## Input` entry is marked `(producer-only)` or `(deprecated alias)` stays out of the hint and so out of its mirrors — `docs/skill-authoring.md`'s `argument-hint` bullet), and then grep the repo for one of that skill's *existing* flags to find what no table lists: prose that describes what a flag does (`help/context-flow.md`'s row for the skill, a `description` naming a mode). In a project with no such table the grep is the whole derivation. A count carried in a plan author's head was short twice — #679, then #2759, whose missing surface was caught only because a byte-pinning suite happened to exist and the full-suite gate compared failing *files* rather than totals (346 failures against a 395 baseline reads as an improvement). Write the table citation and the grep into the plan, not a number.

**Inline self-consistency check:** when a plan task's Step 1 and Step 3 both inline complete code — the full test and the full implementation, not left for the implementer to derive — run the inlined test against the inlined implementation in a scratch directory before finalizing the plan; a red result is a plan defect to fix at authoring time, not a dispatch-time surprise. `plan-audit.js`'s Check C only pre-runs a task's Step 2 `Run:`/`Expected: FAIL` command against the *current* repo — it never exercises the plan's own inlined Step 3 code, so a plan can ship a test asserting a substring's absence beside an implementation that always emits that same substring, and nothing before dispatch catches the contradiction. A pipeline run observed 2026-09-17 hit exactly this: the contradiction survived plan authoring, Check C, and dispatch, and was caught only when the implementer's GREEN run failed — costing one implementer detour and one controller ruling (a `Ruling:` entry in the SDD ledger) to determine which side of the plan was authoritative.

**Go-red control check (extends the Inline self-consistency check):** a negative control is a test that mutates the text or input a positive test pins (removing a clause, deleting an item) to show the pin can fail. When a plan task specifies one, the control must run the same assertion code the positive test runs, against the mutated input, and expect it to throw. Factor the positive assertions into one function that both tests call. A control that only re-asserts its own mutation, such as `doesNotMatch` on the regex it just deleted, cannot fail. The inline self-consistency run above will still report it red, so that run is no evidence for it. #3386's plan shipped exactly that control. It cleared plan audit and the inline run, failed the spec's go-red criterion, and cost one fix round after the per-task review caught it (685179a81).

**Absence-grep control check (extends the Go-red control check):** when a plan step or a pinned acceptance criterion asserts that a grep, or any search, returns nothing, run that exact command once against a file or commit that still contains the target and confirm it matches (for a commit, pipe `git show {base}:{path}` into the same search, or run `git grep -F {pattern} {base} -- {path}`), then record that match in the plan. Prefer `grep -F` (or `git grep -F`) for literal code text: in a basic regex the brackets, backslashes and `*` of a code fragment turn into operators. A search that cannot match its own target exits 1 on the broken tree and the fixed tree alike, so the criterion can never fail and every review that reads it agrees with it. #3536's AC1.1 asserted that a grep for the old block-comment regex returns nothing; #3464's reflect composed it as an escaped JS string and nobody ran it. Under grep's BRE its `\[\s\S\]` is a literal `[`, a whitespace class, a non-whitespace class and a literal `]`, so it exited 1 on the pre-change `tests/bin-lib/exit-code-conformance.test.js` too. The plan copied it into its Global Constraints and Task 2 and plan audit passed it; only the Task 2 implementer caught it at dispatch, where `grep -rnF` matched line 56 of the old file and nothing at HEAD.

**Cross-boundary checks:** when a plan task adds a consumer of an artifact that only this change produces and the two ship through different deployment paths, or a spec or plan asserts a semantic about a schema this project does not own, read `plan-authoring-boundary-checks.md` in this directory and run the matching check (Producer-freshness, Upstream-schema premise). They live there because most plans cross neither boundary.

**Consumer-enumeration check:** when a plan task changes which rows of a shared table or frame a reader returns (a dedup rule, an ordering a caller relies on, an "effective row" rule), enumerate every consumer of that reader — grep for the reader's name and for direct reads of the underlying table — and classify each consumer as *pick-one* (an ordering fix suffices) or *list-all* (needs an explicit collapse/dedup, not just an ordering); record the classification in the task's Files/Interfaces block. An unclassified list-all consumer is a plan defect this check exists to catch: an ordering-only fix reads as complete to a task-level review that compares the reader's own diff against its own task, while a caller elsewhere in the codebase that lists and resolves every returned row keeps failing on exactly the rows the ordering fix left unresolved. An append-only table that held each key twice after a migration appended a migrated twin beside the original row is the archetype: the plan ordered the twins newest-first and stopped, but an admin API endpoint that lists and resolves every returned row kept raising on the un-migrated twin — caught only by the whole-branch review's architecture lens, at the cost of two implementer rounds, one scoped review, and one full re-verification. `Scope keywords:` can name the reader so Check B's fs-walk surfaces consumer files the plan's task list omitted.

**Dependency-caller enumeration check (extends the Consumer-enumeration check):** when a plan task adds an external dependency or side effect to an existing function — a store, network or filesystem read, a new stage or subprocess, a new required environment variable or config key — grep every test directory in the repo, not only the function's own test module, for callers of that function, following wrappers one level up (a test calling a wrapper hits the same dependency) or naming the affected test command instead; list each caller module in the task's Files block (`Modify:`/`Test:`) together with the stub or fixture it needs. A per-task review compares the task's diff against its own brief, so an unlisted caller module in another test file passes every task review and fails only at the whole-branch review or in CI. A configuration-store read added to an export job's entry point, stubbed only in that entry point's own test module while two CI-allowlisted cases in another test module reached the real store, is the archetype — caught only by the whole-branch review's focused test run, at the cost of one Critical finding, one fix-wave item, and a ~30-minute local re-run. `Scope keywords:` can name the function so Check B's fs-walk surfaces caller test files the plan's task list omitted.

**Reader-inventory derivation check (extends the Consumer-enumeration check):** when a spec's deliverables say to apply something "at every reader of" a value — comments, markers, labels, files — derive the plan's reader inventory from the value's read call sites, never from its literal text: find every place code or skill prose reads that kind of value (`--json comments`, `/comments` REST paths, `issue_read`/`get_comments`, `.comments[]`, `listComments`, and so on), then classify each hit as a reader of this value or not, and record the classification in the task's Files block. A grep for the value's literal text (a marker prefix, a heading) is a supplement, never the source: a reader that matches on a plain sentence, or on a prefix the grep never named, still sits on one of those read call sites but is invisible to the literal grep, and a task-level review that compares the plan's inventory against the implemented diff finds the two consistent. #3358's plan derived its marker-reader inventory from greps for marker literals and missed six readers that match on plain sentences or unnamed prefixes — `tidy/SKILL.md`'s parent-gate re-query, `release/bookkeeping.md`'s `Shipped in v…` check, `_shared/headless-self-report.md`'s `Resolved build:` check, the retry-marker prose callers `assess-agent-autonomy/failure-check.md` and `dispatch/settle-and-merge.md`, and `health-core/materiality-digest.js` — of which the whole-branch review caught four and `/claude-tweaks:review`'s lens 3b one more, at the cost of an extra fix wave, a re-review and two PR-body inventory rewrites.

**Retirement-sweep check:** when a plan deletes or retires a named mechanism — a constant, an option, a CLI, a gate — it must carry a task that sweeps every non-history path in the repo (append-only history such as the changelog records what was true and stays) for each phrasing of that mechanism: the identifier, the file path, the option literal, the numeric value as prose, and the issue number used as a label. The task's verification grep names each phrasing, one `-e` per phrasing (`git grep -n -i -e '{phrasing}' …`), and the sweep's file list comes from that grep's output, never from the spec's named list — a spec names the sites its author remembered, not every site that still cites the mechanism. #3311's plan copied its prose-rewrite file list from the spec's boundary amendment 4, which named three files; about 40 further shipped-skill, doc, journey, and test-comment sites still cited the deleted mechanisms as "warning tier", "40 KB ceiling", "#724 budget", "five bloat signals", or `ceiling: Infinity`, and only the whole-branch review caught them (two Important findings), at the cost of one fix wave, two residual sweeps, and a scoped re-review (#3311, squash `f49277005`). This is the plan-time form of the "Deleted-rule citation sweep" and "Grep retired term repo-wide" rules.

**Behavior-change prose sweep (extends the Retirement-sweep check):** when a task changes what an existing mechanism does without retiring it — a selection rule, a parser's coverage, a classification — the same sweep is owed to the prose that describes the old behavior. Grep the old rule's descriptive phrases, not only its identifiers: `Scope keywords:` built from identifiers cannot match a paraphrase, so Check B's fs-walk never surfaces it. List each hit in the task's Files block, or classify it as no-change there. Two specs in one run missed this. After #3541 switched install-record selection to first-applicable, `design-wrapper/impeccable-plugin.md` still said "best project-or-user-scope entry". After #3585 taught the comment stripper regex literals, the `parse-signal-discipline` project skill still said it "does not model regex literals". In both cases only the whole-branch review caught the stale prose, at the cost of a fix-wave item and a scoped re-review each.

**Acceptance-criterion clause-id check:** cite every clause of the spec's `## Acceptance Criteria` by its id, `AC{item}.{clause}`, in the test step that covers it — the test's own name is the natural place (`test('AC2.3: counts each recipient once', …)`). The item is the criterion's 1-based position in the section; the clause is its 1-based position once the item is split on sentence ends and `;`. Run `plan-audit.js {plan} --spec {spec}` while authoring: `checkE.uncovered` lists every clause no test step cites, with its id and text. Citing a criterion by its number alone (`AC2`) covers none of its clauses, and that is the gap this check closes: the incident behind #3099 was a criterion carrying three clauses, a plan that tested two, and a dropped clause that was the only test of a counting invariant a correctness proof rested on — `plan-audit.js` passed, and only the whole-branch review caught it, at the cost of a fix dispatch and a scoped re-review. A clause the plan deliberately leaves untested gets its own line, `Waived AC{item}.{clause}: {reason}`. A spec-coverage map table row naming the id also counts, and quoting the clause text is a fallback, but an id survives rewording, so prefer it.

**Verify-then-maybe-change check:** every sentence in the spec's `## Technical Approach` (its `### Key Files` included) or `## Gotchas` that tells the builder to verify something, read something back, or change something only if a condition holds becomes a plan task or an explicit step inside one, and that task's `Files:` block names each file the sentence reads — as `Modify:` when the condition may change it. A file the build only reads gets a `Waived {path}: {reason}` line whose reason names the step that reads it. Such a sentence is neither a Deliverable nor an Acceptance Criterion, so nothing else carries it into the plan: in the incident behind #3602 a spec named two route files to read back, the plan touched neither, both per-task reviews passed, and only the whole-branch review found the reader the change broke. Run `plan-audit.js {plan} --spec {spec}` while authoring: `checkF.unlisted` lists each path those sections name that no `Files:` block lists.

**AC-evidence persistence check:** when a plan task verifies an acceptance criterion only with a scratch (uncommitted) check — an audit script, a one-off probe, a rendered-page sweep — the plan names that check's run-dir evidence destination, never a conversational build handoff. The destination is one `decisions.md` entry, written via `node "${CLAUDE_PLUGIN_ROOT}/bin/log-decision.js" --run "$PIPELINE_RUN_DIR" --section "/build" --status AUTO --step "AC evidence"` with `--text-file "{text-file}"`, `{text-file}` holding one line carrying the criterion it covers (its `AC{item}` id and wording), the exact command shape, and the pass/fail counts, per `_shared/auto-decision-log.md`'s Text from git or a user paragraph, so a command shape carrying `$`, quotes, or backticks is recorded rather than expanded. The plan also always writes the check's full output to `$PIPELINE_RUN_DIR/evidence/{name}.txt`, created first with `mkdir -p "$PIPELINE_RUN_DIR/evidence"` — an absolute path under the run directory, never a relative one (`_shared/pipeline-run-dir.md`), written with a plain Bash redirect, since a worktree session's Write tool is refused there — and cites that path in the same entry; the log is the raw artifact the entry summarizes, which is what the second call's re-derive-from-artifacts rule checks the entry against. "Scratch checks stay scratch" governs whether a check's *code* is committed, not whether its *result* is recorded: the check's code still stays uncommitted, and only its result goes to the run directory. Under `/claude-tweaks:dispatch`'s two-call split, `build,test` and `review,polish,wrap-up` are separate Task calls that share only the run directory, so a result routed into the handoff is gone before review checks the criterion; `review/code-mode-steps.md` Step 1's Acceptance Criteria check reads these entries instead of re-running the check. A build with no run directory (design mode) reports the result in the handoff as before. #3079's incident: an AC of "a rendered contrast audit over the main routes reports 0 failures" was met by a scratch audit in call 1 whose `decisions.md` named "the AC2 rendered audit" with no result, counts, or log path, so call 2 re-ran the whole audit (68 page renders plus controls).

**Prohibition-vs-existing-mandate check:** when a plan task adds a "never X" rule for an agent role — a reviewer that must not run suites, an implementer that must not push — grep the instruction corpus that role's prompts are built from (here, `plugin/skills/**`, `_shared/` contracts included) for every instruction telling that same role to do X, or anything X subsumes, and name each hit in the plan as either an exception written into the rule or a reconciling edit to that instruction. The prohibition reads as correct inside its own diff, while the mandate it contradicts sits in a paragraph or file the task never opens, so a task-level review comparing plan text against implemented prose has nothing to catch. #3001 added "never run the project's test suites" for `/claude-tweaks:review`'s lens agents: the plan caught lens 3f's Vacuity-evidence diagnostic, which requires one targeted test run, but the `SCRATCH:` probe allowance and the Discrimination diagnostic's revert-and-rerun were reconciled only after the whole-branch review (`8d225ff27`).

**Trust-vs-existing-distrust check:** the mirror of the check above. When a plan task adds a rule that lets an agent role rely on something instead of re-deriving it — cite a recorded result rather than re-run the check, skip a step when a stamp is present — grep the same instruction corpus (`plugin/skills/**`, `_shared/` contracts included) for every mandate telling that role to distrust or re-derive that kind of claim ("re-derive … from raw artifacts", "treat … as unverified", "never trust a prior claim"), and name each hit in the plan as either a carve-out written into the new rule or a reconciling edit to the mandate. The permission reads as correct inside its own diff, while the distrust mandate sits in a template the task never opens, so a task-level review comparing plan text against implemented prose finds them consistent. #3079 let `review/code-mode-steps.md`'s Acceptance Criteria check cite an `AC evidence` entry instead of re-running a scratch check; the plan missed that `dispatch/task-prompt.md`'s second-call template tells the same agent to treat every `decisions.md` claim as unverified until checked against its raw artifact, and only the whole-branch review caught it (PR #3633), at the cost of a fix wave and a scoped re-review.

**Dispatcher-voice check:** when a plan task adds a rule to a file of instructions addressed to a dispatcher (dispatch-prompt notes, lens notes whose siblings say "Tell each dispatched agent…" and where the instruction goes), write the rule in the plan in the neighbouring notes' voice, including the sentence that places it in the agent's prompt. Do not brief the implementer to "phrase it so the agent can apply it from the prompt alone": that brief invites prose addressed to the agent, which reads well in isolation and breaks the file's convention. When the spec enumerates the rule's members (a list of finding kinds, a hyphenated compound such as "missing-or-weak-test"), the plan's test assertion pins each member as a literal, never as "states both halves". A paraphrased assertion and a paraphrased draft agree with each other, so a task-level review comparing prose against plan finds them compliant. #3049's first draft addressed the lens agent directly and dropped "missing test" from the spec's coverage-gap list. The task review returned "Spec compliant", and only the controller's comparison against the neighbouring notes caught both (`139c3d02c`), at the cost of one fix round and a scoped re-review.

**Pairing-loop checks:** when a plan task widens a tolerance, threshold, or window inside a greedy or order-dependent pairing loop, or replaces a first-come pairing loop with best-first assignment, read `plan-authoring-pairing-checks.md` in this directory and run both of its checks (Greedy-matcher widening, Greedy-assignment stranding). They live there because most plans touch no pairing loop.

**Per-task role/review-risk markers (#3378).** Below a task's `### Task N:` heading, outside any fenced code block, an author may add either or both of two optional, line-anchored markers: `**Role:** transcription|integration|judgment` and `**Review risk:** high`. An unmarked task keeps the `size:`-derived mapping (`build/dispatch.md`'s Per-task role/review-risk tier forwarding). Pick a role with SDD's own complexity signals (`## Model Selection`): `transcription` only when the task's own plan text already contains the complete code to write — signature plus tests is `integration`, and under writing-plans 7.0.0's "The implementer writes the body" most mid-size tasks are, so reach for `transcription` rarely; `integration` for a multi-file task with integration concerns or any signature-only task; `judgment` for a task needing design judgment or broad codebase understanding. Mark `Review risk: high` for a task touching any signal `plan-review.md`'s missing-review-risk class lists (concurrency, decision logic, rendering-heavy UI). A marker overrides the header's `size:` mapping for its own task in both directions — intended, since the author sees the full task text, not one run-level estimate. `plan-audit.js --task-markers {plan}` reports a recognized key's unrecognized value (e.g. `**Role:** trivial`) as a warn-only `findings` entry to fix before dispatch; a misspelled key is undetectable and reads as unmarked.

**Governing-skill quote check:** for each file the plan creates or modifies, find the project skills under `.claude/skills/` whose description or body names that file or its module, and quote their applicable rules (bullets, paragraphs, table rows) verbatim into the plan's Global Constraints (never a paraphrase), or say there why none apply. A dispatched implementer sees only its brief, and every task review compares code against the plan, so a rule the plan restated more weakly passes every gate that reads the plan (#3712).
