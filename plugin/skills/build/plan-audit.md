# Common Step 1.5 — Plan Audit

Audit the plan against the actual repo before dispatching execution work. The five deterministic checks below — Check A (paths exist), Check B (scope-keyword sweep), Check C (verification-command pre-check), Check D (control-byte scan), and the headroom check — plus the warn-only Check E (acceptance-criterion clause coverage, #3099) and Check F (spec-named path coverage, #3602) are mechanized in `plugin/bin/plan-audit.js` (#903); this file covers invocation, result interpretation, and policy handling only. Judgment checks (deictic re-resolution, degrade-clause convention, gate-over-producers) stay prose in `plan-authoring.md` — they are not mechanically checkable. The headroom check's composed rows are the multi-spec pre-flight `[IL-140]` lacked: it measures the composed bundle at every compose call site whose sources the plan touches, not only the raw file, so two specs each adding a little prose to different sources of the same call site still see the combined cost.

**Skip condition lives in `build/SKILL.md`'s Common Step 1.5 stub, not here** (the re-read cut: a caller deciding skip-vs-run must never need to load this file to make that decision). This file loads only once the step is confirmed to run. Check D is the one check the skip gate does not cover — even on the skip path, `--bytes` still runs (see that stub's skip sentence): a byte scan on text already in memory costs nothing, and a raw NUL is exactly as fatal in a small plan as a large one.

## Invocation

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/plan-audit.js" {plan-file} [--repo-root {dir}] [--spec {spec-file}] [--count-tasks] [--bytes] [--task-markers]
```

`--repo-root` defaults to `git rev-parse --show-toplevel` of the cwd (or the cwd itself outside a repo) — pass it explicitly only when the plan's own worktree differs from cwd. Stdout is two lines: a compact JSON envelope (`{checkA, checkB, checkC, checkD, headroom, premiseRefs, checkE, checkF}`, each `{ok, ...}`), then a one-line human summary. `checkC` additionally always carries `warnings: [{task, title, raw}, ...]` (tasks whose Step 2 is present but unparseable, see below — a VCS-mutation refusal instead carries `{task, title, command, reason: 'vcs-mutation-refusal', verb}`), `appendShaped: [{task, title, command, path}, ...]` (append-to-existing tasks accepted despite a passing pre-run, see below), and `executed: [{task, command}, ...]` (every command actually run) — all three independent of `ok`. Exit code is `0` iff every check's `ok` is `true` (`headroom.nearCeiling` and `headroom.composedNearCeiling` entries never fail `ok` — only `headroom.breaches` and a `headroom.composed` row with `over > 0` do). Parse the JSON via `JSON.parse(stdout.split('\n')[0])`. `--bytes {plan-file}` runs Check D alone — read-only, no `--repo-root` needed — printing `{"checkD": {...}}` and exiting `1` on findings, `2` on an unreadable file (the same file-read error path the full audit uses).

`--spec {spec-file}` adds Checks E and F. Pass the materialized `work/{n}-spec.md` this build read at Spec Step 1 — in `worktree` mode, the worktree's own copy at that relative path (`flow/materialize.md`: `work/` is the tracked exception that stays in the worktree), not `"$PIPELINE_RUN_DIR"/work/…`, which resolves to the main checkout and holds no `work/` until merge; in `current-branch` mode the two are the same file. Design-doc mode has no materialized spec and omits the flag. Without `--spec`, `checkE` and `checkF` are each `{ok: true, skipped: 'no-spec'}`. An unreadable `--spec` file exits `2` (the plan file's error path, never a silent `skipped`), and `--spec` beside `--count-tasks`, `--bytes`, or `--task-markers` is a usage error (exit `2`).

`--task-markers {plan-file}` (#3378) reads this plan's per-task `**Role:**`/`**Review risk:**` markers — a single-purpose, read-only verb in the same family as `--count-tasks`, never running Checks A-F above. Prints one JSON line, `{"markers": boolean, "tasks": [{"index": n, "title": "...", "role": "transcription"|"integration"|"judgment"|null, "risk": "high"|null}], "findings"?: [{"taskIndex": n, "title": "...", "field": "Role"|"Review risk", "value": "..."}]}` — `markers` is `true` iff any task carries a recognized marker key at all (even with an unrecognized value); `findings` is present only when a recognized key carries a value outside its closed set, and is warn-only — it never changes the exit code. Exits `2` for an unreadable plan or one with no tasks, same as `--count-tasks`. `build/dispatch.md`'s per-task tier forwarding is this flag's one consumer.

## Result interpretation

- **`checkA.ok === false`** (`missing: [{path}, ...]`, plus `missingDetail: [{path, nearestExistingAncestor}, ...]` naming the nearest directory that does exist) — Stop. Present the missing paths (and the nearest existing ancestor, so the author sees where the gap starts). The plan needs revision before execution starts. A `Create:`/`Test:` bullet whose missing parent is brought into existence by *another* `Create:`/`Test:` bullet elsewhere in the same plan is not a finding, and neither is a `Modify:` bullet naming a path an *earlier* task's `Create:` bullet names (a module created in Task N and extended in Task N+1 is a normal plan shape) — only a bullet with no such support, a `Modify:` of a path created only by the same or a later task (or by no task at all), or a `Delete:` bullet (unchanged: it always needs the path to exist today), still fails.
- **`checkC.ok === false`** (`findings: [{task, title, command, expected, actualExitCode, actualSummary}, ...]`) — Stop, unconditionally, the same shape as Check A above — never routed through Check B's auto-mode policy table, and with no `AskUserQuestion` branch. Present the flagged task(s), their commands, and `actualSummary` (the output that already looks like a pass). A non-discriminating verification command is a correctness gap the `_shared/auto-mode-contract.md` HARD-GATE exemption already covers (test failures), not a scope decision with a policy lever. **Resumed build exception (#3666):** on a resume with a still-valid plan (`SKILL.md` Spec Step 2), a finding on a task Spec Step 2 found already implemented is expected — its Step 2 command passes because the task is done — and is not a stop; a finding on any task not yet built still stops.
- **`checkC.appendShaped`** (non-empty, `ok` still `true`) — informational only, never a stop: a task whose Step 1 *appends* new tests to an existing (already-passing) file is not a Check C finding even though its Step 2 pre-run passes today — that's the discrimination the task relies on, not a non-discriminating command. Detected either by an explicit `Expected: FAIL after Step 1` marker on the task (the author-side escape hatch — use it when the heuristic can't see the shape), or by Step 1's text naming a path that's also one of the task's own `Modify:`/`Test:` bullets, exists on disk today, and is the same path Step 2's `Run:` command names. Surface it inline (task, title, command, path) so the audit output still shows the command was pre-run and why it was accepted.
- **`checkC.warnings`** (non-empty, `ok` still `true`) — informational only, never a stop: one entry per task whose Step 2 checkbox line is present but the parser could not extract a `Run:`/`Expected:` pair from it (a wording or formatting drift — e.g. the command sitting in a fenced code block instead of a `Run:` line). Surface it inline (task, title, and the raw excerpt) so a human can judge whether the plan needs updating to the canonical template or the parser needs to learn a legitimately new shape. A warning entry from a genuine VCS-mutation refusal instead carries `{task, title, command, reason: 'vcs-mutation-refusal', verb}` — Check C is documented read-only and never executes a command whose first token (or any token after a top-level `&&`/`;`/`|` segment) is a VCS-mutation verb (`git stash/commit/push/reset/checkout/switch/clean/rebase/merge`, or a writing `gh` subcommand like `gh issue close`/`gh pr merge`), even when the extractor's backtick-span match pulled it out of prose that only mentioned it (#2593).
- **`checkD.ok === false`** (`findings: [{line, column, codePoint, offset}, ...]`, capped at 20 with `truncated: true` beyond that) — Stop, unconditionally, the same Check A-shaped stop as above — never routed through the `scope-creep` policy table. Present each finding as `{line}:{column} {codePoint}` (e.g. `42:7 U+0000`) so the author can jump straight to the offending byte; a legitimate NUL fixture must be written with the `\0` escape, not the raw byte, inside a code fence.
- **`headroom.breaches`** (non-empty) — files over `RAIL_BYTES`, the Read-limit rail in `plugin/bin/lib/skill-audit/budgets.js`; a file this size cannot be read in one Read call. Treat as a Check A-shaped stop: present the breaching file(s) and their byte counts; the plan needs to cut bytes from the file, or move a genuinely lazy section (one some runs never read) into its own cited file, before execution starts. `when:` fencing does not help here — the rail measures the raw file with only the marker lines stripped — and a "read X now" split every run follows moves bytes without cutting what a run loads.
- **`headroom.nearCeiling`** (non-empty, `ok` still `true`) — files at or above 90% of the rail: a plan-time heads-up that never fails the check, informational only. Surface it inline (file, current bytes, remaining headroom) so the plan author can judge whether the *planned* insertion (not estimated by this check — see Non-Goals below) will fit, and if not, plan the same raw-file remedy as a breach (cut bytes, or move a genuinely lazy section out); never blocks.
- **`headroom.composed`** (`[{step, file, line, max, ceiling, over}, ...]`) — one row per compose call site whose sources intersect the plan's touched governed entries, `max` the composed bytes across every combination the sources branch on, measured against the same rail (`ceiling` is `RAIL_BYTES`, with no per-step exceptions). A row with `over > 0` — treat as a Check A-shaped stop, same as a per-file breach: the composed bundle at that call site needs its condition-specific passages fenced with `when:` markers, or composed, before execution starts.
- **`headroom.composedNearCeiling`** (non-empty, `ok` still `true`) — the composed-row analogue of `headroom.nearCeiling`: informational only, never blocks.
- **`headroom.composedErrors`** (`[{step, file, line, error}, ...]`, `ok` still `true`) — a compose call site whose sources intersect this plan's touched governed entries but that could not actually be measured (a missing source, an unreadable source, a malformed `when:` marker) — or, as one row with `step: null`, the composed-bytes report itself crashing before any call site was measured. Informational-but-visible, never blocks — but never treat it as "no finding" either: "could not measure" is not the same claim as "does not apply" (`parse-signal-discipline`). Surface it alongside the other headroom rows so the plan author knows this call site went unchecked, and the CLI's summary line appends `Composed: N unmeasured` whenever it's non-empty.
- **`checkE.uncovered`** (`[{id, clause}, ...]`, `ok` always `true`) — never a stop, and never routed through the `scope-creep` policy: the plan author amends the plan before dispatch. For each entry, either cite `{id}` in the test step that covers that clause, or add a line `Waived {id}: {reason}` when the plan deliberately leaves it untested; then re-run the audit once. In auto mode the amendment needs no prompt — log it to whatever run dir resolves (`_shared/run-dir-resolution.md`): `node "${CLAUDE_PLUGIN_ROOT}/bin/log-decision.js" --run "$PIPELINE_RUN_DIR" --status AUTO --section "/build" --step "Common Step 1.5 (Check E)" --text "amended plan for {N} uncovered AC clause(s) — cited {ids}; waived {ids}" --reversibility high`. In interactive mode, surface the amendment inline — no `AskUserQuestion`.
- **`checkE.unparsed`** (`[{item, raw}, ...]`, `item` null for a section-level entry) — informational-but-visible, never a stop: spec text Check E could not split (no `## Acceptance Criteria` section or an empty one, an item with an unbalanced code span, an unbalanced `(`/`[`, or a fenced block, stray prose beside the list). Never treat it as covered (`parse-signal-discipline`): surface each entry inline, check those criteria against the plan by reading, and log the scan — same command with `--status SCANNED --text "Check E: {N} unparsed AC item(s) — checked by reading" --reversibility n/a`.
- **`checkE.waived`** / **`checkE.covered`** (`[{id, reason}, ...]` / `[{id, via}, ...]`, `via` one of `test-step`, `coverage-map`, `quoted-text`) — informational: with `uncovered` they account for every clause the spec parser produced. A `quoted-text` match is the weakest of the three; prefer converting it to an id citation when amending anyway.
- **`checkE.orphanWaivers`** (`[{id, reason}, ...]`, `ok` always `true`) — informational: a `Waived AC{item}.{clause}:` line whose id matched no clause the spec parser produced. A non-empty list means a stale or typo'd waiver id — the plan author should correct it to a real clause id rather than leave it silently inert.
- **`checkF.unlisted`** (`[{path, section}, ...]`, `ok` always `true`) — Check E's uncovered posture: never a stop, never routed through the `scope-creep` policy, and the plan author amends the plan before dispatch. For each entry, either add `{path}` to the `Files:` block of the task that verifies or changes it (adding that task when none exists), or add a line `Waived {path}: {reason}` when the build only reads it; then re-run the audit once. In auto mode the amendment needs no prompt — log it to whatever run dir resolves (`_shared/run-dir-resolution.md`): `node "${CLAUDE_PLUGIN_ROOT}/bin/log-decision.js" --run "$PIPELINE_RUN_DIR" --status AUTO --section "/build" --step "Common Step 1.5 (Check F)" --text-file "{text-file}" --reversibility high`, `{text-file}` holding `amended plan for {N} unlisted spec path(s) — listed {paths}; waived {paths}` per `_shared/auto-decision-log.md`'s Text from git or a user paragraph (the paths are spec-supplied). In interactive mode, surface the amendment inline — no `AskUserQuestion`.
- **`checkF.unparsed`** (`[{section, raw}, ...]`) — informational-but-visible, never a stop: spec text Check F could not read (a line with an unbalanced or double-backtick code span, or a code fence that never closes). Never treat it as covered (`parse-signal-discipline`): surface each entry inline, check those lines against the plan by reading, and log the scan — same command with `--status SCANNED --text "Check F: {N} unparsed spec block(s) — checked by reading" --reversibility n/a`.
- **`checkF.waived`** / **`checkF.listed`** (`[{path, reason}, ...]` / `[{path, via}, ...]`, `via` is `exact` or `suffix`) — informational: with `unlisted` they account for every path the spec parser extracted. A `suffix` match is the weaker of the two; prefer the full repo-relative path when amending anyway.
- **`checkF.orphanWaivers`** (`[{path, reason}, ...]`, `ok` always `true`) — informational: a `Waived {path}:` line that covers none of the extracted paths (it must equal one or end with `/` + one; a waiver shorter than the spec's path never matches). A non-empty list means a stale or typo'd waiver — the plan author should correct it to an extracted path or drop it rather than leave it silently inert.
- **`checkB.ok === false`** (`unplanned: [string, ...]`) — see "On Check B finding files outside the plan" below; this is the one check routed through the `scope-creep` policy, not a bare stop.

Resolve the `scope-keywords-required` setting — `SCOPE_KEYWORDS_REQUIRED=$(node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-policy.js" --values scope-keywords-required)`:
- `scope-keywords-required: false` — Check B is informational when the plan has no `Scope keywords:` field at all (the CLI reports `checkB.ok: true` trivially in that case — nothing to sweep).
- `scope-keywords-required: true` — gating: if the plan/design has no `Scope keywords:` field (the CLI's `checkB` ran zero sweep), refuse to start. Tell the user: "This project requires scope keywords. Add `Scope keywords: <pattern1, pattern2>` to the plan or design doc and re-run." This is a skill-layer policy check the CLI itself doesn't make — the CLI only reports whether a declared sweep found unplanned matches.

## On Check B finding files outside the plan

### Auto mode (resolved mode is `auto`, including a standalone `/claude-tweaks:build {N} auto` invocation with no `/flow` parent)

Resolve `scope-creep` with ONE resolver call — `node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-policy.js" --run "$PIPELINE_RUN_DIR" scope-creep` (resolve the run dir per `_shared/run-dir-resolution.md` — spawned by `/flow`, or record-mode's own standalone run dir per its materialization exception) — which executes the standard precedence in `_shared/auto-mode-contract.md` (run `config.yml` → project `.claude-tweaks/policy.yml` → schema default) mechanically; apply the envelope's `value`, and carry the envelope's `source` into the row template's `[lever: …]` field (`_shared/auto-decision-log.md`'s Lever attribution section). Log the decision to whatever run dir resolves, per `_shared/run-dir-resolution.md`'s resolution order — an explicit `auto` CLI arg always applies this branch, never the Interactive-mode prompt below, regardless of whether a Manifesto-computed `config.yml` exists. Apply:

| Policy | Action | Log entry |
|---|---|---|
| `add-to-plan` | Auto-add matched files to the plan as new tasks. Commit the plan update. | `AUTO {time} — Step 1.5: scope-creep — added {N} files to plan ({list}). Reversibility: high (commit {hash}). [lever: scope-creep=add-to-plan ({source})]` |
| `stop-and-ask` | Stop. Present the list inline. (Falls through to interactive prompt below.) | `KEPT-PROMPT {time} — Step 1.5: scope-creep matched {N} files, policy is stop-and-ask. Surfaced inline. [lever: scope-creep=stop-and-ask ({source})]` |

## What each check covers

- **Check A** — every path in the plan's `Files:` sections (`Create:`/`Modify:`/`Delete:`/`Test:` bullets) exists, or (for `Create:`/`Test:`, since a `Test:` bullet routinely names a brand-new test file the plan is about to write) its parent directory exists on disk, is exactly one new directory level away from an existing ancestor (#2745 — writing the file creates that single new directory as a side effect, so a lone `Create:`/`Test:` bullet introducing one new module directory passes on its own), **or** is brought into existence by another `Create:`/`Test:` bullet elsewhere in the plan — a `Create:`/`Test:` bullet whose parent is missing by more than one directory level, with no such supporting bullet, still fails. A `Modify:` bullet additionally passes when the path itself doesn't exist yet but an *earlier* task's `Create:` bullet names it (a module created in Task N and extended in Task N+1 is a normal plan shape) — a `Modify:` of a path created only by the same or a later task, or by no task at all, still fails.
- **Check B** — when the plan declares `Scope keywords:`, an fs-walk (never a gitignore-honoring grep — a gitignored-but-plan-relevant file must not silently vanish from the sweep) flags any repo file containing a match that isn't itself one of the plan's declared paths. When a task changes which rows of a shared reader returns (see `plan-authoring-checks.md`'s Consumer-enumeration check), naming that reader in `Scope keywords:` lets this same fs-walk surface consumer files the plan's task list omitted.
- **Check C** — for each task's own `- [ ] **Step 2: …**` sub-step declaring `Run: {command}` / `Expected: FAIL …`, runs `{command}` once, read-only, against current repo state. The only finding: the command already exhibits a passing/success signature (exit code 0, or a success marker with no failure marker) despite the `Expected: FAIL` declaration. A command erroring or cleanly failing pre-dispatch is never a finding — a hard error on a later task in a plan whose tasks build on each other sequentially is common and expected. An append-shaped task (Step 1 appends to an existing, already-passing file named by both a `Modify:`/`Test:` bullet and Step 2's `Run:` command, or declared via the `Expected: FAIL after Step 1` marker) is reported under `appendShaped` instead of `findings` — never a finding. Separately, a task whose Step 2 checkbox line is present but whose `Run:`/`Expected:` pair the parser can't extract (a wording/formatting drift, not "no Step 2 at all") is reported as a `warnings` entry — never a finding, never blocking. Before ever calling `run()`, Check C also refuses (never executes) any extracted command whose first token — or any token immediately after a top-level `&&`/`;`/`|` segment separator — is a VCS-mutation verb; a refused command is reported as a distinct `warnings` entry (`reason: 'vcs-mutation-refusal'`), never a finding. `checkC`'s return also carries `executed` — one `{task, command}` entry per command it actually ran — so the audit output shows exactly what was executed, distinct from what was refused or found unparseable.
- **Check D** — scans the raw plan text (already `readFileSync`'d as UTF-8) for any code point in `U+0000`-`U+001F` or `U+007F` other than tab/LF/CR. The only finding: a raw control byte (the common real-world case: a NUL written as the literal character instead of the `\0` escape inside an inlined test fixture) — a plan carrying one commits as a git-classified binary blob, unreadable to `git diff`/`grep`/`Read`/`Edit` alike, so this is the last cheap place to catch it. Findings cap at 20 (`truncated: true` beyond that).
- **Headroom** — for each existing file (`Modify:`/`Delete:`/`Test:`, never `Create:`) under the governed skill-corpus set (`plugin/skills/**/*.md` — the same set the Read-limit rail binds for every `SKILL.md` and sub-file), its current byte count and headroom against `RAIL_BYTES`, the Read-limit rail in `plugin/bin/lib/skill-audit/budgets.js`. v1 reports current bytes + headroom only — it never estimates the size of the plan's own planned insertion (Non-Goals); the plan author judges borderline cases from the reported headroom. Alongside those per-file rows, it also reports `composed`/`composedNearCeiling`: the composed bundle at every `plugin`-wide compose call site whose sources intersect the plan's touched entries, measured under every combination those sources branch on — the multi-spec pre-flight `[IL-140]` lacked, since it fires per spec regardless of which spec's plan happens to touch which source first. A touched call site the tool couldn't actually measure (missing/unreadable source, malformed marker) reports separately as `composedErrors`, never silently folded into "no findings".
- **Check E** (`--spec` only; warn-only — `ok` is always `true`, so it never changes the exit code: clause splitting is a prose heuristic, and a hard gate would block builds on its false positives) — reads the spec's `## Acceptance Criteria` section: one item per top-level list line (a `[ ]` checkbox stripped), or one per paragraph when the section has no list at all; each item split into clauses on sentence ends and `;`, never inside a code span, after an abbreviation such as `e.g.`, or inside parentheses. Ids are `AC{item}.{clause}`, both 1-based, item being the criterion's position in the section. A clause is **waived** by a plan line `Waived AC{item}.{clause}: {reason}`; otherwise **covered** when its id appears in a task's test step (a `**Step N: …**` sub-step whose title names a test or a verification) or in a markdown table row — a spec-coverage map, accepted when an author writes one, though the installed `/superpowers:writing-plans` template carries none — or when its text is quoted there; otherwise **uncovered**. A bare criterion number (`AC2`) covers no clause: #3099's incident was a criterion counted covered once any task cited its number, while one of its three clauses had no test. Anything the splitter cannot read lands in `unparsed`, never in `covered`.
- **Check F** (`--spec` only; warn-only — `ok` is always `true`, so it never changes the exit code: path extraction from prose is a heuristic, and a hard gate would block builds on its false positives) — reads the spec's `## Technical Approach` (its `### Key Files` included) and `## Gotchas` sections, never `## Acceptance Criteria` or `## Deliverables` (Check E reads the AC section; Deliverables are the plan's own task list), and extracts every repo path they name in a code span. A path-like token has at least one `/`, a file extension, and no spaces, globs, `{placeholders}`, or URL scheme. Both sides are normalized before matching — a leading `./` and a `:NN` / `:NN-MM` line suffix are dropped. A path is **listed** when it equals a path in some task's `Files:` block (`via: 'exact'`) or is a whole-segment suffix of one (`_shared/x.md` matches `plugin/skills/_shared/x.md`, `via: 'suffix'`); **waived** by a plan line `Waived {path}: {reason}` whose path equals it or ends with `/` + it, the same whole-segment rule (a waiver wins over listing; there is no quoted-text fallback, since a path mentioned in task prose is not a task that touches it); otherwise **unlisted**. A path the build only reads is exactly what this check exists to catch, not a false positive: it still needs a task that names it or a waiver. A section the spec lacks contributes nothing; a line with an unbalanced code span or a code fence that never closes lands in `unparsed`, never in `listed`.

Check A/B/C and the headroom check all share Check A/B's existing skip gate (fewer than 3 file references and no `Scope keywords:` field, or `ceremony-profile: fast-lane` — roster tag `plan-audit`, `_shared/ceremony-profile.md`) — none of them introduces a new skip condition of its own. **Check E shares that gate too** (#3099's ruling): like Check D it reads only text already in memory, but it is warn-only, so skipping it on a trivial plan loses a warning, never a stop — unlike a raw NUL, which is fatal at any size. The skip path's `--bytes` call therefore stays Check D alone (`--spec` beside `--bytes` is a usage error). **Check F shares that gate too** (#3602's ruling), for Check E's reason: it reads only text already in memory and is warn-only. **Check D is the one exception**: it runs via `--bytes` even on the skip path (`build/SKILL.md`'s Common Step 1.5 skip sentence) — a byte scan on text already in memory costs nothing, and a raw NUL is exactly as fatal in a two-file plan as a large one. `micro-plan.md`'s fast-lane composed plan skips `plan-audit.js` entirely (it composes the plan from the header and never inlines fixtures), so Check D never applies there either — out of scope by construction, not an oversight.
