# Common Step 2 — Subagent Dispatch Procedure

Full dispatch procedure for the **subagent** execution strategy (Common Step 2's default), read by `SKILL.md`'s retained skeleton bullet: the `profile=frontier` guard, its strategy precondition, the cost-bound distinction, and the complete per-task model-profile / AC-forwarding / review-model-pinning detail.

**`profile=frontier` guard (canonical — cited by `build-options.md`, not restated).** `profile=frontier` is the human-typed hardest-build opt-in: it is reachable **only** by the literal `profile=frontier` (or its `tier=frontier` alias — `build-options.md`'s Model profile override section) token present in the human's own invocation text. No `size:` facet, no policy value, no model stance, and no Pipeline Config Manifesto option ever selects Frontier for a build — the `size:` → profile bridge in the subagent procedure in this file tops out at Capable, full stop. A `/flow` run that forwards the user's own typed token is compliant; a Manifesto question offering `frontier` as a choice is not, and none exists.

**Strategy precondition (numbered step, checked before any dispatch).** When `profile=frontier` (or its `tier=frontier` alias) is present in `$ARGUMENTS`:
1. Resolve the execution strategy that would otherwise apply (see Build Options' default-resolution order).
2. If the resolved strategy is not `subagent` (i.e. it is `batched`), refuse the token at options-resolution time — before invoking either execution skill — with: `"profile=frontier requires the subagent execution strategy (sequential SDD implementer dispatches satisfy the Subagent Contract's no-parallel-fan-out rule for Frontier; batched execution has no such guarantee). Re-run with the subagent strategy, or drop profile=frontier."`
3. If the resolved strategy is `subagent`, proceed — `profile=frontier` binds only inside the subagent procedure below in this file.

This sequential-dispatch precondition is a *distinct* bound from the actual **cost** bound: the per-run cap is `frontier-run-cap` (`.claude-tweaks/policy.yml`, default 3 — `_shared/subagent-dispatch-core.md`'s Model Selection section), enforced by `bin/resolve-profile.js` per dispatch, independent of this strategy check.

**subagent** (default): Check the materialized header's `size:` field (`skills/flow/materialize.md`'s reader table — the header's model-profile signal; a pre-rename header carries `effort:` instead, read as `size` when no `size:` line is present, per that file's "Reading a pre-rename header"). If present, invoke `/superpowers:subagent-driven-development` with an explicit instruction to default every per-task implementer dispatch in this spec to the corresponding model profile — `low` → Fast, `medium` → Standard, `high` → Capable — overriding that skill's own per-task complexity heuristic for this spec's tasks specifically (a spec whose originating finding was already judged cheap or expensive to fix doesn't need re-deriving that signal from file-count heuristics). When the header carries no `size:` field, invoke `/superpowers:subagent-driven-development` with no profile override. **Foreground execution instruction (#1965):** in the same invocation instruction, also direct `/superpowers:subagent-driven-development` to include, in every per-task implementer dispatch and every reviewer dispatch it composes, this constraint: run `npm test` and every other long-running command in the foreground of that turn, output redirected to a file if it's long — never with `run_in_background` — and never end the turn waiting on a background test run, fix-round, or child agent's completion notification; a dispatched agent that yields this way is never re-woken and the run stalls silently. **Forward the spec's Acceptance Criteria to per-task review:** in the same invocation instruction, also direct `/superpowers:subagent-driven-development` to include the relevant excerpt of this spec's own `## Acceptance Criteria` section — read from the materialized spec at `{run-dir}/work/{n}-spec.md`, never re-fetched from the live GitHub issue or re-derived from the task brief — alongside the diff and the task's own brief in every per-task review dispatch, so a per-task review can catch a task brief that misstates a spec criterion instead of relying solely on the final whole-branch review. **Status-token requirement (#2740).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` to require that every per-task implementer dispatch, task-reviewer dispatch, and re-review dispatch it composes ends its own reply with the Subagent Contract's required status line (`STATUS: {WORD}`, one of `DONE`/`DONE_WITH_CONCERNS`/`NEEDS_CONTEXT`/`BLOCKED`, the reply's last non-empty line) per `_shared/subagent-output-contract.md`'s Implementer Status Protocol — reuse that file's canonical wording verbatim rather than inventing new phrasing. **Tree-immutability rule for discrimination checks (#2740).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` to instruct every task-reviewer and re-review dispatch it composes that it must never mutate the shared worktree in place — a discrimination check that needs a reverted or edited file (e.g. proving a new test fails against the pre-fix code) runs in a scratch `git worktree add`, never via `git checkout --` or an in-place edit-then-restore in this shared worktree, since a concurrent implementer's own in-flight edit in the same tree would otherwise be silently lost. **Review findings go through the deferral gate (#3004).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` that every Minor (or higher) finding from a per-task reviewer or the whole-branch review is either fixed in this build, or carried to the ledger only after passing `_shared/deferral-gate.md`'s fix-now check with exactly one `Defer-reason:` from that file's vocabulary, written inline in the row's Resolution text. Severity alone ("minor", "fine to defer") is never a reason. **Carry forward surviving SDD ledger residue before Finish:** in the same invocation instruction, also direct `/superpowers:subagent-driven-development` that, at its own Finish step, before deleting the plan's workspace (`rm -rf <workspace>`), it must copy every remaining `<workspace>/progress.md` line matching `minor (deferred):`, `parked —`, or `Ruling:` into this build's own open items ledger (`/claude-tweaks:ledger`'s Add Item operation) — phase `build`, status `deferred` for a `minor (deferred):` line, `observation` for a `parked —` line, or `open` for a `Ruling:` line — a line matching more than one marker is copied once, under its first match in that order — using the line's own one-liner (the text following the marker) as the ledger Item description. Escape every `|` in a carried one-liner as `\|` (`_shared/ledger-format.md`'s Format section) — a `Ruling:` line routinely quotes a regex alternation or a table fragment. A `minor (deferred):` line carries its `Defer-reason: {value}` from the moment SDD's controller writes it (the review-finding rule above), so the final whole-branch review triages each minor with its reason attached, and the carried row's Resolution text repeats it; a minor with no valid reason is not deferred — it goes to the final review's fix wave (on the single-task fast-lane skip, the last task review's fix loop). A line whose first marker match is `Ruling:` is load-bearing — every pre-flight, mid-run, breaker, and residual final-review ruling — because SDD writes the bare form only where it decided in lieu of a human, and the residual final-review shape has no pinned prefix to sniff; a `parked —` line's first match is `parked —`, so the match order already separates the two classes. For each load-bearing ruling, ledger first, then the file: (1) append the ledger row — phase `build`, status `open`, Item `SDD ruling — {one-liner}: ratify or reverse at the Review Console (staged/sdd-ruling-{N}.md)` (this is the one `open` row the mapping above already copies for a `Ruling:` line, with its Item text set to this form — never a second row); then (2) write the staged file via `node "${CLAUDE_PLUGIN_ROOT}/bin/stage-item.js" --run "$PIPELINE_RUN_DIR" --id "sdd-ruling-{N}" --file {tmp}.md --allocate` (`{N}` a per-invocation counter from 1; `--allocate` for the same clobber reason `build-deviation-{N}` carries it); the temp file must end in `.md`, since `stage-item.js` takes the staged extension from the source; the file opens with a header block `Title:` (the one-liner, truncated to the console's row width) / `Kind: sdd-ruling` / `Ruling:` (the `progress.md` line verbatim) / `Staged-at:` (short HEAD sha) / `Ledger: {ledger path}#{item-number}` (the item number step (1) just assigned — the reason for the order) and a body holding the ruling text, the task number when the line carries one, and the two dispositions (ratify / reverse); then (3) log `STAGED {time} — SDD ruling carried forward: "{one-liner}". Stage path: staged/sdd-ruling-{N}.md. Reversibility: high.` under `## /build` via `log-decision.js`, passing `--text` single-quoted with any `'` in the one-liner written as `'\''` — never double-quoted: a ruling routinely carries backticks and `$`, which a double-quoted shell argument executes as command substitution, and a stray `"` truncates the entry. The path named by step (3)'s `STAGED` line and by the row's Item text is the path `stage-item.js` actually wrote (its first stdout line); when the CLI reports it reallocated the id (`--id {requested} already exists in staged/ — wrote {actual} instead`), update the just-appended row's Item text to the actual path before writing the `STAGED` line — the staged file's `Ledger:` header is unaffected (it names the ledger row, not the file). If `stage-item.js` exits non-zero, write no `STAGED` line: rewrite the row's Item text without its `(staged/…)` suffix — so `_shared/ledger-format.md`'s unapplied-staged-proposal exclusion cannot hide the row — and log `SKIP {time} — SDD ruling carry-forward (degraded): condition: stage-item.js exited {code} for sdd-ruling-{N} ({first stderr line}) → fallback: ledger row #{item} left open with no staged file; the resolve gate drills it. Reversibility: n/a.` (`_shared/auto-decision-log.md`'s Degrade-trace rule). Both Item rewrites edit the cell Add Item's own Edit wrote a moment earlier, before any other writer touches the ledger — the same operation, not an Update Item. Add Item's De-duplication on Append never skips a ruling row: two rulings sharing the template stem are distinct decisions, so every ruling gets its own row and item number. The Review Console's Pending review section resolves it — `apply` there means ratify (`wrap-up/review-console-appendix.md`'s `sdd-ruling-*` bullet). **No run directory** (standalone `/claude-tweaks:build`, no `$PIPELINE_RUN_DIR`): no console will read `staged/`, so append the ledger row with status `open` and the same Item text minus the staged path, stage nothing, and list each ruling in the Step 7 handoff's `### SDD rulings` section (`build/handoff-template.md`); a later standalone `/claude-tweaks:wrap-up`'s resolve gate drills it per item with its existing vocabulary — `Accept` = ratify, `Keep`/`Defer` = reverse as a follow-up, `Fix anyway` = reverse now — and Phase 1's fix-now criteria apply as written (a ruling's text states a decision, not a defect, so it does not qualify on its own). The SDD workspace (including `progress.md`) is deleted immediately after Finish's own "Rulings I made" collection, and claude-tweaks' `/claude-tweaks:wrap-up` reads only the run ledger, never the deleted SDD workspace — copying first is what keeps a deferred-minor or parked finding from being lost at that seam. SDD 6.3.0+ ledgers its pre-flight, fix-loop breaker and final-review decisions as `Ruling:` lines instead of stopping for the human, and `/build` suppresses `/superpowers:finishing-a-development-branch` — the channel SDD names for residual load-bearing findings — so a ruling not copied here reaches no durable record. **Persist SDD's final whole-branch review before Finish (#3386):** in the same invocation instruction, also direct `/superpowers:subagent-driven-development` that, when its final whole-branch review was dispatched, at its own Finish step, before deleting the plan's workspace, it must resolve a session-scoped scratch path with `node "${CLAUDE_PLUGIN_ROOT}/bin/session-tmp-resolve.js" SDD_FINAL_REVIEW=sdd-final-review-{run-id}.md` (`{run-id}` is `basename "$PIPELINE_RUN_DIR"`; no `eval` — it prints `SDD_FINAL_REVIEW="<path>"`), write the review to that printed literal path with the Write tool, and persist it with `node "${CLAUDE_PLUGIN_ROOT}/bin/write-run-artifact.js" --run "$PIPELINE_RUN_DIR" --name sdd-final-review.md --file "{review-path}"`, where `{review-path}` is that same printed literal path substituted in (a shell variable set in an earlier Bash call does not survive into a later one) — never an Edit/Write straight to the run directory, which a worktree-isolated session's harness refuses (`_shared/pipeline-run-dir.md`'s tool-level pinning note); the writer lands it at `$PIPELINE_RUN_DIR/sdd-final-review.md`. The review contains: the final reviewer's findings verbatim with their severities; the reviewed commit SHA (HEAD when the final review's package was built) and that package's base commit; the fix wave's commit range (`FIX_BASE..HEAD`, both ends written as commit SHAs), or "no fix wave"; and the scoped re-review's per-finding verdicts verbatim, or "no re-review" when there was no fix wave. It is maintainer evidence for #3381's double-review measurement — nothing blocks on its absence. A non-zero exit from the writer never blocks Finish — the SKIP line below then records the absent file. Write nothing for a standalone `/build` (no `$PIPELINE_RUN_DIR`) or when the whole-branch review was skipped (the Single-task fast-lane skip below). When SDD returns, if its final whole-branch review was dispatched, log one non-blocking line under `## /build` in `$PIPELINE_RUN_DIR/decisions.md` via `log-decision.js`: `AUTO … — SDD final review captured to sdd-final-review.md` when the file exists, or `SKIP … — SDD final review dispatched but sdd-final-review.md absent` when it does not. The SKIP line is what lets a reader tell a skipped capture apart from a review that never ran. **Standing AC-forwarding verification (#496).** #360's own Acceptance Criterion 4 required live proof this instruction actually lands in a real composed dispatch prompt, not just confirmation the instruction text is correctly worded — and two real opportunities to exercise it (the batch that shipped #360, record #1537) both passed unverified because SDD's own `.superpowers/sdd/{run-slug}/` scratch directory is gitignored and routinely swept by its Finish step before `/build`'s own thread regains control to inspect it. Close that window structurally rather than relying on someone remembering to check: in the same invocation instruction, also direct `/superpowers:subagent-driven-development` that, for its **first** per-task review dispatch only, it must resolve a session-scoped scratch path with `node "${CLAUDE_PLUGIN_ROOT}/bin/session-tmp-resolve.js" SDD_SAMPLE=sdd-dispatch-sample-{run-id}.txt` (`{run-id}` is `basename "$PIPELINE_RUN_DIR"`; no `eval` — it prints `SDD_SAMPLE="<path>"`), write the composed reviewer prompt verbatim to that printed literal path with the Write tool, and persist it with `node "${CLAUDE_PLUGIN_ROOT}/bin/write-run-artifact.js" --run "$PIPELINE_RUN_DIR" --name sdd-dispatch-sample.txt --file "{sample-path}"` before sending it, where `{sample-path}` is that same printed literal path substituted in (a shell variable set in an earlier Bash call does not survive into a later one) — never an Edit/Write straight to the run directory, which a worktree-isolated session's harness refuses (`_shared/pipeline-run-dir.md`'s tool-level pinning note). A non-zero exit from the writer never blocks the dispatch — send the review anyway; the "No sample file at all" branch below then logs it. The persisted copy is a location under the pipeline run directory, not the SDD scratch directory, so it survives past SDD's own Finish step (the run directory itself is only archived, never deleted, at `/wrap-up`). Skip this entirely for a single-task plan (no per-task review dispatch exists to sample). When SDD returns, before proceeding to Common Step 3: if `$PIPELINE_RUN_DIR/sdd-dispatch-sample.txt` (the path the writer echoed) exists, read it with the Read tool and check whether it contains the same Acceptance Criteria excerpt this instruction forwarded.
- **Present:** log `AUTO {time} — AC-forwarding verified: sdd-dispatch-sample.txt contains the forwarded Acceptance Criteria excerpt. Reversibility: n/a.` and delete the sample file with `node "${CLAUDE_PLUGIN_ROOT}/bin/write-run-artifact.js" --run "$PIPELINE_RUN_DIR" --name sdd-dispatch-sample.txt --delete` (its evidence is now in `decisions.md`, not a second copy on disk).
- **Absent from an existing sample file:** this is the real gap #496 exists to catch — file it via `/claude-tweaks:capture` as its own fix-shaped record against `/build`'s Common Step 2 AC-forwarding instruction (a wiring gap between this file's own instruction and SDD's actual per-task template), log `AUTO {time} — AC-forwarding verification FAILED: sdd-dispatch-sample.txt exists but does not carry the Acceptance Criteria excerpt — filed #{new-record}. Reversibility: n/a.`, and continue the build (this is an observability gap in the dispatch instruction, not a build-blocking defect).
- **No sample file at all** (single-task plan, SDD's own procedure didn't honor the copy instruction, or the writer refused): log `SKIP {time} — AC-forwarding verification: no sdd-dispatch-sample.txt (single-task plan, SDD did not honor the sample-copy instruction, or the writer refused). Reversibility: n/a.` via `log-decision.js --status SKIP --section "/build"` per `_shared/auto-decision-log.md`'s degrade-trace rule — never silently proceed with no trace either way.

Standalone `/build` (no `$PIPELINE_RUN_DIR`): skip this verification entirely — there is no durable run directory to sample into, and list the skip in the Step 7 handoff instead. **Forbid `git stash` in every per-task implementer dispatch:** in the same invocation instruction, also direct `/superpowers:subagent-driven-development` to instruct each per-task implementer to never run `git stash` or `git stash pop` — the stash stack is shared repo-wide across every worktree of this checkout, so it can pop or clobber a sibling worktree's in-flight work (`_shared/subagent-dispatch-core.md`'s no-stash rule, cited rather than restated) — and to compare against a baseline via `git show <rev>:<path>` or set its own work aside with a temporary WIP commit instead. **Cherry-pick source-branch PR check (#1957):** worktree strategy only, in the same invocation instruction, also direct `/superpowers:subagent-driven-development` to instruct each per-task implementer that, after any commit whose message carries a `(cherry picked from commit {sha})` trailer, it must run `worktree-setup.md`'s "Cherry-pick source-branch PR check" before starting the next task — a commit with no such trailer needs no action. **`profile=<fast|standard|capable|frontier>` token:** when present in `$ARGUMENTS`, it always wins over the `size:`-derived profile (or the no-override default) for this run only — a one-off way to force extra rigor (or cut cost) on a specific build without re-triaging or re-specifying the record. **`profile=frontier` specifically** (guard above; strategy precondition already confirmed `subagent`): instruct `/superpowers:subagent-driven-development` to resolve each sequential per-task implementer dispatch via `node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-profile.js" frontier --run-dir "$PIPELINE_RUN_DIR"` (`_shared/subagent-dispatch-core.md`'s Model Selection dispatch procedure) rather than hardcoding Fable — degradation to Capable (cap exhausted, non-interactive context, or stance below `default`) is handled entirely by that resolver call and logged in its `source`; this step never re-enumerates the degrade preconditions locally. **Whole-branch review model.** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` to compute the run's diff facts by parsing the branch's `git diff --numstat -z` output first with `bin/lib/git-z.js`'s `parseNumstatZ` and passing the result to `bin/lib/dispatch/ceremony-derive.js`'s `computeDiffFacts` (it takes the parsed `{path, additions, deletions}[]` array, never the raw string; the runnable composition is in `skills/wrap-up/ceremony-derivation.md` step 1); then resolve its own final whole-branch review dispatch via `node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-profile.js" capable --run-dir "$PIPELINE_RUN_DIR" --diff-facts '{diff-facts-json}'` and pass the resolved `model` explicitly on that one dispatch — this review is a third-party dispatch, not one of `_shared/subagent-dispatch-core.md`'s enumerated Frontier singleton slots, so Capable is the ceiling here regardless of `profile=frontier`. `--diff-facts` is a downward-only bound (#1912, `_shared/subagent-dispatch-core.md`'s Model Selection section): on a diff of at most one implementation file and under 60 total lines, the resolver caps this dispatch to Standard instead of Capable and the `source` field reads `diff-ceiling` — never raises the tier, never touches the `profile=frontier` path above. An explicit per-invocation `model` overrides the session's own `/model`/effort (that file's Overrides section, probed 2026-08-17) — this is what keeps a session-level model change from silently downgrading the review. Also instruct that reviewer, in the same dispatch text: review the diff, and run only the focused tests it names — never the full suite. Common Step 5 runs the full suite once, after the review's fix wave (or, on the skip path, after the last task review), and is the producer of the runner-written pass stamp (`verify.js`, #1921); a reviewer-side full run duplicates that pass without producing the artifact. **Folded verification task (#3118).** A plan task folded into Common Step 5 (typically a final "full verification, no new code" task) contributes only its runner checks — the types, lint, and tests `test/verification.md` runs. Every other step it names runs after Step 5 passes and before Common Step 7's handoff: a browser check through `/claude-tweaks:browse`, a script by running it. One that runs and finds a defect is a Step 5-class failure — fix it, commit, re-run that step to confirm the fix, and re-run Step 5 before the handoff, never defer it to `/review`. A step that cannot run (no browser backend, no dev server, a truly manual check) writes `SKIP {time} — {plan task} step "{step}" (skipped): {condition} → not run by /build; surfaced for /review. Reversibility: n/a.` via `log-decision.js --status SKIP --section "/build"` per `_shared/auto-decision-log.md`'s Degrade-trace rule; standalone `/build` (no run dir) lists it in the Step 7 handoff's Skipped steps section instead (`handoff-template.md`). A step that ran in full is never logged as `SKIP`; one that ran only in part (a dev server dying mid-pass) logs `(degraded)` in place of `(skipped)` and names what did not run. The rule keys on the steps the folded task names, not on the record's `surface:`. The upstream step this instruction targets (SDD's `## Final Review`) is pinned in `tools/upstream-drift/manifest.yml`. **Single-task fast-lane skip (#1926; roster tag `sdd-whole-branch-review`, `_shared/ceremony-profile.md`).** Before composing the whole-branch review instruction above, read `config.yml`'s `ceremony-profile` from the run directory and run `node "${CLAUDE_PLUGIN_ROOT}/bin/plan-audit.js" --count-tasks {plan-file}` (one JSON line, `{"tasks": n, "batched": boolean}`; exit 2 means the plan is unreadable or has no tasks — treat as not qualifying). Standalone `/build` (no `config.yml`) never skips. When the profile is `fast-lane` **and** `tasks` is exactly `1` **and** `batched` is `false`, instruct `/superpowers:subagent-driven-development` instead to skip its final whole-branch review dispatch (and the fix wave and re-review that follow it) and stop after the last task review — the task review's diff *is* the whole branch — and log `SKIP {time} — Whole-branch review skipped: fast-lane, single-task plan (task review covers the whole branch). Reversibility: n/a.` written with `log-decision.js --status SKIP --section "/build"` per `_shared/auto-decision-log.md`'s Degrade-trace rule. Multi-task plans and batched plans (`batched: true`, regardless of count) keep the whole-branch review at every profile; a `standard` profile keeps it for any count. Here "batched plan" means a bundled multi-item plan marked per `build/plan-authoring-checks.md` — distinct from the `batched` execution strategy above. The count comes from the plan file only — never from the diff or SDD's own narration (`[IL-07]`). Otherwise — the review is dispatched — log the resolution: `AUTO {time} — Whole-branch review dispatched on {model} (resolve-profile.js capable). Reversibility: n/a (dispatch-time model selection, not a code mutation).` After the final code review completes — or, on the skip path, after the last task review — **stop the skill and return here** — do not let it invoke `/superpowers:finishing-a-development-branch`. `/build` handles post-execution steps (simplification, alignment, verification) before any branch finishing.
