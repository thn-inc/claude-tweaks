# Common Step 2 — Subagent Dispatch Procedure

Full dispatch procedure for the **subagent** execution strategy (Common Step 2's default), read by `SKILL.md`'s retained skeleton bullet: the `profile=frontier` guard, its strategy precondition, the cost-bound distinction, and the complete per-task model-profile / AC-forwarding / review-model-pinning detail.

**`profile=frontier` guard (canonical — cited by `build-options.md`, not restated).** `profile=frontier` is the human-typed hardest-build opt-in: it is reachable **only** by the literal `profile=frontier` (or its `tier=frontier` alias — `build-options.md`'s Model profile override section) token present in the human's own invocation text. No `size:` facet, no policy value, no model stance, and no Pipeline Config Manifesto option ever selects Frontier for a build — the `size:` → profile bridge in the subagent procedure in this file tops out at Capable, full stop. A `/flow` run that forwards the user's own typed token is compliant; a Manifesto question offering `frontier` as a choice is not, and none exists.

**Strategy precondition (numbered step, checked before any dispatch).** When `profile=frontier` (or its `tier=frontier` alias) is present in `$ARGUMENTS`:
1. Resolve the execution strategy that would otherwise apply (see Build Options' default-resolution order).
2. If the resolved strategy is not `subagent` (i.e. it is `batched`), refuse the token at options-resolution time — before invoking either execution skill — with: `"profile=frontier requires the subagent execution strategy (sequential SDD implementer dispatches satisfy the Subagent Contract's no-parallel-fan-out rule for Frontier; batched execution has no such guarantee). Re-run with the subagent strategy, or drop profile=frontier."`
3. If the resolved strategy is `subagent`, proceed — `profile=frontier` binds only inside the subagent procedure below in this file.

This sequential-dispatch precondition is a *distinct* bound from the actual **cost** bound: the per-run cap is `frontier-run-cap` (`.claude-tweaks/policy.yml`, default 3 — `_shared/subagent-dispatch-core.md`'s Model Selection section), enforced by `bin/resolve-profile.js` per dispatch, independent of this strategy check.

**subagent** (default): Check the materialized header's `size:` field (`skills/flow/materialize.md`'s reader table — the header's model-profile signal; a pre-rename header carries `effort:` instead, read as `size` when no `size:` line is present, per that file's "Reading a pre-rename header"). If present, invoke `/superpowers:subagent-driven-development` with an explicit instruction to default every per-task implementer dispatch in this spec to the corresponding model profile — `low` → Fast, `medium` → Standard, `high` → Capable — overriding that skill's own per-task complexity heuristic for this spec's tasks specifically (a spec whose originating finding was already judged cheap or expensive to fix doesn't need re-deriving that signal from file-count heuristics). When the header carries no `size:` field, invoke `/superpowers:subagent-driven-development` with no profile override. **Foreground execution instruction (#1965):** in the same invocation instruction, also direct `/superpowers:subagent-driven-development` to include, in every per-task implementer dispatch and every reviewer dispatch it composes, this constraint: run `npm test` and every other long-running command in the foreground of that turn, output redirected to a file if it's long — never with `run_in_background` — and never end the turn waiting on a background test run, fix-round, or child agent's completion notification; a dispatched agent that yields this way cannot count on being re-woken, and the run stalls silently when it is not. **Forward the spec's Acceptance Criteria to from the materialized spec at `{run-dir}/work/{n}-spec.md`, never re-fetched from the live GitHub issue or re-derived from the task brief — alongside the diff and the task's own brief in every per-task review dispatch, so a per-task review can catch a task brief that misstates a spec criterion instead of relying solely on the final whole-branch review. **Status-token requirement (#2740).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` to require that every per-task implementer dispatch, task-reviewer dispatch, and re-review dispatch it composes ends its own reply with the Subagent Contract's required status line (`STATUS: {WORD}`, one of `DONE`/`DONE_WITH_CONCERNS`/`NEEDS_CONTEXT`/`BLOCKED`, the reply's last non-empty line) per `_shared/subagent-output-contract.md`'s Implementer Status Protocol — reuse that file's canonical wording verbatim rather than inventing new phrasing. **Tree-immutability rule for discrimination checks (#2740).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` to instruct every task-reviewer and re-review dispatch it composes that it must never mutate the shared worktree in place — a discrimination check that needs a reverted or edited file (e.g. proving a new test fails against the pre-fix code) runs in a scratch `git worktree add`, never via `git checkout --` or an in-place edit-then-restore in this shared worktree, since a concurrent implementer's own in-flight edit in the same tree would otherwise be silently lost. **Downstream re-proof after an inserted guard (#3988).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` to instruct every re-review dispatch it composes — the scoped re-review of its final review's fix wave included — that when a fix under review inserts a precondition guard ahead of an existing check, it names each check downstream of that guard and shows that check's test going red with the check itself mutated, not only the new guard, in the scratch worktree the rule above requires; a finding whose downstream test stays green is not ADDRESSED. **Review findings go through the deferral gate (#3004).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` that every Minor (or higher) finding from a per-task reviewer or the whole-branch review is either fixed in this build, or carried to the ledger only after passing `_shared/deferral-gate.md`'s fix-now check with exactly one `Defer-reason:` from that file's vocabulary, written inline in the row's Resolution text. Severity alone ("minor", "fine to defer") is never a reason. **Deferral rulings go through the same gate (#3880).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` that a `Ruling:` whose decision defers work — leaves a finding or a required change unfixed in this build, whether routed to a follow-up record, left as pre-existing, or ruled out of scope — runs `_shared/deferral-gate.md`'s fix-now criteria when it is written, checked against this spec's `## Acceptance Criteria` as literal text from the materialized spec at `{run-dir}/work/{n}-spec.md`. A deferred item an acceptance criterion's literal text covers, or one that meets every fix-now criterion, is not ruled — it is fixed in this build, so it never reaches the Review Console, at the destination its ruling site has: a pre-flight ruling folds it into the affected task's implementer brief; a ruling inside a task's fix loop sends it to that loop's next round; a breaker ruling (after round 5) or a residual left after the final fix wave's scoped re-review gets one targeted fix dispatch plus one scoped re-review, which `/build` authorizes here as an override of SDD's round cap and its single fix wave, for this case only. A fix that scoped re-review does not confirm is staged as a deferral with no reason (`Defers: yes`, no `Defer-reason:`), so the console holds it for a human. A deferral that fails the gate is written with exactly one `Defer-reason: {value}` from that file's vocabulary appended to its `Ruling:` line; that file's bad reasons (pre-existing in a touched file, out of scope, minor) never fail the gate. **Project contract beats spec-mandated literal text (#3557).** In the same invocation instruction, also direct `/superpowers:subagent-driven-development` that spec-mandated literal text — a quoted `decisions.md` line, a status word, an exact message — never overrides a project contract (`_shared/*.md`): when the two conflict, every ruling (pre-flight, fix-loop, or final-review) conforms to the contract and is ledgered as `Ruling: contract-beats-spec — {contract file} over the spec's "{quoted text}" — {cost if wrong}`. The carry-forward below copies that line to the ledger like any other `Ruling:` line, but stages it as an update-the-spec deviation, `build-deviation-{N}` (classification `Update the spec`), through the `build-deviation-{N}` line of the carry-forward commands at the end of this file, in place of `sdd-ruling-{N}` — every `sdd-ruling` name in that procedure (the `--id`, and so the staged path every log line names, and the `Kind:` header) becomes `build-deviation`, and the Item and the staged file's dispositions read apply / decline rather than ratify / reverse — so it reaches the Review Console once, even when Common Step 4.5 is skipped. The spec's text is never kept on the grounds that the spec spelled it out. **Carry forward surviving SDD ledger residue before Finish:** in the same invocation instruction, also direct `/superpowers:subagent-driven-development` that, at its own Finish step, before deleting the plan's workspace (`rm -rf <workspace>`), it must copy every remaining `<workspace>/progress.md` line matching `minor (deferred):`, `parked —`, or `Ruling:` into this build's own open items ledger (`/claude-tweaks:ledger`'s Add Item operation) — phase `build`, status `deferred` for a `minor (deferred):` line, `observation` for a `parked —` line, or `open` for a `Ruling:` line — a line matching more than one marker is copied once, under its first match in that order — using the line's own one-liner (the text following the marker) as the ledger Item description. Escape every `|` in a carried one-liner as `\|` (`_shared/ledger-format.md`'s Format section) — a `Ruling:` line routinely quotes a regex alternation or a table fragment — except a ruling's Item, which the carry-forward call below escapes itself, so pass it unescaped. A `minor (deferred):` line carries its `Defer-reason: {value}` from the moment SDD's controller writes it (the review-finding rule above), so the final whole-branch review triages each minor with its reason attached, and the carried row's Resolution text repeats it; a minor with no valid reason is not deferred — it goes to the final review's fix wave (on the single-task fast-lane skip, the last task review's fix loop). A line whose first marker match is `Ruling:` is load-bearing — every pre-flight, mid-run, breaker, and residual final-review ruling — because SDD writes the bare form only where it decided in lieu of a human, and the residual final-review shape has no pinned prefix to sniff; a `parked —` line's first match is `parked —`, so the match order already separates the two classes. For each load-bearing ruling, write the staged file's text to a temp file ending in `.md` (the staged extension comes from the source): a header block `Title:` (the one-liner, truncated to the console's row width) / `Kind: sdd-ruling` / `Ruling:` (the `progress.md` line verbatim) / `Defers:` (`yes` when the ruling defers work, per the deferral-ruling rule above, else `no` — always written; a `build-deviation-*` file carries it too, and the console ignores it there) / `Defer-reason:` (on a `Defers: yes` ruling only, the one value its line carries, written bare with no backticks — omitted when it carries none, which leaves the item for a human at the console) / `Staged-at:` (short HEAD sha), a blank line, then the ruling text, the task number when the line carries one, and the two dispositions (ratify / reverse). Then carry it forward with one `stage-item.js --ledger` call — the `sdd-ruling-{N}` line of the carry-forward commands at the end of this file (`{N}` a per-invocation counter from 1; `--allocate` is required with `--ledger`). That call is the whole procedure, and the row it writes is the one `open` row the mapping above copies for a `Ruling:` line — never a second row: it stages the file with its `Ledger:` header filled, appends that row, and logs `STAGED`, so no row ever names a file that was not written. Branch on its exit code: 0 is done; exit 3 with stderr starting `stage-item.js: ledger carry-forward degraded —` is a degraded path whose trace is already in `decisions.md` — never retry the call or log it again, unless a following `stage-item.js: warning: could not log SKIP entry` line says that trace itself failed: then write the degraded line's text once as a `SKIP` via `log-decision.js`; any other exit 3 is a wrong run dir (missing, or a worktree shadow per `_shared/pipeline-run-dir.md`'s Anchoring section) that wrote and logged nothing — re-resolve `$PIPELINE_RUN_DIR` and re-run; exit 2 is a malformed invocation (a missing `--item`, `--label`, or `--allocate`, a rejected `--ledger` — not found, wrong name, or outside the run directory and worktree — or an unreadable `--file`) to fix and re-run. Pass `--item` single-quoted with any `'` in the one-liner written as `'\''` — never double-quoted: a ruling routinely carries backticks and `$`, which a double-quoted shell argument executes as command substitution, and a stray `"` truncates the entry. The Review Console's Pending review section resolves it — `apply` there means ratify (`wrap-up/review-console-appendix.md`'s `sdd-ruling-*` bullet). **No run directory** (standalone `/claude-tweaks:build`, no `$PIPELINE_RUN_DIR`): no console will read `staged/`, so append the ledger row with status `open` and the same Item text minus the staged path, stage nothing, and list each ruling in the Step 7 handoff's `### SDD rulings` section (`build/handoff-template.md`). The Item reads `SDD ruling — {one-liner}: ratify or reverse at the Review Console`, with no staged path, and Add Item's De-duplication on Append never skips a ruling row: two rulings sharing the template stem are distinct decisions, so every ruling gets its own row and item number; a later standalone `/claude-tweaks:wrap-up`'s resolve gate drills it per item with its existing vocabulary — `Accept` = ratify, `Keep`/`Defer` = reverse as a follow-up, `Fix anyway` = reverse now — and Phase 1's fix-now criteria apply as written (a ruling's text states a decision, not a defect, so it does not qualify on its own). The SDD workspace (including `progress.md`) is deleted immediately after Finish's own "Rulings I made" collection, and claude-tweaks' `/claude-tweaks:wrap-up` reads only the run ledger, never the deleted SDD workspace — copying first is what keeps a deferred-minor or parked finding from being lost at that seam. SDD 6.3.0+ ledgers its pre-flight, fix-loop breaker and final-review decisions as `Ruling:` lines instead of stopping for the human, and `/build` suppresses `/superpowers:finishing-a-development-branch` — the channel SDD names for residual load-bearing findings — so a ruling not copied here reaches no durable record. **Persist SDD's final whole-branch review before Finish (#3386):** in the same invocation instruction, also direct `/superpowers:subagent-driven-development` that, when its final whole-branch review was dispatched, at its own Finish step, before deleting the plan's workspace, it must resolve a session-scoped scratch path with `node "${CLAUDE_PLUGIN_ROOT}/bin/session-tmp-resolve.js" SDD_FINAL_REVIEW=sdd-final-review-{run-id}.md` (`{run-id}` is `basename "$PIPELINE_RUN_DIR"`; no `eval` — it prints `SDD_FINAL_REVIEW="<path>"`), write the review to that printed literal path with the Write tool, and persist it with `node "${CLAUDE_PLUGIN_ROOT}/bin/write-run-artifact.js" --run "$PIPELINE_RUN_DIR" --name sdd-final-review.md --file "{review-path}"`, where `{review-path}` is that same printed literal path substituted in (a shell variable set in an earlier Bash call does not survive into a later one) — never an Edit/Write straight to the run directory, which a worktree-isolated session's harness refuses (`_shared/pipeline-run-dir.md`'s tool-level pinning note); the writer lands it at `$PIPELINE_RUN_DIR/sdd-final-review.md`. The review contains: the final reviewer's findings verbatim with their severities; the reviewed commit SHA (HEAD when the final review's package was built) and that package's base commit; the fix wave's commit range (`FIX_BASE..HEAD`, both ends written as commit SHAs), or "no fix wave"; and the scoped re-review's per-finding verdicts verbatim, or "no re-review" when there was no fix wave. It is maintainer evidence for #3381's double-review measurement — nothing blocks on its absence. A non-zero exit from the writer never blocks Finish — the SKIP line below then records the absent file. Write nothing for a standalone `/build` (no `$PIPELINE_RUN_DIR`) or when the whole-branch review was skipped (the Single-task fast-lane skip below). When SDD returns, if its final whole-branch review was dispatched, log one non-blocking line under `## /build` in `$PIPELINE_RUN_DIR/decisions.md` via `log-decision.js`: `AUTO … — SDD final review captured to sdd-final-review.md` when the file exists, or `SKIP … — SDD final review dispatched but sdd-final-review.md absent` when it does not.
