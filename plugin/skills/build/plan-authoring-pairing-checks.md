# Plan-Authoring Checks — Pairing Loops

Read from `plan-authoring-checks.md`'s **Pairing-loop checks:** pointer, only when a plan task changes a greedy or order-dependent pairing loop. Same purpose as that file: each check targets a failure that reads as correct to a task-level review comparing plan text against implemented code.

**Greedy-matcher widening check:** when a plan task widens a tolerance, threshold, or window inside a greedy or order-dependent pairing loop (each item takes the first eligible partner, and a taken partner is gone for every later item), the task's tests must include a case where a tighter match for a *later* item competes with the new, wider match for an *earlier* one, and assert that the tight pair wins. The plan then names how the code settles it: settle every tight match before any wide one (two passes), or make the tie-break prefer proximity. Tests that cover the new band in isolation read as complete to a task-level review, because every case pairs exactly as the plan said; the theft only shows when both bands compete in one input, in the order the loop walks. #2955 widened `categoriseReproduction`'s line tolerance from ±2 to a ±5 band gated on text similarity. Its tests exercised the band alone, so A=[x.js:100, x.js:104] against B=[x.js:104] let A:100 take B:104 in the wide band and left A:104, the exact match, unconfirmed. Only the whole-branch review caught it, at the cost of one Important finding, one fix dispatch (`26e856c32`, which added the two-pass order) and a scoped re-review.

**Greedy-assignment stranding check (extends the Greedy-matcher widening check):** when a plan task replaces a first-come pairing loop with best-first assignment (every candidate pair ranked by score and taken best first), or settles the widening check above with a greedy remedy such as two passes or a proximity tie-break, the task's tests must include a case where the globally best pair takes the only partner another item has, and assert that the other item still pairs. The plan then names how the code settles it: a maximum matching (augmenting paths for every item left unpaired after the greedy pass), or a sentence stating why leaving that item unpaired is acceptable. Best-first assignment removes the order dependence, so the both-orders tests the widening check asks for pass and a task-level review reads the fix as complete; but a greedy pass is still not a maximum pairing, and the stranded item only shows in an input where one item has two partners and its neighbour has one. #2907 replaced `categoriseReproduction`'s first-come loop with best-first assignment. With A1 matching B1 at 1.0 and B2 at 0.46, and A2 matching only B1 at 0.71, A1 took B1 and left A2 unconfirmed in either order: 1 confirmed / 2 unconfirmed where 2 / 0 was possible. Only the whole-branch review caught it, at the cost of one Important finding, a controller prototype, one fix dispatch (`6251b384f`, which added augmenting paths) and a scoped re-review.
