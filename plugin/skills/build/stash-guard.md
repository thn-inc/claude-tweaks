# Stash Guard — Non-Zero Compare Outcomes

Read by `dispatch.md`'s **Stash guard around every dispatch that can run git (#4559)** instruction only when a `stash-guard.js` `snapshot` or `compare` exits 3 or 2 — exit 0 needs nothing from this file.

Exit 3 means the CLI has already restored every removed entry it could with `git stash store` and, with `--run`, logged `AUTO {time} — Stash guard: {who} removed stash entr{y,ies} {sha subject …}; restored via git stash store. Reversibility: high.` under `/build` (`{who}` is `implementer for task {k}`, `{role} dispatch for task {k}` or `{role} dispatch`); an entry a concurrent guard had already put back is logged as such and not stored twice; a failed restore is logged as a `FAILED` line carrying its shell-escaped `restoreFailed[].command` (also on stderr); an `added` entry is logged and left on the stack, never popped automatically.

For an implementer or fix dispatch, a `DONE` result becomes `DONE_WITH_CONCERNS` (a `DONE_WITH_CONCERNS` stays as it is) and the stash change (shas and subjects from `removed`/`added`) is named in the next review of that work (the task reviewer or scoped re-review for a task's implementer or fix round, the fix wave's scoped re-review for a whole-branch fix), while a `NEEDS_CONTEXT` or `BLOCKED` result keeps its status — the stash change never upgrades a failed dispatch into a reviewed one — and the stash change is named in its re-dispatch instead.

For a reviewer dispatch (task reviewer, scoped re-review, final code reviewer, fix-wave re-review), its verdict is void (a reviewer that dropped, popped or stored a stash entry may have changed the tree it was judging, so its verdict is not a trustworthy read of the reviewed work) — the CLI has already restored the removed entries; run `git status --porcelain` in the worktree, and when it prints nothing, dispatch the same review again under a fresh snapshot/compare pair (role `{role}-retry`), never acting on the voided verdict; when it prints paths there is no stop either — log `AUTO {time} — Stash guard: {role} dispatch for task {k} {left the tree dirty after restore ({paths}) | changed the stash again on retry}; review dispatched once more, verdict stands. Reversibility: n/a (a detection; the controller never discards worktree changes).` (a whole-branch reviewer's is `{role} dispatch`) — the paths are git-derived text, so never a double-quoted `--text`: write the text between `Stash guard: ` and ` Reversibility:` (the step prefix and the Reversibility suffix are written for you) with the Write tool to the path `node "${CLAUDE_PLUGIN_ROOT}/bin/session-tmp-resolve.js" --value stash-guard-{id}-note.txt` prints, then run `node "${CLAUDE_PLUGIN_ROOT}/bin/log-decision.js" --run "$PIPELINE_RUN_DIR" --status AUTO --section "/build" --step "Stash guard" --text-file "{note}" --reversibility "n/a (a detection; the controller never discards worktree changes)"` (`_shared/auto-decision-log.md`'s Text from git or a user rule; a standalone `/build` with no run dir lists the line in the handoff only) — and dispatch the retry with the dirty paths named in its prompt; that retry's verdict stands. When the retry itself changes the stash again, the CLI has already restored it; log the same line's second form and list it in the handoff, and the retry's verdict stands — at most one retry per review, never a third dispatch (the bound keeps a reviewer that keeps disturbing the stash from looping the pipeline), and no stop; the reviewer's restore is logged like any other and listed in the handoff; every `restoreFailed` command and `added` entry also goes into Common Step 7's handoff (`handoff-template.md`'s Stash guard section), as does every restored entry when `logged` is false or the `/build` is standalone (the handoff is then the only record); when `logged` is false under a run dir the append failed (the CLI also prints `could not append the decisions.md entry` to stderr), so the controller also hand-logs that restore's `AUTO` line under `/build` (step `Stash guard`) with `log-decision.js --text-file` — the shas and subjects are git-derived text — as `_shared/auto-decision-log.md`'s rule for CLIs that log their own entries requires; a reviewer dispatch's own restored and added entries ride its voided-verdict line, not a second slot.

Exit 2 (an unreadable baseline, a git failure, or a failed `snapshot`) is logged with `node "${CLAUDE_PLUGIN_ROOT}/bin/log-decision.js" --run "$PIPELINE_RUN_DIR" --status SKIP --section "/build" --step "Stash guard (degraded)" --text "condition: {id} {snapshot|compare} exited 2 → fallback: stash change undetected for this dispatch" --reversibility n/a` (`_shared/auto-decision-log.md`'s Degrade-trace rule; standalone: the handoff's Skipped steps); after a failed `snapshot`, skip that dispatch's compare — it would exit 2 again on the missing baseline — so the dispatch gets one SKIP line, naming `snapshot`.

The guard adds no new stop: the data-preserving action runs automatically and its evidence lands in `decisions.md` and the Review Console.
