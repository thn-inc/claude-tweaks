# Review — Step 3 Routing (Code Review Findings)

Loaded by `/claude-tweaks:review` Step 3 after lenses 3a-3i have produced findings. Contains the full routing rules — severity-based auto routing, the interactive batch table, recommendation rules, deferral gate, and parallel-fix dispatch contract. Lazy-loaded only when findings actually exist (skip the load entirely when all lenses returned "No findings.") — the canonical per-lens dispatch template that used to force a pre-dispatch load of this file now lives in `step3-lens-dispatch.md`'s "Per-lens Calibration + Output template" section, which is where the CALIBRATION-block byte-identity with `_shared/criteria-review-quality.md` is pinned.

## Inputs

- Findings table merged from lenses 3a-3i, plus open QA ledger entries with phase `test/qa`.
- Pipeline run directory (when in auto/hybrid mode).
- `review-auto-apply-ceiling`, resolved per the Auto mode section below (resolver `--run` overlay; ceiling-conditional default when nothing is set).
- The resolved `review-effort` tier from `/claude-tweaks:review`'s Step 2.5.
- Step 3.7's tiebreak-confirmed findings (`step3-tiebreak.md`), at the severity the tiebreak returned.

**`unconfirmed` findings can originate from several sources**, and all go to the tiebreak (Step 3.7, `step3-tiebreak.md`) before this table — the caller does not distinguish them:

- No reproduction agreement (Step 3) — a lens's finding surfaced by only one of its two reproduction agents. A lens 3f vacuity finding from either source is re-confirmed only by the reviewing agent's own executed run, never by source reading.
- Low-tier single-read (Step 3, `review-effort: low` only) — the tier dispatches one agent per lens instead of a reproduction pair (`step3-lens-dispatch.md`'s "Low-tier single-read dispatch"), so every finding starts `unconfirmed` and goes to the tiebreak (`step3-tiebreak.md`).
- Vacuity claim without execution evidence (lens 3f, Step 3) — a pair-agreed `confirmed` finding that a test "cannot fail" or that cases "are vacuous", downgraded because neither agent showed an observed run or a mutation that stayed green (`step3-lens-dispatch.md`'s Reproduction dispatch section). Reading source alone never re-confirms it; only the reviewing agent running the case and recording the observed output does.
- Cross-lens debate converged negative (Step 3.5) — both judges disagreed.
- A `confirmed` finding downgraded by the Per-Candidate Refutation Pass (Step 3.5, `xhigh`/`max` only) — the finding survived reproduction (and possibly debate) but the falsification agent returned can't-tell or no usable verdict (a `refuted` reply drops it instead), so it joins `unconfirmed` for Step 3.7.
- Gap-sweep, single-source by design (Step 3.6, `xhigh`/`max` only) — a fresh-eyes finding with no reproduction partner, by design (pairing it against a second identical fresh-eyes agent would defeat its purpose).

**Effort-tier surfacing.** By default (`review-effort` at `low`/`medium`/`high`), this table includes only `confirmed` findings. `unconfirmed` (any of the sources above) and `contested` (debate inconclusive) findings reach it only through Step 3.7's `confirmed` outcome (`step3-tiebreak.md`), at which point they are ordinary `confirmed` rows; a tiebreak `console` outcome reaches the Wrap-Up Review Console as its own row, per `step3-tiebreak.md`'s `console` bullet, and its `digest` outcome goes to the materiality digest.

At **`xhigh` and above**, findings the tiebreak left can't-tell (`digest`/`console`) additionally appear inline in this table too — add them as ordinary rows with `(low-confidence)` appended to the Finding column, alongside the `confirmed` rows. They still also get staged to the Wrap-Up Console as before (surfacing inline doesn't remove the staging).

At **`max`**, `contested` findings the tiebreak left can't-tell additionally appear inline as well, on top of the can't-tell rows `xhigh` already added — so at `max` this table shows `confirmed` + can't-tell `unconfirmed` + can't-tell `contested` findings together, all three buckets at once. Add `contested` rows with `(contested — {debate verdicts})` appended to the Finding column, summarizing the side-by-side verdicts from Step 3.5's debate. They still also get staged to `staged/review-contested-{N}.md` as before.

**Refutation overflow note (required when present).** At `xhigh`/`max`, the Per-Candidate Refutation Pass (`step3-debate-and-refutation.md`, step 3) caps its fan-out at 10 candidates. When it capped, it emits a `+{N} more confirmed findings were not refuted …` line — render that line immediately above the findings table, verbatim. Those `+{N}` findings are ordinary `confirmed` rows in the table; the note exists so the reader knows they reached routing without a falsification attempt, rather than having silently passed one. Omit the note only when the pass did not cap (or did not run at all).

**Every finding from lenses 3a-3i must be explicitly resolved.** When lenses were dispatched as parallel Task agents, merge their results into a single table here: combine all findings, preserve their category labels, and de-duplicate — if two lenses flag the same issue, keep the entry with the higher severity. UX findings from lens 3h, coverage findings from lens 3g-cov, and documentation findings from lens 3i are merged into the batch table alongside code review findings with their respective categories ("UX", "Coverage", "Docs").

Unresolved QA ledger entries (status `open`, phase `test/qa`) are included in the code review findings table alongside code review findings. Use the category and severity from the ledger entry. This ensures QA failures flow through the same resolution process as code review findings — they must be explicitly fixed, deferred, or accepted before the review can pass.

## Auto mode (severity-based routing)

When a pipeline run directory exists (see the composed review-dispatch bundle's — `step3-lens-dispatch.md`'s "Composed dispatch-contract bundle" section composes it — run-dir-resolution content for the resolution order and bash snippet, or `_shared/run-dir-resolution.md` directly standalone), resolve `review-auto-apply-ceiling` — `node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-policy.js" --run "$PIPELINE_RUN_DIR" review-auto-apply-ceiling` (JSON envelope, not `--values`, because the next sentence needs `source`). When the envelope's `source` is `default` (no CLI arg, no Manifesto override, no project policy — nothing set at run or policy level), the effective default is ceiling-conditional: `medium` when the resolved `autonomy` ceiling is `unattended`, `low` otherwise — see `_shared/autonomy-ceiling.md` for the rationale; this is a skill-default shift, not a new capability, so an explicit value at any level still wins. A piped `/flow` run never reaches this `source: default` branch for this lever — the Manifesto computes the same ceiling-conditional value into `config.yml` (`flow/manifesto.md`'s Recommendation-defaults row), which resolves as `source: run-config` here, already ceiling-correct. What this branch remains for is a run directory whose `config.yml` never set the lever — e.g. a `/build`-parented review resolving a standalone-materialization run dir, which carries `decisions.md`/`staged/` but no Manifesto-written `config.yml` (`_shared/run-dir-resolution.md`); a standalone `/review` with no run directory never executes this resolution at all (`_shared/policy-schema.md`'s lever row: no standalone direct-read site exists).

Also resolve `review-auto-apply-prose-exempt` the same way — `node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-policy.js" --run "$PIPELINE_RUN_DIR" review-auto-apply-prose-exempt` (boolean, default `true`). When it resolves `true` **and** every `Target:` path in the finding's staged-patch preamble (`_shared/staged-patch.md`) matches `skills/**/*.md` or `docs/**/*.md` — prose-only files; `tests/**` was narrowed out of this set by #1059, since it is executable code in this repo and in every consumer project, and #660's own evidentiary basis never exercised it — look up this finding's row in the table below using a **bumped ceiling** — one severity tier above the resolved `review-auto-apply-ceiling` (`none`→`low`, `low`→`medium`, `medium`→`medium` — capped: the bump never reaches `high` or `critical` at any ceiling value) — instead of the plain ceiling. A finding whose fix spans both an exempt and a non-exempt `Target:` path is not eligible for the bump; it routes on the plain ceiling like any other finding. **When `review-auto-apply-prose-exempt` resolves `false`**, this whole paragraph is inert — every finding routes on the plain, unbumped `review-auto-apply-ceiling` exactly as it did before this dimension existed.

**Test-removal fixes never auto-apply.** When a finding's fix removes test cases, parametrized rows, or assertions — read from the staged-patch diff itself: whole cases or assertion lines deleted from a test file, net; a deletion paired with an addition elsewhere counts as a removal unless the two match one-to-one as the same case (same name and assertions), so a rename, move, or re-parametrization that cannot be matched resolves toward this override — route it STAGED at every `review-auto-apply-ceiling` value (`none`, `low`, `medium`), overriding both the plain ceiling and the prose-exempt bump above. Critical still routes KEPT-PROMPT. A deleted test is a deleted oracle: if the finding behind it is wrong, nothing is left that would fail to show it (#3124). When the override moved the finding from AUTO to STAGED (it changes nothing for a finding that would have staged anyway), log it by passing `--lever "review-auto-apply-ceiling={ceiling} ({source}); test-removal override — staged"` on the STAGED call to `review-routing-line.js`, rendering `[lever: review-auto-apply-ceiling=medium (run-config); test-removal override — staged]`.

Per the `/review` Step 3 Routing row in `_shared/auto-mode-contract.md`, severity routes to: low → AUTO, medium → STAGED, high → STAGED, critical → KEPT-PROMPT (rare; security/correctness hard-fails the bookend) — the `low`-ceiling column below, subject to the test-removal override above. Append every entry to `decisions.md` under the `## /review` heading.

**Ceiling-keyed routing.** The action for a given severity depends on the resolved `review-auto-apply-ceiling` — this table shows every ceiling's behavior in one place; do not read only one column and assume it generalizes:

| Severity | `none` | `low` | `medium` |
|---|---|---|---|
| **Critical** | KEPT-PROMPT | KEPT-PROMPT | KEPT-PROMPT |
| **High** | STAGED | STAGED | STAGED |
| **Medium** | STAGED | STAGED | AUTO |
| **Low** | STAGED (unless the prose-exempt bump below applies, which routes it at `low`) | AUTO | AUTO |

Critical never varies by ceiling — it always interrupts. `none` stages every non-critical finding; `low` (the intrinsic default absent an unattended-autonomy floor — see the paragraph above) additionally auto-applies Low; `medium` additionally auto-applies Medium on top of Low. The test-removal override above takes precedence over every AUTO cell in this table: a fix that removes test cases or assertions is STAGED (KEPT-PROMPT when Critical) at every ceiling.

**What each action means:**

- **AUTO** — Auto-apply the fix. Commit. The wave's re-verify runs under Fix-wave server coordination below. Log: `node "${CLAUDE_PLUGIN_ROOT}/bin/review-routing-line.js" --run "$PIPELINE_RUN_DIR" --route auto --severity {severity} --category '{category}' --at '{file:line}' --commit {hash}`.
- **STAGED** — Stage as patch in `staged/review-{n}.patch` (a finding on this row or AUTO's whose fix is a new work record, not a patch, stages per "Staging a record proposal" below instead). Surface at Review Console. Log: `node "${CLAUDE_PLUGIN_ROOT}/bin/review-routing-line.js" --run "$PIPELINE_RUN_DIR" --route staged --severity {severity} --category '{category}' --at '{file:line}' --stage-path staged/review-{n}.patch`.
- **KEPT-PROMPT** — The patch is staged as for STAGED, but the line does not name it — surface inline ALSO. Critical findings always interrupt. Log: `node "${CLAUDE_PLUGIN_ROOT}/bin/review-routing-line.js" --run "$PIPELINE_RUN_DIR" --route kept-prompt --severity critical --category '{category}' --at '{file:line}'`.

The composer writes each `## /review` entry itself; never hand-type the line or pass `Step 3 Routing:` in a `--text`. Pass `--category` and `--at` single-quoted with any `'` in the value written as `'\''` — never double-quoted: a file name such as `app/routes/posts.$postId.tsx` carries `$`, which a double-quoted shell argument expands, and the logged location would read `posts..tsx`.

**Logging a bumped auto-apply.** When the bump above is what moved a finding from Staged/Kept-prompt under the plain ceiling to Auto under the bumped ceiling, the `AUTO` log entry names the bump explicitly: pass `--lever "review-auto-apply-ceiling={ceiling} ({source}); prose-exempt bump applied"` to `review-routing-line.js`, rendering `[lever: review-auto-apply-ceiling=low (default); prose-exempt bump applied]` — distinguishing it from an ordinary ceiling-driven `AUTO` entry (no trailing clause). A finding that was already going to auto-apply under the plain ceiling (the bump wasn't load-bearing) logs the ordinary format with no bump suffix.

**Ledger first, then the patch.** For a High/Medium finding, append it to the open items ledger (status `open`, phase `review`) before composing the staged patch — the assigned item number is what the patch's `Ledger:` field below points at, so the order matters: a patch composed first would have nothing to reference.

**Staging a patch — validate first, describe the invariant.** Every `staged/review-{n}.patch` written by the rows above follows `_shared/staged-patch.md`: the file opens with a `Target:` / `Invariant:` / `Finding:` / `Staged-at:` / `Ledger:` preamble (the target file plus the one-sentence property the fix establishes — the durable intent — plus the exact ledger row this finding was just appended to) followed by the unified diff, and is validated per that file's Staging-time gate — `git apply --check` from the worktree, then its Stacked check (`bin/check-staged-stack.js`) — **before** the `STAGED` log entry is written. A failing check is handled per that gate and surfaces here, at staging time — never first at the console. Its non-clean outcomes ride on the STAGED bullet's own `review-routing-line.js` call, never a hand-typed line — append the outcome's flags to that call: a re-derive, `--rederived-onto staged/{earlier}.patch`; a conflict, `--conflict staged/{failing}.patch --conflicts-with staged/{other}.patch --stack-stderr '{first stderr line}'`, the two sides read from the CLI's `targetConflict` (one of them is this patch); a stack that could not be verified (exit 2, 3 or 4), `--stack-exit {code} --stack-stderr '{first stderr line}'`. This matters because `/simplify`, polish, and later fix waves legitimately move the target lines between now and the console; the console applies the diff when it still fits and otherwise re-derives the edit from `Invariant:` (that file's Console apply with description fallback), so a stale diff is expected, not an error.

**Staging a record proposal — a confirmed finding with no patch.** A finding the table routes AUTO or STAGED that fails `_shared/deferral-gate.md`'s fix-now criteria and carries a valid `Defer-reason:` has a new work record as its fix (the Defer bullet below), not a diff, so it stages no `.patch`. Critical keeps its KEPT-PROMPT row. Before composing, apply `_shared/materiality-floor.md`'s floor test to a low or medium finding: one that fails the floor with a `Defer-reason:` other than `tangential` goes to the digest container instead, per the next paragraph. A `high` finding never takes the digest branch: it is staged, so its composer line carries the `high-severity finding` token release Step 3 blocks on — `_shared/materiality-floor.md`'s severity override. A `tangential` finding, a `high` one, or one that clears the floor, is staged as follows. Compose the record exactly as the Defer bullet does (`specShapedBody` body, `recordPayload` labels) and write it as `Title:` / `Type:` / `Labels:` / `Defer-reason:` header lines, then a `Finding: {severity} {category} — {one line}` line, a blank line, and the body. That is the header `wrap-up/review-console.md`'s "On approval" step 7 reads. The `Finding:` line sits in the header block, above the blank line, so it stays out of the filed body, which is the text after the header's blank line (`tidy/console-backfill.md`'s File step). `stage-item.js` takes the staged file's extension from `--file` (`plugin/bin/lib/stage-item/write.js`), so write the proposal to the `.md` scratch path that `node "${CLAUDE_PLUGIN_ROOT}/bin/session-tmp-resolve.js" --value review-followup-proposal.md` prints, then pass that printed path as `{proposal}`: `node "${CLAUDE_PLUGIN_ROOT}/bin/stage-item.js" --run "$PIPELINE_RUN_DIR" --id review-followup-1 --file {proposal} --allocate`. `--allocate` moves the id to the next free `review-followup-{n}` slot when `staged/review-followup-1.md` already exists, so take `{n}` from the path its first stdout line prints; a literal `{n}` passed to `--id` exits 2. Never `review-{n}.md`: `stage-item.js` refuses that id (`unmapped-prefix`). A non-zero `stage-item.js` exit stages nothing: write no composer line, and leave the finding's open-items ledger row `open`, its Resolution naming the exit code and stderr, so wrap-up's ledger resolve drills it. Log it, once the file exists: `node "${CLAUDE_PLUGIN_ROOT}/bin/review-routing-line.js" --run "$PIPELINE_RUN_DIR" --route staged --severity {severity} --category '{category}' --at '{file:line}' --stage-path staged/review-followup-{n}.md`. The finding's open-items ledger row is written `deferred`, its Resolution naming `staged/review-followup-{n}.md` (`spec-{N}/staged/review-followup-{n}.md` in a multi-spec run, per `_shared/ledger-format.md`'s Resolution-text requirements), the way `_shared/ledger-format.md`'s `ledger-record-*` Defer records its staged path, so ledger resolve never re-fixes or re-defers a finding the console is already filing. This `deferred` row and the digest branch's `accepted` row below are the two exceptions to the "status `open`" wording in the "Ledger first, then the patch" paragraph above and the "status `open` for staged" sentence below. Nothing is filed here: work-record creation is never silenced in `auto` (`_shared/auto-mode-contract.md`), so the console files the record on approval.

**Below the materiality floor — the digest instead.** A low or medium finding the floor test above routes here goes to the digest container after the Dedup check (`isMaterialityDuplicate`), and skips the compose, stage and composer-log steps above. It is logged with that contract's `AUTO … materiality-floor:` audit line when a run directory resolves; the line's `{item}` names the finding as `{category} at {file:line}`, never its text, and goes through `log-decision.js --text-file` (`_shared/auto-decision-log.md`), so no release-gate token or shell metacharacter quoted in a finding reaches `## /review`. Its open-items ledger row is written `accepted`, the Resolution stating it is below the materiality floor and was digested, naming the digest comment URL on `work-backend: github-issues` or the `specs/digest.md` entry on `local-files` — the entry a Dedup match folded it into, when one did, since that match appends nothing. `accepted` is terminal with a stated reason on both backends; `deferred` is for an item a staged file or a work record still carries, and a digest entry is neither (`_shared/ledger-format.md`). A digest write that fails leaves the row `open`, its Resolution naming the failure — never `accepted` with a URL no write produced. This skill's end-of-run summary states the digest comment URL and the count routed this run, per `_shared/materiality-floor.md`'s "Digest URL and count surfacing" section — never omitted on a zero-routing run. A digest entry is not a work record (`_shared/materiality-floor.md`'s "The digest issue is a container, not a work record"), so this branch is no exception to the "Nothing is filed here" sentence above.

After routing, append all findings to the ledger as usual (status `open` for staged, `fixed` for auto-applied). A finding whose text quotes a `|` is escaped per `_shared/ledger-format.md`'s Format section before its row is appended. The Review Console at `/wrap-up`'s Phase 4 surfaces staged items for batch approval, and its apply step writes each outcome back to the `Ledger:`-named row (`_shared/staged-patch.md`'s Write-back to the ledger) — the ledger entry above is not the last write for that item, just the first.

## Interactive mode (per-batch user input)

Present all findings as a single batch table with recommended actions pre-filled:

```
### Code Review Findings

| # | Finding | Severity | Category | Affected | Recommended |
|---|---------|----------|----------|----------|-------------|
| 1 | {description} | Critical | Security | {files} | Fix now |
| 2 | {description} | High | Error | {files} | Fix now |
| 3 | {description} | Medium | Convention | {files} | Fix now |
| 4 | {description} | Low | Perf | {files} | Fix now |
```

The table renders as markdown, as above. Immediately below it, call `AskUserQuestion` with:

- `question`: `"How do you want to handle these findings?"`, `header`: `"Findings"`, `multiSelect`: `false`
- Option 1 — `label`: `"Apply all (Recommended)"`, `description`: `"Apply all recommended fixes"`
- Option 2 — `label`: `"Override specific items"`, `description`: `"Tell me which #s to change"`

**Hard gate.** Check the response you are about to send: does it already contain the `### Code Review Findings` table above as literal rendered markdown, with a row for every finding? If not, render it now, in this response, before the tool call — "Apply all" with no table above it leaves the user approving an unnamed set of fixes.

If "Override specific items" is chosen, the follow-up is ordinary free-text chat in the next message, per docs/skill-authoring.md's Multi-item decisions convention — not the tool's `Other` field.

**Recommendation rules** (interactive mode — severity-to-route mapping in `auto` mode is the table at the top of this file):

- **Critical** (security vulnerabilities, data loss risks) — always "Fix now". Non-negotiable.
- **High** (broken behavior, missing validation) — default "Fix now".
- **Medium** — default "Fix now". Even if effort is moderate, close the gap now.
- **Low** — default "Fix now". Most low-severity findings are trivial to fix.
- **"Don't fix"** — only for false positives or intentional patterns. If the finding is a genuine improvement, it must be fixed or routed — never silently dismissed.

**When "Fix now" isn't possible**, route to the right destination:

- **Defer** (new work record — born-ready, or `parked` on a concrete wake condition) — the fix is understood but it's bigger and not relevant to the current work. Compose the body via `specShapedBody` (finding + evidence → Current State, citing the origin spec as `refs #{n}`; the fix → Deliverables; the review lens's own check → Acceptance Criteria; `filedBy: 'review'`; `provenance: { origin: 'spec #{n} review ({lens})', deferReason }` — the reason chosen by the mapping below; footer `_Filed by \`review\` via specShapedBody._`), then create it directly via the unified record contract (`_shared/work-record.md`) — `gh issue create` (`work-backend: github-issues`) or `local-store.js`'s `writeRecord` (`work-backend: local-files`) — with `recordPayload({ …, risk, size, ready: true })` scored per the Scoring axis (born-ready per `_shared/work-record.md`'s `/review` row), or `header: 'Trigger: {wake condition}'` + `parked: true` instead of `ready` when the reason is `blocked-dependency`/`blocked-external` with a concrete wake condition. A finding whose verification cannot be honestly stated (its own text names an open choice or missing evidence) uses the composer's `openQuestion` variant and files `needs:definition` (a label with no `recordPayload` parameter — append it at the create call) with no `ready` and no scoring, per `_shared/work-record.md`'s `/review` row; a finding naming an open product choice routes to Capture instead (`tangential` captures). Before composing, apply `_shared/materiality-floor.md`'s floor test to this item (judged the same way this bullet already scores `risk`/`size` for `recordPayload`, plus the `priority` axis no filing path here stamps — the routing skill judges that one too, per that contract): when it fails to clear the materiality floor, and `Defer-reason` is not `tangential` (which always clears the materiality floor per that contract's Overrides section), the batch table's Recommended column shows `"Digest — below floor"` instead of `"Defer — {reason}"` — the digest entry is written only once the human approves that row (via "Apply all" or an override), never silently substituted underneath an unchanged Defer label; once approved, check `isMaterialityDuplicate` (`_shared/materiality-floor.md`'s Dedup section) against the open digest container before appending — a re-encountered finding folds into its existing entry rather than adding a second one — then skip the rest of this bullet's `specShapedBody`/`recordPayload`/`gh issue create` steps for that item. This skill's own end-of-run summary states the digest comment URL and the count routed this run, per `_shared/materiality-floor.md`'s "Digest URL and count surfacing" section — never left implicit in the digest issue alone, and never omitted on a zero-routing run.
- **Capture** — the finding is complex or uncertain and needs brainstorming/exploration before it can be acted on. This enters the full capture → `/superpowers:brainstorming` pipeline. Invoke `/claude-tweaks:capture` with the shaped body and `--defer-reason={value} --source review` (capture's Shaped-body branch — `capture/SKILL.md`), plus `--needs-definition` when the finding names an open choice. This branch's items usually carry `Defer-reason: tangential` (per the Defer bullet above), which `_shared/materiality-floor.md`'s override always clears — a Capture-routed finding with reason `tangential` never routes to the digest container; it files via `/claude-tweaks:capture` as above. A Capture-routed finding carrying a different `Defer-reason:` (the rarer case) is still subject to the same materiality-floor test as the Defer bullet above, applied before invoking capture. Cited here so `_shared/materiality-floor.md`'s Overrides section is confirmed to cover every filing branch in this file, not only the common case — not to be confused with `_shared/deferral-gate.md`'s own "Floor mapping" section, a different, autonomy-ceiling floor with the opposite verdict for `tangential`.

**Deferral gate:** `_shared/deferral-gate.md` is the gate — run its fix-now criteria before any Defer or Capture, and never skip a fix for one of its bad reasons (its list includes "minor / not load-bearing" — severity floors decide what blocks, not what gets fixed). A finding that fails fix-now carries exactly one `Defer-reason:` from that file's vocabulary, chosen by this mapping (one line of justification recorded in `decisions.md` alongside the routing decision):

- a defect in a file the diff does not touch → `pre-existing-outside-diff`
- a fix needing a product/design call → `needs-human-decision`
- a fix that expands scope past the fix-now criteria → `genuinely-larger`
- a fix waiting on unbuilt functionality → `blocked-dependency`
- a fix waiting on external state → `blocked-external`
- a new capability the finding suggests → `tangential` (Capture, not Defer)

A finding that fails fix-now with **no** valid reason stays `open` — in an interactive review it goes to the human drill; in `auto` it becomes an `open` ledger item for wrap-up's Phase 2 drill — it is never filed as a record; it resolves at the human drill (interactive) or wrap-up's ledger resolve gate (auto).

If any findings are "Fix now", make the changes, re-verify per `_shared/deferral-gate.md`'s Re-verification rule (`/claude-tweaks:test --source review`), and verify fixes didn't introduce new findings. In a pipeline run, wrap the wave in Fix-wave server coordination below — stop the run's ephemeral server before the re-verify; the next step that drives a browser starts a fresh one.

## Fix-wave server coordination (pipeline runs)

Every fix wave in this review — AUTO-applied fixes, interactive "Fix now", the parallel fix dispatch below, Step 4's reflect "Change now" re-run, Step 5's simplify re-verification, and Step 6.7's late-findings routing (all in `code-mode-steps.md`) — re-verifies with `/claude-tweaks:test --source review`, and a suite that builds the app (`next build` rewriting `.next`, say) swaps the build out from under the run's ephemeral server (`_shared/dev-url-detection.md`'s Ephemeral server start). Every later browser step is then served a replaced build, and nothing fails loudly (#3021). So, once per wave, never per finding:

1. **Stop before the wave builds.** Before each point in this review that may change code and re-verify — Step 3 Routing's fix wave (before its first fix-agent dispatch, or before its re-verify when the main thread applies the fixes itself), Step 4 (before invoking `/claude-tweaks:reflect`, whose "Change now" fixes re-verify inside it), Step 5 (before invoking `/claude-tweaks:simplify`, which runs verification internally after changes), and Step 6.7's routing wave — read the server record (`_shared/dev-url-detection.md`'s Ephemeral server start item 4: `$MULTISPEC_PARENT_DIR/ephemeral-server.txt` in a multi-spec run, else `{run-dir}/ephemeral-server.txt`). Re-read the file at every point: a server stopped earlier stays stopped (no file, nothing to do), but one a browser step started in between — Step 6's visual review in full mode — is stopped again before Step 6.7's wave. With no run directory or no server record, skip this whole section — a standalone review behaves exactly as before. When the file's worktree root — everything between the port (the second field) and the trailing `detached:` token, since the path may contain spaces — is not this checkout's `git rev-parse --show-toplevel`, leave it alone: that server belongs to another worktree. A record that cannot be parsed — fewer than four fields, a pid or port that is not a positive integer, or no trailing `detached:` token — is unprovable: log `SKIP` via `log-decision.js` naming that condition, leave the file and every process alone, and proceed with the wave. Otherwise stop it with `wrap-up/cleanup-procedures-execution.md` Section D's steps 2-4 — the platform-aware kill wrap-up already uses, an already-gone pid counted as stopped, the port confirmed free, the file deleted. Never hand-roll a kill. When Section D's step 3 reports a real stop failure (anything other than an already-gone pid, e.g. access denied), or its step 4 finds the port still held after the kill (a leader-only stop under `detached:no`), the server is still live: keep the record, so wrap-up's Section D still sees it, and the wave's build may replace what it serves. Log `SKIP` via `log-decision.js` naming that condition, per `_shared/auto-decision-log.md`'s degrade-trace rule, note in Step 7's summary that later browser results may reflect the replaced build, and proceed with the wave — a degrade, never a block.
2. **Re-verify.** Run the wave's re-verify as usual.
3. **Restart lazily, at the next browser step.** Do not start a server in this coordination. The next step that drives a browser — Step 6's visual review in full mode, Step 6.7 item 4's QA re-run, or a later phase — resolves its URL through `dev-url-detection.md`, which reuses a server a re-verify's own QA already started on the post-build app and otherwise, finding no server answering for this checkout, starts one through its Ephemeral server start (Step 3's "no usable server + dev command known" row, auto mode), detached per its Ownership rule. Its item 4 rewrites the server record with the new pid, via a plain Bash redirect into the main checkout's run dir — never a worktree-relative path, which would shadow it and leave Section D killing the old pid (`[IL-127]`) — so wrap-up's Section D stops the server current at end of run. Step 1 already deleted the stale line, so Section D never has a dead pid to kill, and when no later step drives a browser nothing is restarted.

## Parallel fix dispatch (3+ independent fixes)

> **Working Directory Discipline:** Applies to every fix-agent `Task()` dispatch. Apply the Working Directory Discipline rule from the composed review-dispatch bundle (or, standalone, `_shared/subagent-dispatch-core.md`) before any git or path-sensitive command in the agent prompt. See also `_shared/git-discipline.md`.

> **Parallel execution (conditional):** When there are 3+ "Fix now" findings across different files with no shared file dependencies, dispatch fixes as parallel agents using the `/superpowers:dispatching-parallel-agents` pattern — one agent per independent fix domain. Each agent gets: specific file scope, finding details, constraint to not modify other files, and the FIX AGENT line below. Returns summary of changes. After all agents complete, check for conflicts between agent changes, then re-run `/claude-tweaks:test --source review` — the run's ephemeral server, if one was running for this checkout, already stopped before the dispatch, per Fix-wave server coordination above. When fixes overlap files or there are fewer than 3 findings, fix sequentially in the main thread.
>
> **Model profile:** [Use: Standard] — fix agents make targeted code edits constrained to their assigned files. Upgrade to Capable only when the fix requires architectural redesign rather than localized correction. Resolve via `node "${CLAUDE_PLUGIN_ROOT}/bin/resolve-profile.js" standard` (contract § Model Selection).
>
> **No-build line (required):** Inline this line verbatim into every fix-agent prompt, outside the Output template block:
>
> `FIX AGENT: do not run the project's test suites, builds, dev servers, or e2e runners — make the edits and report them; the dispatcher re-verifies.`
>
> It is the fix-path counterpart of `_shared/subagent-dispatch-core.md`'s Read-only Reviewer Discipline (#3001), kept a separate rule: it binds the dispatched fix agents, never the dispatcher's own re-verify, which is what Fix-wave server coordination wraps.
>
> **Output template (each agent must follow exactly):**
>
> ```markdown
> OUTPUT FORMAT (required):
> Per change made:
> - {path}:{line} — {change description}
> If no changes made: return literal text 'No changes.'
> Status line (required): the last non-empty line of your reply must read exactly `STATUS: DONE` (or DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED).
> ```
>
> **Post-dispatch diff audit (mandatory).** After all fix agents return and before re-running `/claude-tweaks:test --source review`, run `git diff --stat` (plus `git status --porcelain` for untracked additions) and verify every file each agent claimed to change actually appears with real hunks. A detailed, specific fix narrative with zero corresponding diff is an observed failure mode — never accept an agent's bullets as evidence of the edit. An agent whose claimed changes are absent from the diff is treated as failed: its findings stay `open`, and the fix is re-applied inline in the main thread (never by re-trusting a second narrative). Only after the audit passes does the dispatcher inspect the bullets for cross-file conflicts and re-run `/claude-tweaks:test --source review`. This audit's sibling runs earlier in the same review — the post-fan-out untracked-file sweep (`step3-lens-dispatch.md`) checks the same class of leftover after the lens/refutation/gap-sweep fan-out, before this routing step ever loads; both apply one rule (report untracked leftovers, never silently trust them) at the two points in the pipeline where dispatched agents write files.

**Write all findings to the open items ledger** (see `/claude-tweaks:ledger`). Use the appropriate `review/*` phase. Status: `open` for "Fix now" items, `deferred` for Defer routes, `accepted` for "Don't fix" items (with reason). After fixing, update status to `fixed`.

## Routing bias

Fix it now — always the recommended default, regardless of severity. Defer when the fix is understood but bigger and not relevant now. Capture when the finding needs exploration before it can be acted on. The goal is to close gaps early, not accumulate a backlog.

## Wait-for-resolution + auto-advance

**Wait for resolution** (interactive mode only). When code review findings exist, present the findings table and wait for the user's response before proceeding to Step 4. In `auto` mode, findings are auto-routed per the severity table above and the skill proceeds without waiting.

**Auto-advance on zero findings:** When there are zero code review findings AND zero unresolved QA ledger entries (`open` items with phase `test/qa`), auto-advance to Step 4 without waiting for user input. Present "No code review findings" as a note within the Step 4 hindsight message.

**Small batch consolidation:** When total findings across Step 3 Routing and Step 4 combined are 5 or fewer items, consolidate into a single batch table with a "Type" column (`Code Review` / `Hindsight`) instead of two sequential tables. This saves one interaction. When more than 5 total, present sequentially (one per message) to keep each decision manageable.
