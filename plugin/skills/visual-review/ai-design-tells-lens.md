# AI Design Tells Lens

Shared, criteria-only checklist — what to flag when applying the AI-design-tells lens during a visual review pass (#2667). No workflow, no Next Actions: this file is the checklist itself, invoked from `page-mode.md`'s Step 4 (Structured Analysis) right after `ux-heuristics-lens.md`. Source: two social-media Reels on AI-generated design's recognizable visual tells — `DcrqbqZRVvC` (transcribed list) and `DcjAVGRBmSC` (Showit, narrative form, folded in). Like `ux-heuristics-lens.md`, treat every row as a manual-inspection prompt, not a hard mechanical rule — several rows are code-inspectable (grep/class-name checks), the rest need judgment from the rendered screen. This is a snapshot of what currently reads as generic; the specific tells drift as AI-design defaults change, so **this list is time-bound and needs periodic refresh** — don't treat it as a permanent canon.

The fix framing from the source material: a tell is fixed by swapping the generic pattern for something specific to the actual product — real photos, real numbers, real copy — not by polishing the same pattern. A finding that recommends "make the gradient subtler" or "use a less generic emoji" has missed the point; the recommendation should name what product-specific content replaces the generic placeholder.

## When this lens applies

Gate invocation on `Surface: web/mobile/desktop` (the same `design-wrapper/frontend-detection.md` signal `ux-heuristics-lens.md` gates on) — a backend/infra record with no rendered UI never pays for this pass. Within visual review, it runs as part of page mode's Step 4 structured analysis, immediately after the UX Heuristics checklist. The code-inspectable rows can be checked against source (class names, imports, font declarations); the judgment rows need a rendered screenshot of the current screen, via the same `browser-review.md` session conventions the UX lens uses.

## The checklist

| Tell | Why it reads as generic | Swap it for | Detection |
|---|---|---|---|
| Purple-to-blue gradients, gradient hero text, and gradient blobs | The single most recognizable AI-design default — nearly every generated landing page reaches for the same `purple → blue` sweep on a hero, a CTA, or a background blob | A solid or duotone treatment drawn from the product's actual brand palette, or a photo/illustration specific to what the product does | Code-inspectable — grep CSS/Tailwind for `bg-gradient-to-*`/`linear-gradient(` spans naming purple/violet/indigo through blue/cyan |
| Emoji in headings | A heading like "🚀 Ship Faster" substitutes a generic icon-feeling for an actual visual identity | A custom icon, illustration, or no decoration at all — let the copy carry the meaning | Code-inspectable — grep heading elements/components for emoji code points |
| Glassmorphism cards | Frosted-glass translucent cards over a blurred background were a 2021 trend now read as a generated-site default, applied with no relationship to the product's own visual language | A flat or bordered card style that matches the rest of the product's actual design system | Code-inspectable — grep for `backdrop-blur`/`backdrop-filter` paired with a semi-transparent background on a card component |
| Low-contrast dark mode | Dark-on-dark text and muted-gray-on-near-black surfaces read as an unconsidered default rather than a deliberate dark theme | A dark theme with deliberately chosen, tested contrast ratios against the product's actual content | Judgment — assess contrast from the live rendered screen; a WCAG contrast-ratio check can support the call but the "does this look considered" judgment itself needs the render |
| Three-icon-boxes-in-a-row layout and badge-above-headline | The default "Features" section shape (three equal-weight icon+text boxes) and the small eyebrow badge sitting above every hero headline are both load-bearing AI-template defaults, not a content-driven layout choice | A layout shaped by how many features the product actually has and how they're best grouped, not padded or trimmed to fit three boxes | Judgment — layout-pattern recognition from the rendered page |
| Lucide icons everywhere, untouched shadcn components, and circle icon containers | Shipping a component library's default icon set and unmodified components with no visual customization signals nobody made a design decision | Icons and components customized (color, weight, shape) to the product's own system, or a different icon set chosen deliberately | Code-inspectable — grep imports for `lucide-react`/`@/components/ui` with no overriding className, and circular icon-container wrappers with default styling |
| Scroll-triggered fade-ins, cursor-following elements, and hover-fade buttons | These motion defaults ship on nearly every AI-generated marketing site regardless of whether the content benefits from them | Motion used only where it clarifies something (a state change, a relationship) — or no motion at all on a page that doesn't need it | Code-inspectable — grep for `IntersectionObserver`-driven fade classes, `mousemove`-bound cursor-follow effects, and opacity-only hover transitions on buttons |
| Inconsistent spacing | Padding/margin values that don't derive from one scale, varying between visually-identical sections | Spacing drawn from one consistent scale across the page | Judgment — compare spacing across sections on the rendered screen |
| Em-dashes everywhere and generic buzzwords | Prose stitched from "seamless", "effortless", "revolutionize", "unlock your potential", and em-dash-joined clauses reads as generated copy rather than a product's own voice | Copy written in the product's actual voice, naming specifics (what it does, for whom) instead of generic superlatives | Code-inspectable — grep rendered text content for em-dash density and a curated buzzword list (e.g. "seamless", "effortless", "elevate", "unlock", "game-changer", "revolutionize") |
| Serif-italic accent words and the Space Grotesque + Instrument Serif font pairing | This specific pairing (a geometric sans for body/headings, an italic serif for one accent word per headline) has become its own recognizable AI-design signature | A type system chosen for the product's own brand, or at minimum a different pairing not drawn from the same default | Code-inspectable — grep `font-family`/`next/font` declarations and CSS for `Space Grotesque`/`Instrument Serif`, or an italic-serif span styled as a headline accent |
| Grain texture overlays | A subtle noise/grain overlay on hero sections or full-bleed backgrounds, applied with no relationship to the product's own aesthetic, reads as a stock finishing touch | A texture or background treatment chosen because it fits the product, or no overlay at all | Code-inspectable — grep for a noise/grain image asset or an SVG `feTurbulence` filter applied as a background overlay |
| Bento grids | An asymmetric grid of unequal-sized boxes, used as a default "showcase" layout regardless of whether the content actually has a natural hierarchy that shape expresses | A layout shaped by the actual content's hierarchy — equal-weight grid, list, or a bento grid only when the content genuinely has emphasis to express | Judgment — layout-pattern recognition from the rendered page |
| Fake testimonials | Generic stock-photo avatars paired with vague, interchangeable quotes ("This changed how we work!") that could apply to any product | Real testimonials with real names/photos (with permission), or no testimonials section until real ones exist | Judgment — assess whether testimonial content/avatars look genuine or template-filled from the rendered screen |

## Reporting a finding

When a screen matches a tell, name the specific tell (not a vague "this looks AI-generated") and cite the concrete evidence — an `eN` ref plus description (per `browser-review.md`'s Element-reference convention) or a screenshot path — the same citation convention `ux-heuristics-lens.md` uses. Findings from this lens fold into the same Step 6 Report & Route table as every other visual-review lens, with `Source = AI Design Tells`. Every finding's recommendation must name a product-specific swap (what replaces the generic pattern), never just "avoid this" or "make it less obvious" — a recommendation that only tones down the same generic pattern has missed the fix framing above.

## What NOT to flag

- A pattern that matches a tell's surface description but is demonstrably intentional and product-specific — e.g. a gradient drawn from the product's own documented brand palette, not the generic purple-to-blue default.
- A judgment-row tell (low-contrast dark mode, inconsistent spacing, three-icon-boxes layout, bento grids, fake testimonials) that doesn't actually read as generic on this specific screen — silence on an inapplicable row is expected, not a missed check.
- A genuine, deliberate design decision already documented in `DESIGN.md` — this lens surfaces observations for judgment, it does not override a documented decision.
