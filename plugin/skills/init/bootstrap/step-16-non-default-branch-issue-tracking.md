# Step 16 — Non-default-branch issue tracking (companion workflow)

*Optional Enhancement step — see `../SKILL.md`'s `## Input` for when this group is offered or filtered, and `../bootstrap-steps.md` for its ordering and renumbering conventions.*

Offer only when the project has a GitHub-flavored remote — same two-tier check Step 9
documents. Check whether
`.github/workflows/track-issue-fixes.yml` already exists. If it does, classify it (below)
instead of offering the setup question.

**Existing file — classify, then act.** Run from the project root:

```bash
node -e "const m=require('${CLAUDE_PLUGIN_ROOT}/bin/lib/issue-branch-tracking.js');console.log(m.classifyExistingWorkflow(require('fs').readFileSync('.github/workflows/track-issue-fixes.yml','utf8')))"
```

GitHub's native `Fixes #N`/`Closes #N` keyword parsing only fires when the referencing
commit lands on the repository's default branch. Projects whose workflow lands fixes on
an integration branch first (`dev`, `staging`, a feature branch) get no signal at all —
the issue just sits open with no record that it's already fixed somewhere.

**Call `AskUserQuestion`:**

- `question`: `"claude-tweaks can wire up automatic issue tracking for non-default branches. GitHub only auto-closes Fixes #N/Closes #N on the default branch — fixes landed elsewhere lose that signal entirely and the issue looks untouched. Set up the tracking workflow?"`, `header`: `"Issue tracking"`, `multiSelect`: `false`
- Option 1 — `label`: `"Yes — write the tracking workflow (Recommended)"`, `description`: `"Writes .github/workflows/track-issue-fixes.yml."`
- Option 2 — `label`: `"Skip"`, `description`: `"Handle issue tracking manually."`

**For option 1 (and for regeneration above) — write the workflow file.** The full YAML is generated by
`bin/lib/issue-branch-tracking.js`'s `generateWorkflowYaml()` — do not hand-author the
file; the generator is the single source of truth (its embedded regex pattern is also
unit-tested). Run — node writes the file only after generation succeeds, so a failure
never leaves an existing workflow truncated:

```bash
mkdir -p .github/workflows
node -e "const y=require('${CLAUDE_PLUGIN_ROOT}/bin/lib/issue-branch-tracking.js').generateWorkflowYaml();require('fs').writeFileSync('.github/workflows/track-issue-fixes.yml',y+'\n')"
```

The generated workflow ships two jobs, both triggered on `push` (excluding the plugin's
`claims-registry` and `health-state` bookkeeping branches). Each job's job-level `if`
also requires the pushed commit messages to contain `#` and a closing-keyword stem, so a
push that references no issue starts no runner:

- **`label-fix-branch`** (runs on any branch that is NOT the repo's default branch) —
  scans the pushed commits for GitHub's own closing keywords
  (`close(s|d)`/`fix(es|ed)`/`resolve(s|d)` + `#N`), and for each matched issue applies
  a `fix-on-<branch>` label (auto-created on first use) plus a comment linking the
  commit SHA.
- **`cleanup-fix-labels`** (runs only on pushes to the default branch) — same scan;
  strips every `fix-on-*` label from matched issues, since GitHub's native parser is
  closing them on this same push.

No `gh issue close` call anywhere in the workflow — it only labels and comments, and the
default-branch merge closes the records. A claude-tweaks `pr-first` run is the one case that
closes sooner: when its PR merges into a non-default base, `pr-first-merge-post-merge.md` Step 4.0
closes the PR's `Fixes` records itself (see "Close-via-merge" in `_shared/issue-claims.md`).

**Failure handling:** if the classifier command fails, or writing the file fails (e.g.
permissions), surface the failure, write nothing further, and continue `/init` — never
abort the rest of bootstrap on this step.

**Re-run behavior:** an existing workflow file is classified, never blindly skipped:
`current` is silent, `prior-generated` is regenerated without a prompt, `modified`
asks first and defaults to keeping the file. With no file present, declining the offer is
fine — it's offered again on the next `/init` run.
