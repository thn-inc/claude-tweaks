# Sweep code regions — skill-prose-conformance-tests

Lazy-loaded from `SKILL.md` (this skill's directory). Read this file when a test sweeps only a skill file's code regions — fences and inline spans — rather than the whole file, because prose and command text may legitimately say different things.

## Sweep code regions, not the whole file, when prose may say what commands may not

Some conventions bind only the *commands* a skill file carries. `plugin/skills/flow/multispec-freshness.md` must parameterize its git commands as `origin/{integration-branch}`, while a paragraph explaining the ladder may legitimately name `origin/main` in passing. `tests/multispec-boundary-freshness.test.js` extracts the code regions first and sweeps only those — fences and inline spans as two passes, not one regex:

```js
function codeRegions(text) {
  const fences = text.match(/```[\s\S]*?```/g) ?? [];
  const stripped = text.replace(/```[\s\S]*?```/g, '');
  const spans = stripped.match(/`[^`\n]+`/g) ?? [];
  return [...fences, ...spans];
}
```

Stripping the fences before scanning for spans is the load-bearing half, and it fails in a way that hides offenders rather than adding noise: on `` ``` tail `origin/x` end ``, the unstripped span regex pairs the fence's closing backtick with the real span's opening one and yields `` ` tail ` `` — the `origin/x` span is never scanned at all. Contrast `tests/frontier-unattended-literal.test.js`, which sweeps whole files with an explicit allowlist: reach for that shape when the literal is banned everywhere, and for region-scoping only when prose and command text genuinely differ in what they may say.

**An empty extraction passes the sweep for free.** `assert.deepStrictEqual(offenders, [], …)` over a derived haystack is green when the extractor returns nothing — a fence style the regex misses (`~~~`, an indented block), a renamed target read as an empty string, or a typo. This is `SKILL.md`'s `doesNotMatch` blind spot (under "Prove go-red with a frozen pre-change excerpt") one level up: there the *control* lacked the tokens, here the *haystack* does. It is live, not hypothetical: `multispec-freshness.md` today has zero fenced blocks and dozens of inline spans (count live: `grep -oE '`[^`\n]+`' plugin/skills/flow/multispec-freshness.md | wc -l`), so the fence half of that helper is currently pinning nothing and a bug in it would not show. Assert the region count is non-empty, and run the same filter over a frozen string carrying the banned literal, so green proves the sweep can still see one.

**Take the sweep root as a parameter, so the go-red control proves the walker as well as the matcher.** `sweepShellEvalFences(root)` in `tests/merge-subject-composer-conformance.test.js` (#3537) walks `root` for `*.md`, reads each file's fences line by line, and matches each block. The live test passes `plugin/skills`; the control passes a temp tree (`fs.mkdtempSync(path.join(os.tmpdir(), …))`, removed in `finally`) holding a nested directory and an indented, list-nested fence, so the identical walk, extraction and match run over a known offender. A control that feeds the matcher a string never exercises the directory walk or the fence open/close logic. A backtick-only extractor mispairs 4-backtick outer fences and unterminated fences (`plugin/skills/tidy/step-6-auto.md`, `step-6-interactive.md` and `plugin/skills/specify/spec-template.md` carry them; none holds a composer call), so revisit it the first time a banned literal could sit inside one.

**Sweep quote context when the convention is about quoting.** A region sweep cannot tell `cp "$S" {tmp-a}` from `cp "{tmp-a}" "$S"`; `tests/session-tmp-placeholder-quoting-conformance.test.js` (#3544) tracks shell state (command, double quote, single quote, `$(…)`, backtick, heredoc, comment) line by line through one fence or one inline command span and classifies each target placeholder as quoted or unquoted. Three things its review rounds taught: open every fence shape (a blockquote-prefixed `> ```bash`, an indented one and an unlabelled one were all missed by the first extractor); report an unbalanced fence that mentions a target as an offender instead of letting the tracker pass it; and key the target list on an explicit name set beside the prefix rule, since a survey keyed on `{tmp-` alone missed `{tmp}`, `{path-A}` and `{ctx-dir}`. The go-red controls are frozen pre-change excerpts run through the same `scanFence` the live sweep calls, and the live sweep asserts a floor on the quoted sites it saw.

**Pin a "never here — step N does" boundary by attribution, not by tombstones.** A section may *mention* a forbidden command only as another step's job ("the scan never deletes; Step 7 runs `git branch -d`"). Tombstoning the phrasings the old text happened to use (`Use \`git -C … branch -d`) cannot see a reworded reintroduction: #4468's review inserted a differently-worded scan-time delete and all 37 assertions stayed green. Sweep the section for every command of the forbidden shape instead, and assert each hit's preceding window names the owning step (`Step 7` within the 40 characters before it), plus a non-empty-hits floor so a renamed section cannot pass on zero matches. `tests/tidy-scan-dispatch-conformance.test.js`'s "names every mutating git command only as Step 7's" test (#4468) went red on three reworded deletes.
