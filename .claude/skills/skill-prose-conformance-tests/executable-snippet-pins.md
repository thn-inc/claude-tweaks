# Binding an executable snippet to a test

Lazy-loaded from `SKILL.md`'s "Bind an executable snippet to a test" stub. Read it when skill prose carries a shell or `node -e` snippet the reader is told to run, and you are writing the test that pins it.

When skill prose carries a shell snippet the reader is expected to execute, bind it to a `node --test` file that both pins it and runs it. `docs/skill-authoring.md`'s "Executable snippets in skill prose" names two forms and **prefers extract-and-run**: the test pulls the fence out of the doc with an anchored regex and executes exactly that string, so the doc is the only source of the executed text and the two cannot drift; the test fails loudly — *"extraction pattern is out of sync"* — when the anchor moves. Shipped instances: `tests/pipeline-run-dir-adoption-anchoring.test.js` and `tests/blast-radius-snippet.test.js`, the latter extracting `plugin/skills/assess-agent-autonomy/merge-check.md`'s Step 1 fence and running it against a fixture git repo.

**Anchor the extraction on structure, not on a sentence.** `tests/blast-radius-snippet.test.js` anchors on the prose phrase "is one CLI call", which any rewording of that paragraph breaks — and the failure then reads as a test defect rather than as the procedure changing. A heading, a fence delimiter, or a table-row prefix survives ordinary editing; this is the extraction-side statement of `SKILL.md`'s first Project Conventions bullet.

Reach for **byte-pinning** when the probe has to wrap the snippet in fixture-specific surroundings — then assert it byte-identical **and** execute it. `tests/spec-template-generator-grep.test.js` is the instance: it holds `plugin/skills/specify/spec-template.md`'s generated-file grep as a `SNIPPET` literal, asserts the structurally anchored extraction equals it byte-for-byte (`assert.strictEqual(m[1], SNIPPET, …)`), then substitutes `{basename}` into the extracted string and runs it under `spawnSync('bash', ['-c', cmd])` against the live repo. `tests/staged-patch-contract.test.js` covers the other half — it probes `git apply --check`'s real accept/reject discrimination on this machine instead of asserting that the contract's sentence about it is true.

**Run a snippet the Bash tool executes under both `bash --noprofile --norc` and `zsh -f`.** The Bash tool runs the user's shell, which is zsh on this repo's macOS host, so a snippet proven only under `bash -c` can still break there: zsh does not word-split an unquoted expansion, and #4107's `ISSUES=($CLOSING)` collapsed two records into one element under zsh only, after review had assumed bash semantics. `-f` and `--noprofile --norc` keep rc files from setting options (`SH_WORD_SPLIT`) behind the test's back. Skip the zsh case with a visible reason when zsh is not on PATH (ubuntu CI), never silently, and keep the frozen pre-change block as a go-red control asserting the shell-specific outcome. `tests/wrap-up-closing-records-array-fill.test.js` (#4107) is the reference shape.

**Lighter variant: pin only the flags, not the side effects.** When the goal is proving a documented snippet's *flags* parse cleanly against the CLI's real arg parser — not exercising the command's full side effects — tokenize the live snippet and feed the resulting argv straight through the parser directly, with no subprocess and no fixture repo. `tests/bin-lib/verify/snippet-conformance.test.js` is the instance: it extracts `verification.md`'s pinned `verify.js` invocation, tokenizes the argv after the script path, and calls `parseArgs` on it. Its go-red proof exercises the extractor itself, not just the assertion — it appends a bogus flag to the *extracted* snippet and asserts the whole extract-plus-parse pipeline throws, catching a broken tokenizer as well as a broken doc.

**Multi-fence-sequence variant: when the bug lives in state handed between calls.** Some procedures are not one snippet but several fences run at different points of one step, communicating through a file they all resolve: one fence resets it, one appends to it per unit, one reads it. Extracting each fence alone against its own fixture proves each runs, but never exercises the handoff, and the handoff is where the defect lives. #3128's cross-invocation manifest accumulation appears only when an earlier invocation's appends survive into a later invocation's read. `tests/specify-ceremony-tally-prose.test.js` (#3128) is the instance. Its `fenceAfter(label)` helper extracts three fences from `plugin/skills/specify/record-creation-subissues.md`, each anchored on its step's bold label (`**Fresh manifest for this invocation.**`, `**Accumulate this unit for the cross-reference pass below.**`, `**Ceremony tally.**`) plus the next `bash` fence. A `makeProject()` factory then runs them in sequence against one scratch project cwd, with a fixed `CLAUDE_CODE_SESSION_ID` and a private `TMPDIR`, so the session-scoped path every fence resolves is the same scratch file and never the machine's shared temp root. Prove the sequence's go-red by **omission**: rerun the same sequence minus the fence under test and assert the stale-state outcome. Its control skips the reset fence and asserts the tally counts three entries instead of one, which attributes the green case to that fence rather than to the fixture. The same shape also catches a fence that *reads* a variable an earlier fence set (#3161): each Bash tool call is its own shell, so run every fence in its **own** `spawnSync('bash', ['-c', fence])` process with that variable deleted from the inherited env — one shared shell, or a machine env that happens to carry it, hides the defect — and make the go-red control the fence minus its own re-resolution line, asserting the failure message (`/fence exited 1: [\s\S]*ENOENT/`), not just that something threw (`tests/specify-crossref-manifest-resolve.test.js`).

**Run-twice variant: when the bug lives in what one run leaves for the next.** Some fences have to behave differently on their second invocation. A resolver that mints a run directory must refuse the directory a previous run left active rather than adopt it, and running the fence once against a fresh fixture can never show that. #3898's release Step 0 guard is the instance. `tests/release-run-dir-lifecycle-conformance.test.js`'s `assertSecondRunRefusesFirst` runs the whole extracted fence twice, end to end, against one `git init` fixture with the real `hooks.js` CLIs and no close between the runs. It asserts three things: the first run printed only its minted directory, the second run's `refused:` line names that same directory, and the second run minted a different one. When the minted name has one-second resolution, wait for the wall clock to enter a new second between runs (`waitForNextSecond`), or the two mints collide by name and the test proves nothing. For the go-red, drop the disjunct that does the refusing and assert the same two-run sequence fails on the refusal line.

**A `node -e` fence that spawns a plugin CLI runs against a stub CLI, with the plugin root passed through the environment.** When the snippet filters or decides on a plugin CLI's verdict (`github-pr-scan.md` item 9's `pr-checks.js --pr` filter, #3469), a shape pin proves the prose names the CLI, not that the filter keeps and drops the right rows. Write the snippet as `PLUGIN_ROOT="${CLAUDE_PLUGIN_ROOT}" node -e "…process.env.PLUGIN_ROOT…"` so the test can point it at a temp root holding a stub `bin/<cli>.js` that answers per argument (one state per fixture row, one `process.exit(1)` row for the failed read) without a live `gh` or a real PR. Extract the fence, substitute the fixture path for the shell variable it reads, run it with `PLUGIN_ROOT` set in the spawn env, and assert both the surviving rows and the stderr line for each dropped one (`tests/display-ci-readers-conformance.test.js`). The env-var form also sidesteps the Windows backslash-in-JS-literal hazard the next paragraph's `CLAUDE_PLUGIN_ROOT` note describes, since no path is interpolated into the JS source at all.

**A fence that writes through a run-dir-anchored CLI still runs — build the fixture the guard expects.** `log-decision.js` and the other sanctioned run-dir writers refuse a `--run` that is not anchored under a checkout's own `.claude-tweaks/pipelines/` (exit 3), so running such a fence against a loose scratch directory fails, and the tempting retreat is a shape pin on the fence text. #3351's `log-decision.js` SKIP fence in `plugin/skills/flow/multispec-preflight-failure.md` took that retreat: its test asserts only that `--text` carries no backtick, which a stray `"` or `$` still passes. Build a `gitRepo` fixture, create the run dir at `{fixture}/.claude-tweaks/pipelines/{run-id}/`, and run the extracted fence under `bash -c` with `cwd` inside the fixture, `PIPELINE_RUN_DIR` set to that run dir and `CLAUDE_PLUGIN_ROOT` set to the checkout's `plugin/`. Then assert exit 0 and the logged line's literal text in that run dir's `decisions.md`. `tests/dispatch-flow-rundir-handoff-fixture.test.js` shows the guard accepting a fixture run dir built this way, though it spawns `log-decision.js` directly rather than from an extracted fence. Pass `CLAUDE_PLUGIN_ROOT` with forward slashes (`path.join(ROOT, 'plugin').split(path.sep).join('/')`): an unquoted `<<NODE_EVAL_EOF` heredoc expands it into a JS string literal, where a Windows `D:\a\…` root reads as escapes and `require` fails with `Cannot find module 'D:aclaude-tweaks…'` on `windows-latest` only (`tests/dispatch-neighbour-in-flight-mcp.test.js`, #3517).

**Run the fence with a hostile placeholder value, not only a benign one.** An extract-and-run test that substitutes ordinary values (a scratch path with no quote in it, a branch named `feat`) proves the fence runs. It never proves the fence passes its values safely. A placeholder pasted into quoted script text, such as `require('{run-dir}/run-state.json')` inside a double-quoted `node -e`, runs green on every benign value and breaks the first time a real path carries a `'`. #3809's review reproduced exactly this in `plugin/skills/flow/worktree-merge.md`'s Step 1 run-state read, which the suite had pinned only for presence and order. `tests/local-merge-close-run-ordering.test.js`'s run-state read test is the shape to copy. It runs the extracted fence line with `{run-dir}` set to a scratch dir named `o'brien run`, then asserts exit 0 and the expected stdout. Its go-red rewrites the line back to the pasted form (`require('{run-dir}/run-state.json')`, trailing argument dropped), asserts the rewrite changed the line, and asserts that form exits non-zero on the same path. The fix such a test pins is to keep every substituted value out of the script text: pass it as an argument (`node -e "…process.argv[1]…" "{run-dir}"`), or pass free text through a file (`log-decision.js --text-file`). Pick the hostile character for the quoting the fence actually uses: `'` breaks a single-quoted string, while `"`, `$` or a backtick breaks a double-quoted shell argument.

**Race variant: when the bug lives in a concurrent change between two clauses of one fence.** A fence that reads a moving ref twice (a tree check on `origin/main`, then a second `rev-parse` of it to record) is correct on a quiet fixture and wrong the moment a sibling's fetch lands between the reads, so a run against a static repo never shows it. #4157's release Step 3 check is the instance: the fix resolves the tip once, in its own first call that prints it, and the tree check compares `HEAD` against that sha pasted in literally (a `TIP=$(git …)` carrying it inside one call is a shape the worktree guard refuses, `_shared/scratch-worktree.md` §7). `tests/release-review-tree-check-conformance.test.js` proves it by running both extracted fences with the sibling's move landed between them: commit and push from a second clone, then `fetch` into the checkout under test (`siblingMove`). When the race sits between two clauses of one fence instead, splice the move into the same `bash -c` at a named anchor, and write the splice helper so it asserts its anchor is present before it replaces anything, or a reworded fence silently runs un-raced and passes. Then assert the recorded value equals the pre-move sha, read from the fixture before the run, and pin that the comparing fence never names the moving ref at all. Each clause whose protection you claim needs its own go-red: doctor that one clause back to the buggy form (`origin/main` in place of the literal, `rereadClause`) and assert the same move now changes the outcome. An earlier version pinned only the rev-list clause, so reverting the tree diff stayed green; every clause that reads the ref is a separate pin.

**Expression variant: when the fence cannot run, extract the guard or predicate and evaluate it.** A fence that calls `gh` can usually still run, against the shell-function stub in the next paragraph. When one genuinely cannot, the tempting retreat is a regex over its guard or predicate text. A text pin cannot see which way a guard points or what a predicate computes: #4469's review found the `SINCE` and `STATE_SEARCH` placeholder guards in `_shared/github-pr-scan-acceptance.md` pinned without their `if (!`, so a guard inverted to throw on every good value and pass every bad one stayed green. Extract the one line or expression and run it with `new Function`, injecting what it reads: `new Function('process', line)({ env })` for a guard, `` new Function('f', 'LIMIT', 'process', `return ${expr};`) `` for a predicate. `tests/acceptance-scan-server-filter.test.js` does both. `guardThrows` asserts each guard throws on every bad value and passes every good one, and its control inverts the guard (`if (!` to `if (`) and asserts a good value now throws. `ceilingMisses` evaluates each parent-fetch predicate over a truth table (at the ceiling, one under it, a limit above and below 1000) and names the rows it gets wrong. Extract shape-agnostically and never de-duplicate. The suite's first `ceilingExprs` matched only the correct comparison and collected matches into a `Set`, so a site slipped to another form was not extracted at all and the identical survivors still counted as one (fixed in `a5020a325`). It now captures the text inside every `fetched.some((f) => …)`, asserts exactly three, and runs a per-site control (`mutateNth`) proving that a mutation in any one site misses table rows in that site only. When the fence does run against a fixture, give it a row that only the clause under test drops. #4466's parent-gate scan fixtures held only due parents, so deleting the scan's `due` filter stayed green until review added a below-floor parent with one sub-issue still open (`tests/below-floor-parent-close-conformance.test.js`, AC3.1).

**A fence that calls `gh` runs against a shell-function stub, not a PATH shim.** Prepend a `gh() { … }` definition to the extracted fence inside the same `bash -c`. The function shadows the binary, so no network is touched and no stub file has to sit on `PATH`. Dispatch on `"$*"` to serve one fixture per call, and pass the fixture paths through the spawn env, forward-slashed, never into the script text. `runClosedFence` in `tests/acceptance-scan-server-filter.test.js` (#4598) is the instance: `gh() { case "$*" in *'closed:>'*) cat "$FAKE_NEW" ;; *) cat "$FAKE_OLD" ;; esac; }` serves the newer date slice to the call whose `--search` carries `closed:>` and the older slice to the other. #4598's review found that fence pinned only by regex and by single guard lines run through `new Function`. Running the whole extracted fence this way is what exercised the slice wiring, the per-slice cap at 999 and 1000 rows, and the number-keyed merge. Keep the expression variant for a fence whose correctness depends on what `gh` itself does (exit codes, pagination, search semantics), which a fixture would only fake.

**Make the stub truncate when the fence's bug is a fetch cap.** A stub that returns its whole fixture hides a hardcoded `--limit`. Have the function read N from `--limit N` or `--limit=N` in its argv and serve only the first N rows of a larger fixture universe (`GH_STUB` in `tests/github-pr-scan-fetch-limit.test.js`, #4820). The frozen pre-change fence then reports 200 of 308 rows with no warning, which reproduces the symptom, and the live fence at a sized limit counts all 308. Freeze the pre-change fence as a constant and run it, and pair it with an in-memory check that reverting the live fence's edits (the limit token and the warning line) equals the frozen text byte for byte, so the frozen copy cannot drift from what shipped. Run the live fence at the boundary: a universe above the limit, exactly at it, and one row under. A fetch that reaches the limit cannot be told from a truncated one, so at-limit warns and one-under does not.

**Raising a fetch limit means re-checking every call that prints its rows, and every fence you touch against the worktree guard.** A call that echoes a fetched list to stdout was bounded by the old cap and is not bounded by the new one: at 1000 rows per list it overruns the Bash result limit. #4820's item 4 writes each list to a file and prints only the remnants, and its test runs the fence at 1000 rows per state and asserts `stdout.length < 1000`. A fence added or reshaped for that change must also pass the worktree guard. `tests/skill-fence-guard-shapes.test.js` sweeps every shell fence under `plugin/skills` for the shapes `_shared/scratch-worktree.md` section 7 lists as refused (git text inside `node -e`, a `$VAR` redirect target), and item 4's first form tripped it only at full verify. Put that suite in the targeted set for any change that adds or edits a fence, and run the fence in the form the agent runs, every `{placeholder}` substituted as literal text (`withPaths` in the item 4 test).

**A fence that captures a `node -e` result in a variable owes its could-not-read arm a run of its own.** `VAR=$(node …)` leaves node's exit status in `$?`, but a skill fence runs without `set -e`, so nothing reads it: a throw reaches the next line as empty output, and a lister reads that as zero records. #4740's mirror fallback in `plugin/skills/wrap-up/cleanup-procedures-execution.md` rethrows every read error except `ENOENT` (`parse-signal-discipline`'s fs error-code split), and the rethrow alone was not enough: without the trailing `|| exit 1` on `RECORDS=$(node -e '…' -- "$MIRROR")`, an unreadable `work/` printed `count=0` and exited 0 under both bash and zsh. Empty-directory and absent-directory fixtures cannot tell the two forms apart. Add a denial fixture (`chmod 000` on the directory, skipped on win32 and under root through `tests/helpers/root.js`'s `chmodDenialSkip`) and assert three things: a non-zero exit, the error code on stderr, and that the code after the capture never ran (no `count=` line). `tests/wrap-up-closing-records-array-fill.test.js`'s unreadable-`work/` case is the instance. Keep the capture a plain assignment: `local VAR=$(…)` and `export VAR=$(…)` exit 0 whatever the command did, in both shells, so a `|| exit 1` after them never fires.
