# Shared contract extraction

How this repo extracts a recurring cross-skill rule into a new `plugin/skills/_shared/*.md` contract and migrates its consumers to cite it instead of restating it. Recurs constantly (`git log --diff-filter=A -- 'plugin/skills/_shared/' 'skills/_shared/'` — both spellings, because this repo's history straddles the #418 payload move (ADR-0015); discount the cutover commit's own bulk add — shows dozens of distinct contract files added since the pattern started — re-run the command for a current count rather than trusting a hardcoded one, deduping by filename across both path spellings since a file re-pathed by the #418 move otherwise double-counts — several explicitly extraction/consolidation commits: `b91e704b`, `47ed1675`, `d937f35d`, `31df65dc`, `ce9dab9c`, `545cd4fd`, `c59f19f8`, `3a270ad4`, `ccd502b0`) but has had no procedural home — the accumulated failure knowledge is scattered across five project-memory entries with no recipe tying them together.

## The steps, in order

1. **Derive the consumer list before writing the contract.** Grep every spelling of the retired vocabulary **and its regex-escaped form**; leaf-only sub-files and test pins are what a shape-match sweep misses. Pair the single-line grep with a `grep -z` / `\s+` control scan — hard-wrapped prose splits a literal mid-command `[IL-66]`. Re-run the derivation after every upstream merge: a sibling branch can land a brand-new consumer file mid-run that no plan's file list could have named (the lesson `.claude/skills/work-record-facet-rename/SKILL.md` records at its "Re-run the vocabulary sweep after every upstream merge" gotcha).
2. **Decide per consumer: surrender, or keep and cite.** Not every consumer surrenders the same amount. Classify each into one of three shapes before editing anything — the split is what makes the conformance suite writable:
   - **retired a standalone clause** and now defers wholly to the new contract
   - **purely additive** — never had a clause of its own, gained only a citation
   - **outcome wording stays owned by the consumer** — the contract owns recognition, the consumer keeps what it *does* about it
3. **Check headroom before you add.** Measure `wc -c` on every file gaining a citation against the Read rail (`RAIL_BYTES`, `plugin/bin/lib/skill-audit/budgets.js`) before planning the additions — a byte-budget can be arithmetically unachievable, and thin headroom makes slimming a prerequisite, not a follow-up (`[IL-70]`; shipped instances that had to split a file mid-migration: `d937f35d`, `47ed1675`). A third remedy alongside slimming and the `_shared/{mode}-invocation.md` extraction pattern below: a **pointer-stub split** — move a whole section into a new sibling `_shared/*.md` file, leave a short pointer paragraph in the original naming the new file, and retarget any test that pins the moved text itself (a byte-pinned snippet, a prose-literal assertion — not a prose-citation pin, which survives the stub untouched) to the new file per `skill-prose-conformance-tests`' "Retargeting existing pins" convention (#1488 took `work-record.md` from over its then-ceiling to 33,094 B this way, extracting its permission matrix into `work-record-permission-matrix.md`; three suites needed pin retargeting). No size pin moves with the section: per-file byte budgets are retired (#3311, decision 0024), and `tests/skill-size-single-source.test.js` fails if a test re-adds one outside `plugin/bin/lib/skill-audit/budgets.js` — the rail measures the new file automatically. Measure every composed bundle a touched file is a source of as well, not only the file's own `wc -c`: `plan-audit.js`'s headroom check reports each one under `headroom.composed`, and a bundle near the rail is reason enough to put the new text in a new `_shared` file even when the raw file has room (#4045: `_shared/pr-first-merge.md` had room on its own, but the `merge` bundle it composes with `pr-checklist-refresh.md` stood at 52,195 of 52,500 B, so the Landed check went to `_shared/acceptance-labeling-landed.md`). A "this file must not grow" or "the bundle stays under the rail" constraint the extraction relies on is held by the `rail:` suite; never restate it as a byte assertion in the extraction's conformance suite, which `tests/skill-size-single-source.test.js` fails (#4045's plan pinned `pr-first-merge.md` at `<= 38412` B, two task reviews and the whole-branch review passed it, and only the full-suite run caught it). Cross-reference `docs/plugin-structure.md`'s per-skill sub-file table as a registration site alongside step 4's `docs/skill-graph.md`.
4. **Update the edges, once.** Every skill relationship is stated once in `docs/skill-graph.md` (CLAUDE.md's Cross-references rule). A new `_shared` file means adding its consumer edges there and adding nothing to any `SKILL.md`'s relationship prose.
5. **Pin the migration with a conformance suite.** Follow the `skill-prose-conformance-tests` skill. Write assertion families matching step 2's classes: contract anchors present, each consumer cites the contract, each retiring consumer no longer carries its retired clause — **each with a whitespace-collapsed control, absence assertions included.** Absence assertions fail open on a line-wrapped literal; presence assertions fail loud. Verify the suite can actually go red: revert one pinned element and re-run before finalizing.
6. **Prove the retirement, don't assert it.** Grep for *citations* of the retired rule — by name, path, and paraphrase — not just restatements of it; dead anchors survive text sweeps. Where a tombstone marker is required, state its scope in the spec — a same-line `grep -v` filter fails on adjacent-line and construct-intro tombstones. Before ruling "no consumer depends on the old behavior", grep repo-wide for the fixture-creation pattern — a per-suite spot check is not a sweep.

## Extending to a later consumer

The steps above describe a first extraction. The shape this repo now runs more often is the second one: an already-extracted contract gains one more consumer pair, no extraction involved (`_shared/untrusted-record-content.md` went #1275 → #1274 → #1391 → #1442). The bullets below are the rules the extraction-time steps do not reach; the Gotchas' "still needs step 4's edge update" bullet is another.

- **The consumer set is the callee's call sites, enumerated at spec time — not the record's file list.** Step 1's derivation has nothing to grep for here: no vocabulary is being retired. Grep the callee's invocation literal instead (`grep -rn 'args: "grant-check' plugin/skills` returns both sites) and give every hit an explicit in-scope-or-deferred verdict before the spec is written. #1391 shipped the obligation to `backlog/refine-headless.md`'s Phase B and left the identical call at `backlog/refine-mode.md`'s Step 3 unwrapped; review found it, not the plan (#1442).
- **When the callee has 2+ call sites, route the caller-side paragraph through a `_shared/{mode}-invocation.md` file before adding it anywhere.** This is what step 3's headroom measurement should *decide* on a later-consumer run: near the rail, slimming is one remedy and a shared invocation file is the better one, because every site after the first then costs a one-line citation or nothing at all. `_shared/ceremony-check-invocation.md` (3,617 B) carries the untrusted-content paragraph once for three call sites, which is why #1274 extended this same contract to ceremony-check without touching `specify/record-creation.md` (40,816 B) and with only a pointer line in `flow/materialize.md` — while #1391, with no `grant-check-invocation.md` to cite, had to defer `refine-mode.md` at 40,933 B of the then-40,960 B ceiling.
- **A caller-side obligation that adds an outcome to a file that logs outcomes by key must name the key.** The caller half of a two-sided contract always states what a missing verdict line does; where the consumer already groups its results by a key (`refine-headless.md`'s `failedKey`, which its Step 4 logs and its Step 5 summary groups by), "skip it and report it" is not yet a deliverable. #1391 reached review before `failedKey: 'grant-check-no-verdict'` was named.
- **A new outcome added at the caller must be swept through every place that consumer already *enumerates* its outcomes, not
  only the paragraph that introduces it.** The bullet above is the headless form of this (name the `failedKey`); the
  human-present form is wider, because a render surface enumerates outcomes in more places than a log does. #1442 added
  `no verdict rendered` to `refine-mode.md`'s Step 3 paragraph and to the two sites its own author thought of, and left four
  stale: `refine-lanes.md`'s lane-precedence sentence, its Grant-lane exclusion clause, and its Flag-back example table, plus
  `refine-closing-summary.md`'s audit-log template. Whole-branch review caught all four (`e971acc4d`), not the plan. Derive the
  site list mechanically before writing the caller paragraph: grep the consumer's directory for the outcome labels the new one
  is joining (`grep -rn 'needs scoring' plugin/skills/backlog/` returns all six sites) and give every hit an explicit
  in-scope-or-not verdict — expect prose false positives (a carve-out saying the label must *not* apply to some record class)
  and classify them rather than edit them. A two-item enumeration goes wrong silently the moment a third item exists: nothing
  about adding the third makes the other two go red.
- **A consumer that cites a contract's recognition rule but deliberately departs from it states the departure in the citing
  sentence, and a test pins that sentence.** It is an exception to "the contract owns recognition" below, and an unstated
  one reads as drift: the next editor "aligns" the consumer with the file it cites and reintroduces the risk
  the departure existed to avoid, with every test green. Put the departure in the sentence that carries the citation, not a
  later paragraph, so an aligning edit has to delete the pinned text and goes red. #2927's `visual-review/SKILL.md` Step 0.5
  cites `design-wrapper/frontend-detection.md`'s Layer 2 → Layer 3 order but treats a declared `web`/`mobile`/`desktop` as
  sufficient without the sniff the cited diagram continues to. Whole-branch review found the exception unstated (M2), and
  mutation M4, an added "on `web`, Layer 3 must also match" line, passed all 9 original tests. Fixed in `7020bc28e`, pinned by
  `tests/visual-review-recommendation-surface-gate.test.js`'s "a declared web/mobile/desktop surface is enough without a
  Layer 3 match".
- **A carve-out that delegates its exceptions to consumers owes one exception list per posture, not per file.** When the contract grants an exemption and says each consumer states its own exceptions (`_shared/worktree-setup.md`'s "Forge-API-only invocations need no worktree"), enumerate every write each posture the citing file runs actually makes before writing its note — one file can host several postures with different write sets. #2727's first `backlog/refine-headless.md` note claimed the carve-out covered "the whole firing", but that file also runs the labeling lanes, which inherit `refine-mode.md`'s `facets.unsynced === true` and `local-files` `writeRecord` exceptions; `refine-mode.md`'s note listed only Step 5's writes, missing the session temp files and the `health-state` ref `merge-lane-breaker.js` pushes. Review caught both (`b65a38b0d`), and the pinning test's description (`tests/worktree-forge-api-carve-out.test.js`'s `'…whole firing is covered…'`) kept the retired claim after the note was narrowed — sweep it with the note.
- **A new verbatim prompt line that joins an existing one in an inlined template is owed everywhere the existing one is substituted.** When a `_shared` line reaches dispatch templates as a bracketed placeholder beside an earlier one, the consumer set includes every file that inlines those templates and maps their placeholders, not only the templates themselves. Grep the sibling placeholder's literal (`grep -rn 'READ-ONLY REVIEW line' plugin/ tests/`) and give each hit a verdict, and scope the contract's own "inline this into…" sentence to the consumers actually wired. #3737 added the `SHELL DISCIPLINE:` placeholder to `/review`'s Step 3 templates; that grep returns `tidy/console-backfill.md`'s substitution list for `step3-tiebreak.md`'s template, which review found unmapped, and the contract sentence first claimed every worktree-isolated implementer, reviewer or lens (both fixed in `1d29ac676`).

## Variant: consolidating runtime sidecar files, not prose

The steps above assume the consolidated artifact is prose. #1752 ran the same recipe one medium over: four (six by build time — #1983/#1984 landed while the record sat in the backlog) ad hoc per-reason `dispatch-*-excluded.json` session-scoped files collapsed into one `dispatch-exclusions.json` of `{reason, records, detail}` entries behind `plugin/bin/lib/dispatch/exclusions.js`. Steps 1, 2, 5 and 6 transfer literally — the retired vocabulary is the old file names *and* their env-var manifest entries (`DISPATCH_BLOCKED_EXCLUDED`, `DISPATCH_OVERSIZED_EXCLUDED`, …), and the consumers are `node -e` snippets inside skill prose, so step 5's pins are `skill-prose-conformance-tests`' extract-and-run anchors — which must be retargeted when the snippet's own *code* changes, not only when its prose is reworded (`tests/dispatch-named-target-exclusion-fixture.test.js`'s `END_ANCHOR` moved from `"$DISPATCH_TARGET_MISSING_EXCLUDED"` to `"$DISPATCH_EXCLUSIONS"`). Steps 3 and 4 do not apply: a `bin/lib/` module has no size budget at all (the Read rail binds skill `.md` only) and no `docs/skill-graph.md` edge. Two rules the prose steps have no analog for:

- **The file boundary was carrying lifecycle differences for free — re-encode them explicitly.** Separate files can have separate lifetimes without anyone deciding so; one merged file cannot. Five of dispatch's reasons are recomputed on every re-pull, while `firing` entries are appended *between* re-runs within one firing (`firing-exclusion.md`) and must survive them — so `queue-pull-script.md` now opens with an explicit truncate-preserving-`firing` step. Omitting it would have silently restored the infinite re-dispatch loop that file exists to prevent. Enumerate each merged input's reset cadence before writing the reset step, and pin the preserved class (`tests/bin-lib/dispatch/exclusions.test.js`). The shipped analog one level up is `wrap-up/cleanup-procedures-execution.md`'s carve-out of `score-history.jsonl` from a bulk cleanup.
- **A persisted consumer keeps its own schema; convert at the boundary and say so there.** Not every reader of the old shape is in scope. The queue-order disk cache (`bin/lib/dispatch/queue-order.js`) keeps its pre-#1752 `{number, blockedBy}[]` `excluded` field, and `queue-pull-script.md` converts in both directions at exactly the two points the schemas meet — cache-hit materialization and write-back — each with a comment saying that is what it is. Migrating the persisted blob instead would have invalidated every existing cache, for a file that is rebuilt from scratch on every miss anyway.

## Project conventions

- **The contract owns recognition and policy; consumers own outcomes.** Never let the extracted contract dictate what a consumer *does* about a condition it recognizes — only how it recognizes and classifies it. This is what keeps step 2's third class (outcome-wording-stays-owned) from collapsing into a restatement.
- **Cite, don't restate — including in the same author's own later prose.** A migration that gets the first N consumers right can still regress on the N+1th: two consumers in record #796's own migration restated burst-shape rules the same plan had written cite-only for the rest, caught only at final whole-branch review. An instruction a skill forwards into another in-session skill invocation (SDD, a component skill) is no exception: the invoked skill runs in the same session and reads the citation, so keep only the call-site wiring inline. #4304's `build/dispatch.md` restated `_shared/pre-review-catchup.md`'s outcome routing on the theory that a forwarded instruction must be self-contained; the copies had already drifted within three fix commits, and collapsing them took a review debate, two tiebreaks and a conformance-test rewrite (b4ad51a81).

## Gotchas

- **A dormant forward reference may already name the future contract.** Check for commented-out or "pending #N" references to the contract file before assuming every consumer starts from zero.
- **A dormant forward reference must be discharged once its follow-up lands, not just left as a pointer.** The other half of the bullet above: when the follow-up record actually ships the fix, its own change must rewrite the "filed separately as #N" placeholder into the real resolution — a contract file asserting a gap is still open after the record that closes it has landed is itself a drift the next reader has to re-discover (#435).
- **Make that forward reference a fixed literal and pin it, so the discharge is mechanical rather than remembered.** The bullet above states the obligation; this is what makes it survive the gap between the two records. Write the placeholder as one fixed row and have the extraction's own conformance suite pin its **presence**; the follow-up record then replaces exactly that row, and its suite pins the same literal's **absence** alongside the successor rows' presence — with the retired row frozen as a control constant, since an absence pin is the direction that fails open. Instance: `plugin/skills/_shared/untrusted-record-content.md`'s `| ceremony-check consumers — … | added by #1274; until it lands, those call sites pass the body unwrapped |` row, pinned present by #1275 and discharged into two real consumer rows by #1274 (`6ff557ae`; `tests/untrusted-record-content-conformance.test.js`'s `FROZEN_FORWARD_ROW`).
- **The live label/edge may already exist from a reverted build** — verify current state before writing, never trust a spec's carrier list as fact in a multi-session repo.
- **Launcher commands and journeys carry the vocabulary too** — a citation swept into skill prose can leave a journey or a paste-ready command still naming the retired clause.
- **Retire every shape of the clause, and re-point every claim about what the suite pins.** A retired clause often has two shapes — prose sentences and table skeletons (header rows). An absence list built from the prose alone lets a template regain a retired table with the suite green; give each skeleton its own header pattern and a frozen-control row, and pick control rows by identity, never `slice(0, n)`. A journey that says which test pins what goes stale the moment the pins move to the contract, so grep `docs/journeys/` for the suite's file name and rewrite each claim. Instance: #3413's whole-branch review caught both (`tests/timing-prose-conformance.test.js`'s `RETIRED` list; the pin sentence in `docs/journeys/read-where-a-pipeline-run-spent-its-minutes-1928.md`).
- **A later consumer added to an already-extracted contract still needs step 4's edge update — plus a sweep step 4 doesn't cover.** Step 4 ("update the edges, once") was written for a brand-new `_shared` file at extraction time. When an *existing* contract instead gains a consumer later — no extraction, just a new citation — also grep the contract file's own self-description ("sole consumer", "only X reads this", "no consumer yet") and update it alongside its `docs/skill-graph.md` row; both go stale the moment a second consumer lands, and the extraction-time step never runs again to catch it (record #194 caught two stale instances — `existing-convention-detection.md`'s own "Read by" line and `docs/skill-graph.md`'s row — only at final review). The contract need not live under `_shared/` for this to bind: when one skill starts citing another skill's own sub-file, that sub-file's "Read by" line and a `docs/skill-graph.md` edge are owed the same way. #3109 wired `/wrap-up`'s `prune-after-wrapup` plan delete through `tidy/plan-citation-check.md` and pinned it, but left that file's header naming only tidy's two call sites and added no graph edge.
- **A later consumer also still owes step 5's conformance pin — the extraction run's suite does not cover it.** The sibling of the bullet above, one step further along. Wiring an already-documented check into a new call site invents no mechanism, so the change reads as too small to pin, and the extraction run's suite already existing makes the pin feel already-written. It is not: that suite pins the consumers that existed when it was authored, and nothing goes red when the N+1th call site's prose is later reworded or dropped. Record #974 wired `_shared/issue-claims.md`'s in-flight-tombstone stop into two new call sites (`dispatch/settle-and-merge.md`'s Claim-contest special case, and `issue-claims.md`'s own gh-absent MCP-transport lock step 4) and shipped no assertion for either; `/claude-tweaks:review`'s Test Quality lens caught it and the two pins landed in `tests/flow-claim-preflight.test.js` after the fact. Write the per-consumer assertion in the same change as the wiring, following the `skill-prose-conformance-tests` skill.
- **The rail headroom check is a merge-time check, not only an authoring-time one.** Step 3's headroom measurement is taken against the base you started from. A file near `RAIL_BYTES` that you also touched can be pushed over by an *upstream merge* that lands new text in it — no edit of yours changed, and the `rail:` suite in `tests/bin-lib/skill-audit/context-cost.test.js` goes red at the merge commit. Re-measure `wc -c` on every near-rail file this migration touches immediately after each upstream merge, not only before planning the additions. Evidence (2026-08-22, the #1261-#1264 batch, under the former 40,960 B per-file ceiling): `plugin/skills/specify/decomposition-mode.md` was at 40,9xx after its own spec's edits; a routine `origin/main` merge added Step 6's staged-marker exception and put it 293 bytes **over** 40,960, forcing an emergency slimming pass (`d7daaccc`) before the branch could go green. The same run's citation migration was already byte-constrained in the other direction — `plugin/skills/review/step3-routing.md` had a floor citation reworded purely to give bytes back (`66836698`, 22,079B -> 22,065B).
- **Extending an already-extracted contract's *closed enumeration* means sweeping the cardinality word too — including in test descriptions.** When a `_shared` contract declares a closed set ("Exactly four event shapes", `plugin/skills/_shared/visual-decision.md`), adding a member is not a vocabulary *retirement*, so step 1's retired-vocabulary sweep never fires on it and step 6's citation sweep has nothing to look for. Grep the cardinal itself (`"four event"`, `"Exactly four"`) across `plugin/`, `tests/`, and `docs/` before editing. Record #1207's plan-authoring sweep found the count restated in two *test descriptions* — `tests/visual-decision-contract-conformance.test.js`'s `'…the four event shapes exactly once'` and `'…exactly the same four shapes'` — text no assertion reads, so it goes stale silently and stays green. Expect a same-word false positive and classify it rather than edit it (`tests/reflect-friction-lens-vocab.test.js`'s "four event types" is an unrelated hook-event vocabulary).
- **A new `_shared` file's own nature does not exempt it from step 4.** "It's a cross-reference/fact table, not an invoked skill" sounds like a reason to skip the `docs/skill-graph.md` edge — it is not. Step 4 keys on the file being new, not on whether a skill *invokes* it. Record #1765's build phase reasoned exactly this way about a new `_shared/fast-lane-digest.md` ("not an invoked skill, so skill-graph.md needs nothing") and skipped the edge; wrap-up's Docs row caught the gap only because the row's own domain-overlap scan happened to read this project skill's text and re-checked step 4 against the live file.

- **A new `_shared/*.md` file's `docs/skill-graph.md` edge is mandatory; a `docs/plugin-structure.md` mention is a judgment call, not a given.** Step 3's "cross-reference `docs/plugin-structure.md`'s per-skill sub-file table as a registration site" is right for a skill's *own* lazy-loaded sub-file and wrong to apply unmodified to a `_shared` contract: that doc carries one curated row for the whole directory (`plugin/skills/_shared/*.md → Cross-skill shared content … — see the directory listing`), not a per-file table, so adding a *new dedicated row* there is drift, not registration. Step 4's edge is still owed, including when no skill names the new file directly — file the graph row under the section for the reader it addresses and say so in the row. #1995's `_shared/dispatch-waiting.md` is the worked case for staying out of `plugin-structure.md` entirely: one `docs/skill-graph.md` row filed under `dispatch` ("cited only from the contract's one-line pointer — no skill names it directly … for want of a section for contract-owned files"), no `plugin-structure.md` edit, ruling narrowed from the plan's first draft at whole-branch review. That is not the only outcome, though: #1926's `_shared/ceremony-profile.md` was added *into* the curated row itself on a review finding ("the curated `_shared` row lists ceremony-profile.md", `399981c52`) — the row's own self-description ("a curated subset … only the fragments worth calling out here") makes whether to fold the new file into that curated list an explicit judgment call each extraction has to make, not a rule that always resolves to "nothing."
- **When headroom forces a split you did not plan, extract the section with no citers and no byte pins.** Step 3's pointer-stub split is normally chosen for cohesion; sometimes it is forced mid-build, when one sentence lands on a file already near the rail. The cohesive section is then the expensive one — every citer needs retargeting and every byte pin needs moving. Pick on cost instead: `grep -rn '{section-heading}'` across `plugin/`, `docs/`, and `tests/`, and take a section that returns nothing. #1995 needed 252 B on `_shared/subagent-output-contract.md` and moved "Waiting for Dispatched Agents" (1,088 B, no external citer, no test pin) rather than a load-bearing section; the whole migration cost one pointer line, one skill-graph row, and zero pin retargeting, and the contract landed at 40,333 B. State in the record that the split was headroom-forced, so the next reader does not mistake the new file's boundary for a designed one.
- **A pointer stub's read condition must cover every path that used to fall through to the moved text.** Inline text is read on every path that reaches that point in the file; a stub is read only when its stated condition holds. Key the condition on an event ("once the write call has run") and any path where that event never happens loses the moved text with no error. List the paths that reach the split point — including the ones that do nothing — and name each in the stub and in the sibling's header. #2841 split shaping mode's Read-back verification and Actions Performed into `shaping-mode-readback.md` behind a stub keyed on the write call; the near-duplicate refusal and the already-shaped no-op both reach that point without writing, and each was caught only at review (`e67e0ed93`, `3e3c8b53c`).
- **Changing an existing contract's *behavior* means sweeping every consumer on its Consumers line for a contrary local rule.** No consumer is added and no vocabulary retired, so neither step 1's derivation nor the later-consumer bullets fire — yet a consumer that restated the old rule in its own file now contradicts the contract. Read the contract's Consumers line, grep each listed file for its local statement of the rule being changed, and for each hit either align it or state an explicit opt-out that the contract's parameterization section lists by name. #2730 widened `_shared/transcript-judge.md`'s watermark write to the self-assessment route and scoped the edit to the feedback consumer; `reflect/SKILL.md`, the contract's second listed consumer, still said "never after a terminal dispatch failure" until review caught it (`17c836464`, opt-out listed in the contract by `d5a5088d8`). The plan's self-check had asked whether reflect *branched on* the watermark — a narrower question than whether any consumer *stated* a contrary rule.
- **Aligning a consumer means editing the procedure it performs, not a sentence that summarizes it.** The sweep in the bullet above finds the consumers; the edit can still land on the wrong sentence. A consumer that both performs the contract's read (a list of what to fetch) and later says it did ("the re-verify above, which includes X") can be aligned on the claim alone, and then reads as fixed while fetching nothing new. #3405 added a head-run `gh run list` read to `_shared/pr-first-merge.md` Step 2.5 and carried it to four restating consumers. In `tidy/actions-github-issues.md`'s Arm ready PR action, `2f8f2b429` added "(which includes Step 2.5's head-run `gh run list` read …)" to the green-by-construction sentence and left the **Re-verify before writing** list it points at unchanged; whole-branch review found it by reading the file, and `90c16ad71` added the read to the list. A whole-file `includes('gh run list')` pin, the shape `90c16ad71` uses for the other three consumers, is green on `2f8f2b429`'s claim-only text, so the pin slices the procedure itself (`tests/merge-verification-gate-conformance.test.js` slices from `**Re-verify before writing` to ``When judging `statusCheckRollup` ``), the region-first rule `skill-prose-conformance-tests` gives for one branch of a multi-branch ruling. For each consumer, edit the sentence that performs the read, and check any "includes", "already", or "same read as" sentence against it.

## Anti-patterns

| Pattern | Why it fails here |
|---|---|
| Deriving the consumer list from the spec's file list alone | A sibling branch lands a new consumer mid-run; the list is a hypothesis, not a fact |
| One sweep grep, single-line, unescaped | Misses the escaped form, the mid-command wrap, and leaf-only sub-files `[IL-66]` |
| Adding the citation to every consumer uniformly | Conflates "retired a clause" with "purely additive"; the conformance suite then can't be written without lying about one class |
| Restating the new edge inside a `SKILL.md` | Two copies of an edge drift; `docs/skill-graph.md` is the single home |
| Asserting the retired clause is gone with a plain `includes()` | Fails open on a line wrap — the deletion is certified without being verified |
| Carrying an extension's *rationale* the way you carry its obligation | An obligation transfers to every call site; the grounds a decision rested on do not. Re-derive each ground against each site's own mechanics, and have the contract say which ones transfer instead of leaving the next reader to assume all of them do. #1276 declined Task-agent isolation for `framing-check` on three grounds, and only two survived the trace — the third (non-gating blast radius) holds at all three `framing-check` sites but not for a gating consumer, so `_shared/untrusted-record-content.md` had to scope the inheritance to "these two structural grounds" explicitly |
