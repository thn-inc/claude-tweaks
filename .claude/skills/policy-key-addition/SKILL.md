# Policy key addition

`plugin/bin/lib/policy-schema.js`'s `POLICY_KEYS` is the data, and `plugin/skills/_shared/policy-schema.md` is the prose index; "if the two disagree, one of them has a bug". `bin/resolve-policy.js` is the one read path skill prose uses. #4609's fourteen keys are the most recent large instance, and its review findings are the gotchas below.

## Sites

1. **The `POLICY_KEYS` row.** `key` (flat kebab-case, `tests/policy-key-naming.test.js`), `type` (`boolean`, `enum`, `integer`, `string`, `list` or `map`), `values` for an enum, and `default` unless the default is derived (`_shared/policy-schema-read-path.md`'s Derived-default keys, Shapes A and B). A derived key is also named in its shape's paragraph there, the membership list `/claude-tweaks:help`'s policy mode reads, and gets a `computed (…)` row in `plugin/skills/help/policy.md`'s Derived-default keys table; #5224 added the Shape B `express-driver-max-lines` without either. `summary`, `category` and `tier` are required (`tests/policy-schema-metadata.test.js`). A boolean's value is the literal `true`/`false`, never `on`/`off`: `resolveValue` falls back to the default on any other spelling (the comment above `POLICY_KEYS`, #660). An enum that gates a code table gets a test asserting its `values` equal that table's keys, as `express-driver-max-size` does for `SIZE_CEILINGS` (`tests/bin-lib/express/eligibility.test.js`): #6018's `express-driver-max-risk` shipped without the twin for `RISK_CEILINGS` and review caught it.
2. **The tier.** The core tier has an enforced cap of 12 (`tests/policy-schema-metadata.test.js`) and sits at it, so a new key is `advanced` unless it replaces a core one.
3. **The key count.** `tests/policy-schema.test.js` pins `POLICY_KEYS.length`. Bump it in the same commit, and rewrite the `Last bump: {old} -> {new}, #{record}` line directly above the assertion — the test fails when that line's new value differs from the pin. The assertion beneath it, `new Set(POLICY_KEYS.map((k) => k.key)).size`, pins the unique-key count and takes the same bump; #5996 found it only after the first red run.
4. **The doc row** in `_shared/policy-schema.md`. Every key needs a table row there that starts `` | `{key}` | `` (`tests/policy-key-naming.test.js`), and its summary must not be copied verbatim from the row's `summary` (`tests/policy-schema-metadata.test.js`). State the value the resolver returns for unset, set and malformed input, from the code, not from intent. #4609's first `risk-path-globs` row said a malformed block resolves `{}`, the unset shape; the code gives `null` with `invalid: true` (review row 9). A consumer that guards a resolved value reads the same output: a malformed value arrives as `source: 'default'` with `invalid: true`, never as a non-default source, so a `source !== 'default'` guard never sees it. Key such a guard on `invalid`, and build its test fixture from a real `resolvePolicyKeys` reply rather than a hand-written one (#5224's `policyStep` guard, `ea298828c` → `3aa4ddf24`). Measure `wc -c` on `_shared/policy-schema.md` against `RAIL_BYTES` (`plugin/bin/lib/skill-audit/budgets.js`) before writing the row, and plan the section move in the same task when the rows will not fit: it has sat past the 47,250 B headroom flag line (90% of the rail) since #5291's two trust-key rows, so the next row may need the split described below. #5291's rows crossed the flag, the move was skipped, and review caught it (`6fc3007dc` then moved the Control mode key table to `_shared/policy-schema-read-path.md`). #4847's `declare-claude-tweaks` row only fit after the lazy `resolveValue` section moved to `_shared/policy-schema-coverage.md`, leaving a pointer stub. If the next row does not fit, move another section the same way (`shared-contract-extraction`'s headroom-forced split). Prefer one with no citers and no byte pins; when none frees enough bytes, a cited section may move if its stub keeps every name a citer uses (#5216 moved the Canonical read path to `_shared/policy-schema-read-path.md` this way). Citers outside the record's scope then need a follow-up record (#5249).
5. **A renamed key** keeps its old name in `RENAMED_KEYS`, never in `POLICY_KEYS`. `tests/policy-schema.test.js` pins that count too.
6. **A Manifesto-visible lever** also walks `_shared/auto-mode-contract.md`'s "Adding a new policy lever" checklist.
7. **A key that lands before its consumer** opens its `summary` with `Not yet used. ` or `Not yet used; ` and joins `NOT_YET_USED` in `tests/resolve-policy-control-mode.test.js`. That file pins both directions: every listed key carries the marker, and no unlisted key does. The record that wires a key's first consumer drops the marker and the list entry in the same commit. #4816 marked #4609's fourteen control-mode keys this way, and the comment above `control-mode` in `POLICY_KEYS` names the record that wires each. "Lands" means merges: a key whose first consumer arrives in a later task of the same PR merges together with it, so it takes no marker, since one task adding the marker only for a later task to drop it is churn the merge never sees. #5599's `review-lens-dispatch` row (task 1) and its reader `step3-workflow-dispatch.md` (task 4) shipped this way, after an implementation ruling on exactly this point. Wiring a flat control-mode key also moves three prose sites that no test reads for it. Its `Owner skill(s)` cell in `_shared/policy-schema-read-path.md`'s Control mode table changes from `none yet (#4608)` to the consuming skill, because that table's intro says a key is inert unless its row names an owner (`tests/risk-flags-refine-prose.test.js` pins the owner cell only for `risk-categories` and `risk-path-globs`). The key also leaves the unused-key list in step 4 of `docs/journeys/resolve-a-policy-key.md` and in step 3 of `docs/journeys/review-project-policy.md`. #4621 moved all three for `owned-owners` because its plan named them; the lists had also kept `control-mode`, `risk-categories` and `risk-path-globs` as unused after #4620 and #4618 wired them, because no test reads them.
8. **A `policyOnly` key** is also named in the `policyOnly` bullet of `_shared/policy-schema-coverage.md`'s "Canonical read path carve-outs", which lists every key carrying the flag (#5119 moved it there from `_shared/policy-schema.md`, which keeps only a pointer stub).
9. **A `policyOnly` key** is also named in the step 3 Red flags list of `docs/journeys/resolve-a-policy-key.md`, which lists every `policyOnly` flat key with its record. No test reads that list: #5119's `verify-suite-slots` was missing from it until #5222's review round added it (`259f5da1c`). A `policyOnly` flag added in a review fix round owes sites 8 and 9 in that same commit: #5563's `6b69def51` set it on `changelog-max-releases` and pinned it in `tests/policy.test.js`, but named the key in neither list.
10. **A factory-refused key** is named in `FACTORY_REFUSED_KEYS` (`plugin/bin/lib/policy-factory.js`) and in the Refused keys bullet of `_shared/policy-schema-read-path.md`'s "Factory layer" section, with its reason. A `policySourceExcluded` key always is (see "Decide who may set it").

## Decide who may set it

Two flags mirror each other, and a third standing source, the factory layer (#6006), needs its own answer. Pick by which source must never set the key:

- **`policyOnly: true`**: the resolver skips the `--run` overlay, so only `policy.yml` or the default applies. Use it for anything executed or anything that names who is trusted. #4609 set it on `deploy-command`, `owned-owners` and `trusted-authors` after review found a run config could otherwise set them (row 10). It set it on `risk-categories` too, because `risk-path-globs` validates against it from policy alone and the two must not disagree (row 11). The resolver reads only the checkout it runs in, so a key that a PR could rewrite in its own branch also needs its consumers to read it from the base branch. The resolver cannot do that for them; #4608 holds that requirement for the consumers (row 15).
- **`policySourceExcluded: true`**: a `policy.yml` value is discarded, so only a run-config source sets the key. Use it for a this-run-only decision that a standing default would quietly make permanent. `merge-authorization` is the one key with this flag today.
- **Factory-settable or refused.** The `CLAUDE_TWEAKS_FACTORY_POLICY` variable and `~/.claude-tweaks/factory-policy.yml` supply any key by default. Add the key to `FACTORY_REFUSED_KEYS` in `plugin/bin/lib/policy-factory.js` when it is a per-run human decision, the human-in-control switch, or an executed string specific to one repository (`_shared/policy-schema-read-path.md`'s "Factory layer" section). Every `policySourceExcluded` key must join it: `tests/policy-schema.test.js`'s "every policySourceExcluded row in POLICY_KEYS is in FACTORY_REFUSED_KEYS" fails otherwise. A key outside the list is settable from the factory layer, so check that a user-wide default is safe for it.

Every new key gets this decision, even when the answer is neither flag. A key whose every consumer reads `policy.yml` directly, never through `resolve-policy.js --run`, is `policyOnly`: an overlay would let `resolve-policy.js --run` report a value no consumer reads. `verify-suite-slots` (#5119, read by `verify.js` only as a flag) and `changelog-max-releases` (#5563, read by both release engines through `policy.js`'s `readChangelogMaxReleases`) are the instances. #5563 first shipped with neither flag, and review caught it (row 12, `6b69def51`). Say the decision in the comment above the row, as both of those do.

Decide from the new key's own routes, never by copying a sibling in its family. `model-stance` carries no flag because it has a per-run route (`resolve-profile.js --stance`, and Manifesto lever 10 writes it to the run config). `model-effort`, which the same resolver reads beside it, has neither route, so it is `policyOnly`. #5941 first gave `model-effort` no flag to match `model-stance`, and the final review caught it (`4de9b6b416`, pinned in `tests/policy.test.js`).

## Validation flags

- **`string`** is non-blank and whitespace-free by default. `allowWhitespace: true` opts a command-shaped value out of the whitespace rule (`release-hook`, `deploy-command`). Add `closedQuote: true` beside it: `parseFlatLines` cuts at any `#`, so a quoted value holding one is cut mid-quote, and `closedQuote` makes the leftover unclosed quote invalid rather than a truncated command. `release-hook` keeps its older contract without it.
- **`pattern`** is a whole-value regex. A URL key uses `HTTP_URL`, which refuses `@` in the authority because `policy.yml` is committed and must never carry a credential (row 14). Plain `http://` stays valid for dev URLs.
- **`list`** takes an optional `element` (`login`, `slug` or `defer-reason` in `LIST_ELEMENT_PATTERNS`; `defer-reason` is built from `DEFER_REASONS`) that every comma-separated entry must match, and an empty entry never does. The unset default is `[]`. A configured list resolves to the raw comma-separated string. On a row with `emptyList: true`, the literal `[]` (`EMPTY_LIST_RE`) is the explicit empty list and resolves `[]`; elsewhere `[]` stays invalid on an element-bearing row, and a blank value reads as unset.
- **`map`** is a block key with no scalar form, so `--values` refuses it. `bin/resolve-policy.js` derives its block-key list from the `type: 'map'` rows. Never restate that list by hand (row 12). A malformed block resolves `null` with `invalid: true`, never a partial map, but only when neither standing source's block parses: since #6006 a malformed `policy.yml` block beside a parsing factory block resolves the factory rows with `source: 'factory'` and `repoInvalid: true`.
- An invalid value resolves to the default with `invalid: true`. `parse-signal-discipline` item 14 covers when that fallback hides a typo from the consumer.

## Gotchas

- **A typo in a block key is invisible to `auditPolicy`**, because `parseFlatLines` drops a key with an empty value. This predates #4609 and also hits `model-profiles` (ledger row 8, deferred). Do not count on the audit to catch a misspelled block key.
- **A block key's resolver and audit must cut comments the same way.** `risk-path-globs` has one parser, `parseRiskPathGlobs`, called by both `resolvePolicyKeys` and `auditPolicy`. `model-profiles` has two readers, `parsePolicyModelConfig` (`model-profiles/policy-fragment.js`) and `extractMapEntry` (`policy-schema.js`). Until #4816 the audit's inline `/#.*$/` left the comment on a CRLF line, since `.` does not match `\r`, so the audit never found a `model-profiles:   # note` block the resolver read. Both now call `policy-fragment.js`'s exported `stripComment`. A new map key reuses one of the two rules rather than writing a third: `stripComment` (a `#` anywhere ends the line) when no value can hold `#`, or `risk-path-globs.js`'s quote-aware rule when one can.
- **Pin each new validation branch with its own assertion.** #4609's `closedQuote` branch had none at first: removing its `isValidValue` call left the suite green (row 6).
- **Changing what an existing value does needs two greps, not one.** Grep the key's kebab-case name across `plugin/skills/`, `docs/journeys/` and `README.md`, then grep its Manifesto display name too: `flow/manifesto-overrides.md`'s Override semantics table names levers that way (`` | Merge verification | `off` | ``), so the kebab-case grep never reaches it. #4550 changed what a derived `merge-verification: off` does; at its base `manifesto-overrides.md` had no `merge-verification` hit, and its stale `off` row and a journey's stale wording were caught only by the final whole-branch review.
- **Setting `policyOnly` on an existing key rewrites claims, not only the flag.** Beyond sites 8 and 9, grep prose that says a run config can set the key. #5830 made `control-mode` `policyOnly` in both directions, dropping the per-run opt-in on purpose; `_shared/autonomy-ceiling.md`'s resolution order still read `control-mode: on (run config or policy.yml)` and a journey still said a run config could turn it on, and review caught both (`5a28b47d9`). Say in the comment above the row that the opt-in is gone.
- **A key joining a family reaches only the callers that list it.** If the family's consumers each spell out the existing keys (a hand-built policy object, a `resolve-policy.js --values` line, a `resolvePolicyKeys` list), a new key is resolved nowhere, and every caller silently runs on its default. Before #5291, every `trustRows` caller passed only `trust-revert-window-days`. Grep every reader of a sibling key, in `plugin/bin/` and in the `node -e` fences under `plugin/skills/`. Then export one key-list constant beside the consumer (`TRUST_POLICY_KEYS` in `plugin/bin/lib/issues/trust.js`), and route each caller through it. A conformance test pins that every caller does (`bin-source-scan-conformance` covers the two-tree scan). The CLI's resolved-key list in `docs/plugin-structure.md` names the keys too.
- **A `map` row resolves nothing from `policy.yml` until `resolvePolicyKeys` has a branch for it.** `parseFlatLines` drops the block's empty-valued header line and skips its indented rows, so a new `type: 'map'` key with no branch of its own resolves its default whatever the file says. Give it one parser, called by a `resolvePolicyKeys` branch and by `auditPolicy`'s invalid-value check, as `risk-path-globs` (`parseRiskPathGlobs`) and `express-driver-models` (`parseDriverModels`, #5917) have. `model-profiles` is the exception: `resolvePolicyKeys` returns the placeholder `{ value: null, source: 'default' }` for it, and only `model-profiles/policy-fragment.js`'s `modelProfilesEntry` reads the block. Any reader that needs the real entry calls it: `bin/resolve-policy.js`, and, since #5917, `express/policy.js`'s `defaultResolvePolicy`, the driver's one policy read. Since #6006 the branch parses both standing sides, `policyRaw` and `factoryRaw`, and merges them through `mergeBlockSides` and `blockEntry` (rows repo over factory, `mergeBlockRows` in `model-profiles/policy-fragment.js`), as both existing branches do; a branch that parses `policyRaw` alone silently ignores the factory layer. A map key also needs an arm in `plugin/bin/lib/policy-factory.js`'s `isMalformedMapBlock` if a variable block that does not parse should yield to a parsing factory file's block; with no arm, the malformed variable block is kept whole and hides the file's. `risk-path-globs` has no arm on purpose: its rows are judged against `risk-categories`, which only the resolver sees.
- **A consumer that builds its own `resolvePolicyKeys` call sees no factory value.** Only `resolvePolicyConfig` (and `bin/resolve-policy.js` through it) and `resolveIntegrationModel` read the factory layer. A consumer that passes `resolvePolicyKeys` only `policyRaw`, or reads through `bin/lib/policy.js`'s `parsePolicy`, resolves the new key as if no factory layer existed (`_shared/policy-schema-read-path.md`'s "Readers outside the layer", #6007). Wire a new key's consumer through `resolvePolicyConfig`, or pass `factoryRaw` from `readFactoryPolicy` called with the caller's `env` and `homeDir`.
- **A key refused by another key's value is refused at the end of its own iteration of `resolvePolicyKeys`' per-key loop, after its source resolution and `policySourceExcluded` check.** `plan-at-specify: on` resolves `off` while `planning-decisions` resolves `ask-all` (#6056). The refusal keeps the key's source, adds a `conflict` field naming the other key, and `bin/resolve-policy.js`'s `warningLines` prints one stderr warning in every output mode, never an error. Read the other key through `firstSourceValue` in `plugin/bin/lib/policy-schema.js` with the same source skips the main loop applies to it (run-config for a `policyOnly` key, the factory source for a refused one), never through `requestedKeys`, whose per-key loop shares no resolved state. Pin the refusal from every source that can set the key (policy and factory), not only `policyRaw`.
- **A consumer that reads `policy.yml` itself finds the file through `locatePolicyFile`.** Call `plugin/bin/lib/policy-file.js`'s `locatePolicyFile(root).path`, never `path.join(root, '.claude-tweaks', 'policy.yml')`. A project that gitignores the file has no copy in a linked worktree, and the locator falls back to the main checkout's file (#4492). A hand-joined path reads no policy there, and every key silently runs on its default. No test pins that a reader routes through the locator, so grep for the constant-held form too: #4492's sweep missed `candidates-agent-trust-scope.js` because it joined a `POLICY_REL` constant, and review found it (`87de255b0`). `plugin/bin/lib/hooks/pre-tool-use.js`'s `POLICY_FILE` matches write targets and reads nothing, so it stays.
