# pre-tool-use.js gate-exemption authoring

`plugin/bin/lib/hooks/pre-tool-use.js` carries a whole family of scoping exemptions on its deny gates — `isPipelineBookkeeping`, `isPolicyFile`/`realTarget`, `isPolicyOnlyCommit`, `isDeleteOnlyPush`, `isStampsGateExemptTarget`, the Bash foreign-repos branch, and `checkBookkeepingStampsGate`'s file-tool foreign-target branch (#1678). Every one of them obeys the same discipline, documented nowhere as a single list before this file — record #1678 reproduced two of these rules' violations in one function in one review pass (`[IL-149]`, `[IL-150]`), which is the evidence this gap was real.

## The discipline

- **Absolute-path-only guard.** A relative path resolves against the *hook process's own cwd* (`repoInfo`'s internal `path.resolve`), not the calling session's `ctx.cwd` — never provable, so it must fall through unchanged, exactly like an indeterminate answer. Check `path.isAbsolute(...)` before doing anything else with a caller-supplied path.

- **Resolve the leaf symlink before deciding — route through `resolveLeaf()`.** A path-based ALLOW/exemption decided on the raw literal target path can be defeated by a symlink located outside the check's scope whose target resolves inside it (or vice versa) — `[IL-150]`. `realTarget()` (near the top of this file) is the gate-side helper, and it routes through `plugin/bin/lib/path-guard`'s `resolveLeaf()` on its `.native` default, like every other new exemption, so both sides of `isPolicyFile`'s equality resolve alike: it follows every symlink including the leaf when something exists there, and falls back to a parent-only resolution (keeping the literal basename) for a genuinely new path with nothing at the leaf yet — never treating an *existing-but-unresolvable* (dangling) symlink as "doesn't exist yet." A new exemption calls `resolveLeaf()` (or `realTarget()`) rather than replicating that three-way shape (resolved / dangling-and-unprovable / new-file-passthrough), and keeps the module's `fs.realpathSync.native` default when it compares the resolved path against a root or an exclusion — the JS form echoes the input's casing on a case-insensitive volume (see the Anti-Patterns row) — don't call `wtDetect.repoInfo()` or any other path-answering function on a literal path without first asking whether the leaf is a symlink.

- **Every unprovable answer fails CLOSED, and a conclusive exemption is never gated on an unrelated inconclusive one.** `wtDetect.repoInfo()`/`mainCheckoutRoot()` return `indeterminate: true` or `null` when the question genuinely went unanswered (a timeout, an EACCES/ELOOP/EIO stat, an unreadable `.git` file) — that is a *different fact* from a definitive negative answer, and must never be read as "not a repo" or "different repo." The subtler failure mode, from `[IL-149]`: don't nest a value's already-conclusive exemption inside a check on a *different, unrelated* value's resolution succeeding. `if (mainRoot) { if (!targetRoot) return {}; }` denies a target `repoInfo` already proved has no repo root at all, on a transient failure of the unrelated `mainRoot` lookup — hoist the conclusive check out so it fires unconditionally on its own evidence. See `docs/donts.md`'s `[IL-83]` for the sibling rule about ordering an exemption after an early return that can claim the same value.

- **A Bash-shaped exemption matches the ENTIRE command string against a grammar** — no extra flag, no shell operator, no env-var prefix slipping past a substring match. Prove the staged set with `git diff --name-status`, never `--name-only` — a rename into the target collapses to one `--name-only` line and hides that a second file also changed.

- **A containment check calls `shared-primitives.js`'s `isPathContained(candidate, root, { orEqual })` — never a retyped `startsWith(root + path.sep)` or a bare `path.relative`-derived `startsWith('..')`.** #3642 removed the `startsWith('..')` copies, which treated a child named `..foo` as outside its root, and the conformance scan now fails on any new one. It also fails on the `startsWith(root + path.sep)` idiom written through a variable (`startsWith(<identifier bound to a path.sep expression>)`, #3892, which routed the two copies that scan found, in `hooks/sweep-shadow.js` and `timing/transcript.js`, through `isPathContained`); the one exception is `visual-decide/server.js`, which keeps a builtins-only whole-segment copy (`rel.split(path.sep)[0] === '..'`) because #1202 AC 8 bars non-builtin imports there. And `plugin/bin/lib/path-guard`'s `isAncestorOrSelf()` is the one helper new containment code calls, via `isPathContained` (admits equality, tests the `..` path segment so a child named `..foo` is contained, takes a `pathImpl` for win32); `isPathContained` is its thin wrapper, default strict (the root itself is excluded), `orEqual` opts equality in. Both of this file's containment-shaped exemptions route through it: `isPipelineBookkeeping` (strict) and `checkTeardownGate`'s own-cwd refusal (`orEqual: true`). #2324's review found the idiom independently retyped in six places — `reconcile/reap-merged.js`, `hooks/worktree-reap.js`, `timing/transcript.js`, and this file's two sites — each copy free to drop the `+ path.sep` (making `/repo/.claude-tweaks-evil` match inside `/repo/.claude-tweaks`) or the equals branch. Pass absolute, already-resolved paths in: it is pure path arithmetic (`path.relative`), never a filesystem call, so a relative argument resolves against `process.cwd()` rather than failing closed and a null argument throws — and it does not substitute for the symlink resolution the `realTarget()` bullet above requires. When the decision is on resolved filesystem paths (an existing read target, or a write's existing parent directory), `plugin/bin/lib/path-guard`'s `resolveWithin()` is the one to reach for.

- **Every new exemption needs a regression test proven to go red on revert.** Write the test, revert only the code fix (`git checkout -- {file}` on that one file, not `git stash`), confirm the new test — and only the new test — fails, then restore the fix. A green suite alone is not evidence the test discriminates. On a case-insensitive fake, a positive "allow" case passes trivially under a revert to the real-fs `realpathSync` (the fake's paths do not exist on disk, so the old code resolves to null and fails open): pair every mis-cased allow with a mis-cased deny, and revert to a fake-aware JS-form `realpathSync` as well, since that echo-form revert is what turns the allow cases red (#3682, `tests/bin-lib/path-guard/pre-tool-use-identity.test.js`).

- **Widening what a gate accepts as logged evidence is a loosening of the gate, so it gets the same discipline as a new exemption.** #3012 made `checkBookkeepingStampsGate` accept a model-worded claim line (`claim-log.js`'s `paraphrasedClaimNumbers`) and a model-worded PR-early Step 1 line (`hasPrEarlyStep1LineFor`) beside the exact formats. What it took, in order: keep the exact-format match first, so everything accepted before is still accepted; count only the text before the `Reversibility:` suffix; require the line to name the step (or the whole-token identifier) before a bare number or branch counts, with `#7` never matching `#700`; reject `FAILED`/`contested` lines whole; and reject negated, hypothetical and other-actor wording (`never`, `would`, `should`, `another`, `sibling` within two words before the verb), because the final review found `would have claimed #N` and `another run claimed #N first` passing. Then calibrate the matcher against the real archive (every `.claude-tweaks/pipelines/archive/*/decisions.md`: the count it accepts, and zero lines it should not), and give each rejection class its own test. A phrase the matcher misses denies, which is the safe direction; a phrase it accepts that did not record the event silently skips the stamp, so tighten toward misses.

- **Not every exemption is decidable from the command grammar alone — some need a live query.** Every exemption above this line is a pure string match: the command text alone proves the exemption holds. `isIntegrationBranchFastForwardPush` (#2542) is the first exemption of a second shape — a fast-forward is a fact about ref state, not something the command text can prove, so the grammar match (`git push <remote> <branch>`, nothing else) is only step one; the exemption still requires a live `git merge-base --is-ancestor` query against the resolved integration branch before it can return true. Keep the two steps in that order and don't let the grammar match alone stand in for the live check — a syntactically-clean fast-forward-shaped command is not evidence of an actual fast-forward.

- **Choose the run a deny reads before writing its first condition — `ctx.runDir` and `ctx.ownedRun` answer different questions.** `bin/hooks.js` hands every gate both (`docs/hooks.md`'s "Two resolutions, not one"): `ctx.runDir` is `resolveRunDir(cwd, process.env)` with no session id — the newest non-terminal run, whoever owns it — while `ctx.ownedRun` is `resolveRun(cwd, process.env, input.session_id, { strictAttribution: true })`, scoped to the calling session and its worktree binding — strict since #3515, so its fallback guess also skips a run bound to any worktree other than the caller's (a main-checkout caller included), while `ctx.runDir` stays non-strict so E1 can still name one. E1 and `checkBookkeepingStampsGate` read `ctx.runDir` on purpose: their subject is the run assigned to *this checkout*, and they downgrade a provably foreign owner to warn + allow. A deny whose condition is a fact about *the caller's own run* — a marker in its `run-state.json`, a file its run dir must hold — reads `ctx.ownedRun.dir` instead and then requires `ctxLib.classifyOwnership({ sessionId, cwd }, state, { fsImpl: deps.fsImpl }) === 'mine'` (the third argument, since #3836, makes the ownership check read the same injected volume as the gate's other comparisons — see the `fsImpl` Anti-Patterns row), because `resolveRun` also returns an ownership-`'indeterminate'` run with `session` attribution and an unowned `fallback` guess. `checkDispatchConfigGate` (#3225) is the shipped instance: its premise probe measured `ctx.runDir` naming an unrelated, newer sibling run from inside a correctly bound worktree, from both the dispatching session and its Task subagent. Log that deny's event to `ctx.ownedRun.dir` with `ctx.ownedRun.attribution`, and test it with a `ctx` whose `runDir` names a different run than `ownedRun` (`tests/hooks-pre-tool-use.test.js`'s "keys on ctx.ownedRun, not ctx.runDir" case) — a fixture where the two coincide cannot tell them apart. **An allow-path breadcrumb is a write too, and it inherits the resolution of the run it is logged against.** `checkBookkeepingStampsGate`'s `gate-exempt-gitignored` event logs against `ctx.runDir` on purpose (its "#1431 audit" comment), and that was the #3401 incident's write: a sibling worktree's gitignored `Write` landed in a newer claim-log-only mint. #3515 therefore made the claim-log-only mint skip apply to every fallback resolution, not just the strict one, because a guard on `ctx.ownedRun` alone would have left that write site untouched. A fix to how either run resolves is proven only by a regression test that fires the very gate whose write misattributed — `tests/hooks-run-attribution.test.js`'s "#3515 incident e2e" case spawns `hooks.js pre-tool-use` on a real `Write` — not by a `resolveRun` unit case alone.

- **An exemption keyed on the run dir's KIND must call `context.js`'s `isAdHocRunDir`, and each gate must state which way ignoring that kind moves its verdict.** #2783 added the first exemptions keyed on what kind of run directory a value is, rather than on a path or the command text. `checkTeardownGate` looks up the target's run with `findRunByWorktreePath(…, { skipAdHoc: true })`, and `hasDistinctOwnedRun` returns false for an owned `-adhoc-standalone` dir. An ad-hoc dir holds only friction events and is minted for nearly every session, so it is never a pipeline assignment. The same exclusion pushes the two gates opposite ways. In the teardown gate it allows the removal, because an ad-hoc dir never makes a worktree "assigned". In `hasDistinctOwnedRun` it keeps the IL-131 record-worktree deny from being downgraded to a warn. So write down the direction for each gate and pin it with a test (`tests/teardown-gate.test.js` and `tests/hooks-bookkeeping-stamps-gate.test.js` carry the two today). The kind is decided by the basename suffix alone, and only `stampAdHocRunDir` (`post-tool-use.js`) and `stampAdHocRunDirForDenial` (`context.js`) mint it. Call the shared predicate rather than retyping the suffix test.

- **A deny on a call that skill prose prescribes fails OPEN on every unprovable answer, and the same change sweeps every prose route into that call.** The fail-CLOSED bullet above governs exemptions, which are narrow allows carved out of a gate that otherwise denies. A deny whose own condition is the narrow case runs the other way: `checkDispatchConfigGate` already returns `{}` on an `indeterminate` `repoInfo`, and `checkReviewConsoleAskGate` (#3712, `[IL-167]`) is the first deny keyed on a non-Bash tool's input field (`AskUserQuestion`'s `tool_input.questions[].header`). The call it blocks is the human's own stop, so a wrong deny strands the run, while a wrong allow only falls back to the stall the gate exists to stop. It returns `{}` on no owned run, `fallback` attribution, an ad-hoc dir, any `classifyOwnership` verdict other than `'mine'`, a malformed `questions`, and a ceiling read that throws (a git failure throws there rather than letting `resolvePolicyConfig` guess `process.cwd()`), and it denies only when every one of those is proven. State the direction in the gate's header comment and give each fail-open condition its own test in `tests/hooks-pre-tool-use.test.js`. Then, because shipped prose tells the model to make the denied call, grep `plugin/skills/` for every route that reaches it (the call with the keyed field, and every link into the section that makes it) and either reroute or pin each one in the same change. #3712's build missed `wrap-up/review-console.md`'s exit-5 line, which still sent `console-resolve.js` exit 5 to "Present a real stop" (an ask the new gate denies) until review rerouted it. `tests/console-resolve-conformance.test.js` now pins that reroute, and `tests/review-console-header-conformance.test.js` pins the keyed header against both console prompts. A tool no existing PreToolUse matcher routes also needs its own `plugin/hooks/hooks.json` entry, pinned by a `tests/hooks-dispatcher.test.js` matcher case.

## Existing coverage, checked

`gh-api-module-pattern` governs the `run(argv, deps)`/`execFileSync` seam elsewhere in `plugin/bin/lib/` — not this file's deny-gate exemptions, which call `wtDetect` directly (no injectable seam beyond `run(ctx, deps)`'s test-only bag: `resolveIntegrationModel`, and since #3682 `fsImpl` and `toplevel`, which let a case-insensitive fake stand in for the volume). Nothing else in `.claude/skills/` touches hooks.

**A fail-open sibling exists and is not covered by this skill's discipline.** `plugin/bin/lib/pr-bookkeeping/precondition.js`'s `checkPrBookkeepingPrecondition` (#2472) reuses `pre-tool-use.js`'s exported `hasMaterializeCommit`/`hasLoggedPrDegrade`/`resolveRunPinnedIntegrationModel` and the same `isLinkedWorktree`/`indeterminate` scoping pattern this skill documents — but it is a benefit-of-the-doubt *precondition* check, not a deny gate, and deliberately inverts the posture: ambiguity resolves to `{ok: true}` (proceed) rather than fail-closed. Do not apply this skill's "every unprovable answer fails CLOSED" rule to that file — it is a correct, intentional divergence, not an instance of the anti-pattern this skill exists to catch.

**A CLI that makes a gated call itself is invisible to this hook, so it re-applies the gate's release conditions in its own code.** A PreToolUse hook sees only the tool call (`node …/phase-exit.js …`), never the `git push` that process spawns through `execFileSync`. `plugin/bin/lib/phase-exit/phase-exit.js`'s `prPushReleased` (#4026) therefore applies `checkBookkeepingStampsGate`'s no-PR release rules to its own push. It imports `hasLoggedPrDegrade`, `hasLoggedPrEarlyStep1` and `hasNoUpstreamYet` from this file's exports rather than reimplementing them, and it keeps the gate's posture: a throw from `hasNoUpstreamYet` counts as not released, so the push is skipped. Each side carries a comment naming the other (here, the one above the `!runState.pr` branch). A change to that branch's release conditions changes `prPushReleased` in the same commit, and a new CLI that makes a gated call itself copies this shape.

## Anti-Patterns

| Pattern | Why It Fails |
|---|---|
| Calling `repoInfo()`/any path-answering function on a literal path without checking for a leaf symlink first | The exact bypass `[IL-150]` names — a symlink outside the check's intended scope can point anywhere |
| Comparing `fs.realpathSync` output against a root or an exclusion (`===`, `path.relative`, `isPathContained`) | On a case-insensitive volume the JS `realpathSync` echoes the input's casing, while `fs.realpathSync.native` returns the canonical case, so a mis-cased path slips past the comparison. #3380's home exclusion in `plugin/bin/lib/superpowers-version.js` did, and PR #3406 (squash-merged as `ffe20b982`) switched it to `.native`. #3495 moved both sides of `isPolicyFile`'s equality to `plugin/bin/lib/path-guard`'s `.native` resolvers (`resolveLeaf()` / `canonicalRealpath()`); #3682 moved the E1/worktree-identity comparisons and the teardown gate's own-cwd containment to `canonicalRealpath()` too, so every resolved-path comparison made in `pre-tool-use.js` itself resolves through path-guard (every worktree lookup it delegates to `context.js` now does too: `findRunByWorktreePath` since #3769, `classifyOwnership`, `findRunsByWorktreePath` and `resolveRun`'s strict-attribution `isOtherWorktreeBound` since #3836; that file's remaining JS-form `realpathSync` sites compare run-dir paths only, as the `lib/hooks/context.js` reason in `tests/path-guard-conformance.test.js`'s ALLOWLIST records); a new exemption that compares resolved paths does the same, resolving both sides through `canonicalRealpath()` / `resolveLeaf()` and never the JS `fs.realpathSync` or `worktree-detect`'s JS-form `safeReal` — a new bare `realpathSync` token in this file also fails `tests/path-guard-conformance.test.js` until that file's exact-count ALLOWLIST entry is updated. Changing the form `realTarget()` returns also changes what every other caller compares it against — enumerate them and read each comparison's other operand (#3495 found `shadowPipelineRunDir` comparing the new `.native` result against a JS-form repo root, a fail-open flip the plan had called fail-safe) |
| Nesting a conclusive exemption's `return {}` inside a check on an unrelated value | A transient failure of the unrelated check denies a target already proven out of scope — `[IL-149]` |
| Treating `mainCheckoutRoot() === null` as "different repo" | `null` also means "the answer is unknown" (EACCES/ELOOP/EIO, unreadable `.git`) — only a resolved-AND-different root exempts |
| Proving a Bash exemption's staged set with `git diff --name-only` | A rename into the target collapses to one line and hides a second changed file — use `--name-status` |
| Retyping `candidate.startsWith(root + path.sep)` or `path.relative(…).startsWith('..')` instead of calling `isPathContained` | Six independent copies existed before #2324; a copy silently drops the separator (a prefix sibling then matches) or the `orEqual` branch, and the `startsWith('..')` form (copies removed by #3642) rejects a child named `..foo` — `tests/path-containment-conformance.test.js` fails either (only `visual-decide/server.js` is exempt, #1202 AC 8) |
| Shipping a new exemption with no regression test proven to fail on revert | A green suite alone proves nothing about whether the new test actually discriminates |
| Paraphrasing the gate's exemptions in skill prose, even beside a citation of `_shared/policy-schema-coverage.md`'s gate-coverage block | #2727 cited the block yet wrote "an untracked or gitignored path the gate exempts"; untracked-not-ignored is the branch this file deliberately reverted (#1395) |
| Keying a deny about the caller's own run on `ctx.runDir` | `ctx.runDir` carries no session id and names the newest non-terminal run — #3225's probe measured it naming an unrelated sibling run from inside a bound worktree; read `ctx.ownedRun` and require `classifyOwnership === 'mine'` |
| Retyping `path.basename(dir).endsWith('-adhoc-standalone')` instead of calling `isAdHocRunDir` or passing `{ skipAdHoc: true }` to `findRunByWorktreePath` | Each copy is one more place a change to the ad-hoc naming must find; `archive-merged.js` carried one until #2783 |
| Threading `deps.fsImpl` into some of a helper's filesystem calls but leaving another on the real `fs` | The un-threaded call answers from the real disk while its operands came from the fake, so the helper mixes two filesystems and no existing test notices. #3769's review found `shadowPipelineRunDir`'s existence `statSync` on the real `fs` beside a comment saying every operand used `fsImpl`. Revert each call's `fsImpl` in turn and require each revert to turn a test red |
| A new gate returning a non-deny `hookSpecificOutput` (`ask`, `additionalContext`, an `allow`) | `run()` hands every outcome to `withGuardRewrite`, which skips the guard normalizer's `updatedInput` whenever a `hookSpecificOutput` is already present (#4028; today only `denyResult` sets one). Such a gate silently turns off the rewrite for every Bash call it answers, and the harness worktree guard then refuses shapes the normalizer would have respelled. Keep a non-deny note in `systemMessage`, or merge the rewrite into the gate's output and test both fields |
