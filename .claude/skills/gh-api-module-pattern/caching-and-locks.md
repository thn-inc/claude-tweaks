## Caching and locks on the seam

Lazy-loaded from `SKILL.md`: read it before adding a memo on the seam, caching a failure or a verdict, or holding `file-lock.js` across a long call.

- **A memoizing *decorator* on the seam is itself a runner — and it must be write-aware whenever its call graph reads back its own writes.** `plugin/bin/lib/reconcile/issue-list-cache.js`'s `createIssueListCache({base})` (#2505) returns `{runner}` on exactly the argv→stdout contract above, so it drops in wherever a `runner` is already injected — `escalate-residue.js` needed no change at all — and `reconcile/index.js` creates **one instance per `reconcile()` pass**, threading it through `archiveMerged`/`reapMerged` into `cache.js`'s `trackResidue`/`pruneResidueFailures`. Per-pass, never a module-level singleton: `reconcile()` is called in-process from `hooks/session-start.js` as well as from `bin/hooks.js reconcile`, so a module-scope memo would serve a later pass a read taken during an earlier one. The hazard that decides the memo's *shape* is read-after-write on the same seam: those callers also write through that runner (`issue create`/`edit`/`close`/`reopen`) and read back within the pass — `escalate-residue.js`'s `structurally-stuck` fingerprint is deliberately path-less, so every stuck dir in a pass converges on the same consolidated record and each read depends on the previous write. Memoizing the raw response string would file N separate issues instead of one (regressing #1811-#1817's original symptom) and let a resolve loop resurrect paths it just removed, so the record never closes. Memoize the **parsed** value and apply each write's effect to it in place — same correctness as invalidating on every write, at zero extra round trips. Three rules keep that honest: only the exact read shape is memoized (`argv[0] === 'issue' && argv[1] === 'list'`) and every other call executes; a throw or an unparseable response is never cached, so the next call retries rather than replaying a failure; and the write-effect applier encodes *this* call graph's write vocabulary (a verb it doesn't know is a deliberate no-op, never a throw and never an invalidation), which is only defensible while the decorator has one caller — say so in the module header, as `issue-list-cache.js` does. Pin it with a stateful fake `base` that counts calls and asserts both the count and that a read after a write reflects the write (`tests/bin-lib/reconcile/issue-list-cache.test.js`), plus a two-instance test proving no cross-pass sharing.
- **A decorator that invalidates by classifying each call, instead of applying each write's effect, discards on any call it does not recognize.** `plugin/bin/lib/learned-skills/learned-skills.js`'s `withReadCache(deps, target)` (#5790) is created inside one `capture()` call and dies with it. It answers a repeated `diff`, `status` or `hash-object` without `-w` from memory, passes `apply --check`, `rev-parse` and `cat-file` through uncached, and clears every kept answer before any other git call runs and before any call carrying `opts.env`. This is the reverse of the effect applier's rule above: an applier must know a write to replay it, so an unknown verb is a no-op there, while here an unknown call is presumed to change state. Derive the classification and the key from git's own argument grammar, not from the calls the caller makes today. (1) The subcommand is the first argument after the leading `-C <dir>`, `-c <k=v>` and `--no-optional-locks`, and its option scan stops at the first `--` or `--end-of-options`: `apply -- --check` names a path called `--check` and must discard, and `hash-object --stdin -- -w` is a read. (2) The key is the argv plus every per-call input that changes the answer: the encoding with an omitted one normalized to the runner's default, the resolved `cwd`, and a hash of the stdin `input`. (3) Git's answer about the working tree also changes when the file changes, so the decorator wraps the fs seams as well: an `unlink`, `writeFile`, `writeFileExclusive` or `rename` (either side) naming the target, or an `rmdir` of the target or a directory above it, discards first. (4) Only a successful answer is kept, and a Buffer is kept and returned as a copy, so no caller sees another's mutation. Its comment names the accepted limit: one writer in the worktree during the call. `headShortReader` in the same file is the single-question form: one reader per `land()` or `stage()` call memoizes only a non-empty `rev-parse --short HEAD`, and a throw or an empty answer is asked again. Pin each rule with a fake git that returns a fresh answer per call and counts argv (the `withReadCache` cases in `tests/bin-lib/learned-skills/capture.test.js`, the HEAD-read cases at the end of `tests/bin-lib/learned-skills/land.test.js`).
- **Caching a *failure* is the exception to "a throw is never cached": a cached failure that outlives the process needs an exact timeout check plus a TTL; one memoized inside a single invocation whose callers all fail open the same way needs neither.** For a cheap call, retrying is the recovery. For a long-bound remote call, every later caller would re-pay the full timeout, so remembering it is the fix. `plugin/bin/lib/docs-health/commit-ref.js`'s `deepenShallowClone` (#2988) writes a timeout marker with a 30-minute `TIMEOUT_MARKER_TTL_MS` after its 120s `fetch --unshallow` times out. The marker is a file in the git-common dir, not an in-process memo, because `docs-health --budget > 1` runs `verify-commit` as a separate process for each citation. Its `isTimeoutError` is `err.code === 'ETIMEDOUT'` alone, not the three-way check `async-fan-out.md`'s `retryOnTimeout` bullet documents. When `execFileSync`'s own `timeout` fires, the error carries `{code: 'ETIMEDOUT', signal: 'SIGTERM'}`. A git killed from outside carries the same `signal: 'SIGTERM'` with no `code` (probed on Node 22). `err.signal === 'SIGTERM'` would therefore record that crash as a timeout and block every retry for the whole TTL. Choose the check by which mistake is cheap. For a retry, a false positive costs one extra attempt, so the broad check is fine. For a cached failure, missing a real timeout costs one extra attempt, and a false positive blocks recovery, so use the exact code. The in-process form is `plugin/bin/lib/claim-targets/claim-targets.js`'s `cachedPrReadGh` (#4423): it memoizes every PR read for one `run()` call, thrown failures included, and re-throws the cached error on each hit. Both callers (`tombstoneInFlightPr`, `staleClaimInFlightPr`) fail open per target, so a replayed failure gives the answer a retry would most likely give, and a hanging `gh pr list` costs one timeout per run instead of one per stale target. The memo dies with the invocation, which stands in for the TTL. Pin it with a throwing fake `gh` that counts calls across two targets sharing one read (`tests/bin-lib/claim-targets/claim-targets.test.js`'s `(stale-pr-4c)` case). The run-state form is `resolveRunPinnedIntegrationModel`'s opt-in degrade memo (#4830, `plugin/bin/lib/hooks/pre-tool-use.js`): it stamps `forgeDegradedAt` in `run-state.json` for `FORGE_DEGRADE_MEMO_TTL_MS`, reads the stamp only after an explicit pin has been ruled out, clears it on the next clean detection rather than waiting for expiry, and treats the stamp as untrusted input — a non-finite or future stamp counts as stale (`0 <= now - at < ttl`), so a clock step can never suppress the probe for good; `isFreshForgeDegradeMemo` and its table test in `tests/hooks-pre-tool-use-forge-memo.test.js` pin that rule.
- **Starting to cache a verdict reopens the timeout check its producer chose for a retry.** The bullet above picks the check by which mistake is cheap, and that answer changes when a caller begins remembering a verdict that was only ever used to decide a retry. #4830's run-scoped degrade memo (`resolveRunPinnedIntegrationModel` in `plugin/bin/lib/hooks/pre-tool-use.js`) stamps `forgeDegradedAt` on every degrade `policy-schema.js`'s `detectIntegrationModel` reports. That function counts any signal-killed `gh` as a timeout (`err.code === 'ETIMEDOUT' || err.signal`), deliberately broader than `isTimeoutError` (#4578), because there a false positive bought one extra attempt. Cached, the same false positive (a `gh` killed from outside on both attempts) now skips the probe for one `FORGE_DEGRADE_MEMO_TTL_MS` (60 s). That is tolerable only because the TTL is short and the memoized answer is the gate's fail-open `local-merge`, and neither #4830's spec nor its plan weighed it. A longer TTL, or a memo whose cached answer denies, needs the exact `ETIMEDOUT` check — and the degrade object passed to `onDegrade` carries only `reason`/`timeoutMs`/`attempts`, not the error code, so the producer must expose it before the caller can filter on it. When you add a memo over an existing classifier, re-run the cheap-mistake choice in the same change.
- **`file-lock.js`'s wait is sized for bookkeeping, so a lock held across a long call needs a wait longer than that call's bound, or it serializes nothing.** `acquireLock` gives up after `CLAUDE_TWEAKS_LOCK_WAIT_MS` (500ms by default) and returns `null`, and its callers then proceed unlocked. That is right for a read-modify-write that takes milliseconds. For a critical section bounded at N ms it means every waiter falls through after half a second and races the holder, which is exactly the concurrency the lock was added to stop, and nothing reports it. `commit-ref.js`'s `deepenShallowClone` (#2988) holds its lock across the 120s `--unshallow` fetch, so it waits `DEEPEN_TIMEOUT_MS + LOCK_WAIT_MARGIN_MS`. The 15s margin keeps a waiter's deadline from landing just before the holder's fetch finishes. `acquireLock`/`withLock` take a per-call `waitMs` option, and `commit-ref.js` passes it by value to its one `acquireLock` call (through an injectable `lock`), so it never writes the env var. Do not set `CLAUDE_TWEAKS_LOCK_WAIT_MS` around a lock call: that env var is the test-only knob, and a long-hold caller passes `waitMs`. A test of which wait a call honoured reads it off a stubbed `Date.now` that advances a fixed step per read, measured from the first read (the one that sets the deadline), never off elapsed real time: a `>= 120` ms or `< 100` ms bound, as #5381's plan first prescribed, is a wall-clock budget that `tests/wall-clock-budget-conformance.test.js` fails. `acquireOnVirtualClock` in `tests/bin-lib/file-lock.test.js` is the helper to copy. A caller's own test only needs a counting `lock` fake that records the `waitMs` it was passed. Put the lock in the repo's real git dir, never at `path.join(root, '.git', …)`. In a linked worktree `.git` is a file, so `mkdirSync` there throws `ENOTDIR` and `acquireLock` silently fails open. Resolve the dir with `git rev-parse --git-common-dir`, then `path.resolve(root, out)`, because the output can be relative. Skip `--path-format=absolute`: it needs git 2.31 or later, and no sibling module uses it. Every worktree of the repo shares that dir, which is also where git keeps its own `shallow.lock`.
- **`cli-wrapper-contract.md`'s "reuse `withLock` rather than hand-rolling a second mutex" holds unless a claim needs something `file-lock.js` cannot give.** There are four such needs, and `plugin/bin/lib/reconcile/post-merge.js`'s run claim (#4797) has all of them. (a) A takeover that only one taker wins: `acquireLock` reclaims a dead lock with `rmSync` and then `mkdirSync`, so two reclaimers of one dead lock can both win. (b) A take that does not block and reports why it failed: `acquireLock` polls for up to its wait (500ms unless `CLAUDE_TWEAKS_LOCK_WAIT_MS` is set) and returns `null` both for "held" and for an I/O error, while the reconciler needs an immediate answer with separate `in-flight` and `claim-failed` reasons. (c) Compatibility with a lock file older builds already use: installed reconcilers create and respect `.post-merge.lock` as a plain empty file, and `file-lock.js`'s directory lock reclaims any lock with no owner file after 5 s (`LOCK_STALE_MS`), so it would take a live old claim. (d) A long hold that readers judge by age: `file-lock.js` has no way to refresh a held lock, while older reconcilers take over a claim idle past `CLAIM_STALE_MS` and the current one stops trusting an idle claim after `CLAIM_MAX_IDLE_MS`. `takeClaim` creates the claim file exclusively (`'wx'`) with the token `{pid}-{random}`. To take over a stale claim it renames the file aside, judges the aside again, and links a live aside back. `heartbeatClaim` refreshes the mtime before every `gh` call, and `releaseClaim` deletes the claim only when it still holds the caller's token. The comment above `takeClaim` lists (a)-(d). A claim that needs none of the four uses `withLock`. A new hand-rolled claim lists the needs it has in a comment above its take function and imports `file-lock.js`'s `isAlive` instead of writing a second pid probe.
- **A memo over git's own answer, validated by a filesystem signature, is a different shape from the runner decorators above.** Its correctness is the completeness of the signature, so derive the signature from what git reads, per `git-ground-truth-test-env`'s "what git reads" section (`plugin/bin/lib/hooks/repo-info-cache.js`, #5294).
