## Caching and locks on the seam

Lazy-loaded from `SKILL.md`: read it before adding a memo on the seam, caching a failure or a verdict, or holding `file-lock.js` across a long call.

- **A memoizing *decorator* on the seam is itself a runner — and it must be write-aware whenever its call graph reads back its own writes.** `plugin/bin/lib/reconcile/issue-list-cache.js`'s `createIssueListCache({base})` (#2505) returns `{runner}` on exactly the argv→stdout contract above, so it drops in wherever a `runner` is already injected — `escalate-residue.js` needed no change at all — and `reconcile/index.js` creates **one instance per `reconcile()` pass**, threading it through `archiveMerged`/`reapMerged` into `cache.js`'s `trackResidue`/`pruneResidueFailures`. Per-pass, never a module-level singleton: `reconcile()` is called in-process from `hooks/session-start.js` as well as from `bin/hooks.js reconcile`, so a module-scope memo would serve a later pass a read taken during an earlier one. The hazard that decides the memo's *shape* is read-after-write on the same seam: those callers also write through that runner (`issue create`/`edit`/`close`/`reopen`) and read back within the pass — `escalate-residue.js`'s `structurally-stuck` fingerprint is deliberately path-less, so every stuck dir in a pass converges on the same consolidated record and each read depends on the previous write. Memoizing the raw response string would file N separate issues instead of one (regressing #1811-#1817's original symptom) and let a resolve loop resurrect paths it just removed, so the record never closes. Memoize the **parsed** value and apply each write's effect to it in place — same correctness as invalidating on every write, at zero extra round trips. Three rules keep that honest: only the exact read shape is memoized (`argv[0] === 'issue' && argv[1] === 'list'`) and every other call executes; a throw or an unparseable response is never cached, so the next call retries rather than replaying a failure; and the write-effect applier encodes *this* call graph's write vocabulary (a verb it doesn't know is a deliberate no-op, never a throw and never an invalidation), which is only defensible while the decorator has one caller — say so in the module header, as `issue-list-cache.js` does. Pin it with a stateful fake `base` that counts calls and asserts both the count and that a read after a write reflects the write (`tests/bin-lib/reconcile/issue-list-cache.test.js`), plus a two-instance test proving no cross-pass sharing.
- **Caching a *failure* is the exception to "a throw is never cached": a cached failure that outlives the process needs an exact timeout check plus a TTL; one memoized inside a single invocation whose callers all fail open the same way needs neither.** For a cheap call, retrying is the recovery. For a long-bound remote call, every later caller would re-pay the full timeout, so remembering it is the fix. `plugin/bin/lib/docs-health/commit-ref.js`'s `deepenShallowClone` (#2988) writes a timeout marker with a 30-minute `TIMEOUT_MARKER_TTL_MS` after its 120s `fetch --unshallow` times out. The marker is a file in the git-common dir, not an in-process memo, because `docs-health --budget > 1` runs `verify-commit` as a separate process for each citation. Its `isTimeoutError` is `err.code === 'ETIMEDOUT'` alone, not the three-way check `async-fan-out.md`'s `retryOnTimeout` bullet documents. When `execFileSync`'s own `timeout` fires, the error carries `{code: 'ETIMEDOUT', signal: 'SIGTERM'}`. A git killed from outside carries the same `signal: 'SIGTERM'` with no `code` (probed on Node 22). `err.signal === 'SIGTERM'` would therefore record that crash as a timeout and block every retry for the whole TTL. Choose the check by which mistake is cheap. For a retry, a false positive costs one extra attempt, so the broad check is fine. For a cached failure, missing a real timeout costs one extra attempt, and a false positive blocks recovery, so use the exact code. The in-process form is `plugin/bin/lib/claim-targets/claim-targets.js`'s `cachedPrReadGh` (#4423): it memoizes every PR read for one `run()` call, thrown failures included, and re-throws the cached error on each hit. Both callers (`tombstoneInFlightPr`, `staleClaimInFlightPr`) fail open per target, so a replayed failure gives the answer a retry would most likely give, and a hanging `gh pr list` costs one timeout per run instead of one per stale target. The memo dies with the invocation, which stands in for the TTL. Pin it with a throwing fake `gh` that counts calls across two targets sharing one read (`tests/bin-lib/claim-targets/claim-targets.test.js`'s `(stale-pr-4c)` case). The run-state form is `resolveRunPinnedIntegrationModel`'s opt-in degrade memo (#4830, `plugin/bin/lib/hooks/pre-tool-use.js`): it stamps `forgeDegradedAt` in `run-state.json` for `FORGE_DEGRADE_MEMO_TTL_MS`, reads the stamp only after an explicit pin has been ruled out, clears it on the next clean detection rather than waiting for expiry, and treats the stamp as untrusted input — a non-finite or future stamp counts as stale (`0 <= now - at < ttl`), so a clock step can never suppress the probe for good; `isFreshForgeDegradeMemo` and its table test in `tests/hooks-pre-tool-use.test.js` pin that rule.
- **Starting to cache a verdict reopens the timeout check its producer chose for a retry.** The bullet above picks the check by which mistake is cheap, and that answer changes when a caller begins remembering a verdict that was only ever used to decide a retry. #4830's run-scoped degrade memo (`resolveRunPinnedIntegrationModel` in `plugin/bin/lib/hooks/pre-tool-use.js`) stamps `forgeDegradedAt` on every degrade `policy-schema.js`'s `detectIntegrationModel` reports. That function counts any signal-killed `gh` as a timeout (`err.code === 'ETIMEDOUT' || err.signal`), deliberately broader than `isTimeoutError` (#4578), because there a false positive bought one extra attempt. Cached, the same false positive (a `gh` killed from outside on both attempts) now skips the probe for one `FORGE_DEGRADE_MEMO_TTL_MS` (60 s). That is tolerable only because the TTL is short and the memoized answer is the gate's fail-open `local-merge`, and neither #4830's spec nor its plan weighed it. A longer TTL, or a memo whose cached answer denies, needs the exact `ETIMEDOUT` check — and the degrade object passed to `onDegrade` carries only `reason`/`timeoutMs`/`attempts`, not the error code, so the producer must expose it before the caller can filter on it. When you add a memo over an existing classifier, re-run the cheap-mistake choice in the same change.
- **`file-lock.js`'s wait is sized for bookkeeping, so a lock held across a long call needs a wait longer than that call's bound, or it serializes nothing.** `acquireLock` gives up after `CLAUDE_TWEAKS_LOCK_WAIT_MS` (500ms by default) and returns `null`, and its callers then proceed unlocked. That is right for a read-modify-write that takes milliseconds. For a critical section bounded at N ms it means every waiter falls through after half a second and races the holder, which is exactly the concurrency the lock was added to stop, and nothing reports it. `commit-ref.js`'s `deepenShallowClone` (#2988) holds its lock across the 120s `--unshallow` fetch, so it waits `DEEPEN_TIMEOUT_MS + LOCK_WAIT_MARGIN_MS`. The 15s margin keeps a waiter's deadline from landing just before the holder's fetch finishes. `file-lock.js` has no per-call wait option, so that module sets the env var around its one `acquireLock` call and then restores the earlier value, or removes it if it was unset. Do not copy that env swap. A second long-hold caller adds a `waitMs` option to `acquireLock`/`withLock` and moves `commit-ref.js` onto it in the same change. Put the lock in the repo's real git dir, never at `path.join(root, '.git', …)`. In a linked worktree `.git` is a file, so `mkdirSync` there throws `ENOTDIR` and `acquireLock` silently fails open. Resolve the dir with `git rev-parse --git-common-dir`, then `path.resolve(root, out)`, because the output can be relative. Skip `--path-format=absolute`: it needs git 2.31 or later, and no sibling module uses it. Every worktree of the repo shares that dir, which is also where git keeps its own `shallow.lock`.
