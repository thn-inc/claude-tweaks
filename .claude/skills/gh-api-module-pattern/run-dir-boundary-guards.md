# Run-directory boundary guards — gh-api-module-pattern

Lazy-loaded from `cli-wrapper-contract.md`: read it before writing a `plugin/bin/` CLI that takes a `--run` argument, whether it writes the run directory or only reads it.

- **A run-directory argument gets one of four boundary guards; pick before writing the check.** `plugin/skills/_shared/pipeline-run-dir.md`'s CLI-argument-boundary section is canonical and enumerates all four itself ("Four shapes live at this boundary"); this bullet is the `bin/`-side summary, never a second registry. **(1) Pipeline-owned binaries** (`hooks.js`, `wrap-up-engine.js`, `materialize.js`, `apply-refine-labels.js`) refuse any value not anchored under the main checkout. `wrap-up-engine.js`, `materialize.js` and `apply-refine-labels.js` exit 2; `hooks.js`'s `resolveRunArg` verbs print `--run path rejected: …` and pick their exit code per verb — 0 for most, 1 for `close-run` (#3025), `resolve-console` (#2568) and `check-pass-reentry` (#3553) — so a caller reads that verb's own `run{Verb}` handler (the `run` its `VERBS` entry names), never a family-wide code. **(2) The two resolver CLIs** (`plugin/bin/resolve-profile.js`, `plugin/bin/resolve-policy.js`, #1065) call `worktree-detect.js`'s `checkRunDirAnchoredOrOutside` — a resolved path inside any checkout must be anchored, a path outside every checkout is accepted as-is — and exit 1, their own documented invocation-failure code. **(3) The *Sanctioned-writer* family** (`cli-wrapper-contract.md`'s exit-code vocabularies) (`log-decision.js`, `stage-item.js`, `set-config.js`, `set-verify-expectations.js`, `write-run-artifact.js`) applies the same strict anchoring, but through one of two exported `resolveTarget` copies rather than `worktree-detect.js` directly — `plugin/bin/lib/stage-item/write.js`'s (imported by `stage-item.js`, `set-config.js`, `set-verify-expectations.js`, `write-run-artifact.js`, and the readers `shadow-dup-proposal.js` and `console-filings.js`) or `plugin/bin/lib/log-decision/append.js`'s (imported by `log-decision.js`, and also by CLIs outside this family that append to `decisions.md` beside their main work — `repair-claim.js`, `release-claim.js`, `materialize.js`, `claim-targets.js` — which keep their own exit codes) — and refuses with exit **3**, not 2. Import the copy that sits beside the writer you call when you add another writer instead of re-deriving the predicate — `set-config.js` (#1376), `set-verify-expectations.js` (#2764) and `write-run-artifact.js` (#3044) import stage-item's, `claim-targets.js` (#2775) imports append.js's together with `appendEntry` — and pin the refusal with a fixture carrying both a real main-checkout run dir and a worktree-local shadow of it, asserting the shadow's file is byte-unchanged after the exit 3. **(4) The composer CLI** (`plugin/bin/compose-context.js`, #1988) is a run-directory *writer* (`{run}/context/{step}.md`) that nonetheless takes the *resolver* family's anchored-or-outside rule — through `plugin/bin/lib/run-dir-guard.js`'s `anchoredOrOutsideMessage`, the shared message renderer the two resolvers already call — and rejects with exit **2**, its malformed-invocation code, not 3. Strict is the default; anchored-or-outside needs a *documented* legitimate outside-repo use, and shape 4's is narrow enough to be non-precedential: its callers never branch on a run-dir code (a skill step's documented fallback on any non-zero exit is to read the named source files directly), and its tests spawn the real binary against tmp-root fixtures outside any checkout, the same documented use the resolvers have. A further writer inherits shape 4's reasoning only if its own callers share it; otherwise shape 3 is the default. `cli-wrapper-contract.md`'s deps-injection rule is scoped to binaries that already have a path-handling seam: `resolve-profile.js` is a `main(argv)` CLI with none, so its guard reads `process.cwd()` and is tested by spawning the real binary against `tests/helpers/git-fixtures.js` repos rather than by a fake (`tests/resolve-profile-run-dir-anchoring.test.js`); `resolve-policy.js` meets the entry contract (#5374), so its core passes `deps.cwd()` to the guard and its anchoring cases run in-process through `runCliSync` against the same real-git fixtures, still with no fake (`tests/resolve-policy-run-dir-anchoring.test.js`, #5384) — `compose-context.js` does have the seam and injects every path-handling call through it (`deps.cwd`, `deps.mainRoot`, `deps.isDirectory`, `deps.anchoredOrOutsideMessage`), which is the shape a new run-dir-taking CLI should copy. **#4027's three mechanics CLIs pair shape 3's predicate with exit 2:** `plugin/bin/manifesto-write.js`, `plugin/bin/pr-early-open.js` and `plugin/bin/context-gauge.js` anchor `--run` strictly through stage-item's `resolveTarget`, also refuse a basename `RUN_ID_RE` rejects, and exit **2**, because each one's 3 already carries a domain answer (`manifesto-write.js`: `config.yml` already present, the case-1 adoption; `pr-early-open.js`: the logged degrade) or it has no 3 at all (`context-gauge.js`, whose measured states all exit 0). Take that split only when the new CLI's 3 is already spoken for; otherwise shape 3's exit 3 stands.
- **A read-only run-dir *reader* still owes a stated boundary posture.** The four shapes above are framed around writes (`pipeline-run-dir.md`'s boundary refuses "before any filesystem write"), so a CLI that only reads a run-dir file looks exempt and gets no guard at all. `plugin/bin/closing-tally.js` (#2729) takes `--run`, joins `decisions.md` onto it with no anchoring check, and spends exit 3 only on an unreadable file: given a worktree-local shadow of the run dir (`[IL-127]`), it tallies the shadow's `decisions.md` and exits 0. That is a confident wrong count, and `/claude-tweaks:backlog refine`'s closing summary renders it verbatim. Pick one when you write the reader: import `lib/stage-item/write.js`'s `resolveTarget` and refuse a non-anchored `--run` on the sanctioned writers' exit 3, or state in the header why an unanchored read is safe for this CLI's callers (for example, a `--file` mode used only by tests). A stated reason has to survive the writer's own resolver: `plugin/bin/check-artifact-overwrite.js --run` (#4593) reads `manifest.yml` unanchored because its writers refuse a non-anchored `--run`, and its first header claimed that without exception, while `hooks.js`'s `resolveRunArg` adopts a worktree-local run dir with no main-checkout twin (#280). Review caught it (`7f2ad26e8`). Read the writer's resolver for its fallbacks and name them in the header. A reader whose 3 already carries a domain answer takes the #4027 split above instead: `plugin/bin/dispatch-resume.js --bound-run` (#4588) spends 3 on a refused or concurrent verdict (JSON on stdout), so it anchors the dir strictly through stage-item's `resolveTarget`, also requires a top-level dir of the main checkout's `.claude-tweaks/pipelines/`, and refuses on exit **2**, its malformed-invocation code.
