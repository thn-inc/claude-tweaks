# gh-api module pattern

How this repo writes Node modules that shell to `gh`. Two shipped instances define the pattern: `plugin/bin/lib/issues/capabilities-probe.js` (reads) and `plugin/bin/lib/issues/link.js` (writes). Two shipped bugs in one session (#626, #610) came from getting the flag rules wrong — read that table before writing any `gh api` call.

## The injectable runner

- The module takes `runner(args)`, invoked as if `gh ${args.join(' ')}`, returning stdout; a throw is a failed call. Export `defaultRunner` = `execFileSync('gh', args, { encoding: 'utf8' })` — always an argv array, never a shell string (no injection surface, no quoting bugs).
- **Every real spawn passes `windowsHide: true` in a form `tests/windows-hide-spawn-conformance.test.js` can see.** The scan reads each `child_process` call's own argument text: it accepts a literal `windowsHide` key there, or a bare identifier as the whole options argument whose own `const X = { … }` literal names it (`plugin/bin/lib/policy-schema.js`'s `execOpts`). A spread — `{ ...QUIET, timeout }` with the flag inside `QUIET` — satisfies neither and fails the full suite; `plugin/bin/pr-checks.js` shipped that shape and moved the key into each call (`8ead0c70b`). The `defaultRunner` one-liner above omits the flag, so a copy of it owes it too.
- Tests never touch real `gh`: fake runners branch on the `args` shape (`isGraphQL`, `isPost`-style lazy helpers) and `throw new Error('unexpected ' + args.join(' '))` on anything unhandled — a wrong endpoint fails loudly instead of passing silently. Record values inside the runner, assert after it returns (an `AssertionError` thrown *inside* a runner can be swallowed by the module's own try/catch).
- **A module may carry two runner seams, and they have opposite failure contracts.** `plugin/bin/lib/claim-targets/claim-targets.js` takes both: `deps.ghApi` — the `plugin/bin/lib/issues/claim-store.js` contract, which *never throws* and returns `{stdout, failure, status}` so a 404/409/422 arrives as data — for contents-API reads and writes, and `deps.gh` — the throwing runner above — for everything else (`repo view`, `label list/create`, `issue edit`, `issue comment`). Decide which seam a call belongs to before writing it: a never-throwing runner wrapped in `try/catch` reads as success on every rejection, and a throwing one used bare escapes uncaught.
- **An argv array stops shell injection, not flag injection.** A caller-supplied value that begins with `-` is still read as an *option* by the command itself, so any such value needs an end-of-options separator ahead of it. For `git` the separator is **`--end-of-options`, not `--`**: `--` switches `rev-parse --verify` and `merge-base` into pathspec mode and silently changes what they resolve — verified empirically before the fix landed, after `--` was tried first (#888 review lens 3b). `plugin/bin/lib/blast-radius-cli.js` is the shipped instance, on both of its revision-resolving calls. Pin the separator with a fake-runner test that asserts the exact argv array for a value like `-evil` (`tests/bin-lib/blast-radius-cli.test.js`), not just that the call succeeded. **`--end-of-options` alone never resolves a revision — it needs `--verify` alongside it.** A bare `git rev-parse --end-of-options <rev>` (no `--verify`) doesn't error and doesn't resolve either: it echoes `--end-of-options` back as a literal output line ahead of the resolved value, because plain `rev-parse` without `--verify` is in multi-arg parse-and-print mode, not single-revision-resolution mode. `plugin/bin/lib/docs-health/commit-ref.js`'s `classifyOne` (#2866) hit this directly — its first cut of peeling an annotated tag to the commit it points at used `rev-parse --end-of-options <sha>^{commit}` without `--verify` and failed with `error: unknown option \`end-of-options'`; adding `--verify` fixed it. Always pair the two.
- **A `git` path-list read also needs `-z`.** An argv that asks git for `--name-only` / `--name-status` output passes `-z` and splits on NUL, besides `--end-of-options` before the ref — see `plugin/skills/_shared/git-path-read.md`.
- **The same seam serves non-`gh` commands.** `plugin/bin/lib/blast-radius-cli.js` takes `deps.git` and `deps.readFile` on exactly the contract above and cites this skill for it. Nothing in the injectable-runner rules is `gh`-specific — the argv-array rule, the loud-throw fake, and record-inside/assert-after all carry over unchanged; only the `gh api` flag table below is `gh`-only.
- **A seam that writes a body widens to `runner(args, input)` and pipes it on stdin, instead of staging a temp file.** `plugin/bin/pr-checklist.js` (#3263) rewrites a PR body with `gh pr edit {n} --body-file -`, its `gh` dep forwarding `input` into `execFileSync`'s options (`stdio: ['pipe', 'pipe', 'pipe']`, keeping `windowsHide` and `timeout` in the same literal). No file exists to leak, clobber across concurrent runs, or have denied by a `tmp/` path rule, and a fake `gh(args, input)` captures the exact bytes written so a test can assert the body is byte-identical outside the edited row. Reads keep the one-argument call; only the write passes `input`.
- **Bound every remote-contacting call on the seam; a local-only call owes no bound.** `execFileSync` has no default timeout, so a black-holed remote hangs the caller indefinitely. Every `gh` call and every network `git` call (`fetch`, `remote prune`, `ls-remote`) passes an explicit `timeout` — `GH_TIMEOUT_MS`, the shared export of `plugin/bin/lib/shared-primitives.js` (imported by `plugin/bin/lib/issues/claim-store.js`, `plugin/bin/claim-targets.js`, and the four call sites #2567 converted below), `FETCH_TIMEOUT_MS = 5000` (`plugin/bin/lib/reconcile/classify.js`, `pr-state.js`, `red-tip.js`), or `plugin/bin/lib/hooks/git-exec.js`'s `DEFAULT_TIMEOUT_MS = 10000` for anything routed through `runGit`. **`GH_TIMEOUT_MS` is a resolved value, not a literal — import it, never retype its default at a new call site.** Since #2567 it resolves once per process in precedence order `CLAUDE_TWEAKS_GH_TIMEOUT_MS` (env var) > the `gh-timeout-ms` policy key (`.claude-tweaks/policy.yml`, bounded 1000-60000 by `policy-schema.js`, which `shared-primitives.js` reads those bounds from rather than re-hard-coding them) > the same 5000 default, and it is exported as a lazy getter (`Object.defineProperty`) so a consumer that requires `shared-primitives.js` for `isPathContained` alone — `hooks/pre-tool-use.js`'s hot path, via `git-exec.js` — never pays for the policy read. A local `const GH_TIMEOUT_MS = 5000;` is therefore not merely duplication: it silently opts that call site out of a GitHub Enterprise Server project's raised bound, where a cold `gh` call routinely exceeds 5s. That is why #2567 replaced the four remaining copies (`lib/compose-subject.js`, `lib/repo-resolve.js`, `lib/worktree/cherry-pick-provenance.js`, and `bin/materialize.js`'s two) with the import. Two `gh` bounds deliberately stay their own values and say why beside themselves — `hooks/teardown-run.js`'s 15000 and `reconcile/preflight.js`'s 2000 — which is the same "widen (or narrow) deliberately with a stated reason" rule, not an exemption from it. A batched call earns a wider bound than the 5s single-call convention — `plugin/bin/fetch-sub-issues.js`'s runner passes `timeout: 30000` for a 50-alias GraphQL batch and states the reason in a comment beside it; widen deliberately with a stated reason rather than carrying 5000 over by copy. Local-only reads (`rev-parse`, `git config`, `branch -r --merged`) owe none, and most shipped ones carry none; a bound on one is harmless, not a defect. When a direct `execFileSync('git', …)` runner does take a bound, import `GIT_TIMEOUT_MS` from the same module rather than typing a literal: it is the lazy getter #3051 added (`CLAUDE_TWEAKS_GIT_TIMEOUT_MS` > the `git-timeout-ms` policy key, bounded 1000-120000 > 30000), sized for `plugin/bin/lib/issues/claims-git-cas.js`'s claims-registry fetch/show/push. `plugin/bin/pr-checks.js`'s `rev-parse` runner and `plugin/bin/lib/compose-subject.js`'s `git diff` `gitRunner` (#3298) carry it on local reads, where it is harmless rather than required. The `defaultRunner` shape above is the argv-array rule, not a complete options object — a `gh` runner copied from it still owes a `timeout`. On a seam that is otherwise all-local, widen it with a per-call options argument rather than bounding every call: `plugin/bin/residue.js`'s `runner(argv, opts)` takes exactly such a per-call `execFileSync` options object (#663), and the seam's existing catch-all already maps a timeout kill onto its normal failure value. The `git remote prune` it was added for was since removed (`plugin/bin/lib/residue/probes/branches.js` states why beside the gap: "No `git remote prune` here: this probe's findings are read-only"); its bounded call site now is `plugin/bin/lib/residue/probes/release.js`'s `git ls-remote --tags origin 'v*'`, which passes `{ timeout: LS_REMOTE_TIMEOUT_MS }` (10000) so a timeout returns `null` into that probe's local-only fallback. That call first shipped unbounded and review caught it (#2882), so a probe that newly contacts a remote passes a `timeout` through `opts` in the same change, never as a follow-up. Omitting the bound is defensible only with a stated reason — `plugin/bin/lib/reconcile/shared-fetch.js` skips `timeoutMs` so `git-exec.js`'s `CT_HOOKS_GIT_TIMEOUT_MS` escape hatch still applies, and says so in a comment.
- **The same probe copied across N *separate* modules is the cross-module instance of the sibling-drift bullet below — consolidate into one shared, injectable helper rather than leaving each copy to drift on its own options object.** `plugin/bin/lib/repo-resolve.js`'s `ghAvailable(deps = {})` (#2017) replaced seven near-verbatim `execFileSync('gh', ['--version'], …)` probes scattered across `file-feedback.js`, `link-records.js`, `materialize.js`, `release-claim.js`, `compose-context/resolve-conditions.js`, `wrap-up/engine-verify.js`, and `repo-resolve.js` itself — each had quietly drifted on its options object (`stdio: 'ignore'` vs `stdio: 'pipe'`, some with no `timeout` at all) before the consolidation. A grep-backed test (`tests/bin-lib/repo-resolve.test.js`) now pins `'--version'` to the single production site, so the count can't silently regress back to N copies. A caller whose own seam shape differs (`engine-verify.js`'s `deps.gh(args, cwd)` takes a `cwd` the shared helper has no slot for) wraps the shared call in a one-line adapter rather than reintroducing a local copy.
- **Sibling default runners in one module drift on their options object — build both from one factory, once you've decided they should share it.** A module shelling to both `git` and `gh` on this seam ends up with a `defaultGit` and a `defaultGh` differing only in the command name, so a rule applied to one silently leaves the other behind. `plugin/bin/lib/wrap-up/engine-verify.js` shipped the pair unbounded, then gained `timeout: 5000` on `defaultGh` alone when the bullet above was applied to its remote-contacting call (`7569d4ce8`, refs #900), and needed a separate whole-branch review later the same day to notice `defaultGit` had been left behind (#1230, `76fd10487`) — one options object, edited twice, hours apart, because nothing but eyeballing the two copies could show they disagreed. It now builds both from `makeDefaultRunner(cmd)` — one closure over one options object — so the two can no longer diverge by copy (#1222). Weigh what the factory costs before reaching for it: it forces symmetry, and the bullet above says symmetry is not automatically correct (that module's `git` calls are all local and owe no bound at all — a uniform 5s is merely harmless there, not required). Factor when the siblings genuinely should share their options; otherwise keep them separate and state beside each why it differs. Same remedy as the sync/async twin drift under **Async fan-out** below, on a different axis: factor at the point of duplication rather than diffing copies later.
- **A seam whose calls are *probes* runs quiet, and carries its own error class so the CLI can pick the exit code.** `plugin/bin/lib/verify/changed-files.js` (#1922) shells to `git` on exactly the seam above, and every real call passes `stdio: ['ignore', 'pipe', 'pipe']` — the posture `blast-radius-cli.js`'s own default `git()` already uses — because base resolution *asks questions it expects to fail*: `merge-base --is-ancestor` on a stale stamp anchor, `rev-parse --verify` on a ref that may not exist. Without the quiet posture a benign miss leaks git's own `fatal:` line to the stderr of a process that is about to exit 0, which reads to a caller as a real error. The message is not thrown away: the module raises a named `ChangedFilesError` carrying it, and the *CLI* — not the module — decides what an unresolvable base means per mode, since the same module-level failure is a different class of problem depending on who asked. `verify.js --scope` maps it to the usage-class exit 2 (an unresolvable base is a malformed invocation, not a check failure), `verify.js --changed-files` to its own documented exit 1, and both re-`throw` anything that is not a `ChangedFilesError` rather than flattening an unrelated bug into a tidy exit code. A bare `throw new Error` on the seam would force the CLI to string-match its own module to tell the two apart.
- **The quiet posture is owed by any call the module catches and recovers from, not only by a probe seam — and a catch that reads the error text needs stderr `'pipe'`, not `'ignore'`.** `plugin/bin/lib/compose-subject.js`'s `realDeps.runner` is a fetch seam, so it stayed on `execFileSync`'s default, which echoes the child's stderr to ours: its handled `Unknown JSON field: "issueType"` rejection (the GraphQL fallback, #2561) printed gh's whole field list ahead of a successful compose, which read as a failure (#3028). It now passes `stdio: ['ignore', 'pipe', 'pipe']`, keeping stderr piped because `isUnknownIssueTypeField` matches on `err.stderr`/`err.message`. `reconcile/preflight.js`'s `['ignore', 'pipe', 'ignore']` suits only a catch that classifies on `err.code`.

- **A memoizing *decorator* on the seam is itself a runner — and it must be write-aware whenever its call graph reads back its own writes.** `plugin/bin/lib/reconcile/issue-list-cache.js`'s `createIssueListCache({base})` (#2505) returns `{runner}` on exactly the argv→stdout contract above, so it drops in wherever a `runner` is already injected — `escalate-residue.js` needed no change at all — and `reconcile/index.js` creates **one instance per `reconcile()` pass**, threading it through `archiveMerged`/`reapMerged` into `cache.js`'s `trackResidue`/`pruneResidueFailures`. Per-pass, never a module-level singleton: `reconcile()` is called in-process from `hooks/session-start.js` as well as from `bin/hooks.js reconcile`, so a module-scope memo would serve a later pass a read taken during an earlier one. The hazard that decides the memo's *shape* is read-after-write on the same seam: those callers also write through that runner (`issue create`/`edit`/`close`/`reopen`) and read back within the pass — `escalate-residue.js`'s `structurally-stuck` fingerprint is deliberately path-less, so every stuck dir in a pass converges on the same consolidated record and each read depends on the previous write. Memoizing the raw response string would file N separate issues instead of one (regressing #1811-#1817's original symptom) and let a resolve loop resurrect paths it just removed, so the record never closes. Memoize the **parsed** value and apply each write's effect to it in place — same correctness as invalidating on every write, at zero extra round trips. Three rules keep that honest: only the exact read shape is memoized (`argv[0] === 'issue' && argv[1] === 'list'`) and every other call executes; a throw or an unparseable response is never cached, so the next call retries rather than replaying a failure; and the write-effect applier encodes *this* call graph's write vocabulary (a verb it doesn't know is a deliberate no-op, never a throw and never an invalidation), which is only defensible while the decorator has one caller — say so in the module header, as `issue-list-cache.js` does. Pin it with a stateful fake `base` that counts calls and asserts both the call count and that a read after a write reflects the write (`tests/bin-lib/reconcile/issue-list-cache.test.js`), plus a two-instance test proving no cross-pass sharing.
- **Caching a *failure* is the one exception to "a throw is never cached", and it needs an exact timeout check plus a TTL.** For a cheap call, retrying is the recovery. For a long-bound remote call, every later caller would re-pay the full timeout, so remembering it is the fix. `plugin/bin/lib/docs-health/commit-ref.js`'s `deepenShallowClone` (#2988) writes a timeout marker with a 30-minute `TIMEOUT_MARKER_TTL_MS` after its 120s `fetch --unshallow` times out. The marker is a file in the git-common dir, not an in-process memo, because `docs-health --budget > 1` runs `verify-commit` as a separate process for each citation. Its `isTimeoutError` is `err.code === 'ETIMEDOUT'` alone, not the three-way check `async-fan-out.md`'s `retryOnTimeout` bullet documents. When `execFileSync`'s own `timeout` fires, the error carries `{code: 'ETIMEDOUT', signal: 'SIGTERM'}`. A git killed from outside carries the same `signal: 'SIGTERM'` with no `code` (probed on Node 22). `err.signal === 'SIGTERM'` would therefore record that crash as a timeout and block every retry for the whole TTL. Choose the check by which mistake is cheap. For a retry, a false positive costs one extra attempt, so the broad check is fine. For a cached failure, missing a real timeout costs one extra attempt, and a false positive blocks recovery, so use the exact code.
- **`file-lock.js`'s wait is sized for bookkeeping, so a lock held across a long call needs a wait longer than that call's bound, or it serializes nothing.** `acquireLock` gives up after `CLAUDE_TWEAKS_LOCK_WAIT_MS` (500ms by default) and returns `null`, and its callers then proceed unlocked. That is right for a read-modify-write that takes milliseconds. For a critical section bounded at N ms it means every waiter falls through after half a second and races the holder, which is exactly the concurrency the lock was added to stop, and nothing reports it. `commit-ref.js`'s `deepenShallowClone` (#2988) holds its lock across the 120s `--unshallow` fetch, so it waits `DEEPEN_TIMEOUT_MS + LOCK_WAIT_MARGIN_MS`. The 15s margin keeps a waiter's deadline from landing just before the holder's fetch finishes. `file-lock.js` has no per-call wait option, so that module sets the env var around its one `acquireLock` call and then restores the earlier value, or removes it if it was unset. Do not copy that env swap. A second long-hold caller adds a `waitMs` option to `acquireLock`/`withLock` and moves `commit-ref.js` onto it in the same change. Put the lock in the repo's real git dir, never at `path.join(root, '.git', …)`. In a linked worktree `.git` is a file, so `mkdirSync` there throws `ENOTDIR` and `acquireLock` silently fails open. Resolve the dir with `git rev-parse --git-common-dir`, then `path.resolve(root, out)`, because the output can be relative. Skip `--path-format=absolute`: it needs git 2.31 or later, and no sibling module uses it. Every worktree of the repo shares that dir, which is also where git keeps its own `shallow.lock`.
- **Pick the git root by what the module reads: `--show-toplevel` for working-tree facts, the `--git-common-dir` parent only for state that must outlive a worktree.** From a linked worktree the common-dir parent is the MAIN checkout, so a `git diff {base}...HEAD`, a `docs/` scan or a frontmatter read run against it sees the main checkout's HEAD and tree and comes back empty without erroring. `plugin/bin/wrap-up-engine.js` keeps both on purpose (#3431): `resolveFactsRoot` (`--show-toplevel`) feeds `gatherFacts` and `buildJourneyFrontmatter`, while `resolveRepoRoot` (common-dir) anchors the telemetry TSV, archived-run lookups and `policy.yml`. A regression test for a root fix needs a fixture that differs between the two roots at every call site that takes the root: the first #3431 test left `buildJourneyFrontmatter` on the wrong root and stayed green because the journey file was identical in both checkouts.
- **A module that parses git's output pins that output's format against the user's and the repo's git config.** A parser written against git's defaults misreads the output under another config, and nothing fails. `diff.noprefix` and `diff.mnemonicPrefix` change the `a/`/`b/` header prefixes. `color.ui=always` and an external diff driver rewrite the text. `core.quotePath`, on by default, prints a non-ASCII path quoted and escaped, so `café.txt` no longer matches its own name. For a path list, pass `-z`, which prints every path verbatim (`plugin/bin/lib/verify/changed-files.js`). For patch text, pass every flag explicitly, as `plugin/bin/lib/review-context/build.js` does (#3020): `-c core.quotePath=false diff --no-color --no-ext-diff --src-prefix=a/ --dst-prefix=b/`. Its first version passed none of them, and an added non-ASCII file over the size cap kept its whole diff chunk. Pin the flags two ways: real-git tests that set the config in the fixture repo, and an exact-argv assertion for the flags no fixture test exercises (`tests/bin-lib/review-context/build.test.js`).

## The three `gh api` value mechanisms (the bug source)

| You are passing… | Flag | Why |
|---|---|---|
| gh's literal `{owner}`/`{repo}`/`{branch}` placeholder in a **field value** | `-F` | Only `-F` substitutes; `-f` sends the braces as a static string (#626) |
| An **already-resolved** string bound to a GraphQL `String!` variable | `-f` | `-F` type-coerces an all-numeric name (`2048`) to an Int and GraphQL rejects it (#610) |
| A numeric **REST body** field (`sub_issue_id`, `issue_id`) | `-F` | So it lands as an integer, not a string |

URL *path* placeholders (`repos/{owner}/{repo}/…`) are a fourth thing: always substituted, no flag involved. Never collapse these into "always -F for owner/repo" — that generalization is exactly what shipped #610's bug, with a plan-authored test pinning the wrong flag.

**Any `-f`/`-F` field flips `gh api`'s default method from `GET` to `POST`.** `gh help api`: "The default HTTP request method is `GET` normally and `POST` if any parameters were added" — so a REST *read* that needs a query parameter passes `--method GET` explicitly (gh then sends the fields as a query string), or puts the parameter in the path (`…/git/trees/{branch}?recursive=1`). Written bare, `gh api repos/…/git/trees/{branch} -f recursive=1` is a POST to a path with no POST route. On `claim-store.js`'s never-throwing seam a 404 or 422 answer classifies as `{failure: null, status}` with no stdout, and `listClaimEntries` as first written in #3098 parses absent stdout as `{}` — an empty listing reported as success, the exact silent-partial-list failure that change set out to remove. A fake-runner test asserting `['-f', 'recursive=1']` pins the argv shape, not what GitHub does with it: pin `--method GET` (or the `?recursive=1` path) in the asserted argv. `gh api graphql` is unaffected — it is always a POST.

**A REST `--json <field>` name is not portable across `gh` versions — prefer the GraphQL equivalent when one exists.** `gh issue view {n} --json parent` throws `Unknown JSON field: "parent"` on `gh` 2.92.0 but works on 2.96.0+ — the REST JSON field list changes between releases, and a caller has no way to detect which fields a given `gh` binary supports short of trying and parsing the error. `Issue.parent` via `gh api graphql` (`repository(owner,name){ issue(number){ parent{ number } } }`) reads the identical data on every `gh` version that can run GraphQL at all, because the GraphQL schema is server-side, not tied to the installed CLI's REST field allowlist. `plugin/bin/lib/wrap-up/engine-verify.js`'s `resolveParent` migrated from the former to the latter for exactly this reason (#1841) — reusing the existing `buildNativeParentQuery` builder (see "Batching and failure posture" below) rather than inventing a new query shape. When a REST `--json` read is genuinely simpler and version drift isn't a concern (a field present since `gh`'s earliest supported version), the plain REST form is still fine — this is a reason to prefer GraphQL for a *newer or less common* field, not a blanket rule against `--json`.

**A caller-overridable REST path has no bound-variable escape hatch.** The `{owner}`/`{repo}` path placeholders above always resolve from `gh`'s own ambient repo context (the cwd's git remote) — there is no `-f owner=…`/`-F owner=…` equivalent that rebinds a REST *path* segment the way `-f owner=…` rebinds a GraphQL variable (row 2 above). A CLI that must honor its own `--repo owner/name` override for a REST call (rather than `gh`'s ambient context) therefore has to build the path string itself — `plugin/bin/fetch-sub-issues.js`'s `--resolve-retries` retry loop does exactly this (`` `repos/${owner}/${repo}/issues/${n}/sub_issues` ``, #1153 review finding). That loses the placeholder mechanism's implicit safety: the interpolated `owner`/`repo` values need their own validation before they reach the path, since a lax upstream parser (this repo's shared `parseRepo` accepts any non-`/` segment, including `.`/`..`) can otherwise redirect the call. `fetch-sub-issues.js` added a narrow `owner !== '.' && owner !== '..'` guard at its own call site rather than tightening the shared `parseRepo` (9 callers, most never resolve a caller-supplied `--repo` at all) — a reminder to validate at the interpolation site when you can't fix the shared resolver's blast radius in the same change.

**A ref name interpolated into a REST path is encoded per segment.** Git allows `#` and `%` in a branch name, and a URL reads them as a fragment start and an escape, so `` `repos/{owner}/{repo}/commits/${branch}` `` can address another ref. `plugin/bin/pr-checks.js`'s `readBase` (#3258) builds the segment as `branch.split('/').map(encodeURIComponent).join('/')`, keeping `/` a separator; `tests/bin-lib/pr-checks/cli.test.js` pins the argv with `release/v1#x`. `plugin/bin/lib/release-preflight/pack.js`'s branch-tip read and `plugin/bin/lib/hooks/teardown-run.js`'s `git/refs/heads/${branch}` delete still interpolate the bare name.

`gh api graphql` is where two of these rows collide: a `String!` variable needs `-f`, and `-f` never expands `{owner}`/`{repo}`, so the placeholder mechanism is simply unavailable to a GraphQL variable. Resolve the slug locally instead — `plugin/bin/lib/hooks/git-exec.js`'s `repoSlugOf` parses it out of `remote get-url origin` and is shared by `reconcile/pr-state.js` and `reconcile/release-merged.js` (#1082) — and pass it as `-f owner=…`/`-f name=…`. `claim-store.js`'s `resolveRepoSlugOrThrow` (the `gh repo view --json nameWithOwner` form, which `claim-targets.js` delegates to since #3438; its non-throwing sibling `resolveRepoSlug` returns `null` on any failure) is for a seam holding a `gh` runner but no repo root; `hooks/teardown-run.js`'s inline copy of the same regex predated the shared helper and now uses `repo-resolve.js`'s `parseRepo` directly (#2747) — see the `--hostname` bullet below. **This file covers Node modules only** — the identical resolve-then-`-f` rule applies verbatim to `gh api graphql` calls written directly in skill-prose bash blocks (no `execFileSync` seam to share a helper through); there, the established shape is `read -r OWNER REPO <<< "$(gh repo view --json owner,name -q '.owner.login + " " + .name')"` immediately before the call, as `plugin/skills/_shared/github-pr-scan.md`, `plugin/skills/init/bootstrap/step-17-work-record-backend.md`, and `plugin/skills/capture/SKILL.md`'s native-type GraphQL fallback all do.

**A `--repo` argument is a *slug*, and the slug is host-qualified — never hand-roll `` `${owner}/${repo}` `` at one.** `plugin/bin/lib/repo-resolve.js`'s `repoSlug({host, owner, repo})` (#2240) is the producer of the value `gh -R/--repo` takes: bare `owner/repo` on github.com, `host/owner/repo` on a GitHub Enterprise Server host, with a missing `host` reading as github.com so a caller threading an optional host through needs no guard of its own. Interpolating `` `${owner}/${repo}` `` at a `--repo` call site instead silently drops that host and sends every GHE call to github.com, where it 404s or — worse — resolves against a same-named public repo. `plugin/bin/lib/wrap-up/pack.js`'s `unblocked` probe shipped exactly that while `repoSlug` was already imported two lines above the bug (#2425, fixed in `06e14b626`); four independent review lenses each found it, which is what a class of bug with no written rule looks like. The producers that go through `repoSlug` today are `release-claim.js`, `file-feedback.js`, `apply-refine-labels.js`, `materialize.js`, `lib/compose-subject.js`, `lib/release-claim/release.js`, `lib/repair-claim/repair.js`, and `lib/wrap-up/pack.js` — **copy one of those, not the paragraph above.** `git-exec.js`'s `repoSlugOf` is a different helper with a different contract: its regex keeps only the last two path segments, so it drops the host *by construction*. That is correct for the GraphQL `-f owner=…`/`-f name=…` pair it was written for and wrong for a `--repo` flag or any host-sensitive REST path, so its `reconcile/` consumers (`escalate-residue.js`'s `--repo`, `release-merged.js`/`claim-store.js`'s `repos/${repoSlug}/…` paths) are github.com-only by inheritance — a known limitation to widen deliberately, never a shape to copy into a new call site. `lib/wrap-up/engine-verify.js`'s `upstream-feedback` check is the one remaining hand-rolled `` `${owner}/${repo}` ``, tolerable only because its own URL regex matches `github.com` alone; widening that regex without switching it to `repoSlug` reintroduces #2425.

**A search-backed call needs a *canonicalized* slug; a REST call survives without one.** GitHub's search API — `gh pr list --search`, `gh issue list --search`, `gh search prs/issues` — does **not** follow a repository rename or transfer redirect, while REST (`gh api repos/{owner}/{repo}/…`) does. So a slug derived from a stale `origin` remote keeps working on every REST call in a module while the search-backed calls in the same module return zero rows, or `Invalid search query`, with no error the caller can see — an empty result set is indistinguishable from "nothing matched in this period." Canonicalize before querying: `gh repo view {slug} --json nameWithOwner -q .nameWithOwner` follows the redirect, and whatever it returns is the slug every subsequent call uses. `plugin/bin/activity-gather.js` does exactly this once per repo, ahead of all six of its queries (#2757). The failure is silent by construction, so a probe cannot find it unless the probe resolves the slug the way the code does: #2757's own Task 0 ran every query against the hand-picked post-transfer slug, proving the argv shapes while never exercising resolution, and four of six queries came back empty on the first real run — after the task reviews and the whole-branch review had all passed.

**A REST call with no `--repo`/`-R` flag needs `--hostname` instead, from the same `parseRepo` host field.** `gh api --method DELETE repos/{owner}/{repo}/…` has no `--repo` slot, so a GitHub Enterprise Server remote needs `--hostname {host}` alongside the call, omitted when `host` is absent or `github.com`. `plugin/bin/lib/hooks/teardown-run.js`'s `defaultGhApiDelete(args, host)` (#2747) is the shipped instance: it resolves `{host, owner, repo}` via `parseRepo` directly, not `repoSlug`, since this call needs the host as its own flag, not folded into a `--repo` value. The same holds when a host-qualified `--repo` feeds `gh api graphql`: the host travels as `--hostname {host}` placed right after `graphql`, omitted for `github.com` or no host. `plugin/bin/lib/issues/resolved-refusal.js`'s `fetchResolvedRefusalEvidence` (#3597) is the instance — a fake-runner test on the exact argv for a GHE host pins it, since a dropped flag silently queries `github.com`.

**A `--repo` *consumer* must accept both shapes.** Once producers emit host-qualified slugs, a CLI taking `--repo` receives either form, so the `github.com/` prefix `parseRepo` needs for a bare value is conditional, not unconditional — `plugin/bin/lib/number-list-cli.js` branches on `opts.repo.split('/').length >= 3` (#2425), because prefixing an already-qualified value builds a 4-segment string that `parseRepo`'s 3-segment regex rejects outright, turning a valid GHE invocation into "could not resolve owner/repo". A new `--repo`-taking CLI copies that branch; a fake-runner test asserting the exact argv for both a bare and a host-qualified `--repo` value pins it, the same way the end-of-options rule above is pinned.

## Batching and failure posture

- Resolve everything up front in one call where the API allows it (aliased GraphQL: one `i{N}: issue(number:{N}){ databaseId }` per distinct number), and chunk the alias list rather than letting one query grow without bound — `plugin/bin/fetch-sub-issues.js` slices its input at 50 numbers per call and merges each chunk's result into one envelope.
- **The alias-query *builder* is a pure function in `plugin/bin/lib/issues/record.js`, separate from whatever runs it.** `buildNativeDependencyQuery`, `buildNativeSubIssuesQuery`, and `buildNativeParentQuery` each take a `numbers` array, return the query string, and return `null` for an empty or non-array input — an empty `repository{}` selection set is invalid GraphQL, so the caller must branch on `null` rather than send it. `record.js` requires nothing but `./facet-shape` and shells out nowhere, which is what lets `tests/bin-lib/issues/record.test.js` pin each builder with plain regex assertions and no fake runner at all; the transport, the chunking, and the partial-result posture below all belong to the caller (`plugin/bin/lib/issues/native-dependencies.js`, `plugin/bin/resolve-blockers.js`, or a skill's own `node -e` line), never to the builder. Add a fourth builder the same way — and factor the shared `query($owner:String!,$repo:String!){ repository(owner:$owner,name:$repo){ … } }` envelope out when you do: the three above repeat it verbatim today (#1194 hindsight).
- **Relay-style cursor pagination direction is a footgun on a connection field whose events accumulate over a long-lived object's life.** `first:N` fetches the OLDEST N nodes; `last:N` fetches the NEWEST N — the same `record.js` file's fourth builder, `buildLinkedPRQuery`, shipped `timelineItems(itemTypes:[CROSS_REFERENCED_EVENT], first:20)`, so a long-lived issue that accumulates many cross-references (other issues discussing the same subsystem, health-sweep dedup comments) can have its own merged PR's reference pushed out of that oldest-20 window entirely, well before any classifier sees it. Confirmed live against #1892/PR#2287: #1892 had accumulated 20+ issue-based cross-references before #2287 ever merged, so `first:20` returned zero PR sources even though the pair should have scored `strong`. Fixed to `last:20` (#2449) — a shipped/duplicate-detection query wants the freshest signal, not the earliest. Check pagination direction against what the query is actually trying to answer; don't copy the `first:N` convention the bounded, order-agnostic alias builders above use onto an accumulating connection without re-deriving it.
- **Two sanctioned partial-result postures; choose by whether the caller can recover per item.** *Throw on a partial result* when partial data is unusable — `plugin/bin/lib/issues/native-dependencies.js`'s `fetchNativeDependencies` throws naming every missing `i{N}` alias (#723), because a caller that silently drops a dependency edge ships a wrong graph. *Return a retry envelope* when the caller has a per-item fallback — the same file's `fetchNativeSubIssues` returns `{byParent, retry}` (#1097), routing a single missing or null alias onto `retry` for the caller's per-parent REST loop instead of failing the whole batch; such a parent never lands in `byParent` as `[]`, because an empty array already means "fetched, has no sub-issues". A whole-response failure (`data.repository` null or missing) throws under *both* postures — an envelope degrades per item, never per batch.
- **Routing an existing caller onto a shared module inherits that module's posture — re-check the caller's blast radius, not just its output shape.** The two postures above are chosen when a module is *written*; the hazard lands at the *caller migration*, where a call site that degraded per item silently starts degrading per batch. `plugin/skills/dispatch/queue-pull-script.md`'s `work-links: native` branch (#1309) moved from a hand-rolled `gh api graphql` response fed to `record.js`'s `partitionByOpenNativeBlockers` — which reads a missing `i{N}` alias as an empty blocker list and so fails open for *that one candidate* — onto `plugin/bin/resolve-blockers.js`, whose `fetchNativeDependencies` throws on any single missing alias (the *throw on a partial result* posture above), exits 3, and disables native blocker filtering for **every** candidate in the run. The per-record output shape was identical and the suite stayed green; only the failure fan-out changed, so no shape-level assertion could catch it. When such a migration is the point of the change, state the old and new degrade granularity side by side in the record, and give the caller an exit-code branch that separates a partial result from a total outage instead of one catch-all `else`.
- **A bulk alias query is chunked, all-or-nothing, and never authorizes a destructive act by itself.** `plugin/bin/lib/reconcile/pr-state.js`'s `resolvePrStatesBulk` (#1082) resolves N branches' governing PRs in `ceil(N/50)` calls of `b{i}: ref(qualifiedName:"refs/heads/…"){ associatedPullRequests }` aliases — the chunk size is probe-measured, not guessed: 50 aliases cost 1 GraphQL rate-limit point. It returns a complete `Map` or a failure sentinel, never a partial map: a transport throw, an HTTP-200 body carrying `errors[]`, and an alias key missing from `data.repository` each fail the whole call, because a dropped chunk's branches are otherwise indistinguishable from branches with no PR. Bulk evidence is also weaker than a per-branch read — `ref()` is null for a branch deleted after its PR merged — so a caller screens with it to skip cheaply and re-confirms via `resolvePrState` before anything destructive (`prune-remote.js`, `archive-branches.js`).
- **A single GraphQL query that errors exits non-zero, but its body is still on stdout — classify absence from that body, never from stderr.** The bulk bullet above covers an HTTP-200 body carrying `errors[]`; a per-object query for a missing node is different: `gh api graphql` exits 1 and still writes the full JSON response to stdout, so the thrown error's `e.stdout` is the evidence (live-probed on PR 999999: `{"data":{"repository":{"pullRequest":null}},"errors":[{"type":"NOT_FOUND","path":["repository","pullRequest"],…}]}` on stdout, `gh: Could not resolve…` on stderr). Read absence only from `errors[].type === 'NOT_FOUND'` at the exact `path` **and** a non-null parent object (`data.repository`) — a null parent means the repo itself did not resolve, which is not proof the child is gone. Everything else (no body, unparseable body, `FORBIDDEN`, a null parent) stays the seam's transport classification. `plugin/bin/lib/reconcile/pr-state.js`'s `isPrNotFoundBody` / `confirmPrNotFound` (#3543) is the reference: its `runClassified` mapError receives the throw and returns `e.stdout`, and the probe keeps stdout piped.
- **A screen value that is *blind* rather than negative may route, never terminate — and the cheap-skip half needs that rule as much as the destructive half.** The bullet above guards only the destructive direction (re-confirm before deleting), which leaves "screens with it to skip cheaply" reading as license to let any non-`MERGED` screen end the decision. That is where `archive-branches.js` shipped a gap: `squashCandidate` read `screenPr.state === 'MERGED'` only, so a screen-`null` branch — the documented deleted-ref blind spot above, the *absence* of an answer rather than a negative one — reached the per-branch confirm only when some other provisional verdict already sent it there (cherry-equivalent, or aged past `BRANCH_AGE_DAYS` onto the tag-and-delete path). A **young, non-cherry-equivalent, squash-merged** branch matched neither, so its provisional `skip`/`too-young` was final on every pass forever, and it never reached the confirm that carries the `mergeCommit` its squash-provenance proof needs (#2322 widened the boolean to `screenPr === null || screenPr.state === 'MERGED'`). Discriminate on whether the screen value is *conclusive*, not on whether it is negative: an `OPEN` screen is a real answer and still short-circuits with no per-branch call at all, while `null` must cost one confirm. Widening a route never widens what the confirm decides — a confirm coming back `null`/`CLOSED`/`OPEN` falls through to the same age rules as before — so the bill is one `gh pr list --head` per screen-null, non-cherry-equivalent branch per pass, bought against converging on the first pass instead of after the age threshold. When adding or changing a screen/confirm caller, enumerate the screen's values against *every* provisional verdict the caller can reach, not just the destructive one; a permanent skip is a verdict too.
- Per-write calls are each independently try/caught into `{ok: [...], failed: [{…, error}]}` — one failed edge never aborts the batch. An "already exists" 422 is a re-run, not a failure: it lands in `ok` with `already: true` (live-confirmed wording: GitHub answers `Validation failed: Target issue has already been taken`).
- Error text: join `err.message`/`err.stderr`/`err.stdout`, with a `String(err)` fallback so a non-Error throw never yields an empty `failed[].error`.
- **Enumerate an operation's full documented error-status set in one sitting.** Adding one status per bug report ships the same misclassification serially: `plugin/bin/lib/issues/claim-store.js`'s Contents-API PUT got its 422 create-race branch in `75c8b3b6`, then the symmetric 409 sha-mismatch branch in `4ee0fbcc` — one defect class, found twice, the second time by a review lens. Read the endpoint's documented statuses first (Contents PUT: 404 read-miss, 409 sha-mismatch, 422 create-race) and branch on all of them in the same commit.
- **Rate-limit recognition and burst pacing.** Classify a `gh api` rate-limit failure per `plugin/skills/_shared/github-rate-limit.md`'s taxonomy before deciding whether to retry — a plain 403 under that file's rules is not transient and must not be retried. When a module issues a scripted sequence of mutative calls, follow that file's burst-shape rules.
- **A transient-failure retry on a non-idempotent mutating call needs a dedup-safe recheck, not the same blind retry as an idempotent read.** A 5xx/timeout/reset signature is ambiguous about *where* the failure happened: the request may have reached GitHub and succeeded, with only the response lost. Retrying `gh issue list`/`issue view` on that signature is free — a second read changes nothing. Retrying `gh issue create` (or any other non-idempotent write) the same way risks filing a duplicate. `plugin/bin/lib/feedback/file-feedback.js`'s `createWithDedupSafeRetry` is the shipped instance (#834/#835 review): before each retry of the create call, it re-runs the module's own dedup search for a marker unique to this call — a hit means the "failed" attempt actually succeeded, so that result is reused instead of creating a second one. A single generic retry wrapper applied uniformly across a module's read and write calls is exactly the shape this hazard hides in.
- **A machine-filed issue carries only the labels its filing context can actually justify — and the module's header says so.** The two shipped `gh issue create` sites split on whether an LLM is in the loop. `plugin/bin/lib/feedback/file-feedback.js`'s `fileDraft` takes `labels` from its caller, because the `/feedback` skill orchestrating it can judge them. `plugin/bin/lib/reconcile/escalate-residue.js` files `--label bug` and nothing else, from the no-LLM contexts named in its header (`session-start.js` in-process, `bin/hooks.js reconcile`) — deliberately, not as a gap (#1216): `risk:*`/`size:*` are content judgments no mechanical caller can score, a fixed always-low default is wrong on its own, and `ready` asserts a spec-shaped body that a terse auto-report is not. Leave the enrichment to the downstream path that demonstrably picks the issue up — a plain open issue is already a backlog-stage record that `/specify` shapes and `/backlog` grants route onward — and record the posture in the module's header comment, since the alternative is a later reader re-opening the thin label set as a missing-facets bug (which is what #1216 was).
- **Widen an existing call's `-q` projection before adding a second API call — once the call itself is proven complete.** When a later step needs one more field off data you already fetched, extend the `jq` filter rather than issuing a fresh request — `plugin/bin/lib/issues/claim-store.js`'s `listClaimEntries` widened `-q .[].name` to `-q '[.[] | {name, sha}]'` to get each claim blob's `sha` from its single directory listing (#820 D6), instead of a second lookup per entry. The projection survived; the endpoint under it did not: #820 kept the Contents-API listing explicitly *instead of* a Git Trees call, and that listing silently capped at 1000 entries until #3098 moved the same `{name, sha}` projection onto the Trees API (next bullet). Widening saves a call only on an endpoint whose result you have already shown to be whole.
- **A listing endpoint's size cap is part of its contract — check it before trusting the list as whole.** The REST Contents API's directory listing (`repos/{owner}/{repo}/contents/{dir}`) returns at most 1000 entries and says nothing when it stops: no `truncated` flag, no `Link` header, just a shorter array indistinguishable from a small directory. `claim-store.js`'s `listClaimEntries` read `claims-registry`'s `claims/` that way from #820 until #3098, by which point every claim sorting past the 1000th (roughly #2983 and up) was invisible to every caller. For a keyspace that grows without bound, read it through the Git Trees API (`repos/{owner}/{repo}/git/trees/{branch}` with `recursive=1` — as a GET; see the method-flip paragraph under the flag table), which carries an explicit `truncated` boolean, and return a truncated response as its own failure value (`'truncated'`, exit 3 from `plugin/bin/list-claims.js`), never as a short success. Route every prose call site through the one tested module rather than an inline `gh api` one-liner, as #3098 did for `_shared/issue-claims.md`, `_shared/github-pr-scan.md`, and `tidy/scan-procedures.md`: three hand-rolled copies of the capped call were three places the fix would otherwise have had to land.
- **A paged REST list that reports `total_count` is whole only when one page holds it all — paginate, or compare and fail closed.** `commits/{sha}/check-runs` and `commits/{sha}/status` page their arrays and report `total_count` beside them. `plugin/bin/lib/reconcile/red-tip.js` reads every page (`gh api --paginate`); `plugin/bin/pr-checks.js`'s `readBase` (#3258) asks for `per_page=100` and, when `total_count` exceeds the array, returns plain `red` with a `… truncated: N of M` `baseReason` instead of comparing against a short list. `plugin/bin/lib/release-preflight/pack.js` counts failures over one 100-row page while reporting `total_count` as the total — the shape not to copy. `per_page` goes in the path, never in `-f` (the method-flip paragraph above).
- **A run list for one sha is a history, not a state — keep each workflow's newest run before reading a failure as current.** `gh run list --commit {sha}` returns every run for the sha, re-runs included, so a failure a later run superseded still shows; check-runs (default `filter=latest`) and commit statuses are already latest per name. `plugin/bin/lib/pr-checks/classify.js`'s `newestRunPerWorkflow` (#3258) keys on `workflowName || name` and keeps the highest numeric `databaseId`, so the `--json` field list must request `databaseId`. A row that still cannot be ordered goes whichever way cannot loosen the verdict the list feeds.
- **Cross-check a documented failure-status word against `append.js`'s `STATUSES` enum before wiring a batch CLI's `catch` to log nothing on failure.** `plugin/bin/lib/log-decision/append.js`'s `STATUSES` (`AUTO`/`STAGED`/`KEPT-PROMPT`/`SCANNED`/`REFUSED`/`SKIP`) has no `FAILED` member. A consuming skill's prose can still document a `FAILED {time} — …` `decisions.md` template its own closing-summary tally counts on — `apply-refine-labels.js` (#844) shipped exactly this gap: its `catch` block only appends to the stdout JSON's `failed[]` array, never to `decisions.md`, because `FAILED` isn't a loggable status. Check the enum, not just the prose, before assuming a documented status word is writable via `appendEntry`.
- **On a path another process may prune, read and catch — never `existsSync`-then-read.** These modules read `.claude-tweaks/pipelines/` run-dirs that this project's own reconcile/archive passes prune concurrently, so an `existsSync` guard ahead of `readFileSync`/`readdirSync` is a window, not a check: the path can vanish between the two calls and the read throws exactly where the guard promised it could not. Read straight off and wrap in `try`/`catch` — an absent path and a mid-read prune then arrive as the same degraded value, with one code path instead of two. `plugin/bin/lib/wrap-up/engine-verify.js` shipped the guard-then-read pair three times (`resolvedIssueNumbers`, `memory-updates`'s index read, and its per-check map); two independent review agents reproduced it and `997e571c` fixed all three. A bare `existsSync` used as a *verdict*, with no read behind it (`resolveArchivedRunDir`, the `run-dir-archived` check), is not this hazard — the pair is.
- **One unit's throw never aborts the report, and the verdict a throw maps to is a decision.** The per-write `{ok, failed}` rule above generalizes past runner calls: any module mapping a registry of independent units to results wraps each unit in its own `try`/`catch`, because one uncaught throw prints no output at all and exits through Node's default path, silently colliding with the CLI's documented exit-code contract. `engine-verify.js`'s `runVerify` maps its `CHECKS` array that way and maps a throw to `fail`, not `unknown`: for a gate whose whole purpose is to block on doubt, a unit that could not determine its own state is evidence to block rather than to shrug. Pick the direction the module errs and say so beside the `catch` — the two are not interchangeable.
- **A corroborating read's failure demotes only the verdicts that read could have changed.** When a CLI pairs a primary read with a second one that can only add evidence in one direction, mapping every failure of the second read to one catch-all state overwrites primary verdicts it could never have overturned. `plugin/bin/pr-checks.js` (#3405) lists `gh run list --commit {headRefOid}` beside `gh pr view`'s `statusCheckRollup`: a head run can turn green into pending or red, never red into anything else. As first built, any runs-read failure returned `read-failed`, and `_shared/pr-check-gate.md` routes `read-failed` fail-open for `/test` and `/review`, so a red rollup plus a transient `gh run list` error let the gate pass. `90c16ad71` keeps the conclusive verdict (`if (runsFailure && verdict.state !== 'red')`), with a CLI test that fails on the prior code; the same CLI also skips the second read when the head is `stale`, so a transient failure cannot turn `stale` into `read-failed`. Before writing the second read's `catch`, list which primary verdicts it can change, and let its failure touch only those.
- **A corroborating read that can *loosen* a verdict moves the primary read's failure gate after it.** The bullet above covers a read that can only tighten. `plugin/bin/pr-checks.js`'s base comparison (#3258) can demote `red` to `inherited-red`, which `_shared/pr-check-gate.md` passes with a caveat, so the runs-read gate now tests the post-comparison verdict (`if (runsFailure && final.state !== 'red')`): when `gh run list` failed, a comparison that would conclude `inherited-red` reports `read-failed`, since a failing head run the partial read missed could be the one attributable failure. The loosening read's own failure still touches only what it could change: `applyBaseComparison` leaves plain `red` with a `baseReason`. Compare against the ref the PR merges into (`gh pr view --json baseRefName`), with the integration-branch resolver only as the fallback when the view names none: a PR into a release branch inherits that branch's red, not the default branch's.
- **`isIndeterminate` is the wrong failure filter when a probe's *negative* answer lives in stdout.** `plugin/bin/lib/hooks/git-exec.js` exports `isIndeterminate` (timeout/spawn/no-git) for failures where "the question went unanswered, rather than answered in the negative" — but that split only holds for a call whose negative answer *is* the non-zero exit (`merge-base --is-ancestor`, `rev-parse --verify`). For a probe that answers in stdout — `git ls-files -- <dir>` prints nothing for an untracked path and still exits 0 — a definitive `FAILURE.GIT_ERROR` (corrupt index, unreadable object store) is exactly as unanswered as a timeout, so filtering on `isIndeterminate` and letting `git-error` fall through to the falsy branch reads "the probe broke" as "the answer is no". `plugin/bin/lib/reconcile/archive-merged.js`'s `hasTrackedContent` (#2227) shipped that in `751f22c92` — the whole-branch review explicitly waved the `git-error` case through as "an answer" — and a later review lens caught it against the module's own sibling guard, `archiveRunDir`'s `ls-files-failed` refusal, which already fails closed on *any* failure; `67af77ee7` made every failure kind assume tracked. When a probe result selects a **route** rather than filling a report field, branch on `failure` as one condition, say which direction is safe in a comment beside it, and check the sibling probe in the same module before adopting a narrower filter than it uses.
- **A catch-all classifier reads the caller's own programming error as a transport failure — check the caller contract before the seam and answer with a distinct value.** `plugin/bin/lib/reconcile/pr-state.js`'s `classifyExecError` maps every throw that is not `gh-absent` to `'network-failure'`, so a misordered call — `resolvePrStateByNumber(4242, { cwd, repo })` — handed `execFileSync` a non-string `cwd`, threw `ERR_INVALID_ARG_TYPE`, and came back `'network-failure'`, the same answer as a real outage (#3029). `byNumberArgsValid` now rejects a non-string `repoRoot`, or a number that is not a positive integer or positive-integer string, before any `gh` call and returns `'invalid-arguments'`. It returns rather than throws because both by-number resolvers feed callers that must never throw (`archive-merged.js`'s SessionStart sweep, `_shared/github-pr-scan.md`'s per-PR loop). The guard owes that never-throw property itself: its first version called `String(number)` on every input, which throws on `Object.create(null)`; the whole-branch review caught it and `9cfb79dd6` checks `typeof` first. Pin each malformed input with its own assertion, a prototype-less object included (`tests/bin-lib/reconcile/pr-state.test.js`). A type guard does not cover a well-typed but wrong value: a `repoRoot` string naming a path that does not exist still reaches `execFileSync`, whose `ENOENT` is the same code a missing `gh` binary raises. `cb18c68b9` rechecks `repoRoot` only after a `gh-absent` classification, so a successful call pays no extra filesystem probe.
