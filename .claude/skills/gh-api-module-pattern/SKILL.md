# gh-api module pattern

How this repo writes Node modules that shell to `gh`. Two shipped instances define the pattern: `plugin/bin/lib/issues/capabilities-probe.js` (reads) and `plugin/bin/lib/issues/link.js` (writes). Two shipped bugs in one session (#626, #610) came from getting the flag rules wrong — read that table before writing any `gh api` call.

## The injectable runner

- The module takes `runner(args)`, invoked as if `gh ${args.join(' ')}`, returning stdout; a throw is a failed call. Export `defaultRunner` = `execFileSync('gh', args, { encoding: 'utf8' })` — always an argv array, never a shell string (no injection surface, no quoting bugs).
- **Every real spawn passes `windowsHide: true` in a form `tests/windows-hide-spawn-conformance.test.js` can see.** The scan reads each `child_process` call's own argument text: it accepts a literal `windowsHide` key there, or a bare identifier as the whole options argument whose own `const X = { … }` literal names it (`plugin/bin/lib/policy-schema.js`'s `execOpts`). A spread — `{ ...QUIET, timeout }` with the flag inside `QUIET` — satisfies neither and fails the full suite; `plugin/bin/pr-checks.js` shipped that shape and moved the key into each call (`8ead0c70b`). The `defaultRunner` one-liner above omits the flag, so a copy of it owes it too.
- **A read-only `git status` passes `--no-optional-locks` before `status`, after any `-C <path>`** (`['-C', wt, '--no-optional-locks', 'status', '--porcelain']`). A plain `status` rewrites the index under `index.lock`, so a sibling session's `git add`/`commit` in that worktree fails meanwhile. `tests/git-status-optional-locks.test.js` fails the full suite on an argv array or a `git … status` command string without it (#3464).
- Tests never touch real `gh`: fake runners branch on the `args` shape (`isGraphQL`, `isPost`-style lazy helpers) and `throw new Error('unexpected ' + args.join(' '))` on anything unhandled — a wrong endpoint fails loudly instead of passing silently. Record values inside the runner, assert after it returns (an `AssertionError` thrown *inside* a runner can be swallowed by the module's own try/catch).
- **A module may carry two runner seams, and they have opposite failure contracts.** `plugin/bin/lib/claim-targets/claim-targets.js` takes both: `deps.ghApi` — the `plugin/bin/lib/issues/claim-store.js` contract, which *never throws* and returns `{stdout, failure, status}` so a 404/409/422 arrives as data — for contents-API reads and writes, and `deps.gh` — the throwing runner above — for everything else (`repo view`, `label list/create`, `issue edit`, `issue comment`). Decide which seam a call belongs to before writing it: a never-throwing runner wrapped in `try/catch` reads as success on every rejection, and a throwing one used bare escapes uncaught.
- **An argv array stops shell injection, not flag injection.** A caller-supplied value that begins with `-` is still read as an *option* by the command itself, so any such value needs an end-of-options separator ahead of it. For `git` the separator is **`--end-of-options`, not `--`**: `--` switches `rev-parse --verify` and `merge-base` into pathspec mode and silently changes what they resolve — verified empirically before the fix landed, after `--` was tried first (#888 review lens 3b). `plugin/bin/lib/blast-radius-cli.js` is the shipped instance, on both of its revision-resolving calls. Pin the separator with a fake-runner test that asserts the exact argv array for a value like `-evil` (`tests/bin-lib/blast-radius-cli.test.js`), not just that the call succeeded. **`--end-of-options` alone never resolves a revision — it needs `--verify` alongside it.** A bare `git rev-parse --end-of-options <rev>` (no `--verify`) doesn't error and doesn't resolve either: it echoes `--end-of-options` back as a literal output line ahead of the resolved value, because plain `rev-parse` is in multi-arg parse-and-print mode, not single-revision mode. `plugin/bin/lib/docs-health/commit-ref.js`'s `classifyOne` (#2866) hit this directly — its first cut of peeling an annotated tag to the commit it points at used `rev-parse --end-of-options <sha>^{commit}` without `--verify` and failed with `error: unknown option \`end-of-options'`; adding `--verify` fixed it. Always pair the two.
- **A `git` path-list read also needs `-z`.** An argv that asks git for a path list (`--name-only` / `--name-status`, `ls-files`, `ls-tree`, `--numstat`, `status --porcelain`) passes `-z` and splits on NUL via `plugin/bin/lib/git-z.js`, besides `--end-of-options` before any ref. A read that never turns git's output into a path (an emptiness test, an exit code, display) carries the same-line `// git-path-read: not a path list (<reason>)` marker instead — see `plugin/skills/_shared/git-path-read.md`.
- **The same seam serves non-`gh` commands.** `plugin/bin/lib/blast-radius-cli.js` takes `deps.git` and `deps.readFile` on the contract above and cites this skill for it. Nothing in the injectable-runner rules is `gh`-specific — the argv-array rule, the loud-throw fake, and record-inside/assert-after all carry over unchanged; only the `gh api` flag table below is `gh`-only.
- **A seam that writes a body widens to `runner(args, input)` and pipes it on stdin, instead of staging a temp file.** `plugin/bin/pr-checklist.js` (#3263) rewrites a PR body with `gh pr edit {n} --body-file -`, its `gh` dep forwarding `input` into `execFileSync`'s options (`stdio: ['pipe', 'pipe', 'pipe']`, keeping `windowsHide` and `timeout` in the same literal). No file exists to leak, clobber across concurrent runs, or have denied by a `tmp/` path rule, and a fake `gh(args, input)` captures the exact bytes written so a test can assert the body is byte-identical outside the edited row. Reads keep the one-argument call; only the write passes `input`.
- **A module that edits an issue or PR body a human may have shaped replaces only its own marker block, never the whole body.** `plugin/bin/lib/reconcile/escalate-residue.js` re-rendered the consolidated structurally-stuck record's entire body on every pass and erased #2724's hand-shaped spec three times (2026-09-30, 2026-10-21, 2026-10-24) before #2724 fixed it. Its `withStuckPaths` is the shipped instance. Anchor the markers to whole lines (`^<!-- name -->\r?$` … `^<!-- /name -->(?=\r?$)`, multiline), so a marker named in prose or an inline-code span is never matched. Replace with a function replacer, so a `$&` or `$1` in the content is never expanded. Render the block with the body's own line ending, so a CRLF body gets no mixed endings. Append the block when a non-empty body has lost it, and render the full template only for an empty body. Pin it with a shaped fixture whose prose names the marker, plus exact-equality tests for CRLF and for a `$` in the content (`tests/bin-lib/reconcile/escalate-residue.test.js`).
- **A module that prunes entries from a record every checkout of the repo shares judges only the entries this checkout owns; every other entry counts as present.** The structurally-stuck fingerprint is path-less, so every checkout and machine appends its stuck run dirs to one record, and a path that is missing from this disk can still be stuck in the checkout that listed it. `plugin/bin/lib/reconcile/cache.js`'s `ownedPathExists(root)` (#4202) is the predicate `escalate-residue.js`'s `convergePaths` receives: it judges a listed path only when it is absolute, already normalized (`path.normalize(p) === p`) and strictly inside `<root>/.claude-tweaks/pipelines` via `isPathContained`, and reports it gone only when path-guard's `lstatType` says `missing`. The list is editable issue text, so a relative or `..`-bearing entry is never judged. Every doubtful case keeps the entry, so the record stays open rather than closing on a live path. Pin a foreign absolute path, a relative entry and an un-normalized entry that must all survive (`tests/bin-lib/reconcile/cache.test.js`'s `assertOwnedPathPredicate`, plus `tests/bin-lib/reconcile/archive-merged.test.js`'s foreign-path cases).
- **Bound every remote-contacting call on the seam; a local-only call owes no bound.** `execFileSync` has no default timeout, so a black-holed remote hangs the caller indefinitely. Every `gh` call and every network `git` call (`fetch`, `remote prune`, `ls-remote`) passes an explicit `timeout` — `GH_TIMEOUT_MS`, the shared export of `plugin/bin/lib/shared-primitives.js` (imported by `plugin/bin/lib/issues/claim-store.js`, `plugin/bin/claim-targets.js`, and the four call sites #2567 converted below), `FETCH_TIMEOUT_MS = 5000` (`plugin/bin/lib/reconcile/classify.js`, `pr-state.js`, `red-tip.js`), or `plugin/bin/lib/hooks/git-exec.js`'s `DEFAULT_TIMEOUT_MS = 10000` for anything routed through `runGit`. **`GH_TIMEOUT_MS` is a resolved value, not a literal — import it, never retype its default at a new call site.** Since #2567 it resolves once per process in precedence order `CLAUDE_TWEAKS_GH_TIMEOUT_MS` (env var) > the `gh-timeout-ms` policy key (`.claude-tweaks/policy.yml`, bounded 1000-60000 by `policy-schema.js`, which `shared-primitives.js` reads those bounds from rather than re-hard-coding them) > the same 5000 default, and it is exported as a lazy getter (`Object.defineProperty`) so a consumer that requires `shared-primitives.js` for `isPathContained` alone — `hooks/pre-tool-use.js`'s hot path, via `git-exec.js` — never pays for the policy read. A local `const GH_TIMEOUT_MS = 5000;` is therefore not merely duplication: it silently opts that call site out of a GitHub Enterprise Server project's raised bound, where a cold `gh` call routinely exceeds 5s. That is why #2567 replaced the four remaining copies (`lib/compose-subject.js`, `lib/repo-resolve.js`, `lib/worktree/cherry-pick-provenance.js`, and `bin/materialize.js`'s two) with the import. Two `gh` bounds deliberately stay their own values and say why beside themselves — `hooks/teardown-run.js`'s 15000 and `reconcile/preflight.js`'s 2000 — which is the same "widen (or narrow) deliberately with a stated reason" rule, not an exemption from it. A batched call earns a wider bound than the 5s single-call convention — `plugin/bin/fetch-sub-issues.js`'s runner passes `timeout: 30000` for a 50-alias GraphQL batch and states the reason in a comment beside it, rather than carrying 5000 over by copy. Local-only reads (`rev-parse`, `git config`, `branch -r --merged`) owe none; a bound on one is harmless, not a defect. When a direct `execFileSync('git', …)` runner does take a bound, import `GIT_TIMEOUT_MS` from the same module rather than typing a literal: it is the lazy getter #3051 added (`CLAUDE_TWEAKS_GIT_TIMEOUT_MS` > the `git-timeout-ms` policy key, bounded 1000-120000 > 30000), sized for `plugin/bin/lib/issues/claims-git-cas.js`'s claims-registry fetch/show/push. `plugin/bin/pr-checks.js`'s `rev-parse` runner and `plugin/bin/lib/compose-subject.js`'s `git diff` `gitRunner` (#3298) carry it on local reads, harmlessly. The `defaultRunner` shape above is the argv-array rule, not a complete options object — a `gh` runner copied from it still owes a `timeout`. On a seam that is otherwise all-local, widen it with a per-call options argument rather than bounding every call: `plugin/bin/residue.js`'s `runner(argv, opts)` takes such a per-call `execFileSync` options object (#663), and the seam's existing catch-all already maps a timeout kill onto its normal failure value. The `git remote prune` it was added for was since removed (`plugin/bin/lib/residue/probes/branches.js` states why beside the gap: "No `git remote prune` here: this probe's findings are read-only"); its bounded call site now is `plugin/bin/lib/residue/probes/release.js`'s `git ls-remote --tags origin 'v*'`, which passes `{ timeout: LS_REMOTE_TIMEOUT_MS }` (10000) so a timeout returns `null` into that probe's local-only fallback. That call first shipped unbounded and review caught it (#2882), so a probe that newly contacts a remote passes a `timeout` through `opts` in the same change, never as a follow-up. Omitting the bound is defensible only with a stated reason — `plugin/bin/lib/reconcile/shared-fetch.js` skips `timeoutMs` so `git-exec.js`'s `CT_HOOKS_GIT_TIMEOUT_MS` escape hatch still applies, and says so in a comment.
- **The same probe copied across N *separate* modules is the cross-module instance of the sibling-drift bullet below — consolidate into one shared, injectable helper rather than leaving each copy to drift on its own options object.** `plugin/bin/lib/repo-resolve.js`'s `ghAvailable(deps = {})` (#2017) replaced seven near-verbatim `execFileSync('gh', ['--version'], …)` probes scattered across `file-feedback.js`, `link-records.js`, `materialize.js`, `release-claim.js`, `compose-context/resolve-conditions.js`, `wrap-up/engine-verify.js`, and `repo-resolve.js` itself — each had drifted on its options object (`stdio: 'ignore'` vs `stdio: 'pipe'`, some with no `timeout` at all) before the consolidation. A grep-backed test (`tests/bin-lib/repo-resolve.test.js`) now pins `'--version'` to the single production site, so the count can't regress to N copies. A caller whose own seam shape differs (`engine-verify.js`'s `deps.gh(args, cwd)` takes a `cwd` the shared helper has no slot for) wraps the shared call in a one-line adapter rather than reintroducing a local copy.
- **Sibling default runners in one module drift on their options object — build both from one factory, once you've decided they should share it.** A module shelling to both `git` and `gh` on this seam ends up with a `defaultGit` and a `defaultGh` differing only in the command name, so a rule applied to one silently leaves the other behind. `plugin/bin/lib/wrap-up/engine-verify.js` shipped the pair unbounded, then gained `timeout: 5000` on `defaultGh` alone when the bullet above was applied to its remote-contacting call (`7569d4ce8`, refs #900), and needed a separate whole-branch review later the same day to notice `defaultGit` had been left behind (#1230, `76fd10487`) — one options object, edited twice, hours apart, with only eyeballing to show the copies disagreed. It now builds both from `makeDefaultRunner(cmd)` — one closure over one options object — so the two can no longer diverge by copy (#1222). Weigh what the factory costs before reaching for it: it forces symmetry, and the bullet above says symmetry is not automatically correct (that module's `git` calls are all local and owe no bound — a uniform 5s is harmless there, not required). Factor when the siblings genuinely should share their options; otherwise keep them separate and state beside each why it differs. Same remedy as the sync/async twin drift under **Async fan-out** below, on a different axis: factor at the point of duplication rather than diffing copies later.
- **A seam whose calls are *probes* runs quiet, and carries its own error class so the CLI can pick the exit code.** `plugin/bin/lib/verify/changed-files.js` (#1922) shells to `git` on exactly the seam above, and every real call passes `stdio: ['ignore', 'pipe', 'pipe']` — the posture `blast-radius-cli.js`'s own default `git()` already uses — because base resolution *asks questions it expects to fail*: `merge-base --is-ancestor` on a stale stamp anchor, `rev-parse --verify` on a ref that may not exist. Without the quiet posture a benign miss leaks git's own `fatal:` line to the stderr of a process that is about to exit 0, which reads to a caller as a real error. The message is not thrown away: the module raises a named `ChangedFilesError` carrying it, and the *CLI* — not the module — decides what an unresolvable base means per mode, since the same failure is a different class of problem depending on who asked. `verify.js --scope` maps it to the usage-class exit 2 (an unresolvable base is a malformed invocation, not a check failure), `verify.js --changed-files` to its own documented exit 1, and both re-`throw` anything that is not a `ChangedFilesError` rather than flattening an unrelated bug into a tidy exit code. A bare `throw new Error` on the seam would force the CLI to string-match its own module to tell the two apart.
- **The quiet posture is owed by any call the module catches and recovers from, not only by a probe seam — and a catch that reads the error text needs stderr `'pipe'`, not `'ignore'`.** `plugin/bin/lib/compose-subject.js`'s `realDeps.runner` is a fetch seam, so it stayed on `execFileSync`'s default, which echoes the child's stderr to ours: its handled `Unknown JSON field: "issueType"` rejection (the GraphQL fallback, #2561) printed gh's whole field list ahead of a successful compose, which read as a failure (#3028). It now passes `stdio: ['ignore', 'pipe', 'pipe']`, keeping stderr piped because `isUnknownIssueTypeField` matches on `err.stderr`/`err.message`. `reconcile/preflight.js`'s `['ignore', 'pipe', 'ignore']` suits only a catch that classifies on `err.code`.

- **A memoizing *decorator* on the seam is itself a runner — and it must be write-aware whenever its call graph reads back its own writes.** `plugin/bin/lib/reconcile/issue-list-cache.js`'s `createIssueListCache({base})` (#2505) returns `{runner}` on exactly the argv→stdout contract above, so it drops in wherever a `runner` is already injected — `escalate-residue.js` needed no change at all — and `reconcile/index.js` creates **one instance per `reconcile()` pass**, threading it through `archiveMerged`/`reapMerged` into `cache.js`'s `trackResidue`/`pruneResidueFailures`. Per-pass, never a module-level singleton: `reconcile()` is called in-process from `hooks/session-start.js` as well as from `bin/hooks.js reconcile`, so a module-scope memo would serve a later pass a read taken during an earlier one. The hazard that decides the memo's *shape* is read-after-write on the same seam: those callers also write through that runner (`issue create`/`edit`/`close`/`reopen`) and read back within the pass — `escalate-residue.js`'s `structurally-stuck` fingerprint is deliberately path-less, so every stuck dir in a pass converges on the same consolidated record and each read depends on the previous write. Memoizing the raw response string would file N separate issues instead of one (regressing #1811-#1817's original symptom) and let a resolve loop resurrect paths it just removed, so the record never closes. Memoize the **parsed** value and apply each write's effect to it in place — same correctness as invalidating on every write, at zero extra round trips. Three rules keep that honest: only the exact read shape is memoized (`argv[0] === 'issue' && argv[1] === 'list'`) and every other call executes; a throw or an unparseable response is never cached, so the next call retries rather than replaying a failure; and the write-effect applier encodes *this* call graph's write vocabulary (a verb it doesn't know is a deliberate no-op, never a throw and never an invalidation), which is only defensible while the decorator has one caller — say so in the module header, as `issue-list-cache.js` does. Pin it with a stateful fake `base` that counts calls and asserts both the count and that a read after a write reflects the write (`tests/bin-lib/reconcile/issue-list-cache.test.js`), plus a two-instance test proving no cross-pass sharing.
- **Caching a *failure* is the one exception to "a throw is never cached", and it needs an exact timeout check plus a TTL.** For a cheap call, retrying is the recovery. For a long-bound remote call, every later caller would re-pay the full timeout, so remembering it is the fix. `plugin/bin/lib/docs-health/commit-ref.js`'s `deepenShallowClone` (#2988) writes a timeout marker with a 30-minute `TIMEOUT_MARKER_TTL_MS` after its 120s `fetch --unshallow` times out. The marker is a file in the git-common dir, not an in-process memo, because `docs-health --budget > 1` runs `verify-commit` as a separate process for each citation. Its `isTimeoutError` is `err.code === 'ETIMEDOUT'` alone, not the three-way check `async-fan-out.md`'s `retryOnTimeout` bullet documents. When `execFileSync`'s own `timeout` fires, the error carries `{code: 'ETIMEDOUT', signal: 'SIGTERM'}`. A git killed from outside carries the same `signal: 'SIGTERM'` with no `code` (probed on Node 22). `err.signal === 'SIGTERM'` would therefore record that crash as a timeout and block every retry for the whole TTL. Choose the check by which mistake is cheap. For a retry, a false positive costs one extra attempt, so the broad check is fine. For a cached failure, missing a real timeout costs one extra attempt, and a false positive blocks recovery, so use the exact code.
- **`file-lock.js`'s wait is sized for bookkeeping, so a lock held across a long call needs a wait longer than that call's bound, or it serializes nothing.** `acquireLock` gives up after `CLAUDE_TWEAKS_LOCK_WAIT_MS` (500ms by default) and returns `null`, and its callers then proceed unlocked. That is right for a read-modify-write that takes milliseconds. For a critical section bounded at N ms it means every waiter falls through after half a second and races the holder, which is exactly the concurrency the lock was added to stop, and nothing reports it. `commit-ref.js`'s `deepenShallowClone` (#2988) holds its lock across the 120s `--unshallow` fetch, so it waits `DEEPEN_TIMEOUT_MS + LOCK_WAIT_MARGIN_MS`. The 15s margin keeps a waiter's deadline from landing just before the holder's fetch finishes. `file-lock.js` has no per-call wait option, so that module sets the env var around its one `acquireLock` call and then restores the earlier value, or removes it if it was unset. Do not copy that env swap. A second long-hold caller adds a `waitMs` option to `acquireLock`/`withLock` and moves `commit-ref.js` onto it in the same change. Put the lock in the repo's real git dir, never at `path.join(root, '.git', …)`. In a linked worktree `.git` is a file, so `mkdirSync` there throws `ENOTDIR` and `acquireLock` silently fails open. Resolve the dir with `git rev-parse --git-common-dir`, then `path.resolve(root, out)`, because the output can be relative. Skip `--path-format=absolute`: it needs git 2.31 or later, and no sibling module uses it. Every worktree of the repo shares that dir, which is also where git keeps its own `shallow.lock`.
- **Pick the git root by what the module reads: `--show-toplevel` for working-tree facts, the `--git-common-dir` parent only for state that must outlive a worktree.** From a linked worktree the common-dir parent is the MAIN checkout, so a `git diff {base}...HEAD`, a `docs/` scan or a frontmatter read run against it sees the main checkout's HEAD and tree and comes back empty without erroring. `plugin/bin/wrap-up-engine.js` keeps both on purpose (#3431): `resolveFactsRoot` (`--show-toplevel`) feeds `gatherFacts` and `buildJourneyFrontmatter`, while `resolveRepoRoot` (common-dir) anchors the telemetry TSV, archived-run lookups and `policy.yml`. A regression test for a root fix needs a fixture that differs between the two roots at every call site that takes the root: the first #3431 test left `buildJourneyFrontmatter` on the wrong root and stayed green because the journey file was identical in both checkouts.
- **A module that parses git's output pins that output's format against the user's and the repo's git config.** A parser written against git's defaults misreads the output under another config, and nothing fails. `diff.noprefix` and `diff.mnemonicPrefix` change the `a/`/`b/` header prefixes. `color.ui=always` and an external diff driver rewrite the text. `core.quotePath`, on by default, prints a non-ASCII path quoted and escaped, so `café.txt` no longer matches its own name. For a path list, pass `-z`, which prints every path verbatim (`plugin/bin/lib/verify/changed-files.js`). For patch text, pass every flag explicitly, as `plugin/bin/lib/review-context/build.js` does (#3020): `-c core.quotePath=false diff --no-color --no-ext-diff --src-prefix=a/ --dst-prefix=b/`. Its first version passed none of them, and an added non-ASCII file over the size cap kept its whole diff chunk. Pin the flags two ways: real-git tests that set the config in the fixture repo, and an exact-argv assertion for the flags no fixture test exercises (`tests/bin-lib/review-context/build.test.js`).
- **A module that switches git's config off through the environment also scrubs the config the environment carries.** `GIT_CONFIG_GLOBAL=/dev/null` and `GIT_CONFIG_NOSYSTEM=1` stop the user's and system config files, but environment-carried config still applies: `GIT_CONFIG_PARAMETERS` (what a parent `git -c key=value` exports to its children) and `GIT_CONFIG_COUNT` with `GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n`. Two more inherited variables change what the call reads or prints: `GIT_COMMON_DIR` points it at another repository, as `GIT_DIR` does, and `GIT_DIFF_OPTS` sets the context length of every diff it emits. `plugin/bin/lib/staged-patch/stack-check.js`'s exported `gitEnv` deletes all of them (#3997). Before that it deleted only `GIT_DIR`, `GIT_WORK_TREE` and `GIT_INDEX_FILE`, so `core.autocrlf=true` injected through `GIT_CONFIG_COUNT` made 11 re-derive tests fail on an LF checkout, and review then found `GIT_COMMON_DIR` and `GIT_DIFF_OPTS` still passing through. A new module that isolates git this way imports `gitEnv` rather than building its own env object. `tests/bin-lib/staged-patch/stack-check.test.js` pins the deletes, including a `GIT_CONFIG_KEY_10` positive and a `GIT_CONFIG_KEY_X` lookalike that must survive.

## The three `gh api` value mechanisms (the bug source)

| You are passing… | Flag | Why |
|---|---|---|
| gh's literal `{owner}`/`{repo}`/`{branch}` placeholder in a **field value** | `-F` | Only `-F` substitutes; `-f` sends the braces as a static string (#626) |
| An **already-resolved** string bound to a GraphQL `String!` variable | `-f` | `-F` type-coerces an all-numeric name (`2048`) to an Int and GraphQL rejects it (#610) |
| A numeric **REST body** field (`sub_issue_id`, `issue_id`) | `-F` | So it lands as an integer, not a string |

URL *path* placeholders (`repos/{owner}/{repo}/…`) are a fourth thing: always substituted, no flag involved. Never collapse these into "always -F for owner/repo" — that generalization is what shipped #610's bug, with a plan-authored test pinning the wrong flag.

**Any `-f`/`-F` field flips `gh api`'s default method from `GET` to `POST`.** `gh help api`: "The default HTTP request method is `GET` normally and `POST` if any parameters were added" — so a REST *read* that needs a query parameter passes `--method GET` explicitly (gh then sends the fields as a query string), or puts the parameter in the path (`…/git/trees/{branch}?recursive=1`). Written bare, `gh api repos/…/git/trees/{branch} -f recursive=1` is a POST to a path with no POST route. On `claim-store.js`'s never-throwing seam a 404 or 422 answer classifies as `{failure: null, status}` with no stdout, and `listClaimEntries` as first written in #3098 parses absent stdout as `{}` — an empty listing reported as success, the silent partial list that change set out to remove. A fake-runner test asserting `['-f', 'recursive=1']` pins the argv shape, not what GitHub does with it: pin `--method GET` (or the `?recursive=1` path) in the asserted argv. `gh api graphql` is unaffected — it is always a POST.

**A REST `--json <field>` name is not portable across `gh` versions — prefer the GraphQL equivalent when one exists.** `gh issue view {n} --json parent` throws `Unknown JSON field: "parent"` on `gh` 2.92.0 but works on 2.96.0+ — the REST JSON field list changes between releases, and a caller can only detect support by trying and parsing the error. `Issue.parent` via `gh api graphql` (`repository(owner,name){ issue(number){ parent{ number } } }`) reads the identical data on every `gh` version that can run GraphQL, because the GraphQL schema is server-side, not tied to the installed CLI's REST field allowlist. `plugin/bin/lib/wrap-up/engine-verify.js`'s `resolveParent` migrated from the former to the latter for exactly this reason (#1841) — reusing the existing `buildNativeParentQuery` builder (see `batching-failure-posture.md` in this skill's directory). When a REST `--json` read is genuinely simpler and version drift isn't a concern (a field present since `gh`'s earliest supported version), the plain REST form is still fine: prefer GraphQL for a *newer or less common* field, not as a blanket rule against `--json`.

**A caller-overridable REST path has no bound-variable escape hatch.** The `{owner}`/`{repo}` path placeholders above always resolve from `gh`'s own ambient repo context (the cwd's git remote) — there is no `-f owner=…`/`-F owner=…` equivalent that rebinds a REST *path* segment the way `-f owner=…` rebinds a GraphQL variable (row 2 above). A CLI that must honor its own `--repo owner/name` override for a REST call therefore has to build the path string itself — `plugin/bin/fetch-sub-issues.js`'s `--resolve-retries` retry loop does exactly this (`` `repos/${owner}/${repo}/issues/${n}/sub_issues` ``, #1153 review finding). That loses the placeholder mechanism's implicit safety: the interpolated `owner`/`repo` values need their own validation before they reach the path, since a lax upstream parser (this repo's shared `parseRepo` accepts any non-`/` segment, including `.`/`..`) can otherwise redirect the call. `fetch-sub-issues.js` added a narrow `owner !== '.' && owner !== '..'` guard at its own call site rather than tightening the shared `parseRepo` (9 callers, most never resolve a caller-supplied `--repo` at all) — a reminder to validate at the interpolation site when you can't fix the shared resolver's blast radius in the same change.

**A ref name interpolated into a REST path is encoded per segment.** Git allows `#` and `%` in a branch name, and a URL reads them as a fragment start and an escape, so `` `repos/{owner}/{repo}/commits/${branch}` `` can address another ref. `plugin/bin/pr-checks.js`'s `readBase` (#3258) builds the segment as `branch.split('/').map(encodeURIComponent).join('/')`, keeping `/` a separator; `tests/bin-lib/pr-checks/cli.test.js` pins the argv with `release/v1#x`. `plugin/bin/lib/release-preflight/pack.js`'s branch-tip read and `plugin/bin/lib/hooks/teardown-run.js`'s `git/refs/heads/${branch}` delete still interpolate the bare name.

`gh api graphql` is where two of these rows collide: a `String!` variable needs `-f`, and `-f` never expands `{owner}`/`{repo}`, so the placeholder mechanism is unavailable to a GraphQL variable. Resolve the slug locally instead — `plugin/bin/lib/hooks/git-exec.js`'s `repoSlugOf` parses it out of `remote get-url origin` and is shared by `reconcile/pr-state.js` and `reconcile/release-merged.js` (#1082) — and pass it as `-f owner=…`/`-f name=…`. `claim-store.js`'s `resolveRepoSlugOrThrow` (the `gh repo view --json nameWithOwner` form, which `claim-targets.js` delegates to since #3438; its non-throwing sibling `resolveRepoSlug` returns `null` on any failure) is for a seam holding a `gh` runner but no repo root; `hooks/teardown-run.js`'s inline copy of the same regex predated the shared helper and now uses `repo-resolve.js`'s `parseRepo` directly (#2747) — see the `--hostname` bullet below. **This file covers Node modules only** — the identical resolve-then-`-f` rule applies verbatim to `gh api graphql` calls written directly in skill-prose bash blocks (no `execFileSync` seam to share a helper through); there, the established shape is `read -r OWNER REPO <<< "$(gh repo view --json owner,name -q '.owner.login + " " + .name')"` immediately before the call, as `plugin/skills/_shared/github-pr-scan.md`, `plugin/skills/init/bootstrap/step-17-work-record-backend.md`, and `plugin/skills/capture/SKILL.md`'s native-type GraphQL fallback all do.

**A `--repo` argument is a *slug*, and the slug is host-qualified — never hand-roll `` `${owner}/${repo}` `` at one.** `plugin/bin/lib/repo-resolve.js`'s `repoSlug({host, owner, repo})` (#2240) is the producer of the value `gh -R/--repo` takes: bare `owner/repo` on github.com, `host/owner/repo` on a GitHub Enterprise Server host, with a missing `host` reading as github.com so a caller threading an optional host through needs no guard of its own. Interpolating `` `${owner}/${repo}` `` at a `--repo` call site instead silently drops that host and sends every GHE call to github.com, where it 404s or — worse — resolves against a same-named public repo. `plugin/bin/lib/wrap-up/pack.js`'s `unblocked` probe shipped exactly that while `repoSlug` was already imported two lines above the bug (#2425, fixed in `06e14b626`); four independent review lenses each found it, which is what a bug class with no written rule looks like. The producers that go through `repoSlug` today are `release-claim.js`, `file-feedback.js`, `apply-refine-labels.js`, `materialize.js`, `lib/compose-subject.js`, `lib/release-claim/release.js`, `lib/repair-claim/repair.js`, and `lib/wrap-up/pack.js` — **copy one of those, not the paragraph above.** `git-exec.js`'s `repoSlugOf` is a different helper with a different contract: its regex keeps only the last two path segments, so it drops the host *by construction*. That is correct for the GraphQL `-f owner=…`/`-f name=…` pair it was written for and wrong for a `--repo` flag or any host-sensitive REST path, so its `reconcile/` consumers (`escalate-residue.js`'s `--repo`, `release-merged.js`/`claim-store.js`'s `repos/${repoSlug}/…` paths) are github.com-only by inheritance — a known limitation to widen deliberately, never a shape to copy into a new call site. `lib/wrap-up/engine-verify.js`'s `upstream-feedback` check is the one remaining hand-rolled `` `${owner}/${repo}` ``, tolerable only because its own URL regex matches `github.com` alone; widening that regex without switching it to `repoSlug` reintroduces #2425.

**A search-backed call needs a *canonicalized* slug; a REST call survives without one.** GitHub's search API — `gh pr list --search`, `gh issue list --search`, `gh search prs/issues` — does **not** follow a repository rename or transfer redirect, while REST (`gh api repos/{owner}/{repo}/…`) does. So a slug derived from a stale `origin` remote keeps working on every REST call in a module while the search-backed calls in the same module return zero rows, or `Invalid search query`, with no error the caller can see — an empty result set is indistinguishable from "nothing matched in this period." Canonicalize before querying: `gh repo view {slug} --json nameWithOwner -q .nameWithOwner` follows the redirect, and whatever it returns is the slug every subsequent call uses. `plugin/bin/activity-gather.js` does exactly this once per repo, ahead of all six of its queries (#2757). The failure is silent by construction, so a probe cannot find it unless the probe resolves the slug the way the code does: #2757's own Task 0 ran every query against the hand-picked post-transfer slug, proving the argv shapes while never exercising resolution, and four of six queries came back empty on the first real run — after the task reviews and the whole-branch review had passed.

**A REST call with no `--repo`/`-R` flag needs `--hostname` instead, from the same `parseRepo` host field.** `gh api --method DELETE repos/{owner}/{repo}/…` has no `--repo` slot, so a GitHub Enterprise Server remote needs `--hostname {host}` alongside the call, omitted when `host` is absent or `github.com`. `plugin/bin/lib/hooks/teardown-run.js`'s `defaultGhApiDelete(args, host)` (#2747) is the shipped instance: it resolves `{host, owner, repo}` via `parseRepo` directly, not `repoSlug`, since this call needs the host as its own flag, not folded into a `--repo` value. The same holds when a host-qualified `--repo` feeds `gh api graphql`: the host travels as `--hostname {host}` placed right after `graphql`, omitted for `github.com` or no host. `plugin/bin/lib/issues/resolved-refusal.js`'s `fetchResolvedRefusalEvidence` (#3597) is the instance — a fake-runner test on the exact argv for a GHE host pins it, since a dropped flag silently queries `github.com`.

**A `--repo` *consumer* must accept both shapes.** Once producers emit host-qualified slugs, a CLI taking `--repo` receives either form, so the `github.com/` prefix `parseRepo` needs for a bare value is conditional, not unconditional — `plugin/bin/lib/number-list-cli.js` branches on `opts.repo.split('/').length >= 3` (#2425), because prefixing an already-qualified value builds a 4-segment string that `parseRepo`'s 3-segment regex rejects outright, turning a valid GHE invocation into "could not resolve owner/repo". A new `--repo`-taking CLI copies that branch; a fake-runner test asserting the exact argv for both a bare and a host-qualified `--repo` value pins it, the same way the end-of-options rule above is pinned.
