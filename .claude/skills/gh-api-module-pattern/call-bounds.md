# Call bounds — gh-api-module-pattern

Lazy-loaded from `SKILL.md` (this skill's directory): read it before adding a `gh` call or a network `git` call (`fetch`, `ls-remote`, `remote prune`) to a module, or before choosing a timeout for one.

- **Bound every remote-contacting call on the seam; a local-only call owes no bound.** `execFileSync` has no default timeout, so a black-holed remote hangs the caller indefinitely. Every `gh` call and every network `git` call (`fetch`, `remote prune`, `ls-remote`) passes an explicit `timeout` — `GH_TIMEOUT_MS`, the shared export of `plugin/bin/lib/shared-primitives.js` (imported by `plugin/bin/lib/issues/claim-store.js`, `plugin/bin/claim-targets.js`, and the four call sites #2567 converted below), `FETCH_TIMEOUT_MS = 5000` (`plugin/bin/lib/reconcile/classify.js`, `pr-state.js`, `red-tip.js`), or `plugin/bin/lib/hooks/git-exec.js`'s `DEFAULT_TIMEOUT_MS = 10000` for anything routed through `runGit`. **`GH_TIMEOUT_MS` is a resolved value, not a literal — import it, never retype its default at a new call site.** Since #2567 it resolves once per process in precedence order `CLAUDE_TWEAKS_GH_TIMEOUT_MS` (env var) > the `gh-timeout-ms` policy key (`.claude-tweaks/policy.yml`, bounded 1000-60000 by `policy-schema.js`, which `shared-primitives.js` reads those bounds from rather than re-hard-coding them) > the same 5000 default, and it is exported as a lazy getter (`Object.defineProperty`) so a consumer that requires `shared-primitives.js` for `isPathContained` alone — `hooks/pre-tool-use.js`'s hot path, via `git-exec.js` — never pays for the policy read. A local `const GH_TIMEOUT_MS = 5000;` is therefore not merely duplication: it silently opts that call site out of a GitHub Enterprise Server project's raised bound, where a cold `gh` call routinely exceeds 5s. That is why #2567 replaced the four remaining copies (`lib/compose-subject.js`, `lib/repo-resolve.js`, `lib/worktree/cherry-pick-provenance.js`, and `bin/materialize.js`'s two) with the import. Three `gh` bounds deliberately stay their own values and say why beside themselves — `hooks/teardown-run.js`'s 15000, `reconcile/preflight.js`'s 2000, and `policy-schema.js`'s `HOOK_FORGE_PROBE_TIMEOUT_MS` (5000 per attempt, which the session-start and pre-tool-use hooks pass to `detectIntegrationModel` so its once-retried probe keeps a 15 s hook worst case rather than inheriting a 60 s `gh-timeout-ms`, #4578) — which is the same "widen (or narrow) deliberately with a stated reason" rule, not an exemption from it. A batched call earns a wider bound than the 5s single-call convention, rather than carrying 5000 over by copy. Every batched `gh` runner outside reconcile imports `shared-primitives.js`'s `GH_BATCH_TIMEOUT_MS` — `max(30000, GH_TIMEOUT_MS)`, so a raised `gh-timeout-ms` widens a batch too (#4815) — and never retypes `timeout: 30000`: `plugin/bin/fetch-sub-issues.js`'s 50-alias GraphQL batch, `plugin/bin/lib/number-list-cli.js`, `plugin/bin/dispatch-resume.js`'s native-dependency read, `plugin/bin/stuck-open-prs.js`'s linked-PR read, `plugin/bin/lib/issues/link.js` and `plugin/bin/lib/preflight-records/preflight-records.js` among them. Reconcile's two 50-alias batches are a deliberate exception that keeps its own 15 s and does not follow `gh-timeout-ms`: `plugin/bin/lib/reconcile/pr-state-batch.js`'s `BATCH_TIMEOUT_MS` ("one call covers up to 50 lookups — roomier than pr-state.js's per-item 5s, same as its BULK_TIMEOUT_MS") and `plugin/bin/lib/reconcile/pr-state.js`'s `BULK_TIMEOUT_MS` ("one chunked call covers many branches — roomier than FETCH_TIMEOUT_MS's per-branch 5s"). Local-only reads (`rev-parse`, `git config`, `branch -r --merged`) owe none; a bound on one is harmless, not a defect. When a direct `execFileSync('git', …)` runner does take a bound, import `GIT_TIMEOUT_MS` from the same module rather than typing a literal: it is the lazy getter #3051 added (`CLAUDE_TWEAKS_GIT_TIMEOUT_MS` > the `git-timeout-ms` policy key, bounded 1000-120000 > 30000), sized for `plugin/bin/lib/issues/claims-git-cas.js`'s claims-registry fetch/show/push. `plugin/bin/pr-checks.js`'s `rev-parse` runner and `plugin/bin/lib/compose-subject.js`'s `git diff` `gitRunner` (#3298) carry it on local reads, harmlessly. The `defaultRunner` shape above is the argv-array rule, not a complete options object — a `gh` runner copied from it still owes a `timeout`. On a seam that is otherwise all-local, widen it with a per-call options argument rather than bounding every call: `plugin/bin/residue.js`'s `runner(argv, opts)` takes such a per-call `execFileSync` options object (#663), and the seam's existing catch-all already maps a timeout kill onto its normal failure value. The `git remote prune` it was added for was since removed (`plugin/bin/lib/residue/probes/branches.js` states why beside the gap: "No `git remote prune` here: this probe's findings are read-only"); its bounded call site now is `plugin/bin/lib/residue/probes/release.js`'s `git ls-remote --tags origin 'v*'`, which passes `{ timeout: LS_REMOTE_TIMEOUT_MS }` (10000) so a timeout returns `null` into that probe's local-only fallback. That call first shipped unbounded and review caught it (#2882), so a probe that newly contacts a remote passes a `timeout` through `opts` in the same change, never as a follow-up. Omitting the bound is defensible only with a stated reason — `plugin/bin/lib/reconcile/shared-fetch.js` skips `timeoutMs` so `git-exec.js`'s `CT_HOOKS_GIT_TIMEOUT_MS` escape hatch still applies, and says so in a comment. To pin a consumer's batched bound in a test, use `tests/helpers/gh-timeout-probe.js`'s `captureGhTimeout` (it stubs `child_process.execFileSync`, evicts the consumer and `shared-primitives.js` from the require cache, and lets the test choose whether the env var is set before the consumer loads or after its factory runs), with `45000` as the above-floor case and `10000` as the below-floor case.
