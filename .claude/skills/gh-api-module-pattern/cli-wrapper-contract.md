## The CLI wrapper contract

- Logic lives in an exported `run(argv, deps)`; every side effect (`runner`, `ghAvailable`, `remoteUrl`, `stdout`, `stderr`) goes through `deps` so tests inject fakes. **Every** `deps` call that can throw (e.g. `remoteUrl` outside a git repo) is try/caught into the documented exit-code contract — an un-wrapped deps call is where #610's one post-review high landed.
- **A CLI that tests call in-process meets the entry contract** (#5374; `plugin/bin/resolve-policy.js` is the worked example). It exports `run` and `realDeps`; `argv` is `process.argv.slice(2)`, and `run` returns an integer exit code or a Promise of one. The script entry is the file's last statement: `if (require.main === module) process.exitCode = run(process.argv.slice(2), realDeps);`. The standard io keys, each present only when the CLI uses it, are `stdout(text)`, `stderr(text)`, `cwd()`, `env` (a plain object, read-only), `stdin()` (the whole input as a string) and `homeDir()`. Above the guard and in everything `run` calls there is no `process.exitCode`, `process.exit()`, `process.chdir()` or write to `process.env`. A relative path is resolved against `deps.cwd()`, never left to `path.resolve` or `fs`: a file path the unconverted CLI handed to `fs` as written takes an unnormalized join (`resolveAgainst(deps.cwd(), p)`, `plugin/bin/lib/health-core/io.js`), so a trailing slash or a `..` after a symlink still reaches the kernel; `path.resolve(deps.cwd(), p)` only where the CLI already normalized or needs one absolute, normalized value, such as a root passed to `git -C` (#5380). Read `deps.cwd()` only where a relative path or a child process needs it: `realDeps.cwd()` is `process.cwd()`, which throws in a deleted working directory. An eager read therefore turns an absolute-path or no-path invocation that worked there into a failure; #5385's final review caught four converted CLIs doing this. Making the read lazy leaves a defaulted option `undefined`, so a message that echoed it names the resolved default instead (`release-bootstrap.js`'s `root is not a directory:`, #5385); `cwdOrUndefined(d)` in `plugin/bin/lib/health-core/io.js` is the degrade for a CLI that carries on without a cwd. Every child process is started with a `cwd` derived from `deps.cwd()` and with `env: deps.env`, and a library function on the CLI's path takes that `env` as an option whose default is the inherited environment, so a `gh` or `git` stub on an injected `PATH` is not skipped. A gh host or config lookup on the CLI's path (`gateOriginRepo`, `ghOptions`, the gh config dir) reads `GH_HOST`, `GH_CONFIG_DIR` and the home directory from the injected `env`/`homeDir` too — pass them through `injectedGhDeps(pickInjected(deps))` (`plugin/bin/lib/repo-resolve.js`; worked example `plugin/bin/lib/wrap-up/engine-verify.js`), since a `GH_HOST` set only in `deps.env` is otherwise ignored with no error. The process-wide timeout knobs are the named exception: `plugin/bin/lib/shared-primitives.js`'s shared `gh`/`git` timeouts read `CLAUDE_TWEAKS_GH_TIMEOUT_MS`, `CLAUDE_TWEAKS_GIT_TIMEOUT_MS` and the `gh-timeout-ms` / `git-timeout-ms` keys of the `policy.yml` at the real working directory once per process, `plugin/bin/lib/hooks/git-exec.js`'s `runGit` reads `CT_HOOKS_GIT_TIMEOUT_MS` from the real `process.env`, and `plugin/bin/lib/file-lock.js`'s lock wait reads `CLAUDE_TWEAKS_LOCK_WAIT_MS` on each acquire from the `env` passed to `withLock`/`acquireLock` (default: the inherited `process.env`), which is threaded today for `hooks.js`'s `ledger-row` (`appendRow`/`settleRow`, `tests/hooks-ledger-row.test.js` sets the wait through the injected env in-process). A caller that passes no `env` (`carryForward`, `log-decision` and `verify-expectations`) still reads the real environment. An in-process test cannot set the other knobs, or this one through such a caller, through `env`, so a test of those is a `spawnCli` test. Tests call the CLI through `tests/helpers/run-cli.js` (`runCli`, or `runCliSync` for a synchronous `run`), passing an absolute `cliPath`; the helper fails the test on a leaked `process.exitCode`, working directory, `process.env` key, signal listener, direct stdout/stderr write, or an `os.homedir()` call under an injected home; each converted CLI keeps one or two `spawnCli` smoke tests for the script entry, shebang and exit code. The helper's `env` defaults to `{}` and is the whole environment the CLI sees, so a CLI that starts `git` or `gh` needs `PATH` (and `SystemRoot` on Windows) in the `env` the test passes. Module-level state under `plugin/bin` (the forge probe's memos, for example) survives between in-process calls in one test file; a case that depends on it passes `fresh: true`, which clears `require.cache` under `plugin/bin` first. A result one test computes and another reuses (a spawned script run compared against an in-process call, say) goes through a memoized helper, never a file-level variable an earlier test assigns, so every test passes alone under `--test-name-pattern` (#5379, `tests/bin-lib/wrap-up/engine-cli.test.js`'s `scriptPlan()`). The helper fails closed: after merging `realDeps` with the test's fakes, it replaces a key named in `FAIL_CLOSED_KEYS` (`runner`, `gh`, `ghAvailable`, `runHook`, `spawn`, `runSuite`) that still holds the CLI's real value with a function that throws, and records the reach so a CLI that catches the throw still fails the test; `allowRealRunner: true` lifts it for one call. The list is by key name: a `realDeps` key that can start `gh` or an arbitrary command carries one of those names, and a record converting a CLI whose `realDeps` holds such a seam under another name (for example `execFileSync`, `runPremiseCheck`) adds that name to `FAIL_CLOSED_KEYS` in the same change. A git-only seam (`git`, `gitRunner`) is deliberately not on the list: it runs real git against the injected `cwd` and `env`, which is the behaviour under test. `tests/bin-lib/cli-entry-conformance.test.js` pins the three structural rules (exports `run`, has the guard, no `process.exitCode`/`process.exit(` above it) for every top-level `plugin/bin/*.js`, with a `NOT_YET` list that only shrinks; `hooks.js` is the one named `EXEMPT` entry there (its entry calls `process.exit(code)` and it has a require-time prefilter; the test names the reason and a proof file), kept apart from the `NOT_YET` list.
- **An injected side-effect dependency (an event emitter, a logger) lives in the exported `realDeps`, never only inside the `require.main` guard.** Wiring it only under the guard keeps tests off the real file but makes the wiring untestable: #5902's final review showed that deleting it left every test green, so a producer could silently stop emitting. Put the real value in `realDeps`, list its key in `tests/helpers/run-cli.js`'s `FAIL_CLOSED_KEYS` so an in-process `runCli` test never reaches it, and give each CLI a one-line test that `realDeps` carries the key.
- **Passing `tests/bin-lib/cli-entry-conformance.test.js` is not meeting the entry contract.** The scan checks the three structural rules only, so a CLI that exports no `realDeps`, passes nothing to `run` from its guard, or resolves a relative path with `path.resolve` instead of `deps.cwd()` passes it. `plugin/bin/ci-workflow-review.js` (#5162) shipped all three past the scan, and review caught them; 8f939ddea added `realDeps`, resolved `--root` against `deps.cwd()`, and moved the CLI test's in-process cases onto `runCliSync`. A new CLI's own test therefore carries what the scan cannot see: its in-process cases go through `runCli`/`runCliSync`, and each path-taking flag gets a relative-path case under an injected `cwd` that differs from the real one.
- **Converting an existing CLI to the entry contract takes two proofs the tests-side journey does not cover.** `docs/journeys/call-a-plugin-bin-cli-in-process-from-a-test-5374.md` starts from a CLI that already meets the contract; the `plugin/bin` side of the change needs these first. (1) Pin the script's output with real-process tests committed before the split, so the split is checked against the old behavior and not against itself: #5374 committed five `resolve-policy.js` script cases in `tests/resolve-policy-entry.test.js` (8fa20f94e) before splitting the file into a core and a printing `run` (75fb7d40e). (2) Prove that each `git` or `gh` child on the CLI's path got the injected `env` with an env-only fixture, not by reading the call: two repos, A with no remote and B with an `origin` and a recorded `origin/HEAD`, the CLI's `cwd` in A and `GIT_DIR=<B>/.git` only in the injected `env`, so a child that inherits the real environment reads A and a child that got `env: deps.env` reads B's remote (`forgePair` in `tests/forge-probe-env.test.js` and `tests/resolve-policy-entry.test.js`). Strip `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and `GIT_COMMON_DIR` from the fixture's own setup `git` calls, so a variable the test runner inherited cannot point them at the wrong repo. `tests/helpers/git-fixtures.js` ships both halves (#5379): `cleanGitEnv()` returns `process.env` minus those four, and `committedRepo({ prefix, branch })` builds a one-commit repo whose setup `git` runs under it, so a new env-only fixture layers `GIT_DIR` onto `{ ...cleanGitEnv() }`, as the suites under `tests/bin-lib/wrap-up/` do, rather than retyping the key loop. Delete the same four from the env a converted test hands the CLI whenever it merges `process.env` and its assertion depends on which repository git finds, or on there being none: a git hook's `GIT_DIR` otherwise reaches the CLI's own git children (#5382's plan-audit no-repo case, fixed in 24c5074dd). A test of the `gh` host probe sets a decoy `GH_HOST` in `process.env` rather than only deleting it from both sides. Find the ambient reads on a CLI's path by running each documented invocation through `runCliSync` and through `spawnCli` against the same fixture, with an injected `cwd`, `env` and `HOME` that differ from the real ones, and comparing the two results, not by reading the code: the read audit for `resolve-policy.js` (#5374) missed sites in four successive passes (plan, plan review, whole-branch review, review phase).
- **A git child that runs under `repoPinnedEnv()` cannot be proved by the `GIT_DIR` fixture above; prove its injected env with a variable git honours that `repoPinnedEnv()` keeps.** `plugin/bin/lib/hooks/git-exec.js`'s `repoPinnedEnv()` deletes `GIT_DIR`, `GIT_WORK_TREE`, `GIT_INDEX_FILE` and `GIT_COMMON_DIR` by design (#4178), so a child that inherited the real environment and one that got `env: deps.env` both lose `GIT_DIR` and read the `cwd`'s repo, and the A/B test stays green either way. Put a value absent from the test process's own environment only in the injected `env`, and read it back from what the child produced: `GIT_AUTHOR_NAME` checked as the new commit's `%an`, or an upstream set only through `GIT_CONFIG_COUNT`/`GIT_CONFIG_KEY_n`/`GIT_CONFIG_VALUE_n` checked in the push-state line it prints. Use one value per child on the path. `tests/archive-run-verb.test.js`'s "AC10.1: archive-run starts the archive commit and its push-state probe with the injected env" (#5375) is the worked example: the author name pins `archiveRunDir`'s commit and the configured upstream pins `archiveCommitLine`'s push-state probe. Its injected `cwd` is pinned by a separate test, a relative `--run` and the branch the committed line names.
- **A converted CLI that prints an `fs` error's `err.message` for a relative path argument maps the resolved path back to the argument's spelling.** Node puts the path it was handed into the message (`ENOENT: no such file or directory, open '<path>'`), so once the read goes through `resolveAgainst(deps.cwd(), p)` the message names the absolute path where the unconverted CLI printed what the caller typed. Swap it back before printing, `err.message.split(resolved).join(asTyped)`: `plugin/bin/plan-audit.js` does this for its plan and spec reads and `plugin/bin/resolve-profile.js` for its frontier-tally append (#5382), and byte-exact stderr assertions in `tests/bin-lib/plan-audit/cli.test.js` and `tests/bin-lib/model-profiles/cli.test.js` pin both. On win32 Node names the path normalized, so an argument holding a `/` (`sub/x`, joined as `C:\cwd\sub/x`) is reported as `C:\cwd\sub\x` and a verbatim split misses it: match a rooted join that is absent verbatim in its `path.normalize` form (`plugin/bin/design-detect.js`, #5381, found only by the Windows CI job).
- **A deps seam that must not be called on some path is pinned by counting calls, not by output parity, whenever the caller tolerates the seam failing.** `plugin/bin/design-detect.js`'s `resolveOperand` swallows a throwing `cwd()` and returns the operand unchanged, so removing its absolute-path short-circuit left a "never call cwd()" test that compared outputs green (#5381's review). Assert zero calls with a counting fake (`cwd: () => { calls += 1; … }`), and prove relative-path resolution with a fixture that exists only under the injected `cwd`, which goes red on a `return p` mutant.
- **A fail-closed branch around an injected dependency needs one test of the real dependency's failure shape, not only a stub that throws.** A stub proves the wrapper catches a throw, not that the real dependency ever throws. `plugin/bin/dispatch-resume.js`'s run-dir listing is the example: `read('run dir listing', …)` mapped a throw to exit 4, but the real `listRunDirsWithState` swallows a `readdirSync` failure into an empty listing, so the branch was unreachable and an unlistable pipelines dir passed the bound-run scan as clean (verdict and `--bound-run` modes) and could report this session's own lock as a live sibling. #4809 added `listRunDirsFailClosed` and the tests that drive the real dependency.
- **A CLI that promises to write nothing pins that promise in-process, beside the spawn check, never with the spawn check alone.** A spawned run in a scratch `cwd` followed by an empty-directory assertion sees only that `cwd`, so a write to the run dir, the home directory or any absolute path passes it. `tests/deferral-route-cli.test.js`'s AC8.3 (#5930) traps the fs mutation family (each name's sync, callback and `fs.promises` form: `writeFile`, `appendFile`, `mkdir`, `rm`, `unlink`, `rename`, `copyFile`, `open`, `createWriteStream` and the rest) with a recording function that throws, calls `run()` once per verdict (each outcome, a refusal and `--help`), restores every original in a `finally`, and asserts no call was recorded; a mutation that appended to `/dev/null` turned it red. Keep AC8.1's spawn check too: only a real child shows that no `gh` or other process runs. When the CLI later gains an opt-in write (#5933's `--run` tally), the trap keeps covering the calls without that flag.
- `require.main === module` guard sets `process.exitCode = run(...)` (never `process.exit`, which can truncate piped stdout). `--help` short-circuits before any availability probe. **This one is pinned mechanically, not by grep** — `tests/bin-lib/exit-code-conformance.test.js` (#1903) walks every `plugin/bin/**/*.js`, extracts the text each `require.main === module` guard governs, and fails on a direct `process.exit(...)` inside it. Three prior records (#1176, #1313, #1535) each closed one violation of this rule found by a manual sweep that missed another, which is why the sweep was replaced. A new guard needs no registration; a deliberate exception goes in that test's `ALLOWLIST` with its reason stated beside it (today: `bin/hooks.js`, whose event tail writes stdout through a synchronous `realDeps.stdoutSync` (`fs.writeSync(1, …)`) and whose verb stdout is a Promise around `process.stdout.write` that the flush sites await before the entry's `process.exit(code)`, and `bin/lib/statusline-wrapper-source.js`, which deliberately hard-stops on a child process's own exit code).
- **Precisely, the scan reads only a file's *last* `require.main === module` guard, and only the text that guard governs** — `extractGuard` takes the last regex match, then either a balanced `{…}` block or the bare statement up to its `;`. A file may hold more than one guard: `bin/hooks.js` has its Bash prefilter fast path (#3074) ahead of the real entry point at the bottom. The last guard is the entry point, since a guard that short-circuits before it must appear first, so a direct `process.exit(...)` in an earlier guard is not checked. `hooks.js`'s prefilter exit is safe because nothing has been written to stdout yet. An exit placed outside any guard is invisible to the scan in a file that also exports something. `hooks.js`'s allowlist entry covers the entry-point guard's `main(...).then((code) => process.exit(code))`, and `tests/bin-lib/exit-code-conformance.test.js` pins that the scan selects that guard, not the prefilter one.
- **The guard rule above only sees a file's own entry-point guard — it does not follow the call graph into a library function that guard invokes.** `plugin/bin/lib/health-core/*.js` are shared library files invoked from deep inside all four health-suite CLIs' (`code-health.js`, `harness-health.js`, `journey-health.js`, `docs-health.js`) own correctly-guarded entry point — outside any guard #1903's scan can see, so a `process.exit()` there was invisible to it (#2053: `churn-report.js`, `mark.js`, `retry-cli.js`'s `update` each did this after a pending stdout/stderr write). The fix mirrors the guard rule's own shape one level down rather than making the mechanical scan call-graph-aware (disproportionate for a bug class with exactly three known instances): each library function returns a numeric code (or `undefined`) instead of exiting, and each CLI's dispatch hands that value on as its exit code. All four CLIs (`harness-health.js` and `journey-health.js` in #5380, `code-health.js` and `docs-health.js` in #5381) return it from `run(argv, deps)` (`if (cmd === 'churn-report') return ctx.cmdChurnReport(args);`), and their entry guard is their only `process.exitCode` write. `tests/bin-lib/exit-code-conformance.test.js` adds a second, narrower rule for this: a flat per-file sweep of `plugin/bin/lib/health-core/*.js` (no guard extraction, no call-graph walk) failing on any direct `process.exit(` anywhere in the file. Never widen this scope to all of `plugin/bin/lib/**` — `bin/lib/statusline-wrapper-source.js`'s own `process.exit()` calls are a different case (a guard-less whole-script file, not a library function invoked from another file's guard) already covered by the guard-scoped test's own `ALLOWLIST` above.
- **A multi-verb dispatcher needs one table-driven guard, not N per-verb ones.** `plugin/bin/hooks.js` isn't a single-purpose CLI in the sense above — it's one `main(argv)` dispatching every subcommand its `VERBS` table names (plus the harness-invoked `EVENTS` names). Before #1143, each subcommand branch treated a stray `--help`/`-h` as an ordinary argument, ran for real, and on the `--run`-omitted verbs could fall through to `resolveRunArg`'s implicit "newest non-terminal run" guess — silently stamping a *sibling session's* `run-state.json` (observed 2026-08-20). The fix generalizes the single-CLI `--help` short-circuit above into one `USAGE` lookup table (verb → usage string) checked once, ahead of every branch in `main()`, before any lib call or `resolveRunArg` scan — not a per-verb early-return copy-pasted into every branch. Since #4181 the guard and the dispatch read the same `VERBS` table (`USAGE` is derived from it), so a verb cannot be dispatched without a usage line; `tests/hooks-help-guard.test.js` asserts every table entry carries a usage line starting with its key and a handler, and that the unknown-verb usage output lists every key.
- Exit codes are a documented contract, and this repo ships **four** base vocabularies — pick the one the CLI's sibling and its consuming prose already use, then spell it out in the file's header comment and `USAGE`:
  - *Combined-2* (`plugin/bin/link-records.js`, `plugin/bin/learned-skills-pr.js`): 0 success or partial-with-`failed`, 1 upstream resolution failure, 2 malformed invocation **or** missing dependency. A run-dir writer may use this family when a refused `--run` is a call to fix rather than a wrong-run-dir branch, and its header must say so: `learned-skills-pr.js` (#5290) exits 2 for an unanchored `--run`, where the *Sanctioned-writer* family below exits 3.
  - *Split-1/2* (`plugin/bin/resolve-blockers.js`, `plugin/bin/fetch-sub-issues.js`): 0 success, 1 malformed invocation, 2 missing dependency or unresolvable owner/repo, 3 the remote call itself failed.
  - *Sanctioned-writer* (`plugin/bin/log-decision.js`, `plugin/bin/stage-item.js`, `plugin/bin/set-config.js`, `plugin/bin/set-verify-expectations.js`, `plugin/bin/write-run-artifact.js`, `plugin/bin/ci-gate-record.js`): 0 written (the written path echoed to stdout), 2 malformed invocation, 3 the run dir is missing or not anchored under the main checkout, or the target file is unwritable — **no 1 at all**. These are the run-directory writers a worktree-isolated session reaches for when Edit/Write refuses the run dir (`decisions.md`, `staged/`, `config.yml`, `verify-expectations.json`, allowlisted top-level run-dir artifacts respectively), and the skill prose that states exit guidance for them (`feedback/upstream-draft.md`, every `set-verify-expectations.js` call site under `wrap-up/` — most `log-decision.js` call sites state none) branches on 3 as "wrong run dir — re-resolve `$RUN_ROOT`". `stage-item.js --ledger` (#3510) overloads exit 3 with logged degraded outcomes (an unreadable or tableless ledger, a ledger whose row numbering is unsafe to extend — a duplicate number or a numbered row outside the table — or a failed staged or ledger write), distinguishable by the stderr prefix `stage-item.js: ledger carry-forward degraded —`: with that prefix the trace is already in `decisions.md` and the call is never retried; any other 3 is still the wrong-run-dir case. Copying *Split-1/2* into a further writer would make its malformed case land on a code its siblings use for an anchoring failure. `set-config.js`'s 0 case is not always just the written-path echo: when a `--set` batch supplies the 13 canonical Manifesto levers (plus at most the run pins, `RUN_PINS`) with `mode=auto`, success additionally prints a `### Pipeline Config (auto)` FYI table on stdout as a mechanical side effect of the write (`isManifestoAutoBatch`/`renderManifestoFyi`, #2735) — any other invocation shape (single-key form, a partial batch, non-`auto` mode) still prints only the per-lever echo lines. `plugin/bin/console-residue.js` (#3370) joins this family with two differences. Its `--run` form is a pure read: exit 0 with empty stdout is the "nothing to show" answer, and the flow summary templates omit their section on exactly that. Its `--ack`/`--ack-all` forms read-modify-write each `console.json` through `writeFileAtomic` under `withLock` on `<console dir>/.console.lock` — the `CONSOLE_LOCK` that `plugin/bin/lib/console/item-resolution.js` exports, because `plugin/bin/console-resolve.js --set-item` (#4170) is a second writer of the same file, and an unlocked ack racing that rewrite would drop one or the other's field. A console whose directory has vanished is refused as a failed write before the lock is taken, since `withLock` creates a missing lock parent and would otherwise recreate an emptied run dir under a concurrent archival. Both forms map a throwing write to exit 3 per console (named on stderr, the remaining consoles still tried, the summary line counting the failures), never an uncaught exit 1. `plugin/bin/shadow-dup-proposal.js` (#3946) joins it with three differences: it only reads the run dir (`staged/`, anchored through stage-item's `resolveTarget`); its one write is a caller-named `--out`, a create-or-overwrite with no lock, whose failure is exit 3 like an unanchored run dir; and exit 2 also covers a refusal that is not malformed — a byte-identical duplicate (the console dismisses it) and an unreadable copy, a leaf symlink included (it opens `staged/` files with `O_NOFOLLOW`, or on a platform without it checks the leaf by lstat and dev/ino identity, since it quotes them into a filed record). `plugin/bin/console-filings.js` (#3949) joins it the same way: it only reads the run dir (anchored through stage-item's `resolveTarget`) and a caller-named `--existing` record list; its writes are a caller-named `--out-dir`'s proposal files, create-or-overwrite with no lock, whose failure is exit 3 like an unanchored run dir; and exit 2 also covers an unparseable `--existing` and an `--only` naming no can't-tell item, the whole call refused with nothing written. `plugin/bin/ci-gate-record.js` (#5160) joins it with two differences: its target is the run dir's `events.jsonl` (one appended `ci-gate` event, called by the pr-first merge gate's Step 2.5, not a stand-in for a refused Edit/Write), and exit 2 also covers a failed or unreadable `gh run list` — overloaded per the inverse-decision bullet below, since Step 2.5 logs a `SKIP` on any non-zero exit; a caller that retries a remote failure reopens it.
  - *Payload-1/Invocation-2* (`plugin/bin/wrap-up-engine.js`, `plugin/bin/declined-learning.js`, `plugin/bin/sdd-ruling-route.js` — whose payload failure is an unreadable `--file`): 0 success, 1 the invocation was well-formed but the stdin/file payload was not (unparseable JSON, a payload that fails validation), 2 malformed invocation (missing/unknown flags, an unknown verb). The split exists because a payload failure is retried with a fixed payload, never by re-reading usage. `declined-learning.js` (#2546) adopted it by citing `wrap-up-engine.js`'s header, not this list; per-verb codes above it (`wrap-up-engine.js verify`'s 3, `render --strict` exiting 2 after printing) stay that CLI's own, per the per-CLI bullet below. `plugin/bin/qa-report.js` (#3328) uses the same 0/1/2 split for its `--results` file payload and adds 3 for an unwritable caller-named `--out`; `--out` is a QA artifact path, not a pipeline run dir, so no run-dir anchoring guard applies and 3 never means "wrong run dir" the way it does for the *Sanctioned-writer* family. `plugin/bin/implementer-tier.js` (#5996) joins it too: an unreadable `--spec-file`, a malformed spec header, or an invalid resolved `implementer-tier` value exits 1, a malformed argv exits 2, and it differs from the two resolver CLIs in one place — a `--run` that `resolvePolicy`'s anchored-or-outside guard refuses exits 2, where `resolve-profile.js` and `resolve-policy.js` exit 1. `plugin/bin/find-run-comment.js` (#3936) joins the family too: its `--comments-file` payload that is unreadable, unparseable, or not a comments list exits 1 and a malformed argv exits 2, with no run-dir argument and so no anchoring guard. It looks its flags up with `Object.hasOwn(FLAGS, a)`, which rejects an inherited key such as a bare `constructor` token; a flag table read with `a in FLAGS` accepts it as a known flag. `plugin/bin/compose-pr-body.js`'s `parseArgs` carried that `in` shape until #4021 moved it to `Object.hasOwn` too. Pin the guard with a value after the key (`'constructor', 'x'`): a trailing bare `constructor` exits 2 under either lookup, because the `in` shape falls through to `needs a value`, so only the pair goes red (`tests/bin-lib/flow/record-steps.test.js`, #4358). `plugin/bin/plan-store.js` (#6052) joins it too, with its own differences: 1 also covers a `read` ref that is missing or names another commit and an invalid `check` verdict; it adds the CLI-own `3` (`EXIT_NO_REF`, `write` only: the ref could not be created or pushed, or the lease was lost, so the caller writes no `Plan:` line); and its `check` exits 2 after printing a `valid:false` verdict naming the first check the malformed input prevents.

  Never mix them inside one family: a caller that branches on a sibling's codes reads the wrong branch silently.

Its deps are `realDeps` minus the `stdout` seam, so it cannot print even by accident, and `run` alone parses argv, calls the core and prints the envelope as its one JSON line on exit 0. An unknown `opts.mode` is a caller bug that `parseArgs` already refused with exit 2 on the CLI path, so the core throws a `TypeError` instead of returning a code a caller could read as retryable. Copy this shape when a lib module would otherwise drive `run` and re-parse its stdout: that round trip creates an unreadable-output failure state that exists only because of the text hop. Moving a caller from `run` to the core shrinks what it can receive: the usage exit 2 and the unreadable-output state are gone, so delete every statement and fake of them in the same change. #4781 removed them from `post-merge.js`'s header, `docs/reconcile-checks.md`, a `hooks.js` comment and a `reconcile-background.test.js` fixture, and review still found `post-merge.test.js`'s M7 feeding the core an exit 2 it cannot return. Pin the split two ways, as `tests/bin-lib/flow/closing-links-cli.test.js` does: the core's envelope deep-equals the line `run` prints for the same fixture, and with no `stdout` injected the core writes nothing to `process.stdout`.
- **A CLI that can perform only part of a decision's effect performs that part and hands the rest to the session as data — the split-transport shape.** `plugin/bin/reflect-apply.js` (#4168) files a reflect finding's `record` destination with `gh issue create` and records a `decline` through the declined-learning store itself, but a Node CLI cannot call MCP and an edit is the session's own tool call. So under `--transport emit` (and for an `edit` or a legacy no-destination file) it reports `session` entries in its envelope — `{ item, outcome: 'edit', target }`, `{ item, outcome: 'record', proposal }` (the proposal file it wrote), `{ item, outcome: 'digest', line, fingerprint }` — and the session reports each back with `--item <name> --applied edited|filed|digested [--ref <ref>]`, the one call that then appends the `AUTO` line. Two consequences to copy. Idempotence rests on that line: an item that already carries its `Reflect apply: staged/{name} {outcome}` line is `alreadyApplied` and nothing runs again, so an effect the CLI performed whose append then failed is a `logFailures` entry carrying its paste-ready command, never a `failed` item (a plain re-run would repeat the effect). And `--dry-run` calls and writes nothing, adding a `planned` list of the outcome each selected item would reach.
- **A CLI whose routes depend on a model-judged step reports that step's inputs as data and takes its result back on a re-run of the same call — the two-pass shape.** `plugin/bin/plan-retention.js` (#4594) computes tidy Step 4's plan routes but cannot run the citation check (a model reads each plan against its related spec). Its first pass reports `citationCheck: true` and the `citationCandidates` to check, with provisional routes that assume none are cited; the session re-runs the identical command adding `--cited <plan>` for each plan the check found cited, and that run's routes are final (`citationCheck: false`). Three consequences to copy. The re-run repeats every plan and every flag of the first call, because a re-run over only the cited plans would route that subset alone and silently mix the two passes' routes; the skill prose must say to re-run "the same call — every plan again", and a conformance pin on that clause (`tests/tidy-plan-retention-conformance.test.js`) stops a later edit narrowing it. A check that finds nothing cited needs no second run, so the prose says so too, or the caller re-runs for nothing. And the result flag is refused rather than ignored where it cannot change a route: `--cited` outside `--retention keep-forever`, or naming a plan not given as a plan argument, is exit 2 with nothing on stdout, because a silently ignored result flag would let the caller believe the check had been applied.
- **A CLI with one code path per work-backend driver carries one safety check per driver — harden them together or not at all.** `plugin/bin/release-note-repair.js` verifies its `github-issues` write in `verify` (via `lib/release-note-repair/apply.js`'s `verifyWritten`) and its `local-files` write inside `repairLocal`. A fix round added the "nothing else changed" proof (`onlyReleaseNoteAdded`) to the first only, so a concurrent edit to a local record that still verified was reported as this run's repair; a lens review caught it a round later and `b3c936252` added the byte-equality gate `repairLocal` now runs before success or restore. When a fix changes one driver's check, the same commit changes or explicitly exempts every sibling driver's equivalent check, and adds a discriminating test per driver (`tests/bin-lib/release-note-repair/cli.test.js`'s "a concurrent edit that would still verify" case is the local-files one). Route both through one shared function where the drivers' inputs allow it; where they don't, say beside each check which sibling it mirrors.
- **A `gh`-absent caller hands the CLI already-fetched records as a file; the CLI never tries to reach MCP itself.** A `plugin/bin/` CLI is a plain Node subprocess and cannot see the agent session's MCP tools. So in a sandbox without `gh`, the calling skill fetches through MCP `issue_read`, reshapes each record to `gh issue view --json number,title,body,labels,url`'s fields, writes the JSON to a session-scoped temp file, and passes its path. Two CLIs ship this seam: `plugin/bin/materialize.js --record-json <path>` (#1459, one record object) and `plugin/bin/preflight-records.js --records-json <path>` (#3351, an array of the requested records). A third, `plugin/bin/stale-claim-pr.js --listing <path>` (#4596, the open-PR array), departs from them twice, both because its verdicts are data on stdout and its exit codes cover only what stops a verdict being reached: the agent writes the MCP `list_pull_requests` entries unreshaped and `plugin/bin/lib/issues/mcp-pr-shape.js` normalizes them in Node on both transports, and a file that will not read, parse or normalize is a `failure` field on an exit-0 line, not exit 2. Its exit 2 means `gh` is absent and no `--listing` was passed, and only that, so a caller runs it bare first and routes exit 2 to the MCP fetch and a re-run with `--listing` (`plugin/skills/_shared/issue-claims.md`'s stale-claim check, `plugin/skills/tidy/scan-procedures.md`). A fourth, `plugin/bin/parent-gate.js --facts-json <path>` (#4603), departs from rule (2) below on exit codes: it splits the file's problems by recovery, so a file that will not read or parse, or a missing required key, is exit 1, a present entry that fails its shape guard (an MCP error or a wrapper the agent wrote as data) is exit 3, and exit 2 means only no GitHub remote for a qualified `--closing` token or an undeterminable repository root. Its header records the departure and why (`mcp-agent-fetch-node-compute` rule 3 maps a guard failure to a failed read, never to content). Copy three things from the first two, not from `parent-gate.js`'s exit-code split unless your prose branches on file problem versus guard failure the same way. (1) That path makes **zero** `gh` calls and never probes for `gh` (`materialize.js` skips `deps.ghAvailable()`), so a fetch-failure code is unreachable there; `preflight-records.js`'s header says outright that this path never exits 1. (2) Every problem with the file lands on the malformed-invocation code, exit 2 in both. `materialize.js` covers a file that will not read or parse; `preflight-records.js` also rejects a wrong shape and a requested number that is missing, duplicated or unrequested (`issuesFromRecordsJson` in `plugin/bin/lib/preflight-records/preflight-records.js`). A new one validates the shape too, since `JSON.parse` succeeds on `null` (the `qa-stamp.js` bullet in `status-as-data.md`). (3) Anything the `gh` path learns from a further call that the file cannot carry degrades visibly. `preflight-records.js` cannot run work-links native's GraphQL call, so it reads `blocked-by` from the bodies, prints a stderr line, and adds `nativeLinksUnchecked: true` to its envelope, a key absent on every other run. The calling prose owns the transport branch: how to fetch and reshape, and what a failed MCP fetch does (`plugin/skills/flow/multispec-preflight-failure.md`'s Transport paragraph stops before claiming and never writes a partial file; `plugin/skills/flow/materialize.md`'s `--record-json` paragraph is the reshape reference). The flag is singular for one record and plural for an array; keep that spelling for the next CLI (`stale-claim-pr.js`'s `--listing` does not).
- **A CLI that replaces a prose procedure inherits every guard the reader's view of the data used to enforce — inventory them before writing it.** `plugin/bin/pr-checklist.js` (#3263) took over the PR phase-checklist flip. The prose it replaced removed a skipped phase's row only "if present and still unchecked", a condition the agent met by reading the body; on the CLI path the agent never sees the body, so the first `--remove` deleted an already-checked row (found at the whole-branch review, fixed in `plugin/bin/lib/flow/pr-checklist.js` with a test that pins a checked row surviving `--remove`). The spec's acceptance criteria had not named the guard. Before the first line of the CLI, list each conditional the prose leaves to what the reader could see ("if present", "still unchecked", "when nothing changed"), give each its own branch and its own status value in the envelope, and add a test per branch.
- **A prose guard that keys on who is calling, or on a human choice no file records, cannot be inherited by the CLI — it becomes an explicit flag the prose passes, and the absent flag takes the safe route.** `plugin/bin/evidence-route.js` (#4125, retired by #4612) had taken over `verification-brief.md` Step 4's screenshot-route decision. Two of the prose's conditions were facts the CLI could not observe for itself: whether the call came from wrap-up Phase 4 execution, and whether an attended console chose "Approve all, leave PR open" (`console.json` records only the resolver's own `merge.resolution`, never an attended choice). They became `--in-run` and `--leave-open`, and the prose added each only when it was true. Each flag only ever widened toward the less safe route (`current-branch` on an unreadable PR state), so a caller that forgot one landed on `evidence-pr`, and its test pinned that both with and without the flag. List these facts in the same inventory as the previous bullet's reader-view conditionals, and for each one that no input file carries, decide the flag's name and its default before writing the CLI.
- **A caller that adds an optional, externally derived pair to a validate-all-then-write batch owes an empty-value rule.** `plugin/bin/set-config.js --set` validates the whole batch before writing any of it, so one invalid pair loses every other pair. #3350 added `integration-model={v}` to the Manifesto's 13-lever batch, with `{v}` taken from `resolve-policy.js --values integration-model`; an invalid pin in `policy.yml` makes that print an empty value, and `integration-model=` then exits 2 with no `config.yml` written, so all 13 levers are lost where the same typo used to cost nothing. Only the whole-branch review caught it. The fix is prose plus tests, not CLI code: `plugin/skills/flow/manifesto.md` says to omit the pair on an empty resolve and log a `SKIP` decision, `steps-and-gates.md` case 3 routes to the same rule, and `tests/bin-lib/set-config/cli.test.js` pins both the 13-lever batch without the pin and the empty-value refusal. When a change adds an optional pair to such a batch, state the omit-on-empty rule at the call site and test the empty case, in the same change.
- **A mutation probe of a CLI that writes outside its `cwd` runs contained, or not at all.** A discrimination check reverts one fix and runs the test, so a mutant that ignores its injected `cwd` or home falls back to the real ones. #5386 ran such mutants from a linked scratch worktree: a cwd-ignoring `sweep-stray-run-dirs.js` resolved the real main checkout through `mainCheckoutRoot` and made 600 archive commits on local `main`, and an `os.homedir` mutant of `install-statusline-wrapper.js` rewrote the real `~/.claude-tweaks/bin/statusline.js`. Before running a mutant of a CLI that commits, pushes or writes under the home, make the test call a dry run or point it at a fixture root, point `os.homedir`, `HOME` and `USERPROFILE` at a decoy directory, and run it in a `git archive` extract (a fresh `git init` plus one snapshot commit), never a linked worktree, whose `git rev-parse --git-common-dir` leads back to the real repository.
- **Merge an `injectedGhDeps` result by property descriptor, never by spread.** `injectedGhDeps({ homeDir })` (`plugin/bin/lib/repo-resolve.js`) returns a lazy `homedir` getter so `homeDir()` runs only when the gh config-dir lookup falls through to the home; an object spread of it, or of a deps object that holds it, calls the getter on the spot.
