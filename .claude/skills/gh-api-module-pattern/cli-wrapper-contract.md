## The CLI wrapper contract

- Logic lives in an exported `run(argv, deps)`; every side effect (`runner`, `ghAvailable`, `remoteUrl`, `stdout`, `stderr`) goes through `deps` so tests inject fakes. **Every** `deps` call that can throw (e.g. `remoteUrl` outside a git repo) is try/caught into the documented exit-code contract — an un-wrapped deps call is where #610's one post-review high landed.
- `require.main === module` guard sets `process.exitCode = run(...)` (never `process.exit`, which can truncate piped stdout). `--help` short-circuits before any availability probe. **This one is pinned mechanically, not by grep** — `tests/bin-lib/exit-code-conformance.test.js` (#1903) walks every `plugin/bin/**/*.js`, extracts the text each `require.main === module` guard governs, and fails on a direct `process.exit(...)` inside it. Three prior records (#1176, #1313, #1535) each closed one violation of this rule found by a manual sweep that missed another, which is why the sweep was replaced. A new guard needs no registration; a deliberate exception goes in that test's `ALLOWLIST` with its reason stated beside it (today: `bin/hooks.js`, whose stdout is a synchronous `fs.writeSync(1, …)` with nothing pending to flush, and `bin/lib/statusline-wrapper-source.js`, which deliberately hard-stops on a child process's own exit code).
- **Precisely, the scan reads only a file's *last* `require.main === module` guard, and only the text that guard governs** — `extractGuard` takes the last regex match, then either a balanced `{…}` block or the bare statement up to its `;`. A file may hold more than one guard: `bin/hooks.js` has its Bash prefilter fast path (#3074) ahead of the real entry point at the bottom. The last guard is the entry point, since a guard that short-circuits before it must appear first, so a direct `process.exit(...)` in an earlier guard is not checked. `hooks.js`'s prefilter exit is safe because nothing has been written to stdout yet. An exit placed outside any guard is invisible to the scan in a file that also exports something. `hooks.js`'s allowlist entry covers the entry-point guard's `main(...).then((code) => process.exit(code))`, and `tests/bin-lib/exit-code-conformance.test.js` pins that the scan selects that guard, not the prefilter one.
- **The guard rule above only sees a file's own entry-point guard — it does not follow the call graph into a library function that guard invokes.** `plugin/bin/lib/health-core/*.js` are shared library files invoked from deep inside all four health-suite CLIs' (`code-health.js`, `harness-health.js`, `journey-health.js`, `docs-health.js`) own correctly-guarded `main()` — outside any guard #1903's scan can see, so a `process.exit()` there was invisible to it (#2053: `churn-report.js`, `mark.js`, `retry-cli.js`'s `update` each did this after a pending stdout/stderr write). The fix mirrors the guard rule's own shape one level down rather than making the mechanical scan call-graph-aware (disproportionate for a bug class with exactly three known instances): each library function returns a numeric code (or `undefined`) instead of exiting, and each CLI's `main()` dispatch line captures that return value into `process.exitCode`, e.g. `if (cmd === 'churn-report') { const code = cmdChurnReport(args); if (code) process.exitCode = code; return; }` — the same `process.exitCode = N; return;` shape every other branch in the same `main()` already uses. `tests/bin-lib/exit-code-conformance.test.js` adds a second, narrower rule for this: a flat per-file sweep of `plugin/bin/lib/health-core/*.js` (no guard extraction, no call-graph walk) failing on any direct `process.exit(` anywhere in the file. Never widen this scope to all of `plugin/bin/lib/**` — `bin/lib/statusline-wrapper-source.js`'s own `process.exit()` calls are a different case (a guard-less whole-script file, not a library function invoked from another file's guard) already covered by the guard-scoped test's own `ALLOWLIST` above.
- **A multi-verb dispatcher needs one table-driven guard, not N per-verb ones.** `plugin/bin/hooks.js` isn't a single-purpose CLI in the sense above — it's one `main(argv)` dispatching every subcommand its `VERBS` table names (plus the harness-invoked `EVENTS` names). Before #1143, each subcommand branch treated a stray `--help`/`-h` as an ordinary argument, ran for real, and on the `--run`-omitted verbs could fall through to `resolveRunArg`'s implicit "newest non-terminal run" guess — silently stamping a *sibling session's* `run-state.json` (observed 2026-08-20). The fix generalizes the single-CLI `--help` short-circuit above into one `USAGE` lookup table (verb → usage string) checked once, ahead of every branch in `main()`, before any lib call or `resolveRunArg` scan — not a per-verb early-return copy-pasted into every branch. Since #4181 the guard and the dispatch read the same `VERBS` table (`USAGE` is derived from it), so a verb cannot be dispatched without a usage line; `tests/hooks-help-guard.test.js` asserts every table entry carries a usage line starting with its key and a handler, and that the unknown-verb usage output lists every key.
- Exit codes are a documented contract, and this repo ships **four** base vocabularies — pick the one the CLI's sibling and its consuming prose already use, then spell it out in the file's header comment and `USAGE`:
  - *Combined-2* (`plugin/bin/link-records.js`): 0 success or partial-with-`failed`, 1 upstream resolution failure, 2 malformed invocation **or** missing dependency.
  - *Split-1/2* (`plugin/bin/resolve-blockers.js`, `plugin/bin/fetch-sub-issues.js`): 0 success, 1 malformed invocation, 2 missing dependency or unresolvable owner/repo, 3 the remote call itself failed.
  - *Sanctioned-writer* (`plugin/bin/log-decision.js`, `plugin/bin/stage-item.js`, `plugin/bin/set-config.js`, `plugin/bin/set-verify-expectations.js`, `plugin/bin/write-run-artifact.js`): 0 written (the written path echoed to stdout), 2 malformed invocation, 3 the run dir is missing or not anchored under the main checkout, or the target file is unwritable — **no 1 at all**. These are the run-directory writers a worktree-isolated session reaches for when Edit/Write refuses the run dir (`decisions.md`, `staged/`, `config.yml`, `verify-expectations.json`, allowlisted top-level run-dir artifacts respectively), and the skill prose that states exit guidance for them (`feedback/upstream-draft.md`, every `set-verify-expectations.js` call site under `wrap-up/` — most `log-decision.js` call sites state none) branches on 3 as "wrong run dir — re-resolve `$RUN_ROOT`". `stage-item.js --ledger` (#3510) overloads exit 3 with logged degraded outcomes (an unreadable or tableless ledger, a ledger whose row numbering is unsafe to extend — a duplicate number or a numbered row outside the table — or a failed staged or ledger write), distinguishable by the stderr prefix `stage-item.js: ledger carry-forward degraded —`: with that prefix the trace is already in `decisions.md` and the call is never retried; any other 3 is still the wrong-run-dir case. Copying *Split-1/2* into a further writer would make its malformed case land on a code its siblings use for an anchoring failure. `set-config.js`'s 0 case is not always just the written-path echo: when a `--set` batch supplies the 13 canonical Manifesto levers (plus at most the `integration-model` run pin) with `mode=auto`, success additionally prints a `### Pipeline Config (auto)` FYI table on stdout as a mechanical side effect of the write (`isManifestoAutoBatch`/`renderManifestoFyi`, #2735) — any other invocation shape (single-key form, a partial batch, non-`auto` mode) still prints only the per-lever echo lines. `plugin/bin/console-residue.js` (#3370) joins this family with two differences. Its `--run` form is a pure read: exit 0 with empty stdout is the "nothing to show" answer, and the flow summary templates omit their section on exactly that. Its `--ack`/`--ack-all` forms read-modify-write each `console.json` through `writeFileAtomic` under `withLock` on `<console dir>/.console.lock` — the `CONSOLE_LOCK` that `plugin/bin/lib/console/item-resolution.js` exports, because `plugin/bin/console-resolve.js --set-item` (#4170) is a second writer of the same file, and an unlocked ack racing that rewrite would drop one or the other's field. A console whose directory has vanished is refused as a failed write before the lock is taken, since `withLock` creates a missing lock parent and would otherwise recreate an emptied run dir under a concurrent archival. Both forms map a throwing write to exit 3 per console (named on stderr, the remaining consoles still tried, the summary line counting the failures), never an uncaught exit 1. `plugin/bin/shadow-dup-proposal.js` (#3946) joins it with three differences: it only reads the run dir (`staged/`, anchored through stage-item's `resolveTarget`); its one write is a caller-named `--out`, a create-or-overwrite with no lock, whose failure is exit 3 like an unanchored run dir; and exit 2 also covers a refusal that is not malformed — a byte-identical duplicate (the console dismisses it) and an unreadable copy, a leaf symlink included (it opens `staged/` files with `O_NOFOLLOW`, since it quotes them into a filed record). `plugin/bin/console-filings.js` (#3949) joins it the same way: it only reads the run dir (anchored through stage-item's `resolveTarget`) and a caller-named `--existing` record list; its writes are a caller-named `--out-dir`'s proposal files, create-or-overwrite with no lock, whose failure is exit 3 like an unanchored run dir; and exit 2 also covers an unparseable `--existing` and an `--only` naming no can't-tell item, the whole call refused with nothing written.
  - *Payload-1/Invocation-2* (`plugin/bin/wrap-up-engine.js`, `plugin/bin/declined-learning.js`): 0 success, 1 the invocation was well-formed but the stdin/file payload was not (unparseable JSON, a payload that fails validation), 2 malformed invocation (missing/unknown flags, an unknown verb). The split exists because a payload failure is retried with a fixed payload, never by re-reading usage. `declined-learning.js` (#2546) adopted it by citing `wrap-up-engine.js`'s header, not this list; per-verb codes above it (`wrap-up-engine.js verify`'s 3, `render --strict` exiting 2 after printing) stay that CLI's own, per the per-CLI bullet below. `plugin/bin/qa-report.js` (#3328) uses the same 0/1/2 split for its `--results` file payload and adds 3 for an unwritable caller-named `--out`; `--out` is a QA artifact path, not a pipeline run dir, so no run-dir anchoring guard applies and 3 never means "wrong run dir" the way it does for the *Sanctioned-writer* family. `plugin/bin/find-run-comment.js` (#3936) joins the family too: its `--comments-file` payload that is unreadable, unparseable, or not a comments list exits 1 and a malformed argv exits 2, with no run-dir argument and so no anchoring guard. It looks its flags up with `Object.hasOwn(FLAGS, a)`, which rejects an inherited key such as a bare `constructor` token; a flag table read with `a in FLAGS` accepts it as a known flag. `plugin/bin/compose-pr-body.js`'s `parseArgs` carried that `in` shape until #4021 moved it to `Object.hasOwn` too.

  Never mix them inside one family: a caller that branches on a sibling's codes reads the wrong branch silently.
- **Changing an existing CLI's exit code is a contract change — sweep every statement of the old code before calling it done.** The code lives in more places than the branch you edit: the file's header comment, a sibling module's comment that justifies its own code by analogy, `docs/`, `_shared/` prose, and this sub-file's own summaries. #3025 made `hooks.js close-run` exit 1 on a rejected `--run`; its tests went green on the code change alone, and the stale "every path exits 0" claims in `hooks.js`'s header, `lib/hooks/teardown-run.js` and `docs/hooks.md` surfaced only in the whole-branch review's fix wave. That fix wave still missed this file's shape-1 summary below, which grouped `hooks.js` under "exit 2" — never true of it — until the run's wrap-up. Grep the verb name together with `exit` across `plugin/`, `docs/` and `.claude/skills/` (`grep -rn 'close-run' plugin docs .claude/skills | grep -i exit`) and fix or delete each hit in the same change.
- **Adding a verb to an existing multi-verb CLI needs the same sweep: every list of the CLI's verbs, and every list of the input files they read, must gain the new entry.** Those lists live outside the file you edit. #3604 (PR #3662) added `corroborate-cross-lens` to `plugin/bin/review-coordination.js` and updated its header comment and `USAGE`. The build's docs sync matched `docs/plugin-structure.md` and `docs/skill-graph.md` through `docs/REGISTRY.md`, and it changed the review row of the sub-file table. It judged everything else in both docs unaffected. Review lens 3a then found two stale lists. The `review-coordination.js` command line in `docs/plugin-structure.md` still named only the four old verbs. The review section's `_shared/session-tmp-root.md` row in `docs/skill-graph.md` lacked the new `review-{ctx-id}-unconfirmed-by-lens.json` input. Fixing them cost a review fix round. A registry match tells you a doc is affected, not which line. Grep for an existing sibling instead: `git grep -n -F 'detect-overlap' -- plugin docs .claude/skills` finds every list of the verbs, and `git grep -n -F 'findings-by-lens.json' -- plugin docs` finds the filename list. Add the new entry to each hit that lists its siblings, in the same change.
- **Adding a flag that a CLI forwards into a library function needs one CLI-level test of the forwarding, and the same sweep of every restated command line.** The library's tests inject `deps` and call the function directly, so they stay green when the CLI drops the flag on the way in. #3636 added `--reverse-failed` to `plugin/bin/hooks.js resolve-console`, which parses it and passes `reverseFailed` into `plugin/bin/lib/reconcile/console-execute.js`'s `resolveConsoleExecution`. Removing `reverseFailed` from that call left every suite green until review added a test to `tests/hooks-resolve-console.test.js` that spawns the real `hooks.js` with a stub `gh` first on `PATH` and asserts the library's `not-ruling-items` refusal reaches stdout; dropping the forwarding turns it red. The same review found the command template in `plugin/skills/_shared/console-execution.md` still naming only `--approve`/`--decline`, while the `--help` test passed on `USAGE` alone. Grep an existing sibling flag (`git grep -n -F -e '--decline' -- plugin docs .claude/skills`) and add the new flag to each command line that restates the verb's flags. In `hooks.js` the flag also goes in the verb's `VERBS` entry's `usage` line, then `KNOWN_FLAGS`, and `VALUE_FLAGS` when it takes a value.
- Every malformed-input class must actually reach its malformed code — `Number('') === 0` passes `Number.isInteger`, so validate positivity and pair-structure explicitly.
- **A value-taking flag given as the last argv element reads `undefined`, and a `!== null` presence check treats that as supplied.** `parseArgs`' `next = () => argv[++i]` returns `undefined` past the end, so an option defaulted to `null` and tested with `opts.x !== null` runs its value path on nothing. #2775's review reproduced it on `claim-targets.js`: a trailing bare `--run` reached `path.basename(undefined)` and threw `ERR_INVALID_ARG_TYPE` uncaught instead of the documented exit 2. Validate the value inside `parseArgs`, the way `preflight-records.js`'s `--integration-branch` (same run) does — `typeof v !== 'string' || !v.trim() || v.startsWith('--')` returns a usage error — and pin both the trailing bare flag and the empty-string value with their own test cases. The `startsWith('--')` test only catches a next flag sitting where the value should be. A value the CLI forwards into a child's argv as a positional (a remote, a ref) rejects any leading `-`, because the child reads `-x` as an option too: `plugin/bin/read-claims.js` (#4818) first copied the `--` shape for `--remote`, and review found `-x` reaching `git fetch` as an option. It now tests `v.startsWith('-')`, pinned with `-x` and `--upload-pack=evil` cases in `tests/read-claims-cli.test.js`; the other fix is `SKILL.md`'s `--end-of-options` separator ahead of the value.
- **Codes above the base vocabulary are per-CLI domain outcomes and are not portable.** `plugin/bin/claim-targets.js` ships 3 (contested — holder JSON on stdout) and 4 (transient `gh` failure), branched on by `plugin/skills/flow/claim-targets.md` Step 2.8; `plugin/bin/fetch-sub-issues.js` ships 4 for "the capability probe says the GraphQL field is unavailable — take the documented fallback". Spell each one out in that CLI's own `USAGE` and in the prose that branches on it; never assume a number carries its meaning across CLIs.
- **The inverse decision needs the same evidence: a domain outcome no caller can act on differently stays on the base code, overloaded and documented.** A new code is earned by a caller that *branches* on it (the bullet above: `claim-targets.js`'s 3/4, branched on by `plugin/skills/flow/claim-targets.md` Step 2.8; `fetch-sub-issues.js`'s 4), not by the outcome being conceptually distinct — so "this is really two different failures" is not by itself a reason to allocate a fourth number. `plugin/bin/lib/compose-subject.js` (#2319) keeps *Split-1/2*'s exit 1 deliberately overloaded across a malformed invocation **and** an uncomposable record, because every merge site that calls it treats every non-zero exit identically and stops before any merge; splitting them would mean editing every one of those fences for a distinction nothing reads. The header's decision comment is where that call-site inventory lives (it has moved once already, when #4073 folded four local-merge fences into `_shared/local-merge-sequence.md`), so read it there rather than counting sites here. Say so in the file's header comment beside the vocabulary, with the condition that would reopen it (compose-subject.js names its own: a caller that needs to park a shaping defect differently from reporting a bad call), so the next reader finds a decision rather than re-filing it as a missing code.
- **Two rejections with the same surface must not share one exit code — and a module that already
  returns an envelope discriminates in the envelope, not by throwing.**
  `plugin/bin/lib/release/precheck.js` refuses a candidate version two ways: it collides with an
  existing claim (`release-local.js` exit 4, a domain code) or a caller-supplied `--release-as` is
  not ahead of the derived base (exit 2, usage). Both read as "candidate refused", so `precheck`
  returns `result.usageError: true` on its existing return shape and the CLI raises its own
  `UsageError` (#2326) — the `ChangedFilesError` split in this skill's `SKILL.md` (the "seam whose
  calls are *probes*" bullet), done with a field instead of an error class because the envelope was
  already there. The module's other caller (`lib/release/run.js`) passes no `releaseAs`, so the
  branch is opt-in.
- **A verb that reports state as data exits 0 in every state — read `status-as-data.md` in this skill's directory before writing one.** It covers a read-only status verb (`verify.js --stamp-status`), a writer that refuses as data (`qa-stamp.js --write`) and an acting verb with a frozen `reason` enum (`impeccable-engine.js`).
- **A guard added to an existing `run(argv, deps)` reaches the environment through `deps` too.** The seam above is stated as "every side effect", so an argument-validation *read* — `process.cwd()`, a git-root probe, a stat — reads as exempt and gets called directly. It isn't. `plugin/bin/materialize.js`'s `--run-dir` anchoring guard (#790) shipped calling `plugin/bin/lib/hooks/worktree-detect.js`'s `isAnchoredUnderRoot` directly while the `cwd`/`mainRoot` calls beside it were already injected; only a review lens caught the one-of-three gap. A validation guard bolted onto an already-seamed CLI is exactly where the seam gets holed, because it doesn't feel like a side effect — inject it (`deps.cwd`, `deps.mainRoot`, `deps.isAnchored`) as you write it, and add the fake to every consuming test's deps object in the same commit.
- **Filesystem reads in a new `plugin/bin/` CLI follow two rules no review is guaranteed to catch.** An existence or type check goes through `plugin/bin/lib/path-guard`'s `lstatType`, never a bare `fs.existsSync` — `tests/path-guard-conformance.test.js` (AC3.1) flags the token in any new `plugin/bin/lib/` file. A file the CLI is about to read is read directly with `ENOENT`/`ENOTDIR` caught as "absent", never checked for existence first (`docs/donts.md` `[IL-146]` — the check-then-read pair leaves a window a sibling session's archive or prune can land in). `plugin/bin/dispatch-resume.js` (#4588) missed both through its task reviews: the final SDD review's conformance sweep caught the first (commit 5614c7246), and review Step 3 caught the second in `classifyPriorRun`'s `run-state.json` read (commit 8308354f3).
- **A run-directory argument gets one of four boundary guards; pick before writing the check.** `plugin/skills/_shared/pipeline-run-dir.md`'s CLI-argument-boundary section is canonical and enumerates all four itself ("Four shapes live at this boundary"); this bullet is the `bin/`-side summary, never a second registry. **(1) Pipeline-owned binaries** (`hooks.js`, `wrap-up-engine.js`, `materialize.js`, `apply-refine-labels.js`) refuse any value not anchored under the main checkout. `wrap-up-engine.js`, `materialize.js` and `apply-refine-labels.js` exit 2; `hooks.js`'s `resolveRunArg` verbs print `--run path rejected: …` and pick their exit code per verb — 0 for most, 1 for `close-run` (#3025) and `resolve-console` — so a caller reads that verb's own `run{Verb}` handler (the `run` its `VERBS` entry names), never a family-wide code. **(2) The two resolver CLIs** (`plugin/bin/resolve-profile.js`, `plugin/bin/resolve-policy.js`, #1065) call `worktree-detect.js`'s `checkRunDirAnchoredOrOutside` — a resolved path inside any checkout must be anchored, a path outside every checkout is accepted as-is — and exit 1, their own documented invocation-failure code. **(3) The *Sanctioned-writer* family above** (`log-decision.js`, `stage-item.js`, `set-config.js`, `set-verify-expectations.js`, `write-run-artifact.js`) applies the same strict anchoring, but through one of two exported `resolveTarget` copies rather than `worktree-detect.js` directly — `plugin/bin/lib/stage-item/write.js`'s (imported by `stage-item.js`, `set-config.js`, `set-verify-expectations.js`, `write-run-artifact.js`, and the readers `shadow-dup-proposal.js` and `console-filings.js`) or `plugin/bin/lib/log-decision/append.js`'s (imported by `log-decision.js`, and also by CLIs outside this family that append to `decisions.md` beside their main work — `repair-claim.js`, `release-claim.js`, `materialize.js`, `claim-targets.js` — which keep their own exit codes) — and refuses with exit **3**, not 2. Import the copy that sits beside the writer you call when you add another writer instead of re-deriving the predicate — `set-config.js` (#1376), `set-verify-expectations.js` (#2764) and `write-run-artifact.js` (#3044) import stage-item's, `claim-targets.js` (#2775) imports append.js's together with `appendEntry` — and pin the refusal with a fixture carrying both a real main-checkout run dir and a worktree-local shadow of it, asserting the shadow's file is byte-unchanged after the exit 3. **(4) The composer CLI** (`plugin/bin/compose-context.js`, #1988) is a run-directory *writer* (`{run}/context/{step}.md`) that nonetheless takes the *resolver* family's anchored-or-outside rule — through `plugin/bin/lib/run-dir-guard.js`'s `anchoredOrOutsideMessage`, the shared message renderer the two resolvers already call — and rejects with exit **2**, its malformed-invocation code, not 3. Strict is the default; anchored-or-outside needs a *documented* legitimate outside-repo use, and shape 4's is narrow enough to be non-precedential: its callers never branch on a run-dir code (a skill step's documented fallback on any non-zero exit is to read the named source files directly), and its tests spawn the real binary against tmp-root fixtures outside any checkout, the same documented use the resolvers have. A further writer inherits shape 4's reasoning only if its own callers share it; otherwise shape 3 is the default. The deps-injection rule above is scoped to binaries that already have a path-handling seam: the two resolvers are `main(argv)` CLIs with none, so their guard calls `worktree-detect` directly and is tested by spawning the real binary against `tests/helpers/git-fixtures.js` repos rather than by a fake — `compose-context.js` does have the seam and injects every path-handling call through it (`deps.cwd`, `deps.mainRoot`, `deps.isDirectory`, `deps.anchoredOrOutsideMessage`), which is the shape a new run-dir-taking CLI should copy. **#4027's three mechanics CLIs pair shape 3's predicate with exit 2:** `plugin/bin/manifesto-write.js`, `plugin/bin/pr-early-open.js` and `plugin/bin/context-gauge.js` anchor `--run` strictly through stage-item's `resolveTarget`, also refuse a basename `RUN_ID_RE` rejects, and exit **2**, because each one's 3 already carries a domain answer (`manifesto-write.js`: `config.yml` already present, the case-1 adoption; `pr-early-open.js`: the logged degrade) or it has no 3 at all (`context-gauge.js`, whose measured states all exit 0). Take that split only when the new CLI's 3 is already spoken for; otherwise shape 3's exit 3 stands.
- **A read-only run-dir *reader* still owes a stated boundary posture.** The four shapes above are framed around writes (`pipeline-run-dir.md`'s boundary refuses "before any filesystem write"), so a CLI that only reads a run-dir file looks exempt and gets no guard at all. `plugin/bin/closing-tally.js` (#2729) takes `--run`, joins `decisions.md` onto it with no anchoring check, and spends exit 3 only on an unreadable file: given a worktree-local shadow of the run dir (`[IL-127]`), it tallies the shadow's `decisions.md` and exits 0. That is a confident wrong count, and `/claude-tweaks:backlog refine`'s closing summary renders it verbatim. Pick one when you write the reader: import `lib/stage-item/write.js`'s `resolveTarget` and refuse a non-anchored `--run` on the sanctioned writers' exit 3, or state in the header why an unanchored read is safe for this CLI's callers (for example, a `--file` mode used only by tests). A reader whose 3 already carries a domain answer takes the #4027 split above instead: `plugin/bin/dispatch-resume.js --bound-run` (#4588) spends 3 on a refused or concurrent verdict (JSON on stdout), so it anchors the dir strictly through stage-item's `resolveTarget`, also requires a top-level dir of the main checkout's `.claude-tweaks/pipelines/`, and refuses on exit **2**, its malformed-invocation code.
- **A sanctioned writer that read-modify-writes a shared file guards it; a create-only writer doesn't.** The *Sanctioned-writer* family above splits on write shape, not on file type. `plugin/bin/lib/log-decision/append.js`'s `appendEntry` read-modify-writes one shared `decisions.md` that concurrent `bin/log-decision.js` processes contend for, so it runs the whole read-modify-write-rename under `plugin/bin/lib/file-lock.js`'s `withLock` (mkdir-based, best-effort/fail-open — a lock it can't acquire in `LOCK_WAIT_MS` proceeds unlocked rather than hanging the caller) and renames a per-process `decisions.md.tmp-${process.pid}` over the target, so a concurrent reader never sees a torn file even when the lock was missed (#816). `plugin/bin/lib/stage-item/write.js` needs neither: it creates `staged/<id><ext>` at a per-item path, so there is no read-modify-write to lose. **This still leaves a narrower hazard the create-only framing doesn't name: a *namespace* race rather than a shared-file one.** `writeStagedItem`'s opt-in `allocate: true` mode (#2770) exists because two independent writers choosing the same `{kind}-{n}` id is a real collision even with no shared file to tear — the fix isn't `withLock` (there is still nothing to lock), it's an exclusive-create (`O_EXCL`) probe of the requested slot, falling back to a directory rescan of `staged/`'s own existing `{kind}-*` entries and a retry loop through any further race, so a losing writer reallocates to the next free slot instead of clobbering.
