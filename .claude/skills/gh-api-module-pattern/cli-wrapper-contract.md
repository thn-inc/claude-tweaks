## The CLI wrapper contract

- Logic lives in an exported `run(argv, deps)`; every side effect (`runner`, `ghAvailable`, `remoteUrl`, `stdout`, `stderr`) goes through `deps` so tests inject fakes. **Every** `deps` call that can throw (e.g. `remoteUrl` outside a git repo) is try/caught into the documented exit-code contract — an un-wrapped deps call is where #610's one post-review high landed.
- `require.main === module` guard sets `process.exitCode = run(...)` (never `process.exit`, which can truncate piped stdout). `--help` short-circuits before any availability probe. **This one is pinned mechanically, not by grep** — `tests/bin-lib/exit-code-conformance.test.js` (#1903) walks every `plugin/bin/**/*.js`, extracts the text each `require.main === module` guard governs, and fails on a direct `process.exit(...)` inside it. Three prior records (#1176, #1313, #1535) each closed one violation of this rule found by a manual sweep that missed another, which is why the sweep was replaced. A new guard needs no registration; a deliberate exception goes in that test's `ALLOWLIST` with its reason stated beside it (today: `bin/hooks.js`, whose stdout is a synchronous `fs.writeSync(1, …)` with nothing pending to flush, and `bin/lib/statusline-wrapper-source.js`, which deliberately hard-stops on a child process's own exit code).
- **Precisely, the scan reads only a file's *first* `require.main === module` guard, and only the text that guard governs** — `extractGuard` takes the first regex match, then either a balanced `{…}` block or the bare statement up to its `;`. That matters the moment you add an early entry-point step above an existing guard, as `bin/hooks.js`'s Bash prefilter fast path does (#3074). The early guard becomes the one the scan reads, so a direct `process.exit(...)` in the file's *later* guard is no longer checked. And an exit placed outside any guard is invisible to the scan in a file that also exports something. #3074's first draft had that shape: `if (require.main === module) EARLY = …;` followed by a top-level `if (EARLY && EARLY.skip) process.exit(0);`. The first guard's text was the assignment alone, so the allowlist's "each still actually needs it" test failed for `hooks.js`. `bddfff622` fixed it by moving the early step and its exit into one braced guard, placed first, with a comment beside it naming this coupling. Keep that shape. `hooks.js` now has two allowlisted direct exits. One is the skip path's `process.exit(0)` in its first guard, safe because nothing has been written to stdout yet. The other is `main()`'s `.then((code) => process.exit(code))` in its second guard, which the scan no longer reads.
- **The guard rule above only sees a file's own entry-point guard — it does not follow the call graph into a library function that guard invokes.** `plugin/bin/lib/health-core/*.js` are shared library files invoked from deep inside all four health-suite CLIs' (`code-health.js`, `harness-health.js`, `journey-health.js`, `docs-health.js`) own correctly-guarded `main()` — outside any guard #1903's scan can see, so a `process.exit()` there was invisible to it (#2053: `churn-report.js`, `mark.js`, `retry-cli.js`'s `update` each did this after a pending stdout/stderr write). The fix mirrors the guard rule's own shape one level down rather than making the mechanical scan call-graph-aware (disproportionate for a bug class with exactly three known instances): each library function returns a numeric code (or `undefined`) instead of exiting, and each CLI's `main()` dispatch line captures that return value into `process.exitCode`, e.g. `if (cmd === 'churn-report') { const code = cmdChurnReport(args); if (code) process.exitCode = code; return; }` — the same `process.exitCode = N; return;` shape every other branch in the same `main()` already uses. `tests/bin-lib/exit-code-conformance.test.js` adds a second, narrower rule for this: a flat per-file sweep of `plugin/bin/lib/health-core/*.js` (no guard extraction, no call-graph walk) failing on any direct `process.exit(` anywhere in the file. Never widen this scope to all of `plugin/bin/lib/**` — `bin/lib/statusline-wrapper-source.js`'s own `process.exit()` calls are a different case (a guard-less whole-script file, not a library function invoked from another file's guard) already covered by the guard-scoped test's own `ALLOWLIST` above.
- **A multi-verb dispatcher needs one table-driven guard, not N per-verb ones.** `plugin/bin/hooks.js` isn't a single-purpose CLI in the sense above — it's one `main(argv)` dispatching every subcommand its `USAGE` table names (plus the harness-invoked `EVENTS` names). Before #1143, each subcommand branch treated a stray `--help`/`-h` as an ordinary argument, ran for real, and on the `--run`-omitted verbs could fall through to `resolveRunArg`'s implicit "newest non-terminal run" guess — silently stamping a *sibling session's* `run-state.json` (observed 2026-08-20). The fix generalizes the single-CLI `--help` short-circuit above into one `USAGE` lookup table (verb → usage string) checked once, ahead of every branch in `main()`, before any lib call or `resolveRunArg` scan — not a per-verb early-return copy-pasted into every branch. Regression risk for this shape specifically: the guard's own coverage can silently drift from the dispatch table it guards (a verb added to `main()`'s `cmd === '...'` chain with no matching `USAGE` entry gets no guard at all) — `tests/hooks-help-guard.test.js` pins this with a structural test scanning `main()`'s source for every `cmd === '...'` branch and asserting each has a `USAGE` entry, not just the reverse (iterating `USAGE`'s own keys, which proves nothing about branches missing from the table).
- Exit codes are a documented contract, and this repo ships **four** base vocabularies — pick the one the CLI's sibling and its consuming prose already use, then spell it out in the file's header comment and `USAGE`:
  - *Combined-2* (`plugin/bin/link-records.js`): 0 success or partial-with-`failed`, 1 upstream resolution failure, 2 malformed invocation **or** missing dependency.
  - *Split-1/2* (`plugin/bin/resolve-blockers.js`, `plugin/bin/fetch-sub-issues.js`): 0 success, 1 malformed invocation, 2 missing dependency or unresolvable owner/repo, 3 the remote call itself failed.
  - *Sanctioned-writer* (`plugin/bin/log-decision.js`, `plugin/bin/stage-item.js`, `plugin/bin/set-config.js`, `plugin/bin/set-verify-expectations.js`, `plugin/bin/write-run-artifact.js`): 0 written (the written path echoed to stdout), 2 malformed invocation, 3 the run dir is missing or not anchored under the main checkout, or the target file is unwritable — **no 1 at all**. These are the run-directory writers a worktree-isolated session reaches for when Edit/Write refuses the run dir (`decisions.md`, `staged/`, `config.yml`, `verify-expectations.json`, allowlisted top-level run-dir artifacts respectively), and the skill prose that states exit guidance for them (`feedback/upstream-draft.md`, every `set-verify-expectations.js` call site under `wrap-up/` — most `log-decision.js` call sites state none) branches on 3 as "wrong run dir — re-resolve `$RUN_ROOT`". Copying *Split-1/2* into a further writer would make its malformed case land on a code its siblings use for an anchoring failure. `set-config.js`'s 0 case is not always just the written-path echo: when a `--set` batch supplies exactly the 13 canonical Manifesto levers with `mode=auto`, success additionally prints a `### Pipeline Config (auto)` FYI table on stdout as a mechanical side effect of the write (`isManifestoAutoBatch`/`renderManifestoFyi`, #2735) — any other invocation shape (single-key form, a partial batch, non-`auto` mode) still prints only the per-lever echo lines. `plugin/bin/console-residue.js` (#3370) joins this family with two differences. Its `--run` form is a pure read: exit 0 with empty stdout is the "nothing to show" answer, and the flow summary templates omit their section on exactly that. Its `--ack`/`--ack-all` forms read-modify-write each `console.json` through `writeFileAtomic` with no `withLock` — tolerable because an ack is human-invoked with no concurrent writer to race — and map a throwing write to exit 3 per console (named on stderr, the remaining consoles still tried, the summary line counting the failures), never an uncaught exit 1.
  - *Payload-1/Invocation-2* (`plugin/bin/wrap-up-engine.js`, `plugin/bin/declined-learning.js`): 0 success, 1 the invocation was well-formed but the stdin/file payload was not (unparseable JSON, a payload that fails validation), 2 malformed invocation (missing/unknown flags, an unknown verb). The split exists because a payload failure is retried with a fixed payload, never by re-reading usage. `declined-learning.js` (#2546) adopted it by citing `wrap-up-engine.js`'s header, not this list; per-verb codes above it (`wrap-up-engine.js verify`'s 3, `render --strict` exiting 2 after printing) stay that CLI's own, per the per-CLI bullet below.

  Never mix them inside one family: a caller that branches on a sibling's codes reads the wrong branch silently.
- **Changing an existing CLI's exit code is a contract change — sweep every statement of the old code before calling it done.** The code lives in more places than the branch you edit: the file's header comment, a sibling module's comment that justifies its own code by analogy, `docs/`, `_shared/` prose, and this sub-file's own summaries. #3025 made `hooks.js close-run` exit 1 on a rejected `--run`; its tests went green on the code change alone, and the stale "every path exits 0" claims in `hooks.js`'s header, `lib/hooks/teardown-run.js` and `docs/hooks.md` surfaced only in the whole-branch review's fix wave. That fix wave still missed this file's shape-1 summary below, which grouped `hooks.js` under "exit 2" — never true of it — until the run's wrap-up. Grep the verb name together with `exit` across `plugin/`, `docs/` and `.claude/skills/` (`grep -rn 'close-run' plugin docs .claude/skills | grep -i exit`) and fix or delete each hit in the same change.
- Every malformed-input class must actually reach its malformed code — `Number('') === 0` passes `Number.isInteger`, so validate positivity and pair-structure explicitly.
- **A value-taking flag given as the last argv element reads `undefined`, and a `!== null` presence check treats that as supplied.** `parseArgs`' `next = () => argv[++i]` returns `undefined` past the end, so an option defaulted to `null` and tested with `opts.x !== null` runs its value path on nothing. #2775's review reproduced it on `claim-targets.js`: a trailing bare `--run` reached `path.basename(undefined)` and threw `ERR_INVALID_ARG_TYPE` uncaught instead of the documented exit 2. Validate the value inside `parseArgs`, the way `preflight-records.js`'s `--integration-branch` (same run) does — `typeof v !== 'string' || !v.trim() || v.startsWith('--')` returns a usage error — and pin both the trailing bare flag and the empty-string value with their own test cases.
- **Codes above the base vocabulary are per-CLI domain outcomes and are not portable.** `plugin/bin/claim-targets.js` ships 3 (contested — holder JSON on stdout) and 4 (transient `gh` failure), branched on by `plugin/skills/flow/claim-targets.md` Step 2.8; `plugin/bin/fetch-sub-issues.js` ships 4 for "the capability probe says the GraphQL field is unavailable — take the documented fallback". Spell each one out in that CLI's own `USAGE` and in the prose that branches on it; never assume a number carries its meaning across CLIs.
- **The inverse decision needs the same evidence: a domain outcome no caller can act on differently stays on the base code, overloaded and documented.** A new code is earned by a caller that *branches* on it (the bullet above: `claim-targets.js`'s 3/4, branched on by `plugin/skills/flow/claim-targets.md` Step 2.8; `fetch-sub-issues.js`'s 4), not by the outcome being conceptually distinct — so "this is really two different failures" is not by itself a reason to allocate a fourth number. `plugin/bin/lib/compose-subject.js` (#2319) keeps *Split-1/2*'s exit 1 deliberately overloaded across a malformed invocation **and** an uncomposable record, because all six merge sites that call it — the two squash sites in `plugin/skills/_shared/pr-first-merge.md` and the four in `tests/merge-subject-composer-conformance.test.js`'s `LOCAL_SITES` — fence the call as `|| exit 1` and treat every non-zero exit identically; splitting them would mean editing six fences for a distinction nothing reads. Say so in the file's header comment beside the vocabulary, with the condition that would reopen it (compose-subject.js names its own: a caller that needs to park a shaping defect differently from reporting a bad call), so the next reader finds a decision rather than re-filing it as a missing code.
- **Two rejections with the same surface must not share one exit code — and a module that already
  returns an envelope discriminates in the envelope, not by throwing.**
  `plugin/bin/lib/release/precheck.js` refuses a candidate version two ways: it collides with an
  existing claim (`release-local.js` exit 4, a domain code) or a caller-supplied `--release-as` is
  not ahead of the derived base (exit 2, usage). Both read as "candidate refused", so `precheck`
  returns `result.usageError: true` on its existing return shape and the CLI raises its own
  `UsageError` (#2326) — the `ChangedFilesError` split in this skill's `SKILL.md` (the "seam whose
  calls are *probes*" bullet), done with a field instead of an error class because the envelope was
  already there. The module's other caller (`lib/release/run.js`) passes no `releaseAs`, so the
  branch is opt-in.
- **A read-only *status* verb is status-as-data: it exits 0 in every state, and the JSON on stdout is the answer.** The vocabularies above key *the outcome of doing something*; a verb that only reports the state of an artifact the CLI itself wrote has no such outcome to key. `plugin/bin/verify.js --stamp-status` (#1921) is the shipped instance — its header states the rule outright ("Status is data, never a failure — exit 0 in every case, including 'no checkout at all'") — and it prints `{present, match, …}` whether the pass stamp is absent, present-but-mismatched, or unreadable because there is no git dir to read from. Spending a non-zero code on "absent" would force every consuming skill to reimplement the state machine in shell, and a sibling reading that code as "not verified" is exactly the misread it prevents. Two constraints keep the exemption honest: malformed invocation of the status verb still throws into the vocabulary's usage code (`--stamp-status` rejects `--cmd`, `--scope`, `--base`, `--integration-branch`), and the exemption is declared in the CLI's own `USAGE` alongside its other modes so a reader sees which verbs it covers.
- **An "exit 0 in every state" promise is only as good as the two places it usually leaks: the parsed input's type, and a side effect whose failure gets swallowed.** `plugin/bin/qa-stamp.js` (#3003) extends status-as-data to a writer: `--write` exits 0 whether it wrote the stamp or refused, and the JSON line (`{written, reason, …}`) is the answer. Review found both leaks in one pass, fixed in `c8ccdf912`. (1) `JSON.parse` succeeds on `null`, a number, or an array, so a `report.json` holding `null` got past the parse `try/catch` and crashed on `report.stories_dir` with a TypeError, a non-zero exit the contract promised never happens. A successful parse is not a valid shape: check `value !== null && typeof value === 'object' && !Array.isArray(value)` before touching a field, and refuse through the same reason the parse failure uses (`report-unreadable`). (2) A result refusal removes a stale same-HEAD stamp, and the first version wrapped that `unlinkSync` in a bare `catch { return false; }`. An `EACCES` therefore reported the same as "nothing to remove", and the stale stamp stayed on disk for the next `--check` to honor. When a side effect changes what the caller should believe, its failure gets its own field (`invalidateFailed: <errno code>`, with `ENOENT` still treated as already gone) and the consuming prose surfaces it. Route the side effect through `deps` (`deps.unlink`) so a test can throw from it: `tests/bin-lib/verify/qa-stamp-cli.test.js` pins both the `null` report and the failed removal.
- **A guard added to an existing `run(argv, deps)` reaches the environment through `deps` too.** The seam above is stated as "every side effect", so an argument-validation *read* — `process.cwd()`, a git-root probe, a stat — reads as exempt and gets called directly. It isn't. `plugin/bin/materialize.js`'s `--run-dir` anchoring guard (#790) shipped calling `plugin/bin/lib/hooks/worktree-detect.js`'s `isAnchoredUnderRoot` directly while the `cwd`/`mainRoot` calls beside it were already injected; only a review lens caught the one-of-three gap. A validation guard bolted onto an already-seamed CLI is exactly where the seam gets holed, because it doesn't feel like a side effect — inject it (`deps.cwd`, `deps.mainRoot`, `deps.isAnchored`) as you write it, and add the fake to every consuming test's deps object in the same commit.
- **A run-directory argument gets one of four boundary guards; pick before writing the check.** `plugin/skills/_shared/pipeline-run-dir.md`'s CLI-argument-boundary section is canonical and enumerates all four itself ("Four shapes live at this boundary"); this bullet is the `bin/`-side summary, never a second registry. **(1) Pipeline-owned binaries** (`hooks.js`, `wrap-up-engine.js`, `materialize.js`, `apply-refine-labels.js`) refuse any value not anchored under the main checkout. `wrap-up-engine.js`, `materialize.js` and `apply-refine-labels.js` exit 2; `hooks.js`'s `resolveRunArg` verbs print `--run path rejected: …` and pick their exit code per verb — 0 for most, 1 for `close-run` (#3025) and `resolve-console` — so a caller reads that verb's own branch in `main()`, never a family-wide code. **(2) The two resolver CLIs** (`plugin/bin/resolve-profile.js`, `plugin/bin/resolve-policy.js`, #1065) call `worktree-detect.js`'s `checkRunDirAnchoredOrOutside` — a resolved path inside any checkout must be anchored, a path outside every checkout is accepted as-is — and exit 1, their own documented invocation-failure code. **(3) The *Sanctioned-writer* family above** (`log-decision.js`, `stage-item.js`, `set-config.js`, `set-verify-expectations.js`, `write-run-artifact.js`) applies the same strict anchoring, but through one of two exported `resolveTarget` copies rather than `worktree-detect.js` directly — `plugin/bin/lib/stage-item/write.js`'s (imported by `stage-item.js`, `set-config.js`, `set-verify-expectations.js`, `write-run-artifact.js`) or `plugin/bin/lib/log-decision/append.js`'s (imported by `log-decision.js`, and also by CLIs outside this family that append to `decisions.md` beside their main work — `repair-claim.js`, `release-claim.js`, `materialize.js`, `claim-targets.js` — which keep their own exit codes) — and refuses with exit **3**, not 2. Import the copy that sits beside the writer you call when you add another writer instead of re-deriving the predicate — `set-config.js` (#1376), `set-verify-expectations.js` (#2764) and `write-run-artifact.js` (#3044) import stage-item's, `claim-targets.js` (#2775) imports append.js's together with `appendEntry` — and pin the refusal with a fixture carrying both a real main-checkout run dir and a worktree-local shadow of it, asserting the shadow's file is byte-unchanged after the exit 3. **(4) The composer CLI** (`plugin/bin/compose-context.js`, #1988) is a run-directory *writer* (`{run}/context/{step}.md`) that nonetheless takes the *resolver* family's anchored-or-outside rule — through `plugin/bin/lib/run-dir-guard.js`'s `anchoredOrOutsideMessage`, the shared message renderer the two resolvers already call — and rejects with exit **2**, its malformed-invocation code, not 3. Strict is the default; anchored-or-outside needs a *documented* legitimate outside-repo use, and shape 4's is narrow enough to be non-precedential: its callers never branch on a run-dir code (a skill step's documented fallback on any non-zero exit is to read the named source files directly), and its tests spawn the real binary against tmp-root fixtures outside any checkout, the same documented use the resolvers have. A further writer inherits shape 4's reasoning only if its own callers share it; otherwise shape 3 is the default. The deps-injection rule above is scoped to binaries that already have a path-handling seam: the two resolvers are `main(argv)` CLIs with none, so their guard calls `worktree-detect` directly and is tested by spawning the real binary against `tests/helpers/git-fixtures.js` repos rather than by a fake — `compose-context.js` does have the seam and injects every path-handling call through it (`deps.cwd`, `deps.mainRoot`, `deps.isDirectory`, `deps.anchoredOrOutsideMessage`), which is the shape a new run-dir-taking CLI should copy.
- **A read-only run-dir *reader* still owes a stated boundary posture.** The four shapes above are framed around writes (`pipeline-run-dir.md`'s boundary refuses "before any filesystem write"), so a CLI that only reads a run-dir file looks exempt and gets no guard at all. `plugin/bin/closing-tally.js` (#2729) takes `--run`, joins `decisions.md` onto it with no anchoring check, and spends exit 3 only on an unreadable file: given a worktree-local shadow of the run dir (`[IL-127]`), it tallies the shadow's `decisions.md` and exits 0. That is a confident wrong count, and `/claude-tweaks:backlog refine`'s closing summary renders it verbatim. Pick one when you write the reader: import `lib/stage-item/write.js`'s `resolveTarget` and refuse a non-anchored `--run` on the sanctioned writers' exit 3, or state in the header why an unanchored read is safe for this CLI's callers (for example, a `--file` mode used only by tests).
- **A sanctioned writer that read-modify-writes a shared file guards it; a create-only writer doesn't.** The *Sanctioned-writer* family above splits on write shape, not on file type. `plugin/bin/lib/log-decision/append.js`'s `appendEntry` read-modify-writes one shared `decisions.md` that concurrent `bin/log-decision.js` processes contend for, so it runs the whole read-modify-write-rename under `plugin/bin/lib/file-lock.js`'s `withLock` (mkdir-based, best-effort/fail-open — a lock it can't acquire in `LOCK_WAIT_MS` proceeds unlocked rather than hanging the caller) and renames a per-process `decisions.md.tmp-${process.pid}` over the target, so a concurrent reader never sees a torn file even when the lock was missed (#816). `plugin/bin/lib/stage-item/write.js` needs neither: it creates `staged/<id><ext>` at a per-item path, so there is no read-modify-write to lose. **This still leaves a narrower hazard the create-only framing doesn't name: a *namespace* race rather than a shared-file one.** `writeStagedItem`'s opt-in `allocate: true` mode (#2770) exists because two independent writers choosing the same `{kind}-{n}` id is a real collision even with no shared file to tear — the fix isn't `withLock` (there is still nothing to lock), it's an exclusive-create (`O_EXCL`) probe of the requested slot, falling back to a directory rescan of `staged/`'s own existing `{kind}-*` entries and a retry loop through any further race, so a losing writer reallocates to the next free slot instead of clobbering. Default (non-`allocate`) callers are unaffected — see `writeStagedItem`'s header comment for which ids are safe to leave on plain overwrite. **The family's third member is guarded by neither, and the bullet above does not classify it:** `plugin/bin/lib/set-config/write.js`'s `setConfigLever` read-modify-writes the shared `config.yml` (replace the key's line, drop later duplicate lines, append when absent) through a bare `fs.writeFileSync` — no `withLock`, no tmp+rename. That is tolerable only because `config.yml` has no concurrent multi-process writer the way `decisions.md` does: the Manifesto writes it once per run, and the ceremony escape hatch downgrades a single lever in place later in that same run. #1580's `--set` batch form narrows the margin rather than widening it — it runs the whole read-modify-write once per lever in a sequential loop (13 rewrites for a full Manifesto), so a downstream `bin/resolve-policy.js --run` read racing that loop can land between two rewrites, and `writeFileSync`'s truncate-then-write opens a short-read window on each one. Before adding a second concurrent writer of `config.yml`, or widening the batch further, give `setConfigLever` the same `withLock` + tmp+rename pairing `appendEntry` already has. The pairing is the repo's established shape for a contended bookkeeping file — `plugin/bin/lib/hooks/context.js` (run-state.json), `plugin/bin/lib/flow/manifest.js` (manifest.yml, tmp+rename only), `plugin/bin/lib/json-store.js`, and `plugin/bin/lib/declined-learning/store.js` all ship some combination of it — but it is documented only in `file-lock.js`'s own header, so a new writer copied from a sibling silently inherits whichever half that sibling happened to have. Decide the shape before writing the file, and reuse `withLock` rather than hand-rolling a second mutex. `plugin/bin/lib/verify-expectations/write.js`'s `writeExpectations` (#2764) is the family's fourth member and takes the full pairing from the start — `withLock` plus `atomic-write.js`'s tmp+rename — because it read-modify-writes one shared `verify-expectations.json` that the Oversight-floor gate, the multi-spec defer protocol, the Review Console's non-Approve-all step-11 write, its empty-console fast path, and `wrap-up-engine.js finish-console` all write.
- **A Split-1/2 CLI that also writes caller-named files maps a write failure to its remote-failure code and states that it is a create-only, no-lock overwrite.** `plugin/bin/lib/compose-subject.js`'s `--out-dir <dir>` (#3522) writes `title.txt`, `body.md` and `message.txt` into a directory the caller names, with `mkdirSync` recursive and a plain `writeFileSync` per file. It sits outside the *Sanctioned-writer* family (there is no run-dir anchoring, no `withLock`, and a second compose into the same directory silently replaces the files), and a failed mkdir or write returns exit 3, the same code as a failed `gh`/`git` read, with the failing path on stderr. Say both in the header comment, and keep the caller's fence stopping on any non-zero exit before it consumes the files. A caller that must not reuse a stale pair removes or re-creates the directory first; this CLI does not.
- When an endpoint has no GitHub MCP equivalent, say so and name the real fallback; never invent an MCP row in `plugin/skills/_shared/github-write-transport.md`.
- **Hoist a warning-emitting check ahead of the destructive call it warns about, not after.** `plugin/bin/repair-claim.js` (commit `387b53f4e`, spec #1608 Finding 3) and `plugin/bin/release-claim.js` (spec #1710) both shipped the same bug independently: `resolveTarget` — the run-dir anchoring check whose stderr warning tells an operator `decisions.md` will not be written — ran *after* the CLI's own destructive write (`repair`/`release.releaseClaim`), so the warning arrived only once the irreversible part was already done. Both fixes were pure reorderings — compute `resolveTarget` (and emit its warning) before the destructive call, leave `formatEntry`/`appendEntry` after it since they need the outcome. Two independent CLIs shipping the identical ordering mistake is a pattern, not a coincidence: when a CLI on this seam pairs a destructive write with a warning about why its own audit trail might not land, write the warning-emitting check first.
- **A CLI whose main work is not a run-dir write can still take `--run` for a best-effort audit line — the anchoring refusal then lands in its envelope, never its exit code.** `plugin/bin/claim-targets.js --run` (#2775) writes Step 2.8's claim-log line to `decisions.md` for each target it claimed. Three choices make that safe. First, `--run`'s basename must equal `--run-id`, else exit 2, so a claim is never logged under another run. Second, the write goes through `lib/log-decision/append.js`'s `resolveTarget` before `appendEntry`, the same check `log-decision.js` runs, so a worktree-local shadow is refused rather than silently written (`[IL-127]`). Third, a refusal or write failure never un-claims a target and never changes the exit code: it is pushed to a `claimLogFailures` array with a stderr line, and that key appears in the JSON only when `--run` was passed, so every existing caller's envelope stays byte-identical. Copy that shape when a CLI's real outcome must not depend on whether its audit line landed, and in the same change give the consuming prose a branch for a non-empty failure array. For `claim-targets.js` that branch is the hand `log-decision.js` call per failed issue, and `flow/claim-targets.md` does not state it yet.
- **A CLI with one code path per work-backend driver carries one safety check per driver — harden them together or not at all.** `plugin/bin/release-note-repair.js` verifies its `github-issues` write in `verify` (via `lib/release-note-repair/apply.js`'s `verifyWritten`) and its `local-files` write inside `repairLocal`. A fix round added the "nothing else changed" proof (`onlyReleaseNoteAdded`) to the first only, so a concurrent edit to a local record that still verified was reported as this run's repair; a lens review caught it a round later and `b3c936252` added the byte-equality gate `repairLocal` now runs before success or restore. When a fix changes one driver's check, the same commit changes or explicitly exempts every sibling driver's equivalent check, and adds a discriminating test per driver (`tests/bin-lib/release-note-repair/cli.test.js`'s "a concurrent edit that would still verify" case is the local-files one). Route both through one shared function where the drivers' inputs allow it; where they don't, say beside each check which sibling it mirrors.
- **A `gh`-absent caller hands the CLI already-fetched records as a file; the CLI never tries to reach MCP itself.** A `plugin/bin/` CLI is a plain Node subprocess and cannot see the agent session's MCP tools. So in a sandbox without `gh`, the calling skill fetches through MCP `issue_read`, reshapes each record to `gh issue view --json number,title,body,labels,url`'s fields, writes the JSON to a session-scoped temp file, and passes its path. Two CLIs ship this seam: `plugin/bin/materialize.js --record-json <path>` (#1459, one record object) and `plugin/bin/preflight-records.js --records-json <path>` (#3351, an array of the requested records). Copy three things from them. (1) That path makes **zero** `gh` calls and never probes for `gh` (`materialize.js` skips `deps.ghAvailable()`), so a fetch-failure code is unreachable there; `preflight-records.js`'s header says outright that this path never exits 1. (2) Every problem with the file lands on the malformed-invocation code, exit 2 in both. `materialize.js` covers a file that will not read or parse; `preflight-records.js` also rejects a wrong shape and a requested number that is missing, duplicated or unrequested (`issuesFromRecordsJson` in `plugin/bin/lib/preflight-records/preflight-records.js`). A new one validates the shape too, since `JSON.parse` succeeds on `null` (the `qa-stamp.js` bullet above). (3) Anything the `gh` path learns from a further call that the file cannot carry degrades visibly. `preflight-records.js` cannot run work-links native's GraphQL call, so it reads `blocked-by` from the bodies, prints a stderr line, and adds `nativeLinksUnchecked: true` to its envelope, a key absent on every other run. The calling prose owns the transport branch: how to fetch and reshape, and what a failed MCP fetch does (`plugin/skills/flow/multispec-preflight-failure.md`'s Transport paragraph stops before claiming and never writes a partial file; `plugin/skills/flow/materialize.md`'s `--record-json` paragraph is the reshape reference). The flag is singular for one record and plural for an array; keep that spelling for a third CLI.
