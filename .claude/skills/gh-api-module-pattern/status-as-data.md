## Status-as-data verbs

Lazy-loaded from `cli-wrapper-contract.md`: read it before writing a verb that reports state as data and exits 0 in every state, instead of keying its exit code on an outcome.

- **A read-only *status* verb is status-as-data: it exits 0 in every state, and the JSON on stdout is the answer.** The exit-code vocabularies in `cli-wrapper-contract.md` key *the outcome of doing something*; a verb that only reports the state of an artifact the CLI itself wrote has no such outcome to key. `plugin/bin/verify.js --stamp-status` (#1921) is the shipped instance — its header states the rule outright ("Status is data, never a failure — exit 0 in every case, including 'no checkout at all'") — and it prints `{present, match, …}` whether the pass stamp is absent, present-but-mismatched, or unreadable because there is no git dir to read from. Spending a non-zero code on "absent" would force every consuming skill to reimplement the state machine in shell, and a sibling reading that code as "not verified" is exactly the misread it prevents. Two constraints keep the exemption honest: malformed invocation of the status verb still throws into the vocabulary's usage code (`--stamp-status` rejects `--cmd`, `--scope`, `--base`, `--integration-branch`), and the exemption is declared in the CLI's own `USAGE` alongside its other modes so a reader sees which verbs it covers.
- **An "exit 0 in every state" promise is only as good as the two places it usually leaks: the parsed input's type, and a side effect whose failure gets swallowed.** `plugin/bin/qa-stamp.js` (#3003) extends status-as-data to a writer: `--write` exits 0 whether it wrote the stamp or refused, and the JSON line (`{written, reason, …}`) is the answer. Review found both leaks in one pass, fixed in `c8ccdf912`. (1) `JSON.parse` succeeds on `null`, a number, or an array, so a `report.json` holding `null` got past the parse `try/catch` and crashed on `report.stories_dir` with a TypeError, a non-zero exit the contract promised never happens. A successful parse is not a valid shape: check `value !== null && typeof value === 'object' && !Array.isArray(value)` before touching a field, and refuse through the same reason the parse failure uses (`report-unreadable`). (2) A result refusal removes a stale same-HEAD stamp, and the first version wrapped that `unlinkSync` in a bare `catch { return false; }`. An `EACCES` therefore reported the same as "nothing to remove", and the stale stamp stayed on disk for the next `--check` to honor. When a side effect changes what the caller should believe, its failure gets its own field (`invalidateFailed: <errno code>`, with `ENOENT` still treated as already gone) and the consuming prose surfaces it. Route the side effect through `deps` (`deps.unlink`) so a test can throw from it: `tests/bin-lib/verify/qa-stamp-cli.test.js` pins both the `null` report and the failed removal.
- **A CLI whose module already returns a discriminated envelope with a frozen `reason` enum may extend status-as-data to a verb that *acts*: exit 0 on every envelope, 2 on usage only.** `plugin/bin/impeccable-engine.js` (#2979) is the shipped instance. Its `run` subcommand execs a third-party launcher for one of four `VERBS` (`signals`, `doctor`, `concept-seed`, `surface-brief`), and `resolve` execs the same launcher's `engine-probe`. Both exit 0 for `{ok:false, reason}` results, and the header states the posture ("failures are data the caller branches on"). Its six failure classes (`FAILURE_REASONS` in `lib/impeccable-engine/index.js`: `not-installed`, `upgrade-required`, `engine-not-installed`, `shape-mismatch`, `exec-failed`, `timeout`, frozen as a cross-sub-issue contract) are more than an exit code can carry, and every consumer is skill prose that parses the JSON anyway. Mapping some of them onto 1/3 would give two channels for one answer. Three conditions keep this honest. (a) The `reason` enum is exported and frozen, so callers branch on a pinned vocabulary, not on free text. (b) A usage error never calls `resolve()`/`run()`, so it never spawns anything (`validateVerbArgs` gates before `run`; an unknown verb is a usage error). (c) The header states the posture outright, the way `verify.js` does. Without a frozen enum, pick one of the four vocabularies in `cli-wrapper-contract.md`.
