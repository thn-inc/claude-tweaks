## Batching and failure posture

- Resolve everything up front in one call where the API allows it (aliased GraphQL: one `i{N}: issue(number:{N}){ databaseId }` per distinct number), and chunk the alias list rather than letting one query grow unbounded — `plugin/bin/fetch-sub-issues.js` slices its input at 50 numbers per call and merges each chunk's result into one envelope.
- **The alias-query *builder* is a pure function in `plugin/bin/lib/issues/record-dependencies.js` (re-exported through `record.js`), separate from whatever runs it.** `buildNativeDependencyQuery`, `buildNativeSubIssuesQuery`, and `buildNativeParentQuery` each take a `numbers` array, return the query string, and return `null` for an empty or non-array input — an empty `repository{}` selection set is invalid GraphQL, so the caller must branch on `null` rather than send it. `record-dependencies.js` requires nothing at all and shells out nowhere, which is what lets `tests/bin-lib/issues/record.test.js` pin each builder with plain regex assertions and no fake runner at all; the transport, the chunking, and the partial-result posture below all belong to the caller (`plugin/bin/lib/issues/native-dependencies.js`, `plugin/bin/resolve-blockers.js`, or a skill's own `node -e` line), never to the builder. Add a fourth builder the same way — and factor the shared `query($owner:String!,$repo:String!){ repository(owner:$owner,name:$repo){ … } }` envelope out when you do: the three above repeat it verbatim today (#1194 hindsight).
- **Relay-style cursor pagination direction is a footgun on a connection field whose events accumulate over a long-lived object's life.** `first:N` fetches the OLDEST N nodes; `last:N` fetches the NEWEST N — the same `record-dependencies.js` file's fourth builder, `buildLinkedPRQuery`, shipped `timelineItems(itemTypes:[CROSS_REFERENCED_EVENT], first:20)`, so a long-lived issue that accumulates many cross-references (other issues discussing the same subsystem, health-sweep dedup comments) can have its own merged PR's reference pushed out of that oldest-20 window, well before any classifier sees it. Confirmed live against #1892/PR#2287: #1892 had accumulated 20+ issue-based cross-references before #2287 ever merged, so `first:20` returned zero PR sources even though the pair should have scored `strong`. Fixed to `last:20` (#2449) — a shipped/duplicate-detection query wants the freshest signal, not the earliest. Check pagination direction against what the query is actually trying to answer; don't copy the `first:N` convention the bounded, order-agnostic alias builders above use onto an accumulating connection without re-deriving it.
- **Two sanctioned partial-result postures; choose by whether the caller can recover per item.** *Throw on a partial result* when partial data is unusable — `plugin/bin/lib/issues/native-dependencies.js`'s `fetchNativeDependencies` throws naming every missing `i{N}` alias (#723), because a caller that silently drops a dependency edge ships a wrong graph. *Return a retry envelope* when the caller has a per-item fallback — the same file's `fetchNativeSubIssues` returns `{byParent, retry}` (#1097), routing a single missing or null alias onto `retry` for the caller's per-parent REST loop instead of failing the whole batch; such a parent never lands in `byParent` as `[]`, because an empty array already means "fetched, has no sub-issues". A whole-response failure (`data.repository` null or missing) throws under *both* postures — an envelope degrades per item, never per batch.
- **Routing an existing caller onto a shared module inherits that module's posture — re-check the caller's blast radius, not just its output shape.** The two postures above are chosen when a module is *written*; the hazard lands at the *caller migration*, where a call site that degraded per item silently starts degrading per batch. `plugin/skills/dispatch/queue-pull-script.md`'s `work-links: native` branch (#1309) moved from a hand-rolled `gh api graphql` response fed to `record.js`'s `partitionByOpenNativeBlockers` — which reads a missing `i{N}` alias as an empty blocker list and so fails open for *that one candidate* — onto `plugin/bin/resolve-blockers.js`, whose `fetchNativeDependencies` throws on any single missing alias (the *throw on a partial result* posture above), exits 3, and disables native blocker filtering for **every** candidate in the run. The per-record output shape was identical and the suite stayed green; only the failure fan-out changed, so no shape-level assertion could catch it. When such a migration is the point of the change, state the old and new degrade granularity side by side in the record, and give the caller an exit-code branch that separates a partial result from a total outage instead of one catch-all `else`.
- **A bulk alias query is chunked, all-or-nothing, and never authorizes a destructive act by itself.** `plugin/bin/lib/reconcile/pr-state.js`'s `resolvePrStatesBulk` (#1082) resolves N branches' governing PRs in `ceil(N/50)` calls of `b{i}: ref(qualifiedName:"refs/heads/…"){ associatedPullRequests }` aliases — the chunk size is probe-measured, not guessed: 50 aliases cost 1 GraphQL rate-limit point. It returns a complete `Map` or a failure sentinel, never a partial map: a transport throw, an HTTP-200 body carrying `errors[]`, and an alias key missing from `data.repository` each fail the whole call, because a dropped chunk's branches are otherwise indistinguishable from branches with no PR. Bulk evidence is also weaker than a per-branch read — `ref()` is null for a branch deleted after its PR merged — so a caller screens with it to skip cheaply and re-confirms via `resolvePrState` before anything destructive (`prune-remote.js`, `archive-branches.js`).
- **A single GraphQL query that errors exits non-zero, but its body is still on stdout — classify absence from that body, never from stderr.** The bulk bullet above covers an HTTP-200 body carrying `errors[]`; a per-object query for a missing node is different: `gh api graphql` exits 1 and still writes the full JSON response to stdout, so the thrown error's `e.stdout` is the evidence (live-probed on PR 999999: `{"data":{"repository":{"pullRequest":null}},"errors":[{"type":"NOT_FOUND","path":["repository","pullRequest"],…}]}` on stdout, `gh: Could not resolve…` on stderr). Read absence only from `errors[].type === 'NOT_FOUND'` at the exact `path` **and** a non-null parent object (`data.repository`) — a null parent means the repo itself did not resolve, which is not proof the child is gone. Everything else (no body, unparseable body, `FORBIDDEN`, a null parent) stays the seam's transport classification. `plugin/bin/lib/reconcile/pr-state.js`'s `isPrNotFoundBody` / `confirmPrNotFound` (#3543) is the reference: its `runClassified` mapError receives the throw and returns `e.stdout`, and the probe keeps stdout piped.
- **A screen value that is *blind* rather than negative may route, never terminate — and the cheap-skip half needs that rule as much as the destructive half.** The bullet above guards only the destructive direction (re-confirm before deleting), which leaves "screens with it to skip cheaply" reading as license to let any non-`MERGED` screen end the decision. That is where `archive-branches.js` shipped a gap: `squashCandidate` read `screenPr.state === 'MERGED'` only, so a screen-`null` branch — the documented deleted-ref blind spot above, the *absence* of an answer rather than a negative one — reached the per-branch confirm only when some other provisional verdict already sent it there (cherry-equivalent, or aged past `BRANCH_AGE_DAYS` onto the tag-and-delete path). A **young, non-cherry-equivalent, squash-merged** branch matched neither, so its provisional `skip`/`too-young` was final on every pass forever, and it never reached the confirm that carries the `mergeCommit` its squash-provenance proof needs (#2322 widened the boolean to `screenPr === null || screenPr.state === 'MERGED'`). Discriminate on whether the screen value is *conclusive*, not on whether it is negative: an `OPEN` screen is a real answer and still short-circuits with no per-branch call at all, while `null` must cost one confirm. Widening a route never widens what the confirm decides — a confirm coming back `null`/`CLOSED`/`OPEN` falls through to the same age rules as before — so the bill is one `gh pr list --head` per screen-null, non-cherry-equivalent branch per pass, bought against converging on the first pass instead of after the age threshold. When adding or changing a screen/confirm caller, enumerate the screen's values against *every* provisional verdict the caller can reach, not just the destructive one; a permanent skip is a verdict too.
- Per-write calls are each independently try/caught into `{ok: [...], failed: [{…, error}]}` — one failed edge never aborts the batch. An "already exists" 422 is a re-run, not a failure: it lands in `ok` with `already: true` (live-confirmed wording: GitHub answers `Validation failed: Target issue has already been taken`).
- Error text: join `err.message`/`err.stderr`/`err.stdout`, with a `String(err)` fallback so a non-Error throw never yields an empty `failed[].error`.
- **Enumerate an operation's full documented error-status set in one sitting.** Adding one status per bug report ships the same misclassification serially: `plugin/bin/lib/issues/claim-store.js`'s Contents-API PUT got its 422 create-race branch in `75c8b3b6`, then the symmetric 409 sha-mismatch branch in `4ee0fbcc` — one defect class, found twice, the second time by a review lens. Read the endpoint's documented statuses first (Contents PUT: 404 read-miss, 409 sha-mismatch, 422 create-race) and branch on all of them in the same commit.
- **Rate-limit recognition and burst pacing.** Classify a `gh api` rate-limit failure per `plugin/skills/_shared/github-rate-limit.md`'s taxonomy before deciding whether to retry — a plain 403 under that file's rules is not transient and must not be retried. When a module issues a scripted sequence of mutative calls, follow that file's burst-shape rules.
- **A transient-failure retry on a non-idempotent mutating call needs a dedup-safe recheck, not the same blind retry as an idempotent read.** A 5xx/timeout/reset signature is ambiguous about *where* the failure happened: the request may have reached GitHub and succeeded, with only the response lost. Retrying `gh issue list`/`issue view` on that signature is free — a second read changes nothing. Retrying `gh issue create` (or any other non-idempotent write) the same way risks filing a duplicate. `plugin/bin/lib/feedback/file-feedback.js`'s `createWithDedupSafeRetry` is the shipped instance (#834/#835 review): before each retry of the create call, it re-runs the module's own dedup search for a marker unique to this call — a hit means the "failed" attempt actually succeeded, so that result is reused instead of creating a second one. A single generic retry wrapper applied uniformly across a module's read and write calls is exactly the shape this hazard hides in.
- **A machine-filed issue carries only the labels its filing context can actually justify — and the module's header says so.** The two shipped `gh issue create` sites split on whether an LLM is in the loop. `plugin/bin/lib/feedback/file-feedback.js`'s `fileDraft` takes `labels` from its caller, because the `/feedback` skill orchestrating it can judge them. `plugin/bin/lib/reconcile/escalate-residue.js` files `--label bug` and nothing else, from the no-LLM contexts named in its header (`session-start.js` in-process, `bin/hooks.js reconcile`) — deliberately, not as a gap (#1216): `risk:*`/`size:*` are content judgments no mechanical caller can score, a fixed always-low default is wrong on its own, and `ready` asserts a spec-shaped body that a terse auto-report is not. Leave the enrichment to the downstream path that demonstrably picks the issue up — a plain open issue is already a backlog-stage record that `/specify` shapes and `/backlog` grants route onward — and record the posture in the module's header comment, since the alternative is a later reader re-opening the thin label set as a missing-facets bug (which is what #1216 was).
- **Widen an existing call's `-q` projection before adding a second API call — once the call itself is proven complete.** When a later step needs one more field off data you already fetched, extend the `jq` filter rather than issuing a fresh request — `plugin/bin/lib/issues/claim-store.js`'s `listClaimEntries` widened `-q .[].name` to `-q '[.[] | {name, sha}]'` to get each claim blob's `sha` from its single directory listing (#820 D6), instead of a second lookup per entry. The projection survived; the endpoint under it did not: #820 kept the Contents-API listing explicitly *instead of* a Git Trees call, and that listing silently capped at 1000 entries until #3098 moved the same `{name, sha}` projection onto the Trees API (next bullet). Widening saves a call only on an endpoint whose result you have already shown to be whole.
- **A listing endpoint's size cap is part of its contract — check it before trusting the list as whole.** The REST Contents API's directory listing (`repos/{owner}/{repo}/contents/{dir}`) returns at most 1000 entries and says nothing when it stops: no `truncated` flag, no `Link` header, just a shorter array indistinguishable from a small directory. `claim-store.js`'s `listClaimEntries` read `claims-registry`'s `claims/` that way from #820 until #3098, by which point every claim sorting past the 1000th (roughly #2983 and up) was invisible to every caller. For a keyspace that grows without bound, read it through the Git Trees API (`repos/{owner}/{repo}/git/trees/{branch}` with `recursive=1` — as a GET; see the method-flip paragraph under the flag table), which carries an explicit `truncated` boolean, and return a truncated response as its own failure value (`'truncated'`, exit 3 from `plugin/bin/list-claims.js`), never as a short success. Route every prose call site through the one tested module rather than an inline `gh api` one-liner, as #3098 did for `_shared/issue-claims.md`, `_shared/github-pr-scan.md`, and `tidy/scan-procedures.md`: three hand-rolled copies of the capped call were three places the fix would otherwise have had to land.
- **A paged REST list that reports `total_count` is whole only when one page holds it all — paginate, or compare and fail closed.** `commits/{sha}/check-runs` and `commits/{sha}/status` page their arrays and report `total_count` beside them. `plugin/bin/lib/reconcile/red-tip.js` reads every page (`gh api --paginate`); `plugin/bin/pr-checks.js`'s `readBase` (#3258) asks for `per_page=100` and, when `total_count` exceeds the array, returns plain `red` with a `… truncated: N of M` `baseReason` instead of comparing against a short list. `plugin/bin/lib/release-preflight/pack.js` counts failures over one 100-row page while reporting `total_count` as the total — the shape not to copy. `per_page` goes in the path, never in `-f` (the method-flip paragraph above).
- **`gh api --paginate` prints each page as its own JSON document, so `JSON.parse` over the whole stdout throws once a second page exists.** Project per item with `--jq` and split on newlines (`--jq '.[].number'` in `plugin/bin/fetch-sub-issues.js` and `plugin/bin/lib/backlog-grant-gate/backlog-grant-gate.js`, `--jq '.[].ref'` in `plugin/bin/lib/reconcile/ledger-residue.js`), or pass `--slurp` for one outer array of pages, as `plugin/bin/lib/activity/gather.js` does. Never hand-parse the concatenated pages: `ledger-residue.js` first shipped a page splitter that review replaced with `--jq` (#3812). A one-page fixture cannot show this failure; a two-page fixture can.
- **`gh pr list` returns at most `--limit` rows (30 by default) and says nothing when it stops, so `--state all --limit N` is a recency window, not a history.** A decision that must see an old PR — a declined proposal that must stay declined, a leftover OPEN PR that blocks a new one — cannot read it from a capped list. Enumerate by a key that has no window: `ledger-residue.js`'s `defaultListRemovalPrs` lists its branch prefix through `git/matching-refs/heads/{prefix}` (paginated), then runs one `gh pr list --head {branch} --state all` per head (#3812, where `--limit 100` covered about a day and a half of this repo's PRs). That key has its own bound: a head deleted after merge drops out, so a check that needs merged PRs whose branches are gone needs another key.
- **`gh pr list --head {branch}` matches the branch name in every repository, forks included (`<owner>:<branch>` is not supported), so a same-named fork PR arrives as one of yours.** Request `isCrossRepository` and drop rows where it is `true` before trusting a row's state or body; a fork's body is text anyone can write. `ledger-residue.js`'s `defaultListRemovalPrs` filters this way and `tests/bin-lib/reconcile/ledger-residue.test.js` pins it with a cross-repo row (#3812 review). `plugin/bin/lib/reconcile/pr-state.js`'s `resolvePrState` does not filter: its `PR_LIST_ARGS` requests no `isCrossRepository`.
- **A run list for one sha is a history, not a state — keep each workflow's newest run before reading a failure as current.** `gh run list --commit {sha}` returns every run for the sha, re-runs included, so a failure a later run superseded still shows; check-runs (default `filter=latest`) and commit statuses are already latest per name. `plugin/bin/lib/pr-checks/classify.js`'s `newestRunPerWorkflow` (#3258) keys on `workflowName || name` and keeps the highest numeric `databaseId`, so the `--json` field list must request `databaseId`. A row that still cannot be ordered goes whichever way cannot loosen the verdict the list feeds.
- **Cross-check a documented failure-status word against `append.js`'s `STATUSES` enum before wiring a batch CLI's `catch` to log nothing on failure.** `plugin/bin/lib/log-decision/append.js`'s `STATUSES` (`AUTO`/`STAGED`/`KEPT-PROMPT`/`SCANNED`/`REFUSED`/`SKIP`) has no `FAILED` member. A consuming skill's prose can still document a `FAILED {time} — …` `decisions.md` template its own closing-summary tally counts on — `apply-refine-labels.js` (#844) shipped exactly this gap: its `catch` block only appends to the stdout JSON's `failed[]` array, never to `decisions.md`, because `FAILED` isn't a loggable status. Check the enum, not just the prose, before assuming a documented status word is writable via `appendEntry`.
- **On a path another process may prune, read and catch — never `existsSync`-then-read.** These modules read `.claude-tweaks/pipelines/` run-dirs that this project's own reconcile/archive passes prune concurrently, so an `existsSync` guard ahead of `readFileSync`/`readdirSync` is a window, not a check: the path can vanish between the two calls and the read throws exactly where the guard promised it could not. Read straight off and wrap in `try`/`catch` — an absent path and a mid-read prune then arrive as the same degraded value, with one code path instead of two. `plugin/bin/lib/wrap-up/engine-verify.js` shipped the guard-then-read pair three times (`resolvedIssueNumbers`, `memory-updates`'s index read, and its per-check map); two independent review agents reproduced it and `997e571c` fixed all three. A bare `existsSync` used as a *verdict*, with no read behind it (`resolveArchivedRunDir`, the `run-dir-archived` check), is not this hazard — the pair is.
- **One unit's throw never aborts the report, and the verdict a throw maps to is a decision.** The per-write `{ok, failed}` rule above generalizes past runner calls: any module mapping a registry of independent units to results wraps each unit in its own `try`/`catch`, because one uncaught throw prints no output at all and exits through Node's default path, silently colliding with the CLI's documented exit-code contract. `engine-verify.js`'s `runVerify` maps its `CHECKS` array that way and maps a throw to `fail`, not `unknown`: for a gate whose whole purpose is to block on doubt, a unit that could not determine its own state is evidence to block rather than to shrug. Pick the direction the module errs and say so beside the `catch` — the two are not interchangeable.
- **A corroborating read's failure demotes only the verdicts that read could have changed.** When a CLI pairs a primary read with a second one that can only add evidence in one direction, mapping every failure of the second read to one catch-all state overwrites primary verdicts it could never have overturned. `plugin/bin/pr-checks.js` (#3405) lists `gh run list --commit {headRefOid}` beside `gh pr view`'s `statusCheckRollup`: a head run can turn green into pending or red, never red into anything else. As first built, any runs-read failure returned `read-failed`, and `_shared/pr-check-gate.md` routes `read-failed` fail-open for `/test` and `/review`, so a red rollup plus a transient `gh run list` error let the gate pass. `90c16ad71` keeps the conclusive verdict (`if (runsFailure && verdict.state !== 'red')`), with a CLI test that fails on the prior code; the same CLI also skips the second read when the head is `stale`, so a transient failure cannot turn `stale` into `read-failed`. Before writing the second read's `catch`, list which primary verdicts it can change, and let its failure touch only those.
- **A corroborating read that can *loosen* a verdict moves the primary read's failure gate after it.** The bullet above covers a read that can only tighten. `plugin/bin/pr-checks.js`'s base comparison (#3258) can demote `red` to `inherited-red`, which `_shared/pr-check-gate.md` passes with a caveat, so the runs-read gate now tests the post-comparison verdict (`if (runsFailure && final.state !== 'red')`): when `gh run list` failed, a comparison that would conclude `inherited-red` reports `read-failed`, since a failing head run the partial read missed could be the one attributable failure. The loosening read's own failure still touches only what it could change: `applyBaseComparison` leaves plain `red` with a `baseReason`. Compare against the ref the PR merges into (`gh pr view --json baseRefName`), with the integration-branch resolver only as the fallback when the view names none: a PR into a release branch inherits that branch's red, not the default branch's.
- **`isIndeterminate` is the wrong failure filter when a probe's *negative* answer lives in stdout.** `plugin/bin/lib/hooks/git-exec.js` exports `isIndeterminate` (timeout/spawn/no-git) for failures where "the question went unanswered, rather than answered in the negative" — but that split only holds for a call whose negative answer *is* the non-zero exit (`merge-base --is-ancestor`, `rev-parse --verify`). For a probe that answers in stdout — `git ls-files -- <dir>` prints nothing for an untracked path and still exits 0 — a definitive `FAILURE.GIT_ERROR` (corrupt index, unreadable object store) is as unanswered as a timeout, so filtering on `isIndeterminate` and letting `git-error` fall through to the falsy branch reads "the probe broke" as "the answer is no". `plugin/bin/lib/reconcile/archive-merged.js`'s `hasTrackedContent` (#2227) shipped that in `751f22c92` — the whole-branch review explicitly waved the `git-error` case through as "an answer" — and a later review lens caught it against the module's own sibling guard, `archiveRunDir`'s `ls-files-failed` refusal, which already fails closed on *any* failure; `67af77ee7` made every failure kind assume tracked. When a probe result selects a **route** rather than filling a report field, branch on `failure` as one condition, say which direction is safe in a comment beside it, and check the sibling probe in the same module before adopting a narrower filter than it uses.
- **A catch-all classifier reads the caller's own programming error as a transport failure — check the caller contract before the seam and answer with a distinct value.** `plugin/bin/lib/reconcile/pr-state.js`'s `classifyExecError` maps every throw that is not `gh-absent` to `'network-failure'`, so a misordered call — `resolvePrStateByNumber(4242, { cwd, repo })` — handed `execFileSync` a non-string `cwd`, threw `ERR_INVALID_ARG_TYPE`, and came back `'network-failure'`, the same answer as a real outage (#3029). `byNumberArgsValid` now rejects a non-string `repoRoot`, or a number that is not a positive integer or positive-integer string, before any `gh` call and returns `'invalid-arguments'`. It returns rather than throws because both by-number resolvers feed callers that must never throw (`archive-merged.js`'s SessionStart sweep, `_shared/github-pr-scan.md`'s per-PR loop). The guard owes that never-throw property itself: its first version called `String(number)` on every input, which throws on `Object.create(null)`; the whole-branch review caught it and `9cfb79dd6` checks `typeof` first. Pin each malformed input with its own assertion, a prototype-less object included (`tests/bin-lib/reconcile/pr-state.test.js`). A type guard does not cover a well-typed but wrong value: a `repoRoot` string naming a path that does not exist still reaches `execFileSync`, whose `ENOENT` is the same code a missing `gh` binary raises. `cb18c68b9` rechecks `repoRoot` only after a `gh-absent` classification, so a successful call pays no extra filesystem probe.
