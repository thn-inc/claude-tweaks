# Dispatch queue-pull exclusion addition

## Overview

Each exclusion pass lives in `plugin/bin/lib/dispatch/queue-pull.js` (#5230: a `PASSES` row plus a `RUNNERS` entry; `/dispatch` Steps 2-3 call it through `plugin/bin/queue-pull.js`) and writes `{reason, records, detail}` entries through `plugin/bin/lib/dispatch/exclusions.js`'s `appendExclusion`, the one sanctioned writer (#3110: it refuses a corrupt file rather than clobbering earlier passes' entries). The pass is the easy part. Every selection form, report and doc that names the reasons must learn the new one too, and the earlier additions missed sites: #3084 fixed the `#N` forms misreporting a `not-spec-shaped` record as an open PR, and #3085 restored the shipped-candidate report.

## The registration set

**Until the removal unit lands, the retained `plugin/skills/dispatch/queue-pull-script.md` is not the live home of a pass but is still mirrored.** A pass change is made in the module and mirrored in the retained `queue-pull-script.md` (header bullet and pass block), so #5227's parity test stays green. Rows 1 and 2 below are that mirror, not the live pass. The one exception is a rule on the `files` transport that reads the agent's raw dependency-freshness text, which the fence never receives: #5408's omitted-dependency check and #5865's `unreadable` entry are module-only by decision, named in the module's header, and take no fence mirror.

## Decisions each pass owes

1. **Removing or not?** A removing reason drops the record from `dispatch-groups.json` before any selection form reads it, so even a named `#N` cannot dispatch it. `oversized` and `neighbour-in-flight` stay in the file and only bare drain's ranking skips them, because a person naming the record accepts that risk. Choose removing only when no one could accept the risk, because a later gate would stop the record anyway after a claim and a spent retry.
2. **Where in the order?** Run a pure pass (no `gh`, such as `not-spec-shaped`) before the `gh`-backed probes, so an excluded candidate costs none of their calls. A pass that judges the remaining pool goes after the passes whose exclusions it should not re-check.
3. **Cache hit too?** Run the pass on a queue-order cache hit when the state it reads can change without touching the records' `updatedAt` (an open PR, a blocker's commit landing). Skipping it there brings back the bug the pass exists to fix. A pass whose verdict a hit replays instead of re-running needs the cache to miss whenever its inputs carry such state: the `blocked` pass reads foreign blocker states the freshness signal cannot see, so `cacheUsable` in `plugin/bin/lib/dispatch/queue-order.js` refuses a hit while any `auto:build` body declares a `Blocked by owner/name#N` line or a persisted exclusion names a foreign blocker (#4793).
4. **Fail open or stop?** A pass whose judgment a later gate repeats before any claim (`/flow` Step 2.7b re-checks blocker landing) fails open with one `Warning:` or `AUTO` line. Only a refused `appendExclusion` write or an unreadable `$DISPATCH_GROUPS` stops the pull. An input that does not resolve skips only the pass that needs it, with one `Warning:` (#5863: an integration branch whose `origin/` ref names no commit skips `target-missing`; `state.integrationBranch` and `integrationRef` stay as resolved, because the unlanded-blocker pass checks landing through the GitHub API). Run the probe that finds it only when the pass does, so an omitted pass costs no call.
5. **Can one record turn the pass off?** When the pass batches every candidate into one call that fails as a whole on a single bad input, screen that input out under its own reason first (#4792's `malformed-blocker`). See `gh-api-module-pattern`'s `batching-failure-posture.md`.
6. **Is the record even in the pool?** The passes only judge the fetched pool. `admitNamed` (#5584, between the pool fetch and the passes) puts a named record that lacks `auto:build` into the pool when the build-authority rule answers `typed`, and records it in `state.typedNumbers`, which the `blocked` pass's grant filter accepts. A refused named record is a printed line, never a pass, a reason word or a registry row, so none of the sites above apply to it; a change to the grant filter or to what a pass assumes about a record's labels must keep `typedNumbers` records judged exactly as granted ones are.
7. **Does the pass hand its verdict on through a file?** When the next pass reads a file whose empty or partial form is itself a valid answer (an empty verified-open-deps file reads as "none open"), write it once after the loop and remove it when that write fails, so the reader fails closed on a missing file. #5311's first fix pre-truncated the file and appended per dependency, so a throw mid-loop left a well-formed wrong answer (fixed in 50eed85ef). Do not pre-truncate it in the fence twin either: a throw between the truncate and the write left the empty file and failed open (#5879). Remove it at the start of the step instead (the gh transport only; on `files` the file is the agent's input and is never removed), so a throw leaves it absent in both twins and the stop-path parity rows still compare the same file state.
8. **Does a new signal mean the same thing to the pass as an existing one?** When a second signal changes the pass's control flow the way an existing one does (#5722's `predates-shaping` beside #4432's `predates-claim-release`: either downgrade skips the files probe), add one shared predicate for the shared meaning (`downgradedAfterMerge` in `plugin/bin/lib/issues/shipped-candidate.js`) and keep the signal-specific one (`predatesClaimRelease`) only where the wording differs, such as the kept line. A call site that tests one signal by name misses the other.

## Common Operations

Derive the site list from the last reason added rather than trusting the table alone:

```bash
git grep -n -l -E "unlanded-blocker|target-missing" -- plugin docs tests
```

Then run the derived-list test, the module suite (its parity tests fail when the module and the retained script disagree) and the new reason's conformance test:

```bash
node tools/run-tests.js tests/dispatch-named-form-exclusion-reasons.test.js tests/bin-lib/dispatch/queue-pull.test.js tests/bin-lib/dispatch/queue-pull-oracle-checks.test.js tests/bin-lib/dispatch/queue-pull-parity-ac1.test.js tests/bin-lib/dispatch/queue-pull-parity-ac4.test.js tests/bin-lib/dispatch/queue-pull-parity-ac5.test.js tests/bin-lib/dispatch/queue-pull-parity-ac7.test.js tests/bin-lib/dispatch/queue-pull-parity-d1.test.js
```

## Anti-Patterns

| Pattern | Why it fails here |
|---|---|
| Adding the pass and its report, but not the `#N` bullets | A named record dropped by the pass prints the wrong reason or none (#3084, after #2829 added `not-spec-shaped`) |
| Wording a removing reason's bullet with "stay IN `dispatch-groups.json`" | The mirrored bullet then disagrees with the module's `removes` column, which `REMOVING_REASONS` derives from; AC11.1 goes red on it. Keep the bullet and the `PASSES` row saying the same thing |
| Writing the entry with `fs.writeFileSync` instead of `appendExclusion` | It clobbers every earlier pass's entries for this firing (#3110) |
| Changing only the retained `queue-pull-script.md` | It is no longer the live path; the CLI runs the module, so the change never takes effect (#5230). Change the module, then mirror the script |
| Changing only the module, until the removal unit lands | #5227's parity test runs the script's fence and the module on the same fixtures and goes red on the drift |
| Keeping the pass's rationale in the module's or script's comments | Running the pass needs none of it, yet every reader of the code pays for it; `queue-pull-notes.md` holds it for whoever changes a pass's position or posture |
| A pass that fails closed on an unreadable input while the queue-order write-back still runs | The persisted blob records the hold as a verdict, so a later cache hit replays it with no `Warning:` line. Set a `state.*` flag in the pass, return early on it in `runWriteBack`, and mirror the skip in the fence's write-back block (#5309 `nativeUnreadable`, #5310 `depFreshFailed`, #5311 `depUnreadable`, #5315 `labelsSkipped`) |
| Appending an existing reason from a second writer outside its `PASSES` row, under the original report line | The report names the first writer's cause for an unrelated one: #5315's non-array-labels eligibility screen writes `malformed-blocker`, and its report line named a blocker declaration until review (81e96e01b). Give the entry its own `detail.cause`, branch the report line on that cause, gate the append on the owning id's omit (`blocker-landing`), and name the second writer in the fence bullet |
