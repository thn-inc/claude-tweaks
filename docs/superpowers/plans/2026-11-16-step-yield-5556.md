# Step Yield File Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every closed pipeline run gets `step-yield.json` beside `timing.json`: per phase, what it cost and what it produced, including review findings by outcome and the minutes each question waited.

**Architecture:** One pure-ish function, `deriveStepYield(runDir, opts)` in `plugin/bin/lib/timing/step-yield.js`, reads only the run directory (plus question ask times handed in from the transcript read the token pass already does), attributes every decision line, event and question to a phase through one exported helper of `derive.js` (`phaseAt`), and counts. Log-line patterns live in readers it imports: `parseEntry` (append.js), `parseTiebreakLine` (console/resolve.js), a new `pair-lines.js` reader for the review pair-line templates, and `decisions-classifier.js` (status vocabulary, lenient time, structural lines). `at-close.js` writes the file on every close outcome under the same never-fail rule as `timing.json`. `tools/step-yield-report.js` runs the same function over an archive and replaces `tools/replay-scratch/review-yield.js`.

**Tech Stack:** Node 18+ CommonJS, `node --test`, no dependencies.

**Spec:** `.claude-tweaks/pipelines/2026-11-16T072116-record-5556/work/5556-spec.md`

Scope keywords: step-yield, review-yield, stepYield

## Global Constraints

- File name `step-yield.json`, exported as a constant `STEP_YIELD_FILE` from `step-yield.js`; `steps` is an array in phase order (the order `derivePhases` returns, keeping only phases with a span).
- `schemaVersion: 1`. A field is added, never renamed, without a `schemaVersion` change and a note in `docs/reference/step-yield.md`.
- No model turn. Reads `timing.json` (when present), `decisions.md` (and each `spec-*/decisions.md` under it), `events.jsonl`, `run-state.json`; nothing else outside the run dir except transcripts the timing writer already resolves.
- A cost field with no source is `null`, never `0`. Cost fields = `tokens` and `agents` (transcript-derived); `minutes`/`ownMinutes` come from `derivePhases` spans and are always numbers (document this in `step-yield.md`).
- Nothing dropped silently: an unrecognised decision-file line or malformed event is counted under its step's `unparsed` (`{ count, samples }`, samples ≤ 5, each the raw line truncated to 200 chars); a line whose time cannot be placed goes to the top-level `unattributed` bucket, which has the same shape as a step's produced counts.
- The yield module holds no regex for a log line (AC3). Patterns live in `append.js` (`parseEntry`), `console/resolve.js` (`parseTiebreakLine`), `timing/pair-lines.js`, `calibration/decisions-classifier.js`.
- Status keys come from one named list, `DECISION_STATUSES`, defined once in `plugin/bin/lib/log-decision/append.js` as `[...STATUSES, 'FAILED']` (`STATUSES` stays the writer's set: `log-decision.js` never writes `FAILED`, a read-only historical status) and re-exported by `decisions-classifier.js`, whose `KIND_RE` is built from it — so the read vocabulary has one source. Every step's `decisions` object carries every status key (0 when none).
- Close never fails or stalls on the yield: written inside `at-close.js`'s existing bound, a failure logs exactly one `SKIP` line (via `log-decision/timing-skip.js`), the file is written whole each close (temp file then rename), no existing file takes precedence.
- Do not edit `plugin/skills/review/step3-lens-dispatch.md` (49,090 B vs 52,500 B rail). Pair-line patterns are additive: a reworded template adds a pattern, never replaces one.
- Leave `tools/efficiency-report.js` unchanged. Do not route the write through `plugin/bin/write-run-artifact.js`.
- `plugin/bin/**` code: no bare `fs.existsSync`/`fs.realpathSync` (path-guard scan) — use `lstatType` from `plugin/bin/lib/path-guard`; any `spawn`/`execFile` passes `windowsHide: true`.
- Decision-line times are local `HH:MM:SS` (`append.js`'s `hms` uses `getHours`); event `ts` is ISO UTC. Reconstruct a line's instant in the reading process's local timezone within the run window (`run-timing.js`'s `runWindow`); this assumes reader TZ = writer TZ — state that limit in `step-yield.md`.
- Commit messages: `{Verb} {what} — {detail}`, body `refs #5556`, trailer `Claude-Session: https://claude.ai/code/session_01UwjosFEytZUCL5KGeiTpPJ`.
- Governing-skill rules: see the section "Governing skills" at the end of this plan (verbatim quotes; every task's implementer must read it).

## Decisions taken under the spec's decision rule (state each in the PR body)

1. **Question ask time source: the transcript's `AskUserQuestion` tool_use row**, not a new PreToolUse event — no new hook surface, and `transcript.js`/`post-tool-use.js` are Key Files while `pre-tool-use.js` is not. The transcript-reading timing derivation persists the pairs as a new top-level `questions` array in `timing.json` (written whenever tokens are derived, `[]` when the transcript held none), so every later close — including one that keeps an existing `timing.json` — re-derives the yield's wait times from the run directory alone. The PostToolUse `ask-user-question` event gains `toolUseId` (from the hook input's `tool_use_id`) for an exact join on new runs; older events join by question text, then not at all (`waitedMinutes: null`). Limit: a run whose `timing.json` has no `questions` key (no transcript read yet, transcript gone, or written before this change) has `waitedMinutes: null`; the archive path's synchronous write gets the wait times once the background token pass writes `timing.json`.
2. **The write lives in `at-close.js`** (not a Key File): it is the one module every closing path already calls (close-run, teardown-run, archive's sync write, the background token pass), so one call site covers all four, and `hooks.js`/`archive-merged.js`/`close-run-state.js`/`teardown-run.js` need no change. Putting it there keeps the rule in code once (decision rule order 2 over 3).
3. **Pair-line counters per form** (written once in `pair-lines.js` and in `step-yield.md`):

| Form (`pair-lines.js` id) | Template head | both | one | relabel |
|---|---|---|---|---|
| `reproduced` | `… finding {path}:{line} reproduced. Confirmed.` | +1 | 0 | 0 |
| `reproduced-severity-contested` | `… reproduced, severity contested (took the lower of the two). Confirmed.` | +1 | 0 | 0 |
| `not-reproduced` | `… not reproduced. Staged to Review Console as low-confidence.` | 0 | +1 | 0 |
| `absence-refuted` | `… absence claim {path}:{symbol} refuted by ground-truth check (…). Not staged.` | 0 | +1 | 0 |
| `vacuity-downgraded` | `lens "3f" vacuity finding … downgraded to unconfirmed …` | 0 | 0 | +1 |
| `vacuity-reconfirmed` | `lens "3f" vacuity finding … re-confirmed by executed run: …` | 0 | +1 | 0 |
| `coincidence` | `… findings {path}:{lineA} / {path}:{lineB} share a location but not substance; both staged unconfirmed.` | 0 | +2 | 0 |

   `raised = both + one`. A relabel adds to no finding count. The six spec forms are these rows with `reproduced-severity-contested` folded into `reproduced` ("a `reproduced` line (severity contested included)"). `vacuity-reconfirmed` counts one=+1 because the spec says so in as many words — "the other forms count findings one reviewer reported, except a vacuity downgrade, which relabels a finding already counted and adds none" — settled at plan review (spec `## Plan Review Clarifications`); `step-yield.md` notes that a finding that was reproduced, downgraded and then re-confirmed therefore counts in both `both` and `one`.
4. **Tiebreak verdict/outcome from `parseTiebreakLine` kinds:** `confirmed` → verdict `confirmed`, outcome `confirmed`; `dropped` → verdict `refuted`, outcome `drop`; `console`/`digested` → outcome `console`/`digest`, verdict `cant-tell` when `reason === 'verdict:cant-tell'`, else verdict `unsettled` (the judge's verdict is not on the line). A review-marked line containing the literal token `judge: none` (#5541, `JUDGE_NONE` in `pair-lines.js`) counts outcome `none` — checked **before** `parseTiebreakLine`, so it counts even when that parser rejects the line's shape (a #5541 no-judge line may carry no evidence); its verdict is the parsed one when `parseTiebreakLine` accepts it, else `unsettled`. Whether or not #5541 has landed. `byVerdict` keys: `confirmed, refuted, cant-tell, unsettled`; `byOutcome` keys: `confirmed, drop, digest, console, none`.
5. **Review counters live on whichever step the lines attribute to** (normally `review`), as that step's `findings` object; absent (`null`) on a step with no pair/tiebreak line. A line mentioning `Reproduction:` or `Tiebreak tiebreak:` that no reader matches counts as `unparsed` in its step.
6. **Multi-record runs:** the parent's yield reads the parent `decisions.md` and every `spec-*/decisions.md`; a `spec-N` child gets no yield file (same rule as `timing.json`, `isSpecChildDir`).
7. **Events:** every well-formed event (object with string `type` and parseable `ts`) counts in its step's `events` map by type; a malformed JSON line or an event without a parseable `ts` counts in the top-level `unparsed`.

## Review Focus

1. A decision line written just before local midnight in a run that crosses midnight — its instant must land on the right day (Task 4 test `crossesMidnight`).
2. A run with no `events.jsonl` at all, or an empty one — `steps: []`, every decision line in `unattributed`, no throw (Task 4 test `noEvents`).
3. A `decisions.md` holding the Manifesto's `Pipeline config snapshot:` block and `- key: value` bullets — structural, never `unparsed` (Task 1 test `structural`).
4. An `ask-user-question` event whose transcript has two asks with identical question text — the join must not reuse one ask for two events (Task 3 test `duplicateQuestionText`).
5. A yield write racing an archive that moves the run dir — never recreates the dir; the write follows `at-close.js`'s archive-twin rule or logs one SKIP (Task 5 test `vanishedDir`).

  Object shape:
  ```
  { schemaVersion, runDir, generatedAt,
    sources: { timing: bool, decisions: bool, events: bool, runState: bool, questions: 'timing.json'|null },
    steps: [ { phase, start, end, minutes, ownMinutes,
               tokens: {input,output,cacheRead,cacheCreate}|null, agents: number|null,
               commits: {<action>: n}, verify: { runs, pass, fail, unknown },
               decisions: {<status>: n},
               events: {<type>: n},
               questions: [ { question, askedAt|null, answeredAt, waitedMinutes|null, askSource: 'toolUseId'|'questionText'|null } ],
               findings: null | { raised, both, one, relabeled,
                                  tiebreak: { byVerdict: {...}, byOutcome: {...} },
                                  byLens: { <lens>: { raised, both, one, relabeled, tiebreak: {byVerdict, byOutcome} } } },
               unparsed: { count, samples } } ],
    unattributed: { commits, verify, decisions, events, questions, findings, unparsed },
    unparsed: { count, samples } }
  ```
  `tokens`/`agents` from the matching `timing.json` phase row (`tokens`, `subagents`) only when `hasTokenTotals(timing)`; else `null`. `verify` from the `derivePhases` row's `verify[]` (`pass === true` → pass, `false` → fail, else unknown). `commits` from `commit` events by `action`. A question's step: `phaseAt` of its ask time, else of its answer time (the event `ts`). `waitedMinutes` = `(answer − ask) / 60000` rounded to one decimal; `null` when the ask time is unknown or the question has no answer.
  Line instant: `parseEntry` first, else `entryClock`; an ISO clock is used as-is; a local clock is placed on the local calendar day that puts it inside `runWindow(runDir, events, runState)` widened by 10 minutes each side, earliest such day when several qualify; no qualifying day, no window, or a window open on either side (`runWindow` returns `-Infinity`/`Infinity` for a side with no source) → `unattributed`. Lines are not assumed to be in time order (`placeEntry` inserts under section headings).
  Line classification order: `isStructuralLine` → skip uncounted; `classifyDecisionLine(line).kind !== 'other'` → count status, then if `isReviewMarkedLine`: a line containing `JUDGE_NONE` → tiebreak counters with outcome `none` (verdict from `parseTiebreakLine` when it accepts the line, else `unsettled`); else `parseTiebreakLine` → tiebreak counters; else `classifyPairLine` → pair counters; else `unparsed`; any other line → `unparsed`.

## Governing skills

**run-directory-fact-packs** (Tasks 4, 5)
> - **Write atomically** (`lib/atomic-write.js`), because a consumer may be reading the previous pack while this one is written.
> - **Multi-spec per-spec dirs.** A `{parent-run-id}/spec-{N}/` dir carries its own `status`, but the run's shared `worktree` and `pr` stamps live on the **parent** run dir, because run-dir enumeration is top-level only (`context.js` `iterRunDirsWithState`).
> - **A stamp the close clears.** `closeRunState` nulls `worktree` and keeps the prior path as `worktreeAtClose` (#3023).
> - **Absence is ENOENT, not a null read.** A helper that returns null on any read error (`pack.js`'s `readText`) cannot answer "does this file exist": an unreadable file reads as missing.
> A field failing any of the three is not a pack field. Plan and code will agree with each other regardless — the defect surfaces only when the pack is run against a real run directory, so run it against one before the review does.

Applied: `writeStepYield` writes temp-then-rename; a `decisions.md`/`timing.json` read distinguishes ENOENT (source absent → `sources.x: false`) from other read errors (counted in top-level `unparsed` with the error code as the sample, never read as absent); Task 4 Step 6 runs it on a real archived run.
