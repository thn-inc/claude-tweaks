# Lens Reviewer Worker Role and Launcher Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Run review lens briefs as lean, read-only headless `claude -p` workers through the driver's existing launcher, in the reviewed worktree, returning exactly the reply shape `review-coordination.js settle-lens-replies` already reads, with every worker's tokens counted in the run's `timing.json`.

**Architecture:** A new `lens-reviewer` role in `plugin/bin/lib/driver/roles.js` (Read, plus Grep/Glob and a closed set of pinned read-only git rules only on `SANDBOX_PROBED_PLATFORMS`, under the sandbox block) whose settings come from a new `lensReviewerSettings` builder, selected in `worker.js` through one `settingsFor(role, opts)` dispatcher; the same module derives the fixed admitted-forms note from the role's own allow rules. A library `plugin/bin/lib/driver/lens-workers.js` validates the workflow script's input, launches one worker per side through `launchWorker` with `cwd` = the reviewed worktree, the context bundle inlined ahead of the brief on stdin, the admitted-forms note as `--append-system-prompt-file`, the lens's model and the role's effort from `roleLaunch('lens-reviewer', policy)`; it maps each envelope to `{lens, side, text, failed}` and appends one dispatch record per worker to `{run}/worker-dispatches.jsonl`. The thin CLI `plugin/bin/review-lens-workers.js` wraps it. `timing/transcript.js` gains a reader for that file and `timing/run-timing.js` merges its items into `timing.json` `dispatches`.

**Tech Stack:** Node 18+ CommonJS, `node --test`, Claude Code CLI `claude -p` (headless), git.

**Spec:** `.claude-tweaks/pipelines/2026-11-23T152543-record-6000/work/6000-spec.md` (record #6000; supersedes the `2026-11-23T062258` copy)

**Scope keywords:** lens-reviewer, review-lens-workers, worker-dispatches

## Global Constraints

- Spec, Deliverable 1 (verbatim): "No Write, no Edit, no network. On a platform outside `SANDBOX_PROBED_PLATFORMS` the role has no Bash, so a lens brief that needs `git show` or `git log` cannot run there: the launcher marks that side `failed: true` with the reason `platform`, and the dispatcher falls back to the Task path (never an empty review)."
- Spec, Deliverable 1 (verbatim): "The probe covers repository-config-driven program starts as well as flags: textconv and external diff via `.gitattributes`, `core.pager`, `core.fsmonitor`, `-c` and `GIT_*` environment, `git grep --open-files-in-pager`, with `--no-ext-diff` and `--no-textconv` pinned where the probe needs them; the role header says that widening the allow list means re-probing."
- Spec, Deliverable 2 (verbatim): "A worker that fails, times out or returns blank text is `text: null, failed: true` with a `reason` (`launch`, `auth`, `timeout`, `blank`, `platform`) on stderr and in the launcher's log, not in the reply shape; a model reply of \"No findings.\" is a valid reply, never `blank`; one worker's failure never touches another's reply. The launcher's exit code is 0 when it printed the reply shape, and 2 on a malformed call."
- Spec, Deliverable 4 (verbatim): "The launcher rejects a lens `3f` entry before any worker starts: that side returns `failed: true` with `reason: excluded`, pinned by a unit test."
- Spec, Decision Q1 (verbatim): "The worker runs in the reviewed worktree, so relative paths, `git grep` and an unranged `git diff`/`git show` all see the reviewed branch. The launcher inlines the context bundle in the prompt rather than copying it into the worktree, so the reviewed tree is never written to."
- Spec, Decision Q2 (verbatim): "The launcher appends one fixed system-prompt note (`--append-system-prompt-file`) listing the exact admitted command forms and telling the worker to run them as written. Because a refused read could still end in \"No findings.\", a worker whose envelope records a git permission denial is `failed: true` with reason `denied` (added to Deliverable 2's reason list), so the dispatcher falls back instead of counting an empty review."
- Spec, Decision Q3 (verbatim): "The effort comes from `roleLaunch('lens-reviewer', policy)`, the role's own `DRIVER_ROLE_PROFILES` row, and a test pins that row. No per-lens effort helper."
- Spec, Gotcha (verbatim): "A lens brief embeds untrusted diff text; the worker's rights, not the prompt, are what contain it. The `auth` flag here means the worker's launch credentials and rights: no credential beyond what `claude -p` needs reaches the generated settings, and no network is granted."
- Spec, Gotcha (verbatim): "Headless worker authentication on env-authenticated hosts is undecided (#5259); the launcher must report a launch failure as a failure, never as an empty review."
- The full failure-reason set is `launch`, `auth`, `timeout`, `blank`, `platform`, `excluded`, `denied`. A reason never enters the reply object.
- The reply `side` labels are exactly `A` and `B` (side A only for `reviewers: 1`), as `plugin/workflows/review-lens-fanout.js` labels them; the dispatch-record `description` is `lens {lens} {side}`, the workflow agent label, so `derive.js`'s `ROLE_PATTERNS` books it as `lens reviewer`.
- Lens token class: `/^[A-Za-z0-9_-]+$/`, the same class `review-lens-fanout.js` and `settle-lens-replies` read.
- Existing roles keep byte-identical argv and settings (spec Key Files: "`worker.js` — reuse the launcher; no behaviour change for existing roles").
- Commit subjects: `{Verb} {what} — {detail}`, every one carrying `refs #6000`; never `closes`/`fixes`.

## Review Focus

1. Lens briefs whose model says "No findings." — must stay a valid reply (`failed: false`), never `blank`, unless the envelope carries a permission denial (Task 3 tests `blank: … "No findings." is a reply` and `AC9.1`).
2. A lens file naming `3f` among other lenses — only 3f's sides fail `excluded`; the others launch (Task 3 test).
3. The CLI killed mid-run (SIGINT/SIGTERM) — running workers are signalled, never orphaned (Task 3 test `forwards termination to every running worker`).
4. A reviewed worktree that is a linked worktree (its git common dir outside `cwd`) — git reads must still work under `blockReadsOutsideWorkingDirectories` and the sandbox read block (Task 2 vector 13, Task 3 test `readPaths carries the git common dir`).
5. A run dir that already has a `worker-dispatches.jsonl` from an earlier review round — records append; `timing.json` counts both rounds (Task 4 test `two launcher runs append`).
