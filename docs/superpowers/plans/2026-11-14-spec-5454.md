# Driver Test-Step Tree Check Implementation Plan

**Goal:** After a green or verdict-less `verify.js` run, the test step reads the worktree. It stops the record with status `fail` when a tracked path differs from HEAD or an untracked file has appeared, so a green verdict is not reported for bytes the commit does not hold. A red run keeps its existing `failing-test` stop.

**Architecture:** `testStep` (`plugin/bin/lib/driver/steps.js`) gains one more read after its existing index-flag re-check and its red-tests branch. A new helper, `testTreeStop(ctx, deps)`, calls `review.js`'s already-exported `treeDelta` with an empty expectation and with `steps.js`'s own `isRunArtifact`. That is the same read and the same exclusion the commit step uses. A non-empty delta, or a read that throws, is a `fail` ahead of a green verdict (`r.code === 0`) and ahead of every verdict-less exit (`r.code` null, or any non-zero other than 1). The review fix round already re-runs `testStep` through its wiring, so its scoped run is covered. The only `review.js` change is two stale comments.

**Tech Stack:** Node 20 CommonJS, `node --test`, the fake-runner harness in `tests/bin-lib/driver/run.test.js` (`harness`, `defaultScript`, `fixRig`, `withRealRepo`).

**Spec:** `.claude-tweaks/pipelines/2026-11-14T213352-spec-5454/work/5454-spec.md` (record #5454)

Scope keywords: testStep, treeDelta, isRunArtifact, newIndexFlagStop, BASE_CALLS_PLAIN, fixRound

## Design decisions (settled from the code)

**1. The excluded paths are exactly what `isRunArtifact` names: `.claude-tweaks/pipelines` and everything under it** (`steps.js:632-636`). These are the paths the commit step also skips (`steps.js:648`, `steps.js:655`), and the review step's tree checks skip the same ones through the wiring (`review.js:665`, `steps.js:1126`). The exclusion applies to tracked and untracked paths alike, as it does in the commit step (plan review, Reading B). Nothing else the driver or `verify.js` writes during or after `testStep` lands in the worktree's tree:
- The run directory is minted with `cwd: mainRoot` (`steps.js:325`), and `resolveRunDir` roots it at `{mainRoot}/.claude-tweaks/pipelines` (`plugin/bin/lib/hooks/run-dir-resolve.js:236`). The worktree is `{mainRoot}/.claude/worktrees/drive-record-{n}` (`steps.js:392`), so the run directory is outside it. Everything the test step itself writes is under the run directory: `gh-config-empty` (`steps.js:778-779`). So are the worker settings (`steps.js:562`), `commit-msg.txt` (`steps.js:662`) and `record.json` (`steps.js:813`).
- `verify.js` writes its logs, its JSON report and the impact file list under `logDir`, which defaults to the checkout's own git dir (`verify.js:518-521`, `verify.js:550`, `verify.js:761`). It also writes the count stamp there (`verify.js:551`), and the pass stamp through `writeStamp(gitDir, …)` (`verify.js:1515`, `plugin/bin/lib/verify/stamp.js:76-80`). A linked worktree's git dir is `{main}/.git/worktrees/{name}`, not part of the tree. Its verify events go to `--run` (`verify.js:1000-1001`, `verify.js:1359-1362`), the run directory again.
- Probed while authoring with real git (scratch repo, read-only for this repo): `treeDelta` returned `[]` for a clean tree and for a tree whose only change was an untracked `.claude-tweaks/pipelines/r/events.jsonl`, and `["a.js","new.txt"]` once a tracked `a.js` was modified and `new.txt` created. Raw status: `" M a.js\0?? .claude-tweaks/pipelines/r/events.jsonl\0?? new.txt\0"`.
- `isRunArtifact` is kept as it is. The exclusion is the existing constant, never a second list.
- Stated residual: a tracked file under `.claude-tweaks/pipelines/` that a test rewrites passes the check. The commit step never stages it either, so the commit and the verdict agree on skipping it. CI on push is the backstop.
- Stated residual: the status read has no `--ignored` (`review.js:659`), so ignored files never count.
- Task 2's docs bullet states both residuals.

**2. Reuse `review.js`'s `treeDelta`, already exported** (`review.js:658-672`, export at `review.js:1190`). With `expected = new Set()` it returns every reported path outside `isRunArtifact`'s paths, both sides of a rename, deduplicated, in status order. It throws on a git failure or a record `parseStatusPorcelainZ` cannot parse in strict mode. Its argv is `['-C', wt, '--no-optional-locks', 'status', '--porcelain', '-z', '--untracked-files=all']` with `{ cwd: wt }`, the same call `gitIn` makes for the commit step (`steps.js:345-347`, `steps.js:648`). `steps.js` already requires `./review` (`steps.js:81`). That import has no cycle, because `review.js` never requires `steps.js` (`review.js:218-230`). The path list in the detail reuses `newIndexFlagStop`'s formatting (`steps.js:534-535`). It is factored into one helper both stops call, with the flag stop's bytes unchanged (`AC7.1 (#5415)` pins them, `run.test.js:1817-1835`). A copy of `treeDelta` or of the commit step's loop is not written.

**3. Order: `verify.js`, then the index-flag re-check, then the red-tests branch, then the tree check, then the verdict-less branches, then green** (plan review, Reading B).
- The flag check is the existing one at `steps.js:782-784`. It keeps its position and precedence: it still runs first and still wins over everything after it, a red run included (`AC2.1 (#5415)`, `run.test.js:1758-1770`, unchanged).
- The red-tests branch (`r.code === 1`, today at `steps.js:791`) moves up, to directly after the flag check, with its result unchanged: `{ status: 'stop', reason: 'failing-test', detail: 'red tests' }`. A red run therefore makes no status read and keeps its existing `stop`/`failing-test` outcome, a changed tree or not. Red tests already stop the record and push nothing, so the tree read would add nothing.
- The tree check goes next. It gates only the two verdicts that let the record go on, or that never judged anything:
  - a green run (`r.code === 0`);
  - a verdict-less run, unfinished (`r.code` null or undefined, `steps.js:786-788`) or with any exit other than 0 and 1 (usage or infrastructure, `steps.js:792`).
- The verdict-less branches and the green return follow, unchanged.
- When the flag and the tree would both fire, the flag stop wins and the tree is not read. A newly flagged path is one git status cannot report, so a tree read after it is not evidence. The review step already uses this flag-then-tree order after an evidence run (`review.js:911-914`, `review.js:1104-1108`), and Global Constraints quotes it from `driver-step-addition`.
- A test step that refuses its scope file returns before `verify.js` and reads nothing (`steps.js:743-762`, `steps.js:775`).

**4. AC2's call-count pins.** Three existing tests pin the plain happy path's recorded calls:
- `AC2.1: happy path calls run in the deliverable order` (`run.test.js:3076-3108`) pins the literal signature. It gains one `'git status'` entry between `'git ls-files'` and `'node express-lane.js check'` at `run.test.js:3102`. That literal is the spec's "differ from before only by the one added status read".
- `AC8.1 (#5415): the happy path reads core.ignoreStat once …` (`run.test.js:1931`, `run.test.js:1961`) and `AC7.1 (#5414): the happy path adds exactly one HEAD read …` (`run.test.js:2105`, `run.test.js:2117`) compare with the literals captured before #5414 (`BASE_CALLS_PLAIN`/`BASE_CALLS_FIX`, `run.test.js:2020-2061`). Each filter chain moves to one helper, `baselineCalls`, which also drops the new read. The driver-step-addition rule quoted below calls for this: "A later check that reads at the same points filters its own reads first".
- The fix-round signature `AC8: one fix round, in order` (`run.test.js:3507-3514`) gains one `'git status'` after the fix round's `'node verify.js'`.
- A new `AC2.1 (#5454)` test pins the count and position, and that `BASE_LINES_*`/`BASE_KEYS_*` are unchanged.
- Red-run recheck (Reading B). Every pinned run above has green `verify.js` runs: the plain harness has one, and `fixRig` has two. Both use the default `{ code: 0 }` reply (`run.test.js:431`), so each gains exactly one read per `verify.js` call and the counts above stand. The tests whose `verify.js` run is red gain no status read. Their call patterns and outcomes are unchanged, and their edits stay none:
  - `AC6.2: red tests stop at test`;
  - the `red tests` scenario;
  - `verify exit 1 is the red-tests stop; …` (its code-1 case);
  - `AC2.1 (#5415)`'s red case, where the flag wins before the red branch;
  - `AC10`'s `verify.js exit 1` row (`run.test.js:3580`, still `fix round test: red tests`);
  - `AC8.1 (#5370)`'s exit-3 case, which is verdict-less: on the clean default tree it reads the tree, finds nothing, and keeps its detail.
- No test pins a call count on a red run.

## Global Constraints

- **Exact strings** (constants in `steps.js`; tests use the literals):
  - `TEST_TREE_UNREADABLE = 'the worktree status is unreadable after the test step'`. No git stderr, no path.
  - Changed tree: `` `the worktree differs from HEAD after the test step on ${n} path(s): ${namedPaths(changed)}` ``. `n` is `changed.length`, the full count.
  - `namedPaths(paths)`: the first `INDEX_FLAG_PATHS_SHOWN` (5) paths, each through `neutralize`, joined with `', '`, then `` `, and ${paths.length - INDEX_FLAG_PATHS_SHOWN} more` `` when there are more. This is exactly the formula at `steps.js:534-535`.
  - Inside the fix round, the stop arrives through the existing `propagate('test', …)` (`review.js:1086`) as `` `fix round test: ${detail}: ${FINDING}` ``. The step result keeps status `fail`, class `pre-push` and reason `fail`, and the final line's `stop.reason` reads `express-error`, through `toEscalationReason`, as for every pre-push `fail`.
- **No new stop class, reason, event field or STEP name.** The stop is the `test` step's own `pre-push` `fail`, which `toEscalationReason` maps to `express-error`. `run.js`, `events.js` and `settle.js` are untouched: the tree check is a read, not a side effect, so it gets no `newCtx` flag and no `interruptClass` rung (`driver-step-addition`: "Needed only for a new durable side effect.").
- **Never write to the tree.** The driver never cleans, stashes or reverts what the tests changed. The settle unit owns the worktree after a stop.
- **Windows:** the real-git test asserts paths git prints (`a.js`, `new.txt`, at the repo root, so no separator). Per `windows-checkout-test-parity`, CI runs on ubuntu only, so dispatch the Windows workflow after the last code change and before merge.
- **Verification shape:** per task, run the named files with `node --test`. The full suite runs centrally at the pipeline's `/test`, never inside a task.
- Governing skill `driver-step-addition`, quoted verbatim:
  - "The worker can shape strings such as its summary, a path it named, or CLI stderr that may echo either. Each such string goes through `events.js`'s `neutralize` before it reaches an event `detail`, a commit message, a PR body or a log line (AC14.3)."
  - "Propagate a re-run step's own status and class unchanged, and list each re-run step's stops in the new module's header."
  - "An interrupt during the launch is still reported as the interrupt (run.js's handler writes it at once; see "Interrupts at await points"). At an evidence run the order is the interrupt, then the flag check, then the tree check."
  - "Pin each new read's position and leave the rest of the run as it was. Capture the happy path's call signatures, event `[step, status]` pairs and per-line key sets on the unmodified code as literal constants (`BASE_CALLS_PLAIN`, `BASE_CALLS_FIX`, `BASE_LINES_*`, `BASE_KEYS_*` in `run.test.js`). Then assert the new run equals them with the new reads filtered out, and that a read sits right before and right after each launch. Fault the n-th read with `nthCall(isHeadRead, n, reply)`. A later check that reads at the same points filters its own reads first (`withoutFlagReads`) and pins their count and order in its own test, as `AC8.1 (#5415)` does over #5414's captures."
  - Site row: "`tests/bin-lib/driver/run.test.js` | A happy-path reply in `defaultScript` for every call the step makes, because the harness throws `unexpected {kind} …` on anything else. A new gh-shaped dep kind joins the kind list in `dispatch` that refuses `pr merge` and `pr ready` (AC8). Add a `SCENARIOS` entry and a row in `AC7.1, AC7.7: outcome and stop class for every stop (table-driven)` for each new stop." The default status reply already answers the new read (`run.test.js:424`). The scenario added below is stateless (a constant reply), so the single-use `nthCall` problem `#5415` avoided does not arise.
- Governing skill `headless-worker-launch`, quoted verbatim: "Treat the worker's index flags and git config as untrusted (#5267)." and "CI on push stays the backstop for what this cannot see: a `.gitattributes` filter, `core.fsmonitor`, and a path already flagged when the worktree is created." The tree check inherits those residuals. It adds three more:

## Review Focus

1. A red `verify.js` run that also changed the tree must keep its `stop`/`failing-test` outcome and make no status read. An unfinished or verdict-less run (exit null, 2, 3) that changed the tree must stop on the tree (`fail`, the tree detail), not on its own verdict-less detail. Task 1 test `(#5454) a red run keeps its failing-test stop and reads no tree; an unfinished or verdict-less run that changed the tree stops on the tree`.
2. A run that both set a new index flag and changed the tree must report the flag and make no tree read. Task 1 test `(#5454) a new flag and a changed tree from the same run: the flag stop wins and the tree is not read`.
3. Some paths only look like ones the commit step skips (`.claude-tweaks/pipelines-old.txt`, `.claude-tweaks/verify-scope.json`), and they must stop the record. A path under `.claude-tweaks/pipelines/` must not, untracked or modified (the stated residual). Task 1 test `(#5454) an untracked file stops the same way; the paths the commit step skips never do`.
4. A fix-round scoped run that changes the tree must stop at the propagated test result, and the kept evidence file must never run. Today the later kept-run tree check catches it under a different detail. Task 1 test `(#5454) a fix-round scoped run that changes the tree stops at the propagated test result`.
5. A rename counts both sides, and more than five paths name five plus `and N more`, with `n` the full count. Task 1 test `AC4.1 (#5454): changed paths reach the detail neutralized, at most five plus the count`.
