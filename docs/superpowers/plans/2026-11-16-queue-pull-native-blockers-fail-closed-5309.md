# Queue pull: one failed native-blockers GraphQL call disables both the blocked and unlanded-blocker passes (#5309) Implementation Plan

**Goal:** A failed native-blockers GraphQL call (`bin/resolve-blockers.js`, one aliased call for every eligible candidate) fails closed for the records it could not read, with one Warning, instead of silently disabling the `blocked` pass's native filtering and, through `preflight-records.js`'s own native read, the `unlanded-blocker` pass.

**Spec:** `.claude-tweaks/pipelines/2026-11-15T162121-spec-5304-5305-5306-5307-5309-5310-5311-5312-5313-5314-5315-5316-5317-5409/spec-5309/work/5309-spec.md` (materialized from GitHub issue #5309)

**User decision (plan review, 2026-11-16, Reading B — recorded in the spec).** Fail closed **only on a real native-blockers query failure**: `resolve-blockers.js` exit 3, or any non-zero exit when the pull runs on `--transport gh`. A failure that is only `gh` being absent (exit 2 on `--transport files`, the normal result under `work-links: native` on an MCP/Routine drain) keeps today's gh-absent fallback and its existing Warning text byte-for-byte, so a gh-absent drain keeps dispatching. The files-transport matrix base and its fault rows, the gh-absent sections of `mcp-transport.md` (line ~175) and `queue-pull-notes.md` (line ~13) are **not** rewritten. Everything below applies to the fail-closed branch only.

**Decision (the build's own).** Today (`plugin/bin/lib/dispatch/queue-pull.js` `runBlocked`'s `native-deps` step, ~line 509; fence `plugin/skills/dispatch/queue-pull-script.md` lines 192-203) a non-zero `resolve-blockers.js` exit leaves `dispatch-native-deps.json` as `{}` and prints `Warning: native dependency query failed — falling back to no native filtering this run: …`; every candidate then stays in `dispatch-groups.json`, the unlanded-blocker pass's `dispatch-unlanded-blockers.js` → `preflight-records.js --work-links native` call hits the same failing GraphQL and prints a second Warning (`LANDING_EXITED`), and the write-back persists the unfiltered groups as a cache verdict that later cache hits replay without re-querying. Fix, in both the module and the fence (the fence still exists — #5231 has not removed it — so the parity row is kept):

1. `resolve-blockers.js` batches every number into one call, so a failure leaves **every queried record** (the `NATIVE_NUMS` set, i.e. every record in `dispatch-eligible.json`) with unreadable native blockers. Each one is excluded under the existing `reason: 'blocked'` with `detail: { blockedBy: ['native blockers (state unreadable)'] }` — a string entry, which `plugin/skills/dispatch/blocked-exclusion-report.md` already renders verbatim, and which `queue-order.js`'s `namesForeignBlocker` does not read as a foreign ref. No new exclusion reason (so `dispatch-queue-exclusion-addition`'s registration sites are not touched).
2. The one Warning replaces the old text: it names the call and the fail-closed consequence, e.g. `Warning: native dependency query failed — every candidate excluded as blocked (native blockers unreadable, fail closed) this run: {stderr}`. Module and fence print the identical bytes.
3. With those records removed from `dispatch-groups.json`, the unlanded-blocker pass sees no candidate that needs the native read — `dispatch-unlanded-blockers.js` prints an empty pool unchanged with no call and no Warning — so the pass is no longer disabled and no second Warning prints. Confirm this on the F-native fault row, do not assume it.
4. The write-back (module `runWriteBack`'s `write-back` step; fence lines ~276-302) writes nothing on a pull whose native query failed, so a failed read is never persisted as a queue-order verdict a later cache hit would replay without re-querying.

Mechanism (how the failure reaches the grouping block, e.g. a marker in `dispatch-native-deps.json` or a state flag) is the implementer's choice, provided module and fence behave identically on every matrix and fault row. The failure marker is set on **every non-success path on `--transport gh`** (any non-zero exit, a null status, a thrown error inside the `native-deps` step), and **only on exit 3 on `--transport files`** — on files, exit 2, exit 1, a null status or a throw keep today's fallback and its old Warning (spec's Plan Review Clarifications). A throw is caught inside the `native-deps` step itself, so it prints only the one Warning (fail-closed text on gh, fallback text on files) with `{stderr}` set to the error message, never also `step()`'s `queue-pull: native-deps: …` line.

**Transport discriminator, both sides.** The module branches on `ctx.options.transport`; the fence has no transport variable today. Before writing the fence branch, read how the parity harness in `queue-pull.test.js` models `--transport files` for the fence (e.g. `gh` absent from PATH, or an env var the harness sets), and key the fence on that same signal, so module and fence agree on every matrix and fault row — never on exit status alone: `resolve-blockers.js` also exits 2 on gh when owner/repo cannot be resolved (#4933), which must fail closed on gh in both.
