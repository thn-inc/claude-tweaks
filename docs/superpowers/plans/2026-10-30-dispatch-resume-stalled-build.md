# Dispatch Resume for a Stalled Build — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `/claude-tweaks:dispatch resume #N` restarts a dispatched build that stalled before the test gate, on its still-open draft PR, with no hand-run plumbing.

**Architecture:** One pure verdict module (`bin/lib/dispatch/resume-eligibility.js`) decides eligibility from the PR, claim blob, labels, prior-run-dir state and sibling liveness, and derives the resume-context block from the archived run's `decisions.md`. A thin gatherer CLI (`bin/dispatch-resume.js --issue <N>`) feeds it live inputs: it finds the PR by head branch `worktree-dispatch-record-{N}` (never from `dispatch-exclusions.json` — a `bot:in-progress` record is dropped by the queue's label pre-filter before the `open-pr` pass and has no exclusion entry), reads the record's labels and claim blob, and classifies the prior run directory archive-first. `claim-targets.js` gains a narrow `--resume-pr <url>` exception for a `'stale'` claim whose in-flight link is exactly that PR; `/flow` forwards it only when invoked with `RESUME_PR=<url>`. The dispatch procedure lives in a new lazy sub-file `dispatch/resume.md` because `dispatch/SKILL.md` has only ~1.5 KB of rail headroom.

**Tech Stack:** Node 18+ CommonJS, `node --test`, markdown skill prose.

**Spec:** `.claude-tweaks/pipelines/2026-10-30T200217-spec-4588/work/4588-spec.md` (worktree copy; refreshed 2026-10-30 with the answered eligibility rules — issuecomment-6532612775 — and 2026-10-31 with the owner-process dead-owner rule and the open-pr-only remedy criterion — issuecomment-6533615614 — and again 2026-10-31 with the third answer set — issuecomment-6540061358: dirty stalled worktree refused, the open-pr-only criterion narrowed to `plugin/skills/dispatch/`, a stateless prior run dir left to reconcile, only a proven owner death counts — and again 2026-10-31 with the fourth answer set — issuecomment-6541879941: the prior run is the one the PR marker names and a differing claim `runId` is refused as `run-mismatch`, a `swept: stale claim` tombstone is eligible, and the Closed rule: the eligible states are exhaustive, every unlisted state is refused with one line naming the state and the manual remedy)

Scope keywords: staleClaimInFlightPr, already has an open PR, claimLogText

## Global Constraints

- Run-id shape: import `RUN_ID_SHAPE` from `plugin/bin/lib/issues/claim-store.js` — never a new regex literal. Any prose copy of the regex must equal `RUN_ID_SHAPE.source` (`tests/issue-claims-stale-open-pr-conformance.test.js`); prefer naming the constant in prose instead of copying it.
- Resume head branch: exactly `worktree-dispatch-record-{N}`; prior run-id slug: exactly `record-{N}` — the run id matches `RUN_ID_SHAPE` **and** its slug (the id with `RUN_ID_SHAPE`'s fixed-width 18-character `YYYY-MM-DDTHHMMSS-` timestamp prefix removed, `id.slice(18)`) equals `record-{N}` by string equality. Never an ends-with test: `…-dispatch-record-12` and `…-record-120` are foreign for #12 (fourth review, low row). The PR is always found from that head branch, never from `dispatch-exclusions.json`.
- Eligible claim states (`classifyClaimBlob` for the state; the verdict parses the blob JSON itself for `reason`, `runId` and `sweptFrom`): a tombstone whose `reason` starts with `failed:` or `abandoned:`, a tombstone whose `reason` starts with `swept: stale claim` (`/tidy`'s `release-claim.js --sweep` release, issuecomment-6541879941 q2), or `'stale'`. Nothing else. `failed:`/`abandoned:`/`swept:` re-claim by the ordinary conditional write; `'stale'` re-claims through `--resume-pr`. A `swept: issue closed` tombstone is not eligible.
- Prior run identity (issuecomment-6541879941 q1): the prior run `{runId}` is the run id the PR body's `claude-tweaks-run:` marker names. The claim's run id is `sweptFrom` for a `swept:` tombstone (its `runId` is the sweeping `/tidy` run, `release-claim.js`'s header) and `runId` otherwise. When the claim's run id differs from the marker's, or the claim names none, the record is refused as `run-mismatch`, naming both run ids and the manual remedy.
- Closed rule (spec D1, issuecomment-6541879941): the eligible states are exhaustive. Every claim, label, worktree, PR or run-directory state not listed as eligible is refused with one line that names the state and a manual remedy — including a `priorRunDir` class the verdict does not know (`unlisted-state`), a stalled worktree checked out on a branch other than the PR head (`worktree-branch`), and (fifth review, applied under this rule) the record-level gates Step 2's queue enforces and resume, which skips Steps 2-3, would otherwise bypass: a closed issue (`record-closed`), an open `Blocked by` dependency, body or native (`blocked-by`), and any `bot:*` label other than `bot:in-progress` and `bot:blocked` — `bot:parked` included (`unlisted-label`); plus, for a reaped worktree, a local `{headRefName}` branch whose tip differs from the PR's `headRefOid` (`branch-diverged`) or that is already checked out in another worktree (`branch-checked-out`), both decided before the mint. A plan review that finds a further unlisted state applies this rule as a plan amendment (a refusal plus its test row), never a `needs-human` spec gap.
- Own kept worktree lock (fourth review, medium row): `findConflictingSession`'s self-exclusion (`ownedWorktreePaths`, `bin/lib/hooks/sibling-sessions.js`) reads only top-level run dirs, so when the session that dispatched the stalled build runs resume itself, its own kept lock on the stalled worktree reads as a sibling once the prior run is archived. The gatherer (Task 3) therefore calls `findConflictingSession` with an injected `listRunDirsWithState` (its existing opts seam) that returns the real listing plus one entry for the prior run — `{dir: priorRunPath, state: {sessionId, worktree: worktreeAtClose || worktree}}` from the prior run's own `run-state.json` (archive-first, the same file the owner probe reads) — added only when that `sessionId` equals the resuming session's `CLAUDE_CODE_SESSION_ID` (non-empty). The exclusion then happens inside `findConflictingSession`'s own loop, so a real sibling listed after the own kept lock is still returned (fifth review, medium row) — never a post-hoc override of the single conflict it returns. `sibling-sessions.js` is not edited.
- Concurrent resume after the bind (fifth review, high row): once step 6's `record-worktree --dispatch` binds the new run, `ownedWorktreePaths` skips `worktreePath` whatever live session holds its lock, so `check-sibling-sessions` cannot see a second resume of the same record there. Step 6a therefore runs `bin/dispatch-resume.js --issue {N} --bound-run {new run dir}` instead: it re-runs the lock check and also scans the top-level run dirs (`listRunDirsWithState` on the main root) for any dir other than `{new run dir}` — skipping this session's own ad-hoc dirs (`isAdHocRunDir` with a matching `sessionId`) — whose `run-state.json` `worktree` normalizes to `worktreePath` and whose `status` is in `NON_TERMINAL`; a hit is `concurrent-resume` (exit 3, line naming that run dir). Whichever of two concurrent resumes checks second sees the other's binding and refuses; the claim write inside call 1 stays the atomic boundary.
- Eligible labels: `auto:build` present and `bot:blocked` absent; `bot:in-progress` only together with a `'stale'` claim; no other `bot:*` label (Closed rule). Eligible record state: the issue is `OPEN` and has no open `Blocked by` dependency — body (`record.js`'s `parseDependencies`), and native (`fetchNativeDependencies`'s `openBlockerIds`) only under `work-links: native` — the same gates Step 2's queue applies (Closed rule). Resume never adds, removes or restores a grant label — a human re-grants via `/claude-tweaks:backlog refine #N`.
- Prior run directory (main checkout's `.claude-tweaks/pipelines/`, resolved as `hooks.js resolve-run-dir --root-only` resolves `$RUN_ROOT` — never cwd): `archive/{runId}` checked first. Eligible when archived, absent, present holding only a `work/` entry, or present with a dead owner. **"Dead owner" is the owner-process probe alone, and only a proven death counts** (spec D1, decided 2026-10-31 on issuecomment-6533615614 q1 and issuecomment-6540061358 q4): no `run-state.json`, a `run-state.json` with no `owner` block, an `owner.sessionId` equal to the resuming session's own `CLAUDE_CODE_SESSION_ID`, or `probeOwnerPid(owner, DEFAULT_PROBES)` (`bin/lib/run-liveness/owner-pid-probe.js`, `probes.js`) returning `negative` with detail `gone`, `pid-reused` or `no-pid`. Any other probe answer is not a death: `positive` or `alive-no-start-time` → `live-owner`; `other-host` (the owner block names a host that is not this machine) → `other-host-owner`, refused, never read as dead; `error` or an unreadable `run-state.json` → `unknown-owner`, refused. An owner block whose `host` is absent or not a non-empty string is not "recorded on another host", but `probeOwnerPid` would answer `other-host` for it, so the gatherer decides it before the probe: no valid pid (`Number.isInteger`, `> 0`, `<= MAX_PID` from `owner-pid-probe.js`) → `dead-owner` (the spec's "no pid"), a valid pid → `unknown-owner` (its process cannot be placed on this host). Never `runLiveness`: heartbeat, worktree-lock and last-commit recency do not make an owner live here — the sibling-session check (run before the mint and repeated after entering the worktree) refuses a live session in that worktree. A present directory with a `run-state.json` and a dead owner is archived before the new run dir is minted (`close-run --run` first when its status is non-terminal, then `archive-run --run`). A present directory with no `run-state.json` (`stateless`; `archive-run` refuses it) is **not archived** (issuecomment-6540061358 q3): resume logs one line to the new run's `decisions.md` and leaves the directory to reconcile's orphaned-run cleanup.
- Stalled worktree (spec D1 "Worktree", issuecomment-6540061358 q1): when `{main root}/.claude/worktrees/dispatch-record-{N}` exists, `git -C {worktreePath} --no-optional-locks status --porcelain -b -z` must print only its `## {branch}` header, naming the PR's head branch (the option before `status` — `tests/git-status-optional-locks.test.js` scans `plugin/bin/`; a different or detached branch refuses as `worktree-branch` under the Closed rule). Any entry after the header refuses the record (`dirty-worktree`) before anything is minted, with a line listing every dirty path and the manual remedy. Resume never commits, stashes, discards or pushes the leftover edits. A missing worktree has nothing to check (step 5 recreates it from the PR head branch). A `git status` that fails on an existing worktree is a transient read failure (CLI exit 4), never read as clean.
- `DISPATCH_HEADLESS`: `dispatch resume #N` is typed by a human, so it follows the same rule `task-prompt.md` already applies to the explicit `#N` form — the first call's invocation line carries no `DISPATCH_HEADLESS=1 ` prefix.

The second call and its continuations carry neither. The Continuation call paragraph itself is not edited.

9. 10. A non-draft open PR on the head branch is refused (`not-draft`), not resumed — pinned in Tasks 2 and 3.

13. More than one same-repo open PR on the head branch is refused inside the pure verdict (`multiple-prs`), and the line names each PR number — pinned in Task 2; the CLI passes the whole listing through untouched — pinned in Task 3.

16. A `swept: stale claim` tombstone is eligible and re-claims by the ordinary write; `swept: issue closed` is not — pinned in Tasks 1 and 2.
17. The marker slug is exactly `record-{N}`: `…-dispatch-record-12` and `…-record-120` are foreign for #12 — pinned in Task 2.
18. The dispatching session's own kept lock on the stalled worktree, with the prior run archived, does not read as a live sibling; a lock whose prior run records a different session id still does, and a real sibling listed after the own kept lock is still found — pinned in Task 3.
21. Resume enforces the queue's record-level gates it would otherwise bypass: a closed issue, an open body or native `Blocked by` dependency, and any other `bot:*` label (`bot:parked`) are refused — pinned in Tasks 2 and 3.
22. A reaped worktree is recreated only from a local `{headRefName}` whose tip equals the PR's `headRefOid` and that no other worktree has checked out — decided before the mint, pinned in Tasks 2 and 3.
23. Task 3 learns the prior run id from `selectResumePr` (Task 2) before any run-dir read; a fork PR listed first never supplies it — pinned in Task 3.
19. `dispatch #N`'s open-pr line names `dispatch resume #N` only when the resume verdict is eligible; the base line stays byte-identical — pinned by Task 4's conformance assertions and the existing L83 pin.

9b. `labels` holds any `bot:*` label other than `bot:in-progress` and `bot:blocked` (first in sorted order) → `unlisted-label`, line `#{N} carries {label} — not resumable while it is set; clear it (gh issue edit {N} --remove-label {label}) once its trigger has fired, then run /claude-tweaks:dispatch resume #{N}`.

10. `priorRunDir` is `live-owner` or `unknown-owner` → `prior-run-live`, line `#{N}'s prior run {runId} has an owner that is not provably dead ({live | unknown}) — not resumable while it may still be running; wait for it to exit, then run /claude-tweaks:dispatch resume #{N}`.

15. `worktreeBranch === null` and `localBranchSha` non-null and ≠ the kept PR's `headRefOid` → `branch-diverged`, line `#{N}'s local branch {headRefName} is at {sha7}, not PR #{pr}'s head {oid7} — push its commits or reset it to origin/{headRefName}, then run /claude-tweaks:dispatch resume #{N}`.
