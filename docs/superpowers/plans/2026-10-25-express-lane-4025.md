# Express Lane (#4025) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let a small, low-risk, singleton record ship through one agent — claim, edit, impacted tests, commit, PR, merge-on-green — with a deterministic eligibility gate in front, escalation back into the normal `/flow` path on any failed check, and deterministic post-merge sampled review behind.

**Architecture:** All deterministic decisions live in a new pure library `plugin/bin/lib/express/` (eligibility, diff bounds, merge-verification override, review sampling) behind one multi-verb CLI `plugin/bin/express-lane.js` (`gate`, `check`, `escalate`, `verify`, `samples`). One shared procedure, `plugin/skills/_shared/express-lane.md`, is the express agent's instructions; `/dispatch` routes an eligible singleton group to it through a new Task template (`dispatch/express-prompt.md`), and `/flow` routes a single eligible record to it through `flow/express-entry.md`. The lane is opt-in (`express-lane: false` by default) and `pr-first`-only.

**Tech Stack:** Node 18+ CommonJS, `node --test`, markdown skill prose.

**Spec:** `.claude-tweaks/pipelines/2026-10-25T215004-record-4025/work/4025-spec.md`

## Global Constraints

- The lane is opt-in: new boolean policy key `express-lane`, default `false`. A consumer project sees no behavior change until it sets `express-lane: true`. This repo's own `.claude-tweaks/policy.yml` is **not** changed by this record (the installed build reads it with older code).
- Express requires `integration-model: pr-first` — CI-green-before-merge is the lane's safety substitute for review, and only a PR carries it.
- Eligibility rule set (settled here, per the spec's "settled in specify" note): labels `risk:low` AND `size:low` AND `ceremony:fast-lane` AND a `type:*` label (`typeOf`, so `compose-subject.js` can compose the merge); no `auto:merge-pending` label (its maturation runs only on the normal Auto-merge gate); 1–3 `### Key Files` entries (`extractKeyFiles`); no Key File that is a frontend file (declared `Surface:` of `web`/`mobile`/`desktop`, or — when no Surface line — `fileMatchesFrontendPredicate`); no Key File under a protected path; no Key File matching `merge-sensitive-paths`; body passes `shapeGate`; the run's `decisions.md` carries no prior escalation for the record.
- Protected paths are project-agnostic Claude Code / plugin conventions, never this repo's `plugin/` prefix (Consumer-portability check): a path segment `hooks` (`(^|/)hooks/`), a basename `hooks.js`, a `skills/_shared/` segment (`(^|/)skills/_shared/` — every `_shared` file is a cross-skill contract, a conservative superset of "multi-consumer"), `(^|/)\.github/` (CI config could otherwise subvert the CI-green gate), and `(^|/)\.claude-tweaks/policy\.yml$`.
- Diff bounds after the build: every changed non-test, non-pipeline-artifact path (`classifyDiffFiles` from `plugin/bin/lib/issues/blast-radius.js`) must be a Key File; no changed path protected or merge-sensitive; implementation lines ≤ `auto-merge-max-lines` (default 40); at least one changed file.
- Express never merges under `merge-verification: off`: the effective value is `wait` when the resolved value is `wait`, else `merge-when-green` (`expressMergeVerification`). It reaches `_shared/pr-first-merge.md` Step 2.5 through the express run dir's own `config.yml` overlay, written once the PR exists.
- Escalation is only possible before the branch is pushed; reasons are exactly `failing-test`, `out-of-bounds`, `gate-denial`, `express-error`. The escalation line is `AUTO {time} — Express lane: escalated #{n} to /flow (reason: {reason}) — {detail}. Reversibility: high (worktree and branch kept).` under `## /express-lane`.
- Post-merge sampling: new integer policy key `express-review-sample-every` (`min: 1`, default `5`); an express merge is sampled when its 1-based ordinal among merged express PRs (sorted by `mergedAt`, ties by PR number) satisfies `isSampleOrdinal(ordinal, every)` from `plugin/bin/lib/issues/grant-sampling.js` — reuse it, never restate it.
- Express PR body marker: `claude-tweaks-express: {run-id}` (plain line) alongside the standard dual run marker; review-done marker: a trusted (`isTrustedComment`, `plugin/bin/lib/issues/comment-trust.js`) PR comment starting `<!-- run-comment: express-review -->`.

## Review Focus

1. **A record whose labels change between queue pull and dispatch** (e.g. a human raises it to `risk:medium` after the pull): the express path must not run on the stale verdict — Task 8's Step 5 routing re-runs `gate --issue` live, and Task 5 pins that `gate --issue` reads labels from the fresh fetch, not from `--records-json`.
2. **An express run whose PR sits pending-review for more than 24 h**: a run dir without `config.yml` is swept as an orphaned mint after 24 h (`classifyRunDir`'s `orphaned-mint`, `plugin/bin/lib/reconcile/archive-merged.js`) — Task 7's procedure writes `config.yml` right after `record-pr`, and Task 5's `check` test pins that its proceed output carries the exact `configSet` string.
3. **Escalation after the run dir already has express content**: the normal first call must adopt it, not refuse it — `computeAdoption` (`plugin/bin/lib/flow/preflight.js`) returns case 2 for `dispatched: true` + no `pr` + no `config.yml`; Task 5 adds a test feeding an escalated express run dir through `computeAdoption` and asserting case 2.
4. **The escalation loop**: `/flow`'s express entry or a dispatch re-route seeing a record that already escalated in this run must not route it to express again — Task 5 pins `gate --run` returning `already escalated in this run`.
5. **Merge-verification `off` on a repo with no PR CI**: express must not degrade to an immediate merge — Task 2 pins `expressMergeVerification('off') === 'merge-when-green'` and Task 5 pins `check`'s `configSet` carries `merge-verification=merge-when-green` when the resolver returns `off`.
