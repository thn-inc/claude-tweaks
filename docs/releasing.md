# Releasing

This repo dogfoods the same release engine every consumer project uses: `/claude-tweaks:release`, driving release-please under `integration-model: pr-first`.

**The whole-branch review still gates the bump** — `/claude-tweaks:release`'s Step 3 runs `/claude-tweaks:review base:{lastTag}` unconditionally, before any merge, for the same reason this always applied: a plan that schedules its version bump as the final step has, by that ordering alone, decided that any cross-task defect ships and is fixed as a patch (`[IL-97]`). Before that review, once its review-tree check passes, Step 3 runs `/claude-tweaks:test full` — the one whole-suite run on the developer machine per version (#5370) — and a failing test stops the release before the console. So does a run that errors, is refused, or ends without a full pass stamp verifying HEAD: absence of a verdict is not a pass.

**An open `release-block` record stops the release first** (#5882). Step 1.5 runs `plugin/bin/release-block.js check` straight after the fact pack, before the review and the suite: an open record carrying the `release-block` label ends the run `HELD`, naming each record in `release-held.md`, in every mode and with no question. An unreadable label state stops it `failed` and never reads as clear. Step 4 re-reads it before the merge, because the review can take hours. Closing the record or removing the label is the explicit act that lifts it. Step 8 sets it on each critical or high finding it files as a record, or declines as covered by an open one; a person can set it by hand. Contract: `plugin/skills/_shared/release-block.md`.

**Invocation:** `/claude-tweaks:release` (no arguments for the on-demand path; `--train` for the scheduled release-train Routine). It reads the preflight fact pack, renders one console, merges the release-please PR via `gh pr merge --squash` — only once `origin/main` still equals the tip Step 3 reviewed, delta-reviewing any commits that arrived and holding the release past `release-tip-moves` moves (#4041) — verifies the resulting tag/GitHub Release/`release: published` workflow run, and books the shipped records. Full procedure: `plugin/skills/release/SKILL.md`.

**Where it runs, and what it leaves behind.** Step 3's review stands in the main checkout (`$RUN_ROOT`), never a worktree. After a fetch, that checkout must be on `main`, 0 commits behind `origin/main`, and differ from it only under `.claude-tweaks/pipelines/`: local `[reconcile] archive run …` commits pass, and anything else stops the run before the console as `failed`, with a recovery chosen by the clause that failed (#4012). With `--as`, Step 5 re-runs that check before the override and builds the `Release-As:` commit on the fetched tip with `git commit-tree`, so only that commit reaches origin and the archive commits stay local (#4139). A standalone release mints its own run directory, because Step 0 never adopts a prior release run's one. At Step 8, in a directory the release created, every finding the review staged gets one disposition (filed as a record, digested, or declined with a reason) and the directory is then closed. It is archived under `.claude-tweaks/pipelines/archive/` only when every finding was disposed of without a failure (a `staged/` or `decisions.md` that cannot be read, for any reason other than not existing, counts as one, #4155); otherwise it stays in place with those findings in `staged/` (#3898). The staged-file prefixes Step 8 recognises are listed in one review staging roster in `plugin/skills/release/disposition.md`, which covers every prefix the review's producers stage, `design-decision-*` included. A `visual-review-*` skip note is archived as a non-finding. A prefix with no roster row still fails closed (#4156).

**What replaced `plugin/bin/release.js`:** release-please (`googleapis/release-please-action@v4`, `.github/workflows/release-please.yml`) computes the version from Conventional Commits on `main` and opens/updates a standing release PR; merging that PR is the bump. `release-please-config.json` pins `release-type: simple` with `plugin/.claude-plugin/plugin.json`'s `$.version` as an `extra-files` target; `.release-please-manifest.json` tracks the current version. `commit-search-depth` is raised to 2000 (release-please's default is 500): release-please reads only that many commits back from the tip, so a burst of non-conventional commits on `main` (600 `[reconcile] archive run …` commits on 2026-11-15) pushed the real `feat`/`fix` commits out of its window and the release PR re-rendered as a patch with one changelog entry. History before the migration (bootstrapped 2026-09-21) was retro-tagged onto real `v*` git tags — see `docs/decisions/0018-release-please-engine.md`.

**The marketplace mirror** is now `.github/workflows/mirror-marketplace.yml`, triggered on `release: published` — the same catalog write `plugin/bin/lib/release/mirror.js` used to perform by hand, preserving its two invariants: the catalog entry is pinned by `sha` (never `ref`), and carries no `version` field (the payload's own `plugin/.claude-plugin/plugin.json` is the single version authority).

**Post-publish release notes.** The same `mirror-marketplace.yml` job runs a second step, `plugin/bin/release-notes-publish.js` (#2582), after the mirror write: release-please has no knowledge of this repo's `Release-Note:` commit trailer, so it never renders a Highlights block. This step walks the just-published commit range, extracts every `Release-Note:` line (a bundled merge commit carries one per bundled record), renders them via `plugin/bin/lib/release-notes.js` — which drops `No user-visible change` notes and exact duplicates — and idempotently appends a `### Highlights` block to both the just-published GitHub Release body and CHANGELOG.md's matching entry (a follow-up commit, pushed with the workflow's own `GITHUB_TOKEN` — the `contents: write` permission this step needs is declared at the workflow level, but `mirror-marketplace.yml` has only the one `mirror` job and only fires on `release: published`, so it cannot reach any other trigger or job).

## Bounding CHANGELOG.md (`changelog-max-releases`)

Off by default (`0` = never trim). Set to `n` and both engines keep the newest `n` release sections after a release: pr-first trims in `release-notes-publish.js`, in the Highlights commit when there is one, else in a `chore: trim CHANGELOG.md to the newest {n} releases` commit; local-merge trims in a separate commit after the release has landed (commit, tag, push, hook), so the tag keeps the full file and a failed hook means no trim. A trim never fails a release: a failure prints `changelog trim: failed ({reason}); file left untrimmed` (when the restore after a failed trim commit also fails, the line says the index may still hold the trimmed file), under pr-first an unreadable `policy.yml` prints `changelog trim: policy unreadable ({reason}); not trimmed`, and the release still reports released. Under local-merge an unreadable `policy.yml` stops `release-local.js` before it changes anything, as it did before the key existed, so that line never prints there.

The trimmed file ends in an `## Older releases` footer with two routes to removed notes: the recorded commit (`git show {sha}:CHANGELOG.md`, the full file up to the first trim) and the release's own tag (`git show v<version>:CHANGELOG.md`, which has no Highlights block).

Opt in only once every session runs this release or newer: an older build reports trimmed versions as missing, and its `/claude-tweaks:tidy` would add them back. After opting in, check that the first release-please PR leaves the footer last. Do not trim inside release-please's own PR: its diff must stay what release-please rendered.

## Manual Steps

Two PATs, both required — their failure modes differ. Without `RELEASE_PLEASE_TOKEN` the mirror silently never runs at all (no workflow run, no error — the release still ships, its catalog entry just doesn't update). Without `MARKETPLACE_TOKEN` it runs and fails loudly, with the explicit error named below.

**`RELEASE_PLEASE_TOKEN`** — a GitHub secret consumed by `.github/workflows/release-please.yml`'s `token:` input. A release-please-created GitHub Release made with the default `GITHUB_TOKEN` does not trigger other workflows — `release: published` stays silent, so `mirror-marketplace.yml` never fires — a documented GitHub Actions restriction, also recorded independently in `.claude-tweaks/policy.yml`'s `release-hook` comment. Set once (2026-09-21): a fine-grained PAT with `contents: write` + `pull requests: write` on `thn-inc/claude-tweaks` itself, stored as a repository secret named `RELEASE_PLEASE_TOKEN`, wired into `release-please.yml`'s `token:` input. If it ever expires, re-issue it and update the secret — no code change needed, the workflow already references it.

**`MARKETPLACE_TOKEN`** — a GitHub secret on this repo, consumed by `mirror-marketplace.yml` as `GH_TOKEN` for its `gh api` calls. It needs write access to `thn-inc/claude-tweaks-marketplace`'s contents (the mirror reads then `PUT`s `.claude-plugin/marketplace.json` there), which the default per-repo `GITHUB_TOKEN` cannot grant since that repo isn't the one the workflow runs in. Set once (2026-09-21): a fine-grained personal access token scoped to `thn-inc/claude-tweaks-marketplace` with Contents: Read and write, stored as a repository secret named `MARKETPLACE_TOKEN` on `thn-inc/claude-tweaks`. If the mirror ever fails with "MARKETPLACE_TOKEN secret is missing or empty," this token specifically has expired — re-issue it and update the secret.

## After the merge: which release carried it

Unchanged — `_shared/pr-first-merge-post-merge.md` Step 4.1 answers this from tag ancestry alone:

```
git fetch origin <integration-branch>
git describe --tags --contains --first-parent --match 'v*' <merge-sha>
```
