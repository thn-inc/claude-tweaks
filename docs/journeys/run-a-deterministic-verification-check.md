# Run a Deterministic Verification Check Through bin/verify.js

**Persona:** claude-tweaks skill author (or a maintainer of a project using the plugin) who wants proof that `verification.md`'s migrated Step 2 invocation actually produces bounded output and a trustworthy `report.json` — rather than trusting the skill's prose to have described the CLI's behavior correctly.
**Goal:** Watch the runner execute a mix of passing, failing, and fail-fast-skipped checks, and confirm stdout stays bounded, exit codes key off each check's own result, and `report.json` carries the evidence `VERIFICATION_PASSED`/`VERIFICATION_SHA` downstream consumers rely on.
**Entry point:** A terminal at a project checkout root, `plugin/bin/verify.js` reachable (this repo's own checkout, or another project's resolved plugin root per `docs/skill-authoring.md`'s plugin-root contract).
**Success state:** A markdown results table on stdout with one row per check plus at most one bounded failing region, a `report.json` whose `pass`/`sha`/`dirty`/`checks` fields match what actually ran, and a non-zero process exit exactly when something failed.

## Steps

### 1. Run the reserved three-stage set — terminal
- **URL:** `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --cmd types="tsc --noEmit" --cmd lint="eslint ." --cmd tests="npm test"`
- **Action:** Run against a project that supplies all three reserved names.
- **Should feel:** One command replacing the old prose-orchestrated capture recipe — no `LOG=`, no `tail`, no `grep` pipeline to hand-assemble, and (since #1921) no `$(git rev-parse --git-dir)` substitution either.
- **Should understand:** `types` and `lint` start concurrently; `tests` only starts once every supplied one of them has exited 0. A stage-1 failure reports `tests` as `skipped: fail-fast` in both the stdout table and `report.json` — never silently dropped, never spawned anyway. Inside a git checkout the runner resolves `--log-dir` itself to `{git-dir}/claude-tweaks-verify` (per-worktree, never the common dir); pass `--log-dir` explicitly only to relocate the logs, and expect a fresh `claude-tweaks-verify-` tmpdir outside any checkout.
- **Red flags:** `tests` spawning before `types`/`lint` finish; a `types` failure that still lets `tests` run; a raw `npm test` log (megabytes of TAP output) landing on stdout instead of a bounded summary.

### 2. Read the bounded stdout, not the log file
- **URL:** the same command's own stdout
- **Action:** Point a check's command at something that fails loudly (e.g. `--cmd tests="node -e \"process.exit(1)\""`), then read what the runner prints.
- **Should feel:** Legible in one screen — a status table plus, only for a failing check, one capped failing-region excerpt (≤100 lines, each line truncated past 500 characters).
- **Should understand:** The full, unbounded output still exists — one plain-text log file per check under `--log-dir` (`{name}.log`) — the runner's own stdout is a summary, never a copy. The trailing `report: {path}` line survives for a reader that consumes all of stdout (`| cat`, `| tee`), because the runner sets `process.exitCode` and lets Node drain pending writes rather than calling `process.exit()` mid-flush. A reader that closes early (`| head`) legitimately truncates the output instead — the runner's EPIPE guard exits quietly rather than crashing.
- **Red flags:** A truncated table with no trailing `report:` line when the reader consumed all of stdout; a failing region that's actually the whole raw log; an EPIPE crash (a raw stack trace) when piped into an early-closing reader.

### 3. Read report.json's evidence fields
- **URL:** `cat {log-dir}/report.json` after Step 1 or 2
- **Action:** Inspect `pass`, `sha`, `dirty`, and each entry under `checks`.
- **Should feel:** Machine-readable proof, not a narrated claim — this is what turns `VERIFICATION_PASSED`/`VERIFICATION_SHA` (the values `/build` and `/test` pass between pipeline steps) into evidence instead of prose.
- **Should understand:** `sha` is `git rev-parse HEAD` as read before the checks started (#3757), never the HEAD at the end of the run, and `dirty` is true when the tree was dirty at the start or the end. A run whose HEAD moved while it ran still writes `report.json` under that start `sha` and keeps its exit code, but writes no pass stamp (Step 7). Outside a git repository `sha` (and `dirty`) is `null`; `dirty: true` means "verified this tree, which is not exactly commit `sha`" — never trust `sha` alone on a dirty tree. Every non-skipped check's entry carries `counts: {tests, pass, fail}` whenever its output parses (TAP, jest/vitest, pytest) — including a failing check, not only a passing one; an unparseable or ambiguous summary omits `counts` entirely rather than guessing. A check that couldn't even spawn records `exitCode: null` plus a `spawnError` string rather than a `counts` block.
- **Red flags:** `report.json`'s `sha` naming a commit that landed while the checks were running; `counts` present with a fabricated or guessed value; `pass: true` while a supplied check's `exitCode` is non-zero or `null`; `report.json` missing or half-written after a run that was interrupted mid-flight (the write is atomic — temp file then rename — so this should never happen).

### 4. Add an unknown check name
- **URL:** `node plugin/bin/verify.js --log-dir /tmp/verify-demo --cmd tests="npm test" --cmd smoke="./scripts/smoke.sh"`
- **Action:** Supply a `--cmd` name outside the reserved `types`/`lint`/`tests` set.
- **Should feel:** Extensible without a spec change — any project-specific check rides along under the same ordering discipline.
- **Should understand:** Unknown names run serially, after the known stages, in the order given, subject to the same fail-fast rule — a failing `tests` skips `smoke`, and a failing `smoke` (if there were a second unknown check after it) would skip that one too. On a `--baseline` run (#3511) neither happens: only a `types`/`lint` failure skips the suites, so adjudication sees every suite's evidence.
- **Red flags:** An unknown check running before `tests` finishes; an unknown check's failure not fail-fasting a later unknown check (outside a `--baseline` run).

### 5. Trigger a usage error
- **URL:** `node plugin/bin/verify.js --log-dir /tmp/verify-demo --cmd "smoke:e2e=echo hi"`
- **Action:** Supply a malformed `--cmd` — an invalid name (must match `[A-Za-z0-9_-]+`), a duplicate name, an empty command, a missing flag value, or an unknown flag.
- **Should feel:** Fails fast and explains itself — no checks spawn, no `report.json` is written.
- **Should understand:** A malformed invocation prints the specific problem plus the usage line to stderr and exits `2`, before anything runs. `--json <path>` relocates the report away from the `{log-dir}/report.json` default used elsewhere in this journey — pass it when a caller needs the report at a fixed, predictable path.
- **Red flags:** Any check spawning despite a malformed invocation; an exit code other than `2` for a usage error.

### 6. Watch a quieter suite surface as a caveat, not a silent pass
- **URL:** two consecutive runs sharing one `--count-stamp` path, e.g. `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --log-dir /tmp/verify-demo1 --count-stamp "$(git rev-parse --git-dir)/claude-tweaks-test-count.json" --cmd tests="npm test"`, then again with fewer tests actually running (e.g. after narrowing a glob)
- **Action:** Compare the first run's stdout/`report.json` against the second's.
- **Should feel:** A quieter suite is impossible to miss — the CAVEAT reads as its own paragraph, distinct from the pass/fail table, not buried in a check's `summary` field.
- **Should understand:** IL-84 (`docs/incident-log.md`) is what this closes: an enumerated-glob `npm test` config once silently excluded a whole test directory while still exiting 0, so under-coverage read identical to a clean pass. `--count-stamp` persists the `tests` check's own parsed count (`extract.js`'s `parseCounts`) across runs; a strict drop between consecutive runs prints a `CAVEAT: test count dropped from {previous} to {current} …` line on stdout and sets `report.json`'s `testCountRegression: {previousTests, currentTests, droppedBy}` — without flipping `report.pass`, since a legitimate test removal also drops the count. Outside a checkout, omitting `--count-stamp` disables persistence and comparison entirely — no stamp file, no caveat, ever; inside a checkout, `--count-stamp` defaults to `{git-dir}/claude-tweaks-test-count.json` (#1921), so persistence and comparison happen automatically unless `--count-stamp` is overridden. A `tests` check whose output doesn't parse at all (family sniffed but no counts line recognized) never disables the comparison silently either: with a count stamp in play, `report.json` gains a `countsUnparsed: {family}` entry on that check and stdout carries its own `CAVEAT: tests counts unparsed (family {family}) — count-stamp comparison skipped; see {logPath}` paragraph, distinct from the count-drop caveat above; outside a checkout (no stamp configured), this caveat never renders either, same as the drop case. Before every parser runs (`sniffFamily`, `parseCounts`, `summaryLine`, `extractFailingRegion`), the runner strips ANSI from an in-memory copy of the output and sets `NO_COLOR=1`/`FORCE_COLOR=0` on the spawned check's own environment (a caller-supplied `FORCE_COLOR` in `process.env` still wins) — a coloured vitest/jest summary line is otherwise invisible to these regexes; the raw log file on disk stays untouched.
- **Red flags:** A count drop that silently passes with no CAVEAT line; a count drop that fails the run outright (this is a caveat, not a gate); a stamp-write failure (e.g. `--count-stamp` pointing at an unwritable path) that crashes the whole run and discards `report.json` even though every check passed — the write is best-effort and must degrade to "no baseline persisted," never to a lost report; a tests check whose counts didn't parse silently skipping the comparison with no `countsUnparsed`/CAVEAT trace at all.

### 7. Read the pass stamp, then confirm --stamp-status agrees
- **URL:** `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --cmd tests="npm test"` followed by `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --stamp-status`
- **Action:** Run the full resolved check set to a passing result inside a git checkout, then read `{git-dir}/claude-tweaks-verify-pass.json` and separately run `--stamp-status`.
- **Should feel:** The pass stamp is the runner's own artifact, not something a skill or agent hand-writes — `verification.md`'s Step 2.5 states this is the only writer (#1921, closing #1784's agent-written-stamp gap).
- **Should understand:** A passing run of every supplied `--cmd` check (none fail-fast skipped) writes `{sha, dirty, scope: "full", fullSha, base: null, changedFiles: [], suitesRun, flakyRetried: [], reportPath, at}` to `{git-dir}/claude-tweaks-verify-pass.json`, keyed on the invoking cwd's own `git rev-parse HEAD` — never on `--git-dir` when one is supplied (see Red flags). `--stamp-status [--git-dir <dir>]` reads that artifact back and recomputes `dirty`/`head` fresh from the live tree rather than echoing the stored stamp, printing `{present, sha, head, dirty, scope, fullSha, match, verifiedHead, baselineAdjudicated, reportPath, legacy}` and always exiting 0 — status is data, never a failure, including when no stamp exists at all. A targeted run (`--no-stamp`, or a `--cmd` set that isn't the full resolved suite) must never leave a stale-but-plausible `scope: "full"` stamp behind for a later `--stamp-status` to misread as a clean full pass. `verifiedHead` (#1923) is the field the re-verify gates read — `true` for a clean HEAD covered by a full pass or by a passing scoped run whose `fullSha` is still an ancestor of HEAD — while `match` keeps its strict full-pass meaning. The stamp's `sha` is the HEAD the runner read *before* the checks started (#3757): commit while the suite is still running and the run writes no pass stamp at all, printing `tree moved during the run (HEAD {start} -> {end}); no pass stamp written`, so `--stamp-status` reads `verifiedHead: false` for the new commit instead of crediting it with a pass it never ran. Only a moved HEAD withholds the stamp — a check that merely leaves an untracked file behind still stamps, with `dirty: true`, which `--stamp-status` never reports as verified. `dirty` is true when the tree was dirty at the start *or* the end of the run, so an edit reverted mid-run never leaves a clean-looking stamp, and the moved check runs after any `--baseline` adjudication, so a commit landing during that re-run is caught too. `--cwd` moves only where the checks spawn, so it must stay inside this checkout (#3799). A subdirectory (a monorepo package) runs and stamps as usual, but a `--cwd` in another repository, a sibling worktree or a non-git directory exits 2 before any check spawns. It prints `--cwd {dir} resolves to git dir {theirs | none (not inside a git checkout)}, not this checkout's ({ours})` and writes no stamp or report. To verify that other checkout, run `verify.js` from inside it. Both git dirs are compared after resolving symlinks and the OS's own path casing, so a symlinked or case-variant `--cwd` that names this checkout still runs and stamps; `--stamp-status --git-dir` compares the same way.
- **Red flags:** A stamp naming a commit that landed while the checks were running, or a `still-verified` scoped run anchored on one; a stamp withheld (no moved-line printed) only because a check left an untracked artifact. A stamp written under a repo other than the one whose HEAD it claims — `--git-dir` on a run redirects `--log-dir`/`--count-stamp` paths only; it never writes the pass stamp, precisely because `gitInfo()` reads HEAD/dirty from the invoking cwd, not from `--git-dir`. `--stamp-status` reporting `match: true` against a dirty tree, or against a stamp whose `scope` isn't `full`. A `--cwd` pointing outside the invoking checkout that runs any check, or that leaves a stamp or `report.json` under the invoking checkout's git dir. A symlinked or case-variant `--cwd` naming the invoking checkout itself refused with exit 2.

### 8. Declare a scope, then watch three consecutive runs shrink to what changed
- **URL:** write `.claude-tweaks/verify-scope.json` (`checks.tests` as a map of suite name → command, `rules` as ordered `{match, suites, static}` globs — see `docs/plugin-structure.md`'s `plugin/bin/lib/verify/` row), then run `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --scope .claude-tweaks/verify-scope.json --integration-branch main --cmd types="tsc --noEmit" --cmd api="pnpm --filter api test" --cmd web="pnpm --filter web test"` three times: once fresh, once after a docs-only commit, once after an `apps/api/**` commit.
- **Action:** Read the `Scope:` line the runner prints above the results table on each run, then `{git-dir}/claude-tweaks-verify-pass.json` after each.
- **Should feel:** The runner, not the operator, decides how much to run — and says so in one line (`Scope: none — 1 changed file(s) since 3af174c00; suites: none; static: no; unmatched: 0`, then `still-verified: bookkeeping-only delta (docs/guide.md)`), so a shed suite is a stated decision with its evidence, never a quiet omission.
- **Should understand:** The first run has no prior stamp, so it is `full` and becomes the anchor (`fullSha`) every later run diffs from. A docs-only delta selects `none` — nothing spawns, the run exits 0, and the stamp is still written with `scope: "none"`, `base` equal to that anchor, and `suitesRun: []`. An `apps/api/**` delta selects `scoped` — only `api` (plus `types`/`lint` when the matching rule says `static: true`) runs, and the stamp carries the prior `fullSha` unchanged: only a `full` run may advance it, and only a `full` run rewrites the legacy bare-SHA twin or the #881 count stamp. A path no rule matches fails closed to `full` and is listed under `unmatched`. Every check the selected mode requires must be supplied as a `--cmd` (a `full` run needs every declared suite) — a missing one is exit 2 naming it, so a partial invocation can never stamp a pass. With no usable anchor, `--integration-branch` (or `--base`) is required — the runner has no `origin/HEAD` fallback; the caller runs `_shared/integration-branch.md`'s ladder, exactly as `blast-radius-cli.js` expects. A `checks.tests` string containing `{base}` switches to tool-scoped mode: the runner substitutes the resolved base into that one command and runs it as `tests`, and such a run never advances `fullSha` either. `report.json` gains a `scope` object (`suites` always an array) mirroring the stamp.
- **Red flags:** A `scoped` or `none` run whose stamp `fullSha` moved to the current HEAD; `--stamp-status` reading `match: true` off a `scope: "scoped"` stamp (it must not — only `full` matches); a `--scope` run at an unchanged HEAD replacing a `full` stamp with `none`; a `--cmd` name outside `types`/`lint`/the declared suites, or a `--base` that disagrees with the stamp anchor, exiting anything other than `2`; a renamed or non-ASCII path (`src/café.js`) appearing mangled in `changedFiles`; an unresolvable base producing an empty changed set instead of an error.

### 9. Ask the runner what changed, instead of hand-rolling git diff
- **URL:** `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --changed-files --integration-branch main` after Step 8's first (full) run, with one further commit and one uncommitted edit in the tree
- **Action:** Read the one JSON line it prints, then compare it with what `git diff --name-only` shows for the same tree.
- **Should feel:** One answer to "what changed in this run" — the same set `verify.js --scope` classifies and `/claude-tweaks:test affected` / `qa affected` scope to, so those consumers cannot disagree; and one flag away, `--ignore-stamp`, the whole branch diff the pipeline's QA story filter and design gate select against, so a build's own source change is never hidden behind the stamp `/build` wrote after it.
- **Should understand:** `{base, files}` — `base` is the explicit `--base` when one is given, else the stamp's `fullSha` when it is still an ancestor of HEAD (under `--integration-branch`, an anchor equal to HEAD falls through, #2486, so a just-stamped HEAD reads the whole branch diff rather than an empty set), else the integration-branch merge-base; `files` is the committed delta since that base ∪ the working tree, untracked files included, and a rename reported at both its old and new path (the old path is gone from HEAD exactly like a deletion; a copy reports only its new path). A bare `git diff --name-only` is empty for every committed pipeline diff, which is why `/claude-tweaks:test affected` and the `qa affected` filter were redefined onto this mode (#1923). It reads only — no report, no stamp, no log dir — and when no base resolves (no stamp, no `--integration-branch`, no `--base`) it exits 1 with a message rather than printing an empty list. Re-run with `--ignore-stamp` (#3048): the stamp anchor is skipped, so `base` is `--base` or the `--integration-branch` merge-base and `files` covers the whole branch — Step 8's full run's own commits included, not just the commit after it. With no `--base` and no `--integration-branch` it exits 1 even though a usable stamp exists; the base-equals-HEAD `warning` still applies.
- **Red flags:** An empty `files` array on a tree with a committed change since the anchor; exit 0 with no output when the base could not be resolved; a `claude-tweaks-verify/` log dir or a stamp appearing after a `--changed-files` call; `--changed-files` accepted alongside `--cmd` or `--scope` (both are usage errors); an `--ignore-stamp` run whose `base` is the stamp's `fullSha`, or that falls back to the stamp when no `--base`/`--integration-branch` is given; `--ignore-stamp` accepted on a check run or `--stamp-status` (usage error, exit 2).

### 10. Watch an allowlisted flake retry itself, and watch the allowlist push back
- **URL:** add to Step 8's declaration `"flaky": {"files": ["tests/flaky.test.js"], "maxRetries": 1}` and `"retry": {"api": "pnpm --filter api test -- {file}"}` (the `api` suite runs `node --test`; spec/TAP output and fully accounted jest/vitest output (#3480) are the families flaky retry accounts for — a pytest suite refuses with `no-accounting-guard: summary`), then run Step 8's invocation with `tests/flaky.test.js` failing once under load; then seed `{git-dir}/claude-tweaks-test-count.json`'s `flakyHits` at `4` for that file and run again; finally seed `flakyHits` at `4` for a second file, `tests/env-flaky.test.js`, that is **not** on `flaky.files` and that fails under load but passes in isolation, and run Step 11's `--run "$PIPELINE_RUN_DIR" … --baseline` invocation once.
- **Action:** Read the `api` row, the `CAVEAT:` lines under the table, `report.json`'s `checks.api.retryDecision`/`retryAttempts`, and the stamp's `flakyRetried`; on the second run, read `report.json.flakyEscalation`; on the third, read the `baseline-flaky` CAVEAT line, `report.json.flakyEscalation[].onAllowlist`, `{run-dir}/staged/flaky-allowlist-tests-env-flaky.test.js.md`, and the `STAGED` entry in `{run-dir}/decisions.md`.
- **Should feel:** The runner adjudicates the flake and says so in the row (`pass (flaky-retried: tests/flaky.test.js)`) and the caveat — no agent-side `node --test` rerun, no second full suite — and the allowlist cannot become permanent quietly: from five hits the second caveat (`CAVEAT: flaky-allowlist: tests/flaky.test.js retried 5 times — file a fix or remove it from the allowlist`) renders on every run until the file is fixed or removed.
- **Should understand:** A retry fires only under `--scope`, only for a `tests`-family check (never `types`/`lint`), and only when **every** failing test file the log names (ANSI stripped; paths as the suite prints them) is matched by `flaky.files` and the suite has a `retry` template — entries are repo-relative paths or `**`/`*` globs (the same forms `rules[].match` accepts), matched against the path exactly as the suite prints it. Any unmatched file, an unparseable log, a missing template, `maxRetries: 0`, or an unreadable log is an ordinary failure whose `retryDecision.reason` says which. The failing path the runner printed is untrusted shell input (#3676). `substituteFile` (`file-template.js`) splices a plain path (`[A-Za-z0-9_@+:./-]` only) into `{file}` byte-for-byte. Any other path — `tests/$(touch x).test.js`, `app/(marketing)/page.test.tsx`, a path with a space — is quoted for the platform's shell: single quotes on POSIX, double quotes under cmd.exe. A template that wraps `{file}` in its own quotes has that wrapper replaced. A path that cannot be quoted safely refuses with `unsafe-path: [{file} ({why})]`: a control character, a leading `-` (the runner would read it as an option), a `%`/`"`/`!` or trailing `\` on win32, or any other quote or escape character left in the template. A vitest multi-project log's `FAIL  |unit| tests/a.test.ts` names `tests/a.test.ts`, never the `|unit|` label. For a spec- or TAP-family log, the named files must also account for the whole failure (#3066): no failing entry left without a test file, summary counts that parse, and failing entries that add up to `fail` + `cancelled` — the same accounting `baseline.js`'s `adjudicate` applies. Otherwise the file list is a known undercount and the check fails with reason `unattributed-failures: {N}` instead of retrying; this test runs before the allowlist match, so it is the reason reported even when a named file is also unlisted. A jest or vitest log is accounted per dialect (#3480): jest's distinct `FAIL` test files must equal `Test Suites: N failed`, vitest's `Test Files N failed`. Any unattributed signal refuses. For either dialect that is a `FAIL` line naming no test file, a coverage or global setup/teardown failure line, Node's `Node.js v…` crash trailer, or more than one summary line. For jest it is also an obsolete-snapshot line, an interrupted `N of M total` run, or a log whose last non-empty line is not jest's `Ran all test suites…` trailer (a crash after or instead of the summary, #3674; counted only when no other unattributed signal already fired). A `--silent` run's `Time:` line and a yarn/pnpm failure trailer also end a run normally; other text after the trailer (jest's open-handle warning, another wrapper's lines) still refuses. For vitest it is also its `Errors` block (the larger of the `Errors` count and the `Unhandled Errors`/`Unhandled Rejection`/`Source Errors` banner, never their sum) or any skipped test file. Vitest has no such guard: its summary (stdout) and failure blocks (stderr) can each end the log. So a jest/vitest log that fully accounts retries, and one that does not fails with `unattributed-failures: {N}`. A pytest log — `extract.js`'s `unattributedFailureCount` returns `null` (as it does for a log carrying more than one runner's markers or none), since pytest's collection `ERROR`s sit outside every `FAILED` line and no failure-accounting guard exists for it (#3204) — never retries: the check fails with reason `no-accounting-guard: {family}`, checked after `no-parse` and before `unattributed-failures`. Five of those reasons route the agent differently afterwards (`verification.md`'s "Flake handling"): an `unlisted: […]` or `unsafe-path: […]` reason selects named-file isolation, while a `no-parse` reason — no failing file could be named at all — or an `unattributed-failures: {N}` or `no-accounting-guard: {family}` reason selects the whole-suite re-run fallback. Only `no-parse` makes the runner append `(retry: no-parse — whole-suite re-run applies)` to that check's stdout summary cell; an `unattributed-failures` or `no-accounting-guard` refusal is read from `report.json`. Files retry serially in log order, each up to `maxRetries` (ceiling 2), stopping at a file's first pass; the first file to exhaust its attempts fails the run (`retryFailed`) and the rest are not attempted. Each attempt is its own `{suite}-retry-{file-slug}-{i}.log`. A retried pass stamps exactly like a clean pass (the retried suite re-ran to green, so the full set passed), and a suite retried to a pass never fail-fast-skips the suites behind it. `summary`/`counts` still describe the original failing run — the row's status and the caveat are the disambiguation. The count stamp keeps `flakyHits` per retried file, pruned to the allowlist only when a declaration was read (a run without one carries the map forward), so the counter survives ordinary full runs. **A file Step 11's `--baseline` adjudicates `flaky` (below) counts into this same `flakyHits` map (#3062)** — `nextFlakyHits`'s keep-set is the declared allowlist UNION whatever this run flagged, not the allowlist alone, so a baseline-flaky file with no `flaky.files` entry at all still accumulates across runs instead of resetting to 1 every time. Each escalation entry now carries `onAllowlist` (`report.json.flakyEscalation`): `true` renders the fix-or-remove wording above; `false` — a file reaching 5 hits purely via baseline adjudication, never declared — instead renders `CAVEAT: flaky-allowlist: {file} baseline-flaky {n} times — not on flaky.files; a staged proposal to add it is pending review`, and, when `--run` names an anchored run directory (Step 11's invocation passes one), the runner itself (never the agent) writes `{run-dir}/staged/flaky-allowlist-{slug}.md` naming the file, its hit count, and the suite's retry-template state, plus a `STAGED` `decisions.md` entry — `.claude-tweaks/verify-scope.json` is never touched by this path; a human approves the proposal at the Review Console.
- **Red flags:** A retry on a run without `--scope`; a retry when any failing file is unlisted; a retry command whose `{file}` reached the shell unquoted for a non-plain path, so that `$(…)`, a backtick or `;` in a printed path ran as shell syntax; an `unsafe-path` refusal that does not name why; a vitest multi-project retry aimed at `|unit| tests/…` instead of the test file; a retry that clears a spec/TAP check whose log carries a failure no named file accounts for, or whose summary counts do not parse (it must refuse with `unattributed-failures: {N}`); a jest/vitest check retried and cleared while its `FAIL` files fall short of `Test Suites`/`Test Files` failed, or beside any other unattributed signal above (it must refuse with `unattributed-failures: {N}`); a jest check retried and cleared whose log ends on anything but a normal run's closing line — the `Ran all test suites…` trailer, or a `--silent` run's `Time:` line, either optionally followed by a yarn/pnpm failure trailer (it must refuse, #3674); a fully accounted jest/vitest check that refuses instead of retrying; a `types`/`lint` failure retried; a pytest check retried and cleared (it must refuse with `no-accounting-guard: summary`); more than `maxRetries` attempts for one file; a `retryFailed` run that still stamped; a `flakyHits` map emptied by a no-declaration run; the escalation caveat absent while `flakyHits` reads 5 or more for an allowlisted file; an agent editing `flaky.files` itself instead of staging a `flaky-allowlist` proposal; a failing check whose `retryDecision.reason` is `no-parse` printing a bare summary cell with no `(retry: no-parse — whole-suite re-run applies)` clause, leaving the isolation path invisible on stdout; a non-allowlisted baseline-flaky file's hit count reset to 1 on the next run instead of accumulating; an escalation at `onAllowlist: false` rendering the "retried…fix or remove" wording instead of the staged-proposal wording, or vice versa; `.claude-tweaks/verify-scope.json` written automatically at the threshold instead of staged; an `onAllowlist: false` escalation — and a staged proposal to *add* the file — for a file already on `flaky.files`, e.g. `tests/flaky.test.js` on this step's third run, whose `--baseline` invocation carries no `--scope`, so no declaration is read and nothing matches; a `baseline-flaky … a staged proposal to add it is pending review` CAVEAT on a run with no anchored `--run` directory, where nothing was staged.

### 11. Verify a checkout with a known failure baseline against the integration branch
- **URL:** `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --run "$PIPELINE_RUN_DIR" --cmd tests="npm test" --cmd-env tests=CT_HOOKS_GIT_TIMEOUT_MS=60000 --baseline origin/main --baseline-cmd tests="node --test {file}"` on a Windows dev checkout of this repo, whose suite fails about 350 tests in about 106 files identically at `origin/main`. Run it once as-is, then once after committing a test that fails in a file that passes at base. Then follow each run with `--stamp-status`.
- **Action:** Read the `Baseline:` line, the table's Status cell, any `ATTRIBUTABLE:` / `CAVEAT: baseline-flaky:` lines, `report.json`'s `baselineAdjudicated`, the process exit code, and `--stamp-status`'s `verifiedHead`/`baselineAdjudicated`.
- **Should feel:** The runner, not the agent, does the by-file comparison against base that used to be hand-run. A branch that adds no failure gets a verified stamp, so `/claude-tweaks:test` and `/claude-tweaks:review` Step 1.5 stop re-running a ~16-minute suite that can never exit 0 here. A branch that does add a failure is named, with no reading of the log required.
- **Should understand:** Adjudication runs only when a check fails. It compares against the merge-base of HEAD and `origin/main` (an adjudicated run's `Baseline:` line names its sha), not `origin/main` itself, so a failure already present where the branch forked stays baseline even after `origin/main` fixes it.
  - **Where a pipeline caller learns to pass these flags (#3933).** `verification.md`'s "Not skipped — execute" block, the one a caller reads right before running the suite, itself says that a pipeline site (`$PIPELINE_RUN_DIR` set) appends `--baseline`/`--baseline-cmd` (and any `--cmd-env`) for each check the declaration gives a `retry.{check}` template. It points at the Baseline adjudication section for the exact form. So a caller following that block alone runs this step's adjudicating invocation, not the bare `--cmd` form, which cannot adjudicate and so can never exit 0 on this checkout.
  - **The scoped form (#3511).** The same adjudication runs on a scoped invocation (Step 8) given `--baseline origin/main` and no `--baseline-cmd`: each declared suite takes its per-file template from the declaration's `retry.{suite}`, and a `--cmd-env` bound to a declared-only suite reaches its base and isolated runs too. A scoped failure is adjudicated on that one invocation — never by re-running the suite unscoped.
  - **Which file a failure names.** A TAP failure names its file only through its own top-level `location:`/`stack:` keys. A meta-test that spawns its own `node --test` run and quotes that child's output in its assertion message carries the child's whole TAP document inside its `error:` value, temp-dir paths and all. Those paths are the child's, never this run's (#3153). Every path is also read against the checkout its log came from, so a path absent from that checkout never names a failing file.
  - **The comparison.** Each failing test file that exists at base runs once at the base commit, in a scratch detached worktree that is removed afterwards, and once in isolation at HEAD. A file absent at base runs neither way and is attributable outright. A test file that fails to load at both counts only when the two logs match once roots and durations are removed, so the error has to be the same one.
  - **Load failures need more than a matching log.** The file must also be unchanged since base and fail at the same sites at base and in the full run (a load failure at `1:1` never covers a file-scoped hook failure). HEAD must also resolve no dependencies: no `node_modules` at its directory or any ancestor, and no `NODE_PATH`, inherited or from the check's own `--cmd-env`. The scratch worktree carries no untracked dependencies, so on a checkout with dependencies installed a load failure is always attributable.
  - **baseline:** the isolated HEAD run fails only tests the base run fails, compared by suite path (`X > works`). Each path occurs once in its tree, names are read byte-for-byte, and a malformed tree is no evidence. A new failing test beside an old environment failure, a test moved between suites, or a loop-generated sibling is therefore not covered. A base log with a timed-out or cancelled test is no evidence either.
  - **Waived failures:** a file whose full run also failed extra tests under load still counts as baseline when the isolated run shows a `✔` pass for every extra one. A test that never ran proves nothing. Such a file prints a `baseline-in-isolation` CAVEAT naming the waived tests.
  - **What it cannot see:** a test that already fails at base covers any failure of that same test at HEAD, whatever the reason. A runner-level `ℹ Error:` diagnostic disqualifies a log, and a parent counts only for its own failure, not an inherited one.
  - **flaky:** the isolated run exited 0, its log accounts for itself with nothing cancelled, and it actually ran tests (pass > 0, fail = 0). Every full-run failure must also show its own `✔` pass there. Each flaky file prints a CAVEAT.
  - **attributable:** everything else, including any file absent at base.
  - **Exit code and table.** The exit code is the gate. An adjudicated pass exits 0 and shows `pass (baseline-adjudicated vs origin/main: {b} baseline, {f} flaky)` in the table. Meanwhile `report.json`'s `pass` and each check's `exitCode` stay raw.
  - **The verdict in report.json.** `report.json` also records the exit-code verdict as `effectivePass` (#3316), beside the raw `pass`. A consumer reads it there rather than re-deriving it from `baselineAdjudicated`.
  - **New and fixed (#3313).** An eligible run also prints `Baseline: {n} new, {m} fixed` and a `FIXED:` line per file that fails at base but passes at HEAD, and records `new`/`fixed` (and `fixedReason` when `fixed` is `null`) in `report.json`; neither changes the verdict, exit code or stamp. `fixed` costs one extra full base run per failing check, so a caller that never reads it passes `--no-baseline-fixed` (with `--baseline`) to skip the run: `fixed` is then `null` with a `fixedReason`. `fixed` is also `null` when no failing file is classified baseline (the base run is skipped) or the base run proves nothing, and stdout then reads `Baseline: {n} new, fixed not computed — {fixedReason}` instead.
  - **Which tests are new (#3723).** `report.json`'s `baselineAdjudicated.attributedTests` names, per attributable file, the tests that are new. Each test is a suite path, outermost suite first. For a file present at base they are the isolated HEAD run's failures that base does not fail; for a file absent at base they are the full run's own failures, with inherited TAP parents dropped. Each entry also records `headFailing`/`baseFailing` and `absentAtBase`, the new tests that exist nowhere at base (`null` when the base run passed). A file gets an entry only when its per-test identity is known (both trees well-formed, the logs accounted). The field is report-only: no verdict, exit code or stamp reads it.
  - **Stamp.** The stamp gains a `baseline` key (no legacy bare-SHA twin), and `--stamp-status` reads `match: false`, `verifiedHead: true`, `baselineAdjudicated: true`. The stamp means "this branch added no failure", not "the suite is green"; hosted CI stays authoritative.
  - **The marker carries forward.** A later scoped or `none` run anchored on that pass's `fullSha` (Step 8) copies the same `baseline` key onto its own stamp, so `--stamp-status` keeps reading `baselineAdjudicated: true` until a full run writes a fresh stamp.
  - **Interrupting the run.** While the scratch worktree exists, a Ctrl-C (`SIGINT`) or `SIGTERM`/`SIGHUP` removes it before the process exits with that signal's conventional code (130/143/129) — run `--baseline` against a check whose `--baseline-cmd` sleeps, send the signal mid-run, and `git worktree list` shows nothing left afterward. The handlers are registered only while the worktree exists and deregistered once adjudication finishes, so a clean run never leaks one. On an uncatchable kill (POSIX `SIGKILL`/`kill -9`, Windows `TerminateProcess`, or any kill before this existed), the worktree survives — the *next* `--baseline` run whose ref resolves (whatever its checks' outcome, even one that never reaches adjudication; a usage error or an unresolvable ref exits 2 first and names nothing) checks `git worktree list` for a `ct-verify-base-*` scratch and, if one is registered, names it on stderr with the exact `git worktree remove --force {path}` command, and leaves it in place rather than sweeping it — a sibling session's own in-flight scratch would look identical.
  - **Limits beyond test identity.** Only test failures are adjudicated: a check whose non-zero exit also comes from something else (a coverage threshold, a post-step chained into the command) while its test failures are all baseline reads as a pass. The base-contains-HEAD refusal checks ancestry, so a base that absorbed this branch through a squash merge is not caught.
  - **When it refuses.** Anything it cannot classify with evidence prints `Baseline: not adjudicated — {reason}` and exits 1. That covers:
    - a fail-fast skip
    - a spawn error
    - a missing `--baseline-cmd`
    - a log with no extractable file, or one outside the spec/TAP families
    - unparsed counts, or spec entries that do not add up to `ℹ fail` plus `ℹ cancelled` (a cancelled test is listed but not counted as failed)
    - a TAP block naming no file
    - a base that already contains HEAD
    - a ref sharing no merge-base with HEAD (`no merge-base between HEAD and {ref} — …`; on a shallow clone that never fetched the fork point, the reason names `shallow clone, fork point not fetched` instead, #3810)
    - a check with no numeric exit (signal-killed)
    - an unreadable check log
    - a spec failing entry naming no test file
    - a failing entry or TAP block naming only paths absent from this checkout (`absent-from-checkout: …`)
    - a working directory that does not resolve under the repository root as git spells it
    - an adjudicator error (for example, the scratch worktree could not be created)
  - An unresolvable ref exits 2 before anything runs.
  - Any other malformed baseline flag also exits 2 before anything runs: an empty `--baseline` value, `--baseline` with no `--baseline-cmd` (without `--scope`), a `--baseline-cmd` whose template lacks `{file}` or that names no `--cmd` (without `--scope`), and either flag beside `--stamp-status` or `--changed-files`. Under `--scope` (#3511) `--baseline-cmd` is optional (a declared suite with no `--baseline-cmd` falls back to the declaration's `retry.{suite}` template), so those two cases are replaced by two scoped ones: a `--baseline-cmd` that names no `--cmd` or declared suite, and `--baseline` with no `--baseline-cmd` and no declared `retry` template.
- **Red flags:**
  - An exit 0 while any `ATTRIBUTABLE:` line printed.
  - A pass over a failure in a file that does not exist at base.
  - A pass when `--baseline` names HEAD itself.
  - An `ATTRIBUTABLE:` line for a file that already failed at the fork point, only because `origin/main` has since fixed it — or a `report.json` `baselineAdjudicated.base` naming `origin/main`'s tip rather than the merge-base (#3810).
  - A file covered as "baseline" when HEAD fails a test in it that base does not.
  - A flaky verdict with no CAVEAT line.
  - A scratch worktree left behind with no stderr line naming it and the `git worktree remove --force` command.
  - A scratch worktree still registered after a `SIGINT`/`SIGTERM`/`SIGHUP` sent mid-run, or a process that exits with any code other than that signal's conventional one (130/143/129).
  - A stale `ct-verify-base-*` worktree silently removed by a later run instead of only named — sweeping it risks deleting a sibling session's own live scratch.
  - `report.json`'s `pass` rewritten to `true`.
  - `report.json`'s `effectivePass` disagreeing with the process exit code.
  - An `ATTRIBUTABLE:` line naming a temp-dir path (`/private/var/folders/…/verify-cli-test-…/tests/env.test.js`) or any path that does not exist in the checkout.
  - An `ATTRIBUTABLE:` line for a file whose base run fails the same tests, only because a failing TAP point's `error:` text quotes a spawned child's timeout. Only that point's own top-level YAML keys (`failureType:`) say whether it timed out (#3153).

### 12. Bound a hung check with --cmd-timeout

- **URL:** `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --cmd tests="node -e \"setInterval(() => {}, 1000)\"" --cmd-timeout tests=2000`
- **Action:** Point a check at a command that never exits, with `--cmd-timeout` naming a bound well under what you're willing to wait.
- **Should feel:** The run ends on its own — no hung terminal, no orphaned process to hunt down and kill by hand.
- **Should understand:** On expiry the runner kills the whole process tree the shell spawned, not just the immediate shell — a negative-pid `SIGKILL` to the POSIX process group (the check is spawned `detached: true` precisely so this group exists), or `taskkill /pid <pid> /T /F` on win32 — and records the run as `{exitCode: null, timedOut: true}`. A `null` exit code is never adjudicated and never passes, so the table shows `fail` with a `timed out after {n}s` summary in place of a blank one, and the run writes no pass stamp. `--cmd-timeout <name>=<ms>` is repeatable (one per check), and a check with no `--cmd-timeout` behaves exactly as before — unbounded.
- **Red flags:** The process (or a descendant it forked) still running after the runner exits; a timed-out check's `report.json` entry missing `timedOut: true`; a pass stamp written despite a timeout.

### 13. Watch a hung baseline per-file run stay timed-out, not silently passed

- **URL:** Step 11's invocation, with `--cmd-timeout tests=5000` added, against a file that hangs only at the base commit (not at HEAD)
- **Action:** Read the `ATTRIBUTABLE:` line for that file.
- **Should feel:** A hang during baseline adjudication ends the same way a hang in the main run does — bounded, not a wedged pipeline.
- **Should understand:** Baseline per-file base/isolated runs (Step 11) reuse the check's own `--cmd-timeout` as their bound — there's no separate flag for it. A per-file run that times out is no evidence either way (it proves nothing about whether the file fails at base), so the file stays `attributable`, but the line names why: `ATTRIBUTABLE: {file} (timed out — base/isolated run exceeded its --cmd-timeout bound)` rather than a bare file name that reads identically to an ordinary attributable failure.
- **Red flags:** A timed-out per-file run read as "passed at base" (it proves nothing — it must stay attributable); an `ATTRIBUTABLE:` line with no timeout note when the underlying run actually timed out.

### 14. Merge the integration branch mid-run, then re-verify only your own delta
- **URL:** after Step 8's first (full) run anchors `fullSha` on a feature branch, `git merge --no-ff main` (bringing in files the branch never touched), commit one own-work change, then re-run Step 8's exact `--scope … --integration-branch main` invocation
- **Action:** Read the `Scope:` line, the `merge-narrowed:` line directly under it, and `report.json`'s `scope.mergeNarrowing`
- **Should feel:** Paying only for what this branch changed — a review-fix re-verify after pulling in the integration branch costs the branch's own suites, not every suite the merge touched.
- **Should understand:** When a usable anchor exists and a merge commit after it has `main` history as its other parent, the runner drops every changed path whose content at HEAD equals `main`'s tip and prints `merge-narrowed: {k} merge-identical path(s) excluded (identical to {ref})`; `report.json` records `scope.mergeNarrowing: {ref, excluded, excludedFiles}` (`null` when no qualifying merge was found). The anchor stays the base — narrowing filters the file list, it never re-bases — and nothing changes for any caller: the scoped invocation already passes `--integration-branch`. Kept regardless of content: working-tree edits, a merged-in file the branch then edited, and every path the branch touched before its last full pass (so a conflict resolved in `main`'s favour is still verified). Without `--integration-branch`, or with no such merge, the set is exactly `anchor..HEAD`. A tool-scoped declaration still substitutes the anchor as `{base}`, so narrowing saves nothing there. An explicit `--base` that contradicts the anchor still exits 2, and its message now points at this narrowing instead of implying `--integration-branch` overrides the anchor. The narrowed set is what gets recorded: a narrowed run's stamp `changedFiles` and `report.json`'s `scope.changedFiles` list only the paths left after narrowing, so the excluded ones are read from `scope.mergeNarrowing.excludedFiles`, never from the stamp.
- **Red flags:** A merged-in, unchanged file still selecting its suite after a qualifying merge; a path the branch deleted or edited before its anchor appearing in `excludedFiles`; a narrowed run whose stamp `fullSha` or `report.json` `scope.base` moved off the anchor; narrowing applied on a run with no `--integration-branch`; a narrowed set that went empty with no `merge-narrowed:` line explaining why nothing ran.

### 15. Declare a known pre-existing failure, then watch an unaccounted failure refuse the waiver
- **URL:** add `"preExisting": ["tests/known-shallow.test.js"]` to Step 8's declaration and run Step 8's `--scope` invocation, first with only that file failing (a `node --test` spec/TAP log), then with that file failing plus one failure whose log entry names no test file (e.g. `test at tests/helper.js:2:1`), and finally with a pytest suite whose summary log names only that file (a jest/vitest suite whose `FAIL` files fully account for `Test Suites`/`Test Files` failed, with none of Step 10's other unattributed signals, adjudicates like the first run, #3480)
- **Action:** Read the `Pre-existing:` line under the table, the process exit code, `report.json`'s `preExistingAdjudicated`/`effectivePass`, and `--stamp-status`'s `preExistingAdjudicated`
- **Should feel:** A shallow-clone precondition failure the project already declared stops blocking the stamp, without a re-run. The waiver is narrow, though. It covers only failures the runner can prove are the declared ones, never a failure it cannot name.
- **Should understand:** The first run exits 0. It prints `Pre-existing: adjudicated — 1 failing file(s) covered by the declared preExisting allowlist: tests/known-shallow.test.js`, keeps `report.json.pass` raw (`false`) beside `effectivePass: true`, and writes a stamp carrying `preExisting: {declared, matched}`. The second run fails (exit 1). It prints `Pre-existing: not adjudicated — unattributed-failures: 1` (#3481): every named file is covered, but the log also carries a failure no named file accounts for, so the named list is a known undercount. This is the same accounting flaky retry applies in Step 10. The third run also fails, with `no-accounting-guard: summary`, because a pytest log's collection `ERROR`s sit outside every `FAILED` line, so its file list has no accounting guard at all. A jest/vitest log is accounted per dialect (#3480), so a fully accounted one adjudicates and a jest/vitest log carrying any of Step 10's unattributed signals refuses with `unattributed-failures: {N}`. That includes a global setup/teardown that threw, which matters most here because this mechanism re-runs nothing. Refusal reasons are checked in order across every failing check: `no-parse`, then `no-accounting-guard: {family}`, then `unattributed-failures: {N}` (summed across checks), then `runner-error` (a Node `ℹ Error:` line the failure count cannot see), then `unlisted: […]`. `report.json` records each as `{declared, eligible: false, reason}`. A covered or `unlisted` run (#3313) also prints `Pre-existing: {n} new, {m} fixed` and a `FIXED:` line per allowlisted test file that did not fail (advice to drop its entry only if its failure is not environment-specific), computed only on a scope-`full` run with no fail-fast-skipped check (otherwise `fixed` is `null` with a `fixedReason`, printed `Pre-existing: {n} new, fixed not computed — {fixedReason}`); neither changes the verdict.
- **Red flags:** A run that exits 0, or writes a stamp, while an unattributed failure, a runner-level error line, or a pytest log sits behind a fully covered file list. A refusal reason missing from the `Pre-existing: not adjudicated — …` line. `effectivePass: true` on a refused run. A fully attributed, fully covered run (a jest/vitest one included) that no longer adjudicates.

### 16. Declare the files a check regenerates, so a passing run still stamps clean
- **URL:** add `"generated": ["next-env.d.ts"]` to Step 8's declaration, where one declared check (a production build, say) rewrites the tracked `next-env.d.ts` on every run. Run Step 8's `--scope` invocation, then `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --stamp-status`, then `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --stamp-status --scope .claude-tweaks/verify-scope.json`. Repeat once with a second, unrelated uncommitted edit in the tree.
- **Action:** Read `{git-dir}/claude-tweaks-verify-pass.json`, `report.json`'s `dirty`, and both `--stamp-status` lines.
- **Should feel:** A check that dirties a known file no longer forces a second, pointless run to earn a stamp. The exemption is narrow and auditable: the stamp lists exactly which paths it excused.
- **Should understand:** When every path dirty at the run's start or end matches a `generated` glob (#2987), the stamp records `dirty: false` and lists those paths as `generatedExempt`. `report.json`'s own `dirty` stays `true`, because other readers rely on it meaning "the tree has an uncommitted change". The exemption applies only to a run whose `--scope` names a readable declaration. One dirty path outside the globs and the stamp is dirty exactly as before. A rename counts both its new path and its deleted source, so renaming an ordinary file into a generated path still disqualifies the stamp. The live tree stays dirty after the run, so a bare `--stamp-status` reads `verifiedHead: false`. With `--scope` it re-checks the same exemption against the live tree and reports the paths as `liveGeneratedExempt`, so `match`/`verifiedHead` can read `true` while its `dirty` field still reports the live `true`. `generatedExempt` is what the stamp recorded and `liveGeneratedExempt` is what this call found; the two can differ. A `--scope` that is missing, invalid, or ignored because `--git-dir` names another checkout is reported as `scopeError`, and the status call still exits 0. A glob that would also cover the declaration itself (`**`, `.claude-tweaks/**`), checked against both `.claude-tweaks/verify-scope.json` and the path `--scope` named, is a declaration error: the check run exits 2 before anything spawns. The re-verify gates (`/test`'s Skip-if-recent, `/review` Step 1.5) call `--stamp-status` with no `--scope` today, so they do not apply the live exemption.
- **Red flags:** `report.json` reading `dirty: false` because of the exemption; an exemption granted on a run with no `--scope`; a clean stamp while a dirty path outside every `generated` glob is in the tree; a `**` or `.claude-tweaks/**` entry accepted; a bare `--stamp-status` reading `verifiedHead: true` over a tree the declaration says is regenerated; a `--scope` that could not be read showing `scopeError: null`.

### 17. Split a suite too long for one call into chunks, then compose the verdict
- **URL:** the chunked invocations in `plugin/skills/test/stamp-composition.md`: `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --run "$PIPELINE_RUN_DIR" --scope .claude-tweaks/verify-scope.json --no-stamp --stamp-suite --cmd types="tsc --noEmit" --cmd lint="eslint ."`, then one `--no-stamp --stamp-suite --cmd {suite}=…` call per declared suite, run one after another. Finish with `node "${CLAUDE_PLUGIN_ROOT}/bin/verify.js" --stamp-status --scope .claude-tweaks/verify-scope.json`, and once more with no `--scope`.
- **Action:** Read each chunk's stdout for a `CAVEAT: --stamp-suite recorded no per-suite pass this run — …` line, `{git-dir}/claude-tweaks-verify-suites.json` after each chunk, and `suiteComposed`/`verifiedHead`/`match` in both status lines.
- **Should feel:** A project whose declared checks take longer than the foreground command cap can still prove HEAD verified, one chunk at a time. No chunk passes silently with nothing recorded behind it.
- **Should understand:** Each chunk is a partial `--cmd` set, so it passes `--no-stamp` and never writes the single full-set stamp. `--stamp-suite` (#3002) writes a per-check record instead: `{sha, dirty, at, reportPath}` keyed by check name, plus `generatedExempt` when Step 16's exemption applied. A check that failed in the chunk has its existing record removed. A fail-fast-skipped check, or one the chunk did not run, keeps whatever record it had. No record is written on a tree dirty outside the declared `generated` paths, when HEAD moved during the run, or when git status could not be read; the CAVEAT line names which. `--stamp-status --scope` composes `suiteComposed: {declared, covered, missing, complete}`. `declared` lists `types` and `lint` when the declaration has them, plus every declared suite. A record counts only at the current HEAD sha, recorded clean, with the live tree clean or generated-exempt. `complete: true` makes `verifiedHead` read `true`. `match` stays tied to the single full-set stamp and is unaffected. With no `--scope`, `suiteComposed` is `null` and per-suite records are never read. Usage errors exit 2: `--stamp-suite` without `--scope`, without any `--cmd` (a chunk never runs the declaration's own commands by default), with `--git-dir`, or on `--stamp-status`/`--changed-files`. The re-verify gates (`/test`'s Skip-if-recent, `/review` Step 1.5, a dispatched group's second-call check) call `--stamp-status` with no `--scope` today, so a complete composition does not yet let them skip a re-run.
- **Red flags:** `match: true` with no single full-set stamp, earned from per-suite records alone; a failing chunk whose earlier record for that check survives; a record written on a tree dirty outside every `generated` path; a chunk that records nothing and prints no CAVEAT; `complete: true` while a declared check has no record at this HEAD; chunks run in parallel against the same checkout (the read-merge-write record file is not safe against that); a plain `--no-stamp` run without `--stamp-suite` changing `claude-tweaks-verify-suites.json`.
