# Select the Dispatch Queue with the queue-pull CLI

**Persona:** the maintainer of `/claude-tweaks:dispatch`'s queue, which since #5230 a program produces, not a model reading a 52 KB script. Also the pipeline driver (`drive.js`) once it calls the CLI, and the agent in a `gh`-absent cloud sandbox that has to feed it MCP-fetched files.
**Goal:** get the same `dispatch-groups.json`, `dispatch-exclusions.json` and next pick that the embedded `queue-pull-script.md` and `next-ranking.md` scripts produce, from one command with a fixed exit-code contract.
**Entry point:** `node plugin/bin/queue-pull.js --transport gh` (or `--transport files` with the agent's input files), then `node plugin/bin/queue-pull.js --rank`, under the session whose `CLAUDE_CODE_SESSION_ID` the session-scoped files belong to.
**Success state:** the session-scoped files match what the scripts would have written for the same inputs, including every exclusion entry in order, the fast-lane bundles, the near-duplicate pairs, the cross-PR overlap file, the staged Close proposals and the `AUTO`/`Warning:` lines on the script's own streams. `dispatch-next-pick.json` holds the group the ranking script would pick, or `null`. The CLI exits 0, and its stdout carries only what the script prints.

## Steps

### 1. Pull the queue through gh
- **URL:** `plugin/bin/queue-pull.js --transport gh`; `plugin/bin/lib/dispatch/queue-pull.js` (`queuePull`, `PASSES`)
- **Action:** The maintainer runs the CLI with `--transport gh`. It runs the passes in `PASSES` order, the order the script runs them: truncate (keeping `firing` entries), fetch and the queue-order cache check, `blocked`, grouping and `oversized`, the cache write-back, `not-spec-shaped`, `open-pr`, `target-missing`, `shipped`, `unlanded-blocker`/`malformed-blocker`, `neighbour-in-flight`, then the cross-PR overlap and near-duplicate passes. Every exclusion goes through `appendExclusion`.
- **Should feel:** Like running the script, minus the script. Same files, same lines, no extra stdout to read.
- **Should understand:** Parity with the scripts is the contract, defects included. A behaviour that looks wrong (a stale session file reused, a string `labels` stopping the whole pull) is reproduced on purpose and filed as its own record, never fixed in the module alone. The paginated `gh` list calls get the batched timeout (`GH_BATCH_TIMEOUT_MS`), so a slow but healthy queue fetch completes as it would under the unbounded script.
- **Red flags:** An exclusion file written with anything but `appendExclusion` (earlier passes' entries and the Loop's `firing` entries vanish). A queue fetch that stops the pull with exit 4 on a large, healthy queue, which means the 5 s single-call bound came back.

### 2. Pick the next group
- **URL:** `plugin/bin/queue-pull.js --rank [--priority high|medium|low]`; `plugin/bin/lib/dispatch/queue-pull.js` (`rankNext`, `rankFromFiles`)
- **Action:** The maintainer runs `--rank`. It drops every group with a member under an `oversized`, `firing` or `neighbour-in-flight` entry, takes each group's best member (priority band, then oldest `createdAt`) as its representative, applies the optional `--priority` filter, and writes the top group or `null` to `dispatch-next-pick.json`.
- **Should feel:** Silent and exact. Stdout stays empty, because the pick is a whole group of full records that must not reach an agent's context. The pick matches `next-ranking.md` expression for expression.
- **Should understand:** A missing or unreadable `dispatch-exclusions.json` reads as no exclusions, as the script reads it. An unknown `--priority` value exits 1 instead of quietly picking nothing. Omit the flag when no filter is wanted, because an empty value exits 1 too.
- **Red flags:** Anything on stdout from `--rank`. A pick that differs from the script's for snake_case `created_at` timestamps, which means the alias step was skipped.

### 3. Pull from a gh-absent sandbox
- **URL:** `plugin/bin/queue-pull.js --transport files --queue-raw … --dep-freshness … --open-numbers … --verified-open-deps … --in-flight-raw … --in-flight-claims … --foreign-states …`; `plugin/skills/dispatch/mcp-transport.md`
- **Action:** The **agent** fetches the records through MCP tools and writes each input file (each flag but `--foreign-states` defaults to its session-scoped path; `--foreign-states` has no default, so the agent passes it whenever it wrote a states file). The claims file covers the claim of every record in the in-flight pool file. It then runs the CLI with `--transport files`. The module copies the queue file into the session file before aliasing its timestamps, so the agent's own file is left as written.
- **Should feel:** Like the gh path, with the agent doing the fetching and Node doing the computing.
- **Should understand:** The documented MCP gaps are behaviour. `dispatch-crosspr-overlap.json` is `[]`, `dispatch-linked-prs.json` stays `{}`, and `open-pr`, `shipped` and `unlanded-blocker` cannot fire on this transport. A missing or malformed in-flight pool or claims file stops the pull (exit 4). A queue or dependency-freshness file that parses but is not a JSON array (a wrapper object, a string) is a failed read, never an empty list (#5307): one `Warning: {file} is not a JSON array — treated as a failed read` line, then that file's unparseable path — the queue file stops the pull, the dependency-freshness file stops a warm-cache check or, on a cold cache, leaves no cache written. A bad `--foreign-states` file (the states file the MCP path passes on the call) excludes each foreign-blocked record as `owner/name#N (state unreadable)`, with one fail-closed `ignored (...)` `Warning:` line: the follow-up lookup's own `gh`-absent Warning is not printed a second time (#5304). A lookup that fails for any other reason still prints its own Warning. Under `work-links: native` with `gh` absent, the native-blockers query keeps its documented fallback: one `Warning: … falling back to no native filtering this run` line, and the pull still dispatches (#5309). A missing or malformed `--verified-open-deps` file fails closed (#5311): every unresolved dependency counts as open, so each record it blocks is excluded as `blocked`, one `Warning: verified-open-deps file missing or malformed — every unresolved dependency treated as open (fail closed) this run` line prints when there is at least one such dependency, and no queue-order cache verdict is written. The agent writes a dependency whose `issue_read` fails into that file as open.
- **Red flags:** `--transport gh` silently falling back to files. With `gh` absent it must exit 2 and name the files transport. A claims file covering only the queue's targets, which leaves in-flight neighbours read as not in flight. A wrapper-object queue file that ends in "no candidates" with exit 0 and no `Warning:` line. A blocked record that dispatches after its dependency's state could not be read, or a later pull that keeps holding it from the cache with no `Warning:` line.

### 4. Read a stop and recover
- **URL:** `plugin/bin/queue-pull.js` (exit codes in the header and USAGE)
- **Action:** A pull that cannot continue exits 4 and prints its stop line on stderr. That happens on a corrupt `dispatch-exclusions.json` (left as it was, and no later pass runs), an unreadable `dispatch-groups.json`, a failed queue or open-numbers fetch, or any internal throw, which prints as `queue-pull: <message>`. A fetch the script fails open on prints the script's zero or one `Warning:`/`AUTO` line and the pull exits 0. A failed cache write-back never fails the pull. Unreadable claims are reported once per pull (#5304): one `AUTO` line names every claim the shipped pass and the neighbour-in-flight pass could not read, with both consequences (release time unknown, no downgrade; treated as not in flight), and a pull that stops partway still prints that line once for the claims read so far. When no integration branch resolves (no `integration-branch` key and `git remote show origin` fails), the target-missing pass prints one `Warning: target-missing pass skipped — …` line and excludes nothing, and the unlanded-blocker pass prints its own skip Warning (#5305). A failed linked-PR query prints one `Warning: linked-PR query failed — falling back to no open-PR or shipped-candidate exclusion this run: …` line, naming both exclusions it turns off, since the shipped pass reads its mentions from that same query (#5306). Under `work-links: native`, a failed native-blockers query fails closed (#5309): on `--transport gh` any failure, and on `--transport files` a `resolve-blockers.js` exit 3 (the spawned CLI's code, not the pull's; for example a GraphQL-blocked sandbox with `gh` present), excludes every eligible record as `blocked` with `native blockers (state unreadable)`, prints one `Warning: native dependency query failed — …` line naming the fail-closed consequence, and writes no queue-order cache verdict. The unlanded-blocker pass then has nothing to read and prints no second Warning. A failed per-dependency `gh issue view {dep}` (the live check for a dependency outside the 200-record open pull) fails closed too (#5311): the dependency counts as open, each record it blocks is excluded as `blocked`, one `Warning: gh issue view {dep} failed — dependency #{dep} treated as open (fail closed) this run` line prints per failed view, and no queue-order cache verdict is written. A `Blocked by #0` is never live-checked; the malformed-blocker pass keeps it.
- **Should feel:** Diagnosable from the exit code and one stderr line, with no guessing whether a partial run is safe to rank, and no fetch failure reported twice or not at all.
- **Should understand:** Exit 3 is reserved and never produced: every remote failure either fails open or stops with 4, exactly as the script does. Exit 1 is a malformed invocation and prints the usage.
- **Red flags:** A partial `dispatch-groups.json` ranked after an exit 4. An exit 4 on a fetch the script fails open on. Two claim-read `AUTO` lines in one pull, or none on a pull whose claim reads failed. Named targets excluded as `absent at origin/` — a comparison against an empty branch name.

### 5. Keep the two implementations equal
- **URL:** `tests/bin-lib/dispatch/queue-pull.test.js` (the parity describes); `tests/bin-lib/dispatch/queue-pull-oracle.js`; the oracle's two bash fences, `plugin/skills/dispatch/queue-pull-script.md` and `plugin/skills/dispatch/next-ranking.md`
- **Action:** A **maintainer editing either script** runs the parity suite. It runs the embedded script under PATH shims for `gh` and `git` and the module over the same canned-response table, on both transports and both cache paths, plus every fetch-failure and files-input fault. It then compares the exit status, every session file, the staged proposals, `decisions.md`, the queue-order cache blob, and the reported lines on both streams: the stop, `AUTO`, `Warning:`, cache, `express-lane:` and `resolve-policy:` lines. Other lines on either stream are not compared as text. A change to a pass lands with the matching module change in the same pull request until the removal unit lands.
- **Should feel:** Like a tripwire. A script edit without the module edit turns the suite red, naming the pair and the file that differ.
- **Should understand:** On win32, or without bash 4 or later, the parity describes skip with `no bash oracle`, and the module's in-process fixtures still run. A `queue-pull: <step>:` diagnostic from the module also fails parity when the script's stderr for the same run shows no error, so a module step that throws and carries on cannot pass as equal.
- **Red flags:** A parity failure fixed by loosening `normalize` or the comparison instead of changing the module. The only permitted exception is the four Node-crash-tail lines, which are compared by their fixed prefix.
