# Resolve the Unattended Console in One Process

**Persona:** the agent session running `/claude-tweaks:wrap-up` at `autonomy: unattended` (an internal tooling user) with nobody to answer a prompt, and the operator who reads the run directory afterwards to see what was decided and why. A second, smaller persona: the same session in `auto` mode deciding how much reflect ceremony a small diff deserves.
**Goal:** resolve every staged item of the Review Console in one process instead of one turn each — one decisions block, one `console.json` the archiver can read (#1854), one rendered table — while the merge itself, the memory writes, and the upstream filings stay in the skill; and let a low-surface `auto`-mode run downgrade its reflect depth whether or not a human is watching.
**Entry point:** Phase 4 of wrap-up reaches `review-console.md`'s "Auto-resolution short-circuit" with `consoleAutoResolve` granted; or Phase 1 reaches `ceremony-derivation.md` on an `auto`-mode run whose `config.yml` still says `ceremony-profile: standard`.
**Success state:** `console-resolve.js` exits `0` and `{run-dir}/console.json` reads `{resolved: true, mode: 'auto-resolve', …}`, `decisions.md` carries a `Console auto-resolved {n} item(s)` header plus one line per item, and the printed table shows every row stamped `AUTO-RESOLVED`; or, for the ceremony persona, `config.yml` reads `ceremony-profile: fast-lane` after a test-and-docs-only diff under `mode: auto`, and is untouched under `confirm`/`hybrid`/`interactive`.

## Steps

### 1. Let the mode, not the presence of a human, gate the ceremony downgrade
- **URL:** `plugin/skills/wrap-up/ceremony-derivation.md`; `shouldDerive({mode, ceremonyProfile})` in `plugin/bin/lib/dispatch/ceremony-derive.js`
- **Action:** At the top of Phase 1, read `config.yml`'s `mode` and `ceremony-profile`; derive only when `mode` is `auto` and the profile is still `standard`, then write `fast-lane` through `set-config.js` when the diff touches zero production files.
- **Should feel:** The 12-minute full-mode reflect on a `size:low` one-file fix is gone; the downgrade fires because the lever was never a question in `auto` mode, not because a dispatch marker happened to be set.
- **Should understand:** Under `confirm`, `hybrid`, and `interactive` the Manifesto presented `ceremony-profile` as a real question, so its value may be a human's answer and is never clobbered; a standalone wrap-up has no `config.yml` and never derives. The escape hatch below Reflect is still the only path back up to `standard`. Shipped prompt prose — markdown under a `skills/`, `agents/`, or `commands/` directory, including a skill named `test` — counts as a production file, so a diff that edits skill or agent prose never reads as docs-only (#3477, `isPromptProsePath`); `docs/**` and a materialized `work/{n}-spec.md` still do.
- **Red flags:** A `DISPATCH_HEADLESS` check reappearing in `ceremony-derivation.md` (`tests/ceremony-derivation-mode-gate.test.js` pins its absence); a `confirm`-mode run whose `config.yml` changed under it; a run whose diff edits `plugin/skills/**/*.md` or `plugin/agents/*.md` logging `Ceremony profile derived from diff: low-surface` (`tests/bin-lib/dispatch/ceremony-derive.test.js`'s AC1.1 case pins the opposite).

### 2. Run the resolver once, and read its exit code before anything else
- **URL:** `node "${CLAUDE_PLUGIN_ROOT}/bin/console-resolve.js" --run "$PIPELINE_RUN_DIR" --policy console-auto` (append `--dry-run` on a dry-run wrap-up)
- **Action:** Invoke it exactly where the short-circuit section places it, after the ceiling check.
- **Should feel:** One command replaces a loop of render-log-write turns; the table it prints is the console, every row already resolved.
- **Should understand:** The CLI re-checks the ceiling itself — run config over project policy, a missing or unreadable policy reads `supervised` — and exits `4` unless it is `unattended` — a resolver that would resolve a console at `supervised`/`trusted` would silence a stop the auto-mode contract lists as never silenced; exit `4` routes to the ordinary "Present a real stop". Exit `5` never asks, because it only arises after the ceiling check passed and an `unattended` console never asks, human present or not (IL-167). It means either a console was already rendered on the PR and is waiting for a human (the CLI never clobbers that file), which follows `_shared/console-on-pr.md`'s Headless conclusion (report `pending-review` with the PR URL), or `console.json` will not parse, which stops and reports the CLI's stderr like exits `2` and `3`. Exit `2` (malformed invocation) and `3` (`--run` not anchored under the main checkout) are HARD-GATE failures: an unattended run has nobody to answer a real stop, so it stops and reports the CLI's stderr. Exit `0` means resolved; a second run on an already-resolved directory re-prints the stored table and writes nothing; `--dry-run` prints without writing anything, `console.json` included. `tests/console-resolve-conformance.test.js` pins the single call site inside the short-circuit section and this exit-code vocabulary (4, 5 routed to the Headless conclusion and never to an ask, and 2-and-3 as HARD-GATE) in `review-console.md`.
- **Red flags:** A `console.json` appearing after a `--dry-run`; a `supervised` run whose decisions block says `at unattended`; two `Console auto-resolved` headers in one `decisions.md`; an `AskUserQuestion` headed "Review Console" instead of this command, or after its exit `5` — `pre-tool-use.js` denies it at `unattended` and names this command (`follow-a-review-console-ask-deny-3712.md`, #3712).

### 3. Read the resolutions the way the skill does — stance per section, merge computed but never executed
- **URL:** `plugin/bin/lib/console/resolve.js` (`SECTION_MAP`, `SECTION_STANCES`); the printed table; `jq .merge "$PIPELINE_RUN_DIR/console.json"`
- **Action:** Execute the returned resolutions through the normal "On approval" steps, per the map `review-console.md` states: `apply` on a Pending-review item (a patch via `git apply`, a staged `.md` proposal the same way) → the staged-items step; `apply` on a queue-write or memory item → the queue-write / memory steps (the refused-proposals check still runs first); `approve` → the skill, doc, journey, configuration and reference-repair steps; `filed` → the upstream-filing step; `stale` → the patch step's `Invariant:` re-derivation; `keep-staged`, `pending` and `refused` → retained, listed in the closing pointer, never applied; then the merge half per `merge.resolution`. The `keep-staged`/`pending` rows also print after the table as a `Needs a human` block, which is carried verbatim into the `PushNotification` and `/flow`'s Pipeline Summary and resurfaced at later SessionStarts until acknowledged. That follow-through is its own journey: `review-what-an-unattended-console-left-open-3370.md` (#3370).
- **Should feel:** The same decisions a human's "Approve all" would have made, in one pass — with the one documented divergence that `unattended` files upstream feedback instead of leaving it unchecked (#347), and with refused proposals still untouched by any lever.
- **Should understand:** The run's staged patches are checked first as one stack, in apply order (`_shared/staged-patch.md`'s Stacked check — a patch re-derived onto an earlier one applies at its position, though not alone), and a patch resolves to `stale — re-derive from Invariant:` when it does not apply at its position, never applied blind (#3290). Low-confidence and Contested findings resolve to `keep-staged`: those rows have no Approve-all default, so the file is retained and nothing is applied. A proposal a `REFUSED` line in `decisions.md` names resolves `refused`; an `sdd-ruling-*` item ratifies (`apply`) only when its staged header shows it safe — `Defers: no`, or a deferral with exactly one valid `Defer-reason:` — and otherwise resolves `pending` (`sdd-ruling-deferral-no-defer-reason` / `sdd-ruling-unclassified` / `sdd-ruling-unreadable`), never auto-ratified (#3880, #4049); an unrecognized staged prefix lands in Pending review as `pending`, never auto-approved — since `stage-item.js` refuses an unmapped id (exit 2, `refused (unmapped-prefix)`), this now covers only a hand-placed or legacy file. A `.shadow-dup` copy never lands there (#3946): one byte-identical to its anchor resolves `dismissed` under Dismissed duplicates (`shadow-dup-duplicate`; informational, executes nothing, the copy stays in `staged/`), and any other copy resolves `apply` under Queue writes, where `review-console.md`'s "On approval" step 7 files it as a `needs:definition` backlog record through `shadow-dup-proposal.js`, quoting the copy verbatim. The quote sits in a fence, and the section parsers skip headings inside a fence (#4169), so a spec-shaped copy never lends the filed record its own Deliverables or Acceptance Criteria — `shapeGate` judges the record's own shape (Open Question, no Acceptance Criteria). That covers `shadow-dup-divergent` (a real, different proposal recovered from a clobbering write) and `shadow-dup-collision` (no comparison was possible — the anchor was missing or unreadable, or the shadow copy's own content couldn't be read). A whitespace- or CRLF-only difference is divergent, so a divergent copy is never dismissed. The curation engine's own `claude-md`/`decision-records` registry rows (`wrap-up-claude-md-`/`wrap-up-adr-` staged prefixes, #2773) resolve `approve` through Configuration updates like any other config proposal — SECTION_MAP recognizes them explicitly rather than falling through to the unmapped-prefix case. Reflect's wrap-up insights table (`staged/wrap-up-reflect-insights.md`) resolves `approve` under its own Reflection insights section (#3926) — `review-console.md`'s "On approval" step 10 applies each row's recommended destination, with D4/D5 rows informational — so an unattended wrap-up no longer lists it under Needs a human. A curation-engine finding read from `engine-state.json` (not a `staged/` file) is labelled `{row}:{targetPath}` — e.g. `skills:.claude/skills/x/SKILL.md` — so each applied or staged row names the file it touched and two findings on one row stay distinct; an older `engine-state.json` whose findings carry `target` instead still labels by that, and a finding with neither takes the row's own `target` (#3389). The merge half honours three carve-outs — a `merge-check` verdict of `needs-human` in `decisions.md` (both the auto-merge short-circuit and the dispatch auto-merge gate log it), any group member lacking both `auto:merge` and an `auto:merge-pending` matured past the project's `grant-veto-window-hours`, and (#2299) `dispatch/drain-pr-overlap.md`'s own Auto-merge-gate hold: when `decisions.md` carries a "held — overlaps drain PR #{pr}" line, the resolver re-checks that PR's *live* state (`gh pr view`) rather than trusting the line as permanent — still open resolves `leave-open`, and the same self-heal applies once it merges or closes, so this carve-out (unlike the other two) never persists past the overlapping PR's own lifetime. It resolves to `leave-open` when the grants cannot be read (`grants-unreadable`), the group cannot be resolved (`members-unresolved`), or a drain-overlap PR's state cannot be re-verified (fails closed, same posture as `grants-unreadable`). Members come from the fact pack's `inputs.records`, falling back to the run dir's materialized headers; the labels are always read live. For a dispatched bundle, this same set of carve-outs is mirrored in `flow/multispec-review-console.md` — the parent call's own `merge.resolution` is always discarded (`members-unresolved`, since a bundle's parent has no `work/` headers), so the bundle's actual merge decision is this mirrored prose, not the per-spec resolver call.
- **Red flags:** `merge.resolution: merge` on a run whose `decisions.md` mentions `needs-human`; a `staged/*.patch` reported `apply` while it does not apply at its apply-order position; `staged/` files deleted after resolution (they are retained as revert artifacts); a bundle group merging while `decisions.md` still carries a "held — overlaps drain PR" line for a PR that `gh pr view` shows as still `OPEN`; a `shadow-dup-divergent` or `shadow-dup-collision` copy resolved `dismissed`, or treated as a redundant copy and discarded without being read — it may be the only surviving copy of a finding; a whitespace- or CRLF-only difference reported as `shadow-dup-duplicate`; a filed shadow-dup record whose `shapeGate` passes on the quoted copy's Acceptance Criteria; a `wrap-up-claude-md-`/`wrap-up-adr-` proposal reported `pending`/`unmapped-prefix` instead of `approve`/Configuration updates; `wrap-up-reflect-insights.md` reported `pending`/`unmapped-prefix` instead of `approve`/Reflection insights; an engine row labelled `skills:undefined` (or `docs:undefined`/`journeys:undefined`), or two engine findings on one row sharing an id.

### 4. Confirm the archiver will see a rendered console
- **URL:** `plugin/bin/lib/reconcile/archive-merged.js` (`readConsoleState`); `tests/bin-lib/reconcile/archive-merged.test.js`
- **Action:** After the merge lands, let `bin/hooks.js reconcile`'s archival sweep read `console.json`.
- **Should feel:** The unattended run's directory finally archives like an interactive run's — #1854's `console-never-rendered` skip no longer fires.
- **Should understand:** `readConsoleState` accepts `resolved: true` regardless of `mode`, so the auto-resolve shape needs no reader change; the write is what was missing.
- **Red flags:** A merged unattended run still sitting under `.claude-tweaks/pipelines/` with `console-never-rendered` in the reconciler's report.
