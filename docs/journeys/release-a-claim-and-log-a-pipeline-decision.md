# Release a Claim, Log a Pipeline Decision, Stage a Proposal, Set a Config Lever, Compose a Record Body, and Repair an Unreadable Claim Blob

**Persona:** claude-tweaks skill author (or a maintainer of a project using the plugin) who wants proof that the release-claim, log-decision, stage-item, set-config, compose-record, and repair-claim CLIs actually perform the read → classify → ownership → write (or compose → validate → write, or read → classify → conditional overwrite) sequence `_shared/issue-claims.md`, `_shared/auto-decision-log.md`, `_shared/pipeline-run-dir.md`, and `_shared/work-record.md` document, rather than trusting the contract's prose.
**Goal:** Watch one claim release resolve against a fake `gh` (own claim, foreign claim, already-released claim), one decisions.md append land under the right heading, one staged proposal file land under `staged/` with the right name, one `config.yml` lever downgrade land in place with its lever-enum guards refusing bad input, one JSON payload file compose into a validated work-record body, and one unreadable claim blob repaired (or a repair correctly refused against a live blob) via `repair-claim.js` — confirming all six CLIs' exit codes and output match what Section E, Shared teardown, Settle, the Wrap-Up Review Console's staging call sites, the ceremony escape hatch, `/capture`/`/specify`'s record-creation steps, and `_shared/issue-claims.md`'s "Repairing an unreadable claim blob" procedure actually invoke.
**Entry point:** A terminal at the plugin checkout root (the repo that ships `plugin/bin/release-claim.js`, `plugin/bin/log-decision.js`, `plugin/bin/stage-item.js`, `plugin/bin/set-config.js`, `plugin/bin/compose-record.js`, and `plugin/bin/repair-claim.js`).
**Success state:** Four release outcomes (`released`, `skipped-not-owner`, `already-released`, `unreadable`) each exit with their documented code, one `decisions.md` file carries a schema-valid entry under a named `## /{skill}` heading, one `staged/` file lands with the id-derived filename `stage-item.js` promises, one `config.yml` lever line is replaced in place (with unknown levers and out-of-enum values refused before any write), one `--set` batch replaces three lever lines in a single call while a second batch naming a non-lever is refused whole (nothing written, not even the entries that validated on their own), one payload composes into a body file that is byte-identical to what `recordPayload` alone would have produced, plus a shape-validation failure that writes nothing when `--require-shaped` is set, and one unreadable claim blob is overwritten by `repairClaim`'s `repaired` outcome with a tombstone whose `reason` carries a `repair-force-release:` prefix (so the trail reads as a repair override, never a routine release) while a live claim is left untouched under `refused`.

## Steps

### 1. Append a decision line and inspect the schema — terminal + a scratch run dir
- **URL:** `PLUGIN_ROOT=$(pwd)/plugin && mkdir -p /tmp/ld-journey/.git && cd /tmp/ld-journey && node "$PLUGIN_ROOT/bin/log-decision.js" --run /tmp/ld-journey --status AUTO --step "Section E" --text "released claim on #999" --reversibility high --section "/wrap-up"`
- **Action:** Run with cwd inside the scratch checkout (`/tmp/ld-journey`), not the plugin checkout root — the anchoring guard matches the run dir's checkout root against the one computed from cwd, so invoking `log-decision.js` from the plugin checkout root against a `/tmp/ld-journey` run dir is `not-anchored` by design and exits `3`. Capture the payload root first (`PLUGIN_ROOT=$(pwd)/plugin` — since #418 the payload is the `plugin/` subtree, not the repo root) so the script itself can still be invoked by absolute path after `cd`.
- **Should feel:** Instant and unambiguous — one echoed schema line, no configuration needed.
- **Should understand:** `cat /tmp/ld-journey/decisions.md` shows the line under a `## /wrap-up` heading — `- AUTO {HH:MM:SS} — Section E: released claim on #999. Reversibility: high.` — exactly the shape `_shared/auto-decision-log.md`'s Entry schema documents. Re-run with `--status STAGED --step "Step 3"` and the second line lands under the same heading, below the first — the Append protocol's per-skill grouping, not append-anywhere.
- **Red flags:** A stack trace instead of exit `2`/`3` on a bad invocation; the entry landing outside `## /wrap-up` on the second call (heading-matching regressed); a run pointed at a path with no `.git` above it succeeding instead of exiting `3`; the command run from the plugin checkout root succeeding — that combination is `not-anchored` by design.

### 2. Watch the anchoring guard refuse a worktree-local shadow — terminal
- **URL:** `mkdir -p /tmp/ld-journey/.claude/worktrees/wt && printf 'gitdir: ../../../.git/worktrees/wt\n' > /tmp/ld-journey/.claude/worktrees/wt/.git && mkdir -p /tmp/ld-journey/.claude/worktrees/wt/.claude-tweaks/pipelines/run-a && node plugin/bin/log-decision.js --run /tmp/ld-journey/.claude/worktrees/wt/.claude-tweaks/pipelines/run-a --status AUTO --text "should be refused"`
- **Action:** Run the command — this simulates a run dir that resolves inside a linked worktree rather than the main checkout.
- **Should feel:** Fail loud and specific, not silent — the exact failure mode `[IL-127]` exists to prevent (a worktree-local shadow copy of pipeline state).
- **Should understand:** Exit `3`, stderr names the shadow path and points at `_shared/pipeline-run-dir.md` — the CLI walks up from the run dir to the nearest `.git`; a `.git` FILE (the `gitdir:` pointer above) means a linked worktree of either domain (`.claude/worktrees/` or `.worktrees/`), never the main checkout, so it refuses rather than silently writing a second, orphaned `decisions.md`.
- **Red flags:** Exit `0` and a `decisions.md` created under the shadow path — the guard has regressed to the domain-substring check it replaced.

### 3. Stage a proposal file and inspect its name — terminal + a scratch run dir
- **URL:** `mkdir -p /tmp/si-journey/.git && echo "proposal body" > /tmp/si-proposal.md && cd /tmp/si-journey && node "$PLUGIN_ROOT/bin/stage-item.js" --run /tmp/si-journey --id leftover-my-slug --file /tmp/si-proposal.md`
- **Action:** Same cwd-inside-the-scratch-checkout discipline as step 1 — `stage-item.js` anchors `--run` the same way `log-decision.js` does. `--id` is the caller's own descriptive id (mirrors `_shared/console-on-pr.md`'s `{kind}-{n}` scheme, e.g. `leftover-{slug}`, `polish-suggestion-{n}` — the CLI itself accepts any safe filename stem, not only that exact shape); `--file` is a path the caller already composed the proposal body into.
- **Should feel:** One command, no template engine — the CLI copies content, it doesn't compose it.
- **Should understand:** stdout prints the written file's realpath (`/private/tmp/si-journey/staged/leftover-my-slug.md` on macOS — note `/private` even though `--run` was given as plain `/tmp/...`), and `cat` on that path shows `proposal body` unchanged. The extension (`.md`) came from `--file`'s own extension, not from `--id` — the same behavior every migrated call site (`wrap-up/leftover-routing.md`, `flow/polish-execution.md`) depends on to keep their `decisions.md` "Stage path:" lines accurate.
- **Red flags:** A written file whose content differs from the source (a template/formatting step sneaking in); the extension not matching `--file`'s; a relative or `--run`-literal (non-realpath) path on stdout that a caller might string-match incorrectly.

### 4. Watch the same anchoring guard refuse a shadow, and reject an unsafe `--id` — terminal
- **URL:** `mkdir -p /tmp/si-journey/.claude/worktrees/wt && printf 'gitdir: ../../../.git/worktrees/wt\n' > /tmp/si-journey/.claude/worktrees/wt/.git && mkdir -p /tmp/si-journey/.claude/worktrees/wt/.claude-tweaks/pipelines/run-a && node plugin/bin/stage-item.js --run /tmp/si-journey/.claude/worktrees/wt/.claude-tweaks/pipelines/run-a --id smoke-1 --file /tmp/si-proposal.md; node plugin/bin/stage-item.js --run /tmp/si-journey --id "../../etc/passwd" --file /tmp/si-proposal.md`
- **Action:** Run both commands — the first repeats step 2's worktree-shadow simulation against `stage-item.js`; the second targets a valid run dir but names an `--id` that would escape `staged/` via path traversal.
- **Should feel:** Fail loud and specific on both — no partial write, no silent path-escape.
- **Should understand:** The first exits `3` with the same shadow-path/anchoring message shape as `log-decision.js`'s (naming the shadow path, pointing at `_shared/pipeline-run-dir.md`). The second exits `2` — `--id` must be a plain filename stem (letters, digits, `.`, `_`, `-`, no separators); `../../etc/passwd` fails that check before any filesystem write is attempted, so nothing outside `staged/` is ever touched, whether or not the run dir itself is valid.
- **Red flags:** Either command exiting `0`; a file appearing anywhere under `/tmp/si-journey/.claude/worktrees/wt/.claude-tweaks/pipelines/run-a/staged/` or outside `/tmp/si-journey/staged/` after these two calls.

### 5. Downgrade a config lever in place, and watch the lever-enum guards refuse bad input — terminal + the step-1 scratch run dir
- **URL:** `printf 'mode: auto\nceremony-profile: fast-lane\nspec: 12\n' > /tmp/ld-journey/config.yml && cd /tmp/ld-journey && node "$PLUGIN_ROOT/bin/set-config.js" --run /tmp/ld-journey --key ceremony-profile --value standard; node "$PLUGIN_ROOT/bin/set-config.js" --run /tmp/ld-journey --key spec --value 13; echo "exit=$?"; node "$PLUGIN_ROOT/bin/set-config.js" --run /tmp/ld-journey --key ceremony-profile --value turbo; echo "exit=$?"`
- **Action:** Reuse step 1's scratch checkout (same cwd-inside-the-scratch-checkout anchoring discipline — `set-config.js` anchors `--run` with the very `resolveTarget` predicate `stage-item.js` exports). The first call is the ceremony escape hatch's own invocation shape (`wrap-up/SKILL.md` Phase 1); the second and third are deliberately bad: a config.yml bookkeeping field that is not a policy lever, then a value outside the lever's enum.
- **Should feel:** Surgical — one line changes, everything else in the file is untouched; refusals are instant and name exactly what was allowed.
- **Should understand:** The first call prints `/private/tmp/ld-journey/config.yml (ceremony-profile: fast-lane -> standard)` — the previous value echoed as evidence for the escape hatch's downgrade log line — and `cat config.yml` shows `ceremony-profile: standard` with `mode: auto` and `spec: 12` byte-identical. The second exits `2` naming the canonical Manifesto lever set (`spec:` is run bookkeeping, not a lever); the third exits `2` listing `fast-lane, standard` as the allowed values. Neither refusal touches the file. A worktree-shadow `--run` (step 2's simulation) exits `3` with the same anchoring message shape as its siblings.
- **Red flags:** The success path rewriting or reordering unrelated lines (the writer should replace one line in place); a refusal exiting `2` but still modifying `config.yml`; an unknown key exiting `0` — the lever-enum guard is the whole point (`[IL-127]`'s shadow-write cousin: a silently-accepted typo'd key is a downgrade that never happens); a duplicated lever line surviving a set (the writer must leave exactly one line for the key).

### 5a. Write a whole Manifesto config.yml in one `--set` batch call, and watch the same guards apply all-or-nothing — terminal + a fresh scratch run dir
- **URL:** `mkdir -p /tmp/ld-journey-set/.git && printf 'mode: auto\nscope-creep: add-to-plan\nceremony-profile: fast-lane\nspec: 12\n' > /tmp/ld-journey-set/config.yml && cd /tmp/ld-journey-set && node "$PLUGIN_ROOT/bin/set-config.js" --run /tmp/ld-journey-set --set "mode=hybrid,scope-creep=stop-and-ask,ceremony-profile=standard"; echo "exit=$?"; cat config.yml; node "$PLUGIN_ROOT/bin/set-config.js" --run /tmp/ld-journey-set --set "mode=auto,spec=13"; echo "exit=$?"; cat config.yml; node "$PLUGIN_ROOT/bin/set-config.js" --run /tmp/ld-journey-set --set; echo "exit=$?"`
- **Action:** The batch form (`--set`, #1580) is what `flow/manifesto.md`'s Approval flow actually invokes to write all 13 canonical levers in one call instead of 13 sequential `--key`/`--value` calls. Three calls in sequence: a valid 3-lever batch, a 2-lever batch where the second entry (`spec=13`) names a bookkeeping field rather than a lever, and a dangling `--set` with no value at all.
- **Should feel:** Composing 13 `key=value` pairs into one command line feels no riskier than the single-key form — the same fail-closed guarantees apply to the whole batch at once, not just to whichever lever happens to be checked first.
- **Should understand:** The first call prints one stdout line per lever (`mode: auto -> hybrid`, `scope-creep: add-to-plan -> stop-and-ask`, `ceremony-profile: fast-lane -> standard`) and `config.yml` shows all three new values with `spec: 12` untouched. The second call exits `2` with `--set entry "spec=13": --key "spec" is not a config.yml policy lever (the canonical Manifesto set: mode, scope-creep, ...)` — note the entry is validated and named as part of the `--set` batch, not misattributed to a bare `--key` flag the caller never passed — and `config.yml` is completely unchanged from the first call's result (all-or-nothing: `mode` is not rewritten to `auto` even though it validates fine on its own, because `spec` in the same batch failed first). The third call exits `2` with `--set requires at least one key=value pair` — a dangling `--set` is reported as its own problem, never misreported as a missing `--key`.
- **Red flags:** The second call's rejection touching `config.yml` at all, in any lever (validate-before-write must cover the *entire* batch, not stop as soon as one entry passes); the second call's error message reading as a bare `--key "spec" is not a config.yml policy lever ...` with no `--set entry` prefix (that's the single-key form's wording leaking into batch mode — a regression #1580's fix wave specifically closed); the third call instead printing `--key <lever> is required` (the dangling-flag misattribution #1580 also fixed); `--set` accepted alongside `--key`/`--value` on the same invocation instead of refused.

### 6. Release a claim you own, then one you don't — terminal, `plugin/bin/lib/release-claim/release.js` directly with an injected fake `gh` runner
- **URL:** `node -e "const {releaseClaim}=require('./plugin/bin/lib/release-claim/release');const liveBlob=()=>({content:JSON.stringify({runId:'runA',sessionId:'s',claimedAt:new Date().toISOString(),ttlHours:72,host:'h'}),sha:'sha1'});let blob=liveBlob();const fakeGh=(args)=>{if(args[0]==='api'&&args[2]==='-q')return JSON.stringify({content:blob.content,sha:blob.sha});if(args[0]==='api'&&args[1]==='--method'&&args[2]==='PUT'){blob={content:'tombstone',sha:'sha2'};return '{}';}if(args[0]==='issue'&&args[1]==='comment')return '';throw new Error('unexpected '+args.join(' '));};const a=releaseClaim({owner:'acme',repo:'w',issueNumber:999,runId:'runA',reason:'merged: spec 999',runner:fakeGh});console.log('Run A:',a.outcome,a.calls.join(','));blob=liveBlob();const b=releaseClaim({owner:'acme',repo:'w',issueNumber:999,runId:'runB',reason:'merged: spec 999',runner:fakeGh});console.log('Run B:',b.outcome,'holder='+b.holder,b.calls.join(','));"`
- **Action:** Run from the checkout root. The script wires an in-memory fake `gh` runner (mirroring `tests/bin-lib/release-claim/cli.test.js`'s `deps({...})` harness) into `releaseClaim` directly — no real `gh`, no network. It calls `releaseClaim` twice against the same live claim blob on issue #999: once as `runId: 'runA'` (the holder), once as `runId: 'runB'` (a different caller — the equivalent of a second pipeline run's `--run <run-dir>` producing a different `runId`, since the CLI derives `runId` from `basename(--run)`).
- **Should feel:** Deterministic per caller — the same call means "release" for the owner and "no-op, someone else has this" for anyone else, with no ambiguity in between.
- **Should understand:** stdout prints exactly `Run A: released read,put,comment` then `Run B: skipped-not-owner holder=runA read`. Run A: blob read → tombstone `PUT` carrying the read `sha` → release comment — the same three-call sequence Section E steps 3-6 describe; `plugin/bin/release-claim.js` maps this `outcome` to exit `0`. Run B: `releaseClaim`'s own ownership check reads the blob (`calls` stops at `read`), sees a `runId` that isn't its own, and returns `{outcome:'skipped-not-owner', holder:'runA'}` before any write — no PUT, no comment, no label edit; the CLI maps this to exit `4` and logs `skipped release of issue #999: claim held by run runA` to its own `decisions.md`. An issue already tombstoned (released or swept) instead throws a `404`/`409`/`422` from the `PUT`, which `releaseClaim` maps to `outcome: 'already-released'` (CLI exit `3`) — the comment still posts, so the trail records the outcome even though nothing was overwritten.
- **Should understand (unreadable blob):** When `classified.state` is `'unreadable'` (the blob's content fails `classifyClaimBlob`'s JSON parse — corrupt, truncated, or hand-typed by mistake), `releaseClaim` returns `{outcome: 'unreadable'}` before any write, the same fail-closed posture as `skipped-not-owner` — nothing is overwritten on a guess. `plugin/bin/release-claim.js` maps this to exit `5`, distinct from `skipped-not-owner`'s exit `4`: a corrupt blob can never self-resolve the way a live holder's claim eventually expires, so callers must not retry-and-wait on `5` the way `4` permits. The CLI's exit-5 message points at `_shared/issue-claims.md`'s "Repairing an unreadable claim blob" section — the human/`/tidy`-invoked override procedure for this state.
- **Red flags:** Run B's call producing a `put` or `issue comment` entry in its `calls` array (a successor's claim is never deleted — `_shared/issue-claims.md`'s Ownership rule); `already-released` instead of `skipped-not-owner` for Run B (means the ownership check ran after, not before, the write attempt); a label-removal failure changing the release outcome (labels are best-effort — the release itself never blocks on them); an `unreadable` outcome retried automatically as if it were `skipped-not-owner`.

### 6a. Sweep a stale or closed-issue foreign claim, and watch an open-issue foreign claim still refuse — terminal, `plugin/bin/lib/release-claim/release.js` directly with an injected fake `gh` runner
- **URL:** `node -e "const {releaseClaim}=require('./plugin/bin/lib/release-claim/release');const staleClaimedAt=new Date(Date.now()-100*3600*1000).toISOString();let blob={content:JSON.stringify({runId:'runA',sessionId:'s',claimedAt:staleClaimedAt,ttlHours:72,host:'h'}),sha:'sha1'};const fakeGh=(args)=>{if(args[0]==='api'&&args[2]==='-q')return JSON.stringify({content:blob.content,sha:blob.sha});if(args[0]==='api'&&args[1]==='--method'&&args[2]==='PUT'){blob={content:'tombstone',sha:'sha2'};return '{}';}if(args[0]==='issue'&&args[1]==='comment')return '';throw new Error('unexpected '+args.join(' '));};const a=releaseClaim({owner:'acme',repo:'w',issueNumber:999,runId:'tidy-run',reason:'swept: stale claim',sweep:{issueClosed:false},runner:fakeGh});console.log('Sweep stale:',a.outcome,'sweptFrom='+a.sweptFrom,a.calls.join(','));const liveClaimedAt=new Date().toISOString();const liveBlob=()=>({content:JSON.stringify({runId:'runA',sessionId:'s',claimedAt:liveClaimedAt,ttlHours:72,host:'h'}),sha:'sha1'});blob=liveBlob();const b=releaseClaim({owner:'acme',repo:'w',issueNumber:999,runId:'tidy-run',reason:'swept: issue closed',sweep:{issueClosed:false},runner:fakeGh});console.log('Sweep live open:',b.outcome,'holder='+b.holder,b.calls.join(','));blob=liveBlob();const c=releaseClaim({owner:'acme',repo:'w',issueNumber:999,runId:'tidy-run',reason:'swept: issue closed',sweep:{issueClosed:true},runner:fakeGh});console.log('Sweep live closed:',c.outcome,'sweptFrom='+c.sweptFrom,c.calls.join(','));"`
- **Action:** Run from the checkout root. Same fake-`gh`-runner idiom as step 6, but the caller's own `runId` (`tidy-run`) never matches the blob's holder (`runA`) — the shape a `/tidy` sweep always has (#2090) — and each call passes `sweep: {issueClosed}` instead of relying on the plain ownership check. Three calls: a `'stale'` foreign blob (unconditional), a `'live'` foreign blob on an open issue, and the same `'live'` blob on a closed issue.
- **Should feel:** The sweep only ever breaks a lock the plain ownership check already would have refused to break, and only in the two cases the flag documents — never a third.
- **Should understand:** stdout prints `Sweep stale: released sweptFrom=runA read,put,comment,label:bot:in-progress`, then `Sweep live open: skipped-not-owner holder=runA read`, then `Sweep live closed: released sweptFrom=runA read,put,comment,label:bot:in-progress`. The stale sweep and the closed-issue sweep both release exactly like step 6's own-claim release (`read,put,comment`, plus the label removal), but with `sweptFrom` naming the original holder — the tombstone's own `runId` is still `tidy-run`, never a fake `runA`. The open-issue sweep stops at `read`, identically to step 6's Run B — `sweep` narrows the ownership check, it never removes it: a `'live'` claim on an open issue is refused whether or not `--sweep` (or `sweep.issueClosed`) was passed.
- **Red flags:** The open-issue sweep producing a `put` or `comment` call (a live claim on an open issue must never be swept, flag or not); a sweep release's tombstone `runId` reading as the original holder instead of the sweep run; `sweptFrom` absent on either successful sweep call; `--sweep` demonstrated only via this direct-module path with no corresponding CLI flag — `plugin/bin/release-claim.js`'s own `--sweep` additionally resolves the issue's open/closed state itself via `gh issue view` before passing `sweep.issueClosed` through, which this module-level call bypasses by injecting the boolean directly.

### 7. Compose a record body from a JSON payload, then watch shape-validation refuse an unshaped one — terminal + a scratch payload file
- **URL:** `mkdir -p /tmp/cr-journey && cat > /tmp/cr-journey/payload.json <<'JSON'
{"title":"A title","body":"## Current State\n\ntext\n\n## Deliverables\n\n- [ ] thing\n\n## Acceptance Criteria\n\n1. done","type":"feature","fingerprint":"journey:demo"}
JSON
node plugin/bin/compose-record.js /tmp/cr-journey/payload.json --out /tmp/cr-journey/body.md --require-shaped && cat /tmp/cr-journey/body.md`
- **Action:** Run from the checkout root. The payload file is written first (a real file, not a CLI flag — this is the escaping-safety property #800 exists to buy: quotes, backticks, `$()`, and newlines in `title`/`body` never touch a shell), then `compose-record.js` reads it, composes the body via `recordPayload`, validates it against `_shared/work-record.md`'s spec-shaped-body check (`--require-shaped`), and writes the result.
- **Should feel:** One command, no template engine, no intermediate "read the JSON back out to grab `.body`" step — the CLI is the whole round trip.
- **Should understand:** stdout prints `{"title":"A title","type":"feature","labels":[],"out":"/tmp/cr-journey/body.md"}`, exit `0`, and `body.md` ends with `<!-- work-fingerprint: journey:demo -->` appended to the composed sections — exactly `recordPayload`'s own fingerprint-marker behavior (`bin/lib/issues/record.js`), unchanged by this wrapper.
- **Should understand (validation failure):** Re-run against an unshaped payload — `printf '{"title":"t","body":"## Current State\\n\\nTODO","type":"feature"}' > /tmp/cr-journey/bad.json && node plugin/bin/compose-record.js /tmp/cr-journey/bad.json --out /tmp/cr-journey/bad-body.md --require-shaped; echo "exit=$?"` — prints `exit=4`, stderr lists all three gaps at once (`missing section: ## Deliverables`, `missing section: ## Acceptance Criteria`, `unresolved placeholder marker: TODO`), and `bad-body.md` is never created (`test -f /tmp/cr-journey/bad-body.md` fails) — a shape-validation failure never leaves a partial file behind.
- **Red flags:** `body.md` missing the fingerprint marker or an empty `labels` array when the payload actually included scoring fields (composition regressed to something other than `recordPayload`); the unshaped payload exiting `0`, or exiting non-zero but still creating `bad-body.md` (validation should gate the write, not run after it); gaps reported one at a time across repeated runs instead of all at once in a single stderr block.

### 8. Repair an unreadable claim blob, then watch the same gate refuse a live one — terminal, `plugin/bin/lib/repair-claim/repair.js` directly with an injected fake `gh` runner
- **URL:** `node -e "const {repairClaim}=require('./plugin/bin/lib/repair-claim/repair');const fieldOf=(a,name)=>{for(let k=0;k<a.length;k++)if(a[k]==='-f'&&String(a[k+1]).startsWith(name+'='))return a[k+1].slice(name.length+1);return undefined;};let blob={content:'not json {{{',sha:'sha1'};let lastPut=null;const fakeGh=(args)=>{if(args[0]==='api'&&args[2]==='-q')return JSON.stringify({content:blob.content,sha:blob.sha});if(args[0]==='api'&&args[1]==='--method'&&args[2]==='PUT'){lastPut=args;blob={content:'tombstone',sha:'sha2'};return '{}';}if(args[0]==='issue'&&args[1]==='comment')return '';throw new Error('unexpected '+args.join(' '));};const a=repairClaim({owner:'acme',repo:'w',issueNumber:999,runId:'runA',mode:'release',reason:'corrupt blob',runner:fakeGh});const written=JSON.parse(Buffer.from(fieldOf(lastPut,'content'),'base64').toString('utf8'));console.log('Corrupt blob:',a.outcome,a.state,a.calls.join(','),'| tombstone reason:',written.reason);blob={content:JSON.stringify({runId:'runB',claimedAt:new Date().toISOString(),ttlHours:72}),sha:'sha3'};const b=repairClaim({owner:'acme',repo:'w',issueNumber:999,runId:'runA',mode:'release',reason:'r',runner:fakeGh});console.log('Live blob:',b.outcome,b.state,b.calls.join(','));"`
- **Action:** Run from the checkout root. Same fake-`gh`-runner idiom as step 6, wired into `repairClaim` directly — no real `gh`, no network. Calls it twice against issue #999: once against a corrupt (unreadable) blob in `release` mode, once against a live claim held by a different run, both under the same `mode: 'release'`.
- **Should feel:** Fail-closed and unambiguous — a blob that classifies as anything but `'unreadable'` on the fresh read is never touched, no matter how the operator asked to repair it.
- **Should understand:** stdout prints exactly `Corrupt blob: repaired unreadable read,put,comment | tombstone reason: repair-force-release: corrupt blob` then `Live blob: refused live read`. The corrupt-blob call reads → classifies `'unreadable'` → overwrites with a releasePayload-shaped tombstone whose `reason` field carries the `repair-force-release:` prefix (so the tombstone content and the mirrored issue comment both read as a deliberate override, never a routine `release-claim.js` release) → posts the comment; `plugin/bin/repair-claim.js` maps this `outcome` to exit `0`. The live-blob call's `calls` array stops at `read` — no `put`, no `comment` — because the fresh read classifies `'live'`, not `'unreadable'`, so `repairClaim` returns `{outcome: 'refused', state: 'live'}` before any write is attempted; the CLI maps this to exit `4`. This is release.js's own gate exactly inverted (`'unreadable'` → proceed; everything else → refuse), kept in its own module specifically so the two gates can never drift into inverting each other.
- **Should understand (CLI wiring):** `plugin/bin/repair-claim.js` resolves and warns on run-dir anchoring (`_shared/pipeline-run-dir.md`'s not-anchored/missing cases, same message shape as `release-claim.js`'s) BEFORE calling `repairClaim` — an operator sees "decisions.md not written" before the blob is overwritten, not after — and its `--mode` flag is the one validation gate restricting the module's `mode` argument to `{release, reclaim}`: `repair.js` itself falls through to the `reclaim` (claim-content) shape for any other value, so nothing outside the CLI enforces that restriction.
- **Red flags:** The live-blob call's `calls` array containing `put` or `comment` (a live/stale/tombstone/absent blob is never overwritten by this tool — the inverse-of-`release.js` gate has drifted); a tombstone `reason` without the `repair-force-release:` prefix (the override reads as an ordinary release in the audit trail); `decisions.md`'s warning appearing only after a successful repair instead of before the destructive call.
