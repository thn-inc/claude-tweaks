# Resolve a Policy Key Through the Canonical Read Path

**Persona:** claude-tweaks skill author (or a maintainer of a project using the plugin) who wants proof that policy resolution honors the documented precedence chain — run config, then `policy.yml`, then the factory layer, then schema default — rather than trusting each skill's prose to have re-implemented it correctly.
**Goal:** Watch one key resolve under three configurations and confirm the returned `{value, source}` envelope changes exactly as `plugin/skills/_shared/policy-schema-read-path.md` §Canonical read path says it will.
**Entry point:** A terminal at a project checkout root (any repo with — or even without — a `.claude-tweaks/policy.yml`).
**Success state:** Three JSON objects whose `source` fields read `default`, `policy`, and `run-config` respectively, plus one `renamed-from` resolution proving the alias table is live, plus one `--all` snapshot whose every row carries `{value, source}` decorated with schema metadata, plus one direct-from-`policy.yml` read proving the enforcement hook honors the same alias table the CLI does, plus three `risk-path-globs` reads (unset, valid block, typo'd block) whose answers — `{}` from `default`, the slug-to-glob map from `policy`, and `null` flagged `invalid` — are each distinct, plus one `source: "factory"` read and one refused factory key that resolves as if unset.

## Steps

### 1. Resolve a schema default — terminal
- **URL:** `node plugin/bin/resolve-policy.js autonomy` (from this repo's checkout root — the payload lives under `plugin/` since #418; in another project, substitute the resolved plugin root per `docs/skill-authoring.md`'s plugin-root contract, which already points at the payload and so carries no `plugin/` segment)
- **Action:** Run the command in a checkout whose `policy.yml` does not set `autonomy`.
- **Should feel:** Instant and unambiguous — one JSON line, no configuration needed.
- **Should understand:** `{"autonomy":{"value":"supervised","source":"default"}}` — `source: "default"` with no `invalid` flag means known-but-unset: the value came from `POLICY_KEYS`' schema row, the single place defaults live. Two keys are the exception — `integration-model` and `merge-verification` carry no schema literal, so their `source: "default"` value is *computed* at resolve time (forge detection per `_shared/integration-model.md`; the four-branch derivation ladder in `_shared/policy-schema-coverage.md`'s `merge-verification` coverage block, run by `plugin/bin/lib/merge-verification.js`) — `node plugin/bin/resolve-policy.js --values merge-verification` on this repo prints `merge-when-green`, not an empty line. A third key derives with a different shape: `housekeeping-auto-merge` keeps its schema literal (`false`, the `supervised` base) but its unset value is derived inside `resolvePolicyKeys` from the same pass's resolved `autonomy` — on a `trusted`/`unattended` project the unset key resolves `{"value":true,"source":"default"}` (#580), and `source: "default"` is deliberately preserved so consumers can tell derived from explicit. A fourth key, `merge-authorization`, is excluded from the `policy.yml` source entirely by its own resolver special case (`#715`) — a `policy.yml` value for it is discarded outright, never merely deprioritized. `express-driver-max-lines` (#5224) derives the way `housekeeping-auto-merge` does: its schema literal is `40`, but unset (or malformed, which also carries `invalid: true`) it resolves the same pass's effective `auto-merge-max-lines` value and keeps `source: "default"`, which is how `drive.js` tells a set bound from the default and passes `check --max-lines` only for a set one. The key itself is `policyOnly`, but `auto-merge-max-lines` is not, so a `--run` overlay of `auto-merge-max-lines` reaches its derived value. A computed `integration-model` (or a `merge-verification` that runs its own detection) whose `gh` probe timed out and then failed its one retry still resolves `local-merge`, but its JSON entry gains an additive `degraded: "timeout"` or `"timeout-then-exit"` reason code, and stderr gets one `resolve-policy: degraded — {key}: …` line in every output mode (#4578; see `resolve-the-integration-model-on-a-slow-gh-host-4578.md`). A clean entry keeps exactly `{ value, source }`. `plan-at-specify` (#6056) is the other additive case: set `on` while `planning-decisions` resolves `ask-all`, it answers `value: "off"`, keeps the source that set it (`policy` or `factory`) and gains `conflict: "planning-decisions"`, and stderr gets one `resolve-policy: warning: plan-at-specify is on but planning-decisions is ask-all — …` line in every output mode, exit 0 (see `plan-a-record-while-shaping-it-6056.md`).
- **Red flags:** A stack trace (invocation failures are one stderr line + exit 1); an unknown key killing the whole call — `{"error":"unknown-key"}` must appear per key while siblings still resolve.

### 2. Read a configured value — `.claude-tweaks/policy.yml`
- **URL:** `node plugin/bin/resolve-policy.js autonomy worktree-always` in a checkout that sets both keys
- **Action:** Run against a project whose `policy.yml` sets `autonomy: unattended` and `worktree-always: true`.
- **Should feel:** Like one lookup replacing a grep pipeline — several keys per call, natively typed.
- **Should understand:** `source: "policy"` names the layer that decided each value; `worktree-always` comes back as boolean `true`, not the string `"true"` — coercion happens in the resolver, so no read site re-implements it. A malformed value (e.g. `trust-revert-window-days: banana`) degrades to the schema default with `"invalid": true` rather than silently activating some other source's value. The `--values` scalar form drops that flag from stdout, which still prints the default (`14`) with exit 0, so `--values` names it on stderr instead: one line per requested key holding a present-but-invalid value, `resolve-policy: warning: trust-revert-window-days has invalid value "banana" — using default "14"` (#4141). A shell capture `$(…)` keeps the default and the operator still sees the typo. The JSON and `--all` forms write no such line, because their `invalid` flag already carries it. A `string` key rejects whitespace by default — the rule that catches a mistyped branch name — but a schema row carrying `allowWhitespace: true` (`release-hook`, a shell command, #2253, and the control-mode string keys `deploy-command`, `deploy-live-workflow` and `dev-test-account`, #4609) accepts it, and one matched pair of surrounding quotes is stripped before validation, so `release-hook: "npm publish --access public"` resolves unquoted; a whitespace-only value is still invalid and still falls back to the default. Two keys escape this reporting: `gh-timeout-ms` (#2567) was the first key carrying an **environment-variable layer above `policy.yml`** — `CLAUDE_TWEAKS_GH_TIMEOUT_MS` wins at the key's actual read site (`plugin/bin/lib/shared-primitives.js`'s lazily-resolved, process-memoized `GH_TIMEOUT_MS` getter) — and `git-timeout-ms` (#3051, `CLAUDE_TWEAKS_GIT_TIMEOUT_MS`, the `GIT_TIMEOUT_MS` getter) followed the same shape. This CLI never consults either variable (a set value only counts when it is a positive integer inside the key's own bounds; otherwise the read site falls through to `policy.yml`), so with one set the CLI answers `source: "policy"` (or `"default"` when `policy.yml` does not set the key) while the bound every `gh` or `git` call actually uses is the env var's. Batched `gh` calls outside reconcile (one aliased query over many records, e.g. `dispatch-resume.js`, `resolve-blockers.js`) read the sibling `GH_BATCH_TIMEOUT_MS` getter instead, which is `max(30000, the resolved gh-timeout-ms)`: raising the key above 30000 widens them too, and a lower value leaves them at 30000 (#4815). The exec seams of `console-resolve.js`, `flow/preflight.js`, `release-preflight/pack.js` and `wrap-up/pack.js` read `GH_BATCH_TIMEOUT_MS` for their `gh` calls too, and `console-resolve.js` and `release-preflight/pack.js` read `GIT_TIMEOUT_MS` for their `git` calls; a `node` spawn in those seams keeps a fixed 30000 (#5050). For these two keys, read the effective value from the consumer whenever the variable may be set; `source` still names the layer *this CLI* used, which is no longer always the layer that decided.
- **Red flags:** String-typed integers or booleans in the JSON; a deprecated key name resolving nothing — `dispatch-pick-max-concurrent: 5` must answer a request for `dispatch-batch-size` with value `5` plus `"renamed-from"`, and a pre-#332 dotted line such as `project.maturity: established` must answer a request for `project-maturity` the same way (the seven #332 renames — `review-auto-apply-ceiling`, `auto-merge-max-lines`/`-files`, `project-maturity`, `harness-health-scoped-rule-budget`/`-always-loaded-budget`, `doc-convention-adr` — are all identity aliases; a user's un-migrated `policy.yml` never silently reverts to defaults, and `/claude-tweaks:init --update`'s policy drift check — `auditPolicy` in `plugin/bin/lib/policy-schema.js` — lists each stray line under `renamedKeys` with its replacement); a quoted `release-hook` resolving with its quotes still attached, or an unmatched leading quote (an unterminated `"foo`) being silently stripped instead of left alone; `--values` on a malformed value printing the default with nothing on stderr (the silent degrade #4141 closed), or the warning leaking onto stdout, where it would corrupt a shell capture.

### 3. Overlay a pipeline run's config — `--run`
- **URL:** `node plugin/bin/resolve-policy.js --run "$PIPELINE_RUN_DIR" review-auto-apply-ceiling`
- **Action:** Run with `--run` pointing at an active pipeline run directory whose `config.yml` sets the requested lever.
- **Should feel:** Deterministic layering — the run's Manifesto answer wins over the project default, and `source: "run-config"` says so.
- **Should understand:** This is the whole precedence chain made mechanical: run config beats `policy.yml` beats the schema default, per key, in one call. A run dir that exists but has no `config.yml` yet is not an error — the overlay is simply absent.
- **Red flags:** A nonexistent `--run` dir resolving anything (must exit 1 with a stderr message); the overlay applying to `model-profiles` (policy-only by contract) or `express-driver-models` (#5917, a `policyOnly` block key) or to a `policyOnly` flat key (`control-mode`, #5830, in both directions: a run config neither switches it off nor on; `deploy-command`, `owned-owners`, `trusted-authors`, `risk-categories`, #4609; `verify-suite-slots`, #5119; `express-driver`, `express-driver-wall-clock-minutes`, `express-driver-spend-ceiling-dollars`, #5216; `express-driver-review`, #5222; `express-driver-max-size`, `express-driver-max-key-files`, `express-driver-max-lines`, #5224; `express-driver-max-risk`, #6018; `changelog-max-releases`, #5563; `filed-record-evidence`, `run-filed-record-cap`, #5933; `model-effort`, #5941; `planning-decisions`, #6051; `plan-at-specify`, #6056). Running this step from a **linked worktree** with a *relative* `--run` (or one pointing inside any checkout other than the main one) exits 1 with a "resolves outside the main checkout" message naming the resolved path — that is the anchored-or-outside guard (#1065, the `[IL-127]` shadow-copy protection) working as designed, not a defect; a `$PIPELINE_RUN_DIR` resolved per `_shared/pipeline-run-dir.md` is always anchored under the main checkout and passes, as does any path outside every checkout.

### 4. Snapshot the whole config — `--all`
- **URL:** `node plugin/bin/resolve-policy.js --all`
- **Action:** Run with no key arguments.
- **Should feel:** One call replacing key-by-key enumeration — the whole config, self-describing.
- **Should understand:** Every schema key returns its `{value, source}` envelope decorated with `summary`/`category`/`tier`/`type`/`default` — a JSON `null` default means no default. `--all` composes with `--run`. `--all --values` and `--all <key>` are invocation errors. The deploy, dev and acceptance levers and `trusted-authors` resolve and validate today, but nothing in the plugin acts on them yet. Their summaries open "Not yet used" until the #4608 record that wires each one drops the marker (#4816).
- **Red flags:** A registered key missing from the output; a row missing `summary`/`category`/`tier`; `--all` accepting key arguments; a control-mode key's summary reading as live behavior (no "Not yet used" opener) while no plugin code consumes it.

### 5. Confirm the enforcement hook honors the same alias — `plugin/bin/lib/policy.js`
- **URL:** `node -e "console.log(require('./plugin/bin/lib/policy.js').isWorktreeAlwaysOn(process.cwd()))"`
- **Action:** Run it in a scratch checkout whose `.claude-tweaks/policy.yml` carries only the pre-#602 line `worktree.always: true`; then again with only `worktree-always: true`; then with both present and disagreeing.
- **Should feel:** The same answer every time the intent is the same — how the line is spelled is not a behavioral lever.
- **Should understand:** The PreToolUse worktree gate never calls `plugin/bin/resolve-policy.js` — it reads `policy.yml` directly through `resolveWorktreeAlways`, which consults the same `RENAMED_KEYS` table the CLI does and returns `{on, matchedKey}` rather than a bare boolean. The current name wins whenever it is present, in any file order; the retired spelling contributes only when the current one is absent. That precedence is what lets a `policy.yml` carry both lines during a migration without ambiguity. `session-start.js`'s unconditional SessionStart banner (`claude-tweaks: worktree-always: ON/OFF (matched key: {key})`) calls this same function, so its answer and the gate's answer can never disagree (`docs/incident-log.md` IL-133). One reader sits outside that function: when a session has no `node`, `plugin/bin/hooks.sh`'s `policy_verdict` reads the same two lines in shell, with the same current-name-wins precedence, to decide its PreToolUse deny. It is a copy of `parseFlatLines` and `resolveWorktreeAlways`, so a change to either needs the same change there; `tests/hooks-launcher.test.js`'s `hooks.sh AC9` differential pins the two to one verdict (#5392, `keep-hooks-running-when-node-is-not-on-path-5392.md`).
- **Red flags:** `worktree.always: true` on its own reading as policy-OFF — an un-migrated project would silently lose worktree enforcement with no error anywhere; the retired spelling winning over the current one when both are set.

### 6. Read a block-style key — `risk-path-globs`
- **URL:** `node plugin/bin/resolve-policy.js risk-path-globs`
- **Action:** Run it with no block set; again with a `risk-path-globs:` block in `policy.yml` holding `  auth: [src/auth/**]` and `  migrations:` followed by `    - db/**`; then again with a typo in one row (`  nope: [a]`).
- **Should feel:** A typo is impossible to mistake for "nothing configured" — the three answers look different.
- **Should understand:** Unset reads `{"value":{},"source":"default"}`. A valid block reads the slug-to-glob map with `source: "policy"`, in either list form. A malformed block reads `{"value":null,"source":"default","invalid":true}` — the whole block is rejected, never a partial map, and `null` keeps a consumer from reading it as "no globs" (#4609). `--values` refuses this key as it does `model-profiles`, and `--run` never overlays it. `express-driver-models` (#5917), the third block key, is read by its own parser (`parseDriverModels` in `policy-schema.js`) and differs on unset: it resolves the four driver roles' defaults (`implementer: standard`, `reviewer: capable`, `merge-check: standard`, `acceptance: standard`) with `source: "default"`, never `{}`. A valid block merges its rows over those defaults with `source: "policy"`; a malformed one (an unknown role, `explorer` included, an unknown profile, a repeated role, an inline value) reads `null` with `invalid: true`, and `drive.js` refuses the run at its policy step.
- **Red flags:** A malformed block resolving `{}`, which would silently switch off a safety check; a key after the block (`autonomy: trusted`) swallowed into it; a malformed `express-driver-models` block resolving the role defaults instead of `null` with `invalid: true`.

### 7. Resolve from a linked worktree of a project that gitignores `policy.yml` — terminal
- **URL:** `node plugin/bin/resolve-policy.js --values integration-branch`, run from inside a linked worktree
- **Action:** In a project that keeps `.claude-tweaks/` out of git and whose main checkout's `policy.yml` sets `integration-branch: develop`, run the command from a linked worktree that has no `policy.yml` of its own. Then commit a `policy.yml` into the worktree's branch and run it again.
- **Should feel:** Like the worktree and the main checkout are the same project. The configured branch comes back, and stderr says where it came from.
- **Should understand:** The first run prints `develop`. Stderr gets one line: `resolve-policy: note — {root} has no .claude-tweaks/policy.yml; read the main checkout's {policyPath}`. The same note appears in every output mode, and stdout is unchanged. In-process callers read it from `resolvePolicyConfig`'s `policySource: "main-checkout"` and `policyPath`. Every policy reader goes through one locator, `plugin/bin/lib/policy-file.js`'s `locatePolicyFile`, so every key and every caller gets this fallback, not just this CLI (#4492). On the second run the worktree's own file wins outright and the main checkout's file is not read. Run from the main checkout, the command behaves exactly as before. A root counts as a linked worktree only when its gitdir's parent is exactly `<main>/.git/worktrees`, so a submodule inside a linked worktree keeps its own policy. If no `integration-branch` is set anywhere, `plugin/bin/pr-early-open.js` run from a linked worktree still opens the draft PR against the GitHub default branch, but first warns on stderr: `pr-early-open.js: warning: no integration-branch found (…) — the draft PR targets the GitHub default branch "{base}" from linked worktree {root}`.
- **Red flags:** An empty line from the first run, which is the #4492 defect that sent draft PRs to the default branch. The note printed when the worktree has its own file. A submodule of a linked worktree reading the superproject's policy. A default-branch fallback from a linked worktree with no stderr warning.

### 8. Supply a value from the factory layer — `CLAUDE_TWEAKS_FACTORY_POLICY` / `~/.claude-tweaks/factory-policy.yml`
- **URL:** `CLAUDE_TWEAKS_FACTORY_POLICY="model-stance: economy" node plugin/bin/resolve-policy.js model-stance`
- **Action:** Run it in a checkout whose `policy.yml` does not set `model-stance`; then add `model-stance: max-rigor` to `policy.yml` and run again; then run it with `CLAUDE_TWEAKS_FACTORY_POLICY="deploy-command: echo hi"` and request `deploy-command`. Put the same text in `~/.claude-tweaks/factory-policy.yml` instead of the variable to see the file path.
- **Should feel:** Like a user-wide default that every repository inherits, and that a repository can always override without anything being said twice.
- **Should understand:**
  - The first run prints `{"model-stance":{"value":"economy","source":"factory"}}`. Stderr says `resolve-policy: note — factory layer (env) supplied model-stance`, with `file` or `env+file` as the origin when the file contributed. Precedence is now run config, then `policy.yml`, then the factory layer, then the schema default (#6006). A `factory` source counts as set, exactly like `policy`.
  - The second run answers `max-rigor` from `policy`, and no note prints.
  - `merge-authorization`, `control-mode`, `deploy-command` and `release-hook` are refused. The third run resolves as if the factory layer were silent and writes `resolve-policy: warning: deploy-command is not settable from the factory layer — ignored`.
  - Block keys (`model-profiles`, `risk-path-globs`, `express-driver-models`) merge per row, the repository row over the factory row. A factory block that does not parse, beside a usable `policy.yml` block, leaves the repository's rows in force and writes `resolve-policy: warning: {key} has a malformed block in the factory layer — ignored, using the repository's rows` in every output mode.
  - An invalid flat factory value resolves the schema default with `invalid: true`. Only `--values` names it on stderr, as `resolve-policy: warning: {key} has invalid value "{raw}" in the factory layer — using default "{default}"`; the JSON and `--all` forms write no such line, as in step 2.
  - Under `tools/run-tests.js` and `tests/helpers/tmp-dir.js`, `CT_FACTORY_POLICY_FILE` points the file at a path that does not exist, so a developer's own factory file never reaches a test run.
  - The full rules are in `_shared/policy-schema-read-path.md`'s `## Factory layer`.
- **Red flags:**
  - A refused key taking its factory value.
  - A factory value overriding a `policy.yml` value.
  - A factory value reported as `source: "default"`, which would re-run forge detection or derivations meant only for unset keys.
  - A factory-sourced invalid value warning as if `policy.yml` held it.
  - A malformed factory block marking a usable `policy.yml` block invalid, or being dropped with no stderr line.
  - A test run that changes when `~/.claude-tweaks/factory-policy.yml` exists.
