# Verify a Wrap-Up Run's Closure Checklist Through wrap-up-engine.js verify

**Persona:** the agent session running `/claude-tweaks:wrap-up` (an internal tooling user), at the point `execution-and-verification.md`'s "Verify execution" section gates the closure line — previously a ~9-item hand-run checklist (`ls` globs, `git log --grep`, `gh issue view`), now a single deterministic verb call.
**Goal:** get a verbatim pass/fail/skip/unknown table proving every closure condition actually landed, and BLOCK the closure line rather than emit it when one didn't — replacing "I ran the checks" narration with evidence.
**Entry point:** the wrap-up run directory (`$PIPELINE_RUN_DIR`) exists, its cleanup/curation steps have executed (or been explicitly deferred), and `execution-and-verification.md` reaches the "Verify execution" section.
**Success state:** a rendered markdown table with one row per check, exit code `0`, and the closure line emitted; or exit code `3` with `BLOCKED — {failing check row}` and the closure line withheld.

## Steps

### 1. Run the verb against the run directory
- **URL:** `node plugin/bin/wrap-up-engine.js verify --run-dir "$PIPELINE_RUN_DIR" --base {base-ref}`
- **Action:** Invoke it exactly as `execution-and-verification.md` instructs, once cleanup has run.
- **Should feel:** One command replacing a hand-run checklist — no more trusting the model's own narration that it checked `git log`, `gh issue view`, and a handful of `ls` globs.
- **Should understand:** `--run-dir` accepts either the run's original path or its archived copy under `.claude-tweaks/pipelines/archive/` — the verb resolves both regardless of which one it's invoked with (#2552 fixed the invocation shape that previously misread the archive path itself as "original path still present"). `--base` is consumed by `carrier-commit` always, and by `reference-repairs` only when `integration-model` is not `pr-first`: under `pr-first`, `reference-repairs` instead resolves the repair commit list from the run's own PR (`gh pr view --json commits`) rather than walking `{base}..HEAD` — a squash-merged PR collapses every `Initiative-Fix:` commit into one multi-file commit on `main`, which `{base}..HEAD` can no longer scope correctly (#2552). `plans-ledger`/`design-caches` scan the checkout the verb is actually invoked FROM (`cwd`, defaulting to `process.cwd()`), never always the main checkout — record #1222 fixed a structural blind spot where a worktree-local leftover (an execution plan, an SDD ledger workspace) was invisible to a scan pinned to `repoRoot`. This mostly matters when the verb runs against a still-live worktree — a `MULTISPEC_REVIEW_DEFER=1` run, or a standalone/manual invocation from inside one — since the mainline single-spec `worktree`/`pr-first` flow runs cleanup (including worktree removal) before verify, so `cwd` has usually already collapsed back to the main checkout by the time these two checks execute there.
- **Red flags:** Any check silently reporting `pass` for a condition that plainly doesn't hold on disk — the exact failure class three separate fix rounds in this feature's own build caught (a match-key bug, a vacuous slug match, an ISO-timestamp-stripping regression) before this journey's own files reached the state they're in now, and the class record #1222 caught later (a worktree-local leftover invisible to a `repoRoot`-only scan).

### 2. Read the table's four distinct states
- **URL:** the same command's stdout
- **Action:** Inspect a row of each kind — `pass`, `fail`, `skip (reason)`, `unknown (reason)`.
- **Should feel:** Each state means something different and none of them silently substitute for another.
- **Should understand:** `pass`/`skip`/`unknown` never change the exit code — only `fail` does (or a `null` run dir, which forces exit 3 even though every row renders `unknown`). `skip` means a real, known condition why the check doesn't apply here (e.g. `deferred to parent console`, `nothing recorded`, or `plans-ledger`'s "found, not owned by this run" — residue that predates the run dir's own creation time, reported informationally rather than counted as a fail, #2552). Another such condition is `run-dir-archived`/`worktree-removed` reading `skip (pending-review — teardown follows the human merge)` when the run's `console.json` records merge resolution `leave-open`. That is the designed resting state of a pr-first run parked for a human merge, where the worktree must stay and the reconciler archives later (#3373). `unknown` means the check genuinely could not run (`gh` absent, `verify-expectations.json` missing) — visible, but not blocking, matching how the old checklist surfaced an un-runnable check rather than treating it as a failed action.
- **Red flags:** A multi-line or pipe-containing detail string breaking the table's column count (the renderer sanitizes this — collapsing whitespace and escaping `|` — so a broken table here means the sanitizer itself regressed).

### 3. Trace a memory or upstream row back to the console that recorded it
- **URL:** `$PIPELINE_RUN_DIR/verify-expectations.json`, written by `review-console.md`'s "On approval" step 11 (under Approve all, via `wrap-up-engine.js finish-console --approve-all`, which preserves the file's other fields)
- **Action:** Open the expectations file the Review Console wrote when it resolved this run's `M#`/`U#` items, and match its `memory`/`upstream` arrays against the table's `memory-updates` and `upstream-feedback` rows.
- **Should feel:** The two checks covering writes that land *outside* the repository rest on something the console actually recorded at resolution time — not on the verb re-deriving intent afterwards from state it cannot see.
- **Should understand:** An absent file and an empty one are distinct states, and the row text says which one happened: no file renders `unknown (expectations file missing)` — the console's own write step never ran — while `{"memory": [], "upstream": []}` renders `skip (nothing recorded)`, meaning it ran and had nothing to record. The console writes the file on every path that reaches a resolution, the empty-console fast path included. Under `MULTISPEC_REVIEW_DEFER=1` (procedure in `review-console-appendix.md`) it writes empty arrays plus a `deferred` list naming the cleanup items the parent console still owns; three of those names (`design-caches`, `worktree`, `run-dir-archival`) turn their rows into `skip (deferred to parent console)`, and the per-spec `memory-updates`/`upstream-feedback` rows read `skip (nothing recorded)` because this spec's own `M#`/`U#` resolution never ran — an accepted limit of per-spec verification under defer, not a clean bill of health.
- **Red flags:** `memory-updates` or `upstream-feedback` reporting `pass` when no expectations file exists at all; an absent file rendering as `skip (nothing recorded)`, which would erase the difference between "the console never wrote it" and "the console had nothing to write".

### 4. Hit a real fail row and watch closure get blocked
- **URL:** `execution-and-verification.md`'s Verify execution section, downstream of Step 1's table
- **Action:** Run the verb against a run where one approved cleanup action didn't actually execute (e.g. the worktree is still listed, or the archive path is missing).
- **Should feel:** The pipeline stops here, not three steps later when something downstream trips over the half-finished state.
- **Should understand:** Exit code `3` means "surface `BLOCKED — {failing check row, verbatim}` and stop" — never emit the closure line. This is a genuinely new exit code (`0` unchanged, `1`/`2` keep their existing "bad payload"/"malformed invocation" meanings from the verb's sibling `plan`/`record`/`render` commands).
- **Red flags:** The closure line emitting anyway despite a `fail` row in the table; a `BLOCKED` message that doesn't name which check failed; a run whose Review Console resolved the merge to `leave-open` reporting `BLOCKED` on `run-dir-archived` or `worktree-removed` because its worktree and run dir were correctly left in place for the human merge (#3373). The other path holds just as firmly: a `merge` resolution, an absent or unreadable `console.json`, or a multi-spec parent run dir (one holding `manifest.yml`, whose `console.json` always reads `leave-open` and is never the bundle's merge decision) must still `fail` when teardown is missing — and `run-dir-archived`'s `archive path missing` and `not git-tracked` rows fail under every resolution, `leave-open` included.

### 5. Run it with `gh` unavailable
- **URL:** the same command, in an environment with no `gh` on `PATH`
- **Action:** Invoke the verb where `acceptance-labeling` (and any `carrier-commit`/`upstream-feedback` fallback needing `gh`) would otherwise need it.
- **Should feel:** Degrades visibly, never silently — a reader sees exactly which rows the environment couldn't evaluate.
- **Should understand:** The verb is deliberately `gh`-CLI-only (module header states this) — a `gh`-absent row always renders `unknown (gh absent)`, never a silent `pass`. Any MCP-path manual verification stays the skill prose's affair, outside this verb's scope.
- **Red flags:** A `gh`-dependent check reporting `pass` when `gh` never actually ran.

### 6. Confirm `carrier-commit` checked this run's record
- **URL:** the table's `carrier-commit` row, from the same command
- **Action:** On a worktree run, read the row and compare it against the record the run built.
- **Should feel:** The closing-keyword check actually ran against this run's record. A missing `Fixes #N` shows up as a failure you can act on, never as a quiet skip.
- **Should understand:** The record numbers come from the run's materialized header, read through `pack.js`'s `resolveRecords`. That is the run dir's own `work/` first, then the worktree's mirror of the run dir: on a worktree run the header is committed only on the feature branch, so the main-checkout run dir has no `work/` before merge. A closed run's worktree comes from `worktreeAtClose`, and a multi-spec `spec-{N}/` dir uses its parent's stamps. Only header records count. A multi-spec manifest's ids include specs that never ran, whose PR line is `Refs`, not `Fixes`. When no header resolves (cleanup already removed the worktree, as it does before verify under pr-first), the row falls back to `verify-expectations.json`'s `issues` array. Review Console step 11 writes that array on every resolution path, including Approve all, where `finish-console`'s `issues` key carries it (#3394). `skip (no resolved issue numbers found)` is correct only for conversation-based work with no record at all.
- **Red flags:** `carrier-commit` reporting `skip` on a record-mode worktree run whose worktree still exists. That is the main-checkout-only read that #3365 removed. Also a `pass` when neither the branch log nor the PR body carries a closing keyword for the record.

### 7. Wrap up a sub-issue whose parent gate isn't due yet
- **URL:** the table's `acceptance-labeling` row, from the same command, on a run that closes a sub-issue with a resolvable parent
- **Action:** Run the verb on a wrap-up of a sub-issue that still has open siblings — the case where the Parent-Gate Procedure (`verification-brief-parent-gate.md`, "Evaluate the gate") correctly applied no label to the sub-issue or the parent.
- **Should feel:** A correct wrap-up closes. The row agrees with the procedure that just ran instead of blocking on a label the procedure was never supposed to apply.
- **Should understand:** For a parent target the check enumerates the parent's sub-issues and computes `parentGateState`, counting every record this run is closing as `CLOSED` (it may still read open on GitHub until the merge lands). Siblings still open → `skip (parent gate #P not due — N sibling sub-issue(s) open)`. A due gate whose sub-issues' highest `risk:*` tier sits below `risk-floor` (size is never read at the parent level) → `skip (parent #P below oversight floor)`. Only a `due`/`gated`/`resolved` gate on an above-floor parent reaches the `demo:pending` + Verification Brief check, so a genuinely ungated due parent still fails `#P: missing demo:pending label`. A sub-issue enumeration that errors, returns nothing, or returns an unparseable line renders the whole row `unknown`, never `fail`. When several run records share a parent, it is enumerated and checked once.
- **Red flags:** `acceptance-labeling | fail | #P: missing demo:pending label` on a sub-issue whose siblings are still open — the #3222 false fail that blocked every wrap-up of a sub-issue that wasn't the last one. Also the last open sibling's wrap-up reading `skip (… not due …)` because its own still-open state was counted, which would hide a genuinely due gate.

## Origin
- Created during build of #900 (wrap-up verify verb — mechanizes `execution-and-verification.md`'s hand-run closure checklist into a deterministic table), part of the shared #343+#900 `/flow` multi-spec run.
- Related: #343 (prerequisite — fixed the same skill file's circular gate condition on the same branch), #892/#891 (the sibling `bin/verify.js` deterministic-check-runner family — a different subsystem covering type/lint/test checks, not this feature's closure-gate checks).
- Updated for #1222 (`plans-ledger`/`design-caches` switched from scanning `repoRoot` to the verb's own invoking `cwd`, closing record #900 finding #3 — a worktree-local leftover was structurally invisible to a main-checkout-only scan under the default `worktree`/`pr-first` mode).
- Updated for #1841 (`acceptance-labeling`'s parent resolution migrated from `gh issue view --json parent` to GraphQL, since `gh` <2.96 rejects that field — the check's gather failure now actually renders `unknown` for this case, matching Step 2's always-documented `unknown` contract rather than the `fail` the old REST call produced on an incompatible `gh` version; the observable row vocabulary and Step 5's gh-absent behavior are unchanged).
- Updated for #2552 (`run-dir-archived` now resolves correctly regardless of which of the two candidate paths `--run-dir` is invoked with; `reference-repairs` under `integration-model: pr-first` verifies via the PR's own commit list instead of walking `{base}..HEAD`; `plans-ledger` reports pre-existing, not-this-run's residue as an informational `skip` rather than a `fail`).
- Updated for #3373. `run-dir-archived` (only its "original path still present" fail) and `worktree-removed` now render `skip (pending-review — teardown follows the human merge)` instead of `fail` when `console.json` records merge resolution `leave-open`. The input is read fail-open, and there is no live PR-state read. The observed trigger was run `2026-10-17T093021-record-3335`, which was otherwise clean but forced to report `BLOCKED`.
- Updated for #3365: `carrier-commit` resolves its record numbers through `pack.js`'s `resolveRecords`, reading the run dir's own `work/` and then the worktree mirror, using header rungs only. It no longer reads only the main-checkout run dir, which is empty before merge. A record that lacks a closing keyword now fails instead of silently skipping. Added step 6.
- Updated for #3394: Review Console Approve all now passes `issues` in `finish-console`'s stdin payload, so after pr-first teardown the `carrier-commit` row falls back to `verify-expectations.json`'s `issues` on an Approve-all run too, resolving the record (pass/fail) instead of skipping. Step 6's "Should understand" line was corrected to match.
- Updated for #3222: `acceptance-labeling`'s parent path now evaluates the parent gate state (self-inclusion of the run's own records) and the parent-path oversight floor before requiring `demo:pending`, skipping an incomplete or below-floor parent instead of failing it; a sub-issue enumeration failure renders `unknown`. `execution-and-verification.md` now notes that `--run-dir` takes the original, pre-archive path. Added step 7.
