# Refine the Backlog Through Decision Lanes

**Persona:** A maintainer sweeping the backlog's label hygiene — `priority:*`, `**Related:**`, and grants (`auto:build`/`auto:merge`) — who wants one confirm gate instead of editing labels record by record.
**Goal:** Run `/claude-tweaks:backlog refine`, read the seven precedence-ordered decision lanes, apply an accepted batch through the single confirm gate, and resolve the one row only a human can decide via its interactive launcher.
**Entry point:** A Claude Code session in a project with `work-backend: github-issues` (or `local-files` for the priority/Related sub-stage only); type `/claude-tweaks:backlog refine`.
**Success state:** A count-summary line, up to seven populated lanes (Re-authorize / Grant / Flag-back / Needs-decision / Priority / Dependency repair / Needs you) each with a paste-ready block — Re-authorize/Grant/Flag-back/Needs-decision/Priority render one `apply-refine-labels.js` batch-dispatch call per lane (Dependency repair keeps its own per-record `gh issue edit --body-file` form, a body rewrite the batch CLI doesn't cover) — one `AskUserQuestion` confirm gate, every applied action logged to `decisions.md`, a closing summary block (per-type tally with always-present `skipped` and `failed` counts — both rendered explicitly as `0 skipped · 0 failed` on a fully clean run — one retry-ready line per failure, one informational line per skip naming the record and what changed, and the absolute run-dir path), an autonomy-ceiling footer, and a closing `Next:` line.

## Steps

### 1. Run `/claude-tweaks:backlog refine` at `supervised` — the cheap path
- **Action:** Run the skill on a repo whose `autonomy` ceiling resolves `supervised` (the project default), without `--trust`.
- **Should feel:** Cheap — the run doesn't pause for a trust-table fetch or a `git log` read; it goes straight from grant-check to the lanes.
- **Should understand:** `refine-mode.md` Step 1 resolves the ceiling once (`resolve-policy.js --values autonomy trust-revert-window-days`). Step 3's "Trust signal" section gates the entire trust-table fetch on that resolved ceiling being `trusted`+ **or** `--trust` being passed; at `supervised` with no `--trust`, `_shared/trust-table.md`'s Fetch section — including its per-parent branches and its own `git log` read — never runs this session, and Trust evidence is omitted from the report. Step 4's footer states the skip plainly: `"Autonomy ceiling: supervised — trust not fetched this run (recorded, never acted on; pass --trust to render it)."` — the skip-case wording, replacing the ceiling-description wording a `trusted`+ (or `--trust`) run would get instead.
- **Should understand:** `--trust` (`SKILL.md`'s Input) is the opt-in that forces the fetch at any ceiling, including `supervised` — it's the only way to see Trust evidence without raising the project's ceiling.
- **Red flags:** A `↳ trust:` consequence line rendered under any lane row on a `supervised`, no-`--trust` run; the ceiling-description footer wording appearing instead of the skip-case wording; a visible delay for a trust-table `git log` fetch on this run.

### 2. Read the lanes — precedence order, one lane per record
- **Action:** Read the report top to bottom: the one-line count-summary first, then the lanes in fixed order — Re-authorize, Grant, Flag-back, Needs-decision, Priority, Dependency repair, Needs you.
- **Should feel:** Like reading a decision queue already sorted for you, not seven independent reports to reconcile — each record shows up exactly once.
- **Should understand:** `refine-mode.md` Step 4 fixes the precedence (Re-authorize → Grant → Flag-back → Needs-decision → Priority → Dependency repair → Needs you); a record qualifying for more than one lane renders in the earliest lane it reaches only. Empty lanes render nothing at all — no heading, no table, no paste block. The count-summary names only the lanes that actually rendered, e.g. `` `24` suggestions across `7` lanes: `2` re-authorize, `7` grant, `3` flag-back, `1` needs-decision, `8` priority, `1` dependency-repair, `2` needs-you `` — counts are lane array lengths, computed fresh every run. A Dependency-repair *annotation* riding under another lane's row is counted under that row's own lane, never double-counted as a Dependency-repair row too. A record already carrying an unresolved `<!-- needs-decision: backlog-refine -->` comment (see Step 4.5 below) renders as a single bare annotation line under the Needs-decision heading rather than a fresh table row, and writes nothing this run. So does a record whose latest grant decision you already resolved `keep` or `build it myself` (Step 4.5 below), as long as its body and labels have not changed since: `#{n} — refusal resolved {choice} on {date}; not re-asked`. That line comes from `plugin/bin/resolved-refusal.js` via `grant-lane-decision.md`'s Resolved-refusal check.
- **Red flags:** The same record number appearing as a row in two different lanes; a fresh `needs:decision` row (and a new decision comment) for a record whose latest grant decision was resolved `keep`/`build it myself` and whose body and labels are unchanged since; a lane with zero rows still printing a heading or empty table; the count-summary total not matching the sum of the lanes actually rendered below it.

### 2.5. Understand why a record landed in Needs-decision instead of Flag-back
- **Action:** Read a Needs-decision row's Evidence column — it names `grant-check`'s `RECOMMEND_BUILD: false` rationale for a record that is already scored (`risk:*` + `size:*` present) and spec-shaped.
- **Should feel:** Like the tool distinguishing "this record needs more information before anyone can act" (Flag-back) from "this record is fully ready, but a human — not automation — has to make the call" (Needs-decision) — two genuinely different situations that used to collapse into the same "needs scoring" comment and strip `ready`, looping the record between `ready` and backlog forever.
- **Should understand:** `refine-mode.md` Step 3 checks for `risk:*`/`size:*` and spec-shape first; on that path only a record missing either still reaches Flag-back. A record that has both but still gets a content-level refusal is stamped `needs:decision` and **keeps `ready`** — no `auto:*` label is written. The one other route into Flag-back for a fully scored, spec-shaped record is Step 3's missing-verdict outcome — `grant-check` rendered no `RECOMMEND_BUILD`/`RECOMMEND_MERGE` line at all (`_shared/untrusted-record-content.md`'s verdict-source rule), so the row is flagged back with reason `no verdict rendered` rather than stamped `needs:decision`: there is no rendered rationale to quote, and a missing verdict is never read as a default grant or refusal. `backlog/grant-lane-decision.md` is where this branch's outcome table and write mechanics actually live (cited from both `refine-lanes.md`'s Needs-decision lane and `refine-headless.md`'s own headless gate-4 refusal, so a record refused interactively or headlessly converges on the same comment shape). The record's GitHub issue gains a structured comment (`## Decision needed` with `**Proposed:**`, `**Why:**`, and a paste-ready `**Command:**` — `_shared/work-record.md`'s canonical decision-comment template) rather than a plain flag-back sentence.
- **Red flags:** A record with both `risk:*` and `size:*` landing in Flag-back instead of Needs-decision when `grant-check` did render a `RECOMMEND_BUILD: false` verdict (a `no verdict rendered` flag-back is the one legitimate exception); a Needs-decision stamp that also strips `ready` or adds an `auto:*` label; a decision comment missing its `**Command:**` line.

### 3. Apply a batch — the confirm gate is the single stop
- **Action:** After reading every lane's paste block, answer the one `AskUserQuestion` under `<!-- refine-confirm-gate -->`: `"Apply these label changes, or override specific items?"` — Option 1 `Apply all recommended (Recommended)`, Option 2 `Override specific items`, Option 3 `Grant auto:build only, hold merge`, Option 4 `Skip all suggestions`.
- **Should feel:** One stop for the whole batch, not seven — each lane's paste block already shows exactly what Option 1 will run, so nothing about the write is a surprise at confirm time. For Re-authorize/Grant/Flag-back/Needs-decision/Priority that's a single `node "${CLAUDE_PLUGIN_ROOT}/bin/apply-refine-labels.js" /tmp/backlog-refine-actions-{lane}.json --run "$PIPELINE_RUN_DIR"` call per lane — one dispatched command applying every row in that lane's `gh issue edit`/`gh issue comment` action, not one paste line per record.
- **Should understand:** `SKILL.md`'s Anti-Patterns table calls this out directly: "Skipping or bulk-bypassing the batch-confirm in `refine` mode … the human action is the load-bearing security signature — never skip it, even for an all-recommended batch." Step 5's Apply section runs each lane's mechanics only after that answer — Priority/Related edits, Grant edits (stripping `bot:blocked` in the same edit as a re-authorize grant), Dependency-repair edits, Flag-back label-removal-plus-comment, Needs-decision's label-plus-comment (keeps `ready`, writes no `auto:*`). `apply-refine-labels.js` applies each lane's actions independently — one failed `gh` call never aborts the rest of the batch — and, when `--run` names a live pipeline run dir, appends up to two `decisions.md` AUTO lines per successfully-applied action (one per step actually attempted — edit, comment) under the `/backlog` heading. Option 3 is a session-wide override: it applies every non-grant suggestion and every grant row's `auto:build`/re-authorize normally, but withholds `auto:merge` on every row for the rest of this run, even rows the Grant lane recommended it for. Every applied action gets up to two lines in this run's `decisions.md` — one per step actually attempted. Once the batch finishes, Step 5 renders a closing summary as assistant text (never left in tool output alone): a per-type tally (`34 priority set · 2 Related updated · 7 granted · 5 flagged back · 1 dependency-repair · 1 needs-decision · 0 skipped · 0 failed`, with `0 skipped` and `0 failed` always shown explicitly on a clean run), one line per failed write naming the record and error followed by a paste-ready retry command, one line per skipped write naming the record and what changed, and the audit trail's absolute run-directory path. The tally line comes from `bin/closing-tally.js --run`, never a hand count: it counts both the closing-summary template lines and `apply-refine-labels.js`'s own `#{n}: applied {labels}` lines (typed by the labels applied), so a batch applied through the documented path reports its real writes. A write logged both ways counts once, a flag-back or needs-decision whose label landed but whose comment failed counts once under `failed`, and any `/backlog` AUTO/FAILED line that matches no tally field surfaces as a one-line unclassified caveat under the tally. Step 5 then closes its own standalone run directory via `close-run --run` — a possible one-line "no recorded wrap-up invocation" notice is expected noise here (refine runs standalone and never invokes `/claude-tweaks:wrap-up`), not a sign of a broken run.
- **Should understand:** Confirming the batch is not a guarantee every row lands — the confirm gate can sit unanswered for a long time, and a sibling session (or `/claude-tweaks:dispatch`) can grant, claim, or flag back the same record in that window. Immediately before writing a priority/related, grant, or flag-back row, Step 5 re-fetches that record's live labels and compares them against the premise the row was built on at Step 1; a row whose premise no longer holds (a grant target that lost `ready` or already gained `auto:build`/`auto:merge`, a flag-back target that already picked up `risk:*`/`size:*`/`auto:build`/`bot:in-progress`) is dropped without writing, logged as a skip, and counted in the closing summary's `skipped` bucket rather than silently applied over someone else's concurrent work. A grant row dropped because a concurrent write already granted the record says in its skip line whether that live grant **agreed** with this run's own `RECOMMEND_MERGE` verdict or **DIVERGED** from it — the DIVERGED form carries the discarded verdict and its grant-check rationale (a headless grant's `auto:merge-pending` counts as merge present; a re-authorize row, which never got a grant-check verdict, keeps the generic line naming the live grant). `grep 'concurrent grant DIVERGED' "$PIPELINE_RUN_DIR/decisions.md"` lists every divergence from one sweep. That reverify **fails closed**: a live-label read that errors — a network error or non-zero `gh` exit, or a `readRecord` failure on a missing/corrupt file under the local-files driver — is treated exactly like a premise mismatch, not like a failed write. The row is skipped rather than written on an unread premise, logged as `AUTO … skipped …` with `{what changed}` = `live-state fetch failed: {error}`, and lands in the same `skipped` bucket — it never produces a `FAILED` line or a retry command. The one reverify outcome that logs nothing at all is a **genuine no-op**: a priority/Related row whose live `priority:*`/`**Related:**` state already matches what the row would write is dropped with no `decisions.md` line and no per-skip line, because nothing changed and there is nothing to audit; only a priority/Related row a concurrent session moved to a *different* value logs an `AUTO … skipped …` line and drops the write rather than overwriting the fresher decision. Dependency-repair rows are outside this **label** reverify entirely — wiring a `blocked-by` link isn't the same race. A separate **body** pre-write reverify covers the two writes that rewrite a record's full body from the Step 1 fetch — the Related-rows body rewrite and dependency-repair's `work-links: body-text` append (never its `work-links: native` sibling, which writes no body text): immediately before either write, Step 5 re-fetches the live body and compares it verbatim against the Step 1-fetched premise, skipping the write on any difference and reusing the same `AUTO … skipped …` log line and `skipped` tally bucket as the label reverify rather than a parallel mechanism.
- **Red flags:** Any label changing on GitHub (or a local record file) before the `AskUserQuestion` is answered; a lane's paste block missing from the report; an `auto:merge` label landing on a record after choosing Option 3; an applied action with no corresponding `decisions.md` line; a closing summary that omits the failed count on a clean run, or that reports the run-dir path as a relative path; a tally reporting `0 granted` or `0 priority set` after `apply-refine-labels.js` logged those writes, or counting one write twice because it was logged both ways; a row's confirmed change landing on GitHub even though a concurrent session had already changed that same record's labels before Step 5's write; a grant row skipped for a concurrent grant whose skip line says neither `agreed` nor `DIVERGED`, or a re-authorize row's skip line claiming either.

### 4. Resolve a Needs-you row — interactive launchers, no batch
- **Action:** On a repo where the Needs-you lane rendered (`needs:definition`-labeled records, or judgment-required rows with no batchable command), read its rows and the report's closing `Next:` line, then run the named launcher directly.
- **Should feel:** Like the report handing you personally the one move only you can make — not another table to batch-approve.
- **Should understand:** Needs-you rows are exempt from paste blocks by design — `refine-lanes.md`'s Needs-you section gives each row an interactive launcher instead: `/claude-tweaks:specify #{n}` for a `needs:definition` gap, `/claude-tweaks:challenge #{n}` for a `solution:unjustified` confirmation, `/claude-tweaks:backlog refine #{n}` for a judgment-required dependency repair — each with a `#`-comment naming why it landed there. The closing `Next:` line names the top Needs-you item whenever that lane is non-empty; only when Needs-you is empty does it fall back to naming the highest-value batch among the lanes above.
- **Red flags:** A Needs-you row carrying a `gh issue edit` paste block; the `Next:` line naming a batch lane while Needs-you still has rows; a launcher missing the `#`-comment explaining why the row needs a human.

### 4.5. Resolve a Needs-decision stamp — `refine #N` in one batch
- **Action:** Run `/claude-tweaks:backlog refine #{n}` (or a comma list, `#{n},#{m}`) directly on the flagged record(s). The resolver fetches each record's unresolved decision comments and any `bot:blocked` state, renders one batch table (choices: keep / build it myself / grant anyway / park / close, plus re-authorize on a `bot:blocked` row), and applies everything through one confirm gate — "Apply all recommended" resolves every row to its safe default (keep the decision, re-authorize every `bot:blocked` row) in a single click, or answer "Override specific rows" in the next message for per-row choices.
- **Should feel:** Like the record handed you a fully-briefed decision, not a chase — the batch table's Evidence column quotes the record's `**Proposed:**` line (or, for a pre-migration comment, its plain rationale sentence) verbatim, and one confirm answer applies every named record's choice instead of a hand-typed `gh` pair per record.
- **Should understand:** `refine #N[,#M...]` is a human-present-only form split into its own file (`backlog/refine-record.md`) from `refine-mode.md`'s whole-queue sweep — it resolves only the named record(s)' own comments, never the rest of the queue, and a Routine can never fire it. Applying a row prepends `**Resolved:** {choice} — {date}` to that same decision comment; the `needs:decision` label comes off a record only once every unresolved `needs-decision:*` comment on it has been answered this way (`_shared/work-record.md`'s Resolution rule) — a record refused by two units concurrently keeps the label until both are resolved.
- **Should understand:** The answer sticks. A `keep` or `build it myself` resolution is honored by every later refine run, human-present or headless (`refine-headless.md`'s gate-4 path logs `not re-asked` instead of re-stamping), until the record's body is edited or any label other than `needs:decision` changes after the resolution. Re-shaping the record or re-scoring its `risk:*`/`size:*` re-opens the grant question. The resolution instant is the earlier of the start of the `**Resolved:**` date (UTC) and the comment's last-edit time, so a date typed in a timezone east of UTC cannot hide a later change.
- **Red flags:** The label removed while a second unresolved `needs-decision:*` comment (from a different unit) is still on the record; a resolution with no `**Resolved:** {choice} — {date}` line prepended; a Routine firing `refine #N` on its own (it is human-present-only, exactly like bare `refine`).
