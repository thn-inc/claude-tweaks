# Accept Built Work Show-First via /demo

**Persona:** claude-tweaks user (or a maintainer of a project using the plugin) returning days after a build shipped, who owes the record a human verdict and does not want to re-derive "how do I test this" from the diff.
**Goal:** Reach an Approve / Request changes / Skip decision on one record after being *shown* the work — the observation plan executed in front of them — rather than being asked to choose how to verify it first.
**Entry point:** A terminal in a session with the plugin loaded, holding a record number from `/claude-tweaks:help`'s outstanding list (Stage 4.7), a pending acceptance label notification (`demo:pending` or `accept:pending`), or the `Acceptance packet:` line on the run's PR. A record below the oversight floor carries the packet and no label, and `/claude-tweaks:demo #N` reads it all the same.
**Success state:** The record carries `demo:approved` (or `demo:changes-requested` plus a linked follow-up record) with no earlier acceptance label left to outrank it, and the human never had to answer a how-do-you-want-to-check-this question. For a `#N,#M` list, every ref that resolved carries its own verdict, applied as that verdict was given — an Approve verdict from a list also carries `demo:approved-batch` alongside `demo:approved` (Step 3); a ref that resolved to nothing was reported and skipped without stopping the rest.

## Steps

### 1. Resolve the one item — `/claude-tweaks:demo #N`
- **URL:** `/claude-tweaks:demo #N` (or bare `/claude-tweaks:demo` for this session's own unrecorded work; or `/claude-tweaks:demo #N,#M` — a `/tidy` Yours group head or a hand-typed list — to take several records one at a time)
- **Action:** Invoke against a record whose wrap-up posted an acceptance packet. A `#N,#M` list is an explicit batch: the first ref runs Steps 1-3 to completion before the second begins.
- **Should feel:** Zero re-derivation — the packet's Test guide (`plugin/skills/_shared/acceptance-packet.md`; the walkthrough composed per `plugin/skills/_shared/try-it.md`) renders first, hoisted out of its place and shown once, the same steps the Pipeline Summary showed. Then come the packet's own title and notes and its remaining sections in the order wrap-up wrote them: What changed, Recording, Couldn't test, Tried to break, Least confident, Risk proofs, Decisions left for you (only when something is left), Deploy status. A section with nothing to report says why in one line, so you can tell "nothing to report" from "never looked".
- **Should understand:** Demo reads the record's comments for the packet before it looks at any label: the earliest comment whose first line is exactly the packet marker, from an owner, member or collaborator (the rules `readPacket` in `plugin/bin/lib/wrap-up/packet-gather.js` implements, which wrap-up's own acceptance check shares). A below-floor record with no parent has a packet and no label, and a record with a pending label in either spelling gets the fresh packet even when an earlier verdict outranks the label, so a re-run on a rejected record shows the new work rather than a reconstruction from the closing commit. The packet is evidence-validated: a narrated claim that cites no gathered fact was dropped, and the count shows above the sections (`N claims were dropped for missing evidence`, zero included); a claim or plan line that carried a credential-shaped value was omitted and named by section and key, never by text; a gap in what wrap-up could read is a partial note. Nothing is claimed as tested that the gathered checks do not show. The `### Observation plan` appendix is builder-authored at wrap-up time (kinds: `rendered-page | app-route | cli | flow | diff` — schema in `plugin/skills/_shared/observation-plan.md`); demo executes it mechanically rather than classifying paths itself, and a packet with no appendix skips straight to the verdict. Demo never composes a fresh Try it block for a packet; a Test guide with nothing in it renders its one empty line. On the `local-files` backend the packet is the block between the `<!-- acceptance-packet:start -->` and `<!-- acceptance-packet:end -->` lines in the record body. A parent-linked sub-issue carries no packet of its own: its walkthrough is the `try-it` comment on the run's PR, and a decomposition parent's gate still posts the legacy `## Verification Brief`. Only a record with no trusted packet falls back to those legacy forms, through `legacy-brief-compatibility.md`: a parent brief, or a brief from a run before the packet, found through the issue's `Verification Brief posted to PR #…` pointer and the PR's `try-it` / `brief` run comment (in a multi-spec bundle, this record's own `try-it:{N}` / `brief:{N}` first, then the plain one), and a fresh Try it block composed from the record's ACs only when none is found. A parent-linked sub-issue's own plan may additionally carry an optional `Full verification:` block — composed by `/demo` itself, not wrap-up, pointing at the parent's eventual end-to-end check and naming which siblings still gate it. Only a comment from an owner, member or collaborator counts as found, on the issue and on the PR alike: a stranger's lookalike packet, brief, pointer or `try-it` comment reads as absent and is named in one skip line above the verdict (`ignore-a-planted-marker-comment-3358.md`).
- **Red flags:** Prepare/Validate output appearing before the Test guide; an empty or placeholder Test guide beyond its one stated line; a freshly composed walkthrough while the record carries a packet; a packet or brief taken from a stranger's comment, or one skipped with no skip line; a trusted packet whose first line names another schema version (`<!-- acceptance-packet: v2 -->`) read as absent or rescued by a legacy brief beside it — it is `unreadable`, reported by that version, and the ref stops; a failed comment read that falls through to the legacy brief forms instead of saying so in one plain line; `/claude-tweaks:demo #N` on a bundled spec rendering a sibling spec's brief (`brief:{M}` never counts for `#N`); a backlog sweep (demo resolves exactly the item(s) you named — `#N`, or a `#N,#M` list one at a time — never a scan for what's outstanding); a "See it yourself"/"Verify it yourself" option in the verdict question (that flow is retired — only briefs posted before the schema shipped walk it, via `legacy-brief-compatibility.md`).

### 2. Watch the plan execute — Prepare → Validate → Show
- **URL:** *(no command — demo drives)*
- **Action:** Nothing. Demo walks the packet's `### Observation plan` appendix (or a legacy brief's plan section) — it runs Prepare commands (`none` → skipped), silently validates URL surfaces with playwright-cli when available (session closed afterward), then Shows: opens the deep link in your browser (`open`/`xdg-open`), runs the `cli` command, walks `flow` Inspect pointers in order (regenerating missing artifacts, stating-and-continuing on failures), or renders the `diff`.
- **Should feel:** Show-first — the work appears in front of you before any question is asked.
- **Should understand:** A Prepare or Validate failure is *evidence for Request changes*, not a debugging detour — demo never fixes the application. A Parent-Gate parent brief (no plan section, walkthrough in its `### Try it — end to end` section) and a no-path-list session-recall entry legitimately skip straight to the verdict. When recall cannot name an entry point either, that entry's Try it block is omitted too, with one plain line saying so where it would render — never an invented entry point. When the plan carries a `Full verification:` block, it renders right after Show, before the verdict question — a pointer to the parent's eventual end-to-end check, not a substitute for it; the verdict you give still concerns only this slice. Its sibling list and its `parent gate` value come from one `bin/parent-gate.js --parent` call, the same code wrap-up's close procedure runs, so the block agrees with wrap-up on cancelled siblings; the record in hand keeps its live state there and is left out of `Pending:`. When the changed artifacts carry an Impeccable direction contract, demo also renders `### The design contract this was built against` above the verdict — the five blocks verbatim plus a `Design-seed:` line, per `plugin/skills/demo/design-contract-section.md`; when nothing resolves there is no heading and no "not found" note, and a malformed contract leaves one plain trace line instead of a section.
- **Red flags:** Demo asking which way you'd like to verify before showing anything; a browser validation session left open; a stale `flow` pointer blocking the walk instead of being stated and passed over; a `Full verification:` block silently missing on a parent-linked record after a failed parent or sibling lookup (a `gh` failure, or a non-zero exit of the `bin/parent-gate.js --parent` call, omits the block but must say so in one plain line above the verdict, naming which lookup failed and quoting the CLI's stderr line).

### 3. Give the verdict — one question
- **URL:** *(AskUserQuestion rendered by demo)*
- **Action:** Pick Approve, Request changes (a one-line reason files a linked follow-up record), or Skip for now.
- **Should feel:** One decision, fully informed — the only question the walkthrough asks.
- **Should understand:** Skip for now says what it leaves behind. On a record with a pending label, it leaves it pending. On a packet with no pending label, it reads the record's `risk:*`/`size:*` against the oversight floor: above it, nothing is written and `/claude-tweaks:tidy`'s acceptance-gap scan surfaces the record again; below it, nothing is written because no disposition is owed, and `/claude-tweaks:demo #N` still reads the packet. Your verdict replaces whatever acceptance label the record already held, so a later Approve on a record you rejected earlier reads `approved` everywhere: demo adds only `demo:*` and removes, in the same command, each prior label the record actually carries in either spelling. A label it does not carry is never passed, since `gh` fails the whole edit on one the repo never created. Approve swaps the pending label for `demo:approved` (and closes a decomposition parent), and a single-record Approve also clears a stale batch label; a batch-sourced Approve (Step 1's `#N,#M` shape) additionally applies `demo:approved-batch` alongside it, so `bin/lib/issues/trust.js`'s coverage/verdict computation can tell a batch sign-off apart from this step's own per-record walkthrough — no extra question, nothing to decide here. Request changes ends this record's walkthrough — a later re-demo is a fresh invocation with fresh preparation. On a `rendered-page`/`app-route` plan with browser tools available, this question is asked in the browser first, on a single-variant recap page (`plugin/skills/demo/browser-verdict.md`): a pick *is* Approve, applied immediately; an exit falls back to the terminal question with Approve omitted; every other event falls back to it unchanged. A `cli`/`flow`/`diff` plan, or a run with no browser tools, goes straight to the terminal question.
- **Red flags:** More than one question per record on the happy path; a verdict written for a session-recall entry (nothing is persisted for those except a Request-changes follow-up); a record still reading `changes-requested` after you approved it; a verdict lost to a `not found` error from removing a label the record never carried; demo adding an `accept:*` label.

### 4. Next ref, same shape — `#N,#M` batches only
- **URL:** *(no command — demo advances to the next ref in the list)*
- **Action:** Nothing. Once this ref's verdict has landed (label swap or follow-up filed), demo re-enters Step 1 for the next ref — a fresh, independent lookup with its own packet or brief, its own walkthrough, its own single verdict question. `## Next Actions` renders once, after the last ref.
- **Should feel:** Like paste-once, decide-per-record — no cross-record table, no apply-all, nothing lost if you stop halfway (every verdict already given is already applied).
- **Should understand:** A batch is your own explicit list, never a backlog scan — what is outstanding is still `/claude-tweaks:help` Stage 4.7's job; the once-per-item scope-fork checkpoint resets for each ref.
- **Red flags:** One combined verdict question spanning several records; a batch table asking for apply-all; the second ref starting before the first ref's label swap landed; a Next Actions block after every item instead of once at the end.
