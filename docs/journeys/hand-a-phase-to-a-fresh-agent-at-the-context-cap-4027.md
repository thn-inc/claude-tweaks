# Hand a Phase to a Fresh Agent at the Context Cap

**Persona:** claude-tweaks maintainer running `/claude-tweaks:flow #N` on a large single record by hand, or `/claude-tweaks:dispatch` over a queue of them, who has seen a long build slow down turn by turn and wants the run to shed its context at a phase boundary instead of dragging it through review, polish and wrap-up.
**Goal:** Read what `/flow` Step 4's context cap check measures, which of its results hand a phase to a fresh agent and which keep going in place, and what each of the two hand-off paths leaves behind — the top-level path, where the parent keeps `wrap-up`, and the dispatched path, where the call stops and its dispatcher continues it.
**Entry point:** A single-spec `/claude-tweaks:flow` run (typed by a human, fired by a Routine, or one of `/dispatch`'s two Task calls per group) that has just passed a phase gate with steps still to run.
**Success state:** `{run}/handoff.json` names the steps still to run and the command that resumes them; the remaining steps ran in one fresh agent (top-level) or one fresh Task call (dispatched) under the same claim, worktree and run directory; no step ran twice; `wrap-up` and the Review Console ran in the agent that owns them; and at most three hand-offs happened in the run.

## Steps

### 1. Gauge the context at a phase boundary — terminal
- **URL:** `node "${CLAUDE_PLUGIN_ROOT}/bin/context-gauge.js" --run "/abs/path/.claude-tweaks/pipelines/{run-id}" --next-steps test,review,polish` — `plugin/skills/flow/SKILL.md` Step 4 item 4, run as its own Bash call after a passing gate.
- **Action:** **`/flow` agent** runs it once a step's gate passes (`build` counts after its automatic `stories`, `polish` after its re-verify) and at least one step is still to run, then reads the one JSON line `{contextTokens, cap, over, transcript, handoff, reason}`.
- **Should feel:** A measurement, not a decision — the call reads a number off the agent's own transcript and the run carries on unless the number says otherwise.
- **Should understand:** The cap is 200,000 tokens (`CONTEXT_CAP_TOKENS` in `plugin/bin/lib/timing/context-gauge.js`, the midpoint of the measured latency curve: 5.0 s per turn under 100k of context, 12.1 s above 300k). The gauge measures the *calling* agent, found as the transcript whose tail holds this very call — an unanswered Bash call naming `context-gauge` and the run id — which is why the run directory is a literal absolute path and never `"$PIPELINE_RUN_DIR"`: a shell variable hides the run id and the gauge drops to a weaker match whose `reason` starts `caller-not-identified`. The check runs only where a fresh agent can take over cleanly: a single-spec run (a multi-spec `resume` would re-target every record in the run dir and skip the later specs' earlier steps, so a `MULTISPEC_PARALLEL_WAVE=1` member never reaches it), never under `interactive` (a fresh `Agent` cannot ask the user anything), and never between `build` and its automatic `stories`. A top-level run additionally never lists `wrap-up` in `--next-steps`, and gauges only when two or more steps remain before it: a single step resumes from that step onward (`steps-and-gates.md`'s Step Arguments), so the child would run `wrap-up` too. A dispatched call gauges with any step left, even one, and its `--next-steps` is every remaining step.
- **Red flags:** `--run "$PIPELINE_RUN_DIR"` in the call; a gauge call between `build` and its `stories`; a top-level run whose `--next-steps` ends in `wrap-up`; a one-entry `--next-steps` on a top-level run; the gauge run inside a multi-spec run or an `interactive` one; a `reason` starting `caller-not-identified` on a hand-off that was nevertheless taken.

### 2. Read a result that keeps going in place — terminal
- **URL:** Step 1's call with `--cap 1000` and no `--next-steps` (a probe: with no step list the gauge reports `over: true` but writes no `handoff.json`), or any of the failure shapes below; `plugin/skills/flow/context-handoff.md`'s Reading the result.
- **Action:** Read the JSON and decide: only `over: true` with a `handoff` path hands off.
- **Should feel:** Safe to ignore when it is quiet — a gauge that cannot tell never stops a run.
- **Should understand:** `over: false` continues here whatever `reason` says, and a missing or unreadable transcript fails open to exactly that with `contextTokens: null`. `over: true` with `handoff: null` also continues here: either `{run}/handoff.json` could not be written (no target records, a failed write), or the caller was not identified and the gauge fell back to a transcript that may belong to a child — a fallback measures but never hands off. The third case is the bound: once the run has made three hand-offs (`HANDOFF_BOUND`, counted in `handoff.json`'s `handoffCount`) the gauge writes nothing and prints `reason` `handoff bound reached (3 handoffs this run): continue in place`. The count is per run, not per call, so a dispatch group's two calls share one run directory and share the three. At the bound the agent never stops: it finishes as it would without the gauge, completing or settling its own HARD-GATE. Exit 2 (an unknown flag, a `--cap` that is not a positive integer, a `--next-steps` entry outside `/flow`'s step names, a `--run` that is missing, outside the main checkout or not a run id) writes nothing and also continues here, as does any non-JSON output. A run directory holding more than one record is refused the same way, as a backstop to the single-spec rule: `over: true`, `handoff: null`, and a `reason` naming the records and #4358 (multi-spec handoff) that ends `continue in place`. The gauge itself logs every non-null `reason` to `decisions.md` as a `SKIP` under `Step 4 context cap`, so a gauge that could not measure or hand off shows at the Review Console with no log line from the agent.
- **Red flags:** A run stopped because the gauge failed; a hand-off taken on `over: true` with `handoff: null`; a fourth `handoff.json` written; `handoffCount` reset between a dispatch group's two calls; a hand-off whose `contextTokens` is `null`.

### 3. Hand the remaining steps to one fresh agent — top-level run
- **URL:** `plugin/skills/flow/context-handoff.md`'s Top-level run, and the child template inlined there; `plugin/skills/flow/steps-and-gates.md`'s Steps Complete note.
- **Action:** **Top-level `/flow` agent** (a human-typed `/flow`, a Routine, or an earlier hand-off's child — a run not bound `dispatched: true` by Step 1 rung 2's read) logs the hand-off (`log-decision.js --status AUTO --step "Step 4 context cap"`), resolves the run directory, the worktree, the plugin root and the model (`resolve-profile.js capable`), dispatches one fresh `Agent` with the template inlined verbatim, waits for it and relays its report unchanged.
- **Should feel:** One agent takes over from a clean context and the parent stays out of the way — the transcript shows a hand-off line, not a replay.
- **Should understand:** The child reads `{run}/handoff.json`, which holds `nextSteps`, the measured `contextTokens` and `cap`, `mode`, `handoffCount`, `writtenAt`, and `resume` — `PIPELINE_RUN_DIR="{run}" /claude-tweaks:flow "{target}" {next-steps}`, with ` auto` appended for `auto`, `confirm` and `hybrid` (all of which run as `auto` past the Manifesto) and omitted under `interactive`. It runs that line as a literal `Skill` invocation; the `PIPELINE_RUN_DIR` prefix is what makes `/flow` adopt this run directory instead of minting a new one, and the child never re-runs a step outside `nextSteps`. It is a fresh `Agent`, never a `fork`, because a fork inherits the very context being shed. A top-level run never hands off `wrap-up`: a subagent cannot call `AskUserQuestion`, so a child running `wrap-up` would strand the Review Console and Step 5's ledger gate, which `auto` never silences. The parent therefore keeps `wrap-up` — after relaying the child's Steps Complete note it runs `wrap-up` and Step 5 itself, continuing its own Step 4 loop with `$PIPELINE_RUN_DIR` unchanged. A top-level session waits for the child's task-notification without a bound, since a child phase often runs past 20 minutes; a child that is itself a subagent waits at most 20 minutes (`sleep 20`, at most 60 times) under its own prompt's rule. The child may cross the cap and hand off in turn, because a fresh agent starts well under the cap and finishes several steps before nearing it again; the bound of three ends the chain regardless.
- **Red flags:** The parent re-running the child's steps while a silent child may still be writing; a `fork` used as the child; the child handed `wrap-up`; a hand-off with no log line; a relayed failure card treated as a pass and `wrap-up` run on it; a blocked report that does not tell the reader to confirm the child has stopped before running `resume`, and does not give `{run}/handoff.json`'s `resume` line on its own line.

### 4. Stop after the phase-exit push and report a hand-off — dispatched call
- **URL:** `plugin/skills/flow/context-handoff.md`'s Dispatched call; `plugin/skills/flow/steps-and-gates.md`'s handed-off Steps Complete note; `plugin/skills/dispatch/two-call-gate.md` §8, `plugin/skills/dispatch/task-prompt.md`'s Continuation call and `plugin/bin/lib/dispatch/first-call-artifact-check.js`'s `parseNextSteps` (the dispatcher's side, walked in `clear-the-two-call-gate-for-a-dispatched-group-2775.md` step 6).
- **Action:** **Dispatched call** (a `/claude-tweaks:dispatch` Task call, `run-state.json` `dispatched: true`) finds `over: true` with a `handoff` path, logs the hand-off, then pushes its branch if the phase-exit push did not run (`git -C "{worktree}" push origin {branch}`, under `integration-model: pr-first`; under `local-merge` or `current-branch` the continuation inherits the worktree and there is nothing to push), stops before the next step, renders the handed-off Steps Complete note, and reports its normal output with `OUTCOME: handoff`, then `NEXT_STEPS: {comma-joined remaining steps}` on the next line, ending `STATUS: DONE`.
- **Should feel:** Quiet and complete — the call ends on a clean stop, not a failure card, and leaves everything the next call needs exactly where it was.
- **Should understand:** Nothing is settled or torn down: the claim, the worktree and the run directory stay, and the template's checks before `build-test-ok` (the pass-stamp confirmation, the bookends) belong to the call that finishes the steps. No `ISSUE #{n}: failed:{gate}` line accompanies it, since a hand-off happens only after a passing gate. The handed-off Steps Complete note names only the steps this agent ran and says the run is not finished — the nothing-left-behind gate, the surveys and the Pipeline Summary are deferred to the agent that runs `wrap-up` — and ends with `Handed off: {next-steps} continue in a fresh agent from {PIPELINE_RUN_DIR}/handoff.json.` The dispatcher reads `NEXT_STEPS` through `parseNextSteps`, restricted to the steps that call can still run (`build`, `stories`, `test` for the first call; `test`, `review`, `polish`, `re-verify`, `wrap-up` for the second), and continues the call in a fresh Task call in the same worktree with the same template and its step list replaced; a missing, empty, unknown or repeated entry fails closed to `build-test-blocked` or `blocked` instead of becoming a continuation that skips or repeats a step. Its artifact check, claim-log check and stamp read wait for the report that carries `build-test-ok`, and the same three-per-run bound applies, so a fourth hand-off report is not continued.
- **Red flags:** A hand-off reported with the branch unpushed under `pr-first`; the claim released or the worktree removed at the stop; `OUTCOME: handoff` without a `NEXT_STEPS:` line, or with a `wrap-up` the call cannot run; a `STATUS` other than `DONE` on a clean hand-off; a handed-off report that runs the artifact check or is routed to the `cleanup-only` teardown.

### 5. Resume by hand from handoff.json — terminal
- **URL:** `{run}/handoff.json` and its `resume` field; `plugin/skills/flow/context-handoff.md`'s Top-level run, wait item.
- **Action:** **Maintainer** reads `{run}/handoff.json` after a blocked report (a child's bound expired, the `Agent` call failed, the bound of three stopped a continuation) and, once the child is confirmed stopped, pastes the `resume` line as written.
- **Should feel:** Recoverable — the file already names the steps and the command, so nothing has to be reconstructed from the transcript.
- **Should understand:** `resume` is `PIPELINE_RUN_DIR="{run}" /claude-tweaks:flow "{target}" {next-steps}`, where `{target}` is the run's records taken from its `spec-{N}/` subdirectories in `manifest.yml` order, or from its `work/{n}-spec.md` names. Running it while the child is still writing would put two agents in one worktree, which is why every blocked report says to confirm the child has stopped first. `handoff.json` is written atomically, only under a `--run` anchored to the main checkout (a worktree-local shadow run directory is refused with exit 2), and `handoffCount` there is the only record of how many of the run's three hand-offs are spent.
- **Red flags:** `resume` run while a child may still be writing; a hand-written `/flow` invocation without the `PIPELINE_RUN_DIR` prefix, which mints a new run directory beside the one holding the work; a `handoff.json` under a worktree-local `.claude-tweaks/`.
