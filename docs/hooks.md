# Hooks

All hook registrations route through `plugin/bin/hooks.js <event>` — one dispatcher, one module per event in `plugin/bin/lib/hooks/`. Rules:

- **Never break a session**, scoped to harness-dispatched hook events. Every such path — including a PreToolUse deny — exits 0; no hook module ever sets a non-zero `exit`. A deny is communicated entirely via `hookSpecificOutput.permissionDecision: 'deny'` in the stdout JSON, not the process exit code (see `pre-tool-use.js`'s own header comment for why exit 2 doesn't work for this). New modules must pass the garbage-stdin invariant test in `tests/hooks-dispatcher.test.js`. The directly invoked CLI verbs (`record-worktree`, `resolve-run-dir`, `close-run`, …) are a separate contract and may exit non-zero on malformed or rejected input.
- **Tiered posture per `_shared/auto-mode-contract.md`:** block (E1 wrong-checkout commit; the `worktree-always` policy gate; the Review Console ask gate — an `AskUserQuestion` whose question carries `header: "Review Console"` (exact match) is denied only when the session provably owns its run, which excludes fallback attribution, ad-hoc dirs, and any `classifyOwnership` verdict other than `mine`, and that run's ceiling grants `consoleAutoResolve`; it fails open in every other case, including a session whose cwd is the main checkout while the run's worktree is still live or after it was removed, which resolves to its ad-hoc twin (#2783) or classifies `indeterminate`, rationale in `[IL-167]`), warn (non-blocking systemMessage), inform (SessionStart additionalContext), log (append to the run dir's `events.jsonl`). What the `worktree-always` gate covers, what it deliberately doesn't, and its one `.claude-tweaks/pipelines/` exemption are stated once — in `plugin/skills/_shared/policy-schema-coverage.md`'s `worktree-always` coverage block, pinned to `pre-tool-use.js`'s exported `GATE_COVERAGE` by `tests/hooks-gate-coverage.test.js`. Don't restate the list here or anywhere else; five files did and all five went stale `[IL-93]`.
- **Project-agnostic by construction:** modules key off plugin-owned state (`$PIPELINE_RUN_DIR`, `.claude-tweaks/pipelines/`, `.claude-tweaks/policy.yml`), never off project structure. E1/E2/E3 no-op without a resolved run dir — the `worktree-always` policy gate is the one PreToolUse check that is deliberately run-independent, since its job is to require a worktree even before any pipeline run exists. `post-tool-use.js`'s closing-keyword check (warn tier) is the analogous exception on the PostToolUse side — it fires on any `git commit` regardless of run-dir state, since the gap it catches (a fix commit made outside the structured `/specify` → `/build` → `/wrap-up` pipeline, with no closing keyword) is exactly a commit that would never resolve a run dir in the first place. The deferred-subproject capture check (also warn tier) mirrors this on `Write`: it fires on any write to `docs/superpowers/specs/*-design.md` regardless of run-dir state, since a brainstorming session that hasn't reached `/specify` yet has no pipeline run dir to gate on either.
- **Ambiguity resolves to allow** — E1 denies only provable mismatches. A recorded worktree whose path no longer exists also resolves to allow (fail-open) — tear-down without close-run ends enforcement, not the session. Ownership counts toward provability: `record-worktree` stamps the recording session's id (`CLAUDE_CODE_SESSION_ID`), and a wrong-checkout commit from a *different* session is allowed with a warn (`wd-foreign-session` event) instead of denied; missing identity on either side falls back to deny.
- **Subagent Contract status-line check tier change (warn → one-shot block, #1936):** `subagent-stop.js`'s E3 check now forces one in-run retry per `(session_id, agent_id)` on a genuine status-line violation, via `SubagentStop`'s `{ decision: 'block', reason }` JSON output (live-confirmed supported on this harness) — a second violation by the same agent, or a failed retry-counter write, falls through to the pre-existing warn-and-log behavior unchanged.
- **SubagentStop pending-dispatch exemption (#3015):** `subagent-stop.js` does not grade a reply while the subagent's own async `Agent` launches (`toolUseResult.isAsync`) lack a matching `task-notification` (by agentId or tool-use-id) before it — delivered either as an `origin.kind: 'task-notification'` user entry or as a `queued_command` attachment's `prompt` (an `api-request-blob` request echo of either is read too); a worker fork counts only its own launches after its `<fork-boilerplate>` user entry, not the parent history it inherits (a boundary echoed only inside an `api-request-blob` line is an unrecognized carrier and returns to normal grading); launches older than 60 minutes no longer count, and any unrecognized shape (a `<task-notification>` or `<fork-boilerplate>` in any other carrier included) returns to normal grading. Silent like the #2041/#2714 exemptions (no event). The #2041 immediately-after-signal exemption reads the same two completion carriers through one shared predicate (#3589). It does not read an `api-request-blob` echo, which repeats notifications already delivered. Residual risk: a child that never reports hides a violating final reply made within its 60-minute window, and that reply is never re-graded — a hung child leaves the skipped yield as the agent's last stop, so a skip-count ceiling would not catch it either.
- `post-tool-use-failure` (`PostToolUseFailure`, Bash only, log tier) — logs Claude Code's own worktree-isolation Bash refusal as `wd-guard-refusal` (`reason: harness-worktree-isolation`); every other tool failure is ignored (#2783).
- `user-prompt-submit` (`UserPromptSubmit`, no matcher, log tier) — records a typed `/claude-tweaks:<skill>` first line as `skill_invoked { skill, source: "user" }` in the owned run's `events.jsonl`, through the same run resolution as `skill-invocation.js`; a `skill_invoked` line without `source` is model-initiated (no `source: "model"` is ever written). `bin/lib/hooks/bash-prefilter.js` skips any payload lacking the substring `claude-tweaks:` before a heavy module loads, since the event fires on every human prompt and Claude Code waits for it. Read-only apart from the one `appendEvent`, offline-safe, and it never writes stdout, so it never blocks or annotates a prompt. Like the PostToolUse Skill hook, the strict owned-run resolution's `attribution: no run dir attributed` stderr diagnostic (`plugin/bin/hooks.js`) can fire once per typed prompt (or per prompt that merely mentions `claude-tweaks:`) when a candidate run is dropped; it is harmless under exit 0 and visible only in `--debug` output.
- **Git-stash worktree-hazard gate (warn tier, #1967):** `pre-tool-use.js`'s `checkGitStashWarn` fires on a bare `git stash` or `git stash pop` Bash command issued from inside a linked worktree — the stash stack is repository-wide, shared by every worktree of the same main checkout, so either shape can push onto or pop a sibling worktree's WIP. Unlike E1, there is no provable "whose stash entry is this" signal to deny on, so this is a warn-only `systemMessage` pointing at `git show <rev>:<path>` (read a baseline without mutating the tree) or a temporary WIP commit applied by SHA. Run-independent, like the `worktree-always` policy gate — it fires with no `$PIPELINE_RUN_DIR` at all. Read-only stash subcommands (`list`, `show`, `drop`, `apply`, …) are deliberately left alone, mirroring `git-command.js`'s own `PLUMBING_WRITE_SUBCOMMANDS` comment on why `stash` needs a second token resolved before its mutating shape can be told apart from its read-only one.
- **Powershell-opaque-command gate (block tier, #3061):** `pre-tool-use.js`'s `checkPowershellOpaqueCommand` denies a `powershell`/`pwsh` Bash call carrying `-Command` or `-EncodedCommand` under the same `worktree-always`-and-not-isolated condition the E1 gate above enforces — a deliberate, narrow exception to "ambiguity resolves to allow": `git-command.js`'s `gitTargets`/`fileWriteTargets` never read inside an interpreter's literal argument text (the same deliberately-uncovered class as `sh -c`/`python -c`), so a git call wrapped in `-Command`/`-EncodedCommand` would otherwise evade E1 entirely. The deny is content-agnostic — it fires on the shape, never on proving the text actually contains `git` — since there is nothing useful a content-aware check could still allow once the text is opaque to this module. `powershell -File <path>` alone (no `-Command`, no `-EncodedCommand`) carries no inline text and is never denied by this gate, the same not-opaque-text category a plain `bash script.sh` already falls into. Abbreviated flag forms (`-Com`, `-EncodedCom`, …) are a deliberate, documented miss, matching this module's usual best-effort posture.
- **Bash prefilter (#3074):** `hooks.json` registers ONE unconditional handler per tool-use event for `Bash` — never per-pattern `if` entries, which Claude Code runs all of (undeduplicated) whenever it cannot evaluate them statically (any `$VAR`, any loop), launching the hook 28 + 18 times for one call. `bin/hooks.js` instead consults `bin/lib/hooks/bash-prefilter.js` before any heavy `require`: it exits 0 — silent, except that a pre-tool-use Bash skip can print the guard normalizer's `hookSpecificOutput.updatedInput` JSON (the next bullet) — unless the command contains a covered word (`PRE_TOOL_USE_WORDS` / `POST_TOOL_USE_WORDS`) anywhere, as a shell word or path basename (the words are read both as typed and with every backslash-newline removed, since bash joins `g\` + newline + `it` into `git`, #4281), and it fails open to the full handler on anything unreadable or any non-`Bash` tool. It also runs the full handler whenever the command holds both a shell assignment (`NAME=`) and a `$NAME`/`${NAME}` reference, because `git-command.js`'s `substituteVars` can assemble a program name from pieces no single word spells (`G=gi; ${G}t push`); assignment values are scanned as words too, so `G=git; $G push` is reached. Known limit: a program name produced by command substitution (`$(echo git) push`) is not reached, and the handler cannot resolve it either. Bare shell redirection (the operators `GATE_COVERAGE.bashRedirections` names) has no command word to key on, so `hasFileRedirection` (pre-tool-use only — `fileWriteTargets` is the only consumer) runs `git-command.js`'s own `forEachShellSegment`/`redirectRawTargets`/`resolveWriteTarget` directly instead (a win32 drive-relative target such as `D:x` anchored at its own drive's root, since it resolves against any cwd on that drive, #4281; the guard parsers themselves give a drive-relative path on a different drive than the session cwd, `D:repo` from `C:\…`, no target, because the per-drive cwd Windows would resolve it against is not visible to the hook, so it fails open rather than fabricate a target), keeping `2>&1`/`> /dev/null` on the skip path by excluding fd duplications and `DEVNULL_LIKE` sinks the same way the parser does (#3080). Both the prefilter and `fileWriteTargets` walk `forEachShellSegment`, which drops heredoc bodies that an allowlisted data reader (`node`, `cat`, `python3`, …) reads and scans every other body as its own chunk, via `git-command.js`'s `stripHeredocBodies` (#3989, #4149). A `>` inside a `node … <<EOF` script is then not a redirect. The fail-closed cases are stated once, in the coverage block. A new Bash write shape or git action must be reachable through that word set — the word set is derived from `git-command.js`'s `GUARDED_PROGRAM_WORDS`, and `tests/hooks-bash-prefilter.test.js`'s differential corpus pins it against the five guard parsers for every command the corpus lists (#3092) — a new parser or word needs its own corpus line. A side effect: `checkGitStashWarn` is now reachable for a plain `git stash`, which no predicate ever named. `post-tool-use-failure` (#2783) is gated on a different signal, since it fires for every failed Bash call: it skips unless the payload (raw, or its parsed `error`) carries `Refusing to run it`, the phrase the harness worktree-isolation refusal it logs always contains. That phrase and the hook's regex both come from `bin/lib/hooks/harness-refusal.js`, and `tools/upstream-drift/manifest.yml`'s `claude-code` entry asserts those fragments, plus anchors unique to the matched templates, against the installed Claude Code binary, so a reworded refusal surfaces as upstream drift (when the upstream-drift sweep, `tools/upstream-drift/run.js` or the repo-local `/upstream-drift` skill, runs) instead of silently dropped `wd-guard-refusal` events. To verify launch counts, count processes (a launch logger prepended to `bin/hooks.js` in a `--plugin-dir` copy driven by `claude -p`), never `--debug-file` hook lines: the debug log prints one line per hook command per call, even when the old layout launched 28 processes for it.
- **Guard normalizer (#4028, no tier — it only rewrites):** `bin/lib/hooks/guard-rewrite.js`'s `rewriteForGuard` rewrites five Bash shapes the harness's worktree-isolation guard refuses although their meaning is fully known from the text, and hands the result back as `hookSpecificOutput.updatedInput`. Rule ids: `inline-literal-assignment` (a literal assigned then referenced), `plugin-root-placeholder` (`${CLAUDE_PLUGIN_ROOT}/bin/…`, a resolution — the Bash tool leaves the variable unset), `node-eval-separator` (`--` before a `$` operand of `node -e`/`-p`), `quote-escaped-space` (`a\ b` to `"a b"`), `drop-redundant-cd` (`cd <cwd> &&` when the shell is already there). Contract:
  - **Linked worktree only.** The default detector walks up to the first `.git` entry; a file means linked, anything else (a directory, unreadable, a symlink) means not. Anywhere else it returns nothing.
  - **Normalize, never bypass.** A PreToolUse `updatedInput` is applied before the guard and the guard re-checks the rewritten command (`docs/reference/pretooluse-updatedinput-worktree-guard.md`, measured on Claude Code 2.1.302), so the output never carries `permissionDecision`: an `allow` would skip the permission prompt for the rewritten text, and a rewrite into a refused form is refused anyway. `guardRewriteOutput` builds the `hookSpecificOutput` both wiring sites emit.
  - **Rules 1 and 2 decline on doubt.** They apply only when every command-position word is a plain literal outside the runner, reserved-word and computed-name-assigning builtin sets, and the command has no arithmetic context (`commandWordsPlain` and `hasArithmetic`; `tests/bin-lib/hooks/guard-rewrite.test.js` runs every positive case through bash and zsh and compares stdout, stderr and exit status). Rule 2 inlines only files under the plugin's own `bin/`. Residuals the text cannot show, stated in the module header: shell-snapshot functions and aliases (also reached through zsh glob qualifiers), a same-named file under another plugin's `bin/`, and `node-eval-separator`'s divergence for a runtime value starting with `-`, accepted by ruling.
  - **Never throws.** Any failure returns no rewrite, and the prefilter's plain silent skip (or `run()`'s unchanged outcome) stands. The module requires only `path` and `bin/lib/path-guard`.
  - **Wiring.** `bash-prefilter.js`'s `earlyGate` requires it lazily inside a try on a pre-tool-use skip and returns `{ raw, skip: true, json }`; `bin/hooks.js` prints that JSON with `writeSync` and exits 0. On the full path, `pre-tool-use.js`'s `run()` calls `withGuardRewrite` at both return sites: the merge applies on allow outcomes only (an outcome that already has a `hookSpecificOutput`, a deny included, is left as it is), keeps any `systemMessage`, and requires the module lazily inside a try so a load fault there never disables a deny gate (`tests/hooks-dispatcher.test.js` pins that a throwing load still denies).
  - **Instrument.** `tools/guard-refusals.js` counts the refusals per pipeline from the local transcript store (`docs/plugin-structure.md`'s `tools/` line).
- Run-dir state files written by hooks: `events.jsonl` (append-only typed events — including the runner-written `verify` event under `verify.js --run`, #1928; `gate-denial`, `wd-ambiguous`, and `wd-deny` are counted per run into `timing.json`'s `totals.guard` by `bin/phase-timing.js` (#1929); `contract-violation` fires only on a real `agent_transcript_path`, the parent-transcript fallback having been removed in #1928 — and never when that `agent_transcript_path` is identical to the same event's own `transcript_path`, a known-unreliable attribution narrowed out in #2036) and `run-state.json` (status: active | interrupted | clean, worktree assignment, `worktreeAtClose` — the prior worktree path a close keeps when it nulls `worktree`, so wrap-up verify can still check the directory is gone (#3023) — owning session id, owning Claude Code process id (`ownerPid`, from `CLAUDE_PID` at `record-worktree` time and at an ad-hoc mint, #3845), the `owner` block (who owns the run and when it last proved it was alive, #3973 — see Ownership), and — under `integration-model: pr-first` — the run's PR as `pr: { number, url, branch? }`). **`pr.branch` (#1672)** is recorded by the `record-pr` verb itself, derived from the still-live worktree at stamp time via `run-integrity.js`'s `deriveBranch`; it is optional and absent on every run stamped before #1672, and on any run whose worktree wasn't derivable. It exists so `run-integrity.js` can still name a run's branch *after* the worktree is torn down — the normal end state of a shipped run, and previously the point at which `checkRunIntegrity` fell open to `in-progress` permanently. **`pr.number` is the run's PR identity (#3416):** a worktree's branch name is reused across runs, so `reconcile/archive-merged.js` (both archive loops, via `resolveRunPrState`) and `reconcile/release-merged.js` (Phase 1.5) resolve a stamped run's PR with `gh pr view {pr.number}` first, falling back to `gh pr list --head {branch}` only when no number is stamped; a failed by-number probe skips the run for that pass rather than falling back to the branch (the one exception is claim release for a candidate with no resolvable branch at all, which keeps the #3249 issue-closed path) — and a probe that GitHub's GraphQL API confirms names no PR (a stale stamp) classifies `pr-not-found`, read from the structured `NOT_FOUND` error and never from gh's stderr text, and escalates through `archive-merged.js`'s structurally-stuck tracking once the run dir is past its 7-day TTL (#3543). Skills write run-state only through `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" record-worktree <path>` / `close-run` (plus the one creation-time stamp: wrap-up Phase 1 writes the initial `run-state.json` with `createdBy` when it creates a standalone run dir). `resolve-run-dir --create` (#692) may mint the run *directory* itself (mkdir, plus `decisions.md`/`staged/` under `--standalone`) — but it never touches `run-state.json`: that first write is still exclusively `record-worktree`/`close-run`'s, or wrap-up's own creation-time stamp above. **A second creation-time stamp (#500, widened #1333):** `post-tool-use.js`'s `stampAdHocRunDir` mints and stamps a `{ts}-adhoc-standalone` run dir directly (both the `resolve-run-dir --create --standalone` mint and the `run-state.json` write, in-process — this is hook code itself, not a skill, so the "skills write run-state only through the CLI" rule above doesn't apply to it) when this session finds no run dir already owned yet AND either (a) an `EnterWorktree` call just fired, or (b) `ctx.cwd` is observed resolving to a worktree entry distinct from the main repo root for any other tool call — covering a worktree created by a tool other than claude-tweaks' own `EnterWorktree` (another plugin's worktree-management skill, a raw `git worktree add`), which never fires `EnterWorktree` at all. Path (b) is rate-limited to at most one `git worktree list` per session (a session-scoped marker file, `bin/lib/session-tmp.js`'s convention) — this hook fires on every `PostToolUse` event across every session, so an unconditional check would be a real perf cost. **(#1864)** That marker is written only after an attempted, resolvable lookup — when `ctx.cwd` no longer exists on disk (the shape an `ExitWorktree(action:'remove')` event's `PostToolUse` fires with, against the just-deleted directory), the lookup is skipped entirely and the marker is not written, since a failure there means the check never actually ran, not that it ran and found nothing; writing the marker anyway would have permanently defeated path (b) for a later raw `git worktree add` in the same session. Closes the ad-hoc-worktree-dev-session blind spot in `skills/reflect/full-mode.md`'s Friction Lens for both worktree-creation paths, not just claude-tweaks' own. It never overwrites a genuinely owned run: gated on `ctxLib.isTrustedOwnedRun(ctx.ownedRun)` — a `fallback`-attributed guess does not count as owned (#2783) — and `resolveRun`'s session arm prefers a formal session-owned run dir over a newer ad-hoc one when that formal run is bound to the caller's own worktree (`classifyOwnership` `'mine'`), so a formal pipeline's later `record-worktree` stamp is never shadowed — while an older formal run whose binding is merely unprovable (its worktree since removed) never displaces the ad-hoc dir. **Not a pipeline run (#2783):** an ad-hoc dir holds only friction events, so every consumer asking which pipeline run a worktree or caller belongs to skips it — the teardown gate and `reap-merged.js`'s reap trail (`findRunByWorktreePath`'s `skipAdHoc`), the mutating verbs' implicit `--run` resolution, `resolveRun`'s fallback guess (hence `ctx.runDir` and E1), and the stale-run banner (`collectStaleRuns`). **Lifecycle (#1117):** a `-adhoc-standalone` dir never gets `config.yml` in practice either (`/flow`'s Manifesto is what writes one; `bin/set-config.js`'s `setConfigLever` also creates the file in whatever run dir its `--run` names, but no caller ever points it at an ad-hoc dir), and is deliberately long-lived — a real dev session can go untouched for days before `/claude-tweaks:wrap-up` finally reads its friction record. `reconcile/archive-merged.js`'s `isOrphanedMint` (below) is a blind mtime heuristic built for a different case (an abandoned `/flow`/`/dispatch` pre-Manifesto mint), so it exempts any `-adhoc-standalone`-suffixed dir (`isAdHocStandaloneMint`) outright rather than racing it against a 24h TTL. It carries a real `worktree` in its `run-state.json`, unlike a genuine orphaned mint, which has none — but the ordinary merged-PR path `archiveMerged` runs for every other run dir does not reliably reach an ad-hoc dir in practice: it requires two things an ad-hoc dir does not get: a resolvable branch — since #1684 the still-registered worktree at sweep time, or, when none resolves, `run-integrity.js`'s `fallbackBranch` (`run-state.json`'s `pr.branch`, or a `decisions.md` PR-early lifecycle line), neither of which an ad-hoc session normally writes — and a `console.json` written into that exact directory, which nothing in this codebase writes there. **A genuinely-abandoned ad-hoc dir (its recorded worktree no longer resolves in a fresh `git worktree list` at all — the session has definitively ended) is swept separately once `ADHOC_SUPERSEDED_TTL_MS` (30 days) has elapsed since it was last touched (`isAdHocStandaloneSuperseded`, #1604); a still-live one (worktree still registered) is never swept by this path regardless of age, preserving #1117's own invariant unchanged.** A main-checkout ad-hoc dir, which `adhoc-superseded` can never claim, is swept by `adhoc-session-ended` once its session reads `dead` and 7 days have passed (#4179), and every genuine ad-hoc dir is exempt from `structurally-stuck` escalation at `no-branch`/`no-worktree`/`no-pr` (#2724, `isAdHocIntrinsicSkip`, widened by #4179) — no branch, worktree or PR is its normal state.
- **`record-worktree` requires `--run` — no implicit fallback (#1124).** Before #1124, omitting `--run` fell through to the newest-non-terminal-run resolver (the "Two resolutions, not one" note below), which could silently target and corrupt a *different*, live sibling session's `run-state.json` — reproduced 3 times independently in one firing against this same subcommand, including via a bare `--help` invocation (the fallback resolved before argument parsing ever rejected the call). `record-worktree` now refuses outright — `claude-tweaks: record-worktree requires --run`, non-zero exit, no write of any kind — whenever `--run` isn't passed explicitly; every sanctioned caller already names its own run directory, so nothing legitimate relies on the old guess. Always pass an explicit, anchored `--run <dir>` naming this session's own run directory for a real invocation — a bare `--help`/`-h` is exempt since #1143's dedicated dispatch-table guard intercepts it before this check (or any other documented verb's own check) ever runs, printing that verb's usage and exiting 0 with no run-dir resolution at all.
- **Archived is terminal (#208), writer side only since #1103's fix-wave-1.** Once a run-id exists under `.claude-tweaks/pipelines/archive/{run-id}/`, `run-dir-resolve.js`'s `resolve()` — the one writer chokepoint for `.claude-tweaks/pipelines/{run-id}/` creation — refuses to (re-)create or reuse a live directory sharing that run-id's name (adopted `PIPELINE_RUN_DIR` env var, `newestMatch` reuse, and both `--create` mint branches all carry the guard); this half fails OPEN on a read error other than "doesn't exist" — an unreadable `archive/` creates exactly as it did before this invariant existed, never silently suppressing a genuinely unfinished run. The reader side (`context.js`'s `iterRunDirsWithState`) no longer treats mere existence of `archive/{run-id}/` as proof of a completed archive: `archiveRunDir` (`reconcile/archive-merged.js`) creates that directory via `fs.mkdirSync` as its very first action, before any content moves, so an existence-only reader check stranded any run whose archival then failed partway (git-mv-failed, commit-failed, tracked-entry, move-failed, …) as permanently "already archived" — the literal double-nesting bug #1103 reports. The reader now relies solely on the archive twin's own `run-state.json` genuinely reading `status: 'clean'`; a resurrected or corrupted twin state, or an empty/incomplete twin, no longer hides the live run dir.
- **An explicit `--run <dir>` must be *anchored*, not merely real** (`#790`/`[IL-127]`). The fourteen subcommands that accept it — `record-worktree`, `record-pr`, `spec-status`, `manifest-init`, `close-run`, `teardown-run`, `check-resume-freshness`, `check-staged-inventory`, `check-session-residue`, `check-pass-reentry`, `archive-run`, `delete-ledger`, `resolve-ledger`, `resolve-console` — resolve the value against the caller's cwd and then require it to sit under the main checkout, the same adoption-time check `_shared/pipeline-run-dir.md` applies to `PIPELINE_RUN_DIR`. A separator-free value (a bare run-id basename) whose cwd-relative reading is not a directory is retried under `<main checkout>/.claude-tweaks/pipelines/<value>` before being rejected (#3025) — the form `/claude-tweaks:dispatch`'s `$RUN_ID` passes. A path that exists but resolves inside a linked worktree is ordinarily a shadow copy `git worktree remove` later destroys, so it is refused (`--run path rejected: …`) and nothing is recorded, rather than written to the shadow; a cwd with no determinable git root is refused separately, with its own distinct reason. One narrow exception (`#280`): a worktree-local candidate that resolves inside a linked worktree of this same repo, under a run-id-shaped `.claude-tweaks/pipelines/` segment, and is already an *initialized* run dir (carries `decisions.md`, `run-state.json`, or `config.yml` — not a bare `mkdir`), with no counterpart at the same pipelines-relative path under the main checkout, is adopted instead of refused — the recovery path for a session whose harness refused every main-checkout write and so had no anchored copy to name in the first place; see `_shared/pipeline-run-dir.md`'s "Worktree-local `--run` fallback (#280)". Refusal exits 0 for every one of these subcommands except `close-run`, which exits 1 so a scripted caller can tell "not closed" apart from a successful close (#3025), `resolve-console`, which exits 1 on any unresolved console (#2568), and `check-pass-reentry`, which exits 1 (and prints nothing on stdout) so its skill caller reads a refusal as a stop rather than a verdict (#3553) — the never-break-a-session invariant is not widened by any of them. `bin/wrap-up-engine.js` and `bin/materialize.js` carry the same guard on their `--run-dir`, where it surfaces as exit 2 instead (`docs/plugin-structure.md`'s command reference). Default to a standalone `bin/{name}.js` sibling when a same-purpose precedent CLI already exists; default to a `hooks.js` subcommand only for the first one, or for state genuinely coupled to hook enforcement itself.
- **Two resolutions, not one** (`context.js`'s `resolveRun`, since 6.47.0): enforcement reads the newest non-terminal run *regardless of owner* — E1's foreign-session warning exists precisely to tell a bystander the checkout belongs to someone else's worktree. Anything that **writes** (event breadcrumbs, `interrupted`/`lastEvent` stamps) uses the ownership-scoped `ctx.ownedRun` instead: a run owned by another session is never written to, and an unowned run is written to but tagged `attribution: "fallback"`. Ownership is stamped only by `record-worktree`, so runs that never provisioned a worktree stay unowned by design `[IL-96]`. `session-end`'s `interrupted` stamp is additionally withheld, with no event written, when the run's `ownerPid` and the ending process's `CLAUDE_PID` are both known and differ (a nested `claude -p` started from the owner's session, which can share its session id, #3845) — and only while the `ownerPid` process is still alive, so a crash followed by a resume in a new process still stamps; unknown on either side keeps the pre-#3845 behaviour. The stamp never outlives the process it names: a `resume` SessionStart (`source: "resume"`, the owning session id returning under a new process) re-stamps an already-stamped run's `ownerPid` with the resumed process's pid, while a `startup` SessionStart (what a nested `claude -p` looks like) never does. Fallback attribution additionally skips *unadopted mints* — run dirs carrying no `run-state.json` and either no `decisions.md` or one holding only `flow` Step 2.8's claim-log lines — its claim, canonical or paraphrased, plus its file-overlap / `bot:in-progress` projection notes (`classifyDecisions` → `'claim-log-only'`, #3363, #3665; an empty or unreadable `decisions.md` still counts as adopted) — a `dispatch` Step 4 / `flow` Step 2.8 mint that no invocation initialized — so a fresh mint can never absorb foreign events; consequently the no-`--run` CLI fallback (`record-pr`/`close-run` — `record-worktree` no longer has one, #1124) only ever resolves an adopted run (#721). **Claim-log-only mints and strict attribution (#3515):** the claim-log-only half of that mint check is tested first (`isClaimLogOnlyMint`), so a strict resolution names the skipped mint in its `dropped` list rather than skipping it silently — the #3401 incident's write was pre-tool-use's `gate-exempt-gitignored` breadcrumb, logged against `ctx.runDir`. `ctx.ownedRun` alone resolves with `strictAttribution`, which additionally skips any candidate bound to a worktree other than the caller's resolved toplevel (a main-checkout caller included, and a binding gone from disk); E1's owner-unfiltered `runDir` stays non-strict so it can still resolve a worktree-bound run from the main checkout. When the #3515 skips leave `ctx.ownedRun` with nothing, the dispatcher prints one `attribution: no run dir attributed — …` line to stderr per hook process, and nothing is attributed to `ctx.ownedRun`. **Worktree-aware since #1410:** a candidate is also skipped when `classifyOwnership` (#1098's composite session+worktree-binding predicate) classifies it `'foreign'` — provably bound to a different, still-live worktree than the caller's own cwd, regardless of session id. This closes the cross-worktree shape (a concurrent sibling worktree's event — e.g. an `ask-user-question` answered in one session — landing in an unrelated run's `events.jsonl`, tagged `attribution: "fallback"`) without narrowing the fallback for any candidate lacking a provable worktree binding — `classifyOwnership` fails open to `'indeterminate'`, never `'foreign'`, on unprovable evidence. Both sides of that comparison must be provable, which bounds how far the skip reaches: the caller's own cwd must itself resolve inside a *linked* worktree (a caller in the main checkout — where most hook firings happen — classifies `'indeterminate'` and still guesses into the candidate — for E1's `runDir` only; the strict write path above skips it), and the candidate's recorded `worktree` must still exist on disk as a directory. `classifyOwnership` also returns `'foreign'` on a bare session-id mismatch, but neither fallback arm reaches that branch: the unknown-caller arm has no session id to compare against, and the known-caller arm only ever tests candidates whose `run-state.json` records no `sessionId` at all. **Ad-hoc dirs are never guessed into (#2783):** both fallback arms also skip any `-adhoc-standalone` dir (`isSkippableFallbackCandidate`'s `isAdHocRunDir` check), since one holds a single session's friction events and is reachable by that session only through the session arm; the session arm's ad-hoc-vs-formal preference is stated in the `stampAdHocRunDir` bullet above.
- **Background convergence (`integration-model: pr-first` only):** `plugin/bin/lib/reconcile/` (fast-forward, worktree reap, claim release, run-dir archive, branch archival, merged remote-branch pruning, residue-ledger removal PRs, console execution, red-tip detection) runs from SessionStart and dispatch's own trigger points — a session that opened a run's PR need not be the one that finishes it, since state converges from GitHub, not from session continuity. **SessionStart splits the set in two (#820)**: the cheap read/detect checks (fast-forward, red-tip, console detection) run inline in the hook's own process, while the write-only janitorial ones (claim release, run-dir archive, branch archival, merged remote-branch pruning, residue-ledger removal PRs, worktree reap) run in a detached `node plugin/bin/hooks.js reconcile-background` child process — so their outcome is surfaced exactly once, on a LATER SessionStart firing, always one session's worth of latency behind. Six scoping rules keep this gate from over- or under-firing:
  - **Run-scoped sentinel.** `hasMaterializeCommit(worktreeRoot, runDir)` builds its pathspec from `path.basename(runDir)` — `.claude-tweaks/pipelines/{run-id}/work` plus the multi-record `.claude-tweaks/pipelines/{run-id}/spec-*/work/*` — relative to the worktree root, where `flow/materialize.md`'s worktree-local mirror of the run dir lives. The multi-record arm needs its **trailing** `/*`: git's default pathspec wildcards only apply to the final path component, so `spec-*/work` never matches (measured). The `git log` is further range-bound to `{integration}..HEAD` (`resolveIntegrationBranch`, `#1674`): once a run's materialize commit merges into the integration branch, an unbounded walk would match it in every later worktree's inherited history and arm the gate against runs that never materialized a commit of their own; a bound that can't be used — `resolveIntegrationBranch` returning `null`, **or** returning a name git can't resolve (a stale `integration-branch:` key; `readIntegrationBranch` does no ref-existence check) — falls back to the pre-`#1674` unbounded walk rather than returning `false`, since `false` here means *the gate is not armed* and disabling a protection on a config typo is the worse trade. That fallback keeps IL-131 armed but, before `#1688`, did not extend `#1674`'s fix to those repos: a no-remote project still had a real local integration branch that was merely unresolvable, so the inherited-history false positive persisted there. `#1688` closes that gap with a third resolution source scoped to this call site alone — a local `main`/`master` probe (`resolveLocalDefaultBranchBound`), tried only when `resolveIntegrationBranch` itself comes up empty — and separately fixes a related staleness: whichever of the three sources produced the bound is upgraded to its already-on-disk `origin/{name}` remote-tracking ref when one exists (`preferRemoteTrackingRef`, no fetch), so a lagging local ref that has already merged `origin/{integration}` in (as `worktree-setup.md`'s post-creation catch-up does routinely) no longer reproduces the same inherited-history arm. `#2571` fixed a further blind spot in this same function: a multi-spec `/flow` run's per-spec skill invocations receive `$PIPELINE_RUN_DIR` = `{parent}/spec-{N}/`, not the parent — `path.basename(runDir)` of that value is `spec-{N}`, which carries no ISO-timestamp prefix and is never itself a real top-level run id, so the pathspec built from it never matched the real committed path `{parent-run-id}/spec-{N}/work/{N}-spec.md` and the gate stayed permanently disarmed for every multi-spec run. `perSpecPathspec` now detects this shape — a bare `spec-{digits}` basename whose *parent* directory basename is itself run-id-shaped (`RUN_ID_RE`) — and resolves the pathspec against the parent's run id, scoped to this one spec's own nested `work/` rather than the `spec-*` wildcard the parent-dir branch above uses.

On a provable owner-vs-caller mismatch the gate warns instead of denying, exactly as E1 does — otherwise the deny's own `record-worktree --run` remediation would tell the agent to corrupt that sibling's `run-state.json` (the `--run` rule at the top of this list). ## Ownership

Composite identity, not raw session-id equality (`#1098`, hardened by `#1012`/`#1099`): `classifyOwnership(caller, runState)` in `context.js` compares two independent axes — `caller = { sessionId, cwd }` against exactly two fields of `runState`, its own `sessionId` and `worktree` — and returns exactly one of three verdicts: `'mine'`, `'foreign'`, or `'indeterminate'`. A session-id match on both sides is NOT sufficient evidence of ownership: *`CLAUDE_CODE_SESSION_ID` is shared across all subagents of a session (observed 2026-08-20 via the #965 probe, recorded in parent #1096 — scope: Task-tool subagents of an interactive session; re-verify before extending the claim to cloud Routines or headless runs, and re-verify if harness session handling changes); it identifies the session, never the agent; no ownership decision may treat its equality as sufficient.* Session ids that provably differ short-circuit straight to `'foreign'`; every other case routes through the worktree-binding axis: a caller resolving inside the run's recorded `worktree` is `'mine'` (binding outranks incomplete identity; both the binding and git's toplevel resolve through path-guard's `.native` `canonicalRealpath`, so a binding that differs only in letter case on a case-insensitive volume still matches, #3836 — the same holds for `findRunByWorktreePath` (since #3769), `findRunsByWorktreePath` and `resolveRun`'s strict-attribution skip); a caller provably inside a *different* live worktree than a binding that provably exists on disk is `'foreign'`; a caller in the main checkout with no binding but matching ids is `'mine'`; and every case the predicate can't prove either way — an unresolvable or non-absolute `cwd`, a binding gone from disk, a caller outside any known checkout, equal ids from inside a worktree with no binding — degrades to `'indeterminate'`. Fail-open by design: unprovable evidence never classifies `'foreign'`, preserving `resolveRun`'s own documented asymmetry (an unowned run may still be ours; a provably-foreign run never is).

The five mutating run-state verbs (`close-run`, `record-worktree`, `record-pr`, `spec-status`, `teardown-run`), plus `delete-ledger` (#2544 — it deletes the run's ledger file rather than run state, but takes the same path) and its read-only twin `resolve-ledger` (#3897), resolve an omitted `--run` through this predicate via `resolveRunArg`'s `unambiguousOnly` path (`resolveImplicitRunUnambiguous` in `hooks.js`, `#1012`) — replacing the pre-`#1012` "newest non-terminal run" guess with an unambiguous-only order: **(1)** `PIPELINE_RUN_DIR` env, resolved as-is and unfiltered (the write-time ownership guard below is what protects this arm — an inherited env var reaching a foreign run is a documented pollution vector, `#1038`); **(2)** a cwd-binding reverse lookup (`findRunByWorktreePath`) — a run whose recorded `worktree` IS the caller's own cwd is provably this caller's, even with N siblings live; **(3)** otherwise every non-terminal run dir is scanned and any candidate classifying `'foreign'` against this caller is excluded — exactly one survivor is acted on. Two or more survivors, or zero survivors among one-or-more total candidates, refuses outright and lists every candidate as a paste-ready `--run <dir>` line (foreign ones annotated `(recorded by another session/worktree)`) rather than guessing: `claude-tweaks: multiple candidate runs — pass --run explicitly:` for two-or-more survivors after filtering, or `claude-tweaks: the only candidate run(s) are recorded by another session/worktree — pass --run explicitly to act on one:` when every candidate was excluded as foreign. Genuinely zero non-terminal runs system-wide falls through to each verb's ordinary "no pipeline run dir found" message instead of an empty refusal listing.

**Explicit `--run` always overrides** this whole implicit-resolution ladder (subject only to the anchoring check earlier in this file) — it is the one documented way to act on a run this predicate would otherwise refuse or exclude. `record-pr` and `spec-status` additionally carry a narrower write-time guard: an *implicit* resolution (no `--run`) whose resolved run still classifies `'foreign'` — reachable only via the unfiltered env-var arm above, since arms (2)/(3) already exclude foreign candidates by construction — refuses the write (`claude-tweaks: run {id} was recorded by another session/worktree — refusing to record a PR/spec status against it without an explicit --run`); an explicit `--run` bypasses this guard too. `close-run` carries its own analogous foreign-owner and live-worktree refusals via `closeRunState`, documented at that function's own call sites rather than restated here.

**The `owner` block and `runLiveness` (#3973).** `run-state.json` carries `owner: { sessionId, host, pid, pidSource, pidStartedAt, heartbeatAt }` beside `ownerPid` (#3845). **Removal condition for top-level `ownerPid` (#4153):** `owner.pid` is the newer stamp of the same process, and `ownerPid` survives only because `isNestedSession` (session-end's nested-session guard) is its only reader that gates behaviour (`restampOwnerPidOnResume` reads it only to maintain it); retire it — `ownerPidPatch` stops stamping it and session-start's `restampOwnerPidOnResume` is deleted — once `isNestedSession` reads `owner.pid`, which first needs every writer that stamps `ownerPid` to stamp the owner block too (`record-worktree` stamps `ownerPid` from `CLAUDE_PID` alone but writes the owner block only with `CLAUDE_CODE_SESSION_ID`); tracked by #4318, the record that carries out that reader migration. `pid` is the owning Claude process and `pidSource` says how it was found: `env` (`CLAUDE_PID`, which a hook process receives as its own session's `claude` pid — measured on Claude Code 2.1.302), `ancestry` (the nearest `claude` ancestor, at most 8 `ps` hops), or `null` when neither answers. `pidStartedAt` is the raw `ps -o lstart=` string taken under `LC_ALL=C`/`TZ=UTC`, compared by equality only and never parsed; `null` on win32 or when `ps` fails. Writers: `record-worktree` (only with `CLAUDE_CODE_SESSION_ID`, and it is the adoption path, so it alone replaces another session's block) and both ad-hoc mints (`post-tool-use.js`'s `stampAdHocRunDir` and `context.js`'s `stampAdHocRunDirForDenial`); any other stamp never replaces a block carrying a different session id (`ownerStampPatch`). A hook failure degrades to a stamp without the block. **Heartbeat (`refreshOwnerBlock`):** the owner's own hooks rewrite `heartbeatAt` at most once per `HEARTBEAT_THROTTLE_MS` (60 s, `run-liveness/constants.js`), only for owner-attributed events — never `fallback`, never another session's run — from the dispatcher's common path before `mod.run` for every event except `session-start`, which refreshes itself before its reconcile spawn. Events the Bash/prompt prefilter at the top of `hooks.js` short-circuits never reach the dispatcher and so never heartbeat; the PID probe is the backstop. A heartbeat is not strictly behavior-neutral: each write (tmp file, rename, lock dir) moves the run dir's mtime and bumps `updatedAt`, which `archive-merged.js`'s mtime-based TTLs (`isStaleDir`: orphaned-mint 24 h, adhoc-superseded 30 d, adhoc-session-ended 7 d, structurally-stuck 7 d) read — the safe direction, since a sweep is only delayed while the owner is actively firing hooks. The same call **re-stamps** pid, `pidSource`, `pidStartedAt`, host and `heartbeatAt` in one write (a `claude --resume` under a new process, or a reused pid), but only when the stored owner process is not provably alive — the decision is `run-liveness/owner-pid-probe.js`'s `probeOwnerPid`, the same probe `runLiveness` reports as its owner-pid entry (#4153), and only `other-host`, `no-pid`, `gone` and `pid-reused` allow a re-stamp; every `error` keeps the block, including a `null` start time (`start-time-unavailable`) and a stored `pidStartedAt` that is not a `ps` string (`invalid-start-time`); only a non-null, differing start time is pid reuse — a nested `claude -p` sharing the session id neither heartbeats nor takes the block over. A run-state with no `owner` block is **legacy**, never an error: the heartbeat never gives a legacy run a block; only a fresh stamp by one of the writers above does. `run-liveness/index.js`'s `runLiveness(runDir)` reads the block and injectable probes (owner pid, heartbeat, worktree lock, last commit, owner events) into a `live | dead | unknown` verdict with its evidence: a positive among owner pid (alive, start time matching), heartbeat (younger than 10 min), worktree lock (in use) or last commit (younger than 10 min) → `live`; else any probe that could not answer (an `error`, never folded into "no") → `unknown`; else a death witness (the owner pid gone or reused; or a SessionEnd after the last heartbeat with the run stamped `interrupted`/`session-end`, when the owner pid is unknown or alive with no stored start time to check it against — every death witness except the legacy one needs an owner block; or, for a legacy run, no owner event for 72 h (with no owner events at all, the age is measured from the run id's own timestamp) with no in-use lock and no commit for 72 h or no commits/worktree at all) → `dead`; else `unknown`. A block whose `sessionId` differs from the run-state's current non-empty `sessionId` (an older build re-stamping through `record-worktree` spreads the old block under a new session id, as does the block-build-failed fallback) is not evidence about the current session: the owner-pid and heartbeat entries are `error` / `owner-session-mismatch`. An `invalid-now` (non-finite `now`) makes all five entries `error`; a non-string stored `pidStartedAt` on a live pid is `error` / `invalid-start-time`; and the SessionEnd witness counts only `session-end` events whose `sessionId` is the owner block's. In the lock and commit probes a recorded worktree path that is missing is a `no-worktree` negative, while an unreadable one, or one that is not a directory or symlink, is an `error`, and so is an existing directory that `git worktree list` does not list for its main checkout. A `run-state.json` that exists but cannot be read as a JSON object makes the owner-pid, heartbeat, lock and commit entries `error` / `unreadable-run-state` (an absent file is a legacy run), and a stored `pid` above int32 is `no-pid`, never a death witness. One caller consumes the verdict: `archive-merged.js`'s `adhoc-session-ended` sweep (#4179), through `adHocSessionLiveness`, which neutralises the lock and commit probes for a main-checkout dir; the remaining consumers are #3977 and #3979.

Also consulted at PreToolUse (`#1099`): `checkTeardownGate` and the E1 wrong-checkout deny in `pre-tool-use.js` route their own same-session-sibling-worktree checks through `classifyOwnership` instead of raw session-id equality — a sibling agent of the same session bound to a different live worktree now classifies `'foreign'` (warn + allow, `wd-foreign-teardown`/`wd-foreign-session` events) rather than being treated as the run's own session (same-session deny), closing the enforcement-side half of the gap `[IL-152]` documents.
