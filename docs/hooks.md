# Hooks

All hook registrations route through `plugin/bin/hooks.js <event>` — one dispatcher, one module per event in `plugin/bin/lib/hooks/`. Rules:

- **Never break a session.** Every path — including a PreToolUse deny — exits 0; no module ever sets a non-zero `exit`. A deny is communicated entirely via `hookSpecificOutput.permissionDecision: 'deny'` in the stdout JSON, not the process exit code (see `pre-tool-use.js`'s own header comment for why exit 2 doesn't work for this). New modules must pass the garbage-stdin invariant test in `tests/hooks-dispatcher.test.js`.
- **Tiered posture per `_shared/auto-mode-contract.md`:** block (E1 wrong-checkout commit; the `worktree-always` policy gate), warn (non-blocking systemMessage), inform (SessionStart additionalContext), log (append to the run dir's `events.jsonl`). What that gate covers, what it deliberately doesn't, and its one `.claude-tweaks/pipelines/` exemption are stated once — in `plugin/skills/_shared/policy-schema-coverage.md`'s `worktree-always` coverage block, pinned to `pre-tool-use.js`'s exported `GATE_COVERAGE` by `tests/hooks-gate-coverage.test.js`. Don't restate the list here or anywhere else; five files did and all five went stale `[IL-93]`.
- **Project-agnostic by construction:** modules key off plugin-owned state (`$PIPELINE_RUN_DIR`, `.claude-tweaks/pipelines/`, `.claude-tweaks/policy.yml`), never off project structure. E1/E2/E3 no-op without a resolved run dir — the `worktree-always` policy gate is the one PreToolUse check that is deliberately run-independent, since its job is to require a worktree even before any pipeline run exists. `post-tool-use.js`'s closing-keyword check (warn tier) is the analogous exception on the PostToolUse side — it fires on any `git commit` regardless of run-dir state, since the gap it catches (a fix commit made outside the structured `/specify` → `/build` → `/wrap-up` pipeline, with no closing keyword) is exactly a commit that would never resolve a run dir in the first place. The deferred-subproject capture check (also warn tier) mirrors this on `Write`: it fires on any write to `docs/superpowers/specs/*-design.md` regardless of run-dir state, since a brainstorming session that hasn't reached `/specify` yet has no pipeline run dir to gate on either.
- **Ambiguity resolves to allow** — E1 denies only provable mismatches. A recorded worktree whose path no longer exists also resolves to allow (fail-open) — tear-down without close-run ends enforcement, not the session. Ownership counts toward provability: `record-worktree` stamps the recording session's id (`CLAUDE_CODE_SESSION_ID`), and a wrong-checkout commit from a *different* session is allowed with a warn (`wd-foreign-session` event) instead of denied; missing identity on either side falls back to deny.
- **Git-stash worktree-hazard gate (warn tier, #1967):** `pre-tool-use.js`'s `checkGitStashWarn` fires on a bare `git stash` or `git stash pop` Bash command issued from inside a linked worktree — the stash stack is repository-wide, shared by every worktree of the same main checkout, so either shape can push onto or pop a sibling worktree's WIP. Unlike E1, there is no provable "whose stash entry is this" signal to deny on, so this is a warn-only `systemMessage` pointing at `git show <rev>:<path>` (read a baseline without mutating the tree) or a temporary WIP commit applied by SHA. Run-independent, like the `worktree-always` policy gate — it fires with no `$PIPELINE_RUN_DIR` at all. Read-only stash subcommands (`list`, `show`, `drop`, `apply`, …) are deliberately left alone, mirroring `git-command.js`'s own `PLUMBING_WRITE_SUBCOMMANDS` comment on why `stash` needs a second token resolved before its mutating shape can be told apart from its read-only one.
- Run-dir state files written by hooks: `events.jsonl` (append-only typed events — including the runner-written `verify` event under `verify.js --run`, #1928; `gate-denial`, `wd-ambiguous`, and `wd-deny` are counted per run into `timing.json`'s `totals.guard` by `bin/phase-timing.js` (#1929); `contract-violation` fires only on a real `agent_transcript_path`, the parent-transcript fallback having been removed in #1928 — and never when that `agent_transcript_path` is identical to the same event's own `transcript_path`, a known-unreliable attribution narrowed out in #2036) and `run-state.json` (status: active | interrupted | clean, worktree assignment, owning session id, and — under `integration-model: pr-first` — the run's PR as `pr: { number, url, branch? }`). **`pr.branch` (#1672)** is recorded by the `record-pr` verb itself, derived from the still-live worktree at stamp time via `run-integrity.js`'s `deriveBranch`; it is optional and absent on every run stamped before #1672, and on any run whose worktree wasn't derivable. It exists so `run-integrity.js` can still name a run's branch *after* the worktree is torn down — the normal end state of a shipped run, and previously the point at which `checkRunIntegrity` fell open to `in-progress` permanently. Skills write run-state only through `node "${CLAUDE_PLUGIN_ROOT}/bin/hooks.js" record-worktree <path>` / `close-run` (plus the one creation-time stamp: wrap-up Phase 1 writes the initial `run-state.json` with `createdBy` when it creates a standalone run dir). `resolve-run-dir --create` (#692) may mint the run *directory* itself (mkdir, plus `decisions.md`/`staged/` under `--standalone`) — but it never touches `run-state.json`: that first write is still exclusively `record-worktree`/`close-run`'s, or wrap-up's own creation-time stamp above. **A second creation-time stamp (#500, widened #1333):** `post-tool-use.js`'s `stampAdHocRunDir` mints and stamps a `{ts}-adhoc-standalone` run dir directly (both the `resolve-run-dir --create --standalone` mint and the `run-state.json` write, in-process — this is hook code itself, not a skill, so the "skills write run-state only through the CLI" rule above doesn't apply to it) when this session finds no run dir already owned yet AND either (a) an `EnterWorktree` call just fired, or (b) `ctx.cwd` is observed resolving to a worktree entry distinct from the main repo root for any other tool call — covering a worktree created by a tool other than claude-tweaks' own `EnterWorktree` (another plugin's worktree-management skill, a raw `git worktree add`), which never fires `EnterWorktree` at all. Path (b) is rate-limited to at most one `git worktree list` per session (a session-scoped marker file, `bin/lib/session-tmp.js`'s convention) — this hook fires on every `PostToolUse` event across every session, so an unconditional check would be a real perf cost. **(#1864)** That marker is written only after an attempted, resolvable lookup — when `ctx.cwd` no longer exists on disk (the shape an `ExitWorktree(action:'remove')` event's `PostToolUse` fires with, against the just-deleted directory), the lookup is skipped entirely and the marker is not written, since a failure there means the check never actually ran, not that it ran and found nothing; writing the marker anyway would have permanently defeated path (b) for a later raw `git worktree add` in the same session. Closes the ad-hoc-worktree-dev-session blind spot in `skills/reflect/full-mode.md`'s Friction Lens for both worktree-creation paths, not just claude-tweaks' own. It never overwrites an already-owned run: gated on `ctx.ownedRun.dir` being null, so a formal pipeline's own `PIPELINE_RUN_DIR`/`record-worktree` stamp is never shadowed. **Lifecycle (#1117):** a `-adhoc-standalone` dir never gets `config.yml` in practice either (`/flow`'s Manifesto is what writes one; `bin/set-config.js`'s `setConfigLever` also creates the file in whatever run dir its `--run` names, but no caller ever points it at an ad-hoc dir), and is deliberately long-lived — a real dev session can go untouched for days before `/claude-tweaks:wrap-up` finally reads its friction record. `reconcile/archive-merged.js`'s `isOrphanedMint` (below) is a blind mtime heuristic built for a different case (an abandoned `/flow`/`/dispatch` pre-Manifesto mint), so it exempts any `-adhoc-standalone`-suffixed dir (`isAdHocStandaloneMint`) outright rather than racing it against a 24h TTL. It carries a real `worktree` in its `run-state.json`, unlike a genuine orphaned mint, which has none — but the ordinary merged-PR path `archiveMerged` runs for every other run dir does not reliably reach an ad-hoc dir in practice: it requires two things an ad-hoc dir does not get: a resolvable branch — since #1684 the still-registered worktree at sweep time, or, when none resolves, `run-integrity.js`'s `fallbackBranch` (`run-state.json`'s `pr.branch`, or a `decisions.md` PR-early lifecycle line), neither of which an ad-hoc session normally writes — and a `console.json` written into that exact directory, which nothing in this codebase writes there. **A genuinely-abandoned ad-hoc dir (its recorded worktree no longer resolves in a fresh `git worktree list` at all — the session has definitively ended) is swept separately once `ADHOC_SUPERSEDED_TTL_MS` (30 days) has elapsed since it was last touched (`isAdHocStandaloneSuperseded`, #1604); a still-live one (worktree still registered) is never swept by this path regardless of age, preserving #1117's own invariant unchanged.**
- **`record-worktree` requires `--run` — no implicit fallback (#1124).** Before #1124, omitting `--run` fell through to the newest-non-terminal-run resolver (the "Two resolutions, not one" note below), which could silently target and corrupt a *different*, live sibling session's `run-state.json` — reproduced 3 times independently in one firing against this same subcommand, including via a bare `--help` invocation (the fallback resolved before argument parsing ever rejected the call). `record-worktree` now refuses outright — `claude-tweaks: record-worktree requires --run`, non-zero exit, no write of any kind — whenever `--run` isn't passed explicitly; every sanctioned caller already names its own run directory, so nothing legitimate relies on the old guess. Always pass an explicit, anchored `--run <dir>` naming this session's own run directory for a real invocation — a bare `--help`/`-h` is exempt since #1143's dedicated dispatch-table guard intercepts it before this check (or any other documented verb's own check) ever runs, printing that verb's usage and exiting 0 with no run-dir resolution at all.
- **Archived is terminal (#208), writer side only since #1103's fix-wave-1.** Once a run-id exists under `.claude-tweaks/pipelines/archive/{run-id}/`, `run-dir-resolve.js`'s `resolve()` — the one writer chokepoint for `.claude-tweaks/pipelines/{run-id}/` creation — refuses to (re-)create or reuse a live directory sharing that run-id's name (adopted `PIPELINE_RUN_DIR` env var, `newestMatch` reuse, and both `--create` mint branches all carry the guard); this half fails OPEN on a read error other than "doesn't exist" — an unreadable `archive/` creates exactly as it did before this invariant existed, never silently suppressing a genuinely unfinished run. The reader side (`context.js`'s `iterRunDirsWithState`) no longer treats mere existence of `archive/{run-id}/` as proof of a completed archive: `archiveRunDir` (`reconcile/archive-merged.js`) creates that directory via `fs.mkdirSync` as its very first action, before any content moves, so an existence-only reader check stranded any run whose archival then failed partway (git-mv-failed, commit-failed, tracked-entry, move-failed, …) as permanently "already archived" — the literal double-nesting bug #1103 reports. The reader now relies solely on the archive twin's own `run-state.json` genuinely reading `status: 'clean'`; a resurrected or corrupted twin state, or an empty/incomplete twin, no longer hides the live run dir.
- **An explicit `--run <dir>` must be *anchored*, not merely real** (`#790`/`[IL-127]`). The eight subcommands that accept it — `record-worktree`, `record-pr`, `spec-status`, `close-run`, `teardown-run`, `check-resume-freshness`, `check-staged-inventory`, `archive-run` — resolve the value against the caller's cwd and then require it to sit under the main checkout, the same adoption-time check `_shared/pipeline-run-dir.md` applies to `PIPELINE_RUN_DIR`. A path that exists but resolves inside a linked worktree is ordinarily a shadow copy `git worktree remove` later destroys, so it is refused (`--run path rejected: …`) and nothing is recorded, rather than written to the shadow; a cwd with no determinable git root is refused separately, with its own distinct reason. One narrow exception (`#280`): a worktree-local candidate that resolves inside a linked worktree of this same repo, under a run-id-shaped `.claude-tweaks/pipelines/` segment, and is already an *initialized* run dir (carries `decisions.md`, `run-state.json`, or `config.yml` — not a bare `mkdir`), with no counterpart at the same pipelines-relative path under the main checkout, is adopted instead of refused — the recovery path for a session whose harness refused every main-checkout write and so had no anchored copy to name in the first place; see `_shared/pipeline-run-dir.md`'s "Worktree-local `--run` fallback (#280)". Refusal still exits 0 — the never-break-a-session invariant is not widened. `bin/wrap-up-engine.js` and `bin/materialize.js` carry the same guard on their `--run-dir`, where it surfaces as exit 2 instead (`docs/plugin-structure.md`'s command reference). The two resolver CLIs — `bin/resolve-profile.js` (`--run-dir`) and `bin/resolve-policy.js` (`--run`) — carry the *anchored-or-outside* variant instead (`worktree-detect.js`'s `checkRunDirAnchoredOrOutside`, exit 1, #1065): paths outside any checkout stay accepted for their documented journey/test use; the two-rule split's canonical statement is `plugin/skills/_shared/pipeline-run-dir.md`'s Anchoring section (the CLI-argument-boundary guard). **`archive-run` on an adopted `#280` run dir (#1452):** its `git -C mainRoot mv` can never see a source path living only inside the linked worktree, so `archive-run` now detects a tracked `work/` on this fallback path upfront and defers with a distinct message rather than running (and misreporting as a generic `git-mv-failed`) a doomed move — the transient condition self-resolves once the run's branch merges. The fallback's own twin check (the `mainArchivedCandidate` comparison above) also now distinguishes a genuinely completed archive twin from a stale `{status: "archiving"}` claim stub `archiveRunDir` leaves behind on a failed attempt (`isLiveArchiveTwin`, TTL-bounded per `context.js`'s `ARCHIVE_CLAIM_TTL_MS`) — a stale stub no longer permanently blocks every later retry.
- Hook processes are spawned with the harness's own environment, so a `PIPELINE_RUN_DIR` exported inside a Bash tool call does not reach them; hooks instead resolve runs from the Bash call's cwd, and a commit issued from inside a worktree that contains no `.claude-tweaks/` resolves no run dir and is allowed (fail-open).
- **New pipeline-bookkeeping write verb: `hooks.js` subcommand, or a standalone sibling CLI?** `record-worktree`/`close-run`/etc. are `hooks.js` subcommands because they're hook-adjacent run-state writes with no independent precedent. `bin/log-decision.js` (#686) and `bin/stage-item.js` (#637) are standalone CLIs instead, each mirroring the other's shape (arg-parsing, `--run` anchoring, injectable-deps) rather than becoming `hooks.js` subcommands — once one pipeline-bookkeeping write CLI ships standalone, its sibling follows the same shape rather than forcing a rename into `hooks.js` (a silent breaking rename CLAUDE.md's expand-contract discipline forbids). Default to a standalone `bin/{name}.js` sibling when a same-purpose precedent CLI already exists; default to a `hooks.js` subcommand only for the first one, or for state genuinely coupled to hook enforcement itself.
- **Two resolutions, not one** (`context.js`'s `resolveRun`, since 6.47.0): enforcement reads the newest non-terminal run *regardless of owner* — E1's foreign-session warning exists precisely to tell a bystander the checkout belongs to someone else's worktree. Anything that **writes** (event breadcrumbs, `interrupted`/`lastEvent` stamps) uses the ownership-scoped `ctx.ownedRun` instead: a run owned by another session is never written to, and an unowned run is written to but tagged `attribution: "fallback"`. Ownership is stamped only by `record-worktree`, so runs that never provisioned a worktree stay unowned by design `[IL-96]`. Fallback attribution additionally skips *unadopted mints* — run dirs carrying neither `run-state.json` nor `decisions.md` (a `dispatch` Step 4 / `flow` Step 2.8 mkdir that no invocation initialized) — so an empty mint can never absorb foreign events; consequently the no-`--run` CLI fallback (`record-pr`/`close-run` — `record-worktree` no longer has one, #1124) only ever resolves an adopted run (#721). **Worktree-aware since #1410:** a candidate is also skipped when `classifyOwnership` (#1098's composite session+worktree-binding predicate) classifies it `'foreign'` — provably bound to a different, still-live worktree than the caller's own cwd, regardless of session id. This closes the cross-worktree shape (a concurrent sibling worktree's event — e.g. an `ask-user-question` answered in one session — landing in an unrelated run's `events.jsonl`, tagged `attribution: "fallback"`) without narrowing the fallback for any candidate lacking a provable worktree binding — `classifyOwnership` fails open to `'indeterminate'`, never `'foreign'`, on unprovable evidence. Both sides of that comparison must be provable, which bounds how far the skip reaches: the caller's own cwd must itself resolve inside a *linked* worktree (a caller in the main checkout — where most hook firings happen — classifies `'indeterminate'` and still guesses into the candidate), and the candidate's recorded `worktree` must still exist on disk as a directory. `classifyOwnership` also returns `'foreign'` on a bare session-id mismatch, but neither fallback arm reaches that branch: the unknown-caller arm has no session id to compare against, and the known-caller arm only ever tests candidates whose `run-state.json` records no `sessionId` at all.
- **Background convergence (`integration-model: pr-first` only):** `plugin/bin/lib/reconcile/` (fast-forward, worktree reap, claim release, run-dir archive, branch archival, merged remote-branch pruning, console execution, red-tip detection) runs from SessionStart and dispatch's own trigger points — a session that opened a run's PR need not be the one that finishes it, since state converges from GitHub, not from session continuity. **SessionStart splits the set in two (#820)**, and only SessionStart: the cheap read/detect checks (fast-forward, red-tip, console detection) run inline in the hook's own process, while the write-only janitorial ones (claim release, run-dir archive, branch archival, merged remote-branch pruning, worktree reap) run in a detached `node plugin/bin/hooks.js reconcile-background` child process — so their outcome is surfaced exactly once, on a LATER SessionStart firing, always one session's worth of latency behind. The inline pass additionally short-circuits entirely when another session in the same repo already ran it within a short TTL (`plugin/bin/lib/reconcile/cache.js`), trading that much staleness for a session start that costs nothing when sessions arrive in bursts. The `reconcile` subcommand and dispatch's own trigger points are unaffected — they still run the full set in one process. Red-tip is the one unconditional, inform-tier check in the set — a failing CI conclusion on the integration branch's tip surfaces at SessionStart regardless of `merge-verification` policy, since it's the only coverage for direct pushes no merge gate ever sees. Run-dir archive convergence has a blind spot, not a guarantee: `archive-merged.js` iterates via `iterRunDirsWithState`, which permanently skips any run whose `run-state.json` already reached `status: clean` — so a run that reached `clean` without being archived (a teardown path that marks terminal but misses the move) is invisible to this sweep forever, not just delayed. Archival must happen as part of teardown itself; `plugin/bin/residue.js`'s `pipeline-run` probe is the separate backstop that reads `.claude-tweaks/pipelines/` directly to catch dirs that already fell into this gap. Worktree reap never touches the calling session's own cwd, regardless of PR/lock state (#644, `reap-merged.js`'s `isOwnCwd`, skip reason `own-cwd`); a path stuck at `move-failed`/`removal-failed` for `RESIDUE_ESCALATE_THRESHOLD` consecutive passes (`cache.js`, persisted across process invocations so `reconcile-background` and the `reconcile`/`reconcile-summary` subcommands observe the same streak) escalates once via `escalate-residue.js` and never re-escalates while still failing. `node plugin/bin/hooks.js reconcile-summary` prints the one-line residue summary (`reconcile: {archived} archived, {stuck} stuck (oldest {age}), mirror ff {…}`) `/claude-tweaks:flow`'s closing report renders (`flow/summary-template.md`); the `reconcile` subcommand's JSON also carries the same line as `residueSummary`. A second, narrower blind spot (#848): `iterRunDirsWithState`'s `RUN_ID_RE` filter only recognizes the canonical dash-containing `YYYY-MM-DDT…` name — a non-canonical mint (e.g. a hand-typed `date -u +%Y%m%dT%H%M%S`, dashes dropped) is invisible to every check keyed off that enumeration, the same way an already-`clean` run is. Unlike that gap, this one is now surfaced rather than silent: `context.js`'s `findNonCanonicalRunDirs` scans for the dash-less shape and `reconcile`'s `index.js` reports any hit as a `non-canonical-run-dir` entry in `result.skipped` (naming the directories) on every pass, ahead of every other gate. All three run-dir mint sites now produce the canonical shape mechanically via `run-dir-resolve.js`'s `formatTimestamp()` (`resolve-run-dir --create`), so a fresh non-canonical name is not expected in practice — this is a defensive report, not a self-heal, since the directory is never renamed automatically. The detached child receives the spawning session's id via a `CLAUDE_TWEAKS_SESSION_ID` env var set at the `session-start.js` spawn site (never `CLAUDE_CODE_SESSION_ID` — unreliable for a hook-spawned process) — `bin/hooks.js`'s `reconcile-background` subcommand reads it and threads it into `reconcile({ sessionId })`, which is what lets `archive-merged.js`'s ownership gate (`isAbandonedInterrupted`) refuse to auto-close a run this same session still owns, on the one path that actually runs the `archive` check in production (#1687).
- **`worktree-always` verdict banner (inform tier):** `session-start.js` prints one `worktree-always: ON (matched key: worktree-always|worktree.always)` / `OFF (no key)` line per session, sourced from `plugin/bin/lib/policy.js`'s `resolveWorktreeAlways` — the same resolver `pre-tool-use.js`'s gate calls, so the announcement can never disagree with enforcement (`docs/incident-log.md` `[IL-133]`). Silent when no `policy.yml` exists anywhere in the ancestor chain, and silent (falls through to the existing best-effort `catch`, no throw) on any parse failure — it cannot itself widen the never-break-a-session invariant.
- **`port-services` lease line (inform tier, #1792):** when the `port-services` policy resolves non-empty, `session-start.js` calls `bin/lib/ports/ensure.js` and prints one `claude-tweaks: ports {base}-{base+9} (PORT=… {NAME}_PORT=…)` line — or, when a foreign process has taken the previously-leased block and `.env.local`'s managed region is stale, `claude-tweaks: ports REALLOCATED {from}→{to} — a foreign process took the old block; URLs moved: …` (never silent — a reallocation moves URLs). An invalid service name (fails `^[a-z][a-z0-9-]*$`) is dropped and reported on its own line; more entries than the registry's `BLOCK_SIZE` (10) disables port isolation for the session, also reported. `ensure()` throwing is caught and reported as `claude-tweaks: ports ensure failed — {message}`, same never-break-a-session posture as every other block in this hook. Unset `port-services` (the default) creates no `~/.claude-tweaks/ports.json` and prints nothing. The managed region's first line is `CLAUDE_TWEAKS_LEASE={base}` (#1927), the lease token a project can key a test database on; the rendered line lists only the port pairs.
- **Staged-proposal approval banner (inform tier, #1493 AC5):** `session-start.js` separately scans `.claude-tweaks/pipelines/` for `*-tidy-standalone*`/`*-sweep-standalone*` run dirs (the naming convention `tidy/step-6-auto.md`'s archival compaction already uses) whose `run-state.json` reached `status: 'clean'` but whose `staged/` directory is non-empty, and relays one line per run naming its `/claude-tweaks:tidy --approve <dir>` command, capped at `MAX_REPORTED`. This is deliberately a separate scan from the stale/interrupted-runs check above it in the file — `context.js`'s `iterRunDirsWithState` skips any run already at `status: 'clean'`, so a run that finished cleanly but still carries un-actioned staged proposals needs its own directory read to surface at all.
- **Bookkeeping-stamps gate (block tier, IL-131):** `pre-tool-use.js`'s `checkBookkeepingStampsGate` denies a covered Edit/Write/NotebookEdit/commit/push once **this run's own** materialize commit has landed on the run's branch but `record-worktree` never stamped `run-state.json.worktree`, or — under a `pr-first` run — `record-pr` never stamped `run-state.json.pr`. Same ambiguity-resolves-to-allow posture as E1: no materialize commit yet, `ctx.runDir` itself unresolved (a resolved run dir with no `run-state.json` yet is not this case — #1456, it falls through to the ordinary stamp-missing deny below instead), or a target outside a linked worktree all no-op. A run whose `decisions.md` already carries the mandated `PR-early run lifecycle: ... FAILED` degrade line is exempted from the PR-stamp deny — a genuine push/PR-create failure still degrades gracefully, never a hard block, and the deny message names `bin/log-decision.js` as the runnable way to log it. A second, narrower exemption (`#989`) covers the chicken-and-egg case the degrade-line exemption doesn't: a Bash `git push` whose every target is establishing that branch's upstream tracking ref for the first time (`hasNoUpstreamYet` — `@{u}` fails with a git-error exit) is allowed through even with no PR yet recorded, because that push **is** `pr-early-run-lifecycle.md` Step 2 itself — without it, the PR-stamp deny would fire on the one action a PR stamp cannot exist without, making `build/worktree-setup.md` Step 6 — the caller that invokes that whole procedure — structurally impossible to ever complete. (Note the two step numbers name two different files: `pr-early-run-lifecycle.md` itself has only Steps 1–4.) It is one-shot and never persisted as `prExempt`: a later push of an already-tracked branch still falls through to the ordinary deny when no PR was ever recorded, preserving IL-131's "keep pushing forever, never open the PR" close. Reuses `GATE_COVERAGE`'s existing tool/gitAction list — no `hooks.json` or coverage-prose change. Six scoping rules keep it from over- or under-firing:
  - **Run-scoped sentinel.** `hasMaterializeCommit(worktreeRoot, runDir)` builds its pathspec from `path.basename(runDir)` — `.claude-tweaks/pipelines/{run-id}/work` plus the multi-record `.claude-tweaks/pipelines/{run-id}/spec-*/work/*` — relative to the worktree root, where `flow/materialize.md`'s worktree-local mirror of the run dir lives. A repo-root-relative `work` pathspec could never match the canonical write location (the gate would be inert everywhere), and a widened `*/work/*` would match any legacy pre-anchoring top-level `work/*-spec.md` still in history and arm the gate on every branch. The multi-record arm needs its **trailing** `/*`: git's default pathspec wildcards only apply to the final path component, so `spec-*/work` never matches (measured). The `git log` is further range-bound to `{integration}..HEAD` (`resolveIntegrationBranch`, `#1674`): once a run's materialize commit merges into the integration branch, an unbounded walk would match it in every later worktree's inherited history and arm the gate against runs that never materialized a commit of their own; a bound that can't be used — `resolveIntegrationBranch` returning `null`, **or** returning a name git can't resolve (a stale `integration-branch:` key; `readIntegrationBranch` does no ref-existence check) — falls back to the pre-`#1674` unbounded walk rather than returning `false`, since `false` here means *the gate is not armed* and disabling a protection on a config typo is the worse trade. That fallback keeps IL-131 armed but, before `#1688`, did not extend `#1674`'s fix to those repos: a no-remote project still had a real local integration branch that was merely unresolvable, so the inherited-history false positive persisted there. `#1688` closes that gap with a third resolution source scoped to this call site alone — a local `main`/`master` probe (`resolveLocalDefaultBranchBound`), tried only when `resolveIntegrationBranch` itself comes up empty — and separately fixes a related staleness: whichever of the three sources produced the bound is upgraded to its already-on-disk `origin/{name}` remote-tracking ref when one exists (`preferRemoteTrackingRef`, no fetch), so a lagging local ref that has already merged `origin/{integration}` in (as `worktree-setup.md`'s post-creation catch-up does routinely) no longer reproduces the same inherited-history arm.
  - **Ownership.** `ctx.runDir` reaches the gate unfiltered by session id (`ctxLib.resolveRunDir(cwd, process.env)`), so the run it names may be a live sibling session's. On a provable owner-vs-caller mismatch the gate warns instead of denying, exactly as E1 does — otherwise the deny's own `record-worktree --run` remediation would tell the agent to corrupt that sibling's `run-state.json` (the `--run` rule at the top of this list). On the `record-worktree` branch specifically — where `runState.worktree` is provably unset, so `sessionId` (stamped together with `worktree`) is almost always unset too and the owner-vs-caller comparison can barely engage — a second signal augments it (`hasDistinctOwnedRun`, #1259): a caller whose own `ctx.ownedRun.dir` already names a *different*, already-recorded run is treated as foreign even with no `sessionId` on either side. The `record-pr` branch keeps `isForeignSessionCall` alone, unchanged.
  - **Path exemptions.** A file-tool target inside `.claude-tweaks/pipelines/` or at `.claude-tweaks/policy.yml` is exempt, resolved against the *target's* own repo root (run dirs are anchored to the main checkout, so `decisions.md` normally sits outside the worktree). Without this the PR-stamp deny's own escape hatch — writing that degrade line — would itself be deniable.
  - **Foreign repos.** For the Bash branch, each git target's own main-checkout root is compared against this worktree's; a command targeting only unrelated repositories (`git -C /elsewhere commit`) is not gated. Mirrors E1's `mainRoot`/`actualMainRoot` check, including its unprovable-case posture.
  - **Foreign targets (file-tool branch, #1678).** The Edit/Write/NotebookEdit branch mirrors the Foreign-repos rule above: a file-tool call's own write TARGET — not just the calling session's `cwd` — is resolved via `wtDetect.repoInfo`, and a target that is definitively outside any git repository (a session scratchpad) or inside an unrelated repository no-ops the gate. Same unprovable-case posture as every other file-tool exemption here: an `indeterminate` target (git ran but gave no usable answer) is never exempted by this rule and falls through to the ordinary stamp-missing deny. Three further fail-closed layers narrow when this actually exempts: the target path must be `path.isAbsolute` — a relative `file_path` resolves against the hook process's own cwd, not the calling session's, so it is unprovable here and always falls through; a target `repoInfo` proves has no repo root at all exempts unconditionally, independent of whether this worktree's own main-checkout root resolves; but the different-repo case requires BOTH sides' `mainCheckoutRoot` to resolve AND differ — an unresolvable root on either side means "unknown," not "different," and also falls through to the deny. The target's leaf is resolved before `repoInfo` is asked — a symlink at the leaf is followed (mirroring `realTarget()` above), an existing-but-unresolvable (dangling) leaf is unprovable and falls through to the deny, and a path with nothing at the leaf yet (an ordinary new-file Write) is passed through unresolved.
  - **The run's pin, not a fresh detection.** The PR branch resolves `integration-model` through `policy-schema.js`'s `resolvePolicyConfig({ runDir })` (policy.yml + `{run-dir}/config.yml`), falling back to forge detection only when the run pinned nothing — per `_shared/integration-model.md`'s "re-detecting mid-run" anti-pattern. Both stamps already present short-circuits before any git or `gh` spawn — and so does `runState.worktree` alone once `runState.prExempt` is set: the first time the PR branch proves no further PR-stamp denial is possible for this run (model resolved cleanly to non-pr-first, or pr-first with the degrade line already logged in decisions.md — both permanent for the life of the run), it persists `prExempt: true` to `run-state.json` so every later covered call — including a `local-merge` run's steady state, which never sets `runState.pr` — skips repoInfo, `hasMaterializeCommit`, and this resolution entirely. Persisted rather than cached in-memory because each hook invocation is a fresh process. Never persisted when the resolution itself threw (a transient failure, not a provable verdict, unlike the two cached cases which are immutable for the life of the run); persisted regardless of caller session identity — unlike the worktree/PR stamps themselves, `prExempt` names no owning session, so a provably-foreign call computing it is not the corruption hazard the deny's own remediation text warns about.

## Ownership

Composite identity, not raw session-id equality (`#1098`, hardened by `#1012`/`#1099`): `classifyOwnership(caller, runState)` in `context.js` compares two independent axes — `caller = { sessionId, cwd }` against exactly two fields of `runState`, its own `sessionId` and `worktree` — and returns exactly one of three verdicts: `'mine'`, `'foreign'`, or `'indeterminate'`. A session-id match on both sides is NOT sufficient evidence of ownership: *`CLAUDE_CODE_SESSION_ID` is shared across all subagents of a session (observed 2026-08-20 via the #965 probe, recorded in parent #1096 — scope: Task-tool subagents of an interactive session; re-verify before extending the claim to cloud Routines or headless runs, and re-verify if harness session handling changes); it identifies the session, never the agent; no ownership decision may treat its equality as sufficient.* Session ids that provably differ short-circuit straight to `'foreign'`; every other case routes through the worktree-binding axis: a caller resolving inside the run's recorded `worktree` is `'mine'` (binding outranks incomplete identity); a caller provably inside a *different* live worktree than a binding that provably exists on disk is `'foreign'`; a caller in the main checkout with no binding but matching ids is `'mine'`; and every case the predicate can't prove either way — an unresolvable or non-absolute `cwd`, a binding gone from disk, a caller outside any known checkout, equal ids from inside a worktree with no binding — degrades to `'indeterminate'`. Fail-open by design: unprovable evidence never classifies `'foreign'`, preserving `resolveRun`'s own documented asymmetry (an unowned run may still be ours; a provably-foreign run never is).

The five mutating run-state verbs (`close-run`, `record-worktree`, `record-pr`, `spec-status`, `teardown-run`) resolve an omitted `--run` through this predicate via `resolveRunArg`'s `unambiguousOnly` path (`resolveImplicitRunUnambiguous` in `hooks.js`, `#1012`) — replacing the pre-`#1012` "newest non-terminal run" guess with an unambiguous-only order: **(1)** `PIPELINE_RUN_DIR` env, resolved as-is and unfiltered (the write-time ownership guard below is what protects this arm — an inherited env var reaching a foreign run is a documented pollution vector, `#1038`); **(2)** a cwd-binding reverse lookup (`findRunByWorktreePath`) — a run whose recorded `worktree` IS the caller's own cwd is provably this caller's, even with N siblings live; **(3)** otherwise every non-terminal run dir is scanned and any candidate classifying `'foreign'` against this caller is excluded — exactly one survivor is acted on. Two or more survivors, or zero survivors among one-or-more total candidates, refuses outright and lists every candidate as a paste-ready `--run <dir>` line (foreign ones annotated `(recorded by another session/worktree)`) rather than guessing: `claude-tweaks: multiple candidate runs — pass --run explicitly:` for two-or-more survivors after filtering, or `claude-tweaks: the only candidate run(s) are recorded by another session/worktree — pass --run explicitly to act on one:` when every candidate was excluded as foreign. Genuinely zero non-terminal runs system-wide falls through to each verb's ordinary "no pipeline run dir found" message instead of an empty refusal listing.

**Explicit `--run` always overrides** this whole implicit-resolution ladder (subject only to the anchoring check earlier in this file) — it is the one documented way to act on a run this predicate would otherwise refuse or exclude. `record-pr` and `spec-status` additionally carry a narrower write-time guard: an *implicit* resolution (no `--run`) whose resolved run still classifies `'foreign'` — reachable only via the unfiltered env-var arm above, since arms (2)/(3) already exclude foreign candidates by construction — refuses the write (`claude-tweaks: run {id} was recorded by another session/worktree — refusing to record a PR/spec status against it without an explicit --run`); an explicit `--run` bypasses this guard too. `close-run` carries its own analogous foreign-owner and live-worktree refusals via `closeRunState`, documented at that function's own call sites rather than restated here.

Also consulted at PreToolUse (`#1099`): `checkTeardownGate` and the E1 wrong-checkout deny in `pre-tool-use.js` route their own same-session-sibling-worktree checks through `classifyOwnership` instead of raw session-id equality — a sibling agent of the same session bound to a different live worktree now classifies `'foreign'` (warn + allow, `wd-foreign-teardown`/`wd-foreign-session` events) rather than being treated as the run's own session (same-session deny), closing the enforcement-side half of the gap `[IL-152]` documents.
