# Skill authoring conventions

Loaded when authoring or editing skill files (`plugin/skills/**/*.md`). Dispatched implementer/reviewer/QA agents do not need this — it is not part of their per-dispatch context.

## SKILL.md structure

Every skill follows this structure:
1. YAML frontmatter: `name`, `description` (trigger condition)
2. Interaction style directive (identical across all skills)
3. H1 title with one-line description
4. Lifecycle position — a one-line `Lifecycle:` marker where one line suffices, or a diagram where the shape needs more (consumer sets, mechanism flows, cycles); the canonical full chain lives in `/claude-tweaks:help`
5. "When to Use" section
6. Input resolution (how `$ARGUMENTS` is parsed)
7. Numbered workflow steps
8. Anti-Patterns table (`| Pattern | Why It Fails |`)

**Adding a mode or argument to an existing argument-dispatched skill:** enumerate and update every mode-conditional block in the host SKILL.md — skip lines, section gates, and the terminal `## Next Actions` block — not only the blocks the change directly names; missing one produces a contradictory double-`AskUserQuestion` prompt at runtime. A brand-new flag (no arity change) still has syntactic-mirror surfaces of its own that a change scoped only to `## Input`'s table can silently miss — every row of the Argument-hint mirror surfaces table below restates the whole grammar inline and drifts independently of that table (#679: a dispatched edit added a flag's table row but left the mirrors naming only the old set, caught by controller re-read rather than the dispatch's own verification). Treat every row of that table as always in scope for a new-flag addition, not only an arity change (except that a flag whose `## Input` entry is marked `(producer-only)` or `(deprecated alias)` stays out of the hint and therefore out of its mirrors — the `argument-hint` bullet under Frontmatter conventions). When the change alters an argument's **arity** (a single ref becoming a `#N,#M` list), the sweep is repo-wide rather than host-file-scoped: grep the retiring cardinality vocabulary (`per invocation`, `single record`, `one item`, a bare `[#N]` hint) across `plugin/skills/`, `docs/`, and `README.md`, since a deliverable's own file list will not name every prose sentence that asserted the old cardinality (#695: six live sentences in files no deliverable named — five caught only at the whole-branch review, and `_shared/work-record.md`'s not until wrap-up). A retirement's negative-sweep acceptance criterion ("grep X returns nothing") must also state its scope relative to run artifacts: the implementing plan's own replacing-blocks quote the retired literal verbatim, so exclude that plan file explicitly and note that the unrestricted sweep passes only once wrap-up's plan cleanup deletes it (#726).

**A routing token that replaces a skill's phases owns every flag the skill accepts.** When a new token routes to a sub-file in place of some or all of the host skill's phases (`wrap-up`'s `merge` → `merge-mode.md`, in place of Phases 1-4), the replaced phases took their flag semantics with them. The routed file enumerates every flag in the host's `argument-hint` and states, for each, one of three outcomes: rejected in combination (report both tokens, run neither), re-implemented (the route provides the flag's guarantee itself), or ignored (the report says so). Nothing is silently inherited: #3784's `merge --dry-run` would have merged for real, because the dry-run guarantee lived in the phases merge mode replaced, and its `--skill-budget`/`--doc-budget` were silently ignored until review.

### Argument-hint mirror surfaces

The one enumeration of every place a skill's argument grammar is restated verbatim. The `argument-hint` frontmatter value is canonical; every other row must carry the same string byte-for-byte once that surface's own wrapping (a code span, the card's `\|` pipe escapes) is removed. `tests/argument-hint-mirrors.test.js` reads this table and walks each row for every skill, and it pins its own extractor registry to the rows in both directions — a row added here fails the suite until its extractor exists, and an extractor whose row is removed fails it too. Other files cite this section; none restates the list.

| Surface | File | Where | Presence |
|---|---|---|---|
| `frontmatter` | `plugin/skills/{skill}/SKILL.md` | The `argument-hint:` frontmatter value — the canonical form every other row is compared against | required |
| `input-parse-line` | `plugin/skills/{skill}/SKILL.md` | The code span on the `## Input` section's restatement line — a line that opens with `$ARGUMENTS` as a code span, then `is parsed as`, `is` or `=`, then the span | when-present |
| `usage-line` | `plugin/skills/{skill}/SKILL.md` | The grammar that follows `usage: /claude-tweaks:{skill}` on a usage line the skill prints when it refuses an invocation | when-present |
| `syntax-block` | `plugin/skills/{skill}/SKILL.md` | The grammar that follows `/claude-tweaks:{skill}` on a line of the `## Syntax` section, before that section's first sub-heading | when-present |
| `reference-card-takes` | `plugin/skills/help/reference-card.md` | The `Takes` cell of every `/claude-tweaks:{skill}` row in the three command tables | required |

`required` means every skill carries the surface. `when-present` means a skill may omit it, but a skill that writes it writes the whole hint — an abbreviation (`[flags]`, `--kind=<value>`) is drift, because the next flag added to the hint has no obvious place to land in it. A skill whose `## Input` opens straight into its argument table has no restatement line and nothing to mirror there; `tests/argument-hint-input.test.js` separately checks both directions between the hint and that section: every bracketed leaf of the hint is documented there, and every `--flag` its table documents is in the hint unless the row is marked (the `argument-hint` bullet under Frontmatter conventions).

To add a surface, add its row and then its extractor in that test's `EXTRACTORS` (file content and skill name in, every grammar string found out). A place that *describes* a flag in prose — `plugin/skills/help/context-flow.md`'s row for a skill, a `description` naming a mode — is not a mirror and does not belong in the table; it is found by grepping for one of the skill's existing flags, which is why `plugin/skills/build/plan-authoring-checks.md`'s Mirror-surface enumeration check asks for both. The table exists because the count was carried in memory and was short twice: #679 named the first two rows, #2759 found the reference card's `Takes` column only because a byte-pinning suite happened to cover it, and the two reviews of this table's own first draft found the usage line and then `flow`'s `## Syntax` block.

Skills do **not** carry a Relationship to Other Skills table. That convention was removed in v6.34.0 — every edge is recorded once in `docs/skill-graph.md` instead.

**Size:** the Read-limit rail is the only size limit that binds and blocks — every shipped skill `.md` and every composed bundle must fit one Read call (`RAIL_BYTES`/`RAIL_LINES` in `plugin/bin/lib/skill-audit/budgets.js`, enforced through `rail.js` by the `rail:` suite in `tests/bin-lib/skill-audit/context-cost.test.js`). Per-invocation cost is shown, never gated: `/review`'s skill load delta and `/harness-health`'s transcript-measured load. Coherence is the corpus-relative `sizeOutlier` bloat signal — a prompt to look at a file, not a limit. When a file grows, the remedy depends on which number is near the rail (Extracting to a sub-file under budget pressure, below).

No file carries a tighter per-file byte pin than the rail: #3311 removed the last ones (`flow/manifesto.md`, `flow/multi-spec.md` and the rest), and `tests/skill-size-single-source.test.js` fails if a new one appears anywhere but `plugin/bin/lib/skill-audit/budgets.js`. Check `wc -c` against `RAIL_BYTES` before adding to a file near the rail.

**Extracting to a sub-file under budget pressure.** The remedy depends on which number is near the rail. A composed bundle gets `when:` fencing or composition (Composition over fragmentation, below). A raw file gets bytes cut, or a genuinely lazy section — one some runs never read — moved into a cited sub-file; fencing cannot help a raw file, because the rail measures it with only the marker lines stripped. Never a "read X now" split that every run follows: it moves bytes without cutting what a run loads, and trimming inline prose until it loses clarity is no better. Worked lazy-unit examples: `journey-health/deep-tier.md` (read only under `--deep`, #1806) and `wrap-up/resume-halted-run.md` (read only on `resume`, #2006).

## Instruction-prose diet: operative text vs. provenance narrative

Operative text — a `## Step N` body, a gate table, a Next Actions block, an Anti-Patterns row — states the rule and cites its `[IL-nn]` tag (`docs/incident-log.md`) or the record number that motivated it. One sentence of rationale is allowed alongside the citation; a paragraph retelling what happened, who filed it, or which prior draft it replaced is not — that narrative belongs in `docs/incident-log.md` or `docs/decisions/`, cited by tag rather than restated. This does not apply to this file (`docs/skill-authoring.md`) or other authoring/reference docs: those are read by a human shaping a skill, not composed into a pipeline step's runtime context, so a fuller "why" is appropriate there (#1909).

Compliant: `Never {action} — {one-clause consequence} [IL-NN].`
Non-compliant: the same rule followed by a paragraph re-explaining the incident that produced it — cite the real tag and move the retelling to that incident-log entry instead.

## Conditional blocks and the composer

A `plugin/skills/_shared/*.md` contract or a skill sub-file may fence a passage that applies only under one resolved run condition, so a step reads one composed bundle instead of every branch of every file:

```markdown
<!-- when: integration-model=pr-first -->
… the pr-first branch …
<!-- /when -->
```

**Marker grammar.** `<!-- when: {key}={value} -->` opens a block and `<!-- /when -->` closes it, each on its own line; exactly one `key=value` per marker; a pair opens and closes in the same file; nesting depth at most 1 — an inner block is kept only when both its own condition and the enclosing block's hold. Six keys, in this canonical order: `integration-model` (`pr-first`|`local-merge`), `mode` (`auto`|`confirm`|`interactive`|`hybrid`), `attendance` (`headless`|`attended`), `transport` (`gh`|`mcp`), `worktree-policy` (`always`|`optional`), `work-backend` (`github-issues`|`local-files`). A malformed marker (unclosed, unknown key or value, nesting deeper than 1, a close with no open) is a compose error — the composer exits 2 naming the file and line and writes nothing; it never silently keeps or drops a branch. Marker-shaped lines inside a fenced code block (``` or ~~~) are literal text to the composer — never markers, never validated, never stripped — which is how a composed file documents this grammar without triggering it.

**`mode=confirm` never resolves at runtime.** The vocabulary accepts it, but no run directory can produce it: `resolve-conditions.js` reads `mode` only from the run's `config.yml`, and the sanctioned writer for that file (`bin/lib/set-config/write.js`'s `CONFIG_ONLY_VALUES`) admits only `auto`, `hybrid`, and `interactive` — a `confirm` run writes `auto` once its gate resolves. A `<!-- when: mode=confirm -->` fence is therefore stripped from every bundle a real run composes, and survives only in the `unresolved` both-branches case, so fence such a passage on `mode=auto` or leave it unconditional. Whether the value stays in the vocabulary at all is #1987's open call.

**`attendance` is the autonomy ceiling, not human presence.** `resolve-conditions.js` sets `attendance=headless` exactly when the resolved `autonomy` policy is `unattended`, `attended` at any other set value, and `unresolved` when `autonomy` is unset; nothing in it reads whether a human is in the session. A human-confirmed step in an `unattended` run (`wrap-up/merge-mode.md`) therefore composes as `headless`, so an `attendance=attended` fence cannot carry content that only such a step needs. Put that content in a file the human-confirmed path reads directly, as #3784 did with its attended Conflict procedure.

**Call-site form.** A step that reads several fenced sources composes them once per step:

```bash
node "${CLAUDE_PLUGIN_ROOT}/bin/compose-context.js" --run "$PIPELINE_RUN_DIR" --step {step} {files}
```

then reads `{run}/context/{step}.md` — the sources in argv order, untaken blocks removed, marker lines stripped, opening with a `<!-- resolved: … -->` line naming every key's value. Source paths are given install-safe — `"${CLAUDE_PLUGIN_ROOT}/skills/_shared/{file}.md"`, never a repo-relative `plugin/skills/…` path, which resolves only inside a claude-tweaks checkout and makes the call fail (and the fallback fire) in every installed consumer; `tests/skill-prose-plugin-root-invocations.test.js` pins this for compose-context source arguments the same way it pins `node plugin/bin/…`. The step checks the command's exit code before reading the bundle — a failed call writes nothing and leaves any prior bundle at that path untouched, so reading without checking hands the step stale prose from an earlier composition. A key the run cannot resolve (no `config.yml` on a standalone run, no policy file) keeps **both** branches and is listed as `unresolved` in that line and in the CLI's JSON output — a branch is never dropped on a guess. `transport` is the one key that is always resolved (it is a probe for `gh`, never a guess); `integration-model` resolves only from the run's `config.yml` pin or `policy.yml`, never from forge detection, and is `unresolved` otherwise. The bundle is regenerated on every call, never cached, since the Manifesto can re-answer a lever mid-run. The rail check on composed bundles (`rail.js`'s `composedRailViolations`, which finds call sites through `context-cost.js`'s `findComposeCallSites`) scans single-line calls only — a call wrapped across lines is not measured — so keep the call on one line.

**Every call site carries this fallback sentence verbatim:** *if the compose command is unavailable or exits non-zero, read the named source files directly.*

**A fenced block never holds the only copy of a heading, Step label, or anchor another file cites** — every citation must resolve in every composition, so headings and anchors stay outside the fences and only the condition-specific prose goes inside. When a whole section body is fenced, its heading therefore renders as a bare heading in the untaken composition — expected, not truncation: it marks where the branch would sit.

**Composition over fragmentation.** When a composed bundle grows, the standing response is to fence the condition-specific passages and let the composer trim them per run — not to split the file again (a raw file near the rail is the other case, above). A file's own size measures what a run *could* load; composed bytes per step measure what it *does*.

## Inline `_shared` contract vs a new component skill

When a new capability needs a canonical, citable procedure, choose between two shapes:

- **Inline `plugin/skills/_shared/*.md` contract** — every consumer already holds full context at the
  moment it needs the procedure (an agent mid-fix, mid-reflect). The procedure needs no
  independent invocation, no `Skill`-tool dispatch, and no lifecycle position of its own. Each
  consumer cites it by filename inline in a step it already runs.
- **New component skill** — the capability needs its own `Skill`-tool invocation, has callers
  that do *not* already hold the necessary context (so a fresh dispatch must gather it), or needs
  its own Component-Skill Contract / Next Actions / interaction pattern independent of any single
  caller.

Example: `plugin/skills/_shared/causal-depth.md` (a why-chain contract fired inline by an agent already
holding a debugging trace or a reflect pass's near-miss description) chose the inline form over a
new component skill, because both its consumers already hold the context the chain needs — a
fresh dispatch would have to re-derive it from scratch.

## Interaction patterns

- **Decisions** — call the `AskUserQuestion` tool with human-readable options (2-4 typical) so the user gets a native rendered choice instead of typing a digit back. Mark the recommended option's label with `(Recommended)`. An option's `description` states the consequence of choosing it, in one clause — rejected alternatives and the reasoning behind a recommendation belong in the message body above the call (or, for a multi-item batch, in the table's own row prose), never inside an option's `description` field. **Cost/effort/churn admissibility** — when the project's CLAUDE.md carries a zero-cost/zero-time (or equivalent) philosophy, a Recommended option's stated justification must not rest on cost, effort, or churn vocabulary (e.g. "churn", "cheapest", "not worth it", "too many files to touch", "smallest change"); restate the justification on correctness/quality grounds before marking the option Recommended, or demote it (don't mark it Recommended) if no correctness-grounded justification holds.
- **Multi-item decisions** — batch table with pre-filled recommendations, rendered as markdown (AskUserQuestion cannot display dense multi-row data). A verb-grouped list report (e.g. `/tidy`'s Applied/Approve/Yours/Clean sections) satisfies this convention equally — the binding requirement is pre-filled recommendations rendered in chat before one apply-all/override question, not the table form itself. **When a row is a genuine recommendation-vs-alternative decision** — a closed set of meaningfully different values where one was chosen over the others (e.g. a backend choice, a git strategy) — show the alternative(s) alongside the recommendation, not the recommendation alone: either a dedicated `Options` column listing every value with the recommended one bolded (`flow/manifesto.md`'s Policy levers table is the canonical example), or an inline `**{recommended}** (Recommended) — alt: {alternative}` cell when a separate column doesn't fit the table's shape. This does **not** apply to a row whose "recommendation" is a proposed action on an independent finding (a tidy action, a backlog label change) — those have no fixed alternative-value set to hide; leave those as a single recommended-action column. Then capture the terminal apply-all/override decision with one `AskUserQuestion` call (2-4 options: at minimum "Apply all recommended" and "Override specific items"). When "Override specific items" is chosen, the user's #-by-# corrections are ordinary free-text chat in the next message — not the tool's `Other` field, which is a single answer to the batch question, not a per-item list. For 10+ items, lead with a severity/count summary before the full table so the user sees the scope before the details. **Per-item loops are the exception:** when a skill's procedure walks a human-supplied list one item at a time and each item's decision *is* the judgment being collected (`/demo`'s per-ref verdict, `/specify`'s per-record design-intent question) rather than a recommendation to confirm, that skill's own body states that this batch-table convention does not apply to it. The Interaction style directive line is never edited to say so — it is byte-identical across every skill (pinned by `tests/bin-lib/skill-audit/house-structure.test.js`).
- **Pre-write reverify (confirm-then-apply)** — an `AskUserQuestion` gate has no timeout, so the interval between building a batch row's premise and writing that row is unbounded; where concurrent sessions touch the same subjects, the premise decays across that interval however carefully it was computed. A skill that confirms a table and then walks it writing must re-read the live state of each row's subject **immediately before that row's own write**, compare it against the premise captured when the table was built (the values already fetched, not re-derived), and drop the row — logging the skip, never silently — when the two disagree. **Fail closed:** a re-read that errors is treated as a mismatch, not as permission to proceed, since writing on an unread premise is the exact failure being prevented. The user's approval authorizes the *action*, never the *state the action was computed against*. A residual read-to-write window remains wherever the backing store offers no conditional write (GitHub's label and comment APIs offer none) — document it as an accepted residual; it is not a reason to skip the re-read. Rows whose write cannot be invalidated by a concurrent decision (a link repair, an append-only note) are out of scope — say which, rather than applying the rule uniformly and pretending the whole table shares one race. Implemented independently today at `plugin/skills/backlog/refine-mode.md`'s Step 5 (grant / flag-back / priority label writes, #764), `plugin/skills/tidy/actions-github-issues.md`'s "Re-verify before writing — never trust the scan's own snapshot" (the gated `[parent-gate]` and PR-arm actions `plugin/skills/tidy/step-6-auto.md` stages), `plugin/skills/_shared/console-on-pr.md`'s comment recompose (re-fetch immediately before writing, re-merge if the body moved underneath), and `plugin/skills/_shared/console-execution.md`'s check-then-act execution claim (read `console.json` immediately before writing `executingAt`). The post-mortem is `docs/donts.md`'s `[IL-135]`.
- **Chunked multiSelect batch** — for a list of N candidate items each needing an independent file/skip decision (not a single apply-all-or-override choice over a table), render each item as one option (`label` = short title, `description` = one-line summary) inside a `multiSelect: true` `AskUserQuestion` call, and chunk the list into calls of at most 4 items — `AskUserQuestion`'s own per-question option cap. Every option renders unchecked by default; checking it is the explicit per-item approval act (no pre-selection exists on the tool's current schema). See `plugin/skills/_shared/upstream-feedback-batch.md` for the full contract (rendering, chunking, question text, decline/edit handling).
- **One decision per message** — never make more than one `AskUserQuestion` call in a single response. If a skill produces multiple decision tables, present them sequentially (one call per message, wait for resolution before showing the next).
- **Skill handoffs (Next Actions)** — End each skill with a `## Next Actions` block (standalone, top-level; a Next Actions block nested inside a larger rendered report template — Pipeline Summary, failure cards, review summary — may stay `### Next Actions` as that report's own subsection heading), rendered as **plain markdown**: one paste-ready command per line, fully qualified (`/claude-tweaks:{skill}`) with all parameters pre-filled, an em-dash annotation after the command, the recommended option first with its command bolded and its annotation suffixed `(recommended)`. An option carrying a runnable, state-changing command (a release bump, a push, a delete, a merge) is never marked `(recommended)` on an unverified premise — its annotation names the check that verified it, and the option is omitted entirely when that check didn't run (record #680: a paste-ready release command was marked recommended for work a prior release had already carried). Options are dynamically generated from available context (journeys, UI changes, worktree mode, QA stories, browser availability) — never a navigation menu of generic commands without parameters. A single surviving option still renders as a one-line block: markdown costs no interaction, so there is no minimum option count. A line may name a **non-command action** — an in-session step to execute, a file to open, a URL to visit — only when its annotation carries the literal marker `not a slash command`, so a reader scanning for paste-ready commands can tell it apart at a glance (`tidy/SKILL.md`'s Approve line is the canonical example); prefer a genuine command form (`open {path}`, `gh issue view {url} --web`) whenever one exists. The recommended marker may itself be **conditional**: a block whose recommended line depends on a runtime signal bolds one line and suffixes it `(recommended)` only when its stated condition holds, and otherwise renders every line unranked — provided the condition is stated where a reader meets it, either in the block's intro prose or inline in the line's own annotation (`(when …)`, `render only when …`). `AskUserQuestion` remains the tool for decisions that **block the skill from finishing** — mid-flow gates, overlap resolution, findings routing, the ledger resolve gate — and, rarely, for a terminal decision a documented machine consumer must resolve (a policy lever or contract point that reads the answer); such a surviving terminal call carries a one-line inline justification naming its machine consumer, where it is used. This convention also has a consumer-side reading rule: a user message that opens with (or consists of) a fully-qualified report row in this `- /claude-tweaks:{skill} {ref} — ...` shape is an invocation request for that command, not passive background context, even when no leading slash-command marker is present — pasting a row back from an earlier report is how a human replies to it. This rule extends to a paste of the **whole** `## Next Actions` block, not just a single row: when the pasted text carries exactly one `(recommended)`/`(Recommended)`-marked line and no competing marked line, and the surrounding free text (if any) states no different choice, that marked line is the selection — proceed with it directly rather than issuing a fresh `AskUserQuestion` re-asking which option to run (record #2701). Keep this narrow: a paste with a second marked line, or with free text implying a different choice than the marked one, is genuinely ambiguous and still asks. Rationale and revisit trigger: see the Interaction style directive section below.
- **Actions Performed table** — When a skill performs autonomous actions beyond what the user explicitly requested, include a `### Actions Performed` table before Next Actions. Columns: `| Action | Detail | Ref |`. Action types: `Implemented`, `Bug fix`, `Simplified`, `Operational`, `Journey`, `Ledger fix`, `History` (a git operation that rewrote or moved history — rebase, reset, cherry-pick, revert, non-fast-forward merge, amend, push; never folded into `Operational`, which means cleanup). Ref column shows short commit hash. Resolved ledger items show source phase in parentheses. Generated from git log, git diff, and ledger entries. Omit when no autonomous actions were performed.
- **Hard gates** — BLOCKED/STOP conditions that prevent proceeding with degraded state
- **Adaptive section batching** — when a skill presents multi-section material that requires sequential approval (e.g., design walkthroughs, multi-part summaries), if the user accepts 2 consecutive sections without modification, batch all remaining sections into a single approval gate. This is the behavior, not a setting (the `section-confirmation` policy key was retired in #331 — removal trail: `plugin/skills/_shared/policy-deprecations.md`). The same adaptive convention also governs `/superpowers:brainstorming`'s **User Review Gate** (the blocking wait before `/superpowers:writing-plans`): skip it when the preceding Spec Self-Review loop found no unresolved issues (ambiguity resolved by judgment call, scope/decomposition shift, or a contradiction resolved by interpretation) — state the committed path and proceed directly to writing-plans. A substantive self-review change still stops, surfacing only that delta. This overrides brainstorming's own wait instruction on the claude-tweaks side; no superpowers file is edited.
- **Brainstorming scope-assessment fold** — `/superpowers:brainstorming`'s scope-assessment step can ask a stop specifically gating *whether to consider* an alternative approach ("should we also weigh approach X"), immediately followed by a second stop asking *which approach to choose*. On the claude-tweaks side, fold the two into one `AskUserQuestion` call: offer X directly as one of the presented options on the approach-choice question, and skip the prior gating question entirely — the gate is fully subsumed by the choice (record #2701). This overrides brainstorming's own two-stop scope-assessment flow on the claude-tweaks side; no superpowers file is edited, mirroring the User Review Gate override above.
- **Front-door confirm + opt-in Customize** — when a flow gathers multiple sequential inputs (schedule, environment, etc.) before one consequential action, front-load a defaults-based preview+confirm as the fast path and gate the sequential input-gathering behind an explicit `Customize` choice reached only from that confirm, rather than always running the gathering up front. Collapses N round-trips to 1 for the common case.
- **Component-skill contract** — Skills that are routinely invoked by other skills (e.g., `/simplify`, `/reflect`, `/deepen`, `/journeys`, `/visual-review`, `/design-wrapper`, `/capture`, `/challenge`, `/stories`) MUST detect whether they were invoked by a parent skill or directly by a user. When invoked by a parent, omit the `## Next Actions` block — the parent owns the handoff and Next Actions belong to the parent's flow. When invoked directly, render Next Actions as usual. Document this contract explicitly with a labeled `## Component-Skill Contract` paragraph placed **immediately before `## Anti-Patterns`** (after any post-workflow documentation sections such as Output contract or Reference sub-files). The paragraph must name the parent skills and use a **programmatic detection signal** — preferred is `$PIPELINE_RUN_DIR` (set by `/flow` and all pipeline orchestrators), with an explicit `--source <parent-skill>` flag as fallback for direct invocation where ambiguity exists. Vague signals like "pipeline context arguments" or "whether the caller consumes the return value" are insufficient — the model cannot reliably detect those at invocation time.

  **Canonical CSC template** (copy-paste, customize the parent list):

  ```markdown
  ## Component-Skill Contract

  When `$PIPELINE_RUN_DIR` is set, `/claude-tweaks:{this-skill}` is running inside a pipeline (invoked by `/claude-tweaks:{parent-1}`, `/claude-tweaks:{parent-2}`, or another pipeline orchestrator). In that case omit the `## Next Actions` block — the parent owns the handoff.

  Direct invocation may pass `--source <parent-skill>` as an explicit fallback when ambiguity exists (rare; `$PIPELINE_RUN_DIR` is the primary signal).
  ```

- **Next Actions placement** — Render as `## Next Actions` (top-level section, NOT `###`) placed **at the end of the workflow steps and before Component-Skill Contract / Anti-Patterns**. Conceptually: Next Actions is the user-facing handoff after the last workflow Step; CSC and Anti-Patterns are meta-documentation for skill authors and should come last. The retired Relationship table was meta-documentation of the same kind — which is why it could leave the shipped payload entirely rather than merely move down the file. A skill with no Component-Skill Contract still places Next Actions before Anti-Patterns.

## Frontmatter conventions

- **`name`** — required. The **bare** skill name (`wrap-up`), never `claude-tweaks:wrap-up` — the harness prepends the plugin namespace itself, so a prefixed value renders as `/claude-tweaks:claude-tweaks:wrap-up` in the command list. This does not change prose cross-references, which still use the fully-qualified `/claude-tweaks:{skill}` form; the two were conflated in `e9d5cb4a` and separated again in 6.50.1.
- **`description`** — required. Trigger sentence ("Use when …", or an equivalent "Use to …" / "Use for …" phrasing) followed by optional keywords. Keep it short — every description loads into every session — and under the CLI's 1,536-character per-description listing max (`DESCRIPTION_MAX_CHARS`, the `rail: every skill description fits the CLI listing max` test) — and preserve every Keywords token unless demonstrably redundant with one already kept: it's the skill-selection surface, and a lost keyword can stop a skill from firing (#394). Don't restate a skill-graph edge ("works as a step within /X", "used by /Y") — edges live once in `docs/skill-graph.md` (CLAUDE.md's Cross-references) — unless the edge is the skill's trigger condition or its only disambiguation from a same-named skill.
- **`allowed-tools`** — **omit by default**. Skills inherit the global tool set when this field is absent. Declare `allowed-tools:` only to **restrict** — e.g., a read-only auditing skill that should never modify files would declare `allowed-tools: Read, Grep, Glob, Bash`. Declaring a narrow set (like `allowed-tools: Bash`) when the skill actually uses Read/Edit/Glob/Task is a bug — it either lies about the contract or silently breaks the skill if the harness enforces it. When in doubt, omit the field.
- **`argument-hint`** — required whenever a skill's `## Input` section documents any accepted argument grammar; omit only for a skill that genuinely takes no arguments at all — none currently do (every skill in this plugin declares a non-empty `argument-hint`), but the convention still applies if one is ever added. Shows as greyed-out placeholder text in the terminal when the user types `/claude-tweaks:{skill}` — purely cosmetic, has no effect on how `$ARGUMENTS`/`$1`/`$2` are parsed at runtime. Always quote the value (`"..."`, or `'...'` when the hint itself contains a literal `"`) — an unquoted value starting with `[` is invalid YAML (parsed as a flow sequence, not a string). Derive the hint directly from the skill's own `## Input` section — same bracket/pipe convention as `.claude/commands/*.md`: `[optional]`, `<required>`, `a|b` for alternatives. The hint is the grammar a person types, so it carries every flag `## Input` documents, unless that flag's entry is marked. There are two marks. A flag only an agent or another skill passes, never a person typing the command (a producer's Capture route, a parent skill naming itself), is marked `(producer-only)`. A retired spelling is marked `(deprecated alias)`. The mark goes in the first cell of the flag's `## Input` table row, or right after the leading code span of its `## Input` bullet, and a marked flag stays out of the hint and its mirrors. `tests/argument-hint-input.test.js` checks both directions, reading every `--flag` from table rows' first cells and bullets' leading code spans: an unmarked flag must be in the hint, a marked one must not. Keep it in sync when `## Input` changes — note that `tests/argument-hint-input.test.js` opens a bracket group at *every* `[`, including one nested inside a leading `<...>` alternation, so a hint like `<#N[,#M...]|record-id[,id...]|...>` makes `,#M...` and `,id...` leaves that must appear literally in `## Input` (`#`-led leaves are exempt as placeholders; `,id...` is not — write `record-id[,id...]` somewhere in the section's prose, as `/specify` does); and when the change is an *arity* change, the hint's mirror surfaces (the Argument-hint mirror surfaces table under `## SKILL.md structure`), the rest of `## Input`, and the `description` are only the start of the edit list: run the repo-wide cardinality sweep in `## SKILL.md structure`'s "Adding a mode or argument" paragraph above, and derive the file list from its grep hits rather than from the spec's named deliverables.

## Plugin-root references (`CLAUDE_PLUGIN_ROOT`)

Skill prose that shells out to a plugin file writes `node "${CLAUDE_PLUGIN_ROOT}/bin/{cli}.js" …` — and, inside a `node -e` program, `require('${CLAUDE_PLUGIN_ROOT}/bin/…')` with the placeholder embedded directly in the string literal. `${CLAUDE_PLUGIN_ROOT}` is a **model-resolved placeholder, not a shell contract**: the harness does not set `CLAUDE_PLUGIN_ROOT` in the Bash tool environment (verified empirically 2026-08-07 through 2026-08-11, locally and in cloud sandboxes — #170), so a verbatim run fails with `Cannot find module '/bin/…'`. The executing agent MUST substitute the absolute plugin root before running the command, derived from the invoked skill's own context — the `Base directory for this skill:` line the Skill tool prints, minus the trailing `skills/{name}` segment. This file does not ship; the runtime agent's copy of the rule (resolve once, substitute the literal into every later command and subagent prompt, plus the no-Skill-invocation fallback) lives in `plugin/skills/_shared/worktree-setup.md`'s Post-creation catch-up (#2702) — keep the two in step.

Rules that follow:

- Keep writing the `${CLAUDE_PLUGIN_ROOT}` spelling in skill prose, **including inside a `node -e` program's `require(...)` call** — `require('${CLAUDE_PLUGIN_ROOT}/bin/…')`, never `require(process.env.CLAUDE_PLUGIN_ROOT + '/bin/…')`. The `process.env.CLAUDE_PLUGIN_ROOT` spelling reads as ordinary, plausible-looking JS with no visual cue that it needs substitution, so an executing agent following the snippet literally spawns a real Node process whose environment genuinely has no `CLAUDE_PLUGIN_ROOT` set (the harness's substitution only rewrites the `${CLAUDE_PLUGIN_ROOT}` token in the raw skill-prose text before the agent reads it — it never exports the variable into a Bash-tool-launched subprocess's real environment) and fails with `Cannot find module 'undefined/bin/…'` (#802). `${CLAUDE_PLUGIN_ROOT}` inside a JS string literal is the single canonical spelling, everywhere a plugin file path appears in skill prose. Do not hardcode an absolute path (plugin cache locations differ per machine and per account config dir), and do not add a shell lookup ladder to resolve it at runtime — a glob over cache directories is fragile across those same layouts, and worktree-isolated sessions limit what Bash commands can run (see `plugin/skills/_shared/scratch-worktree.md`'s "## 7. Shell constraint"), so the ladder is unrunnable exactly where builds happen.
- `plugin/hooks/hooks.json` is the exception, not the model for skill prose: hook processes are spawned by the harness with `CLAUDE_PLUGIN_ROOT` populated in their environment, so hook command strings — and only hook command strings — may read the real `process.env.CLAUDE_PLUGIN_ROOT` at runtime.
- The substituted root points at the **installed** build, which can lag a claude-tweaks dev checkout — when the running build matters, resolve it from `${CLAUDE_PLUGIN_ROOT}/.claude-plugin/plugin.json` (CLAUDE.md `[IL-89]`, `[IL-119]`).
- A `Cannot find module '/bin/…'` / `'undefined/bin/…'` failure means the placeholder reached the shell (or a spawned Node process) unsubstituted — re-issue with the resolved absolute path; do not diagnose the CLI itself.

## Executable snippets in skill prose

A fenced `bash` block a skill tells an agent to run verbatim is code, and it drifts like code: a later prose edit changes the documented procedure while nothing re-checks that the changed procedure still works. Every such block in `plugin/skills/**` today is bound to a `node --test` file that both pins the snippet and executes it against a fixture — see the two forms below. Bind each new one the same way.

- **Extract and run** — the test pulls the block out of the doc with a heading-anchored regex and runs exactly that string (`tests/pipeline-run-dir-adoption-anchoring.test.js`, which does this for `plugin/skills/_shared/pipeline-run-dir.md` and for `plugin/skills/wrap-up/SKILL.md`'s own copy of the same resolution). The doc is the only source of the executed text, so the two cannot drift, and the test fails loudly — *"extraction pattern is out of sync with the doc"* — when the heading or fence moves. Prefer this form.
- **Byte-pin and run** — the test holds the snippet as a literal constant, asserts the doc's fence is byte-identical to it, then runs the constant (`tests/spec-template-generator-grep.test.js`). Use it when the probe must wrap the snippet in fixture-specific surroundings, and accept that a deliberate doc edit has to be mirrored in the constant.

Either way the string must actually be **executed**, not only matched. Two whole-branch reviews caught real defects in one such snippet — a silent `mv` collision and a silent `mv` failure — only because a live probe ran it; a snippet asserted by shape alone is untested prose.

**Never let one command read a path it also redirects onto.** `>` truncates its target when the shell sets the command up, *before* the reading process opens it — so `node -e "… require('\$X') …" > "\$X"` reads an empty file rather than what the previous step wrote there. Write to a distinct path and `mv` it over the original after the process has exited. This shipped in `plugin/skills/backlog/overview-mode.md`'s Step 1 fold-in script until #1388, and it is hard to spot on review because neither failure mode names the redirect: a reader that tolerates empty input silently produces a wrong result, and one that does not throws from inside the `node -e` program. `tests/backlog-overview-foldin-no-truncation.test.js` is the worked extract-and-run binding, with the pre-fix bytes frozen as its go-red control.

**Never write a bare backtick inside a double-quoted `node -e "..."` block's JS comment.** Bash performs command substitution on backtick pairs while it parses the enclosing double-quoted string — *before* `node` ever sees the text — so a markdown-style `` `next` `` inside a JS comment executes `next` as a shell command and prints `next: command not found` to stderr on every invocation (harmless when the token names nothing real, a latent hazard if it ever does). `node --check` cannot catch this: the JS is syntactically valid either way, since bash has already stripped the backticks by the time node parses it. This shipped in `plugin/skills/dispatch/queue-pull-script.md` and, independently, in `plugin/skills/_shared/github-pr-scan.md`, until #1964. Drop the backticks in JS comments (plain text or single-quote the token instead), or use the single-quoted `node -e '...'` form, where bash performs no substitution inside `'...'` at all. `tests/node-e-snippet-syntax.test.js` is the worked binding — a live-corpus sweep that fails on a bare backtick inside any double-quoted `node -e` body under `plugin/skills/**/*.md`.

**Double-quote every temp-path placeholder on a shell command line.** A session-tmp path (`_shared/session-tmp-root.md`) sits under `os.tmpdir()`, which can contain a space — a Windows `C:\Users\First Last\…` profile, or a user-set `TMPDIR` — so an unquoted `cp "$SNAPSHOT" {tmp-records-file}` or `> {tmp-faceted-file}` word-splits the substituted path into two arguments. Write `"{tmp-records-file}"` in the fence itself, and substitute a bare path or a bare `$VAR` into it, never a pre-quoted value (`= "$VAR"` yields `""$VAR""`, an unquoted expansion). A placeholder already inside a double-quoted `node -e "…"` string needs nothing more; shell-level single quotes do not count, since `'$VAR'` never expands. This shipped unquoted in `plugin/skills/_shared/record-queue-fetch.md` and a dozen sibling files until #3544. `tests/session-tmp-placeholder-quoting-conformance.test.js` is the worked binding — a shell-quote-state sweep over every `bash` fence (blockquoted ones included) and single-line inline command span under `plugin/skills/**/*.md`, failing on a named temp-path placeholder in unquoted context; add a new session-tmp placeholder to its `NAMED_TARGETS` when you introduce one under a name outside the `{tmp-*}` family.

**Never assign a variable in one fenced block and read it from another.** Two fenced `bash` blocks separated by prose — numbered steps, or a heading boundary — read as two independent Bash tool invocations to an executing agent, and each invocation gets a fresh shell: a variable set in the first block (`LOCKFILE=$(ls package-lock.json … | head -1)`) arrives unset in the second, so a comparison built on it (`[ "$LOCKFILE" -nt node_modules ]`) silently evaluates against an empty string instead of failing loudly. `plugin/skills/_shared/worktree-setup.md`'s own divergence-check section documents this exact rule inline ("Assigned and used in the same call — a fresh shell per Bash invocation means a value resolved elsewhere would arrive empty here"), and the same construct still reappeared in that file's own Dependency-freshness-check section (#2348, its Step 1/Step 3 split) a few hundred lines below the documented precedent — caught only by an independently-dispatched review lens agent's live execution, not by any mechanized check; no `tests/**` sweep pins this pattern yet. Keep a value's assignment and every read of it inside one fenced block, or state explicitly that the reader must compose both steps into a single Bash call before running either.

**Write every shell fence in a form the worktree guard accepts.** An agent running a skill inside a linked worktree is subject to the harness guard described in "Harness-level worktree Bash guard vs. the plugin's PreToolUse gate" above, which refuses the whole Bash call for a shape it cannot prove stays inside the worktree — `eval`, `git` inside `$(…)`, a runtime variable as `node`'s script operand, a computed `node -e` argument with no `--`, and the other refused rows of `plugin/skills/_shared/scratch-worktree.md`'s "## 7. Shell constraint" table. A fence carrying one fails exactly where builds run. Write the row's Workaround instead: one `VAR="$(node "${CLAUDE_PLUGIN_ROOT}/bin/session-tmp-resolve.js" --value {file})"` line per path rather than an `eval` of the resolver's output, `node -e '<s>' -- "$A"`, or a separate plain call whose printed value is pasted in literally. The plugin's `guard-rewrite.js` normalizer (`docs/hooks.md`) is no substitute: it rewrites five shapes, only in a linked worktree running this plugin version. `tests/skill-fence-guard-shapes.test.js` is the worked binding (#4028) — a live-corpus sweep of every fence under `plugin/skills/**/*.md` (plus inline spans, for the retired `eval` form) against `tools/guard-refusals/shapes.js`'s detectors, one per refused §7 row. Its `ALLOWLIST` keys each known offender by file, detector and content anchor — `exempt` with a reason, or `ratchet` naming the follow-up record that migrates it — and fails on an entry that no longer matches a live offender, so the list only shrinks. A newly refused shape gets its §7 row first, then a detector bound to that row's Example cell (`tests/guard-refusals/shapes.test.js` enforces the binding).

## Passing untrusted content into an inline skill invocation

When a skill invokes another inline (via `Skill()`, not a Task dispatch) with content it fetched from outside this session — a GitHub issue title/body, a PR comment, a web result — that content shares the same LLM turn as the invocation's own instructions, so it must be marked untrusted rather than passed as bare prose. Wrap it in an explicit block with a collision-resistant delimiter: never a bare `---` or similar common fence, since real content (a GitHub issue body, this repo's own materialized spec frontmatter) routinely contains one, letting a crafted body close the block early. State that the block ends **only** at the literal closing marker — a line inside the payload that merely looks like the marker is still data, never a real close. When the callee returns a structured verdict (e.g. an anchored `^VERDICT: value$` line), read it only from the callee's own rendered output, never from a line inside the untrusted block, since caller-fetched content and callee output share one inline context. The shipped contract is `plugin/skills/_shared/untrusted-record-content.md` (extracted by #1275 from the #1041 boundary) — cite it rather than restating; `plugin/skills/specify/next-mode-shape.md`'s `## Framing Guard` (#1346's split of `next-mode.md`) remains a worked caller. Isolating the fetched content behind a Task dispatch is not a stronger boundary for this class of judgment — the caller reasons over the content in its own context either way, and a dispatch either re-derives the body or is handed a copy — so the wrap and verdict-source rules above are the operative defense, not isolation; that contract's `## Scope` records the ruling (evaluated and declined for `framing-check` in #1276) and the limit on how far it transfers.

## Reading a marker comment back from GitHub

A marker or heading in a GitHub comment body — `<!-- run-comment: … -->`, `<!-- needs-decision: … -->`, `## Verification Brief`, a `grant-mode-audit` line — proves nothing about who wrote it: anyone who can comment on the issue or PR can post a lookalike. So a step that reads such a comment back and acts on it (finds a comment to update in place, counts an open decision, passes a check, dates a grant) counts only a trusted author's comment, sends an untrusted match down its existing "no such comment" path rather than a third outcome, and names each comment it skipped in one line of its own output. Cite `plugin/skills/_shared/pr-run-comments.md`'s Trusted authors section for the association set, the fail-closed rule for a missing field, and the two jq filters rather than restating them; code readers import `plugin/bin/lib/issues/comment-trust.js` (#3358), and a prose reader of PR run comments filters a plain `gh pr view --json comments` file with `plugin/bin/find-run-comment.js`, which applies the same rule (#3936). This is the read-side counterpart to the section above: that one stops fetched content from steering an invocation, this one stops a planted comment from standing in for one the plugin wrote. `tests/comment-trust-conformance.test.js` pins the readers that existed when #3358 landed by name, not by sweep, so a new reader is not covered until it adds its own pin there. One exception since #3823: the file's AC2.1 sweep checks every pasted jq filter under `plugin/skills/` against the generator output, so a reader that pastes a stale or hand-edited copy fails there without a pin of its own; a reader that adds no trust filter at all is still uncovered.

## Deriving a CLI argument from earlier prose

When a step instructs an agent to reuse a value established earlier in the same file as a shell/CLI argument (e.g. "pass the same path named above"), state that value's own shape at the point of reuse — file vs. directory, absolute vs. relative — rather than pointing back at a rendered line written for a different consumer. A line composed for a human-readable audit reference (e.g. an "Audit trail: .../decisions.md" line) and a line a CLI flag like `--run <dir>` expects are not interchangeable just because they were built from the same path; a later step that assumes they are can pass a file path where a directory is required, or vice versa, and fail silently if the receiving command tolerates a bad argument by no-op'ing rather than erroring. Verify the shape the new consumer needs before writing "the same path as above."

## Reusing another step's fail-open read

A read that fails open is safe only relative to where its fall-through lands. When a step borrows another step's read — the same `run-state.json` marker, the same probe — state the fall-through direction in the new context and check that an unreadable input still lands somewhere safe there. #3377's plan-review step (`build/plan-review.md`) borrowed `flow/SKILL.md` Step 1 rung 2's "is a human present" read: in `/flow` an unreadable marker falls through to `auto`, which is safe, but in the plan review the same fall-through reached an `AskUserQuestion` that a dispatched Task subagent cannot call. Four of twelve review lens agents flagged it, and review fixed it to fail closed on tool availability.

## Self-checks an agent can actually evaluate

A self-check written into skill prose ("confirm exactly one `X` invocation happened for this item before proceeding") is only worth its bytes if the agent can evaluate it from what its own transcript shows. Inside a loop whose per-iteration calls are **unattributed** — identical arguments every pass, nothing in the call tying it to the item being processed — a per-item attribution claim is unverifiable, so it passes vacuously: the agent that collapsed N iterations into one call reads the check and sees nothing contradicting it. Anchor the count to a boundary the transcript does show instead — the calls made **since the previous iteration's own write/create call** (or since the loop started, for the first iteration) — and require exactly one there. `skills/specify/record-creation-subissues.md`'s (#1346's split of `record-creation.md`) per-sub-issue loop is the worked example: a sub-issue has no number until its create call, so its `ceremony-check`/`framing-check` invocations carry no `#{n}` and the since-the-last-create window is the only thing separating one iteration's calls from the next's (#708). Where the calls *are* attributed — `shaping-mode-stamping.md` passes `#{n}` to both — the per-item form is verifiable as written and stays.

## Harness-level worktree Bash guard vs. the plugin's PreToolUse gate

A session working inside a worktree created by `EnterWorktree` (or entered into one) is subject to a Claude Code CLI harness-level guard on the Bash tool — separate from, and unrelated to, this plugin's own `worktree-always` PreToolUse gate (`plugin/bin/lib/hooks/pre-tool-use.js`). The two are easy to conflate when triaging feedback (`#174` was originally filed against the wrong one). When the harness cannot cheaply verify that a command's effects stay inside the worktree, it refuses the whole call outright: `this command is too complex to verify that it stays inside the worktree; break it into plain, separate commands.` That literal is only one of the wordings the harness emits — `plugin/skills/_shared/scratch-worktree.md`'s "## 7. Shell constraint" current-state table records others, including `runs a string through complete, which can't be verified to stay inside the worktree` (#1651) and `names git in a form too complex to verify …` (#1876) — so identify a harness refusal by the absence of the plugin's own deny prefix below, never by exact-matching this one string. This is harness code the plugin has no access to, and no hook changes what it accepts. A PreToolUse `updatedInput` is applied before it and the guard re-checks the rewritten command (measured, `docs/reference/pretooluse-updatedinput-worktree-guard.md`), so the plugin's `guard-rewrite.js` normalizer can only hand it a different, accepted spelling of five known shapes in a linked worktree (`docs/hooks.md`); a refusal of one of those shapes means the normalizer declined or was not loaded. The plugin's own gate produces entirely different deny text (`claude-tweaks: this project requires an isolated worktree for...`, `claude-tweaks working-directory discipline: ...`), which is how the two are told apart in practice. `/claude-tweaks:feedback`'s Step 1 applies this test before it names a plugin hook as a refusal's affected component (#3338). It greps the quoted reason clause under the plugin's `bin/`, and with no match it routes the report as a `_shared/scratch-worktree.md` §7 table-row candidate.

For the empirically observed boundary of what Bash commands pass and fail in a worktree session, see `plugin/skills/_shared/scratch-worktree.md`'s "## 7. Shell constraint" — that is the canonical, detailed statement that skill implementers will actually encounter in their dispatch context.

A refusal without the plugin's deny prefix is not automatically this guard, either. A Claude Code permission rule denies with different wording — `Permission to use Bash with command … has been denied` — when a configured `deny` rule matches the command or a path it names. Check the session's permission rules before filing it against the guard or the plugin. That section's `.log`-read row (#2776) records one such report, produced by a user-scope `Read(**/*.log)` rule.

Since #2783 the plugin does see these refusals after the fact: the `post-tool-use-failure` hook (`PostToolUseFailure`, Bash only) logs each refusal whose text carries the harness's `This session is isolated in the worktree … Refusing to run it` frame to the run dir's `events.jsonl` as `wd-guard-refusal` with `reason: harness-worktree-isolation`, and `/claude-tweaks:reflect`'s Friction Lens reads them. That is observation only, never enforcement — see `docs/hooks.md`'s "Observed here, not enforced" paragraph.

## Harness-level skill re-invocation vs. batched Skill calls (#2728)

A second same-session `Skill` tool invocation of a skill the harness has already flagged as
previously loaded re-injects only a short "already loaded" acknowledgment, not the skill's full
body — **but only when that invocation is its own message.** Batching several `Skill` tool calls
into one assistant message each re-injects its target's full text, even for a skill invoked
earlier in the same conversation; one `Skill` call per message is what gets the short
already-loaded form. This is harness behavior — which invocation form a given message
produces is not something a `SKILL.md`, `_shared/*.md`, or any plugin hook controls or can change.
The actionable, plugin-side consequence is a calling-convention rule for anything that
programmatically re-invokes the same skill more than once in a session (a dispatch prompt, a loop
body, an orchestrating skill step): issue each repeat `Skill` invocation as its own message/turn,
never batched alongside other tool calls in one message, if avoiding the full re-injection cost
matters for that call site.

## Interaction style directive

Every skill follows this identical directive, but it is no longer restated inline in any `SKILL.md` (#1909): the SessionStart hook injects it into every session's context once, from a single source (`plugin/bin/lib/hooks/interaction-style.js`, wired in `session-start.js`). A new skill needs no frontmatter block for this — the directive already applies to it. Do not add a `> **Interaction style:**` line to a `SKILL.md`; `tests/skill-conventions.test.js` and `tests/bin-lib/skill-audit/house-structure.test.js` fail a skill that does.

```
> **Interaction style:** Single decisions → one `AskUserQuestion` call, one option marked Recommended. Multi-item → batch table with recommendations pre-filled, then one `AskUserQuestion` for apply-all/override. Never more than one call per decision; resolve each before the next. Terminal `## Next Actions` → plain markdown: paste-ready fully-qualified commands, recommended first and bold, one per line — `AskUserQuestion` there only for a documented machine-consumed decision, named inline.
```

The terminal clause changed from mandating an `AskUserQuestion` menu to plain markdown in 2026-08 (#646). Evidence basis: the 2026-08-16 session evaluation's Avoidable-interactions findings — both terminal menus that fired (`/backlog overview`, `/specify`) were rejected outright, costing two interruptions for zero decisions — plus the project's standing report-line convention (actionable report lines carry paste-ready commands; interactive launchers are reserved for human-owed decisions). Two structural points closed the loop: pipeline-invoked skills already suppress the terminal menu via their Component-Skill Contract, so the clause only ever fired on standalone close-outs; and a genuinely headless caller cannot answer an `AskUserQuestion` at all — headless resolution happens via policy levers and `consoleAutoResolve`, never a terminal menu. The evidence base is one evaluated session plus those standing conventions — stated honestly, not presented as settled by volume. Revisit trigger: a later session evaluation showing the markdown close-outs going unused, or users asking for the menus back.

## Parallel execution directives

Skills use three standardized blockquote forms to signal when operations should run concurrently:

| Form | Trigger | Use for |
|------|---------|---------|
| **Form A — parallel tool calls** | `> **Parallel execution:** Use parallel tool calls aggressively — all {tools} operations in {scope} are independent and should run concurrently.` | Independent read-only operations (Glob, Grep, Read, Bash). Front-loads I/O before analysis. |
| **Form B — parallel Task agents** | `> **Parallel execution:** Dispatch {scope} as parallel Task agents — each runs independently and returns {output format}. Assemble results after all agents complete.` | Heavier analytical work where each unit can run in a separate agent thread. |
| **Form C — conditional** | `> **Parallel execution (conditional):** When {condition}, dispatch {scope} as parallel Task agents. Otherwise, run sequentially in the main thread.` | Context-dependent dispatch — e.g., only for large diffs or multiple independent journeys. |

Use the exact blockquote prefix (`> **Parallel execution:**` or `> **Parallel execution (conditional):**`) so directives are visually consistent and greppable across skills.

Forms B and C always pair with the **Subagent Contract** (`plugin/skills/_shared/subagent-output-contract.md`) — minimal input, Templates A/B/C for output, then one of `DONE / DONE_WITH_CONCERNS / NEEDS_CONTEXT / BLOCKED` as a trailing `STATUS: {WORD}` line — the reply's last non-empty line. Each dispatch picks a model profile (`Fast | Standard | Capable`); default to the cheapest that fits the work. Third-party agents are exempt from the agent-side protocol (see CLAUDE.md's Subagent Contract section); the dispatcher's side still applies in full.

**A Form B/C site can itself run inside a dispatched agent** — `/review`'s Step 3 lens fan-out runs inside `/dispatch`'s second Task call. There, "assemble results after all agents complete" is governed by `_shared/subagent-dispatch-core.md`'s Foreground Execution Discipline: the agent keeps its turn alive until every child reports, and self-judges a read-only unit as `unconfirmed` when no `Agent` tool exists or a child is still silent at the bound. Cite that section from the site rather than writing a site-specific ruling, such as skipping the dispatch when the host is a subagent — `review/step3-lens-dispatch.md` carried exactly that carve-out until #3078 replaced it with the shared rule.

**Everything the agent must satisfy goes inside the inlined block.** A requirement written in the skill's own prose beside the template — a rule about what a section must always state, a constraint on when a line may be omitted, a tie-break the agent has to apply — is invisible to the agent: it receives the fenced block, not the file around it. Fold such requirements into the fence itself, or into the dispatch prompt's own enumerated contents list, and read the assembled prompt as the agent would receive it before shipping it. Inlining the template is necessary but not sufficient; the surrounding prose is not part of the dispatch. Inside the fence, order matters too: when a rule carries an exemption, state the exemption's **condition before its example** (or as its own bullet) — never `e.g. {example} … with {condition}`. An example that precedes its qualifying clause is read as the whole rule and the clause is dropped, independently and in the same direction, by the agent and by its reviewer (#704 Task 7).

## Model-version prompting notes

Anthropic documents behavioral differences between Claude model versions that can silently
change how an existing skill's prose is followed — not because the skill's instructions are
wrong, but because the model reading them defaults differently than the model the skill was
written against. Run this checklist whenever a new Claude model version ships, not only for
the Fable 5.1 delta below: re-read the model's own "Prompting Claude {version}" doc (when
Anthropic publishes one) and re-check the deltas that apply to skill instructions specifically.

**Verification/self-check instruction audit (record #2679).** Also part of this checklist:
sample a skill's verification/self-check instructions (and CLAUDE.md's own) against the
effort/verbosity levers in `docs/reference/claude-quality-levers.md` — reasoning-effort
defaults, response-length system-prompt caps, and idle-session context-clearing behavior, none
of which depend on model weights. For each sampled instruction, produce a keep (still
compensating for a real gap) or trim (redundant with the new model's own default behavior)
decision rather than assuming more verification is always safer — a stale instruction can cost
extra turns on a model that already does the check unprompted.

**Description trim audit (record #2799).** Also part of this checklist: re-measure description
totals against the listing budget and re-judge descriptions per
`docs/reference/skill-description-audit.md`, trimming only clauses that are body content or
restated edges, never Keywords tokens or name-collision disambiguation.

**Prompt-audit run over the shipped library (record #3848).** Also part of this checklist: on each
new model release, run Claude Code's prompt audit over the shipped skill prose with
`claude -p "/doctor prompt-audit plugin/" --allowedTools "Read,Glob,Grep,Skill" --disallowedTools "Edit,Write,NotebookEdit,Bash"`
(a read-only tool set), then once more with no path argument to cover CLAUDE.md and `.claude/skills/`.
The audit is the `prompt-audit [<path>]` argument of `/doctor` in Claude Code 2.1.305, not a standalone
`/prompt-audit` command; with no path it audits only session-loaded configuration. Route each finding
through the same three-bucket comparison #3056 used: already covered by `/claude-tweaks:harness-health`,
already covered by this checklist, or genuinely new (a genuinely new finding gets a spec-shaped backlog
record via `/claude-tweaks:capture`, or a stated reason for no action). Do not run the nested
`claude -p` inside an active pipeline session until #3845 is fixed: a nested `claude -p` there marks
the parent's run interrupted at its SessionEnd. `/claude-tweaks:harness-health` does not reach
`plugin/` by design: its discovery (`plugin/bin/lib/harness-health/scope.js`) reads only the
project's `.claude/skills/`, `.claude/rules/`, CLAUDE.md, the auto-memory index, and
`PRODUCT.md`/`DESIGN.md` when design integration is enabled, so this run is the only automated reader
of the shipped library's prose.

**Claude Fable 5.1 vs. Fable 5** (source:
https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-fable-5-1):

| Delta | What changed | What a skill author should check for |
|---|---|---|
| Tool-call batching | In coding/agent loops, 5.1 may issue one independent tool call per turn instead of batching them, where the next calls are implied by the task rather than explicitly requested. | A skill step that names several independent read-only operations (Glob/Grep/Read/Bash) should carry one of this file's own Parallel execution directive forms (see that section above) rather than assuming the model batches them unprompted. |
| Progress-update prompting | 5.1 writes fewer user-facing updates during long tool-calling turns by default, especially at higher effort — a final message can cover only the last step instead of the whole task. | A skill that runs a long, mostly-silent tool chain (a multi-phase pipeline, a sweep) should say explicitly when it wants interim narration and what each update should contain — distinct from this repo's own `auto-decision-log.md` silent-automation-is-forbidden rule, which governs *audit trail*, not conversational narration. |
| Effort-level selection | Effort-level names don't correspond to the same amount of thinking across model versions — a `Fast`/`Standard`/`Capable`/`Frontier` mapping tuned for one model version is not guaranteed to hold for the next. | Re-run the model-profile sweep in `_shared/subagent-output-contract.md`'s Model Selection section against the new model version's own evals before assuming an existing profile mapping still holds. |
| Formatting | 5.1 leans toward less bold/fewer headers/lists by default than earlier models did; anti-formatting instructions written against an earlier model's over-formatting tendency can now over-correct. | A skill carrying explicit anti-bullet/anti-bold language (written against an earlier model's opposite bias) should be re-checked against the new model's own default rather than assumed still necessary. |
| Safeguard false positives | 5.1's safety classifiers produce fewer false positives than earlier launches, but specific phrasings (e.g. "does this compile?" vs. "are there bugs?") and base64 tool output still trigger them more than other phrasings. | A skill instructing an agent to phrase a security/bug-finding request should prefer "are there bugs/vulnerabilities" phrasing over "does this compile/pass" phrasing, and avoid routing base64-encoded tool output through a step that also asks the model to reason about it. |
| Subagent and vision handling | 5.1 coding agents get lower time-to-completion when the lead agent keeps working while a dispatched subagent runs, rather than blocking on it; vision work benefits from crop/zoom tooling on dense images. | A skill dispatching Task-tool subagents for independent work should not require blocking-wait phrasing when the lead has other independent work to continue; a skill analyzing a screenshot/chart should offer a crop/zoom step rather than a single full-image read when detail matters. |
