# The pipeline driver (`drive.js`)

`plugin/bin/drive.js` takes each named record, one at a time and in order, from admission to a draft PR with CI read; with `--budget` it picks the records itself from the dispatch queue (see "Picking records: `--budget`"). A program owns every step; the implementer only writes the change, and the judgment workers only read. A record merges only when it carries `auto:merge` and `auto:build` and the read-only judgment workers clear it — see "The merge step" and "Judgment workers". This page is documentation, not a contract: a few tests in `tests/bin-lib/driver/run.test.js` pin named rules in it, but nothing checks the rest, so update it by hand when the code below changes. The code is the source of truth.

## Running it

```
node plugin/bin/drive.js #N [#M…]
node plugin/bin/drive.js --no-settle #N [#M…]
node plugin/bin/drive.js [--no-settle] --budget <n|all>
node plugin/bin/drive.js --check #N
node plugin/bin/drive.js #N --run <dir> --no-settle
node plugin/bin/drive.js --help
```

- `#N` (or a bare `N`) is a positive record number; duplicates are dropped, order is kept.
- `--no-settle` turns the driver's own settle off, for a caller that settles stops itself. A stop then makes none of the settle calls (under `--run`, a pre-push stop still writes its escalation line; see "When a run stops"); the final line carries the structured `stop` object and `settle: left-to-caller` when the stop's row has calls (`none` otherwise). Default is on.
- `--budget` takes a positive integer (no leading zero) or `all`, is exclusive with named records, and may be given once. `--no-settle` then applies to each driven record. See "Picking records: `--budget`".
- `--check #N` is the read-only verdict: it runs the policy, fetch, eligibility and admission steps (`steps.js`'s `CHECK_STEPS`, the head of the table) and prints one line, `{"record":N,"admitted":bool,"reasons":[…],"widenedBy":[…]}`, the eligibility reasons then the admission reasons (admission still runs after an eligibility refusal, so every reason is reported), then, when admission refused the grant and the typed command was not accepted, one more string, `typed command not accepted: ` and the reason words joined with `, ` (the stop detail's suffix below). `widenedBy` lists `risk`, `ceremony` and/or `protected-path` for a record admitted beyond low risk, fast-lane ceremony or with a protected Key File (empty when eligibility refuses; it can be non-empty beside `"admitted":false` when admission refuses a widened record, for example with the reviewer step off); readers ignore keys they do not know. The record is named, as `drive.js #N` names it, so a typed command can stand in for `auto:build` here too. It takes exactly one record reference and no other option, and makes no write of any kind: no claim, run directory, worktree, comment or label. Exit 0 once a verdict was printed, admitted or not; exit 1, nothing on stdout, when none could be computed (a step failed); exit 2 when malformed.
- `--run <dir>` adopts a run directory and worktree that `/claude-tweaks:dispatch` already made, instead of minting `drive-{n}` and creating `drive-record-{n}`. It requires `--no-settle` and exactly one record, may be given once, and is exclusive with `--budget` and `--check`. A relative `<dir>` is read against the working directory. Before any step, `bin/lib/driver/adopt.js` checks that `<dir>` resolves (by `log-decision.js`'s own anchoring guard) to a direct child of the main checkout's `.claude-tweaks/pipelines/`, that the working directory is inside a linked worktree of that same checkout (not the checkout itself), that `<dir>/run-state.json` names that worktree (dispatch's `hooks.js record-worktree` bind wrote it; compared after realpath), and that the worktree is on a branch. Any failure exits 3 and writes nothing. Once adopted, `adopt.js` also fills `lane: driver` into the run's `manifest.json` (a first known lane wins; best-effort, never changes the outcome — `docs/reference/run-manifest.md`), and the claim's run id is `<dir>`'s basename, the claim log goes to `<dir>`, and the record is built, pushed and opened as a PR from the worktree's own branch. No `git worktree add`, leftover check or `hooks.js record-worktree` call is made, since dispatch's bind is the only one, and the final line's `stop.created` is all false.
- `--in-flight-prs <file>` and `--near-dup-pairs <file>` each take a value, may be given once, and are refused with `--budget` and `--check` (exit 2); `--near-dup-pairs` is also refused without `--in-flight-prs`, which it refines. A relative file is read against the working directory. They feed the merge step's drain-overlap hold; see "The merge step".
- `--help` (or `-h`) prints the usage and exits 0 before any probe of `gh`, `git` or policy.

Exit codes:

| Code | Meaning |
|---|---|
| 0 | Every named record reached its final event, whatever its outcome. Outcomes are data. With `--budget`, also a loop that ended normally: `budget`, `exhausted`, `permission-stop`, `claim-stop` or `policy-refused`. |
| 1 | The policy, or the run's repository or integration branch, cannot be resolved; no further record is attempted. Under `--run`, also an adopted worktree that is on the integration branch itself: `adopt.js` cannot see the integration branch, so the policy step refuses it (`refused`, nothing written) before the claim. With `--budget`, also a failed queue pull. |
| 2 | Malformed invocation (no record reference, a non-numeric one; with `--budget`, a bad or repeated value, or a named record beside it; with `--run`, a missing, empty or repeated value, no `--no-settle`, more than one record, or `--budget` or `--check` beside it; with `--in-flight-prs` or `--near-dup-pairs`, a missing, empty, flag-shaped or repeated value, `--budget` or `--check` beside either, or `--near-dup-pairs` without `--in-flight-prs`), `gh` or `git` absent, or an internal error. |
| 3 | `--run` refused: the run directory is missing or not a run directory under the main checkout, or the working directory is not a linked worktree of it, or the run directory's run-state.json does not name that worktree, or the worktree has no branch. Nothing is written. This is a per-CLI code (as `log-decision.js` and `express-lane.js` use 3 for an unanchored run directory). No caller treats it differently from other non-zero exits: dispatch's driver route reads every non-zero exit as `blocked`. |

With `--check`, the codes mean: 0 a verdict was printed (admitted or not); 1 none could be computed (nothing on stdout); 2 malformed (anything but exactly one record reference).

## Build authority

Admission refuses a record without `auto:build` (`record lacks auto:build`) unless a typed command stands in for the label (#5584). The rule is `resolveBuildAuthority` in `plugin/bin/lib/issues/build-authority.js`; it answers `label`, `typed` or `none`, and admission lifts the grant refusal only on `typed`. A typed command stands in for `auto:build` for that run only. It writes no label and never implies `auto:merge`. A merge grant (`auto:merge`, or `auto:merge-pending` at maturation) authorizes a merge only when the same live label read also carries `auto:build` (#5734): a typed run on a record without `auto:build` ends at `pending-review` (the merge step stops `not-authorized`), and a person merges it with `/claude-tweaks:wrap-up #N merge`. It lifts no other gate: a parked, blocked or unready record is still refused.

The rule's states, first match wins (the same table heads `build-authority.js`):

| State | Answer |
|---|---|
| `labels` is not an array | `none` (`labels-unreadable`) |
| labels carry `auto:build` | `label`; nothing else is read |
| the command did not name the record | `none` (`not-named`) |
| named, labels lack `ready` | `none` (`not-ready`) |
| named, labels carry `bot:blocked`, `bot:parked` or `parked` | `none` (`held`) |
| named, `ready`, inside a Claude Code session, every session condition holds | `typed` |
| named, `ready`, outside a Claude Code session, every terminal condition holds | `typed` |
| anything else | `none`, each failed condition named |

Inside a session means `CLAUDECODE` or `CLAUDE_CODE_SESSION_ID` is set. Session conditions: `CLAUDE_CODE_ENTRYPOINT` is exactly `cli`; `CLAUDE_CODE_SESSION_ATTENDED` is exactly `1`; `CLAUDE_CODE_REMOTE` and `CC_HUB_RUN` are unset or empty; when `CC_POSTURE` or `CC_LAUNCHED_BY` is set, `CC_LAUNCHED_BY` is exactly `user`; and the transcript check (`readTypedCommand`, `plugin/bin/lib/issues/typed-command.js`) finds that a person typed a `/claude-tweaks:dispatch` line naming the record within the last 30 minutes. Terminal conditions: stdin is a terminal, `CI` is unset or empty, and the `CLAUDE_CODE_REMOTE`, `CC_HUB_RUN` and launcher conditions above; no transcript is read. What the check reads and the probe behind it are in `docs/hooks.md`'s "Typed dispatch command"; the reason words and remedies are in `plugin/skills/dispatch/queue-pull-notes.md`'s Typed command section.

The rule has three callers, and none restates it: the queue pull's named path (`plugin/bin/lib/dispatch/queue-pull.js`, `--named`), resume (`plugin/bin/dispatch-resume.js`) and this driver's admission step (`plugin/bin/lib/driver/steps.js`). A new caller calls `resolveBuildAuthority` and never reads the pointer or the transcript itself. The queue pull and resume always pass stdin as not a terminal, so only `drive.js` can take the terminal path.

In the driver a record is named only when it is one of `drive.js`'s own record arguments; a record the `--budget` loop picked never is, so it needs the label. `drive.js #N` typed by a person at a terminal outside any session is the second way to `typed`. Run by the model inside a session, it takes the session path by default and so needs the transcript check for that record: a Bash child of a session inherits `CLAUDECODE` and `CLAUDE_CODE_SESSION_ID` and has stdin not a terminal. That is a default, not a barrier: environment spoofing from a session's Bash child is not prevented. A child that clears `CLAUDECODE` and `CLAUDE_CODE_SESSION_ID` and runs `drive.js` under a pty takes the terminal path, and one that points `CLAUDE_CONFIG_DIR` at a forged transcript passes the transcript check. This is the same class as the accepted residual that a session can add the label by hand. A launcher must not give `drive.js` a terminal on stdin unless a person is at it: a job runner that does, and sets none of the variables above, reads as a person. It must leave stdin a pipe or set `CC_HUB_RUN`.

The `admission` event line carries `authority` (`label`, `typed` or `none`). When admission refuses the grant and the answer is `none` with reason words, the stop's detail is the unchanged refusal text followed by `; typed command not accepted: ` and the words joined with `, `, as the queue pull's line joins them (for example `record lacks auto:build; typed command not accepted: not-named`). An answer with no reason words, or a stop that does not include the grant refusal, adds nothing.

## Picking records: `--budget`

`--budget <n|all>` picks the records itself instead of taking names. The loop is `plugin/bin/lib/driver/budget.js`'s `runBudget`; the queue-pull module and ranking are `plugin/bin/lib/dispatch/queue-pull.js`'s.

Selection:

- Each round is a fresh queue pull, then the `next` ranking over the pulled groups. The grouping is the one the module applies under the project's `express-lane` and `express-driver` values: with `express-driver` `split` or `on`, a fast-lane record this driver would take stays a singleton rather than joining a bundle (#6011). The queue pull's driver half also resolves `express-driver-max-risk` and `express-driver-protected-paths` and asks the widened question: a record widened by risk, ceremony or a protected Key File is driver-routable only with the reviewer step on for it (#6018, #6019). A bundle's members are driven one at a time, in the bundle's order. The loop never reorders or filters beyond the pre-screen and its own `firing` set.
- The pre-screen is the eligibility step's own call over the pulled record. It may skip a record, never admit one: an admitted record still takes the full per-record path (fetch, eligibility, admission, claim). It runs only over groups the ranking could select. A group the pull excluded for a reason the ranking never selects (`UNSELECTABLE_REASONS`: today `oversized` and `neighbour-in-flight`, tied to the queue-pull module's PASSES registry) is never pre-screened, counted or added to `firing`. A selectable group whose every member the pre-screen rules out is counted `skipped` and joins `firing` without costing a pull; that count is taken as each pull arrives, including groups beyond where the run stopped (whatever its `ended` reason), while the skip members of a mixed group are counted only when the loop reaches them. Each counted skip writes `drive.js: pre-screen skipped #N (…); no live fetch` to stderr, naming the eligibility reasons. A record the pre-screen cannot read (no `labels`, a non-string `body`, or an eligibility call that throws) writes `drive.js: pre-screen could not read #N (…); taking the full path` to stderr and takes the full path.
- An empty pulled group, or a group member that is not an object with a positive integer `number`, makes the pull malformed: `ended: pull-failed`, exit 1.
- `express-driver: off` refuses before the pull (`policy-refused`).

Counting: a record consumes budget when its claim was obtained and its run directory minted (`driven`), whatever its outcome. A refused, pre-screen-skipped or contested record, or a claim that fails any other way, consumes nothing.

Termination: every handled record joins this invocation's `firing` set and is never selected twice, so a queue that never shrinks still ends. The run ends when:

- the budget is spent (`budget`);
- the ranking returns `null` (`exhausted`);
- a pull fails or is malformed, or the ranking throws (`pull-failed`);
- a claim stop ends it: `claim-targets.js` exit 7 gives `permission-stop`, counted in `permissionStopped`; exit 2 or 6 gives `claim-stop`, counted in `claimFailed`. That record gets the claim row's settle (one comment and `bot:blocked`, no release call; under `--no-settle` none of it runs and the record's final line carries `settle: left-to-caller`), and the rest of the budget goes unused. Exits 4 and 5, a killed claim, an exit 0 that claimed nothing and a failed mint count `claimFailed` and the loop goes on; exit 3 counts `contested` and the loop goes on.

When no summary line is written: an unreadable policy or a refused origin exits 1, and an interrupt ends the process by its signal. The loop yields to the event loop and checks for an interrupt after the policy step, before and after each queue pull, and after each driven record; a pending signal ends the process at any of those points with no summary line. The hub reads the exit code, or the death by signal.

What the queue pull itself writes, accepted as dispatch has it: the target-missing and shipped passes log decisions and stage Close proposals into the newest `dispatch-standalone` run directory (or an inherited `PIPELINE_RUN_DIR`), and the write-back pass rewrites the queue-order cache. The pull's own session files sit under `os.tmpdir()`. The module's stdout (warnings, AUTO lines) goes to the driver's stderr, so stdout carries JSON event lines only.

## Outcome words

| Outcome | Stop class that gives it |
|---|---|
| `pending-review` | `none`: green CI, a CI state other than green, or a failed summary entry. The draft PR stays for a human. Also what the merge step reports for every stop it makes, with a `reason` (see "The merge step"). |
| `merged` | The merge step merged the PR and confirmed it on a read (no stop class: `merge` reports it as a result). |
| `armed` | The merge step armed auto-merge and the forge holds the merge; the reconciler completes cleanup. |
| `express-escalated` | `pre-push`: any stop before the push, with no PR recorded and nothing pushed. |
| `blocked` | `claim` (any claim failure), `blocked` (any stop after the push, or a non-zero exit of `check` or `escalate`), and a stop class outside the known set (also flagged `unclassified`). |
| `refused` | `refused`: not eligible, not admitted, routing off, an unreadable record. Nothing is written. |

## Event lines

One JSON object per line on stdout and, once the run directory exists, in `{run-dir}/driver-events.jsonl`.

A step line: `ts`, `run` (the run id, `null` before the run directory exists), `record`, `step`, `status` (`ok`, `fail`, `stop`), `ms`, any extra fields the step adds (the `eligibility` step adds `widenedBy`, only for a record admitted above `risk:low` or with a non-fast-lane ceremony (#6018); the `admission` step adds `authority`, see "Build authority"; the worker step adds `usage`, `turns`, `denials`, `sessionId` (the worker's session id, only when the envelope names one), `tests` (which path the targeted test command took, #5915: `declared` when origin's `verify-scope.json` gave a usable `impact.command`, `none` when there is no such file, no `impact.command` or an unusable one, `unreadable` when a git read or the JSON parse failed, `unsupported-platform` when the implementer has no Bash and nothing was read), `profile` (the work profile the launch resolved, #5997), `attempt` (`1` on a first launch's line, only when the line also carries `model`; `2` on an implementer relaunch's line, `3` on a second relaunch's under the effort ladder; a relaunch's line also carries `escalatedFrom`, the previous attempt's profile, and `trigger`, `cannot-complete` or `red-tests`; see "Worker models"), `fix` (`true` only on the review fix round's relaunch line, which sits inside the `review` line's `ms`; that line adds `profile` only) and, when the last turn crossed the spend ceiling, `spendOverrun`; the `review` step adds `returned`, `reproduced`, `discarded`, `usage`, `denials`, `costUsd`, `turns` and, when a fix round ran in a session the envelope names, `fixSessionId`), and `detail` when there is one. The `worker`, `review`, `merge-check` and `merge-acceptance` lines also carry `model`, the requested model alias, once a launch resolved one (#5917; see "Worker models"), and `effort`, the requested effort level or `null` (#5942; see "The `effort` field" there). A worker or test line that triggered a relaunch rule but did not relaunch carries `noRelaunch` (`no-step-up` or `clamped`); a relaunch writes a second `worker`, `commit` and `test` line under their own names. A step that is skipped (the `review` step with policy `express-driver-review` off, or beyond-express on a record inside the express bounds) writes no line at all. `step` is one of: `policy`, `fetch`, `eligibility`, `admission`, `claim`, `run-dir`, `worktree`, `worker`, `commit`, `test`, `check`, `review`, `push`, `pr`, `record-pr`, `set-config`, `summary`, `ci`, `merge`; the merge step's own sub-step events are `merge-entry`, `merge-supplier`, `merge-check`, `merge-acceptance`, `merge-closing-links`, `merge-compose`, `merge-overlap`, `merge-ready`, `merge-gate`, `merge-watch`, `merge-park`, `merge-conflict`, `merge-accept-park`, `merge-call`, `merge-confirm`, `merge-post-merge`, `merge-release-status`, `merge-reconcile`, `merge-teardown`, `merge-delete-branch` and `merge-close-run`; a settle call uses one of the `settle-*` names below.

The final line (`step: "final"`) adds:

| Field | Meaning |
|---|---|
| `outcome` | The outcome word. When settle ran, the class it settled to (a failed escalate reads `blocked`). |
| `msTotal`, `msWithoutCi` | Elapsed time with and without the CI wait. |
| `pr`, `ci` | The PR number and the CI word; `ci` is `pending` when a PR exists and CI was never read. |
| `costUsd`, `turns`, `denialCount` | The implementer's cost, turns and permission-denial count, summed over every implementer launch: the first, each relaunch under `implementer-tier: record` (one, or two under the effort ladder), and the review fix round's (`null` with no worker). The reviewer's cost and turns are not included; they are on the `review` line. |
| `stop` | The structured stop (below). |
| `settle` | `done` (the row had calls and they ran), `left-to-caller` (`--no-settle`, and the row has calls), `none` (the stop's row has no calls, with or without `--no-settle`), or `interrupted` (see below). `left-to-caller` always means there is something to settle. |
| `settleFailed` | Step names of settle calls that failed. |
| `settleRow` | The row of the settle table used (`refused`, `claim-contested`, `claim`, `pre-push`, `blocked`, `none`), or `null` when nothing stopped or an interrupt landed before settle started (an interrupt during settle keeps the row it was running). |
| `unclassified` | `true` when the stop class is outside the table; it was settled by the `blocked` row. |
| `settleNote` | A note from settle: the TTL note for a claim that may have been written, or the unreadable `run-state.json` note. |
| `spendOverrun` | `true` when a worker returned normally but its cost crossed the spend ceiling. Reported, never settled; the run continues. |
| `eventsFileError` | Present when appending to the jsonl failed. |
| `merge` | Present when the merge step ran: `{ outcome, reason, mergeCommit, postMerge }`. `postMerge` is `{ verdict, failedSteps, failures }` for `merged` and `null` otherwise. |
| `eventsFile` | `stdout-only` when neither the run directory nor its archive twin existed after the merge step's reconcile, so the events went to stdout alone. Absent otherwise. |

The `stop` object: `step`, `class` (`refused`, `claim`, `pre-push`, `blocked`, `none`), `pushed`, `created` (`{ worktree, branch }`, what this run created), `reason`, `detail`, `checkLogged` (`check`'s `logged` value: whether `check` wrote its own decision line, proceed or escalate; `null` when `check` did not run). A pre-push `reason` is always one of `failing-test`, `out-of-bounds`, `gate-denial` or `express-error`, so a `--no-settle` caller need not re-derive it. A claim stop's reason is `claim-exit-{code}`, `claim-exit-none` when `claim-targets.js` was killed or timed out, or `fail` when it exited 0 without claiming the record, when the run directory could not be minted, or for an interrupt after the claim.

A `--budget` run writes one more line, last (the summary line, `step: "budget"`, with `run` and `record` `null`; it goes to stdout only, never to a run directory's jsonl). Every handled record is in exactly one counter. Fields are added and never renamed: a consumer in another repository, the hub, reads this line.

| Field | Meaning |
|---|---|
| `budget` | The value given: a positive integer or `all`. |
| `driven`, `refused`, `skipped`, `contested`, `claimFailed`, `permissionStopped` | The six counters. `driven` is the records that consumed budget (claim obtained, run directory minted); `refused` a record refused before the claim (a failed live fetch, eligibility or admission); `skipped` a record the pre-screen ruled out (a whole-group skip is counted as each pull arrives, including groups beyond where the run stopped, whatever its `ended` reason; the skip members of a mixed group are counted only when the loop reaches them); `contested` a claim lost (`claim-targets.js` exit 3); `claimFailed` any other claim failure; `permissionStopped` an exit 7. |
| `ended` | Why the loop ended: `budget`, `exhausted`, `permission-stop`, `claim-stop`, `pull-failed` or `policy-refused`. |
| `status` | From `ended`: `ok` for `budget`, `exhausted` and `policy-refused`; `stop` for `permission-stop` and `claim-stop`; `fail` for `pull-failed`. |
| `detail` | Present with `permission-stop`, `claim-stop` (the exit code and record) and `pull-failed` (`queue pull failed: ` followed by the first line of the failure). |

`policy-refused` is preceded by a `policy` line with status `stop` and `detail` `express-driver off: --budget drives nothing`. `tests/bin-lib/driver/run.test.js` pins the exit codes and the `ended` to `status` mapping (`budget AC9.5`); `tests/bin-lib/driver/budget.test.js` pins the loop.

Settle calls are step lines named `settle-escalate`, `settle-comment-pr`, `settle-comment-record`, `settle-label`, `settle-release`, `settle-remove-worktree`, `settle-delete-branch` and `settle-close`, emitted before the final line. A failed call has status `fail`, is never retried, and does not stop the calls after it (one exception, below).

## Station events

The station file, `.claude-tweaks/station-events.jsonl` in the main checkout, is the contract other tools read; `driver-events.jsonl` is not. The driver mirrors its own step lines into it through the same sink (`started` and `exited` for `worker`, `test`, `review`, `pr`, `ci` and `merge`, plus a `session_bound` for every worker session, the review fix worker's included, and the merge-station boundaries from three merge sub-steps), and an unwritable file never changes a driver result. The line format, stations and failure posture are in [docs/reference/station-events.md](reference/station-events.md).

## The reviewer step

Between `check` and `push` the driver can run one read-only reviewer worker (`plugin/bin/lib/driver/review.js`). The reviewer returns findings, each with a location, a claim and an evidence test file. A finding counts only when its evidence file, which the driver (not the reviewer) writes into the worktree and runs once with `node --test`, fails. A finding whose test passes, does not load, or cannot be placed is discarded and removed. Nothing the reviewer says is acted on without a red test.

Policy key `express-driver-review` (`policy.yml` only; a `--run` config never switches it):

| Value | Effect |
|---|---|
| `off` | The step is skipped and writes no event line. |
| `on` | The step runs for every record. |
| `beyond-express` (default, also for an unset or malformed value) | The step runs for a record whose size label is missing or not `low`, or that has more than three Key Files (`EXPRESS_MAX_KEY_FILES`), or a record widened by risk; a record with unreadable Key Files counts as beyond. A record inside the express bounds skips it. The driver's eligibility gate refuses the same records (a size label missing or not `low`, more than three Key Files), so under this default and the default lane bounds the step runs in a real run only for a record widened by risk, which the default ceiling admits only when it carries both `risk:low` and a higher risk label, with `risk:low` the last risk label (risk is a last-match-wins facet); widening the lane bounds (below) or `on` is how it runs. |

The `review` event line adds `returned`, `reproduced`, `discarded` (returned = reproduced + discarded when the pass does not stop), and the reviewer's own `usage`, `denials`, `costUsd` and `turns` (`null`, or `[]` for `denials`, when the reviewer returned no envelope). The final line's `costUsd` and `turns` leave the reviewer out, so a record's total spend is the two lines added. The reviewer launches on the `reviewer` model from `express-driver-models` (default `capable`), and the line's `model` names it (see "Worker models"). TAP output of each evidence run goes to `{run-dir}/review/review-evidence-{i}.tap`, and of the fix round to `{run-dir}/review/fix-evidence-{i}.tap`.

**One fix round.** When at least one finding is confirmed, the implementer launches once more with the first prompt plus the confirmed findings. The driver then rewrites each evidence file from the recorded content, commits, re-runs the scoped tests, runs each evidence file directly, judges that the worker changed something beyond the evidence files (after every rerun has passed), and runs `check` again. There is no second round: the fix round launches one more implementer, so a record makes at most three implementer launches (first attempt, relaunch, fix round), four under the effort ladder (a second relaunch), and with the step on up to four workers beside the merge ones (five under the ladder), each under the full ceilings. The fix round launches on the profile of the attempt that went green. After the fix commit, every evidence file must be tracked at HEAD with its recorded content (CRLF against LF ignored), which catches a fix worker that gitignores, deletes or edits the regression test, and before each direct run the file in the worktree must still resolve where it was confirmed (no parent swapped for a symlink) and hold those bytes, read from disk rather than through git status (a `--skip-worktree` or `--assume-unchanged` flag hides an edit from it). A fix commit that finds nothing to commit stops the round, and a fix worker that moved HEAD has already stopped at its launch (Worker rights). A stop names the finding as `{cause}: {path}:{line} {claim}`, with the reviewer's text on one line, bounded, and with no issue reference or mention. Like every pre-push stop it settles as `express-escalated`, except a propagated test or `check` result, which keeps its own class.

### Residuals

- The driver runs worker-written test code with its own rights, as its own test step and every other lane already do.
- The evidence test is run once, so a test that is red by flakiness confirms a finding that is not real.
- A red test is the reviewer's own assertion, so a wrong expectation confirms a wrong finding.
- The evidence file is always run with `node --test`, whatever runner the project's `npm test` uses. In a project on another runner only evidence written against `node:test` can be confirmed, and that project's own CI is what then catches a regression test its suite does not run.
- The classification rule covers only the `node --test` TAP shape captured for #5222. A Node or reporter upgrade means re-capturing the fixtures in `tests/bin-lib/driver/fixtures/review-evidence/`.
- An evidence path holding a character `node --test` expands as a glob (`[ ] { } ( ) ! + @`, beside the already refused `* ?`) is refused unwritten, so a legitimate test at a bracketed path (for example `app/[id]/page.test.js`) is discarded, not run.
- The reviewer's read confinement rests on `--restricted` alone: its launch has no settings file and no read block, and no live probe of a `settings: false` launch has been made. The evidence run has HOME and the network.
- The tree check reads plain `git status`, so it cannot see an evidence test that changes ignored files (for example `node_modules/` or build output) or creates empty directories. Such changes can affect later runs.

### Lane bounds

Four policy keys bound the records and diffs the driver takes on (#5224, #6018). All four are `policy.yml` only: a `--run` config never widens them. Each defaults to the express lane's value, and a malformed value resolves to the default (`invalid: true`), so it never widens the lane. One value is not resolved away: an all-digit `express-driver-max-lines` past 2^53 passes the resolver but is not a safe integer, so the policy step refuses it before any record is claimed and the run exits 1.

| Key | Default | Bounds |
|---|---|---|
| `express-driver-max-size` | `low` | The highest size label eligibility accepts. `low` accepts `size:low` only; `medium` accepts `size:low` and `size:medium`. A `size:high` record is never accepted. |
| `express-driver-max-key-files` | `3` (`EXPRESS_MAX_KEY_FILES`) | The most Key Files eligibility accepts. |
| `express-driver-max-lines` | unset = `auto-merge-max-lines` | The implementation-line bound `check` applies to a record the reviewer step is on for. |
| `express-driver-max-risk` | `low` | The highest risk label eligibility accepts. `low` accepts `risk:low` only; `medium` adds `risk:medium`; `high` adds `risk:high`. An unlabelled risk is refused under every value. |

A record beyond the express bounds (a size label that is not `low`, or more than `EXPRESS_MAX_KEY_FILES` Key Files) is admitted only when the reviewer step is on for it; otherwise admission refuses it with `record is beyond the express bounds and the reviewer step is off for it`. When a record beyond the express bounds, with the reviewer step off for it, is inside the lane bounds but fails another eligibility rule, the eligibility stop names that admission reason after eligibility's own. The driver passes `check --max-lines` only when `express-driver-max-lines` is set and the reviewer step is on for the record; otherwise it passes no flag and `check` reads `auto-merge-max-lines` itself. The worker's prompt states whichever bound `check` applies. Whether the reviewer step is on is decided once per record, in the eligibility step, and admission, the flag and the reviewer step all read that one answer. With `express-driver-review: on`, any recognised `ceremony:*` label passes eligibility (an unrecognised spelling still refuses). A record admitted above `risk:low`, with a non-fast-lane ceremony, or with a protected Key File (below), is widened: it is admitted only with the reviewer step on for it (otherwise admission refuses it with `record is admitted widened (above low risk, with a non-fast-lane ceremony or a protected Key File) and the reviewer step is off for it`; `record widening facts unreadable` when the facts cannot be read), turns the reviewer on under `beyond-express` (`admitted widened by risk`), and always stops at the merge step as `widened-admission`, so a human merges it. The widened values are chosen by editing `policy.yml`, not by the change that added these keys: its defaults widen nothing.

`express-driver-protected-paths` (#6019, `policy.yml` only, not a bound) takes `refuse` (the default: a protected Key File refuses, as before) or `reviewer`. Under `reviewer` the merge-time families (`hooks/`, `hooks.js`, `hooks.sh`, `skills/_shared/`, `CODEOWNERS`) pass eligibility with `protected-path` in `widenedBy`; the build-time families (`.github/`, `.gitlab-ci.yml`, `.circleci/`, `.githooks/`, `.husky/`, `package.json`, `.claude/settings*.json`, `.mcp.json`, and `.claude-tweaks/policy.yml` and `.claude-tweaks/verify-scope.json`, which `check` and `verify.js` read from the PR's own worktree, so a branch editing them would loosen the checks that judge it) refuse under every value, and `merge-sensitive-paths` still refuses. The driver passes `check --protected-paths reviewer` only when the key is `reviewer` and the reviewer step is on for the record; `check` then reports every merge-time protected path in the diff in `bounds.protectedPaths`, listed Key Files included; the paths that add the check-time widening are the unlisted ones it can now report, a protected test file or a rename's old path (any other unlisted path already refuses as `outside Key Files`), and the driver adds `protected-path` to `widenedBy` too (also when the envelope carries no `protectedPaths` array, which fails closed). A check-time `protected-path` reads `admitted widened by protected-path` in the merge-entry detail, like an eligibility-time one, and the check's proceed line in `decisions.md` names the reported paths. The record always stops at `widened-admission`, so a human merges it. The protected list is the `protected-paths` key (#6020), read from the main checkout's `policy.yml`: unset or malformed keeps the shipped list, and a set list replaces it. Under `reviewer` a path the project adds is never build-time, and a build-time family the project removes is not protected at all.

## The merge step

`plugin/bin/lib/driver/merge.js` is the last step. It runs only after the CI wait ends `green` (any other CI word leaves the step line `not entered: ci {word}`), makes no model call itself, and takes its one judgment from `deps.judgments`, the supplier `mergeStep` builds from `deps.createJudgments` (production binds it to judgments.js; see "Judgment workers"). A deps object with neither a supplier nor `createJudgments` stops at `no-supplier`. It never stops the run: every stop is a result, so the record's outcome comes from it, not from a stop class. The source of truth is the code; this section is copied by hand.

Entry runs in this order, and each refusal is `pending-review` with the reason named: the supplier is present (`no-supplier`, with no other call made); `gh` is available (`gh-absent`); the record's live labels carry `auto:merge` and `auto:build` (`labels-unreadable`, `not-authorized`); the record is not widened (`widened-admission`): the run's widening list, unioned with the risk and ceremony widenings recomputed from the live labels, and a missing or malformed list stops too; the run logged its summary entry (`summary-entry-missing`); `integration-model` resolves `pr-first` and the run records a PR (`not-pr-first`); with `--in-flight-prs`, the drain-overlap hold below finds no open listed PR sharing a path or closing a strong near-duplicate partner, and can read its inputs (`drain-overlap`, `near-duplicate`, `in-flight-unreadable`, `in-flight-read-failed`); one supplier call returned a well-formed answer (`supplier-failed`), whose verdict is `auto-merge` (`verdict-not-confirmed`), whose acceptance is completed (`acceptance-not-completed`), and whose verdict line is confirmed in `decisions.md` (`verdict-not-confirmed`). Then the closing-link check, the subject composition (`compose-refused`), mark-ready (`ready-failed`), the gate, the bounded watch (15 minutes, polled every 30 seconds, so a PR that turns conflicting mid-watch stops as `conflict` at that poll), the labels read again immediately before the merge call (which rechecks the widening on that read: a widening found there stops at `merge-call` as `widened-admission`, detail `widened by … at the pre-merge read`), and `gh pr merge ... --match-head-commit {head}` against the head `check` verified. The merge is confirmed by a read: only a `MERGED` state is `merged`, an open PR holding auto-merge is `armed`, anything else is `merge-refused`. A `merge-refused` stop (a checks, permission or unrecognized refusal of the merge call, or a confirmation read showing neither state) leaves one comment on the PR from a fixed template, per `_shared/pr-first-merge.md` Step 3's "degrade to ready+comment", and parks nothing; a failed post is named in the event detail and logged to `decisions.md` as a SKIP.

The route through the gate follows the `merge-verification` policy key, read once at entry and named on the `merge-entry` event (`lever {value} ({source})`). Only `merge-when-green` changes the route: `wait`, `off` and an unresolved value all run as `wait`, and `off` or an unresolved value is logged to `decisions.md` as such. On the gate's first read, a PR that is not open is `pr-not-open` and a head other than the one `check` verified is `moving-target`. On a later read (the fresh read before an immediate merge, or a watch poll), a PR no longer open or with a changed head re-enters the gate once, recomposing the subject; a second change is `moving-target`. A conflicting PR takes the conflict path on any read. On the gate's first read and each watch poll, red checks park as `check-failed:{names}` and a draft skip with no ready trigger parks as `draft-skip-without-ready-trigger:{files}`; the fresh read before an immediate merge reads no checks. Otherwise:

| The read finds | `wait` | `merge-when-green` |
|---|---|---|
| green checks, on the gate's first read | a fresh read, then `gh pr merge --squash` | `gh pr merge --auto --squash` |
| green checks, on a watch poll | a fresh read, then `gh pr merge --squash` | the same as `wait` |
| pending checks, merge state `BLOCKED` | the bounded watch | `gh pr merge --auto --squash`, which arms auto-merge |
| pending checks, any other merge state | the bounded watch | the bounded watch |

A watch that reaches its 15-minute bound with checks still pending parks as `checks-pending-timeout`. An `--auto` call GitHub refuses as not allowed moves the rest of the run to the `wait` column: a green read takes the fresh read and the immediate merge, and a pending one goes to the bounded watch (a watch the arm interrupted keeps its deadline).

**The drain-overlap hold.** With `--in-flight-prs <file>` (a JSON array of PR numbers or `{ number }` objects, the other drain PRs in flight) the step holds at entry, after the `not-pr-first` check and the lever read and before the judgment supplier, so a held record launches no merge-check or acceptance worker and its PR stays in draft (`merge-overlap` sub-step), since compose, mark-ready and the merge call all come later. It reads the own PR's changed paths and each listed PR's state and paths (`gh pr view --json state,files`, through the batch bound); a listed PR no longer `OPEN` is skipped, the own PR in the list is ignored, and the first open one sharing a path holds as `drain-overlap`, naming the PR and the shared paths. With `--near-dup-pairs <file>` (dispatch's strong near-duplicate pairs, `[{ records: [a, b], … }]`, strong pairs only, as `queue-pull.js` writes it) the same read also takes `closingIssuesReferences`, and an open listed PR that closes a strong partner of this record holds as `near-duplicate`. A `drain-overlap` or `near-duplicate` hold, when the run has a run directory, first writes the prose hold's `decisions.md` line, `Auto-merge gate: group [#{n}] held — overlaps drain PR #{pr} on {files}; merge order is a human call.` (or `(near-duplicate of #{partner})` in place of `on {files}`), which the Review Console's resolver parses (`drainOverlapHoldPrs`, `console/resolve.js`); a failed write is named in the event detail and never lifts the hold. The fail-closed holds name no PR and write no such line. It ports `dispatch/drain-pr-overlap.md` Step 6's hold with two deliberate differences: paths compare by plain equality (no hub-file filter), and every read fails closed: an unreadable or malformed file holds as `in-flight-unreadable`, and a failed or unparseable PR read, or a file list of exactly 100 entries (possibly cut by GitHub), holds as `in-flight-read-failed`. With `--in-flight-prs` absent no hold is applied: that is the standalone case of one record at a time, so the caller that runs a drain passes the list. A relative file is resolved against the working directory.

The reason words are a closed list (`REASONS` in `merge.js`); anything else is `unclassified`, with the failing sub-step named in the event detail: `no-supplier`, `labels-unreadable`, `not-authorized`, `widened-admission`, `summary-entry-missing`, `not-pr-first`, `gh-absent`, `supplier-failed`, `verdict-not-confirmed`, `acceptance-not-completed`, `compose-refused`, `ready-failed`, `state-read-failed`, `pr-not-open`, `moving-target`, `checks-read-failed`, `check-failed:{names}`, `checks-pending-timeout`, `draft-skip-without-ready-trigger:{files}`, `conflict`, `merge-refused`, `drain-overlap`, `near-duplicate`, `in-flight-unreadable`, `in-flight-read-failed`, `awaiting-local-acceptance`, `park-failed`, `already-parked`, `park-state-unknown`.

**The local acceptance park.** Past the gate and before the first merge call of any mode (an arm included), the step ports `_shared/pr-first-merge.md` Step 2.9 once per run (`merge-accept-park` sub-step) through `bin/accept-park.js`. `parked --record {n} --run {run dir}` exiting 0 (parked by an earlier run) stops as `already-parked`, and exiting 6 (unknown) as `park-state-unknown`, both with no `park` call, so this run archives and releases nothing; any other exit (2, 3) than 5 (not parked, which control mode off always prints, with no forge read) stops as `supplier-failed`. Then `decide --run {run dir} --head {the verified head}` (under control mode `--head` is the diff tripwire's target, a full oid the driver already holds; the CLI's `--run` is optional; without it `decide` reads the repo-root `policy.yml` alone, as tidy's record-linked arm runs it; the driver is deterministic Node and passes no `--classification`, so its tripwire reads the path globs alone and the packet says `agent classification not run`, where a Step 2.9 merge also gets the agent's reading; the call runs under its own budget, `decideTimeoutMs` in `merge.js`: one CLI bound plus nine of the live `GIT_TIMEOUT_MS`): a non-zero exit, or a line that is not exactly one decision for the run's record, is `supplier-failed`; no park continues to the merge call unchanged; a park runs `park` under its own time budget (`parkTimeoutMs` in `merge.js`: five CLI bounds, reconcile's archive bound and two of the live `GIT_TIMEOUT_MS`, 810 s at the defaults; a budget, not a true sum, since `park`'s node children carry no inner timeout and its claim release makes several git calls) with `--claimed` the run's record, `--head` the verified head, `--worktree` the run's worktree and `--worktree-mode remove` (`caller` under `--run`, where the dispatching session removes the worktree). The park owns the archive, the claim release and (standalone) the worktree removal, so the step runs no teardown and writes no decision line after it; it follows the run directory into the archive as reconcile does. A park that exits 0 is `awaiting-local-acceptance`, its detail naming each `steps` entry with `ok: false`; any other exit is `park-failed`. Neither merges. The two calls run with control mode off too, so a spawn, EACCES or timeout failure of `accept-park.js` there stops the merge as `supplier-failed` (or `park-state-unknown` on a `parked` exit 6) where, before the park, the run would have merged: a deliberate deviation that fails closed.

What each `pending-review` reason leaves behind:

| Reasons | PR | Record labels | Comments |
|---|---|---|---|
| `no-supplier`, `summary-entry-missing`, `not-pr-first`, `supplier-failed`, `verdict-not-confirmed`, `acceptance-not-completed` | draft, untouched (a `supplier-failed` from the local acceptance park: ready) | none written | none written by `merge` |
| `gh-absent`, `labels-unreadable`, `not-authorized`, `widened-admission`, `compose-refused` | draft when the stop precedes mark-ready; otherwise as the last call left it (ready) — the labels are read again before the merge call, and the gate's re-entry recomposes the subject | none written | none written by `merge` |
| `ready-failed`, `state-read-failed`, `pr-not-open`, `moving-target`, `checks-read-failed` | as the last call left it (ready once marked ready) | none written | none |
| `merge-refused` | ready (for a confirmation-read refusal, as that read found it) | none written | one on the PR |
| `check-failed:{names}`, `checks-pending-timeout`, `draft-skip-without-ready-trigger:{files}` | ready (re-drafted only by the label-failure fallback) | `bot:parked` | one on the record |
| `conflict` | ready | none | one on the PR |
| `drain-overlap`, `near-duplicate`, `in-flight-unreadable`, `in-flight-read-failed` | draft (the hold runs before mark-ready) | none written | none written by `merge` |
| `awaiting-local-acceptance` (this run's `park` succeeded) | ready, open | `accept:pending` | the acceptance packet (posted or edited by `park`) |
| `already-parked`, `park-state-unknown` | ready (made ready, if draft, before the park check), open | none written (an `already-parked` record keeps the pending label an earlier park wrote; a `park-state-unknown` one may not carry it) | none written |
| `park-failed` | ready, open | whatever `park`'s steps 1 and 2 wrote before failing; after a killed or unstarted call (no exit code), steps 3 to 5 may also have run, so the record may be parked (the detail says to re-check with `accept-park.js parked`) | as `park` left it |
| `unclassified` | as the last call left it | none | none |

What each outcome leaves behind:

- `merged`: the post-merge sequence ran. Reconcile archived the run (the later decision lines and the final event follow it into `archive/{run-id}/`), and released the claim; the worktree, the local branch and the remote branch were removed. Under `--run` the worktree and the local branch are kept for the caller (teardown makes no git call and says so on its `merge-teardown` event); the remote branch is still deleted and the run still closed. A post-merge failure never changes the outcome from `merged`; it is named in `postMerge.failures`.
- `armed`: the claim, the worktree and the run directory all stay. The reconciler completes cleanup on merged evidence once the forge has merged the PR, and the locked worktree is reaped after its owner pid dies (24h orphan grace).
- `pending-review`: the PR is left as the table above says. `merge.js` makes no release, label-removal or git call that would undo the claim, so the claim is left as it was (the settle `none` row below makes none either). `already-parked` and `park-state-unknown` follow that rule: no `park` call ran, the run directory is not archived and the claim is not released. The exception is `awaiting-local-acceptance`, which only a successful `park` call reports: `accept-park.js park` itself archives the run and releases the claim, and removes the worktree for a standalone run (a failure among those is named in the detail). Under a `--run` adoption the park is called with `--worktree-mode caller`, reports `caller-removes {path}` for its removal step and leaves the worktree in place; the dispatching session removes it (`plugin/skills/dispatch/driver-route.md`).

The final line carries a `merge` field (`{ outcome, reason, mergeCommit, postMerge }`) and, when the events could no longer be written to a run directory, `eventsFile: 'stdout-only'`. An interrupt (SIGINT, SIGTERM) during the merge step makes no further call and emits nothing more: the step yields only while it awaits the supplier (which itself checks after each worker launch, and then logs, emits and launches nothing further) and during the watch's sleeps, and checks for an interrupt after each (every other call is synchronous, so a signal is seen at the next of those points or after the step). A signal that arrives after a merge landed still reports `pending-review` (stop class `none`), because the step has no interrupt rung of its own; the reconciler's merged-evidence checks complete such a run. The watch's wait is reported on each `merge-watch` event and added to `msTotal - msWithoutCi`.

## Judgment workers

The merge step's one judgment comes from two read-only headless workers, run in order by the supplier `createJudgments({ deps, shared })` (`plugin/bin/lib/driver/judgments.js`). `realDeps.createJudgments` binds it, and `mergeStep` builds the supplier over the merge deps and the run's shared state (so a signal can kill a running worker). The source of truth is the code; this section is copied by hand.

**Roles and rights.** Both roles (`merge-check`, `acceptance` in `roles.js`) get `Read`, `Grep` and `Glob` only and launch under the same ceilings as every other worker. A worker returns a result and nothing else: the merge-check worker a verdict and a rationale, the acceptance worker Try it groups, an observation plan, claims and a parent brief. It never writes a file, a comment, a label or a decision line, and any labels in its output are never read. Code does every write, and worker text reaches a posted body only through the packet renderers (`inline`, or the packet's own `render`), line by line. Before a `try-it-only` or `due-exceeds` post, every worker-written field also passes the packet's credential screen (`findCredentialInText`); a hit stops the route, names the field and never the value, and posts nothing.

**The supplier and its return shape.** `judgments(ctx)` resolves to `{ mergeCheck: { verdict }, acceptance: { completed } }`, the shape `merge.js`'s `consultSupplier` takes, and never throws. The merge-check half runs first; acceptance runs only after a verdict that code logged and re-read from `decisions.md` (`confirmFromFile`) as `auto-merge`. Any other verdict (`needs-human`, `unconfirmed`) returns `acceptance: { completed: false }` with no acceptance launch. A worker that returns anything but the exact string `auto-merge`, a failed or timed-out launch, a missing skill section, a failed record or diff read, and a verdict line that could not be logged or confirmed are all not-`auto-merge`: every failure on the way is a stop, never a pass.

**The three code floors.** Decided before any launch, with no judgment: a blast radius that failed to run, returned unusable output or reported no finite size ceilings (`blast-radius-failed`), a change that touches a sensitive path (`sensitive-path`), and a diff over the prompt cap of 100,000 bytes (`diff-truncated`), so no verdict is reached on a diff the judge saw only in part. The merge-check event's `floor` is one of these three or `none`. Each is `needs-human`, logged as the verdict line, and launches no worker.

**Acceptance routes.** Decided in code from `parent-gate.js --sub-issue {n} --closing {n}` and the record's `risk:*`/`size:*` labels against the `risk-floor` and `size-floor` policy values; the worker never picks the route.

| Input | Route | Labels |
|---|---|---|
| parent gate exit 0, `state` `incomplete`, `gated` or `resolved` | `try-it-only` | none |
| `state: due`, `exceeds === false` | `try-it-only` (the end-to-end Try it rides in the same comment) | none |
| `state: due`, `exceeds === true` | `due-exceeds` | `accept:pending` on the parent |
| `state: no-parent`, floor not exceeded | `no-parent-exempt` | none |
| `state: no-parent`, floor exceeded (an unscored record counts as exceeded) | `no-parent-gated` | `accept:pending` on the record |
| parent gate exit non-zero, or stdout that did not parse (including exit 0 with JSON `null`) | fails open to the two no-parent rows, with `fallback: parent-gate failed` named in the detail | per the no-parent row |
| exit 0 with a `state` outside the five, or `due` with a non-boolean `exceeds` | no route: the acceptance stops with the state named | none |

The `try-it-only` routes post the Try it block as the `try-it` run comment on the PR (the trusted one is updated in place, else one is created). `due-exceeds` also posts the parent's verification brief on the parent (once) and applies `accept:pending` there (the successor spelling of `demo:pending`, `_shared/work-record.md`: readers accept either, the driver writes the new one). The no-parent routes have no separate PR comment: the Try it block reaches the acceptance packet's Test guide through `acceptance-packet.js` (`gather`, `render`, `post`), and `no-parent-exempt` then records the oversight exemption with `set-verify-expectations.js`. Both `gather` calls are handed the record body as `--spec` (read once, written to the run's `acceptance/` temp dir), so the worker sees the record's acceptance criteria and the packet lists them as not-run rows. The first `gather` supplies the facts the worker cites; the second adds the links built from its Try it groups. A `render` that reports any dropped or screened claim stops the route before the label and the post: a partial packet is not a completed acceptance. An observation plan of kind `app-route` or `rendered-page` stops acceptance: it needs the visual-review safety net, which the driver does not run.

**Models.** `merge-check` and `acceptance` launch on their `express-driver-models` profiles (default `standard`), and the `merge-check` and `merge-acceptance` lines carry `model`. A launch-time model refusal (`DRIVER_MODEL_REFUSED`) is a throwing launch: it reads as `needs-human` for `merge-check` and `completed: false` for `acceptance`, with the code in the line's `detail` (see "Worker models").

**Prompts.** The merge-check judge's prompt is `assess-agent-autonomy/merge-check.md`'s Step 2, read at run time; a diff cut at the prompt cap is marked `[diff truncated]`; merge-check never launches on one, because the `diff-truncated` floor decides it first. The record and parent bodies are wrapped as untrusted content. Before wrapping, the title and body are NFKC-normalised, invisible format characters are removed, and every run of three or more angle-like characters (ASCII and the guillemet, angle-bracket and math forms NFKC leaves unfolded) is replaced, whatever words surround it, so only the template's own two marker lines carry such a run. This is a structural defang, not a check of the marker wording: a marker split across two lines, padded with zero-width characters or spelled in fullwidth forms leaves no run to forge. It covers only those characters. A lookalike outside the set (the Canadian syllabics `ᐸ` `ᐳ`, the curved angle brackets `⧼` `⧽`) or angle characters separated by spaces pass through unchanged, so a body can still hold a line that looks like the end marker; only the prompt's instruction then keeps the judge from reading it as one. The acceptance prompts are read at run time from `_shared/try-it.md`, `_shared/observation-plan.md`, `_shared/acceptance-packet.md` and `wrap-up/verification-brief-parent-gate.md`. A skill file edit therefore changes the judge with no driver change.

**Re-run rule.** Any change to a judgment prompt, to a skill file a judgment prompt is taken from (`merge-check.md` and the files above), or to the model a judgment role launches with re-runs `node tools/driver-merge-check-eval.js evaluate` as part of that change's own acceptance.

## When a run stops

The source of truth is `SETTLE_ROWS` in `plugin/bin/lib/driver/settle.js`; this table is copied by hand.

Under `--run --no-settle` none of the rows below runs, except the `pre-push` row's call 1: the driver still writes the escalation line (`Express lane: escalated #{n} to /flow`, through `express-lane.js escalate`) to the adopted run directory, unless `check` already wrote it (`step: check` and `checkLogged: true`). That is a write to dispatch's run directory, not teardown: the ordinary first call dispatch makes after `express-escalated` runs `/build`, whose already-shipped check reads that line (`hasEscalation`) and then judges against `origin/{integration-branch}` only, since the adopted worktree holds the driver worker's unmerged commits. If that call fails, the final line reads `blocked` (`settleRow: blocked`, `settleFailed: ["settle-escalate"]`) and the blocked row is left to the caller. The claim, the worktree, its branch and the run directory all stay for the caller, and so does the draft PR if there is one. The final line names the row the caller settles by (`settleRow`; `settle` is `left-to-caller` when that row has calls), and `stop.created` is all false because the driver created neither the worktree nor the branch.

| Stop | Settle calls, in order |
|---|---|
| `refused` | None. Nothing is written; the event names every reason. |
| `claim`, `claim-targets.js` exit 3 (held by another run or in flight) | None. The driver never held the claim, and a label would hide the other run's live claim. Outcome `blocked`; the event names the exit code. |
| `claim`, any other claim failure: a non-zero exit other than 3 (1, 2, 4, 5, 6, 7), an exit 0 that did not claim the record, a killed or timed-out run (`claim-exit-none`), or a failed run-directory mint | 1. one comment on the record naming the step and exit code; 2. `bot:blocked` added. No release call: no run directory exists, and `release-claim.js` needs `--run`. A claim that may have been written (exit 5, `claim-exit-none`, or a claim held when the mint failed) lapses by its TTL, and `settleNote` says so. A comment for a stop with no exit code (`claim-exit-none`, an exit 0 that did not claim, a failed mint) names none. |
| `pre-push` (`express-escalated`) | 1. `express-lane.js escalate` with the reason and a detail file, unless the stop is `check`'s own escalate verdict and `check` already wrote the line (`step: check` and `checkLogged: true`); 2. one comment on the record, ending with `<!-- express-driver: escalated -->`; 3. `release-claim.js`; 4. `git worktree remove --force --force` of the record's worktree, only when `stop.created.worktree` is true; 5. `git branch -D` of its local branch, only when `stop.created.branch` is true; 6. `hooks.js close-run --run {run-dir}`, so the run is no longer left active naming a removed worktree. The run directory stays: it holds the escalation line. If call 1 fails, calls 4, 5 and 6 do not run and the remaining calls are the `blocked` row's, so no work is discarded without an escalation on record. |
| `blocked`: a stop after the push, or a non-zero exit of `check` or `escalate` | 1. one comment on the PR, only when a PR exists; 2. one comment on the record, both naming the failed step; 3. `bot:blocked` added; 4. `release-claim.js` (no `--remove-grants`). The draft PR, branch and worktree stay. |
| `none` (`pending-review`) | None. The PR stays in draft for a human; the claim is left as it was. |

Notes:

- As a safety net, a `pre-push` stop is settled by the `blocked` row instead when `pushed` is true or `run-state.json` records a PR. No pre-push step stops after the push today (a failed `gh pr create` or `record-pr` is already class `blocked`), so this guards a misclassified or future step. An unreadable `run-state.json` on a pre-push stop is settled by the `blocked` row too, keeping the work, and sets `settleNote`.
- A stop class outside the table is settled by the `blocked` row and flagged `unclassified`.
- `git worktree remove` runs with `--force --force` because the driver creates the worktree locked. A worktree that is no longer registered is "already gone", not a failure; so is a branch that no longer exists.
- A `release-claim.js` exit 3 (already released) or 4 (held by another run) is not a failure.
- Comments and the escalate detail file are built from fixed templates. The worker, test and `check` detail is reduced first: allow-listed characters only, at most 200 characters, `@` neutralized, paths replaced by `<path>`, token-shaped strings by `<redacted>`, and `GH-N` and `www.` shapes split (`GH N`, `www `) so GitHub neither backlinks nor autolinks them. A bare host such as `evil.com` is left as is; GitHub links only `www.` and scheme forms.
- No settle call uses a model.

## After an interrupt

A run stopped by SIGINT or SIGTERM settles nothing, so the process exits promptly and never removes a worktree a worker may still be writing to. If the signal lands while settle is running, settle stops before its next call. The final line says `settle: interrupted`, and `settleFailed` names any settle calls that had already failed. The `outcome` word names the stop's class, not what landed: an interrupted pre-push stop wrote no escalation line. A record interrupted before its run directory existed has nothing to pass to `--run`; its claim lapses by its TTL.

Manual cleanup for an interrupted record:

- Release the claim: `node plugin/bin/release-claim.js {n} --run {run-dir} --reason interrupted`. The claim also lapses by its TTL.
- Remove the worktree and branch the run created: `git worktree remove --force --force {wt}`, then `git branch -D {branch}`. Or leave them for the standard path.
- If you removed the worktree, close the run: `node plugin/bin/hooks.js close-run --run {run-dir}`. Otherwise the run stays active, naming a worktree that is gone. This is the same call settle makes last on a pre-push stop.

## Taking an escalated record again

The pre-push escalation comment ends with the marker `<!-- express-driver: escalated -->`. Admission refuses a record that carries it in a comment from a trusted author (`already escalated by the driver`), so an escalated record goes to the standard path and is not driven again. To let the driver take it again, delete the comment carrying the marker. If the record's comments cannot be read, admission refuses (`record comments unreadable`). No label is added, and neither the prose express lane nor the standard path reads the marker.

## Worker rights

Per role (`plugin/bin/lib/driver/roles.js`); the launcher is `worker.js`.

- Tools: the implementer gets `Read`, `Write`, `Edit` and, on `darwin` only, `Bash`; the reviewer, explorer, `merge-check` and `acceptance` roles get `Read`, `Grep` and `Glob`.
- Every worker launches with `-p --safe-mode --restricted`, a short `--tools` list, `--disable-slash-commands`, `--strict-mcp-config` and `--permission-prompts none`. `--restricted` ignores user, project and local settings files and confines the file tools to the working directory. No role launches with a bypass flag, and rights are never widened after a denial; denials are data in the event line.
- The implementer's generated settings use `defaultMode: dontAsk` and an exact allow list: `Read`, `Edit` and `Write`, plus, on `darwin` only (the sandbox-probed platform), the test rule and read-only `git status`, `git diff`, `git log`, `git show` and `git ls-files`. The deny list names `gh`, `git push`, `git commit`, `git add`, `curl` and `wget`. The test rule is the project's declared targeted runner: `impact.command` from `origin/{ref}`'s `.claude-tweaks/verify-scope.json`, cut before its trailing ` {files}` (this repository: `node tools/run-tests.js --files-from`). It is read from the base by object id, never from the worker's copy, once per record, so it comes from project configuration, never from a record or a worker. With no usable declaration, or on a platform where the implementer has no Bash (where nothing is read), there is no test rule, and the prompt tells the worker not to run tests.
- Tests: the worker runs only the test files covering its change, listed in `.claude-tweaks/pipelines/worker-test-files.txt`, never the whole suite. The driver removes that file after each implementer launch, so it never blocks the worktree's removal; a removal that fails is noted in the step's `detail` and never stops the record. The driver's test step (`verify.js`, after the commit) is the gate: a red run there stops the record.
- Sandbox: on a probed platform (`darwin` today) the implementer runs inside the Bash sandbox with the network denied and writes confined to the working directory and the CLI's own scratch root. Reads are confined too (`permissions.blockReadsOutsideWorkingDirectories`, #5268): code the worker runs, such as its tests, can read only the working directory, the CLI's own carve-outs and the test command's toolchain. The launcher derives that toolchain at launch (`toolchainReadPaths` in `roles.js`: the install root above the command's `bin/`, plus the root of the interpreter its shebang names) and re-opens it through `sandbox.filesystem.allowRead`, never `/`, the home directory or an ancestor of it. On any other platform the implementer has no Bash at all.
- HEAD: the driver reads HEAD before and after every implementer launch (the implementer step and the review fix round alike). A worker launch after which HEAD has moved, by a commit or a reset, stops the record with status `fail`, naming both shas. A launch after which HEAD cannot be read stops it the same way, naming the earlier sha. When HEAD cannot be read before the launch, the worker is not launched at all: the record stops with status `fail`, naming no sha. A switch to another branch, or a detached HEAD, at the same commit is caught by the push guard's branch check: before pushing, the driver reads `refs/heads/{branch}` and stops the record with status `stop` (pre-push) when it is not the commit `check` verified, or when it cannot be read. An interrupt during the launch is reported as the interrupt. The driver never resets HEAD to recover.
- Index flags: once the worktree is created, the driver reads which paths the index flags (`git ls-files -v`), and it reads them again after each point where worker-written code has run: every implementer launch (the implementer step and the review fix round alike), the test step and every evidence run. A path flagged skip-worktree or assume-unchanged that was not flagged when the worktree was created stops the record with status `fail`, naming at most five of the new paths and their count. A read that fails stops it the same way. Flags present when the worktree is created, such as a sparse checkout's skip-worktree flags, never count, and a flag cleared since then is no stop. Every check compares with that first read, so a flag set between two check points, by a commit hook for example, is caught at the next one. The driver never clears a flag to recover. Before that first read, the driver refuses a worktree whose git config sets `core.ignoreStat` true, stopping the record with status `fail`: git would then mark every path the driver stages assume-unchanged, so the check would stop every record. A `core.ignoreStat` read that fails other than as not set stops it the same way. CI on push runs HEAD and remains the backstop for what this check cannot see, such as a `.gitattributes` filter, `core.fsmonitor`, or a path already flagged when the worktree is created, whose bytes code the driver runs can rewrite without the commit ever staging them.
- Tree after the tests: after the test step's `verify.js` run and its index-flag read, a run with red tests keeps its red-tests stop. For any other run, green or one that gave no verdict, the driver reads `git status` of the worktree, untracked files included. A tracked path that differs from HEAD, or an untracked file, stops the record with status `fail`, naming at most five of the paths and their count. Paths under `.claude-tweaks/pipelines/`, which the commit step also skips, never count, tracked or not. A read that fails stops it the same way, with a fixed detail. The driver's own `git commit` runs the project's git hooks, so a file a hook writes (a post-commit cache file that is not gitignored, say) is first seen by this check and reported as left after the test step. A verdict-less run's stop also names why the run gave no verdict. A newly set index flag outranks this stop. The review fix round's test run is checked the same way. The driver never cleans the tree to recover. Some changes are not caught: a change to an ignored file or an empty directory, which `git status` does not list; a rewrite of a tracked file under `.claude-tweaks/pipelines/`; and anything a red run left. CI on push runs HEAD and remains the backstop.
- Ceilings: `express-driver-wall-clock-minutes` and `express-driver-spend-ceiling-dollars` bound each worker launch, not the record: with the reviewer step on, a record can launch up to six workers (reviewer, implementer, relaunched implementer, fix implementer, and, when it merges, `merge-check` and `acceptance`; seven under the effort ladder, with a second relaunched implementer), each under the full ceilings, so the worst case is four implementer launches per record, the review fix round included (under the effort ladder; three otherwise); there is no run-wide budget. The launcher enforces the wall-clock ceiling by killing the worker (reason `wall-clock-ceiling`) and passes the spend ceiling as `--max-budget-usd` (reason `spend-ceiling`). Either is settled as a pre-push `express-error` for a pre-push launch. A judgment worker killed at a ceiling (envelope status `timeout` or `fail`), or whose launch throws, never reads as a pass: `merge-check` yields `needs-human` (logged as the verdict line, so the record ends `pending-review` / `verdict-not-confirmed`), and `acceptance` yields `completed: false` (`pending-review` / `acceptance-not-completed`). A spend overrun on a judgment worker that still returned a valid result is not read: the result is used as returned. A spend overrun reported after a normal return is named only in the final line (`spendOverrun`), and only for the implementer launches: a reviewer overrun reaches no line, though the `review` line's `costUsd` shows what the reviewer spent.
- The worker's own text is untrusted input; the driver takes the changed files from git, not from the worker.

## Worker models

Every driver worker launches with an explicit `--model`, never the account's default model (#5917). Policy key `express-driver-models` (`policy.yml` only; a `--run` config never sets it) is an indented block of `role: profile` rows over exactly four roles, with these defaults for a role left out:

| Role | Default |
|---|---|
| `implementer` | `implementer: standard` |
| `reviewer` | `reviewer: capable` |
| `merge-check` | `merge-check: standard` |
| `acceptance` | `acceptance: standard` |

The profile is `fast`, `standard`, `capable` or `frontier`. `explorer` is not a key: its `standard` default lives in `roles.js` (`DRIVER_ROLE_PROFILES`), and a row naming it, like any unknown role or profile, is a schema error. A block that sets one role keeps the other defaults (the merge is per role).

`launchTracked` (`plugin/bin/lib/driver/launch.js`) resolves the role's profile through `profiles.js` `resolve()` as an unattended launch and passes the result as `--model`. The `model-profiles` rows and `model-ceiling` apply, and a row's `effort` reaches the worker as `--effort` only under `model-effort: profile` (see "The `effort` field" below); `frontier` launches on the Capable model; `model-stance` and `frontier-run-cap` do not move a driver model.

**Refusal.** The policy step refuses the run (`refused`, before the claim) for an invalid `express-driver-models`, `model-profiles`, `model-ceiling` or `model-effort` (`driver model policy invalid: model-effort`; an unknown effort level in a `model-profiles` row refuses too, because `resolve()` throws on it), and for any role it cannot resolve, naming the key or the role. A malformed key the driver never reads (`frontier-run-cap`) refuses nothing. A refusal at launch time is an `Error` with code `DRIVER_MODEL_REFUSED` and a message that starts `no model for driver role {role}`. It throws before any process starts and is never retried on the account's default model. In the worker step it writes no `worker` line: the final line's `stop` names the step and the role. The `review` line, and the `merge-check` and `merge-acceptance` lines, name the code in `detail` on a refusal.

**The `model` field.** It names the requested alias, not what ran. The `worker`, `review`, `merge-check` and `merge-acceptance` lines carry it once a launch resolved a model, a launcher throw's `fail` line included; a line from before this change, or one whose launch never resolved a model, lacks it.

**The `effort` field.** The driver passes `--effort {level}` to a worker only when `model-effort: profile` is set and the role's resolution gives a level (`profiles.js` `resolve()`'s `launchEffort`; a Fast resolution gives none); under `implementer-tier: record` the implementer's level is then the effort ladder's, which can sit below its resolution's (see "Effort ladder (#6002)" below). `roles.js` refuses a level outside `low`, `medium`, `high`, `xhigh` and `max` before any process starts, since the CLI itself only warns on an unknown level. The driver resolves with the default stance (`launch.js` passes no `model-stance`), so a project's `model-stance` does not shift a driver worker's effort. The `worker`, `review`, `merge-check` and `merge-acceptance` lines carry `effort` beside `model`: the requested level, not what ran, and `null` when no flag was passed (key unset or `inherit`, or a Fast resolution; the two are indistinguishable by design). The review fix round's implementer relaunch writes its own `worker` line with `fix: true` and its own `effort`, before the `review` line, which names only the reviewer's; the station mirror maps a `fix: true` line to no station events. What a launch without the flag ran at is recorded in the `Launch effort (#5942)` bullet of `worker.js`'s module header, not here.

**Implementer tier (#5997).** Policy key `implementer-tier` (read through the same policy resolver as `express-driver-models`) is `lane` by default, which changes nothing. Under `record`, the implementer's first profile is the record rule's (`fast` for `size:low` with one or two Key Files, `standard` otherwise); `express-driver-models.implementer` is then not used for it, though still validated. It resolves through `resolve()`, so `model-profiles` and `model-ceiling` apply. The driver relaunches the implementer once (twice under the effort ladder, below), at `stepUp` of the first profile, after `cannot-complete` (no commit yet, the edits kept, the reason in the prompt) or red tests (on top of the first commit; the prompt carries the failing files and failure lines, capped at 20 files and 4 KB with a `[failure output truncated]` marker; a readable report that names no failing file sends the failure lines alone, without the failing-files heading; or fixed text when the report cannot be read). A relaunch writes its own `worker`, `commit` and `test` lines (`attempt` 2, `escalatedFrom`, `trigger`); `check` runs once, after the final test. There is no relaunch on a worker `fail`, at no step-up (`noRelaunch: 'no-step-up'`), or when `model-ceiling` clamps the step-up to the first model (`noRelaunch: 'clamped'`). A red run relaunches whether or not it changed the tree, and the relaunch commit stages what the test run wrote like any worker edit. A stepped-up profile that does not resolve is a refused relaunch (`DRIVER_MODEL_REFUSED`, no `worker` line, the detail names the relaunch). A second failure ends the record as one failure of that kind does, its detail carrying `after one relaunch (trigger, from to to)`; the relaunch commit's changed files are the union of both commits' paths, and after `cannot-complete` the PR summary is the relaunch's own while after `red-tests` the two concatenate. The fix round launches on the profile of the attempt that went green, so a record has at most three implementer launches (four under the effort ladder). The probe behind the `fast` default is in `worker.js`'s `Fast implementer (#5997)` header bullet; its numbers are not copied here.

**Effort ladder (#6002).** Under `implementer-tier: record` with `model-effort: profile`, the implementer climbs effort before profile. Its first launch starts at the record's effort: the first profile's level capped at `low` for `risk:low` and at `medium` for `risk:medium`, and the profile's own level for `risk:high` or no single valid `risk:` label, never above `high`. The first escalation steps effort one level on the same profile, and in the driver only for red tests, while the effort is below `high` (the standard lane, `nextAttempt`'s other caller, also steps effort for a failed fix-round re-review; the driver has no such trigger); `cannot-complete`, and any later escalation, steps the profile (`stepUp`) at that profile's own level, clamped to `high`. There are at most two escalations, so three implementer launches before the fix round: the first relaunch's `cannot-complete` or red tests queue the second, and a failure after it ends the record as one failure of that kind does, its detail carrying `after two relaunches (trigger, from to to; trigger, from to to)` with each side `{profile}@{effort}`. Each implementer `worker` line carries `attempt` (`1` to `3`) and its own `effort`; a profile step that would repeat the current model is `noRelaunch: 'clamped'`, and one from `capable` is `'no-step-up'`. The fix round launches on the profile and effort of the attempt that went green. Under `model-effort: inherit` the ladder is off: one relaunch, one profile up, no `effort` passed, and the note reads as above. The ceilings bound each launch, not the ladder. The probe behind starting `standard` at `low` is in `worker.js`'s `Standard implementer at low effort (#6002)` header bullet; its numbers are not copied here.
